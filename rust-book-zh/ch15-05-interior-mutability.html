Rust 程序设计语言

RefCell<T> 与内部可变性模式

内部可变性（interior mutability）是 Rust 中的一种设计模式，它允许你在存在指向数据的不可变引用时修改数据；通常情况下，借用规则是不允许这样做的。为了修改数据，该模式在数据结构内部使用 unsafe 代码来变通 Rust 中管理修改和借用的常规规则。unsafe 代码向编译器表明，我们在手动检查这些规则，而不是依赖编译器替我们检查；我们会在第 20 章进一步讨论 unsafe 代码。

只有当我们能够确保在运行时遵守借用规则时，才能使用那些运用了内部可变性模式的类型，即便编译器无法保证这一点。所涉及的 unsafe 代码会被封装在安全的 API 中，而外部类型仍然是不可变的。

让我们通过考察遵循内部可变性模式的 RefCell<T> 类型来探究这个概念。

在运行时强制执行借用规则

与 Rc<T> 不同，RefCell<T> 类型代表对其所存储数据的单一所有权。那么，是什么让 RefCell<T> 不同于 Box<T> 这样的类型呢？回想一下你在第 4 章学过的借用规则：

  • 在任意给定时刻，你要么只能有一个可变引用，要么只能有任意数量的不可变引用（但不能两者同时存在）。
  • 引用必须始终有效。

对于引用和 Box<T>，借用规则的这些不变量是在编译时强制执行的。而对于 RefCell<T>，这些不变量是在运行时强制执行的。对于引用，如果你违反了这些规则，会得到一个编译错误。而对于 RefCell<T>，如果你违反了这些规则，程序会 panic 并退出。

在编译时检查借用规则的优势在于，错误能在开发过程中更早地被发现，而且由于所有分析都已提前完成，不会对运行时性能产生任何影响。出于这些原因，在大多数情况下，在编译时检查借用规则都是最好的选择，这也是 Rust 将其作为默认行为的原因。

而在运行时检查借用规则的优势在于，某些内存安全的场景得以被允许，而这些场景原本会被编译时检查所禁止。像 Rust 编译器这样的静态分析本质上是保守的。代码的某些属性是不可能通过分析代码检测出来的：最著名的例子就是停机问题（Halting Problem），它超出了本书的范围，不过是一个值得研究的有趣话题。

因为有些分析是不可能完成的，所以如果 Rust 编译器无法确定代码是否遵守了所有权规则，它就可能会拒绝一个正确的程序；从这个意义上说，它是保守的。如果 Rust 接受了一个错误的程序，用户就无法信任 Rust 所做的保证了。然而，如果 Rust 拒绝了一个正确的程序，虽然会给程序员带来不便，但不会发生任何灾难性的后果。当你确信代码遵守了借用规则，而编译器无法理解和保证这一点时，RefCell<T> 类型就很有用了。

与 Rc<T> 类似，RefCell<T> 只能用于单线程场景，如果你尝试在多线程上下文中使用它，会得到一个编译时错误。我们会在第 16 章讨论如何在多线程程序中获得 RefCell<T> 的功能。

下面回顾一下选择 Box<T>、Rc<T> 或 RefCell<T> 的理由：

  • Rc<T> 允许同一数据有多个所有者；Box<T> 和 RefCell<T> 只有单一所有者。
  • Box<T> 允许在编译时检查的不可变借用或可变借用；Rc<T> 仅允许在编译时检查的不可变借用；RefCell<T> 允许在运行时检查的不可变借用或可变借用。
  • 因为 RefCell<T> 允许在运行时检查的可变借用，所以即便 RefCell<T> 本身是不可变的，你也可以修改其内部的值。

在不可变值的内部修改值，这就是内部可变性模式。让我们来看一个内部可变性能派上用场的场景，并研究它是如何实现的。

使用内部可变性

借用规则的一个推论是，当你有一个不可变值时，就不能以可变方式借用它。例如，下面这段代码无法编译：

fn main() {
    let x = 5;
    let y = &mut x;
}

如果尝试编译这段代码，你会得到如下错误：

$ cargo run
   Compiling borrowing v0.1.0 (file:///projects/borrowing)
error[E0596]: cannot borrow `x` as mutable, as it is not declared as mutable
 --> src/main.rs:3:13
  |
3 |     let y = &mut x;
  |             ^^^^^^ cannot borrow as mutable
  |
help: consider changing this to be mutable
  |
2 |     let mut x = 5;
  |         +++

For more information about this error, try `rustc --explain E0596`.
error: could not compile `borrowing` (bin "borrowing") due to 1 previous error

然而，在某些情况下，让一个值在其方法内部修改自身、而在其他代码看来却是不可变的，会很有用。值的方法之外的代码无法修改这个值。使用 RefCell<T> 是获得内部可变性能力的一种方式，但 RefCell<T> 并没有完全绕开借用规则：编译器中的借用检查器允许这种内部可变性，借用规则改为在运行时检查。如果你违反了这些规则，得到的将是一个 panic!，而不是编译错误。

让我们通过一个实际的例子，看看如何使用 RefCell<T> 来修改一个不可变值，以及为什么这样做很有用。

使用模拟对象进行测试

在测试过程中，程序员有时会用一个类型来代替另一个类型，以便观察特定的行为，并断言它被正确地实现了。这种占位类型被称为测试替身（test double）。可以从电影拍摄中“替身演员”的意义上来理解它：由另一个人代替演员来完成某个特别棘手的场景。在运行测试时，测试替身会代替其他类型。模拟对象（mock object）是一种特定类型的测试替身，它会记录测试过程中发生的事情，以便你断言正确的操作确实发生了。

Rust 中的对象与其他语言中的对象并不是同一个意义上的概念，Rust 的标准库也不像某些其他语言那样内置了模拟对象功能。不过，你完全可以创建一个结构体，让它起到与模拟对象相同的作用。

我们要测试的场景是这样的：我们将创建一个库，它会根据一个最大值来跟踪某个值，并根据当前值与最大值的接近程度发送消息。例如，这个库可以用来跟踪用户被允许调用 API 的次数配额。

我们的库只提供两项功能：跟踪一个值与最大值的接近程度，以及确定在什么时候应该发送什么消息。使用我们这个库的应用程序需要自行提供发送消息的机制：应用程序可以直接向用户显示消息、发送电子邮件、发送短信，或者做其他事情。库不需要知道这些细节。它只需要一个实现了我们所提供的名为 Messenger 的 trait 的东西。示例 15-20 展示了这个库的代码。

这段代码中重要的一点是，Messenger trait 有一个名为 send 的方法，它接受一个 self 的不可变引用以及消息文本。这个 trait 就是我们的模拟对象需要实现的接口，这样模拟对象就能以与真实对象相同的方式被使用。另一个重要的地方是，我们想要测试 LimitTracker 上 set_value 方法的行为。我们可以改变传给 value 参数的值，但 set_value 并不返回任何东西供我们进行断言。我们希望能够做到：如果用某个实现了 Messenger trait 的东西以及某个特定的 max 值创建一个 LimitTracker，那么当我们为 value 传入不同的数字时，messenger 会被告知发送相应的消息。

我们需要一个模拟对象，在我们调用 send 时，它不会发送电子邮件或短信，而只是记录它被告知要发送的消息。我们可以创建模拟对象的一个新实例，再创建一个使用该模拟对象的 LimitTracker，调用 LimitTracker 上的 set_value 方法，然后检查模拟对象中是否有我们期望的消息。示例 15-21 展示了实现这样一个模拟对象的尝试，但借用检查器不允许这样做。

这段测试代码定义了一个 MockMessenger 结构体，它有一个 sent_messages 字段，其类型为存储 String 值的 Vec，用来记录它被告知要发送的消息。我们还定义了一个关联函数 new，以便方便地创建一开始消息列表为空的新 MockMessenger 值。然后，我们为 MockMessenger 实现了 Messenger trait，这样就可以把一个 MockMessenger 交给 LimitTracker 了。在 send 方法的定义中，我们获取作为参数传入的消息，并把它存储到 MockMessenger 的 sent_messages 列表中。

在测试中，我们测试的是当 LimitTracker 被告知把 value 设置为超过 max 值 75% 的某个值时会发生什么。首先，我们创建一个新的 MockMessenger，它一开始的消息列表是空的。然后，我们创建一个新的 LimitTracker，并传给它这个新 MockMessenger 的引用以及 max 值 100。我们以值 80 调用 LimitTracker 上的 set_value 方法，这个值超过了 100 的 75%。接着，我们断言 MockMessenger 所记录的消息列表中现在应该有一条消息。

我们无法修改 MockMessenger 来记录消息，因为 send 方法接受的是 self 的不可变引用。我们也不能采纳错误信息中的建议，在 impl 方法和 trait 定义中都使用 &mut self。我们不希望仅仅为了测试而修改 Messenger trait。相反，我们需要找到一种方法，让测试代码在现有的设计下正确工作。

这正是内部可变性可以发挥作用的场景！我们将把 sent_messages 存储在一个 RefCell<T> 中，这样 send 方法就能修改 sent_messages，以存储我们见到的消息。示例 15-22 展示了具体的代码。

现在 sent_messages 字段的类型是 RefCell<Vec<String>>，而不是 Vec<String>。在 new 函数中，我们围绕空 vector 创建了一个新的 RefCell<Vec<String>> 实例。

对于 send 方法的实现，第一个参数仍然是 self 的不可变借用，这与 trait 的定义相符。我们对 self.sent_messages 中的 RefCell<Vec<String>> 调用 borrow_mut，以获取 RefCell<Vec<String>> 内部值（也就是那个 vector）的可变引用。然后，我们就可以对这个 vector 的可变引用调用 push，以记录测试期间发送的消息。

我们需要做的最后一处修改是在断言中：为了查看内部 vector 中有多少项，我们对 RefCell<Vec<String>> 调用 borrow，以获取这个 vector 的不可变引用。

现在你已经知道如何使用 RefCell<T> 了，让我们深入了解一下它的工作原理！

在运行时跟踪借用

在创建不可变引用和可变引用时，我们分别使用 & 和 &mut 语法。而对于 RefCell<T>，我们使用 borrow 和 borrow_mut 方法，它们是 RefCell<T> 所拥有的安全 API 的一部分。borrow 方法返回智能指针类型 Ref<T>，borrow_mut 方法返回智能指针类型 RefMut<T>。这两个类型都实现了 Deref，所以我们可以把它们当作普通引用来对待。

RefCell<T> 会记录当前有多少个处于活跃状态的 Ref<T> 和 RefMut<T> 智能指针。每次调用 borrow 时，RefCell<T> 都会把活跃的不可变借用计数加一。当一个 Ref<T> 值离开作用域时，不可变借用计数减一。就像编译时的借用规则一样，RefCell<T> 让我们在任意时刻可以拥有多个不可变借用或一个可变借用。

如果我们试图违反这些规则，我们不会像使用引用时那样得到编译错误，而是 RefCell<T> 的实现会在运行时 panic。示例 15-23 展示了对示例 15-22 中 send 实现的修改。我们故意尝试在同一作用域中创建两个活跃的可变借用，以说明 RefCell<T> 会在运行时阻止我们这样做。

我们为 borrow_mut 返回的 RefMut<T> 智能指针创建了一个变量 one_borrow。然后，以同样的方式在变量 two_borrow 中创建了另一个可变借用。这样就在同一作用域中产生了两个可变引用，这是不被允许的。当我们运行库的测试时，示例 15-23 中的代码可以编译通过，没有任何错误，但测试会失败：

注意，代码 panic 时给出的信息是 already borrowed: BorrowMutError。这就是 RefCell<T> 在运行时处理违反借用规则的情况的方式。

像我们这里所做的那样，选择在运行时而不是编译时捕获借用错误，意味着你可能会在开发过程的更晚阶段才发现代码中的错误：甚至可能要等到代码部署到生产环境之后。此外，由于是在运行时而不是编译时跟踪借用，代码还会付出少量的运行时性能代价。然而，使用 RefCell<T> 使得我们能够编写一个模拟对象，让它在只允许使用不可变值的上下文中也能修改自身，以记录它所见到的消息。尽管存在这些权衡，你仍然可以使用 RefCell<T> 来获得比普通引用更多的功能。

允许可变数据拥有多个所有者

RefCell<T> 的一种常见用法是与 Rc<T> 结合使用。回想一下，Rc<T> 允许某些数据拥有多个所有者，但它只提供对这些数据的不可变访问。如果你有一个存储了 RefCell<T> 的 Rc<T>，就可以得到一个既能拥有多个所有者又能被修改的值！

例如，回想一下示例 15-18 中的 cons list 示例，我们在那里使用 Rc<T> 让多个列表共享另一个列表的所有权。因为 Rc<T> 只存储不可变的值，所以一旦创建了列表中的值，就无法再修改它们。让我们加入 RefCell<T>，利用它来修改列表中的值。示例 15-24 展示了通过在 Cons 定义中使用 RefCell<T>，我们就能修改存储在所有列表中的值。

我们创建了一个 Rc<RefCell<i32>> 实例的值，并把它存储在一个名为 value 的变量中，以便稍后直接访问它。然后，我们在 a 中创建了一个 List，它的 Cons 变体存储了 value。我们需要克隆 value，这样 a 和 value 都能拥有内部值 5 的所有权，而不是把所有权从 value 转移给 a，或者让 a 从 value 借用。

我们把列表 a 包装在一个 Rc<T> 中，这样在创建列表 b 和 c 时，它们都可以引用 a，这和我们在示例 15-18 中所做的一样。

在创建了 a、b 和 c 中的列表之后，我们希望给 value 中的值加上 10。为此，我们对 value 调用 borrow_mut，这里用到了第 5 章“-> 运算符到哪去了？”中讨论过的自动解引用功能，将 Rc<T> 解引用为内部的 RefCell<T> 值。borrow_mut 方法返回一个 RefMut<T> 智能指针，我们对它使用解引用运算符并修改内部值。

当我们打印 a、b 和 c 时，可以看到它们的值都变成了修改后的 15，而不是 5：

$ cargo run
   Compiling cons-list v0.1.0 (file:///projects/cons-list)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.63s
     Running `target/debug/cons-list`
a after = Cons(RefCell { value: 15 }, Nil)
b after = Cons(RefCell { value: 3 }, Cons(RefCell { value: 15 }, Nil))
c after = Cons(RefCell { value: 4 }, Cons(RefCell { value: 15 }, Nil))

这个技巧非常巧妙！通过使用 RefCell<T>，我们得到了一个对外不可变的 List 值。但我们可以使用 RefCell<T> 上提供内部可变性访问的方法，在需要时修改数据。借用规则的运行时检查可以保护我们免受数据竞争的影响，而为了在数据结构中获得这种灵活性，有时牺牲一点速度是值得的。注意，RefCell<T> 不能用于多线程代码！Mutex<T> 是 RefCell<T> 的线程安全版本，我们会在第 16 章讨论 Mutex<T>。
