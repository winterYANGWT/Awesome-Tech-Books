Rust 程序设计语言

unsafe Rust

到目前为止，我们讨论过的所有代码都在编译时强制执行了 Rust 的内存安全保证。然而，Rust 内部还隐藏着另一种语言，它不会强制执行这些内存安全保证：它叫作 unsafe Rust（不安全的 Rust），用起来和常规 Rust 完全一样，但会赋予我们额外的超能力。

unsafe Rust 之所以存在，是因为静态分析本质上是保守的。当编译器试图判断代码是否维护了这些保证时，拒绝一些有效的程序要好过接受一些无效的程序。尽管代码可能没有问题，但只要 Rust 编译器没有足够的信息来确定这一点，它就会拒绝这段代码。在这些情况下，你可以使用不安全代码告诉编译器：“相信我，我知道自己在做什么。”不过要注意，使用 unsafe Rust 的风险由你自己承担：如果不正确地使用不安全代码，就可能因内存不安全而出现问题，比如解引用空指针。

Rust 之所以有一个不安全的“另一面”，另一个原因是底层的计算机硬件本质上就是不安全的。如果 Rust 不允许你执行不安全操作，有些任务你就无法完成。Rust 需要允许你进行底层系统编程，比如直接与操作系统交互，甚至编写你自己的操作系统。支持底层系统编程正是这门语言的目标之一。下面我们来探索可以用 unsafe Rust 做些什么，以及该怎么做。

施展不安全超能力

要切换到 unsafe Rust，需要使用 unsafe 关键字，然后开启一个新的块来存放不安全代码。在 unsafe Rust 中，你可以执行五种在安全 Rust 中无法执行的操作，我们称之为不安全超能力（unsafe superpowers）。这些超能力包括：

  1. 解引用裸指针。
  2. 调用不安全的函数或方法。
  3. 访问或修改可变静态变量。
  4. 实现不安全 trait。
  5. 访问 union 的字段。

需要明白的重要一点是，unsafe 并不会关闭借用检查器，也不会禁用 Rust 的任何其他安全检查：如果你在不安全代码中使用引用，它仍然会被检查。unsafe 关键字只是让你能够使用这五种特性，编译器不会对它们进行内存安全检查。在 unsafe 块内部，你仍然能获得一定程度的安全性。

此外，unsafe 并不意味着块中的代码一定是危险的，或者一定会有内存安全问题：其用意在于，由作为程序员的你来确保 unsafe 块中的代码会以有效的方式访问内存。

人难免会犯错，错误总会发生，但由于这五种不安全操作必须位于标注了 unsafe 的块中，你就能知道任何与内存安全相关的错误一定出在某个 unsafe 块里。请让 unsafe 块保持短小；以后排查内存 bug 时，你会庆幸自己这么做了。

为了尽可能地隔离不安全代码，最好将这类代码封装在一个安全抽象中，并提供安全的 API，本章稍后研究不安全函数和方法时会讨论这一点。标准库的一部分就是在经过审查的不安全代码之上实现的安全抽象。将不安全代码包装在安全抽象中，可以防止 unsafe 的使用蔓延到你或你的用户想要使用这些由 unsafe 代码实现的功能的每一个地方，因为使用安全抽象本身是安全的。

接下来我们依次看看这五种不安全超能力。我们还会看到一些为不安全代码提供安全接口的抽象。

解引用裸指针

在第 4 章“悬垂引用”部分中，我们提到编译器会确保引用总是有效的。unsafe Rust 有两种被称为裸指针（raw pointer）的新类型，它们与引用类似。和引用一样，裸指针也可以是不可变的或可变的，分别写作 *const T 和 *mut T。这里的星号不是解引用运算符，而是类型名称的一部分。在裸指针的语境下，不可变意味着指针在被解引用之后不能直接被赋值。

与引用和智能指针不同，裸指针：

  • 允许忽略借用规则，可以同时存在指向同一位置的不可变指针和可变指针，或者多个可变指针
  • 不保证指向有效的内存
  • 允许为空
  • 不实现任何自动清理

通过不让 Rust 强制执行这些保证，你可以放弃有保障的安全性，以换取更高的性能，或者换取与另一种语言或硬件交互的能力，因为在这些场合中 Rust 的保证并不适用。

注意，这段代码中并没有使用 unsafe 关键字。我们可以在安全代码中创建裸指针，只是不能在 unsafe 块之外解引用裸指针，稍后你就会看到这一点。

我们使用裸借用运算符创建了裸指针：&raw const num 会创建一个 *const i32 不可变裸指针，而 &raw mut num 会创建一个 *mut i32 可变裸指针。由于它们是直接从一个局部变量创建的，我们知道这两个裸指针是有效的，但并不能对任意一个裸指针都做出这样的假设。

为了说明这一点，接下来我们将创建一个无法如此确定其有效性的裸指针：这次使用关键字 as 对一个值进行类型转换，而不是使用裸借用运算符。示例 20-2 展示了如何创建一个指向内存中任意位置的裸指针。尝试使用任意内存的行为是未定义的：该地址上可能有数据，也可能没有；编译器可能会把代码优化得根本不访问内存；程序也可能因段错误（segmentation fault）而终止。通常没有充分的理由编写这样的代码，尤其是在可以改用裸借用运算符的情况下，但这么做确实是可能的。

回忆一下，我们可以在安全代码中创建裸指针，但不能解引用裸指针并读取其指向的数据。在示例 20-3 中，我们对裸指针使用了解引用运算符 *，这需要一个 unsafe 块。

创建一个指针并不会造成任何危害；只有当我们试图访问它所指向的值时，才可能会遇到无效的值。

还要注意，在示例 20-1 和示例 20-3 中，我们创建的 *const i32 和 *mut i32 两个裸指针都指向同一个内存位置，也就是存储 num 的地方。如果我们改为尝试创建 num 的一个不可变引用和一个可变引用，代码将无法编译，因为 Rust 的所有权规则不允许可变引用与任何不可变引用同时存在。而使用裸指针，我们可以创建指向同一位置的可变指针和不可变指针，并通过可变指针修改数据，这就可能造成数据竞争。务必小心！

既然有这么多危险，为什么还要使用裸指针呢？一个主要的使用场景是与 C 代码交互，你将在下一节中看到。另一个场景是构建借用检查器无法理解的安全抽象。我们先介绍不安全函数，然后看一个使用了不安全代码的安全抽象的示例。

调用不安全函数或方法

可以在 unsafe 块中执行的第二种操作是调用不安全函数。不安全函数和方法看起来与常规函数和方法完全一样，只是在定义的其余部分之前多了一个 unsafe。此处的 unsafe 关键字表示调用这个函数时有一些我们需要满足的要求，因为 Rust 无法保证我们已经满足了这些要求。在 unsafe 块中调用不安全函数，就表示我们已经阅读过这个函数的文档，并承担起遵守该函数契约的责任。

下面是一个名为 dangerous 的不安全函数，它的函数体中什么也没做：

fn main() {
    unsafe fn dangerous() {}

    unsafe {
        dangerous();
    }
}

我们必须在一个单独的 unsafe 块中调用 dangerous 函数。如果尝试在没有 unsafe 块的情况下调用 dangerous，就会得到一个错误：

$ cargo run
   Compiling unsafe-example v0.1.0 (file:///projects/unsafe-example)
error[E0133]: call to unsafe function `dangerous` is unsafe and requires unsafe block
 --> src/main.rs:4:5
  |
4 |     dangerous();
  |     ^^^^^^^^^^^ call to unsafe function
  |
  = note: consult the function's documentation for information on how to avoid undefined behavior

For more information about this error, try `rustc --explain E0133`.
error: could not compile `unsafe-example` (bin "unsafe-example") due to 1 previous error

通过 unsafe 块，我们是在向 Rust 断言：我们已经阅读了该函数的文档，理解如何正确地使用它，并且已经核实我们履行了该函数的契约。

要在 unsafe 函数的函数体中执行不安全操作，你仍然需要使用 unsafe 块，就像在常规函数中一样；如果你忘记了，编译器会发出警告。这有助于我们让 unsafe 块尽可能小，因为可能并不是整个函数体都需要执行不安全操作。

在不安全代码之上创建安全抽象

一个函数包含不安全代码，并不意味着我们需要将整个函数都标记为不安全的。事实上，将不安全代码包装在安全函数中是一种常见的抽象。作为例子，我们来研究一下标准库中的 split_at_mut 函数，它需要用到一些不安全代码。我们将探讨可以如何实现它。这个安全方法定义在可变切片上：它接受一个切片，并在作为参数传入的索引处将其拆分为两个切片。示例 20-4 展示了如何使用 split_at_mut。

仅使用安全 Rust 是无法实现这个函数的。一种尝试可能类似示例 20-5，但它无法编译。为简单起见，我们将 split_at_mut 实现为函数而不是方法，并且只针对 i32 值的切片，而不是泛型类型 T。

这个函数首先获取切片的总长度。然后，它通过检查作为参数传入的索引是否小于或等于长度，来断言该索引位于切片之内。这个断言意味着，如果我们传入一个大于长度的索引来拆分切片，函数会在尝试使用该索引之前 panic。

接着，我们在一个元组中返回两个可变切片：一个从原始切片的开头到索引 mid，另一个从 mid 到切片的末尾。

当我们尝试编译示例 20-5 中的代码时，会得到一个错误：

  |     --------------------------^^^^^^--------
  |     |     |                   |
  |     |     |                   second mutable borrow occurs here

For more information about this error, try `rustc --explain E0499`.
error: could not compile `unsafe-example` (bin "unsafe-example") due to 1 previous error

Rust 的借用检查器无法理解我们借用的是切片的不同部分；它只知道我们从同一个切片借用了两次。借用切片的不同部分从根本上说是没问题的，因为这两个切片并不重叠，但 Rust 还没有聪明到能看出这一点。当我们知道代码没问题而 Rust 并不知道时，就该求助于不安全代码了。

示例 20-6 展示了如何使用一个 unsafe 块、一个裸指针以及对不安全函数的一些调用，让 split_at_mut 的实现能够正常工作。

回忆一下第 4 章“切片类型”部分的内容：切片由一个指向某些数据的指针和切片的长度组成。我们使用 len 方法获取切片的长度，使用 as_mut_ptr 方法访问切片的裸指针。在本例中，由于我们有一个 i32 值的可变切片，as_mut_ptr 会返回一个类型为 *mut i32 的裸指针，我们将它存储在变量 ptr 中。

我们保留了 mid 索引位于切片之内的断言。接下来就是不安全代码：slice::from_raw_parts_mut 函数接受一个裸指针和一个长度，并创建一个切片。我们用这个函数创建一个从 ptr 开始、包含 mid 个元素的切片。然后，我们以 mid 作为参数调用 ptr 上的 add 方法，得到一个从 mid 开始的裸指针，再使用这个指针、以 mid 之后剩余的元素个数作为长度创建另一个切片。

slice::from_raw_parts_mut 函数是不安全的，因为它接受一个裸指针，并且必须相信这个指针是有效的。裸指针上的 add 方法也是不安全的，因为它必须相信偏移之后的位置同样是一个有效的指针。因此，我们必须在对 slice::from_raw_parts_mut 和 add 的调用外面套上一个 unsafe 块，才能调用它们。通过检查代码，并加上 mid 必须小于或等于 len 的断言，我们可以断定 unsafe 块中用到的所有裸指针都是指向切片内数据的有效指针。这是对 unsafe 的一种可接受且恰当的使用。

注意，我们不需要将最终得到的 split_at_mut 函数标记为 unsafe，并且可以在安全 Rust 中调用这个函数。我们为不安全代码创建了一个安全抽象，这个函数的实现以安全的方式使用了 unsafe 代码，因为它只会根据该函数有权访问的数据来创建有效的指针。

相比之下，示例 20-7 中对 slice::from_raw_parts_mut 的使用很可能会在使用该切片时崩溃。这段代码获取一个任意的内存位置，并创建了一个包含 10,000 个元素的切片。

我们并不拥有这个任意位置上的内存，也无法保证这段代码创建的切片包含有效的 i32 值。试图把 values 当作有效的切片来使用，会导致未定义行为。

使用 extern 函数调用外部代码

有时，你的 Rust 代码可能需要与用另一种语言编写的代码交互。为此，Rust 提供了 extern 关键字，用于创建和使用外部函数接口（Foreign Function Interface，FFI）。FFI 是一种让某种编程语言定义函数，并允许另一种（外部的）编程语言调用这些函数的方式。

示例 20-8 演示了如何集成 C 标准库中的 abs 函数。从 Rust 代码中调用在 extern 块中声明的函数通常是不安全的，因此 extern 块也必须标记为 unsafe。原因在于，其他语言并不会强制执行 Rust 的规则和保证，而 Rust 也无法检查它们，所以确保安全的责任就落在了程序员身上。

在 unsafe extern "C" 块中，我们列出了想要调用的、来自另一种语言的外部函数的名称和签名。"C" 部分定义了外部函数所使用的应用二进制接口（application binary interface，ABI）：ABI 定义了如何在汇编层面调用函数。"C" ABI 是最常见的 ABI，它遵循 C 编程语言的 ABI。有关 Rust 支持的所有 ABI 的信息，请参阅 Rust 参考手册。

在 unsafe extern 块中声明的每一项都隐式地是不安全的。不过，有些 FFI 函数调用起来确实是安全的。例如，C 标准库中的 abs 函数不涉及任何内存安全方面的问题，而且我们知道可以用任意 i32 来调用它。在这类情况下，我们可以使用 safe 关键字来表明：尽管这个特定的函数位于 unsafe extern 块中，调用它也是安全的。做出这一修改后，调用它就不再需要 unsafe 块了，如示例 20-9 所示。

将函数标记为 safe 并不会让它本身变得安全！这更像是你向 Rust 做出的一个承诺，保证它是安全的。确保这个承诺得到兑现，仍然是你的责任！

从其他语言调用 Rust 函数

我们也可以使用 extern 来创建一个接口，让其他语言能够调用 Rust 函数。这时不需要创建整个 extern 块，而是在相关函数的 fn 关键字之前加上 extern 关键字并指定要使用的 ABI。我们还需要添加 #[unsafe(no_mangle)] 注解，告诉 Rust 编译器不要对这个函数的名称进行修饰。名称修饰（mangling）是指编译器将我们给函数起的名字改成另一个名字，新名字包含了更多供编译过程的其他环节使用的信息，但对人来说更难读懂。每种编程语言的编译器修饰名称的方式都略有不同，因此为了让其他语言能够通过名字引用 Rust 函数，我们必须禁用 Rust 编译器的名称修饰。这样做是不安全的，因为缺少内置的名称修饰，不同的库之间可能会发生名称冲突，所以我们有责任确保所选的名称在不经修饰的情况下导出是安全的。

在下面的例子中，我们让 call_from_c 函数在被编译为共享库并从 C 链接之后，能够被 C 代码访问：

#[unsafe(no_mangle)]
pub extern "C" fn call_from_c() {
    println!("Just called a Rust function from C!");
}

extern 的这种用法只需要在属性中使用 unsafe，而不需要在 extern 块上使用。

访问或修改可变静态变量

在本书中，我们还没有讨论过全局变量。Rust 确实支持全局变量，但它们可能会与 Rust 的所有权规则产生冲突。如果两个线程访问同一个可变全局变量，就可能导致数据竞争。

在 Rust 中，全局变量被称为静态（static）变量。示例 20-10 展示了一个以字符串切片为值的静态变量的声明和使用示例。

静态变量与常量类似，我们在第 3 章“声明常量”部分讨论过常量。按照惯例，静态变量的名称采用 SCREAMING_SNAKE_CASE 形式。静态变量只能存储具有 'static 生命周期的引用，这意味着 Rust 编译器能够自行推断出生命周期，我们不需要显式地标注它。访问不可变静态变量是安全的。

常量与不可变静态变量之间有一个细微的区别：静态变量中的值在内存中拥有固定的地址，使用这个值时总是会访问同一份数据。而常量则允许在每次被使用时复制其数据。另一个区别是静态变量可以是可变的。访问和修改可变静态变量是不安全的。示例 20-11 展示了如何声明、访问和修改一个名为 COUNTER 的可变静态变量。

与常规变量一样，我们使用 mut 关键字来指定可变性。任何读写 COUNTER 的代码都必须位于 unsafe 块中。示例 20-11 中的代码可以编译，并如我们所料打印出 COUNTER: 3，因为它是单线程的。如果有多个线程访问 COUNTER，很可能会导致数据竞争，因此这属于未定义行为。所以，我们需要将整个函数标记为 unsafe，并在文档中说明其安全限制，让任何调用该函数的人都知道哪些事情可以安全地做、哪些不可以。

每当我们编写一个不安全函数时，惯用的做法是写一条以 SAFETY 开头的注释，说明调用者需要做些什么才能安全地调用该函数。同样，每当我们执行一个不安全操作时，惯用的做法是写一条以 SAFETY 开头的注释，解释安全规则是如何得到维护的。

此外，编译器默认会通过一个编译器 lint 拒绝任何创建指向可变静态变量的引用的尝试。你要么通过添加 #[allow(static_mut_refs)] 注解显式地放弃该 lint 的保护，要么通过某个裸借用运算符创建的裸指针来访问可变静态变量。这也包括引用被隐式创建的情况，比如在这个代码示例的 println! 中使用它时。要求通过裸指针来创建指向可变静态变量的引用，有助于让使用它们时的安全要求更加显而易见。

对于可以全局访问的可变数据，很难确保不存在数据竞争，这就是 Rust 认为可变静态变量不安全的原因。在可能的情况下，最好使用我们在第 16 章讨论过的并发技术和线程安全的智能指针，这样编译器就能检查来自不同线程的数据访问是否安全。

实现不安全 trait

我们可以使用 unsafe 来实现一个不安全 trait。当一个 trait 中至少有一个方法带有编译器无法验证的某种不变量（invariant）时，这个 trait 就是不安全的。要声明一个 trait 是 unsafe 的，我们需要在 trait 之前加上 unsafe 关键字，并且同样将该 trait 的实现标记为 unsafe，如示例 20-12 所示。

通过使用 unsafe impl，我们承诺会维护那些编译器无法验证的不变量。

举个例子，回忆一下我们在第 16 章“使用 Send 和 Sync 实现可扩展的并发”部分讨论过的 Send 和 Sync 标记 trait：如果我们的类型完全由其他实现了 Send 和 Sync 的类型组成，编译器就会自动为它实现这两个 trait。如果我们实现的类型包含了某个没有实现 Send 或 Sync 的类型（比如裸指针），而我们又想把该类型标记为 Send 或 Sync，就必须使用 unsafe。Rust 无法验证我们的类型是否满足“可以安全地跨线程发送或从多个线程访问”的保证；因此，我们需要手动进行这些检查，并通过 unsafe 表明这一点。

访问联合体的字段

最后一种只能在 unsafe 中进行的操作是访问联合体的字段。联合体（union）类似于 struct，但在某个特定的实例中，同一时刻只会使用其中一个已声明的字段。联合体主要用于与 C 代码中的联合体交互。访问联合体的字段是不安全的，因为 Rust 无法保证当前存储在联合体实例中的数据是什么类型。你可以在 Rust 参考手册中进一步了解联合体。

使用 Miri 检查不安全代码

在编写不安全代码时，你可能想要检查自己写的代码是否真的安全且正确。最好的方法之一是使用 Miri，这是一个用于检测未定义行为的 Rust 官方工具。借用检查器是在编译时工作的静态工具，而 Miri 则是在运行时工作的动态工具。它通过运行你的程序或测试套件来检查代码，并检测你何时违反了它所理解的 Rust 应当如何运作的规则。

使用 Miri 需要 Rust 的 nightly 构建版本（我们会在附录 G：Rust 是如何开发的与“Nightly Rust”中进一步讨论）。你可以通过输入 rustup +nightly component add miri 来同时安装 nightly 版本的 Rust 和 Miri 工具。这不会改变你的项目所使用的 Rust 版本；它只是把这个工具添加到你的系统中，以便你在需要时使用。你可以通过输入 cargo +nightly miri run 或 cargo +nightly miri test 在项目上运行 Miri。

Miri 正确地警告我们正在将整数转换为指针，这可能是个问题，但 Miri 无法确定是否真的存在问题，因为它不知道这个指针是从哪里来的。接着，Miri 在示例 20-7 存在未定义行为的地方返回了一个错误，因为我们有一个悬垂指针。多亏了 Miri，我们现在知道存在未定义行为的风险，并可以思考如何让代码变得安全。在某些情况下，Miri 甚至能就如何修复错误给出建议。

Miri 并不能捕获你在编写不安全代码时可能犯下的所有错误。Miri 是一个动态分析工具，所以它只能捕获实际运行到的代码中的问题。这意味着你需要将它与良好的测试技术结合使用，才能增强你对所编写的不安全代码的信心。Miri 也无法覆盖代码可能不健全（unsound）的所有情形。

换句话说：如果 Miri 确实发现了问题，你就知道存在 bug；但 Miri 没有发现 bug，并不意味着就没有问题。不过，它能发现的问题已经很多了。试着在本章其他的不安全代码示例上运行它，看看它会说些什么吧！

正确使用不安全代码

使用 unsafe 来施展刚才讨论的五种超能力之一并没有错，甚至也不会招人反感，但要写出正确的 unsafe 代码会更加棘手，因为编译器无法帮你维护内存安全。当你有理由使用 unsafe 代码时，就可以使用它，而显式的 unsafe 标注能让你在问题发生时更容易追踪到问题的根源。每当你编写不安全代码时，都可以借助 Miri 来更有把握地确认你编写的代码遵守了 Rust 的规则。

要更深入地了解如何高效地使用 unsafe Rust，请阅读 Rust 关于 unsafe 的官方指南《The Rustonomicon》。
