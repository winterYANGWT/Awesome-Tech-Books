Rust 程序设计语言

future 与 async 语法

Rust 异步编程的核心要素是 future，以及 Rust 的 async 和 await 关键字。

future 是一个现在可能还没有就绪、但在未来某个时刻会就绪的值。（同样的概念在许多语言中都有出现，有时会以 task 或 promise 等其他名字出现。）Rust 提供了一个 Future trait 作为基础构件，这样不同的异步操作就可以用不同的数据结构来实现，同时拥有统一的接口。在 Rust 中，future 就是实现了 Future trait 的类型。每个 future 都保存着它自身的信息：已经取得了多少进展，以及“就绪”意味着什么。

你可以把 async 关键字应用于代码块和函数，表明它们可以被中断和恢复。在 async 块或 async 函数中，你可以使用 await 关键字来等待一个 future（await a future，也就是等它变为就绪）。在 async 块或函数中等待 future 的每一个位置，都是该块或函数可能暂停和恢复的地方。向 future 查询其值是否已经可用的过程称为轮询（polling）。

其他一些语言，比如 C# 和 JavaScript，也使用 async 和 await 关键字进行异步编程。如果你熟悉这些语言，可能会注意到 Rust 在处理这套语法上有一些显著的不同。我们后面会看到，这么做是有充分理由的！

编写异步 Rust 代码时，我们在大多数情况下使用的是 async 和 await 关键字。Rust 会把它们编译成使用 Future trait 的等价代码，就像它把 for 循环编译成使用 Iterator trait 的等价代码一样。不过，由于 Rust 提供了 Future trait，你在需要时也可以为自己的数据类型实现它。本章中我们会看到的许多函数，其返回类型都有自己的 Future 实现。我们会在本章末尾回过头来看这个 trait 的定义，并深入探究它是如何工作的，但目前这些细节已经足够让我们继续前进了。

这些内容可能感觉有点抽象，所以让我们来编写第一个异步程序：一个小型网页抓取器。我们会从命令行传入两个 URL，并发地抓取它们，然后返回先完成的那个的结果。这个例子会涉及不少新语法，不过别担心——我们会边写边解释你需要知道的一切。

我们的第一个异步程序

为了让本章的重点放在学习 async 上，而不是在生态系统的各个部分之间疲于应付，我们创建了 trpl crate（trpl 是“The Rust Programming Language”的缩写）。它重导出了你需要的所有类型、trait 和函数，主要来自 futures 和 tokio 这两个 crate。futures crate 是 Rust 异步代码实验的官方大本营，Future trait 最初实际上就是在那里设计出来的。Tokio 是如今 Rust 中使用最广泛的异步运行时，尤其是在 Web 应用领域。当然，还有其他很棒的运行时，它们可能更适合你的需求。我们在 trpl 的底层使用 tokio crate，是因为它经过了充分的测试，而且被广泛使用。

在某些情况下，trpl 还会重命名或包装原始的 API，好让你专注于与本章相关的细节。如果你想了解这个 crate 做了什么，我们鼓励你去看看它的源代码。你可以看到每个重导出的项来自哪个 crate，而且我们留下了大量注释来解释这个 crate 做了什么。

创建一个名为 hello-async 的新二进制项目，并添加 trpl crate 作为依赖：

$ cargo new hello-async
$ cd hello-async
$ cargo add trpl

现在，我们可以使用 trpl 提供的各种组件来编写第一个异步程序了。我们将构建一个小型命令行工具，它会抓取两个网页，从每个网页中提取 <title> 元素，并打印出先完成整个过程的那个页面的标题。

定义 page_title 函数

我们先来编写一个函数，它接受一个页面 URL 作为参数，向其发出请求，并返回 <title> 元素的文本（见示例 17-1）。

首先，我们定义一个名为 page_title 的函数，并用 async 关键字标记它。然后我们使用 trpl::get 函数抓取传入的 URL，并加上 await 关键字来等待响应。为了获取 response 的文本，我们调用它的 text 方法，并再次用 await 关键字等待它。这两个步骤都是异步的。对于 get 函数，我们必须等待服务器发回响应的第一部分，其中包括 HTTP 头、cookie 等，这部分可以与响应体分开发送。尤其是在响应体非常大的时候，它可能需要一段时间才能全部到达。因为我们必须等待整个响应到达，所以 text 方法也是异步的。

我们必须显式地等待这两个 future，因为 Rust 中的 future 是惰性的（lazy）：在你用 await 关键字要求它们之前，它们什么也不会做。（事实上，如果你没有使用某个 future，Rust 会给出一个编译器警告。）这可能会让你想起第 13 章“使用迭代器处理一系列元素”部分中对迭代器的讨论。除非你调用迭代器的 next 方法——无论是直接调用，还是通过 for 循环或 map 等在底层使用 next 的方法——否则迭代器什么也不会做。同样，除非你显式地要求，否则 future 也什么都不会做。这种惰性让 Rust 可以在真正需要之前避免运行异步代码。

注意：这与我们在第 16 章“使用 spawn 创建新线程”部分中使用 thread::spawn 时看到的行为不同，在那里，我们传递给另一个线程的闭包会立即开始运行。这也与许多其他语言处理异步的方式不同。但这对于 Rust 能够提供其性能保证非常重要，就像迭代器的情况一样。

拿到 response_text 之后，我们就可以使用 Html::parse 把它解析成 Html 类型的实例。现在我们拥有的不再是一个原始字符串，而是一个可以把 HTML 当作更丰富的数据结构来处理的数据类型。特别是，我们可以使用 select_first 方法来查找给定 CSS 选择器的第一个匹配实例。通过传入字符串 "title"，我们会得到文档中的第一个 <title> 元素（如果有的话）。由于可能没有任何匹配的元素，select_first 返回一个 Option<ElementRef>。最后，我们使用 Option::map 方法，它让我们在 Option 中有值时处理该值，没有值时则什么也不做。（这里我们也可以使用 match 表达式，但 map 更符合惯用写法。）在提供给 map 的函数体中，我们对 title 调用 inner_html 来获取它的内容，这个内容是一个 String。最终，我们得到一个 Option<String>。

注意，Rust 的 await 关键字放在你要等待的表达式之后，而不是之前。也就是说，它是一个后缀（postfix）关键字。如果你在其他语言中用过 async，这可能和你习惯的不一样，但在 Rust 中，这让方法链用起来顺手得多。因此，我们可以修改 page_title 的函数体，把 trpl::get 和 text 函数调用链接在一起，并在它们之间使用 await，如示例 17-2 所示。

这样，我们就成功编写了第一个异步函数！在 main 中添加调用它的代码之前，我们再多谈谈我们写下的代码以及它的含义。

当 Rust 看到一个用 async 关键字标记的代码块时，会把它编译成一个独一无二的、实现了 Future trait 的匿名数据类型。当 Rust 看到一个用 async 标记的函数时，会把它编译成一个非异步函数，其函数体是一个 async 块。异步函数的返回类型，就是编译器为该 async 块创建的匿名数据类型。

因此，编写 async fn 等价于编写一个返回其返回类型的 future 的函数。对编译器来说，像示例 17-1 中 async fn page_title 这样的函数定义，大致等价于如下定义的非异步函数：

#![allow(unused)]
fn main() {
extern crate trpl; // required for mdbook test
use std::future::Future;
use trpl::Html;

fn page_title(url: &str) -> impl Future<Output = Option<String>> {
    async move {
        let text = trpl::get(url).await.text().await;
        Html::parse(&text)
            .select_first("title")
            .map(|title| title.inner_html())
    }
}
}

让我们逐一看看转换后版本的各个部分：

  • 它使用了我们在第 10 章“使用 trait 作为参数”部分中讨论过的 impl Trait 语法。
  • 返回值实现了 Future trait，其关联类型为 Output。注意，Output 类型是 Option<String>，与 async fn 版本的 page_title 原本的返回类型相同。
  • 原函数体中调用的所有代码都被包裹在一个 async move 块中。记住，代码块是表达式。整个代码块就是函数返回的表达式。
  • 正如刚才所说，这个 async 块产生一个类型为 Option<String> 的值。这个值与返回类型中的 Output 类型相匹配。这和你见过的其他代码块是一样的。
  • 新的函数体之所以是一个 async move 块，是由它使用 url 参数的方式决定的。（本章后面我们会详细讨论 async 与 async move 的区别。）

现在我们可以在 main 中调用 page_title 了。

用运行时执行异步函数

首先，我们来获取单个页面的标题，如示例 17-3 所示。遗憾的是，这段代码目前还无法编译。

我们沿用了第 12 章“接受命令行参数”部分中获取命令行参数的模式。然后，我们把 URL 参数传给 page_title 并等待结果。由于这个 future 产生的值是 Option<String>，我们使用 match 表达式，根据页面是否有 <title> 打印不同的消息。

我们只能在异步函数或 async 块中使用 await 关键字，而 Rust 不允许我们把特殊的 main 函数标记为 async。

error[E0752]: `main` function is not allowed to be `async`
 --> src/main.rs:6:1
  |
6 | async fn main() {
  | ^^^^^^^^^^^^^^^ `main` function is not allowed to be `async`

main 之所以不能被标记为 async，是因为异步代码需要一个运行时（runtime）：一个负责管理异步代码执行细节的 Rust crate。程序的 main 函数可以初始化一个运行时，但它本身并不是运行时。（稍后我们会进一步了解为什么会这样。）每个执行异步代码的 Rust 程序，都至少有一处设置了用来执行 future 的运行时。

大多数支持异步的语言都会自带一个运行时，但 Rust 没有。相反，Rust 有许多不同的异步运行时可供选择，每一个都针对其目标用例做出了不同的权衡。例如，一个拥有许多 CPU 核心和大量内存的高吞吐量 Web 服务器，与一个只有单个核心、少量内存且无法进行堆分配的微控制器，二者的需求截然不同。提供这些运行时的 crate 通常还会提供常用功能的异步版本，比如文件或网络 I/O。

在这里以及本章余下的部分中，我们会使用 trpl crate 中的 block_on 函数，它接受一个 future 作为参数，并阻塞当前线程，直到这个 future 运行完成。在幕后，调用 block_on 会使用 tokio crate 设置一个运行时，用来运行传入的 future（trpl crate 的 block_on 的行为与其他运行时 crate 中的 block_on 函数类似）。一旦 future 完成，block_on 就会返回该 future 产生的值。

我们可以把 page_title 返回的 future 直接传给 block_on，等它完成后，再像示例 17-3 中尝试的那样对得到的 Option<String> 进行匹配。不过，在本章的大多数示例中（以及现实世界中的大多数异步代码中），我们要做的不只是一次异步函数调用，因此我们会传入一个 async 块，并在其中显式地等待 page_title 调用的结果，如示例 17-4 所示。

呼——我们终于有了一些能运行的异步代码！不过，在添加让两个网站相互竞速的代码之前，我们先简单地把注意力转回到 future 的工作原理上。

每一个 await 点（await point）——也就是代码中使用 await 关键字的每一个位置——都代表着一个把控制权交还给运行时的地方。为了让这一切能够运作，Rust 需要跟踪 async 块中涉及的状态，这样运行时就可以先去启动其他一些工作，等到准备好再次尝试推进第一个工作时，再回来继续。这是一个看不见的状态机，就好像你编写了下面这样一个枚举，用来保存每个 await 点处的当前状态：

#![allow(unused)]
fn main() {
extern crate trpl; // required for mdbook test

enum PageTitleFuture<'a> {
    Initial { url: &'a str },
    GetAwaitPoint { url: &'a str },
    TextAwaitPoint { response: trpl::Response },
}
}

然而，手动编写在各个状态之间转换的代码既繁琐又容易出错，尤其是当你以后需要给代码添加更多功能和更多状态的时候。幸运的是，Rust 编译器会自动为异步代码创建和管理状态机的数据结构。围绕数据结构的常规借用和所有权规则依然全部适用，令人高兴的是，编译器同样会替我们检查这些规则，并提供有用的错误信息。本章后面我们会处理其中的几个错误。

归根结底，总得有某个东西来执行这个状态机，而这个东西就是运行时。（这就是为什么你在了解运行时的时候可能会碰到执行器（executor）这个说法：执行器是运行时中负责执行异步代码的那部分。）

现在你就能明白，为什么在示例 17-3 中编译器不允许我们把 main 本身变成一个异步函数了。如果 main 是一个异步函数，就需要由别的东西来管理 main 所返回的 future 的状态机，可 main 是程序的起点啊！因此，我们在 main 中调用 trpl::block_on 函数来设置一个运行时，并运行 async 块返回的 future，直到它完成为止。

注意：有些运行时提供了宏，让你可以编写异步的 main 函数。这些宏会把 async fn main() { ... } 改写成普通的 fn main，其做法与我们在示例 17-4 中手动完成的一样：调用一个函数，像 trpl::block_on 那样把一个 future 运行至完成。

现在，让我们把这些部分组合起来，看看如何编写并发代码。

让两个 URL 并发竞速

在示例 17-5 中，我们使用从命令行传入的两个不同 URL 调用 page_title，并通过选出先完成的那个 future 来让它们竞速。

我们首先对用户提供的每个 URL 调用 page_title，并把得到的 future 分别保存为 title_fut_1 和 title_fut_2。记住，它们目前还什么都不会做，因为 future 是惰性的，而我们还没有等待它们。接着，我们把这两个 future 传给 trpl::select，它会返回一个值，表明传入的 future 中哪一个先完成。

注意：在底层，trpl::select 是基于 futures crate 中定义的一个更通用的 select 函数构建的。futures crate 的 select 函数能做很多 trpl::select 函数做不到的事情，但它也带来了一些额外的复杂性，我们暂时可以略过不谈。

两个 future 都有可能合理地“胜出”，因此返回一个 Result 并不合适。取而代之的是，trpl::select 返回一个我们之前没见过的类型：trpl::Either。Either 类型和 Result 有点类似，因为它也有两种情况。不过，与 Result 不同的是，Either 中并没有内置成功或失败的概念。它使用 Left 和 Right 来表示“二者之一”：

#![allow(unused)]
fn main() {
enum Either<A, B> {
    Left(A),
    Right(B),
}
}

如果第一个参数胜出，select 函数会返回包含该 future 输出的 Left；如果第二个 future 参数胜出，则返回包含它的输出的 Right。这与调用函数时参数出现的顺序一致：第一个参数位于第二个参数的左边。

我们还修改了 page_title，让它同时返回传入的那个 URL。这样，即使先返回的页面没有可供我们解析的 <title>，我们仍然可以打印出有意义的信息。有了这些信息之后，最后我们更新 println! 的输出，既指出哪个 URL 先完成，也显示该 URL 对应网页的 <title>（如果有的话）。

现在，你已经构建了一个能正常工作的小型网页抓取器！挑几个 URL 运行一下这个命令行工具吧。你可能会发现，有些网站总是比其他网站快，而在另一些情况下，哪个网站更快则每次运行都不一样。更重要的是，你已经学会了使用 future 的基础知识，现在我们可以更深入地探究 async 能做些什么了。
