使用消息传递在线程间传送数据

一种日益流行的确保并发安全的方式是消息传递，即线程或 actor 之间通过相互发送包含数据的消息来进行通信。Go 语言文档中有一句口号很好地概括了这种思想：“不要通过共享内存来通信；而要通过通信来共享内存。”

为了实现基于消息发送的并发，Rust 标准库提供了通道（channel）的实现。通道是一个通用的编程概念，数据通过它从一个线程发送到另一个线程。

你可以把编程中的通道想象成一条有方向的水道，比如一条小溪或一条河流。如果你把橡皮鸭之类的东西放进河里，它就会顺流而下，一直漂到水道的尽头。

通道由两部分组成：发送端（transmitter）和接收端（receiver）。发送端就是你把橡皮鸭放进河里的上游位置，接收端则是橡皮鸭最终抵达的下游位置。代码的一部分调用发送端的方法并传入想要发送的数据，另一部分则检查接收端是否有消息到达。当发送端或接收端中的任何一方被丢弃时，就称这个通道被关闭（closed）了。

接下来，我们会逐步编写一个程序：其中一个线程生成值并通过通道发送出去，另一个线程接收这些值并将其打印出来。我们会使用通道在线程间发送一些简单的值来演示这一功能。一旦你熟悉了这项技术，就可以将通道用于任何需要相互通信的线程，比如聊天系统，或者一个由多个线程分别执行计算的一部分、再把各部分结果发送给一个线程进行汇总的系统。

首先，在示例 16-6 中，我们会创建一个通道，但不用它做任何事情。注意，这段代码现在还无法编译，因为 Rust 无法知道我们想通过通道发送什么类型的值。

我们使用 mpsc::channel 函数创建一个新的通道；mpsc 是多生产者，单消费者（multiple producer, single consumer）的缩写。简而言之，Rust 标准库实现通道的方式意味着一个通道可以有多个产生值的发送端，但只能有一个消费这些值的接收端。想象一下多条小溪汇入一条大河：沿着任何一条小溪漂下的东西，最终都会汇入同一条河。我们现在先从单个生产者开始，等这个例子能正常运行后，再添加多个生产者。

mpsc::channel 函数返回一个元组，其第一个元素是发送的一端，即发送端；第二个元素是接收的一端，即接收端。在很多领域中，tx 和 rx 传统上分别是 transmitter（发送端）和 receiver（接收端）的缩写，所以我们用这两个名字来命名变量，以表示通道的两端。我们使用了带有模式的 let 语句来解构元组；我们会在第 19 章讨论在 let 语句中使用模式以及解构。目前只需知道，以这种方式使用 let 语句，可以方便地提取出 mpsc::channel 返回的元组中的各个部分。

我们把发送端移动到一个新建线程中，并让它发送一个字符串，这样新建线程就可以和主线程通信了，如示例 16-7 所示。这就像是在河流上游放入一只橡皮鸭，或者从一个线程向另一个线程发送一条聊天消息。

我们再次使用 thread::spawn 来创建一个新线程，然后使用 move 把 tx 移动到闭包中，这样新建线程就拥有了 tx。新建线程需要拥有发送端，才能通过通道发送消息。

发送端有一个 send 方法，它接受我们想要发送的值。send 方法返回一个 Result<T, E> 类型，所以如果接收端已经被丢弃、值无处可发，发送操作就会返回一个错误。在这个例子中，我们调用了 unwrap，在出错时直接 panic。但在实际的应用程序中，我们应当妥善地处理错误：可以回顾第 9 章，复习一下恰当处理错误的策略。

在示例 16-8 中，我们会在主线程中从接收端获取值。这就像是在河流的尽头从水中捞起橡皮鸭，或者接收一条聊天消息。

接收端有两个很有用的方法：recv 和 try_recv。这里我们使用的是 recv，它是 receive（接收）的缩写，它会阻塞主线程的执行，一直等到有值通过通道发送过来。一旦有值被发送过来，recv 就会以 Result<T, E> 的形式返回它。当发送端关闭时，recv 会返回一个错误，表示不会再有更多的值到来了。

try_recv 方法不会阻塞，而是会立即返回一个 Result<T, E>：如果有可用的消息，就返回一个包含该消息的 Ok 值；如果此时没有任何消息，就返回一个 Err 值。如果线程在等待消息的同时还有其他工作要做，使用 try_recv 会很有用：我们可以编写一个循环，每隔一段时间就调用一次 try_recv，有消息可用时就处理消息，否则就先做一会儿其他工作，然后再次检查。

为了简单起见，这个例子中我们使用了 recv；除了等待消息之外，主线程没有其他工作要做，所以阻塞主线程是合适的。

运行示例 16-8 中的代码时，我们会看到主线程打印出了这个值：

Got: hi

完美！

通过通道转移所有权

所有权规则在消息发送中起着至关重要的作用，因为它们能帮助你编写安全的并发代码。在整个 Rust 程序中都考虑所有权，其好处就在于能够防止并发编程中的错误。我们来做一个实验，看看通道和所有权是如何协同工作来防止问题的：我们会尝试在把 val 值发送到通道之后，继续在新建线程中使用它。尝试编译示例 16-9 中的代码，看看为什么不允许这样做。

这里，我们尝试在通过 tx.send 把 val 发送到通道之后再打印它。允许这样做是个坏主意：一旦值被发送到另一个线程，那个线程就可能在我们再次使用该值之前修改或丢弃它。另一个线程所做的修改有可能会因为数据不一致或不存在而导致错误或意外的结果。不过，如果我们尝试编译示例 16-9 中的代码，Rust 会给出一个错误：

$ cargo run
   Compiling message-passing v0.1.0 (file:///projects/message-passing)
error[E0382]: borrow of moved value: `val`
  --> src/main.rs:10:27
   |
 8 |         let val = String::from("hi");
   |             --- move occurs because `val` has type `String`, which does not implement the `Copy` trait
 9 |         tx.send(val).unwrap();
   |                 --- value moved here
10 |         println!("val is {val}");
   |                           ^^^ value borrowed here after move

For more information about this error, try `rustc --explain E0382`.
error: could not compile `message-passing` (bin "message-passing") due to 1 previous error

我们的并发错误导致了一个编译时错误。send 函数会获取其参数的所有权，当值被移动后，接收端就获得了它的所有权。这样可以防止我们在发送值之后又不小心再次使用它；所有权系统会检查一切是否正常。

发送多个值

示例 16-8 中的代码可以编译并运行，但它并没有清楚地向我们展示两个独立的线程正在通过通道相互通信。

在示例 16-10 中，我们做了一些修改，以证明示例 16-8 中的代码是并发运行的：新建线程现在会发送多条消息，并在每条消息之间暂停一秒钟。

这一次，新建线程中有一个字符串 vector，我们想把其中的字符串发送给主线程。我们遍历这些字符串，逐个发送，并在每次发送之间以一个表示一秒的 Duration 值调用 thread::sleep 函数来暂停。

在主线程中，我们不再显式地调用 recv 函数，而是把 rx 当作一个迭代器来使用。对于接收到的每一个值，我们都将其打印出来。当通道关闭时，迭代就会结束。

运行示例 16-10 中的代码时，你应该会看到如下输出，每行之间会暂停一秒：

Got: hi
Got: from
Got: the
Got: thread

因为主线程的 for 循环中没有任何暂停或延迟的代码，所以我们可以看出，主线程是在等待接收来自新建线程的值。

创建多个生产者

前面我们提到过，mpsc 是多生产者，单消费者（multiple producer, single consumer）的缩写。现在我们就来用上 mpsc，扩展示例 16-10 中的代码，创建多个线程，让它们都向同一个接收端发送值。我们可以通过克隆发送端来做到这一点，如示例 16-11 所示。

这一次，在创建第一个新建线程之前，我们对发送端调用了 clone。这会给我们一个新的发送端，可以把它传给第一个新建线程。我们再把原来的发送端传给第二个新建线程。这样就有了两个线程，它们各自向同一个接收端发送不同的消息。

运行这段代码时，你的输出应该类似下面这样：

Got: hi
Got: more
Got: from
Got: messages
Got: for
Got: the
Got: thread
Got: you

根据你所用系统的不同，你看到的值的顺序可能会有所不同。这正是并发既有趣又困难的地方。如果你尝试使用 thread::sleep，在不同的线程中给它传入不同的值，那么每次运行的不确定性都会更大，每次都会产生不同的输出。
