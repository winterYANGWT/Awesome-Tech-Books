改进我们的 I/O 项目

有了这些关于迭代器的新知识，我们就可以用迭代器来改进第 12 章中的 I/O 项目，让代码中的一些地方更加清晰简洁。我们来看看迭代器如何改进 Config::build 函数和 search 函数的实现。

使用迭代器去掉 clone

在示例 12-6 中，我们添加的代码接受一个 String 值的切片，通过索引切片并克隆这些值来创建 Config 结构体的实例，从而让 Config 结构体拥有这些值。在示例 13-17 中，我们重现了示例 12-23 中 Config::build 函数的实现。

当时我们说过不必担心这些低效的 clone 调用，因为将来会去掉它们。现在，这个时候到了！

我们之所以在这里需要 clone，是因为参数 args 是一个包含 String 元素的切片，而 build 函数并不拥有 args。为了返回一个拥有所有权的 Config 实例，我们必须克隆 Config 的 query 和 file_path 字段的值，这样 Config 实例才能拥有它自己的值。

利用关于迭代器的新知识，我们可以修改 build 函数，让它获取一个迭代器的所有权作为参数，而不是借用一个切片。我们将使用迭代器的功能，来代替检查切片长度并索引特定位置的代码。由于将由迭代器来访问这些值，这会让 Config::build 函数所做的事情更加清晰。

一旦 Config::build 获取了迭代器的所有权，并且不再使用会产生借用的索引操作，我们就可以把 String 值从迭代器中移动到 Config 中，而不是调用 clone 并进行新的内存分配。

直接使用返回的迭代器

打开你的 I/O 项目的 src/main.rs 文件，它看起来应该是这样的：

文件名：src/main.rs

use std::env;
use std::error::Error;
use std::fs;
use std::process;

use minigrep::{search, search_case_insensitive};

fn main() {
    let args: Vec<String> = env::args().collect();

    let config = Config::build(&args).unwrap_or_else(|err| {
        eprintln!("Problem parsing arguments: {err}");
        process::exit(1);
    });

    // --snip--

    if let Err(e) = run(config) {
        eprintln!("Application error: {e}");
        process::exit(1);
    }
}

pub struct Config {
    pub query: String,
    pub file_path: String,
    pub ignore_case: bool,
}

impl Config {
    fn build(args: &[String]) -> Result<Config, &'static str> {
        if args.len() < 3 {
            return Err("not enough arguments");
        }

        let query = args[1].clone();
        let file_path = args[2].clone();

        let ignore_case = env::var("IGNORE_CASE").is_ok();

        Ok(Config {
            query,
            file_path,
            ignore_case,
        })
    }
}

fn run(config: Config) -> Result<(), Box<dyn Error>> {
    let contents = fs::read_to_string(config.file_path)?;

    let results = if config.ignore_case {
        search_case_insensitive(&config.query, &contents)
    } else {
        search(&config.query, &contents)
    };

    for line in results {
        println!("{line}");
    }

    Ok(())
}

我们首先把示例 12-24 中 main 函数的开头部分改为示例 13-18 中的代码，这次使用的是迭代器。在我们同样更新 Config::build 之前，这段代码是无法编译的。

env::args 函数返回的是一个迭代器！我们不再把迭代器的值收集到一个 vector 中、然后再把切片传给 Config::build，而是直接把 env::args 返回的迭代器的所有权传给 Config::build。

接下来，我们需要更新 Config::build 的定义。我们把 Config::build 的签名改成示例 13-19 那样。这段代码仍然无法编译，因为我们还需要更新函数体。

标准库中 env::args 函数的文档显示，它返回的迭代器的类型是 std::env::Args，该类型实现了 Iterator trait，并返回 String 值。

我们更新了 Config::build 函数的签名，使参数 args 具有一个带有 trait bound impl Iterator<Item = String> 的泛型类型，而不再是 &[String]。这里使用的是我们在第 10 章“使用 trait 作为参数”部分讨论过的 impl Trait 语法，它意味着 args 可以是任何实现了 Iterator trait 并返回 String 项的类型。

由于我们获取了 args 的所有权，并且会在遍历 args 时修改它，因此可以在 args 参数的声明中加上 mut 关键字，使其可变。

使用 Iterator trait 的方法

接下来，我们来修改 Config::build 的函数体。因为 args 实现了 Iterator trait，我们知道可以在它上面调用 next 方法！示例 13-20 将示例 12-23 中的代码改为使用 next 方法。

请记住，env::args 返回值中的第一个值是程序的名称。我们想忽略它并获取下一个值，所以我们首先调用一次 next，并且不对其返回值做任何处理。然后，我们再调用 next 来获取要放入 Config 的 query 字段中的值。如果 next 返回 Some，我们就使用 match 提取出其中的值；如果它返回 None，则意味着提供的参数不够，我们就提前返回一个 Err 值。对于 file_path 的值，我们也做同样的处理。

使用迭代器适配器让代码更清晰

我们还可以在 I/O 项目的 search 函数中利用迭代器。示例 13-21 重现了示例 12-19 中该函数的实现。

我们可以使用迭代器适配器方法，以更简洁的方式编写这段代码。这样做还能让我们避免使用一个可变的中间 vector results。函数式编程风格倾向于尽量减少可变状态的数量，以使代码更加清晰。去掉可变状态还可能为将来的改进提供便利，让搜索能够并行进行，因为我们不必管理对 results vector 的并发访问。示例 13-22 展示了这一修改。

回想一下，search 函数的目的是返回 contents 中所有包含 query 的行。与示例 13-16 中的 filter 例子类似，这段代码使用 filter 适配器，只保留那些使 line.contains(query) 返回 true 的行。然后，我们用 collect 把匹配的行收集到另一个 vector 中。简单多了！你也可以随意对 search_case_insensitive 函数做同样的修改，让它也使用迭代器方法。

作为进一步的改进，可以去掉对 collect 的调用，并将返回类型改为 impl Iterator<Item = &'a str>，从而让 search 函数返回一个迭代器，使这个函数本身成为一个迭代器适配器。注意，你还需要更新测试！在做出这一修改之前和之后，分别用你的 minigrep 工具搜索一个大文件，观察行为上的差异。修改之前，程序在收集完所有结果之前不会打印任何结果；而修改之后，每找到一个匹配的行就会立即打印出来，因为 run 函数中的 for 循环能够利用迭代器的惰性。

在循环与迭代器之间做选择

接下来一个合乎逻辑的问题是：在你自己的代码中应该选择哪种风格，为什么？是示例 13-21 中的原始实现，还是示例 13-22 中使用迭代器的版本（假设我们是在返回之前收集所有结果，而不是返回迭代器）？大多数 Rust 程序员更喜欢使用迭代器风格。一开始要掌握它会有点难，但一旦你熟悉了各种迭代器适配器及其作用，迭代器反而会更容易理解。代码不必再纠缠于循环的各种细节和构建新的 vector，而是专注于循环的高层目标。这把一些常见的代码抽象掉了，从而更容易看出这段代码所特有的概念，比如迭代器中每个元素必须满足的过滤条件。
