Rust 程序设计语言

使用字符串存储 UTF-8 编码的文本

我们在第 4 章中谈到过字符串，现在我们要更深入地了解它们。Rust 新手通常会因为三个原因的叠加而在字符串上卡住：Rust 倾向于暴露可能出现的错误；字符串是一种比许多程序员所以为的更复杂的数据结构；还有 UTF-8。当你从其他编程语言转过来时，这些因素结合在一起，可能会让字符串显得很难。

我们在集合的语境下讨论字符串，是因为字符串是作为字节的集合实现的，外加一些方法，用于在这些字节被解释为文本时提供有用的功能。在本节中，我们将讨论 String 上那些每种集合类型都有的操作，比如创建、更新和读取。我们还会讨论 String 与其他集合的不同之处，也就是人和计算机解读 String 数据的方式存在差异，这使得对 String 进行索引变得复杂。

定义字符串

我们首先来定义字符串（string）这个术语的含义。Rust 的核心语言中只有一种字符串类型，那就是字符串切片 str，它通常以借用的形式 &str 出现。在第 4 章中，我们讨论过字符串切片，它们是对存储在别处的某些 UTF-8 编码字符串数据的引用。例如，字符串字面量存储在程序的二进制文件中，因此它们就是字符串切片。

String 类型由 Rust 标准库提供，而不是编写在核心语言中，它是一种可增长、可变、拥有所有权、UTF-8 编码的字符串类型。当 Rustacean 提到 Rust 中的“字符串”时，他们可能指的是 String 类型，也可能指的是字符串切片 &str 类型，而不是专指其中某一种。虽然本节主要讨论的是 String，但这两种类型在 Rust 标准库中都被大量使用，而且 String 和字符串切片都是 UTF-8 编码的。

使用 + 或 format! 拼接字符串

你经常会想要把两个已有的字符串组合在一起。一种方法是使用 + 运算符，如示例 8-18 所示。

字符串 s3 将包含 Hello, world!。s1 在相加之后不再有效的原因，以及我们使用 s2 的引用的原因，都与使用 + 运算符时所调用方法的签名有关。+ 运算符使用的是 add 方法，其签名大致如下：

fn add(self, s: &str) -> String {

在标准库中，你会看到 add 是使用泛型和关联类型定义的。这里我们代入了具体类型，这正是我们用 String 值调用该方法时所发生的事情。我们将在第 10 章讨论泛型。这个签名为我们提供了理解 + 运算符那些微妙之处所需的线索。

首先，s2 前面有一个 &，这意味着我们是把第二个字符串的引用加到第一个字符串上。这是由 add 函数的 s 参数决定的：我们只能把字符串切片加到 String 上，而不能把两个 String 值相加。但是等等，&s2 的类型是 &String，而不是 add 第二个参数所指定的 &str。那么，为什么示例 8-18 能够编译呢？

我们之所以能在 add 调用中使用 &s2，是因为编译器可以将 &String 参数强制转换为 &str。当我们调用 add 方法时，Rust 使用了解引用强制转换，在这里它把 &s2 变成了 &s2[..]。我们将在第 15 章更深入地讨论解引用强制转换。因为 add 没有获取 s 参数的所有权，所以在这个操作之后，s2 仍然是一个有效的 String。

其次，我们可以从签名中看到，add 获取了 self 的所有权，因为 self 没有 &。这意味着示例 8-18 中的 s1 会被移动到 add 调用中，此后就不再有效了。所以，虽然 let s3 = s1 + &s2; 看起来像是会复制两个字符串并创建一个新的字符串，但实际上这条语句会获取 s1 的所有权，在其后追加 s2 内容的副本，然后返回结果的所有权。换句话说，它看起来做了很多次复制，但实际上并没有；这种实现比复制更高效。

如果我们需要拼接多个字符串，+ 运算符的行为就会变得笨拙：

fn main() {
    let s1 = String::from("tic");
    let s2 = String::from("tac");
    let s3 = String::from("toe");

    let s = s1 + "-" + &s2 + "-" + &s3;
}

此时，s 将会是 tic-tac-toe。有了这么多 + 和 " 字符，很难看清楚到底发生了什么。对于更复杂的字符串组合，我们可以改用 format! 宏：

fn main() {
    let s1 = String::from("tic");
    let s2 = String::from("tac");
    let s3 = String::from("toe");

    let s = format!("{s1}-{s2}-{s3}");
}

这段代码同样会把 s 设置为 tic-tac-toe。format! 宏的工作方式与 println! 类似，但它不是把输出打印到屏幕上，而是返回一个包含这些内容的 String。使用 format! 的代码版本要容易阅读得多，而且 format! 宏生成的代码使用的是引用，所以这个调用不会获取任何参数的所有权。

错误信息说明了一切：Rust 的字符串不支持索引。但为什么不支持呢？要回答这个问题，我们需要讨论 Rust 是如何在内存中存储字符串的。

内部表示

String 是对 Vec<u8> 的封装。我们来看看示例 8-14 中那些经过正确 UTF-8 编码的示例字符串。首先是这一个：

fn main() {
    let hello = String::from("السلام عليكم");
    let hello = String::from("Dobrý den");
    let hello = String::from("Hello");
    let hello = String::from("שלום");
    let hello = String::from("नमस्ते");
    let hello = String::from("こんにちは");
    let hello = String::from("안녕하세요");
    let hello = String::from("你好");
    let hello = String::from("Olá");
    let hello = String::from("Здравствуйте");
    let hello = String::from("Hola");
}

在这个例子中，len 的值将是 4，这意味着存储字符串 "Hola" 的 vector 长度为 4 个字节。用 UTF-8 编码时，其中每个字母都占用 1 个字节。然而，下面这一行可能会让你感到意外（注意，这个字符串开头是西里尔大写字母 Ze，而不是数字 3）：

fn main() {
    let hello = String::from("السلام عليكم");
    let hello = String::from("Dobrý den");
    let hello = String::from("Hello");
    let hello = String::from("שלום");
    let hello = String::from("नमस्ते");
    let hello = String::from("こんにちは");
    let hello = String::from("안녕하세요");
    let hello = String::from("你好");
    let hello = String::from("Olá");
    let hello = String::from("Здравствуйте");
    let hello = String::from("Hola");
}

如果有人问你这个字符串有多长，你可能会说 12。实际上，Rust 的答案是 24：这是用 UTF-8 编码“Здравствуйте”所需的字节数，因为这个字符串中的每个 Unicode 标量值都需要占用 2 个字节的存储空间。因此，对字符串字节的索引并不总是对应一个有效的 Unicode 标量值。为了演示这一点，来看下面这段无效的 Rust 代码：

let hello = "Здравствуйте";
let answer = &hello[0];

你已经知道，answer 不会是第一个字母 З。用 UTF-8 编码时，З 的第一个字节是 208，第二个字节是 151，所以看起来 answer 实际上应该是 208，但 208 本身并不是一个有效的字符。如果用户要求获取这个字符串的第一个字母，返回 208 很可能并不是他们想要的；然而，这是 Rust 在字节索引 0 处所拥有的唯一数据。即使字符串只包含拉丁字母，用户通常也不希望返回字节值：如果 &"hi"[0] 是返回字节值的有效代码，它返回的将是 104，而不是 h。

所以答案是：为了避免返回意外的值、造成可能无法被立即发现的 bug，Rust 根本不会编译这样的代码，从而在开发过程的早期就防止了误解的发生。

字节、标量值和字形簇

关于 UTF-8 还有一点：从 Rust 的角度来看，实际上有三种看待字符串的相关方式：字节、标量值和字形簇（grapheme cluster，最接近我们所说的字母的概念）。

如果我们看一下用天城文书写的印地语单词“नमस्ते”，它会被存储为一个如下所示的 u8 值 vector：

[224, 164, 168, 224, 164, 174, 224, 164, 184, 224, 165, 141, 224, 164, 164,
224, 165, 135]

这是 18 个字节，也是计算机最终存储这些数据的方式。如果我们把它们看作 Unicode 标量值，也就是 Rust 的 char 类型，那么这些字节看起来是这样的：

['न', 'म', 'स', '्', 'त', 'े']

这里有六个 char 值，但第四个和第六个并不是字母：它们是单独存在时没有意义的变音符号。最后，如果我们把它们看作字形簇，就会得到人们所说的组成这个印地语单词的四个字母：

["न", "म", "स्", "ते"]

Rust 提供了多种不同的方式来解读计算机所存储的原始字符串数据，这样无论数据使用的是哪种人类语言，每个程序都可以选择它所需要的解读方式。

Rust 不允许我们通过索引 String 来获取字符的最后一个原因是：索引操作预期总是只需要常数时间（O(1)）。但对于 String 来说，无法保证这样的性能，因为 Rust 必须从头开始遍历内容直到索引位置，才能确定其中有多少个有效字符。

字符串切片

对字符串进行索引通常是一个坏主意，因为字符串索引操作的返回类型应该是什么并不明确：是字节值、字符、字形簇，还是字符串切片。因此，如果你确实需要使用索引来创建字符串切片，Rust 会要求你更加明确。

与其使用 [] 和单个数字进行索引，不如使用 [] 和一个范围来创建包含特定字节的字符串切片：

#![allow(unused)]
fn main() {
let hello = "Здравствуйте";

let s = &hello[0..4];
}

这里，s 将是一个 &str，它包含字符串的前 4 个字节。前面我们提到过，这些字符每个都占 2 个字节，这意味着 s 将是 Зд。

如果我们尝试用类似 &hello[0..1] 的方式只对某个字符的部分字节进行切片，Rust 会在运行时 panic，就像在 vector 中访问无效索引时一样：

$ cargo run
   Compiling collections v0.1.0 (file:///projects/collections)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.43s
     Running `target/debug/collections`

thread 'main' (6017738) panicked at src/main.rs:4:19:
end byte index 1 is not a char boundary; it is inside 'З' (bytes 0..2 of string)
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

使用范围创建字符串切片时应当小心谨慎，因为这样做可能会让你的程序崩溃。

遍历字符串

操作字符串片段的最佳方式，是明确表明你需要的是字符还是字节。对于单独的 Unicode 标量值，使用 chars 方法。对“Зд”调用 chars 会将其拆分开，返回两个 char 类型的值，你可以遍历结果来访问每个元素：

#![allow(unused)]
fn main() {
for c in "Зд".chars() {
    println!("{c}");
}
}

这段代码会打印出如下内容：

З
д

另外，bytes 方法会返回每一个原始字节，这可能适合你所在的领域：

#![allow(unused)]
fn main() {
for b in "Зд".bytes() {
    println!("{b}");
}
}

这段代码会打印出组成这个字符串的 4 个字节：

208
151
208
180

不过一定要记住，有效的 Unicode 标量值可能由不止 1 个字节组成。

从字符串中获取字形簇（例如天城文的情况）是很复杂的，所以标准库并没有提供这个功能。如果你需要这样的功能，可以在 crates.io 上找到相应的 crate。

处理字符串的复杂性

总而言之，字符串是复杂的。不同的编程语言在如何向程序员呈现这种复杂性方面做出了不同的选择。Rust 选择将正确处理 String 数据作为所有 Rust 程序的默认行为，这意味着程序员必须预先在处理 UTF-8 数据上花更多心思。这种权衡比其他编程语言暴露出了更多字符串的复杂性，但它让你不必在开发周期的后期再去处理涉及非 ASCII 字符的错误。

好消息是，标准库在 String 和 &str 类型的基础上提供了大量功能，帮助你正确处理这些复杂的情况。一定要查阅文档，了解一些实用的方法，比如用于在字符串中搜索的 contains，以及用于将字符串的某些部分替换为另一个字符串的 replace。
