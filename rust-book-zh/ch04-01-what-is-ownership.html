Rust 程序设计语言

什么是所有权？

所有权（ownership）是一组规则，它决定了 Rust 程序如何管理内存。所有程序在运行时都必须管理它们使用计算机内存的方式。有些语言具有垃圾回收机制，在程序运行时定期寻找不再使用的内存；在另一些语言中，程序员必须显式地分配和释放内存。Rust 则采用了第三种方式：通过所有权系统管理内存，编译器会检查一组规则。只要违反了其中任何一条规则，程序就无法编译。所有权的任何特性都不会在程序运行时拖慢它的速度。

因为所有权对很多程序员来说是一个新概念，所以确实需要一些时间来适应。好消息是，你对 Rust 和所有权系统的规则越有经验，就越能自然地编写出安全且高效的代码。坚持下去！

理解了所有权，你就为理解 Rust 那些独特的特性打下了坚实的基础。在本章中，你将通过一些例子来学习所有权，这些例子都围绕一种非常常见的数据结构展开：字符串。

栈与堆

很多编程语言并不需要你经常考虑栈和堆。但在 Rust 这样的系统编程语言中，值是位于栈上还是堆上，会影响语言的行为，也决定了你为什么必须做出某些选择。本章稍后会结合栈和堆来描述所有权的部分内容，所以这里先做一个简短的说明作为准备。

栈和堆都是代码在运行时可以使用的内存，但它们的组织方式不同。栈按照获取值的顺序存储值，并以相反的顺序移除值，这被称为后进先出（last in, first out，LIFO）。想象一摞盘子：当你添加更多盘子时，会把它们放在这摞盘子的顶部；当你需要一个盘子时，就从顶部拿走一个。从中间或底部添加或移除盘子可就没那么方便了！添加数据叫作入栈（pushing onto the stack），移除数据叫作出栈（popping off the stack）。栈中存储的所有数据都必须有已知且固定的大小。在编译时大小未知或者大小可能变化的数据，则必须存储在堆上。

堆的组织性要差一些：当你把数据放到堆上时，你要请求一定大小的空间。内存分配器会在堆中找到一块足够大的空位，把它标记为已使用，并返回一个指针（pointer），也就是该位置的地址。这个过程叫作在堆上分配内存（allocating on the heap），有时简称为分配（allocating）（将值推入栈中不被视为分配）。因为指向堆的指针大小已知且固定，所以你可以把指针存储在栈上，但当你需要实际的数据时，就必须沿着指针去访问。想象一下去餐馆就座的情景。进门时，你说明你们一行有几个人，服务员会找到一张能坐下所有人的空桌，并把你们领过去。如果你们当中有人来晚了，他可以询问你们坐在哪里，从而找到你们。

入栈比在堆上分配内存要快，因为分配器无需寻找存储新数据的位置；这个位置总是在栈顶。相比之下，在堆上分配空间需要做更多的工作，因为分配器必须先找到一块足够大的空间来存放数据，然后还要做一些记录工作，为下一次分配做准备。

访问堆上的数据通常比访问栈上的数据慢，因为你必须沿着指针才能找到它。现代处理器在内存中跳转越少，速度就越快。继续用餐馆打个比方，设想一位服务员要为许多桌客人点餐。最高效的做法是先把一桌的菜点完，再去下一桌。先给 A 桌点一个菜，再给 B 桌点一个，然后又回到 A 桌，再回到 B 桌，这样的过程就会慢得多。同样的道理，处理器处理彼此相邻的数据（就像栈上的数据那样）通常比处理相距较远的数据（就像堆上的数据可能的那样）效率更高。

当代码调用一个函数时，传入函数的值（可能包括指向堆上数据的指针）以及函数的局部变量会被压入栈中。当函数结束时，这些值会被弹出栈。

跟踪代码的哪些部分正在使用堆上的哪些数据，尽量减少堆上的重复数据，以及清理堆上不再使用的数据以免耗尽空间，这些都是所有权要解决的问题。一旦理解了所有权，你就不需要经常考虑栈和堆了。不过，知道所有权的主要目的是管理堆上的数据，有助于解释它为什么以这样的方式工作。

所有权规则

首先，我们来看看所有权的规则。在学习后面说明这些规则的例子时，请记住它们：

  • Rust 中的每一个值都有一个所有者（owner）。
  • 值在任一时刻只能有一个所有者。
  • 当所有者离开作用域时，这个值将被丢弃。

变量作用域

既然我们已经掌握了基本的 Rust 语法，后面的例子中就不再包含所有的 fn main() { 代码了。所以如果你在跟着动手实践，请务必手动把下面的例子放到 main 函数中。这样一来，我们的例子会更简洁一些，让我们能够专注于实际的细节，而不是样板代码。

作为所有权的第一个例子，我们来看看一些变量的作用域。作用域（scope）是程序中某个项有效的范围。以下面这个变量为例：

#![allow(unused)]
fn main() {
let s = "hello";
}

变量 s 指向一个字符串字面量，字符串的值被硬编码到了程序的文本中。这个变量从声明的那一刻起直到当前作用域结束都是有效的。示例 4-1 展示了一个程序，其中的注释标明了变量 s 在何处有效。

换句话说，这里有两个重要的时间点：

  • 当 s 进入作用域时，它就是有效的。
  • 它一直保持有效，直到离开作用域为止。

目前为止，作用域与变量何时有效之间的关系，与其他编程语言中的情况类似。现在我们将在这一理解的基础上，引入 String 类型。

String 类型

为了说明所有权的规则，我们需要一种比第 3 章“数据类型”部分介绍的类型更复杂的数据类型。之前介绍的类型大小都是已知的，可以存储在栈上，并在其作用域结束时被弹出栈；而且如果代码的其他部分需要在不同的作用域中使用同一个值，还可以快速而简单地复制它们，从而创建一个新的、独立的实例。但我们想要研究的是存储在堆上的数据，并探索 Rust 如何知道何时清理这些数据，而 String 类型就是一个很好的例子。

我们将专注于 String 中与所有权相关的部分。这些方面同样适用于其他复杂的数据类型，无论它们是由标准库提供的还是由你自己创建的。我们会在第 8 章中讨论 String 与所有权无关的方面。

我们已经见过字符串字面量了，它们的字符串值被硬编码到程序中。字符串字面量很方便，但并不适用于所有需要使用文本的场景。原因之一是它们是不可变的；另一个原因是，并不是所有字符串的值都能在编写代码时就知道：例如，如果我们想获取用户输入并把它存储起来，该怎么办呢？正是为了应对这些情况，Rust 提供了 String 类型。这个类型管理分配在堆上的数据，因此能够存储在编译时大小未知的文本。你可以使用 from 函数基于字符串字面量来创建 String，像这样：

#![allow(unused)]
fn main() {
let s = String::from("hello");
}

双冒号 :: 运算符让我们可以把这个特定的 from 函数置于 String 类型的命名空间之下，而不必使用诸如 string_from 这样的名字。我们会在第 5 章“方法”部分进一步讨论这种语法，并在第 7 章“引用模块树中项的路径”中讨论如何使用模块进行命名空间管理。

这种字符串可以被修改：

fn main() {
    let mut s = String::from("hello");

    s.push_str(", world!"); // push_str() appends a literal to a String

    println!("{s}"); // this will print `hello, world!`
}

那么，区别在哪里呢？为什么 String 可以被修改而字面量却不行？区别在于这两种类型处理内存的方式。

内存与分配

对于字符串字面量，我们在编译时就知道其内容，所以文本被直接硬编码进最终的可执行文件中。这就是字符串字面量快速而高效的原因。不过这些特性都只是源于字符串字面量的不可变性。遗憾的是，对于那些在编译时大小未知、且在程序运行时大小可能发生变化的文本，我们无法为每一段都在二进制文件中放入一块内存。

对于 String 类型，为了支持一段可变、可增长的文本，我们需要在堆上分配一块在编译时大小未知的内存来存放内容。这意味着：

  • 必须在运行时向内存分配器请求内存。
  • 需要一种在我们用完 String 之后把这些内存归还给分配器的方法。

第一部分由我们来完成：当我们调用 String::from 时，它的实现会请求所需的内存。这一点在各种编程语言中几乎是通用的。

然而，第二部分就不同了。在具有垃圾回收器（garbage collector，GC）的语言中，GC 会跟踪并清理不再使用的内存，我们不需要操心这件事。在大多数没有 GC 的语言中，识别内存何时不再被使用并调用代码显式地释放它，就是我们自己的责任了，这跟请求内存时一样。正确地做到这一点，历来是一个困难的编程问题。如果忘记释放，就会浪费内存；如果过早释放，就会得到一个无效的变量；如果重复释放，这同样是一个 bug。我们需要让每一次 allocate 都恰好对应一次 free。

Rust 采取了一条不同的路径：一旦拥有内存的变量离开作用域，内存就会被自动归还。下面是示例 4-1 中作用域例子的另一个版本，这次使用 String 而不是字符串字面量：

fn main() {
    {
        let s = String::from("hello"); // s is valid from this point forward

        // do stuff with s
    }                                  // this scope is now over, and s is no
                                       // longer valid
}

有一个很自然的时机可以把 String 所需的内存归还给分配器：当 s 离开作用域的时候。当变量离开作用域时，Rust 会为我们调用一个特殊的函数。这个函数叫作 drop，String 的作者可以在这里放置归还内存的代码。Rust 会在右花括号处自动调用 drop。

注意：在 C++ 中，这种在项的生命周期结束时释放资源的模式有时被称为资源获取即初始化（Resource Acquisition Is Initialization，RAII）。如果你用过 RAII 模式，就会对 Rust 中的 drop 函数感到很熟悉。

这种模式对 Rust 代码的编写方式有着深远的影响。现在看起来它可能很简单，但在更复杂的情况下，当我们想让多个变量使用在堆上分配的数据时，代码的行为可能会出人意料。现在我们就来探讨其中的一些情况。

变量与数据交互的方式：移动

在 Rust 中，多个变量可以以不同的方式与同一份数据交互。示例 4-2 展示了一个使用整数的例子。

我们大概能猜到这段代码在做什么：“将值 5 绑定到 x；然后复制 x 中的值，并将其绑定到 y。”现在我们有了两个变量 x 和 y，它们都等于 5。实际情况也确实如此，因为整数是具有已知固定大小的简单值，这两个 5 值都被压入了栈中。

现在我们来看看 String 版本：

fn main() {
    let s1 = String::from("hello");
    let s2 = s1;
}

这看起来非常相似，所以我们可能会认为它的工作方式也是一样的：也就是说，第二行会复制 s1 中的值，并将其绑定到 s2。但实际情况并不完全是这样。

请看图 4-1，了解 String 在底层究竟发生了什么。String 由三部分组成，如图左侧所示：一个指向存放字符串内容的内存的指针、一个长度和一个容量。这组数据存储在栈上。右侧则是堆上存放内容的内存。

图 4-1：绑定到 s1 的、值为 "hello" 的 String 在内存中的表示

长度是 String 的内容当前使用的内存大小，以字节为单位。容量是 String 从分配器获得的内存总量，同样以字节为单位。长度和容量之间的区别很重要，但在当前的上下文中并不重要，所以现在可以先忽略容量。

当我们把 s1 赋值给 s2 时，String 的数据被复制了，这意味着我们复制了栈上的指针、长度和容量，而并没有复制指针所指向的堆上的数据。换句话说，内存中的数据表示如图 4-2 所示。

图 4-2：变量 s2 在内存中的表示，它拥有 s1 的指针、长度和容量的副本

这种表示并不像图 4-3 那样，图 4-3 是 Rust 同时复制堆上数据时内存的样子。如果 Rust 这样做，那么当堆上的数据很大时，s2 = s1 这一操作在运行时性能方面的开销可能会非常大。

图 4-3：如果 Rust 也复制堆上的数据，s2 = s1 可能会产生的另一种结果

前面我们说过，当变量离开作用域时，Rust 会自动调用 drop 函数并清理该变量的堆内存。但图 4-2 显示两个数据指针指向了同一个位置。这就有问题了：当 s2 和 s1 离开作用域时，它们都会尝试释放同一块内存。这被称为二次释放（double free）错误，也是我们之前提到过的内存安全 bug 之一。两次释放同一块内存可能导致内存损坏，进而可能引发安全漏洞。

为了确保内存安全，在 let s2 = s1; 这一行之后，Rust 认为 s1 不再有效。因此，当 s1 离开作用域时，Rust 不需要释放任何东西。看看在创建 s2 之后尝试使用 s1 会发生什么；这样是行不通的：

fn main() {
    let s1 = String::from("hello");
    let s2 = s1;

    println!("{s1}, world!");
}

你会得到一个类似这样的错误，因为 Rust 禁止你使用已经失效的引用：

error: could not compile `ownership` (bin "ownership") due to 1 previous error

如果你在使用其他语言时听说过浅拷贝（shallow copy）和深拷贝（deep copy）这两个术语，那么只复制指针、长度和容量而不复制数据的做法，听起来可能就像是浅拷贝。但是因为 Rust 同时使第一个变量失效了，所以这个操作不叫浅拷贝，而叫作移动（move）。在这个例子中，我们会说 s1 被移动到了 s2 中。所以，实际发生的情况如图 4-4 所示。

图 4-4：s1 失效之后内存中的表示

这样就解决了我们的问题！因为只有 s2 是有效的，当它离开作用域时，就只有它会释放这块内存，问题就解决了。

此外，这里还隐含了一个设计选择：Rust 永远不会自动创建数据的“深”拷贝。因此，任何自动的复制在运行时性能方面都可以被认为是开销很小的。

作用域与赋值

反过来，作用域、所有权以及通过 drop 函数释放内存三者之间的关系也同样成立。当你给一个已有的变量赋予一个全新的值时，Rust 会调用 drop，立即释放原来那个值的内存。例如，请看下面的代码：

fn main() {
    let mut s = String::from("hello");
    s = String::from("ahoy");

    println!("{s}, world!");
}

我们首先声明了一个变量 s，并将它绑定到一个值为 "hello" 的 String 上。接着，我们立即创建了一个值为 "ahoy" 的新 String，并把它赋值给 s。此时，已经没有任何东西引用堆上原来的那个值了。图 4-5 展示了此时栈和堆上的数据：

图 4-5：初始值被整体替换之后内存中的表示

于是，原来的字符串立即离开了作用域。Rust 会对它运行 drop 函数，它的内存会被马上释放。当我们在最后打印这个值时，它将是 "ahoy, world!"。

变量与数据交互的方式：克隆

如果我们确实想要深度复制 String 在堆上的数据，而不仅仅是栈上的数据，可以使用一个叫作 clone 的常用方法。我们会在第 5 章讨论方法语法，不过因为方法是很多编程语言中的常见特性，你之前很可能已经见过它们了。

下面是一个 clone 方法的实际例子：

fn main() {
    let s1 = String::from("hello");
    let s2 = s1.clone();

    println!("s1 = {s1}, s2 = {s2}");
}

这段代码能够正常运行，并且显式地产生了图 4-3 所示的行为，即堆上的数据确实被复制了。

当你看到对 clone 的调用时，就知道有一些任意的代码正在被执行，而这些代码的开销可能很大。它是一个直观的标志，表明这里发生了一些不同寻常的事情。

只在栈上的数据：Copy

还有一个我们尚未谈到的细节。下面这段使用整数的代码（其中一部分在示例 4-2 中展示过）能够正常运行，并且是有效的：

fn main() {
    let x = 5;
    let y = x;

    println!("x = {x}, y = {y}");
}

但这段代码似乎与我们刚刚学到的内容相矛盾：我们没有调用 clone，但 x 依然有效，并没有被移动到 y 中。

原因在于，像整数这样在编译时大小已知的类型完全存储在栈上，所以复制它们的实际值是很快的。这意味着在创建变量 y 之后，我们没有理由要让 x 失效。换句话说，这里的深拷贝和浅拷贝没有任何区别，所以调用 clone 并不会与通常的浅拷贝有什么不同，我们可以省略它。

Rust 有一个叫作 Copy trait 的特殊注解，我们可以把它用在像整数这样存储在栈上的类型上（我们会在第 10 章中进一步讨论 trait）。如果一个类型实现了 Copy trait，那么使用它的变量不会被移动，而是会被简单地复制，这样在赋值给另一个变量之后，它们仍然有效。

如果一个类型或者它的任何部分实现了 Drop trait，Rust 就不允许我们用 Copy 来注解这个类型。如果某个类型在值离开作用域时需要进行特殊处理，而我们又给这个类型加上了 Copy 注解，就会得到一个编译时错误。要了解如何为你的类型添加 Copy 注解来实现这个 trait，请参阅附录 C 中的“可派生的 trait”。

那么，哪些类型实现了 Copy trait 呢？你可以查看给定类型的文档来确认，不过一般来说，任何由简单标量值组成的组合都可以实现 Copy，而任何需要分配内存或属于某种形式的资源的类型都不能实现 Copy。下面是一些实现了 Copy 的类型：

  • 所有的整数类型，例如 u32。
  • 布尔类型 bool，它的值是 true 和 false。
  • 所有的浮点类型，例如 f64。
  • 字符类型 char。
  • 元组，前提是它只包含同样实现了 Copy 的类型。例如，(i32, i32) 实现了 Copy，但 (i32, String) 没有。

所有权与函数

将值传递给函数的机制，与把值赋给变量时的机制类似。向函数传递一个变量会发生移动或复制，就像赋值一样。示例 4-3 中有一个带有注释的例子，标明了变量在何处进入和离开作用域。

如果我们在调用 takes_ownership 之后尝试使用 s，Rust 就会抛出一个编译时错误。这些静态检查可以保护我们免于犯错。试着在 main 中添加使用 s 和 x 的代码，看看在哪些地方可以使用它们，在哪些地方所有权规则会阻止你这样做。

返回值与作用域

返回值也可以转移所有权。示例 4-4 展示了一个返回某个值的函数的例子，其中的注释与示例 4-3 中的类似。

变量的所有权每次都遵循相同的模式：把一个值赋给另一个变量时会移动它。当一个包含堆上数据的变量离开作用域时，它的值会被 drop 清理掉，除非这份数据的所有权已经被移动到了另一个变量。

虽然这样能行得通，但在每个函数中都先获取所有权、再返回所有权，就有点烦琐了。如果我们想让函数使用一个值但不获取它的所有权，该怎么办呢？如果我们还想再次使用传入的任何东西，就得把它们再传回来，此外还要加上函数体中产生的、我们可能也想返回的任何数据，这实在是相当恼人。

Rust 确实允许我们使用元组返回多个值，如示例 4-5 所示。

但对于一个本应很常见的概念来说，这种做法太过繁琐，工作量也太大了。幸运的是，Rust 提供了一种无需转移所有权就能使用值的特性：引用。
