Rust 程序设计语言

引用循环会导致内存泄漏

Rust 的内存安全保证使得意外创建出永远不会被清理的内存（称为内存泄漏，memory leak）变得困难，但并非不可能。完全防止内存泄漏并不在 Rust 的保证范围之内，这意味着在 Rust 中内存泄漏是内存安全的。通过使用 Rc<T> 和 RefCell<T>，我们可以看到 Rust 是允许内存泄漏的：我们可以创建出各个项在一个循环中相互引用的引用关系。这会造成内存泄漏，因为循环中每一项的引用计数永远都不会变为 0，这些值也就永远不会被丢弃。

创建引用循环

让我们来看看引用循环是如何发生的，以及如何防止它。首先从示例 15-25 中 List 枚举的定义和一个 tail 方法开始。

我们使用的是示例 15-5 中 List 定义的另一个变种。现在 Cons 变体中的第二个元素是 RefCell<Rc<List>>，这意味着我们不再像示例 15-24 那样能够修改 i32 值，而是希望修改 Cons 变体所指向的 List 值。我们还添加了一个 tail 方法，以便在拥有一个 Cons 变体时方便地访问其第二项。

在示例 15-26 中，我们添加了一个使用示例 15-25 中定义的 main 函数。这段代码在 a 中创建了一个列表，又在 b 中创建了一个指向 a 中列表的列表。然后，它修改 a 中的列表使其指向 b，从而创建了一个引用循环。在这个过程中有一些 println! 语句，用来展示各个时间点的引用计数。

我们在变量 a 中创建了一个 Rc<List> 实例，它存储了一个初始列表为 5, Nil 的 List 值。然后，我们在变量 b 中创建了另一个 Rc<List> 实例，它存储了另一个 List 值，该值包含 10 并指向 a 中的列表。

我们修改 a，让它指向 b 而不是 Nil，从而形成一个循环。具体做法是：使用 tail 方法获取 a 中 RefCell<Rc<List>> 的引用，并把它放进变量 link 中。然后，我们对这个 RefCell<Rc<List>> 使用 borrow_mut 方法，把其中的值从一个存储 Nil 值的 Rc<List> 改为 b 中的 Rc<List>。

运行这段代码时（暂时保持最后一个 println! 被注释掉），我们会得到如下输出：

$ cargo run

    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.53s
     Running `target/debug/cons-list`
a initial rc count = 1
a next item = Some(RefCell { value: Nil })
a rc count after b creation = 2
b initial rc count = 1
b next item = Some(RefCell { value: Cons(5, RefCell { value: Nil }) })

a rc count after changing a = 2

在我们把 a 中的列表修改为指向 b 之后，a 和 b 中 Rc<List> 实例的引用计数都是 2。在 main 的末尾，Rust 会丢弃变量 b，这会使 b 的 Rc<List> 实例的引用计数从 2 减为 1。此时该 Rc<List> 在堆上的内存不会被丢弃，因为它的引用计数是 1 而不是 0。接着，Rust 会丢弃 a，这同样会使 a 的 Rc<List> 实例的引用计数从 2 减为 1。这个实例的内存也无法被丢弃，因为另一个 Rc<List> 实例仍然引用着它。分配给这个列表的内存将永远不会被回收。为了直观地展示这个引用循环，我们绘制了图 15-4。

图 15-4：列表 a 和 b 相互指向形成的引用循环

如果取消最后一个 println! 的注释并运行程序，Rust 会尝试打印这个循环：a 指向 b，b 又指向 a，如此往复，直到栈溢出为止。

与真实世界的程序相比，这个示例中创建引用循环的后果并不算严重：我们刚创建完引用循环，程序就结束了。然而，如果一个更复杂的程序在循环中分配了大量内存，并长时间持有这些内存，那么程序就会使用比实际需要更多的内存，并可能压垮系统，导致可用内存耗尽。

创建引用循环并不容易，但也并非不可能。如果你有包含 Rc<T> 值的 RefCell<T> 值，或者其他类似的结合了内部可变性和引用计数的类型嵌套组合，就必须确保不会创建出循环；你不能指望 Rust 替你捕获它们。创建引用循环属于程序中的逻辑错误，你应该使用自动化测试、代码评审以及其他软件开发实践来尽量避免。

另一种避免引用循环的解决方案是重新组织数据结构，使得一部分引用表达所有权，而另一部分引用不表达所有权。这样一来，你可以拥有由一些所有权关系和一些非所有权关系构成的循环，而只有所有权关系才会影响一个值能否被丢弃。在示例 15-25 中，我们总是希望 Cons 变体拥有它们的列表，因此无法重新组织这个数据结构。让我们来看一个使用由父节点和子节点构成的图的例子，看看什么时候使用非所有权关系是防止引用循环的合适方式。

使用 Weak<T> 避免引用循环

到目前为止，我们已经演示了调用 Rc::clone 会增加 Rc<T> 实例的 strong_count，并且只有当 Rc<T> 实例的 strong_count 为 0 时，它才会被清理。你还可以通过调用 Rc::downgrade 并传入 Rc<T> 的引用，来创建指向 Rc<T> 实例中值的弱引用。强引用（strong reference）是你共享 Rc<T> 实例所有权的方式。弱引用（weak reference）不表达所有权关系，它们的计数不会影响 Rc<T> 实例何时被清理。弱引用不会造成引用循环，因为一旦所涉及值的强引用计数变为 0，任何包含弱引用的循环都会被打破。

当你调用 Rc::downgrade 时，会得到一个 Weak<T> 类型的智能指针。调用 Rc::downgrade 不会让 Rc<T> 实例中的 strong_count 加 1，而是让 weak_count 加 1。与 strong_count 类似，Rc<T> 类型使用 weak_count 来记录存在多少个 Weak<T> 引用。区别在于，Rc<T> 实例被清理时并不要求 weak_count 为 0。

由于 Weak<T> 所引用的值可能已经被丢弃了，因此要对 Weak<T> 所指向的值做任何操作，你都必须确保这个值仍然存在。为此，可以在 Weak<T> 实例上调用 upgrade 方法，它会返回一个 Option<Rc<T>>。如果 Rc<T> 值尚未被丢弃，你会得到 Some 结果；如果 Rc<T> 值已经被丢弃，则会得到 None 结果。因为 upgrade 返回的是 Option<Rc<T>>，Rust 会确保 Some 和 None 两种情况都得到处理，因此不会出现无效指针。

作为示例，我们不再使用每一项只知道下一项的列表，而是创建一棵树，其中每一项既知道它的子项，也知道它的父项。

创建树形数据结构

首先，我们将构建一棵树，其中的节点知道它们的子节点。我们会创建一个名为 Node 的结构体，它存储自身的 i32 值以及对其子 Node 值的引用：

文件名：src/main.rs

use std::cell::RefCell;
use std::rc::Rc;

#[derive(Debug)]
struct Node {
    value: i32,
    children: RefCell<Vec<Rc<Node>>>,
}

fn main() {
    let leaf = Rc::new(Node {
        value: 3,
        children: RefCell::new(vec![]),
    });

    let branch = Rc::new(Node {
        value: 5,
        children: RefCell::new(vec![Rc::clone(&leaf)]),
    });
}

我们希望 Node 拥有它的子节点，同时也希望与变量共享这份所有权，这样就能直接访问树中的每一个 Node。为此，我们把 Vec<T> 的项定义为 Rc<Node> 类型的值。我们还希望能够修改哪些节点是另一个节点的子节点，所以在 children 中用 RefCell<T> 包裹 Vec<Rc<Node>>。

接下来，我们将使用这个结构体定义，创建一个名为 leaf 的 Node 实例，其值为 3 且没有子节点；再创建另一个名为 branch 的实例，其值为 5，并以 leaf 作为其子节点之一，如示例 15-27 所示。

我们克隆了 leaf 中的 Rc<Node> 并把它存储在 branch 中，这意味着 leaf 中的 Node 现在有两个所有者：leaf 和 branch。我们可以通过 branch.children 从 branch 访问到 leaf，但没有办法从 leaf 访问到 branch。原因在于 leaf 没有指向 branch 的引用，也不知道它们之间存在关联。我们希望 leaf 知道 branch 是它的父节点。接下来我们就来实现这一点。

添加从子节点到其父节点的引用

为了让子节点知道它的父节点，我们需要在 Node 结构体定义中添加一个 parent 字段。难点在于确定 parent 应该是什么类型。我们知道它不能包含 Rc<T>，因为那样会造成引用循环：leaf.parent 指向 branch，而 branch.children 指向 leaf，这会导致它们的 strong_count 值永远不会变为 0。

换个角度思考这些关系：父节点应该拥有它的子节点；如果父节点被丢弃了，它的子节点也应该随之被丢弃。然而，子节点不应该拥有它的父节点；如果我们丢弃一个子节点，父节点应该依然存在。这正是使用弱引用的场景！

所以，我们不用 Rc<T>，而是让 parent 的类型使用 Weak<T>，具体来说是 RefCell<Weak<Node>>。现在 Node 结构体的定义如下所示：

文件名：src/main.rs

use std::cell::RefCell;
use std::rc::{Rc, Weak};

#[derive(Debug)]
struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,
    children: RefCell<Vec<Rc<Node>>>,
}

fn main() {
    let leaf = Rc::new(Node {
        value: 3,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![]),
    });

    println!("leaf parent = {:?}", leaf.parent.borrow().upgrade());

    let branch = Rc::new(Node {
        value: 5,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![Rc::clone(&leaf)]),
    });

    *leaf.parent.borrow_mut() = Rc::downgrade(&branch);

    println!("leaf parent = {:?}", leaf.parent.borrow().upgrade());
}

节点将能够引用它的父节点，但并不拥有它的父节点。在示例 15-28 中，我们更新 main 以使用这个新定义，这样 leaf 节点就有办法引用它的父节点 branch 了。

创建 leaf 节点的方式与示例 15-27 类似，只是多了 parent 字段：leaf 一开始没有父节点，所以我们创建了一个新的、空的 Weak<Node> 引用实例。

此时，当我们尝试使用 upgrade 方法获取 leaf 父节点的引用时，会得到一个 None 值。我们可以在第一个 println! 语句的输出中看到这一点：

leaf parent = None

当我们创建 branch 节点时，它的 parent 字段中也会有一个新的 Weak<Node> 引用，因为 branch 没有父节点。我们仍然让 leaf 作为 branch 的子节点之一。一旦有了 branch 中的 Node 实例，我们就可以修改 leaf，给它一个指向其父节点的 Weak<Node> 引用。我们对 leaf 的 parent 字段中的 RefCell<Weak<Node>> 使用 borrow_mut 方法，然后使用 Rc::downgrade 函数，从 branch 中的 Rc<Node> 创建一个指向 branch 的 Weak<Node> 引用。

当我们再次打印 leaf 的父节点时，这一次会得到一个存储着 branch 的 Some 变体：现在 leaf 可以访问它的父节点了！当我们打印 leaf 时，也避免了像示例 15-26 中那样最终导致栈溢出的循环；Weak<Node> 引用会被打印为 (Weak)：

leaf parent = Some(Node { value: 5, parent: RefCell { value: (Weak) },
children: RefCell { value: [Node { value: 3, parent: RefCell { value: (Weak) },
children: RefCell { value: [] } }] } })

没有出现无限的输出，这表明这段代码并没有创建引用循环。我们也可以通过查看调用 Rc::strong_count 和 Rc::weak_count 所得到的值来判断这一点。

可视化 strong_count 和 weak_count 的变化

让我们创建一个新的内部作用域，并把 branch 的创建移到这个作用域中，来看看 Rc<Node> 实例的 strong_count 和 weak_count 值是如何变化的。这样，我们就能看到 branch 被创建，以及在离开作用域时被丢弃的过程中会发生什么。修改后的代码如示例 15-29 所示。

leaf 创建之后，它的 Rc<Node> 的强引用计数为 1，弱引用计数为 0。在内部作用域中，我们创建了 branch 并将它与 leaf 关联起来。此时打印计数，branch 中的 Rc<Node> 的强引用计数为 1，弱引用计数也为 1（因为 leaf.parent 通过 Weak<Node> 指向了 branch）。当我们打印 leaf 中的计数时，会看到它的强引用计数为 2，因为 branch 现在在 branch.children 中存储了 leaf 的 Rc<Node> 的一个克隆，但它的弱引用计数仍然为 0。

当内部作用域结束时，branch 离开作用域，其 Rc<Node> 的强引用计数减为 0，因此它的 Node 被丢弃。来自 leaf.parent 的弱引用计数 1 对 Node 是否被丢弃没有任何影响，所以我们不会遇到任何内存泄漏！

如果在作用域结束之后尝试访问 leaf 的父节点，我们会再次得到 None。在程序的末尾，leaf 中的 Rc<Node> 的强引用计数为 1，弱引用计数为 0，因为变量 leaf 再次成为了该 Rc<Node> 的唯一引用。

所有管理计数和值丢弃的逻辑都内置在 Rc<T> 和 Weak<T> 及其 Drop trait 的实现中。通过在 Node 的定义中规定子节点到其父节点的关系应该是一个 Weak<T> 引用，你就能让父节点指向子节点、子节点也指向父节点，而不会造成引用循环和内存泄漏。

总结

本章介绍了如何使用智能指针来提供与 Rust 默认通过普通引用所提供的不同的保证和权衡。Box<T> 类型具有已知的大小，并指向分配在堆上的数据。Rc<T> 类型会记录堆上数据的引用数量，使得数据可以拥有多个所有者。RefCell<T> 类型凭借其内部可变性，为我们提供了一种在需要不可变类型、却又需要修改该类型内部值时可以使用的类型；它还在运行时而不是编译时强制执行借用规则。

本章还讨论了 Deref 和 Drop trait，它们实现了智能指针的许多功能。我们探讨了可能导致内存泄漏的引用循环，以及如何使用 Weak<T> 来防止它们。
