从单线程服务器到多线程服务器

目前，服务器会依次处理每个请求，也就是说，在第一个连接处理完之前，它不会处理第二个连接。如果服务器收到的请求越来越多，这种串行执行的方式就会越来越不理想。如果服务器收到一个需要很长时间才能处理完的请求，那么即使后续的新请求能够很快处理完，它们也必须等到这个耗时的请求结束才行。我们需要解决这个问题，不过首先来实际看看这个问题。

使用线程池提高吞吐量

线程池（thread pool）是一组已经创建好的线程，它们处于就绪状态，等待着处理任务。当程序收到一个新任务时，会将池中的一个线程分配给这个任务，由该线程来处理它。在第一个线程处理任务期间，池中其余的线程可以处理任何其他到来的任务。当第一个线程处理完它的任务后，它会回到空闲线程池中，准备处理新的任务。线程池让你能够并发地处理连接，从而提高服务器的吞吐量。

我们会把池中的线程数量限制为一个较小的值，以防范 DoS 攻击；如果让程序在每个请求到来时都创建一个新线程，那么有人向服务器发起 1000 万个请求，就可能耗尽服务器的所有资源，使请求处理陷入停滞，造成严重破坏。

因此，我们不会无限制地创建线程，而是让固定数量的线程在池中等待。到来的请求会被发送到池中进行处理。线程池会维护一个传入请求的队列。池中的每个线程都会从这个队列中取出一个请求，处理该请求，然后再向队列索要下一个请求。采用这种设计，我们最多可以并发处理 N 个请求，其中 N 是线程的数量。如果每个线程都在响应一个长时间运行的请求，后续请求仍然可能在队列中堆积，但我们已经提高了在达到这种状况之前能够处理的长时间运行请求的数量。

这项技术只是提高 Web 服务器吞吐量的众多方法之一。你还可以探索其他方案，比如 fork/join 模型、单线程异步 I/O 模型以及多线程异步 I/O 模型。如果你对这个主题感兴趣，可以进一步了解其他解决方案并尝试实现它们；对于 Rust 这样的底层语言来说，所有这些方案都是可行的。

在开始实现线程池之前，我们先来讨论一下使用线程池应该是什么样子。当你尝试设计代码时，先编写客户端接口有助于指导你的设计。按照你希望调用的方式来组织代码的 API；然后在这个结构之内实现功能，而不是先实现功能再设计公有 API。

从 ThreadPool 向线程发送代码

我们在示例 21-14 的 for 循环中留下了一条关于创建线程的注释。这里我们来看看如何真正地创建线程。标准库提供了 thread::spawn 作为创建线程的方式，而 thread::spawn 期望在线程创建后立刻得到一些让线程运行的代码。然而，在我们的场景中，我们希望先创建线程，然后让它们等待我们之后发送过来的代码。标准库的线程实现并没有提供任何这样做的方法；我们必须手动实现它。

我们将在 ThreadPool 和线程之间引入一个新的数据结构来实现这种行为，由它来管理这一新行为。我们把这个数据结构称为 Worker，这是池化实现中的一个常用术语。Worker 会获取需要运行的代码，并在自己的线程中运行这些代码。

可以把它想象成在餐厅厨房里工作的人：员工们一直等到顾客的订单到来，然后负责接下这些订单并完成它们。

我们不再在线程池中存储由 JoinHandle<()> 实例组成的 vector，而是存储 Worker 结构体的实例。每个 Worker 会存储一个 JoinHandle<()> 实例。然后，我们会在 Worker 上实现一个方法，它接受一个包含待运行代码的闭包，并把它发送给已经在运行的线程去执行。我们还会给每个 Worker 一个 id，以便在记录日志或调试时能够区分池中不同的 Worker 实例。

下面是创建 ThreadPool 时将会发生的新流程。在以这种方式设置好 Worker 之后，我们再来实现把闭包发送给线程的代码：

  1. 定义一个 Worker 结构体，它持有一个 id 和一个 JoinHandle<()>。
  2. 修改 ThreadPool，让它持有一个由 Worker 实例组成的 vector。
  3. 定义一个 Worker::new 函数，它接受一个 id 数字，并返回一个 Worker 实例，该实例持有这个 id 以及一个用空闭包创建的线程。
  4. 在 ThreadPool::new 中，使用 for 循环的计数器生成一个 id，用这个 id 创建一个新的 Worker，并把这个 Worker 存储到 vector 中。

通过通道向线程发送请求

我们要解决的下一个问题是，传给 thread::spawn 的闭包什么也不做。目前，我们在 execute 方法中得到了想要执行的闭包。但在创建 ThreadPool 的过程中创建每个 Worker 时，我们就需要给 thread::spawn 一个要运行的闭包。

我们希望刚刚创建的 Worker 结构体能够从 ThreadPool 持有的队列中获取要运行的代码，并把这些代码发送到自己的线程中运行。

我们在第 16 章中学过的通道——一种在两个线程之间通信的简单方式——非常适合这个用例。我们将使用一个通道作为任务队列，execute 会把一个任务从 ThreadPool 发送给 Worker 实例，再由 Worker 把任务发送给它的线程。计划如下：

  1. ThreadPool 会创建一个通道，并持有发送端。
  2. 每个 Worker 都会持有接收端。
  3. 我们将创建一个新的 Job 结构体，用来存放想要通过通道发送的闭包。
  4. execute 方法会通过发送端发送它想要执行的任务。
  5. 在自己的线程中，Worker 会循环遍历它的接收端，并执行收到的任何任务的闭包。

这段代码试图把 receiver 传给多个 Worker 实例。这是行不通的，你应该还记得第 16 章讲过：Rust 提供的通道实现是多生产者、单消费者的。这意味着我们不能简单地克隆通道的消费端来修复这段代码。我们也不希望把一条消息多次发送给多个消费者；我们想要的是一个消息列表配上多个 Worker 实例，使得每条消息只被处理一次。

此外，从通道队列中取出一个任务需要修改 receiver，因此这些线程需要一种安全的方式来共享和修改 receiver；否则，我们可能会遇到竞态条件（第 16 章中介绍过）。

回想一下第 16 章中讨论过的线程安全的智能指针：为了在多个线程之间共享所有权，并允许这些线程修改值，我们需要使用 Arc<Mutex<T>>。Arc 类型能让多个 Worker 实例拥有接收端，而 Mutex 则能确保同一时间只有一个 Worker 从接收端获取任务。示例 21-18 展示了我们需要做出的修改。

在 ThreadPool::new 中，我们把接收端放进了一个 Arc 和一个 Mutex 中。对于每个新的 Worker，我们都会克隆这个 Arc 来增加引用计数，使得这些 Worker 实例能够共享接收端的所有权。

完成这些修改后，代码就能编译了！我们离目标越来越近了！

实现 execute 方法

最后，让我们来实现 ThreadPool 上的 execute 方法。我们还会把 Job 从结构体改为一个 trait 对象的类型别名，这个 trait 对象持有 execute 所接收的闭包类型。正如第 20 章“类型同义词与类型别名”部分所讨论的，类型别名可以把很长的类型变短，便于使用。请看示例 21-19。

使用在 execute 中得到的闭包创建一个新的 Job 实例之后，我们将这个任务发送到通道的发送端。我们对 send 调用了 unwrap，以应对发送失败的情况。例如，如果我们让所有线程都停止执行，也就意味着接收端已经停止接收新消息，那么就可能发生发送失败。目前，我们还无法让线程停止执行：只要线程池存在，线程就会一直执行下去。我们之所以使用 unwrap，是因为我们知道失败的情况不会发生，但编译器并不知道这一点。

不过我们还没有完全完成！在 Worker 中，传给 thread::spawn 的闭包仍然只是引用了通道的接收端。我们需要的是让这个闭包永远循环下去，不断向通道的接收端请求任务，并在得到任务时运行它。让我们对 Worker::new 做出示例 21-20 所示的修改。

在这里，我们首先对 receiver 调用 lock 来获取互斥锁，然后调用 unwrap，在出现任何错误时 panic。如果互斥锁处于中毒（poisoned）状态，获取锁就可能失败；当某个其他线程在持有锁期间 panic 而没有释放锁时，就会出现这种状态。在这种情况下，调用 unwrap 让当前线程 panic 是正确的做法。你也可以随意把这个 unwrap 改成 expect，并附上一条对你来说有意义的错误消息。

如果获得了互斥锁上的锁，我们就调用 recv 从通道中接收一个 Job。最后一个 unwrap 同样会略过这里可能出现的任何错误；如果持有发送端的线程已经关闭，就可能出现错误，这与接收端关闭时 send 方法会返回 Err 类似。

对 recv 的调用会阻塞，因此如果还没有任务，当前线程就会一直等待，直到有任务可用为止。Mutex<T> 确保了同一时间只有一个 Worker 线程在尝试请求任务。

在第 17 章和第 19 章中学习了 while let 循环之后，你可能会好奇，为什么我们没有像示例 21-21 那样编写 Worker 线程的代码。

这段代码可以编译和运行，但不会产生预期的线程行为：慢请求仍然会导致其他请求等待处理。原因有些微妙：Mutex 结构体没有公有的 unlock 方法，因为锁的所有权是基于 lock 方法所返回的 LockResult<MutexGuard<T>> 中 MutexGuard<T> 的生命周期的。这样一来，借用检查器就能在编译时强制执行这样一条规则：除非持有锁，否则不能访问由 Mutex 守护的资源。然而，如果我们不注意 MutexGuard<T> 的生命周期，这种实现也可能导致锁被持有的时间超出预期。

示例 21-20 中使用 let job = receiver.lock().unwrap().recv().unwrap(); 的代码之所以能够正常工作，是因为在使用 let 时，等号右侧表达式中用到的任何临时值都会在 let 语句结束时立即被丢弃。然而，while let（以及 if let 和 match）直到相关代码块结束时才会丢弃临时值。在示例 21-21 中，锁在调用 job() 的整个过程中一直被持有，这意味着其他 Worker 实例无法接收任务。
