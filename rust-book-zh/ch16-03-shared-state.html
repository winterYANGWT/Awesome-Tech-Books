Rust 程序设计语言

共享状态并发

消息传递是处理并发的一种好方法，但并不是唯一的方法。另一种方法是让多个线程访问同一份共享数据。再来看看 Go 语言文档中那句口号的这一部分：“不要通过共享内存来通信。”

通过共享内存来通信会是什么样子的？此外，为什么消息传递的拥护者会告诫人们不要使用内存共享呢？

从某种意义上说，任何编程语言中的通道都类似于单一所有权，因为一旦你把一个值发送到通道中，就不应该再使用这个值了。共享内存并发则类似于多重所有权：多个线程可以同时访问同一块内存位置。正如你在第 15 章中所看到的，智能指针让多重所有权成为可能，但多重所有权会增加复杂性，因为需要管理这些不同的所有者。Rust 的类型系统和所有权规则在正确地进行这种管理方面提供了极大的帮助。作为一个例子，我们来看看互斥锁，它是共享内存中较为常见的并发原语之一。

使用互斥锁控制访问

Mutex 是 mutual exclusion（互斥）的缩写，意思是互斥锁在任意时刻只允许一个线程访问某些数据。要访问互斥锁中的数据，线程必须先发出信号，表明它想要访问，具体做法是请求获取互斥锁的锁。锁（lock）是互斥锁的一部分，它是一种数据结构，用来记录当前是谁拥有对数据的独占访问权。因此，我们说互斥锁通过锁机制守护（guarding）着它所持有的数据。

互斥锁以难以使用著称，因为你必须记住两条规则：

  1. 在使用数据之前，必须先尝试获取锁。
  2. 用完互斥锁所守护的数据之后，必须解锁数据，这样其他线程才能获取锁。

用现实世界中的例子来比喻互斥锁：想象在一次会议上举行一场只有一支麦克风的小组讨论。在小组成员发言之前，他们必须先请求或示意自己想要使用麦克风。拿到麦克风之后，他们想讲多久就可以讲多久，讲完后再把麦克风交给下一位请求发言的小组成员。如果某位小组成员讲完之后忘了把麦克风交出去，其他人就都无法发言了。如果对这支共享麦克风的管理出了差错，小组讨论就无法按计划进行！

要正确地管理互斥锁可能极其棘手，这也是为什么那么多人热衷于使用通道。然而，得益于 Rust 的类型系统和所有权规则，你不会在加锁和解锁上出错。

Mutex<T> 的 API

作为如何使用互斥锁的一个例子，我们先在单线程环境中使用互斥锁，如示例 16-12 所示。

和很多类型一样，我们使用关联函数 new 来创建一个 Mutex<T>。要访问互斥锁内部的数据，我们使用 lock 方法来获取锁。这个调用会阻塞当前线程，使其在轮到我们拥有锁之前无法做任何工作。

如果另一个持有锁的线程发生了 panic，那么 lock 调用就会失败。在这种情况下，再也没有人能够获取这个锁了，所以我们选择使用 unwrap，在遇到这种情况时让当前线程 panic。

获取锁之后，我们就可以把返回值（在这里名为 num）当作指向内部数据的可变引用来使用。类型系统确保了我们在使用 m 中的值之前先获取锁。m 的类型是 Mutex<i32> 而不是 i32，所以我们必须调用 lock 才能使用这个 i32 值。我们不可能忘记这一点；否则类型系统不会允许我们访问内部的 i32。

lock 调用会返回一个名为 MutexGuard 的类型，它被包装在一个 LockResult 中，我们通过调用 unwrap 处理了这个 LockResult。MutexGuard 类型实现了 Deref，用来指向我们的内部数据；这个类型还提供了一个 Drop 实现，当 MutexGuard 离开作用域时会自动释放锁，这发生在内部作用域的末尾。因此，我们不用担心忘记释放锁而导致互斥锁无法被其他线程使用，因为锁的释放是自动进行的。

丢弃锁之后，我们可以打印互斥锁的值，可以看到我们成功地把内部的 i32 修改成了 6。

哇，这条错误信息真是啰嗦！需要关注的重点是这一部分：`Rc<Mutex<i32>>` cannot be sent between threads safely。编译器还告诉了我们原因：the trait `Send` is not implemented for `Rc<Mutex<i32>>`。我们会在下一节讨论 Send：它是确保我们在线程中使用的类型适用于并发场景的 trait 之一。

遗憾的是，Rc<T> 并不能安全地在线程间共享。当 Rc<T> 管理引用计数时，它会在每次调用 clone 时增加计数，并在每个克隆被丢弃时减少计数。但它没有使用任何并发原语来确保对计数的修改不会被另一个线程打断。这可能会导致计数出错——这类难以察觉的 bug 又可能进一步导致内存泄漏，或者导致某个值在我们用完之前就被丢弃了。我们需要的是一个和 Rc<T> 完全一样、但以线程安全的方式修改引用计数的类型。

使用 Arc<T> 进行原子引用计数

幸运的是，Arc<T> 正是这样一个类似于 Rc<T>、并且可以安全地用于并发场景的类型。其中的 a 代表原子（atomic），意思是它是一个原子引用计数（atomically reference-counted）类型。原子类型是另一种并发原语，这里我们不会详细介绍：更多细节请参阅标准库中 std::sync::atomic 的文档。目前你只需要知道，原子类型的工作方式类似于基本类型，但可以安全地在线程间共享。

你可能会好奇，为什么不是所有的基本类型都是原子的，以及为什么标准库中的类型没有默认实现为使用 Arc<T>。原因在于，线程安全会带来性能上的损耗，而你只希望在真正需要时才付出这种代价。如果你只是在单个线程中对值进行操作，那么代码无须强制提供原子类型所带来的那些保证，就可以运行得更快。

让我们回到这个例子：Arc<T> 和 Rc<T> 的 API 是相同的，所以我们只需修改 use 这一行、new 的调用以及 clone 的调用，就能修复程序。示例 16-15 中的代码终于可以编译并运行了。

比较 RefCell<T>/Rc<T> 与 Mutex<T>/Arc<T>

你可能已经注意到，counter 是不可变的，但我们却可以获取它内部值的可变引用；这意味着 Mutex<T> 提供了内部可变性，就像 Cell 家族一样。正如我们在第 15 章中使用 RefCell<T> 来修改 Rc<T> 内部的内容那样，我们使用 Mutex<T> 来修改 Arc<T> 内部的内容。

另一个需要注意的细节是，在使用 Mutex<T> 时，Rust 并不能保护你免受所有类型的逻辑错误。回想一下第 15 章，使用 Rc<T> 有造成引用循环的风险，即两个 Rc<T> 值相互引用，从而导致内存泄漏。类似地，Mutex<T> 也有造成死锁（deadlock）的风险。当一个操作需要锁住两个资源，而两个线程各自获取了其中一个锁时，就会发生死锁，导致它们永远相互等待。如果你对死锁感兴趣，可以尝试编写一个会发生死锁的 Rust 程序；然后研究任意一门语言中针对互斥锁的死锁缓解策略，并尝试在 Rust 中实现它们。标准库中 Mutex<T> 和 MutexGuard 的 API 文档提供了一些有用的信息。
