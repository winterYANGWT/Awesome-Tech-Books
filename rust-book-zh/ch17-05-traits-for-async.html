Rust 程序设计语言

深入了解异步相关的 trait

在本章中，我们以各种方式使用了 Future、Stream 和 StreamExt 这几个 trait。不过到目前为止，我们一直避免深入探究它们如何工作、彼此如何配合的细节，对于日常的 Rust 工作来说，这在大多数时候都没有问题。但有时你会遇到一些情况，需要再多了解一些这些 trait 的细节，以及 Pin 类型和 Unpin trait。在本节中，我们会深入到足以应对这些场景的程度，而把真正深入的探讨留给其他文档。

Future trait

我们先来仔细看看 Future trait 是如何工作的。Rust 是这样定义它的：

#![allow(unused)]
fn main() {
use std::pin::Pin;
use std::task::{Context, Poll};

pub trait Future {
    type Output;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
}

这个 trait 定义中包含了一堆新类型，还有一些我们之前没见过的语法，所以我们来逐一分析这个定义。

首先，Future 的关联类型 Output 表明了这个 future 最终会解析为什么。这类似于 Iterator trait 的关联类型 Item。其次，Future 有一个 poll 方法，它的 self 参数是一个特殊的 Pin 引用，另一个参数是 Context 类型的可变引用，返回值是 Poll<Self::Output>。稍后我们会进一步讨论 Pin 和 Context。现在，我们先关注这个方法的返回值，也就是 Poll 类型：

#![allow(unused)]
fn main() {
pub enum Poll<T> {
    Ready(T),
    Pending,
}
}

这个 Poll 类型与 Option 类似。它有一个带值的变体 Ready(T)，和一个不带值的变体 Pending。不过，Poll 表达的含义与 Option 大不相同！Pending 变体表示这个 future 还有工作要做，所以调用者需要稍后再来检查。Ready 变体则表示这个 Future 已经完成了它的工作，T 值已经可用。

注意：很少需要直接调用 poll，但如果你确实需要这么做，请记住，对于大多数 future 来说，在 future 返回 Ready 之后，调用者不应该再次调用 poll。许多 future 在就绪之后如果再被轮询，就会 panic。可以安全地再次轮询的 future 会在其文档中明确说明。这与 Iterator::next 的行为类似。

当你看到使用 await 的代码时，Rust 会在底层把它编译成调用 poll 的代码。回头看一下示例 17-4，我们在其中等单个 URL 的页面标题解析完成后将其打印出来，Rust 会把它编译成类似（但不完全是）下面这样的代码：

match page_title(url).poll() {
    Ready(page_title) => match page_title {
        Some(title) => println!("The title for {url} was {title}"),
        None => println!("{url} had no title"),
    }
    Pending => {
        // But what goes here?
    }
}

当 future 仍处于 Pending 状态时，我们该怎么办呢？我们需要某种方式来一次又一次地重试，直到这个 future 最终就绪。换句话说，我们需要一个循环：

let mut page_title_fut = page_title(url);
loop {
    match page_title_fut.poll() {
        Ready(value) => match page_title {
            Some(title) => println!("The title for {url} was {title}"),
            None => println!("{url} had no title"),
        }
        Pending => {
            // continue
        }
    }
}

然而，如果 Rust 真的把它编译成正好是这样的代码，那么每个 await 都会是阻塞的——这恰恰与我们的目标背道而驰！实际上，Rust 会确保这个循环能够把控制权交给某个东西，由它暂停这个 future 上的工作，转而处理其他 future，之后再回来检查这个 future。正如我们已经看到的，这个东西就是异步运行时，而这种调度和协调工作正是它的主要职责之一。

在“使用消息传递在两个任务之间发送数据”部分中，我们描述了对 rx.recv 的等待。recv 调用会返回一个 future，而等待这个 future 就会对它进行轮询。我们提到过，运行时会暂停这个 future，直到它就绪：要么得到 Some(message)，要么在通道关闭时得到 None。在对 Future trait，尤其是 Future::poll 有了更深入的了解之后，我们就能明白这是如何运作的了。当 future 返回 Poll::Pending 时，运行时就知道它还没有就绪。反过来，当 poll 返回 Poll::Ready(Some(message)) 或 Poll::Ready(None) 时，运行时就知道这个 future 已经就绪，并推进它。

运行时具体如何做到这一点的细节超出了本书的范围，但关键是要理解 future 的基本机制：运行时会轮询它所负责的每一个 future，并在 future 尚未就绪时让它重新进入休眠。

Pin 类型与 Unpin trait

回到示例 17-13，我们使用 trpl::join! 宏来等待三个 future。然而，更常见的情况是有一个集合（比如 vector），其中包含若干个 future，而具体数量要到运行时才能知道。我们把示例 17-13 改成示例 17-23 中的代码：把这三个 future 放进一个 vector，并改为调用 trpl::join_all 函数。不过这段代码目前还无法编译。

我们把每个 future 都放进一个 Box 中，把它们变成 trait 对象（trait object），就像我们在第 12 章“从 run 返回错误”部分中做的那样。（我们会在第 18 章详细介绍 trait 对象。）使用 trait 对象让我们可以把这些类型所产生的每个匿名 future 都当作同一种类型来对待，因为它们都实现了 Future trait。

这也许会让人感到意外。毕竟，这些 async 块都没有返回任何东西，所以每一个产生的都是 Future<Output = ()>。不过别忘了，Future 是一个 trait，而且编译器会为每个 async 块创建一个独一无二的枚举，即使它们的输出类型完全相同。正如你不能把两个不同的手写结构体放进同一个 Vec 中一样，你也不能混用编译器生成的不同枚举。

接着，我们把这个 future 的集合传给 trpl::join_all 函数，并等待其结果。然而，这段代码无法编译；以下是错误信息中的相关部分。

这条错误信息中的 note 告诉我们，应该使用 pin! 宏来固定（pin）这些值，也就是把它们放进 Pin 类型中，由 Pin 类型保证这些值不会在内存中被移动。错误信息表明之所以需要固定，是因为 dyn Future<Output = ()> 需要实现 Unpin trait，而它目前并没有实现。

trpl::join_all 函数返回一个名为 JoinAll 的结构体。这个结构体对类型 F 是泛型的，而 F 被约束为必须实现 Future trait。直接用 await 等待一个 future 时，会隐式地固定这个 future。这就是为什么我们不需要在每个想要等待 future 的地方都使用 pin!。

然而，我们在这里并不是直接等待一个 future。相反，我们是通过把一个 future 集合传给 join_all 函数，构造出一个新的 future，即 JoinAll。join_all 的签名要求集合中各项的类型都实现 Future trait，而只有当 Box<T> 所包装的 T 是一个实现了 Unpin trait 的 future 时，Box<T> 才会实现 Future。

要消化的东西可真不少！为了真正理解这一点，我们再深入一点，看看 Future trait 实际上是如何工作的，尤其是与固定相关的部分。再看一遍 Future trait 的定义：

#![allow(unused)]
fn main() {
use std::pin::Pin;
use std::task::{Context, Poll};

pub trait Future {
    type Output;

    // Required method
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
}

cx 参数及其 Context 类型，是运行时在保持惰性的同时，又能真正知道何时该去检查某个 future 的关键所在。同样，其工作原理的细节超出了本章的范围，通常只有在编写自定义的 Future 实现时才需要考虑这些。我们转而关注 self 的类型，因为这是我们第一次看到 self 带有类型注解的方法。self 的类型注解与其他函数参数的类型注解作用类似，但有两个关键区别：

  • 它告诉 Rust，要调用这个方法，self 必须是什么类型。
  • 它不能是任意类型。它只能是实现该方法的类型本身、指向该类型的引用或智能指针，或者包装了指向该类型的引用的 Pin。

我们会在第 18 章中进一步了解这种语法。目前只需要知道：如果想要轮询一个 future，检查它是 Pending 还是 Ready(Output)，我们就需要一个用 Pin 包装的、指向该类型的可变引用。

Pin 是一个用于包装类指针类型的包装器，这些类指针类型包括 &、&mut、Box 和 Rc。（严格来说，Pin 适用于实现了 Deref 或 DerefMut trait 的类型，但这实际上等同于只适用于引用和智能指针。）Pin 本身并不是指针，也不像 Rc 和 Arc 那样拥有引用计数之类的自身行为；它纯粹是一个工具，编译器可以利用它来强制施加对指针用法的约束。

回想一下，await 是通过调用 poll 来实现的，这开始能够解释我们之前看到的那条错误信息了，但那条信息说的是 Unpin，而不是 Pin。那么，Pin 和 Unpin 究竟有什么关系？为什么 Future 要求 self 必须位于 Pin 类型中才能调用 poll？

还记得本章前面讲过，future 中的一系列 await 点会被编译成一个状态机，而编译器会确保这个状态机遵守 Rust 关于安全性的所有常规规则，包括借用和所有权。为了做到这一点，Rust 会查看从一个 await 点到下一个 await 点（或者到 async 块的末尾）之间需要用到哪些数据，然后在编译出的状态机中创建一个相应的变体。每个变体都会获得对源代码中这一段将要用到的数据的所需访问权限，可能是获取这些数据的所有权，也可能是获取对它们的可变或不可变引用。

到目前为止一切顺利：如果我们在某个 async 块中把所有权或引用搞错了，借用检查器会告诉我们。可一旦我们想要到处移动与这个块对应的 future——比如把它移动到一个 Vec 中，再传给 join_all——事情就变得棘手起来了。

当我们移动一个 future 时——无论是把它推入某个数据结构，以便作为迭代器配合 join_all 使用，还是从函数中返回它——实际上意味着移动 Rust 为我们创建的那个状态机。与 Rust 中大多数其他类型不同，Rust 为 async 块创建的 future，可能会在其任意变体的字段中包含指向自身的引用，如图 17-4 中的简化示意图所示。

不过，默认情况下，任何包含指向自身引用的对象被移动都是不安全的，因为引用总是指向它所引用之物的实际内存地址（见图 17-5）。如果你移动了数据结构本身，那些内部引用仍会指向旧的位置。然而，那块内存位置现在已经无效了。一方面，当你修改这个数据结构时，那块内存中的值不会随之更新。另一方面——也是更重要的一点——计算机现在可以自由地把那块内存另作他用！之后你可能会读到完全不相干的数据。

理论上，Rust 编译器可以在对象每次被移动时，尝试更新指向它的每一个引用，但这可能会带来大量的性能开销，尤其是当需要更新的是一整张引用网的时候。如果我们能够转而确保相关的数据结构不会在内存中移动，就根本不需要更新任何引用了。这正是 Rust 借用检查器的用途所在：在安全代码中，它会阻止你移动任何还有活跃引用指向它的项。

Pin 在此基础上为我们提供了所需的确切保证。当我们通过把指向某个值的指针包装在 Pin 中来固定这个值时，它就再也不能移动了。因此，如果你有一个 Pin<Box<SomeType>>，实际上被固定的是 SomeType 值，而不是 Box 指针。图 17-6 展示了这个过程。

事实上，Box 指针仍然可以自由地移动。记住：我们关心的是确保最终被引用的数据待在原地不动。如果指针移动了，但它所指向的数据仍在原来的位置，如图 17-7 所示，那就不会有任何潜在的问题。（作为一个独立的练习，你可以查阅这些类型以及 std::pin 模块的文档，尝试弄清楚如何用包装了 Box 的 Pin 做到这一点。）关键在于，自引用类型本身不能移动，因为它仍然处于被固定的状态。

不过，大多数类型都可以完全安全地到处移动，即使它们恰好位于 Pin 指针之后。只有当项含有内部引用时，我们才需要考虑固定的问题。数字和布尔值这样的基本类型值是安全的，因为它们显然没有任何内部引用。你在 Rust 中平时使用的大多数类型也都没有。例如，你可以放心地到处移动一个 Vec。根据我们目前所了解的，如果你有一个 Pin<Vec<String>>，你就必须通过 Pin 提供的那些安全但受限的 API 来完成所有操作，尽管在没有其他引用指向 Vec<String> 时，移动它总是安全的。我们需要一种方式来告诉编译器，在这类情况下移动项是没问题的——这就轮到 Unpin 登场了。

Unpin 是一个标记 trait（marker trait），类似于我们在第 16 章中见过的 Send 和 Sync trait，因此它本身没有任何功能。标记 trait 存在的唯一目的，就是告诉编译器在特定的上下文中使用实现了某个 trait 的类型是安全的。Unpin 告诉编译器，某个给定的类型不需要维护任何关于相关的值能否被安全移动的保证。

和 Send 与 Sync 一样，对于所有能够证明是安全的类型，编译器都会自动为它们实现 Unpin。同样与 Send 和 Sync 类似，有一种特殊情况是某个类型没有实现 Unpin。它的表示法是 impl !Unpin for SomeType，其中 SomeType 是这样一个类型的名称：每当指向该类型的指针被用在 Pin 中时，它确实需要维护那些保证才能确保安全。

换句话说，关于 Pin 和 Unpin 之间的关系，有两点需要记住。第一，Unpin 是“常规”情况，而 !Unpin 是特殊情况。第二，一个类型实现的是 Unpin 还是 !Unpin，只有在你使用指向该类型的固定指针（比如 Pin<&mut SomeType>）时才有意义。

为了更具体地说明这一点，想一想 String：它有一个长度，以及组成它的 Unicode 字符。我们可以把 String 包装在 Pin 中，如图 17-8 所示。不过，和 Rust 中的大多数其他类型一样，String 会自动实现 Unpin。

因此，我们可以做一些在 String 实现了 !Unpin 时属于非法的操作，比如像图 17-9 那样，在内存中完全相同的位置上用另一个字符串替换原来的字符串。这并不违反 Pin 的约定，因为 String 没有任何会让移动变得不安全的内部引用。这也正是它实现 Unpin 而不是 !Unpin 的原因。

现在，我们已经足以理解示例 17-23 中那个 join_all 调用所报告的错误了。我们最初试图把 async 块产生的 future 移动到一个 Vec<Box<dyn Future<Output = ()>>> 中，但正如我们所看到的，这些 future 可能含有内部引用，因此它们不会自动实现 Unpin。一旦固定了它们，我们就可以把得到的 Pin 类型传入 Vec，并且可以确信 future 中的底层数据不会被移动。示例 17-24 展示了如何修复这段代码：在定义三个 future 的地方分别调用 pin! 宏，并调整 trait 对象的类型。

现在这个示例可以编译并运行了，而且我们可以在运行时向 vector 中添加或移除 future，并把它们全部合并起来。

Pin 和 Unpin 主要在构建底层库或者构建运行时本身的时候才显得重要，而不是在日常的 Rust 代码中。不过，当你在错误信息中看到这些 trait 时，现在你就能更清楚地知道该如何修复代码了！

注意：Pin 和 Unpin 的这种组合，使得在 Rust 中安全地实现一整类复杂类型成为可能，否则这些类型会因为是自引用的而难以实现。需要 Pin 的类型如今最常出现在异步 Rust 中，不过偶尔你也可能在其他场景中看到它们。

Pin 和 Unpin 的具体工作原理，以及它们必须遵守的规则，在 std::pin 的 API 文档中有详尽的介绍，所以如果你有兴趣了解更多，那里是一个很好的起点。

如果你想更详细地了解底层的工作原理，请参阅 Asynchronous Programming in Rust 的第 2 章和第 4 章。

Stream trait

既然你已经对 Future、Pin 和 Unpin 这几个 trait 有了更深入的理解，我们就可以把注意力转向 Stream trait 了。正如你在本章前面学到的，流类似于异步迭代器。不过，与 Iterator 和 Future 不同的是，截至本书撰写时，标准库中还没有 Stream 的定义，但确实有一个来自 futures crate 的非常通用的定义，在整个生态系统中被广泛使用。

在看 Stream trait 如何把 Iterator 和 Future 这两个 trait 结合起来之前，我们先回顾一下它们的定义。从 Iterator 那里，我们得到了序列的概念：它的 next 方法提供一个 Option<Self::Item>。从 Future 那里，我们得到了随时间推移逐渐就绪的概念：它的 poll 方法提供一个 Poll<Self::Output>。为了表示一个随时间推移逐渐就绪的项的序列，我们定义了一个把这些特性结合在一起的 Stream trait：

#![allow(unused)]
fn main() {
use std::pin::Pin;
use std::task::{Context, Poll};

trait Stream {
    type Item;

    fn poll_next(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>
    ) -> Poll<Option<Self::Item>>;
}
}

Stream trait 定义了一个名为 Item 的关联类型，表示流所产生的项的类型。这与 Iterator 类似，可能有零个到多个项；而与 Future 不同，后者总是只有一个 Output，即使它是单元类型 ()。

Stream 还定义了一个用来获取这些项的方法。我们把它命名为 poll_next，以表明它像 Future::poll 那样进行轮询，又像 Iterator::next 那样产生一系列的项。它的返回类型把 Poll 和 Option 结合在了一起。外层类型是 Poll，因为它和 future 一样，需要检查是否就绪。内层类型是 Option，因为它和迭代器一样，需要表明是否还有更多的消息。

与这个定义非常相似的东西很可能最终会成为 Rust 标准库的一部分。在此期间，它是大多数运行时工具集的一部分，所以你可以依赖它，我们接下来介绍的所有内容通常都是适用的！

不过，在“流：按顺序排列的 future”部分的示例中，我们并没有使用 poll_next 或 Stream，而是使用了 next 和 StreamExt。当然，我们可以通过手写自己的 Stream 状态机，直接基于 poll_next API 来工作，就像我们可以直接通过 future 的 poll 方法来使用它们一样。不过，使用 await 要好得多，而 StreamExt trait 提供了 next 方法，让我们正好可以这样做：

#![allow(unused)]
fn main() {
use std::pin::Pin;
use std::task::{Context, Poll};

trait Stream {
    type Item;
    fn poll_next(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>,
    ) -> Poll<Option<Self::Item>>;
}

trait StreamExt: Stream {
    async fn next(&mut self) -> Option<Self::Item>
    where
        Self: Unpin;

    // other methods...
}
}

注意：我们在本章前面实际使用的定义与此略有不同，因为它要支持那些尚不支持在 trait 中使用异步函数的 Rust 版本。因此，它看起来是这样的：

fn next(&mut self) -> Next<'_, Self> where Self: Unpin;

这个 Next 类型是一个实现了 Future 的 struct，它让我们可以用 Next<'_, Self> 来为指向 self 的引用的生命周期命名，这样 await 就能配合这个方法使用了。

StreamExt trait 也是所有可用于流的有趣方法的所在之处。对于每一个实现了 Stream 的类型，StreamExt 都会被自动实现，但这两个 trait 是分开定义的，这样社区就可以不断迭代改进各种便捷的 API，而不会影响到作为基础的那个 trait。

在 trpl crate 所使用的 StreamExt 版本中，这个 trait 不仅定义了 next 方法，还提供了 next 的默认实现，正确地处理了调用 Stream::poll_next 的细节。这意味着，即使你需要编写自己的流式数据类型，也只需要实现 Stream，之后任何使用你的数据类型的人都可以自动对它使用 StreamExt 及其方法。

关于这些 trait 的底层细节，我们就介绍到这里。最后，让我们来思考一下 future（包括流）、任务和线程是如何结合在一起的！
