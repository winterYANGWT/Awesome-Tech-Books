Rust 程序设计语言

实现一种面向对象设计模式

状态模式（state pattern）是一种面向对象设计模式。该模式的关键在于，我们定义一个值在内部可能拥有的一组状态。这些状态由一组状态对象（state object）表示，而值的行为会根据其状态而改变。我们将通过一个博客文章结构体的例子来讲解，这个结构体有一个字段用于保存其状态，该状态是“草稿”“审核中”“已发布”这一组状态对象中的一个。

这些状态对象共享功能：当然，在 Rust 中我们使用的是结构体和 trait，而不是对象和继承。每个状态对象负责自身的行为，并决定自己何时应当转变为另一种状态。持有状态对象的值对各个状态的不同行为、以及何时在状态之间转换一无所知。

使用状态模式的优点在于，当程序的业务需求发生变化时，我们无需修改持有状态的值的代码，也无需修改使用该值的代码。我们只需更新某个状态对象内部的代码来改变它的规则，或者再增加一些状态对象。

首先，我们会以一种更传统的面向对象方式来实现状态模式。然后，我们会使用一种在 Rust 中更自然一些的方法。让我们深入进去，使用状态模式逐步实现一个博客文章的工作流程。

最终的功能如下：

  1. 博客文章一开始是一份空白的草稿。
  2. 草稿完成后，请求对文章进行审核。
  3. 文章通过审核后，就会被发布。
  4. 只有已发布的博客文章才会返回可供打印的内容，这样未经审核的文章就不会被意外发布。

对文章尝试进行的任何其他修改都不应产生效果。例如，如果我们在请求审核之前就尝试批准一篇博客文章草稿，那么这篇文章应当仍然是一份未发布的草稿。

尝试传统的面向对象风格

组织代码来解决同一个问题的方式有无数种，每种都有不同的权衡。本节的实现更接近传统的面向对象风格，这种风格在 Rust 中也可以写出来，但没有利用 Rust 的某些优势。稍后，我们会展示另一种解决方案，它仍然使用面向对象设计模式，但组织方式对有面向对象经验的程序员来说可能不那么熟悉。我们会对比这两种方案，体会以不同于其他语言的方式设计 Rust 代码所带来的权衡。

示例 18-11 以代码形式展示了这个工作流程：这是我们将在名为 blog 的库 crate 中实现的 API 的一个用法示例。这段代码目前还无法编译，因为我们还没有实现 blog crate。

我们希望允许用户使用 Post::new 创建一篇新的博客文章草稿。我们希望能够向博客文章中添加文本。如果我们在审核通过之前就立即尝试获取文章的内容，那么应该得不到任何文本，因为这篇文章仍然是草稿。出于演示目的，我们在代码中添加了 assert_eq!。针对这一点，一个很好的单元测试是断言博客文章草稿的 content 方法返回空字符串，不过我们不会为这个例子编写测试。

接下来，我们希望能够请求审核文章，并且希望在等待审核期间 content 返回空字符串。当文章通过审核时，它就应当被发布，这意味着调用 content 时会返回文章的文本。

注意，我们与这个 crate 交互时用到的唯一类型是 Post 类型。这个类型会使用状态模式，并持有一个值，这个值是三种状态对象之一，分别代表文章可能处于的各种状态——草稿、审核中或已发布。从一种状态转变为另一种状态的过程会在 Post 类型内部进行管理。状态会随着库的用户对 Post 实例调用的方法而改变，但用户不必直接管理状态的变化。此外，用户也不会在状态上犯错，比如在文章审核之前就将其发布。

定义 Post 并创建新实例

让我们开始实现这个库吧！我们知道需要一个公有的 Post 结构体来存放一些内容，所以先从这个结构体的定义开始，再定义一个关联的公有函数 new 来创建 Post 的实例，如示例 18-12 所示。我们还会创建一个私有的 State trait，它定义了 Post 的所有状态对象都必须具备的行为。

接着，Post 会在一个名为 state 的私有字段中，用 Option<T> 包裹一个 Box<dyn State> trait 对象来保存状态对象。稍后你就会明白为什么需要 Option<T>。

State trait 定义了不同文章状态所共有的行为。状态对象有 Draft、PendingReview 和 Published，它们都会实现 State trait。目前，这个 trait 还没有任何方法，我们先只定义 Draft 状态，因为这是我们希望文章开始时所处的状态。

当我们创建一个新的 Post 时，会把它的 state 字段设置为一个存放着 Box 的 Some 值。这个 Box 指向一个新的 Draft 结构体实例。这就确保了每当我们创建一个新的 Post 实例时，它都会从草稿状态开始。由于 Post 的 state 字段是私有的，因此无法创建处于其他任何状态的 Post！在 Post::new 函数中，我们把 content 字段设置为一个新的空 String。

存储文章内容的文本

我们在示例 18-11 中看到，我们希望能够调用一个名为 add_text 的方法，并向它传递一个 &str，这个 &str 随后会被添加为博客文章的文本内容。我们把它实现为一个方法，而不是把 content 字段以 pub 的形式暴露出去，这样以后我们就可以实现一个方法来控制如何读取 content 字段中的数据。add_text 方法非常简单直接，所以让我们把示例 18-13 中的实现添加到 impl Post 块中。

add_text 方法获取 self 的可变引用，因为我们要修改调用 add_text 的那个 Post 实例。然后，我们对 content 中的 String 调用 push_str，并传入 text 参数，将其追加到已保存的 content 中。这一行为并不取决于文章所处的状态，所以它不属于状态模式的一部分。add_text 方法完全不与 state 字段交互，但它是我们想要支持的行为的一部分。

确保草稿文章的内容为空

即使我们已经调用了 add_text 并向文章中添加了一些内容，我们仍然希望 content 方法返回一个空的字符串切片，因为这篇文章仍处于草稿状态，正如示例 18-11 中第一个 assert_eq! 所示。现在，我们先用能满足这个要求的最简单的方式来实现 content 方法：总是返回一个空的字符串切片。等到我们实现了改变文章状态、使其能够发布的功能后，再来修改它。到目前为止，文章只能处于草稿状态，所以文章内容应当总是为空。示例 18-14 展示了这个占位实现。

添加了这个 content 方法之后，示例 18-11 中直到第一个 assert_eq! 为止的所有代码都能按预期工作了。

请求审核，从而改变文章的状态

接下来，我们需要添加请求审核文章的功能，它应当把文章的状态从 Draft 变为 PendingReview。示例 18-15 展示了这段代码。

我们为 Post 提供一个名为 request_review 的公有方法，它获取 self 的可变引用。然后，我们对 Post 的当前状态调用一个内部的 request_review 方法，这第二个 request_review 方法会消费当前状态并返回一个新状态。

我们把 request_review 方法添加到 State trait 中；现在所有实现了该 trait 的类型都需要实现 request_review 方法。注意，这个方法的第一个参数不是 self、&self 或 &mut self，而是 self: Box<Self>。这种语法意味着该方法只有在持有该类型的 Box 上调用时才有效。这种语法会获取 Box<Self> 的所有权，使旧状态失效，从而让 Post 的状态值可以转变为新的状态。

为了消费旧状态，request_review 方法需要获取状态值的所有权。这正是 Post 的 state 字段中的 Option 发挥作用的地方：我们调用 take 方法，把 Some 值从 state 字段中取出，并在原处留下一个 None，因为 Rust 不允许结构体中存在未填充的字段。这让我们能够把 state 值从 Post 中移出，而不是借用它。然后，我们会把文章的 state 值设置为这次操作的结果。

我们需要暂时把 state 设置为 None，而不是用类似 self.state = self.state.request_review(); 这样的代码直接设置它，这样才能获得 state 值的所有权。这就确保了在我们把旧的 state 值转换为新状态之后，Post 无法再使用它。

Draft 上的 request_review 方法返回一个新的、装箱的 PendingReview 结构体实例，它表示文章正在等待审核时的状态。PendingReview 结构体同样实现了 request_review 方法，但不做任何转换，而是返回它自身，因为当我们对一篇已经处于 PendingReview 状态的文章请求审核时，它应当继续保持 PendingReview 状态。

现在我们可以开始看出状态模式的优点了：无论 Post 的 state 值是什么，Post 上的 request_review 方法都是一样的。每个状态都负责自己的规则。

我们会让 Post 上的 content 方法保持原样，即返回一个空的字符串切片。现在，Post 既可以处于 Draft 状态，也可以处于 PendingReview 状态，而我们希望在 PendingReview 状态下也有同样的行为。现在，示例 18-11 直到第二个 assert_eq! 调用为止都可以正常工作了！

添加 approve 来改变 content 的行为

approve 方法与 request_review 方法类似：它会把 state 设置为当前状态在被批准时所应有的值，如示例 18-16 所示。

我们把 approve 方法添加到 State trait 中，并新增一个实现了 State 的结构体，即 Published 状态。

与 PendingReview 上 request_review 的工作方式类似，如果我们对 Draft 调用 approve 方法，它不会产生任何效果，因为 approve 会返回 self。当我们对 PendingReview 调用 approve 时，它会返回一个新的、装箱的 Published 结构体实例。Published 结构体实现了 State trait，对于 request_review 方法和 approve 方法，它都会返回自身，因为在这些情况下文章应当保持在 Published 状态。

现在我们需要更新 Post 上的 content 方法。我们希望 content 返回的值取决于 Post 的当前状态，所以要让 Post 委托给定义在其 state 上的 content 方法，如示例 18-17 所示。

因为我们的目标是把所有这些规则都保留在实现了 State 的结构体内部，所以我们对 state 中的值调用 content 方法，并把文章实例（也就是 self）作为参数传入。然后，返回对 state 值调用 content 方法所得到的值。

我们对 Option 调用 as_ref 方法，因为我们需要的是 Option 中值的引用，而不是值的所有权。由于 state 是 Option<Box<dyn State>>，调用 as_ref 时会返回 Option<&Box<dyn State>>。如果不调用 as_ref，就会得到一个错误，因为我们不能把 state 从函数参数中借用的 &self 中移出。

接着我们调用 unwrap 方法，我们知道它永远不会 panic，因为我们知道 Post 上的方法能够确保在它们执行完毕时，state 总是包含一个 Some 值。这正是我们在第 9 章“当你比编译器掌握更多信息时”部分讨论过的情况之一：我们知道 None 值永远不可能出现，尽管编译器无法理解这一点。

此时，当我们对 &Box<dyn State> 调用 content 时，解引用强制转换会作用于 & 和 Box，因此 content 方法最终会在实现了 State trait 的类型上被调用。这意味着我们需要把 content 添加到 State trait 的定义中，并在那里放置根据当前状态决定返回什么内容的逻辑，如示例 18-18 所示。

我们为 content 方法添加了一个返回空字符串切片的默认实现。这意味着我们不需要在 Draft 和 PendingReview 结构体上实现 content。Published 结构体会覆盖 content 方法，并返回 post.content 中的值。虽然这样很方便，但让 State 上的 content 方法来决定 Post 的内容，模糊了 State 的职责与 Post 的职责之间的界限。

注意，正如我们在第 10 章讨论过的那样，这个方法需要生命周期注解。我们获取一个 post 的引用作为参数，并返回该 post 某一部分的引用，因此返回的引用的生命周期与 post 参数的生命周期相关。

大功告成——示例 18-11 的全部代码现在都能工作了！我们已经用博客文章工作流程的规则实现了状态模式。与这些规则相关的逻辑存在于状态对象中，而不是分散在 Post 的各处。

为什么不用枚举？

你可能一直在想，为什么我们不使用一个以各种可能的文章状态作为变体的枚举。这当然也是一种可行的解决方案；你可以试一试，然后比较最终的结果，看看你更喜欢哪一种！使用枚举的一个缺点是，每个检查枚举值的地方都需要一个 match 表达式或类似的结构来处理每一种可能的变体。这可能会比这种 trait 对象方案更加重复。

评估状态模式

我们已经展示了 Rust 能够实现面向对象的状态模式，来封装文章在各个状态下应有的不同行为。Post 上的方法对这些不同的行为一无所知。由于我们组织代码的方式，要了解已发布的文章可能有哪些不同的行为，只需查看一个地方：Published 结构体上对 State trait 的实现。

如果我们要创建一个不使用状态模式的替代实现，可能会改为在 Post 的方法中，甚至在 main 代码中使用 match 表达式来检查文章的状态，并在这些地方改变行为。这意味着我们必须查看好几个地方，才能理解文章处于已发布状态时的全部影响。

使用状态模式时，Post 的方法以及使用 Post 的地方都不需要 match 表达式；要添加一个新状态，只需添加一个新的结构体，并在一处为这一个结构体实现 trait 方法即可。

使用状态模式的实现很容易扩展以添加更多功能。为了体会维护使用状态模式的代码有多简单，可以试试下面这些建议：

  • 添加一个 reject 方法，将文章的状态从 PendingReview 改回 Draft。
  • 要求调用两次 approve 之后，状态才能变为 Published。
  • 只允许用户在文章处于 Draft 状态时添加文本内容。提示：让状态对象负责内容可能发生的变化，但不负责修改 Post。

状态模式的一个缺点是，由于状态之间的转换是由状态自身实现的，因此有些状态之间是相互耦合的。如果我们在 PendingReview 和 Published 之间添加另一个状态，比如 Scheduled，就必须修改 PendingReview 中的代码，让它转换到 Scheduled。如果 PendingReview 不需要因为新增状态而改变，工作量就会少一些，但那就意味着要换用另一种设计模式了。

另一个缺点是我们重复了一些逻辑。为了消除部分重复，我们可能会尝试为 State trait 上的 request_review 和 approve 方法提供返回 self 的默认实现。然而，这行不通：当把 State 用作 trait 对象时，trait 并不确切知道具体的 self 会是什么，因此返回类型在编译时是未知的。（这是前面提到的 dyn 兼容性规则之一。）

其他重复之处还包括 Post 上 request_review 和 approve 方法的实现很相似。这两个方法都对 Post 的 state 字段使用 Option::take，并且如果 state 是 Some，就委托给被包裹的值对同一方法的实现，再把 state 字段的新值设置为其结果。如果 Post 上有很多遵循这种模式的方法，我们可能会考虑定义一个宏来消除重复（参见第 20 章“宏”部分）。

完全按照面向对象语言中的定义来实现状态模式，并没有尽可能充分地利用 Rust 的优势。让我们来看看可以对 blog crate 做哪些修改，从而把无效的状态和转换变成编译时错误。

将状态和行为编码为类型

我们将向你展示如何重新思考状态模式，以获得另一组不同的权衡。我们不再把状态和转换完全封装起来、让外部代码对它们一无所知，而是把状态编码成不同的类型。这样一来，Rust 的类型检查系统就会通过产生编译器错误，来阻止在只允许使用已发布文章的地方使用草稿文章。

让我们来看看示例 18-11 中 main 的第一部分：

我们仍然支持使用 Post::new 创建处于草稿状态的新文章，以及向文章内容中添加文本的功能。但我们不再让草稿文章拥有一个返回空字符串的 content 方法，而是让草稿文章根本没有 content 方法。这样，如果我们尝试获取草稿文章的内容，就会得到一个编译器错误，告诉我们该方法不存在。因此，我们不可能在生产环境中意外地显示草稿文章的内容，因为那样的代码根本无法编译。示例 18-19 展示了 Post 结构体和 DraftPost 结构体的定义，以及它们各自的方法。

Post 和 DraftPost 结构体都有一个私有的 content 字段，用来存储博客文章的文本。这两个结构体都不再有 state 字段，因为我们把状态的编码转移到了结构体的类型上。Post 结构体将代表一篇已发布的文章，它有一个返回 content 的 content 方法。

我们仍然有一个 Post::new 函数，但它返回的不是 Post 的实例，而是 DraftPost 的实例。由于 content 是私有的，并且没有任何函数返回 Post，所以现在无法创建 Post 的实例。

DraftPost 结构体有一个 add_text 方法，因此我们可以像以前一样向 content 添加文本，但请注意，DraftPost 并没有定义 content 方法！所以现在程序确保了所有文章都从草稿文章开始，而草稿文章的内容无法用于显示。任何试图绕过这些约束的做法都会导致编译器错误。

那么，我们如何得到一篇已发布的文章呢？我们希望强制执行这样一条规则：草稿文章必须经过审核和批准才能发布。处于待审核状态的文章仍然不应显示任何内容。让我们通过添加另一个结构体 PendingReviewPost 来实现这些约束：在 DraftPost 上定义返回 PendingReviewPost 的 request_review 方法，并在 PendingReviewPost 上定义返回 Post 的 approve 方法，如示例 18-20 所示。

request_review 和 approve 方法获取 self 的所有权，从而消费 DraftPost 和 PendingReviewPost 实例，并分别把它们转换为 PendingReviewPost 和已发布的 Post。这样，在我们对 DraftPost 实例调用 request_review 之后，就不会再残留任何 DraftPost 实例，以此类推。PendingReviewPost 结构体上没有定义 content 方法，所以与 DraftPost 一样，尝试读取它的内容会导致编译器错误。因为获得一个定义了 content 方法的已发布 Post 实例的唯一途径，是对 PendingReviewPost 调用 approve 方法，而获得 PendingReviewPost 的唯一途径，是对 DraftPost 调用 request_review 方法，所以我们现在已经把博客文章的工作流程编码进了类型系统。

不过，我们还需要对 main 做一些小的修改。request_review 和 approve 方法返回的是新实例，而不是修改调用它们的结构体，所以我们需要添加更多 let post = 遮蔽赋值来保存返回的实例。我们也不能再保留那些断言草稿文章和待审核文章的内容为空字符串的断言，而且也不再需要它们：试图使用处于这些状态的文章内容的代码已经无法编译了。示例 18-21 展示了 main 中更新后的代码。

我们需要对 main 做出重新赋值 post 的修改，这意味着这个实现已经不再完全遵循面向对象的状态模式了：状态之间的转换不再完全封装在 Post 的实现内部。然而，我们的收获是，借助类型系统以及在编译时进行的类型检查，无效状态现在已经不可能出现了！这确保了某些 bug，比如显示未发布文章的内容，会在进入生产环境之前就被发现。

请在示例 18-21 之后的 blog crate 上尝试完成本节开头建议的那些任务，看看你对这个版本代码的设计有何看法。注意，在这种设计中，有些任务可能已经完成了。

我们已经看到，尽管 Rust 能够实现面向对象设计模式，但 Rust 中也可以使用其他模式，比如把状态编码到类型系统中。这些模式有着不同的权衡。虽然你可能非常熟悉面向对象模式，但重新思考问题以利用 Rust 的特性能够带来好处，比如在编译时就防止某些 bug。由于 Rust 具有所有权等面向对象语言所没有的特性，面向对象模式在 Rust 中并不总是最佳的解决方案。

总结

无论读完本章后你是否认为 Rust 是一门面向对象语言，你现在都知道了可以使用 trait 对象在 Rust 中获得一些面向对象的特性。动态分发能够以少量运行时性能为代价，为你的代码带来一定的灵活性。你可以利用这种灵活性来实现面向对象模式，从而提高代码的可维护性。Rust 还拥有所有权等面向对象语言所没有的其他特性。面向对象模式并不总是利用 Rust 优势的最佳方式，但它是一个可用的选项。

接下来，我们将学习模式，这是 Rust 中另一个能够带来大量灵活性的特性。我们在本书中已经简单地接触过它们，但还没有见识过它们的全部能力。让我们开始吧！
