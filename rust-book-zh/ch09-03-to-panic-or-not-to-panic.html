Rust 程序设计语言

要不要 panic!

那么，该如何决定什么时候应该调用 panic!，什么时候应该返回 Result 呢？代码 panic 之后就无法恢复了。不论是否存在恢复的可能，你都可以在任何错误情况下调用 panic!，但这样一来，你就是在替调用代码做出“这种情况不可恢复”的决定。当你选择返回 Result 值时，你就把选择权交给了调用代码。调用代码可以选择以适合其自身情况的方式尝试恢复，也可以认定此时的 Err 值不可恢复，于是调用 panic!，把你的可恢复错误变成不可恢复错误。因此，在定义一个可能失败的函数时，返回 Result 是一个不错的默认选择。

在示例、原型代码和测试这类场景中，编写会 panic 的代码比返回 Result 更合适。我们先来探讨原因，然后讨论编译器无法判断失败不可能发生、而你作为人类却可以判断的情况。本章最后会给出一些通用的指导原则，帮助你决定在库代码中是否应该 panic。

示例、原型代码与测试

当你编写示例来阐明某个概念时，如果同时加入健壮的错误处理代码，可能会让示例变得不那么清晰。在示例中，大家都明白，对 unwrap 这类可能 panic 的方法的调用只是一个占位符，代表你希望应用程序处理错误的方式，而具体方式可能因代码其余部分的功能而异。

同样，在编写原型、尚未准备好决定如何处理错误时，unwrap 和 expect 方法非常方便。它们会在代码中留下清晰的标记，等你准备好让程序变得更健壮时再来处理。

如果测试中的某个方法调用失败了，你会希望整个测试都失败，即使这个方法并不是被测试的功能。因为 panic! 正是将测试标记为失败的方式，所以调用 unwrap 或 expect 恰恰就是应该发生的事情。

当你比编译器掌握更多信息时

当你有其他某种逻辑能确保 Result 一定是 Ok 值，但编译器无法理解这种逻辑时，调用 expect 也是合适的。你仍然会得到一个需要处理的 Result 值：你所调用的操作在一般情况下仍然有失败的可能，尽管在你的特定情况下从逻辑上讲这是不可能的。如果你通过人工检查代码能够确保永远不会出现 Err 变体，那么调用 expect 并在参数文本中写明你认为永远不会出现 Err 变体的理由，是完全可以接受的。下面是一个例子：

fn main() {
    use std::net::IpAddr;

    let home: IpAddr = "127.0.0.1"
        .parse()
        .expect("Hardcoded IP address should be valid");
}

我们通过解析一个硬编码的字符串来创建一个 IpAddr 实例。我们能看出 127.0.0.1 是一个有效的 IP 地址，所以在这里使用 expect 是可以接受的。然而，使用一个硬编码的有效字符串并不会改变 parse 方法的返回类型：我们得到的仍然是一个 Result 值，而编译器仍然会要求我们把 Result 当作可能出现 Err 变体那样来处理，因为编译器还没有聪明到能看出这个字符串总是一个有效的 IP 地址。如果这个 IP 地址字符串来自用户而不是硬编码在程序中，因而确实存在失败的可能，那么我们肯定会希望以更健壮的方式来处理 Result。在参数中提及“这个 IP 地址是硬编码的”这一假设，可以提醒我们：如果将来需要从其他来源获取 IP 地址，就应该把 expect 换成更好的错误处理代码。

错误处理指导原则

当代码有可能最终陷入坏状态时，建议让代码 panic。在这里，坏状态（bad state）是指某些假设、保证、契约或不变量被打破，比如有无效的值、相互矛盾的值或缺失的值被传入你的代码，并且还满足以下一条或多条：

  • 这种坏状态是意料之外的，而不是像用户输入了格式错误的数据那样偶尔可能发生的情况。
  • 在此之后的代码需要依赖于不处于这种坏状态，而不是在每一步都检查这个问题。
  • 没有好的办法把这一信息编码进你所使用的类型中。我们将在第 18 章“将状态和行为编码为类型”部分通过一个例子来说明这是什么意思。

如果有人调用你的代码并传入了没有意义的值，最好的做法是尽可能返回一个错误，以便库的使用者决定在这种情况下要做什么。然而，在继续执行可能不安全或有害的情况下，最好的选择可能是调用 panic!，提醒使用你的库的人他们的代码中有 bug，以便他们在开发过程中修复它。同样，如果你调用了不受你控制的外部代码，而它返回了一个你无法修复的无效状态，那么 panic! 往往也是合适的。

不过，当失败是可以预料的时候，返回 Result 比调用 panic! 更合适。例如，解析器接收到格式错误的数据，或者 HTTP 请求返回了一个表明你已触及速率限制的状态码。在这些情况下，返回 Result 表明失败是一种预料之中的可能性，调用代码必须决定如何处理它。

当你的代码执行的某个操作在使用无效值调用时可能会让用户面临风险，那么你的代码应该先验证这些值是否有效，并在值无效时 panic。这主要是出于安全方面的考虑：试图对无效数据进行操作可能会让你的代码暴露在漏洞之下。这也是标准库在你尝试越界访问内存时会调用 panic! 的主要原因：试图访问不属于当前数据结构的内存是一个常见的安全问题。函数通常都有契约（contract）：只有当输入满足特定要求时，函数的行为才能得到保证。在契约被违反时 panic 是合理的，因为违反契约总是意味着调用方存在 bug，而且这不是一种你希望调用代码必须显式处理的错误。事实上，调用代码没有任何合理的方式可以恢复；需要由调用方的程序员来修复代码。函数的契约，尤其是违反后会导致 panic 的契约，应当在该函数的 API 文档中加以说明。

然而，在所有函数中都进行大量的错误检查会显得冗长又烦人。幸运的是，你可以利用 Rust 的类型系统（也就是编译器所做的类型检查）替你完成许多检查。如果你的函数以某个特定类型作为参数，你就可以放心地继续编写代码逻辑，因为编译器已经确保了你拿到的是一个有效的值。例如，如果你使用的是某个类型而不是 Option，那么你的程序期望的是有值而不是无值。这样你的代码就不必处理 Some 和 None 两个变体对应的两种情况：它只需要处理一种肯定有值的情况。试图向你的函数传入空值的代码根本无法通过编译，所以你的函数不必在运行时检查这种情况。另一个例子是使用 u32 这样的无符号整数类型，它能确保参数永远不会是负数。

接下来，我们实现了一个名为 value 的方法，它借用 self，没有其他参数，并返回一个 i32。这类方法有时被称为 getter，因为它的作用是从字段中获取数据并将其返回。这个公有方法是必要的，因为 Guess 结构体的 value 字段是私有的。value 字段必须是私有的，这一点很重要，这样使用 Guess 结构体的代码就不能直接设置 value：guessing_game 模块之外的代码必须使用 Guess::new 函数来创建 Guess 的实例，从而确保 Guess 不可能拥有一个未经 Guess::new 函数中的条件检查过的 value。

这样一来，一个参数或返回值只能是 1 到 100 之间数字的函数，就可以在其签名中声明它接收或返回的是 Guess 而不是 i32，并且无需在函数体中做任何额外的检查。

总结

Rust 的错误处理特性旨在帮助你编写更加健壮的代码。panic! 宏表明程序处于一种它无法处理的状态，让你可以通知进程停止运行，而不是带着无效或错误的值继续执行。Result 枚举利用 Rust 的类型系统来表明操作可能会失败，而且你的代码可以从这种失败中恢复。你可以使用 Result 告诉调用你代码的代码：它也需要处理可能的成功或失败。在合适的场景中使用 panic! 和 Result，会让你的代码在面对不可避免的问题时更加可靠。
