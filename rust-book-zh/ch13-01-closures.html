Rust 程序设计语言

闭包

Rust 的闭包是一种匿名函数，你可以把它保存在变量中，或者作为参数传给其他函数。你可以在一个地方创建闭包，然后在别处调用它，在不同的上下文中对它求值。与函数不同，闭包可以捕获其定义所在作用域中的值。我们将演示闭包的这些特性如何实现代码复用和行为定制。

捕获环境

我们首先来看看如何使用闭包捕获其定义所在环境中的值，以便稍后使用。场景是这样的：我们的 T 恤公司时不时会向邮件列表中的某个人赠送一件独家的限量版 T 恤作为促销活动。邮件列表中的人可以选择在个人资料中添加自己最喜欢的颜色。如果被选中获得免费 T 恤的人设置了最喜欢的颜色，他们就会得到那个颜色的 T 恤；如果这个人没有指定最喜欢的颜色，他们就会得到公司当前库存最多的那种颜色。

实现这个功能的方式有很多。在这个例子中，我们将使用一个名为 ShirtColor 的枚举，它有 Red 和 Blue 两个变体（为简单起见，限制了可选颜色的数量）。我们用一个 Inventory 结构体来表示公司的库存，它有一个名为 shirts 的字段，其中包含一个 Vec<ShirtColor>，表示当前库存中 T 恤的颜色。定义在 Inventory 上的 giveaway 方法获取免费 T 恤获得者可选的 T 恤颜色偏好，并返回这个人将得到的 T 恤颜色。这一设置如示例 13-1 所示。

main 中定义的 store 还剩下两件蓝色 T 恤和一件红色 T 恤可用于这次限量版促销活动的分发。我们分别为一位偏好红色 T 恤的用户和一位没有任何偏好的用户调用了 giveaway 方法。

同样，这段代码有很多种实现方式。为了把重点放在闭包上，除了使用闭包的 giveaway 方法体之外，我们只使用了你已经学过的概念。在 giveaway 方法中，我们以 Option<ShirtColor> 类型的参数获取用户偏好，并在 user_preference 上调用 unwrap_or_else 方法。Option<T> 上的 unwrap_or_else 方法是由标准库定义的。它接受一个参数：一个不带任何参数并返回 T 类型值的闭包（T 与 Option<T> 的 Some 变体中存储的类型相同，在本例中就是 ShirtColor）。如果 Option<T> 是 Some 变体，unwrap_or_else 就返回 Some 中的值；如果 Option<T> 是 None 变体，unwrap_or_else 就调用闭包，并返回闭包所返回的值。

我们将闭包表达式 || self.most_stocked() 指定为 unwrap_or_else 的参数。这个闭包本身不接受任何参数（如果闭包有参数，它们会出现在两条竖线之间）。闭包体调用了 self.most_stocked()。我们在这里定义闭包，而 unwrap_or_else 的实现会在需要结果时再对闭包求值。

运行这段代码会打印出：

    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.27s
     Running `target/debug/shirt-company`
The user with preference Some(Red) gets Red
The user with preference None gets Blue

这里有一个有趣之处：我们传入了一个在当前 Inventory 实例上调用 self.most_stocked() 的闭包。标准库并不需要知道我们定义的 Inventory 或 ShirtColor 类型，也不需要知道我们在这个场景中想要使用的逻辑。闭包捕获了 self 这个 Inventory 实例的不可变引用，并将它与我们指定的代码一起传给 unwrap_or_else 方法。而函数则无法以这种方式捕获其环境。

推断和注解闭包类型

函数和闭包之间还有更多区别。闭包通常不要求你像 fn 函数那样注解参数或返回值的类型。函数之所以需要类型注解，是因为类型是暴露给用户的显式接口的一部分。严格地定义这个接口，对于确保所有人都对函数使用和返回的值的类型达成一致非常重要。而闭包并不用于这样的公开接口：它们存储在变量中，在使用时既不需要命名，也不会暴露给我们库的用户。

闭包通常很短，并且只与一个狭小的上下文相关，而不是适用于任意场景。在这些有限的上下文中，编译器能够推断出参数和返回值的类型，就像它能够推断出大多数变量的类型一样（在极少数情况下，编译器也需要闭包的类型注解）。

和变量一样，如果我们想提高明确性和清晰度，也可以添加类型注解，代价是代码会比严格必要的更冗长一些。为闭包注解类型的写法如示例 13-2 中的定义所示。在这个例子中，我们定义了一个闭包并将其存储在变量中，而不是像示例 13-1 那样在作为参数传递的位置上定义闭包。

添加类型注解后，闭包的语法看起来就与函数的语法更相似了。为了便于比较，这里我们定义了一个将其参数加 1 的函数，以及一个具有相同行为的闭包。我们添加了一些空格来对齐相关的部分。这说明了闭包语法与函数语法是多么相似，区别只在于闭包使用了竖线，并且有很多语法是可选的：

fn  add_one_v1   (x: u32) -> u32 { x + 1 }
let add_one_v2 = |x: u32| -> u32 { x + 1 };
let add_one_v3 = |x|             { x + 1 };
let add_one_v4 = |x|               x + 1  ;

第一行展示的是一个函数定义，第二行展示的是一个带有完整注解的闭包定义。在第三行中，我们去掉了闭包定义中的类型注解。在第四行中，我们去掉了大括号，因为闭包体只有一个表达式，所以大括号是可选的。这些都是有效的定义，被调用时会产生相同的行为。add_one_v3 和 add_one_v4 这两行要求闭包必须被求值才能通过编译，因为它们的类型需要从使用方式中推断出来。这类似于 let v = Vec::new();：要么需要类型注解，要么需要向 Vec 中插入某种类型的值，Rust 才能推断出它的类型。

对于闭包定义，编译器会为其每个参数和返回值推断出一个具体的类型。例如，示例 13-3 展示了一个简短闭包的定义，它只是返回作为参数接收到的值。这个闭包除了用于本例之外没什么用处。注意，我们没有在定义中添加任何类型注解。由于没有类型注解，我们可以用任意类型来调用这个闭包，这里我们第一次用的是 String。如果接着尝试用一个整数来调用 example_closure，就会得到一个错误。

捕获引用或移动所有权

闭包可以通过三种方式从其环境中捕获值，这直接对应于函数获取参数的三种方式：不可变借用、可变借用和获取所有权。闭包会根据函数体如何处理所捕获的值来决定使用哪种方式。

如果你想强制闭包获取它在环境中所用值的所有权，即使闭包体并不严格需要所有权，也可以在参数列表前使用 move 关键字。

这种技巧主要在把闭包传给新线程时有用，它可以移动数据，使数据归新线程所有。我们会在第 16 章讨论并发时详细介绍线程以及为什么要使用线程，不过现在，我们先简单了解一下如何使用一个需要 move 关键字的闭包来创建新线程。示例 13-6 展示了修改后的示例 13-4，它在新线程而不是主线程中打印 vector。

我们创建了一个新线程，并将一个闭包作为参数交给该线程运行。闭包体会打印出这个列表。在示例 13-4 中，闭包只通过不可变引用捕获了 list，因为这是打印 list 所需的最少访问权限。在这个例子中，尽管闭包体仍然只需要一个不可变引用，我们还是需要在闭包定义的开头加上 move 关键字，来指定应当把 list 移动到闭包中。如果主线程在对新线程调用 join 之前执行了更多操作，那么新线程可能会在主线程的其余部分结束之前完成，也可能是主线程先结束。如果主线程保持着 list 的所有权，却在新线程之前结束并丢弃了 list，那么线程中的不可变引用就会失效。因此，编译器要求把 list 移动到交给新线程的闭包中，这样引用才会有效。试着去掉 move 关键字，或者在定义闭包之后在主线程中使用 list，看看会得到什么编译器错误！

将捕获的值移出闭包

一旦闭包从其定义所在的环境中捕获了某个值的引用或所有权（这影响的是有什么会被移进闭包，如果有的话），闭包体中的代码就决定了稍后对闭包求值时这些引用或值会发生什么（这影响的是有什么会被移出闭包，如果有的话）。

闭包体可以执行以下任意一种操作：将捕获的值移出闭包、修改捕获的值、既不移动也不修改值，或者一开始就不从环境中捕获任何东西。

闭包捕获和处理环境中值的方式，会影响闭包实现哪些 trait，而 trait 正是函数和结构体用来指定它们可以使用哪种闭包的方式。根据闭包体处理值的方式，闭包会以叠加的方式自动实现这三个 Fn trait 中的一个、两个或全部三个：

  • FnOnce 适用于可以被调用一次的闭包。所有闭包都至少实现了这个 trait，因为所有闭包都可以被调用。一个将捕获的值从闭包体中移出的闭包只会实现 FnOnce，而不会实现其他任何 Fn trait，因为它只能被调用一次。
  • FnMut 适用于不会将捕获的值移出闭包体、但可能会修改捕获的值的闭包。这类闭包可以被调用多次。
  • Fn 适用于既不将捕获的值移出闭包体、也不修改捕获的值的闭包，以及不从环境中捕获任何东西的闭包。这类闭包可以被调用多次而不会修改其环境，这在诸如并发地多次调用同一个闭包等场景中非常重要。

让我们来看看示例 13-1 中用到的 Option<T> 上 unwrap_or_else 方法的定义：

impl<T> Option<T> {
    pub fn unwrap_or_else<F>(self, f: F) -> T
    where
        F: FnOnce() -> T
    {
        match self {
            Some(x) => x,
            None => f(),
        }
    }
}

回想一下，T 是一个泛型类型，表示 Option 的 Some 变体中值的类型。这个类型 T 也是 unwrap_or_else 函数的返回类型：例如，在 Option<String> 上调用 unwrap_or_else 的代码会得到一个 String。

接下来，注意 unwrap_or_else 函数还有一个额外的泛型类型参数 F。F 类型是名为 f 的参数的类型，也就是我们调用 unwrap_or_else 时提供的闭包。

泛型类型 F 上指定的 trait bound 是 FnOnce() -> T，这意味着 F 必须能够被调用一次、不接受任何参数，并返回一个 T。在 trait bound 中使用 FnOnce 表达了这样一个约束：unwrap_or_else 调用 f 的次数不会超过一次。在 unwrap_or_else 的函数体中可以看到，如果 Option 是 Some，f 就不会被调用；如果 Option 是 None，f 会被调用一次。由于所有闭包都实现了 FnOnce，unwrap_or_else 可以接受这三种闭包中的任何一种，做到了尽可能地灵活。

注意：如果我们想做的事情不需要从环境中捕获值，那么在需要实现某个 Fn trait 的东西的地方，可以使用函数名而不是闭包。例如，对于一个 Option<Vec<T>> 值，我们可以调用 unwrap_or_else(Vec::new)，在值为 None 时得到一个新的空 vector。编译器会自动为函数定义实现适用的那些 Fn trait。

现在我们来看看定义在切片上的标准库方法 sort_by_key，看看它与 unwrap_or_else 有何不同，以及为什么 sort_by_key 在 trait bound 中使用的是 FnMut 而不是 FnOnce。这个闭包接受一个参数，即当前正在处理的切片元素的引用，并返回一个可以排序的 K 类型的值。当你想按每个元素的某个特定属性对切片进行排序时，这个函数就很有用。在示例 13-7 中，我们有一个 Rectangle 实例的列表，并使用 sort_by_key 按它们的 width 属性从小到大排序。

sort_by_key 之所以被定义为接受一个 FnMut 闭包，是因为它会多次调用该闭包：对切片中的每个元素各调用一次。闭包 |r| r.width 不会从其环境中捕获、修改或移出任何东西，所以它满足 trait bound 的要求。

与之相对，示例 13-8 展示了一个只实现了 FnOnce trait 的闭包，因为它将一个值移出了环境。编译器不允许我们将这个闭包用于 sort_by_key。

这是一种刻意设计的、绕弯子的（而且行不通的）方式，试图统计 sort_by_key 在对 list 排序时调用闭包的次数。这段代码试图通过把 value（一个来自闭包环境的 String）推入 sort_operations vector 来进行计数。闭包捕获了 value，然后通过将 value 的所有权转移给 sort_operations vector，把 value 移出了闭包。这个闭包只能被调用一次；尝试第二次调用它是行不通的，因为那时 value 已经不在环境中，无法再次被推入 sort_operations！因此，这个闭包只实现了 FnOnce。当我们尝试编译这段代码时，会得到如下错误，指出 value 不能被移出闭包，因为闭包必须实现 FnMut：
