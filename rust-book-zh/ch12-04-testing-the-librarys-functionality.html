Rust 程序设计语言

采用测试驱动开发完善功能

既然我们已经把搜索逻辑放在 src/lib.rs 中，与 main 函数分离开来，那么为代码的核心功能编写测试就容易多了。我们可以直接用各种参数调用函数并检查返回值，而不必从命令行调用我们的二进制程序。

在本节中，我们将按照测试驱动开发（test-driven development，TDD）的流程为 minigrep 程序添加搜索逻辑，步骤如下：

  1. 编写一个会失败的测试并运行它，确保它失败的原因符合你的预期。
  2. 编写或修改刚好足够的代码，让新测试通过。
  3. 重构刚刚添加或修改的代码，并确保测试仍然通过。
  4. 从第 1 步开始重复！

TDD 虽然只是众多编写软件的方法之一，但它有助于驱动代码设计。在编写让测试通过的代码之前先编写测试，有助于在整个开发过程中保持较高的测试覆盖率。

我们将以测试驱动的方式实现真正执行搜索的功能：在文件内容中搜索查询字符串，并生成一个与查询匹配的行的列表。我们会把这个功能放在一个名为 search 的函数中。

编写一个失败的测试

在 src/lib.rs 中，我们将像第 11 章中那样添加一个包含测试函数的 tests 模块。这个测试函数指定了我们希望 search 函数具有的行为：它接受一个查询和要搜索的文本，并只返回文本中包含该查询的那些行。示例 12-15 展示了这个测试。

这个测试搜索字符串 "duct"。我们要搜索的文本有三行，其中只有一行包含 "duct"（注意，开头双引号后面的反斜杠告诉 Rust 不要在这个字符串字面量内容的开头放置换行符）。我们断言 search 函数返回的值中只包含我们预期的那一行。

如果现在运行这个测试，它会失败，因为 unimplemented! 宏会以 “not implemented” 信息 panic。按照 TDD 的原则，我们将迈出一小步，只添加刚好足够的代码，使调用函数时测试不会 panic：把 search 函数定义为总是返回一个空 vector，如示例 12-16 所示。这样测试应该就能编译，并且会失败，因为空 vector 与包含 "safe, fast, productive." 这一行的 vector 不匹配。

现在我们来讨论一下，为什么需要在 search 的签名中定义一个显式的生命周期 'a，并将这个生命周期用于 contents 参数和返回值。回想一下第 10 章中的内容：生命周期参数指定了哪个参数的生命周期与返回值的生命周期相关联。在本例中，我们表明返回的 vector 应当包含引用参数 contents（而不是参数 query）切片的字符串切片。

换句话说，我们告诉 Rust，search 函数返回的数据与通过 contents 参数传入 search 函数的数据存活得一样久。这一点很重要！切片所引用的数据必须有效，引用才能有效；如果编译器以为我们是在创建 query 而不是 contents 的字符串切片，它的安全检查就会出错。

如果我们忘记了生命周期注解就尝试编译这个函数，会得到如下错误：

error: could not compile `minigrep` (lib) due to 1 previous error

Rust 无法知道输出需要的是这两个参数中的哪一个，所以我们需要明确地告诉它。注意，帮助信息建议为所有参数和输出类型指定相同的生命周期参数，这是不正确的！因为 contents 是包含我们所有文本的参数，而我们想要返回的是该文本中匹配的部分，所以我们知道 contents 是唯一应当通过生命周期语法与返回值相关联的参数。

其他编程语言并不要求你在签名中把参数与返回值关联起来，但随着时间的推移，这种做法会变得越来越容易。你也许可以将这个例子与第 10 章“用生命周期验证引用”部分中的例子做个比较。

编写让测试通过的代码

目前，我们的测试之所以失败，是因为我们总是返回一个空 vector。为了修复这个问题并实现 search，程序需要遵循以下步骤：

  1. 遍历内容中的每一行。
  2. 检查该行是否包含我们的查询字符串。
  3. 如果包含，就把它添加到要返回的值列表中。
  4. 如果不包含，什么也不做。
  5. 返回匹配结果的列表。

让我们逐步完成每一步，先从遍历每一行开始。
