Rust 程序设计语言

引用模块树中项的路径

为了告诉 Rust 在模块树中的哪里能找到某个项，我们使用路径，就像在文件系统中导航时使用路径一样。要调用一个函数，我们需要知道它的路径。

路径有两种形式：

  • 绝对路径（absolute path）是从 crate 根开始的完整路径；对于来自外部 crate 的代码，绝对路径以 crate 名开头，而对于当前 crate 中的代码，则以字面量 crate 开头。
  • 相对路径（relative path）从当前模块开始，使用 self、super 或当前模块中的某个标识符。

绝对路径和相对路径后面都跟着一个或多个由双冒号（::）分隔的标识符。

回到示例 7-1，假设我们想调用 add_to_waitlist 函数。这就相当于在问：add_to_waitlist 函数的路径是什么？示例 7-3 是去掉了部分模块和函数之后的示例 7-1。

我们将展示两种从 crate 根中定义的新函数 eat_at_restaurant 里调用 add_to_waitlist 函数的方法。这些路径都是正确的，但还存在另一个问题，导致这个示例无法直接编译。我们稍后会解释原因。

eat_at_restaurant 函数是我们库 crate 公有 API 的一部分，所以我们用 pub 关键字来标记它。在“使用 pub 关键字暴露路径”部分，我们会更详细地介绍 pub。

在 eat_at_restaurant 中第一次调用 add_to_waitlist 函数时，我们使用的是绝对路径。add_to_waitlist 函数与 eat_at_restaurant 定义在同一个 crate 中，这意味着我们可以用 crate 关键字作为绝对路径的开头。然后我们依次写出每一层模块，直到到达 add_to_waitlist。你可以设想一个具有相同结构的文件系统：我们会指定路径 /front_of_house/hosting/add_to_waitlist 来运行 add_to_waitlist 程序；用 crate 名从 crate 根开始，就像在 shell 中用 / 从文件系统根开始一样。

在 eat_at_restaurant 中第二次调用 add_to_waitlist 时，我们使用的是相对路径。这个路径以 front_of_house 开头，它是与 eat_at_restaurant 定义在模块树同一层级的模块的名字。这里对应到文件系统，相当于使用路径 front_of_house/hosting/add_to_waitlist。以模块名开头意味着这是一个相对路径。

选择使用相对路径还是绝对路径，要根据你的项目来决定，这取决于你更可能把项的定义代码与使用该项的代码分开移动，还是一起移动。例如，如果我们把 front_of_house 模块和 eat_at_restaurant 函数一起移动到一个名为 customer_experience 的模块中，就需要更新指向 add_to_waitlist 的绝对路径，但相对路径仍然有效。然而，如果我们把 eat_at_restaurant 函数单独移动到一个名为 dining 的模块中，调用 add_to_waitlist 的绝对路径保持不变，但相对路径就需要更新。总体而言，我们倾向于使用绝对路径，因为我们更有可能希望把代码定义和项的调用彼此独立地移动。

让我们试着编译示例 7-3，看看它为什么还不能编译！我们得到的错误如示例 7-4 所示。

错误信息说模块 hosting 是私有的。换句话说，我们为 hosting 模块和 add_to_waitlist 函数写出的路径是正确的，但 Rust 不允许我们使用它们，因为它无权访问私有部分。在 Rust 中，所有项（函数、方法、结构体、枚举、模块和常量）默认对父模块都是私有的。如果你想让一个函数或结构体这样的项成为私有的，就把它放到一个模块里。

父模块中的项不能使用子模块中的私有项，但子模块中的项可以使用其祖先模块中的项。这是因为子模块封装并隐藏了自己的实现细节，但子模块能够看到自己被定义时所处的上下文。继续用我们的餐厅来打比方：可以把私有性规则想象成餐厅的后勤办公室，里面发生的事情对餐厅顾客来说是不公开的，但办公室经理可以看到并处理他们所经营的餐厅里的一切事务。

Rust 之所以选择让模块系统这样运作，是为了让隐藏内部实现细节成为默认行为。这样一来，你就知道修改内部代码的哪些部分不会破坏外部代码。不过，Rust 也提供了选择：你可以使用 pub 关键字将某个项设为公有，从而把子模块代码的内部部分暴露给外层的祖先模块。

使用 pub 关键字暴露路径

让我们回到示例 7-4 中告诉我们 hosting 模块是私有的那个错误。我们希望父模块中的 eat_at_restaurant 函数能够访问子模块中的 add_to_waitlist 函数，因此我们用 pub 关键字标记 hosting 模块，如示例 7-5 所示。

遗憾的是，示例 7-5 中的代码仍然会导致编译器错误，如示例 7-6 所示。

这是怎么回事？在 mod hosting 前面加上 pub 关键字会让这个模块变成公有的。有了这个改动，如果我们能访问 front_of_house，就能访问 hosting。但 hosting 的内容仍然是私有的；把模块设为公有并不会使其内容也变为公有。模块上的 pub 关键字只允许其祖先模块中的代码引用它，而不允许访问它内部的代码。因为模块是一个容器，所以只把模块设为公有并不能做太多事情；我们还需要更进一步，选择将模块中的一个或多个项也设为公有。

示例 7-6 中的错误说 add_to_waitlist 函数是私有的。私有性规则不仅适用于模块，也同样适用于结构体、枚举、函数和方法。

让我们在 add_to_waitlist 函数的定义前加上 pub 关键字，把它也设为公有的，如示例 7-7 所示。

现在代码可以编译了！为了弄清楚为什么添加 pub 关键字之后，在私有性规则下我们就能在 eat_at_restaurant 中使用这些路径，我们来分别看一下绝对路径和相对路径。

在绝对路径中，我们从 crate 开始，也就是我们 crate 模块树的根。front_of_house 模块定义在 crate 根中。虽然 front_of_house 不是公有的，但由于 eat_at_restaurant 函数与 front_of_house 定义在同一个模块中（也就是说，eat_at_restaurant 和 front_of_house 是兄弟），我们可以在 eat_at_restaurant 中引用 front_of_house。接下来是用 pub 标记的 hosting 模块。我们可以访问 hosting 的父模块，因此可以访问 hosting。最后，add_to_waitlist 函数被标记为 pub，并且我们可以访问它的父模块，所以这个函数调用是可行的！

在相对路径中，除了第一步之外，逻辑与绝对路径相同：路径不是从 crate 根开始，而是从 front_of_house 开始。front_of_house 模块与 eat_at_restaurant 定义在同一个模块中，所以从定义 eat_at_restaurant 的模块开始的相对路径是可行的。然后，因为 hosting 和 add_to_waitlist 都被标记为 pub，路径的其余部分也是可行的，因此这个函数调用是有效的！

如果你打算分享你的库 crate，让其他项目可以使用你的代码，那么你的公有 API 就是你与 crate 用户之间的约定，它决定了用户如何与你的代码交互。在管理公有 API 的变更、让人们更容易依赖你的 crate 这方面，有许多需要考虑的问题。这些问题超出了本书的讨论范围；如果你对这个话题感兴趣，请参阅 Rust API 指南。

同时包含二进制 crate 和库 crate 的包的最佳实践

我们提到过，一个包可以同时包含 src/main.rs 二进制 crate 根和 src/lib.rs 库 crate 根，并且这两个 crate 默认都以包名命名。通常，这种同时包含库 crate 和二进制 crate 的包，在二进制 crate 中只会放置刚好足以启动可执行文件的代码，由它去调用库 crate 中定义的代码。这样，其他项目就能最大程度地利用这个包所提供的功能，因为库 crate 的代码是可以共享的。

模块树应该定义在 src/lib.rs 中。这样，在二进制 crate 中就可以通过以包名开头的路径来使用任何公有项。二进制 crate 就像一个完全外部的 crate 使用库 crate 那样，成为库 crate 的用户：它只能使用公有 API。这有助于你设计出良好的 API；因为你不仅是作者，同时也是用户！

在第 12 章中，我们会通过一个同时包含二进制 crate 和库 crate 的命令行程序来演示这种组织方式。

以 super 开头的相对路径

我们可以在路径开头使用 super，来构造从父模块（而不是当前模块或 crate 根）开始的相对路径。这就像在文件系统路径中以 .. 语法开头，表示进入父目录。使用 super 让我们可以引用一个我们已知位于父模块中的项。当某个模块与其父模块关系密切，而父模块将来某一天可能会被移动到模块树中的其他位置时，这能让重新组织模块树变得更容易。

来看示例 7-8 中的代码，它模拟了这样一种场景：厨师修正了一份错误的订单，并亲自把它端给顾客。定义在 back_of_house 模块中的函数 fix_incorrect_order 通过指定以 super 开头的 deliver_order 路径，调用了定义在父模块中的 deliver_order 函数。

fix_incorrect_order 函数位于 back_of_house 模块中，所以我们可以使用 super 进入 back_of_house 的父模块，在这个例子中也就是根模块 crate。我们从那里查找 deliver_order，并且找到了它。成功！我们认为，back_of_house 模块和 deliver_order 函数之间很可能会保持这种关系，如果我们决定重新组织 crate 的模块树，它们也会被一起移动。因此，我们使用了 super，这样将来如果这段代码被移动到别的模块中，需要更新代码的地方就会更少。

将结构体和枚举设为公有

我们还可以使用 pub 将结构体和枚举指定为公有的，但在结构体和枚举上使用 pub 时还有一些额外的细节需要注意。如果我们在结构体定义前使用 pub，结构体本身会变成公有的，但结构体的字段仍然是私有的。我们可以根据具体情况，决定每个字段是否公有。在示例 7-9 中，我们定义了一个公有的 back_of_house::Breakfast 结构体，它有一个公有的 toast 字段，但 seasonal_fruit 字段是私有的。这模拟了餐厅中的一种情况：顾客可以挑选随餐提供的面包种类，但随餐搭配哪种水果则由厨师根据当季的水果和库存情况来决定。可供应的水果变化很快，所以顾客既不能选择水果，甚至也看不到自己会拿到哪种水果。

因为 back_of_house::Breakfast 结构体中的 toast 字段是公有的，所以我们可以在 eat_at_restaurant 中使用点号读写 toast 字段。注意，我们不能在 eat_at_restaurant 中使用 seasonal_fruit 字段，因为 seasonal_fruit 是私有的。试着取消注释修改 seasonal_fruit 字段值的那一行，看看你会得到什么错误！

另外还要注意，因为 back_of_house::Breakfast 有一个私有字段，所以这个结构体需要提供一个公有的关联函数来构造 Breakfast 的实例（这里我们把它命名为 summer）。如果 Breakfast 没有这样的函数，我们就无法在 eat_at_restaurant 中创建 Breakfast 的实例，因为我们无法在 eat_at_restaurant 中设置私有字段 seasonal_fruit 的值。

与此相反，如果我们把一个枚举设为公有，那么它的所有变体也都会变成公有的。我们只需要在 enum 关键字前面加上 pub，如示例 7-10 所示。

因为我们把 Appetizer 枚举设为了公有，所以可以在 eat_at_restaurant 中使用 Soup 和 Salad 变体。

如果枚举的变体不是公有的，枚举就没什么用处了；在每种情况下都要给所有枚举变体标注 pub 会很烦人，所以枚举变体默认就是公有的。结构体的字段即使不公有，结构体通常也很有用，所以结构体字段遵循一般规则：除非用 pub 标注，否则所有内容默认都是私有的。
