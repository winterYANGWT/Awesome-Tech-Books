Rust 程序设计语言

宏

我们在本书中一直在使用像 println! 这样的宏，但还没有完整地探讨过宏是什么以及它是如何工作的。宏（macro）这个术语指的是 Rust 中的一系列特性：使用 macro_rules! 的声明宏，以及三种过程宏：

  • 自定义 #[derive] 宏，用于指定在结构体和枚举上使用 derive 属性时所添加的代码
  • 类属性宏，用于定义可用于任意项的自定义属性
  • 类函数宏，看起来像函数调用，但操作的是作为其参数传入的标记（token）

我们会依次讨论每一种宏，但首先，我们来看看既然已经有了函数，为什么还需要宏。

宏与函数的区别

从根本上说，宏是一种编写“能编写其他代码的代码”的方式，这被称为元编程（metaprogramming）。在附录 C 中，我们讨论了 derive 属性，它会为你生成各种 trait 的实现。我们在整本书中也一直在使用 println! 和 vec! 宏。所有这些宏都会展开，生成比你手写的代码更多的代码。

元编程有助于减少你需要编写和维护的代码量，这也是函数的作用之一。不过，宏还拥有一些函数所不具备的额外能力。

函数签名必须声明函数参数的个数和类型。而宏则可以接受数量可变的参数：我们可以用一个参数调用 println!("hello")，也可以用两个参数调用 println!("hello {}", name)。此外，宏是在编译器解释代码的含义之前展开的，因此宏可以做到诸如在给定类型上实现 trait 这样的事情。函数就做不到这一点，因为函数是在运行时被调用的，而 trait 需要在编译时实现。

实现宏而不是函数的缺点在于，宏定义比函数定义更加复杂，因为你是在编写“能编写 Rust 代码的 Rust 代码”。由于这种间接性，宏定义通常比函数定义更难阅读、理解和维护。

宏与函数之间的另一个重要区别是：在文件中调用宏之前，你必须先定义宏或将其引入作用域；而函数则可以在任何地方定义、在任何地方调用。

用于通用元编程的声明宏

Rust 中使用最广泛的宏形式是声明宏（declarative macro）。它们有时也被称为“示例宏”（macros by example）、“macro_rules! 宏”，或者干脆就叫“宏”。从核心上说，声明宏允许你编写一些类似于 Rust match 表达式的东西。正如第 6 章所讨论的，match 表达式是一种控制结构，它接受一个表达式，将该表达式的结果值与各个模式进行比较，然后运行与匹配的模式相关联的代码。宏也会将一个值与关联着特定代码的模式进行比较：在这种情况下，值是传给宏的 Rust 源代码字面量；模式会与这段源代码的结构进行比较；而当某个模式匹配时，与该模式相关联的代码会替换传给宏的代码。这一切都发生在编译期间。

要定义宏，需要使用 macro_rules! 结构。我们通过观察 vec! 宏是如何定义的，来探索如何使用 macro_rules!。第 8 章介绍了如何使用 vec! 宏来创建一个包含特定值的新 vector。例如，下面的宏会创建一个包含三个整数的新 vector：

#![allow(unused)]
fn main() {
let v: Vec<u32> = vec![1, 2, 3];
}

我们也可以使用 vec! 宏来创建一个包含两个整数的 vector，或者一个包含五个字符串切片的 vector。用函数是无法做到同样的事情的，因为我们无法预先知道值的个数和类型。

接着，我们以 macro_rules! 和所定义的宏的名称（不带感叹号）开始宏定义。在本例中，名称 vec 后面跟着一对花括号，表示宏定义的主体。

vec! 主体中的结构与 match 表达式的结构类似。这里有一个分支，其模式为 ( $( $x:expr ),* )，后面跟着 => 以及与该模式相关联的代码块。如果模式匹配，就会生成相关联的代码块。鉴于这是该宏中唯一的模式，只有一种有效的匹配方式；任何其他模式都会导致错误。更复杂的宏会有不止一个分支。

宏定义中有效的模式语法与第 19 章介绍的模式语法不同，因为宏模式匹配的是 Rust 代码的结构，而不是值。我们来逐一看看示例 20-35 中各个模式片段的含义；完整的宏模式语法请参阅 Rust 参考手册。

首先，我们使用一对圆括号把整个模式括起来。我们使用美元符号（$）在宏系统中声明一个变量，它将包含与模式相匹配的 Rust 代码。美元符号清楚地表明这是一个宏变量，而不是普通的 Rust 变量。接下来是一对圆括号，它会捕获与括号内模式相匹配的值，以便在替换代码中使用。$() 中是 $x:expr，它会匹配任意 Rust 表达式，并将该表达式命名为 $x。

$() 后面的逗号表示，在每个与 $() 中的代码相匹配的代码实例之间，必须出现一个字面的逗号分隔符。* 表示该模式会匹配零个或多个 * 之前的内容。

当我们以 vec![1, 2, 3]; 调用这个宏时，$x 模式会匹配三次，分别匹配三个表达式 1、2 和 3。

现在我们来看看与这个分支相关联的代码主体中的模式：对于模式中与 $() 匹配的每个部分，都会生成 $()* 中的 temp_vec.push()，根据模式匹配的次数生成零次或多次。$x 会被替换为每个匹配到的表达式。当我们以 vec![1, 2, 3]; 调用这个宏时，生成的用来替换该宏调用的代码如下：

{
    let mut temp_vec = Vec::new();
    temp_vec.push(1);
    temp_vec.push(2);
    temp_vec.push(3);
    temp_vec
}

我们定义了一个宏，它可以接受任意数量、任意类型的参数，并能生成创建一个包含指定元素的 vector 的代码。

要进一步了解如何编写宏，请查阅在线文档或其他资源，比如由 Daniel Keep 发起、Lukas Wirth 接续编写的 “The Little Book of Rust Macros”。

用于从属性生成代码的过程宏

宏的第二种形式是过程宏，它的行为更像函数（并且也是一种过程）。过程宏（procedural macro）接受一些代码作为输入，对这些代码进行操作，然后产生一些代码作为输出，而不是像声明宏那样匹配模式并用其他代码替换原有代码。三种过程宏分别是自定义 derive 宏、类属性宏和类函数宏，它们的工作方式都很相似。

在创建过程宏时，其定义必须位于一个具有特殊 crate 类型的独立 crate 中。这是出于一些复杂的技术原因，我们希望将来能消除这一限制。在示例 20-36 中，我们展示了如何定义一个过程宏，其中 some_attribute 是一个占位符，代表使用某种特定类型的宏。

定义过程宏的函数接受一个 TokenStream 作为输入，并产生一个 TokenStream 作为输出。TokenStream 类型由 Rust 自带的 proc_macro crate 定义，它表示一个标记序列。这就是宏的核心：宏所操作的源代码构成了输入的 TokenStream，而宏产生的代码就是输出的 TokenStream。这个函数上还附加了一个属性，用来指定我们正在创建的是哪种过程宏。同一个 crate 中可以包含多种过程宏。

我们来看看不同种类的过程宏。我们先从自定义 derive 宏开始，然后再解释其他几种形式与它之间的细微差别。

注意，我们把代码拆分成了两个函数：负责解析 TokenStream 的 hello_macro_derive 函数，以及负责转换语法树的 impl_hello_macro 函数：这让编写过程宏更加方便。对于你所见到或创建的几乎每一个过程宏 crate，外层函数（在本例中是 hello_macro_derive）中的代码都是一样的。而你在内层函数（在本例中是 impl_hello_macro）的函数体中编写的代码，则会根据过程宏的用途而有所不同。

我们引入了三个新的 crate：proc_macro、syn 和 quote。proc_macro crate 是 Rust 自带的，所以我们不需要把它添加到 Cargo.toml 的依赖中。proc_macro crate 是编译器的 API，它允许我们在自己的代码中读取和操作 Rust 代码。

syn crate 会把 Rust 代码从字符串解析为我们可以对其进行操作的数据结构。quote crate 则会把 syn 的数据结构转换回 Rust 代码。这些 crate 让解析我们可能想要处理的任何 Rust 代码都变得简单多了：为 Rust 代码编写一个完整的解析器可不是件简单的事。

当我们库的用户在某个类型上指定 #[derive(HelloMacro)] 时，hello_macro_derive 函数就会被调用。之所以能这样，是因为我们在这里用 proc_macro_derive 标注了 hello_macro_derive 函数，并指定了名称 HelloMacro，它与我们的 trait 名称相匹配；这是大多数过程宏都遵循的惯例。

很快我们就会定义 impl_hello_macro 函数，我们将在其中构建想要包含进来的新 Rust 代码。但在此之前，请注意我们的 derive 宏的输出同样是一个 TokenStream。返回的 TokenStream 会被添加到我们 crate 的用户所编写的代码中，因此当他们编译自己的 crate 时，就会获得我们在修改后的 TokenStream 中提供的额外功能。

你可能已经注意到，我们在这里调用了 unwrap，这样当对 syn::parse 函数的调用失败时，hello_macro_derive 函数就会 panic。我们的过程宏有必要在出错时 panic，因为为了符合过程宏 API，proc_macro_derive 函数必须返回 TokenStream 而不是 Result。我们通过使用 unwrap 简化了这个例子；在生产代码中，你应该使用 panic! 或 expect 来提供更具体的错误信息，说明哪里出了问题。

这里使用的 stringify! 宏是 Rust 内置的。它接受一个 Rust 表达式，比如 1 + 2，并在编译时将该表达式转换为一个字符串字面量，比如 "1 + 2"。这与 format! 或 println! 不同，后两者是会对表达式求值、然后将结果转换为 String 的宏。#name 输入有可能是一个需要按字面打印的表达式，所以我们使用 stringify!。使用 stringify! 还能在编译时将 #name 转换为字符串字面量，从而省去一次内存分配。

接下来，我们来探讨其他几种过程宏与自定义 derive 宏有何不同。

类属性宏

类属性宏与自定义 derive 宏类似，但它们不是为 derive 属性生成代码，而是允许你创建新的属性。它们也更加灵活：derive 只适用于结构体和枚举；而属性还可以应用于其他项，比如函数。下面是一个使用类属性宏的例子。假设你在使用某个 Web 应用框架时，有一个名为 route 的属性用于标注函数：

#[route(GET, "/")]
fn index() {

这个 #[route] 属性将由该框架定义为一个过程宏。宏定义函数的签名看起来像这样：

#[proc_macro_attribute]
pub fn route(attr: TokenStream, item: TokenStream) -> TokenStream {

这里有两个 TokenStream 类型的参数。第一个用于属性的内容：即 GET, "/" 部分。第二个是该属性所附加到的项的主体：在本例中，就是 fn index() {} 以及函数体的其余部分。

除此之外，类属性宏的工作方式与自定义 derive 宏相同：你创建一个 crate 类型为 proc-macro 的 crate，并实现一个生成你想要的代码的函数！

类函数宏

类函数宏定义的是看起来像函数调用的宏。与 macro_rules! 宏类似，它们比函数更灵活；例如，它们可以接受数量未知的参数。然而，macro_rules! 宏只能使用我们在前面“用于通用元编程的声明宏”部分讨论过的类似 match 的语法来定义。类函数宏接受一个 TokenStream 参数，并且与另外两种过程宏一样，其定义会使用 Rust 代码来操作这个 TokenStream。类函数宏的一个例子是 sql! 宏，它的调用方式可能像这样：

let sql = sql!(SELECT * FROM posts WHERE id=1);

这个宏会解析其中的 SQL 语句，并检查其语法是否正确，这比 macro_rules! 宏所能完成的处理要复杂得多。sql! 宏的定义会是这样的：

#[proc_macro]
pub fn sql(input: TokenStream) -> TokenStream {

这个定义与自定义 derive 宏的签名类似：我们接收圆括号内的标记，并返回我们想要生成的代码。
