Rust 程序设计语言

将 crate 发布到 Crates.io

我们已经把 crates.io 上的包用作项目的依赖，不过你也可以发布自己的包，把代码分享给其他人。crates.io 上的 crate 注册表会分发你的包的源代码，所以它托管的主要是开源代码。

Rust 和 Cargo 有一些功能可以让你发布的包更容易被人们找到和使用。接下来我们会讨论其中一些功能，然后讲解如何发布一个包。

编写有用的文档注释

准确地为包编写文档能帮助其他用户了解如何以及何时使用它们，因此值得花时间编写文档。在第 3 章中，我们讨论了如何使用两个斜杠 // 来注释 Rust 代码。Rust 还有一种专门用于文档的注释，被很直白地称为文档注释（documentation comment），它会生成 HTML 文档。这些 HTML 会展示公有 API 项的文档注释内容，面向的是那些想知道如何使用你的 crate、而不是你的 crate 是如何实现的程序员。

文档注释使用三个斜杠 /// 而不是两个，并且支持使用 Markdown 标记来格式化文本。文档注释要放在被注释项的正前方。示例 14-1 展示了一个名为 my_crate 的 crate 中 add_one 函数的文档注释。

这里我们描述了 add_one 函数的作用，接着以 Examples 为标题开始一个部分，然后提供演示如何使用 add_one 函数的代码。运行 cargo doc 就可以根据这些文档注释生成 HTML 文档。这个命令会运行随 Rust 一起分发的 rustdoc 工具，并把生成的 HTML 文档放到 target/doc 目录中。

为了方便起见，运行 cargo doc --open 会为当前 crate 构建 HTML 文档（同时也会构建该 crate 所有依赖的文档），并在网页浏览器中打开结果。导航到 add_one 函数，你就能看到文档注释中的文本是如何渲染的，如图 14-1 所示。

图 14-1：add_one 函数的 HTML 文档

常用的文档部分

我们在示例 14-1 中使用了 # Examples 这个 Markdown 标题，在 HTML 中创建了一个标题为“Examples”的部分。下面是 crate 作者在文档中常用的其他一些部分：

  • Panics：说明被注释的函数可能会 panic 的场景。不希望程序 panic 的调用者应当确保不在这些情况下调用该函数。
  • Errors：如果函数返回 Result，那么描述可能出现的错误种类，以及在什么条件下会返回这些错误，对调用者很有帮助，这样他们就能编写代码，以不同的方式处理不同种类的错误。
  • Safety：如果调用该函数是 unsafe 的（我们会在第 20 章讨论不安全性），就应该有一个部分来解释为什么这个函数是不安全的，并说明函数期望调用者维护哪些不变量。

大多数文档注释并不需要包含所有这些部分，但这是一份很好的清单，可以提醒你用户会关心代码的哪些方面。

文档注释作为测试

在文档注释中添加示例代码块，有助于演示如何使用你的库，而且还有一个额外的好处：运行 cargo test 时，文档中的代码示例会被当作测试运行！没有什么比带有示例的文档更好的了。但也没有什么比无法运行的示例更糟糕的了——因为在文档写好之后，代码已经发生了变化。如果我们对示例 14-1 中 add_one 函数的文档运行 cargo test，会在测试结果中看到像这样的一个部分：

   Doc-tests my_crate

running 1 test
test src/lib.rs - add_one (line 5) ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.27s

现在，如果我们修改函数或者示例，使示例中的 assert_eq! 发生 panic，然后再次运行 cargo test，就会看到文档测试发现了示例和代码彼此不同步的问题！

包含项注释

//! 这种风格的文档注释会为包含这些注释的项添加文档，而不是为跟在注释后面的项添加文档。我们通常在 crate 根文件（按照惯例是 src/lib.rs）或者模块内部使用这种文档注释，为整个 crate 或整个模块编写文档。

例如，要为包含 add_one 函数的 my_crate crate 添加描述其用途的文档，我们在 src/lib.rs 文件的开头添加以 //! 开头的文档注释，如示例 14-2 所示。

注意，最后一行以 //! 开头的注释之后没有任何代码。因为我们用 //! 而不是 /// 开始这些注释，所以我们是在为包含这些注释的项编写文档，而不是为跟在注释后面的项编写文档。在本例中，这个项就是 src/lib.rs 文件，也就是 crate 根。这些注释描述的是整个 crate。

运行 cargo doc --open 时，这些注释会显示在 my_crate 文档的首页上，位于 crate 公有项列表的上方，如图 14-2 所示。

项内部的文档注释特别适合用来描述 crate 和模块。用它们来解释这个容器的整体用途，帮助用户理解 crate 的组织结构。

导出便于使用的公有 API

发布 crate 时，公有 API 的结构是一个需要重点考虑的问题。使用你的 crate 的人不像你那样熟悉它的结构，如果你的 crate 有一个很庞大的模块层级，他们可能很难找到自己想用的部分。

在第 7 章中，我们介绍了如何使用 pub 关键字将项设为公有，以及如何使用 use 关键字将项引入作用域。然而，在你开发 crate 时觉得合理的结构，对你的用户来说可能并不太方便。你可能想把结构体组织在一个包含多个层级的层次结构中，但这样一来，想要使用你定义在层级深处的某个类型的人，可能很难发现这个类型的存在。他们也可能会因为必须输入 use my_crate::some_module::another_module::UsefulType; 而不是 use my_crate::UsefulType; 而感到恼火。

好消息是，如果这个结构不便于其他人从另一个库中使用，你并不需要重新调整内部的组织方式：你可以使用 pub use 重导出项，构建一个与私有结构不同的公有结构。重导出（re-exporting）会把位于某处的公有项在另一处也设为公有，就好像它是在另一处定义的一样。

例如，假设我们创建了一个名为 art 的库，用来对艺术概念进行建模。这个库中有两个模块：kinds 模块包含两个名为 PrimaryColor 和 SecondaryColor 的枚举，utils 模块包含一个名为 mix 的函数，如示例 14-3 所示。

图 14-3 展示了 cargo doc 为这个 crate 生成的文档首页的样子。

依赖这个库的另一个 crate 需要使用 use 语句将 art 中的项引入作用域，并且要按照当前定义的模块结构来指定路径。示例 14-4 展示了一个使用 art crate 中 PrimaryColor 和 mix 项的 crate。

示例 14-4 中使用 art crate 的代码作者，必须弄清楚 PrimaryColor 位于 kinds 模块中，而 mix 位于 utils 模块中。art crate 的模块结构对于开发 art crate 的人来说更有意义，而对使用它的人来说则没那么重要。这种内部结构对于想要弄明白如何使用 art crate 的人来说并没有提供任何有用的信息，反而会造成困惑，因为使用它的开发者必须弄清楚去哪里找，还必须在 use 语句中写出模块名。

当存在大量嵌套模块时，使用 pub use 在顶层重导出类型，可以显著改善使用该 crate 的人的体验。pub use 的另一个常见用法是在当前 crate 中重导出某个依赖的定义，使那个 crate 的定义成为你的 crate 公有 API 的一部分。

设计一个有用的公有 API 结构与其说是一门科学，不如说是一门艺术，你可以反复迭代，找到最适合用户的 API。选择 pub use 让你可以灵活地安排 crate 的内部结构，并且把内部结构和你呈现给用户的内容解耦。看看你安装过的一些 crate 的代码，看看它们的内部结构是否与其公有 API 有所不同。

设置 Crates.io 账号

在发布任何 crate 之前，你需要在 crates.io 上创建一个账号并获取一个 API 令牌（token）。为此，请访问 crates.io 首页并通过 GitHub 账号登录。（目前必须使用 GitHub 账号，不过该网站将来可能会支持其他创建账号的方式。）登录之后，访问 https://crates.io/me/ 上的账号设置页面并获取你的 API 密钥。然后运行 cargo login 命令，并在提示时粘贴你的 API 密钥，就像这样：

$ cargo login
abcdefghijklmnopqrstuvwxyz012345

这个命令会把你的 API 令牌告诉 Cargo，并将其存储在本地的 ~/.cargo/credentials.toml 中。注意，这个令牌是一个秘密：不要与任何其他人分享。如果出于任何原因与他人分享了它，你应该撤销它，并在 crates.io 上生成一个新的令牌。

为新 crate 添加元数据

假设你有一个想要发布的 crate。在发布之前，你需要在 crate 的 Cargo.toml 文件的 [package] 部分中添加一些元数据。

你的 crate 需要一个独一无二的名字。在本地开发 crate 时，你可以随意给它起名。然而，crates.io 上的 crate 名称是按照先到先得的原则分配的。一旦某个 crate 名称被占用，其他人就不能再用这个名称发布 crate 了。在尝试发布 crate 之前，先搜索一下你想用的名字。如果这个名字已经被用过了，你就需要另找一个名字，并编辑 Cargo.toml 文件中 [package] 部分下的 name 字段，使用新名称进行发布，就像这样：

文件名：Cargo.toml

[package]
name = "guessing_game"

即使你已经选好了一个独一无二的名字，此时运行 cargo publish 来发布 crate，也会先得到一个警告，然后是一个错误：

$ cargo publish
    Updating crates.io index
warning: manifest has no description, license, license-file, documentation, homepage or repository.
See https://doc.rust-lang.org/cargo/reference/manifest.html#package-metadata for more info.
--snip--
error: failed to publish to registry at https://crates.io

Caused by:
  the remote server responded with an error (status 400 Bad Request): missing or empty metadata fields: description, license. Please see https://doc.rust-lang.org/cargo/reference/manifest.html for more information on configuring these fields

出现这个错误是因为你缺少了一些关键信息：描述和许可证是必需的，这样人们才能知道你的 crate 是做什么的，以及可以在什么条款下使用它。在 Cargo.toml 中添加一段只有一两句话的描述，因为它会和你的 crate 一起出现在搜索结果中。对于 license 字段，你需要提供一个许可证标识符值（license identifier value）。Linux 基金会的软件包数据交换（SPDX）列出了可以用作这个值的标识符。例如，要指定你的 crate 使用 MIT 许可证，就添加 MIT 标识符：

文件名：Cargo.toml

[package]
name = "guessing_game"
license = "MIT"

如果你想使用一个没有出现在 SPDX 中的许可证，就需要把该许可证的文本放到一个文件里，将这个文件包含在项目中，然后使用 license-file 来指定该文件的名称，而不是使用 license 键。

关于哪种许可证适合你的项目，这方面的指导超出了本书的范围。Rust 社区中的很多人会像 Rust 本身一样，为自己的项目采用 MIT OR Apache-2.0 双许可证。这种做法也说明，你可以用 OR 分隔多个许可证标识符，为项目指定多个许可证。

添加了唯一的名称、版本号、描述和许可证之后，一个准备发布的项目的 Cargo.toml 文件可能看起来像这样：

文件名：Cargo.toml

[package]
name = "guessing_game"
version = "0.1.0"
edition = "2024"
description = "A fun game where you guess what number the computer has chosen."
license = "MIT OR Apache-2.0"

[dependencies]

Cargo 的文档介绍了你还可以指定的其他元数据，它们能让其他人更容易地发现和使用你的 crate。

发布到 Crates.io

现在你已经创建了账号、保存了 API 令牌、为 crate 选好了名字，并指定了必需的元数据，可以发布了！发布 crate 会把一个特定的版本上传到 crates.io 供他人使用。

要小心，因为发布是永久性的。对应的版本永远无法被覆盖，除特定情况外，代码也无法被删除。Crates.io 的一个主要目标是充当代码的永久存档，这样所有依赖 crates.io 上 crate 的项目都能一直正常构建。如果允许删除版本，就不可能实现这个目标。不过，你能发布的 crate 版本数量是没有限制的。

再次运行 cargo publish 命令。这次应该会成功：

发布现有 crate 的新版本

当你修改了 crate 并准备发布新版本时，需要修改 Cargo.toml 文件中指定的 version 值并重新发布。请根据你所做修改的类型，使用语义化版本规则来决定合适的下一个版本号是什么。然后运行 cargo publish 上传新版本。

从 Crates.io 弃用版本

虽然你无法删除 crate 之前的版本，但可以阻止将来的任何项目把它们添加为新的依赖。当某个 crate 版本由于某种原因出现问题时，这一点很有用。在这种情况下，Cargo 支持撤回（yank）某个 crate 版本。

撤回（yanking）一个版本会阻止新项目依赖这个版本，同时允许所有已经依赖它的现有项目继续使用。本质上，撤回意味着所有带有 Cargo.lock 的项目都不会被破坏，而将来生成的任何 Cargo.lock 文件都不会使用被撤回的版本。

要撤回 crate 的某个版本，请在你之前发布过的 crate 的目录中运行 cargo yank 并指定要撤回的版本。例如，如果我们发布了一个名为 guessing_game 的 crate 的 1.0.1 版本，并且想要撤回它，就在 guessing_game 的项目目录中运行以下命令：

$ cargo yank --vers 1.0.1
    Updating crates.io index
        Yank guessing_game@1.0.1

在命令中加上 --undo，还可以撤销一次撤回，允许项目重新开始依赖这个版本：

$ cargo yank --vers 1.0.1 --undo
    Updating crates.io index
      Unyank guessing_game@1.0.1

撤回不会删除任何代码。例如，它无法删除意外上传的密钥等机密信息。如果发生了这种情况，你必须立即重置这些机密信息。
