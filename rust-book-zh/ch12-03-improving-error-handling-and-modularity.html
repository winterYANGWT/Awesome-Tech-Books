Rust 程序设计语言

重构以改进模块化与错误处理

为了改进程序，我们要修复四个与程序结构以及潜在错误处理方式相关的问题。第一，我们的 main 函数现在执行两项任务：解析参数和读取文件。随着程序的增长，main 函数要处理的独立任务会越来越多。一个函数承担的职责越多，就越难以推理、越难以测试，修改时也越容易破坏其中的某个部分。最好把功能拆分开来，让每个函数只负责一项任务。

这个问题也与第二个问题相关：虽然 query 和 file_path 是程序的配置变量，但像 contents 这样的变量则用于执行程序的逻辑。main 越长，需要引入作用域的变量就越多；作用域中的变量越多，就越难记住每个变量的用途。最好将配置变量组织到一个结构中，使它们的用途一目了然。

第三个问题是，我们在读取文件失败时使用 expect 来打印错误信息，但错误信息只会打印 Should have been able to read the file。读取文件可能因为多种原因而失败：例如文件可能不存在，或者我们可能没有打开它的权限。目前无论是哪种情况，我们都会打印同样的错误信息，这不会给用户提供任何有用的信息！

第四，我们使用 expect 来处理错误，如果用户运行程序时没有提供足够的参数，他们会从 Rust 那里得到一个 index out of bounds 错误，而这个错误并不能清楚地说明问题所在。最好把所有错误处理代码都放在一个地方，这样将来的维护者在需要修改错误处理逻辑时，只需查看一处代码。把所有错误处理代码放在一处，也能确保我们打印的信息对最终用户是有意义的。

让我们通过重构项目来解决这四个问题。

二进制项目的关注点分离

将多项任务的职责都交给 main 函数，这种组织问题在许多二进制项目中都很常见。因此，许多 Rust 程序员发现，当 main 函数开始变得庞大时，将二进制程序的不同关注点拆分开来是很有用的。这个过程包含以下步骤：

  • 将程序拆分成 main.rs 文件和 lib.rs 文件，并将程序的逻辑移到 lib.rs 中。
  • 只要命令行解析逻辑还比较少，它就可以保留在 main 函数中。
  • 当命令行解析逻辑开始变得复杂时，将其从 main 函数中提取到其他函数或类型中。

经过这个过程之后，留在 main 函数中的职责应当仅限于以下几项：

  • 使用参数值调用命令行解析逻辑
  • 进行其他配置
  • 调用 lib.rs 中的 run 函数
  • 如果 run 返回错误，则处理该错误

这种模式讲的就是关注点分离：main.rs 负责运行程序，lib.rs 负责处理手头任务的所有逻辑。因为你无法直接测试 main 函数，所以这种结构通过将程序的所有逻辑移出 main 函数，让你可以测试这些逻辑。留在 main 函数中的代码会足够少，只需阅读就能验证其正确性。让我们按照这个过程来重写程序。

提取参数解析器

我们将把解析参数的功能提取到一个由 main 调用的函数中。示例 12-5 展示了 main 函数新的开头部分，它调用了一个新函数 parse_config，我们将在 src/main.rs 中定义这个函数。

我们仍然将命令行参数收集到一个 vector 中，但不再在 main 函数中把索引 1 处的参数值赋给变量 query、把索引 2 处的参数值赋给变量 file_path，而是将整个 vector 传给 parse_config 函数。然后由 parse_config 函数负责决定哪个参数放进哪个变量的逻辑，并将这些值传回给 main。我们仍然在 main 中创建 query 和 file_path 变量，但 main 不再负责确定命令行参数与变量之间的对应关系。

对于我们这个小程序来说，这样的重写似乎有些小题大做，但我们正在以小步渐进的方式进行重构。做完这个改动后，再次运行程序，确认参数解析仍然正常工作。经常检查进度是个好习惯，这有助于在问题出现时找出其原因。

组织配置值

我们还可以再迈出一小步，进一步改进 parse_config 函数。目前我们返回的是一个元组，但随后又立即把这个元组拆分成单独的部分。这表明我们可能还没有找到正确的抽象。

另一个表明还有改进空间的迹象是 parse_config 中的 config 部分，它暗示我们返回的两个值是相关的，并且都是同一个配置值的组成部分。目前，除了把这两个值组合成一个元组之外，我们并没有在数据结构中体现出这层含义；我们改为把这两个值放进一个结构体中，并给结构体的每个字段起一个有意义的名字。这样做能让这段代码将来的维护者更容易理解不同的值之间有什么关系，以及它们各自的用途。

示例 12-6 展示了对 parse_config 函数的改进。

我们新增了一个名为 Config 的结构体，它定义了名为 query 和 file_path 的字段。parse_config 的签名现在表明它返回一个 Config 值。在 parse_config 的函数体中，我们以前返回的是引用 args 中 String 值的字符串切片，而现在我们将 Config 定义为包含拥有所有权的 String 值。main 中的 args 变量是这些参数值的所有者，它只是让 parse_config 函数借用这些值，这意味着如果 Config 试图获取 args 中值的所有权，就会违反 Rust 的借用规则。

管理 String 数据的方式有很多种；最简单（尽管效率稍低）的方法是在这些值上调用 clone 方法。这会为 Config 实例制作一份数据的完整副本供其拥有，与存储字符串数据的引用相比，这会花费更多的时间和内存。不过，克隆数据也让我们的代码变得非常直观，因为我们不必管理引用的生命周期；在这种情况下，牺牲一点性能来换取简洁性是值得的。

使用 clone 的权衡

由于 clone 有运行时开销，许多 Rustacean 都倾向于避免用它来解决所有权问题。在第 13 章中，你将学习如何在这类情况下使用更高效的方法。但就目前而言，复制几个字符串以便继续推进是完全可以的，因为这些复制只会发生一次，而且文件路径和查询字符串都非常小。有一个虽然效率稍低但能正常工作的程序，要好过在第一遍编写时就试图对代码进行过度优化。随着你对 Rust 越来越有经验，一开始就采用最高效的解决方案会变得更容易，但现在调用 clone 是完全可以接受的。

我们更新了 main，把 parse_config 返回的 Config 实例放进一个名为 config 的变量中，并修改了之前使用独立的 query 和 file_path 变量的代码，改为使用 Config 结构体上的字段。

现在我们的代码更清楚地表明了 query 和 file_path 是相关的，而且它们的用途是配置程序的工作方式。任何使用这些值的代码都知道可以在 config 实例中按用途命名的字段里找到它们。

为 Config 创建构造函数

到目前为止，我们已经从 main 中提取出负责解析命令行参数的逻辑，并将其放到了 parse_config 函数中。这样做帮助我们看出 query 和 file_path 这两个值是相关的，而这种关系应当在代码中体现出来。接着我们添加了一个 Config 结构体，用来为 query 和 file_path 的共同用途命名，并且能够让 parse_config 函数以结构体字段名的形式返回这些值的名称。

既然 parse_config 函数的用途是创建一个 Config 实例，我们就可以把 parse_config 从一个普通函数改为一个与 Config 结构体关联的、名为 new 的函数。做出这个修改会让代码更加惯用。我们可以通过调用 String::new 来创建标准库中 String 等类型的实例。类似地，把 parse_config 改成与 Config 关联的 new 函数之后，我们就可以通过调用 Config::new 来创建 Config 的实例。示例 12-7 展示了我们需要做的修改。

我们把 main 中调用 parse_config 的地方改为调用 Config::new。我们把 parse_config 的名字改成了 new，并把它移到一个 impl 块中，这样 new 函数就与 Config 关联起来了。再次尝试编译这段代码，确保它能正常工作。

修复错误处理

现在我们来修复错误处理。回想一下，如果 args vector 中的元素少于三个，尝试访问其索引 1 或索引 2 处的值就会导致程序 panic。试着不带任何参数运行程序，结果会是这样：

index out of bounds: the len is 1 but the index is 1 这一行是给程序员看的错误信息。它无法帮助最终用户理解他们应该怎么做。我们现在就来解决这个问题。

改进错误信息

在示例 12-8 中，我们在 new 函数中添加了一项检查，在访问索引 1 和索引 2 之前先验证切片是否足够长。如果切片不够长，程序就会 panic 并显示一条更好的错误信息。

这段代码类似于我们在示例 9-13 中编写的 Guess::new 函数，那里当 value 参数超出有效值范围时，我们调用了 panic!。这里我们不是检查值的范围，而是检查 args 的长度是否至少为 3，这样函数的其余部分就可以在这个条件已经满足的前提下运行。如果 args 中的元素少于三个，这个条件就为 true，我们会调用 panic! 宏立即终止程序。

在 new 中加入这几行额外的代码之后，我们再次不带任何参数运行程序，看看现在的错误是什么样子：

$ cargo run
   Compiling minigrep v0.1.0 (file:///projects/minigrep)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.0s
     Running `target/debug/minigrep`

thread 'main' (6023776) panicked at src/main.rs:26:13:
not enough arguments
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

这个输出好多了：我们现在有了一条合理的错误信息。不过，其中也包含了一些我们不想展示给用户的多余信息。也许我们在示例 9-13 中使用的技巧并不是这里的最佳选择：正如第 9 章所讨论的，调用 panic! 更适合用于编程问题，而不是使用问题。因此，我们将改用你在第 9 章学过的另一种技巧——返回一个 Result，用它来表示成功或错误。

返回 Result 而不是调用 panic!

我们可以改为返回一个 Result 值，它在成功时包含一个 Config 实例，在出错时则描述问题所在。我们还要把函数名从 new 改成 build，因为许多程序员都认为 new 函数永远不会失败。当 Config::build 与 main 交互时，我们可以使用 Result 类型来表明出现了问题。然后，我们可以修改 main，把 Err 变体转换成对用户更实用的错误信息，而不会出现调用 panic! 所带来的那些关于 thread 'main' 和 RUST_BACKTRACE 的附加文本。

示例 12-9 展示了我们需要对这个现在名为 Config::build 的函数的返回值所做的修改，以及为返回 Result 而需要对函数体所做的修改。注意，在我们同样更新 main 之前，这段代码是无法编译的，我们会在下一个示例中更新 main。

我们的 build 函数返回一个 Result，在成功时包含一个 Config 实例，在出错时包含一个字符串字面量。我们的错误值将始终是具有 'static 生命周期的字符串字面量。

我们在函数体中做了两处修改：当用户没有传入足够的参数时，我们不再调用 panic!，而是返回一个 Err 值；并且我们把返回值 Config 包装在了 Ok 中。这些修改使函数符合其新的类型签名。

从 Config::build 返回 Err 值，使得 main 函数可以处理 build 函数返回的 Result 值，并在出错时更干净地退出进程。

调用 Config::build 并处理错误

为了处理错误情况并打印对用户友好的信息，我们需要更新 main，让它处理 Config::build 返回的 Result，如示例 12-10 所示。我们还将不再依赖 panic! 来让命令行工具以非零错误码退出，而是改为手动实现这一点。非零退出状态是一种约定，用于向调用我们程序的进程表明程序以错误状态退出。

在这个示例中，我们使用了一个还没有详细介绍过的方法：unwrap_or_else，它由标准库定义在 Result<T, E> 上。使用 unwrap_or_else 可以让我们定义一些自定义的、不使用 panic! 的错误处理。如果 Result 是 Ok 值，这个方法的行为与 unwrap 类似：它返回 Ok 所包装的内部值。然而，如果值是 Err 值，这个方法就会调用闭包中的代码，闭包是我们定义并作为参数传给 unwrap_or_else 的匿名函数。我们会在第 13 章中更详细地介绍闭包。现在你只需要知道，unwrap_or_else 会把 Err 的内部值（在本例中就是我们在示例 12-9 中添加的静态字符串 "not enough arguments"）传给闭包中位于两条竖线之间的参数 err。闭包中的代码在运行时就可以使用这个 err 值。

我们新增了一行 use，将标准库中的 process 引入作用域。在出错时运行的闭包代码只有两行：打印 err 值，然后调用 process::exit。process::exit 函数会立即停止程序，并将传入的数字作为退出状态码返回。这与我们在示例 12-8 中使用的基于 panic! 的处理方式类似，但我们不会再得到那些多余的输出了。让我们试一试：

$ cargo run
   Compiling minigrep v0.1.0 (file:///projects/minigrep)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.48s
     Running `target/debug/minigrep`
Problem parsing arguments: not enough arguments

太好了！这样的输出对用户友好多了。

从 main 中提取逻辑

既然我们已经完成了对配置解析的重构，现在就来处理程序的逻辑。正如我们在“二进制项目的关注点分离”中所说，我们将提取一个名为 run 的函数，它将包含 main 函数中目前所有与设置配置或处理错误无关的逻辑。完成之后，main 函数会变得简洁，只需检查就能轻松验证其正确性，而且我们将能够为其余所有逻辑编写测试。

示例 12-11 展示了提取 run 函数这一小步渐进式的改进。

现在 run 函数包含了 main 中从读取文件开始的所有剩余逻辑。run 函数接受 Config 实例作为参数。

从 run 返回错误

把剩余的程序逻辑分离到 run 函数中之后，我们就可以像示例 12-9 中对 Config::build 所做的那样改进错误处理了。run 函数不再通过调用 expect 让程序 panic，而是在出错时返回一个 Result<T, E>。这能让我们以对用户友好的方式，进一步把错误处理相关的逻辑集中到 main 中。示例 12-12 展示了我们需要对 run 的签名和函数体所做的修改。

这里我们做了三处重要的修改。首先，我们把 run 函数的返回类型改为 Result<(), Box<dyn Error>>。这个函数之前返回的是单元类型 ()，我们在 Ok 的情况下仍然保留它作为返回值。

对于错误类型，我们使用了 trait 对象 Box<dyn Error>（并且在文件顶部用 use 语句将 std::error::Error 引入了作用域）。我们会在第 18 章中介绍 trait 对象。现在你只需知道，Box<dyn Error> 表示函数会返回一个实现了 Error trait 的类型，但我们不必指定返回值具体是哪种类型。这让我们可以灵活地在不同的错误情况下返回不同类型的错误值。dyn 关键字是 dynamic（动态）的缩写。

其次，我们去掉了对 expect 的调用，改用 ? 运算符，正如我们在第 9 章中讨论过的那样。? 不会在出错时 panic!，而是会从当前函数返回错误值，交由调用者处理。

第三，run 函数现在在成功时返回一个 Ok 值。我们在签名中将 run 函数的成功类型声明为 ()，这意味着我们需要把单元类型的值包装在 Ok 值中。这种 Ok(()) 语法乍看起来可能有点奇怪。但像这样使用 () 是一种惯用的方式，表明我们调用 run 只是为了它的副作用；它不会返回我们需要的值。

Rust 告诉我们，代码忽略了 Result 值，而这个 Result 值可能表明发生了错误。但我们并没有检查是否出现了错误，编译器在提醒我们这里可能应该有一些错误处理代码！我们现在就来解决这个问题。

在 main 中处理 run 返回的错误

我们将使用一种与示例 12-10 中处理 Config::build 类似的技巧来检查并处理错误，不过略有不同：

文件名：src/main.rs

use std::env;
use std::error::Error;
use std::fs;
use std::process;

fn main() {
    // --snip--

    let args: Vec<String> = env::args().collect();

    let config = Config::build(&args).unwrap_or_else(|err| {
        println!("Problem parsing arguments: {err}");
        process::exit(1);
    });

    println!("Searching for {}", config.query);
    println!("In file {}", config.file_path);

    if let Err(e) = run(config) {
        println!("Application error: {e}");
        process::exit(1);
    }
}

fn run(config: Config) -> Result<(), Box<dyn Error>> {
    let contents = fs::read_to_string(config.file_path)?;

    println!("With text:\n{contents}");

    Ok(())
}

struct Config {
    query: String,
    file_path: String,
}

impl Config {
    fn build(args: &[String]) -> Result<Config, &'static str> {
        if args.len() < 3 {
            return Err("not enough arguments");
        }

        let query = args[1].clone();
        let file_path = args[2].clone();

        Ok(Config { query, file_path })
    }
}

我们使用 if let 而不是 unwrap_or_else 来检查 run 是否返回了 Err 值，如果是，就调用 process::exit(1)。run 函数并不像 Config::build 返回 Config 实例那样返回一个我们想要 unwrap 的值。因为 run 在成功时返回 ()，我们只关心能否检测到错误，所以不需要 unwrap_or_else 来返回解包后的值，因为那个值只会是 ()。

if let 和 unwrap_or_else 函数的主体在两种情况下是一样的：打印错误并退出。

将代码拆分到库 crate 中

到目前为止，我们的 minigrep 项目看起来很不错！现在我们将拆分 src/main.rs 文件，把一部分代码放进 src/lib.rs 文件中。这样我们就可以测试这些代码，并让 src/main.rs 文件承担更少的职责。

我们把负责搜索文本的代码定义在 src/lib.rs 而不是 src/main.rs 中，这样我们（或者任何使用我们 minigrep 库的人）就可以在 minigrep 二进制程序之外的更多场合调用这个搜索函数。

首先，我们在 src/lib.rs 中定义 search 函数的签名，如示例 12-13 所示，其函数体调用了 unimplemented! 宏。等到填充具体实现时，我们会更详细地解释这个签名。

我们在函数定义上使用了 pub 关键字，将 search 指定为库 crate 公有 API 的一部分。现在我们就有了一个既可以在二进制 crate 中使用、又可以进行测试的库 crate！

接下来，我们需要把 src/lib.rs 中定义的代码引入 src/main.rs 中二进制 crate 的作用域并调用它，如示例 12-14 所示。

我们添加了一行 use minigrep::search，将库 crate 中的 search 函数引入二进制 crate 的作用域。然后，在 run 函数中，我们不再打印文件的内容，而是调用 search 函数，并将 config.query 的值和 contents 作为参数传入。接着，run 会使用一个 for 循环，打印 search 返回的每一个与查询匹配的行。现在也正是时候删除 main 函数中显示查询内容和文件路径的那些 println! 调用了，这样程序就只会打印搜索结果（如果没有出错的话）。

注意，搜索函数会在任何打印发生之前，先把所有结果收集到它返回的 vector 中。在搜索大文件时，这种实现显示结果可能会比较慢，因为结果不是在找到时立即打印出来的；我们将在第 13 章讨论一种使用迭代器来解决这个问题的可行方法。

呼！工作量真不小，但我们已经为将来的成功打好了基础。现在处理错误要容易得多，代码也变得更加模块化了。从现在开始，我们几乎所有的工作都会在 src/lib.rs 中完成。

让我们利用这种新获得的模块化，做一件对旧代码来说很困难、但对新代码来说很容易的事情：编写一些测试！
