构建单线程 Web 服务器

我们先从让一个单线程 Web 服务器跑起来开始。在动手之前，让我们快速了解一下构建 Web 服务器所涉及的协议。这些协议的细节超出了本书的范围，不过简要的概述就能为你提供所需的信息。

Web 服务器涉及的两个主要协议是超文本传输协议（Hypertext Transfer Protocol，HTTP）和传输控制协议（Transmission Control Protocol，TCP）。这两个协议都是请求-响应（request-response）协议，也就是说，由客户端（client）发起请求，服务器（server）监听请求并向客户端提供响应。这些请求和响应的内容由协议定义。

TCP 是较底层的协议，它描述了信息如何从一个服务器传送到另一个服务器的细节，但并不规定这些信息是什么。HTTP 构建在 TCP 之上，它定义了请求和响应的内容。从技术上讲，HTTP 也可以与其他协议一起使用，但在绝大多数情况下，HTTP 都是通过 TCP 发送数据的。我们将直接处理 TCP 以及 HTTP 请求和响应的原始字节。

监听 TCP 连接

我们的 Web 服务器需要监听 TCP 连接，因此这是我们要实现的第一部分。标准库提供了 std::net 模块，可以让我们做到这一点。让我们像往常一样新建一个项目：

$ cargo new hello
     Created binary (application) `hello` project
$ cd hello

现在，在 src/main.rs 中输入示例 21-1 中的代码作为开始。这段代码会在本地地址 127.0.0.1:7878 上监听传入的 TCP 流。当它收到一个传入的流时，就会打印出 Connection established!。

使用 TcpListener，我们可以在地址 127.0.0.1:7878 上监听 TCP 连接。在这个地址中，冒号之前的部分是代表你的计算机的 IP 地址（它在每台计算机上都一样，并不特指作者的计算机），而 7878 是端口。我们选择这个端口有两个原因：HTTP 通常不使用这个端口，因此我们的服务器不太可能与你机器上可能正在运行的其他 Web 服务器发生冲突；而且 7878 是在电话键盘上输入 rust 所对应的数字。

在这个场景中，bind 函数的作用类似于 new 函数，它会返回一个新的 TcpListener 实例。这个函数之所以叫 bind，是因为在网络领域，连接到一个端口进行监听被称为“绑定到端口”（binding to a port）。

bind 函数返回一个 Result<T, E>，这表明绑定有可能失败。例如，如果我们运行了程序的两个实例，就会有两个程序监听同一个端口。因为我们编写的只是一个用于学习的基础服务器，所以不必操心如何处理这类错误；我们直接使用 unwrap，在发生错误时让程序停止。

TcpListener 上的 incoming 方法会返回一个迭代器，它为我们提供一系列的流（更具体地说，是 TcpStream 类型的流）。单个流（stream）代表客户端与服务器之间的一个打开的连接。连接（connection）指的是完整的请求和响应过程：客户端连接到服务器，服务器生成响应，然后服务器关闭连接。因此，我们将从 TcpStream 中读取客户端发送的内容，然后把响应写入流中，从而将数据发回给客户端。总的来说，这个 for 循环会依次处理每个连接，并为我们产生一系列需要处理的流。

目前，我们对流的处理只是调用 unwrap：如果流出现任何错误，就终止程序；如果没有错误，程序就打印一条消息。在下一个示例中，我们将为成功的情况添加更多功能。当客户端连接到服务器时，我们之所以可能从 incoming 方法收到错误，是因为我们实际上遍历的并不是连接，而是连接尝试（connection attempt）。连接可能会因为多种原因而失败，其中很多原因与具体的操作系统有关。例如，许多操作系统对能够同时支持的打开连接数有上限；超出这个数量的新连接尝试会产生错误，直到某些已打开的连接被关闭为止。

让我们试着运行这段代码！在终端中执行 cargo run，然后在 Web 浏览器中加载 127.0.0.1:7878。浏览器应该会显示类似“Connection reset”（连接被重置）的错误消息，因为服务器目前没有发回任何数据。但当你查看终端时，应该会看到浏览器连接到服务器时打印出的若干条消息！

     Running `target/debug/hello`
Connection established!
Connection established!
Connection established!

有时，一次浏览器请求会让你看到打印出多条消息；原因可能是浏览器除了请求页面之外，还请求了其他资源，比如出现在浏览器标签页上的 favicon.ico 图标。

也有可能是因为服务器没有返回任何数据，浏览器在尝试多次连接服务器。当 stream 在循环末尾离开作用域并被丢弃时，连接会作为 drop 实现的一部分被关闭。浏览器有时会通过重试来处理已关闭的连接，因为问题可能只是暂时的。

浏览器有时还会在不发送任何请求的情况下打开多个到服务器的连接，这样如果之后确实要发送请求，这些请求就能更快地完成。发生这种情况时，无论连接上有没有请求，我们的服务器都会看到每一个连接。例如，许多版本的基于 Chrome 的浏览器都会这样做；你可以使用隐私浏览模式或换一个浏览器来禁用这项优化。

重要的是，我们已经成功获取到了一个 TCP 连接的句柄！

读取请求

让我们来实现从浏览器读取请求的功能！为了把“先获取连接”和“再对连接执行某些操作”这两个关注点分离开来，我们将新建一个函数来处理连接。在这个新的 handle_connection 函数中，我们会从 TCP 流中读取数据并打印出来，以便查看浏览器发送过来的数据。将代码修改为示例 21-2 所示的样子。

我们将 std::io::BufReader 和 std::io::prelude 引入作用域，以便使用那些能让我们读写流的 trait 和类型。在 main 函数的 for 循环中，我们不再打印一条表示已建立连接的消息，而是调用新的 handle_connection 函数并把 stream 传给它。

在 handle_connection 函数中，我们创建了一个新的 BufReader 实例，它包装了对 stream 的引用。BufReader 通过替我们管理对 std::io::Read trait 方法的调用来增加缓冲功能。

我们创建了一个名为 http_request 的变量，用来收集浏览器发送给服务器的请求中的各行。通过添加 Vec<_> 类型注解，我们表明希望把这些行收集到一个 vector 中。

BufReader 实现了 std::io::BufRead trait，该 trait 提供了 lines 方法。lines 方法每当遇到换行字节时就会切分数据流，并返回一个 Result<String, std::io::Error> 的迭代器。为了得到每个 String，我们对每个 Result 进行 map 和 unwrap。如果数据不是有效的 UTF-8，或者从流中读取时出现了问题，Result 就可能是一个错误。同样，生产环境中的程序应当更优雅地处理这些错误，但为了简单起见，我们选择在出错时直接停止程序。

浏览器通过连续发送两个换行符来标志一个 HTTP 请求的结束，因此为了从流中获取一个请求，我们会不断读取行，直到遇到一个空字符串行为止。把这些行收集到 vector 中之后，我们使用美化的调试格式将它们打印出来，以便查看 Web 浏览器发送给服务器的指令。

仔细看看 HTTP 请求

HTTP 是一种基于文本的协议，请求采用如下格式：

Method Request-URI HTTP-Version CRLF
headers CRLF
message-body

第一行是请求行（request line），它包含了客户端所请求内容的信息。请求行的第一部分表示所使用的方法，比如 GET 或 POST，它描述了客户端以何种方式发起这次请求。我们的客户端使用的是 GET 请求，这意味着它是在请求获取信息。

请求行的下一部分是 /，它表示客户端所请求的统一资源标识符（uniform resource identifier，URI）：URI 与统一资源定位符（uniform resource locator，URL）几乎相同，但不完全一样。就本章的目的而言，URI 和 URL 之间的区别并不重要，不过 HTTP 规范使用的是 URI 这个术语，所以在这里你可以在心里把 URI 替换成 URL。

最后一部分是客户端所使用的 HTTP 版本，然后请求行以一个 CRLF 序列结尾。（CRLF 代表回车（carriage return）和换行（line feed），这些术语来自打字机时代！）CRLF 序列也可以写作 \r\n，其中 \r 是回车，\n 是换行。CRLF 序列将请求行与请求数据的其余部分分隔开。注意，打印 CRLF 时，我们看到的是新起一行，而不是 \r\n。

查看目前运行程序时收到的请求行数据，可以看到 GET 是方法，/ 是请求 URI，HTTP/1.1 是版本。

请求行之后，从 Host: 开始的其余各行都是标头（header）。GET 请求没有主体（body）。

编写响应

接下来我们要实现发送数据来响应客户端的请求。响应采用如下格式：

HTTP-Version Status-Code Reason-Phrase CRLF
headers CRLF
message-body

第一行是状态行（status line），它包含响应所使用的 HTTP 版本、一个概括请求结果的数字状态码，以及一个为状态码提供文字描述的原因短语（reason phrase）。CRLF 序列之后是任意数量的标头、另一个 CRLF 序列，以及响应的主体。

下面是一个响应示例，它使用 HTTP 1.1 版本，状态码为 200，原因短语为 OK，没有标头，也没有主体：

HTTP/1.1 200 OK\r\n\r\n

状态码 200 是标准的成功响应。这段文本就是一个极简的成功 HTTP 响应。让我们把它写入流中，作为对成功请求的响应！在 handle_connection 函数中，删除打印请求数据的 println!，并替换为示例 21-3 中的代码。

新增的第一行定义了 response 变量，用于保存成功消息的数据。然后，我们对 response 调用 as_bytes，将字符串数据转换为字节。stream 上的 write_all 方法接受一个 &[u8]，并将这些字节直接通过连接发送出去。因为 write_all 操作可能会失败，所以我们像之前一样对任何错误结果使用 unwrap。同样，在真实的应用程序中，你应当在这里添加错误处理。

完成这些修改后，让我们运行代码并发起一个请求。由于我们不再向终端打印任何数据，因此除了 Cargo 的输出之外不会看到其他输出。当你在 Web 浏览器中加载 127.0.0.1:7878 时，应该会看到一个空白页面，而不是错误。你刚刚亲手编码实现了接收 HTTP 请求并发送响应！

重构

目前，if 和 else 块中有大量重复：它们都在读取文件，并将文件内容写入流中。唯一的区别在于状态行和文件名。让我们把这些差异提取到单独的 if 和 else 行中，由它们把状态行和文件名的值赋给变量，从而让代码更加简洁；然后，我们就可以在读取文件和写入响应的代码中无条件地使用这些变量。示例 21-9 展示了替换掉大段 if 和 else 块之后的代码。

现在，if 和 else 块只是在一个元组中返回状态行和文件名的相应值；然后，我们在 let 语句中使用模式进行解构，将这两个值赋给 status_line 和 filename，这一点我们在第 19 章中讨论过。

之前重复的代码现在位于 if 和 else 块之外，并使用了 status_line 和 filename 变量。这样一来，两种情况之间的差异就更容易看清了；而且如果我们想改变文件读取和响应写入的方式，只需要修改一处代码。示例 21-9 中代码的行为与示例 21-7 中的完全相同。

目前，我们的服务器运行在单个线程中，这意味着它一次只能处理一个请求。让我们通过模拟一些慢请求来看看这会带来什么问题。然后，我们会修复它，让服务器能够同时处理多个请求。
