Rust 程序设计语言

使用 trait 对象抽象共同行为

在第 8 章中我们提到过，vector 的一个局限是它只能存储同一种类型的元素。在示例 8-9 中我们找到了一个变通办法：定义一个 SpreadsheetCell 枚举，它的变体可以分别存放整数、浮点数和文本。这意味着我们可以在每个单元格中存储不同类型的数据，同时仍然用一个 vector 来表示一行单元格。当可互换的项是一组在编译代码时就已知的固定类型时，这是一个非常好的解决方案。

然而，有时我们希望库的使用者能够扩展在某个特定场景下有效的类型集合。为了展示如何做到这一点，我们将创建一个图形用户界面（GUI）工具的示例，它会遍历一个项的列表，对每一项调用 draw 方法将其绘制到屏幕上——这是 GUI 工具的一种常见技术。我们会创建一个名为 gui 的库 crate，其中包含一个 GUI 库的结构。这个 crate 可能会提供一些供人使用的类型，比如 Button 或 TextField。此外，gui 的用户还会想要创建自己的可绘制类型：例如，某个程序员可能会添加 Image，另一个程序员可能会添加 SelectBox。

在编写这个库时，我们无法预知并定义其他程序员可能想要创建的所有类型。但我们确实知道，gui 需要记录许多不同类型的值，并且需要对这些不同类型的值逐一调用 draw 方法。它不需要确切知道调用 draw 方法时会发生什么，只需要知道这个值有这个方法可供我们调用即可。

在一门具有继承的语言中，要做到这一点，我们可能会定义一个名为 Component 的类，它有一个名为 draw 的方法。其他类，比如 Button、Image 和 SelectBox，会继承 Component，从而继承 draw 方法。它们可以各自覆盖 draw 方法来定义自己的定制行为，而框架则可以把所有这些类型都当作 Component 实例来对待，并对它们调用 draw。但由于 Rust 没有继承，我们需要另一种方式来组织 gui 库，让用户能够创建与该库兼容的新类型。

为共同行为定义 trait

为了实现我们希望 gui 具备的行为，我们会定义一个名为 Draw 的 trait，它有一个名为 draw 的方法。然后，我们就可以定义一个存放 trait 对象的 vector。trait 对象（trait object）既指向一个实现了我们所指定 trait 的类型的实例，也指向一张用于在运行时查找该类型上 trait 方法的表。创建 trait 对象的方式是：先指定某种指针，比如引用或 Box<T> 智能指针，然后是 dyn 关键字，再指定相关的 trait。（我们会在第 20 章“动态大小类型与 Sized trait”部分讨论 trait 对象必须使用指针的原因。）我们可以用 trait 对象来代替泛型类型或具体类型。无论在哪里使用 trait 对象，Rust 的类型系统都会在编译时确保在该上下文中使用的任何值都实现了 trait 对象所对应的 trait。因此，我们不需要在编译时知道所有可能的类型。

我们提到过，在 Rust 中，我们刻意不把结构体和枚举称为“对象”，以便与其他语言中的对象区分开来。在结构体或枚举中，结构体字段中的数据与 impl 块中的行为是分开的；而在其他语言中，数据和行为组合成的单一概念通常被称为对象。trait 对象与其他语言中的对象的不同之处在于，我们不能向 trait 对象中添加数据。trait 对象不像其他语言中的对象那样用途广泛：它们的特定用途是对共同行为进行抽象。

示例 18-3 展示了如何定义一个名为 Draw 的 trait，它有一个名为 draw 的方法。

这种语法在我们第 10 章讨论如何定义 trait 时应该已经见过了。接下来是一些新语法：示例 18-4 定义了一个名为 Screen 的结构体，它持有一个名为 components 的 vector。这个 vector 的类型是 Box<dyn Draw>，这是一个 trait 对象；它代表 Box 中任何实现了 Draw trait 的类型。

我们会在 Screen 结构体上定义一个名为 run 的方法，它会对 components 中的每一项调用 draw 方法，如示例 18-5 所示。

这与定义一个使用带 trait bound 的泛型类型参数的结构体的工作方式不同。泛型类型参数一次只能被替换为一种具体类型，而 trait 对象则允许在运行时由多种具体类型来充当该 trait 对象。例如，我们本可以使用泛型类型和 trait bound 来定义 Screen 结构体，如示例 18-6 所示。

这会把我们限制在这样的 Screen 实例上：其组件列表中的元素要么全是 Button 类型，要么全是 TextField 类型。如果你只会用到同构集合，那么使用泛型和 trait bound 是更好的选择，因为这些定义会在编译时被单态化以使用具体类型。

另一方面，如果使用基于 trait 对象的方法，一个 Screen 实例就可以持有一个既包含 Box<Button> 又包含 Box<TextField> 的 Vec<T>。让我们看看这是如何工作的，之后再讨论它对运行时性能的影响。

实现 trait

现在我们来添加一些实现了 Draw trait 的类型。我们会提供 Button 类型。同样，真正实现一个 GUI 库超出了本书的范围，所以 draw 方法的方法体中不会有任何有用的实现。为了想象一下实现可能是什么样子，Button 结构体可能会有 width、height 和 label 字段，如示例 18-7 所示。

Button 上的 width、height 和 label 字段会与其他组件上的字段有所不同；例如，TextField 类型可能除了这些字段之外还有一个 placeholder 字段。我们想要在屏幕上绘制的每种类型都会实现 Draw trait，但会在 draw 方法中使用不同的代码来定义如何绘制该特定类型，就像这里的 Button 一样（如前所述，这里没有实际的 GUI 代码）。例如，Button 类型可能还会有一个额外的 impl 块，其中包含与用户点击按钮时所发生的事情相关的方法。这类方法并不适用于 TextField 这样的类型。

如果使用我们库的某个人决定实现一个带有 width、height 和 options 字段的 SelectBox 结构体，那么他们也会在 SelectBox 类型上实现 Draw trait，如示例 18-8 所示。

现在，我们库的用户可以编写他们的 main 函数来创建一个 Screen 实例。他们可以把 SelectBox 和 Button 分别放进 Box<T> 中使其成为 trait 对象，再添加到 Screen 实例中。然后，他们就可以调用 Screen 实例上的 run 方法，该方法会对每个组件调用 draw。示例 18-9 展示了这一实现。

编写这个库时，我们并不知道有人可能会添加 SelectBox 类型，但我们的 Screen 实现能够操作这个新类型并绘制它，因为 SelectBox 实现了 Draw trait，也就是说它实现了 draw 方法。

这种只关心值所响应的消息、而不关心值的具体类型的概念，类似于动态类型语言中鸭子类型（duck typing）的概念：如果它走起来像鸭子，叫起来也像鸭子，那它一定就是鸭子！在示例 18-5 中 Screen 上 run 的实现里，run 不需要知道每个组件的具体类型是什么。它不会检查某个组件是 Button 的实例还是 SelectBox 的实例，只是对该组件调用 draw 方法。通过把 Box<dyn Draw> 指定为 components vector 中值的类型，我们就把 Screen 定义为需要那些可以调用 draw 方法的值。

使用 trait 对象和 Rust 的类型系统来编写类似于鸭子类型的代码，其优势在于我们永远不必在运行时检查某个值是否实现了某个特定方法，也不必担心在值没有实现某个方法却仍然调用它时会出错。如果值没有实现 trait 对象所需的 trait，Rust 就不会编译我们的代码。

例如，示例 18-10 展示了如果我们尝试创建一个以 String 作为组件的 Screen 会发生什么。

因为 String 没有实现 Draw trait，所以我们会得到这个错误：

这个错误让我们知道：要么我们向 Screen 传递了本不打算传递的东西，因此应该传递另一种类型；要么我们应该在 String 上实现 Draw，这样 Screen 就能够对它调用 draw 了。

执行动态分发

回忆一下第 10 章“使用泛型的代码的性能”部分中我们对编译器在泛型上执行的单态化过程的讨论：编译器会为我们用来替换泛型类型参数的每一种具体类型，生成函数和方法的非泛型实现。单态化所产生的代码执行的是静态分发（static dispatch），也就是编译器在编译时就知道你调用的是哪个方法。与之相对的是动态分发（dynamic dispatch），也就是编译器在编译时无法确定你调用的是哪个方法。在动态分发的情况下，编译器生成的代码会在运行时确定要调用哪个方法。

当我们使用 trait 对象时，Rust 必须使用动态分发。编译器并不知道可能会与使用 trait 对象的代码一起使用的所有类型，所以它不知道应该调用哪个类型上实现的哪个方法。取而代之的是，Rust 会在运行时使用 trait 对象内部的指针来确定要调用哪个方法。这种查找会产生静态分发所没有的运行时开销。动态分发还会阻止编译器选择内联方法的代码，进而妨碍某些优化；此外，Rust 对于哪些地方可以使用、哪些地方不能使用动态分发有一些规则，称为 dyn 兼容性（dyn compatibility）。这些规则超出了本节讨论的范围，不过你可以在 Rust 参考手册中了解更多相关内容。不管怎样，我们在示例 18-5 编写的代码中确实获得了额外的灵活性，并在示例 18-9 中得以支持多种类型，所以这是一个需要权衡的问题。
