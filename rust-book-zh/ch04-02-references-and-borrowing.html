Rust 程序设计语言

引用与借用

示例 4-5 中元组代码的问题在于，因为 String 被移动到了 calculate_length 中，所以我们必须把 String 返回给调用函数，才能在调用 calculate_length 之后继续使用这个 String。其实，我们可以提供一个指向 String 值的引用。引用就像指针一样，是一个地址，我们可以沿着它访问存储在该地址上的数据，而这些数据归其他某个变量所有。与指针不同的是，引用保证在其生命周期内始终指向某个特定类型的有效值。

下面展示了如何定义并使用一个以对象的引用作为参数、而不是获取值的所有权的 calculate_length 函数：

首先，注意到变量声明和函数返回值中的元组代码全都不见了。其次，注意我们把 &s1 传给了 calculate_length，并且在它的定义中，我们接收的是 &String 而不是 String。这些 & 符号表示引用，它们让你可以引用某个值而不获取它的所有权。图 4-6 描绘了这一概念。

图 4-6：&String s 指向 String s1 的示意图

注意：与使用 & 进行引用相反的操作是解引用（dereferencing），它通过解引用运算符 * 来完成。我们会在第 8 章看到解引用运算符的一些用法，并在第 15 章讨论解引用的细节。

我们来仔细看看这里的函数调用：

fn main() {
    let s1 = String::from("hello");

    let len = calculate_length(&s1);

    println!("The length of '{s1}' is {len}.");
}

fn calculate_length(s: &String) -> usize {
    s.len()
}

&s1 语法让我们创建一个指向 s1 的值、但并不拥有它的引用。因为引用并不拥有这个值，所以当引用不再被使用时，它所指向的值也不会被丢弃。

同样，函数签名使用 & 来表明参数 s 的类型是一个引用。我们来加上一些解释性的注释：

fn main() {
    let s1 = String::from("hello");

    let len = calculate_length(&s1);

    println!("The length of '{s1}' is {len}.");
}

fn calculate_length(s: &String) -> usize { // s is a reference to a String
    s.len()
} // Here, s goes out of scope. But because s does not have ownership of what
  // it refers to, the String is not dropped.

变量 s 有效的作用域与任何函数参数的作用域一样，但当 s 不再被使用时，引用所指向的值不会被丢弃，因为 s 并没有所有权。当函数以引用而不是实际的值作为参数时，我们就不需要为了交还所有权而返回这些值，因为我们从来就没有获得过所有权。

我们把创建引用的行为称为借用（borrowing）。就像在现实生活中一样，如果某人拥有某样东西，你可以从他那里借来。用完之后，你必须把它还回去。它并不属于你。

那么，如果我们尝试修改借用的东西，会发生什么呢？试试示例 4-6 中的代码。剧透一下：这行不通！

正如变量默认是不可变的，引用也是如此。我们不能修改引用所指向的东西。

可变引用

只需做几处小小的调整，改用可变引用（mutable reference），我们就能修复示例 4-6 中的代码，从而允许修改借用的值：

首先，我们把 s 改为 mut。然后，在调用 change 函数的地方用 &mut s 创建一个可变引用，并更新函数签名，用 some_string: &mut String 来接收一个可变引用。这样就非常清楚地表明，change 函数将会修改它所借用的值。

可变引用有一个很大的限制：如果你有一个指向某个值的可变引用，就不能再有指向该值的其他引用。下面这段试图为 s 创建两个可变引用的代码将会失败：

错误如下：

$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0499]: cannot borrow `s` as mutable more than once at a time
 --> src/main.rs:5:14
  |
4 |     let r1 = &mut s;
  |              ------ first mutable borrow occurs here
5 |     let r2 = &mut s;
  |              ^^^^^^ second mutable borrow occurs here
6 |
7 |     println!("{r1}, {r2}");
  |                -- first borrow later used here

For more information about this error, try `rustc --explain E0499`.
error: could not compile `ownership` (bin "ownership") due to 1 previous error

这个错误表明这段代码是无效的，因为我们不能在同一时间多次将 s 作为可变的借用。第一个可变借用在 r1 中，它必须持续到在 println! 中被使用为止；但在创建这个可变引用和使用它之间，我们又试图在 r2 中创建另一个可变引用，借用与 r1 相同的数据。

这个禁止在同一时间对同一数据存在多个可变引用的限制，允许修改，但方式非常受控。这是 Rust 新手常常感到棘手的地方，因为大多数语言都允许你随时修改数据。有这个限制的好处是，Rust 可以在编译时就防止数据竞争。数据竞争（data race）类似于竞态条件，它会在以下三种行为同时发生时出现：

  • 两个或更多的指针同时访问同一数据。
  • 至少有一个指针被用来写入数据。
  • 没有使用任何机制来同步对数据的访问。

数据竞争会导致未定义行为，而且当你试图在运行时追踪它们时，可能很难诊断和修复；Rust 通过拒绝编译存在数据竞争的代码来避免这个问题！

一如既往，我们可以使用花括号来创建一个新的作用域，从而允许拥有多个可变引用，只是不能同时拥有：

fn main() {
    let mut s = String::from("hello");

    {
        let r1 = &mut s;
    } // r1 goes out of scope here, so we can make a new reference with no problems.

    let r2 = &mut s;
}

对于可变引用与不可变引用的混用，Rust 也强制执行类似的规则。下面这段代码会导致错误：

fn main() {
    let mut s = String::from("hello");

    let r1 = &s; // no problem
    let r2 = &s; // no problem
    let r3 = &mut s; // BIG PROBLEM

    println!("{r1}, {r2}, and {r3}");
}

错误如下：

$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
 --> src/main.rs:6:14
  |
4 |     let r1 = &s; // no problem
  |              -- immutable borrow occurs here
5 |     let r2 = &s; // no problem
6 |     let r3 = &mut s; // BIG PROBLEM
  |              ^^^^^^ mutable borrow occurs here
7 |
8 |     println!("{r1}, {r2}, and {r3}");
  |                -- immutable borrow later used here

For more information about this error, try `rustc --explain E0502`.
error: could not compile `ownership` (bin "ownership") due to 1 previous error

哇哦！在拥有指向同一个值的不可变引用时，我们同样不能拥有可变引用。

不可变引用的使用者可不希望值在他们眼皮底下突然被改变！不过，多个不可变引用是允许的，因为只读取数据的人没有能力影响其他人对数据的读取。

注意，引用的作用域从它被引入的地方开始，一直持续到最后一次使用该引用为止。例如，下面这段代码可以编译，因为不可变引用的最后一次使用是在 println! 中，在引入可变引用之前：

fn main() {
    let mut s = String::from("hello");

    let r1 = &s; // no problem
    let r2 = &s; // no problem
    println!("{r1} and {r2}");
    // Variables r1 and r2 will not be used after this point.

    let r3 = &mut s; // no problem
    println!("{r3}");
}

不可变引用 r1 和 r2 的作用域在它们最后一次被使用的 println! 之后就结束了，而这发生在可变引用 r3 被创建之前。这些作用域没有重叠，所以这段代码是允许的：编译器能够判断出，在作用域结束之前的某个位置，该引用就已经不再被使用了。

尽管借用错误有时可能令人沮丧，但请记住，这是 Rust 编译器在提前（在编译时而不是运行时）指出一个潜在的 bug，并准确地告诉你问题出在哪里。这样，你就不必去追查为什么你的数据和你预想的不一样了。

悬垂引用

在具有指针的语言中，很容易在释放某块内存的同时保留指向它的指针，从而错误地造出一个悬垂指针（dangling pointer）——它引用的内存位置可能已经分配给了别人。相比之下，在 Rust 中，编译器保证引用永远不会成为悬垂引用：如果你有一个指向某些数据的引用，编译器会确保这些数据不会在其引用离开作用域之前离开作用域。

我们来尝试创建一个悬垂引用，看看 Rust 如何通过编译时错误来防止它们：

错误如下：

$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0106]: missing lifetime specifier
 --> src/main.rs:5:16
  |
5 | fn dangle() -> &String {
  |                ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from
help: consider using the `'static` lifetime, but this is uncommon unless you're returning a borrowed value from a `const` or a `static`
  |
5 | fn dangle() -> &'static String {
  |                 +++++++
help: instead, you are more likely to want to return an owned value
  |
5 - fn dangle() -> &String {
5 + fn dangle() -> String {
  |

For more information about this error, try `rustc --explain E0106`.
error: could not compile `ownership` (bin "ownership") due to 1 previous error

这条错误信息涉及一个我们还没有讲到的特性：生命周期。我们会在第 10 章详细讨论生命周期。不过，如果你忽略关于生命周期的部分，这条信息确实揭示了这段代码出问题的关键所在：

this function's return type contains a borrowed value, but there is no value
for it to be borrowed from

我们来仔细看看 dangle 代码的每个阶段到底发生了什么：

因为 s 是在 dangle 内部创建的，所以当 dangle 的代码执行完毕时，s 就会被释放。但我们却试图返回一个指向它的引用。这意味着这个引用将会指向一个无效的 String。这可不行！Rust 不会允许我们这样做。

这里的解决方法是直接返回 String：

fn main() {
    let string = no_dangle();
}

fn no_dangle() -> String {
    let s = String::from("hello");

    s
}

这样就没有任何问题了。所有权被移出去了，也没有任何东西被释放。

引用的规则

我们来回顾一下关于引用的讨论：

  • 在任意给定时刻，你要么只能有一个可变引用，要么只能有任意数量的不可变引用。
  • 引用必须总是有效的。
