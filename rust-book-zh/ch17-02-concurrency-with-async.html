用 async 实现并发

在本节中，我们将把 async 应用到第 16 章中用线程解决过的一些并发难题上。由于我们已经在那里讨论过很多关键思想，本节将重点关注线程和 future 之间的不同之处。

在很多情况下，使用 async 处理并发的 API 与使用线程的 API 非常相似。而在另一些情况下，它们最终却大不相同。即使线程和 async 的 API 看起来很相似，它们的行为也往往不同——而且它们的性能特征几乎总是不同的。

使用 spawn_task 创建新任务

我们在第 16 章“使用 spawn 创建新线程”部分处理的第一个操作，是在两个独立的线程上分别计数。我们用 async 来做同样的事情。trpl crate 提供了一个 spawn_task 函数，它看起来与 thread::spawn API 非常相似；还提供了一个 sleep 函数，它是 thread::sleep API 的异步版本。我们可以把它们结合起来实现计数的例子，如示例 17-6 所示。

作为起点，我们用 trpl::block_on 来搭建 main 函数，这样我们的顶层函数就可以是异步的了。

注意：从这里开始，本章的每个示例都会在 main 中包含这段完全相同的、使用 trpl::block_on 的包装代码，因此我们通常会像省略 main 一样省略它。记得在你自己的代码中加上它！

然后，我们在这个代码块中编写两个循环，每个循环都包含一个 trpl::sleep 调用，它会在发送下一条消息之前等待半秒（500 毫秒）。我们把一个循环放在 trpl::spawn_task 的主体中，另一个放在顶层的 for 循环中。我们还在 sleep 调用之后加上了 await。

这段代码的行为与基于线程的实现类似——包括这样一个事实：当你自己运行它时，可能会看到消息在终端中以不同的顺序出现：

hi number 1 from the first task!
hi number 2 from the first task!
hi number 2 from the second task!
hi number 3 from the first task!
hi number 3 from the second task!
hi number 4 from the first task!
hi number 4 from the second task!
hi number 5 from the first task!

一旦主 async 块中的 for 循环结束，这个版本就会停止，因为 spawn_task 生成的任务会在 main 函数结束时被关闭。如果你想让它一直运行到该任务完成，就需要使用 join 句柄来等待第一个任务完成。使用线程时，我们用 join 方法来“阻塞”，直到线程运行结束。在示例 17-7 中，我们可以用 await 来做同样的事情，因为任务句柄本身就是一个 future。它的 Output 类型是 Result，所以在等待它之后，我们还要对它调用 unwrap。

这个更新后的版本会一直运行，直到两个循环都结束：

hi number 1 from the second task!
hi number 1 from the first task!
hi number 2 from the first task!
hi number 2 from the second task!
hi number 3 from the first task!
hi number 3 from the second task!
hi number 4 from the first task!
hi number 4 from the second task!
hi number 5 from the first task!
hi number 6 from the first task!
hi number 7 from the first task!
hi number 8 from the first task!
hi number 9 from the first task!

到目前为止，看起来 async 和线程给出的结果差不多，只是语法不同：使用 await 而不是对 join 句柄调用 join，以及对 sleep 调用进行等待。

更大的区别在于，我们不需要为此再生成一个操作系统线程。事实上，我们在这里甚至不需要生成任务。因为 async 块会被编译成匿名的 future，所以我们可以把每个循环都放进一个 async 块中，然后使用 trpl::join 函数让运行时把它们都运行至完成。

在第 16 章“等待所有线程结束”部分中，我们展示了如何对调用 std::thread::spawn 时返回的 JoinHandle 类型使用 join 方法。trpl::join 函数与之类似，只不过它针对的是 future。当你给它两个 future 时，它会产生一个新的 future，一旦你传入的两个 future 都完成了，这个新 future 的输出就是一个包含每个 future 各自输出的元组。因此，在示例 17-8 中，我们使用 trpl::join 来等待 fut1 和 fut2 都结束。我们不等待 fut1 和 fut2，而是等待 trpl::join 产生的那个新 future。我们忽略了它的输出，因为那只是一个包含两个单元值的元组。

运行这段代码，我们会看到两个 future 都运行到了完成：

hi number 1 from the first task!
hi number 1 from the second task!
hi number 2 from the first task!
hi number 2 from the second task!
hi number 3 from the first task!
hi number 3 from the second task!
hi number 4 from the first task!
hi number 4 from the second task!
hi number 5 from the first task!
hi number 6 from the first task!
hi number 7 from the first task!
hi number 8 from the first task!
hi number 9 from the first task!

现在，你每次都会看到完全相同的顺序，这与我们在使用线程以及在示例 17-7 中使用 trpl::spawn_task 时看到的情况大不相同。这是因为 trpl::join 函数是公平的（fair），也就是说，它会以同样的频率检查每个 future，在它们之间交替进行，并且在另一个 future 已经就绪时，绝不会让某一个抢先跑在前面。对于线程，由操作系统决定检查哪个线程以及让它运行多长时间。而对于异步 Rust，则由运行时决定检查哪个任务。（在实践中，细节会变得很复杂，因为异步运行时在管理并发时，可能会在底层使用操作系统线程，所以保证公平性对运行时来说可能要费更多功夫——但这仍然是可以做到的！）运行时并不需要为任何给定的操作保证公平性，它们通常会提供不同的 API，让你选择是否需要公平性。

试试下面这些等待 future 的变体，看看它们会有什么效果：

  • 去掉其中一个或两个循环外面的 async 块。
  • 在定义每个 async 块之后立即等待它。
  • 只把第一个循环包裹在 async 块中，并在第二个循环的主体之后等待得到的 future。

作为额外的挑战，看看你能否在运行代码之前就推断出每种情况的输出！

使用消息传递在两个任务之间发送数据

在 future 之间共享数据的方式也会让你感到熟悉：我们会再次使用消息传递，只不过这次使用的是这些类型和函数的异步版本。为了说明基于线程的并发与基于 future 的并发之间的一些关键区别，我们会采取一条与第 16 章“使用消息传递在线程间传送数据”部分略有不同的路线。在示例 17-9 中，我们先只使用一个 async 块——不像之前生成单独的线程那样生成单独的任务。

这里我们使用了 trpl::channel，它是我们在第 16 章中配合线程使用的多生产者、单消费者通道 API 的异步版本。这个 API 的异步版本与基于线程的版本只有一点点不同：它的接收端 rx 是可变的而非不可变的，而且它的 recv 方法产生的是一个需要我们等待的 future，而不是直接产生值。现在我们就可以从发送端向接收端发送消息了。注意，我们不必生成单独的线程，甚至连任务都不需要；我们只需要等待 rx.recv 调用即可。

std::mpsc::channel 中同步的 Receiver::recv 方法会一直阻塞，直到收到一条消息。trpl::Receiver::recv 方法则不会，因为它是异步的。它不会阻塞，而是把控制权交还给运行时，直到收到一条消息或者通道的发送端关闭为止。相比之下，我们不需要等待 send 调用，因为它不会阻塞。它也不需要阻塞，因为我们向其中发送消息的通道是无界的。

注意：由于所有这些异步代码都运行在一个 trpl::block_on 调用中的 async 块里，所以其中的一切都可以避免阻塞。然而，它外面的代码会阻塞，等待 block_on 函数返回。这正是 trpl::block_on 函数的意义所在：它让你可以选择在哪里阻塞以等待一组异步代码，从而选择在哪里实现同步代码与异步代码之间的过渡。

关于这个例子，请注意两点。第一，消息会立刻到达。第二，尽管我们在这里使用了 future，但目前还没有任何并发。示例中的一切都是按顺序发生的，就和没有涉及任何 future 时一样。

我们先来解决第一点：发送一系列消息，并在它们之间休眠，如示例 17-10 所示。

除了发送消息之外，我们还需要接收它们。在这个例子中，由于我们知道会有多少条消息传入，所以可以手动调用四次 rx.recv().await 来接收。不过在现实世界中，我们通常要等待的消息数量是未知的，因此需要一直等待下去，直到确定再也没有消息为止。

在示例 16-10 中，我们使用 for 循环来处理从同步通道接收到的所有项。然而，Rust 目前还没有办法对一系列异步产生的项使用 for 循环，所以我们需要使用一种之前没见过的循环：while let 条件循环。它是我们在第 6 章“用 if let 和 let...else 简洁地控制流程”部分中见过的 if let 结构的循环版本。只要它所指定的模式能够持续匹配值，这个循环就会一直执行下去。

rx.recv 调用会产生一个 future，我们对它进行等待。运行时会暂停这个 future，直到它就绪为止。每当有一条消息到达，这个 future 就会解析为 Some(message)，消息到达多少次就解析多少次。当通道关闭时，无论是否有消息到达过，这个 future 都会解析为 None，表示再也没有值了，因此我们应该停止轮询——也就是停止等待。

while let 循环把这一切整合到了一起。如果调用 rx.recv().await 的结果是 Some(message)，我们就能拿到这条消息，并且可以像使用 if let 时那样在循环体中使用它。如果结果是 None，循环就会结束。每当循环完成一轮，它都会再次遇到 await 点，于是运行时会再次暂停它，直到另一条消息到达。

现在，代码已经能成功地发送和接收所有消息了。遗憾的是，还存在几个问题。其一，消息并不是以半秒的间隔到达的，而是在我们启动程序 2 秒（2,000 毫秒）之后一下子全部到达。其二，这个程序永远不会退出！它会一直等待新消息。你需要使用 ctrl-C 来关闭它。

单个 async 块中的代码是线性执行的

我们先来看看，为什么消息是在完整的延迟之后一下子全部到达，而不是每条之间都有延迟。在一个给定的 async 块中，await 关键字在代码中出现的顺序，也就是程序运行时它们被执行的顺序。

示例 17-10 中只有一个 async 块，所以其中的一切都是线性运行的。这里仍然没有并发。所有的 tx.send 调用都会先执行，它们与所有的 trpl::sleep 调用及其相关的 await 点交错进行。只有在这之后，while let 循环才能开始经过 recv 调用上的那些 await 点。

为了得到我们想要的行为，即在每条消息之间都有休眠延迟，我们需要把 tx 和 rx 的操作分别放进各自的 async 块中，如示例 17-11 所示。这样运行时就可以使用 trpl::join 分别执行它们，就像示例 17-8 中那样。同样，我们等待的是调用 trpl::join 的结果，而不是各个单独的 future。如果我们依次等待各个单独的 future，最终只会回到顺序执行的流程——这恰恰是我们不想要的。

使用示例 17-11 中更新后的代码，消息会以 500 毫秒的间隔被打印出来，而不是在 2 秒后一股脑儿地全部出现。

将所有权移动到 async 块中

不过，由于 while let 循环与 trpl::join 之间的交互方式，这个程序仍然永远不会退出：

  • 只有当传给 trpl::join 的两个 future 都完成时，它返回的 future 才会完成。
  • tx_fut future 会在发送完 vals 中的最后一条消息并结束休眠后完成。
  • rx_fut future 要等到 while let 循环结束才会完成。
  • while let 循环要等到等待 rx.recv 产生 None 时才会结束。
  • 只有当通道的另一端关闭后，等待 rx.recv 才会返回 None。
  • 只有当我们调用 rx.close，或者发送端 tx 被丢弃时，通道才会关闭。
  • 我们没有在任何地方调用 rx.close，而 tx 要等到传给 trpl::block_on 的最外层 async 块结束时才会被丢弃。
  • 这个代码块无法结束，因为它被阻塞在等待 trpl::join 完成上，这又让我们回到了这个列表的开头。

现在，我们发送消息的那个 async 块只是借用了 tx，因为发送消息并不需要所有权；但如果我们能把 tx 移动到那个 async 块中，它就会在该块结束时被丢弃。在第 13 章“捕获引用或移动所有权”部分中，你学习了如何在闭包中使用 move 关键字；而正如第 16 章“在线程中使用 move 闭包”部分所讨论的，在使用线程时，我们经常需要把数据移动到闭包中。同样的基本规律也适用于 async 块，因此 move 关键字用在 async 块上的效果，就和用在闭包上一样。

在示例 17-12 中，我们把用于发送消息的代码块从 async 改为 async move。

当我们运行这个版本的代码时，它会在最后一条消息发送并接收之后优雅地关闭。接下来，我们看看如果要从多个 future 发送数据，需要做哪些改动。

使用 join! 宏合并多个 future

这个异步通道也是一个多生产者通道，因此如果我们想从多个 future 发送消息，可以对 tx 调用 clone，如示例 17-13 所示。

首先，我们克隆 tx，在第一个 async 块外面创建了 tx1。我们像之前处理 tx 那样，把 tx1 移动到这个块中。然后，我们再把原来的 tx 移动到一个新的 async 块中，在那里以稍慢一些的延迟发送更多消息。我们碰巧把这个新的 async 块放在了用于接收消息的 async 块之后，不过把它放在前面也完全可以。关键在于 future 被等待的顺序，而不是它们被创建的顺序。

两个用于发送消息的 async 块都需要是 async move 块，这样 tx 和 tx1 才会在这些块结束时被丢弃。否则，我们又会回到最初那个无限循环中。

最后，我们从 trpl::join 换成了 trpl::join!，以处理多出来的那个 future：join! 宏可以等待任意数量的 future，前提是我们在编译时就知道 future 的数量。本章后面我们会讨论如何等待一个数量未知的 future 集合。

现在我们能看到来自两个发送端 future 的所有消息了；而且由于两个发送 future 在发送后使用的延迟略有不同，消息也会以那些不同的间隔被接收：

received 'hi'
received 'more'
received 'from'
received 'the'
received 'messages'
received 'future'
received 'for'
received 'you'
