Rust 程序设计语言

如何编写测试

测试（test）是一些 Rust 函数，用来验证非测试代码是否按照预期的方式运行。测试函数的函数体通常执行以下三个操作：

  • 设置所需的数据或状态。
  • 运行你想要测试的代码。
  • 断言结果符合你的预期。

我们来看看 Rust 专门为编写执行这些操作的测试而提供的功能，其中包括 test 属性、几个宏以及 should_panic 属性。

测试函数的结构

最简单地说，Rust 中的测试就是一个带有 test 属性注解的函数。属性是关于 Rust 代码片段的元数据，例如我们在第 5 章中与结构体一起使用的 derive 属性。要把一个函数变成测试函数，只需在 fn 之前的那一行加上 #[test]。当你使用 cargo test 命令运行测试时，Rust 会构建一个测试运行器二进制文件，它会运行这些带注解的函数，并报告每个测试函数是通过还是失败。

每当我们用 Cargo 新建一个库项目时，它都会自动为我们生成一个测试模块，其中包含一个测试函数。这个模块为你提供了编写测试的模板，这样你就不必在每次开始新项目时都去查找确切的结构和语法。你可以随意添加任意多个测试函数和测试模块！

在实际测试任何代码之前，我们会先通过试验这个模板测试来探索测试工作方式的某些方面。然后，我们会编写一些真实的测试，调用我们编写的代码并断言其行为是正确的。

既然你已经看到了不同场景下的测试结果是什么样子，现在我们来看看除 panic! 之外其他一些在测试中很有用的宏。

使用 assert! 检查结果

标准库提供的 assert! 宏在你想确保测试中的某个条件求值为 true 时非常有用。我们给 assert! 宏传入一个求值结果为布尔值的参数。如果值为 true，什么也不会发生，测试通过。如果值为 false，assert! 宏就会调用 panic! 让测试失败。使用 assert! 宏可以帮助我们检查代码是否按照我们的意图运行。

在第 5 章的示例 5-15 中，我们使用了一个 Rectangle 结构体和一个 can_hold 方法，示例 11-5 再次列出了它们。我们把这段代码放到 src/lib.rs 文件中，然后使用 assert! 宏为它编写一些测试。

can_hold 方法返回一个布尔值，这意味着它非常适合使用 assert! 宏。在示例 11-6 中，我们编写了一个测试来检验 can_hold 方法：创建一个宽为 8、高为 7 的 Rectangle 实例，并断言它能容纳另一个宽为 5、高为 1 的 Rectangle 实例。

注意 tests 模块中的 use super::*; 这一行。tests 模块是一个普通的模块，遵循我们在第 7 章“引用模块树中项的路径”部分介绍过的常规可见性规则。因为 tests 模块是一个内部模块，我们需要把外部模块中被测试的代码引入内部模块的作用域。这里我们使用了 glob 通配符，这样外部模块中定义的所有内容在这个 tests 模块中都可用。

使用 assert_eq! 和 assert_ne! 测试相等性

验证功能的一种常见方式，是测试被测代码的结果与你期望代码返回的值是否相等。你可以使用 assert! 宏并传给它一个使用 == 运算符的表达式来做到这一点。不过，这种测试实在太常见了，所以标准库提供了一对宏，即 assert_eq! 和 assert_ne!，来更方便地进行这种测试。这两个宏分别比较两个参数是否相等或不相等。如果断言失败，它们还会打印出这两个值，这样就更容易看出测试为什么失败；相比之下，assert! 宏只会表明它从 == 表达式得到了一个 false 值，而不会打印出导致 false 值的那些值。

我们的测试捕获到了这个 bug！tests::it_adds_two 测试失败了，信息告诉我们失败的断言是 left == right，以及 left 和 right 的值分别是什么。这条信息帮助我们开始调试：left 参数（存放的是调用 add_two(2) 的结果）是 5，而 right 参数是 4。可以想象，当我们有大量测试时，这会特别有帮助。

注意，在某些语言和测试框架中，相等性断言函数的参数被称为 expected 和 actual，并且指定参数的顺序很重要。然而在 Rust 中，它们被称为 left 和 right，我们指定期望值和代码产生的值的顺序并不重要。我们可以把这个测试中的断言写成 assert_eq!(4, result)，这会产生同样的失败信息，显示 assertion `left == right` failed。

如果我们给 assert_ne! 宏的两个值不相等，它就会通过；如果相等，它就会失败。当我们不确定某个值会是什么，但知道这个值肯定不应该是什么时，这个宏最为有用。例如，如果我们要测试一个保证会以某种方式改变其输入的函数，但输入被改变的方式取决于我们运行测试那天是星期几，那么最好的断言可能就是函数的输出不等于输入。

在底层，assert_eq! 和 assert_ne! 宏分别使用了 == 和 != 运算符。当断言失败时，这些宏会使用调试格式打印它们的参数，这意味着被比较的值必须实现 PartialEq 和 Debug trait。所有的基本类型和大部分标准库类型都实现了这些 trait。对于你自己定义的结构体和枚举，需要实现 PartialEq 才能断言这些类型的值是否相等；还需要实现 Debug，以便在断言失败时打印这些值。因为这两个 trait 都是可派生的 trait（正如第 5 章示例 5-12 中提到的），所以通常只需在结构体或枚举的定义上添加 #[derive(PartialEq, Debug)] 注解即可。关于这些以及其他可派生 trait 的更多细节，请参阅附录 C“可派生的 trait”。

添加自定义失败信息

你还可以向 assert!、assert_eq! 和 assert_ne! 宏传入可选参数，添加一条与失败信息一同打印的自定义信息。在必需参数之后指定的任何参数都会被传递给 format! 宏（在第 8 章“使用 + 或 format! 拼接字符串”部分讨论过），所以你可以传入一个包含 {} 占位符的格式字符串，以及要填入这些占位符的值。自定义信息对于记录断言的含义很有用；当测试失败时，你能更清楚地了解代码出了什么问题。

例如，假设我们有一个按名字向人打招呼的函数，我们想测试传入函数的名字会出现在输出中：

文件名：src/lib.rs

pub fn greeting(name: &str) -> String {
    format!("Hello {name}!")
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn greeting_contains_name() {
        let result = greeting("Carol");
        assert!(result.contains("Carol"));
    }
}

这个程序的需求还没有最终确定，而且我们很确定问候语开头的 Hello 文本将来会改变。我们决定不想在需求变化时还得更新测试，所以我们不检查与 greeting 函数返回值的完全相等，而只是断言输出中包含输入参数的文本。

使用 should_panic 检查 panic

除了检查返回值之外，检查代码是否按照我们的预期处理错误情况也很重要。例如，考虑我们在第 9 章示例 9-13 中创建的 Guess 类型。其他使用 Guess 的代码都依赖于这样一个保证：Guess 实例只会包含 1 到 100 之间的值。我们可以编写一个测试，确保尝试用超出该范围的值创建 Guess 实例时会 panic。

为此，我们给测试函数添加 should_panic 属性。如果函数内的代码 panic，测试就通过；如果函数内的代码没有 panic，测试就失败。

示例 11-8 展示了一个测试，它检查 Guess::new 的错误情况是否在我们预期的时候发生。

我们把 #[should_panic] 属性放在 #[test] 属性之后、它所作用的测试函数之前。我们来看看这个测试通过时的结果：

使用 should_panic 的测试可能不够精确。即使测试 panic 的原因与我们预期的不同，should_panic 测试也会通过。为了让 should_panic 测试更加精确，我们可以给 should_panic 属性添加一个可选的 expected 参数。测试框架会确保失败信息中包含所提供的文本。例如，考虑示例 11-9 中修改后的 Guess 代码，其中 new 函数会根据值是太小还是太大而以不同的信息 panic。

在测试中使用 Result<T, E>

到目前为止，我们所有的测试在失败时都会 panic。我们也可以编写使用 Result<T, E> 的测试！下面是示例 11-1 中的测试，它被改写为使用 Result<T, E>，并在失败时返回一个 Err 而不是 panic：

pub fn add(left: u64, right: u64) -> u64 {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_works() -> Result<(), String> {
        let result = add(2, 2);

        if result == 4 {
            Ok(())
        } else {
            Err(String::from("two plus two does not equal four"))
        }
    }
}

现在，it_works 函数的返回类型是 Result<(), String>。在函数体中，我们不再调用 assert_eq! 宏，而是在测试通过时返回 Ok(())，在测试失败时返回一个包含 String 的 Err。

让测试返回 Result<T, E>，就可以在测试的函数体中使用问号运算符，这样可以很方便地编写这样的测试：只要其中任何操作返回 Err 变体，测试就应该失败。

不能对使用 Result<T, E> 的测试使用 #[should_panic] 注解。要断言某个操作返回 Err 变体，不要对 Result<T, E> 值使用问号运算符，而应该使用 assert!(value.is_err())。
