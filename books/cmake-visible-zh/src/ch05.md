# 第 5 章 缓存：为什么“改了不生效”

在 `CMakeLists.txt` 里把 `option(USE_FAST "Use the fast code path" ON)` 的 `ON` 改成 `OFF`，重新配置，`USE_FAST` 还是 `ON`。在一个用户项目的文档里，`cache` 出现了 164 次；这个“改了不生效”正好是理解缓存（cache）的入口。

`option()` 只负责在缓存里没有这一项、也没有同名普通变量时写下默认值。下面两行只差一个词，效果却取决于构建目录里有没有上一次留下的缓存：

```cmake
option(USE_FAST "Use the fast code path" ON)   # 第一次配置
option(USE_FAST "Use the fast code path" OFF)  # 改完再配置，值仍是 ON
```

## 5.1 缓存是什么

第 1 章已经见过构建目录里的 `CMakeCache.txt`。缓存就是里面那一组跨配置保留的变量：配置开始时 cmake 先把它读回来，脚本里的 `option()`、`set(... CACHE ...)` 再按需增改。第一次配置没有这个文件，所以每一项都是新写进去的。

```cmake
{{#include code/ch05/5_1_cache_basics/CMakeLists.txt}}
```
{{#sidefx ch05/5_1_cache_basics}}

第 3 步到第 7 步，缓存栏里我们写的五项依次出现：`USE_FAST:BOOL=ON`、`APP_MODE:STRING=demo`、`APP_DATA_DIR:PATH=/work/src/data`、`ENABLE_LOG:BOOL=OFF`、`BUILD_TOKEN:INTERNAL=internal-42`。五项都带着类型，第 8、9 步的两个 `message()` 分别打印这五项；第 14 步文件执行完，配置结束时它们被写进 `CMakeCache.txt`。

切到生成页点开 `build/CMakeCache.txt`，五项都在里面。下面是其中三项，按文件里的顺序：

```text
//Where the data lives
APP_DATA_DIR:PATH=/work/src/data

//Which mode the app runs in
APP_MODE:STRING=demo

//Use the fast code path
USE_FAST:BOOL=ON
```

每一项上面一行 `//` 就是 `option()` 或 `set(... CACHE ...)` 后面的说明；`BUILD_TOKEN` 在文件后面的 INTERNAL 段。

| 类型 | 写法 | cmake-gui 里 |
|---|---|---|
| `BOOL` | `option()` 或 `set(... CACHE BOOL ...)` | 复选框 |
| `STRING` | `set(... CACHE STRING ...)` | 文本框 |
| `PATH` | `set(... CACHE PATH ...)` | 文件对话框，选目录 |
| `FILEPATH` | `set(... CACHE FILEPATH ...)` | 文件对话框，选文件 |
| `INTERNAL` | `set(... CACHE INTERNAL ...)` | 不显示 |

`CMakeCache.txt` 的格式就是 `名字:类型=值`，`//` 开头的行是该缓存项的说明。下一次配置开头，cmake 把这个文件读回内存；脚本再看到同名项时，沿用的就是旧值。

类型不只是给人看的：`BOOL` 让 GUI 画复选框，`PATH` 和 `FILEPATH` 让 GUI 打开文件对话框。`-D` 不带类型、脚本再用 `set(... CACHE PATH ...)` 或 `FILEPATH` 补类型时，命令行给的相对路径会按当前工作目录转成绝对路径；`-DP:PATH=data` 这样带着类型的写法不会转。`INTERNAL` 不是给用户改的，它隐含 `FORCE`，每次配置都会重写，适合放构建令牌这类工程内部的值。

## 5.2 缓存是粘的：默认值只在第一次生效

第一次配置用默认值 `ON` 的版本，后两次换成只改了默认值的 `v2`：

```cmake
{{#include code/ch05/5_2_option_sticky/CMakeLists.txt}}
```
`v2/CMakeLists.txt`：

```cmake
{{#include code/ch05/5_2_option_sticky/v2/CMakeLists.txt}}
```
{{#sidefx ch05/5_2_option_sticky}}

第一次运行的第 3 步先打印配置前缓存 `USE_FAST=[]`，第 4 步 `option()` 在空缓存里写下 `USE_FAST:BOOL=ON`，第 5 步打印 ON。第二次没有清空构建目录，第 3 步读到旧值 `[ON]`；第 4 步的 `option(... OFF)` 后面什么变化也没有，值仍是 ON，第 5 步打印 ON，构建页 0 条命令，程序还是 `fast path`。第三次从头配置，构建目录被删掉，第 3 步又打印 `[]`，第 4 步才重新写下 `USE_FAST:BOOL=OFF`，程序变成 `slow path`。

| 运行 | `CMakeLists.txt` 的默认值 | 配置前缓存 | 配置后 `USE_FAST` | 运行结果 |
|---|---|---|---|---|
| 1 | ON | 无 | ON | `fast path` |
| 2 | OFF | ON | ON | `fast path` |
| 3 | OFF | 无（从头配置） | OFF | `slow path` |

{{#fig ch05/cache_runs}}

`option()` 的帮助原文是：如果变量已经是普通变量或缓存变量，命令什么也不做。对普通变量，字面意思成立；对缓存变量，它指的是值不变：没有类型的项会补上 `BOOL` 和说明，带类型的项值不变，说明文字仍可能更新。

缓存项在第一次配置时写进 `CMakeCache.txt`，之后每次配置都从那里读回；`CMakeLists.txt` 里的默认值只在没有旧项时才有机会被用到。这是缓存这一侧的原因，5.4 还会看到同名普通变量让默认值同样不生效。

## 5.3 命令行 -D、FORCE 和 -U

用户改缓存的正规入口是 `-D`。下面第一次带两个 `-D` 配置，第二次不带，第三次换成加了 `FORCE` 的 `v2`：

```cmake
{{#include code/ch05/5_3_dash_d/CMakeLists.txt}}
```
`v2/CMakeLists.txt`：

```cmake
{{#include code/ch05/5_3_dash_d/v2/CMakeLists.txt}}
```
{{#sidefx ch05/5_3_dash_d}}

第一次带 `-DUSE_FAST=OFF -DLOG_LEVEL=debug`。第 4 步先打印配置前的缓存：`USE_FAST=[OFF]`、类型 `UNINITIALIZED`；第 5 步 `option()` 把它补成 `BOOL`，值仍是 OFF；第 6 步 `set(... CACHE STRING ...)` 把 `LOG_LEVEL` 从 `UNINITIALIZED` 补成 `STRING`，值仍是 debug。

不带类型的 `-D` 项在配置开始时是 `UNINITIALIZED`；`set(CACHE)` 不改值，只补类型和说明。

第二次不带 `-D`：第 4 步打印 `USE_FAST=[OFF]`、类型 `BOOL`；第 5、6 步都没有缓存变化，第 7 步仍打印 OFF 和 debug。`-D` 已经把值写进了缓存，和 `option()` 的默认值一样会留下来。

第三次换成 `v2`，命令行还写着 `-DUSE_FAST=OFF`，第 4 步打印的仍是 OFF（类型 `UNINITIALIZED`）；第 5 步 `set(USE_FAST ON CACHE BOOL ... FORCE)` 把缓存里的 OFF 改成 ON，第 7 步打印 ON，程序走 `fast path`。`FORCE` 每次配置都覆盖，用户的 `-D` 永远轮不到生效，所以它只该用于工程自己算出来、必须说了算的值。

- `-D` 也可以带类型，`-DUSE_FAST:BOOL=OFF` 会直接建一个 BOOL 项，省掉“先 UNINITIALIZED 再补类型”这一步。
- 想删掉某一项用 `-U`：`cmake -U USE_FAST -B build` 删除匹配的缓存项，下一次配置再走“第一次”的路径。

## 5.4 普通变量遮住缓存变量

缓存变量和普通变量可以同名。[4.2 节](ch04.md)讲过 `${X}` 先找普通变量、最后找缓存；这一节看两条写缓存的命令遇到同名变量时怎么走。下面的例子先建普通变量，再建缓存项，`option()` 也遇到一个已有的普通变量：

```cmake
{{#include code/ch05/5_4_shadow/CMakeLists.txt}}
```
{{#sidefx ch05/5_4_shadow}}

第 4 步 `set(BAR cached CACHE STRING ...)` 确实建了缓存项 `BAR:STRING=cached`，但第 5 步打印 `BAR=normal cached=cached`：`${BAR}` 先找到第 3 步的普通变量，`$CACHE{BAR}` 才绕过它直接读缓存。第 7 步 `option(FEATURE ...)` 遇到第 6 步的普通变量 OFF，什么也没做；第 8 步缓存里没有 FEATURE。第 12 步 `unset(LEVEL)` 删掉普通变量，第 13 步 `${LEVEL}` 就落到了缓存里的 quiet。

| 表达式 | 值 | 原因 |
|---|---|---|
| `${BAR}` | `normal` | 当前作用域的普通变量优先 |
| `$CACHE{BAR}` | `cached` | 直接读缓存项 |
| `${FEATURE}` | `OFF` | 普通变量遮住，`option()` 没有建缓存 |
| `$CACHE{FEATURE}` | 空 | 缓存里没有这一项 |
| `${LEVEL}`，`unset` 前 / 后 | `normal` / `quiet` | 普通绑定删掉后露出缓存 |

`CMP0077`（3.13 起）让 `option()` 在有普通变量时不动缓存，`CMP0126`（3.21 起）让 `set(CACHE)` 不删同名普通变量；`cmake_minimum_required(VERSION 3.25...4.2)` 把两条都设成 NEW，旧策略的行为见 [第 23 章](ch23.md)。`unset(X)` 只删普通绑定，所以缓存会露出来；`set(X "")` 不一样，它留下一个已定义的、值为空的普通变量，`${X}` 仍然是空，缓存继续被遮住。

写缓存时，两条命令的入口并不一样：`option()` 先看同名普通变量，`set(CACHE)` 不看。

## 5.5 用缓存还是用普通变量

把前面的例子放在一起，规则不复杂：用户需要改的开关用 `option()` 或 `CACHE`；工程内部的中间值用普通变量；“只想让子工程用不同默认值”时，在 `add_subdirectory()` 之前用普通变量覆盖。

```cmake
{{#include code/ch05/5_5_parent_override/CMakeLists.txt}}
```
`sub/CMakeLists.txt`：

```cmake
{{#include code/ch05/5_5_parent_override/sub/CMakeLists.txt}}
```
{{#sidefx ch05/5_5_parent_override}}

第 3 步在顶层 `set(SUB_BUILD_TESTS OFF)`；第 4 步进入 `sub/`，这个普通变量随目录作用域复制过去（[第 4 章](ch04.md)）。第 5 步子目录的 `option(SUB_BUILD_TESTS ... ON)` 什么也没做，第 6 步打印 OFF。第 8 步 `if` 不成立，子目录结束时没有 `sub_test` 这个目标；缓存栏里也没有 `SUB_BUILD_TESTS`。

这个办法依赖 `CMP0077` 的 NEW 行为。用户在命令行写 `-DSUB_BUILD_TESTS=ON` 也不管用：普通变量仍然优先，只是缓存里会多一个没人读的 `UNINITIALIZED` 项。要在自己的工程里临时改，只能删掉顶层那行 `set()`。

同样的技巧在 [第 15 章](ch15.md) 给依赖设置不同默认值时会再用到。

| 命令 | 作用 |
|---|---|
| `cmake --fresh -B build` | 删掉缓存重新配置（3.24 起） |
| `cmake -LH -B build` | 列出非高级缓存项和说明 |
| `ccmake build`、`cmake-gui build` | 在终端或图形界面里改同一份缓存 |

## 速查

| 写法 | 副作用发生在 | 注意 |
|---|---|---|
| `option(X "说明" ON)` | 第一次配置写 `X:BOOL` | 有同名普通变量时不动；无类型缓存项补类型和说明 |
| `set(X v CACHE STRING "说明")` | 缓存里没有 `X` 时写入 | 有旧项不改值；无类型才补类型和说明 |
| `set(X v CACHE ... FORCE)` | 每次配置都覆盖 | 用户的 `-D` 无效 |
| `cmake -DX=v -B build` | 配置开始时写缓存 | 不带类型是 `UNINITIALIZED`，会留下来 |
| `cmake -U X -B build` | 删除匹配的缓存项 | 下一次配置又按第一次处理 |
| `unset(X)` | 只删普通绑定 | 同名缓存值重新可见 |
| `$CACHE{X}` | 跳过普通变量 | 缓存没有该项时展开为空 |

## 思考题

1. 把 5.2 的第二次运行换成 `set(USE_FAST OFF CACHE BOOL "..." FORCE)`，再配置一次。`USE_FAST` 会变成 OFF 吗？构建页会有几条命令？
   <details><summary>提示</summary>FORCE 会覆盖缓存里的 ON，即使没有 fresh；编译定义从 1 变成 0，Ninja 要重编和重链。</details>
2. 5.4 里把 `unset(LEVEL)` 换成 `set(LEVEL "")`。第 13 步会打印什么？程序里的 `level` 又是什么？
   <details><summary>提示</summary>空字符串仍然是已定义的普通变量，普通变量优先于缓存。</details>
3. 在 5.5 的配置命令里加 `-DSUB_BUILD_TESTS=ON`。`sub_test` 会构建吗？缓存里会不会多一项？
   <details><summary>提示</summary>先看顶层 `set()` 和 `option()` 谁先发生；再看 `-D` 建的是什么类型的缓存项。</details>
4. 一个第三方子工程写了 `set(USE_FAST ON CACHE BOOL "..." FORCE)`。不改它的源码，你能用命令行让它走另一条路吗？
   <details><summary>提示</summary>FORCE 在脚本执行时覆盖命令行，`-D` 和 `-U` 都挡不住；只能改它的 CMakeLists，或让它别再 FORCE。</details>
