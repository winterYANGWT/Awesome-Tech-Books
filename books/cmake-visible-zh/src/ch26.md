## 26.2 安装和导出

安装规则单独放在 `cmake/ringInstall.cmake`，由顶层 `CMakeLists.txt` 最后的 `if(PROJECT_IS_TOP_LEVEL)` 决定要不要读。子目录使用者不做安装，也就不会在别人的构建里登记一串 `install()`。

```cmake

```

`ringConfig.cmake.in` 只需要三行：

```cmake
{{#include code/ch26/26_1_skeleton/cmake/ringConfig.cmake.in}}
```
{{#sidefx ch26/26_1_skeleton run=2 step=42 label="第 42 步只是登记安装规则"}}

第 42 步 `install(TARGETS …)` 和第 43 步 `install(EXPORT …)` 在配置页的“文件”栏里都没有新增文件；前者只登记复制规则，后者也只是登记，导出的 `ringTargets.cmake` 要到生成阶段才写进 `build/CMakeFiles/Export/…`。第 44、45 步的 `configure_package_config_file()` 和 `write_basic_package_version_file()` 才是配置阶段真的写文件：`build/ringConfig.cmake` 和 `build/ringConfigVersion.cmake` 当场出现。

切到运行页，`cmake --install` 把 `libring.a`、两个头文件和四份 `.cmake` 文件复制进 `prefix`。两个头文件是 `FILE_SET HEADERS` 一起复制过去的：`ring.hpp` 和生成出来的 `ring_export.h`；目录结构按文件集的 `BASE_DIRS` 保留，所以 `ring_export.h` 落在 `include/ring/` 下，而不是 `include/` 根上。

安装后的 `ringTargets.cmake` 做三件事：`add_library(ring::ring STATIC IMPORTED)` 创建导入目标，`set_target_properties` 写上 `INTERFACE_COMPILE_FEATURES "cxx_std_17"`，`target_sources(… FILE_SET HEADERS)` 把 `${_IMPORT_PREFIX}/include` 和两个头文件登记进去。`ringTargets-noconfig.cmake` 再补 `IMPORTED_LOCATION_NOCONFIG`；`ringConfig.cmake` 开头的 `@PACKAGE_INIT@` 展开后，用 `get_filename_component` 从自己的位置退回 `prefix`。只写 `install(TARGETS …)`，前缀里有文件却没有 `ringTargets.cmake`，下游的 `find_package` 不会创建 `ring::ring`；只写 `install(EXPORT …)`，导入目标指向的文件不在前缀里。

`base` 是 `hidden`，自己不能当 `--preset` 用；`binaryDir` 里的 `${presetName}` 让 `debug` 和 `asan` 各自落在 `build/debug`、`build/asan`，同名缓存项不会互相覆盖。`asan` 只写 `inherits: "debug"` 和 `GAUGE_SANITIZE=ON`，`CMAKE_BUILD_TYPE` 从 `debug` 继承。

{{#sidefx ch26/26_4_presets run=2 step=5 label="asan 的编译选项从哪里来"}}

第 3 步 `option()` 保留预设放进缓存的值 `ON`，把类型从 `UNINITIALIZED` 补成 `BOOL`，说明也补上；第 17 步的 message 打印 `GAUGE_SANITIZE=ON`。第 5、6 步的 `add_compile_options()`、`add_link_options()` 写在 `add_library()` 之前，第 7 步创建 `gauge` 时就把编译选项 `-fsanitize=address,undefined -fno-omit-frame-pointer` 和链接选项 `-fsanitize=address,undefined` 带进目标。运行页的 `ctest` 里这个测试仍然通过；构建页的六条命令中，编译命令带 `-fsanitize=address,undefined -fno-omit-frame-pointer`，链接命令只带 `-fsanitize=address,undefined`。

## 26.5 对照常见模板

三个常见模板解决的是同一类问题，但把复杂度放在不同位置。下面按各自的仓库文件比较，不按宣传页的说法。

| 模板 | 依赖怎么来 | 安装/导出 | 选项命名 | 测试入口 |
|---|---|---|---|---|
| cmake-init | `find_package`，或 vcpkg、conan 的预设 | `cmake/install-rules.cmake`：`install(TARGETS … INCLUDES DESTINATION)`、`install(EXPORT)`、版本文件 | `<name>_DEVELOPER_MODE`、`BUILD_SHARED_LIBS`、`BUILD_TESTING` | 只有开发者模式才 `add_subdirectory(test)`；test/ 单独配置时 `find_package(<name>)` |
| cmake_template | CPM 拉 fmt、spdlog、Catch2、CLI11、FTXUI | `cmake/PackageProject.cmake` 包装 `install(TARGETS … PUBLIC_HEADER)` 和 ycm | `myproject_ENABLE_*`、`myproject_WARNINGS_AS_ERRORS`、`myproject_BUILD_FUZZ_TESTS` | `include(CTest)` 后由 `BUILD_TESTING` 控制，Catch2 |
| ModernCppStarter | CPM 拉 PackageProject.cmake、fmt、doctest | 一次 `packageProject(NAME … INCLUDE_DESTINATION include/Greeter-${PROJECT_VERSION} DEPENDENCIES "fmt 10.2.1")` | 没有统一的工程前缀；测试工程用 `ENABLE_TEST_COVERAGE`、`TEST_INSTALLED_VERSION` | `test/` 自己是一个工程；`TEST_INSTALLED_VERSION` 决定 `find_package` 还是 `CPMAddPackage(SOURCE_DIR ..)` |
| 本书的 ring | 先 `find_package(GTest)`，`FetchContent` 只做兜底 | `cmake/ringInstall.cmake` + `ringConfig.cmake.in`，显式写 `FILE_SET`、`install(EXPORT)`、版本文件 | `RING_BUILD_TESTS`、`RING_BUILD_EXAMPLES`、`RING_WARNINGS`、`RING_SANITIZE` | `tests/` 只在顶层加入；`consumer/` 是独立消费工程 |

cmake-init 只在 `CMAKE_SKIP_INSTALL_RULES` 时跳过安装规则，安装命令本身不判断是不是顶层；ring 反过来，非顶层根本不读 `ringInstall.cmake`。两种选择都成立：前者让子目录使用也带安装能力，后者保证被 `add_subdirectory` 时不留下安装规则。

cmake_template 用宏和 `packageProject()` 把安装细节藏起来，选项带 `myproject_` 前缀；ModernCppStarter 把选择放进 `test/` 自己的选项。两者都默认用 CPM 下载依赖。ring 不引入 CPM 或 PackageProject，`install(TARGETS … FILE_SET … EXPORT)`、`install(EXPORT)`、`configure_package_config_file()` 各占一行，读者能对着录制看到每一步的副作用；代价是安装文件要自己维护。

依赖策略的差别也在这里：模板把“拉依赖”当成工程骨架的一部分，ring 把依赖当外部条件——GTest 先找系统，找不到才用 `FetchContent` 兜底。最低版本同样如此：`FILE_SET` 从 3.23 起，`FIND_PACKAGE_ARGS` 从 3.24 起，ring 取 3.25，两个功能都能用；cmake-init 从 3.14 起，cmake_template 要求 3.29，ModernCppStarter 写的是 3.14...3.22。

## 速查

| 写法 | 副作用发生在 | 注意 |
|---|---|---|
| `project(ring VERSION 0.3.0)` | 配置，第 2 步 | `PROJECT_IS_TOP_LEVEL` 同时定下 |
| `option(RING_BUILD_TESTS … ${PROJECT_IS_TOP_LEVEL})` | 配置，第一次配置时写缓存 | 子目录里默认 `OFF` |
| `add_library(ring::ring ALIAS ring)` | 配置，不新增可构建目标（目标栏列出 ALIAS） | 安装后同名目标由 `ringTargets.cmake` 创建 |
| `target_sources(… FILE_SET HEADERS)` | 配置，写 `INTERFACE_INCLUDE_DIRECTORIES` | 安装时保留 `BASE_DIRS` 下的目录结构 |
| `generate_export_header()` | 配置阶段写文件 | 导出头要进文件集才会被安装 |
| `install(TARGETS … FILE_SET … EXPORT)` | 配置登记，安装时复制 | 配置页不会多出文件 |
| `configure_package_config_file()` | 配置阶段写 `ringConfig.cmake` | 版本文件另用 `write_basic_package_version_file()` |
| `FetchContent_Declare(… FIND_PACKAGE_ARGS)` | 配置，`MakeAvailable` 时先找包 | 找不到才下载 |
| `cmake --workflow --preset dev` | 配置、构建、测试依次执行 | 工作流预设要文件版本 6（3.25） |

## 思考题

1. 把 26_1 的 `RING_BUILD_TESTS` 默认值从 `${PROJECT_IS_TOP_LEVEL}` 改成 `ON`，再跑“作为子目录”那一次。构建目录里会多出哪些目标？`ring_test` 的 `-I` 从哪里来？
   <details><summary>提示</summary>测试目标会在 `ring-build` 里创建，GTest 仍从系统找；子目录使用者通常不会在自己的 ctest 里跑它们。</details>
2. 去掉 26_1 里 `$<BUILD_INTERFACE:ring_warnings>` 外面的 `$<BUILD_INTERFACE:…>`，直接写 `ring_warnings`，再配置顶层工程。生成阶段会报什么？为什么？
   <details><summary>提示</summary>`install(EXPORT)` 发现 `ring` 的链接接口引用了不在导出集里的 `ring_warnings`，报 “requires target … that is not in any export set”。</details>
3. 把 26_4 的 `add_compile_options()` 移到 `add_library(gauge)` 之后，再跑 `asan` 预设。`gauge` 的编译命令里还有 `-fsanitize=address,undefined` 吗？`gauge_app` 呢？
   <details><summary>提示</summary>`add_compile_options()` 只初始化之后创建的目标；`gauge` 没有，`gauge_app` 和 `gauge_test` 有。</details>
4. 把 26_1 的 `FILE_SET HEADERS` 换成 `install(DIRECTORY include/ DESTINATION include)`，安装后 `prefix/include/ring/ring_export.h` 还在吗？消费工程会停在哪一步？
   <details><summary>提示</summary>生成头在构建目录，不在 `include/` 源目录里；安装树缺了它，消费工程编译 `ring.hpp` 时找不到 `ring/ring_export.h`。</details>

## 延伸阅读

- [cmake-init](https://github.com/friendlyanon/cmake-init)：生成器式的工程骨架，开发者模式和安装规则分得很开。
- [cmake_template](https://github.com/cpp-best-practices/cmake_template)：C++ Best Practices 的模板，选项前缀 `myproject_`，依赖走 CPM。
- [ModernCppStarter](https://github.com/TheLartians/ModernCppStarter)：CPM + PackageProject.cmake，测试目录是一个独立工程。
- [PackageProject.cmake](https://github.com/TheLartians/PackageProject.cmake)：`packageProject()` 的实现，安装和导出都在这个函数里。
- [`target_sources()` 的 File Sets 一节](https://cmake.org/cmake/help/v4.2/command/target_sources.html#file-sets)：`BASE_DIRS`、`FILES` 和安装时的相对路径规则。
- [`install(TARGETS)` 的 `FILE_SET`](https://cmake.org/cmake/help/v4.2/command/install.html#install-targets)：文件集安装到哪个目录、怎样和 `EXPORT` 一起用。
- [`FetchContent_Declare()` 的 `FIND_PACKAGE_ARGS`](https://cmake.org/cmake/help/v4.2/module/FetchContent.html#command:fetchcontent_declare)：先找包、找不到再下载的写法。
- [`CMakePackageConfigHelpers`](https://cmake.org/cmake/help/v4.2/module/CMakePackageConfigHelpers.html)：Config 文件和版本文件的生成命令。
