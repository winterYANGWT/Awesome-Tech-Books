## 6.1 cmake_parse_arguments

第 7 步进入 `mylib_add_tool` 时，变量栏里能看到 `ARGC=9`、`ARGV0=greet`、`ARGV1=SOURCES`。函数名后面的第一项是目标名，所以解析要从下标 1 开始，这就是 `PARSE_ARGV 1` 的作用。

第 8 步 `cmake_parse_arguments` 一次定义了一组变量：`arg_SOURCES=main.cpp;greet.cpp`、`arg_LIBS=core`、`arg_OUTPUT_NAME=hello`、`arg_INSTALL=TRUE`。两个“检查用”的变量这时是未定义的：`arg_UNPARSED_ARGUMENTS` 和 `arg_KEYWORDS_MISSING_VALUES`；第 11 步的 `message()` 把它们打印成空串。

第 13–18 步都在用解析结果：第 13 步建目标，第 14、15 步用 `arg_LIBS` 和 `arg_OUTPUT_NAME`，第 16 步用 `arg_INSTALL` 决定要不要执行第 17 步的 `install()`，第 18 步打印 `已创建 hello，链接 core`。函数的参数没有直接展开成 `add_executable(${ARGN})`，而是先变成有名字的变量，再按需取用。

切到第二次运行，调用改成 `mylib_add_tool(greet SOURCE main.cpp OUTPUT_NAME)`。

- 第 8 步的变量栏里，`arg_SOURCES` 没有出现（第 9 步把它打印成空），`arg_OUTPUT_NAME` 是空值；`arg_UNPARSED_ARGUMENTS=SOURCE;main.cpp`，`arg_KEYWORDS_MISSING_VALUES=OUTPUT_NAME`。
- 第 13 步函数用 `message(FATAL_ERROR)` 停下，配置以错误结束，而不是建出一个缺少源文件的 `greet`。
- 两个检查变量就是函数的防线：`arg_UNPARSED_ARGUMENTS` 抓住拼错或多出来的词，`arg_KEYWORDS_MISSING_VALUES` 抓住“关键字后面没有值”。

{{#fig ch06/parse_args}}

函数用 `DEFINED` 判断这两个变量是否存在，而不是把它们的值直接放进 `if()`：一个孤零零的 `OFF` 会被当成假。`PARSE_ARGV` 这种写法从 3.7 起才有，`KEYWORDS_MISSING_VALUES` 从 3.15 起才有；3.5 起命令已经是内置的，不用再 `include(CMakeParseArguments)`。

前缀 `arg` 是惯例：关键字大写，变量就成了 `arg_SOURCES` 这样，和缓存变量的大写名字不容易撞。前缀由写函数的人选，同一个作用域里两个宏都用 `arg` 时，后一个会覆盖前一个的变量；函数有独立作用域，问题小一些。

- 第 4–5 步：`APPEND` 把 `core` 又加了一次，`REMOVE_DUPLICATES` 去掉重复项，变量从 6 项回到 5 项。
- 第 6–7 步：`if(WIN32)` 在 Linux 上走 `else()`，`FILTER ... EXCLUDE REGEX "^gui_win$"` 把 `gui_win` 筛掉，留下 `gui_linux`。
- 第 8–12 步：`TRANSFORM ... PREPEND "src/"` 给每一项加前缀，`TRANSFORM ... REPLACE "$" ".cpp"` 在末尾补扩展名，结果从 `core` 这样的名字变成 `src/core.cpp` 这样的路径；`SORT` 排序，`FIND` 得到 `src/net.cpp` 的下标 3，`JOIN` 拼出一行。

这些结果没有停在 `message()` 里：第 14 步 `add_library(mylib STATIC ...)` 直接收到四个路径。构建页的第 1 到第 4 条命令分别编译 `src/core.cpp`、`src/gui_linux.cpp`、`src/log.cpp`、`src/net.cpp`，`gui_win.cpp` 一条命令也没有。运行页打印 `23`：`net_value()` 是 `core` 的 1 加 `log` 的 2，共 3，加上 `gui_linux` 的 20；`gui_win` 的 10 在 Linux 上没有参与编译，换成 Windows 分支会得到 13（10+3）。

`list()` 的修改发生在当前作用域，和 `set()` 一样；在函数里改完，要把列表送出去仍然得用 `PARENT_SCOPE` 或 `return(PROPAGATE)`（[4.2 节](ch04.md)）。另外，源文件列表最好手写或用明确的规则拼出来，不要用 `file(GLOB)` 代替这里的第一步（[第 25 章](ch25.md)）。

## 6.3 string() 和正则

版本号常常只写在 `version.txt` 里。工程要在 `project(VERSION)` 和编译宏里用同一个值，就得把它读进来、拆开、再拼成合法的标识符。

```cmake
{{#include code/ch06/6_3_string_regex/CMakeLists.txt}}
```
{{#sidefx ch06/6_3_string_regex}}

- 第 2–3 步：`file(READ)` 把整个文件读进 `VERSION_TEXT`，换行也在里面；`file(STRINGS ... REGEX "^v")` 只取 `v1.4.2` 这一行并去掉换行，得到 `VERSION_LINE`。
- 第 4–5 步：`string(REGEX MATCH "^v([0-9]+\\.[0-9]+\\.[0-9]+)$" ...)` 匹配成功，括号里的内容进了 `CMAKE_MATCH_1`，马上存进 `APP_VERSION`。
- 第 6–7 步：第二次 `REGEX MATCH` 找 `codename: Aurora`，`CMAKE_MATCH_1` 被新的匹配覆盖，所以立刻存下 `APP_CODENAME`。
- 第 8–10 步：`project(... VERSION 1.4.2 ...)` 之后出现 `PROJECT_VERSION`、`PROJECT_VERSION_MAJOR`；`TOUPPER` 得到 `AURORA`，`MAKE_C_IDENTIFIER` 把 `build-1.4.2` 变成 `build_1_4_2`。
- 第 12–15 步：`configure_file()` 写出 `build/config.h`；`BUILD_ID` 进目标的 `COMPILE_DEFINITIONS`，构建命令里有 `-DBUILD_ID=...`，运行页打印 `1.4.2 AURORA build_1_4_2`。

`CMAKE_MATCH_<n>` 只保存最近一次匹配的结果，中间再匹配一次就会被覆盖；需要保留时，像第 5、7 步那样马上 `set()` 到自己的变量里。`file(STRINGS)` 的 `REGEX` 是逐行筛选：每一行做正则匹配，匹配到的行留下，不要求整行匹配；`string(REGEX ...)` 的输入是一整段字符串，可以跨行。两者别混用。

第 4 到第 7 步分别取出文件名 `widget.cpp`、扩展名 `.cpp`、主干 `widget` 和父目录。第 8 步 `RELATIVE_PATH` 把父目录换算成相对源码根的 `src`，第 9 步 `IS_ABSOLUTE` 回答 `ON`。第 10 步 `APPEND` 把构建目录、`bin`、`tools` 拼成 `/work/build/bin/tools`；第 15 到第 18 步用旧写法把这四种都算了一遍，结果相同，区别只在写法：

| 要得到 | `cmake_path` | 旧写法（对应） | 示例里的值 |
|---|---|---|---|
| 文件名 | `GET ... FILENAME` | `get_filename_component(... NAME)` | `widget.cpp` |
| 扩展名 | `GET ... EXTENSION` | `get_filename_component(... EXT)` | `.cpp` |
| 主干 | `GET ... STEM` | `get_filename_component(... NAME_WE)` | `widget` |
| 父目录 | `GET ... PARENT_PATH` | `get_filename_component(... DIRECTORY)` | `/work/src/src` |

结果在第 22 步被用上：`RUNTIME_OUTPUT_DIRECTORY` 设成刚拼出的目录。构建页最后一条链接命令的 `-o` 是 `bin/tools/widget`，运行页要执行 `./build/bin/tools/widget`。如果只把路径打印出来，不设这个属性，产物仍然会落在构建目录的根下。

`cmake_path()` 只做语法处理，不检查文件是否存在，也不碰磁盘。它在 3.20 加入；`GET ... EXTENSION` 默认取最左边的点，`a.tar.gz` 会得到 `.tar.gz`，加 `LAST_ONLY` 才只取 `.gz`。老工程里的 `get_filename_component()` 没有被删掉，读旧代码时知道两者对应即可。

## 6.5 调用约定：返回值、作用域和名字前缀

`cmake/banner.h.in`：

```cmake

```
{{#sidefx ch06/6_5_helper_module}}

第 4 步 `include(MyHelpers)` 进入 `cmake/MyHelpers.cmake`，它只是定义两个函数，没有新建作用域。第 7 步调用 `myhelpers_configure_banner(BANNER_HEADER BANNER_INCLUDE_DIR)`，形参 `out_header` 收到的值是变量名 `BANNER_HEADER`，不是它的值。

第 8 步 `CMAKE_CURRENT_FUNCTION_LIST_DIR` 给出 `/work/src/cmake`，也就是函数定义所在的目录；第 15 步的 `CMAKE_CURRENT_LIST_DIR` 给出 `/work/src`，那是调用者正在处理的文件所在目录。`CMAKE_CURRENT_FUNCTION_LIST_DIR` 从 3.17 起才有；这个函数用它定位 `banner.h.in`，调用者从哪个子目录来都不影响。

- 第 11 步 `configure_file()` 写出 `build/generated/banner.h`。
- 第 12、13 步用 `set(... PARENT_SCOPE)` 把两个路径送到调用者；第 15 步离开函数时，变量栏的“外层作用域”里正好多出 `BANNER_HEADER` 和 `BANNER_INCLUDE_DIR`。
- 第 19 步 `return(PROPAGATE BANNER_ID)` 把局部变量交给调用者，外层作用域里出现 `BANNER_ID`；这需要 3.25 起和 CMP0140 的 NEW 行为，本工程的 `3.25...4.2` 已经满足。
- 第 24 步把 `BANNER_ID` 加进目标的 `COMPILE_DEFINITIONS`，构建命令里出现 `-DBANNER_ID=...`；运行页打印 `HelperModule 0.9 id_banner_0_9`。

{{#fig ch06/helper_scope}}

| 约定 | 这个示例里 | 不这样做会怎样 |
|---|---|---|
| 名字带项目前缀 | `myhelpers_configure_banner` | 通用名字容易和别的模块撞，`include()` 后更难查 |
| 结果变量名由参数传入 | `out_header`、`out_include` | 函数写死 `BANNER_HEADER`，换个结果名就得改函数 |
| 结果用 `PARENT_SCOPE` 或 `return(PROPAGATE)` | 第 12、13、19 步 | 函数返回后局部变量消失，调用者什么也拿不到 |
| 模块文件用 `CMAKE_CURRENT_FUNCTION_LIST_DIR` 定位 | 第 8 步的 `template_dir` | 用调用者的 `CMAKE_CURRENT_LIST_DIR`，从子目录调用时找不到模板 |

## 速查

| 写法 | 作用 | 注意 |
|---|---|---|
| `cmake_parse_arguments(PARSE_ARGV N prefix "OPT" "ONE" "MULTI")` | 解析函数参数 | `N` 是开始解析的 `ARGV` 下标；示例用 1 跳过目标名，函数名不在 `ARGV` 里；`PARSE_ARGV` 从 3.7 起 |
| `prefix_UNPARSED_ARGUMENTS` | 没有对应关键字的参数 | 全部认出时未定义，不要当空列表用 |
| `prefix_KEYWORDS_MISSING_VALUES` | 关键字后面缺值 | 3.15 起；和 UNPARSED 一起检查 |
| `list(APPEND ...)` / `REMOVE_DUPLICATES` | 增项、去重 | 修改当前作用域的变量 |
| `list(FILTER ... INCLUDE/EXCLUDE REGEX ...)` | 按正则筛选 | 3.6 起；默认子串匹配，整项匹配自己写 `^...$` |
| `list(TRANSFORM ... PREPEND/REPLACE ...)` | 批量改每一项 | 3.12 起；不改变项数 |
| `list(SORT)`、`list(JOIN)`、`list(FIND)` | 排序、拼字符串、找下标 | `FIND` 找不到返回 `-1` |
| `string(REGEX MATCH ...)` + `CMAKE_MATCH_1` | 提取一段文本 | 下一次匹配会覆盖 `CMAKE_MATCH_*` |
| `string(TOUPPER)` / `string(MAKE_C_IDENTIFIER)` | 生成宏名、标识符 | 标识符里的非字母数字会变成下划线 |
| `file(READ)` / `file(STRINGS ... REGEX ...)` | 读整个文件 / 按行过滤 | `STRINGS` 去掉行尾换行 |
| `cmake_path(GET/APPEND/RELATIVE_PATH/IS_ABSOLUTE)` | 拆路径、拼路径、算相对路径 | 3.20 起；只做语法处理 |
| `get_filename_component(... NAME/EXT/DIRECTORY)` | 旧的路径拆分 | 仍然可用，和新命令结果对应 |
| `CMAKE_CURRENT_FUNCTION_LIST_DIR` | 函数定义所在的目录 | 3.17 起；不是调用者目录 |
| `return(PROPAGATE var)` | 把局部变量交给调用者 | 3.25 起，需要 CMP0140 NEW |

## 思考题

1. 把 6.1 的调用改成 `mylib_add_tool(greet OUTPUT_NAME hello SOURCES main.cpp LIBS core INSTALL)`，关键字顺序换了。先预测 `arg_SOURCES`、`arg_INSTALL`、`arg_UNPARSED_ARGUMENTS` 的值，再录一次对照。
   <details><summary>提示</summary>`cmake_parse_arguments` 不要求关键字按声明顺序出现；`INSTALL` 是选项，位置不影响。</details>
2. 在 6.2 的 `list(FILTER ...)` 后面加一行 `list(REMOVE_ITEM SOURCES "gui_linux")`。构建还能通过吗？运行页会变成什么？
   <details><summary>提示</summary>`main.cpp` 调用 `gui_value()`，但两个 gui 源文件都不再参与编译。</details>
3. 把 6.3 的 `version.txt` 第一行改成 `v2.0.0-rc1`。`string(REGEX MATCH)` 还匹配吗？`APP_VERSION` 会是什么？`project(VERSION ...)` 会怎样？
   <details><summary>提示</summary>正则末尾的 `$` 要求整行只有三段数字；匹配失败时 `CMAKE_MATCH_1` 不会保留上一次的值。</details>
4. 在 6.5 里加一个子目录 `sub/CMakeLists.txt`，在子目录里调用 `myhelpers_configure_banner(...)`，并把函数里的 `CMAKE_CURRENT_FUNCTION_LIST_DIR` 换成 `CMAKE_CURRENT_LIST_DIR`。预测 `configure_file()` 会去找哪个文件。
   <details><summary>提示</summary>`CMAKE_CURRENT_LIST_DIR` 在函数里指向调用者正在处理的文件所在目录，也就是 `sub/`。</details>
