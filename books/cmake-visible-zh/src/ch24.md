# 第 24 章 调试 CMake

配置时报“找不到 `ZLIB_INCLUDE_DIR`”，或者链接行上多了一个没写过的 `-D`，第一反应是加 `message()`。但 `message()` 只能打印你想到要打印的东西。下面五个工具分别盯着配置、查找、单步、生成和构建，先看它们各自能看见哪一层。

## 24.1 message 的级别和 CHECK_START

`message()` 不只有 STATUS。它按级别过滤：默认只显示 STATUS 及更严重的消息，VERBOSE、DEBUG、TRACE 默认都藏着，`--log-level` 可以临时放开。

```cmake
{{#include code/ch24/24_1_message_levels/CMakeLists.txt}}
```
{{#sidefx ch24/24_1_message_levels}}

运行 1 是默认级别。第 7 步 `message(CHECK_START ...)` 打印 `-- 查找 fast 实现`，第 9 步 `CHECK_PASS` 把结果接在同一行；第 13 步 `CHECK_FAIL` 也一样。第 16 步的 `message(VERBOSE ...)` 没有输出，第 17、18 步的 DEBUG、TRACE 消息也没有打印。

运行 2 加了 `--log-level=VERBOSE --log-context`：第 16 步出现 `-- [demo] 编译定义：APP_IMPL_fast=1`。第 7、9 步的前缀是 `[demo.scan]`，第 14 步 `POP_BACK` 之后，第 15 步回到 `[demo]`；DEBUG 和 TRACE 仍然不出现。

`CHECK_START/PASS/FAIL` 始终是 STATUS 级别，默认就打印，它们只把一次检查的开始和结果配对。嵌套检查时，往 `CMAKE_MESSAGE_INDENT` 里加空格，结果行会跟着缩进。`CMAKE_MESSAGE_CONTEXT` 是给消息加位置标签的列表，还要 `--log-context` 或 `CMAKE_MESSAGE_CONTEXT_SHOW` 才显示。

| 级别 | 默认显示 | 典型用途 |
|---|---|---|
| `ERROR`、`WARNING`、`NOTICE` | 是 | 错误和要用户注意的事 |
| `STATUS` | 是 | 配置进度、`CHECK_*` 的结果 |
| `VERBOSE` | 否 | 项目用户偶尔想看的细节 |
| `DEBUG` | 否 | 项目开发者看的内部细节 |
| `TRACE` | 否 | 极细的逐条记录，通常临时加 |

`NOTICE`、`VERBOSE`、`DEBUG`、`TRACE` 从 3.15 起；`--log-level` 从 3.16 起；`CHECK_*`、`--log-context`、`CMAKE_MESSAGE_CONTEXT` 从 3.17 起。`CMAKE_MESSAGE_LOG_LEVEL` 可以把级别存进缓存，命令行参数优先。

## 24.2 --trace 和 --trace-expand

`message()` 要你先猜到该打印什么；trace 不用，它把每一条执行的命令按顺序打出来，`--trace-source` 再把它限制在一个文件里。

```cmake
{{#include code/ch24/24_2_trace/CMakeLists.txt}}
```
{{#sidefx ch24/24_2_trace}}

运行 2 在构建后用 `--trace --trace-source=CMakeLists.txt` 再配置一次。运行页里每条命令一行，格式是 `文件(行): 命令(参数)`；`CMakeLists.txt` 第 17、18 行的参数还是 `${EXTRA_FLAGS}`、`${APP_DEFS}` 原文。

运行 3 第一条命令换成 `--trace-expand`：第 17 行变成 `target_compile_options(app PRIVATE  )`，两个空格之间什么也没有；第 18 行变成 `FEATURE_FAST=1;FEATURE_LOG=1`。第二条命令加 `--trace-format=json-v1`，同一份记录变成一行一个 JSON，`args` 是展开后的数组。要把 trace 当数据分析，就把这份 JSON 写到文件，再让脚本按 `cmd` 过滤；人眼看几十行还行，几千行就难了。

| CMakeLists 第 17、18 行 | `--trace` 打印 | `--trace-expand` 打印 |
|---|---|---|
| `target_compile_options(app PRIVATE ${EXTRA_FLAGS})` | `… PRIVATE ${EXTRA_FLAGS} )` | `… PRIVATE  )` |
| `target_compile_definitions(app PRIVATE ${APP_DEFS})` | `… PRIVATE ${APP_DEFS} )` | `… PRIVATE FEATURE_FAST=1;FEATURE_LOG=1 )` |

所以 `--trace` 回答“这一行执行了没有、从哪个文件哪一行来”，`--trace-expand` 回答“它实际收到了什么”。`--trace-source` 只保留指定文件的命令；第一次全新配置时，编译器检测的 `try_compile` 也有一份 `CMakeLists.txt`，会被一并收进来，在已有构建目录上再跑就没有这些临时文件的行。

`--trace-source` 从 3.7 起，`--trace-format` 从 3.17 起。`--trace-redirect=文件` 把 trace 写进文件而不是终端；查看器的录制器自己就是这样收 trace 的。

## 24.3 --debug-find 和 --debug-output

`find_package()` 失败时，真正有用的信息是“它去过哪些目录”。`--debug-find` 把这趟查找的每一步打出来，`--debug-find-pkg` 和 `--debug-find-var` 再把范围缩到一个包或一个变量。

```cmake

```
{{#sidefx ch24/24_3_debug_find}}

运行 1 的参数是 `--debug-find-var=ZLIB_INCLUDE_DIR`。第 5 步 `find_package(ZLIB)` 的输出以 `CMake Debug Log at …/FindZLIB.cmake:165 (find_path)` 开头，先列这次 `find_path` 的设置（`VAR`、`NAMES` 等），再列试过的每个目录，最后是 `The item was found at`，空一行后是 `/usr/include/`。

运行 2 打开 `BUILD_TESTS`，参数换成 `--debug-find-pkg=GTest`。第 10 步的输出只跟 GTest 有关：`find_package considered the following locations for GTest's Config module`，最后找到 `/usr/lib/x86_64-linux-gnu/cmake/GTest/GTestConfig.cmake`。ZLIB 那一步没有调试输出：过滤条件只认 GTest；ZLIB 仍会执行查找，只是它的 debug 日志被过滤掉了。

`--debug-find` 从 3.17 起，不带过滤，连 `project()` 里检测编译器的 `find_program` 也会打印；两个过滤参数从 3.23 起。示例在 `project()` 之后把 `CMAKE_FIND_USE_SYSTEM_ENVIRONMENT_PATH` 设为 OFF，只为让输出里不出现 PATH 上的每个目录；你调试自己的工程时不必关。

| 写法 | 只看 | 从哪版 |
|---|---|---|
| `--debug-find` | 所有 `find_*` 调用 | 3.17 |
| `--debug-find-pkg=GTest` | `find_package(GTest)` 及其内部 | 3.23 |
| `--debug-find-var=ZLIB_INCLUDE_DIR` | 结果变量是它的 `find_*` | 3.23 |

只想在工程里临时看一段查找，可以在 `CMakeLists.txt` 里 `set(CMAKE_FIND_DEBUG_MODE TRUE)`，看完再设回 FALSE；它和 `--debug-find` 是一回事，只是范围可以缩到几条命令。

`--debug-output` 是另一回事：它打印 CMake 自己的调试信息，例如 `message(SEND_ERROR)` 的调用栈。查“这个参数从哪来”时，它通常不如 trace 和 file API 直接。

## 24.4 CMake 的调试器

`--debugger` 从 3.27 起。它不打印日志：cmake 在 `--debugger-pipe` 指定的 Unix socket（Windows 上是命名管道）上按 DAP（Debug Adapter Protocol）说话，客户端可以下断点、单步、读变量。

客户端先发 `initialize`，再发 `setBreakpoints` 和 `configurationDone`；cmake 每走到断点回一个 `stopped`，客户端问栈和变量，然后发下一步动作。

| DAP 请求 | 作用 |
|---|---|
| `initialize` | 握手；回包里带 `cmakeVersion` |
| `setBreakpoints` | 给一个文件的若干行下断点 |
| `configurationDone` | 告诉 cmake 可以开始执行 |
| `stackTrace` | 当前的调用栈：文件、行、函数 |
| `scopes`、`variables` | 当前帧的 `Locals`、`CacheVariables`、`Targets` |
| `next`、`stepIn`、`stepOut` | 单步、进入函数、跳出 |
| `disconnect` | 结束调试，让 cmake 继续跑完 |

VS Code 的 CMake Tools 也用这套接口，可以在 `CMakeLists.txt` 里下断点、单步、看变量，相关说明见延伸阅读。

{{#fig ch24/sidefx_recorder}}

本书查看器的配置页就是这样一个客户端：它在顶层文件里下断点，再单步进入函数和被 include 的文件；每次停下把调用栈、各层变量、缓存和目标存下来，相邻两次停下的差就是上一条命令的副作用。{{#figref ch24/sidefx_recorder}} 画的就是这个循环，附录 C 写了完整实现和它看不到的东西。

调试器停在命令之前，`else()`、`endif()` 这类结束标记不停，`project()`、`enable_language()`、`try_compile()` 的内部也不逐行进。`--debugger-dap-log=文件` 可以把协议往来记下来，客户端行为不对时先看它。

调试器给的是任意时刻的状态，给不了“最终参数是谁加的”。这件事由 file API 补上：配置结束后，codemodel v2 给每个目标的编译参数、包含目录和链接库，并带一条回溯到哪条命令。24.5 接着看它和 graphviz。

## 24.5 file API 和 --graphviz

`--graphviz` 把目标之间的链接关系写成 Graphviz 的 `.dot` 文本；`file API` 则把每个目标的最终参数和出处写成 JSON，给工具读。

{{#sidefx ch24/24_5_graphviz}}

运行 2 在构建后执行 `cmake --graphviz=deps.dot -S src -B build`。运行页输出 `Generate graphviz: /work/deps.dot`，文件列表新增 `deps.dot`、`deps.dot.app`、`deps.dot.core`，以及 `deps.dot.core.dependers`、`deps.dot.util.dependers` 等几个文件。

`deps.dot` 里节点是目标，边是链接关系：`app -> core` 和 `core -> ZLIB::ZLIB` 是 dotted，`core -> util` 没有 style（默认实线）；前两条是 PRIVATE，后一条是 PUBLIC。要画成图片需要另装 Graphviz，`dot -Tpng -o deps.png deps.dot`。依赖图太大时，在 `CMakeGraphVizOptions.cmake` 里把 `GRAPHVIZ_GENERATE_PER_TARGET` 和 `GRAPHVIZ_GENERATE_DEPENDERS` 都设为 FALSE，才只留总图；只把 `GRAPHVIZ_GENERATE_PER_TARGET` 设为 FALSE 还会留下 `*.dependers`。

file API 走另一个方向：客户端在构建目录里放一个空文件，告诉 CMake 要哪类对象。

```sh
mkdir -p build/.cmake/api/v1/query/client-mytool
touch build/.cmake/api/v1/query/client-mytool/codemodel-v2
cmake -S src -B build
```

文件名里的 `codemodel-v2` 是对象名和主版本号；下次配置时 CMake 在 `build/.cmake/api/v1/reply/` 下写 `index-*.json`，再按索引写每个目标的 JSON。`codemodel` 的编译组和链接项都带 `backtrace`，指明是哪条命令加的；查看器生成页的“来自哪一行”就来自这里。查看器请求的是 `codemodel` v2、`cache` v2 和 `cmakeFiles` v1。

graphviz 看目标之间的依赖，file API 看每个目标最后拿到的参数和它们出处；一个给人看布局，一个给工具读细节。

构建阶段还有 `cmake --build build --verbose`，把每条真实的编译、链接命令打出来。它已经不经过 CMake 脚本，本章只指一下。

## 速查

| 写法 | 作用 | 注意 |
|---|---|---|
| `message(VERBOSE/DEBUG/TRACE ...)` | 分级打印 | 默认显示到 STATUS；3.15 起 |
| `message(CHECK_START/PASS/FAIL ...)` | 把检查的开始和结果配对 | 始终是 STATUS；3.17 起 |
| `--log-level=VERBOSE` | 临时放开某一级 | 3.16 起；`CMAKE_MESSAGE_LOG_LEVEL` 可持久化 |
| `--log-context` | 显示 `CMAKE_MESSAGE_CONTEXT` | 3.17 起 |
| `--trace` | 打印每条命令和位置 | 参数不展开 |
| `--trace-expand` | 同上，变量已展开 | 3.4 起；空变量会留下空位 |
| `--trace-source=文件` | 只留这个文件 | 3.7 起；同名临时文件也会被收进来 |
| `--trace-format=json-v1` | 一行一个 JSON | 3.17 起；`--trace-redirect` 写文件 |
| `--debug-find` | 打印所有 `find_*` | 3.17 起，输出很长 |
| `--debug-find-pkg=GTest` | 只调试这个包的查找 | 3.23 起 |
| `--debug-find-var=VAR` | 只调试结果变量是 `VAR` 的查找 | 3.23 起 |
| `--debugger --debugger-pipe=…` | DAP 调试器 | 3.27 起；配合客户端使用 |
| `--graphviz=deps.dot` | 生成目标依赖图 | 3.10 起区分 PUBLIC/INTERFACE/PRIVATE 线型 |
| file API | 生成后读最终参数和回溯 | 查询文件放在构建目录的 `.cmake/api/v1/query/` |

## 思考题

1. 给 24_1 再加一次运行，参数是 `--log-level=DEBUG --log-context`。第 17 步会出现什么？第 18 步呢？
   <details><summary>提示</summary>DEBUG 会出现，前缀是 `[demo]`；TRACE 仍被挡住。第 14 步已经 `POP_BACK`，所以不再是 `[demo.scan]`。</details>
2. 24_2 的配置页第 10 步里，`target_compile_options` 的参数已经是空的；`--trace` 输出第 17 行却还写着 `${EXTRA_FLAGS}`。这两个输出分别是谁给的？
   <details><summary>提示</summary>查看器每一步的参数来自它自己跑的 `--trace-expand`；`--trace` 只照抄源文件，所以还留着变量名。</details>
3. 24_3 的 GTest 用 `--debug-find-var=GTest_DIR` 为什么看不到它的配置搜索？
   <details><summary>提示</summary>config 模式的 `find_package` 不调用一个结果变量叫 `GTest_DIR` 的 `find_*`；它直接找 `GTestConfig.cmake`。这种包搜索要用 `--debug-find-pkg`。</details>
4. 把 24_5 的 `target_link_libraries(core PUBLIC util)` 改成 PRIVATE，`deps.dot` 里 `core -> util` 那条边会变成什么样式？
   <details><summary>提示</summary>从默认实线变成 dotted。PRIVATE 只改边型和用法要求的传递；静态库链接时 `util` 仍会通过 `$<LINK_ONLY:…>` 出现在 app 的链接行上。</details>
