# 第 13 章 构建时做事：add_custom_command 和 add_custom_target

配置时生成的文件，只在下次重新配置时更新（[第 12 章](ch12.md)）。要让“输入变了就重新生成”，得把生成挪到构建阶段：写成 `add_custom_command(OUTPUT …)`，让 Ninja 去盯着输入和输出。

配置页第 3 步 `add_custom_command()` 没有新增文件：它没有生成 `table.cpp`，只是把一条构建规则登记进工程。第 4 步 `add_executable()` 把 `main.cpp` 和 `/work/build/table.cpp` 一起列为 `app` 的源文件；生成页的 `app` 卡片里，`table.cpp` 后面标着“生成的”。

`OUTPUT` 指向构建目录里的 `table.cpp`，不是源码目录；它和手写的源文件一样参与编译，但不会出现在 `git status` 里。`VERBATIM` 让参数原样传给命令，路径里有空格也不会被拆开。

构建页一共 4 条命令：第 1 条带着 `-DINPUT=… -DOUTPUT=…` 调用 `cmake -P gen_table.cmake` 生成 `table.cpp`，第 2、3 条分别编译 `main.cpp` 和 `table.cpp`，第 4 条链接。运行页打印 `table: 3 rows, sum 15`。

{{#fig ch13/custom_command_graph}}

第二次运行只替换了 `table.csv`，没有配置；构建页只剩 3 条命令：生成、编译 `table.cpp`、链接，`main.cpp` 的编译不见了。{{#figref ch13/custom_command_graph}} 画的就是这条链：Ninja 看到 csv 比 table.cpp 新，沿着 `OUTPUT` 和 `DEPENDS` 找到它，只重跑链上的规则。`DEPENDS` 里还写了 `gen_table.cmake`，改生成脚本同样会触发重跑。

## 13.2 DEPENDS、BYPRODUCTS 和 WORKING_DIRECTORY

```cmake
{{#include code/ch13/13_2_missing_depends/CMakeLists.txt}}
```
{{#sidefx ch13/13_2_missing_depends}}

配置页第 3 步同样只是登记规则；这个例子的 `add_custom_command()` 少了 `DEPENDS`，却多了 `BYPRODUCTS` 和 `WORKING_DIRECTORY`。构建页第 1 条命令以 `cd /work/src` 开头，因为 `WORKING_DIRECTORY` 指向源码目录，`INPUT=table.csv` 和 `-P gen_table.cmake` 才能写相对路径；不写时默认是构建目录。`BYPRODUCTS` 声明了 `table.rows.txt`，构建页的“构建产生的文件”里能看到它；`OUTPUT` 写的是绝对路径，主产物仍在 `build/`。

第二次运行替换 csv、不配置；构建页 0 条命令，只有查看器的一句“没有要执行的命令：所有产物都是最新的。”，运行页仍是 `sum 15`。csv 变了，但规则里没有任何东西指向它，Ninja 认为 `table.cpp` 还是最新的。

第三次运行换成补了 `DEPENDS table.csv gen_table.cmake` 的 CMakeLists，再改 csv；构建页先出现 `[0/1] cmake --regenerate-during-build`，接着生成、编译 `table.cpp`、链接，运行页变成 `sum 60`。

- 漏写 `DEPENDS`：改输入不重跑；删掉 `table.cpp` 会重跑，因为输出缺失。
- `BYPRODUCTS` 是给构建工具看的“副产物清单”，别的规则可以依赖它；它不是 `OUTPUT` 的替代品。

`DEPENDS` 可以写文件，也可以写目标：写可执行目标或库目标时，既有目标级依赖，也会在目标重新编译后触发重跑；写 `add_custom_target()` 创建的目标时只有目标级依赖，要按文件依赖就依赖它产生的文件。相对路径先按当前源码目录找，找不到再按构建目录解释。这也是 `add_custom_command()` 和 `add_custom_target()` 的分工：一个管文件，一个管动作。

```cmake
{{#include code/ch13/13_3_post_build/CMakeLists.txt}}
```
{{#sidefx ch13/13_3_post_build}}

第 3 步 `add_executable()` 先建 `app`；第 4 步的 `add_custom_command(TARGET app POST_BUILD …)` 必须写在它后面。这一步没有新目标，也没有新增文件，只把命令挂到 `app` 上。

构建页只有 2 条命令；第 2 条把链接和 `cmake -E make_directory`、`cmake -E copy` 串在同一个 `&&` 链里——TARGET 形式把命令挂在这个目标的构建规则上，不是单独一条规则。运行页执行 `build/dist/app-copy`，打印 `app is running`。`make_directory` 和 `copy` 都用 `cmake -E`，不靠 shell 的 `cp`，换平台也能跑。

第二次不配置、不改文件，构建页 0 条命令，复制也没有再执行：目标不需要重建，POST_BUILD 就不跑。`PRE_LINK` 在编译后链接前跑，`PRE_BUILD` 在非 Visual Studio 生成器下等同于 `PRE_LINK`。

- TARGET 形式没有 `OUTPUT`；别的规则要依赖 POST_BUILD 写出的文件，或希望文件被删掉后重建，才用 `BYPRODUCTS` 声明，Ninja 才知道它是这条规则的产物。本例只是复制一份，不声明也能构建。

{{#figref ch13/custom_target_graph}} 把三个入口画在一起。第一次构建 4 条命令：先 `touch stamp.txt`，再编译、链接 `app`，最后打印 `audit`。`audit` 带 `ALL`，所以进了默认构建，但 `ALL` 不保证它排在最前面；`stamp` 没写 `ALL`，是 `add_dependencies(app stamp)` 把它拉进来的。

{{#fig ch13/custom_target_graph}}

第二次不配置、不改文件，构建页仍有 2 条命令：`stamp.txt` 被重新 touch，`audit` 又打印一次，编译和链接没有出现——custom target 没有输出文件，永远算过期。`ALL` 只决定它进不进默认构建，不会让它变成有输出的目标。

第三次指定 `--target format`：只有 1 条 `clang-format --dry-run --Werror main.cpp`，因为 `main.cpp` 故意没格式化，它返回 1，构建失败。`format` 不在 `ALL` 里，默认构建不会碰它。

需要产出文件、让别的目标按文件依赖它的，用 `add_custom_command(OUTPUT …)`；`format`、`audit` 这类没有输出文件的动作正适合 `add_custom_target()`。

## 13.5 execute_process 还是 add_custom_command——一张表

| | `execute_process()` | `add_custom_command(OUTPUT …)` |
|---|---|---|
| 执行阶段 | 配置 | 构建 |
| 何时重跑 | 每次配置 | 输出缺失，或 `DEPENDS` 比输出新 |
| 输出在哪 | 命令写到哪里就是哪里，CMake 不跟踪 | `OUTPUT`、`BYPRODUCTS`，Ninja 记着 |
| 依赖构建出来的程序 | 不行，配置时程序还没构建 | 可以，`$<TARGET_FILE:gen>` 加 `DEPENDS gen` |

`execute_process()` 在配置阶段跑，不能拿它调用还没构建的 `gen`；`add_custom_command()` 的命令在构建阶段跑，可以依赖刚构建出来的目标。

`execute_process()` 也不是不能用：配置时就要拿到结果（编译器版本、git 哈希）时它正合适，只是别用它生成参与编译的源文件。

配置页第 3 步建 `gen`，第 4 步的规则用 `$<TARGET_FILE:gen>` 作命令；这个表达式在生成阶段展开成 `/work/build/gen`。第 5 步 `add_executable()` 把 `table.cpp` 列进 `app`。

构建页 6 条命令，顺序是：编译 `gen.cpp`、链接 `gen`、运行 `gen` 写 `table.cpp`、编译 `main.cpp`、编译 `table.cpp`、链接 `app`。`$<TARGET_FILE:gen>` 给的是目标级依赖，保证 `gen` 先构建；`DEPENDS gen` 再给文件级依赖，`gen` 重新编译后 `table.cpp` 会重新生成。`COMMAND` 直接写目标名 `gen` 也会被换成构建出的路径；要把路径放进参数，只能写 `$<TARGET_FILE:gen>`。

## 速查

| 写法 | 执行时机 | 什么时候重跑 | 注意 |
|---|---|---|---|
| `add_custom_command(OUTPUT …)` | 构建 | 输出缺失，或 `DEPENDS` 比输出新 | 输出要列进某个目标的源文件，或由别的规则 `DEPENDS` 它；漏 `DEPENDS` 就不重跑 |
| `add_custom_command(TARGET … POST_BUILD …)` | 该目标链接后 | 该目标被重建时 | 必须写在目标定义之后；目标不重建就不执行 |
| `add_custom_target(…)` | 每次构建这个目标 | 永远 | 没有输出文件；默认不构建，`ALL` 进默认，或由 `add_dependencies` 拉进来 |
| `execute_process()` | 配置 | 每次配置 | 输入变了要重新配置，和构建阶段无关 |

## 思考题

1. 在 `13_1_custom_output` 里把 `DEPENDS` 中的 `gen_table.cmake` 删掉，只修改生成脚本的输出格式，再构建。生成命令会重跑吗？如果删掉 `build/table.cpp` 呢？
   <details><summary>提示</summary>Ninja 只认规则里写出的依赖；输出缺失是另一条触发条件。两种情况下分别看构建页第 1 条命令有没有出现。</details>
2. `13_2_missing_depends` 的第二次运行没有重跑。不改 CMakeLists，执行什么命令能让 `table.cpp` 按新 csv 重新生成？`touch table.csv` 为什么没用？
   <details><summary>提示</summary>删掉输出会让规则重跑；`touch` 只改输入的时间戳，而输入不在依赖里。</details>
3. 给 `13_4_custom_target` 的 `format` 加上 `ALL`，然后执行默认构建。预测构建页有哪几条命令、退出码是多少；如果 `main.cpp` 一直不格式化，这个工程还能不能构建成功？
   <details><summary>提示</summary>`ALL` 只是把它加进默认构建；`clang-format --dry-run --Werror` 在格式不对时返回非零，Ninja 会停下。</details>
4. 只修改 `13_5_build_tool` 的 `gen.cpp`，再构建。哪些命令会重跑？`table.cpp` 会不会重新生成？如果把 `DEPENDS gen` 删掉呢？
   <details><summary>提示</summary>`$<TARGET_FILE:gen>` 只给目标级依赖，`DEPENDS gen` 才给文件级依赖；对比两次构建页的命令条数。</details>
