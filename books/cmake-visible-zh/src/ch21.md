# 第 21 章 质量工具接进构建

[第 20 章](ch20.md) 的 preset 能把 `PROJ_SANITIZE=address;undefined` 写进缓存，但 preset 只负责把值送到 CMake 手里。值最后变成编译命令、链接命令上的什么参数，还是包在命令外面，是本章这几个变量和属性决定的。这几个位置各管一件事，接错地方时现象很不一样。

一条编译命令上可以挂好几个位置，先看全貌。

## 21.1 sanitizer 选项

sanitizer 有两半：编译器插检查代码，运行时库在程序启动时接管。两半靠同一个 `-fsanitize=` 参数接上，所以函数里要同时写 `target_compile_options()` 和 `target_link_options()`。`target_link_options()` 只对会链接的目标有效；示例的 `probe` 是可执行文件，静态库要把同一组参数设成 `INTERFACE` 交给下游。

`proj_enable_sanitizers()` 把 `PROJ_SANITIZE` 里的名字拼成一个 `-fsanitize=` 参数，同时加到目标的编译选项和链接选项上。

`CMakeLists.txt`：

```cmake
{{#include code/ch21/21_1_sanitizers/CMakeLists.txt}}
```

`cmake/Sanitizers.cmake`：

```cmake
{{#include code/ch21/21_1_sanitizers/cmake/Sanitizers.cmake}}
```
{{#sidefx ch21/21_1_sanitizers}}

第 8 步调用函数，第 12 步和第 13 步分别给 `probe` 加上 `COMPILE_OPTIONS` 和 `LINK_OPTIONS`；生成页里两条都标着来自 `cmake/Sanitizers.cmake`。构建页只有两条命令，编译和链接各带一次 `-fsanitize=address,undefined`。

运行页里 `./build/probe` 退出码 1，先打出 UBSan 的 `index 3 out of bounds`，接着是 `ERROR: AddressSanitizer: stack-buffer-overflow`。程序故意读了 `values[3]`，数组只有三个元素。编译把检查代码插进去，链接把 sanitizer 的运行时接进来。

第 2 次运行换成 `thread`，两条命令变成 `-fsanitize=thread`，这次只构建、不运行。第 3 次把 `address` 和 `thread` 混在一起，第 11 步 `message(FATAL_ERROR)` 让配置失败；在终端里写带分号的 `-D` 要给整个参数加引号，分号是 CMake 的列表分隔符。第 3 步的 `set(PROJ_SANITIZE "" CACHE STRING ...)` 把命令行给的 `UNINITIALIZED` 补成 `STRING`，值没变，见 [5.3 节](ch05.md)。

`PROJ_SANITIZE` 可以取的值：

| 值 | 编译和链接参数 | 运行时检查 | 注意 |
|---|---|---|---|
| `address` | `-fsanitize=address` | 越界、use-after-free、double free | 不能和 `thread` 同用 |
| `undefined` | `-fsanitize=undefined` | 有符号溢出、空指针、数组下标越界 | 可以分别和 `address`、`thread` 同用 |
| `address;undefined` | `-fsanitize=address,undefined` | 上面两类 | 示例第 1 次运行用的组合 |
| `thread` | `-fsanitize=thread` | 数据竞争 | 不能和 `address` 同用；可以和 `undefined` 一起编 |
| 空 | 不加参数 | 无 | 普通构建 |

## 21.2 编译器启动器

启动器的典型用途是 ccache 和 distcc：编译命令不变，只是在前面多一个程序。它不碰链接，因为链接不重复编译，没有编译结果可缓存。

编译器启动器（compiler launcher）是一段包在编译器外面的命令。CMake 把它写在每条编译命令的最前面，源文件、`-o`、`-c` 这些参数原样传给它。

`CMakeLists.txt`：

```cmake
{{#include code/ch21/21_2_launcher/CMakeLists.txt}}
```

`tools/log-cc.sh`：

```sh
{{#include code/ch21/21_2_launcher/tools/log-cc.sh}}
```
{{#sidefx ch21/21_2_launcher}}

构建页的第 1、2 条命令都以 `sh ../src/tools/log-cc.sh` 开头，后面才是 `/usr/bin/g++ ... -c ...`；第 3 条链接命令没有启动器。运行页的 `cat build/compile.log` 打出两行，正是这两条编译命令。

脚本先追加一行，再 `exec "$@"` 把参数交回给编译器，所以构建照常完成，`app` 打印 `hello from launcher`。脚本用 `sh` 调用，不需要可执行位；路径写成相对 `build/` 的 `../src/tools/log-cc.sh`，因为 Ninja 在构建目录里执行命令。ccache 接在同一个变量上：把值换成 `ccache`，命令就变成 `ccache /usr/bin/g++ ...`；在终端里写这条 `-D` 也要给整个参数加引号。

本机没有装 ccache，这个示例用只记日志的脚本代替；日志里的命令行没有启动器自己，因为脚本记录的已经是它收到的参数。启动器只作用于编译；要同样包住链接，用 3.21 起的 `CMAKE_<LANG>_LINKER_LAUNCHER`（或目标属性 `<LANG>_LINKER_LAUNCHER`）。`CMAKE_<LANG>_COMPILER_LAUNCHER` 从 3.4 起有，在目标创建时初始化同名属性，写在 `add_executable()` 之后不会回头改已经建好的目标。

## 21.3 clang-tidy 和 compile_commands.json

clang-tidy 可以单独跑，也可以让 CMake 在每次编译时顺手跑一遍。后者不需要编辑器或编译数据库，代价是每条编译命令都多一次进程启动。`compile_commands.json` 记录每个源文件的完整编译命令，是 clangd 和单独跑的 clang-tidy（`-p`）共用的东西；CMake 集成的那条路不需要它。

第 3 步打开 `CMAKE_EXPORT_COMPILE_COMMANDS`，生成页的文件列表里多出 `build/compile_commands.json`；运行页的 `grep` 从里面打出两条 `"file"`，分别是 `core.cpp` 和 `main.cpp`。导出编译数据库和让 CMake 跑 tidy 互相独立：打开 `CMAKE_EXPORT_COMPILE_COMMANDS` 不会自动让 tidy 运行，设了 tidy 也不要求它存在。

第 4 步把 `CMAKE_CXX_CLANG_TIDY` 设成 `clang-tidy -checks=...`，第 5 步创建的 `core` 目标继承它；第 7 步创建的 `app` 也继承，但第 9 步把 `app` 的 `CXX_CLANG_TIDY` 设成空，等于退出检查。`CMAKE_CXX_CLANG_TIDY` 从 3.6 起有，变量在目标创建时初始化同名属性；把属性设成空字符串是常用的逐目标关闭办法。

构建页的第 1 条命令以 `cmake -E __run_co_compile --tidy=...` 开头，后面才是编译器；第 3 条 `app` 的编译还是普通的 `g++`。tidy 在 `core.cpp` 第 3 行报了 `readability-braces-around-statements`，构建仍然退出 0：它只报告，不替编译器判错。`CMAKE_EXPORT_COMPILE_COMMANDS` 从 3.5 起有，只对 Makefile 和 Ninja 生成器有效。

## 21.4 覆盖率

覆盖率工具不是另一套构建系统：它在编译时插计数代码，在链接时接运行时，程序跑完再把计数写成文件。GCC 的 `--coverage` 就是这两件事的简写。编译时写 `.gcno`，运行时写 `.gcda`，`gcov` 再把两张表合起来。

`CMakeLists.txt`：

```cmake
{{#include code/ch21/21_4_coverage/CMakeLists.txt}}
```
{{#sidefx ch21/21_4_coverage}}

第 2、3 步在 `project()` 之前给 `Coverage` 配置写了两个缓存项。放在 `project()` 之前是因为 `project()` 会为 `CMAKE_BUILD_TYPE` 对应的配置建空的缓存项；这次配置已经指定 `Coverage`，之后再 `set(... CACHE ...)` 不带 `FORCE` 就改不动（[5.3 节](ch05.md)）。

`CMAKE_CXX_FLAGS_COVERAGE` 同时进编译和链接，`CMAKE_EXE_LINKER_FLAGS_COVERAGE` 只给可执行文件的链接再加一次。共享库和模块的链接命令本来就会带上 `CMAKE_CXX_FLAGS_COVERAGE` 里的 `--coverage`，不必再写进 `CMAKE_SHARED_LINKER_FLAGS_COVERAGE`/`CMAKE_MODULE_LINKER_FLAGS_COVERAGE`；这两个变量留给别的链接专用参数。

构建页的编译命令带 `--coverage -O0 -g`，链接命令是 `--coverage -O0 -g --coverage`：`CMAKE_CXX_FLAGS_COVERAGE` 也会进链接命令，`CMAKE_EXE_LINKER_FLAGS_COVERAGE` 又加了一次。两次不冲突；`ctest` 跑完测试，运行页里 `find build -name '*.gcda' -print` 打出 `build/CMakeFiles/check.dir/main.cpp.gcda`。`CMakeFiles/` 下的文件在文件栏里按目录合并，具体路径看这条 `find` 的输出。

接着 `gcov` 打出 `Lines executed:77.78% of 9`、`Branches executed:66.67% of 6`，并写出 `build/main.cpp.gcov`；点开能看到每行执行次数，没走到的行是 `#####`。本机没有 gcovr，示例停在 `gcov`；gcovr 读的是同一批 `.gcda`/`.gcno`，只是把结果汇总成报告。第 2 次运行换成一个干净的构建目录，配置成 `Release`：编译和链接变成 `-O3 -DNDEBUG`，没有 `--coverage`，`ctest` 之后检查 `.gcda` 的结果是 `no-gcda`。

## 速查

| 想挂的东西 | 写法 | 作用在哪一步 | 看哪里 |
|---|---|---|---|
| 编译器启动器 | `CMAKE_<LANG>_COMPILER_LAUNCHER` 或目标属性 `<LANG>_COMPILER_LAUNCHER` | 每条编译命令前 | 构建页的命令前缀、启动器日志 |
| sanitizer | `target_compile_options()` + `target_link_options()` | 编译和链接 | 构建页两条命令、运行时的 ASan 输出 |
| clang-tidy | `CMAKE_<LANG>_CLANG_TIDY` 或目标属性 `<LANG>_CLANG_TIDY` | 每条编译命令（经 `__run_co_compile`） | 构建页的 `__run_co_compile` |
| 编译数据库 | `CMAKE_EXPORT_COMPILE_COMMANDS` | 生成阶段 | 生成页的 `compile_commands.json` |
| 覆盖率 | `CMAKE_<LANG>_FLAGS_<CONFIG>`、`CMAKE_EXE_LINKER_FLAGS_<CONFIG>` | 对应配置的编译和链接 | 构建页的 `--coverage`、运行后的 `.gcda` |

## 思考题

1. 把 `21_1` 的 `PROJ_SANITIZE` 改成只写 `address`，再构建运行。构建页的两条命令、运行页的报错会少掉什么？
   <details><summary>提示</summary>少了 <code>-fsanitize=undefined</code> 和 UBSan 的 <code>runtime error</code> 两行；ASan 的 stack-buffer-overflow 还在。</details>
2. 把 21.2 的 `-DCMAKE_CXX_COMPILER_LAUNCHER=...` 从命令行挪到 `add_executable(app ...)` 后面，用 `set(CMAKE_CXX_COMPILER_LAUNCHER ...)` 设置。构建页还会出现启动器吗？
   <details><summary>提示</summary>不会；变量在目标创建时初始化属性，app 已经建好了。把 set 放到 add_executable 之前，或者直接设目标属性 <code>CXX_COMPILER_LAUNCHER</code>。</details>
3. 21.3 里 `app` 为什么没有走 co-compile？把第 9 步的 `set_target_properties(... CXX_CLANG_TIDY "")` 删掉，构建页第 3 条命令会变成什么？
   <details><summary>提示</summary>app 继承了变量，但目标属性被设成空；删掉后 app 的编译也变成 <code>cmake -E __run_co_compile --tidy=...</code>，两个源文件都会检查。</details>
4. 把 21.4 的两个 `set(... CACHE ...)` 移到 `project()` 后面，重新配置。构建页的 `--coverage` 会消失吗？为什么？
   <details><summary>提示</summary>会。这次配置指定了 Coverage，project() 已经建好空的 <code>CMAKE_CXX_FLAGS_COVERAGE</code> 缓存项；不带 FORCE 的 set(CACHE) 不改已有值，把默认值放回 project() 之前，或者显式 FORCE。</details>
