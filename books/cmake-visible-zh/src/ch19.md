# 第 19 章 CTest

“先 `enable_testing()`，再 `add_test()`，最后跑 `ctest`。”这条建议看起来只差两行命令，中间却隔着一个生成阶段：ctest 读的是生成时写出的测试清单。

[第 18 章](ch18.md) 已经用 `add_test()` 把安装和下游构建串了起来；这一章把 CTest 本身拆开看。先跑两个测试，一个通过，一个故意失败。

{{#sidefx ch19/19_1_add_test step=3 label="从 enable_testing 开始"}}

第 3 步 `enable_testing()` 只把内置变量 `CMAKE_TESTING_ENABLED` 置上，没有写文件。第 5、6 步的 `add_test()` 也没有改动变量、缓存或目标：它们只是把测试命令登记进当前目录的测试表。切到生成页，`build/CTestTestfile.cmake` 才出现，文件里有两条 `add_test`，可执行文件已经换成 `/work/build/probe` 的绝对路径。

运行页的 ctest 依次启动两个测试。`returns_zero` 拿到参数 `ok`，返回 0，记为通过；`returns_one` 返回 1，记为失败，命令最后的退出码是 8。默认情况下，CTest 只看进程退出码，不读测试打印了什么；测试名会原样出现在每一行和失败列表里，起名时让它说明测的是什么。

{{#fig ch19/ctest_files}}

每个调用过 `enable_testing()` 的目录都会在生成阶段得到一个 `CTestTestfile.cmake`，ctest 从构建目录顶层读起，再按文件里的 `subdirs()` 进入子目录。这也是 `enable_testing()` 应该写在顶层 `CMakeLists.txt` 的原因。ctest 不编译任何东西：源码改了而没重新构建，它运行的还是旧程序。

测试名、命令和属性都写在同一份清单里，19.4 节会看到属性也只是清单上的几行。

```cmake

```
{{#sidefx ch19/19_2_build_testing run=2 step=6 label="运行 2：单独配置的 include(CTest)"}}

第一次运行由 `host` 配置，`lib` 只是子目录：`project(Calc)` 把 `PROJECT_IS_TOP_LEVEL` 设成 `OFF`，`if(PROJECT_IS_TOP_LEVEL)` 不进去，所以 `include(CTest)` 根本没执行，缓存里没有 `BUILD_TESTING`。构建页的目标只有 `calc` 和 `host_app`，运行页的 `ctest -N` 报 `Total Tests: 0`。

第二次单独配置 `lib`。第 6 步 `include(CTest)` 在模块里执行了 193 条命令：缓存多出 `BUILD_TESTING:BOOL=ON`、`SITE`、`MAKECOMMAND` 等 10 项，目标栏多出 28 个 `Continuous`、`Experimental`、`Nightly` 开头的 UTILITY 目标，还写了 `DartConfiguration.tcl`。第 7 步的条件成立，第 8 步进入 `tests/`，第 11 步 `add_test()` 登记 `calc_add`；构建多出 `calc_test`，ctest 跑完 1/1 通过。

第三次运行时 `-DBUILD_TESTING=OFF`，`include(CTest)` 只执行了 7 条命令，缓存里的 `BUILD_TESTING` 从 `UNINITIALIZED` 变成 `BOOL`，值仍是 `OFF`，也没有那些仪表板目标。`option()` 遇到已有的缓存项只补类型和说明，不改值（[第 5 章](ch05.md)）。

| 运行 | `PROJECT_IS_TOP_LEVEL` | `include(CTest)` | 测试目标 | 测试数 |
|---|---|---|---|---|
| 被 `host` 包含 | `OFF` | 没执行 | 无 | 0 |
| 单独配置 | `ON` | 193 条命令 | `calc_test` | 1 个 |
| 单独配置，`BUILD_TESTING=OFF` | `ON` | 7 条命令 | 无 | 0 |

`BUILD_TESTING` 是缓存变量，`-DBUILD_TESTING=OFF` 只改当前构建目录里的那一份。同一个源码目录可以同时有开测试和关测试的两个构建目录，互不影响。

`include(CTest)` 在 `BUILD_TESTING` 为 `ON` 时会替你调用 `enable_testing()`；为 `OFF` 时连这一步也不做，所以第三次运行只执行了 7 条命令。

`include(CTest)` 不是一个只加一个开关的小模块，它自己就会建目标、写文件。所以示例把 `include(CTest)` 也放进了 `if(PROJECT_IS_TOP_LEVEL)`；测试本身再用 `if(PROJECT_IS_TOP_LEVEL AND BUILD_TESTING)` 挡一次。只写 `if(BUILD_TESTING)` 不够：父工程可能已经打开 `BUILD_TESTING`，子工程的测试照样会进来。

{{#sidefx ch19/19_3_gtest step=8 label="从 gtest_discover_tests 开始"}}

第 8 步 `gtest_discover_tests(t)` 写出的唯一文件是 165 字节的 `t[1]_include.cmake`，目标上多了一个 `CTEST_DISCOVERED_TEST_COUNTER` 属性。它没有在配置阶段运行测试程序，也没有列出任何用例。`GTest::gtest_main` 和 [7.5 节](ch07.md) 的 `ZLIB::ZLIB` 一样是导入目标，由 `find_package` 从 GTest 的 Config 文件带进来，链接时把 `libgtest_main.a` 和 `libgtest.a` 写进命令。

构建页只有两条命令，第二条在链接完 `t` 之后接着执行 `/usr/bin/cmake -P …/GoogleTestAddTests.cmake`。这正是 POST_BUILD 命令：脚本运行 `t --gtest_list_tests`，把用例名写成 JSON，再生成 `build/t[1]_tests.cmake`。文件里每个 `TEST` 变成一条 `add_test`，命令带 `--gtest_filter=套件.用例`。

{{#fig ch19/discover}}

运行页的 ctest 于是列出 `Arithmetic.Adds`、`Arithmetic.Multiplies`、`Text.Joins` 三条，各自单独运行。只想确认清单时用 `ctest -N`，它列出用例但不启动进程。用例名来自编译出来的程序，不是 CMake 读源码猜的：新加一个 `TEST` 后不重新构建，ctest 的清单不会变。

`gtest_discover_tests()` 不会替你打开测试。没有 `enable_testing()`（或 `include(CTest)`）时，测试表不会被写出来，ctest 也就找不到这些用例。GoogleTest 模块只负责“发现”，打开 CTest 仍是工程自己的事。

## 19.4 测试属性：WILL_FAIL、正则、超时、标签和环境

```cmake
{{#include code/ch19/19_4_test_props/CMakeLists.txt}}
```
{{#sidefx ch19/19_4_test_props step=6 label="从 WILL_FAIL 开始"}}

第 6 步给 `wrong_exit` 设了 `WILL_FAIL TRUE`，它的进程返回 1，ctest 仍记为 Passed。第 8 步把 `ENVIRONMENT "GREETING=CMake"`、`PASS_REGULAR_EXPRESSION "hello, CMake"` 和两个标签一起写进 `greeting`；程序打印 `hello, CMake`，正则命中，测试通过。第 10 步给 `slow_probe` 设 `TIMEOUT 1`，它睡 3 秒，运行页里显示 `***Timeout`，ctest 退出码是 8。

这些属性各自管什么：

| 属性 | 作用 | 这次的结果 |
|---|---|---|
| `WILL_FAIL` | 反转退出码的判断 | `wrong_exit` 返回 1，记为 Passed |
| `PASS_REGULAR_EXPRESSION` | 输出必须匹配正则 | `greeting` 打印 `hello, CMake` |
| `TIMEOUT` | 进程最多跑几秒 | `slow_probe` 1 秒后超时 |
| `LABELS` | 给测试贴标签，供 `-L` 筛 | `unit`、`fast`、`slow` |
| `ENVIRONMENT` | 给测试进程加环境变量 | `GREETING=CMake` |
| `FIXTURES_*` | 给一组测试加 setup 和 cleanup | 三条 fixture 测试依次跑 |

18.2 已经用 `FIXTURES_SETUP`/`FIXTURES_REQUIRED` 排过安装和下游构建；这里换成三个测试共用一个文件：`fixture_setup` 带 `FIXTURES_SETUP DATA` 建文件，`fixture_user` 带 `FIXTURES_REQUIRED DATA` 检查文件，`fixture_cleanup` 带 `FIXTURES_CLEANUP DATA` 删文件。`fixture_user` 失败时清理仍会执行。

第二条命令 `ctest -N -L unit` 只按标签筛，却列出 4 条：`greeting`、`fixture_setup`、`fixture_user`、`fixture_cleanup`。CTest 自动把被选中测试所依赖的 fixture 的 setup 和 cleanup 一起加进来。

`WILL_FAIL` 只反转退出码；超过 `TIMEOUT` 仍然失败，段错误这类系统级失败也可能失败。`PASS_REGULAR_EXPRESSION` 下进程退出码被忽略，但超时照样失败、系统级失败仍可能失败；输出匹配不上时，退出码为 0 也失败。`ENVIRONMENT` 只给测试进程加变量，不改配置阶段的环境；`TIMEOUT` 的单位是秒，到点后 CTest 结束该进程。

## 19.5 ctest 的常用参数

| 参数 | 作用 | 注意 |
|---|---|---|
| `-R <正则>` | 只跑名字匹配的测试 | 按测试名匹配，不是按源文件 |
| `-L <正则>` | 只跑标签匹配的测试 | 会把 fixture 的 setup/cleanup 一起带上 |
| `-j <N>` | 最多 N 个测试并行 | 默认串行；有共享文件的测试要自己错开 |
| `--output-on-failure` | 失败时打印测试自己的输出 | 通过的测试不打印；`-V` 才打印全部 |
| `--test-dir <目录>` | 指定构建目录 | 3.20 起；省掉先 `cd build` |
| `--rerun-failed` | 只重跑上一次失败的测试 | 会忽略 `-R`、`-L` 等筛选参数 |

这些参数可以叠加，例如在构建目录外执行 `ctest --test-dir build -R greeting --output-on-failure`。`-R` 和 `-L` 同时给时，测试要两个条件都满足；`--rerun-failed` 则优先于这些筛选，只认上一次的失败列表。

并行跑会打乱测试的输出顺序，也可能让共用同一个文件的测试互相踩。fixture 的 setup 和 cleanup 在 `-j` 下仍按先后顺序执行，但测试体之间没有互斥。要固定这些参数重复使用，下一章的 `testPresets` 就是把它们写进 `CMakePresets.json`。

## 速查

| 写法 | 副作用发生在 | 注意 |
|---|---|---|
| `enable_testing()` | 配置时置 `CMAKE_TESTING_ENABLED`；生成时写 `CTestTestfile.cmake` | 写在顶层；ctest 从构建目录顶层找清单 |
| `add_test()` | 配置时登记，生成时写进清单 | 不构建、不运行；命令里的目标会换成绝对路径 |
| `include(CTest)` | 配置时加 `BUILD_TESTING` 等缓存项、一批仪表板目标 | 子工程里也生效；放在 `if(PROJECT_IS_TOP_LEVEL)` 里 |
| `gtest_discover_tests(t)` | 配置时写 include 文件；构建的 POST_BUILD 阶段列用例 | 要先 `enable_testing()` 或 `include(CTest)` |
| `set_tests_properties()` | 配置时写进清单 | 测试属性只能在创建测试的目录里设 |
| `ctest` | 运行时读清单、起进程 | 不编译；源码变了先 `cmake --build` |
