# 第 15 章 把依赖带进构建：子目录、FetchContent、先找再下载

同事给项目的建议是：GTest 只走 `find_package`，新克隆的机器先装好；再加一个 FetchContent 兜底。这两句话放进同一份 CMakeLists，谁先谁后？先从把一份第三方源码直接放进仓库的做法看起。

## 15.1 add_subdirectory 引入第三方源码

第三方库的源码就在 `third_party/tiny/`，把它当普通子目录加进来：

```cmake
{{#include code/ch15/15_1_vendored/CMakeLists.txt}}
```

`third_party/tiny/CMakeLists.txt` 是它自己的工程文件：

```cmake
{{#include code/ch15/15_1_vendored/third_party/tiny/CMakeLists.txt}}
```
{{#sidefx ch15/15_1_vendored}}

第一次运行的第 3 步 `add_subdirectory()` 立刻进入 `third_party/tiny/CMakeLists.txt`。第 5 步它的 `project()` 把 `PROJECT_IS_TOP_LEVEL` 从 `ON` 改成 `OFF`；第 6 步 `option(TINY_BUILD_TOOL …)` 往缓存里加了一项 `TINY_BUILD_TOOL:BOOL=ON`；第 9、12 步 `tiny` 和 `tiny_tool` 两个目标进了同一张目标表。缓存和目标都是整个工程共用的，子目录的开关不会只留在子目录里。

第 8 步 tiny 把自己目录的 `CMAKE_CXX_FLAGS` 追加了 `-Wall`。这个变量只在 `third_party/tiny` 目录作用域里存在，所以构建页里 `tiny` 和 `tiny_tool` 的编译命令有 `-Wall`，`app` 的没有。第三方工程改自己的编译选项可以，但它管不到你的目标。

第二次运行把那一行换成 `add_subdirectory(third_party/tiny EXCLUDE_FROM_ALL SYSTEM)`。`tiny_tool` 的目标仍然在第 12 步被创建，但构建页只剩 4 条命令，没有编译 `tool.cpp`：`EXCLUDE_FROM_ALL` 只把它排除出父目录的默认构建，被 `app` 依赖的 `tiny` 照样要建。`app` 的编译命令从 `-I…/third_party/tiny/include` 变成了 `-isystem …/third_party/tiny/include`，这是 `SYSTEM`（3.25 起）的效果：消费者的头文件搜索把它当系统目录，警告默认不再从那里冒出来。

## 15.2 FetchContent：配置时把源码取到 `_deps`

源码不一定放在仓库里。把 tiny 打成一个 tar.gz 放在 `deps/`，让 FetchContent 在配置时解开：

```cmake
{{#include code/ch15/15_2_fetchcontent/CMakeLists.txt}}
```
{{#sidefx ch15/15_2_fetchcontent}}

第 3 步 `include(FetchContent)` 先建了四个缓存项，其中 `FETCHCONTENT_BASE_DIR` 是 `/work/build/_deps`。第 4 步 `FetchContent_Declare()` 只登记 URL 和 `URL_HASH`，没有任何文件变化。第 7 步 `FetchContent_MakeAvailable(tiny)` 才真的解压：文件列表里出现 `build/_deps/tiny-src/CMakeLists.txt`、`tiny.cpp`、`include/tiny.h`，变量里多了 `tiny_SOURCE_DIR` 和 `tiny_BINARY_DIR`，缓存里多了 `Tiny_SOURCE_DIR`、`Tiny_BINARY_DIR` 和 `FETCHCONTENT_SOURCE_DIR_TINY`。

同一步还写出 `build/CMakeFiles/fc-stamp/tiny/` 和 `fc-tmp/tiny/` 下的下载、校验脚本。这里没有 `tiny-subbuild`：CMake 3.30 起，`CMP0168` 为 `NEW` 时下载、解压直接在配置进程里做；3.29 及更早会另起一个 `_deps/tiny-subbuild` 子工程。两种实现下源码都在 `tiny-src`，构建目录都在 `tiny-build`；OLD 还会多一个 `tiny-subbuild`。

第二次运行的第 7 步没有任何文件变化，只把 `tiny_SOURCE_DIR` 等变量重新设一遍，构建页也是 0 条命令。在同一个构建目录里，解压只在第一次发生，后面配置直接复用 `_deps` 里的源码。

{{#fig ch15/fetch_flow}}

顺序是先声明、再满足。默认的 `OPT_IN` 模式下，带 `FIND_PACKAGE_ARGS` 时，满足的第一步是 `find_package()`；`NEVER` 跳过这步，`ALWAYS` 即使没写这段也先找。

`FetchContent_MakeAvailable()` 取到源码后，如果源码顶层有 `CMakeLists.txt`，最后仍然走 `add_subdirectory()`，所以 15.1 里“目标进本工程”的现象在这里同样成立。取到的源码里有 `option()` 时，它也会进你的缓存；15.2 的 tiny 没有。

> **旧资料提示**：2018 年前后的教程常用 `ExternalProject_Add()` 拉第三方库。它在构建阶段才下载，配置阶段拿不到目标，不能直接 `target_link_libraries`。FetchContent（3.11 起）把源码取到配置阶段，就是为了解决这个问题。

## 15.3 先找再下载：FIND_PACKAGE_ARGS

`find_package()` 的模块模式、配置模式和 `GTest_DIR` 从哪来，[第 14 章](ch14.md) 已经讲过。这里只关心它在 FetchContent 里什么时候被调用。

{{#sidefx ch15/15_3_find_or_fetch}}

第一次运行的第 5 步 `FetchContent_MakeAvailable(GTest)` 没有下载，而是调用了 `find_package(GTest … CONFIG)`：变量里出现 `GTest_FOUND=1`、`GTest_VERSION=1.17.0`，缓存里出现 `GTest_DIR`。第 7 步的 `build/_deps 不存在` 说明它根本没有建 `_deps` 目录；构建页链接的是 `/usr/lib/x86_64-linux-gnu/libgtest_main.a`。

第二次运行加了 `-DFETCHCONTENT_TRY_FIND_PACKAGE_MODE=NEVER`（3.24 起）。这个值在 `FetchContent_Declare()` 执行时被记下，`MakeAvailable()` 于是跳过 `find_package()`，第 5 步解压出自带的 `fake-gtest`，第 7 步变成 `build/_deps 存在`。构建页里多了 `-DFAKE_GTEST=1`，运行程序打印 `fake gtest`。

第 5 步的目标栏把这件事显示得很清楚：第一次是导入的 `GTest::gtest_main`，第二次是别名 `GTest::gtest_main`。两条路径的目标名一样，所以 `target_link_libraries(app PRIVATE GTest::gtest_main)` 一个字不用改。反过来，自带的源码包必须提供同名目标；名字对不上，生成阶段就会报找不到 `GTest::gtest_main`（带 `::` 的名字必须是已存在的目标）。

## 15.4 依赖提供者和包管理器

`FIND_PACKAGE_ARGS` 是工程自己的选择。如果用户想统一接管工程里的 `find_package()`，可以在第一次 `project()` 里注入一个依赖提供者（dependency provider，3.24 起）。下面的 provider 把 Tiny 指到仓库里的目录：

```cmake

```

工程本身只写普通的 `find_package()`：

```cmake
{{#include code/ch15/15_4_dependency_provider/CMakeLists.txt}}
```
{{#sidefx ch15/15_4_dependency_provider}}

第 2 步 `project()` 的输出里，`provider: 在 project() 里被 include` 排在编译器检测之前；缓存变化里已经有 `TINY_LOCAL_DIR`。provider 是在第一次 `project()` 里、启用语言之前被 include 的，所以它能在那时注册。

第 3 步 `find_package(Tiny CONFIG REQUIRED)` 把请求交给 provider，第 4 步是 provider 里的 `if()`，第 5 步设 `Tiny_DIR`，第 6 步用 `find_package(… BYPASS_PROVIDER)` 读 `TinyConfig.cmake`。第 7 步目标栏里出现导入目标 `Tiny::tiny`，第 8–9 步给它设 include 目录并让 `Tiny_FOUND` 为真，第 10 步 provider 返回时再置真一次。`BYPASS_PROVIDER` 是必须的，否则这次调用又会回到 provider 自己。

如果 provider 只改了查找路径、没有建出目标，就不要把 `Tiny_FOUND` 设为真：返回时不设它，CMake 会退回内置的 `find_package()`。设了真又没建目标，后面的 `target_link_libraries()` 会报找不到 `Tiny::tiny`。

{{#fig ch15/provider_inject}}

包管理器接进来的方式可以归成这张表：

| 做法 | 常见接入点 | 代价 |
|---|---|---|
| `add_subdirectory` | 源码在仓库里，直接加 | 第三方的 option 进你的缓存，目标进你的工程 |
| `FetchContent` | 配置时按 URL 取源码 | 首次配置要下载/解压；要固定哈希 |
| `find_package` | 包已经装在这台机器上 | 新克隆的机器要先装；找不到就得不到目标，写了 `REQUIRED` 才在配置时报错 |
| vcpkg / Conan | 工具链文件；Conan 也可用 `cmake-conan` 的 provider | 配置前多一步安装；工具链会影响所有查找 |

`FIND_PACKAGE_ARGS` 是工程作者写在声明里的顺序，provider 是用户在所有工程外面加的接管点。用户设了 provider 后，只要它也声明 `FETCHCONTENT_MAKEAVAILABLE_SERIAL`，`FetchContent_MakeAvailable()` 也会先把请求交给它；包管理器可以用这个机制同时接管 `find_package()` 和 FetchContent。

本书不联网，vcpkg 和 Conan 只说到这里。自己写 provider 时，入口还是 `CMAKE_PROJECT_TOP_LEVEL_INCLUDES`：把它指向一个 `.cmake` 文件，文件里调用 `cmake_language(SET_DEPENDENCY_PROVIDER …)`。

## 15.5 作为子工程被别人用：PROJECT_IS_TOP_LEVEL

库的作者也会被别人 `add_subdirectory()` 或 FetchContent 引入。测试要不要跟着构建，取决于这次是不是主工程：

```cmake

```

下游工程这样引入它：

```cmake
{{#include code/ch15/15_5_top_level/consumer/CMakeLists.txt}}
```
{{#sidefx ch15/15_5_top_level}}

第一次把 `tiny/` 当主工程配置：第 2 步的 `PROJECT_IS_TOP_LEVEL` 是 `ON`，第 3 步 `option()` 的默认值就是 `ON`，缓存里写入 `TINY_BUILD_TESTS:BOOL=ON`；第 8 步建出 `tiny_test`，构建页有 4 条命令。

第二次从 `consumer/` 引入：consumer 才是主工程，第 5 步 `FetchContent_MakeAvailable()` 进入 tiny 的 `project()` 时，`Tiny_IS_TOP_LEVEL` 是 `OFF`，`option()` 的默认值变成 `OFF`，输出里是 `TINY_BUILD_TESTS=OFF top=OFF`。构建页只有 `tiny` 和 `app` 的 4 条命令，没有 `tiny_test`。

`PROJECT_IS_TOP_LEVEL` 是 3.21 起由 `project()` 设置的变量，在子目录里再调用一次 `project()` 就会变成 `OFF`。用 `option(TINY_BUILD_TESTS … ${PROJECT_IS_TOP_LEVEL})` 把默认值和这个事实绑在一起；用户仍然可以用 `-DTINY_BUILD_TESTS=ON` 显式打开测试。

## 速查

| 写法 | 副作用发生在 | 留下什么 |
|---|---|---|
| `add_subdirectory(third_party/x)` | 配置，立刻读它的 CMakeLists | 目标进本工程；它的 `option()` 进你的缓存 |
| `add_subdirectory(… EXCLUDE_FROM_ALL)` | 配置时设目录属性；生成时从父目录的 `ALL` 里去掉 | 被依赖的目标仍会构建；显式构建也会构建 |
| `add_subdirectory(… SYSTEM)` | 配置时设目录属性；生成时写进消费者的编译命令 | 消费者用 `-isystem` 找它的头文件（3.25 起） |
| `FetchContent_Declare(x …)` | 配置，只登记 | 不下载；`URL_HASH`、`FIND_PACKAGE_ARGS` 记在这里 |
| `FetchContent_MakeAvailable(x)` | 配置 | 先问 provider（若设置），再找包（可选），否则取源码并 `add_subdirectory` |
| `PROJECT_IS_TOP_LEVEL` | `project()` 时设置 | 被引入且自带 `project()` 时是 `OFF`（3.21 起） |
