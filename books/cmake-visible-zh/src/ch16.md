# 第 16 章 安装：install() 和 GNUInstallDirs

`cmake --install build --prefix /tmp/x` 之后，`/tmp/x` 里只有 install() 规则点名的东西：`bin/` 里的程序、`lib/` 里的库、`include/` 里的头文件。先看一个库、一个程序和一组公共头文件。

`install()` 的写法看起来像“现在就复制”，实际只是往构建目录的安装脚本里加一条规则。真正碰磁盘的是后来的 `cmake --install`，它执行 `cmake_install.cmake`。

## 16.1 install(TARGETS)

配置页第 7 步 `install(TARGETS ...)` 执行完，变量、缓存、目标、文件四栏都没有变化；查看器在这一步下面写着“只是登记一条安装规则：写进 cmake_install.cmake（生成阶段），cmake --install 时才执行”。第 4 步 `target_sources(FILE_SET HEADERS)` 已经把 `include/` 加进 `greet` 的 `INTERFACE_INCLUDE_DIRECTORIES`，所以第 6 步接上 `greet` 的 `greet_app`，在构建页的编译命令里带着 `-I/work/src/include`。

`ARCHIVE` 接住静态库，`RUNTIME` 接住可执行文件，`FILE_SET HEADERS` 接住第 4 步登记的头文件集；这三种产物的 DESTINATION 各写各的。install() 也可以不给 DESTINATION，这时 CMake 用 GNUInstallDirs 的值，或者退回内置的 `lib`、`bin`、`include`。

`FILE_SET HEADERS` 从 3.23 起才有；更早的工程用 `PUBLIC_HEADER` 属性加 `install(TARGETS ... PUBLIC_HEADER DESTINATION ...)`。

生成页里出现 `build/cmake_install.cmake`。去掉外面的 component 判断，三条规则就是三个 `file(INSTALL ...)`：

```cmake
file(INSTALL DESTINATION "${CMAKE_INSTALL_PREFIX}/lib" TYPE STATIC_LIBRARY FILES "/work/build/libgreet.a")
file(INSTALL DESTINATION "${CMAKE_INSTALL_PREFIX}/include/greet" TYPE FILE FILES "/work/src/include/greet/greet.h")
file(INSTALL DESTINATION "${CMAKE_INSTALL_PREFIX}/bin" TYPE EXECUTABLE FILES "/work/build/greet_app")
```

脚本开头把 `CMAKE_INSTALL_PREFIX` 默认成 `/usr/local`，`--prefix prefix` 在运行 `cmake --install` 时覆盖它。运行页第一条命令按脚本装了 `prefix/lib/libgreet.a`、`prefix/include/greet/greet.h`、`prefix/bin/greet_app`；第二条命令运行装好的 `greet_app`，打印 `hello from installed greet`。

完整安装还会写 `build/install_manifest.txt`，把装过的文件按绝对路径列一行；它只是记录，`cmake --install` 没有卸载命令。想撤掉一次安装，得照 manifest 删文件，或者把旧前缀整个删掉；装到新前缀只是另装一份，旧文件还在。

## 16.2 GNUInstallDirs 和目录布局

```cmake
{{#include code/ch16/16_2_gnuinstalldirs/CMakeLists.txt}}
```
{{#sidefx ch16/16_2_gnuinstalldirs}}

第一次运行的第 3 步 `include(GNUInstallDirs)` 执行了 650 条命令，缓存新增 16 个 `CMAKE_INSTALL_*` 项；第二次运行的同一步是 475 条，这些项已经在缓存里，不再标新增。第一次的那 16 项在这一步被标成新增，之后缓存一栏默认按高级项藏起来，取消勾选“隐藏高级项（ADVANCED）”才看得到，其中 `CMAKE_INSTALL_BINDIR=bin`、`CMAKE_INSTALL_LIBDIR=lib`、`CMAKE_INSTALL_INCLUDEDIR=include`。第 4 步的 message 把这三个值打印成一行输出。

这 16 项是缓存变量；`include(GNUInstallDirs)` 同时算出 16 个 `CMAKE_INSTALL_FULL_*` 普通变量，把前缀拼成绝对路径。install() 里通常用 `CMAKE_INSTALL_<dir>` 这一组，`FULL_*` 写死绝对路径，`--prefix` 就带不动它。

第二次运行带 `-DCMAKE_INSTALL_LIBDIR=lib64`，第 4 步打印 `lib=lib64`，第 9 步 `install(TARGETS ...)` 的参数也跟着变成 `lib64`。安装到 `prefix-lib64` 时，库落在 `prefix-lib64/lib64/libdirs.a`，程序和头文件仍在 `bin/`、`include/dirs/`。`--prefix` 只换前缀，不会改这三个变量的值。

| 变量 | 默认值 | 接住哪类产物 |
|---|---|---|
| `CMAKE_INSTALL_BINDIR` | `bin` | `RUNTIME`：可执行文件 |
| `CMAKE_INSTALL_LIBDIR` | `lib` | `LIBRARY`、`ARCHIVE`：共享库、静态库 |
| `CMAKE_INSTALL_INCLUDEDIR` | `include` | `FILE_SET HEADERS`、`PUBLIC_HEADER` |

install() 里写变量、不写死目录，打包的人只改缓存就能改布局。Debian 在 `CMAKE_INSTALL_PREFIX` 为 `/usr` 时，`LIBDIR` 可能是 `lib/<多架构元组>`，这是模块文档里的特例。`DESTINATION` 写相对路径时，安装脚本把它拼到运行时的前缀后面；写绝对路径就原样使用，`--prefix` 管不到它。

配置页第 4 到第 8 步是五条 install()：目标、文档、目录、CODE、SCRIPT，执行完都没有变量、缓存、目标或文件的变化。第 7 步的方括号参数不做变量展开，`${CMAKE_INSTALL_PREFIX}` 原样进了脚本；第 8 步只记下脚本的路径。

`install(FILES)` 只复制文件并保留文件名，`install(PROGRAMS)` 还会给可执行权限。`install(DIRECTORY)` 按目录树整段复制，适合文档、资源和示例工程。

安装时，`install(DIRECTORY assets/ ...)` 先报 `prefix/share/misc/assets` 这个目录，再报里面的 `logo.txt`、`notes.txt`。接着 `install(CODE)` 和 `install(SCRIPT)` 各执行一次，`prefix/share/misc/build-info.txt` 最后是两行：

```text
misc 1.0
post_install.cmake 执行了
```

`assets/` 末尾的斜杠表示复制目录内容；不写斜杠，`assets` 这个目录名会被追加到 DESTINATION 后面。`install(SCRIPT)` 的相对路径按当前源码目录解析，脚本里的变量到安装时才求值。

`install(CODE)` 和 `install(SCRIPT)` 在安装脚本里按声明顺序执行，前面的文件复制完了才轮到它们；所以脚本可以接着改刚装好的文件。

## 16.4 组件

```cmake
{{#include code/ch16/16_4_components/CMakeLists.txt}}
```
{{#sidefx ch16/16_4_components}}

第一次运行完整安装，运行页的三条 `Installing` 分别落在 `prefix/bin`、`prefix/lib`、`prefix/include/parts`。第二次运行没有配置页，只有运行页：`--component runtime` 只执行 `COMPONENT runtime` 的那一条规则，输出里只有 `prefix-runtime/bin/parts_app`，文件列表里也只有它和 manifest。

组件不改变构建产物，只给安装规则分组。打开 `cmake_install.cmake`，每条规则外面都套着一个组件判断，比如 devel 的两条是 `if(CMAKE_INSTALL_COMPONENT STREQUAL "devel" OR NOT ...)`；`--component runtime` 时这些判断为假，文件就不会复制。

没写 `COMPONENT` 的规则属于默认组件 `Unspecified`；完整安装会装所有组件，`--component devel` 则只装库和头文件。Unix Makefiles 生成器的 `list_install_components` 目标会打印 `Available install components are: ...`；Ninja 下这个目标是空的，不能靠它列组件。

| 组件 | 规则 | 装什么 |
|---|---|---|
| `runtime` | `RUNTIME` | `parts_app` |
| `devel` | `ARCHIVE`、`FILES` | `libparts.a`、`parts.h` |
| `Unspecified` | 没写 `COMPONENT` | 这个示例里没有 |

## 16.5 安装后的 rpath

```cmake
{{#include code/ch16/16_5_install_rpath/CMakeLists.txt}}
```
{{#sidefx ch16/16_5_install_rpath}}

第一次运行里，第 10、11 步只是登记规则；构建页第 4 条链接命令给构建树的 `greet_app` 加了 `-Wl,-rpath,/work/build`，所以它在 `build/` 里能运行（[第 11 章](ch11.md)）。安装时脚本把这段构建树 rpath 清成空，运行页第一条命令末尾的 `Set non-toolchain portion ... to ""` 就是它。再运行 `prefix/bin/greet_app` 退出码 127，动态加载器找不到 `libgreet.so`；`readelf -d` 里只有 `NEEDED`，没有 `RUNPATH`。

`NEEDED` 只记录库名，找库的路径在 `RUNPATH`（或 `RPATH`）里；没有这一项，加载器不会去程序旁边的 `lib/` 找。

第二次运行第 8 步 `set(CMAKE_INSTALL_RPATH "$ORIGIN/../${CMAKE_INSTALL_LIBDIR}")`（录制里展开成 `$ORIGIN/../lib`）。`CMAKE_INSTALL_RPATH` 在创建目标时初始化 `INSTALL_RPATH`（和 [7.3 节](ch07.md) 的 `CMAKE_CXX_STANDARD` 同一机制），所以它写在第 9 步 `add_executable` 之前、共享库之后，只给程序设。安装脚本把程序的 RUNPATH 改成 `$ORIGIN/../lib`；构建页这次 0 条命令，文件是安装这一步改的。

| 运行 | 安装后的 `RUNPATH` | `prefix/bin/greet_app` |
|---|---|---|
| 第一次 | 空 | 退出码 127，找不到 `libgreet.so` |
| 第二次 | `$ORIGIN/../lib` | 退出码 0，打印 `hello from shared greet` |

`$ORIGIN` 由动态加载器换成程序所在目录：从 `prefix/bin` 往上一级是 `prefix`，再进 `lib` 就是 `prefix/lib`。运行页里程序打印 `hello from shared greet`，`readelf -d` 里多出 `(RUNPATH) Library runpath: [$ORIGIN/../lib]`。整个前缀搬到别处，这个相对路径仍然成立。

`--prefix` 只改前缀，不会替你补上 RUNPATH；装到系统库目录之外时，通常得自己写 RUNPATH，或者设 `LD_LIBRARY_PATH`。

## 速查

| 写法 | 副作用发生在 | 注意 |
|---|---|---|
| `install(TARGETS ...)` | 生成 `cmake_install.cmake`，安装时复制 | DESTINATION 相对前缀；`FILE_SET HEADERS` 从 3.23 起 |
| `include(GNUInstallDirs)` | 配置时 | 往缓存加 16 个高级的 `CMAKE_INSTALL_*` 项 |
| `install(FILES ...)`、`install(DIRECTORY ...)` | 安装时复制 | DIRECTORY 末尾的 `/` 决定是否多一层目录名 |
| `install(SCRIPT ...)` | 安装时执行脚本 | 变量到安装时才求值 |
| `install(CODE ...)` | 安装时执行代码 | 双引号字符串在配置时展开；方括号参数留到安装时 |
| `COMPONENT`、`--component` | 安装时筛选规则 | 没写组件名时归 `Unspecified` |
| `CMAKE_INSTALL_RPATH` | 安装时改写 RUNPATH | 在要影响的目标创建前设置；用 `$ORIGIN` 写相对路径 |

## 思考题

1. 把 16.1 的 `FILE_SET HEADERS DESTINATION include` 改成 `include/vendor`，安装后头文件在 `prefix/` 的哪里？`greet_app` 的编译命令会变吗？
   <details><summary>提示</summary>安装目的地只影响安装树；构建树里 `greet_app` 用的还是 `INTERFACE_INCLUDE_DIRECTORIES` 里的源码路径。</details>
2. 把 16.3 的 `install(CODE [[...]])` 改成双引号字符串，会发生什么？用 `--prefix` 装到别处时，`build-info.txt` 会写到哪里？
   <details><summary>提示</summary>双引号里的 `${CMAKE_INSTALL_PREFIX}` 在配置时就展开成 `/usr/local`；安装脚本里留下的是这个绝对路径，`--prefix` 改不了它。</details>
3. 16.4 第二次运行只装了 `parts_app`。把这个 `prefix-runtime` 目录复制到一台没有 `libparts.a` 的机器上，`parts_app` 能运行吗？
   <details><summary>提示</summary>静态库在链接时已经进了程序；组件只是把文件分组，不是运行时依赖。</details>
4. 把 16.5 的 `set(CMAKE_INSTALL_RPATH ...)` 移到 `add_library` 之前，重新安装后 `libgreet.so` 会多什么？`greet_app` 还能运行吗？
   <details><summary>提示</summary>变量会给之后创建的每个目标初始化 `INSTALL_RPATH`；共享库也会被写上 `$ORIGIN/../lib`，程序不受影响。</details>
