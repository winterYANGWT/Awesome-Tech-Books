# 第 11 章 库：静态、动态和符号可见性

有经验的同事看完你的库，常会提两句：加一个导出头 `x_export.h`，把默认符号可见性设成 hidden。为什么值得多一个头文件和一项设置？先从一个不写库类型的工程看起。

同一个 `add_library(x src.cpp)`，只改命令行上的 `BUILD_SHARED_LIBS`，产物就从 `libx.a` 换成 `libx.so`。后面几节再给 `.so` 加版本号、找它的路径，再回到导出头，最后看对象库。[第 10 章](ch10.md)拆的是编译参数，这一章看编译出的对象文件怎样变成库、又怎样被程序和别的库找到。

```cmake
{{#include code/ch11/11_1_build_shared_libs/CMakeLists.txt}}
```
{{#sidefx ch11/11_1_build_shared_libs}}

第一次运行带 `-DBUILD_SHARED_LIBS=OFF`，配置页第 3 步 `add_library(x src.cpp)` 建出的是 `STATIC_LIBRARY`；第二次带 `ON`，同一个目标变成 `SHARED_LIBRARY`。两次的 `CMakeLists.txt` 一个字没改，变的只是 `add_library()` 读到的变量值。静态库把用到的对象文件复制进 app，共享库只在 app 里留一个 `DT_NEEDED`，运行时再加载。

构建页的差别更具体。第一次一共 4 条命令，第 2 条用 `ar qc` 打出 `libx.a`；第二次也是 4 条，第 1 条编译命令多了 `-fPIC` 和 `-Dx_EXPORTS`，第 2 条换成 `g++ -shared ... -o libx.so`。`-fPIC` 让代码能在进程里被搬到任意地址，`.so` 需要它；静态库不搬，所以不用。

`BUILD_SHARED_LIBS` 只决定“没写类型时用哪种”，不会覆盖显式写下的 `STATIC` 或 `SHARED`（[7.1 节](ch07.md)）。CMake 默认不定义这个变量，所以在全新的构建目录里不传 `-D` 时结果仍是静态库；同一个目录里已有的 `-D` 缓存项会留着，要用 `-U` 或改缓存才能回到静态库。工程若要提供开关，应在顶层、所有 `add_library()` 之前用 `option()` 建立缓存项。

配置页第 5 步设置 `VERSION 1.2.3` 和 `SOVERSION 1`，目标属性里立刻多了这两项。构建页第 2 条链接命令把 `-Wl,-soname,libx.so.1` 交给链接器，输出文件名是 `libx.so.1.2.3`；第 3 条 `cmake -E cmake_symlink_library` 建出两个符号链接，运行页的 `ls -l` 能看到 `libx.so -> libx.so.1`、`libx.so.1 -> libx.so.1.2.3`。

构建页第 5 条把 app 和 `libx.so.1.2.3` 连起来，链接器写进 ELF 的 `DT_NEEDED` 却是 SONAME `libx.so.1`；运行页的 `readelf -d` 能看到 app 的 `NEEDED` 和库文件的 `SONAME` 都是这一项。程序运行时找的是 `libx.so.1`，不是构建时看到的完整文件名；安装后的下游用 `-lx` 链接时找 `libx.so`，构建树里 CMake 直接把完整文件名写进链接命令。

{{#fig ch11/soname_links}}

`SOVERSION` 是运行时找库的依据：ABI 变了就把它加一，新程序找 `libx.so.2`，旧程序仍找 `libx.so.1`，两套库可以并存在同一台机器上。

```cmake
{{#include code/ch11/11_3_rpath/CMakeLists.txt}}
```
{{#sidefx ch11/11_3_rpath}}

这次没有 `VERSION`，`.so` 的 SONAME 就是 `libx.so`。构建页第 4 条链接 app 的命令里有 `-Wl,-rpath,/work/build`；运行页的 `readelf -d build/app` 里，`NEEDED` 是 `libx.so`，`RUNPATH` 是 `/work/build`，所以直接执行 `./build/app` 就能打印 `x=42`。

这条 rpath 是 CMake 自动加的：构建树里的程序要能找到构建树里的共享库。`readelf -d` 是 after 命令，看到的是链接完成后的 ELF，配置页里没有 rpath 的痕迹。`BUILD_RPATH` 属性可以在自动值之外再添目录；安装时这条构建树路径会被清掉，默认不会留下安装树路径，要指定安装树的路径得设置 `INSTALL_RPATH`（或 `CMAKE_INSTALL_RPATH`），见 [16.5 节](ch16.md)。

{{#fig ch11/shared_lookup}}

动态链接器的查找顺序不是“先看程序里的路径”：`LD_LIBRARY_PATH` 排在 `RUNPATH` 前面，两者都没命中，才查 `/etc/ld.so.cache` 和 `/lib`、`/usr/lib`。这也解释了为什么临时换一个库做实验时，设 `LD_LIBRARY_PATH` 能盖过程序自带的 `RUNPATH`。

{{#sidefx ch11/11_4_visibility}}

第一次运行的第 6 步只改了两个属性；第 7 步 `generate_export_header(x)` 才写出 `build/x_export.h`，文件栏里能看到它。头文件里 `X_EXPORT` 展开成 `__attribute__((visibility("default")))`，`X_NO_EXPORT` 是 `visibility("hidden")`；Linux 上“构建库”和“使用库”两个分支的值相同，Windows 上才是 `dllexport` 和 `dllimport` 的差别。这个头文件写在构建目录里，不在源码目录。

构建页第 1 条编译命令因此多了 `-fvisibility=hidden` 和 `-fvisibility-inlines-hidden`。前者把没标 `X_EXPORT` 的函数默认藏起来，后者专门处理 inline 函数生成的弱符号；运行页的 `nm -D --defined-only` 只剩一行 `T x_value`。

第二次运行把 `CMakeLists.txt` 换成 `v2/` 里的版本，只删掉 `set_target_properties` 那三行，`generate_export_header(x)` 还在。这次的第 6 步仍然执行 `generate_export_header(x)`，文件内容没变，文件栏不会标改写；构建页第 1 条不再有那两个 visibility 选项，`-Dx_EXPORTS`、两个 `-I`、`-fPIC` 都还在，`nm` 的结果变成三行：

| 运行 | `nm -D --defined-only` 里的符号 |
|---|---|
| 默认隐藏 | `T x_value` |
| 不隐藏 | `W _Z12detail_scalei`、`T x_extra`、`T x_value` |

`T` 是普通的已定义符号，`W` 是弱符号，来自那个 inline 函数。

`x_extra` 和 `detail_scale` 并不想给别人用，却都进了动态符号表。下游只要声明一下就能调用它们，链接器也不会拦；等你想改这两个函数的签名时，才发现已经有人依赖了。导出头加 hidden 可见性，就是先把“公开 API”画成一条线，线外的东西默认不导出。

```cmake
{{#include code/ch11/11_5_object_lib/CMakeLists.txt}}
```
{{#sidefx ch11/11_5_object_lib}}

配置页第 3 步建出的 `common` 是 `OBJECT_LIBRARY`，生成页里它的产物是 `CMakeFiles/common.dir/./common.cpp.o`，不是 `.a` 或 `.so`。构建页一共 5 条命令：第 1 条就编译出这个 `.o`，第 4、5 条链接 `app` 和 `tool` 时都直接带上它，所以源文件只编译了一次，两个程序各有一份对象代码。

对象库适合“同一批源文件要进多个目标”的场合，比如库和它的测试程序；`target_link_libraries()` 从 3.12 起可以直接链接它，用法要求照常传递，这里的 `include/` 目录就是通过 `common` 的 PUBLIC 包含目录传给两个程序的。它在同一个构建树里复用很方便；下游要一个能直接拿走的 `libcommon.a` 时，静态库更直接。只有头文件的库用 INTERFACE 类型，它连编译命令都不产生，见 [8.3 节](ch08.md)。

## 速查

| 写法 | 副作用发生在 | 注意 |
|---|---|---|
| `add_library(x src.cpp)` | 配置阶段定类型，构建阶段产出库文件 | 变量没定义时是 STATIC；想固定就写类型 |
| `-DBUILD_SHARED_LIBS=ON` | 下一次配置时改变默认类型 | 只影响没写类型的 `add_library()` |
| `VERSION 1.2.3`、`SOVERSION 1` | 生成阶段定 soname，构建阶段建符号链接 | `SOVERSION` 是 ABI 版本，不是补丁号 |
| `target_link_libraries(app PRIVATE x)` | 生成阶段写入 `-Wl,-rpath,...`，构建阶段写进 ELF | 安装后的 rpath 由 `INSTALL_RPATH` 决定（[16.5 节](ch16.md)） |
| `CXX_VISIBILITY_PRESET hidden` | 构建阶段的编译命令加 `-fvisibility=hidden` | 公开 API 要标 `X_EXPORT` |
| `generate_export_header(x)` | 配置阶段写出 `build/x_export.h` | 安装时要和公开头文件一起装出去（[第 16 章](ch16.md)） |
| `add_library(o OBJECT ...)` | 构建阶段只编译一次，对象文件进各个消费者 | 没有 `.a`/`.so` 产物 |

## 思考题

1. 把 `11_1` 的 `add_library(x src.cpp)` 改成 `add_library(x STATIC src.cpp)`，再分别用 `-DBUILD_SHARED_LIBS=OFF` 和 `ON` 配置，目标类型和产物会变吗？
   <details><summary>提示</summary>显式写下的类型优先；变量只给没写类型的 `add_library()` 用。</details>
2. 把 `11_2_soversion` 的 `SOVERSION` 改成 2、`VERSION` 改成 2.0.0，重新构建后 `libx.so` 和 `libx.so.2` 各指向哪个文件？旧 app 的 `DT_NEEDED` 会跟着变吗？
   <details><summary>提示</summary>SONAME 在链接时写进 ELF；已经链接好的旧程序不会因为换了库文件而改自己的 `DT_NEEDED`。</details>
3. 在 `11_4_visibility` 里给 `x_extra` 也加上 `X_EXPORT`，`nm -D --defined-only` 会多出哪一行？如果把 `VISIBILITY_INLINES_HIDDEN` 关掉，`detail_scale` 会回来吗？
   <details><summary>提示</summary>先分清 `T` 和 `W`；inline 符号同时受 `-fvisibility` 和 `-fvisibility-inlines-hidden` 影响。</details>
4. `11_5_object_lib` 如果改成 `add_library(common STATIC common.cpp)`，构建页会多出哪条命令、少掉什么？要把 `common` 安装给别人用时，哪种类型更方便？
   <details><summary>提示</summary>静态库会多一条 `ar` 命令，但只产出一个 `libcommon.a`；对象库没有可安装的库文件。</details>
