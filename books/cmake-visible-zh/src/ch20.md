# 第 20 章 预设：CMakePresets.json

用户的项目里有一排 preset：`debug`、`release`、`asan-ubsan`、`tsan`、`coverage`。每个都对应一条以前要手敲很长的 `cmake` 命令。预设（preset）只是把这些参数写进一个 JSON 文件吗？

打开 20.1 的配置页，先别看第 1 步。缓存面板里已经有 `CMAKE_BUILD_TYPE=Debug`、`PROJ_OPT_LEVEL=0`、`PROJ_WARNINGS=TRUE` 三项；它们不是 `CMakeLists.txt` 写的，查看器里也没有 `-D`。preset 在 CMake 读第一行之前，就把这些值以 `-D` 的形式放进了缓存，只是查看器只显示手敲的 argv，不显示展开的 `-D`；缓存项的帮助于是写着 `No help, variable specified on the command line`。

`base` 是 `hidden`：它自己不能用 `--preset base` 启动，只负责给别的预设当父预设；在示例目录执行 `cmake --list-presets`，只会看到 `debug` 和 `release`。`binaryDir` 里的 `${presetName}` 在选用预设时换成 `debug` 或 `release`，用 `${sourceParentDir}` 让它落在源码目录旁边而不是里面。`generator` 只在 `base` 写一次，`debug` 和 `release` 只写自己不同的缓存项，构建目录因此各有一份。

运行 1 的命令行是 `cmake -S src -B build/debug -G Ninja --preset debug`。第 3 步 `message()` 打印 `config=Debug level=0 warn=TRUE`，说明 `debug` 从 `base` 继承了全部三项；第 5 步 `target_compile_definitions()` 把前两项写进 `app` 的 `COMPILE_DEFINITIONS`；第 6 步 `if(PROJ_WARNINGS)` 判断为真，第 7 步 `target_compile_options()` 再把 `-Wall -Wextra` 加进编译选项，生成页里两个 `-D` 后面标着来自第 5 步这一行。运行 2 的缓存换成了 `Release` 和 `3`，编译命令里多了 `-O3 -DNDEBUG`（`CMAKE_BUILD_TYPE` 的作用见 [10.3 节](ch10.md)）。

| 运行 | 命令行 | 第 1 步之前的 `PROJ_OPT_LEVEL` | 运行页 |
|---|---|---|---|
| 1 | `--preset debug` | `0` | `config=Debug opt=0` |
| 2 | `--preset release` | `3` | `config=Release opt=3` |
| 3 | `--preset debug -DPROJ_OPT_LEVEL=7` | `7` | `config=Debug opt=7` |

运行 3 在 `--preset` 后面又加了 `-D`。preset 给 `PROJ_OPT_LEVEL` 的值是 0，命令行的 `-D` 把它改成 7；第 3 步打印 `level=7`，构建命令里的宏也跟着变。所以 preset 更像一组默认参数，不是不可覆盖的配置。

`asan` 的 `inherits` 是数组：先 `debug`，再 `strict`。前两项来自 `base`：`CMAKE_BUILD_TYPE=Debug` 和 `PROJ_WARNINGS`；`strict` 补上 `PROJ_WERROR=ON`，`asan` 自己再加 `PROJ_SANITIZE=address;undefined`。打开配置页，第 1 步之前这四项已经在缓存里；多个父预设冲突时，`inherits` 数组里靠前的优先。

第 3 步 `message()` 打印 `label=asan-team42`。`environment` 里的 `PROJ_STAGE` 先定义，`PROJ_LABEL` 用 `$env{PROJ_STAGE}` 引用同一个预设里的值，用 `$penv{TEAM_TAG}` 取父进程的 `TEAM_TAG`；`$env{}` 会先看 `environment` 字段，`$penv{}` 只看外面。这个 label 在第 6 步被 `configure_file()` 写进 `preset_info.h`，运行页最后打印出来；配置预设的 `environment` 直接作用于配置过程，构建、测试和打包预设默认继承关联配置预设的环境（`inheritConfigureEnvironment` 默认 true），但它仍不会自动变成程序运行时的环境。

`if(PROJ_SANITIZE)` 在第 13 步判断为真，第 14 步 `string(REPLACE ...)` 把 `address;undefined` 换成 `address,undefined`，第 15、16 步分别加进编译和链接选项。构建页两条命令里都有 `-fsanitize=address,undefined`；完整的 sanitizer 模块留给 [第 21 章](ch21.md)。`msan` 的 `condition` 比较 `${hostSystemName}` 和 `Windows`，在 Linux 上不启用，运行页里的 `cmake -S src --list-presets` 只列出 `"debug"` 和 `"asan"`。

运行 1 只配置；运行页里再执行 `cmake -E chdir src cmake --workflow --preset ci`（示例工程在 `src/` 下，先切进去）。输出分成三段，开头的 `Executing workflow step 1 of 3: configure preset "ci"`、`step 2 ... build preset`、`step 3 ... test preset` 就是 workflow 的三步。构建那段从 `[1/6]` 到 `[6/6]`，测试那段是 `1/1 Test #1: greet ... Passed` 和 `100% tests passed`。

workflow 预设的 `steps` 第一项必须是 configure，后面每项必须是 build、test 或 package，而且关联的 `configurePreset` 要和第一项相同。所以 `buildPresets` 和 `testPresets` 里都写 `configurePreset: "ci"`。三处同名的 `ci` 不冲突：配置、构建、测试预设各有各的命名空间。

`cmake --workflow --preset ci` 没有新的构建逻辑：它相当于按 `steps` 依次执行 `cmake --preset ci`、`cmake --build --preset ci`、`ctest --preset ci`，每一步的输出原样接在一起。`buildPresets` 里的 `jobs: 2` 等于 `cmake --build -j 2`，`testPresets` 里的 `outputOnFailure` 等于 `ctest --output-on-failure`。

| 种类 | 文件里的数组 | 用哪条命令 | 关键字段 |
|---|---|---|---|
| 配置 | `configurePresets` | `cmake --preset ci` | `generator`、`binaryDir`、`cacheVariables` |
| 构建 | `buildPresets` | `cmake --build --preset ci` | `configurePreset`、`targets`、`jobs` |
| 测试 | `testPresets` | `ctest --preset ci` | `configurePreset`、`filter`、`output` |
| 打包 | `packagePresets` | `cpack --preset ci` | `configurePreset`、`generators` |
| 工作流 | `workflowPresets` | `cmake --workflow --preset ci` | `steps` |

`steps` 里不能再嵌套一个 workflow，也不能从 build 或 test 开始，每次 workflow 都先配置；`workflowPresets` 从文件版本 6（CMake 3.25）起才有。想跳过配置，就直接用 `cmake --build --preset ci` 和 `ctest --preset ci`；只想看有哪些 workflow，执行 `cmake --list-presets=workflow`。`--fresh` 会先丢掉缓存再执行第一步，第一步等价于 `cmake --fresh --preset ci`。

## 20.4 CMakeUserPresets.json 和团队约定

项目文件 `CMakePresets.json` 进版本库，个人文件 `CMakeUserPresets.json` 留在本机。CMake 会读工程根目录（源码目录）下这两个文件，用户文件自动包含项目文件，不需要写 `include`；项目文件里的预设不能继承用户文件里的预设。`include` 字段从版本 4（CMake 3.23）起才有，可以把共享片段拆到别的 JSON 文件里。

```json
{
  "version": 6,
  "configurePresets": [
    {
      "name": "local-asan",
      "inherits": "asan",
      "binaryDir": "${sourceDir}/build/local-asan"
    }
  ]
}
```

这个文件只加一个 `local-asan`，继承项目里的 `asan`，再覆盖 `binaryDir`。别人拉下代码看不到它；它引用的 `asan` 仍然来自项目文件。反过来，项目文件里的预设不能继承 `local-asan`，个人预设不会进入团队的继承链。

`include` 里的相对路径按当前文件算，可以多层包含，但不能成环。项目文件直接或间接包含的文件应当由项目提供；用户文件可以包含任意位置的文件。被包含文件里的预设，可以被包含它的文件继承。

| 文件或字段 | 提交？ | 用途 | 约束 |
|---|---|---|---|
| `CMakePresets.json` | 提交 | 团队共用的配置、构建、测试、工作流 | 只能继承本文件或它 `include` 的文件里的预设 |
| `CMakeUserPresets.json` | 不提交 | 本机的编译器、路径、个人开关 | 可以继承项目文件里的预设；自动包含项目文件 |
| `include` | 视被包含文件 | 把共享片段拆成多个文件 | 版本 4 起；不能形成包含环 |
| 被项目 `include` 的文件 | 通常提交 | 平台或组件的公共片段 | 应保证项目里能找到 |

{{#fig ch20/preset_files}}

团队约定可以压成四句：项目文件只放人人相同的预设；机器相关的路径和开关放用户文件，并把用户文件加进 `.gitignore`；平台差异用 `condition`，不要复制整份预设；共享片段用 `include` 拆开。CI 和本地都跑同一组预设，CI 的入口就是 `cmake --workflow --preset ci`，两边少一层差异。

预设文件不声明目标，也不直接生成构建规则，它只在配置开始前摆好缓存、生成器、构建目录和环境。编译选项通常仍写在 `CMakeLists.txt` 里（`cacheVariables` 可以塞 `CMAKE_CXX_FLAGS`，但那样就把选项放到了 CMakeLists 的条件之外）；`${sourceDir}` 这些宏在选用预设时展开，不会传进 CMakeLists。

项目文件里不要写死 `/home/…` 这样的路径，用 `${sourceDir}`、`${sourceParentDir}`、`${presetName}` 这些宏，换一台机器仍然成立。`binaryDir` 也一样，写 `${sourceDir}/build` 或 `${sourceParentDir}/build`，不要写死某个人的主目录。`CMakeUserPresets.json` 只给自己用，可以写绝对路径；它自动包含项目文件，但同类预设不能两边同名。

## 速查

| 写法 | 副作用发生在 | 注意 |
|---|---|---|
| `cmake --preset debug` | 读第一行之前写缓存、选生成器和构建目录 | 命令行再给 `-D` 会覆盖 preset 的值 |
| `hidden: true` | 不列出、不能直接启动 | 只当父预设；可以不写 `generator`、`binaryDir` |
| `inherits` | 合并父预设的字段和 `cacheVariables` | 数组里靠前的优先；冲突时不会自动报错 |
| `condition` | 不满足时预设不出现 | 版本 3 起；常用 `${hostSystemName}` |
| `environment` + `$env{}` / `$penv{}` | 配置过程，以及默认继承它的构建/测试/打包过程 | `$env{}` 先看本预设，`$penv{}` 只看父进程；`inheritConfigureEnvironment` 默认 true |
| `workflowPresets` | 依次跑配置、构建、测试、打包 | 版本 6 起；第一步必须是 configure |

## 思考题

1. 在 20.1 里给 `debug` 加一条 `"PROJ_OPT_LEVEL": "9"`，再运行 `cmake --preset debug`。第 1 步之前的缓存里这个值是多少，`base` 里的 `"0"` 去哪了？
   <details><summary>提示</summary>子预设自己的字段覆盖父预设；缓存里只会留下一个值。</details>
2. 把 20.2 的 `asan` 改成 `"inherits": ["strict", "debug"]`，缓存和编译选项会怎样变？有没有哪一项因此消失？
   <details><summary>提示</summary>两项并不冲突，取并集；顺序只在同一个字段被两个父预设同时定义时才起作用。</details>
3. 在 20.3 的 `buildPresets` 里加 `"targets": ["app"]`，workflow 的第二步还会构建 `test_greet` 吗？测试那一步会报什么？
   <details><summary>提示</summary>构建预设只构建指定目标，测试预设仍会去找 `test_greet`。</details>
4. 同事把 `CMakeUserPresets.json` 提交进了仓库，会发生什么？如果项目文件想继承他的个人预设，CMake 会允许吗？
   <details><summary>提示</summary>项目文件不能继承用户文件里的预设；用户文件应当被忽略。</details>
