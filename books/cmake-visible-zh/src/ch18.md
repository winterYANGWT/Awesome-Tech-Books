# 第 18 章 证明它能用：安装后消费测试

用户项目评审的第 2 条是：“install 契约写得很全，但没有任何东西真正验证它能用。” [17.5 节](ch17.md) 已经手动装过一次、手动配过一次下游；把这两步交给一个只认安装前缀的工程，缺口才会露出来。

安装树和源码树是两套路径。消费测试让一个独立工程只拿着前缀去找包；它如果还要回头 `include` 源码，就不算验证。

第三个测试的 `cmake --build … --target run` 先构建 app，再执行它的 `run` 目标；`PASS_REGULAR_EXPRESSION` 要求输出里有 `hello, installed package!`。ctest 只看这段输出，进程退出码被忽略：最后一个 `Passed` 的通过条件是输出匹配。

运行页的改动文件同时列出 `build/consumer/app` 和 `build/prefix/lib/cmake/Greet/GreetConfig.cmake`；配置、构建、安装都确实发生过。前缀在构建目录里，不依赖系统里是否装过 Greet；换一台机器，这个测试仍然从零开始装。CTest 本身在 [第 19 章](ch19.md) 展开；这里只用它的 fixture、测试属性，以及 `--output-on-failure`、`-V` 这样的输出开关。

## 18.3 常见的坏法

消费测试能抓住的几类问题先列在表里，“谁发现”是第一次报错的位置。

| 坏法 | 谁发现 | 现象 |
|---|---|---|
| 导出目标只写 `$<BUILD_INTERFACE:…>` | 下游编译 | 不偷源码时找不到 `greet/greet.h`（18.1） |
| 头文件没有 `install(FILES/DIRECTORY)` | CMake 生成 | `includes non-existent path`（18_3_missing_header） |
| 导出接口带构建树绝对路径 | CMake 生成 | `prefixed in the build directory`（18_3_absolute_include） |
| Config 漏 `find_dependency` | 下游生成 | 链接接口里的目标不存在（[17.3 节](ch17.md)） |
| 版本文件的兼容策略不符 | 下游 `find_package` | 找不到兼容版本（18.4） |
| 下游偷 `include` 源码树 | 不一定报错 | 安装树坏了也“通过”（18.1） |

前两行都属于“只在构建树里成立”：源码树里编得过，安装树里没有对应的头文件或包含目录。第三行更直接，导出的接口把本机的构建路径写死了。

“只写 BUILD_INTERFACE”已经在 18.1 看到。忘了装头文件更早被抓住，不用等编译：

{{#sidefx ch18/18_3_missing_header}}

运行 1 的安装输出里只有 `libgreet.a` 和四份 `.cmake`，没有 `include/`。运行 2 走完 `find_package`、创建导入目标，配置结束进入生成阶段时 CMake 报 `Imported target "Greet::greet" includes non-existent path "/work/prefix/include"`，指向 `INTERFACE_INCLUDE_DIRECTORIES`。

导出接口里的绝对路径也是生成阶段报错。下面这个 greet 把构建目录里的 `generated/` 直接写进了 PUBLIC：

```cmake
{{#include code/ch18/18_3_absolute_include/CMakeLists.txt}}
```
{{#sidefx ch18/18_3_absolute_include}}

第 4 步的目标属性里，`INTERFACE_INCLUDE_DIRECTORIES` 是 `$<BUILD_INTERFACE:…>;/work/build/generated`；第 7 步 `install(EXPORT …)` 登记完，配置结束的输出里有 `Target "greet" INTERFACE_INCLUDE_DIRECTORIES property contains path` 和 `which is prefixed in the build directory`。

修法是构建树里的目录只放进 `$<BUILD_INTERFACE:…>`，安装后要用的目录放进 `$<INSTALL_INTERFACE:…>`（生成的头文件也得先 install）；导出的接口里不能出现 `/work/build` 或 `/work/src` 这样的本机路径。

17.3 的漏 `find_dependency` 是另一类：`find_package` 能成功，生成阶段才报“目标不存在”。表里的几类问题都不该靠人工记得，应该各有一个反例测试，或者至少有一条能重复执行的消费测试。

## 18.4 版本兼容检查

`write_basic_package_version_file(... COMPATIBILITY SameMajorVersion)` 在配置阶段写出版本文件；`find_package` 每次都会读它，请求了版本时才用它判断兼容性。18_4 的 greet 声明 `VERSION 1.2.0`，app 先请求 1.0，再换成 2.0：

`SameMajorVersion` 要求主版本相同，并且包不比请求的版本旧；2.0 会被拒。`SameMinorVersion` 连次版本也要相同；选哪种由包的作者决定，版本文件只把这个决定变成可执行的比较。

`app/v2/CMakeLists.txt`：

```cmake
{{#include code/ch18/18_4_version_compat/app/v2/CMakeLists.txt}}
```
{{#sidefx ch18/18_4_version_compat}}

运行 1 第 13 步写出的 `GreetConfigVersion.cmake` 里，`SameMajorVersion` 在包不比请求旧时，主版本相同就放行。运行 2 第 11 步判断 `PACKAGE_FIND_VERSION_MAJOR` 和 `CVF_VERSION_MAJOR` 都是 1，第 12 步把 `PACKAGE_VERSION_COMPATIBLE` 置为 `TRUE`，下游被接受。

运行 3 第 5 步的 `VERSION_LESS` 判断 1.2.0 小于请求的 2.0，第 6 步把 `PACKAGE_VERSION_COMPATIBLE` 置为 `FALSE`；第 8 步之后，`find_package` 报 `Could not find a configuration file for package "Greet" that is compatible with requested version "2.0"`，并列出考虑过的 `/work/prefix/lib/cmake/Greet/GreetConfig.cmake, version: 1.2.0`。

| 下游请求 | 版本文件里的判断 | `PACKAGE_VERSION_COMPATIBLE` | 结果 |
|---|---|---|---|
| 1.0 | 主版本都是 1 | `TRUE` | 接受 |
| 2.0 | 1.2.0 小于 2.0 | `FALSE` | 拒绝 |

版本文件不检查 API 是否真的变了，它只执行你写下的兼容策略。消费测试要固定的是“这个策略在安装后的下游会怎么表现”，不是“版本号写对了”。

如果下游只写 `find_package(Greet)`、不带版本，版本文件仍会读，但不会因兼容性拦住它；兼容性检查只在请求里写了版本时才有意义。

## 速查

| 写法 | 副作用发生在 | 注意 |
|---|---|---|
| `add_test(NAME … COMMAND ${CMAKE_COMMAND} --install …)` | ctest 运行时 | 测试是一条普通进程；默认退出码非 0 就算失败 |
| `FIXTURES_SETUP` / `FIXTURES_REQUIRED` | ctest 调度时 | setup 先跑；`-j` 下也保持这个顺序 |
| `-DCMAKE_PREFIX_PATH=…` | 下游配置 | 只给前缀，不给 `<名字>_DIR`，才像外部用户 |
| `PASS_REGULAR_EXPRESSION` | ctest 判分时 | 只要输出匹配就算通过，进程退出码被忽略 |
| `write_basic_package_version_file(… COMPATIBILITY …)` | 配置阶段 | 下游无论是否请求版本都会读版本文件；只有请求了版本，兼容性判定才会拒绝包 |

## 思考题

1. 18.2 去掉三个测试的 fixture 属性，再用 `ctest -j 4` 跑。哪个测试可能先跑，会看到什么错误？
   <details><summary>提示</summary>顺序不再保证；配置测试若先于安装，`find_package(Greet)` 找不到 `GreetConfig.cmake`；构建测试若先于配置，会找不到 `build/consumer/CMakeCache.txt`。</details>
2. 18.1 的 greet 补上 `$<INSTALL_INTERFACE:include>`，再删掉 app 的 `include_directories`。生成页和构建页会各多出什么？
   <details><summary>提示</summary>导入目标多出 `INTERFACE_INCLUDE_DIRECTORIES`；app 的编译命令从 `-I 源码树` 变成 `-isystem /work/prefix/include`，构建通过。</details>
3. 18.3 把 `${CMAKE_CURRENT_BINARY_DIR}/generated` 换成 `${CMAKE_CURRENT_SOURCE_DIR}/include`，报错的最后一句会怎么变？
   <details><summary>提示</summary>从 `prefixed in the build directory` 变成 `prefixed in the source directory`；CMake 两个前缀都检查。</details>
4. 18.4 把 `SameMajorVersion` 改成 `ExactVersion`，运行 2 的 `find_package(Greet 1.0)` 还会通过吗？
   <details><summary>提示</summary>`ExactVersion` 要求请求版本和包版本完全一致；1.0 被拒，只有请求 1.2.0 才通过。</details>
