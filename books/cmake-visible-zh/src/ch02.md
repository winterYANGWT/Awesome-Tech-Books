# 第 2 章 project() 做了什么

[第 1 章](ch01.md)的最小工程里，`project()` 只占一行，查看器却在第 2 步记下 300 多个变量、59 个缓存项和 6199 条模块命令。它到底做了什么？

## 2.1 第一次 project()：检测编译器

```cmake
{{#include code/ch02/2_1_project/CMakeLists.txt}}
```
{{#sidefx ch02/2_1_project}}

第 2 步 `project()` 停下时，变量栏多了 300 多个变量，缓存栏多了 59 个缓存项，“文件”一栏在 `CMakeFiles/` 下多了 6 个文件。这个工程只写了 `project(Probe LANGUAGES CXX)`，那 6199 条命令是 CMake 自带模块在 `project()` 里执行的，不是 `CMakeLists.txt` 里的下一行。

{{#fig ch02/project_steps}}

第 3 步把缓存里的几个值打印了出来：`CMAKE_CXX_COMPILER` 是 `/usr/bin/g++`，`CMAKE_AR` 是 `/usr/bin/ar`，`CMAKE_BUILD_TYPE` 是空的，`CMAKE_INSTALL_PREFIX` 是 `/usr/local`。这些值都能在“缓存”栏里逐个点开，类型分别是 `FILEPATH`、`FILEPATH`、`STRING`、`PATH`。

检测结果落在 `CMakeFiles/4.2.3/` 里。文件栏里点开 `build/CMakeFiles/4.2.3/CMakeCXXCompiler.cmake`，能看到 `CMAKE_CXX_COMPILER_ID` 是 `GNU`、`CMAKE_CXX_COMPILER_VERSION` 是 `15.2.0`、`CMAKE_CXX_STANDARD_COMPUTED_DEFAULT` 是 `17`、`CMAKE_CXX_SIZEOF_DATA_PTR` 是 `8`；`CMakeSystem.cmake` 里则是 `CMAKE_SYSTEM_NAME` 为 `Linux`、`CMAKE_SYSTEM_PROCESSOR` 为 `x86_64`、`CMAKE_CROSSCOMPILING` 为 `FALSE`。

| 类别 | 例子（本机值） | 在哪看 |
|---|---|---|
| 编译器 | `CMAKE_CXX_COMPILER=/usr/bin/g++`、`CMAKE_AR=/usr/bin/ar` | 缓存、`CMakeCXXCompiler.cmake` |
| 平台 | `CMAKE_SYSTEM_NAME=Linux`、`CMAKE_SYSTEM_PROCESSOR=x86_64` | `CMakeSystem.cmake` |
| 工具 | `CMAKE_MAKE_PROGRAM`、`CMAKE_LINKER=/usr/bin/ld` | 缓存 |
| 构建类型 | `CMAKE_BUILD_TYPE` 为空 | 缓存 |
| 安装 | `CMAKE_INSTALL_PREFIX=/usr/local` | 缓存 |
| 项目 | `PROJECT_NAME=Probe`、`Probe_SOURCE_DIR=/work/src` | 变量栏、缓存 |

`CMAKE_BUILD_TYPE` 为空，是因为 Ninja 是单配置生成器；构建类型和它的编译参数在第 10 章展开。`CMAKE_INSTALL_PREFIX` 是这台 Linux 上的默认值，安装规则怎么用它放在第 16 章。

`CompilerIdCXX/` 里的 `CMakeCXXCompilerId.cpp` 就是那个检测程序的源文件，`a.out` 是编出来的结果；同一个编译器下一次配置不再需要它们，直接从 `CMakeCXXCompiler.cmake` 读回结果。

缓存和普通变量要分开看：`CMAKE_CXX_COMPILER`、`CMAKE_AR` 在缓存里，`PROJECT_NAME`、`PROJECT_SOURCE_DIR` 在变量栏里。前者下一次配置还能读回，后者每次配置由 `project()` 重新算。

缓存栏里 `Demo_SOURCE_DIR`、`Demo_BINARY_DIR`、`Demo_IS_TOP_LEVEL` 的类型都是 `STATIC`，`Sub_*` 那三项也一样；`PROJECT_*` 和 `Demo_VERSION` 是普通变量，不进缓存。`PROJECT_IS_TOP_LEVEL` 和 `<名字>_IS_TOP_LEVEL` 从 3.21 起才有。`CMAKE_PROJECT_NAME` 由顶层 `CMakeLists.txt` 里的 `project()` 定下，子目录改不了它；没有第二次 `project()` 时，`PROJECT_NAME` 也会继承父目录的值。

{{#fig ch02/two_projects}}

{{#figref ch02/two_projects}}画的是这两层作用域：`PROJECT_*` 在子目录里被第二个 `project()` 覆盖，返回时恢复；`CMAKE_PROJECT_NAME` 只在顶层那次 `project()` 定下，子目录读到的一直是 `Demo`。目录作用域怎么复制、怎么销毁，第 4 章会拆开讲。

第一次运行的第 2 步 `project(NoLang LANGUAGES NONE)` 只有 195 条模块命令，新增 72 个内置变量、18 个缓存项，没有编译器检测。第 5 步 `enable_language(CXX)` 才执行 6005 条模块命令，文件栏这时多出 4 个新文件（`CMakeCXXCompiler.cmake`、`CompilerIdCXX/` 等），`CMakeConfigureLog.yaml` 也被改写；第 6 步打印出的 `CMAKE_CXX_COMPILER` 是 `/usr/bin/g++`。

第二次运行先删掉构建目录，再换成 `project(Default)`，没写 `LANGUAGES`。第 2 步的 12021 条命令和 10 个新文件里，C 和 CXX 两套检测都在：`CMakeCCompiler.cmake` 与 `CMakeCXXCompiler.cmake` 同时出现。`project(X)` 默认同时启用 C 和 CXX，不是只启用 CXX。

| 时刻 | 启用的语言 | 模块命令 | 文件变化 |
|---|---|---|---|
| `project(... NONE)`，第 2 步 | 无 | 195 | 2 个新文件：`CMakeSystem.cmake`、`CMakeConfigureLog.yaml` |
| `enable_language(CXX)`，第 5 步 | CXX | 6005 | 4 个新文件，外加被改写的 `CMakeConfigureLog.yaml` |
| `project(Default)`，第 2 步 | C、CXX | 12021 | 两套编译器文件，共 10 个 |

`enable_language()` 和 `project()` 一样会检测语言，但不会创建 `PROJECT_*` 变量。文档还要求它在文件作用域里调用、不能在第一次 `project()` 之前调用，并且要在用到这门语言的所有目标的最高公共目录里调用。

需要按条件启用语言时，`enable_language()` 才有意义；如果一开始就知道要 C 和 CXX，直接写在 `project()` 的 `LANGUAGES` 里更短，也让检测集中在一处。

## 2.4 第二次配置为什么快

```cmake
{{#include code/ch02/2_4_reconfigure/CMakeLists.txt}}
```
{{#sidefx ch02/2_4_reconfigure}}

第一次运行的第 2 步是 6199 条模块命令；第二次在同一个构建目录里再配置，第 2 步只有 701 条。缓存栏没有新增项，`CMakeFiles/4.2.3/` 也没有新文件：`project()` 直接从上次的检测结果里读回了编译器、ABI 和编译特性。

第二次构建是 0 条命令，`app` 没有重新编译。第三次点“从头再来”，构建目录被删掉，6199 条模块命令、59 个缓存项和 6 个 `CMakeFiles/` 下的文件又都回来了。

| 运行 | 第 2 步模块命令 | 缓存新增 | `CMakeFiles/` 下新文件 | 构建命令 |
|---|---|---|---|---|
| 第一次 | 6199 | 59 | 6 | 2 |
| 第二次，同一个构建目录 | 701 | 0 | 0 | 0 |
| 第三次，`fresh` | 6199 | 59 | 6 | 2 |

第二次不是零：`project()` 仍要设置变量、读缓存，只是跳过了编译检测程序这一大块。编译器路径、版本和 ABI 都在构建目录里，删掉构建目录就等于把这些结果一起删掉，所以“从头再来”会回到第一次的样子。

第二次配置仍然会重新生成 `build.ninja`，所以生成页不是空的；省掉的是检测，不是生成。

## 2.5 project() 之前能做什么

`2_5_before_project` 的 `CMakeLists.txt` 和 2.4 的只差工程名（`Switch`）；两次运行的差别在命令行。

{{#sidefx ch02/2_5_before_project}}

第一次运行的第 2 步是 GNU 15.2.0，构建页用 `/usr/bin/g++`；第二次先删掉构建目录，再在命令行给 `-DCMAKE_CXX_COMPILER=clang++`，第 2 步换成 Clang 21.1.8，构建页每条命令都改用 `/usr/bin/clang++`，运行页打印 `clang`。

`CMAKE_CXX_COMPILER` 在第一次 `project()` 启用语言时定下来，文档说一旦设置就不能再改。所以换编译器要放在第一次 `project()` 之前，最好走命令行或工具链文件；工程里在 `project()` 之后 `set()` 它已经晚了。工具链文件在第一次 `project()` 里读，可能被 `try_compile()` 再读一次，第 22 章专门讲。

`cmake_minimum_required()` 必须放在最前面，文档的原话是 even before `project()`。它先把策略版本定下来；`VERSION 3.25...4.2` 里的两个版本号就是最低版本和策略版本，写成单个版本会改变策略范围，第 23 章会看到具体差别。

| 想做的事 | 放在哪里 | 注意 |
|---|---|---|
| 定最低版本和策略 | 文件第一行 `cmake_minimum_required()` | 要在 `project()` 之前 |
| 换编译器 | 命令行 `-DCMAKE_CXX_COMPILER=…` 或工具链文件 | 第一次 `project()` 之前；一旦设置不能再改 |
| 一次性注入 | `CMAKE_PROJECT_TOP_LEVEL_INCLUDES`（3.24 起） | 在第一次 `project()` 里、工具链文件之后、启用语言之前执行 |
| 设 C++ 标准等初值 | `project()` 前后都可以 | 只要在创建目标之前，`add_*()` 时才复制成目标属性（第 7 章） |

`CMAKE_PROJECT_TOP_LEVEL_INCLUDES` 列出的文件在 `project()` 内部执行，适合做一次性的环境准备；它不替代工具链文件。`CMAKE_CXX_STANDARD` 这类变量不依赖 `project()`，但写在 `add_executable()` 后面就只影响之后创建的目标。

## 速查

| 写法 | 副作用发生在 | 注意 |
|---|---|---|
| `project(名字 VERSION … LANGUAGES CXX)` | 第 2 步：设 `PROJECT_*`、检测编译器、写 `CMakeFiles/<版本>/`、写缓存 | 第一次调用做检测，之后读结果 |
| `project(名字 LANGUAGES NONE)` | 只设项目变量和系统信息 | 不检测任何编译器 |
| `enable_language(CXX)` | 调用这一步才检测并写 `CMakeCXXCompiler.cmake` | 不能在函数里、不能在第一次 `project()` 前 |
| `cmake --fresh -B build` | 丢掉旧缓存，重新检测 | 3.24 起 |
| `-DCMAKE_CXX_COMPILER=clang++` | 第一次 `project()` 时按这个编译器检测 | 最稳妥是新构建目录或 `fresh`；设过就不能改 |
| `CMAKE_PROJECT_TOP_LEVEL_INCLUDES` | 第一次 `project()` 内部、启用语言前 | 3.24 起；不是工具链文件的替代品 |

   <details><summary>提示</summary>CMake 发现编译器变量和缓存不一致，会提示需要删除缓存并重新配置；旧构建目录里的检测结果不能混用。</details>
