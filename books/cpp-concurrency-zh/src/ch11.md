# 第 11 章 C++ 内存模型：数据竞争为什么是未定义行为

两个线程各对同一个 `uint64_t` 加 100 万次，最后通常不是 2000000。ThreadSanitizer 报的是 `data race`，不是“少加了几次”。

这两个说法差别很大：前者是症状，后者是诊断。数据竞争一旦成立，程序的行为就不再是“某个值算错了”，而是整段执行失去定义。

## 11.1 丢失更新只是症状，数据竞争才是诊断

C++ 对数据竞争的定义有四个条件，缺一不可：

| 条件 | 含义 | 本例 |
|---|---|---|
| 同一内存位置 | 两次访问落在同一块存储上 | 两个线程都访问 `counter` |
| 至少一个写 | 读—读不构成竞争 | 两个 `++` 都要写回 |
| 至少一个非原子 | 两个都是原子操作就不算 | `uint64_t` 的 `++` 不是原子操作 |
| 没有先行发生关系 | 两次访问之间没有 happens-before 边 | 两个线程之间没有任何同步 |

四条都满足时，标准直接规定行为未定义，定义在 `[intro.races]`。这不是“读到了旧值”那么轻：编译器可以假设数据竞争不存在，并据此改变生成的代码。其中“没有先行发生关系”最容易被忽略：它不是说两次访问在时间上隔得远，而是说语言里找不到一条从一次访问通到另一次访问的边。

`counter++` 看起来是一条语句，实际至少是三个操作：

1. 把 `counter` 读进寄存器；
2. 在寄存器里加一；
3. 把结果写回 `counter`。

两个线程的读和写交错时，后写的会覆盖先写的，这就是丢失更新。交错过程在第 4 章已经画过；这里要强调的是，丢失更新只是数据竞争最常见的一种表现，不是它的全部。

{{#fig ch11/ub_cone}}

未定义行为不等于“每次结果都错”：

- 程序可能碰巧输出 2000000；
- 也可能换编译器、换优化级别、换机器后崩溃；
- 编译器还可以假设竞争不存在，把值留在寄存器里，或者把不相干的读写重排。

所以“跑通一次”不能作为正确性证据。读 TSan 报告时，先看两条栈，再看它们访问的地址和访问类型，最后问：这两个访问之间，本该有哪条同步边？

修法不是在报告行上随手加一把锁，而是找到保护这个对象的同步设施。`counter` 是共享累加器，就该由一把锁或一个原子对象保护；如果每个线程只写自己的结果槽，最后在 `join` 之后合并，就不存在对同一位置的并发写。

`results[0]` 和 `results[1]` 是不同的内存位置，两个线程各写各的，不需要同步。

- 构造完成与新线程开始执行同步；
- 线程函数看到的是构造之前已经写好的数据，不需要额外加锁。

## 11.2 对象、内存位置和位域：什么算“同一位置”

对象是一块存储区域；内存位置（memory location）是标准用来判断竞争的更小单位。非位域的标量对象各占一个内存位置，相邻的非零宽位域合起来算一个。

换成两个 `int` 成员后，TSan 没有报告。`a` 和 `b` 是两个内存位置，两个线程各写各的，不需要同步。它们可能落在同一条缓存行上，写起来会互相拖慢，这是伪共享，属于性能问题，不是正确性问题，第 18 章再展开。

数组的每个元素是独立的内存位置；`std::vector<int>` 这类标量元素容器也一样（`vector<bool>` 是位压缩特例，不适用）。两个线程分别写 `v[0]` 和 `v[1]` 不需要同步，前提是 `v` 本身不再被扩容或重新分配。

`std::string` 要看清访问的是哪一个对象：

- 对象本身的状态（指针、长度、容量）在 `std::string` 对象里；
- 字符存储是另一个对象：短字符串可能在对象内部，长字符串另行分配；
- 一个线程改字符内容、另一个线程改对象状态（例如 `push_back`），仍然可能竞争。

零宽位域用来分隔相邻位域，必须写成无名的形式：

```cpp
struct Bits {
    unsigned bf1 : 3;
    int : 0;          // 正确：无名零宽位域，让下一个位域从新的分配单元开始
    unsigned bf3 : 3;
};
```

| 第一步：同一内存位置？ | 第二步：有先行发生关系？ | 结论 |
|---|---|---|
| 是 | 否 | 数据竞争，行为未定义 |
| 是 | 是 | 没有竞争 |
| 否 | 不用看 | 没有竞争 |

判断顺序是固定的：先问位置，再问边；不要反过来从“有没有加锁”猜。

## 11.3 修改顺序：每个对象一条线，不同对象之间没有线

每个原子对象都有一条修改顺序（modification order），所有线程必须认可同一条。`memory_order_relaxed` 只给每个对象一条这样的线，不要求把不同对象的顺序合成一条全局时间线；不同线程完全可能以不一致的顺序观察不同对象。

修改顺序只约束同一个对象，不约束不同对象之间的先后。默认的 `seq_cst` 是另一回事：它给所有 `seq_cst` 操作一条全局总序，所以刚才那种不一致的观察不会出现；[13.1 节](ch13.md)讲总序，[13.2 节](ch13.md)讲 relaxed。

标准只对原子对象定义修改顺序；非原子对象要靠先行发生关系，才能让所有线程按同一条顺序观察它。

{{#fig ch11/modification_order}}

图里的读写都用 `memory_order_relaxed`。`x` 和 `y` 各自从 0 单调到 1，但两条线之间没有箭头，读线程 B 可以先看到 `y` 的新值，再看 `x` 的旧值。这不是缓存“坏了”，而是语言模型允许的，换成默认的 `seq_cst` 这条执行就被总序排除。

缓存一致性保证一条缓存行不会永远停在旧副本，但它不保证不同地址上的操作按程序顺序可见。把“最终会看见”当成“按顺序看见”，是很多错误代码的起点；第 13 章会从 store buffer 讲起。

`volatile` 的作用是提醒编译器：这个对象的值可能被程序之外的东西改变，别把对它的读写优化掉。它不提供：

- 原子性；
- 先行发生关系。

## 11.4 先行发生：把两个线程接起来的那条边

线程内是“序前于”（sequenced-before）：同一线程里，前一条语句的求值排在后面之前。线程间靠“同步于”（synchronizes-with）接起来；两者合起来是先行发生（happens-before），并且可以传递：A 先行于 B、B 先行于 C，则 A 先行于 C。

{{#fig ch11/hb_graph}}

常见的同步点：

- `std::thread` 构造完成与新线程开始执行同步；线程函数返回与 `join` 返回同步。
- `mutex` 的 `unlock` 与下一次 `lock` 同步。
- `promise::set_value` 与 `future::get` 同步。
- `latch::count_down` 与因此被解除阻塞的 `wait` 返回同步；`barrier` 的到达与通过同步。
- `future::wait` 返回也与共享状态的就绪同步。
- 原子操作的 release/acquire 也能建立同步，第 13 章再讲。

条件变量本身不建立同步：

- 它依赖配套的互斥量；
- 被保护的数据必须在同一把锁下读写，否则“被唤醒”不等于“看得到”；
- `wait` 返回时确实重新拿到了锁，但只有锁内读写的数据才受这条边保护。

同一个函数调用里多个实参的求值顺序，在 C++17 起仍然是未指定的，但彼此是 indeterminately sequenced：一个实参的求值不会和另一个交错。不要把它当成“有先后”，也不要因为顺序未指定就认为有数据竞争；它既不建立先行发生，也不构成数据竞争。

判断一段代码有没有竞争，画一张“谁在什么锁、什么 future 之后读什么”的图，比逐行读代码可靠。图上没有边的地方，就是需要补同步的地方；锁、future、latch 的边都画得出来，画不出来的地方，就是竞争藏身的地方。

| 设施 | 建立了哪条边 | 能否跨进程 | 典型误用 |
|---|---|---|---|
| `pthread_mutex_lock/unlock` | 同一互斥量上的 unlock 与下一次 lock 同步，起 acquire/release 的作用 | 可以，需 `PTHREAD_PROCESS_SHARED` 和共享内存 | 用不同的互斥量保护同一份数据 |
| `pthread_join` | 线程完成与 join 返回同步 | 不能 | 线程已经 detach 还去 join |
| `pthread_cond_wait` | 本身不建立；靠配对的互斥量 | 可以，需进程共享属性 | 被保护的数据不在同一把锁下读写 |
| C11 `atomic_load_explicit`/`atomic_store_explicit` | 同一原子对象上的 release store 与读到它的 acquire load 同步 | 共享内存加无锁实现时可行，标准不保证 | 用 relaxed 操作却指望数据可见 |
| OpenMP `flush` / `barrier` | flush 使本线程的写对团队可见；barrier 带隐式 flush | 不能，只覆盖团队内的线程 | 以为 flush 本身能消除数据竞争 |
| `futex(2)` | 只负责睡眠和唤醒，不建立语言级先行发生 | 可以，共享 futex | 把它当互斥量用，却不配原子操作和栅栏 |
| `membarrier(2)` | 给一组线程发内存屏障 | 进程内为主；`GLOBAL` 覆盖全系统，但不是跨进程同步 | 以为它能替代语言级的同步设施 |

`futex(2)` 和 `membarrier(2)` 都工作在系统调用层：前者管等待队列，后者管屏障。它们能帮助实现同步设施，但不能替代语言级的先行发生关系。

## 11.5 条件竞争、数据竞争与“良性”竞争

条件竞争（race condition）是更宽的说法：结果依赖执行顺序。数据竞争是更窄的语言级判定：同一内存位置、至少一个写、没有先行发生关系。条件竞争可以没有数据竞争。

| 概念 | 判据 | 后果 |
|---|---|---|
| 条件竞争 | 结果依赖执行顺序 | 可能正确，也可能出错 |
| 数据竞争 | 同一位置、至少一个写、无先行发生关系 | 未定义行为 |

每个成员函数都加了锁，`empty()` 和 `pop()` 各自都是原子的；但“检查”和“取数”之间，另一个线程可以把唯一元素取走。这是接口竞争，属于条件竞争，不是数据竞争。

示例在 `pop()` 里做了两件事：

- 在 `pop()` 里先检查，空栈就调用 `abort()`，把未定义行为变成一次可复现的崩溃；
- 真实实现里没有这个检查，读到的是越界内存，后果不可预测。

修法有两种：把检查和取数合成一个操作（例如 `pop` 返回 `std::optional<T>`，空栈时返回空），或者改变返回值的语义（返回 `std::shared_ptr<T>`，让对象在取走之后仍然存活）。第 7 章的队列用的是前一种思路。

| 修法 | 做法 | 代价 |
|---|---|---|
| 合并检查和取数 | `pop` 返回 `std::optional<T>` | 调用者要处理空值 |
| 延长对象生命周期 | 返回 `std::shared_ptr<T>` | 多一次引用计数 |

## 速查

| 步骤 | 问题 | 若为“是” |
|---|---|---|
| 1 | 两个访问是否落在同一内存位置？ | 继续第 2 步；否则不是数据竞争 |
| 2 | 是否至少有一个写？ | 继续；读—读不构成竞争 |
| 3 | 是否至少有一个不是原子操作？ | 继续；两个都是原子操作则不是数据竞争 |
| 4 | 两次访问之间有没有先行发生关系？ | 有则不是竞争；没有则是数据竞争，行为未定义 |

| 设施 | 建立的边 | 注意 |
|---|---|---|
| `std::thread` 构造 | 构造完成 → 新线程开始 | 构造前写好的数据对新线程可见 |
| `join` | 线程完成 → join 返回 | 之后读各线程写下的结果安全 |
| `mutex` 的 `unlock`/`lock` | 前一次 unlock → 下一次 lock | 同一把锁，保护同一份数据 |
| `promise`/`future` | `set_value` → `get` 返回 | 共享状态只能设置一次 |
| `latch` | `count_down` → `wait` 返回 | 适合一次性发布 |
| `barrier` | 到达 → 通过 | 适合分阶段循环 |
| 原子 release/acquire | store → 读到该值的 load | 第 13 章 |

| 写法 | 原子性 | 建立先行发生 | 常见误用 |
|---|---|---|---|
| `volatile` | 不提供 | 不提供 | 当线程间标志或计数器 |
| `std::atomic` | 单个操作原子 | release/acquire 可以 | 以为 `counter = counter + 1` 是原子的 |
| `mutex` | 临界区串行 | unlock 与 lock 同步 | 锁外读写被保护的数据 |

## 思考题

1. 把 11.1 的 `counter` 换成 `std::atomic<int>` 的 `++`，结果一定是 2000000 吗？如果主线程在 `join` 之前读一次 `counter`，能读到哪些值？

   <details><summary>提示</summary>

   一定是 2000000：原子的读—改—写不会丢更新，和内存序无关。`join` 之前读到的是某个已经被写下的值，范围从 0 到 2000000；不会读到撕裂的中间值，但也不能假设它等于线程已经完成的总数。

   </details>

2. 11.2 里两个线程分别写相邻位域，为什么 TSan 报的是同一地址？如果改成两个普通 `int` 成员，报告会消失吗？

   <details><summary>提示</summary>

   相邻的非零宽位域合起来算一个内存位置，两个位域对象共享同一个存储单元，所以报告里的地址相同。换成两个 `int` 成员后，它们是两个内存位置，TSan 不再报告；但两者可能落在同一条缓存行上，性能仍会受伪共享影响。

   </details>

3. 用 `std::promise<Data*>` 把一个堆对象的地址交给另一个线程，先行发生链由哪几步组成？如果只用 `std::atomic<Data*>` 的 relaxed store，链断在哪？

   <details><summary>提示</summary>

   链是：写线程构造 `Data`，然后 `set_value`；读线程 `get` 返回，拿到指针。`set_value` 与 `get` 同步，构造在前，所以读线程看到完整的对象。relaxed store 只保证指针本身不撕裂，不建立同步；读线程可能先看到指针，却看不到构造函数写下的成员。

   </details>

4. 一个只读的配置表，启动后不再修改，多个线程直接读是否需要同步？如果它在运行期偶尔更新，应该用锁、`atomic<shared_ptr>` 还是 `shared_mutex`？

   <details><summary>提示</summary>

   启动后不再修改，只要发布动作本身有先行发生关系（例如在创建线程之前初始化，或用一次 `join`/`promise` 交付），之后并发读不需要同步。运行期更新时，锁最简单；`atomic<shared_ptr>` 适合整体替换、读多写少；`shared_mutex` 适合读临界区较长、读者多而写者少的场景，但要测量读者之间的争用。

   </details>
