# 第 7 章 条件变量与线程安全队列

消费者线程写的是 `if (q.empty()) cv.wait(lock);`。生产者偶尔在消费者“检查完、还没进入 `wait`”的缝里调用 `notify_one`，消费者于是永远睡下去，程序在关闭时挂住。

把 `if` 改成 `while` 只修好了虚假唤醒；通知的时机、取出元素与构造返回值的顺序、`close` 的广播，还要一起改。

## 7.1 等待事件的三种办法

等一个事件有三类做法，差别在“等待时谁在消耗 CPU”和“多久能看见变化”：

- 忙轮询：`while (!ready) {}`。延迟最低，但等待线程一直占着 CPU；线程数超过核数时还会拖慢别人。
- 定时睡眠：`while (!ready) sleep_for(1ms);`。省 CPU，但平均多等半个周期；睡得太久响应差，睡得太短又接近轮询。
- 条件变量：等待者挂到内核等待队列，通知者只在状态可能改变时唤醒它。等待时不占 CPU，唤醒延迟由调度决定。

{{#fig ch07/wait_strategies}}

图里同时画了两件事：

- 每次等待的墙钟时间：从生产者开始睡到消费者看见标志。
- 这段时间里两个线程消耗的 CPU 时间：忙轮询会把它撑满。

忙轮询的 CPU 时间和等待时间几乎一样长，等待线程几乎一直在跑。1 ms 睡眠把等待拉长，CPU 时间很小；条件变量两头都低。

三行输出对应三种策略：

单个原子标志可以改用 C++20 的 `std::atomic<T>::wait`/`notify_one`。注意两点：

- 它等的是“值变了”，不是“有人通知”；值在 `wait` 之前已经改变时会立刻返回。
- 它只保护这一个原子值，不保护复合不变量；队列内容仍要 mutex 加条件变量。
- `notify_one`/`notify_all` 要和 `atomic::wait` 配对；不要和条件变量的通知混用。

`yield()` 只是让出 CPU，不保证条件会变；`sleep` 不能当同步原语。事件循环里跨线程唤醒常用 `eventfd`/pipe，把“有事件”变成 fd 可读，第 33 章展开。

条件变量的延迟不一定比忙轮询低，但等待期间不占 CPU。事件频繁、每次等得很短时可以自旋；等得久、又不确定什么时候来，就用条件变量。

## 7.2 条件变量的规则

两种条件变量分工不同：

- `std::condition_variable` 只能配 `std::unique_lock<std::mutex>`，开销小。
- `std::condition_variable_any` 能配任意 BasicLockable，通常开销更大。
- 两者都不保护数据；被保护的变量必须在同一把锁下读写。
- 条件变量本身不建立数据同步；数据可见性仍由配套的互斥量负责。
- 通知密集时，先改完状态再决定要不要通知；无谓的通知只会增加唤醒和重新加锁。

`wait(lock, pred)` 等价于 `while (!pred()) wait(lock);`。谓词在持锁状态下求值，不能有副作用；虚假唤醒是正常返回，不是错误。

`wait` 原子地释放互斥量并睡眠，醒来后重新加锁。通知方可以持锁或不持锁调用 `notify_*`。

持锁通知会让被唤醒的线程先卡在重新加锁上，通常解锁后再通知。

{{#fig ch07/condvar}}

看第 3 步：解锁和睡眠是一个原子动作，别的线程不可能插在中间。第 9 步醒来后先重新加锁，第 10 步再查谓词；虚假唤醒也从第 10 步回到检查。

条件变量没有记忆。在 `wait` 之前发出的 `signal` 会丢失，所以谓词必须由共享状态表达，不能只靠通知。

`notify_one` 和 `notify_all` 的区别：

- `notify_one` 唤醒至少一个等待者，具体哪个由实现和调度决定。
- `notify_all` 唤醒全部；关闭和广播状态时用。
- 被唤醒的线程发现谓词为假，要回去继续等。

选哪个取决于“一个元素够不够多个消费者分”。

`wait_for`/`wait_until` 和销毁规则：

- `std::cv_status::timeout` 是超时返回值，拼写不是 `time_out`。
- `wait_until` 接 `time_point`，`wait_for` 接 `duration`。
- 销毁仍有等待者的条件变量是未定义行为；glibc 2.43 上会阻塞，不能依赖 `EBUSY`。
- `wait_for` 返回 `timeout` 只说明条件还没成立，超时后仍要重查谓词。

| 项目 | `std::condition_variable` | `std::condition_variable_any` | `pthread_cond_t` |
|---|---|---|---|
| 配什么锁 | `unique_lock<mutex>` | 任意 BasicLockable | 配套的 `pthread_mutex_t`，必须由调用者持有 |
| 谓词重载 | `wait(lock, pred)` | `wait(lock, pred)` | 没有，自己写 `while` |
| 超时 | `wait_for`/`wait_until`，返回 `cv_status` | 同左 | `pthread_cond_timedwait`，绝对 `timespec` |
| 单调时钟 | 用 `steady_clock` 的 `time_point` | 同左 | 默认 `CLOCK_REALTIME`；用 `condattr_setclock` 或 `pthread_cond_clockwait` |
| `stop_token` | 没有 | C++20 有 `wait(lock, token, pred)` | 没有 |
| 销毁 | 有等待者时未定义 | 同左 | 同左 |

> **旧资料提示**：用 `if` 包住 `wait`，或者用 `pthread_cond_wait` 的返回值判断虚假唤醒，都是旧写法。返回值 0 只表示成功返回，虚假唤醒也返回 0；谓词必须放进 `while`/`wait(lock, pred)`。见 [37.3 节](ch37.md)。

## 7.3 线程安全队列 ThreadSafeQueue

接口和关闭语义：

- 内部是 `queue<T>` + `mutable mutex` + `condition_variable`；不要暴露分开的 `front()` 和 `pop()`，否则接口之间会有竞争。
- `mutable` 让 `const` 的 `size()` 也能加锁；`try_pop` 用返回值表示有没有取到。
- `wait_pop` 的谓词是 `!q.empty() || closed`；队列空且已关闭返回 `nullopt`，非空时先取完。
- `push` 关闭后返回 false；`close` 置位后 `notify_all`，并且幂等。
- 队列析构前要先 `close`、再 `join` 所有消费者，否则等待者可能访问已销毁的条件变量。
- `try_pop` 适合轮询式消费者；它不睡眠，也不会因为关闭而阻塞。

|---|---|---|---|

| 关闭 | 没有 | `closed` + `notify_all`，幂等 | `closed` + `pthread_cond_broadcast` |

## 7.4 通知策略、关闭与异常

`notify_one` 有一个异常洞：消费者被唤醒、把元素从队列取出，构造返回值时抛异常（拷贝构造、移动构造、分配失败），元素已经不在队列里，其他消费者还在睡；如果生产者已经结束，其他消费者永远等不到。

- 改用 `notify_all`：唤醒开销大，但不会漏掉其他消费者。
- 在异常路径补一次通知：代码短，但每条退出路径都要记得补。
- 把可能抛异常的分配移到 `push`：队列存 `std::shared_ptr<T>`，`wait_pop` 只拷贝指针，不抛。
- 用 `shared_ptr` 的代价是每个元素一次堆分配；分配在 `push` 里做，异常在入队前就处理掉。
- `push` 也要保证强异常安全：先构造节点或指针，再改队列；失败时队列保持原样。

关闭顺序的三条规则：

- 先置 `closed`、解锁，再 `notify_all`。
- 不要在持锁时 `join` 消费者。
- 消费者退出前要把队列里的元素处理完，或者明确丢弃并在文档里写清楚。

`std::queue<T>` 的 `pop()` 返回 void，`wait_pop` 要先把元素移到返回值再 `pop`。移动构造若不 `noexcept`，`push` 里的分配和移动也可能抛。

`std::condition_variable_any` 的 `wait` 可以接 `std::stop_token`（C++20），`std::condition_variable` 没有这个重载。要让普通条件变量响应停止请求，用 `std::stop_callback` 在停止时 `notify_all`；`notify_all_at_thread_exit` 适合“线程退出时再唤醒”，但不要用它替代明确的关闭协议。

关闭和停止是两件事：`close` 表示不会再有新元素，停止表示消费者该退出。先停止生产、再关闭队列，最后 `join`。

## 7.5 用停止令牌打断等待

C++20 的 `std::stop_token`/`std::stop_source`/`std::stop_callback` 把“请求停止”变成标准接口。`std::jthread` 析构先 `request_stop()` 再 `join()`；线程不检查 `stop_token` 时，`join` 仍可能永久等下去。

`std::condition_variable_any::wait(lock, token, pred)` 在停止请求到来时立即返回：谓词为假时返回 false，谓词为真时返回 true。`std::condition_variable` 没有 `stop_token` 重载，常见做法是用 `std::stop_callback` 注册一个回调，在回调里 `notify_all`，然后正常 `wait`。

`stop_token`/`stop_callback` 的几条规则：

- 构造函数注册回调，析构注销。
- 回调在调用 `request_stop()` 的线程里执行，必须短、不能抛异常。
- 注册时停止已经请求，回调会在注册线程里立即执行。
- `stop_source` 可以拷贝，多个持有者共享同一个停止状态。
- 普通 `condition_variable` 不会因停止自动醒来；要么用 `_any` 的 `stop_token` 重载，要么注册回调。

停止是协作式的：线程要在循环或等待点检查 `stop_requested()`，不会强制杀死线程。`std::atomic::wait` 没有停止参数，等原子值时要么用 `wait_for` 轮询，要么改用条件变量。

`pthread_cancel` 是另一套机制，异步取消可能让 C++ 对象来不及析构，放到第 20 章。

## 7.6 pthread 条件变量与封装反例

`pthread_cond_init`/`destroy`/`wait`/`timedwait`/`signal`/`broadcast` 都返回错误码。全局或静态条件变量可以用 `PTHREAD_COND_INITIALIZER`。

`pthread_cond_wait` 必须持有配套的 `pthread_mutex_t`，它原子地释放互斥量并睡眠，返回前重新加锁。谓词必须放在 `while` 里，不能靠返回值区分虚假唤醒：正常唤醒也返回 0。

`pthread_cond_timedwait` 有三点要注意：

- 参数是绝对 `timespec`，不是时长。
- 默认 `CLOCK_REALTIME`，会被校时影响；需要单调时钟时用 `pthread_condattr_setclock(CLOCK_MONOTONIC)`。
- 返回 `ETIMEDOUT` 只表示超时，醒来后仍要重查谓词。
- `pthread_cond_signal` 不保证唤醒哪个线程；POSIX 不规定优先级或 FIFO。

glibc 2.30 起还有 `pthread_cond_clockwait`，可以直接指定时钟。glibc 2.43 的头文件仍只在 `_GNU_SOURCE` 下声明它，要用它时源码要写 `#define _GNU_SOURCE`。

`pthread_cond_wait` 是取消点；如果线程可能被 `pthread_cancel`，要准备 cleanup handler。新代码优先用协作式停止。

## 速查

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `std::condition_variable` | 等复合谓词 | 只配 `unique_lock<mutex>`；没有 `stop_token` 重载 |
| `std::condition_variable_any` | 配任意 BasicLockable | 开销更大；C++20 有 `wait(lock, token, pred)` |
| `wait(lock, pred)` | 谓词版等待 | 等价于 `while (!pred()) wait(lock);` |
| `wait_for` / `wait_until` | 超时等待 | 不带谓词时返回 `cv_status`；`_for` 收 duration，`_until` 收 time_point |
| `notify_one` / `notify_all` | 唤醒至少一个 / 全部 | 条件变量没有记忆；通常解锁后再通知 |
| `std::stop_token` / `stop_source` | 协作式停止 | `jthread` 析构先 `request_stop()` 再 `join()` |
| `std::stop_callback` | 停止时执行回调 | 在请求线程执行；必须短、不能抛；注册时已停止会立即执行 |
| `pthread_cond_wait` | pthread 等待 | 必须持有配套 mutex；谓词放 `while`；返回 0 也可能是虚假唤醒 |
| `pthread_cond_timedwait` | pthread 超时等待 | 绝对 `timespec`；默认 `CLOCK_REALTIME`；超时返回 `ETIMEDOUT` |
| `pthread_condattr_setclock` | 选条件变量时钟 | 用 `CLOCK_MONOTONIC` 避开校时 |
| `PTHREAD_COND_INITIALIZER` | 静态初始化 | 只用于全局或静态条件变量 |
| `pthread_cond_signal` / `broadcast` | 唤醒一个 / 全部 | 在 `wait` 之前发出会丢失 |

## 思考题

1. 预测：把 `7_2_lost_wakeup.cpp` 里的 `notify_one` 移到加锁之前或之后，挂起的概率会怎么变？为什么仍然不能保证不丢？

   <details><summary>提示</summary>

   移到加锁之前，通知更早，落空的概率更大；移到解锁之后，消费者仍可能还没进入 `wait`。条件变量只在“已经睡进等待队列”之后才接收通知，检查和睡眠之间的窗口无法靠调整顺序消除；正确做法是让谓词由共享状态表达，并在持锁时检查。

   </details>

2. 找错：`7_3_threadsafe_queue.cpp` 的 `wait_pop` 如果先 `q.pop()` 再构造返回值，异常时会发生什么？把构造放到 `pop` 之前呢？

   <details><summary>提示</summary>

   先 `pop` 再构造，元素已经销毁，构造抛异常就丢了任务；其他消费者未必收到通知。把构造放到 `pop` 之前，异常时元素还在队列里，但下一次取到的可能是被移动过的对象，需要保证移动构造不抛或能回滚。

   </details>

3. 权衡：队列关闭时，消费者应该取完剩余元素还是立即丢弃？两种策略对“任务不丢”和“退出够快”各有什么代价？

   <details><summary>提示</summary>

   取完剩余元素不丢任务，但关闭要等队列排空，生产者可能还在提交；立即丢弃退出快，但已经入队的任务会消失，必须让调用者知道丢了多少。选择要写进接口文档，并让 `close` 的返回值或状态可查询。

   </details>

4. 迁移：把 `7_5_stop_token_wait.cpp` 改成普通 `condition_variable` + `stop_callback`，需要保证回调注册和队列状态之间的什么顺序？

   <details><summary>提示</summary>

   先注册回调，再检查队列和停止状态；注册前已经请求停止时，`stop_callback` 会立即执行。回调只做 `notify_all`，不要碰队列；队列状态仍由 mutex 保护，消费者醒来后在锁内重查谓词。

   </details>
