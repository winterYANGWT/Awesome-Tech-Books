# 第 22 章 OpenMP

同一段 π 的梯形积分，加上 `reduction(+:sum)`，多线程比串行快了几倍；但 1、2、4、8 线程算出的末几位不同。把 `reduction` 换成 `critical`，结果不再丢更新，耗时却随线程数上升。

差别不在浮点库，而在四件事：线程组什么时候建、变量在哪个作用域、归约在哪里合并、迭代分给谁。

```c
double sum = 0.0;
#pragma omp parallel for reduction(+:sum)
for (long i = 0; i < n; ++i) {
    double x = (i + 0.5) / n;
    sum += 4.0 / (1.0 + x * x);
}
```

## 22.1 从 pragma 到线程组：编译、运行与 fork-join

- `-fopenmp` 同时作用于预处理、编译和链接；没有它，`#pragma omp` 被忽略，但 `omp.h` 和 `omp_*` 调用会编译失败，所以要用 `#ifdef _OPENMP` 包住；

注意第 2 步和第 4 步：`parallel` 在入口建立线程组，入口没有屏障，各线程先后进入；块尾有隐式屏障，先做完的要等齐，之后只有 primary 线程继续执行。OpenMP 5.x 规范用 primary/worker 称呼，旧资料里的 master/slave 仍常见。

线程数按以下顺序决定，前面的覆盖后面的：

- `num_threads(n)` 子句；
- `omp_set_num_threads(n)`；
- 环境变量 `OMP_NUM_THREADS`；
- 实现的默认值。

`OMP_DYNAMIC=true` 允许运行时少开线程，所以区域内 `omp_get_num_threads()` 返回实际线程数，不是请求值。要固定线程数做实验时，设 `OMP_DYNAMIC=false`。

`#pragma omp parallel for` 是 `parallel` 和 `for` 的组合构造，不是“先开线程，再随便写一个 for”。`nowait` 只能放在 `for`、`sections`、`single` 等 worksharing 构造上，不能放在 `parallel` 或合并的 `parallel for` 上，GCC 15.2 会报 `nowait is not valid for #pragma omp parallel for`。

> **旧资料提示**：旧教程说每次 `parallel for` 都新建、销毁线程。现代 OpenMP 运行时通常复用线程池，`parallel for` 未必每次创建线程，具体行为依实现；要测创建开销就自己计时。第 40 章会讲这条经验为什么过时。

计时接口有三点要注意：

- `omp_get_wtime()` 返回从某个固定起点算起的墙钟秒数，规范只保证同一线程内这条时间轴不变，不保证跨线程一致；
- `omp_get_wtick()` 给分辨率，计时示例先预热、重复取最小值或中位数；
- 计算结果要一起输出，防止循环被优化掉。

结构化块只能有一个入口和一个出口：`break`、`return`、`goto` 不能跳出并行区，C++ 异常也不能穿过 OpenMP 区域，异常必须在区域内部捕获。

| 设施 | pthread | C++ 标准库 | OpenMP | 语义差别 |
|---|---|---|---|---|
| 线程组 | 没有组，线程各自独立 | 没有组，线程是对象 | `parallel` 建立一个 team | 组内线程共享块尾屏障 |
| 创建 | `pthread_create` 逐个创建 | `std::thread`/`std::jthread` 逐个创建 | 遇到指令隐式创建 | 没有线程句柄 |
| 数量控制 | 自己算，逐个创建 | 自己算，逐个创建 | `num_threads`、`omp_set_num_threads`、`OMP_NUM_THREADS` | 运行时可以动态调整 |
| 汇入 | `pthread_join` 逐个等 | `join()` 或 `jthread` 析构 | 块尾隐式屏障 | `join` 等一个，屏障等全组 |
| 错误报告 | 返回错误码 | 抛 `std::system_error` | 没有对应的创建返回码 | 资源不足时的行为依实现 |
| 属性 | `pthread_attr_t` 可设栈大小、调度 | 不能设栈大小，`native_handle()` 拿到底层句柄 | `OMP_STACKSIZE`、`OMP_PROC_BIND` 等环境变量 | 创建属性控制更粗 |

`sched_setaffinity(2)` 和 `pthread_setaffinity_np(3)` 决定线程落在哪个 CPU，不决定 OpenMP 怎么划分迭代。绑核影响缓存和 NUMA，调度子句影响谁做哪些迭代，两者不要混为一谈。

## 22.3 归约：从 critical 到 reduction

`#pragma omp critical [(name)]` 是代码块级的互斥。所有未命名 `critical` 在整个程序里共用一把锁，命名 `critical` 按编译期名字区分。它不能 `try_lock`、不能限时、不是 RAII，异常离开时不会自动解锁。

把 `critical` 套在整个函数调用外面，会把函数里的全部工作串行化。正确做法是只保护“读—改—写”共享累加器的那一两行，或者干脆用 `reduction`。下面的版本每 64 个梯形进一次临界区，故意让争用出现在计时里：

`-` 不是“按顺序减”。每个线程先算自己的带符号部分和，结束时再相加，所以 `reduction(-:x)` 的结果不能和串行左折叠逐位比较。

`#pragma omp atomic` 只保护一条特定形式的标量更新：

- 可以写成 `x++`、`x--`、`x op= expr`、`x = x op expr` 等；
- `x += y++` 只保护 `x`，`y++` 仍在临界区外，`y` 自己的竞争要另外处理。

OpenMP 5.0 起 `atomic` 可以带 memory-order 子句，默认是 `seq_cst`。本机 GCC 15.2 接受 `atomic relaxed`，但 `_OPENMP` 仍报 4.5，不能据此认为它完整支持 5.x。

用了 `nowait` 的 `for` 上的 `reduction`，在原变量上读写会和归约合并竞争。要么保留隐式屏障，要么自己加 `barrier`。

## 22.4 循环并行化与循环携带依赖

`parallel for` 只接受规范形式的 for：初始化 `i = start`，条件对循环不变量做 `<`、`<=`、`>`、`>=`，增量是 `++i`、`i++`、`i += inc` 等。迭代次数必须在进入循环前可算，不能有 `break`、`return`、`goto` 跳出，也不能让异常穿出。

迭代怎么分由 `schedule` 决定，循环变量自动私有，末尾默认有隐式屏障。`nowait` 去掉屏障，但只有在确认后续代码不读本轮结果时才是安全的。

循环携带依赖指一次迭代写、另一次迭代读或写同一个变量。Fibonacci 的 `f[i] = f[i-1] + f[i-2]` 是典型，编译器不检查依赖，`parallel for` 照样编译。重复运行时大多数都错，具体次数会随调度变，这里只记现象，不把某次统计当结论。

## 22.5 调度与负载均衡

`schedule(kind[, chunk])` 的 kind 有 `static`、`dynamic`、`guided`、`auto`、`runtime`。`chunk` 是正整数，只有前三种接受。

| kind | chunk | 分配方式 |
|---|---|---|
| `static` | 省略 | 切成大约相等、每线程至多一块的连续块 |
| `static` | 有 | 按 chunk 轮转，`static,2` 是两块一组 |
| `dynamic` | 省略 | 块大小为 1，做完一块再领下一块 |
| `guided` | 省略 | 块大小按剩余迭代数除以线程数递减，下限为 1 |
| `auto` | 不接受 | 完全交给实现 |
| `runtime` | 不接受 | 从 `OMP_SCHEDULE` 或 `omp_set_schedule` 读取 |

`static` 不带 chunk 才接近“块划分”。用 `schedule(static, n/thread_count)` 想强制块划分是错的：n 不能被线程数整除时 chunk 取整，线程会拿到多段不连续的迭代，n 小于线程数时 chunk 可能算成 0，而 OpenMP 要求正整数。

`static` 不带 chunk 时每个线程拿一段连续的块；`static,2` 下线程 0 先拿开头两个，再拿轮转到它的后续两个，块不连续。

`static` 的四行工作量从低到高差出几倍：拿到小块的线程早早结束，拿到大块的线程拖住整体。`static,1` 把各线程的工作量拉平，最慢的线程也随之下降。

`dynamic,1` 和 `guided` 的分配每次不同，但最大工作量也在平均附近。块越小越均衡，领任务的同步和缓存开销越高；块大到一定程度就退化成 `static`。

- `schedule(nonmonotonic)` 允许块以任意顺序执行，依赖执行顺序的代码不能用。

## 22.6 同步构造：critical、atomic、barrier 与锁

三个同步设施的分工：

- `barrier` 是线程组级同步点，组内所有线程都必须到达；`for`、`sections`、`single` 末尾默认有隐式屏障，`nowait` 去掉它，屏障不能放在 worksharing 构造内部；
- `atomic` 只保证被更新变量的那一次读-改-写原子，不保护同一语句里的其他副作用；
- `critical` 保护整个代码块，未命名时全局共锁；`omp_lock_t` 把互斥绑在数据结构上，要手动 init/destroy 和 set/unset，没有 RAII。

三个 try-lock 的返回值方向不同：

| 接口 | 成功 | 失败 |
|---|---|---|
| `omp_test_lock` | 非 0 | 0 |
| `pthread_mutex_trylock` | 0 | `EBUSY` |
| `std::mutex::try_lock` | `true` | `false` |

OpenMP 没有条件变量。需要等待时只能轮询共享标志，配 `atomic` 或 `critical`，或者用 `task`/`taskgroup` 表达结构化等待。轮询会烧 CPU，也不能替代“队列非空”这种谓词。

| 设施 | pthread | C++ 标准库 | OpenMP | 语义差别 |
|---|---|---|---|---|
| 互斥 | `pthread_mutex_t` | `std::mutex`、`lock_guard` | `critical`、`omp_lock_t` | OpenMP 无 RAII，锁要手动配对 |

同一临界区不要混用 `atomic` 和 `critical`，两者不互斥。互斥不保证公平。嵌套临界区要固定加锁顺序，命名 `critical` 只能区分名字，不能解决交叉加锁顺序。

## 22.7 任务、SIMD 与 OpenMP 的边界

`#pragma omp task`（OpenMP 3.0）把一段代码变成可延迟执行的任务。遇到任务的线程可以立刻执行，也可以放进任务池让组内其他线程取。`taskwait` 等子任务，`taskgroup` 等一组任务，`depend(in/out/inout)`（OpenMP 4.0）表达任务间依赖。

任务不是 C++ 的 future：

- 没有返回值通道，异常不能穿出任务，取消要用 `cancel`/cancellation point（OpenMP 4.0）；
- 外层共享的变量仍然共享，其余变量默认 `firstprivate`，可以用 `shared`/`private`/`firstprivate` 覆盖。

{{#fig ch22/task_pool}}

任务的存储必须在任务完成前保持有效。栈上的局部数组不能随手交给未等待的任务；父任务要等 `taskwait` 返回再离开作用域。

- 任务适合递归、不规则循环和 `while` 循环；
- 不适合“每轮都要全局屏障”的规则循环，规则循环用 `parallel for` 或 `taskloop`，同步点更少。

三个边界特性：

- `simd`（OpenMP 4.0）只是向量化提示，不创建线程；`safelen`/`simdlen` 声明依赖距离和向量长度，`declare simd` 让函数可被向量化调用，也可以组合成 `parallel for simd`；
- `target`（OpenMP 4.0）把区域卸载到设备，`target teams distribute parallel for` 是常见的 GPU 写法；本书环境没有验证到可用的 GPU 设备，`target` 只能在主机执行，这里只讲结构；
- `masked`（OpenMP 5.1）取代 `master`，可以由 `filter` 选线程，默认线程 0；`master` 在 5.1 起被标记弃用，GCC 15.2 实测接受 `masked`，但 `_OPENMP` 仍报 4.5。

> **旧资料提示**：旧教程用 `master` 表示“线程 0 执行”。OpenMP 5.1 起 `master` 被标记弃用，新代码写 `masked`；`single` 没有弃用。第 40 章会讲这条。

和 C++17 执行策略、TBB、C++26 `std::execution` 的差别，主要在三个问题：谁决定任务粒度、谁负责调度、异常怎么传。

| 写法 | 粒度 | 调度 | 异常 |
|---|---|---|---|
| OpenMP `parallel for` | 程序员用 `schedule` 定 | 运行时按子句分 | 不能穿出区域 |
| OpenMP `task` | 程序员决定在哪生成 | 运行时任务池 | 不能穿出任务 |
| TBB `parallel_for`/`task_group` | 程序员给 range 和 body | 工作窃取 | 在等待点重新抛出 |
| C++17 `par` | 实现决定 | 实现决定 | 调用 `std::terminate` |
| C++26 `std::execution` | 由 scheduler 决定 | 由 scheduler 决定 | 由 sender/receiver 传播 |

C++26 的 `std::execution` 有 `parallel_scheduler` 和 `get_parallel_scheduler()`，但没有可以自己配线程数的线程池类。本机 GCC 15 / Clang 21 都没有实现，表里只写结构，不当作可运行示例。

## 速查

| 接口或写法 | 作用 | 默认值/版本 | 坑 |
|---|---|---|---|
| `-fopenmp` | 打开预处理、编译、链接支持 | GCC/Clang 通用 | 不加时 pragma 被忽略，`omp_*` 调用编译失败 |
| `_OPENMP` | 实现声称的 OpenMP 版本 | GCC 15.2 为 `201511` | 不能判断单个 5.x 特性 |
| `omp_get_thread_num` | 队内编号 | `0…t-1` | 不是 `std::thread::id` |
| `omp_get_num_threads` | 当前团队实际线程数 | 区域内有效 | 受 `OMP_DYNAMIC` 影响 |
| `omp_get_max_threads` | 下次默认线程数 | 实现决定 | 不是当前团队大小 |
| `omp_set_num_threads` | 设置后续区域线程数 | — | 被 `num_threads` 覆盖 |
| `omp_get_wtime` | 墙钟秒数 | `double` | 起点任意，只测同一线程的差值 |
| `parallel` | 建线程组 | 入口无屏障 | 块尾隐式屏障 |
| `parallel for` | 组合构造 | 循环必须规范 | `nowait` 不能加 |
| `for` | 在已有组内分迭代 | 末尾隐式屏障 | 不创建线程 |
| `sections`/`single` | 非迭代 worksharing | 末尾隐式屏障 | `single` 不是“只一次初始化” |
| `master`/`masked` | 指定线程执行 | `masked` 5.1 起 | `master` 已弃用 |
| `critical` | 块级互斥 | 未命名全局共锁 | 不能 try、不是 RAII |
| `atomic` | 单条标量更新 | 5.0 起可带 memory-order | 不保护同句其他副作用 |
| `barrier` | 团队同步点 | 所有线程必须到达 | 不能部分线程绕过 |
| `nowait` | 去掉末尾屏障 | worksharing 和 `target` 等构造可用，不能加在 `parallel` 上 | 后续读本轮结果会竞争 |
| `reduction` | 私有副本加合并 | 初值按操作符 | 合并顺序未指定，浮点末位会变 |
| `private` | 每线程未初始化副本 | 不写回 | 读未初始化值是未定义行为 |
| `firstprivate` | 进入时拷贝初值 | 拷贝构造 | 形参指向的对象仍可能共享 |
| `lastprivate` | 退出时写回最后一次 | 拷贝赋值 | “最后”是顺序最后，不是最后写完 |
| `shared` | 大家看同一份 | 默认作用域 | 不提供互斥 |
| `default(none)` | 强制写明作用域 | — | 漏写就编译失败 |
| `schedule(static/dynamic/guided[,chunk])` | 迭代分配 | chunk 正整数 | `static` 无 chunk 块大小未指定 |
| `OMP_SCHEDULE` | `runtime` 的调度 | 如 `dynamic,2` | 只影响 `runtime` |
| `OMP_NUM_THREADS` | 默认线程数 | 实现默认 | 被 `num_threads` 覆盖 |
| `OMP_DYNAMIC` | 允许运行时调整线程数 | 实现定义 | 固定实验时设 false |
| `OMP_PROC_BIND`/`OMP_PLACES` | 绑核 | 实现支持 | 不决定迭代划分 |
| `task`/`taskwait`/`taskgroup`/`depend` | 任务与依赖 | 3.0/4.0 | 没有返回值通道 |
| `taskloop` | 循环拆任务 | 4.5 | 需要编译器支持 |
| `simd` | 向量化提示 | 4.0 | 不创建线程 |
| `target` | 卸载到设备 | 4.0 | 本机没有验证到 GPU |
| `omp_lock_t`/`omp_nest_lock_t` | 数据结构上的锁 | 手动 init/destroy | 异常路径不会自动解锁 |

## 思考题

1. 把 22.3 的 `reduction(+:pi)` 换成 `reduction(-:pi)`，1、2、4 线程的结果分别会是什么？和串行左折叠一定相同吗？

   <details><summary>提示</summary>

   1 线程只有一个副本，结果和串行左折叠相同。多线程时每个线程先算自己的带符号部分和，结束时再相加，等于把区间拆开分别做减法再合并，和逐个减不一样。改示例里的操作符跑一次，比较 `diff`。

   </details>

2. 22.4 的 Fibonacci 循环加上 `schedule(static,1)` 后仍然错，问题在调度还是在依赖？如果先把前两项算好再并行，能修好吗？

   <details><summary>提示</summary>

   问题在跨迭代依赖，调度只改变谁先读。前两项已经是 1 和 1，但 `f[2]` 还要等 `f[1]`，`f[3]` 还要等 `f[2]`，整条链没有断开。要并行得换算法，例如矩阵幂或先算闭式解。

   </details>

3. 22.5 的负载随下标增长，`static`、`static,1`、`dynamic,1`、`guided` 四种调度在小迭代数和大迭代数下各自什么时候更合适？

   <details><summary>提示</summary>

   小迭代数时同步开销占比高，`static` 的大块往往够用。负载不均且迭代多时，`static,1` 或 `dynamic,1` 更均衡；`guided` 想兼顾大块开头和小块收尾。用 `22_5_schedule` 改 N 和 `work_of` 的系数实测。

   </details>

4. 把 22.6 的每线程队列改成 `task` + `depend` 的生产者消费者，终止条件要怎么表达？OpenMP 没有条件变量，这个方案会多付出什么？

   <details><summary>提示</summary>

   终止不能只看队列空，要等所有生产者都声明不再生产，类似示例里的 `done_sending`。任务依赖能表达“某条消息入队后再出队”，但等待仍要靠任务图或轮询。代价是任务创建和数据环境拷贝的开销，队列满时也没有条件变量可睡。

   </details>
