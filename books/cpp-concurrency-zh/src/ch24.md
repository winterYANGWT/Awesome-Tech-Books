# 第 24 章 案例：n 体问题与树搜索

n 体模拟从 1 线程往上加，加速比没有随线程数线性增长，越往后收益越小，调度或布局换错，差距会拉大。TSP 的动态版本在子树不均时比静态版快。终止协议写错，却会提前退出，漏掉一条更优回路。

两个现象都不是“线程开得不够”。前者卡在负载、缓存行和同步上，后者卡在终止条件上。这一章按 Foster 的划分、通信、凝聚、映射四步，把两个串行程序改成并行程序。

## 24.1 从串行 n 体到 Foster 四步

n 体问题每个时间步要算每个粒子受到的其他所有粒子的引力，计算量 O(n²)；再用欧拉方法把力变成加速度，更新速度和位置。下面是一个时间步的核心：

```cpp

```

`forces[q]` 先在单独的循环里清零，再累加。清零这一步不能省：漏掉它，上一轮的力会留下来，粒子会越飞越快。位置、速度、质量只读，力只由负责 q 的线程写，所以这两个循环按粒子切开就不会有竞争。

- 校验和：所有位置的加权和，参与打印，防止循环被优化掉；
- 编译选项：不开 `-ffast-math`，否则浮点结果不可比。


单线程的毫秒数只用来做加速比的分母。校验和每次相同，计时每次不同。

Foster 四步把“怎么拆”讲成一串决定：

{{#fig ch24/foster}}

| 步骤 | 在 n 体里做什么 | 得到什么 |
|---|---|---|
| 划分 | 把“某粒子在某时刻的 F、s、v”各看成一个任务 | 任务图 |
| 通信 | F(q,t) 要所有粒子在 t 时刻的位置和质量；s、v 要本粒子的状态 | 按时刻的全对全位置读取 |
| 凝聚 | 把同一粒子在所有时刻的 F、s、v 合成一个复合任务 | 每个粒子一个任务 |
| 映射 | 把粒子分给线程；每个时刻仍要读所有粒子的位置并屏障 | 每线程一段粒子 |

凝聚把同一粒子的所有时间步放进一个任务，映射就只剩一维：把粒子分给线程。欧拉方法每一步都要用上一步的位置和速度，本粒子的状态留在同一线程，就不必每步搬走；但每个时间步仍要读其他粒子的位置，步骤之间仍有屏障。

AoS 和 SoA 的取舍可以写成一张表：

| 布局 | 一次读什么 | 适合 |
|---|---|---|
| AoS（`Particle[]`） | 一个粒子的全部字段 | 按粒子遍历、缓存整条记录 |
| SoA（`pos[]`、`vel[]`、`mass[]`） | 一个分量的一段 | 集合通信、SIMD、只读部分字段 |

数据布局决定通信和缓存；两种都能写对，性能不同，要用示例测，不能凭直觉选。

- `rel` 每次都是 0：每个 q 的内层求和顺序没变，线程只改变了“谁算哪个 q”，没有改变浮点加法顺序；

复杂度是 O(steps·n²)。n 很小时，线程创建和每步三次屏障占主导，n 很大时，内存带宽、伪共享和 NUMA 访问占主导。加速比的上限由这两头夹住，不是由线程数决定。

## 24.2 简化算法与三种同步方案

牛顿第三定律给出 `f_qk = -f_kq`。只对 `k > q` 算一次力，同时加到 `forces[q]` 和 `forces[k]`，计算量减半。这里的力是 `m_q m_k (r_k - r_q) / r^3`，两个粒子的质量都要乘，更新速度时再除以本粒子的质量：

```cpp
for (int q = 0; q < N; ++q)
    for (int k = q + 1; k < N; ++k) {
        Vec3 f = force_between(q, k);
        forces[q] += f;
        forces[k] -= f;   // 写的是别的粒子的数据
    }
```

代价有两个：`forces` 必须在单独循环里清零；线程负责 q，却要写 `forces[k]`，直接并行化就有竞争。三种修法：

| 方案 | 正确性 | 争用 | 内存 | 适用场景 |
|---|---|---|---|---|
| 全局 `critical` | 正确 | 最重，所有力的更新串行 | O(n) | 只用来验证结果 |
| 每粒子一把 `omp_lock_t` | 正确 | 比全局锁轻，仍要成对加解锁 | O(n) | 粒子数多、冲突分散 |
| 每线程局部力数组 | 正确 | 无锁，第二阶段才合并 | O(t·n) | 默认选择，内存够时 |

局部数组的两阶段法：第一阶段每个线程只写自己那一行，行与行之间按缓存行对齐；屏障之后，第二阶段按粒子把各行加起来。

简化算法在 1 线程下就比基本算法快，因为计算量减半，串行校验和还与基本版逐位相同，说明两版算同一个物理系统。2 线程的加速比却明显低于 2，原因不是同步，而是块划分：q 越小，内层循环越长，线程 0 干了大部分活。24.3 会用循环划分修它。

`atomic` 的保证只有一层：

- 对每个 double 单独做 `atomic`，只保证单个 double 的原子性；
- 它不能把“更新 q 和 k 两个分量”变成一对原子操作，读者仍可能看到 q 的新值和 k 的旧值。

需要成对一致时，用局部数组或锁。

## 24.3 数据布局、伪共享与调度

简化算法的力循环长度随 q 增大而变短。块划分把连续的 q 给一个线程，线程 0 拿到最长的那些循环；循环划分（`schedule(static,1)`）把 q 分散开，负载更均衡，代价是每次访问的粒子更分散，缓存局部性变差。


看 `block` 和 `force_cyclic` 两组：从 2 线程起，只有力循环用循环划分的版本明显更快。再看 `all_cyclic`：把求和与更新也改成循环划分，和 `force_cyclic` 互有胜负，没有稳定的额外收益。完整程序：[24_3_schedule.cpp](code/ch24/24_3_schedule.cpp)。

原因在 `forces[q]`：相邻 q 被不同线程写，落在同一条缓存行上，伪共享的窗口变大了。求和和更新只占一个时间步的一小部分，所以伪共享的代价没有把整体拖慢，差值不大，也随运行波动。

{{#fig ch24/nbody_pipeline}}

图是简化版默认（块划分）的一个时间步：清零不划分，每个线程清自己那一行；算力用循环划分，按粒子求和、更新用块划分。三个 `omp for` 末尾各有一个隐式屏障：算力写完力才能求和，求和写完 `forces` 才能更新，更新写完位置才能算下一步。

伪共享和真正的共享是两回事。两个线程各加各的计数器，结果完全正确，但两个计数器若在同一条缓存行，性能会差几倍，完整程序见 [24_3_false_sharing.cpp](code/ch24/24_3_false_sharing.cpp)：

`std::hardware_destructive_interference_size` 有三点要注意：

- 本机 GCC 15 和 Clang 21 都报 64，它只是实现给的提示值；
- ARM 等平台可能不同，`alignas(64)` 也不是跨平台保证；

三种调度的代价不同：

| 调度 | 什么时候分 | 代价 |
|---|---|---|
| `static` | 进入循环时一次分完 | 最便宜，负载不均时最慢的线程拖住全体 |
| `dynamic` | 每次领一块 | 块越小，领任务的开销越大 |
| `guided` | 块从大到小 | 比 `static` 贵，兼顾开头大块和结尾小块 |

负载不可预测时，先用 `runtime` 配合 `OMP_SCHEDULE` 做实验，再把选中的调度写死。

`OMP_PROC_BIND`/`OMP_PLACES` 把线程绑到核，影响缓存和 NUMA 就近访问，它们不决定谁做哪些迭代。系统调用一侧，[sched_setaffinity(2)](https://man7.org/linux/man-pages/man2/sched_setaffinity.2.html) 设置线程的 CPU 亲和性，[pthread_setaffinity_np(3)](https://man7.org/linux/man-pages/man3/pthread_setaffinity_np.3.html) 是 pthread 的封装；两者也只影响线程落在哪个核。

线程数也不等于核数：SMT 的兄弟线程共享执行单元，内存带宽可能先饱和。`hardware_concurrency()` 只是逻辑线程数的提示，取不到时返回 0。

## 24.4 TSP 串行基线：递归、迭代与数据结构

TSP 的搜索树以家乡为根，每个结点是一条部分回路。`Feasible` 用当前最佳代价剪枝，`Best_tour` 在叶子处比较，`Update_best_tour` 更新全局最优。`best_tour_cost` 初始化为比任何可能回路都大的值。

12 个城市已经能展开上百万个结点，规模再大就要靠更好的下界或更强的剪枝。

{{#fig ch24/tsp_tree}}

图里有一条被剪掉的枝和一条走到叶子的枝。剪枝的条件是“已走代价 + 下一条边 ≥ 当前最优”，不是“这条回路一定不优”；所以剪枝只影响速度，不影响正确性。

递归 DFS 最直观：

```cpp
void dfs(Tour& t) {
    if (t.n == N) { consider_leaf(t); return; }
    for (int v = 0; v < N; ++v)
        if (feasible(t, v)) {
            add_city(t, v);
            dfs(t);
            remove_last_city(t);
        }
}
```

它只有当前结点可访问，不方便把子树分给别的线程。非递归版用显式栈保存整条部分回路，每个栈元素都是一份可以独立取走的任务，代价是复制。

```text
{{#include code/ch24/24_4_tsp_serial.out}}
```

- 两种写法的结点数完全相同，最佳回路也相同，因为遍历顺序一致：递归按 v 从小到大，迭代把子城市倒序压栈，出栈还是从小到大；
- 迭代版明显慢一截，时间花在复制整条回路上，但这个“更慢的串行算法”正是后面并行化的基础：栈里的任务可以独立取走，递归的调用栈不行；
- 完整程序：[24_4_tsp_serial.cpp](code/ch24/24_4_tsp_serial.cpp)。

数据结构影响复制成本：

- 回路用固定长度数组加城市数，不额外分配；
- 栈用 `std::vector` 并预留容量，热循环里不反复分配；
- 邻接矩阵只读，所有线程共享一份，不需要锁。

多解时结果不唯一，计时也不稳定。输出要打印最佳代价和访问到的结点数，不要只打印时间；否则一次运行变快，分不清是剪枝更好还是少搜了。

动态划分让空闲线程在条件变量上等待；有工作的线程发现有人在等，就把自己的栈分离出一半，`notify_one` 交给等待者。

{{#fig ch24/split_stack}}

分离时按部分回路的边数（已访问城市数）轮流分配，让两边任务量接近，城市数达到“截止大小”的回路不再拆分，因为对应子树已经很小。

临界区要保护三件事：等待线程数、待交接的 `new_stack`、以及“是否已经没有工作”。先快速检查，加锁后再检查一次，避免检查后被别人改掉。


这次四个线程的结点数接近，总时间比静态版短。代价是 `splits` 和栈复制：分得太细，线程会把时间花在“为分任务而分任务”上。截止大小和初始 BFS 深度要一起调，没有一组值对所有图都好，完整程序见 [24_5_tsp_dynamic.cpp](code/ch24/24_5_tsp_dynamic.cpp)。

| 方案 | 优点 | 代价 | 什么时候更好 |
|---|---|---|---|
| 静态 | 同步少：只在更新最佳代价时加锁/原子读写，无栈复制，结果稳定 | 子树不一时负载不均 | 子树工作量接近，或线程数少 |
| 动态 | 负载均衡，适合不规则搜索 | 条件变量、锁、栈复制 | 子树大小差异大，线程数多 |

## 24.6 终止检测：条件变量、原子计数与丢失唤醒

朴素的终止判断是“我的栈空、所有线程都空闲”。但“某个线程的栈空”不等于“它以后不会收到任务”：工作可能在栈之间传递，也可能由外部生产者提交，检查之后才到达。

> **旧资料提示**：旧写法用普通 `int` 无锁读 `best_tour_cost`，再用 `volatile` 防止优化。C++11 起，未同步的读写是数据竞争，`volatile` 不建立先行发生关系；改用 `std::atomic<int>` 或始终持锁。原因见 [38 章](ch38.md)。

## 24.7 三种实现对比与选择

- 三条曲线都远低于 `y=x`；Pthreads 和 std::thread 到 8 线程以后还在涨，但每增加一个线程带来的增益比 4 到 8 线程时小；
- OpenMP 还能再涨一段：它的线程组一直活着，屏障和等待策略与另外两版不同；
- 一种解释是 Pthreads 和 `std::barrier` 每次同步可能让线程睡下；每步计算不够大时，唤醒和迁移的成本更明显；
- 这不是“OpenMP 一定更快”的结论，具体原因要在本机 profile，换一个问题曲线就会变。

共享内存的通信比 MPI 便宜，但伪共享、缓存一致性和锁争用会把收益吃掉；同样 4 线程，静态划分和动态划分的胜负取决于子树工作量的分布，不能只看平均耗时。

计时和指标有三条规矩：

- 用 `std::chrono::steady_clock`，先预热、重复取中位数；
- 加速比 `S=T1/Tp`、效率 `E=S/p`，强可扩展和弱可扩展要分开说；
- 2011 年的绝对时间不能外推到今天的机器：核数、NUMA、SMT 和内存带宽都变了，必须重测。

共享内存并行的三套写法，差别集中在这几行：

| 维度 | Pthreads（C） | OpenMP（C/C++） | C++ 标准库 |
|---|---|---|---|
| 创建 | `pthread_create` 逐个建，属性用 `pthread_attr_t` | `parallel` 隐式建线程组 | `std::thread`/`std::jthread` 逐个建 |
| 数据共享 | 全局/堆共享，局部私有 | `shared`/`private`/`firstprivate` 子句 | 捕获列表决定复制还是引用 |
| 循环划分 | 自己算每个线程的起止和步长 | `schedule(static/dynamic/guided)` | 没有；自己切或交给并行算法 |
| 屏障 | `pthread_barrier_t`（可选），或条件变量手写 | `barrier`，`for` 末尾隐式屏障 | `std::barrier`/`std::latch`（C++20） |
| 条件变量 | `pthread_cond_t` | 没有，只能忙等或 `task` | `std::condition_variable` |
| 取消 | `pthread_cancel`，延迟或异步 | `cancel`，协作式 | `std::stop_token`，协作式（C++20） |
| 错误报告 | 返回错误码 | 运行时通常不报错 | 构造/加锁失败抛 `std::system_error` |
| 代码量 | 最多 | 最少 | 中等 |

选型先看内存模型：跨节点、内存装不下，用 MPI（第 29–31 章）；共享内存里能用 `parallel for` 表达，用 OpenMP；需要条件变量、读写锁、细粒度同步，用 Pthreads 或 C++ 标准库。

`std::async` 不是线程池。标准允许它每次新建线程，递归调用可能创建过多线程，它也没有可以配置的线程数。`std::execution`（C++26）是另一套 sender/receiver 模型，本机 GCC 15 / Clang 21 未实现，不能拿它当“标准库线程池”。

> **旧资料提示**：`#pragma omp master` 表示“线程 0 执行”。OpenMP 5.1 起它被弃用，改用 `masked`；GCC 15 已经接受 `masked`，但 `_OPENMP` 仍报 4.5，不能靠宏判断单个特性。原因见 [40 章](ch40.md)。

## 速查

| 设施 | 用途 | 代价 | 坑 |
|---|---|---|---|
| `parallel` + `for` | 建线程组、分迭代 | 每次进入有开销，`for` 末尾有屏障 | `parallel` 放进时间步循环会反复建组 |
| `schedule(static)` | 进入时一次分完 | 最便宜 | 负载不均时最慢的线程拖住全体 |
| `schedule(static,1)` | 按 1 个一块轮转 | 局部性变差 | 相邻写可能伪共享 |
| `schedule(dynamic)` | 谁空谁领 | 每次领任务有开销 | 块太小会把时间花在领任务上 |
| `schedule(guided)` | 块从大到小 | 比 static 贵 | 块大小是实现给的，不保证 |
| `critical` | 块级互斥 | 未命名时全局共锁 | 不能 try、不是 RAII |
| `atomic` | 单条标量更新 | 比普通写贵 | 不保护同句的其他副作用 |
| `barrier` | 团队同步 | 线程越多越贵 | 不能只让部分线程到达 |
| `omp_lock_t` | 数据结构的锁 | 手动 init/destroy | 异常路径不会自动解锁 |
| `omp_test_lock` | 非阻塞加锁 | 轮询耗 CPU | 成功返回非 0，和 `pthread_mutex_trylock` 相反 |
| `reduction` | 私有副本加合并 | 合并顺序未指定 | 浮点末位会变 |
| `firstprivate`/`private` | 每线程副本 | 有拷贝成本 | `private` 不初始化、不写回 |
| `std::thread`/`jthread` | 线程对象 | 创建/汇入有开销 | `jthread` 析构会请求停止再 join |
| `std::condition_variable` | 等待/唤醒 | 虚假唤醒、通知丢失 | 必须用谓词循环 |
| `std::atomic<int>` | 无锁共享标量 | 比普通读贵 | 只保护这一个变量 |
| `std::barrier`/`latch` | 屏障/一次性闩 | C++20；实现可能睡线程 | 参与线程数要固定 |
| `hardware_destructive_interference_size` | 缓存行间距提示 | 只是提示值 | 不要写死到协议里 |
| `alignas` | 对齐请求 | 过度对齐要有分配器支持 | 不是跨平台缓存行保证 |
| `steady_clock` | 墙钟计时 | 分辨率依实现 | 不要用 `system_clock` 测间隔 |

## 思考题

1. 24.3 的简化 n 体，如果把所有循环都改成 `schedule(static,1)`，8 线程的耗时会比“只有力循环循环划分”更好还是更差？为什么？

   <details><summary>提示</summary>

   先看 `24_3_schedule.out` 的 `all_cyclic` 行。力循环需要循环划分来均衡；求和和更新只占一小部分，改成循环划分不会让负载更均，反而让相邻的 `forces[q]` 被不同线程写，增加伪共享。差值不大，但方向稳定。

   </details>

2. 24.6 的终止判断如果只把 `if` 改成 `while`、不把“队列为空”和“空闲计数”放在同一把锁下，还会不会提前退出？画出那个窗口。

   <details><summary>提示</summary>

   会。`while` 只解决虚假唤醒，不解决复合条件的原子性。若“队列为空”用另一把锁或原子变量读，“空闲计数”用另一把锁，两个检查之间别人可以把任务放进队列、把计数加一；你看到的仍是“空且都空闲”。把两件事放进同一把锁，或用一个关闭标志加谓词。

   </details>

3. 24.5 的分离栈，截止大小调大和调小分别会让“任务太少”还是“同步太多”成为瓶颈？静态划分在什么数据分布下反而更好？

   <details><summary>提示</summary>

   截止大小调小，深层的回路不再拆，太多子树留在一个线程，任务太少、负载不均；调大，深层的回路也拆，分离次数和栈复制变多，同步成为瓶颈。静态划分在子树工作量接近、或线程数很少时更好，因为它没有条件变量和栈复制的开销。

   </details>

4. 把 24.2 的两阶段局部力数组用到 24.4 的 TSP 上，哪些共享状态可以照搬，哪些必须换成“每线程最佳代价 + 最后归约”？

   <details><summary>提示</summary>

   邻接矩阵只读，可以照搬共享。`best_cost` 不能照搬“每线程一行再求和”，因为最优是取最小，不是相加；可以让每个线程维护本地最优，最后取 `min`，或者用 `std::atomic<int>` 配 CAS。局部栈本来就是每线程私有的，不需要归约。

   </details>
