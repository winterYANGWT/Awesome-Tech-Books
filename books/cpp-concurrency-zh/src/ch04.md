# 第 4 章 竞争条件与互斥量

两个线程各对同一个 `uint64_t` 加 100 万次，程序打印的数几乎每次都不一样，多数运行小于 200 万。把 `counter++` 换成 `counter.fetch_add(1)`，结果稳定在 200 万；换成两个必须一起更新的字段，数字又开始漂。

问题不在“加一”这条指令，而在“读—改—写”被拆成了三步，以及“多个字段必须一起变”这个条件没有被守住。

## 4.1 不变量、条件竞争与数据竞争

不变量（invariant）是程序在任何时刻都必须成立的条件，例如“链表里的每个结点只出现一次”“所有账户的余额之和等于总额”。线程交错执行时，一个操作可能只完成了前半步，不变量就在这段中间状态里被破坏。

条件竞争（race condition）是结果依赖执行顺序的现象。两个线程各往线程安全的日志里追加一行，先 A 后 B 和先 B 后 A 都是合法的两行日志，这是良性竞争；两个线程同时修改同一个账户，顺序会改变余额，这是恶性竞争。

{{#fig ch04/race_tree}}

数据竞争（data race）是语言层面更窄的定义：两个线程访问同一内存位置，至少一个是写，至少一个不是原子操作，而且两次访问之间没有先行发生（happens-before）关系。满足这些条件的程序有未定义行为，编译器可以假设它不会发生。

| 概念 | 判据 | 后果 |
|---|---|---|
| 不变量 | 任何观察点都必须成立的条件 | 被中间状态破坏时，程序逻辑出错 |
| 条件竞争 | 结果依赖执行顺序 | 良性竞争可以接受，恶性竞争不行 |
| 数据竞争 | 同一内存位置、至少一个写、无先行发生关系 | 未定义行为 |

C++ 的“内存位置”不总是一个独立变量。同一个结构体里相邻的两个位域可能共用同一个内存位置，两个线程分别写它们仍然是数据竞争；两个位域之间隔着零长度位域或普通成员时，才落在不同位置。

两种常见的错误修法：
- `volatile` 不提供原子性，也不建立先行发生关系，不能拿来修数据竞争。
- `-O0` 只是让编译器暂时不重排，错误仍然存在。

检测手段是 ThreadSanitizer（TSan）加重复运行，但 TSan 只覆盖实际执行到的路径，不能证明没有竞争。

## 4.2 互斥量与 RAII

`std::mutex` 提供 `lock()`、`unlock()` 和 `try_lock()`，不可复制、不可移动。标准要求调用 `lock()` 的线程不持有该 mutex；同一线程重复加锁、非持有者 `unlock()`、析构时仍被锁，都是未定义行为。

{{#fig ch04/mutex_states}}

不要手写 `lock()`/`unlock()`。`std::lock_guard` 在构造时加锁、析构时解锁，是最小的 RAII 包装；C++17 起可以写 `std::lock_guard guard(m);`，模板参数由构造函数推导。

| 锁对象 | 构造 | 所有权与能力 | 适用场景 |
|---|---|---|---|
| `std::lock_guard` | 构造即加锁，可接 `adopt_lock` | 不可移动，不能手动解锁 | 一个作用域只锁一把锁 |
| `std::unique_lock` | 可 `defer_lock`、`try_to_lock`、`adopt_lock` | 可移动、可手动加解锁、可查询 `owns_lock()` | 需要延迟加锁、转移所有权、配条件变量 |
| `std::scoped_lock` | C++17，构造时锁住一个或多个 | 不可移动，析构时全部解锁 | 一次锁多把，按内部算法避免死锁 |

`std::scoped_lock` 锁多把时调用 `std::lock`，要么全锁住，要么一把都不锁；`std::try_lock` 是非阻塞版本，全部成功返回 `-1`，否则返回第一个失败的参数的零基下标，并释放之前已经拿到的锁。

| 方案 | 优点 | 代价 |
|---|---|---|
| `void pop(T&)` | 不额外分配，接口简单 | 元素必须可拷贝或移动，且移动不能抛异常 |

| 保留 `empty()` | 兼容旧调用 | 检查和操作之间仍然有接口竞争 |

## 4.4 锁的粒度、`unique_lock` 与所有权

粒度是“一把锁保护多少数据、持有多久”。

`std::unique_lock` 的所有权可以随返回值移出函数，用来实现“加锁后把访问权交给调用者”的网关。调用者要守住两条：
- 锁对象不能比它保护的数据活得更久。
- 数据也不能在锁对象之前被销毁。

`std::unique_lock` 支持 `defer_lock`、`try_to_lock`、`adopt_lock`、`owns_lock()`、手动 `lock()`/`unlock()` 和移动，`lock_guard` 没有这些能力，也更小。

一次锁多个互斥量用 `std::scoped_lock` 或 `std::lock`，不要自己按两个方向分别加锁。死锁的完整讨论在第 5 章。

> **旧资料提示**：旧教程里写完整的 `std::lock_guard<std::mutex>`，再用 `std::lock` 配 `adopt_lock`。C++17 起可以写 `std::lock_guard guard(m);`，多把锁直接用 `std::scoped_lock`，见 [37.4 节](ch37.md)。

## 4.5 互斥量的底层：futex 与等待队列

Linux 上 `std::mutex` 和 `pthread_mutex_t` 的无竞争路径通常在用户态用原子指令完成，不进入内核；有竞争时才调用 `futex(2)`。

{{#fig ch04/futex}}

`FUTEX_WAIT` 做两件事：
- 比较用户态的值和期望值，相等才睡眠，不等则返回 `EAGAIN`。
- 把比较和睡眠放在内核里一次完成，避免“检查后可以睡，真正睡下时唤醒已经过去”的丢失唤醒。

`FUTEX_WAKE` 唤醒等待队列上的一个或多个线程。

futex 的版本和实现边界：
- 完整的 futex 语义从 Linux 2.6 起，2.5.7 有过语义不同的早期版本。
- 具体实现不是标准的一部分，不能假设某个 `std::mutex` 一定用 futex。

## 4.6 pthread 互斥量与 C11 对照

pthread 互斥量有五个基本函数：`pthread_mutex_init`、`destroy`、`lock`、`trylock`、`unlock`。属性参数传 `NULL` 用默认值；全局或静态锁可以用 `PTHREAD_MUTEX_INITIALIZER`，`pthread_mutex_t` 不能拷贝。

`pthread_mutex_trylock` 成功返回 0，普通锁被其他线程占用时返回 `EBUSY`；这是错误码，不设置 `errno`。销毁仍被加锁的互斥量是未定义行为，glibc 可能返回 `EBUSY`，但不能依赖。

| 属性 | 类型固定，无属性对象 | `pthread_mutexattr_t` | `mtx_init` 的类型参数 |
| 递归 | 用 `std::recursive_mutex` | `PTHREAD_MUTEX_RECURSIVE` | `mtx_recursive` |
| 超时 | 用 `std::timed_mutex` | `pthread_mutex_timedlock` | `mtx_timed` + `mtx_timedlock` |
| 跨进程 | 不提供 | `PTHREAD_PROCESS_SHARED` | 不提供 |
| robust | 不提供 | `PTHREAD_MUTEX_ROBUST` | 不提供 |
| 析构 | 析构函数，持有锁时未定义 | `pthread_mutex_destroy`，持有锁时未定义 | `mtx_destroy` |

POSIX 不保证等待顺序，“普通锁按优先级排队”是旧教程的误读。优先级继承要用 `PTHREAD_PRIO_INHERIT` 属性，标准库没有这个旋钮。需要公平性时，只能在接口层自己排队。

## 速查

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `std::mutex` | 独占互斥量 | 不可复制、不可移动；重入、非持有者解锁、带锁析构都未定义 |
| `std::lock_guard` | 构造加锁、析构解锁 | C++17 起可 CTAD；不能手动解锁 |
| `std::unique_lock` | 可延迟、可移动、可手动解锁 | 比 `lock_guard` 大；条件变量要求它 |
| `std::scoped_lock` | 一次锁多个 | C++17；内部用 `std::lock` 避免死锁 |
| `std::lock` / `std::try_lock` | 一次锁多个 / 非阻塞尝试 | `try_lock` 全成功返回 `-1`，否则返回失败下标 |
| `defer_lock` / `try_to_lock` / `adopt_lock` | 延迟 / 尝试 / 接管 | `adopt_lock` 要求调用者已经持有锁 |
| `std::recursive_mutex` | 同线程可重入 | 解锁次数必须配平，通常应改设计 |
| `std::timed_mutex` | 带超时的互斥量 | 用 `try_lock_for` / `try_lock_until` |
| `pthread_mutex_init` / `destroy` | 初始化 / 销毁 | 属性传 `NULL` 用默认；不能拷贝 |
| `PTHREAD_MUTEX_INITIALIZER` | 静态初始化 | 只用于全局或静态锁 |
| `pthread_mutex_trylock` | 非阻塞加锁 | 成功 0，占用 `EBUSY`，不设 `errno` |
| `pthread_mutexattr_settype` | 选 NORMAL/ERRORCHECK/RECURSIVE/DEFAULT | 默认 NORMAL；DEFAULT 在 glibc 上同 NORMAL |
| `pthread_mutexattr_setpshared` | 进程间共享 | 还要把锁放进共享内存 |
| `pthread_mutexattr_setrobust` | 持有者死亡后的恢复 | `EOWNERDEAD` 后要 `pthread_mutex_consistent` |
| `futex(2)` 的 `FUTEX_WAIT`/`FUTEX_WAKE` | 睡眠 / 唤醒 | 值不等时 `WAIT` 返回 `EAGAIN` |

## 思考题

1. 把 `4_1_lost_update.cpp` 的 `counter++` 换成 `counter.fetch_add(1, std::memory_order_relaxed)`，结果一定是 2000000 吗？如果主线程在 `join` 之前读一次 `counter`，能读到什么范围？

   <details><summary>提示</summary>

   一定是 2000000：原子的读—改—写不会丢更新，和内存序无关。`join` 之前读到的值一定在 0 到 2000000 之间，具体是多少没有保证；`join` 之后才能读到最终值。

   </details>

2. `4_3_pointer_escape.cpp` 里如果回调只在锁内使用指针、不保存，是否就没有问题？如果回调又启动一个线程呢？

   <details><summary>提示</summary>

   只在锁内使用没有问题，指针没有离开临界区。如果回调把指针交给新线程，新线程在锁外访问它，锁的保护范围又没有覆盖到，就重新变成数据竞争；回调必须保证不把引用带出去。

   </details>

3. 一个读多写少、每个操作只读一个字段的计数器，用 `std::mutex`、`std::atomic` 还是 `std::shared_mutex`？各自保护的是什么？

   <details><summary>提示</summary>

   单个计数器用 `std::atomic` 最直接，它保护的是这一个值的读—改—写；`std::mutex` 保护一段临界区，适合多个字段一起变；`std::shared_mutex` 保护的是读写之间的排斥，只有读操作占大多数、临界区又较长时才可能划算。

   </details>

4. 把 `4_2_mutex_sum.cpp` 改成每个线程先累加到私有变量、最后只加一次全局变量，临界区次数从多少次降到多少次？

   <details><summary>提示</summary>

   从每个线程 100 万次、共 200 万次加锁，降到每个线程结束时一次、共 2 次。代价是每个线程多一个局部变量和最后一次合并；这也是贯穿示例从共享累加器走向私有累加的那一步。

   </details>
