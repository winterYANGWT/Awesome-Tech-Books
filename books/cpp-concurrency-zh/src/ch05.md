# 第 5 章 死锁与加锁的规矩

转账程序压测几万次才挂一次：两个线程都停在“开始转账”，CPU 占用为 0。把栈取出来，一个停在 `lock(账户2)`，另一个停在 `lock(账户1)`。

{{#fig ch05/deadlock_conditions}}

死锁要同时满足四个条件，破坏任意一个就能避免：

- 互斥：资源一次只能一个线程用；只读数据或复制数据可以绕开。
- 持有并等待：拿着锁再等下一把；一次全锁，或先拿齐再开始。
- 不可抢占：别人不能把锁拿走；用 `try_lock` 失败回滚或超时。
- 循环等待：等待关系首尾相接；固定顺序或层级锁。

四个条件里，互斥通常最难去掉：只要还要写共享数据，就得有某种排斥。工程上更常破坏后三个，尤其是循环等待。

同一个线程也可能把自己锁死。标准要求调用 `lock()` 的线程不持有该锁；违反这个前条件就是未定义行为，libstdc++ 的实现通常直接挂住，不能依赖它报错。

| 场景 | 结果 |
|---|---|
| 同一线程对 `std::mutex` 重复 `lock()` | 未定义行为；libstdc++ 通常挂住 |
| 同一线程对 `PTHREAD_MUTEX_NORMAL` 重复加锁 | 死锁 |
| 同一线程对 `PTHREAD_MUTEX_ERRORCHECK` 重复加锁 | 返回 `EDEADLK` |
| `std::thread` join 自己 | 抛 `std::system_error`，错误条件是 `resource_deadlock_would_occur` |
| 两个线程互相 join | 通常挂起，`pthread_join` 可能报 `EDEADLK` |

这些场景的共同点是等待关系没有出口：要么等自己，要么等一个不会结束的线程。自 join 的错误码和互相 join 的挂起，区别在于实现能不能看出环。

`std::thread::join()` 发现自己 join 自己时会报错；两个线程互相 join 时，检测不保证成功，libstdc++ 上就是一起等下去。`pthread_join` 的错误码 `EDEADLK` 也只表示“检测到了”，不是保证。

`sleep` 只能把时间窗口开大，不能保证两个线程一定按那个顺序走到锁前。稳定复现靠的是同步点，不是时间：

- `std::latch`：等 N 个线程到齐再一起走。
- `std::barrier`：分阶段，每阶段一起继续。
- 条件变量：等谓词成立再继续。

> **旧资料提示**：旧教程里用 `sleep` 制造交错来演示死锁。`sleep` 只扩大窗口，不保证顺序；C++20 起可以用 `std::latch`/`std::barrier` 固定交错，见 [第 37 章](ch37.md)。

## 5.2 全锁或全不锁：`std::lock` 与 `scoped_lock`

`std::lock(m1, m2, ...)` 的约定是：调用返回时要么每把锁都拿到，要么一把都不持有。中间可能先拿一部分再退回去；典型实现先锁一把，再逐个 `try_lock` 其余，失败就释放已拿到的锁，退避后重试。

它消除的是“相反顺序”这一类环，不保证公平，也不保证不活锁。标准只要求调用序列不导致死锁，具体算法留给实现。

`std::lock` 只保证两件事：

- 正常返回时，参数里的锁全部由当前线程持有。
- 抛异常时，它会把这次已经拿到的锁释放掉。

`std::try_lock` 是非阻塞版本：全部成功返回 -1，否则返回第一个失败的参数下标，并把之前拿到的锁释放掉。它适合“试一下，失败就做别的”的场景，不适合拿来空转。

`try_lock` 失败后立刻重试会空转，必须有退避。退避可以是让出 CPU、短暂睡眠或随机化等待时间，目的都是让另一方能推进。

| 方案 | 运行期锁集合 | 可能活锁 | 代码侵入 | 适用场景 |
|---|---|---|---|---|
| 固定全局顺序 | 能，自己排序 | 否 | 小，靠约定和评审 | 锁的编号稳定，跨团队 |
| `std::lock` | 不能，参数个数编译期固定 | 实现可能重试 | 小 | 少量已知的锁 |
| `std::scoped_lock` | 不能 | 同上 | 最小 | C++17 起一次锁多把 |
| `try_lock` 回滚 | 能 | 是，必须退避 | 大 | pthread、运行期锁集合 |
| 层级锁 | 能，逐个检查 | 不能消除同层环 | 中，调试构建 | 抓同线程的顺序错误 |

`std::lock` 的“全锁或全不锁”是返回时的状态，不是整个过程都不持有任何锁；别的线程可能在这段时间里看到其中一把已被持有，但调用者不会带着半套锁返回。所以它不是让多个锁变成一个原子操作。

## 5.3 层级锁与运行时检查

层级锁给每把锁一个数值，规定只能从高层级锁到低层级。`lock()` 前检查当前线程已持有的最高层级，违反就抛异常或返回错误。

{{#fig ch05/hierarchy}}

实现用 `thread_local` 保存当前层级。`lock()` 成功后把当前值设为这把锁的层级，同时把上一层存进锁对象；`unlock()` 恢复上一层。

`try_lock()` 走同样的检查，失败时不能改当前值。检查只读当前线程的 `thread_local`，所以两个线程各持一把同层锁再互相请求，它抓不到。

| 能抓到 | 抓不到 |
|---|---|
| 同一线程先持低层锁、再请求高层锁 | 两个线程各持一把同层锁，再按相反顺序请求 |
| `try_lock()` 里的同样违规 | 跨进程的锁，`thread_local` 不共享 |
| 调试构建里的顺序错误 | 运行期才知道下标的锁集合 |

更常见的做法是给锁规定全局顺序：按地址、按桶下标、按账户 ID。把顺序写进类型名、注释或封装函数，再用代码评审和静态检查保证。

层级值不必连续，10000、5000、1000 只是给读者看的顺序；真正参与比较的是数值大小。

`std::scoped_lock` 不做层级检查，`std::lock` 也只处理一次调用里的多把锁；运行时检查有成本，通常只在调试构建里开，发布构建关掉后就退化成普通互斥量。

> **旧资料提示**：手写 `hierarchical_mutex` 做层级检查、用 `std::lock` 加 `adopt_lock` 锁多个，是 C++11 时代的写法。C++17 的 `std::scoped_lock` 解决一次锁多个；标准仍没有层级锁，见 [第 37 章](ch37.md)。

{{#fig ch05/join_deadlock}}

`std::jthread` 的析构会先 `request_stop()` 再 `join()`，析构发生在持锁作用域里同样会挂。`std::async` 返回的 future 也要小心。`launch::async` 下销毁最后一个引用共享状态的 future 时，如果任务还没结束，标准允许它阻塞到任务完成，在持锁时销毁就会把等待带进锁里。

线程池里任务等待子任务也能死锁：固定数量的工作线程全部在等自己提交的任务，没有线程去执行队列里的任务。修法是让等待者帮忙执行队列里的任务（`run_pending_task()`）、用工作窃取，或者限制任务依赖。等待者帮忙时还要防止任务继续提交子任务，把递归深度变成新的死锁。

条件变量等待会释放互斥量，被唤醒后重新加锁。通知方若持锁调用 `notify`，被唤醒的线程会先阻塞在重新加锁上；通常先解锁再通知，减少无谓的阻塞。

| 等待方 | 被等方需要的资源 | 修法 |
|---|---|---|
| 持锁 `join` 的主线程 | worker 要同一把锁才能结束 | 先解锁再 `join`，或让 worker 不依赖这把锁 |
| 销毁 future 的线程 | 任务要同一把锁才能完成 | 在锁外销毁最后一个 future，或先 `wait()` |
| 线程池里的任务 | 空闲工作线程执行子任务 | `run_pending_task()`、工作窃取、限制依赖 |
| 条件变量的通知方 | 等待者被唤醒后要重新加锁 | 先解锁再 `notify`，不要在持锁时等对方 |

条件变量的通知本身不阻塞，但被唤醒的线程要先重新加锁才能从 `wait` 返回。关闭顺序也属于这一类：先 `request_stop()` 或置停止标志，再 `join`，不要在持锁时做这两件事。

多线程进程里 `fork` 还有另一种等待：子进程只复制调用 `fork` 的线程，却继承其他线程留下的锁状态。若某把锁在 `fork` 时正被别的线程持有，子进程再锁它就是永久等待。`pthread_atfork` 只能在 `fork` 前后处理注册过的锁，实际项目更稳妥的做法是 `fork` 后立刻 `exec`，或用 `posix_spawn`。

等待线程结束也可以看成一把“线程锁”：只等待比自己低层的线程，能避免互相 join 的环。

## 5.5 活锁、饥饿与公平性

死锁是谁也不动，活锁是线程一直在动但系统状态不前进，饥饿是某个线程长期拿不到资源。

| 现象 | 线程在做什么 | 系统状态 |
|---|---|---|
| 死锁 | 都阻塞在等待 | 不前进 |
| 活锁 | 都在重试或让路 | 不前进 |
| 饥饿 | 别人一直成功，它一直失败 | 整体在前进，它没有 |

活锁和死锁都会让完成计数停住，区别是活锁的线程仍在消耗 CPU，栈里看到的是重试循环而不是 `futex` 等待。

gdb 里主线程停在 `sleep_for`，两个工作线程都停在 `SpinBarrier::wait()` 第 24 行。栈里没有 `futex` 等待。

加随机退避通常能打破对称：失败后等一个随机时间再重试，让两边错开。它不保证一定成功，只是把“每次同时撞上”变成小概率事件；退避可以按这个顺序加：

- 先 `yield()`，让出一次 CPU。
- 再短暂 `sleep_for`，时间随失败次数翻倍。
- 最后加 jitter，让两个线程不在同一刻醒来。

饥饿是另一回事。POSIX 不保证互斥量或读写锁的等待顺序，glibc 的普通互斥量不承诺 FIFO；读写锁默认读者优先时，写者可能长期等待。

读者优先的锁在读者源源不断时，写者只能等读者空档；写者优先的锁会让新读者排到写者后面。

公平性不是正确性的一部分：程序不挂，但某个线程可能一直拿不到锁。

两个可移植性限制：

- `pthread_rwlockattr_setkind_np` 是 GNU 扩展，不是 POSIX。
- glibc 忽略 `PTHREAD_RWLOCK_PREFER_WRITER_NP`，要用 `PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP`；标准库 `std::shared_mutex` 没有对应旋钮。

优先级反转是另一种饥饿：低优先级线程持锁，高优先级线程等锁，中优先级线程抢占 CPU。带 `PTHREAD_PRIO_INHERIT` 的互斥量能缓解，标准库没有这个属性。

`std::mutex` 的自旋和调度策略会影响尾延迟。只测吞吐量不够，还要看最大等待时间；`yield` 只是让出 CPU，不保证别的线程能前进。

> **旧资料提示**：认为普通互斥量按优先级公平排队，是旧教程的误读。POSIX 不保证等待顺序或公平性；需要公平或优先级继承要用实时互斥量或自己实现，见 [第 37 章](ch37.md)。

## 5.6 调试死锁：gdb 与超时

死锁程序不会自己退出。先在脚本里用 `timeout` 限时，再取栈；`timeout` 因超时退出时返回 124，脚本据此判断“它挂住了”。


- CPU 占用接近 0：更像死锁。

## 速查

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `std::lock` | 一次锁多个互斥量 | 返回时全锁或全不锁；算法由实现决定 |
| `std::try_lock` | 非阻塞地试多个 | 全成功返回 -1，否则返回第一个失败的下标 |
| `std::scoped_lock` | C++17 的 RAII 多锁 | 构造时调用 `std::lock`；不做层级检查 |
| `std::defer_lock` / `adopt_lock` | 延迟加锁 / 接管已加锁 | `adopt_lock` 要求调用者已持有锁 |
| `std::unique_lock` | 可移动、可手动加解锁 | 条件变量和两阶段加锁用得上 |
| `pthread_mutex_trylock` | 非阻塞加锁 | 成功 0，占用 `EBUSY` |
| `PTHREAD_MUTEX_ERRORCHECK` | 检错互斥量 | 重复加锁返回 `EDEADLK` |
| `PTHREAD_PRIO_INHERIT` | 优先级继承属性 | 标准库没有对应旋钮 |
| `pthread_rwlockattr_setkind_np` | 改读写锁偏好 | GNU 扩展；`PREFER_WRITER_NP` 在 glibc 上被忽略 |
| `std::latch` / `std::barrier` | 固定线程交错 | C++20；比 `sleep` 可靠 |
| `thread apply all bt` | 打印所有线程的栈 | 配合 `set pagination off` |
| `info threads` / `thread N` / `frame N` | 选线程和栈帧 | 取栈后用 |
| `set scheduler-locking on` | 单步时冻结其他线程 | 取栈不需要 |
| `timeout` / `pstack` / `gcore` | 限时、取栈、生成 core | `pstack` 很多发行版不装 |
| `/proc/<pid>/task/<tid>/wchan` | 看线程的等待点 | 内核栈 `stack` 需要权限 |

## 思考题

1. 把 `5_1_abba_deadlock.cpp` 的 `std::mutex` 换成 `std::recursive_mutex`，死锁会消失吗？如果两个线程仍然按相反顺序锁两把不同的锁呢？

   <details><summary>提示</summary>

   换成 `std::recursive_mutex` 不会让两个线程的 ABBA 消失：A 持有 m1 等 m2，B 持有 m2 等 m1，重入能力帮不上忙。它只允许同一线程对同一把锁重复加锁；两把不同的锁仍然是两个独立的等待。

   </details>

2. `5_4_join_under_lock.cpp` 里把 `join` 移到解锁之后，为什么还可能死锁？如果工作线程需要主线程先设置一个标志呢？

   <details><summary>提示</summary>

   把 `join` 移出锁作用域能解决“主线程持锁等 worker”的环，但如果 worker 还要等主线程先设置标志，而主线程在 `join` 之后才设置，环就换到了标志上。要先把标志置好、通知 worker，再 `join`；或者让 worker 自己检查停止条件。

   </details>

3. 一个桶数组有 64 把锁，运行期要一次锁 3 个桶；用 `std::scoped_lock`、按下标排序逐个锁、还是一把大锁，各自在什么负载下更好？

   <details><summary>提示</summary>

   `std::scoped_lock` 只能锁编译期已知个数的锁，3 个桶可以在分支里展开成 3 个参数，但下标组合多时很笨。按下标排序适合大多数并发读写；一把大锁在冲突少、临界区短时最简单，冲突多时会拖住所有桶。

   </details>

4. 把 `5_3_hierarchical_mutex.cpp` 的层级检查改成“按账户 ID 排序后加锁”，需要改哪些接口？跨进程的锁还能用吗？

   <details><summary>提示</summary>

   需要把“先锁谁”从锁对象自己决定改成调用方按账户 ID 排序，接口要接收账户 ID 或返回排序后的锁列表；`lock()`/`unlock()` 不再需要 `thread_local`。跨进程时每个进程有自己的 `thread_local`，层级检查只能覆盖本进程；跨进程锁要靠共享内存里的固定顺序或带健壮属性的 pthread 锁。

   </details>
