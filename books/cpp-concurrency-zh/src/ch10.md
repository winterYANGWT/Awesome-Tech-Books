# 第 10 章 线程局部存储、可重入与线程安全的库

```c
char *tok = strtok(line, " ");
while (tok != NULL) {
    emit(tok);
    tok = strtok(NULL, " ");
}
```

两个线程各拿一行调用这段代码，第一次跑对，第二次词就少了。共享状态不在自己的全局变量里，而在 `strtok` 的静态指针里。

另一个程序在信号处理函数里调用 `printf`，平时没事，收到信号后偶尔卡死；锁也不在自己代码里，而在 stdio 内部。

| 函数 | 隐藏状态 | 可重入替代 |
|---|---|---|
| `inet_ntoa` | 返回静态缓冲区，下一次调用改写上一次的结果 | `inet_ntop`，结果写进调用者缓冲区 |
| `getservbyname`/`getservbyport` | 返回静态 `servent` | `_r` 版本 |
| `localtime`/`gmtime` | 返回静态 `struct tm` | `localtime_r`/`gmtime_r` |
| `rand` | 隐藏的种子 | `rand_r`，或每线程一个 `std::mt19937` |

前三行返回指针的函数，共同点是返回值指向库自己的一份存储，调用者没有地方放状态，下一次调用一改写，上一次的结果就变了。`rand` 藏的是种子，不在返回值里，和返回缓冲区的三行不是一类。`inet_ntoa` 尤其隐蔽，因为它的返回值看起来像普通字符串，很容易被存进另一个变量后继续使用。

`errno` 是反例：POSIX 要求它线程局部，一个线程失败不会覆盖另一个线程的错误码。但 `errno` 只在失败后有意义，成功调用也可能改它，所以要在失败后立刻读。

C++ 的 `std::strtok` 就是 C 的 `strtok`，仍然共用那个指针。C++ 里可以每个线程用自己的 `std::istringstream` 加 `std::getline`，或者用 `std::string_view` 加 `std::from_chars`（C++17），状态全部放在局部变量里。

- `std::strtok` 没有 C++ 特化，调用的仍是 C 库那份静态状态。
- 每线程一个流对象就够了，流对象本身不要跨线程共享。
- `from_chars` 不分配内存，适合解析数字；切分单词仍要自己找分隔符。

C11 附录 K 的 `strtok_s` 是可选接口，多一个缓冲区大小参数，签名和 `strtok_r` 不同；glibc 2.43 没有提供它，不能把它当成可移植的替代。

> **旧资料提示**：用 `strtok`、`inet_ntoa`、`localtime` 的静态缓冲区做多线程解析，是旧教程里的常见写法。改用 `strtok_r`、`inet_ntop`、`localtime_r`，或者 C++ 的 `from_chars`/`istringstream`；`errno` 虽然是线程局部的，也不要跨两次库调用保存。见 [第 37 章](ch37.md)。

## 10.2 `thread_local` 语义

{{#fig ch10/tls_layout}}

`thread_local` 可以修饰命名空间变量、静态成员和块作用域变量，每个线程一份。x86-64 上通常用 `%fs` 指向当前线程的 TLS 块，变量地址是基址加一个固定偏移；共享库里的模型可能是 general-dynamic，需要 `__tls_get_addr`，比普通全局变量略贵，但仍比加锁便宜。

命名空间或静态成员的 `thread_local` 在该线程第一次 odr-use 之前初始化。块作用域的 `thread_local` 在控制流第一次经过声明时初始化；并发进入同一条声明时，其他线程等待初始化完成，有动态初始化的对象由实现保证这个等待。

析构在该线程退出时按构造逆序执行，析构函数抛异常会调用 `std::terminate`。把 `thread_local` 对象的指针或引用交给其他线程，必须保证目标线程还活着、对象还没析构；线程退出后再用就是悬空。

| 声明位置 | 什么时候初始化 | 什么时候析构 |
|---|---|---|
| 命名空间变量 | 本线程第一次 odr-use 之前，可以推迟 | 线程退出时 |
| 类的静态成员 | 本线程第一次 odr-use 之前，可以推迟 | 线程退出时 |
| 块作用域变量 | 控制流第一次经过声明时 | 线程退出时，按构造逆序 |

- `thread_local` 只隔离变量本身，不隔离它指向的堆对象；堆对象仍要自己同步。
- 不同线程的析构没有全局顺序，只有线程内部是逆序。

## 10.3 可重入、线程安全与异步信号安全

{{#fig ch10/reentrancy}}

三个词说的不是一件事：

- 线程安全（thread-safe）：多个线程同时调用不会破坏不变量，可以用锁实现。
- 可重入（reentrant）：不依赖可变的全局/静态状态，能在被打断后再次进入，通常也不持有不可重入的锁。
- 异步信号安全（async-signal-safe）：可以在信号处理函数里调用，POSIX 有一张明确的列表。

三者不能互相替代：

- `malloc` 是线程安全的，但不是异步信号安全的。
- `localtime_r` 可重入，却不在 POSIX 的 async-signal-safe 列表里。
- 用互斥量保护的函数是线程安全的，但同一线程递归调用会死锁，因此不可重入。

| 性质 | 能否加锁 | 能否递归 | 能否在信号处理函数里用 | 例子 |
|---|---|---|---|---|
| 线程安全 | 可以 | 普通 mutex 不支持，递归会死锁 | 不可以 | `malloc`、`printf` |
| 可重入 | 不依赖不可重入的锁 | 可以 | 不保证 | `localtime_r` |
| 异步信号安全 | 不能依赖普通锁 | 可以在 handler 里再次进入 | 可以 | `write` |

- 线程安全可以用锁换正确性，代价是竞争和阻塞。
- 可重入不能用普通锁，因为中断可能正好发生在持锁期间。
- 异步信号安全只认 POSIX 列表，不认“平时没出错”。

## 10.5 pthread TLS 与 C11

{{#fig ch10/tls_impl}}

pthread 的线程局部存储用 `pthread_key_t`（完整程序：[10_5_pthread_key.c](code/ch10/10_5_pthread_key.c)）：

- `pthread_key_create(&key, destructor)` 建键，键是进程内共享的，值才是每线程一份。
- `pthread_setspecific(key, value)` 设值，`pthread_getspecific(key)` 取值。
- 线程退出时对每个非空值调用 destructor；值为 NULL 就不调用。
- destructor 里又给同一个键设了非空值，POSIX 允许再调用，反复到没有非空值；glibc 到 `PTHREAD_DESTRUCTOR_ITERATIONS` 轮就停，其他实现可能不设上限。POSIX 只要求这个宏至少 4，glibc 是 4。
- 键的数量有限，`PTHREAD_KEYS_MAX` 在 glibc 是 1024，POSIX 下限是 128；`pthread_key_delete` 之后键不能再用。

C++ 的 `thread_local` 由语言保证构造和析构；pthread key 只保证对非空值调用 destructor，而且可能多轮。迁移时不能假设两者完全等价：`thread_local` 也不能在运行期动态创建任意多个键，需要动态键时仍要用 key 或 `tss_t`。

- 编译期已知的固定变量用 `thread_local`，代码最短，构造/析构由语言负责。
- 需要按插件、按连接动态建很多份每线程数据时，用 pthread key 或 `tss_t`，并自己管理每个值的生命周期。
- 从 key 迁到 `thread_local` 时，先确认旧 destructor 有没有在释放前做额外动作。

## 10.6 线程安全的库与可观测性

{{#fig ch10/shared_ptr}}

标准库的线程安全保证是分层的。`std::cout` 的单个插入不数据竞争，但多线程输出会交错；`std::shared_ptr` 的控制块引用计数是原子的，多个线程各自拷贝、销毁不同 `shared_ptr` 实例安全，但同一个 `shared_ptr` 对象被一个线程读、另一个线程写就是数据竞争。

| 操作 | 是否安全 |
|---|---|
| 多个线程各自拷贝、销毁不同的 `shared_ptr` 实例 | 安全，控制块引用计数是原子的 |
| 同一个 `shared_ptr` 对象被一个线程读、另一个线程赋值或 `reset` | 数据竞争 |
| 多个线程通过各自的 `shared_ptr` 读同一个被管理对象 | 只读安全；有写就要自己同步 |
| 控制块里引用计数的增减 | 由实现原子地完成 |

`std::rand` 不保证线程安全，glibc 的实现用锁把它串行化，但状态仍是共享的，结果不可重复；每个线程一个 `std::mt19937` 才能既独立又可重复。`std::locale` 的全局设置和 `std::cout` 的格式标志（宽度、精度、填充）也可能共享，改之前要同步。

可观测性方面：

- `pthread_setname_np` 给线程命名，名字最长 16 字节（含结尾的 0），glibc 2.12 起。
- `gettid()` 返回内核线程号，和 `pthread_self()` 不是一回事；日志里同时记 `gettid` 和 `/proc/self/task/<tid>/comm`，才能和 `ps -L`、`perf` 对上。
- 日志用 `osyncstream` 或每线程缓冲，别让多行日志在文件里互相穿插。
- 不要用 `pthread_kill(t, 0)` 判断线程是否存活，`pthread_t` 会在汇入或分离后复用（[第 26 章](ch26.md)）。
- 多线程进程里的 `fork` 和信号分发，也在第 26 章展开。

> **旧资料提示**：用 `pthread_key_create` 或 GCC 的 `__thread` 做每线程数据，是旧写法。C++11 起 `thread_local` 由语言保证构造/析构；pthread key 只对非空值调用 destructor，可能多轮。见 [第 37 章](ch37.md)。

## 速查

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `thread_local` | 每线程一份的变量 | 命名空间/静态成员首次 odr-use 前初始化；块作用域首次经过声明时初始化；线程退出逆序析构 |
| `pthread_key_create` | 建 TLS 键 | destructor 只对非空值调用；键是进程共享的 |
| `pthread_setspecific`/`pthread_getspecific` | 设/取每线程值 | 值类型是 `void*`，生命周期自己管 |
| `pthread_key_delete` | 删键 | 不检查、也不调用 destructor |
| `PTHREAD_DESTRUCTOR_ITERATIONS` | glibc 的 destructor 轮数上限 | POSIX 要求这个宏至少 4；glibc 是 4 |
| `pthread_once` | 进程内一次性初始化 | 不是 TLS，不创建每线程副本 |
| `_Thread_local` | C11 的每线程变量 | 等价于 C++ 的 `thread_local` |
| `tss_create`/`tss_set`/`tss_get`/`tss_delete` | C11 的 TLS | `<threads.h>` 可选；glibc 2.28 起 |
| `strtok_r` | 可重入分词 | 每个线程传自己的 `saveptr` |
| `inet_ntop` | 地址转字符串 | 结果写进调用者缓冲区 |
| `localtime_r`/`gmtime_r` | 时间转换 | 结果写进调用者提供的 `struct tm` |
| `getpwnam_r` | 用户信息 | 同样把结果写进调用者缓冲区 |
| `rand_r` | 可重入随机数 | 种子由调用者保存 |
| `std::mt19937` | C++ 随机引擎 | 每个线程一个，别共享 |
| `std::from_chars` | 解析数字 | 不读 `errno`，进度由返回的指针给出 |
| `std::osyncstream` | 整段原子输出 | 每个线程一个；`emit()` 或析构时写出 |
| `flockfile`/`funlockfile` | 锁住 C stdio 一段 | 异常路径要解锁 |
| `std::atomic<std::shared_ptr<T>>` | 原子读写 `shared_ptr` | C++20；不保证无锁，本机是 `false` |

## 思考题

1. 预测：`10_1_strtok_shared.c` 里两个线程各分 100 个词，最坏情况一个线程能拿到多少个词？为什么有时又完全正确？

   <details><summary>提示</summary>

   静态指针一次只指向一个字符串，但另一个线程的非 NULL 调用会把指针重置到自己的字符串，所以一个线程能先走自己的词、再接着走对方的词，最多接近 200 个。两个线程如果被调度成先后执行，指针每次都在自己的字符串上，就会完全正确；这正是“输出对一次不能证明程序对”。可以把 `kWords` 改小、去掉 `sched_yield` 观察概率变化。

   </details>

2. 找错：`10_2_tls_pointer.cpp` 里如果主线程在目标线程退出前就读指针，为什么仍然可能不安全？`thread_local` 对象的析构和线程函数的返回谁先谁后？

   <details><summary>提示</summary>

   线程函数先返回，然后才析构 `thread_local` 对象，最后线程真正结束、`join` 返回。主线程在目标线程退出前读，可能和析构并发，仍然是没有同步的访问；指针发布只给了地址，没有延长对象生命周期。安全做法是让对象活到所有使用者都结束，或者把数据复制出来再交出去。

   </details>

3. 权衡：每线程一个 `std::mt19937`、一个 `rand_r` 的种子、一个全局加锁的 `rand`，在可重复性和性能上各自怎么取舍？

   <details><summary>提示</summary>

   每线程 `mt19937` 性能最好、序列独立，但每个线程的种子要单独设计，否则可能生成相同序列；`rand_r` 轻量、可重复，但状态只有 32 位，质量较弱；全局加锁的 `rand` 可重复但把线程串行化，锁竞争会吃掉并行收益。要可重复就给每个线程固定的、互不相同的种子，并记录种子。

   </details>

4. 迁移：把 `10_4_osyncstream.cpp` 的 `std::cout` 改成 C 的 `printf`，还能用 `osyncstream` 吗？需要 `flockfile` 还是自己加锁？

   <details><summary>提示</summary>

   `osyncstream` 包装的是 C++ 的 streambuf，不能直接包 `printf`。可以用 `flockfile(stdout)`/`funlockfile(stdout)` 把一整行包住，或者先 `snprintf` 到自己的缓冲区再一次 `write`；自己加锁也可以，但要保证异常路径解锁。C stdio 的锁和 C++ 流不是同一套设施，别混着假设。

   </details>
