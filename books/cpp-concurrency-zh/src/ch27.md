# 第 27 章 进程间通信：管道、共享内存、信号量、消息队列、传递文件描述符

kvd 改成 4 个 worker 的进程池，哈希表搬进共享内存。客户端 A 的 `SET k 1` 返回 `OK`，客户端 B 的 `GET k` 却拿到一串乱码：表里存的是 `std::string` 对象的指针，指向 A 的堆。

子进程第一次 `read` 返回 3，第二次返回 0。0 不是“读到了空数据”，是 EOF：管道里没有字节，而且不可能再有了。

EOF 的条件是**所有**写端都关闭。`fork` 之后父子各有一份 `fd[1]`，子进程不关自己的写端，父进程关掉也没用，读端仍有一个写者。示例里子进程一开始就 `close(fd[1])`，父进程写完再 `close`，条件才成立，父进程也要关掉不用的 `fd[0]`。

`pipe` 是半双工的：`fd[0]` 只读、`fd[1]` 只写。要双向通信就建两个管道，或者用 `socketpair`。

{{#fig ch27/pipe_fd}}

看第 4 步：最后一个写端关闭。第 5 步的 `read` 才返回 0；在此之前读端只会阻塞等待。

`pipe2`（Linux 2.6.27）在创建时直接设 `O_CLOEXEC` 或 `O_NONBLOCK`，省掉两次 `fcntl`，也避免 `fork` 和 `fcntl` 之间的竞态。本机实测 `pipe2(fd, O_CLOEXEC | O_NONBLOCK)` 后两个标志都在。

管道有两个容量相关的数：

- `PIPE_BUF` 在 Linux 上是 4096（`fpathconf(fd, _PC_PIPE_BUF)`）。不超过它的 `write` 是原子的，多个写者的数据不会交错；超过以后内核可以穿插，读到的是拼接结果。
- 默认容量是本机的 65536 字节（`fcntl(fd, F_GETPIPE_SZ)`）。`F_SETPIPE_SZ`（Linux 2.6.35）可以调大，本机用 root 调到 1 MiB 成功；上限受 `/proc/sys/fs/pipe-max-size` 限制。

容量是上限，不是保证。写满后 `write` 阻塞，读端关掉后写触发 `SIGPIPE`（[26.6 节](ch26.md)）。

`socketpair(AF_UNIX, SOCK_STREAM | SOCK_CLOEXEC | SOCK_NONBLOCK, 0, sv)` 返回两个全双工的 fd，标志位同样在 2.6.27 起可用。全双工不等于保留消息边界：

三条 4 字节消息共 12 字节。`SOCK_STREAM` 上第一次 `read(6)` 拿到 `AAAABB`，第二次拿到 `BBCCCC`，第三次直接 EOF：两次读把三条消息吃完了，边界不见了。

- 要传结构体，换成 `SOCK_SEQPACKET`，让内核保留边界；
- 或者自己加长度前缀，循环读到够为止。

`SOCK_SEQPACKET` 上每次 `read` 正好一条消息，返回 4。代价是单条消息不能超过缓冲区，否则会被截断并丢掉多余部分。不能假设一次 `read` 就是一个完整对象。

管道和 socketpair 都只能传字节；想把一个已经打开的 fd 送过去，要用 27.5 的 `SCM_RIGHTS`。

> **旧资料提示**：旧教程把 `SOCK_STREAM` 当消息传输，假设一次 `read` 就是一条消息。`SOCK_STREAM` 只保证字节顺序；要边界用 `SOCK_SEQPACKET`，或者自己加长度前缀。第 41 章会讲这条。

## 27.2 共享内存：映射、生命周期与“指针不能过去”

{{#fig ch27/shm_layout}}

两个进程各有一张页表，映射到同一个物理页框。虚拟地址通常不同：A 里是 `0x7f…1000`，B 里是 `0x7f…3000`。同一段字节在两边偏移相同，地址不同。

所以共享段里不能存指针。

| 可以放 | 不能放 |
|---|---|
| 整数、`char[N]`、定长结构体 | 指针、`std::string`、`std::vector`、带虚函数的对象 |

`exec` 之后代码、堆、栈全换了，旧地址不再映射，解引用得到 `SIGSEGV`。就算没崩，读到的也只是别人地址空间里的字节。乱码的来源就在这里。

- `std::string` 对象本身也不能放进去：它内部有指向字符数据的指针，两个进程的堆地址不同；
- 短字符串优化会把内容放在对象内部，长度和容量字段也可能被各自解释。

正确做法是定长数组加长度，或者只存偏移和下标。

POSIX 共享内存分四步：

| 调用 | 作用 |
|---|---|
| `shm_open` | 创建或打开名字，返回 fd |
| `ftruncate` | 把对象设成固定大小 |
| `mmap(MAP_SHARED)` | 映射进进程地址空间 |
| `shm_unlink` | 删名字，不删已打开的映射 |

writer 退出后对象仍在：`shm_open` 创建的是有内核持久性的对象，名字挂在 `/dev/shm` 下。`shm_unlink` 只删名字，已经打开的 fd 和映射继续有效，最后一个使用者退出后才真正释放。

- 本机 glibc 2.43 链接 `shm_open` 不需要 `-lrt`，示例只用 `-pthread` 就编过了；老的 glibc 可能要加，写构建脚本时别把版本写死。
- System V 是四个调用：`shmget(key, size, IPC_CREAT | 0600)` → `shmat` → `shmdt` → `shmctl(IPC_RMID)`；`IPC_RMID` 只是打删除标记，最后一个进程 detach 后才释放。
- `memfd_create`（Linux 3.17）创建没有名字的共享内存，返回 fd，可以 `F_ADD_SEALS` 防止被改大小或写入。
- `mmap(MAP_SHARED | MAP_ANONYMOUS)` 也能得到共享页，但只对 `fork` 出来的亲缘进程有效。

> **旧资料提示**：旧教程说 `shm_open` 一定要加 `-lrt`。本机 glibc 2.43 不需要；老 glibc 可能要，构建脚本别把版本写死。第 41 章会讲这条。

放进共享段的结构要满足三条：

- trivially copyable，没有虚函数、没有 `std::string` / `std::vector` / `std::shared_ptr`；
- 大小固定，用 `char[N]` 加长度字段代替变长容器；
- 对齐一致，同一个结构体在两个进程里用同一份头文件、同样的编译选项，必要时用 `static_assert` 和 `offsetof` 检查。

共享内存不提供同步。要锁，锁本身也必须在共享段里，见下一节。

带 `SEM_UNDO` 时值回到 1，不带时停在 0。临界区里的数据改到一半就死掉，`SEM_UNDO` 不会帮你回滚；它只在进程退出时撤销计数，多个进程的撤销顺序也不由你控制。

> **旧资料提示**：把 `SEM_UNDO` 当崩溃恢复。它只撤销信号量计数，不能回滚临界区的数据；持锁进程死亡要用 robust 互斥量加 `pthread_mutex_consistent`，或者由外部监督重启。第 41 章会讲这条。

POSIX 无名信号量有两个要点：

- `sem_init(&s, 1, value)` 的 `pshared` 非 0 只表示“可以跨进程”，前提是 `sem_t` 本身在共享内存里；
- 命名信号量用 `sem_open("/name", O_CREAT, 0600, value)`，`sem_unlink` 删名字。

`sem_trywait` 是非阻塞版，值为 0 时返回 `EAGAIN`；要等超时用 `sem_timedwait`。

`sem_wait` 可能被信号打断返回 `EINTR`，要重试。`sem_post` 是 async-signal-safe 的，可以放进信号处理函数；但处理函数里不要做复杂逻辑。

跨进程互斥量需要两个属性，缺一不可：

- `pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED)`：允许跨进程；
- `pthread_mutexattr_setrobust(&attr, PTHREAD_MUTEX_ROBUST)`：持锁者死了能查出来。

锁对象必须放在共享段里。只设 `pshared` 不设 robust，持锁者死亡后锁永远不释放，就是章节开头那个故障。

| 设施 | 跨进程属性 | 持锁者死亡 | 能放进 shared memory | 备注 |
|---|---|---|---|---|

| `std::counting_semaphore` | 无 | 不适用 | 否 | C++20，只有进程内语义 |

读写锁也有 `PTHREAD_PROCESS_SHARED` 属性（`pthread_rwlockattr_setpshared`），但 **POSIX 没有 robust 读写锁**。持锁者死亡后没有标准手段恢复，只能由外部监督把整组 worker 停掉、重建共享段；27.6 就是这么做的。

C++20 的 `std::mutex`、`std::shared_mutex`、`std::counting_semaphore` 只有进程内语义，标准没有给它们 `pshared` 或 robust 接口，跨进程仍要用 pthread/POSIX。

按 3、1、2 发送，按类型 1、2、3 取，出队顺序就和发送顺序不同。`msgrcv` 成功时返回复制到 `mtext` 的字节数，不是 0；输出里 `返回 4`、`返回 6` 就是这个长度。

| `msgtype` | 取哪一条 |
|---|---|
| `0` | 队列里的第一条，不管类型 |
| `> 0` | 第一条该类型的消息 |
| `< 0` | 类型值不超过 `|msgtype|` 的消息中类型最小的一条 |

`msgrcv` 还有两个 `msgflg` 标志：

- `MSG_EXCEPT` 排除指定类型；
- `MSG_NOERROR` 允许截断。

队列满时 `msgsnd` 默认阻塞，带 `IPC_NOWAIT` 返回 `EAGAIN`。`msgrcv` 默认也阻塞，带 `IPC_NOWAIT` 且无消息时才返回 `ENOMSG`。`msgctl(IPC_RMID)` 唤醒所有等待者并让它们返回 `EIDRM`。

POSIX 消息队列用名字打开，名字以 `/` 开头、里面不能再有 `/`，对象挂在 `/dev/mqueue` 下。`mq_notify` 可以把“队列从空变成非空”通知成信号或线程：



通知有三个限制：

- 只有队列**之前为空**时，新消息才触发；
- 通知只发生一次，收完要重新注册；
- 同一时刻只有一个进程能注册。

消息还有优先级：`mq_send` 给一个 `unsigned`，`mq_receive` 总是取最高优先级的那条，同一优先级按 FIFO。

示例里两轮都重新注册，所以两次都收到 `SI_MESGQ`。

两类消息队列在 fd 上不一样：

- System V 消息队列不是 fd，不能 `poll`/`epoll`；
- POSIX 消息队列在 Linux 上底层就是一个 fd（`mq_overview(7)` 明确写了），可以 `select`/`poll`/`epoll`；但 POSIX 不要求这样实现，换平台未必成立。

| | System V | POSIX |
|---|---|---|
| 创建 | `msgget(key, flags)` | `mq_open("/name", …)` |
| 发送 | `msgsnd` | `mq_send` |
| 接收 | `msgrcv`（可按类型挑） | `mq_receive`（按优先级） |
| 边界 | 保留 | 保留 |
| 通知 | 无 | `mq_notify` |
| 是 fd 吗 | 不是 | Linux 上是 |
| 起始版本 | System V | POSIX.1-2001 |

消息队列适合把请求分给一组 worker：每条消息自带类型，接收方按类型分派，不必自己切分字节流。

System V 消息队列不提供 fd。POSIX 消息队列在 Linux 上是 fd，但这只是实现方式，POSIX 不要求。两种队列都不提供连接的语义。

控制缓冲区用 `char buf[CMSG_SPACE(sizeof(int))]` 分配，`cmsg_len` 写 `CMSG_LEN(sizeof(int))`。接收端用 `CMSG_FIRSTHDR`/`CMSG_NXTHDR` 遍历，检查 `cmsg_level == SOL_SOCKET`、`cmsg_type == SCM_RIGHTS`，还要检查 `MSG_CTRUNC`。

传的是“打开文件描述”的引用，不是 fd 号：

- 接收方得到一个新的 fd 编号，示例里父子两个编号不同；
- 两个 fd 指向同一个打开文件描述，共享文件偏移和状态标志；
- 子进程设的 `O_NONBLOCK`，父进程收到后也能看到；
- `MSG_CMSG_CLOEXEC`（Linux 2.6.23）让收到的 fd 自动带 `FD_CLOEXEC`，示例里打印为 1；
- 发送方可以立刻 `close` 自己那份，只要接收方还开着，文件就不会关。

这条路径也常用来把监听 socket 交给 worker，或者把日志文件的 fd 交给专门的日志进程。

`CMSG_SPACE(sizeof(int))` 在 64 位上要 24 字节，8 字节连一个 `cmsghdr` 都放不下，fd 没有被安装。接收端必须检查 `MSG_CTRUNC` 并拒绝使用，不能假设“数据到了，fd 也一定到了”。还有两个边界：

- Linux 一次最多传 253 个 fd（`SCM_MAX_FD`）；
- `pidfd_getfd`（Linux 5.6）可以在有 ptrace 权限时复制别的进程的 fd，但要先拿到目标进程的 pidfd，不是 `SCM_RIGHTS` 的通用替代。

这也解释了 `fork` 之后子进程为什么能直接用父进程的 fd：复制的是 fd 表项，两个表项指向同一个打开文件描述。

四类需求的总表：

| 方式 | 传什么 | 有无边界 | 能否跨无关联进程 | 是否 fd | 同步怎么做 | 起始版本 |
|---|---|---|---|---|---|---|
| `pipe` / `pipe2` | 字节 | 无 | 只能亲缘进程（fd 可 `SCM_RIGHTS` 传） | 是 | 不提供 | `pipe2` 2.6.27 |
| `socketpair` | 字节或数据包 | `SEQPACKET` 有 | 只能亲缘进程（fd 可 `SCM_RIGHTS` 传） | 是 | 不提供 | 4.2BSD |
| System V 共享内存 | 共享字节 | 不适用 | 能，按 key | 否（`shmid`） | 另加信号量/互斥量 | System V |
| POSIX 共享内存 | 共享字节 | 不适用 | 能，按名字 | 是（`shm_open`） | 另加信号量/互斥量 | POSIX.1-2001 |
| `memfd_create` | 共享字节 | 不适用 | 靠 `SCM_RIGHTS` 传 fd | 是 | 另加信号量/互斥量 | Linux 3.17 |
| System V 信号量 | 计数 | 不适用 | 能，按 key | 否 | 就是同步设施 | System V |
| POSIX 信号量 | 计数 | 不适用 | 能，按名字或在共享段 | 否 | 就是同步设施 | POSIX.1-2001 |
| robust 互斥量 | 锁状态 | 不适用 | 能，锁在共享段 | 否 | 就是同步设施 | POSIX.1-2008 |
| System V 消息队列 | 带类型的消息 | 有 | 能，按 key | 否 | 满时阻塞 | System V |
| POSIX 消息队列 | 带优先级的消息 | 有 | 能，按名字 | Linux 上是 | `mq_notify` | POSIX.1-2001 |
| `SCM_RIGHTS` | fd 的引用 | 随消息 | 能，要 AF_UNIX socket | 传的就是 fd | 不提供 | 4.2BSD |

## 27.6 kvd_shm：prefork 进程池 + 共享哈希表

{{#fig ch27/prefork_shm}}

父进程先建监听 fd 和共享段，再 `fork` 4 个 worker（{{#figref ch27/prefork_shm}} 只画 3 个作示意）。worker 继承监听 fd，各自阻塞在 `accept` 上，内核一次只唤醒一个。

多个 worker 等同一个监听 fd 时有两个做法：

- 用 `epoll` 加 `EPOLLEXCLUSIVE`（Linux 4.5）减少惊群；
- 或者各自用 `SO_REUSEPORT`（Linux 3.9）建监听 socket。

- 客户端 A 的 `SET k 1` 和客户端 B 的 `GET k` 都成功。表只有一份，每个 worker 读到的都是同一张表，不再是 `kvd_fork` 那种各有一份；这次运行没有记录两个客户端分别由哪个 worker 服务，输出本身不证明它们落到了不同 worker。
- `kill -9 worker` 之后，父进程先停掉其余 worker，再重建共享段。恢复后 `GET k` 返回 `NOT_FOUND`：旧表随旧段一起丢了。这是“整池重启”的代价，不是 bug。
- 重建后再 `SET k 2`、`GET k`，服务恢复；两轮的 `errors=0`、`mismatches=0` 说明重建前后的请求都没有协议错误。

这也是 prefork 池的常见形态：worker 只处理连接，表由所有 worker 共享，父进程只负责监督和回收。

共享段的大小是固定的：2048 个槽，每个 key/value 各 256 字节，表满时新 key 写不进去，`SET` 返回 `ERROR table full`。真实服务要算好容量，或者把溢出写到磁盘。

与第 25 章的 `kvd_fork` 相比，写入现在互相可见，代价是定长数据结构、手工加锁、崩溃恢复和调试难度。每个 worker 的请求都可能在持锁时死掉，所以共享段里的锁越多，要重建的范围越大。

## 速查

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `pipe` / `pipe2` | 半双工字节流 | 所有写端关闭后读端才见 EOF；`pipe2` 2.6.27 |
| `socketpair` | 全双工 UNIX socket | `SOCK_STREAM` 不保留边界，`SOCK_SEQPACKET` 保留 |
| `PIPE_BUF` | 原子写的上限 | Linux 4096；超过可能与其他写者交错 |
| `F_GETPIPE_SZ` / `F_SETPIPE_SZ` | 查/改管道容量 | 默认 65536；2.6.35 起 |
| `shmget`/`shmat`/`shmdt`/`shmctl` | System V 共享内存 | `IPC_RMID` 只打删除标记 |
| `shm_open`/`ftruncate`/`mmap`/`shm_unlink` | POSIX 共享内存 | `shm_unlink` 只删名字 |
| `memfd_create` | 匿名共享内存 fd | Linux 3.17；可 `F_ADD_SEALS` |
| `semget`/`semop`/`semctl` | System V 信号量集 | `SEM_UNDO` 只补偿计数，不是崩溃恢复 |
| `sem_init`/`sem_wait`/`sem_post` | POSIX 无名信号量 | `pshared=1` 且 `sem_t` 在共享段 |
| `sem_open`/`sem_unlink` | 命名信号量 | 名字以 `/` 开头 |
| `pthread_mutexattr_setpshared` | 跨进程互斥量 | 锁必须在共享段 |
| `pthread_mutexattr_setrobust` + `pthread_mutex_consistent` | 持锁者死亡恢复 | `EOWNERDEAD`；不修复就解锁会变 `ENOTRECOVERABLE` |
| `pthread_rwlockattr_setpshared` | 跨进程读写锁 | 没有 robust 版本 |
| `msgget`/`msgsnd`/`msgrcv`/`msgctl` | System V 消息队列 | `msgrcv` 返回字节数；无消息用 `IPC_NOWAIT` 返回 `ENOMSG` |
| `mq_open`/`mq_send`/`mq_receive`/`mq_notify` | POSIX 消息队列 | 名字以 `/` 开头；通知一次性 |
| `sendmsg`/`recvmsg` + `SCM_RIGHTS` | 传 fd | 只能 AF_UNIX；检查 `MSG_CTRUNC` |
| `MSG_CMSG_CLOEXEC` | 收到的 fd 带 `FD_CLOEXEC` | Linux 2.6.23 |
| `pidfd_getfd` | 复制别的进程的 fd | Linux 5.6；要 ptrace 权限 |

## 思考题

1. 27.2 的共享结构里如果放一个 `std::string`，为什么两个进程看到的长度可能不同？把 `std::string` 换成 `char[64]` + `uint32_t len` 后，还有哪些字段需要检查对齐？

   <details><summary>提示</summary>

   `std::string` 对象里有指向字符数据的指针，两个进程的堆地址不同；短字符串优化还会把内容放在对象内部，长度和容量字段也可能被各自解释。换成定长数组后，检查 `len` 是否紧跟在数组后面、结构体总大小是否因尾部填充而变化、用 `offsetof` 和 `static_assert` 固定偏移，并在两端用同一个头文件编译。

   </details>

2. 27.3 的 robust 互斥量在持锁者被 `SIGKILL` 后，下一个 `lock` 返回 `EOWNERDEAD`；如果这个进程不调用 `pthread_mutex_consistent` 就解锁，再下一个 `lock` 会得到什么？

   <details><summary>提示</summary>

   得到 `ENOTRECOVERABLE`。内核认为临界区一直没被修复，这把锁从此不可用，只能 `destroy`。可以改 `27_3_robust_mutex.c`，把 `consistent` 那行注释掉，观察下一次 `lock` 的返回值。

   </details>

3. kvd 的共享表用“每桶一把读写锁”和“全局一把互斥量”，在 4 个 worker、读写比 9:1 时各自瓶颈在哪？读写锁一定更好吗？

   <details><summary>提示</summary>

   全局锁把 4 个 worker 的所有请求串行化，读多时也无法并行；每桶锁让不同桶并行，但热点 key 落在同一桶时仍会争用，读锁的共享还会带来缓存行在核间搬运。读写比 9:1 时读写锁通常占优，但桶太少、热点集中或临界区极短时，全局锁的简单和低开销可能反超，要用 `kvbench` 在本机测。

   </details>

4. 把 27.5 的 `SCM_RIGHTS` 改成传 `pidfd` 或 `memfd`，接收端能做什么、不能做什么？为什么 `SCM_RIGHTS` 仍然是传“已打开文件”的通用方式？

   <details><summary>提示</summary>

   `pidfd` 指向进程而不是文件，接收端只能对它做进程相关操作（发信号、等待），不能读写文件；`memfd` 是一块匿名内存文件，接收端能映射和读写，也能共享偏移；但它只能承载内存内容，代表不了发送方原本打开的文件、管道或 socket。`SCM_RIGHTS` 传的是任意已打开文件的引用，接收方得到的新 fd 和发送方共享打开文件描述，文件、socket、管道都适用。

   </details>
