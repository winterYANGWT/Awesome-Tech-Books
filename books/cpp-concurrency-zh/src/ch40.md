# 第 40 章 并行编程模型的演进：OpenMP、并行算法与 MPI

一台 32 线程的机器上，`std::for_each(std::execution::par, ...)` 只用了一个线程；同一份代码换到装了 TBB 的机器上却跑满。另一段 `schedule(static, n / thread_count)` 把第 0 号线程分到了数组的头和尾，和“块划分”的预期相反。

两个现象都不是编译器坏了：一个卡在后端选择，一个卡在对调度子句的误读。先看这两行代码，再看 OpenMP、C++17 并行算法和 MPI 各自改了什么。

```cpp
std::for_each(std::execution::par, v.begin(), v.end(), f);
// 32 线程机器上可能只有 1 个线程
#pragma omp parallel for schedule(static, n / thread_count)
// 线程 0 可能拿到 0–1 和 8–9
```

## 40.1 OpenMP 3.0 不是全貌：task、simd、target、depend

{{#fig ch40/omp_models}}

**旧写法**：把 OpenMP 等同于 `#pragma omp parallel for`、`reduction` 和 `critical`，认为 3.0 已经覆盖主要用法。

**当时为什么这样写**：3.0（2008）只有 fork-join 和 worksharing 最成熟；规则循环是当时的主要负载，矩阵乘法和数值积分用它就能讲完。

**问题在哪**：fork-join 表达不了递归和不规则循环，数据环境、锁和取消的坑也比教材里多。

- `private` 的初值未指定，`firstprivate` 才复制外层值；不写 `default` 时，parallel 区域里的变量默认 `shared`。
- `critical` 不写名字时，全程序共用一个未命名的锁；`omp_lock_t` 没有 RAII，忘记 `omp_unset_lock` 就死锁。
- `master` 在 OpenMP 5.1 起弃用，`masked` 是替代；`single` 没有弃用，它仍由一个线程执行并带隐式屏障。
- `cancel`（4.0）和 `std::stop_token` 都是协作式取消，区别是 OpenMP 只在 cancellation point 生效。
- `std::mutex`/`std::barrier` 能替锁和屏障，但替不了 `parallel for` 的迭代划分和隐式屏障；worksharing 仍要 OpenMP 或并行算法。

**取代它的**：3.0 加 `task`/`taskwait`，4.0 加 `simd`、`target`、`depend`、`cancel` 和 `atomic` 的更新，4.5 加 `taskloop`、`taskloop simd`、`hint`，5.0 加 `metadirective`、`requires`，5.1 加 `masked`。

| 版本 | 年份 | 本章用到的变化 | 本机 |
|---|---|---|---|
| 3.0 | 2008 | `task`、`taskwait` | GCC 15 支持（本章示例） |
| 4.0 | 2013 | `simd`、`target`、`depend`、`cancel` | GCC 15 支持 `simd`；`target` 无设备 |
| 4.5 | 2015 | `taskloop`、`taskloop simd`、`hint` | GCC 15 的 `_OPENMP` 是 201511 |
| 5.0 | 2018 | `metadirective`、`requires`、`scan` | 部分特性可用，按编译器实测 |
| 5.1 | 2020 | `masked` | GCC 15 实测接受，宏仍是 4.5；Clang 21 报 202011 |
| 5.2 | 2021 | 当前规范 | 只作规范依据 |

`target` 在 4.0 加入，把区域卸载到设备。本机 `omp_get_num_devices()` 返回 0，`target` 区域只在主机执行；这能跑通代码，但不能验证设备端的线程和拷贝。

## 40.2 调度子句的四个误解：`master`、`nowait`、`static` chunk、`guided`

{{#fig ch40/static_chunk}}

**旧写法**：把下面四件事当成 OpenMP 的标准语义。

- 用 `master` 表示“线程 0 执行”。
- 给 `parallel for` 加 `nowait`。
- 把 `schedule(static, n / thread_count)` 当块划分。
- 把 `guided` 的 `chunksize` 当固定块大小。

**当时为什么这样写**：3.0/4.0 的教材需要“只让一个线程做初始化”的写法，`master` 最直接。`nowait` 被笼统地讲成“不等其他人”，`n/p` 看起来就像每块大小；`guided` 的块会缩小，容易被读成“块大小 1”。

**问题在哪**：这四处都能用编译错误或输出拆穿。

- `nowait` 不能用于 `parallel` 或合并的 `parallel for`；它用于 `for`、`sections`、`single` 等构造，5.2 还允许 `target` 和带 `depend` 的 `taskwait`。
- `dynamic` 省略 chunk 时默认 1，所以线程会频繁领小块；这也是它和 `guided` 的差别之一。
- `static` 带 chunk 时按块轮流分给线程，`n/p` 取整后线程会拿到多个不连续的块。
- `guided` 的第二个参数是块大小的下限，不是固定块大小。
- `runtime` 从 `OMP_SCHEDULE` 读调度，`OMP_NUM_THREADS` 只给默认线程数。

| 子句 | 能用于哪些构造 | 语义 | 旧教程的误解 |
|---|---|---|---|
| `master` / `masked` | parallel 区域内的结构化块 | `master` 只让线程 0 执行；`masked` 让满足 `filter` 的线程执行，默认 `filter(0)` | `master` 是唯一写法；其实 5.1 起弃用，`masked` 可写 `filter(2)` |
| `nowait` | `for`、`sections`、`single` 等 worksharing；5.2 还允许 `target`、带 `depend` 的 `taskwait` | 去掉构造末尾的隐式屏障 | 可用于 `parallel` 或 `parallel for`；编译直接失败 |
| `static` chunk | worksharing-loop | 按 chunk 轮流分配，线程可能拿到多个不连续块 | `n/thread_count` 等于块划分；要连续块应省略 chunk |
| `guided` | worksharing-loop | 块大小约等于“剩余迭代数 / 线程数”，逐渐缩小 | `chunksize` 是块大小，省略时为 1；其实它是块大小的下限 |
| `runtime` | worksharing-loop | 从 `OMP_SCHEDULE` 读取 kind 和 chunk | `OMP_NUM_THREADS` 能决定实际线程数；它只给默认值 |

**取代它的**：新代码用 `masked` 或 `single` 表达“一个线程做”，用 `single nowait` 表达“一个线程做且不等”。要连续块就写 `schedule(static)`，要固定块大小才写 `schedule(static, k)`。

**今天还用得着吗**：`master` 仍能编译，但已是弃用写法，`single` 没有弃用，二者差别是隐式屏障。`master`/`masked` 没有隐式屏障，`single` 默认有，GCC 15 接受 `masked` 而 `_OPENMP` 仍报 4.5，所以可移植性要按目标编译器实测，不能只看宏。

> **旧资料提示**：旧教程把 `master` 当“线程 0 执行”的标准写法，把 `nowait` 说成可用于 `parallel for`，把 `static, n/p` 当块划分。OpenMP 5.1 起改用 `masked`；`nowait` 不能用于 `parallel`/`parallel for`，可用于 worksharing 和 5.2 的 `target`、带 `depend` 的 `taskwait`。调度细节见 [22.5 节](ch22.md)。

```cpp

```

```text

```

`before for_each(par)` 打印了，`after` 没有，`seq` 也一样。C++ 标准对四种策略写了同一条规则：元素访问函数因未捕获异常退出时调用 `std::terminate`，所以需要异常沿调用栈传播时不要用带策略的重载。可以把异常捕获在元素函数内部，存进 `std::exception_ptr`，算法返回后再重抛。

- 算法自己申请临时内存失败时，仍可能抛 `std::bad_alloc`；这和元素函数抛异常是两回事。
- `par_unseq` 和 `unseq` 下不能有锁或阻塞，标准明确说阻塞同步有死锁风险。

| 策略 | 在哪执行 | 同一线程内能否交错 | 元素函数抛异常 | 版本 |
|---|---|---|---|---|
| `seq` | 调用线程 | 否 | `terminate` | C++17 |
| `par` | 调用线程或库创建的线程 | 否 | `terminate` | C++17 |
| `par_unseq` | 未指定线程 | 是，允许向量化 | `terminate` | C++17 |
| `unseq` | 调用线程 | 是，允许向量化 | `terminate` | C++20 |

`find` 的并行版能否提前停止由实现决定，`for_each` 的处理顺序也不保证。ranges 算法在 C++20/23 没有策略重载；C++26 草案（P3179）加了 `ranges::for_each(exec, ...)` 这类重载，本机 GCC 15 / Clang 21 都没有实现，未编译验证。

**取代它的**：按目标选写法。

- 要并行就链接 TBB 并确认后端。
- 要异常就自己捕获；要顺序或异常传播就用不带策略的重载。
- 要向量化用 `unseq`，但要保证元素函数没有锁和阻塞。

**今天还用得着吗**：`par` 仍是“许可”，不是“请求”。同一行代码在不同后端、不同数据规模下可能只跑一个线程，也可能跑满；判断依据是实测的线程数和耗时，不是写了哪个策略。

## 40.5 并行度不是核数：`hardware_concurrency()`、`std::async` 与“一核一线程”

**旧写法**：线程数直接取 `std::thread::hardware_concurrency()`，或者按“一核最多一个线程”写死；认为 `std::async` 会充分利用硬件、不会超额。

**当时为什么这样写**：2011 年的机器多是同构双核/四核，教学假设一核一线程，计时和划分都按这个模型简化；`hardware_concurrency()` 看起来就是核数。

**问题在哪**：它只是逻辑 CPU 数提示，可能返回 0，也不区分 P/E 核、SMT、NUMA、CPU 亲和性和 cgroup 配额；容器里常远大于可用 CPU。`std::async` 也没有“用满硬件、不超额”的保证，`deferred` 甚至可能根本不执行。

## 40.6 MPI 的三十年：阻塞集合 → 非阻塞/持久/大计数

{{#fig ch40/mpi_overlap}}

**旧写法**：下面四种写法在 MPI-1/2 时代很常见。

- 每个时间步都用阻塞 `MPI_Allreduce`/`MPI_Allgather`，通信完再计算。
- 认为小消息的 `MPI_Send` 不会阻塞，可以先发后收。
- 认为派生数据类型一定比基本类型慢。
- C++ 程序直接用 MPI 的 C++ 绑定。

**当时为什么这样写**：MPI-1（1994）已有点对点的阻塞和非阻塞通信，但集合通信只有阻塞版本；MPI-2（1997）加了单边、动态进程和并行 I/O，集合仍是阻塞。C++ 绑定在 MPI-2 时代可用，教材自然拿来用。

**问题在哪**：四个假设各有各的问题。

- 阻塞集合把通信和计算串成两段。
- `MPI_Send` 可能缓冲后立即返回，也可能一直阻塞到匹配接收。
- C++ 绑定在 MPI-3.0 已移除。
- 派生类型的开销要看实现和消息形状。

| MPI 版本 | 通信 | 大计数 | C++ 绑定 | 本机支持 |
|---|---|---|---|---|
| MPI-1（1994） | 点对点阻塞/非阻塞、阻塞集合 | `int` 计数 | 无 | 可用 |
| MPI-2（1997） | 加单边、动态进程、并行 I/O；集合仍阻塞 | `int` 计数 | 有 C++ 绑定 | 可用 |
| MPI-3.0（2012） | 加非阻塞集合、`MPI_Comm_split_type` | `MPI_Count` 与 `_x` 查询 | 移除 | 可用 |
| MPI-4.0（2021） | 加持久集合、分区通信 | `_c` 大计数例程 | 无 | `MPI_Get_version` 报 3.1，`MPI_Allreduce_init` 实测 4 rank 可用（其它未逐一验证） |
| MPI-4.1（2023） | 修正和澄清 4.0 | 同 4.0 | 无 | 修正/澄清，未逐项验证 |

MPI-4.0 的持久集合用 `MPI_Allreduce_init` 建请求，之后每次 `MPI_Start`/`MPI_Wait` 复用参数，省掉重复初始化。本机 Open MPI 5.0.10 的 `MPI_Get_version` 报 3.1，`mpi.h` 里却声明并导出了 `MPI_Allreduce_init`；4 rank 实测能完成一次持久 `Allreduce`。

- 版本号是声明，接口是否存在要单独查头文件和符号。
- `MPI_IN_PLACE` 可以用在 root 的 `MPI_Reduce`、`MPI_Gather`、`MPI_Scatter` 等集合操作里，省掉一次发送缓冲；非 root 不能随便用。
- `MPI_Isend` + `MPI_Waitall` 是安全写法；需要确认对方已收到时，用 `MPI_Ssend` 或 `MPI_Sendrecv`。

派生数据类型不一定慢：`MPI_Type_contiguous` 这种连续类型通常能高效处理，不必逐元素打包。带间隙的 `MPI_Type_create_struct` 才可能需要打包，是否变慢取决于实现、消息大小和网络，测过再决定。

MPI-5.0 于 2025 年 6 月通过，主要新增标准 ABI；本机的 Open MPI 5.0.10 报的版本还是 3.1，本书不展开。

**取代它的**：MPI-3.0 起用 `MPI_Iallreduce`/`MPI_Ibcast`/`MPI_Iallgather` 把通信和计算重叠；MPI-4.0 起用持久集合减少重复初始化，用 `_c` 接口处理大计数。

- C++ 程序直接用 C API，或者用 Boost.MPI 这类包装库。
- 需要“发送方确认对方已收到”时用同步发送，不要靠小消息的缓冲猜测。

**今天还用得着吗**：阻塞集合仍然适合“通信后马上要用结果”的小规模代码。非阻塞和持久集合适合每个时间步都要同步、且中间有计算可做的循环，MPI+OpenMP 的分工仍是节点间 MPI、节点内 OpenMP。每个 rank 的线程数和绑核要一起设。

> **旧资料提示**：旧写法每个时间步只用阻塞集合通信，`MPI_Allgather` 完再算。MPI-3.0 起有非阻塞集合，MPI-4.0 起有持久集合；重叠的收益要测，见 [30.6 节](ch30.md)。

## 40.7 2011 年的性能数字为什么不能外推：Amdahl、忙等、读写锁、伪共享

{{#fig ch40/false_sharing}}

**旧写法**：拿 2011 年测出的秒数和加速比表当结论；按“一核一线程”定线程数；用忙等、读写锁和 `clock()` 的旧经验直接套到今天。

**当时为什么这样写**：那时的机器是 2×4 核或 4×双核，NUMA 和 cgroup 还不常见，教学假设同构、一核一线程，测一次就能代表一类机器。

**问题在哪**：Amdahl 公式仍然成立，但 `p` 和串行部分在异构核、NUMA、功耗墙下更难定义；绝对时间不可复现，只有定性结论还能迁移。

- 忙等在线程数超过核数后退化；现代互斥量有自适应自旋，`std::mutex` 在 Linux 上落到 futex。
- 读写锁不保证公平，写者可能饿死；`std::shared_mutex` 的优先级策略由实现决定。
- 伪共享按缓存行发生：x86-64 常见 64 B，ARM 可能是 64 或 128 B；C++17 的 `hardware_destructive_interference_size` 只是实现定义提示值。
- `high_resolution_clock` 可能只是 `system_clock` 的别名；计时要用 `steady_clock` 或 `CLOCK_MONOTONIC`。
- `parallel for` 不一定每次创建线程，现代运行时通常复用线程池；2011 年“每次 fork-join 慢 17%–22%”的数字不能照搬。

两个线程各写自己的计数器，逻辑上没有竞争。布局 A 的两个计数器在同一缓存行，写 `a` 或 `b` 都让整行失效，缓存行在两个核之间来回搬；布局 B 用 `alignas(64)` 把两个计数器分到不同行，耗时明显下降。

程序里的 64 是 x86-64 的常见值，不是可移植常量。C++17 的 `std::hardware_destructive_interference_size` 在本机是 64，但标准只说它是实现定义的提示值；跨平台代码应读这个常量，或者在目标平台实测。

**取代它的**：计时用 `steady_clock`/`CLOCK_MONOTONIC`，先预热、多次取中位数或最小值；测量时绑核、隔离 CPU、固定频率，减少迁移和频率变化。

- 每线程一个 `std::pmr::unsynchronized_pool_resource` 可以减少分配器竞争。
- 复用线程池、减少 fork-join 的结构结论仍然成立，但具体开销要重测。

**今天还用得着吗**：Amdahl 和强/弱可扩展仍用来估算上限，但今天还要看 roofline，判断是算力受限还是带宽受限。负载均衡、伪共享、通信开销、块划分和循环划分这些定性结论仍然成立；具体的秒数、倍数和“17%–22%”只能当历史数据，必须在目标机器上重测。

## 速查

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `#pragma omp parallel for` | 并行化规则循环 | 不写 `schedule` 时由实现决定；末尾有隐式屏障 |
| `#pragma omp task` / `taskwait` | 动态任务和等待子任务 | 3.0 起；未显式指定的自动变量默认 `firstprivate`，包围上下文共享的变量和静态/动态存储仍 `shared` |
| `#pragma omp simd` / `target` | 向量化提示 / 设备卸载 | 4.0 起；`target` 要有设备才真正卸载 |
| `#pragma omp masked` / `master` | 让一个线程执行 | 5.1 起用 `masked`；`master` 已弃用 |
| `nowait` | 去掉 worksharing 末尾的隐式屏障 | 不能用于 `parallel` 或 `parallel for` |
| `schedule(static\|dynamic\|guided\|runtime[,chunk])` | 迭代分配 | `static` 不带 chunk 才是连续块；`guided` 的 chunk 是下限 |
| `reduction` / `critical` / `atomic` | 归约 / 命名临界区 / 原子更新 | 不写名字的 `critical` 全程序共用一把锁 |
| `OMP_NUM_THREADS` / `OMP_SCHEDULE` / `OMP_DISPLAY_ENV` | 默认线程数 / runtime 调度 / 打印环境 | `OMP_NUM_THREADS` 不保证实际线程数 |
| `std::execution::seq/par/par_unseq/unseq` | 执行策略 | 只是许可；策略版元素函数抛异常会 `terminate` |
| `std::reduce` / `transform_reduce` | 并行归约 | 要求结合律和交换律；浮点末位可能不同 |
| `std::inclusive_scan` / `exclusive_scan` | 并行前缀和 | `exclusive_scan` 的 `init` 必需，位置和 `inclusive_scan` 不同 |
| `MPI_Allreduce` / `MPI_Iallreduce` | 阻塞 / 非阻塞全归约 | 非阻塞要 `MPI_Wait`/`MPI_Test`，完成前不能复用缓冲 |
| `MPI_Allreduce_init` / `MPI_Start` | 持久集合 | MPI-4.0；本机声明 3.1 但实测可用 |
| `MPI_Type_contiguous` / `MPI_Type_create_struct` | 派生数据类型 | 连续类型通常高效；带间隙的结构体可能打包，实测为准 |
| `hardware_concurrency` / `sched_getaffinity` / `hardware_destructive_interference_size` | 逻辑 CPU 提示 / 亲和性 / 缓存行提示 | 都可能和实际可用资源不同；不要写死 |

## 思考题

1. （预测）4 个线程、10 次迭代，`schedule(static, 2)` 下线程 0 拿到哪些迭代？改成 `schedule(static)` 呢？如果 `n=11`，`static, 2` 的最后一块归谁？

   <details><summary>提示</summary>

   `static,2` 按 chunk 轮流分：线程 0 拿 0–1 和 8–9；`static` 不分 chunk，线程 0 拿 0–2。`n=11` 时共有 6 块，最后一块只有 1 个迭代，仍按轮转回到线程 0。用 `40_2_schedule.c` 改 `n` 和 `num_threads` 可以验证，但规范只保证“大致相等”，余数的具体分法不要当便携结论。

   </details>

2. （找错）40.3 的 `for_each(par)` 为什么只跑一个线程？代码里哪一步决定后端？如果换成 Clang + libstdc++，结论会变吗？

   <details><summary>提示</summary>

   编译时 libstdc++ 的 PSTL 选择后端：没有 TBB 头就走串行后端，有 TBB 头并链接 `-ltbb` 才走 TBB。`-D_GLIBCXX_USE_TBB_PAR_BACKEND=0` 是在源码外强制切后端，所以同一份代码线程数从多个变 1 个。Clang 21 也用 libstdc++ 15，后端选择同样看 TBB 头，不因为换了编译器就自动并行。

   </details>

3. （权衡）`reduce(par)` 的浮点结果和串行不同，什么情况下可以接受？什么情况下必须逐位一致？

   <details><summary>提示</summary>

   只要误差在业务容差内、且不依赖末位做相等比较，就可以接受；科学计算通常只要求误差界。需要可复现实验、逐位比较、和旧结果做二进制对比，或者累加顺序本身有语义时，必须固定顺序，用 `accumulate` 或固定分块和固定合并顺序。`40_4_pi_float.cpp` 的 `ulp_diff` 可以用来量化差异。

   </details>

4. （迁移）把 40.2 的 `master` 改成 `masked`，在 `_OPENMP=201511` 的 GCC 15 上能编译吗？可移植性怎么保证？

   <details><summary>提示</summary>

   能，GCC 15 实测接受 `#pragma omp masked` 和 `filter(k)`，虽然 `_OPENMP` 仍是 201511（4.5）。可移植性不能只看宏：要在目标编译器上编译，查它的 OpenMP 支持表；对只支持 4.5 的编译器，保留 `master` 或改用 `if (omp_get_thread_num() == 0)` 更稳，但要注意 `master` 没有隐式屏障。

   </details>
