# 第 3 章 线程：创建、等待与所有权

一个函数启动线程后很快返回，线程还在读它的局部数组；同一个程序可能正常、可能打印垃圾，换一台机器就崩。另一种版本是启动后忘了 `join`，`main` 正常返回，进程却在 `std::thread` 析构时突然中止。

两个故障都出在“线程对象的生命周期”和“线程访问的数据的生命周期”没有对齐。

```cpp
void spawn() {
    int value = 42;
    std::thread t([&] { std::cout << value; });
    t.detach();
}  // value 销毁，线程可能还在读它
```

## 3.1 进程里的线程：地址空间、栈与内核调度实体

{{#fig ch03/address_space}}

线程是进程里的执行流。它有自己的栈、程序计数器、寄存器组和线程局部存储（TLS）。代码、全局/静态数据、堆和文件描述符表由同进程的线程共享，信号处理函数也是全进程共享的，一个线程改了处理方式，其他线程看到的是同一份。

{{#fig ch03/thread_lifecycle}}

新建的线程先就绪，等调度器选中才运行。等 I/O 或锁时阻塞，被唤醒后回到就绪队列。`join` 在终止之后回收资源，`detach` 把回收责任交给运行时，调用后不能再 `join`。

Linux 用 `clone` 创建任务，线程共享下面这些标志：

- `CLONE_VM`：同一地址空间。
- `CLONE_FS`：文件系统信息。
- `CLONE_FILES`：文件描述符表。
- `CLONE_SIGHAND`：信号处理函数。
- `CLONE_THREAD`：同一线程组，`getpid()` 返回同一个 TGID。

从 Linux 2.5.35 起 `CLONE_THREAD` 必须同时带 `CLONE_SIGHAND`，从 2.6.0 起后者又要求 `CLONE_VM`。所以这些标志不是随便挑的组合。

NPTL 是 1:1 模型，每个线程是一个内核调度实体，从 glibc 2.3.2 起提供，需要 Linux 2.6 的特性。LinuxThreads 没有用 `CLONE_THREAD`，每个“线程”有不同 PID，还多一个管理线程；它在 glibc 2.4 起不再受支持。

`gettid(2)` 返回内核 TID（Linux 2.4.11 起，glibc 包装 2.30 起），`pthread_self()` 返回不透明的 `pthread_t`。两者类型不同，不能互换。

LinuxThreads 的 `getpid()` 在每个线程返回不同值，NPTL 全部返回同一个 TGID。

| 资源 | 属于谁 |
|---|---|
| 栈、寄存器、程序计数器、TLS | 每个线程私有 |
| 代码、全局/静态数据、堆 | 进程内共享 |
| 文件描述符表、信号处理函数 | 进程内共享 |

两个线程栈上局部变量的地址差大于 1 MiB，说明它们是两段独立映射，不是同一摞栈。输出里的 PID 和 TID 每次运行都会变，正文不引用具体值。

本机 `ulimit -s` 是 8192 KiB，所以新线程默认栈是 8 MiB。glibc 取的是进程启动时的 `RLIMIT_STACK`，不是写死 8 MiB；栈底还有一条 4 KiB 保护区。

线程总数还受 `RLIMIT_NPROC`、`/proc/sys/kernel/threads-max` 和 cgroup `pids.max` 限制。标准库在 Linux 上建在 pthread 上，`native_handle()` 返回 `pthread_t`；Windows 的 MSVC 不是这样。

## 3.2 启动、汇入与 `std::jthread`

`std::thread` 构造即启动。构造函数把可调用对象和参数按值复制或移动进线程存储，入口可以是函数、函数对象、lambda、成员函数指针加对象指针。

- 普通函数：`std::thread t(f, args...)`。
- 函数对象：对象被复制进线程存储。
- lambda：捕获列表决定它能看到什么。
- 成员函数：`std::thread t(&Worker::run, &w, 7)`。

构造本身还有两个细节：

- 失败时抛 `std::system_error`，错误码是 `resource_unavailable_try_again`。
- 参数在创建线程前就被求值，复制或移动时的异常在主线程抛出。

| 操作 | 之后 `joinable()` | 说明 |
|---|---|---|
| `join()` | false | 等待线程结束并回收 |

`join()` 等到线程结束，调用后 `joinable()` 为 false；对不可汇入的对象再 `join()` 抛 `std::system_error`，错误码是 `invalid_argument`。析构时仍 `joinable()` 会调用 `std::terminate`。

`detach()` 让线程后台运行，之后不能再汇入，也不能再访问调用者的栈。

线程对象和参数有这几条规则：

- 成员函数指针加对象指针可以作为入口，后面的参数依次对应成员函数参数。

没有守卫，异常离开 `main` 时 `thread` 仍 joinable，析构调用 `terminate`；输出只有 `terminate called` 和 `what()`，随后 SIGABRT。

守卫本身有三条规则：

- 守卫的析构里不要调用可能抛异常的代码，`join` 失败只能终止。
- 自己创建的线程优先 `std::jthread`，包装外部 `std::thread` 时才用守卫。
- 守卫对象不能比它引用的 `std::thread` 对象活得更久。

`std::vector<std::jthread>` 析构时对每个元素先 `request_stop()` 再 `join()`，比手写 `join_threads` 简单。

`std::jthread` 的停止是协作式的：线程不检查 `stop_token`，`request_stop()` 只置位，不会强行结束。析构仍会 `join`，所以不检查的线程会让析构一直等。

`join()` 本身可能抛 `std::system_error`，但在析构里抛会直接 `std::terminate`；守卫的构造函数应先检查 `joinable()`。

> **旧资料提示**：旧教程里手写 `thread_guard`/`scoped_thread`/`joining_thread` 管汇入。C++20 起 `std::jthread` 直接提供 RAII 汇入和停止令牌；包装外部线程时守卫仍可用，见 [第 37 章](ch37.md)。

## 3.5 pthread：创建、退出、汇入、分离

{{#fig ch03/pthread_fork_join}}

`pthread_t` 在 glibc 上是整型，但 POSIX 只保证它是不透明类型；比较用 `pthread_equal`，不要直接打印或当整数。拿任意整数当 `pthread_t` 传给 `pthread_join`，glibc 会解引用内部指针，可能直接崩。

`pthread_detach` 把线程标成分离，退出时自动回收，也可以在创建前用 `PTHREAD_CREATE_DETACHED` 设置。已分离线程 `join` 返回 `EINVAL`；对已分离的线程再 detach 行为未指定。

- `long`：LP64 上和指针同宽，LLP64 上只有 32 位。
- `intptr_t`/`uintptr_t`：明确能装下指针的整数类型。
- 每线程结构体：编号、输入、输出放在一起，生命周期最清楚。
- 结构体在堆上分配时，要保证 `pthread_join` 返回之后才释放。
- 输入数据若由主线程修改，要用同步把修改和线程启动排好。

## 3.7 线程数量、标识与分块

`hardware_concurrency()` 返回逻辑 CPU 数的提示，取不到时返回 0。不能写 `hardware_concurrency() - 1`，0 时会无符号下溢成巨大值。CPU 密集型任务的起点是物理核数或逻辑 CPU 数，I/O 密集型可以更多，还要看 cgroup 的 CPU 配额和 NUMA。

`std::thread::id` 可拷贝、比较、排序、哈希，能作为关联容器键；默认构造值表示“没有线程”。

物理核数和逻辑 CPU 数不是一回事：本机 16 核 32 线程，SMT 让两个逻辑 CPU 共享一个物理核的取指和缓存资源。CPU 密集型先按物理核数估，再实测调整。

- 块与块之间不重叠，线程之间没有共享写。

|---|---|---|
| `std::thread` | 构造即启动线程 | 参数默认按值复制；析构时 joinable 会 `terminate` |

## 思考题

1. 把 `3_7_sum_threads.cpp` 的线程数从 16 增到 32，耗时大约怎么变？如果 N 只有 10^4，结论会变吗？

   <details><summary>提示</summary>

   本机是 16 核 32 线程，16 到 32 只是把 SMT 的第二条硬件线程用满，整数加法又受内存带宽和串行合并限制，耗时不会减半，可能持平甚至略差。N 只有 10^4 时，创建、汇入和合并的固定开销远大于计算，线程越多越慢；把 `kN` 改小、把线程列表加上 32 就能验证。

   </details>

2. `3_3_detach_dangling.cpp` 里把 `detach` 改成 `join` 就一定安全吗？如果线程函数保存了指针、join 后主线程又释放对象呢？

   <details><summary>提示</summary>

   改成 `join` 只能保证线程在局部数组销毁之前结束，前提是线程不把指针或引用存到别处。如果线程把指针存进全局容器，`join` 之后主线程再释放对象，那个指针仍然悬空；`join` 建立的是“线程已结束”的顺序，不是对象的永久生命周期。要保证所有权，用 `shared_ptr` 或让线程持有对象的所有权。

   </details>

3. 一个线程要读大文件并解析，另一个线程要处理网络事件；用 `std::thread`、`std::jthread` 还是事件循环，各自在什么条件下更合适？

   <details><summary>提示</summary>

   两个长期任务、共享数据很少时，两个 `std::thread` 最直接；需要优雅退出时用 `std::jthread` 加 `stop_token`，让读文件的一端在检查点退出。网络连接很多、每个事件都很短时，单线程事件循环加非阻塞 I/O 更省线程；但阻塞读大文件会卡住事件循环，必须把文件读放到工作线程或异步 I/O。没有一种结构在所有条件下都更好，先看连接数、阻塞点和退出需求。

   </details>

4. 把 `3_5_pthread_hello.c` 改成传一个每线程结构体（含编号、输入指针、输出槽），需要改哪些生命周期约束？

   <details><summary>提示</summary>

   每个线程要有自己的结构体实例，不能把循环里同一个栈变量的地址传进去；结构体要活到 `pthread_join` 返回之后，通常在堆上分配或放进一个足够长的数组。输入指针指向的数据要在线程运行期间保持只读且有效，输出槽由主线程在 join 之后读取；如果多个线程写同一个输出槽，还要加锁或改成每个线程一个槽。

   </details>
