# 第 14 章 基于锁的数据结构

一个栈的 `empty()`、`top()`、`pop()` 都加了锁，两个线程仍能在 `empty()` 返回 true 之后让 `pop()` 落到空栈上。把队列拆成头尾两把锁，程序又可能时快时慢、偶尔卡死。

```cpp
if (!stack.empty()) {
    stack.pop();  // empty() 返回之后锁已经释放
}
```

锁加对了地方，接口和锁顺序仍然会出错。

线程安全只要求不丢数据、不破坏不变量；真正并发还要求多个线程能同时进入。互斥量把访问串行化，所以设计顺序是先保证安全，再尽量缩小临界区。

下面两张清单用来审一个基于锁的容器。先问安全，再问并发；安全没过，谈并发没有意义。

| 安全四问 | 要检查什么 |
|---|---|
| 中间状态 | 有没有线程能看到不变量被破坏的半成品 |
| 接口竞争 | 检查、取数、删除是不是分开的多次调用 |
| 异常安全 | 抛出异常时锁和数据结构是否仍然一致 |
| 死锁 | 多个互斥量的加锁顺序是否处处相同 |

| 并发四问 | 要检查什么 |
|---|---|
| 移出锁外 | 分配、构造、拷贝能否在加锁前完成 |
| 分区保护 | 不同互斥量能否保护互不相交的区域 |
| 是否都需要同一把锁 | 读和读、读和写能不能分开 |
| 小改动 | 换返回类型、加一个哑节点能否提高并发 |

- 四问没有先后，任何一问不过，都要先退回去改设计。
- 安全四问不过时，不要用更细的锁去补；先让不变量和接口正确。

构造、析构、赋值和 `swap` 也要单独说明约束。对象在构造期间被另一个线程看到，本身就是发布问题（[第 11 章](ch11.md)）；析构前要保证没有线程还在访问它，通常是先 `join`。

异常安全是安全的一部分。锁用 `std::lock_guard`、`std::unique_lock` 或 `std::scoped_lock` 管理，异常路径才会解锁；数据结构的修改要么完成、要么回滚。

返回引用或指针时，还要保证弹出后数据仍然存活。`std::optional<T>` 返回的是副本，`std::shared_ptr<T>` 让对象脱离容器后继续活着；裸引用做不到这一点，异常路径的测试见[第 21 章](ch21.md)。

谓词读的变量必须在同一把锁下修改，否则通知到了也看不见。`wait` 可能虚假唤醒，所以必须循环检查；`wait(lock, pred)` 就是 `while (!pred()) wait(lock);`。

通知有两个版本，分工不同：

- `notify_one` 唤醒至少一个等待者，适合一个元素只够一个消费者取。
- `notify_all` 唤醒全部，适合关闭、广播状态变化。
- `notify_one` 不保证唤醒哪个线程，也不保证先等的先醒。
- 条件变量本身不保护数据，它只负责睡眠和唤醒；数据仍由那把 mutex 保护。

通知可以放在锁内，也可以放在解锁之后。锁内通知让被唤醒的线程立刻又去抢同一把锁，通常多一次阻塞，而解锁后通知则让它直接取数据。队列数据始终由那把 mutex 保护，代价只是通知可能落在消费者已经取走元素之后，变成一次空唤醒。

## 14.3 两把锁的队列与哑节点

{{#fig ch14/two_lock_queue}}

单链表队列用 `head` 管弹出、`tail` 管推入。哑节点改变了空队列的形状：

- 没有哑节点时，空队列的 `head == tail`，`head->next` 和 `tail->next` 是同一个对象，push 和 pop 会碰同一个 `next`，两把锁保不住。
- 加了哑节点后，`head` 指向哑节点，`tail` 指向最后一个节点；空队列时两者指向同一个哑节点。
- 只要 `head != tail`，pop 摘的是哑节点后面的数据节点，push 改的是 tail 节点，两者不是同一个对象。

所以两把锁保护的不是“两个不同的指针”，而是“两个不同的节点”。空队列时 pop 只比较指针、不读 `next`，等 push 完成之后才会看到新节点。

`push` 在锁内改完 `tail`、解锁后再 `notify_one()`。返回值有两种写法，异常安全的关键都在顺序：

快照的代价有三项：

- 锁住全部桶时，写者完全停下。
- 拷贝 N 个条目要 O(N) 时间和额外内存。
- 桶数越多，锁数组本身的缓存行流量越大。

写这个结构要守住四条规则：

- `std::mutex` 不可拷贝、不可移动，节点类型要自定义构造/析构，或者把锁放进 `std::unique_ptr<std::mutex>`；这会改变节点布局和分配次数。
- 销毁一个仍被锁住的互斥量是未定义行为。删除时先 `unlock`，再让 `removed` 析构；顺序看起来反直觉，但必须这样写。
- 遍历期间节点的 `next` 可能被删除线程改掉。“下一个节点”必须先在当前节点的锁内读出来，再锁住它；不能先解引用、再补锁。
- 手递手保证“我持有的节点不会被别人释放”，代价是每访问一个节点至少两次锁操作。链表很长、临界区很短时，它通常比整表锁慢。

遍历的并发和代价要分开看：

- 读操作也要逐节点加锁，不能像读写锁那样让多个读者真正并行。
- 并发度高不等于总时间短：锁操作次数、缓存行流量和临界区长度一起决定结果。
- 反过来，如果所有操作都按同一方向推进，就不会出现不同线程以不同顺序加锁。

本机一次运行里，读 99.9% 时读写锁最快，每节点锁最慢；读写混合时读写锁和整表互斥量接近，每节点锁仍然最慢。数字会随机器和负载变化，这个方向不变。

细粒度锁的账要这样算：

- 每次移动都要加解锁，线程数不够多、临界区很短时，多出来的锁操作比它省下的等待还贵。
- 读写锁只在读多写少时占优；读者计数本身也要修改锁的内部状态，仍可能造成缓存行乒乓。
- 标准不保证读者/写者优先级，glibc 默认读者优先，写者可能饿死；可移植代码不能依赖某个优先级。
- 锁和它保护的数据放在同一条缓存行上，对持有锁的线程有利；其他线程来抢锁时，会把整条缓存行拖来拖去。热点数据要按缓存行对齐，用 `std::hardware_destructive_interference_size` 或 `alignas`（[第 18 章](ch18.md)）。

选择锁粒度要看测量：先写正确版本，再用真实负载测吞吐和尾延迟。不要因为“更细”就认为“更快”，也不要因为“粗”就认为“不可扩展”。测量时把线程数、读写比例、键分布和临界区长度都记下来，换一个负载结论就可能反过来。

长尾和迁移性也要看：

- 只看平均吞吐会漏掉长尾。用 p99 或最大延迟一起比较，才能看出细粒度锁在热点桶上排队多久。
- 线程数翻倍时，每节点锁的加锁次数按节点数增长，整表锁只按操作数增长。
- 同一份代码换一台机器，结论也可能变，报告结果时把 CPU、线程数和编译选项一起写出来。

| 能力 | C++ | pthread | OpenMP | 备注 |

| 递归锁 | `std::recursive_mutex` | `PTHREAD_MUTEX_RECURSIVE` | `omp_nest_lock_t` | 递归持有要配对释放 |

## 速查

| 检查项 | 通过标准 |
|---|---|
| 中间状态 | 没有线程能看到不变量被破坏的半成品 |
| 接口竞争 | 检查与取数在同一个临界区内 |
| 异常安全 | 锁由 RAII 管理，修改要么完成要么回滚 |
| 死锁 | 所有路径的加锁顺序一致 |
| 移出锁外 | 分配、构造、拷贝尽量在加锁前完成 |
| 分区保护 | 不同互斥量保护不相交的区域 |
| 锁的必要性 | 读和读、读和写已经能分开 |
| 小改动 | 换返回类型、加哑节点能提高并发 |

| 结构 | 锁范围 | 主要死锁风险 |
|---|---|---|
| 单锁栈/队列 | 整个容器 | 无多锁顺序；但接口竞争和持锁通知要处理 |
| 两把锁队列 | 头一把、尾一把 | `get_tail` 必须在 `head_mutex` 内，顺序固定为 head→tail |
| 分桶表 | 每个桶一把读写锁 | `get_map` 按桶下标递增；有人反序就会死锁 |
| 手递手链表 | 每个节点一把 | 只能同方向推进；删除先解锁再析构 |

| 设施 | C++ | pthread | 注意 |
|---|---|---|---|
| 普通互斥量 | `std::mutex` | `pthread_mutex_t` | C++ 用 RAII 包装，pthread 手动加解锁 |
| 递归锁 | `std::recursive_mutex` | `PTHREAD_MUTEX_RECURSIVE` | 递归持有要配对释放 |
| 读写锁 | `std::shared_mutex` | `pthread_rwlock_t` | C++17 起有 `shared_mutex` |
| 限时锁 | `std::timed_mutex` | `pthread_mutex_timedlock` | 超时后仍要检查条件 |
| 多锁一起加 | `std::scoped_lock` | 无对应接口 | 个数在编译期固定 |
| 条件变量 | `std::condition_variable` | `pthread_cond_t` | 只负责等待/通知，不保护数据 |

## 思考题

1. 14.3 的两把锁队列，如果 `push` 在持有 `tail_mutex` 时调用 `notify_one`，而消费者在 `wait_pop` 里持有 `head_mutex`，会不会死锁？为什么？

   <details><summary>提示</summary>

   不会。消费者等的是条件变量，`wait` 会原子地释放 `head_mutex`；`push` 的 `notify_one` 不需要 `head_mutex`，也不等消费者释放任何锁。可能变慢的是被唤醒的消费者立刻又去抢 `head_mutex`，不是死锁。把 `notify_one` 放到解锁之后可以少一次阻塞。

   </details>

2. 14.5 的手递手链表，如果遍历时先读 `next`、解锁当前节点、再锁 `next`，哪个窗口会让节点被删除？画出两个线程的交错。

   <details><summary>提示</summary>

   窗口在“解锁当前节点”和“锁住 next”之间。另一个线程可以在这段时间里锁住当前节点、把 next 从链上摘下并释放，遍历线程再锁 next 时用的已经是被释放的地址。正确顺序是持有当前锁时读出 next、先锁 next、再释放当前锁；本章的 `find` 和 `remove_if` 都是这样写的。

   </details>

3. 把 14.4 的分桶表改成“桶数随元素数增长”，`get_map` 的快照还能按固定顺序加锁吗？需要什么额外约束？

   <details><summary>提示</summary>

   不能直接按固定下标加锁：桶数组会重新分配，桶数也会变。需要先用一把表级锁或原子指针拿到当前桶数组的稳定视图，再按这个视图的下标递增加锁；扩容时要么停止取快照，要么让旧数组在读者离开后再释放。否则两个线程可能拿着不同版本的桶数组，顺序无从谈起。

   </details>

4. 读多写少的配置缓存，用每桶 `shared_mutex`、整表 `shared_mutex`、还是 RCU/`atomic<shared_ptr>`？分别适合什么更新频率？

   <details><summary>提示</summary>

   每桶 `shared_mutex` 适合键多、写分散、更新每秒几次到几百次；整表 `shared_mutex` 适合读极多、写极少且更新很小的表，代码最简单；RCU 适合读路径不能加锁、更新不频繁、又能接受旧值短暂可见的场景。RCU 读者只读指针；`atomic<shared_ptr>` 的读者要复制一个 `shared_ptr`，每次读都增减引用计数，标准也不保证无锁（本机 libstdc++ 15.2 不是无锁）。前两种读者仍要改锁的计数，后两种都要处理旧版本回收。用 14.6 的方法测吞吐和尾延迟再定。

   </details>
