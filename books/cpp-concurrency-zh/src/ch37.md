# 第 37 章 线程与同步 API 的三代：pthread、C++11、C++20

1995 年的 pthread、2011 年的 C++11 线程库、2020 年的 C++20 同步设施，管的是同一件事：线程怎么开始、怎么等、怎么结束。三代 API 的写法不同，语义上的差别常常只在“谁负责等”这一句。

一个 `std::thread` 对象在函数返回时被析构，如果它还 joinable，编译不报错，运行时直接 `std::terminate`。2011 年要靠手写 `thread_guard` 才能活下来；C++20 的 `jthread` 把这件事放进了析构函数。

## 37.1 `void*` 参数、`-lpthread` 与实参求值顺序

**旧写法**：`pthread_create` 的入口是 `void *(*)(void *)`，两个参数要打包成 `struct`，返回值也只能是一个 `void *`，再经 `pthread_join` 取回。

**当时为什么这样写**：POSIX 要在 C 里做一个类型无关的线程接口，只能用一个 `void *` 传递任意数据。C 没有模板和变参模板，打包结构体是当时最直接的办法。

**问题在哪**：`int` 或 `long` 直接和指针互转是实现定义的行为，32 位和 64 位、LP64 和 LLP64 上宽度不一样；跨平台要经过 `intptr_t`。

| 任务 | pthread | C++11 | C++20 | C11 |
|---|---|---|---|---|
| 创建 | `pthread_create(&t, attr, fn, arg)` | `std::thread t(f, args...)` | `std::jthread t(f, args...)` | `thrd_create(&t, fn, arg)` |
| 传参 | 打包 `struct`，只传一个 `void*` | 按值拷贝/移动，`std::ref` 共享 | 同 C++11，另可自动传 `stop_token` | 只传一个 `void*` |
| 返回值 | `void*`，经 `pthread_join` 取回 | 函数返回值被丢弃，用 `future`/`promise` | 同 C++11 | `int`，经 `thrd_join` 取回 |
| 汇入 | `pthread_join(t, &ret)` | `t.join()` | 析构自动 `request_stop()` + `join()` | `thrd_join(t, &res)` |
| 链接 | `-pthread` | 同左 | 同左 | `-pthread` |

> **旧资料提示**：旧教程写 `-lpthread`。链接选项改用 `-pthread`；glibc 2.34 起 libpthread 已并入 libc，但 `-pthread` 仍要写，原因见本节。

**今天还用得着吗**：pthread 仍用于线程属性、绑核、信号、`fork` 这些标准库不覆盖的场合。Linux 上的 libstdc++/libc++ 把 `std::thread` 建在 pthread 上，Windows 的 MSVC 不是。

`-pthread` 同时作用于预处理和链接（定义 `_REENTRANT`），`-lpthread` 只链接。glibc 2.34 起 libpthread 并入 libc，`ldd` 只看得到 libc。`pthread_*` 用返回码报错、不设 `errno`，C++ 标准库用异常。

## 37.2 线程的结束：`thread_guard`、`pthread_cancel` → `jthread` + `stop_token`

**旧写法**：`std::thread` 析构时只要 `joinable()` 为真就调用 `std::terminate`。C++11 时代用 `thread_guard`/`joining_thread` 在析构里 `join()`；pthread 这边用 `pthread_cancel` 发取消请求。

**当时为什么这样写**：`std::thread` 不想替用户决定 join 还是 detach，两个选择都有代价；`pthread_cancel` 则想提供一个“从外面结束线程”的办法，默认是延迟取消。

**问题在哪**：`terminate` 不给栈展开；取消只在取消点生效，线程可以 `PTHREAD_CANCEL_DISABLE` 把请求一直排队。`pthread_cleanup_push/pop` 还必须在同一作用域成对出现。

## 37.3 把 `sleep`/`usleep` 当同步

**旧写法**：旧代码常写 `data = 42; sleep(1);`，以为睡够时间另一线程就一定能看到。`usleep` 在 POSIX.1-2001 标为 obsolescent，POSIX.1-2008 删除；`nanosleep` 只保证至少等这么久。

**当时为什么这样写**：在没有条件变量的代码里，睡眠是最省事的“等一等”。它不引入锁和回调，单机短延时看起来也能工作。

## 37.4 一次锁多个、层级锁与读写锁

本节三种锁各管一件事：
- `std::lock`/`std::scoped_lock` 一次锁多个，避免这一次调用的死锁。
- 层级锁记录顺序，标准没有，要自己写。
- `std::shared_mutex` 读写分开，读多写少时用。

**旧写法**：两个账户转账，最直接的写法是先锁 `from` 再锁 `to`；两个方向同时跑，就会各持一把、各等一把。C++11 用 `std::lock(m1, m2)` 加两个 `adopt_lock`，pthread 没有等价的“一次锁两把”函数。

**当时为什么这样写**：转账需要同时改两个余额，锁一把再锁另一把是直觉写法；单线程测试永远看不到问题，死锁只在交错时出现。

**问题在哪**：`std::lock` 只能避免这一次调用的死锁，不做全局顺序检查；手写的层级锁要自己记录当前层级，标准没有层级锁。

| 写法 | 一次锁几个 | 版本 | 要注意 |
|---|---|---|---|
| `std::lock` + `adopt_lock` | 2 个或更多 | C++11 | 只保证这一次调用不死锁 |
| `std::scoped_lock` | 2 个或更多 | C++17 | 参数个数编译期固定 |
| `std::shared_lock` + `unique_lock` | 读/写分开 | C++14/17 | 不保证优先级 |
| `pthread_mutex_lock` 循环 | 运行期数组 | POSIX | 要自己定顺序，可配 `pthread_mutex_trylock` |

## 37.5 手写屏障/闩 → `barrier`/`latch`/`counting_semaphore`

**旧写法**：没有 `std::barrier` 时，屏障用互斥量、条件变量和一个计数器手写：每个线程加一，最后一个广播，其他人 `while` 等待。

**当时为什么这样写**：pthread 的 `pthread_barrier_*` 从 POSIX.1-2001 起就是可选特性（`_POSIX_BARRIERS`，属于 ADVANCED REALTIME THREADS），不是每个平台都有；手写一套能同时覆盖没有屏障的系统。

**问题在哪**：典型 bug 是计数器没复位，或者没有 generation：第二轮把旧计数带进来，`count == N` 再也不成立，所有线程都等在 `while` 里。

## 37.6 线程属性与栈：`getstackaddr` 与 32 位上限

**旧写法**：旧教程把 `pthread_attr_t` 展开成 `char[36]`，再用 `pthread_attr_getstackaddr`/`setstackaddr` 读写栈地址；这两个函数在 POSIX.1-2001 标为过时，POSIX.1-2008 删除。

**当时为什么这样写**：32 位 glibc 的 `pthread_attr_t` 刚好 36 字节，旧教程直接按布局访问。`getstackaddr` 也只能给出一个地址，无法说明栈的大小和增长方向。

**问题在哪**：`pthread_attr_t` 是不透明类型，x86-64 glibc 2.43 是 56 字节；按 36 字节展开会越界或读到别的字段，换架构、换 glibc 就坏。`getstackaddr` 还没有大小和增长方向，无法可移植地使用。

{{#fig ch37/thread_stack}}

图里标出 `pthread_attr_setstacksize` 改的是每个线程栈的保留大小，guard page 由实现加；主线程栈可以增长，新线程的栈在创建时固定。

本机 GCC 15 对旧函数的诊断是一行：`warning: 'pthread_attr_getstackaddr' is deprecated [-Wdeprecated-declarations]`。

| 限制 | 本机容器 | 管什么 |
|---|---|---|
| cgroup `pids.max` | 17104 | 这个 cgroup 里任务（线程）总数 |
| `/proc/sys/kernel/threads-max` | 114029 | 全系统任务上限 |
| `RLIMIT_NPROC` | unlimited | 每个真实 UID 的进程/线程数 |
| `RLIMIT_AS` | unlimited | 地址空间；每个线程栈都占一块 |
| `RLIMIT_NOFILE` | 524288 | fd 数，不是线程数 |
| 默认栈 | 8 MiB | 每个新线程的虚拟地址保留 |

**取代它的**：改用 `pthread_attr_getstack`/`setstack`（起始地址 + 大小），`setstacksize` 至少 `PTHREAD_STACK_MIN`（本机 16 KiB），有些系统还要求页对齐。`setstack` 让调用者自己分配栈，guard 由调用者负责；`setstacksize` 的 guard 由实现加。

**今天还用得着吗**：线程数上限不是“4 GB 除以默认栈”：64 位地址空间、`RLIMIT_AS`、`RLIMIT_NPROC`、cgroup `pids.max`、内核 `threads-max`、每个线程的内核栈和调度实体都限制。`hardware_concurrency()` 只是逻辑 CPU 数提示。

把栈降到 64 KiB 能减少每个线程的地址空间占用，在地址空间或内存是瓶颈时能多开线程，但栈溢出风险随之增加，本机先撞到的可能是 `pids.max`。`pthread_attr_setdetachstate`、`pthread_attr_setguardsize`、`pthread_attr_setaffinity_np` 仍是 pthread 独有；C++ 标准库没有属性对象，`jthread` 也没有栈大小接口。

## 37.7 任务队列的管道：`result_of`、`copy_exception`、只能移动的任务

**旧写法**：旧任务队列用 `std::result_of<F(Args...)>` 推返回类型，用 `std::function<void()>` 装任务；`std::packaged_task` 是 move-only，`std::function` 要求目标可拷贝，装不进去。

**当时为什么这样写**：C++11 的 `std::function` 是唯一现成的类型擦除工具，`result_of` 是当时推导可调用对象返回类型的标准写法；任务队列先能跑起来，再谈 move-only。

**问题在哪**：`std::result_of` 在 C++17 弃用、C++20 从标准移除；libstdc++ 15 仍保留旧名作兼容，不能据此认为标准还有它。`std::function` 的拷贝语义会在 `packaged_task`、捕获 `unique_ptr` 的 lambda 上直接编译失败。

## 37.8 C11 `<threads.h>`：第三条路为什么没走通

**旧写法**：C11 提供可选 `<threads.h>`：`thrd_t`、`thrd_create`/`thrd_join`、`mtx_t`、`cnd_t`、`tss_t`；入口是 `int (*)(void*)`，返回值是 `int`，但仍只有一个 `void*` 参数。

**当时为什么这样写**：C11 想把线程做成 C 标准的一部分，给不能直接用 pthread 的平台一个统一接口；返回值用 `int` 比 `void*` 直观，`mtx_t` 还分 `mtx_plain`/`mtx_recursive`/`mtx_timed`。

**问题在哪**：C11 把它列为可选：定义了 `__STDC_NO_THREADS__` 就可以不提供，采用不广，嵌入式/Windows 支持差异大。它没有解决 pthread 的属性、取消、信号、`fork`、亲和性；C++ 标准库也不是它的包装。

| 项目 | pthread | C11 threads |
|---|---|---|
| 入口 | `void *(*)(void *)` | `int (*)(void *)` |
| 返回值 | `void*`，经 `pthread_join` | `int`，经 `thrd_join` |
| 属性、取消、亲和性 | 有 | 没有 |

## 速查

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `pthread_create` / `pthread_join` | C 线程创建/汇入 | 入口和返回值都是 `void*`；返回码不设 `errno` |
| `pthread_cancel` / `pthread_setcancelstate` | 延迟取消 | 只在取消点生效；`PTHREAD_CANCEL_DISABLE` 只排队 |
| `pthread_cleanup_push` / `pop` | 取消清理 | 同一作用域成对出现 |
| `std::thread` | C++11 线程 | 析构时 joinable 就 `terminate` |
| `std::jthread` / `stop_token` / `stop_source` / `stop_callback` | C++20 协作停止 | 析构先 `request_stop` 再 `join`；不保证响应 |
| `std::barrier` / `std::latch` | 屏障/闩 | C++20；barrier 有完成函数，latch 一次性 |
| `std::counting_semaphore` / `binary_semaphore` | 计数信号量 | C++20；无持有者，任何线程可 `release`；只有进程内语义 |
| `std::scoped_lock` | 一次锁多个 | C++17；参数个数编译期固定 |
| `std::shared_mutex` / `std::shared_lock` | 读写锁 | C++17；不保证优先级，写者可能饿死 |
| `std::invoke_result_t` | 返回类型推导 | C++17；替代 `result_of` |
| `std::move_only_function` | move-only 类型擦除 | C++23；可装 `packaged_task` |
| `std::make_exception_ptr` | 保存异常 | `copy_exception` 不是标准名 |
| `-pthread` | 预处理 + 链接 | 不写 `-lpthread`；glibc 2.34 起并入 libc |
| `thrd_create` / `mtx_t` / `cnd_t` | C11 threads | 可选；glibc 2.28 起提供 |

## 思考题

1. `jthread` 析构时工作线程正阻塞在 `read` 上，主线程调用 `request_stop()` 后，析构会返回吗？如果把 `read` 换成 `condition_variable_any::wait(lock, token, pred)` 呢？

   <details><summary>提示</summary>

   `request_stop()` 只置位停止状态并调用回调，`read` 不看 `stop_token`，所以析构里的 `join()` 会一直等 `read` 返回。带 token 的 `wait` 会注册回调，停止请求能唤醒它，线程检查后退出；`read` 要改成 `poll` 加超时，或由另一个线程关闭 fd。

   </details>

2. 37.5 的手写屏障在第二轮为什么死锁？换成 `std::barrier` 后，哪个状态由标准库接管了？

   <details><summary>提示</summary>

   第一轮 `count` 加到 3 后广播，但没有复位；第二轮 `count` 变成 4、5、6，`while (count != 3)` 永远为真。`std::barrier` 在完成函数返回后把 expected count 复位，并用内部的阶段状态区分轮次；`arrive_and_drop` 还会把后续阶段的初始计数减一。

   </details>

3. `pthread_cancel` 的“立即杀死”和 `stop_token` 的“协作退出”各自适合什么关闭顺序？分别举一个不适合对方的场景。

   <details><summary>提示</summary>

   取消适合线程正阻塞在 `read`、`sleep`、`pthread_cond_wait` 上，且清理能由 cleanup handler 完成的场景；它不保证线程在任意点安全退出，异步取消更危险。`stop_token` 适合要先停止接收新任务、排空队列、再释放资源的顺序；线程不检查 token 时 `jthread` 的析构仍会卡住。

   </details>

4. 把一个用 `void*` 传两个参数的 pthread 程序改成 `std::thread`，哪些地方必须用 `std::ref`？

   <details><summary>提示</summary>

   线程函数要修改调用方的对象、或对象本身不可拷贝（`mutex`、`condition_variable`、`packaged_task`）时用 `std::ref`；只读共享用 `std::cref`。按值传递会得到副本，地址不同；`std::ref` 只是把地址包起来，调用方必须保证对象活到 `join` 之后。

   </details>
