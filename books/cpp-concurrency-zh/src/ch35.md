# 第 35 章 并发服务器的结构：半同步/半异步、领导者/追随者、线程池、进程池

每连接一个线程的 kvd 在第 2000 条长连接上没撑住：`pthread_create` 返回 `EAGAIN`，进程只剩一条错误日志。换成固定 8 个 worker 的线程池后线程数稳住了，P99 却变差——请求队列没有上限，慢客户端把队列塞满，所有请求一起排队。

这一章把“socket 归谁管、连接是否固定执行体”拆成两个问题，用四种结构回答：能跑的版本有三个，半同步/半反应堆和每 worker 一个 epoll 接同一份 kvbench，进程池只演示通知和回收，35.7 的 `shm` 一列用的是第 27 章的 `kvd_shm`。取舍靠测，不靠名字。

## 35.1 池与执行体：为什么预创建，池多大

{{#fig ch35/pool_model}}

池的第一件事是把执行体的创建从请求路径上挪走。`clone`/`fork` 要建地址空间或共享地址空间、登记调度实体，线程还要有栈；这些成本放在每条新连接上，长连接一多就变成数量和内存的爆炸。

- 每连接一个线程：N 条连接就是 N 个栈和 N 个调度实体，大部分时间在等 `recv`。
- 每连接一个进程：还要多一份页表和一整套 fd 表，写时复制也挡不住切换成本。
- 池把创建放在启动时，请求到达时只做“取一个执行体、放回一个执行体”。

线程池多大取决于任务在等什么：CPU 密集型接近核数，I/O 密集型可以更多，但受 fd、内存和下游服务限制。`std::thread::hardware_concurrency()` 只是提示，算不出来时返回 0，池大小要 clamp 到至少 1（C++ 标准 `[thread.thread.static]`）。

```cpp
unsigned n = std::thread::hardware_concurrency();
if (n == 0) n = 1;
```

容器里不能按 `nproc` 估并行度：`nproc` 看的是 CPU 亲和性和在线 CPU，GNU coreutils 9.8（2025 年）以前不看 cgroup 配额，别的实现（本机 Ubuntu 用的是 uutils）也不一定看。cgroup v2 下要看 `/sys/fs/cgroup/cpu.max`：第一列是配额、第二列是周期，本机是 `max 100000`，表示没有配额。文件格式由内核规定，进程所在的 cgroup 路径是 `/proc/self/cgroup` 里 `0::` 后面那一段，容器里一般就是根。

| 限制 | 从哪里读 | 限制了什么 |
|---|---|---|
| CPU 配额 | `/sys/fs/cgroup/cpu.max` | 能用多少 CPU 时间 |
| 进程/线程数 | `/sys/fs/cgroup/pids.max` | 池最多能建多少执行体 |
| 打开文件数 | `RLIMIT_NOFILE`（`getrlimit`） | 连接、epoll、端口文件的总数 |
| 每用户进程数 | `RLIMIT_NPROC`（`getrlimit`） | `pthread_create`/`fork` 何时返回 `EAGAIN` |

进程池常见的 3–10 个子进程是经验值，不是定律。按内存、fd 预算和故障隔离需求定：每个子进程都有独立地址空间，隔离好，但共享状态要另做。

启动顺序可以这样排：

- 先建监听 fd，再建池，最后才把监听 fd 注册进 epoll。
- 预热：让每个 worker 先跑一个空任务，把栈和分配器准备好。
- 停止：关监听、关队列、唤醒并 `join` 所有执行体。

池要能启动、预热、扩缩和优雅停止。C++20 的 `std::jthread` 析构时先 `request_stop()` 再 `join()`（`[thread.jthread.dtor]`），适合协作停止；`stop_token` 只能传“该停了”，不会替你把阻塞在队列上的线程叫醒，队列仍要 `close` 并唤醒等待者。

## 35.2 两个正交问题：socket 归谁、连接是否固定执行体

{{#fig ch35/design_space}}

问题一：监听 socket 和连接 socket 由主线程统一管，还是 worker 自己 `accept`。主线程 accept 后，可以把连接 fd 交给某个 worker 自己的 epoll，也可以自己读完请求、只把任务放进队列；跨进程交 fd 要 `SCM_RIGHTS`。

问题二：同一连接上的多个请求是否始终由同一个执行体处理。无状态任务可以跨执行体；kvd 的解析缓冲和连接状态要求固定，否则半个请求留在 A 的缓冲里，B 只看到后半截。

四种组合都在 {{#figref ch35/design_space}} 里：左上角是半同步/半异步，主线程 accept 后把连接分给某个 worker 自己的 epoll，跨进程要 `SCM_RIGHTS`；左下角是半同步/半反应堆，主线程负责读写，就绪的请求进队列，任意 worker 取。右列两种由 worker 自己 accept，省掉传 fd，但要处理分流和归属。

- 同进程：fd 表共享，把 fd 数值交给 worker 就行。
- 跨进程：用 `SCM_RIGHTS` 传 fd，或让 worker 自己 accept。

管道只能传字节，不能传 fd。旧写法“父进程 accept 后往管道写数据，把连接交给子进程”是断裂的：子进程收到的是数据副本，拿不到那个 socket。跨进程交连接要用 `sendmsg` 的 `SCM_RIGHTS`，或者让子进程自己 `accept`（`SO_REUSEPORT`）。

`EPOLLONESHOT` 和“连接固定到 worker”是两种归属办法：前者把连接动态借给一个 worker，处理完用 `EPOLL_CTL_MOD` 重新注册；后者静态绑定，连接从生到死只在一个事件循环里。

| 结构 | 谁 accept | 连接归属 | 是否传 fd | 锁/队列 | 适用 |
|---|---|---|---|---|---|
| 半同步/半反应堆 | 主线程 | 可跨 worker，同一时刻一个 | 不传，连接由主线程读写 | 请求队列锁 | 读多、业务复杂、要集中做 I/O |
| 半同步/半异步 | 主线程 | 固定到某个 worker 的 epoll | 同进程共享 fd 表；跨进程 `SCM_RIGHTS` | 通知机制 | 连接多、accept 集中 |
| 每 worker 一个 epoll | 各 worker | 固定到 accept 它的 worker | 不需要 | 无跨 worker 队列 | 长连接、高吞吐 |
| 领导者/追随者 | 当时的 Leader | 可跨，靠 `EPOLLONESHOT` 一次只给一个 | 不需要 | 推选锁 | 设计对照，事件源单一 |

## 35.3 半同步/半反应堆：一个 I/O 线程 + 工作线程池

{{#fig ch35/half_sync_half_reactive}}

主线程用 epoll 只做 accept、read、write：攒到至少一行完整请求，就把连接对象和这一批完整的行（最多 16 行）投进队列。worker 解析、查表、生成响应，写回可以回主线程，也可以 worker 直接写并给连接加锁。这里选前者，worker 完全不碰 socket。

这就是“模拟 Proactor”：worker 看到的是主线程已经读完的数据，完成事件由主线程代劳，不是内核给的完成通知。

队列必须有界。满了就暂停 `EPOLLIN`（背压），或直接返回错误；无界队列会把慢客户端的问题放大成内存和尾延迟问题。

- 队列满：暂停读，等 worker 腾出位置再恢复。
- 连接关闭：`shared_ptr` 延长生命周期，结果回来时检查 `closed`。

- 队列长度继续涨，内存跟着涨。

连接归属还有一条路：`EPOLLONESHOT`。

- 主线程把连接借给一个 worker，同一连接同一时刻只有一个 worker。
- worker 处理完用 `EPOLL_CTL_MOD` 交回，代价是每次多一次 `epoll_ctl`。

## 35.4 每执行体一个事件循环：SO_REUSEPORT 与 EPOLLEXCLUSIVE

{{#fig ch35/per_worker_loop}}

N 个线程/进程各自 `epoll_create1`。监听可以共享一个 fd，用 `EPOLLEXCLUSIVE`（Linux 4.5）让内核优先唤醒一个等待者；也可以各自 `socket`+`SO_REUSEPORT`（Linux 3.9）+`bind`+`listen`，由内核按四元组分流。

- `SO_REUSEPORT` 要求每个 socket 都设该选项（包括第一个），且所有绑定进程的有效 UID 相同。
- `EPOLLEXCLUSIVE` 只能用在 `EPOLL_CTL_ADD`，之后对同一对 epoll/fd 做 `MOD` 返回 `EINVAL`；它不保证只唤醒一个，也不保证公平。
- 连接不跨执行体，没有请求队列锁，也没有跨线程任务传递；代价是连接迁移、全局统计和优雅退出更麻烦。

## 35.5 领导者/追随者：省掉请求队列的锁

{{#fig ch35/leader_followers}}

线程只有三种状态：Leader 在 `epoll_wait` 等事件，Processing 处理事件，Follower 睡在池里等成为 Leader。任意时刻只有一个 Leader。

事件到达后先 `promote_new_leader`，再处理事件。推选新 Leader 和 Follower 加入都要同步（旧资料叫 Synchronizer），否则两个线程同时成为 Leader，或者都睡死。

```cpp
void promote_without_wakeup(int current) {
    leader = (current + 1) % kThreads;  // 改了 leader
}                                        // 但没有 cv.notify_all()
```

上面这段就是下面死锁示例的错法。改了 `leader` 只让谓词变真，不会把已经睡在条件变量上的线程叫醒。

- 等待者醒来靠通知，不靠谓词自己变真。
- 处理完事件的线程回到池里，也要重新等一次。

共享事件源上的连接要配 `EPOLLONESHOT`：一次事件只交给一个线程，处理完用 `EPOLL_CTL_MOD` 重新注册；否则同一个连接可能被两个 Leader 同时拿到。连接因此可以在不同轮次换人处理，但同一时刻只有一个线程。

优点是没有请求数据要跨线程传，也没有请求队列的锁。锁没有消失，只是从“队列”移到了“Leader 推选”。缺点是：

- 只支持一个事件源集合。
- 推选和唤醒有成本，状态机容易写错。
- 今天更常用 `SO_REUSEPORT` 或 accept mutex 达到类似效果；领导者/追随者适合作为设计对照。

## 35.6 进程池：socketpair 通知、子进程 accept、SIGCHLD 回收

{{#fig ch35/process_pool}}

父进程创建监听 fd 和 N 个子进程，父子之间用 `socketpair` 通知“有新连接，去 accept”。子进程继承监听 fd，自己 `accept`，避免跨进程传连接 fd；父进程不 accept，也不持有连接。

- 父进程只保留监听 fd；连接 fd 由子进程 `accept4` 得到，父进程没有可关的那一份。
- `SIGCHLD` 用循环 `waitpid(-1, …, WNOHANG)` 回收到 0 或 `ECHILD`；标准信号会合并，读到一个通知不代表只有一个子进程退出。
- 子进程崩溃后按需补一个，槽位和 socketpair 一起换新。


```text

```

看 `进程数从 3 回到 4`：`kill -9` 之后父进程收到 `SIGCHLD`，`waitpid` 回收，再 `fork` 一个补上。这个替换示例用 `sigwait` 同步等信号，避免“信号在检查和 `sigsuspend` 之间到达”的丢失唤醒。

`SO_REUSEPORT` 版本的变化：

- 每个子进程自己 `socket`+`bind`+`listen`，内核分流，父进程不再需要 `socketpair`。
- 要求同 UID、所有 socket 都设该选项。
- `SIGCHLD` 回收照旧；优雅退出从“停止通知”改成给每个子进程发 `SIGTERM`。

进程池默认不共享存储，要共享得用共享内存和进程间锁。这也是 `kvd_shm` 和 35.4 的 `kvd_reuseport` 的分界：前者共享表，后者是线程版，所有 worker 共用同一个 `Store`。只有换成每个子进程自己 `bind` 的 `SO_REUSEPORT` 进程版，才会各存各的。

| 对照项 | 线程池 | 进程池 |
|---|---|---|
| 隔离 | 共享地址空间，一个线程崩了全进程受影响 | 独立地址空间，一个子进程崩了可补 |
| 创建成本 | `clone` + 栈，便宜 | `fork` + 页表/地址空间，贵 |
| 共享状态 | 直接读写，要加锁 | 默认不共享，要共享得用 IPC/共享内存 |
| 通信 | 队列、条件变量、eventfd | socketpair、管道、共享内存 |
| 故障恢复 | 线程异常通常终止进程 | 父进程回收后补一个 |

CGI 是进程池的典型：`fork` + `dup2` + `exec`，把连接 fd 复制到标准输入输出。今天用 `posix_spawn` + `posix_spawn_file_actions_adddup2`，并把无关 fd 设 `CLOEXEC`，免得漏进子进程。

- 单线程 epoll 的吞吐最高；半同步/半反应堆低一截。
- 每 worker 一个 epoll 在连接少时接近单线程，连接多时掉下来。
- 共享内存进程池（`kvd_shm`）的 P99 最低，但它在共享内存和跨进程锁上多付了成本。

数字会随机器、负载和内核变化，这里只讲方向。尾延迟的来源按出现频率排：请求队列排队、慢客户端、accept 不均、内存分配、日志。先测量再优化，把线程数翻倍经常只是把排队挪到别处。

回环测试只讲趋势，不能外推到多机：回环没有真实网络的重传、RTT 和带宽限制，客户端和服务器还抢同一组核。

> **旧资料提示**：线程数按 `nproc` 估，今天按 cgroup 的 `cpu.max`、`pids.max` 和实测决定；读取接口见 [第 42 章](ch42.md)。

## 速查

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `pthread_create` | 建线程 | 返回错误码，不设 `errno`；资源不足返回 `EAGAIN` |
| `pthread_detach` | 分离线程 | 之后不能 `join`；池析构不会等它 |
| `std::thread` | C++11 线程 | 析构时仍 joinable 会 `std::terminate()` |
| `std::jthread` | C++20 线程 | 析构先 `request_stop()` 再 `join()` |
| `std::stop_token` | 协作停止 | 线程不检查就不会停 |
| `std::counting_semaphore` | C++20 计数信号量 | 可替代 `sem_t`，不替队列做上限 |
| `std::condition_variable` | 等待/唤醒 | 谓词 + 通知一起用，防丢失唤醒 |
| `epoll_create1(EPOLL_CLOEXEC)` | 建事件表 | Linux 2.6.27 起 |
| `EPOLLONESHOT` | 事件只触发一次 | 处理完 `EPOLL_CTL_MOD` 重置 |
| `EPOLLEXCLUSIVE` | 减少惊群 | 4.5 起；只能 `ADD`，`MOD` 返回 `EINVAL` |
| `SO_REUSEPORT` | 多 socket 绑同一端口 | 3.9 起；所有 socket 都设，同有效 UID |
| `socketpair` | 父子双向字节通道 | 只传字节，不传 fd；要 fd 用 `SCM_RIGHTS` |

| `posix_spawn` | fork+exec 的可移植封装 | 用 file actions 做 `dup2`，fd 设 `CLOEXEC` |
| `RLIMIT_NOFILE` | fd 上限 | 连接、epoll、端口文件都算 |
| `RLIMIT_NPROC` | 每用户进程/线程上限 | 对 `CAP_SYS_RESOURCE`/`CAP_SYS_ADMIN` 不生效 |

| 结构 | accept 者 | 连接归属 | 锁/队列 | 适用 |
|---|---|---|---|---|
| 半同步/半反应堆 | 主线程 | 可跨，同一时刻一个 | 有界请求队列 | 读多、业务复杂 |
| 半同步/半异步 | 主线程 | 固定到某个 worker 的 epoll | 通知，跨进程传 fd | 连接多、accept 集中 |

## 思考题

1. （预测）35.3 的有界队列从 1024 降到 64，吞吐和 P99 会怎么变？慢客户端比例升高时呢？

   <details><summary>提示</summary>

   队列小，背压来得早：读被暂停得更频繁，吞吐可能下降，但排队长度上限小，P99 的尾部会被压住。慢客户端比例升高时，队列更快被占满，暂停读会影响所有连接，P99 反而可能变差；用 `--queue-cap 64` 和 1024 各跑一轮对比。

   </details>

2. （找错）35.4 的 `SO_REUSEPORT` 版本如果只给其中一个 worker 设了该选项，`bind` 会成功吗？连接会落到哪些 worker？

   <details><summary>提示</summary>

   不会成功，后 `bind` 的 socket 返回 `EADDRINUSE`。`SO_REUSEPORT` 要求参与共享地址的每个 socket 在 `bind` 前都设它，包括第一个；只设一个时，其余 socket 仍在抢同一个地址。

   </details>

3. （权衡）半同步/半反应堆和每 worker 一个 epoll，在“短连接、每连接一个请求”和“长连接、每连接大量请求”下各自表现如何？

   <details><summary>提示</summary>

   短连接、每连接一个请求时，半同步/半反应堆的队列和 eventfd 交接占大头，吞吐和尾延迟都不占优；每 worker 一个 epoll 省掉交接，但 accept 分布可能不均。长连接、每连接大量请求时，队列只按连接出现一次，半同步/半反应堆的集中读更容易成为瓶颈；每 worker 一个 epoll 让读也分散，通常更合适。

   </details>

4. （迁移）把 35.6 的进程池改成 `SO_REUSEPORT` 版本：父进程还需要 `socketpair` 吗？`SIGCHLD` 回收和优雅退出要改哪里？

   <details><summary>提示</summary>

   不需要 `socketpair` 通知，每个子进程自己 `socket`+`SO_REUSEPORT`+`bind`+`listen`。`SIGCHLD` 回收不变，仍要循环 `waitpid` 并补子进程；优雅退出时父进程不能再靠“停止通知”让子进程空闲，要给每个子进程发 `SIGTERM`；子进程的信号处理器停止 accept、排空手头连接后退出，父进程等所有子进程回收完。

   </details>
