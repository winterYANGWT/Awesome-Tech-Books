## 26.1 信号的基本语义：产生、处置、阻塞、未决

{{#fig ch26/signal_delivery}}

先看第 2 步到第 4 步：信号产生后先进入 pending 位图；如果当前线程的掩码挡着它，内核不会递送，只会留着这个未决位。第 7 步才是处理函数真正执行。

处置和排队规则：

- 处置只有 `SIG_DFL` 默认、`SIG_IGN` 忽略、用户处理函数三种。
- `SIGKILL` 和 `SIGSTOP` 不能被捕获、阻塞或忽略；`sigaction` 对它们返回 `EINVAL`。
- 忽略的处置在 exec 后仍保留；捕获的处置在 exec 后恢复默认。
- 标准信号不排队：阻塞期间产生多次，pending 位图里只保留一个位。
- 实时信号才排队，`sigqueue` 还能附带一个 `sigval`。

`sigaction` 的 `sa_handler` 和 `sa_sigaction` 二选一；后者配合 `SA_SIGINFO` 能拿到 `siginfo_t`。

`sa_mask` 只在处理函数执行期间追加屏蔽，`SA_NODEFER` 可以不让当前信号自动屏蔽。`SA_RESETHAND` 让处理函数执行一次后恢复默认，`SA_ONSTACK` 改用备用栈。

信号掩码有三条规则：

- 每个线程一份；单线程用 `sigprocmask`，多线程用 `pthread_sigmask`。
- 新建线程继承创建者的掩码。
- `fork` 出的子进程继承掩码和处置，未决集清空。
- `SIG_SETMASK` 直接替换整个掩码，`SIG_BLOCK`/`SIG_UNBLOCK` 只做并集或差集。

`kill` 的 `pid` 参数决定收信者：

| `pid` | 收信者 |
|---|---|
| `> 0` | 指定进程 |
| `0` | 调用者所在进程组的所有进程，包括调用者自己 |
| `-1` | 除 init 外所有有权限的进程 |
| `< -1` | 进程组 `-pid` 的所有进程 |
| 任意 | `sig == 0` 时只检查存在性和权限，不发信号 |

`kill` 失败返回 -1 并设置 `errno`：无效信号是 `EINVAL`，没权限是 `EPERM`，目标不存在是 `ESRCH`。

`SA_RESTART` 只让一部分系统调用自动重启。`epoll_wait`、`poll`、`select`、`nanosleep`、`clock_nanosleep` 即使设了 `SA_RESTART`，被处理函数打断时仍返回 `EINTR`。

`EINTR` 的处理有两条：

- 它不是“调用失败”，而是“调用没做完”，已经产生的副作用要自己记账。
- 重试前要重算剩余超时；已经读到的字节不能丢，否则会重复处理。

## 26.2 async-signal-safe：处理函数里只能做很少的事

{{#fig ch26/async_safe}}

处理函数和主流程在同一个线程里运行，随时可能打断一条正在执行的语句。它只能调用 POSIX 列为 async-signal-safe（异步信号安全）的函数：`write`、`read`、`_exit`、`kill`、`waitpid`、`sem_post`、`sigaction` 等。`printf`、`malloc`、`syslog`、`pthread_mutex_lock`、`std::mutex::lock` 都不在列表里。

处理函数还和主流程共享 `errno`。进入时保存、返回前恢复，否则主流程刚设置的错误码会被处理函数覆盖。

```c
static void on_signal(int signo) {
    int saved = errno;
    /* 只做 async-signal-safe 的事 */
    errno = saved;
}
```

`volatile sig_atomic_t` 只保证“一个处理函数和主流程之间”的整个 `sig_atomic_t` 对象读写不被撕裂（本机是 4 字节），不提供跨线程同步。C++ 的 `std::atomic` 只有在操作属于“plain lock-free atomic operation”时才被标准列为 signal-safe；带锁的实现、或者运行时不 lock-free 的原子类型，不能带进处理函数，下面几点尤其重要。

- `std::atomic` 是否可用，取决于这次操作是不是 plain lock-free，不能只看类型名。
- `std::atomic_signal_fence` 只约束同一线程的编译器重排，不建立跨线程同步。
- 它也不会让 `malloc`、`printf` 或 `std::mutex::lock` 变得可调用。
- 处理函数里的 `write` 也可能只写一部分；不要为剩下的字节循环等待，丢掉通知比卡住好。
- `syslog` 也可能拿锁或分配内存；处理函数里不要写日志。
- 要唤醒其他线程时，写一个字节到 `eventfd` 或非阻塞 pipe，比在 handler 里抢锁稳。

最常用的两类是处理函数往非阻塞 pipe/eventfd 写一个字节，或者设置一个 `volatile sig_atomic_t` 标志；`sem_post` 也是 async-signal-safe 的唤醒方式，`signalfd`/`sigwait` 则把信号移出处理函数。其余工作留给主循环。

## 26.3 统一事件源：自管道、signalfd 与 eventfd

{{#fig ch26/signalfd_pipeline}}

统一事件源（unified event source）的意思是：信号不要单独占一条执行路线，而是变成事件循环里可读的 fd。图里第 4 步到第 7 步是重点：信号挂在 pending 里，`signalfd` 的 fd 变可读，`epoll_wait` 返回后，第 7 步才 `read` 出 `signalfd_siginfo`。`signalfd` 不是处理函数。

自管道有四个要点：

- 用 `pipe2(O_NONBLOCK | O_CLOEXEC)` 建一对 fd。
- 处理函数只往写端写一个字节。
- 主循环读读端，读到后再做真正的工作。
- 写端满了就丢通知；标准信号本来会合并，字节只能当“有信号来过”的提示。

`signalfd` 省掉了处理函数。先用 `pthread_sigmask` 在所有线程屏蔽目标信号，再调 `signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC)`；`read` 得到 `struct signalfd_siginfo`，用 `ssi_signo` 区分信号。

结构体里还有 `ssi_pid` 和 `ssi_uid`，能看出是谁发的；一次 `read` 可以取走多个已经 pending 的结构体。

`signalfd`、`eventfd` 和 `timerfd` 的实现细节：

- `eventfd` 不携带信号编号，内核只维护 64 位计数器；`read` 清零，`EFD_SEMAPHORE` 时每次减一。
- `signalfd`、`eventfd`、`timerfd` 都能进同一个 `epoll`；`timerfd` 把定时也变成 fd。
- `timerfd` 的 `read` 返回 `uint64_t` 的到期次数，不是时间戳。
- `signalfd` 的掩码可以用 `signalfd(fd, &mask, 0)` 更新，不必重建 fd。
- `read` 仍可能返回 `EAGAIN` 或 `EINTR`，事件循环要按普通非阻塞 fd 处理。
- `signalfd` 本身不在 async-signal-safe 列表里，只给主循环读。
- `eventfd` 的计数器上限是 2^64-2；写满后非阻塞写返回 `EAGAIN`。

## 26.4 信号与线程：pthread_sigmask、sigwait、pthread_kill

{{#fig ch26/thread_mask}}

所有线程共享信号处置，但每个线程有自己的掩码。进程定向的信号会送给任意一个没有屏蔽它的线程。Linux 的实现注释说主线程没屏蔽时通常先给主线程，但 POSIX 只要求“任选一个未屏蔽线程”，不能把这个顺序写进程序逻辑。

标准做法是反过来：主线程在创建其他线程之前先屏蔽要接管的信号，所有新线程继承同一个掩码，再起一个专用线程循环 `sigwait`。这样信号只会在那个线程被取走，不会突然打断某个工作线程。

`sigwait` 有四条容易记错的规则：

- 成功返回 0，失败返回错误码，不设置 `errno`。
- 被取走的信号不再调用处理函数。
- `sigwaitinfo` 还能拿到 `siginfo_t`；`sigtimedwait` 可以带超时。
- `sigwait` 是取消点；用 `pthread_cancel` 时要把清理路径想清楚。

`pthread_kill(t, sig)` 把信号定向到某个线程。`sig == 0` 时只做错误检查，不发信号；但 `pthread_t` 在线程结束后会被复用，不能用它判断线程是否还活着。

不要把信号当通用线程通信：

- 唤醒工作线程用 `eventfd`、条件变量或 `stop_token`，这些接口能带状态和超时。
- `pthread_kill` 只能发给同一进程里的线程；跨进程要用 `kill` 或 `pidfd_send_signal`。

## 26.5 多线程进程里的 fork：只有调用线程活下来

{{#fig ch26/fork_thread}}

`fork` 只复制调用它的那个线程，其他线程在子进程里不存在。但地址空间是整份复制的，别的线程持有的互斥量、条件变量、`std::mutex` 状态也跟着复制过去。子进程再对同一把锁加锁，就可能永远等一个不会回来的解锁。

`pthread_atfork(prepare, parent, child)` 可以注册 fork 前后的回调。`prepare` 在调用 `fork` 的线程里、fork 之前执行；`parent` 和 `child` 分别在父/子进程里执行。

`prepare` 按注册逆序执行，`parent`/`child` 按注册正序执行。它只覆盖注册过的锁，还有几条限制：

- 库或第三方代码里的锁不会自动纳入。
- 调用 `fork` 的线程自己已经持有某把锁时，`prepare` 里再锁它会自死锁。
- `std::mutex` 没有可移植的 atfork 钩子；它的内部状态不能由标准接口安全地重置。
- `prepare` 卡在锁上时，`fork` 也一起卡住；它不是“无代价的保险”。
- `fork` 还复制 fd 表：监听 socket、epoll fd、连接 fd 都会进子进程。

Linux 的 libstdc++ 用 pthread mutex 实现 `std::mutex`，但 C++ 标准没有给 atfork 定义接口；把 `std::mutex` 塞进 pthread 回调不是可移植做法。

`fork` 之后的子进程要注意：

- 子进程总是只保留调用线程；其他线程不再存在，它们的栈和 TLS 内存仍随地址空间复制过来，只是没有线程使用。
- `exec` 之前只能调用 async-signal-safe 函数。
- 用 `_exit`，不要用 `exit`；`exit` 会刷新从父进程复制来的 stdio 缓冲、执行 `atexit` 回调。
- 首选 `posix_spawn`，或者 `fork` 后立刻 `exec`；`posix_spawn` 用 file_actions 做 dup2 和 close。

必须在多线程进程里 fork 时，把相关锁纳入 `atfork`，并在子进程里尽快 exec。Linux 5.3 起的 `clone3` 和 `pidfd` 给进程管理更多控制，但不改变“fork 只复制一个线程”这个事实。

## 26.6 服务器最常遇到的三个信号：SIGHUP、SIGPIPE、SIGURG

{{#fig ch26/sighup}}

SIGHUP 常用来重读配置。处理函数只设标志或写一个字节，解析配置放到主循环。没有控制终端的守护进程不会因为终端挂起自动收到 SIGHUP，要 `kill -HUP` 显式发。

SIGPIPE 在向读端已关闭的管道或 socket 写数据时产生，默认处置下进程被终止，写调用不会返回。忽略、捕获或阻塞 SIGPIPE 后，`write` 才返回 -1、`errno=EPIPE`。规避方式有三种：进程级忽略（影响所有线程）、`send(MSG_NOSIGNAL)`、用 `EPOLLRDHUP` 或 `recv` 返回 0 提前发现对端关闭。

SIGURG 的处理要点：

- 先用 `fcntl(F_SETOWN)` 设宿主。
- 多线程里用 `F_SETOWN_EX` 加 `F_OWNER_TID`（Linux 2.6.32）把通知送到具体线程。
- 处理函数里用 `recv(MSG_OOB)` 读那个字节。
- `sockatmark` 判断读指针是否已到标记；今天也可以用 `epoll` 的 `EPOLLPRI`。
- OOB 只有一个紧急指针，不同协议栈的语义不完全一致。

| 信号 | 典型来源 | 默认处置 | 处理要点 |
|---|---|---|---|
| SIGHUP | 终端挂起、`kill -HUP` | 终止 | 只写一个字节，主循环重读配置 |
| SIGPIPE | 写已关闭的管道/socket | 终止 | 忽略、`MSG_NOSIGNAL`、`EPOLLRDHUP` |
| SIGURG | TCP 带外数据 | 忽略 | `F_SETOWN`/`F_SETOWN_EX`、`recv(MSG_OOB)` |

SIGHUP 的处理函数不要 `fopen`：`fopen` 可能 `malloc`，可能和主线程的 stdio 锁冲突。只写一个字节，让主循环去读文件。

`POLLPRI=1` 说明带外数据让 fd 进入优先事件，`SIGURG=1` 说明宿主设置生效。`sockatmark=1` 时读指针停在紧急标记上，先读走普通数据 `abc`，再用 `MSG_OOB` 读 `!`，最后继续读 `def`。常见的错误有几处：

- `kill(0, sig)` 包括调用者自己。
- 默认处置的宏是 `SIG_DFL`，不是 `SIG_DEF`。
- `SA_INTERRUPT` 在 Linux 上是历史空操作，是否中断只看 `SA_RESTART`。

- `SA_RESTART` 不影响 `epoll_wait`，`EINTR` 仍要自己重试。

另外，管道读端关闭时写端得到的是 `POLLERR`，不是 `POLLHUP`。判断 TCP 对端关闭用 `EPOLLRDHUP` 或 `recv` 返回 0 更可靠。

> **旧资料提示**：旧教程用 `signal()` 装处理函数。POSIX.1-2001 起应优先 `sigaction()`，它能控制 `sa_mask`、`SA_RESTART` 和 `SA_SIGINFO`；原因见 [第 41 章](ch41.md)。

> **旧资料提示**：自管道统一事件源仍然可用，但 Linux 上可以用 `signalfd`（2.6.22）和 `eventfd`（2.6.22）省掉处理函数；取舍见 [第 41 章](ch41.md)。

> **旧资料提示**：用 `pthread_kill(t, 0)` 判断线程是否存活不可靠。应改用 `join`、`stop_token` 或应用层心跳；见 [第 37 章](ch37.md)。

## 速查

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `sigaction` | 设置处置、`sa_mask`、`sa_flags` | 比 `std::signal` 完整；`SA_RESTART` 只重启部分调用 |
| `sigset_t`、`sigemptyset`、`sigaddset` | 构造信号集 | 布局是实现私有的，只用这组函数 |
| `sigprocmask` | 单线程改掩码 | 多线程改用 `pthread_sigmask` |
| `pthread_sigmask` | 改当前线程掩码 | 新线程继承创建者掩码；返回错误码，不设 `errno` |
| `sigpending` | 查调用线程的未决集 | 标准信号只保留一个 pending 位 |
| `sigwait` | 同步取信号 | 目标信号要在所有线程屏蔽；成功返回 0，失败返回错误码 |
| `sigwaitinfo`、`sigtimedwait` | 同步取信号并取 `siginfo_t` 或超时 | 目标信号要在所有线程屏蔽；成功返回信号编号，失败返回 -1 并设置 `errno` |
| `pthread_kill` | 定向给某个线程 | `sig=0` 只做错误检查；线程 ID 会复用 |
| `kill`、`raise` | 发信号 | `kill(0, sig)` 包括调用者；`sig=0` 只检查存在性 |
| `signalfd` | 把信号变成 fd | 先屏蔽；不能处理 `SIGKILL`/`SIGSTOP` 和同步异常 |
| `eventfd` | 64 位计数器唤醒 | `read` 清零；`EFD_SEMAPHORE` 时每次减一 |
| `timerfd` | 把定时变成 fd | `read` 得到到期次数，不是时间 |
| `pipe2` | 建自管道 | `O_NONBLOCK | O_CLOEXEC`；满了会丢通知 |
| `volatile sig_atomic_t` | 处理函数和主流程之间的标志 | 只保证整个 `sig_atomic_t` 对象读写不被撕裂 |
| `std::atomic_signal_fence` | 同线程编译器栅栏 | 不建立跨线程同步，不解决 async-signal-safe |
| `MSG_NOSIGNAL` | 压住这次 `send` 的 SIGPIPE | 仍返回 `EPIPE`；忽略 SIGPIPE 则是进程级 |
| `F_SETOWN_EX` + `F_OWNER_TID` | 把 SIGURG 送到指定线程 | Linux 2.6.32 起；单线程可用 `F_SETOWN` |
| `pthread_atfork` | fork 前后的回调 | 只覆盖注册过的锁；`prepare` 可能自死锁 |
| `posix_spawn` | 交给实现做 fork+exec | 多线程进程里比手写 fork 安全 |

## 思考题

1. （找错）26.2 的处理函数如果改成 `write(2, "sig\n", 4)`，它一定安全吗？`write` 本身是 async-signal-safe，但 fd 2 可能被谁关掉或替换？

   <details><summary>提示</summary>

   不一定。fd 2 可能已关闭而返回 `EBADF`，也可能被重定向到阻塞的管道、socket 或普通文件；`write` 仍可能阻塞或只写一部分。async-signal-safe 只说明函数内部不拿不安全的锁，不说明目标 fd 一定可写、不会阻塞。

   </details>

2. （预测）26.4 里主线程屏蔽了 SIGUSR1，但某个 worker 在创建后自己 `pthread_sigmask(SIG_UNBLOCK, ...)`，`pthread_kill` 定向发给这个 worker 时，`sigwait` 线程还能收到吗？

   <details><summary>提示</summary>

   不能。定向信号只挂在这个 worker 的 pending 集里；worker 解除屏蔽后，处理函数在它自己身上执行。`sigwait` 等的是调用线程可取的 pending 信号，拿不到别的线程的定向信号。把 `pthread_kill` 换成 `kill(getpid(), SIGUSR1)` 才会变成进程定向，结果取决于哪个线程没屏蔽。

   </details>

3. （权衡）`signalfd` 和专用 `sigwait` 线程各适合什么服务器结构？如果信号必须在 `epoll_wait` 同一线程里处理，选哪个，代价是什么？

   <details><summary>提示</summary>

   单线程事件循环、信号要和 I/O 一起排队的程序选 `signalfd`：没有额外线程，但只能在 Linux 上用，且要先在所有线程屏蔽。信号很少、逻辑独立的程序可以用 `sigwait` 线程，代价是多一个线程和一套停止协议，信号处理与 I/O 的先后顺序也不再由 `epoll` 统一决定。

   </details>

4. （迁移）把 26.5 的死锁例子改成“子进程 fork 后立刻 exec”，哪些锁问题消失了？哪些 fd 继承问题反而更需要 `CLOEXEC`？

   <details><summary>提示</summary>

   子进程不再碰父进程的互斥量和 C++ 对象，锁死锁和 `atfork` 都不需要了。但 exec 会保留所有没设 `FD_CLOEXEC` 的 fd：监听 socket、epoll fd、其他连接、管道写端都会漏进新程序。创建时用 `SOCK_CLOEXEC`/`O_CLOEXEC`，或用 `close_range` 批量关闭。

   </details>
