# 第 13 章 内存序与栅栏

四个线程、两个原子 `bool`、一个原子 `int`。默认内存序下 `assert(z != 0)` 从不触发，换成 `relaxed` 或 release/acquire，标准都允许它偶尔触发。三种写法都没有数据竞争，差别只在允许看到什么顺序。

本机是 x86-64。x86 的 TSO 会挡住一部分弱序结果：四线程的独立读独立写（IRIW）形状在本机连 `relaxed` 都不触发，所以 13.2 和 13.3 的失败例子改用 store buffer 形状，它在 x86 上能看见；13.6 解释为什么。

## 13.1 顺序一致：先有一条所有人都同意的总序

{{#fig ch13/seq_cst_total_order}}

`memory_order_seq_cst` 是所有原子操作的默认值。它不只给每个变量一条修改顺序，还给所有 `seq_cst` 操作一条全局总序 S。总序有三条含义：

- 每个 `seq_cst` 操作在 S 上有一个位置。
- 每个线程看到的顺序都是这条 S 的子序列。
- 不同变量的 store 也在同一条 S 上，不只是同一个变量有顺序。

看第 2–6 步。A 先读到 `x=true`，再读到 `y=false`，这说明在 S 里，写 y 排在 A 的 y 读之后。B 要读到 `y=true`，它的 y 读就必须排在写 y 之后。

把这条链拆开看：

- A 读到 `x=true`，说明 A 的 x 读在写 x 之后。
- A 又读到 `y=false`，说明 A 的 y 读在写 y 之前。
- B 读到 `y=true`，说明 B 的 y 读在写 y 之后；B 的 x 读又在 y 读之后，所以它必在写 x 之后。

两个读者都失败需要一条环：A 的 y 读 → 写 y → B 的 y 读 → B 的 x 读 → 写 x → A 的 x 读 → A 的 y 读，矛盾。

程序统计的是“两个读者都没看到对方写”的轮数。100 万轮里是 0：不是运气好，而是总序不允许那种执行。这条总序不是免费的：处理器要让所有核在顺序上达成一致，通常比 acquire/release 贵。

代价主要在 store：

- x86-64 的 acquire/release 几乎不需要额外指令。
- `seq_cst` store 才要 `xchg` 或 `mfence` 一类操作。
- ARM64 的代价关系不同，13.6 再讲。

写新代码时先用 `seq_cst` 把逻辑写对，再用性能数据决定要不要放宽；不要一上来就挑最弱的内存序。

## 13.2 自由序：每个变量一条修改顺序

{{#fig ch13/relaxed_notebooks}}

`memory_order_relaxed` 只保证两件事：

- 同一个原子变量有一条所有线程认可的修改顺序。
- 同一线程对同一变量的操作不会被重排。

不同变量之间没有顺序，也不建立同步。13.1 的四线程 IRIW 在本机 x86-64 上连 `relaxed` 也不触发：TSO 不允许两个读者看到相反的顺序。要在这台机器上看见失败，用 store buffer 形状：每个线程先写自己的变量，再读对方的变量。

## 13.3 获取-释放：成对同步，没有总序

{{#fig ch13/store_buffer}}

release/acquire 的规则有两条：

- release store 与“读到该 store 写入的值（或释放序列中后续值）”的 acquire load 同步。

## 13.4 栅栏：给一组操作排序

{{#fig ch13/fence_position}}

`std::atomic_thread_fence(memory_order_release)` 放在数据写之后、发布用的原子 store 之前，能把前面的写和后面的 store 排成“先于”；后面的 store 本身可以是 relaxed。读线程在 load 之后放 acquire 栅栏，能把后面的读排到 load 之后。

```cpp
void writer() {
    x.store(true, std::memory_order_relaxed);
    std::atomic_thread_fence(std::memory_order_release);
    y.store(true, std::memory_order_relaxed);
}

void reader() {
    while (!y.load(std::memory_order_relaxed)) {
    }
    std::atomic_thread_fence(std::memory_order_acquire);
    if (x.load(std::memory_order_relaxed)) ++z;
}
```

栅栏的位置决定它排序的范围：

- release 栅栏放在数据写之前：前面没有写，排不了任何东西；它应放在数据写之后、release store 之前。
- acquire 栅栏放在 load 之前：只能管后面的操作，管不了前面的 load。
- `seq_cst` 栅栏夹在 store 与 load 之间：store 先于后面的 load；下面的例子在 x86 上用这个形状。

栅栏不仅能排序原子操作，也能排序非原子操作。把上面的 `x` 换成普通 `bool`，只要 `y` 仍是原子变量，release 栅栏前的普通写、acquire 栅栏后的普通读仍被排序，`x` 上没有数据竞争。

本机 x86 的两个事实：

- release 栅栏对写—写不产生硬件指令，只阻止编译器重排。
- 同样的位置错误在 x86 上看不出来，在 ARM 上会。为了在这台机器上看见“位置”的效果，下面两个例子用 store buffer 形状和 `seq_cst` 栅栏：在这个形状里，只有 `seq_cst` 栅栏能挡住 store→load 重排。

## 13.5 释放序列与读-改-写链

{{#fig ch13/release_sequence}}

释放序列是以一个 release store 为头、后面跟着同一变量上的一串读-改-写操作（C++20 起只算读-改-写，同线程的普通 store 不算）。链上的操作可以全是 `relaxed`，但 acquire load 读到链上任意一个值时，仍与最初的 release store 同步。

释放序列的两个边界：

- 链上必须有同一变量上的读-改-写；只有普通 store 时，释放序列不成立。
- 它解决的是“第二个消费者为什么也能看到生产者写的数据”，不是“消费者之间怎么排队”。

如果链上没有读-改-写、只有普通 store，第二个消费者要么读到生产者直接写的值，要么读到别人的普通写，同步关系会断。

释放序列常和“计数器加一/减一”一起出现。链上的每个读-改-写都返回前一个值，所以两个消费者拿到的下标不会重复，这也是它可以同时做“计数”和“领任务”的原因。写这种代码时要把“谁 release、谁 acquire、链从哪里开始”画出来，不能只凭“用了 acquire”就认为安全。

TSO 的两条规则：

- load 不与 load 重排，store 不与 store 重排。
- store 之后的 load 可以越过 store。

## 13.7 读多写少：seqlock 的版本计数

seqlock（顺序锁）用一个版本号保护一块不是单个原子对象的数据。

版本协议：

- 写者开始写之前把版本加一，版本变成奇数。
- 写数据。
- 写完再把版本加一，版本变成偶数。
- 读者先读版本，读数据，再读版本；两次不同或第一次是奇数就重试。

读者不阻塞、不写共享状态，写者也不等读者。它适合读多写少、数据小、读操作可以重来的场景，例如时间戳、配置快照、统计计数。

版本号的读写要用 release/acquire（或配合栅栏），保证“先写数据、后写偶数版本”和“先读版本、后读数据”的顺序；只在版本前后加普通读写，编译器或处理器仍可能重排。

版本协议的两个要求：

- 写者先写数据，再写偶数版本。
- 读者先读版本，再读数据。

> **旧资料提示**：把 seqlock 的数据写成普通 `int`，只在版本号上用原子操作，在 C++ 里仍然是数据竞争。C++20 起可以用 `atomic_ref` 给普通字段加 relaxed 原子访问，或者按 Boehm 的论文逐条论证；见 [38.4 节](ch38.md)。

两个字段合起来不是原子的，读者可能读到“写了一半”的值。seqlock 的正确性建立在“发现版本变化就丢弃这次读”上，所以读操作必须能重试，不能有副作用。下面把 `x`、`y` 写成 relaxed 原子，避免 C++ 层面的数据竞争，如果它们是普通 `int`，这个程序在标准意义上有数据竞争（Boehm 的论文讨论的正是这个问题）。

**对照**：

| 写法 | 等价于哪种内存序 | 适用场景 | 不能做什么 |
|---|---|---|---|
| C++ `std::atomic` 的 `memory_order` | 逐操作指定六种内存序 | 共享内存、无锁结构 | 不会自动给非原子数据加同步 |
| C11 `atomic_load_explicit`/`atomic_store_explicit` | `memory_order_*`，另有 `atomic_thread_fence` | C 代码、C11 原子类型 | 不能直接用于 C++ 对象 |
| pthread `lock`/`unlock` | lock 相当于 acquire，unlock 相当于 release | 保护临界区 | 不提供全局总序，不能替代原子操作 |
| OpenMP `flush`；5.0 起 `atomic` 的 memory-order 子句 | `flush` 默认按 `seq_cst`；子句可写 acquire/release 等 | OpenMP 线程组内的共享数据 | GCC 15 接受 `atomic release` 这类子句；`_OPENMP` 仍是 201511，不能只看宏判断单个特性 |
| MPI RMA `MPI_Win_flush`/`MPI_Win_sync`/`MPI_Win_fence` | 建立远程写的可见性，不是 C++ 的 `memory_order` | 分布式内存的 RMA | 不能拿来给本地共享内存排序 |

## 速查

| 内存序 | 保证 | 代价与注意 |
|---|---|---|
| `relaxed` | 原子性；同一变量一条修改顺序 | 最弱；不能用来发布数据 |
| `consume` | C++26 起按 acquire 处理，已弃用 | 不要在新代码里用 |
| `acquire` | load 之后的读写不越过它 | 读端；要配对 release |
| `release` | store 之前的读写不越过它 | 写端；要配对 acquire |
| `acq_rel` | 读-改-写同时有 acquire 和 release | CAS 循环常用 |
| `seq_cst` | 所有 `seq_cst` 操作一条全局总序 | 默认值；store 最贵 |

| 项目 | 规则 |
|---|---|
| release/acquire 配对 | release store 与读到该值（或释放序列中后续值）的 acquire load 同步 |
| 没有同步 | store 不是 release，或 load 不是 acquire；load 不可能是 release |
| 释放序列 | release store 为头，后接同一变量上的 RMW 链；acquire 读到链上任意值仍同步 |
| seqlock 版本协议 | 写前加一（奇数），写后加一（偶数）；读者首尾版本一致才接受 |
| 常见错误 | 把 acquire 栅栏放在 load 前；把 release 栅栏放在数据写前；用 `volatile` 当同步 |

| 项目 | 内容 |
|---|---|
| `atomic_thread_fence(order)` | 可用 `relaxed`、`acquire`、`release`、`acq_rel`、`seq_cst` |
| release 栅栏 | 排序前面的写与后面的写；放在数据写之前无效，应放在数据写之后、release store 之前 |
| acquire 栅栏 | 排序前面的读与后面的读；放在 load 之前无效 |
| `seq_cst` 栅栏 | 同时有 acquire 和 release 语义，还进入全局总序 |
| `atomic_signal_fence` | 只排同一线程内信号处理函数与主代码；不跨线程 |

## 思考题

1. 预测：13.1 的四个线程全部用 `seq_cst`，`z == 0` 一次都不出现；如果只把两个写线程改成 `release`、两个读线程改成 `acquire`，`z == 0` 会出现吗？为什么？

   <details><summary>提示</summary>

   标准允许它出现：两个读者各自只和不同的变量同步，可以看到两个相反的世界。本机 x86-64 的 TSO 不允许 IRIW，所以这个四线程版本在 x86 上跑不出来；13.2 的 store buffer 形状能跑出来。ARM64 上两者都可能出现，13.6 解释差别。

   </details>

2. 找错：13.4 的栅栏放错位置后断言会触发；如果把 release 栅栏放在两次 store 之间、但 acquire 栅栏放在两次 load 之后，会发生什么？画出先行发生边。

   <details><summary>提示</summary>

   acquire 栅栏在两个 load 之后，它只能约束栅栏之后的访存，管不了已经过去的两个 load；第二个 load 仍可能被重排到第一个之前，读到旧值。把 acquire 栅栏挪到两个 load 之间，第二个 load 才落在栅栏之后，release 栅栏与 acquire 栅栏的同步边才能把它接上。

   </details>

3. 迁移：把 13.5 的两个消费者改成三个，释放序列还成立吗？如果生产者用 `count.store(20, relaxed)`，哪个同步边断了？

   <details><summary>提示</summary>

   释放序列本身对三个、四个消费者都成立：链的长度不改变“acquire 读到链上任意值仍与链头同步”。但示例每个消费者固定领 10 个，改成三个消费者要把领取数量调成 6、7、7 之类，保证总数正好 20、下标不重叠。生产者的 store 改成 relaxed 后，链头不再是 release store，消费者读到的值没有 release 操作可配对，生产者写的数据就没有先行发生保证。

   </details>

4. 权衡：一个读多写少的配置发布场景，用 `atomic<shared_ptr>`、release/acquire 的 `atomic<Config*>`、还是 `shared_mutex`？分别要付出什么代价？

   <details><summary>提示</summary>

   `atomic<shared_ptr>` 读写都原子，但本机 libstdc++ 15 的 `is_lock_free()` 是 `false`，内部有锁；`atomic<Config*>` 读端几乎免费，但要自己管旧配置的回收（RCU、风险指针或引用计数）；`shared_mutex` 最简单、生命周期清楚，但读者会阻塞写者，写者也会阻塞读者。按读比例、配置大小和回收能力选。

   </details>
