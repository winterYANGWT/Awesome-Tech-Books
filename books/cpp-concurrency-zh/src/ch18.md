# 第 18 章 性能：度量、可扩展性与数据布局

同一个程序，线程数翻倍，耗时未必减半，有时还会回升。两个计数器紧挨着放，多线程一跑就慢了几倍。用 `clock()` 计时，250 毫秒的等待像没发生。

三个现象分别指向三件事：可扩展性的定义、计时的协议、数据布局。下面先定义量，再定计时协议，最后把这两样用到伪共享、超额申请、矩阵形状和服务器上。

## 18.1 先定义量：加速比、效率与 Amdahl

先固定三个量：加速比 `S = T_串行 / T_并行`，效率 `E = S / p`，理想线性加速比是 `p`。

`T_串行` 必须说清是哪一种：同一台机器上单线程跑同一程序，还是最快机器上的最优串行算法。两者差别很大，不能混着比。下面一律用前者，基准和并行版在同一台机器、同一次会话里测。

{{#fig ch18/speedup}}

图里两条线在低线程数几乎重合，之后越拉越开。不是程序写错了，而是固定问题规模下，能并行的部分就那么多。

Amdahl 把这件事写成公式：串行部分占 `r`，`p` 个处理器上的加速比上限是 `1 / (r + (1-r)/p)`，再多的核也超不过 `1/r`。

| 串行比例 `r` | 核数再多也超不过 |
|---|---|
| 5% | 20× |
| 10% | 10× |
| 20% | 5× |

看第 4 步：`r` 越小上限越高，但只要 `r` 不为零，上限就是一个常数。

每组前两列是人为设定的串行比例和线程数，`ceiling` 是公式，`measured` 是实测。实测大多低于上限，`p` 较小时两者接近，测量噪声会让个别点略高。`p` 越大差得越远：线程创建、join、私有结果合并和内存带宽都没有写进公式。

实测低于上限，通常是这几笔开销：

- 线程创建和 join：每次并行都要付。
- 私有结果最后的合并：线程越多，合并点越多。
- 内存带宽不够：核在等数据，不在算。
- 任务分得不均：最慢的线程拖住全局。

Amdahl 只回答“串行部分限制了多少加速”，不回答“这段代码是算力受限还是带宽受限”。后者要 roofline 模型，先量峰值算力和带宽；本书没有标定本机的这两个峰值，只讲方法。

问题规模也会变，两种可扩展性回答不同的问题：

- **强可扩展**：问题规模固定，增加 `p` 仍保持效率。
- **弱可扩展**：问题规模随 `p` 同倍率增加，效率保持。

Gustafson 指出规模变大时串行比例可能下降，所以 HPC 还能得到很大加速比。这不推翻 Amdahl，只是换了前提。

公式还假设处理器同构、问题规模固定。今天有大小核、NUMA、功耗墙和 cgroup 配额，`p` 不再是同质常数。正文只讲趋势和数量级，绝对秒数只对“本机这一次运行”有意义。

> **旧资料提示**：旧教程用 2011 年的绝对秒数和“一核一线程”假设外推今天的结果。应在目标机器上绑核、隔离 CPU、固定频率，并注明 SMT、NUMA 和 cgroup 配额；第 40 章会讲这些前提为什么变。

`clock()` 返回进程消耗的 CPU 时间，`sleep_for` 阻塞的 250 毫秒不计入。`wall_minus_clock_ms` 就是把等待漏掉的那部分。测性能要测墙上时钟，等待锁、等待 I/O、等待其他线程的时间都是真实开销。

| 计时器 | 量的是什么 | 阻塞等待算不算 |
|---|---|---|
| `clock()`、`CLOCK_PROCESS_CPUTIME_ID` | 进程的 CPU 时间 | 不算 |
| `steady_clock`、`CLOCK_MONOTONIC` | 墙上时钟 | 算 |

> **旧资料提示**：旧教程用 `clock()` 或 `gettimeofday` 计时。`clock()` 量的是 CPU 时间；`gettimeofday` 读的是可被系统时间调整的实时钟，分辨率也不保证。C++11 起用 `steady_clock`，POSIX 用 `clock_gettime(CLOCK_MONOTONIC)`；第 40 章会讲这条经验为什么过时。

注意第 5 步和第 7 步：只取主线程时间会漏掉最慢的线程；重复 5 次取最短，比取平均更接近这台机器能给的最好情况。平均会被偶发的调度、迁移和中断拉高。

一份可复用的计时协议：

- 测墙上时钟，不测 CPU 时间；C++ 用 `steady_clock`，不用可能被系统时间调整的 `high_resolution_clock`。
- 起点用 `latch`、`barrier` 或 `MPI_Barrier` 对齐，各线程记自己的结束时间，再取全局最大值。
- 重复多次取最短，不取平均；同时保留分布，报告 p99 时不要用平均值掩盖长尾。
- 排除 I/O、初始化和第一次缺页，先预热；固定线程数，必要时绑核。
- SMT、NUMA、cgroup CPU 配额都会让同一份代码在不同环境差很多，报告时要写清。
- 测量代码自己不能有数据竞争，否则读数不可信。

六条里最容易省的是对齐和取最大：省掉它们，测出来的时间往往偏小。

计时 API 的对照：

| 目的 | C++ | pthread/POSIX | OpenMP | MPI |
|---|---|---|---|---|
| 墙上时钟 | `std::chrono::steady_clock::now()` | `clock_gettime(CLOCK_MONOTONIC, …)` | `omp_get_wtime()` | `MPI_Wtime()` |
| CPU 时间 | `std::clock()` | `clock_gettime(CLOCK_PROCESS_CPUTIME_ID, …)` | 无专用接口 | 无专用接口 |
| 分辨率 | `steady_clock::period` | `clock_getres(CLOCK_MONOTONIC, …)` | `omp_get_wtick()` | `MPI_Wtick()` |
| 屏障对齐 | `std::barrier`、`std::latch` | `pthread_barrier_wait()` | `#pragma omp barrier` | `MPI_Barrier()` |
| 取全局最大 | 自己归约 | 自己归约 | `reduction(max:…)` | `MPI_Reduce(…, MPI_MAX, …)` |

`steady_clock` 保证单调、不会被系统时间调整，但不保证跨进程或跨机器一致。`MPI_Wtime` 的时间原点是任意的，而且只保证本进程内的时间轴；多机计时仍要 Barrier 对齐、Reduce 取最大。

本机 16 个物理核、32 个逻辑线程。线程数这样定：

- CPU 密集型以“可用核数”为起点，超过逻辑线程数以后，切换和缓存失效开始占上风。
- `std::thread::hardware_concurrency()` 只给逻辑线程数提示，可能返回 0，也不看 cgroup 配额、`cpuset`、NUMA 节点和大小核。

- I/O 密集型可以超订，用更多线程填满等待；但线程太多会增加切换和内存占用，不是“越多越好”。

## 18.5 矩阵-向量乘法的三种布局

{{#fig ch18/matvec_shapes}}

`y = A·x` 按行划分：线程 `i` 算 `y` 的一段连续行，只读 `A`、`x`，只写自己的 `y`，不需要同步。按列划分会让多个线程写同一段 `y`，需要原子或私有副本。

三种形状暴露不同问题：

- `8,000,000 × 8`：`y` 很长，每个线程写一段，主要是写缺失。
- `8000 × 8000`：`y` 中等，伪共享只发生在块边界。
- `8 × 8,000,000`：`y` 只有 8 个元素，多个线程的 `y` 落在同一缓存行，伪共享最严重。

同一份 800 万元素的矩阵换成三种形状。`square` 随线程数下降，`tall_thin` 主要受内存带宽限制、线程数增加后改善有限；`short_wide` 整体反而上升：8 个 `y` 挤在一行，线程越多，行转移越频繁。

这里用 `volatile` 强制每次迭代真正写回 `y`，否则编译器会把累加留在寄存器里，伪共享就消失。数据布局是一等设计指标，下面三项都会改变缓存命中：

- 行优先还是列优先。
- 结构体数组（AOS）还是数组结构体（SOA）。
- 连续存放还是分散存放。

分块大小有两头：

- 块太小：循环和边界开销占上风。

## 18.6 服务器端性能：池化、复制、切换、锁

{{#fig ch18/server_levers}}

服务器性能有四个杠杆：

- **池化**：线程池、进程池、连接池、缓冲区池，把创建移到启动阶段。
- **减少复制**：`sendfile`、`splice`、共享内存，解析时用下标或 `string_view` 指回原缓冲区。
- **控制切换**：CPU 密集型按核数，I/O 密集型用事件循环加少量线程，或更多线程填满等待。
- **减少锁**：无共享设计、读写锁、细粒度锁；细粒度不一定更快，要量。

性能测试要同时报告三样东西：

- 吞吐：每秒处理多少请求。
- 延迟：p50 和 p99，不只用平均。

## 速查

| 量 | 定义 | 注意 |
|---|---|---|
| 加速比 | `S = T_串行 / T_并行` | `T_串行` 的定义要固定；旧资料可能把分子分母排反 |
| 效率 | `E = S / p` | 理想线性时 `E = 1`，实际低于 1 |
| Amdahl | `S ≤ 1 / (r + (1-r)/p)`，上限 `1/r` | 假设规模固定、处理器同构 |
| 强可扩展 | 规模不变，增加 `p` 仍保持效率 | 回答“这台机器能扩到多大” |
| 弱可扩展 | 规模随 `p` 同倍率增加，效率保持 | 回答“规模变大时能不能跟着扩” |
| roofline | 算力上限与带宽上限取小 | 需要先量出峰值算力和带宽，本书没有标定本机的数值 |

| 检查项 | 做法 | 不这么做会怎样 |
|---|---|---|
| 时钟 | `steady_clock`、`CLOCK_MONOTONIC`、`omp_get_wtime`、`MPI_Wtime` | `clock()` 漏掉阻塞等待，`high_resolution_clock` 可能被调时 |
| 起点 | `latch`、`barrier`、`MPI_Barrier` 对齐 | 早启动的线程把慢线程的开销藏起来 |
| 终点 | 各线程记自己的结束时间，取全局最大 | 只取主线程会漏掉最慢的线程 |
| 重复 | 多次取最短，保留分布和 p99 | 平均被调度和中断拉高 |
| 环境 | 预热、绑核、固定线程数，注明 SMT/NUMA/cgroup | 同一份代码换台机器结论就变 |
| 正确性 | 计时代码自己不能有数据竞争 | 读数不可信，优化方向也会错 |

| 修法 | 做法 | 适用与注意 |
|---|---|---|
| padding | `alignas(hardware_destructive_interference_size)` 或手工填充 | 多线程各写各的字段；代价是占内存 |
| 本地累加 | 每线程先累加私有副本，最后合并 | 高频计数、归约；合并仍要同步 |
| 分块 | 把矩阵切成能放进缓存的子块 | 块太小循环开销大，太大装不进缓存 |
| SOA/AOS | 按访问模式选数组结构体或结构体数组 | 单线程连续访问用 AOS，按字段批量处理用 SOA |
| 读写分离 | 只读数据与频繁写的数据分开放 | 避免写操作让只读行失效 |

## 思考题

1. 一个程序 90% 可并行，`p=8` 时 Amdahl 上限是多少？实测只有 4×，可能是哪些开销造成的？

   <details><summary>提示</summary>

   上限是 `1 / (0.1 + 0.9/8) ≈ 4.7`。实测 4× 说明除了那 10% 串行段，还有线程创建、join、私有结果合并、内存带宽和负载不均。把 `p` 从 1 加到 8 重跑 `18_1_amdahl.cpp`，看 `measured` 和 `ceiling` 的差距怎么变。

   </details>

2. 18.2 的 `18_2_unsynced_timing.cpp` 在主线程读工作线程的结果，为什么 TSan 报竞争？如果把结果改成 `std::atomic<long long>`，读数就可信了吗？

   <details><summary>提示</summary>

   主线程的读和工作线程的写之间没有先行发生关系，非原子对象就是数据竞争。改成 `atomic` 只保证单次读写原子化，读到的仍可能是计算到一半的值；要拿到最终结果，仍要 `join` 或用 `latch` 建立同步。

   </details>

3. 18.3 的伪共享修法用到第 14 章的分桶表，桶数和缓存行怎么对齐？桶锁和桶数据放同一行会怎样？

   <details><summary>提示</summary>

   每个桶的锁和数据整体按缓存行对齐，桶与桶之间留出至少一条缓存行的间距；桶数取 2 的幂时，可以用哈希值低位选桶。桶锁和桶数据同一行时，一个线程改数据会让另一个线程的锁失效，锁竞争和伪共享叠在一起。

   </details>

4. 一台 32 逻辑线程、cgroup 限制 4 核的容器里，线程池开多少线程？CPU 密集型和 I/O 密集型分别怎么定？

   <details><summary>提示</summary>

   CPU 密集型按 4 核起步，通常 4 到 8 个线程，再用实测微调。I/O 密集型可以更多，用等待时间除以计算时间估算，但要受内存、fd 和下游容量限制；`hardware_concurrency()` 报 32，不能直接拿来开池。

   </details>
