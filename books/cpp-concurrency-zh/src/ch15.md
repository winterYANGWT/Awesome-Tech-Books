# 第 15 章 无锁数据结构与进展保证

一个栈用 `atomic_flag` 自旋锁保护，函数里没有一次 `mutex` 调用，它却仍然只允许一个线程进入。另一个 CAS 循环的 `push` 看上去每次都能成功，某个线程却可能一直重试；`pop` 的 CAS 写对了，节点释放的时机仍然能把程序打崩。

## 15.1 非阻塞不等于无锁：三层进展保证

{{#fig ch15/progress_ladder}}

三档保证的区别在“其他线程在干什么”：

- **无阻碍**（obstruction-free）：其他线程都停住时，当前线程能在有限步内完成。它最弱，常用来描述“还没真正无锁”的实现。
- **无锁**（lock-free）：多个线程并发操作时，至少有一个能在有限步内完成；某个线程被挂起，其他线程不必等它。
- **无等待**（wait-free）：不管其他线程怎么运行，每个线程都能在自己的有限步内完成。

理想化的无等待队列给每个线程预留一个槽，入队和出队都只写自己的槽，不用 CAS。真实实现要处理槽满、槽空和回收，代价并不小，所以本章的多数结构都不是无等待。

无锁也不保证公平：某个线程可能一直抢不到 `head`，但至少有一个线程在推进。工程上关心的是最坏等待时间，而不是“平均很快”。

- CAS 重试循环是无锁的典型实现：失败就重读再试，重试次数没有上限，个别线程可能一直失败，所以它是无锁，不是无等待。
- 无锁只保证系统整体有进展，不保证某个线程不被饿死。
- 自旋锁没有任何阻塞调用，但同一时刻只允许一个线程进入；持锁者被挂起时，其他线程只能在原地转。它只是“没有阻塞调用”，不是无锁结构，也不要把“没有 `mutex`”当成“无锁”。

- 8 个线程各 push 10 万个节点，最后遍历到 80 万个，值的和也等于闭式解，说明没有丢节点。
- 看第 4 步：B 的 CAS 失败，但失败不是错误。

`compare_exchange` 失败时把 `head` 当时的值写回 `expected`，成功时 `expected` 不变；这里的 `expected` 就是 `new_node->next`，下一轮循环直接用新的 `node->next` 重试，不必再 `load` 一次。这就是 [12.2 节](ch12.md) 讲的 expected 回写语义。

几个细节：

- `compare_exchange_weak` 允许伪失败：值明明相等也返回 `false`。放在循环里，伪失败只多跑一轮，不会破坏正确性；只尝试一次时用 `compare_exchange_strong`。
- `head` 要显式初始化。C++20 起 `std::atomic<T>` 的默认构造会值初始化，C++17 及以前自动存储期的对象不写初值；写 `{nullptr}` 更清楚。
- push 是无锁的：CAS 真正失败，说明 `head` 已经被别的线程改过，至少有一个线程在推进；伪失败只是这一轮没成。
- 它不是无等待的：某个线程可能一直碰上失败，重试次数没有上限。
- 新节点的 `next` 在发布前只由本线程写；CAS 成功时的 release 语义把节点和它的数据一起发布。15.6 再逐操作放宽。

push 的线性化点就是那次成功的 CAS：在它之前，节点只属于本线程；在它之后，所有线程都能从 `head` 走到这个节点。失败者的重试不改变线性化点，只改变谁先到达它。

push 不会遇到 ABA：它只把 `head` 换成一个新地址，新节点在发布前不会被别人看见，也不依赖旧 `head->next` 的内容。ABA 是 pop 的问题。

返回 `std::shared_ptr<T>` 可以把“取数据”和“删节点”解耦：弹出时把数据移进 `shared_ptr`，节点本身仍然泄露，但数据不会悬空。代价是每次弹出多一层引用计数。它没有解决节点回收，只解决了数据生命周期。

如果数据本身很小、节点很多，`shared_ptr` 的引用计数可能比数据还贵。这时要么接受泄露，要么直接上第 16 章的回收方案，不要指望 `shared_ptr` 顺手把节点也管了。

ABA 也会在这里出现：如果节点被复用，`head` 从 A 变成 B 又变回 A，CAS 仍会成功，但它基于的 `next` 已经失效（15.5 节）。判断一个无锁 pop 能不能用，先问三个问题：

1. 节点什么时候归还？
2. 谁来归还？
3. 归还前还有谁可能读它？

回答不了这三个问题，就还没有解决回收。第 16 章专门处理它。


- 生产者写 100 万个 `uint64_t`，消费者求和，校验和等于 `0+1+…+999999` 的闭式解。

下标的内存序可以分开看：

| 操作 | 内存序 | 理由 |
|---|---|---|
| 生产者读自己的 `tail` | `relaxed` | 只有生产者写它，读回自己写的值 |
| 生产者读消费者的 `head` | `acquire` | 确认槽已经被读完，才能覆盖 |
| 生产者发布 `tail` | `release` | 把“槽已写好”和槽里的数据一起发布 |
| 消费者读自己的 `head` | `relaxed` | 只有消费者写它 |
| 消费者读生产者的 `tail` | `acquire` | 看到 `tail` 才能读槽 |
| 消费者发布 `head` | `release` | 把“槽已读完”告诉生产者 |

跨线程的那一条边必须是 release/acquire，两个下标各自占一条缓存行，避免 `head`/`tail` 互相拖慢。槽里的数据按缓存行对齐也能减少伪共享（[第 18 章](ch18.md)）。SPSC 不需要 CAS，因为没有两个生产者同时改 `tail`。

生产者读 `head` 用 acquire，不只是为了“看到最新值”，更是为了确保消费者对槽的读已经完成，生产者才能覆盖它。消费者读 `tail` 用 acquire，同理。

把两个下标都改成 `relaxed`，槽里的数据是非原子类型，ThreadSanitizer 立刻报数据竞争：


```text

```

- 报告把 `push()` 里写槽和 `pop()` 里读槽配成一对竞争访问。
- release/acquire 不是装饰：少了它，生产者写槽和消费者读槽之间没有先行发生关系。

容量和缓存行也有取舍：

- 容量为 N 的环要区分“空”和“满”：留一个空槽最简单，`tail - head == N - 1` 就是满，最多放 N-1 个元素。
- 也可以用额外的原子计数，代价是每次操作多一次原子读；容量太大浪费缓存，太小让生产者频繁空转。
- 槽里的数据如果很大，按缓存行对齐可以减少一次写碰到两条缓存行。
- 生产者和消费者速度差很大时，纯空转会浪费 CPU；可以睡在 `std::atomic::wait` 或信号量上。

- 线程 1 读到 A 后被停住，线程 2 弹出 A 和 B、释放它们，又分配到地址相同的 A' 压回去。
- 线程 1 的 CAS 只比较地址，看到“还是 A”，于是成功，但它记下的 `next` 已经失效。
- 第 5 步的 CAS 成功，不是因为数据值相等，而是因为地址还是 X；地址相同、历史不同（第 6 步）才是 ABA。

ABA 不只出现在栈上：任何“先读指针、再 CAS 指针”的结构都可能碰上。只要节点会被回收或复用，就要把版本计数、延迟回收或风险指针纳入设计。


- 高 16 位放 tag，低 48 位放地址，每一次弹出、压入都让 tag 加一。
- CAS 比较的是整个 64 位字，地址相同但 tag 不同就会失败并重试。
- 空指针也可以带非零 tag，判断栈空要看指针部分，不能直接和 0 比。

这个写法依赖本机 x86-64（4 级页表）的用户态地址不超过 48 位；换平台或换用 5 级页表要先确认指针位宽。更通用的做法是 `std::atomic<counted_node_ptr>`，结构体是 16 字节，是否无锁取决于平台（[12.6 节](ch12.md)），本机 GCC 15 上不是无锁，Clang 21 加 `-mcx16` 才是。

多生产者会同时改 `tail`：先写数据，再挂 `next`，再换 `tail`，中间任何一步失败，其他线程都可能看到半完成状态。常见做法是给 `tail` 加计数、把 `next` 改成原子变量，失败者替成功者把 `next` 和 `tail` 补上，这叫帮助（helping）；它把“忙等”变成“合作”，CAS 失败的线程不再空转，而是执行未完成的那一步。

MPSC 可以拆成两步：生产者先用 `fetch_add` 占一个位置，再写槽并置就绪标志；消费者只读就绪标志为真的槽。占位成功但写入失败的线程要把位置补完，否则消费者会永远等下去，这就是帮助机制要解决的问题。

- **写多生产者队列时还有两个坑**：
  - 有的多生产者 push 在解引用 `old_tail` 时没有保护，另一个线程可能已经回收了该节点；这个版本只能当反例。
  - 帮助机制提高进展，但代码复杂，只在热路径上值得做。工程上常先用 SPSC 或带锁的 `std::deque`。

- push 的 CAS 用 release、失败路径 relaxed。
- pop 每轮用 acquire 读 `head`，摘链 CAS 用 acquire、失败路径 relaxed。
- pop 失败后重新 `load`，不拿失败回写的 `old` 去读 `next`：如果失败路径是 relaxed，回写的 `old` 没有 acquire 语义，紧接着读 `old->next` 就可能读到没发布的数据。

`pop` 里读 `next` 只是一次普通指针读，没有内存序可设：节点和它的 `next` 已经由 `head` 的 acquire 建立先行发生关系。若把 `next` 改成原子变量、且要跨过它获取另一个线程发布的数据，那个 load 才需要 acquire。

放宽不是“把 `seq_cst` 全换成 `relaxed`”，release 写必须有人 acquire 读，否则数据没有发布。失败路径通常可以 relaxed，因为它不发布新数据，只是重读。前提是后续不再用失败回写的旧值去解引用。

ThreadSanitizer 能查数据竞争，但不能证明 relaxed 程序的内存序正确，它只覆盖实际执行到的路径。要证明，需要模型检查器（CDSChecker、GenMC 等，能处理的语言特性有限，用之前看它的文档）或完整的形式化论证。每次放宽后都要重跑压力测试和 TSan，确认实际执行到的路径没有变化。

同一件事在其他接口里的写法：

| 结构或操作 | C++ | C11 | OpenMP | 限制 |
|---|---|---|---|---|
| 原子指针 | `std::atomic<T*>` | `_Atomic(T*)` | 无对应类型 | OpenMP 没有原子指针类型 |
| CAS 循环 | `compare_exchange_weak` | `atomic_compare_exchange_weak` | 5.2 才有 `compare` 子句 | 4.5/5.1 没有；5.2 也只覆盖条件更新形式 |
| 自旋锁 | `atomic_flag` + acquire/release | `atomic_flag` + `atomic_flag_test_and_set` | 4.5/5.1 无 test-and-set | OpenMP 5.2 才加 `compare`；pthread 只能用锁或信号量 |
| 内核态 | 用户态用 C11/C++ 原子或 `__atomic_*` 内建 | 同左 | 同左 | Linux 内核有 `cmpxchg`、`atomic_t`、RCU，用户态不能直接用 |

> **旧资料提示**：把 CAS 循环说成“无等待”。CAS 循环是无锁，不是无等待；无等待要求每个线程都有界步数。见 [第 38 章](ch38.md)。

> **旧资料提示**：用 Concurrency TS 的 `atomic_shared_ptr` 做回收。C++20 的标准对应物是 `std::atomic<std::shared_ptr<T>>`，且不保证无锁。见 [38.6 节](ch38.md)。

> **旧资料提示**：指望标准 GC 解决节点回收。C++23 移除了标准 GC 支持（P2186R2），无锁回收仍要风险指针、引用计数或 RCU。见 [38.8 节](ch38.md)。

## 速查

| 保证 | 定义 | 例子 | 某个线程被挂起时 |
|---|---|---|---|
| 无阻碍 | 其他线程都停住时，当前线程能在有限步内完成 | 没有竞争的 CAS 循环 | 其他线程停住才能保证完成 |
| 无锁 | 并发时至少有一个线程能在有限步内完成 | Treiber push | 至少有一个线程能推进 |
| 无等待 | 每个线程都能在自己的有限步内完成 | 理想化无等待队列 | 每个线程都有界完成 |

非阻塞（non-blocking）是这三档的统称，不是第四档保证；自旋锁只是没有阻塞调用，不在三档里。

| 操作 | 步骤 | 内存序 | 回收风险 |
|---|---|---|---|
| push | 建节点 → `next = head` → CAS 换 `head` | 成功 release，失败 relaxed | 节点发布后不能提前释放 |
| pop | 读 `head` → 读 `next` → CAS 换 `head` | 读 `head` acquire，CAS 成功 acquire，失败 relaxed 后重读 | 读 `next` 后、CAS 前，`old_head` 可能被释放；节点复用还会 ABA |
| 回收 | 延迟释放，确认没有读者 | 与发布/读取配对 | 不解决回收就会泄漏；过早释放就是 UAF |

| 问题 | 写法 | 注意 |
|---|---|---|
| 空/满 | `head == tail` 为空；`tail - head == N-1` 为满 | 留一个空槽，最多 N-1 个元素 |
| 生产者发布 | release store `tail` | 消费者必须 acquire load `tail` |
| 消费者归还 | release store `head` | 生产者必须 acquire load `head` |
| 自己的下标 | relaxed load | 只读自己写的值 |
| 缓存行 | `alignas(64)` 分开 `head`/`tail` | 槽里的数据也可按缓存行对齐 |

   push 的 release 是发布方：它把新节点和 `data` 一起交给读方。改成 relaxed 后，pop 的 acquire 再强也读不到“发布”之前的写，因为 release 那一半没了。反过来，push 用 release、pop 用 relaxed，则读方不建立先行发生关系，同样可能读到旧数据。

   </details>

2. 15.3 的 pop 在读 `next` 后、CAS 前被挂起，另一个线程弹出并释放了 `old_head`；如果节点不释放、只泄露，程序还会不会错？如果节点被复用呢？

   <details><summary>提示</summary>

   只泄露不会 UAF：节点一直有效，读 `next` 和 CAS 都不会踩到已释放内存，程序能跑完，代价是内存一直涨。节点被复用就不同：地址可能相同、内容已经换了，CAS 可能误成功，这就是 ABA；15.5 的两个例子分别演示了误成功和加 tag 后失败重试。

   </details>

3. 把 15.4 的 SPSC 环改成 MPSC（多生产者、单消费者），哪些下标需要 CAS？哪些可以用 `fetch_add`？需要帮助机制吗？

   <details><summary>提示</summary>

   消费者仍然只改 `head`，可以用普通的 release store。多个生产者抢同一个 `tail`，要么用 CAS 自己算新位置，要么用 `fetch_add` 先占一个位置再写槽；后者要处理“占位成功但写入失败”的半完成状态，通常需要帮助或每个槽一个就绪标志。只改 `tail` 的 CAS 不够，还要保证消费者不会读到只写了一半的槽。

   </details>

4. 一个读多写少的配置表，用无锁 `atomic<shared_ptr<Config>>`、`shared_mutex`、还是 RCU？三者的回收延迟和读开销各是什么量级？

   <details><summary>提示</summary>

   `atomic<shared_ptr<Config>>` 读一次要多一次引用计数，且标准不保证无锁（本机 libstdc++ 15.2 不是无锁）；`shared_mutex` 读要拿共享锁，写要等读者退出；RCU 读侧几乎零开销，但旧配置要等一个宽限期才能释放，回收延迟最长。读多写少、能容忍旧配置晚一点释放时 RCU 合适；不能容忍延迟或没有 RCU 库时，`shared_mutex` 更稳。

   </details>
