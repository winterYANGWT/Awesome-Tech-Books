# 第 34 章 事件库的内部结构：Libevent，以及 Asio、libuv 的对照

`kvd_loop` 越改越像 Libevent：注册队列、活动队列、时间堆、唤醒 fd 一个不少。换用现成的事件库，工作线程里 `event_add` 偶发崩溃；`fork` 出来的子进程事件循环也不工作。

两个故障都不是 API 拼错，而是漏了库的前置条件。这一章从 Libevent 的五组件和后端函数表讲起，再对照 Asio 和 libuv 的代码形状。

## 34.1 事件库替你做了什么：五组件与后端函数表

{{#fig ch34/reactor_components}}

自己写的 Reactor 里，`epoll` 的 fd、回调、定时器和唤醒管道是散的；Libevent 把它们收进五个角色。图里的对应关系可以直接背成一张表。

| 组件 | Libevent 里的东西 | 职责 |
|---|---|---|
| 句柄 | `ev_fd` | fd 或信号值，内核通过它报告就绪 |
| 事件多路分发器 | `eventop` + `evmap` | 把 `select`/`poll`/`epoll_wait` 封成同一套 `add`/`del`/`dispatch` |
| 事件处理器 | `event` | 描述“关心哪个 fd 的什么事件、超时多久、回调是谁” |
| 具体事件处理器 | 用户写的回调 | 真正的业务逻辑 |
| Reactor | `event_base` | 持有后端、队列、时间堆，驱动整个循环 |

这五个角色不是 Libevent 的发明，而是 Reactor 的通用分层：换一个库，名字会变，句柄、分发器、处理器和循环的边界不会变。看懂这层映射，读 epoll 或 Asio 的代码时就知道每一段在补哪个洞。

{{#fig ch34/eventop_backends}}

`eventop` 是后端函数表：`name`、`init`、`add`、`del`、`dispatch`、`dealloc`、`need_reinit`、`features`、`fdinfo_len`。上层只调这些函数指针，不关心底下是 epoll 还是 kqueue。

`features` 是能力位，不是性能分数：
- `EV_FEATURE_ET`：后端支持 `EV_ET` 边沿触发。
- `EV_FEATURE_O1`：单个事件触发近似 O(1)，`select`/`poll` 是 O(n)。
- `EV_FEATURE_FDS`：后端能收普通文件，不只 socket；epoll 没有这一位。

后端按 `eventops[]` 的顺序选第一个可用的：Linux 上 epoll 在前，BSD/macOS 用 kqueue，Windows 用 IOCP 或 select。本机 `event_base_get_method()` 返回 `epoll`，`event_base_get_features()` 报 `ET|O1`；epoll 不收普通文件，所以没有 `FDS`。

看 hello 的输出时，注意三件事：
- 定时器和信号都在同一个 base 里。
- 信号回调只调 `loopexit`，不直接结束进程。
- 空 base 的 `dispatch` 返回 1。

`1 timer` 在 `2 SIGINT` 前面：定时器回调里 `raise(SIGINT)`，信号处理函数只往 socketpair 写一个字节，信号事件要到下一次 dispatch 迭代才处理，仍在同一次 `event_base_dispatch` 调用内。

`dispatch` 返回 0 表示被 `loopexit` 正常结束，`got_exit=1` 说明退出原因；空 base 的 `dispatch` 返回 1，表示没有 pending 或 active 事件。

- 事件循环的三种结束方式：没有事件时返回 1、`loopexit`、`loopbreak`。
- `dispatch` 返回 1：没有 pending 或 active 事件。
- `loopexit`：跑完当前这轮后退出，可以延迟到指定时间。
- `loopbreak`：当前事件处理完立即退出。

循环每轮先算 `dispatch` 的超时：有活动事件时置 0，否则取时间堆堆顶；没有事件也没有活动回调时返回 1。`EVLOOP_ONCE` 只跑一轮，`EVLOOP_NONBLOCK` 不阻塞。

`event_base` 里能数出这些成员：
- 选中的后端和私有数据、事件变更缓冲 `changelist`、信号后端 `evsig_info`。
- 按优先级分组的活动队列、通用定时器队列、时间堆。
- fd/信号映射 `evmap`、注册队列、唤醒 socketpair。
- 线程锁、条件变量，以及当前正在执行的事件。

> **旧资料提示**：旧教程把事件源等同于 `select`/`poll`/`epoll`。`signalfd`、`timerfd`、`eventfd`、`pidfd` 也是 fd 事件源；Libevent 2.1.12 的代码里有 `eventfd`/`timerfd` 支持，但没有用 `io_uring`（Linux 5.1），见 [42.5 节](ch42.md)。

## 34.2 Libevent 的对象模型：event、event_base、evmap 与时间堆

{{#fig ch34/event_lifecycle}}

`event_new(base, fd, events, cb, arg)` 创建一个事件；`evtimer_new` 是 `event_new(base, -1, 0, ...)` 的包装，`evsignal_new` 自带 `EV_SIGNAL | EV_PERSIST`。事件类型可以或 `EV_READ`、`EV_WRITE`、`EV_TIMEOUT`、`EV_SIGNAL`、`EV_PERSIST`、`EV_ET`。

| 事件类型 | 含义 | 注意 |
|---|---|---|
| `EV_TIMEOUT` | 超时 | 回调的 `what` 里有这一位 |
| `EV_READ` | 可读 | 监听 fd 上也表示有新连接 |
| `EV_WRITE` | 可写 | 一直关注会空转，按需加 |
| `EV_SIGNAL` | 信号 | `fd` 是信号值，不是 fd |
| `EV_PERSIST` | 触发后自动重加 | 定时器的 `tv` 变成重复间隔 |
| `EV_ET` | 边沿触发 | 需要后端支持，fd 要非阻塞 |

`EV_ET` 只在支持边沿触发的后端上有意义；后端不支持时不会按边沿触发工作。`EV_FINALIZE` 和 `EV_CLOSED` 是 2.1 才有的扩展，前者给多线程关闭用，后者要求后端支持 `EV_FEATURE_EARLY_CLOSE`。

服务端和两个客户端都在同一个 base 里：监听 fd 用 `EV_READ | EV_PERSIST` 接受连接，连接 fd 用 `EV_READ | EV_PERSIST` 回射。输出里 `served=2`、`echoed=18` 对应两条连接各 9 字节，`loop: rc=0` 说明两个客户端都读回后由 `loopexit` 结束。

- 监听 fd 和连接 fd 用的是同一套 `event` API。
- 回射是逐字节的，不解析请求边界。
- 两个客户端由同一个循环推进，没有第二个线程。

`evmap` 按 fd/信号聚合：同一个 fd 上可以挂多个 `event`，读计数或写计数第一次从 0 变 1 时才调用后端的 `add`。`event_new` 的最后一个参数（内部存在 `evcb_arg`）让回调找到自己的连接对象；示例里这个 `arg` 就指向 `struct Conn`。

同一个 fd 上的读和写可以分开注册，`evmap` 用 `nread`/`nwrite` 计数决定何时调用后端的 `add`/`del`；最后一个读事件删掉时，才把读兴趣从 epoll 摘掉。

事件的四个动作可以按生命周期记：
- `event_new`：分配并绑定 base、fd、回调和 `arg`。
- `event_add`：进注册队列，有超时再进时间堆。
- `event_del`：从注册队列、活动队列和时间堆里摘掉。
- `event_free`：释放对象；base 不替你释放。

`event_add(ev, tv)` 的 `tv` 为 `NULL` 表示不设超时；`EV_PERSIST` 触发后自动重新加入，非持久事件要自己再 `event_add`。

`event_del` 取消，`event_free` 释放；`event_base_free` 只释放 base，不释放每个 `event`，顺序反了就是泄漏。

`event_add` 的两个细节：
- 定时器是相对时间，进堆时换成绝对时间。
- 删除事件会同时从注册队列、活动队列和时间堆摘掉。

`tv` 是相对时间，`event_add` 把它换算成绝对超时塞进最小堆，堆顶就是下一次 `dispatch` 的超时上限。

非持久事件触发一次就从注册队列消失；要持续读，要么加 `EV_PERSIST`，要么在回调末尾再 `event_add`。`EV_PERSIST` 定时器的 `tv` 是重复间隔，不是一次性截止时间。

`event_base_once` 是一次性投递的快捷方式：不用自己准备 `event`，回调后内部对象自动释放。它适合从工作线程把一小段逻辑扔回循环线程，不适合高频路径。

> **旧资料提示**：旧教程按 Libevent 2.0.19 的字段逐个讲 `event` 和 `event_base`。2.1.12 的字段已经变过，要学的是“注册队列 + 活动队列 + 时间堆 + 唤醒 fd”的分层，不是结构体布局；逐字段分析见 [42.7 节](ch42.md)。

## 34.3 线程安全与 fork：evthread、event_reinit

Libevent 默认不是线程安全的。`evthread_use_pthreads()` 必须在创建任何 `event_base` 之前调用，并链接 `-levent_pthreads`；本机 2.1.12 返回 0。

TSan 报的是 `counter`，不是 Libevent 内部。库本身没有插桩，TSan 看不到库内部的数据访问，但仍能通过 pthread 拦截器看到锁的获取和释放，所以报告只落在我们自己的普通 `int` 上。`event_add` 从工作线程调用是安全的，前提是已经启用 evthread，不启用时连 `event_add` 本身都可能崩溃。

启用 evthread 后，这些入口才可以从其他线程调：
- `event_add` / `event_del`。
- `event_active`。
- `event_base_once`。

{{#fig ch34/libevent_threads}}

库的锁保护的是 base 的变更队列、活动队列和唤醒 fd，不保护你的计数器。回调只在循环线程里跑，工作线程只负责投递；共享数据仍要自己加锁或用原子。

库的锁不会延伸到回调里的业务对象：两个工作线程同时改一个 `std::map`，仍然要自己加锁；回调在循环线程里串行，也不等于回调里的操作天然线程安全。

线程支持打开后，`event_base_dispatch` 仍只能在一个线程里跑；工作线程可以投递，但不能自己再进同一个 base 的循环。要多个循环就建多个 base，每个线程一个。

输出里两条路径的 `reads` 不同：调用 `event_reinit` 时子进程读到 1 字节；不调用时子进程的 ET 读事件一次都没触发。

原因是父子共享同一个 epoll 实例，父进程在 300 ms 内先把它取走了；子进程的 `event_reinit=0` 表示后端重建成功。

- 调用 `event_reinit` 时子进程读到 1 字节。
- 不调用时子进程的 `reads=0`。

`event_reinit` 会关闭旧的信号 socketpair、重新初始化后端、把已有事件重新注册；返回 0 表示全部重加成功。父子共享同一个 epoll 实例时，一边 `epoll_wait` 取走的就绪项，另一边看不到。

epoll 后端在 `fork` 后的行为：
- 子进程继承 epoll fd，兴趣表也共享。
- 父进程取走 ET 边沿后，子进程看不到。
- `event_reinit` 新建实例，再把已有事件重加。

`fork` 之后的安全写法：
- 只让子进程 `exec`，不碰父进程的 base。
- 子进程要跑循环，先 `event_reinit(base)`，再注册自己的事件。
- 多线程程序 `fork` 后只有调用线程存在，子进程尽量只调用 async-signal-safe 函数再 `exec`。

`event_base_loopbreak` 处理完当前事件就返回，`event_base_loopexit` 可以延迟到指定时间；退出原因看 `event_base_got_break` 和 `event_base_got_exit`。`event_base_dispatch` 相当于 `event_base_loop(base, 0)`，每个 base 同时只允许一个循环，重入返回 -1。

退出码不要和退出原因混在一起：`dispatch`/`loop` 返回 0 只表示正常结束，`got_break`/`got_exit` 才说明是哪种；返回 1 表示事件已经跑完。

> **旧资料提示**：旧教程写“Libevent 是线程安全的”，还常用依赖全局 `current_base` 的 `event_init()`。前者要先 `evthread_use_pthreads()` 并链接 `-levent_pthreads`，而且只保护 base 内部；后者只适合 1.x 单线程写法，新代码用 `event_base_new()`。见 [42.7 节](ch42.md)。

## 34.4 三种风格对照：Libevent、Asio、libuv

Libevent 是 C 接口，核心是 `event`/`event_base`，附件有 `bufferevent`、HTTP、DNS；跨平台后端，线程支持要显式启用。

Asio 的 handler 队列没有内建上限，`post` 得太多同样会把内存吃光；要背压得自己在业务层做，比如限制在途请求数、暂停读。

| 事件库 | 语言 | 循环对象 | 定时器 | 信号 | 线程模型 | 协程 | 本机验证 |
|---|---|---|---|---|---|---|---|
| Libevent | C | `event_base` | `evtimer_new` + 时间堆 | `evsignal_new` | 显式 `evthread_use_pthreads()`，回调在循环线程 | C 无；C++ 可自己包 | 2.1.12 编译运行 |
| Asio | C++ | `io_context` | `steady_timer` | `signal_set` | `io_context` 多线程 + strand | C++20 `co_spawn` + `awaitable` | Boost 1.90 编译运行 |
| libuv | C | `uv_loop_t` | `uv_timer_t` | `uv_signal_t` | 单循环线程 + 线程池 | 无，C 回调接口 | 本机未安装，未编译 |

strand 保证的是“同一个连接的回调不并发”，不是“所有连接串行”：
- 不同连接可以落在不同线程。
- 同一连接的读、写、关闭按提交顺序执行。
- `Store` 仍要自己处理多线程，桶锁不能省。

libuv 本机没有安装：`pkg-config` 查不到 `libuv`，也没有 `uv.h`，所以只做对照，不编译。Asio 有 `thread_pool`，但它只是一个执行任务的线程池，不替你限制队列和做背压；Libevent 和 libuv 不提供业务线程池。

libuv 的 `uv_loop_t` 跑一个循环，`uv_tcp_t`、`uv_timer_t`、`uv_signal_t` 都是句柄；它自带线程池处理 DNS 和文件系统这类阻塞操作，但业务回调仍在循环线程。

三者都只提供“就绪/完成通知”，不解析协议。选型看约束：语言与类型安全、协程支持、跨平台、HTTP/DNS 等附件、调试与社区；不要只看基准数字。

- Asio 的 `signal_set` 把 SIGTERM/SIGINT 变成完成事件，处理函数里停 `io_context`，acceptor 随 `Server` 析构关闭；这相当于 Libevent 的 `evsignal_new` 加 `loopexit`。
- 已有大量 C 代码、要 HTTP：Libevent 的 `evhttp` 最省胶水。
- 新 C++ 项目、要协程和类型安全：Asio，HTTP 用 Boost.Beast。
- 要跨平台、和 Node.js 生态一致：libuv，但 HTTP 附件要自己找。

`BEV_OPT_CLOSE_ON_FREE` 让 `bufferevent_free` 顺带关 fd；`BEV_OPT_DEFER_CALLBACKS` 把回调推迟到事件循环的安全点，降低回调里释放对象时踩栈的风险。

回调拿到 `shared_ptr` 后，即使服务器表里删掉连接，对象也活到回调返回；`bufferevent_free` 只是把 fd 和缓冲还给库。Asio 的 handler 捕获 `self` 也是同一目的。

Asio 的连接生命周期靠 `self` 和 strand：
- handler 捕获 `self`，连接对象不会提前析构。
- 同一个连接的 handler 在 strand 上串行。
- 不同连接可以并行。

Asio 版用 `async_read_until` 读一行、`async_write` 写回；每个连接一个 strand，`io_context` 跑两个线程，连接状态只在 strand 里改。

- 本机这一轮：Libevent 版吞吐更高、P99 更低。
- 差别有一部分来自实现：Asio 版每读一行一次 `async_read_until`，每行都走一遍 strand 调度；Libevent 版把输入攒在 `bufferevent` 里批量解析。不能把这次数字当成两个库的通用排名。
- 回环、单机、8 条连接、流水线 4 只覆盖一种形状；连接数、请求大小、写比例一变，排序可能变。要选型就在自己的流量模型下测，不要拿这里的数字当结论。
- `Store` 每个桶一把 `shared_mutex`，`Parser` 是逐字节状态机；这两个文件一行没改，换的只有 accept、读、写和关闭。

`--port-file` 的写法两个版本一致：先 bind 端口 0，拿 `getsockname`/`local_endpoint` 得到实际端口，再写临时文件、`rename`。客户端只读一次，不会读到半个端口号。

两个服务器都忽略 `SIGPIPE`；发送失败时检查错误码并关闭连接，避免对端先关时进程被信号杀掉。

事件库不改变协议和存储的复杂度：`Store` 的桶锁竞争、`Parser` 的逐字节拷贝、每行一次 `std::string` 分配，仍然是瓶颈。换库只改 I/O 层，不会让这两个瓶颈消失。

## 速查

| 接口或写法 | 作用 | 线程/fork 注意 |
|---|---|---|
| `event_base_new` | 新建一个 Reactor | 每线程一个 base，或一个循环线程 |
| `event_base_free` | 释放 base | 不释放每个 `event`；先 `event_free` |
| `event_base_dispatch` | 跑循环 | 相当于 `event_base_loop(base, 0)` |
| `event_base_loop` | 带 flags 的循环 | 每个 base 同时只允许一个循环，重入 -1 |

| `event_base_loopbreak` | 处理完当前事件就退出 | `got_break` 查原因 |
| `event_new` | 创建事件 | `arg` 在回调里取回 |
| `event_add` | 注册事件和超时 | `tv` 为 `NULL` 表示不设超时 |
| `event_del` | 取消事件 | 回调里删自己要小心生命周期 |
| `event_free` | 释放事件 | 会先 `event_del` |
| `evtimer_new` | 一次性定时器 | 是 `event_new(base, -1, 0, ...)` 的包装 |
| `evsignal_new` | 信号事件 | 自带 `EV_SIGNAL \| EV_PERSIST` |

## 思考题

1. （预测）把 34.3 的计数器改成 `std::atomic<int>`，TSan 还会报吗？如果只把 `event_add` 放进锁里、计数器仍用普通 `int`，为什么还不够？

   <details><summary>提示</summary>

   换成 `std::atomic<int>` 后 TSan 不再报这个计数器：原子的读-改-写建立了先行发生关系。只锁 `event_add` 不够，因为库的锁只覆盖 base 的内部结构，不覆盖回调和主线程对 `counter` 的访问；那两处仍是普通读写，TSan 照样报。

   </details>

2. （找错）34.5 的 Libevent 版本如果在 `bufferevent` 回调里直接 `delete` 连接对象，下一次回调会发生什么？用 `shared_from_this` 或延迟删除怎么修？

   <details><summary>提示</summary>

   回调返回后 Libevent 仍可能持有 `bufferevent` 和 `arg`，下一次读写或事件回调会用到已经释放的对象，属于释放后使用。让连接继承 `enable_shared_from_this`，回调开头取 `self`，关闭时只从服务器表里移除，等当前回调返回再让最后一个 `shared_ptr` 析构；或者把删除投递到循环的下一轮。

   </details>

3. （权衡）一个已经有大量 C 代码的团队要加 HTTP 服务，选 Libevent、Asio 还是 libuv？把“语言、协程、HTTP 附件、线程模型、调试”列成一张表再判断。

   <details><summary>提示</summary>

   先看团队能维护哪种语言：C 代码多、不想引入 C++ 生命周期，Libevent 的 `evhttp` 和 C 接口最省事；要用 C++20 协程和类型安全，Asio 更合适，但 HTTP 要自己解析或用 Boost.Beast；libuv 的强项是跨平台和 Node.js 生态，HTTP 附件不如前两者。线程模型上三者都要自己决定循环线程和 worker 的分工，调试工具也都只能看到自己的回调。

   </details>

4. （迁移）把 33 章的 `kvd_loop` 换成 Libevent 后，原来的时间堆、`signalfd`、`eventfd` 分别由库的哪个组件接管？哪些还需要自己写？

   <details><summary>提示</summary>

   时间堆由 `event_base` 的定时器队列和最小堆接管，`evtimer_new` 的 `tv` 就是入口；`signalfd` 由 `evsignal_new` 加内部信号 socketpair 接管；`eventfd` 的跨线程唤醒由 base 的唤醒 socketpair 和 `event_active`/`event_add` 接管。还需要自己写的是协议解析、连接状态、输出缓冲和背压、业务线程与共享数据的同步。

   </details>
