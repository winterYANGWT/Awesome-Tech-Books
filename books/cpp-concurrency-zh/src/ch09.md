# 第 9 章 future、promise、异步任务与超时

```cpp
int compute();
void start() {
    int result = 0;
    std::thread([&] { result = compute(); }).detach();
}  // 返回后 result 所在的栈没了
```

`detach` 的线程还在往主线程栈上的 `result` 写；主线程一返回，这块栈就没了。结果不是“算得慢”，而是没有地方放，也没有人负责等。

另一个版本用 `std::async` 递归快排，每层都开一个任务；元素一多，线程数按任务树增长，最后抛出 `std::system_error`。两个故障是同一个问题：结果放在哪、任务什么时候算、谁等它。

- `std::async(std::launch::async, …)` 通常立刻在新线程上跑。
- 主线程等 `started` 为真，证明 `get()` 之前任务已经在工作。
- `get()` 阻塞到结果就绪，然后返回值。

`wait()` 只等不取；`wait_for()` 和 `wait_until()` 带超时，返回 `future_status::ready`、`timeout` 或 `deferred`。`deferred` 只在任务还没开始、共享状态里存的是延迟函数时出现。

- 四个线程各持有一个 `shared_future` 副本，计算只发生一次。
- `get()` 返回的是只读引用，要改还得自己同步。
- 不要多个线程同时改同一个 `shared_future` 对象，通常每个线程拷一份副本。

`std::async` 的参数传递规则和 `std::thread` 类似：默认按值拷贝或移动，要传引用用 `std::ref`。不同点在返回值：`async` 直接给你一个 future。

{{#fig ch09/async_policy}}

三条路的区别：

- `launch::async`：任务通常在另一个线程执行，future 析构可能等到任务结束。
- `launch::deferred`：任务推迟到 `get()`/`wait()`，在调用线程执行；不取就一直不跑。
- 默认策略：由实现选 `async` 或 `deferred`，标准不保证选哪个。

future 的值类型可以是引用或 void，`get()` 的返回类型随之变化。

因此不要在持锁的作用域里销毁最后一个 future：任务可能正等着同一把锁，析构就会卡住。

`std::future` 没有 `then()`，也没有取消接口。C++20 的 `stop_token` 不会自动接到 `std::async` 上；要停止长任务，得把 token 传进任务，由任务自己检查。

- `future` 默认构造时没有共享状态；对无效 future 调 `get()` 是未定义行为，实现可能抛 `no_state`。
- 共享状态由生产者创建，future 只是引用它。
- `get()` 释放 future 的引用；最后一个引用消失时状态销毁。
- `share()` 把 future 转成 `shared_future`，原 future 随即失效。
- future 的移动构造不抛异常，可以安全放进容器。

## 9.3 `std::async` 的启动策略与陷阱

启动策略只有两个枚举值，默认是两者的按位或：

- `launch::async`：要求异步执行，通常新建线程。
- `launch::deferred`：推迟到第一次 `get()`/`wait()`，在调用线程执行。
- 默认 `async | deferred`：由实现选择，标准不保证选哪个。

`deferred` 不是“后台任务”。如果永远不 `get`/`wait`，它可能永远不执行。`async` 也不保证线程复用或数量控制，标准没有“线程池”承诺。

默认策略下，实现可以在“没有更多并发收益”时选 deferred；不能靠默认 `async` 保证后台执行。`future_status::deferred` 表示任务还没开始，`wait_for` 会立刻返回。

输出：


- `deferred` 在 `get()` 之前没执行。
- `get()` 时它在调用线程上跑，所以线程号和主线程相同。
- `async` 在另一个线程上跑，两者返回值相同。

递归 `std::async` 快排每层都开任务，任务数按区间数增长。元素一多，线程创建就会失败，`async` 抛 `std::system_error`。

- `cutoff` 让小于 4096 个元素的区间直接 `std::sort`，不再开任务。

{{#fig ch09/async_tree}}

看第 2–3 步：左半区开一个 `async` 任务，右半区留在当前线程。第 6 步到 cutoff 后串行。没有 cutoff 时，任务树会一直分到单个元素，任务数按元素数增长。

标准没有给 `std::async` 取消接口。长任务要用 `std::jthread` 加 `stop_token`，或者自己的线程池；future 析构在 `launch::async` 下可能等到任务结束。

`async` 抛出的异常存进 future，`get` 时重新抛出。创建线程失败则直接抛 `std::system_error`，错误条件通常是 `resource_unavailable_try_again`。

- 不保证任务马上开始，也不保证同时运行的任务数。
- 返回值可以移动进容器，但 future 本身不能拷贝。

| 设施 | 谁设值 | 能否拷贝 | 异常怎么传 | 启动策略 | 析构行为 |
|---|---|---|---|---|---|
| `std::future<T>` | 共享状态的生产者 | 否，move-only | `get()` 重新抛出 | 取决于生产者 | 释放共享状态；`async` 的最后一个 future 可能等任务 |
| `std::shared_future<T>` | 同上 | 是 | 每个副本 `get()` 都重新抛出 | 取决于生产者 | 释放自己那份引用 |
| `std::promise<T>` | `set_value`/`set_exception` | 否，move-only | 显式 `set_exception` | 无 | 未设值则 `broken_promise` |
| `std::packaged_task<R(Args...)>` | 执行 `operator()` | 否，move-only | 自动存进 shared state | 无 | 未执行则 `broken_promise` |
| `std::async` | 被调函数 | 返回的 future 不可拷贝 | 自动存进 future | `async`/`deferred`/默认 | 见 `future` 一行 |

> **旧资料提示**：认为 `std::async` 会充分利用硬件、不会超额申请，是错的。标准不保证线程复用或数量控制，`deferred` 还可能根本不执行；递归 `async` 会创建过多线程。见 [第 39 章](ch39.md)。


- 本机 libstdc++ 15 的 `high_resolution_clock` 就是 `system_clock` 的别名。
- 它的 `is_steady` 为 false，不能拿来计时。
- 要计时就用 `steady_clock`。
- `high_resolution_clock` 的节拍可能更细，但 `is_steady` 为 false 时仍然不能用于超时。

`duration` 的隐式转换只在不会截断时发生，其余要 `duration_cast`；它是截断，不是四舍五入。`time_point` 是某个时钟上的绝对时刻，`now() + duration` 得到截止点。

例如 `duration<int, milli>` 可以隐式转成 `duration<int, micro>`，反过来必须 `duration_cast`。两个不同时钟的 `time_point` 不能直接比较。`system_clock` 的 `now()` 可能倒退，不能用来算时间差。

后缀的命名规则：

- `_for` 等一段时长，参数是 `duration`。
- `_until` 等到时间点，参数是 `time_point`。
- `sleep_for`/`sleep_until`、`timed_mutex::try_lock_for/until`、`unique_lock` 的超时构造、条件变量的 `wait_for/until`、future 的 `wait_for/until` 都遵循这个命名。

用 `system_clock` 做 `wait_until` 时，校时会改变实际等待时长。跨时区、日历用 C++20 的 `zoned_time`/`year_month_day`，但超时仍用 `steady_clock`。

| 接口 | 参数 | 返回 | 用哪个时钟 |
|---|---|---|---|
| `sleep_for` | `duration` | 无 | 实现用单调时钟计时 |
| `sleep_until` | `time_point<Clock>` | 无 | 调用者给的 `Clock` |
| `timed_mutex::try_lock_for` | `duration` | bool | 实现用单调时钟 |
| `timed_mutex::try_lock_until` | `time_point<Clock>` | bool | 调用者给的 `Clock` |
| `cv.wait_for` | `duration` | `cv_status` 或 bool | 实现用单调时钟 |
| `cv.wait_until` | `time_point<Clock>` | `cv_status` 或 bool | 调用者给的 `Clock` |
| `future.wait_for` | `duration` | `future_status` | 实现用单调时钟 |
| `future.wait_until` | `time_point<Clock>` | `future_status` | 调用者给的 `Clock` |
| `pthread_cond_timedwait` | 绝对 `timespec` | 0 或 `ETIMEDOUT` | 默认 `CLOCK_REALTIME`；可用 `pthread_condattr_setclock` 改成 `CLOCK_MONOTONIC` |

pthread 的 `pthread_cond_timedwait` 用绝对 `timespec`，默认 `CLOCK_REALTIME`。要单调时钟，初始化条件变量前用 `pthread_condattr_setclock(CLOCK_MONOTONIC)`。条件变量的时钟在初始化时绑定，之后不能改。

glibc 2.30 起还有 `pthread_cond_clockwait`，可以直接指定时钟。glibc 2.43 的头文件仍只在 `_GNU_SOURCE` 下声明它。

`sem_timedwait` 同样用 `CLOCK_REALTIME` 的绝对时间。`clock_nanosleep` 可以指定 `clockid`，要单调就用 `CLOCK_MONOTONIC`。系统校时会让 `sem_timedwait` 的实际等待变长或变短。

- 手上是时长就用 `_for`。
- 手上是截止点就用 `_until`。
- 两者可以互相换算，但时钟必须是同一个。

## 9.5 组合异步任务：then、when_all、when_any 的今天


- N5050 的 `exec.tex` 有 `when_all`，没有 `when_any`。
- TS 的 `when_any` 结果带索引，告诉你哪个 future 先就绪；其余 future 不会自动取消。

`co_await` 需要一个 awaiter；`std::future` 没有提供，不能直接 `co_await` 一个 future。Asio 的 `awaitable` 和 `use_awaitable` 是常见替代，但那是库设施，不是标准库。

## 9.6 函数式并行与任务分解

函数式风格把每个任务看成“输入→输出”，任务之间不共享可变状态，结果用 future 传，天然没有数据竞争。代价是 `partition` 仍要串行做，`std::async` 递归仍会创建过多线程。

`std::sort` 本身串行；并行快排的加速来自把左右区间分给不同线程，`partition` 那一步不会变快。

并行快排的骨架：

- 选 pivot，`partition` 把区间分成两半。
- 左半区交给 `std::async`，右半区在当前线程递归。
- 区间小于 cutoff（例如 4096）就串行 `std::sort`。
- cutoff 太小，任务和线程创建开销会吞掉收益；太大，叶子串行部分又限制加速比。
- 父任务 `get()` 左半区的 future，再合并两个有序区间。
- 线程数要有上限；只靠 cutoff 只能压任务数，不能压并发数。

- 先收集所有结果和异常，别在循环中途退出。

## 速查

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `std::future<T>` | 一次性结果槽 | move-only；`get()` 后 `valid()` 为 false |
| `get()` | 等结果并取走 | 值被移动，异常被重新抛出；只能取一次 |
| `wait()` | 只等不取 | 不消耗结果；`valid()` 仍为 true |
| `wait_for` / `wait_until` | 带超时等待 | 返回 `ready`/`timeout`/`deferred` |
| `std::shared_future<T>` | 多读者结果槽 | 可拷贝；`get()` 返回 `const T&`；每个线程用自己的副本 |
| `std::async` | 启动任务并返回 future | 默认策略由实现选；future 析构可能阻塞 |
| `launch::async` | 要求异步执行 | 通常新线程；不保证线程池或数量控制 |
| `launch::deferred` | 延迟到 `get`/`wait` | 在调用线程执行；不取就不跑 |
| `std::packaged_task<R(Args...)>` | 把可调用对象和 future 绑定 | move-only；`get_future()` 只能调一次 |
| `std::promise<T>` | 手动设值的一端 | `set_value`/`set_exception`/`set_value_at_thread_exit` |
| `broken_promise` | 生产者没设值就销毁 | `get()` 抛 `std::future_error` |
| `std::current_exception` | 捕获当前异常 | 配合 `set_exception` 跨线程传异常 |
| `std::rethrow_exception` | 重新抛出 `exception_ptr` | 在 `get()` 或收集异常时用 |
| `std::make_exception_ptr` | 直接构造异常指针 | `copy_exception` 是草案名 |
| `steady_clock` | 单调时钟 | 超时和计时用它 |
| `system_clock` | 墙上时钟 | 可被校时；不要用来算超时 |
| `duration_cast` | 显式转换时长 | 截断，不四舍五入 |
| `std::move_only_function` | 可装 move-only 可调用对象 | C++23；替代装不下 `packaged_task` 的 `std::function` |

## 思考题

1. 预测：`9_1_async_result.cpp` 里如果不调用 `get()`、只让 future 析构，`launch::async` 和 `launch::deferred` 两种策略下任务分别会不会执行？

   <details><summary>提示</summary>

   `launch::async` 下，最后一个 future 析构会等任务结束，所以任务会执行完。`launch::deferred` 下，析构不会调用延迟函数；没有 `get`/`wait`，任务根本不会开始。把 `get()` 注释掉，分别用两种策略跑一次就能看到。

   </details>

2. 找错：`9_2_broken_promise.cpp` 里如果把 `promise` 改成 `packaged_task`、任务没执行就销毁，future 会以什么状态就绪？

   <details><summary>提示</summary>

   和 promise 未设值一样：共享状态以 `broken_promise` 就绪。`get()` 抛 `std::future_error`，错误码是 `future_errc::broken_promise`。`packaged_task` 的析构会放弃共享状态，不会替你执行任务。

   </details>

3. 权衡：一个登录流程要依次做“验证、取用户、取订单、更新界面”，用同步、`async`、回调、协程四种写法，各自在什么条件下更好？

   <details><summary>提示</summary>

   同步最简单，但会阻塞调用线程；`async` 能把整段移到后台，但每一步仍是阻塞的，且没有取消。回调不占线程，适合事件循环，但异常和生命周期要自己管；协程把异步写成顺序代码，适合步骤多、需要组合的场景，但要有支持 `co_await` 的运行时。

   </details>

4. 迁移：把 `9_6_parallel_quicksort.cpp` 的 `async` 改成固定 8 个线程的池，cutoff 和任务队列应该怎么配合？

   <details><summary>提示</summary>

   cutoff 要大于“提交一个任务”的开销，否则任务太多、队列竞争反而更慢；任务队列只放区间，工作线程从队列取。工作线程不能阻塞等子任务的 future，否则 8 个线程可能全在等，队列里的子任务没人执行；要么用“等待时帮忙取任务”，要么把子任务作为新任务提交、用完成计数收尾。

   </details>
