# 第 33 章 事件循环：Reactor、统一事件源、定时器与状态机

kvd 的 epoll 版能跑，但每加一个功能就要改 `epoll_wait` 后面的大 `switch`；空闲连接不关，内存一直涨。

按 Ctrl-C 直接退出，正在写的响应被截断。三件事分别指向 Reactor、定时器和优雅退出。

## 33.1 Reactor 的组件与一次事件的生命周期

{{#fig ch33/reactor_loop}}

Reactor 把“等事件”和“处理事件”分开。句柄是事件源在程序里的代表：Linux 下 I/O 是 fd，信号是信号值。事件多路分发器把 `epoll_wait` 包成注册、删除和等待三个动作。

| 组件 | 33.1 的示例里 | 职责 |
|---|---|---|
| 句柄 | fd、信号值 | 内核用它通知就绪 |
| 事件多路分发器 | `epoll` | 注册兴趣、等待就绪 |
| 事件处理器 | `Handler` | 声明 `handle_event` 回调 |
| 具体事件处理器 | `Acceptor`、`Connection` | 做 accept、读写、关闭 |
| Reactor | `EventLoop` | 循环、注册/删除、分派 |

一次事件的生命周期只有四步：`epoll_wait` 返回就绪数组，Reactor 用 `data.ptr` 找到处理器，调用 `handle_event`，处理器决定改兴趣、关闭或重新注册。

句柄不一定非是 fd：信号值也能当句柄，但进入 epoll 时必须先变成 fd（33.3）。Reactor 不关心业务，只负责“谁就绪、叫谁”。

`Acceptor` 和 `Connection` 都只实现 `fd()` 与 `handle_event()`；监听器和连接在 Reactor 眼里没有区别。

`run()` 先算最近的定时器截止时间，把它作为 `epoll_wait` 的超时；I/O 事件处理完再跑到期定时器，最后才清空 `retired_`。

- 回调里不能做阻塞操作，也不能做长计算。一个慢请求会把整个循环拖住，后面的连接都只能等；耗时任务要投递到线程池，见[第 35 章](ch35.md)。
- 回调里删除自己是常见需求。`Connection::close()` 先把 `shared_ptr` 交给 `EventLoop::retire()`，等这一批事件处理完再析构；否则就绪数组里的裸指针会在同一批的后续事件里变成悬空指针。
- 回调只改兴趣不重新注册，下一次就收不到事件；`remove()` 只摘兴趣，`close` 由连接自己做。`close` 要等同一 open file description 的所有 fd 都关闭才摘除兴趣，有 `dup`/`fork` 共享时要在复制之前 `DEL`。

## 33.2 事件循环的实现：回调、任务队列与唤醒

{{#fig ch33/eventfd_wakeup}}

`EventLoop` 持有 epoll fd、待执行任务队列和 `eventfd`。其他线程调 `runInLoop` 时，只把任务压进队列还不够：循环可能正睡在 `epoll_wait`，必须再写 `eventfd` 把它叫醒。

`eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC)` 从 Linux 2.6.22 起提供，两个标志从 2.6.27 起；`read` 得到 8 字节计数并清零，写端写一个 1 即可。计数器在溢出前不会阻塞。

计数由内核维护：多个线程同时写，值相加；循环读一次就清零，不需要每个任务一个字节。`EFD_SEMAPHORE` 会把语义改成“每次 read 减一”，默认不是这样。

这个上限要可配置，调用方要能区分“拒绝”和“已执行”。

## 33.3 统一事件源：signalfd、timerfd、eventfd

{{#fig ch33/unified_source}}

`signalfd` 从 Linux 2.6.22 起提供，`SFD_NONBLOCK`/`SFD_CLOEXEC` 从 2.6.27 起。用法有一个硬性前提：先在**所有线程**用 `pthread_sigmask` 屏蔽目标信号，再 `signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC)`；`read` 得到 `struct signalfd_siginfo`，按 `ssi_signo` 分派。

- `signalfd` 不能处理 `SIGKILL`、`SIGSTOP`，也不能处理同步产生的异常信号（例如访问非法地址产生的 `SIGSEGV`）。这些信号要么无法屏蔽，要么根本不会进入信号队列。
- `timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC)` 从 Linux 2.6.25 起提供，`TFD_*` 标志从 2.6.27 起；`timerfd_settime` 可以设 `TFD_TIMER_ABSTIME` 和周期；`read` 返回一个 `uint64_t`，是到期次数，不是时间。
- `eventfd` 做跨线程、跨进程唤醒；`pipe2` 是可移植替代，但多一个 fd、多一次用户态拷贝。三类 fd 和连接 fd 在同一个 `epoll` 里，按 `data.ptr` 的类型标签分派。

顺序是 `timerfd` → `eventfd` → `signalfd`：定时器 100ms 先到，工作线程 500ms 后写 eventfd，循环醒来再给自己发 SIGTERM。三路事件在同一个 `epoll` 实例上等，但不是同一次 `epoll_wait`：每次返回后处理一类，处理函数仍然是三个。

`signalfd` 的 `read` 可以一次返回多个 `signalfd_siginfo`；缓冲区只放一个时就循环读到 `EAGAIN`，否则同一批信号会留在队列里。统一事件源只是“同一个等待”，不是“同一个处理函数”。

| 事件源 | 传什么 | 能进 epoll | 起始版本 | 坑 |
|---|---|---|---|---|
| 自管道 | 1 字节信号值 | 能 | `pipe2` 2.6.27；`pipe` POSIX | 处理函数里只能 `write`；管道满会丢 |
| `signalfd` | `signalfd_siginfo` | 能 | 2.6.22 | 先屏蔽；`SIGKILL`/`SIGSTOP`、同步异常不行 |
| `eventfd` | 8 字节计数 | 能 | 2.6.22；flags 2.6.27 | `read` 清零；`EFD_SEMAPHORE` 改语义 |
| `timerfd` | 8 字节到期次数 | 能 | 2.6.25；`TFD_*` 2.6.27 | 绝对/相对；读的是次数不是时间 |
| `pidfd` | 进程退出 | 能 | `pidfd_open` 5.3；`waitid(P_PIDFD)` 5.4 | 只通知退出；发信号要 `pidfd_send_signal` |

表里的五类源都是通知通道，读到的是“发生了什么”，不是业务数据；真正的数据通道是连接 fd。

> **旧资料提示**：旧教程用自管道把信号接进 `select`/`poll`。Linux 上可以直接换成 `signalfd` + `eventfd`（2.6.22 起），少一个 pipe 和一次拷贝；细节见[第 41 章](ch41.md)。

## 33.4 定时器：时间堆、时间轮与超时扣减

{{#fig ch33/timer_heap}}

三种用户态容器和一种内核定时器各有位置。选容器先看定时器数量和超时分布，不要只看“插入是 O(几)”。

| 容器 | 插入 | 删除 | 取最近 | 精度 | 适用场景 |
|---|---|---|---|---|---|
| 升序链表 | O(n) | O(1)（有指针） | O(1) 表头 | tick | 定时器少、实现简单 |
| 时间轮 | O(1) | O(1) | O(1) 当前槽 | 槽间隔 | 大量短超时 |
| 最小堆 | O(lg n) | O(lg n)（任意删要标记） | O(1) 堆顶 | `time_point` | 通用 |
| `timerfd` | 内核维护 | 内核维护 | 内核 | 纳秒 | 少量截止时间或周期 |

`std::priority_queue` 默认是最大堆，要显式给 `std::greater`，或者写一个“到期早的优先”的比较器。到期时间相同的定时器用 `std::multimap`/`std::multiset`，不要用 `std::map`/`std::set` 丢键。

键用 `std::chrono::steady_clock::time_point`，不要用 `system_clock` 或 `time()`：后者只有 1 秒分辨率，还会被校时。

堆里是 10 个不同截止时间的定时器，输出按 50ms、100ms、…、500ms 的顺序触发；`id` 是插入顺序，和触发顺序无关。`epoll_wait` 这里没有注册 fd，只借它的超时参数等堆顶。

- `epoll_wait` 的超时会被 I/O 事件提前打断，返回后要用 `now` 重算剩余，不能把上次的 timeout 直接减一。
- `epoll_wait` 返回 0 只说明超时；返回大于 0 也可能已经有定时器到期，处理完 I/O 后仍要跑 `run_expired`。
- `timerfd` 让内核维护定时，用户态只算“最近截止时间”并把它作为 `epoll_wait` 的超时。
- `std::priority_queue` 不支持 decrease-key；改超时用惰性标记，或者直接用 `std::multimap` 按 `time_point` 排序。

## 33.5 增量状态机：半行请求与可恢复解析

{{#fig ch33/parser_state}}

协议状态机分三段：请求行（方法、key、value）→ 换行 → 下一条。kvd 没有 body，但状态机要能停在任意字节边界，下次从停下的地方继续。

缓冲区保留未消费的字节；用 `checked_index`、`read_index`、`start_line` 三个下标，或 `std::string_view` 切片。不要每读一行就 `memmove` 整个缓冲区，也不要假设 `\r\n` 一定在同一次 `recv` 里。

解析器返回三种结果：需要更多数据、完成一个请求、协议错误。它不阻塞、不碰 fd，可以单独测试，喂任意切分。

| 结果 | 含义 | 调用方动作 |
|---|---|---|
| `nullopt` | 还没有完整行 | 保留缓冲，等下一次 `recv` |
| `Request` | 完成一个请求 | 处理，继续 `next()` |
| `ParseError` | 协议错误 | 回 `ERROR`，丢到下一个换行 |

- 状态机只保存“读到哪个字段”，不保存 fd；同一个 parser 可以喂来自 socket、管道或测试数组的字节。
- `read_index` 是写到的位置，`checked_index` 是解析到的位置，`start_line` 是当前行起点；消费后只前移，不搬数据。
- 示例为了短，把字段攒进 `token_`；生产代码可以在同一个缓冲区上用这三个下标，省掉字段拷贝。

长度上限：一行 ≤1024 字节、key/value ≤256 字节；超限返回 `ERROR` 并关闭，防止一个不发换行的客户端把内存吃光。检查要在读入时做，不能先 `append` 再判断。

## 33.6 优雅退出与背压：停止接收、排空、关闭

{{#fig ch33/shutdown}}

退出顺序：收到 SIGTERM → 停止 `accept`（从 epoll 删监听 fd 或关闭）→ 通知 worker 不再取新任务 → 在限期内排空进行中的请求 → 关闭连接 → 释放定时器和 fd。

非阻塞 `send` 会短写：把未发送的字节留在连接自己的输出缓冲里，注册 `EPOLLOUT`，下次可写时从断点继续。不要假设一次 `send` 发完。

- `shutdown(SHUT_WR)` 只关写方向；要确认对端收到，先半关闭再等读方向 EOF，或者让协议自己带确认。
- `std::jthread` 的析构会 `request_stop` + `join`；要并行清理，先对所有 `stop_source` 请求停止，再统一汇入。

```text
{{#include code/ch33/33_6_graceful/output.out}}
```

服务端先打印 `SIGTERM: stop accepting`，此时请求已经收下、响应还要等 500ms；定时器到期后打印 `pending request: response ready` 和 `response written`，再关连接。客户端先收到完整的 `VALUE hello`，下一次 `recv` 才得到 0。

排空要有期限。如果某个连接一直不读，服务器不能无限等；到期限就记一条日志、强制关闭，并把这个连接算作失败，而不是把整个进程卡住。

- 背压要同时管住输出缓冲和请求队列。输出缓冲超过高水位就暂停读（从 epoll 摘掉 `EPOLLIN`），低于低水位再恢复；请求队列满了就拒绝新请求或让调用方等待。
- 暂停读不是丢数据：对端的 TCP 发送窗口会变小，发送方自然放慢。直接丢响应会破坏协议，让客户端收到半个 `VALUE`。

客户端只发不读，服务端把响应全塞进 `std::string`，每 1 MiB 打印一次；到 8 MiB 触发断言。真实的服务器不会打印完就安全退出，它会继续向堆要内存，直到 `bad_alloc` 或被 OOM killer 杀掉。

`std::jthread` + `std::stop_token` 做协作停止。`std::condition_variable_any::wait` 有 `stop_token` 重载，`std::condition_variable` 没有；要等一个可被 stop 的谓词，前者更直接。

不要在处理函数里 `exit`。`signalfd` 读到 SIGTERM 后设退出标志，让循环把当前事件处理完；`exit` 会跳过局部对象的析构，正在写的响应就断了。

| `signalfd(-1, &mask, SFD_NONBLOCK \| SFD_CLOEXEC)` | 信号变 fd | 2.6.22；`SFD_*` 2.6.27 | 先 `pthread_sigmask` 屏蔽 |
| `timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK \| TFD_CLOEXEC)` | 定时变 fd | 2.6.25；`TFD_*` 2.6.27 | `read` 得到的是次数 |
| `timerfd_settime(..., TFD_TIMER_ABSTIME, ...)` | 设绝对/周期定时 | 2.6.25 | 绝对时间用 `CLOCK_MONOTONIC` |
| `pipe2(O_NONBLOCK \| O_CLOEXEC)` | 可移植唤醒 | 2.6.27 | 多一个 fd，可能写满 |
| `std::priority_queue` + `std::greater` | 最小堆定时器 | C++98 | 默认是最大堆 |
| `std::multimap`/`std::multiset` | 允许相同到期时间 | C++98 | `map`/`set` 会丢键 |
| `std::chrono::steady_clock` | 单调时钟 | C++11 | 不要用 `system_clock` 算超时 |
| `std::jthread` / `std::stop_token` | 协作停止 | C++20 | 析构会 `request_stop` + `join` |
| `std::condition_variable_any::wait(lock, stop_token, pred)` | 可停止的等待 | C++20 | `condition_variable` 没有这个重载 |

## 思考题

1. （预测）33.2 的循环把“执行 pending 任务”放在“处理到期定时器”之前或之后，会对定时精度和任务延迟产生什么影响？用 `33_4_timer_drift` 的数据说明。

   <details><summary>提示</summary>

   放在定时器之前，长任务会推迟同一轮的到期回调，`timerfd` 的绝对截止时间也可能被拖晚；放在之后，定时器先跑，pending 任务的平均延迟会变大。`33_4_timer_drift` 里 `sleep` 的累计漂移随轮次增长，说明“每次晚一点”会累加；绝对定时器把误差压在单次唤醒上，不会累积。

   </details>

2. （找错）33.5 的解析器如果假设“一次 `recv` 至少有一整行”，在哪种客户端行为下会解析失败？把 1 字节切分的测试跑一遍，错在第几步？

   <details><summary>提示</summary>

   客户端把 `SET alpha 1\n` 拆成多次发送，或者一次只发一个字节时，第一次 `recv` 只有 `S`，按“整行”解析会立刻失败。`split=1` 的输出里，`S`、`E`、`T` 之后都还没有换行，解析器必须返回“需要更多数据”，而不是报错或丢掉半行。

   </details>

3. （权衡）`timerfd` 和用户态最小堆各适合什么场景？如果服务器有 10 万个空闲连接、超时时间集中在 30 秒，哪种更省？

   <details><summary>提示</summary>

   `timerfd` 适合少量截止时间或固定周期，让内核维护；10 万个连接各建一个 timerfd 会多出 10 万个 fd，代价高。最小堆把所有连接的超时放在一个堆里，插入/删除 O(lg n)，取最近 O(1)，更适合这种“大量连接、超时集中”的场景；`33_4_timerfd_idle` 的周期扫描只适合连接少的演示。

   </details>

4. （迁移）把 33.6 的优雅退出用到第 35 章的线程池服务器：主循环、worker、任务队列分别要在什么顺序停止，才能既不丢请求也不死锁？

   <details><summary>提示</summary>

   先停止 accept，再让主循环不再往队列投递新任务；然后关闭队列并通知所有 worker（`stop_token` 或 `close` + 唤醒），等 worker 把已取走的任务处理完；最后 `join` 所有 worker，再释放队列和连接。反过来先 `join` worker 会死锁，先关队列而不唤醒会让 worker 睡在条件变量上。

   </details>
