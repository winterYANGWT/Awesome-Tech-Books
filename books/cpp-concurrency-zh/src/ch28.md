# 第 28 章 进程内的消息传递：通道与 actor

三个线程共享一个 `std::queue`，每个操作都加了锁，程序还是偶发卡死。改成每个 actor 一个邮箱后卡死消失，但关闭时最后一条消息丢了，接收线程一直等不到“结束”通知。

问题不在于锁写得对不对，而在于“谁拥有这条消息、谁负责叫醒谁”没有写进接口。

## 28.1 从共享内存到消息：所有权、通道与 actor

{{#figref ch28/shared_vs_message}} 的上半部分是共享内存模型：三个线程读写同一个 `std::queue`，正确性靠锁、原子和条件变量。下半部分是消息传递模型：线程只发消息，不碰别人的状态，消息把数据的所有权从发送者交给接收者。

通道（channel）是有类型的先进先出队列（FIFO）：`send` 入队，`recv` 出队。它可以有多个生产者和多个消费者，可以有界（满时发送者等待，形成背压）或无界（用内存换吞吐）。

`close` 表示不会再有新消息，但已经入队的消息通常还要能取完。actor 是“身份 + 邮箱 + 行为”：一个 actor 一个邮箱，一次处理一条，状态只被自己的线程修改；CSP（Communicating Sequential Processes）更强调通道，actor 更强调邮箱和身份，进程内实现很接近。

- 通道有类型：`Channel<Message>` 只接受 `Message`，编译期就挡住别的类型。
- 有界通道满时让发送者等待，背压沿调用链往回传；无界通道没有这个反馈。
- `close` 只表示“不会再有新消息”，不等于“立刻丢弃队列里的消息”。

- 同步点在队列内部：`push` 和 `pop` 拿同一把锁，`wait` 的谓词同时检查空和关闭。

- 共享队列的关闭靠调用方额外约定；通道把 `close` 写进类型，所有使用者看到同一套语义。

## 28.2 一个有界通道：C++20 实现

`Channel<T>` 的内部是 `std::mutex`、两个条件变量 `not_empty`/`not_full`、一个 `std::deque<T>`、容量和 `closed` 标志。

`send(T)` 按值收下再移动，满时等 `not_full`；`recv()` 在空且未关闭时等 `not_empty` 并返回 `std::optional<T>`；`close()` 置 `closed` 后唤醒两边。

所有等待都必须带谓词：`not_full.wait(lock, [&]{ return q.size() < capacity || closed; })`。被唤醒后还要重查 `closed`，否则关闭时阻塞的发送者永远不会返回。

```cpp
bool send(T value) {
    std::unique_lock<std::mutex> lock(m_);
    not_full_.wait(lock, [&]{ return q_.size() < capacity_ || closed_; });
    if (closed_) {
        return false;
    }
    q_.push_back(std::move(value));
    lock.unlock();
    not_empty_.notify_one();
    return true;
}
```

- `close()` 的语义要写进接口：不再接受新消息，已入队的消息由 `recv` 取完。
- 队列空且关闭后 `recv` 返回 `nullopt`；`send` 返回 `false`。
- `close` 可重复调用；先置标志、解锁、再 `notify_all`，减少被唤醒线程立刻撞回锁上的概率。

- `std::optional<T>` 把“暂时没消息”和“已关闭”分开：`recv` 只有关闭且队空才返回 `nullopt`。
- 如果提供 `try_send`，它不等待，满时立刻返回 `false`，适合不能阻塞的调用方。
- `send` 收 `T` 而不是 `T&&`，让 move-only 类型也能走移动构造。
- `recv` 返回 `optional` 而不是抛异常：关闭是正常控制流，不是错误。

- 死锁常见于发送者在满时等，消费者却在等生产者发另一条消息；有界通道要配超时或 `try_send`，或者保证消费者不再反向依赖生产者。

| 项目 | 同步方式 | 背压 | 关闭 | 所有权 | 调试难度 |
|---|---|---|---|---|---|
| 有界 `Channel<T>` | 两个条件变量 + 谓词 | 满时 `send` 等待 | `close` 排空后返回 `nullopt` | 元素 move 进队列 | 状态都在队列内部 |
| `std::queue` + mutex + cv | 一把锁 + 一个条件变量 | 要自己加容量判断 | 要自己定标志和唤醒 | 元素 move 进队列 | 调用方各自持锁，容易漏唤醒 |

pthread 没有通道：`pthread_cond_wait` 返回 0 或错误码，等待要放在 `while` 里重查谓词；`pthread_cond_signal`/`broadcast` 也返回错误码，关闭时用 `broadcast`。

## 28.3 消息类型与分派：variant、any 与类型擦除

## 28.4 actor 模型：邮箱、状态机与生命周期

一个 actor 通常是一个线程 + 一个有界邮箱 + 一个状态机。线程循环 `recv`，按消息类型更新状态、发消息，处理完一条再取下一条；状态只被这个线程写，所以不需要锁。

消息的所有权通过移动转移。请求—应答可以把 `std::promise<T>` 放进请求消息，actor 处理完 `set_value`，调用方用 `future.get()` 等结果。

要超时就 `wait_for`；超时后销毁 `future` 并不会销毁共享状态，actor 仍可安全 `set_value`，只是结果没人取。要真正取消，得另加协议，例如取消消息或共享标志。

## 28.5 关闭与终止：close、毒丸、引用计数

毒丸（poison pill）是一条特殊的“停止”消息，放在所有正常消息之后。消费者只有一个时，FIFO 保证它被处理时前面的消息已经处理完；多个生产者时每个生产者都要放一个，或由一个协调者最后放。

## 28.6 三层消息传递：进程内、操作系统 IPC 与 MPI

进程内通道在同一地址空间里传 move-only 对象，没有序列化，延迟最低；代价是生命周期和关闭协议要自己管。

操作系统 IPC 走内核：`pipe`/`socketpair`（`SOCK_STREAM`）传字节流，`mq_open`/`mq_send`/`mq_receive` 传有类型的有界消息，`SCM_RIGHTS` 传 fd，共享内存 + 信号量传大块数据。错误码和阻塞语义由 POSIX/Linux 规定。

MPI 的进程各有私有地址空间，消息按通信子、源/目的 rank、tag 匹配，数据类型描述内存布局。MPI 的“消息”不是 C++ 对象，不能把指向本机对象的指针当消息内容；跨机器还要考虑字节序和类型布局。

{{#fig ch28/three_layers}}

三行的共同点是“发送者把数据交给一个中间层”，区别在中间层做什么：进程内只搬所有权，OS IPC 要复制字节或映射页，MPI 还要打包、匹配和走网络。MPI 的集合通信建立在点对点消息和通信子之上，不是消息队列的替代品。

| 层 | 地址空间 | 传递单位 | 是否有类型 | 阻塞与缓冲 | 顺序 | 关闭与失败 | 典型接口 |
|---|---|---|---|---|---|---|---|
| 进程内 `Channel<T>` | 同一进程共享 | move-only C++ 对象 | 有（模板类型） | 有界时满则等，无界只受内存限制 | FIFO | `close` + `join`，对象生命周期 | `send`/`recv`/`close` |
| POSIX `pipe`/`mq` | 同机不同进程 | 字节流 / 有类型消息 | `pipe` 无，`mq` 有 | `pipe` 满时阻塞；`mq` 受 `mq_msgsize`、`mq_maxmsg` 限制 | 字节流 FIFO；`mq` 同优先级 FIFO，可按优先级取 | EOF、`EPIPE`、`EINTR`、`EAGAIN` | `pipe`/`read`/`write`，`mq_open`/`mq_send`/`mq_receive` |
| MPI | 跨进程、跨机器，私有 | 按数据类型描述的内存布局 | 有（通信子 + tag + datatype） | 实现可缓冲，`MPI_Ssend` 保证同步 | 同一（源, tag）不超越 | `MPI_Finalize` 前完成通信、补匹配接收 | `MPI_Send`/`MPI_Recv`/`MPI_Wait` |

同一进程的线程之间优先用通道/actor，同一台机器的进程之间用 pipe/socket/共享内存，跨机器用 MPI 或 socket。混合场景常见 MPI + 线程：节点间 MPI，节点内通道/OpenMP。

混合程序要把 MPI 调用限制在同一个线程，或者用 `MPI_THREAD_MULTIPLE`；节点内的通道和节点间的 MPI 各有各的关闭顺序，两边的超时和错误要分别处理。

三层的关闭/失败语义不同：进程内是对象生命周期，OS IPC 是 fd 关闭和 `EPIPE`/`EINTR`，MPI 是 `MPI_Finalize` 前必须完成通信、补上匹配接收。不能把一层的经验直接搬到另一层。

- 跨机器时字节序和类型布局要显式约定；直接用 `memcpy` 发结构体只适合同构机器。
- 进程内的超时通常靠 `wait_for`，OS IPC 靠 `O_NONBLOCK` 和 `poll`，MPI 靠非阻塞请求加 `MPI_Test`。

## 速查

| 设施 | 作用 | 关闭/失败语义 | 坑 |
|---|---|---|---|
| `std::queue` + `std::mutex` + `std::condition_variable` | 最小共享队列 | 自己定 `closed` 和唤醒 | 谓词漏掉 `closed`，或只置标志不通知 |
| `std::deque<T>` | 通道的底层容器 | 无 | 队头队尾都要在锁内操作 |
| `std::optional<T>` | `recv` 的返回值 | `nullopt` 表示已关闭且队空 | 和“暂时没消息”要区分开 |
| `std::counting_semaphore` | 计数空位或消息数 | 关闭仍要互斥量配合 | 用计数代替谓词，关闭时竞争难写对 |
| `std::variant` / `std::visit` | 封闭消息集的分派 | 漏分支是编译错误 | 访问器要覆盖所有 alternatives |
| `std::get<T>` / `holds_alternative<T>` | 取或检查 variant 的值 | 取错抛 `bad_variant_access` | 先用 `holds_alternative` 判断 |
| `std::any` / `any_cast` | 开放消息集的分派 | 取错返回空指针或抛 `bad_any_cast` | 通常有堆分配，无编译期穷尽检查 |
| `std::function` | 存可拷贝的处理函数 | 空调用抛 `bad_function_call` | 目标必须可拷贝 |
| `std::move_only_function` | 存只能移动的处理函数 | 空调用违反前置条件，未定义行为 | C++23 起 |
| `std::promise` / `std::future` | 请求—应答的结果槽 | 未设值就销毁得到 `broken_promise` | `get()` 只能调一次；超时后 promise 仍可安全设值，只是没人取 |
| `std::jthread` / `stop_token` | 自动汇入 + 协作停止 | 析构先 `request_stop()` 再 `join()` | 普通 `condition_variable` 不会因 `request_stop` 醒来 |
| `std::condition_variable_any` + `stop_token` | 可中断的等待 | 停止请求到达时返回 `false` | 通常比 `condition_variable` 多一层内部锁 |

## 思考题

1. 预测：28.2 的有界通道容量从 8 改成 1，4 个生产者/4 个消费者的总吞吐会怎么变？如果把 `close` 放在生产者发完最后一条之后、消费者取完之前，会不会丢消息？

   <details><summary>提示</summary>

   容量 1 时每发一条就可能等一次空位，生产者和消费者被强行交替，吞吐通常明显下降。`close` 只表示“不会再有新消息”，已经入队的消息仍由 `recv` 取完，所以不会丢；丢消息发生在 `close` 之后还有 `send`，或消费者先退出。

   </details>

2. 找错：28.5 的毒丸方案在“两个生产者、一个消费者”时，只放一个毒丸会怎样？如果生产者 A 先放毒丸、生产者 B 还有消息没发，消费者会提前退出吗？

   <details><summary>提示</summary>

   两种设计要分开看。若消费者见到任意一个毒丸就退出：A 先放毒丸，消费者处理完 A 之前的消息就会退出，B 之后发的消息没人取，`send` 可能永远阻塞。若消费者要集齐与生产者数相同的毒丸才退出：只放一个不会让它退出，它会一直等第二个。本章示例用的是后一种设计，消费者见到 3 个毒丸才 `break`。

   </details>

3. 权衡：28.3 的 `variant`、`any`、继承三种消息分派，在消息类型数量、扩展频率、分派热度和二进制体积上各自怎么取舍？

   <details><summary>提示</summary>

   `variant` 适合类型少而封闭、分派热、愿意为每个分支生成代码的场景，二进制会随分支增长。`any` 适合类型经常增加、分派不热的场景，代价是堆分配和运行期检查。继承 + `dynamic_cast` 适合插件式扩展，但每条消息都要堆分配和 RTTI，分派链长时最慢。

   </details>

4. 迁移：把 28.4 的 ATM actor 改成“每个 actor 一个线程 + 一个有界邮箱”，如果银行 actor 处理慢、ATM 邮箱满，调用方应该阻塞、超时还是丢弃？三种选择分别会把故障推到哪里？

   <details><summary>提示</summary>

   阻塞把故障推回调用方：界面或客户端卡住，但消息不丢。超时把故障留在 ATM：调用方拿到失败，要决定重试还是放弃，重试可能放大压力。丢弃把故障藏起来：调用方以为请求已提交，账目可能对不上。可以先阻塞加超时，再把超时作为错误消息回给调用方。

   </details>
