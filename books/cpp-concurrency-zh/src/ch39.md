# 第 39 章 异步任务的十年：从 `future.then` 到 `std::execution`

旧代码里 `f.then([](int x){ ... })` 在 C++20 编译器上只剩一行错误，另一个 `std::async` 的 future 在析构时停住半秒，调用方却以为任务被取消。

两个现象来自同一件事：future 承诺的东西比多数人以为的少。

```cpp
auto f = std::async(std::launch::async, work);
f.then([](int x) { use(x); });  // C++20 没有这个成员
```

`async` 那组 `wait_for(0s)` 返回 `timeout`、`executed=0`，说明任务已经交给别的线程但还没完成，`deferred` 那组返回 `deferred`、`executed=0`，说明任务根本还没开始。`get` 之后两组才都变成 `executed=1`。

{{#fig ch39/future_states}}

看第 3 步：`deferred` 的 `wait_for` 不会执行任务，只有 `get`/`wait` 才会。

三种策略和最容易踩的坑：

- `launch::async`：调用返回时线程已经启动，future 析构要等它结束。
- `launch::deferred`：只保存函数和参数，`get`/`wait` 才在调用线程执行。
- 不传策略：等价于 `async | deferred`，实现可以选 deferred，所以“后台任务”可能根本没在后台跑。
- 实际最容易踩的坑：代码看起来起了后台任务，实际可能一行都没跑，直到 `get` 才在调用线程执行。要并发就写 `launch::async`，要延迟就写 `launch::deferred`，别让实现替你决定。

**当时为什么这样写**：C++11 想要一个比 pthread 简单的“起任务、取结果”接口，默认策略把选择留给实现，本意是兼顾并发和延迟执行。

**问题在哪**：`launch::async` 的 future 在最后一个引用时析构，会阻塞到任务完成，`launch::deferred` 的 future 在最后一个引用时析构，则把任务丢掉。

计时从 future 进作用域开始，到析构返回结束，析构耗时和 `sleep_for` 同量级，方向是“等”而不是“取消”。`std::async` 也不是线程池：标准只要求 `launch::async` 如同在新线程执行，不承诺复用，也不承诺不超过硬件线程数，递归 `async` 会把线程数推高。析构的两种结果如下。

- `launch::async`：future 是最后一个引用且任务还没完成时，析构阻塞到它结束。
- `launch::deferred`：最后一个引用且任务还没开始，析构直接销毁保存的函数，任务不会执行。

**取代它的**：需要可控并发度时自己建池（[第 19 章](ch19.md)），C++26 的 `std::execution` 是另一条路，本机未实现。只起一个任务、以后取结果，`async` 仍然合适。`get` 只能调一次，要多方取结果用 `shared_future`。

**今天还用得着吗**：单个后台任务、一次性结果，`async` 比手写线程短，要批量、限流、取消，就不要用它。

> **旧资料提示**：旧教程说 `std::async` 会“用满硬件、不会超额申请”。C++11 起就没有这个保证，需要可控并发度就自己建池。

{{#fig ch39/then_chain}}

看图的上半部分：TS 的 `then` 直接挂在 future 上，下半部分把组合（`just | then | when_all`）和调度位置分开。

TS 的三件套和现状：

- `then(f)`：前一个 future 就绪后调用 `f`，返回新 future。
- `when_all(a, b, ...)`：等所有 future 就绪，返回全部结果。
- `when_any(a, b, ...)`：等第一个就绪，结果里带索引。
- 现状：当年的实现能编，换到今天的标准库反而找不到成员，而替代接口还没落地。

**当时为什么这样写**：Concurrency TS（2015）想补上 future 缺的组合能力，`then` 返回新 future，延续返回 future 时自动展平，`when_all`/`when_any` 负责等待。

**问题在哪**：TS 已经规定了 `then` 的返回类型（延续返回 future 时自动展平）和错误沿链传播；没定的是怎么和执行器/调度器结合，以及取消——TS 里没有取消。这些和 executors 提案纠缠，TS 没有并入 C++17/20/23。

没定的两件事：

- 调度器：延续在哪个线程跑，TS 没有统一参数，由实现决定。
- 取消：TS 没有取消机制，停止不了已经在跑的步骤。

两个等待都返回 `timeout`，因为 promise 一直没赋值。`is_steady=0` 只说明它不单调，libstdc++ 15 的实现里 `high_resolution_clock` 是 `system_clock` 的别名，不能拿它测间隔。`cv_status::timeout` 的拼写是 `timeout`，`time_out` 是旧表里的笔误。

- 测间隔：`steady_clock`，它保证单调。
- 记日历时间：`system_clock`，配合 `zoned_time` 和 `year_month_day`。
- 等相对时间：`wait_for(duration)`，等绝对时刻：`wait_until(time_point)`。

**当时为什么这样写**：名字里带 high resolution，看起来最适合计时，`shared_future` 又不如 `future` 常用，很多人第一次见。

**问题在哪**：`wait_for` 收 duration，是相对超时，`wait_until` 收 time_point，是绝对时刻。`high_resolution_clock` 不保证单调，系统时间一跳，测出的间隔就可能为负。

三个坑：

- `high_resolution_clock` 不保证单调，系统时间回拨时间隔可能变负。
- `wait_until` 要 `time_point`，传 duration 编译不过。
- `cv_status` 的枚举值是 `timeout`，`time_out` 是旧表笔误。

**取代它的**：计时用 `steady_clock`，日志和跨时区调度用 C++20 的 `year_month_day`、`sys_days`、`zoned_time`、`utc_clock`/`tai_clock`/`gps_clock`。`wait_for` 按标准应当用 steady clock 度量，`wait_until(system_clock)` 会跟着系统时间走。

**今天还用得着吗**：`shared_future` 仍适合“一份结果、多个消费者”，时钟按用途分，计时和日历不要混。

`throw(int)` 在 C++17 起被移除，空 `throw()` 在 GCC 15 和 Clang 21 上还能编译，但标准语法只有 `noexcept`，新代码不要写。

**当时为什么这样写**：C++11 有了 `exception_ptr`，但名字和用法不直观，动态异常规格是从 C++98 带过来的，旧代码里很多。

**问题在哪**：异常不捕获就出不了线程，工作线程直接 terminate，带执行策略的算法（包括 `seq`）在元素访问函数抛异常时也 terminate，只有不带策略的重载才传播。`seq` 会传播是旧说法，和 N5050 不符。异常出不了线程有三种情况：

- 工作线程里没人捕获，异常离开线程函数就 `std::terminate`。
- 带执行策略的算法（包括 `seq`）在用户函数抛异常时 terminate。
- 任务队列里不 `catch` 再 `set_exception`，调用方永远等不到结果。

**取代它的**：`make_exception_ptr`/`current_exception`/`rethrow_exception`，空 `throw()` 改 `noexcept`，任务队列里 `catch` 后 `set_exception`。C++23 的 `std::expected` 适合传可预期错误，和 future 的异常通道互补。

**今天还用得着吗**：`packaged_task`/`promise` 仍是标准工具，跨任务边界时，先想清楚是异常还是返回值。

{{#fig ch39/yield_vs_wait}}

图的上半条路是 `yield` 轮询：空队列也反复查，下半条是 `cv.wait`：没有任务就睡眠，`notify_all` 才醒。

阻塞 worker 的三种写法：

- 条件变量：`wait(lock, predicate)`，`close` 时 `notify_all`。
- 计数信号量：每个任务 `release` 一次，worker `acquire` 一次。
- `atomic::wait`：在原子计数上等，适合没有队列、只有完成数的场景。

池大小也不要照抄 `hardware_concurrency()`：容器里的 cgroup 配额、NUMA 节点和 I/O 比例都会改变最优值，这个函数还可能返回 0。

**当时为什么这样写**：轮询池代码短、没有丢失唤醒问题，任务到达的延迟也低，在老机器上，空转一个核的代价没人测。

**问题在哪**：`yield` 只是让出时间片，不阻塞，空队列时 worker 立刻回来，仍然占满一个核。关闭顺序错了还会丢任务或永久等待。关闭线程池的顺序如下。

- 先置 `done` 并 `notify_all`，让睡着的 worker 醒来。
- 再 `join` 所有 worker，确保没有任务还在跑。
- 最后销毁队列和线程对象，反了就会丢任务或永久等待。

顺序反了，worker 可能在队列销毁后才醒来。这里的队列是[第 7 章](ch07.md) `ThreadSafeQueue` 的简化版，第 19 章会在这个池上加工作窃取。

**取代它的**：条件变量加队列、`std::counting_semaphore`（C++20）或 `atomic::wait`（C++20）阻塞，`jthread` + `stop_token` 自动 `request_stop`，但仍要 `notify_all` 唤醒 worker。`std::function` 要求可拷贝，move-only 任务用 `std::move_only_function`（C++23）。

**今天还用得着吗**：标准到 C++23 没有 `std::thread_pool`，C++26 的 `std::execution` 也没有可配置线程数的池类，写服务器或批处理仍要自己建池。池大小看 cgroup 配额、NUMA 和 I/O 比例，`hardware_concurrency()` 只是提示，可能返回 0。多线程日志用 `std::osyncstream`。

{{#fig ch39/sender_graph}}

图里 `just → then → when_all` 只是在描述工作，`connect` 到 receiver 后才 `start`，完成只能走 `set_value`/`set_error`/`set_stopped` 三条通道之一。

| 组合方式 | `std::future`/`async` | Concurrency TS | C++26 `std::execution` |
|---|---|---|---|
| 取结果 | 有，`get` 一次 | 有 | 有，`std::this_thread::sync_wait`（未实现） |
| 串联 | 无 | 有，`then` | 有，`then`（未实现） |
| 等待全部 | 无，手写 `get` | 有，`when_all` | 有，`when_all`（未实现） |
| 等待任一 | 无 | 有，`when_any` | 无（N5050） |
| 错误传递 | 有，`get` 重抛 | 有，沿链传播 | 有，`set_error`（未实现） |
| 取消 | 无 | 无 | 有，`set_stopped`（未实现） |
| 调度位置 | 仅 launch 策略 | 无，`then` 的续延在哪个线程跑由实现决定 | 有，`schedule(sched)`（未实现） |

表里最容易被误解的是“串联”和“等待全部”：future 一侧要手写，TS 一侧有接口但没进标准，`std::execution` 一侧有接口但本机未实现。

sender/receiver 的五个名字：

- `scheduler`：执行资源，`schedule(sched)` 得到一个 sender。
- `sender`：描述“将来会完成的工作”，可以 `| then` 组合。
- `receiver`：接收完成通知，有 `set_value`/`set_error`/`set_stopped`。
- `operation_state`：`connect(sender, receiver)` 得到它，`start` 后开始执行。

要和现有 future 代码桥接，常见做法是用 `promise` 包一层：sender 完成时 `set_value`，旧代码继续在 future 上 `get`。

**当时为什么这样写**：P0443 系列想统一 executor 概念，让算法和调度器解耦，讨论了很多年，接口一直没收敛。

**问题在哪**：`std::execution` 不是 future 的 drop-in：没有 `get()`，错误走 `set_error`，取消走 `set_stopped`，调度位置由 `schedule(sched)` 指定，旧代码要桥接。标准仍不提供 socket 和定时器，I/O 仍要事件循环或 Asio；`when_any` 不在 N5050 里。

- 没有 `get()`：结果通过 receiver 的 `set_value` 交回来。
- 错误和取消分开：错误走 `set_error`，取消走 `set_stopped`。
- 调度位置由 `schedule(sched)` 指定，不是由 launch 策略或实现挑线程。

这三条决定了旧代码不能只换头文件。

**取代它的**：C++26 采纳 P2300：`scheduler`、`sender`、`receiver`、`operation_state`、`connect`/`start`，`schedule(sched)` 指定执行位置。

```cpp
// C++26，本书环境（GCC 15 / Clang 21）尚未实现，未编译验证
namespace ex = std::execution;
auto work = ex::when_all(
    ex::just(20) | ex::then([](int x) { return x + 2; }),
    ex::just(20));
auto [a, b] = std::this_thread::sync_wait(std::move(work)).value();
```

**今天还用得着吗**：今天能用的是线程池、Asio、协程，sender/receiver 等实现成熟再迁移。先学会把任务图和执行位置分开，这个思路现在就能用。

`std::future` 没有 `await_ready`/`await_suspend`，不能直接 `co_await`，要自己写 awaiter，或者换 Asio/cppcoro/libunifex。

**当时为什么这样写**：C++20 只标准化了协程的语言部分，标准库给了 `coroutine_traits`/`coroutine_handle`，没有给 task 类型，大家以为 future 会补上 awaiter，但没有。

**问题在哪**：最小 `task<T>` 要写 `promise_type` 和 `initial_suspend`/`final_suspend`，还要管结果、异常和帧的销毁，`await_ready`/`await_suspend`/`await_resume` 是让 `task` 本身能被 `co_await` 时才要写的另一层。promise 的定制点少一个通常编译不过，`final_suspend` 挂住后没人 `destroy` 才会泄漏帧。协程不提供的三件事如下。

- 没有标准 task：`std::future` 也没有 `co_await`，两边接不上。
- 帧的生命周期要自己管：`final_suspend` 挂住后，谁 destroy 要写清楚。
- 恢复线程由 awaiter 决定：协程自己不创建线程，也不做 I/O。

**取代它的**：自己写 task/awaiter，或用 Asio 的 `awaitable`、cppcoro、libunifex，C++23 的 `std::generator` 只能做同步生成器，异步 task 仍没有标准类型。`std::execution` 的 sender 是另一条路。

**今天还用得着吗**：I/O 密集、需要顺序写法时，协程加现成库很合适，CPU 密集任务仍要交给线程池，协程不会让它变快。

## 速查

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `std::async(policy, f, args...)` | 起一个异步任务 | 不传策略时实现可选 deferred |
| `launch::async` | 如同在新线程执行 | 最后一个引用且未就绪时，析构阻塞 |
| `launch::deferred` | 延迟到 `get`/`wait` 才执行 | 最后一个引用且没 `get` 时任务被丢弃 |
| `std::future<T>` | 单所有者的结果 | `get` 只能一次，之后 `valid()==false` |
| `std::shared_future<T>` | 多消费者共享结果 | `get()` 返回 `const T&` |
| `std::promise<T>` | 手动设置值或异常 | 析构前没设置就是 `broken_promise` |
| `std::packaged_task<R()>` | 把可调用对象和 future 绑定 | 异常存进 shared state，`get` 重抛 |
| `wait_for(duration)` | 相对超时 | 返回 `future_status` |
| `wait_until(time_point)` | 绝对超时 | 第二参数是时刻，不是 duration |
| `future_status` | `ready`/`deferred`/`timeout` | 看到 `deferred` 说明任务还没跑 |
| `cv_status` | `timeout`/`no_timeout` | 拼写是 `timeout`，不是 `time_out` |
| `make_exception_ptr` | 把异常存成 `exception_ptr` | C++11 起，没有 `copy_exception` |
| `current_exception` / `rethrow_exception` | 捕获和重抛当前异常 | 跨线程要靠 shared state 传递 |
| `std::move_only_function` | 装 move-only 任务 | C++23，`std::function` 要求可拷贝 |
| `std::execution::just`/`then`/`when_all`；`std::this_thread::sync_wait` | sender/receiver 组合 | C++26，本机未实现 |
| `co_await`/`co_return`/`coroutine_handle` | 协程的语言设施 | 标准库没有现成 task，协程不建线程 |

## 思考题

1. （预测）`launch::deferred` 的 future 一直不 `get()`，任务会执行吗？future 析构会阻塞吗？如果把同样的代码换成 `launch::async`，析构会怎样？

   <details><summary>提示</summary>

   `deferred` 的任务不会执行：shared state 销毁时只销毁保存的可调用对象，不调用它，析构也不等。换成 `launch::async` 后，future 析构会阻塞到任务完成，任务已经跑完，结果只是没人取。用 39.1 的两个示例分别改一行就能看到差别。

   </details>

2. （找错）39.1 的析构计时为什么不能说明“任务被取消”？如果调用方想在中途取消任务，应该改什么？

   <details><summary>提示</summary>

   析构的耗时来自等待，不是取消：`sleep_for` 照常走完，任务照常返回，只是 main 在析构里等它。`std::future` 没有取消接口，要取消就把任务改成接受 `std::stop_token`，在循环或等待点检查 `stop_requested()`，并用 `jthread` 或自己的池去触发。

   </details>

3. （权衡）没有标准 `when_all` 时，用 `async` + 两次 `get` 和用 `std::counting_semaphore` 各自适合什么场景？

   <details><summary>提示</summary>

   任务数固定、调用方只关心最终结果时，`async` + `get` 最简单，代价是调用线程按顺序阻塞在每个 future 上。任务数多、任务还会动态增加，或者想在等待时继续做别的事，就用信号量（或条件变量）记完成数：每个任务 `release` 一次，等待方 `acquire` 够 N 次再继续；也可以用原子计数器从 N 减到 0，再唤醒等待方。

   </details>

4. （迁移）把 39.5 的 `std::function` 队列换成 `std::move_only_function`，哪些任务原来放不进去？换完还要注意什么？

   <details><summary>提示</summary>

   `packaged_task`、`promise` 加 future 的组合、捕获了 `std::unique_ptr` 的 lambda，以及任何只可移动的 lambda，原来都因为 `std::function` 要求可拷贝而放不进去。换完要注意 `move_only_function` 不能拷贝，提交接口要按值接收再 `std::move`，队列取出时也只能移动。

   </details>
