# 第 17 章 划分工作

三角形工作量：第 i 行做 i+1 次迭代。把 1000 行按连续块分给 4 个线程，最后一个线程分到 43.7% 的迭代；改成循环划分，四个线程的迭代数都在 12.5 万上下，但每次访问都要跨过别人的块。

划分不是把行数平均切一刀。负载、通信和缓存局部性要一起看，这一章用求和、快速排序、流水线和直方图把这笔账算清楚。

```cpp
// 三角形工作量：第 i 行有 i+1 次迭代
size_t lo = rows * tid / p, hi = rows * (tid + 1) / p;
for (size_t i = lo; i < hi; ++i)
    for (size_t j = 0; j <= i; ++j) sum += i * j;
```

## 17.1 三种划分方式与两个指标

{{#fig ch17/partition_taxonomy}}

三种方式的区别在“什么时候知道边界”：

- 按数据：处理前边界已知，每块交给一个线程，线程之间不通信，最后合并部分结果。`for_each`、矩阵-向量乘法、直方图都属于这一类。

- 按任务类型：数据长度未知，或不同工作要不同处理，用分离关注点（GUI、I/O、计算线程）或流水线（阶段之间用队列）。

Foster 四步法把这件事拆成可重复的四步：

1. 划分：把问题和数据拆成尽量多的细任务。
2. 通信：找出任务之间要传的数据和同步。
3. 凝聚：把小任务合并成适合执行体的粒度。
4. 映射：把任务分配给线程或进程，让通信少、负载均衡。

四步不是一次成功。凝聚之后可能发现负载不均，要回到划分。映射之后可能发现通信太多，要回到凝聚，每一步都用测量验证。

常见的递归划分示例有三个缺陷，照抄会得到竞态或创建不出线程：

| 旧写法 | 问题 | 今天怎么写 |
|---|---|---|
| `boost::shared_ptr` | 多一个外部依赖 | `std::shared_ptr`（C++11 起） |
| `hardware_concurrency()-1` | 返回 0 时无符号下溢 | 先判断 0，再 clamp 到至少 1 |
| worker 里 `push_back` 到共享 `threads` | 这个向量没有同步 | 线程数固定，别在 worker 里改线程表 |

> **旧资料提示**：`boost::shared_ptr` 在 C++11 后可以由 `std::shared_ptr` 代替；两者的所有权语义和引用计数开销见 [第 37 章](ch37.md)。

> **旧资料提示**：`std::thread::hardware_concurrency()` 从 C++11 起就可能返回 0，不能直接减一；线程数的取法见 [第 39 章](ch39.md)。

流水线有两个指标：

- 首件延迟：第一件走完四段的时间。计时从创建线程之前开始，包含线程启动和调度开销，所以比四段之和略大；四段之和是它的下界。

| 阶段 | 基准 | 放慢后 |
|---|---|---|
| 读 | 20µs | 20µs |
| 解析 | 20µs | 20µs |
| 计算 | 10µs | 50µs |
| 写 | 10µs | 10µs |

队列必须有界，否则生产快、消费慢时内存会无限增长。队列满时，生产者有三种策略：

- 阻塞：等队列有空位，把压力反推给上游，这里选这一种。
- 丢弃：适合可丢的采样、日志，但计数类工作不能丢。
- 降级：减小批量或降低精度，把决定写进设计文档。

阶段划分要让各阶段耗时接近。某个阶段明显更慢时，增加该阶段的执行体，或把它再拆成几个子阶段；不要平均给所有阶段加人。

块大小有两头：

- 太小：几十万次任务提交和原子操作把时间吃光，`ms` 很高。
- 太大：单块尾部很长，最后几块决定总时间，`ms` 不再下降。

块很大时单块 `p99` 比小块高，因为单块本身变长；它只计块内计算，不含领任务的等待，不能当端到端尾延迟看。

调度方式有四种常见组合：

- 静态：工作量可预测时用，没有领任务的同步，但负载可能不均。
- 动态：每次领一块，负载均匀，代价是每次都要同步；块太大退化成静态，太小同步开销高。
- `guided`：块从大到小，是静态和动态的折中（[第 22 章](ch22.md)）。
- 工作窃取：每个线程有本地队列，空闲线程从别的线程队尾偷任务；竞争小，但实现复杂（[第 19 章](ch19.md)）。

测量时要同时看总时间和尾延迟。平均吞吐变好但 p99 变差，对服务器来说可能不可接受；块大小要按负载的分布选，不只看平均值。

> **旧资料提示**：手写并行 `for_each`/`find` 做数据划分，在 C++17 起可以换成带执行策略的并行算法；libstdc++ 15 的 `std::execution::par` 需要 TBB 后端，其他实现不一定，原因和写法见 [第 23 章](ch23.md) 与 [第 40 章](ch40.md)。

- TSan 在 `++bin_counts[...]` 这一行报数据竞争。
- 把 TSan 关掉再跑，总数通常少于 2000000：多个线程读到同一个旧值，各自加一，最后只留下一个加一。

本地数组把竞争消掉，代价是 `b × 线程数` 的空间；桶很多、线程很多时，它会占满缓存。替代方案有三种：

- 桶分块：把桶分成几段，每段一个本地数组，合并时只加有数据的段。
- 每线程负责一部分桶：按数据项所属的桶分派，通信量取决于分派方式。
- 原子计数：桶多时写分散、竞争小；桶少时所有线程抢同几个计数器。

最后的合并可以串行，也可以树形相加。树形相加的通信量是 `O(b log p)`，但实现复杂，桶数不大时串行合并往往更快。

Foster 四步不是线性的：凝聚之后可能发现负载不均，要回到划分；映射之后可能发现通信太多，要回到凝聚。每一步都要用测量验证，而不是照着四步走一遍就结束。

同一件事在四套 API 里的写法：

| 划分方式 | C++ 写法 | OpenMP 子句 | MPI 对应 |
|---|---|---|---|
| 块划分 | `std::thread` 按区间分 | `schedule(static)`、`schedule(static,c)` | 块分布，`MPI_Scatterv`/`MPI_Gatherv` |
| 循环划分 | 线程 `i` 取 `i, i+p, …` | `schedule(static,1)`、`schedule(dynamic,1)` | 下标自己算；非连续数据要派生类型或 `MPI_Alltoallv` |
| 块-循环 | 固定 `c` 轮转 | `schedule(static,c)`、`schedule(dynamic,c)` | 裸 `MPI_Scatterv`/`MPI_Gatherv` 只适合连续块；块-循环要派生类型或 `MPI_Alltoallv` |
| 递归或任务 | 任务栈、`std::async` | `task`、`taskloop` | 主从任务队列，MPI 没有任务构造 |
| 流水线 | 队列加线程 | 没有直接对应 | `MPI_Send`/`MPI_Recv` 串成阶段 |

MPI 的划分还要考虑进程间的通信量：块分布让每个进程只和邻居交换边界，循环分布让每次迭代都可能要全局收集。求和本身用 `MPI_Reduce` 更直接（[第 29 章](ch29.md)）。

`MPI_Scatterv`/`MPI_Gatherv` 每次只搬每个进程一段连续数据，循环和块-循环的本地数据不连续。要先用 `MPI_Type_vector` 建派生类型，或者改用 `MPI_Alltoallv`；`MPI_Allgatherv` 收直方图时也一样。

| 划分方式 | 适用条件 | 代价 |
|---|---|---|
| 按数据 | 处理前边界已知，元素做同一件事 | 工作量不均时后面线程偏重；块边界可能伪共享 |
| 按递归结构 | 先算一步才知道子范围 | 任务栈或队列的同步；递归要有阈值 |
| 按任务类型 | 数据长度未知，或等待性质不同 | 队列要有界；慢阶段会反压上游 |

块、循环、块-循环的写法与缓存行为：

| 写法 | 线程 `i` 处理 | 缓存行为 | 负载 |
|---|---|---|---|
| 块 | `[i*n/p, (i+1)*n/p)` | 顺序访问，预取和缓存行都用得上 | 工作量均匀时局部性最好 |
| 循环 | `i, i+p, i+2p, …` | 跨步访问，缓存行被多个线程分用 | 均匀 |
| 块-循环 | 每轮 `c` 个，轮转分配 | `c` 大接近块，`c` 小接近循环 | 用 `c` 调 |

Foster 四步的检查清单：

| 步骤 | 检查问题 | 本章例子 |
|---|---|---|
| 划分 | 任务够细吗？边界无重叠、无遗漏吗？ | 三角形按行分块 |
| 通信 | 任务之间传什么？同步几次？ | 快速排序的任务栈 |
| 凝聚 | 任务太小吗？合并到执行体粒度 | 直方图的本地数组 |
| 映射 | 负载均衡吗？通信少吗？ | 4 个线程各一份本地计数 |

## 思考题

1. 17.2 的三角形工作量有 1000 行，4 个线程。块划分和循环划分下每个线程各做多少次迭代？块-循环取 `c=2` 时，最大/最小负载比是多少？

   <details><summary>提示</summary>

   块划分按行切，四份分别是 31375、93875、156375、218875，最大/最小 6.98。循环划分每 4 行取一行，四份都在 12.5 万上下，比是 1.01。`c=2` 也接近 1.01。可以改 `17_2_load_imbalance.cpp` 里的 `ROWS` 和 `P` 验证。

   </details>

2. 17.3 把 `[first,pivot)` / `[pivot,last)` 写成 `[first,pivot]` / `[pivot,last)`。哪个元素会被排序两次？并行时为什么会出现数据竞争，而不是简单的重复排序？

   <details><summary>提示</summary>

   枢轴元素 `a[pivot]` 同时落在两个区间。两个子任务在不同线程上运行，对 `a[pivot]` 的访问没有先行发生关系，至少一个是写，按 C++ 的定义就是数据竞争，结果未定义。TSan 报告里的读、写行号会指向 `partition_range`。

   </details>

3. 17.4 是“读 → 解析 → 计算 → 写”四阶段。哪个阶段适合多开执行体？如果再插入一个“压缩”阶段，应该放在哪里，队列容量怎么定？

   <details><summary>提示</summary>

   先测各阶段耗时，最慢的阶段是瓶颈，给它多开执行体或再拆子阶段；其他阶段加人只会增加排队。队列容量按到达的突发长度和可接受的内存定，跑起来看最大队长和 p99；容量太小会频繁反压，太大则失去背压、内存上涨。

   </details>

4. 17.6 的直方图，桶数从 8 增加到 100 万时，本地数组还合适吗？改用原子计数、分块本地计数，还是每个线程负责一部分桶？

   <details><summary>提示</summary>

   `b × p` 会从 32 个计数涨到几百万个，缓存放不下。原子计数在桶多时写分散、竞争小，桶少时所有线程抢同几个计数器；分块本地计数把桶分成几段，每段一个本地数组，合并时只加有数据的段；每线程负责一部分桶则要把数据项按桶分派，通信量取决于分派方式。先估算 `b × p × 8` 字节，再实测。

   </details>
