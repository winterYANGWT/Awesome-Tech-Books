# 第 36 章 io_uring 与协程

epoll 在 10 万连接上还能跑，但每次读写都要一次系统调用；连接一多，`epoll_wait` 加 `recv`/`send` 的系统调用占比就上去了。io_uring 把提交和完成放进两个环形队列，一次 `io_uring_enter` 可以送一批请求，代价是代码里到处是 `sqe`、`cqe` 和缓冲区生命周期。

再换成 C++20 协程，异步 I/O 看起来像顺序代码，但协程帧可能比它引用的局部变量活得久：

```cpp
std::string text = "local";
asio::co_spawn(ioc, show_later(text), asio::detached);
// start() 返回后 text 已销毁；定时器触发时协程才去读它
```

## 36.1 完成式 I/O：SQ/CQ、提交与收割

{{#fig ch36/sq_cq}}

io_uring（Linux 5.1）在内核和用户之间共享两个环。提交队列 SQ 由用户写、内核读，完成队列 CQ 由内核写、用户读。`io_uring_setup` 的 `entries` 是提示，内核至少给这么多，CQ 默认是 SQ 的两倍。

一次操作分五步：

1. `io_uring_get_sqe` 取一个空位。
2. `io_uring_prep_read/write/accept/recv/send/close/timeout` 填好。
3. `io_uring_submit` 提交。
4. `io_uring_wait_cqe` 或 `io_uring_peek_batch_cqe` 收割。
5. 处理完 `io_uring_cqe_seen` 把槽位还回去。

输出里有三处值得看：

- 四步各自 `submit` 一次，因为例子要看清每一步，真实服务器会把能一起提交的 SQE 攒起来。

和 epoll 的差别在通知的内容。epoll 说“这个 fd 可读”，应用随后调 `read`，数据在 `read` 里才从内核复制到用户缓冲。io_uring 说“这个读已经完成”，复制已经做完，或者已经失败。

完成式模型还带来两件工具。`IOSQE_IO_LINK` 把下一个 SQE 链在当前操作后，前一个失败会让后续以 `-ECANCELED` 结束。批量收割则把很多 CQE 一次取走。

| 模型 | 谁搬数据 | 通知什么 | 每次操作的成本 | 本机是否验证 |
|---|---|---|---|---|
| 阻塞 I/O | 应用在 `read` 里等内核搬 | 无，返回即有数据 | 一次系统调用，等待期间不占 CPU | 验证 |
| 非阻塞 I/O | 应用在成功的那次 `read` 里搬 | 无，应用自己轮询 | 每次尝试一次系统调用 | 验证 |
| epoll | 应用在就绪后的 `read` 里搬 | 就绪 | `epoll_wait` 加每次读写 | 验证（第 32 章） |
| io_uring | 内核搬 | 完成 | SQE/CQE 准备加摊销后的 `io_uring_enter` | 验证（本章） |
| Asio 协程 | 底层仍是 epoll 或 io_uring | 完成回调恢复协程 | 协程帧分配加调度 | 验证（本章） |

限制也要先知道：

- 容器常用的 seccomp 策略可能直接拦掉 `io_uring_setup`。
- `/proc/sys/kernel/io_uring_disabled` 为 2 时全部禁用，为 1 时只有 `CAP_SYS_ADMIN` 或 `io_uring_group` 成员能用。
- 生产代码要在启动时试一次 `io_uring_queue_init`，失败就回退到 epoll。

`SQPOLL` 是另一种交换：内核起一个线程轮询 SQ，应用不用每次 `io_uring_enter`，但空闲时也占 CPU；创建它需要相应权限，权限不够 `io_uring_setup` 返回 `EPERM`。内核线程空闲超过 `sq_thread_idle` 毫秒后会置 `IORING_SQ_NEED_WAKEUP`，应用还得负责唤醒。

> **旧资料提示**：旧教程把 POSIX AIO 的 `aio_read`/`aio_write` 当成内核在后台搬数据。Linux 上 glibc 用用户态辅助线程模拟；内核 AIO（`io_submit`）对普通文件可用，但只有 `O_DIRECT` 文件才保证真异步，buffered 文件可能同步完成，socket 的读写不支持。真正的完成式 I/O 是 io_uring（Linux 5.1 起），细节见 [第 42 章](ch42.md)。

环的行为有两点：

- 环只有 4 个位置，填满后第 5 次 `get_sqe` 返回 `NULL`。
- `submit` 提交了 4 个，再取就成功。

`io_uring_wait_cqe` 等到至少一个完成，`io_uring_peek_cqe` 不进入内核、没有就返回 `-EAGAIN`，`io_uring_peek_batch_cqe` 一次取一批。每个 CQE 处理完都要 `io_uring_cqe_seen`，槽位才会被内核复用。漏掉它，CQ 迟早会满。

CQ 满时要分内核版本：

- 5.5 起的内核带 `IORING_FEAT_NODROP`，完成事件先存在内核里，等用户收割腾出位置再补进来，代价是慢路径。
- 更早的内核会丢 CQE 并增加 `cq.koverflow`。
- 默认 CQ 是 SQ 的两倍，网络负载下可以显式调大 `cq_entries`。

注册能省掉每次操作的固定开销：

- `io_uring_register_files` 把 fd 注册进内核，之后不必再查进程 fd 表、加文件引用。
- `io_uring_register_buffers` 把缓冲区注册进去，省掉每次 I/O 的映射和页引用操作。

注册的缓冲区在注册期间不能释放或移动，否则内核手里就是悬空引用；注册的 fd 则可以关闭，内核已经持有文件引用。

`IOSQE_IO_LINK` 适合 `read → write → close` 这种有依赖的链，不适合互相独立的请求：链会强制串行，内核没法并行或重排。链必须放在同一次 `submit` 里，最后一条不带 link 标志。

`IOSQE_IO_HARDLINK` 与 LINK 的区别只在失败后的行为：链上某一步失败，后续照样执行。需要“无论前一步成败都要尝试”的清理链才用它。

两个持久操作各自只提交一次：

- `arm_accept` 的每个 accept CQE 带回一个新 fd，代码随后为它装一支 multishot recv。
- `arm_recv` 把 `addr` 设为 `NULL`，打开 `IOSQE_BUFFER_SELECT`，再填 buffer group；内核在数据到达时才从缓冲区池里挑一块。

缓冲区有几条规则：

- CQE 的 `flags` 低 16 位是标志；`IORING_CQE_F_BUFFER` 置位时，高 16 位才是 buffer id，用 `flags >> IORING_CQE_BUFFER_SHIFT` 取。
- 缓冲区在 CQE 回来之前不能复用，例子处理完这段数据就立刻把 buffer 加回 ring。
- 池空时 recv 以 `-ENOBUFS` 结束，multishot 也停，要补缓冲后重新装。
- `IORING_OP_PROVIDE_BUFFERS` 把一批缓冲区作为操作提交；5.19 起还可以用 registered pbuf ring 在用户态补环。

背压有两个来源：

- CQ 满时内核进入溢出状态，用户要继续收割。
- 缓冲区耗尽时 recv 停，用户要归还或补充。

## 36.4 C++20 协程：co_await 一个 socket 操作

{{#fig ch36/coro_frames}}

协程三件套是 `promise_type`、awaiter 和 `coroutine_handle`。`promise_type` 决定协程怎么开始、怎么结束、返回值放哪、异常放哪；awaiter 的 `await_ready`、`await_suspend`、`await_resume` 决定一次 `co_await` 怎么挂起和恢复。

```cpp
{{#include code/ch36/36_4_coro_min/task.hpp:promise}}
```

`initial_suspend` 返回 `suspend_always`，协程创建后先挂起，等调用方 `resume`；`final_suspend` 也挂起，调用方还能读 `value`，读完由 `task` 的析构函数销毁帧；`unhandled_exception` 把异常存进 `exception_ptr`，不能吞掉。

`co_await` 先问 `await_ready`。返回 false 就把当前协程的 handle 交给 `await_suspend`，它可以返回三种值：

- `void`：挂起后由别人恢复。
- `bool`：false 表示不挂起，继续执行。
- 另一个 `coroutine_handle`：对称转移，直接跳到那个协程。

恢复在哪个线程由 executor 决定，语言本身不创建线程。

```cpp

```

这个 awaiter 只做两件事：

- `await_suspend` 把 handle 和到期时间放进单线程的定时器队列。
- `run_one_timer` 睡到最早的时间，再 `resume` 对应的协程。

临时 awaiter 的寿命要记清：

- `co_await timer_awaiter{100ms}` 里的临时对象活到整个 `co_await` 全表达式结束，`await_resume` 返回后才销毁；挂起期间它一直在协程帧里。
- 但 `co_await` 结束后它就没了：可以在这个全表达式内（包括挂起期间）通过引用或指针用它，不能把这样的引用留到 `co_await` 之后；需要更久的值在挂起前拷进队列或协程帧。

Asio 把这一套包装成 `boost::asio::awaitable<T>`。`co_spawn(ioc, coro(), token)` 启动协程，`use_awaitable` 把 `async_read`、`async_write`、`steady_timer::async_wait` 变成可 `co_await` 的操作，`this_coro::executor` 取当前协程的 executor。Boost 1.90 的 Asio 是 header-only，链接只需 `-pthread`。

异常由协程体的 `unhandled_exception` 保存，`co_spawn` 的完成处理器再取走。`detached` 的处理器什么都不做，异常会被丢掉；要在乎异常，就挂一个真正的完成处理器，或在协程体里 catch。

同一连接的回调不能并发：

- 例子给每个连接建一个 strand，`async_accept` 时就把新 socket 绑到这个 strand 上。

- 连接状态只在 strand 里改，就不需要额外的锁。

协程帧的成本来自几处：

- 每个连接一个帧，连接数很高时分配和缓存压力不能忽略。
- 可以在 `promise_type` 里自定义 `operator new`。Boost.Asio 的 `awaitable` 已经这样做了：协程帧从每个线程的回收缓存里分配，用完放回缓存（`boost/asio/impl/awaitable.hpp`）。
- 这不改变“每个连接仍然占一个帧”的事实，只是把分配从通用堆换成池。

`co_spawn(..., detached)` 后帧由 Asio 管理，协程结束时销毁；如果用 `co_spawn` 的完成处理器，处理器拿到 `exception_ptr` 或结果。不要在协程体里保存 `this` 或引用而不保证对象活到协程结束，这正是 36.4 反例的另一种形式。

{{#fig ch36/coro_vs_callback}}

回调版把同一件事拆成 `on_read`、`on_write` 两个状态；协程版是一条顺序流程。解析器和 `Store` 完全相同，差别只在 I/O 层：前者要维护“现在该读还是该写”，后者由 `co_await` 的位置决定。

系统调用数差别更明显：

```text
{{#include code/ch36/36_6_uring_vs_epoll/syscalls.out}}
```

两版的系统调用花在不同地方：

- epoll 版每批数据都要 `recv` 和 `send`，事件循环还要 `epoll_wait`。
- io_uring 版把这些压进少量 `io_uring_enter`，系统调用数少几倍。

系统调用少不等于吞吐高。请求小、连接少、回环延迟低时，SQE/CQE 的准备和收割本身也是成本。三组连接数只用于看趋势，绝对值不要和其他机器或内核版本比，两版的源码都在 `36_6_uring_vs_epoll/` 里可以改参数重跑。

读图时先看系统调用数的比例，再看吞吐和 P99。如果系统调用数降了而吞吐没升，说明瓶颈不在内核入口，而在用户态的准备、解析或拷贝。

什么时候值得用 io_uring：

- 高 IOPS、大批量提交、少拷贝，尤其是磁盘 I/O 和 `O_DIRECT`。
- 需要链式操作、multishot、provided buffers，减少重复提交。
- 能控制内核版本和容器策略，确认 `io_uring_setup` 可用。

什么时候 epoll 更稳：

- 连接数和请求率都不高，epoll 的代码和调试工具更成熟。
- 容器 seccomp 禁用 io_uring，或内核版本低于需要的特性。
- 内核低于 5.19 时 multishot accept 和 pbuf ring 不可用，只能退回 one-shot 提交，或直接用 epoll。
- 团队没有精力维护 SQE/CQE 和缓冲区生命周期。

`SQPOLL` 用 CPU 换系统调用，空闲时也占一个内核线程；只有在持续高负载、且能接受这个 CPU 开销时才考虑。

协程也不是零成本：

- 帧分配、调度、调试栈不直观。
- 协程不创建线程，CPU 密集任务仍然要交给线程池。
- 协程跑在线程上，`strand` 只是保证同一连接不被两个线程同时碰。

`std::stop_token` 能做线程间的协作停止，但它不替代 socket 的取消；Asio 的 `cancellation_slot` 才接在挂起的 I/O 操作上。

C++26 的 `std::execution`（sender/receiver，P2300）提供组合和调度抽象，但不提供 I/O 后端：

```cpp
// C++26，本书环境（GCC 15 / Clang 21）尚未实现，未编译验证
namespace ex = std::execution;
auto work = ex::when_all(
    ex::schedule(ex::get_parallel_scheduler()) | ex::then([]{ /* 任务 A */ }),
    ex::schedule(ex::get_parallel_scheduler()) | ex::then([]{ /* 任务 B */ }));
std::this_thread::sync_wait(std::move(work));
```

它组合的是“尚未开始的工作”，调度由 scheduler 决定；socket 的完成事件仍要 epoll、io_uring 或 Asio 提供。libstdc++ 15 没有可用实现，这里只介绍，不编译。

- **回退**：启动时探测 `io_uring_queue_init` 的返回值，失败就用第 32、33 章的 epoll 事件循环。
- **基准**：固定连接数、请求大小、读写比，比较系统调用数、吞吐、P99 和 CPU，不要跨机器比绝对值。

> **旧资料提示**：epoll 的就绪模型加回调链，可以换成 io_uring 的完成模型，或者换成 Asio 协程的顺序写法；前者在 [42.5 节](ch42.md) 里作为“旧写法为什么被取代”重讲，后者见 [36.5 节](ch36.md) 和 [39.7 节](ch39.md)。

> **旧资料提示**：回调式异步不是唯一写法。C++20 起可以用 `co_await` 把回调写成顺序代码，Asio 的 `awaitable` 是现成的一条路；标准库本身仍没有 socket 的 awaitable，见 [第 39 章](ch39.md)。

## 速查

| 接口或写法 | 作用 | 生命周期/版本注意 |
|---|---|---|
| `io_uring_queue_init(entries, &ring, flags)` | 建 SQ/CQ 并映射 | 成功返回 0，失败返回负 `errno`；`entries` 是提示，CQ 默认两倍 |
| `io_uring_queue_exit` | 释放环 | 退出前收完或取消在途请求 |
| `io_uring_get_sqe` | 取一个 SQE 空位 | SQ 满返回 `NULL`，先 `submit` 再取，不能对 `NULL` prep |
| `io_uring_prep_read/write/accept/recv/send/close/timeout` | 填 SQE | 操作数指向的缓冲区要活到 CQE 回来 |
| `io_uring_submit` | 提交已填的 SQE | 返回提交数；SQPOLL 下返回值可能偏大 |
| `io_uring_submit_and_wait(ring, n)` | 提交并等 n 个完成 | 返回提交数，不是完成结果 |
| `io_uring_wait_cqe` | 等至少一个完成 | 返回 0 或负 `errno`，和 `cqe->res` 无关 |
| `io_uring_peek_cqe` / `peek_batch_cqe` | 非阻塞取完成 | 没事件返回 `-EAGAIN` 或 0 个；溢出时会进内核 |
| `io_uring_cqe_seen` | 标记 CQE 已消费 | 每个 CQE 都要调用，否则槽位不回收 |
| `cqe->res` / `user_data` | 结果 / 关联请求 | `res` 是字节数或负 `errno`；`user_data` 由用户填 |
| `IOSQE_IO_LINK` | 把下一个 SQE 链在当前操作后 | 前一个失败后续 `-ECANCELED`；链必须在同一次提交 |
| `io_uring_register_files/buffers` | 注册 fd / 缓冲区 | 缓冲区注册期间不能释放或移动；fd 注册后内核持有引用 |
| `io_uring_setup_buf_ring` + `IOSQE_BUFFER_SELECT` | provided buffer ring | 5.19 起；`IORING_CQE_F_BUFFER` 置位时 flags 高 16 位是 bid，CQE 回来前不能复用 |
| `io_uring_prep_multishot_accept/recv_multishot` | 一次提交多次完成 | accept 5.19 起，recv 6.0 起；看 `IORING_CQE_F_MORE` |
| `co_await` / `co_spawn` / `awaitable` / `use_awaitable` | 协程和 Asio 包装 | 恢复线程由 executor 决定；引用捕获要保证活到恢复 |
| `cancellation_slot` / `cancellation_signal` | 取消挂起的异步操作 | `terminal` 让操作以 `operation_aborted` 结束 |
| `std::execution` 的 sender/receiver | 组合和调度 | C++26，无 I/O 后端；libstdc++ 15 未实现，未编译验证 |

## 思考题

1. （预测）36.2 的 `36_2_uring_batch.c` 一次提交 64 个读，但只对 32 个 CQE 调 `cqe_seen`，下一次 `io_uring_wait_cqe` 会怎样？CQ 满了会阻塞谁？

   <details><summary>提示</summary>

   已经躺在 CQ 里的 32 个完成事件仍然能被 `wait_cqe` 取到，所以它不会因为“没 seen”而立刻阻塞。继续产生完成事件而 CQ 没有空位时，带 `IORING_FEAT_NODROP` 的内核把事件存进溢出链表，等 `cqe_seen` 腾出槽位再补；更早的内核会丢 CQE 并增加 `cq.koverflow`。CQ 满不会阻塞内核线程，阻塞的是等完成的应用。

   </details>

2. （找错）36.4 的 `36_4_coro_dangling.cpp` 如果把引用捕获改成值捕获，崩溃会消失吗？协程帧里还有哪些对象可能比连接活得久？

   <details><summary>提示</summary>

   值捕获会把 `std::string` 拷进协程帧，帧活到协程结束，所以这个反例会消失。但协程帧里保存的迭代器、`string_view`、指向连接对象的 `this`、以及指向 `co_await` 临时 awaiter 成员的引用（它在全表达式结束后销毁），都可能比它们指向的对象活得久。关键是让对象的生命周期覆盖整个协程，或者用 `shared_ptr` 明确共享所有权。

   </details>

3. （权衡）什么时候用 io_uring、什么时候用 epoll 加线程池？把“连接数、请求大小、系统调用占比、容器限制”列成判据。

   <details><summary>提示</summary>

   连接多、请求小、系统调用占比高时，io_uring 的批量提交和完成队列收益最大；请求大、连接少、CPU 是瓶颈时，epoll 加线程池更简单。容器 seccomp 禁用 io_uring、内核版本不够、或需要大量现成调试工具时，epoll 是更稳的选择。先用 `kvbench` 固定参数测系统调用数和 P99，再决定。

   </details>

4. （迁移）把 36.5 的 `kvd_coro` 改成多线程 `io_context`：`strand` 要加在哪一层？关闭时怎样保证协程不会在对象销毁后恢复？

   <details><summary>提示</summary>

   每个连接一个 strand，并在 `async_accept` 时就把新 socket 绑到该 strand；连接状态只在 strand 里改。关闭时先停 accept，再对每个连接发取消，等所有协程退出、`io_context` 排空后才销毁连接表和 `Store`。不要只 `stop()` 就析构 `io_context`，挂起的操作和协程帧还在。

   </details>
