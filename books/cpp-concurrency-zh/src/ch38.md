# 第 38 章 内存模型是怎么来的：`volatile`、双重检查锁、`consume` 与回收

一个懒初始化单例偶尔崩溃：线程 B 读到了非空指针，对象的字段却还是未初始化的值。编译器不报错，ThreadSanitizer 也可能只给出半份答案，因为那个指针是普通变量。

这一章从这段代码往回看：`volatile` 为什么不是同步，双重检查锁错在哪，原子变量的初始化和能力边界，`consume` 为什么被放弃，以及标准 GC 删除后无锁内存怎么回收。

## 38.1 `volatile` 不是同步

**旧写法**：一个 `volatile int ready` 当门铃，生产者先写 `data`，再写 `ready = 1`；消费者 `while (!ready) {}`，然后读 `data`。旧教程说 `volatile` 让编译器每次都去内存读，所以“跨线程能看见”。

**当时为什么这样写**：C++11 之前标准不承认线程，也没有内存模型，编译器按单线程假设优化；多线程只能靠平台库，这是“线程不能做成库”的根源。`volatile` 至少保证访问不被删掉、按抽象机的顺序发生，看起来像同步。

**问题在哪**：它不保证原子性、不建立 happens-before、也不阻止 CPU 重排。C++11/C11 起，两个线程对同一非原子对象的并发访问（至少一个写）是 data race，属于未定义行为；`-O0` 只是让错误暂时不出现。

```cpp
std::atomic<int> data{0};
std::atomic<bool> ready{false};

// 生产者
data.store(42, std::memory_order_relaxed);
ready.store(true, std::memory_order_release);

// 消费者
while (!ready.load(std::memory_order_acquire)) {}
int x = data.load(std::memory_order_relaxed);
```

**今天还用得着吗**：`volatile` 仍用于 MMIO（内存映射 I/O）和信号标志，它不是线程同步。`volatile sig_atomic_t` 是另一条规则，C 标准保证信号处理函数能原子访问它，但不能把这个结论类推到线程。

## 38.2 双重检查锁 → 局部 `static` 与 `call_once`

**旧写法**：先读普通指针判空，加锁后再判空，`new` 之后赋值：

```cpp
Singleton* instance = nullptr;
std::mutex init_mutex;

Singleton* get() {
    if (instance == nullptr) {                 // 第一次检查，锁外
        std::lock_guard<std::mutex> lock(init_mutex);
        if (instance == nullptr) {             // 第二次检查，锁内
            instance = new Singleton();
        }
    }
    return instance;
}
```

**当时为什么这样写**：每次调用都加锁太贵，第一次检查让已初始化的快路径完全无锁；第二次检查防止两个线程同时构造。C++11 之前局部 `static` 的线程安全没有标准保证，旧代码只能自己写这套双重检查锁（double-checked locking pattern，DCLP）。

**问题在哪**：“分配”“构造”“赋值”之间没有同步。另一个线程可能在赋值之后、构造完成之前读到非空指针，看到半构造对象；普通指针的读和写本身也构成 data race。

## 38.3 原子变量的初始化：`ATOMIC_VAR_INIT`、`ATOMIC_FLAG_INIT`、默认构造

**旧写法**：`std::atomic<int> a = ATOMIC_VAR_INIT(0);`、`atomic_init(&a, 0)`、`std::atomic_flag f = ATOMIC_FLAG_INIT;`。块作用域的 `std::atomic<int> a;` 在 C++17 及以前值不确定，必须先初始化。

**当时为什么这样写**：`atomic<T>` 不可拷贝、不可赋值，默认构造在旧标准里不保证给值；`ATOMIC_VAR_INIT` 用于静态存储期的常量初始化，`atomic_init` 用于还没初始化的对象，`ATOMIC_FLAG_INIT` 是 `atomic_flag` 唯一可靠的初始化方式。

**问题在哪**：C++20 起 `ATOMIC_VAR_INIT` 和 `atomic_init` 被弃用，`atomic<T>` 的默认构造改为值初始化 `T()`，块作用域的 `std::atomic<int> a;` 现在是 0。`std::atomic_flag` 默认构造即 clear，`test()` 和 `wait`/`notify` 也都是 C++20；`atomic_init` 只该用于还没初始化的对象，不能拿它给已构造的原子对象“重新赋值”。

| 写法 | C++17 | C++20 |
|---|---|---|
| `std::atomic<int> a;`（块作用域） | 值不确定 | 0 |
| `std::atomic_flag f;` | 需要 `ATOMIC_FLAG_INIT` | clear |
| `ATOMIC_VAR_INIT` / `atomic_init` | 可用 | 弃用 |

## 38.4 原子类型的能力与边界：无锁、浮点、16 字节、缺的运算

**旧写法**：把 `std::atomic<T>` 当成“一定无锁”，把 16 字节结构体直接塞进 `atomic`；浮点用互斥量保护；最大值、最小值、除法都用一把锁或自己写循环。

**当时为什么这样写**：C++11 里只有 `atomic_flag` 明确保证无锁，其他 `atomic<T>` 可能内部用锁；`is_lock_free()` 只能运行时查，`is_always_lock_free` 到 C++17 才有；浮点原子算术到 C++20 才加入。

**问题在哪**：`is_lock_free()` 可能返回 false，尤其 16 字节结构体；`compare_exchange` 按值表示比较，`+0.0`/`-0.0` 的表示不同会被判不等，NaN 同样的位模式却可以相等。整型原子仍没有除法、乘法和移位，只能用 CAS 循环。

| `atomic<shared_ptr>` | 无，只有非成员函数 | 有；标准不保证无锁 | 有 | 无 |
| `fetch_max`/`fetch_min` | 无 | 无 | 有；本机未实现 | 无 |
| `memory_order_consume` | 有（语义很弱） | 有 | 弃用，等同 `acquire` | 有 |

## 38.5 忙等 → `atomic::wait`/`notify`

**旧写法**：`while (v.load() == old) std::this_thread::yield();`，或者每轮 `sleep_for` 一小段时间再查。

**当时为什么这样写**：C++11/17 没有原子量上的阻塞等待；条件变量要配互斥量和谓词，只等一个标志时显得重。空循环或 `yield` 至少不用建条件变量。

**问题在哪**：空循环一直占 CPU，`yield` 只是让出时间片、不保证对方能前进，`sleep` 又把等待时间写死，短了浪费延迟，长了浪费响应。C++20 的 `atomic::wait` 把“等一个值变化”交给内核的等待队列。

Linux 上 libstdc++ 通常落到 `futex(2)`；4 字节标量可以直接等在那个字上，其他类型用等待表，所以 `atomic<T>` 不要求刚好 4 字节，但也不保证无锁。

**今天还用得着吗**：`atomic::wait` 适合“等一个值变化”的一对一/多对一场景；线程池的空队列仍用 `counting_semaphore` 或条件变量，因为要等的是“队列非空”这个复合条件，不是单个原子值。

## 38.6 `shared_ptr` 的原子访问：非成员函数 → `atomic<shared_ptr>`

**旧写法**：`std::atomic_load(&sp)`、`std::atomic_store(&sp, p)`、`std::atomic_exchange`、`std::atomic_compare_exchange_strong`/`weak`，参数是 `shared_ptr<T>*`。Concurrency TS 还提出过 `std::experimental::atomic_shared_ptr<T>`。

**当时为什么这样写**：并发拷贝同一个 `shared_ptr` 是安全的，引用计数是原子的。不安全的是一个线程拷贝或读、另一个线程同时给同一个 `shared_ptr` 赋值或 `reset`，那是对同一个对象的 data race；C++11 只给了这组非成员函数，要求所有访问都经过它，TS 则承诺一个可无锁的原子 `shared_ptr`。

**问题在哪**：非成员函数写法别扭，容易和 `atomic<T>` 的成员函数混，C++20 起弃用，C++26 草案已移除。标准版的 `std::atomic<std::shared_ptr<T>>` 不保证无锁，本机 libstdc++ 15 的 `is_lock_free()` 是 false，TS 的 `atomic_shared_ptr` 也没有进标准；libstdc++ 15 还保留旧的非成员重载，但会给弃用警告。

| 写法 | 版本 | 无锁 |
|---|---|---|
| 非成员 `atomic_load(&sp)` | C++11；C++20 弃用 | 实现决定 |
| `std::atomic<std::shared_ptr<T>>` | C++20 | 不保证 |

## 38.7 `memory_order_consume` 与 `kill_dependency`

**旧写法**：发布一个 `Data*` 时用 `release` store，读者用 `memory_order_consume` 读指针，再读 `p->x`；需要切断依赖链时用 `std::kill_dependency(p)`。

**当时为什么这样写**：`consume` 想表达比 `acquire` 更弱的“数据依赖”序：只保证顺着指针依赖读到的东西可见，不保证无关变量。若硬件能只靠地址依赖排序，可能比 `acquire` 便宜。

**问题在哪**：编译器很难可靠实现依赖链，GCC/Clang 实际上一直把 `consume` 当 `acquire`，`kill_dependency` 也基本无效。C++26（P3475R2）把 `consume` 按 `acquire` 处理并放进弃用清单，新代码不应再写。

## 38.8 标准 GC 被移除，风险指针与 RCU 进入 C++26

**旧写法**：用 C++11 的“最小垃圾回收支持”——`std::declare_reachable`、`std::pointer_safety`、`std::get_pointer_safety`；无锁结构里干脆不回收节点，靠“程序退出时一起释放”或可选的 GC。

**当时为什么这样写**：C++11 只给了很小的 GC 接口，实际回收器要另外装；无锁 `pop` 一旦删除节点，另一个线程可能还在解引用，所以最初的版本故意泄露节点，等有 GC 再说。

**问题在哪**：C++23（P2186R2）移除了标准里的 GC 接口，`std::pointer_safety` 在 C++23 起不存在；泄露节点也不是回收方案，长时间运行会把内存吃光。`shared_ptr` 能管生命周期，但 `atomic<shared_ptr>` 在本机不是无锁的，不能替代无锁回收。

同一段代码在 C++20 下能编译，换到 C++23 就找不到 `std::pointer_safety`。标准 GC 的移除不代表“不用回收”，只代表标准不再提供这套接口。

**取代它的**：C++26 加入 `<hazard_pointer>`（P2530R3）和 `<rcu>`。风险指针在解引用前登记，删除线程扫描所有登记，没人指向才释放，RCU 则让读者在宽限期内继续读、写者延迟释放；本机 libstdc++ 15 没有这两个头文件，下面只写片段，未编译验证。

```cpp
// C++26，本书环境未实现，未编译验证
struct Node : std::hazard_pointer_obj_base<Node> {
    int value;
    Node* next;
};
std::atomic<Node*> head;
void reader() {
    std::hazard_pointer h = std::make_hazard_pointer();
    Node* p = h.protect(head);
    use(p->value);   // h 活着，p 不会被回收
}
```

```cpp
// C++26，本书环境未实现，未编译验证
struct Config : std::rcu_obj_base<Config> { int value; };
std::atomic<Config*> current;
void reader() {
    std::scoped_lock<std::rcu_domain> rcu(std::rcu_default_domain());
    Config* c = current.load(std::memory_order_acquire);
    use(c->value);
}
void update(Config* next) {
    Config* old = current.exchange(next);
    old->retire();
}
```

- 风险指针：`std::hazard_pointer`、`make_hazard_pointer()`、`protect()`、`try_protect()`、`hazard_pointer_obj_base<T>::retire()`。
- RCU：`rcu_obj_base`、`rcu_retire`、`rcu_synchronize`、`rcu_barrier`、`rcu_default_domain()`。

**今天还用得着吗**：先用 `shared_ptr` 加锁，确认瓶颈后再上风险指针/RCU，并用 ASan/TSan 验证。标准 GC 已经不在，`atomic<shared_ptr>` 又不是无锁的；需要无锁读、低频写的链表或配置表，风险指针和 RCU 是标准给出的方向。

## 速查

| 旧写法 | 取代它的 | 从哪个版本起 | 本书在哪讲 |
|---|---|---|---|
| `volatile` 忙等当同步 | `std::atomic` + release/acquire；`atomic::wait` | C++11 / C++20 | 38.1、38.5 |
| 双重检查锁 | 局部 `static` / `std::call_once` | C++11 | 38.2 |
| `ATOMIC_VAR_INIT`/`atomic_init` | 默认构造、显式初值 | C++20 | 38.3 |
| `atomic_load(shared_ptr*)` | `std::atomic<std::shared_ptr<T>>` | C++20 | 38.6 |
| `memory_order_consume` | `memory_order_acquire` | C++26 弃用 | 38.7 |
| 标准 GC 接口 | 风险指针 / RCU | C++26（本机未实现） | 38.8 |

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `std::atomic<T>` | 原子读写和读-改-写 | 不可拷贝；默认构造 C++20 起值初始化 |
| `atomic_flag` | 最小原子标志 | C++20 默认 clear；`test`/`wait` 是 C++20 |
| `atomic_ref<T>` | 给普通对象加原子访问 | 对齐、所有访问都走它 |
| `is_lock_free()` / `is_always_lock_free` | 查是否无锁 | 运行时/编译期，结果随平台和选项变 |
| `memory_order_relaxed/acquire/release/acq_rel/seq_cst/consume` | 内存序 | `consume` 在 C++26 等同 `acquire` |
| `wait`/`notify_one`/`notify_all` | 原子量上的阻塞等待 | 允许虚假唤醒；没有超时版本 |
| `std::call_once`/`std::once_flag` | 一次性初始化 | 函数抛异常时 flag 不置位 |
| `std::hazard_pointer`/`std::rcu_obj_base` | C++26 回收设施 | 本机未实现，未编译验证 |

## 思考题

1. 把 38.1 的 `volatile int ready` 换成 `std::atomic<int>`，但生产者和消费者都只用 `memory_order_relaxed`，消费者能看到 `data` 吗？

   <details><summary>提示</summary>

   不能保证。`relaxed` 只保证这个原子量自身的修改顺序，不建立跨线程的先行发生关系；`data` 仍是普通变量时，读写它仍是 data race。要让 `data` 可见，至少把 `ready` 的写改成 release、读改成 acquire，或者把 `data` 也做成原子并参与同一对同步。

   </details>

2. 38.2 的双重检查锁里，哪个写和哪个读之间缺少 happens-before？如果只把 `instance` 改成 `std::atomic<Singleton*>`，`constructed` 的读就安全了吗？

   <details><summary>提示</summary>

   正文这段 `instance = new Singleton()` 在构造完成后才发布，把指针改成默认 `seq_cst` 的 `std::atomic`，store 和 load 就建立 release/acquire，字段可见；锁外读与锁内写之间的数据竞争也消失。但 38_2 的示例把 `instance = this` 提前到构造完成之前，这时任何内存序都不够，必须先把发布移到字段写完之后。

   </details>

3. `std::atomic<std::shared_ptr<T>>` 的 `is_lock_free()` 为 false 时，一个读多写少的配置表还值得用它吗？

   <details><summary>提示</summary>

   要看读的开销和竞争程度。它虽然内部用锁，但每次 `load` 只锁一小段、返回一个 `shared_ptr`，读多写少时通常比“每次读都拿一把大互斥量”伸缩性好；如果读线程非常多、写很少，锁仍可能成为瓶颈，这时风险指针或 RCU 更合适。先测量，再决定是否值得换成无锁回收。

   </details>

4. 把 38.4 的 `atomic_raise`（CAS 求最大值）改写成 C++26 的 `fetch_max`；`atomic_halve` 的除法有对应的 `fetch_*` 吗？本机编译不了时怎么验证逻辑？

   <details><summary>提示</summary>

   除法没有对应的 `fetch_*`（`fetch_max`/`fetch_min` 只求极值），仍要 CAS 循环。`fetch_max` 可以先用 `compare_exchange_weak` 写参考实现（本章的 `atomic_raise` 就是），把语义定义成“循环 CAS 直到当前值不小于目标值”；再用随机输入、边界值（相等、小于、大于）和并发线程对拍。等有支持 C++26 的编译器时，只替换实现、保留测试，输出应逐位一致。

   </details>
