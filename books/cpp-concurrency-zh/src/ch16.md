# 第 16 章 无锁结构的内存回收：风险指针、引用计数、epoch 与 RCU

第 15 章的 pop 能正确换掉 `head`，但节点一 `delete`，另一个线程手里的指针就悬空。不 `delete`，内存一直涨。窗口只有两行：

```cpp
Node* old = head.load();
Node* next = old->next;
if (head.compare_exchange_weak(old, next)) {
    delete old;
}
```

回收问题不是“记得释放”，而是“怎么知道最后一个读者已经走了”。三类答案：让读者发布地址、给节点计数、按时间段划分读者。

- 数据：由 `shared_ptr<T>` 管，最后一个持有者离开才释放；
- 裸指针 `old_head`：只是读线程的临时值，没有任何生命周期保证。

- 风险指针：读者把自己正在读的地址写进一个槽，删除者扫描槽，没人指向才删；
- 引用计数：节点自己记着还有几个引用，最后一个引用离开时删；
- epoch/RCU：读者进入临界区时记下时间段，写者等所有旧时间段的读者离开再删。

回收协议不能靠“线程不会那么巧被挂起”来保证。ASan 能抓住实际发生的释放后使用，压力测试能放大窗口，模型检查器能枚举交错。本机没有 CDSChecker、GenMC，本章的协议只用 ASan、TSan 和压力循环验证。

示例是教学实现，不是工业级库。生产环境优先用成熟库或标准设施：

- Folly 的 hazptr：风险指针的工业实现；
- liburcu：用户态 RCU；
- C++26 的 `<hazard_pointer>`、`<rcu>`：本机尚未实现。

- 这一版只回收节点，不回收数据：示例把 `shared_ptr<int>` 从节点里 `move` 出来，节点被删时它持有的 `shared_ptr` 才释放；
- 如果数据必须比节点活得久，就让别的对象持有它；
- 回收方案要先说清“回收的是节点还是数据”，两者的生命周期可能不同。

还有两个实现上的坑：

- 待删链用单独的 `retire_next`，不复用 `next`：读者可能正在读 `Y->next`，回收线程却把 `Y->next` 改成链指针，这本身就是数据竞争；
- `threads_in_pop` 是原子变量，但“计数为 1”不等于“没有别的读者”：新读者可能在判断之后进入，所以这个方案能讲清延迟回收，不能上线；
- 高负载下待删链无限增长，最后还是回到“谁来回收、什么时候回收”；
- 回收时机要和“节点是否复用”一起定：只泄露、不删除也不复用，能避开 ABA，但内存会一直涨；
- 判断和摘链没有放在同一把锁里，靠的是摘链后的第二次检查；新进入的线程看不到链上的节点，这个论证只对当前结构成立。

## 16.3 风险指针：每个线程发布自己在读的地址

每个线程有一个风险指针（hazard pointer）槽。读到 `old_head` 后，先把槽设成 `old_head`，再重读 `head` 确认它没变。确认之后才解引用。

{{#fig ch16/hazard_protocol}}

看第 2、3 步：先发布 `hp=A`，再重读 `head`。顺序不能反。如果先重读、再发布，另一个线程可能在你重读之后、发布之前把 A 删掉，你发布的已经是一个悬空地址。

- 发布：把候选地址写进自己的槽；
- 重读：确认 `head` 还是它；
- 解引用：只有确认之后才读 `next`。

`protect_head()` 是协议的核心：`t_hp.set(p)` 发布，`g_head.load() == p` 确认。不相等就清空槽、重读、重试。删除线程扫描所有槽，没人指向该节点才 `delete`，否则挂到待回收链稍后再试。

- 程序自己统计的存活节点是 0，ASan/UBSan 无报告，TSan 无报告；
- 每次回收是 O(待回收节点数 × 槽数)，示例每 64 个退休节点扫一次；
- 槽表固定 16 个，表满时要么扩容、要么抛异常；
- 每个线程退出时要归还槽，示例用 `thread_local` 的 RAII 对象做这件事；
- 槽表大小要按最大线程数配；线程数超过槽数时，新线程拿不到槽，必须扩容或让创建失败；
- 示例用 `seq_cst` 把顺序写清楚。风险指针的发布和重读也是先写后读：发布 `hp` 用 release、重读 `head` 用 acquire 不够，存储缓冲区会让两边都读到旧值；要么都用 `seq_cst`，要么用非对称栅栏（发布侧轻、回收侧重）再逐条论证。

C++26 把风险指针纳入标准（`<hazard_pointer>`，P2530R3），接口大致是这样：

```cpp
struct Name : std::hazard_pointer_obj_base<Name> { /* ... */ };
std::atomic<Name*> name;

void print_name() {
    std::hazard_pointer h = std::make_hazard_pointer();
    Name* p = h.protect(name);   // 保护期开始，*p 可安全访问
}

void update_name(Name* n) {
    Name* old = name.exchange(n);
    old->retire();               // 交给标准库延迟回收
}
```

| 接口 | 作用 |
|---|---|
| `make_hazard_pointer()` | 取得一个 `std::hazard_pointer` |
| `h.protect(head)` | 发布保护并返回可安全解引用的指针 |
| `obj->retire()` | 把对象交给标准库延迟回收 |

- C++26 本机 GCC 15.2 / Clang 21 没有 `<hazard_pointer>`，未编译验证，`__has_include` 为假；
- 旧教程的 `HpOwner operator=(const HpOwner&)=delete;` 返回类型写成 `HpOwner` 而不是 `HpOwner&`，能编译但不符合赋值运算符的惯例；
- 风险指针不要求双字 CAS，代价是每次 pop 都可能扫描整张表和整条待回收链。

## 16.4 引用计数：把计数塞进指针

分离引用计数把“外部计数”和指针放进同一个结构体，把“内部计数”放进节点。读指针前先给外部计数加一，保证解引用期间节点不会被删。释放时把外部计数并入内部计数，两个计数都归零才 `delete`。

{{#fig ch16/refcount_states}}

看第 2、3 步：T1、T2 各读一次 `head`，外部计数从 1 加到 3。第 4 步 T1 弹出 A，`head` 改指 B（B 的外部计数是 1），把 `ext-2=1` 并入 A 的内部计数。

- 外部计数：跟着指针走，读之前先加一；
- 内部计数：跟着节点走，外部引用转进来后在这里归零。

减 2 是因为 head 的那次引用没了，T1 自己的引用也在弹出时消失，剩下的 1 属于 T2。第 5 步是反例：A 的内部计数还是 1，立刻删会让 T2 访问已释放节点；第 6 步 T2 的 CAS 失败、释放引用，内部计数归零，第 7 步才删。

- GCC 15.2：加不加 `-mcx16` 都是 `is_lock_free()==false`；

位宽是取舍，不是标准规定：

| 字段 | 示例宽度 | 约束 |
|---|---|---|
| 外部计数 | `int` | 至少要能容纳同时读 `head` 的线程数 |
| 内部计数 | `int` | 所有外部引用转进来后不能回绕 |
| 指针 | 平台指针宽度 | 和外部计数一起放进 16 字节结构体（64 位） |

- 位宽：外部计数用完整 `int`，2 位只够 0–3，8 个线程不够；把内部计数压进 30 位、外部计数压进 2 位，是队列 tail 的技巧，不能直接搬；
- 溢出：增加前检查 `INT_MAX`，内部计数也要检查，不能静默回绕；
- ABA：每次改 `head` 都改计数，CAS 不会看到完全相同的旧值，前提是计数没回绕。

## 16.5 epoch 与 RCU：让读者不等待

epoch 回收把时间分成一段段。读者进入临界区时记下当前 epoch，写者删除节点后等到“所有可能持有旧 epoch 的读者都离开”再释放。

读者不等待，遍历期间不写被保护的数据结构。进入和离开时只写自己的槽和 `active`，只有写者承担等待。

{{#fig ch16/epoch}}

看第 6、7 步：读者 1 离开还不够，读者 2 也离开，最后一个旧 epoch 的读者走了。第 8 步写者才释放 X，读者全程没有等待；第 4、5 步里写者每退休一个节点都把全局 epoch 加一，所以 X 要等到 epoch 到 7。

读者侧只有三件事：

- 进入时读全局 epoch，写自己的槽；
- 遍历期间不写共享状态；
- 离开时清 `active`。

`enter()` 先读全局 epoch、写自己的槽，再把 `active` 置真，`leave()` 只清 `active`。读者是“先写 `active`、再读 `head`”，写者是“先改 `head`、再读 `active`”，这是先写后读的 Dekker 模式。release/acquire 不够，存储缓冲区会让两边都读到旧值，所以 `active`、`head` 和读者槽里的 `epoch` 都用 `seq_cst`。

写者退休节点时记下当时的 epoch，等 `g_epoch >= retire_epoch + 2` 并且 `grace_passed()` 为真才删。读者只是遍历，写者等；4 个读者和 1 个写者跑完，写者释放了 10000 个节点，栈为空。

- 一个慢读者会把所有人的宽限期拖住：只要还有一个读者停在旧 epoch，写者就不能释放这段时间删除的节点；
- 读者阻塞得越久，回收延迟越长，写者占用的内存越多；
- 延迟由读者的停留时间决定，不是固定开销；最慢的那个读者决定宽限期，其他读者早走也没用。

RCU（read-copy update）是 epoch 思路的成熟形态。读侧 `rcu_read_lock`/`rcu_read_unlock` 几乎不花钱，写侧用 `synchronize_rcu` 等一个宽限期，或用 `call_rcu` 延迟回调。Linux 内核大量使用，用户态可以用 liburcu 这类库。

- 读侧：进入和离开临界区几乎只是编译器屏障，不能睡眠，也不能调用可能阻塞的函数；
- 写侧：`synchronize_rcu` 要等宽限期，`call_rcu` 把回调排队；
- 内存：旧节点在宽限期内不能复用。

C++26 把 RCU 纳入标准（`<rcu>`）：

```cpp
std::rcu_domain& dom = std::rcu_default_domain();
{
    std::scoped_lock<std::rcu_domain> rlock(dom);  // 读侧临界区
    // 访问受保护的节点
}
std::rcu_synchronize();   // 等一个宽限期
std::rcu_retire(p);       // 或把释放安排到宽限期之后
```

C++26，本机 GCC 15.2 / Clang 21 没有 `<rcu>`，未编译验证。liburcu 本机也没有安装，未编译验证。标准里还有 `rcu_obj_base<T, D>`、`rcu_barrier()` 等设施，名字见 `[saferecl.rcu]`。

- RCU 适合读多写少、读者临界区短、可以容忍旧节点晚一点释放的场景；
- 它不适合读者会阻塞很久、或写者需要立即回收内存的场景；
- 把 `condition_variable::wait` 放进 RCU 读侧临界区，读者会一直持有旧 epoch，宽限期推不动，写者只能看着内存涨。

平均开销接近，不代表尾延迟接近：风险指针要扫描整张表和整条待回收链，引用计数在最后一个引用离开时立即删，epoch/RCU 则取决于读者什么时候离开。选型要看内存余量和尾延迟，不要只看平均吞吐。

- 三者同一数量级，不代表尾延迟相同；
- 风险指针的扫描成本随待回收链长度增长；
- epoch 的回收延迟取决于读者，不在这张图里。

| 方案 | 额外空间 | 每次操作 | 回收延迟 | 依赖 |
|---|---|---|---|---|
| 风险指针 | 每线程一个槽，槽表固定 | 扫描槽表和待回收链 | 中等 | 不要求双字 CAS |
| 分离引用计数 | 计数在 16 字节指针字里 | 多一次双字 CAS | 最短 | 16 字节无锁 CAS |
| epoch/RCU | 按 epoch 和未释放节点计 | 读侧几乎零，写侧等宽限期 | 最长 | 库或内核支持 |

C++ 标准设施、liburcu、`std::shared_ptr`、pthread 线程局部存储的对照：

| 设施 | 能做什么 | 不能做什么 |
|---|---|---|
| C++26 `std::hazard_pointer` | 发布保护、`retire()` 延迟回收 | 本机 GCC 15.2 / Clang 21 未实现 |
| C++26 `std::rcu_domain`、`rcu_synchronize` | 读侧临界区、宽限期、延迟退休 | 本机未实现；读者不能长期阻塞 |
| liburcu | 用户态 RCU，读侧几乎零开销 | 本机未安装，未编译验证 |
| `std::atomic<std::shared_ptr<T>>` | 原子地换一个 `shared_ptr` | 不保证无锁；libstdc++ 15.2 为 `false` |
| pthread `pthread_key_create` | 线程退出时调用析构函数 | 只做线程退出清理，不能回答“节点何时可删” |
| `std::shared_ptr<T>` | 共享数据所有权 | 不保护裸节点指针，节点仍可能悬空 |

- `std::atomic<std::shared_ptr<T>>` 和标准 GC 都不是“免费回收”：前者不保证无锁，后者在 C++23 已被移除（P2186R2）；
- 标准库到 C++26 仍没有无锁容器，也没有像 GC 那样通用的回收器；`std::hazard_pointer` 和 `<rcu>` 是两套具体的回收设施，不是容器。

## 速查

| 方案 | 机制 | 开销 | 适用 |
|---|---|---|---|
| 风险指针 | 读者发布地址，删除者扫描 | 每线程一槽；回收 O(待删 × 槽) | 节点多、线程中等、平台不支持双字 CAS |
| 分离引用计数 | 外部计数在指针字，内部计数在节点 | 每次操作多一次双字 CAS | 竞争不激烈、能接受 16 字节无锁 CAS |
| epoch/RCU | 读者记 epoch，写者等宽限期 | 读侧近零；写者等，旧节点占内存 | 读多写少、读者短、内存充足 |

| 步骤 | 要求 | 做错会怎样 |
|---|---|---|
| 读 `head` | 先拿到候选地址 | — |
| 发布 `hp` | 把候选地址写进自己的槽 | 发布太晚，别人已经删了 |
| 重读 `head` | 确认仍是同一个地址 | 少这一步，发布前已被释放 |
| 解引用 | 只在确认之后读 `next` | 读到已释放节点 |
| 清空 `hp` | 读完立即清 | 槽一直被占，别人无法回收 |
| 扫描 | 删除者读所有槽 | 漏看一个槽就提前删 |

| 设施 | 头文件/接口 | 本机状态 |
|---|---|---|
| 风险指针 | `<hazard_pointer>`、`std::hazard_pointer`、`std::hazard_pointer_obj_base` | GCC 15.2 / Clang 21 没有该头文件，未编译验证 |
| RCU | `<rcu>`、`std::rcu_domain`、`rcu_synchronize`、`rcu_retire` | 同上，未编译验证 |
| 原子 `shared_ptr` | `std::atomic<std::shared_ptr<T>>`（C++20） | 可编译；libstdc++ 15.2 上 `is_lock_free()==false` |
| 标准 GC | C++23 起移除（P2186R2） | 不能当可选方案 |

## 思考题

1. 16.3 的风险指针如果先重读 `head`、再发布 `hp`，哪个交错会让 ASan 报释放后使用？画出两个线程的步骤。

   <details><summary>提示</summary>

   读线程先读 `head=A` 并重读一次确认 A；在它发布 `hp=A` 之前，写线程弹出 A 并 `delete`；读线程随后发布 `hp=A`，再解引用 A。发布时 A 已经不在了，重读也救不了。把 `16_3_hazard_missing.cpp` 的 `hazard.store(p)` 和重读顺序对调，就能复现。

   </details>

2. 找错：16.4 的 `counted_node_ptr` 在 32 位平台上指针只有 4 字节，外部计数 2 位够不够？如果不够，哪些操作会溢出？

   <details><summary>提示</summary>

   2 位只能表示 0 到 3；每个读 `head` 的线程都要把外部计数加一，8 个线程同时读就会超过 3。`increase_head_count()` 的 CAS 会回绕，`ext-2` 变成错误的值，节点可能提前删或永远不删。位宽和平台指针大小是两件事；32 位平台上结构体是 8 字节，但计数宽度仍要按并发读者数选。示例的 `static_assert(sizeof(counted_node_ptr)==16)` 把它限定在 64 位；32 位平台要去掉这个断言，按 8 字节结构体重新验证。

   </details>

3. 迁移：把 16.5 的 epoch 回收用到第 7 章的任务队列，读者临界区包含 `condition_variable::wait` 会有什么问题？宽限期还能推进吗？

   <details><summary>提示</summary>

   `wait` 会让读者停在旧 epoch 里，宽限期要等它离开才能结束；写者删掉的节点一直不能释放，内存只涨不降。RCU 要求读侧临界区短且不阻塞；任务队列的等待要么放在 RCU 外面，要么换回引用计数/风险指针等方案。

   </details>

4. 权衡：一个读多写少的路由表，节点很大、更新很少，用风险指针、引用计数、RCU 还是 `shared_mutex`？从内存占用和尾延迟两方面比较。

   <details><summary>提示</summary>

   RCU 的读侧几乎零开销，尾延迟最好，但旧节点要等宽限期，节点大时内存占用高；风险指针每线程一个槽，读侧要发布和重读，尾延迟中等；引用计数每次读都要动计数，节点大时缓存开销明显；`shared_mutex` 写者会挡住读者，尾延迟最差。节点很大、更新很少时，先看内存余量能不能容忍 RCU 的延迟释放，再看读侧尾延迟的要求。

   </details>
