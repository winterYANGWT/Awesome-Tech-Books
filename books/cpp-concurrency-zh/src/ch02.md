## 2.1 存储层次与局部性

CPU 和 DRAM 之间有多级 cache，越靠近核越小越快。x86-64 上一条 cache line（缓存行）通常是 64 字节，一次取一整行；说“命中”还是“缺失”，要先说清是相对哪一层。

{{#fig ch02/memory_hierarchy}}

每一层 cache 通常分成若干组，一个地址先映射到组，再在组内选一路。两个常用变量映射到同一组时会互相替换，这叫冲突缺失，组相联和替换策略就是用来减少这种情况的。

本机的三个数：
- L1d：每核 48 KiB。
- L2：每核 1 MiB。
- L3：两块 32 MiB。

图里的周期数是典型值，不是本机实测；能确定的是数量级：L1 几个周期，L2 十几个，L3 几十个，DRAM 几百个。

空间局部性让连续访问比跳跃访问快，因为一条线里的相邻字节会被一起取进来。时间局部性让重复访问留在上层，循环里反复用的数组比只扫一遍的数组更容易命中。

{{#fig ch02/row_column}}

缺失不都一样，常见分三类：
- 冷缺失：这一行第一次被访问，必须从下层取。
- 容量缺失：工作集比这一层大，旧行被换出后又用到。
- 冲突缺失：两个常用地址映射到同一组，互相把对方挤掉。

写 cache 有写直达（write-through）和写回（write-back）两种策略。写回给脏行做标记，等这一行被换出时再写主存，写直达每次都往下一层写。缺失时 CPU 不一定停住，它可以乱序执行别的指令，但依赖这条数据的指令仍要等。

虚拟存储器以 4 KiB 页为基页，页表把虚拟页号映射到物理页号；TLB 缓存最近用过的页表项，页缺失会陷入内核。x86-64 的大页是 2 MiB 和 1 GiB，用大页能减少 TLB 压力，代价是内部碎片和分配限制。

C++17 在 `<new>` 里给了两个实现定义值：

| 常量 | 含义 | 本机 GCC 15 / Clang 21 |
|---|---|---|
| `std::hardware_destructive_interference_size` | 避免伪共享时，两个并发访问对象之间的最小建议间距 | 64 |
| `std::hardware_constructive_interference_size` | 适合放在同一 cache line 里、被并发线程一起访问的最大连续字节数 | 64 |

两个值都只是提示，不能写死成跨编译器的 ABI 常量；换平台、换编译器都要重新取。

## 2.2 缓存一致性与 MESI

每个核有私有 cache 后，一个核写了某个地址，其他核的旧副本必须失效，这叫缓存一致性（cache coherence）。监听协议（snooping）靠总线广播失效，目录协议（directory）用目录记录谁有副本；核多以后广播太吵，目录更常见。

{{#fig ch02/false_sharing_layout}}

两个计数器放在同一条 64 字节行里时，核 0 写 `cnt0`、核 1 写 `cnt1`，硬件看到的都是“这一行被写了”，于是让对方的整行失效。两个变量没关系，缓存行却只能在两个核之间来回搬，这就是伪共享（false sharing）。

MESI 把每条 cache line 标成四个状态：

| 状态 | 含义 | 本核写命中时 |
|---|---|---|
| Modified（M） | 只有本核有，已修改，和主存不一致 | 直接写，仍是 M |
| Exclusive（E） | 只有本核有，干净 | 直接写，变 M |
| Shared（S） | 多个核都有，干净 | 先取得所有权（RFO），把其他副本置 I，再变 M |
| Invalid（I） | 本核没有有效副本 | 先取回整行，再写 |

{{#fig ch02/mesi}}

E 状态看起来只是 S 的少副本版本，作用却很大：核 0 独占一行时再写，不需要发 RFO，直接变 M。如果两个核都持有 S，写之前必须先让对方的副本失效。

写共享行要先发 RFO（read for ownership），拿到独占权才能改：
- 第 3 步核 0 写，核 1 的副本失效。
- 第 4 步核 1 写，核 0 的副本失效。
- 第 6 步核 0 又写，整行再搬回来。

抢的是 64 字节，不是那 8 字节的计数器。

一致性只保证“同一个地址的写最终能被看到”，不保证不同地址之间的顺序，也不把多条写变成一个原子事务。两个变量都在同一条线上时，一致性协议照样一次搬一整行，这就是伪共享只有性能问题、没有正确性问题的原因。

## 2.3 一致性还不够：编译器与 CPU 都会重排

缓存一致性解决“值会不会看到”，不解决“什么时候看到”和“不同变量之间的顺序”。编译器可以把无关的访存挪位置，CPU 可以用 store buffer 暂存写，用 invalidate queue 延迟处理失效。x86-64 是较强的 TSO 模型，ARM64 弱得多，但两者都允许某些重排。

{{#fig ch02/visibility_layers}}

编译器重排最常见的形态是把循环里的读提到循环外，或者把两次写调换。CPU 的 store buffer 让写先停在自己核里，invalidate queue 让失效请求晚一点处理；这两层都不是缓存一致性协议能修的。

| 取法 | 返回什么 | 是否受容器限制 | 能不能指导线程数 |
|---|---|---|---|
| `hardware_concurrency()` | 逻辑 CPU 数的提示值，取不到时返回 0 | 通常不看 affinity 和 cgroup | 只能当上限提示，不能直接用 |
| `sched_getaffinity(2)` | 当前线程可运行的 CPU 集合 | 受 cpuset 限制 | 能指导绑核和线程数，但不看 `cpu.max` 配额 |
| cgroup v2 `cpu.max` | CPU 时间配额和周期，`max` 表示不限 | 是，容器的主要限制之一 | 能指导 CPU 预算，不能直接当并行度 |
| `nproc` | 可用处理器数，本机 32 | 通常跟 affinity 走 | 快速估计可以；GNU coreutils 9.8（2025 年）起才按 `cpu.max` 配额取整，更早的版本和本机用的 uutils 版不能指望 |

## 2.5 数据布局：行主序、分块与伪共享

三个校验和相同，`j-i` 慢约一个数量级，`i-j` 最快，4×4 分块居中。纯求和只读一遍，块里的数据没有被第二次使用，分块省不下重复读，反而多了循环开销，它主要改善 TLB 命中，所以没能超过 `i-j`。

| 顺序 | 内层步长 | 现象 |
|---|---|---|
| `i-j` | 4 B | 连续，预取有效 |
| `j-i` | 16 KiB | 每读一个元素换一行 |
| `block-4` | 块内 4 B，块间跳 | 块内连续，块间换行 |

分块边界最好落在 cache line 上：一个线程的块从行中间开始，它和邻居就会写同一条线。把每块的行宽补齐到 64 字节的倍数，或者按整行分块，能消掉这类边界伪共享。

{{#fig ch02/matrix_shapes}}

矩阵-向量乘法的形状能把问题分开：`8,000,000×8` 的 `y` 很长，每个线程分到连续的一段，主要是写 `y` 的缺失，`8000×8000` 的 `y` 只有 8000 个元素，分块边界可能落在 cache line 中间，边界处出现伪共享，`8×8,000,000` 让多个线程写同一行的相邻元素，伪共享最严重。旧资料里的更新次数和形状对不上，这里只取“哪种形状最慢”的结论，计时全部在本机重测。

| 布局 | 局部性 | 伪共享风险 | 适用数据 |
|---|---|---|---|
| AoS（每个元素带所有字段） | 一次处理一个对象时好 | 不同线程写同一对象的相邻字段时高 | 对象小、字段总是一起用 |
| SoA（每个字段一个数组） | 按字段扫描时好，利于向量化 | 字段之间没有 | 按字段分给不同线程、数组很大 |
| 行优先遍历 | 内层连续，预取和 cache line 都用得上 | 线程分块边界不对齐时高 | 矩阵按行算 |
| 列优先遍历 | 每步跨一行，空间局部性差 | 多线程写同一列时高 | 只有列操作是主要访问时 |
| 4×4 分块 | 块小，适合放进一行或几行 | 块边界不对齐时高 | 块内数据会被重复使用 |
| 64×64 分块 | 块能放进 L1/L2 | 边界对齐后低 | 矩阵乘法、模板计算 |
| 128×128 分块 | 可能超过 L1，仍可能放进 L2 | 边界对齐后低 | 大矩阵、多次复用 |

AoS 把同一个对象的所有字段放在一起，一次处理一个对象时局部性好。SoA 把每个字段拆成独立数组，按字段扫描或分给不同线程时连续，代价是访问一个对象的多个字段要读多个数组。

块大小要同时满足两个条件：块能放进 L1 或 L2，块内又有足够多的复用。4×4 的块只有 16 个元素，复用少，64×64 的块在 4096×4096 的矩阵乘法里更常见。

伪共享的修法有三种：
- 把热点变量用 `alignas(std::hardware_destructive_interference_size)` 分开。
- 每个线程用本地副本，最后合并。
- 把只读数据和可写数据分开。

第一种要看编译器实际给的值，第二种多一次合并，第三种要改数据布局。

> **旧资料提示**：旧教程把 `hardware_destructive_interference_size` 解释成“可共享的最大字节数”。它是“避免伪共享的最小间距”，`constructive` 才是可共享的连续字节数；两者都是 C++17 的实现定义值，见 [18.3 节](ch18.md)。

## 思考题

1. 把 `2_2_false_sharing.cpp` 的两个计数器改成 `alignas(128)`，耗时一定会更好吗？如果 L2 是 1 MiB、cache line 是 64 字节，多占的 64 字节会影响什么？

   <details><summary>提示</summary>

   不一定。128 字节间距仍然能避开 64 字节的伪共享，但每个计数器占的空间更大，数组或结构体数组的密度下降，单线程扫描时更容易缺页、占用更多 cache line。先用 64 字节对齐测一遍，再用 128 字节测一遍，比较的是同一个访问模式下的总耗时，不是对齐值本身。

   </details>

2. `2_3_volatile_flag.c` 里如果把 `ready` 改成 `std::atomic<bool>`、数据仍是普通 `int`，还用 relaxed 读写，能保证读线程看到数据吗？

   <details><summary>提示</summary>

   不能。`ready` 的 relaxed store/load 只保证这个标志本身是原子的，不建立 `data` 写和读之间的先行发生关系；读线程可能看到 `ready == true`，读到的 `data` 仍是旧值。把 store 改成 release、load 改成 acquire，或者两边都用默认的 `seq_cst`，才有保证。

   </details>

3. 一个 8×8,000,000 的矩阵-向量乘法，按行分块和按列分块各有什么缓存问题？在 32 线程的机器上应该先改布局还是先加锁？

   <details><summary>提示</summary>

   按行分块时每行只有 8 个元素，一个线程处理一行，`y` 的相邻元素会被多个线程写，容易落在同一条 cache line 上；按列分块时每一列跨 8 行，访问步长大，空间局部性差。这里没有共享累加，加锁只会更慢；先按 cache line 对齐 `y` 的线程边界，或者让每个线程先写本地副本再合并，再考虑并行划分。

   </details>

4. 把 `2_5_matrix_traversal.cpp` 的分块大小从 4 改成 32、64、128，画出耗时曲线，解释为什么不是越大越好。

   <details><summary>提示</summary>

   块太小，循环和边界判断的开销占比高，块内数据也没被充分复用；块大到超过 L1（本机 48 KiB）后，一个块在再次使用前就被换出，L2 甚至 L3 的流量增加。曲线通常先降后升，最低点大约在“块能放进 L1/L2、又足够大以摊薄开销”的位置。用 `2_5_matrix_traversal.cpp` 改 `kBlock` 就能测，注意保持校验和不变。

   </details>
