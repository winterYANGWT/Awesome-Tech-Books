看最后三行：异常没有穿过 `join` 回到 `main`，而是在线程启动函数里直接调用了 `terminate`。标准规定，线程函数以未捕获异常退出时调用 `terminate`（`[thread.thread.constr]`）。

两条独立的路径：

- 工作线程里未捕获的异常，在线程启动函数里直接 `terminate`。
- 线程对象析构时仍 `joinable`，在栈帧结束时 `terminate`。

`joinable()` 为真时，`std::thread` 的析构函数调用 `terminate`（`[thread.thread.destr]`）。这和工作线程里的异常是两件独立的事：一个发生在异常逃出线程函数时，另一个发生在持有线程对象的栈帧结束时。

{{#fig ch21/exception_paths}}

图里三条路径要分开看：上边是异常逃出边界，中间是 `catch` 后交给 `future`，下边是线程对象仍 `joinable`。前两条和第三条的风险来源不同，修法也不同。

线程构造本身也会失败。资源不足时 `std::thread` 抛 `std::system_error`，错误条件是 `resource_unavailable_try_again`。如果代码在一个循环里创建线程，失败时前面已经创建的线程仍是 `joinable`，装线程的 `vector` 一析构，又会走到图里下边那条路。

跨线程传异常的标准工具是 `std::exception_ptr`。工作线程在 `catch (...)` 里取 `std::current_exception()`，通过 `std::promise::set_exception()` 交给共享状态，主线程在 `future::get()` 时重新抛出：

```cpp
std::promise<int> promise;
auto result = promise.get_future();
std::thread worker([&] {
    try { promise.set_value(compute()); }
    catch (...) { promise.set_exception(std::current_exception()); }
});
try {
    int value = result.get();  // 异常在这里重抛
} catch (const std::exception& e) {
    std::printf("worker 失败：%s\n", e.what());
}
worker.join();
```

> `std::packaged_task` 把这一步自动化了，适合放进线程池：

- 任务抛出的异常自动存进共享状态。
- `future::get()` 时重新抛出，调用者只写一次 `catch`。

```cpp
std::packaged_task<int()> task([] { return compute(); });
std::future<int> result = task.get_future();
std::thread worker(std::move(task));
// ...
try {
    int value = result.get();
} catch (const std::exception& e) {
    std::printf("task 失败：%s\n", e.what());
}
worker.join();
```

`std::jthread` 只负责析构时 `request_stop()` 再 `join()`，它不捕获异常。工作线程该 `catch` 的还是要 `catch`；`stop_token` 只解决“要不要停”，不解决“抛了怎么办”。

## 21.2 数据结构的异常安全：不变量、接口与 notify_one 的洞

看一个数据结构的异常安全，先问四个问题：

- 有没有线程能看到不变量被破坏的中间状态？
- 有没有接口竞争，比如 `empty()` 和 `pop()` 分开调用？
- 异常抛出时，锁和数据结构是否仍然一致？
- 加锁顺序会不会死锁（[第 14 章](ch14.md)）？

`notify_one()` 有一个专门的洞：被唤醒的线程取走元素，在构造返回值时抛异常，它不会再把通知传给别人。其他等待者可能永远睡下去。

`wait_pop()` 先摘除、解锁，再构造 `std::optional<Item>`，移动构造抛异常时，元素已经不在队列里。B 随后进入 `wait_pop`，队列为空，生产者也不再 `push`，主线程卡在 `join`。gdb 里 B 停在 `ItemQueue::wait_pop` 的 `cv_.wait`（第 57 行），主线程停在 `main` 的 `b.join()`（第 105 行）。

修法有三种，各有代价：

| 修法 | 怎么改 | 代价 |
|---|---|---|
| `notify_all` | 每次入队唤醒全部等待者 | 消费者多时唤醒和重新加锁开销大 |
| 异常路径补通知 | `catch` 里再 `notify_one()` | 每条退出路径都要记得补，容易漏 |
| 分配移到 `push` | 队列存 `shared_ptr<T>`，`pop` 只拷贝指针 | 每个元素多一次堆分配和解引用 |

`notify_all` 的行为要分两种情况：

- 队列里还有元素或已经 `close`：所有等待者都重新检查谓词，B 不会漏掉。
- 既没有元素也没有 `close`：B 仍会睡回去，问题变成关闭协议没写清楚，不是单靠换通知能解决的。

`push()` 里 `make_shared` 失败时，元素还没进队列，队列保持原样；`wait_pop()` 拷贝指针不抛，通知不会在“取元素”这一步丢掉。消费者处理任务时仍可能抛，所以循环里还有 `try`/`catch`。

引用输出和删除节点是两处容易漏的异常路径：

- 引用输出的 `pop` 要反过来：先赋值，再摘除节点。赋值抛异常时节点还留在队列里，下一个消费者还能取到；先 `pop` 再构造，异常一来元素就丢了。
- 删除链表节点时，先解锁，再让 `unique_ptr` 析构。节点里如果带着自己的互斥量，销毁一个仍被锁住的互斥量是未定义行为，解锁必须发生在析构之前。

锁用 RAII 管理，正常和异常路径都能解锁：

```cpp
{
    std::lock_guard<std::mutex> lock(m);
    do_work();  // 抛异常也会解锁
}
```

手写 `m.lock(); do_work(); m.unlock();` 时，`do_work()` 一抛，`unlock()` 就漏了。`std::unique_lock` 用于需要中途解锁或配合条件变量的场景，`std::scoped_lock` 用于一次锁多个互斥量。析构路径不要抛异常，析构函数里抛异常，栈展开时又会 `terminate`。

`future::get()` 在主线程重抛工作线程的异常，外层的 `catch` 能接住。`join_threads` 守卫持有线程 `vector` 的引用，析构时把仍 `joinable` 的线程全部 `join`，这样正常返回和异常退出都不会留下 `joinable` 的线程对象；线程构造抛出的 `std::system_error` 也在同一个 `try` 里被接住。

- 对“必须算完”的任务不合适：任务如果检查 `stop_token`，可能提前退出。

第一个 `get()` 抛出后，循环就退出了，后面 `future` 的异常还留在共享状态里，没有人再取。要收集所有异常，就逐个 `get()` 并 `catch`，或者用 `exception_ptr` 列表保存。

> `std::async` 的异常安全有三个前提：

- future 析构释放共享状态时，如果状态由 `std::async` 创建、还没就绪，并且这是最后一个引用，标准允许它阻塞等待。
- `launch::async` 的任务在新线程里跑；`launch::deferred` 的任务只在等待时执行，析构不会替你把任务跑完。
- 标准说的是“as if in a new thread”，不承诺每次创建一个新的 OS 线程。

要可控线程数，仍要自己建池。

> **旧资料提示**：旧写法认为 `std::async` 的异常安全靠 future 析构等待。它只在共享状态由 `std::async` 创建、未就绪且这是最后一个 future 引用时才可能等待；`launch::deferred` 不会因此开始执行，标准也不保证每次都创建新的 OS 线程，原因见 [第 39 章](ch39.md)。

C++17 并行算法不是“自动传播异常”的工具。带执行策略的算法里，元素访问函数抛出异常时，`seq`、`par`、`par_unseq`、`unseq` 都调用 `std::terminate`（`[execpol.seq]` 等），只有不带策略的重载才把异常传给调用者。

并行算法为并行化申请临时内存失败时，标准允许它抛 `bad_alloc`；元素访问函数抛出的异常仍按策略 `terminate`（`[algorithms.parallel.exceptions]`）。

## 21.4 评审清单与测试矩阵

评审并发代码时，把下面九个问题逐条问一遍：

| 问什么 | 为什么 |
|---|---|
| 哪些数据需要保护？ | 先找共享的可写状态 |
| 如何证明保护有效？ | 锁、原子或不可变，不能靠“看起来没事” |
| 哪些线程会同时进入？ | 画出并发路径，不只看函数名 |
| 当前持有哪些锁？ | 锁的作用域要覆盖整个不变量 |
| 其他线程可能持有哪些锁？ | 找锁顺序反转 |
| 两个线程的操作之间有什么依赖？ | 谁先谁后，靠什么建立先行发生 |
| 读到的数据是否仍合法？ | 对象可能已被销毁或移走 |
| 假设其他线程会改数据，意味着什么？ | 检查整个临界区，不只检查一行 |
| 如何确保这种事不发生？ | 把假设写成接口约束或断言 |

报告指向 `save_ptr`，两行栈都落在 `legacy_strtok`。`strtok` 的实现在 libc 里，没有为 TSan 插桩，直接调 `strtok` 看不到报告，所以反例把同一份状态放进示例，`strtok(3)` 自己标的是 `MT-Unsafe race:strtok`。修法是 `strtok_r`，把 `saveptr` 交给调用者，每个线程用自己的状态。

`errno` 是线程局部的，但这不代表使用 `errno` 的函数可重入。线程安全和可重入不是同义词：用锁保护的函数可以线程安全，但递归调用会死锁，所以不可重入，`strtok_r` 把状态交给调用者，才是可重入版本。`inet_ntoa` 返回的缓冲区会被后续调用覆盖，`gethostbyname` 在 man 页面里标了 `MT-Unsafe`，都不能想当然地并发调用。

“只有在多核、多线程下才出现的问题才更可能是并发 bug”这条经验法则过强。`strtok` 的竞争在单核上也会因时间片切换出现，多核只是让它更容易暴露（把进程绑到一个核，TSan 仍报同一竞争）。

> 可测试性设计比事后调试便宜：

- 单线程测试能排除普通 bug，但不能排除并发 bug。
- 把并发代码拆成可单线程测试的块，状态机的每个状态单独测。
- 把“读共享数据 / 变换数据 / 更新共享数据”分开，变换部分往往可以纯函数化。
- 在写代码之前就想好怎么测，尤其是关闭、取消和异常路径。
- 测试库函数时，把“线程安全”和“可重入”分开问。

同一份负载下 TSan 不再报告。这里用 `memory_order_relaxed` 就够了：只需要原子性，不需要用它给别的数据排序。TSan 的边界要记住：

- 只覆盖实际执行到的路径。跑一次没报告，不等于没有竞争，要配合压力测试、随机延迟、不同线程数和不同机器。

- libgomp 没有为 TSan 插桩，GCC 编译的 OpenMP 程序在 TSan 下可能误报。这类示例要么用 Clang + libomp，要么写 `// tsan: no` 并说明原因。
- 本机没有 Valgrind，Helgrind/DRD 用不了，正文只用 TSan 和 ASan。

| `catch fork` / `catch syscall clone clone3` | 在 `fork`/建线程处停下（glibc 2.34 起 `pthread_create` 走 `clone3`，只抓 `clone` 停不下来） |

## 21.7 压力测试与性能回归

压力测试用大量重复、随机延迟、不同线程数和不同起跑顺序提高暴露概率。下面的例子对第 7 章那种线程安全队列做固定 push/pop/close，只把 `yield`/`sleep_for` 的时机随机化：


```text

```

每轮用不同的种子，随机化 `yield`/`sleep_for` 的时机；生产者固定 push、消费者固定 pop，最后一个生产者 close。失败时打印种子、线程数和每个生产者最近的 push 值。

把 `kBaseSeed` 改成失败的种子，或运行时加 `--seed <种子> --rounds 1`，就能用同一组随机延迟重跑；内核调度仍不保证复现同一次交错。能重放的失败比“再跑一遍”有价值。

{{#fig ch21/stress_loop}}

压力测试不能证明没有 bug，只能提高“碰巧遇到”的机会。确定性录制回放（例如 `rr`）会把所有线程串行到一个核上，能录到线程交错，但复现不了真正并行才出现的问题，不要假设它录下所有交错。

性能回归也是测试。固定机器、固定线程数、同一份负载，记录吞吐和 p99；只比较平均值会掩盖尾延迟退化（[第 18 章](ch18.md)）。

压测器本身要先审查。一个常见的错误是把 `EAGAIN` 当成失败：非阻塞 `accept`/`read` 在没数据时返回 `EAGAIN`，健康的连接会被误关。另一个绝对化的说法是“单线程 I/O 复用施压最高”，多核上单进程只能用一个核，要压满机器就得多开事件循环或进程。

> 测试放进 CI 时有三条规则：

| CI 规则 | 做法 |
|---|---|
| 超时与资源 | 设超时、限制资源 |
| 失败分类 | 区分偶发失败和稳定失败 |
| 保留证据 | 偶发失败不直接重跑，保留日志、种子和线程栈 |

## 速查

| 异常来源 | 现象 | 修法 |
|---|---|---|
| 工作线程异常逃出边界 | `std::terminate` | `catch (...)` + `exception_ptr` / `packaged_task` |
| 线程对象析构时仍 `joinable` | `std::terminate` | `join` / `detach` / `join_threads` / `jthread` |
| 线程构造失败 | `std::system_error`，已建线程仍 `joinable` | 守卫 + `try`/`catch`，按逆序回收 |
| `vector<std::thread>` 半途析构 | `std::terminate` | `join_threads` 守卫或 `vector<jthread>` |
| 只 `get()` 第一个 future | 后续异常不可见 | 逐个 `get()` + `catch`，或 `exception_ptr` 列表 |
| 并行算法元素函数抛异常 | `terminate`（含 `seq`） | 自己包装任务，或不用执行策略 |

| 手段 | 问什么 / 怎么用 | 注意 |
|---|---|---|
| 评审九问 | 数据、锁、顺序、生命周期、接口 | 先找共享可写状态 |
| 测试矩阵 | 空/非满/满 × 单/多线程操作 | 每格有确定断言，不靠 `sleep` |
| 起跑门 | `latch` 一次性，`barrier` 可重复 | 所有线程先报到，再同时开始 |
| 压力测试 | 随机种子、线程数、操作序列 | 失败记录种子和栈，能重放 |

| 工具 | 能发现 | 不能发现 | 本机可用性 |
|---|---|---|---|
| ThreadSanitizer | 数据竞争、锁顺序反转 | 释放后使用、越界、内存序正确性 | 可用 |
| ASan / UBSan | 释放后使用、越界、部分 UB | 数据竞争 | 可用 |

## 思考题

1. 21.3 的 `21_3_multi_failure.cpp` 两个工作线程都抛异常，主线程只 `get()` 第一个 future 就退出，第二个异常去哪了？如果改成逐个 `get()`，能看到两个吗？

   <details><summary>提示</summary>

   第二个异常留在它自己的共享状态里。主线程离开循环后没有再 `get()`，future 析构只释放共享状态，不会重抛。逐个 `get()` 并 `catch` 才能看到两个；本章示例打印的“可见异常数 1 / 实际失败数 2”就是这个差别。

   </details>

2. 21.2 的 `notify_one` 异常洞，三种修法各自在什么时序下仍会丢通知？`notify_all` 为什么能修好？

   <details><summary>提示</summary>

   `notify_all` 让所有等待者都醒来重查谓词；如果还有元素或已经 `close`，就不会漏。补通知要在每条异常路径上都补，漏一条就回到原状。`shared_ptr` 只保证 `pop` 不抛，消费者处理任务时仍可能抛，仍要自己 `catch`。

   </details>

3. 把 21.4 的测试矩阵用到第 14 章的两把锁队列，空队列、满队列、一边 push 一边 pop 各需要什么起跑门？哪些格子必须用多线程？

   <details><summary>提示</summary>

   空队列测“pop 等待 push 唤醒”，满队列测“push 等待 pop 腾位置”，一边 push 一边 pop 测两个方向同时发生。用 `latch` 让两个线程先报到，再同时进入；单线程格子只能测接口，不能测交错，必须用多线程的格子是后两类。

   </details>

4. 一个偶发失败的死锁，先用 TSan、gdb、压力测试还是模型检查器？每种手段能回答什么问题、不能回答什么问题？

   <details><summary>提示</summary>

   先 gdb 看现场：谁持有什么、在等什么，能直接看到环。TSan 能报锁顺序反转，但只在执行到那条路径时。压力测试提高复现概率，不能证明没有。模型检查器适合小模型，不适合真实规模；本机也没有安装。

   </details>
