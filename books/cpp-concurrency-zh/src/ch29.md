# 第 29 章 MPI 入门：点对点通信

4 个进程围成一圈，每个先 `MPI_Send` 给右邻居，再 `MPI_Recv` 左邻居。`mpirun` 启动后没有任何输出，`timeout` 到点才被杀死。把 `MPI_Send` 换成 `MPI_Ssend`，挂住的位置又变了。

```c
int right = (rank + 1) % size;
int left = (rank + size - 1) % size;
MPI_Send(&rank, 1, MPI_INT, right, 0, MPI_COMM_WORLD);
MPI_Recv(&value, 1, MPI_INT, left, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
```

这不是网络慢。四个进程都在等对方先接收，而每个进程的下一步才是接收。消息传递的第一课，是分清“调用返回”“消息发出”“对方收到”这三件事。

## 29.1 分布式内存与 SPMD：第一个 MPI 程序

分布式内存里，每个进程有自己的地址空间。CPU 不能解引用另一个进程的指针，也不能直接读它的堆和栈；跨进程拿数据只有一条路：把数据打包成消息，显式地发过去。

MPI 是一套函数库，不是新语言。C、C++、Fortran 都能调用它；`mpicc`、`mpicxx` 是包装脚本，替你补上头文件路径和链接库。

{{#fig ch29/distributed_memory}}

图里每个节点只画了 CPU 和私有内存。跨节点的箭头不是内存总线，而是互连网络上的消息；接收端必须自己调用 `MPI_Recv`，数据才会进入它的地址空间。

一个 MPI 程序启动后，所有进程跑同一个可执行文件，靠 rank 走不同分支，这叫 SPMD（Single Program, Multiple Data）。rank 从 0 连续编到 p−1，`MPI_COMM_WORLD` 是启动时包含全部进程的默认通信子。

{{#fig ch29/spmd}}

rank 0 并不是“主进程”，它只是分支里负责汇总的那个。所有 rank 都要走到 `MPI_Finalize`；如果 rank 0 提前退出，其他 rank 的发送可能永远等不到接收。

非 0 号进程各发一条带 `\0` 的字符串。读这段输出看两点：

- 0 号按 `src = 1, 2, …, p−1` 的顺序接收。
- 输出顺序固定，不是因为网络按 rank 排队，而是因为 rank 0 按这个顺序调用 `MPI_Recv`。

`MPI_Init(&argc, &argv)` 初始化 MPI 运行时，`MPI_Finalize()` 释放它。两者之间才能调用其他 MPI 函数，`Finalize` 之后连 `MPI_Comm_rank` 都不能再调。

三个最常用的查询是：

- `MPI_Comm_size(MPI_COMM_WORLD, &p)` 取通信子里的进程数。
- `MPI_Comm_rank(MPI_COMM_WORLD, &rank)` 取当前进程的编号。
- `MPI_COMM_WORLD` 是启动时包含全部进程的默认通信子。

通信子（communicator）是一组可以互相发消息的进程。集合通信要求组内所有进程都调用同一个函数，而且调用顺序一致。

SPMD 的常见错误是让 rank 0 单独调用集合通信：

```c
if (rank == 0) {
    MPI_Bcast(&n, 1, MPI_INT, 0, MPI_COMM_WORLD);  /* 其他 rank 没调用 */
}
```

其他 rank 的反应是：

- 不会“自动收到”这条广播。
- 会停在下一个集合操作上等 rank 0，整个作业挂住。

集合通信的规则在第 30 章展开，这里先记住：分支可以按 rank 走，集合调用不能。

版本和语言绑定有三条边界：

- Open MPI 5.0.10 的 `MPI_Get_version` 报 3.1，MPI 标准已经到 4.1（2023）。
- MPI-4 的持久集合和分区通信接口在本机 `mpi.h` 里有声明，大计数 `_c` 接口没有；本章只讲 3.1 里稳定的部分。
- C++ 绑定在 MPI-3.0 已经移除；C++ 程序直接用 C API，或者用包装库。

大多数 MPI 函数把错误码作为 `int` 返回值，`MPI_Wtime`/`MPI_Wtick` 例外，直接返回时间。`MPI_COMM_WORLD` 默认挂的是 `MPI_ERRORS_ARE_FATAL`：参数错、缓冲区溢出、通信子不匹配，都会直接终止整个作业。要自己处理，先换处理器，再用 `MPI_Error_string` 解释：

```c
MPI_Comm_set_errhandler(MPI_COMM_WORLD, MPI_ERRORS_RETURN);
int rc = MPI_Send(buf, count, MPI_INT, dest, tag, MPI_COMM_WORLD);
if (rc != MPI_SUCCESS) {
    char text[MPI_MAX_ERROR_STRING];
    int len = 0;
    MPI_Error_string(rc, text, &len);
    fprintf(stderr, "MPI 错误：%.*s\n", len, text);
}
```

编译和运行：

```bash
mpicc -std=c17 -O2 -Wall -Wextra hello.c -o hello
mpirun -np 4 ./hello
```

root 下运行要在命令前加 `OMPI_ALLOW_RUN_AS_ROOT=1 OMPI_ALLOW_RUN_AS_ROOT_CONFIRM=1`；进程数超过可用核数时加 `--oversubscribe`。这些是 Open MPI 的启动器选项，不是 MPI 标准的一部分。

> **旧资料提示**：旧教程用 `MPI_Address` 取结构体字段地址。MPI-2 起改用 `MPI_Get_address`，偏移类型是 `MPI_Aint`；`MPI_Address` 已过时，见 [第 40 章](ch40.md)。

## 29.2 点对点通信：匹配、tag 与 communicator

```c
int MPI_Send(const void *buf, int count, MPI_Datatype datatype,
             int dest, int tag, MPI_Comm comm);
int MPI_Recv(void *buf, int count, MPI_Datatype datatype,
             int source, int tag, MPI_Comm comm, MPI_Status *status);
```

前三个参数描述缓冲区：起始地址、元素个数、MPI 数据类型。后三个参数描述信封：目的 rank、tag、通信子。`MPI_Recv` 的前三个参数描述接收缓冲区，接下来的三个是匹配条件，最后是状态对象。

一条消息能被接收，要同时满足：

- 通信子相同，发送的 `dest` 等于接收 rank，接收的 `source` 等于发送 rank。
- tag 相同；接收端可以用 `MPI_ANY_TAG` 通配。
- 类型签名相容：基本类型一致，接收容量不小于发送量。

接收端的 `source` 可以用 `MPI_ANY_SOURCE`，但发送端的 `dest` 必须写明确；通信子没有通配符。

{{#fig ch29/message_match}}

看第 4 步：接收端先用 `MPI_ANY_SOURCE` 和 `MPI_ANY_TAG`，匹配的是“最早到达的符合条件的消息”，也就是 tag 1 那条。第 6 步指定 tag 2，才取走第二条。变量叫什么、缓冲区多大，都不参与信封匹配。

`MPI_Status` 至少有 `MPI_SOURCE`、`MPI_TAG`、`MPI_ERROR` 三个成员。实际元素个数不能从 status 直接读字节数，要用接收时的类型换算：

```c
MPI_Status status;
MPI_Recv(&value, 1, MPI_DOUBLE, MPI_ANY_SOURCE, 7, MPI_COMM_WORLD, &status);
int count = 0;
MPI_Get_count(&status, MPI_DOUBLE, &count);
```

不关心状态时传 `MPI_STATUS_IGNORE`。顺序规则有两条：

- 同一发送者先后发的两条消息，如果都能匹配同一个接收，先发的不会被后发的超越；tag 相同是常见情形。
- 不同发送者之间没有这个保证；如果两条消息分别匹配不同的接收（接收指定了不同 tag），到达顺序可以不同。

`MPI_PROC_NULL` 是合法的哑元 rank。向它发送立即成功，从它接收立即返回空消息，status 里 `source = MPI_PROC_NULL`、`tag = MPI_ANY_TAG`、count 为 0。环或网格的边界进程可以用它省掉 `if (partner >= 0)` 分支：

```c
int left = (rank == 0) ? MPI_PROC_NULL : rank - 1;
MPI_Sendrecv(&send, 1, MPI_INT, right, 0, &recv, 1, MPI_INT, left, 0,
             MPI_COMM_WORLD, MPI_STATUS_IGNORE);
```

| 维度 | MPI | `std::promise`/`std::future` | POSIX `pipe` |
|---|---|---|---|
| 寻址 | 通信子 + rank + tag | 同一个进程内的 future 对象 | fd 对，没有 rank/tag |
| 匹配 | 通信子、source/dest、tag、类型签名 | 一个 future 对应一个结果 | 按字节流顺序，没有消息边界 |
| 阻塞 | `Send` 可能缓冲也可能等接收；`Recv` 等到匹配 | `get()` 等到值或异常 | 读空/写满时阻塞，受容量限制 |
| 错误 | 返回码；默认 `MPI_ERRORS_ARE_FATAL` | `broken_promise`、存储的异常 | `errno`、`EPIPE`、`EINTR` |
| 类型 | `MPI_Datatype` 描述内存布局 | 模板类型，编译期检查 | 无类型，字节流 |
| 缓冲区生命周期 | 阻塞发送返回后可复用；接收完成前不能读 | 值移进共享状态，`get()` 取走 | `write` 返回后内核已复制，可复用 |

## 29.3 阻塞、缓冲与死锁

{{#fig ch29/send_modes}}

标准发送模式（`MPI_Send`）可以先把消息复制到内部缓冲区再返回，也可以阻塞到接收端开始接收。到底走哪条路，取决于实现、消息大小和 eager/rendezvous 阈值；标准不保证“小消息一定不阻塞”。

看第 6 步：标准发送的返回点由实现决定。不要把 `MPI_Send` 返回当成“对方收到了”，它只说明发送缓冲区可以复用。

另外三种模式控制的是“发送何时可以返回”，不是“消息是否可靠”：

- `MPI_Ssend`：同步发送，只有匹配的接收已经开始才返回。
- `MPI_Bsend`：缓冲发送，用户先用 `MPI_Buffer_attach` 提供缓冲区，发送复制进去就返回。
- `MPI_Rsend`：就绪发送，要求接收已经 posted；否则是错误，结果未定义。

{{#fig ch29/deadlock_ring}}

环上每个 rank 都先 `MPI_Send`、再 `MPI_Recv`，四个 `Send` 就形成等待环。每个 `Send` 都在等右邻的 `Recv`，而每个 rank 的 `Recv` 要等自己的 `Send` 返回。

- 第一段把 `MPI_Send` 换成 `MPI_Ssend`，所有 rank 都先同步发送，没有 rank 先 post 接收，所以 5 秒内全部卡住，脚本判定 `deadlock detected`。
- 第二段改成偶数 rank 先发后收、奇数 rank 先收后发，环上的等待方向一致，四个 rank 都完成交换。

```c
if (rank % 2 == 0) {
    MPI_Ssend(&send_value, 1, MPI_INT, right, 0, MPI_COMM_WORLD);
    MPI_Recv(&recv_value, 1, MPI_INT, left, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
} else {
    MPI_Recv(&recv_value, 1, MPI_INT, left, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
    MPI_Ssend(&send_value, 1, MPI_INT, right, 0, MPI_COMM_WORLD);
}
```

这个重排对本章的环够用，但它有两个局限：

- 进程数、拓扑或消息方向一变，分支就要重写。
- 它没有把发送和接收绑定成一次原子操作，调试时仍要逐个 rank 看。

每个 rank 发出自己的值，收到左邻的值：rank 0 发 0 收 30，rank 1 发 10 收 0。`MPI_Sendrecv` 有三条规则：

- 发送缓冲区和接收缓冲区必须不重叠。
- 两个方向可以不同 tag、不同长度、不同数据类型。
- 要原地交换，用 `MPI_Sendrecv_replace`。

非阻塞通信把“提交”和“完成”分开：

```c
MPI_Request req[2];
MPI_Isend(sendbuf, n, MPI_DOUBLE, right, 0, MPI_COMM_WORLD, &req[0]);
MPI_Irecv(recvbuf, n, MPI_DOUBLE, left, 0, MPI_COMM_WORLD, &req[1]);
MPI_Waitall(2, req, MPI_STATUSES_IGNORE);
```

非阻塞请求有三条生命周期规则：

- `MPI_Isend`/`MPI_Irecv` 返回请求对象，只表示请求已经提交。
- 发送缓冲区在 `MPI_Wait`/`MPI_Test` 完成前不能复用，接收缓冲区在完成前不能读。
- `MPI_Waitall` 等一组请求，`MPI_Test` 只问“完成了吗”。

用 `MPI_Ssend` 替换 `MPI_Send` 是诊断手段：替换后死锁，说明原来的“能跑”只是内部缓冲区帮了忙。替换后能跑，也不证明程序安全，只说明这一次的规模、实现和消息大小没有触发阻塞。

> **旧资料提示**：旧教程说“`MPI_Send` 返回后就可以复用发送缓冲区”，这话对阻塞发送成立，但别把它理解成“对方收到了”。非阻塞发送要等 `MPI_Wait`/`MPI_Test` 完成，见 [第 40 章](ch40.md)。

`MPI_Get_count` 和 `MPI_Get_elements` 的分工是：

- 对基本类型，`Get_count` 就是元素个数。
- 对派生类型，`Get_count` 可能返回 `MPI_UNDEFINED`，这时用 `Get_elements` 取基本元素个数。

不要拿 `Probe` 返回的 status 直接当数据读，它只有信封。

`MPI_Iprobe` 是非阻塞版本，返回 `flag`；没有消息时立即返回，有消息时 status 和 `MPI_Probe` 一样。用它轮询时注意两点：

- 它适合轮询“有没有新消息”，不适合在热循环里空转。
- MPI 没有条件变量，轮询间隔和退避要自己控制。

工作池里通常这样用它：

- `MPI_ANY_SOURCE` 加 `MPI_Probe` 按消息到达顺序取任意 worker 的结果。
- `status.MPI_SOURCE` 告诉你是谁发的，回信时用它。
- `Probe` 和随后的 `Recv` 必须用同一个信封；中间被别的线程取走，`Recv` 会一直等。

## 29.5 I/O、错误处理与线程

{{#fig ch29/io_layers}}

多数实现允许所有 rank 写 stdout/stderr，但输出顺序不确定，一行还可能被另一个 rank 打断。标准输入通常只有 rank 0 能读，因为无法把一条输入流合理地切给多个进程。

可靠做法是：rank 0 读入，用 `MPI_Bcast` 分发；输出统一由 rank 0 打印，或者每行加 rank 前缀。大规模输出用 MPI-IO 的 `MPI_File_*` 或专门的数据收集，不要靠所有 rank 抢终端。

终端 I/O 有三条实践规则：

- 标准输入只让 rank 0 读，读完再广播。
- 标准输出尽量只让 rank 0 写；其他 rank 的输出先发回 rank 0。
- 调试用的 stderr 可以保留，但要接受不同 rank 的行交错。

- C++20 的 `std::osyncstream` 能避免同一进程内多个线程的输出交错，管不了多个 MPI 进程。

线程和 MPI 混用时有两个边界：

- `std::thread` 和 pthread 都只能在同一个进程里创建线程，不能跨进程创建 rank。
- 进程内的线程要调 MPI，先用 `MPI_Init_thread(&argc, &argv, required, &provided)` 声明级别；`required` 是你要的级别，`provided` 是实现实际给的级别，程序必须按 `provided` 退化。

每个 rank 请求 `MPI_THREAD_FUNNELED`，本机 Open MPI 给的也是 `MPI_THREAD_FUNNELED`；每个 rank 用 OpenMP 开 2 个线程做局部循环，只有主线程调用 MPI。如果 `provided` 只有 `MPI_THREAD_SINGLE`，整个 MPI 进程就必须单线程运行，连 OpenMP 线程也不能创建，不只是 MPI 调用期间不能有其他线程。

`provided` 低于 `required` 时，按下面的顺序退化：

- `MULTIPLE` 降到 `SERIALIZED`：所有 MPI 调用加一把进程内的锁。
- `SERIALIZED` 降到 `FUNNELED`：把 MPI 调用集中到主线程。
- `FUNNELED` 降到 `SINGLE`：不要在 MPI 进程里再开线程。

| 初始化/设施 | 允许的调用 | 线程数 | 错误处理 |
|---|---|---|---|
| `MPI_Init` | 未声明线程支持，按单线程用 | 单线程 | 返回码；默认 fatal |
| `MPI_THREAD_SINGLE` | 进程只有一个线程 | 1 | 返回码；默认 fatal |
| `MPI_THREAD_FUNNELED` | 多线程，但只有调用 `MPI_Init` 的线程能调 MPI | 多线程 | 返回码；默认 fatal |
| `MPI_THREAD_SERIALIZED` | 多线程，但同一时刻只能有一个线程调 MPI | 多线程 | 返回码；默认 fatal |
| `MPI_THREAD_MULTIPLE` | 任意线程可以同时调 MPI | 多线程 | 返回码；默认 fatal |
| OpenMP | 并行区里的线程共享进程，MPI 调用仍受上面的级别限制 | 由 `num_threads`/`OMP_NUM_THREADS` 定 | 无 MPI 返回码 |

`MPI_Query_thread` 查当前级别，`MPI_Is_thread_main` 判断当前线程是不是调用 `MPI_Init` 的那个。即使 `MULTIPLE`，也不要让多个线程同时用同一个 `MPI_Request` 或同一块通信缓冲区。

通信子可以再分。`MPI_Comm_split(comm, color, key, &newcomm)` 按颜色分组、按键排序，`MPI_Comm_free` 释放；`MPI_Comm_split_type(..., MPI_COMM_TYPE_SHARED, ...)` 是 MPI-3.0 起的接口，按共享内存节点分组，做 MPI+OpenMP 时常用。

每个 MPI 调用都要检查返回码。默认的 `MPI_ERRORS_ARE_FATAL` 会 abort 整个作业，调试时先换成 `MPI_ERRORS_RETURN`，再用 `MPI_Error_string` 打印。`MPI_Abort` 是异常终止，`MPI_Finalize` 是正常结束，两者不要混。

## 29.6 把点对点用对：梯形积分的三种写法

{{#fig ch29/trap_flow}}

梯形积分把 `[a,b]` 分成 n 个小区间，每个小区间的面积是 `h[f(x_i)+f(x_{i+1})]/2`，`h=(b-a)/n`。每个进程算自己那段区间的局部和，最后汇总到 rank 0。

n 不能被 p 整除时，不要假设整除。用 `local_n = n / p + (rank < n % p)` 分配，前 `n % p` 个 rank 多算一个；起始偏移是 `rank * (n/p) + min(rank, n%p)`。

rank 0 读入 `a`、`b`、`n`，三次 `MPI_Bcast` 分发，每个 rank 算局部和，非 0 号 `MPI_Send` 给 0 号，0 号按 rank 顺序累加。输出只打印 rank 0 看到的 `pi` 和相对误差，相对误差在 10⁻¹³ 量级，具体末几位会随编译器和归约顺序变。另外两点由代码保证：

- 三次 `MPI_Bcast` 后，每个 rank 的 `a`、`b`、`n` 相同。
- `if (rank != 0)` 分支让非 0 号只发一次，rank 0 收 p−1 次。

这三种写法在通信量和结果归属上不同：

| 写法 | 通信量 | 谁拿到结果 | 适用 |
|---|---|---|---|
| 点对点 `Send`/`Recv` | rank 0 收 p−1 次，线性 | 只有 rank 0 | 进程数小，或结果只需要 root |
| `MPI_Reduce` | 典型树形，约 log₂p 轮 | 只有 root | 结果只需要 root，进程数大 |
| `MPI_Allreduce` | 典型树形或蝶形，约 log₂p 轮 | 所有进程 | 每个进程都要用总和 |

浮点归约的顺序由实现决定，`MPI_Reduce` 不保证和串行逐位相同。比较结果时注意：

- 浮点用相对误差，不要用 `==`。
- 整数归约可以逐位比较。
- 归约顺序固定也不等于和串行逐位相同，编译器的向量化会改变顺序。

计时用 `MPI_Wtime()` 取墙钟秒数，`MPI_Wtick()` 查分辨率。计时协议分三步：

- 先 `MPI_Barrier` 对齐，让所有 rank 从同一时刻开始。
- 各进程记自己的起止，算出本地耗时。
- 再用 `MPI_Reduce(MPI_MAX)` 取最慢进程的时间。

```c
MPI_Barrier(comm);
double t0 = MPI_Wtime();
/* 本地计算 */
double local = MPI_Wtime() - t0;
double slowest = 0.0;
MPI_Reduce(&local, &slowest, 1, MPI_DOUBLE, MPI_MAX, 0, comm);
```

不要跨 rank 相减时间戳：不同节点的时钟不保证同步，`MPI_Wtime` 也不保证各 rank 的起点相同。`MPI_IN_PLACE` 可以让 root 把自己的输入直接放在接收缓冲区里，减少一次复制，但只在该集合操作允许时使用。

输入由 rank 0 读入后广播，输出由 rank 0 打印，这样终端 I/O 只发生在一个进程里。下一章把这里的局部和换成 `MPI_Reduce`，再讨论集合通信的树形和蝶形结构。

| `mpicc`/`mpicxx` | 编译 MPI 程序的包装脚本 | — | 忘了用包装脚本，头文件和库路径对不上 |
| `mpirun -np N` | 启动 N 个 rank | — | root 要加允许变量；超核要 `--oversubscribe` |
| `MPI_Init`/`MPI_Finalize` | 初始化和释放 MPI | — | 两者之间才能调 MPI；`Finalize` 后不能再调 |
| `MPI_Init_thread` | 带线程级别初始化 | — | `provided` 可能低于 `required` |
| `MPI_Comm_size`/`MPI_Comm_rank` | 取进程数和 rank | — | rank 是 0…p−1，不是 PID |
| `MPI_COMM_WORLD` | 默认通信子 | — | 集合通信要求组内都调用 |
| `MPI_Send`/`MPI_Recv` | 点对点收发 | 标准发送可能缓冲也可能阻塞；接收总阻塞 | 返回不等于对方收到；tag/通信子错会挂住 |
| `MPI_Ssend` | 同步发送 | 等匹配接收开始 | 所有 rank 先 Ssend 会死锁 |
| `MPI_Bsend` | 缓冲发送 | 用户先 `MPI_Buffer_attach` | 缓冲区不够会出错 |
| `MPI_Rsend` | 就绪发送 | 接收必须已经 posted | 没 posted 是错误，结果未定义 |
| `MPI_Isend`/`MPI_Irecv` | 非阻塞收发 | 立即返回请求 | 完成前不能复用缓冲区 |
| `MPI_Wait`/`MPI_Waitall`/`MPI_Test` | 等请求完成 | 阻塞或轮询 | 只保证本地完成，不保证对方收到 |
| `MPI_Sendrecv`/`MPI_Sendrecv_replace` | 一次完成发送和接收 | 由 MPI 调度 | 两个缓冲区不能重叠（`_replace` 除外） |
| `MPI_Status` | 接收状态 | — | 不要直接读字节数 |
| `MPI_Get_count` | 按接收类型算元素个数 | — | 派生类型可能返回 `MPI_UNDEFINED` |
| `MPI_Get_elements` | 按基本类型算元素个数 | — | 和 `Get_count` 的区别在派生类型 |

| `MPI_ANY_SOURCE`/`MPI_ANY_TAG` | 接收端通配 | — | 发送端不能通配；通信子没有通配 |
| `MPI_Probe`/`MPI_Iprobe` | 探测消息，不取走 | 阻塞/立即返回 | Probe 不删除消息；Probe 和 Recv 要配对 |
| `MPI_PROC_NULL` | 哑元 rank | 发送/接收立即返回 | 常用于边界，不能当普通 rank 算 |
| `MPI_Bcast` | 一对多广播 | 集合通信 | 组内所有 rank 都要调用 |
| `MPI_Reduce` | 归约到 root | 集合通信 | 浮点顺序不保证和串行相同 |
| `MPI_Wtime`/`MPI_Wtick` | 墙钟秒数和分辨率 | — | 不要跨 rank 相减时间戳 |

## 思考题

1. 预测：29.3 的环如果有 3 个进程，偶数先发/奇数先收的重排还能破环吗？如果进程数是奇数，边界怎么处理？

   <details><summary>提示</summary>

   3 个进程时，rank 0 和 2 先发，rank 1 先收；rank 0 发给 1 能匹配，rank 0 的 Send 返回后转去收来自左邻 rank 2 的消息，rank 2 的 Send 随即匹配，仍然能推进。奇数个进程时，rank p−1（偶数）发给 rank 0（偶数），rank 0 发完给 1 后也会转去接收，所以不会永久卡住。更稳妥的写法还是 `MPI_Sendrecv`，不要靠奇偶分支证明正确性。

   </details>

2. 找错：29.2 的 `MPI_Recv` 用 `MPI_ANY_SOURCE` 收两条不同来源、相同 tag 的消息，收到的顺序由什么决定？如果两条消息都到了，`MPI_Get_count` 能区分它们吗？

   <details><summary>提示</summary>

   由消息到达接收端的先后决定，不是发送端的调用顺序；不同发送者之间没有 non-overtaking 保证。两条都到了时，`MPI_Get_count` 只能告诉你当前这条的长度，不能区分是谁发的；要看 `status.MPI_SOURCE`，或者用指定 source 的 `MPI_Recv` 分别收。

   </details>

3. 权衡：29.6 的三种归约写法，点对点、`MPI_Reduce`、`MPI_Allreduce` 分别在什么进程数、消息大小和是否需要广播结果时更合适？

   <details><summary>提示</summary>

   点对点版在 p 很小时简单，p 大时 root 要收 p−1 次，线性汇总成为瓶颈；结果只需要 root 时用 `MPI_Reduce`，让实现选树形或蝶形；每个进程都要用总和时用 `MPI_Allreduce`，省掉“先 Reduce 再 Bcast”的两步。小消息时减少轮数和延迟更重要，大消息时减少总字节数、提高带宽利用率更重要。

   </details>

4. 迁移：把 29.5 的 `MPI_Init_thread(MPI_THREAD_FUNNELED)` 改成 `MPI_THREAD_MULTIPLE`，哪些 MPI 调用可以真正并发？如果实现只提供 `SERIALIZED`，程序要怎么退化？

   <details><summary>提示</summary>

   `MULTIPLE` 下不同线程可以同时调用 MPI，但同一个 `MPI_Request`、同一块缓冲区仍然只能由一个线程操作；锁和队列要自己保证。实现只给 `SERIALIZED` 时，所有 MPI 调用要放进同一把锁或同一个线程，其他线程只做本地计算，等主线程统一收发。不要假设 `provided` 一定等于 `required`。

   </details>
