# 第 23 章 C++17 并行算法与执行策略

```cpp
std::for_each(std::execution::par, v.begin(), v.end(), f);
```

同一行代码，编译链接都通过。`v` 小、`f` 轻时，`top` 里只看到少数线程，把 `f` 换成上千次 `sin` 后，线程数升到几十个。另一个程序在 `par` 的 lambda 里 `throw`，没有进 `catch`，直接 `terminate`。

两件事指向同一份契约：策略只给实现“可以并行”的许可，同时改掉了复杂度和异常规则。许可不等于请求，也不等于线程数。

## 23.1 执行策略是许可，不是请求

C++17 给一部分标准算法加了执行策略重载：`std::execution::seq`、`par`、`par_unseq`，类型分别是 `sequenced_policy`、`parallel_policy`、`parallel_unsequenced_policy`。C++20 增加 `unseq` 和 `unsequenced_policy`。

`std::is_execution_policy_v<P>` 用来识别策略类型，实现可以增加自己的策略，用户不能给这个 trait 加特化。策略对象本身没有线程数、块大小之类的参数。

{{#fig ch23/policy_contract}}

看第一行：只有 `seq` 和 `unseq` 保证元素函数都在调用线程上。看第二、三行：`par_unseq` 和 `unseq` 允许同一条线程上的两段元素函数交错，目的是让编译器把多个元素打包成一条 SIMD 指令。

四种策略的差别可以按“在哪执行、能不能交错”来记：

- `seq`：元素访问都在调用线程，不交错。算法自己规定了顺序的（例如 `for_each` 从 `first` 到 `last`）仍按该顺序；`reduce` 这类允许重排的算法在 `seq` 下也可能重排。
- `par`：可以在调用线程，也可以在库创建的线程；同一线程上的调用不交错，线程之间、迭代之间的顺序都不指定。
- `par_unseq`：可以在未指定的线程上以任意顺序执行，同一线程内还可以交错。
- `unseq`：只在调用线程内乱序、向量化，不创建并行线程。

`seq` 不是“普通重载的串行版”。它仍是策略重载，复杂度按策略版放宽，元素函数抛异常也按策略版的规则终止。`for_each(seq, …)` 的顺序能保住，但异常保不住。

“许可”有两层意思。实现可以在资源不足时退回串行，也可以在任务太小时根本不拆，反过来，写了 `par` 也不会自动把工作分好。标准只规定允许什么，不规定用几个线程、怎么分块。

{{#fig ch23/pstl_layers}}

## 23.2 哪些算法有策略重载：迭代器、复杂度与归约

有策略重载的算法是一张固定的名单，不是所有标准算法都有。常见的几类：

- 遍历、查找、计数：`for_each`、`for_each_n`、`find`、`find_if`、`any_of`、`all_of`、`none_of`、`count`、`count_if`；
- 比较、复制、变换：`mismatch`、`equal`、`search`、`copy`、`copy_if`、`move`、`transform`、`replace`、`replace_if`；
- 修改、划分、排序：`fill`、`generate`、`remove`、`unique`、`reverse`、`rotate`、`partition`、`sort`、`stable_sort`、`nth_element`；
- 最值、有序检查：`min_element`、`max_element`、`minmax_element`、`lexicographical_compare`、`is_sorted`；
- `<numeric>`：`reduce`、`transform_reduce`、`inclusive_scan`、`exclusive_scan`，以及两个 `transform_*_scan`。

并行归约要换成 `std::reduce` 或 `std::transform_reduce`，并行前缀和要换成 `inclusive_scan` 或 `exclusive_scan`。这不是改名：新算法明确允许重排，因此对操作有额外要求，策略版还有三条硬约束：

- 要求前向迭代器（forward iterator），不接受输入迭代器和输出迭代器；
- 策略版允许实现复制可平凡复制、可平凡析构的元素，不能依赖元素地址就是原对象；
- 复杂度从“至多 n 次”放宽到 O(n)，常数和额外遍历可能变大。

需要元素身份时，用 `std::reference_wrapper` 包一层，或者换成不依赖地址的写法。带副作用的函数也不要随手放进 `par`：调用次数和顺序都不再由你控制。

- `reduce` 的默认操作是 `std::plus<>`，返回类型由初值决定。它允许把元素重新排列，所以操作要满足结合律和交换律，浮点加法不满足结合律，末几位就可能不同。
- `transform_reduce` 有两种形式：先变换再归约，或对两个序列做点积。变换不作用在初值上，初值会被拷贝，返回类型也由初值决定，可以用 `std::invoke_result_t` 推导变换结果，`std::result_of` 从 C++17 起弃用、C++20 移除。
- `inclusive_scan` 的第 i 个输出包含第 i 个输入，`exclusive_scan` 不包含，并且必须给初值。两者只重排括号、不交换元素顺序，所以要求结合律，不要求交换律。

| 算法 | 策略重载 | 是否可归约 | 前缀和 | 异常 | 迭代器要求 |
|---|---|---|---|---|---|
| `accumulate` | 无 | 严格左折叠 | 否 | 传给调用者 | 输入迭代器 |
| `reduce` | 有 | 可重排，要求结合律和交换律 | 否 | `terminate` | 前向迭代器 |
| `partial_sum` | 无 | 严格顺序 | 是 | 传给调用者 | 输入迭代器 |
| `inclusive_scan` | 有 | 可重排括号，要求结合律 | 是 | `terminate` | 前向迭代器 |

## 23.3 异常与并行算法的契约

标准在四个策略小节里写了同一句话：元素访问函数因未捕获异常退出时，调用 `std::terminate`。`seq`、`par`、`par_unseq`、`unseq` 一个不少。

{{#fig ch23/exception_path}}

## 23.5 真实用法：日志计数与 map-reduce

`std::ranges::fold_left`（C++23）是顺序折叠，也不能传 `par`。要并行 ranges，C++20/23 只能先取出迭代器区间，再调用策略版算法；C++26（N5050）给多数 ranges 算法加了策略重载（例如 `ranges::for_each(par, …)`、`ranges::sort(par, …)`），但 `fold_left` 仍没有，本机 libstdc++ 15 也还没实现这些重载。

> **旧资料提示**：旧教程说 ranges 算法可以加执行策略。C++20/23 的 ranges 算法没有策略重载；C++26 给多数 ranges 算法加了，但本机 libstdc++ 15 没实现，`fold_left` 仍没有。要并行就先取 `begin()`/`end()`，或者用支持 C++26 的实现。第 40 章会讲这条。

C++26 的 `std::execution`（P2300，sender/receiver）是另一套模型。它提供 `schedule`、`then`、`when_all`、`bulk` 等组合子，用 `std::this_thread::sync_wait` 在边界上取结果：

```cpp
// C++26，本书环境（GCC 15 / Clang 21）尚不支持，未编译验证
auto work = std::execution::schedule(std::execution::get_parallel_scheduler())
          | std::execution::then([]{ return parse_line(); });
auto [value] = std::this_thread::sync_wait(std::move(work)).value();
```

它不是执行策略的替代品，也不是 `std::future` 的 drop-in：错误走 `upon_error`/`set_error` 通道，停止走 `set_stopped`，组合方式也不同。本机 GCC 15 连 `std::execution::schedule` 这个名字都没有。

{{#fig ch23/model_map}}

C++17 策略能控制的东西很少：没有线程数、没有块大小、没有 `reduction` 子句、没有调度器。需要这些旋钮时，用 OpenMP（第 22 章）或 TBB 的 `parallel_for`/`parallel_reduce`/`partitioner`。

后端选择要写清：libstdc++ 的选择是 PSTL + TBB（没有 TBB 头就退回串行），本机没装 libc++，它的实现未验证，MSVC 的情况本书环境也无法验证。不要写“C++17 并行算法一定用 TBB”，也不要把“加了 `par`”当成“一定开了线程”。

| 模型 | 线程数 | 块大小 | 调度 | 归约 | 异常 | 后端 |
|---|---|---|---|---|---|---|
| C++17 策略 | 不能指定 | 不能指定 | 实现决定 | `reduce` 等 | `terminate` | PSTL + TBB/串行 |
| OpenMP | `num_threads` | `schedule` 的 chunk | `static`/`dynamic`/`guided` | `reduction` | 区内捕获 | libgomp/libomp |
| TBB | `global_control` | `blocked_range` | `partitioner` | `parallel_reduce` | 等待点重抛 | oneTBB |
| pthread | 自己建 | 自己切 | 自己写 | 自己合并 | 自己处理 | 无算法库 |

pthread 一侧没有算法库，只能手工拆循环、手工合并，第 3、4 章的 API 不再重复。系统调用一侧也没有算法级对应，只有 `sched_setaffinity(2)` 影响线程落在哪个 CPU 上。

> **旧资料提示**：旧教程说 `std::async` 会保证用满硬件线程、不会超额申请。标准没有这个保证，线程数由实现决定；第 39 章会讲这条。

## 思考题

1. 23.1 的小工作量 `for_each(par)` 只用了一个线程，这是标准允许的吗？如果把元素数增加到 10⁷，线程数一定增加吗？

   <details><summary>提示</summary>

   允许。标准只给许可，实现可以因为任务太小退回串行，也可以始终只用调用线程。元素数增加会提高拆分的概率，但不保证线程数增加：后端、每元素工作量、机器负载都会影响结果。把 `23_1_backend` 的规模改几档多跑几次，观察 `small_threads` 和 `large_threads` 的变化。

   </details>

2. 23.4 的 `push_back` 在 `par` 下是数据竞争；如果改成 `par_unseq` 再加 `std::mutex`，是编译错误、运行时死锁，还是未定义行为？为什么？

   <details><summary>提示</summary>

   是未定义行为。`mutex::lock` 会和其他调用同步，属于 vectorization-unsafe，标准规定从 `par_unseq` 的元素函数里调用它是未定义行为。典型表现是同一线程上两段元素函数交错，一段持锁、另一段等锁，形成自死锁；编译器不会为此报错。

   </details>

3. 23.5 的日志计数，用 `transform_reduce` 合并整张 `unordered_map`、用每线程局部 map 再归并、用排序后 `inclusive_scan`，三种写法各自在什么数据规模下更合适？

   <details><summary>提示</summary>

   页面少、行数中等时，直接合并 `unordered_map` 最省代码；页面多、行数大时，局部 map 或按块归并能减少拷贝；如果日志已经按页面排序，`inclusive_scan` 只需扫描一遍。比较时把解析成本也算进去，并用 `23_5_log_bench` 的方法先预热、取中位数。

   </details>

4. 把 23.3 的异常捕获模式套到 OpenMP 的 `parallel for` 上，`exception_ptr` 应该放在哪里、由谁检查？和 `std::execution` 的 sender/receiver 错误通道有什么不同？

   <details><summary>提示</summary>

   每个线程一个槽，或一把锁保护的共享槽；在循环体内 `catch` 并写入，循环结束后由主线程检查并重抛。不能让异常穿出 `parallel` 区域。sender/receiver 把错误作为完成信号的一部分沿管道传递，由 `upon_error` 或 `sync_wait` 处理，不需要自己准备共享槽。

   </details>
