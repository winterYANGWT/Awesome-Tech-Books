# 第 41 章 进程与信号的旧坑

一个多线程服务器让工作线程 `fork` 出子进程去写日志，子进程立刻卡住。父进程的日志锁正被主线程持有，`fork` 只复制了调用它的那个线程，子进程里的锁却还是“已加锁”，属主已经不在了。

```c
static pthread_mutex_t log_mutex = PTHREAD_MUTEX_INITIALIZER;

void log_line(const char *s)
{
    pthread_mutex_lock(&log_mutex);
    write(STDOUT_FILENO, s, strlen(s));
    pthread_mutex_unlock(&log_mutex);
}
/* 主线程持有 log_mutex，工作线程 fork 后，子进程调用 log_line */
```

这一章按接口分组：信号、子进程通知、定时、`fork`、fd 继承、IPC、socket 激活。每个案例都先说旧写法当时解决了什么，再看它今天在哪里咬人。

## 41.1 `signal` → `sigaction`：语义、`SA_RESTART`、async-signal-safe

**旧写法**

```c
signal(SIGALRM, on_alarm);   /* 处理函数保持还是重置？带不带 SA_RESTART？ */
alarm(1);
```

**当时为什么这样写**：C 标准只提供 `signal`，一行就能装处理函数，早年的教程和示例都用它。它不要求记住 `struct sigaction` 的字段，也不要求先 `sigemptyset`。

**问题在哪**：`signal()` 的语义随实现，同一个程序换一个 libc 或换一组特性宏，重启行为就变了。

- SysV 语义：处理函数只运行一次，随后重置为 `SIG_DFL`。
- BSD 语义：处理函数保持，并且自动加上 `SA_RESTART`。
- glibc 2 的 `signal()` 默认走 BSD；特性宏不满足时退回 SysV。

处理函数还受另一条限制：只能调用 async-signal-safe 的函数。`printf`、`malloc`、`pthread_mutex_lock` 都不在 POSIX 的列表里，`malloc` 是线程安全的，但不是 async-signal-safe。处理函数可能打断 `malloc` 内部持锁的临界区，`errno` 也要先保存再恢复。

**取代它的**：用 `sigaction` 把三件事写清楚。

- `sa_handler` 或 `sa_sigaction`：处理函数。

**今天还用得着吗**：维护老代码时还会见到 `signal`，读的时候先确认它在这个平台上是不是 BSD 语义。新代码直接用 `sigaction`，代价只是多写几行。可重入和线程安全不是一回事：线程安全可以用锁实现，可重入要求不依赖可变的全局状态，`malloc` 是前者的例子，不是后者。

## 41.2 `SIGCHLD`、`waitpid` 与自管道 → `signalfd`/`pidfd`

**旧写法**

```c
static int selfpipe[2];
static void on_sigchld(int signo)
{
    unsigned char b = (unsigned char)signo;
    write(selfpipe[1], &b, 1);   /* 处理函数只 write */
}
/* 主循环把 selfpipe[0] 加进 epoll，可读时 waitpid(-1, ..., WNOHANG) */
```

**当时为什么这样写**：`SIGCHLD` 的默认动作是“忽略”，但子进程仍会变成僵尸，父进程必须 `waitpid`。在 `signalfd` 出现之前，自管道是把信号接进 `epoll` 的常见办法：处理函数写一个字节，主循环在事件循环里读。

**问题在哪**：`SIGCHLD` 会被合并。三个子进程几乎同时退出，未决位只有一位，处理函数可能只跑一次，如果处理函数里只 `waitpid` 一次，就留下两个僵尸。`waitpid` 本身在 async-signal-safe 列表里，但处理函数里循环回收会拖长中断。

- 自管道还有几个约束：管道要 `O_NONBLOCK`，否则处理函数可能阻塞在满管道上。
- 写失败会丢通知，主循环仍要 `waitpid(WNOHANG)` 扫干净。
- 两个 fd 才能接进 `epoll`，每个信号占一个字节。

**取代它的**：`signalfd` 适合已经有事件循环的服务器：屏蔽信号，创建 `signalfd`，加进 `epoll`，收到后读结构体，再 `waitpid` 回收。`pidfd_open` 给子进程一个句柄，`poll` 等它退出，`waitid(P_PIDFD)` 取状态，`pidfd_send_signal` 在 5.1 起可以对着句柄发信号，避免“PID 被复用后杀错进程”。

**今天还用得着吗**：自管道仍然合适：它不依赖 Linux，处理函数只调 `write`，能接进任何事件循环。`signalfd` 是 Linux 专用，而且要求进程统一屏蔽信号，和第三方库共用信号时容易打架。`pidfd` 不负责回收，普通服务器仍要 `waitpid`，它解决的是“等哪个进程”和“PID 复用”，不是“谁来收尸”。

## 41.3 `alarm`/`setitimer` → `timerfd`

**旧写法**

```c
alarm(1);                    /* 一次，秒级 */
setitimer(ITIMER_REAL, &it, NULL);   /* 微秒，可周期，信号是 SIGALRM */
```

**当时为什么这样写**：早期没有“定时器 fd”这种东西，进程能用的定时接口就是 `alarm` 和 `setitimer`，到期都送 `SIGALRM`。事件循环还没普及，程序本来就靠信号打断系统调用来做事。

**问题在哪**：`alarm` 和 `setitimer` 的局限不止一个。

- `alarm` 一次性、秒级，想周期就得在处理函数里重新 `alarm`。
- `setitimer` 支持微秒和周期，但 POSIX.1-2008 已标为 obsolescent。
- 两者共用 `SIGALRM`，会互相覆盖；到期走信号，进不了 `epoll`。

## 41.4 多线程进程里的 `fork` → `posix_spawn`

**旧写法**：多线程服务器在工作线程里直接 `fork`，子进程接着调用日志、内存分配、锁之类的库函数，出问题时用 `pthread_atfork(prepare, parent, child)` 在 fork 前后加锁、解锁。

**当时为什么这样写**：`fork` 的写时复制很便宜，子进程能直接继承已打开的连接和缓存，省掉重新初始化。`pthread_atfork` 看起来能解决锁的问题：prepare 里把所有相关 mutex 锁住，parent 和 child 里再解开。

**问题在哪**：`fork` 只复制调用它的那个线程，另外两个后果要一起看。

- 别的线程不存在，它们持有的锁却以“已加锁”复制过去。
- `pthread_atfork` 只覆盖注册过的锁，`malloc` 和库内部锁不在里面。
- prepare 要拿的锁可能正被别的线程持有，prepare 自己先阻塞。

## 41.5 close-on-exec 与 fd 传递：`fcntl` → `O_CLOEXEC`/`accept4`/`pipe2`/`SCM_RIGHTS`

**旧写法**

```c
int fd = open(path, O_RDONLY);
fcntl(fd, F_SETFD, FD_CLOEXEC);   /* 两步之间有一个窗口 */
```

**当时为什么这样写**：`O_CLOEXEC` 要 Linux 2.6.23 才有，`accept4` 要 2.6.28，`pipe2` 要 2.6.27。在那之前，创建 fd 的接口没有“顺手设 close-on-exec”的参数，只能在创建后补一次 `fcntl`。

**问题在哪**：`open` 返回和 `fcntl` 执行之间有一个窗口。

- fd 已经能被同一进程的其它线程看到。
- 另一个线程在这个窗口里 `fork` + `exec`，新程序继承这个 fd。
- 泄漏监听 socket、日志或凭据文件，就是安全问题。

`FD_CLOEXEC` 只影响 `exec`，不影响 `fork`。子进程继承父进程的 fd 是正常行为，除非 fd 标了 close-on-exec。

## 41.6 System V IPC → POSIX IPC 与 `memfd`

**旧写法**

```c
int id = shmget(IPC_PRIVATE, 4096, IPC_CREAT | 0600);
char *p = shmat(id, NULL, 0);
/* semget/semop/semctl、msgget/msgsnd/msgrcv 也是同一套 key 接口 */
```

**当时为什么这样写**：System V IPC 在 POSIX IPC 之前就普及了，`shmget`、`semget`、`msgget` 用 key 找对象，父子进程不需要约定文件名。老服务器和数据库至今还在用这套接口。

**问题在哪**：对象用 key 标识，不是 fd，不能加进 `epoll`。

- key 由 `ftok` 生成时可能碰撞，清理要 `shmctl`/`semctl`/`msgctl`。
- `shmctl(IPC_RMID)` 是标记删除，还有进程附着时共享内存段不会立刻消失；`msgctl`/`semctl` 的 `IPC_RMID` 立即删除。
- `SEM_UNDO` 只在进程退出时补偿计数，不是健壮锁。

另一个坑是 `msgrcv`：成功时返回复制进 `mtext` 的字节数，失败才返回 -1。若按“返回 0 就是失败”来判断，长度为零的消息返回值也是 0，会被误当成失败。这一点在老教程里经常写错。

- 命名对象在 `/dev/shm`；`shm_unlink` 只删名字，最后一个映射消失才释放。

**取代它的**：POSIX 接口都围绕名字和 fd。
- 共享内存：`shm_open` + `ftruncate` + `mmap`，用完 `shm_unlink`。
- 信号量：`sem_open` 或 `sem_init(pshared=1)`，`sem_t` 必须在共享内存里。
- 消息队列：`mq_open`/`mq_send`/`mq_receive`；匿名共享用 `memfd_create`。

`memfd_create`（3.17）创建没有名字的共享内存 fd，可以 `mmap`、可以 `SCM_RIGHTS` 传给别的进程，加 `MFD_ALLOW_SEALING` 后还能用 `fcntl(F_ADD_SEALS)` 冻结大小或内容。父子进程共享一块匿名内存，不需要先起名字。

`sem_init(pshared=1)` 要求 `sem_t` 本身在共享内存里，放在普通全局变量里父子各一份，`pshared=1` 也没有意义。本机 glibc 2.43 编译这些程序不需要 `-lrt`，链接 `-pthread` 就够。

**今天还用得着吗**：System V IPC 仍在老代码、数据库和某些容器工具里，读得懂、能用 `ipcs`/`ipcrm` 排查就行。新代码优先 POSIX 接口：名字直观、能 `unlink`、和 fd 模型更接近。需要匿名共享或把内存当 fd 传时，用 `memfd`，需要崩溃后仍能恢复的锁，用健壮互斥量，不要指望 `SEM_UNDO`。

## 41.7 xinetd → systemd socket 激活

**旧写法**：xinetd 监听端口，收到连接后 `fork`/`exec` 一个子服务，把 socket 接到子进程的 stdin/stdout，服务里直接 `read(0)`/`write(1)`。每个连接一个进程。

**当时为什么这样写**：服务不用自己处理监听、守护进程化和并发，配置文件里写一行就能上线。连接少、服务启动慢也没关系，`fork`/`exec` 的代价被网络延迟盖住。

**问题在哪**：每个连接一个进程，代价随连接数上来。

- 进程创建和地址空间初始化都不便宜。
- 服务的输入输出绑死在 0/1/2，改成“外部传 fd”要额外约定。
- 没有统一按需启动和依赖排序，端口何时可连要靠脚本保证。

xinetd 自己也会成为单点：它不跑，所有服务都不可用，它的配置和日志格式又是另一套。现代发行版默认不装它，但嵌入式和老机房还在用。

{{#fig ch41/socket_activation}}

图里 systemd 先 `bind`/`listen`，连接到了才启动服务，监听 fd 作为 3 号传进去，服务不用自己监听。连接在服务启动前到达也不会丢，因为 socket 已经在监听，连接排在 backlog 里。

- **取代它的**：systemd 的 `.socket` 负责监听，`.service` 启动时接收 fd。
- 监听 fd 从 3 开始，`LISTEN_FDS` 是数量，`LISTEN_PID` 是目标进程。

- `Accept=no` 由服务自己 `accept`；`Accept=yes` 每个连接起一个实例。

**今天还用得着吗**：xinetd 在嵌入式和老系统里还能见到，读配置时注意它每个连接起一个进程。systemd socket 激活是 Linux 发行版的主流做法，优点是按需启动、能并行启动、服务重启时监听 socket 不丢连接。它不是 POSIX 标准，换到非 systemd 的环境要自己实现“fd 3 + 环境变量”的约定，或者退回服务自己 `bind`。

## 思考题

1. （预测）`SIGCHLD` 的处理函数里只设标志、不 `waitpid`，子进程会变成僵尸吗？如果改成 `SIG_IGN` 呢？

   <details><summary>提示</summary>

   会。默认动作是“忽略”，但这里的忽略只是不采取动作，退出状态仍留在进程表里，父进程必须 `waitpid`。把处置显式设成 `SIG_IGN`（或给 `SIGCHLD` 设 `SA_NOCLDWAIT`）才会自动回收，POSIX 对 `SIG_IGN` 的行为留了余地，Linux 上是不产生僵尸。

   </details>

2. （找错）41.4 的 fork 死锁里，子进程继承的 mutex 处于什么状态？`pthread_atfork` 的 prepare 能救它吗？

   <details><summary>提示</summary>

   继承时 mutex 是“已加锁”，属主是父进程里那个不存在于子进程的线程。如果 prepare 在 fork 前拿到这把锁，父子回调里再解开，能救这一把，但它只覆盖注册过的锁，`malloc` 和库内部的锁不在其中，prepare 自己也可能阻塞在别人持有的锁上。

   </details>

3. （权衡）`signalfd` 和自管道都能把信号变成 fd，什么时候自管道仍然更合适？

   <details><summary>提示</summary>

   自管道不依赖 Linux，处理函数只调 `write`，能接进任何事件循环，也不需要全进程统一屏蔽信号。`signalfd` 要和 `pthread_sigmask` 配合，和第三方库的信号处理容易冲突，需要跨平台或库代码不能改信号屏蔽字时，自管道更稳。

   </details>

4. （迁移）把 41.5 的 `fcntl` 写法改成 `accept4`，哪些错误处理要跟着变？

   <details><summary>提示</summary>

   `accept4` 把“接受连接”和“设 `SOCK_NONBLOCK`/`SOCK_CLOEXEC`”合成一次调用，失败时返回 -1 并设 `errno`，不会留下一个已经接受、标志还没设的 fd。要处理 `EINTR`、`EAGAIN`（非阻塞监听 fd）、`EMFILE`/`ENFILE`，并且 `flags` 只能是这两个之一，老内核不支持 `accept4` 时要退回 `accept` 加 `fcntl`，但那个窗口又回来了。

   </details>
