# 第 6 章 读写锁与一次性初始化

一个 DNS 缓存 99.9% 的请求是查询、0.1% 是更新，换成读写锁后查询吞吐反而下降。另一个服务用“先检查指针、为空才加锁”的双重检查锁做懒初始化，压测时偶尔读到半构造对象。两个问题都与读有关：读锁并不便宜，无锁读也不安全。

## 6.1 读多写少与读写锁

读写锁（reader-writer lock）允许多个读者同时持有读锁，写者独占。C++14 有 `std::shared_timed_mutex`，C++17 有 `std::shared_mutex`；读锁用 `std::shared_lock`，写锁用 `std::lock_guard`、`std::unique_lock` 或 `std::scoped_lock`。

| 接口 | 标准版本 | 读锁 | 写锁 | 超时 | 跨进程 | 优先级旋钮 | 可升级 |
|---|---|---|---|---|---|---|---|
| `std::shared_mutex` | C++17 | `std::shared_lock` | `lock_guard`/`unique_lock`/`scoped_lock` | 不保证 | 不提供 | 无 | 无 |
| `std::shared_timed_mutex` | C++14 | `std::shared_lock` | `lock_guard`/`unique_lock` | `try_lock_shared_for`/`until` | 不提供 | 无 | 无 |
| `pthread_rwlock_t` | POSIX.1-2001 | `pthread_rwlock_rdlock` | `pthread_rwlock_wrlock` | `timedrdlock`/`timedwrlock` | `pshared` + 共享内存 | `setkind_np`（GNU） | 无 |

`std::shared_mutex` 可能只是 `std::shared_timed_mutex` 的同义词，标准不要求它更轻。需要限时接口时直接用 `shared_timed_mutex`，它的 `try_lock_shared_for`/`until` 超时返回 `false`，不抛超时异常。

`std::shared_lock` 只能管共享锁，不能升级成写锁。需要“查不到就插入”时，先释放读锁，再拿写锁复查。

| pthread 的坑 | 说明 |
|---|---|
| 没有 RAII | 每条路径自己解锁，包括提前 `return` |
| 错误码 | 返回错误码本身，不设置 `errno` |

pthread 接口没有 RAII：每个 `rdlock`、`wrlock` 都必须配一个 `unlock`，每条路径（包括提前 `return`）都要自己保证。示例用 `CHECK` 宏检查每个调用的返回码；pthread 函数返回错误码本身，不设置 `errno`。

- 每个加锁分支都要有对应的解锁，包括错误路径。
- `pthread_rwlock_unlock` 不区分调用者持有的是读锁还是写锁。
- 销毁仍在使用的锁是未定义行为。
- 跨进程要同时设 `pshared` 并把锁本身放进共享内存。

链表查询只读，插入要独占。读线程只查预置的 0..999，写线程插入 1000..2999，所以最后长度固定，校验不依赖调度顺序。

> **旧资料提示**：旧教程里说 pthread 原本没有读写锁。POSIX.1-2001 已经标准化 `pthread_rwlock_*`；C++14 有 `shared_timed_mutex`，C++17 有 `shared_mutex`，见 [37.4 节](ch37.md)。

## 6.2 读写锁的代价、公平性与实现

读写锁的内部状态至少有四项：活动读者数、等待读者数、写者是否持有、等待写者数。读锁要原子加计数，写锁要等读者清零，解锁时要决定唤醒读者还是写者。

{{#fig ch06/rwlock_impl}}

用“一个互斥量 + 两个条件变量”可以写一个最小实现：读者在“无写者且没有等待写者”时进入，写者在“无写者且无读者”时进入。下面这个版本让写者优先，写者排队后新读者也一起等：

三个测试分别看到：

- 5 个读者能同时持有。
- 读者持有时写者进不来，读者退出后才进。
- 写者排队后，新读者不再插队。

写者优先减少了写者饥饿，代价是读者可能排队。`active_readers_` 减到 0 时只唤醒一个写者；写者解锁时如果还有等待写者，就继续唤醒写者，否则用 `notify_all` 放读者进来。


写者等待随读者数增加。示例让读者按 1 ms 的间隔依次到达，是为了稳定复现“读者不断插队”。

真实负载里是否饥饿取决于到达节奏和实现。如果读者一直重入，写者等不到所有读者同时退出的窗口，就会一直等到读者停下。

POSIX 不规定读者/写者优先级。glibc 默认 `PTHREAD_RWLOCK_PREFER_READER_NP`，读锁可递归持有，写者可能饥饿。`pthread_rwlockattr_setkind_np` 可设 `PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP`，但 `PTHREAD_RWLOCK_PREFER_WRITER_NP` 在 glibc 里被忽略。

| 负载 | 更合适的锁 |
|---|---|
| 读多写少 | 读写锁，测过再用 |
| 读写都频繁 | 整表 mutex |

这些都不是可移植接口；`std::shared_mutex` 没有优先级旋钮，标准也不保证公平，写者饥饿是合法行为。

需要这些旋钮时只能用 pthread，并接受 `_np` 的可移植性代价。写者优先也不是免费的：写者排队时新读者一起等，读多写少的负载可能被一个不常出现的写者拖住。

- 读多写少：读写锁可能划算，但仍要测量。
- 读写都频繁：整表互斥往往更简单。
- 每结点锁：并发度高，固定开销也高。

细粒度锁不一定更快。每结点一把锁会增加加解锁次数和 cache line 流量；旧资料里 2011 年的绝对秒数不能复用，只保留“读多写少才占优、细粒度不一定快”的结论。

| 方案 | 并发度 | 主要代价 |
|---|---|---|
| 整表一把锁 | 最低 | 所有操作串行，临界区短时锁本身占比高 |
| 每桶一把读写锁 | 按桶并发 | 桶多则锁对象多，可能伪共享 |
| 每结点一把锁 | 最高 | 每次移动都加解锁，通常比整表锁慢 |

> **旧资料提示**：旧教程用 2011 年机器上的绝对秒数证明“读写锁总是更快”或“细粒度锁更快”。绝对时间不可复用，结论要在目标机器上重测，见 [40.3 节](ch40.md)。

## 6.3 分桶与细粒度锁

把一张大表按哈希分成固定数量的桶，每个桶一把 `std::shared_mutex`，读写只锁对应的桶。桶数取 2 的幂或质数，按 `hash(key) % bucket_count` 定位；键分布不均时，质数通常更稳。

{{#fig ch06/buckets}}

桶号只由哈希值决定，同一个键永远落在同一个桶；因此单键的读写只需要一把桶锁。桶与桶之间没有共享状态，不同桶的操作可以真正并行。

桶锁只保护桶内的 `unordered_map`。跨桶的不变量要另外设计，不能指望多把桶锁自动给你一致快照。

下面用 64 个桶，8 个线程做插入、更新、查询、删除，最后逐键校验；快照按桶下标从小到大锁住所有桶，复制完再逆序解锁：

|---|---|

快照返回后检查两类不变量：

- 单键校验：值错误 0 处。
- 快照校验：镜像错误 0 处。

总操作数和条目数也固定。

快照期间写者被挡住，所以复制到的每个 `Record` 都满足 `mirrored == generation + key`。

如果只锁前 32 个桶、复制后再锁后 32 个，前后两半来自不同时刻。写者又只改一个桶时，快照就可能把旧的一半和新的一半拼在一起。

- 单键读写：只锁一个桶。
- 一致快照：按同一顺序锁全部桶。

`std::scoped_lock` 只能锁编译期已知个数的锁。运行期的桶数组要自己写下标循环。示例把循环封在 `AllBuckets` 的构造和析构里，异常时也能逆序解锁。

所有代码必须用同一顺序；有人按 0→63、有人按 63→0，就会死锁。

示例选 64 个桶，是因为 8 个线程下每个线程平均分到 8 个桶，冲突概率低，锁对象也不至于太多。实际桶数要按并发写量、键分布和缓存大小测。

- 桶数太少：哈希冲突和锁争用一起上升。
- 桶数太多：内存和锁对象之间的 cache line 冲突上升。

桶数太少会争用，太多会浪费内存并增加锁对象之间的 cache line 冲突。锁对象相邻时可以 `alignas(64)` 填充，让每把锁独占一条缓存行。

每结点一把锁（手递手）并发度更高，但每次移动都要加解锁。`std::mutex` 不可移动，结点里放锁要自定义构造/析构，或者用 `unique_ptr<std::mutex>`。容器的迭代器、异常安全和内存回收留到第 14 章。

## 6.4 一次性初始化：双重检查锁为什么错

朴素做法是每次访问都用 `std::unique_lock` 包住“检查指针 + 初始化”，正确，但所有线程都排队。初始化完成后，后续访问仍要为一次检查加锁、解锁。

```cpp
std::unique_lock<std::mutex> lock(g_mutex);
if (g_config == nullptr) g_config = new Config;
lock.unlock();
```

报告里 `Read of size 8` 在 `:20`，是锁外的 `if (g_config == nullptr)`。`Previous write of size 8` 在 `:23`，旁边标着 `mutexes: write M0`。锁外的读和锁内的写之间没有先行发生（happens-before）关系，构成数据竞争。

另一个线程可能看到“指针已赋值、对象还没构造完”的中间状态；TSan 只报第一次冲突，后面的字段竞争不再展开。

- 第一次：恰好一个线程执行初始化，其他线程睡眠等待。
- 之后：一次原子检查，不再执行初始化函数。
- 抛异常：这次不算完成，下一次重新执行。

正确做法是 `std::call_once` 加 `std::once_flag`，或者 C++11 起线程安全的函数内局部 `static`。`call_once` 保证所有调用中恰好一个执行初始化，其他调用阻塞到它完成。

初始化函数抛异常时标志不会置位，下一次调用会重试；成功返回后，所有被动调用都能看到初始化结果。`call_once` 的开销主要在第一次，成功之后后续调用不再执行初始化函数，只剩一次完成状态检查。

同一线程在初始化函数里再次调用同一个 `once_flag` 会等自己，实际会死锁。初始化函数可以是成员函数，用 `this` 传参；`once_flag` 本身不可拷贝、不可移动，通常作为类成员或全局对象。

- C++：异常会传回调用者，标志保持未完成。
- C：没有异常，失败状态要自己记录。

`pthread_once` 不负责析构，也没有异常；初始化函数失败只能自己用返回值或全局状态报告。C++ 的 `call_once` 会把异常继续抛给调用者。

- `pthread_once` 只保证初始化函数调用一次，对象什么时候释放要自己安排。
- `call_once` 的“只执行一次”包括异常：失败的那次不算完成，下一次会再试。

| 方案 | 首次开销 | 后续开销 | 异常安全 | 能否析构 | 适用场景 |
|---|---|---|---|---|---|
| 每次加锁 | 加锁 + 检查 | 每次加锁 | RAII 保证解锁 | 能 | 初始化很便宜、调用不频繁 |
| DCLP | 加锁 + 构造 | 锁外读 | 有数据竞争 | 能，但可能读到半构造对象 | 不要用 |
| `std::call_once` | 一个线程执行，其他等待 | 一次原子检查 | 抛出后下次重试 | 对象自己管理 | 连接、配置、单例 |
| 局部 `static` | 一个线程构造，其他等待 | 一次检查 | 抛出后下次重试 | 程序退出时析构 | 函数级单例 |
| `pthread_once` | 一个线程执行，其他等待 | 无操作 | 无异常机制 | 不负责析构 | C 代码、长期存活的全局对象 |

C++20 的 `std::atomic<std::shared_ptr<T>>` 可以原子读写 `shared_ptr`，但 libstdc++ 15 上 `is_lock_free()` 为 `false`，不能把无锁算法建立在这个假设上。它只让 `shared_ptr` 本身的读写原子，不能取代 `call_once` 的“只初始化一次”语义。

> **旧资料提示**：双重检查锁加普通指针的懒初始化，在 C++11 起可以直接换成局部 `static` 或 `call_once`。DCLP 的锁外读是数据竞争，见 [38.2 节](ch38.md)。

## 6.5 静态初始化、`constexpr` 与 `constinit`

全局/静态对象的动态初始化顺序在不同翻译单元之间未指定。一个全局对象在构造时使用另一个还没构造的全局对象，就是静态初始化顺序问题。

例如日志对象在构造时读取全局配置，而配置对象在另一个翻译单元里，链接顺序一变，日志可能先构造，读到的就是零初始化后的空配置。把配置改成 `constexpr` 表或 `constinit` 变量，才能保证它在 `main` 之前可用。

{{#fig ch06/static_init}}

`constinit` 不能替代 `constexpr`：它只保证初始化时机，不保证值能在编译期使用。`g_config`、`g_config_mutex`、`g_requests` 都在 `main` 之前就绪；`g_squares` 由 `constexpr` 函数在编译期算好，`static_assert` 直接检查结果。

`constinit` 适合全局的 `std::mutex`、原子变量、配置表。它不能解决运行期才有的依赖。

- `constinit` 只约束初始化发生在静态阶段，不要求 `constexpr` 求值。
- `constinit` 本身不保证变量是常量表达式；要在 `static_assert` 里用，仍然需要 `constexpr`。
- 把需要运行期构造的类型（例如调用非 `constexpr` 函数构造的 `std::vector`）声明成 `constinit`，编译会直接失败。

函数内局部 `static` 的初始化是懒加载、线程安全的（C++11 起），但析构顺序在程序退出时由实现管理。其他线程不能在析构开始后继续使用它；需要跨线程长期使用时，通常让对象活到进程结束，或者显式管理生命周期。

`std::atomic` 的默认构造在 C++20 起值初始化；`ATOMIC_VAR_INIT`/`ATOMIC_FLAG_INIT` 已弃用，新代码直接写 `std::atomic<int> x{0};`、`std::atomic_flag f;`。`constexpr` 不等于线程安全，它只保证初始化阶段没有竞争。

## 速查

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `std::shared_mutex` | C++17 的读写锁 | 读锁共享、写锁独占；无优先级旋钮 |
| `std::shared_timed_mutex` | C++14 的带超时读写锁 | `try_lock_shared_for`/`until` |
| `std::shared_lock` | 管读锁的 RAII | 构造加共享锁，析构解锁 |
| `std::unique_lock`/`lock_guard` | 管写锁的 RAII | 写锁独占 |
| `pthread_rwlock_t` | POSIX 读写锁 | `rdlock`/`wrlock`/`unlock` 必须配对 |
| `pthread_rwlockattr_setpshared` | 跨进程读写锁 | 锁本身要放在共享内存里 |
| `pthread_rwlockattr_setkind_np` | glibc 的读者/写者偏好 | GNU 扩展；`PREFER_WRITER_NP` 被忽略 |
| `std::call_once`/`std::once_flag` | 一次性初始化 | 异常不置位，下次重试；不要递归 |
| `pthread_once`/`PTHREAD_ONCE_INIT` | C 接口的一次性初始化 | 不析构、无异常 |
| 函数内 `static` | 懒加载单例 | C++11 起线程安全；析构由实现管理 |
| `constexpr` | 编译期求值 | 只保证初始化阶段，不等于线程安全 |
| `constinit` | 强制静态初始化 | C++20；不要求 `const` |
| `std::atomic<T> x{0}` | 原子变量显式初始化 | C++20 起默认构造值初始化 |
| `ATOMIC_VAR_INIT`/`ATOMIC_FLAG_INIT` | 旧式原子初始化 | C++20 起弃用 |

## 思考题

1. 把 `6_1_rwlock_bench.cpp` 的读比例从 99.9% 降到 80%，`shared_mutex` 和 `mutex` 的耗时谁更低？如果读临界区只有一条 `map::find` 呢？

   <details><summary>提示</summary>

   80% 时写者已经频繁拿走独占锁，读写锁的读者计数和唤醒开销很难摊薄，通常是 `mutex` 更低。临界区只剩一条 `find` 时，锁本身占主导，`shared_mutex` 的优势更小；用示例改比例和临界区实测，不要背结论。

   </details>

2. 把 `6_4_dclp.cpp` 里的 `p` 改成 `std::atomic<Config*>`、仍用 `p = new Config`，能消除竞争吗？对象的构造和指针的发布之间还需要什么？

   <details><summary>提示</summary>

   指针本身的读写成原子操作后，指针不再撕裂，但 `new Config` 的构造和 `p.store(...)` 仍是两步；其他线程可能 `load` 到非空指针时构造还没完成。要用 release store 发布、acquire load 读取，或者直接用 `call_once`/局部 `static`。

   </details>

3. 一个 64 桶的哈希表，读操作占 95%，快照每分钟一次；用每桶 `shared_mutex`、整表 `shared_mutex` 还是 RCU 式复制，各自在什么条件下更好？

   <details><summary>提示</summary>

   每桶锁在读写都频繁、快照能按固定顺序锁全部桶时合适；整表读写锁实现简单，但所有桶共享一个读者计数，桶多时争用明显；RCU 式复制让读者完全不加锁，适合读极多、写很少且能接受额外内存和回收延迟的场景，代价是写者要复制和替换整份数据。

   </details>

4. 把 `6_3_bucket_map.cpp` 的快照改成“只锁前 32 个桶、复制后再锁后 32 个”，会读到什么？如果写者只改一个桶呢？

   <details><summary>提示</summary>

   前后两半来自不同时刻，快照不再是同一时刻的一致视图；如果写者只改后 32 个桶里的一个键，前半可能是旧值，后半是新值。写者只改一个桶时，桶内仍然一致，但跨桶的不变量（例如两个键的和）可能被破坏。

   </details>
