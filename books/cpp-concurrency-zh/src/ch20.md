# 第 20 章 取消与关闭

主线程想停掉后台索引线程。第一版直接 `pthread_cancel`，线程死在 `malloc` 里，堆锁再也没释放；第二版换成 `std::atomic<bool>` 标志，线程却睡在 `condition_variable::wait` 上，永远没机会看这个标志。

```cpp
pthread_cancel(index_thread);   // 线程可能停在 malloc 内部
stop.store(true);               // 线程睡在 cv.wait 上，看不到
```

取消不是发一个信号，而是让线程在安全点自己退出。发起方请求，目标方在检查点或等待返回后响应，双方对“什么时候算停”有共同定义。

## 20.1 为什么不能杀死线程：协作取消的三要素

{{#fig ch20/cancel_levels}}

三档方式的差别不在“快不快”，而在中断点由谁选。

- 随时杀死：由发起方选，线程可能停在半条赋值语句上，C++ 析构不保证。
- 延迟取消：由取消点选，线程走到取消点才响应，资源仍要靠清理函数。
- 协作停止：由目标线程自己选，清理代码能完整跑完。

{{#figref ch20/cancel_levels}} 里最下面一档需要三样东西。

- 一个停止标志，让目标线程知道“该退了”。
- 一组检查点，让目标线程在循环里、任务边界上主动查这个标志。
- 一个能被唤醒的阻塞等待，让睡着的线程醒来重查。

缺一个，线程就可能“看到了标志但还在睡”，或者“醒了但已经晚了”。

最简单的标志是 `std::atomic<bool>`。工作线程在循环里检查它，主线程置位后 `join`。它不处理阻塞等待，所以只适合纯计算循环。

## 20.2 jthread 与 stop_token：标准库的协作停止

`std::jthread` 析构时若仍 joinable，先 `request_stop()` 再 `join()`。如果可调用对象的第一个参数是 `std::stop_token`，`jthread` 会把内部 `stop_source` 的 token 传进去；否则按普通 `std::thread` 的方式调用。

{{#fig ch20/stop_token}}

`stop_source::request_stop()` 是线程安全的：第一次真正发出请求时返回 `true`，之后再调用返回 `false`，停止请求不能撤回。

- `stop_token::stop_requested()` 查询是否已请求，不会打断线程。
- `stop_token::stop_possible()` 查询这个 token 是否还可能收到请求；默认构造的 token 返回 `false`。
- `std::stop_callback` 在 `request_stop()` 的调用线程上同步执行。

回调要短、不能阻塞，也不能抛异常；抛异常会 `terminate`。

- 回调对象的析构会等正在执行的回调返回；如果回调在另一个线程上跑，析构会阻塞。
- 不要在回调里销毁自己所在的 `stop_callback`。
- 标准不规定多个回调的执行顺序，所以不要依赖注册顺序。

## 20.3 阻塞等待怎么被唤醒：condition_variable_any + stop_token / stop_callback

{{#fig ch20/cv_stop}}

C++20 的 `std::condition_variable_any::wait(lock, token, pred)` 会在等待期间注册停止回调。停止请求到来时，等待被唤醒并返回 `pred()` 的结果。

- 谓词要把“已请求停止”算进去，否则停止请求到来时 `wait` 可能返回 `false`，调用方必须检查返回值。
- 把停止写进谓词，才能用返回 `true` 表示“可以退出”；返回 `true` 只表示谓词成立，不表示没有停止请求。
- 回调的注册只覆盖这一次等待；下一次 `wait` 会重新注册。

`std::condition_variable` 没有这个重载，只能自己用 `stop_callback` 调 `notify_all()`。用回调唤醒 `condition_variable` 时，回调对象必须活到等待结束；通常把它放在等待循环外面的作用域里，确保析构在 `wait` 返回之后。

丢失唤醒的经典写法是先检查 `stop_requested()`，再 `wait()`。如果停止请求正好在这两步之间到来，线程会睡下去；`cv_any` 的 token 重载和 `stop_callback` 都是为了关掉这个窗口。

`wait_for(1ms)` 轮询能工作，但代价不小。

- 每次超时都会唤醒一次，线程多时定时器开销明显。

- 它只应作为没有标准设施时的退路。

## 20.4 pthread_cancel、清理函数与取消点

`pthread_cancel` 默认延迟取消，取消状态默认 enabled。

- `pthread_setcancelstate(PTHREAD_CANCEL_DISABLE/ENABLE, ...)` 控制是否响应；关掉后请求排队，重新打开才响应。
- `pthread_setcanceltype(PTHREAD_CANCEL_DEFERRED/ASYNCHRONOUS, ...)` 控制何时响应；异步取消可以在任意指令处发生，危险得多。

取消点是 POSIX 列出的一组函数，例如 `pthread_join`、`pthread_cond_wait`、`sem_wait`、`sigwait`，以及 `read`、`write`、`open`、`close` 等可能阻塞的调用；完整列表看 `pthreads(7)`。在取消点之外，延迟取消不会生效，可以显式调用 `pthread_testcancel()`。

`pthread_cleanup_push`/`pthread_cleanup_pop` 把清理函数压入线程的清理栈。取消发生时按后进先出执行，用来解锁互斥量、关闭 fd、释放内存。两个宏必须在同一作用域内配对，否则编译不过，用 `return`、`break`、`continue`、`goto` 提前离开这一对宏也是未定义行为。

{{#fig ch20/cancel_points}}

C++ 对象在 `pthread_cancel` 下不保证析构。异步取消更危险，可能在构造函数、`new`、锁的内部状态中间打断。

- C++ 代码优先用 `stop_token`。
- 必须用 `pthread_cancel` 时，把临界区设为不可取消。
- 或者只在线程的 C 风格边界上取消，让清理函数负责资源。

|---|---|---|---|
| C++20 `stop_token` / `jthread` | 协作式：请求停止，目标线程查询或在可中断等待中返回 | 目标线程正常退出，C++ 析构保证执行；`stop_callback` 做唤醒、关 fd | 不能强制；不检查 token 的线程会一直跑 |

| MPI `MPI_Cancel` | 只标记未完成的非阻塞通信请求；调用是局部的，可能稍后才真正取消 | 之后还要 `MPI_Wait`/`MPI_Test`；用 `MPI_Test_cancelled` 区分成功与正常完成 | 阻塞的 `MPI_Send`/`MPI_Recv` 不能从外部取消 |

## 20.5 关闭顺序：先全部请求停止，再统一 join

{{#fig ch20/shutdown_order}}

关闭一组线程时，先对全部线程 `request_stop()`（或置标志并唤醒），再逐个 `join()`。

- 这样各线程可以并行清理，关闭总时间接近最慢的那个线程。
- 反过来“通知一个、等一个”会让关闭时间变成各线程清理时间之和。
- 如果某个线程在等另一个线程的资源，串行关闭还可能死锁。

关闭还要处理几件事。

- 幂等性：重复调用 `shutdown()` 不应重复 `join`、不应重复释放；用状态机（`running`/`closing`/`closed`）或 `std::once_flag` 保护。
- 排空和丢弃要显式选择：排空是“不再接受新任务，执行完队列再退”，丢弃是“立即停，未执行的任务返回失败”。
- 线程池（第 19 章）和服务器（第 33 章）都要在接口上说清是哪一种。
- `std::vector<std::jthread>` 的析构是逐个元素先 `request_stop()` 再 `join()`，不会先全部请求停止；要并行清理仍要手动先请求、再统一 `join`。
- 不要从工作线程 `join` 自己，会死锁；不要让 `jthread` 的析构在持有锁时等待，回调或析构可能重入。

关闭路径本身要无锁，或只使用固定顺序的锁。

## 速查

| 要素 | 作用 | 常见位置 / 注意 |
|---|---|---|
| 停止标志 | 让目标线程知道“该退了” | `std::atomic<bool>`、`std::stop_token`；不要用普通 `bool` |
| 检查点 | 目标线程主动查标志 | 循环每轮、每批任务后、任务边界；纯计算循环没有阻塞，检查点就够 |
| 可唤醒等待 | 让睡着的线程醒来查标志 | `cv_any.wait(lock, token, pred)`；`condition_variable` 要配 `stop_callback` 调 `notify_all` |
| 清理 | 退出前释放锁、fd、内存 | C++ 用 RAII；pthread 用清理栈；两者都不要依赖“线程被杀后还会析构” |

| 接口 | 作用 | 生命周期 / 注意 |
|---|---|---|
| `std::jthread` | 若 joinable，析构先 `request_stop()` 再 `join()` | 只保证请求和等待，不保证线程很快停 |
| `stop_source::request_stop()` | 发出停止请求 | 线程安全；第一次返回 true，之后返回 false |
| `stop_token::stop_requested()` | 查询是否已请求 | 不会打断线程，只是查询 |
| `stop_token::stop_possible()` | 查询是否还可能请求 | 默认构造的 token 返回 false |
| `std::stop_callback` | 停止时执行回调 | 在 `request_stop` 的调用线程上同步执行；要短、不能抛异常；析构会等回调返回 |
| `cv_any.wait(lock, token, pred)` | 可被停止请求唤醒的等待 | 等待期间注册回调；返回 `pred()` 的结果；谓词要包含停止条件 |

| pthread 接口 | 作用 | 注意 |
|---|---|---|
| `pthread_cancel` | 发取消请求 | 默认延迟取消；返回 0 只表示请求已排队 |
| `pthread_setcancelstate` | 开/关取消响应 | 默认 enabled；关掉后请求排队，重新打开才响应 |
| `pthread_setcanceltype` | 选延迟或异步 | 默认 `PTHREAD_CANCEL_DEFERRED`；异步可在任意指令处生效 |
| `pthread_testcancel` | 显式取消点 | 长计算循环里可以自己插 |
| `pthread_cleanup_push`/`pop` | 压入/弹出清理函数 | 同一作用域配对；取消和 `pthread_exit` 时执行，正常 `return` 不执行 |
| `pthread_join` | 回收线程 | 被取消的线程返回 `PTHREAD_CANCELED`；普通互斥量不会因持有者死亡自动解锁 |

## 思考题

1. 20.1 的 `20_1_pthread_async.c` 如果在线程持有互斥量时被异步取消，另一个线程调用 `pthread_mutex_lock` 会返回什么？如果改成延迟取消，结果有什么不同？

   <details><summary>提示</summary>

   普通互斥量的 `pthread_mutex_lock` 不会返回错误，它会一直阻塞；锁的持有者已经被杀死，锁没有释放。改成延迟取消后，线程如果没有走到取消点，取消请求一直挂着，主线程仍然阻塞；走到取消点后如果没有清理函数，锁还是留着。区别是“什么时候死”，不是“死得安不安全”。

   </details>

2. 20.3 的 `20_3_cv_lost.cpp` 已经置了 `atomic<bool>` 标志，为什么消费者还睡死？把 `wait` 改成 `wait_for(1ms)` 能修好吗？代价是什么？

   <details><summary>提示</summary>

   消费者在置标志之前已经检查过 `stop=false`，随后进入 `cv.wait`；谓词只看队列，不看 `stop`，也没有 `notify_all`，所以没人叫醒它。改成 `wait_for(1ms)` 会周期性地醒来重查，能绕过这次丢失唤醒，但会增加唤醒次数、受时钟粒度限制，1 毫秒内多次状态变化仍可能被合并。正确做法是让谓词包含停止条件，并用 `cv_any` 的 token 重载或 `stop_callback` 唤醒。

   </details>

3. 把 20.5 的关闭顺序用到第 19 章的线程池，排空模式下“不再接受新任务”和“执行完队列”之间的窗口怎么处理？

   <details><summary>提示</summary>

   在队列的同一把锁下把 `accepting` 置为 false，并在这个线性化点上判定每个提交：之前的任务已经进队，之后的任务直接返回失败。然后唤醒所有工作线程排空队列，等队列为空且活跃任务为 0，再 `request_stop()` 和统一 `join()`。不要先 `request_stop()` 再排空，否则工作线程可能在任务还没做完时就退出。

   </details>

4. 一个后台线程池需要在 100 ms 内退出，用 `stop_token` 轮询、`condition_variable_any` 唤醒，还是 `pthread_cancel`？各自的清理责任是什么？

   <details><summary>提示</summary>

   优先 `cv_any` 加 `stop_token`：停止请求能立即叫醒等待，线程醒来后自己清理并退出，延迟主要取决于清理代码。`stop_token` 轮询只有在检查间隔远小于 100 毫秒时才够快，否则会拖长退出时间。`pthread_cancel` 能打断阻塞调用，但清理责任落在清理函数上，C++ 析构不保证执行；异步取消还可能停在锁或分配器内部，只适合 C 风格边界。

   </details>
