# 第 1 章 并发与并行：为什么用、什么时候不用

界面程序在后台压缩一个文件夹，整窗卡住，鼠标几秒才响应一次。把压缩挪到另一个线程后界面顺了，压缩本身却没有变快。

同一个改动解决了一个问题，没有解决另一个问题：并发改善的是等待和响应，不保证计算变快；拆线程有成本，任务不够大时拆了更慢。

```cpp
void on_compress_click() {
    compress_all(files);   // 在界面线程里跑几百毫秒到几秒
    update_progress();     // 这期间窗口不处理鼠标和重绘
}
```

## 1.1 三个词：并发、并行、分布式

先看两个任务在单核和双核上的时间线。

{{#fig ch01/tasks_on_cores}}

第 3 步：单核同一时刻只有一个任务在跑，交替推进就是并发。第 6 步：两个核各跑一个任务，同一时刻两条指令流都在执行，这才是并行。第 2 步的切换要保存寄存器、指令指针和栈，本身有开销。

| 词 | 本书用法 | 最小条件 |
|---|---|---|
| 并发（concurrency） | 程序结构：多个任务在同一时段内推进 | 单核时间片交替也算 |
| 并行（parallelism） | 同时执行：多条指令流在同一时刻跑 | 至少两个核或执行单元 |
| 分布式（distributed） | 多机协作：多个程序通过网络通信 | 彼此不共享地址空间 |

分布式是另一条轴：多个程序各跑各的，通过网络传消息，谁也不直接读对方的内存。它可以是多台机器，也可以是同一台机器上的多个进程；关键不是机器数量，而是地址空间不共享。

两种并行方式：

- 任务并行（task parallelism）：把不同任务分给不同执行流。
- 数据并行（data parallelism）：把数据分块，让各执行流做同样的操作。

两者可以嵌套：线程池里每个线程先领不同任务，任务内部再对数组分块。批改试卷是常用类比：每人负责一道题是任务并行，每人负责一组学生是数据并行。真实程序常把两者叠起来：先按任务分组，再在组内按数据分块。

并行程序不会从串行循环自动长出来。对 1..N 求和，两种归约的差别在轮数：

- 主从式：主执行流逐个收部分和，8 个执行流收 7 次，1000 个收 999 次。
- 树形：两两合并，8 个执行流 3 轮，1000 个 10 轮。

总工作量没变，结构和轮数变了。

## 1.2 为什么用：分离关注点与性能

用并发有两个理由：分离关注点（separation of concerns）和性能。前者把界面响应、I/O 等待、后台计算放到不同执行流，按职责划分而不是按核数划分，单核上也有意义；后者把任务分块并行，收益受 Amdahl 定律限制。

界面程序就是分离关注点：界面线程只处理事件和重绘，压缩线程只做压缩，两者通过队列传进度。线程数按职责定，可能只有两个，和机器有几十个核没有关系。

两个指标：

| 指标 | 定义 |
|---|---|
| 加速比（speedup） | 串行时间 / 并行时间 |
| 效率（efficiency） | 加速比 / 执行流数 |

两者都要在同一问题规模、同一台机器上测。

性能的理由更窄：只有可并行的部分才会随执行流增加而变快。设串行部分占串行执行时间的比例为 `r`，`p` 个执行流时加速比上限是 `1 / (r + (1-r)/p)`，`p` 再大也越不过 `1/r`。

| 负载 | 线程数起点 | 注意 |
|---|---|---|
| CPU 密集型 | 物理核数 | 超线程不把算力翻倍 |
| I/O 密集型 | 可以超过核数 | 上限由等待比例和测量决定 |

强可扩展（strong scaling）指问题规模不变、增加执行流仍保持效率；弱可扩展（weak scaling）指问题规模随执行流同倍增加。前者看固定任务能压出多少并行，后者看更大的问题能不能用更多的核。

做容量规划时先分清问的是哪一个，否则“能扩展到 64 核”这句话没有意义。

CPU 密集型从物理核数起步，I/O 密集型可以超订，但线程数要用测量决定，不能靠公式猜。`hardware_concurrency()` 只是提示值，取不到时返回 0。计时有三点：

- 用 `std::chrono::steady_clock` 测墙上时钟。
- 先预热，重复取中位数或最小值。
- `high_resolution_clock` 可能是 `system_clock` 的别名，不适合计时。

## 1.3 什么时候不用：成本清单

拆线程的唯一理由是收益大于成本。成本不只是“建一个线程”，还包括栈、调度实体、切换、缓存污染和同步调试。

| 成本 | 说明 | 怎么量 |
|---|---|---|
| 创建与回收 | 内核任务、栈映射、线程局部存储 | 用 `steady_clock` 包住 create 加 join |
| 每线程栈 | 默认取 `RLIMIT_STACK`，本机 `ulimit -s` 是 8192 KiB | `ulimit -s`、`pthread_attr_setstacksize` |
| 调度实体 | 每个线程对应一个内核调度实体 | `ps -L`、`/proc/self/task` |
| 上下文切换 | 保存寄存器、换栈，缓存和地址转换缓存（TLB）变冷 | `getrusage` 的 `ru_nvcsw`/`ru_nivcsw` |
| 同步与维护 | 锁、条件变量、复现和调试 | ThreadSanitizer（TSan）、压测、日志 |

本机每线程栈的默认大小是 8 MiB 虚拟地址，保护区默认一个页（4 KiB）。栈是虚拟地址，按需映射物理页，所以 1000 个线程不一定立刻吃掉 8 GiB 物理内存；但内核任务和 `cgroup` 的 `pids.max` 是硬限制，32 位进程还要受地址空间限制。

任务太小、串行比例太高、数据无法分块、结果要求严格顺序时，拆线程通常更慢。先考虑替代手段，再决定要不要自己建线程。

| 场景 | 先用什么 |
|---|---|
| 大量 I/O 等待 | 事件循环 |
| 大量短任务 | 线程池 |
| 规则循环 | OpenMP |
| 多机 | MPI |
| 大量并发等待 | 协程 |

## 1.4 多进程还是多线程

进程和线程的第一差别是地址空间：进程各有一份，线程共享同一份。

| | 进程 | 线程 |
|---|---|---|
| 地址空间 | 独立 | 共享代码、全局数据、堆和文件描述符（fd） |
| 通信方式 | pipe、socket、共享内存、MPI | 直接读写共享变量 |
| 创建成本 | 创建和切换通常更贵 | 创建和切换更便宜 |
| 崩溃影响 | 通常只死一个进程 | 整个进程退出 |
| 标准接口 | C++23 仍没有，靠 POSIX/Linux 或 MPI | `std::thread`、pthread |

选择依据不是“线程比进程轻”这一条。要隔离崩溃、要跨语言、要复用现成的进程模型，选进程；要共享大对象、要频繁通信、要低创建开销，选线程。

进程之间也可以用共享内存映射同一块物理页，那是有意的共享，要配进程间锁；它不改变“默认各自一份”的事实。

- 多线程进程里 `fork` 只复制调用它的那个线程，子进程还继承互斥量和条件变量的状态；`fork` 后、`exec` 前只能调用异步信号安全（async-signal-safe）函数，子进程要用 `_exit`。
- C++ 标准到 C++23 仍没有进程和进程间通信（IPC）接口，跨进程要用 POSIX/Linux 或 MPI。
- 标准库建在 pthread 上只说 Linux：libstdc++/libc++ 是这样，Windows 的 MSVC 不是。

`pthread_atfork` 可以在 `fork` 前后加回调，但它只能处理注册过的锁，不能把所有状态都修好；更稳妥的做法是 `fork` 后立刻 `exec`，或者用 `posix_spawn`。

## 1.5 C++ 的四代设施与本书的四套 API

C++98 不承认线程存在，也没有内存模型；线程只能靠 POSIX、Windows API 或 Boost 这类库。C++11 才把线程和内存模型写进标准。

先按年代看四条线。

{{#fig ch01/api_timeline}}

| 版本 | 并发与并行设施 |
|---|---|
| C++11 | 内存模型、`thread`、`mutex`、`condition_variable`、`future`、`atomic` |
| C++14 | `shared_timed_mutex` |
| C++17 | `scoped_lock`、`shared_mutex`、并行算法、`hardware_destructive_interference_size` |
| C++20 | `jthread`/`stop_token`、`latch`/`barrier`/`counting_semaphore`、`atomic::wait`、`atomic_ref`、`osyncstream` |
| C++23 | `move_only_function`、`stacktrace` |
| C++26 | `std::execution`、`hazard_pointer`、`rcu`，本机 GCC 15/Clang 21 未实现 |

C++11 的关键不是多了几个类，而是第一次给出内存模型：什么算数据竞争、什么操作建立先行发生关系、编译器允许做哪些重排。没有这一层，标准库的线程设施无法跨平台定义。

C++26 的三项在本机编译不了，本书只介绍，不写可运行示例。

- pthread 是 C 接口，长处在属性、取消、信号、`fork`，以及可放在共享内存里的进程间同步对象。
- C11 `<threads.h>` 是可选设施，glibc 2.28 起提供；没有 barrier、读写锁和信号量。
- OpenMP 用编译指示建线程组，没有独立线程对象。
- MPI 管的是进程，用单程序多数据（SPMD）风格，地址空间私有。
- Linux 系统调用（`clone`、`futex`、`epoll`、`signalfd`）负责标准库不覆盖的部分。

| API | 执行单位 | 谁创建 | 怎么等待 | 怎么传参 | 地址空间 | 典型实现 |
|---|---|---|---|---|---|---|
| C++ 标准库 | 线程 | `std::thread`/`std::jthread` | `join`/`future` | 函数参数、lambda 捕获 | 共享 | libstdc++、libc++、MSVC |
| pthread | 线程 | `pthread_create` | `pthread_join` | `void*` 参数 | 共享 | glibc NPTL |
| OpenMP | 线程组 | 运行时按编译指示建 | 隐式屏障、`nowait` | 共享变量、数据环境子句 | 共享 | libgomp、libomp |
| MPI | 进程 | `mpirun`/`mpiexec` | `MPI_Wait`、集合通信 | 消息、`MPI_Send`/`MPI_Recv` | 私有 | Open MPI、MPICH |

四套 API 的分工可以用一句话记：标准库管可移植的线程和同步，pthread 管标准库没有的平台能力，OpenMP 管规则循环的并行化，MPI 管多机进程通信。

| 场景 | 写法 | 注意 |
|---|---|---|
| C++ | `g++-15 -std=c++20 -pthread` | `-pthread` 同时作用于预处理和链接 |
| C | `gcc -std=c17 -pthread` | pthread 返回错误码，不设 `errno` |

| MPI | `mpicxx`/`mpicc`，`mpirun -np N` | 进程数由 `-np` 决定 |

链接用 `-pthread` 而不是 `-lpthread`：glibc 2.34 起 libpthread 已并入 libc，`-pthread` 还让预处理器定义 `_REENTRANT`，并按平台加线程链接选项。只写 `-lpthread` 在 glibc 2.34 以后仍可能链接成功，但语义和可移植性都差一截。

pthread 函数返回错误码而不是设置 `errno`，示例在每次调用后检查返回值。

> **旧资料提示**：旧教程写 `-lpthread`，还常说“C++0x 标准库还在开发，将来也许比 pthread 更合适”。C++11 已发布，C++20 又加了 `jthread`、`stop_token`、信号量、闩和屏障；新 C++ 代码优先标准库，见 [第 37 章](ch37.md)。

## 速查

| 接口或写法 | 作用 | 注意 |
|---|---|---|
| `std::thread` / `std::jthread` | 启动线程 | `jthread` 析构先 `request_stop()` 再 `join()` |
| `join` / `detach` / `joinable` | 等待、分离、查询 | `std::thread` 析构时仍 joinable 会 `terminate` |
| `hardware_concurrency()` | 硬件线程数提示 | 取不到返回 0，不能当核数保证 |
| `std::chrono::steady_clock` | 墙上时钟计时 | 单调，起点任意；先预热、重复取最小值 |
| `-pthread` | 编译和链接线程支持 | 不写 `-lpthread`；glibc 2.34 起已并入 libc |
| `-fopenmp` | 打开 OpenMP | GCC 15 实现 4.5，Clang 21 是 5.1 |
| `mpicxx` / `mpirun` | 编译、启动 MPI 程序 | 进程数由 `-np` 给，不是线程数 |
| `pthread_create` / `pthread_join` | 创建、汇入 pthread | 返回错误码，不设 `errno` |
| `clone` 的共享标志 | 决定哪些资源共享 | `CLONE_VM`、`CLONE_FS`、`CLONE_FILES`、`CLONE_SIGHAND` |
| `gettid` | 内核线程号 | 和 `pthread_self()` 的句柄不是一回事 |
| `/proc/self/task` | 进程的任务表 | 同一 PID 下每个 TID 一行 |
| `fork` / `_exit` | 创建子进程、退出子进程 | 多线程进程 `fork` 后、`exec` 前只能调 async-signal-safe 函数 |

## 思考题

1. 把 `1_2_amdahl_ceiling.cpp` 的串行比例从 10% 改成 1%，16 线程的加速比大约会到多少？如果串行部分是一次 10 ms 的 I/O，结论会变吗？

   <details><summary>提示</summary>

   按 `1/(0.01+0.99/16)` 算，上限约 14，已经接近 16；实测会被线程开销和内存带宽拉低。若那 10 ms 是真的串行等待、不能与计算重叠，它仍按 Amdahl 定律摊在总时间里；如果能与计算重叠，它就不该算进串行比例。改常量后重跑，看 CSV 和图的走向。

   </details>

2. `1_3_forgot_join.cpp` 里没有异常、程序也正常退出，为什么仍然可能 `terminate`？

   <details><summary>提示</summary>

   析构函数不检查线程有没有跑完，只检查 `joinable()`。只要没有 `join` 或 `detach`，`std::thread` 离开作用域时就走 `terminate` 分支，哪怕工作线程已经结束。把析构放到 `t.join()` 之后，或者改用 `std::jthread`，都能避开。

   </details>

3. 一个每天跑一次的批处理任务和一个每秒钟处理上千连接的服务器，线程数、进程数和事件循环各应该怎么选？

   <details><summary>提示</summary>

   批处理追求吞吐量，可以用多进程或 MPI 跨机、进程内用 OpenMP 或线程池把核吃满，线程数接近物理核数，任务少时不必强上事件循环。服务器追求大量连接的响应和尾延迟，通常用事件循环加固定大小的工作线程池，不要一个连接一个线程；多进程可以用来隔离或绕开 GIL 一类限制，但进程间要显式通信。两者都要用压测和测量定参数。

   </details>

4. 把 `1_1_tree_merge.cpp` 的树形归并改成主从式，合并次数和代码结构各有什么变化？

   <details><summary>提示</summary>

   8 段数据主从式仍要 7 次归并，但主执行流要串行做 7 步，树形只有 3 层；总工作量一样，关键路径从 7 步降到 3 步。代码上，主从式只需要一个“当前结果”槽和一组把部分结果送回来的工作线程；树形要为每一层准备一组结果槽，层与层之间用 `join` 或屏障分开。段数不是 2 的幂时，树形还要处理落单的一段。

   </details>
