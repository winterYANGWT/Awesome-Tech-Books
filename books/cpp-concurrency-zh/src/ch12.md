# 第 12 章 原子类型与操作

两个线程各对同一个 `counter` 做 100 万次 `++`，第 11 章的程序丢了更新。把 `counter` 换成 `std::atomic<int>`，`fetch_add` 把读、加、写合成一步，结果稳定在 2000000。

但 `std::atomic` 不能拷贝，`compare_exchange` 失败后 `expected` 会变，16 字节的结构体也不一定无锁。三件事都来自同一个设计：原子类型只提供不可分割的操作，不提供普通对象的语义。

## 12.1 原子类型与不可分割的读-改-写

`counter++` 是读、加、写三步，两个线程的步骤可以交错。`fetch_add` 是一步：其他线程只能看到加之前或加之后的值。

{{#fig ch12/rmw_atomic}}

看第 2 步和第 4 步：A 返回时变量已经是 1，B 的一步完成之后才是 2。第 4 章那张丢失更新的图里，两个线程都读到 0；这里没有“读到 0 再写回 1”的中间窗口。

标准原子类型都在 `<atomic>`：

- `atomic_flag`：最小的原子类型，只有 set 和 clear 两个状态。
- `atomic<bool>`：比 `atomic_flag` 多出 load、store、exchange 和 compare_exchange。
- 整型特化：`atomic<int>`、`atomic<unsigned long>` 等，支持 `fetch_add`、`fetch_and` 这类读-改-写。
- 指针特化：`atomic<T*>`，按元素大小做地址偏移。
- `atomic<UDT>`：用户自定义类型，要求可平凡拷贝。

原子类型不可拷贝、不可赋值。拷贝一个原子对象，等于把“读源对象”和“写目标对象”拼成一组操作；这组操作不是原子的，别的线程能看见只拷贝了一半的状态。

## 12.2 compare_exchange：CAS 循环与 expected 回写

`compare_exchange` 是“比较后写入”：当前值等于预期值时才写入新值，否则把当前值带回来。它也是自己实现其他读-改-写的基础。

{{#fig ch12/cas_loop}}

看第 4 步：CAS 失败不是错误，它把变量当时的 7 写回 `expected`。第 5 步之后，循环手里的 `expected` 已经是最新值，所以第 6 步可以直接重试，不用再 `load` 一次。

规则只有两条：

- 当前值等于 `expected`：写入 `desired`，返回 `true`。
- 当前值不等于 `expected`：把当前值写回 `expected`，返回 `false`。

`expected` 是引用参数。循环里每次重新 `load` 会多一次读，还可能把已经拿到的值覆盖掉；失败路径已经替你写好了新值。

- 失败路径更新 `expected`，下一轮直接用它算 `desired`。
- 循环开头不要再 `load`，否则等于把 CAS 刚拿到的值扔掉。

- ARM 这类 load-locked/store-conditional 机器上，`weak` 才划算。
- 放在循环里的 CAS 用 `weak`，只尝试一次或伪失败代价高时用 `strong`。

成功和失败可以分别给内存序。失败路径只能是 `relaxed`、`acquire` 或 `seq_cst`，给 `release`/`acq_rel` 是错的，也不要把失败路径设得比成功路径更强。常用组合是成功 `acq_rel`、失败 `acquire`，或成功 `release`、失败 `relaxed`。

成功路径用 `release` 时，失败路径只能是 `relaxed` 或 `acquire`，因为失败没有发生写，不需要释放。

| 成功路径 | 常用失败路径 |
|---|---|
| `acq_rel` | `acquire` |
| `release` | `relaxed` 或 `acquire` |
| `seq_cst` | `seq_cst` 或 `acquire` |

成功路径是读-改-写，失败路径只是一次原子读；这也是失败路径不能用 `release` 的原因。

标准原子整型没有乘法、除法、移位，也没有取模。需要这些运算时，用 CAS 循环自己写；C++26 才加入 `fetch_max`/`fetch_min`，本机 GCC 15 还没有。

- 缺失的运算：`*`、`/`、`%`、`<<`、`>>`。
- 补法：读当前值，算出结果，再 `compare_exchange` 重试。

CAS 循环本身不保证无锁。底层 `compare_exchange` 如果落到 libatomic 的锁，循环只是在锁外又包了一层重试，进展保证已经变了，第 15 章会回到这一点。

CAS 循环假设“值没变就没人动过”。如果值从 A 变成 B 又变回 A，CAS 仍会成功，这就是 ABA。节点会被复用、地址会被回收时，要加版本计数或 tagged pointer，第 15 章展开。

## 12.3 指针、整数、浮点与通用类型

类型不同，可用操作也不同。标准保证无锁的只有 `atomic_flag` 和两个整型别名；其余类型要看实现。

`sizeof(Item)` 是 8，所以 `fetch_add(1)` 的字节差是 -8；`p++` 返回 `items[1]`，`p` 已经指向 `items[2]`，`++p` 和 `p += 1` 返回新地址。

原子整型支持 `fetch_and`/`fetch_or`/`fetch_xor`、复合赋值和自增自减。没有乘法、除法、移位，也没有取模，这些都要用 CAS 循环补。

- 位运算：`fetch_and`、`fetch_or`、`fetch_xor` 适合位掩码。
- 算术：原子整型通常当计数器，缺失的乘除影响不大，但要知道它们不存在。

`fetch_add` 返回旧值，`+=` 返回新值，`++`/`--` 的前后缀与普通整数一致。

- 复合赋值：`+=`、`-=`、`&=`、`|=`、`^=`。
- 自增自减：前缀返回新值，后缀返回旧值。

`atomic<UDT>` 有三条限制：

- 可平凡拷贝：没有虚函数、没有虚基类、拷贝赋值由编译器生成，所有基类和非静态成员也满足。
- 只在足够小时才可能无锁：结构体一超过 8 字节，很多平台就退回锁。
- 比较按值表示，不是 `operator==`：不参与值表示的填充位会被忽略，但同一个值有多种位表示时仍可能判不等；联合体里参与部分成员值表示的填充位，甚至会让比较永远失败。

`std::atomic<T>` 的大小和对齐不要求和 `T` 相同，标准只要求它能存下 `T`。所以不要用 `sizeof(T)` 推断 `sizeof(std::atomic<T>)`。

## 12.5 等待与通知：把自旋换成阻塞

`while (!ready.load()) {}` 会一直占着 CPU。C++20 的 `atomic<T>::wait(old)` 在值已经不等于 `old` 时立即返回，否则阻塞到被 notify 或虚假唤醒。

别的线程只 store 新值不会把它叫醒。`notify_one`/`notify_all` 负责唤醒，`atomic_flag` 也有 `wait`/`notify_one`/`notify_all`。

{{#fig ch12/wait_notify}}

看第 4 步和第 5 步：`store(1)` 只改了值，已经阻塞的消费者仍要等 `notify_one`。第 6 步醒来后重查值，`wait` 才返回。

值在 `wait` 之前已经变了，`wait` 会立即返回；没有等待者的 notify 会丢失，但这时等待者已经看到新值，丢了也无害。

- `wait(old)`：值已经不等于 `old` 时立即返回；否则阻塞到被通知或虚假返回。
- `notify_*`：唤醒等待同一个对象的等待者。

`wait` 可能虚假返回，必须放在谓词循环里。它只负责睡眠和唤醒，不提供互斥；被保护的数据仍要用锁或别的原子协议。

`wait`/`notify` 和条件变量比：

| 项目 | `atomic<T>::wait` | 条件变量 |
|---|---|---|
| 要不要 mutex | 不要 | 要，且要和数据同一把锁 |
| 能等什么 | 一个原子值上的通知（醒来重查值） | 任意谓词 |
| 适合的场景 | 一个标志、一个计数 | 队列非空、缓冲区有空位 |
| 虚假唤醒 | 有，必须循环重查 | 有，必须循环重查 |

队列这类“条件依赖被保护数据”的场景仍用条件变量。`atomic::wait` 只适合“一个标志/一个计数”的稳定状态。

条件变量能等任意谓词，代价是要配一把 mutex；`atomic::wait` 代码短，但只能等一个原子值。

标准还提醒：等待操作可能观察不到短暂的原子值（A-B-A）。如果条件只是暂时成立，等待者可能继续睡。所以 `wait` 的条件应当是稳定状态，不是一闪而过的值。

## 12.6 无锁性与可移植性：is_lock_free 到底保证什么

`is_lock_free()` 回答“这个对象上的操作是不是不加锁”，实现可以用一条指令，也可以用 LL/SC 重试，只要不内部加锁。它可以随平台、编译选项、对象大小变化，同一次程序执行里，同一类型的查询结果一致；`is_always_lock_free` 是编译期常量，适合写 `static_assert`。

C++11 时明确保证的只有 `atomic_flag` 无锁。C++20 又增加 `atomic_signed_lock_free` 和 `atomic_unsigned_lock_free` 两个保证无锁的整型别名。其他 `atomic<T>` 都可能内部用锁，哪怕 `sizeof(T)` 很小。

| 查询 | 时机 | 用途 |
|---|---|---|
| `is_lock_free()` | 运行期 | 这个对象上的操作是否无锁 |
| `is_always_lock_free` | 编译期 | 写 `static_assert`，或选类型 |
| `ATOMIC_*_LOCK_FREE` | 预处理 | 0 从不、1 有时、2 总是无锁 |

**对照**：

| 接口 | 保证 | 能否指定内存序 | 是否保证无锁 |
|---|---|---|---|
| C++ `std::atomic<T>` | 单个操作原子，默认 `seq_cst` | 能，每个操作可带 `memory_order` | 只有 `atomic_flag` 和两个整型别名保证 |
| C11 `<stdatomic.h>` | `_Atomic` / `atomic_int`，`atomic_fetch_add` 等 | 能，`memory_order_*` | 不保证，查 `atomic_is_lock_free` |
| pthread | 没有原子类型，用 `pthread_mutex_t` 或信号量 | 不适用 | 不适用 |
| OpenMP `atomic` | 只覆盖 `x++`、`x += expr` 这类有限语句 | 4.5 有 `seq_cst` 子句 | 不承诺无锁 |
| Linux 用户态 `__atomic_*` | GCC 内建，按类型生成指令或调用 libatomic | 能，`__ATOMIC_*` | 大类型可能走 libatomic 的锁 |
| Linux 内核 `atomic_t`/`refcount_t` | 内核内部原子计数，`refcount_t` 额外防溢出 | 没有逐操作的内存序参数，用屏障 | 由内核实现保证 |

> **旧资料提示**：用非成员 `atomic_load(&sp)`/`atomic_store(&sp, ...)` 访问 `shared_ptr`。C++20 起用 `std::atomic<std::shared_ptr<T>>`，但它不保证无锁。见 [38.2 节](ch38.md)。

> **旧资料提示**：认为“`atomic` 通常最快、一定无锁”。先查 `is_lock_free()`/`is_always_lock_free`（C++17 起有编译期常量）。见 [38.2 节](ch38.md)。

## 速查

| 类型或接口 | 可用操作 | 无锁保证 |
|---|---|---|
| `atomic_flag` | `test`、`test_and_set`、`clear`、`wait`/`notify_*` | 标准保证 |
| `atomic<bool>` | load、store、exchange、compare_exchange、wait/notify | 实现决定 |
| 整型原子 | 上述操作，加 `fetch_add/sub/and/or/xor`、复合赋值、自增自减 | 实现决定；两个别名保证 |
| `atomic<T*>` | load、store、exchange、compare_exchange、`fetch_add/sub`、`+=`/`-=`、`++`/`--` | 实现决定 |
| 浮点原子 | load、store、exchange、compare_exchange、C++20 起 `fetch_add/sub` | 实现决定 |
| `atomic<UDT>` | load、store、exchange、compare_exchange | 实现决定，通常大于 8 字节就有锁 |
| `atomic_ref<T>` | 同 `atomic<T>`，另有 `required_alignment`、`address` | 实现决定 |
| `atomic<shared_ptr<T>>` | load、store、exchange、compare_exchange | 标准不保证，本机不是无锁 |

| `compare_exchange` 的项目 | 内容 |
|---|---|
| 签名 | `compare_exchange_weak(T& expected, T desired, memory_order success, memory_order failure)`；`strong` 同理 |
| 成功 | 当前值等于 `expected`，写入 `desired`，返回 `true`，`expected` 不变 |
| 失败 | 当前值写回 `expected`，返回 `false`，不写 `desired` |
| `weak` 与 `strong` | `weak` 允许伪失败，适合循环；`strong` 不伪失败，适合只试一次 |
| 失败内存序 | 只能 `relaxed`、`acquire`、`seq_cst`；不能 `release`/`acq_rel`，不要比成功路径强 |
| 常见错误 | 循环里重新 `load` 覆盖 `expected`；把失败当异常；忽略 ABA |

## 思考题

1. 两个线程各对同一个 `atomic<int>` 做 100 万次 `fetch_add(1, memory_order_relaxed)`，结果一定是 2000000 吗？如果主线程在 `join` 前读一次，能读到哪些值？

   <details><summary>提示</summary>

   一定是 2000000：原子的读-改-写不会丢更新，和内存序无关。`join` 之前读到的是 0 到 2000000 之间的某个值，具体取决于读到哪一次修改；`join` 返回之后才保证看到两个线程的全部写入。

   </details>

2. 找错：`compare_exchange_weak(expected, desired)` 放在循环里，但循环开头每次都 `expected = current.load()`。这为什么会多一次读、并可能把失败路径刚写回的值覆盖掉，ABA 又和这行 `load` 有什么关系？改成不重新 `load` 后，失败路径的 `expected` 是谁写的？

   <details><summary>提示</summary>

   多出的 `load` 会把上一次失败回写的值覆盖掉，等于丢掉了 CAS 已经拿到的当前值。ABA 不因这行 `load` 产生：CAS 只比较值表示，带不带它都可能把 A→B→A 当成没变，要用版本计数或 tagged pointer 解决。去掉这行后，失败路径由 `compare_exchange_weak` 自己把当前值写进 `expected`。

   </details>

3. 迁移：把 12.4 的 `vector<int>` 换成共享内存里的 `struct { int a; int b; }` 数组，`atomic_ref` 要对齐到什么边界？如果另一端进程用普通读写访问，会发生什么？

   <details><summary>提示</summary>

   对齐到 `std::atomic_ref<Point>::required_alignment`，它至少是 `alignof(Point)`，可能更大；用 `alignas` 保证数组每个元素都满足。另一端用普通读写就绕过了原子访问，和本章的混用例子一样，构成数据竞争。

   </details>

4. 权衡：一个“等标志变成 true”的循环，用 `atomic::wait`、条件变量、还是每 1 ms 轮询？三种写法在什么负载下各自更合适？

   <details><summary>提示</summary>

   等得久、只有一个标志，用 `atomic::wait`，不需要 mutex。条件依赖队列内容、要和数据同一把锁，用条件变量。等待很短、事件频繁，轮询延迟最低，但会占 CPU；1 ms 睡眠是折中，响应和占用都随周期变化。

   </details>
