# 第 6 章 第一个完整 CUDA C++ 程序：不只是一段 kernel

很多 CUDA 入门材料会从一个 `__global__` 函数开始，这没有错，但它容易让人误以为 CUDA 的核心只是写 kernel。能运行、能定位错误、能继续优化的 CUDA C++ 程序是一条完整链路：host 准备数据，device 分配空间，输入拷到 device，host 发起 kernel，检查 launch，同步执行，结果拷回 host，最后释放资源。

向量加法 `C[i] = A[i] + B[i]` 是最适合做第一段完整程序的例子。它足够简单，不会遮住 CUDA 的结构；它也足够完整，能把内存管理、线程索引、边界检查和错误处理都串起来。

## 6.1 问题的由来

如果只看 kernel：

```cpp
__global__ void vec_add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}
```

你只能看到 device 侧的一小段逻辑。更多问题在 host 侧：`a`、`b`、`c` 从哪里来？这些指针指向 host memory 还是 device memory？`n` 个元素需要启动多少线程？kernel launch 是否成功？kernel 内是否发生非法访问？什么时候 host 能看到结果？

CUDA C++ 的第一课应该写完整程序，而不是只写完整 kernel。

## 6.3 详解

### 6.3.1 CUDA C++ 文件多了两类东西

第一类是语言扩展：

| 语法 | 作用 |
|---|---|
| `__global__` | 声明 kernel，host 发起，在 device 上执行 |
| `<<<grid, block>>>` | 从 host 侧启动 kernel |
| `threadIdx`、`blockIdx` | 让 device 侧线程知道自己负责哪份数据 |
| `__shared__`、`__device__`、`__constant__` | 描述 device 侧变量存储位置 |

第二类是 Runtime API：

| API | 作用 |
|---|---|
| `cudaMalloc`、`cudaFree` | 分配和释放 device memory |
| `cudaMemcpy` | 在 host 与 device 之间、device 与 device 之间拷贝数据 |
| `cudaMemset` | 初始化 device memory |
| `cudaDeviceSynchronize` | 等待 device 工作完成 |
| `cudaGetLastError`、`cudaPeekAtLastError` | 检查 Runtime error state |

语言扩展让你表达 GPU 上的并行函数，Runtime API 让 host 能管理 GPU 资源并提交工作。

### 6.3.2 边界检查是 CUDA kernel 的基本结构

block 数通常用向上取整：

```cpp
int threads = 256;
int blocks = (n + threads - 1) / threads;
```

如果 `n` 不是 256 的整数倍，最后一个 block 一定会多出一些线程。多出的线程没有对应数据，所以 kernel 里必须有：

```cpp
if (i < n) {
    c[i] = a[i] + b[i];
}
```

这不是保守写法，它本来就是 CUDA 索引模式的一部分。

## 6.4 代码示例

下面是显式内存管理版本的完整 vector add。它比 Unified Memory 版本啰嗦，但边界更清楚，适合建立第一条程序链路。

```cpp
#include <cuda_runtime_api.h>
#include <cstdio>
#include <cstdlib>
#include <cmath>
#define CUDA_CHECK(call)                                                   \
    do {                                                                   \
        cudaError_t err__ = (call);                                        \
        if (err__ != cudaSuccess) {                                        \
            std::fprintf(stderr, "%s:%d CUDA error: %s\n",                \
                         __FILE__, __LINE__, cudaGetErrorString(err__));   \
            std::exit(1);                                                  \
        }                                                                  \
    } while (0)
__global__ void vec_add(const float* a, const float* b, float* c, int n)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}
int main(int argc, char** argv)
{
    int n = argc > 1 ? std::atoi(argv[1]) : 1 << 20;
    size_t bytes = static_cast<size_t>(n) * sizeof(float);
    CUDA_CHECK(cudaSetDevice(0));
    float* h_a = static_cast<float*>(std::malloc(bytes));
    float* h_b = static_cast<float*>(std::malloc(bytes));
    float* h_c = static_cast<float*>(std::malloc(bytes));
    if (!h_a || !h_b || !h_c) return 1;
    for (int i = 0; i < n; ++i) {
        h_a[i] = static_cast<float>(i);
        h_b[i] = 2.0f * static_cast<float>(i);
    }
    float *d_a = nullptr, *d_b = nullptr, *d_c = nullptr;
    CUDA_CHECK(cudaMalloc(&d_a, bytes));
    CUDA_CHECK(cudaMalloc(&d_b, bytes));
    CUDA_CHECK(cudaMalloc(&d_c, bytes));
    CUDA_CHECK(cudaMemcpy(d_a, h_a, bytes, cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemcpy(d_b, h_b, bytes, cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemset(d_c, 0, bytes));
    int threads = 256;
    int blocks = (n + threads - 1) / threads;
    vec_add<<<blocks, threads>>>(d_a, d_b, d_c, n);
    CUDA_CHECK(cudaPeekAtLastError());
    CUDA_CHECK(cudaDeviceSynchronize());
    CUDA_CHECK(cudaMemcpy(h_c, d_c, bytes, cudaMemcpyDeviceToHost));
    for (int i = 0; i < n; ++i) {
        float expected = h_a[i] + h_b[i];
        if (std::fabs(h_c[i] - expected) > 1e-5f) {
            std::fprintf(stderr, "mismatch at %d: got %f expected %f\n",
                         i, h_c[i], expected);
            return 1;
        }
    }
    CUDA_CHECK(cudaFree(d_c));
    CUDA_CHECK(cudaFree(d_b));
    CUDA_CHECK(cudaFree(d_a));
    std::free(h_c);
    std::free(h_b);
    std::free(h_a);
    return 0;
}
```

编译：

```bash
nvcc -O2 vector_add.cu -o vector_add
./vector_add
```

如果要在 profiling 时保留源码行号：

```bash
nvcc -O2 -lineinfo vector_add.cu -o vector_add
```

## 6.5 工程判断

| 位置 | 应该检查 | 常见错误 |
|---|---|---|
| host allocation | `malloc` 是否成功 | 只检查 CUDA API，不检查 host 内存 |
| device allocation | `cudaMalloc` 返回值 | 分配大小用错类型或溢出 |
| H2D copy | `cudaMemcpyHostToDevice` 方向 | 源/目的指针写反 |
| launch | grid/block 是否合理 | block 线程数超过设备上限 |
| launch error | `cudaPeekAtLastError` | 以为三尖括号会返回错误码 |
| execution error | `cudaDeviceSynchronize` | 只检查 launch，不检查执行 |
| D2H copy | 同步后的结果拷回 | kernel 未完成就读结果 |
| free | host/device 分别释放 | `free` 和 `cudaFree` 混用 |

## 6.6 API 与要点速查

`cudaMemcpyKind` 常见方向：

| 枚举 | 含义 |
|---|---|
| `cudaMemcpyHostToHost` | host 到 host |
| `cudaMemcpyHostToDevice` | host 到 device |
| `cudaMemcpyDeviceToHost` | device 到 host |
| `cudaMemcpyDeviceToDevice` | device 到 device |
| `cudaMemcpyDefault` | 在 UVA 可用时由 runtime 根据指针判断 |

错误检查相关 API：

| API | 行为 |
|---|---|
| `cudaPeekAtLastError` | 查看最近错误但不清除 |
| `cudaGetLastError` | 获取并清除最近错误 |
| `cudaGetErrorString` | 把错误码转为可读字符串 |
| `cudaDeviceSynchronize` | 等待 device 并暴露异步执行错误 |

初始化和收尾：

| API | 用途 |
|---|---|
| `cudaSetDevice` | 设置当前 host thread 使用的 device |
| `cudaInitDevice` | 显式初始化指定 device |
| `cudaDeviceReset` | 重置当前 device，释放当前进程相关资源 |

## 6.7 练习

1. 把向量加法按三个版本重写一遍：先写纯 CPU 版本；再写一个只有分配、拷贝、launch、拷回、释放的最小 CUDA 版本，不加任何错误检查；最后补上 `CUDA_CHECK`、launch 后检查和结果校验，得到 6.4 节的程序。每个版本都和 CPU 版本的输出逐元素比较。你会发现，一切正常时最小版本也能给出正确结果，所以“结果对了”不能说明程序结构完整，错误检查的价值要到出错时才看得出来。
2. 去掉 kernel 里的 `if (i < n)`，用一个不是 256 整数倍的 `n` 运行程序（6.4 节的程序从命令行读 `n`，例如 `./vector_add 1000001`），再用 `compute-sanitizer ./vector_add 1000001` 运行一次。直接运行时程序很可能照常结束，因为越界的几百字节通常还落在 driver 按较大粒度分配的空间里，不会立刻触发错误；sanitizer 则会报告越界访问，出错的线程都在最后一个 block 里。恢复边界检查后，报告消失。
3. 分别注入两类错误：把 `threads` 改成 2048，制造 launch 配置错误；或者把传给 kernel 的 `d_c` 换成 `nullptr`，制造执行期非法访问。在最小版本和完整版本里各跑一次，记录错误在哪一行被发现。最小版本最多只能看到结果不对，看不出错在哪一步；完整版本里，配置错误在 `cudaPeekAtLastError` 处报告，非法访问要到 `cudaDeviceSynchronize` 才暴露。

## 6.8 小结

读完本章，你应该能够：

- 写出完整 CUDA C++ 程序，而不是只写 kernel。
- 区分 host memory、device memory 和拷贝方向。
- 在 launch 后检查提交错误，在同步点检查执行错误。
- 解释为什么 bounds checking 是必要结构。
- 把资源释放放回完整生命周期里。
