# 第 85 章 MD force-only CUDA port：一个线程负责一个粒子

## 85.1 问题的由来

真实的 CUDA 迁移通常不是一次把整个程序改成 GPU 版本。更常见的路线是先迁移最热的函数，测量收益和新的瓶颈，再决定是否扩大数据常驻 device 的范围。本章的示例就是这样一个 force-only port：只把求力函数移植到 GPU，其余流程仍留在 CPU。

## 85.2 核心模型

| CPU baseline | CUDA port |
|---|---|
| 外层 `i` 串行循环 | 一个线程负责一个粒子 `i` |
| `nbr_count/nbr_list` 邻居表 | 每个线程读取自己的邻居列表 |
| 对 `i/j` 同时累加力 | 每个线程只写自己的 `fx[i]`、`fy[i]`、`fz[i]`、`epot[i]` |
| host 数组 | 位置拷到 device，结果拷回 host |
| CPU 函数调用 `compute_forces_cpu` | `forces_kernel<<<grid, block>>>` |

这一版移植的关键是避免写冲突：不再让一个 pair 同时更新两个粒子，而是让每个线程计算本粒子受到的总力。

## 85.3 详解

kernel 的线程映射很直接：

```cpp
// 第 84 章的最小镜像函数，加上 __host__ __device__ 后 CPU 和 GPU 两边共用
__host__ __device__ inline double nearest_image(double d, double len)
{
    return d - len * round(d / len);
}

// 一个线程负责一个粒子 i。device 端的邻居表按转置布局存放：
// 粒子 i 的第 k 个邻居在 nbr_list[k * count + i]
__global__ void forces_kernel(int count, double box_len,
                              const int* nbr_count, const int* nbr_list,
                              const double* x, const double* y, const double* z,
                              double* fx, double* fy, double* fz, double* epot)
{
    const int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= count) return;                         // 多出来的线程直接退出

    const double cutoff2 = 2.5 * 2.5;
    const double inv_rc6 = 1.0 / (cutoff2 * cutoff2 * cutoff2);
    const double e_shift = 4.0 * inv_rc6 * (inv_rc6 - 1.0);   // 和 CPU 版相同的势能平移
    const double xi = x[i], yi = y[i], zi = z[i];
    double fxi = 0.0, fyi = 0.0, fzi = 0.0, ei = 0.0;    // 在寄存器里累加

    for (int k = 0; k < nbr_count[i]; ++k) {
        const int j = nbr_list[k * count + i];      // 同一个 k，相邻线程读相邻地址
        const double dx = nearest_image(xi - x[j], box_len);
        const double dy = nearest_image(yi - y[j], box_len);
        const double dz = nearest_image(zi - z[j], box_len);
        const double r2 = dx * dx + dy * dy + dz * dz;
        if (r2 > cutoff2) continue;
        const double inv_r2 = 1.0 / r2;
        const double inv_r6 = inv_r2 * inv_r2 * inv_r2;
        const double e = 4.0 * inv_r6 * (inv_r6 - 1.0) - e_shift;
        const double f = 24.0 * inv_r2 * inv_r6 * (2.0 * inv_r6 - 1.0);
        fxi += f * dx;                              // 只累加 i 受的力，不碰 j
        fyi += f * dy;
        fzi += f * dz;
        ei += 0.5 * e;                              // 这一对在 j 的线程里还会再算一次
    }
    fx[i] = fxi;                                    // 每个线程只写自己的粒子
    fy[i] = fyi;
    fz[i] = fzi;
    epot[i] = ei;
}
```

和[第 84 章](ch084.md)的 CPU 版相比，有两处刻意的不同。

第一，kernel 不使用牛顿第三定律。CPU 版每个 pair 只算一次，同时更新 `i` 和 `j` 两个粒子；如果 GPU 上也这样做，负责 `i` 的线程和负责 `j` 的线程会同时往同一个 `fx[j]` 上累加，产生写冲突。这里的做法是让每个线程遍历自己的全部邻居，不再跳过 `j < i`，每个 pair 在 `i`、`j` 两个线程里各算一次，计算量翻倍，换来的是每个线程只写自己的 `fx[i]`、`fy[i]`、`fz[i]`、`epot[i]`，不需要原子操作。势能仍然每次记一半，所以每个粒子的 `epot[i]` 和 CPU 版一致。

第二，device 端的邻居表换成了转置布局：粒子 `i` 的第 `k` 个邻居放在 `nbr_list[k * count + i]`，也就是先放所有粒子的第 0 个邻居，再放所有粒子的第 1 个邻居，依此类推。一个 warp 里的线程负责编号相邻的粒子，在循环的同一轮里都读第 `k` 个邻居，地址正好连续，可以合并成少数几次内存事务。CPU 版的 `nbr_list[i * max_nbr + k]` 放到 GPU 上，相邻线程的地址会相隔 `max_nbr` 个元素。host 端在把邻居表拷到 device 之前，先按新布局重排一次即可。

host 包装函数负责准备盒子参数、位置拷贝、kernel launch 和结果回传。入门阶段最容易上手的是一维 launch：例如 `block = 128`，`grid = (count + block - 1) / block`，每个线程负责一个粒子，多出来的线程在 kernel 开头按 `i >= count` 判断后直接退出。

## 85.4 代码示例

在 force-only port 里，host 包装函数 `compute_forces_gpu`（代码见[第 86 章](ch086.md)）每次被调用都按这个顺序执行：把位置 `x/y/z` 拷到 device，启动 `forces_kernel`，再把 `fx/fy/fz/epot` 拷回 host。积分、能量统计和输出仍留在 CPU 上，和[第 84 章](ch084.md)的 baseline 一样。

可以把本章看作“定位到热点之后，第一版迁移怎么做”的具体例子，它对应[第 30 章](ch030.md)性能排查流程之后的下一步。

## 85.5 工程判断

| 问题 | 判断 |
|---|---|
| 为什么一个线程一个粒子 | 并行形状简单，并且每个线程只写自己的输出 |
| 为什么还要拷回 host | force-only port 仍让主模拟流程停留在 CPU |
| 新瓶颈可能是什么 | 每步 host/device 往返、邻居表布局、全局内存访问模式 |
| 下一步优化是什么 | 把积分、归约、速度缩放等继续迁到 device，减少往返 |

## 85.6 API 与要点速查

| 要点 | 说明 |
|---|---|
| 错误检查 | 保留 `CHECK_CUDA` 的习惯：kernel launch 后先检查 launch 错误，再在同步处捕获执行错误 |
| 性能解释 | 不只报加速比，还要说明数据传输占总时间的比例 |
| 数据布局差异 | CPU 用 `nbr_list[i * max_nbr + k]`，同一粒子的邻居连续存放；GPU 用 `nbr_list[k * count + i]`，同一个 `k` 下相邻线程读相邻地址，访存可以合并（见[第 28 章](ch028.md)） |

## 85.7 小结

读完本章，你应该能够把一个 CPU 热点函数改写成第一版 CUDA kernel：先选线程映射，再处理写冲突，然后明确数据传输边界，最后用 baseline 验证正确性和收益。
