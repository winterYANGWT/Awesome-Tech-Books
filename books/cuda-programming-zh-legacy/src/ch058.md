# 第 58 章 VMM：把虚拟地址、物理内存和访问权限拆开管理

## 58.1 问题的由来

`cudaMalloc` 很方便，因为它一次性替你完成了物理内存分配、虚拟地址选择、映射和访问权限设置。方便的代价是控制粒度粗：你很难精确安排地址范围、把不同 GPU 的物理内存拼成连续虚拟地址、只给某个 allocation 开放 peer access，或者把物理 allocation 导出给另一个进程。

Virtual Memory Management API 把这些动作拆开。你不再直接得到一个“已经能用”的 pointer，而是自己管理 physical allocation、virtual address reservation、mapping 和 access rights。

## 58.2 核心模型

VMM 把“地址”和“内存”拆成两个对象：`CUdeviceptr` 表示保留的虚拟地址范围，`CUmemGenericAllocationHandle` 表示物理 allocation。两者各自创建、各自释放，中间靠 map 连起来，再由 access 设置决定谁能访问。

## 58.3 详解

使用 VMM 前要先查设备能力。不是所有平台都支持 VMM、fabric handle 或 multicast。

```cpp
int supports_vmm = 0;
cuDeviceGetAttribute(
    &supports_vmm,
    CU_DEVICE_ATTRIBUTE_VIRTUAL_MEMORY_MANAGEMENT_SUPPORTED,
    device);
```

物理 allocation 的属性由 `CUmemAllocationProp` 描述。最常见的 device allocation 是 pinned type + device location：

```cpp
CUmemAllocationProp prop{};
prop.type          = CU_MEM_ALLOCATION_TYPE_PINNED;  // 使用期间物理页不迁移
prop.location.type = CU_MEM_LOCATION_TYPE_DEVICE;    // 物理页放在 GPU 上
prop.location.id   = device;                         // 哪一张 GPU：device ordinal
```

VMM allocation 必须满足粒度要求。先用 `cuMemGetAllocationGranularity` 查询，再把请求的 `bytes` 向上对齐到这个粒度的整数倍。

```cpp
size_t granularity = 0;
cuMemGetAllocationGranularity(&granularity, &prop,
                              CU_MEM_ALLOC_GRANULARITY_MINIMUM);
size_t size = (bytes + granularity - 1) / granularity * granularity;
```

有了对齐后的 size，接下来依次 reserve 虚拟地址、`cuMemCreate` 物理内存、`cuMemMap` 建立映射、`cuMemSetAccess` 设置权限。`cuMemMap` 只是建立 mapping，不会自动开放访问权限。没有 `cuMemSetAccess`，kernel 访问映射地址可能直接崩溃。这个设计让 VMM 可以精确控制哪个 device 能读写哪段地址。

如果 allocation 还要交给其他进程使用，`cuMemCreate` 和 map 之间会多出导出、传递、导入 handle 三步。单节点上用操作系统句柄（Linux 的 POSIX fd、Windows 的 Win32 handle）；多节点且平台提供 IMEX channel 时，改用 fabric handle。导入方拿到的仍然只是物理 allocation，还要自己 reserve、map、set access。下一章详细讨论这条路径。

## 58.4 代码示例

下面是单进程单 GPU 的最小 VMM 生命周期，写成 `vmm_alloc` / `vmm_free` 一对函数。前面两个片段就是 `vmm_alloc` 的开头，区别只是每个 Driver API 调用都包上了检查 `CUresult` 的 `CU_CHECK`，对齐后的大小存进了 `buf.size`。

```cpp
#include <cuda.h>
#include <cstdio>
#include <cstdlib>

#define CU_CHECK(call)                                                 \
    do {                                                               \
        CUresult status_ = (call);                                     \
        if (status_ != CUDA_SUCCESS) {                                 \
            const char* name_ = nullptr;                               \
            cuGetErrorName(status_, &name_);                           \
            std::fprintf(stderr, "%s:%d: %s -> %s\n", __FILE__,        \
                         __LINE__, #call, name_ ? name_ : "unknown");  \
            std::exit(EXIT_FAILURE);                                   \
        }                                                              \
    } while (0)

struct VmmBuffer {
    CUdeviceptr ptr = 0;                      // 预留的虚拟地址
    size_t size = 0;                          // 按粒度对齐后的大小
    CUmemGenericAllocationHandle handle = 0;  // 物理分配
};

VmmBuffer vmm_alloc(CUdevice device, size_t bytes)
{
    CUmemAllocationProp prop{};
    prop.type          = CU_MEM_ALLOCATION_TYPE_PINNED;
    prop.location.type = CU_MEM_LOCATION_TYPE_DEVICE;
    prop.location.id   = device;

    size_t granularity = 0;
    CU_CHECK(cuMemGetAllocationGranularity(&granularity, &prop,
                                           CU_MEM_ALLOC_GRANULARITY_MINIMUM));

    VmmBuffer buf;
    buf.size = (bytes + granularity - 1) / granularity * granularity;

    // 1. 预留虚拟地址  2. 创建物理内存  3. 映射
    CU_CHECK(cuMemAddressReserve(&buf.ptr, buf.size, 0, 0, 0));
    CU_CHECK(cuMemCreate(&buf.handle, buf.size, &prop, 0));
    CU_CHECK(cuMemMap(buf.ptr, buf.size, 0, buf.handle, 0));

    // 4. 只给分配所在的这张 GPU 开放读写
    CUmemAccessDesc access{};
    access.location = prop.location;
    access.flags    = CU_MEM_ACCESS_FLAGS_PROT_READWRITE;
    CU_CHECK(cuMemSetAccess(buf.ptr, buf.size, &access, 1));
    return buf;
}

void vmm_free(VmmBuffer& buf)
{
    CU_CHECK(cuMemUnmap(buf.ptr, buf.size));        // 先解除映射
    CU_CHECK(cuMemRelease(buf.handle));             // 再释放物理内存
    CU_CHECK(cuMemAddressFree(buf.ptr, buf.size));  // 最后归还虚拟地址
    buf = VmmBuffer{};
}
```

注意释放顺序：先 unmap，再 release physical handle，最后 free virtual address。反过来做会留下悬空映射或释放失败。

## 58.5 工程判断

| 需求 | VMM 价值 | 代价 |
|---|---|---|
| 连续 VA，背后来自多个 GPU allocation | 高 | 需要自己管理 map offset |
| per-allocation peer access | 高 | access descriptor 必须维护 |
| 跨进程或跨节点 handle | 高 | 要处理 OS/fabric handle 传递 |
| 普通单进程分配 | 通常不必 | `cudaMalloc` 或 `cudaMallocAsync` 更简单 |
| 自定义 allocator | 很有用 | 生命周期和粒度由你负责 |
| 图形互操作或系统库底层 | 很有用 | 平台 handle 和安全属性复杂 |

## 58.6 API 与要点速查

核心 API：

| API | 作用 |
|---|---|
| `cuMemGetAllocationGranularity` | 查询 allocation 粒度 |
| `cuMemCreate` | 创建 physical allocation，返回 generic allocation handle |
| `cuMemAddressReserve` | 保留虚拟地址范围 |
| `cuMemMap` | 把 allocation handle 映射到虚拟地址 |
| `cuMemSetAccess` | 设置访问权限 |
| `cuMemGetAccess` | 查询访问权限 |
| `cuMemUnmap` | 解除映射 |
| `cuMemRelease` | 释放 physical allocation handle |
| `cuMemAddressFree` | 释放虚拟地址范围 |

关键类型和枚举：

| 名称 | 说明 |
|---|---|
| `CUmemGenericAllocationHandle` | 物理 allocation handle |
| `CUmemAllocationProp` | allocation 属性 |
| `CUmemAccessDesc` | 访问权限描述 |
| `CU_MEM_ALLOCATION_TYPE_PINNED` | VMM 常用 allocation type |
| `CU_MEM_LOCATION_TYPE_DEVICE` | device memory location |
| `CU_MEM_ACCESS_FLAGS_PROT_READWRITE` | 读写权限 |
| `CU_DEVICE_ATTRIBUTE_VIRTUAL_MEMORY_MANAGEMENT_SUPPORTED` | 查询 VMM 支持 |

和 peer access 的区别：

| 机制 | 粒度 |
|---|---|
| `cudaDeviceEnablePeerAccess` | 影响目标 peer 的所有已存在和未来 `cudaMalloc` allocation |
| VMM `cuMemSetAccess` | 对指定 VA range 和指定 device 设置权限 |

## 58.7 小结

读完本章，你应该能够：

- 说清 VMM 为什么把地址、物理内存、映射和权限拆开。
- 写出 reserve-map-access-release 的最小生命周期。
- 知道 `cuMemMap` 后还必须 `cuMemSetAccess`。
- 按正确顺序释放 VMM memory。
