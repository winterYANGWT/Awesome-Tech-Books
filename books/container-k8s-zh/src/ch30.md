# 第 30 章 认证、授权与 RBAC、ServiceAccount

shorty 的 api 现在跑在 `s3-stateful` 里，进程只连 PostgreSQL 和 Redis，从不调用 Kubernetes API。但它仍然带着一个身份：`shorty` namespace 里的 `default` ServiceAccount。这个身份默认什么也做不了，可一旦有人图省事给 `default` 绑一个角色，所有没写 `serviceAccountName` 的 Pod 都会一起拿到这份权限。攻击者只要能在该 namespace 里创建一个 Pod，就能用这个身份去读它本来读不到的东西。

另一边，运维在笔记本上敲的是同一条 `kubectl` 命令，换一个 context 就可能从成功变成 `Forbidden`。命令没变、集群没变，变的是 kubeconfig 里的 user，以及这个 user 在 apiserver 眼里属于哪些组。把这两件事分开看，`403` 就不再神秘：apiserver 先认出了“你是谁”，再查“你能做什么”。

Kubernetes 把访问控制拆成三段：认证（authentication）、授权（authorization）、准入（admission）。认证回答身份，授权回答动作，准入在对象落盘前再看一眼内容。本章按这三段顺序走：先看 apiserver 怎么认人，再给 api 建一个独立的 ServiceAccount 和最小 Role，然后用 kubeconfig 换一个只读身份验证 `can-i`，最后故意越权，看 RBAC 和准入如何拦截。

> **起点**：`s3-stateful` 已经就绪，api 和 worker 都用 namespace 的 `default` ServiceAccount，集群里没有任何自定义的 Role、ClusterRole 或绑定。一步到位：`bash code/ch30/setup.sh`。脚本建单节点 kind 集群，预拉 `busybox:1.37`，下面的示例都在这套集群上跑。

## 30.1 三段式访问控制

请求进入 apiserver 之前先过 TLS。apiserver 默认在第一个非 localhost 网卡的 6443 端口上提供 TLS，生产集群通常对外是 443；证书和私钥由 `--tls-cert-file`、`--tls-private-key-file` 指定。如果集群用私有 CA，客户端 kubeconfig 里要带上这个 CA，否则连信任都建立不起来。客户端也可以在这一步出示 TLS 客户端证书，但证书只是认证的一种材料，TLS 握手成功不代表请求被授权。

TLS 之后是认证。认证模块拿到的输入是整个 HTTP 请求，实际主要看请求头和客户端证书。Kubernetes 支持客户端证书、静态 token、bootstrap token、OIDC、ServiceAccount 的 JWT 等多种方式；可以同时配置多个，按顺序逐个尝试，直到一个成功。认证失败返回 `401`。成功之后，apiserver 得到一个 username，有的认证方式还会给出 groups；后续授权和审计日志都围绕这个 username 展开。Kubernetes 没有 `User` 对象，也不在 API 里存用户资料，用户名和组只是认证器给出的字符串。

匿名请求是认证阶段的一个特殊情况。按官方文档，只要授权模式不是 `AlwaysAllow`，匿名访问默认就是开着的，可以用 `--anonymous-auth=false` 关掉；没有通过任何认证器的请求会得到用户名 `system:anonymous` 和组 `system:unauthenticated`。默认的 RBAC 只把 `system:public-info-viewer` 这类只读的公开信息角色绑给未认证组，所以匿名请求访问 Pod、Secret 这些资源时通常拿到的是 `403`，不是 `401`。说“匿名请求默认关闭”并不准确：默认打开的是匿名认证，默认拒绝的是匿名授权。

认证之后是授权。一次授权决策需要知道请求者、动作和受影响的对象，RBAC、ABAC、Node、Webhook 都是拿这些属性做判断。配置多个授权模块时，只要任意一个模块允许，请求就通过；全部拒绝才返回 `403`。RBAC 的规则是纯加法，没有“deny”规则，所以“默认拒绝”不是某条规则写出来的，而是没有规则匹配时的结果。ABAC 是早期模式，策略文件一行一个 JSON 对象；现在新集群的标准是 RBAC，官方文档把 ABAC 放在“从 ABAC 升级”的上下文里讲。

`system:masters` 是一个内建的组，加入它的用户拥有不受限制的集群管理员权限，绕过 RBAC 和 Webhook 的检查。这个组不能靠删 RoleBinding 收回权限，所以官方建议只把它当 break-glass 手段，平时不要把人加进去；真要给人集群管理员，应该建一个指向 `cluster-admin` 的 ClusterRoleBinding，至少还能审计和撤销。kind 用 kubeadm 建的集群里，admin 证书其实属于 `kubeadm:cluster-admins` 组，再通过一个显式的绑定拿到 `cluster-admin`，并不是 `system:masters`。这一点在下面的输出里能直接看到。

授权通过后还有准入。准入控制器分两类：mutating 控制器可以改对象，validating 控制器只能拒绝；执行顺序是先 mutating 再 validating。和授权模块不同，准入控制器能读到对象内容，而且只对创建、修改、删除、连接（proxy）这类请求生效，纯读请求不经过准入。任何一个准入控制器拒绝，请求立刻失败；全部通过后，对象还要过一遍对应 API 的校验例程，才写进存储。ServiceAccount 的 token 注入、Pod Security Admission、ResourceQuota 的用量检查，都在这一层发生。

> **旧资料提示**：旧教程用 `--admission-control` 配置准入插件。现在 kube-apiserver 的参考页把这个参数标为 DEPRECATED，改用 `--enable-admission-plugins` / `--disable-admission-plugins`；具体从哪个版本开始改名，refs 里的文档没有明确写，本书不写死版本号。

审计是另一条线，不属于认证、授权、准入中的任何一段，但三者都会留下记录。审计按策略决定记录哪些阶段、带不带请求和响应体；每条记录能回答谁、什么时候、对什么、做了什么、从哪里发起。审计默认不开：不给 apiserver 传 `--audit-policy-file` 就不会记录事件。排查权限问题时，审计日志和 `kubectl auth can-i` 是两种互补的证据，前者是事后事实，后者是事前询问。

## 30.2 ServiceAccount 与投射 token

ServiceAccount 是 namespace 级的非人类身份，用来给 Pod、控制器、CI 这类程序一个可认证的名字。它不是 User 对象，也没有密码；它存在于 API 里，名字在 namespace 内唯一。每个 namespace 创建时都会自动得到一个 `default` ServiceAccount，Pod 不写 `spec.serviceAccountName` 时就用它。默认 ServiceAccount 本身没有业务权限，只有所有已认证身份都有的 API discovery、`selfsubject*` 这类基础规则；但它的权限是 namespace 共享的，谁给 `default` 加了角色，所有用 `default` 的 Pod 都会继承。

在 Kubernetes 1.22 及以后，kubelet 通过 `TokenRequest` API 为 Pod 申请短期 token，再以 projected volume 的形式挂进容器；token 会自动轮换。1.24 起，Kubernetes 默认不再为每个 ServiceAccount 自动创建长期有效的 `default-token-*` Secret（`LegacyServiceAccountTokenNoAutoGeneration` 在 1.24 beta、1.26 GA，1.27 移除了这个门控），所以新集群里 `kubectl get secrets` 看不到那种 Secret 是正常的。老集群升级上来可能还留着旧的 token Secret，它们不会自动消失，但新 Pod 用的是投射 token，不读这些 Secret。

投射 token 挂在 `/var/run/secrets/kubernetes.io/serviceaccount/` 下，目录里有 `token`、`namespace`、`ca.crt` 三个文件。`token` 是一个 JWT，payload 里有 `aud`（受众，默认是 apiserver 的 URL）、`exp`/`iat`/`nbf`（过期、签发、生效时间）、`iss`（签发者）、`sub`（ServiceAccount 的用户名），以及 `kubernetes.io` 下的 namespace、Pod、ServiceAccount 和 node 引用。token 绑定到具体的 Pod 和 ServiceAccount：删掉 Pod 或 ServiceAccount，这个 token 就失效（Pod 删除时凭据最迟在 deletionTimestamp 后 60 秒撤销）；kubelet 在 token 活过 80% TTL 或超过 24 小时时会主动申请轮换，应用要重新读文件，不能把 token 缓存在内存里一直用。

不需要 API 访问的 Pod 应该关掉自动挂载。`automountServiceAccountToken: false` 可以写在 Pod 上，也可以写在 ServiceAccount 上；两处都写时 Pod 的设置优先。关掉之后目录不会出现，应用连 token 文件都读不到。需要临时给集群外的程序一个身份时，可以用 `kubectl create token` 走 TokenRequest 手工签发，`--duration` 指定有效期，`--audience` 指定受众；不指定时由 apiserver 决定有效期和默认受众。token 是 bearer 凭据，拿到文件的人就能冒充这个 ServiceAccount，不要把它打进日志、镜像或 ConfigMap。

`sa-token-reader` 这个 Pod 指定了 `serviceAccountName: shorty-api`，日志里先 `ls -l` 挂载目录：`ca.crt`、`namespace`、`token` 都是指向 `..data/` 的符号链接。kubelet 对投射文件用基于符号链接的原子写入，更新 token 时容器里看到的路径不变，读到的要么是旧内容、要么是新内容。`namespace` 文件的内容是 `shorty`，应用可以用它知道自己在哪个 namespace，不必依赖环境变量。

JWT 的 payload 被 `tr ',' '\n'` 拆成一行一个字段。`aud` 是 `https://kubernetes.default.svc.cluster.local`，`iss` 与它相同；`exp`、`iat`、`nbf` 是 Unix 秒，示例里的数字每次运行都会变，不要拿它当固定值。`kubernetes.io` 里同时有 `namespace`、`node`、`pod`、`serviceaccount` 四组引用，`pod.uid` 和 `serviceaccount.uid` 把 token 绑到具体对象；`sub` 是 `system:serviceaccount:shorty:shorty-api`，这就是 apiserver 在授权时看到的用户名。

`sa-no-token` 的 Pod 也用了 `shorty-api`，但加了 `automountServiceAccountToken: false`，日志只有 `no token mounted`。这说明关闭挂载不需要换 ServiceAccount，也不需要改镜像；如果应用根本不以这个身份访问 API，这是最省事的收窄方式。

最后一段先 `kubectl create token` 手工签一个 10 分钟的 token，再创建一个 `TokenReview` 对象让 apiserver 验证它。输出第一行 `true` 表示认证通过，第二行是 `system:serviceaccount:shorty:shorty-api`，第三行是它的组：`system:serviceaccounts`、`system:serviceaccounts:shorty`、`system:authenticated`。TokenReview 走的就是 apiserver 的 token 认证器：验签名、验过期、验 token 里引用的对象还在不在、验受众。它和 Pod 里挂的 token 是同一套机制，只是签发入口不同。

> **旧资料提示**：旧教程说“每个 Pod 都会自动挂一个 `default-token-*` Secret”。这是 1.24 之前的做法；现在默认是 TokenRequest 投射的短期 token，Secret 列表里没有 `default-token-*` 不代表 ServiceAccount 坏了。

## 30.3 RBAC 对象与规则

RBAC 只有四类对象：Role、ClusterRole、RoleBinding、ClusterRoleBinding。Role 一定属于某个 namespace，只能授予该 namespace 内的权限；ClusterRole 不属于 namespace，可以用来授予集群级资源（Node、PV）、非资源 URL（`/healthz`），也可以授予所有 namespace 里的 namespaced 资源。RoleBinding 把角色绑到一组 subject 上，作用范围就是它所在的 namespace；ClusterRoleBinding 的作用范围是整个集群。RoleBinding 可以引用同 namespace 的 Role，也可以引用一个 ClusterRole，但后者仍然只在 RoleBinding 的 namespace 内生效，这是复用公共角色的常用做法。绑定创建后 `roleRef` 不能改，要换角色只能删掉重建；`kubectl auth reconcile` 会处理这种删除重建。

一条 rule 由 `apiGroups`、`resources`、`verbs` 三部分组成，可选 `resourceNames`。core 组的 `apiGroups` 是空字符串 `[""]`，`apps`、`batch`、`rbac.authorization.k8s.io` 这些要写组名；`resources` 用 API URL 里的复数名，子资源用斜杠，例如 `pods/log`、`deployments/status`；`verbs` 是 `get`、`list`、`watch`、`create`、`update`、`patch`、`delete`、`deletecollection` 这些动作。`resourceNames` 把 get/update/patch/delete 这类针对单个对象的请求收窄到指定名字，但它不能限制顶层 create（创建时名字还可能由 apiserver 生成），也不能限制 deletecollection；用 `resourceNames` 限制 list/watch 时，客户端必须带 `metadata.name` 的 field selector，否则请求不会被授权。通配符 `*` 看起来省事，但新资源、新子资源、新动词都会自动落进这个通配符，最小权限场景下不要用。

subject 可以是 User、Group 或 ServiceAccount。ServiceAccount 的用户名是 `system:serviceaccount:<namespace>:<name>`，它自动属于 `system:serviceaccounts:<namespace>` 和 `system:serviceaccounts` 两个组；所有认证成功的身份还都在 `system:authenticated` 组里。写 RoleBinding 时 ServiceAccount 的 namespace 不能省；`kubectl create rolebinding --serviceaccount` 的格式是 `<namespace>:<name>`，跨 namespace 绑定时很容易写错。

ClusterRole 可以用 `aggregationRule` 把多个带特定标签的 ClusterRole 合并进来。控制面里的控制器会监听这些对象，把匹配标签的规则填进聚合角色的 `rules`；因此不要在聚合角色的清单里手写 `rules`，否则服务端 apply 会争抢字段所有权，控制面又会把规则覆盖回去。内建的 `admin`、`edit`、`view` 就是这么聚合出来的，`system:aggregate-to-admin` 这类标签不要随便改，改错会影响所有用这些角色的人。

`bind` 和 `escalate` 是两个危险动词。`escalate` 允许用户创建或修改包含自己没有的权限的 Role/ClusterRole；`bind` 允许用户创建绑定，把某个角色授出去，即使他自己没有这个角色里的权限。RBAC 默认会阻止“授予自己没有的权限”，但这两个动词是官方留的口子；给出去就等于把提权能力交出去，审计时要重点看。

## 30.4 最小权限与 namespace 作用域

给工作负载授权时，优先用 Role + RoleBinding，把权限限制在它真正工作的 namespace 里；ClusterRoleBinding 只在必须跨 namespace 或访问集群级资源时用。一个 namespace 里的 RoleBinding 不会因为 subject 是另一个 namespace 的 ServiceAccount 就扩大范围，绑定的作用域永远是 RoleBinding 所在的 namespace。内建的 `view` 是只读里比较安全的一档，它故意不允许读 Secret，因为读到 Secret 就可能拿到别的 ServiceAccount 凭据；`edit` 更宽，它允许读 Secret、允许用 namespace 里任意 ServiceAccount 跑 Pod，等于把该 namespace 里所有身份的能力都交出去；`admin` 还能在 namespace 里建 Role/RoleBinding。用这些内建角色前先看它们的边界，不要以为 `edit` 只是“改改 Deployment”。

`resourceNames` 是把权限收窄到具体对象的主要手段，但它只对能指名道姓的动词有效。`create` 在授权时还不知道新对象的名字，所以不能按名字限制；`deletecollection` 一次删一批，也不能按名字限制；`list`/`watch` 要配 `metadata.name` 的 field selector 才会被授权。也就是说，`resourceNames` 适合“只读某一个 ConfigMap/Secret/Deployment”，不适合“只允许创建某类对象”。

Secret 的 `get`、`list`、`watch` 都要当成高危权限。`get` 能读一个 Secret 的内容；`list` 和 `watch` 的响应里包含整个 namespace 的 Secret 内容，`kubectl get secrets -A -o yaml` 一条命令就能把能列出来的 Secret 全拿走。`pods/exec` 的 `create` 等于在容器里执行任意命令，能读挂载的 token、能访问该 Pod 的网络；`nodes/proxy` 的 `get` 也不是只读权限，它把请求转到 kubelet API，可以拿日志、attach 进程，而且绕过审计和准入。创建 Pod 或工作负载的权限同样危险：能创建 Pod 就能挂任意 Secret/ConfigMap、用 namespace 里任意 ServiceAccount、挂 hostPath 卷，所以“能建 Pod”在安全上远不止“能跑一个容器”。

`system:aggregate-to-admin`、`system:aggregate-to-edit`、`system:aggregate-to-view` 这些标签是内建角色聚合的入口，不要为了给某个 CRD 加权限去改内建角色本身；正确做法是新建一个带对应标签的 ClusterRole，让聚合控制器把规则并进去。改内建角色会在 apiserver 重启时被自动协调覆盖，覆盖不掉的改动还可能让所有依赖这个角色的人一起出问题。

权限不是建完就完了。定期用 `kubectl auth can-i --list --as=...` 看每个 ServiceAccount 的有效规则，用审计日志看哪些规则实际被用过；离开的人、过期的 CI 身份、临时排障留下的绑定都要清理。RBAC 只做加法，没有“拒绝”规则，所以一条多余的通配符不会被他处的拒绝规则抵消，只能删掉。

## 30.5 kubeconfig 与多环境

kubeconfig 是一份 YAML，顶层有 `clusters`、`users`、`contexts` 和 `current-context`。`clusters` 里的每一项记录 server 地址和 CA，`users` 记录证书、token 或 OIDC 配置，`contexts` 把 cluster、user 和 namespace 组合成一个名字，`current-context` 指向默认用哪一个。`kubectl` 默认读 `$HOME/.kube/config`；`--kubeconfig` 指定单个文件且不与其它文件合并，`KUBECONFIG` 环境变量则是多个文件的列表，Linux 用冒号分隔、Windows 用分号分隔。合并时第一个设置某个值或 map key 的文件获胜，后面的文件不会覆盖它；`current-context` 也按这个规则取第一个。kubeconfig 里的相对路径相对于文件所在目录解析，命令行上的路径相对于当前工作目录。

多环境最常见的用法是给 dev、staging、prod 各一个 cluster 条目，给人或机器各一个 user 条目，再按“环境 + 身份”建 context。切换环境只改 `current-context`，不改文件内容：`kubectl config use-context staging`。临时只想改 namespace，可以用 `kubectl config set-context --current --namespace=shorty`，它只动当前 context 的 namespace 字段。`--context` 命令行参数可以临时覆盖 `current-context`，适合脚本里固定环境。

kubeconfig 里可能有私钥、token 和集群 CA，要按凭据管理，不要提交到 Git，也不要用来源不明的 kubeconfig：官方文档明确警告，精心构造的 kubeconfig 可能导致恶意代码执行或文件泄露，拿到不可信文件时要像审查 shell 脚本一样先看内容。

`kubectl get pods` 能列出 `shorty` 里的 Pod，包括已经 `Completed` 的 `sa-token-reader`、`sa-no-token` 和迁移 Job 的 Pod；`view` 允许读 Pod。`kubectl delete pod -l app.kubernetes.io/name=api` 则对两个 api Pod 各返回一条 `Forbidden`，消息里是 `User "system:serviceaccount:shorty:shorty-reader" cannot delete resource "pods"`。同一个 context 里读可以、删不行，差别只在 RoleBinding 引用的 `view` ClusterRole 没有 `delete` 动词。

示例里的 user 是机器身份（ServiceAccount token）。人用的 OIDC、客户端证书也放在 `users` 的同一个位置，区别只在认证器怎么验证；多环境时给每个环境一个 cluster 条目、给每种身份一个 user 条目，再用 context 组合，不要把 prod 的 admin 证书塞进 dev 的 context 里。

## 30.6 多租户边界

namespace 首先是一个命名和策略作用域：不同 namespace 里可以有同名对象，Role、RoleBinding、NetworkPolicy、ResourceQuota、LimitRange 这些对象都按 namespace 生效。它不是一个网络边界，也不是一个安全边界。Kubernetes 默认允许所有 Pod 互相通信，流量不加密；如果 CNI 不支持 NetworkPolicy，写了策略也会被忽略。namespace 也不隔离集群级资源：CRD、StorageClass、Webhook、PersistentVolume、Node 都不属于任何 namespace，一个租户改了它们，可能影响所有租户。

要把一个 namespace 当成“租户”来用，至少要配四样东西。RBAC 限制谁能在这个 namespace 里做什么；NetworkPolicy 做默认拒绝再按需放行（第 24 章）；Pod Security Admission 限制 Pod 能用的特权、宿主路径和能力（第 31 章）；ResourceQuota 和 LimitRange 限制这个租户能占多少 CPU、内存、对象数量，并给没写 requests/limits 的 Pod 兜底。缺任何一项，隔离都只停留在名字层面。

ResourceQuota 是 namespace 级对象，可以限制 `requests.cpu`、`limits.memory` 这类计算资源的总和，也可以限制 Pod、Service、ConfigMap、Secret 等对象的数量。开了 CPU/内存配额后，新 Pod 必须写 requests 或 limits，否则可能被准入拒绝；LimitRange 可以给没写的 Pod 补默认值。配额只管 namespace 内的用量，不管网络流量，也不管节点上的实际争抢；一个租户把配额用满，别的租户的配额还在，但节点上的 noisy neighbor 仍可能影响它们，这时要靠 requests/limits、优先级和节点隔离。

多租户通常分软硬两档。软多租是多个团队共享一个集群，彼此有一定信任，靠 RBAC、配额、NetworkPolicy 把边界画出来；硬多租是互不信任的租户共享集群，需要更强的数据面隔离：专用节点池、污点与容忍、沙箱容器（gVisor/Kata 这类用户态内核或轻量 VM），甚至每个租户一个独立集群。节点隔离能减少容器逃逸后的影响面，但 kubelet 和 apiserver 仍是共享服务，攻击者仍可能从节点上的权限横向移动；所以“独立节点”不等于“独立集群”。

还有一类绕过风险不在 namespace 的模型里：能直接访问 kubelet API 或 etcd 的人，可以绕过 apiserver 的认证、授权、准入和审计。`nodes/proxy` 的 `get` 就能把请求转到 kubelet，`pods/exec` 的 `create` 能在容器里执行命令；安全清单要求 apiserver、kubelet、etcd 都不要暴露在公网，etcd 要走 mTLS 并限制访问。另一个常被忽略的入口是“能创建 Pod”：创建者可以挂任意 Secret、用任意 ServiceAccount、挂 hostPath，等于绕过 namespace 里的大部分隔离。所以 RBAC 不仅要管“谁能读 Secret”，还要管“谁能建 Pod、谁能在哪个 namespace 建 Pod”。

`shorty-deployer` 只拿到一条自定义规则：在 `shorty` 里 `create` `rolebindings`。`can-i create rolebindings` 返回 `yes`，说明它确实能建绑定。然后它试图创建一个指向 `cluster-admin` 的 RoleBinding，把 `cluster-admin` 绑到自己身上；apiserver 拒绝，错误是 `attempting to grant RBAC permissions not currently held`，后面列出它想授予但自己没有的权限：`APIGroups:["*"], Resources:["*"], Verbs:["*"]` 和 `NonResourceURLs:["*"], Verbs:["*"]`。

namespace 边界在这段输出里也看得很清楚：Role 和 RoleBinding 都在 `shorty`，按现在的绑定，`shorty-deployer` 也只能在 `shorty` 里建绑定。它不能把这个绑定建到别的 namespace，除非别的 namespace 里也有允许它 `create rolebindings` 的绑定。跨 namespace 的权限不是靠一个全局开关打开的，而是每个 namespace 各自授权。

## 30.7 排障：Forbidden 从哪里查

看到 `Forbidden` 先分清楚是认证还是授权。`401 Unauthorized` 是认证没过：证书过期、token 无效、凭据不被这个 apiserver 接受；`403 Forbidden` 是认证过了、授权没过：apiserver 已经知道你是谁，只是没有规则允许这个动作。排障时不要一上来就改 Role，先确认请求到底以谁的身份发出。

第一步是问具体动作：`kubectl auth can-i <verb> <resource> --as=system:serviceaccount:<ns>:<name> -n <ns>`。`--as` 要求调用者有 `impersonate` 权限，集群 admin 一般都有；普通用户没有时，用 `kubectl auth can-i` 查自己，或者让对方在自己的 context 里跑。第二步是看有效规则：`kubectl auth can-i --list --as=... -n ...`，这张表比逐条读 Role 快，能直接看出某个资源有没有动词、是不是被 `resourceNames` 限制、`apiGroups` 是哪一组。

常见错误集中在四个地方。第一是 namespace：RoleBinding 建在 `default`，Pod 在 `shorty`，绑定根本不生效；或者 `--as` 后面的 ServiceAccount namespace 写错。第二是 `apiGroups`：Deployment、StatefulSet、DaemonSet 在 `apps` 组，Job、CronJob 在 `batch` 组，Pod、ConfigMap、Secret 在 core 组（空字符串）；把 `deployments` 写到 `[""]` 里，`can-i` 对 `deployments.apps` 就是 `no`。第三是 `resourceNames`：名字大小写、拼写要完全一致，请求的 namespace 也要和绑定所在 namespace 对上，而且它不能限制 `create` 和 `deletecollection`。第四是 subject：RoleBinding 里 ServiceAccount 的 name 或 namespace 写错，或者 Pod 用了另一个 SA，绑定看起来在、实际没绑上。

如果 `can-i` 是 `yes` 但 Pod 里的程序还是读不到 API，就换一条线查：Pod 有没有挂 token、`automountServiceAccountToken` 有没有被关、Pod 的 `serviceAccountName` 是不是你以为的那个、token 有没有过期、Pod 到 apiserver 的网络通不通。api 镜像是 distroless，没有 shell，不能 `kubectl exec` 进去看文件；可以看 Pod 的 `spec.serviceAccountName` 和 `spec.automountServiceAccountToken`，或者用同样 SA 起一个带 shell 的调试 Pod 去看挂载目录。`kubectl describe pod` 的 Events 能看到挂载和拉镜像的问题，`kubectl logs` 能看到应用自己报的 401/403。

## 上生产前

**默认拒绝、最小权限，人和机器分开。** 新 namespace 先不给任何业务权限，按工作负载逐个建 Role + RoleBinding；人用 OIDC/SSO 的组做身份，机器用独立的 ServiceAccount，不要让人和 Pod 共用 `cluster-admin`。`system:masters` 只留作 break-glass，平时不给任何人；需要集群管理员就给一个可审计、可撤销的 `cluster-admin` ClusterRoleBinding。没有匿名访问需求时，给 apiserver 加 `--anonymous-auth=false`，把 `system:unauthenticated` 这条路彻底关掉。

**Secret 的读权限和 Pod 的执行权限要按高危权限对待。** 不给 `secrets` 的 `list`/`watch`，因为一次 list 就能带走整个 namespace 的 Secret；`get` 也要按需给，最好用 `resourceNames` 收窄。`pods/exec` 的 `create` 能进容器执行命令，`nodes/proxy` 的 `get` 能转到 kubelet，`pods` 的 `create` 能挂 Secret、用任意 SA、挂 hostPath，这些权限都要单独评估。`bind` 和 `escalate` 是 RBAC 的提权口子，给出去之前先想清楚谁能借此拿到 `cluster-admin`；审计策略里要能查到对这些动词的调用。

**每个 namespace 配齐配额、网络策略和 PSA。** ResourceQuota 限制 CPU/内存和对象数量，LimitRange 给没写 requests/limits 的 Pod 兜底，NetworkPolicy 先默认拒绝再按需放行，Pod Security Admission 限制特权、宿主路径和能力。这四样少一样，namespace 就只是名字边界。互不信任的租户不要只靠 namespace 分隔：按信任级别拆集群，或者至少用专用节点池、沙箱容器和更严格的网络策略；kubelet、apiserver、etcd 不要暴露在公网。

**凭据要能轮换，权限要能回收。** ServiceAccount 的投射 token 会自动轮换，但手工创建的长期 Secret token、kubeconfig 里的客户端证书、CI 里存的 token 都要有有效期和轮换流程。人离职、项目下线、临时排障结束，对应的 RoleBinding、ServiceAccount、token 都要清理；定期用 `can-i --list` 和审计日志做权限复核，重点看通配符、`bind`/`escalate`、`secrets`、`pods/exec` 和跨 namespace 的绑定。kubeconfig 按环境分开，prod 的凭据不要出现在开发机上，更不要提交到 Git。

| `--kubeconfig` / `KUBECONFIG` | 指定单个文件 / 合并多个文件 | `--kubeconfig` 不合并；合并时第一个值获胜 |
| `rules[].apiGroups/resources/verbs/resourceNames` | Role 的权限规则 | core 组写 `[""]`；`resourceNames` 不限制 create/deletecollection |
| `subjects[].kind/name/namespace` | 绑定的对象 | ServiceAccount 的 namespace 不能省 |
| `automountServiceAccountToken` | 是否把 SA token 挂进 Pod | 默认挂载；Pod 的设置覆盖 ServiceAccount 的设置 |
| `system:serviceaccount:<ns>:<name>` | ServiceAccount 的用户名 | 组是 `system:serviceaccounts:<ns>` 和 `system:serviceaccounts` |
| `bind` / `escalate` | 绕过 RBAC 提权防护的两个动词 | 高危，审计重点 |
| `system:masters` | 绕过 RBAC 和 Webhook 的内建组 | 只做 break-glass，删绑定也收不回 |

本章结束时，`shorty` 里的 api 已经用上 `ServiceAccount shorty-api`；`Role shorty-config-reader` 只允许 `get`/`list` ConfigMap，对应的 RoleBinding 把它绑到该 SA；30.4 的 `shorty-one-deployment-reader` 进一步把 Deployment 读权限收窄到名为 `api` 的对象。`shorty-reader`（只读）和 `shorty-deployer`（能建 RoleBinding 但不能提权）是演示身份，留在集群里不影响主链路。下一章在这个基础上打开 namespace 的 PSA `restricted` 标签，并给 api 配 securityContext。
