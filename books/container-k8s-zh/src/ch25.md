# 第 25 章 入口流量：从 Ingress 到 Gateway API（ingress-nginx 已于 2026-03 停止维护）

第 24 章把 shorty 的数据层收紧之后，api 仍然只有一个 ClusterIP。集群里的 worker 能连它，postgres 能连它，但从集群外访问 `http://shorty.local/` 没有任何入口：没有进程监听 80/443，也没有一条规则把域名和路径翻译成后端的 Service。用 `Service type=LoadBalancer` 或 `NodePort` 能把端口暴露出去，但那是四层转发，解决不了“同一个 80 端口按 Host 和路径分给不同后端”的问题。

七层的入口在 Kubernetes 里有两套 API。一套是 Ingress，规则简单，生态成熟，但 API 已经冻结；另一套是 Gateway API，把“谁提供入口”“谁监听端口”“谁定义路由”拆成不同对象，交给不同角色管理。2025 年 11 月，Kubernetes 项目宣布 ingress-nginx 退休，2026 年 3 月起不再维护，这让“新集群默认装一个 ingress-nginx”的习惯正式结束。本章要回答的就是：一段 Ingress YAML 背后到底是谁在监听 80/443，为什么现在新项目应该从 Gateway API 开始，以及存量 Ingress 怎么迁过去。

> **起点**：`s3-stateful` 已经跑起来，api、worker、postgres、redis 的 Service 都可用，集群里没有任何入口控制器。本章从 `bash code/ch25/setup.sh` 开始。setup 会建一个单节点 kind 集群、拉起 s3、预拉前端镜像，并把 `ingress2gateway` 装进 lab。第 24 章的 Calico 和 NetworkPolicy 不在这个起点里；如果你在那一章的集群上继续，要确保入口控制器所在 namespace 能访问 api 的 8080。

## 25.1 Ingress 模型与 API 冻结

Ingress 是一组七层路由规则，不是代理本身。一个 Ingress 对象说清楚三件事：哪些 Host（`spec.rules[].host`）的哪些路径（`paths[].path`）应该转发到哪个 Service 的哪个端口（`backend.service.name` 和 `backend.service.port`）；TLS 用哪个 Secret 终止；没有规则匹配时交给谁（`spec.defaultBackend`）。它不包含“监听哪个网卡”“用哪个进程”“证书怎么续”这些实现细节，这些都由 Ingress controller 决定。

所以只创建一个 Ingress 对象没有任何效果。Kubernetes 官方文档写得很直接：必须有一个 Ingress controller 来满足这个 Ingress，只创建资源本身不会产生作用。控制器通常是一个 Deployment，配合一个 `type=LoadBalancer` 或 `NodePort` 的 Service，把节点上的 80/443 接进来；它 watch Ingress 和 IngressClass，把规则翻译成 nginx、Envoy、HAProxy 之类的配置，再 reload 数据面。`kubectl get ingress` 里的 `ADDRESS` 为空，往往不是 Ingress 写错了，而是没有控制器给它分配地址。

控制器的行为可以用“watch、翻译、reload”三个词概括。它 watch Ingress、IngressClass、Service 和 EndpointSlice：Ingress 提供 host/path/backend，IngressClass 告诉它这份规则归不归自己管，Service 和 EndpointSlice 提供后端地址。任何一边变化，它都重新生成一份数据面配置，校验后 reload。这个循环是异步的，所以 `kubectl apply` 返回 `created` 之后，入口可能还要几秒才生效；`kubectl get ingress` 的 `ADDRESS` 和 Event 是观察这个循环的窗口。

IngressClass 是“用哪个控制器实现这份规则”的选择器。它有一个 `spec.controller` 字段，值是控制器的标识；Ingress 的 `spec.ingressClassName` 指向一个 IngressClass 对象。Kubernetes 1.18 之前用的是 `kubernetes.io/ingress.class` 注解，这个注解从未正式定义，只是被广泛支持；`ingressClassName` 不是它的直接替代，因为前者指向控制器名字，后者指向一个包含更多配置的 IngressClass 资源。一个集群可以把某个 IngressClass 标成默认（注解 `ingressclass.kubernetes.io/is-default-class: "true"`），没有写 `ingressClassName` 的 Ingress 就会落到它上面。

Ingress 只处理 HTTP 和 HTTPS。想把任意端口或任意协议暴露到集群外，仍然要用 `Service type=NodePort` 或 `LoadBalancer`。这条边界很重要：Ingress 不是“集群的万能入口”，它只认识 Host、路径、TLS 这些 Web 概念。

`pathType` 是每个 path 的必填字段，有三个值。`Exact` 按大小写精确匹配整个 URL 路径；`Prefix` 按 `/` 切分后的路径元素逐段匹配，大小写敏感，`/foo/bar` 能匹配 `/foo/bar/baz`，但不能匹配 `/foo/barbaz`；`ImplementationSpecific` 把匹配方式交给 IngressClass，具体实现可以把它当成 `Prefix`、`Exact`，也可以自己定义。Ingress 的匹配优先级是“最长路径优先”，长度相同时 `Exact` 优先于 `Prefix`。这些规则看起来细，但迁移到 Gateway API 时，`Prefix` 到 `PathPrefix` 的映射、尾斜杠和 URL 规范化的处理，都会在这里出问题。

Ingress API 从 Kubernetes 1.19 起是 stable（`networking.k8s.io/v1`）。Kubernetes 项目现在已经把 Ingress API 冻结：它仍然是 GA，仍然受 GA API 的稳定性保证，项目也没有计划移除它，但不会再给它加新功能。新特性都进了 Gateway API。这个状态和“废弃”不是一回事：已经写好的 Ingress 可以继续用，只是不要指望它再长出按 header 匹配、按权重分流、跨 namespace 挂载这些能力。

## 25.2 ingress-nginx 退役与迁移

Ingress API 冻结是一件事，ingress-nginx 退休是另一件事。前者说的是 API 不再加功能，后者说的是一个具体实现不再维护。Kubernetes 项目在 2025 年 11 月宣布 ingress-nginx 退休，2026 年 3 月起停止维护。已经发布的镜像和 Helm chart 不会消失，但不再有安全修复，也不会再针对新的 Kubernetes 版本做兼容性测试。对一个还在接收外部流量的入口来说，“能跑”和“有人修 CVE”是两回事。

很多人把 ingress-nginx 当成 Kubernetes 的默认控制器，因为它长期是 kind、minikube 和各种教程里的第一个选择。它不是 Kubernetes 内置组件，也从来不是唯一选择。Kubernetes 官方文档的 Ingress controller 页面列了几十个实现，项目自己维护的是 AWS 和 GCE 的两个；ingress-nginx 只是其中社区使用最广的一个。现在它停止维护，迁移不是“把镜像标签换一下”，而是要重新选一个还在维护的实现，并重新验证它的行为。

迁移有两条路。第一条是换一个受支持的 Ingress controller，继续用 Ingress API：规则文件基本不动，但注解要重写，因为注解是控制器私有的契约，不是 Ingress API 的一部分。第二条是直接上 Gateway API：Ingress 的 host/path/backend 能机械转换，TLS Secret 可以复用，但 rewrite、超时、限流、灰度这些用注解表达的能力，要换成 HTTPRoute 的 filter、`backendRefs` 或实现自己的策略 CRD。两条路可以并行：先把入口切成新实现，确认流量正常，再决定要不要继续往 Gateway API 走。

迁移前先盘点，不要先改 YAML。把现有 Ingress 按 host 列出来，逐个记录：路径和 `pathType`、后端 Service 和端口、TLS Secret 名字、有没有 rewrite/redirect、连接和读取超时、请求体大小限制、限流和并发限制、认证、会话保持、灰度或 A/B 注解。前面几项是 Ingress API 的标准字段，后面的几乎都在注解里。盘点的结果是两张表：哪些能自动转换，哪些必须手工映射，哪些在新实现里没有对应能力、需要改架构。

盘点表可以直接当迁移工单用：一行一个 Ingress，列是 host、path、`pathType`、后端、TLS Secret、注解清单、目标写法、验证方式。注解清单不要只抄名字，要把值也抄下来，因为同一个注解在不同实现里的单位可能不同（秒和毫秒、字节和 MB），照抄数字很容易把 30 秒配成 30 毫秒。迁移完成后，用同一张表逐行打勾，比“看起来都迁完了”可靠。

> **旧资料提示**：很多旧教程把 ingress-nginx 当成“Kubernetes 默认的 Ingress controller”，安装步骤里直接 `kubectl apply` 它的清单。它不是内置组件，而且已经在 2025 年 11 月宣布退休、2026 年 3 月起停止维护；新集群不要把它当默认选项，存量集群要尽快换到受支持的实现或 Gateway API。

## 25.3 Gateway API 的资源模型

Gateway API 不是 apiserver 自带的 API。它是一组 CRD，由 SIG-Network 维护，安装到集群里之后才出现 `gateway.networking.k8s.io` 这个 API 组。这一点和 Ingress 不同：Ingress 是 `networking.k8s.io/v1` 的内置资源，任何 Kubernetes 集群都有；Gateway API 要先装 CRD，再装一个实现了这些 CRD 的控制器，两者缺一不可。只装 CRD 时，`kubectl get gateway` 能返回空列表，但不会有任何数据面。

Gateway API 的核心是四个 stable 的 kind。`GatewayClass` 描述“哪一类 Gateway，由哪个控制器实现”，它是集群级对象，`spec.controllerName` 必须和实现注册的名字一致。`Gateway` 描述“一个具体的入口实例”：监听哪些端口、什么协议、哪些 hostname、TLS 怎么终止、允许哪些 namespace 的 Route 挂上来；它是 namespace 级对象。`HTTPRoute` 描述“HTTP 请求怎么从 Gateway 的 listener 转到后端 Service”，包括 hostnames、path/header 匹配、filter 和 backendRefs。`GRPCRoute` 是 gRPC 版本，结构和 HTTPRoute 类似。除此之外还有 experimental 通道的 TLSRoute、TCPRoute、UDPRoute 等，本章只装 standard 通道，不碰这些。

这套模型是围绕角色设计的。基础设施提供者管 GatewayClass 和底层负载均衡；集群运维管 Gateway，决定开哪些端口、用哪张证书、哪些 namespace 能挂 Route；应用开发者只写自己 namespace 里的 HTTPRoute，把 host/path 指到自己的 Service。这个分工比 Ingress 清楚：Ingress 把“用哪个控制器”和“路由规则”塞在同一个对象里，谁都能改 `ingressClassName`，也都能改 TLS；Gateway API 把边界拆开，Gateway 的 `allowedRoutes` 和 Route 的 `parentRefs` 必须双方都同意，才能建立连接。

`parentRefs` 是 Route 绑 Gateway 的字段。默认情况下，`parentRefs[].namespace` 不写就指 Route 自己的 namespace；跨 namespace 引用要显式写 namespace，并且目标 Gateway 的 listener 要允许。`sectionName` 可以只绑某一个 listener，`port` 可以按端口绑；不写就绑这个 Gateway 上所有匹配的 listener。一个 Route 可以写多个 `parentRefs`，但每个父对象都要独立接受它。

`allowedRoutes` 是 Gateway 这一侧的过滤器。它有两个维度：`namespaces.from` 可以是 `Same`（默认，只允许同 namespace）、`All`（所有 namespace）或 `Selector`（按 namespace 标签选）；`kinds` 可以限制只允许 HTTPRoute 或某几种 Route。跨 namespace 的场景里，Gateway 的 `allowedRoutes` 和 Route 的 `parentRefs.namespace` 必须同时对得上，否则 Route 的 `Accepted` 条件会是 `False`。这不是多余的仪式：它防止一个应用团队把自己的 Route 挂到别人的 Gateway 上，偷偷改掉入口的 host 或 TLS。

## 25.4 安装一个 Gateway 实现

CRD 只是类型定义，真正把 Gateway 变成监听的进程、把 HTTPRoute 变成 nginx 配置的，是 Gateway 实现。常见的两个选择是 NGINX Gateway Fabric（NGF）和 Envoy Gateway：前者用 NGINX 做数据面，后者用 Envoy。本章选 NGF，因为它的数据面就是 nginx，配置和日志对读过 Ingress 的读者比较熟；这不代表它比 Envoy Gateway 更适合所有场景。

NGF 的安装分两层。控制面是一个 Deployment，跑在 `nginx-gateway` namespace，watch GatewayClass、Gateway、HTTPRoute 和 Secret，负责把配置翻译成 nginx 配置。数据面不是提前装好的：每创建一个 Gateway，NGF 就为该 Gateway 创建一个 Deployment 和一个 Service，Service 名字是 `<gateway 名字>-nginx`，Pod 里跑 nginx。这个设计和 Ingress controller 不同：Ingress controller 通常是一个共享的 Deployment，所有 Ingress 共用；Gateway API 允许一个 Gateway 一个数据面，隔离性更好，但每个 Gateway 都要占一份资源。

## 25.5 路由、TLS 与灰度

Gateway 只负责“在哪里听”，HTTPRoute 才负责“怎么分”。一个 HTTPRoute 的骨架是 `parentRefs`、`hostnames` 和 `rules`。`parentRefs` 指向 Gateway，可以带 `sectionName` 只绑某个 listener；`hostnames` 是这组规则匹配的 Host，必须落在 Gateway listener 的 hostname 范围内；`rules[].matches` 里可以写 path、headers、queryParams、method，`rules[].backendRefs` 指定后端 Service 和端口，还能带 `weight`。

host 匹配是最外层。客户端请求 `http://shorty.local/healthz` 时，curl 会发 `Host: shorty.local`；如果直接访问 `http://127.0.0.1:18080/healthz`，Host 就是 `127.0.0.1:18080`，不会匹配 `shorty.local`。示例里用 `-H 'Host: shorty.local'` 就是为了把 Host 头和地址分开，模拟 DNS 已经把 `shorty.local` 解析到入口地址之后的行为。真实环境里由 DNS 把域名指到 Gateway 的地址，Host 头自然就是域名。

path 匹配的默认类型是 `PathPrefix`，值必须是 `/` 开头的绝对路径，不能有连续的 `//`。`PathPrefix` 按 `/` 切分路径元素逐段匹配，大小写敏感，尾斜杠忽略；`/api` 能匹配 `/api`、`/api/`、`/api/links`，但不匹配 `/apix`。`Exact` 只匹配完全相同的路径，`/api` 不匹配 `/api/`。`RegularExpression` 是实现相关的能力，不是所有实现都支持，NGF 支持但本章不用。多条规则都能匹配时，更具体的路径优先；这是 HTTPRoute 规范定义的优先级，不是 nginx 自己的 `location` 顺序。

TLS 在 Gateway 的 listener 上配置，不在 HTTPRoute 上。`protocol: HTTPS`、`port: 443`、`tls.mode: Terminate`，再用 `certificateRefs` 指向一个 `kubernetes.io/tls` 类型的 Secret，Secret 里要有 `tls.crt` 和 `tls.key`。TLS 在 Gateway 终止，Gateway 到后端 Service 仍然是明文 HTTP；这一点和 Ingress 的 TLS 行为一样。Secret 默认必须和 Gateway 在同一个 namespace；跨 namespace 引用需要目标 namespace 里的 ReferenceGrant 放行，否则 listener 的 `ResolvedRefs` 会变成 `False`。

自签证书用 `openssl req -x509` 生成。`-subj '/CN=shorty.local'` 设置 Common Name，`-addext 'subjectAltName=DNS:shorty.local'` 加 SAN；现代客户端主要看 SAN，只写 CN 不够。生成的证书没有 CA 签名，`curl` 默认会拒绝它，报 `self-signed certificate`（退出码 60；具体文案随 OpenSSL 版本和证书链变化，Java/Go 客户端常见的说法是 `certificate signed by unknown authority`）；`curl -k` 跳过校验，`openssl s_client` 可以看到 subject 和 issuer 都是 `shorty.local`。生产环境不能用自签证书，要用 cert-manager、ACME 或企业 CA 签发的证书；自签只适合本地验证和内部测试。

`backendRefs` 可以写多个后端，每个后端带一个 `weight`。weight 是相对权重，不是百分比：两个后端各写 1 就是各 50%，写 90 和 10 就是 90/10，写 9 和 1 也是 90/10；只写一个且 weight 大于 0 就是 100%。weight 默认是 1，最小值 0，最大值 1,000,000。weight 为 0 的条目不接收流量，可以在正式放量前先把新版本挂上去，确认 Service、端口和 `ResolvedRefs` 都没问题，再改数字。实现按权重做的是统计意义上的选择，不是严格的“第 9 个请求给旧版、第 10 个给新版”；样本越小，实际比例偏离权重越明显。

这套字段在 NGF 2.8.0 上可用。它的 Gateway API 兼容表按 Route 类型分行：HTTPRoute 的 `backendRefs` 支持多个后端和 `weight`，表里的 `weight: Not supported` 属于 TLSRoute 那一行；HTTPRoute 的 `backendRefs` 只是不支持在引用单个后端时再套 filter（backend ref filters），本章不用这个能力。读兼容表时要看清限制写在哪一行：把 TLSRoute 的限制套到 HTTPRoute 上，就会得出“只能有一个后端”的错误结论。具体行为仍以实测为准。

filter 用来改请求或响应。`RequestRedirect` 可以把 HTTP 重定向到 HTTPS，指定 `scheme` 和 `statusCode`；它不能和 `backendRefs` 同时出现在一条规则里。`URLRewrite` 可以改 path 或 Host，比如把 `/api` 前缀换成 `/`，或者把请求转到另一个 host。ingress-nginx 的 `rewrite-target` 注解在 Gateway API 里通常映射成 `URLRewrite`，但具体到某个实现，filter 的支持程度不一样，迁移时要看实现的 conformance 列表。

## 25.6 从 Ingress 迁移

迁移工具叫 `ingress2gateway`，是 Gateway API 项目维护的转换器。它读取 Ingress 和某些实现的私有 CRD，输出 Gateway API 的 Gateway、HTTPRoute 等对象。它支持从集群里读，也支持 `--input-file` 读本地 YAML；`--providers=ingress-nginx` 告诉它按 ingress-nginx 的注解方言解释输入。本章用 v1.2.0，输出的是 `gateway.networking.k8s.io/v1` 的 stable 对象。

转换器只做“结构翻译”，不复制注解。它的 README 明确写了这一点：ingress2gateway 不打算把 Ingress 的注解搬到 Gateway API 对象上。原因很直接：注解是控制器私有的，Gateway API 标准里没有对应字段；工具能识别一部分常见注解，把它们翻译成 filter 或 timeout，但不可能覆盖所有实现的所有注解。转换结果里的警告就是让你知道哪些东西被丢掉了。

TLS Secret 可以复用。Ingress 的 `spec.tls[].secretName` 和 Gateway listener 的 `certificateRefs` 都指向同一个 `kubernetes.io/tls` Secret，证书和私钥的格式一样。转换器会为每个 TLS host 生成一个 443 listener，并额外生成一个 HTTPRoute，把 80 的请求 308 重定向到 443；这是因为 ingress-nginx 在配置了 TLS 之后默认会做 ssl-redirect。这个行为不是 Ingress API 规定的，而是 ingress-nginx 的默认值，迁移时要确认新实现是否也这样。

pathType 的映射比传闻简单。Gateway API 的 spec 明确写了：`PathPrefix` 在语义上等价于 Ingress 的 `Prefix`，`Exact` 也一一对应。ingress2gateway 的转换表同样写的是 `Prefix` → `PathPrefix`。真正需要人工确认的不是匹配算法，而是实现层的 URL 规范化、尾斜杠和重定向：ingress-nginx 可能会合并斜杠、做大小写或百分号编码处理，Gateway API 标准不规定这些，NGF 和 Envoy Gateway 的行为也可能不同。工具会专门警告“Gateway API 不支持配置 URL normalization”，这句话值得在迁移评审里保留。

`kubectl diff` 的退出码是 1 表示有差异，不是命令失败。输出里能看到几类差异：Gateway 的 listener 名字从 `http`/`https` 变成 `shorty-local-http`/`shorty-local-https`，线上对象的 `labels` 被删掉，`gateway.networking.k8s.io/generator` 注解被加上；HTTPRoute 的 `parentRefs` 被加上 `port: 443` 和 `sectionName: shorty-local-https`，线上多出来的 `/healthz` 规则在生成对象里没有；重定向用的 `shorty-http-redirect` 是一个新对象，在 diff 文件的后半段出现。`generation`、`resourceVersion`、`last-applied-configuration` 这些是运行时或 apply 元数据，不是语义差异。这些差异要逐条判断：哪些是工具生成的、可以接受；哪些是线上对象有而生成对象没有的、不能覆盖。

两条注解没有被搬到 HTTPRoute 上，输出里的 `nginx annotations not copied` 就是检查结果。这不是工具漏了，而是设计如此：`proxy-body-size` 和 `limit-rps` 没有标准字段，硬塞进 HTTPRoute 的注解只会制造一个“看起来迁移了、实际没生效”的假象。正确做法是把它们翻译成实现自己的策略对象，或者在迁移评审里明确接受“新入口暂时没有这两个限制”，再排期补上。

生成的清单还要过一遍服务端 dry-run。`kubectl apply --dry-run=server` 会检查 CRD schema、必填字段和 CEL 校验，但不会真的改线上对象；这一步通过，说明转换结果至少是合法的 Gateway API 资源。真正 apply 之前，先把旧 Ingress 的 YAML 备份出来，删掉旧对象之后如果发现路由不对，可以用备份快速回滚。

转换器的输出是起点，不是终点。它能把 host/path/backend/TLS 这些结构化的字段搬过去，但搬不了“为什么这条规则存在”的上下文：哪条 path 是给移动端的、哪个 header 是给内部测试的、哪个超时是为了绕过一个慢后端。这些信息要从 Ingress 的注释、提交记录和监控里找回来，写进新的 HTTPRoute 或实现策略里，否则迁移完成后规则看起来一样，行为却少了几个约束。

最后的 `curl` 是在旧 Ingress 删除之后发的：`/healthz` 仍然返回 `ok`，说明流量已经走 Gateway，不依赖 Ingress。迁移期更稳妥的做法是两套入口并行：DNS 的 TTL 调短，先把一小部分流量指到新入口，观察错误率和延迟，再逐步切全部；旧 Ingress 和旧控制器保留到观察期结束。本章的 lab 里没有 DNS 服务器，所以用“删掉旧对象、再请求一次”来模拟切流完成，生产环境不要这么干。

## 25.7 排障：404 与 TLS 握手失败

`curl` 返回 404 时，先区分是“没有匹配的 Route”还是“匹配了但后端不对”。最外层的信号在 Gateway 和 HTTPRoute 的 status 里：Gateway 的 listener 有 `Programmed`、`ResolvedRefs` 条件，HTTPRoute 的 `status.parents[].conditions` 有 `Accepted`、`ResolvedRefs`。如果 Route 的 `Accepted` 是 `False`，请求根本不会进入它的规则，404 是正常的；如果 `Accepted` 是 `True` 但 `ResolvedRefs` 是 `False`，规则在，后端 Service 或端口引用有问题，通常会返回 500 或 503，而不是 404。

`parentRefs` 的 namespace 和 name 是最常见的错误。Route 和 Gateway 在同一个 namespace 时，`parentRefs[].namespace` 可以省略；不在同一个 namespace 时必须显式写，而且 Gateway 的 `allowedRoutes.namespaces.from` 要允许。名字写错、`sectionName` 写了一个不存在的 listener、`port` 和 listener 端口对不上，都会让 `Accepted` 变成 `False`，reason 通常是 `NoMatchingParent` 或类似的值。

hostnames 对不上也会 404。Gateway listener 的 `hostname`、HTTPRoute 的 `hostnames`、请求的 `Host` 头三者要能匹配；只匹配其中两个不够。用 `curl -H 'Host: ...'` 测试时，注意端口也算在 Host 头里：`127.0.0.1:18080` 和 `shorty.local` 不是一回事。

后端端口错时，先看 Service 的实际端口，再看 `backendRefs[].port` 是不是同一个。`kubectl -n shorty get svc api -o jsonpath='{.spec.ports[*].port}'` 输出 8080；如果 HTTPRoute 写的是 80，NGF 会找不到后端，`ResolvedRefs` 变成 `False`，请求会失败（通常是 500/503，具体状态看实现）。端口名和端口号都可以用，但名字必须在 Service 里存在。

`kubectl get gateway,httproute` 的表格里，Gateway 的 `PROGRAMMED` 是 `True`；HTTPRoute 的表格只有 `NAME`、`HOSTNAMES`、`AGE`，`Accepted` 要看后面的 status 条件。输出里多出的 `kind-ingress-gateway` 是 lab 的 cloud-provider-kind 注册的，不是本章的 Gateway；真实集群也可能有多个实现，按名字找自己的。故意建的 `shorty-bad-port` 父 Gateway 是有效的，所以 `Accepted` 还是 `True`，但它引用的 8081 端口在 `api` Service 上不存在，`ResolvedRefs` 变成 `False`，reason 是 `BackendNotFound`。这就是“路由被接受、后端引用解析不了”的样子，和“父对象根本不存在”是两种不同的故障。把它删掉，避免它干扰后面的请求。

同一个地址，`Host: other.local` 返回 404，`Host: shorty.local` 返回 200。404 不是 nginx 挂了，而是没有任何 HTTPRoute 的 `hostnames` 匹配 `other.local`；数据面按规范返回 404。这个对比把“入口进程活着”和“路由匹配上了”分开：端口能连、TLS 能握手，不代表 Host 和 path 能命中规则。

控制器日志用 `kubectl -n nginx-gateway logs deploy/ngf-nginx-gateway-fabric` 看。NGF 的日志是 JSON，字段多，排障时先看 `level` 和 `msg`；如果 Route 被拒绝，日志里通常会有对应的 reason 和对象名。日志里没有报错也不代表配置正确，最终还是要用 `Accepted`/`ResolvedRefs` 条件和实际请求验证。

TLS 报 `self-signed certificate`、`certificate signed by unknown authority` 或 `unable to get local issuer certificate` 时，先确认这是不是自签证书。`openssl s_client` 的 `issuer` 和 `subject` 相同，就是自签；`curl -k` 能过，说明证书本身和 SNI 都没问题，只是客户端不信任签发者。把 CA 加进系统信任库（`/usr/local/share/ca-certificates/` 加 `update-ca-certificates`）或者用 `--cacert` 指定 CA，才能在不跳过校验的情况下验证证书链。生产环境应该用 ACME 或企业 CA 签发的证书，自签只用于本地和测试。

> **旧资料提示**：旧教程里排查 Ingress 404 时常说“看 nginx 的 `location` 配置”。Gateway API 的实现不一定把配置暴露成 nginx 文件，NGF 的配置在数据面 Pod 里动态生成；先看 Gateway/HTTPRoute 的 status 条件，再看控制器日志，比直接翻 nginx.conf 更快，也更接近 API 的语义。

## 上生产前

新项目从 Gateway API 开始，Ingress 只用于存量迁移。Ingress API 已经冻结，ingress-nginx 在 2026 年 3 月之后不再维护，继续在新集群里默认装它，等于把入口交给一个不会再有安全修复的组件。选实现时先看它支持的 Gateway API 版本和 conformance 结果，再看数据面是不是团队已经会运维的（NGINX、Envoy、HAProxy），不要只看安装命令短不短。存量 Ingress 可以继续跑，但要有明确的迁移时间表；迁移期间旧控制器保留，新入口并行，按 DNS 或流量比例切。

Gateway 的 `allowedRoutes` 要按 namespace 限制，不要图省事写 `from: All`。入口是集群的边界，一个应用团队如果能把自己的 HTTPRoute 挂到生产 Gateway 上，就能改 host、改 path、甚至用 `RequestRedirect` 把流量导走。用 `from: Same` 让应用只在自己的 namespace 里挂路由，或者用 `Selector` 按 namespace 标签放行；跨 namespace 的证书引用用 ReferenceGrant，不要用通配的 `All`。TLS 证书用 cert-manager 或 ACME 自动续期，不要用自签证书上生产；自签只适合本地验证，浏览器和客户端不会信任它。

入口控制器至少 2 副本，配合 PodDisruptionBudget。单副本的控制器在节点 drain、滚动升级或 OOM 时会有一段没有数据面的时间；2 副本加 PDB 能让自愿中断期间至少留一个。数据面的副本数按流量定，控制面和数据面要分别算资源，不要只给控制面加副本。2.5 GB 的 lab 里只开一个副本，是为了给示例留内存，不是生产建议。

超时、请求体大小、限流不要用默认值。不同实现的默认值不一样：NGF 和 Envoy Gateway 的读超时、body size、连接数限制都可能在实现自己的策略 CRD 里，而不是 HTTPRoute 的标准字段。迁移前把旧入口的这些参数盘点出来，逐条在新实现里配好，再用压测和故障注入验证；默认值在低流量下看不出问题，到了大请求或慢客户端才会暴露。

灰度用 header 或权重，配合指标和回滚。header 适合内部用户或特定客户端先试，规则确定、容易回滚；按比例放量用 `backendRefs[].weight`，NGF 2.8.0 支持，但换实现前仍要核对兼容表里对应的 Route 类型。无论用哪种，都先把新版本接一小部分流量，观察错误率、P95 延迟和后端资源，确认稳定后再放大，不要一次切 100%。灰度期间新旧版本的日志、指标要能分开看，否则出了问题分不清是哪一边；权重是相对值，最后一步可以把旧版本设成 0，保留规则方便回滚。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `kubectl get ingress,ingressclass,gateway,httproute` | 一次看四类入口对象 | Ingress 与 Gateway 是两套 API，不要混着看 |
| `spec.rules[].http.paths[].pathType` | Ingress 路径匹配类型 | 必填；`Prefix`、`Exact`、`ImplementationSpecific` |
| `spec.ingressClassName` | Ingress 选 IngressClass | 不写时用默认 class；class 不存在不会在 apply 时被拒 |
| `parentRefs` | HTTPRoute 绑 Gateway | `namespace` 默认同 namespace；`sectionName` 可只绑一个 listener |
| `allowedRoutes.namespaces.from` | Gateway 允许哪些 namespace 挂 Route | 默认 `Same`；跨 namespace 用 `Selector` 或 `All` |
| `backendRefs[].weight` | 同一规则里多个后端的相对权重 | 默认 1，最小 0，最大 1,000,000；不是百分比；NGF 2.8.0 的 HTTPRoute 支持 |
| `tls.mode` / `tls.certificateRefs` | Gateway 终止 TLS | `Terminate` 默认；引用 `kubernetes.io/tls` Secret |
| `curl -H 'Host: shorty.local'` | 不改 DNS 测 host 路由 | 端口也在 Host 头里，别只写域名 |
| `openssl req -x509 -newkey rsa:2048 -nodes` | 生成自签证书 | 加 `-addext 'subjectAltName=DNS:shorty.local'` |
| `ingress2gateway print --providers=ingress-nginx` | 把 Ingress 转成 Gateway/HTTPRoute | 注解不复制，警告要逐条处理 |
| `kubectl diff -f` | 对比生成清单和线上对象 | 退出码 1 表示有差异，不是失败 |
| `kubectl wait --for=jsonpath=...` | 等 Gateway/Route 的条件 | 条件在 `status.listeners` 或 `status.parents` 下 |
| `curl -k` / `openssl s_client` | 跳过自签证书校验 / 看证书 | 生产不要用 `-k` 代替信任链配置 |

本章结束时，`shorty` 运行在单节点 kind 集群上，集群里有 Gateway API 1.6.3 的 CRD、NGINX Gateway Fabric 2.8.0、`Gateway shorty-gw`、`HTTPRoute shorty` 和 `Secret shorty-tls`；`curl -H 'Host: shorty.local'` 经 Gateway 返回 `ok`，旧的 Ingress 已经删除，只留下转换文件作为迁移记录。下一章从 `s3-stateful` 继续讲存储，入口这条链路不再改。
