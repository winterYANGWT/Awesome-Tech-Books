# 第 9 章 Dockerfile 与构建缓存

shorty 的 api 只有几个 Go 文件，改掉 `http.go` 里的一行注释，再执行一次 `docker build`，输出里 `RUN go mod download` 又跑了一遍，依赖重新从代理下载。代码只改了一行，依赖却没有变，为什么构建把两者绑在了一起？答案不在 Go，而在 Dockerfile 的指令顺序：`COPY . .` 把经常变化的源码复制进了依赖层之前，源码一变，这一层和它后面的所有步骤都失效。

`shorty:dev` 在前面的章节里一直是个黑盒：仓库脚本把它构建出来，我们只管 `docker run`。这一章把这个盒子打开，从一份能用的单阶段 Dockerfile 开始，逐条解释每个指令在构建图上做了什么；然后看构建上下文、层和缓存键，解释“命中”和“不命中”分别由什么决定；再把同一份应用改成多阶段 scratch 镜像，最后故意制造两个与 `.dockerignore` 有关的故障。

本章的示例都在 lab 里跑，Docker Engine 29.9.2，buildx 0.38.1。构建输出统一加 `--progress=plain`，因为默认的进度界面会把并行的步骤压缩成几行，看不清哪一步命中了缓存。

> **起点**：第 8 章结束时 `shorty-api` 以 uid 65532 运行，`shorty:dev` 已经由仓库脚本构建好。本章先把它删掉重建，示例会重新构建 `shorty:dev` 并在 18080 端口启动 `shorty-api`。在 lab 里执行 `bash code/ch09/setup.sh` 拉好基础镜像；如果从第 8 章接着做，脚本也会清掉旧的 `shorty-api` 容器，避免名字冲突。第 8 章的 `shorty-pg`、`shorty-redis` 还在，本章不动它们；重启的 `shorty-api` 只用来验证构建产物，不再带第 8 章的 seccomp 和 `--cap-drop` 参数。

`# syntax=docker/dockerfile:1` 是解析器指令，必须放在第一行、任何注释和空行之前。它告诉 BuildKit 用哪个 Dockerfile 前端来解析这份文件；`docker/dockerfile:1` 跟随 1.x 的最新稳定版，构建时会自动检查更新。不写这一行也能构建，用的是 BuildKit 内置的前端；写了以后，新语法和修复不必等 Docker Engine 升级。

`FROM golang:1.27.3-trixie` 固定了发行版和 Go 版本。标签仍然可变：维护者可以把同一个 `1.27.3-trixie` 重新发布成另一份内容。要完全固定，可以写 `golang:1.27.3-trixie@sha256:...`，代价是每次升级都要手动换 digest。生产上通常两者都写：标签给人看，digest 给构建用。

这里没有选 `alpine` 再手工装 Go：`golang:1.27.3-trixie` 已经带好编译器、标准库和 CA 证书，构建阶段不需要自己维护工具链。构建镜像大一点没关系，它不会进入最终运行镜像；9.4 的多阶段会把这份成本留在 `build` 阶段。真正要控制大小的是最后那个阶段，而不是中间阶段。

`WORKDIR /src` 设工作目录，后面的 `COPY`、`RUN` 都相对于它。用绝对路径，不要用 `RUN cd` 代替；`WORKDIR` 在目录不存在时会创建它，也会进入镜像配置，容器启动时仍以它为默认目录。

接下来是这一章最关键的两行：

```dockerfile
COPY go.mod go.sum ./
RUN go mod download
```

`go.mod` 和 `go.sum` 只在依赖变化时变，源码每天都在变。把它们单独复制、先下载依赖，依赖层就有了一个稳定的缓存键。等 `COPY . .` 把源码复制进来时，即使源码变了，前面的 `RUN go mod download` 仍然可以复用。这就是 9.3 要验证的效果。

`RUN CGO_ENABLED=0 go build -trimpath -o /shorty .` 做静态编译。关闭 cgo 后，生成的二进制不依赖 glibc，才能放进 `scratch` 这种没有 libc 的根文件系统。`-trimpath` 去掉构建机器的绝对路径，让不同机器上的产物更容易一致。这条 `RUN` 的结果是文件系统里多了一个 `/shorty`，所以它会产生新层。

最后两行：

```dockerfile
ENTRYPOINT ["/shorty"]
CMD ["serve"]
```

这是 exec 形式，JSON 数组里的第一项是可执行文件，不会经过 shell。`ENTRYPOINT` 是固定的入口，`CMD` 是默认参数；`docker run shorty:dev version` 会把 `CMD` 换成 `version`，实际执行 `/shorty version`。稍后的多阶段示例会用到这个行为。

exec 形式和 shell 形式的差别不只在写法。shell 形式写成 `CMD /shorty serve`，容器启动的是 `/bin/sh -c "/shorty serve"`，PID 1 是 shell，应用是它的子进程；`docker stop` 发来的 SIGTERM 先到 shell，shell 不一定会转发。exec 形式让 `/shorty` 直接成为 PID 1，信号能送到应用。README 里 shorty 收到 SIGTERM 后会先把 readiness 置为失败、等几秒再关闭，这依赖信号真的能到达它。

为了让输出不受 lab 里旧缓存的影响，这条构建命令加了 `--no-cache`；平时不需要加，只有在想确认“从零开始也能构建”或者怀疑缓存有问题时才用。`--provenance=false` 只是关掉额外的来源证明清单，让输出短一些，和构建结果无关。`--no-cache` 并不是让每一行都变成 `DONE`：只改元数据、没有命令要执行的 `WORKDIR` 仍可能显示 `CACHED`，判断构建是否真的重做要看产生文件系统的步骤和最终镜像 ID。

`docker run` 之后 `curl /healthz` 返回 `ok`。shorty 在没有设置 `SHORTY_DB_URL` 时使用内存存储，所以这个容器不需要 PostgreSQL 或 Redis；`/healthz` 只表示进程活着，不检查依赖。容器监听 8080，发布到宿主机 127.0.0.1:18080。

单阶段镜像能用，但它把编译器、Go 模块缓存和源码都留在了最终镜像里。9.4 会看到它有多大。

## 9.2 构建上下文与 .dockerignore

`docker build` 的最后一个参数不是 Dockerfile 的路径，而是构建上下文（build context）。上下文是 builder 在构建时能访问的文件集合，`COPY` 和 `ADD` 只能从这个集合里取文件。Dockerfile 本身可以用 `-f` 指定到上下文之外：9.1 的命令是 `-f first.Dockerfile`，上下文却是 `../app/api`，所以 Dockerfile 在 `src/code/ch09/`，源码从 `src/code/app/api/` 读。

这条规则解释了常见的困惑：“Dockerfile 明明写了 `COPY config.yaml .`，为什么说找不到？”因为 `config.yaml` 不在上下文目录里，或者被 `.dockerignore` 排除了。上下文之外的路径，包括 `../` 和绝对路径，`COPY` 都不能引用。

上下文不一定是本地目录：也可以传 Git 仓库 URL、tar 包，或者把 Dockerfile 从标准输入喂进去。远程 Git 上下文由 builder 克隆，子模块会一起带上；本地 tar 包则把包内路径当作上下文根。无论哪种形式，`COPY` 的源路径都相对于上下文根，而不是相对于 Dockerfile 所在目录。

上下文是递归打包的。指定一个本地目录，所有子目录都会包含进来；上下文越大，客户端要扫描、计算校验和、传给 builder 的数据就越多。使用远程 builder 时这部分走网络，差距更明显。`.dockerignore` 放在上下文根目录，语法接近 `.gitignore`：每行一个模式，`#` 开头是注释，`**` 匹配任意多层目录，`!` 表示例外且后面的规则覆盖前面的。Dockerfile 和 `.dockerignore` 本身即使被排除也仍会发给 builder，但不能被 `COPY` 进镜像。

这里有个容易误读的细节：BuildKit 会跳过没有被任何指令引用的文件。如果把 Dockerfile 改成只 `COPY app.txt /app.txt`，即使上下文里有 22 MB 无关文件，`transferring context` 也可能只有几十字节。BuildKit 只传它需要的文件，这是它相对旧构建器的改进之一。所以“上下文大小”和“本次传输大小”不是一回事：前者是潜在上限，后者取决于指令引用了什么。也正因为如此，`COPY . .` 会把整个未被忽略的目录纳入缓存键，影响最大。

如果同一目录里有多个 Dockerfile，可以给每个 Dockerfile 配一个专用 ignore 文件：把文件放在 Dockerfile 旁边，命名为 `<Dockerfile 名>.dockerignore`，它的优先级高于上下文根目录的 `.dockerignore`。`!` 例外规则按行序决定结果，最后一条匹配的规则生效；写 `*.md` 再写 `!README.md`，就只保留根目录的 README。

`.dockerignore` 里写什么，取决于项目。Go 项目通常排除 `.git`、编辑器目录、测试数据、本地二进制；Node 项目排除 `node_modules`；Python 项目排除 `__pycache__`、`.venv`。不要把 `go.sum`、`package-lock.json` 这类锁文件排除掉，构建需要它们来保证依赖版本一致；9.7 的第一个故障就是排错了文件。

上下文控制在 MB 级还有一个缓存上的好处：`COPY` 和 `ADD` 的缓存校验和会看文件内容与元数据，文件越多，任何无关文件变化都可能让 `COPY . .` 失效。把测试数据、日志、构建产物排除掉，缓存命中率会更稳定。

## 9.3 层与缓存失效

镜像由层组成。`RUN`、`COPY`、`ADD` 会改动文件系统，产生新的层；`ENV`、`EXPOSE`、`USER`、`CMD`、`ENTRYPOINT`、`STOPSIGNAL` 这类指令主要改镜像配置，不产生有实际文件内容的层。`WORKDIR` 会创建目录，算文件系统改动。这个区分在 `docker history` 里能看出来：配置指令的记录大小是 0B，真正的文件改动才有大小。

> **旧资料提示**：旧教程常说“每条指令一层”。更准确的说法是：`RUN`、`COPY`、`ADD`、`WORKDIR` 这类会改动文件系统的指令才产生有内容的层；`ENV`、`EXPOSE`、`USER` 主要改镜像配置，`docker history` 里能看到 0B 的记录，但没有对应的文件系统层（依据 `docker:manuals/build/cache/invalidation.md` 和 9.6 的 `docker history` 输出）。

BuildKit 为每条指令算一个缓存键。规则可以概括成四条：

- 基础镜像先参与比较，然后按 Dockerfile 顺序逐条比较指令和缓存里的记录。
- `RUN` 的缓存键主要来自命令字符串。命令没变，BuildKit 就复用结果，不会进容器里看文件是不是过期了；所以 `apt-get update` 单独一条 `RUN` 时，后面的 `apt-get install` 改了包列表也可能复用旧的索引。
- `COPY`、`ADD` 以及 `RUN --mount=type=bind` 会额外计算文件校验和。文件内容或元数据变了就失效，但文件的 mtime 不参与计算；只 `touch` 一下不会让缓存失效。
- 一旦某条指令失效，它后面的所有指令都不再使用缓存。

缓存是构建器的本地状态，不是镜像的一部分。删掉镜像不会清掉缓存，`docker builder prune` 才会；反过来，换一台机器或换一个 builder，缓存就不在。知道缓存在哪里，才能判断一次“突然变慢”是缓存丢了，还是指令顺序真的变了。

所以“把变化少的放前面”不是风格建议，而是缓存模型直接推出来的结论。依赖清单变化少，源码变化多，就先复制清单、下载依赖，再复制源码、编译。

CI 里的 builder 往往是临时的，本地缓存带不过去，这时用 `--cache-to` 把缓存导出到 registry、下一次用 `--cache-from` 拉回来，比每次从零下载依赖快得多。代价是缓存镜像本身要存储和传输，而且缓存键仍然要匹配；换了依赖版本或基础镜像，导入的缓存也救不了。

`--no-cache` 和 `--cache-from` 经常一起被提到，但作用相反：`--no-cache` 让本次构建不使用本地缓存，所有步骤重新执行；`--cache-from` 是从外部（例如 registry 里的缓存镜像）导入缓存，让另一台机器或 CI 上的构建也能命中。`--cache-from` 不会强制重建，`--no-cache` 也不会去拉新的基础镜像；要更新基础镜像用 `--pull`。三者可以组合，但目的不同。

单阶段镜像把构建工具也带进了运行环境。多阶段构建在同一个 Dockerfile 里写多个 `FROM`，每个 `FROM` 开始一个新阶段；只有最后阶段的文件系统进入最终镜像，前面阶段的产物用 `COPY --from` 取出来。

`FROM golang:1.27.3-trixie AS build` 给第一阶段起名 `build`。名字比数字 `0` 稳定：以后在前面插入阶段，`COPY --from=build` 不用改。`FROM scratch` 是空根文件系统，不包含 shell、libc、包管理器，也不包含 `/etc/passwd`。

`COPY --from=build /out/shorty /shorty` 只取编译产物。`COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/ca-certificates.crt` 取 CA 证书：scratch 里没有根证书，shorty 如果要访问 HTTPS 目标，没有这份文件就会报证书错误。基础镜像文档把 CA 证书列为程序常见的运行时依赖之一，这不是可选的装饰。

`USER 65532:65532` 用数字 UID/GID，不依赖 `/etc/passwd` 里的用户名。scratch 里没有用户数据库，写名字反而会让运行时找不到用户；数字 UID 在 Kubernetes 的 `runAsNonRoot` 和 Pod Security Standards 下也更好检查。`ENTRYPOINT` 和 `CMD` 与单阶段版本一致。

`docker image ls` 的两行是关键。`shorty:dev` 的 `DISK USAGE` 约 1.7GB，`CONTENT SIZE` 约 399MB；`shorty:scratch` 分别是 28.4MB 和 9.42MB。`DISK USAGE` 是解压后占用的磁盘，`CONTENT SIZE` 是压缩后的内容大小；两者都不是“镜像里所有文件加起来”的精确值，但量级足够说明问题：从数百 MB 降到数十 MB。

`docker run --rm shorty:scratch version` 输出 `shorty dev`，说明静态二进制在没有 libc 的 scratch 里能跑。`--entrypoint sh` 则直接失败：`exec: "sh": executable file not found in $PATH`。这不是镜像坏了，而是 scratch 里本来就没有 shell；生产环境想保留一点调试能力，可以换成 distroless 的 static nonroot，或者单独做一个 debug 阶段，而不是把 shell 塞回运行镜像。

scratch 的代价是调试困难：没有 shell、没有 `ls`、没有包管理器，进容器只能靠应用自己的日志和二进制。生产上常见的折中是 distroless 的 static nonroot 变体：它把 shell 和包管理器去掉，同时保留运行所需的用户和证书；本 lab 不依赖 gcr.io，示例统一用 scratch。

`COPY --from` 也可以直接从外部镜像取文件，例如 `COPY --from=nginx:1.29-alpine /etc/nginx/nginx.conf /nginx.conf`；这时不要求那个镜像先出现在本地，builder 会去仓库拉。它和 `COPY --from=build` 的区别只是来源：前者是镜像，后者是本文件里的阶段。

`--target` 可以只构建到某个阶段。`docker build --target build -f multi.Dockerfile -t shorty:build ../app/api` 会停在 `build` 阶段，得到一个带 Go 工具链的镜像，适合调试编译问题。BuildKit 只构建目标阶段依赖的阶段；同一个 Dockerfile 里与目标无关的阶段会被跳过，这一点比旧构建器更省时间。多阶段不是高级技巧，Go、Java、Node 的生产镜像基本都这么写。把构建阶段和运行阶段分开，也让缓存边界更清楚：依赖和编译都在 build 阶段，运行阶段只负责装产物。

`ARG BUILD_ONLY=from-arg` 和 `ENV PERSISTED=from-env` 的差别在 `Config.Env` 里：只有 `PERSISTED` 出现。`EXPOSE 8080` 只是在镜像配置里声明端口，`docker image inspect` 显示 `{"8080/tcp":{}}`；它不会发布端口，`docker run -P` 才会根据它做随机映射。`VOLUME /data` 让运行时为这个路径创建一个匿名卷，`docker inspect` 的 `Mounts` 里能看到 `volume /data` 和一个随机卷名；删容器时加 `-v` 才会把匿名卷一起删掉。

匿名卷的生命周期和容器是分开的：`docker rm` 不带 `-v` 时，卷会留下来，下次用 `--volumes-from` 或手工挂载还能读到旧数据；这也意味着反复创建带 `VOLUME` 的容器会积累匿名卷，清理时要显式处理。示例里用 `docker rm -fv` 把容器和卷一起删掉，避免 lab 里留下垃圾。

`USER` 之后的指令都以这个用户执行，前面的 `RUN id` 已经验证过。`STOPSIGNAL SIGQUIT` 写进镜像配置，`docker stop` 会把它作为停止信号发给 PID 1；如果 PID 1 是 shell 而不是应用，信号可能停在 shell 这一层，这就是前面强调 exec 形式的原因。

`HEALTHCHECK --interval=5s --timeout=2s --retries=2 --start-period=3s CMD wget ...` 的四个参数分别控制检查间隔、单次超时、连续失败几次算不健康、启动后多久开始计入失败。`docker image inspect` 把它们显示成纳秒：`5000000000` 就是 5 秒。省略参数时由引擎默认值兜底；需要精确控制启动慢的服务时，把 `--start-period` 写出来，别依赖默认值。`CMD` 形式是 exec（直接执行），`CMD-SHELL` 是 shell 形式；上例用 shell 是为了让 `|| exit 1` 生效。

`ADD payload.tar.gz /opt/` 会自动把本地 tar 解开，`/opt` 里只有 `hello.txt`，没有 `payload.tar.gz`。`ADD` 还支持从 HTTPS 和 Git URL 取文件，这些隐式行为让缓存键和结果不如 `COPY` 直观；不需要自动解压或远程抓取时，用 `COPY`。

`docker history` 里非顶层记录的 `IMAGE` 列显示 `<missing>`，这是 containerd 镜像存储下的正常现象，不是镜像损坏；要追某条指令，用 `--no-trunc` 看完整的 `CREATED BY`。

## 9.6 BuildKit 输出、构建检查与可复现

BuildKit 的输出和旧构建器长得不一样。旧版会打印 `Sending build context to Docker daemon`、`Step 1/6`、`Removing intermediate container`；BuildKit 用 `#N` 标识步骤，用 `CACHED` 表示命中，不再创建中间容器，所以也没有“删除中间容器”这一步。`docker build --progress=plain` 会保留每个步骤的完整日志，包括 `RUN` 里的命令输出；默认的 `auto` 进度在终端里更紧凑，但会把并行的步骤折叠起来。

一次构建的输出大致可以分成四段：`#1 [internal] load build definition` 读 Dockerfile，`#N [internal] load .dockerignore` 和 `#N [internal] load build context` 处理上下文，中间的 `[n/m]` 是 Dockerfile 指令，最后的 `exporting to image` 把结果写回镜像库。`#1 [internal]` 这种带 `internal` 的步骤不是 Dockerfile 里的指令，是构建器自己的准备工作；看到它们不用慌。

> **旧资料提示**：旧构建器的输出是 `Sending build context to Docker daemon`、`Step 1/6`、`Removing intermediate container`；BuildKit 改成 `#N` 步骤和 `CACHED`，并且不再创建中间容器，所以也没有“删除中间容器”这一行（依据 `docker:manuals/build/buildkit/_index.md` 和本章的构建输出）。

输出报了三条：两条 `SecretsUsedInArgOrEnv`（`ENV TOKEN` 和 `ARG PASSWORD`），一条 `MaintainerDeprecated`。`MAINTAINER` 从 Docker 1.13 起就被弃用，改用 `LABEL`；检查器会直接指出行号。`--check` 在有违规时以非 0 退出，适合放进 CI 作为门禁。

> **旧资料提示**：`MAINTAINER` 从 Docker 1.13 起被弃用，改用 `LABEL` 记录维护者信息；`--check` 会直接把这条标成 `MaintainerDeprecated`（依据 `docker:manuals/engine/release-notes/prior-releases.md` 的 1.13.0 弃用项）。

但这份输出也暴露了检查器的边界：`FROM ubuntu:latest` 和 `RUN apt-get update && apt-get install -y curl` 没有被报。也就是说，本章这个 buildx 版本的检查规则不会替你强制“基础镜像不要用 latest”，也不会强制“apt 缓存在同一条 `RUN` 里清掉”。这两件事仍然要写进评审清单，不能因为 `--check` 通过就认为没问题。检查规则会随 Dockerfile 前端版本变化，升级 buildx 后要重新看一遍它到底报什么。检查器是提醒，不是安全审计的替代品；它没报，不等于镜像里没有 secret。

普通构建也会在结束时显示检查结果，不需要额外加 `--check`。9.5 的构建末尾就有两条 `SecretsUsedInArgOrEnv`，那是构建时自动跑的检查，不影响构建成功；`--check` 的区别是只检查、不构建，并且把违规当成失败。

可复现要处理两个“可变”来源：Dockerfile 语法和基础镜像。`# syntax=docker/dockerfile:1` 锁定前端的主版本，避免不同机器用不同解析器；要完全固定可以写 `docker/dockerfile:1.8@sha256:...`，但大多数团队用 `:1` 就够了，因为它只接收 1.x 的兼容更新。基础镜像用 `name:tag@sha256:...` 固定内容；标签负责可读性，digest 负责可复现。只写 digest 不方便看版本，只写标签又可能悄悄换内容，两者一起写最稳。

另一条可复现的线索是时间戳。`SOURCE_DATE_EPOCH` 会影响构建中创建文件的 mtime，也会参与 `WORKDIR` 的缓存判断；把它固定成提交时间或 0，可以让同一份输入产出同样的元数据，但每次提交都改这个值会让缓存频繁失效。可复现和缓存命中需要一起权衡，不能只追求其中一个。

`--pull` 和 `--no-cache` 也常被混为一谈。`--pull` 让构建去仓库检查基础镜像有没有更新；`--no-cache` 只禁用本地构建缓存，不会拉新基础镜像。要“基础镜像最新、所有步骤重跑”，两个都加。

## 9.7 排障：COPY 找不到文件与缓存不失效

第一个故障：`.dockerignore` 把 `go.sum` 排除了。文件明明在目录里，`COPY go.mod go.sum ./` 却失败。

```console
{{#include code/ch09/9_8_troubleshoot_copy.out}}
```

`ls -l` 显示 `/tmp/shorty-copyfail/go.sum` 存在，大小 3383 字节。构建时 `[3/6] COPY go.mod go.sum ./` 报 `failed to calculate checksum ... "/go.sum": not found`，最后的错误是 `failed to compute cache key`。BuildKit 在算 `COPY` 的缓存键时才发现文件不在上下文里，所以错误消息不是“文件不存在”，而是“算校验和失败”。同一段输出里还有一条 `CopyIgnoredFile` 检查警告，明确指出 `go.sum` 被 `.dockerignore` 排除在第 6 行。

旧教程里的错误文本通常是 `COPY failed: file not found in build context or excluded by .dockerignore`，那是旧构建器的说法；BuildKit 下看到的是上面这种校验和错误。定位方法不变：`--progress=plain` 找到失败的那条 `COPY`，`ls` 确认文件在上下文目录，再看 `.dockerignore`。这次还可以更早发现：`docker build --check` 会在构建前报 `CopyIgnoredFile`。修法是删掉 `.dockerignore` 里的 `go.sum` 一行，重新构建成功。

第二个故障更隐蔽：改了源码，构建却全部 `CACHED`，镜像里的程序还是旧版本。

```console
{{#include code/ch09/9_9_troubleshoot_cache.out}}
```

这个例子里，`settings.go` 被 `.dockerignore` 排除，`COPY . .` 的校验和不包含它。第一次构建输出 `base`；把 `settings.go` 里的 `v1` 改成 `v2` 后再构建，`[3/4] COPY . .` 和 `[4/4] RUN go build` 都是 `CACHED`，运行仍然输出 `base`。这不是缓存“没更新”，而是构建的输入确实没变：被排除的文件从来不在 `COPY` 的输入集合里。

`--no-cache` 验证了这一点：所有步骤重新执行，镜像仍然输出 `base`，因为 `settings.go` 还是没被复制进去。`--no-cache` 只能绕过缓存，不能改变 `.dockerignore`。把 `.dockerignore` 清空后再构建，`COPY . .` 和 `go build` 重新执行，输出才变成 `v2`。

排障顺序可以固定成三步：先用 `docker build --progress=plain` 找到失败或命中的步骤，再用 `ls` 和 `.dockerignore` 确认这一步的输入到底有哪些文件，最后才用 `--no-cache` 区分“缓存问题”和“输入问题”。顺序反过来，容易在缓存上折腾半天，最后发现是文件根本没进上下文。

`.dockerignore` 应该和 Dockerfile 一起进代码评审。它决定了构建的输入边界，改一行就可能让某个文件从缓存键里消失，或者让 `COPY` 直接失败；把它当成构建配置的一部分，而不是随手加的忽略列表。

这两个故障的共同点是：`COPY` 的输入不是“目录里有什么”，而是“上下文里有什么，且没有被 `.dockerignore` 排除”。排障时先确认这一点，再怀疑缓存。`docker build --check` 能提前抓出 `CopyIgnoredFile`，`--progress=plain` 能让你看到失败或命中的具体步骤，`--no-cache` 只能用来区分“缓存问题”和“输入问题”，不能拿来当修复。

## 上生产前

- 基础镜像固定标签加 digest，升级时改 digest 而不是让同名标签漂移；同时保留标签，方便人读。定期用 `--pull` 重建，别把“固定”做成“永不更新”，安全补丁还是要进来。
- 构建参数不要传 secret。`ARG` 不在容器的 `Config.Env` 里，但会出现在 `docker history` 和构建缓存里；`ENV` 更是直接写进镜像配置。需要凭据时用 `--mount=type=secret`，并让 `--check` 的 `SecretsUsedInArgOrEnv` 作为兜底提醒。
- 依赖清单先 `COPY`、源码后 `COPY`，把 `RUN` 依赖安装放在两者之间；`.dockerignore` 排除 `.git`、测试数据、依赖目录和构建产物。构建上下文控制在 MB 级，`COPY . .` 的缓存键才不会被无关文件拖累。
- 最终镜像用多阶段加 `scratch` 或 distroless，只留二进制、CA 证书和必要的配置；运行用户用数字 UID，别把编译器和包管理器带进生产镜像。镜像大小和漏洞数量都会因此下降。
- CI 里固定跑 `docker build --check`，并把 `CACHED` 行数、构建时长和镜像大小作为指标。临时 builder 上加 `--cache-from`/`--cache-to` 复用缓存；`--no-cache` 只用于验证，不要放进日常流水线。

| 指令 | 作用 | 备注 |
|---|---|---|
| `FROM` | 设置基础镜像，开始一个新阶段 | 生产写 `tag@sha256:...` |
| `ARG` | 构建期变量 | 不进入 `Config.Env`，但会进 `history` 和缓存 |
| `ENV` | 镜像环境变量 | 进入镜像配置，容器运行时可见 |
| `WORKDIR` | 设置后续指令和容器的工作目录 | 用绝对路径，目录不存在会创建 |
| `COPY` | 从上下文或前一阶段复制文件 | `COPY --from=<stage>` 取产物 |
| `ADD` | 类似 `COPY`，额外支持自动解压本地 tar、HTTPS/Git URL | 隐式行为多，优先用 `COPY` |
| `RUN` | 在构建容器里执行命令，产生新层 | 依赖安装和清理放同一条 |
| `CMD` | 默认命令或默认参数 | exec 形式是 JSON 数组 |
| `ENTRYPOINT` | 固定入口 | 与 `CMD` 组合，exec 形式让应用成为 PID 1 |
| `USER` | 之后指令和容器进程的用户 | 生产用数字 UID |
| `EXPOSE` | 声明端口 | 只写配置，不发布端口 |
| `VOLUME` | 声明匿名卷挂载点 | 运行时自动创建匿名卷 |
| `HEALTHCHECK` | 容器健康检查 | `--interval`/`--timeout`/`--retries`/`--start-period` |
| `STOPSIGNAL` | `docker stop` 发送的信号 | 由 PID 1 处理，注意 shell 形式 |

| 命令或写法 | 作用 | 备注 |
|---|---|---|
| `docker build -f <文件> <上下文>` | 指定 Dockerfile，上下文按最后一个参数算 | Dockerfile 可以在上下文外 |
| `docker build -t <名字:标签> .` | 构建并打标签 | 不写标签会得到 `latest` |
| `docker build --target <阶段>` | 只构建到指定阶段 | BuildKit 跳过无关阶段 |
| `docker build --progress=plain` | 显示完整步骤日志 | 排障时优先用 |
| `docker build --no-cache` | 本次不使用本地缓存 | 不会拉新基础镜像 |
| `docker build --cache-from` | 导入外部缓存 | 常与 `--cache-to` 配对 |
| `docker build --check` | 只做静态检查 | 有违规时非 0 退出 |
| `docker build --pull` | 检查并拉取新的基础镜像 | 和 `--no-cache` 不同 |
| `.dockerignore` 的 `**`、`!` | 多层匹配、例外规则 | 后面的规则覆盖前面的 |
