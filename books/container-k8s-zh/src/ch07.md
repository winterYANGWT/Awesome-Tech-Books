# 第 7 章 资源限制与 cgroup v2：CPU、内存、OOM

第 6 章结束时，`shorty-api`、`shorty-pg`、`shorty-redis` 三个容器在 `shorty-net` 上互相用服务名访问，api 发布在 8080。它们能跑通，但没有任何资源上限：api 可以吃掉宿主机所有 CPU，也可以一直申请内存，直到把整台机器拖垮。这一章给它们加上限制，并且把“限制真的生效了”这件事变成可读的文件和数字。

先看两个具体问题。第一个，给 api 加 `--memory 128m` 之后，容器可能在某次请求后直接消失，`docker ps -a` 只留下 `Exited (137)`。137 是 128 加 9，表示进程收到 `SIGKILL`；但 `SIGKILL` 不等于 OOM，也可能是有人执行了 `docker kill`，或者宿主内存耗尽时内核挑了它。要区分这几种情况，得看 `OOMKilled` 和 `memory.events`。第二个，`--cpus 0.5` 和 `--cpu-shares 512` 看起来都在“限制 CPU”，实际完全不是一回事：前者是 CFS 配额，直接把容器每 100 ms 能用的 CPU 时间切掉一半；后者只是争抢时的相对权重，空闲时容器照样能跑满一个核。

这一章按“参数落到哪个文件 → 内存怎么被杀 → CPU 怎么被限 → 怎么观测 → Kubernetes 怎么表达 → 怎么用故障开关复现”走。所有结论都落在 cgroup v2 的文件和 `docker stats` 的输出上，最后用两个真实故障把“被限流”和“被 OOM kill”分开。

> **起点**：第 6 章结束。lab 里有 `shorty:dev`、`shorty:0.1`，`shorty-api`、`shorty-pg`、`shorty-redis` 三个容器在 `shorty-net` 上，api 未设资源限制，PostgreSQL 里已有一条链接。`bash code/ch07/setup.sh` 会重建这三个容器、执行一次 migrate，并写入一条测试链接。

## 7.1 cgroup v2 下 Docker 参数落到哪

cgroup（control group，控制组）是内核用来分组记账和限制资源的机制。cgroup v1 把 memory、cpu、pids 等控制器分别挂在不同的层级下；cgroup v2 改成单一层级，所有控制器都挂在 `/sys/fs/cgroup` 这一棵树下。判断当前系统用哪一版，看 `/sys/fs/cgroup/cgroup.controllers` 是否存在：存在就是 v2，不存在才按 v1 找。Kubernetes 从 1.25 起把 cgroup v2 标为 stable；1.35 起 cgroup v1 被弃用，kubelet 默认不再在 v1 节点上启动，除非把 `failCgroupV1` 设成 false。Docker 从 20.10 起支持 cgroup v2，要求 containerd 1.4 以上、runc 1.0.0-rc91 以上、内核 4.15 以上（推荐 5.2 以上）。

`docker info` 会把这两件事分开报：`Cgroup Version` 是 2，`Cgroup Driver` 是 `cgroupfs` 或 `systemd`。版本决定文件长什么样，driver 决定目录放在哪；两者都不是 Docker 自己的抽象，而是它交给内核和 init 系统的结果。本 lab 是 dind，dockerd 在容器里跑，driver 是 `cgroupfs`；发行版上由 systemd 启动的 Docker 默认用 `systemd`，所以同一个 `--memory` 在两台机器上的 cgroup 路径可能完全不同。

Docker 参数不直接写内核文件，而是写进容器的 cgroup 目录。要找这个目录，最可靠的办法不是猜路径，而是从容器的主进程出发：`docker inspect .State.Pid` 拿到 PID，再读 `/proc/<pid>/cgroup`。cgroup v2 的输出只有一行，格式是 `0::/路径`。这个路径相对于 `/sys/fs/cgroup`，把它拼上去就是容器的 cgroup 目录。不同 cgroup driver 的路径不一样：cgroupfs 驱动通常是 `/docker/<完整 ID>`，systemd 驱动则是 `/system.slice/docker-<完整 ID>.scope`。所以排障时先读 `/proc`，不要照着教程里的固定路径找。

探针容器的 `HostConfig` 一行把 Docker 侧的值列出来：`Memory=67108864`、`MemorySwap=67108864`、`NanoCpus=500000000`、`CpuShares=512`、`CpusetCpus=0`、`PidsLimit=64`。这些是 Docker 保存的配置，不是内核实际生效的值；真正生效的要看下一组文件。`memory.max` 等于 64 MiB，`cpu.max` 是 `50000 100000`，`cpu.weight` 是 59，`cpuset.cpus` 是 0，`pids.max` 是 64。两边能对上，但单位不同：Docker 用字节和纳 CPU，cgroup 用字节、微秒和权重。

`--memory` 写的是 `memory.max`，这是硬上限，不是预留。Docker 还有 `--memory-reservation`，它是软限制，只在 Docker 检测到宿主内存紧张或争抢时才生效，而且必须设得比 `--memory` 小；软限制不保证容器不超过它，所以不能用它来代替硬上限。`memory.max` 的单位是字节，`cpu.max` 的两个数字单位是微秒，`cpu.weight` 是相对权重，`pids.max` 是进程/线程数；这些单位不统一，读文件时不要拿 Docker 的 `Memory`、`NanoCpus` 直接和文件名对。`--memory-swap` 的规则要分情况看，不能一句话概括：如果设成正整数，它表示“内存加 swap 的总量”，比如 `--memory 300m --memory-swap 1g` 允许 300 MB 内存加 700 MB swap；如果设成 0，等于没设；如果设成和 `--memory` 相同的值，容器不能用 swap；如果不设，而 `--memory` 设了，容器最多可以用和内存一样多的 swap，前提是宿主机配置了 swap；如果显式设成 `-1`，则 swap 不设上限。例子里的 `shorty-swap` 只设了 `--memory 64m`，Docker 就把 `MemorySwap` 记成 128 MiB，内核的 `memory.swap.max` 是 64 MiB，也就是“内存 64m + 最多 64m swap”。探针容器把两者设成相同值，`memory.swap.max` 就是 0。这里要注意宿主机：本 lab 的父 cgroup 关了 swap，所以即使 `memory.swap.max` 是 64 MiB，也换不出去；在有 swap 的宿主机上，同样的配置会先换页，表现为变慢，而不是立刻收到 137。

`--cpus 0.5` 落到 `cpu.max` 的 `50000 100000`：每 100 ms 最多用 50 ms CPU 时间。CFS 周期的默认值是 100000 微秒，Docker 文档建议大多数场景直接用 `--cpus`，只有在需要精确控制周期和配额时才拆成 `--cpu-period` 和 `--cpu-quota`；周期不是越小越好，太小会让线程频繁被切断，反而增加调度开销。它也可以拆成 `--cpu-period=100000 --cpu-quota=50000`，官方文档说 `--cpus` 是这两个参数的等价写法。`--cpu-shares 512` 落到 `cpu.weight`，在这台机器上是 59；默认的 1024 对应 100。59 不是 50，也不表示“半个 CPU”，它只是权重标度上的一个相对值。权重只在多个 cgroup 争抢同一个 CPU 时按比例分配，空闲时不封顶。`--cpuset-cpus 0` 落到 `cpuset.cpus`，把容器绑到 0 号 CPU；`--pids-limit 64` 落到 `pids.max`，限制的是这个 cgroup 里的进程和线程总数。`--pids-limit` 的 Docker 默认值是 0，表示不限制，设成 -1 也是不限制。

`memory.max` 里的 `max` 不是“零”或“无限大”的数值，而是 cgroup v2 表示“不设上限”的字符串；`pids.max` 也一样。脚本里如果要判断有没有限制，不能把 `max` 当数字比较，要先判断字符串。`cpuset.cpus` 和 `cpuset.cpus.effective` 也要分开看：前者是配置值，可能为空（表示继承父级），后者是内核实际允许的 CPU 集合。

例子最后用 `docker update` 把运行中的 api 改成 `--memory 128m --memory-swap 128m --cpus 0.5`。`HostConfig` 随之变成 `Memory=134217728`、`MemorySwap=134217728`、`NanoCpus=500000000`，`memory.max` 是 134217728，`memory.swap.max` 是 0，`cpu.max` 是 `50000 100000`。这就是本章终点的 api。`docker update` 能改运行中容器的这些 cgroup 参数，不需要重建容器；但不是所有参数都能热改，改之前先看 `docker update --help`。

> **旧资料提示**：旧教程里的 `cpu.shares`、`memory.limit_in_bytes`、`cpu.cfs_quota_us` 是 cgroup v1 的文件名。cgroup v2 里对应的是 `cpu.weight`、`memory.max`、`cpu.max`，路径也从按控制器分目录变成了单一层级。看到教程让你 `cat /sys/fs/cgroup/memory/docker/...`，先确认节点到底是 v1 还是 v2。

## 7.2 内存上限与 OOM

`--memory` 是硬上限，意思是 cgroup 在记账时不允许这个组的匿名内存无限超过 `memory.max`。进程申请内存、触碰页面时，内核先尝试回收这个 cgroup 里的页缓存；回收不掉，就触发 cgroup 的 OOM killer，挑一个进程杀掉。被杀的是容器的主进程时，容器就退出；退出码是 137，因为进程收到 `SIGKILL`。`--memory` 不是预留，它不保证节点上一定留有这么多内存，也不阻止其他容器把节点吃满；它只保证这个容器不会超过这个数。

`OOMKilled=true` 是 Docker 给出的直接证据，但它不是唯一的 137 来源。Docker 还会调整 daemon 的 OOM 优先级，让 daemon 比普通容器更难被宿主 OOM 选中；容器自己的 OOM 优先级默认不调整，所以在宿主整体内存耗尽时，容器比 daemon 更容易被杀。`--oom-kill-disable` 看起来能“关掉 OOM”，但官方文档明确要求只在设了 `--memory` 时使用，否则宿主可能先被杀；而且在 cgroup v2 上这个标志会被 Docker 丢弃，不能把它当成保护手段。如果 `OOMKilled=false` 而退出码是 137，先查三件事：有没有人执行过 `docker kill`（默认发 `SIGKILL`）；宿主是不是整体内存耗尽，内核杀了这个进程；容器里是不是有进程自己发了 `SIGKILL`。`docker events` 能看到 kill 和 oom 事件，宿主侧可以看 `dmesg` 或内核日志。把 137 一律当成 OOM，会漏掉“发布脚本误杀容器”这种很常见的事故。

宿主 OOM 和 cgroup OOM 是两层。cgroup OOM 发生在容器自己的 `memory.max` 被突破时，`memory.events` 会记在容器或它的父 cgroup 上；宿主 OOM 发生在整台机器的内存耗尽时，内核从全局挑进程，容器只是候选之一，`OOMKilled` 不一定会被标成 true。容器里跑着数据库、构建任务这类大内存进程时，两层都要看：先看容器的 `memory.events`，再看宿主的 `dmesg` 和 `docker events`。

“短时间冲高也会被杀”是 cgroup 记账方式决定的：内核在分配和触碰页面时记账，不是每分钟取一次平均值。一个请求突然申请几百 MB，哪怕容器的平均内存只有几十 MB，也会在申请的那一刻触发回收和 OOM。反过来，如果超出的部分主要是可回收的页缓存，内核可能先回收，容器不一定马上死；这就是为什么看 `memory.peak` 和 `memory.events` 比看平均内存更有意义。例子里的 api 在 64 MiB 下第 8 次请求就被杀，不是因为“平均用了 64 MiB”，而是因为那一次分配把 cgroup 推过了 `memory.max`。

例子随后把 api 换回 128 MiB、0.5 CPU 重启。容器换了，数据没有丢：`links=1` 来自 PostgreSQL，`GET /r/<code>` 返回 302。这里要区分“容器可写层”和“数据库卷”：api 的 cgroup 和进程都没了，但链接在 `shorty-pg` 的卷里，重启 api 不会影响它。OOM 杀掉的是进程，不是数据卷。

> **旧资料提示**：有的旧资料说“容器 OOM 时 Docker 不检测、不处理”。现在 `docker inspect .State.OOMKilled` 会标记这次退出是否由 OOM 引起，重启策略（`--restart`）也会按容器的退出行为处理；Docker 还会调整 daemon 的 OOM 优先级，让容器比 daemon 更容易被选中。说“Docker 完全不管”是不准确的。

## 7.3 CPU：权重与配额

CPU 有两种完全不同的限制方式。配额（quota）是“每个周期最多用多少时间”，由 CFS 带宽控制实现，落到 `cpu.max` 的 quota 和 period；权重（shares/weight）是“争抢时按什么比例分”，落到 `cpu.weight`。配额是硬上限，权重是软优先级。把这两个混在一起，就会出现“我设了 512，为什么它还是跑满一个核”或者“我设了 0.5，为什么吞吐只有一半”的疑问。

`cpu.max` 是 `50000 100000`，即每 100 ms 最多 50 ms。CFS 的限流是“按周期结算”的：一个周期内用超了配额，这个 cgroup 会被压住，等到下一个周期再放行；所以 50% 的配额不等于“每个瞬间都只能用半个核”，而是长期平均最多半个核，短时间可以有突发，但会被周期边界切回来。`cpu.stat` 里 `nr_periods 2`、`nr_throttled 1`、`throttled_usec 47654`：两个周期里有一次被限流，累计被压住约 47.7 ms。`docker stats` 的 CPU% 是 50.18%，接近配额的一半。这里的 50% 是“一个 CPU 的 50%”，不是“整机 32 个 CPU 的 50%”；`docker stats` 的 CPU% 以单核为 100%，所以 50% 就是半个核。

权重那一组是 `--cpu-shares 512`。这里要区分“配额”和“权重”的观测方式：配额看 `cpu.max` 和 `nr_throttled`，权重看 `cpu.weight` 和争抢时的实际分配；`cpu.weight` 是配置值，不会因为容器忙不忙而变，`nr_throttled` 只在有配额时才会增长。它的 `cpu.max` 是 `max 100000`，`cpu.stat` 的 `nr_throttled` 和 `throttled_usec` 都是 0，`docker stats` 的 CPU% 是 100.43%。这不是说权重没生效，而是说这台机器有 32 个 CPU、没有别的容器和它抢同一个核，权重没有可分配的争抢对象。把两个同样绑在 0 号 CPU 上、权重分别是 512 和 1024 的容器同时跑满，它们会按大约 1:2 分这个核的时间；如果只跑一个，它仍然能用满这个核。`--cpu-shares` 的默认值是 1024，`--cpu-shares` 只影响相对比例，不保证也不预留具体 CPU。

`--cpuset-cpus` 是另一种约束：它不改配额，而是把容器允许运行的 CPU 集合缩小到指定核，落到 `cpuset.cpus`。7.1 的探针设了 `--cpuset-cpus 0`，`cpuset.cpus` 就是 0。绑核适合 NUMA、缓存局部性、实时任务这类场景；它不能替代配额，因为绑到一个核不等于限制只能用半个核。反过来，只设配额不绑核，容器可以在任意核上跑，只是总量受限。

`--cpuset-cpus` 和 `--cpus` 可以叠加：绑到 0 号核、再设 0.5 配额，容器就只能在 0 号核上用半个核的时间；如果只绑核不设配额，它可以跑满那个核。反过来说，设了配额不绑核，容器会在所有核之间迁移，缓存局部性差一些，但总量仍然受限。Kubernetes 里对应的字段是 `cpu` 的 request/limit，以及可选的 CPU 管理器静态策略；后者需要 kubelet 配置和 Guaranteed QoS，不是默认行为。

多线程应用要特别注意：`--cpus 0.5` 限制的是整个 cgroup 的总量，不是每个线程 0.5。一个开 8 个 worker 的进程在 0.5 CPU 的配额下，8 个线程一起争这 50 ms，吞吐不会因为线程多而翻倍，反而可能因为上下文切换和限流更差。调优时先看 `cpu.stat` 的 `nr_throttled`，再决定是加 CPU、减并发，还是把长任务拆出去；不要只看应用自己的线程数。

> **旧资料提示**：cgroup v1 的 `cpu.stat` 里常见 `throttled_time`，cgroup v2 的字段叫 `throttled_usec`，单位是微秒。旧脚本按 `throttled_time` grep 会得到空结果，不是没有限流，而是字段名变了。

`docker stats` 的 API 和 CLI 还有一个差别：CLI 会减掉缓存，API 返回的是总用量和缓存量，由客户端自己算。官方 stats 文档写得很明确：Linux 上 CLI 报告的 MEM USAGE 减掉了 cache，cgroup v1 用 `total_inactive_file`，cgroup v2 用 `inactive_file`；API 不做这个减法。所以用 `docker stats` 和用 `/containers/<id>/stats` 写监控，得到的数字可能不一样，比较之前先确认口径。

`docker stats` 这一行里，api 的 MEM USAGE / LIMIT 是 `6.938MiB / 128MiB`，PIDS 是 7；load 容器是 `9.148MiB / 14.3GiB`，因为它是普通容器，没有设内存上限，LIMIT 显示的是宿主内存。api 的 CPU% 只有 3.07%，load 的 CPU% 是 92.47%：这不是 api 的配额没生效，而是 `/healthz` 太便宜，瓶颈在“用 wget 生成请求”的这一侧，api 根本没忙起来。CPU limit 是上限，不是目标值；看到 3.07% 只能说明“没到上限”，不能说明“限制没生效”。

`PIDS` 这一列也容易误读：它统计的是容器创建的进程和内核线程，不是 `ps` 里看到的“进程数”。Go 程序看起来只有一个进程，但运行时会有多个线程，PIDS 可能是 8；一个 shell 里 fork 出很多子进程，PIDS 会跟着涨。把 PIDS 当进程数做容量规划会偏小，把它当线程数看才接近。

内存要对齐两个口径。`memory.current` 是 cgroup 当前记账的内存，包含页缓存；`docker stats` 的 MEM USAGE 会减掉缓存：在 cgroup v1 上减 `total_inactive_file`，在 cgroup v2 上减 `inactive_file`。这次 `memory.current` 是 7,274,496 字节，`inactive_file` 是 8,192 字节，两者相减是 7,266,304 字节，约 6.93 MiB，和 stats 的 `6.938MiB` 基本一致；stats 的采样时刻和读文件不是同一瞬间，差几 KB 是正常的。`memory.stat` 里的 `anon 6586368`、`file 8192` 说明几乎全是匿名内存，页缓存只有 8 KB；`memory.peak` 是 11,399,168 字节，比当前值高，因为进程启动时曾经到过更高的水位。峰值是“自 cgroup 创建以来的最高记账值”，容器重启后重新开始，不会跨容器继承。

`memory.peak` 不是“重启前的峰值”的持久记录，它属于 cgroup，cgroup 被删掉就没了；容器重启会新建 cgroup，峰值从零开始。所以看“这个容器历史上最高到过多少”，要靠监控系统采集，不能指望退出后再读文件。`memory.current` 也会随着页缓存回收、Go GC 返回内存而下降，单次读数的参考价值有限，趋势和峰值更有用。

`cpu.stat` 这一组是 `usage_usec 173666`、`nr_periods 30`、`nr_throttled 0`、`throttled_usec 0`。api 有 0.5 CPU 的配额，但这次负载只用了约 0.17 秒 CPU，没有触发限流；`nr_periods` 是经过的 CFS 周期数，`nr_throttled` 是被限流的周期数。`cgroup.events` 的 `populated 1` 表示这个 cgroup 里还有进程，`frozen 0` 表示没有被 freezer 冻结；容器退出后目录会被删掉，这两个值也就没了。

`docker inspect` 把运行状态和配置分开：`.State` 是运行状态，`Status=running`、`OOMKilled=false`；`.HostConfig` 是启动配置，`Memory=134217728`、`MemorySwap=134217728`、`NanoCpus=500000000`。排障时不要拿 `.HostConfig.Memory` 当“当前用了多少”，它只是上限；当前用量在 `memory.current` 或 `docker stats` 里。

Docker daemon 自己也能暴露 Prometheus 指标。做法是在 `/etc/docker/daemon.json` 里写 `metrics-addr`，然后重启 dockerd：

```json
{
  "metrics-addr": "127.0.0.1:9323"
}
```

重启后 `curl http://127.0.0.1:9323/metrics` 就能看到 `engine_daemon_*` 指标。Docker 官方文档提醒这些指标名还在变化，只能监控 Docker 自身，不能替代应用的 `/metrics`。本 lab 的 dockerd 是 dind 容器里的进程，直接重启它会把 lab 一起停掉，所以例子用同一个二进制在另一个 socket 上起了一个临时 daemon，只验证 `metrics-addr` 和输出格式；生产上把配置写进 `daemon.json` 再重启 `docker` 服务即可。输出里的 `engine_daemon_engine_info` 带版本、内核、存储驱动，`engine_daemon_container_states_containers{state="running"}` 是 daemon 看到的容器状态计数；`daemon_id` 每次启动都不同，不要拿它做固定断言。

## 7.5 Kubernetes 侧：requests、limits 与 QoS

Kubernetes 把资源拆成 requests 和 limits 两个字段。requests 是调度依据：kube-scheduler 把 Pod 放到节点上时，保证节点上所有已调度 Pod 的 requests 之和不超过节点可分配量；它也是资源保证的下限。limits 是运行时的上限：kubelet 把 limits 传给容器运行时，最终由 cgroup 执行。只写 limit 不写 request 时，准入会把 limit 复制成 request；所以“我只写了 limit”并不等于“没有 request”，这一点会影响 QoS 分类。

CPU 和 memory 的 limit 执行方式不同。CPU limit 由 CFS 配额实现，超过就 throttle，容器不会被杀；memory limit 由 cgroup 内存控制器实现，超过时先回收，回收不掉就 OOM kill。Kubernetes 文档说 memory limit 是“反应式”的：容器可能短暂超过 limit，但一旦内核检测到压力就可能被杀；实际是否立刻被杀，取决于超出的是可回收页缓存还是匿名内存。7.2 的 64 MiB 实验就是匿名内存超过 `memory.max` 后立刻触发 OOM 的例子。

调度器只看 requests，不看 limits。节点上所有 Pod 的 requests 之和不能超过节点的可分配资源，但 limits 之和可以超过，这就是 overcommit；超卖让集群利用率更高，也让节点在峰值时更容易出现争抢和 OOM。kubelet 会把 requests 作为下限尽量保证，把 limits 交给 cgroup 执行；CPU 的 request 还会影响 `cpu.weight`，内存在启用 Memory QoS 时才可能映射到 `memory.min`/`memory.low`，默认并不做这种保护。

QoS 是 Kubernetes 根据 requests 和 limits 给 Pod 分的类。Guaranteed 要求每个容器都有 CPU 和 memory 的 request 与 limit，且两者相等；Burstable 是“不满足 Guaranteed，但至少有一个容器设了 CPU 或 memory 的 request 或 limit”；BestEffort 是“所有容器都没有 CPU 和 memory 的 request 和 limit”。节点资源紧张时，kubelet 先驱逐 BestEffort，再 Burstable，最后 Guaranteed；因资源压力驱逐时，只有超过 request 的 Pod 才是候选。QoS 在 Pod 创建时确定，运行期间不会因为改资源而自动换类；会改变 QoS 的原地调整会被准入拒绝。

QoS 的判定规则是逐容器的：Guaranteed 要求“每个容器”的 CPU 和 memory 都同时有 request 和 limit 且相等；只要有一个容器缺一个字段，整个 Pod 就掉到 Burstable。BestEffort 要求所有容器都没有 CPU 和 memory 的 request/limit，其他资源（比如 `ephemeral-storage`）不影响这个分类。

QoS 不是“性能等级”，它主要影响驱逐顺序和调度时的资源核算。Guaranteed 的 Pod 也可能因为超过 limit 被 OOM kill，只是它最不容易因为节点压力被驱逐；BestEffort 的 Pod 可以用节点上没被 request 占掉的所有资源，但节点一紧张，它最先被挑中。不要把 limit 当保证：limit 只限制上限，不预留资源；要保证，靠的是 request 和 Guaranteed QoS，或者给节点留出足够的余量。

HPA 的利用率也以 request 为分母。官方文档写得很清楚：资源指标利用率是“当前使用量 / 容器的 resource request”，如果某个容器没有设置对应的 request，Pod 的 CPU 利用率就没有定义，HPA 不会根据这个指标做任何动作。HPA 算的是 Pod 内容器的总和，再除以 request 的总和；给应用加 sidecar 时，sidecar 也要有 request，否则 HPA 可能因为“有一个容器没 request”而不动作。所以 HPA 不生效时，先看 Pod 有没有 requests，而不是先怀疑 metrics-server；这部分在第 29 章展开。

## 7.6 用故障开关做可重复的压测

shorty 的故障开关既可以用环境变量在启动时设置，也可以用 `/admin/fault` 在运行时改。三个和资源相关的开关是：`SHORTY_FAULT_LATENCY_MS` 给每个请求加延迟，`SHORTY_FAULT_ERROR_RATE` 按比例返回 500，`SHORTY_FAULT_LEAK_MB` 每个请求分配并保留指定 MB 的内存。`/admin/fault` 本身不经过故障中间件，所以把 `error_rate` 设成 1 之后仍然能通过它关掉；这个设计是为了避免“打开故障后关不掉”。

泄漏那一组：`memory.current` 从 19,156,992 字节变成 20,205,568 字节，净增 1,048,576 字节，正好 1 MiB。这说明 `leak_mb=1` 分配的那一块确实被保留下来，而且在这段时间里没有被 GC 回收；换一个时刻，其他分配和回收可能让净值偏离 1 MiB，所以不要拿单次差值当精确计量，要看多次请求后的趋势和 `memory.peak`。重启 api 后 `/admin/fault` 回到全零：`{"latency_ms":0,"error_rate":0,"leak_mb":0,"not_ready":false,"crash_after":0,"ignore_sigterm":false}`；`links=1`，`GET /r/<code>` 还是 302，说明故障开关和 OOM 都没有碰数据库。

压测要可重复，关键不是“跑一次看看”，而是固定变量：固定客户端并发数、固定持续时间、固定请求路径和请求体，记录开始前的 `memory.current`/`cpu.stat` 和结束后的值；每次换参数只改一个变量。用 `/admin/fault` 的好处是同一个容器、同一份数据、同一个镜像，不用为了制造故障重建环境；坏处是忘了关，下一次测试会带着上一次的延迟或错误率。所以脚本结束时应该显式把开关归零，或者重启容器回到环境变量默认值。

做延迟对比时，至少记录三次并看中位数，不要拿一次 0.49 秒和一次 0.52 秒下结论；做吞吐对比时，先预热，再固定时长采样，报告成功请求数、失败数和 P95，而不是只报一个平均值。故障开关本身也会影响测量：`latency_ms` 加的是服务端 sleep，客户端看到的 `time_total` 会包含它；`error_rate` 打开后，失败请求也会占用连接和服务端处理时间。

## 上生产前

内存 limit 要按峰值留余量，不要按平均用量卡。`--memory` 是硬上限，超过时内核会 OOM kill；页缓存、临时对象、并发峰值都会让瞬时用量高于稳定值。先压测拿到 `memory.peak`，再在峰值上留出至少 20%–30% 的余量；如果应用有已知的批处理或大对象，单独估算。不要把 limit 当“保证”，保证要靠 Kubernetes 的 requests 和 Guaranteed QoS，或者给节点留出足够的空闲内存。

CPU limit 会导致 throttle，延迟敏感的服务要慎用低 limit。`--cpus 0.5` 的容器在流量上来时会被硬切到半个核，P99 延迟会明显变差；优先用 requests 保证调度，再靠足够的副本分摊负载。如果确实要设 CPU limit，先看 `cpu.stat` 的 `nr_throttled` 和 `throttled_usec`，确认限流发生在哪个时间段、影响了哪些请求；不要只看平均 CPU%。

设 `--pids-limit`/`pids.max` 防 fork bomb。一个失控的进程不断 fork，会把节点的 PID 表吃光，影响同一台机器上的所有容器；`pids.max` 到顶后 fork 失败，至少把故障限制在一个容器里。数值要按应用的线程数、子进程数和突发并发估算，设得太小会让正常请求也 fork 失败。`--memory-swap` 要显式规划：不设时 Docker 会按内存的两倍记总限额，宿主机有 swap 时容器就可能换页，表现为延迟抖动；不想让容器用 swap，就把 `--memory-swap` 设成和 `--memory` 相同。

监控要看 `OOMKilled`、`nr_throttled`、`memory.peak`，不要只看平均 CPU 和平均内存。平均内存会掩盖瞬时峰值，平均 CPU 会掩盖周期性限流；OOMKilled 是结果，`memory.events` 的 `oom_kill` 是过程，两个都要采集。Kubernetes 侧还要看 Pod 的 QoS、requests/limits 是否被准入改写、节点压力驱逐的 Event；HPA 的利用率以 requests 为分母，没有 requests 的 Pod 不会给出可用的 CPU 利用率。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `--memory` | 内存硬上限，落到 `memory.max` | 不设则无上限；最小值 6m |
| `--memory-swap` | 内存加 swap 的总量，落到 `memory.swap.max` | 不设时最多可用与内存等量的 swap；等于 `--memory` 时禁用 swap；0 视为未设；-1 不限制 |
| `--cpus` | CFS 配额，落到 `cpu.max` 的 quota/period | 不设则 `max 100000`；`--cpus 0.5` 等于 `50000 100000` |
| `--cpu-shares` | 相对权重，落到 `cpu.weight` | 默认 1024 对应 100；只在争抢时生效 |
| `--cpuset-cpus` | 允许运行的 CPU 集合，落到 `cpuset.cpus` | 从 0 开始编号，如 `0-3`、`1,3` |
| `--pids-limit` | 进程/线程数上限，落到 `pids.max` | 0 或 -1 表示不限制 |
| `memory.max` | cgroup 内存硬上限 | `max` 表示不限制 |
| `memory.current` | 当前记账内存，含页缓存 | 与 `docker stats` 的 MEM USAGE 口径不同 |
| `memory.peak` | 自 cgroup 创建以来的内存峰值 | 容器重启后重新开始 |
| `memory.events` | `oom`、`oom_kill`、`max` 等事件计数 | `memory.events.local` 只统计本层 |
| `cpu.max` | CFS 配额和周期 | 格式 `quota period`；`max` 表示不限额 |
| `cpu.weight` | CPU 相对权重 | 默认 100；对应 `--cpu-shares 1024` |
| `cpu.stat` | CPU 用量和限流统计 | 看 `nr_throttled`、`throttled_usec` |
| `cgroup.events` | cgroup 是否有进程、是否冻结 | `populated`、`frozen` |
| `docker stats --no-stream` | 一次采样看 CPU、内存、PIDs | MEM USAGE 会减掉 `inactive_file` |
| `resources.requests/limits` | Kubernetes 的调度依据和运行上限 | requests 是下限，limits 是上限 |
| `status.qosClass` | Pod 的 QoS 类 | Guaranteed、Burstable、BestEffort |
