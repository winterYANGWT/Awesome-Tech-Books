# 第 28 章 资源管理与调度：requests/limits、QoS、亲和、taint、优先级，以及 GPU 与 DRA（1.34 GA）

`kubectl -n shorty get pod -o wide` 里，api 的两个副本常常一起落在 `shorty-worker`，另一个 worker 空着；再给一个 requests 2Gi 内存的 Pod，它却一直 Pending，而 `kubectl describe node shorty-worker` 又显示还有 2 GB 内存。这两件事看起来矛盾，其实问的是两个不同的问题：调度器不看节点“实际还剩多少内存”，它看的是节点可分配量减去已调度 Pod 的 requests；而副本要不要打散，也不会因为节点空着就自动发生，除非工作负载里写了拓扑分布或反亲和。

把 Pod 放到节点上是一次带约束的匹配。requests 是调度器记账的货币，limits 是节点上 cgroup 的执行上限；nodeSelector、nodeAffinity、taint/toleration 决定“能不能去”，topologySpreadConstraints 和 podAntiAffinity 决定“去得均不均匀”，PriorityClass 决定“排队时谁先走、资源不够时谁被赶走”。这些机制各管一段，混在一起猜就会在 Pending、Evicted、OOMKilled 之间来回打转。

这一章还是从 shorty 的 api 出发：先看 requests/limits 和三种 QoS，再拆开调度器的过滤与打分，然后用亲和、污点、拓扑分布和优先级把副本放到该去的地方。接着看 Pod 级资源和原地调整，最后用概念和一个小实验解释 GPU 的 device plugin 与 DRA（Dynamic Resource Allocation，动态资源分配）。第 28.8 节把 Pending 的常见事件按排查顺序串起来。

> **起点**：本章从 `s3-stateful` 开始：3 节点 kind 集群（1 个控制面、2 个 worker），postgres 是 StatefulSet 加 PVC `data-postgres-0`，redis/worker 各 1 副本，api 2 副本，api 没有 resources/affinity。控制面节点带默认的 `NoSchedule` 污点，两个 worker 由 setup.sh 打上 `shorty.example.com/role=worker`。一步到位：`bash code/ch28/setup.sh`。

## 28.1 requests、limits 与 QoS

CPU 和内存是最常写的两种资源。CPU 的单位是核，`0.5` 和 `500m` 是同一个量；内存用字节，`64Mi` 是 64 MiB，注意 `M` 和 `Mi`、`m` 和 `Mi` 的区别：`400m` 内存是 0.4 字节，不是 400 MiB。`ephemeral-storage` 和 `hugepages-<size>` 也能写 requests/limits，前者算节点本地临时盘，后者只对 Linux 大页有意义。扩展资源（例如 `nvidia.com/gpu`）只能写整数，且 requests 和 limits 必须相等。

requests 参与调度，limits 是运行时上限。调度器给 Pod 选节点时，会把 Pod 里所有容器的 requests 按资源相加，再看节点的 `status.allocatable` 减掉已调度 Pod 的 requests 之后还够不够；它不看节点上此刻的实际用量。所以“节点还有 2 GB 空闲内存”并不等于“调度器认为还能放一个 requests 2 GiB 的 Pod”：如果已调度 Pod 的 requests 已经把可分配量占满，或者这个 Pod 的 requests 比任何单节点的可分配量都大，它就永远排不上去，哪怕机器几乎在空转。节点可分配量本身也小于硬件容量，kubelet 要给系统进程和 Kubernetes 组件留出 reserved。

limits 由 kubelet 通过容器运行时写进 cgroup，最终由内核执行。CPU 超 limit 会被 CFS 配额节流：在每一个周期里用完配额就停到下一个周期，容器不会因为超 CPU 被杀。内存超 limit 走 OOM：内核在内存压力下选择进程杀掉，通常是容器里的 PID 1，然后 kubelet 按 restartPolicy 重启容器，`kubectl describe pod` 里能看到 `OOMKilled` 和退出码 137。内存限制是反应式的，容器可能先超过 limit 一点，等内核发现压力才被杀。只写 limit、不写 request 时，Kubernetes 会把同一个资源的 limit 复制成 request；这条规则对 QoS 判定很关键。

Pod 的 requests 通常是各容器 requests 之和，Pod 的 limits 也是各容器 limits 之和。一个容器可以超过自己的 request 使用节点上的空闲资源，但节点一旦出现压力，超出 request 的 Pod 就会成为驱逐候选。QoS 就是在这个基础上给 Pod 分三档：

| QoS | 判定条件 | 节点压力下的驱逐顺序 |
|---|---|---|
| Guaranteed | 每个容器（或 Pod 级资源）的 CPU、内存 request 都大于 0，且分别等于 limit | 最后 |
| Burstable | 不满足 Guaranteed，但至少一个容器（或 Pod 级）写了 CPU/内存 request 或 limit | 中间 |
| BestEffort | 所有容器和 Pod 级都没有 CPU/内存 request 或 limit | 最先 |

`Guaranteed` 的“每个容器”是字面意思：只要有一个 sidecar 没写 CPU request，整个 Pod 就掉到 Burstable。反过来，只写了 limits 的 Pod 因为 limit 被复制成 request，如果 CPU 和内存都这么写，反而可能是 Guaranteed。QoS 写在 `status.qosClass` 里，不是 `spec` 字段；它在 Pod 创建时确定，之后不能通过原地调整改成另一档，想改只能重建 Pod。驱逐时先 BestEffort、再 Burstable、最后 Guaranteed；因资源压力驱逐时，只有超出 requests 的 Pod 才是候选，没超 requests 的低优先级 Pod 不会被 kubelet 以资源压力为由赶走。

## 28.2 调度器：过滤与打分

kube-scheduler 监听“还没有绑定节点”的 Pod。每发现一个，它先在调度队列里按优先级排队，然后走一遍调度周期：Filter 把不能去的节点去掉，Score 给剩下的节点打分，最后 Bind 把选中的节点写回 API server，Pod 的 `spec.nodeName` 被填上，目标节点上的 kubelet 才开始拉镜像、起容器。Filter 会看节点可分配资源够不够、污点能不能容忍、nodeSelector/nodeAffinity 匹不匹配、Pod 反亲和是否冲突、hostPort 有没有空闲、PVC 能不能在候选节点上绑定、拓扑分布是否满足；Score 则在这些可行节点里挑“更合适”的，例如资源更均衡、镜像已经在节点上、拓扑分布更均匀。一个节点都没留下时，Pod 停在 Pending，调度器写 `FailedScheduling` Event；这时 PostFilter 里的抢占逻辑可能尝试赶走低优先级 Pod，但那是下一节的事。

`nodeSelector` 是最简单的约束：Pod 写一组键值，节点必须全部匹配，语法只有“与”。`nodeAffinity` 更灵活，分 `requiredDuringSchedulingIgnoredDuringExecution` 和 `preferredDuringSchedulingIgnoredDuringExecution` 两种。required 不满足就不调度，preferred 不满足仍然调度，只是得分低；`IgnoredDuringExecution` 的意思是调度时看 label，调度完之后节点 label 变了也不会把 Pod 赶走。多个 `nodeSelectorTerms` 之间是“或”，一个 term 里的多个 `matchExpressions` 之间是“与”；preferred 的 `weight` 取 1–100，命中多个偏好时把权重相加再和其他打分一起排序。`nodeSelector` 和 `nodeAffinity` 同时写时，两个都必须满足。

`nodeName` 是另一条路：Pod 的 `spec.nodeName` 一旦非空，调度器直接忽略这个 Pod，由指定节点上的 kubelet 尝试运行。它绕过的不只是 Filter/Score，还包括 nodeSelector、nodeAffinity 和 `NoSchedule` 污点检查；节点不存在时 Pod 不会运行，资源不够时 Pod 会失败并给出 `OutOfmemory`、`OutOfcpu` 一类原因，节点上有 `NoExecute` 污点时 kubelet 仍会把不容忍的 Pod 赶走。官方文档把 `nodeName` 定位成给自定义调度器或特殊场景用的旁路，普通工作负载要限定节点，用 nodeSelector 或 nodeAffinity，让调度器仍然参与决策。

`nodeName` 和 nodeSelector 不是等价写法。旧教程里“想指定节点就写 nodeName”的做法会跳过调度器的所有检查，节点被其他 Pod 占满时没有任何保护；用 `nodeSelector: kubernetes.io/hostname: <节点名>` 能达到“只去这个节点”的效果，还能让调度器检查资源、污点和 PVC。

调度门（scheduling gates）解决的是另一个问题：Pod 已经创建，但还没准备好被调度。`.spec.schedulingGates` 是一个字符串列表，只能在创建 Pod 时设置；创建后可以按任意顺序删除 gate，但不能新增。只要列表非空，调度器就不把 Pod 放进活跃队列，Pod 的 STATUS 显示 `SchedulingGated`。这个机制适合批处理先创建、等依赖的数据或镜像准备好再放行，也适合让上层控制器先把一批 Pod 建出来、再统一开闸；Pod 在门里时还可以收紧 nodeSelector/nodeAffinity，但不能放宽。这个字段在 Kubernetes 1.30 成为 stable。

`NodeDeclaredFeatures` 是 1.37 成为 stable 的节点能力上报机制。kubelet 启动时把当前节点真正支持的、仍在演进的节点级特性写进 Node 的 `.status.declaredFeatures`；调度器的 `NodeDeclaredFeatures` 插件在 PreFilter 推断 Pod 需要哪些特性，在 Filter 检查候选节点有没有声明，准入控制器和 kubelet 还会在绑定、启动时再校验一次。它主要给引入新节点特性的 Kubernetes 开发者用，缓解控制面和节点版本不一致时的 skew：Pod 不会被放到一个“版本看起来够、实际没开这个特性”的节点上。普通应用不需要直接读写这个字段。

> **旧资料提示**：旧教程用 `kube-scheduler --policy-config-file` 配 Predicates 和 Priorities。调度框架在 Kubernetes 1.19 成为 stable，扩展点改成 Plugin；`--policy-config-file`、`--policy-configmap` 等参数在 1.23 起不再支持，改用 `KubeSchedulerConfiguration` 的 profiles 和 plugins。

## 28.3 污点与容忍

nodeAffinity 是 Pod 吸引节点，taint 是节点排斥 Pod。给节点打上 `key=value:Effect` 的污点后，只有带匹配 toleration 的 Pod 才能留下或被调度。toleration 的 `operator` 默认是 `Equal`，此时 `key`、`value`、`effect` 都要和污点一致；`operator: Exists` 只要求 key 存在，不写 value。key 为空且 operator 为 Exists 时匹配所有 key，但 effect 仍要匹配；effect 为空时匹配该 key 的所有 effect。多个污点和多个 toleration 一起看时，先去掉能匹配的污点，剩下的污点再按 effect 生效。

三种 effect 的差别在“对已经运行的 Pod 怎么办”。`NoSchedule` 只阻止新的调度，已经在节点上的 Pod 不动；`PreferNoSchedule` 是软版本，调度器尽量避开，但没有别的地方可去时仍然会放；`NoExecute` 最强硬，节点上新加的 NoExecute 污点会立刻驱逐不容忍的 Pod，带 `tolerationSeconds` 的 toleration 则允许 Pod 再留一段时间，时间到了由节点生命周期控制器驱逐。节点失联、NotReady、内存/磁盘/PID 压力这些情况，控制面会自动打上内置污点；`node.kubernetes.io/not-ready` 和 `unreachable` 默认是 NoExecute，Kubernetes 还会自动给 Pod 加 300 秒的 toleration，所以节点故障后 Pod 通常还能留 5 分钟。DaemonSet 的 Pod 对这两个污点没有时间限制，避免节点一抖就被赶走。

用 kubeadm 建的集群会给控制面节点打 `node-role.kubernetes.io/control-plane:NoSchedule`，kind 建出来的控制面也一样。普通业务 Pod 没有这个 toleration，就不会跑到控制面上；DaemonSet 如果要在控制面也跑一份，必须显式加这条 toleration。DaemonSet 控制器会自动加 `not-ready`、`unreachable`、`memory-pressure`、`disk-pressure`、`pid-pressure`、`unschedulable` 等 toleration，但不会自动容忍 `control-plane`。

> **旧资料提示**：旧说法是“DaemonSet 绕过调度器，直接在每个节点上起 Pod”。现在不是这样：DaemonSet 控制器给 Pod 写一条匹配目标节点名的 `nodeAffinity`，Pod 创建后仍由默认调度器绑定；节点资源不够时，调度器还可能按优先级抢占其他 Pod。

## 28.4 拓扑分布与高可用

反亲和能避免两个副本落在同一节点，但它是“禁止”，节点少的时候容易把 Pod 卡在 Pending。拓扑分布（topology spread）换了一种说法：不禁止同节点，而是限制各拓扑域之间副本数的差距。`topologySpreadConstraints` 的核心字段是 `maxSkew`、`topologyKey`、`whenUnsatisfiable` 和 `labelSelector`：`topologyKey` 是节点 label 的键，值相同的节点属于同一个域（例如 `kubernetes.io/hostname` 的每个节点是一个域，`topology.kubernetes.io/zone` 的每个可用区是一个域）；`maxSkew` 是允许的最大差值；`labelSelector` 选出参与计数的 Pod，通常要匹配 Pod 自己的 label。

`whenUnsatisfiable: DoNotSchedule` 是默认值：放进去会超过 maxSkew 就不调度。`ScheduleAnyway` 不阻止调度，只是给能减小差距的节点更高分。`minDomains` 用来处理“域太少”的情况：比如要求至少 3 个可用区，实际只有 2 个，则全局最小值按 0 算，skew 会变大，从而阻止继续往已有域里堆。`minDomains` 只能和 `DoNotSchedule` 一起用，不写时按 1 处理；它在 Kubernetes 1.30 成为 stable。多个约束之间是“与”，同一个 `topologyKey` 和 `whenUnsatisfiable` 组合只能出现一次。节点缺少 `topologyKey` 时会被跳过，既不参与计数，也不会被选中。

还有两个容易忽略的字段。`nodeAffinityPolicy` 默认 `Honor`，只把匹配 Pod 的 nodeSelector/nodeAffinity 的节点算进域；`nodeTaintsPolicy` 默认 `Ignore`，污点节点也会被算进域。这个默认值在“控制面有污点、worker 只有两个”的集群里很关键：如果 Pod 没有 nodeAffinity 把控制面排除，又不写 `nodeTaintsPolicy: Honor`，控制面会被当成一个 0 副本的域，`maxSkew: 1` 会让第 3 个副本开始就放不进去。`nodeAffinityPolicy` 和 `nodeTaintsPolicy` 都在 1.33 成为 GA。

`podAntiAffinity` 仍然有用：required 规则适合“两个副本绝对不能同节点”的硬约束，preferred 规则适合尽量打散但允许挤一挤。硬反亲和和 `DoNotSchedule` 一样，节点不够时会让副本 Pending；先用 preferred 或 `ScheduleAnyway` 观察分布，再决定要不要收紧。PDB（PodDisruptionBudget）是另一层：它限制的是驱逐（drain、升级这类自愿中断）时最少保留几个 Pod，不是调度约束，也不阻止抢占；抢占对 PDB 只是 best effort。

## 28.5 优先级与抢占

PriorityClass 是集群级对象，`value` 是必填的 32 位整数，越大优先级越高；允许的范围是 -2147483648 到 1000000000，超过 10 亿的值留给系统组件。Kubernetes 自带两个类：`system-cluster-critical` 的值是 2000000000，`system-node-critical` 是 2000001000。`globalDefault: true` 让没有写 `priorityClassName` 的 Pod 使用这个类的值，整个集群只能有一个 globalDefault；它只影响之后创建的 Pod，不会改已经存在的 Pod。`preemptionPolicy` 默认是 `PreemptLowerPriority`，设成 `Never` 时 Pod 仍然排在低优先级 Pod 前面，但不会赶走别人，只等资源自然空出来；非抢占的高优先级 Pod 仍然可以被更高优先级的 Pod 抢占。

调度队列按优先级排序，高优先级 Pod 先被尝试。一个高优先级 Pod 找不到可行节点时，调度器进入抢占：它找一个节点，假设把里面一个或多个低优先级 Pod 删掉后这个 Pod 能放下；能放下才考虑，然后尽量选优先级最低的受害者，并且尽量不违反 PDB。抢占不是“立刻把节点清空”，受害者会走优雅终止，默认 30 秒；在它们退出期间，调度器可能先把节点让给另一个更高优先级的 Pod。被选中的节点写在抢占者的 `status.nominatedNodeName` 里，但抢占者不一定会落到那个节点，`nominatedNodeName` 也不等于 `spec.nodeName`。被抢占的 Pod 会带上 `DisruptionTarget` condition，reason 是 `PreemptionByScheduler`，然后进入 Terminating；PDB 在抢占里只是 best effort，找不到不违反 PDB 的受害者时仍然会抢占。

优先级不要乱给。普通业务 Pod 拿到很高的 `value`，会在资源紧张时把数据库、监控甚至系统组件赶走；多租户集群里，恶意用户也可以创建最高优先级的 Pod。可以用 ResourceQuota 限制某个命名空间能使用哪些 PriorityClass，或者限制高优先级 Pod 的数量。PriorityClass 和 QoS 是两个正交的维度：调度器的抢占只看优先级，不看 QoS；kubelet 的节点压力驱逐会同时看是否超出 requests、Pod 优先级和用量相对 requests 的比例，所以一个低优先级但没超 requests 的 Pod 不会因为资源压力被 kubelet 驱逐，而一个高优先级但超了 requests 的 Pod 仍可能被驱逐。

## 28.6 Pod 级资源与原地调整

前面写的 resources 都在容器上。Pod 级资源是另一层：在 `spec.resources` 里直接写 CPU、内存（以及 hugepages）的 requests/limits，给整个 Pod 一个总预算，容器之间可以共享空闲资源。`PodLevelResources` 在 Kubernetes 1.32 进入 alpha，1.34 进入 beta；两处都写时，Pod 级的 requests/limits 优先于容器级，QoS 也按 Pod 级判定。它适合容器很多、逐个估算不现实的工作负载，例如一个主容器加多个 sidecar。代价是容器级和 Pod 级的语义要分清：Pod 级的 limit 是所有容器合计的上限，不是每个容器各自的上限；Pod 级资源的原地调整在 1.36 进入 beta（`InPlacePodLevelResourcesVerticalScaling`，默认开启），和容器级原地调整是两套入口，不能混为一谈。

容器级原地调整（in-place Pod resize）在 Kubernetes 1.35 成为 stable，门控锁定为开启。它允许改运行中 Pod 的 CPU/内存 requests/limits，不重建 Pod。做法是更新 Pod 的期望资源，走 `/resize` 子资源：`kubectl patch pod <name> --subresource resize`，或者 `kubectl edit pod <name> --subresource resize`。API 里的 `spec.containers[*].resources` 是期望值，`status.containerStatuses[*].resources` 是 kubelet 实际配置到容器上的值，`status.containerStatuses[*].allocatedResources` 是 kubelet 确认过的分配量；调度器在 resize 未完成时会取期望、已分配、实际三者的最大值来记账，避免把节点超卖。

进度看 Pod 的 condition，不是 `status.resize`：`PodResizePending` 表示 kubelet 暂时不能应用，reason 可能是 `Infeasible`（节点根本放不下）或 `Deferred`（现在不行、以后也许行）；`PodResizeInProgress` 表示已经接受、正在应用。`resizePolicy` 控制每种资源改动后要不要重启容器，`NotRequired` 是默认，`RestartContainer` 适合那些启动时才能确定内存布局的应用。原地调整的边界不少：只能改 CPU 和内存，不能删掉已经设置的 request/limit，只能改成别的值；QoS 在创建时确定，调整不能把 Burstable 改成 Guaranteed；非重启的 init 容器和临时容器不能调；Windows Pod 不支持；使用 static CPU/内存管理策略的 Pod 也不能调。

## 28.7 GPU、DRA 与 Workload API（概念为主）

GPU 在 Kubernetes 里通常走 device plugin。节点上装好驱动和厂商插件，插件向 kubelet 注册并上报设备数量，节点上就出现一个扩展资源名，NVIDIA 的是 `nvidia.com/gpu`。Pod 在容器的 `resources.limits` 里写 `nvidia.com/gpu: 1`，调度器按整数记账，把 Pod 放到还有空闲 GPU 的节点；容器里的运行时再把这个设备挂进去。GPU 只能写在 limits 里：只写 limits 时 Kubernetes 把 limit 复制成 request；同时写 requests 和 limits 时两者必须相等；只写 requests 不写 limits 会被拒绝。扩展资源不能超卖，一个小数也不行。节点没有驱动或 device plugin 时，这个资源名根本不会出现在 `status.allocatable` 里，Pod 会 Pending。

DRA 是 device plugin 之外的另一套设备申请方式。它在 Kubernetes 1.34 成为 stable，1.35 起门控锁定为开启。API 组是 `resource.k8s.io/v1`，四个核心对象分工如下：

| 对象 | 作用 |
|---|---|
| `DeviceClass` | 设备类别和筛选规则，通常由驱动或管理员创建，可用 CEL 按属性筛选 |
| `ResourceClaim` | 一次设备申请，写在命名空间里，可以被多个 Pod 共享 |
| `ResourceClaimTemplate` | 按 Pod 生成独立 ResourceClaim 的模板，生命周期跟随 Pod |
| `ResourceSlice` | 驱动发布的一批设备及其容量，调度器据此找得到哪个节点有空闲设备 |

DRA 的流程是：驱动创建 ResourceSlice，工作负载创建 ResourceClaim 或 ResourceClaimTemplate，调度器为 claim 找满足条件的设备、把分配结果写进 claim 的 `status.allocation`，再把引用这个 claim 的 Pod 绑定到能访问该设备的节点；kubelet 和驱动通过 gRPC 做节点上的设备准备。和 device plugin 相比，DRA 支持按属性表达式筛选、设备共享、按 claim 传厂商配置，应用不用在容器里写设备数量。GPU 只是其中一种设备，FPGA、网卡、加速器都可以走这条路。注意 DRA 目前不支持对 DRA 资源做抢占：高优先级 Pod 申请不到设备时只能等，不能把正在用设备的低优先级 Pod 赶走。

Workload API 是更高一层的调度描述。`scheduling.k8s.io/v1beta1` 的 `Workload` 定义一组 PodGroupTemplate，`PodGroup` 是运行时的组，`schedulingPolicy.gang.minCount` 表示“至少这么多个 Pod 能同时放下，整组才开始调度”，也就是 gang scheduling。`GenericWorkload` 在 1.37 进入 beta，但默认关闭；Job 控制器把 `.spec.scheduling` 编译成 Workload/PodGroup 的能力还依赖 `WorkloadWithJob`（1.36 alpha）。所以这一节只讲对象关系，lab 里没有开启这些门控，也没有 GPU。

## 28.8 排障：Pod Pending 与副本挤在一起

Pod Pending 时，第一步是 `kubectl describe pod` 看 Events，重点看 `FailedScheduling` 的 Message。调度器会把所有节点的失败原因压缩成一句 `0/3 nodes are available: ...`，分号前是汇总，分号后逐条列出原因。常见的有 `Insufficient cpu`、`Insufficient memory`、`node(s) had untolerated taint`、`node(s) didn't match Pod's node affinity/selector`、`persistentvolumeclaim "..." not found`，以及拓扑分布的 `node(s) didn't match pod topology spread constraints`。`preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling` 表示抢占也救不了，通常是没有更低优先级的受害者，或者受害者走了也放不下。

`too-big` 的 `2 Insufficient cpu` 不是因为节点真的用了 100 个核，而是它的 request 超过了两个 worker 的可分配 CPU；控制面那 1 个节点则先被污点挡住。`control-plane-only` 的 `1 node(s) had untolerated taint(s)` 是控制面的默认污点，`2 node(s) didn't match` 是另外两个 worker 的主机名不匹配。`missing-pvc` 的 `persistentvolumeclaim "no-such-pvc" not found` 发生在调度阶段的卷检查，不是 kubelet 挂载失败。三个例子的修法完全不同：降 requests、加 toleration 或改 nodeSelector、先创建 PVC。

副本挤在一起时，先看 `topologySpreadConstraints` 的 `topologyKey` 在节点上到底有没有 label、值是不是每个节点都不同。`kubernetes.io/hostname` 通常每个节点一个值；如果用了自定义的 `zone` label 但只给部分节点打了，缺 label 的节点会被跳过，分布自然不对。再看 `maxSkew`、`minDomains`、`labelSelector` 是否匹配 Pod 自己的 label，以及 `nodeTaintsPolicy` 是否把不该算的节点算进了域。`DoNotSchedule` 太严会让副本 Pending，可以先把 `whenUnsatisfiable` 改成 `ScheduleAnyway` 观察实际分布，确认 label 和域没问题后再收紧；也可以临时把 `maxSkew` 调大，判断是约束本身不可能满足，还是节点资源不够。

排查顺序可以固定成：requests 能不能被任何节点满足 → nodeSelector/nodeAffinity 是否匹配 → 污点有没有 toleration → PVC/PV 是否能绑定 → 拓扑分布/反亲和是否互相冲突 → 优先级和抢占是否被 PDB 或资源挡住。Pending 是调度阶段，`ContainerCreating` 是绑定之后的拉镜像/挂卷阶段，`CrashLoopBackOff` 是容器启动之后，三个阶段的日志和事件不在同一层，不要用 `kubectl logs` 去查一个还没被调度的 Pod。

## 上生产前

**requests 按实测的 P95 设，limits 留出余量。** requests 太小会把节点超卖，流量高峰时大家抢 CPU，延迟抖动；requests 太大又会浪费可调度容量。CPU limit 设得太紧会持续 throttle，应用看起来“没跑满”但响应变慢；内存 limit 设得太贴近峰值会 OOMKilled，设得太松则节点可能被一个 Pod 拖垮。关键服务要么用 Guaranteed（requests=limits），用确定的容量换稳定性，要么用足够多的副本来吸收单副本故障；不要为了 QoS 好看把所有 Pod 都写成 Guaranteed，那会让集群失去弹性。

**多副本用 topology spread 或反亲和打散，再用 PDB 保护自愿中断。** 只写 `replicas: 2` 不保证两个副本在两个节点上，调度器完全可能把它们放在同一台机器。用 `topologyKey: kubernetes.io/hostname` 做节点级打散，用 `topology.kubernetes.io/zone` 做可用区级打散；`DoNotSchedule` 之前先用 `ScheduleAnyway` 看实际分布，确认 label 和域都正确。PDB 只约束 drain、升级这类自愿驱逐，不约束抢占和节点故障，不要把“有 PDB”当成“不会中断”。

**PriorityClass 只给关键系统和真正需要抢占的业务。** 普通业务拿到高优先级，资源紧张时会把数据库、监控和系统组件赶走；多租户集群还要用 ResourceQuota 限制哪些命名空间能用高优先级类。抢占会让低优先级 Pod 进入 Terminating，长任务可能白跑；如果只是想让任务排队靠前、不想杀别人，用 `preemptionPolicy: Never`。系统自带的 `system-cluster-critical`、`system-node-critical` 不要拿来给业务用。

**GPU/DRA 要先有驱动和容量，再谈调度。** GPU 节点要装驱动、device plugin 或 DRA 驱动；DRA 还要有 DeviceClass、ResourceSlice 和节点 label/污点，调度器才知道哪个节点有哪种设备。GPU 是扩展资源，不能超卖，requests 和 limits 必须相等；DRA 目前不支持对设备资源抢占，高优先级 Pod 也只能等设备释放。容量规划要按设备型号、显存和拓扑（同一 NUMA、同一交换机）做，不能只看“节点上插了几张卡”。

**原地调整是 Pod 级操作，不等于改了 Deployment。** 容器级原地调整在 1.35 已经 stable，但只支持 CPU/内存，不能改 QoS 档位，不能删除已经设置的 request/limit；Pod 级资源的原地调整在 1.36 进入 beta，入口和容器级不同。改完一个 Pod 不会改 Deployment 模板，下一次滚动更新会把副本拉回模板值；要让改动持久，模板也要改。内存调小是 best-effort，应用正在用的内存超过新 limit 时 resize 会停在 InProgress，生产上先用 VPA 的推荐值观察，再决定是否自动应用。

**PID 限制要按节点统一配置。** `podPidsLimit` 配在 kubelet 上，同一个 Pod 落到不同节点可能拿到不同的上限；节点之间配置不一致时，排障会看到“换个节点就好了”的假象。给系统和 Kubernetes 组件预留 PID，再给 Pod 设一个足够应用启动的上限，重点防 fork bomb，不要把它当成精细的并发控制。

|---|---|---|
| `resources.requests` | 调度器记账的量 | 只写 limit 时复制为 request |
