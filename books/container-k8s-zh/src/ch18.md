# 第 18 章 API 对象与 kubectl：GVK、label、namespace、server-side apply

上一章结束时，shorty 的 Deployment 已经在集群里跑起来了。如果只看自己写的那份清单，很容易以为集群里的对象就是清单的样子：一个 `apiVersion`、一个 `kind`、一段 `spec`，仅此而已。把 `kubectl -n shorty get deploy api -o yaml` 的输出完整打出来，会看到它长得多——API server 补上了 `strategy`、`progressDeadlineSeconds` 这类默认值；控制器写入了 `status`，里面有副本数、条件和观测到的代次；kubectl 留下了一条 `last-applied-configuration` 注解；`metadata` 里还有一段默认不显示的 `managedFields`（加 `--show-managed-fields` 才看得到），记录哪个客户端改过哪些字段。这些多出来的东西不是噪音，它们分别回答了三个问题：这个对象是什么、它现在怎么样、上一次是谁改的。

`kubectl apply` 和 `kubectl create` 的差别，就藏在这些字段里。`create` 是一次 POST，把清单当成新对象交给 API server，对象已经存在就报 `AlreadyExists`。`apply` 不是单一动作：客户端会先读活对象，再和本地清单、上次应用的记录做三方比较，算出只包含差异的 patch，最后发 PATCH；对象不存在时才发 POST。这也解释了为什么 `apply` 能反复执行，而 `create` 不能。

两个人同时改同一个对象时，谁会赢？在传统的客户端 apply 里，后提交的那个通常赢，而且不会收到任何警告；前一个人的改动如果不在后一个人的清单里，可能被保留，也可能被清掉，取决于它是否出现在 `last-applied-configuration` 里。Server-Side Apply（SSA）把“谁拥有哪个字段”搬到服务端，用 `managedFields` 记录字段归属；后一个人要改别人拥有的字段，API server 直接拒绝，并告诉你和哪个 manager 冲突。这不是为了阻止协作，而是把“覆盖”从默认行为变成需要显式确认的动作。

本章从拆开一个现成的 Deployment 开始，先认清 GVK、metadata、spec 和 status；然后看 namespace、label、annotation 怎么把对象分组和标记；接着把 `kubectl` 的输出、发现和 kubeconfig 用顺；再比较三种对象管理方式，动手制造一次 SSA 冲突，用 `--force-conflicts` 接管字段，用 `--dry-run=server` 和 `diff` 预演变更；最后看 ownerReference 的级联删除和 finalizer 卡住时怎么救。末尾两个排障场景，一个是 `metadata.resourceVersion` 缺失的更新错误，一个是删不掉的名字空间。

> **起点**：本章从 `s1-api` 开始。单节点 kind 集群里，名字空间 `shorty` 中已有 `Deployment api`（1 副本）、`Service api`（ClusterIP 8080）和 `ConfigMap shorty-config`，镜像 `shorty:0.1` 已经加载进节点。`bash code/ch18/setup.sh` 会重建集群、构建并加载 shorty 镜像、apply `s1-api`，然后等 Deployment 可用。本章后面的示例都在这个状态上继续，示例之间也会互相衔接（例如 18.4 把 api 交给 SSA 管理，18.5 接着接管 `replicas`）。

## 18.1 对象解剖：apiVersion/kind/metadata/spec/status

Kubernetes 的对象是一份“意向记录”（record of intent）。创建对象时，你把期望状态写进 `spec`；控制平面里的控制器不断把实际状态拉向这个期望，并把观测结果写进 `status`。清单里必须有的四个顶层字段是 `apiVersion`、`kind`、`metadata` 和 `spec`（并非所有对象都有 `spec`，例如 ConfigMap 用 `data`，但大多数工作负载对象遵循这个结构）。`apiVersion` 和 `kind` 一起回答“这是什么”，`metadata` 回答“它叫什么、属于谁”，`spec` 回答“我要它怎样”，`status` 回答“它现在怎样”。

`apiVersion` 的写法是 `group/version`。`apps/v1` 里的 group 是 `apps`，version 是 `v1`；`kind` 是 `Deployment`。三者合起来就是常说的 GVK（group/version/kind）。核心组（core group）的对象省略 group，只写版本，例如 Pod 的 `apiVersion: v1`。GVK 是清单里的说法；到了 HTTP 层，同样的东西用 GVR（group/version/resource）表示，resource 是 URL 里的复数名词，例如 `deployments`。Deployment 的 REST 路径是 `/apis/apps/v1/namespaces/shorty/deployments/api`：`apps` 是 group，`v1` 是 version，`deployments` 是 resource，`shorty` 是名字空间，`api` 是对象名。核心组的路径省掉 group，写成 `/api/v1/namespaces/shorty/pods/...`。

GVK 和 GVR 不是两套模型，而是同一份发现信息的不同投影。`kubectl api-resources` 把这张表打出来：每一行有 resource 名、short name、API version、是否 namespaced、kind。`kubectl get deploy` 里的 `deploy` 就是 short name，kubectl 通过 Discovery API 把它解析成 `deployments.apps`，再拼出 REST 路径。自定义资源（CRD）也走同一套发现：只要 CRD 注册了 group/version/kind，`api-resources` 里就会出现对应行，`kubectl get` 就能用它的 short name 或复数名访问。知道这一点，遇到“这个集群里到底有没有某种资源”“它是不是名字空间级的”就不用猜。

`metadata` 里最容易被忽略的是几个名字相近的字段。`name` 是对象在“同一 API group、同一 resource、同一名字空间”内的唯一标识；`generateName` 不是名字，而是前缀，API server 会在后面加随机后缀，Pod 和 ReplicaSet 常用它。`labels` 和 `annotations` 都是键值对，区别在用途：label 用来选择和分组，annotation 用来存不参与选择的附加信息。`ownerReferences` 指向属主对象，垃圾回收靠它判断谁该跟着谁删；`finalizers` 是一组键，删除请求到达时，只要列表非空，对象就停在 `Terminating`。`uid` 是整个集群唯一的身份，对象删掉再建同名对象，`uid` 会变；`resourceVersion` 是这次写入的版本号，更新时用它做乐观并发控制；`generation` 是期望状态的一个代次序号，控制器用它判断自己处理的是不是最新一代。

`spec` 和 `status` 的边界，是理解控制器行为的关键。`spec` 是你写的期望，`status` 是控制器写的观测；普通 `kubectl apply` 不会去改 `status`，它走的是主资源，不是 `status` 子资源。也正因为如此，`kubectl get -o yaml` 里会出现很多你没写过的字段：`replicas: 1`、`strategy.type: RollingUpdate`、`maxSurge`/`maxUnavailable` 都是 API server 在创建时补的默认值；`status.observedGeneration` 表示控制器已经处理到哪一代，`status.availableReplicas` 表示当前有多少副本可用。排障时先看 `observedGeneration` 是否追上 `metadata.generation`，能快速区分“控制器还没处理”和“处理了但没成功”。

## 18.2 namespace、label、annotation

名字空间（Namespace）首先是一个名字作用域。同一个名字空间里，同一类资源只能有一个 `api`；换一个名字空间，可以再有一个 `api`，两者互不冲突。它也是很多策略的作用域：ResourceQuota 限制一个名字空间能用的 CPU、内存和对象数量，LimitRange 给这个空间里的 Pod 设默认 requests/limits，RBAC 的 Role 和 RoleBinding 通常按名字空间授权，NetworkPolicy 也是名字空间级的资源。删除一个名字空间时，Kubernetes 会异步删除它里面的名字空间级对象；Namespace 本身是集群级对象，不属于任何名字空间，Node、PersistentVolume 也一样。

但名字空间不是网络边界，也不是安全边界。两个名字空间里的 Pod 默认可以互相访问，除非你装了执行 NetworkPolicy 的 CNI 并写了策略；名字空间也不阻止一个有权跨空间读 Secret 的用户。官方多租户文档把这一点说得很直接：名字空间提供的是 API 资源的逻辑隔离，要真正隔离租户，还得配 RBAC、NetworkPolicy、Pod 安全性准入等一整套控制。把它当成“ Kubernetes 的租户”会高估它：它能帮你组织对象、配配额、缩小授权范围，但不会自动把网络和权限切开。

集群起来时自带四个名字空间：`default` 给没写名字空间的请求用，`kube-system` 放控制平面组件，`kube-public` 放所有客户端都可读的公共信息，`kube-node-lease` 放节点的 Lease 对象。`kubectl get namespaces -o name` 里还能看到本章的 `shorty`。从 Kubernetes 1.22 起，控制平面会给每个名字空间自动加上不可变的 `kubernetes.io/metadata.name=<名字>` 标签，所以可以用 label selector 选名字空间，而不必依赖名字本身。日常操作里 `-n shorty` 和 `--namespace shorty` 等价；把当前 context 的默认名字空间设成 `shorty` 之后可以省略，但脚本里最好显式写，免得换 context 时跑到别的空间。

标签（label）是用于识别和选择对象的键值对。它的键可以带一个 DNS 子域前缀，例如 `app.kubernetes.io/name`，斜杠后面是名字部分；值最多 63 个字符，可以包含字母、数字、`-`、`_`、`.`。Kubernetes 推荐了一套 `app.kubernetes.io/*` 标签：`name` 是应用名，`instance` 是实例名，`version` 是版本，`component` 是组件，`part-of` 是所属的上层应用，`managed-by` 是管理工具。它们不是强制的，但工具和人都能按同一套键来查，比每个团队自创 `app`、`service`、`project` 更省事。Pod 上常见的 `pod-template-hash` 不是人加的，是 ReplicaSet 控制器加的，用来区分不同版本的 Pod 模板。

标签的价值在选择器（selector）。等值选择器写成 `env=dev`、`tier!=frontend`，集合选择器写成 `env in (dev,staging)`、`tier notin (frontend,backend)`、`partition`（存在这个键）、`!partition`（不存在）。多个条件用逗号分隔，彼此是逻辑与；Kubernetes 的 label selector 没有逻辑或，要用“或”只能写成 `env in (dev, staging)` 这种集合形式。Service 的 `spec.selector` 只支持等值匹配；Deployment、ReplicaSet、DaemonSet、Job 这些较新的资源支持 `matchLabels` 和 `matchExpressions`，`matchExpressions` 的 operator 可以是 `In`、`NotIn`、`Exists`、`DoesNotExist`，`matchLabels` 和 `matchExpressions` 里的条件全部要满足。写选择器之前先想清楚“这个标签是不是用来标识身份的”；如果只是记录构建号、负责人、变更单号，应该放 annotation，不要放 label。

注解（annotation）也是键值对，但不参与选择。它的值可以是任意字符串，包括空格、换行、JSON、YAML；所有注解的键和值加起来不能超过 256 KiB。注解常用来放构建信息、发布单链接、镜像 digest、变更原因、控制器需要的配置。`kubernetes.io/change-cause` 是一个约定俗成的注解，用来记录“为什么改”，例如把镜像从 0.1 升到 0.2 时写上升级单号；它不会影响调度或选择，只是给人看的。label 和 annotation 的键语法相同，都有可选的 DNS 前缀；`kubernetes.io/` 和 `k8s.io/` 前缀保留给 Kubernetes 核心组件，业务自定义的键应该用自己的域名前缀。

最后一条注解写进 `kubernetes.io/change-cause`，`jsonpath` 再把它读出来，值原样返回。`kubectl explain deployment.spec.selector.matchExpressions` 则把集合选择器的字段摊开：`key`、`operator`、`values`，operator 的合法值就是 `In`、`NotIn`、`Exists`、`DoesNotExist`。这一段没有直接创建带 `matchExpressions` 的 Deployment，但字段的含义和前面 `-l 'env in (...)'` 的语义是同一套；真正写进 `spec.selector.matchExpressions` 时，controller 会按同样的规则匹配 Pod。

## 18.3 kubectl 的输出与发现

`kubectl` 本身不实现调度、不存状态，它就是一个 API 客户端：读 kubeconfig 找到 API server 和凭据，把子命令翻译成 HTTP 请求，再把响应按你要求的格式打印。理解这一点，输出格式和“为什么这个命令查不到资源”就都好解释了。`-o wide` 是在默认表格上多加几列（Pod 的 IP、所在节点、NOMINATED NODE、READINESS GATES 等）；`-o yaml`/`-o json` 返回 API 对象的完整序列化；`-o name` 只打印 `resource/name`，适合喂给 `xargs` 或循环；`-o jsonpath` 和 `-o custom-columns` 用来从 JSON 结构里挑字段。格式的选择取决于下一步：人看用 `wide`，存档用 `yaml`，脚本用 `name`、`jsonpath` 或 `custom-columns`。

`jsonpath` 的模板用花括号包起来，支持 `range`/`end` 遍历列表、`?()` 过滤、`[*]` 通配、`[start:end]` 切片，以及 `text`、`@` 这些函数。字段名里带点（例如 `kubernetes.io/change-cause`）时要写成 `kubernetes\.io/change-cause`，否则点会被当成路径分隔符。JSONPath 不支持正则；需要正则匹配时，用 `-o json` 接 `jq`，或者用 `custom-columns` 把字段取出来再交给 shell。`custom-columns` 的写法是 `列名:.字段路径`，列名随便取，字段路径用点号分隔，输出自带表头；它比一长串 `jsonpath` 更适合给人看，也比 `-o wide` 更灵活。

`--sort-by` 接一个字段路径，按该字段排序，例如按名字、按重启次数、按创建时间。`-L`/`--label-columns` 把某个标签作为额外一列打出来，`--show-labels` 则把所有标签塞进最后一列。`kubectl get pods -A` 列出所有名字空间的 Pod，`-A` 是 `--all-namespaces` 的缩写；这两个选项在脚本里很常用，但要记住它们只改变查询范围，不会改变权限——没有权限的名字空间仍然会被 API server 拒绝或过滤。

> **旧资料提示**：旧教程里用 `kubectl get pods -a` 或 `--show-all` 显示所有 Pod（包括已经终止的），`-a/--show-all` 在 kubectl 1.14 已经移除；现在要按状态筛就用 field selector，例如 `--field-selector=status.phase=Running`，要按标签筛就用 `-l`。

发现资源靠三条命令。`kubectl api-versions` 列出集群当前提供的 group/version，例如 `apps/v1`、`batch/v1`；`kubectl api-resources` 列出每个 group/version 下的 resource、short name、是否 namespaced、kind，还能用 `--api-group`、`--namespaced`、`--verbs` 过滤；`kubectl explain` 查字段的 schema 和说明。`api-resources` 回答“有没有这种资源、它叫什么、是不是名字空间级”，`explain` 回答“这个字段是什么类型、默认值是什么、下面还有哪些字段”。

> **旧资料提示**：旧教程用 `kubectl get componentstatuses` 检查集群健康。ComponentStatus API 从 Kubernetes 1.19 起已经弃用，`kubectl get --raw='/readyz?verbose'` 和 `/livez` 才是当前检查 API server 健康的方式；节点和 Pod 的健康要看各自的 `status` 与 Event。`explain --recursive` 会递归展开子字段，字段多的时候用 `--max-depth` 限制层数，否则输出可能几百行。CRD 注册后也会出现在 `api-resources` 和 `explain` 里，所以这套方法不限于内置资源。

Event 是排查对象状态变化的第一手材料。`kubectl get events` 默认按名字空间列，`--sort-by=.metadata.creationTimestamp` 按时间排，`-o custom-columns` 可以只留 `TYPE`、`REASON`、`OBJECT` 三列；`kubectl events --types=Warning` 是较新的子命令写法，只筛 Warning。Event 里的 `involvedObject` 指向出事的对象，`reason` 是机器可读的原因（`Scheduled`、`Pulling`、`FailedMount`、`Unhealthy` 等），`message` 是人读的细节。Event 有保留时间，过一阵会被清理，所以排障时先看 Event，再去看 Pod 的 `status` 和容器日志。

## 18.4 三种对象管理方式

`kubectl` 管理对象有三条路，官方把它们叫命令式命令（imperative commands）、命令式对象配置（imperative object configuration）和声明式对象配置（declarative object configuration）。三者的区别不在“用不用 YAML”，而在“谁决定这次要做什么操作”。命令式命令把操作写在命令行里，`kubectl run`、`kubectl create deployment`、`kubectl expose` 都属于这一类；命令式对象配置把操作写在命令里、对象写在文件里，例如 `kubectl create -f`、`kubectl replace -f`；声明式配置只给文件或目录，由 kubectl 自己判断每个对象该创建还是更新，`kubectl apply -f` 是代表。

命令式命令适合一次性任务和开发时的快速验证。它快，但不在 Git 里留下“这次做了什么”，也无法 review；对象被删了，命令历史不会自动把它恢复。`kubectl run` 在早期版本可以用 `--generator` 生成 Deployment 或 Job，这个参数在 kubectl 1.18 已经移除，现在它只创建一个 Pod；要 Deployment 就用 `kubectl create deployment`，要 Job 就用 `kubectl create job`。如果只是想拿一份清单，可以加 `--dry-run=client -o yaml`，让 kubectl 把将要提交的对象打印出来，再存进 Git。

> **旧资料提示**：旧教程里用 `kubectl run --generator=deployment/v1beta1 ...` 让 `kubectl run` 顺手创建 Deployment 或 Job。`--generator` 在 kubectl 1.18 已经移除，`kubectl run` 现在只创建 Pod；要 Deployment 用 `kubectl create deployment`，要 Job 用 `kubectl create job`。

命令式对象配置比纯命令多了一份文件，能进 Git、能 review，但操作仍然由人指定：`create` 只在对象不存在时成功，`replace` 用文件里的完整对象覆盖活对象。`replace` 的坑在于“完整”二字：文件里没写的字段会被丢掉，包括其他控制器后来写进去的字段。官方文档专门警告，对 `Service` 的 `LoadBalancer` 这类会被集群独立更新字段的资源，不要用 `replace`。它适合“一个文件、一个 writer、改动不频繁”的场景；一旦两个人改同一个对象，或者控制器也会写这个对象，覆盖就会丢东西。

声明式配置把“创建还是更新”交给 kubectl。客户端 apply 会读三样东西：本地清单、活对象、活对象上的 `kubectl.kubernetes.io/last-applied-configuration` 注解。它先算出“上次清单里有、这次清单里没有”的字段并从活对象里清掉，再算出“这次清单里有、值和活对象不一样”的字段写进去，最后把新清单写回注解。因为写的是 patch 而不是整个对象，其他 writer 后来加的、不在上次清单里的字段会被保留。`kubectl diff -f` 可以先看这次 apply 会改什么；`apply -f` 不会自动删除目录里已经移除的对象，要删得显式 `delete -f` 或用 `--prune`。

客户端 apply 的“保留别人的改动”是有限度的：它只知道上次清单和这次清单，不知道某个字段现在是谁的。如果另一个 writer 改了同一个字段，而你的清单里也写了这个字段，apply 会直接覆盖，不会提醒。Server-Side Apply 把这件事搬到服务端：每个写请求带一个 field manager 名字，API server 在 `metadata.managedFields` 里记录每个字段归谁；apply 时如果某个字段的当前值和你的值不同、且归另一个 manager，就返回冲突，列出冲突字段和 manager。你可以选择放弃这个字段、把值改成和服务端一样以共享所有权，或者用 `--force-conflicts` 强行接管。前两种是协作，第三种是“我知道我在覆盖谁”。

## 18.5 Server-Side Apply 与 dry-run

Server-Side Apply 的核心参数只有三个：`--server-side` 让 apply 走 `application/apply-patch+yaml` 的 PATCH，`--field-manager=<名字>` 指定这次写入的身份，`--force-conflicts` 在冲突时强行覆盖。`--field-manager` 不是给人看的备注，它是 `managedFields` 里的键：同一个对象被多个控制器或流水线修改时，靠这个名字区分“这是部署流水线写的”“这是 HPA 写的”“这是运维临时改的”。名字应该稳定、可追溯，例如 `ci-shorty-deploy`、`argocd-controller`、`hpa`，不要每次随机生成，否则冲突信息里全是陌生 manager，查不到源头。

冲突有三个解法，官方文档写得很清楚：覆盖值并成为唯一 manager（`--force-conflicts`）、放弃这个字段（从本地清单里删掉）、接受服务端的值并共享所有权（把本地值改成和服务端一样再 apply）。`--force-conflicts` 的语义不只是“这次写进去”：它会把字段从其他 manager 的 `managedFields` 条目里移除，所有权转移给当前 manager。对 HPA、Deployment 控制器这类会持续写 `replicas` 的组件，强行接管之后，下一次控制器写入可能又把所有权拿回去，所以“抢”之前要先确认谁应该拥有这个字段。控制器自己用 SSA 时通常总是 force，因为它管理的就是自己的对象；人用 force 则要谨慎。

`--dry-run=server` 和 `--dry-run=client` 不是一回事。`client` 只在本地把对象打印出来，不联系 API server，适合生成 YAML；`server` 会把请求完整走一遍 API server 的处理链：认证、准入、字段校验、默认值、合并冲突，直到写存储之前停下，返回的对象和真正写入时几乎一样，但保证不落盘、不产生副作用。也正因为走了完整链路，它需要和真实请求相同的权限；`kubectl diff` 就是用 server-side dry-run 算差异的，官方文档说它需要 `PATCH`、`CREATE`、`UPDATE` 权限。dry-run 里有些生成值（UID、resourceVersion、creationTimestamp、Service 的 ClusterIP）可能和真正写入时不同，不能拿 dry-run 的结果当最终对象存起来。

`managedFields` 默认不在 `kubectl get -o yaml` 里显示，要看它得加 `--show-managed-fields`（只对 `json`/`yaml` 输出有效）。每个条目有 `manager`、`operation`、`apiVersion`、`time` 和 `fieldsV1`；`operation` 是 `Apply` 表示最后一次改这个字段的是 SSA，`Update` 表示是 PUT 或其他非 apply 写入。`fieldsV1` 是一棵树，`f:` 前缀表示字段名，空对象 `{}` 表示这个字段本身归该 manager 所有。排障时按字段路径反查 manager，比看整段 JSON 快得多；本章示例用 `jq` 的 `select(.fieldsV1."f:spec"."f:replicas")` 只留下拥有 `replicas` 的条目。

## 18.6 ownerReference、级联删除与 finalizer

标签表达的是“我属于哪个组”，属主引用（ownerReference）表达的是“谁创建了我、谁该负责删我”。这两件事经常同时存在，但不能互相替代。一个 Pod 可以有 `app.kubernetes.io/name=api` 标签，也可以有指向 ReplicaSet 的 ownerReference；标签用于 Service 选后端、用于人做批量查询，ownerReference 用于垃圾回收器判断删除顺序。官方文档明确说，删除 Job 时 Kubernetes 用 ownerReference 而不是标签来决定清理哪些 Pod——因为标签可能被改，ownerReference 不会。

一个有效的 ownerReference 包含属主的 `apiVersion`、`kind`、`name` 和 `uid`，并且必须和附属对象在同一个名字空间（名字空间级的附属可以指向集群级属主，反过来不行）。`uid` 很关键：删掉一个叫 `api` 的 Deployment 再建一个同名 Deployment，新对象的 `uid` 不同，旧的 ownerReference 不会误认新对象为属主。`blockOwnerDeletion` 控制这个附属是否阻止属主被删；控制器自动写 ownerReference 时通常把它设为 `true`，垃圾回收器会先处理这些附属。跨名字空间的 ownerReference 被设计为不允许；如果出现，垃圾回收器会报 `OwnerRefInvalidNamespace` 的警告 Event，并把该引用当成不存在。

Deployment 创建 ReplicaSet，ReplicaSet 创建 Pod，这条链就是 ownerReference 串起来的。删 Deployment 时，默认的级联策略是 `background`：API server 立刻删掉 Deployment 对象，垃圾回收器在后台删 ReplicaSet，ReplicaSet 的删除再触发 Pod 的删除。`foreground` 相反，属主先进入“删除中”，等所有 `blockOwnerDeletion=true` 的附属删完，属主才真正消失；`orphan` 则把附属的 ownerReference 清掉，让它们变成孤儿，属主先走。`kubectl delete --cascade=background|foreground|orphan` 可以显式选，默认是 `background`；这个默认值在 `kubectl delete --help` 里能看到。

finalizer 是删除流程里的“等待点”。删除一个带 finalizer 的对象时，API server 不会立刻删它，而是做三件事：给对象写 `metadata.deletionTimestamp`，保留对象并让它进入 `Terminating`，返回 202 Accepted。控制器看到 `deletionTimestamp` 后去做清理，完成后把对应的 finalizer 从 `metadata.finalizers` 里删掉；列表空了，对象才真正消失。finalizer 本身只是一组键，不包含要执行的代码；真正干活的是监视这个对象的控制器。自定义 finalizer 的键必须是带域名的限定名，例如 `example.com/hold`，不能只写 `hold`。删除请求发出后，不能再给对象加新的 finalizer，也不能改 `deletionTimestamp`，只能删列表里已有的项。

这个机制也解释了“删不掉”的两种常见形态。第一种是对象卡在 `Terminating`，因为某个 finalizer 对应的控制器不工作、或者根本没装，没人来删这个键。第二种是名字空间卡在 `Terminating`：名字空间控制器要先删掉里面所有名字空间级对象，只要有一个对象因为 finalizer 删不掉，名字空间就停在那里。救援手段是找到具体对象、看清 finalizer 的用途，再决定是否手动删键；`kubectl patch ... -p '{"metadata":{"finalizers":[]}}'` 能强行清空，但官方文档明确警告，不要在没弄清 finalizer 作用时这么做——它可能代表尚未完成的存储回收、外部负载均衡清理或备份。

## 18.7 排障：resourceVersion 缺失与删不掉的名字空间

先看一个很具体的报错：`metadata.resourceVersion: Invalid value: 0: must be specified for an update`。它来自 HTTP PUT 路径，不是 PATCH。Kubernetes 的 update 语义是“用新对象替换旧对象”，API server 要求客户端在请求体里带上读到的 `metadata.resourceVersion`，用来检测“你读到的版本是不是已经过期”：如果别人在你读取之后改了对象，版本不匹配，API server 返回 409 Conflict，而不是让你的旧副本覆盖新改动。错误里的 `0` 表示服务端收到的版本是空值，也就是请求体里根本没有 `resourceVersion`。旧资料常把这个值写成 `0x0`，本 lab 的 kubectl 1.37 实测打印的是 `0`，含义相同。

这个错误不是所有资源都会报。ConfigMap、Deployment、Pod 这类核心资源的更新策略允许无条件更新（`AllowUnconditionalUpdate=true`），PUT 里省略 `resourceVersion` 也能写成功；CRD 和 APIService 这类资源的策略不允许，PUT 缺少版本时才会返回同样的错误。`kubectl replace` 通常会先 GET 活对象，把当前 `resourceVersion` 补进 PUT，所以直接对普通资源执行 replace 往往不会报；会报的是没有经过这层补全的 PUT，例如脚本或控制器直接调用 API、模板把版本显式写成空串，或者客户端只有 update 权限而没有 get 权限（补版本的那次 GET 失败）。混用 `create`/`replace`/`apply` 的风险更多在别处：replace 不会更新 `last-applied-configuration`，下一次 apply 可能按旧注解误删字段。`kubectl apply` 走 PATCH，不需要客户端提供 `resourceVersion`，所以统一到 apply 能同时避开这两类问题。下面的例子借一个最小 CRD 复现，因为核心资源不会触发这条校验；CRD 本身是第 33 章的主题，这里只把它当成一个会拒绝无条件更新的 API 对象。

修复方法按推荐顺序：改用 `kubectl apply -f`，让 kubectl 自己算 patch；如果确实需要 replace，先 `kubectl get <resource> <name> -o yaml > live.yaml`，保留里面的 `metadata.resourceVersion`，改完再 replace；自己发 PUT 的脚本要显式带上读到的版本。最后才是 `kubectl replace --force`，它先删后建，会短暂中断服务，也会换掉对象的 UID。不要手工编辑 `resourceVersion`，它是 API server 维护的不透明版本号，不是时间戳，也不是越大越好。

第二个故障是删除名字空间一直停在 `Terminating`。`kubectl delete namespace` 是异步的：命令返回 `deleted` 只表示删除请求被接受，名字空间控制器还要逐个删除里面的名字空间级对象。只要有一个对象因为 finalizer 删不掉，名字空间就停住。排查顺序是：先看名字空间状态和 `spec.finalizers`，再列出这个空间里还存在的对象，重点看带 `deletionTimestamp` 和 `finalizers` 的；找到具体对象后，确认 finalizer 对应的控制器是否还在工作，最后才决定是否手动清空 finalizer。不要直接改 etcd，etcd 里的键是 API server 的存储格式，绕过 API 改它可能留下不一致的缓存和引用。

列残留对象可以用 `kubectl api-resources --verbs=list --namespaced -o name` 拿到所有名字空间级、支持 list 的资源名，再逐个 `kubectl -n <ns> get <resource>`；本章示例用一个 shell 循环做这件事，只打印带 `deletionTimestamp` 的对象。也可以用 `xargs` 写成一行，但资源类型多的时候，循环更容易控制错误输出。找到对象后，`kubectl -n <ns> patch <resource> <name> --type=merge -p '{"metadata":{"finalizers":[]}}'` 清空 finalizer；如果对象本身还持有外部资源（云盘、负载均衡器、备份），要先让对应的控制器完成清理，否则清掉 finalizer 只是把问题推到下一次。

## 上生产前

清单进 Git，统一用 SSA 和固定的 field manager，生产环境禁止 `kubectl edit`。`kubectl edit` 走的是 update，不是 apply：它不会更新 `last-applied-configuration`，也不会像 SSA 那样先检查字段归属，改完就写回活对象。下一次流水线 apply 时，如果清单里没有这个字段，它可能被当成“上次清单里有、这次没有”而清掉；如果清单里有，又会把人工改动覆盖。把 `kubectl edit` 留给出故障时的临时诊断，改完必须回填到 Git；长期做法是让 CI 用 `--server-side --field-manager=ci-<service>` 写，控制器用自己的 manager，谁改了什么在 `managedFields` 里查得到。

用 label 做选择器和成本分摊，用 annotation 做变更说明。选择器标签要稳定、低基数，例如 `app.kubernetes.io/name`、`app.kubernetes.io/component`、`environment`、`team`、`cost-center`；不要放请求 ID、时间戳、每次构建都变的镜像 digest，这些值会让选择器失去意义，也会把监控指标的基数撑大。成本分摊靠 `team`/`cost-center`/`environment` 这类标签，配合账单或监控工具按标签聚合。变更说明放 annotation，例如 `kubernetes.io/change-cause: "shorty 0.2, ticket OPS-1234"`，它不影响选择，但查历史时能直接看到原因。

名字空间按团队和环境划分，并配上 ResourceQuota、LimitRange 和 NetworkPolicy。ResourceQuota 限制总量，LimitRange 给单个 Pod/容器设默认 requests/limits，NetworkPolicy 控制东西向流量；这三样加上 RBAC 和 Pod 安全性准入，才构成一套可用的隔离。仍然不要把名字空间当安全边界：它本身不阻止跨空间网络访问，也不阻止有权限的用户读别的空间的 Secret。官方建议生产集群不要把所有东西都放在 `default`，但“多建几个名字空间”不等于“已经隔离”。

删除前确认 ownerReference、finalizer 和 PDB。删 Deployment 会级联删 ReplicaSet 和 Pod，默认是 `background`：命令很快返回，Pod 在后台慢慢消失；要观察完整删除过程就用 `--cascade=foreground`，要保留 Pod 做迁移就用 `--cascade=orphan`。PDB 不会阻止 `kubectl delete`，但它会限制 drain/eviction 这类自愿中断，删工作负载前要看 PDB 和当前副本数，避免一次把可用副本清空。finalizer 只能在确认对应清理工作已经完成后手动删；namespace 卡在 `Terminating` 时，先找残留对象，不要直接改 etcd，也不要习惯性地 `--force --grace-period=0`。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `kubectl api-resources` | 列出 resource、short name、APIVERSION、是否 namespaced、kind | `--api-group`、`--namespaced`、`--verbs` 过滤 |
| `kubectl api-versions` | 列出集群提供的 group/version | 例如 `apps/v1`、`batch/v1` |
| `kubectl explain <kind>.<field>` | 查字段 schema 和说明 | `--recursive` 展开子字段，`--max-depth` 限层数 |
| `kubectl get -o wide/yaml/json/name` | 表格、完整对象、只取名字 | `name` 适合喂给循环 |
| `kubectl get -o jsonpath=...` | 按模板取字段 | 支持 `range`/`end`、`?()` 过滤；不支持正则 |
| `kubectl get -o custom-columns=...` | 自定义列表格 | 自带表头 |
| `kubectl get --sort-by=... -L <label>` | 排序、把标签作为一列 | `--show-labels` 显示全部标签 |
| `kubectl label/annotate ... --overwrite` | 改标签/注解 | 覆盖已有键必须加 `--overwrite` |
| `kubectl apply -f` | 客户端 apply，写 `last-applied-configuration` | 对象不存在时创建，存在时 patch |
| `kubectl create -f` | 命令式创建 | 对象已存在则报 `AlreadyExists`，不写 `last-applied` |
| `kubectl replace -f` | 用完整对象替换（PUT） | 清单必须带 `metadata.resourceVersion` |
| `kubectl apply --server-side --field-manager=<name>` | 服务端 apply，记录字段归属 | manager 名字要稳定、可追溯 |
| `--force-conflicts` | 冲突时覆盖并转移字段所有权 | 慎用；会从其他 manager 的条目里移除字段 |
| `--dry-run=server` | 走完整准入、校验、合并，不落盘 | 需要和真实写入相同的权限 |
| `kubectl diff -f` | 预览 apply 会改什么 | 使用 server-side dry-run；有差异时退出码为 1 |
| `kubectl delete --cascade=...` | 选级联策略 | 默认 `background`，另有 `foreground`、`orphan` |
| `kubectl patch ... -p '{"metadata":{"finalizers":[]}}'` | 清空 finalizer | 只在确认清理工作已完成时使用 |

| 字段 | 含义 |
|---|---|
| `apiVersion` / `kind` | GVK：group/version 与对象类型；核心组只写版本 |
| `metadata.name` / `generateName` | 名字或名字前缀；后者由 API server 加随机后缀 |
| `metadata.labels` | 用于选择器的标识键值对 |
| `metadata.annotations` | 非标识元数据，总值上限 256 KiB |
| `metadata.ownerReferences` | 属主引用，垃圾回收依据；不能跨名字空间 |
| `metadata.finalizers` | 删除前必须清空的键列表 |
| `metadata.resourceVersion` | 写入版本，update 用它做乐观并发控制 |
| `metadata.generation` / `status.observedGeneration` | 期望状态的代次与控制器已观测到的代次 |
| `spec` / `status` | 期望状态 / 控制器观测到的当前状态 |
| `metadata.managedFields` | SSA 的字段归属记录，默认不显示 |
