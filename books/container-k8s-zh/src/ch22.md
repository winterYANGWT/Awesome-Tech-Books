# 第 22 章 StatefulSet 与有状态应用

第 21 章把迁移和清理从 Deployment 里拆了出来，`shorty` 的数据库却还是老样子：一个 `Deployment postgres`，一份 `PersistentVolumeClaim postgres-data`，一个 `Service postgres`。单副本时它跑得很好，因为 Service 只把流量送给那一个 Pod。可是这个组合没有回答一个更基本的问题：如果这个 Pod 被删掉，新 Pod 的名字是随机后缀，IP 也是新的，副本之间靠什么认出彼此？

把副本数改成 2 会更糟。两个 Pod 都挂同一份 `ReadWriteOnce` 的 `postgres-data`，在单节点上它们会同时挂载成功，然后两个 PostgreSQL 进程争同一个数据目录；换到多节点，第二个 Pod 可能因为卷被占用而起不来。Deployment 的模型是“副本可以互换”，它不记录“哪个副本对应哪份数据”，也不保证启动顺序。数据库需要的恰好是这些：每个成员有固定名字，有固定的网络地址，有只属于自己的一份存储。

StatefulSet 就是为这三件事准备的。它给每个 Pod 一个序号、一个稳定的域名和一份由模板生成的 PVC；它在扩缩容时按序号启动和停止；它还能在删除或缩容时按策略决定 PVC 的去留。这一章从 `s2-data` 出发，先在一个隔离的命名空间里看清这三样东西，再把 `shorty` 的 PostgreSQL 从 Deployment 真正迁到 StatefulSet，最后练习强制删除和备份恢复。迁移完成后，集群进入 `s3-stateful`，后面讲 Service、存储、网络策略的章节都从这里继续。

> **起点**：本章从 `s2-data` 开始。集群里有 `Namespace shorty`、`Deployment postgres` 和 PVC `postgres-data`、`Deployment redis`、两个 api 副本、一个 worker，以及已完成的 `Job shorty-migrate`。`bash code/ch22/setup.sh` 会重建单节点 kind 集群、构建并加载 `shorty:0.1` 和 `shorty-worker:0.1`、加载 PostgreSQL/Redis/busybox 镜像并 apply `stages/s2-data`。22.1–22.3 在额外的 `sts-demo` 命名空间里做身份和保留策略实验，不碰 `shorty` 里的旧库；22.4 才迁移它。

## 22.1 稳定身份：名字、DNS、卷

StatefulSet 给 Pod 的身份由三部分组成：一个序号（ordinal）、一个稳定的网络标识、一份稳定的存储。官方文档把“稳定”定义成“跨 Pod 重新调度仍然保持”。Pod 可以被删掉、被挪到别的节点、被重建，但它拿到的名字、域名和 PVC 还是原来那套。StatefulSet 不保证 Pod 永远活着，也不保证 IP 不变；它保证的是这三样东西不随重建而改变。

名字的规则是 `<StatefulSet 名>-<序号>`，序号默认从 0 到 N-1。`postgres` 这个 StatefulSet 的 Pod 就叫 `postgres-0`、`postgres-1`。控制器还会给 Pod 加两个标签：`statefulset.kubernetes.io/pod-name` 等于 Pod 名，`apps.kubernetes.io/pod-index` 等于序号；后者方便按序号过滤日志或指标。Pod 里的 hostname 也被设成 Pod 名，这是“名字”落到进程里的方式。

网络标识来自一个 headless Service。普通 Service 有一个 ClusterIP，kube-proxy 把访问 VIP 的流量转发到后端 Pod；headless Service 把 `clusterIP` 设成 `None`，没有 VIP，DNS 直接返回后端 Pod 的地址。StatefulSet 的 `serviceName` 必须指向这样一个 Service，控制器才会给每个 Pod 注册 `<pod 名>.<service 名>.<命名空间>.svc.cluster.local` 形式的域名。以本章的演示为例，完整域名是 `postgres-0.postgres.sts-demo.svc.cluster.local`；在 `shorty` 命名空间里就是 `postgres-0.postgres.shorty.svc.cluster.local`。查 Service 名本身会返回所有 Running 且 Ready 的后端地址；查单个 Pod 的域名才能定位到具体成员。

存储来自 `volumeClaimTemplates`。它不是“ Pod 模板里的一个 volume”，而是“每个 Pod 各生成一份 PVC”的模板。模板名是 `data`、Pod 是 `postgres-0`，生成的 PVC 就叫 `data-postgres-0`；`postgres-1` 对应 `data-postgres-1`。PVC 在 Pod 调度前创建，StorageClass 决定它怎么绑定 PV。这个名字规则是后面所有保留、清理操作的基础：看到 `data-postgres-3`，就知道它属于 3 号成员。

删除前记下的 `before` 行里，UID 和 IP 都是旧 Pod 的值。`kubectl delete pod postgres-0 --wait=true` 之后，控制器立刻用同一个名字重建。`after` 行的 UID 和 IP 都变了，名字仍然是 `postgres-0`。UID 变了说明这是一个全新的 API 对象；IP 变了说明网络地址不是身份的一部分。真正没变的是三样：名字、域名、PVC。卷里那个由第一次启动写入的 `initial` 还在，说明新 Pod 挂的还是同一份数据。

这里要区分“稳定”和“不变”。名字和 PVC 的名字是稳定契约；Pod 的 UID、IP、所在节点、容器 ID 都会变。写应用时不能把成员身份存成 IP 或 UID，只能存序号或域名。反过来说，DNS 也不是瞬间生效的：官方文档提醒，如果别的客户端在 Pod 创建前查过这个名字，DNS 负缓存会让失败结果保留几秒，刚建的 Pod 可能暂时查不到。要立刻发现新成员，应该查 API，而不是只靠 DNS。

Deployment 和 StatefulSet 的差别可以压成一句话：Deployment 的 Pod 是可互换的副本，名字和存储都不跟副本走；StatefulSet 的 Pod 是有编号的成员，名字、域名和 PVC 都跟着编号走。如果应用不需要这三样中的任何一个，用 Deployment 更简单；StatefulSet 的额外约束只在需要它们时才划算。

> **旧资料提示**：更早的教程把 StatefulSet 叫 PetSet。今天的 API 只有 `StatefulSet`，旧清单里的 `kind: PetSet` 要改成 `kind: StatefulSet`；`PetSet` 这个资源类型已经不存在。

## 22.2 有序部署、缩容与更新

StatefulSet 的默认 `podManagementPolicy` 是 `OrderedReady`。它的规则可以概括成三句话：创建时按序号从 0 到 N-1，前一个 Pod 必须 Running 且 Ready 才创建下一个；缩容时按序号从 N-1 到 0 终止，后一个 Pod 完全终止才删下一个；扩容时新成员要等所有前任 Ready。`minReadySeconds` 如果设了，还要在 Ready 之后多等这么久才算可用。

这条规则解决了数据库集群里最常见的启动依赖：0 号成员先起来并完成初始化，1 号成员才知道该连谁；反过来缩容时先停编号最大的成员，集群的成员列表不会出现空洞。代价是启动慢：N 个副本要一个一个来，任何一个卡住，后面的都不会创建。StatefulSet 不会跳过坏掉的成员去创建下一个，这是“有序”的一部分，不是故障。

第一张表的 `CREATED` 只有 `postgres-0` 一行。`kubectl scale` 把期望副本数改成 2 后，`rollout status` 先打印 `Waiting for 1 pods to be ready...`，再打印 rollout 完成；这不是重复输出，而是控制器在等第一个新成员就绪。第二张表里多出 `postgres-1`，它的 `CREATED` 明显晚于 `postgres-0`。只看最终状态看不出“等 0 号 Ready 才建 1 号”，但把两张表的时间戳和控制器日志放在一起，顺序就出来了：0 号先存在，1 号是后来创建的。

PVC 表里出现 `data-postgres-0` 和 `data-postgres-1` 两个 Bound 的卷。它们不是 StatefulSet 对象里的一个共享卷，而是 `volumeClaimTemplates` 按 Pod 各生成一份。`postgres-1` 被删除后 `data-postgres-1` 仍然留着，这是下一节的主题；在这里先记住：副本数和 PVC 数不是一回事，PVC 的生命周期不跟着 Pod 走。

缩容的过程更能说明“逆序”。`kubectl scale --replicas=1` 之后，脚本没有立刻去读状态，而是先 `wait --for=delete pod/postgres-1`，再等 `status.readyReplicas` 回到 1。`get pod,pvc` 里只剩 `postgres-0` Running，两个 PVC 都还在；`get statefulset` 的 `REPLICAS 1`、`CURRENT 1`、`READY 1` 说明控制器已经接受新的期望值，`STRATEGY RollingUpdate` 是默认更新策略。缩容时先终止 1 号，再考虑 0 号；这里 0 号本来就要保留，所以只看到 1 号离开。

`podManagementPolicy: Parallel` 是另一条路。它保留每个 Pod 的唯一名字和存储，但创建和删除不再互相等待：所有成员一起拉起，一起终止。滚动更新时，只有 `maxUnavailable` 大于 1 才会并行替换多个 Pod。它适合成员之间没有启动依赖的场景，比如一组各自处理分片的 worker；不适合主从数据库，因为从库可能在主库还没 Ready 时就去连它，然后进入 CrashLoop。选 `Parallel` 的前提是应用自己能处理“成员随时出现或消失”，而不是为了把启动时间从 30 秒压到 5 秒。

更新策略默认也是 `RollingUpdate`，顺序和终止相反：从序号最大的 Pod 开始，一次更新一个，等它 Running 且 Ready 再更新下一个。`kubectl rollout status statefulset/postgres` 看的就是这个过程。`kubectl rollout history` 和 `kubectl rollout undo` 也能用，StatefulSet 用 ControllerRevision 保存模板历史，`revisionHistoryLimit` 默认保留 10 个修订。

`updateStrategy.rollingUpdate.partition` 用来做分阶段升级。设成 2，表示序号大于等于 2 的 Pod 更新到新模板，序号小于 2 的保持旧版本；即使这些旧 Pod 被删掉，重建出来仍然是旧版本。把 partition 从 N 逐步降到 0，就能一批一批地升级；设成大于副本数的值，模板更新完全不会下发。它适合“先升级一个从库观察，再升级其余成员”的流程，但要求应用能接受新旧版本同时存在。

有序更新有一个官方文档明确写出的坑：如果新模板本身有问题，Pod 永远起不来，StatefulSet 会停在那里等它 Ready。这时只把模板改回旧版本不够，控制器还在等那个坏 Pod；必须把已经用坏模板创建的 Pod 删掉，控制器才会用回滚后的模板重建。官方把这叫 forced rollback，排障时先看 `rollout status` 卡在哪个序号，再决定删哪个 Pod。

还有两个操作细节。第一，`kubectl apply` 一份没写 `replicas` 的清单，会把手工 `kubectl scale` 出来的副本数覆盖回清单里的值（通常是 1）；扩缩容后如果要保留，清单和集群要同步。第二，单实例数据库的 PVC 访问模式，官方文档建议生产用 `ReadWriteOncePod`，它比 `ReadWriteOnce` 更严格，能保证同一时刻只有一个 Pod 挂载这份卷；`ReadWriteOnce` 在单节点上可能被两个 Pod 同时挂上，正是 22.6 要利用的缝隙。

## 22.3 volumeClaimTemplates 与保留策略

`volumeClaimTemplates` 生成的 PVC 名字是 `<模板名>-<Pod 名>`。这个命名不是装饰：StatefulSet 重建 Pod 时按这个名字去找 PVC，找到了就复用，找不到才创建。所以 `data-postgres-0` 必须一直存在，`postgres-0` 才能拿回自己的数据；如果手工把 PVC 改名或删掉，控制器会创建一个空的替代品，数据库看到的是“初始化一个新库”，不是原来的数据。

PVC 的创建时机取决于 StorageClass 的 `volumeBindingMode`。kind 自带的 `standard` 是 `WaitForFirstConsumer`，PVC 先 Pending，等 Pod 调度到某个节点后才绑定该节点上的 PV；`Immediate` 模式则在 PVC 创建时立刻绑定。两种模式下，StatefulSet 都是先创建 PVC 再调度 Pod，只是“Bound”出现的时间不同。看到 PVC 短暂 Pending 不一定是故障，要结合 StorageClass 和 Pod 事件判断。

默认的保留策略是“都保留”。删掉 StatefulSet，Pod 会被级联删除，PVC 不会跟着删；缩容时也一样，被缩掉的成员的 PVC 留在集群里。要注意，删除 StatefulSet 对象时官方不保证 Pod 按逆序优雅终止；需要顺序停机，就先 `scale --replicas=0` 再删对象。下面的例子把 22.2 留下的两个 PVC 和 StatefulSet 分开：

如果要让 PVC 跟着 StatefulSet 走，用 `persistentVolumeClaimRetentionPolicy`。它有两个维度：`whenDeleted` 管整个 StatefulSet 被删除时，`whenScaled` 管缩容时；每个维度可以取 `Delete` 或 `Retain`，默认都是 `Retain`。这个字段从 Kubernetes 1.23 的 alpha 走到 1.27 的 beta，在 1.32 转为 stable；1.32 及以后的集群不需要再开特性门控。

> **旧资料提示**：旧教程常说“StatefulSet 的 PVC 永远保留”。默认行为确实是 `Retain`，但从 1.32 起可以用 `persistentVolumeClaimRetentionPolicy` 把 `whenDeleted` 或 `whenScaled` 设成 `Delete`；保不保留要看清单，不是永远。

`get pvc` 用 `custom-columns` 取 `ownerReferences[0]`，两行的 owner 都是 `StatefulSet/postgres`。这是策略生效的机制：控制器给 PVC 加上指向 StatefulSet 的属主引用，删除 StatefulSet 后，垃圾回收器等对应的 Pod 终止，再回收 PVC。`delete statefulset` 之后两次 `wait --for=delete pvc` 都返回 `condition met`，最后的 `get pvc` 是 `No resources found`。PVC 底下的 PV 会按 StorageClass 的回收策略继续处理：动态供应的 PV 默认继承 StorageClass 的 `reclaimPolicy`，`Delete` 会连后端存储一起删，`Retain` 则留下一个 `Released` 的 PV 等管理员手工处理。

`whenScaled: Delete` 的语义更窄：只有“因为缩容而被删除的 Pod”对应的 PVC 会被回收。节点故障后控制器补一个新 Pod、用户手工 `kubectl delete pod`、滚动更新换 Pod，这些情况都不触发 `whenScaled`，PVC 仍然保留给替代的 Pod。官方文档特别说明，策略只对 StatefulSet 删除或缩容造成的 Pod 移除生效；不要把 `whenScaled: Delete` 当成“Pod 一删就清卷”的开关。

对数据库来说，`whenDeleted: Delete` 很方便，也很危险。它让“删 StatefulSet”变成“删数据”，而且这个动作可能只比 `kubectl delete` 多几秒。默认的 `Retain` 更安全，代价是清理时要多一步：先确认备份，再删 StatefulSet，再按名字删 PVC，最后看 PV 是被回收还是留在 `Released`。删 PVC 不等于删 PV，删 PV 也不一定删后端存储，这三层要分开看。

还有一个常见误解：`persistentVolumeClaimRetentionPolicy` 是生命周期管理，不是备份。它只能决定“删的时候留不留”，不能防止误删表、写坏数据、PVC 被手工删除或整个命名空间被删。下一节迁移时会把旧 PVC 留着做回滚点，但真正的数据安全仍然要靠 22.7 的备份和恢复演练。

## 22.4 单实例 PostgreSQL 的迁移

`shorty` 的 PostgreSQL 是单实例：`Deployment postgres` 1 副本，`strategy: Recreate`，挂 PVC `postgres-data`，前面是 `Service postgres`。api 和 worker 通过 ConfigMap 里的 `postgres://shorty@postgres:5432/shorty` 连它。单实例用 Deployment 并不是错误，官方甚至有一个“单实例有状态应用”的教程就是这么做的；它的问题是名字不稳定、没有按成员的 PVC 模板、也没法平滑地扩成多副本。迁移到 StatefulSet 是把这些能力补上，不是换一个更高级的控制器。

迁移的核心不是“把 Deployment 改成 StatefulSet”这一行，而是“数据怎么从旧卷到新卷，怎么证明没丢”。StatefulSet 的 `volumeClaimTemplates` 会创建一份全新的空卷 `data-postgres-0`，它不会自动接管旧的 `postgres-data`。所以必须做一次备份和恢复，并且在切换前后核对数据。下面的步骤把写入方停掉，用 Job 做 dump 和 restore，避免手工进 Pod 执行命令。

第一步是停写。api 和 worker 是仅有的写入方；把它们缩到 0，迁移期间就不会有新链接或点击计数进旧库：

接下来用 `Job pg-seed` 写入 3 行固定数据。日志里的 `INSERT 0 3` 是 PostgreSQL 对插入的返回，`links rows: 3` 是迁移前的基准行数。这 3 行是演示数据，真实迁移时应该用业务表里已有的数据；关键是先记下一个可核对的数量或校验和，恢复后再比一次。

备份 Job 把 `pg_dump -Fc` 的输出写到独立的 PVC `postgres-backup`，日志里只打印文件大小（2 KB 左右）。`-Fc` 是 PostgreSQL 的自定义格式，包含 schema、数据和索引，恢复时要用 `pg_restore`，不能直接喂给 `psql`。备份卷和数据库卷分开，删 StatefulSet 时不会连带删掉备份；但它仍在同一个集群、同一个 StorageClass 上，生产环境还要把文件复制到对象存储或另一套存储里。

然后删掉旧的 Deployment。`delete deployment postgres` 之后，`wait --for=delete pod` 确认旧 Pod 终止，`get pvc postgres-data` 显示它仍然是 `Bound`。这一步是回滚点：旧数据没有被删，只是没有 Pod 在用它。保留它，直到新库验证通过并且业务运行了一段时间。

Service 不能原地从 ClusterIP 改成 headless，`clusterIP` 是创建后不可变的字段，所以先 `delete service postgres`，再 apply 新的 headless Service。这个短暂的空窗对 api 没有影响，因为 api 已经是 0 副本；如果换成不能停机的系统，就不该复用同名 Service，而应该建一个新名字的 Service，改应用配置后再切。新 Service 的 selector 仍然是 `app.kubernetes.io/name: postgres`，但此时旧 Deployment 已经删除，后端只剩即将创建的 `postgres-0`。

`postgres-sts.yaml` 里有四样和旧 Deployment 不同的东西：`serviceName: postgres` 指向 headless Service；`volumeClaimTemplates` 里的 `data` 生成 `data-postgres-0`；`persistentVolumeClaimRetentionPolicy` 显式写成 `Retain/Retain`，避免误删；容器模板沿用原来的 PostgreSQL 镜像、环境变量、Secret 挂载和 readiness 探针。`rollout status` 等到 `postgres-0` Ready，`get pod,pvc` 里能看到新 Pod 和 `data-postgres-0`，同时旧的 `postgres-data` 和备份卷 `postgres-backup` 都还在。

恢复 Job 连的是 headless Service，`pg_restore --no-owner` 把 schema 和数据写进新库，日志最后一行是 `links rows after restore: 3`，和迁移前的 3 一致。`--no-owner` 是因为备份里的属主可能和集群里的角色名不完全对应；单实例演示里两者都叫 `shorty`，但生产里常常需要显式映射。

数据一致不代表应用能用。脚本把 api 扩回 2、worker 扩回 1，等 Deployment 就绪，再用一个 busybox Job 从集群内部访问 `http://api:8080/readyz`，日志是 `ok`。这个检查同时覆盖了 api 到 PostgreSQL 和 Redis 的连接；如果 Service 名字、端口或密码文件挂错，`/readyz` 会返回 503 并说明原因，而不是让用户先发现。

最后的 `get statefulset,pod,service,pvc` 里，`postgres` 是 `1/1` Ready，Service 的 `CLUSTER-IP` 是 `None`，`data-postgres-0` 是 `Bound`；EndpointSlice 的 `ADDRESSES` 是 `postgres-0` 的地址，`PORTS` 是 5432。旧 PVC `postgres-data` 还在列表里，这是有意保留的回滚点，不是忘记清理。确认新库稳定后，再按 22.3 的步骤删旧 PVC。

回滚方案要提前想清楚：如果新库校验失败，把 api/worker 再缩到 0，删掉 StatefulSet（保留 `data-postgres-0` 供排查），重新创建原来的 Deployment 并挂 `postgres-data`，把 Service 改回 ClusterIP。切换之后新库如果已经接受写入，这些写入不会自动回到旧库；回滚会丢这一段数据。所以要么在切换时保持停写直到验证通过，要么接受“回滚丢增量”，要么做双向同步——单实例迁移通常选第一种。

这套流程的边界也要说清楚：`pg_dump`/`pg_restore` 是逻辑备份，适合中小数据库；数据量大时 dump 时间和恢复时间会线性增长，期间必须停写。更大的数据库要用物理备份、持续 WAL 归档或存储快照，这些是第 26 章和备份系统的事。StatefulSet 在这里提供的是稳定的新家，不是零停机迁移工具。

## 22.5 故障与强制删除

节点失联时，Pod 不会立刻从 API 里消失。kubelet 停止上报后，Node 控制器先把节点标成 `NotReady`，Pod 在一段时间后进入 `Unknown` 或 `Terminating`；如果节点只是网络分区，恢复后 kubelet 会自己完成删除。官方文档给出的处理顺序是：确认节点真的死了（断电、永久断网），就删掉 Node 对象；只是分区，就等它恢复或修复网络；只有这两种都做不到时，才考虑强制删除 Pod。

强制删除的命令是 `kubectl delete pod <pod> --force --grace-period=0`。它的关键不是“删得快”，而是“不等待 kubelet 确认容器已经停止”。API 会立刻释放 Pod 名字，StatefulSet 控制器看到名字空出来，就会创建同名的替代 Pod。如果旧容器还在运行、还能写卷，替代 Pod 也挂同一个 PVC，就会出现两个同身份成员同时写一份数据。官方把这叫违反 StatefulSet 的“至多一个”语义，后果可能是数据损坏或 quorum 系统的 split brain。

`delete` 的输出里有一行警告：立即删除不等待确认，资源可能继续在集群里运行。命令返回后，脚本轮询 `postgres-0` 的 UID，直到它变成新值，再等新 Pod Ready。`before` 和 `after` 两行的 UID、IP 都不同，名字都是 `postgres-0`，`get pvc data-postgres-0` 仍然是同一个 `Bound` 卷。也就是说，StatefulSet 在几秒内就把身份重新挂到了一个全新的 Pod 上，没有任何“旧 Pod 是否停了”的检查。

为了把风险显形，脚本又创建了一个 `pg-duplicate` Pod，直接挂 `data-postgres-0`，跑同一个 PostgreSQL 镜像。它没有被调度器拒绝，也没有被准入控制拦住；日志显示它发现数据目录里已有数据库，跳过初始化，做了自动恢复，最后打印 `database system is ready to accept connections`。在这个 lab 里，第二个 postmaster 真的起来了，两个进程同时对着同一份数据目录。Kubernetes 只保证“同一时间最多一个同名 Pod 对象”，它不保证“同一份数据上最多一个数据库进程”；后者要靠存储的访问模式、数据库自己的锁或 Operator 来保证，而这里的 `ReadWriteOnce` 在单节点上并没有阻止两个 Pod 挂同一个卷。

这个演示在 `get pod` 显示 Running 后立即删除了 `pg-duplicate`，没有让它继续写。生产环境绝不能这样试：正确顺序是先隔离旧节点（关机、断网、从负载均衡摘掉），确认旧 Pod 不可能再联系集群或写存储，再强制删除；如果节点确认死亡，优先删 Node 对象，让控制器按正常流程清理。若 Pod 卡在 `Unknown`，官方还给出 `kubectl patch pod <pod> -p '{"metadata":{"finalizers":null}}'` 作为最后手段，它只移除 API 里的对象，同样不处理还在运行的容器。

还有一条硬规则：StatefulSet 的 Pod 模板不要设 `terminationGracePeriodSeconds: 0`。官方文档明确说这做法不安全，会跳过优雅终止，让数据库来不及 flush 和关闭连接；强制删除是例外手段，不是默认配置。

多副本数据库的 split brain 不是 `kubectl` 能解决的问题。StatefulSet 提供稳定名字、顺序和卷，不提供选主、quorum、复制或 fencing。PostgreSQL 主从、etcd、Kafka 这类系统要靠自身的 quorum 和租约，或者用 Operator 把“旧主隔离、提升新主”做成受控流程；只靠 StatefulSet 的序号，两个成员都认为自己是主时，谁也无法裁决。

## 22.6 备份与恢复

StatefulSet 的 PVC 不是备份。PVC 保护的是“Pod 重建后数据还在”，它和 Pod 在同一个集群、同一个存储系统、同一个故障域里；误删表、写坏数据、PVC 被删、命名空间被删、存储后端故障，这些场景它都救不了。`persistentVolumeClaimRetentionPolicy` 更不是备份，它只决定删除时 PVC 跟不跟着走。

备份分两类。逻辑备份用 `pg_dump` 导出 SQL 或自定义格式，恢复时用 `pg_restore` 或 `psql`；它跨版本、跨平台，能只备份一个库或一张表，但数据量大时慢。物理备份直接复制数据文件或打存储快照，快、适合大库，但和 PostgreSQL 版本、文件系统、存储系统绑定。Kubernetes 的 `VolumeSnapshot` 属于后者：它通过 CSI 驱动给卷打快照，需要 `VolumeSnapshot`、`VolumeSnapshotContent`、`VolumeSnapshotClass` 这些 CRD，以及快照控制器和 CSI sidecar；这些不是核心 API，本书的 kind 环境也没有安装快照 CRD 和 CSI 快照驱动，所以本章只能用逻辑备份。快照的细节放在第 26 章。

> **旧资料提示**：用 `emptyDir` 存 Cassandra 或数据库数据。`emptyDir` 的生命周期跟着 Pod：容器崩溃不丢，Pod 从节点上删除就永久丢失；数据库必须用 PVC/CSI 提供的持久卷。

`pg-count` 先确认当前是 3 行。备份 Job 把同一个数字再打印一次（`links rows before backup: 3`），然后把 `pg_dump -Fc` 写到 `/backup/shorty-backup.dump`；文件 2 KB 左右，因为只有 3 行和一张小表。`get pvc postgres-backup` 显示备份卷是独立的 `Bound` PVC，和 `data-postgres-0` 不是同一份。

然后 `pg-drop` 执行 `DROP TABLE links;`，日志里的 `DROP TABLE` 是 PostgreSQL 的返回，`links table dropped: t` 说明 `to_regclass('links')` 已经是 NULL。这一步模拟误操作；在真实事故里，表可能是被 `DELETE` 清空、被错误的迁移改坏，或者整个库被删，恢复步骤类似，但“恢复到哪个时间点”要先想清楚。

恢复 Job 用 `pg_restore --no-owner` 把 dump 写回去，日志显示 `links rows after restore: 3`，和删除前一致。同一段脚本用 `date +%s` 在 `pg_restore` 前后取时间，最后一行打印 `RTO: <秒数>s`。这次的数字接近 0，不是“恢复不需要时间”，而是只有 3 行、卷在本地、镜像已预热，`pg_restore` 和计数落在同一个秒里；RTO 要以真实数据量和真实存储测，不能用这个数字做容量规划。RTO 指从故障到服务恢复的时间，RPO 指最多能丢多少数据；逻辑备份的 RPO 是“最后一次成功备份”，不是 0。

最后一步是应用连通性。恢复 Job 只证明了表和数据回来了，脚本又跑了一个 busybox Job 访问 `/readyz`，输出 `ok`。恢复演练如果只做 `SELECT count(*)`，会漏掉密码、Service、连接串、迁移版本这些问题；至少要让一个真实客户端走一遍读和写。

这套流程放到生产还要补三件事。第一，备份文件要离开集群：写到对象存储、另一套集群或离线介质，并校验可读；只存在 `postgres-backup` 这个 PVC 上，集群没了备份也没了。第二，备份要定时：用第 21 章的 CronJob 每天或每小时跑一次 `pg_dump`，失败要告警，历史文件要按保留策略清理。第三，恢复要演练：定期在独立的命名空间或独立数据库里恢复一份，核对行数、关键查询和应用连通，而不是等真出事时第一次执行 `pg_restore`。

对写入频繁的库，逻辑备份要挑低峰期；大库要考虑物理备份加 WAL 归档做时间点恢复（PITR）。这些超出单实例 StatefulSet 的范围，但方向要提前定：StatefulSet 负责让数据库有一个稳定的家，备份系统负责让这个家可以重建。

`get pod` 里 `postgres-bad-0` 是 `Pending`，`get pvc` 里 `data-postgres-bad-0` 也是 `Pending`。`describe pvc` 的事件直接写出 `storageclass.storage.k8s.io "does-not-exist" not found`，`describe pod` 的调度事件则说它在等一个绑不上的 PVC。两个对象一起看，就能把“容器起不来”和“卷没准备好”分开；只重启 Pod 或重拉镜像没有用，要先修 StorageClass 或 PVC。`kubectl describe pod postgres-0` 的 `Events` 里常见 `pod has unbound immediate PersistentVolumeClaims`，再 `kubectl describe pvc data-postgres-0` 就能看到更具体的原因：`storageclass.storage.k8s.io "xxx" not found` 表示清单里的 `storageClassName` 写错了或集群没装这个 StorageClass；`no persistent volumes available for this claim and no storage class is set` 表示没有默认 StorageClass，也没有现成的 PV 可匹配。先 `kubectl get storageclass` 确认名字和默认标记，再决定是改 PVC 还是补 StorageClass。

`WaitForFirstConsumer` 的 StorageClass 会让 PVC 在 Pod 调度前保持 Pending，这是正常的，不要把它当成绑定失败；等 Pod 被调度后 PVC 才会 Bound。反过来，如果 PVC 已经 Bound、Pod 还是 Pending，就看 `describe pod` 的调度事件：节点资源不足、`nodeSelector` 不匹配、污点没有容忍、命名空间配额不够，都会显示在 `FailedScheduling` 的 message 里。`kubectl get events --sort-by=.lastTimestamp` 能把 PVC、调度器、kubelet 的事件按时间排在一起，比只看 Pod 状态有用。

删了 StatefulSet 之后 PVC 还在，这是默认行为，不是“删除失败”。22.3 已经看到：`whenDeleted` 和 `whenScaled` 默认都是 `Retain`，控制器只删 Pod，卷留给下一次恢复或人工处理。要清理就显式删 PVC，例如 `kubectl delete pvc data-postgres-0`；如果 PVC 卡在 `Terminating`，先确认没有 Pod 还在挂它，`kubernetes.io/pvc-protection` finalizer 会等 Pod 终止后才放行。删 PVC 之后 PV 是否消失，取决于 PV 的 `reclaimPolicy`：`Delete` 会连后端存储一起回收，`Retain` 会留下 `Released` 的 PV，需要管理员手工清理或重新绑定。

迁移后 api 连不上，先查 Service 的 selector，而不是先改连接串。`kubectl get service postgres -o yaml` 看 `spec.selector`，`kubectl get pod postgres-0 --show-labels` 看 Pod 的实际标签；两边对不上时，Service 的 EndpointSlice 是空的，DNS 能解析出 Service 名但没有后端地址。`kubectl get endpointslice -l kubernetes.io/service-name=postgres` 看 `ADDRESSES` 是否为空，比 `curl` 更快定位。另一个常见问题是旧 Deployment 的 Pod 还带着同样的标签，Service 把流量分给了旧库；迁移时先删旧 Deployment 或给它换标签，确认 EndpointSlice 里只剩 `postgres-0`。

headless Service 的名字还必须和 StatefulSet 的 `serviceName` 完全一致，命名空间也要一致。`postgres-0.postgres.shorty.svc.cluster.local` 里，第一个 `postgres` 是 Pod 名，第二个是 Service 名，第三个是命名空间；改错任何一段，解析都会失败。应用如果只写 `postgres`，它走的是 Service 名，不依赖 Pod 的 FQDN；要直连某个成员时才用完整域名。

最后，滚动更新卡住时先看 `kubectl rollout status statefulset/postgres` 停在哪个序号，再 `kubectl describe pod` 看那个 Pod 为什么不 Ready。如果是新模板本身坏了，按 22.2 的 forced rollback 处理：先把模板改回去，再删掉用坏模板创建的 Pod，控制器才会继续。

## 上生产前

**单实例 StatefulSet 只是起点，不是生产数据库的完整方案。** 它给你稳定名字、稳定卷和有序启停，但不提供主从切换、故障检测、备份调度和 fencing。生产里优先用托管数据库或成熟的 Operator；如果必须自己管，至少把备份、恢复演练、监控和升级流程补齐，再谈多副本。StatefulSet 能保证“同一个名字同一份卷”，不能保证“这份卷里的数据是对的”。

**PVC 保留策略要显式写，删 StatefulSet 前先备份。** 默认的 `Retain/Retain` 会在删 StatefulSet、缩容后留下 PVC，容易积累孤儿卷；`whenDeleted: Delete` 又会让删除动作连带删数据。两种都不是“默认安全”，要在清单里写清楚并让团队知道。删 StatefulSet 之前先确认备份可恢复，不要依赖“默认保留”当保险。

**数据库数据不要放 `emptyDir`，也不要放 `hostPath` 做跨节点持久化。** `emptyDir` 随 Pod 删除永久丢失，容器崩溃不丢、Pod 被删就丢；`hostPath` 把数据绑在某个节点的目录上，Pod 被调度到别的节点就看不到，节点损坏也无法恢复。用 PVC 加 CSI 或动态供应，单实例优先 `ReadWriteOncePod`，它比 `ReadWriteOnce` 更能保证同一时刻只有一个 Pod 挂载。

**强制删除只在确认旧 Pod 不再写卷时使用。** 节点确认死亡就删 Node 对象，网络分区就等恢复；`--force --grace-period=0` 是最后手段。删之前隔离旧节点、确认 kubelet 不会再启动容器，删之后检查新 Pod 是否真的独占卷。多副本数据库的选主和 split-brain 交给数据库或 Operator，不要指望 StatefulSet 的序号。

**备份要存到集群外，并定期做恢复演练。** 备份 PVC 和数据库在同一个集群、同一个 StorageClass 上，集群级故障会一起带走；把 dump 复制到对象存储或另一套环境，定期在独立命名空间恢复并验证行数、关键查询和 `/readyz`。用 RTO 和 RPO 说话：逻辑备份的 RPO 是最后一次成功备份，大库要物理备份加 WAL 归档才能做到更小。

**更新要有顺序和回退方案。** 用 `OrderedReady` 加 readinessProbe，让新版本真正能服务再动下一个；需要分批时用 `partition`，先升一个从库观察。不要把 `terminationGracePeriodSeconds` 设成 0，数据库需要时间 flush 和关闭连接。镜像写具体 tag，清单提交到版本控制，手工 `kubectl scale` 的结果会被下一次 apply 覆盖。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `serviceName` | 指定管理 Pod DNS 的 headless Service | 必填；Service 要自己创建，`clusterIP: None` |
| `podManagementPolicy` | `OrderedReady` 或 `Parallel` | 默认 `OrderedReady`；Parallel 不等待成员就绪 |
| `volumeClaimTemplates` | 为每个 Pod 生成 PVC | PVC 名 `<模板名>-<Pod 名>`，如 `data-postgres-0` |
| `persistentVolumeClaimRetentionPolicy` | 控制删除/缩容时 PVC 去留 | 默认 `Retain/Retain`；1.32 stable |
| `updateStrategy.type` | `RollingUpdate` 或 `OnDelete` | 默认 `RollingUpdate`，从最大序号往下更新 |
| `updateStrategy.rollingUpdate.partition` | 只更新序号大于等于它的 Pod | 不设则全部更新；用于分阶段升级 |
| `minReadySeconds` | Pod Ready 后至少多久算可用 | 默认 0；影响滚动更新节奏 |
| `replicas` | 期望成员数 | 默认 1；`kubectl apply` 会覆盖手工 scale |
| `kubectl rollout status sts/postgres` | 等 StatefulSet 更新完成 | 卡住时按序号查 Pod |
| `kubectl scale sts/postgres --replicas=N` | 扩缩容 | 缩容按序号从大到小 |
| `kubectl delete pod postgres-0 --force --grace-period=0` | 强制删除成员 | 立即释放名字，不等待 kubelet 确认 |
| `kubectl get endpointslice -l kubernetes.io/service-name=postgres` | 看 Service 的后端 | 为空通常是 selector 不匹配或 Pod 未 Ready |
| `kubectl wait --for=delete pvc/data-postgres-0` | 等 PVC 真正删除 | `whenDeleted: Delete` 时用 |

本章结束时，`shorty` 的 PostgreSQL 已经换成 `StatefulSet postgres`（1 副本）、headless `Service postgres` 和 PVC `data-postgres-0`，数据迁移和恢复演练都通过；旧 PVC `postgres-data` 还留着作回滚点，确认无误后按 22.3 的步骤删除。redis（1 副本）、worker（1 副本）、api（2 副本）和已完成的 `Job shorty-migrate` 保持原样。下一章从 `s3-stateful` 开始，讲 Service 的几种暴露方式和 EndpointSlice。
