# 第 19 章 Pod：多容器、init、原生 sidecar（1.33 GA）、探针、优雅终止

第 18 章结束时，shorty 的 api 是 `shorty` 命名空间里的一个单容器 Deployment，配置来自 ConfigMap，对象用 SSA 管理。它能启动，也能通过 Service 访问，但 Kubernetes 对它的健康几乎一无所知：容器进程退出，kubelet 会按 `restartPolicy` 重启；进程还在、HTTP 已经卡死，或者数据库连不上，Kubernetes 看不出来。Deployment 判断 Pod 可用的依据也只是“容器已经启动”，而不是“应用真的能处理请求”。

这带来两个直接的问题。第一，滚动更新或扩容时，新 Pod 刚一启动就可能被加入 Service 的 EndpointSlice，而它可能还在加载数据、建立连接，第一批请求于是打到还没准备好的进程上。第二，进程僵死时没有东西能把它拉回来，只能等人发现。探针就是为这两个问题准备的：readiness 决定要不要给这个 Pod 发流量，liveness 决定要不要重启容器，startup 给慢启动应用一段专门的宽限期。

这一章还回答一个更基础的问题：为什么同一个 Pod 里的两个容器可以用 `localhost` 互相访问，而不同 Pod 的容器不行？答案在 Pod 的共享执行环境里。理解这一点之后，init 容器、原生 sidecar、共享卷这些“多容器”用法才有共同的判断标准。最后，Pod 被删除时并不是“说没就没”：从 Endpoint 摘除、发 SIGTERM、等待宽限期、必要时 SIGKILL，每一步都影响正在处理的请求。

> **起点**：第 18 章结束。`shorty` 命名空间里有 `s1-api` 的 Deployment、Service 和 ConfigMap，api 是单容器、没有探针。`bash code/ch19/setup.sh` 会建一个单节点 kind 集群、构建并加载 `shorty:0.1`、apply `s1-api`，再把本章要用的 `busybox:1.37` 预拉进节点；本章后面的示例都在这个状态上继续。

## 19.1 Pod 是共享执行环境，不是容器组

把 Pod 叫“容器组”容易让人以为它只是把几个容器打包在一起。官方定义强调的是“共享上下文”：一个 Pod 里的容器被放在同一台机器上，共享一组 Linux namespace、cgroup 和存储卷，并且作为一个整体被调度。这个共享上下文才是 Pod 的本质；“容器组”只是它的一种外观。

具体到 Linux，Pod 里的容器共享 network、UTS 和 IPC namespace。共享 network namespace 意味着它们看到同一张网卡、同一个 IP、同一段端口空间，所以一个容器监听 8080，另一个容器用 `localhost:8080` 就能访问；也意味着两个容器不能同时监听同一个端口。共享 UTS namespace 意味着它们看到同一个 hostname，默认就是 Pod 的名字。共享 IPC namespace 意味着它们可以用 SystemV 信号量或 POSIX 共享内存通信，而不同 Pod 的容器默认做不到。除此之外，默认情况下每个容器仍然有自己的 PID namespace 和 mount namespace（`shareProcessNamespace: true` 可以改变 PID 这一项）：在容器 A 里 `ps` 看不到容器 B 的进程，两个容器也可以有同名但内容不同的 `/etc/config`。卷是另一条共享通道：同一个 `emptyDir` 或 ConfigMap 卷可以挂进多个容器，它们看到的是同一份文件。

network namespace 不是凭空来的。kubelet 让容器运行时先创建一个 Pod sandbox（沙箱），也就是常说的 pause 容器；sandbox 持有 Pod 的 network namespace，CNI 插件把网卡和 IP 配到它里面，之后创建的业务容器再加入这个 namespace。Pod 的 `PodReadyToStartContainers` condition 就表示 sandbox 建好、网络配好、卷挂好，可以开始拉镜像、建容器了。所以“Pod 的 IP”严格来说是 sandbox 的 IP，业务容器只是共用。

最后一段在 kind 节点上直接问容器运行时：用 `crictl` 找到 sandbox 和两个容器的 PID，再读 `/proc/<pid>/ns/net`。三行 netns 指向同一个 namespace，说明 sandbox、server、client 确实在同一个网络栈里。这个检查依赖节点上的 `crictl` 和权限，平时排障不需要这么做；它的价值是把“共享 network namespace”从文档里的说法变成可观察的事实。

Pod 是最小调度单元，这句话有两层意思。第一，调度器以 Pod 为单位选节点，Pod 里的容器一定在同一台机器上，不能一个在节点 A、一个在节点 B。第二，Pod 一旦绑定到节点，就不会被“重新调度”到另一个节点；节点挂了，Pod 会被删除，由上层控制器创建一个新的、名字可能相同但 UID 不同的 Pod。容器重启只发生在同一个 Pod 内、同一台节点上，Pod 本身不迁移。

于是“这些容器分开到不同机器还能工作吗”成了一个实用的拆分判据。如果两个进程通过 Service、数据库连接或消息队列通信，分开之后仍然能工作，它们就应该是两个 Pod，各自扩缩容、各自滚动更新、各自失败。api 和 PostgreSQL 是典型：它们通过 TCP 通信，数据库有自己的持久化和生命周期，塞进一个 Pod 只会让扩缩容和故障隔离变糟。反过来，一个读共享 `emptyDir` 的日志收集器、一个把 `/metrics` 转成另一种格式的 adapter、一个在 `localhost` 上给主容器做 TLS 终止的代理，离开同一个 Pod 就没有意义，它们才适合放在一起。

## 19.2 生命周期、阶段与重启策略

Pod 的 `status.phase` 只有五个值，官方文档对每个值都给了明确的边界：

| phase | 含义 |
|---|---|
| `Pending` | Pod 已被集群接受，但还有一个或多个容器没有建好、没有准备好运行；包括等待调度和下载镜像的时间 |
| `Running` | Pod 已绑定到节点，所有容器都已创建，至少有一个容器还在运行，或者正在启动、重启 |
| `Succeeded` | 所有容器都以成功状态退出，并且不会再被重启 |
| `Failed` | 所有容器都已终止，至少有一个容器以失败状态终止，并且不会再被重启 |
| `Unknown` | 无法取得 Pod 状态，通常是与节点通信出错 |

这五个值是数据模型的一部分，含义被严格限定；除了文档写明的，不要从某个 phase 推断更多东西。`kubectl get pods` 里看到的 `CrashLoopBackOff`、`Terminating` 不是 phase，而是 kubectl 为了方便人看而显示的 Status：前者表示容器在崩溃循环里、kubelet 正在退避等待，后者表示 Pod 正在删除。排障时把 Status 当成 phase，就会得出“Pod 处于 CrashLoopBackOff 阶段”这种不存在的说法。

每个容器自己还有三个状态。`Waiting` 是还没有进入运行或终止，例如正在拉镜像、挂 Secret；`Running` 是进程在跑，如果配了 `postStart`，它已经执行过；`Terminated` 是曾经运行过、现在结束了，会带原因、退出码和起止时间。`kubectl describe pod` 会把每个容器（包括 init 容器）的状态分开列出，判断“是 Pod 起不来”还是“某个容器起不来”，要看这里，而不是只看 Pod 的 phase。

`restartPolicy` 是 Pod 级的字段，取值 `Always`、`OnFailure`、`Never`，默认 `Always`。它作用于应用容器和常规 init 容器；原生 sidecar 例外，它自己声明 `restartPolicy: Always`，不看 Pod 级的值。三种策略与退出码的组合可以列成一张表：

| 退出码 | `Always` | `OnFailure` | `Never` |
|---|---|---|---|
| 0（成功） | 重启 | 不重启 | 不重启 |
| 非 0（失败） | 重启 | 重启 | 不重启 |

在会重启的 `restartPolicy` 下，容器退出后 kubelet 不是立刻无限重试。第一次崩溃后会立即重启，之后按指数退避：10 秒、20 秒、40 秒，一直翻倍到 300 秒封顶；如果容器连续运行了 10 分钟没有出问题，退避计时器会重置。`CrashLoopBackOff` 就是“退避等待中”这个状态的外在表现。退避只影响同一个 Pod 内的容器重启，不会让 Pod 换节点。

`terminationGracePeriodSeconds` 的默认值是 30 秒。它管的是删除 Pod 时留给进程退出的总时间，19.6 会展开。这里先记住一个容易踩的点：它不是一个“等待时间”参数，而是从删除开始倒计时的上限，`preStop` 和正常关闭都在这段时间里。

Pod 创建之后大部分字段不能改。官方列出的原地更新范围是：`spec.containers[*].image`、`spec.initContainers[*].image`、`spec.activeDeadlineSeconds`、`spec.terminationGracePeriodSeconds`、`spec.tolerations`（只能新增条目）、`spec.schedulingGates`。metadata 里 namespace、name、uid、creationTimestamp 这类字段不可变，label 和 annotation 可以改。CPU 和内存走另一条路：`resize` 子资源允许原地调整容器资源，`InPlacePodVerticalScaling` 从 1.27 alpha、1.33 beta 走到 1.35 GA；QoS 类在创建时确定，改资源不会改变它。

> **旧资料提示**：旧教程常说“Pod 完全不可变，改任何字段都要删掉重建”。这句话在 Deployment 的 Pod 模板层面基本成立——改模板会生成新 Pod——但对一个已经存在的 Pod 不成立：上面列出的字段可以原地改，镜像改了甚至不会重启 Pod（只会在下一次容器重启时生效），资源也可以通过 `resize` 子资源调整。真正不可变的是 Pod 的身份（namespace、name、UID）和大部分 spec。

## 19.3 探针：startup、readiness、liveness

探针（probe）是 kubelet 对容器周期性执行的诊断。它不是应用自己上报的健康状态，而是 kubelet 主动去问：执行一条命令、发一个 HTTP 请求、建一个 TCP 连接，或者走 gRPC 健康检查。三种探针问的是不同的问题，失败后的动作也不同。

startup 探针只回答“应用启动完了吗”。配置之后，kubelet 在 startup 成功之前不会执行 liveness 和 readiness；startup 失败超过阈值，kubelet 杀死容器，容器按 `restartPolicy` 重启。它只在启动阶段执行，不像另外两个贯穿整个生命周期。这解决的是慢启动应用的老问题：如果直接把 liveness 的 `initialDelaySeconds` 调得很大，应用一旦在启动后死锁，要等很久才会被发现；startup 把“启动期”和“运行期”分开，启动期可以给到几分钟，运行期的 liveness 仍然可以很灵敏。

readiness 探针回答“现在可以接流量吗”。失败时 kubelet 不会重启容器，而是把 Pod 的 `Ready` condition 置为 false，EndpointSlice 控制器把 Pod IP 从匹配的 Service 的 EndpointSlice 中移除。容器继续运行，探针继续执行；等它恢复，Pod 会重新变成 Ready，IP 也会回到 EndpointSlice。readiness 适合检查“依赖是否可用”“缓存是否预热完”“是否正在退出”。

liveness 探针回答“这个容器还有救吗”。失败超过阈值，kubelet 杀死容器，再按 `restartPolicy` 决定是否重启。它不会等 readiness 成功；如果希望启动后再开始探测，用 `initialDelaySeconds` 或 startup。官方对 liveness 的警告很重：它必须真的表示不可恢复的故障，比如死锁；把下游依赖（数据库、Redis）写进 liveness，数据库一抖动，所有 api 容器会一起重启，故障反而扩大。依赖检查应该放在 readiness 里。

三种探针共用五个时间/次数字段，默认值如下：

| 字段 | 默认值 | 说明 |
|---|---|---|
| `initialDelaySeconds` | 0 | 容器启动后等多久开始探测；配了 startup 时，liveness/readiness 的延迟从 startup 成功后算 |
| `periodSeconds` | 10 | 探测间隔；容器未 Ready 时 readiness 可能被更频繁地执行 |
| `timeoutSeconds` | 1 | 单次探测超时 |
| `successThreshold` | 1 | 失败后连续成功多少次才算恢复；liveness 和 startup 必须是 1 |
| `failureThreshold` | 3 | 连续失败多少次判定整体失败 |

检查机制有四种。`httpGet` 对 Pod IP 发 HTTP GET，状态码在 200–399 之间算成功；`path` 默认 `/`，`scheme` 默认 HTTP，`httpHeaders` 可以加自定义头，`host` 默认是 Pod IP。`exec` 在容器里执行命令，退出码 0 算成功；它每次探测都要 fork 进程，Pod 密度高、间隔短时会给节点带来额外开销。`tcpSocket` 从节点上对 Pod IP 的端口建 TCP 连接，端口能连上就算成功；连接建立后立刻被关闭也算健康。`grpc` 调用 gRPC Health Checking Protocol，响应 `SERVING` 才算成功；它要求写 `port`，不能用端口名，也不能自定义 hostname。gRPC 探针在 1.23 alpha、1.24 beta、1.27 stable。

> **旧资料提示**：旧教程常把探针说成只有 `exec`、`httpGet`、`tcpSocket` 三种机制。今天检查机制有四种，多了一个 gRPC；探针类型也从 liveness/readiness 两种变成三种，多了 startup。startup 在 1.16 alpha、1.18 beta、1.20 GA，gRPC 在 1.23 alpha、1.24 beta、1.27 stable，两者的版本节奏不一样。

还有两个版本细节值得写进清单。startup 探针在 1.16 alpha、1.18 beta、1.20 GA。探针级的 `terminationGracePeriodSeconds` 从 1.25 起可用、1.28 GA，但 readiness 探针不允许设置它，API server 会拒绝。

`kubectl describe pod` 末尾的 Events 给出直接证据：`Readiness probe failed: HTTP probe failed with statuscode: 503`。注意 `RESTARTS` 仍然是 0，容器没有被重启——readiness 失败只影响“是否接流量”，不影响“是否活着”。liveness 探的是 `/healthz`，这个接口只表示进程还在，所以它一直成功。这正是开头那个问题的答案：readiness 失败摘流量，liveness 失败重启容器，两者检查的端点不同，结果就不同。

## 19.4 init 容器与原生 sidecar

init 容器（Init Container）是在应用容器之前运行的容器，用来做初始化：等依赖的 Service 出现、拉取配置、跑迁移、给共享卷准备文件。它和普通容器的区别只有两条：init 容器必须运行到完成，而且每个 init 容器必须成功，下一个才会开始。多个 init 容器严格按 `initContainers` 数组的顺序串行执行；全部成功之后，kubelet 才创建应用容器。

失败的处理方式取决于 `restartPolicy`。init 容器失败时，kubelet 按 Pod 的 `restartPolicy` 重试；如果 Pod 是 `Always`（Deployment 的默认值），init 容器实际按 `OnFailure` 处理，也就是一直重试到成功。如果 Pod 是 `Never`，init 失败会让整个 Pod 进入 `Failed`，不会无限重试。等待重试期间，`kubectl get pod` 显示 `Init:CrashLoopBackOff`，`describe` 里的 init 容器可能显示 `Waiting`、原因是 `CrashLoopBackOff`，也可能显示正在再次运行；`Last State` 一定是上一次的 `Terminated` 和具体退出码。

init 容器有几个限制。常规 init 容器不支持 `lifecycle`、`livenessProbe`、`readinessProbe`、`startupProbe`；它也不需要 readiness，因为“完成”本身就是就绪的前提。所有 init 容器成功之前，Pod 不能 Ready，`Initialized` condition 是 false，Pod 处于 `Pending`。init 容器的端口不会汇总到 Service 里，Service 只选择应用容器。改 init 容器的 image 不会重启或重建 Pod，只影响下一次启动。

资源计算是 init 容器最容易算错的地方。Pod 对某种资源的有效请求/限制，取下面两者中较大的一个：所有应用容器（包括原生 sidecar）请求/限制之和；所有 init 容器中该资源的最大请求/限制。再加上 Pod overhead。调度按这个有效值进行，所以 init 容器可以临时预留比应用期更多的资源，但不会在应用运行时继续占用。QoS 类也按这个有效值判定。

原生 sidecar 是 init 容器的一个特例：写在 `initContainers` 里，但声明 `restartPolicy: Always`。`SidecarContainers` 特性在 1.28 alpha、1.29 beta（默认启用）、1.33 GA。它启动在应用容器之前，但启动后不退出，而是持续运行；kubelet 把它标记为 started 之后，才继续启动下一个 init 容器或应用容器。它独立于主容器重启，可以有自己的探针；它的 readiness 结果参与 Pod 是否 Ready 的判断。Pod 终止时，kubelet 等主容器完全停止后才终止 sidecar，并按定义顺序的逆序关闭；如果主容器用完了宽限期，sidecar 可能只收到 SIGTERM 就紧接着被 SIGKILL，所以 sidecar 退出码非 0 在 Pod 终止时是正常的。对 Job 来说，sidecar 不会阻止 Job 在主容器完成后结束，这是它和“普通容器形式的 sidecar”最大的区别之一。

传统 sidecar 就是普通容器：和主容器一起在 `containers` 数组里，没有启动顺序保证，共享 Pod 级 `restartPolicy`，主容器退出后它不会自动被单独保留。它今天仍然能用，适合不需要启动顺序、不需要独立生命周期的场景；需要“先启动、后关闭、独立重启”的时候，用原生 sidecar。

## 19.5 多容器模式与共享卷

一个 Pod 里放多个容器，通常落在四种模式里。sidecar 在主容器旁边提供辅助能力：收集日志、转发指标、做代理。adapter 把主容器的输出转换成另一种格式，比如把应用的私有指标转成 Prometheus 格式。ambassador 替主容器访问外部服务，主容器只连 `localhost`，由 ambassador 处理 TLS、重试、服务发现。init 容器则是另一种：它在主容器之前跑完就退出，不做长期服务。四者的共同点是“这些容器必须在一起”，而不是“把它们打包省事”。

共享卷是多容器协作的另一半。`emptyDir` 在 Pod 被调度到节点时创建，Pod 删除时一起删除；它适合放日志、缓存、临时交换文件。同一个 `emptyDir` 可以挂进多个容器，容器之间通过文件交换数据；如果只是通过 `localhost` 交换请求，就不需要卷。ConfigMap、Secret、Downward API 也可以作为卷挂进来，通常以只读方式提供配置，不是容器间通信通道。

> **旧资料提示**：旧教程说每个 Pod 会自动挂一个 `default-token-*` Secret。1.22 起，Kubernetes 默认用 TokenRequest 把短期、自动轮换的 token 以投射卷挂进 Pod；1.24 起不再为每个 ServiceAccount 自动创建永久 token Secret，这个行为在 1.27 GA。今天在 Pod 里看到的是一个 projected 类型的卷，不再是那个固定名字的 Secret。

Docker 官方文档对“一个容器跑多个进程”的建议同样适用于 Pod：每个容器只负责一个关注点，一个容器承担应用的多个方面会降低隔离和复用；一个服务 fork 出多个工作进程没有问题，但不要把无关的服务塞进同一个容器。到了 Kubernetes，这条建议还要加一层：无关的进程应该拆成不同的 Pod，有关的辅助进程才放进同一个 Pod 的不同容器。判断标准还是 19.1 的那句——分开到不同机器还能工作吗？

多容器 Pod 用 `kubectl logs` 时必须用 `-c` 指定容器，否则 kubectl 会报错让你从容器列表里选一个；不要靠猜，先看清容器名。排障时先 `kubectl get pod -o jsonpath='{.spec.containers[*].name}'` 确认容器名，再 `kubectl logs -c`。

## 19.6 优雅终止与 preStop

删除 Pod 不是一个瞬间动作。你执行 `kubectl delete pod` 之后，API server 先给 Pod 写入 `deletionTimestamp` 和宽限期，Pod 在 `kubectl get` 里显示 `Terminating`；与此同时，控制平面把 EndpointSlice 里这个 Pod 对应的 endpoint 标记为 terminating，`ready` 变成 false（对象不会立刻删除），`serving` 表示它是否还能接流量。节点上的 kubelet 看到删除标记后，如果配了 `preStop`，先在容器里执行 hook；hook 完成后，容器运行时向容器里的 PID 1 发 SIGTERM；宽限期到点，还有进程没退出就发 SIGKILL。

顺序里有几个容易忽略的细节。第一，宽限期从删除开始计时，不是在 SIGTERM 之后才开始；`preStop` 花的时间也算在这段时间里。第二，`preStop` 必须执行完才会发 SIGTERM，hook 卡住会把整个宽限期耗掉。第三，hook 的投递语义是“至少一次”，kubelet 重启等情况下可能重复执行，所以 hook 要幂等。第四，普通容器收到 TERM 的顺序是任意的；如果 Pod 里有原生 sidecar，kubelet 会等主容器完全停止后才终止 sidecar，并按定义顺序逆序关闭。

对 shorty 来说，应用自己已经做了一半的优雅终止：收到 SIGTERM 后，它先把 readiness 置为失败，等 `SHORTY_SHUTDOWN_DELAY` 秒（默认 5 秒），再调用 `http.Server.Shutdown`，最多再等 10 秒让在处理的请求完成，然后退出。这段等待是给 EndpointSlice 和 kube-proxy 留出摘流量的时间；如果进程一收到信号就关监听，正在路上的新连接会直接被拒绝。另一半在 Kubernetes 侧：`terminationGracePeriodSeconds` 必须大于“最慢请求 + preStop + SHUTDOWN_DELAY”，否则 SIGKILL 会在请求完成前落下。

`preStop` 适合做应用自己不负责的收尾。比如一个没有优雅关闭逻辑的第三方进程，可以用 `preStop` 执行 `sleep 5`，让负载均衡先把它摘掉；`sleep` 类型的 hook 在 1.29 alpha、1.30 beta、1.34 GA。有原生 sidecar 时，kubelet 已经负责“主容器先停、sidecar 后停”，不需要再用 `preStop` 手工排序。

## 19.7 排障：Pod 一直重启

如果是 `OOMKilled`，看 `resources.limits.memory` 和容器的实际用量。`kubectl describe pod` 会显示 `Last State: Terminated`、`Reason: OOMKilled`、`Exit Code: 137`；第 7 章在 Docker 侧看过 cgroup v2 的 `memory.max` 和 `memory.events`，Kubernetes 只是把 limit 写进同一个 cgroup 文件，内核的 OOM killer 行为没有变。先确认 limit 是不是按实测的峰值设的，再决定是调大 limit 还是修内存泄漏；单纯把 limit 调大往往只是把 OOM 推迟。

## 上生产前

每个长时间运行的服务都要有 readiness 和 liveness，慢启动的服务再加 startup。readiness 检查“现在能不能接流量”，liveness 检查“进程是否还活着”；只有 liveness 没有 readiness，滚动更新时新 Pod 会在没准备好时接流量；只有 readiness 没有 liveness，死锁的进程会一直挂着不重启。startup 的 `failureThreshold` 要按实测的启动时间设，不要抄默认值：默认 3 次 × 10 秒只有 30 秒，一个要加载大表的服务可能根本起不来。

liveness 不要检查下游依赖。数据库挂了，所有 api 的 liveness 一起失败，kubelet 会把它们全部重启，重启期间请求全部失败，数据库恢复后还要面对冷启动。依赖检查放在 readiness 里：数据库不可用时 Pod 被摘流量，但进程不重启，数据库恢复后 readiness 自然恢复。这也是 19.3 里 `RESTARTS` 保持 0 的原因。

`terminationGracePeriodSeconds` 要大于“最慢请求 + preStop + 应用自己的关闭等待”。默认 30 秒对大多数 HTTP 服务够用，但对长连接、文件上传、流式响应不够；反过来，设得过大也有代价：节点 drain 时最多要等每个 Pod 的宽限期，滚动更新会变慢。用 PDB 保护自愿中断，让 drain 一次只影响一部分副本，而不是把全部 api 同时删掉。

不要在 Pod 里放多个无关进程。共享 network namespace 意味着端口冲突，共享 cgroup 意味着一个进程的内存泄漏会拖垮整个 Pod；sidecar 也要算进 requests/limits，否则调度器看到的资源和实际用量对不上。共享卷只放确实需要交换的数据：`emptyDir` 随 Pod 删除，不能当持久化存储；多个容器同时写同一个文件要有明确的协议，否则排障时很难判断是谁改的。

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `containers[].name/image/ports/resources/volumeMounts` | 应用容器的基本信息 | 名字在 Pod 内必须唯一 |
| `initContainers[]` | 启动前按顺序执行的容器 | 必须全部成功；不支持 lifecycle 和探针（原生 sidecar 例外） |

| `startupProbe` | 启动探针 | 成功后才会执行 liveness/readiness |
| `readinessProbe` | 就绪探针 | 失败时摘 Endpoint，不重启容器 |
| `livenessProbe` | 存活探针 | 失败时杀死容器，按 restartPolicy 重启 |
