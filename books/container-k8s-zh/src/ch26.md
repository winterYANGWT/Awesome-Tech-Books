# 第 26 章 存储：PV、PVC、StorageClass、CSI、快照

`kubectl -n shorty get pvc data-postgres-0` 显示 `Bound`，容量 1Gi，`STORAGECLASS` 是 `standard`。把同一份清单拿到另一个没有默认 StorageClass 的集群，只改名字和容量，PVC 却一直 Pending。`kubectl describe pvc` 的 Events 可能是 `waiting for first consumer to be created before binding`，也可能是 `storageclass.storage.k8s.io "..." not found`；前者在等 Pod 被调度，后者根本没有可用的制备器。

`1Gi` 只回答“要多少”，不回答“从哪来、什么时候给、删了以后还在不在”。这三个问题分别落在 PVC 的 `storageClassName`、StorageClass 的 `volumeBindingMode`，以及 PV 的 `persistentVolumeReclaimPolicy` 上。把它们混成“存储就是一个 PVC”，排障时就会在 Pending 的几种原因之间来回猜。

Kubernetes 把存储拆成两层：集群管理员提供 PV（PersistentVolume）或能自动制备 PV 的 StorageClass，用户只提交 PVC（PersistentVolumeClaim）。PV 是集群资源，PVC 是命名空间里的申领；Pod 只认 PVC，不关心背后是本地磁盘、云盘还是 NFS。CSI 是这两层之下的插件接口，决定 Kubernetes 怎么调用存储厂商的驱动。

本章从 shorty 的 postgres 数据盘出发，先把卷按生命周期分开，再看 PV/PVC 怎么绑定、StorageClass 怎么动态制备，然后拆开 CSI 的对象，最后用回收策略、扩容和访问模式解释 Pending、Released 和 Multi-Attach 这些现象。快照在 kind 里没有 CRD，只讲对象关系和安装清单。

> **起点**：本章从 `s3-stateful` 开始：单节点 kind 集群，shorty 的 api 2 副本、postgres 是 StatefulSet 加 PVC `data-postgres-0`（1Gi，默认 StorageClass `standard`）、redis 和 worker 各 1 副本。集群里没有 VolumeSnapshot CRD。一步到位：`bash code/ch26/setup.sh`。

## 26.1 volume 类型与生命周期

Pod 里的容器看到一个根文件系统，起点是镜像的内容，可写层属于容器。容器崩溃或被 kubelet 重启时，这一层会从镜像重新开始，容器生命周期内写下的文件不再存在。volume（卷）是另一层：它在 Pod 的 `.spec.volumes` 里声明，在容器的 `.spec.containers[*].volumeMounts` 里挂到某个路径，数据是否存在、存在哪里、Pod 删除后是否保留，由卷的类型决定。卷不是容器的属性，而是 Pod 的属性；同一个卷可以挂给 Pod 里的多个容器，让它们通过文件系统交换数据。卷不能挂载在另一个卷里面；`subPath` 是同一个卷里的子路径，不是第二个卷。

卷的第一个分界线是生命周期。`emptyDir`、`configMap`、`secret`、`downwardAPI` 和通用临时卷的挂载跟着 Pod 生命周期：Pod 被删除，挂载消失；ConfigMap 和 Secret 对象本身还在 API 里，通用临时卷创建的 PVC 则会被一起删除。PVC 不属于任何 Pod：PVC 对象单独存在，Pod 只是引用它，删 Pod 不会删 PVC，也不会删 PVC 绑定的 PV。这个区别解释了本章开头的问题：删掉 postgres 的 Pod，`data-postgres-0` 还在；删掉 `data-postgres-0`，才轮到 PV 的回收策略决定数据盘的去留。

`emptyDir` 在 Pod 被分配到节点时创建，初始为空；Pod 从节点上移除时，里面的数据永久删除。它适合临时排序、缓存、内容管理器抓下来的文件这类可以重建的数据。容器崩溃不会把 Pod 从节点上移除，所以 `emptyDir` 在容器重启之间是保留的；这一点和“容器可写层重启就没了”刚好相反。`emptyDir.medium: Memory` 会挂一个 tmpfs，读写快，但写入量计入容器的内存限制；不写 `medium` 时落在节点磁盘上，可以用 `sizeLimit` 限制容量，容量从节点的 ephemeral storage 里扣。

`hostPath` 直接把节点上的文件或目录挂进 Pod，路径写的是节点，不是容器。它看起来最像“持久化”，实际最危险：同一个 Pod 模板在不同节点上会看到不同文件；节点上的 kubelet 凭据、容器运行时 socket、`/var/log` 都可能被读到；`hostPath` 的磁盘用量不计入 ephemeral storage，写满节点也没有配额兜底。官方文档的建议很直接：能不用就不用，需要节点本地持久数据时用带 `nodeAffinity` 的 `local` PV，而不是 `hostPath`。`hostPath.type` 的 `DirectoryOrCreate`、`FileOrCreate` 等值只控制“路径不存在时怎么办”，不解决安全和调度问题。`emptyDir` 和 `hostPath` 都没有容量隔离，写满的是节点磁盘，配额要由 Pod 的 ephemeral storage 或节点侧监控来兜。

`configMap` 和 `secret` 卷把 API 对象里的数据变成文件，通常挂配置文件、证书、密码。两者都是只读挂载；Secret 由 tmpfs 支撑，不落到节点的非易失存储。用 `subPath` 挂单个文件时，ConfigMap 或 Secret 更新后容器里的文件不会跟着变，因为 `subPath` 绑定的是更新前的那一份；要热更新就挂整个目录。`projected` 卷把多个来源投射到同一个目录：Secret、ConfigMap、downwardAPI、serviceAccountToken 是常用的四种，另外还有受特性门控的 clusterTrustBundle 和 podCertificate。所有来源必须和 Pod 在同一个命名空间。

通用临时卷（generic ephemeral volume）介于两者之间：Pod 里写 `ephemeral.volumeClaimTemplate`，控制器为这个 Pod 创建一个真实的 PVC，Pod 删除时 PVC 也被删除，PV 再按 StorageClass 的回收策略处理。它在 Kubernetes 1.23 成为 stable，适合“每个 Pod 要一块固定大小、但不要求跨 Pod 保留”的临时空间，例如模型的临时缓存。它和 `emptyDir` 的区别是卷可以由网络存储或 CSI 提供，能有固定容量，也能在驱动支持时用快照、克隆、扩容这些 PVC 的能力；代价是多了一个 PVC 对象和一次动态制备。直接在 Pod 里写 `csi` 的 inline ephemeral 卷是另一种，1.25 成为 stable，只有明确支持 ephemeral 模式的 CSI 驱动才能用。`emptyDir` 和通用临时卷都随 Pod 删除，但前者由 kubelet 在节点本地创建，后者走 StorageClass 和 PV，可以落在网络存储上，也能用容量上限、快照和克隆；选择标准是数据要不要跨节点、要不要这些能力，而不是名字里有没有 ephemeral。

## 26.2 PV/PVC 绑定

PV 是集群里的一块存储，和节点一样是集群资源；PVC 是命名空间里的申领，描述“我要多大、要什么访问模式、要哪个类”。控制平面里有一个控制循环盯着新的 PVC，找到匹配的 PV 就把两者绑在一起。绑定是一对一的：一个 PVC 只能绑一个 PV，一个 PV 也只能被一个 PVC 使用。绑定关系写在 PV 的 `spec.claimRef` 和 PVC 的 `spec.volumeName` 里，前者是 PV 指向申领，后者是申领指向 PV。

PV 的 `spec` 里，`capacity.storage` 是容量，`accessModes` 是访问模式，`volumeMode` 是 `Filesystem` 或 `Block`，`storageClassName` 是所属的类，`persistentVolumeReclaimPolicy` 是回收策略。PVC 的 `spec` 用同样的 `accessModes` 和 `volumeMode` 表达需求，用 `resources.requests.storage` 表达容量。匹配时容量是“至少满足”：PVC 要 800Mi，可以绑到 1Gi 的 PV；绑定后这 1Gi 都归这个 PVC，剩下的 200Mi 不会再分给别人。

访问模式有四种，缩写和语义如下。

| 缩写 | 全名 | 语义 |
|---|---|---|
| RWO | ReadWriteOnce | 可以被单个节点以读写方式挂载；同一节点上的多个 Pod 仍可能同时读写 |
| ROX | ReadOnlyMany | 可以被多个节点以只读方式挂载 |
| RWX | ReadWriteMany | 可以被多个节点以读写方式挂载 |
| RWOP | ReadWriteOncePod | 只能被单个 Pod 以读写方式挂载 |

`ReadWriteOnce` 约束的是节点，不是 Pod。两个 Pod 跑在同一个节点上，共用同一个 RWO 卷是允许的；换成两个节点，有 attach/detach 的存储就会阻止第二个节点挂载。需要“整个集群只有一个 Pod 能写”时，用 `ReadWriteOncePod`。它在 Kubernetes 1.22 引入，1.29 成为 stable，只支持 CSI 卷，而且不能和其他访问模式组合。访问模式主要用来匹配 PV/PVC 和约束挂载位置；除了 RWOP，它们并不在挂载后提供写保护，PV 写成 `ReadOnlyMany` 也不保证文件系统真的只读。PV 的 `mountOptions` 会原样传给 mount，驱动不支持时制备失败；这些选项不在 API 层校验，写错只会在挂载时暴露。

`volumeMode` 的默认值是 `Filesystem`，Kubernetes 会在块设备上创建文件系统再挂载；设成 `Block` 则把设备原样交给容器，Pod 里用 `volumeDevices` 而不是 `volumeMounts`，应用要自己处理裸块设备。`volumeMode` 也参与绑定匹配：PV 是 `Block`、PVC 是 `Filesystem` 时不会绑定。PVC 还可以用 `selector` 按标签筛选 PV；带非空 `selector` 的 PVC 不能走动态制备，因为新制备的 PV 不一定带这些标签，这种写法只适合静态 PV 池。

PV 的 `status.phase` 有 `Available`、`Bound`、`Released`、`Failed` 四个值；PVC 的 `status.phase` 有 `Pending`、`Bound`、`Lost` 三个值。`Lost` 表示 PVC 曾经绑定过 PV，但那个 PV 已经不存在，数据也没了。看到 PVC 不是 `Bound`，先看 `kubectl describe pvc` 的 Events，而不是先怀疑应用。

静态绑定有两种写法。PVC 里写 `volumeName` 是指定“我要这个 PV”；PV 里写 `claimRef` 是管理员预留“这个 PV 只给某个命名空间的某个 PVC”。`claimRef` 更适合管理员预先分配，因为它在 PVC 创建之前就能把 PV 占住，别的 PVC 不会抢走。示例用后者：PV 预留 `storage-demo/manual-pvc`，PVC 请求 800Mi，绑定到 1Gi 的 `manual-pv`。

## 26.3 StorageClass 与动态制备

静态 PV 需要管理员提前建好，PVC 只能从现有池子里挑。StorageClass 把“建 PV”这一步也交给控制器：PVC 只写类名和容量，StorageClass 里的 provisioner 收到请求，调用存储后端创建卷，再生成 PV 并绑定。类里的 `provisioner` 必填，可以是 in-tree 名字，也可以是外部驱动的名字；外部 provisioner 自己跑，Kubernetes 只负责把 PVC 交给它。`parameters` 是传给 provisioner 的键值表，`reclaimPolicy` 默认 `Delete`，`volumeBindingMode` 默认 `Immediate`；`allowVolumeExpansion` 不写时不允许扩容。

`storageclass.kubernetes.io/is-default-class: "true"` 这个注解把类标成默认。PVC 不写 `storageClassName` 时，`DefaultStorageClass` 准入控制器把默认类名填进 PVC；集群里没有默认类，PVC 就保持没有类，直到默认类出现。这个回填在 Kubernetes 1.28 成为 stable：先创建的 PVC 不会因为当时没有默认类而永远卡住，默认类出现后控制面会补上。反过来，PVC 显式写 `storageClassName: ""` 表示“我不要类”，只和没有类的 PV 绑定，动态制备对它是关闭的。多个类都标成默认时，Kubernetes 用最近创建的那个；生产上应该只保留一个默认类。

`parameters` 最多 512 个键，键和值的总长度不能超过 256KiB；`allowedTopologies` 可以在 `WaitForFirstConsumer` 之上再限制可用区，替代旧驱动里的 `zone`/`zones` 参数。`volumeBindingMode` 决定什么时候绑定和制备。`Immediate` 在 PVC 创建时就开始，适合所有节点都能访问的共享存储；如果存储只在某个可用区或某台节点上，PVC 可能先绑到一个 Pod 去不了的卷，Pod 因此调度失败。`WaitForFirstConsumer` 等到有 Pod 使用这个 PVC 时才绑定，调度器会把 Pod 的节点选择、亲和性、污点容忍和存储拓扑一起考虑，再决定在哪制备卷。kind 自带的 `standard` 用的就是 `WaitForFirstConsumer`。StorageClass 只影响动态制备，不会把已经存在的静态 PV 变成动态卷；PVC 指定了类之后，只能绑同类的 PV，要绑没有类的 PV 时 PVC 的 `storageClassName` 也必须是空。类名是绑定匹配的一部分。

`WaitForFirstConsumer` 有一个常见坑：不要在 Pod 里用 `nodeName` 指定节点。`nodeName` 会绕过调度器，PVC 等不到“第一次消费”的调度决策，会一直 Pending；要限定节点，用 `nodeSelector` 的 `kubernetes.io/hostname`，让调度器仍然参与。

## 26.4 CSI：存储插件怎么工作

CSI（Container Storage Interface）是一个标准接口，存储厂商按它实现驱动，Kubernetes 按它调用驱动，双方不用把代码合进 Kubernetes 仓库。和早年的 in-tree 插件相比，CSI 驱动可以独立发布、独立升级，集群管理员装哪个驱动、给哪个 StorageClass 用，都是集群侧的配置。

按 CSI 规范，驱动通常提供两组服务。Controller 侧负责卷的生命周期：创建、删除、扩容、给节点 attach/detach，以及快照；它通常以 Deployment 或 StatefulSet 跑在控制面或专用节点上，通过外部 sidecar（external-provisioner、external-attacher、external-resizer、csi-snapshotter）和 Kubernetes 的 API 对接。Node 侧负责把卷弄到节点上并挂进容器：格式化、stage、publish、unmount；它以 DaemonSet 跑在每个节点上，需要访问宿主机的设备和 mount 命名空间，所以常以特权容器运行，并通过 node-driver-registrar 把自己注册到 kubelet。

Kubernetes 用三个对象记录这些事。`CSIDriver` 是集群级对象，名字就是驱动名；`spec.attachRequired` 告诉 attach/detach 控制器这个驱动是否需要 attach，`podInfoOnMount` 决定 kubelet 是否把 Pod 名、命名空间、UID 传给驱动，`volumeLifecycleModes` 声明支持 Persistent、Ephemeral 还是两者。`CSINode` 每个节点一个，和节点同名，列出这个节点上注册了哪些驱动；它由 kubelet 在驱动注册时自动写入，不需要驱动自己创建。`VolumeAttachment` 记录“把某个卷 attach 到某个节点”的意图和结果，`spec.attacher` 是驱动名，`spec.nodeName` 是目标节点，`status.attached` 由 external-attacher 在 attach 成功后置为 true；它和 `CSIDriver`、`CSINode` 一样是集群级对象。`CSINode` 缺失通常意味着这个节点没有注册 CSI 驱动，或者 kubelet 版本太旧。

`StorageClass.parameters` 里除了驱动自己的参数，还可以放 `csi.storage.k8s.io/` 前缀的键，把 Secret 的名字和命名空间传给对应的 sidecar，例如 provisioner、controller-publish、node-stage、node-publish 各阶段的 Secret。键名由 Kubernetes CSI 项目的 sidecar 约定，例如 `csi.storage.k8s.io/provisioner-secret-name` 和 `csi.storage.k8s.io/provisioner-secret-namespace`，controller-publish、node-stage、node-publish、controller-expand 各有一对同样格式的键（见 Kubernetes CSI 文档的 “Secrets and Credentials” 一页）。它们不是 Kubernetes 核心 API 的字段，驱动是否用到某个阶段的 Secret 要看驱动文档；本书的 local-path 驱动不需要 Secret，所以没有在 lab 里演示。

in-tree 插件已经大面积退场。AWS EBS 和 Azure Disk 的 in-tree 驱动在 Kubernetes 1.19 弃用，1.27 移除；GCE PD 在 1.17 弃用，1.28 移除。`CSIMigration` 在 1.25 成为 stable，迁移期间旧的 StorageClass 和 PV 还能用，但实际操作被转发到同名 CSI 驱动，集群里必须装好对应的驱动。新集群、新 StorageClass 不要再写 `kubernetes.io/aws-ebs`、`kubernetes.io/gce-pd`、`kubernetes.io/azure-disk` 这些 provisioner 名。CSI 驱动还有自己的版本兼容矩阵；官方文档提醒驱动不一定兼容所有 Kubernetes 版本，升级集群前要确认驱动支持的版本范围。

kind 自带的 `standard` 不是 CSI。它的 provisioner 是 `rancher.io/local-path`，一个外部 provisioner：它直接创建 `hostPath` 类型的 PV，不实现 CSI 的 Controller/Node 服务，不会注册 `CSIDriver`，不会在 `CSINode` 的 `drivers` 列表里留下条目，也不会创建 `VolumeAttachment`。这正好用来看“有动态制备”和“有 CSI”是两件事。

## 26.5 快照、克隆与扩容

卷快照（VolumeSnapshot）是某个时间点的一份卷副本。Kubernetes 用三个 CRD 表达它：`VolumeSnapshot` 是用户提出的快照请求，`VolumeSnapshotContent` 是集群里真实的快照资源，`VolumeSnapshotClass` 描述用哪个驱动、怎么删、带什么参数。这三个对象属于 `snapshot.storage.k8s.io` API 组，不是核心 API；集群里不装 CRD，apiserver 不认识这个 kind。

快照能力不是装一个 CRD 就完事。官方文档列出的组件有四类：CRD、快照控制器（snapshot controller）、和 CSI 驱动一起部署的 `csi-snapshotter` sidecar、以及对快照对象做校验的 validating webhook。快照控制器监听 `VolumeSnapshot` 和 `VolumeSnapshotContent`，负责创建和删除 content；`csi-snapshotter` 监听 content，调用驱动的 `CreateSnapshot`/`DeleteSnapshot`；webhook 负责更严格的校验。CRD、快照控制器和 webhook 通常是 Kubernetes 发行版的责任；`csi-snapshotter` 和 CSI 驱动一起部署，但也不是驱动核心逻辑的一部分。驱动还必须实现快照能力，没实现的驱动即使 CRD 在，快照也会失败。`VolumeSnapshotContent` 里记录 `driver`、`source.volumeHandle`（动态制备）或 `source.snapshotHandle`（预制备）、`sourceVolumeMode` 和 `volumeSnapshotRef`，它和 PV 一样是集群级资源，`VolumeSnapshot` 才是命名空间里的请求。

动态快照在 `VolumeSnapshot.spec.source.persistentVolumeClaimName` 里写源 PVC，`volumeSnapshotClassName` 指定类；预制备快照则写 `volumeSnapshotContentName`。`VolumeSnapshotClass` 的 `deletionPolicy` 是 `Delete` 或 `Retain`：删 `VolumeSnapshot` 时，`Delete` 会把底层快照和 content 一起删，`Retain` 会保留两者。快照进行期间，源 PVC 受“使用中的存储对象保护”，删 PVC 会被推迟到快照 `readyToUse` 或中止之后。

扩容走的是 PVC 而不是 PV。StorageClass 的 `allowVolumeExpansion: true` 打开扩容后，编辑 PVC 的 `spec.resources.requests.storage` 调大，控制器会扩容底层卷；只能变大，不能变小。文件系统扩容只支持 XFS、Ext3、Ext4，通常在 Pod 启动时做，支持在线扩容的文件系统可以在 Pod 运行时完成；使用中的 PVC 不需要删 Pod 重建，文件系统扩完之后容器就能看到新容量。PVC 的 `status.allocatedResourceStatuses` 和 Events 能看到扩容进度。底层驱动不支持扩容时，请求会一直重试或直接被拒绝。

`VolumeSnapshotClass` 创建后不能更新，`deletionPolicy` 必须写；不写 `volumeSnapshotClassName` 时，Kubernetes 会按 PVC 的 StorageClass 驱动去找默认快照类，默认类用 `snapshot.storage.kubernetes.io/is-default-class: "true"` 标记，同一个驱动只能有一个默认类。启用 `VolumeSnapshotTopology` 的集群里，多可用区快照可能只在部分区域可用，恢复时控制器会参考 `VolumeSnapshotContent` 上记录的拓扑，把新卷放到快照数据所在的位置。

`VolumeAttributesClass` 是另一层：StorageClass 描述“卷从哪来、多大、什么回收策略”，VolumeAttributesClass 描述“卷的性能参数”，例如 IOPS、吞吐。它在 Kubernetes 1.34 成为 GA，可以禁用；只能用于 CSI 卷，而且驱动要实现 `ModifyVolume`。PVC 的 `spec.volumeAttributesClassName` 可以从一个类改到另一个类，控制器调用驱动在线修改，不用重建卷；类名可变，类里的参数本身不可变。这个能力主要面向云盘，kind 的 local-path 不支持。

快照的 `deletionPolicy` 和 PV 的 `reclaimPolicy` 是两套独立策略：删快照按前者处理 `VolumeSnapshotContent`，删 PVC 按后者处理 PV；PV 是 `Retain` 不代表快照一定保留，反过来也一样。

快照不等于备份。快照在存储系统里创建，和源卷在同一个后端、同一个账号、同一个区域；源卷所在账号或区域出问题，快照也可能一起不可用。误删 PVC 再误删快照，或者存储后端本身故障，快照救不了。生产上要把快照当成“快速回滚点”，另外做跨集群或对象存储的备份，并定期做恢复演练。

## 26.6 回收、扩容与排障

PVC 删除后，PV 的去留由 `persistentVolumeReclaimPolicy` 决定。`Delete` 会删除 PV 对象，并让存储后端删除对应的卷；动态制备的 PV 默认继承 StorageClass 的回收策略，而 StorageClass 不写 `reclaimPolicy` 时默认就是 `Delete`。`Retain` 只删除 PVC，PV 变成 `Released`，后端卷和数据都还在；管理员要手动删 PV、清理数据、再删后端存储资产，或者用同样的存储资产重新建一个 PV。手工回收的顺序不能反过来：先删 PV 对象，再清理后端数据，最后删后端资产；如果先删后端资产，PV 对象还在，但后端数据已经没了，后续恢复和审计都对不上。`Recycle` 已经弃用，只在少数卷类型上有意义，新集群不要用。

“删了 PVC，数据盘会不会一起删”没有统一答案，先看 PV 的回收策略，再看 PVC 是不是还在被 Pod 使用。只要还有 Pod 引用 PVC，PVC 就带着 `kubernetes.io/pvc-protection` finalizer，删除会被推迟到 Pod 终止之后；PV 被 PVC 绑定时也有 `kubernetes.io/pv-protection`，不会先于 PVC 消失。删除顺序不对时，finalizer 会保护后端卷，但这也意味着 `kubectl delete pvc` 可能短时间停在 `Terminating`，不是卡死。

PVC 停在 `Terminating` 时，`kubectl describe pvc` 的 Finalizers 里能看到 `kubernetes.io/pvc-protection`；PV 被绑定时，`kubectl describe pv` 里能看到 `kubernetes.io/pv-protection`。这两个 finalizer 是“使用中的存储对象保护”的可见证据，也是为什么删 PVC 不是立刻完成。

`Delete` 的删除顺序还有一个细节：Kubernetes 1.31 给 CSI PV 加了 `external-provisioner.volume.kubernetes.io/finalizer`，确保后端卷真的删掉之后才移除 PV 对象；这个行为由 `HonorPVReclaimPolicy` 控制，1.33 成为 stable。没有它，先删 PV 再删 PVC 可能留下孤儿后端卷。

## 26.7 排障：PVC 一直 Pending

PVC Pending 时，第一步永远是 `kubectl describe pvc`，看 Events 的 Reason 和 Message。排查顺序可以固定成：PVC 的 `status.phase` 和 `spec.storageClassName` → 有没有匹配的 PV → StorageClass 和 provisioner 是否正常 → 使用它的 Pod 有没有被调度。常见的几类原因指向完全不同的修复方向。

第一类是“没有类”。PVC 不写 `storageClassName`，集群又没有默认 StorageClass，就没有 provisioner 为它动态制备，PVC 只能匹配没有类的静态 PV；如果 PVC 写了类名但类不存在，事件会是 `storageclass.storage.k8s.io "..." not found`。第二类是“有类但没有 PV”：`storageClassName: ""` 的 PVC 只找没有类的静态 PV，找不到就一直 Pending；静态 PV 的容量、访问模式、`volumeMode` 和类名任何一个不匹配，也都绑不上。第三类是 `WaitForFirstConsumer`：PVC 在等一个使用它的 Pod，事件是 `waiting for first consumer to be created before binding`；这时候 Pod 没调度，PVC 就不会绑定，先看 Pod 为什么没调度，而不是去改 PVC。第四类是 provisioner 自己失败，例如云盘配额不足、可用区没有容量、参数不被驱动接受，事件里会有 `ProvisioningFailed` 和驱动的错误信息。

三个 PVC 都是 `Pending`，但 Events 给出三种不同原因：`missing-class` 是 `ProvisioningFailed`，StorageClass 不存在；`no-class` 是 `FailedBinding`，显式写了空类但没有可匹配的静态 PV；`waiting` 是 `WaitForFirstConsumer`，用的是默认类但在等 Pod。修复分别是创建类、创建匹配的 PV 或改用有类的动态制备、给 `waiting` 创建一个使用它的 Pod。不要用“删 PVC 重建”来赌，前两类重建多少次都一样，第三类删了反而丢掉绑定进度。

PVC 是 `Bound` 而 Pod 还是 Pending，问题通常不在存储。先看 `kubectl describe pod` 的 `FailedScheduling`：节点资源不够、nodeSelector 没匹配、污点没有容忍、亲和性冲突、拓扑分布约束都会让 Pod 停住。PVC 已经绑定但 Pod 起不来，再看 `FailedMount`：卷 attach 不上、挂载点被占用、Secret 或 ConfigMap 缺 key，都会在这一层报错。

`Multi-Attach error` 是另一类。本书的 kind 用 local-path，不做 attach，复现不了这个错误；下面的处理顺序来自 RWO 的挂载语义，没有在本地验证。RWO 卷已经 attach 到节点 A，旧 Pod 还没完全终止，新 Pod 被调度到节点 B，kubelet 会报这个卷已经独占挂载在另一个节点。处理顺序是等旧 Pod 终止、确认 detach 完成，再让新 Pod 重试；只有确认节点已经失联、旧 Pod 永远不会回来时，才考虑强制删除 Pod 或清理 VolumeAttachment。卷本身没有坏，是访问模式不允许两个节点同时挂。RWOP 的冲突更直接：调度器事件会写 `PersistentVolumeClaim with ReadWriteOncePod access mode already in-use by another pod`，有些版本或路径可能用 `volume is already used by pod` 这类措辞；约束的是 Pod 而不是节点，所以同节点也不能起第二个。

> **旧资料提示**：旧教程里还会出现 `kubernetes.io/aws-ebs`、`kubernetes.io/gce-pd`、`kubernetes.io/azure-disk` 这些 in-tree provisioner。它们在 Kubernetes 1.27/1.28 前后被移除，PVC 或 PV 如果还引用这些类型，事件里可能出现 `no volume plugin matched`。新集群要装对应的 CSI 驱动，用 CSI 的 provisioner 名。

## 上生产前

**有状态数据用 PVC 加 CSI，不要用 hostPath 或 emptyDir 存持久数据。** hostPath 把数据绑在单台节点上，节点坏了 Pod 就起不来，Pod 模板在不同节点还会看到不同文件；emptyDir 跟着 Pod 消失；容器重启时它还在，但 Pod 一旦被删除就没了。节点本地存储不是不能用，但要用 `local` PV 加 `nodeAffinity`，并接受“节点不可用数据就不可用”的可用性代价；真正要跨节点、要快照、要扩容的数据，用 CSI 加 PVC。

**先定回收策略，再定备份策略。** `Delete` 省事，但删 PVC 就等于删数据盘；`Retain` 安全，但会留下 `Released` 的 PV 和后端卷，需要有人定期清理，否则存储会越用越少。生产上把回收策略写进 StorageClass，不要依赖默认值；`Delete` 的类要配快照并另做跨集群备份，`Retain` 的类要有清理责任人和清理脚本。快照不是备份：它和源卷在同一个存储后端，账号、区域或后端故障会一起坏，必须另做一份跨集群或对象存储的备份。

**生产用 `WaitForFirstConsumer` 加拓扑感知。** 云盘、本地盘这类只在部分节点或可用区可用的存储，`Immediate` 可能先把 PVC 绑到一个 Pod 去不了的卷，Pod 因此永远调度不上。`WaitForFirstConsumer` 让调度器先选节点再制备；如果还要限制可用区，用 StorageClass 的 `allowedTopologies`，不要用 Pod 的 `nodeName` 绕过调度器。

**扩容前确认三件事：`allowVolumeExpansion`、驱动能力、文件系统类型。** 没有 `allowVolumeExpansion: true`，改 PVC 会被直接拒绝；有开关但驱动不支持，请求会卡在扩容中；文件系统不是 XFS、Ext3、Ext4，文件系统层扩不了。扩容只能变大，不能变小；生产上先在一个 PVC 上验证，再批量改，改完检查 `status.allocatedResourceStatuses` 和容器里的 `df`。

**访问模式不是写保护，RWO 也不是单 Pod。** 需要单 Pod 写时用 `ReadWriteOncePod`，并确认 CSI 驱动和 sidecar 版本支持；需要多节点共享写时用 `ReadWriteMany`，并确认后端真的是共享文件系统。不要把 `ReadWriteOnce` 当成数据库的“单写者锁”，在有 attach/detach 的存储上它只阻止跨节点挂载，同节点上的两个 Pod 仍然能同时写。
