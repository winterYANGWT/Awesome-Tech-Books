# 第 17 章 集群架构：一次 `kubectl apply` 背后发生了什么

第 16 章结束时，`shorty` 的清单已经能在 kind 集群里跑起来。重新 apply 一遍，终端几乎立刻打印 `deployment.apps/api created` 和 `service/api created`。如果紧接着执行 `kubectl get pods -n shorty`，可能只看到 `No resources found`；再过一两秒，Pod 才以 `Pending`、`ContainerCreating` 出现，最后变成 `Running`。`created` 只说明 API server 把对象写进了存储，不说明调度器已经选了节点，更不说明 kubelet 已经起了容器。

这中间至少有几棒接力：请求先过 TLS 认证、RBAC 授权和准入控制，对象写进 etcd；控制器看到 Deployment 后创建 ReplicaSet 和 Pod；调度器给 Pod 选一个节点，把结果写回 API server；目标节点上的 kubelet 通过 watch 看到这个 Pod，再通过 CRI 让 containerd 拉镜像、起 sandbox、起容器；最后 kubelet 把状态写回 API server，`kubectl get` 才看得到 `Running`。任何一棒掉了，都会在 Pod 的 `status` 或 Event 里留下痕迹。

这一章就沿着这条链走一遍。先把 `kube-system` 里的组件和节点上的进程对上号，再用一个临时 Pod 把 `apply` 的请求、调度和 kubelet 事件排成时间线；然后看控制面到节点的两条通信方向，看 Lease 怎么做心跳和选主；最后把控制面容器暂停，观察客户端超时和恢复。过程中会反复区分“控制面记录的期望状态”和“节点上真正跑着的进程”。

> **起点**：第 16 章结束。单节点 kind 集群 `shorty` 里，节点是 `shorty-control-plane`，名字空间 `shorty` 中有 `Deployment api`（1 副本）、`Service api`（ClusterIP 8080）和 `ConfigMap shorty-config`，镜像 `shorty:0.1` 已加载进节点。`bash code/ch17/setup.sh` 会重建集群并 apply `s1-api`。本章不修改应用对象；17.3 临时创建一个 `trace-demo` Pod 后删除，17.6 暂停控制面后会恢复。结束时集群和应用对象与第 16 章相同。

```console

```

输出里有四行以节点名结尾：`etcd-shorty-control-plane`、`kube-apiserver-shorty-control-plane`、`kube-controller-manager-shorty-control-plane`、`kube-scheduler-shorty-control-plane`。这是 kubeadm 部署控制面的方式：每个组件是一个静态 Pod，manifest 放在节点的 `/etc/kubernetes/manifests` 下，由该节点的 kubelet 直接监视并启动，不经过 Deployment 或 ReplicaSet。名字后面的节点名是静态 Pod 的命名约定，不是随机后缀。它们的 IP 与节点的 InternalIP 相同，因为这些 Pod 使用宿主网络；静态 Pod 不是普通工作负载，不参与调度。

另外四行不是控制面。`coredns` 的两个副本是集群 DNS，`kindnet` 是 kind 自带的 CNI DaemonSet，`kube-proxy` 负责 Service 的转发规则。它们放在 `kube-system` 是因为提供集群级功能，不代表它们属于控制面。`kubectl get pods -n kube-system` 看到的是“这个集群装了哪些系统组件”，不是一张固定的架构图；不同发行版、不同 CNI、是否装 Dashboard 或 metrics-server，都会改变这个列表。

四个控制面组件的分工可以先记成一句话：**apiserver 是唯一入口，etcd 是唯一持久存储，scheduler 只做放置决定，controller-manager 只通过 apiserver 改对象。**

`kube-apiserver` 暴露 Kubernetes HTTP API，所有客户端——`kubectl`、kubelet、scheduler、controller-manager、Operator——都连它。它本身不把集群状态存在本地磁盘：对象校验、准入、默认值处理完之后，状态写进 etcd。apiserver 可以水平复制多个实例，前面放负载均衡；每个实例有自己的 watch 缓存，所以“无状态”指的是没有需要持久化的权威数据，不是说进程里没有缓存。Kubernetes 1.26 起，每个 apiserver 还会在 `kube-system` 里写一个 `apiserver-<hash>` 的 Lease 来公布自己的身份，这会在 17.5 看到。

`etcd` 是那个唯一有状态的地方。官方文档把它描述为“保存所有 API server 数据的、一致且高可用的键值存储”。Deployment 的 `spec`、Pod 的 `status`、Service 的 ClusterIP、Lease 的 `renewTime`，最终都在 etcd 里。其他组件不直接连 etcd；scheduler 和 controller-manager 都是通过 apiserver 的 watch 和写接口来读写的。这样做的好处是 etcd 只需要面对 apiserver 一种客户端，认证、授权、准入和版本转换都集中在 apiserver 一层。

`kube-scheduler` 只负责回答“这个 Pod 应该放到哪个节点”。它 watch 那些还没有 `spec.nodeName` 的 Pod，先过滤掉资源不够、亲和性不满足、污点不容忍的节点，再给剩下的节点打分，最后通过 apiserver 的 binding 子资源把选择写回去。它不拉镜像、不创建容器，也不关心容器起来以后是否健康。Pod 被绑定之后，`spec.nodeName` 有了值，这才成为目标节点 kubelet 的“期望状态”。

`kube-controller-manager` 是一个进程里跑了很多个控制循环：Deployment 控制器根据 `replicas` 创建 ReplicaSet，ReplicaSet 控制器再创建 Pod；Node 控制器处理节点失联、加污点和驱逐；Job 控制器创建 Pod 并跟踪完成；EndpointSlice 控制器把 Pod IP 填进 Service 的后端。它同样不运行 Pod，只通过 apiserver 创建、更新、删除对象。控制器之间也不直接调用，一个控制器写下的对象，另一个控制器通过 watch 看到，再接着做下一步。

`cloud-controller-manager` 只在云上出现，负责把节点、路由、LoadBalancer 这些云资源对接进集群。kind 跑在本机 Docker 上，没有云控制器；`kubectl describe node` 里的 `ProviderID: kind://docker/shorty/shorty-control-plane` 是 kind 自己填的，不是云控制器在管节点。自建机房或学习环境里看不到这个组件是正常的。

> **旧资料提示**：旧教程里的“Master 节点”就是今天的控制平面节点。官方文档现在用 control plane（控制平面），`master` 只作为历史称呼保留在术语表里；kubeadm 生成的节点角色标签是 `node-role.kubernetes.io/control-plane`。看到 `master` 字样时按控制平面理解，不要以为它是另一类组件。

这些组件之间没有一张互相直连的网。controller-manager 创建 Pod 是写 apiserver，scheduler 看到 Pod 是 watch apiserver，kubelet 看到 Pod 也是 watch apiserver。唯一的例外是 apiserver 主动连 kubelet 的 10250 端口，用来取日志、`exec` 和 `port-forward`，这条反向连接在 17.4 单独讲。

## 17.2 节点：kubelet、CRI、kube-proxy、CNI

控制面决定“应该有什么”，节点负责“真的跑起来”。在 kind 里，节点本身是一个 Docker 容器，名字是 `shorty-control-plane`；集群里的 Node 对象也叫这个名字。节点上最重要的进程 kubelet 不是 Pod，在这个 kind 节点上是 systemd 服务；容器运行时 containerd 也不是 Pod。`kubectl get pods -n kube-system` 能看到的只有以 Pod 形式部署的 kube-proxy 和 kindnet，看不到 kubelet 和 containerd。

kubelet 的职责可以分成四类：从 apiserver watch 属于本节点的 Pod；通过 CRI 调运行时，按顺序创建 sandbox、拉镜像、起容器；执行 startup/readiness/liveness 探针，把结果写回 Pod 的 `status`；挂载卷、写容器日志、上报节点状态。它不决定 Pod 放在哪，也不创建 Deployment 或 Service；这些是控制面的事。containerd 负责真正的容器生命周期，kubelet 只通过 CRI 的 gRPC 接口和它说话，不直接调 `runc`。

kube-proxy 维护的是 Service 的转发规则。每个节点上的 kube-proxy watch Service 和 EndpointSlice，在节点上写 iptables、IPVS 或 nftables 规则，把发往 ClusterIP 的流量重定向到某个后端 Pod。它不分配 Pod IP，也不决定节点 IP；Pod 网段和 Pod IP 由 CNI 插件负责。这个集群里的 CNI 是 kindnet，它以 DaemonSet 的形式在每个节点跑一个 Pod，给新建的 sandbox 配 veth、分配地址、写路由。

> **旧资料提示**：旧教程说“kube-proxy 给每个节点分配唯一 IP”。节点 IP 由宿主机或云网络决定，kubelet 可以用 `--node-ip` 指定；Pod IP 由 CNI 分配；kube-proxy 只维护 Service 的转发规则，不分配地址。

节点状态有两条上报路径。一条是 Node 对象的 `.status`，kubelet 在状态变化时更新，没有变化时也会定期刷新；另一条是 `kube-node-lease` 名字空间里与节点同名的 Lease，kubelet 默认每 10 秒更新一次 `spec.renewTime`，比完整 Node 状态轻得多。控制面用 Lease 判断节点是否还活着：超过 `node-monitor-grace-period`（默认 50 秒）没有续约，Ready 条件会变成 `Unknown`，再往后可能触发 Pod 驱逐。`kubectl describe node` 顶部的 `Lease` 块就是这条心跳，不是另一个组件。

最后一条 `kubectl top node` 报 `Metrics API not available`。`top` 走的不是 Node 对象的 `Capacity`，而是 Metrics API；这个集群还没有装 metrics-server，所以没有数据。第 29 章装好 metrics-server 之后，`kubectl top node` 才会显示 CPU/内存的实际使用量。现在要看资源承诺，读 `describe node` 的 `Allocated resources`；要看实际用量，得先有 metrics 管线。

## 17.3 一次 apply 的旅程

知道了组件是谁，接下来把一个 Pod 从提交到 Running 的过程拆开。这里故意用一个裸 Pod，不经过 Deployment：如果还用 `Deployment api`，中间会多出 Deployment 控制器创建 ReplicaSet、ReplicaSet 控制器创建 Pod 两步，时间线会更长。裸 Pod 能把“apiserver 写入—调度—kubelet 启动”这三段看得更清楚。

第一段只保留了三行：一条 GET、一条 POST 和 `pod/trace-demo created`。GET 的 URL 是 `/api/v1/namespaces/shorty/pods/trace-demo`，返回 `404 Not Found`；这说明对象还不存在。接着 POST 到 `/api/v1/namespaces/shorty/pods`，返回 `201 Created`。这是客户端 apply 的典型节奏：先读活对象，不存在才创建；存在则算 patch。`kubectl create` 不读，直接 POST，对象已存在就报 `AlreadyExists`。URL 里的 `fieldManager=kubectl-client-side-apply` 说明这次写入的字段管理者是客户端 apply，第 18 章讲 SSA 时会再看到这个字段。

`201 Created` 只代表 apiserver 已经把对象写进 etcd 并返回了响应。此时调度器可能还没看到它，kubelet 更没开始拉镜像。所以 `apply` 后面紧跟 `get pods` 看到 `Pending` 或短时间的空列表，不是命令失败，而是异步链路还没走完。例子用 `kubectl wait --for=condition=Ready` 等到 Pod 真正就绪，而不是 `sleep` 一个拍脑袋的秒数；这也是判断“到底跑起来没有”的可靠办法。

从 POST 到 Running，中间至少发生这些事：

1. **TLS 与认证**：`kubectl` 用 kubeconfig 里的客户端证书连 apiserver 的 HTTPS 端口（kind 把节点容器的 6443 映射到本机的一个高位端口）。apiserver 用配置的 CA 验证证书，把请求关联到一个用户名和组；证书无效或缺失会得到 401。
2. **授权**：apiserver 把“用户、动词 create、资源 pods、名字空间 shorty”交给授权模块。kubeadm 默认启用 RBAC 和 Node 授权；没有权限的用户会得到 403，而不是 404。
3. **准入**：请求先过 mutating 准入（可以改对象，例如补 ServiceAccount、加默认 toleration），再过 validating 准入（只做接受/拒绝）。ServiceAccount、LimitRanger、ResourceQuota、PodSecurity 都在这一层；任何一个拒绝，整个请求立刻失败。
4. **校验与持久化**：apiserver 按 Pod 的 schema 做字段校验，分配 `uid`、`resourceVersion`，把对象写进 etcd。写成功之后，watch 缓存收到变更，所有 watch 这个资源的客户端都会收到事件。
5. **调度**：scheduler watch 到没有 `spec.nodeName` 的 Pod，过滤、打分，选出一个节点，通过 binding 把节点写回 Pod。Event 里的 `Scheduled` 就是这一步，来源是 `default-scheduler`。
6. **kubelet 启动**：目标节点的 kubelet watch 到“分配给我的新 Pod”，通过 CRI 调 containerd。顺序通常是先建 Pod sandbox（pause 容器、网络 namespace、CNI 配网），再拉镜像（已经存在就跳过下载），然后创建并启动业务容器。
7. **状态回写**：kubelet 把容器 ID、镜像 ID、`Ready` 条件、重启次数写回 Pod 的 `status`，apiserver 再写进 etcd。`kubectl wait` 看到 `Ready=True` 才返回。

事件表把第 5 到第 7 步按时间排了出来。`Scheduled` 的来源是 `default-scheduler`，消息是 `Successfully assigned shorty/trace-demo to shorty-control-plane`，时间戳比后面三条早一秒；后面三条 `Pulled`、`Created`、`Started` 的来源都是 `kubelet`，`Pulled` 的消息明确说镜像 `already present on machine`，这三条落在同一秒，`--sort-by=.lastTimestamp` 排不出更细的先后，只能靠因果理解：先有调度，kubelet 才可能看到 Pod；先有 sandbox 和镜像，才有容器创建和启动。`kubectl get events` 的默认列里还有 `OBJECT` 和 `MESSAGE`，排障时优先看 `REASON` 和 `SOURCE`，它们直接告诉你哪一环在说话。

任何一步失败，都会在这条链上留下不同的痕迹。认证失败是 401，授权失败是 403；准入拒绝通常带一条明确的错误消息，资源不合法是 4xx；调度不上去，Pod 停在 `Pending`，Event 里是 `FailedScheduling` 和具体原因（资源不足、污点、亲和性）；镜像拉不下来是 `ImagePullBackOff`；容器起来又退出是 `CrashLoopBackOff`，`kubectl describe pod` 的 `State` 和 `Last State` 会有退出码。把这些现象和链路上的位置对上，比单纯背 Pod 的几种状态有用。

例子最后删掉了 `trace-demo`。这个 Pod 只是为了看请求和事件，不属于 `shorty` 的应用对象；本章结束时，`shorty` 里仍然只有 `Deployment api` 和 `Service api`。

## 17.4 控制面到节点的通信

17.3 的链路里有一个容易被忽略的方向：kubelet 不是被动等 apiserver 推消息，而是主动 watch；但 `kubectl logs`、`kubectl exec`、`kubectl port-forward` 又是 apiserver 主动连 kubelet。两个方向都存在，走的端口和证书也不同。

节点到控制面是主方向。kubelet 启动时用 kubeconfig 里的客户端证书连 apiserver 的 6443，之后 watch 分配给自己的 Pod、更新 Pod 的 `status`、写 Event、续约 Lease。Pod 里的进程要访问 apiserver 时，用的是挂载进容器的 ServiceAccount token 和集群 CA，走 `kubernetes` Service 的 ClusterIP，再由 kube-proxy 转到 apiserver。官方文档把这叫 hub-and-spoke：节点和 Pod 的所有 API 调用都终止在 apiserver，其他控制面组件不对外暴露远程服务。

控制面到节点是反方向。apiserver 要取容器日志、attach 到进程、转发端口时，连的是 kubelet 的 HTTPS 端口 10250。端口表里写得很清楚：10250 是 Kubelet API，使用者是节点自己和控制面。`kubectl exec` 的路径是：kubectl → apiserver 的 exec 子资源 → apiserver 作为客户端连 kubelet 的 10250 → kubelet 通过 CRI 在容器里执行命令。`kubectl logs` 和 `port-forward` 也走这条代理，不直接从你的电脑连 Pod IP。

> **旧资料提示**：旧教程里的“apiserver 默认有一个 8080 insecure port”已经不成立。Kubernetes 1.24 移除了 `--insecure-port`、`--insecure-bind-address`、`--address`、`--port` 这些不安全地址参数（它们在 1.20 起就已经不起作用）；kubeadm 至今仍在静态 Pod 清单里写 `--insecure-port=0`，只是把这个历史选项明确关掉。今天 apiserver 只提供 HTTPS，默认端口 6443。

证书这件事要说得准确一点。kubelet 连 apiserver 时出示客户端证书，apiserver 用集群 CA 验证；apiserver 连 kubelet 时也出示客户端证书（kubeadm 生成的是 `apiserver-kubelet-client.crt`），kubelet 用 `clientCAFile` 验证它。但 apiserver 默认**不验证 kubelet 的服务端证书**：官方文档明确说，默认情况下 apiserver 不校验 kubelet 的 serving certificate，这让连接可能被中间人攻击，不适合在不可信网络上跑。要开启校验，得给 apiserver 传 `--kubelet-certificate-authority`。所以“双向 TLS”只对了一半：双方都会出示证书，但服务端证书的校验默认只发生在 kubelet 这一侧。


kubelet 配置里 `authentication.anonymous.enabled` 是 `false`，`webhook.enabled` 是 `true`，`authorization.mode` 是 `Webhook`。这三项决定了请求的命运：没有客户端证书、也不是 ServiceAccount token 的请求，连匿名身份都拿不到，直接在认证阶段被拒绝，返回 401。`curl -k` 只跳过客户端对服务端证书的校验，不会让 kubelet 相信你；`-k` 在这里只是为了看到 401，而不是让连接被证书错误挡住。

这里要纠正一个常见说法：“kubelet 默认关闭匿名访问。”上游 kubelet 的默认其实是允许匿名请求，默认授权模式是 `AlwaysAllow`；kubeadm 生成的 kubelet 配置把 `anonymous.enabled` 设成 `false`、授权模式设成 `Webhook`，才变成现在这样。换句话说，401 是 kubeadm 的安全基线，不是 kubelet 的通用默认值。自建集群如果只看到“能连上 10250”，不要以为这是安全的；要检查 kubelet 的 `--anonymous-auth`、`--authorization-mode` 和 `--client-ca-file`。

`kubectl exec` 能成功，是因为 apiserver 有 kubelet 认可的客户端证书，并且 kubelet 会把授权请求转给 apiserver 的 SubjectAccessReview。普通用户能不能 exec，取决于他在 apiserver 侧有没有 `pods/exec` 的 create 权限；kubelet 只负责执行 apiserver 已经授权的请求。`/shorty version` 输出了 `shorty dev`，说明命令确实进了容器，而不是在节点上跑。

如果控制面不能直接连到节点——节点在私有子网、NAT 后面，或者防火墙只允许节点主动外连——就用 Konnectivity。它在控制面网络里跑一个 server，在节点网络里跑 agent；agent 主动连 server 并保持连接，控制面到 kubelet、Pod、Service 的流量都从这条连接走。官方文档把它作为 SSH tunnel 的替代品；SSH tunnel 已弃用，不要在新建集群里用。Konnectivity 的文档状态是 beta（v1.18 起），生产使用前要按所用发行版的版本确认。

不管用不用 Konnectivity，10250 都不应该暴露到公网。kubelet API 能看日志、执行命令、转发端口，等于节点上的一个高权限入口；官方端口表把它列为控制面/节点内部使用，不是给终端用户直连的。

## 17.5 高可用与 Lease

单节点 kind 集群里，scheduler 和 controller-manager 都只有一个实例，“选主”看起来没有意义；但 Lease 对象仍然存在，因为同一套机制在 HA 集群里决定谁干活。先看这些 Lease，再看生产环境的 3/5 节点拓扑。

```console

```

`kube-system` 里的 Lease 不止业务组件。`kube-scheduler` 和 `kube-controller-manager` 是选主用的；`apiserver-<hash>` 是每个 apiserver 公布自己身份的 Lease，名字里的 hash 来自该 apiserver 看到的主机名，`holderIdentity` 是“名字_uuid”的形式。apiserver 的 Lease 在官方示例里 `leaseDurationSeconds` 是 3600，不是 15 秒级的抢占锁；它不用于抢占式选主，而是让客户端能发现当前有几个 apiserver。apiserver 退出后，过期的身份 Lease 由新的 apiserver 在 1 小时后回收。

第二张表把 scheduler 和 controller-manager 的字段单独列出来：`holderIdentity` 是当前 leader，`renewTime` 是最近一次续约，`DURATION` 是 15 秒。leader 会周期性地更新 `renewTime`，其他实例 watch 这个对象；如果 leader 在租约过期前没有续上，别的实例就会尝试用新的 `holderIdentity` 更新它，靠 `resourceVersion` 的乐观并发保证只有一个成功。`holderIdentity` 里带节点名和 uuid，所以组件重启后 identity 会变；看到 holder 变化，先查组件是不是重启过，不要直接当成“集群被入侵”。

`kube-node-lease` 里是每个节点的心跳 Lease，名字和 Node 对象相同，`holderIdentity` 就是节点名。它和 `kube-system` 里的选主 Lease 不是一回事：节点 Lease 由 kubelet 续，用来判断节点是否存活；选主 Lease 由控制面组件续，用来保证同一时刻只有一个 scheduler/controller-manager 在写。两者都用 `coordination.k8s.io/v1` 的 Lease 对象，但目的、续约周期和消费者不同。

生产控制面一般跑 3 或 5 个节点。kubeadm 的默认拓扑是 stacked etcd：每个控制面节点上同时跑 apiserver、scheduler、controller-manager 和一个本地 etcd member；apiserver 前面放一个负载均衡，kubelet 和 kubectl 连 LB，不直接连某一个 apiserver。另一种是 external etcd：控制面和 etcd 分开，至少 3 个控制面节点加 3 个 etcd 节点。stacked 省机器，但一台机器挂掉会同时损失一个控制面实例和一个 etcd member；external 多一倍机器，换来的是一层故障隔离。两种拓扑都要求奇数个 etcd member，才能形成稳定的多数派。

etcd 用 Raft 复制日志，写请求要多数派确认才能提交。多数派永久丢失时，etcd 集群就算失败：Kubernetes 无法再修改状态，已经调度好的 Pod 可能继续跑，但新 Pod 无法调度。注意这不是“自动切到只读模式”：读请求也可能因为拿不到一致的 `resourceVersion` 而失败，apiserver 的 `/readyz` 会报 etcd 相关检查失败。官方文档的措辞是“cannot make any changes to its current state”，不是“还可以正常读”。

多副本控制面还要解决“谁是新 leader”的问题。普通 Lease 选主是抢占式的：谁先更新成功谁当 leader。Kubernetes 1.31 引入 alpha、1.33 进入 beta 的 `CoordinatedLeaderElection` 特性门控提供了另一种方式：组件通过 LeaseCandidate 注册自己的 binary version 和 emulation version，选主策略 `OldestEmulationVersion` 优先选 emulation version 最低的实例，再比 binary version 和创建时间。这样在控制面滚动升级、新旧版本并存的窗口里，可以让旧版本的实例继续当 leader，减少版本切换带来的抖动。这个特性在 1.33 默认关闭，要同时打开 `CoordinatedLeaderElection` 门控和 `coordination.k8s.io/v1beta1` API 组；不打开时仍然用原来的 Lease 抢占式选主。

单节点集群里，scheduler 和 controller-manager 的 Lease 只有自己持有，没有 standby；它们挂了就是挂了，不会有人接管。HA 集群里才有“leader 挂了，另一个实例在 15 秒租约过期后接手”这回事。生产上要监控 Lease 的 `renewTime` 是否持续更新，而不是只看 Pod 是不是 Running：组件进程还在、但选主循环卡住，Pod 仍然显示 Running，实际已经不再干活。

## 17.6 故障注入：把 apiserver 暂停

前面看的都是正常路径。要验证“控制面挂了会怎样”，最直接的办法是把控制面停掉。kind 的控制面是一个 Docker 容器，名字是 `shorty-control-plane`；在 lab 里可以用 `docker pause` 冻结它，模拟 apiserver 不可达，再用 `docker unpause` 恢复。这个操作不会删容器，也不会重建集群，适合做一次可逆的故障演练。

```console
{{#include code/ch17/17_6_apiserver_pause.out}}
```

`docker pause` 的输出是容器名，随后 `kubectl` 在 5 秒的请求超时后报 `Unable to connect to the server: …`，后半句是 `context deadline exceeded` 或 `request canceled while waiting for connection (Client.Timeout exceeded while awaiting headers)`：两者都是客户端超时，只是超时时连接所处的阶段不同，每次运行可能出现其中任意一种。这不是 403，也不是 404：请求根本没有得到 HTTP 响应。`timeout 20` 是外层保险，防止 kubectl 在没有超时的情况下一直挂着；真正让命令返回的是 `--request-timeout=5s`。恢复后，`kubectl wait` 重新连上 apiserver，Pod 回到 `Ready`，`kubectl get pods` 显示它还在，重启次数没有增加；最后的 UID 比较说明这个 Pod 没有被删除重建。

这里有一个必须说清楚的 lab 限制：kind 的“控制面容器”同时就是唯一的工作节点。`docker pause shorty-control-plane` 冻结的不只是 apiserver，还包括这个容器里的 kubelet、containerd 和 `shorty` 容器。所以在暂停的 15 秒里，Pod 的进程其实也被冻住了，它并没有继续对外服务。恢复后 UID 不变、容器没有重启，说明的是“状态没有丢”，不是“数据面一直可用”。

在多节点集群里，控制面和 worker 是不同机器：暂停控制面不会停掉 worker 上的 kubelet 和容器，已经运行的 Pod 可以继续跑；但新 Pod 无法调度，Pod 状态和 EndpointSlice 不再更新，`kubectl` 也读不到最新状态。这个结论来自控制面与节点分离的架构，本书的单节点 lab 没有在本地验证多节点下的持续服务。官方的 etcd 文档也提醒：多数派永久丢失时，Kubernetes 不能修改状态，已经调度的 Pod 可能继续运行，但新 Pod 无法调度。

恢复之后，kubelet 和 controller-manager 的 watch 连接要重新建立。watch 断线重连时，客户端会带着最后的 `resourceVersion` 重新 list/watch；如果这个版本已经被 etcd 压缩掉，apiserver 返回 `410 Gone`，客户端必须重新 list 一次再开始 watch。`kubectl` 每次命令都是新连接，所以它看起来只是“超时了一下，然后又好了”；常驻的控制器和 kubelet 则会在日志里留下重连和重新同步的痕迹。

用 `docker pause` 做演练要注意两点。第一，它冻结整个容器，不是只停 apiserver 进程；在单节点 kind 里，这等于把整个集群冻住。第二，它不是 HA 测试：真正的 HA 要验证“一个 apiserver 挂了，LB 把请求转到另一个”“一个 etcd member 挂了，多数派还在”“scheduler leader 挂了，standby 在租约过期后接手”。这些需要至少 3 个控制面节点，本书的 2.5 GB lab 跑不下，只讲机制，不做本地演练。

## 17.7 排障：连接被拒绝与节点 NotReady

`kubectl` 报 `The connection to the server 127.0.0.1:... was refused` 时，先分清是“连不上 apiserver”还是“apiserver 返回了错误”。`refused` 是 TCP 层被拒绝：端口没有进程监听，或者 Docker 的端口映射不在了。它和 401、403、404 完全不是一类问题，改 kubeconfig 里的用户或权限不会有帮助。

```console

```

例子故意把 server 指到 `https://127.0.0.1:1`，复现 refused 的文本；前面几行 `memcache.go` 是客户端在重试 API 组发现，最后一行 `The connection to the server ... was refused` 才是结论。真实环境里端口来自 kubeconfig 的 `server` 字段，kind 通常是 `127.0.0.1` 上的一个高位端口，不是 6443。看到这个错误，按下面的顺序查：

1. `kubectl config view --minify` 看当前 context 的 `server` 是不是你以为的那个集群；多套 kubeconfig 时，context 选错比集群坏了更常见。
2. `kind get clusters` 看 `shorty` 还在不在；不在就说明集群被删了，`kubectl` 当然连不上。
3. `docker ps --filter name=shorty-control-plane` 看控制面容器是否在跑。输出里的 `Up` 表示容器在，`Exited` 表示容器退了；`docker pause` 过的容器仍然是 `Up`，但不会响应请求，需要 `docker unpause`。
4. `docker logs shorty-control-plane` 看节点容器的 stdout。这个 kind 节点上它没有输出：节点由 systemd 启动，启动日志进了 journald，不在容器的 stdout 里。所以它既不是 apiserver 日志，也不能当控制面启动日志用；apiserver 是节点里的静态 Pod，日志要看 `kubectl -n kube-system logs kube-apiserver-shorty-control-plane`，apiserver 已经不可用时则进节点用 `crictl ps -a` 找到容器再 `crictl logs`。
5. 容器退了就 `docker start shorty-control-plane`；只是 pause 就 `docker unpause shorty-control-plane`；集群状态坏了，删掉重建比在容器里手工修更省时间：`kind delete cluster --name shorty`，再跑 `bash code/ch17/setup.sh`。

第二个常见故障是节点 `NotReady`。这时 apiserver 是好的，`kubectl get nodes` 能看到节点，只是 `STATUS` 不是 `Ready`。先 `kubectl describe node shorty-control-plane` 看 `Conditions`：`Ready` 的 `Status` 是 `False` 还是 `Unknown`，`Reason` 是 `KubeletNotReady`、`NodeStatusUnknown` 还是别的；再看 `NetworkUnavailable` 是否 `True`，`MemoryPressure`/`DiskPressure`/`PIDPressure` 是否有一个为 `True`。`KubeletReady` 是健康时的 `Reason`，不是条件类型；不要把 `Ready` 和 `KubeletReady` 当成两个条件。

如果 `Ready` 是 `Unknown`，通常是 kubelet 不再续约 Lease，或者节点到 apiserver 的网络断了；如果是 `False`，更像 kubelet 还在、但自己报告了不健康。`NetworkUnavailable=True` 指向 CNI：kindnet 的 Pod 没起来、Pod 网段配错，或者节点容器网络被破坏。资源压力条件为 `True` 时，先看磁盘和内存，不要继续往节点上调度。

进节点看进程：`docker exec shorty-control-plane crictl ps` 看容器运行时里还有哪些容器；`docker exec shorty-control-plane journalctl -u kubelet -n 50 --no-pager` 看 kubelet 最近的日志；`systemctl status kubelet` 和 `systemctl status containerd` 看两个服务是不是 active。kubelet 挂了，静态 Pod 也会受影响；containerd 挂了，kubelet 会报 CRI 连接失败。单节点 kind 里，节点容器被 pause 或 stop 也会表现成 NotReady，所以先确认 `docker ps` 里的状态，再进节点查。

排障的顺序可以总结成“从外往里”：先确认 kubeconfig 指向的 server 和集群存在，再确认控制面容器和端口，再确认 apiserver 的 `/readyz`，最后才进节点看 kubelet 和运行时。反过来，一上来就翻 apiserver 日志，很容易在 context 选错这种问题上绕很久。

## 上生产前

生产控制面至少 3 个节点，规模大或升级窗口要求高时用 5 个；etcd 用独立磁盘，避免和容器镜像、日志抢 I/O；apiserver 前面放负载均衡，kubelet 和用户都连 LB，不直连某一个实例。控制面节点不要跑业务 Pod：生产集群通常保留 `node-role.kubernetes.io/control-plane:NoSchedule` 污点，让普通 Pod 调度不上去；如果为了省机器把污点去掉，业务和 apiserver、etcd 会互相抢 CPU、内存和磁盘，故障时一起挂。这个 kind 集群的 `Taints` 是 `<none>`，所以 `shorty` 能落在控制面节点上；这是单节点教学环境对拓扑的简化，不是生产配置。

监控要覆盖三层。apiserver 用 `kubectl get --raw '/readyz?verbose'` 看每个检查项，etcd 的 `etcd ok`、`etcd-readiness ok` 失败了，先查 etcd 而不是 apiserver；etcd 还要看磁盘 fsync 延迟和 WAL 目录的 IO，etcd 对磁盘延迟非常敏感；scheduler 和 controller-manager 看 Lease 的 `renewTime` 是否持续更新，Lease 不续约比 Pod 显示 Running 更能说明组件已经失去领导权。节点侧看 `Ready` 条件和 Lease，不要只看 `kubectl get nodes` 的 `STATUS` 一列。

网络只开必要端口：apiserver 的 6443（或 LB 的 443）、kubelet 的 10250（只对控制面开放）、etcd 的 2379-2380（只对 apiserver 和 etcd 成员开放）。控制面不能直连节点时用 Konnectivity，让节点侧的 agent 主动外连，不要把 10250 暴露到公网；kubelet API 能执行命令、读日志，暴露它等于把节点的高权限入口交出去。节点之间和节点到控制面的流量放在私有网络，公网只暴露 LB 的 443。

升级前先查 API 弃用和组件版本偏差，按 kubeadm 的顺序：先升第一个控制面节点，再升其余控制面节点，最后升 worker；不要跳过 minor 版本。控制面先升、节点后升，是因为 apiserver 要能接受旧 kubelet 的连接，而旧 apiserver 不一定认识新 kubelet 的字段。升级前备份 etcd，升级后验证 `/readyz`、Lease 续约和业务 Pod 的 `Ready`，不要只看 `kubectl version` 的版本号。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `kubectl get --raw '/readyz?verbose'` | 逐项检查 apiserver、etcd、informer 等是否就绪 | 任一项失败时 HTTP 返回非 200；输出里能看到 `etcd ok` |
| `kubectl get pods -n kube-system -o wide` | 看控制面静态 Pod、DNS、CNI、kube-proxy | 静态 Pod 名以节点名结尾，IP 是节点 IP |
| `kubectl describe node <node>` | 看 `Capacity`、`Allocatable`、`Conditions`、`Non-terminated Pods`、`Lease` | 不显示实际用量；实际用量要 metrics |
| `kubectl get lease -n kube-system` | 看 scheduler、controller-manager、apiserver 的 Lease | `holderIdentity`/`renewTime` 用 `-o yaml` 或 custom-columns 看 |
| `kubectl get lease -n kube-node-lease` | 看每个节点的心跳 Lease | kubelet 默认每 10 秒续约 |
| `kubectl apply -v=6 -f <file>` | 看客户端发出的请求 URL 和响应码 | 只是客户端日志，不代表对象已经 Running |
| `kubectl get events --sort-by=.lastTimestamp` | 按时间看调度和 kubelet 事件 | 同一秒的事件要靠因果关系排序 |
| `kubectl top node` | 看节点实际 CPU/内存用量 | 需要 metrics-server；没装时报 `Metrics API not available` |
| `kubectl exec -n shorty deploy/api -- /shorty version` | 验证 apiserver 经 10250 代理到 kubelet | 需要 `pods/exec` 的 create 权限 |
| `docker pause shorty-control-plane` / `docker unpause ...` | 冻结/恢复 kind 控制面容器 | 只用于 lab；单节点会把工作负载一起冻结 |
| `crictl ps` / `crictl logs <id>` | 在节点里看容器运行时和容器日志 | 需要进节点执行 |
| `journalctl -u kubelet -n 50 --no-pager` | 看 kubelet 日志 | 节点 NotReady 时先看这里 |

| 字段 | 含义 | 备注 |
|---|---|---|
| `Node.status.capacity` | 节点上报的总资源 | 包含系统预留前的量 |
| `Node.status.allocatable` | 可分配给普通 Pod 的资源 | 已扣掉 `systemReserved`/`kubeReserved` 等 |
| `Node.status.conditions[].type=Ready` | 节点是否可接受 Pod | `Reason=KubeletReady` 是健康时的原因 |
| `Node.status.conditions[].type=NetworkUnavailable` | CNI 是否配置好 | 健康时可能不出现；出现 `True` 要查 CNI |
| `Pod.spec.nodeName` | 调度器绑定的节点 | 为空表示还没调度 |
| `Lease.spec.holderIdentity` | 当前 leader 或节点身份 | 组件重启后可能变化 |
| `Lease.spec.renewTime` | 最近一次续约时间 | 不更新说明 holder 可能已经卡住 |
