# 第 33 章 扩展 Kubernetes：CRD、控制器与 Operator

shorty 的备份一直是手工活：登录到 postgres Pod，跑一次 `pg_dump`，把文件拷出来。有人提议做成 Kubernetes 原生对象，以后只要写一个 `ShortyBackup`，再 `kubectl get shortybackup` 就能看到备份状态。YAML 很快就写好了，`kubectl apply` 也返回了 `created`，可是集群里没有多出任何 Job，数据库也没有被备份。问题不在 YAML 写错了，而在于 Kubernetes 只认识了一个新的数据结构，还没有任何程序去响应它。

这就是 API 扩展和控制器要分开讲的原因。Kubernetes 的 API 是声明式的：客户端把“想要什么”写进对象，apiserver 负责校验和存储，至于“怎么做到”，由控制器去补。CRD 只完成前半段，让 apiserver 接受一种新对象，负责校验、存储、版本和 RBAC；它不执行任何业务逻辑。要让 `ShortyBackup` 真的变成一次 `pg_dump`，需要另一个程序 watch 这些对象，比较期望状态和实际状态，再创建 Job、更新 status。这个程序就是控制器；把领域知识写进控制器，再用 CRD 暴露配置，合起来就是 Operator。

本章沿着这条线做三件事：先加 CRD，看清“只是存数据”的边界；再写一个最小 Operator，把 CR 协调成备份 Job；最后给 CRD 加版本、给控制器加 finalizer 和 status，并故意制造“没有 Job”“删不掉”“RBAC 拒绝”这些故障。整个过程都在 `s4-prod` 上做，shorty 的 api、worker、postgres、redis 和现有 NetworkPolicy 都不动。

> **起点**：`s4-prod` 已就绪，命名空间 `shorty` 里有 api、worker、postgres、redis、RBAC、NetworkPolicy 和 Gateway。从本章目录执行 `bash code/ch33/setup.sh`，它会建好集群和 `s4-prod`，再构建并加载本章要用的 `shorty-operator:0.1` 镜像。

## 33.1 API 扩展的两条路

Kubernetes 提供两种把新 API 加进集群的方式。第一种是 CustomResourceDefinition（CRD）：写一个 `apiextensions.k8s.io/v1` 的 CRD 对象，声明组、版本、资源名、作用域和 schema，apiserver 就会为它生成 REST 路径，像处理 Pod、Service 一样处理它的对象。第二种是聚合层（aggregation layer）：注册一个 `APIService`，把某个 URL 路径交给集群里另一个 extension apiserver 处理；这个 apiserver 自己实现 REST 语义和存储，主 apiserver 只做代理。

两者不是替代关系。CRD 的优点是简单：不用写 apiserver，不用额外部署服务，schema、版本、RBAC、watch、finalizer 这些通用能力都由主 apiserver 提供。CRD 的 `metadata.name` 必须是 `<复数>.<组>` 的形式，比如 `shortybackups.shorty.example.com`；apiserver 据此生成 `/apis/shorty.example.com/v1alpha1/namespaces/<ns>/shortybackups` 这样的 REST 路径。`kubectl` 不需要为 CRD 装插件，它从 discovery 里读到组、版本、资源名和作用域，就能拼出请求。代价是它只能按 Kubernetes 的对象模型工作，存储固定在 etcd，补丁支持 JSON Patch、JSON Merge Patch 和 Server-Side Apply，但不支持为内置类型准备的那种 Strategic Merge Patch。聚合层反过来：你可以自己决定存储、协议和额外的子资源，但要自己构建、部署、升级一个 apiserver，还要保证它对 apiserver 的 discovery 请求在五秒内返回。官方文档的建议很直接：字段不多、主要给自己或小项目用，选 CRD；需要特殊存储、特殊 REST 路径，或者要支持 Protocol Buffers 之类的能力，才考虑聚合层。

| 对比项 | CRD | 聚合 API |
|---|---|---|
| 要不要写 apiserver | 不用，主 apiserver 直接服务 | 要，自己实现并部署 |
| 存储 | etcd，和内置对象一样 | 自己决定 |
| 版本与转换 | 支持多版本，转换用 None 或 webhook | 自己实现 |
| 适用场景 | 大多数领域对象、Operator 的配置入口 | 特殊存储、特殊协议、额外子资源 |

什么时候不该加 CRD？如果配置本来就是一个格式完整的文件，比如 `my.cnf`、`pom.xml`，或者程序只会在 Pod 里把它当文件读，ConfigMap 更合适；如果数据是敏感凭据，用 Secret。CRD 适合的是“要让 `kubectl` 和客户端库把它当一等对象操作、要用 `.spec/.status` 约定、要写控制器观察它”的场景。本章的备份请求需要 status、需要控制器、需要 `kubectl get` 看到进度，所以它适合 CRD，而不是塞进一个 ConfigMap 的 key 里。

## 33.2 CRD schema、版本与子资源

`apiextensions.k8s.io/v1` 要求 CRD 带结构化 schema（structural schema）。结构化的意思是：根节点和每个对象字段都要有非空的 `type`，数组要有 `items`，`allOf`、`anyOf`、`oneOf`、`not` 里出现的字段必须在外面也声明过，`metadata` 只能限制 `name` 和 `generateName`。不满足这些规则的 CRD 会在 `NonStructural` 条件里报出来，schema 也就不能可靠地做裁剪和默认值。

本章的 CRD 里，`spec.database` 是 `string`、`enum: [postgres]`、默认 `postgres`，`spec.retentionDays` 是 `integer`、范围 1 到 30、默认 7。`required` 只列了 `database`，所以 `retentionDays` 可以省略，apiserver 会在准入时把默认值填进去。默认值属于 schema，不是控制器逻辑；控制器读到的对象里已经有 `retentionDays: 7`，不需要自己再补。

schema 同时决定“哪些字段能进来”。`apiextensions.k8s.io/v1` 默认开启裁剪（pruning）：apiserver 不认识、schema 里也没有声明的字段，在写进 etcd 之前会被删掉。这个行为和 v1beta1 时代的 `preserveUnknownFields: true` 相反；v1 要求结构化 schema，并把 `preserveUnknownFields` 固定为 `false`。如果确实要保留一段任意 JSON，可以在子树里写 `x-kubernetes-preserve-unknown-fields: true`，但这会放弃那一段的字段校验，不应该拿来当偷懒的开关。

裁剪和“拒绝”是两件事。`kubectl apply` 默认会做服务端字段校验（field validation），遇到 schema 里不存在的字段时，apiserver 返回的是 strict decoding error，而不是悄悄裁掉；只有客户端显式关掉校验，或者请求没有要求 strict，未知字段才会被裁剪。类型错误则由 schema 校验直接拒绝。示例先制造这两种失败，再把 `compress` 加进 schema，让同一个对象通过。

第一条错误是 `strict decoding error: unknown field "spec.compress"`：`compress` 不在 schema 里，请求在解码阶段就被拒绝，对象没有创建。第二条是 `spec.retentionDays in body must be of type integer: "string"`：字段存在，但传了字符串，schema 的 `type` 校验失败。把 `compress` 加进 schema 并重新 apply CRD 之后，同一个 `shorty-backup-bad` 创建成功；读回来的 `retentionDays` 是 `7`，`compress` 是 `true`，说明默认值和显式字段都生效了。最后的 `kubectl get` 里 `PHASE` 是空的，因为这时还没有控制器写 status，这个空列本身就是下一节的引子。示例最后把这个演示对象删掉，避免它进入后面的 reconcile。

版本在 `spec.versions` 里声明。每个版本有 `name`、`served` 和 `storage`：`served` 决定这个版本有没有 REST 端点，`storage` 决定新写入的对象存到哪个版本；有且只有一个版本能是 `storage: true`。多个版本可以共用 schema，也可以各自写 schema。`conversion.strategy` 只有两个值：`None` 表示读不同版本时只改 `apiVersion`，适合各版本字段完全一样的情况；`Webhook` 表示把转换交给一个外部服务，适合字段改名、结构变化的情况。`None` 不是“自动帮你转换”，schema 不同却用 `None`，读出来的对象很可能缺字段。

子资源（subresources）是 CRD 另一组常用字段。`subresources.status: {}` 会暴露 `/status` 子资源：对主资源的 PUT/POST/PATCH 忽略 status 的改动，对 `/status` 的 PUT 只校验 status；`metadata.generation` 在 spec 变化时递增，改 metadata 或 status 不递增。这让控制器可以只写 status，而用户只写 spec，RBAC 也能把两者分开授权。`subresources.scale` 则把 `.spec.replicas` 和 `.status.replicas` 映射成 `/scale`，让 HPA、PDB 这类按副本数工作的组件能操作自定义资源；本章的备份对象没有副本概念，所以只用 status。

`shortNames` 和 `categories` 只影响 `kubectl` 的别名和分组，不改变 API；`deprecated` 和 `deprecationWarning` 则会在客户端访问旧版本时返回警告头，给迁移留出提示。`selectableFields` 可以让字段选择器使用 `spec` 里的字段，但它是较新的能力，用之前要确认集群版本和特性门控。`additionalPrinterColumns` 决定 `kubectl get` 显示哪些列。示例里加了 `Database`、`Phase`、`Age` 三列；`NAME` 是隐式列，不用声明。列的 `type` 可以是 `integer`、`number`、`string`、`boolean`、`date`，值类型不匹配时该列留空；`priority` 大于 0 的列只在 `-o wide` 下显示。把 `Phase` 指向 `.status.phase` 很实用：控制器还没写 status 时它空着，写完之后 `kubectl get` 直接能看到进度。

> **旧资料提示**：旧资料常说“Kubernetes 没有通用策略控制器，做校验必须装 Gatekeeper”。ValidatingAdmissionPolicy 在 Kubernetes 1.30 成为稳定特性，用 CEL 就能做字段级和对象级校验；Gatekeeper/OPA 仍有它的位置，但不是所有策略的前提。

> **旧资料提示**：另一条旧写法是用 OpenAPI v2 的 `swagger.json` 和 Strategic Merge Patch 描述 API 扩展。现在 apiserver 同时提供 OpenAPI v2 和 v3，v3 是首选，因为它对 schema 的表示更完整；Server-Side Apply 在 Kubernetes 1.22 成为稳定特性。CRD 不支持 Strategic Merge Patch，更新自定义对象应该用 JSON Merge Patch、JSON Patch 或 Server-Side Apply。

字段级校验之外，跨字段规则和更复杂的策略可以写在 CRD 的 `x-kubernetes-validations` 里（CEL 表达式），也可以用 ValidatingAdmissionPolicy。ValidatingAdmissionPolicy 在 Kubernetes 1.30 成为稳定特性，用 CEL 声明校验，不需要为每条规则部署一个 webhook。它不是“必须装 Gatekeeper 才能做策略”的反例，而是说：Kubernetes 自带的准入策略已经能覆盖不少字段级和对象级检查；Gatekeeper/OPA 仍然适合需要 Rego 生态和跨集群策略分发的场景，但不是所有校验的前提。

## 33.3 控制器模式

控制器是一个控制循环：观察至少一种资源，读出期望状态，比较实际状态，然后采取行动让两者靠近。Kubernetes 内置的 Job 控制器就是这样工作的：你创建一个 Job，期望它完成；Job 控制器创建 Pod，Pod 完成后它把 Job 标成 `Finished`。控制器通常不自己运行容器，它向 apiserver 发请求，让 kubelet、Job 控制器这些组件去完成实际动作。

自定义控制器也一样。它 watch `ShortyBackup` 对象，把对象的 name 放进工作队列，然后调用 `reconcile`。`reconcile` 读当前对象，检查 Job 是否存在、status 是什么，缺什么就创建什么，最后把结果写回 status。生产里的控制器一般用 client-go 的 informer：informer 在本地维护一份 list/watch 的缓存，事件到达时只把 key 放进队列，reconcile 从缓存读对象；队列有限速和指数退避，失败的任务不会立刻打爆 apiserver。队列的 key 通常是 `namespace/name`，同一个对象在队列里只会有一份；reconcile 失败后按指数退避，从毫秒级开始翻倍，到上限后放弃并记录错误，而不是无限快速重试。

`reconcile` 必须幂等、可重入。幂等的意思是“跑一次和跑十次结果一样”：Job 已经存在就不要再建，PVC 已经绑定就不要重复申请，status 没有变化就不要每轮都写。可重入的意思是“从任何中间状态进来都能继续”：控制器可能在创建 Job 之后、更新 status 之前崩溃，下一轮要能从“Job 已存在、status 还是 Running”这个状态接着做，而不是假设自己一定从零开始。同一个对象可能因为 resync、控制器重启、事件重复而被协调很多次；创建 Job 前要先查，创建时遇到 `AlreadyExists` 要当作成功，更新 status 要能接受冲突后重试。控制器还要能处理“对象已经被删除”的情况：先看 `metadata.deletionTimestamp`，做清理，再移除 finalizer。子资源用 `ownerReferences` 指向 CR，Kubernetes 的垃圾回收器就知道它们属于谁；owner reference 必须和属主在同一个 namespace，跨 namespace 的 owner reference 会被当成无效。

本章的 Operator 为了把代码压小，没有用 informer，而是每两秒 `list` 一次 `shortybackups`，对每个对象调用同一个 `reconcile`。这不是教学上的偷懒，而是把“控制器 = 幂等的 reconcile 循环”这件事单独露出来：轮询和 watch 只是触发方式不同，`reconcile` 的内容一样。生产实现应该换回 informer 和限速队列，尤其是对象多、事件密集的时候；固定两秒轮询会浪费 apiserver 的读请求，也不会按失败次数退避。

## 33.4 写一个最小 Operator

Operator 没有规定语言。只要程序能作为 Kubernetes API 的客户端，能 list/watch 自定义资源、创建关联对象、更新 status，就可以是 Operator。Go 有 client-go、controller-runtime、kubebuilder，Python 有官方客户端和 Kopf，Rust、Java、.NET 也都有各自的库。本章选 Python，因为代码短，标准库加官方 `kubernetes` 客户端就能把 list、create、patch 和 Lease 选主写完；代价是没有 controller-runtime 那样的缓存、队列和代码生成，生产项目通常会用更完整的框架。

RBAC 只给控制器需要的东西：对 `shortybackups` 和 `shortybackups/status` 的 get/list/watch/update/patch，对 `shortybackups/finalizers` 的 update，对 Job 的 get/list/watch/create/delete，对 PVC 的 get/list/watch/create/delete，对 Lease 的 get/create/update/patch。没有 `cluster-admin`，没有通配符。`blockOwnerDeletion: true` 的 owner reference 会让 apiserver 检查控制器对属主 finalizers 的更新权限，所以 finalizers 那一条不能省。

镜像由 `Dockerfile.operator` 构建：`python:3.15.2-slim-trixie` 加固定版本的 `kubernetes==37.0.1`，以非 root 的 65532 运行，入口是 `python3 /app/shorty_operator.py`。客户端库会带进 `urllib3`、`requests`、`PyYAML` 这些依赖，镜像比 Go 静态二进制大，但对一个只跑几个副本的控制器来说可以接受；真正要控制的是版本固定、基础镜像的漏洞扫描和重建频率，而不是只看镜像大小。示例里镜像只在本机构建、`kind load` 进节点，所以 Deployment 写的是 `shorty-operator:0.1` 这个本地 tag；生产应该把镜像推到 registry，用 `@sha256:...` 固定 digest，避免 tag 被重新指向。Deployment 本身也按 `restricted` 写：`runAsNonRoot`、`seccompProfile: RuntimeDefault`、`allowPrivilegeEscalation: false`、丢掉所有 capability、只读根文件系统，`/tmp` 用 emptyDir。

还有一条容易漏的：`s4-prod` 的 `default-deny` 把 operator 的出站也关了。Operator 要到 apiserver 读 CR、写 status，示例加了一条只选 operator Pod 的 NetworkPolicy，`egress: - {}` 放行全部出站；生产应该把 `to` 收窄到 apiserver 的地址和端口，而不是像示例这样放行所有目的地。漏了这条策略时，现象是日志停在 `started`、没有后续 reconcile；排障时先看控制器能不能连上 apiserver。

## 33.5 生命周期：finalizer、status、conditions

删除一个带 finalizer 的对象时，apiserver 不会立刻删它：先写 `metadata.deletionTimestamp`，返回 202 Accepted，然后等控制器把 `metadata.finalizers` 里的项逐个移除；列表空了，对象才真正消失。finalizer 的名字必须是带域名的限定名，比如 `shorty.example.com/backup-cleanup`；Kubernetes 会拒绝没有域名的自定义 finalizer。finalizer 里不写代码，它只是一个标记，告诉控制器“删除前还有事要做”。

用 finalizer 的场景是“对象之外还有资源”。本章的 Operator 创建了 Job 和 PVC，PVC 里是备份文件；如果直接删 CR，owner reference 的垃圾回收会删掉 Job/PVC，但那是异步的，而且如果备份文件在集群外（比如对象存储），垃圾回收根本管不到。finalizer 给了控制器一个明确的清理窗口：删 Job、删 PVC、删外部文件，确认都删掉了，再移除自己的 finalizer。清理失败就保留 finalizer，下一轮重试；不要为了“让它快点消失”手工删 finalizer，除非你确认清理已经用别的方式完成。

status 是控制器的输出，不是 spec 的镜像。示例用 `status.phase` 表示 Pending/Running/Completed/Failed，用 `status.conditions` 记录 `Ready` 条件，字段是 `type`、`status`、`reason`、`message`、`lastTransitionTime`；`observedGeneration` 记录控制器最后处理的 `metadata.generation`。不要把 spec 里的字段整套抄进 status，也不要把 status 当成第二份配置；status 应该回答“现在到哪一步了、为什么”，而不是“用户想要什么”。`lastTransitionTime` 只在条件状态或原因变化时更新，不是每次 reconcile 都刷新；否则时间戳会一直变，基于它的告警和审计也没有意义。`observedGeneration` 落后于当前 generation，说明控制器还没处理最新的 spec，这比只看 phase 更能发现“控制器卡住了”。

`reconcile` 里不要做长时间阻塞的操作。创建 Job 是异步的：控制器只负责把 Job 对象写进 apiserver，Job 控制器再去创建 Pod、等容器结束；本章的 Operator 每轮只读 Job 的 status，不 `sleep` 等备份完成。清理也一样：删除 Job/PVC 是发请求，不是等 Pod 完全退出；如果删除请求失败，保留 finalizer，下一轮再试。把等待放在控制器的主循环里，会让所有对象都卡住，leader 也更容易因为续约超时被换掉。

owner reference 和 finalizer 解决的不是同一个问题。owner reference 让垃圾回收器知道 Job/PVC 属于哪个 CR，CR 被删除后它们会被回收；finalizer 让删除过程停在“等控制器清理”这一步，给控制器机会处理集群外的资源。本章的 Operator 两者都用了：Job/PVC 带 owner reference，CR 带 finalizer。只写 owner reference，集群外的东西没人删；只写 finalizer，控制器挂了对象会一直 Terminating。两者配合，删除才是可预期、可重试的。

## 33.6 Operator 的边界与成熟度

Operator 适合“有领域运维知识”的应用。数据库、消息队列、分布式存储这些系统，部署只是第一步，后面还有初始化、扩缩容、主从切换、备份恢复、版本升级、故障转移；这些知识写进控制器，用户只需要改 CR 的字段，Operator 负责把一系列动作串起来。反过来，一个无状态 Web 服务，Deployment、Service、ConfigMap、HPA 已经够用，再写一个 Operator 只是把 YAML 换成另一种 YAML，维护成本反而更高。简单部署用 Helm 或 Kustomize 就够了；需要“根据实际状态做决策”的时候，才轮到 Operator。

写 Operator 之前要想清楚升级和分发。一个常见的误区是把“能自动做一件事”当成“必须写 Operator”：如果只是把一组固定清单参数化，Helm 的 values 或 Kustomize 的 overlay 更简单，升级和回滚也更容易审计；Operator 的优势在运行时决策，比如“主库挂了要提升哪个从库”“备份失败了要不要重试、重试几次”，这些逻辑用模板表达不了。CRD 一旦发布，旧对象会一直存在，字段改名、类型变化、默认值变化都要靠多版本和 conversion webhook；webhook 本身是高可用服务，apiserver 调用它失败会直接影响读写。Operator 自己的版本也要能滚动升级，控制器的新旧版本可能同时运行，reconcile 要兼容两种对象。备份/恢复/升级步骤要写成文档，最好能在 CI 里跑一遍，而不是只存在于作者脑子里。OperatorHub 是查找现成 Operator 的目录，OLM 是另一种打包和安装层；它们是分发方式，不是运行 Operator 的前提，本章的最小实现只有 CRD、Deployment、RBAC 和镜像。

CRD 的版本演进是这里最容易低估的部分。版本号不是装饰：`v1alpha1` 表示还可能改字段，`v1beta1` 表示字段基本稳定，`v1` 表示向后兼容的承诺；一旦有外部用户，就不能靠“改一下 YAML 再 apply”来改字段名。旧版本要先标记 `deprecated`，给客户端迁移时间，再设 `served: false`，最后才从 `spec.versions` 里删掉。给 CRD 加一个 `v1` 并把 `storage` 改成 `true`，已有对象不会自动重写到新版本；它们仍然按写入时的版本存储，直到下一次更新。`status.storedVersions` 记录所有曾经作为 storage 的版本，读对象时可以请求任何 `served: true` 的版本，apiserver 按 `conversion.strategy` 转换。`None` 只改 `apiVersion`，字段完全一样时才安全；字段变了就要写 webhook，而且 webhook 必须处理旧版本到新版本、新版本到旧版本的转换。

apply `crd-v1.yaml` 后，`spec.versions` 里 `v1alpha1` 是 `served=true storage=false`，`v1` 是 `served=true storage=true`；`status.storedVersions` 是 `["v1alpha1","v1"]`，说明两个版本都曾作为存储版本。读同一个 `shorty-backup`，默认版本（用一个新的 discovery cache）返回 `shorty.example.com/v1`，显式指定 `v1alpha1` 返回 `shorty.example.com/v1alpha1`，两者的 `phase` 都是 `Completed`，因为两个版本的 schema 完全一样，`conversion.strategy: None` 只改了 `apiVersion`。显式请求 `v1alpha1` 时出现的弃用警告来自 CRD 里的 `deprecated: true` 和 `deprecationWarning`，不是错误。

这里有一个 `kubectl` 的实际行为：它会把 discovery 结果缓存在本地，刚改完 CRD 时，默认的 `kubectl get shortybackup` 可能还按旧版本 `v1alpha1` 发请求，于是打出弃用警告；换一个 `--cache-dir` 或等缓存刷新后，默认版本才变成 `v1`。写脚本时显式写 `shortybackup.v1.shorty.example.com` 最稳，不依赖缓存状态。这个细节也说明“版本优先级”是 apiserver 的 discovery 决定的，不是 YAML 里的顺序。

要把已有对象真正迁到 `v1`，有两条路：用 `StorageVersionMigration` 让 apiserver 批量重写，或者自己 list 所有对象、逐个更新，强制按当前 storage 版本写回。确认 `status.storedVersions` 里只剩 `v1` 之后，才能把 `v1alpha1` 从 `spec.versions` 里删掉；顺序反了，旧对象可能读不出来。跨版本字段变化一定要有 conversion webhook，并且在上生产前用真实对象测试两个方向的转换，不能只在 `None` 策略下点一下 `kubectl get`。

## 33.7 排障：CR 没有 Job、删不掉、schema 与版本

“CR 创建成功，但没有 Job”要按三层查。第一层是控制器在不在：`kubectl get pods` 看 operator 副本，`kubectl logs` 看它有没有 `started`、有没有开始 reconcile。第二层是控制器能不能访问 apiserver：日志里如果只有 `started` 就没了，或者出现 `403`、`Forbidden`，先查 RBAC 和 NetworkPolicy；`s4-prod` 的 `default-deny` 会挡住 operator 到 apiserver 的 443，示例里必须额外加一条放行规则。第三层是 CR 自己的状态：`status.conditions` 里 `Ready=False` 的 `reason` 和 `message` 通常会写清楚是 PVC 创建失败、Job 创建失败还是 Job 运行失败；没有 status 往往意味着控制器根本没处理到它。除了 logs 和 status，`kubectl get events -n shorty --sort-by=.lastTimestamp` 也能看到 Job/PVC 创建失败、Pod 调度失败这类事件；本章的 Operator 没有主动发 Event，所以事件只能补充 apiserver 和 Job 控制器的视角，不能替代控制器日志。

“删 CR 卡住”几乎总是 finalizer 加控制器不在。`kubectl get ... -o jsonpath='{.metadata.deletionTimestamp}'` 有值、`metadata.finalizers` 非空，对象就会停在 Terminating；这不等于 etcd 坏了，也不等于 apiserver 卡了。先看控制器 Pod 是否在跑、日志里有没有 cleanup 记录；控制器恢复后会继续删 Job/PVC、移除 finalizer。只有在确认清理已经用别的方式完成之后，才考虑手工移除 finalizer；直接 `kubectl patch` 把 finalizers 清空，可能留下没人管的 Job、PVC 或外部备份文件。

“CRD apply 报 strict decoding error”先看 schema，而不是先怀疑 apiserver。未知字段说明 schema 里没有这个字段；类型错误说明字段的 `type` 不匹配。`additionalProperties` 在 CRD schema 里不能设为 `false`，所以不能靠它来“禁止多余字段”；结构化 schema 加严格字段校验才是正路。改完 schema 后，旧对象不会自动重新校验；如果新旧 schema 的必填字段不同，已有对象可能在下一次更新时才报错，升级前要拿真实对象跑一遍。

“改完 CRD 后旧 CR 读不出来”要查 `status.storedVersions` 和 `conversion.strategy`。对象可能还存储在旧版本，而新版本 schema 删了字段或改了类型；`None` 转换只改 `apiVersion`，不会补字段。用 `kubectl get shortybackup.v1...` 和 `kubectl get shortybackup.v1alpha1...` 分别读，能看出是哪个版本的问题；如果是 webhook 转换，apiserver 日志和 webhook 日志里会有 `ConversionReview` 的失败原因。删旧版本之前，先确认 `storedVersions` 里没有它，否则存储层还有旧版本对象，读请求会失败。

排障的顺序可以固定成“对象 → 控制器 → 权限/网络 → 版本”。先看 CR 的 status、finalizer、deletionTimestamp，再看控制器 Pod 和日志，然后看 RBAC、NetworkPolicy、apiserver 的拒绝信息，最后才看 CRD 的版本和转换。这个顺序和[第 32 章](ch32.md)的“对象 → 控制器 → 节点 → 组件”一致，只是这里的“节点”换成了 operator 自己的运行环境。不要一上来就删 finalizer 或重启 apiserver，那些动作会把可恢复的问题变成不可恢复的状态。

## 上生产前

CRD 要结构化、版本化、带 status 子资源。schema 里写清 `type`、`required`、`enum`、范围，能给默认值的给默认值；不要用 `x-kubernetes-preserve-unknown-fields` 绕开校验。第一次发布就用带版本号的组，比如 `v1alpha1` 或 `v1beta1`，不要等到字段改不动了才想起 conversion。给 `/status` 单独授权，让用户写 spec、控制器写 status；`additionalPrinterColumns` 选真正需要一眼看到的字段。CRD 删除会连带删除所有自定义对象，生产里要像对待数据库表一样对待它的生命周期。

控制器要幂等、可重入、能退避。创建子资源前先查，遇到 `AlreadyExists` 当成功；更新 status 接受 409 后重试；失败按指数退避，不要固定间隔打 apiserver。多副本用 Lease 选主，leader 续约失败要主动退出；RBAC 只给需要的动词和资源，不要用 `cluster-admin` 图省事。镜像和依赖固定版本或 digest，控制器本身也要能滚动升级。Operator 还要纳入网络策略：`default-deny` 下不给它到 apiserver 的出口，它会安静地卡在启动日志上。

Operator 的备份、恢复、升级要有文档，并且实际演练过。CRD 的多版本、conversion webhook 的证书和超时、旧对象迁移、`storedVersions` 的清理顺序，都要写成步骤；删除 CR 用 finalizer 清理 Job、PVC、对象存储里的备份文件，清理失败就保留 finalizer 重试。不要把“备份成功”只写在 status 里，要有可验证的产物和校验和；也不要把备份文件只放在本地 PVC 上，节点一丢就没了。

不要用 CRD 存大批量业务数据。自定义资源和 ConfigMap 一样占 apiserver 的存储，对象多、更新频繁会把 etcd 和 apiserver 拖慢；官方文档明确建议不要把应用数据、终端用户数据或监控数据存进 CRD。etcd 不是数据库，CRD 适合存“配置和期望状态”，不适合存日志、事件流、图片或大 JSON。数据量大的东西放对象存储或数据库，CRD 里只放指向它的引用。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `kubectl get crd` | 看集群里注册了哪些 CRD | `VERSIONS` 里 `(storage)` 标出存储版本 |
| `kubectl api-resources` | 看新资源有没有进入 discovery | CRD 建立后可能要等 OpenAPI/discovery 刷新 |
| `kubectl explain <kind>.<field>` | 读 CRD 发布的 schema | 依赖 OpenAPI，刚 apply 完可能暂时找不到 |
| `spec.versions[].schema.openAPIV3Schema` | 结构化 schema | v1 必填；`type`、`required`、`default` 都写在这里 |
| `served` / `storage` | 是否提供端点 / 是否写 etcd | 有且只有一个 `storage: true` |
| `subresources.status` | 暴露 `/status` | 控制器只写 status，spec 变化才递增 `generation` |
| `conversion.strategy` | 多版本之间怎么转换 | `None` 只改 `apiVersion`；字段变化用 `Webhook` |
| `additionalPrinterColumns` | `kubectl get` 的列 | `priority > 0` 只在 `-o wide` 显示 |
| `metadata.finalizers` | 删除前等控制器清理 | 自定义 finalizer 必须带域名 |
| `status.conditions` | 控制器写的状态条件 | 字段：`type/status/reason/message/lastTransitionTime` |
| `metadata.ownerReferences` | 让子资源跟随属主回收 | 不能跨 namespace |
| `kubectl get shortybackup.v1.shorty.example.com` | 显式按某个版本读 CR | 避免 kubectl discovery 缓存留在旧版本 |
| `kubectl wait --for=jsonpath=...` | 等 CR 的 status 字段 | 比等随机后缀的 Job 名稳定 |

- [使用聚合层扩展 Kubernetes API](https://kubernetes.io/zh-cn/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/)：APIService 如何把 URL 路径代理到 extension apiserver，以及 discovery 的延迟要求。
- [使用 CustomResourceDefinition 扩展 Kubernetes API](https://kubernetes.io/zh-cn/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/)：CRD 的创建、结构化 schema、裁剪、默认值、printer columns、status/scale 子资源和 finalizer。
- [CustomResourceDefinition 的版本](https://kubernetes.io/zh-cn/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definition-versioning/)：多版本、`served/storage`、`None` 与 webhook 转换、`storedVersions` 和存储版本迁移。
- [Operator 模式](https://kubernetes.io/zh-cn/docs/concepts/extend-kubernetes/operator/)：Operator 的动机、典型组成、部署方式和可用框架。
- [控制器](https://kubernetes.io/zh-cn/docs/concepts/architecture/controller/)：控制循环、期望状态与实际状态、Job 控制器和控制器与 apiserver 的关系。
- [Finalizers](https://kubernetes.io/zh-cn/docs/concepts/overview/working-with-objects/finalizers/)：删除时间戳、202 响应、finalizer 的移除顺序和手工移除的风险。
- [属主与附属](https://kubernetes.io/zh-cn/docs/concepts/overview/working-with-objects/owners-dependents/)：owner reference、`blockOwnerDeletion`、跨 namespace 限制和级联删除。
- [Kubernetes API](https://kubernetes.io/zh-cn/docs/concepts/overview/kubernetes-api/)：discovery、OpenAPI v2/v3、资源组版本和补丁格式。
- [服务器端应用（Server-Side Apply）](https://kubernetes.io/zh-cn/docs/reference/using-api/server-side-apply/)：SSA 的字段管理、冲突和与客户端 apply 的区别。
- [验证准入策略（ValidatingAdmissionPolicy）](https://kubernetes.io/zh-cn/docs/reference/access-authn-authz/validating-admission-policy/)：用 CEL 做字段级和对象级校验，1.30 稳定。
