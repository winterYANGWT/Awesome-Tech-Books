# 第 15 章 开发与 CI 中的容器：dev container、Testcontainers、CI 里构建镜像

第 14 章结束时，shorty 的 Compose 栈在一台机器上跑得很好：PostgreSQL、Redis、migrate、api、worker 都在，`curl localhost:8080/readyz` 返回 `ok`。把仓库交给同事，他执行同一条 `docker compose up -d`，却可能得到完全不同的结果：本机没装对 Go 版本，`api` 构建失败；宿主目录的权限是 700，容器里的非 root 用户读不到配置；上一次测试留下的数据库里还有半张表；CI 机器上的 Docker 版本又不支持 Compose 文件里的某个字段。

这些问题的共同点是“环境”没有被当成代码管理。镜像解决了运行时依赖，但开发时用的工具链、编辑器、测试数据库、CI 里的构建器，仍然散落在每台机器上。这一章把这几层分别收进容器：用 bind mount 和 Compose Watch 把源码变更送进运行中的容器；用 Dev Container 把整个开发环境写成 `devcontainer.json`；用 Testcontainers 在测试代码里启动一次性的真实依赖；再用 buildx 把“构建一次、按 digest 晋升”的流水线跑通。最后回到 Kubernetes，看本地进程怎么连上集群里的服务，以及镜像里没有 shell 时怎么调试。

这一章不引入新的应用代码。shorty 还是第 14 章那套 Compose 服务，示例围绕它的镜像、Dockerfile 和测试展开；15.6 会临时建一个单节点 kind 集群，验证本地开发流程，但不会把 Compose 栈搬进集群。

> **起点**：第 14 章结束。Compose 栈可用，`shorty:0.1`、`shorty-worker:0.1` 已经构建过。在仓库根目录执行 `bash code/ch15/setup.sh`，它会重建这两个镜像并把 Compose 栈拉起来，启动本地 registry `ch15-registry`（监听 5000），把 Dev Containers CLI 0.89.0 装进命名卷 `ch15-devcontainer-cli`，预热 Go 模块缓存，并预构建 `shorty:dev` 供 15.2 的 dev container 复用。15.6 会另建一个名为 `shorty` 的单节点 kind 集群。

## 15.1 源码挂载与热更新

bind mount（绑定挂载）是把宿主机的目录直接映射进容器。容器里的进程读写这个路径时，看到的就是宿主机上的文件，没有复制，也没有中间层。对开发来说这很直接：编辑器在宿主机上保存，容器里的解释器或 Web 服务器下一次读文件就能看到新内容，不需要重建镜像。代价是容器的文件视图从此依赖宿主机：路径必须存在，权限必须匹配，不同操作系统的文件系统语义、inotify 事件和大小写规则都会渗进来。

Docker 提供 `-v` 和 `--mount` 两种写法。`-v` 更短，源路径不存在时会自动创建一个目录；`--mount` 更明确，源路径不存在时直接报错，不会悄悄建一个空目录。开发环境里推荐后者，因为“挂载了一个不存在的目录”通常意味着配置写错了，而不是想要一个空目录。只读挂载在 `--mount` 里写 `readonly`，在 `-v` 里写 `:ro`；它让容器能读宿主文件，但不能修改或删除它们。

shorty 的首页 HTML 在构建时用 `go:embed` 嵌进了二进制，所以给 `api` 容器挂一个 `templates` 目录并不会改变它返回的页面。为了单独观察 bind mount 的行为，下面的例子用一个 nginx 容器挂载宿主上的 `api/templates`；挂载点和“改文件、刷新页面”的流程与真实项目一致。

输出里先看到 `Version 1`，改完宿主文件后第二次 `curl` 得到 `Version 2`，中间没有重启 nginx。这就是 bind mount 的“热”更新：容器里的 `/usr/share/nginx/html/index.html` 和宿主上的文件是同一个 inode，宿主的写入立刻对容器可见。`ls -ln` 在宿主机和容器里都显示属主为 `0 0`，权限是 `644`；`-n` 让 `ls` 直接打印数字 uid/gid，而不是查名字，这样对比才不会被两边不同的 `/etc/passwd` 干扰。

再往下，容器里以 root 往只读挂载写文件，得到 `Read-only file system`。这不是权限位的问题，而是挂载本身是只读的，内核在 VFS 层就拒绝了写。最后一段把 `api/data` 以可写方式挂进去，用 `--user 1000:1000` 运行 busybox，容器创建的文件在宿主上显示为 `1000 1000`。bind mount 不改变文件的数字属主，容器里是谁写的，宿主上就是谁的 uid；如果这个 uid 和宿主上的开发者账号不一致，就会出现“文件在，但打不开”或“能读不能改”的问题。示例里先用 `chmod 777` 让目录可写，只是为了让这段演示能跑；实际项目应该让容器用户与宿主用户对齐，或者在镜像里预先 `chown` 好目录，而不是把权限放成 777。

Compose Watch 把这件事做得更细。它在 `compose.yaml` 的 `develop.watch` 下配置一组规则，每条规则有 `path` 和 `action`：`sync` 把变化的文件同步进容器，`rebuild` 重新构建镜像并替换容器，`restart` 只重启容器，`sync+restart` 同步后重启，`sync+exec` 同步后在容器里执行命令。`sync` 适合解释型语言和静态资源，`rebuild` 适合编译型语言或依赖清单变化，`sync+restart` 适合改 nginx 配置这类“文件变了但进程要重读”的场景。

Watch 的路径规则有几条容易踩的边界：`path` 相对于 Compose 项目目录；目录会被递归监视；不支持 glob；`.dockerignore` 里的模式会作为隐式忽略规则生效；`ignore` 里的模式相对于当前规则的 `path`，不是项目根目录；`.git` 和常见编辑器的临时文件会自动忽略。另外，Watch 只对用 `build` 从本地源码构建的服务生效，不跟踪只写了 `image` 的预构建服务。容器镜像里需要有 `stat`、`mkdir`、`rmdir`，并且容器里的 `USER` 要能写目标路径，否则同步会失败。

`.dockerignore` 不只是构建时少传文件，它还会影响 Watch 的判断。构建上下文里有一个几百 MB 的 `node_modules` 或 `.git` 时，`docker build` 会慢，Watch 也会把其中每个文件都当成候选变更；把这些路径写进 `.dockerignore`，构建和监视都会轻松。但 `.dockerignore` 是构建上下文的规则，不是容器的访问控制：它不会阻止 bind mount 把宿主目录带进容器，也不会让容器里的进程看不到已经挂进去的文件。

## 15.2 Dev Container：把开发环境也容器化

bind mount 只解决了“源码怎么进去”，没有解决“容器里该装什么”。Go 版本、gopls、调试器、linter、shell 补全、git 配置，仍然由每台机器自己维护。Dev Container 的思路是把这套开发环境也写进仓库：一个 `devcontainer.json` 描述用哪个镜像或 Dockerfile、装哪些 feature、挂哪些目录、转发哪些端口、创建后跑什么命令；编辑器或 CLI 通过 Docker 启动这个容器，然后把终端和语言服务接进去。

`devcontainer.json` 里最核心的选择是 `image` 和 `build` 二选一。`image` 直接引用一个预构建镜像，适合工具链已经很稳定的项目；`build` 指向 Dockerfile，可以带 `context`、`target` 和 `args`。本章的配置用 `build`，并把 `target` 指到 shorty 的 `build` 阶段。这个阶段有 Go 工具链和源码，适合开发；生产用的 `distroless` 阶段只有二进制和运行时需要的最小文件，不适合跑 `go test`。多阶段构建本来就是为这种分离准备的：每个 `FROM` 开一个新阶段，`COPY --from` 只把需要的产物带到下一个阶段，`--target` 可以停在任意阶段。

`features` 是在基础镜像上追加工具的机制，比如在 Debian 镜像里装 Node、在 Ubuntu 镜像里装 kubectl。feature 的版本必须固定：写 `ghcr.io/devcontainers/features/...:1` 这种主版本标签，维护者更新 `1` 指向的内容时，同一份配置在同事机器上装出来的工具就会变。Dev Containers CLI 0.89.0 默认在 `build`/`up` 时生成 `.devcontainer-lock.json`，把 feature 的版本和完整性固定下来；仓库里应该提交这个 lockfile，CI 里用 `--frozen-lockfile` 拒绝漂移。本章的配置没有用 feature，所以示例加了 `--no-lockfile`，避免在 shorty 源码目录里写文件。

`mounts` 用来加额外的挂载。示例把命名卷 `ch15-gomod` 挂到 `/go/pkg/mod`、`ch15-gocache` 挂到 `/root/.cache/go-build`，这样开发容器删掉重建时 Go 模块和编译缓存还在；setup 里先在同样的工作目录 `/workspaces/api` 预热一次编译，避免第一次 `go test` 在内存紧张的机器上把编译器 OOM。`forwardPorts` 告诉编辑器把容器里的 8080 转发到本机；`postCreateCommand` 在容器创建后执行一次，示例里是 `go mod download`，把依赖预热好。`remoteUser` 设成 `root` 是因为 `build` 阶段默认就是 root；真实项目更常见的是在 Dockerfile 里建一个非 root 用户，再让 `remoteUser` 指向它。

Dev Container 也可以用在 CI：`devcontainer build` 预构建带工具链的镜像，CI job 直接用它跑 lint 和测试，避免每个 job 重新装工具。这条路径和“用 dev container 当开发环境”是同一份配置的两种用法，前提仍是镜像、feature 和 CLI 版本都固定；否则 CI 只是把“同事机器环境不对”换成了“runner 环境不对”。

开发容器不是生产镜像。把 `devcontainer.json` 的 `target` 指到 `build` 阶段，生产仍然用 Dockerfile 最后的 `distroless` 阶段；不要把 dev container 的镜像推到生产 registry，也不要在 `devcontainer.json` 里写生产 Secret。需要更接近生产的调试时，可以另建一个带 shell 的 debug 阶段，而不是把工具链塞回 runtime 镜像。

## 15.3 Testcontainers：测试里的真实依赖

单元测试可以用内存存储，但仓储层、SQL、事务、迁移这些代码，只有对着真实的 PostgreSQL 才能测出问题。传统的做法是让 CI 提供一个长期运行的测试数据库，开发者本地再装一个；结果是测试之间互相污染，迁移版本不一致，CI 和本地行为不同。Testcontainers 把依赖变成测试代码的一部分：测试开始时用 Docker 启动一个 PostgreSQL（或 Redis、Kafka、MySQL），测试结束时删掉；端口由 Docker 随机分配，数据库是全新的。

最后一条 `docker ps -a --filter label=org.testcontainers=true` 只剩 `testcontainers/ryuk:0.14.0`，PostgreSQL 和 `shorty:0.1` 都不见了。Testcontainers 给会话创建的容器打上标签，测试结束时 `Terminate` 会删掉它们；即使测试进程没有调用 `Terminate`，Ryuk 也会按标签清理，并在没有事情可做时自己退出。要确认某个测试没有泄漏容器，用这个标签过滤比记容器名字可靠。

Compose 的 `depends_on` 和 Testcontainers 的等待策略解决的是同一类问题，但机制不同。Compose 的 `depends_on` 只保证容器按依赖顺序启动；要让依赖“可用”，得给服务写 `healthcheck`，再用 `condition: service_healthy` 等健康检查通过；`service_completed_successfully` 则等一次性任务成功结束。Testcontainers 不读 Compose 的依赖图，它在测试代码里用 `wait.ForLog`、`wait.ForListeningPort`、`wait.ForExit` 这些策略显式等待。两者都不能只等“容器 Running”：数据库进程启动和接受连接之间有一段时间，迁移任务也可能以非 0 退出。

CI 里跑 Testcontainers 需要一个可用的 Docker daemon：要么把宿主机的 `/var/run/docker.sock` 挂进测试容器，要么用 Testcontainers Cloud 这类托管方案。本章只在本地跑，没有用云。示例里的 `golang` 容器加了 `--network host`，是因为测试进程本身在容器里，需要从 `localhost` 访问 Docker 发布的随机端口；在普通宿主机上直接 `go test` 时不需要这一层，测试进程本来就在宿主网络里。镜像固定 digest、数据库每次全新、端口随机，这三点一起保证测试可重复，也不会和同一台机器上的其他测试抢端口。

Docker socket 的权限等同 root：能连上它的人可以启动特权容器、挂宿主目录。CI 里不要把 socket 挂给不可信的 PR 构建，优先用 rootless Docker、隔离的 runner 或托管的测试服务；确需 DinD 时，privileged 也应该是例外而非常规配置。

## 15.4 CI 里构建镜像

本地能构建不代表 CI 能构建。CI 机器的 CPU 架构、Docker 版本、缓存状态、 registry 凭据都和开发机不同；如果每次 CI 都从零拉依赖、从零编译，反馈会慢到没人愿意等。Docker 官方把 CI 里的 Docker 分成两种用法：把 Docker 当可复现的构建环境，以及在 CI 里构建镜像。前者用 Dockerfile 固定编译器、系统库和工具版本；后者用 buildx 和缓存后端，把“构建一次”做成流水线的一等公民。

示例脚本 `ci` 用 docker-container driver 的 buildx builder，而不是默认的 docker driver。registry cache 在默认 docker driver 下要求 containerd image store；docker-container driver 没有这个限制，也更容易把缓存和镜像分开。缓存写到 `localhost:5000/shorty:buildcache`，用 `mode=max` 把中间阶段也导出去；`--cache-from` 在缓存不存在时只会让导入失败，构建本身继续，所以第一次运行不需要特殊分支。第一次构建用 `--load` 把单平台镜像装进本地 Docker，跑一次 `shorty version` 冒烟测试；通过后再用 `--push` 推同一个镜像。这就是 `test-before-push` 的思路：先让镜像在本地可运行，再推 registry。

GitHub Actions 里的写法是同样的顺序，只是换成 `docker/build-push-action` 的输入：第一步 `load: true` 和测试用的 tag，第二步 `push: true`、`platforms: linux/amd64,linux/arm64`，两步之间用 `cache-from`/`cache-to` 复用缓存。`platforms` 决定目标平台；`--load` 把结果装进本地镜像存储，多平台发布通常直接 `--push`，能不能把 manifest list 装进本地取决于镜像存储（containerd image store 支持 manifest list，老存储不支持），所以测试步骤通常只构建当前平台，推送步骤再构建全部平台。官方文档特别说明，`linux/amd64` 在第一步已经构建过，第二步只补 `linux/arm64`，不会把两个平台都重做一遍。凭据用 CI 的 secret 传给 `docker/login-action`，不要写进 Dockerfile 的 `ARG`/`ENV`；构建日志要归档，失败时才能看到是哪一层、哪条命令出的问题。

buildx 的 builder 是一个独立的 BuildKit 实例，docker-container driver 的缓存不在本地 Docker 的镜像存储里，所以“删掉 builder”确实等于清空本地构建缓存。也正因为如此，第一次构建必须用 `--load` 才能让 `docker run` 看到镜像；`--push` 只把结果送到 registry，不会自动装进本地 Docker。日志里能区分“构建”和“导出/推送”：`CACHED` 是构建阶段的命中，`exporting`/`pushing` 是结果离开 builder 的动作。

第一段冷构建日志里 `cold CACHED lines: 7` 不是零：`ci` 在一次调用里先 `--load` 测试、再 `--push`，第二步复用了第一步的层。`smoke: shorty demo-1` 是镜像里 `shorty version` 打印的版本，冒烟测试通过后才会 push。删掉 builder 再跑，`smoke` 仍然通过，后面的 `CACHED` 行来自 registry 里的 `buildcache`：新 builder 没有本地层缓存，只能从 registry 导入；能命中说明缓存确实跨 builder 保存了下来。最后的 `sha256:...` 是 `shorty:ci-demo-1` 的 manifest digest，下一节会用它做晋升。

真实 CI 还要处理 registry 的 TLS 和认证。示例用 `localhost:5000` 的 HTTP registry，buildx builder 通过 `--driver-opt network=host` 访问它；生产 registry 通常是 HTTPS，登录信息由 CI secret 注入。不要把 `~/.docker/config.json` 或密码提交到仓库，也不要把 `--build-arg` 当成秘密通道：构建参数会留在镜像历史和构建日志里。

## 15.5 镜像晋升：构建一次，按 digest 提升

有了 CI 产出的 `shorty:ci-<sha>`，下一步是把它送到 `dev`、`staging`、`prod`。常见的错误做法是每个环境重新构建一次：`dev` 用一套 build args，`staging` 用另一套，`prod` 再构建一次。三次构建的输入即使看起来一样，基础镜像、依赖下载、编译器补丁都可能不同；出了问题也无法证明三个环境跑的是同一份代码。正确做法是只构建一次，把同一个 manifest 用不同的 tag 指过去。

tag 只是一个可变的指针，digest 才是镜像内容的哈希。Kubernetes 文档说得很直接：tag 可以移动，digest 不可变；镜像名同时带 tag 和 digest 时，拉取只使用 digest。`docker buildx imagetools create -t localhost:5000/shorty:prod localhost:5000/shorty:ci-promote-1@sha256:...` 做的是在 registry 里复制 manifest 和缺失的 blob，然后写一个新的 tag；它不会重新执行 Dockerfile，也不会产生新的镜像内容。多平台镜像的 manifest list 也一样，复制的是 index 和它引用的各个平台 manifest。

```console
{{#include code/ch15/15_6_promote_digest.out}}
```

输出里 `dev` 和 `prod` 两行是同一个 `sha256:...`，`same digest` 是脚本用 `[ "$dev" = "$prod" ]` 做的断言。`imagetools create` 的日志显示它在 `copying` 和 `pushing` 已有的 manifest，而不是构建新的层；源是 `ci-promote-1@sha256:...`，目标 tag 是 `prod`。这正是“按 digest 晋升”：晋升动作只改 registry 里的指针，不改镜像内容。

多平台镜像是 manifest list（或 OCI image index），一个 digest 指向多个平台 manifest。`imagetools create` 复制的是这个 index 和它引用的 blob，不是把某个平台的镜像重新 build 一遍；所以 `dev` 和 `prod` 两个 tag 指向的 index digest 相同，各自平台上的内容也相同。只在一个平台构建、却给另一个平台打 tag，会让节点拉到不匹配的架构；多平台发布要在 CI 的构建步骤就把 `platforms` 写全。

为什么不直接把 digest 当 tag 用？因为人需要可读的指针。`prod`、`staging` 是给人看的入口，CI 和审计记录里保存 digest；部署清单可以写 tag，发布记录里必须写 digest。只写 tag 的清单在回滚时说不清“上一次”到底是哪个内容；只写 digest 的清单又难读。两者都写是常见的折中：`image: shorty:prod@sha256:...`，Kubernetes 拉取时只用 digest，tag 只作为注释。

环境差异不应该做进镜像。数据库地址、日志级别、外部 API 的 endpoint 用 ConfigMap、Secret 或环境变量注入；同一个 digest 在三个环境跑，配置由部署清单提供。这样回滚也简单：把 `prod` 指回上一个 digest，而不是重新构建一个“旧版本”。Kubernetes 的 `imagePullPolicy` 默认规则也值得记住：指定 digest 或不带 `latest` 的 tag 时是 `IfNotPresent`，带 `latest` 或不写 tag 时是 `Always`；这个字段在对象第一次创建时就定下来，之后把 tag 改成 `latest` 不会自动把策略改成 `Always`。生产上更稳的写法是 `image: shorty@sha256:...`，或者 tag 加 digest 一起写。

## 15.6 本地 Kubernetes 开发

开发时经常需要让本机的进程或浏览器访问集群里的 Service。`kubectl port-forward` 把本地端口转发到 Pod、Deployment、ReplicaSet 或 Service 的端口；示例用 `service/api`，`kubectl` 会选一个匹配的 Pod，把本地 18080 转到 8080。它只支持 TCP，不能转发 UDP；权限上需要能 `get` 目标 Pod，并在 `pods/portforward` 子资源上 `create`。官方文档提醒，port-forward 由 API server 授权，可能绕过集群的网络策略，所以它适合开发调试，不适合当成生产暴露服务的手段。

```console
{{#include code/ch15/15_7_kubectl_debug.out}}
```

前半段先确认 Pod 是 `1/1 Running`，然后 `kubectl port-forward service/api 18080:8080` 在本地起监听，`curl localhost:18080/healthz` 返回 `ok`。日志里的 `Forwarding from 127.0.0.1:18080 -> 8080` 和 `[::1]` 两行说明 IPv4 和 IPv6 的回环都在转发；端口 18080 是示例选的，换成别的空闲端口也一样。

后半段处理“镜像里没有 shell”的情况。`shorty:0.1` 是 distroless 镜像，`kubectl exec` 进去没有 `sh`、没有 `ps`、没有 `curl`。`kubectl debug` 给运行中的 Pod 加一个 ephemeral container（临时容器），示例用 `busybox:1.37`，并给它 `sleep 3600` 作为主命令：没有 TTY 时，busybox 默认的 `sh` 会立刻退出，调试容器就没了。`--target=api` 让调试容器共享目标容器的进程命名空间，所以 `ps` 能看到 shorty 进程；`wget` 从同一个 Pod 的网络命名空间访问 `127.0.0.1:8080/healthz`，返回 `ok`。最后 `pod uid unchanged` 和 `restartCount=0` 说明原 Pod 没有被重建，原容器也没有重启。

Ephemeral container 在 Kubernetes 1.25 起是 stable；它不能被删除或修改，加进去之后只能通过删除整个 Pod 来清理，所以不要在生产 Pod 上随手加。`--target` 需要容器运行时支持进程命名空间共享；不支持时，调试容器可能起不来，或者起来后看不到目标进程。`kubectl debug` 的 `--profile` 还会给调试容器套一层安全配置：`general` 是默认，`baseline`/`restricted` 按 Pod 安全性标准限制能力，`netadmin`/`sysadmin` 放开网络或系统管理能力。排查网络问题时用 `netadmin` 比手工加 privileged 更可控；但 profile 只影响调试容器，不会改变原容器的 securityContext。

`kubectl debug` 还有 `--copy-to`，可以复制一个 Pod 并改命令或镜像，适合原 Pod 一启动就崩溃、连 ephemeral container 都来不及加的情况；复制出来的 Pod 是新的，原 Pod 不动。

`kubectl cp` 只适合临时取文件。它依赖容器镜像里有 `tar`，distroless 镜像没有，所以对 shorty 的 runtime 容器直接 `kubectl cp` 会失败；官方文档也把 `kubectl exec` 加 `tar` 管道列为更可控的替代。需要长期保留的文件应该走对象存储、PVC 或日志，而不是从运行中的容器里拷。

> **旧资料提示**：旧教程里调试容器常用 `docker exec` 进去改文件，再重启进程。运行中的容器可写层不是配置来源，Pod 一重建改动就丢；今天用 `kubectl debug`/ephemeral container 做临时排查，配置改动走 ConfigMap 和新的 rollout。

Telepresence 走的是另一条路：`telepresence connect` 把本机接入集群，`telepresence intercept <service> --port <local>:<remote>` 把发往集群 Service 的流量转到本机进程，同时在目标 Pod 旁安装 traffic-agent 做流量捕获。它适合“本地跑一个服务、连集群里的数据库和其他服务”的开发方式。本章的 lab 没有安装 Telepresence，上面这些是官方文档的描述，没有在本地验证；需要装的时候按官方 quick start 固定版本，不要直接取 latest。

开发环境不要用生产 Secret。Dev Container、Compose 和本地 kind 里的数据库密码、registry 凭据都应该是独立的演示值；生产 Secret 由集群的 Secret 管理和 RBAC 控制，不通过 `.env` 或 `devcontainer.json` 分发。`.env` 只放在本地，加进 `.gitignore`；需要给同事共享的默认值写在 `.env.example` 里，不放真实密码。

## 15.7 排障：watch 不触发、uid 读不到、Testcontainers 找不到 Docker

`docker compose watch` 不触发时，先把它从 `up` 里拆出来，单独运行 `docker compose watch --no-up` 看输出。常见原因有四类：服务只有 `image` 没有 `build`，Watch 根本不跟踪；`path` 写错或指向项目目录之外；文件被 `.dockerignore` 或 `ignore` 规则排除了；容器里的 `USER` 没有目标目录的写权限，同步动作失败但 Compose 不一定把错误放大。`ignore` 的模式相对于当前规则的 `path`，不是项目根目录；`*.tmp` 只会忽略 `path` 下的临时文件，不会忽略项目根目录的同名文件。Watch 也不支持 glob，想匹配多层目录要用 `**` 或把 `path` 指到更上层。

bind mount 里的文件“在，但容器里读不到”，先看数字 uid 和权限位，而不是先怀疑 Docker。下面的例子把文件属主设成 1000、权限 600，再用 uid 65534 的容器去读，内核会返回 `Permission denied`；换成 uid 1000 就能读。修法有两种：让容器里的进程以文件属主运行（Compose 的 `user:`、Kubernetes 的 `securityContext.runAsUser`），或者在构建/部署时把文件 `chown` 给运行用户。把权限改成 777 能让错误消失，但也让任何用户都能改这个文件，不应该作为默认方案。

```console
{{#include code/ch15/15_8_troubleshoot.out}}
```

修 uid 不匹配时，先确认容器里实际运行的用户，而不是看 Dockerfile 最后一行。镜像可能用 `USER` 指令切了用户，Compose 的 `user:` 又会覆盖它，Kubernetes 的 `runAsUser` 再覆盖一层；`docker exec id` 或 `kubectl exec -- id` 看到的是最终结果。文件权限则要在宿主上 `ls -ln` 看数字属主，再和容器里的 uid 对比；只看 `ls -l` 的名字，在两边的 `/etc/passwd` 不一致时会得出错误结论。

Testcontainers 报找不到 Docker 环境时，先看 `DOCKER_HOST`。Testcontainers for Go 的查找顺序是 `~/.testcontainers.properties` 的 `tc.host`、`DOCKER_HOST`、Go context 里的 `DOCKER_HOST`、默认的 `/var/run/docker.sock`，最后才是 rootless 的 socket 路径；如果测试进程在容器里，宿主机的 socket 必须挂进来，路径要和 `DOCKER_HOST` 对得上。示例把 `DOCKER_HOST` 指到一个不存在的 socket，测试在创建 provider 时就失败，不会去启动 PostgreSQL；这正是 CI 里“runner 没有 Docker”时的早期症状。排障时先 `docker info` 确认 daemon 可达，再确认 socket 挂载和权限，最后才怀疑 Testcontainers 的版本。

CI 里不要把 privileged DinD 当成默认方案。官方 CI 文档把 Docker 作为构建环境，并给出托管 CI 和官方 Docker 镜像的用法；privileged DinD 需要额外的内核能力和安全让步，只有在 CI 平台不提供 Docker socket、又无法用托管方案时才考虑。能用 rootless Docker 或隔离 runner 时，优先用它们，并把 socket 的访问限制在确实需要构建和测试的 job 上。

> **旧资料提示**：旧教程常把“Jenkins + privileged Docker-in-Docker”写成标准做法。今天的官方 CI 文档先给托管 CI 和官方镜像方案，privileged 只是其中一种选项；能挂 socket 或使用托管构建服务时，不必默认开 privileged。

## 上生产前

开发容器和 Compose 都不进生产。`devcontainer.json` 里的 `features`、`mounts`、`postCreateCommand` 是为了让人写得快，不是为了运行得稳；Compose 的 `develop.watch` 也不该出现在生产部署里。生产用多阶段 Dockerfile 的 runtime 阶段，加上 Kubernetes 清单；开发阶段可以有 shell、调试器和源码，runtime 阶段只留二进制和运行所需的证书。

CI 只构建一次，按 digest 晋升。`dev`、`staging`、`prod` 是同一个 manifest 的不同 tag，晋升动作只改 registry 指针；配置用 ConfigMap/Secret 或环境变量覆盖，不要为每个环境重新构建一个“配置镜像”。回滚时把 tag 指回上一个 digest，保留构建日志和 digest 记录，才能说清楚线上跑的是哪次提交。

测试容器固定镜像 digest，CI 的 Docker socket 权限最小化。`postgres:18.6-alpine` 这种 tag 会移动，测试依赖也可能跟着变；把 digest 写进测试代码，升级时显式改一次。CI 里优先 rootless Docker 或隔离 runner，socket 只挂给需要构建/测试的 job；privileged DinD 是例外，不是默认。

开发 Secret 与生产 Secret 分离，`.env` 不提交。开发容器、Compose、kind 里的密码只用于本地演示；生产 Secret 由集群管理和 RBAC 控制。构建时需要的凭据用 BuildKit 的 secret mount 或 CI secret，不要写进 `ARG`/`ENV`，否则会留在镜像历史和构建日志里。

构建缓存和发布镜像分开存放。`buildcache` 是一个独立的 tag，不随 `shorty:ci-<sha>` 一起发布；缓存可以丢，镜像不能丢。推送前先跑冒烟测试或单元测试，推送后按第 13 章的办法对 digest 做扫描和签名，再进入晋升流程。
