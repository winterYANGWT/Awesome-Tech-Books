# 第 24 章 Pod 网络、CNI 与 NetworkPolicy

到第 23 章结束时，shorty 的 api、worker、postgres、redis 已经各有 ClusterIP Service，Pod 之间也能用服务名互相访问。这套网络是“全通”的：worker 能连 postgres，任何一个临时 Pod 也能连 postgres，甚至能直接访问 api 的 8080。只要有一个 Pod 被拿下，或者有人误起了一个带 shell 的调试 Pod，数据库就暴露在同一个平面网络上。

Kubernetes 没有把“默认拒绝”设成初始状态。NetworkPolicy 是一个普通的 API 对象，真正把规则变成 iptables、nftables 或 eBPF 程序的是 CNI 插件。这带来两个经常一起出现的问题：策略写好了却没有 CNI 执行；或者 CNI 在执行，但选择器根本没有选中你以为的那个 Pod。

本章沿着 shorty 的数据层走一遍：先看 Pod 之间到底怎么通，再确认 CNI 是谁、负责什么，然后装一个明确支持 NetworkPolicy 的 Calico，从默认拒绝开始，一条一条放行 DNS、api 到 postgres、worker 到 redis 和 Gateway 到 api。最后故意改坏一个标签，看看“策略没生效”和“策略选错了对象”在输出上有什么区别。

> **起点**：`s3-stateful` 已经跑起来，集群是 2 节点（1 控制面 + 1 worker）的 kind 集群。本章从 `bash code/ch24/setup.sh` 开始。setup 先用带默认 kindnet 的 2 节点集群把 s3 拉起来，24.1 和 24.2 在这套网络上观察 Pod 直通和 kindnet 的策略行为；24.3 会把它重建为 `disableDefaultCNI: true` 的集群再装 Calico，避免 kindnet 和 Calico 同时往 `/etc/cni/net.d` 写配置。

## 24.1 Kubernetes 网络模型

Kubernetes 官方把集群网络拆成四个问题：同一个 Pod 内多个容器之间的通信、Pod 与 Pod 之间的通信、Pod 与 Service 之间的通信、集群外部与 Service 之间的通信。第一个问题由 Pod 自己解决：Pod 里的容器共享同一个网络命名空间，所以它们看到同一个 IP、同一个回环接口，用 `localhost` 就能互相访问。后面三个才是 CNI、kube-proxy 和入口组件分工的地方。

Pod 网络模型有三条硬要求。每个 Pod 拿到一个集群范围内唯一的 IP；所有 Pod 之间可以直接通信，不经过代理，也不做地址转换（NAT），无论它们在同一台节点还是不同节点；节点上的 kubelet、系统守护进程也能访问本节点的所有 Pod。这里的“直接”说的是三层可达：从源 Pod 发往目标 Pod IP 的包，目的地址始终是目标 Pod 的 IP，而不是先改成某个节点的地址。

Pod 到 Service 是另一层。Service 的 ClusterIP 是虚拟地址，由 kube-proxy 或 CNI 自带的服务代理监听 Service 和 EndpointSlice，把访问虚拟 IP 的连接改写到一个后端 Pod。kube-proxy 在 Linux 上可以用 iptables、IPVS 或 nftables 模式；一些 CNI 会用自己的数据面替代 kube-proxy。无论哪种实现，应用看到的都是稳定的 Service 名字或 ClusterIP，后端 Pod 的增删由控制面更新 EndpointSlice。

集群外部访问 Service 则走 NodePort、LoadBalancer 或 Ingress/Gateway。NodePort 在每个节点上开一个端口；LoadBalancer 依赖云厂商或本地负载均衡实现；Ingress/Gateway 是七层的 HTTP 路由。它们都建立在 Service 之上，不改变 Pod 之间那张三层网络。

每个节点还会分到一段 Pod CIDR，写在 Node 对象的 `spec.podCIDR` 里。在 kind 里，kube-controller-manager 按 `--cluster-cidr=10.244.0.0/16` 给每个节点切出 `/24`，所以两个节点分别拿到 `10.244.0.0/24` 和 `10.244.1.0/24`；CNI 的 IPAM 在这段地址里给 Pod 分配具体 IP，再把 veth、路由或 overlay 隧道配好。把这段关系和 Service CIDR 分开看：Service 的虚拟 IP 由 apiserver 分配，不占 Pod CIDR。地址段不能在集群之间重叠，否则跨集群访问或与外部网络对接时会撞车。NetworkPolicy 只处理三层和四层的流量，也就是 IP、协议和端口；它不管 HTTP 路径、TLS 证书或 gRPC 方法，那些要靠 Ingress、Gateway、服务网格或应用自己。

“Pod 间不 NAT”在实现上不等于“永远看不到地址改写”。同节点直通通常只是 veth 到网桥；跨节点可能走 VXLAN 封装，外层源地址是节点 IP，内层仍然是 Pod IP；到了目标节点解封装后再交给目标 Pod。应用看到的源地址应该还是源 Pod 的 IP，但抓包时在节点物理接口上看到的是封装后的外层头，别把这两种视角混在一起。

> **旧资料提示**：旧教程里常写“Pod IP 由 Docker 根据 docker0 分配”。那是 dockershim 还在时的做法。Kubernetes 1.24 移除了 dockershim，kubelet 不再通过 Docker 管理 Pod 网络；现在 Pod 地址由 CNI 的 IPAM 分配，节点上有没有 docker0 与 Pod 网络无关。

Service 的虚拟 IP 还带来一个观察上的陷阱：在 Pod 里 `curl api` 看到的是 ClusterIP，包在节点上被 DNAT 成某个后端 Pod 的 IP，NetworkPolicy 看到的通常是后端 Pod 的地址。用 `kubectl get endpointslice` 能看到 Service 背后的 Pod IP 和端口；排查“Service 不通”时，先确认 EndpointSlice 里有地址，再看 NetworkPolicy 是否允许源 Pod 到这些地址的端口。

## 24.2 CNI：网络是谁配的

CNI 是一份插件规范，不是某个具体产品。kubelet 通过 CRI 让容器运行时创建 Pod sandbox；容器运行时读取 `/etc/cni/net.d` 下的配置（通常是 `*.conflist`），按顺序调用 `/opt/cni/bin` 里的插件：先创建 veth，再调用 IPAM 分配地址，最后可能调用 `portmap`、`bandwidth` 这些元插件。Kubernetes 1.24 移除了 dockershim，kubelet 不再自己管理 CNI，`cni-bin-dir` 和 `network-plugin` 这两个 kubelet 参数也已经删除；现在这条链路归容器运行时管。

一个 CNI 实现通常要回答三个问题。地址从哪里来：是每个节点一段 Pod CIDR 的 host-local IPAM，还是 Calico 的 IPPool、Cilium 的 IPAM。包怎么走：同节点走 veth 和网桥，跨节点走路由、IPIP/VXLAN 隧道或 BGP。策略怎么执行：把 NetworkPolicy 翻译成 iptables/nftables 规则，或者用 eBPF 程序在 socket 层做判断。前两个问题决定“通不通”，第三个问题决定“能不能只让一部分通”。

kind 默认装的是 kindnet。它是一个很小的 CNI，DaemonSet 在每个节点跑一个 Pod，负责给 Pod 分配地址和配置路由；kind 会在节点的 `/etc/cni/net.d` 下写一份 kindnet 的 conflist。Calico、Cilium、Antrea 是常见的替代实现：它们都能实现 NetworkPolicy，但数据面、可观测能力和运维方式不同。

选 CNI 不是只看“支不支持 NetworkPolicy”一个勾。Calico 在三层用 BGP 或 IPIP/VXLAN 做跨节点路由，Cilium 主要用 eBPF，Antrea 用 Open vSwitch；它们的运维方式、内核要求、可观测能力和资源占用都不同。本章选 Calico 是因为它在 kind 上安装直接、`calicoctl` 能单独读 IPPool，而且策略行为容易对照 iptables 观察；这不等于它适合所有集群。

CNI 配置文件本身不神秘。一个 `.conflist` 至少要有 `cniVersion`、`name` 和 `plugins` 数组；数组里的插件按顺序执行，前一个插件的输出会传给后一个。Kubernetes 要求 CNI 规范 v0.4.0 或更高，推荐 v1.0.0。容器运行时负责读这个目录，kubelet 只通过 CRI 请求“给这个 Pod 准备 sandbox”，不直接解析 JSON。

CNI 不支持 NetworkPolicy 时，最危险的地方是它不会报错。`kubectl apply -f policy.yaml` 照样返回 `created`，`kubectl get networkpolicy` 也能看到对象，但数据面没有任何规则，Pod 之间还是全通。Kubernetes 的 NetworkPolicy 文档写得很直接：创建了 NetworkPolicy 但没有实现它的控制器，这个对象没有任何效果。所以“策略存在”不等于“策略生效”，必须用一条新连接去验证。

## 24.3 安装 Calico 并验证

Calico 和 kindnet 不能在同一个节点上共存：两者都会写 `/etc/cni/net.d`，都会给 Pod 配地址，谁先被容器运行时读到，另一套就可能完全不生效。正确做法是建集群时加 `disableDefaultCNI: true`，让节点先没有 CNI，再装 Calico。这样还能看到没有 CNI 时节点为什么是 `NotReady`，以及 Calico 装好后它们怎么恢复。

Calico 有两种常见安装方式。直接用 `calico.yaml` 清单会把 `calico-node` 和 `calico-kube-controllers` 装进 `kube-system`；用 Tigera Operator 则先装一个 Operator，再提交 `Installation` 自定义资源，组件落在 `calico-system`。Operator 多一个 Pod，但升级和裁剪组件更清楚。本章用 Operator，并只提交一个最小的 `Installation`：不装 Calico API Server、Goldmane 和 Whisker，2.5 GB 的 lab 里没必要多跑这些。

验证 Calico 不能只看 `kubectl get pods` 的 `Running`。`calico-node` 的 readiness 表示它已经能在这个节点上工作；但策略是否真的下发到内核，还要看节点的 `cali*` 接口、Felix 日志和一条实际的拒绝规则。本章在 24.4 用 deny-all 加超时做这条端到端验证，单纯“Pod 都是 Running”不算完成。

`calicoctl get ippool -o wide` 读的是 Calico 自己的 IPPool，不是 Kubernetes 的 Node 对象。这里应该看到 `10.244.0.0/16`，和节点的 `PODCIDR` 同属一个地址空间。如果 IPPool 写成默认的 `192.168.0.0/16`，节点可能 Ready，但 Pod 拿不到可路由的地址，或者跨节点直接不通。

`calico-node` 是 DaemonSet，不是普通 Deployment：它要读写节点上的 `/etc/cni/net.d`、`/var/run/calico` 和内核路由表，所以每个节点都必须有一个。Operator 根据 `Installation` 生成这些对象；如果 Operator 自己没 Ready，`calico-system` 里可能连 DaemonSet 都不会出现，这时先看 `kubectl -n tigera-operator describe deployment/tigera-operator`，不要直接去改 Calico 的 DaemonSet。

安装完成后 `kubectl get pods -n calico-system` 里所有 Pod 都应该是 `Running`，`calico-node` 在每个节点上一个。只要有一个 `calico-node` 没 Ready，就不要继续写策略：那个节点上的 Pod 可能根本没有网络，策略更无从谈起。

## 24.4 NetworkPolicy 语义

NetworkPolicy 的行为只有一句话：默认不隔离；一旦有一条策略选中了某个 Pod，并且 `policyTypes` 包含 `Ingress` 或 `Egress`，这个 Pod 在那个方向上就变成“默认拒绝、只放行规则里列出的连接”。没有一个叫 `deny` 的规则可以写，所有规则都是 allow，多个策略的效果取并集。顺序不重要，因为不存在“后面的规则覆盖前面的规则”。

`podSelector` 选的是**同一个 namespace** 里的 Pod，空选择器 `{}` 表示这个 namespace 的所有 Pod。它不能跨 namespace 选；跨 namespace 要在 `ingress.from` 或 `egress.to` 里写 `namespaceSelector`。`namespaceSelector` 按 namespace 的标签选，不是按名字；不过 Kubernetes 会自动给每个 namespace 打上 `kubernetes.io/metadata.name: <名字>`，所以用这个标签可以按名字选。`ipBlock` 则按 CIDR 选集群外的地址，不适合拿来选 Pod，因为 Pod IP 是临时的。

一条 `ingress` 规则里的 `from` 是一个数组。数组里的多个元素是“或”：来自 A 或来自 B 都行。一个元素里同时写 `namespaceSelector` 和 `podSelector` 是“与”：必须是那个 namespace 里带那个标签的 Pod。这个 YAML 缩进很容易写错，`kubectl describe networkpolicy` 会把解析后的结果打出来，改完策略应该看一眼。

`ports` 里的 `port` 是目标端口，`protocol` 默认是 TCP，可以写 UDP 或 SCTP。`endPort` 从 Kubernetes 1.25 起 stable，用来表示一个端口范围；它必须和 `port` 一起出现，`endPort` 不能小于 `port`，两个都必须是数字。CNI 不支持 `endPort` 时，策略只会按单个 `port` 生效，这也是换 CNI 后要验证的细节。

一条连接要被允许，源 Pod 的 Egress 策略和目标 Pod 的 Ingress 策略都要放行；只放行一边，连接仍然建立不起来。应答流量会被隐式允许，所以不需要为回包再写一条反方向规则。这个“两边都要”是本章后面写策略时最容易被忽略的地方。

前半段没有策略，`/readyz` 返回 `ok`。应用 `default-deny` 后，`kubectl get networkpolicy` 能看到对象，`spec` 里是 `podSelector: {}` 和 `policyTypes: [Ingress, Egress]`。再访问同一个 Pod IP，`wget` 等到超时，打印 `denied`。如果这里收到的是 `Connection refused`，那更像是进程没监听或 Service 没有端点，不是 NetworkPolicy：策略拒绝通常表现为包被丢掉，客户端只能等到超时。

还有两类流量不受普通 Pod 选择器控制。Pod 访问自己所在的节点、节点访问本节点的 Pod，官方模型把这条路径视为始终允许；`ipBlock` 又可能因为 Service 的 DNAT、云负载均衡或 SNAT 而看到改写后的源地址。写策略时不要假设“看到的源 IP”一定是客户端 Pod 的 IP，跨 Service、NodePort、LoadBalancer 的路径要单独验证。

NetworkPolicy 的另一条边界是 `hostNetwork: true` 的 Pod：官方文档明确说这种行为未定义，最常见的实现干脆忽略它们，把它们的流量当成节点流量。shorty 的 Pod 都没有用 `hostNetwork`；如果以后要加一个用主机网络的 agent，不要假设它会受这套策略约束。

> **旧资料提示**：另一种常见说法是“CNI 自带 NetworkPolicy，所以装上就一定生效”。Calico、Cilium 确实实现了策略，但前提是 `calico-node`/Cilium agent 在每个节点都健康、策略对象在正确的 namespace、选择器选中了目标。对象创建成功只代表 apiserver 接受了它，不代表数据面已经编程；用一条新连接验证，仍然是最低要求。

默认拒绝 Egress 也会把 DNS 挡掉。此时 shorty 里的 Pod 不只是连不上数据库，连 `postgres` 这个名字都解析不了。这不是“网络全挂了”，而是策略按预期生效了；下一步必须先把 53 端口放回去。

## 24.5 默认拒绝 + 逐步放行

放行的顺序不是随意的。先放 DNS，因为后面的规则都用服务名；再放业务端口，每加一条就用一条新连接验证；最后放外部入口。这样任何一步失败，原因都局限在刚加的那条规则里。下面每一步都只改一个方向或一个端口，前一步通过再做下一步。

这里有一个实际输出带来的修正：shorty 的 `/readyz` 不只 ping PostgreSQL，还 ping Redis。只放行 5432 时，`/readyz` 返回的是 `not ready: redis: ...`，不是 `ok`；这恰好证明数据库那条路已经通了。放行 Redis 之后，`/readyz` 才变成 `ok`。所以本章的 `allow-api-db` 只负责数据库，Redis 由 `allow-worker-redis` 一起放行；策略名字里的 `worker` 是指 Redis 的主要使用者，不是唯一使用者。

api 自己也要连 Redis：创建短链时它会把任务 `LPUSH` 到 `shorty:jobs`。如果只放 worker 到 Redis，api 创建链接和 `/readyz` 都会失败。`allow-worker-redis` 因此同时选中 api、worker 和 redis，允许 api/worker 进出 6379。这个例子说明策略要按应用的真实依赖写，不能照着拓扑图想当然。

worker 到 postgres 的放行放在最后。`allow-api-db-worker.yaml` 把 worker 加进 `allow-api-db` 的源和选择范围，对象名仍然是 `allow-api-db`，所以不需要改其他策略的引用。worker 到 postgres 和 worker 到 redis 都通了之后，数据层的三条路径才完整：api 读写数据库、api 入队、worker 取任务并写回数据库。

最后是外部入口。示例创建一个 `ingress` namespace，放一个带 `app.kubernetes.io/name=gateway` 标签的客户端；`allow-gateway` 用 `namespaceSelector` 选 `ingress`，用 `podSelector` 选这个标签，只放行到 api 的 8080。两个选择器写在同一个 `from` 元素里，表示“ingress 命名空间里的 gateway Pod”，不是“ingress 命名空间里的任何 Pod，或者任意命名空间里的 gateway Pod”。

放行顺序也可以反过来做“先全放、再逐条收紧”，但默认拒绝起步更安全：每一步的失败都是“少了一条 allow”，而不是“多了一条没注意的放行”。如果从全通开始，最后很难证明没有漏掉某个端口；从默认拒绝开始，连接矩阵里的每一条通路都能对应到一条策略。

策略写完后，`kubectl get networkpolicy` 里应该有 `default-deny`、`allow-dns`、`allow-api-db`、`allow-worker-redis`、`allow-gateway` 五个对象，后四个都是 additive 的 allow。`default-deny` 一直保留，它保证以后新增的 Pod 即使没有被任何 allow 选中，也不会回到全通状态。

## 24.6 观测与排障

排查 NetworkPolicy 的第一步不是读 YAML，而是确认 CNI 还在工作。`kubectl get pods -n calico-system` 看 `calico-node` 是不是每个节点都 Ready，`kubectl get nodes` 看节点是不是 Ready。CNI Pod 挂了，Pod 可能还保持 Running，因为已有网络命名空间还在，但新建 Pod、更新策略、跨节点路由都会出问题。

第二步才是看策略对象。`kubectl get networkpolicy -o yaml` 能看到 `podSelector`、`policyTypes` 和每条 `from/to`；`kubectl describe networkpolicy` 会把空选择器和解析后的规则用文字展开。重点核对三件事：策略在不在目标 Pod 的 namespace；`podSelector` 是否真的选中目标；`policyTypes` 是否包含你要限制的方向。少写一个 `Ingress`，入站就仍然全通。

第三步是用一条新连接复现。不要用已有的长连接测，因为 NetworkPolicy 对已经建立的连接是否立即生效由实现决定；也不要只看 `kubectl exec` 里的 `ping`，NetworkPolicy 对 ICMP 的行为是未定义的，有的 CNI 放行，有的拒绝。用 `wget`、`curl`、`nc` 或应用自己的客户端建立一条新的 TCP 连接，看到超时才有意义。

Calico 的 Felix 日志在 `calico-system` 的 `calico-node` 里，能看到策略同步、IPSet 和 iptables 编程的错误：

```bash
kubectl -n calico-system logs -l k8s-app=calico-node --tail=50
```

这个命令在示例里没有跑，因为日志内容和时间戳每次都不一样；排障时它值得先看。本章的最小安装没有开 flow log，默认不会给每个被拒绝的包留事件；要看五元组级的拒绝记录，需要额外的流量观测组件。用 Cilium 时，Hubble 可以直接看丢包和策略判定；本章没有装 Cilium，所以不展示 Hubble 的输出。

如果策略对象刚更新，数据面可能需要几秒钟同步。Calico 的 Felix 会定期把策略和 Endpoint 变化同步到 iptables/eBPF；在这之前，新建的 Pod 可能处于“已经有隔离、allow 还没下发”的短暂状态，表现为刚启动时完全不通，几秒后恢复。官方文档把这种分布式实现下的短暂不一致写得很清楚，所以探针和重试不是多余。

需要看包到底有没有到目标时，可以在 Pod 的网络命名空间或节点上抓包。节点上抓 `10.244.0.0/16` 的流量能看到跨节点包；在 Pod 的 netns 里抓能看到策略之后剩下什么。抓包要选对接口：Pod 里通常是 `eth0`，节点上可能是 `cali*`、`vxlan.calico` 或 `tunl0`，取决于封装方式。

最后用一个标签错误把“策略选错对象”演示出来。`api-canary` 是一个独立的 Pod，带 `app.kubernetes.io/name=api`，所以 `allow-gateway` 会选中它；`ingress` namespace 里的客户端能访问它的 8080。把它的 `name` 标签改成 `api-old`，`default-deny` 仍然选中它（空选择器选中所有 Pod），但 `allow-gateway` 不再匹配，访问变成超时。改回标签后又恢复。

这个例子里没有 Deployment 滚动，因为改的是独立 Pod 的标签；如果在 Deployment 的 Pod 模板上改标签，控制器会重建 Pod，现象会混入滚动更新。无论哪种方式，结论都一样：NetworkPolicy 的选择器按标签匹配，不按 Pod 名字、镜像名或工作负载名匹配。选不中就是没有 allow，默认拒绝就会把它挡住。

这里还有一个容易反过来的地方：如果 namespace 里**没有** `default-deny`，把目标 Pod 的标签改到所有策略之外，它反而会变成非隔离状态，所有流量都放行。示例里之所以改标签后是拒绝，是因为空选择器的 `default-deny` 仍然选中它。生产环境要保留这条兜底策略，否则“策略没选中”会变成“完全没有策略”。

## 24.7 排障：apply 了 deny-all 但还能访问

先确认 CNI 是否实现 NetworkPolicy。`kubectl get pods -n calico-system` 里 `calico-node` 是否每个节点都 Ready；如果用的是 kindnet，先看 `kube-system` 里的 kindnet DaemonSet。CNI 没跑或没实现策略时，NetworkPolicy 对象会安静地躺在 apiserver 里，流量照旧。

再确认策略有没有选中目标。`kubectl get networkpolicy -n shorty -o yaml` 看 `podSelector`，`kubectl get pod --show-labels` 看目标 Pod 的实际标签，`kubectl describe networkpolicy` 看解析后的规则。常见的错误是策略在 `default` namespace、Pod 在 `shorty`；或者标签是 `app=api`，策略写的是 `app.kubernetes.io/name=api`。选择器不会帮你猜。

然后确认方向和端口。只写 `policyTypes: [Ingress]` 不会限制出站；只放行源 Pod 的 Egress、没放行目标 Pod 的 Ingress，连接仍然不通；端口写 8080 但应用监听 8081，也会超时。DNS 被挡是最常见的“全挂”：先放行 53，再排查业务端口，否则你会在一个连名字都解析不了的 Pod 里查 HTTP。

策略文件的组织方式会直接影响排障速度。策略文件不是越短越好。把 DNS、数据层、入口拆成独立对象，失败时能快速定位是哪一层；把所有规则堆进一个对象，排障时只能整份读。测试时最好把命令、期望结果、实际结果和验证时间记录在同一个变更里。策略是安全边界，不是一次性配置；下次有人改标签或加端口，应该能从记录里看出这条连接原来为什么被允许。测试要从源和目标两侧分别做。源 Pod 的 Egress 被挡住，目标侧抓包什么都看不到；目标 Pod 的 Ingress 被挡住，源侧只会看到超时。先确认源 Pod 的 Egress 规则，再看目标的 Ingress 规则，最后才怀疑网络插件。用 `kubectl exec` 时也要注意：exec 进程共享 Pod 的网络命名空间，它发出的连接和主容器走同一套策略，适合做端口测试，不适合判断“应用自己的连接池还能不能用”。

不要用 `kubectl exec` 到 Pod 里 `ping` 作为唯一判据。NetworkPolicy 对 ICMP 的行为没有定义，`ping` 不通不代表 TCP 不通，`ping` 通也不代表 8080 放行。用实际协议和端口建立新连接，才和策略的 L3/L4 语义对得上。

## 上生产前

选一个明确支持 NetworkPolicy 的 CNI，并在预发用一条真实的拒绝规则验证。Calico、Cilium、Antrea 都在 Kubernetes 的 NetworkPolicy provider 列表里；不要因为“集群能通”就假设策略会执行。把验证做成一个固定脚本：建两个 Pod，应用 deny-all，确认新连接超时，再删掉策略确认恢复。换 CNI 版本、升级节点、改数据面模式之后都重跑一次。

默认拒绝要成为 namespace 的基线，而不是等出事再补。先建 `default-deny`，再按“DNS、数据库、缓存、入口”的顺序逐条放行；每条策略进 Git，变更走 review。策略是 additive 的，新增一条 allow 不会自动收紧旧规则；定期用 `kubectl get networkpolicy -A -o yaml` 和实际连接矩阵对照，防止规则越加越宽。

本章在 2.5 GB 的 lab 里只提交了 Operator 和一个最小的 `Installation`，没有装 Calico API Server、Goldmane、Whisker，也没有开 flow log；Operator 实际拉起的 Pod 有 `calico-node`、typha、`calico-kube-controllers` 和 CSI node driver。生产环境如果要做网络可观测，这些组件和它们的资源开销要单独算，不能把 lab 里的最小安装直接当成生产拓扑。

namespace 也不是网络隔离的同义词。它提供名字作用域，配合 ResourceQuota 划分资源；NetworkPolicy 才是 Pod 间流量的边界，RBAC 才是 API 操作的边界。多租户如果要求强隔离，仍然要考虑多集群、沙箱运行时或虚拟集群，而不是只给 namespace 打一个标签。

用 namespace 标签做租户或环境隔离，但不要把 namespace 本身当安全边界。namespace 只是名字作用域和配额边界；网络隔离靠 NetworkPolicy，身份和权限靠 RBAC，Pod 安全靠 PSA，节点隔离靠多集群或沙箱运行时。跨 namespace 的访问要在策略里显式写 `namespaceSelector`，并给 namespace 打稳定的标签，不要依赖自动生成的 `kubernetes.io/metadata.name` 之外的名字约定。

如果团队只能用托管集群，先确认厂商把 NetworkPolicy 实现到了哪一层：有的托管集群默认 CNI 不执行策略，需要显式开启；有的把策略交给云防火墙，选择器和端口语义会与上游有差异。选型时把“支持 NetworkPolicy”写进验收项，而不是写在功能对比表里就算完成。

要能看见被拒绝的流量。Cilium 的 Hubble 可以直接看丢包和策略判定；Calico 需要额外开 flow log 或接观测组件。没有观测时，排障只能靠 `wget` 超时和猜。至少给关键 namespace 准备一个“连接矩阵”测试：哪些 Pod 到哪些端口应该通、哪些应该超时，出问题时先跑矩阵，再看 CNI 日志。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `kubectl get pods -o wide` | 看 Pod IP 和所在节点 | `IP` 列由 CNI 分配，`NODE` 列用来确认跨节点 |
| `kubectl get networkpolicy` | 列出 namespace 里的策略对象 | 对象存在不代表 CNI 执行 |
| `kubectl get networkpolicy <名字> -o yaml` | 看完整选择器和规则 | 重点看 `podSelector`、`policyTypes`、`from/to` |
| `podSelector` | 选本 namespace 的 Pod | 空 `{}` 选中全部 |
| `namespaceSelector` | 按 namespace 标签选 | 自动标签 `kubernetes.io/metadata.name` |
| `ipBlock` | 按 CIDR 选集群外地址 | 不适合选临时 Pod IP |
| `policyTypes` | 声明限制入站、出站或两者 | 不写时默认 Ingress，有 egress 规则再加 Egress |
| `ports.port` / `endPort` | 目标端口或端口范围 | `endPort` 在 Kubernetes 1.25 stable，需要 CNI 支持 |
| `kubectl get pods -n calico-system` | 看 Calico 组件 | `calico-node` 每节点一个 |
| `kubectl logs -n calico-system -l k8s-app=calico-node` | 看 Felix 策略同步日志 | 本章的最小安装没有开 flow log |
| `calicoctl get ippool -o wide` | 看 Calico 的 Pod 地址池 | 要和 Node 的 `spec.podCIDR` 对齐 |
| `tcpdump` | 在 Pod netns 或节点抓包 | 先确认接口和封装方式 |

如果要把这套策略交给别人复现，`kubectl get networkpolicy -n shorty -o yaml` 的输出比截图可靠；YAML 里能看出 namespace、选择器和端口，截图只能看出名字。策略文件进 Git 时，把 `default-deny` 和 allow 放在同一个目录、按编号排序，新增规则时 diff 一眼能看出来。

本章结束时，`shorty` 运行在 2 节点 Calico 集群上，`default-deny` 加 `allow-dns`、`allow-api-db`、`allow-worker-redis`、`allow-gateway` 五条策略把数据层和入口收紧；api/worker/postgres/redis 仍然可用，测试用的 `probe`、`ingress` namespace 和 `api-canary` 已清理。
