# 第 5 章 数据：volume、bind mount、tmpfs，备份与权限

第 4 章结束时，`shorty-api` 已经能处理信号、写 JSON 日志，也能被 `docker stop` 干净地关掉。但它存链接用的是内存：进程一退，所有短码和点击计数都没了。对一个短链服务来说，这不是“重启后慢一点”，而是用户手里的链接直接失效。把容器删掉再重建，问题更明显——新容器和旧容器没有任何关系，旧容器里写过的东西也不会跟过来。

这不是 `shorty` 的 bug。容器的可写层本来就跟容器同生共死：它是在镜像的只读层之上临时加的一层，删容器时这一层一起删。真正要解决的问题是“数据放在容器生命周期之外”，这一章要用的三种位置是：由 Docker 管理的命名卷（volume）、直接挂宿主路径的 bind mount、以内存为主、默认不落盘的 tmpfs。三者看起来都是容器里的一个目录，但生命周期、权限、备份方式和适用场景完全不同。

这一章从“写进可写层的数据怎么丢”开始，依次做出三种挂载；然后用 PostgreSQL 把“容器重建、数据还在”跑通，做一次 `pg_dump`/`pg_restore` 并用行数验证；最后看磁盘占用和清理，故意制造几个与卷、权限有关的故障。过程中会反复回到同一个判断：这份数据在容器删除、宿主机重启、备份恢复之后，应该还在吗？

> **起点**：第 4 章结束。`shorty:dev` 与 `shorty:0.1` 可用，`shorty-api` 以内存存储监听 8080，没有数据库。`bash code/ch05/setup.sh` 会重新构建这两个镜像、拉取 `postgres:18.6-alpine`，并启动 `shorty-api`；本章后面的示例都在这个状态上继续。

## 5.1 可写层不是存储

先做一个最小实验：在容器里写文件，然后删掉容器，再起一个新容器找这个文件。这个动作不需要数据库，也不需要挂载，目的是把“容器里的文件系统”和“宿主机上的文件系统”分开看。

`docker diff` 的输出要按三个字母读：`A` 是 added（新增），`C` 是 changed（修改），`D` 是 deleted（删除）。例子创建了 `/data.txt`，又在 `/var/lib` 下创建了 `shorty` 目录和 `cache.txt`，所以看到 `A /data.txt`、`A /var/lib/shorty`、`A /var/lib/shorty/cache.txt`；同时 `/var` 和 `/var/lib` 的目录内容变了，标记为 `C`。这些变化都发生在容器的可写层里，不在镜像里，也不在宿主机的某个业务目录里。`docker diff` 比较的是“容器当前的文件系统”和“它启动时那份镜像”，所以它只适合看一个容器改了什么，不是备份工具。

`docker rm -f` 之后，可写层随容器一起删除。新起的 `shorty:dev` 容器基于同一个镜像，`/data.txt` 不存在，`ls` 报 `No such file or directory`。注意这不是“文件被删了”，而是这个文件从来没有出现在镜像里；旧容器的那一份只存在于旧容器的可写层，容器没了，层也没了。

有人会用 `docker commit` 把当前容器提交成新镜像，让 `/data.txt` 留在镜像里。第 2 章已经用 `docker commit` 观察过这个过程：它确实能把可写层固化成一个新镜像，但这是反模式。数据一旦进了镜像，就变成只读镜像的一部分，更新一条记录要重新提交、重新分发镜像；多个副本各自提交会得到不同镜像；镜像层里还会混进密码、临时文件和日志。`commit` 适合一次性实验和留证，不适合当持久化方案。真正要持久化的数据，必须放在容器生命周期之外的挂载里。

Docker 官方列出的持久化挂载不止三种；本章用到的这三类，区别可以先记成一张表：

| 方式 | 数据在哪 | 谁管理 | 容器删除后 | 典型用途 |
|---|---|---|---|---|
| volume（命名卷） | 宿主机上 Docker 管理的目录 | Docker daemon | 还在 | 数据库、需要长期保留的数据 |
| bind mount | 你指定的宿主路径 | 你自己 | 还在，但取决于那个路径 | 开发时挂源码、只读配置 |
| tmpfs | 宿主机内存（可能换出到 swap） | 内核 tmpfs | 容器停止即消失 | socket、临时缓存、敏感中间数据 |

三种挂载在容器里都表现为一个目录或文件，容器里的进程不需要知道自己用的是哪一种。区别在容器外面：卷由 Docker 管，bind mount 由你管，tmpfs 由内核管、默认不落盘（但可能换出到 swap）。下一节先看命名卷，因为数据库最常选它。

> **旧资料提示**：旧教程常说“数据卷就是 `/var/lib/docker/volumes` 下的一个目录，直接进去改就行”。这个路径在默认的 local 驱动下确实能看到，但它是 Docker 的内部布局，卷驱动和存储后端变化时布局会变；管理卷要用 `docker volume inspect`，不要直接改底层目录。官方文档明确把直接访问卷数据称为 unsupported、undefined behavior。

## 5.2 命名卷：Docker 管理的持久化

命名卷（named volume）是 Docker 里最适合数据库的持久化方式。它有一个稳定的名字，例如 `shorty-pgdata`，创建之后可以挂给任意容器；容器删了，卷还在；卷的底层目录由 Docker 管理，你通过 `docker volume` 子命令操作它，而不是直接改 `/var/lib/docker/volumes` 下的文件。

`docker volume create` 返回卷名，`docker volume inspect` 说明这个对象由谁管：`Driver=local` 表示用本地的 local 卷驱动，`Scope=local` 表示只在这台 Docker 主机上有效，`Mountpoint` 是 Docker 在宿主机上放数据的目录。这个路径在默认配置下是 `/var/lib/docker/volumes/shorty-pgdata/_data`，但它是实现细节；换卷驱动、换存储后端（例如 containerd snapshotter）或换 Docker 版本，布局都可能不同。管理卷要用 `docker volume ls/inspect/rm`，不要在宿主机上直接改 `_data` 里的文件。

例子用了两种挂载语法。第一次是 `--mount type=volume,src=shorty-pgdata,dst=/var/lib/postgresql`，第二次是 `-v shorty-pgdata:/var/lib/postgresql`。两者在这个场景下等价；`--mount` 把类型、源、目标写成键值对，读起来更清楚，也支持 `volume-subpath`、`volume-nocopy`、`volume-opt` 这些 `-v` 表达不了的选项。`-v` 的三个字段用冒号分隔：卷名、容器路径、可选的 `ro`/`nocopy` 等选项。日常写 `-v` 更短，但出现“这到底是卷还是宿主目录”的歧义时，`--mount` 更不容易写错。

PostgreSQL 启动需要一点时间，所以例子用 `pg_isready` 轮询，而不是 `sleep`。`pg_isready` 返回 `accepting connections` 才说明数据库能接受连接；此时建表、插入一行 `survives`，再 `docker rm -f shorty-pg`。注意这里删的是容器，不是卷：`docker rm` 只删容器记录和可写层，卷是独立对象。重建容器时继续挂同一个 `shorty-pgdata`，`SELECT * FROM keep_me` 仍然返回那一行。这就是“容器重建、数据还在”的最小闭环。

`docker inspect` 的 `.Mounts` 数组把这件事说得很直白：`Type` 是 `volume`，`Source` 是 Docker 管理的 `_data` 目录，`Destination` 是容器里的 `/var/lib/postgresql`，`RW` 是 `true`。排障时先看这几个字段，能快速区分“挂的是卷”还是“挂的是宿主目录”。如果 `Type` 是 `bind`，`Source` 就是你写的宿主路径；如果 `Source` 为空、`Type` 是 `tmpfs`，数据就在内存里。

卷的生命周期独立于容器：没有容器使用时，卷仍然存在，Docker 不会自动删它。删除卷是单独的动作：`docker volume rm shorty-pgdata`，或者清理命令。这里有一个容易记错的点：`docker volume prune` 默认只删**未使用的匿名卷**，命名卷不在默认清理范围内；要连命名卷一起删，得加 `--all`。官方文档的警告文本写的是 “anonymous local volumes not used by at least one container”，`docker system prune` 默认也不碰卷，只有加 `--volumes` 才会清匿名卷。把这条记反，要么以为备份卷很安全、要么以为清理命令会顺手删掉数据库卷，两种都会出事。

卷的内容还有两个容易忽略的默认行为。第一，挂载一个**空卷**到容器里一个已经有文件的目录时，Docker 会先把镜像里那个目录的内容复制进卷，再挂载；这解释了为什么有些官方镜像的卷第一次启动就有初始配置。第二，挂载一个**非空卷**到已有目录时，镜像里的内容会被卷遮住，容器看到的是卷里的东西。这两种行为都只影响容器里的视图，不会改镜像；不想让 Docker 复制，可以用 `volume-nocopy`。

备份卷的官方做法是起一个临时容器，把卷和宿主目录同时挂进去，用 `tar` 打包。这个做法适合文件级数据，也适合停机后的数据库目录；但数据库运行时直接 `tar` 数据目录，得到的文件在页级别上可能不一致，恢复时可能起不来。数据库更稳的备份是下一节的 `pg_dump`：它由 PostgreSQL 自己保证一致性，恢复到另一个实例也更方便。

> **旧资料提示**：`--volumes-from` 仍然能用，但它把“共享哪个容器的卷”隐式绑定到容器上；今天更清楚的写法是显式命名卷，或在 Compose 里声明卷。

## 5.3 bind mount：开发目录与只读配置

命名卷适合“数据归 Docker 管、应用只管读写”的场景。开发时还有另一类需求：宿主机上的源码、配置、构建产物要实时出现在容器里，改完文件不用重建镜像。这时用 bind mount：把宿主机的一个路径直接挂到容器里的一个路径，两边看到的是同一份文件。

bind mount 的语法和卷很像，但源是宿主路径。`-v /host/path:/container/path:ro` 用冒号分隔，`--mount type=bind,src=/host/path,dst=/container/path,readonly` 用键值对。下面的例子把一个配置目录只读挂进容器，先读配置文件，再尝试写，预期失败。

第一条输出的重点是 `bind source path does not exist`。`--mount` 在默认情况下不会替你在宿主机上创建目录：源路径不存在，Docker 直接拒绝创建容器。`-v` 的行为不同，它会自动创建一个目录，而且是以 root 身份创建。例子里的 `ls -ld /data` 看到 `root root`，宿主机上的 `ls -ldn` 也显示 uid/gid 都是 0。这个差别很实际：如果你本来想挂一个文件，`-v` 却创建了一个同名目录，容器里就会报“是一个目录”；如果你用非 root 用户跑容器，root 拥有的宿主目录又可能写不进去。`--mount` 还有一个 `bind-create-src` 选项，可以显式让它创建源目录，但多数情况下更好的做法是自己先建好目录、设对所有者，再启动容器。

只读挂载的输出分两部分。`docker exec ch05-ro cat /etc/shorty/app.env` 能读到配置文件，说明挂载本身是通的；`docker inspect` 的 `.Mounts` 里，`Type` 是 `bind`，`Source` 是宿主上的 `/book/src/code/ch05/config`，`Destination` 是容器里的 `/etc/shorty`，`Mode` 是 `ro`，`RW` 是 `false`。随后 `echo ... >> /etc/shorty/app.env` 报 `Read-only file system`，这是内核在挂载点上拒绝写，不是应用自己的权限检查。`ro` 是挂载属性，对容器里的所有进程生效，包括 root；即使容器里的 root 有 CAP_DAC_OVERRIDE，也改不了只读挂载。

只读挂载的典型用途是配置、证书、静态资源。同一个宿主目录可以同时以读写方式挂给一个容器、以只读方式挂给另一个容器；只读的限制是每个挂载点各自的，不会改宿主目录的权限。反过来，bind mount 默认是读写的，容器里的进程可以创建、修改、删除宿主上的文件，包括系统文件；官方文档专门提示了这一点。给配置目录加 `:ro` 是最低成本的防线，但不要把整个 `/etc` 或 `/var/lib/docker` 挂进去再指望 `:ro` 能兜底。

SELinux 主机上还要处理标签。`-v` 的第三个字段可以加 `:z` 或 `:Z`：`:z` 表示这个挂载内容在多个容器间共享，`:Z` 表示私有、不共享。Docker 会修改宿主文件或目录的 SELinux 标签，所以 `:Z` 用在 `/home`、`/usr` 这类系统目录上会把宿主机搞坏。`--mount` 不支持设置 SELinux 标签，需要标签时只能用 `-v`。如果宿主机没有启用 SELinux，这两个选项没有效果；如果启用了而你没加，容器可能报 `Permission denied`，但 `ls -l` 的普通权限看起来完全正常，这时要用 `ls -Z` 看标签。

bind propagation 是另一个进阶项，默认是 `rprivate`。它控制“在一个挂载点里再挂一个文件系统”时，这个新挂载会不会传播到其他副本；只有当容器里还要挂载（例如 Docker-in-Docker、Kubernetes 的 CSI 挂载）时才需要 `rshared`/`rslave`。普通开发目录不需要改传播属性，改了反而扩大挂载事件的影响范围。`--mount` 用 `bind-propagation=`，`-v` 把 `rshared` 等写在第三个字段里。

开发时挂源码很方便：改宿主文件，容器里立刻看到。但这条路径不适合生产。bind mount 的源是“这台宿主机上的这个路径”，容器被调度到另一台机器、路径不存在或权限不同，启动就会失败；镜像也因此不再自包含。生产容器应该把代码打进镜像，配置用只读挂载或编排系统的 ConfigMap/Secret；确实要挂宿主目录时，把它当成宿主机和容器之间的显式接口来管理，记录路径、所有者、SELinux 标签和备份责任。

## 5.4 tmpfs：只放临时数据

第三种挂载是 tmpfs。它正常情况下不写宿主磁盘，也不进镜像层，数据只存在内存里；容器停止，tmpfs 挂载被移除，里面的文件就没了。这个“丢”是特性而不是缺陷：socket、临时缓存、一次性的解密结果、只在进程生命周期内需要的凭据，都不应该落到磁盘上。

```console

`df -h /run` 这一行说明挂载生效了：文件系统是 `tmpfs`，大小 16M，挂载点是 `/run`，初始使用量为 0。`dd` 写 32 MB 时，写到 16 MiB 就报 `No space left on device`，`16+0 records out` 和 `16777216 bytes` 说明它确实只写进了 16 MiB，剩下的一半没有空间。注意 `dd` 失败后 `/run/big` 这个半截文件还在，直到下一条命令 `rm -f` 才清掉；这也是 tmpfs 的一个特点：写满不会自动回滚，应用要自己处理 ENOSPC。

`docker inspect` 的那一行值得单独说。`Tmpfs={"/run":"size=16m,mode=1777"}` 说明 `--tmpfs` 的参数被记在 `.HostConfig.Tmpfs` 里，而 `.Mounts` 是空数组 `[]`。这和 `--mount type=tmpfs` 不一样：用 `--mount` 挂的 tmpfs 会出现在 `.Mounts` 里，`Type` 是 `tmpfs`、`Source` 为空。所以判断“容器里有没有 tmpfs”不能只看 `.Mounts`，`--tmpfs` 写的要看 `.HostConfig.Tmpfs`，或者进容器看 `df`/`findmnt`。这是 CLI 记录方式上的差异，不影响挂载本身。

停止再启动之后，`/run/keep` 报 `No such file or directory`。`docker stop` 移除 tmpfs 挂载，`docker start` 重新创建一个空的 tmpfs；不是文件被删了，而是上一次挂载的内存页已经释放。容器重启、宿主机重启也一样。需要跨重启保留的东西不能放 tmpfs，哪怕它“只是临时放一下”——只要进程或节点重启的时机不可控，就不算临时。

tmpfs 的容量默认不是无限的。`--mount type=tmpfs` 不写 `tmpfs-size` 时，默认上限是宿主机总内存的 50%；`--tmpfs` 用 `size=` 指定，例子写的是 16 MB。更重要的是，tmpfs 的用量计入容器的内存 cgroup 限制：给容器设了 `--memory 128m`，tmpfs 里写的数据也算在这 128 MB 里；把 `tmpfs-size` 设得比内存限制还大，并不会给容器额外的内存，写满时可能先触发 OOM。这个行为在把 tmpfs 当“免费缓存”用的时候很容易踩到。

还有一点和“只存在内存”有关：Linux 的 tmpfs 页可以被换出到 swap。官方文档专门提示，tmpfs 里的临时数据可能被写到 swap 文件，从而落到磁盘上。所以 tmpfs 适合放“丢了可以重建”的临时数据，不适合把它当成“绝对不会落盘的秘密存储”；要保证敏感数据不落盘，得同时管住 swap（关闭或加密），而不是只加一个 `--tmpfs`。

tmpfs 的典型用法是 `/run` 下的 socket、临时缓存、一次性的解密结果。`mode=1777` 是带 sticky 位的世界可写目录，适合多个进程共享的 `/tmp`/`/run`；如果只有容器里的某个 uid 需要写，用 `uid=`/`gid=` 和更窄的 `mode` 更安全。`--tmpfs` 不能用于 Swarm service，服务里要用 `--mount type=tmpfs`；单机 `docker run` 两种都可以。

```

第一条命令把三件事放在一起：运行用户 `postgres` 的 uid 是 70，`PGDATA` 是 `/var/lib/postgresql/18/docker`，`/etc/passwd` 里的 `postgres` 条目也是 70/70。最后的 `ls -ld` 显示这个目录的 owner 是 `postgres`、group 是 `root`、权限是 `700`。**uid 不要背。** 这个 Alpine 镜像是 70，Debian 版 `postgres:18.6-trixie` 是 999，不同版本、不同基础镜像都可能变；判断办法就是进容器读 `/etc/passwd` 和 `id`，再看 `PGDATA` 目录的 owner。宿主目录的 uid/gid 要跟这个用户对上，否则 PostgreSQL 可能起不来，或者被 entrypoint 悄悄改掉属主。

`PGDATA` 的路径也要以镜像为准。这个 18.6 镜像的 `PGDATA` 是带主版本号的 `/var/lib/postgresql/18/docker`，所以卷挂在 `/var/lib/postgresql` 这一层，而不是旧教程里的 `/var/lib/postgresql/data`。官方镜像还把 `/var/lib/postgresql` 声明成了 `VOLUME`：即使你不写 `-v`，Docker 也会给它一个匿名卷。把命名卷挂到 `/var/lib/postgresql/data` 并不会接管真正的 `PGDATA`，数据会落在镜像声明的匿名卷里，你以为的 `shorty-pgdata` 其实是空的。判断卷有没有挂对，不要看命令，进容器 `echo $PGDATA` 再 `ls -ld` 那个目录。

`shorty migrate` 用 `--network container:shorty-pg` 起了一个一次性容器。这个参数让新容器共享 postgres 的网络 namespace，所以 DSN 里写 `127.0.0.1:5432` 就能连上；它只用于一次性任务，不是服务之间的常规连接方式。第 6 章会用自定义网络和服务名替代它。`migrate` 的输出说明 `links` 表和过期索引已就绪；随后插入三行，`count` 是 3，这是备份前的基准。

备份前又重建了一次容器，这次同时挂 `shorty-pgdata` 和 `shorty-backup`。`shorty-backup` 是独立卷，挂到 `/backup`；备份文件写在这里，不在容器的 `/tmp` 或可写层。`pg_dump -Fc` 的 `-Fc` 是 custom 格式：它是二进制、压缩过的，能用 `pg_restore` 选择性恢复，也能并行恢复；纯文本格式要用 `psql` 灌回去。例子用 `docker exec` 在容器内走 Unix socket：这个镜像初始化出来的 `pg_hba.conf` 对 local 连接是 trust，所以 `-U shorty` 能直接备份；这是容器内本地连接的便利，不是生产认证方式。生产里的备份脚本不要把密码放在命令行参数，用 `.pgpass`、环境文件或 secret 挂载；跨主机备份要显式走 TCP，并用 scram 或证书认证。

`ls -lh` 看到文件只有几 KB，文件头是 `PGDMP`，说明 custom 格式写成功了。这个文件在 `/backup` 卷里，容器删了它还在；如果写到容器可写层，容器一删就没了。注意这个 lab 里文件权限是 `-rw-rw-rw-`：`docker exec` 以 root 运行，备份文件的权限由当时的 umask 决定，这里就成了所有人可读写。备份里是整库数据，生产要在 `pg_dump` 之前设 `umask 077`，或者以 `postgres` 用户运行并 `chmod 600`，不要把“备份”变成新的泄露面。

恢复前先把 `links` 和 `keep_me` 都删掉，模拟数据全丢。`DROP TABLE` 成功，随后查 `links` 报 `relation "links" does not exist`，这就是灾难现场。`pg_restore` 从 `/backup/shorty.dump` 恢复，没有输出；再用 `-tAc` 查 `count(*)`，只输出 `3`，和备份前一致。行数对上只说明数据回来了，生产还要检查索引、约束、序列和权限；这个例子里 `links` 的主键和 `links_expires_at_idx` 都在 dump 里，恢复时会一起建。

`pg_restore` 默认不会先清理目标库里已存在的对象。如果只删了 `links`、`keep_me` 还在，恢复在重建 `keep_me` 的主键时就会报 `multiple primary keys for table "keep_me" are not allowed`。这不是备份坏了，而是恢复到非空库的常见冲突。要么像例子这样先删掉要恢复的对象，要么用 `pg_restore --clean --if-exists`，要么恢复到空库。生产演练要按真实恢复路径走一遍，不能只验证“dump 文件存在”。

## 5.6 存储驱动、磁盘与清理

到这里，数据已经有了三个位置：镜像层、容器可写层、卷/绑定挂载。磁盘告警时，先要知道空间被谁占了。Docker 的镜像和容器层由存储驱动管理：传统 graph driver 里最常见的是 `overlay2`，Docker Engine 29.0 起新安装默认用 containerd 镜像存储，底层是 `overlayfs` snapshotter。两者的共同点是分层和写时复制；区别在镜像内容的组织方式，以及 `docker image ls` 的列。排障时不要背驱动名，先看 `docker info` 的 `Storage Driver` 和 `DriverStatus`。

> **旧资料提示**：旧教程常把 Device Mapper、AUFS 当常见存储驱动。Device Mapper 已弃用，并在 Docker Engine v25.0 移除；AUFS 也早不是默认值。传统 graph driver 的默认是 `overlay2`，Engine 29.0 起新安装默认用 containerd 镜像存储。

`docker system df` 把占用分成四类：`Images`、`Containers`、`Local Volumes`、`Build Cache`。镜像和容器层、卷、构建缓存是分开算的；`docker system prune` 默认清理停止的容器、未使用的网络、悬空镜像和构建缓存，但**不清理卷**。`docker volume prune` 默认只清匿名卷，命名卷要加 `--all`。这两个命令的差别，决定了“清磁盘”会不会顺手把数据库卷删掉。

第一张 `docker system df` 是基线：`Images` 里有基础镜像、shorty 镜像和 postgres 镜像，`Containers` 是四个运行中容器的可写层，`Local Volumes` 是 `shorty-pgdata` 和 `shorty-backup`，`Build Cache` 是前面构建留下的缓存。`ACTIVE` 表示当前被使用的对象数，`RECLAIMABLE` 表示按当前规则可以回收的部分。注意 `Containers` 这一行在容器停止后仍然占空间：停止容器只释放进程，不释放可写层，除非删掉容器。

制造之后，`Images` 多出 4 个：三次不带 tag 的构建留下三个悬空镜像（`<none>:<none>`），第四次带 `ch05-disk:1` 的构建再多一个带 tag 的镜像；`Containers` 多出两个，是刚退出但没删的容器，可写层占了十几 MB；`Build Cache` 的条数和大小也跟着涨，因为每次构建都会留下缓存记录。`docker ps -a` 能看到两个 `Exited (0)` 的容器，`docker image ls -f dangling=true` 能列出三个 `<none>`。悬空镜像的定义是“没有 tag，也没有容器引用”；它不等于“没用的镜像”，只是 Docker 不知道你想不想留它。

`docker system prune -f` 的输出只保留了三类行：`Deleted Containers`、`Deleted Images`、`Deleted build cache objects`，最后是 `Total reclaimed space`。回收量以最后一行为准：两个停止容器、三个悬空镜像和一部分构建缓存都算在里面。`Local Volumes` 没有出现在删除列表里，后面的 `docker volume ls` 也证明 `shorty-pgdata` 和 `shorty-backup` 都还在。`docker system prune` 默认不碰卷，这是它和 `docker volume prune` 最重要的区别。

带 tag 的 `ch05-disk:1` 也没有被删。`docker system prune` 默认只删悬空镜像，不删“有 tag 但没容器用”的镜像；要连这些一起删，得用 `docker system prune -a` 或 `docker image prune -a`。这正是回滚镜像容易被误删的地方：昨天的版本标签还在本地，但没有容器在用，`-a` 会把它清掉。清理前先确认回滚窗口和镜像清单，别把 `-a` 当成默认参数。

清理后的 `docker system df` 里，`Images`、`Containers` 和 `Local Volumes` 回到清理前的数量，但 `Build Cache` 没有归零，`RECLAIMABLE` 列还显示一小部分可回收。`docker system prune` 不是“把缓存清零”，它只删 BuildKit 判定为未使用的那部分；有些缓存仍然被当前镜像或构建记录引用，或者不在默认清理范围内。要更细地按 builder 清，用 `docker buildx prune`；要看每个对象占多少，用 `docker system df -v`。

`Local Volumes` 这一行要单独看。`docker volume prune` 默认只删**匿名卷**，命名卷要加 `--all`；`docker system prune --volumes` 也只清匿名卷，命名卷仍然保留。所以“`docker volume prune` 会删掉数据库卷”这句话只在加了 `--all`、并且卷没有被任何容器使用时才成立。反过来说，`--all` 很危险：一个已经删掉的数据库容器留下的卷、一个还没挂回去的备份卷，都可能在这一步被清掉。清理命令先在预发跑，确认 `docker volume ls` 里哪些名字是数据、哪些是临时卷，再决定加不加 `--all`。

磁盘告警时，先分两层看。宿主机层用 `df -h` 看分区；Docker 层用 `docker system df` 看对象。5.6 的第一行 `docker info` 给出 `Storage Driver=overlayfs` 和 `Docker Root Dir=/var/lib/docker`；`Docker Root Dir` 是镜像和容器层的根目录，containerd 镜像存储还可能使用独立的路径，如果它们和 `/var/lib/docker` 不在同一个分区，只看一个 `df` 会漏。`overlayfs` 是 containerd snapshotter 的名字；传统 graph driver 下会显示 `overlay2`。两者都用分层和写时复制，`docker system df` 的读法一样，但不要把 `overlayfs` 当成 `overlay2` 的别名去查旧文档。

containerd 镜像存储还有一个磁盘上的差别：它同时保留压缩层和解压后的内容，所以同样的镜像可能比传统 overlay2 占更多空间；这是 Engine 29 新安装默认 containerd 镜像存储后，磁盘告警变常见的原因之一。官方文档给的建议是定期 `docker image prune`、用 `docker system df` 监控、必要时把数据目录换到更大的分区。`docker image prune` 默认只删悬空镜像，`-a` 才删所有未被容器使用的镜像；和 `docker system prune -a` 一样，先确认回滚依赖。

## 5.7 排障：卷挂错、权限不对、容器删了卷还在

这一节把前面几节最容易出错的三个场景串起来。第一个是“宿主目录挂进去，PostgreSQL 起不来”；第二个是“目录非空，initdb 拒绝初始化”；第三个是“容器删了，以为卷也没了”。三个故障的现象不同，但定位入口都指向同一个地方：`docker inspect` 的 `.Mounts` 和宿主目录的 uid/gid。

先看权限。下面的容器用 `--user 70:70` 按镜像里的 `postgres` 用户运行，宿主目录 `/tmp/ch05-pg-bad` 事先不存在，靠 `-v` 自动创建。

```console
{{#include code/ch05/5_7_troubleshooting.out}}
```

`docker logs` 的第一行就是结论：`mkdir: can't create directory '/var/lib/postgresql/18/': Permission denied`。容器不是没挂上，`docker inspect` 的 `.Mounts` 明确显示 `Type=bind`、`Source=/tmp/ch05-pg-bad`、`Destination=/var/lib/postgresql`、`RW=true`；挂载是对的，错的是目录的所有者。`ls -ldn` 显示宿主目录是 `0 0`，也就是 root:root、权限 755；容器里的进程是 uid 70，没有权限在这个目录下创建 `18` 这一层。`PGDATA` 是 `/var/lib/postgresql/18/docker`，`18` 目录都建不出来，initdb 根本没机会跑。

修复有两条路。第一条是把宿主目录的所有者改成镜像里的 uid/gid，例如 `chown 70:70 /tmp/ch05-pg-bad`，再启动容器；Debian 版如果 uid 是 999（本例的 `postgres:18.6-trixie` 就是），就 `chown 999:999`。第二条是改用命名卷，让 Docker 管目录，例子选的是这条：删掉 `shorty-pg`，`docker volume ls` 仍然能看到 `shorty-pgdata`，用同一个卷重建，`pg_isready` 接受连接，`SELECT count(*) FROM links` 返回 3。命名卷由 Docker 创建和管理，不会像 `-v /tmp/...` 那样先造一个 root:root 的宿主目录；entrypoint 也能按镜像里的用户处理它。bind mount 不会替你做这件事。

不要用 `chmod 777` 绕过。数据库目录一旦对所有人可写，宿主机上的任何进程都能改数据文件；`chmod 777` 还把“谁拥有这个库”这个问题掩盖了，下次换 uid 还得再猜。正确做法是让目录的 uid/gid 与镜像里的运行用户一致，权限保持 `700` 或 `750`，需要组访问时再加组。SELinux 主机还要加 `:z`/`:Z`，否则普通权限全对也会 `Permission denied`。

还有一个容易被“修复”掩盖的情况：不写 `--user` 时，官方 postgres 镜像的 entrypoint 以 root 启动，会先把 `PGDATA` chown 给 `postgres`，再降权运行。容器可能正常起来，但宿主目录的所有者被悄悄改成了容器里的 uid；这在单机开发看不出问题，到了多主机或备份脚本里就会变成“文件属主怎么变了”。bind mount 给数据库用时，先 `ls -ldn` 确认 uid，再启动，不要依赖 entrypoint 帮你改。

第二个故障是目录非空。例子把 `PGDATA` 指到 `/var/lib/postgresql/data`，并把一个含有 `README` 的宿主目录挂到同一个路径。`initdb` 的输出是 `directory "/var/lib/postgresql/data" exists but is not empty`，后面还给了提示：要么清空目录，要么换一个目录。这个错误和权限错误不同：目录可写，但里面已经有文件，`initdb` 拒绝在一个“看起来像已有数据库”的目录上初始化，以免覆盖数据。宿主目录如果是文件系统的挂载根，`lost+found` 也会让它非空；不要把一个已经有内容的目录直接指给 `PGDATA`。

第三个故障是“容器删了，卷还在”。例子里的 `docker rm -f shorty-pg` 没有带 `-v`，`shorty-pgdata` 仍然在 `docker volume ls` 里，重建后数据也在。这不是巧合：`-v` 只影响**匿名卷**，命名卷本来就不会因为删容器而消失。旧说法“`docker rm` 一定要带 `-v` 才能保住/删掉卷”把两种卷混在了一起：命名卷用 `docker volume rm` 删，匿名卷才跟 `docker rm -v` 或 `docker run --rm` 的清理有关。用匿名卷时，删容器不带 `-v` 会留下一个 64 位十六进制名字的卷，`docker volume ls -f dangling=true` 能找到它，再用 `docker volume inspect` 看 `Mountpoint` 或挂给新容器验证内容。

最后把 api 切到 PostgreSQL。`shorty-api` 用 `shorty-pg` 的容器 IP 作为 DSN 主机，`/readyz` 返回 200，`docker ps` 只剩 `shorty-api` 和 `shorty-pg`，`links` 表里还是 3 行。这个 IP 是临时的：容器重建后 IP 会变，api 的 DSN 就失效了。第 6 章会用自定义 bridge 网络和内嵌 DNS，把 DSN 里的 IP 换成服务名 `shorty-pg`，这也是为什么这一章不把“用 IP 连接”写成最终方案。

## 上生产前

**数据库用命名卷或 CSI 卷，不用 bind mount 到宿主临时目录。** 命名卷的生命周期由 Docker 管，删容器不会删卷；bind mount 依赖宿主路径、所有者和 SELinux 标签，换一台机器就可能起不来。Kubernetes 里对应的是 PVC/CSI 卷，不是 `hostPath`。不管用哪种，卷都要纳入备份和恢复演练：这一章的 `pg_dump`/`pg_restore` 是最小演练，生产还要覆盖全量、增量、恢复时间目标和恢复点目标。

**卷权限按镜像的 uid/gid 设，不要用 `chmod 777`。** 先 `docker exec <容器> id <用户>` 和 `grep` `/etc/passwd` 确认 uid，再在宿主上 `chown` 成同一个 uid/gid；需要组访问时用 `750`/`770`，不要放开到所有人。SELinux 主机加 `:z`（共享）或 `:Z`（私有），并知道 `:Z` 会改宿主标签。数据库目录的属主被 entrypoint 悄悄改掉，是多主机备份和审计里很难查的一类问题。

**生产容器尽量只读根文件系统，把可写目录显式挂成卷或 tmpfs。** `--read-only` 会让容器里所有没挂载的路径都不可写，包括 `/tmp`、日志目录、socket 目录；先跑一遍 `docker diff` 看应用实际写了哪些路径，再把这些路径逐个挂成卷或 tmpfs，剩下的保持只读。不要为了省事把整个根文件系统挂成可写；只读根文件系统能挡住很多“应用往镜像层写文件”的问题。

**清理命令先在预发跑，`docker volume prune --all` 尤其危险。** 默认的 `docker volume prune` 只删匿名卷，`--all` 才删命名卷；`docker system prune` 默认不删卷，`--volumes` 也只删匿名卷。一个已经删掉的数据库容器留下的卷、一个还没挂回去的备份卷，都可能被 `--all` 清掉。清理前先用 `docker volume ls` 和 `docker volume inspect` 对名字，确认哪些是数据卷；`docker system prune -a` 还会删掉没容器使用的回滚镜像，先看回滚窗口。

**构建缓存也要算进磁盘预算。** `docker system df` 的 `Build Cache` 可能比镜像还大；`docker system prune` 只清它判定为未使用的部分，`docker buildx prune` 按 builder 清。CI 里每次构建都留下缓存，时间长了会占满 `/var/lib/docker` 或 containerd 的数据目录；把缓存后端放到 registry 或定期清理，比等磁盘告警再处理更可控。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `docker volume create/ls/inspect/rm` | 创建、列出、查看、删除卷 | 命名卷删容器不删；`rm` 正在使用的卷会失败 |
| `docker volume prune` | 清理未使用的卷 | 默认只删匿名卷；命名卷加 `--all` |
| `-v name:/path` / `--mount type=volume,src=name,dst=/path` | 挂命名卷 | `--mount` 更显式，支持 `volume-subpath`/`volume-nocopy` |
| `-v /host:/path:ro` / `--mount type=bind,src=/host,dst=/path,readonly` | 挂宿主目录 | `--mount` 默认不创建源目录；`-v` 会创建 root 拥有的目录 |
| `:z` / `:Z` | SELinux 共享/私有标签 | 只能用于 `-v`；`--mount` 不支持 |
| `bind-propagation=` / `rshared` | 控制挂载传播 | 默认 `rprivate`；只有嵌套挂载才需要改 |
| `--tmpfs /path:size=16m,mode=1777` | 挂内存文件系统 | `--mount type=tmpfs` 用 `tmpfs-size`/`tmpfs-mode` |
| `docker inspect .Mounts` | 看挂载的 `Type`/`Source`/`Destination`/`RW` | `--tmpfs` 写在 `.HostConfig.Tmpfs`，不在 `.Mounts` |
| `docker diff` | 看容器可写层的 A/C/D 变化 | 不是备份工具；数据应挂载到卷/绑定挂载/tmpfs |
| `docker system df` | 看镜像、容器、卷、构建缓存占用 | `-v` 看每个对象；`df -h` 看宿主分区 |
| `docker system prune` | 清停止容器、悬空镜像、未使用缓存 | 默认不删卷；`-a` 连未使用 tag 镜像一起删 |
| `docker volume prune --all` | 连命名卷一起清 | 可能删掉未挂载的数据库/备份卷，先核对 |
| `pg_dump -Fc -f /backup/db.dump` | custom 格式逻辑备份 | 写到卷或宿主目录，不要留可写层 |
| `pg_restore -d db /backup/db.dump` | 从 custom 格式恢复 | 默认不清理已有对象，必要时 `--clean --if-exists` |

本章结束时，`shorty-api` 和 `shorty-pg` 都在运行，数据库用命名卷 `shorty-pgdata`，另有一个备份卷 `shorty-backup`；`shorty migrate` 已建好 `links` 表，表里有 3 行。api 目前用 postgres 的容器 IP 连接，下一章把它和 postgres 接到同一个自定义网络，用服务名互相解析。
