# 第 3 章 运行时栈：CLI → dockerd → containerd → runc，以及 CRI

第 2 章把 `shorty:0.1` 拆成了层、manifest 和 config，落进 containerd 的镜像存储。镜像有了，接下来要让它变成一个进程。这一步在终端里只是一行 `docker run`，但一行命令背后至少经过四个角色。`docker` 客户端、`dockerd`、`containerd`、`runc` 各管一段，任何一段出问题，现象都不一样：`docker ps` 有容器但 `ps` 找不到进程，或者进程在跑而 Docker 不知道它，都是真实会遇到的故障。

先看两个具体问题。第一，`docker run -d shorty serve` 之后，`/shorty serve` 的父进程是谁？很多人会猜 `dockerd`，实际是 `containerd-shim`，而 `runc` 在启动完进程以后已经退出了。第二，Kubernetes 的 kubelet 为什么不直接调用 Docker？因为 kubelet 只认一套 gRPC 接口 CRI（Container Runtime Interface，容器运行时接口），Docker Engine 本身不实现这套接口，节点上换成了 containerd 的 CRI 插件。把这两条链画清楚，才能解释为什么节点上没有 `docker` 命令，Pod 却照样能跑。

这一章沿着两条链走：Docker 的 `docker → dockerd → containerd → shim → runc`，以及 Kubernetes 的 `kubectl → kubelet → CRI → containerd → shim → runc`。中间会手工写一个 OCI runtime bundle，用 `crictl` 从节点内部看容器，故意让 RuntimeClass 找不到 handler，最后用 `runc` 和 `crictl` 排查“容器到底跑没跑”。

> **起点**：第 2 章结束。lab 里有 `shorty:0.1` 和 `busybox:1.37`，没有运行中的容器，也没有 kind 集群。`bash code/ch03/setup.sh` 会重新构建 `shorty:0.1` 并拉取 `busybox:1.37`；3.3 起才会创建单节点 kind 集群。

## 3.1 Docker 的四层：client、dockerd、containerd、runc

`docker` 命令本身不创建容器。它是客户端，把参数拼成 REST 请求，通过 `/var/run/docker.sock` 发给 `dockerd`。Docker 官方文档把这条边界写得很清楚：客户端和 daemon 用 REST API 通信，可以走 UNIX socket，也可以走网络；daemon 负责镜像、容器、网络、卷这些对象。所以 `docker` 二进制可以在另一台机器上，`dockerd` 才是真正监听请求的进程。

`/var/run/docker.sock` 的权限等于宿主 root：能写这个 socket 的人可以让 dockerd 起一个挂载宿主根目录的容器。客户端也可以通过 `DOCKER_HOST` 连到远程 daemon，这时 `docker` 和容器不在同一台机器上，“本机 ps 找不到容器进程”是正常的。Docker 的 client/server 分层不是为了好看，它决定了排障时先看哪一侧：`docker version` 的 Client 段来自本地二进制，Server 段来自 socket 另一端。

`dockerd` 管的是“Docker 对象”：镜像的 tag 和引用、容器元数据、网络端点、卷挂载、端口发布、日志驱动。它不直接 fork 容器进程，容器生命周期交给 containerd。containerd 管两件事：镜像内容与快照（snapshotter 把镜像层铺成 rootfs），以及容器任务（task）。收到启动请求后，containerd 启动一个 `containerd-shim`，shim 再调用 `runc`。`runc` 读取 OCI runtime bundle，创建 namespace、挂载 rootfs、写 cgroup，最后 `execve` 容器进程；进程起来以后 runc 自己退出，剩下的由 shim 看着。

`ps` 的几行里，PID 1 是 `docker-init`（本书的 lab 本身是一个 dind 容器，它的 PID 1 是 `docker-init`；普通 Linux 宿主机上这里是 `systemd`），`dockerd` 是另一个 PID；shim 的 PPID 列是 1，`/shorty serve` 的 PPID 等于 shim 的 PID。**`shorty` 的父进程是 shim，不是 dockerd**；shim 的父进程又是 PID 1，不是 dockerd。`pstree` 从 shim 开始，shim 下面就是 `shorty`；`dockerd` 那一支只有它自己的线程，没有 shim。父子关系反映的是“谁负责回收这个进程”，不是“谁发起了创建请求”。shim 被 reparent 到 PID 1，是为了让它独立于 daemon 的请求处理循环：容器进程的 stdio、退出码和信号由 shim 收着，再通过 containerd 报回去。

第二个误读是“containerd 一定是独立进程”。`ps` 里确实没有 `containerd`，只有 `dockerd` 和 shim；但 `docker version` 报告 containerd `v2.4.2`，`ctr` 也能通过 `/var/run/docker/containerd/containerd.sock` 看到同一个容器和它的 task。原因是 Docker Engine 29.7.0 起支持把 containerd 嵌进 `dockerd` 进程（embedded containerd，实验特性），这时 daemon 和 containerd 走内存连接，task shim 仍然是独立进程。官方文档说默认仍是“单独启动并管理 containerd”；这个 lab 的 dind 镜像里没有系统 containerd，看到的就是嵌入模式。判断方法不是只看 `ps`，而是看 `docker version` 的 containerd 版本和 socket 路径。

还要注意，Docker 用的 containerd 和 Kubernetes 节点用的 containerd 不是同一个实例。Docker 的这个 containerd 归 dockerd 管，namespace 是 `moby`；官方文档明确说 embedded 模式不包含 CRI，不能同时开 `embedded-containerd` 和 `cri-containerd`。节点上给 kubelet 用的是另一个 containerd 进程，namespace 是 `k8s.io`，它才启用 CRI 插件。把这两个实例混在一起，就会得出“Docker 里有容器，为什么 kubelet 看不见”的错误结论。

`docker info` 这一行给出 Server 29.9.2、Storage `overlayfs`、Cgroup `cgroupfs`。这里的 `overlayfs` 是 containerd snapshotter 的驱动名，不是旧的 overlay2 graph driver；`docker info -f '{{ .DriverStatus }}'` 会显示 `driver-type io.containerd.snapshotter.v1`，说明镜像存储走的是 containerd。

`ctr` 的两行输出说明 containerd 自己记着什么：`containers list` 里有容器 ID、镜像引用 `docker.io/library/shorty:0.1` 和运行时 `io.containerd.runc.v2`；`tasks list` 里同一个 ID 对应一个 PID、状态 `RUNNING`，这个 PID 就是 `ps` 里 `/shorty serve` 的 PID。`runc --root /var/run/docker/runtime-runc/moby list` 又往下走了一层：它看到的状态是 `running`，bundle 路径是 `/run/docker/containerd/daemon/io.containerd.runtime.v2.task/moby/<容器 ID>`。这个路径把 containerd 的 task 目录和 runc 的 bundle 对上了，也说明 Docker 的容器归在 containerd 的 `moby` namespace 里。

把 `ctr` 的两张表分开看：`containers list` 是 container 元数据，`tasks list` 才是正在运行的进程；一个 container 可以没有 task（还没 start，或者已经退出）。镜像的 manifest、config 和 layer 在 containerd 的 content store 里，snapshotter 把 layer 铺成 rootfs，task 才对应进程。dockerd 负责把 `shorty:0.1` 这样的 tag 解析成 digest，再让 containerd 去取内容；真正碰镜像层的是 containerd，不是 runc。

四层不是四个必须独立存在的进程，而是四个职责边界。dockerd 的边界是 Docker API 和 Docker 对象；containerd 的边界是 content store、snapshot 和 task；shim 的边界是“容器进程的父进程”，负责 stdio、退出码和信号；runc 的边界是“按 OCI spec 把进程放进隔离环境”。边界清楚的好处是排障可以二分：`docker ps` 有而 `ctr tasks list` 没有，问题在 dockerd 到 containerd 之间；`ctr tasks list` 有而 `ps` 没有，问题在 shim/runc 或进程本身。

这也是为什么 `docker` 客户端可以远程连 daemon，而 `runc` 不能：dockerd 暴露的是网络/UNIX socket 上的 API，runc 只接受本地的一个 bundle 目录。把这两类接口混在一起，就会以为“有 socket 就能管容器”，实际上 runc 连“列出所有容器”都要靠 `--root` 指向正确的 state 目录。

反过来，`ps` 里有 `/shorty serve` 而 `docker ps` 里没有，也不一定是灵异事件：可能是容器已经退出但 shim 还没回收，可能是有人用 `runc` 手工起的容器，也可能是另一个 daemon（比如节点上的 containerd）在管它。先确认这个进程的父进程和 cgroup，再决定去问哪个 daemon。

`runc` 在 `ps` 里找不到，不是它没参与，而是它的生命周期只到“把进程启动起来”为止。它不做守护、不监听 socket、不管理运行中的容器；`runc list` 能列出状态，是因为它读的是磁盘上的 state 文件，不是因为它还在内存里盯着。下一节把 bundle 拆开，看它到底读了哪些字段。

> **旧资料提示**：旧教程常把 libcontainer 说成“Docker 的容器格式”或“Docker 的原生执行环境”。Docker 1.11 拆出 containerd 和 runc 之后，执行走的是 OCI runtime；现在 Docker 文档的表述是 containerd 管生命周期、默认用 runc，libcontainer 不再是需要读者理解的对外概念。

## 3.2 OCI runtime bundle：config.json + rootfs

`runc` 不认识镜像，也不认识 Docker 的 tag。它只认一个目录：里面有一份 `config.json` 和一个 `rootfs/`。这份 `config.json` 遵循 OCI Runtime Spec，描述“要启动哪个进程、进程看到什么样的 namespace、rootfs 在哪、cgroup 怎么建、挂载哪些文件系统”。`rootfs/` 就是容器里的 `/`。两者合起来叫 OCI runtime bundle，是“运行一个容器”的最小输入。

`runc spec` 生成的默认配置里，`process.args` 是 `["sh"]`，`process.terminal` 是 `true`，`root.path` 是 `rootfs`、`root.readonly` 是 `true`，`linux.namespaces` 包含 pid、network、ipc、uts、mount、cgroup 六类，`linux.cgroupsPath` 是 `null`。这份默认值适合“在终端里交互式跑一个 shell”：terminal 为 true 时，runc 需要一个 console socket 来转发 TTY。例子要的是非交互的前台输出和后台 sleep，所以先把 `terminal` 改成 false；否则 `runc create` 会因为拿不到 console 而失败。

`root.path` 是相对 bundle 目录的路径，`runc` 会把它 `pivot_root` 成容器里的 `/`；`root.readonly` 为 true 时，容器的根文件系统只读。`process.args` 是容器里的 PID 1，它退出容器就退出。`linux.namespaces` 决定隔离哪些资源；默认的六类不含 user namespace，所以容器里的 root 和宿主 root 的 uid 相同，这一点在第 8 章讲安全时会再回来。`linux.cgroupsPath` 为空时，runc 会自己找一个位置建 cgroup；例子显式写成 `ch03-runc`，方便在 `/sys/fs/cgroup` 下找到它。`linux.resources` 里的 `memory`、`cpu` 等字段才是限额，Docker 的 `--memory` 最终会落到这里。

`runc spec` 生成的是“能跑起来”的起点，不是安全基线。`config.json` 里还有例子没展开的字段：`mounts` 决定 `/proc`、`/dev`、`/sys` 这些挂载，`process.capabilities` 决定容器保留哪些 capability，`linux.seccomp` 决定系统调用过滤，`linux.resources` 决定 cgroup 限额。runc 只按这些字段执行，不判断它们是否合理；默认 spec 给的是“能跑”的配置，生产要在它上面按最小权限收紧。它默认让进程以 root 运行，capabilities、seccomp、AppArmor 都没有按业务收紧；Docker 和 containerd 会在它上面覆盖用户、capabilities、seccomp profile 和 cgroup 限额。读 bundle 时要区分“runc 的默认值”和“这个容器实际生效的值”，后者以 `runc state` 指向的 bundle 和 `/proc/<pid>/status` 为准。

第一个 `runc run ch03-oneshot` 是前台模式：创建、启动、等 `/bin/echo` 退出、删除，一条命令走完。输出只有 `hello from runc`，随后的 `runc list` 只剩表头，说明容器记录已经被清掉了。`runc run` 不适合跑长期服务，因为它会占住当前终端直到进程退出；要分离运行就用 `create` 加 `start`。

`runc create ch03-runc` 之后，`runc state` 的 `status` 是 `created`，进程已经有了 PID，但还没有执行 `process.args`；`runc start` 之后才变成 `running`。这时 `runc exec ch03-runc /bin/echo inside-runc` 能在同一个容器的 namespace 里再起一个进程，输出 `inside-runc`。`runc kill` 之后 `status` 变成 `stopped`，`pid` 变成 0；`runc delete` 之后 `runc list` 不再有这条记录。**`stopped` 是 runc 记录里的一个中间状态，`delete` 才是记录消失**；这两个动作分开，正好对应 3.7 里 Docker 容器停止后 `runc list` 的表现。

bundle 里没有镜像名、没有网络配置、没有卷。`runc` 也不拉镜像：它假定 `rootfs/` 已经存在。真实环境里 rootfs 通常是 snapshotter 挂出来的 overlay 挂载点，不是 `docker export` 复制出来的一棵目录树；复制只在教学和离线调试时用。网络 namespace 默认是新建的空 namespace，里面只有 loopback，veth、IP、路由要由 CNI 或 Docker 网络驱动在 runc 之外配置好。

网络由 CNI 或 Docker 的网络驱动在 bundle 之外准备好，卷是额外的 bind mount，镜像拉取和解压是 containerd 的事。`runc` 只负责“按这份描述把一个进程放进隔离环境里”。也正因为它只做这一件事，它才可以被替换：youki、gVisor 的 `runsc`、Kata 的 shim 都可以接在 containerd 后面，只要它们能理解同一份 OCI 配置。

## 3.3 Kubernetes 的 CRI：kubelet 只认接口

kubelet 不链接 Docker 的客户端库，也不解析 Docker 的 API。它按 CRI 定义的一组 gRPC 接口调用节点上的容器运行时。CRI 把接口分成两组：`RuntimeService` 管 Pod sandbox 和容器的生命周期、exec/attach、日志、stats；`ImageService` 管拉镜像、列镜像、查镜像状态。kubelet 通过 `--container-runtime-endpoint` 指定运行时端点，官方 kubelet 参考页给 containerd 的默认值是 `unix:///run/containerd/containerd.sock`；节点上的 containerd 打开 CRI 插件后监听这个 socket。

kubelet 的同步循环对每个 Pod 先创建 sandbox，再创建业务容器。sandbox 创建失败，业务容器根本不会进入创建阶段；`crictl pods` 的 STATE 是 sandbox 的状态，`crictl ps` 的 STATE 是容器的状态，两者可以不一致。`ImageService` 则是另一条路径：kubelet 先 `ImageStatus`/`PullImage`，再让 `RuntimeService` 用镜像 ID 起容器。镜像拉取失败和 sandbox 创建失败在事件里是两类不同的原因，排障时不要混。CRI 的 `v1` API 在 Kubernetes 1.23 稳定，Kubernetes 1.26 起 kubelet 只支持 `v1`，不实现 `v1` 的运行时会连节点都注册不上。

这里要区分 `crictl` 和 `docker`。`crictl` 是 CRI 的调试客户端，它只做 CRI 协议里有的操作：列 sandbox、列容器、看日志、inspect、stats、pull 镜像。它没有 build、没有 compose、没有 `docker run` 那套参数；它按 CRI 的 ID、Pod/容器名和 label 定位对象，不认 Docker 的镜像 tag 和容器名那一套。把它当成“Docker CLI 的替代品”会处处碰壁。它的 endpoint 可以写在 `/etc/crictl.yaml`，也可以用 `--runtime-endpoint` 或 `CONTAINER_RUNTIME_ENDPOINT` 临时覆盖；如果都不写，它会依次试一组已知路径。

那 pause 在哪？`crictl images` 里的 `registry.k8s.io/pause 3.10` 就是 sandbox 镜像。Pod 创建时，containerd 先起一个 pause 容器，由它持有这个 Pod 的 network、IPC、UTS 等 namespace；业务容器再加入这些 namespace。所以同一 Pod 里的容器共享网络和 IPC，能通过 `localhost` 互访。pause 不跑业务代码，它的作用是让 namespace 有一个长期存在的持有者：业务容器重启，sandbox 不必重建；sandbox 重建，Pod 里的容器就都要重来。

节点上的 `ps` 给出最后一层证据：`containerd` 是父进程为 1 的独立进程，`kubelet` 是另一个独立进程，另外还有一串 `containerd-shim`。每个 sandbox 和每个容器都对应一个 shim；shim 的父进程同样是 1。把这张图和 3.1 的 Docker 图并排看，区别只在“谁调用 containerd”：Docker 是 `dockerd`，Kubernetes 是 `kubelet` 通过 CRI。再往下，shim 和 runc 是同一套东西。

## 3.4 dockershim 移除：1.24 的分界线

dockershim 是 kubelet 里的一段适配代码：它把 CRI 请求翻译成 Docker Engine 的 API，让 kubelet 能通过 Docker 管容器。Kubernetes 1.20 宣布弃用，1.24 正式移除；1.23 是最后一个还带 dockershim 的版本。常见的误记是“1.25 才移除”，差了一个 minor。移除之后，节点运行时必须是实现 CRI 的组件：containerd、CRI-O，或者用 `cri-dockerd` 把 Docker Engine 重新包一层。

为什么要移？Docker Engine 的 API 不是 CRI，kubelet 为了支持它要在树内维护一套 Docker 特有的逻辑；每加一个运行时都要改 kubelet，违背了 CRI 的插件设计。把 dockershim 拿掉以后，kubelet 只面对 CRI，containerd 和 CRI-O 各自实现同一套 gRPC 接口，运行时可以独立升级。

移除 dockershim 不等于 Docker 不能跑容器。Docker Engine 29 自己也是 containerd 加 runc 的封装：它跑容器没有问题，问题只是 kubelet 不再通过 dockershim 调它。节点上同时装 Docker 和 containerd 时最容易混淆：`docker run` 的容器归 Docker 的 daemon，`crictl ps` 的容器归 kubelet 用的 containerd，两边各有自己的镜像存储和 namespace。

节点上的 Docker 容器不会自动变成 Pod。迁移后要有新的 Pod 来重新创建容器，原来 `docker run` 出来的东西不会因为换了运行时就被接管；先加新节点、验证，再逐个替换旧节点，比原地改 endpoint 稳。

迁移时先确认节点到底在用哪个运行时：`kubectl get nodes -o wide` 的 CONTAINER-RUNTIME 列、`crictl info` 的 runtimeName/版本、`systemctl status containerd`，这三个比 `docker info` 可靠。确实需要 Docker Engine 的镜像构建缓存或 `docker` 生态时，可以用 `cri-dockerd`：它自己实现 CRI，socket 默认是 `/run/cri-dockerd.sock`，kubelet 指向它，而不是指向 `/var/run/docker.sock`。

cgroup driver 也要对齐。kubelet 和运行时必须用同一个 driver（`cgroupfs` 或 `systemd`），containerd 2.x 在 `[plugins.'io.containerd.cri.v1.runtime'.containerd.runtimes.runc.options]` 里设 `SystemdCgroup = true`；cgroup v2 上官方推荐 `systemd`。两边不一致时，Pod 可能起不来，或者资源限制写到了错误的层级，表现成“限额不生效”。

镜像能跨运行时，靠的是通用的镜像格式（Docker media type 或 OCI media type）和 CRI 的 `ImageService` 解耦：构建工具、镜像仓库、运行时可以独立替换，只要它们都遵守同一份镜像格式和同一套 CRI 接口。把“Docker 构建”当成“只能 Docker 运行”，是把构建工具和运行时绑死了。下面的对照实验把这一点拆开：

## 3.5 RuntimeClass：同一集群换运行时

RuntimeClass 是一个集群级对象（non-namespaced），只有两个关键字段：`metadata.name` 是 Pod 里 `runtimeClassName` 引用的名字，`handler` 是 CRI 实现认识的运行时配置名。handler 必须是合法的 DNS label；RuntimeClass 的名字必须是合法的 DNS subdomain。节点上的 containerd 在 `/etc/containerd/config.toml` 里为每个 handler 配一段 runtime，containerd 2.x 的配置路径是 `[plugins.'io.containerd.cri.v1.runtime'.containerd.runtimes.<handler>]`，1.x 是 `[plugins.'io.containerd.grpc.v1.cri'.containerd.runtimes.<handler>]`；升级 containerd 大版本时，handler 的配置段要跟着改，否则 RuntimeClass 会突然找不到 handler。kubelet 把 Pod 的 `runtimeClassName` 解析成 handler，再通过 CRI 告诉 containerd“这个 Pod 用哪个 runtime”。不写 `runtimeClassName` 就用默认 handler。

RuntimeClass 对象本身不创建运行时，它只是名字到 handler 的映射；handler 的实现要先在节点上装好、在 containerd 里配好，RuntimeClass 才有意义。

RuntimeClass 还能带 `scheduling` 和 `overhead`。`scheduling.nodeSelector` 和 `tolerations` 在准入时与 Pod 自己的设置合并，用来把 Pod 约束到真正装了这个运行时的节点；默认假设所有节点配置一致。`overhead` 的 `podFixed` 是每个 Pod 的固定开销，准入控制器会把它写进 Pod 的 `.spec.overhead`；调度器按“容器 requests 之和 + overhead”选节点，kubelet 按这个总和设置 Pod cgroup，驱逐排序和 ResourceQuota 也会算进去。gVisor、Kata 这类运行时每个 Pod 要多占一份内存和 CPU，不写 overhead 就会低估节点容量。

`overhead` 可以算一笔账。官方 Pod Overhead 页的例子给 `kata-fc` 写 `memory: 120Mi`、`cpu: 250m`；一个容器 requests 是 `memory: 100Mi`、`cpu: 500m` 的 Pod，调度器按 `220Mi` 和 `750m` 去找节点，kubelet 也按这个总和设 Pod cgroup。准入控制器会把 overhead 写进 `.spec.overhead`，如果 Pod 清单自己已经写了这个字段，会被拒绝。容量规划里漏掉这 120Mi，节点就会在真正跑起来之后比预期更早被占满。

## 3.6 运行时排障入口

`crictl` 的第一件事是把 endpoint 指对。节点的 containerd 监听 `unix:///run/containerd/containerd.sock`；`crictl` 的 endpoint 有三种设法：命令行 `--runtime-endpoint`、环境变量 `CONTAINER_RUNTIME_ENDPOINT`、配置文件 `/etc/crictl.yaml`；配置文件默认路径可以用 `--config` 换。镜像端点可以单独用 `--image-endpoint` 或 `IMAGE_SERVICE_ENDPOINT`，不写时通常跟运行时端点相同。指错有两种典型报错：路径不存在时是 `no such file or directory`，路径存在但不是 CRI socket 时是 `connection refused`。两种都不是“容器坏了”，而是客户端没连上运行时。

`crictl info` 是运行时的总览。`defaultRuntime` 是 `runc`，`handlers` 只有 `runc` 和 `test-handler`，`runcType` 是 `io.containerd.runc.v2`。这解释了 3.5 为什么失败：Pod 要的是 `runsc`，节点上没有这个 handler。`test-handler` 是 kind 节点配置里带的，不是 gVisor；handler 名字和二进制要对上，光有一个 RuntimeClass 对象不够。

`crictl inspect` 用容器 ID，不用 Docker 的短 ID。例子里的 `state` 是 `CONTAINER_RUNNING`，`exitCode` 是 0；`crictl inspectp` 看 sandbox，`crictl inspect` 看容器，两个对象不要混。`crictl stats` 给出 CPU、内存、磁盘、inode、swap 的采样，数值每次都会变，排障时看量级和趋势，不要抄具体数字。`crictl logs --tail=3` 读的是容器 stdout/stderr，shorty 的三行 JSON 里有启动时的故障开关、内存存储警告和监听地址；它和 `docker logs` 的差别只是走 CRI，不是另一份日志。

最后两条是节点级的兜底。`systemctl status containerd` 确认 unit 是 `active (running)`，`Main PID` 指向 containerd 进程；`journalctl -u containerd` 里能看到 3.5 留下的 `RunPodSandbox ... no runtime for "runsc" is configured`。这条日志和 Pod 的 Event 是同一件事的两个视角：kubelet 看到 sandbox 创建失败，containerd 记录了自己拒绝的原因。

`nerdctl` 是另一条路。它直接对 containerd 提供 Docker 风格的命令，按 namespace 隔离：Docker 的容器在 `moby`，Kubernetes 的在 `k8s.io`。用 `nerdctl ps` 之前先确认 `--address` 和 `--namespace`，否则看到的是另一组容器，甚至以为 Pod 消失了。`nerdctl` 不是 CRI 客户端，它不能替代 `crictl` 看 sandbox 和 CRI 事件；它的价值是镜像、网络、容器文件系统这些 containerd 层面的操作更顺手。

Pod 日志的落点是节点的 `/var/log/pods`，kubelet 可以用 `podLogsDir` 改这个根目录，默认值就是 `/var/log/pods/`。目录名由 namespace、Pod 名和 UID 组成，下面再按容器分目录；`crictl logs` 读的是同一份 CRI 日志，但 Pod 被删除后 `crictl` 就找不到了，`/var/log/pods` 里的文件可能还在（取决于清理策略）。kubelet 自己的日志在 systemd 节点上用 `journalctl -u kubelet` 读；它记录的是“我请求运行时做什么、运行时返回什么”，和 containerd 的日志对起来看，才能区分是 kubelet 没发请求，还是运行时拒绝了请求。

`crictl` 和 `kubectl` 也不是同一层：`kubectl` 读写 API server 里的对象，`crictl` 读写节点上的运行时。如果 `crictl` 连上了但列表是空的，先确认它查的是 CRI 这一侧：Kubernetes 的容器在 containerd 的 `k8s.io` namespace，Docker 的在 `moby`；`crictl` 走 CRI，默认不会去列 Docker 的容器。API server 里 Pod 已经删了，节点上可能还有没清理完的 sandbox；反过来，节点上容器还在跑，API 里可能已经看不到 Pod。排障时两边都要看，不能拿一边否定另一边。节点上排障的顺序可以记成：`crictl info` 看运行时和 handler，`crictl ps -a` 看容器状态，`crictl inspect` 看退出码，`crictl logs` 看应用输出，最后才是 `systemctl`/`journalctl` 看 containerd 本身。

这个顺序不是死的，但大方向是先确认“客户端连上了”，再确认“运行时里有对象”，最后才看“应用为什么退出”。脚本里不要写死一个 endpoint：节点换 socket 或换运行时，先看 `/etc/crictl.yaml`，再用 `--runtime-endpoint` 临时覆盖。反过来先翻应用日志，很容易在 endpoint 写错时白找半天。

## 3.7 排障：容器停了，runc 里还剩什么

一个常见的预期是：`docker stop` 之后 `runc list` 里那条记录会变成 `stopped`。实际跑一遍会发现不是这样。下面的例子先起一个 Docker 容器，看 `runc list`；再停掉它，看同一个列表；最后用 CRI 起一个以退出码 7 结束的 Pod，从节点上读退出码。

```console
{{#include code/ch03/3_7_runtime_troubleshooting.out}}
```

`docker ps` 里有 `ch03-stop` 和 `shorty-control-plane` 两个容器；`runc list` 里也有两条 `running`，ID 和 `docker ps` 的前 12 位对得上。也就是说，Docker 的每个容器在 runc 里都有一条 task 记录，kind 节点容器也不例外。`runc list` 不是“容器清单”，它列的是 runc 这个 runtime 管理的 task。

`docker stop --timeout 1` 返回后，`runc list` 只剩 `shorty-control-plane` 那一条，`ch03-stop` 消失了，不是变成 `stopped`。原因是 shim 在容器退出后把 runc 的 task 删掉了：runc 只负责把进程启动起来，进程死了它就收尾；Docker 的容器记录还在，所以 `docker ps -a` 仍能看到 `ch03-stop`，状态是 `Exited (137)`，`docker inspect` 的 `.State.ExitCode` 也是 137。137 是 128+9，表示 `--timeout 1` 到点后发了 SIGKILL；不加 `--timeout` 时 Docker 默认等 10 秒，shorty 的 5 秒优雅退出有机会跑完，退出码可能是 0。这里用 1 秒是为了让输出稳定，不是让你在生产里缩短超时。

`stopped` 这个状态在哪里能看到？3.2 里手工 `runc kill` 之后、`runc delete` 之前，`runc state` 明确返回 `status: stopped`、`pid: 0`。区别在于那个容器是 runc 自己创建的，runc 保留它的 state 文件；Docker 的容器由 shim 管理，shim 在退出时就把 task 删了。**所以“停没停”不要用 `runc list` 判断，用 `docker ps -a` 或 `crictl ps -a`。**

CRI 这一侧的例子更能说明退出码从哪来。`pod-exit.yaml` 里的 busybox 执行 `exit 7`，`restartPolicy: Never`，Pod 最终是 `Error`。`kubectl get pod -o jsonpath` 从 `.status.containerStatuses[0].state.terminated.exitCode` 读到 7；节点上 `crictl ps -a` 看到容器 `Exited`，`crictl inspect` 的 `.status.exitCode` 也是 7。这两个数字来自同一份 CRI 状态：kubelet 把容器的退出码写进 Pod status，`crictl` 从 containerd 读原始状态。

`systemctl is-active containerd` 返回 `active`，`journalctl -u containerd` 的最后几行是 shim 清理、sandbox 退出和网络拆除。注意日志里的 `exit_status:137` 是 pause sandbox 的退出状态，不是业务容器的 7；业务退出码在 `crictl inspect` 和 Pod 的 `containerStatuses` 里。读 containerd 日志要和对象对上，不能看到一个数字就当成应用退出码。

退出码的读法可以再细一层：`0` 是正常退出，`1` 是应用自己报错，`126`/`127` 常见于命令不可执行或找不到，`137` 是 SIGKILL，`143` 是 SIGTERM。`OOMKilled` 不是退出码，它在 `terminated.reason` 里；看到 137 时要先分清是 `docker stop` 超时、节点驱逐，还是 cgroup 内存限制。

排障时可以按这个顺序走：

- `crictl` 报 `connection refused` 或 `no such file`：先确认 endpoint 写的是节点上的 containerd socket，再 `systemctl status containerd`、`journalctl -u containerd` 看服务是否在跑。3.6 的两种错误已经覆盖了路径写错和指到非 CRI socket 两种情况。
- `crictl ps` 里没有业务容器：不要只查 Docker。先 `kubectl get pod -o wide` 和 `kubectl describe pod` 看 Pod 是否被调度、sandbox 是否创建；再看 `crictl pods` 和 `crictl ps -a`，最后看 kubelet 日志（`journalctl -u kubelet`）和 Pod 的 `containerStatuses`。
- 容器在 `crictl ps -a` 里是 `Exited`：用 `crictl inspect` 读 `exitCode`，用 `crictl logs` 读应用输出；如果是 `OOMKilled` 或节点驱逐，再去看 cgroup 和节点事件。
- 节点上还有 Docker：`docker ps` 只说明 Docker 自己的容器在不在，不能说明 kubelet 的 Pod 在不在；两者是两个 daemon、两个 namespace。

## 上生产前

**节点只装一种 CRI 运行时。** containerd、CRI-O、cri-dockerd 选一个，让 kubelet 的 `--container-runtime-endpoint` 只指向它。不要在同一节点上既让 kubelet 用 containerd，又用 Docker Engine 跑业务容器：kubelet 不知道 Docker 里的容器，调度、资源账本、重启策略、日志收集都不覆盖它们；两套镜像存储还会各占一份磁盘。节点上保留 Docker CLI 只用于调试可以，但不能把它当成 Pod 的运行时。

**固定版本，升级前做 skew 检查。** 节点运行时和 kubelet 的接口是 CRI，`crictl info` 能看出运行时名称、版本、默认 handler 和已配置的 handler，`kubelet --version` 看 kubelet 版本。Kubernetes 1.26 起只支持 CRI `v1`；containerd 1.x 不支持 `RuntimeConfig` RPC，官方文档说 Kubernetes 1.38 会去掉对旧 containerd 的回退。升级顺序、运行时大版本和 kubelet 的兼容窗口要在预发验证，不能在生产节点上直接换。

**RuntimeClass 的 overhead 要进容量规划。** 只要用了 gVisor、Kata 或任何每个 Pod 有固定开销的运行时，就在 RuntimeClass 里写 `overhead.podFixed`，让调度器、Pod cgroup、驱逐和 ResourceQuota 都算上这份开销。gVisor/Kata 的兼容性和启动延迟要在预发用真实业务跑一遍：系统调用、GPU、特权操作、内核参数这些能力，不同的运行时支持程度不一样。异构节点用 `scheduling.nodeSelector` 把 Pod 约束到装了对应 handler 的节点，不要让 Pod 落到没有 handler 的节点上再失败。

**排障用 `crictl`/`nerdctl`，日志认 `/var/log/pods`。** 节点上不要依赖 `docker ps`：它只显示 Docker 自己的容器。看 Pod 的 sandbox 用 `crictl pods`，看容器用 `crictl ps -a`，看退出码用 `crictl inspect`，看应用输出用 `crictl logs`；更底层的 containerd 操作用 `nerdctl`，但要先选对 `--address` 和 `--namespace`。Pod 日志的默认落点是 `/var/log/pods`，`crictl logs` 和它读的是同一份 CRI 日志；Pod 删除后 `crictl` 找不到，文件可能还在，采集和排查要以节点上的目录为准。

| `runc run` / `runc create` + `start` | 前台运行 / 分离创建再启动 | `create` 后状态 `created`，`start` 后 `running` |
| `crictl info` | 运行时的默认 handler、handler 列表、runtimeType | 端点默认从 `/etc/crictl.yaml` 读 |
| `crictl pods` / `crictl inspectp` | 看 Pod sandbox（pause） | sandbox 不是 `crictl ps` 里的容器 |
| `crictl ps -a` / `crictl inspect` | 看容器状态和退出码 | `ps -a` 只显示 `Exited`，退出码在 `inspect` 的 `.status.exitCode` |
| `crictl logs` / `crictl stats` | 读容器日志 / 采样资源 | 日志落点默认 `/var/log/pods`；stats 数值随时间变 |
| CRI socket | containerd 的 CRI 端点 | Linux 默认 `unix:///run/containerd/containerd.sock` |
| `--container-runtime-endpoint` | kubelet 指向运行时 | kubelet 参考页给 containerd 的默认值同上 |
| `runtimeClassName` / `handler` | Pod 选 RuntimeClass，RuntimeClass 选 CRI handler | handler 必须在节点 containerd 配置里存在 |
| `overhead.podFixed` | 每个 Pod 的固定开销 | 计入调度、Pod cgroup、驱逐和 ResourceQuota |

本章结束时，lab 本地仍有 `shorty:0.1` 和 `busybox:1.37`，没有运行中的容器，也没有 kind 集群；下一章用 `shorty:0.1` 讲容器从启动到退出的完整生命周期。
