# 第 10 章 BuildKit：多阶段、缓存挂载、secret、多架构

第 9 章结束时，`shorty:dev` 能构建，`shorty-api` 也能跑，但每次换一台 CI 机器，`RUN go mod download` 都要把依赖重新下载一遍。镜像层缓存留在上一台机器的 Docker 里，新机器没有。更麻烦的是私有依赖：构建要读公司制品库的 token，token 一旦进了 `ARG` 或 `ENV`，就会留在 `docker history` 和镜像层里，镜像推到哪里，凭据就跟到哪里。

这一章把构建从“本机能跑”推到“换机器也能快、凭据不落地、能出两个架构”。BuildKit 是 Docker 的构建后端，buildx 是操作它的 CLI；先把默认 builder 和独立 builder 分清，再用同一个 Dockerfile 的 `build`、`dev`、`runtime` 三个阶段把开发镜像和生产镜像分开。接着把 Go 的模块缓存、编译缓存和 Python 的 pip 缓存挂进 `RUN`，让它们留在 builder 而不是镜像层里；用 `--mount=type=secret` 把 token 限制在一条 `RUN` 的生命周期内；最后用交叉编译一次产出 amd64 和 arm64 的 manifest list，并用 registry cache 让另一台机器也能命中。

本章的 lab 是 Docker Engine 29.9.2、buildx 0.38.1，`docker-container` builder 里的 BuildKit 是 v0.33.1。lab 里没有注册任何 binfmt/QEMU 处理器，所以多架构部分走交叉编译，不依赖模拟。

> **起点**：第 9 章结束时有单阶段的 `shorty:dev` 和运行中的 `shorty-api`。本章的 `setup.sh` 会删掉旧的 `shorty-api`，拉好 Go、Python、alpine、redis 和 registry 镜像，并在 8080 端口起一个只认 token 的私有制品库；`shorty:0.1` 和 `shorty-worker:0.1` 在本章重新构建。在 lab 里执行 `bash code/ch10/setup.sh`，然后从 10.1 开始建 builder。

## 10.1 BuildKit/buildx 的默认行为

Docker Engine 23.0 的发布说明里有一条：在 Linux 上把 Buildx 和 BuildKit 设为默认构建器，`docker build` 成为 `docker buildx build` 的别名，旧构建器只能用 `DOCKER_BUILDKIT=0` 显式打开。所以今天不需要再设 `DOCKER_BUILDKIT=1`；需要确认的是“现在用的是哪个 builder”。

BuildKit 的内核是一张 LLB（Low-Level Build）依赖图。每条 `FROM`、`COPY`、`RUN` 都是图上的一个节点，节点之间用内容校验和连起来；缓存不是靠比较镜像历史猜出来的，而是直接看这张图的校验和。好处是判断更准，而且这张图可以导出到 registry，换一台机器再导入。10.6 的 registry cache 就是把这个能力用在 CI 上；本章前面的 cache mount 则是另一套机制，作用在单个 builder 的目录上，两者不要混为一谈。BuildKit 官方页面把 builder 定义为运行构建的 BuildKit daemon：默认 builder 用 `docker` 驱动，BuildKit 库直接编在 dockerd 里；`docker-container` 驱动则另起一个 BuildKit 容器，能配置、能导出缓存、能构建多架构。

第一条 `docker buildx ls` 只有 `default*`，驱动是 `docker`，BuildKit 版本 v0.34.0，平台列是 `linux/amd64 (+4)`。星号表示当前选中的 builder。`(+4)` 是 buildx 对平台列表的缩写，完整列表要用 `docker buildx inspect` 看；这里只需要知道默认 builder 跟着 dockerd 走，平台就是本机平台。

`docker buildx create --name ch10 --driver docker-container --driver-opt network=host --use` 建了一个独立 builder，`--use` 把它设为当前选中。为什么不直接用 default builder？`docker` 驱动的 builder 和 dockerd 绑在一起，缓存导出选项不全，也不能改 BuildKit 配置；`docker-container` 驱动把 daemon 放进独立容器，缓存导出、多架构、BuildKit 配置都完整。代价是多一个容器要管，构建结果也不会自动 load。`inspect --bootstrap` 会先把 builder 容器拉起来：第一次要拉 `moby/buildkit:buildx-stable-1`，输出里 `#1 pulling image` 和 `#1 creating container buildx_buildkit_ch100` 就是这一步。之后看到 `Driver: docker-container`、`Status: running`、`BuildKit version: v0.33.1`，以及 `Driver Options: network="host"`。BuildKit 版本和 buildx 版本不是一个东西：buildx 0.38.1 是客户端，v0.33.1 是 builder 里跑的 daemon。

`network=host` 是为了让 builder 容器和构建步骤都能用 lab 的 `localhost`。本章后面要把镜像推到 `localhost:5000` 的 registry，构建时还要访问 `localhost:8080` 的制品库；`docker-container` builder 默认在自己的网络里，`localhost` 指的是 builder 容器自己，不是 lab。加上 host 网络后，builder 自己推 registry、`RUN` 里访问制品库，都走同一套地址。代价是 builder 和宿主机共享网络，生产上要按团队的网络策略决定，不能无脑照抄。

`inspect` 的 `Platforms` 只列出 builder 能直接执行的平台：`linux/amd64` 和它的几个变体，没有 `linux/arm64`。这不等于它不能构建 arm64；10.5 会用交叉编译在 amd64 上产出 arm64 二进制。真正需要目标平台执行 `RUN` 时，才需要 QEMU 或原生节点。`buildx ls` 的最后一段显示 `ch10*` 和 `default` 两个 builder，`ch10` 在前并带星号。`docker build` 和 `docker buildx build` 在这里有一个容易踩的差别：`docker build` 为了兼容旧脚本，默认仍然找 dockerd 自带的 default builder，不会自动用你 `--use` 选中的 builder；要用非默认 builder，得写 `docker build --builder ch10` 或设 `BUILDX_BUILDER=ch10`。本章统一用 `docker buildx build`，它读的是当前选中的 builder。

builder 的缓存是跟着 builder 走的。切回 `default` 时，`ch10` 里那些层和 cache mount 都还在磁盘上，但这次构建不会用它们；这也是为什么 CI 要固定 builder 的名字，不能每次随机建一个。`docker-container` 驱动不会像 `docker` 驱动那样自动把结果装回本地镜像库。`docker buildx build` 默认只把结果留在 builder 的缓存里；要拿回本地，加 `--load`；要推到 registry，加 `--push`。这就是后面每条构建命令都带 `--load` 或 `--push` 的原因。排障时用 `--progress=plain` 看完整步骤，buildx 的 `--debug` 打开客户端的调试日志；如果连 BuildKit daemon 的 debug 日志也要，需要在 builder 配置里开 `debug = true`，那是另一层。

> **旧资料提示**：旧教程里“用 BuildKit 要先 `export DOCKER_BUILDKIT=1`”只适用于 Docker Engine 23.0 之前。23.0 起 Linux 上默认就是 Buildx/BuildKit；反过来，要临时回到旧构建器才写 `DOCKER_BUILDKIT=0`（依据 `docker:manuals/engine/release-notes/23.0.md`）。

```dockerfile

```

一个阶段不是容器里的一个目录，而是一串指令执行完之后的文件系统快照。`FROM ... AS build` 给这个快照起名，后面的 `FROM build AS dev` 从它继续，`COPY --from=build` 则建立一条从 build 到 runtime 的依赖边：只把指定路径复制过去，其余内容不跟着走。BuildKit 构建的是这些阶段组成的图，目标阶段没有依赖到的分支会被整段跳过。

`FROM --platform=$BUILDPLATFORM golang:1.27.3-trixie AS build` 把构建阶段固定在 builder 自己的平台上。单平台构建时 `$BUILDPLATFORM` 就是 `linux/amd64`；10.5 做多架构时，这个写法让编译在 amd64 上跑，不会为了 arm64 去模拟整条 Go 工具链。`ARG TARGETOS` 和 `ARG TARGETARCH` 是 BuildKit 预定义的构建参数，值为目标平台；`go build` 用它们设置 `GOOS` 和 `GOARCH`。`ARG VERSION=0.1` 是应用自己的版本号，默认 0.1，构建时可以用 `--build-arg` 覆盖。

两个 `RUN --mount=type=cache` 先埋个伏笔：`/go/pkg/mod` 放模块，`/root/.cache/go-build` 放编译缓存。它们挂在 `RUN` 上，不会成为镜像层；10.3 专门验证这一点。

`FROM build AS dev` 从构建阶段接着走，所以 dev 里已经有 Go 工具链、shell、源码和编译产物。它只多了一条 `WORKDIR /src` 和 `CMD ["bash"]`。`FROM scratch AS runtime` 从空文件系统开始，只 `COPY --from=build /out/shorty /shorty`，然后设数字 UID 65532 和入口。默认构建的是最后一个阶段 runtime；要 dev 就显式 `--target dev`。

第一段构建用了 `--target dev`，`tail` 留下的最后几行是 `[build 4/6] RUN go mod download`、`[build 6/6] RUN ... go build`、`[dev 1/1] WORKDIR /src`，然后直接导出。runtime 阶段的 `COPY --from=build` 根本没有出现，因为 dev 不依赖 runtime，BuildKit 把它整段跳过了。旧构建器会把 `--target` 之前的每个阶段都走一遍，BuildKit 只走目标阶段依赖的子图，这是官方多阶段页面明确列出的差别。同一份 Dockerfile 里如果还有一个独立的 `test` 阶段，构建 runtime 时它会被跳过；只有显式 `--target test` 才会跑测试。

第二段构建不写 `--target`，目标是最后一个阶段 runtime。输出里 `[build 4/6] RUN ... go mod download` 和 `[build 6/6] RUN ... go build` 都是 `CACHED`，只有 `[runtime 1/1] COPY --from=build` 是新执行的，因为它要把二进制放进一个新的 scratch 根文件系统。`docker image inspect` 把差别量化了：dev 的 `layers=13`、`size` 约 1.32 GB；runtime 的 `layers=1`、`size` 约 17.7 MB。`size` 是解压后所有层的总和，不是压缩后的传输大小；但量级差别已经足够说明问题。

dev 的 13 层主要来自 `golang:1.27.3-trixie` 的基础层、`COPY` 和 `RUN`；runtime 的 1 层只有 `COPY --from=build` 写进去的二进制。`docker run --rm shorty:dev-ch10 sh -c 'go version; ls /src'` 输出 `go version go1.27.3 linux/amd64` 和九个源码文件，说明 dev 里确实有完整的开发环境。`docker run --rm shorty:0.1 version` 输出 `shorty 0.1`，这个 0.1 来自 Dockerfile 的 `ARG VERSION=0.1`，构建时没有覆盖；`--build-arg VERSION=0.2` 会把它改掉。而 `--entrypoint sh` 直接报 `exec: "sh": executable file not found in $PATH`，因为 scratch 里没有 shell，也没有 libc 和包管理器。生产镜像不需要这些，调试时才需要，所以把调试工具留在 dev 阶段。

`COPY --from` 也可以从外部镜像取文件，例如 `COPY --from=nginx:1.29-alpine /etc/nginx/nginx.conf /nginx.conf`；这时 BuildKit 会先拉那个镜像，只取指定路径，不会把整个 nginx 镜像并进最终镜像。

`COPY --from=build` 只复制 `/out/shorty` 一个文件，构建阶段的 Go 工具链、模块缓存、源码都留在 build 阶段，不会进入 runtime。这也是为什么 `--target dev` 和默认 runtime 能共用一份 Dockerfile：两者的差异只在最后一个阶段，前面的编译步骤完全相同，BuildKit 还可以复用同一份 build 缓存。构建上下文也只传变化的文件：第一次传完整上下文，第二次只剩很小的增量；`.dockerignore` 排掉的测试文件和 `.git` 从来不在传输集合里。要注意 `--from` 只认阶段名或镜像名，不认容器里的任意路径；如果构建产物被写在 cache mount 里，它不会被 `COPY --from` 带出来，因为 mount 的内容不属于阶段文件系统。

> **旧资料提示**：多阶段构建在今天不是“高级技巧”，官方把它放在 Build 的基础路径里，和 `--target`、`COPY --from`、BuildKit 跳过无关阶段一起讲。把“一个 Dockerfile 同时产出开发镜像和生产镜像”当默认做法，比维护两份 Dockerfile 更不容易漂移。

> **旧资料提示**：旧教程里常见先 `COPY` 再 `RUN chown -R`。从 Docker 17.09 起 `COPY --chown=65532:65532 源 目标` 可以直接改复制层的属主，少一层，也不用把整个目录再写一遍。

## 10.3 缓存挂载：依赖不进入层

镜像层缓存解决的是“同一个 builder 上，输入没变就不重跑”。CI 换机器时，新 builder 没有这些层，`RUN go mod download` 照样要联网。缓存挂载解决的是另一个问题：把一个目录持久化在 builder 里，`RUN` 每次执行都能读写它，但它不属于镜像层。依赖下载一次，后面即使 `RUN` 因为参数或源码变化而重跑，也只下载新增或变化的包。

第一次构建 `cached module zips before: 0`，`after: 10`，整条 `RUN` 是秒级。第二次把 `CACHE_BUST` 改成 2，`RUN echo` 和后面的步骤都重新执行，但 `before` 已经是 10，整条 `RUN` 只用了 0.1 秒，`after` 还是 10；`go build` 从接近十秒降到不到一秒，`[runtime 1/1]` 直接 `CACHED`。这不是层缓存命中，因为 `RUN` 确实执行了；命中是 mount 里的内容。

第三次加 `--no-cache`，`before` 又回到 0，`go mod download` 重新下载了一遍。这一点和很多人的直觉相反：`--no-cache` 不仅让层缓存失效，连 cache mount 也不复用，依赖会重新下载。但第四次不加 `--no-cache`、只把 `CACHE_BUST` 改成 4，`before` 又回到 10，说明 `--no-cache` 只是这次构建不用缓存，并没有把磁盘上的目录删掉。要清掉 builder 磁盘上的缓存用 `docker buildx prune`，它删的是 builder 的缓存记录。`docker image inspect` 显示 `image layers=1`，说明 10 个模块 zip 和 Go 编译缓存都没有进镜像；`docker buildx du` 的 `Total` 约 2.1GB，是 builder 的缓存总量，包含基础镜像层、模块和编译结果，不在 `shorty:cachetest` 里。

cache mount 和 bind mount 的区别也要分清：bind mount 默认只读，`RUN` 对它的写入在指令结束后丢弃；cache mount 可读写，内容跨构建保留在 builder 里。前者适合把源码临时挂进去编译，后者适合包管理器缓存。两者都不写进镜像层，但只有 cache mount 会在下一次构建时还在。

Python 的写法一样，只是路径不同：`RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt`。本章的 `worker.Dockerfile` 用了 `id=shorty-pip`，10.6 的 bake 输出里能看到 pip 在下载 wheel，第二次构建就会复用这个目录。其他包管理器同理，Go 用 `/go/pkg/mod` 和 `/root/.cache/go-build`，npm 用 `/root/.npm`，apt 用 `/var/cache/apt` 和 `/var/lib/apt`。

cache mount 的目录在构建结束后不会随容器删除；它由 builder 管理，`docker buildx du` 统计的就是这些目录加上层缓存。`--no-cache` 让这次构建不使用它们，但不会删除磁盘上的内容；`docker buildx prune` 才会真正回收。两者解决的是不同问题：前者是“这次不要用”，后者是“把旧的清掉”。

`sharing=locked` 是并发场景的开关。多个构建同时写同一个 cache mount 时，`sharing=locked` 让它们排队，避免两个进程同时改同一批文件；官方 apt 示例对 `/var/cache/apt` 和 `/var/lib/apt` 都加了 `sharing=locked`，因为 apt 需要独占访问。Go 的模块缓存和编译缓存一般可以共享，本章没有加锁；如果 CI 会在同一个 builder 上并行跑多个构建，按工具的并发安全性决定。

`id=` 的作用是给缓存分命名空间。不同项目如果复用同一个 id，缓存会混在一起；本章给 Go 模块、Go 编译、pip 各用一个 id，读者可以按项目名或工具名替换。缓存挂载只在本地 builder 上有效，换机器就没了；要让另一台机器也命中，得靠 10.6 的外部缓存后端。

## 10.4 构建 secret：token 不进层

私有依赖的 token 不能用 `ARG` 或 `ENV` 传。官方 secrets 页面把原因写得很直接：构建参数和环境变量会留在最终镜像里；`ARG` 不进容器的 `Config.Env`，但会出现在 `docker history` 的 `ARG` 和 `RUN` 记录里；`ENV` 更是直接写进镜像配置。secret mount 则是把 secret 从构建客户端临时挂进构建容器，只在一条 `RUN` 期间可见，不写进镜像。

先用一个错误的 token 构建，`curl` 得到 `401`，构建失败。这说明制品库真的在校验，不是把 token 当装饰。换成 `/tmp/ch10-token` 后，`[build 5/5]` 的 `RUN` 约两秒完成，镜像导出成功；`docker run --rm shorty:secret` 输出 `private module loaded from the artifact server`，说明私有模块确实被编译进去了。

`docker history --no-trunc shorty:secret` 的输出只剩四条：`ENTRYPOINT`、`COPY`、`CMD`、`ADD`，`RUN` 这一步没有记录，其余层的 ID 是 `<missing>`。所以 history 只能算一半证据：再用 `grep -F "$TOKEN"` 搜，输出 `history: token not found`；在镜像里搜 `/secretapp /etc /usr /bin /sbin /root /tmp`，输出 `image: token not found`。最后一条搜索把 `/secretapp` 也包含进去了，二进制里没有 token；构建阶段下载的 tar.gz 和解压出来的源码只存在于 build 阶段，runtime 阶段只 `COPY` 了二进制。

secret 的生命周期只覆盖挂载它的那条 `RUN`。`RUN` 结束时，挂载点从构建容器里消失，BuildKit 也不会把它算进这一层的 diff；但如果 `RUN` 自己把值写进文件、写进数据库或拼进 URL，那就是应用代码在泄露，secret mount 管不了。

secret 不是“构建完就自动销毁”的魔法。它只在 `RUN` 期间挂载，`RUN` 结束后挂载点消失；但如果 `RUN` 把 token 写进文件、提交到镜像层，或者把带 token 的 URL 写进 `/root/.gitconfig`，那还是会留下。构建完成后要立即撤销临时 token，尤其是在 token 有写权限或长期有效时；示例里的 token 是假的，真实环境要按“已经泄露”处理，轮换后再重建。

secret 的 `id` 只是构建客户端和 Dockerfile 之间的名字，不是权限系统。任何能改 Dockerfile 的人都能把 `cat /run/secrets/git_token` 加进 `RUN`，所以 secret 的权限要按“构建脚本可信”来设计，CI 里还要限制谁能改构建配置。

私有 Git 仓库还有两种用法：`--mount=type=ssh` 把 SSH agent 或 key 挂进构建，适合 `git clone`；远程 Git 上下文和 `ADD` 拉私有仓库可以用预定义的 `GIT_AUTH_TOKEN`/`GIT_AUTH_HEADER` secret。它们和 `--mount=type=secret` 是同一套“构建客户端提供、构建容器临时使用”的模型，不要把 token 写进 Dockerfile 或 `.netrc` 再 `COPY` 进去。

## 10.5 多架构构建

多平台镜像的结构和单平台不一样：单平台是一个 manifest 指向一份 config 和一组层；多平台是一个 manifest list（OCI 里叫 image index），指向多个 manifest，每个 manifest 对应一个平台。推 registry 时，registry 保存 manifest list 和各个 manifest；拉取时 Docker 按本机架构选对应的那个。Docker Engine 29.0 起新安装默认用 containerd 镜像存储，原生支持 manifest list，不需要额外配置。

`shorty.Dockerfile` 的构建阶段用 `FROM --platform=$BUILDPLATFORM` 固定在 builder 平台，`ARG TARGETOS/TARGETARCH` 接收目标平台，`GOOS/GOARCH` 交给 Go 编译器。这样 amd64 和 arm64 的二进制都在 amd64 上编译出来，不需要 QEMU。构建输出里的 `[linux/amd64->arm64 build ...]` 就是这个意思：构建阶段跑在 amd64，产物给 arm64。

```console

```

`--platform` 可以只写一个平台做本地验证，也可以写多个平台做发布；多平台时 BuildKit 为每个平台各算一条构建链。`--platform linux/amd64,linux/arm64` 让 BuildKit 为两个平台各算一条构建链。`tail` 里能看到 `[linux/amd64 build 6/6]` 用 `GOARCH=amd64`，`[linux/amd64->arm64 build 6/6]` 用 `GOARCH=arm64`；最后 `#18 exporting manifest list sha256:...`，`pushing manifest for localhost:5000/shorty:0.1@sha256:...`。registry 里存的是 index，不是单个镜像。`--push` 时 BuildKit 先把两个平台的层推上去，再推各自的 manifest，最后推 index；任何一步失败，index 都不会指向不完整的平台。

`docker image ls localhost:5000/shorty` 是空的，因为 `--push` 只推 registry，不装回本地。`docker buildx imagetools inspect localhost:5000/shorty:0.1` 显示 `MediaType: application/vnd.oci.image.index.v1+json`，下面两个 `Manifests`：一个 `Platform: linux/amd64`，一个 `Platform: linux/arm64`，各自有自己的 digest。`docker run --rm --platform linux/amd64 localhost:5000/shorty:0.1 version` 会先从 registry 拉 manifest list，选中 amd64，再拉对应的层，输出 `shorty 0.1`；输出里的 `Digest: sha256:...` 是 manifest list 的 digest，不是某个平台的 digest。

`--load` 的行为要按镜像存储区分。本章的 Docker 29.9.2 用 containerd 镜像存储，`--load` 能把两个平台一起装进本地镜像库，`docker image ls shorty` 里 `shorty:multi` 的 `DISK USAGE` 是 22 MB，比单平台的 17.7 MB 大，因为装了两份 manifest 和两份层。在只支持单平台 manifest 的镜像存储上，`--load` 装不回两个平台，只能 `--push` 到 registry，或者换成 containerd 镜像存储。官方多平台页面把“需要支持 manifest list 的镜像存储”写在 Prerequisites 里，Docker Desktop 和 Engine 29.0+ 默认满足。

除了 QEMU，还可以给 builder 追加多个原生节点：`docker buildx create --append --name ch10 node-arm64`，让 arm64 的构建落到 arm64 机器上。Docker Build Cloud 也是这个思路，只是节点由服务方管。多原生节点比 QEMU 快，但要多维护几台构建机。

`imagetools inspect` 里的 `Digest` 是 manifest list 的 digest，下面两个 `Name` 是各平台 manifest 的 digest；拉取时 Docker 先拿 list，再按本机 `GOARCH` 选其中一个。部署时如果要固定到某个平台，可以用 `image@sha256:<平台 manifest 的 digest>`，而不是 list 的 digest。

QEMU 是可选的另一条路。BuildKit 官方发布版自带 QEMU 用户态模拟器，`RUN` 里执行目标架构的二进制时会自动用；如果没有，可以 `docker run --privileged --rm tonistiigi/binfmt --install all` 注册 binfmt，然后用 `cat /proc/sys/fs/binfmt_misc/qemu-*` 看 flags 里有没有 `F`。本章的 lab 里 `ls /proc/sys/fs/binfmt_misc` 是空的，所以不能用模拟；交叉编译照样能产出两个平台的镜像，而且构建时间更短。不能交叉编译的语言（比如某些 C 扩展）才需要 QEMU 或原生 arm64 节点；QEMU 的代价是编译和压缩这类计算密集步骤会慢很多，官方页面明确建议能用交叉编译或多原生节点就不要全量模拟。

多架构发布前用 `imagetools inspect` 确认每个平台的 manifest 都在，再用 `docker run --platform` 在对应平台上跑一次。`--load` 只解决本地镜像库，不能代替 `--push`；registry 里的 manifest list 才是别人拉得到的东西。

第一次构建末尾的 `writing cache image manifest sha256:...` 是缓存镜像写进 registry 的证据。然后 `docker buildx prune -af --builder ch10` 清掉本地缓存，它回收了约 2.6 GB；`docker buildx du` 从 GB 级降到十几 MB，剩下的主要是缓存记录元数据，不是可复用的层。再构建时，输出第一行就是 `#6 importing cache manifest from localhost:5000/shorty:buildcache`，接着 `#9` 到 `#14` 全是 `CACHED`，`sending tarball` 只花 0.1 秒。本地已经没有层了，这些层是从 registry 的缓存镜像里导回来的。

`--cache-from` 可以写多次，按顺序尝试多个缓存来源；主分支和当前分支各一个 cache tag 是常见做法。缓存后端不是“命中一次就永远命中”。缓存的键仍然包含基础镜像 digest、`COPY` 的文件校验和、`RUN` 的命令字符串；基础镜像更新、`go.mod` 变了、Dockerfile 改了，对应层还是会失效。registry cache 只是把这些层搬到另一台机器，不改变缓存失效的规则。

构建成功，但末尾有一条警告：`SecretsUsedInArgOrEnv: Do not use ARG or ENV instructions for sensitive data (ARG "TOKEN")`。这是 BuildKit 构建时自动跑的检查，不需要 `--check`；它只提醒，不阻止构建。`docker history --no-trunc` 里能看到 `RUN |1 TOKEN=<redacted> /bin/sh -c echo "$TOKEN" > /token.txt` 和 `ARG TOKEN=<redacted>`。`<redacted>` 是示例命令用 `sed` 替换的，实际值就在那个位置；`docker run` 里 `/token.txt` 有 23 字节，`grep` 也能直接在 `/token.txt` 找到 token。

定位方法就是这两步：`docker history --no-trunc` 看每条记录的 `CreatedBy`，再用 `docker run --rm image sh -c 'grep -r TOKEN /'` 在文件系统里搜。BuildKit 下有些层的 ID 会显示 `<missing>`，但 `CreatedBy` 的文本通常还在；如果 history 被压缩得看不出来，可以把镜像 `docker save` 成 tar，逐层解开再搜。搜文件系统时用 `find / -path /proc -prune -o -path /sys -prune -o -type f -print` 之类的写法避开虚拟目录，再对结果 `grep`，比直接 `grep -r /` 稳。搜的时候要限定目录或排除 `/proc`、`/sys`、`/dev`，否则会扫到虚拟文件系统；本章的例子只搜 `/token.txt`，因为已经知道泄露点。真实镜像里可以从 `/app`、`/etc`、`/root`、`/tmp` 这些常见位置开始，再扩大范围。

`--check` 能提前抓 `SecretsUsedInArgOrEnv`，把它放进 CI 是低成本的兜底，但它只认已知的模式；自定义脚本里 `curl -H "Authorization: $TOKEN"` 这种写法它未必能判断，所以它不能替代人工审计和轮换流程。

修复用 `fixed.Dockerfile`：`RUN --mount=type=secret,id=git_token,target=/run/secrets/git_token` 读 token，只写一句 `secret read, not written` 到 `/status.txt`。构建后 `docker history` 里搜不到 token，镜像里也搜不到；`docker run --rm shorty:fixed` 输出 `secret read, not written`。这并不能“洗掉”旧镜像：旧的 `shorty:leak` 层还在本地，推过 registry 的话还在 registry，必须删掉旧镜像、轮换 token，再重新构建。改 Dockerfile 只是让下一次构建不再泄露，已经泄露的凭据要按泄露处理：先撤销或轮换 token，再删掉带旧层的本地镜像和 registry 里的旧 tag，最后用新 token 重建。只改 Dockerfile 而不轮换，旧 token 仍然有效，旧镜像也仍然能被拉下来。

第二个故障是 `exec format error`。本章的 lab 是 x86_64，`/proc/sys/fs/binfmt_misc` 里注册的处理器数量是 0。用 `--platform linux/arm64` 跑 10.5 推上去的镜像，Docker 会正确地拉 arm64 manifest 和层，但内核执行 `/shorty` 时发现它是 aarch64 二进制，直接报 `exec /shorty: exec format error`。

同一张 manifest list，换成 `--platform linux/amd64` 就输出 `shorty 0.1`。内核在 `execve` 时读 ELF 头，发现机器类型不是 x86-64，就返回 `ENOEXEC`，Docker 把它显示成 `exec format error`；这跟镜像层有没有拉全无关。`--platform` 只负责选 manifest，不负责模拟；要模拟就装 binfmt/QEMU，要原生就跑在 arm64 节点上，要避免模拟就用 10.5 的交叉编译。检查 binfmt 时看 `/proc/sys/fs/binfmt_misc/qemu-arm64` 的 flags 里有没有 `F`；如果目录里没有 `qemu-*`，就是没注册。`docker buildx imagetools inspect` 能确认 arm64 manifest 在不在；manifest 在、运行报 `exec format error`，先查 binfmt，再查镜像里是不是错放了别的架构的二进制。

`exec format error` 也可能发生在构建阶段：如果 Dockerfile 没有 `--platform=$BUILDPLATFORM`，BuildKit 会尝试在目标平台执行 `RUN`，没有模拟时同样报这个错。先看错误发生在 `RUN` 还是 `docker run`，再决定是改交叉编译还是装 binfmt。

## 上生产前

- CI 用独立 builder 加 registry cache，不要每次从零构建。builder 的生命周期可以很短，但 `--cache-to/--cache-from type=registry` 要指向一个持久的缓存仓库；缓存 key 仍然绑定基础镜像 digest、`go.mod`/`requirements.txt` 和 Dockerfile，基础镜像升级后该失效就让它失效，不要为了命中率把依赖版本钉死在旧版本上。
- 构建 secret 一律用 `--mount=type=secret`，构建结束立即撤销临时 token。不要把长期 token 放进 CI 变量再用 `ARG` 传；`ARG` 的值会进 `docker history`，`ENV` 会进镜像配置，两者都不能当 secret 用。secret 只保证“不在镜像里”，不保证“构建日志里没有”；`RUN` 里不要 `echo` 它。
- 多架构发布前用 `docker buildx imagetools inspect` 验证每个平台的 manifest，再在对应平台上跑一次。`--load` 只影响本地镜像库，不能代替 `--push`；Docker 29 的 containerd 存储能把 manifest list 装回本地，旧存储只能装单平台，团队要按自己的 Engine 和存储驱动确认。
- 固定 `# syntax=docker/dockerfile:1`，避免 Dockerfile 前端语法随 builder 漂移。`1` 只跟随 1.x 的兼容更新，不会跳到 2.x；要完全固定可以写 `docker/dockerfile:1.8@sha256:...`。builder 镜像和 BuildKit 版本也要在 CI 里固定或至少记录；本章的 builder 是 BuildKit v0.33.1，`buildx inspect` 的输出就是版本证据。升级 builder 后，cache mount、secret、多架构的行为都要重新跑一遍本章的示例。
- CI 的缓存作用域要和代码分支、基础镜像绑定。同一个 registry 缓存被所有分支共用时，一个分支改依赖会让其他分支的缓存失效；可以用不同的缓存 tag 区分主分支和 PR，或者只让主分支写、PR 读。
- 给 builder 的缓存留磁盘和清理策略。`docker buildx du` 看总量，`docker buildx prune` 按时间或大小清理；cache mount 的依赖缓存和 registry cache 都不在镜像里，不清理会一直长大。`--no-cache` 只用于验证，不要放进日常流水线，它连 cache mount 一起绕过。

| `--mount=type=cache,target=/go/pkg/mod` | 依赖缓存挂载 | 不进镜像层；`id=` 分命名空间 |
| `--mount=type=cache,...,sharing=locked` | 并发构建排队写缓存 | apt 等需要独占的工具用 |
| `--mount=type=secret,id=git_token,target=/run/secrets/git_token` | 把 secret 临时挂进 `RUN` | 默认路径 `/run/secrets/<id>` |
| `--secret id=git_token,src=...` / `env=...` | 给构建传 secret | 也可用 `type=file`/`type=env` |
| `--cache-to type=registry,ref=...,mode=max` | 导出缓存到 registry | `mode=max` 含中间阶段 |
| `--cache-from type=registry,ref=...` | 从 registry 导入缓存 | 目标不存在时导入失败但构建继续 |
| `docker buildx imagetools inspect <镜像>` | 看 manifest list 和各平台 | 验证多架构发布 |
| `docker history --no-trunc` | 看每层 `CreatedBy` | 查 `ARG`/`ENV` 泄露 |

本章结束时，lab 里有 `shorty:0.1`（scratch、UID 65532、17.7 MB）和 `shorty-worker:0.1`（Python、UID 10001、222 MB），`shorty-api`、`shorty-worker`、`shorty-redis` 三个容器在 `shorty-net` 上运行；builder `ch10` 里留着 Go/Python 缓存，`localhost:5000` 上有 `shorty:0.1` 的 amd64+arm64 manifest list 和 `shorty:buildcache` 缓存镜像。第 11 章从这里继续，把镜像做得更小、更安全，并补上 SBOM 和扫描。
