# 第 8 章 容器安全基线：用户、capability、seccomp、userns、rootless

第 7 章压测时，shorty 的 api 容器因为内存泄漏被 OOMKilled。把内存上限调大之后服务恢复了，但另一个问题一直没动：这个容器是 root，带着 Docker 默认的那组 capability，seccomp 用的是默认 profile，根文件系统可写，镜像里还有一个完整的 shell。它能跑，是因为 lab 里的东西都可信；换成别人的镜像、别人的构建产物，这一套默认值就是攻击面。

先回答两个具体问题。第一，容器里的 root 和宿主 root 是同一个 uid 吗？默认情况下是：Docker 不启用 user namespace 时，容器里的 uid 0 就是宿主上的 uid 0，容器往命名卷写文件，宿主上看到的属主也是 0。第二，`--privileged` 到底打开了多少东西？它不是“多给几个权限”，而是把 capability、默认 seccomp、默认 AppArmor、SELinux 标签、设备访问和 `/sys` 一起放开，Docker 官方文档的原话是“容器几乎可以做宿主能做的一切”。

这两个问题决定了本章的做法：先把进程从 root 换成非 root，再把 root 的权限拆成 capability 按需给，再用 seccomp 缩小系统调用面，最后看 userns-remap 和 rootless 改变了哪一层映射、没有改变什么。短链服务 shorty 继续作为例子；这一章用 `shorty:dev`，它保留了构建阶段的 shell，方便进容器里看 uid、`/proc/self/status` 和文件权限。生产镜像要到第 10 章才去掉这些工具。

> **起点**：第 7 章结束。lab 里没有 kind 集群，`shorty-api`、`shorty-pg`、`shorty-redis` 在 `shorty-net` 上，api 以默认 root、未加安全选项运行；`shorty:dev` 可用。`bash code/ch08/setup.sh` 会重新构建 `shorty:dev`、准备 `busybox:1.37`，并装上 8.4 和 8.7 用到的 `rootlesskit`、`slirp4netns`、`capsh`。8.6 会临时建一个单节点 kind 集群，跑完删掉。

## 8.1 容器 root 与 user namespace

Docker 默认不为容器创建 user namespace。`docker run` 会创建 PID、network、mount、IPC、UTS 等 namespace，但 uid 和 gid 仍直接使用宿主的映射，所以容器里的 uid 0 在宿主内核看来也是 uid 0。Docker 的安全文档把 user namespace 单列出来：Docker 1.10 起 daemon 直接支持它，但默认不启用。默认路径下，容器 root 能改的文件、能发的信号，和宿主 root 是同一套权限检查。

```

第一段输出里，`shorty:dev` 不带 `--user` 跑 `id`，结果是 `uid=0(root)`。接着创建一个命名卷，让容器往 `/data/root.txt` 写一行，再在宿主上看这个卷的目录和文件：`stat` 的两行都是 `0:0`，目录 `755`、文件 `644`。这不是 Docker 把文件“复制成 root”，而是写文件的那个进程在宿主上就是 uid 0；卷只是宿主文件系统上的一棵目录树，`docker volume inspect` 给出的 `Mountpoint` 是它当前的位置，具体路径随存储后端变化，不能当成稳定接口。

然后加 `--user 65532:65532` 启动 api。`docker inspect` 的 `.Config.User` 是 `65532:65532`，这只说明容器的进程以这个 uid 启动；镜像里的 `/out/shorty` 仍然属于 root，`/` 也仍然属于 root。容器里的 `id` 变成 `uid=65532`，`/tmp` 是 `1777`，所以 `write /tmp: ok`；往 `/ch08-write` 写的时候，VFS 按普通文件权限拒绝，报 `Permission denied`。同一个卷再用 uid 0 跑一次，卷里的文件还是 `0:0`，说明 `--user` 没有改变挂载点的属主，只改变了进程的凭据。应用要写挂载目录时，这一点会直接变成故障，8.7 的第二个例子就是它。

判断当前容器有没有 user namespace，不能只看 `id`。先 `docker inspect -f '{{.State.Pid}}' <容器>` 拿到宿主上的 PID，再读 `/proc/<pid>/uid_map`：没有 user namespace 时，映射通常是 `0 0 4294967295`，也就是整段直通；`userns-remap` 会看到 `0 231072 65536` 这样的区间；rootless 下容器 0 映射到启动 daemon 的用户（例如 `0 1000 1`），其余 uid 再用 subuid 补齐。`docker info` 的 `Security Options` 能告诉你 daemon 是否开了 rootless 或 AppArmor，但看不到单个容器的映射，最终还是要读 `uid_map`。

`--user` 不是 user namespace。它把进程换成另一个 uid，但容器仍然没有 user namespace；如果进程回到 uid 0，它在宿主上还是 root。要让容器里的 0 不等于宿主上的 0，需要 `userns-remap`。Docker 的做法是在 daemon 上配置 `userns-remap`，把容器的 uid 0 映射到 `/etc/subuid` 里给某个用户分配的从属 uid 区间：例如 `testuser:231072:65536` 表示容器里的 0 对应宿主上的 231072，容器里的 1 对应 231073，依此类推。`/etc/subgid` 管 gid。这个映射对容器透明，但会带来两个实际后果：daemon 仍然以 root 运行（它只是替容器做映射），而且启用 `userns-remap` 会遮住 `/var/lib/docker` 下已有的镜像和容器层，官方建议在新安装上启用，不要在已有数据的 daemon 上直接打开。配置写在 `daemon.json` 的 `userns-remap` 字段或 `dockerd --userns-remap`，改完要重启 dockerd；对单个容器可以用 `--userns=host` 临时关掉映射，但镜像层属主仍然是映射后的 uid，`sudo` 和 setuid 程序可能因此表现异常。

`userns-remap` 也不是没有代价。官方列出的不兼容项包括 `--pid=host`、`--network=host`、不认识 daemon uid 映射的外部卷/存储驱动，以及不带 `--userns=host` 的 `--privileged`；user namespace 里的 root 还不能 `mknod` 创建设备节点。bind mount 的属主要提前安排好，否则容器里的 root 在宿主上是一个高号 uid，写不进原来的目录。它适合“进程必须在容器里当 root，但不想在宿主上当 root”的场景；如果应用本身能以非 root 跑，直接用 `--user` 更简单，也不需要 daemon 级配置。

Kubernetes 侧对应的是 Pod user namespace。Pod 设 `spec.hostUsers: false` 后，kubelet 会为每个 Pod 分配互不重叠的宿主 uid/gid 区间，容器里的 root 在节点上是非特权用户；`runAsUser`、`runAsGroup`、`fsGroup` 仍然指容器内的用户，卷里的 inode 属主按容器内视角处理。这个特性在 Kubernetes 1.28 进入 alpha，1.30 beta，1.36 转为 stable（特性门控 `UserNamespacesSupport`）。它要求节点文件系统支持 idmap mount，至少 Linux 6.3；NFS 卷不支持，`hostNetwork`、`hostPID`、`hostIPC` 也不能和 `hostUsers: false` 同时使用。本书的嵌套实验环境里，Pod user namespace 的 sandbox 会卡在 `mounting "sysfs" ... operation not permitted`，所以第 31 章只能讲机制并展示这个限制，没有在本地跑通成功路径。本节在 Docker 侧也没有真的重启 daemon 去开 `userns-remap`，因为那会清空 lab 的镜像存储；`--user` 的例子是实测，`userns-remap` 的映射规则来自官方文档。

> **旧资料提示**：旧教程常把“容器 root 就是宿主 root”当成永远成立。默认的 rootful Docker 确实如此，但 `userns-remap`、rootless Docker 和 Kubernetes 的 Pod user namespace 都会改变映射；判断当前环境要看 `docker info` 的 `Security Options`、容器的 uid 映射和 `/etc/subuid`，不能只看 `id`。

## 8.2 capabilities：把 root 拆成小权限

capability 把“root / 非 root”的二选一拆成一组细粒度权限：绑定 1024 以下端口是 `CAP_NET_BIND_SERVICE`，发原始套接字是 `CAP_NET_RAW`，改文件属主是 `CAP_CHOWN`，挂载文件系统是 `CAP_SYS_ADMIN`。Docker 默认不是“全给 root”，而是只给一组它认为常见且风险较低的 capability；官方文档的表述是“丢掉除所需之外的全部 capability”，这是一个 allowlist，不是 denylist。

```

第一个 `CapEff` 是 `00000000a80425fb`。用宿主机上的 `capsh --decode` 展开，得到 14 个 capability：`chown`、`dac_override`、`fowner`、`fsetid`、`kill`、`setgid`、`setuid`、`setpcap`、`net_bind_service`、`net_raw`、`sys_chroot`、`mknod`、`audit_write`、`setfcap`。这是 Docker 29.9.2 的默认集；不同版本会增删，不要把“14 个”当成契约。`CapBnd` 和 `CapEff` 相同，说明这组权限也在 bounding set 里，进程以后不能再把丢掉的 capability 捡回来。

capability 不是一个数字，而是 permitted、effective、inheritable、bounding 几个集合。`CapEff` 是进程此刻真正生效的集合，`CapBnd` 是上限；Docker 的 `--cap-drop` 会把 capability 从 bounding set 里去掉，所以即使进程随后执行一个带文件 capability 的二进制，也不能把它重新加回 effective。`--cap-add` 则是在 bounding set 和 effective set 里同时放回一项。读 `/proc/<pid>/status` 时至少看 `CapEff` 和 `CapBnd` 两行，只看 `id` 会以为“不是 root 就没有权限”，或者反过来以为“root 就什么都能做”。

`--cap-drop=ALL` 之后，`CapEff` 和 `CapBnd` 都变成全 0。busybox 的 `ping` 需要构造 ICMP 原始套接字，内核在 `socket(AF_INET, SOCK_RAW, ...)` 这一步返回 `EPERM`，busybox 把它打印成 `ping: permission denied (are you root?)`；错误文本不是 `Operation not permitted`，但原因是同一个。加回 `NET_RAW`，其他仍然全 drop，ping 就通了。这个对照说明 capability 是“按项加回”，不是“要么 root 要么不能用”。

`--privileged` 的输出是 `000001ffffffffff`，即 41 位全 1。Docker CLI 参考把它的效果列得很具体：启用全部 Linux capability、关闭默认 seccomp、关闭默认 AppArmor、关闭 SELinux 进程标签、授予所有宿主设备、把 `/sys` 和 cgroup 挂载改成可写。它存在的理由是 Docker-in-Docker 这类特殊场景，不是日常运行参数；一个有 `--privileged` 的容器拿到宿主 root shell 并不困难。

最后两行是 `--security-opt=no-new-privileges`。进程的 `NoNewPrivs` 从 0 变成 1，含义是进程及其子进程不能再通过 setuid/setgid 程序或文件 capability 获得新权限；官方文档说 `su`、`sudo` 这类提权命令因此不再工作，seccomp 过滤器也会在权限降下来之后才应用。它不减少已有的 capability，只是堵住“执行一个 setuid 程序再涨权限”这条路。

还有一项不要随手加：`CAP_SYS_ADMIN`。它覆盖挂载、`pivot_root`、设置 namespace、部分 `ioctl` 等一大堆操作；很多需要它的场景其实是需要更窄的 `CAP_NET_ADMIN`、`CAP_SYS_CHROOT` 或一个 sidecar。默认集里没有它，只在明确需要时才加。

把这两节连起来，一个业务的默认起点应该是 `--user` 加 `--cap-drop=ALL`，再按实际需要 `--cap-add` 一项。8.7 会看到 `--cap-drop=ALL` 之后连绑 80 端口都不行，这就是“默认拒绝、按需加回”的直接代价。

## 8.3 seccomp、AppArmor、SELinux

capability 管的是“这个进程能不能做某类操作”，seccomp 管的是“这个进程能不能发起某个系统调用”。两者不重叠：一个进程可以有 `CAP_NET_RAW`，但 seccomp 仍然可以禁止 `socket`；反过来，seccomp 放行 `mount`，没有 `CAP_SYS_ADMIN` 也挂不上。Docker 默认给每个容器装一个 seccomp profile，官方文档说它从 300 多个系统调用里禁用“大约 44 个”，这个数字随版本变化；profile 是一个 allowlist，默认动作是 `SCMP_ACT_ERRNO`，再对具体系统调用改成 `SCMP_ACT_ALLOW`。

```

`Seccomp: 2` 是过滤模式，`Seccomp_filters: 1` 说明挂了一个过滤器。接着用一个自定义 profile：默认放行，只把 `uname` 的规则改成 `SCMP_ACT_ERRNO`。同一个 `uname -a` 在默认 profile 下打印 `Linux ... 7.0.0-38-generic ... GNU/Linux`，在自定义 profile 下 coreutils 报 `uname: cannot get system name: Operation not permitted`。这里顺便看到一个事实：容器里的 `uname` 看到的是宿主内核版本，不是镜像里的某个“容器内核”；容器和宿主共享内核，这也是后面说 rootless 不保护内核漏洞的原因。

`seccomp=unconfined` 把过滤器摘掉，`Seccomp` 变成 0、`Seccomp_filters` 变成 0。它适合排障时确认“是不是 seccomp 拦的”，不适合作为生产默认值。

默认 profile 挡住的系统调用不止 `uname` 这一类“信息查询”。Docker 官方表格里列了 `mount`、`umount2`、`pivot_root`、`unshare`、`setns`、`ptrace`、`bpf`、`kexec_load`、`init_module` 等：它们要么能改宿主状态，要么是内核漏洞的高风险入口，要么已经被 capability 挡住、再加一层 seccomp 作为纵深。`unshare` 也在拒绝表里，所以第 1 章要复现 `unshare --user`，必须换一个允许它的 seccomp profile；只加 capability 不够，seccomp 会先把它拦掉。这类实验通常还要 `CAP_SYS_ADMIN` 才能做其他 namespace 操作，两个一起用基本等于把容器当成宿主进程在跑，只适合一次性实验。

AppArmor 和 SELinux 是另一层：它们按路径或标签限制程序能访问哪些资源。Docker 在启用 AppArmor 的宿主机上会自动生成并加载 `docker-default` profile，容器默认使用它；`--security-opt apparmor=profile` 可以换成一个已经加载的 profile。SELinux 则通过标签工作，bind mount 的 `:z` 表示内容在多个容器间共享，`:Z` 表示私有、不共享，两者都会改宿主上的标签，所以只对确实需要 SELinux 的目录用。

AppArmor 和 SELinux 的区别在策略的写法上：AppArmor 用文件路径匹配，profile 里写“允许读 `/etc/nginx/**`、拒绝写 `/var/www/**`”；SELinux 用 inode 上的标签和策略里的类型规则，路径改名不会绕过标签。一个节点通常只启用其中一种，具体看发行版；Kubernetes 的 `securityContext` 分别用 `appArmorProfile` 和 `seLinuxOptions` 传这些设置。两者都不是“开了就安全”：profile 写得太宽、以 complain 模式运行、或者容器本来就是 privileged，限制都会失效。

本书的 lab 是嵌套的 dind，`cat /proc/self/attr/current` 显示 `unconfined`，而不是普通宿主机上的 `docker-default (enforce)`；这说明外层环境没有把 AppArmor profile 施加到内层容器。示例能确认的是 daemon 侧配置了 AppArmor（`docker info` 的 `Security Options` 里有 `apparmor`），不能把 `docker-default` 的拦截效果当成在这个 lab 里实测过。SELinux 在 lab 里没有启用，`:z`/`:Z` 的语义来自 Docker 的 bind mount 文档，本书没有做 SELinux 的运行时验证。

这三样东西的共同点是“减少攻击面”，不是“防逃逸”的充分条件。Kubernetes 的 Linux 内核安全页面明确列了 seccomp 的局限：配置可能随应用更新失效，攻击者仍然可以用被放行的系统调用打内核漏洞，按应用维护 profile 在规模上很难。AppArmor 和 SELinux 也一样，它们限制的是被允许的路径和标签，内核本身的漏洞、`--privileged`、挂进来的宿主目录都不在它们的防护范围内。

> **旧资料提示**：旧教程常写“Docker 默认丢弃 37 个 capability、seccomp 拦截 44 个 syscall”。这两个数字都随 Docker 版本变化，官方 seccomp 页面只说“约 44 个、300+ 里”，capability 默认集也没有承诺固定数量。写基线时应该写“默认集”与“按需 drop ALL”，不要写死数字。

## 8.4 rootless Docker

rootless 模式把 dockerd 和容器一起放进一个 user namespace，daemon 以普通用户身份运行。它和 `userns-remap` 的区别在于谁来承担 root：`userns-remap` 的 daemon 仍然是 root，只是把容器里的 uid 映射到 subuid；rootless 的 daemon 本身就不是 root。Docker 官方文档说 rootless 模式除了 `newuidmap`、`newgidmap` 之外不使用 setuid 二进制或文件 capability，这两个工具用来给 user namespace 分配多个 uid/gid。

装 rootless 之前要先满足两个前置条件：`newuidmap`/`newgidmap` 在 PATH 里，并且 `/etc/subuid`、`/etc/subgid` 给运行 daemon 的用户至少 65536 个从属 uid/gid。发行版的软件包通常带 `dockerd-rootless-setuptool.sh install`，它会创建 systemd user unit、把 `DOCKER_HOST` 指到 `unix:///run/user/<uid>/docker.sock`，并给 CLI 建一个 `rootless` context。没有 systemd 的环境可以手动用 `rootlesskit` 启动，本书的示例就是这条路径；它比安装脚本多做了几件底层的事，所以看起来长，但原理一样：先创建 user namespace，再在 namespace 里启动 dockerd。

rootless 的 daemon socket 不在 `/var/run/docker.sock`，默认在 `$XDG_RUNTIME_DIR/docker.sock`，所以 `docker` 客户端要用 `DOCKER_HOST` 或 `docker context use rootless` 指过去。不要用 `sudo docker` 去连 rootless daemon，sudo 会切回 root，环境变量和 socket 路径都变了；也不要把 rootless 的 socket 暴露给其他用户，能写它的人仍然能控制这个用户的 daemon 和容器。

{{#include code/ch08/8_4_rootless_info.out}}
```

`docker info` 的 `Security Options` 里多出 `rootless`，同时 `Cgroup Driver` 是 `none`。这不是配置漏了：官方 troubleshooting 说 rootless 下 cgroup 相关功能只有在 cgroup v2 加 systemd 委派时才可用，`docker info` 显示 `Cgroup Driver: none` 就表示 `--memory`、`--cpus`、`--pids-limit` 这些参数会被忽略。本节的重点是权限模型，不是资源限制；真正要用 rootless 跑生产负载，得先把 systemd 的 cgroup 委派配好。

`ps` 的三行里，`rootlesskit`、它 re-exec 出来的 `exe` 子进程和 `dockerd --rootless` 都是 `rls` 用户。dockerd 不是 root，容器进程也不是从宿主 root 派生的。按 Docker 的 UID/GID 映射文档，rootless 下容器 uid 0 映射到运行 rootless Docker 的宿主用户（这里是 uid 1000），容器 uid 1 及以上映射到 `/etc/subuid` 里的从属区间；这和 `userns-remap` 把容器 0 映射到 subuid 起点（231072）不一样。两者都让容器里的 root 在宿主上变成非特权 uid，但落点不同，排障时看 `/proc/<pid>/uid_map` 才不会猜错。

端口那一行是 rootless 最常遇到的限制。`docker run -p 80:8080` 要 rootlesskit 在宿主网络里绑定 80，而 rootlesskit 以 uid 1000 运行，没有 `CAP_NET_BIND_SERVICE`，于是报 `cannot expose privileged port 80`，最后一句是 `bind: permission denied`。换成 `18080:8080` 就成功。官方给了三个放开的办法：改用 1024 以上的端口、给 rootlesskit 二进制加 `cap_net_bind_service`、或者把 `net.ipv4.ip_unprivileged_port_start` 调成 0。本书的 lab 宿主恰好把 `ip_unprivileged_port_start` 设成了 0，所以示例在启动 rootless daemon 前把它调回 1024，否则这个限制根本不会出现；这也说明“同样一条 `-p 80`，在不同宿主机上结果可能不同”，排障要先看这个 sysctl。

rootless 降低的是“daemon 或容器运行时被攻破”的后果：攻击者拿到的不是宿主 root，而是启动 daemon 的普通用户，容器里的 root 也只在自己的 user namespace 里有意义。它不改变容器和宿主共享内核这件事，内核漏洞、镜像里的恶意内容、应用本身的漏洞仍然要按照原来的方式补。存储和网络也有差异：rootless 常用 `fuse-overlayfs` 或受限的 overlayfs，网络走 slirp4netns 或 pasta，`docker run -p` 默认不传递源 IP，吞吐也比内核态的 bridge/NAT 低。本书的 lab 用 slirp4netns，启动脚本还做了两处环境适配：在私有 mount namespace 里准备可写的 `/run`，并在启动的几秒内放开 `apparmor_restrict_unprivileged_userns`；生产上按官方 rootless 安装脚本走，不需要这些。

> **旧资料提示**：旧教程把 `--privileged` 当作跑 Docker-in-Docker 的常规手段。Docker 官方的 CI 文档现在给的是 Docker 官方镜像和 BuildKit，rootless 文档也给了 `docker:dind-rootless` 的路径；`--privileged` 应该作为最后手段，并且只放在隔离的 runner 或单独节点上。

## 8.5 镜像与运行时基线

把上面几项合起来，才是可以复制的运行时基线：非 root、`--cap-drop=ALL`、`no-new-privileges`、只读根文件系统、按需的可写 tmpfs 或卷，以及默认的 seccomp profile。镜像侧还有三条：基础镜像尽量小、引用用 digest 而不是浮动 tag、生产镜像里不要留 shell 和包管理器。Docker 的构建最佳实践和 Kubernetes 的安全清单都把“最小内容、非 root、digest”写在前面；Kubernetes 清单还明确说，排障应该用 ephemeral container，而不是在生产镜像里留一套调试工具。

镜像侧的非 root 要在 Dockerfile 里就做好，而不是只在 `docker run` 时加 `--user`。官方构建最佳实践建议创建专用的用户和组，用 `USER` 切过去，避免安装或使用 `sudo`，也不要反复在 root 和普通用户之间切换。只加 `--user` 而不改镜像里文件和目录的权限，应用可能连自己的二进制、配置或缓存都读不了；8.7 的 secret 故障就是同一个问题的另一个面。镜像里创建用户时用固定的数字 UID，Kubernetes 的 `runAsNonRoot` 才能在启动前判断“这个镜像默认是不是 root”。

shorty 的 api 本身不往 `/tmp` 写文件；这里用同一个镜像里的 shell 验证的是“这个容器还能写哪里”，不是 shorty 的业务行为。worker 的心跳文件才是应用真的写 `/tmp` 的例子，第 14 章会看到。生产镜像在第 10 章会换成 `scratch` 加静态二进制，没有 shell、没有包管理器，到那时 `docker exec` 这条验证路径本身也会消失，排障要改用 `kubectl debug` 的 ephemeral container 或一个临时副本。

只读根文件系统不是所有应用都能直接开。需要写配置、缓存、PID 文件、上传目录的程序，要么把这些路径改成 `--tmpfs`（数据随容器消失），要么挂一个明确的命名卷或 bind mount（数据持久化），要么在启动时把只读层复制到可写层。`--tmpfs /tmp` 只适合临时文件；把数据库的数据目录放在 tmpfs 上，容器一停数据就没了。

`--read-only` 也不会阻止容器通过挂进来的目录写宿主。真正危险的是把 `/var/run/docker.sock` 挂进容器：Docker 安全文档说，能控制 daemon 的人就可以让 daemon 起一个把宿主 `/` 挂进去的容器，效果等于宿主 root；把 socket 交给业务容器，等于把这条路径交给业务代码。宿主 `/`、`/proc`、`/sys` 和设备也一样，`--device` 应该按需给具体设备，不要用 `--privileged` 一把打开。

`no-new-privileges` 只阻止“执行 setuid 程序后涨权限”，不阻止进程用已有的 capability 做事；它也不能替代非 root。一个以 uid 0 运行、带 `CAP_SYS_ADMIN` 的容器，即使开了 `no-new-privileges`，仍然能做很多宿主级操作。

镜像引用固定 digest 是另一条独立基线。tag 可以被重新推送，`shorty:0.1` 今天和明天可能指向不同的 manifest；`shorty@sha256:...` 才是不可变的内容地址。Kubernetes 的安全清单把“用 digest 或验证签名”列为镜像项，Docker 构建最佳实践也建议固定基础镜像的 digest 并定期更新。最小基础镜像减少的是镜像里可被利用的二进制和 shell，和非 root、capability、seccomp 是叠加关系，不是替代关系。

## 8.6 Kubernetes 侧对照：securityContext 与 PSA

Docker 的 `--user`、`--cap-drop`、`--security-opt` 在 Kubernetes 里对应 Pod 和容器的 `securityContext`。常用的字段有：Pod 级的 `runAsNonRoot`、`runAsUser`、`runAsGroup`、`fsGroup`，容器级的 `allowPrivilegeEscalation`、`capabilities.drop`、`seccompProfile.type`、`readOnlyRootFilesystem`。`fsGroup` 解决的是卷的组属主问题：挂进来的卷会被设置成这个 gid，组内可读写的文件对容器里的非 root 用户就可访问；Docker 的 `--user` 没有对应的自动改属主机制，所以 8.7 要手工 `chmod`。

Pod Security Standards 把策略分成三档：Privileged 完全不限制，Baseline 阻止已知的提权配置，Restricted 在 Baseline 之上要求非 root、禁止提权、drop ALL、明确 seccomp。标签有 `pod-security.kubernetes.io/enforce`、`warn`、`audit` 三种模式，每种还可以用 `enforce-version`、`warn-version`、`audit-version` 固定策略版本；不写版本时用 `latest`，也就是当前集群的最新策略。三种模式可以分开设置，例如先只开 `warn` 观察一段时间，再切到 `enforce`，这是把现有工作负载迁移到 Restricted 的常用路径。模式是命名空间属性，不是 Pod 属性；同一个 Pod 在哪个命名空间创建，就受哪个命名空间的策略约束。下面的例子在一个 `restricted` 命名空间里创建一个 root、privileged 的 Deployment。

这六项对应一份合格的 `securityContext`：`runAsNonRoot: true` 且 `runAsUser` 不为 0；`allowPrivilegeEscalation: false`；`capabilities.drop: ["ALL"]`，Restricted 只允许再加回 `NET_BIND_SERVICE`；`seccompProfile.type: RuntimeDefault`；以及不要 `privileged`。`readOnlyRootFilesystem: true` 不在这六项里，PSA Restricted 也没有强制它，但运行时基线仍然建议开启。`fsGroup` 和 `runAsGroup` 不在这条错误里，因为它们不决定 Pod 是否违反 Restricted，但决定挂载卷能不能被非 root 进程读写。

`securityContext` 的优先级也要记清楚：Pod 模板里的 `securityContext` 会覆盖镜像里的 `USER`，容器级的字段又会覆盖 Pod 级的同名字段；`fsGroup` 只有 Pod 级，没有容器级。没写的字段不是“自动安全”，而是交给运行时默认值或 kubelet 配置，例如 seccomp 是否默认 `RuntimeDefault` 取决于节点配置，不能假设所有集群都一样。把关键字段显式写出来，PSA 才能稳定地判断，审计时也能看出这个 Pod 的意图。

PSA 是命名空间级的准入，不是沙箱。Restricted 确实会拒绝 `hostPath` 和 `privileged`，但一个有权限创建命名空间、修改命名空间标签或在 Privileged 命名空间里创建 Pod 的人，可以绕开这层策略；Kubernetes 的安全清单也提醒，能创建 Pod 的 RBAC 权限本身就可能等于节点访问权。所以 PSA 要和 RBAC、节点隔离、NetworkPolicy 一起用，不能把它当成“集群里不可能出现特权容器”的保证。第 31 章会在 shorty 的命名空间里正式落地 Restricted，并补上 `fsGroup`、`readOnlyRootFilesystem` 和 ValidatingAdmissionPolicy。

## 8.7 排障：drop ALL 后绑不了 80、非 root 读不到 secret

第一个故障是“收紧了 capability 之后，服务起不来”。shorty 默认监听 8080，把 `SHORTY_LISTEN` 改成 `:80`，再用 `--cap-drop=ALL` 启动，进程日志最后一行是 `listen tcp :80: bind: permission denied`。

```console
{{#include code/ch08/8_7_troubleshooting.out}}
```

这里有个环境细节：本书的 lab 宿主把 `net.ipv4.ip_unprivileged_port_start` 设成了 0，普通用户也能绑 80，所以示例用 `--sysctl net.ipv4.ip_unprivileged_port_start=1024` 把容器网络的这个值调回常规值；不加这一行，root 即使没有 `CAP_NET_BIND_SERVICE` 也能绑成功，故障就复现不出来。排障时先看这个 sysctl，再看 capability，顺序不能反。

定位 capability 有两条路。镜像里如果有 `capsh`，`capsh --print` 会列出当前进程的 effective、bounding 和 permitted 集合；如果有 `getcap`，`getcap /path/to/binary` 看的是文件 capability，不是进程的。示例不依赖镜像里有没有这些工具，而是读 `/proc/<pid>/status` 的 `CapEff`，再用宿主上的 `capsh --decode` 展开。加回 `NET_BIND_SERVICE` 后，`CapEff` 是 `0x0000000000000400`，decode 出来只有 `cap_net_bind_service`，80 端口能绑，`curl` 返回 `ok`。修复要么加这一项 capability，要么把监听端口改成 8080；前者给的是“绑低端口”的能力，后者改的是应用配置，通常更小。

第二个故障是“非 root 读不到挂进来的 secret”。文件在宿主上是 `0:0 600`，容器以 65532 运行，bind mount 进来后 `cat` 报 `Permission denied`。`--mount` 只负责把路径挂进去，不会改文件属主，也不会因为容器里的 uid 是 65532 就自动 chown；Docker 的 `--user` 和 bind mount 之间没有 `fsGroup` 这种联动。修复可以 `chmod 644`（组和其他用户可读）、`chown 65532`（只给这个 uid）、或者把文件放进一个组可读的目录并让容器用户加入那个组。示例用 `chmod 644` 是最小改动；生产里更常见的是在 Kubernetes 用 `fsGroup`，或者在 initContainer 里 `chown`，而不是把 secret 做成全局可读。

输出里的 `stat` 是 `0:0 600`，`cat` 是 `Permission denied`；`chmod 644` 之后同一个挂载读到 `demo-password`，说明问题在文件权限，不在 mount 语法。

错误文本里的 errno 也值得分清。绑低端口在 Linux 上返回 `EACCES`，日志通常写成 `permission denied`；没有 `CAP_NET_RAW` 时创建原始套接字返回 `EPERM`，busybox 会写成 `permission denied (are you root?)`；文件 mode 不对也是 `EACCES`。同样是“权限不够”，前者缺 capability，后者缺文件权限，修复方向完全不同。看 `CapEff` 能确认前者，看 `stat` 的 uid/gid/mode 能确认后者，不要只凭错误文本里的一个词判断。

除了进程内的 `/proc`，`docker inspect` 也能把“请求的配置”和“实际生效的配置”对上：`HostConfig.CapDrop`、`HostConfig.CapAdd`、`HostConfig.SecurityOpt`、`HostConfig.ReadonlyRootfs`、`Config.User`。如果 `CapDrop` 是 `["ALL"]` 而 `CapAdd` 是空，进程的 `CapEff` 却是 0，这不是 Docker 没生效，而是本来就没有 capability；反过来，`CapAdd` 里有一项但 `CapEff` 没有，就要看镜像是不是把二进制设了 file capability，或者启动脚本又降了权限。

这两个故障的排查顺序是一样的：先看错误文本是 `EPERM`/`EACCES` 还是别的，再看进程的 uid、`CapEff`、`NoNewPrivs`，最后看挂载点和文件 mode。不要一上来就加 `--privileged`；它会让两个故障都“消失”，但也会把 8.2 到 8.5 收紧的东西全部退回去。

## 上生产前

把“默认非 root”写进启动模板，而不是靠镜像作者记得写 `USER`。`--user 65532:65532` 是最低要求；再叠加 `--cap-drop=ALL`、`--security-opt=no-new-privileges` 和默认 seccomp。需要绑低端口就只加 `NET_BIND_SERVICE`，需要原始套接字就只加 `NET_RAW`，每加一项都要能说出对应的系统调用和业务理由。镜像里的 `USER` 可以被编排覆盖，Kubernetes 的 `securityContext` 优先级高于镜像；两边都写，才不会因为换一个基础镜像就退回 root。

不要把 `docker.sock`、宿主 `/`、`--privileged` 带进业务容器。`--privileged` 会同时打开 capability、设备、seccomp、AppArmor 和 SELinux，Docker 官方文档说容器几乎可以做宿主能做的一切；`docker.sock` 等于把 daemon 的控制权交出去。确实需要构建镜像、访问设备或跑嵌套容器时，用 rootless、BuildKit、独立 runner 或单独节点，并且把这类工作负载和业务负载分开审批、分开调度。

只读根文件系统加显式可写卷，应该作为新服务的默认，而不是出事后才加的补丁。`--read-only` 会把应用偷偷写 `/var`、`/etc` 的行为暴露出来；需要临时目录就 `--tmpfs /tmp`，需要持久化就挂命名卷。生产镜像里不要留 shell 和包管理器，排障用 `kubectl debug` 的 ephemeral container 或一个临时的调试副本。镜像引用固定 digest、基础镜像尽量小，这两条和运行时参数一样重要，但它们属于镜像和供应链，第 10 到 13 章会展开。

这些项要尽量变成模板和准入，而不是靠人记。Docker 侧把参数写进 Compose 或启动脚本的默认值；Kubernetes 侧把 `securityContext` 写进工作负载模板，再用 PSA 的 `enforce=restricted` 兜底。镜像 digest 可以在 CI 里固定，构建时用 `USER` 和非 root 目录权限做静态检查。人只在例外时显式打开一项，并在清单里写清楚理由；如果一项权限只能靠“大家都知道要加”来维持，它迟早会在某次复制粘贴里丢掉。

rootless 和 `userns-remap` 降低的是宿主风险，不替代补丁、最小镜像和网络策略。rootless 下 cgroup 限制要 systemd 委派，`-p` 不能直接发布 1024 以下端口，网络走用户态栈会慢一些；`userns-remap` 要提前规划 subuid/subgid 和卷属主，启用后会遮住旧的镜像层。把它们当成“多一层隔离”，不要当成“可以少打补丁”的理由。

| `securityContext.seccompProfile.type` | seccomp profile | Restricted 要求 `RuntimeDefault` 或 `Localhost` |
| `securityContext.readOnlyRootFilesystem` | 只读根文件系统 | PSA Restricted 不强制；运行时基线建议开启 |
| `securityContext.privileged` | 特权容器 | Restricted 禁止；会覆盖 seccomp/AppArmor |

本章结束时，`shorty-api` 以 uid 65532、`--cap-drop=ALL`、自定义 seccomp 运行，`shorty-pg` 和 `shorty-redis` 仍在 `shorty-net` 上；rootless 和 userns 的对照已经做过，但没有改 lab 的 daemon 配置。下一章从 `shorty:dev` 这个还带 shell 的镜像开始，拆开看它是怎么构建出来的。
