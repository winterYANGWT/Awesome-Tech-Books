# 第 23 章 Service、EndpointSlice、kube-proxy 与集群 DNS

`kubectl -n shorty get svc api` 会给出一个 `10.96.0.0/16` 里的地址，而 api 的两个 Pod 各自有 `10.244.x.x` 的地址。在 Pod 里执行 `wget http://api:8080/healthz` 能拿到 `ok`；把同一个地址交给 `ping`，一个包也回不来。另一个常见现象是 Service 明明有 ClusterIP，`curl` 却立刻返回 `Connection refused`，而不是超时。

这两个现象指向同一件事：ClusterIP 不是某台主机上的地址，而是一组由 kube-proxy 维护的转发规则。规则只对特定协议和端口生效，而且规则的另一端必须真的有就绪的 Pod。把 Service 当成“有一个 IP 的负载均衡器”去理解，就会在 ping、DNS、NodePort 和排障上接连踩坑。

本章沿着一条请求走完这条链路：先看 Service 的四种类型和端口的含义，再拆开 Service 背后的 EndpointSlice，然后看 kube-proxy 在节点上写的 iptables/nftables 规则，接着解释集群 DNS 如何把名字变成 ClusterIP 或 Pod IP。最后用 `internalTrafficPolicy: Local` 故意制造“同节点没有后端”的失败，并检查双栈字段和 ClusterIP 的分配方式。

> **起点**：本章从 `s3-stateful` 开始：3 节点 kind 集群，api 2 副本，postgres 是 StatefulSet 加 headless Service，redis 和 worker 各 1 副本，四个 Service 目前都是 ClusterIP。一步到位：`bash code/ch23/setup.sh`。这个脚本还会启动 `cloud-provider-kind`，用来给 `type: LoadBalancer` 分配地址。

## 23.1 Service 的四种类型

先把最小的对象看清楚。`Service` 的 `selector` 选出 Pod，`ports` 声明怎么把 Service 端口映射到容器端口。`port` 是客户端连 Service 时用的端口，`targetPort` 是 Pod 里进程真正监听的端口；不写 `targetPort` 时它默认等于 `port`。`targetPort` 也可以写 Pod 端口定义里的名字，例如 shorty 的 api 把 8080 命名为 `http`，Service 就写 `targetPort: http`。这样以后改容器端口，只要改 Pod 的 `containerPort` 名字对应的数字，Service 不用跟着改。

`type: ClusterIP` 是默认值。apiserver 从 `--service-cluster-ip-range` 里分配一个虚拟 IP，kube-proxy 在每个节点上写一条规则：目的地址等于这个 ClusterIP、目的端口等于 `port` 的 TCP 或 UDP 包，被改写成某个后端 Pod 的 `targetPort`。所以从 Pod 里访问 `api:8080` 能通，是因为请求先在节点上被 DNAT 到了 `10.244.x.x:8080`。`ping` 不通也很正常：ClusterIP 没有绑定在任何网卡上，也没有进程会回应 ICMP Echo；kube-proxy 的规则处理的是 Service 端口上的 TCP/UDP，不是“到这个 IP 的所有流量”。把 ping 失败当成 Service 坏了，是排障时最常见的误判之一。

Service 也不要求一定有 selector。给一个不写 selector 的 Service 手工创建 EndpointSlice，就能把集群外的数据库、另一个集群的地址，或者迁移中的一部分后端挂到同一个 Service 名下；控制器不会覆盖你手工创建的 slice，`kubernetes.io/service-name` 标签负责建立关联。这种写法在“生产用外部数据库、测试用集群内数据库”的迁移期很有用，但地址的生命周期要自己管，Pod 重建时不会自动更新。

`type: NodePort` 在 ClusterIP 的基础上再加一层：控制面从 `--service-node-port-range`（默认 30000–32767）里分配一个端口，每个节点都在这个端口上监听，再转发到 Service 的后端。客户端用任意节点的 IP 加 `nodePort` 就能访问，不依赖集群内的 DNS。`nodePort` 可以自己指定，但必须落在允许的范围里；范围被分成静态段和动态段，默认 30000–30085 留给手工指定，30086 以上由控制面动态分配，这样可以降低手工端口和自动分配撞车的概率。示例里显式写了 30080，就是为了让它稳定地落在静态段。手工指定仍然可能和别的 Service 冲突，冲突时 API 会拒绝创建。

`type: LoadBalancer` 又建立在 NodePort 上：云控制器（cloud-controller-manager）向云厂商申请负载均衡器，把流量导到节点端口；地址异步写进 `Service.status.loadBalancer.ingress`。在 kind 里没有云厂商，默认这个字段会一直是空的，`EXTERNAL-IP` 显示 `<pending>`。本书的 lab 用 `cloud-provider-kind` 补上这个控制器，它监听 LoadBalancer Service，在 Docker 里创建 Envoy 容器做数据面，再把容器地址写回 status。示例里的 `api-lb` 因此能拿到一个真实可访问的地址；换到没有 LB 实现的裸金属集群，要么装 MetalLB 之类的实现，要么接受 `<pending>`。

`type: ExternalName` 是另一种东西：它没有 ClusterIP，也不经过 kube-proxy，只让集群 DNS 返回一条 CNAME 记录，指向 `spec.externalName`。客户端拿到的是外部域名，后续解析和连接都由客户端自己完成。因为 DNS 层只做别名，HTTP 的 `Host` 头和 TLS 证书仍然按客户端请求的名字来，目标服务器可能不认识这个名字；这是使用 ExternalName 时要注意的边界，不是配置错误。

最后是 `sessionAffinity`。默认是 `None`，每次新连接可以落到任意后端；设成 `ClientIP` 后，同一个客户端 IP 的连接会尽量落到同一个 Pod，`sessionAffinityConfig.clientIP.timeoutSeconds` 默认 10800 秒（3 小时）。它解决的是“有状态会话”这一类问题，不解决后端故障：Pod 挂了，亲和性不会把会话转移到别处，只会重新选一个可用后端。

## 23.2 EndpointSlice：Service 背后是什么

Service 对象本身只声明“选哪些 Pod、映射哪个端口”，它不保存后端 IP。真正被 kube-proxy 消费的是 EndpointSlice：EndpointSlice 控制器根据 Service 的 selector 找到 Pod，把 Pod 的 IP、端口、就绪状态和节点信息写进 `discovery.k8s.io/v1` 对象。一个 Service 可以对应多个 EndpointSlice，按地址族（IPv4/IPv6）、协议、端口和 Service 名分组；默认每个 slice 最多 100 个端点，`--max-endpoints-per-slice` 最大可以调到 1000。这个设计是为了在大规模集群里只更新变化的那一片，而不是每次重建一个包含上千地址的大对象。

每个端点在 `endpoints[]` 里至少有三类信息。`addresses` 是 IP 列表；`conditions` 里有 `ready`、`serving`、`terminating`，`ready` 基本等于“`serving` 为真且不在终止中”，但 Service 设了 `publishNotReadyAddresses: true` 时它会被强制为真；`nodeName` 和 `zone` 是拓扑信息，23.5 的拓扑感知路由和 `internalTrafficPolicy: Local` 都依赖它们。EndpointSlice 用 `kubernetes.io/service-name` 标签关联 Service，还带一个 `endpointslice.kubernetes.io/managed-by` 标签，控制器写的值是 `endpointslice-controller.k8s.io`；手工创建 EndpointSlice 给无 selector 的 Service 用时，应该换一个自己的值，不要冒充控制器。

旧的 `Endpoints` API 在 Kubernetes 1.33 标记为弃用。它仍然能用，`kubectl get endpoints` 也仍然会返回数据，但它不支持双栈、不能表达 `trafficDistribution` 需要的信息，端点超过 1000 个时还会截断。新代码和排障都应该先看 EndpointSlice；`kubectl get endpoints` 只作为和旧脚本、旧监控兼容的入口。

> **旧资料提示**：旧教程常把 Endpoints 说成 Service 的“buddy 对象”，排障时只看 `kubectl get endpoints`。EndpointSlice 在 1.21 成为 stable，Endpoints 在 1.33 标记弃用；新脚本和新排障流程应该用 `kubectl get endpointslice -l kubernetes.io/service-name=<名字>`，`get endpoints` 只用于兼容旧工具。

## 23.3 kube-proxy 的 iptables/IPVS/nftables

Service 的虚拟 IP 不是靠某个进程监听实现的，而是靠每个节点上的 kube-proxy 把转发规则写进内核。kube-proxy 监听 Service 和 EndpointSlice 的变化，为每个 Service 的 ClusterIP:port 建立一条入口规则，再为每个 ready 端点建立一条 DNAT 规则。三种 Linux 模式做的是同一件事，区别在于用哪套内核接口、规则的数据结构和更新成本。

`iptables` 模式是最长久、也是 Kubernetes 1.37 仍然默认的模式。它为每个 Service 建几条链，为每个端点再建几条：`KUBE-SERVICES` 按目的 IP/端口分流到 `KUBE-SVC-...`，`KUBE-SVC-...` 用随机或会话亲和选一个后端，跳到 `KUBE-SEP-...`，最后由 `KUBE-SEP-...` 做 DNAT，把目的地址改成 Pod IP。规则数量随 Service 和端点数量线性增长；几万个 Service/Pod 的集群里，一次变更可能要更新几万条规则，这是 iptables 模式的主要扩展性瓶颈。kube-proxy 用 `minSyncPeriod` 控制两次同步之间的最小间隔（默认 1s），把短时间内的多个端点变更合并成一次规则更新；`syncPeriod` 控制与单个 Service 变更无关的周期性检查，例如发现外部程序改坏了 kube-proxy 的规则。`minSyncPeriod` 调大能减少重复工作，但规则与 API 状态的不同步时间也会变长，默认值在多数集群里够用。

`ipvs` 模式把 Service 和后端放进内核 IPVS 的哈希表，规则同步和转发性能比 iptables 好，曾经是“大规模集群推荐模式”。这个说法今天已经不成立：IPVS 模式在 Kubernetes 1.35 标记弃用，1.40 起默认关闭（可以用 `KubeProxyIPVS` 特性门控重新打开），1.43 完全移除。官方文档给的理由很直接：IPVS 的内核 API 和 Kubernetes Service 的语义并不匹配，很多边界情况一直没能正确实现。新集群不应该再选 IPVS。

`nftables` 模式是官方给出的替代。它在 1.29 进入 alpha，1.31 进入 beta，1.33 成为 stable（特性门控 `NFTablesProxyMode`），要求内核 5.13 或更高。和 iptables 模式相比，它处理端点变更更快，包处理路径也更适合大量 Service；但 Kubernetes 1.37 的默认值仍然是 iptables，官方计划在未来的版本把默认值改成 nftables。升级集群时如果配置里没写 `mode`，默认值变化会让代理后端在升级后悄悄换掉，所以生产集群应该在 kube-proxy 配置里显式写死模式。

还有一个常见混淆：kube-proxy 不负责给 Pod 分配 IP。Pod IP 由 CNI 插件分配，kube-proxy 只负责“到 Service 的流量怎么转到已经存在的 Pod IP”。Pod 没有 IP、Pod 网络不通，是 CNI 的问题；Service 的 ClusterIP 有地址但没有后端，才是 EndpointSlice 或 selector 的问题。

在 nftables 模式下，这些链会变成 nftables 的 table/chain/set，逻辑仍然是“匹配 ClusterIP 和端口，选择端点，DNAT”。如果你在节点上只看到 `KUBE-SERVICES` 而没有对应的 nftables 规则，先确认 kube-proxy 的 `mode` 和节点内核，而不是直接认定 Service 配置错了。

kube-proxy 直接改内核规则，这也意味着它适合由理解后果的管理员运行，不适合和别的网络代理抢同一台节点。官方文档提醒：kube-proxy 写的规则在有些情况下不会自动清理，可能要等到节点重启；它虽然带一个 `cleanup` 功能，但那不是正式支持的接口。换模式或卸载 kube-proxy 之前，先确认节点上的旧规则不会和新的代理实现打架。

> **旧资料提示**：旧教程常写“ClusterIP 一定是 iptables 实现的”。这只在 kube-proxy 用 iptables 模式时成立；IPVS 和 nftables 模式同样实现 ClusterIP，规则形态完全不同。另一个过时说法是“IPVS 是推荐模式”，它在 1.35 已弃用，1.43 会被移除。

## 23.4 集群 DNS 的命名与解析

集群 DNS 解决的是“客户端不应该记住 ClusterIP，更不应该记住 Pod IP”。在 kind 里，CoreDNS 以 Deployment 运行，前面是一个名叫 `kube-dns` 的 ClusterIP Service；`kube-dns` 这个名字是历史兼容名，和 CoreDNS 的实现无关。kubelet 在每个 Pod 启动时改写它的 `/etc/resolv.conf`：`nameserver` 指向 `kube-dns` 的 ClusterIP，`search` 里放当前 namespace、`svc.cluster.local` 和 `cluster.local`，`options` 里放 `ndots:5`。

`ndots:5` 决定了一个名字先按“相对名”还是“绝对名”解析。名字里的点少于 5 个时，解析器会先依次拼接 `search` 里的后缀，全部失败后才把原名当成绝对域名再查一次。所以 `api` 会先变成 `api.shorty.svc.cluster.local`，`api.shorty` 会变成 `api.shorty.svc.cluster.local`（第一个 search 后缀不一定命中，后面会命中），而 `api.shorty.svc.cluster.local` 本身有 4 个点，仍然会先被 search 列表试一遍，最后才按绝对名解析。多出来的查询通常不可见，但在 DNS 负载高、或者名字本身是外部域名时，`ndots:5` 会让解析变慢，也会让 `search` 写错时出现“短名能通、全名不通”或相反的现象。名字末尾带点（例如 `api.shorty.svc.cluster.local.`）表示它已经是绝对域名，解析器不会再拼 search 后缀；在脚本和配置里写全限定名时，带上末尾的点可以避免一次多余的查询。

Service 的 DNS 记录分两种。普通 ClusterIP Service 的 A/AAAA 记录返回 ClusterIP；headless Service（`clusterIP: None`）的 A/AAAA 记录返回所有 ready 后端 Pod 的 IP。命名格式都是 `<service>.<namespace>.svc.cluster.local`，同一个 namespace 里可以省略 `<namespace>.svc.cluster.local`。SRV 记录还能带出命名端口，例如 `_http._tcp.api.shorty.svc.cluster.local`；这条记录在客户端需要“服务发现 + 端口号”时有用，普通 HTTP 客户端一般不用。

`dnsPolicy` 决定 Pod 的解析配置从哪来。默认是 `ClusterFirst`：先查集群 DNS，集群域名之外的名字转发给上游。`Default` 让 Pod 继承节点的 `/etc/resolv.conf`，不保证能解析 Service。`None` 完全忽略 Kubernetes 的 DNS 配置，必须自己写 `dnsConfig`。`hostNetwork: true` 的 Pod 如果仍写 `ClusterFirst`，会退化成 `Default`；要让这种 Pod 用集群 DNS，必须显式写 `ClusterFirstWithHostNet`。这是 hostNetwork Pod 经常“解析不了 Service 名”的原因。

`nslookup api.shorty.svc.cluster.local` 返回 api 的 ClusterIP，`nslookup api` 也返回同一个地址；后者能成立，是因为 search 域把它补成了完整名字。短名的原始输出会先打印 search 列表里其他候选域的 NXDOMAIN，中间给出 `Name:` 和 `Address:`，后面还跟着宿主机域的 SERVFAIL；示例只保留解析结果这两行。busybox 的 `nslookup` 只要任意一个候选域返回错误就以非 0 退出，不能拿退出码判断短名是否解析成功。最后查一个不存在的 `api.nope.svc.cluster.local`，CoreDNS 的 kubernetes 插件直接返回 `NXDOMAIN`，`nslookup` 同样以非 0 退出。这里特意把名字放在 `cluster.local` 里面：如果查的是 `api.nope` 这种看起来像外部域名的名字，查询会被转发给上游 DNS，而本书 lab 的上游会对未知名字返回一个通配地址，看起来像“解析成功”，其实不是集群 DNS 的答案。这个失败是预期的：`NXDOMAIN` 表示“这个名字不存在”，和“DNS 服务器连不上”是两回事；如果连 `kube-dns` 的地址都 ping 不通，先查 CoreDNS Pod 和 `kube-dns` 的 EndpointSlice，而不是改应用的域名。

DNS 排障的顺序应该是：先 `cat /etc/resolv.conf` 确认 `nameserver` 和 `search`；再 `kubectl -n kube-system get pods -l k8s-app=kube-dns` 看 CoreDNS 是否 Running；再 `kubectl -n kube-system get endpointslice -l kubernetes.io/service-name=kube-dns` 看 DNS Service 有没有后端；最后才看 CoreDNS 日志和上游 DNS。跳过前三步直接改 CoreDNS 配置，往往会把一个 namespace 或 search 域的问题放大成集群故障。

## 23.5 流量策略与拓扑感知

默认的 `internalTrafficPolicy: Cluster` 允许 kube-proxy 把请求转到集群里任意 ready 端点，哪怕那个 Pod 在另一个节点。`internalTrafficPolicy: Local` 把候选端点限制在“客户端 Pod 所在节点”：kube-proxy 按 EndpointSlice 里的 `nodeName` 过滤，只保留本节点的地址。好处是流量不出节点，延迟低、跨节点带宽省；代价是节点上没有这个 Service 的端点时，kube-proxy 没有可转发的目标，包会被丢弃。Service 对象仍然存在，ClusterIP 仍然能查到，但请求超时——这和“后端全挂了”表现很像，区别是只有部分节点上的客户端受影响。

`externalTrafficPolicy` 管的是从节点外部进来的流量，也就是 NodePort、LoadBalancer 和 ExternalIP。默认 `Cluster` 会把外部流量转到任意节点上的端点，转发过程中可能做一次 SNAT，客户端源 IP 会丢失。设成 `Local` 后，节点只把流量交给本节点的端点，不做 SNAT，客户端 IP 得以保留；但如果某个节点没有本地端点，它不会把流量转给别的节点，而是直接丢弃。云负载均衡器的健康检查会探测节点的 kube-proxy 端口，`Local` 下只有本节点有端点时健康检查才返回 200，没有端点的节点会被摘掉。这要求后端副本足够多、分布足够广；只有 1 个副本时，`externalTrafficPolicy: Local` 会把“副本所在节点之外的入口”全部变成不可用。

拓扑感知路由解决的是另一个维度的问题：同一个 zone 内的流量尽量留在 zone 内，但不要求“必须在同一节点”。给 Service 加 `service.kubernetes.io/topology-mode: Auto` 后，EndpointSlice 控制器按各 zone 可分配 CPU 的比例给端点写 `hints.forZones`，kube-proxy 按 hints 过滤。这个特性在 1.33 成为 stable（特性门控 `TopologyAwareHints`）。它有几个前提：每个 zone 至少 3 个端点时才容易分配得均匀（官方给的数字是少于 3 个时约 50% 的概率分配不均、回退到全集群路由）；`internalTrafficPolicy: Local` 的 Service 不会使用 hints；任何一个节点缺少 zone 标签或 CPU 信息、或者 hints 不完整，kube-proxy 都会回退到所有端点。新版还可以用 `spec.trafficDistribution: PreferSameZone` 或 `PreferSameNode` 表达同类偏好，语义比 annotation 更直接；两者同时设置时，annotation 优先。

要让 Pod 均匀分布到各 zone，调度侧用 `topologySpreadConstraints`；Service 的拓扑感知只负责“已经分布好的端点在解析和转发时优先选近的”，不能替你把 Pod 调度到正确的位置。这两个东西经常一起出现，但职责不同。

## 23.6 双栈与 ClusterIP 分配

IPv4/IPv6 双栈在 Kubernetes 1.23 成为 stable，1.21 起默认启用。要让一个集群真正双栈，几处配置必须同时成立：kube-apiserver 的 `--service-cluster-ip-range` 同时给 IPv4 和 IPv6 CIDR，kube-controller-manager 的 `--cluster-cidr` 和 `--service-cluster-ip-range` 同时给两份，kube-proxy 的 `--cluster-cidr` 也要有，裸金属节点还要给 kubelet 指定 `--node-ip=<IPv4>,<IPv6>`；CNI 也必须支持双栈。少任何一处，Service 可能只拿到一个地址族，或者 Pod 根本没有 IPv6 地址。

Service 用 `ipFamilyPolicy` 和 `ipFamilies` 控制地址族。`SingleStack` 是默认值，只分配第一个配置的 Service CIDR 的地址；`PreferDualStack` 在双栈集群里分配 IPv4 和 IPv6 两个 ClusterIP，单栈集群里退化成单栈；`RequireDualStack` 在双栈集群里同样分配两个，但在不支持双栈的集群里创建会直接失败。`ipFamilies` 的顺序决定哪个地址进旧的 `clusterIP` 字段，例如 `["IPv6","IPv4"]` 会让 `clusterIP` 取 IPv6。这个字段只能有条件地改：可以增加或删除次要地址族，不能改主地址族；把 `SingleStack` 改成 `PreferDualStack` 可以补上另一个族，反过来会只保留第一个。

ClusterIP 由 apiserver 从 Service CIDR 里分配，动态分配优先用地址段的上半部分，静态指定的地址应该从下半部分选。分配范围按公式 `min(max(16, cidrSize / 16), 256)` 划出静态段：`/24` 的静态段是前 16 个地址，`/20` 和 `/16` 是前 256 个。指定一个已经被占用的 `clusterIP` 会返回冲突错误；指定一个不在 Service CIDR 里的地址会返回 422。这个分配记录存在于控制面，集群扩容或迁移时不要手工改 Service CIDR，已经分配的地址不会自动重编。启用 `MultiCIDRServiceAllocator` 后，控制面用 `IPAddress` 和 `ServiceCIDR` 对象记录分配，可以通过新增 `ServiceCIDR` 对象扩大可用范围，IPv6 的掩码也可以小于传统的 /108；但这仍然是容量规划工具，不会把已有 Service 的地址搬到新段里。

`clusterIP: None` 是 headless Service 的写法，不是“留空”。留空会走动态分配，`None` 才表示不分配虚拟 IP、kube-proxy 不处理它、DNS 直接返回后端 Pod 的地址。StatefulSet 的稳定网络标识就依赖这个组合：`serviceName` 指向 headless Service，Pod 名加 Service 名构成 `<pod>.<service>.<namespace>.svc.cluster.local`。

## 23.7 排障：有 ClusterIP 却连不上

`Connection refused` 和超时是两种不同的失败。拒绝通常来自 kube-proxy 的 REJECT 规则：Service 存在、ClusterIP 有地址，但 EndpointSlice 里一个 ready 端点都没有，内核直接拒绝连接（表现为 `Connection refused`），客户端立刻失败。超时更像是包被丢弃：`internalTrafficPolicy: Local` 在本节点没有端点，或者 NetworkPolicy 把流量挡了，或者 CNI 路由不通。先分清这两种，再去查对应的层。

第一步永远是看 EndpointSlice，而不是先怀疑 DNS 或 kube-proxy。


`api-broken` 的 selector 写成了 `app.kubernetes.io/name: ap1`，所以 `kubectl get endpointslice -l kubernetes.io/service-name=api-broken` 虽然能看到一个 slice，但 `ENDPOINTS` 是 `<unset>`，展开后的 `endpoints` 是 `null`。对照 `kubectl get pods -l app.kubernetes.io/name=api`，Pod 明明是 Running；这说明问题不在 Pod，而在 Service 和 Pod 的标签没有对上。没有端点时，`wget` 得到 `Connection refused`，而不是超时；`kubectl get endpoints api-broken` 也显示 `<none>`，和 EndpointSlice 的结论一致。

把 selector 改成 `app.kubernetes.io/name: api` 后，EndpointSlice 里的 `ENDPOINTS` 重新出现，`wget` 恢复 `ok`。修复动作很小，但定位顺序很重要：如果先去重启 kube-proxy 或 CoreDNS，就会在一个纯粹的标签拼写错误上浪费很多时间。

selector 对了但仍然没有 ready 端点，下一个怀疑对象是 readiness。Pod 可以是 `Running`，但 `READY` 是 `0/1`：readinessProbe 失败时，EndpointSlice 里的端点会变成 `ready=false`，Service 不会把它算作可用后端。`kubectl get pods` 的 `READY` 列、`kubectl describe pod` 的 `Readiness probe failed` 事件、以及 `kubectl get endpointslice` 的 `conditions.ready` 要一起看。`publishNotReadyAddresses: true` 的 Service 是例外，它会把这些端点也发布出去，通常只用于 StatefulSet 的启动引导。

端口也要对。`port` 是 Service 的端口，`targetPort` 是容器端口；数字 `targetPort` 写错时 EndpointSlice 仍然有地址，但 DNAT 到了 Pod 上没有进程监听的端口，表现同样是 `Connection refused`。如果 `targetPort` 用的是命名端口，确认 Pod 的 `containerPort` 名字拼写一致；名字对不上时 EndpointSlice 的端口可能为空，Service 也不会有正确的后端。

DNS 报 `NXDOMAIN` 是另一条线。先确认查询的名字和 namespace：在 `shorty` 里查 `api` 能命中 `api.shorty.svc.cluster.local`，在别的 namespace 里查 `api` 就会 NXDOMAIN，必须写 `api.shorty` 或全名。再看 `/etc/resolv.conf` 的 `search` 和 `ndots`：search 域被改错、或者 Pod 用了 `dnsPolicy: Default`/`None`，短名就不会按预期补全。`NXDOMAIN` 说明 DNS 服务器正常回应了“不存在”，不是 CoreDNS 挂了；如果所有名字都超时，才去查 `kube-dns` 的 EndpointSlice 和 CoreDNS Pod。

如果 selector、EndpointSlice 和 readiness 都正常，但只有部分客户端失败，重点转向“路径”而不是“后端”：从哪个节点发起、那个节点有没有本地端点（`internalTrafficPolicy: Local`）、NetworkPolicy 是否允许这个方向、Pod 的 `targetPort` 在容器里是否真的在监听。在客户端 Pod 里对后端 Pod IP 直接发一次请求，可以快速区分“Service 转发坏了”和“后端本身不可达”；直接连 Pod IP 通、连 ClusterIP 不通，问题在 Service/kube-proxy；两者都不通，问题在 Pod、CNI 或网络策略。

最后才是 kube-proxy。只有当前两步都正常、节点上的规则却明显缺失时，才需要看 kube-proxy 的日志、`mode` 和节点上的 iptables/nftables 规则。把 kube-proxy 当成第一嫌疑人，通常是因为它的名字最像“负责网络的组件”，但 Service 排障里它排在 selector、EndpointSlice 和 readiness 之后。

## 上生产前

**用 Service 名做服务发现，不要在任何配置里写 Pod IP。** Pod 会重建、IP 会变，写死 Pod IP 的配置在下一次滚动更新后就失效。普通无状态服务用 ClusterIP Service 加 DNS 名；需要稳定身份和逐 Pod 寻址的（数据库、消息队列）用 headless Service 加 StatefulSet，让客户端按 `<pod>.<service>` 访问。环境变量也能提供 Service 地址，但它只在 Pod 创建时注入，Service 后建就不会出现在已有 Pod 里；DNS 没有这个顺序问题。

**生产优先 nftables，IPVS 不要再上新集群。** Kubernetes 1.37 的默认仍是 iptables，但 nftables 从 1.33 起 stable，端点多、变更频繁时更合适；升级前要在 kube-proxy 配置里显式写 `mode`，否则未来默认值切换会让代理后端在升级时变化。IPVS 在 1.35 弃用、1.40 默认关闭、1.43 移除，继续用它等于给自己安排一次迁移。切换模式后要重新检查 NodePort 的监听地址和主机防火墙，nftables 模式默认只在节点主 IP 上提供 NodePort。

**`externalTrafficPolicy: Local` 必须配足够的副本和分布。** 它保留客户端源 IP，但没有本地端点的节点会直接丢包；只有 1 个副本或所有副本挤在一个节点时，开启它会把一部分入口变成 503。配合反亲和性或 `topologySpreadConstraints` 把副本打散，用 PDB 保证滚动更新和驱逐时仍有足够副本。`internalTrafficPolicy: Local` 是类似的取舍：省掉跨节点流量，换来“本节点没有端点就失败”；适合 DaemonSet、本地缓存这类天然每节点都有副本的服务，不适合副本很少的关键 API。

**双栈要提前规划两套 CIDR，Service CIDR 不要事后改。** Service CIDR 是 apiserver 的启动配置，已经分配的 ClusterIP 不会因为改范围而自动重编；MultiCIDRServiceAllocator 允许通过 ServiceCIDR 对象增加地址段，但这是一次容量规划，不是无损迁移。Node CIDR、Pod CIDR、Service CIDR 三者不能重叠，IPv4 和 IPv6 各要一套；CNI、kube-proxy、kubelet 的 `--node-ip` 都要同时支持，缺一个就会得到“Pod 有 IPv6、Service 没有”的半双栈状态。

**把“没有 ready 端点”当成一等告警。** Service 的 ClusterIP 一直存在，`kubectl get svc` 永远好看；真正决定可用性的是 EndpointSlice 里的 ready 端点数和 `conditions.ready`。对关键 Service 监控端点数量、readiness 失败次数和 EndpointSlice 的变更，比监控 Service 对象本身更有意义。排障时按 selector → EndpointSlice → readiness → targetPort → kube-proxy 的顺序走，不要从最底层的规则开始猜。

| `nslookup` / `dig` | 在 Pod 里验证 DNS | 先看 `/etc/resolv.conf` 的 search 和 ndots |
| `kubectl -n kube-system get configmap kube-proxy -o yaml` | 看代理模式 | `mode` 为空表示用版本默认值 |

本章结束时，`shorty` 仍然是 `s3-stateful` 的布局，另外多了 `Service api-nodeport` 和 `Service api-lb`；api、worker、postgres、redis 都能用 Service 名互相访问，EndpointSlice 和 DNS 的验证已完成，DNS 调试 Pod 和 Local 策略的客户端已删除。下一章会在这个网络上装 CNI、写 NetworkPolicy，把“谁能访问谁”从默认全通改成默认拒绝。
