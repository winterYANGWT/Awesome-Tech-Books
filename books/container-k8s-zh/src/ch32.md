# 第 32 章 威胁建模与集群加固

shorty 现在“能跑”了：Gateway 把外网请求转给 api，HPA 按 CPU 扩副本，PSA 把不符合 `restricted` 的 Pod 挡在门外，NetworkPolicy 默认拒绝。前面几章的努力都围绕一条路径：请求从 apiserver 进来，先认证、再鉴权、再过准入，最后写进 etcd。可攻击者不一定走这条路。节点上的 kubelet 10250 端口可以直接 exec 进容器，etcd 2379 端口里躺着所有 Secret，containerd 的 socket 能启动新容器。apiserver 的审计、准入和 RBAC 在这三条路前面都看不见。

从攻击面看，集群有三个入口：apiserver、kubelet、etcd。从攻击者想拿到的东西看，也是三样：能当集群管理员用的凭据、节点上的 root、etcd 里的全部数据。apiserver 是正门，有 TLS、认证、授权、准入、审计一层层挡着；kubelet 和 etcd 常常被当成“内网的东西”而疏于配置，一旦能直连，绕过的正是 apiserver 最值钱的那几层控制。把这三个入口的信任边界画清楚，比背一堆加固命令更有用。

本章按 STRIDE 把威胁和攻击面列出来，然后沿着 apiserver 的正门做一次审计，再从 Pod 和节点外直连 kubelet 看它会返回什么，接着用 ResourceQuota 和 LimitRange 限制资源耗尽，检查静态加密与证书轮换，最后用 kube-bench 跑一次 CIS 基线。每一节都尽量落到一个能观察的结果上：审计日志里的一行、kubelet 返回的状态码、配额拒绝的报错、证书的到期时间、kube-bench 的 FAIL 项。

> **起点**：`s4-prod` 已就绪，集群是 1 控制面 + 2 worker；建集群时通过 kind 的 `kubeadmConfigPatches` 给 apiserver 加了审计参数，策略文件和日志目录从 lab 的 `/tmp/ch32-audit-*` 挂进节点，所以本章的集群比 `s4-prod` 多一份审计配置。一步到位：`bash code/ch32/setup.sh`。脚本还会预拉 `busybox:1.37`、`curlimages/curl:8.16.0`、`aquasec/kube-bench:v0.16.0`，后面的示例不再等镜像下载。

## 32.1 STRIDE 与攻击面

STRIDE 是一张检查表，不是一套工具。它把威胁分成六类：身份伪造（Spoofing）、篡改（Tampering）、否认（Repudiation）、信息泄露（Information disclosure）、拒绝服务（Denial of service）、提权（Elevation of privilege）。对着 Kubernetes 逐条问“这件事在这里长什么样”，比泛泛地说“要注意安全”更容易落到具体对象上。

| 威胁 | 在集群里的具体形态 | 先看什么 |
|---|---|---|
| 身份伪造 | 偷到 kubeconfig、ServiceAccount token、客户端证书或 bootstrap token；伪造 kubelet 身份 | 认证方式、token 有效期、证书私钥权限、`system:masters` |
| 篡改 | 改镜像 tag、往 registry 推同名镜像、改 ConfigMap/Secret、改准入 Webhook | 镜像 digest/签名、RBAC 的写权限、准入链、etcd 写权限 |
| 否认 | 审计没开、日志只留在节点上、日志可被有节点权限的人删改 | 审计策略、日志后端、日志外置与保留 |
| 信息泄露 | Secret 以 base64 存在 etcd、环境变量进日志、hostPath 读节点文件、`nodes/proxy` 读容器输出 | 静态加密、Secret 挂载方式、RBAC、节点访问 |
| 拒绝服务 | 一个 namespace 建满 Pod、耗尽 CPU/内存/Pod IP、CronJob 造出海量 Job、API 请求打满 apiserver | ResourceQuota、LimitRange、API 优先级和公平性、HPA 上限 |
| 提权 | `privileged: true`、`hostPath` 挂 `/`、`hostPID`/`hostNetwork`、`CAP_SYS_ADMIN`、runtime socket | PSA、securityContext、准入策略、节点隔离 |

攻击面则是另一张表：apiserver、kubelet、etcd、容器运行时、CNI、镜像供应链、CI。apiserver 是唯一有完整认证、授权、准入、审计的入口；kubelet 的 API 直接操作节点上的容器，默认配置还曾经允许匿名访问；etcd 保存全部 API 对象，任何被它信任的客户端证书都能读写全部数据；runtime socket 能启动新容器、进入现有容器，效果接近节点 root；CNI 和主机网络决定了 NetworkPolicy 能不能看见流量；镜像供应链和 CI 则在集群外面，决定了跑起来的镜像本身可不可信。

“攻击者最想拿到的三个入口”可以按价值排：第一是能当集群管理员用的凭据，拿到它就能创建 privileged Pod，再拿到节点；第二是节点 root，拿到节点就能读 kubelet 配置、etcd 证书、所有挂在该节点上的 Secret；第三是 etcd，拿到它等于拿到整个集群的状态，连 apiserver 都不用经过。三者常常是一条链：一个泄漏的 token 建出 privileged Pod，Pod 挂上 hostPath 拿到节点，节点上再读 etcd 客户端证书。

kubelet 直连比 apiserver 更危险，原因不在端口，而在它前面的控制少。apiserver 的请求会过认证、授权、准入和审计；kubelet 的 `/pods`、`/logs`、`/exec` 不走 Kubernetes 的准入，也不写 Kubernetes 审计日志。官方文档说得很直接：对 kubelet API 的直接访问不受准入控制影响，也不会被 Kubernetes 审计日志记录。只要网络能到 10250，攻击者就能枚举节点上的 Pod、读日志、在容器里执行命令；如果 kubelet 还开着匿名访问和 `AlwaysAllow`，连凭据都不需要。

etcd 更直接：它保存的是 API 对象的最终形态，Secret 也在里面。对 etcd 的访问通常只靠客户端证书，etcd 自己没有细粒度的授权模型，任何被它信任的证书都能读写全部数据。也就是说，读到 apiserver 的 etcd 客户端证书私钥，或者能签一张被 etcd 信任的证书，就等于拿到集群管理员权限，而且这条路径不经过 apiserver 的准入和审计。静态加密能挡住“只拿到 etcd 磁盘/快照”的人，但挡不住“拿到 etcd 客户端证书”的人，这两个威胁要分开防。

`kubectl get svc -A -o wide` 里有三条值得停下来看的记录。`api-nodeport` 是 `NodePort`，把 8080 映射到节点上的一个高位端口；`api-lb` 是 `LoadBalancer`，除了 8080 还分到一个 NodePort，`EXTERNAL-IP` 是 `<pending>`，因为 kind 里没有云负载均衡实现，换成云厂商就会填上地址；`shorty-gw-nginx` 也是 `LoadBalancer`，80 映射到另一个 NodePort，它是 Gateway 的数据面，不是 shorty 应用自己建的。NodePort 的默认范围是 30000–32767，这三个端口都落在这个区间里；具体端口每次创建都可能不同，`jq` 那段按类型筛出来的三行就是它们。

`kubectl get networkpolicy -A` 只有 shorty 一个 namespace 有策略：`default-deny` 选中所有 Pod，`allow-dns` 放行 DNS，`allow-api-db` 放行 5432，`allow-worker-redis` 放行 6379，`allow-gateway` 放行 8080。`describe allow-gateway` 把规则展开：入站 8080 只接受两类来源，一类是 shorty 里带 `app.kubernetes.io/part-of=shorty` 的 Pod，另一类是 Gateway 数据面；出站除了 8080，还允许到 `nginx-gateway` namespace 拿配置。

这三条 Service 加上这组策略，才构成完整的暴露面。只看 Service 类型会漏掉“谁能到节点 IP”；只看 NetworkPolicy 会漏掉“Service 已经在节点上开了端口”。`api-lb` 的 `<pending>` 也不等于“没有暴露”：NodePort 已经分配，节点 IP 加上分配到的那个端口就能到后端，是否有云负载均衡只影响外网入口。反过来，NetworkPolicy 是在 Pod 的 veth 上做的，Service 的 NodePort 只是 kube-proxy 的一条转发规则；策略放行的是“从哪些 Pod/namespace 来”，不是“从哪个 Service 来”。对 `hostNetwork` Pod，NetworkPolicy 的行为甚至是未定义的，有的 CNI 会忽略它，这部分在 32.3 会看到。

所以“暴露面”要分三层看：Service 的 `type` 和端口决定节点/外网有没有入口，NetworkPolicy 决定 Pod 这一层收不收，节点防火墙和云安全组决定外部能不能到节点 IP。三层里任何一层单独看都会得出错误结论。清单里的“限制 LoadBalancer 和 ExternalIP”说的也是这一层：不是所有 Service 都该用 `LoadBalancer`，用之前先问一句“这个入口真的需要公网地址吗”。

> **旧资料提示**：旧教程把 PodSecurityPolicy（PSP）和 Gatekeeper 当成唯一的策略方案。PSP 在 Kubernetes 1.25 已经被移除；Pod Security Admission 在 1.25 稳定，按 namespace 标签执行 `privileged`/`baseline`/`restricted` 三档。需要字段级校验时，ValidatingAdmissionPolicy 在 1.30 稳定，可以直接在 apiserver 里写 CEL 规则，不必先装一个 Webhook。PSA 负责“Pod 安全字段的粗档位”，VAP 负责“你关心的具体字段”，两者不是替代关系。

## 32.2 apiserver 访问与审计

apiserver 的请求要过三段：认证回答“你是谁”，授权回答“你能做什么”，准入在对象落盘前再看一眼内容。审计不是第四段，它横着切这三段：请求在 `RequestReceived` 时生成一个事件，响应头发出时可能生成 `ResponseStarted`（只有 watch 这类长请求才有），响应体发完生成 `ResponseComplete`，处理过程中 panic 则生成 `Panic`。每个事件按审计策略决定记不记、记多少，再写到后端。认证失败、授权失败、准入拒绝都会留下记录，这也是审计比应用日志更适合做安全事件回溯的原因。

审计策略由一组规则组成，请求按顺序和规则匹配，第一条匹配的规则决定这条事件的级别。级别有四个：`None` 不记；`Metadata` 只记请求的用户、时间、资源、动词、响应码等元数据；`Request` 再加请求体；`RequestResponse` 连响应体也记。`Request` 和 `RequestResponse` 对非资源请求不适用。策略文件必须至少有一条规则，没有 `rules` 的文件会被当成非法配置；完全不传 `--audit-policy-file` 时，apiserver 一条审计事件都不记。

本章用的策略在 `code/ch32/audit-policy.yaml` 里。它省略 `RequestReceived` 阶段，Secret 只记 `Metadata`，改 ConfigMap、Deployment、Role 这类对象时记 `Request`，其余请求记 `Metadata`。

把这个文件交给 apiserver 要两个参数：`--audit-policy-file` 指向策略文件，`--audit-log-path` 指向日志文件。只给策略不给日志路径，等于没有后端，事件不会落盘；`--audit-log-path=-` 表示写到标准输出。日志后端写 JSONlines，一行一个事件，配套的轮转参数是 `--audit-log-maxage`（保留天数）、`--audit-log-maxbackup`（保留文件数）、`--audit-log-maxsize`（单文件多少 MB 后轮转）。日志后端的默认模式是 `blocking`，写日志会阻塞请求处理；Webhook 后端默认是 `batch`，异步批量发送。两种后端都支持截断，默认关闭。

审计日志要外置。留在节点容器的可写层里，节点一重建就没了；有节点写权限的人也能改。生产里常见两种做法：Log 后端写到挂载出来的宿主机目录，再由节点上的采集器送走；或者直接用 Webhook 后端发给集群外的审计服务。官方文档提醒，控制面以 Pod 运行时，策略文件和日志目录都要用 `hostPath` 挂载，否则 apiserver 容器里看不到宿主机上的文件。

kind 把 kubeadm 的参数藏在 `kubeadmConfigPatches` 里。`apiServer.extraArgs` 加参数，`apiServer.extraVolumes` 把策略文件和日志目录挂进 apiserver 静态 Pod；节点的 `extraMounts` 再把 lab 里的文件挂进节点。本章的 `kind-3n-audit.yaml` 就是这么写的，`setup.sh` 在建集群前把策略复制到 `/tmp/ch32-audit-policy.yaml`，日志目录建在 `/tmp/ch32-audit-log`，所以日志落在节点外。

第一段 `grep` 从静态 Pod 清单里读到五个参数：策略文件是 `/etc/kubernetes/audit-policy.yaml`，日志是 `/var/log/kubernetes/audit/audit.log`，单文件 50 MB 后轮转，保留 1 天、2 个备份。`ls -l` 看到这个日志已经有几 MB，权限是 `600 root:root`；它落在 lab 的 `/tmp/ch32-audit-log`，不在节点容器的可写层里。

接着 `kubectl get secret shorty-db` 发出一次普通的读请求。`jq` 从日志里筛出 `objectRef.resource` 是 `secrets`、名字是 `shorty-db` 的那条，输出里有四样东西：`user` 是 `kubernetes-admin`，`verb` 是 `get`，`resource` 是 `secrets`，`code` 是 `200`。这四个字段正好回答“谁、做了什么、对什么、结果如何”。真实审计里还会看到 `sourceIPs`、`userAgent`、`requestReceivedTimestamp` 等字段，排障时用它们区分是人、是控制器还是某个 CI。

最后一条 `jq` 把 `requestObject` 和 `responseObject` 是否为 `null` 打出来，两个都是 `false`，说明这条事件是 `Metadata` 级别，Secret 的内容没有进日志。这是有意的：如果对 Secret 用 `RequestResponse`，日志本身就会变成一份明文 Secret，静态加密辛辛苦苦挡住的泄露，从审计日志又漏出去。需要还原“改了什么”的对象，比如 ConfigMap、Deployment、Role，才用 `Request` 记请求体。

策略改完要让 apiserver 重新加载。kube-apiserver 是静态 Pod，直接改 `/etc/kubernetes/manifests/kube-apiserver.yaml` 里的参数或挂载，kubelet 会发现文件变化并重建容器，效果就是重启 apiserver；用 kubeadm 管的集群则是改 `ClusterConfiguration` 后 `kubeadm upgrade` 或重新生成静态 Pod。重启期间 `kubectl` 会短暂连不上，等 `kubectl get --raw /readyz` 返回 `ok` 再继续。如果 apiserver 起不来，先看 `docker logs shorty-control-plane`，最常见的原因是审计策略 YAML 缩进错了或 `rules` 为空。

审计本身也有成本。官方文档说它会增加 apiserver 的内存占用，因为每个请求的审计上下文要留到响应结束；日志后端还是同步写，磁盘慢会直接拖慢请求。所以策略要按“需要什么”来写，不要一上来就 `RequestResponse` 全量；日志要轮转、要外置、要有人看。只开审计不设保留和告警，最后只会得到一堆没人读的文件。

> **旧资料提示**：旧教程里的 apiserver 有一个 `--insecure-port`，用明文 HTTP 暴露 8080 或 8081。这个参数在 Kubernetes 1.37 的 apiserver 上已经不存在，今天的 apiserver 只提供 HTTPS；kubeadm 的实现说明里仍显式写 `--insecure-port=0`，表示不要明文端口。看到要求打开 insecure port 的步骤，直接跳过。

## 32.3 绕过 apiserver 的风险

apiserver 的正门有完整的控制，但节点上还有几扇侧门。第一扇是静态 Pod：kubelet 会直接加载 `/etc/kubernetes/manifests` 里的清单，或者从指定 URL 拉清单，apiserver 不管理这些 Pod。能写这个目录的人可以改控制面组件的参数，也可以塞一个新 Pod 进去；如果用了非法的 namespace 名，这个 Pod 不会出现在 API 里，只能到节点上才看得见。即使静态 Pod 过不了准入，kubelet 也不会把它注册到 apiserver，但它仍然会在节点上跑。控制面组件本身就是静态 Pod，所以这扇门天然存在，只能靠文件权限和节点访问控制来守。

第二扇是 kubelet API。kubelet 通常在节点的 TCP 10250 上提供 HTTPS API，`/pods` 能列出节点上的 Pod，`/logs` 能读容器日志，`/exec` 能在容器里执行命令。对 kubelet 的直接访问不受 Kubernetes 准入控制影响，也不会被 Kubernetes 审计日志记录。也就是说，攻击者从 10250 进去，RBAC、PSA、VAP、审计这些在 apiserver 上的控制全都看不到。更隐蔽的是 `nodes/proxy` 子资源：通过 apiserver 访问 `nodes/proxy` 时，请求会被代理到 kubelet，`get` 动词并不是只读，官方文档明确说它授权访问可以在任意容器里执行命令的端点。

kubelet 的默认认证和授权很宽松。没有指定配置文件时，未被其他认证方式拒绝的 HTTPS 请求会被当成匿名请求，用户是 `system:anonymous`，组是 `system:unauthenticated`；授权模式默认是 `AlwaysAllow`，通过认证的请求一律放行。kubeadm 建集群时会把它改成 `authentication.anonymous.enabled: false`、`authentication.webhook.enabled: true`、`authorization.mode: Webhook`，所以未认证请求会拿到 401，认证通过但 RBAC 不允许的请求会拿到 403。老集群、手工搭的集群、某些托管环境不一定做了这个切换，这就是要实际打一次 10250 的原因。

第三扇是 etcd。etcd 监听 2379，Kubernetes 只把 apiserver 和备份工具当作合法客户端。对 etcd 的访问通常只靠客户端证书，etcd 没有一套被广泛采用的细粒度授权模型；任何被它信任的 CA 签出的客户端证书都能读写全部数据。读到 apiserver 的 etcd 客户端证书私钥，或者能签一张被 etcd 信任的证书，就能直接读 Secret、改 RBAC 规则、创建新工作负载，完全绕过 apiserver 的准入和审计。静态加密防的是“只拿到 etcd 磁盘或快照”的人，防不了“拿到 etcd 客户端证书”的人。

第四扇是容器运行时 socket。节点上的 containerd 或 Docker 通过 UNIX socket 接受 kubelet 的请求；能访问这个 socket 的人可以启动新容器、进入现有容器、挂载节点目录，效果接近节点 root。把 socket 通过 `hostPath` 挂进业务容器，等于把节点 root 交给这个容器；挂父目录、挂 `/var/run` 也一样。第五扇是 CNI 和主机网络：`hostNetwork: true` 的 Pod 和节点共用网络栈，能直接访问 127.0.0.1 上的 kubelet、etcd 和云元数据地址；NetworkPolicy 对 `hostNetwork` Pod 的行为是未定义的，有的 CNI 会忽略它。CNI 本身是集群级组件，攻破 CNI 就能改 Pod 网络规则。

对策要按“谁能到哪”来写，而不是只加一条 NetworkPolicy。控制面和 etcd 只放在内网，安全组/防火墙只放行 apiserver 的 6443 给需要的来源，kubelet 的 10250 和 etcd 的 2379 不对业务网段开放。kubelet 关闭匿名访问，认证用 Webhook 或证书，授权用 Webhook，只读端口设为 0；RBAC 里不要给 `nodes/proxy` 的通配权限，监控需要时给细粒度的子资源。etcd 用双向 TLS，CA 只用于 etcd，服务器证书和 apiserver 客户端证书的私钥按最高级别保护。节点 SSH 只给必要的人，运行时 socket 不挂给业务容器，PSA 或准入策略禁止 `privileged`、`hostPath`、`hostPID`、`hostNetwork` 这些字段。

如果这里拿到的是 `200` 和一大段 JSON，说明 kubelet 还允许匿名访问，而且授权模式很可能是 `AlwaysAllow`，这是需要立刻修的高危配置。如果拿到 `403`，说明请求被认证成了某个身份，但授权没通过，通常是匿名访问开着、授权已经换成 Webhook；这时还要看匿名身份为什么能通过认证。401 和 403 的区别在排障时很有用：401 是“没认出你是谁”，403 是“认出来了，但不允许”。

`grep` 从 kubelet 的配置里读到 `anonymous.enabled: false` 和 `authorization.mode: Webhook`，和 401 的结果对得上。kubelet 的客户端证书是另一套东西，由 kubelet 自己轮换，下一节会看到它不在 `kubeadm certs check-expiration` 的列表里。最后删掉这个临时 Pod；它只是为了演示“从集群里能到节点”，不是业务该有的配置。

这里还要看到一个连带问题：这个 Pod 用了 `hostNetwork`，它自己就绕过了 shorty 的 NetworkPolicy。`default-deny` 选中的是 shorty 里的 Pod，这个 Pod 在 `default` namespace，且共享节点网络栈；它访问 kubelet 的流量根本不过 Pod 的 veth。攻击者拿到“能创建 hostNetwork Pod”的权限，就已经绕过了一部分网络隔离。所以 PSA 的 `restricted` 档位会拒绝 `hostNetwork`，这不是多此一举。

## 32.4 网络、多租户与配额

Kubernetes 默认允许所有 Pod 互相通信，NetworkPolicy 才把这个默认反过来。多租户的第一条规则是每个 namespace 先放一个 `default-deny`，把入站和出站都关掉，再显式放行 DNS、应用依赖和入口。DNS 必须放行，否则 Service 名字解析不了，应用会表现成“网络不通”，实际是解析失败。跨 namespace 的访问也要显式放行，不要用空 `namespaceSelector: {}` 图省事，那等于对所有 namespace 开门；官方多租户指南明确建议给 namespace 打稳定标签，用标签选择器而不是空选择器。

NetworkPolicy 只解决网络这一层，多租户还要把另外几层叠上去：namespace 提供名字和对象边界，RBAC 限制谁能读写这个 namespace 里的对象，PSA 限制 Pod 能用哪些安全字段，ResourceQuota 限制这个 namespace 能消耗多少资源，LimitRange 给没写 requests/limits 的容器补默认值。任何一层单独用都不够：只做 NetworkPolicy，租户仍能建一百个 Pod 把节点压垮；只做配额，租户仍能挂 hostPath 读节点；只做 RBAC，租户仍能在自己的 namespace 里建 privileged Pod。

ResourceQuota 是 namespace 级的硬上限。`pods: "10"` 限制非终止状态的 Pod 总数，`requests.cpu: "2"` 限制所有非终止 Pod 的 CPU 请求之和；还可以限制 `requests.memory`、`limits.cpu`、`services`、`secrets`、`persistentvolumeclaims` 等。创建或更新违反配额时，apiserver 返回 403 Forbidden，错误里会写清楚 requested、used、limited 三个数。配额不会追溯：已经创建的 Pod 不会被赶走，改小配额也不会让现有用量立刻下降；它只拦新的创建和更新。

配额和 HPA 会互相牵制。HPA 想扩到 5 个副本，但 `pods` 或 `requests.cpu` 的配额只够 3 个，多出来的 Pod 会被拒绝，HPA 的状态里会看到 `FailedCreate` 或副本数上不去。上线前要把 HPA 的 `maxReplicas` 和配额一起算，不要只调其中一个。配额本身也是 API 对象，能改配额的人就能给自己扩额，所以要用 RBAC 或 VAP 限制对 ResourceQuota 的写权限。

LimitRange 解决另一个常见问题：Pod 没写 requests/limits 时，配额系统可能直接拒绝它，或者调度器只能按 0 请求处理。LimitRange 的 `defaultRequest` 和 `default` 会在准入阶段给容器补上默认值；它只对新建或更新的 Pod 生效，已经在跑的 Pod 不变。一个 namespace 里如果有多个 LimitRange，应用哪个默认值是不确定的，所以一个 namespace 只放一个默认值规则。LimitRange 不检查默认值之间的一致性，`default` 可能小于某个容器显式写的 request，最后 Pod 会调度失败，这一点要在清单里自己保证。

`quota.yaml` 建好之后，`describe resourcequota` 的表里能看到 `pods` 和 `requests.cpu` 两行：`pods` 一行是当前非终止 Pod 数，`requests.cpu` 是 300m，硬上限是 10 和 2。Pod 数会随 HPA 副本和 Job 留下的 Pod 变；300m 来自 api 的两个副本各 50m、postgres 100m、redis 50m、worker 50m，量级不变。

接着创建 `quota-filler`，它请求 1800m CPU。配额准入算出 300m + 1800m 超过 2 核，直接拒绝，错误里是 `exceeded quota`，并列出 requested、used、limited。这里没有创建成功任何 Pod，所以不会留下半成品；Deployment 这类控制器创建的 Pod 被拒时，控制器会重试并把 `FailedCreate` 写进 Deployment 的状态，现象是副本数上不去，而不是 `kubectl apply` 报错。

`LimitRange` 加在 `quota-filler` 之后。`defaulted-pod` 的容器故意不写 `resources`，创建后读它的 `resources` 字段，已经补上了 `requests.cpu: 50m`、`memory: 64Mi` 和 `limits.cpu: 200m`、`memory: 128Mi`。这两个默认值让新 Pod 既能过配额（有 requests 可算），又不会因为没写 limits 而变成 BestEffort。最后读配额对象的 `spec.hard`，`requests.cpu` 已经是 `4`；状态里的用量是异步更新的，读 spec 更稳定。

配额不是“资源足够”的证明。它只保证这个 namespace 不会超过自己那份额度，不保证节点上真的有这么多可分配资源；多个 namespace 的配额之和超过集群容量时，仍然会先到先得。真正的隔离要靠节点池、taint/toleration、优先级和抢占，配额只是第一道闸。对多租户来说，最稳的做法还是按信任级别拆集群：强隔离的租户单独一个集群，弱隔离的团队共享一个集群但各自一个 namespace。

## 32.5 静态加密、KMS 与证书

Secret 在 etcd 里默认是明文。`kubectl get secret -o json` 看到的 base64 只是编码，不是加密；能读 etcd 的人可以直接拿到明文。静态加密（encryption at rest）解决的是“etcd 的磁盘、快照或备份落到别人手里”这个威胁：apiserver 在写 etcd 之前把对象加密，读的时候再解密，etcd 只看到密文。它不解决“apiserver 主机被攻破”或“有人拿到 etcd 客户端证书”的问题，那两个威胁要靠主机加固和证书保护。

加密配置是一个 `EncryptionConfiguration` 对象，`resources` 列出要加密的资源，`providers` 是有序的提供程序列表。第一个 provider 用来加密新写入的数据；读取时按顺序尝试每个 provider，直到有一个能解密。`identity` 是明文，也是默认值；`aescbc` 是 AES-CBC 加 PKCS#7 填充，快但容易受密文填塞攻击，官方不推荐；`aesgcm` 最快，但每写入 20 万次必须轮换；`secretbox` 用 XSalsa20 和 Poly1305，强度高；`kms` 用封套加密，强度最高。KMS v2 从 Kubernetes 1.29 起稳定，KMS v1 从 1.28 起弃用、从 1.29 起默认禁用。

KMS 的封套加密分两层：apiserver 为每个对象生成数据加密密钥（DEK），用 DEK 加密对象，再用远端 KMS 里的密钥加密密钥（KEK）加密 DEK，最后把密文和加密后的 DEK 一起写进 etcd。KMS v2 为每个 apiserver 生成 DEK，KEK 轮换时种子也跟着轮换；KMS 插件以 gRPC 服务的形式跑在控制面主机上，通过 UNIX socket 和 apiserver 通信。用本地密钥时，密钥就在控制面主机的 `EncryptionConfiguration` 文件里，拿到 etcd 快照还要拿到这份配置才能解密；用 KMS 时，攻击者要同时攻破 etcd 和 KMS 才能拿到明文。

证书是另一个“平时不管、出事全挂”的地方。kubeadm 生成的客户端证书默认 1 年到期，CA 证书默认 10 年；`kubeadm certs check-expiration` 会列出 `/etc/kubernetes/pki` 里的客户端证书和 kubeconfig 里内嵌的客户端证书的到期时间、剩余时间，以及签发它的 CA。它不会列 `kubelet.conf`，因为 kubeadm 把 kubelet 配成自动轮换，证书在 `/var/lib/kubelet/pki` 下，kubelet 在当前证书快过期时自己生成新密钥、发 CSR、取回新证书。

`check-expiration` 的表里，`apiserver`、`apiserver-etcd-client`、`etcd-server`、`etcd-peer`、`front-proxy-client` 这些叶子证书的剩余时间都是 300 多天，CA 的剩余时间是 9 年左右。叶子证书每年都要续，CA 十年一换；如果集群超过一年没升级，叶子证书就会先过期。apiserver 的证书过期，`kubectl` 连不上；apiserver 访问 etcd 的客户端证书过期，apiserver 起不来；etcd 的 peer 证书过期，etcd 集群选不出 leader。这些现象看起来都像“集群突然全挂”，实际只是证书到期。

kubeadm 在控制面升级时会自动续所有证书，所以“每年至少升级一次”不仅是跟版本，也是续证书。也可以手动 `kubeadm certs renew`，多控制面要在每个控制面节点上执行；它用 `/etc/kubernetes/pki` 里的 CA 重新签，属性和 SAN 从现有证书读。由外部 CA 签的证书 kubeadm 管不了，要自己续。kubelet 的证书是另一套，`rotateCertificates: true` 时自动轮换；示例里能看到 `rotateCertificates: true` 和 `kubelet-client-current.pem` 这个指向最新证书的符号链接。

证书和密钥要按凭据管理：CA 私钥、apiserver 的 etcd 客户端私钥、kubelet 的客户端私钥，拿到任何一个都可能扩大攻击面。`check-expiration` 要定期跑，最好接进监控；到期前留出续期和滚动重启的窗口，不要等告警当天才处理。

> **旧资料提示**：旧教程说证书手工签发一次就不用管。kubeadm 生成的客户端证书默认 1 年到期，CA 默认 10 年；不升级控制面就要手动 `kubeadm certs renew`，kubelet 的客户端证书则靠 `rotateCertificates` 自动轮换。把证书当成一次性工作，是“集群突然全挂”的常见原因。

## 32.6 基线检查与加固清单

前面几节是按威胁挑重点，基线检查是反过来：拿一张公认的清单逐项跑，看看漏了什么。kube-bench 是最常用的 Kubernetes CIS 基线工具，它把 CIS Kubernetes Benchmark 的检查项写成 YAML，读节点上的 apiserver、controller-manager、scheduler、etcd、kubelet 配置和进程参数，输出 PASS、FAIL、WARN 和 INFO。它检查的是“节点和组件的配置”，不检查应用镜像里的漏洞，那部分要用 Trivy 这类镜像扫描器。

kube-bench 在 Kubernetes 里通常以 Job 跑，因为要读宿主机的 `/etc/kubernetes`、`/var/lib/kubelet`、`/var/lib/etcd`，还要看宿主机的进程表，所以 Pod 要 `hostPID: true` 并挂这些 `hostPath`。控制面的检查项只存在于控制面节点，Pod 必须用 `nodeSelector` 指到控制面并容忍 `node-role.kubernetes.io/control-plane:NoSchedule` 这个污点。这些字段和 PSA 的 `restricted` 档位直接冲突：`hostPID`、`hostPath` 都会被拒绝，所以 kube-bench 要放在一个不套 `restricted` 的独立 namespace，并且这个 namespace 的创建权限要收紧。

kind 环境有几个已知的偏差。节点是容器，没有完整的 systemd，`4.1.1` 这类“检查 kubelet service 文件权限”的项会直接 FAIL，另一些服务检查会跳过；`/etc/kubernetes` 在控制面节点上存在，但 worker 上没有，Job 调度到 worker 就只能跑节点检查，控制面项全是空的。CIS Benchmark 和 Kubernetes 版本不是一一对应，kube-bench v0.16.0 的配置目录里最新的是 `cis-1.24`，1.37 的集群也只能按这套检查项跑，报告里的编号不能当成 1.37 的官方基准。看到 FAIL 是正常的，关键是把每条 FAIL 归到“环境限制”“已知例外”“需要修”三类里。

除了 kube-bench，清单扫描可以用 kube-score 和 kubesec：它们读 YAML，不连集群，检查 securityContext、resources、探针、镜像 tag、RBAC 这些字段，适合放进 CI 的 `kubectl apply --dry-run=server` 之前。镜像扫描用 Trivy，查基础镜像和依赖里的 CVE；供应链再往前是签名和 SBOM，第 13 章已经做过。三类工具的输出要合在一起看，不能拿“kube-bench 通过”当成“应用也安全”。

`security-checklist` 把检查项分成认证与授权、网络、Pod 安全、Secret、镜像、准入控制器几组；`application-security-checklist` 则从开发者视角列了 ServiceAccount、securityContext、RBAC、镜像、NetworkPolicy。两份清单都明确说“清单本身不足以获得好的安全态势”，因为 Kubernetes 的安全不是一刀切，某些建议对特定业务可能过严或过松。落地时每条发现要有 owner、优先级和例外到期日：能修的排期修，暂时不能修的写清楚原因和到期时间，到期复查，而不是在报告上写一句“已知风险”就结束。

修两项。第一项是把 `default` ServiceAccount 的 `automountServiceAccountToken` 设为 `false`：shorty 里不需要访问 API 的 Pod 不再自动拿到 token，减少 token 泄露面。第二项是 32.4 加的 LimitRange，它让新容器即使没写 requests/limits 也有默认值，避免被配额拒绝或变成 BestEffort。两项都只影响新 Pod，已经在跑的 Pod 不会变；要验证生效，看 ServiceAccount 的字段和新 Pod 的 `resources`，不要看旧 Pod。

基线检查的结论要归档，不是跑完就丢。把 kube-bench 报告、kube-score/kubesec 输出、Trivy 结果按日期存起来，和上一版对比，才能看出“这次修了什么、又新出了什么”。扫描通过只说明“这次扫描的规则没发现问题”，不说明系统绝对安全；规则会漏、配置会漂、新 CVE 会出现，定期重跑和人工复核都不能省。

## 32.7 排障：kube-bench、审计与 apiserver

kube-bench 的 Job 失败或没有输出，先分三层查。第一层是 Pod 有没有跑起来：`kubectl -n kube-bench get pods -o wide` 看它调度到了哪个节点、是不是 `Completed`；如果一直 `Pending`，多半是 `nodeSelector` 写错或没容忍控制面的污点。第二层是 Pod 有没有权限读宿主机：`hostPID` 是不是 `true`，`/etc/kubernetes`、`/var/lib/kubelet` 这些 `hostPath` 有没有挂上；如果 Pod 在 PSA `restricted` 的 namespace 里，`hostPID` 和 `hostPath` 会被准入直接拒绝，Job 对象在、Pod 却建不出来。第三层是节点上有没有东西可读：worker 节点没有 `/etc/kubernetes`，调度到那里只能跑节点检查，控制面项会是空的；kind 还缺 systemd，一些检查会跳过。

审计日志没有内容，先确认 apiserver 真的带上了参数。`docker exec shorty-control-plane grep audit /etc/kubernetes/manifests/kube-apiserver.yaml` 看 `--audit-policy-file` 和 `--audit-log-path` 在不在；再看 `ls -l` 的路径和挂载是否一致，策略文件是不是挂进了 apiserver 容器。策略文件里 `rules` 为空、缩进错了、`level` 拼错，都会让 apiserver 起不来或一条不记。日志后端默认是 `blocking`，如果文件写不进去，请求也会受影响，所以路径的权限和磁盘空间也要看。

apiserver 起不来，先看节点容器的日志：`docker logs shorty-control-plane`。kube-apiserver 是静态 Pod，kubelet 会不断重建它，节点日志里能看到容器退出和 kubelet 的报错；最常见的根因是审计策略 YAML 格式错误、`--audit-policy-file` 指向的文件不存在、挂载路径写错。改完清单后用 `kubectl get --raw /readyz` 循环等它恢复；如果 `kubectl` 完全连不上，就看 `docker exec shorty-control-plane crictl ps -a` 里 apiserver 容器是不是在反复重启，再回到节点日志找原因。


示例先看正常的 kube-bench Pod：`get pods -o wide` 能看到它在 `shorty-control-plane` 上 `Completed`；`jsonpath` 打出 `hostPID` 是 `true`，`etc-kubernetes=/etc/kubernetes`，说明它确实按预期挂了宿主机的配置目录。`docker exec ... test -d /etc/kubernetes` 再确认节点上这个目录存在；如果这里返回非 0，kube-bench 就只能跑节点检查。

接着把同样的 `hostPID` 和 `hostPath` 放进 `shorty`，PSA 在创建 Pod 时直接拒绝，错误里写 `violates PodSecurity "restricted:latest"` 并点名 `host namespaces` 和 `hostPath`。这就是“Job 失败/无输出”的一个典型原因：Job 本身创建成功，但它管理的 Pod 被准入挡住，`kubectl get pods` 里没有 Pod，只有 Job 的 Event 或 `FailedCreate`。排障时不要只盯 Job 的 `status`，要往下看它创建的 Pod 和 Event。

最后两段是审计排障的入口：`grep` 确认 apiserver 清单里有 `--audit-policy-file` 和 `--audit-log-path`，`ls` 确认日志文件存在；`docker logs shorty-control-plane | tail` 在示例里没有输出，这说明节点容器的 stdout 不一定有内容，看到空白不代表 apiserver 没问题。要进节点用 `crictl ps -a` 找到 apiserver 容器，再用 `crictl logs` 看它的输出，或者看 `/var/log/pods` 下的对应目录；`docker logs` 只是入口，不是唯一证据。

排障的顺序可以固定成“对象 → 控制器 → 节点 → 组件”四层：先看 API 对象和 Event，再看控制器为什么没建出 Pod，再看 Pod 调度到哪个节点、节点上的运行时和 kubelet 是否正常，最后看组件自己的日志。kube-bench、审计、apiserver 这三类问题分别落在控制器、节点、组件层，按这个顺序走，比一上来就重启 apiserver 有效。

## 上生产前

控制面和 etcd 只放内网。apiserver 的 6443 只对需要的来源开放，kubelet 的 10250 和 etcd 的 2379 不对业务网段开放；云上用安全组，自建用防火墙，规则要跟着节点增减走。kubelet 关闭匿名访问，认证用 Webhook 或证书，授权用 Webhook，只读端口设为 0。节点 SSH 只给必要的人，最好走堡垒机；运行时 socket 不挂给业务容器，PSA 或准入策略禁止 `privileged`、`hostPath`、`hostPID`、`hostNetwork`。

审计要开、要外置、要有人看。策略按需要选 `Metadata` 或 `Request`，Secret 不要用 `RequestResponse`；日志走宿主机目录加采集器，或者 Webhook 送到集群外，设置轮转和保留期。静态加密优先用 KMS v2，密钥不跟 etcd 快照放在一起；用本地密钥时，`EncryptionConfiguration` 的权限要收到只有 apiserver 能读。证书要定期 `kubeadm certs check-expiration`，每年至少升级一次控制面，让 kubeadm 顺手续期；外部 CA 签的证书要自己排期。

网络和资源的上限要一起设。每个 namespace 先 `default-deny`，再显式放行 DNS 和依赖；跨 namespace 用稳定标签，不要用空 `namespaceSelector`。`ResourceQuota` 防一个 namespace 吃光集群，`LimitRange` 给没写 requests/limits 的容器补默认值，PSA 按信任级别选 `baseline` 或 `restricted`。强隔离的租户单独一个集群，弱隔离的团队共享集群但各自 namespace；不要把“同一个集群里的不同 namespace”当成硬多租户。

基线检查要定期跑，发现项要有 owner、优先级和例外到期日。kube-bench 的报告、kube-score/kubesec 的清单扫描、Trivy 的镜像扫描结果按日期归档，和上一版对比；不要因为某次扫描通过就认为系统绝对安全。规则会漏、配置会漂、新 CVE 会出现，扫描只是把已知问题摆到桌面上，修不修、什么时候修，还是要人来做决定。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `kubectl get svc -A -o wide` | 找 NodePort/LoadBalancer 暴露面 | 默认类型是 ClusterIP；NodePort 默认 30000–32767 |
| `kubectl get networkpolicy -A` | 看默认拒绝和放行规则 | 需要支持 NetworkPolicy 的 CNI |
| `--audit-policy-file` / `--audit-log-path` | 开审计、指定策略和日志 | 不传策略就不记事件 |
| `level: None/Metadata/Request/RequestResponse` | 每条规则记多少 | 第一条匹配的规则生效 |
| `--audit-log-maxage/maxbackup/maxsize` | 审计日志轮转 | 按磁盘和保留要求设置 |
| `kubeadm certs check-expiration` | 查 kubeadm 管理的证书到期 | 不含自动轮换的 kubelet 证书 |
| `kubeadm certs renew` | 手动续证书 | 多控制面要逐台执行 |
| `EncryptionConfiguration` 的 `providers` | 静态加密 | 第一个 provider 加密新数据，`identity` 是默认 |
| `ResourceQuota` / `LimitRange` | namespace 资源上限 / 默认 requests、limits | 配额拒绝返回 403 |
| `kubectl auth can-i` | 问某个身份能不能做某个动作 | 只做授权判断，不实际读对象 |
| `kubectl get --raw /readyz` | 看 apiserver 是否就绪 | 重启后循环等到 `ok` |
| `kubectl -n kube-bench logs job/kube-bench` | 读 CIS 报告 | Job 需要 hostPID 和 hostPath |

本章结束时，`s4-prod` 的主链路不变，shorty 多了一个 `ResourceQuota`、一个 `LimitRange` 和一份 kube-bench 报告；审计日志在集群外，证书检查记录和加固清单归档。下一章从这里开始扩展 API。
