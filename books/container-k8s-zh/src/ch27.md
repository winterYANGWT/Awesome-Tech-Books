# 第 27 章 ConfigMap 与 Secret，以及外部 secret 管理

shorty 的 api 镜像里没有数据库地址，也没有密码。连接串的地址来自 `shorty-config`，密码来自 `shorty-db` 挂进容器的文件。这样改一个日志级别、换一个上游地址，不需要重新构建镜像，也不需要重新推送镜像；但配置和密码一旦离开镜像，就多出了一组新问题：它们怎么进容器，改了以后容器里什么时候能看到，谁能读到它们，以及集群把它们存在哪里。

先看两个具体现象。把 `shorty-config` 里的 `SHORTY_BASE_URL` 从 `http://api:8080` 改成 `http://shorty.local`，已经运行的 api 进程不会自己变，必须让 Pod 重启；换成 volume 挂载，文件最终会变，但进程仍然不会自动重读。另一个现象是 `kubectl get secret shorty-db -o yaml` 里的 `db_password` 是一串 base64，看起来“加密”了，`base64 -d` 就能还原。前一个现象是注入方式和热更新的边界，后一个是 Secret 的安全模型。

Kubernetes 把这两类数据拆成两个对象：ConfigMap 放非敏感配置，Secret 放密码、token、证书这类需要限制读取范围的数据。两者的 API 形状几乎一样，都是键值对，都能通过环境变量或文件进容器；差别在于 Secret 在传输、落盘、RBAC 和审计上会被额外对待，而 ConfigMap 不会。把密码放进 ConfigMap 不会报错，但会把“需要额外保护”这个信息丢掉。

本章从 `s3-stateful` 出发。第 18 章已经建了 `shorty-config`，第 21 章建了 `shorty-db` 并把密码文件挂进了 postgres、worker、api 和迁移 Job；到本章起点，拆分只完成了一半：配置和密码确实不在镜像里，但 api 用的是最省事的 `envFrom` 整包注入，Secret 的挂载、热更新、不可变性和读取权限都还没有单独检查过。本章把这些边界补齐，再看生产上怎么把 secret 放到集群外。

> **起点**：本章从 `s3-stateful` 开始。单节点 kind 集群的 `shorty` 命名空间里有 `ConfigMap shorty-config`、`Secret shorty-db`，api 2 副本通过 `envFrom` 读取整个 ConfigMap，并把 `shorty-db` 挂到 `/etc/shorty`，密码文件是 `/etc/shorty/db_password`；postgres 是 StatefulSet `postgres`，PVC `data-postgres-0` 已绑定。一步到位：`bash code/ch27/setup.sh`。

## 27.1 ConfigMap：非敏感配置

把配置写进镜像的代价，不是“镜像大了一点”，而是每次改配置都要走一遍构建、推送、拉取、滚动更新。配置和代码的发布节奏本来就不一样：日志级别可能为了排查问题临时调高，上游地址可能因为一次迁移而改，功能开关可能按环境不同。把它们塞进镜像，等于把两种节奏绑死。ConfigMap 把配置从镜像里拿出来，变成一个可以在 API 里单独读写的对象；镜像只保留“怎么读配置”的代码。

ConfigMap 的对象结构和其他资源不同，它没有 `spec`，顶层是 `data` 和 `binaryData`。`data` 放 UTF-8 字符串，值可以是一行，也可以是一整个配置文件；`binaryData` 放二进制，值必须是 base64 编码的字符串。两个字段都可选，但同一个 key 不能同时出现在两边。名字必须是合法的 DNS 子域名，key 只能由字母、数字、`-`、`_`、`.` 组成。单个 ConfigMap 的数据不能超过 1 MiB，超过这个大小的配置应该放到独立的文件服务或数据库，而不是硬塞进 API 对象。

创建 ConfigMap 有两条路。声明式是写 YAML 再 `kubectl apply`；命令式是 `kubectl create configmap`，数据来自目录、文件或字面量。`--from-file` 把文件名当 key、文件内容当 value，也可以写成 `--from-file=key=path` 指定 key；`--from-literal` 直接给键值对，适合少量标量。目录方式只收普通文件，子目录、符号链接和设备会被忽略，文件名不合法时命令可能失败但不一定打印错误，所以批量导入前先看一眼目录里有什么。

配置进容器有四种方式：写在 `command`/`args` 里、作为环境变量、作为只读卷里的文件，或者应用自己调用 API 读。前三种由 kubelet 在启动容器时把数据交给容器，最后一种要在代码里实现 watch 或轮询。环境变量有两种写法：`envFrom.configMapRef` 把整个 ConfigMap 的 key 都变成环境变量，`env.valueFrom.configMapKeyRef` 只挑一个 key，并且可以把环境变量名改成和 key 不同。卷挂载则把每个 key 变成一个文件，文件名就是 key；可以用 `items` 只投射部分 key，用 `defaultMode` 控制权限，用 `subPath` 只挂一个文件。

`immutable: true` 是 ConfigMap 的另一个开关。Kubernetes 1.19 引入这个字段，1.21 成为 stable；标记之后不能改 `data`/`binaryData`，也不能把 `immutable` 改回 false，只能删除重建。它能防止误改；kubelet 也不必再 watch 这些对象的变化，在有大量 ConfigMap 的集群里能明显减轻 kube-apiserver 的负载。代价是更新流程变成“建新名字、切流量、删旧对象”，27.4 会演示这个流程。

> **旧资料提示**：旧教程常把 ConfigMap 当成“会自动同步的配置中心”，挂上卷就期待进程立刻读到新值。官方文档的措辞是卷里的内容“最终”会更新，环境变量则不会更新；应用进程也不会自动重读文件。需要热加载就自己在进程里 watch 文件或发信号，否则重启 Pod 是最可靠的办法。


## 27.2 Secret：敏感数据

Secret 和 ConfigMap 的用法几乎一样：都是键值对，都能用 `envFrom`、`valueFrom` 或卷挂载进容器。差别在 API 对它的处理。Secret 的值在 `data` 里必须是 base64 编码的字符串；如果不想手工编码，可以写 `stringData`，API 收到后把它合并进 `data`，同名 key 以 `stringData` 为准。`stringData` 只是写入时的便利字段，读回来时不会出现；它和服务端 apply 配合得不好，用 SSA 管理 Secret 时应该直接写 `data`。`data` 和 `stringData` 的 key 规则、1 MiB 大小限制和 ConfigMap 一样。

`type` 字段决定 Secret 的用途和校验规则。不写 type 或写空字符串，按 `Opaque` 处理，`kubectl create secret generic` 建的就是这种。`kubernetes.io/dockerconfigjson` 放 `~/.docker/config.json` 格式的镜像仓库凭据，key 必须是 `.dockerconfigjson`，kubelet 用它拉私有镜像；`kubernetes.io/tls` 放证书和私钥，key 必须是 `tls.crt` 和 `tls.key`；`kubernetes.io/basic-auth` 要求 `username` 和 `password`；`kubernetes.io/ssh-auth` 要求 `ssh-privatekey`。`kubernetes.io/service-account-token` 是旧式的长期 token，今天创建 ServiceAccount 时不会再自动生成这种 Secret，Pod 默认拿到的是 TokenRequest 签发的短期投射 token，27.6 会看这个变化。

创建 Secret 的常用命令是 `kubectl create secret generic`，数据来自 `--from-literal` 或 `--from-file`。`--from-file` 的文件内容会原样编码，文件末尾多一个换行，解码后就多一个换行；用 `echo -n` 或 `printf` 写文件可以避免。`kubectl create secret docker-registry`、`kubectl create secret tls` 是另外两个专用子命令，分别生成 `dockerconfigjson` 和 `tls` 类型。Secret 的名字必须是合法的 DNS 子域名，和 ConfigMap 一样。

Secret 挂成卷时，kubelet 把数据放在 `tmpfs` 里，不写节点的非易失存储；Pod 删除后，kubelet 删掉本地副本。卷里的每个 key 是一个文件，默认权限 `0644`，可以用 `defaultMode` 改整个卷、用 `items[].mode` 改单个 key。权限位是 POSIX 权限，不是加密；能读这个文件的进程就能拿到明文。Secret 只会被送到需要它的节点，但同一节点上的特权容器可以看到该节点上所有被使用的 Secret，官方文档把这一点写成了明确的警告。

`shorty-db` 的 type 是 `Opaque`，`data.db_password` 是 `c2hvcnR5LWRldi1wYXNzd29yZA==`，解码后 19 个字节。临时 Secret `demo-login` 的 `password` 是 `UzNjcmV0IQ==`，`base64 -d` 直接打印出 `S3cret!`。这两组输出说明 base64 只是编码：它让值在 YAML 里不直观，但不提供任何密钥，任何人拿到这段字符串都能还原。把 Secret 清单提交到 Git，等于把密码提交到 Git，只是换了一种写法。

api 的卷参数是 `/etc/shorty shorty-db 292`。`292` 是十进制，换成八进制是 `0444`，即所有用户只读、属主不可写；`defaultMode` 在 YAML 里写 `0444` 就是让它以八进制解析。Secret 卷的文件权限最终由 kubelet 设置，容器的 `securityContext`、`fsGroup` 和 CSI 驱动都可能影响实际结果，排障时以容器里 `ls -lL` 看到的为准，不要只看清单。

busybox Pod 里，`env | grep PASSWORD` 只匹配到 `SHORTY_DB_PASSWORD_FILE=/etc/shorty/db_password`，没有 `SHORTY_DB_PASSWORD`；密码文件 19 字节，权限 `-r--r--r--`，挂载类型是 `tmpfs`。`SHORTY_DB_PASSWORD_FILE` 这个名字里含有 `PASSWORD`，所以用 `grep PASSWORD` 判断“有没有密码”会误判；要判断明文密码有没有进环境变量，应该匹配 `^SHORTY_DB_PASSWORD=` 这个完整赋值。api 的代码只读 `SHORTY_DB_PASSWORD_FILE` 指向的文件，把文件内容拼进连接串，启动日志里的 `db_url` 用 `***` 遮住密码；这样密码不会出现在 `kubectl describe pod` 的环境变量里，也不会出现在进程的 `environ` 里。

Secret 卷挂到 `/etc/shorty` 而不是 `/run/secrets`，是本书实验环境的一个具体选择。Debian/Alpine 镜像里 `/var/run` 通常指向 `/run`，kubelet 又把 ServiceAccount token 投射到 `/var/run/secrets/kubernetes.io/serviceaccount`；把 Secret 卷挂到 `/run/secrets` 会和这个路径冲突，runc 报 `create mountpoint ... read-only file system`。换一个不和 token 路径重叠的目录就能避开，这不是 Kubernetes 的通用规则，但排障时值得先想到。

> **旧资料提示**：旧教程里常看到每个 Pod 自动挂一个 `default-token-*` Secret。Kubernetes 1.24 起不再自动创建这种长期 token Secret，Pod 默认通过 TokenRequest 拿到有有效期、会自动轮换的投射 token；用 `kubectl get secret` 找不到 `default-token-*` 是正常现象，不是集群坏了。


## 27.3 注入方式与热更新边界

配置进容器的方式决定了它什么时候更新。环境变量是在容器启动时由 kubelet 解析成进程环境的一部分，进程运行期间不会再变；ConfigMap 或 Secret 更新后，已经在跑的容器里还是旧值。卷挂载不一样：kubelet 周期性同步卷内容，ConfigMap/Secret 更新后，挂载目录里的文件最终会变；但“文件变了”和“进程读到新值”是两件事，进程不重新打开文件、不重新解析配置，就仍然按旧值工作。

卷更新的延迟不是一个固定秒数。kubelet 每次周期同步时检查挂载的 ConfigMap 是否新鲜，但它可能用 watch、TTL 缓存或直接向 API server 查询，具体由 `configMapAndSecretChangeDetectionStrategy` 决定，默认是 watch。官方文档给的估算是最长等于 kubelet 同步周期加上缓存传播延迟；任务页按默认值举例，同步周期约 1 分钟、缓存 TTL 约 1 分钟，所以最坏要等两分钟左右。更新 Pod 的注解可以触发一次立即同步，这是文档给出的加速手段，但不是应用层的热加载。

`subPath` 是另一个边界。用 `subPath` 把 ConfigMap 里的单个文件挂到容器里时，kubelet 不会把后续更新写进这个挂载点；文件在容器生命周期内保持挂载时的内容。要热更新就挂整个目录，让每个 key 变成目录里的文件；如果应用只认一个固定路径，可以在应用侧读目录里的文件，或者接受 `subPath` 不更新、靠重启生效。

应用进程本身也不会自动重读配置。改完 ConfigMap，进程要么收到 SIGHUP 之类的信号后重新加载，要么由外部控制器重启 Pod，要么自己 watch 文件变化。Kubernetes 没有“配置变更自动通知进程”的机制；`checksum/config` 注解是社区常见的做法：把 ConfigMap 内容的哈希写进 Deployment 的 Pod 模板注解，配置一变，注解变，Pod 模板变，Deployment 就滚动更新。这个注解不是 Kubernetes 内置字段，`kubectl apply` 不会自动算哈希；工具可以在渲染清单时把配置的哈希写进注解，关键是让 Pod 模板带上配置版本的指纹。

## 27.4 不可变对象与版本化

`immutable: true` 把 ConfigMap 或 Secret 变成只读对象。它的价值不在于“多一个开关”，而在于把配置更新从“原地改一个字段”变成“创建新版本、切换引用”。原地改配置的风险是：改错了很难回滚，多个 Pod 可能在某个时间点读到不同的值，审计记录里也只有一个对象被反复覆盖。不可变对象让每次配置变更都有一个独立的、可追溯的对象。

标记为 immutable 之后，`data` 和 `binaryData` 都不能再改，`immutable` 本身也不能从 true 改回 false；唯一的更新方式是删除再创建。官方文档特别提醒：已有 Pod 仍然保持着对被删除 ConfigMap 的挂载点，所以删了之后应该重建这些 Pod。这个提醒也解释了为什么“删了同名重建”不适合作为生产更新手段：旧 Pod 不会自动切到新对象，同名的删除和创建之间也没有一个原子切换点。

更稳的做法是版本化名字。配置从 `shorty-config` 变成 `shorty-config-v2`，Deployment 的 Pod 模板引用新名字；新 Pod 用新对象启动，旧 Pod 继续用旧对象，滚动完成后再删旧对象。名字里可以带版本号、日期或内容哈希，只要保证“同一份配置对应同一个名字”。这样回滚就是切回旧名字，不需要去猜某个字段原来是什么。

`checksum/config` 注解是另一层。它把配置内容的哈希写进 Pod 模板的 `metadata.annotations`；配置变，哈希变，Pod 模板变，Deployment 就滚动更新。这个注解不是 Kubernetes 内置的，API server 不会替你计算；具体哈希由生成清单的工具算，GitOps 工具则依赖清单本身的 diff。无论哪种方式，触发滚动的都是“Pod 模板变了”，不是“ConfigMap 变了”。

删掉 `shorty-release` 后，例子创建的是 `shorty-release-v2`，不是同名重建。然后 `kubectl patch --type=json` 改三处：Pod 模板的 `release` 标签改成 `green`，`checksum/config` 注解改成 `green`，容器的 `envFrom` 指向 `shorty-release-v2`。`rollout status` 等到新副本可用，新 Pod 的 `printenv RELEASE` 是 `green`。这三个改动里，真正让新 Pod 读到新值的是 `envFrom` 的名字；标签和注解是给选择和触发滚动用的。

这个例子是先删旧对象再建新对象，因为旧的 Pod 还在跑，删掉 ConfigMap 不会立刻中断它；生产上顺序应该反过来：先建新版本，改 Deployment 引用新版本，等滚动完成，再删旧版本。先删后建会留下一个窗口：如果此时有新 Pod 被调度，它引用的对象已经不存在，会起不来（env 引用是 `CreateContainerConfigError`，卷引用是 `ContainerCreating`/`FailedMount`）。27.7 会看这个错误。

版本化也影响回滚。Deployment 的 `rollout undo` 回滚的是 Pod 模板，模板里的 `envFrom` 指回旧名字，旧 ConfigMap 只要还在，回滚就能成功；如果旧 ConfigMap 已经删了，模板回滚过去也起不来。所以删旧版本之前，先确认没有回滚需求，或者保留足够的版本。GitOps 下这些对象都在 Git 里，回滚是 revert 一个 commit，而不是在集群里 `kubectl edit`。


## 27.5 外部 secret 管理

Secret 放在集群里，解决了“密码不进镜像”，但没有解决“密码从哪来、谁来轮换、谁能审计”。如果密码是运维手工 `kubectl create secret` 写进去的，它通常还会在某个人的笔记本、CI 变量或聊天记录里留一份；轮换时靠人记得改，改完还要记得重启工作负载。生产上的目标是把 secret 的“源头”放到一个专门管理密钥的系统里，Kubernetes 只拿短期凭据或同步后的副本。

[External Secrets Operator（ESO）](https://external-secrets.io/)是其中一种落地方式。它在集群里运行控制器，定义 `SecretStore` 或 `ClusterSecretStore` 描述“去哪里取、用什么身份取”，再用 `ExternalSecret` 描述“取哪些 key、写成哪个 Kubernetes Secret”。控制器按 `refreshInterval` 去 Vault、AWS Secrets Manager、GCP Secret Manager 等后端拉取，把结果写成一个普通 Secret。应用侧不用改：它仍然挂载或引用一个 Kubernetes Secret，只是这个 Secret 不再由人手工维护。轮换是否自动生效，取决于 ESO 有没有刷新、Secret 有没有变、应用有没有重新读取，后两步和 27.3 的边界一样。

[Secrets Store CSI Driver](https://secrets-store-csi-driver.sigs.k8s.io/)走另一条路。它是每个节点上的 DaemonSet，配合各厂商的 provider；Pod 用 `SecretProviderClass` 描述外部存储和要挂的 key，kubelet 在挂载卷时向 provider 取数据，把 secret 作为卷挂进容器，默认不落成 etcd 里的 Secret。需要让其他控制器或 env 引用时，可以用 `secretObjects` 把指定 key 同步成 Kubernetes Secret。它的优点是 secret 不必先复制进 etcd，权限可以细到 Pod 的 ServiceAccount；代价是多了一个节点级组件和 provider，排障要同时看 CSI 驱动、provider 和外部服务。

[SOPS](https://getsops.io/)和[Sealed Secrets](https://github.com/bitnami-labs/sealed-secrets)解决的是“加密文件能不能进 Git”。SOPS 用 KMS、age 或 PGP 加密 YAML 里的值，文件可以提交到 Git，部署时由 CI 或控制器解密；Sealed Secrets 用一个集群内的控制器和公钥，把明文 Secret 加密成 `SealedSecret`，只有对应私钥的控制器能解回 Secret。两者都把“加密后的配置”纳入版本控制，适合 GitOps；但密钥本身的权限、轮换和备份仍然是核心问题，加密文件进了 Git 不等于可以随便公开。

这三种方式的共同点是：secret 的源头在集群外或独立的管理系统里，Kubernetes 里的 Secret 只是投影或缓存；轮换、审计、最小权限由源头系统负责。选择时看三件事：应用能不能改造成从文件或 API 读、集群能不能承受一个控制器或 DaemonSet、以及团队有没有能力管理外部系统的身份和网络。ESO、Secrets Store CSI、SOPS 和 Sealed Secrets 都没有在本书的 kind 集群里安装，本节只讲对象关系和取舍，本书没有在本地验证这些控制器。不要把长期静态密钥写进 Git，也不要把“用了 ESO”当成“Secret 就安全了”；同步到 Kubernetes 的 Secret 仍然受 27.6 的 RBAC、etcd 和审计规则约束。

## 27.6 加密、RBAC 与审计

Secret 的默认状态经常被高估。Kubernetes 默认把 Secret 以未加密的形式存进 etcd；能访问 API server 的人可以读它，能访问 etcd 的人也可以读它，能创建 Pod 的人可以把同命名空间里的 Secret 挂进自己的 Pod。base64 只改变显示形式，不改变谁能读。要把 Secret 用在生产上，至少要做三件事：给 etcd 开静态加密、用 RBAC 把读取范围缩到最小、打开审计记录访问。

静态加密由 kube-apiserver 的 `--encryption-provider-config` 打开，配置文件是 `EncryptionConfiguration`。`resources` 列出要加密的资源，`providers` 列出加密提供者；列表里的第一个 provider 负责写，其余 provider 负责读旧数据。`identity` 是默认 provider，表示不加密；`aescbc`、`aesgcm`、`secretbox` 用本地密钥；`kms` 把密钥交给外部 KMS。只写 `identity` 等于没开加密；把 `identity` 放在第一位，新写入的数据仍然是明文。开启加密后，已有的 Secret 不会自动重写，需要把全部 Secret 读出来再写回去，官方文档给的做法是 `kubectl get secrets --all-namespaces -o json | kubectl replace -f -`。

KMS 比本地密钥多一层。KMS provider 用信封加密：Kubernetes 为数据生成数据加密密钥（DEK），用 KMS 里的密钥加密 DEK，etcd 里存的是被 KMS 保护过的 DEK 和密文；攻击者要同时拿到 etcd 和 KMS 才能解密。KMS v2 在 Kubernetes 1.25 进入 alpha、1.27 进入 beta、1.29 成为 stable；KMS v1 在 1.28 弃用，1.29 起默认关闭。KMS v2 每次加密生成新的 DEK，性能比 v1 好，配置里要写 `apiVersion: v2`、`name`、`endpoint` 和 `timeout`。本书的 kind 集群没有配 KMS，也没有配 `--encryption-provider-config`，下面的输出会看到 apiserver 的启动参数里没有这两项。

RBAC 的粒度是“资源 + 动词 + 命名空间”。`get`、`list`、`watch` 三个动词对 Secret 来说都意味着能读到内容：`list` 会返回一批 Secret 的完整对象，`watch` 会在变化时把内容推过来。只给 `get` 不给 `list` 也不等于安全，因为能创建 Pod 的人可以挂载 Secret；官方文档把“能创建 Pod”列为可以间接读取 Secret 的权限。生产上不要把 Secret 的读取权限给普通开发者，不要用 cluster-admin 图省事，按命名空间和 ServiceAccount 分开授权。

`automountServiceAccountToken: false` 是另一条边界。Pod 不需要调用 API server 时，不应该自动挂 ServiceAccount token；token 是身份凭据，泄露后可以被用来冒充这个 ServiceAccount。Kubernetes 1.24 起不再为每个 ServiceAccount 自动创建长期 token Secret，Pod 默认拿到的是 TokenRequest 签发的投射 token，有有效期、会自动轮换；投射卷的文档说 `expirationSeconds` 默认 1 小时；本集群 Pod 里看到的是 3607 秒，kubelet 在过期前续期。旧教程里的 `default-token-*` 已经不再是默认形态。

审计记录谁在什么时候读了哪个 Secret。kube-apiserver 默认不写审计日志，要传 `--audit-policy-file` 和 `--audit-log-path`（或 webhook 后端）。审计级别 `Metadata` 只记请求元数据，`Request` 记请求体，`RequestResponse` 连响应体一起记；对 Secret 来说，后两者可能把密码写进审计日志，审计日志本身要按敏感数据保护。排障时先确认审计策略有没有覆盖 `secrets` 资源，再看日志里是哪个用户、哪个 ServiceAccount、从哪个 IP 发起的请求。

## 27.7 排障：CreateContainerConfigError

`CreateContainerConfigError` 是 kubelet 在“准备容器配置”阶段失败，容器还没有真正启动。它和 `ImagePullBackOff`、`CrashLoopBackOff` 不是一类：镜像可能已经拉下来了，进程也还没跑，失败发生在把 Secret、ConfigMap、环境变量这些引用装配成容器配置的时候。看到这个状态，第一步不是删 Pod 重建，而是 `kubectl describe pod` 看 Events 的最后几条。

最常见的两条消息是 `secret "shorty-db" not found` 和 `couldn't find key db_password in Secret shorty/shorty-db`。前者是对象不存在：名字拼错、namespace 不对、Secret 还没创建，都会这样；Pod 只能引用同 namespace 的 Secret，跨 namespace 必须在本 namespace 里再建一个。后者是对象存在但 key 不对：Secret 里只有 `password`，Pod 却要 `db_password`，或者大小写、点号、下划线不一致。检查顺序是 namespace → 名字 → key，三步都能用 `kubectl get secret -n <ns> <name> -o jsonpath='{.data}'` 直接确认。

引用方式不同，报错位置也不同。用 `env.valueFrom.secretKeyRef` 或 `envFrom` 时，kubelet 在装配环境变量时失败，Pod 停在 `CreateContainerConfigError`；用 Secret 卷时，卷挂载失败通常表现为 `ContainerCreating` 加 `FailedMount` 事件，消息里同样有 `secret ... not found`。两种都要看 Events，不要只盯 Pod 的 STATUS。把引用标成 `optional: true` 可以让 Pod 先启动，但应用拿到的是空值或缺失的文件，问题只是被推迟到运行期，不会消失。

Secret 更新后应用没变，先确认它是怎么进容器的。看 Deployment 的 Pod 模板：`envFrom`、`env.valueFrom` 是环境变量路径，更新 Secret 不会改已运行进程的环境；`volumes` + `volumeMounts` 是文件路径，kubelet 最终会更新文件，但 `subPath` 挂载不会。再进容器看实际值：`kubectl exec <pod> -- cat /path` 读文件，`kubectl exec <pod> -- printenv NAME` 读环境变量；两个值不一样时，通常就是 env 和 volume 混用了，或者进程缓存了旧配置。环境变量路径必须重启 Pod（至少重建容器），volume 路径要确认应用有没有重新打开文件。

文件权限是另一个常见坑。ConfigMap 和 Secret 卷的默认权限是 `0644`，`defaultMode: 0444` 让所有用户只读；非 root 进程读 0444 一般没问题。但如果为了收紧权限改成 `0440` 或 `0400`，就要让容器进程的组或用户匹配文件属主：ConfigMap 卷默认属主是 root，`securityContext.fsGroup` 会把卷的组改成指定 GID，容器里的非 root 用户才能按组读。只设 `runAsUser`/`runAsGroup` 不够，文件属组不会自动跟着变。

## 上生产前

**配置和密码都不进镜像，Secret 优先用 volume 或外部 secret 管理。** 环境变量适合非敏感的短配置，不适合长期密码：`kubectl describe pod`、崩溃转储、子进程环境都会把它暴露出来。用 `SHORTY_DB_PASSWORD_FILE` 这类文件路径，把密码留在 tmpfs 卷里；再往上走，用 ESO 或 Secrets Store CSI 把源头放到 Vault、云 Secrets Manager 这类系统里，Kubernetes 里的 Secret 只做投影或缓存。

**开静态加密和 KMS，限制 RBAC，打开审计。** 默认的 Secret 只是 base64，etcd 里是明文；生产要配 `EncryptionConfiguration`，把 KMS v2 放在 provider 列表第一位，确认 KMS v1 已经不需要。RBAC 只给必要的 ServiceAccount `get` 权限，不给普通用户 `list`/`watch` Secret；不需要访问 API server 的 Pod 设 `automountServiceAccountToken: false`。审计策略要覆盖 `secrets`，审计日志本身按敏感数据保护。

**配置变更走 GitOps 和滚动更新，不要 `kubectl edit` 后指望进程自动重读。** ConfigMap/Secret 的清单进 Git，变更经过 review 和 diff；用 `checksum/config` 注解或版本化名字触发 Deployment 滚动。改完配置后确认新 Pod 真的读到了新值，再删旧版本；不要在正在服务的 Pod 上直接改文件，也不要把“文件最终会更新”当成“应用已经生效”。

**轮换密钥要演练，immutable 对象更新用新名字。** 轮换不只是改 Secret，还要改数据库、外部系统、客户端和缓存里的旧凭据；先建新版本、切流量、确认新凭据可用，再删旧版本。`immutable` 对象不能原地改，删了重建会让旧 Pod 继续挂旧对象、新 Pod 可能读到缓存里的旧值，留下一个难以解释的窗口。保留至少一个可回滚的旧版本，确认没有回滚需求后再清理。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `kubectl create configmap` | 从文件、目录或字面量建 ConfigMap | 文件 basename 是 key；`--from-file=key=path` 可改名 |
| `kubectl create secret generic` | 建 Opaque Secret | `--from-literal`/`--from-file`；`data` 存 base64 |
| `data` / `binaryData` | ConfigMap 的文本/二进制字段 | 单对象上限 1 MiB；key 不能重复 |
| `stringData` | Secret 的明文写入字段 | 写入时合并进 `data`，读回不出现；SSA 下不推荐 |
| `envFrom.configMapRef` / `secretRef` | 整包注入环境变量 | 只在容器启动时读一次 |
| `env.valueFrom.configMapKeyRef` / `secretKeyRef` | 只注入一个 key | 可改环境变量名；key 不存在会 `CreateContainerConfigError` |
| volume `items` / `defaultMode` | 选择 key、设置权限 | 默认 `0644`；`0444` 是十进制 292 |
| `subPath` | 只挂卷里的一个文件 | 不接收 ConfigMap/Secret 更新 |
| `immutable: true` | 禁止修改数据 | 1.19 引入，1.21 stable；只能删了重建 |
| `checksum/config` | 配置哈希写进 Pod 模板 | 不是内置字段；由生成清单的工具算 |
| `SHORTY_DB_PASSWORD_FILE` | 让应用从文件读密码 | 本书示例用 `/etc/shorty/db_password` |
| `EncryptionConfiguration` / KMS v2 | etcd 静态加密 | KMS v2 1.29 stable；KMS v1 1.28 弃用 |
| `kubectl auth can-i` | 检查某个主体能不能做某动作 | `--as=system:serviceaccount:<ns>:<sa>` |
| `kubectl describe pod` | 看 `CreateContainerConfigError` 的 Event | 先看 `secret ... not found` / `couldn't find key` |

- [配置 Pod 使用 ConfigMap](https://kubernetes.io/zh-cn/docs/tasks/configure-pod-container/configure-pod-configmap/)：`--from-file`/`--from-literal`、`envFrom`、`valueFrom`、卷挂载和 `subPath`。
- [Secret](https://kubernetes.io/zh-cn/docs/concepts/configuration/secret/)：类型、base64、`stringData`、tmpfs 卷、不可变对象和安全模型。
- [使用 kubectl 管理 Secret](https://kubernetes.io/zh-cn/docs/tasks/configmap-secret/managing-secret-using-kubectl/)：`kubectl create secret generic`、`--from-file`、查看和解码。
- [安全地分发凭据](https://kubernetes.io/zh-cn/docs/tasks/inject-data-application/distribute-credentials-secure/)：Secret 卷、`items`、`defaultMode`、env 注入和更新边界。
- [Kubernetes Secret 的良好实践](https://kubernetes.io/zh-cn/docs/concepts/security/secrets-good-practices/)：静态加密、最小权限、命名空间隔离、外部 secret 管理和 base64 不是加密。
- [静态加密 Secret 数据](https://kubernetes.io/zh-cn/docs/tasks/administer-cluster/encrypt-data/)：`EncryptionConfiguration`、provider 顺序、`identity` 默认值和重写全部 Secret。
- [使用 KMS 提供者进行数据加密](https://kubernetes.io/zh-cn/docs/tasks/administer-cluster/kms-provider/)：KMS v2 配置、信封加密、v1 弃用和 v2 的 stable 版本。
- [ServiceAccount](https://kubernetes.io/zh-cn/docs/concepts/security/service-accounts/)：投射 token、`automountServiceAccountToken: false` 和 1.24 起不再自动创建长期 token Secret。
- [审计](https://kubernetes.io/zh-cn/docs/tasks/debug/debug-cluster/audit/)：审计策略、级别、日志后端和 `--audit-policy-file`。
