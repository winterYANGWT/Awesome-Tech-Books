# 第 4 章 容器的生命周期与 PID 1：信号、重启策略、日志、exec

`docker stop shorty-api` 打下去，终端停了十秒才返回，`docker logs` 里只有启动日志，没有“收到退出信号”。这时最容易下两个相反的结论：应用没处理 SIGTERM，或者 Docker 根本没把信号发出去。两种都可能，但排查方向完全相反。Docker 发了信号却没人接，和 Docker 没发，在容器里看到的现象可以一模一样：进程最后都被 SIGKILL，退出码都是 137。

要分清这两件事，得同时看三个地方：容器里的 PID 1 是谁，进程有没有装信号处理器，以及 `docker stop` 的等待时间花在哪。这一章从 `docker stop` 这根线头往外拉，先看状态和退出码，再看 PID 1 与信号转发，然后把重启策略、日志和 `exec` 串起来。最后故意做一个收不到 SIGTERM 的容器，按真实排障顺序定位。

> **起点**：第 3 章结束时 lab 里没有运行中的容器，本地有 `shorty:0.1` 和 `busybox:1.37`。本章用带 shell 的 `shorty:dev` 做调试，`bash code/ch04/setup.sh` 会从同一个 Dockerfile 的 build 阶段构建它，再派生 exec 形式、shell 形式两个小镜像。本章不建 kind 集群。

## 4.1 状态与退出码

容器的生命周期由 Docker daemon 记录成一组状态。刚 `docker create` 出来是 `created`；PID 1 跑起来是 `running`；`docker pause` 把进程冻结成 `paused`；配置了重启策略、正在两次启动之间等待时是 `restarting`；进程结束、容器记录还在是 `exited`；清理没有完成时还可能出现 `dead`。`dead` 不是正常停止会经过的一站，遇到它先看 daemon 日志，不要把它当成“应用退出了”。

`docker ps -a` 的 `STATUS` 列把这些状态翻译成人看的文字：`Created`、`Up 3 seconds`、`Up 2 seconds (Paused)`、`Exited (0) <时间> ago`。默认表里没有单独的 `EXIT` 列，退出码就在 `Exited (N)` 的括号里。要拿机器可读的值，别解析这一列，直接读 `docker inspect` 的 `.State`。下面的例子依次走 `create`、`start`、`pause`、`stop`、`start`、`rm`，每一步都看一次 `docker ps -a`。

> **旧资料提示**：旧教程常说“容器只有六种状态”，并把状态机画成一条闭环。现代 Docker 还会出现 `dead`，它不是正常生命周期的一步，而是删除或清理没有完成时留下的状态；看到它先看 daemon 日志，不要拿六状态表硬套。

`docker create` 不只是“占个名字”。它已经把容器的配置、可写层和网络设置准备好了，只是还没有启动 PID 1；所以 `created` 和 `exited` 的区别是“从来没跑过”和“跑过又停了”。`docker ps` 默认只列 `running`，排障时一定要带 `-a`，否则一个已经退出的容器看起来像不存在。`docker wait` 则适合脚本：它阻塞到容器退出，然后打印退出码，4.5 用它等一个注定崩溃的容器。

`docker create` 之后是 `Created`，`docker start` 之后是 `Up`，`docker pause` 之后括号里多出 `(Paused)`。`docker stop` 返回时容器已经是 `Exited (0)`：SIGTERM 发给了 PID 1，shorty 处理了它，正常退出。再 `docker start` 同一个容器，它又回到 `Up`，`StartedAt` 会更新；这不是新建容器，内存存储里的链接也不会保留。

`docker inspect .State` 那段 JSON 是判断退出原因的主要依据。`ExitCode` 是 0，`OOMKilled` 是 false，`Error` 是空字符串，`StartedAt` 和 `FinishedAt` 给出这次运行的时间窗口。`Error` 记录的是 daemon 启动或运行容器时的错误，不是应用写到 stderr 的内容；应用输出要去 `docker logs` 看（4.4）。`OOMKilled` 在容器因内存不足被杀时是 true，不能只看 137 就认定 OOM。

退出码的约定是 128 加信号编号。143 是 128+15，表示进程被 SIGTERM 结束；137 是 128+9，表示被 SIGKILL 结束。例子里的 143 是 busybox 的 shell 自己 `trap "exit 143" TERM` 得到的：它装了处理器，收到 TERM 后主动用 143 退出。137 则是 `docker kill -s KILL` 直接杀，进程没有机会清理；两边的 `OOMKilled` 都是 false，说明这一次的 137 与内存无关。

还有一个常见的 1：应用自己报错退出，或者命令找不到、参数不对。4.5 会让 shorty 用故障开关以 1 退出，日志里能看到触发原因。看到非零退出码，先按 128+N 拆信号，再看 `OOMKilled`，最后看日志和 `.State.Error`，不要一上来就改重启策略。

`StartedAt` 和 `FinishedAt` 是 UTC 时间，`FinishedAt` 在一次都没启动过的容器上可能是零值；`Error` 为空只说明 daemon 没有记录启动错误，不代表应用没有报错。137 尤其要拆开看：可能是 `docker stop` 超时后的 SIGKILL，可能是 cgroup 内存限制触发的 OOM，也可能是有人 `docker kill -s KILL`。三种情况的退出码一样，区别在 `OOMKilled`、时间点和 `docker events` 的 `kill`/`die` 记录里。

状态变化也可以从事件流看。`docker events --filter container=<名字>` 会按时间顺序打出 `create`、`start`、`die`、`stop`、`destroy` 这些动作；`die` 事件带退出码，`stop` 事件表示收到了停止请求。它适合回答“这个容器是被人停的，还是自己退的”，比只看 `docker ps -a` 的最后一帧更有信息。4.3 会用它看重启策略留下的 `die`/`start` 对。

## 4.2 PID 1 与信号转发

容器里的 PID 1 就是镜像的 `ENTRYPOINT`/`CMD` 启动的那个主进程。PID namespace 里的 1 号进程和宿主机的 init 有一个重要区别：内核不会对 PID 1 执行信号的默认动作。一个没装 SIGTERM 处理器的普通进程收到 TERM 会死；同样的进程作为 PID 1，收到 TERM 会被忽略。所以主进程必须自己 `signal.Notify` 或 `trap`，否则 `docker stop` 只能等超时再发 SIGKILL。

shell 形式会把这件事弄复杂。`CMD /shorty serve` 不是直接执行 `/shorty`，Docker 会把它包成 `/bin/sh -c "/shorty serve"`。PID 1 是 `/bin/sh`，shorty 是它的子进程；`docker stop` 的 SIGTERM 只发给 PID 1 的 sh。sh 在等子进程，没有把信号转发给 shorty，自己又因为 PID 1 的身份忽略默认动作，于是这 3 秒里谁都没退出，直到 Docker 发 SIGKILL。

先看两个镜像的元数据。`shorty:ch04` 是 `Entrypoint=["/shorty"] Cmd=["serve"]`，PID 1 直接是 shorty；`shorty:ch04-shell` 是 `Entrypoint=null Cmd=["/bin/sh","-c","/shorty serve"]`，多了一层 shell。`/proc/1/cmdline` 把这一点坐实：shell 形式看到的是 `/bin/sh -c /shorty serve`，exec 形式看到的是 `/shorty serve`。

shell 形式 `docker stop -t 3` 之后，退出码是 137，`OOMKilled` 是 false，日志里连“收到退出信号”都没有。这说明 shorty 根本没收到 TERM：Docker 发了，但收件人是 sh，sh 没转交。3 秒是 `-t 3` 给的等待时间，不是 Docker 的默认值；不传 `-t` 时默认等 10 秒，4.8 会实测这个数字。exec 形式的对照组用 `-t 10`，shorty 在第 5 秒的 `SHUTDOWN_DELAY` 之后完成关闭，退出码 0，日志依次出现收到信号、开始关闭、HTTP 已关闭、进程退出。

这里有一个容易忽略的细节：Docker 只把停止信号发给 PID 1，不会自动发给容器里的所有进程。PID 1 的责任是把信号传给该传的子进程，或者在退出时把子进程一起收掉。shell 包装既不做转发，又因为 PID 1 的身份不执行默认动作，所以整棵进程树会一直挂到 SIGKILL。`docker kill --signal` 也是发给 PID 1，不会绕过这个问题。

`docker stop` 的默认信号是 SIGTERM，等 10 秒再 SIGKILL；`-t` 改等待秒数，`-s` 改这一次发送的信号。镜像可以用 `STOPSIGNAL` 改默认停止信号，Kubernetes 里还可以用容器 lifecycle 的 `stopSignal` 覆盖镜像的 `STOPSIGNAL`。下面的第二个例子用一个 `STOPSIGNAL SIGINT` 的镜像验证：不传 `-s`，`docker stop` 发的也是 SIGINT，shorty 的日志里 `"signal":"interrupt"`。

先看 `--init`。`/proc/1/cmdline` 是 `/sbin/docker-init -- /shorty serve`，`ps` 里 PID 1 是 `docker-init`，shorty 是 PID 7 的子进程；`docker stop` 仍然能让 shorty 收到 TERM，退出码 0。docker-init 负责把信号转给子进程，并在子进程退出后回收孤儿进程，这正是“应用不擅长当 PID 1”时需要的补丁。它不是让 shell 包装变好的工具，shell 包装的问题仍然是应用不在 PID 1。

再看 `STOPSIGNAL`。`shorty:ch04` 的 `StopSignal` 是空的，`shorty:ch04-int` 是 `SIGINT`；不传 `-s` 直接 `docker stop`，shorty 日志里的 `"signal":"interrupt"`，退出码 0。这说明停止信号可以从镜像层面改，不必每次在命令行写 `-s`。改之前要确认应用真的处理这个信号；把 `STOPSIGNAL` 改成应用不认识的信号，只会把 10 秒等待变成 137。

exec 形式也不是万能的。它只保证信号能到 PID 1，应用还得自己装处理器、自己决定退出前做什么。一个用 exec 形式启动但完全没处理 SIGTERM 的程序，仍然会等到超时被 SIGKILL；区别是它有机会在日志里留下“收到了但我不理”，而 shell 包装连这个机会都没有。

如果确实需要一层 init 来回收僵尸进程，用 `docker run --init`，不要自己写一个 `sh -c` 包装。`--init` 会把 `/sbin/docker-init` 放到 PID 1，shorty 变成它的子进程；docker-init 负责转发信号和回收孤儿进程。它解决的是“主进程不擅长当 init”的问题，不是“shell 不转发信号”的许可证：shell 包装仍然会把应用推离 PID 1，能改成 exec 形式就改。

为什么需要回收？容器里的 PID 1 除了收信号，还要 `wait` 掉被 reparent 过来的孤儿进程。一个只启动子进程、自己不 wait 的主进程，会让退出的子进程变成僵尸，占着 PID 表项；进程表满了，新进程就起不来。很多应用主进程并不实现这套逻辑，所以官方建议用 `--init` 注入一个专门做这件事的小 init。判断要不要加，看主进程是不是会 fork 出短期子进程、退出后又不 wait；一个单线程 HTTP 服务通常不需要，一个会调外部命令的脚本或 supervisor 就需要。

## 4.3 重启策略与退避

`--restart` 有四种取值。`no` 是默认值，退出就退出；`on-failure[:max-retries]` 只在退出码非零时重启，可以限定重试次数；`always` 不管退出码都重启，手动 `docker stop` 之后不会立刻拉起来，但 daemon 重启后会；`unless-stopped` 和 `always` 类似，区别是手动停过的容器在 daemon 重启后也不再启动。手动停止会暂时压住重启策略，直到 daemon 重启或你再次 `docker start`，这是为了避免“停不下来”的循环。

策略可以在 `docker run` 时给，也可以用 `docker update --restart unless-stopped <容器>` 改一个已经存在的容器。`on-failure:3` 的 3 是“daemon 再尝试几次”，不是“总共启动几次”；例子里的第一次启动不算在 3 次里，所以日志有四行。次数用完后容器停在 `exited`，`RestartCount` 保留在 `.State` 里，方便你判断它已经试过几轮。重启策略只作用于容器，不作用于 Swarm service；Swarm 有自己的 service restart 配置。

选策略时先问“这个容器该不该一直活着”。长期服务用 `always` 或 `unless-stopped`，让 daemon 重启后也能回来；一次性任务用 `no` 或 `on-failure:1`，失败了让人看见，而不是无限重试。给一个配置写错、每次启动都崩的容器配 `always`，只会把日志刷满、把 CPU 占住，问题一点没解决。`on-failure` 的 `max-retries` 是给“可能恢复的临时故障”留的窗口，不是给“代码 bug”兜底的。

例子用 `on-failure:3` 跑一个立即 `exit 1` 的 busybox。最终 `RestartCount=3`、`ExitCode=1`，`docker logs` 里有四行 `start`：第一次启动加三次重启。`docker inspect .HostConfig.RestartPolicy` 返回 `{"Name":"on-failure","MaximumRetryCount":3}`，这是策略真正落盘的地方；`docker ps` 的 `STATUS` 只告诉你现在在跑还是在退。

`docker events` 里，策略重启留下的是一对 `die` 和 `start`，不是 `restart`。例子把每次 `start` 的 `TimeNano` 取出来相减，`start` 到下一次 `start` 的间隔约为 200 ms、300 ms、500 ms，逐次变长；第一次 `die` 到下一次 `start` 的等待在 100 ms 量级。Docker 官方文档没有写这条曲线的具体数值和封顶值，正文只能说到“从 100 ms 量级开始指数增长，封顶值需核实”；换 Engine 版本时以 `docker events` 的时间戳为准。大纲说 events 里会有 `restart` 事件；在 lab 的 Docker 29.9.2 上，策略重启和手动 `docker restart` 留下的主要是 `die`/`start`，手动路径的事件窗口里也只能稳定看到重新 `start`，没有独立的 `restart` 动作。判断重启次数看 `.RestartCount` 和 `start` 事件，不要依赖 `restart` 这个动作名。

这里有一条官方文档和实测对不上的地方需要说明。文档说重启策略要等容器成功运行至少 10 秒才生效，理由是防止根本起不来的容器进入重启循环；但例子里的容器启动后立刻退出，仍然重启了三次。至少在这条路径上，`on-failure:3` 的计数照常工作。实践上不要依赖“10 秒保护”，给短生命周期容器设 `max-retries` 或改用 Job/CronJob 这类一次性工作负载，才是可控的做法。

重启策略不区分失败原因。业务代码 `panic`、配置错误退出、被 OOM killer 杀，退出码都是非零，`on-failure` 都会重启；它不会因为 `OOMKilled=true` 就换一种处理。要区分原因，得看 `.State.OOMKilled`、日志和退出码。重启只能把“进程挂了”拉回来，不能把“进程活着但处理不了请求”拉回来，后者要靠探针或健康检查。

`live-restore` 是另一回事。默认情况下 dockerd 停止时会把运行中的容器一起停掉；在 `daemon.json` 里设 `"live-restore": true`，daemon 不在时容器继续跑，升级 daemon 后还能接回来。它只支持补丁版本升级，不保证跨大版本；只作用于独立容器，不作用于 Swarm service；也不替代重启策略，更不是编排。容器里的进程崩了，live-restore 不会替你拉起；节点失联后的重新调度，它也不管。

Kubernetes 侧的重启策略是 Pod 的 `restartPolicy`：`Always`（默认）、`OnFailure`、`Never`。kubelet 的重启退避是另一套数值，官方文档写的是 10 秒、20 秒、40 秒，封顶 300 秒，容器稳定运行 10 分钟后重置。不要把 Docker 的退避和 Kubernetes 的 `CrashLoopBackOff` 混成一个东西：名字像，实现和数值都不同。

## 4.4 日志：json-file 与读取方式

Docker 默认把容器的 stdout/stderr 收走，写成 `json-file`。每一行是一个 JSON 对象，字段是 `log`、`stream`、`time`：`log` 是应用写出的内容（带换行），`stream` 是 `stdout` 或 `stderr`，`time` 是 daemon 收到这一行的时间。`docker logs` 读的就是这份记录，所以容器退出后、只要还没 `docker rm`，日志仍然在。


例子让 shorty 在 2 秒后以 1 退出。`docker ps -a` 显示 `Exited (1)`，`docker logs` 仍能读到退出前的 JSON 行，最后一行是“故障开关触发退出”。`docker inspect` 的 `HostConfig.LogConfig.Type` 是 `json-file`，`.LogPath` 指向 `/var/lib/docker/containers/<id>/<id>-json.log`；把最后一行交给 `jq`，正好看到 `log`、`stream`、`time` 三个字段，`stream` 是 `stdout`。

读日志的常用参数：`--tail N` 只看最后 N 行，`-t` 给每行加时间戳，`--since` 限定时间窗口，`-f` 持续跟随。`--since` 和 `--tail` 可以一起用；`-f` 在容器退出后不会自己结束，脚本里要加超时或改用 `docker logs` 的一次性读取。注意 `docker logs` 显示的是应用写到 stdout/stderr 的内容，不是容器内某个日志文件的内容；应用如果把日志写进 `/var/log/app.log`，`docker logs` 就是空的。

`json-file` 默认不轮转：`max-size` 默认 -1（不限），`max-file` 默认 1，而且 `max-file` 只有在设了 `max-size` 时才生效。生产上必须配 `--log-opt max-size=10m --log-opt max-file=3` 之类，或者在 `daemon.json` 里设默认值。例子里的 busybox 只写 300 行，用 `max-size=1k --max-file=2` 就能看到目录里只剩当前日志和轮转文件，总数不超过 `max-file`；这也说明轮转是 daemon 按大小做的，不是应用自己删文件。

`local` 驱动用更紧凑的格式并默认压缩，默认保留 100 MB（20 MB × 5 个文件），适合不想自己算轮转的场景。远程驱动（`splunk`、`fluentd`、`awslogs` 等）把日志发走；Docker 会用 `local` 驱动做一份本地缓存，这就是 dual logging，`docker logs` 默认还能读最近一段。缓存可以用 `cache-disabled` 关掉，关掉之后 `docker logs` 会报 `configured logging driver does not support reading`。远程驱动下 `docker logs` “没有输出”先查这个开关，不要先怀疑应用。缓存的默认上限是 5 个 20 MB 文件（压缩前），比默认 json-file 的“不限”小得多，排查很久以前的日志时要知道这一点。

日志驱动和轮转参数是容器创建时定下的。改 `daemon.json` 只影响之后新建的容器，已有容器会保留原来的配置；要改一个已存在容器的日志驱动，只能重建它。查当前 daemon 的默认驱动用 `docker info --format '{{.LoggingDriver}}'`，这一点在升级 Docker Engine 版本时尤其重要，查单个容器用 `docker inspect -f '{{.HostConfig.LogConfig.Type}}'`。时间戳 `time` 是 daemon 收到这一行的时间，不是应用自己打的时间；应用日志里如果另有 `ts` 字段，两者可能差几毫秒到几秒，排时序时以应用字段为准。

日志从应用到驱动是一条管道：应用写 stdout/stderr，容器运行时把这两条流接到 daemon，daemon 再交给日志驱动。默认是阻塞投递：驱动写得慢，应用的 `write` 就会被挡住，严重时整个进程卡住。configure 文档给了 `mode=non-blocking` 和 `max-buffer-size`，让 daemon 先用一个每容器缓冲区接住；缓冲区满了会丢新消息，而不是阻塞应用。高吞吐服务要在这两者之间选：宁可丢日志也不能拖垮业务，还是宁可慢也不能丢。

最后一条纪律：日志只写 stdout/stderr。容器内文件会跟着容器删除而消失，也不会被 `docker logs`、`kubectl logs` 或日志采集器自动收走。`json-file` 的文件是 daemon 的私有存储，官方文档明确说不要用外部工具去改它；要读就用 `docker logs`，要长期保存就配远程驱动或采集器。

`docker logs` 也不是日志平台。它只在单机上读本地驱动，没有检索、聚合、保留策略，容器删了日志就没了；多副本、多节点时，你要登录每台机器分别看。生产上要么在 daemon 层配远程驱动，要么在节点上跑采集器读日志文件，要么应用直接写结构化日志到采集端。`docker logs` 的定位是排障时快速看最近几行，不是长期存储。

## 4.5 exec、attach 与调试

`docker exec` 在已经在运行的容器里新起一个进程，这个进程进入容器的 namespace，但不会替代 PID 1。`docker exec -it shorty-api sh` 给你一个交互 shell；`docker exec shorty-api cat /proc/1/status` 则直接看 PID 1 的状态。`-i` 保留 stdin，`-t` 分配 TTY；脚本里通常只用 `-i` 或都不用，交互排查才用 `-it`。

`docker attach` 不一样。它接的是 PID 1 的 stdin/stdout/stderr，不是新起进程；在 TTY 里按 Ctrl-C，SIGINT 会被转发给 PID 1（Docker 27 修过 CLI 在 SIGINT 时提前退出、不转发的问题）。如果 attach 的是 shorty-api，这个 Ctrl-C 就是发给 shorty 的 SIGINT，会触发优雅退出，把线上容器停掉。看日志用 `docker logs`，不要用 attach；确实要交互时，用 `--detach-keys`（默认 Ctrl-P Ctrl-Q）先脱身，别按 Ctrl-C。这个例子没有真的 attach：check_examples 的会话没有 TTY，非交互地 attach 会挂住或报 TTY 相关的错误；要看 PID 1 的 stdio，`/proc/1` 和 namespace 已经够说明问题。

> **旧资料提示**：旧教程里用 `docker attach` 看日志，理由是“attach 能看到实时输出”。attach 接的是 PID 1 的 stdio，输入也会进 PID 1，Ctrl-C 可能把容器带走；只读地跟随日志应该用 `docker logs -f`。

`nsenter` 只在调试宿主机的 namespace 时需要，比如容器运行时自己也出了问题，你要进宿主机某个进程的 netns 看网卡。普通容器排障用 `docker exec` 就够了：它已经把你放进容器的 namespace，不需要再 `nsenter -t <pid> -n`。把 nsenter 当默认工具，容易进错 namespace，也容易在只读或没有权限的节点上失败。

exec 和 attach 的差别可以记成一句话：exec 是“再开一个进程”，attach 是“接上已有的 PID 1”。exec 的进程退出不会影响主进程，主进程照常监听端口，这是两者最实际的区别；attach 的终端断开、Ctrl-C、Ctrl-D 都可能变成主进程的信号。看日志、跑一次 `ps`、拷文件，用 exec 或 cp；只有需要直接和主进程的 stdin 交互时，才考虑 attach，而且要先想好怎么 detach。

生产容器经常没有 shell。`shorty:0.1` 是 distroless，`docker exec -it shorty:0.1 sh` 会报找不到 `sh`；`shorty:dev` 有 shell，只是因为它是构建阶段。Kubernetes 里的对应手段是 `kubectl debug` 加的临时容器（ephemeral container），它在 1.25 稳定，可以 `--target` 到目标容器的进程 namespace，也可以用 `--copy-to` 复制一个 Pod 改命令调试。临时容器不会被写进 Pod 的 `containers`，也不会参与重启策略，适合一次性排查。Docker 侧没有完全等价的东西，只能换一个带工具的镜像、用 `docker cp` 把静态二进制拷进去，或者接受“这个容器不可 exec”。

`docker logs -f` 是 attach 的只读替代品：它跟随 stdout/stderr，不接 stdin，按 Ctrl-C 只停掉这个跟随进程，不会把信号送进容器。要看历史日志用 `docker logs`，要实时看用 `-f`，要进容器执行命令用 `exec`；这三件事不要再用 attach 一个命令全包。

## 4.6 优雅退出与 readiness

shorty 收到 SIGTERM 后做三步：先把 `/readyz` 置为 503，让新流量别再进来；再等 `SHORTY_SHUTDOWN_DELAY`（默认 5 秒），给负载均衡器和调用方时间把请求摘走；最后调用 `http.Server.Shutdown`，它会在 10 秒超时内等待正在处理的请求结束。三步都写 JSON 日志。这个顺序是应用自己实现的，Docker 不知道什么是 readiness。

例子把 `SHUTDOWN_DELAY` 调成 2 秒，先打开 3 秒延迟，发一个慢请求，再把新请求的延迟关掉，然后 `docker stop -t 15`。stop 之后轮询 `/readyz` 拿到 503 和 `not ready: shutting down`；慢请求最终仍然是 200，耗时约 3 秒；`docker stop` 等到进程退出才返回，退出码 0。日志按顺序出现“收到退出信号”“开始关闭 HTTP 服务”“HTTP 服务已关闭”“shorty 退出”，中间那 2 秒就是等待窗口。

这里有两个时间要分清。`SHUTDOWN_DELAY` 是应用自己等的 2 秒，`docker stop -t 15` 是 Docker 给整个退出过程的上限；`http.Server.Shutdown` 的 10 秒又是应用内部的第二道上限。`-t` 必须大于“等待时间 + 最慢请求的剩余时间”，否则 Docker 会在应用关完之前发 SIGKILL，日志停在半路，退出码变成 137。例子用 15 秒覆盖 2 秒等待加 3 秒请求，留了余量。

`docker stop` 和 `docker kill` 的语义不同：`stop` 先发 TERM 再等，`kill` 直接发 KILL（默认），不给应用清理机会。`docker stop` 返回得晚不一定是 Docker 卡住，它在等 PID 1 退出；返回得早也不一定是优雅，可能是应用立刻退出了。要看它到底等了多久，用 `time docker stop` 或前后两个时间戳，别凭感觉。

Docker 没有 readiness 这个概念。`HEALTHCHECK` 只能把容器标成 `healthy`/`unhealthy`，它不会替你从端口映射或外部负载均衡里摘流量；容器仍然在跑，`docker stop` 也仍然按信号流程走。要把“不接新请求”做出来，只能像 shorty 这样在应用里实现，或者在外面加代理。Kubernetes 才有 readinessProbe 这套机制：探针失败会把 Pod 从 Service 的 EndpointSlice 里摘掉。

`HEALTHCHECK` 和 readiness 的另一个区别是节奏。healthcheck 有 `interval`、`timeout`、`retries`、`start-period`，它是 daemon 周期性地执行一条命令；readinessProbe 是 kubelet 周期性发请求或执行命令，失败只影响“是否接流量”，不影响容器是否重启。livenessProbe 才会重启容器。把三者混成一个 `/healthz`，经常会出现“依赖数据库慢一点，容器就被 liveness 杀掉”的连锁反应。

Kubernetes 的终止流程和这里对应：kubelet 先跑 `preStop`（如果配了），再给容器 PID 1 发 TERM；`terminationGracePeriodSeconds` 从 preStop 开始前就计时，默认 30 秒，超时就 KILL。所以 `terminationGracePeriodSeconds` 要覆盖 preStop 加应用退出，和 `docker stop -t` 是同一个道理。镜像里的 `STOPSIGNAL` 会被遵循；1.33 起还有 alpha 的 `ContainerStopSignals`，可以在容器 lifecycle 里覆盖停止信号，默认没开。

preStop 和应用自己的等待不要重复。shorty 已经在应用里等 5 秒，如果 preStop 再 `sleep 10`，总时间就变成 15 秒，`terminationGracePeriodSeconds` 必须把两段都算进去。preStop 适合做应用不便于自己做的事，比如从注册中心摘地址、等一个外部连接排空；应用已经实现的 readiness 翻转和 `Shutdown`，不需要再用 preStop 包一遍。顺序也要注意：preStop 在 TERM 之前，应用还没收到 TERM，`/readyz` 可能仍然是 200；要让 preStop 期间就停止接流量，得在 preStop 里主动打应用的摘流接口，或者依赖 Service 的 endpoint 摘除。

`docker exec shorty-broken cat /proc/1/cmdline` 看到 `/bin/sh -c /shorty serve`，PID 1 是 sh；`docker inspect` 的 `.Config.Cmd` 也是 `["/bin/sh","-c","/shorty serve"]`。计量一下 `docker stop` 的耗时，正好 10 秒，说明 Docker 发的是 SIGTERM，等满默认时间才 SIGKILL。日志里没有“收到退出信号”，因为 shorty 从来没收到。修复不是加 `--init`，也不是把 `-t` 调大，而是把入口改成 exec 形式：`ENTRYPOINT ["/shorty"]`，或者至少在 shell 包装里写 `exec /shorty serve`，让 shorty 自己成为 PID 1。例子后半段换成 exec 形式，`/proc/1/cmdline` 变成 `/shorty serve`，`docker stop` 正常返回 0。

第二个故障是 `docker logs` 为空。先看日志驱动和 `.LogPath`，不要先怀疑应用没打日志。例子用 `--log-driver none` 起一个容器，`docker logs` 直接报 `configured logging driver does not support reading`，`docker inspect` 显示 `driver=none`、`path=` 为空。换成远程驱动且关掉 dual logging，也会是类似的“读不到”。另一种更常见：驱动是 `json-file`、`.LogPath` 有文件，但应用把日志写进了容器内的文件，stdout 是空的；这时 `docker logs` 当然没有内容，要改应用写 stdout/stderr。

`.LogPath` 为空不一定是驱动坏了。`none` 驱动本来就不落盘；远程驱动如果没开缓存，也不会有本地路径；容器刚创建还没启动时，路径可能还没建好。判断顺序是 `docker info --format '{{.LoggingDriver}}'` 看 daemon 默认，`docker inspect -f '{{json .HostConfig.LogConfig}}'` 看这个容器实际用的驱动和参数，再看 `.LogPath`。三者对上了，才轮到怀疑应用。

排障顺序可以固定成四步：先 `docker inspect -f '{{.State.Status}} {{.State.ExitCode}} {{.State.OOMKilled}}'` 看结果；再 `docker logs` 看应用最后说了什么；然后 `docker exec cat /proc/1/cmdline` 或 `docker inspect .Config` 看 PID 1 和入口形式；最后才看 `.HostConfig.LogConfig` 和 `.LogPath`。前两步区分“应用错误”和“信号问题”，后两步区分“没发信号”和“发了没人接”。不要用 `docker attach` 代替 `docker logs`，attach 会把你的 Ctrl-C 送进 PID 1。

还有一种 137 是应用自己忽略了 SIGTERM。shorty 有 `SHORTY_FAULT_IGNORE_SIGTERM=true` 的故障开关，打开后它会在日志里写“忽略 SIGTERM”，然后继续运行，直到 `docker stop` 超时被 SIGKILL。它和 shell 包装的现象都是 137，区别在日志：忽略 SIGTERM 的应用会留下“收到信号但忽略”的记录，shell 包装则连“收到”都没有。定位时先看日志有没有这一行，再看 PID 1 是不是应用。

排障时不要一上来就 `docker restart` 或加 `--restart=always`。容器已经退出，重启只会把现场洗掉，下一次还是同样的退出码。先把 `.State`、`docker logs` 和 `/proc/1/cmdline` 三份证据留下来，再决定是改入口、改信号处理器，还是改日志配置。重启是恢复手段，不是诊断手段。

## 上生产前

**主进程必须是 PID 1，并自己处理 SIGTERM。** 用 exec 形式的 `ENTRYPOINT`/`CMD`，不要用 shell 形式包一层；如果确实需要 shell 做环境准备，最后用 `exec` 把主进程替换上去。需要回收僵尸进程时用 `--init`，不要把“写一个更复杂的 shell 包装”当成 init。上线前在容器里 `cat /proc/1/cmdline` 确认一次，比看 Dockerfile 更可靠。

**超时要大于最慢请求的退出时间。** `docker stop -t` 和 Kubernetes 的 `terminationGracePeriodSeconds` 覆盖的是“preStop/等待 + 正在处理的请求 + 关闭连接”，不是只看应用自己的 sleep。先量最慢请求的 P99，再留余量；常见的 20–30 秒是个起点，不是固定答案。超时太小，日志会停在半路，退出码 137，看起来像应用崩了。

**日志只写 stdout/stderr，并给 json-file 设上限。** 配 `max-size`/`max-file`，或者把默认驱动换成会轮转的 `local`；不要让 json-file 无限增长把磁盘写满。远程驱动要确认 dual logging 是否开着，否则 `docker logs` 在排障时可能什么都读不到。容器内日志文件既不会被 `docker logs` 收走，也会随容器删除消失。

**重启策略只解决“进程挂了”。** `always` 和 `unless-stopped` 能把崩溃的进程拉回来，但进程活着、端口在听、请求全 500 的情况，重启策略看不见。可用性要靠 readiness/liveness 探针、健康检查和外部负载均衡；Kubernetes 里还要把 `restartPolicy` 和探针分开看，别把 `CrashLoopBackOff` 当成应用健康的证明。

**不要把 `live-restore` 当编排。** 它让 dockerd 重启时容器不死，但只对补丁升级有保证，不跨大版本，不管 Swarm service，也不会在进程崩溃后拉起容器。单机 Docker 的重启策略和 live-restore 都只是本机手段；跨节点的重新调度、副本维持和滚动更新，要交给编排层。

|---|---|---|
