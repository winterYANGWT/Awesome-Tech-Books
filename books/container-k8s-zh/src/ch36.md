# 第 36 章 集群运维：升级、etcd 备份恢复、节点维护、多集群

周六凌晨的维护窗口，值班同事准备给 shorty 的节点打内核补丁。他先执行 `kubectl drain`，命令停在 `Cannot evict pod as it would violate the pod's disruption budget`；加上 `--ignore-daemonsets` 之后，又卡在 emptyDir 上。同一个窗口里，另一位同事在升级 Kubernetes：他先换了 worker 上的 kubelet，控制面还是旧版本，结果新 kubelet 注册不回来。两件事都不大，但都说明集群运维不是“敲一条命令”，而是一组有顺序、有回滚、有检查点的动作。

到第 35 章为止，`s4-prod` 已经是一个能接流量、能被观测的集群：api 两副本，postgres 用 StatefulSet 和 local-path 卷，Gateway 和 NetworkPolicy 都在，Prometheus 能看指标。它仍然只是一个单集群：一个控制面节点、两个 worker，etcd 作为静态 Pod 跑在控制面节点里。控制面节点一停，API 就没了；local-path 卷只属于某一个节点；证书和 etcd 数据目录都在节点本地。生产运维要处理的正是这些“单点”和“本地状态”。

这一章沿着一次维护窗口的顺序走：先看 Kubernetes 的版本偏差和升级顺序，再做一次 etcd 快照与恢复，然后 cordon/drain/uncordon 一个 worker，接着检查证书、KMS 和密钥轮换，最后看节点关机、swap、kubelet 配置，以及“单集群 HA”和“多集群”的区别。每个动作都在 `s4-prod` 上做，做完把集群恢复健康；多集群只做 kubeconfig context 的概念演示，不在 lab 里起第二个集群。

> **起点**：`s4-prod` 已就绪，集群是 1 控制面 + 2 worker；etcd 在控制面节点的静态 Pod 里，postgres 的数据在 local-path 卷上。第 35 章的 Prometheus、kube-state-metrics 和 OTel Collector 可以继续用，本章不依赖它们。一步到位：`bash code/ch36/setup.sh`。脚本会重建 3 节点集群、装好 metrics-server 和 Gateway，并预拉 `alpine:3.22` 供维护演示使用。

## 36.1 版本、skew 与升级顺序

Kubernetes 的升级不是把三个节点的 kubelet 一起换掉。控制面组件、kubelet、kubectl 各有自己的版本，彼此之间允许一定偏差（skew），超出范围就可能出现“新 kubelet 注册不上”“kubectl 解析不了新字段”这类问题。先把当前版本和升级计划摆出来，比直接背命令有用。


前三组命令确认当前状态：控制面节点里的 kubeadm 是 `v1.37.0`，kubectl 客户端和服务端都是 `v1.37.0`，三个节点的 kubelet 也都是 `v1.37.0`。`kubectl version` 里的 `Kustomize Version` 是 kubectl 内置的 Kustomize，不是集群组件，升级时不用管它。

`kubeadm upgrade plan v1.37.1` 的输出分三段。第一段是版本检查：集群 `1.37.0`，kubeadm `v1.37.0`，目标 `v1.37.1`。第二段列“控制面升级后还要手动升级的组件”，这里只有三个 kubelet：`shorty-control-plane`、`shorty-worker`、`shorty-worker2`，当前都是 `v1.37.0`，目标是 `v1.37.1`。第三段列 `kubeadm upgrade apply` 会动的组件：kube-apiserver、kube-controller-manager、kube-scheduler 从 `v1.37.0` 到 `v1.37.1`，kube-proxy 从 `1.37.0` 到 `v1.37.1`；CoreDNS 已经是 `v1.14.6`，etcd 已经是 `3.7.0-0`，这次不需要换。最下面还有一张组件配置版本表：`kubeproxy.config.k8s.io` 和 `kubelet.config.k8s.io` 的 `CURRENT` 与 `PREFERRED` 都是 `v1alpha1`/`v1beta1`，`MANUAL UPGRADE REQUIRED` 是 `no`，说明这次不需要手工迁移组件配置。

这张计划表回答了两个问题。哪些东西由 `kubeadm upgrade apply` 负责？控制面静态 Pod 和 kube-proxy、CoreDNS 这些 addon。哪些东西 kubeadm 不碰？三个 kubelet。kubelet 在节点上由系统包管理，kubeadm 只负责生成它的配置；所以计划表把它们单独列在“必须手动升级”里。输出最后还有一句 `Note: Before you can perform this upgrade, you have to update kubeadm to v1.37.1.`：节点上的 kubeadm 还是 `v1.37.0`，得先换 kubeadm 二进制，再执行 `kubeadm upgrade apply v1.37.1`。

顺序因此是“控制面 → 其他控制面 → worker”。第一个控制面节点用 `kubeadm upgrade apply`，它会检查集群是否可升级、所有节点是否 Ready、控制面是否健康，执行版本偏差策略，拉取新镜像，替换控制面静态 Pod，更新 CoreDNS 和 kube-proxy，并在这个节点上续 kubeadm 管理的证书。其余控制面节点用 `kubeadm upgrade node`，不再需要 `upgrade plan`，也不需要在每个节点上重复升级 CNI。worker 也是 `kubeadm upgrade node`，但要一台一台来，先 drain 再动 kubelet，保证业务容量。官方文档明确要求：做 minor 版本的 kubelet 升级前必须先 drain 节点，因为控制面节点上也可能跑 CoreDNS 这类关键 Pod。

版本偏差有三条常用边界。kubectl 与 apiserver 最多差一个 minor：1.37 的 kubectl 可以连 1.36、1.37、1.38 的控制面，超出这个范围不保证兼容。kubelet 可以比 kubeadm 旧最多三个 minor：kubeadm 1.37 可以配 1.37、1.36、1.35、1.34 的 kubelet；这条来自 kubeadm 的偏差说明，反过来“kubelet 比 apiserver 新”是不推荐的。Kubernetes 项目只为最近三个 minor 维护发布分支（官方版本偏差策略页的原话是 “maintains release branches for the most recent three minor releases”），安全修复也只回移到这三个分支；1.37 发布后，1.34 及更早的 minor 就不再有补丁。

升级前还要做两件与版本号无关的事。第一，读 release notes 和弃用清单，确认要删的 API 没有被自己的清单使用；`kubectl convert -f pod.yaml --output-version v1` 可以把旧 `apiVersion` 的清单转成新版本；它是需要单独安装的 `kubectl-convert` 插件，而且转换只改 API 版本，不保证行为不变。第二，备份 etcd 和业务数据。`kubeadm upgrade` 不碰工作负载，但控制面升级期间 apiserver 会短暂不可用，升级 etcd 时还会重启 etcd 静态 Pod；官方文档建议在升级 etcd 前先做快照，并在升级前停几秒 apiserver，让在途请求结束。升级失败时，kubeadm 会把 etcd 数据和静态 Pod 清单备份到 `/etc/kubernetes/tmp/kubeadm-backup-*`，可以用它回滚；这个目录不会自动清理，升级完要手工删。

在 kind 里，这一节只做到 `upgrade plan`。kind 的“节点”是 Docker 容器，Kubernetes 版本由节点镜像决定；换 minor 或 patch 通常要新建一个使用新 `kindest/node` 镜像的集群，再把工作负载迁过去，而不是在容器里 `apt upgrade kubelet`。kind 没有提供原地升级集群的命令，换 Kubernetes 版本的常规做法是用新版本的节点镜像重建集群；本书的升级演练用 kubeadm 在节点里完成，只用来展示 kubeadm 的升级流程。真实集群的升级演练应该在预发环境按同样的“控制面 → worker”顺序走一遍，记录每一步的耗时和回滚点，再排生产窗口。

## 36.2 etcd 快照与恢复

Kubernetes 的所有 API 对象最终都存在 etcd 里：Deployment、Service、Secret、RBAC、CRD，连 Lease 和 Event 也在。apiserver 本身不持久化业务状态，它把对象写进 etcd 再读出来。因此 etcd 的快照就是“某一刻整个集群的对象图”，而恢复 etcd 就是把这张图退回到那个时刻。这个特性既是保险，也是陷阱：它保的是 Kubernetes 对象，不是 PV 里的数据，也不包括快照之后发生的任何变更。


etcd 在控制面节点上是一个静态 Pod，节点上没有单独的 etcd 服务。示例先用 `crictl ps --name etcd -q` 找到容器 ID，再用 `crictl exec` 在这个容器里调用 `/usr/local/bin/etcdctl`。这和直接 ssh 到一台独立 etcd 机器上执行 `etcdctl` 是一回事，只是 etcd 跑在容器里。三个证书参数对应 etcd 静态 Pod 的 `--trusted-ca-file`、`--cert-file`、`--key-file`：`ca.crt` 用来验证 etcd 服务端，`server.crt`/`server.key` 是 etcd 自己的服务端证书和私钥；示例把它们同时当作客户端证书用，生产上可以给 etcdctl 单独签一套客户端证书。`--endpoints=https://127.0.0.1:2379` 走本机回环，不经过网络。

`snapshot save` 的输出是几条 JSON 日志，最后两行是 `Snapshot saved at ...` 和 `Server version 3.7.0`。这个文件 13 MB，`etcdutl snapshot status` 把它当成一个独立的数据库打开，给出五列：`HASH` 是快照内容的校验值，`REVISION` 是 etcd 的全局修订号，`TOTAL KEYS` 是键的数量，`TOTAL SIZE` 是文件大小，`VERSION` 是 etcd 版本。`TOTAL KEYS` 包含所有 namespace 里的对象、系统对象和控制器写入的状态；`REVISION` 每次写操作都会增加，所以每次拍快照的数值不同，正文不应该引用具体数字。状态表能打开，说明文件没有在复制过程中损坏；要验证内容是否可用，还是得在演练环境里真的恢复一次。

`etcdctl snapshot status` 和 `etcdctl snapshot restore` 从 etcd 3.5 起标记为废弃，计划在 3.6 移除；官方推荐用 `etcdutl` 做离线校验和恢复。示例因此用 `etcdutl snapshot status`。`etcdctl snapshot save` 仍然是对运行中的成员做在线快照的入口，它通过 etcd 的维护 API 读取一致的状态，不需要停 etcd。快照文件最后用 `docker cp` 复制到 lab 的 `/tmp/ch36-etcd-snapshot.db`，再用 `sha256sum` 记下摘要。真实环境这一步之后还要传到集群外的对象存储、加密、设置保留期，并且把“快照文件能不能解密、能不能恢复”纳入定期演练；把快照和 etcd 数据放在同一块盘上，等于没有备份。

```console

```

恢复演练先制造一个“快照之后才存在”的对象：`post-snapshot-marker` ConfigMap。然后按官方顺序停掉 apiserver、controller-manager、scheduler。这三个都是静态 Pod，kubelet 通过监视 `/etc/kubernetes/manifests` 来管理它们；把清单移到 `/tmp/ch36-manifests`，等 `crictl ps --name kube-apiserver` 只剩表头，就说明 apiserver 容器已经退出。此时 `kubectl` 不能再用了，后面的检查都走节点上的 `crictl` 和 `docker exec`。

恢复用 `etcdutl snapshot restore` 写到 `/var/lib/etcd/restored`，而不是覆盖正在使用的 `/var/lib/etcd`。`--name`、`--initial-cluster`、`--initial-advertise-peer-urls` 必须和 etcd 静态 Pod 清单一致：清单里的 peer URL 是 `https://<节点 IP>:2380`，快照里记录的成员信息会被 etcdutl 裁掉，重新生成一个单成员集群，如果不显式给这些值，etcd 起来后会因为成员 URL 不匹配而退出。示例从清单里读出 `PEER`，再原样传给 etcdutl；节点 IP 每次建集群都可能不同，所以不能写死。

恢复完先别急着起 apiserver。把 etcd 清单也移走，等 etcd 容器退出，再把清单里的 `volumes.hostPath.path` 从 `/var/lib/etcd` 改成 `/var/lib/etcd/restored`，放回清单目录。kubelet 看到新清单会重建 etcd 容器，它现在读的是恢复出来的数据。确认 etcd 容器 Running 之后，再把 apiserver、controller-manager、scheduler 的清单放回去，轮询 `/readyz` 直到返回 `ok`。这个顺序很重要：如果 apiserver 先起来而 etcd 还没准备好，apiserver 会不断重连、日志里全是 `connection refused`，控制器也会反复重启。

恢复后的 `kubectl get nodes` 显示三个节点都 Ready，`kubectl -n shorty get pods -o wide` 显示 api、postgres、redis、worker、Gateway 都还在，Pod 名字和恢复前一样。原因不是 apiserver 把 Pod 重建了，而是 kubelet 和容器运行时一直没有停：apiserver 不在的时候，已经运行的容器继续跑，kubelet 继续管理它们并反复尝试连接 apiserver；新的 API 请求（创建、更新、删除、调度）全部失败。等 apiserver 回来，它从 etcd 里读到的 Pod 对象还是快照里的那些，kubelet 也还在原节点上，所以对象和容器对得上。

`post-snapshot-marker` 的 `NotFound` 是这次演练的重点：快照之后创建的 ConfigMap 没有回来。同理，快照之后扩容出来的 Pod、改过的 Secret、删除的 Deployment，都会回到快照时刻的状态。恢复不是“把集群修好”，而是“把集群退回到某个时间点”；这之后必须重新 apply 期望的清单，或者从 GitOps 重新同步。对 shorty 来说，etcd 快照能找回 Deployment 和 Service，但找不回 postgres 表里的短链；那部分要靠 `pg_dump`、WAL 归档或存储卷快照，和 etcd 快照是两套备份。

恢复时最常见的错误是 `data-dir ... not empty or could not be read`。etcdutl 不允许往一个已经有数据的目录里恢复，解决办法是换一个新目录（示例里的 `/var/lib/etcd/restored`），或者先停 etcd、清空旧目录再恢复。不要为了省事直接 `rm -rf /var/lib/etcd`：先确认 etcd 已停、快照可用、旧数据不再需要。恢复后 apiserver 起不来，排查顺序是证书（apiserver 的 `--etcd-certfile`/`--etcd-cafile` 是否能连 etcd）、`--etcd-servers` 是否指向正确的地址、data-dir 的属主和权限是否能被 etcd 进程读写。这三项在 36.7 会再出现一次。

这次演练的快照只有 13 MB，恢复看起来很快，但不要把 lab 的数字当成生产 RTO。真实集群的 etcd 可能几十 GB，恢复要重放 WAL、重建 apiserver 缓存，还要等控制器和 CNI/CSI 恢复；RTO 只能用自己集群的快照定期演练来测。演练时记录四个时间点：开始停控制面、etcd 恢复完成、apiserver ready、所有工作负载 Ready。只测到 apiserver ready 不够，shorty 的 Gateway 和 postgres 可能还要更久。

## 36.3 节点维护：cordon/drain/uncordon

给节点打内核补丁、换网卡、扩内存，都要先把上面的 Pod 挪走。Kubernetes 把这件事拆成两个动作：`cordon` 只把节点标记为不可调度，新的 Pod 不再落上来，已有的 Pod 继续跑；`drain` 在 cordon 的基础上，用 Eviction API 把 Pod 一个个驱逐，并遵守 PodDisruptionBudget（PDB）。`uncordon` 把标记去掉，让节点重新可调度。三个命令的分工很清楚：cordon 是“不再接新活”，drain 是“把现有的活挪走”，uncordon 是“恢复接活”。

```console
{{#include code/ch36/36_4_drain_node.out}}
```

示例先建了 4 个只跑 `sleep` 的 Pod，并用一条软反亲和规则让它们尽量避开 postgres 所在的节点。postgres 用的是 kind 自带的 `local-path` 卷，PV 绑定在某个节点上；把 postgres 驱逐到另一台节点，它起不来，因为卷跟不过去。输出里的 `postgres 在 ...，维护 ...` 一行给出这次的实际节点：postgres 在哪台，示例就选另一台做维护。4 个演示 Pod 都落在被维护的节点上：软反亲和只避开 postgres，不避开自己，调度器把能放下的都放在同一个节点，这在容量足够时很常见。

`kubectl drain "$TARGET" --ignore-daemonsets --delete-emptydir-data --timeout=180s` 的输出分几段。第一行 `node/<被维护节点> cordoned` 说明它先做了 cordon；接着 `Warning: ignoring DaemonSet-managed Pods: kube-system/kindnet-..., kube-system/kube-proxy-...` 说明 DaemonSet 的 Pod 被跳过，drain 不会删它们，因为 DaemonSet 控制器会立刻在原地重建；然后是一串 `evicting pod` 和 `pod/... evicted`，包括 api、redis、worker、Gateway、migrate Job 和 4 个演示 Pod；最后 `node/<被维护节点> drained` 表示普通 Pod 都已驱逐完。`--timeout=180s` 是整次 drain 的全局时限，不是单个 Pod 的宽限期；超过这个时间 drain 会报错并留下 cordon 状态，需要手工 `uncordon`。

驱逐走的是 Eviction API，不是直接 DELETE，所以 PDB 会生效。`s4-prod` 里 api 的 PDB 是 `minAvailable: 1`，api 有 2 个副本；drain 先驱逐其中一个，PodDisruptionBudget 控制器允许，因为还剩 1 个可用；新 Pod 在另一个 worker 上起来后，再驱逐第二个，仍然满足预算。如果 PDB 是 `minAvailable: 2` 而只有 2 个副本，第一个驱逐就会被拒绝，drain 会一直重试到超时。36.7 会用 1 副本 + `minAvailable: 1` 复现这个错误。

`kubectl get nodes` 里被维护节点的状态是 `Ready,SchedulingDisabled`，这是 cordon 的正常表现：节点还健康，只是不接新 Pod。`kubectl -n shorty get pods --field-selector spec.nodeName=$TARGET` 返回 `No resources found`，说明普通 Pod 都走了；DaemonSet 的 kindnet 和 kube-proxy 还在，但它们不会出现在 shorty namespace 里。4 个演示 Pod 全部到了另一台 worker，因为被维护节点 cordon 后，只有它有资格接收新 Pod。

`kubectl uncordon "$TARGET"` 之后节点回到 `Ready`，但已经迁到另一台 worker 上的 Pod 不会自动搬回来。Kubernetes 的调度器只决定“新 Pod 放哪”，不做运行中 Pod 的再平衡；要让它们回去，得触发一次滚动更新（改模板、`kubectl rollout restart`）或者删掉 Pod 让控制器重建。这也是为什么维护后不要只看节点 Ready，还要看 Pod 的分布和 PDB 的 `ALLOWED DISRUPTIONS` 是否恢复。

维护前要确认四件事。副本数够不够：如果某个 Deployment 只有 1 个副本，drain 期间业务会中断。PDB 合不合理：`minAvailable` 等于副本数会让 drain 卡住，`maxUnavailable` 也要留出至少 1 个可动。有没有本地卷：`local-path`、hostPath、`ReadWriteOnce` 的 PV 绑定在节点上，驱逐后 Pod 可能一直 Pending，drain 本身却会成功。有没有 emptyDir：emptyDir 的数据随 Pod 删除而丢失，drain 默认拒绝删这类 Pod，必须显式加 `--delete-emptydir-data` 才继续。

DaemonSet 的 Pod 要用 `--ignore-daemonsets` 跳过。`kubectl drain` 的帮助写得很清楚：有 DaemonSet 管理的 Pod 时，不加这个参数 drain 不会继续；即使加了，drain 也不会删这些 Pod，因为 DaemonSet 控制器会立刻在同一个节点重建，删了没有意义。节点要下线时，这些 Pod 随节点一起消失；节点还在维护时，它们继续跑。

`--force` 是另一回事。它允许 drain 删除没有控制器管理的 Pod（裸 Pod），或者在控制器对象已经丢失时继续。它不会让 PDB 失效，也不会帮你保留 emptyDir 数据；用之前要确认那个 Pod 删了不会有人重建。真正会绕过 PDB 的是 `--disable-eviction`，它强制用 DELETE 而不是 Eviction API；这个参数只适合 break-glass，平时不要用。

> **旧资料提示**：旧教程里的 `kubectl drain --delete-local-data` 在今天已经不存在。kubectl 1.37 的 `kubectl drain --help` 里只有 `--delete-emptydir-data`，帮助文本是“Continue even if there are pods using emptyDir (local data that will be deleted when the node is drained)”。kubectl 1.20 引入了新名字 `--delete-emptydir-data`，旧的 `--delete-local-data` 进入弃用；本章实测 kubectl 1.37 的 `drain --help` 里已经没有旧参数。看到旧命令直接换成 `--delete-emptydir-data`。

## 36.4 证书、KMS 与密钥轮换

Kubernetes 的控制面是一条 TLS 链：kubectl 连 apiserver 要验证 apiserver 的服务端证书，apiserver 连 kubelet 和 etcd 要出示客户端证书，kubelet 向 apiserver 注册也要客户端证书。任何一环过期，症状都不是“证书错误”这么干净：apiserver 可能直接起不来，kubelet 可能一直 NotReady，etcd 可能拒绝 apiserver 的连接。证书检查应该和磁盘、内存一样，是定期巡检项，而不是等出事再查。


`kubeadm certs check-expiration` 列出两类东西。上半部分是 `/etc/kubernetes/pki` 下的叶子证书和内嵌在 kubeconfig 里的客户端证书：`admin.conf`、`apiserver`、`apiserver-etcd-client`、`apiserver-kubelet-client`、`controller-manager.conf`、`etcd-healthcheck-client`、`etcd-peer`、`etcd-server`、`front-proxy-client`、`scheduler.conf`、`super-admin.conf`。下半部分是三个 CA：`ca`、`etcd-ca`、`front-proxy-ca`。叶子证书的 `RESIDUAL TIME` 是 `364d`，CA 是 `9y`，因为 kubeadm 默认给叶子证书 1 年、CA 10 年。`EXTERNALLY MANAGED` 这一列在我们的集群里全是 `no`；如果某个证书由外部 CA 签发，这里会是 `yes`，kubeadm 就不负责续它。

`kubelet.conf` 不在列表里。kubeadm 把 kubelet 配成自动轮换客户端证书，证书放在 `/var/lib/kubelet/pki`，kubelet 在证书快到期时自己生成新密钥、发 CSR、取回新证书；`rotateCertificates: true` 就是这个行为。它和 apiserver 的叶子证书是两套生命周期，检查时不要漏掉。服务端证书的自动轮转是另一个开关（`serverTLSBootstrap`），需要 apiserver 批准 CSR；没开的话，kubelet 服务端证书仍然要手工管。

第二段 awk 把 `RESIDUAL TIME` 里以 `d` 结尾、数值小于等于 30 的项打印出来；这次输出是 `30 天内到期: 0 项`。生产里应该反过来：把“剩余天数小于 30”做成告警，而不是等人来看表。30 天是常见的预警线，不是 Kubernetes 的默认值；窗口多长取决于你续证书要多久、要不要走变更审批。CA 的 `9y` 看起来很远，但 CA 轮换比叶子证书复杂得多。

续期前先记下 apiserver 证书的序列号和 `notAfter`，执行 `kubeadm certs renew all` 后再看一次。输出里两次 `serial` 不同，说明文件确实重新签过；`notAfter` 往后推了一年，但因为两次操作只差几分钟，日期看起来只差几分钟，不会在日期上跳一年。`check-expiration` 里 apiserver 的 `RESIDUAL TIME` 仍然是 `364d`，原因相同；不要因为天数没变就以为没续。

`kubeadm certs renew all` 的输出逐条列出续了哪些证书：admin、apiserver、apiserver 访问 etcd、apiserver 访问 kubelet、controller-manager、etcd healthcheck、etcd peer、etcd server、front-proxy、scheduler、super-admin。最后一句是重点：`You must restart the kube-apiserver, kube-controller-manager, kube-scheduler and etcd, so that they can use the new certificates.` 续期只改磁盘上的文件，正在运行的进程还拿着旧证书。静态 Pod 不能直接 `kubectl delete`，要把 `/etc/kubernetes/manifests` 里对应的清单移走，等 kubelet 停掉容器，再放回去让它重建；apiserver 重启期间 API 会短暂不可用，要在维护窗口做。示例没有重启，所以输出里的序列号是“文件里的新证书”，不是“apiserver 正在用的证书”；生产上这两者要分开确认。

`kubeadm upgrade` 会自动续它管理的证书，所以“每年至少升级一次控制面”同时解决了版本和证书两件事。如果不想让它续，可以给 `kubeadm upgrade apply` 或 `kubeadm upgrade node` 加 `--certificate-renewal=false`。kubeadm 不能管理外部 CA 签的证书；CA 本身的轮换 kubeadm 也不支持开箱即用，官方指向手工轮换 CA 的流程。CA 轮换要同时换信任包和叶子证书，顺序错了会让集群在中间状态不可用；这件事要单独演练，不要和普通 patch 升级混在一起。

KMS 是另一层。默认的 `identity` provider 不加密 etcd 里的数据，Secret 在 etcd 里是明文；`EncryptionConfiguration` 可以选 `aescbc`、`aesgcm`、`secretbox` 或 `kms`。本地密钥（前三种）能防 etcd 盘被偷，但防不了主机被攻破，因为密钥文件就在控制面主机上。KMS 用信封加密：apiserver 用 DEK 加密对象，DEK 再由远程 KMS 的 KEK 加密；攻击者要同时拿到 etcd 和 KMS 才能解密。KMS v2 在 Kubernetes 1.29 稳定，v1 在 1.28 弃用、1.29 起默认关闭；新集群应该直接用 v2。

KMS v2 的密钥轮换靠 `key_id`。apiserver 大约每分钟轮询一次 KMS 插件的 `Status`，`key_id` 变了就认为远程 KEK 换了；它会在后续写操作中用新 KEK 重新包 DEK，旧数据在下一次写时被标记为 stale。官方建议 KEK 至少每 90 天轮换一次，因为无法控制一个 DEK 被写了多少次。轮换不是瞬间生效：apiserver 会以最后一次有效状态继续工作约三分钟，插件观察到 `key_id` 变化还需要时间，所以要留出 `3 + N + M` 分钟的迁移窗口。用本地密钥时，`EncryptionConfiguration` 的 key 也要轮换，改完配置后用 `kubectl get secrets --all-namespaces -o json | kubectl replace -f -` 把所有 Secret 重写一遍，让它们用新 key 重新加密；apiserver 加 `--encryption-provider-config-automatic-reload=true` 可以每分钟自动加载新配置，不用重启。

备份加密要和 etcd 快照一起考虑。快照里可能包含 Secret 的密文，也可能包含明文（如果没开加密）；加密密钥不能和快照放在同一个地方，否则拿到快照的人也能解密。KMS 的 KEK 在远程 KMS 里，etcd 快照里只有被 KEK 包住的 DEK，这是它比本地 key 文件强的地方；代价是恢复时 KMS 必须可用，否则 apiserver 读不出 Secret。演练 etcd 恢复时要把“KMS 可用”作为前置条件写进去。

## 36.5 节点关机、swap 与 kubelet 配置

节点不会总是优雅地退出。计划内的重启会先发 SIGTERM，计划外的断电、内核 panic、云主机被回收则不会。Kubernetes 对这两种情况的态度不同：能提前感知的关机，kubelet 可以按顺序终止 Pod；感知不到的关机，只能靠节点控制器在超时后把节点标记为不可用，再由管理员用 out-of-service 污点强制迁移。理解这套机制，才知道 `kubectl get nodes` 里的 `NotReady` 之后会发生什么。

```console
{{#include code/ch36/36_6_node_shutdown.out}}
```

示例先选了一个没有 postgres 的 worker。输出里的 `postgres 在 ...，停 ...` 一行给出这次的实际节点：postgres 的 local-path 卷绑在它所在的节点上，示例停的是另一台，不会把它卷进去。`docker exec` 读 kubelet 配置，看到四行：`failSwapOn: false`、`memorySwap: {}`、`shutdownGracePeriod: 0s`、`shutdownGracePeriodCriticalPods: 0s`。这说明 kind 节点允许 kubelet 在 swap 存在时启动，但没有给 Pod 分配 swap（`memorySwap` 为空，默认 `NoSwap`）；关机的两个 grace period 都是 0，所以优雅关机实际上没有启用。

为了有 Pod 可迁，示例在停节点前重新建了 4 个 `maintenance-demo` Pod；软反亲和让它们先落在没有 postgres 的那台 worker 上，输出里能直接看到这 4 个 Pod。`docker stop "$TARGET"` 模拟节点直接关机，而不是先 drain。kubelet 不再续 Lease，节点控制器在 `--node-monitor-grace-period`（默认 50 秒）之后把 Ready 条件置为 `Unknown`。输出里 `Ready condition: Unknown`，`kubectl get node` 的 STATUS 列显示 `NotReady`。这时候节点上的 Pod 在 API 里还是 `Running`，因为 kubelet 已经不在，没人去删它们；节点控制器默认还要再等 5 分钟，才会对失联节点上的 Pod 发起驱逐。这个 5 分钟是节点控制器的默认行为，不能靠 `--node-monitor-grace-period` 缩短；急着迁移只能用 out-of-service 污点。

`kubectl taint node "$TARGET" node.kubernetes.io/out-of-service=nodeshutdown:NoExecute` 是官方给非优雅关机的开关。加上这个污点后，不能容忍它的 Pod 会被强制删除，卷的 detach 也会立即执行，不用等 5 分钟。`NodeOutOfServiceVolumeDetach` 在 1.24 是 alpha、1.26 是 beta、1.28 稳定；它解决的正是“节点已经没了，StatefulSet 的 Pod 还卡在 Terminating，卷也挂在新节点上”的问题。示例加完污点后，api 和 `maintenance-demo` 的 `rollout status` 都走到成功，原节点上的 Pod 数变成 0，新 Pod 全部到了另一台 worker 上。Gateway 的 Pod 在输出截取时是 `0/1 Running`，还没 Ready；这类组件恢复比 api 慢，检查时要多看一步。

这个污点不能随手加。官方要求先确认节点真的已经关机或断电，而不是正在重启；加错了会把还活着的节点上的 Pod 强删。节点恢复后要先等它 Ready，再摘掉污点；示例最后 `kubectl wait --for=condition=Ready` 返回 `condition met`，`kubectl taint ... out-of-service-` 返回 `untainted`，三个节点都回到 Ready。如果节点永远回不来，Pod 会被迁走，但节点对象和它的本地卷还需要人工清理。

如果关机是计划内的，应该让 kubelet 做优雅关机，而不是靠污点。`GracefulNodeShutdown` 在 1.21 进入 beta 并默认启用，但它依赖 systemd 的 inhibitor lock；kubelet 检测到关机后把 Node 标成 NotReady，reason 是 `node is shutting down`，拒绝新 Pod，然后分两阶段终止 Pod：先普通 Pod，再 critical Pod。两个配置项 `shutdownGracePeriod` 和 `shutdownGracePeriodCriticalPods` 默认都是 0，必须都设成非零值才会生效。比如总宽限 30 秒、critical Pod 留 10 秒，那么前 20 秒给普通 Pod，后 10 秒给 critical Pod。`GracefulNodeShutdownBasedOnPodPriority` 在 1.23 alpha、1.24 beta 并默认启用，可以按 PriorityClass 再细分每个优先级段的关机时间。

kind 节点的 kubelet 配置里两个 grace period 都是 0，所以 `docker stop` 不会走优雅关机；这也解释了为什么 Pod 在节点失联后还挂在那里。真实节点要在节点池的 kubelet 配置里显式设置这两个值，并且确认 systemd 的关机流程会给 kubelet 足够时间。Debian 的 `unattended-upgrades` 默认配置会改关机宽限，官方特别提醒它和优雅关机冲突：如果 `shutdownGracePeriod` 大于 30 秒，kubelet 可能拿不到 inhibitor lock，优雅关机失效。

swap 是另一个和节点行为相关的开关。`NodeSwap` 在 1.22 alpha、1.28 beta、1.34 稳定；Linux 节点默认不允许 kubelet 在 swap 开启时启动，要用 swap 必须设 `failSwapOn: false`，并在 `memorySwap.swapBehavior` 里选 `NoSwap` 或 `LimitedSwap`。`NoSwap` 是默认值，Pod 不能用 swap，但系统进程和 kubelet 自己仍然可以用；`LimitedSwap` 只允许 Burstable QoS 的 Pod 用 swap，Guaranteed 和 BestEffort 不行，额度按 memory request 占节点总内存的比例算。调度器目前不考虑 swap，节点上有 swap 也不会让 Pod 更容易被放上来；swap 还会让延迟变得不可预测，内存压力下容易出现 noisy neighbor。控制面节点官方建议完全不配 swap；真要给工作负载用，选加密的独立磁盘，并把 kubelet 的驱逐阈值设在 `vm.min_free_kbytes` 之下，让内核先换页、kubelet 后驱逐。

kubelet 的配置应该走 `KubeletConfiguration` 文件，而不是继续堆命令行 flag。kubeadm 生成的配置在 `/var/lib/kubelet/config.yaml`，kubelet 用 `--config` 指向它；`shutdownGracePeriod`、`failSwapOn`、`memorySwap`、`rotateCertificates` 这些字段都在这个文件里。Kubernetes 1.28 起还支持 `--config-dir` 的 drop-in 目录，按文件名排序合并，后缀必须是 `.conf`；命令行参数仍然可以覆盖配置文件里的同名字段，但旧的那些 `--shutdown-grace-period` 之类 flag 已经标记为 deprecated，应该迁移到配置文件。改完配置要重启 kubelet，重启前先 `systemctl cat kubelet` 确认它加载的是哪个 `--config`，否则改了文件也不生效。

## 36.6 多集群：先分清 HA 与多集群

“高可用”和“多集群”经常被混着说，但它们解决的不是同一个问题。单集群 HA 是同一个集群里放多个控制面节点和多个 etcd 成员，靠 quorum 和负载均衡扛住单台机器故障；多集群是多个独立的 apiserver/etcd 集群，各自有独立的身份、网络和存储。一个集群即使有三个控制面节点，它仍然是一个集群；反过来，起两个单控制面的集群，也不会让其中任何一个变成 HA。

kubeadm 的 HA 拓扑有两种。stacked etcd 把 etcd 成员和控制面组件放在同一批节点上，这是 kubeadm 的默认拓扑，最少三个控制面节点；external etcd 把 etcd 放在另一批节点上，控制面和 etcd 各至少三台，机器数量翻倍，但一边故障不会同时带走另一边。两种拓扑都需要一个负载均衡器把 apiserver 暴露给 worker，kubeadm 用 `--control-plane-endpoint` 指定这个地址。

> **旧资料提示**：旧教程里常见“手工搭三节点 etcd，再在前面放 HAProxy/Keepalived”。这套做法仍然能工作，但负载均衡、健康检查、证书和 etcd 成员都要自己维护；今天更常见的是 kubeadm 的 `--control-plane-endpoint`，或者直接用托管控制面，把 etcd 和 apiserver 的运维交给云厂商。

本书的 lab 是单控制面，没有做 HA 演练，这一段的拓扑结论来自官方 HA 页面，具体负载均衡器配置没有在本地验证。

多集群的动机通常是这几类：故障域隔离（一个 region 挂了，另一个 region 还能服务）、合规（数据必须留在某个国家或某个账户里）、就近访问（用户离集群近，延迟低）、团队或租户隔离（每个团队一个集群，避免互相影响）。Kubernetes 的多租户页面把“给每个租户一个专用集群”列为一种隔离手段，并指出它在托管 Kubernetes 上更容易做，代价是要管理多个集群的复杂度。多租户页面也提醒：专用集群的隔离更强，但不等于自动获得高可用；每个集群仍然要自己配控制面副本、etcd quorum、备份和升级。

```console
{{#include code/ch36/36_7_kubeconfig_contexts.out}}
```

多集群在客户端的第一层就是 kubeconfig。一个 context 是三元组：cluster（apiserver 地址和 CA）、user（客户端证书或 token）、namespace（默认命名空间）。`kubectl config get-contexts` 列出当前 kubeconfig 里的所有 context，`*` 是当前使用的那个；`kubectl config use-context` 只改客户端的选择，不改任何集群里的权限。示例先复制了一份 kubeconfig 到 `/tmp/ch36-kubeconfig`，后面的操作都在这份副本上做，不会污染 `~/.kube/config`。

示例加了一个名为 `unreachable` 的 cluster，server 指向 `https://127.0.0.1:1`，并加了一个使用它的 context。`--insecure-skip-tls-verify=true` 只是跳过 TLS 证书校验，不会让一个不存在的端口变得可连；`kubectl get nodes` 先打出几条 `memcache.go` 的发现失败日志，最后一行是 `The connection to the server 127.0.0.1:1 was refused - did you specify the right host or port?`。这些 `memcache.go` 行是 kubectl 在拉 API group 列表时的重试，不是集群坏了；真正的结论在最后一行：TCP 连接被拒绝。把 context 切回 `kind-shorty`，同一条 `kubectl get nodes` 立刻返回三个节点，说明 kubeconfig 的切换只影响“请求发往哪里”，不影响集群本身。

真实的多集群工具链不在这个 lab 里做完整示例。Cluster API 是 Kubernetes 的子项目，用声明式对象管理集群的生命周期（创建、升级、扩缩节点）；Karmada 做多集群的应用分发和调度；Submariner、Liqo 解决跨集群网络和资源；Istio 的多集群模式把服务网格铺到多个集群。选用前要按自己的场景评估这些项目的成熟度、版本兼容性和运维成本；本书没有在 lab 里安装它们，所以只讲边界，不给命令。它们共同的难点不是“怎么把两个集群连起来”，而是身份（每个集群有自己的 CA 和 RBAC，跨集群要统一认证）、网络（Pod/Service DNS 和 IP 段不能冲突，跨集群服务发现要额外组件）、数据（跨集群复制没有免费的一致性，写冲突要有业务策略）。

> **旧资料提示**：Federation v1（`federation.k8s.io` API）早已从 Kubernetes 移除，KubeFed 项目也已归档（SIG Multicluster 在 2022 年 11 月宣布，仓库于 2023 年 4 月归档，并推荐 Karmada 作为后继）；当前 1.37 的官方文档里已经没有 Federation 的条目。旧教程里“用 Federation 做多集群”的步骤不能照做，今天要用 Cluster API、Karmada 这类外部项目，版本和成熟度以各项目的发布说明为准。另外，多集群不是单集群 HA 的替代品：两个各只有一个控制面的集群，合起来仍然没有 quorum，任何一个集群的控制面挂了，它自己就不可用。

## 36.7 排障：drain 被 PDB 挡住、emptyDir 与 etcd data-dir

节点维护和 etcd 恢复的报错都很短，但每一条都指向一个具体的控制面对象或本地状态。这一节把四个最常见的错误放在一起跑一遍：PDB 挡住 drain、DaemonSet 没加 `--ignore-daemonsets`、emptyDir 没加 `--delete-emptydir-data`、etcd 恢复到非空目录。前三个发生在 drain，最后一个发生在恢复；它们的共同点是“命令没有错，缺的是一个显式决定”。


第一个例子是 1 个副本 + `minAvailable: 1` 的 PDB。`pdb-demo` 只有一个 Pod，PDB 要求至少 1 个可用，`ALLOWED DISRUPTIONS` 是 0；drain 一尝试驱逐就报 `Cannot evict pod as it would violate the pod's disruption budget.`，重试几次后全局超时。`kubectl get pdb` 和 `kubectl get deployment` 放在一起看最清楚：`MIN AVAILABLE` 是 1，`READY` 是 `1/1`，没有任何余量。先加副本（比如 2 个），让 `ALLOWED DISRUPTIONS` 变成 1，或者临时把 PDB 的 `minAvailable` 调到 0；示例选了后者，因为演示环境只有一个副本。生产更推荐先加副本，再把 PDB 改回去；调低 PDB 会让维护窗口内的可用性下降，不能当成常态。

drain 失败后节点仍然是 cordon 状态，输出里的 `node/... cordoned` 不会自动撤销。解决 PDB 后要重新执行 drain，或者先 `kubectl uncordon` 再重来；不要以为命令退出了节点就恢复了调度。`--disable-eviction` 可以绕过 PDB，但它直接用 DELETE，等于放弃 Eviction API 的保护；只在确认业务可以中断时用，平时不要把它当成“让 drain 过去”的捷径。

第二个例子是不加 `--ignore-daemonsets`。drain 在节点上看到 kindnet 和 kube-proxy 这两个 DaemonSet 的 Pod，直接报 `cannot delete DaemonSet-managed Pods (use --ignore-daemonsets to ignore)`，命令退出，节点保持 cordon。DaemonSet 的 Pod 不能靠 drain 迁走：DaemonSet 控制器会把它们在同一节点重建，而且它们能容忍 unschedulable 污点。维护时加 `--ignore-daemonsets` 跳过它们；节点真的要下线时，这些 Pod 随节点一起消失，不需要提前删。

第三个例子是 emptyDir。`emptydir-demo` 把 `/data` 挂成 emptyDir，drain 默认拒绝删它，报 `cannot delete Pods with local storage (use --delete-emptydir-data to override)`。emptyDir 的生命周期和 Pod 绑定，Pod 一删数据就没了；drain 让你显式确认这件事。确认数据可以丢之后加 `--delete-emptydir-data`，drain 继续，Pod 被驱逐；如果数据不能丢，应该先把数据复制出来，或者把 emptyDir 换成 PVC。注意 `--delete-emptydir-data` 只影响 emptyDir，不会处理 hostPath 或本地 PV；本地卷的 Pod 被驱逐后可能因为卷的节点亲和性一直 Pending，drain 本身却会成功。

第四个例子是 etcd 恢复。`etcdutl --data-dir /var/lib/etcd snapshot restore` 报 `data-dir "/var/lib/etcd" not empty or could not be read`，因为这个目录里已经有数据（可能是 etcd 当前或之前的 data-dir）。正确做法是换一个新目录（示例恢复时用的是 `/var/lib/etcd/restored`），或者先停 etcd、确认快照可用、清空旧目录再恢复。不要在 etcd 运行时 `rm -rf` 数据目录；那会把正在写的 WAL 和 db 一起删掉，连回滚的机会都没有。

最后一段输出是 apiserver 起不来时的检查顺序。先看 `/etc/kubernetes/manifests/kube-apiserver.yaml` 里的 `--etcd-servers`、`--etcd-cafile`、`--etcd-certfile` 是否指向恢复后的 etcd 和正确的证书；再看 etcd 清单里的 `--data-dir`，确认它和恢复出来的目录一致；最后 `ls -ld` 看数据目录的属主和权限，etcd 进程必须能读写。示例里的 `ls -ld /var/lib/etcd` 看的是父目录，实际 `--data-dir` 可能是它下面的 `restored` 之类的子目录，要以清单为准。apiserver 的容器日志用 `crictl ps -a --name kube-apiserver` 找到退出的容器，再 `crictl logs <id>` 看具体报错；如果是证书过期或 SAN 不匹配，日志里会有 `x509`；如果是连不上 etcd，会有 `connection refused` 或 `context deadline exceeded`。这三类原因对应三种修法，不要一上来就重建集群。

## 上生产前

升级的顺序是控制面 → 其他控制面 → worker，每一台 worker 先 drain 再动 kubelet；升级前读 release notes 和弃用 API，确认 CNI/CSI/设备插件有对应版本，备份 etcd 和业务数据，并保留回滚路径。`kubeadm upgrade apply` 失败时可以重跑，它会把 etcd 数据和静态 Pod 清单备份到 `/etc/kubernetes/tmp`；不要把“升级”和“改集群配置”放在同一个窗口，`kubeadm upgrade` 不支持顺带重配集群，重配走单独的集群重配流程（`kubeadm-reconfigure` 任务页）。

etcd 快照要定期做、存到集群外、加密、设置保留期，并且定期在隔离环境里恢复演练。快照只包含 etcd 里的 Kubernetes 对象，不包含 PV 里的业务数据；postgres 的表要靠 `pg_dump`、WAL 归档或卷快照。恢复会把集群退回到快照时刻，快照之后创建或修改的对象都会丢，所以恢复后必须重新同步 GitOps/清单，并核对业务数据。RTO 要在自己的数据量上测，不能拿 lab 里 13 MB 的快照当生产指标。

节点维护用 cordon/drain/uncordon，不要直接关机。维护前确认副本数、PDB、local-path/hostPath 卷、emptyDir 数据和 DaemonSet；PDB 的 `ALLOWED DISRUPTIONS` 为 0 时先加副本或调整预算，不要用 `--disable-eviction` 硬闯。drain 失败后节点会保持 cordon，处理完原因要显式 `uncordon`；维护后 Pod 不会自动回到原节点，需要时用滚动更新重新分布。

证书和密钥要有到期监控。kubeadm 管理的叶子证书默认 1 年，CA 默认 10 年，`kubeadm upgrade` 会顺手续期；不升级的集群要单独 `kubeadm certs renew`，并在维护窗口重启 apiserver/controller-manager/scheduler/etcd。kubelet 客户端证书走自动轮换，不要和 apiserver 证书混在一个检查项里。KMS v1 已弃用，新集群用 KMS v2；KEK 至少 90 天轮换一次，本地 key 轮换后用 `kubectl replace` 重写 Secret，etcd 快照和加密密钥分开存放。

swap 和关机行为要按节点池配置，不要全集群一个默认值。`GracefulNodeShutdown` 的两个 grace period 默认是 0，不配就不会生效；swap 默认 `NoSwap`，要开 `LimitedSwap` 就得接受延迟和驱逐行为的变化，控制面节点不要配 swap。多集群先解决身份、网络和数据一致性，再谈工具；单集群 HA 是多控制面 + etcd quorum，多集群不能替代它。托管控制面或 kubeadm 的 `--control-plane-endpoint` 比手工 HAProxy/Keepalived 更省事，但负载均衡器和 etcd 的运维责任要写清楚。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `kubectl version` | 查客户端/服务端版本 | 客户端与服务端最多差 1 个 minor |
| `kubeadm upgrade plan vX.Y.Z` | 升级前检查，列控制面/节点组件目标版本 | 只做计划，不改集群 |
| `kubeadm upgrade apply vX.Y.Z` | 升级第一个控制面节点和 addon | 先升级 kubeadm 二进制；会续 kubeadm 管理的证书 |
| `kubeadm upgrade node` | 升级其余控制面节点或 worker 的配置 | worker 先 drain，再升级 kubelet |
| `kubectl cordon <node>` | 标记节点不可调度 | 不驱逐已有 Pod |
| `kubectl drain <node>` | cordon + 驱逐 Pod | 遵守 PDB；常配 `--ignore-daemonsets`、`--delete-emptydir-data` |
| `kubectl uncordon <node>` | 恢复节点调度 | 不会把已迁走的 Pod 搬回来 |
| `etcdctl snapshot save` | 在线保存 etcd 快照 | 需要 `--endpoints` 和 `--cacert/--cert/--key` |
| `etcdutl snapshot status` | 校验快照 | `etcdctl snapshot status` 自 3.5 起弃用 |
| `etcdutl snapshot restore` | 恢复到新 data-dir | 目标目录必须为空；`--name`/`--initial-cluster` 要和清单一致 |
| `kubeadm certs check-expiration` | 查证书到期 | 不含自动轮换的 kubelet 证书 |
| `kubeadm certs renew all` | 续 kubeadm 管理的证书 | 多控制面逐台执行；之后重启控制面组件 |
| `kubectl config get-contexts` | 列出 kubeconfig 的 context | context = cluster + user + namespace |
| `kubectl config use-context <name>` | 切换 context | 只改客户端，不改集群权限 |
| `failSwapOn` / `memorySwap.swapBehavior` | kubelet 的 swap 开关 | 默认不允许 swap 启动；`NoSwap` 是默认行为 |
| `shutdownGracePeriod` / `shutdownGracePeriodCriticalPods` | 优雅关机宽限 | 默认 0，必须都设非零才生效 |

本章结束时，`s4-prod` 已恢复健康：etcd 从快照恢复到 `/var/lib/etcd/restored`，快照文件留在集群外的 `/tmp/ch36-etcd-snapshot.db`；两个 worker 都做过 drain/uncordon，证书续期文件已生成，多集群只留下 `/tmp/ch36-kubeconfig` 里的一个不可达 context。下一章从这个健康的 `s4-prod` 继续。
