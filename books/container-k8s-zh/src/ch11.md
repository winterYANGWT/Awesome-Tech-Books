# 第 11 章 小而安全的镜像：基础镜像选择、非 root、漏洞扫描

shorty 的 api 在第 10 章已经缩到 20 MB 左右：一个静态编译的 Go 二进制，放在 `scratch` 里，没有 shell，没有包管理器。看起来该做的都做了。可把它和 worker 一起交给 Trivy 扫描，结果并不一样：`shorty:0.1` 报出 2 个 HIGH，全部来自 Go 依赖 `golang.org/x/text`；`shorty-worker:0.1` 报出 44 个 Debian 系统包 HIGH 和 4 个 Python 包 HIGH。镜像小，确实把操作系统那一大片 CVE 去掉了，但没有把语言依赖的 CVE 一起去掉。

这也是本章要回答的两个问题。第一个是“镜像越小越安全吗”：小只能说明携带的组件少，不能说明留下的组件没有漏洞，也不能说明构建方式、运行用户和元数据是正确的。第二个是“scratch 连 shell 都没有，出问题怎么排”：没有 shell 是安全设计，不是镜像坏了；排障要靠 `docker inspect`、`docker cp`、临时容器和节点上的 `crictl`，而不是往生产镜像里加一个 shell。

沿着这两个问题，本章先把同一个 shorty 二进制放进 alpine、python slim 和 scratch，量一量体积和 shell 的差别；再把最终镜像固定到 UID 65532、只读根文件系统和 tmpfs；然后扫描、生成 SBOM、跑构建检查、写 OCI 标签；最后处理“exec 找不到 sh”和“Trivy 报了一堆 CVE”这两个现场故障。

> **起点**：第 10 章结束时，lab 里已有 scratch 的 `shorty:0.1` 和 `shorty-worker:0.1`。本章不建 kind 集群，执行 `bash code/ch11/setup.sh` 会把 `shorty:0.1` 重建为起点状态（scratch、非 root、还没有 OCI 标签），构建 `shorty-worker:0.1`，拉取 `alpine:3.22`、`python:3.15.2-slim-trixie`、`busybox:1.37`、`registry:3.0.0` 和 `aquasec/trivy:0.76.1`，并把 Trivy 的漏洞库预下载到 `ch11-trivy-cache` 卷。漏洞库会随时间更新，示例里的 CVE 编号和数量以运行时的库为准；正文只引用这次运行的输出。

## 11.1 基础镜像的取舍

Dockerfile 的第一行 `FROM` 决定了后面所有层站在什么根文件系统上。官方文档把基础镜像分成几类：Docker Official Images、Verified Publisher 镜像，以及你自己用 tar 导入或从 `scratch` 搭的镜像。选择时先看来源是否可信，再看它是否只包含运行这个程序需要的东西；基础镜像里的每个包都会进入你的镜像，也会进入你的漏洞报告。

`scratch` 是最极端的一类。它不是可以从 registry 拉取、运行或打标签的镜像，只是 Dockerfile 里的一个保留名字，表示“下一层就是镜像的第一层文件系统”。官方文档明确说，用 `scratch` 构建的镜像只能运行不依赖其他程序或资源的二进制；一旦程序需要动态链接库、CA 证书或语言运行时，就得自己把这些文件复制进去。Go 的静态编译正好适合这种模式：`CGO_ENABLED=0` 加上 `-trimpath -ldflags="-s -w"`，产出一个不依赖 libc 的二进制，`scratch` 里只放它、证书和时区数据就够了。

distroless 介于 `scratch` 和完整发行版之间。它保留运行程序所需的运行时依赖，但去掉 shell、包管理器和调试工具，通常还带 CA 证书和非 root 用户。shorty 原来的 `app/api/Dockerfile` 写的是 `gcr.io/distroless/static-debian13:nonroot`，`nonroot` 这个标签表示默认以非 root 运行。本章不在 lab 里拉取 gcr.io 的 distroless 镜像，示例统一用 `scratch` 加手动复制 `/etc/ssl/certs/ca-certificates.crt` 和 `/usr/share/zoneinfo` 来等价演示；两种写法的安全边界接近，区别主要在 distroless 自带了一些运行时文件和非 root 用户。选 distroless 之前，仍然要看清楚它的标签里到底有什么。

distroless 也不是免费的。它没有 shell 和包管理器，意味着不能在运行中的容器里 `apt upgrade` 或 `apk add` 修一个包；基础镜像里的库出了 CVE，只能等上游发新镜像，或者自己基于它的 rootfs 重新构建。它也不提供交互式排障环境，出问题要靠临时容器和日志。选它之前要接受这两个约束，而不是只看“没有 shell 更安全”。

alpine 是另一种常见的“小”。它用 musl libc，自带 `/bin/sh` 和 `apk`，基础镜像只有十几 MB；代价是包管理器和 shell 都进了最终镜像，攻击面比 `scratch` 大，而且 musl 和 Debian slim 的 glibc 不是一回事。Go 静态二进制对 libc 不敏感，放 alpine 里能跑；Python 的 C 扩展、预编译 wheel 和某些依赖则要重新确认有没有 musl 版本。slim 是 Debian 的裁剪版，保留 glibc 和 `apt`，体积比 alpine 大得多，但对 Python 这类需要 glibc 和系统库的运行时更省事。Docker 的 Python 指南里能看到 `python:3.13-slim` 这样的写法；关键是固定小版本和发行版，不要用 `latest`。

Python 镜像的标签要看全。`python:3.15.2-slim-trixie` 同时固定了 Python 小版本和 Debian 发行版；只写 `3.15-slim` 会随 patch 漂移，只写 `slim` 更不行。alpine 的 `apk` 和 shell 让运行中的容器还能装软件，这既是排障的便利，也是攻击者的便利；如果选 alpine，至少不要在最终镜像里保留可写的包缓存和编译工具。

这一节把同一个 shorty 二进制分别放进这三种基础镜像，只比较基础镜像带来的体积和文件，不比较应用逻辑。为了让三个镜像跑同一个二进制，slim 那一份把 Go 二进制放进了 `python:3.15.2-slim-trixie`；它说明的是基础镜像的成本，不是说 Go 程序应该用 Python 镜像。真实的 Python 服务（比如 shorty-worker）才应该用 slim。

三个数字分别是 30.4 MB、202.3 MB 和 20.3 MB。alpine 比 scratch 多了约 10 MB，多出来的是 alpine 的根文件系统、`/bin/sh` 和 `apk`；slim 的 202.3 MB 里，绝大部分是 Python 运行时和 Debian 的用户态，shorty 的二进制只占约 13 MB。`--entrypoint sh` 让 alpine 和 slim 里的 shell 真的执行了 `echo shell=yes`，并分别打印出 `/sbin/apk` 和 `/usr/bin/apt-get`；scratch 那一份直接报 `exec: "sh": executable file not found`，但紧接着 `shorty:scratch version` 仍然输出 `shorty 0.1`，说明缺 shell 不影响程序本身。

基础镜像的标签同样重要。`alpine:3.22`、`python:3.15.2-slim-trixie` 都是具体版本，`latest` 不是。官方最佳实践说标签是可变的：同一个 `3.21` 今天可能指向 3.21.1，三个月后可能指向 3.21.4；要完全固定，就把 digest 一起写进 `FROM`，例如 `alpine:3.22@sha256:...`。固定 digest 的代价是不会自动收到安全更新，所以还要定期用 `--pull` 重建，或者让 Dependabot 之类工具定期改 digest。`--no-cache` 只重建构建步骤，不会拉新基础镜像；要新基础镜像得用 `--pull`。

## 11.2 非 root 与文件权限

镜像里的 `USER` 决定容器默认以哪个 UID/GID 启动。shorty 的最终镜像写的是 `USER 65532:65532`，一个不在 `/etc/passwd` 里的数字 UID（scratch 里根本没有这个文件）；数字比用户名稳定，换基础镜像时不会因为用户名不存在而启动失败。官方最佳实践也建议在需要固定身份时显式写 UID/GID，因为镜像构建时自动分配的“下一个 UID”并不保证每次相同。

```console
{{#include code/ch11/11_2_nonroot_run.out}}
```

`docker image inspect --format 'User={{.Config.User}}'` 读出 `User=65532:65532`，这是镜像配置里的默认用户；`docker run --rm shorty:0.1 version` 以这个身份启动，输出 `shorty 0.1`。但 `shorty:0.1` 里没有 `id`，所以后面的 busybox 探针换用同样 UID：`uid=65532 gid=65532 groups=65532`，接着 `touch /probe` 报 `Permission denied`。这不是 busybox 的问题，而是根目录属于 root，65532 没有写权限。

只读根文件系统把这个边界再收紧一层。`--read-only` 把容器的根挂载成只读，`--tmpfs /tmp` 单独给 `/tmp` 一个可写的内存文件系统；示例里写 `/tmp/shorty` 成功并读回 `ok`，去掉 `--tmpfs` 后同样的写入报 `Read-only file system`。这也解释了为什么应用只应该写 `/tmp` 或显式挂载的卷：根文件系统上的任何写入，在 `--read-only` 下都会失败；如果确实要写，就把那个目录做成 tmpfs 或卷，而不是把整个根文件系统改成可写。

`USER` 只是默认值，不是强制。`docker run --user 0:0` 可以把用户改回 root；真正把“必须非 root”变成准入要求的是 Kubernetes 的 `securityContext.runAsNonRoot` 和 Pod Security Standards。到了 Kubernetes 里，`readOnlyRootFilesystem: true` 对应这里的 `--read-only`，`emptyDir.medium: Memory` 对应 tmpfs；`runAsUser`/`runAsGroup` 则把 UID/GID 固定下来。

只读根文件系统会把应用平时藏起来的写入暴露出来。常见的例子是日志写到 `/var/log`、上传文件写到 `/app/uploads`、Python 写 `__pycache__`、Java 写临时文件；这些路径在可写根文件系统下不会报错，切成 `--read-only` 之后才集中失败。正确的修法是把需要写的目录显式做成 tmpfs 或卷，并让属主匹配运行 UID；如果只是把 `--read-only` 去掉，等于把刚收紧的边界又放开。

文件属主在构建时就该定好。`COPY --chown=65532:65532` 让复制进镜像的文件直接属于 65532，不需要再加一个 `RUN chown` 层；`shorty.Dockerfile` 里的二进制、证书和时区目录都用了这个写法。11.3 的 `docker export | tar -tv` 会看到 `65532/65532`，这是镜像里的真实属主；而 `docker cp` 到宿主机后显示 `root root`，那是宿主机用户的属主，不能用它判断镜像里的权限。

`COPY --chown` 只影响这次复制进去的文件，不会改变基础镜像里已有文件的属主；`/tmp` 的 1777 权限是基础镜像给的，不需要自己再 `chmod`。应用确实要写某个目录时，先在 Dockerfile 里创建目录、用 `COPY --chown` 放文件，或者挂一个属主正确的卷；这比把目录改成 777 更可控。

Python 服务还要注意字节码缓存。worker 的 Dockerfile 设了 `PYTHONDONTWRITEBYTECODE=1` 和 `PYTHONUNBUFFERED=1`：前者阻止 Python 在导入模块时写 `__pycache__`，后者让日志立即刷出。只读根文件系统下，`__pycache__` 写不进去只会产生警告或失败，提前关掉更干净。`PYTHONDONTWRITEBYTECODE` 只解决 `.pyc`，应用自己写的缓存、上传文件和临时文件仍要放到 `/tmp` 或卷里。不要用 `chmod 777` 解决权限问题：它把文件开放给所有用户，既掩盖了属主设计错误，也让被攻破的进程更容易改写文件。需要可写目录时，用 `COPY --chown` 定好属主，再配 tmpfs 或卷。

## 11.3 减小攻击面

最终镜像里应该只有运行程序需要的东西：二进制、CA 证书、时区数据，必要时再加配置文件。编译器、包管理器、shell、测试文件和源码都不应该出现在最终阶段。多阶段构建让这件事很自然：构建阶段用 `golang:1.27.3-trixie`，运行阶段从 `scratch` 开始，只 `COPY --from=build` 三个东西。`CGO_ENABLED=0` 保证二进制不依赖 libc，`-trimpath` 去掉构建机器的路径，`-ldflags="-s -w"` 去掉符号表和调试信息；这些都不会让程序少功能，但会让镜像更小、信息更少。

先看一个容易误判的地方。`shorty:0.1` 的 `Entrypoint` 是 `["/shorty"]`，`Cmd` 是 `["serve"]`；`docker run shorty:0.1 sh` 并不会去找 shell，它只是把 `sh` 追加成 `/shorty` 的参数，于是 shorty 打印用法后以 2 退出。要验证“镜像里没有 shell”，得用 `--entrypoint sh` 覆盖入口，或者对运行中的容器执行 `docker exec`。

```console
{{#include code/ch11/11_3_shell_absent.out}}
```

`docker run --rm --entrypoint sh shorty:0.1 -c 'echo hi'` 才给出 `exec: "sh": executable file not found in $PATH`。这不是镜像损坏，而是镜像里根本没有 `/bin/sh`；对运行中的容器执行 `docker exec shorty-api sh` 也会因为找不到 sh 失败，只是这个 lab 的 Docker 29 只返回 127，没有把 OCI 文本打出来（11.7 会看到）。判断依据应该是 `docker inspect` 里的 `Entrypoint`/`Cmd` 和退出码，而不是“容器起不来”这类猜测。

没有 shell 也能取文件。`docker create` 只创建容器不启动，`docker cp shorty-copy:/shorty /tmp/shorty-copy` 把二进制复制到宿主机，`ls -l` 能看到它约 13 MB。注意 `docker cp` 之后宿主机上的属主是 `root root`，因为复制动作由宿主机的 root 执行；要看镜像里的属主，用 `docker export shorty-copy | tar -tv shorty`，输出里的 `65532/65532` 才是 `COPY --chown` 的结果。这个区别在排查权限问题时很重要：不要拿 `docker cp` 出来的文件权限去判断容器里的权限。

最后一段输出是 slim 基础镜像里的 SUID 文件：`/usr/bin/su`、`/usr/bin/passwd`、`/usr/bin/mount` 等一共 11 个。scratch 里没有这些文件，因为它只有二进制、证书和时区。SUID 程序允许普通用户以文件属主的身份执行，是提权路径的一部分；如果必须用 slim 或完整发行版，至少不要给容器 `CAP_SYS_ADMIN`，在 Kubernetes 里设 `allowPrivilegeEscalation: false`，并把不需要的 SUID 位去掉。Docker 里对应的运行时选项是 `--security-opt=no-new-privileges`，它阻止进程通过 setuid 获得新权限。

在后面的层里删文件，不等于文件从镜像里消失。Docker 镜像由层叠加而成，`RUN rm /bin/sh` 只是在最上面一层记了一个 whiteout，下面的层里仍然有 `/bin/sh`；把镜像 `docker save` 出来或者用能读所有层的扫描器，还是能看到它。要去掉 shell 和包管理器，正确做法是从一个没有它们的 base 开始（scratch、distroless），或者用多阶段构建只把需要的文件复制到新的 `scratch` 阶段，而不是在完整发行版上删文件。

镜像里也不该有 `.git`、测试数据、构建凭据和私钥。`.git` 里可能有历史提交和已经删掉的密钥，`COPY . .` 会把它整个带进构建阶段；`.dockerignore` 把这些文件排除在构建上下文之外，多阶段构建让它们停留在构建阶段。需要凭据时用 `--mount=type=secret`，不要用 `ARG`/`ENV` 传（第 10 章做过）。`COPY --link` 是另一件可选的事：它把这次复制做成独立层，前面的层变化时这一层仍然可以复用；本章的 `shorty.Dockerfile` 对二进制用了它。它只影响层组织，不改变文件内容，也不影响非 root 和扫描的结论。

无 shell 镜像的排障最终会走到 Kubernetes。`kubectl debug` 给已有 Pod 加一个临时容器（ephemeral container），里面可以带 busybox、curl、strace 等工具；`crictl exec` 则在节点侧对目标容器执行命令，不会把节点上的工具带进镜像。Kubernetes 文档明确说，ephemeral container 的用途之一就是调试没有 shell 和调试工具的 distroless 镜像；具体用法放在第 35 章，本章只需要记住：不要为了排障往生产镜像里加 shell。

## 11.4 漏洞扫描与 SBOM

扫描器看两件事：操作系统包（apt/apk 装的）和语言依赖（Go module、Python 包）。Trivy 和 Grype 都能扫这两类；本章用 Trivy，因为它在容器里跑起来不需要额外安装，且能直接通过 Docker socket 读本地镜像。先记录 Trivy 和漏洞库的版本，再扫描；否则同一份镜像在不同时间扫出不同结果，报告没法复现。

Trivy 和 Grype 是两个常用的扫描器，漏洞库和评分策略由各自项目维护；同一个镜像用不同工具扫，条目和 severity 可能不一样。团队要固定一个扫描器和库的更新策略，报告里写清工具名和库版本，才能跨时间比较。本章只实测 Trivy，不在 lab 里对比两者。

```console

```

第一段是 `trivy version`：Trivy 0.76.1，漏洞库 Schema Version 2，`UpdatedAt` 和 `DownloadedAt` 都打出来了。扫描命令加了 `--skip-db-update`，所以用的是这个已经下载好的库；在生产 CI 里，要么定期更新库再扫，要么把库版本固定下来，并把 `UpdatedAt` 写进报告。

`shorty:0.1` 的扫描结果是 2 个 HIGH、0 个 CRITICAL，目标类型是 `gobinary`，两条都出在 `golang.org/x/text v0.29.0`：CVE-2026-56851 和 CVE-2026-56852，修复版本分别是 0.41.0 和 0.39.0。这个镜像里没有 Debian 包，Trivy 仍然从 Go 二进制的 build info 里读出了模块版本并匹配 CVE。**scratch 去掉的是操作系统包，不是语言依赖**；这是“小不等于安全”最直接的证据。修复这两条不需要换基础镜像，需要升级 `golang.org/x/text` 后重新构建——本章不改 `app/` 的源码，所以示例里这两条仍然在。

worker 的结果更直观：`shorty-worker:0.1` 的 Debian 13.7 基础镜像有 44 个 HIGH，Python 包还有 4 个 HIGH。输出里只保留了目标名和 `Total:` 行，两个 `Total` 分别对应 OS 包和 Python 包；完整表格会列出每个 CVE、安装版本和修复版本。把这两个数字和 shorty 的 2 个放在一起，就能看出基础镜像的选择把 CVE 面从几十个降到了两个，但没有降到零。

门禁的写法是把 `--exit-code 0` 改成 `--exit-code 1`。示例用 0 只统计，不阻断；设置 1 后，只要扫到 `HIGH,CRITICAL` 范围内的漏洞，Trivy 就以非 0 退出，CI 的 build 阶段会失败。真实项目还要决定“有修复版本的才阻断”还是“全部阻断”：`--ignore-unfixed` 可以只看有修复版本的漏洞，但会放过暂时无补丁的风险，取舍要写进策略。

`--exit-code 1` 只按 severity 判断，不区分有没有修复版本。团队如果决定“只阻断可修复的漏洞”，可以加 `--ignore-unfixed`，并在报告里注明；如果决定“无补丁也必须有人签字”，就不要加。门禁的阈值和例外要写进 CI 配置，而不是靠 reviewer 记住。

示例的最后一条命令用 worker 跑 `--exit-code 1`，输出 `trivy exit=1`；换成没有 HIGH/CRITICAL 的镜像，同样的命令会输出 0。CI 只需要看这个退出码，不需要解析表格。

扫描报告要和基础镜像的 digest、Trivy 的库版本一起归档。worker 的基础镜像是 `python:3.15.2-slim-trixie`，它的 digest 可以从 `docker image inspect` 的 `RepoDigests` 读出来；`shorty:0.1` 的基础是 `scratch`，没有 digest，报告里就写 `scratch` 和构建时 Dockerfile 的提交号。只写“扫过了”没有意义，下次复现时不知道扫的是哪个镜像、哪个库。

`RepoDigests` 只有在镜像被 push 或 pull 过之后才有值；本地刚 build 出来的镜像可能是空的。报告里可以同时写基础镜像的 tag、本地 `RepoDigests`（如果有）和 Dockerfile 的提交号，三样至少有一样能定位到具体内容。

> **旧资料提示**：旧流程把镜像扫描放在发布前的最后一步，甚至当成可选项；现在构建检查和 SBOM 都是构建产物的一部分，应该和 build 一起进主流水线。

SBOM 是另一类产物：它不告诉你“有没有漏洞”，而是告诉你“镜像里有什么”。BuildKit 在构建时用 Syft 扫描最终阶段，生成 SPDX 文档，并把它作为 attestation 挂到镜像索引上；`--sbom=true` 是 `--attest type=sbom` 的简写。关键点是它跟着镜像走，不是另存一个文本文件：推镜像时 attestation 一起推，拉镜像的人可以用 `imagetools inspect` 看到它。

示例先起一个临时的 `registry:3.0.0`，因为 `imagetools inspect` 只认 registry 里的引用，本地 `--load` 的镜像不能直接用它查看索引；`--push` 之后，`docker buildx imagetools inspect` 显示这是一个 OCI image index，里面有一条 `linux/amd64` 的镜像 manifest，还有一条 `unknown/unknown` 的 manifest，它的注解是 `vnd.docker.reference.type: attestation-manifest`，`vnd.docker.reference.digest` 指回镜像 manifest。这条 attestation 的 payload 就是 SPDX JSON；`--format '{{ json .SBOM.SPDX }}'` 可以把它取出来，`--format '{{ range .SBOM.SPDX.packages }}...'` 可以逐包列出名字和版本。

本章的构建只出现了一条 attestation manifest（SBOM）。provenance 是另一类 attestation，记录“这个镜像怎么构建的”，用 `--provenance=mode=min|max` 控制，和 SBOM 一样挂在索引上。文档说默认会加 min 级 provenance；本章这个构建的 inspect 只显示了一条 attestation manifest，构建日志里对应的是 `generating sbom`。需要可验证的 provenance 时，显式加 `--provenance=mode=max` 并再检查索引。SBOM 和 provenance 都要求镜像存储能保存 image index：本 lab 的 Docker 29 用 containerd 镜像存储，所以 `--load` 和 `--push` 都能带 attestation；classic image store 不支持 index，会直接报错，`docker-container` driver 则不受这个限制（第 10 章已经用过这个 driver）。

SBOM 默认只扫最终阶段。多阶段构建里，builder 安装的编译器、测试工具和构建期依赖不会出现在最终 SBOM 里；要连它们一起扫，得在 Dockerfile 里设 `BUILDKIT_SBOM_SCAN_STAGE` 或 `BUILDKIT_SBOM_SCAN_CONTEXT`。这不是说默认 SBOM 没用，而是说它回答的是“运行镜像里有什么”，不是“构建过程中用过什么”。

## 11.5 构建检查

`docker build --check` 不执行构建，只把 Dockerfile 和构建选项拿去做静态检查。Build checks 从 Dockerfile 1.8 开始提供，buildx 0.15.0 及以后支持；普通 `docker build` 也会顺带跑检查，但默认只把违规当 warning，退出码仍是 0；`--check` 只要有违规就以非 0 退出；在 Dockerfile 里写 `# check=error=true`，普通构建也会在检查阶段失败。

这一节故意写一个包含多种坏味道的 Dockerfile：未固定的 `debian:latest`、`apt-get` 装包后不清理 `/var/lib/apt/lists`、用 `ADD` 拉远程 URL、用 `ARG`/`ENV` 传密码、shell 形式的 `CMD`。

```console
{{#include code/ch11/11_6_image_build_check.out}}
```

实际输出和很多资料的说法不一样。`--check` 报了 3 条 warning，来自两条规则：`SecretsUsedInArgOrEnv`（`ARG DB_PASSWORD` 和 `ENV DB_PASSWORD` 各一条）和 `JSONArgsRecommended`（`CMD echo "shorty"` 应该用 JSON 形式）。它**没有**报 `FROM debian:latest` 未固定版本，没有报 `apt-get` 缓存没清，也没有报远程 `ADD`。在这个 lab 的 Docker 29.9.2 + buildx 0.38.1 上，这三项不在默认检查集里；换一个 buildx 版本可能会变，但不能把 `--check` 当成“基础镜像固定、包缓存清理、远程 ADD”的保证。

第二段用同一个文件跑普通 `docker build`，因为文件头有 `# check=error=true`，它在检查阶段就停了：先列出 3 条 warning，再报 `ERROR: ... lint violation found for rules: ...`，退出码非 0。也就是说，`# check=error=true` 把“warning”升级成了“构建失败”，但前提是检查集里确实有这条规则；没有规则的检查项，写多少遍 `error=true` 也不会报。

所以构建检查要分两层。第一层是 `--check` 和 `# check=error=true`，把已有的 lint 规则变成门禁；第二层是自己补的策略，比如在 CI 里 grep `FROM .*:latest`、检查 `apt-get install` 所在层有没有 `rm -rf /var/lib/apt/lists/*`、禁止 `ADD https://`，或者用 Docker Scout/第 13 章的策略引擎。两层都放在 build 阶段，不要等镜像跑起来再查；`--check` 在 PR 里就能给出文件和行号，修起来比运行时故障便宜得多。

`--check` 仍然要解析基础镜像的 metadata，所以要能访问 registry；完全离线的环境要先把基础镜像放进本地缓存。`docker/build-push-action` 从 6.6.0 起、`docker/bake-action` 从 5.6.0 起支持 build checks，GitHub Actions 的 PR diff 里能直接看到文件名和行号。把这些检查放在 build 阶段，和编译、单元测试一起跑，不要等镜像推到 registry 之后才查。

输出里的 `(line 7)`、`(line 8)`、`(line 11)` 是行号，修的时候直接跳到对应行。检查通过时输出 `Check complete, no warnings found!`；有违规时先列规则名和文档链接，再列 `ERROR: lint violation found for rules: ...`。

## 11.6 标签、注解与可追溯

镜像标签（label）是写在镜像配置里的键值对，`docker image inspect` 的 `Config.Labels` 能直接读出来。OCI 镜像规范定义了一组标准键，常用的有 `org.opencontainers.image.title`、`description`、`version`、`revision`、`created`、`source` 和 `licenses`。本章用 `LABEL` 写这些键，因为 `LABEL` 会进入镜像配置，本地不推 registry 也能看到。

> **旧资料提示**：旧 Dockerfile 用 `MAINTAINER` 写作者信息，这个指令已经废弃，改用 `LABEL`。

> **旧资料提示**：Label Schema 的 `org.label-schema.*` 是更早的约定，很多旧镜像还在用；新镜像用 OCI 的 `org.opencontainers.image.*`。

注解（annotation）和标签不是一回事。标签描述 Docker 资源（镜像、容器、网络、卷），注解描述 OCI 组件（manifest、index、descriptor）；注解可以挂在 manifest 或 index 上，用 `--annotation` 传入，但 Docker Engine 的镜像存储不支持加载带注解的镜像，所以带注解的构建通常要直接 `--push` 到 registry。`docker buildx imagetools inspect --raw` 能看到注解。本章的 `docker image inspect` 例子看的是标签；推到 registry 时，可以把同样的 `org.opencontainers.image.*` 键再用 `--annotation` 挂到 manifest/index 上。

`created` 在示例里写成固定值，是为了让重复构建的输出稳定；真实 CI 通常传 `date -u +%Y-%m-%dT%H:%M:%SZ`，代价是每次构建的镜像 digest 都会变。`revision` 应该传 `git rev-parse HEAD`，`source` 传仓库地址；这两个值让拿到镜像的人能回到源码。版本号用 `VERSION` 传，不要从 `latest` 标签猜。

`shorty.Dockerfile` 里还有两件事：二进制用了 `COPY --link`，以及构建命令的 `--sbom=true` 让 BuildKit 导出了一条 attestation manifest。于是同一个镜像有了三件可追溯的东西：镜像 digest 标识内容，SBOM 说明里面有什么，provenance 说明怎么构建的。digest 在 `docker push` 后由 registry 返回，也可以用 `docker image inspect` 的 `RepoDigests` 读；发布和回滚都应该用 digest，而不是 tag（第 12 章）。tag 只是给人看的可变指针，`shorty:0.1` 今天和明天可能指向不同的 digest。

标签还可以用来筛选和审计。`docker image ls --filter label=org.opencontainers.image.version=0.1` 能列出某个版本的所有镜像，`docker inspect` 能按标签找到构建来源；这些查询依赖标签写在 `Config.Labels` 里，而不是写在 README 里。注解适合放那些不进入镜像配置、但需要跟着 manifest 走的元数据，比如某个平台的构建来源；两者可以写同一组键，但用途不同。

Buildx 还能自动加 Git 标签：设 `BUILDX_GIT_LABELS=1` 会加 `org.opencontainers.image.revision` 和 Dockerfile 相对路径，设成 `full` 会加全部标签（包括 `org.opencontainers.image.source`）。本章示例是手动传，因为示例不在 Git 仓库里；真实 CI 可以用这个开关减少漏传。

## 11.7 排障：无 shell 的镜像和“CVE 很多”

第一个现场故障是 `docker exec shorty-api sh` 失败。镜像里没有 `/bin/sh`，这不是镜像坏了，而是 11.3 说的安全设计。先看 `docker inspect` 的 `Entrypoint` 和 `Cmd`，确认容器本来就应该运行 `/shorty serve`；再看进程是否正常，`curl /healthz` 能返回 `ok` 就说明服务活着。这个 lab 的 Docker 29.9.2 对缺失命令只返回退出码 127，没有打印 OCI 文本；`docker run --rm --entrypoint sh` 才能看到完整的 `exec: "sh": executable file not found`（11.3 的输出）。不同 Docker 版本的错误文本不一样，判断时以 Entrypoint/Cmd、退出码和服务本身为准。

`docker exec` 返回 127，`docker inspect` 显示 `Entrypoint=["/shorty"] Cmd=["serve"]`，`curl /healthz` 返回 `ok`，说明容器在正常运行，只是没有 shell。需要文件时用 `docker cp shorty-api:/shorty /tmp/shorty-api`，不需要进容器；`ls -l` 显示二进制约 13 MB。在 Kubernetes 里，对应的做法是 `kubectl debug` 加一个 ephemeral container，或者登录节点用 `crictl exec`。Kubernetes 文档明确把“镜像没有 shell 和调试工具”列为 ephemeral container 的适用场景；具体命令在第 35 章。

`kubectl debug` 的临时容器默认有自己的根文件系统，不是目标容器的；要在临时容器里看目标容器的文件，可以开 `shareProcessNamespace` 后从 `/proc/1/root` 进去。`crictl exec` 则是登录节点后对目标容器执行命令，它不会把节点上的工具带进容器，命令本身仍然要在镜像里存在。两条路都不需要改生产镜像。

第二个现场故障是 Trivy 报了大量 CVE。先别急着换基础镜像，按顺序看三件事：第一，基础镜像的 tag/digest 是不是过期了，`docker image inspect` 的 `RepoDigests` 和 `Created` 能看出本地镜像的构建时间，`docker build --pull` 能拉新基础镜像；第二，Trivy 的 `UpdatedAt` 是不是新的，库太旧会漏报，库太新可能引入新的 CVE 匹配；第三，CVE 出在 OS 包还是语言依赖。shorty 的 2 条 HIGH 全在 `golang.org/x/text`，换基础镜像没用，要升级 Go 模块；worker 的 44 条在 Debian 包，4 条在 Python 包，前者靠更新 `python:3.15.2-slim-trixie` 或换更小的基础镜像，后者靠升级 `requirements.txt` 里的包。

处理顺序应该是“先确认基础镜像和库的版本，再决定升级依赖、升级基础镜像还是换基础镜像”，而不是“看到 CVE 就把 alpine 换成 scratch”。如果是 base image 的包，先看上游有没有新 tag 或新 digest；如果是应用依赖，升级 `go.mod` 或 `requirements.txt`；如果暂时没有修复版本，记录例外、责任人和到期时间，下一次扫描时重新评估。scratch 可能把 44 条 OS CVE 变成 0，但语言依赖的 2 条还在；如果应用依赖的某个库只有 glibc 版本，换 scratch 还会直接跑不起来。扫描结果要连同基础镜像 digest、Trivy 库版本和修复决定一起归档，下一次重建时才能判断“这条 CVE 是修了、忽略了，还是换了基础镜像之后消失了”。

“小不等于安全”在这两个故障里都能落地：小镜像减少了可攻击的组件和 OS CVE，但没有减少应用依赖的 CVE，也没有让排障变简单；无 shell 限制了攻击者拿到交互式 shell 的可能，但要求团队提前准备 `kubectl debug`、`crictl` 和 `docker cp` 这些不动镜像的排障手段。把这两面都接受，才算真正用好了小镜像。

还要说清楚：无 shell 不是防入侵。应用本身的 RCE 不会因为镜像里没有 `/bin/sh` 就消失，攻击者仍然可以用语言运行时执行代码、读文件、发网络请求；无 shell 只是让“拿到交互式 shell 再装工具”这一步更难，把攻击面收窄了一点。它不能替代非 root、只读根文件系统、能力裁剪、seccomp 和 NetworkPolicy。把这些一起做，才是“小”带来的实际收益。

## 上生产前

- 基础镜像固定到 digest，同时保留可读的 tag；定期用 `--pull` 重建，或者让 Dependabot 之类工具定期更新 digest。`latest` 只用于本地实验；固定 digest 不等于永不更新，安全补丁还是要进来。
- 非 root、只读根文件系统、无 shell 三条一起做：`USER` 写数字 UID，`COPY --chown` 定好属主，需要写的地方只给 tmpfs 或显式卷。需要 shell 时用 ephemeral container，不要往生产镜像里加。
- 扫描按 severity 设门禁，`--severity HIGH,CRITICAL --exit-code 1` 放进 CI 的 build 阶段；报告里记录基础镜像 digest、Trivy 库的 `UpdatedAt` 和修复决定。只扫描不阻断，等于没有门禁。
- SBOM 和 provenance 随镜像推送，不要另存文本；发布和回滚用 digest，不用 tag。tag 带 git sha 或版本号，`LABEL`/注解写 `source`、`revision`、`created`，让拿到镜像的人能回到源码。
- 语言依赖也是镜像的一部分。scratch/distroless 去掉的是大部分 OS 包，不会去掉 Go module 和 Python 包的 CVE；升级依赖后要重新构建、重新扫描，不能因为“镜像里没有 apt”就认为不会再出 CVE。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `FROM scratch` | 从空文件系统开始 | 不能 pull/run/tag；静态二进制要自己带证书、时区 |
| `FROM <image>:<tag>@sha256:...` | 固定基础镜像 | 生产建议 tag + digest；`--pull` 才会检查新镜像 |
| `USER 65532:65532` | 设置默认运行用户 | 数字 UID 不依赖 `/etc/passwd`；`docker run --user` 可覆盖 |
| `COPY --chown=65532:65532` | 复制时设定属主 | 避免额外的 `RUN chown` 层 |
| `COPY --link` | 把复制做成独立层 | 只影响层组织，不改变文件内容 |
| `docker run --read-only --tmpfs /tmp` | 只读根文件系统 + 可写 `/tmp` | 对应 K8s 的 `readOnlyRootFilesystem` + `emptyDir.medium: Memory` |
| `docker image inspect --format '{{.Config.User}}'` | 看镜像默认用户 | 不是运行时强制 |
| `docker export <容器> \| tar -tv <文件>` | 看镜像内文件属主 | `docker cp` 到宿主机会变成本机属主 |
| `docker build --check` | 只跑构建检查 | 有违规时非 0；默认不执行构建 |
| `# check=error=true` | 让普通构建在检查阶段失败 | 只对检查集里存在的规则生效 |
| `docker buildx build --sbom=true --push` | 生成 SBOM attestation 并随镜像推送 | `--sbom=true` 等价于 `--attest type=sbom` |
| `docker buildx imagetools inspect <镜像>` | 看索引里的 attestation manifest | 需要镜像在 registry 里 |
| `trivy image --severity HIGH,CRITICAL --exit-code 1 <镜像>` | 按 severity 扫描并做门禁 | 示例用 `--exit-code 0` 只统计 |
| `trivy version` | 看 Trivy 和漏洞库版本 | 报告里记录 `UpdatedAt` |
| `docker image inspect --format '{{json .Config.Labels}}'` | 看 OCI 标签 | `--format '{{range $k,$v := .Config.Labels}}...'` 可逐行读 |

本章结束时，`shorty:0.1` 是一个非 root、无 shell、带 7 个 `org.opencontainers.image.*` 标签和 SBOM attestation 的 scratch 镜像，`shorty-worker:0.1` 仍是带 shell 和 apt 的 python slim 镜像；扫描报告已经按“镜像 digest + Trivy 库版本 + HIGH/CRITICAL 计数”的口径记录。下一章把这个镜像推到本地 registry，用 digest 发布和回滚（[第 12 章](ch12.md)）。
