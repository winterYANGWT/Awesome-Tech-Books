# 第 31 章 工作负载安全与准入控制：securityContext、Pod Security Admission、ValidatingAdmissionPolicy

`shorty` 跑在 `s3-stateful` 里，api 的 Deployment 清单中没有一个 `securityContext` 字段。它之所以看起来“已经是非 root”，是因为 `shorty:0.1` 的镜像是 distroless 的 `nonroot` 变体，镜像元数据里写着用户 65532。可 PSA 看不到镜像里的 `USER`，它只看提交上来的 Pod 清单。换一个默认 root 的镜像，或者有人把镜像标签换掉，这个 Pod 就会以 uid 0 跑起来，而清单上没有任何东西能拦住它。

这一章要把“镜像碰巧安全”变成“清单明确要求安全”。先给 api 补上 non-root、只读根文件系统、drop ALL、`RuntimeDefault` seccomp；再在 namespace 上打开 Pod Security Admission（PSA），让不合规的 Pod 根本创建不出来；然后用 ValidatingAdmissionPolicy（VAP）和 MutatingAdmissionPolicy（MAP）写自己的 CEL 策略；最后处理两个迁移问题：Pod user namespace 能不能用，以及已经被移除的 PodSecurityPolicy（PSP）怎么换成 PSA。

PSA 的 `restricted` 到底检查哪些字段？把它拆开看，核心就是四类：不能提权、不能以 root 运行、必须丢掉全部 capability、必须显式设置 seccomp。剩下的是卷类型、`procMount`、host namespace 这些基线项。`kubectl apply` 只给一句 `violates PodSecurity`，通常不是 apiserver 只报了一条，而是错误信息太长，第一行就把后面几条截在了视线之外；也可能是被拒的是 Deployment 创建的 Pod，而 `apply` 本身成功，真正的拒绝藏在 ReplicaSet 的 Event 里。这两个现象在后面都会出现。

> **起点**：`s3-stateful` 已经就绪，单节点 kind 集群，api 的 Pod 模板里没有 `securityContext`，`shorty` namespace 也没有任何 `pod-security.kubernetes.io/*` 标签。一步到位：`bash code/ch31/setup.sh`。脚本重建集群、部署 `s3-stateful`，并把 `busybox:1.37` 预拉进节点。

## 31.1 securityContext：把 Pod 收紧

`securityContext` 有两个层级。Pod 级的 `spec.securityContext` 作用于这个 Pod 里的所有容器，容器级的 `spec.containers[*].securityContext` 只作用于那个容器；两边都设置同一个字段时，容器级优先。这不是“合并”，而是逐字段覆盖：Pod 级写了 `runAsUser: 1000`，某个容器写了 `runAsUser: 65532`，那个容器就是 65532，其他没写的容器仍是 1000。`runAsGroup`、`runAsNonRoot`、`seccompProfile` 都是这个规则；`allowPrivilegeEscalation`、`readOnlyRootFilesystem`、`capabilities` 只存在于容器级，Pod 级没有对应字段。

先看 api 的起点。Deployment 的 Pod 模板里 `securityContext` 是空的，容器的 `securityContext` 也没有：

```console
{{#include code/ch31/31_1_securitycontext_hardened.out}}
```

输出里只有一个 `{}`，那是 Pod 级的空对象；第二段容器级字段为空，所以后面没有内容。然后 `kubectl patch` 把加固项写进 Deployment，滚动更新完成后，两个新 Pod 的字段是 `runAsNonRoot: true`、`runAsUser: 65532`、`fsGroup: 65532`、`fsGroupChangePolicy: OnRootMismatch`，容器级是 `allowPrivilegeEscalation: false`、`readOnlyRootFilesystem: true`、`capabilities.drop: ["ALL"]`，Pod 级还有 `seccompProfile.type: RuntimeDefault`。这些字段不是给镜像看的，是给 kubelet 和容器运行时看的：kubelet 在启动容器前检查 `runAsNonRoot`，运行时按 `runAsUser` 设置进程 uid，按 `capabilities` 决定保留哪些内核能力，按 `seccompProfile` 选择系统调用过滤配置。

`runAsNonRoot: true` 和 `runAsUser` 解决的是两个不同的问题。`runAsUser` 直接指定 uid，写 0 就是 root；`runAsNonRoot: true` 则要求 kubelet 在运行时检查镜像或 `runAsUser` 给出的用户，发现是 0 就拒绝启动容器。只写 `runAsUser: 65532` 能保证这个清单跑成非 root，但换一个清单、换一个镜像就可能忘掉；只写 `runAsNonRoot: true` 不写 `runAsUser`，则 uid 来自镜像元数据。生产上两个一起写：`runAsNonRoot` 是约束，`runAsUser` 是明确的值。api 的镜像本来就是 65532，这里仍然显式写出来，目的是让清单自己说清楚，而不是依赖镜像作者。

`runAsGroup` 设置主组，`fsGroup` 设置一个补充组，用来解决卷的属组问题。kubelet 挂载支持 `fsGroup` 的卷时，会把卷的属组改成 `fsGroup`，给组加读写权限，并设置 setgid 位，让新创建的文件继承这个组。示例里的 `emptyDir` 挂到 `/data`，`stat` 显示 `uid=0 gid=65532 mode=2777`：属主仍是 root，属组变成了 65532，`2777` 里的 `2` 就是 setgid。随后往 `/data/probe` 写文件成功，说明只读根文件系统不会把挂载的卷也变成只读。`fsGroupChangePolicy` 控制挂载时要不要递归改属主：默认 `Always`，每次挂载都扫一遍；`OnRootMismatch` 只在卷根目录的属主或权限不匹配时才递归改。官方文档明确说这个字段对 `secret`、`configMap`、`emptyDir` 这类临时卷没有效果，所以它不是一个适用于所有卷的加速开关。

`readOnlyRootFilesystem: true` 只影响容器的根文件系统，也就是镜像层和可写层；`emptyDir`、`secret`、`configMap`、PVC 这些挂载点不受影响。这一点在输出里很直接：`touch /blocked` 返回 `Read-only file system`，而 `echo ok > /data/probe` 成功。很多应用默认往 `/tmp`、`/var/run` 或自己的工作目录写东西，打开只读根之后会启动失败；正确做法是把需要写的目录显式挂成 `emptyDir` 或 PVC，而不是把整个根文件系统放回可写。api 只写 stdout，不落盘，所以可以直接开只读根；如果它要写缓存，就得在 `/tmp` 上挂一个 `emptyDir`。

`allowPrivilegeEscalation: false` 控制进程能不能获得比父进程更高的权限，典型场景是执行带 setuid 位的二进制。它对应内核的 `no_new_privs` 标志，默认值是 `true`，也就是不阻止提权。这个字段不能和 `privileged: true` 或 `CAP_SYS_ADMIN` 同时使用，官方文档说这种组合是不一致的。`capabilities.drop: ["ALL"]` 则把运行时默认给的一组 capability 全部丢掉；restricted 标准允许再加回 `NET_BIND_SERVICE`，因为非 root 进程绑定 80 端口需要它。api 监听 8080，不需要任何 capability，所以只 drop 不 add。

`seccompProfile.type` 有三个值：`RuntimeDefault` 用容器运行时自带的默认 profile，`Unconfined` 不做系统调用过滤，`Localhost` 用节点上预先放好的 profile 文件。restricted 只允许 `RuntimeDefault` 和 `Localhost`，并且要求显式设置；缺省不等于 `RuntimeDefault`，PSA 会把“没写”当成违规。示例里把 `seccompProfile` 放在 Pod 级，所有容器共用；如果某个容器需要不同的 profile，可以在容器级覆盖。`Localhost` 还要写 `localhostProfile`，路径相对于 kubelet 配置的 seccomp profile 目录。

`procMount` 是另一个容易被忽略的字段。默认值 `Default` 会让运行时遮住 `/proc` 下一些敏感路径，比如 `/proc/kcore`、`/proc/keys`、`/proc/sysrq-trigger`，并把 `/proc/sys` 等挂成只读。`Unmasked` 则绕过这些遮罩，通常只在容器里再跑容器时才需要。官方文档从 Kubernetes 1.30 起强制要求：设 `procMount: Unmasked` 的 Pod 必须同时设 `spec.hostUsers: false`，也就是启用 Pod user namespace；1.12 到 1.29 没有这道检查。restricted 标准只允许 `Default` 或留空，所以业务 Pod 不要碰这个字段。

容器级覆盖 Pod 级这件事，示例里用 shell Pod 验证：Pod 级 `runAsUser: 1000`，容器级写 65532，`id` 输出 `uid=65532 gid=65532 groups=65532`。这不是因为 shell 镜像里恰好有个 65532 用户，而是 kubelet 按容器级的值设置了进程 uid。反过来说，Pod 级的 `runAsUser` 不是“建议值”，而是会被容器级覆盖的默认值；排查“为什么这个容器是 root”时，要同时看 Pod 和容器两层的 `securityContext`，以及镜像的 `USER`。

加固后的 api 仍然能通过 Service 回答 `/readyz`，输出是 `ok`。这说明只读根、非 root、drop ALL、`RuntimeDefault` seccomp 这套组合没有破坏 shorty 的主链路：它只连 PostgreSQL 和 Redis，日志写 stdout，不依赖任何被砍掉的能力。换一个应用时不能假设同样成立，要按它实际打开的文件、绑定的端口、调用的系统调用来逐项验证。只读根和 drop ALL 最常踩的坑是应用要写临时文件、要绑小于 1024 的端口、或者要调用某个需要特权的系统调用；前两个分别用 `emptyDir` 和 `NET_BIND_SERVICE` 解决，第三个要先确认是不是真的需要，而不是直接开 `privileged`。

## 31.2 Pod Security Admission

api 的清单已经收紧了，但集群里还有 postgres、redis、worker，它们仍然是默认配置。PSA 的作用是让整个 namespace 有一个统一的下限，而不是靠每个 Deployment 的作者记得写 `securityContext`。它在 Pod 创建和更新时检查 Pod 对象，按 namespace 上的标签选择 `privileged`、`baseline`、`restricted` 三档策略；三档是累加的，`restricted` 包含 `baseline` 的全部限制，再加一组更严格的字段。

PSA 有三个模式，每个模式一个标签：`pod-security.kubernetes.io/enforce` 直接拒绝违规 Pod，`.../warn` 返回 HTTP 警告但放行，`.../audit` 只在审计日志里加注解。每个模式还可以跟一个 `-version` 标签，把策略锁在某个 Kubernetes 小版本，比如 `enforce-version=v1.37`；不写就是 `latest`，跟随集群版本。PSA 在 Kubernetes 1.25 稳定（1.22 alpha、1.23 beta），同一条版本线上 PSP 在 1.25 被移除。这两个变化经常一起出现：升级到 1.25 以后，PSP 的对象和准入插件都没有了，namespace 标签成为内置的替代品。

`restricted` 到底检查什么？在 `baseline` 之上，它要求 `spec.volumes[*]` 只能是 `configMap`、`csi`、`downwardAPI`、`emptyDir`、`ephemeral`、`persistentVolumeClaim`、`projected`、`secret` 这几种；要求每个容器 `allowPrivilegeEscalation` 必须是 `false`；要求 Pod 或所有容器 `runAsNonRoot: true`；要求 `runAsUser` 不能是 0；要求 `seccompProfile.type` 是 `RuntimeDefault` 或 `Localhost`，缺省不行；要求 `capabilities.drop` 包含 `ALL`，`capabilities.add` 最多只能有 `NET_BIND_SERVICE`。`baseline` 还管 host namespace、`privileged`、`hostPath`、`hostPort`、AppArmor、SELinux、`procMount` 和 sysctl。把这些字段逐条对照，就能理解为什么一个看起来“能跑”的 Pod 会被拒。

示例先做 dry-run。这时 `shorty` 还没有标签，命令只在服务端评估现有 Pod，不写入：

```console
{{#include code/ch31/31_2_psa_restricted.out}}
```

dry-run 的警告说 `postgres-0 (and 3 other pods)` 违反 `restricted:latest`，列出四项：`allowPrivilegeEscalation != false`、`unrestricted capabilities`、`runAsNonRoot != true`、`seccompProfile`。这四项正好对应上面那组 hardening 检查，说明现有 Pod 里只有 api 在 31.1 被改过，postgres、redis、worker 和 migrate 的 Pod 都还停在默认配置。注意这只是警告，现有 Pod 不会被驱逐，也不会被重启；已有的不合规 Pod 不会因为标签变化被拒绝，只有更新到非豁免字段时才会撞上检查。真正打标签的命令随后执行，输出里的警告变成 `restricted:v1.37`，因为这次带了 `enforce-version`；标签仍然打上了，现有 Pod 也仍然在跑。

接下来直接创建那个 root 且 privileged 的 Pod。输出里被拒的那一行以 `Error from server (Forbidden)` 开头，后面是 `violates PodSecurity "restricted:v1.37"`，然后六项违规用逗号连在一起：`privileged (...)`、`allowPrivilegeEscalation != false (...)`、`unrestricted capabilities (...)`、`runAsNonRoot != true (...)`、`runAsUser=0 (...)`、`seccompProfile (...)`。这就是那句“只给一句 `violates PodSecurity`”的真面目：它不是一条，而是六条挤在一行里。第一项是 `privileged`，因为 `privileged: true` 同时触发了 baseline 的检查；如果 Pod 只是 root、没有开 privileged，第一项就会是 `allowPrivilegeEscalation != false`。每一项都带一句“哪个容器、该改哪个字段”，照着改就能过。读这种错误时不要只看冒号后的第一个词，要把整行按逗号拆开；终端窄的时候它会自动折行，更容易漏掉后面的项。

然后 apply 一个同样配置的 Deployment。输出只有一条 `Warning: would violate PodSecurity "restricted:latest"`，然后是 `deployment.apps/psa-root-demo created`，退出码是 0。原因是 `enforce` 只作用于 Pod，不作用于 Deployment 这类工作负载对象；`warn` 和 `audit` 才会对工作负载对象生效，所以 Deployment 本身能通过，警告来自 `warn`。真正创建 Pod 的是 ReplicaSet 控制器，它拿着 Pod 模板去创建 Pod，这时 `enforce` 才拒绝。拒绝记录在 ReplicaSet 的 Event 里，示例用 `printf` 打出的那一行以 `psa-root-demo-...: Error creating:` 开头，内容和直接创建 Pod 时一样，只是随机后缀不同。

这解释了另一种“apply 只给一句”的错觉：`apply` 确实成功了，失败发生在控制器异步创建 Pod 的时候，要看 `kubectl describe replicaset` 或 Event，而不是 `kubectl apply` 的退出码。直接创建 Pod 时错误立刻返回；通过 Deployment、StatefulSet、Job 创建 Pod 时，错误会晚一步出现在工作负载对象的 Event 上。排障时要先分清被拒的是哪一个对象。

两处版本后缀不同也值得注意：`apply` 的警告是 `restricted:latest`，Event 是 `restricted:v1.37`。警告来自 `warn` 模式，我们只给 `enforce` 设了 `-version`，`warn-version` 没设，所以它用 `latest`；Event 来自 `enforce`，用的是 `v1.37`。三个模式各有自己的版本标签，想三边一致就三个都写。把 `enforce-version` 锁住可以避免升级集群时策略突然变严或变松，代价是升级后要手动评估并更新版本标签。

PSA 的豁免是静态配置，写在 apiserver 的准入配置文件里，按用户名、`runtimeClass` 或 namespace 三个维度匹配；命中豁免的请求会跳过 `enforce`、`warn`、`audit` 三种行为。它不是 namespace 标签，也不能在运行时用 `kubectl` 改。官方文档特别提醒：大多数 Pod 是控制器创建的，豁免一个终端用户只能豁免他直接创建 Pod 的请求，不能豁免他创建的 Deployment；也不要随便豁免 `system:serviceaccount:kube-system:replicaset-controller`，那等于豁免所有能创建工作负载的人。

PSA 的边界也要说清楚：它只做校验，不做变更。它不会替你补 `runAsNonRoot` 或 `seccompProfile`，也不会像 PSP 那样给 Pod 设默认值。它只有三档，不能按 ServiceAccount 做更细的区分；需要“只允许某个仓库的镜像”“必须带 owner 标签”这类规则时，要用下一节的 VAP，或者 Kyverno、Gatekeeper 这类策略引擎。PSA 是底线，不是完整策略系统。

## 31.3 ValidatingAdmissionPolicy（CEL）

PSA 只有三档，能管的是“别开特权、别用 root”这类通用底线。真实集群里还有别的规则：所有 Pod 必须带 `team` 标签，镜像只能来自某个仓库，Ingress 的 host 必须在白名单里。这些规则以前主要靠 validating webhook：自己写一个 HTTP 服务，部署在集群里，注册 `ValidatingWebhookConfiguration`，apiserver 每次请求都回调它。webhook 灵活，但要多维护一个服务，还要处理证书、超时、失败策略和高可用。

ValidatingAdmissionPolicy（VAP）把这类校验做进了 apiserver：策略用 CEL 写，对象存在 etcd 里，不需要额外的服务。一个策略由两部分组成：`ValidatingAdmissionPolicy` 描述逻辑，`ValidatingAdmissionPolicyBinding` 把它和具体的资源范围绑起来。只创建策略不创建绑定，策略不会生效；绑定可以有好几个，同一个策略在不同 namespace 可以有不同的参数。

策略的主体是 `spec.matchConstraints` 和 `spec.validations`。`matchConstraints.resourceRules` 用 `apiGroups`、`apiVersions`、`operations`、`resources` 选请求，比如所有 core 组的 `pods` 的 `CREATE` 和 `UPDATE`。`validations[].expression` 是一段 CEL，返回 `true` 表示通过，返回 `false` 表示违反；违反时按绑定的 `validationActions` 处理。`failurePolicy` 管的是另一类情况：表达式编译失败、求值报错、参数找不到。`Fail` 拒绝请求，`Ignore` 放行请求；不写时默认 `Fail`。这两个字段容易混：`failurePolicy` 决定“策略坏了怎么办”，`validationActions` 决定“策略说不行怎么办”。

绑定里的 `validationActions` 可以是 `Deny`、`Warn`、`Audit`。`Deny` 拒绝，`Warn` 在 HTTP 响应头里加警告但放行，`Audit` 只在审计事件里写一条注解。`Deny` 和 `Warn` 不能同时用，官方文档说这会把同一条失败重复到响应体和警告头里。想把新策略先试运行，可以用 `Warn` 或 `Audit`；确认没有误伤后再改成 `Deny`。`Audit` 的注解键是 `validation.policy.admission.k8s.io/validation_failure`，值里带策略名、绑定名、表达式序号和消息。

```console
{{#include code/ch31/31_3_vap_require_label.out}}
```

策略的表达式是 `has(object.metadata.labels) && 'team' in object.metadata.labels`。`has()` 先确认 `metadata.labels` 这个字段存在，`in` 再确认 `labels` 这个 map 里有 `team` 键；两个条件都成立才通过。这里不能用 `object.metadata.labels.team` 直接取，因为标签不存在时 CEL 会报“找不到字段”，那会走 `failurePolicy`，而不是按“校验失败”处理。`has()` 和 `in` 的组合是 CEL 里判断可选字段和 map 键的标准写法。

绑定用 `namespaceSelector` 把范围限制在 `shorty`。`kubernetes.io/metadata.name` 是 namespace 自动带的标签，值就是 namespace 名；这样策略对象是集群级的，但只在这个 namespace 生效。`matchConstraints` 和绑定的 `matchResources` 是交集：请求要先被策略的 `matchConstraints` 选中，再被绑定的 `matchResources` 选中，才会求值。绑定也可以按 `objectSelector` 选对象，或者用 `resourceRules` 再收窄。

被拒的那一行是 `The pods "vap-no-label" is invalid: : ValidatingAdmissionPolicy 'require-team-label' with binding 'require-team-label-binding' denied request: 'team' label is required`。第一个冒号后面的空段是 kubectl 对准入错误的格式化，不是策略返回了空字段；真正有用的是策略名、绑定名和最后的 `message`。如果 `validations[]` 里不写 `message`，错误会变成 `failed expression: <表达式>`，把 CEL 原文带出来；写了 `message` 就只显示自定义文本。策略多了以后，`message` 要写清楚“哪个字段、期望什么”，否则排障时只能去翻策略源码。

示例在创建策略后先等 `status.observedGeneration` 变成 1，再创建绑定。`observedGeneration` 表示控制器已经看到这一代策略，但绑定的注册也是异步的：在 lab 里观察到，绑定创建后立刻发请求，偶尔会在策略生效之前通过；示例于是在绑定之后用 server-side dry-run 轮询同一个 Pod，直到它被拒绝，再做真正的 `apply`。这一步在 `.out` 里没有输出，因为它只用于等待。生产上写自动化时也要考虑这个窗口：创建完策略和绑定，先用一个已知会失败的 dry-run 探针确认策略已经生效，再把流量或 CI 放过来。

带 `team: shorty` 的同一个 Pod 被接受，`kubectl get pod --show-labels` 显示 `app=vap-with-label,team=shorty`。这说明策略没有误伤合规对象；策略的 `operations` 同时写了 `CREATE` 和 `UPDATE`，但示例只验证了创建，更新一个已有 Pod、把 `team` 标签删掉的场景要自己补测。

VAP 支持参数化：`spec.paramKind` 指定参数资源的 GVK，绑定里的 `paramRef` 指向一个具体对象，CEL 里用 `params` 访问。参数可以是 ConfigMap，也可以是 CRD；`paramRef` 的 `name` 和 `selector` 二选一，`parameterNotFoundAction` 是必填项，决定参数找不到时是 `Allow` 还是 `Deny`。没有 `paramKind` 时 `params` 是 null，表达式里如果要访问参数，先加一条 `params != null` 的校验，避免策略在没绑参数时出错。参数化适合“每个 namespace 的副本上限不同”这类场景，不适合把整条策略塞进 ConfigMap。

VAP 在 Kubernetes 1.30 稳定。它不能用来拦截 VAP 自己和 VAPBinding 的创建，也不能拦截 TokenReview、SubjectAccessReview 这些认证授权虚拟资源；这是为了避免策略把集群锁死。`status.typeChecking` 会给出表达式的类型检查结果，类型错误不会阻止策略创建，策略仍然会参与求值，出错时按 `failurePolicy` 处理；语法错误则会在创建时直接拒绝。这个区别在 31.7 会看到。

## 31.4 MutatingAdmissionPolicy（CEL）

VAP 只能拒绝，不能改对象。MutatingAdmissionPolicy（MAP）补上另一半：它在准入的 mutating 阶段按 CEL 修改对象，同样不需要 webhook 服务。典型的用途是给没有 `team` 标签的 Pod 注入默认值、给所有 Pod 加一组 annotation、或者往 Pod 里插一个 sidecar。它和 VAP 一样由“策略 + 绑定”组成，策略描述改什么，绑定描述对哪些请求改。

MAP 的 `spec.mutations` 是一个列表，每一项要么是 `patchType: ApplyConfiguration`，要么是 `patchType: JSONPatch`。`ApplyConfiguration` 的 `expression` 返回一个 CEL `Object`，按 server-side apply 的合并策略写进对象；`JSONPatch` 的 `expression` 返回一个 `JSONPatch` 数组，按 JSON Patch 的 `add`/`replace`/`remove` 操作改对象。`ApplyConfiguration` 不能改 atomic 的 struct、map 或 array，否则可能把没写进 apply 配置的值整个删掉；`metadata.labels` 是可合并的 map，所以只写 `team` 一个键不会清掉其他标签。JSONPatch 更接近“精确改某一个路径”，但路径不存在时要自己处理，比如父 map 不存在就得先 add 父 map。

`reinvocationPolicy` 是 MAP 的必填字段，取值 `Never` 或 `IfNeeded`。示例用 `Never`，表示每个绑定在一次准入里最多调用一次；`IfNeeded` 允许在对象被其他插件修改后再次调用，适合“别的 webhook 可能改 Pod，改了以后我还要再补一次”的场景，但会让最终结果更难预测。`failurePolicy` 和 VAP 一样，管表达式出错时是 `Fail` 还是 `Ignore`，默认 `Fail`。

MAP 没有 `validationActions`，绑定里也没有 `Warn`/`Audit` 这种试运行模式。变更一旦绑定就生效，所以“先审计”要靠别的办法：先用 `kubectl apply --dry-run=server -o yaml` 看 MAP 会把对象改成什么样，只把绑定挂在测试 namespace，打开审计日志看请求体和最终对象；确认没有隐式行为再扩大范围。变更策略比校验策略更难回滚，因为它改的是落盘的对象；一个错误的默认标签或 sidecar 注入，可能让整个 namespace 的 Pod 都起不来。

MAP 在 Kubernetes 1.36 稳定，API 是 `admissionregistration.k8s.io/v1`。它和 VAP 一样支持 `paramKind`/`paramRef` 参数化，适合“不同 namespace 注入不同的 team 默认值”这类场景。它同样不能修改 MAP/VAP 自己和它们的绑定，避免策略把自己改坏。

> **旧资料提示**：早期做 sidecar 注入基本只有 mutating webhook 一条路，要自己部署服务、管证书、处理超时。Kubernetes 1.36 起 MAP 稳定，简单的默认标签、annotation、sidecar 注入可以直接写成 CEL；但复杂的模板渲染、外部系统查询仍然更适合 webhook 或专门的控制器。

## 31.5 Pod user namespace

前面几节都在改 Pod 的 `securityContext`，但有一个限制绕不过去：容器里的 root 就是节点上的 root，只要容器逃逸或者内核有漏洞，攻击者拿到的就是宿主权限。Pod user namespace 换了一个思路：容器里仍然可以是 uid 0，但这个 0 只在一个新的 user namespace 里有效，映射到节点上是一个没有特权的 subuid。容器里的进程觉得自己是 root，能 `apt`、能写自己的文件，但在节点上它连别人的文件都碰不到。

启用方式是 `spec.hostUsers: false`。这个字段默认是 `true`，表示 Pod 用节点的 user namespace；设成 `false` 才会新建一个。kubelet 负责给每个 Pod 分配不重叠的 host UID/GID 范围，Pod 里的 `runAsUser`、`runAsGroup`、`fsGroup` 仍然指容器内的用户，挂载卷时按容器内的 uid/gid 处理，所以同一个卷可以在启用和未启用 user namespace 的 Pod 之间共享。默认映射范围是 0–65535，超出范围的文件在容器里会显示成 overflow ID（通常是 65534），而且改不了；从 Kubernetes 1.33 起可以用 kubelet 的 `userNamespaces.idsPerPod` 调整每个 Pod 的 ID 数量，默认 65536，必须是 65536 的倍数。

它对节点有实打实的要求。文件系统要支持 idmap mount：`/var/lib/kubelet/pods/` 所在的文件系统要支持，Pod 挂的所有卷也要支持；Linux 6.3 起 tmpfs 才支持 idmap，而 ServiceAccount token、Secret 这些默认就用 tmpfs，所以低于 6.3 的内核基本不用考虑。官方列出的常见支持文件系统有 btrfs、ext4、xfs、fat、tmpfs、overlayfs；NFS 客户端还不支持 idmap，NFS 卷不能用在 user namespace Pod 里。运行时这边，runc 要 1.2 以上、crun 要 1.9 以上；CRI 实现里 containerd 2.0 以上、CRI-O 1.25 以上支持。kubelet 还要能拿到 subordinate UID/GID：节点上要有 `kubelet` 用户，装了 `getsubids`，`/etc/subuid` 和 `/etc/subgid` 里给这个用户配一段范围，起始值必须是 65536 的倍数且不小于 65536，长度至少是 `65536 × maxPods`，user 和 group 的范围要一致，而且只能写一行。

限制也要记住：启用 user namespace 的 Pod 不能再用 `hostNetwork`、`hostIPC`、`hostPID`，不能用 `volumeDevices` 这种裸块设备，NFS 卷不行；`privileged` 容器和 user namespace 的组合也要单独核对，不能假设所有特权操作都能正常工作。PSA 对这类 Pod 有明确的放宽：`runAsNonRoot` 和 `runAsUser` 在 `baseline`/`restricted` 下都不再检查，因为容器里的 root 不是节点上的 root；`baseline` 下 `procMount` 也放宽，但 `restricted` 下仍然只能用默认或空的 `procMount`。

把 user namespace 上生产的节奏应该是先在预发找一台和线上同内核、同文件系统、同运行时的节点，跑一个 `hostUsers: false` 的 Pod，确认 `id` 在容器里是 0、在节点上是 subuid，再验证挂载的 PVC、Secret、emptyDir 都能读写。不要直接在全集群打开，也不要把 `hostUsers: false` 当成“开了就安全”的开关：它降低的是容器逃逸后的影响，不能替代非 root、只读根、drop ALL 这些约束。

## 31.6 从 PSP 迁移

PodSecurityPolicy（PSP）是 Kubernetes 早期的 Pod 安全机制：集群里建一堆 PSP 对象，再用 RBAC 把 `use` 权限授给用户或 ServiceAccount，apiserver 在准入时选一个 PSP 来校验，还能给 Pod 设默认值。它在 Kubernetes 1.21 被弃用，1.25 随 `policy/v1beta1` 一起移除。移除的不只是一个 API 版本，而是整个准入插件和 RBAC 里的 `podsecuritypolicies` 资源；升级到 1.25 以后，旧的 PSP 清单、Role 里的 `use` 规则、依赖 PSP 默认值的应用都会一起失效。

输出里的 `no matches for kind "PodSecurityPolicy" in version "policy/v1beta1"` 是客户端在做 REST 映射时给出的：它不知道这个 kind 对应哪个资源，所以连请求都没发出去。`kubectl get psp` 的说法不同，是 `the server doesn't have a resource type "psp"`：这次请求发出去了，apiserver 告诉客户端没有这个资源类型。两句话是一个意思，PSP 的 API 已经不存在了。旧教程里“先 apply 一个 PSP，再建 Role 授予 `use`”的步骤，今天第一步就会失败。

替代方案是 namespace 上的 PSA 标签加 Pod 自己的 `securityContext`。示例建了一个 `psp-demo` namespace，先打 `enforce=baseline`，再用 `kubectl run` 创建一个默认配置的 root Pod；baseline 接受它，Pod 正常 Running。然后把标签改成 `enforce=restricted`，同样的 `kubectl run` 被拒绝，错误里列出 `allowPrivilegeEscalation != false`、`unrestricted capabilities`、`runAsNonRoot != true`、`seccompProfile` 四项。PSP 里常见的 `runAsUser: MustRunAsNonRoot`、`requiredDropCapabilities: [ALL]`、`allowPrivilegeEscalation: false`，在 PSA 里分别对应 `runAsNonRoot: true`、`capabilities.drop: ["ALL"]`、`allowPrivilegeEscalation: false`；PSP 的 `volumes` 白名单在 restricted 里对应那八种卷类型。`privileged: false`、host namespace、hostPath 这些 baseline 已经覆盖，不需要在 Pod 里重复写。

迁移的步骤官方页面写得很细，顺序大致是：先盘点现有 PSP 和被哪些 Role/ClusterRole 授予了 `use`，把会改 Pod 的 PSP 字段（`defaultAllowPrivilegeEscalation`、`defaultAddCapabilities`、`defaultRuntimeClassName` 等）先消掉，避免关掉 PSP 后 Pod 少了默认值；再给每个 namespace 选一个 PSA 级别，用 `kubectl label --dry-run=server` 评估现有 Pod，用 `audit`/`warn` 跑一段时间；确认没有误伤后改成 `enforce`；最后删掉 PSP 和对应的 RBAC 规则。这个顺序的重点是“先让工作负载自己满足要求，再关掉旧机制”，反过来做会直接造成中断。

PSA 不能完全覆盖 PSP 的能力。它不做变更，不会给 Pod 补默认的 `runAsUser`、`fsGroup`、seccomp profile；它只有三档，不能按 ServiceAccount 做更细的区分；它的豁免只有用户名、`runtimeClass`、namespace 三个维度。需要“这个 namespace 只允许某个仓库的镜像”“必须带 cost-center 标签”“PVC 必须用某个 StorageClass”这类规则时，用 VAP，或者 Kyverno、Gatekeeper 这类策略引擎。官方的 `migrate-from-psp` 页面明确说 PSA 是 PSP 的替代，但不是 1:1 的替代；`psp-to-pod-security-standards` 页面有一张逐字段的对照表，迁移时按那张表逐条核对。

示例里的 `psp-demo` 最后被删掉，`shorty` 的 VAP/MAP 绑定只作用在 `shorty`，所以 `psp-demo` 里的 root Pod 没有被 `team` 标签策略影响。这也说明策略的作用域要写清楚：PSA 看 namespace 标签，VAP/MAP 看绑定里的 `namespaceSelector`，三者是独立的，不要以为给 `shorty` 建了策略，别的 namespace 就自动受保护。

> **旧资料提示**：旧教程里的 `PodSecurityPolicy` 清单、`kubectl create clusterrole ... --resource podsecuritypolicies`、`kubectl get psp` 在今天都不再有效。PSP 在 1.25 移除，替代是 PSA 加 `securityContext`；需要更细的策略时用 VAP/Kyverno/Gatekeeper，不要再往集群里写 PSP 清单。

## 31.7 排障：PSA 拒绝与 CEL 报错

PSA 拒绝 Pod 时，先分清被拒的是哪个对象。直接 `kubectl apply` 一个 Pod，错误会立刻返回，Pod 根本没有创建出来，所以 `kubectl describe pod` 找不到它；只能看 `kubectl apply` 的错误。通过 Deployment、StatefulSet、Job 创建 Pod 时，工作负载对象本身能通过，ReplicaSet/控制器创建 Pod 失败，Event 记在工作负载对象上，`kubectl describe deployment` 或 `kubectl describe replicaset` 能看到 `Error creating: ... violates PodSecurity ...`。Event 里的字段列表和直接创建 Pod 时一样，只是多了一层“控制器异步创建”的时序。

在正式收紧 namespace 之前，用 `kubectl label --dry-run=server --overwrite namespace <ns> pod-security.kubernetes.io/enforce=restricted` 评估现有 Pod。示例先在已经 `enforce=restricted` 的 `shorty` 上跑了一次，输出只有 `namespace/shorty not labeled (server dry run)`：标签值没变，kubectl 不会重新评估。换一个还没打标签、里面有一个默认配置 root Pod 的 `triage-demo`，同样的命令才会输出 `Warning: legacy: allowPrivilegeEscalation != false, unrestricted capabilities, runAsNonRoot != true, seccompProfile`，并列出违反的 Pod 名。这个细节说明 dry-run 评估发生在标签变更的准入里；值没变就没有变更，也就没有评估。要在收紧前评估，就在标签还没打或者准备换级别的时候跑。

VAP 的排障和 PSA 不同。VAP 直接拒绝一个 Pod 请求时，对象没有落盘，不会产生 Pod Event；如果 Pod 是控制器创建的，失败仍可能出现在 ReplicaSet 的 Event 里。错误信息本身带策略名、绑定名和 `message`，如果策略里没写 `message`，会带 `failed expression: <表达式>`。想知道是哪条表达式，先看错误里的表达式原文，再回去对 `spec.validations` 的下标；如果策略用了 `messageExpression`，消息会由 CEL 生成，失败时回退到静态 `message`。如果开了审计，审计日志里还会有一条 `validation.policy.admission.k8s.io/validation_failure` 注解，值是 JSON 列表，包含 `message`、`policy`、`binding`、`expressionIndex`、`validationActions`，比 kubectl 的错误更适合事后追查。

策略本身写错了，分两种。语法错误在创建或更新策略时就被拒绝，输出里是 `compilation failed: ... Syntax error ...`，不会留下一个坏对象。类型错误则能创建成功，结果写在 `status.typeChecking.expressionWarnings` 里：示例的策略匹配 Pod，却写了 `object.spec.replicas`，输出是 `spec.validations[0].expression` 加 `/v1, Kind=Pod: ERROR: <input>:1:12: undefined field 'replicas'`。类型检查不影响策略行为，策略仍然会参与求值；真到运行时，这个表达式会报错，再按 `failurePolicy` 决定是拒绝还是放行。所以看到 `status.typeChecking` 有 warning 不能当没看见，要么改表达式，要么把 `failurePolicy` 设成 `Ignore` 并接受它可能不生效。

修类型错误时，先确认 `matchConstraints` 匹配的资源到底有没有这个字段。Pod 没有 `spec.replicas`，Deployment 才有；同一个表达式匹配多个资源时，apiserver 会逐个类型检查，`expressionWarnings` 里会有多段。类型检查还有几个边界：`resourceRules` 里用了 `*` 的组、版本、资源不会被检查；最多检查 10 个匹配类型；CRD 不参与类型检查。这些边界意味着“创建时没报错”不等于“运行时不会出错”，关键策略还是要用真实对象跑一遍。

MAP 的排障更直接：它不改请求的成败，只改对象。用 `kubectl apply --dry-run=server -f pod.yaml -o yaml` 看最终对象里多了什么、少了什么；如果 dry-run 的结果和预期不符，先检查 `mutations` 的 `patchType` 和路径。MAP 没有 `status.typeChecking` 那样的试运行结果，也没有 `validationActions`，所以它的“审计”只能靠 dry-run、限制绑定范围、打开审计日志看请求体。上线前至少在测试 namespace 里对比“关掉绑定”和“打开绑定”两次 dry-run 的差异，确认没有覆盖掉用户自己写的标签或 sidecar。

最后，PSA、VAP、MAP 三层要一起看。PSA 先按 namespace 拒绝明显不安全的 Pod，VAP 再按业务规则拒绝，MAP 在最前面补默认值；一个 Pod 被拒，可能是三层中的任何一层。排障顺序是：先看错误里的 `violates PodSecurity` 还是 `ValidatingAdmissionPolicy`，前者查 namespace 标签和 Pod 的 `securityContext`，后者查策略、绑定和 `message`；都没有，再去看 mutating webhook 和控制器事件。

## 上生产前

**新 namespace 先 `baseline` enforce、`restricted` warn/audit，再逐步收紧。** `baseline` 能挡住已知的提权，对大多数业务镜像的兼容性更好；`restricted` 直接 enforce 容易把还没改完的 Job、CronJob、第三方 chart 全部挡在门外。先让 `warn` 和 `audit` 跑一段时间，看警告和审计日志里到底有哪些工作负载不合规，改完再切 `enforce`。namespace 标签本身就是高权限：谁能更新 Namespace，谁就能把 `enforce` 从 `restricted` 改回 `privileged`，所以 PSA 标签要和 RBAC 一起管，不能只给业务团队 `patch namespaces`。`enforce-version` 建议锁在升级前的小版本，升级集群后先评估新版本的策略差异，再改标签。

**业务 Pod 默认非 root、只读根、drop ALL、`RuntimeDefault` seccomp。** 这四项覆盖了 restricted 的核心检查，剩下的 `runAsUser != 0`、卷类型、`procMount` 按应用实际情况补。确实需要例外的（比如必须绑 80 端口的旧应用、需要写 `/var/lib` 的有状态服务），用 `NET_BIND_SERVICE`、`emptyDir`、PVC 这些最小手段解决，不要直接开 `privileged` 或 `hostPath`。例外要记录在案：哪个 namespace、哪个工作负载、为什么、什么时候复查。PSA 的豁免是 apiserver 静态配置，改一次要滚动重启 apiserver，适合“整个 namespace 或整个 RuntimeClass”级别的例外，不适合给单个 Pod 开口子。

**VAP 先 `Warn`/`Audit` 再 `Deny`，MAP 先 dry-run 再绑定。** VAP 的绑定可以只给 `Warn` 或 `Audit`，先看误报；确认后再加 `Deny`。`failurePolicy` 默认 `Fail`，表达式出错会拒绝请求，所以策略上线前要用真实对象跑一遍 `status.typeChecking`，把 `undefined field` 这类错误清掉。MAP 没有 `Warn`/`Audit`，只能靠 dry-run 看最终对象、限制绑定范围、开审计日志；变更策略改的是落盘对象，回滚比校验策略麻烦，先在测试 namespace 里对比开关绑定前后的 dry-run 结果。策略要和代码一样进 Git、有测试用例，别在集群里手改。

**PSP 已经移除，不要再写 PSP 清单。** 新集群直接用 PSA 标签加 `securityContext`；从旧集群升级，按 `migrate-from-psp` 的顺序先盘点、再 dry-run/audit/warn、最后 enforce，迁移完把 Role/ClusterRole 里对 `podsecuritypolicies` 的 `use` 规则一起删掉。PSA 覆盖不到的细粒度规则用 VAP、Kyverno 或 Gatekeeper；选一个团队能维护的，不要三套策略引擎同时上。审计日志要能查到准入拒绝和策略变更，否则出了问题只能靠猜。

**Pod user namespace 先在预发验证内核、存储和运行时。** 节点内核至少 6.3，`/var/lib/kubelet/pods` 和所有卷的文件系统要支持 idmap mount，runc/containerd 版本要够，`/etc/subuid`、`/etc/subgid` 要给 `kubelet` 配好范围；NFS 卷、`hostNetwork`、裸块设备这些组合要逐项排除。验证通过再按 namespace 或 RuntimeClass 小范围打开，不要全集群一刀切。它降低的是容器逃逸后的影响，不能替代非 root、只读根、drop ALL；两者是叠加关系，不是二选一。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `spec.securityContext` | Pod 级安全上下文，作用于所有容器 | 容器级同名字段覆盖 Pod 级 |
| `runAsNonRoot` | 要求容器以非 root 运行 | `true` 时 kubelet 校验 uid，0 则拒绝启动 |
| `runAsUser` / `runAsGroup` | 指定容器进程的 uid / gid | 不写时用镜像元数据 |
| `fsGroup` | 卷的属组，设置 setgid 让新文件继承 | 只对支持 fsGroup 的卷生效 |
| `fsGroupChangePolicy` | 挂载时是否递归改卷属主 | 默认 `Always`；`OnRootMismatch` 只在根目录不匹配时改；对 secret/configMap/emptyDir 无效果 |
| `readOnlyRootFilesystem` | 容器根文件系统只读 | 默认 `false`；挂载的卷不受影响 |
| `allowPrivilegeEscalation` | 是否允许进程提权 | 默认 `true`；`false` 设置 `no_new_privs`，不能与 privileged 或 `CAP_SYS_ADMIN` 同用 |
| `capabilities.drop` / `add` | 丢弃 / 加回 Linux capability | restricted 要求 drop `ALL`，add 只允许 `NET_BIND_SERVICE` |
| `seccompProfile.type` | 系统调用过滤配置 | `RuntimeDefault`、`Localhost`、`Unconfined`；restricted 不允许缺省 |
| `procMount` | `/proc` 的遮罩方式 | 默认 `Default`；`Unmasked` 需要 `hostUsers: false`（1.30 起强制） |
| `hostUsers` | 是否使用节点的 user namespace | 默认 `true`；`false` 启用 Pod user namespace |
| `pod-security.kubernetes.io/enforce` | PSA 拒绝级别 | `privileged` / `baseline` / `restricted` |
| `pod-security.kubernetes.io/warn` | PSA 警告级别 | 返回 HTTP 警告但放行 |
| `pod-security.kubernetes.io/audit` | PSA 审计级别 | 只在审计日志里加注解 |
| `pod-security.kubernetes.io/<mode>-version` | 锁定策略版本 | 不写为 `latest`；三个模式各自独立 |
| `kubectl label --dry-run=server --overwrite ns <ns> ...` | 收紧前评估现有 Pod | 标签值不变时不会重新评估 |
| `kubectl describe deployment/replicaset` | 看控制器创建 Pod 的 PSA 拒绝 Event | 直接创建的 Pod 没有 Event，只有 apply 错误 |
| `ValidatingAdmissionPolicy` | CEL 校验策略 | 需要 Binding 才生效；1.30 stable |
| `matchConstraints.resourceRules` | 策略匹配的资源与操作 | `apiGroups`、`apiVersions`、`operations`、`resources` 都必填；`*` 表示全部 |
| `validations[].expression` | CEL 校验表达式 | 返回 `false` 按 `validationActions` 处理 |
| `failurePolicy` | 表达式出错时的行为 | `Fail`（默认）或 `Ignore` |
| `validationActions` | 校验失败时的动作 | `Deny`、`Warn`、`Audit`；`Deny` 与 `Warn` 不能同用 |
| `paramKind` / `paramRef` | 参数化策略 | `paramRef` 的 `parameterNotFoundAction` 必填 |
| `status.typeChecking` | CEL 类型检查结果 | 类型错误只写 warning，不阻止创建 |
| `MutatingAdmissionPolicy` | CEL 变更策略 | 需要 Binding；1.36 stable |
| `mutations[].patchType` | 变更方式 | `ApplyConfiguration` 或 `JSONPatch` |
| `reinvocationPolicy` | 是否允许重复调用变更 | `Never` 或 `IfNeeded`，必填 |

本章结束时，`shorty` 的 namespace 带 `enforce=restricted`、`warn=restricted`、`audit=restricted`、`enforce-version=v1.37`；api 的 Deployment 带 non-root、只读根、drop ALL、`RuntimeDefault` seccomp；集群里有 VAP `require-team-label` 和它的 Binding、MAP `default-team` 和它的 Binding；user namespace 实验 Pod 已删除，PSP 演示 namespace 也已删除。下一章在这个基础上做威胁建模、审计和集群加固。
