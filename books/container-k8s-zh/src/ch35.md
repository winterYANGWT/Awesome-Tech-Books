# 第 35 章 可观测性与排障：日志、指标、追踪，排障顺序

周五下午，值班群里有人说 shorty 的短链打不开了，浏览器显示 502。你上集群看：`kubectl -n shorty get pods` 全是 Running，`kubectl -n shorty get deploy` 显示 2/2，Gateway 的 `PROGRAMMED` 是 True。再刷新几次，有时正常，有时 502。问题不在“Pod 有没有起来”这一层，而在请求从 Gateway 到 api 的哪一段被丢掉了，以及为什么只有一个副本在接流量。

到第 35 章为止，`s4-prod` 里已经有 HPA 和 metrics-server：`kubectl top` 能看此刻的 CPU 和内存，`kubectl logs` 能看当前容器的输出。但这些都是“此刻”。metrics-server 不在磁盘上留历史，`kubectl top` 给的是一个瞬时值；Pod 一重启，上一次的日志只剩 `--previous` 里的一段；跨 Gateway、api、postgres 的延迟，没有任何数据能把一次请求经过的几跳拼起来。生产里的 502 往往就卡在这里：没有趋势、没有离散事件、没有调用链，只能靠猜。

这一章先定一个排障顺序：事件 → 状态 → 日志 → exec/debug → 指标/追踪 → 节点/运行时。然后给集群补上最小的 Prometheus、kube-state-metrics、ServiceMonitor 和 OpenTelemetry Collector，让指标和追踪真正可用；最后用 `kubectl debug`、临时容器（ephemeral container）和 `crictl` 处理没有 shell 的容器与节点，并把告警规则和事件保留讲清楚。顺序比工具重要：先确认影响面，再定位到层，最后才钻到某一个进程。

> **起点**：`s4-prod` 已就绪。`shorty` 命名空间里 api 是 2 副本，postgres、redis、worker、Gateway 和五条 NetworkPolicy 都在；metrics-server 提供 Metrics API，HPA 在 2–5 之间伸缩。集群里没有 Prometheus、没有日志聚合、没有追踪。一步到位：`bash code/ch35/setup.sh`。

## 35.1 三信号与排障总顺序

可观测性（observability）在 Kubernetes 里通常指三类信号：指标（metrics）、日志（logs）和追踪（traces，官方中文文档把 traces 译作“链路”）。它们回答的问题不一样，不能互相替代。

| 信号 | 回答的问题 | shorty 里的来源 |
|---|---|---|
| 指标 | 现在和过去一段时间的趋势：请求量、错误率、延迟、CPU/内存、副本数 | kubelet 的 cAdvisor、kube-state-metrics、api 的 `/metrics` |
| 日志 | 某一次请求或某一次启动到底发生了什么，错误信息是什么 | 容器的 stdout/stderr，落到节点 `/var/log/pods` |
| 追踪 | 一次请求经过 Gateway、api、postgres 时，每一跳各花了多久 | 应用和控制面发出的 OTLP span |

只有指标，能看到 5xx 从 0 涨到 20%，但不知道是数据库超时还是代码 panic；只有日志，能找到一条具体的报错，但不知道这是个例还是所有副本都在报；只有追踪，能看出 api 等 postgres 花了 800 ms，但没有指标就不知道这个延迟是不是最近才出现。排障时三种信号要交替用，顺序上先便宜、后昂贵。

顺序是：`kubectl get events` → `describe pod/svc` → `logs`/`logs --previous` → `exec`/`debug` → 指标/追踪 → 节点/运行时。事件是 apiserver 里现成的记录，调度失败、镜像拉不下来、探针失败、挂载失败都会写成 Event，一条命令就能看，不需要进容器。`describe` 把 spec 和 status 放在一起，能看出“期望几个副本、实际几个 Ready、容器上次为什么退出”。日志回答进程自己怎么说，`--previous` 专门看上一次崩溃前的那一段。`exec`/`debug` 用来验证容器里的环境：DNS、端口、文件、依赖。指标和追踪回答“多大范围、哪一跳慢”，通常要等 Prometheus 和 Collector 装好之后才有。节点和运行时放在最后，因为 `crictl`、节点磁盘、运行时错误影响的是节点上的所有 Pod，只有排除了应用层才值得往下钻。

在钻进任何一层之前，先确认影响面：是全部请求还是部分请求，是一个副本还是所有副本，是一个节点还是整个集群，从什么时候开始。`kubectl get pods` 和 `kubectl get deploy` 看副本，EndpointSlice 看 Service 到底把哪些 Pod 当成后端，Gateway/HTTPRoute 的 condition 看入口有没有接受这条路由。影响面决定了往哪一层查：只有一个副本不 Ready，先查这个 Pod；所有副本都不 Ready，先查共享的依赖（数据库、Redis、ConfigMap、Secret）；只有一台节点上的 Pod 出问题，直接跳到节点。

然后只挑一个副本，通过 `kubectl port-forward` 直接打它的 `/admin/fault?not_ready=true`。返回的 JSON 是完整的故障开关快照，`not_ready` 变成 `true`；这个管理接口本身不受 readiness 影响，否则打开开关后就关不掉了。`kubectl wait --for=condition=Ready=false` 等到 kubelet 下一次探测，事件表里就出现 `Warning Unhealthy`。

事件表要按 `LAST SEEN` 读：`0s` 那条是刚刚的 readiness 503；时间更早的那些是 Pod 启动阶段留下的，应用还没开始监听，探针先失败。同一个 Pod 的多条同类事件会被合并，`LAST SEEN` 是最近一次的时间，`describe` 的 Events 段里还会带累计次数。用 `--field-selector reason=Unhealthy` 把探针失败单独筛出来，比在全部事件里翻要快。

再看状态：Deployment 的 `READY` 从 `2/2` 变成 `1/2`，Pod 变成 `0/1`，但 `RESTARTS` 仍然是 0。`describe` 里 `State` 是 `Running`、`Restart Count` 是 0，Conditions 里 `Ready` 和 `ContainersReady` 是 `False`，`PodScheduled` 是 `True`。这三行合起来说明：Pod 调度没问题、容器没重启、进程还活着，只是应用自己报告没就绪。这正是 readiness 和 liveness 的分工：readiness 失败只把 Pod 从 Service 后端摘掉，liveness 失败才会重启容器。

日志进一步确认应用没有卡住：`/readyz` 的请求都返回 503，耗时不到 1 毫秒。如果是数据库连接超时，这里会看到几秒的耗时或者 `error` 字段；如果是进程卡死，探针会报 `context deadline exceeded`，而不是一个干净的 503。事件表里更早的那些也是启动阶段的表现，和当前的 503 不是同一次原因。

EndpointSlice 是 Service 和 Pod 之间的那张表：这个副本还在表里，但 `ready=false`；另一个副本是 `ready=true`。kube-proxy 只把 ready 的地址放进负载均衡，所以这个 Pod 收不到新请求，但也没有被杀掉。最后直接请求它的 `/readyz`，返回 `not ready: fault: not_ready`，原因就写在响应体里，不用再从 503 反推。

Gateway 这时仍然返回 200，因为还有一个副本在服务。影响面是“容量减半”，不是“全站 502”。如果两个副本都掉出去，EndpointSlice 里就没有 ready 的地址，Gateway 会返回 502——35.7 会用另一个原因复现这个结果。恢复时只需要把开关关掉，kubelet 按 `periodSeconds: 5` 重新探测，几秒后 `READY` 回到 `2/2`；整个过程没有重建 Pod，也没有重启容器。

## 35.2 指标：metrics-server 与 Prometheus

metrics-server 提供的是 Metrics API（`metrics.k8s.io`），它通过 API 聚合层注册成 `v1beta1.metrics.k8s.io` 这个 APIService，从每个节点的 kubelet 拉 CPU 和内存，再在内存里聚合成 `NodeMetrics` 和 `PodMetrics`。`kubectl top`、HPA 和 VPA 都读这个 API。它只做“自动扩缩容所需的最小资源指标”：没有 HTTP 状态码、没有延迟直方图、没有历史曲线，也不是给长期存储和查询用的。官方文档明确说 Metrics API 不是完整监控流水线的替代品。

> **旧资料提示**：旧教程里用 Heapster + InfluxDB + Grafana 做监控。Heapster 已经退役，官方 RBAC 参考里 `system:heapster` 这个角色标着 deprecated；现在资源指标由 metrics-server 提供，长期指标用 Prometheus 或托管服务。

Prometheus 走的是另一条路：它按固定间隔主动抓取（scrape）目标的 `/metrics`，把样本写进自己的时序数据库（TSDB），然后用 PromQL 查询、用规则告警。Kubernetes 的控制面组件（kube-apiserver、kube-scheduler、kube-controller-manager、kube-proxy、kubelet）都以 Prometheus 文本格式暴露 `/metrics`；kubelet 还额外暴露 `/metrics/cadvisor`、`/metrics/resource`、`/metrics/probes`。应用的 `/metrics` 也是同一种文本格式，shorty 的 `shorty_http_requests_total`、`shorty_http_request_duration_seconds` 就是按这个格式写的。

中间还差一层对象状态。cAdvisor 和 kubelet 给的是资源用量，Prometheus 不知道“这个 Deployment 期望 2 个副本、实际 1 个 Ready”。kube-state-metrics 连 apiserver，把对象状态转成 `kube_pod_status_ready`、`kube_pod_container_info` 这样的指标，所以“副本不足”“Pod 卡在 Terminating”“PVC 容量”这类告警都靠它。

装 Prometheus 有两条路：自己写 StatefulSet、ConfigMap 和抓取配置，或者用 prometheus-operator。operator 管着几类 CRD：`Prometheus` 描述一个 Prometheus 实例（副本数、保留期、选择哪些 ServiceMonitor/PrometheusRule），`ServiceMonitor` 描述抓哪些 Service 的哪个端口，`PrometheusRule` 描述告警和记录规则，`Alertmanager` 描述告警路由。operator 监听这些 CR，生成 StatefulSet、ConfigMap、Service 和 Secret。本章用 `kube-prometheus-stack` 这个 chart 装 operator 和这些 CRD，再用 values 文件关掉不需要的部分。

## 35.3 日志：节点、容器与轮转

容器日志的入口是标准输出和标准错误。容器运行时把这两个流接住，按 CRI 日志格式写到节点上的文件；kubelet 负责告诉运行时写到哪里，并在 `kubectl logs` 时把文件内容读回来。默认目录是 `/var/log/pods/<namespace>_<pod>_<uid>/<container>/<n>.log`，`<n>` 从 0 开始，轮转后递增。`/var/log/containers` 下面是另一套按 `<pod>_<namespace>_<container>-<containerID>.log` 命名的符号链接，指向 `/var/log/pods` 里的真实文件；旧的采集脚本和 `docker logs` 时代的习惯认这个目录，kubelet 仍然维护它。

> **旧资料提示**：旧教程让从 `/var/lib/docker/containers` 读容器日志。Kubernetes 1.24 移除 dockershim 后，节点运行时通常是 containerd，Kubernetes 的日志在 `/var/log/pods` 和 `/var/log/containers`；Docker 自己的目录不再是集群日志的来源。

kubelet 负责轮转：`containerLogMaxSize` 默认 10Mi，`containerLogMaxFiles` 默认 5，两个都在 kubelet 配置文件里改。`kubectl logs` 只读**最新的那个文件**，所以一个 Pod 写了 40MiB 日志、每 10MiB 轮转一次时，`kubectl logs` 最多只能拿到 10MiB。容器重启时，kubelet 默认保留上一个已终止容器的日志，这就是 `kubectl logs --previous` 能读到崩溃前那一段的原因；Pod 被驱逐时，日志跟着容器一起离开节点。

系统组件的日志走另一条路。用 systemd 的节点上，kubelet 和容器运行时默认写 journald，用 `journalctl -u kubelet` 看；没有 systemd 时写 `/var/log` 下的 `.log` 文件。跑在静态 Pod 里的 apiserver、scheduler、controller-manager 写 `/var/log`，绕过容器的日志机制。把这些目录挂进 Pod 时，轮转要自己负责，Kubernetes 不管。

单机的 `kubectl logs` 不是集群级日志方案。Pod 被删、节点挂了、日志轮转覆盖了，日志就没了。生产通常在每台节点上跑一个日志代理的 DaemonSet（Fluent Bit、Vector、OpenTelemetry Collector 都行），tail `/var/log/pods` 或 `/var/log/containers`，转发到集中式存储；也可以在 Pod 里加 streaming sidecar，把应用写的文件转到自己的 stdout。前者不需要改应用，后者适合应用只会写文件的场景，但会多一份磁盘和内存开销。本章不装日志后端，只把 JSON 日志、节点上的文件和 `--previous` 这三件事做扎实。

示例先制造三种结果：`/` 返回 200，`/r/nope` 返回 404，把 `error_rate` 开到 1 之后三次 `POST /api/links` 都返回 500。`kubectl logs` 拿到的是 JSON 行，`jq` 按 `msg == "request"` 和 `status >= 400` 过滤，四行分别是那次 404 和三次 500。注意 404 花了 30ms（查了一次存储），500 只花了 0.007ms——错误在进入业务逻辑之前就返回了。文本日志要用正则去抠状态码，字段一改就失效；JSON 日志按字段过滤，稳定得多。

节点上的路径能对上：`/var/log/pods` 下是 `shorty_<pod 名>_<uid>` 目录，`/var/log/containers` 下是 `api-..._shorty_api-<containerID>.log` 的符号链接，箭头指向 `/var/log/pods/.../api/0.log`。采集代理读哪一边都可以，读 `/var/log/containers` 的好处是文件名里带 Pod、namespace 和容器名，不用自己拼路径；坏处是它只是链接，Pod 删掉后链接也会消失。

最后让这个容器崩溃一次：`crash_after=3` 让进程在 3 秒内以非 0 退出，`kubectl wait` 等到 `restartCount` 变成 1。`lastState.terminated` 里 `exitCode=1`、`reason=Error`，这是容器状态里的“上次怎么死的”。`kubectl logs --previous --tail=4` 的最后一行是 `"msg":"故障开关触发退出"`，原因直接写在日志里。shorty 没有往 `/dev/termination-log` 写东西，所以 `lastState.terminated.message` 是空的；如果应用习惯把最后一句错误写进 termination message，Kubernetes 会把它放进容器状态，默认路径是 `/dev/termination-log`，单条超过 4096 字节会被截断。把 `terminationMessagePolicy` 设成 `FallbackToLogsOnError`，termination message 为空且容器以错误退出时，kubelet 会退而取日志的最后一段（最多 2048 字节或 80 行）。

节点上的日志文件会按 10MiB × 5 份轮转，超过的部分 `kubectl logs` 读不到；要查更早的日志，只能靠节点上的文件或已经采集到后端的副本。生产里把日志代理的采集位置、保留期和轮转配置一起纳入容量规划，不要等磁盘被 `/var/log/pods` 填满才发现。

## 35.4 追踪：OpenTelemetry 与组件 tracing

一条追踪（trace）是一次请求的完整路径，由多个跨度（span）组成。每个 span 有 trace ID、span ID、父 span ID、开始/结束时间、名称和一组属性；父子关系把 Gateway 收到请求、api 处理请求、api 查 postgres 这几步串成一棵树。跨进程传递靠上下文传播（context propagation），Kubernetes 和 OpenTelemetry 都用 W3C Trace Context。采样（sampling）决定哪些请求留下 span：全量采集在生产里通常太贵，常见做法是头部采样（在大致固定的比例上决定）或尾部采样（先收集，再按错误/延迟保留）。

OpenTelemetry 的传输协议是 OTLP。gRPC 的默认端口是 4317，HTTP 的默认端口是 4318；两者都能承载同样的 span。Collector 把链路拆成三段：receiver 接收（`otlp`）、processor 处理（`batch`、采样、脱敏、属性改写）、exporter 导出（`otlphttp` 到后端，或者 `debug` 打到 stdout）。应用侧用 OTel SDK 生成 span，把 exporter 指向 Collector；Collector 再决定往哪里送。这样应用不用知道后端是 Jaeger、Tempo 还是商业服务。采样要写进设计：头部采样在 SDK 里决定，成本低，但会丢掉没被采到的错误请求；尾部采样在 Collector 里缓冲整条 trace，按错误或慢请求保留，代价是内存和延迟。生产至少要保证错误请求可见，否则 5xx 发生时恰好没有 span。

Kubernetes 的控制面组件也能直接发 OTLP。kube-apiserver 给进来的 HTTP 请求、发给 webhook/etcd 的请求和重入请求生成 span，并用 W3C Trace Context 往下传；它不采用请求里带的 trace context，因为 apiserver 经常是公网入口。开启方式是给 apiserver 一个 `--tracing-config-file`，文件里是 `TracingConfiguration`，`samplingRatePerMillion: 100` 表示一万个请求留一个，默认 endpoint 是 `localhost:4317`。kubelet 的配置里对应 `tracing.samplingRatePerMillion`，收集垃圾回收、Pod 同步和每个 gRPC 方法的 span，并把上下文传给 CRI 运行时，containerd、CRI-O 的 span 能挂到 kubelet 的 trace 下面。`APIServerTracing` 在 1.22 alpha、1.27 beta、1.34 stable；`KubeletTracing` 在 1.25 alpha、1.27 beta、1.34 stable。1.37 里 tracing 的 instrumentation 本身还没有稳定性承诺，span 名称和属性可能随版本变，告警和仪表盘不要依赖具体的 span 名。

本章不装 Jaeger 或 Tempo：一个完整的追踪后端要存储、查询和 UI，lab 的内存放不下，也不是这一节的重点。示例只装一个 Collector，用 `debug` exporter 把 span 打到 stdout，验证“应用发 OTLP → Collector 接收 → 处理 → 导出”这条链路。生产里把 exporter 换成 `otlphttp`，指向 Tempo、Jaeger 或云厂商的 OTLP 端点即可。

## 35.5 运行时与网络排障

`kubectl exec` 进不去容器时，先分清是“没有 shell”还是“进程已经挂了”。前者用临时容器（ephemeral container），后者只能看 `--previous` 日志或 `kubectl debug` 的 Pod 副本。临时容器在 1.25 稳定：它被加到正在运行的 Pod 里，和原容器共享网络命名空间（加 `--target` 可以共享 PID 命名空间），但不替换、不重启原容器，也不能在 Pod 创建后再删掉，清理办法是重建 Pod。临时容器不能配端口、探针和资源限额，所以它只适合排障，不适合当 sidecar。

shorty 的 api 是 scratch 镜像，连 `sh` 都没有，`kubectl exec` 会报 `executable file not found`。这时用 `kubectl debug` 加一个带 curl 的临时容器，直接请求 `localhost:8080`：网络命名空间是 Pod 的，所以 localhost 就是 api 自己。shorty 的 namespace 开了 PSA `restricted`，临时容器也要满足同样的限制，示例用 `--profile=restricted`；不写 `--profile` 时 kubectl 用的是 `legacy`，官方已经计划弃用它，新脚本建议显式写 `general` 或 `restricted`。

节点这一层用 `crictl`。它是 CRI 运行时的命令行客户端，端点可以写在 `/etc/crictl.yaml`，也可以用 `--runtime-endpoint`、`--image-endpoint` 或 `CONTAINER_RUNTIME_ENDPOINT`/`IMAGE_SERVICE_ENDPOINT` 指定；`crictl ps -a` 列容器，`crictl pods` 列 Pod，`crictl logs <containerID>` 看日志，`crictl inspect <containerID>` 看运行时层面的 spec 和状态。不设端点时 crictl 会依次尝试一组已知地址，可能拖慢命令，所以在节点上显式写 `/etc/crictl.yaml` 更稳。节点上没有 shell 或不想 SSH 时，用 `kubectl debug node/<node>` 起一个调试 Pod：它把节点根文件系统挂在 `/host`，容器跑在节点的 IPC、网络和 PID 命名空间里，但默认不是特权容器；需要 `chroot /host` 或抓包时加 `--profile=sysadmin`。调试完把 Pod 删掉。

Service 不通时，按 EndpointSlice → DNS → iptables/nftables → 抓包的顺序查。先确认 Service 的 selector 能选中 Pod、EndpointSlice 里有 ready 的地址；再用一个同 namespace 的 Pod 解析 Service 名，排除 DNS；然后在节点上看 kube-proxy 写的规则（iptables 模式看 `iptables-save | grep <service>`，IPVS 模式看 `ipvsadm -ln`），最后才用 tcpdump 抓包。`kubectl port-forward` 是这条链路的对照组：它绕过 Service 和 kube-proxy，直接把本地端口转到 Pod，如果 port-forward 能通而 Service 不通，问题就在 Service、Endpoints 或网络策略，不在应用。

## 35.6 告警与事件

PrometheusRule 是 prometheus-operator 定义的一类 CR，里面是规则组，每组一组 `expr`、`for`、`labels`、`annotations`。`expr` 为真时告警先进入 pending，持续 `for` 指定的时间后变成 firing；`for: 0m` 表示当次判定就 firing，只适合 lab。规则标签里的 `severity` 决定走哪条路由，注解里的 `summary`、`description`、`runbook_url` 是给人看的；没有 runbook 的告警等于没有告警，值班的人还得从头查一遍。

Prometheus 只负责判定和触发，真正把告警送出去的是 Alertmanager。Alertmanager 接收 Prometheus 推来的告警，按 `route` 树分组、抑制、静默，再发给 receiver（邮件、Slack、PagerDuty、webhook）。本章的 values 把 Alertmanager 关掉了，所以示例里的告警只在 Prometheus 里变成 firing，不会有人收到通知；生产要把 Alertmanager 装起来，或者用云厂商兼容的告警服务，并且给每条路由配好接收人和升级策略。

告警要基于症状和 SLO，不要给每个指标都配一条。用户能感知的是错误率、延迟、可用副本数和入口 5xx；内部指标（某个队列长度、某台机器的磁盘）可以作为辅助，但要能回答“它坏了用户会怎样”。一条 `ShortyHigh5xx` 比十条“某个 Pod 的 CPU 超过 50%”有用；副本不足、PVC 使用率、证书到期、etcd 延迟这些也属于“坏了会出事”的症状。每条告警都要有 runbook：先看哪个面板、跑哪条查询、找谁升级。

事件和告警是两套东西。Event 是 apiserver 里的对象，默认只保留 1 小时（kube-apiserver 的 `--event-ttl` 默认 `1h0m0s`），适合排障时看最近发生了什么，不适合当审计或长期趋势。生产通常用 `kubernetes-event-exporter` 之类的工具把 Event 转发到日志或消息系统，再把“某类 Event 的频率”做成指标；对象状态的长期变化则交给 kube-state-metrics。

规则文件里 `release: kps` 这个标签不能少：Prometheus CR 的 `ruleSelector` 和 `serviceMonitorSelector` 一样，默认只选带这个标签的对象。规则组名是 `shorty.rules`，告警名是 `ShortyHigh5xx`，表达式是“5xx 的速率除以全部请求的速率大于 5%”，`for: 0m` 让它在 lab 里立刻 firing。

示例先确认规则已经出现在 Prometheus 的 rules API 里：`state=inactive`、`health=ok`，说明表达式能编译、只是还没满足条件。然后先发一个 500，让 `status=500` 的序列以 1 进入 Prometheus；否则故障期间 `/metrics` 也被注入 500，Prometheus 抓不到中间值，`rate` 会把“从无到 27”算成 0。接着把 `error_rate` 调到 0.5，每秒 5 个请求，跑 10 秒，一共 50 个。这里既不能开 1、也不能跑久：shorty 的 `/healthz` 和 `/readyz` 也走同一个故障开关，`error_rate=1` 会让 Pod 在几秒内变成 NotReady，被 EndpointSlice 摘掉，Prometheus 就抓不到它的 5xx 计数；0.5 让探针还有机会成功，Pod 留在后端，计数器才能被 scrape 到；示例里 50 个请求有相当一部分拿到 500，比例足够触发 5% 的阈值。Prometheus 每 15 秒抓一次，`rate(...[5m])` 在两个采样点之后就能算出比例；用 5 分钟窗口而不是 1 分钟，是为了让这 10 秒的突发在窗口里留得久一点：规则加载和判定有延迟，1 分钟窗口很可能在判定时已经滑过去了。轮询到 `state=firing` 后，`ALERTS{alertname="ShortyHigh5xx"}` 的 `alertstate` 也是 `firing`，`value` 是 1。这时没有 Alertmanager，所以不会再有人收到消息；如果装了 Alertmanager，Prometheus 会把这条 firing 推过去，由路由决定发给谁。

5xx 比例这个表达式有个边界：没有流量时 `rate` 没有样本，比值不是 0 而是没有数据，告警不会触发；要单独用 `absent()` 或“请求量低于阈值”的规则覆盖“没有流量”的情况。延迟告警通常用 `histogram_quantile(0.99, sum by (le) (rate(shorty_http_request_duration_seconds_bucket[5m])))`，比单看平均值更能反映长尾。生产里的 `for` 一般设 5 到 10 分钟，避免一次抖动就打醒人；同时给告警加 `severity` 和 runbook，让“收到告警之后做什么”不依赖某个人的记忆。

## 35.7 排障：Service 502 与查不到的指标、追踪

502 是代理层在说“上游没有给我一个有效响应”。在 shorty 这条链路上，从外到内是 Gateway → HTTPRoute → Service → EndpointSlice → Pod → 容器端口 → 应用。先看 Gateway 和 HTTPRoute 的 condition（`Accepted`、`Programmed`），确认入口接受了这条路由；再看 Service 的 selector 和 ports；再看 EndpointSlice 的 addresses 和 ready；再看 Pod 的 Ready 和容器端口；最后才查 NetworkPolicy 和应用本身。跳步的代价是很容易在错误的层里改东西：Pod 明明是好的，却去重启它。顺序不是死的：日志里已经有明确的错误时，可以直接跳到那一层，但不要跳过“确认影响面”。

“Pod 是 Running，为什么 Service 没有后端”通常有四种原因：selector 不匹配（拼写错、label 改过、Pod 在别的 namespace）；readiness 失败（Pod Running 但 Ready False）；`targetPort` 写错或端口名对不上；Pod 和 Service 不在同一个 namespace（Service 只能选同 namespace 的 Pod）。前两种最常见，而且只有 EndpointSlice 能把它们区分开：selector 错时 EndpointSlice 里根本没有地址，readiness 失败时地址还在、`ready=false`。

指标和追踪查不到时，先查数据源而不是查应用。`kubectl top` 报 `Metrics API not available`，先 `kubectl get apiservice v1beta1.metrics.k8s.io`：NotFound 说明 metrics-server 没装；`AVAILABLE` 是 False 就看 kube-system 里的 metrics-server Pod 和 apiserver 的聚合层。Prometheus 的 target DOWN，按 ServiceMonitor 的 `selector`/`port`/`namespaceSelector` → Prometheus CR 的 `serviceMonitorSelector`/`serviceMonitorNamespaceSelector` → Service 的端口名 → NetworkPolicy 的顺序查；35.3 的 DOWN 就是 shorty 的 default-deny 挡住了 monitoring。trace 没有 span，查 exporter 的 endpoint 和端口、采样率是不是 0、Collector 的 receiver 有没有收到、pipeline 里有没有接上 traces；组件 tracing 还要确认特性门控和 `--tracing-config-file`。

## 上生产前

**三种信号分开存、分开保留。** 日志要外置：节点上的 DaemonSet 代理（Fluent Bit、Vector、OpenTelemetry Collector）tail `/var/log/pods` 或 `/var/log/containers`，送到集中式日志存储，按天/周设保留期；指标要长期化：Prometheus 本地 TSDB 只适合短期，生产用远程写、Thanos 或托管服务，保留期按查询需求定；追踪按采样率留：全量采集的成本随流量线性涨，常见做法是低比例头部采样加错误/慢请求的尾部采样。三种数据混在一个存储里，查询模式和保留策略会互相牵制，成本也下不来。

**告警基于症状和 SLO，不基于每个 Pod。** 用户能感知的是 5xx 比例、p99 延迟、可用副本和入口错误；CPU 高不等于用户受影响，某个 Pod 重启一次也不一定值得叫醒人。每条告警要有 `severity`、owner 和 runbook，`for` 设 5 到 10 分钟过滤抖动；Alertmanager 要配路由、分组、抑制和值班表，静默要有期限。事件默认只留 1 小时，生产用事件导出器把 Event 送进日志或消息系统，否则故障过去后什么都没留下。

**生产镜像不加 shell，排障用临时容器和节点工具。** scratch 或 distroless 镜像里没有 sh 是好事，不要为了 `kubectl exec` 方便把 shell、curl、tcpdump 加回去。需要进容器时用 `kubectl debug` 加临时容器，PSA `restricted` 下用 `--profile=restricted`；需要看节点时用 `kubectl debug node` 加 `--profile=sysadmin`，或者 SSH 到节点用 `crictl`。`pods/ephemeralcontainers` 的 `create` 和 `nodes/proxy` 的 `get` 都是高权限，谁能用要写进 RBAC 和审计。

**监控监控系统本身。** 单副本 Prometheus 是单点，Pod 重建期间没有指标；示例没有配持久卷，数据随 Pod 消失。生产给 Prometheus 配 PVC 或远程存储，给 Alertmanager 配副本，监控规则数量、规则评估耗时、KSM 的 series 基数和 Prometheus 的磁盘使用。控制面、etcd、PVC 使用率和证书到期也要有告警；这些对象坏了，应用指标再全也查不动。`kubectl top` 和 Metrics API 只覆盖 CPU/内存，别把它当成长期监控。

| `rate()` / `histogram_quantile()` | PromQL 算速率和分位数 | 前者用于 counter，后者用于 histogram |
| `kubectl port-forward` | 绕过 Service 直接验证 Pod | 只用于本地验证，不是生产入口 |

本章结束时，`shorty` 跑在单节点 kind 集群的 `s4-prod` 上，`monitoring` 里有单副本 Prometheus、kube-state-metrics 和 OTel Collector，`shorty` 里有 `ServiceMonitor` 和 `ShortyHigh5xx` 规则；`kubectl debug` 加临时容器验证过 api 的 `/healthz`。下一章在这个集群上做 etcd 快照、节点维护和升级演练。
