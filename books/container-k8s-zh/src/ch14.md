# 第 14 章 Compose：服务、网络、卷、依赖与健康检查、profiles、watch（附：Swarm 去哪了）

shorty 到第 13 章已经有了五个组件：PostgreSQL、Redis、一次性执行的 `migrate`、HTTP 服务 `api`、队列消费者 `worker`。它们各自能跑，但每次从头搭一遍都要先 `docker network create`，再 `docker volume create`，然后按顺序跑迁移、起数据库、起缓存、起应用。把顺序写进脚本也不稳：数据库进程已经启动，不代表它已经能接受连接；`api` 抢在前面连过去，日志里就是 `connection refused`。

有人于是写了一份 `compose.yaml`，给 `api` 加上 `depends_on: [postgres]`，再跑 `docker compose up`，`api` 还是先起来并报连接失败。这不是 Compose 没有执行依赖，而是 `depends_on` 的默认语义只保证“依赖的容器已经启动”，不保证“里面的进程已经准备好”。要把“启动”变成“就绪”，得让 Compose 有办法判断就绪：给依赖加 `healthcheck`，把条件改成 `service_healthy`。

这一章把 shorty 的五个组件写成一份 Compose 项目，先看 project、service、network、volume 这些模型元素，再看构建、依赖和健康检查，然后把网络、端口、卷和 secret 拆开，接着用 profiles 和多文件管本地开发配置，用 watch 做热更新。最后回到一个经常被问到的问题：Compose 的 `depends_on` 到了 Swarm 里为什么不起作用，Swarm 今天还剩什么。

> **起点**：第 13 章结束时，`shorty:0.1` 已经带 SBOM、provenance 和签名，本地 registry 可用；单机容器、网络、卷都操作过，但还没有 Compose 文件。本章不建 kind 集群。在 lab 里执行 `bash code/ch14/setup.sh`：它会构建 `shorty:0.1` 和 `shorty-worker:0.1`，拉取 `postgres:18.6-alpine`、`redis:8.8.4-alpine`、`nginx:1.29-alpine` 和 `python:3.15.2-slim-trixie`，预构建 `tools` 和演示 watch 的 `page` 镜像，并把 lab 的 inotify 实例上限调大，避免多个任务同时跑 `compose watch` 时撞上系统限制。

## 14.1 Compose 模型：project/service/network/volume

一个 `compose.yaml` 对应一个 project。project 不是“这组容器的名字”，而是资源归属的边界：Compose 创建的网络、卷、容器都会带上项目前缀，默认网络叫 `<project>_default`，命名卷叫 `<project>_<volume>`。本章的文件在顶层写 `name: shorty`，所以运行起来看到的是网络 `shorty_default`、卷 `shorty_pgdata`、容器 `shorty-api-1`。同一个文件可以用 `-p` 或 `COMPOSE_PROJECT_NAME` 换成另一个项目名，在同一台机器上再部署一份，资源不会互相覆盖。

service 是容器模板，不是容器本身。`api` 这个 service 描述“用哪个镜像、传什么环境变量、开哪些端口、依赖谁”，`docker compose up` 按这个模板创建一个容器；如果以后把副本数调大，同一个 service 会对应多个容器。Compose 文件里写的是期望状态，创建、启动、删除容器是 CLI 根据这个模型去执行的动作。

project 下面是几类资源。service 通过网络互相通信，默认情况下 Compose 给项目建一个 bridge 网络，所有 service 加入，服务名就是 DNS 名。service 把持久数据写进 volume，卷可以是 Compose 管理的命名卷，也可以是宿主路径的绑定挂载。configs 和 secrets 是两类特殊的配置：它们在容器里都表现为挂载的文件，前者用于普通配置，后者用于密码、证书这类敏感数据。顶层声明这些资源，service 再按需引用，这样网络、卷、密钥可以跨 service 复用。

顶层 `version` 字段已经是历史。Compose v1 用 `2.x`、`3.x` 这样的文件格式版本，v2 和 v5 改用 Compose Specification，`version` 变成可选并被忽略。今天写 `version: "3.8"` 不会让文件更兼容，只会让读者以为它还有作用；14.7 的 Swarm 示例是唯一的例外，因为 `docker stack deploy` 明确只接受 legacy v3 文件，那里必须写。

> **旧资料提示**：旧教程常要求 `compose.yaml` 顶层写 `version: "3.7"` 或 `version: "2"`。Compose v2 和 v5 已经忽略这个字段，Compose Specification 把它变成可选；旧文件格式 2.x/3.x 在 2017 年后被合并进规范，不再需要版本号（依据 `docker:manuals/compose/intro/history.md`）。

## 14.2 服务、构建与依赖

`api` 的 `build` 段指向 `../app/api`，`dockerfile` 写 `Dockerfile`。`context` 是构建上下文，`dockerfile` 相对于上下文；`target` 可选，用来停在多阶段 Dockerfile 的某个阶段。shorty 的 api Dockerfile 有两个阶段：`build` 编译，最后一个阶段只复制二进制。这里不写 `target`，Compose 构建到最后阶段；如果要做调试镜像，可以写 `target: build`，得到带 Go 工具链和源码的阶段。`image: shorty:0.1` 给构建结果一个固定名字，后面的 `migrate` 直接引用同一个镜像，不需要重复构建。

`docker compose config --images` 只列镜像名，`config --hash` 给每个 service 算一个配置哈希，用来判断某次改动会影响哪些 service；这两个子命令都不启动容器。`docker compose build api` 可以只构建一个 service，`--no-cache` 会强制重做每一层，适合怀疑缓存有问题时。

`migrate` 是一次性任务，但它在 Compose 里仍然是一个 service：镜像相同，`command` 换成 `migrate`，`restart: "no"`，跑完退出。`api` 和 `worker` 用 `restart: unless-stopped`，进程意外退出时由 Docker 重启；`migrate` 不能这么设，否则迁移失败会无限重跑。`restart` 只负责“容器退出后要不要再起”，不负责“依赖有没有准备好”，这两件事要分开看。

依赖写在 `depends_on` 里，长格式的 `condition` 有三种：

- `service_started`：依赖的容器启动即可，等价于短格式 `depends_on: [postgres]`，也是默认行为。
- `service_healthy`：依赖的 healthcheck 通过，才创建依赖它的 service。
- `service_completed_successfully`：依赖的容器以 0 退出，才继续。

本章的链条是：`postgres` 健康后 `migrate` 启动；`migrate` 以 0 退出后 `api` 和 `worker` 启动；`api`/`worker` 还各自等 `postgres` 和 `redis` 健康。`docker compose up` 会按依赖顺序创建和启动，`down` 按相反顺序停止和删除。

`up -d --build --quiet-build` 里，`--build` 让 Compose 先构建带 `build` 的 service，`--quiet-build` 只把构建日志收起来，镜像还是会重新构建。输出被截断到末尾几行，能看到 `postgres` 先 `Healthy`，`migrate` 才 `Starting`，然后 `Exited`；`api` 和 `worker` 最后才 `Started`。这些 `Waiting`、`Healthy`、`Exited` 行就是依赖条件在起作用，不是装饰性的进度条。

`up -d` 返回时，容器已经启动，但不等于 `api` 已经能服务。脚本用 `curl` 轮询 `/readyz` 到成功，而不是 `sleep` 固定秒数；`readyz` 返回 `ok` 才说明数据库和 Redis 都连上了。这个区别在 14.3 会放大：容器启动和进程就绪之间可能差十几秒。

`ps -a` 的表格里，`api` 和 `worker` 是 `running`，`Health` 为空，因为这两个 service 没有配 healthcheck；`postgres` 和 `redis` 是 `running`、`healthy`；`migrate` 是 `exited`、`ExitCode` 为 0。`-a` 不能省，否则已经退出的 `migrate` 不会出现在列表里。`ExitCode` 对运行中的容器也会显示 0，判断一次性任务是否成功要看 `State` 和退出码两个字段。

`migrate` 的日志只有一行：`links` 表和过期索引已就绪，可重复执行。迁移脚本是幂等的，所以重复 `up` 不会因为表已存在而失败；这也是它能安全地作为每次启动的前置步骤的原因。

最后两行确认了卷。`docker volume ls` 里是 `shorty_pgdata`，`docker volume inspect` 显示驱动是 `local`。这个卷在 `docker compose down` 时默认保留，只有 `down -v` 才会删除；14.3 为了让数据库从空数据开始，用了 `down -v`，平时不要随手加 `-v`。

依赖顺序解决的是“谁先启动”，没有解决“启动后能不能用”。下一节把 healthcheck 拆开，看看它到底检查了什么，以及为什么它不能代替应用自己的 readiness。

## 14.3 healthcheck 与就绪

healthcheck 是一段在容器里周期性执行的命令。退出码 0 表示健康，非 0 表示这次检查失败；连续失败到 `retries` 次，容器被标记为 `unhealthy`。`interval` 是两次检查的间隔，`timeout` 是单次检查的超时，`start_period` 给启动慢的进程留出缓冲，避免刚启动就被判失败。这几个值没有一条适合所有服务，数据库、缓存、HTTP 服务的启动曲线不一样，要按实测调。

`test` 有两种写法。`["CMD", "redis-cli", "ping"]` 直接执行 `redis-cli`，不经过 shell，参数就是数组里的元素；`["CMD-SHELL", "pg_isready -U shorty -d shorty"]` 把字符串交给容器的 `/bin/sh -c`，可以用管道、重定向和 shell 变量。只写一个字符串时，等价于 `CMD-SHELL` 加这个字符串。用 `CMD` 时没有 shell 做变量替换，`$POSTGRES_USER` 不会被展开；要在 Compose 文件里引用容器内的环境变量，得写 `$$POSTGRES_USER`，让 Compose 把 `$$` 变成一个 `$` 留给容器里的 shell。

本章的 postgres 用 `pg_isready` 检查服务器是否接受连接，redis 用 `redis-cli ping` 检查是否能拿到 `PONG`。这两个命令都只验证“服务能响应”，不验证业务表是否存在、队列是否可用。`api` 的 `/readyz` 检查的是数据库连接和 Redis 连接，`/healthz` 只检查进程还活着；三个检查各管一段，不能互相替代。

先看没有 healthcheck 时会发生什么。`compose.race.yaml` 只保留 postgres 和 api，postgres 的 `command` 先 `sleep 12` 再执行 entrypoint，`api` 的依赖写成 `service_started`：

```console

```

`down -v` 先把正常栈删掉，连卷一起删，保证 race 项目从空数据库开始。`up -d` 的输出被截断，但能看出 postgres 和 api 几乎同时 `Started`；Compose 只等到 postgres 容器进程启动，就认为 `service_started` 条件满足，于是创建 api。此时 postgres 里的 entrypoint 还在 sleep，5432 端口没有监听。

`readyz` 的第一次结果是 `503`，响应体是 `not ready: database: failed to connect to ... connect: connection refused`。这条 `connection refused` 在 HTTP 响应里，不在 api 日志里；api 的日志只在依赖全部连通后写一行“数据库和 Redis 已就绪”，失败重试不逐条打印。排障时只看 `docker compose logs api` 会以为什么都没发生，`curl -i` 或看 `/readyz` 的响应体才有线索。

api 没有因为数据库没起来而退出。它照常监听，后台每 2 秒重试；postgres 的 12 秒过去、数据库开始接受连接后，同一个 `/readyz` 变成 `200`，响应体是 `ok`。这说明应用自身的重试和退避是必要的：Compose 只能把启动顺序排好，运行期间数据库重启、网络抖动，仍然要由应用自己恢复。

换回带 healthcheck 的 `compose.yaml`，Compose 会等 postgres 的 `pg_isready` 通过，再创建 migrate；migrate 退出 0 后，api 和 worker 才启动。最后的 `ps` 里 postgres 和 redis 是 `healthy`，api 和 worker 没有 healthcheck，只显示 `running`；`readyz` 已经返回 `ok`。这里的 `service_healthy` 不是“api 已经就绪”，它只表示 postgres 这一层通过了检查；api 是否真的能服务，仍然由 api 自己的 `/readyz` 回答。

> **旧资料提示**：旧教程里常写“`depends_on` 保证依赖服务就绪”。它只保证启动顺序；短格式等价于 `service_started`，要等健康检查必须写长格式的 `condition: service_healthy`，要等一次性任务成功必须写 `service_completed_successfully`（依据 `docker:manuals/compose/how-tos/startup-order.md`）。

`docker inspect --format '{{json .State.Health}}' <容器>` 能看到最近几次检查的输出和退出码，`docker compose ps` 只给一个状态；排查检查命令本身写错时，前者更有用。

healthcheck 还有一个边界：它由 Compose 或容器运行时执行，结果只影响 `docker compose ps` 里的健康状态和依赖判断。Kubernetes 的 readinessProbe 会让 Pod 从 Service 的 EndpointSlice 里摘掉，Compose 没有这层流量控制；一个 `healthy` 的容器照样可能返回 503。把 healthcheck 当成“容器还活着”的粗粒度信号，把 `/readyz` 当成“应用能不能接请求”的细粒度信号，两者都保留。

## 14.4 网络、端口与卷

Compose 默认给项目建一个 bridge 网络，名字是 `<project>_default`。每个 service 的容器加入这个网络，服务名注册到 Docker 的内嵌 DNS，容器之间用服务名互相访问。shorty 的 `SHORTY_DB_URL` 写的是 `postgres:5432`，`SHORTY_REDIS_ADDR` 写的是 `redis:6379`，这些名字不是宿主机的域名，而是 `shorty_default` 里的服务名。

```console
{{#include code/ch14/14_4_compose_secret.out}}
```

`getent hosts api` 在 postgres 容器里解析出一个容器 IP，后面跟着 `api`。这个 IP 是容器启动时从网络子网里分配的，容器重建就会变；服务名不变，所以应用里应该写服务名，不要写 IP。`docker network ls` 里能看到 `shorty_default` 是 `bridge` 驱动；`network inspect` 列出四个正在网络里的容器，`migrate` 已经退出，不在列表里。

`docker compose port api 8080` 输出 `0.0.0.0:8080`，说明宿主的所有地址都能访问 api 的 8080。postgres 的 `ports` 和 `expose` 都是 `null`：它没有发布端口，也没有在 Compose 文件里声明 `expose`。镜像里的 `EXPOSE 5432` 只是元数据，告诉使用者和工具“这个镜像默认监听 5432”，不会在宿主机上开端口；网络内的容器仍然可以通过 `postgres:5432` 连它，因为它们在同一个 bridge 网络里。

`ports` 和 `expose` 的区别在方向：`ports` 把容器端口发布到宿主机，会在宿主机上生成监听和转发规则；`expose` 只在网络内声明端口，供链接的服务发现，不碰宿主机。shorty 只需要把 api 的 8080 发布出来给浏览器和 curl 用，postgres、redis 都不该发布；生产环境更不应该把数据库端口开到公网。只在本机访问可以写成 `127.0.0.1:8080:8080`，避免开发端口被局域网里的其他机器看到。

数据落在命名卷 `pgdata` 上，service 里写成 `pgdata:/var/lib/postgresql`。PostgreSQL 18 的 `PGDATA` 是 `/var/lib/postgresql/18/docker`，所以卷挂在它的上一层 `/var/lib/postgresql`，而不是直接挂 `PGDATA`；这是第 5 章已经确认过的路径。命名卷由 Docker 管理，`down` 保留，`down -v` 删除；绑定挂载写成 `./data:/var/lib/postgresql`，数据落在宿主目录里，权限、属主、备份都由宿主负责。开发时绑定挂载看得见文件，生产上命名卷或云盘更常见。

secret 的处理更能看出 Compose 的模型。文件在 `secrets/db_password.txt`，顶层声明 `db_password` 的来源是 `file`，postgres、migrate、api、worker 各自在 service 的 `secrets` 列表里引用它。Compose 把内容以单个文件挂到容器的 `/run/secrets/db_password`，不是塞进环境变量。

`docker compose config` 的 `secrets` 段只显示对象名 `shorty_db_password` 和宿主文件路径 `/book/src/code/ch14/secrets/db_password.txt`，没有密码内容；紧接着的 `grep` 在完整 config 里找演示密码，结果是“没有明文密码”。这不是说 secret 文件本身加密了，文件仍然是明文；它只是不会被 `config` 展开到模型里。secret 文件不要提交到仓库，本章的密码只用于本地实验。

api 的环境变量里是 `SHORTY_DB_PASSWORD_FILE=/run/secrets/db_password`，不是密码本身；shorty 启动时读这个文件，把密码填进 DSN，日志不会打印它。postgres 用官方镜像的 `POSTGRES_PASSWORD_FILE` 约定，效果相同。容器里的文件权限是 `644 root`，api 以非 root 用户运行，仍然能读；如果改成只允许 root 读，api 就会启动失败。Compose secret 是绑定挂载的单文件，权限由宿主文件决定，需要让目标用户可读。

configs 和 secrets 长得很像，但用途不同：configs 是普通配置，默认只读，容器里通常挂到 `/etc` 一类的位置；secrets 是敏感数据，挂到 `/run/secrets/<name>`。shorty 没有用 configs，因为它的配置都能用环境变量表达；如果以后要把 `nginx.conf`、`prometheus.yml` 这类文件挂进去，用 configs 比在 Dockerfile 里 `COPY` 更灵活，也比绑定挂载更少依赖宿主路径。

网络、端口、卷、secret 这四样都是 project 级别的资源，service 只是引用它们。下一节把 `tools` 这个只在调试时用的 service 放进 profile，再看不改主文件怎么叠加开发配置。

## 14.5 profiles 与多文件


第一条 `ps -a --services` 只有五个 service，`tools` 不在里面。`config --services` 配合 `--profile tools` 能看到六个，说明 profile 里的 service 仍然属于模型，只是默认不启动。`--profile tools up -d` 之后，`ps -a` 里多了 `tools`；`migrate` 还是 `exited`，因为 `-a` 把一次性任务也列出来。

`run --rm tools` 启动一个一次性的 tools 容器，执行 `psql` 查询 `links` 表的行数，输出 `0`，然后删掉容器。`run` 默认会启动 `depends_on` 里的 postgres 和 redis，所以不需要先手动起数据库；`--rm` 只删这次 run 的容器，不删 service 的容器。输出里的 `shorty-tools-run-...` 是这次一次性容器的名字，随机后缀每次不同，正文不引用它。

profile 也可以用环境变量激活：`COMPOSE_PROFILES=tools docker compose up`；多个 profile 写多个 `--profile`，或者用逗号分隔的 `COMPOSE_PROFILES`；`--profile "*"` 启用全部。`profiles` 的名字要匹配 `[a-zA-Z0-9][a-zA-Z0-9_.-]+`，不能有空格。

多文件覆盖是另一套机制。默认情况下 Compose 读 `compose.yaml`，如果同目录有 `compose.override.yaml` 会自动叠加；本章的覆盖文件叫 `compose.dev.yaml`，因为它不是每个命令都想要的默认值，显式写 `-f compose.yaml -f compose.dev.yaml` 才生效。合并规则是：标量覆盖，映射逐键合并，列表追加；相对路径以第一个文件所在目录为基准。

最后一段输出验证了合并：`SHORTY_LOG_LEVEL` 从 `info` 变成 `debug`，`SHORTY_BASE_URL` 被改成 `http://shorty.localhost`，而 `SHORTY_LISTEN` 在覆盖文件里没写，仍然保留基础文件里的 `:8080`。`environment` 是映射，所以是按 key 合并，不是整个替换；如果写成列表，行为会不一样。覆盖文件只写要改的键，不要把整个 service 再抄一遍。

`include` 解决的是另一个问题：把别的团队维护的 Compose 文件当成模块引进来。它和 `-f` 合并不同，`include` 里的每个路径按自己的项目目录加载，加载完把资源复制进当前模型；两个文件里出现同名资源会报冲突。`include` 还可以指向 OCI artifact 或 Git 仓库，适合复用一整套依赖服务。短小的覆盖用 `-f`，跨项目的复用用 `include`，只复用单个 service 的字段用 `extends`。`include` 的一个常见用法是把第三方依赖单独放一份文件，主文件只写自己的 service；`include` 是递归的，被包含的文件还可以继续 include。

profile 和多文件都只改变“这次命令看到哪些 service、哪些字段”，不改变镜像本身。下一节把开发循环再往前推一步：文件改了以后，怎么让容器里的内容跟着变。

## 14.6 watch 与本地开发

`develop.watch` 是 Compose 的开发特性：它监听宿主上的文件，按规则把变化同步进容器，或者重建镜像、重启容器。每条规则有 `path` 和 `action`，`path` 相对于项目目录，目录会递归监听，不支持 glob；`ignore` 相对于这条规则的 `path`，语法和 `.dockerignore` 一样；`.git` 和常见编辑器的临时文件会被自动忽略。

action 有几种：`sync` 把文件复制到 `target`，容器不重启，适合模板、静态资源、解释型语言的源码；`rebuild` 重新构建镜像并替换容器，适合编译型语言、Dockerfile 或依赖清单变化；`restart`（Compose 2.32 起）只重启容器；`sync+restart`（Compose 2.23 起）先同步再重启，适合 `nginx.conf` 这类改完要重新加载的配置。`watch` 只对带 `build` 的 service 生效，纯 `image` 的 service 没有源码可监听。

shorty 的 api 把 HTML 模板编译进了二进制，所以改模板必须 rebuild，不能 sync。为了把两种 action 都看清楚，本节用 `page` 这个演示 service：它基于 `python:3.15.2-slim-trixie`，`http.server` 从 `/srv` 读 `index.html` 和 `VERSION`；`index.html` 配 `sync`，`VERSION` 配 `rebuild`。page 放在 `watch` profile 里，不干扰前面五个服务。

先 `up -d page`，等 8081 能响应，页面标题是 v1，`/VERSION` 也是 `v1`。然后启动 `docker compose watch page`，等日志出现 `Watch enabled`，再改 `index.html`。日志里的 `Syncing service "page" after 1 changes were detected` 说明这是 sync：文件被复制进容器，镜像没有重建，刷新页面标题变成 v2。

第二次 watch 改的是 `VERSION`。日志里出现 `Rebuilding service(s) ["page"]` 和 `Container shorty-page-1 Recreated`，`/VERSION` 变成 `v2`。rebuild 会重新构建镜像，Compose 默认还会清理被替换下来的 dangling 镜像；`docker compose watch --prune=false` 可以保留它们。这里的两段 watch 是脚本用 `setsid` 放到后台、轮询到结果后杀掉的；手动开发时直接在终端里跑 `docker compose watch`，按 Ctrl-C 结束。

watch 与绑定挂载的区别值得说清楚。绑定挂载把宿主目录直接映射进容器，容器看到的就是宿主文件，改完立刻生效，但依赖宿主路径、文件系统权限和 uid 映射；在远程 Docker 或不同平台上，路径和权限问题会变得很麻烦。watch 是把文件复制进容器，或者重建镜像，不要求容器和宿主共享同一个目录；它可以按规则忽略 `node_modules`、构建产物这些不该同步的内容，代价是有一层监听和复制，且需要容器里有 `stat`、`mkdir`、`rmdir` 这些基本工具。

watch 的定位是开发循环，不是生产发布：它监听的是开发机上的源码，生产镜像应该是构建好、打过标签、推送到 registry 的产物。把 `develop.watch` 留在生产用的 Compose 文件里没有意义，反而会让配置更难审计。shorty 的 api 用 rebuild，是因为它的运行时镜像是 distroless，里面没有 shell 和这些文件工具；page 用 python-slim，才有条件做 sync。

## 14.7 Swarm 去哪了

Compose 解决单机多容器，Swarm 解决多机编排。`docker stack deploy` 仍然存在，也仍然接受 Compose 文件，但它接受的是 legacy v3 格式，不是本章前面用的 Compose Specification；官方文档在这一页明确说最新格式和 `docker stack deploy` 不兼容。所以下面的 `compose.swarm.yaml` 从主文件改出来：顶层写 `version: "3.8"`，去掉 `name`、`develop`、`profiles`、`secrets`，保留 `depends_on`，看看 Swarm 怎么处理它。

```console
{{#include code/ch14/14_7_swarm_depends_ignored.out}}
```

`docker swarm init --advertise-addr eth0` 把当前 Docker 切到 swarm mode。lab 里有多个网络接口，不指定 `--advertise-addr` 会报 `could not choose an IP address to advertise`；普通单网卡机器通常不需要这个参数。`docker stack deploy -d --resolve-image never` 把文件提交给 Swarm，`-d` 立刻返回，`--resolve-image never` 表示直接用本机已有的 `shorty:0.1`，不去 registry 查 digest；真实的跨节点 swarm 不能这样，镜像必须先推到所有节点都能访问的 registry。

`postgres` 的 command 还是先 `sleep 12` 再启动数据库，`api` 的 `depends_on` 还是写着 postgres。结果是：两个 task 都进入 `Running`，api 先开始监听，`/readyz` 返回 503，响应体里是连接拒绝；postgres 的日志在十几秒后才出现 `database system is ready to accept connections`。`depends_on` 在这里没有把 api 压后，因为 Swarm 调度的是 task，不是 Compose 的 service 启动序列；`depends_on` 是 Compose CLI 在单机上实现的顺序控制，`stack deploy` 不会把它翻译成调度约束。

这不是说 `depends_on` 在 Swarm 里“报错”，它被接受，只是不保证启动顺序。要让 api 在数据库后面启动，得靠应用自己重试，或者在入口脚本里轮询依赖；Swarm 没有 Compose 的 `condition` 这种启动阻塞。Swarm 有自己的任务状态和重启策略，它不会把 Compose 的 healthcheck 翻译成“等依赖健康再调度”的阻塞条件。

Swarm mode 仍然随 Docker Engine 提供，`docker swarm init`、`docker service`、`docker stack` 都还能用；经典 Swarm（独立镜像那个）官方文档明确说“不再积极开发”，不要和 Engine 内置的 swarm mode 混淆。从 Docker 29 的发布说明看，Swarm 相关的条目以修复为主，覆盖 overlay 网络、routing mesh、DNS 这些老问题，没有新的编排模型或调度能力；把它当成“仍在维护、但不再扩展”的运行时更合适。

新项目的多机编排基本都选 Kubernetes：生态、Operator、GitOps、可观测性都围绕它，Compose 则退回到本地和单机。Docker 文档的定位也是分开的：如果你不打算用 Swarm 做生产运行时，就用 Compose；如果目标是 Kubernetes，文档单独给出了 Docker Desktop 的 Kubernetes 集成入口。选型建议是本书的判断，不是 Docker 的硬性规定。Compose 文件仍然有价值，因为它是描述“一组容器怎么协作”的最短形式，Kubernetes 章节里的很多概念都能和它对应上。

最后 `docker stack rm` 删掉 stack，`docker swarm leave --force` 退出 swarm，`docker info` 显示 `swarm=inactive`。这一步不能省：lab 是共用的，留下 swarm 状态会影响后面的示例。

`up -d` 以非 0 退出，错误里直接点名 `shorty-postgres-1` 和 `unhealthy`。`ps -a` 显示 postgres 是 `running`、`unhealthy`，api、worker、migrate 停在 `created`；这说明 Compose 卡在依赖条件上，容器建好了但没有启动。`logs postgres` 里是 PostgreSQL 的启动日志，健康检查命令自己的输出不在容器的 stdout 里；要看 `docker inspect` 的 `.State.Health.Log`，本例里是 `2 /var/run/postgresql:6543 - no response`，才能区分“数据库没起来”和“检查命令本身写错”。

修复分两步：先 `down -v` 清掉这个不健康的 project，再用正确的 `compose.yaml` 重新 `up`。重跑后 `/readyz` 返回 `ok`，`ps` 里 postgres 和 redis 都是 `healthy`。如果错误是启动慢而不是检查命令错，优先增大 `start_period`，给启动阶段更多时间；如果是数据目录权限问题，检查命名卷的属主和 `PGDATA` 路径；如果依赖写成了短格式，改成 `condition: service_healthy`。

第二个故障是 `port is already allocated`。脚本先停掉 Compose 栈，用 nginx 容器占住宿主 8080，`ss -ltn` 能看到监听；再 `docker compose up -d`，api 的端口发布失败，错误里是 `Bind for :::8080 failed: port is already allocated`。

排法很直接：`ss -ltnp 'sport = :8080'` 或 `docker ps --filter publish=8080` 找到占用者；如果是旧容器，停掉或删掉；如果是必须保留的服务，改 `ports` 的宿主端口，或者用 `${SHORTY_API_PORT:-8080}` 换一个端口。不要改容器端口 8080，api 监听的就是 8080；要改的是冒号左边的宿主端口。脚本删掉占用容器、`down` 掉失败留下的容器再 `up`，`/readyz` 恢复；最后的 `ps` 不带 `-a`，只显示运行中的 api/worker 和健康的 postgres/redis，migrate 已经退出。

这两个故障都说明一件事：Compose 的错误信息已经把对象名和原因写出来了，先读错误，再 `ps`、`logs`、`ss`，不要一上来就 `down -v`。`down -v` 会删卷，数据库数据一起没；只有确认数据可以丢，或者本来就是演示环境，才加 `-v`。

## 上生产前

Compose 的定位是本地和单机。它能在同一台机器上把五个服务编排好，但没有多节点调度、跨节点网络、滚动更新和故障转移；这些是 Kubernetes 的职责，从第 16 章开始。不要把 `docker compose up` 当成生产部署命令，也不要把 Swarm 当成默认的下一步：Docker 文档建议不打算用 Swarm 做生产运行时就用 Compose；本书的建议是，新项目的多机编排直接选 Kubernetes。

启动顺序用 healthcheck 加 `condition`，不要用 `sleep`。`sleep 30` 在开发机上可能够，在慢盘、冷启动、镜像首次拉取的机器上就不够；反过来，它会让每次启动都白等。shorty 的 api 即使依赖都健康，也会在运行期遇到数据库重启和网络抖动，所以应用自己要有重试和退避。Compose 只把“第一次启动”的顺序排好，运行期的恢复要靠应用和运行时。

secret 用 Compose 的 `secrets` 或文件挂载，不要写进普通环境变量，也不要把 `compose.yaml` 里的密码提交到仓库。环境变量会出现在 `docker inspect`、进程环境和部分日志里；secret 至少是一个权限可控的文件。生产上更常见的是外部 secret 管理器或编排器的 Secret 对象，Compose 的文件 secret 只是本地等价物。

镜像要固定 digest。`shorty:0.1` 这个标签可以被重新推送成完全不同的内容，`shorty@sha256:...` 才是不可变的。`build` 只用于开发：生产镜像应该在 CI 里构建一次、扫描、签名、推送到 registry，部署时按 digest 拉取；本章的 `build` 是为了让读者看到 context、target 和 image 的关系，不是生产模板。

卷的生命周期要单独管理。`docker compose down` 默认保留命名卷，`down -v` 删除；生产上数据库卷应该有备份、容量监控和权限检查，不能依赖“容器删了数据还在”这种偶然。把数据库和缓存放在同一个 Compose 项目里很方便，但也意味着它们的资源边界、升级节奏和故障域绑在一起，规模变大后要拆开。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `docker compose config` | 展开变量、合并文件/profile，打印最终模型 | `-q` 只校验；`--services`/`--volumes` 只列名字 |
| `docker compose up -d --build` | 构建并启动项目 | `-d` 后台；`--quiet-build` 隐藏构建日志 |
| `docker compose down` | 停止并删除容器、网络 | 默认保留命名卷；`-v` 连卷一起删 |
| `docker compose ps -a` | 看 service 状态、健康和退出码 | 不加 `-a` 看不到已退出的一次性任务 |
| `docker compose logs <service>` | 看某个 service 的日志 | `-f` 跟随；`--tail` 限行数 |
| `docker compose build` | 只构建不启动 | `--no-cache` 强制重建；`--pull` 拉基础镜像 |
| `docker compose run --rm <service> <cmd>` | 一次性运行 service | 默认启动 `depends_on`；`--rm` 跑完删容器 |
| `depends_on.<svc>.condition` | 启动条件 | `service_started`（短格式默认）、`service_healthy`、`service_completed_successfully` |
| `healthcheck.test` | 健康检查命令 | `CMD` 直接执行；`CMD-SHELL` 经 `/bin/sh -c`；字符串等价于 `CMD-SHELL` |
| `healthcheck.interval/timeout/retries/start_period` | 检查节奏和失败阈值 | 按服务调；`start_period` 给启动留缓冲 |
| `profiles` | 给 service 分组，默认不启用 | `--profile tools` 或 `COMPOSE_PROFILES=tools` |
| `develop.watch[].action` | 文件变化后的动作 | `sync`、`rebuild`、`restart`、`sync+restart`；只对带 `build` 的 service 生效 |
| `secrets` | 把文件挂到 `/run/secrets/<name>` | 顶层声明来源，service 里引用；不要提交密码文件 |
| `ports` / `expose` | 发布到宿主 / 只在网络内声明 | `ports` 写 `宿主:容器`；`expose` 不碰宿主 |

本章结束时，Compose 项目 `shorty` 的五个 service 达到预期状态：`postgres`、`redis` 健康，`migrate` 退出 0，`api`、`worker` 运行；命名卷是 `shorty_pgdata`；`tools` profile 没有启动。下一章在这个栈上做开发与 CI：用 watch 和 Testcontainers 把本地循环跑顺，再把“构建一次、按 digest 晋升”的流水线搭起来。
