# 第 34 章 打包与交付：Kustomize、Helm、GitOps、渐进式发布

s4-prod 的清单已经是五个 YAML 文件，api、worker、postgres、redis、Gateway、NetworkPolicy 都在里面。每次改一个环境，做法还是复制目录、改副本数、改域名，再手工 `kubectl apply -f`。三套环境看起来只差几个字段，实际上 probe 的超时、资源限额、镜像 tag 都在慢慢分叉。更麻烦的是反向的问题：有人在 Git 里把镜像从 0.1 改成 0.2，集群里却还是 0.1，因为那次提交之后没有人记得 apply。

这两个问题指向同一件事：清单没有单一的来源，集群也没有持续对账。Kustomize 把公共对象和环境差异拆开，Helm 把一组对象打成一个有版本、可回滚的 release，Argo CD 把 Git 当成期望状态反复比对。三者解决的不是同一个层次的问题：Kustomize 负责组合和 patch，Helm 负责模板和发布记录，Argo CD 负责把 Git 的变化同步到集群。把它们混成“都是包管理”会错过各自的边界。

本章的示例都从 s4-prod 开始。`setup.sh` 会建好集群、装好 s4-prod 的前置组件，并在 lab 里起一个 `localhost:5000` 的 registry，后面推 OCI chart 和按 digest 提升时要用。Argo CD 和 Gitea 不放在 setup 里，读者会在 34.3 看到它们是怎么装进去的。

交付链路可以拆成四层来看：制品是镜像和 chart，清单是 Kustomize 或 Helm 渲染出的对象，同步器是 Argo CD，流量切换是 Gateway 或 Service。层与层之间的契约越清楚，出问题时越容易定位：镜像 digest 不对，查构建和 registry；清单不对，查 Kustomize 或 values；集群和 Git 不一致，查 Application；只有一部分请求出错，查路由权重和 canary。下面每一节只改一层，尽量不让问题跨层传播。

> **起点**：shorty 处于 s4-prod 状态，清单是 `src/code/stages/s4-prod/` 下手工 apply 的五个文件；lab 里另有一个本地 registry。一步到位：`bash code/ch34/setup.sh`。

## 34.1 Kustomize：base + overlay + patch

三套环境复制粘贴的第一个代价是“公共部分”没有地方放。改一个 probe 的超时，要改三份文件；第二个代价是差异被埋在大段 YAML 里，review 时看不出 dev 和 prod 到底差在哪。Kustomize 的做法是反过来：base 放所有环境共用的对象，overlay 只放这个环境相对 base 的差异，最后把两者组合成完整的清单。

一个目录里有 `kustomization.yaml` 就是一个 Kustomize 项目。base 用 `resources` 列出要包含的 YAML；overlay 用 `resources` 指向 base，再用 `replicas`、`images`、`patches`、`configMapGenerator` 这些字段做环境定制。`namePrefix` 和 `nameSuffix` 给所有对象加统一前缀或后缀，`labels` 和 `commonLabels` 给对象加标签。`kubectl kustomize <目录>` 只把组合结果打印出来，不连接集群；`kubectl apply -k <目录>` 才会写集群。这个分工让“先看渲染结果，再决定应不应该 apply”成为默认动作。

本章的 base 里放了 api 的 Deployment 和 Service，加一个 `configMapGenerator` 生成运行时配置。Deployment 刻意保留了 s4-prod 里的 ServiceAccount、securityContext、探针、资源限额和 `shorty-config` 的 `envFrom`，这样 overlay 渲染出来的对象和集群里的真实对象不会差出一大截。`configMapGenerator` 的内容是 `SHORTY_LOG_LEVEL` 和 `SHORTY_BASE_URL`，Kustomize 会在名字后面加内容 hash，并把 Deployment 里对它的引用一起改掉。

base 不是越小越好。有人把 base 写成“最小可运行”的三行 Deployment，把 probe、securityContext、resources 全放进 overlay，结果每个环境都要重复一遍生产配置，改一处仍然要改三份。判断标准是“这个字段是不是所有环境都一样”：一样就进 base，不一样才进 overlay。本章的资源限额在 dev 和 prod 不同，所以放 patch；ServiceAccount、探针、securityContext 三套环境相同，留在 base。

dev 和 prod 的 overlay 只做三件事：`replicas` 改副本数，`configMapGenerator` 用 `behavior: merge` 覆盖 `SHORTY_BASE_URL`，`patches` 用带 `target` 的 strategic merge patch 改资源 requests/limits。target 写了 `group`、`version`、`kind`、`name`，没有写 `namespace`；base 里的对象没有 namespace，overlay 的 `namespace` 是在 patch 之后才加上的，target 要和 patch 匹配时的对象一致，这一点在 34.7 会看到一个写错 target 的例子。

`patches` 支持 strategic merge 和 JSON6902 两种写法。strategic merge 像一个小 YAML，只写要改的字段，列表按 `name` 合并；JSON6902 是一串 `op`/`path`/`value`，适合改 strategic merge 表达不了的字段。strategic merge 对内置类型有合并语义，对 CRD 不一定知道列表怎么合并；改 CRD 或任意字段时，JSON6902 更可控，但它必须写 `target`，路径写错时渲染会直接失败或匹配不到对象，不会自动回退到别的字段。

`diff` 的两边是把生成名归一化之后的 dev 和 prod。差异只有三处：`SHORTY_BASE_URL` 从 `http://dev.shorty.example` 变成 `https://shorty.example`，`replicas` 从 1 变成 2，资源从 250m/128Mi 变成 500m/256Mi。这正是“环境之间只应该差副本数、域名和资源”的可检查形式；如果 diff 里出现一整套探针或 securityContext，说明有人把公共对象复制进了 overlay。

最后的 `kubectl apply -k ... --dry-run=server` 走了一遍 apiserver 的校验：ConfigMap 是 `created`，Service 和 Deployment 是 `configured`，但没有落盘。这里用 `--dry-run=server` 而不是直接 apply，是因为当前集群里的 api 已经由 s4-prod 管理，直接 apply 会把它改成 Kustomize 的版本；本章后面会让 Argo CD 接管，接管前先只做校验。

`commonLabels` 的坑值得单独说。它会把标签同时写进 `metadata.labels`、Pod 模板标签和 selector。对一个已经存在的 Deployment，selector 是不可变的，改了就会被 apiserver 拒绝。示例最后渲染了一个只加 `commonLabels` 的 Deployment，selector 里出现了 `app.kubernetes.io/managed-by: kustomize`；拿它去 `apply --dry-run=server`，输出是 `field is immutable`。本章的 base 因此改用 `labels` 加 `includeSelectors: false`，只给对象加标签，不动 selector；Pod 模板里的 `app.kubernetes.io/part-of: shorty` 是 base 显式写的，因为 NetworkPolicy 要靠它选 Pod。

`namePrefix` 和 `nameSuffix` 适合让 dev 和 prod 在同一个 namespace 里并存，例如 dev 用 `namePrefix: dev-` 生成 `dev-api`。Kustomize 会把这个前缀应用到所有对象名，也会改写 Service、`envFrom`、`volume` 这些按名字引用对象的地方；如果手写引用漏了，渲染结果会指向不存在的名字。本章的 dev overlay 只渲染不 apply，所以没有加前缀，diff 才能聚焦在副本数、域名和资源上。`images` 在 overlay 里改镜像的 name、tag 或 digest；34.6 会用 `digest` 把同一个 artifact 从 dev 提升到 prod。

`secretGenerator` 和 `configMapGenerator` 一样，可以从文件或 literals 生成对象，默认也带内容 hash。区别是 Secret 的 values 会做 base64，渲染结果里仍然是可逆的编码，不要把“base64 过”当成加密；真正的敏感值要么来自集群外的 secret manager，要么在 apply 前才注入。Kustomize 的 generator 适合生成“配置内容变了要触发滚动更新”的对象，不适合当密钥管理方案。

## 34.2 Helm：模板、values 与 release

Kustomize 的组合对象是“已经写好的 YAML”，Helm 的组合对象是“带参数的模板”。一个 chart 至少包含 `Chart.yaml`、`values.yaml` 和 `templates/`。`Chart.yaml` 写 chart 的名字、版本和 `appVersion`；`values.yaml` 给模板提供默认值；`templates/` 里的文件用 Go template 语法生成 Kubernetes 清单，公共片段放在 `_helpers.tpl`，`NOTES.txt` 是安装成功后打印的提示。本章的 chart 把 api 的 Deployment、Service 和 values 里的副本数、镜像、base URL、资源限额参数化，release 名和对象名用 `shorty.fullname` 统一。

`_helpers.tpl` 里的 `define` 不会直接生成对象，它定义的是可复用的模板片段；Deployment 和 Service 用 `include` 把 `shorty.fullname`、`shorty.labels` 展开，再用 `nindent` 控制缩进。这样 release 名、chart 名和标签只在 helper 里写一次，改的时候不会出现 Deployment 和 Service 各写一套、标签对不上的情况。`NOTES.txt` 不是 Kubernetes 对象，它只在 `helm install`/`upgrade` 成功后打印，适合放端口转发和排障命令。

`values.yaml` 是默认值，不是环境配置的垃圾桶。把 dev、staging、prod 的域名和副本数都塞进一个 values 文件，再用条件判断选环境，最后会得到和复制 YAML 一样难读的结果。更好的做法是每个环境一个 values 文件，只写和默认值不同的键，用 `-f` 叠加；默认 values 只放能安全用于本地 lab 的值。`helm template` 可以在不碰集群的情况下把每个环境的 values 渲染出来做 diff，这就是 34.1 里 Kustomize overlay diff 的 Helm 版本。

Helm 的 `template` 子命令只在本地渲染，不连接集群；官方文档明确说，需要从集群里查的值会被本地假造，服务端的校验也不会做。示例先用 `helm lint` 检查 chart，再用 `helm template shorty ./chart --set replicaCount=3` 看 values 有没有生效：输出是 `replicas=3`，镜像是 `localhost:5000/shorty:0.1`。`--set` 适合一两个临时值，环境差异多的时候应该写 values 文件，用 `-f` 传入，避免把一长串 `--set` 塞进命令行。

`helm upgrade --install` 把“第一次安装”和“以后升级”合成一条命令：release 不存在就安装，存在就升级。CI 里常用它来保证幂等，但要注意它不会自动回滚；升级失败时加 `--rollback-on-failure` 可以让 Helm 在失败后回退到上一个成功的 revision，代价是失败路径也要等 `--wait` 超时。`helm install shorty ./chart -n shorty-helm --create-namespace --wait` 输出 `STATUS: deployed`，`REVISION: 1`。`--wait` 会等到 Deployment 的 Pod 可用再返回，所以紧接着 `kubectl get deploy,svc,pods` 看到的是 `2/2`，不需要再等。Helm 把 release 记录存在 Kubernetes Secret 里，名字是 `sh.helm.release.v1.shorty.v1`，类型是 `helm.sh/release.v1`；Helm 自己没有数据库，集群就是它的存储。`helm history` 的 `REVISION` 列就是这些 Secret 的版本。

`helm template` 和集群对象做 diff 时，模板里把副本数改成 3，diff 里能看到 `replicas: 2` 变成 `replicas: 3`。同一份 diff 还会看到 `generation: 1` 变成 `2`，这是 apiserver 在 spec 变化时自己维护的字段，不是 chart 写出来的，apply 时不需要管它。`helm upgrade --set replicaCount=3` 之后 Deployment 变成 3 副本，`helm history` 多出 revision 2；`helm rollback shorty 1` 把副本数退回 2，但历史里不是删掉 revision 2，而是新增 revision 3，描述是 `Rollback to 1`。回滚本身也是一次发布，这一点在审计时很重要。

chart 也能作为 OCI artifact 推到 registry。示例用 `helm package` 打出 `shorty-0.1.0.tgz`，再 `helm push ... oci://localhost:5000/charts --plain-http`；输出里有 `Pushed` 和 chart 的 digest，`helm show chart` 能从 registry 把元数据拉回来。生产里通常会再加签名和扫描，34.5 会讲制品门禁；这里先确认 chart 的版本和镜像的版本是两件事：chart 的 `version: 0.1.0` 是打包版本，`appVersion: "0.1"` 是应用版本，镜像 tag 又是第三个东西。

Helm 是 Kubernetes 生态里的工具，不是 Kubernetes 内置的包管理器。Kubernetes 官方文档讲声明式对象管理时会提 Kustomize，但没有 Helm 章节；Helm 的安装、chart 仓库、release 存储都在它自己的文档里。把 Helm 当成 `kubectl` 的一部分，会在版本升级、RBAC 和 release 存储位置上判断错。`helm uninstall` 会删除 release 记录和它管理的对象，本章没有执行，因为后面还要用这个 release 做对照。

> **旧资料提示**：旧教程常说“Helm 是 Kubernetes 的包管理器”，暗示它是集群内置能力。Helm 是集群外的客户端加库，release 信息存在集群的 Secret 里；Kubernetes 官方文档没有 Helm 章节，Kustomize 才是 kubectl 直接支持的那一个。

## 34.3 GitOps：Argo CD

Kustomize 和 Helm 解决的是“怎么生成清单”，GitOps 解决的是“谁把清单送到集群，以及怎么证明集群和清单一致”。Git 里放期望状态，Argo CD 的 Application 指向仓库、路径和 revision，controller 周期性把 live state 和 target state 做比较。比较结果写在 Application 的 `status.sync.status` 里：一致是 `Synced`，不一致是 `OutOfSync`，生成清单失败是 `ComparisonError`；工作负载是否正常则看 `status.health.status`，例如 `Healthy`、`Progressing`、`Degraded`。`Synced` 只说明清单已经提交，不代表 Pod 已经可用；`Healthy` 只说明 Argo CD 认得的工作负载健康，不代表业务指标正常。发布门禁要把这两个状态和真正的探针、指标分开看。

一个最小的 Application 只需要四样东西：`source.repoURL`、`source.targetRevision`、`source.path` 和 `destination`。本章的 Application 指向 Gitea 里的 `shorty-deploy` 仓库，路径是 `overlays/prod`，revision 是 `main`，目标是集群内的 `shorty` namespace。`syncPolicy.automated` 打开自动同步；`prune` 决定 Git 里删掉的对象要不要在集群里删，`selfHeal` 决定集群里被手工改动的对象要不要拉回 Git。两个默认值都是 false，这是有意的安全设计：自动删除和自动覆盖都可能把别人的改动抹掉。

`AppProject` 是 Application 的权限边界。它限制 `sourceRepos`（能从哪些仓库拉）、`destinations`（能往哪些集群和 namespace 写）以及 `clusterResourceWhitelist`（能不能建集群级对象）。本章的 default project 为了 demo 放开了 `*`，生产里应该按团队和环境拆 project，把 prod 的 project 限制到 prod 仓库和 prod namespace。私有仓库的凭据放在 `argocd` namespace 的 Secret 里，由 repo-server 使用；不要把 SSH key 写进 Application 的 YAML。

`targetRevision` 不一定是分支名，也可以是 tag 或 commit SHA。分支适合 dev，tag 或 commit 适合 prod；commit SHA 最严格，但每次提升都要改 Application 或 Git 里的引用。`syncPolicy.automated.enabled: false` 可以临时暂停自动同步，同时保留 `prune`/`selfHeal` 的配置；这比把整个 `automated` 删掉再恢复更不容易漏字段。

## 34.4 渐进式发布：金丝雀/蓝绿

Deployment 的 RollingUpdate 是副本级的：它逐个替换 Pod，`maxUnavailable` 和 `maxSurge` 控制的是可用副本数，不是流量比例。两个副本、`maxSurge: 1` 的滚动更新，最多会有三个 Pod 同时存在，但新版本一上来就可能接住一半流量；它不能保证“只让 10% 的用户看到新版本”。要做按比例的灰度，需要两个 Deployment（stable 和 canary）加一个能按权重转发的入口；Service 本身只做四层负载均衡，权重控制要交给 HTTPRoute 这类七层路由。

本章用 Gateway API 的 `HTTPRoute` 做 90/10。stable 的 `api` Service 和 canary 的 `api-canary` Service 各有自己的 selector；HTTPRoute 的 `backendRefs` 里给两个 Service 分别写 `weight: 90` 和 `weight: 10`。Gateway 控制器把权重翻译成自己的上游配置，请求按权重分配，不需要为了 10% 的流量去凑副本数。两个 Deployment 用同一个镜像，canary 通过 `SHORTY_BASE_URL=http://canary.shorty` 让响应里的 `short_url` 带上可区分的域名；stable 的 base URL 来自 Git 里的 `https://shorty.example`，统计响应就能知道请求落在哪一边。

示例先创建 `api-canary` 和它的 Service，再把 HTTPRoute 改成 `api=90 api-canary=10`。通过 Gateway 的 Service `shorty-gw-nginx` 做 port-forward，连续发 200 个创建短链的请求；脚本把响应里含 `canary.shorty` 的算 canary，其余算 stable，并检查 canary 是否落在 5 到 50 之间。本次运行的计数会在输出里，比例接近 9:1；这个范围留得比较宽，是因为七层代理的分配不保证每一百个请求都精确是九比一。

然后给 canary 打开故障开关：`/admin/fault?error_rate=1` 让它的所有请求返回 500。这个开关也会影响 `/healthz` 和 `/readyz`，所以 canary 的 readiness 很快会失败并被摘掉；示例只发 100 个请求，在这个时间窗内统计 5xx，输出里能看到大约十个 5xx。真实环境里应该把业务错误率和健康探针分开，或者用独立的分析指标，不能靠一个会把 Pod 弄 unready 的开关做长时间灰度。

发现问题后把 HTTPRoute 的权重改成 `api=100 api-canary=0`。Gateway 控制器重载配置没有可以直接 `kubectl wait` 的条件，示例用连续 5 个 2xx 来判断新配置已经生效，然后再发 100 个请求：`5xx=0`、`canary_hits=0`。这说明流量已经全部回到 stable，而不是“canary 刚好自己恢复了”。演练结束后示例会删掉带故障的 canary Pod，等新 Pod 恢复健康，再把权重调回 90/10，给下一章留一个可继续观察的起点；最后 `kill` 掉 port-forward，不在 lab 里留下后台进程。

蓝绿是另一种切法：stable 和 green 各有一套完整的 Deployment 和 Service，切换时改 Service 的 selector，或者改 HTTPRoute 的 backendRef，让全部流量一次性切过去。蓝绿的回滚同样是切回旧 Service，代价是两套环境要同时跑；金丝雀的代价是要有按比例的路由和足够的观测。两者都不需要改镜像，前提是镜像已经按 digest 固定，这一点在 34.5 和 34.6 继续。

权重决定同一条规则里各 backend 分到的比例；90/10 的目标是约九成请求走 stable、一成走 canary。把 canary 的权重设成 0，表示这个 backend 不参与分流，但对象和 Service 仍然保留，便于随时把权重调回去。调权重之前要先确认两个 Service 的 EndpointSlice 都有地址，否则 10% 的权重会落到一个没有后端的 Service 上，表现为间歇性 503，而不是“金丝雀版本有问题”。

Argo Rollouts 和 Flagger 把“调权重、看指标、自动回滚”做成控制器：它们可以按步骤把权重从 10% 提到 30%、50%，每一步查 Prometheus 的成功率或延迟，不达标就自动退回。自动判断的前提是可信的指标，指标来自第 35 章的 Prometheus 和 kube-state-metrics；没有指标时，这些控制器只能按固定的时间和权重走，和手工脚本差别不大。

指标分析还要先定“什么叫坏”。只看 5xx 会漏掉延迟升高和超时；只看平均值会被长尾掩盖。比较实用的一组是 canary 的错误率、P95/P99 延迟和请求量，和 stable 的同一组指标做对比，再设一个最小请求数，避免流量太少时统计噪声触发误判。这些阈值应该写在 Rollout 的 AnalysisTemplate 或 Flagger 的 metric 里，和代码一起 review，而不是发布时凭感觉调。

## 34.5 发布门禁与制品

发布时写 `image: shorty:0.1` 的问题是 tag 会动。今天 `0.1` 指向这个 digest，明天有人重新 push 同一个 tag，集群再拉一次就换成了另一个文件系统。生产清单应该写 digest：`localhost:5000/shorty@sha256:...`。digest 是内容寻址的，tag 可以变，digest 不会；34.6 的提升也会用同一个 digest 从 dev 移到 prod，而不是在每个环境重新构建。

`imagePullPolicy` 也要跟着改。用 tag 时 `IfNotPresent` 可能让节点一直用本地旧镜像；用 digest 时拉取的内容是固定的，`IfNotPresent` 只是省一次网络请求。真正要保证“部署的就是签过名的那个”靠的是清单里的 digest 和准入校验，不是拉取策略。节点上的镜像缓存、registry 的 tag 覆盖、CI 里的重新构建，都可以让 tag 指向别的内容，digest 不会。

示例先关掉 Argo CD 的自动同步，避免 selfHeal 把手工改动立刻拉回去；然后把 api 的镜像换成一个不存在的 digest，并在 Deployment 上写 `kubernetes.io/change-cause`。`kubectl set image` 之后，新的 ReplicaSet 会试着拉这个 digest，Pod 停在 `ErrImagePull`；因为 base 里设了 `maxUnavailable: 0`、`maxSurge: 1`，旧的两个 Pod 不会被杀掉，rollout 一直等不到新 Pod 可用，`kubectl rollout status` 在 30 秒后以非 0 退出。


`rollout history` 里能看到 `bad digest sha256:000...` 这条 change-cause。`kubectl rollout undo` 把 Deployment 退回上一个 revision，`rollout status` 等到旧的两个 Pod 继续可用；输出里的 `rollback_seconds` 是 0 到 1 秒（同一秒内完成时打印 `<1`，否则打印秒数）：坏 digest 的 Pod 从未 Ready，旧 Pod 一直在服务，undo 只是把新 ReplicaSet 缩掉，所以从 undo 到恢复只有一两秒。这个数字说明的是“没有停机”，不是“回滚一定这么快”；如果坏版本已经接了一部分流量，恢复时间还要加上摘流量和重建连接的时间。

PDB 的 `minAvailable` 可以是整数或百分比，`maxUnavailable` 和它只能选一个；用百分比时要按副本数换算，边界在副本数很小时容易和直觉不一致。它约束的是 eviction API，也就是 `kubectl drain`、节点升级这类自愿驱逐；直接删 Pod、节点宕机、容器 OOM 不经过 eviction，PDB 拦不住。把 PDB 当成“发布不会中断”的保证，会漏掉 readiness 和滚动更新参数这两个更直接的门禁。

`maxUnavailable: 0` 和 readiness 探针是这里的两个门禁。`maxUnavailable: 0` 保证滚动更新先加新 Pod、后删旧 Pod；readiness 保证新 Pod 真的能服务之后才被算进可用副本。PDB 是另一层：s4-prod 里的 `PodDisruptionBudget api` 用 `minAvailable: 1` 限制自愿驱逐（drain、升级节点），它不覆盖节点宕机、OOM 这类非自愿中断，也不替代 readiness。发布时如果 PDB 的 `minAvailable` 等于副本数，drain 会被卡住，这是配置问题，不是 PDB 失效。

`kubectl diff` 和 `kubectl apply --dry-run=server` 是发布前的静态门禁。`kubectl diff` 用 server-side dry-run 算出 apply 会改什么，需要 `PATCH`、`CREATE`、`UPDATE` 权限；`--dry-run=server` 让 apiserver 做准入和 schema 校验，但不写 etcd。34.1 已经用 `apply -k --dry-run=server` 验证过 Kustomize 的输出；在 CI 里，这两个命令比“先 apply 到 staging 看看”便宜得多。

制品门禁还包括 SBOM、provenance 和签名。第 13 章用 cosign 和 policy-controller 演示过：镜像推 registry 时生成 SBOM 和 provenance，签名之后在准入层校验，未签名的镜像被拒。交付流水线要保证“部署的 digest 就是签过名、扫过的那个 digest”，而不是重新 tag 一次再部署；签名和扫描的对象是 digest，tag 只是人看的别名。

`--record` 已经不在 kubectl 1.37 里了，`kubectl set image --help` 和 `kubectl annotate --help` 都找不到这个参数。change-cause 现在要显式写 annotation，或者由 GitOps 工具在提交信息里带出来。`kubectl rolling-update` 这个旧子命令也不在当前 kubectl 里；滚动更新由 Deployment 控制器完成，不需要客户端一直连着。

> **旧资料提示**：旧教程用 `kubectl rolling-update` 或 `--record` 做发布和记录变更。`kubectl rolling-update` 早已移除，`--record` 在 kubectl 1.37 里也没有了；用 Deployment 的滚动更新加 `kubernetes.io/change-cause` annotation，或者让 Argo CD 从 Git 提交里取变更说明。

在 GitOps 里，手工 `kubectl rollout undo` 只是应急手段。Argo CD 的自动同步开着时，下一轮对账会按 Git 把 Deployment 改回去；正确的回滚是 `git revert` 那个提交，让 Git 和集群一起回到旧 digest。Argo CD 的 `argocd app rollback` 在 automated sync 打开时不能做，官方文档明确要求先关自动同步；生产里更常见的是 revert commit，而不是在集群里点回滚。

## 34.6 多环境与配置提升

多环境最容易犯的错是“每个环境重新构建一次”。dev 构建一个镜像，staging 用同一份代码再构建一个，prod 又构建一个；三个镜像的 digest 不同，测试过的内容不等于上线的那个。正确做法是只构建一次，得到 digest，然后把这个 digest 从 dev 提升到 staging、prod。环境之间只改配置：副本数、资源、域名、开关；这些差异放在 overlay 或 values 里，不放进镜像。

示例先构建并推送 0.2，只构建这一次。然后从 `RepoDigests` 里取出 digest，写进 dev overlay 的 `images`，提交；再把 dev 里刚写入的同一行 digest 写进 prod overlay，提交。两次提交之后 `git log` 能看到 dev 和 prod 各一条；`kubectl kustomize` 渲染 prod，镜像已经是 `localhost:5000/shorty@sha256:...`。push 到 Gitea 后，Argo CD 在下一轮对账里把 Deployment 的 image 改成这个 digest，`kubectl get deployment -o jsonpath` 读到的就是 spec 里的 digest。

```console

```

输出里的 digest 每次构建都不同，正文不引用具体值；关键是三处一致：`docker image inspect` 取出的 digest、dev overlay 里的 digest、prod Deployment 的 spec 里的 digest。`kubectl wait --for=jsonpath=...` 等到 Deployment 的镜像真的变成这个 digest，再 `rollout status`；只等 Application 的 `Synced` 不够，因为 Application 可能在 Git 拉取之前就已经是 Synced。

环境隔离用 namespace 或集群，不要靠“在同一个 namespace 里加前缀”当唯一边界。本章的 GitOps overlay 指向 `shorty` namespace，dev overlay 只用于渲染对比；真实的多环境会给 dev、staging、prod 各自一个 namespace 或集群，Argo CD 用不同的 destination。`targetRevision` 可以是分支、tag 或 commit：dev 跟 `main`，prod 跟一个 tag 或固定 commit，这样 prod 不会因为别人往 `main` 推了一个提交就自动变化。

提升的顺序应该是 dev 验证、staging 验证、prod 上线，每一步用同一个 digest。staging 的副本数、域名和资源可以比 dev 更接近 prod，但镜像不能重新构建；如果 staging 用的是另一个 digest，前面所有测试都没有覆盖到 prod 真正要跑的那个文件系统。提升脚本要检查“目标环境渲染出的 digest 等于源环境渲染出的 digest”，不相等就停止。

Git 分支策略没有唯一答案，但要和 Argo CD 的 revision 对上。用分支 Promotion 时，合并到 `prod` 分支触发 prod 同步；用 tag 时，Argo CD 的 `targetRevision` 指向 tag，提升就是打一个新 tag；用目录 Promotion 时，同一个分支里 dev/prod 两个 overlay，提升就是改 prod overlay 的 digest。三种方式都能做到“同一 artifact”，关键是不要让流水线在提升时重新构建。

配置提升还要注意“配置也是代码”。数据库密码、TLS 证书、外部服务的地址不应该跟在镜像 digest 后面一起提升；它们由 Secret、ConfigMap 或外部的 secret manager 管理，overlay 只引用名字。本章的 `shorty-config` 和 `shorty-db` 还是 s4-prod 里那份，Kustomize 的 `envFrom` 只是引用它；生产里应该把 Secret 的创建和轮换放到 Git 之外的流程，Git 里只放引用和校验用的 hash。

## 34.7 排障：ComparisonError、OutOfSync、Helm 归属与 patch 目标

`ComparisonError` 和 `OutOfSync` 是两类不同的失败。`ComparisonError` 发生在“生成 target state”阶段：repo 拉不下来、路径不存在、Kustomize/Helm 渲染报错，Application 根本没有得到一份可比较的清单；`OutOfSync` 是清单生成成功了，但 live state 和它不一致。前者查 repo-server 和仓库，后者查集群里的对象和 sync 操作；把两者混在一起，会在错误的组件里翻日志。

Argo CD 报 `ComparisonError` 时，先看 Application 的 condition message，再看 repo-server 日志。示例把 `path` 写成 `overlays/missing`，Application 的 condition 是 `Failed to load target state: ... overlays/missing: app path does not exist`；repo-server 的日志里有同一条 `app path does not exist`。这类错误通常是 repo URL、路径、分支三者之一写错，或者仓库是私有的但 Argo CD 没有凭据。先确认 repo-server 能 clone，再确认路径在那个 revision 里存在；不要从 controller 的日志开始猜。


`OutOfSync` 但 sync 失败，常见原因是 CRD 还没 Established、RBAC 不允许 apply、namespace 不存在，或者对象被别的 controller 改成了不可变字段。先看 sync 操作的 message 和 `kubectl apply` 的原始错误；CRD 用 `kubectl get crd <name> -o jsonpath='{.status.conditions}'` 看 `Established`，RBAC 用 `kubectl auth can-i` 验证，不要直接给 Argo CD 的 ServiceAccount 加 `cluster-admin` 了事。

Helm 的 `rendered manifests contain a resource that already exists` 是另一个常见报错。它的意思是 chart 渲染出的对象在集群里已经存在，但没有这个 release 的归属信息（`meta.helm.sh/release-name`、`meta.helm.sh/release-namespace` 和 `app.kubernetes.io/managed-by: Helm`）。示例用 release 名 `api` 装到 `shorty` namespace，撞上 Argo CD 管理的 `api` Service；Helm 4.3.1 的实际报错是 `unable to continue with install: Service "api" in namespace "shorty" exists and cannot be imported into the current release`，后面列出缺失的 label/annotation。旧版 Helm 的措辞是 `rendered manifests contain a resource that already exists`，意思一样。处理方式只有两个：改名/改 namespace 让对象不冲突，或者确认归属后用 `--take-ownership` 接管；后者会把对象从原来的管理者手里拿走，生产里要非常谨慎。排障时先看 Helm 报的是哪个对象、缺哪个 label/annotation，再去确认这个对象本来由谁管理；不要为了让 install 通过就批量加 `--take-ownership`，那会把两个发布系统的所有权混在一起。

Kustomize 的 patch 不生效，先查 `patches[].target` 的 `group`、`version`、`kind`、`name`、`namespace`。示例的 `badpatch` 把 target 的 `name` 写成 `api-typo`，匹配不到 base 里的 `api`，渲染结果还是 1 个副本；`goodpatch` 写回 `api`，渲染结果是 5。`namespace` 同理：target 匹配的是 patch 应用时的对象，不是最终 apply 时的对象；base 里没写 namespace，target 就不要写 namespace。

## 上生产前

Git 是唯一的事实源，生产集群不接受手工 `kubectl apply`。这不是说永远不能用 `kubectl` 排查，而是说任何会改变 spec 的操作都要能回到 Git。Argo CD 的 `prune` 和 `selfHeal` 要分开开：selfHeal 适合防止手工改动，prune 会在 Git 里删掉对象时真的删集群对象，先在非生产环境跑一段时间，确认没有人靠“集群里还有”来保命。

同一个 digest 从 dev 提升到 prod，配置用 overlay 或 values 区分。镜像只构建一次，SBOM、provenance 和签名都绑在这个 digest 上；提升时改的是清单里的 digest，不是重新构建或重新打 tag。环境差异只放副本数、资源、域名和开关，公共对象放 base 或 chart 模板，overlay 里不要复制大段 YAML。

发布用 PDB、readiness 和金丝雀，不要只靠 Deployment 的 RollingUpdate。PDB 保护自愿驱逐，readiness 保证新 Pod 真的能服务，金丝雀把真实流量按比例送过去；自动回滚需要可信的指标，指标不可信时，自动回滚只会把问题放大。每次发布写 `kubernetes.io/change-cause`，回滚演练要记录从发现问题到恢复的时间。

Helm chart 要版本化、签名、扫描，Kustomize overlay 要能被 diff 审阅。chart 的 `version` 和 `appVersion` 分开管，chart 的依赖锁版本；overlay 的 `images` 用 digest，patch 的 target 写清楚。CI 里至少跑 `kubectl kustomize`、`helm template`、`kubectl diff` 或 `--dry-run=server`，不要用“apply 到 staging 没报错”代替静态校验。

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `kubectl kustomize <dir>` | 只渲染 Kustomize 目录 | 不连接集群 |
| `kubectl apply -k <dir>` | 渲染并 apply | `-k` 指向含 `kustomization.yaml` 的目录 |
| `resources` | base 包含的对象文件或目录 | overlay 里通常指向 `../../base` |
| `patches[].target` | 按 group/version/kind/name/namespace 选对象 | namespace 要和 patch 时的对象一致 |
| `images` | 改镜像 name/tag/digest | digest 与 tag 不要同时写 |
| `configMapGenerator` / `secretGenerator` | 从 literals/files 生成对象 | 名字默认带内容 hash |
| `helm template <name> <chart>` | 本地渲染 chart | 不连接集群 |
| `helm install/upgrade/rollback` | 创建、升级、回滚 release | `rollback` 会新增 revision |
| `helm history <name>` | 看 release 历史 | 记录存在 Secret 里 |
| `helm push <tgz> oci://...` | 把 chart 推到 OCI registry | 本地 HTTP registry 要 `--plain-http` |
| `argocd app sync/diff` | 同步/比较 Application | core 安装没有 server 时用 `kubectl` 看 status |
| `HTTPRoute.backendRefs[].weight` | 按权重分流 | 权重是相对值，90/10 表示约 9:1 |
| `kubernetes.io/change-cause` | 记录 Deployment 变更原因 | 替代已移除的 `--record` |
