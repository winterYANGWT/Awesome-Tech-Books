# 第 12 章 Registry、tag 与 digest、私有仓库与离线分发（含国内网络下取镜像）

周一早上，值班同事说 staging 的 shorty 行为和周五不一样了。查下去，Deployment 里写的是 `shorty:0.1`，周五构建的确实是 0.1，但周末有人用同一个 tag 又推了一次；节点上现在跑的是新内容，而回滚时把 tag 改回 `0.1` 也没有用，因为它已经指向新的镜像。这类问题不是靠“发布时小心一点”能解决的：只要部署清单里写的是 tag，tag 就是一个可以被移动的指针。

第 11 章结束时，`shorty:0.1` 和 `shorty-worker:0.1` 只存在于构建机的本地镜像库里。别的机器、别的节点、CI 的另一个 runner 都拿不到它们。要把镜像送出去，需要一个 registry（镜像仓库服务）；要保证送出去之后不再变，需要 digest（摘要）；要让私有 registry 只认自己人，需要认证；要在断网或慢网的环境里搬运，需要能离线的包。这一章沿着 shorty 的发布路径把这四件事做一遍。

先不急着上 Kubernetes。本章前半段在 Docker 里把镜像推到本地 registry，观察 tag 和 digest 的区别、登录凭据写到了哪里、registry 怎么加认证；后半段用 Secret 让 Kubernetes 拉私有镜像，最后处理离线分发和国内网络下最常见的几个卡点。故障部分会故意用错地址、写错 Secret，看看报错长什么样。

> **起点**：第 11 章结束的状态：`shorty:0.1`、`shorty-worker:0.1` 已在本地构建好，没有推送到任何 registry，也没有 registry 在运行。执行 `bash code/ch12/setup.sh` 会构建镜像、启动一个临时的本地 registry，并起一个单节点 kind 集群备用。

## 12.1 tag、digest 与 repository

先把几个词分开。registry 是提供镜像服务的那个端点，比如 `localhost:5000` 或 `registry.k8s.io`；repository（仓库）是 registry 里的一个名字，比如 `shorty`，一个 registry 可以有很多 repository；tag 是 repository 下面可变的指针，比如 `0.1`、`latest`；digest 是镜像内容的哈希，形如 `sha256:12cf...`。一个完整的镜像引用可以写成 `[registry-host[:port]/]repository[:tag][@digest]`，其中 registry 不写时默认是 Docker Hub，tag 不写时默认是 `latest`。

`docker tag` 只加一个别名，不复制任何层。执行 `docker tag shorty:0.1 localhost:5000/shorty:0.1` 之后，本地镜像库里多了一条“这个名字指向这份内容”的记录，磁盘上的层还是同一份。`docker push` 才把内容传到 registry，并在本地记下 registry 返回的摘要，也就是 `docker image inspect` 里的 `RepoDigests`。示例里 `RepoDigests` 有两行，一行是短名字 `shorty@sha256:...`，一行是 `localhost:5000/shorty@sha256:...`，两个名字指向同一个摘要，这正说明名字可以有很多个，内容只有一个。

看输出时抓住三处。第一处是 push 的末尾：`0.1: digest: sha256:... size: ...`，registry 接受了这个 manifest，并告诉我们它的摘要。第二处是 `docker run --rm "localhost:5000/shorty@$digest" version` 第一次输出 `shorty dev`。第三处是紧接着用 `--build-arg VERSION=0.2` 构建了 0.2 的内容，再推到同一个 `0.1` tag 上，然后分别用 digest 和 tag 启动：digest 仍然是 `shorty dev`，tag 已经变成 `shorty 0.2`。中间那次 digest 启动还触发了从 registry 拉取（本地没有这个 digest 的标签引用），说明 registry 里旧 digest 的 manifest 和层都还在，移动 tag 不会删掉旧内容。

`docker image inspect` 里会同时看到 `.Id` 和 `RepoDigests`。在 lab 的 Docker 29（containerd 镜像存储）上，示例里这两个值是同一个摘要；旧版 overlay2 存储更接近把 config 对象的摘要当镜像 ID。`docker run`、`docker push` 认的是 manifest digest，`docker image ls` 显示的是短 ID；讨论“回滚到哪个 digest”时以 registry 返回的 manifest digest 为准，不要拿短 ID 当唯一依据。同一个镜像在不同 registry 里如果 manifest 被重新生成（比如多平台索引不同、attestation 不同），manifest digest 可能不同；生产清单里写的是 registry 返回的那个 manifest digest，用 `docker image inspect` 或 `docker buildx imagetools inspect` 读。

这里有一个和旧教程不一样的地方：**不要用“push 之前 `RepoDigests` 为空”来判断镜像有没有推过**。Docker 29 新安装默认使用 containerd 镜像存储，本地构建或 `docker tag` 之后，`docker image inspect` 就可能已经给出摘要，因为 manifest 摘要是本地内容库算出来的，和 registry 里有没有这份内容无关。真正能说明问题的是 registry 能不能按这个 digest 提供 manifest，示例里用 `docker run ...@sha256:...` 从 registry 拉取就是一次实测。用旧版 overlay2 存储的 Engine 通常要 push 之后才有 `RepoDigests`，两种行为都不能拿来当“是否已发布”的可靠判据。

digest 的价值在部署侧。Kubernetes 的 `image` 字段同样接受 `repository@sha256:...`，也接受 `repository:tag@sha256:...`；同时写 tag 和 digest 时，**只有 digest 参与拉取**，tag 只是给人看的。`imagePullPolicy` 的默认值和镜像写法有关：不写策略、镜像用 digest 时默认 `IfNotPresent`；不写策略、tag 是 `latest` 或者干脆没写 tag 时默认 `Always`；写了非 `latest` 的 tag 时默认 `IfNotPresent`。这个默认值只在对象第一次创建时写入，之后改镜像字段不会自动改策略，要显式改。`Always` 也不是每次都重新下载所有层：kubelet 让容器运行时去 registry 解析 tag 或 digest，已经在本地的层会复用。

`0.1`、`v0.1`、`release-0.1` 是三个不同的 tag，它们之间没有任何自动对应关系；改名不会改变镜像内容，只是多了一个名字。tag 区分大小写，`0.1` 和 `0.1-RC` 是两个不同的指针；写错一个字符就是另一个路径。

回滚应该回到 digest。tag 是给人读的别名，今天可以指向 A，明天可以指向 B；digest 由内容决定，同一个 digest 拉下来的 manifest 和层不会变。发布清单里写 digest，回滚时把 digest 改回上一个版本，节点上跑的就是确定的代码；写 tag 的回滚只是把指针拨回去，指针背后的内容可能早就被覆盖了。Kubernetes 文档也明确建议生产环境避免 `:latest`，因为它既难追踪当前版本，也难正确回滚。

repository 的名字可以带斜杠，比如 `team/shorty`，斜杠前面是 registry 里的命名空间；`docker tag` 可以在同一个镜像上挂多个名字，`docker push` 默认只推你指定的那个名字，要一次推多个 tag 可以用 `docker push --all-tags`。tag 的字符集和长度也有约束：Kubernetes 文档给出的规则是最多 128 个字符，只允许字母、数字、下划线、点和连字符，并且不能以点或连字符开头。digest 目前常见的是 `sha256`，算法写在冒号前面，后面是十六进制哈希；换算法时写法不变，仍然是 `名字@算法:哈希`。这些格式不是 Docker 独有的，OCI Distribution 和 Kubernetes 都按同一套规则解析。

## 12.2 Docker Hub 与登录

`docker login` 做的事情比它看起来少：它把用户名和密码（或 access token）发给 registry 做一次校验，然后把凭据写到本地，供之后的 push/pull 使用。默认位置是 `~/.docker/config.json`，`auths` 下面按 registry 地址存一条 `auth`。示例里 `auths` 的键是 `localhost:5000`，`credsStore` 是 `null`，说明没有配置凭据助手，凭据就放在这个文件里。登录时那行 `WARNING! Your credentials are stored unencrypted` 不是客套话：把 `auth` 做 base64 解码就得到 `shorty:s3cret`，base64 只是编码，不是加密。文件权限和所在机器的安全边界才是这一层的保护。

示例里的 registry 此时还没有配认证，所以随便给一组用户名密码都会显示 `Login Succeeded`。这并不代表服务端认可了这组凭据，只代表 CLI 把地址、用户名和密码写进了本地配置；真正会不会被拒绝，要等 push/pull 时 registry 返回 401 才知道。也正因为如此，登录成功不能当作“密码正确”的证明，更不能把 `docker login` 写进 CI 后就认为镜像安全了。

`~/.docker/config.json` 是多个 registry 共用的一份配置，`auths` 下面按地址分开存；登录一个新的 registry 不会覆盖旧的，`docker logout` 也只删指定 registry 的那一条。地址的写法要和 push/pull 时用的名字一致：`localhost:5000` 和 `127.0.0.1:5000` 是两个键，`https://index.docker.io/v1/` 是 Docker Hub 的特殊写法。CI 里如果多个任务共用一个 HOME，凭据会互相覆盖，最好用 `--config` 指向任务自己的目录，或者每个任务单独登录、跑完就 logout。

`auth` 是 `用户名:密码` 的 base64，这意味着任何能读这个文件的人都能还原出密码。生产环境应该用 credential helper：在 `~/.docker/config.json` 里配置 `credsStore`（全局）或 `credHelpers`（按 registry），凭据交给系统的密钥环、`pass`、`secretservice` 这类程序保管，配置文件里只留 helper 的名字和 registry 地址，不再出现 `auth` 字段。Kubernetes 的文档也提醒，用了 credentials store 之后，`config.json` 里看到的是 `credsStore` 而不是 `auth`，这时创建 Secret 要换一种方式，不能直接复制 `auth`。此外，Docker Hub 现在推荐用 access token 而不是账号密码登录，token 可以单独撤销，泄露后的影响范围比账号密码小。

> **旧资料提示**：旧教程里凭据放在 `~/.dockercfg`，`docker login` 还要输 email；现代 Docker 用 `~/.docker/config.json`，登录只需要用户名和密码/access token，不再要求 email。

Docker Hub 的拉取限流和席位政策是会变的，官方页面上的额度、适用对象和统计口径都调整过，正文不写死具体数字。对本书的示例来说，重要的有两点：匿名拉取会受限制，认证用户的额度按账号/组织计算；公开镜像也不等于永久可用，作者可以删仓库、删 tag、用同一个 tag 推新内容。生产环境应该用受控 registry、镜像缓存或 mirror，把“能不能拉到”从别人的政策里拿出来。lab 的 Docker 配了 `mirror.gcr.io` 作为 Docker Hub 的 mirror，所以示例里照常写 `alpine:3.22` 这样的名字；mirror 的配置在 daemon 侧，不在 `docker pull` 的参数里，12.6 会再讲。

席位政策还影响“能不能看”。Docker Hub 的私有仓库数量、协作者数量、组织成员数都和订阅有关，政策调整时受影响的往往不是拉取本身，而是团队里谁能看到哪个仓库。把生产镜像放在个人账号的私有仓库里，人员变动、账号停用、账单失败都会变成发布故障；至少要用组织账号，重要的镜像要有第二份受控 registry。公开镜像也有类似的归属问题：镜像的作者可以删除仓库，Docker Hub 也可能因为政策或滥用下架内容，清单里写死一个公开 tag 而不留本地副本，等于把可用性交给了别人。

> **旧资料提示**：旧教程里说生产要开 Docker Content Trust（`DOCKER_CONTENT_TRUST=1`）来给镜像签名。DCT 正在退役，Notary v1 服务将停止；现在的主流是 cosign/Sigstore 这类工具，签名对象是 digest，验签放在准入层，第 13 章展开。

输出里 `docker inspect` 的 `running` 说明容器在跑；`curl -s localhost:5000/v2/` 返回 `{}`，这是 registry 的 API 版本探测端点，能返回 200 就说明服务端在正常工作，哪怕里面还没有镜像。push 之后 `_catalog` 返回 `{"repositories":["shorty"]}`，`tags/list` 返回 `{"name":"shorty","tags":["0.1"]}`：registry 里现在有一个 repository 叫 `shorty`，它下面有一个 tag 叫 `0.1`。最后 `docker inspect` 的 `Mounts` 一行显示 `volume registry-data -> /var/lib/registry`，这就是数据能活过容器重建的原因。

`localhost:5000` 能直接用 HTTP，是因为 Docker 把 `127.0.0.0/8` 当成默认不安全的本地地址，不会强制 TLS。换成一个非 localhost 的地址，Docker 会先尝试 HTTPS；registry 只会说 HTTP，于是 push 报 `http: server gave HTTP response to HTTPS client`。这时候有两个选择：给 registry 配 TLS（生产必须这样），或者在 `/etc/docker/daemon.json` 里把地址加进 `insecure-registries` 并重启 daemon（只适合本地实验）。`--insecure-registry` 不是“关掉证书校验”这么简单，它让 Docker 对那个地址走明文 HTTP，凭据和镜像内容都会裸奔，生产环境不要用。

registry 容器本身没有认证：任何人只要能访问 5000 端口，就能 push 和 pull。示例的 `-p 5000:5000` 会把端口发布到宿主的所有接口，不是只监听 localhost；lab 的网络是隔离的，所以问题不大，但在真实主机上这等于把 registry 暴露到内网。一旦端口能被别人访问，就必须加认证和 TLS。12.4 加认证，TLS 的选择在“排障”和“上生产前”再说。

`_catalog` 只列出 repository 的名字，不列 tag，也不保证顺序；要列某个 repository 的 tag，得再请求 `/v2/<name>/tags/list`。这两个端点都属于 registry 的只读 API，开了认证之后同样要带凭据；生产环境通常还会在 registry 前面放一层网关，只暴露必要的路径和动作，不让外部直接访问管理端点。

数据卷里存的不只是“镜像文件”。registry 用一套内容寻址的目录保存 blob、manifest 和 tag 的映射，`/var/lib/registry` 直接拷走可以作为冷备份，但更稳妥的是用 registry 自己的 API 做复制，或者在存储层做快照。删 tag 不会立刻删 blob，因为同一个 digest 可能还被别的 tag 引用；要真正回收空间，需要 registry 的垃圾回收流程，而且要在只读或停写窗口里做。生产上还要考虑保留策略：旧 digest 留多久、被删的 tag 能不能恢复、审计日志保存多久。这些都不是 `docker run registry` 一条命令能带上的。

## 12.4 私有仓库认证与 push/pull

给 registry 加认证最省事的办法是 htpasswd 文件。`htpasswd -Bbn shorty s3cret` 生成一行 `shorty:$2y$...`：用户名、冒号、bcrypt 哈希。`-B` 指定 bcrypt，`-b` 从命令行取密码，`-n` 把结果打到标准输出而不是写文件。文件挂进容器后，用三个环境变量告诉 registry 怎么用它：`REGISTRY_AUTH=htpasswd` 启用 htpasswd 认证，`REGISTRY_AUTH_HTPASSWD_REALM=shorty` 是 401 响应里 `Www-Authenticate` 的 realm，`REGISTRY_AUTH_HTPASSWD_PATH=/auth/htpasswd` 是容器里的文件路径。registry 读的是哈希，不是明文；示例里只打印用户名和哈希的前四个字符（`$2y$`），不要把整行哈希贴进日志或工单。

示例先在没有登录的情况下 push 一个 `shorty:private`。请求到达 registry，registry 返回 401 和 `Www-Authenticate: Basic realm="shorty"`，Docker 没有可用的凭据，push 以 `no basic auth credentials` 失败。注意这个失败发生在**推送之前**，不是因为镜像内容有问题。然后用 `docker login` 登录，再 push 同一个 tag，这次成功；删掉本地 tag 再 `docker pull`，也成功，说明读同样受认证保护。最后的 `docker logout` 把本地凭据删掉，避免下一个人在这台机器上直接用到你的身份。

认证和 TLS 要一起看。htpasswd 保护的是“谁可以推/拉”，Basic 认证在 HTTP 上只是 base64 编码的 `用户名:密码`，没有加密；只有在 TLS 里，凭据和内容才不被旁听。所以生产 registry 的组合是 TLS + 认证，而不是只加一个 htpasswd。示例里 `localhost:5000` 走 HTTP 只是为了本地实验。

`docker logout` 只删本地保存的凭据，不会在服务端注销 token，也不会撤销 access token。CI 里更常见的做法是用短期 token、`--password-stdin` 从环境变量或文件读密码，任务结束就丢弃；不要把密码写在 `docker login -p` 的命令行里，那会进 shell 历史和进程列表。Kubernetes 的 Secret 也一样，`kubectl create secret docker-registry` 的命令行参数会留在 shell 历史里，官方文档专门提醒了这一点，生产应该用文件或外部密钥管理。

跨 registry 复制镜像不要用 `docker pull` + `docker tag` + `docker push` 这三步。三步会在本地落一份完整镜像，多平台 manifest、attestation 一类的附属内容容易在重新 push 时丢掉，磁盘和带宽也要付两份。`skopeo copy docker://源/镜像:tag docker://目标/镜像:tag` 直接在两个 registry 之间搬，多平台 index 默认会保留；要复制 repository 里的所有 tag 加 `--all`，要强制所有平台加 `--multi-arch all`。`crane copy` 是同类工具。它们都按 digest 校验，复制完可以用 `skopeo inspect` 或 `crane digest` 对一下源和目标的摘要。示例里没有装 skopeo，这一步只讲用法，不在 lab 里跑。

htpasswd 是 registry 自带的最小认证方案，它只回答“这个用户名密码对不对”，不区分 repository：只要通过认证，就能推/拉这个 registry 里的所有仓库。需要按项目、按团队控制读写权限时，htpasswd 不够，要用 Harbor 这类带 RBAC 的 registry，或者在 registry 前面放一个能做 token 授权的服务。别把“加了 htpasswd”当成完整的权限模型。

htpasswd 文件可以有多行，一行一个用户，加人就是追加一行；文件权限要收窄，因为它虽然是哈希，仍然可以被离线爆破弱密码。bcrypt 的 cost 越高，验证越慢，暴力破解也越难，但每次 push/pull 都要做一次验证，registry 的并发高时要把这个成本算进去。删用户就是删对应行，然后重启 registry 让新文件生效；只改文件不重启，行为取决于实现有没有热加载，最稳的做法还是重启。htpasswd 只解决“用户名密码”这一种认证，token、OIDC、LDAP 这些要走 registry 的 auth 插件或前置代理，别指望一个 htpasswd 文件覆盖所有企业认证需求。

第一条命令确认 `shorty` 命名空间里已经有默认 ServiceAccount，后面给 ServiceAccount 加 `imagePullSecrets` 时用的就是它。示例故意先 apply Pod、后建 Secret。Pod 里写了 `imagePullSecrets: [{name: regcred}]`，但 `shorty` 命名空间里还没有这个 Secret，Event 里会出现 `FailedToRetrieveImagePullSecret`，意思是“这个 Secret 我拿不到，接下来会尝试不带凭据拉，可能失败”；同时还有一条 `Failed`，内容是 registry 拒绝匿名拉取，containerd 把它写成 `no basic auth credentials`，Pod 进入 `ImagePullBackOff`。不同运行时和 registry 的错误文本不完全一样，有的会直接写 `401 Unauthorized`，但事件里的关键字都是“认证没通过”。`kubectl describe pod` 能同时看到这两条，排障时先看它，而不是只看 Pod 的 `STATUS`。

`ImagePullBackOff` 里的 `BackOff` 是 kubelet 在退避重试：每次失败后等待时间变长，直到一个上限。Secret 建好之后，示例先打印它的类型，确认是 `kubernetes.io/dockerconfigjson`，再删掉旧 Pod 重建，让 kubelet 重新走一次调度和拉取。不需要改 Pod 的镜像名；新 Pod 拉到 `localhost:5000/shorty:0.1`，`kubectl logs` 输出 `shorty dev`，说明镜像里的程序真的跑起来了，不只是“镜像拉下来了”。

三个容易写错的地方。第一，Secret 必须和 Pod 在同一个 namespace（命名空间）；在 `default` 里建的 `regcred`，`shorty` 里的 Pod 引用不到。第二，`--docker-server` 必须和镜像引用里的 registry 部分完全一致；镜像是 `localhost:5000/shorty:0.1`，server 就写 `localhost:5000`，不要写 `http://localhost:5000` 或 `localhost`，端口不能省。Docker Hub 的 server 按官方文档写 `https://index.docker.io/v1/`。第三，`imagePullSecrets` 是 Pod（或 Pod 模板）级别的，Deployment 要在 `spec.template.spec.imagePullSecrets` 里写；如果希望 namespace 里所有 Pod 都继承，可以给 ServiceAccount（服务账号）加 `imagePullSecrets`，新创建的 Pod 会自动带上。

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: default
  namespace: shorty
imagePullSecrets:
  - name: regcred
```

上面的片段只是示意 ServiceAccount 的字段；实际操作可以用 `kubectl patch serviceaccount default -n shorty -p '{"imagePullSecrets":[{"name":"regcred"}]}'`。注意它影响的是**之后创建**的 Pod，已经在跑的 Pod 不会因为改了 ServiceAccount 就自动多出凭据。Secret 里的凭据是静态的，registry 换了密码或 token 过期，所有引用它的 Pod 都会在下一次拉取时失败；生产环境更稳妥的是 kubelet credential provider 或短期的镜像仓库 token，而不是把长期密码塞进每个 namespace 的 Secret。

还有一个和 digest 相关的细节：示例里写了 `imagePullPolicy: Always`。如果不写，`0.1` 这样的非 `latest` tag 默认是 `IfNotPresent`，节点上已经有这个镜像时 kubelet 根本不会联系 registry，Secret 缺失或密码错误都看不出来。排障时要么显式 `Always`，要么换一个节点上没有的 tag/digest，才能让拉取真的发生。

除了 `kubectl create secret docker-registry`，也可以从已有的 `config.json` 直接建：`kubectl create secret generic regcred --from-file=.dockerconfigjson=$HOME/.docker/config.json --type=kubernetes.io/dockerconfigjson`。这条路径适合已经登录过多台 registry 的构建机，但要注意 `config.json` 里可能不止目标 registry 的凭据，建出来的 Secret 会把它们一起带进集群；更稳妥的是先复制一份，只保留需要的 `auths` 条目。用 credential helper 时，`config.json` 里没有 `auth`，`--from-file` 复制过去也无法在节点上还原密码，这时要么在 CI 里显式生成 dockerconfigjson，要么用 `kubectl create secret docker-registry` 直接给凭据。

Secret 里的 `.dockerconfigjson` 是 base64 编码的 JSON，不是加密；`kubectl get secret regcred -o yaml` 能看到它，`kubectl get secret ... -o jsonpath` 再 `base64 -d` 就能读出 `auths` 里的用户名和密码。所以 Secret 的 RBAC 要收紧，能读 Secret 的人等于能拿到 registry 凭据；不要把 Secret 清单提交到 Git，也不要在 CI 日志里 `cat` 它。Secret 有大小限制（etcd 对单个对象有上限），一个 dockerconfigjson 里塞几十个 registry 的凭据不现实；多 registry 时按团队或环境拆 Secret，Pod 可以引用多个 `imagePullSecrets`。

## 12.6 离线分发与慢网

`docker save` 把一个镜像的层和 manifest 打成一个 tar，`docker load` 再从 tar 装回本地镜像库。示例先记下 `shorty:0.1` 的镜像 ID，save 之后删掉本地镜像，再 load 回来，比较两次的 ID。输出里 `Loaded image: shorty:0.1` 说明 tag 跟着回来了，`before` 和 `after` 两行相同说明内容没有变；`docker image ls` 里也能看到 `shorty:0.1` 还在。这个 tar 可以拷到断网的机器上，`docker load` 之后就能直接 `docker run`，不需要 registry。

```console
{{#include code/ch12/12_6_offline_save_load.out}}
```

`docker save` 默认会把镜像里可用的平台都带上。多平台镜像在 Docker 29 的 containerd 存储里包含多个平台的 manifest，直接 save 会很大，也可能在目标机器上不可用；用 `docker save --platform linux/amd64` 只导出目标平台的镜像内容；如果镜像带 attestation，tar 里可能仍带着 `unknown/unknown` 的附属 manifest。`docker load` 不会重新计算内容，示例比较的 `.Id` 在 lab 的 Docker 29 上和 `RepoDigests` 是同一个摘要（containerd 存储用 manifest 摘要做镜像 ID），load 前后都保持不变；但 tar 里没有 registry 侧的签名，SBOM/attestation 也不一定以可验证的形式保留。要连这些一起搬，用 `skopeo copy docker://... dir:...` 或 `oci:` 格式，而不是 `docker save`；多平台 index 默认保留，要所有 tag 才加 `--all`。

本章没有在 lab 里装 skopeo，下面的命令按 skopeo 官方文档写；示例只跑 `docker save`/`docker load` 这一条路径。`skopeo` 不依赖 Docker daemon，适合在构建机和离线区之间搬。`skopeo copy docker://registry.example/shorty:0.1 dir:/media/usb/shorty` 会把 manifest 和所有 blob 放进一个目录；到目标机器上 `skopeo copy dir:/media/usb/shorty docker://localhost:5000/shorty:0.1` 推回去。`dir:` 是 skopeo 自己的目录格式，`oci:` 是 OCI Image Layout，后者更适合长期归档。复制前后用 `skopeo inspect --format '{{.Digest}}'` 对一下 digest，确认没有搬到一半。`crane copy` 也能做同样的事，选团队里已有的工具即可。

慢网和国内网络下，mirror 和代理是另一条路。Docker 的 mirror 配在 daemon 侧，`/etc/docker/daemon.json` 的 `registry-mirrors` 是一个地址列表；Kubernetes 节点用的是 containerd，mirror 配在 containerd 的 `registry.mirrors` 里，和 Docker 的 daemon.json 不是一回事。`docker pull` 命令本身没有“这次走哪个 mirror”的参数，改的是 daemon 或节点的配置。mirror 可能是旧的、缺 tag 的，甚至是别人搭的；拉下来之后要用 digest 对一下，不能因为“拉到了”就认为内容正确。代理（HTTP_PROXY/HTTPS_PROXY）要在 daemon 的启动环境里配；在 shell 里 `export HTTPS_PROXY` 不会改变 daemon 的拉取路径。

mirror 和私有 registry 的职责不一样。mirror 是上游 registry 的缓存，命中就省一次跨境拉取，没命中还得回源；私有 registry 是权威副本，tag 和保留策略由自己控制。国内团队常见的做法是：CI 推自己的私有 registry，基础镜像用内部 mirror 或同步任务定期复制，节点只信任这两个来源；不要把生产镜像交给一个来路不明的公共 mirror。mirror 同步时最好按 digest 校验，并且记录同步时间；基础镜像的 tag 被上游移动时，mirror 可能还留着旧 digest，靠 tag 判断“是不是最新”并不可靠。

> **旧资料提示**：旧教程里把 `k8s.gcr.io` 当成 Kubernetes 官方镜像仓库。这个 registry 已经在 2023 年冻结，并重定向到 `registry.k8s.io`；新清单应该直接写 `registry.k8s.io`，不要等重定向。

tar 本身没有签名，`docker load` 也不会检查来源；从 U 盘、对象存储或跳板机搬过来的包，先算一遍 `sha256sum`，和打包时记录的值对一下，再 load。包里的镜像 digest 和 tar 文件的校验和是两回事：tar 校验和证明“文件没被换过”，镜像 digest 证明“load 出来的内容和构建时一致”，两个都要有。tar 不要放在可写共享目录里让所有人取，能改 tar 的人就能改里面的镜像。

离线包要记录 digest，不要只记 tag。tag 在打包和拆包之间可能被重新指向，digest 不会；把 `skopeo inspect` 得到的 digest、构建时间、SBOM 文件和 tar 放在一起，到了目标机器先校验 digest 再 load。也不要把 `latest` 打进离线包：`latest` 在源端和目标端都只是一个可变的别名，出了问题无法判断包里到底是哪一版。

如果构建机和 registry 不在同一台机器上，`docker context` 可以让你在多个 daemon 之间切换：`docker context create buildhost --docker host=ssh://build@builder`，然后 `docker --context buildhost build ...`。这样镜像在构建机上直接构建、直接推送，不用先拉到笔记本再推回去。context 里可以带 TLS 信息，凭据仍然按 registry 走 `docker login`，不要把长期密码写进 context 文件。

## 12.7 排障：HTTP registry 与 ImagePullBackOff

第一个故障是地址。示例把 registry 发布在 5000 端口，然后用 lab 的 eth0 地址（不是 `localhost`）去 push。Docker 对非 `127.0.0.0/8` 的地址默认先试 HTTPS，registry 只会说 HTTP，于是报 `http: server gave HTTP response to HTTPS client`。这个错误不是“registry 没起来”，registry 其实好好的，只是 Docker 用错了协议。用 `curl -v http://<地址>:5000/v2/` 能拿到 HTTP 响应（12.3 的无认证 registry 返回 200，12.4 加了认证之后返回 401），用 `curl -v https://<地址>:5000/v2/` 会看到 TLS 握手失败或收到明文 HTTP 响应，两边一对照就清楚了。

```console
{{#include code/ch12/12_7_troubleshoot.out}}
```

修复有两条路。生产环境给 registry 配 TLS 证书，Docker 和 containerd 都信任这个证书，push/pull 走 HTTPS；本地实验可以把地址加进 `/etc/docker/daemon.json` 的 `insecure-registries`：

```json
{
  "insecure-registries": ["192.0.2.10:5000"]
}
```

改完要重启 Docker daemon。这个配置让 Docker 对这个地址走明文 HTTP，凭据和镜像内容都不加密；它只适合本地实验，不要写进生产节点。示例里的修复更简单：把 registry 放回 `localhost:5000`，Docker 对 `127.0.0.0/8` 默认按不安全地址处理，不需要改 daemon.json。这也是为什么本书的本地 registry 一直用 `localhost:5000`。

第二个故障是 Kubernetes 的 `ImagePullBackOff`。示例建了一个 Secret `wrongreg`，但 `--docker-server` 写的是 `localhost:5001`，镜像却在 `localhost:5000`。把 `.dockerconfigjson` 解码后看 `auths` 的键，只有 `localhost:5001`；kubelet 按镜像的 registry 部分去找凭据，找不到 `localhost:5000` 的条目，就只能匿名拉，registry 返回 401，Pod 进入 `ImagePullBackOff`。这种错误和“Secret 不存在”不同：Secret 存在，只是键不匹配。`kubectl describe pod` 里通常能看到 `Failed to pull image ... no basic auth credentials` 或 `401 Unauthorized`；如果是证书问题，还会看到 `x509: certificate signed by unknown authority`，那是节点不信任 registry 的 CA，要去查 containerd 的 CA 配置或把正确的 CA 装到节点上。

排查顺序可以固定下来：先 `kubectl -n <命名空间> get secret <名字>` 确认 Secret 在不在、类型对不对；再解码 `.dockerconfigjson`，用 `jq '.auths | keys'` 看键是不是镜像的 registry 地址；然后 `kubectl describe pod` 看 Event 是 `FailedToRetrieveImagePullSecret` 还是 `Failed`；最后确认镜像名里的 registry、端口、repository 和 tag 有没有写错。Secret 的 namespace 和 Pod 的 namespace 必须一致，`--docker-server` 的端口不能省，这两条是最常见的。改完 Secret 后可以等 kubelet 下一次退避重试，也可以删掉 Pod 重建；示例选择重建，顺便验证新 Pod 能拉到镜像。

如果 Event 是 `x509`，问题在 TLS 而不是用户名密码：节点上的 containerd 不信任 registry 的证书。registry 容器的日志也值得看：`docker logs shorty-registry` 会记录每个请求的路径和状态码，401、404、500 分别是认证、路径/仓库不存在、服务端错误；如果日志里连请求都没有，问题在网络或 DNS，不在认证。先确认 registry 证书的 SAN 包含节点实际使用的地址（IP 或域名），再把签发它的 CA 放到节点的信任目录；containerd 的 `registry.configs."host".tls.ca_file` 和 Docker 的 `/etc/docker/certs.d/<host>/ca.crt` 是两套配置，不要只配了 Docker 就以为节点也能用。`docker info` 能看构建机上的 `Insecure Registries`，`crictl info` 或 containerd 的配置能看节点上的 registry 设置；两边不一致时，构建机 push 成功不代表节点 pull 成功。

## 上生产前

生产 registry 至少要有 TLS、认证和保留策略。TLS 保护凭据和内容，认证决定谁能推、谁能拉，保留策略决定旧 digest 和旧 tag 留多久。匿名 push 必须关闭；匿名 pull 是否允许要看镜像的敏感程度。tag 的不可变（immutable tag）能防止“同一个 tag 被重推”，但它不能替代 digest 部署，因为删除/重建仓库、改 tag 规则这些操作仍然能让名字指向别的内容。

部署清单写 digest，tag 只做别名。发布流水线在 push 之后读出 digest，把它写进 Deployment/Pod 的 `image`；回滚时改回上一个 digest，而不是改 tag。这样即使 registry 上的 tag 被移动，节点拉到的内容也不会变。`imagePullPolicy` 要和写法匹配：用 digest 时默认 `IfNotPresent` 是合理的；用可变 tag 时不要指望 `IfNotPresent` 帮你发现上游变化。

节点上的凭据要用 credential helper 或短期 token，不要把一个长期密码写进 DaemonSet、节点文件或每个 namespace 的 Secret。Kubernetes 的 `imagePullSecrets` 和 ServiceAccount 适合中小规模；节点多、registry 多时，kubelet credential provider 能从外部按需取短期凭据。无论哪种方式，密码都不应该出现在镜像、清单仓库和 `kubectl` 命令行历史里。

离线包要同时记录 digest 和 SBOM。`docker save` 适合单平台、临时搬运；跨 registry、多平台、要保留 attestation 时用 `skopeo copy`（多平台 index 默认保留；要所有 tag 才加 `--all`）。包到目标机器后先校验 digest，再 load/push；不要把 `latest` 打进包里，也不要把“能 load”当作“内容正确”。

`insecure-registries` 只用于本地实验。生产 registry 用自签证书时，要把 CA 装到每个节点的 containerd 信任链里，而不是在节点上关掉校验；`x509: certificate signed by unknown authority` 这类 Event 说明节点不信任 registry，不是密码错了。mirror 也要按同样的标准检查：mirror 是别人维护的缓存，可能缺 tag、可能过期，拉下来之后用 digest 对一下。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `docker login/logout` | 写入/删除本地 registry 凭据 | 默认写 `~/.docker/config.json`；有 `credsStore` 时写 helper |
| `docker tag` | 给镜像加一个名字 | 只加别名，不复制层 |
| `docker push/pull` | 与 registry 传输镜像 | 非 `127.0.0.0/8` 的地址默认要求 HTTPS |
| `docker save/load` | 把镜像打成 tar / 从 tar 装回 | 可用 `--platform` 限定平台 |
| `skopeo copy` | 在 registry、`dir:`、`oci:` 之间复制 | `--all` 复制所有 tag；`--multi-arch all` 复制所有平台；不依赖 Docker daemon |
| `docker image inspect .RepoDigests` | 看名字对应的 manifest 摘要 | containerd 存储下本地构建后可能已有值 |
| `curl localhost:5000/v2/_catalog` | 列出 registry 里的 repository | 认证开启后需要凭据 |
| `htpasswd -Bbn user pass` | 生成 bcrypt 格式的认证文件 | registry 通过 `REGISTRY_AUTH*` 环境变量读取 |
| `kubectl create secret docker-registry` | 创建 `kubernetes.io/dockerconfigjson` Secret | `--docker-server` 要与镜像的 registry 完全一致 |
| `imagePullSecrets` | Pod/ServiceAccount 引用拉取凭据 | Secret 必须同 namespace |
| `imagePullPolicy` | 控制何时拉镜像 | digest → `IfNotPresent`；`latest`/无 tag → `Always`；其他 tag → `IfNotPresent` |

本章结束时，本地 registry 里有 `localhost:5000/shorty:0.1` 和它的 digest，`shorty` namespace 里的 `regcred` 让 Pod 能拉取私有镜像；为了给后面的章节让出 lab 内存，示例最后用 `kind delete cluster` 把单节点集群删掉了。
