# 第 20 章 Deployment 与滚动更新、DaemonSet

上一章结束时，`shorty` 的 api 只有 1 个副本，Service `api` 把 8080 端口的流量直接送到这个 Pod。现在要把镜像从 `shorty:0.1` 换成 `shorty:0.2`。如果按最直觉的做法删掉旧 Pod 再建新的，旧 Pod 一进入 Terminating，EndpointSlice 里就没有它了；新 Pod 从创建到监听 8080 还有一段时间，这段时间里访问 ClusterIP 会得到 `connection refused`。线上看到的就是一次短暂的 503。

Deployment 的默认策略是 RollingUpdate，它本来就是为了避免这种“先删后建”。但滚动更新不等于自动零停机：控制器只保证在 `maxUnavailable` 允许的范围内替换 Pod，而“可用”是按 Pod 的 Ready 条件算的。没有 readinessProbe 时，容器进程刚起来就被当成 Ready，Service 可能把请求发给一个还没开始监听的进程；`maxUnavailable` 设得太大时，旧 Pod 会被一次删掉好几个，剩下的副本未必接得住流量。滚动更新的参数决定的是边界，探针决定的是边界里那个 Pod 到底算不算可用。

`maxSurge: 1` 和 `maxUnavailable: 1` 到底允许几个 Pod 不存在？以 2 个副本为例，滚动过程中可用（Ready）的 Pod 不少于 `2 - 1 = 1` 个，Pod 总数不超过 `2 + 1 = 3` 个：最多允许 1 个 Pod 不可用，最多允许比期望多 1 个 Pod。它不表示“可以随便少 1 个再多多 1 个”，两个方向分别受两个参数约束；百分比还要按副本数取整，默认的 25%/25% 在 2 个副本上会变成 0 个不可用、1 个 surge。这些数字会贯穿本章。

这一章在 3 节点集群上把 api 扩到 2 个副本，做一次有请求压着的滚动更新，再用坏镜像和 `rollout undo` 走一遍回滚；然后故意改成 `Recreate` 看停机，用 DaemonSet 覆盖 3 个节点，最后用 PDB 挡住 `kubectl drain`。示例里的 api 带 readinessProbe，滚动更新才有可判断的依据；没有这个探针，后面的“无 503”结论不成立。

> **起点**：上一章结束时的 `s1-api`：`Deployment api` 1 个副本，`Service api`（ClusterIP 8080），没有 PDB。`bash code/ch20/setup.sh` 会建 1 控制面 + 2 worker 的 kind 集群，apply `s1-api`，再给 api 补上 readinessProbe、`minReadySeconds: 5`、`progressDeadlineSeconds: 30` 和 `maxSurge: 1`/`maxUnavailable: 1`；同时把 `shorty:0.1` 复制成 `shorty:0.2`，并把 `busybox:1.37` 预加载进节点。

## 20.1 Deployment→ReplicaSet→Pod 的所有权

第二条命令 `kubectl scale deployment api --replicas=4` 只改了 Deployment 的 `.spec.replicas`。后面的 `rollout status` 不是“发布新版本”，它只是在等这个 Deployment 达到期望状态；`kubectl rollout status` 读的是 Deployment 的 `.status.conditions` 和副本计数，成功时返回 0，失败时返回非 0。输出里省略掉的几行是它在等 4 个副本都可用；扩容本身不会创建新的 ReplicaSet，也不会产生新的 revision。

`kubectl get rs` 的 `DESIRED` 是控制器希望这个 RS 维持的副本数，`CURRENT` 是它实际看到的 Pod 数，`READY` 是其中 Ready 的 Pod 数；三个数在稳定状态下应该相等，滚动过程中会短暂不一致。这里有两个 ReplicaSet，这是本章 setup 留下的：`s1-api` 原本的 Deployment 已经创建了一个 RS，setup 给 api 加上 readinessProbe 和 `minReadySeconds` 时改了 Pod 模板，Deployment 又创建了一个新 RS，并把旧的缩到 0。旧的 RS 没有被删除，因为它是 Deployment 的历史 revision，回滚时还要用。名字里的 hash 就是 `pod-template-hash`，它由 Pod 模板计算出来，被加到 RS 的选择算符、Pod 模板标签和 Pod 上。新旧 RS 的选择算符因此不会重叠，旧 RS 不会把新 Pod 认成自己的，新 RS 也不会收养旧 Pod。`kubectl get deployment` 的三列也要会读：`READY` 是可用副本数/期望副本数，`UP-TO-DATE` 是已经匹配当前模板的副本数，`AVAILABLE` 是连续满足 `minReadySeconds` 的副本数；扩容后这三列都到 4，才说明 4 个副本真的能接流量，而不只是被创建出来。

接下来的两条 `jsonpath` 命令是在读 `ownerReferences`。两个 RS 的 owner 都是 `Deployment/api`；4 个 Pod 的 owner 都是当前的 RS。这条链是 Kubernetes 垃圾回收的依据：删掉 Deployment，它的 RS 和 Pod 会按级联规则一起删；删掉一个 RS，它下面的 Pod 也会被删。`kubectl get pods -o wide` 还顺带说明了调度结果：4 个 Pod 都落在两个 worker 上，控制面节点没有；因为 kind 给控制面打了 `node-role.kubernetes.io/control-plane:NoSchedule` 污点，普通 Pod 不会上去，20.5 的 DaemonSet 会显式容忍它。

最后一段故意违反“不要直接管理 Deployment 拥有的 RS”这条规则：先找出当前 `spec.replicas > 0` 的那个 RS，把它改成 1，再等它回到 4。RS 确实被缩到了 1，但 Deployment 控制器很快发现自己的期望副本数和活动 RS 的实际副本数不一致，又把 RS 扩回 4；`wait` 的两条输出分别等到 `spec.replicas=4` 和 `status.readyReplicas=4`，最后的 `get rs` 显示 `4 4 4`。这说明直接改 RS 只是制造了一次漂移，控制器会把它拉回去；要扩缩容就改 Deployment，要让 Deployment 完全不管这些 RS，只能不用 Deployment、直接管理 RS。

> **旧资料提示**：旧教程里常见的“更新 Deployment 会删除并重建所有 Pod”只对 `strategy.type: Recreate` 成立。`RollingUpdate` 是默认值，它逐步扩新 RS、缩旧 RS，不会先把所有 Pod 删光；`Recreate` 才是先删全部旧 Pod 再建新 Pod，20.4 会实际看到这段停机。

所有权还有两个容易踩的约束。第一，`.spec.selector` 必须匹配 `.spec.template.metadata.labels`，否则 API 直接拒绝创建；第二，`apps/v1` 的 Deployment 创建后 `.spec.selector` 不可变，改它只能删掉重建。`pod-template-hash` 是控制器自己加的，不要手改，也不要让别的控制器用重叠的 selector 去选同一批 Pod；多个控制器抢同一批 Pod 时，Kubernetes 不会阻止，行为会变得不可预测。20.7 会用一个 selector 和模板标签不一致的清单，看 API 的报错。

`kubectl rollout status` 也能用来判断发布卡住：如果新 RS 迟迟没有可用副本，命令会一直打印 `Waiting for deployment ...`，直到 `progressDeadlineSeconds` 到期才报错退出。20.3 会看到这个失败路径。

Deployment 的 `strategy.type` 默认就是 `RollingUpdate`，`maxSurge` 和 `maxUnavailable` 的默认值都是 25%。这两个值都可以写成整数或百分比：`maxUnavailable` 的百分比按期望副本数向下取整，`maxSurge` 的百分比向上取整。以 2 个副本为例，默认的 25% 会得到 `maxUnavailable=0`、`maxSurge=1`，也就是滚动时最多 3 个 Pod、至少 2 个可用；3 个副本时 25% 分别得到 0 和 1，范围是 3 到 4 个；4 个副本时两个方向都是 1，范围是 3 到 5 个。本章为了把两个方向都讲清楚，显式设成了 1/1，范围变成 1 到 3 个 Pod。两个值不能同时为 0，否则控制器没有任何腾挪空间，API 会拒绝这种配置。

记不住字段默认值时，用 `kubectl explain deployment.spec.strategy.rollingUpdate` 在本机查，输出跟着集群版本走，比翻旧教程可靠。`minReadySeconds: 5` 的含义是：新 Pod 的容器 Ready 之后，还要连续 5 秒没有容器崩溃，才算 Available。它不会让 Pod 晚一点被 Service 选中，Service 仍然按 Ready 条件摘挂端点；它影响的是 Deployment 什么时候认为“这个新副本已经稳定”，从而决定是否继续缩旧 RS。没有它，一个新 Pod 刚 Ready 就被计入可用，探针偶发失败时控制器可能已经继续往下走。`progressDeadlineSeconds: 30` 是本章为了在示例里快速看到失败而设的；默认是 600 秒，必须大于 `minReadySeconds`，生产上要按最慢的启动时间留足。

示例里的客户端 Pod 用 Service 名字 `http://api:8080/healthz` 连续请求，每 100 ms 一次。输出最后一行里 `fail=0`：滚动更新期间每一次请求都拿到了 200。这个结果说明 Service 在整段替换过程中始终有可用的后端；它不代表“绝对不会 503”，只代表这次 2 副本、1/1、带 readinessProbe 的组合没有出现无后端的时间窗。把 `maxUnavailable` 改成 2，或者把 readinessProbe 去掉，结论就会变。

`rollout status` 的输出把过程分成了几段：先等 Deployment 观察到 spec 更新，然后等新 RS 的第一个 Pod 可用，再等旧 RS 的 Pod 终止。中间的 `1 old replicas are pending termination...` 不是卡住，而是控制器在等旧 Pod 走完优雅终止。`kubectl rollout status` 只报它关心的状态，不会逐条列出每个 Pod；要看“新旧交替”的顺序，应该读 Deployment 的 Events，而不是用 `kubectl get pods -w` 盯屏。发布前可以先用 `kubectl diff -f api-deployment.yaml` 看清单和集群的差异，确认只改了想改的字段；如果要在一个发布里改多处模板，`kubectl rollout pause` 暂停，改完再 `resume`，暂停期间控制器不会因为 `progressDeadlineSeconds` 报超时，恢复后所有改动合成一次滚动更新。用 `kubectl set image` 适合临时改一个镜像；如果 Deployment 由清单管理，下一次 `kubectl apply` 会把 replicas 和镜像一起覆盖，手工 scale 的副本数也会丢。发布流水线应该改清单再 apply，`set image` 只用于交互式排障。

`get rs` 现在有 3 个 RS：两个更早的已经缩到 0，当前的那个是 2 个副本。`get pods --show-labels` 里只剩两个 Running 的 Pod，标签都带当前 RS 的 `pod-template-hash`；旧 hash 的两个 Pod 在 `kubectl wait --for=delete` 之后才消失。Deployment 的 Events 最后四行就是这次替换的顺序：新 RS 从 0 扩到 1，旧 RS 从 2 缩到 1，新 RS 从 1 扩到 2，旧 RS 从 1 缩到 0。按控制器的计数，峰值时是 3 个 Pod，正好等于 `replicas + maxSurge`；旧 RS 最少保留 1 个，正好等于 `replicas - maxUnavailable`。

这里还有一个经常被忽略的细节：Kubernetes 在计算 `availableReplicas` 时不算正在终止的 Pod，所以滚动过程中实际存在的 Pod 总数可能短暂超过 `replicas + maxSurge`，直到旧 Pod 的 `terminationGracePeriodSeconds` 走完。示例里 `kubectl wait --for=delete` 就是在等这两个正在终止的旧 Pod；如果只看 `kubectl get pods` 的某一帧，会看到 3 个甚至 4 个 Pod，但其中一部分已经是 Terminating。

> **旧资料提示**：旧教程里常用 `kubectl get pods -w` 展示滚动更新，更老的做法是用 `kubectl rolling-update` 做发布。后者在 kubectl 1.37 里已经不存在（实测报 `unknown command`），现在用 Deployment 加 `kubectl rollout`；`-w` 的输出依赖你按下的时机，也不适合放进自动化脚本，Deployment 的 Events 已经按顺序记录了每一次 `ScalingReplicaSet`，`kubectl rollout status` 则给出可判断成功失败的单行结论。

把 `maxSurge` 设为 0、`maxUnavailable` 设为 1，滚动时不会多建 Pod，但会先让一个旧 Pod 下线；把 `maxUnavailable` 设为 0、`maxSurge` 设为 1，则先建新 Pod、等它可用再删旧的，副本数始终不少于期望值，代价是需要节点上多放一个 Pod 的容量。前者适合节点资源紧张、但能接受短暂少一个副本的服务；后者适合不能少副本的服务。两者都要求 readinessProbe 真的能反映“可以接流量”，否则参数只是纸面上的边界。

## 20.3 回滚与历史

发布坏镜像时，Deployment 不会立刻把旧 Pod 全部换掉，它会先按滚动策略创建新 Pod；新 Pod 拉不到镜像，就一直不 Ready，旧 Pod 继续服务。`progressDeadlineSeconds` 到期后，控制器把 `Progressing` 条件置为 `False`、原因是 `ProgressDeadlineExceeded`，但不会自动回滚，也不会再继续扩新 RS。

```console
{{#include code/ch20/20_3_rollout_undo.out}}
```

`shorty:0.9` 这个 tag 在节点上不存在，`imagePullPolicy: IfNotPresent` 让 kubelet 去仓库拉，仓库里也没有这个镜像，于是新 Pod 进入 `ImagePullBackOff`；在退避之前，它的状态可能短暂显示为 `ErrImagePull`。`rollout status` 在 30 秒的进度期限后报 `error: deployment "api" exceeded its progress deadline` 并以 1 退出；这正是脚本和 CI 应该捕获的信号。命令里的 `--timeout=90s` 是 kubectl 客户端愿意等多久，Deployment 的 `progressDeadlineSeconds` 是服务端判断“多久没进展”的期限；客户端超时调得比服务端短，就会在条件变成 `ProgressDeadlineExceeded` 之前先退出。`get pods` 里两个新 Pod 都是 `ImagePullBackOff`，一个旧 Pod 还在 Running；`describe` 的 `Progressing` 条件是 `False/ProgressDeadlineExceeded`，`Available` 仍然是 `True/MinimumReplicasAvailable`，因为旧副本还撑着一个可用实例。控制器停在这里，不会把最后一个旧 Pod 删掉。

`rollout history` 的 `CHANGE-CAUSE` 来自 `kubernetes.io/change-cause` 注解。文档说这个值在 revision 创建时从 Deployment 的注解复制过去；实际输出里 revision 2 也显示成 `rolling update to shorty:0.2`，revision 3 和 4 都显示 `bad image shorty:0.9`；同样的 cause 出现在两个 revision 上，`CHANGE-CAUSE` 在这些 revision 上不是发布当时的快照。把它当成“发布说明的索引”可以，当成不可篡改的审计记录不行；要确认某一版到底改了什么，用 `rollout history --revision=N` 看模板详情，真正的发布记录放在 CI、Git 提交或单独的发布系统里。

回滚用 `kubectl rollout undo deployment/api`，默认回到上一个 revision。`rollout undo` 只回滚 Pod 模板，不回滚 `.spec.replicas`；如果发布过程中手动扩过副本，回滚不会把副本数改回去。要回到指定版本用 `--to-revision=2`，revision 号从 `rollout history` 里读；`--revision=2` 加在 `rollout history` 后面则是看那一版的 Pod 模板详情，不是回滚。回滚本身也是一次滚动更新，所以 `rollout status` 仍然要等新 RS 的 Pod 可用；如果回滚后的模板也起不来，进度期限仍然会报 `ProgressDeadlineExceeded`，不会因为“这是回滚”就跳过检查。刚 `undo` 完时 Deployment 的 `Progressing` 条件可能还是上一次的 `False/ProgressDeadlineExceeded`，立刻跑 `rollout status` 会直接报同样的错；示例先等 `Progressing` 条件回到 `True`，再等 status，避免把旧条件当成新发布的结果。

这次 `undo` 输出了一条警告：这个 Deployment 之前由 `kubectl apply` 管理，回滚不会更新 `kubectl.kubernetes.io/last-applied-configuration` 注解，下一次 `kubectl apply` 可能把回滚结果覆盖掉。生产上更稳的做法是从 Git 里取出旧版本的清单重新 apply，或者在回滚后同步更新 Git 和 last-applied 注解；不要只看 `rollout undo` 成功就以为状态已经收敛。

`rollout restart` 不换镜像，它给 Pod 模板加一个 `kubectl.kubernetes.io/restartedAt` 注解，触发一次新的滚动更新。示例最后一条 `jsonpath` 显示镜像仍然是 `shorty:0.2`，但 Pod 已经被新的 RS 重建。它适合“配置在外部、Pod 需要重新读取”的场景，比如挂载的 ConfigMap 变了但进程不监听文件变化；如果镜像也变了，应该用 `set image` 或 apply 新清单，restart 不会帮你换镜像。

> **旧资料提示**：旧教程里用 `kubectl ... --record` 自动把命令写进 `CHANGE-CAUSE`。官方文档已经把 `--record` 标为弃用、说它会在未来版本移除；kubectl 1.37 的 `kubectl set image --help` 里已经没有这个参数。现在要在发布前显式 `kubectl annotate deployment/api kubernetes.io/change-cause="..."`，或者由 CI 写入这个注解。

`revisionHistoryLimit` 默认保留 10 个旧 RS，超过的会被垃圾回收；把它设为 0 会清掉历史，之后不能再回滚。这个回收只在 Deployment 进入 complete 状态之后才开始；如果发布一直卡在失败状态，旧 RS 可能比这个限制多，`get rs` 会越积越长。旧 RS 不是免费的：每个都占 etcd 里的对象，也会让 `kubectl get rs` 越来越长；但它保留着那一版的 Pod 模板，是 `--to-revision` 能工作的前提。回滚演练要定期做，否则真出事时才发现历史已经被清理或权限不够。

## 20.4 Recreate 与停机取舍

Recreate 的规则很简单：升级时先杀掉所有旧 Pod，等它们都终止，再创建新 Pod。它不读 `maxSurge`/`maxUnavailable`，因为这两个参数只属于 RollingUpdate。下面的例子把 api 的策略改成 Recreate，用一个客户端持续请求，再把镜像从 `shorty:0.2` 换回 `shorty:0.1`。

```console

```

`kubectl patch` 把 `strategy.type` 换成 `Recreate`，同时移除了 `rollingUpdate` 字段，避免留下一个对 Recreate 无意义的配置。`set image` 触发更新后，`rollout status` 先报 `0 out of 2 new replicas have been updated`，再报 `0 of 2 updated replicas are available`，最后成功；这段输出对应的就是“旧 Pod 已经全删、新 Pod 还没起来”的空窗。客户端的 `fail` 计数不为 0，`ok` 计数是空窗前后的成功请求；失败的那些请求在客户端看来是 `connection refused`，因为 Service 的 EndpointSlice 里没有 Ready 的后端，kube-proxy 直接拒绝了连接。数字不大，但对一个持续有流量的服务来说，任何一次失败都是用户看到的错误页。只看 `rollout status` 是发现不了这段空窗的：它最终会返回成功，因为新 Pod 确实起来了；衡量停机时间要用客户端视角的请求计数，或者看 Service 的端点数量随时间的变化。

`get pods` 最后只剩两个新 Pod，旧的已经在 Recreate 的第一阶段被删干净；它们属于同一个新 RS，名字里的 hash 相同。Recreate 的“先删后建”只对升级过程成立。官方文档特别说明：如果你手动删掉一个 Pod，ReplicaSet 会立刻创建替代 Pod，即使旧 Pod 还在 Terminating；Recreate 不保证“任意时刻最多一份”。需要严格的“最多一份”语义，应该用 StatefulSet 或应用层的单例锁，而不是把 Recreate 当成互斥机制。

Recreate 适合两类版本：新旧版本不能同时存在，或者同时存在会破坏数据的。例如数据库 schema 只能由新版本迁移、旧版本不能识别新列；或者某个单例进程同一时刻只能有一个实例持有锁。这类升级本来就要停机，RollingUpdate 只会把“两个版本同时写同一份数据”的风险藏起来。无状态服务应该用 RollingUpdate；有状态服务应该看 StatefulSet 的有序策略，第 22 章会把 postgres 换成 StatefulSet 再讲。

示例最后把策略恢复成 RollingUpdate，并显式写回 1/1。策略变更本身不会触发滚动更新，因为没有改 Pod 模板；下一次改镜像时才会按新策略执行。生产上如果从 Recreate 切回 RollingUpdate，最好在维护窗口里做，确认新策略已经写入 spec 后再发下一次版本。恢复后可以用 `kubectl get deployment api -o yaml` 看 `spec.strategy`，确认 `rollingUpdate` 字段和类型同时存在，不要只改类型留下一个空的策略对象。

## 20.5 DaemonSet：每个节点一个

DaemonSet 的清单结构和 Deployment 很像：`spec.selector` 选 `app.kubernetes.io/name: node-agent`，`spec.template` 里的 Pod 必须带同样的标签，selector 创建后也不能改；区别在副本语义，Deployment 关心“总共几个副本”，DaemonSet 关心“每个节点有没有一个”。日志采集、监控 agent、CNI 插件这类工作负载必须落在每台机器上，不能接受调度器把两个副本都塞到同一个节点，也不能因为节点扩容就漏掉新机器；DaemonSet 控制器就是为这个语义存在的。如果只想覆盖一部分节点，可以在 Pod 模板里写 `nodeSelector` 或 `nodeAffinity`，控制器只给匹配的节点创建 Pod；节点标签变了，DaemonSet 会补上新增的匹配节点，也会删掉不再匹配的节点上的 Pod。

```console
{{#include code/ch20/20_5_daemonset_nodes.out}}
```

`kubectl apply` 创建 DaemonSet 后，`rollout status` 报 `0 of 3 updated pods are available`，然后 `1 of 3`，最后成功；`get daemonset` 的 `DESIRED/CURRENT/READY/UP-TO-DATE/AVAILABLE` 都是 3。`get pods -o wide` 的三行覆盖了 `shorty-worker`、`shorty-control-plane`、`shorty-worker2` 三个节点，每个节点正好一个。控制面节点上也有，是因为清单里显式加了 `node-role.kubernetes.io/control-plane:NoSchedule` 的 toleration；不加这条，控制面的污点会把 Pod 挡掉，只剩两个 worker 有 agent。

`kubectl get daemonset` 的 `DESIRED` 是符合条件的节点数，`CURRENT` 是已经创建 Pod 的节点数，`READY` 是 Pod Ready 的节点数；`NODE SELECTOR` 为 `<none>` 表示没有 `nodeSelector`，控制器按 nodeAffinity 给每个节点发一个 Pod。`updateStrategy=RollingUpdate`、`maxUnavailable=1` 表示更新模板时一次最多让一个节点上的 agent 不可用；DaemonSet 的 `maxSurge` 默认是 0，也就是先删旧 Pod 再建新 Pod，不会在节点上同时跑两个 agent。这个默认值和 DaemonSet 的定位有关：很多 agent 要绑 hostPort、挂宿主目录或占固定资源，多一个副本可能直接冲突。要减少同时中断的节点数，可以调小 `maxUnavailable`；要做到零中断，需要 `maxSurge > 0`，让新 Pod 先起来再删旧的，但这要求节点上能同时容纳两个 agent。

最后一段 `jsonpath` 读的是每个 Pod 的 `spec.affinity.nodeAffinity`：三行都显示 `metadata.name=<节点名>`，`scheduler=default-scheduler`。DaemonSet 控制器先为每个符合条件的节点创建 Pod，并写入一条只匹配该节点名的 nodeAffinity；Pod 创建后由默认调度器接手，调度器把 Pod 绑定到目标节点，写入 `.spec.nodeName`。这条链路今天看起来理所当然，但旧版本不是这样：`ScheduleDaemonSetPods` 特性门控在 1.11 是 alpha，1.12 进入 beta 并默认开启，1.17 转为 stable；在此之前，DaemonSet 控制器直接写 `spec.nodeName`，绕过调度器。

> **旧资料提示**：旧教程说“DaemonSet 直接写 `spec.nodeName`，不经过 scheduler”。这个说法在 1.12 以前成立；今天控制器用的是 nodeAffinity，真正绑定节点的是默认调度器。绕过调度器意味着不经过资源过滤、亲和性和抢占，这在节点资源紧张时会出问题。

DaemonSet 还会自动加一组 toleration，让 Pod 能落在 `not-ready`、`unreachable`、`disk-pressure`、`memory-pressure`、`pid-pressure` 和 `unschedulable` 的节点上；`hostNetwork: true` 的 DaemonSet 还会加 `network-unavailable`。这些自动容忍是为了让节点级 agent 在节点还没完全 Ready 时也能启动，避免“网络插件没起来 → 节点不 Ready → 网络插件没地方跑”的死锁。自己加的 toleration 只负责业务污点，比如控制面或专用节点。

DaemonSet 的 Pod 也占节点容量，调度器按 requests 判断节点放不放得下；requests 写得太小，节点会先被排满，运行时再因为实际用量超限被驱逐。一个 requests 很小的 agent 乘以几百个节点，就是几百份 CPU 和内存；如果 agent 有短暂的内存峰值，节点上的普通 Pod 可能先被驱逐。上线前要把 DaemonSet 的 requests 算进节点可分配资源，并给它设 limit；不要让“每个节点一个”变成“每个节点都超卖”。

## 20.6 PDB 与自愿中断

PDB（PodDisruptionBudget，干扰预算）保护的是“自愿中断”：`kubectl drain`、节点维护、集群缩容这些由人或控制器主动发起的驱逐。节点宕机、内核 panic、OOM 这类非自愿中断，PDB 挡不住；它只能保证在有人主动驱逐时，可用副本数不低于预算。

```console
{{#include code/ch20/20_6_pdb_block_drain.out}}
```

`minAvailable: 2` 和 2 个副本组合起来，`ALLOWED DISRUPTIONS` 是 0：再驱逐任何一个 api Pod，可用数都会降到 1，低于预算。这个 0 是控制器根据 `currentHealthy`、`desiredHealthy` 和 `expectedPods` 算出来的，不是手写的字段；Pod 数量或健康状态一变，它就会跟着变。`kubectl drain` 先把节点标记为 `SchedulingDisabled`（输出里的 `node/... cordoned`），然后对节点上的 Pod 调用 Eviction API。api Pod 的驱逐请求被拒绝，输出里 kubectl 每隔 5 秒重试一次，10 秒超时后放弃；错误信息是 `Cannot evict pod as it would violate the pod's disruption budget.`。这里的 `--timeout=10s` 是 kubectl drain 自己等多久，不是 PDB 的有效期；把超时调长，kubectl 会继续重试，但预算不放开就永远不会成功。不要为了让 drain 返回成功就删掉 PDB 或直接删 Pod，那等于放弃预算保护。节点没有自动恢复可调度，`get node` 里仍然是 `Ready,SchedulingDisabled`，要手动 `kubectl uncordon`。

`--ignore-daemonsets` 是 drain 必需的：DaemonSet 的 Pod 被驱逐后，控制器会立刻在同一个节点上重建，drain 永远清不空这个节点；kubectl 用这个参数跳过它们。输出里的 `Warning: ignoring DaemonSet-managed Pods: ... shorty/node-agent-...` 就是在说这件事。这个 PDB 的 selector 只匹配 api，DaemonSet 的 Pod 不在预算里，也不应该被 drain 当成普通工作负载。

PDB 的 selector 如果写成空 map `{}`，会匹配命名空间里的所有 Pod；这通常不是想要的效果，除非你确实要给整个命名空间设一个总预算。PDB 只保护“有控制器管理、且 PDB selector 能匹配到”的 Pod。它通过 Pod 的 `ownerReferences` 找到管理工作负载，再读工作负载的 `.spec.replicas` 来算期望副本数；所以 PDB 的 selector 要和 Deployment 的 selector 对得上，否则预算算不到这些 Pod。`minAvailable` 和 `maxUnavailable` 只能选一个；百分比会向上取整，7 个 Pod 配 `minAvailable: 50%` 会要求 4 个可用，而不是 3 个。这里的 `maxUnavailable` 和 Deployment 滚动更新里的 `maxUnavailable` 同名，但语义不同：前者是 PDB 允许的“自愿驱逐导致的不可用数”，后者是 Deployment 在发布过程中允许的“不可用副本数”。PDB 不会阻止 Deployment 的滚动更新，但滚动更新期间被删的 Pod 会计入预算；所以发布和维护撞在一起时，留给 drain 的余量会更小。

`unhealthyPodEvictionPolicy` 控制“不健康但还在 Running 的 Pod”能不能被驱逐。默认是 `IfHealthyBudget`：应用已经被打断时，尽量让这些 Pod 有机会恢复；代价是 CrashLoopBackOff 的 Pod 可能把 drain 永久卡住。设成 `AlwaysAllow` 可以让 drain 跳过这些不健康的 Pod，适合节点维护场景。这个字段在 1.26 是 alpha、1.27 进入 beta、1.31 转为 stable；老集群上可能看不到。

`minAvailable: 2` 加 2 个副本是“零自愿中断”的极端配置，只适合“宁可维护做不了，也不能少一个副本”的场景。真要可运维，至少要有 3 个副本、预算留出 1 个的余量；单副本加 `minAvailable: 1` 等价于不允许任何驱逐，节点永远 drain 不掉。PDB 也不能防“有人直接 `kubectl delete deployment`”：删除工作负载绕过 Eviction API，PDB 不会拦。PDB 的 `status` 里还有 `currentHealthy`、`desiredHealthy`、`expectedPods` 三个数，排障时先看它们是否和 `kubectl get pods` 对得上；对不上通常是 selector 写错或 Pod 还没 Ready。示例最后删掉 PDB，是为了让集群回到本章终点的“无 PDB”状态；生产上不应该在维护前随手删预算，除非你已经准备好接受停机。

## 20.7 排障：滚动更新卡住与 selector 不匹配

滚动更新卡住时，`kubectl rollout status` 会一行行重复 `Waiting for deployment "api" rollout to finish: 1 out of 2 new replicas have been updated...`。这句话只说明“新 RS 还没有达到期望”，不说明原因；先看 `kubectl get events --field-selector involvedObject.name=api --sort-by=.lastTimestamp`，再依次看三个地方：`kubectl describe deployment api` 的 `Conditions` 和 `Events`，`kubectl get pods` 的 `STATUS`，以及新 Pod 的 `kubectl describe pod`。`ProgressDeadlineExceeded` 是结果，不是原因；真正的原因通常在 Pod 的 `ImagePullBackOff`、`CrashLoopBackOff`、`Pending` 或探针失败里。

镜像拉不到时，`get pods` 的 `STATUS` 是 `ErrImagePull` 或 `ImagePullBackOff`，`describe pod` 的 Events 会写 `Failed to pull image` 和具体的 401/404/超时。如果容器启动后立刻退出，`kubectl logs` 只看得到当前这次尝试的日志；上一次崩溃的日志用 `kubectl logs --previous`，结合 `describe pod` 的 `Last State` 才能看到退出码。镜像名拼错、tag 不存在、私有仓库没配 imagePullSecret、节点到仓库的网络不通，都会走到这里。修法是改对镜像，然后 `kubectl rollout undo` 回到上一个 revision，或者把清单改对后重新 apply；不要只把 `progressDeadlineSeconds` 调大，那只会让失败来得更晚。

容器起来了但进程退出，`STATUS` 是 `CrashLoopBackOff`，`describe pod` 的 `Last State` 会给出退出码和原因，`kubectl logs` 给出应用日志。探针配置错也会让 Pod 一直不 Ready：readinessProbe 的路径、端口、`initialDelaySeconds` 不对，Pod 会 Running 但一直 `0/1`，Deployment 的新 RS 就永远凑不齐可用副本。从一个有 curl/wget 的 Pod 手工请求探针路径，或者看 `describe pod` 的 `Warning Unhealthy` 事件，确认是应用没起来还是探针写错。

修好之后，`kubectl rollout undo` 只适合“上一版是好的、这一版要整体撤回”；如果只是探针参数写错、镜像本身没问题，改清单再 apply 更直接。回滚和修复都要再跑一次 `kubectl rollout status`，确认新 RS 的可用副本数真的到了期望值，而不是只看命令退出码。

第二类故障发生在 apply 阶段，Pod 还没创建就被 API 拒绝：

```console

```

`api-bad-selector.yaml` 的 `selector` 选的是 `app.kubernetes.io/name: api`，Pod 模板标签却是 `app.kubernetes.io/name: shorty-api`，API 直接报 `selector does not match template labels`，对象没有创建。把模板标签改成 `api` 之后，同一个名字的 Deployment 才能创建成功，`rollout status` 走完，`get deployment` 显示 `1/1`；示例随后把它删掉，集群里只剩原来的 `api`。

错误信息里的两个 map 就是全部线索：左边是 `spec.selector.matchLabels`，右边是 `spec.template.metadata.labels`，报错文本会把不匹配的那个值打印出来；先把两个 map 逐键对齐，再谈别的。这个错误在第一次创建时最容易修：改 selector 或改模板标签都行。已经创建的 Deployment 不能改 selector，`apps/v1` 把它当成不可变字段；这时只能改模板标签去匹配 selector，或者删掉 Deployment 重建（重建会删掉它拥有的 Pod，除非用 `--cascade=orphan` 留下它们）。示例里的 `api-bad-selector` 也用了和 api 相同的 selector，只用于验证校验错误，创建后立刻删掉；生产里不要让两个 Deployment 的 selector 重叠，重叠时控制器会抢同一批 Pod，行为不可预测。

`selector does not match template labels` 也可能在 `kubectl apply` 更新已有 Deployment 时出现：有人只改了 selector，没改模板标签。因为 selector 不可变，API 会先报不匹配；即使两者都改了，也会因为 selector 变更被拒绝。遇到这种报错，先看 `spec.selector.matchLabels` 和 `spec.template.metadata.labels` 两个 map，确认哪一边少了键，而不是反复 apply 同一个清单。

## 上生产前

至少 2 个副本，并且给这个工作负载配 PDB；单副本配 `minAvailable: 1` 等于不允许任何自愿驱逐，节点维护会永远做不完。PDB 的预算要留出一个副本的余量：3 副本配 `minAvailable: 2` 可以轮换，2 副本配 `minAvailable: 2` 就是本章的零中断配置，只适合“维护可以等，副本不能少”的场景。

`maxUnavailable` 不要设成 0 却不给 `maxSurge`；两个都为 0 时控制器没有腾挪空间，滚动更新根本不会开始。反过来，`maxUnavailable` 设得太大，比如等于副本数，滚动更新会一次删光旧 Pod，和 Recreate 没有区别。用 `maxSurge` 换可用性，用 `minReadySeconds` 换稳定，两者要一起看。

readinessProbe 要和 `minReadySeconds` 一起用。探针负责“这个 Pod 现在能不能接流量”，`minReadySeconds` 负责“它稳定了多久才算数”；只有探针没有 `minReadySeconds`，新 Pod 刚 Ready 就可能被算作可用；只有 `minReadySeconds` 没有探针，控制器等的只是一个永远 Ready 的假信号。`progressDeadlineSeconds` 要大于最慢一次启动的时间，默认 600 秒对大多数服务够用，但批处理型或要拉大镜像的服务可能不够。

发布用 digest，不要只用 tag。`shorty:0.2` 这个 tag 可以被重新推到同一个名字上，下一次拉取就换成了另一份镜像；`shorty@sha256:...` 把内容和名字绑定，回滚记录也能对得上。每次发布前写 `kubernetes.io/change-cause`，但不要把它当审计日志；真正的发布记录放在 CI 或 Git 里。回滚演练要定期做，确认 `rollout history` 还在、权限还在、镜像还在。

DaemonSet 要显式容忍控制面污点和专用节点污点，否则新加的节点上不会跑 agent；但容忍越多，agent 越可能落到不该落的地方，污点和容忍要成对管理。DaemonSet 的 requests 要算进节点容量：每个节点一份，乘以节点数就是集群级开销；给 agent 设 limit，避免它在某个节点上把普通 Pod 挤掉。

Recreate 只在“新旧版本不能并存”时用，并且要接受停机；无状态服务用 RollingUpdate，有状态服务用 StatefulSet 的有序策略。不要让两个 Deployment 的 selector 重叠，selector 创建后不可变，规划时就把标签定好；需要改 selector 时，删掉重建并接受 Pod 被替换的代价。

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `kubectl rollout status deployment/api` | 等滚动更新完成 | 成功退出 0；`ProgressDeadlineExceeded` 时退出非 0 |
| `kubectl rollout history deployment/api` | 看 revision 和 `CHANGE-CAUSE` | `--revision=N` 看单版详情；历史存在 RS 里 |

| `kubectl rollout restart deployment/api` | 不换镜像强制重建 | 给模板加 `kubectl.kubernetes.io/restartedAt` |
| `strategy.type` | 替换策略 | `RollingUpdate`（默认）或 `Recreate` |
| `maxSurge` / `maxUnavailable` | 滚动更新的上下界 | 默认各 25%；百分比 surge 向上取整、unavailable 向下取整；不能同时为 0 |
| `minReadySeconds` | 新 Pod 稳定多久算 Available | 默认 0 |
| `progressDeadlineSeconds` | 多久没进展就报失败 | 默认 600；必须大于 `minReadySeconds` |
| `revisionHistoryLimit` | 保留多少个旧 RS | 默认 10；设为 0 不能回滚 |
| DaemonSet `updateStrategy.rollingUpdate.maxUnavailable` | 一次更新几个节点 | 默认 1；`maxSurge` 默认 0 |
| PDB `minAvailable` / `maxUnavailable` | 自愿中断的预算 | 二选一；百分比向上取整 |
| `unhealthyPodEvictionPolicy` | 不健康 Pod 能否驱逐 | `IfHealthyBudget`（默认）或 `AlwaysAllow`；1.31 GA |
| `kubectl drain NODE --ignore-daemonsets` | 清空节点 | 遵守 PDB；DaemonSet Pod 被跳过 |

本章结束时：`Deployment api` 2 个副本，镜像 `shorty:0.1`；`DaemonSet node-agent` 在 3 个节点上各 1 个 Pod；没有 PDB，3 个节点都处于可调度状态。下一章在这个状态上加入 postgres、redis、worker 和一次性 Job。
