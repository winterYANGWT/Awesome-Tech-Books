# 第 2 章 镜像：层、内容寻址与 OCI 格式（containerd 镜像存储）

第 1 章把容器拆成了 namespace、cgroup 和 rootfs 三件事，其中 rootfs 的来源就是镜像。到了这一章，问题变成：镜像里到底装了什么？为什么 `shorty:0.1` 在 `docker image ls` 里的 `CONTENT SIZE` 只有几 MB，`DISK USAGE` 却大好几倍？为什么 Dockerfile 里写一句 `rm` 删掉一个 10 MB 的文件，新镜像不但没有变小，磁盘占用还可能更大？还有，`latest` 标签到底指向哪个镜像，为什么同一个标签今天拉到的内容和上周不一样？

这些问题的答案不在 `docker build` 的黑盒里，而在几个 JSON 和一堆 blob 里：manifest 说明“这个镜像由哪个 config、哪些 layer 组成”，config 说明“这些 layer 解压后是什么、按什么顺序叠”，layer 则是真正的文件系统增量。理解这套结构之后，tag、digest、多架构镜像、`docker history`、`docker commit` 的行为都能对上号。

> **起点**：第 1 章结束时 lab 里没有长期容器。本章仍然不建集群；`setup.sh` 会拉取 `alpine:3.22`、`busybox:1.37`，并用 `src/code/app/api/Dockerfile` 构建 `shorty:0.1`。第一次构建要下载 Go 模块，之后会复用构建缓存。本章结束时同样没有长期容器。运行 `bash code/ch02/setup.sh` 可以把 lab 带到这个状态。

## 2.1 层、config 与 manifest：镜像不是 tar 包

把镜像 `docker save` 成一个 tar，再解开，会看到一个很像普通 tar 的目录。但镜像本身不是“一个打包好的根文件系统”，而是一组按内容寻址（content-addressable）的 blob 加几个描述它们的 JSON。描述关系分三层：

- **manifest**：一个很小的 JSON，列出这个镜像的 config blob 和每一层 layer blob 的 digest、大小、媒体类型。
- **config**：另一个 JSON，记录 `architecture`、`os`、`config`（Env、Cmd、Entrypoint 等）以及 `rootfs.diff_ids`。`diff_ids` 是每一层**解压后**的 tar 的 sha256。
- **layer**：真正的文件系统增量，通常是 tar 加 gzip 或 zstd 压缩。manifest 里记的 layer digest 是 **压缩后** blob 的 sha256，和 config 里的 diffID 不是同一个值。

`docker image inspect` 的 `RootFS.Layers` 就是 config 里的 `rootfs.diff_ids`。`shorty:0.1` 的镜像是从 `gcr.io/distroless/static-debian13:nonroot` 加上一个 `COPY` 构建出来的，所以它不是“两层”，而是 14 层：distroless 基础镜像自己就由 13 个层组成，最后才是复制 shorty 二进制的那一层。

再看 `docker save` 出来的目录。`index.json` 指向一个 OCI image index；这个 index 里有两条 manifest：一条是 `linux/amd64` 的镜像，另一条是 `unknown/unknown` 的 attestation（BuildKit 默认生成的构建证明）。真正的 amd64 manifest 里，`config` 是一个 digest，`layers` 是 14 个 digest。这一层的 `mediaType` 是 `application/vnd.oci.image.layer.v1.tar+gzip`，`size` 是压缩后的大小；所以你在 `docker image ls` 里看到的“大小”和 `docker image inspect` 里的 `Size` 不是同一把尺子。

最后一段把同一个 blob 算了两遍：直接对压缩文件做 sha256，得到 manifest 里第一层的 digest；用 `gzip -dc` 解压后再做 sha256，得到的值正好等于 config 里 `rootfs.diff_ids[0]`。两个值不同，但描述的是同一层，这就是 digest 与 diffID 的关系，也是“内容寻址”的含义：blob 的名字由内容算出来，内容一样，名字就一样。

一次 pull 的顺序也建立在这套结构上。运行时先取 tag 对应的 index 或 manifest，按里面的 descriptor 逐个请求 config 和 layer blob；每收到一个 blob，重新算一遍 sha256，和 descriptor 里的 digest 比对，再写入本地 content store。任何一个 blob 的内容和 digest 对不上，拉取就会失败（不同 registry 报 `digest mismatch` 或校验错误）；manifest 本身也由它的 digest 标识。所以 digest 不只是“名字”，还是完整性校验：你按 `name@sha256:...` 拉取时，拿到的内容必须能算出这个值。OCI 的 layer 媒体类型还有 `tar+zstd` 等变体，本例是 `tar+gzip`，所以能用 `gzip -dc` 解开；遇到 zstd 要换对应的解压器。

config 里的 `config` 字段（Env、Cmd、Entrypoint、Labels 等）是运行时默认值，它们不占文件系统层，但会留在镜像 config 里。把密码写进 `ENV` 不会让镜像变大多少，却会让任何拿到镜像的人都能在 `docker image inspect` 里读到；把密码写进 `ARG` 再在 `RUN` 里使用，值还可能出现在 `docker history` 的 `CREATED BY` 里。层的大小和安全不是一回事，2.6 之后的上生产前会再强调这一点。

内容寻址带来的直接结果是去重。两个镜像如果 `FROM` 同一个基础镜像，它们会引用同一批 layer digest；本地只需要存一份，拉取时也只需要下载缺的那几层。`shorty:0.1` 和 `shorty:dev` 共享层吗？几乎没有：前者的基础镜像是 distroless，后者来自 `golang:1.27.3-trixie` 的构建阶段，两者没有共同的 layer。真正共享层的是同一基础镜像的不同应用镜像，例如两个都从 `alpine:3.22` 开始构建的服务。判断是否共享，看 manifest 里的 layer digest，不要看镜像名字或 `docker history` 的 `SIZE` 列。

> **旧资料提示**：旧教程里说“镜像 ID 是 65 个十六进制字符”或“短 UUID”。实际是 64 个十六进制字符（256 bit），`docker image ls` 默认只显示前 12 位。镜像 ID、manifest digest、index digest 不是同一个概念，后面会分别看到。

## 2.2 OCI 镜像格式与 manifest list

2.1 里的三层结构不是 Docker 独有的。OCI（Open Container Initiative）的 image-spec 把 manifest、config、layer 和 index 定义成一套公开格式，Docker 镜像格式与它在这些字段上是兼容的：manifest 里的 `mediaType`、`config.digest`、`layers[].digest`，config 里的 `rootfs.diff_ids`，都是同一套语义。Docker 文档把多平台结构叫 **manifest list**，Kubernetes 文档和 OCI 规范叫 **image index**，指的是同一个东西：一个顶层 JSON，按 `platform` 列出若干 manifest 的 digest。

一个单平台镜像的顶层就是一个 manifest；一个多平台镜像的顶层是 index。`alpine:3.22` 是后者：它的 index 里有 `linux/amd64`、`linux/arm64/v8`、`linux/arm/v6` 等条目，每个条目指向一个独立的 manifest，每个 manifest 又有自己的 config 和 layer 集合。拉取时，Docker 或 containerd 先取 index，再按当前机器的 `os`/`architecture` 选一个 manifest，只下载那个 manifest 的 layer。

默认的 `imagetools inspect` 会打印 `Name`、`MediaType`、`Digest`，以及每个 manifest 的 `Platform` 和一堆注解；它适合人看，但为了显示注解会逐个拉取子 manifest，慢而且更容易碰到 registry 限流。`--raw` 只取 index 本身，CI 里做“有没有 arm64”这种判断足够了。`docker manifest inspect` 不经过 buildx，直接向 registry 要 manifest 或 index，适合在最小镜像的 CI runner 里用。

第二段是 `docker image ls --tree`。`--tree` 在 Docker 29.9 的 `docker image ls --help` 里仍标为 experimental，但输出结构已经能说明问题。第一行的 `alpine:3.22` 是顶层 index，它的 ID 就是 index digest 的前 12 位；下面每个平台行是 index 里的一个 manifest，ID 是 manifest digest 的前 12 位。`DISK USAGE` 和 `CONTENT SIZE` 只有 amd64、arm64 两行有值，因为 `setup.sh` 只拉取了这两个平台的 layer；其余平台在 index 里存在，但本地没有内容，所以显示 `0B`。这不是镜像坏了，而是按需拉取的结果。

第三段故意用 `--platform linux/arm64` 运行。容器启动到 `execve` 时，内核看到的是 AArch64 的 ELF，而当前节点是 x86-64，又没有注册 qemu/binfmt，于是返回 `exec format error`。这个错误和镜像内容损坏无关；在 arm64 机器上同一条命令会成功，在 amd64 上装了 binfmt 模拟器也可以运行（性能另说）。最后一段换回 `linux/amd64`，`uname -m` 输出 `x86_64`，证明同一个 tag 可以按 platform 选到不同的 manifest。

Kubernetes 里也是同一套选择逻辑，只是选择发生在节点上：kubelet 把 Pod 的镜像引用交给容器运行时，运行时按节点的 `os`/`architecture` 选 manifest。如果镜像没有对应平台的 manifest，Pod 会停在 `ImagePullBackOff` 或 `ErrImagePull`；如果选到了错误架构的二进制并且节点没有模拟器，容器会以 `exec format error` 退出。

多平台镜像不是手工 `docker tag` 出来的，而是一次构建出来的。`docker buildx build --platform linux/amd64,linux/arm64` 会让 BuildKit 为每个平台执行一遍构建，生成各自的 manifest，再写一个 index；`--push` 才能把整个 index 推到 registry；只在本机看单个平台时，再单独 `--load` 或 `docker pull --platform`。BuildKit 还会为构建结果生成 attestation manifest（就是输出里 `unknown/unknown` 的那条），所以 index 的条目数可能比平台数多。检查发布结果时，既要看到目标平台的条目，也要知道 attestation 不是可运行的镜像。

Dockerfile 里可以用 BuildKit 预定义的 `TARGETOS`、`TARGETARCH` 做交叉编译，让 builder 在原生平台编译出目标平台的二进制，避免为每个平台跑一遍 QEMU。生产上发布多架构镜像时，`docker buildx imagetools inspect` 或 `docker manifest inspect` 应该能看到每个目标平台的 digest，而不是只有一个 `unknown/unknown` 的 attestation。

## 2.3 containerd image store：Engine 29 的默认存储

Docker Engine 29.0 起，全新安装默认使用 **containerd image store**。从旧版本升级上来的 daemon 不会自动切换，仍然使用经典的 graph driver（通常是 `overlay2`），直到在 `daemon.json` 里打开 `features.containerd-snapshotter`。两种后端的镜像和容器在切换后会互相“看不见”，但数据还在磁盘上，切回去就能重新看到。这个默认值的变化是理解本章输出差异的前提。

containerd 不用“存储驱动”（storage driver）这个说法，而用 **snapshotter**。`overlay2` 是 Docker 经典 graph driver 的名字；`overlayfs` 是 containerd 的 snapshotter 名字，两者只差一个字母，但不是同一个组件。`docker info` 里同时给出 `Storage Driver` 和 `driver-type`，后者才是后端类型。

第一段里 `Storage Driver: overlayfs` 是给人看的名字，`driver-type` 是 `io.containerd.snapshotter.v1`，说明这个 daemon 走的是 containerd 的 snapshotter，而不是 `overlay2`。如果看到的是 `Storage Driver: overlay2` 且没有 `driver-type`，那就是经典 image store，`docker image ls` 的列和 image mount 的支持情况都会不一样；升级后尤其容易把两者混为一谈。

第二段是 Engine 29 的 `docker image ls`。列已经变成 `IMAGE / ID / DISK USAGE / CONTENT SIZE / EXTRA`，没有旧的 `SIZE`，更没有 `VIRTUAL SIZE`。`DISK USAGE` 是本地实际占用的空间，`CONTENT SIZE` 是镜像内容的大小；containerd 同时保留从 registry 收到的压缩 blob 和解压后的快照，所以前者通常大于后者。`shorty:0.1` 的 `CONTENT SIZE` 是个位数 MB，`shorty:dev` 是几百 MB，差的是 Go 工具链和构建阶段带进来的文件，不是 shorty 的代码。这也回答了开头的问题：两个镜像“看起来一样大”，可能只是 `CONTENT SIZE` 接近，解压后的快照和基础镜像完全不同。这些数字会随镜像是否已经解压、是否被容器引用而变化，比较时看列的含义，不要记绝对值。

`--tree shorty:0.1` 的输出里，顶层是 image，下面只有一个 `linux/amd64` 子行；子行 ID 是 manifest digest 的前缀，和 2.1 输出里 amd64 manifest 的 digest 前缀一致。输出里的 `docker image --help` 列出 `build`、`history`、`import`、`inspect`、`load`、`ls`、`prune`、`pull`、`push`、`rm`、`save`、`tag`，没有 `mount`。有些资料写 `docker image mount` 把镜像内容只读挂载，这个命令在 Docker 29 里不存在。实际做法是 `docker run --mount type=image,src=...,dst=...`，最后一段就是把 `busybox:1.37` 的根文件系统挂到 alpine 容器的 `/dbg`，再从 alpine 里读它的 `/bin`。这个挂载是只读的，源镜像必须已经在本地，且只在 containerd image store 下可用；调试没有 shell 的镜像时，可以拿它当工具箱。

containerd 的数据目录和 Docker 的 `Docker Root Dir` 是分开的。官方文档特别提醒：如果你把 Docker 的 data-root 改到大分区，containerd 的 content store 不会跟着搬，需要单独配置，否则镜像可能把根分区写满。从经典 image store 迁移时，旧镜像在新后端里是隐藏的，不是删除；要复用就先 `docker push` 到 registry，或者 `docker save` 成 tar 再 `docker load`。这也是为什么升级后 `docker image ls` 看起来“空了”，但 `/var/lib/docker` 的磁盘占用还在。

snapshotter 把每一层解压成一个 snapshot，容器启动时把镜像的 snapshot 按顺序叠成 lowerdir，再加一个可写的 upperdir。多个镜像引用同一个 layer digest 时，containerd 的 content store 只保留一份压缩 blob，解压后的 snapshot 也按 digest 复用。`docker image ls` 的 `DISK USAGE` 统计的是这些 snapshot 和 blob 的实际占用，因此同一个基础镜像被多个应用镜像使用时，数字不会简单相加。

Engine 29 的 `docker image ls` 默认是折叠视图，一个多平台镜像只占一行；`--tree` 才把它展开成顶层 index 加每个平台的 manifest。2.2 的 alpine 输出里，amd64 和 arm64 两行有内容，其余平台是 `0B`；到了 2.3 的 `shorty:0.1`，只有一个平台，所以只有一行。`EXTRA` 列在当前输出里是空的，先不要依赖它。要用脚本取这些数字，`docker image ls --format` 目前只暴露旧的 `Size` 字段，拿不到 `CONTENT SIZE` 列；需要看总量时用 `docker system df -v`；要精确到层，用 `docker image ls --tree` 或 containerd 的 `ctr` 工具（本章不展开），不要解析给人看的表格。

> **旧资料提示**：旧教程里的 `docker images` 有 `VIRTUAL SIZE` 列，`docker images -a` 还会列出构建中间层。现代输出是 `SIZE`（经典 store）或 `DISK USAGE`/`CONTENT SIZE`（containerd store）；BuildKit 不创建可启动的中间镜像，`-a` 也不会再列出一串构建步骤。

## 2.4 可写层与 copy-on-write

容器启动时，镜像的所有层都是只读的 lowerdir，containerd 在它们上面再加一个可写的 upperdir。容器里的 `/` 看到的是这些目录叠加后的 merged 视图。读一个只在 lower 里的文件，直接读 lower；第一次写一个已存在的文件，overlayfs 会把整个文件复制到 upper（copy-up），之后的写都落在 upper；删一个文件，不会去改 lower，而是在 upper 里放一个 whiteout 记录，让 merged 视图看不到它。

从宿主上看，一次 overlay 挂载有四个目录：`lowerdir` 是只读的镜像层，`upperdir` 是容器的可写层，`workdir` 是 overlayfs 内部用的临时目录，`merged` 是容器里看到的统一视图。删除一个**目录**时，upper 里放的不是针对每个文件的 whiteout，而是一个 opaque 标记，让整个目录在 merged 里不可见；删除单个文件才是 whiteout。容器删除后，upper 和 work 一起丢掉，lower 里的镜像层不受影响，所以“容器里删了文件”不会改镜像，除非你把它 commit 成新镜像。

这解释了一个反直觉现象：在 Dockerfile 的下一层删除上一层的大文件，镜像不会变小。删除只是多了一个 whiteout，上一层的数据仍然在 layer blob 里，仍然要占磁盘、仍然要被拉取。下面的例子把这一步做成可观察的。

所以“减小镜像”的正确做法不是 `RUN rm`，而是不要在上一层产生这个文件：用多阶段构建把编译产物复制到最终镜像，或者在同一个 `RUN` 里先下载、用完再删，让临时文件根本不进入任何一层。`RUN apt-get update && apt-get install ... && rm -rf /var/lib/apt/lists/*` 之所以有效，是因为这些操作在**同一层**里完成，中间状态不会单独成为一个 blob；拆成两条 `RUN` 就没有这个效果。

copy-up 还有性能边界。overlayfs 按文件复制，哪怕只改大文件的一个字节，第一次写也要把整个文件复制到 upper；数据库、日志这类写密集的目录应该用 volume，绕过 overlay。层数也有成本：经典 `overlay2` 驱动官方文档写“原生支持最多 128 个 lower 层”，超过这个数量要么合并层，要么换存储；containerd 的 `overlayfs` snapshotter 是另一套实现，具体上限取决于内核和发行版，需核实。工程上的做法是保持层数少、层序稳定，不要为了“每条命令一层”把镜像拆成几十层。

overlayfs 还共享 page cache：多个容器读同一个 lower 文件，内存里只有一份页缓存，读多写少的场景很省内存；代价是第一次写要 copy-up，写大文件会有明显的延迟尖峰。把写密集的目录放到 volume，既绕开 copy-up，也让备份和容量规划更清楚。overlayfs 只实现 POSIX 的一个子集，最典型的是 `rename(2)`：当源和目标不在同一层时，目录 rename 会返回 `EXDEV`（cross-device link），应用要自己退化成“复制再删除”。这也是为什么在容器里做大量文件操作、数据库写入或包管理时，直接把数据放在 overlay 上容易遇到奇怪的错误；把写密集的数据放到 volume，既避开 copy-up，也避开这些语义差异。

> **旧资料提示**：旧教程常用“在最后一层删掉缓存/文档”来瘦身，并展示 `docker images` 的体积下降。在分层文件系统里，删除只产生 whiteout，上一层的字节仍然在。要么在同一层里删，要么用多阶段构建只复制产物。

## 2.5 tag 是可变指针，digest 才是身份

`alpine:3.22` 里的 `3.22` 是 tag，`shorty:0.1` 里的 `0.1` 也是 tag。tag 是人类起的名字，它本身不包含内容；真正决定“拉到什么”的是 tag 解析到的 manifest digest（多架构时是 index digest）。同一个 tag 可以今天指向 alpine、明天指向 busybox，`docker tag` 在本地就能做到，registry 上重新 push 同名 tag 也一样。

digest 是内容算出来的，不能指向别的内容。`name@sha256:...` 这种写法把名字和 digest 绑在一起；如果同时写 tag 和 digest（`name:tag@sha256:...`），Kubernetes 和 Docker 都只用 digest，tag 只起注释作用。

digest 的格式是 `sha256:` 加 64 个小写十六进制字符。长度不对、出现非十六进制字符，Docker 会在解析引用时报 `invalid reference format`；格式正确但 registry 里没有这个 blob，才会报“找不到”。多架构镜像有两个层级的 digest：index 的 digest 和每个平台 manifest 的 digest。写 index digest 时，运行时还能按 platform 选；写某个平台的 manifest digest 时，就把平台也固定死了，换到另一种架构的节点上会拉不到或 `exec format error`。生产清单通常固定 index digest，除非你明确要某个平台。

有些 registry 提供“tag 不可变”策略，push 同名 tag 会被拒绝；这是 registry 侧的约束，不是 OCI 格式的保证。换一个 registry、换一个仓库，或者管理员关掉策略，tag 又可以移动。所以清单里写 digest 仍然是最可靠的做法；`imagePullPolicy` 只影响拉取时机，不会把可变 tag 变成不可变引用。

输出的最后两段把同样的思路用到本地构建的 `shorty:0.1`：`docker image ls --digests` 用 `REPOSITORY / TAG / DIGEST / IMAGE ID / ...` 这套列显示 `shorty@sha256:...`，`docker run` 直接写这个 digest 也能启动，不需要 tag。本地 tag 被覆盖不会改这个 digest；推到 registry 后，同一个 digest 仍然是这个名字，tag 只是另一个入口。

`latest` 不是一个特殊版本，它只是“没有写 tag 时的默认 tag”。`docker pull alpine` 等价于 `docker pull alpine:latest`，Kubernetes 里不写 tag 也按 `latest` 处理。`latest` 指向哪个 digest，取决于最后一次 push 或 tag 的人；它不保证最新，也不保证不变。生产清单里写 `latest`，等于把“这次到底部署了什么”交给 registry 的当前状态。

Kubernetes 的 `imagePullPolicy` 经常被误解。`Always` 的意思是“每次启动容器都让运行时去 registry 解析一次镜像引用”：如果写的是 tag，运行时会把这个 tag 解析成当时的 digest，再下载缺失的 layer；如果所有 layer 都在本地，它仍然可能复用缓存。所以 `Always` 保证的是“重新解析”，不是“内容一定和上次相同”。如果 tag 被移动，`Always` 会拉到新内容；如果写的是 digest，解析结果永远是这个 digest，tag 怎么动都不影响。Kubernetes 文档还规定了默认值：不写 `imagePullPolicy` 且用 digest 时是 `IfNotPresent`，用 `:latest` 或不写 tag 时是 `Always`，用其他 tag 时是 `IfNotPresent`；这个字段在对象第一次创建时就定下，之后改镜像引用不会自动改回来。

生产清单应该写成这样，tag 只放在注释里：

```yaml
containers:
  - name: api
    image: registry.example.com/shorty@sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef  # 示例值，实际用 imagetools 取
```

升级时改 digest，不改同名 tag；回滚时把 digest 改回去。这样 Git 里的清单、集群里跑的镜像、registry 里的 blob 三者能对上，也不会出现“同一份 Deployment 在不同节点拉到不同内容”的混合版本。多架构镜像的 digest 通常是 index digest，节点按 platform 选 manifest，但 index 的内容仍然由 digest 固定。

## 2.6 commit 与 Dockerfile：理解层可以，构建不行

`docker commit` 把容器的可写层（upperdir）固化成新镜像的一层，新镜像继承容器启动时的 config（Env、Cmd、Entrypoint 等），可以用 `-c` 改其中一部分。它适合一次性实验：起一个容器，改几个文件，看看 `docker diff` 和 `docker history` 会记录什么。它不适合作为构建方式：提交出来的镜像没有 Dockerfile 可 review，没有可重复的指令序列，也没有 BuildKit 的缓存和依赖图；下一个人只能从 `docker history` 的 `CREATED BY` 里猜当时发生了什么。


`docker diff` 的输出有四个标记：`A` 新增、`C` 修改、`D` 删除。这里除了三个文件，还多了一行 `C /app`：目录的元数据（mtime、size）也变了，所以目录本身被标记为修改。`D /app/delete.txt` 不是“文件从磁盘上消失”，而是 upperdir 里多了一个 whiteout；提交之后，这个 whiteout 会成为新镜像的一层，下层的数据仍然在。

`docker commit` 生成的镜像历史很说明问题：最上面一层的 `CREATED BY` 是 `sleep 300`，也就是容器启动时的命令，不是“我执行了 echo/rm”。COMMENT 是 `-m` 写的那句话，SIZE 只有十几 kB——新增和修改的文件、以及删除的 whiteout 被打进同一层。再往下是基础镜像的 `RUN` 层、`CMD` 和 `ADD` 层。commit 只记录“容器最后长什么样”，不记录“怎么变成这样”。

`docker export` 把容器的当前文件系统打成一个 tar（已经展开，不含层和镜像元数据）；`docker import` 再把这个 tar 变成一个单层镜像。输出里 `layers=1`，`cmd=null`，`entrypoint=null`：原来的 `CMD`/`ENTRYPOINT` 没了，`history` 也只剩一条 `Imported from -`。`export/import` 适合搬一个文件系统或做离线检查，不适合发布应用镜像；它把多阶段构建、层缓存、元数据全部压平了。要保留层和元数据，用 `docker save`/`docker load` 搬镜像；要保留文件系统但接受压平，才用 `export`/`import`。

多阶段构建是控制最终层数的常用手段：builder 阶段装编译器、下载依赖、跑测试，runtime 阶段只 `COPY` 产物和运行时文件。`shorty:0.1` 就是这样来的，最终镜像里没有 Go 工具链；`shorty:dev` 保留了 builder 阶段，所以 `docker image ls` 里比前者大一个数量级。两个镜像的层数和大小差这么多，不是 shorty 的代码变了，而是最终阶段选择带走什么。

可复现的构建要用 Dockerfile + BuildKit。Docker Engine 23.0 起，Linux 上的 `docker build` 默认走 Buildx + BuildKit；BuildKit 读取 Dockerfile，按指令生成 LLB 依赖图，再执行和导出。构建步骤、缓存命中和每条指令的耗时可以用 `docker build --progress=plain` 看到；要跳过缓存复现一次完整构建，用 `--no-cache`。可复现还不止“有 Dockerfile”：基础镜像要固定 digest，依赖版本要锁定，构建参数和时间戳要可重复，`RUN --mount=type=cache` 的缓存目录不会进入层但会影响构建速度。`docker commit` 没有这些抓手，所以它只能用来观察，不适合放进 CI。

BuildKit 不会为每条 `RUN` 创建可启动的中间容器，也不会留下 `docker images -a` 能列出的中间镜像；`docker history` 仍然会记录每条指令的 `created_by`，但除了顶层，IMAGE 列大多是 `<missing>`。这不是镜像损坏，而是构建模型变了，2.7 会再看一次这个现象。

> **旧资料提示**：旧教程把 `docker commit` 当作主要构建方式，甚至用“起容器、装软件、commit”代替 Dockerfile。今天标准做法是 Dockerfile + BuildKit；commit 只用于一次性实验或抢救一个正在运行的容器里的改动。

## 2.7 排障：digest 写错与“看不到中间层”

第一个故障是手写 digest 时抄错。常见来源是从网页或聊天窗口复制了一个被截断的值，或者把 tag 的 digest 和平台的 manifest digest 搞混。表现有两种：digest 格式不对时，Docker 直接报 `invalid reference format`；格式对但内容不存在时，registry 返回 `manifest unknown`、`401 Unauthorized` 或 `digest mismatch`，具体文本取决于 registry。下面的例子把当前 amd64 manifest 的 digest 最后一位改掉，再看两种命令的反应。

错误文本还能再细分一层。`invalid reference format` 是引用语法错，根本没到 registry；`manifest unknown` 或 `no such manifest` 是 registry 里没有这个 manifest；`401 Unauthorized` 可能是没有登录，也可能是 registry 对不存在的 blob 统一返回 401（本 lab 的 ECR 端点就是这样）；`digest mismatch` 则是内容取回来了，但算出的 sha256 和请求的 digest 不一致，属于传输或存储损坏，和“名字写错”不是一类问题。先看错误发生在解析、鉴权还是校验阶段，再决定是改清单、登录，还是重试/换 registry。

修复不是“再猜一位”，而是重新取当前 digest。`docker buildx imagetools inspect <name>:<tag>` 会打印 tag 当前指向的 index 和每个平台的 manifest；脚本里用 `--raw` 加 `jq` 最稳。`docker manifest inspect` 也能看到 index，但它只做一次解析，不打印注解，适合快速核对。不要把网页上截断的 digest、`docker images` 里 12 位的短 ID、或者 `docker history` 里的 IMAGE 列当成完整 digest：短 ID 只是前缀，历史里的 `<missing>` 根本不是 digest。

第二个“故障”不是故障。用 BuildKit 构建的镜像，`docker history` 仍然列出 Dockerfile 的每条指令，但只有最上面一层的 IMAGE 是当前镜像的 ID，其余大多是 `<missing>`；`docker image ls -a` 也不会像旧版 builder 那样列出一串中间镜像。因为 BuildKit 不创建可启动的中间容器/镜像，它把指令组织成 LLB 依赖图，直接产出最终快照。看到 `<missing>` 不要以为层丢了；要确认层在不在，看 `RootFS.Layers` 的数量和 `docker save` 出来的 blob 列表，而不是看 IMAGE 列。

BuildKit 的步骤和 `docker history` 可以对照看：`docker build --progress=plain` 会打印每条指令、缓存命中情况和耗时，`docker history --no-trunc` 则给出最终镜像里每条指令的 `created_by`。如果构建日志里有一步没出现在 history 里，通常是因为它只改了元数据（`ENV`/`LABEL`）或者被后面的阶段丢弃了；如果 history 里有一步构建日志里没有，检查是不是用了缓存。两者对不上时，先看 `--progress=plain` 的完整输出，不要只看最后几行。

如果 digest 本身是对的、registry 也返回了内容，但过一段时间再拉又失败，要考虑 registry 的垃圾回收：删掉 tag 不一定立刻删 blob，但 GC 可能清掉没有被任何 manifest 引用的层，旧 digest 就真的取不到了。本地 `docker image prune` 只影响这台机器，不会动 registry；生产回滚依赖的 digest 要在 registry 侧确认还在，不能只看本地缓存。

还有一个容易混淆的现象：`docker history` 的行数可能比 `RootFS.Layers` 多。`ENV`、`LABEL`、`CMD`、`ENTRYPOINT` 这类只改元数据的指令会出现在 history 里，`SIZE` 是 `0B`，config 里带 `empty_layer: true`，它们不产生 layer。2.1 的 `shorty:0.1` 就是 16 条 history、14 个 diffID。

## 上生产前

生产清单里的镜像引用写 digest，tag 只放在注释或单独的元数据里。升级时改 digest，不改同名 tag；回滚时把旧 digest 写回去。这样 Git 里的清单、集群里运行的镜像、registry 里的 blob 能对上，也不会因为别人在同一 tag 上 push 了新内容，导致同一份 Deployment 在不同节点拉到不同版本。

清理策略按 digest 而不是 tag 做。`docker image prune` 默认只删 dangling 镜像；`docker image prune -a` 会删掉所有没有被容器引用的镜像，包括你准备用来回滚的旧版本。执行前先确认回滚方案，必要时用 `--filter until=...` 限制范围，或者先把要保留的 digest 记下来。registry 侧的垃圾回收也可能删掉旧 digest 的 blob，回滚前要确认它还在。

不要把 secret 写进任何一层。`ARG`、`ENV` 的值会留在镜像 config 和 `docker history` 的 `CREATED BY` 里，`RUN` 里的密码也可能被层缓存保留；拿到镜像的人可以解开每一层。构建时用 BuildKit 的 `--mount=type=secret` 或 SSH mount，把凭据临时挂进构建容器，不让它进入最终层（第 10 章会做这个例子）。

镜像仓库的保留策略也要按 digest 设计。有些 registry 只保证“最近 N 天”或“最近 N 个 tag”，删掉 tag 不等于删掉 blob，但 GC 之后旧 digest 可能真的取不到；回滚窗口要覆盖这个保留期。生产环境还应该在准入层校验 SBOM 或 provenance 证明，确认这个 digest 是谁、用什么构建出来的；digest 只保证内容没变，不证明构建者可信。

多架构镜像发布前，用 `docker buildx imagetools inspect` 或 `docker manifest inspect` 确认每个目标平台都有 manifest，而不是只有一个 amd64 或一个 `unknown/unknown` 的 attestation。只发布 amd64 的镜像到 arm64 节点，轻则 `ImagePullBackOff`，重则容器启动后 `exec format error`；在 CI 里把平台列表和 `--platform` 固定下来，比上线后靠日志猜更省事。
