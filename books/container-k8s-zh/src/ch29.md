# 第 29 章 自动伸缩：HPA、VPA、原地调整资源（1.35 GA）、节点伸缩

api 的 Deployment 里写着 `requests.cpu: 45m`，副本数是 2。照着示例创建 HPA，`kubectl get hpa api` 的 TARGETS 一栏却是 `<unknown>/50%`，REPLICAS 停在 2。另一边，`kubectl top pods` 直接报 `error: Metrics API not available`。看起来 HPA 坏了，实际上它只是没有指标可读。

kind 默认不装 metrics-server，集群里也没有 `metrics.k8s.io` 这个 APIService。HPA 自己不采集 CPU；它每 15 秒向 Metrics API 要一次数据，拿不到就把 TARGETS 写成 `<unknown>`，并在 Event 里留下原因。metrics-server 才是那个从每台节点的 kubelet 收集 `/metrics/resource`、再把结果注册成 Metrics API 的组件。把两者混在一起，就会在“HPA 坏了”和“没装监控”之间来回猜。

有指标之后，HPA 也只是按一个公式改副本数：`ceil(当前副本数 × 当前指标 / 目标指标)`。CPU 利用率的分母是 requests，不是 limit，也不是节点容量；默认还有 10% 的容差和缩容稳定窗口。于是“CPU 到 80% 还不扩”可能有很多种解释：80% 正好是目标值、没设 requests、指标没取到、流量没打到这个 Deployment，或者 behavior 把扩缩限制住了。

再往上一层，VPA 改的是 requests/limits，原地调整让改资源不必重建 Pod，节点伸缩则在 Pod 没有节点可调度时加机器。这三件事和 HPA 不是替代关系，而是分别在副本、单 Pod 资源和节点容量三个层面工作。本章按这个顺序做：先让 Metrics API 有数据，再用 HPA 扩到 4 个副本，然后故意去掉 requests 看 HPA 为什么停住，接着用 behavior 控制缩容节奏，最后把 VPA、原地调整和节点伸缩放回它们各自的位置。

> **起点**：本章从 `s3-stateful` 开始：3 节点 kind 集群，api 2 副本，已经带上 `requests.cpu: 45m`、`memory: 64Mi` 和 `limits.cpu: 500m`、`memory: 256Mi`，但集群里没有 Metrics API。一步到位：`bash code/ch29/setup.sh`。

## 29.1 metrics-server 与 Metrics API

Kubernetes 的资源指标管道由三段组成。节点上的 kubelet 内置 cAdvisor，从 cgroup 读出每个容器的 CPU 和内存，通过 `/metrics/resource` 暴露节点级汇总；metrics-server 通过 Kubernetes API 跟踪节点和 Pod 列表，再逐个访问 kubelet 拉取指标，聚合成 Pod 和 Node 两种视图；最后，metrics-server 把结果作为一个聚合 API 注册到 apiserver，组名是 `metrics.k8s.io`，HPA、VPA 和 `kubectl top` 都从这个 API 读数据。`metrics-server` 是 Metrics API 的参考实现，不是 Kubernetes 核心组件，kind、kubeadm 和大多数托管集群都不会默认安装它。

这条管道只提供 CPU 和内存，够 HPA 按资源利用率扩缩，也够 `kubectl top` 显示用量。它不提供请求数、队列长度、延迟这类业务指标；要按这些指标扩缩，得再装 custom metrics adapter 或 external metrics adapter，把 `custom.metrics.k8s.io`、`external.metrics.k8s.io` 注册成另外的 APIService。HPA 的 `autoscaling/v2` 能同时读这三类 API，但资源指标这条最短的路径要先打通。

安装 metrics-server 需要 Deployment、Service、ServiceAccount、ClusterRole、ClusterRoleBinding，以及一个名为 `v1beta1.metrics.k8s.io` 的 APIService。APIService 的作用是告诉 apiserver：“`metrics.k8s.io` 这个组不在 apiserver 进程里，请把请求转发给 kube-system 里的 metrics-server Service。”聚合层没配好、Service 没有 Endpoint、metrics-server 连不上 kubelet，都会让这个 APIService 变成 `False`，HPA 也就拿不到数据。先看没有 Metrics API 时是什么样子。

## 29.2 HPA 算法

HPA 是一个控制循环，不是一次性动作。`kube-controller-manager` 里的 HPA 控制器默认每 15 秒同步一次：它按 `scaleTargetRef` 找到 Deployment，按 Deployment 的 selector 找到 Pod，从 Metrics API 读每个 Pod 的 CPU/内存，算出期望副本数，再通过 Deployment 的 `scale` 子资源改 `spec.replicas`。HPA 不直接创建或删除 Pod，滚动更新和 ReplicaSet 的增减仍由 Deployment 控制器负责。这也解释了为什么 HPA 只对支持 `scale` 子资源的对象有效，DaemonSet 这种不能扩缩的对象不在它的范围内。

算法本身只有一个比例：

`desiredReplicas = ceil(currentReplicas × currentMetricValue / desiredMetricValue)`

按 CPU 利用率扩缩时，`currentMetricValue` 是所有目标 Pod 的平均利用率，`desiredMetricValue` 是 HPA 里的 `averageUtilization`。示例里 api 每个 Pod 的 `requests.cpu` 是 45m，目标设成 50%，压测把两个 Pod 的平均利用率推到 80%，控制器算的是 `ceil(2 × 80 / 50) = ceil(3.2) = 4`。多出来的两个 Pod 就绪后，同样的总请求量被摊到四个 Pod 上，平均利用率下降，副本数才会稳定。公式里的“当前指标”不是 limit 的百分比，也不是节点 CPU 的百分比，而是“用量 ÷ requests”。

开头 HPA 显示 `cpu: 2%/50%`，因为 api 空载时几乎没有 CPU 消耗。压测起来后，前 25 秒 TARGETS 一直停在 2%，这是因为 metrics-server 的采集窗口和 HPA 的同步周期都有延迟，不是压测没生效。到 t=30s，HPA 读到 `cpu: 45%`，还在容差内；t=45s 读到 `cpu: 80%`，`DESIRED` 变成 4；t=60s，`REPLICAS` 变成 4，Deployment 也是 `4/4`。从 2 到 4 的过程没有经过 3，因为 80% 对应的比例是 1.6，向上取整直接得到 4。

`kubectl top` 的 Pod 列表会比 Deployment 慢一拍：新 Pod 要等 metrics-server 下一轮采集才会出现，所以这里可能先只列出两个旧 Pod，也可能四个都在，取决于采集的时间点。这次四个 Pod 各用 6m 到 11m，加起来约 31m，平均到每个 45m 的 request 不到 20%；新 Pod 的 CPU 明显低于扩缩前，因为同样的请求量被摊到了四个 Pod 上。HPA 的 TARGETS 仍显示 61%，这是上一次只有两个 Pod 时的读数，`currentMetrics` 的更新比 `top` 慢。副本数也没有立刻降回去，因为 HPA 默认的缩容稳定窗口是 300 秒。示例在读完 top 后停掉压测，接下来 29.4 会用 `behavior` 把这个窗口改小，观察缩容的时间线。

默认容差是 10%：比例在 1.0 附近 ±10% 以内时，HPA 认为“已经够接近目标”，不做扩缩。容差可以用 kube-controller-manager 的 `--horizontal-pod-autoscaler-tolerance` 改集群默认值；`behavior.scaleUp.tolerance` / `scaleDown.tolerance` 让单个 HPA 分别设置两个方向的容差，`HPAConfigurableTolerance` 在 Kubernetes 1.37 成为 stable。容差解释了一个常见疑问：目标设成 80%，平均利用率正好 80% 时，比例是 1.0，HPA 不会扩；目标设成 50%、当前 80% 时，比例是 1.6，早就该扩了。看到“CPU 到 80% 还不扩”，先确认 80% 是相对 requests 的利用率，还是监控面板上的节点/limit 百分比，再看 target 是多少。

CPU 利用率的分母只有 requests。Pod 的 request 是 45m、limit 是 500m，用量 90m 时利用率是 200%，不是 limit 的 20%。如果容器没有设置 CPU request，这个 Pod 的 CPU 利用率没有定义，HPA 不会为这个指标采取动作；29.3 会把这个条件做出来。HPA 还会把尚未 Ready 的 Pod、最近才 Ready 的 Pod 和缺指标的 Pod 先放到一边，缩容时按 100% 目标值估算它们，扩容时按 0% 估算，避免新 Pod 还没报到就把副本数算得过高或过低。`--horizontal-pod-autoscaler-initial-readiness-delay` 默认 30 秒，`--horizontal-pod-autoscaler-cpu-initialization-period` 默认 5 分钟，就是为这段启动期留的。

`autoscaling/v2` 在 Kubernetes 1.23 成为 stable，`metrics` 是一个数组，可以同时写 CPU、内存、Pod 指标、Object 指标和 External 指标；`targetCPUUtilizationPercentage` 那种单指标写法属于 `autoscaling/v1`，v2 会用 `metrics` 表达同样的目标。多个指标各自算出一个期望副本数，HPA 取其中最大的一个；如果某个指标取不到、而其他指标建议缩容，HPA 会跳过这次缩容，但仍然允许按能取到的指标扩容。`ContainerResource` 类型可以只按某个容器（例如 api，而不是 sidecar）的用量扩缩，`HPAContainerMetrics` 在 1.30 成为 stable。示例只用了 CPU，是因为 shorty 的 api 只有一个业务容器；多指标和容器级指标的写法在官方 HPA 页面和演练里都有完整清单。

## 29.3 HPA 不扩的排查

HPA 不扩时，最先要区分的是“没有指标”和“指标算出来不需要扩”。`<unknown>` 说明 HPA 算不出一个百分数；最常见的原因是没从 Metrics API 拿到目标 Pod 的数据，也可能是目标 Pod 没有 requests。`FailedGetResourceMetric` 也是前者，但它只说明“资源指标取不到”，具体是 metrics-server 连不上 kubelet、Pod 没有 requests，还是新 Pod 还没被采集到，要看 Event 的 Message。后者则是 HPA 读到了指标，只是比例没有超过容差，或者被 `minReplicas`/`maxReplicas`/`behavior` 限制住了，状态里通常会出现 `ScalingLimited`。

第一步永远是 `kubectl describe hpa` 看 Conditions 和 Events。Conditions 里 `AbleToScale` 表示 HPA 能不能读写目标的 scale 子资源，`ScalingActive` 表示它能不能算出期望副本数，`ScalingLimited` 表示算出来的值有没有被上下限截断。Events 里会按时间留下每次失败的原因，比只看 TARGETS 有用得多。

改完模板后 Deployment 滚动出 4 个新 Pod。新 Pod 刚起来时 metrics-server 还没有它们的采样，HPA 可能先报 `did not receive metrics for targeted pods (pods might be unready)`；等采集完成，稳定下来的 Message 是 `missing request for cpu in container api of Pod ...`，TARGETS 变成 `cpu: <unknown>/50%`，REPLICAS 停在 4。HPA 没有把副本数改回 2，因为指标无效时它不会做扩缩决定；`ScalingActive=False`、`FailedGetResourceMetric` 就是这件事的正式记录。

这条 Message 就是“没设 requests 也能按 CPU 扩”这个旧说法的反例。CPU 利用率是 `usage / requests`，没有 requests 就没有分母，HPA 不会猜一个分母出来。内存指标同理：按 `averageUtilization` 扩缩内存时，也要有 `requests.memory`；按绝对用量（`AverageValue`）扩缩时不需要利用率，但那是另一种 target 类型。

把 requests/limits 恢复后，Deployment 再滚动一次，HPA 的条件回到 `ScalingActive=True`、`ValidMetricFound`，TARGETS 恢复成 `cpu: 2%/50%`。副本数仍是 4，因为默认缩容稳定窗口还没走完；这与“HPA 坏了”是两件事。示例到这里结束，29.4 会把缩容窗口显式写出来，观察它怎么影响副本数。

除了缺 requests，还有几类常见原因，排查顺序可以固定成下面这样。

第一类是指标管道断了。`kubectl get apiservice v1beta1.metrics.k8s.io` 不是 `Available`，或者 `kubectl top pods` 报 `Metrics API not available`，先修 metrics-server，不要动 HPA。29.1 已经演示过这条路径。APIService 是 `Available=True` 但 `kubectl top` 仍然报错时，看 metrics-server 的日志和 kubelet 的 10250 端口，常见原因是证书、网络策略或 kubelet 没有开指标端点。

第二类是 requests 缺失或不完整。Pod 里只要有一个容器没有该资源的 request，这个 Pod 的利用率就没有定义；HPA 会把这个 Pod 放到一边，全部 Pod 都这样时 TARGETS 就是 `<unknown>`。多容器 Pod 里 sidecar 没有 requests 也会触发，不一定是你以为的业务容器。

第三类是目标值和容差。目标 80%、当前 80% 时比例是 1.0，HPA 不扩；目标 50%、当前 55% 时比例是 1.1，刚好在默认 10% 容差边缘，也可能不动。把 `kubectl get hpa` 的 TARGETS 读成“当前值/目标值”，再和 `behavior` 里的 `tolerance` 对一下，不要只看监控面板上的 CPU 百分比。

第四类是 `behavior`。`scaleDown.stabilizationWindowSeconds` 默认 300 秒，缩容会延迟；`scaleUp` 被 `selectPolicy: Disabled` 或很小的 `Policies` 限制住时，扩容也会变慢。29.4 会展开这几个字段。`ScalingLimited=True` 且 Reason 是 `TooManyReplicas`、`TooFewReplicas` 或 `DesiredWithinRange` 时，说明算出来的值被 `maxReplicas`/`minReplicas` 截断了，改 HPA 的上下限，不是改应用。

第五类是流量没有打到被 HPA 的 Deployment。Service 的 selector 写错、压测客户端打到了另一个 Service、或者 HPA 的 `scaleTargetRef.name` 指向了别的 Deployment，都会让 HPA 看到的目标 Pod 一直是空闲的。排查时把 `kubectl get hpa -o yaml` 里的 `scaleTargetRef`、`kubectl get deploy -l <selector>` 选出来的 Pod、以及压测客户端实际访问的 Service/EndpointSlice 三样对上，再去看利用率。

## 29.4 HPA behavior 与缩到零

29.2 的 HPA 没有写 `behavior`，用的是默认值：缩容稳定窗口 300 秒，缩容策略每 15 秒最多删 100% 的当前副本；扩容稳定窗口 0 秒，每 15 秒最多加 4 个 Pod 或 100% 的当前副本，取两者中较大的。默认值适合大多数服务，但它意味着“负载掉了以后，副本数还会在原地待五分钟”，也意味着“如果指标抖动，副本数可能上下跳”。`behavior` 就是用来改这两个方向的节奏的。

`stabilizationWindowSeconds` 是一个滚动窗口，不是“等这么久再动手”的定时器。HPA 在每次同步时都会记下一条期望副本数；缩容时，它回看窗口内所有期望值，取其中最高的一个。只要窗口里还有一条“4 个副本”的记录，它就不会把目标改成 2。`policies` 则限制每个方向在 `periodSeconds` 内最多变多少个 Pod 或百分之多少；多个策略同时存在时，默认 `selectPolicy: Max` 选允许变化最大的那个，`Min` 选最小的，`Disabled` 直接关掉这个方向。`periodSeconds` 最大 1800 秒。

`kubectl get hpa -o yaml` 的输出里，除了写进去的 `stabilizationWindowSeconds: 120` 和 `policies`，还能看到 `selectPolicy: Max` 和整个 `scaleUp` 默认块。`selectPolicy` 没有写，默认值补齐成 `Max`；`scaleUp` 没有写，默认值补齐成 0 秒窗口、每 15 秒 4 个 Pod 或 100%。这说明 `behavior` 不是“写多少生效多少”，没写的字段会用默认值合并，排查时要把合并后的对象读全。

时间线里，t=0 到 t=100 秒 `current` 一直是 4，尽管 CPU 已经从 74% 掉到 2%，`desired` 也一直显示 4。到 t=120 秒，`desired` 才变成 3；t=140 秒，`current` 变成 3；t=160 秒，`desired` 变成 2；t=180 秒，`current` 变成 2。稳定窗口负责“先不动”，策略负责“每次只动一个”，两者叠加就是这条 4 → 3 → 2 的阶梯。如果只设 120 秒窗口、不设策略，窗口一过 HPA 可以按默认的 100%/15s 一次性从 4 降到 2，阶梯就没了。

这里也能看出“缩容太快会抖动”的机制。压测停止后如果立刻把 4 个 Pod 砍到 2 个，剩下的 2 个会立刻承担原来的全部流量，平均利用率可能从 20% 跳到 90%，HPA 下一轮又要把副本加回去；加回去以后每个 Pod 的利用率又降下来，于是再缩。`stabilizationWindowSeconds` 让缩容决定看一段历史，`policies` 让每次变化有上限，`tolerance` 让目标附近的小波动不触发动作，三者一起把这种振荡压下去。反过来说，窗口设得太大、策略设得太慢，故障时缩不下去，也会浪费资源；窗口和策略要按压测的升降速来定，不是越大越安全。

`behavior` 在 `autoscaling/v2` 里从 1.23 起 stable。`scaleUp`/`scaleDown` 下都可以写 `stabilizationWindowSeconds`、`policies`、`selectPolicy`，`tolerance` 字段在 1.37 成为 stable。策略的 `type` 只有 `Pods` 和 `Percent` 两种，`value` 是数量或百分比，`periodSeconds` 是最长 1800 秒的观察窗口。

缩到零是另一个方向。HPA 默认的最小副本数是 1；把 `minReplicas` 设成 0 需要 `HPAScaleToZero` 特性门控，这个门控在 Kubernetes 1.37 是 beta，并且必须同时在 kube-apiserver 和 kube-controller-manager 上打开：apiserver 负责接受 `minReplicas: 0`，controller-manager 负责真的把工作负载缩到 0。更重要的是，缩到零只支持 Object 和 External 指标，不支持 CPU、内存这类 Resource 指标。原因很直接：CPU 和内存是 running Pod 的用量，副本数为 0 时没有 Pod 可测，指标就断了；队列长度、Kafka lag 这类外部指标不依赖 Pod 是否存在，才能把副本从 0 拉回 1。HPA 把工作负载保持在 0 时会在 status 里记一条 `ScaledToZero=True` 的条件，用来区分“是我缩到零的”和“有人手动把副本改成 0 的”。

> **旧资料提示**：`autoscaling/v1` 的 `targetCPUUtilizationPercentage` 不是唯一写法。`autoscaling/v2` 在 1.23 成为 stable，用 `metrics` 数组表达 CPU、内存、自定义指标和外部指标，用 `behavior` 控制扩缩节奏，还能用 `ContainerResource` 按单个容器扩缩；旧清单里的 `targetCPUUtilizationPercentage` 仍然能被 API 接受，但它表达不了多指标和 behavior。

## 29.5 VPA：纵向扩缩的代价

HPA 改的是副本数，VPA（VerticalPodAutoscaler）改的是单个 Pod 的 requests/limits。它适合“副本数不能再加、但每个副本明显偏小或偏大”的工作负载，例如单实例数据库、必须固定副本数的有状态服务，或者长期空转、requests 设得过高的批处理。VPA 不是 Kubernetes 核心 API：它是一个 CRD，API 组是 `autoscaling.k8s.io`，当前 stable 版本是 `autoscaling.k8s.io/v1`，要单独安装。HPA 是核心 `autoscaling` 组的资源，这也是两者最容易混淆的地方。

VPA 由三个组件组成。Recommender 周期性读取目标 Pod 的历史和当前用量，算出 target、lower bound、upper bound 三种推荐，写进 VPA 对象的 `.status.recommendation`；Updater 比较 Pod 现有 requests 和推荐值，差距超过阈值时按更新模式驱逐 Pod 或原地改资源；Admission Controller 是一个 mutating webhook，在 Pod 创建时把推荐值写进新 Pod。只装 Recommender 时，VPA 只“给建议”，不会动 Pod；这也是本书实验环境的装法。

`updateMode` 决定 Updater 和 Admission Controller 怎么用这些建议。`Off` 只写 status，不动 Pod；`Initial` 只在 Pod 第一次创建时套用推荐，之后不再改；`Recreate` 在推荐与现状差距大时驱逐 Pod，让工作负载控制器创建新 Pod，Admission Controller 再把新值写进去；`InPlaceOrRecreate` 先尝试原地改，改不了再驱逐；`InPlace` 只原地改，改不了就等着重试。`Auto` 从 VPA 1.4.0 起已弃用，现在只是 `Recreate` 的别名；旧资料里的 `Off/Initial/Recreate/Auto` 四种模式已经不够用了，新清单应该按当前文档写 `Recreate` 或 `InPlaceOrRecreate`。

改 requests 通常意味着重建 Pod。`Recreate` 会驱逐，`Initial` 等待下一次创建，只有 `InPlace`/`InPlaceOrRecreate` 才可能不重建；而原地改又依赖 Kubernetes 的 `InPlacePodVerticalScaling`（29.6 会讲）。所以 VPA 的代价不是“多占一点 CPU”，而是“可能在不该重启的时候重启一个数据库”。生产上要配 PDB、把 `minAllowed`/`maxAllowed` 收窄、用 `controlledValues: RequestsOnly` 避免 VPA 同时改 limits，并且先跑一段 `Off` 看推荐值是否合理。

VPA 和 HPA 不要同时按同一个指标工作。VPA 把 CPU requests 调高，HPA 算出来的 CPU 利用率会立刻下降，于是 HPA 缩副本；副本少了，每个 Pod 的负载又上去，VPA 再调高 requests，两个控制器就会互相追。常见组合是 HPA 按 CPU 扩副本、VPA 只按内存给推荐，或者 VPA 保持 `Off` 只做容量评估；如果两个都要自动改，至少要让它们控制不同的资源，并且接受请求值变化会改变 HPA 的分母。

VPA 也需要 Metrics API。Recommender 从 `metrics.k8s.io` 读 Pod 的 CPU/内存，没有 metrics-server 时它给不出推荐；这一点和 HPA 相同。VPA 还受 LimitRange 约束：admission controller 和 updater 会把推荐值裁剪到命名空间 LimitRange 的 min/max 之内，再按 request-to-limit 比例调整 limit。生产上如果同时有 LimitRange 和 VPA，先确认两者的边界不冲突。

## 29.6 原地调整与节点伸缩

HPA 和 VPA 都在改“要多少资源”，但传统上改 Pod 的 requests/limits 要删掉旧 Pod、创建新 Pod。原地调整（in-place Pod resize）把这一步省掉：直接改运行中 Pod 的 CPU/内存，kubelet 把新值应用到容器的 cgroup，不重建 Pod。这个特性在 Kubernetes 1.27 进入 alpha，1.33 进入 beta，1.35 成为 stable（`InPlacePodVerticalScaling` 门控从 1.35 起锁定为 true），所以 1.37 的集群默认就能用。

原地调整通过 Pod 的 `resize` 子资源完成，命令是 `kubectl patch pod <名字> --subresource resize`，或者 `kubectl edit pod <名字> --subresource resize`。`kubectl` 客户端至少要是 1.32，旧客户端会报 `invalid subresource`。改的是 Pod 的 `spec.containers[*].resources`，也就是“期望值”；`status.containerStatuses[*].resources` 是 kubelet 已经应用到运行容器的“实际值”，两者对上了才算完成。中间的进度写在 Pod condition 里：`PodResizePending` 表示还没法应用，`reason: Infeasible` 是当前节点做不到、`reason: Deferred` 是暂时做不到但以后可能行；`PodResizeInProgress` 表示已经分配、正在改。

原地调整的边界不少。只有 CPU 和内存能改，其他资源不行；Pod 的 QoS 类在创建时确定，resize 不能把它从 Burstable 改成 Guaranteed，所以 Burstable Pod 不能把 CPU 和内存的 request/limit 同时改成相等；已经设置的 request/limit 不能整个删掉，只能改成别的值；不可重启的 Init 容器和临时容器不能改，sidecar 可以；Windows Pod、使用 static CPU/Memory manager 的 Pod 也有额外限制。容器还可以用 `resizePolicy` 指定某类资源变化时要不要重启容器：`NotRequired` 是默认值，CPU 一般不需要重启；`RestartContainer` 常用于内存，因为很多运行时不能动态改内存上限。

示例先取一个 api Pod，记下 `restartCount=0`，然后只把 CPU limit 从 500m 改成 600m。`status.limits.cpu` 先显示 500m，下一轮变成 600m；`restartCount` 前后都是 0，`kubectl describe pod` 里 State 是 Running、Restart Count 是 0、Limits 已经是 `cpu: 600m`、Requests 还是 `cpu: 45m`。Pod 没有换名字，也没有经过 Deployment 的滚动更新；这和你改 Deployment 模板后看到的新 ReplicaSet、新 Pod 名字是两回事。

接着要 1000 个 CPU。这个 patch 被 apiserver 直接拒绝：`node didn't have enough allocatable resources: cpu, requested: 1000000, allocatable: 32000`。kind 节点只有 32 核，1000 核超过 allocatable，请求在到达 kubelet 之前就失败了，Pod 的 spec 和 status 都还是上一次的 600m。官方任务页描述的是“patch 成功、Pod 出现 `PodResizePending`、`reason: Infeasible`”的路径；本书在 1.37 的 lab 里实测到的是准入阶段直接 `Forbidden`。两种结果都说明同一件事：原地调整不能突破节点容量。请求没有超过 allocatable、只是节点当前空闲容量不够时，才会走 `Deferred` 排队、等别的 Pod 释放资源后重试。

最后把请求改回 45m/500m，`status.limits.cpu` 回到 500m，Pod 仍然是 Running。原地调整适合“调大一点 limit、调小一点 request”这种不想打断连接的场景；它不负责给 Pod 找一台有容量的节点，节点不够时还是失败或排队。

节点伸缩是第三层。HPA 把副本数从 2 加到 4，调度器发现有两个新 Pod 没有节点放得下，就会让它们 Pending；节点自动伸缩器看到 Pending 的 Pod，向云厂商申请一台新节点，节点加入后再让调度器把 Pod 放上去。反过来，节点利用率长期很低时，伸缩器会把 Pod 驱逐、合并到更少的节点上，再删掉空节点。官方文档把前者叫 node provisioning（以前叫 scale-up），后者叫 node consolidation（以前叫 scale-down）。节点伸缩器只看 Pod 的 requests，不看实际用量；requests 设得太小，新节点可能还是放不下或很快又不够；设得太大，节点又合并不掉。

目前 SIG Autoscaling 赞助的两个实现是 Cluster Autoscaler 和 Karpenter。Cluster Autoscaler 在预先配置好的 node group 里加减节点，一个实例可以管多个 group；它不支持 auto-provisioning，节点组的规格要提前配好。Karpenter 按 NodePool 的约束直接创建云厂商资源，支持 auto-provisioning，节点规格可以按 Pending Pod 的需求动态选，生命周期管理也更多（例如到期重建、自动升级）。两者都依赖云厂商 API，本书的 kind 集群没有云节点池，节点伸缩只在概念层面讲，没有在 lab 里验证。

节点伸缩要和 PDB、PriorityClass、节点池一起配。缩节点时，节点上的 Pod 要被驱逐；没有 PDB 的关键服务可能一次被赶走太多；没有优先级，kube-system 的组件和业务 Pod 抢容量时排序不清楚。扩容有冷启动：申请虚拟机、加入集群、拉镜像都要时间，关键的登录、支付链路不能只靠“临时加机器”兜底，要预留容量或预热节点。节点池则决定新节点落在哪个可用区、什么规格、带什么标签和污点；这些约束会和 Pod 的 affinity、topologySpreadConstraints 一起决定 Pod 最终能不能被放上去。

事件驱动扩缩是 HPA 的补充。KEDA 这类外部组件把队列长度、Kafka lag、HTTP 并发等指标通过 external metrics adapter 暴露成 `external.metrics.k8s.io`，HPA 用 `type: External` 的 metric 读它，再按目标值扩副本。KEDA 本身不是 Kubernetes 核心，也不在本书的 lab 里安装；这里只需要知道它和 HPA 的关系：HPA 仍然是执行扩缩的那个控制器，KEDA 负责把外部指标接进来、并在没有负载时把副本降到 0。CPU、内存这类 Resource 指标不能缩到 0，队列长度这种 External 指标可以，这也是 29.4 里 `HPAScaleToZero` 只支持 Object/External 的原因。

把三层放在一起看：HPA 决定“要几个副本”，VPA/原地调整决定“每个副本要多少 CPU/内存”，节点伸缩决定“有没有节点放这些副本”。只配 HPA，副本加了但节点不够，Pod 会 Pending；只配 VPA，requests 调大后可能连调度都通不过；只配节点伸缩，节点加了但副本数没变，只是多花钱。三层要一起看指标和事件，缺一层都会在某个环节卡住。

## 29.7 排障：HPA 显示 `<unknown>`

`kubectl get apiservice v1beta1.metrics.k8s.io` 的 `AVAILABLE` 是 `True`，`SERVICE` 指向 `kube-system/metrics-server`，说明聚合层已经把这个 API 接上了。`kubectl top pods` 能列出 api 的 CPU/内存，说明 metrics-server 到 kubelet 的路也是通的。`kubectl get hpa` 的 TARGETS 是 `cpu: 2%/50%`，REPLICAS 是 2，HPA 已经能算出利用率。`kubectl describe hpa` 里 `ScalingActive=True`、`Reason=ValidMetricFound`，说明指标没有问题；`ScalingLimited=True`、`Reason=TooFewReplicas`，说明算出来的期望值低于 `minReplicas`，HPA 只能把副本保持在 2，这不是故障，是下限在起作用。Events 里可能还留着之前扩缩和失败的记录，按时间读最近一条。最后 `kubectl get deployment api -o jsonpath=...` 打出的 requests/limits 就是 HPA 的分母。

如果第一步就不对，按 29.1 修 metrics-server：APIService 不存在、`Available=False`、`kubectl top` 报 `Metrics API not available`，都先不要动 HPA。如果 APIService 是 `True` 但 top 仍然报错，看 `kubectl -n kube-system logs deploy/metrics-server` 和 kubelet 的 10250 端口，常见原因是证书、网络策略、kubelet 没开指标端点。

如果第二步不对，也就是 TARGETS 是 `<unknown>`、`ScalingActive=False`、`Reason=FailedGetResourceMetric`，读 Event 的 Message。`missing request for cpu` 指向 requests 缺失（29.3）；`did not receive metrics for targeted pods` 通常是新 Pod 还没被采集，等一轮再看；`no metrics returned from resource metrics API` 可能是 metrics-server 到 kubelet 的采集失败，也可能是目标 Pod 全被过滤掉了。不要只凭 Reason 是 `FailedGetResourceMetric` 就断定是 metrics-server。

如果前两步都对、HPA 还是不扩，按 29.3 的五类原因检查：目标值和容差（80% 对 80%、50% 对 55%）、`behavior` 的窗口和策略、`ScalingLimited` 是否被 `maxReplicas`/`minReplicas` 截断、以及压测流量是不是真的打到了这个 Deployment。流量这一项最容易被忽略：Service 的 selector、EndpointSlice 的 endpoint、HPA 的 `scaleTargetRef` 三者只要有一个对不上，HPA 看到的目标 Pod 就一直是空闲的。

需要持续观察时，交互式可以用 `kubectl get hpa api -w`；本章的示例不用 `-w`，因为 watch 的输出会一直增长，不适合写进 `.out`。要留历史，应该用 Prometheus 之类的监控系统采集 HPA 的 `status.currentReplicas`、`status.desiredReplicas` 和 `kube_horizontalpodautoscaler_status_condition`，而不是靠终端里的 watch。

## 上生产前

**HPA 之前先把 requests 设对，target 要靠压测定。** 没有 requests，CPU/内存利用率没有分母，HPA 只能显示 `<unknown>`；requests 设得离谱，HPA 会在错误的基数上扩缩。target 不要拍脑袋写 50% 或 80%：用和生产相近的请求压一遍，看单 Pod 在目标延迟下的 CPU 用量，再留出安全边际。`behavior` 也要一起定，至少把 `scaleDown.stabilizationWindowSeconds` 和每次删除的 Pod 数写清楚，否则默认的 5 分钟窗口会让缩容看起来“不生效”，默认的 100%/15s 又可能在指标抖动时一次删太多。

**VPA 和 HPA 不要按同一个指标互相打架。** VPA 改 requests 会改变 HPA 的分母：VPA 把 CPU requests 调高，HPA 看到的利用率立刻下降，于是缩副本；副本少了，单 Pod 负载升高，VPA 又建议调高 requests。生产上要么让 HPA 按 CPU 扩副本、VPA 只按内存给建议，要么先让 VPA 跑 `Off` 只收集推荐，确认稳定后再切 `Recreate` 或 `InPlaceOrRecreate`。VPA 的自动更新可能驱逐 Pod，必须配 PDB；`minAllowed`/`maxAllowed` 要收窄，避免推荐值无界；有状态服务还要评估重启后的恢复时间。

**节点伸缩要配 PDB、优先级和节点池，扩容有冷启动。** 节点伸缩器只看 Pod 的 requests：requests 太小，新节点可能仍然放不下或很快又不够；requests 太大，节点合并不掉。缩节点会驱逐 Pod，没有 PDB 的关键服务可能一次被赶走太多；没有 PriorityClass，kube-system 组件和业务 Pod 抢容量时排序不清楚。新节点从申请到能跑 Pod 要几十秒到几分钟，关键流量要预留容量或预热节点，不能把节点伸缩当成瞬时的兜底。

**监控 HPA 的条件和副本变化，不要只看 TARGETS。** 至少采集 `ScalingActive`、`ScalingLimited`、`AbleToScale` 三个条件和 `currentReplicas`/`desiredReplicas`；`ScalingActive=False` 持续几分钟就该告警，`ScalingLimited=True` 说明长期顶在 max 或 min，需要调上下限或加节点。Events 里的 `FailedGetResourceMetric`、`FailedComputeMetricsReplicas` 也要进日志/告警，不要等用户发现扩容不生效。

**metrics-server 只适合做当前的资源指标管道，不要拿它当长期监控。** Metrics API 只提供 CPU/内存和当前采集窗口的数据，不提供历史查询；要看趋势、做容量规划、按业务指标扩缩，得把指标送进 Prometheus 之类的系统，再用 custom/external metrics adapter 接回 HPA。metrics-server 本身也要有副本和资源限制，它挂了 HPA 会全部变成 `<unknown>`，这属于控制面的单点，不是应用故障。

| `kubectl get hpa` / `kubectl get hpa -w` | 看当前值/目标值、副本数 | `-w` 只适合交互观察，示例不用 |
| `kubectl describe hpa` | 看 Conditions 和 Events | 排障第一步 |
| `kubectl autoscale deployment api --cpu=50% --min=2 --max=5` | 命令式创建 HPA | 生成的仍是 `autoscaling` 对象，生产建议用清单 |
| `autoscaling/v2` 的 `metrics` | 多指标、CPU/内存/自定义/外部指标 | 1.23 stable；`ContainerResource` 需要 `HPAContainerMetrics` |
| `behavior.scaleUp` / `scaleDown` | 稳定窗口、策略、选择策略、容差 | 默认缩容窗口 300s，扩容窗口 0s |
| `stabilizationWindowSeconds` | 回看窗口内最高的期望副本数 | 缩容用它防抖；`periodSeconds` 最大 1800 |
| `policies` / `selectPolicy` | 每次最多变多少 Pod/百分比 | 默认 `Max`；`Min` 取最小变化，`Disabled` 关闭方向 |
| `HPAScaleToZero` | 允许 `minReplicas: 0` | 1.37 beta；只支持 Object/External 指标 |
| `kubectl get vpa` / `kubectl describe vpa` | 看 VPA 模式和推荐值 | VPA 是 CRD，需要单独安装 |
| `updateMode` | VPA 怎么应用推荐 | `Off`/`Initial`/`Recreate`/`InPlaceOrRecreate`/`InPlace`；`Auto` 已弃用 |
| `kubectl patch pod <名字> --subresource=resize` | 原地改 CPU/内存 | kubectl ≥ 1.32；`PodResizePending`/`PodResizeInProgress` 看进度 |
| `resizePolicy` | 改资源时是否重启容器 | 默认 `NotRequired`；内存常用 `RestartContainer` |
| `kubectl get events --field-selector involvedObject.name=api` | 只看 api 相关事件 | 比翻全部 Event 快 |

本章结束时，`shorty` 仍是 `s3-stateful` 的布局：api 的 requests 是 45m/64Mi、limits 是 500m/256Mi，`HPA api` 的范围是 2–5、目标 CPU 50%；29.2 的压测把它扩到过 4 个副本，29.4 的缩容实验又把它降回 2 个。`kube-system` 里有 metrics-server 和只装 Recommender 的 VPA，`shorty` 里有 `updateMode: Off` 的 `api-vpa`，它只写推荐值，不改 Pod。下一章给 api 配 ServiceAccount 和 RBAC，伸缩这条线保持现在的状态。
