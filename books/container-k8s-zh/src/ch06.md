# 第 6 章 单机网络：bridge、内置 DNS、端口发布与 nftables，link 为什么淘汰

第 5 章结束时，`shorty-api` 和 `shorty-pg` 都在跑，PostgreSQL 的数据在命名卷 `shorty-pgdata` 里，`shorty migrate` 已经建好表。`curl localhost:8080/healthz` 能返回 `ok`，看起来一切正常。但只要把 `shorty-api` 删掉重建，它就连不上数据库了：它的 `SHORTY_DB_URL` 里写的是 `shorty-pg` 当时的容器 IP，而容器重建后 IP 会变。这是本章要解决的第一个问题。

第二个问题更隐蔽。在后面的实验里，把 api 发布到 `-p 8080:8080`、再接进 `shorty-net` 之后，从宿主 `curl localhost:8080` 能通，从另一个容器访问 `api:8080` 也通，但这两条路径并不是同一条。前者要经过宿主防火墙的 DNAT，后者走的是 bridge 内部的二层转发。分不清这两条路径，遇到“连不上”时就只能挨个试。

把这两个问题分开看，会发现它们都指向同一件事：容器的网络身份是临时的。容器 IP 从网络的地址池里分配，容器删了就可能被别人拿走；端口发布是创建时的参数，创建后改不了；名字解析则取决于容器接在哪个网络、有没有别名。本章的实验都围绕这三个“临时身份”展开，先让 shorty 用稳定的名字跑起来，再拆开底层看它们是怎么实现的。

这一章把 shorty 从默认 bridge 搬到自定义网络 `shorty-net`，用服务名 `postgres`、`redis`、`api` 互相访问；然后拆开 veth、docker0、内嵌 DNS 和 NAT 规则，看它们各自在哪一层；再故意让 api 只监听回环地址、制造端口冲突，练习判断故障在 DNS、监听地址还是防火墙；最后解释 `--link` 为什么被淘汰，以及 UFW 为什么管不住 Docker 发布的端口。

> **起点**：第 5 章结束。`shorty-api` 在默认 bridge 上，通过 `shorty-pg` 的容器 IP 连数据库，api 只发布在 `127.0.0.1:8080`；`shorty-pg` 用命名卷 `shorty-pgdata`，表已建好；还没有 `shorty-net`，也没有 `shorty-redis`。`bash code/ch06/setup.sh` 会构建带 shell 的 `shorty:dev`，拉起 pg、执行 migrate，再起 api 并等到 `/readyz` 通过。

## 6.1 Linux 网络底稿：netns、veth、bridge、路由

容器里的 `eth0` 不是一块真的网卡，而是一对 veth（virtual Ethernet）设备的一端。veth pair 像一根虚拟网线：一端放在容器的 network namespace（netns）里，叫 `eth0`；另一端留在宿主的 netns 里，名字是 `veth` 加一串随机字符，被接到一个 Linux bridge 上。默认情况下这个 bridge 叫 `docker0`，所以“容器接在默认 bridge 上”不是比喻，而是宿主上真有一个二层交换机，容器的 veth 是它的一个端口。

每个容器有自己的 netns，里面有一张独立的路由表。容器发包给同网段的其他容器时，直接 ARP 对方 IP，bridge 按 MAC 转发；发给外网时，默认路由指向 bridge 的网关地址，也就是 bridge 自己在宿主上的 IP。这个网关不是 NAT 设备，它只是把包转给宿主的路由表；NAT 是后面 6.3 要看的另一组规则。

bridge 在宿主上是一个普通的二层设备：`docker0` 有 MAC 地址，也有 `172.18.0.1` 这个 IP，宿主的路由表里有一条 `172.18.0.0/16 dev docker0`。容器发 ARP 问“谁是 172.18.0.1”，`docker0` 用自己的 MAC 回答；容器把帧发给这个 MAC，bridge 再按目的 MAC 转发到对应的 veth 端口。这个过程和物理交换机没有本质区别，只是端口变成了 veth。

`docker network inspect bridge` 给出默认 bridge 的网段和网关。这个 lab 是 `172.18.0.0/16`、网关 `172.18.0.1`；很多资料和默认安装是 `172.17.0.0/16`、`172.17.0.1`，两者都可能，判断依据永远是 `docker network inspect bridge`，不是记一个固定地址。网关就是 `docker0` 接口的地址，容器把它当作去往其他网段的下一跳。

`container pid=... netns=net:[...]` 这一行说明 netns 挂在容器进程上：`/proc/<pid>/ns/net` 是一个指向 netns inode 的链接。`ip netns list` 没有输出，因为 `ip netns` 只列出注册在 `/run/netns` 下的具名 netns，Docker 创建的是匿名 netns，不往那里注册。要进容器的 netns，可以用 `nsenter -t <pid> -n`，或者更简单的 `docker exec`；6.7 会用 `nsenter` 看容器里的监听地址。

容器里的 `eth0` 拿到了本网段的一个地址，默认路由是 `default via 172.18.0.1 dev eth0`，另有一条 `172.18.0.0/16 dev eth0` 的直连路由。三条信息合起来说明：同网段走二层，出网段走网关，容器自己不知道 veth 的对端叫什么。

宿主这一侧，例子先用 `/sys/class/net/eth0/iflink` 读出容器 `eth0` 的对端 ifindex，再用它从 `ip -o link` 里找到宿主上对应的 veth 接口。`bridge link show dev` 的输出里，`master docker0` 表示这个 veth 被接到了 `docker0`，`state forwarding` 表示 bridge 正在转发。最后 `ip route | grep docker0` 给出宿主的直连路由，说明 `172.18.0.0/16` 是从 `docker0` 出去的。把两边的 ifindex 对上，就能确认“容器里的 eth0”和“宿主上的 vethXXXX”是同一根虚拟网线的两端；名字每次创建都会变，不要把它写进脚本。

容器删除时，这一对 veth 一起消失，`docker0` 上的端口也没了，IP 回到地址池。下次再起同名容器，可能拿到完全不同的 IP 和 veth 名。这就是为什么 6.2 里要换成名字：名字由网络和容器元数据决定，不随 IP 分配变化；IP 只是当前这一刻的地址。

排障时的四件套可以这样分工：`ip netns` 看有没有具名 netns（Docker 的通常看不到）；`ip link` 和 `bridge link` 看宿主上的 veth 接到了哪个 bridge、是不是 up；`ip route` 看容器或宿主的默认路由；`ip addr` 看地址和网段。再加上 `nsenter -t <pid> -n` 或 `docker exec`，就能把“容器里看到的”和“宿主上看到的”对上。

> **旧资料提示**：旧教程常说“docker0 的网关是 `172.17.42.1`”。现代 Docker 的默认 bridge 通常是 `172.17.0.1/16`，但这个 lab 分配到了 `172.18.0.0/16`；地址池可以被 `daemon.json` 的 `default-address-pools` 改，也可能因为已有网段而避开。以 `docker network inspect bridge` 的 `IPAM.Config` 为准，不要背地址。

## 6.2 默认 bridge 与自定义 bridge

默认 bridge 只提供 IP 连通，不提供名字解析。所有没写 `--network` 的容器都被塞进同一个 `bridge` 网络，它们可以用 IP 互相访问，但 `getent hosts postgres` 不会成功，因为容器里的 `/etc/resolv.conf` 只是宿主 resolv.conf 的拷贝，没有 Docker 的内嵌 DNS。Docker 文档把这一点写得很直接：默认 bridge 上的容器只能按 IP 访问，除非用遗留的 `--link`。

```console

```

前三条命令是“默认 bridge 没有名字解析”的证据：`nameserver` 指向宿主 DNS，不是 `127.0.0.11`；`getent hosts postgres` 没有任何输出，`exit=2`；`/etc/hosts` 里匹配 `postgres` 的行数是 0。api 能连上 pg，靠的是 `SHORTY_DB_URL` 里写死的容器 IP，而不是名字。

`docker network create shorty-net` 创建一个用户自定义 bridge。它和默认 bridge 是两种东西：每个自定义网络有自己的 bridge 接口、自己的子网，接在里面的容器可以通过容器名或网络别名互相解析。例子把 pg 以别名 `postgres` 接进去，把 api 以别名 `api` 接进去，redis 创建时就直接接在 `shorty-net` 上。`docker network inspect` 的成员列表按名字排序后是 `shorty-api`、`shorty-pg`、`shorty-redis`，三个容器都在同一个二层域里。

接入之后，api 的 `/etc/resolv.conf` 变成 `nameserver 127.0.0.11`，并多了 `options ndots:0`；`getent hosts postgres` 返回 `postgres` 和它在 `shorty-net` 里分到的地址。`127.0.0.11` 是 Docker 内嵌 DNS 的固定地址，它只负责这个网络里的名字，外部域名会转发给宿主配置的 DNS。`ndots:0` 让不带点的名字先按绝对名字查询，避免被 search domain 干扰。

内嵌 DNS 是“按网络”的，不是“按容器”的全局服务。同一个容器接了两个自定义网络，每个网络里的别名分别生效；容器名在它接入的每个网络里都能解析，`--network-alias` 则只属于某一次连接。默认 bridge 没有这个解析器，所以 6.2 开头 `getent hosts postgres` 才只能返回失败，而不能像自定义网络那样返回一个地址。

最后两步验证 DNS 是“跟着网络成员关系走”的：把 pg 从 `shorty-net` 断开，api 里的 `getent hosts postgres` 立刻变成 `exit=2`；再接回去，同一个名字又能解析。这里重新连上又拿到了同一个地址，但这是 IPAM 的分配结果，不能依赖；容器重建、网络重连、扩缩容都可能换地址，所以代码里只写名字。

这也是自定义 bridge 和默认 bridge 的关键差别。默认 bridge 上的容器要换网络，只能停掉再用新的 `--network` 重建；自定义网络可以在容器运行中 `docker network connect` / `disconnect`，还能在连接时加 `--alias`。自定义网络还提供更好的隔离：只有接在同一个网络里的容器能互相访问，默认 bridge 上所有没写 `--network` 的容器都混在一起。

还有一个容易忽略的差别：默认 bridge 的配置（MTU、iptables 规则、绑定地址等）是全局的，改它要改 `daemon.json` 并重启 Docker；每个自定义 bridge 可以在 `docker network create` 时单独设 `--subnet`、`--gateway`、`-o com.docker.network.driver.mtu=...`。多个项目共用一台宿主时，这一点比“名字解析”更能避免互相踩踏：给每个项目一个网络，子网和规则互不干扰。

api 现在虽然能解析 `postgres`，但它的 `SHORTY_DB_URL` 仍然是旧 IP。下一节重建 api 时会把地址改成 `postgres`，顺便把 redis 地址也配上，让服务名真正进到配置里。

## 6.3 端口发布与 nftables/iptables

bridge 网络上的容器端口，默认对宿主和同一个网络里的其他容器开放，但对宿主之外、以及其他 bridge 网络里的容器不开放。要让外部访问，必须发布端口：`-p 8080:8080` 在宿主上开一个口，用防火墙规则把流量转给容器。Docker 文档把这件事描述成 NAT、PAT 和 masquerade 的组合；落到 Linux 上，入站是 `nat` 表里的 DNAT，出站是 `nat` 表里的 MASQUERADE。

```console
{{#include code/ch06/6_3_port_publish.out}}
```

重建后 `docker port` 给出两行：`0.0.0.0:8080` 和 `[::]:8080`，意思是宿主所有 IPv4 和 IPv6 地址上的 8080 都接。`docker inspect` 的 `NetworkSettings.Ports` 也是同样的两组 `HostIp`/`HostPort`。不写宿主 IP 时，`-p` 默认绑所有地址；这也是它“默认不安全”的原因：只要宿主有公网地址，端口就对外了。

`iptables -t nat -S DOCKER` 那一行是入站 DNAT 的直接证据：目的端口 8080 的包被改写到容器的 IP:8080，`! -i br-...` 表示从其他接口进来的包才匹配，`br-...` 是 `shorty-net` 对应的 bridge。包到宿主后先过 `PREROUTING`，在 `nat` 表被 DNAT 成容器 IP，再走 `FORWARD` 到 bridge；回包由 conntrack 按连接状态还原，不需要再写一条反向规则。这里用 iptables 看，是因为 lab 的后端是 iptables；Docker 29 切到 nftables 后端后，同样的 DNAT 会写进 nft 的 `docker-bridges` 表，6.6 再展开。

“经过了几层 NAT”可以这样回答：外部入站一次 DNAT，容器出站一次 MASQUERADE，返回方向由 conntrack 还原；不是每经过一个组件就做一次地址转换。宿主本机访问发布的端口时，还可能经过默认开启的 userland proxy（`docker-proxy`），它在宿主上监听同一个端口，把连接转给容器；6.7 的 `ss` 会看到这个进程。DNAT 规则和 `docker-proxy` 是配合关系，不是两套互相矛盾的机制。

如果宿主端口和容器端口不同，DNAT 还包含端口转换：`-p 8081:8080` 会把宿主 8081 改写到容器的 8080，这就是 PAT（Port Address Translation）。协议默认是 TCP，UDP 要写 `-p 8080:8080/udp`，SCTP 写 `/sctp`；同一个端口可以同时发布 TCP 和 UDP，但要写两条 `-p`。发布到指定宿主地址用 `-p 192.168.1.100:8080:80`，只绑 IPv4 可以用 `-p 0.0.0.0:8080:80`，只绑 IPv6 用 `-p '[::]:8080:80'`。

`-p 127.0.0.1:8080:8080` 把发布限制在宿主回环地址，`docker port` 只剩 `127.0.0.1:8080`。Docker 文档提醒：28.0.0 之前的版本里，同一 L2 网段的其他主机也能访问发布到 localhost 的端口（moby/moby#45610）；28.0.0 起修掉了这个行为。生产里优先用这种写法，前面再放反向代理。

`-P` 是另一种发布方式：它把镜像 `EXPOSE` 的端口随机映射到宿主的高端口。`shorty:dev` 没有 `EXPOSE`，所以例子用 `--expose 8080` 补一个；`docker port` 显示宿主分到了一个高端口，`curl` 这个随机端口也能返回 `ok`。`-P` 适合临时实验，不适合需要稳定入口的服务。

`EXPOSE` 本身只是镜像元数据，说明“这个镜像里的进程打算监听这个端口”，它不会自动发布端口，也不影响容器之间能不能访问。`-p` 不需要镜像先 `EXPOSE`，`-P` 才依赖它。把 `EXPOSE` 当成防火墙或访问控制是常见的误解：它既不打开宿主端口，也不限制容器网络。

端口发布是创建时决定的。`docker update --help` 的输出里没有 publish 相关的选项，`HostConfig.PortBindings` 在容器创建后就固定了；要换宿主端口或绑定地址，只能删掉容器重建。例子最后又重建了一次，把 api 改回只绑 `127.0.0.1:8080`。

> **旧资料提示**：有的材料把 `-p` 叫“NodePort publishing”。NodePort 是 Kubernetes Service 的概念，Docker 这里叫端口发布（port publishing）或端口映射；两者都在宿主上开端口，但实现和语义不同。Docker 的说法见端口发布页面。

## 6.4 host、none、overlay、macvlan/ipvlan

bridge 是单机默认，但不是唯一的网络驱动。选哪个驱动，取决于“容器需不需要自己的网络身份”和“要不要跨主机”。

`host` 让容器直接共享宿主的 network namespace：容器没有自己的 IP，`-p` 也不起作用，应用直接绑宿主端口。下面的例子先把 api 停掉，腾出 8080，再起一个 host 网络的 api：

```

`curl localhost:8080/healthz` 返回 `ok`，`docker inspect` 显示 `network_mode=host`、`ports={}`，说明没有端口映射这回事。容器里 `ls /sys/class/net` 看到的是宿主网卡（`eth0`、`docker0`、其他 bridge 和 veth），宿主的 `ss` 也直接看到 `shorty` 进程监听 `*:8080`。host 网络省掉了 NAT 和 `docker-proxy`，性能路径短，适合需要处理大量端口或对延迟敏感的场景。

host 模式在 Linux 上直接可用；Docker Desktop 4.34 起才支持，而且要在设置里显式打开。它和 `-p` 不兼容：如果用 `docker run --network host -p 8081:8080`，Docker 会警告 `Published ports are discarded when using host network mode`，然后忽略 `-p`。端口冲突也不再由 Docker 分配，而是应用 `bind()` 时自己发现，这正是例子里的报错形态。

第二个 host 容器没有再起一份网络栈，它和第一个共享宿主 netns，于是两个进程抢同一个 `:8080`。报错是应用自己打的 `listen tcp :8080: bind: address already in use`，不是 Docker 的端口分配错误。这一点要和 6.7 的 `port is already allocated` 区分：host 网络没有端口发布，Docker 不负责分配，冲突发生在 `bind()`。

`none` 更彻底：容器只有 loopback，没有 `eth0`，也没有 IPv6 loopback。它适合完全离线的批处理，或者你要自己把网卡塞进 netns 的场景。没有网络驱动帮忙，容器不能访问外部，外部也不能访问它。

`overlay` 是跨主机的网络：它在宿主网络之上用 VXLAN 把多个 Docker daemon 连成一个虚拟二层网络，容器可以像在同一台机器上一样按名字互访。即使用 standalone 容器，也必须先加入 Swarm；跨主机要放行 `2377/tcp`（Swarm 控制面）、`4789/udp`（overlay 数据）、`7946/tcp` 和 `7946/udp`（节点间通信）。`--attachable` 允许 standalone 容器接入，`--opt encrypted` 打开 VXLAN 层的 IPsec 加密。单机实验用不到它。

`macvlan` 给每个容器分配一个 MAC 地址，让容器在局域网里看起来像一台物理机：需要指定宿主父接口（`-o parent=eth0`），需要交换机支持混杂模式，容器会占用局域网的 IP。它的限制也很硬：容器不能直接和宿主通信（Linux 内核的限制），需要额外接一个 bridge 网络；rootless 模式不支持；多数云厂商会拦。它适合要保留原有网络身份的老应用。

`ipvlan` 和 `macvlan` 类似，但容器共享父接口的 MAC，只分配 IP。默认是 L2 模式；`ipvlan_mode=l3` 让宿主像路由器一样在不同子网间转发，L3 模式丢弃广播和组播，容器的默认网关指向自己的 `eth0`，并且要求容器网段和宿主默认网段分开。还有 `l3s` 模式。它的好处是 MAC 地址压力小，适合大规模和需要和物理网络集成的场景；代价是路由要自己规划。

这几种驱动不是按“新旧”排序的，而是按网络边界选的：容器只需要和同宿主上的其他容器说话，用 bridge；需要宿主网络栈的全部能力，用 host；完全不要网络，用 none；要跨主机，用 overlay；要让容器在物理交换机看来是一台独立主机，用 macvlan；要复用父接口 MAC、又需要 L3 路由，用 ipvlan。选错驱动通常不是“性能差一点”，而是地址规划、交换机配置或安全边界整个对不上。

单机实验优先用 bridge：不需要 Swarm、不需要物理网卡、不占局域网 IP，出问题也最容易在宿主上看到 veth 和规则。host 只在确实需要宿主网络栈时用；overlay、macvlan、ipvlan 的完整验证需要多主机或可控制的物理网络，本书没有在 lab 里验证它们，只按官方文档讲清边界。

## 6.5 link 为什么淘汰

`--link` 是 Docker 网络功能出现之前的容器互联办法。它在接收方容器的 `/etc/hosts` 里写一条静态记录，把源容器的名字或别名指到源容器的 IP；旧版本还会把源容器的环境变量注入接收方，包括 `DB_PORT_5432_TCP_ADDR` 这类连接信息。下面的例子在默认 bridge 上用 `--link` 起一个 busybox：

```

命令下面第一行就是弃用告警。Docker 文档说：默认 bridge 上的 link 已弃用，计划在 Docker Engine 30.0 移除；从 29.6 起，创建带 link 的容器会打印告警。这个 lab 是 29.9.2，实际告警文案是“deprecated and will be removed in a future release”，没有写死 30.0；版本和时间点以文档为准。

`/etc/hosts` 里有一行 `db ... shorty-pg`：别名 `db`、源容器 ID、源容器名都在同一行。`ping db` 能通，`docker inspect` 的 `HostConfig.Links` 是 `["/shorty-pg:/ch06-link/db"]`。但 `env | grep '^DB_'` 没有任何输出：Docker 28.4 弃用 link 环境变量，29.0 起默认关闭，计划在 30.0 移除。也就是说，在 29.x 上，link 剩下的主要就是这条静态 hosts 记录。

这条记录有几个根本问题。第一，方向单一：只有接收方能解析源，源不能反过来解析接收方；两个容器要双向访问，就得建两条 link。第二，静态：它绑定的是创建时的容器 IP，源容器重建、扩缩容、滚动更新都不会自动变成服务发现。第三，注入环境变量会把源容器的所有 Docker 环境变量暴露给接收方，包括可能误放的敏感信息；Docker 文档专门警告过这一点。

Docker 文档说，源容器重启后，接收方的 `/etc/hosts` 会更新成新 IP。这个行为在“一个源、一个接收方”的小实验里看起来够用，但它仍然不是服务发现：一个别名只能指一个容器，多副本时没有负载均衡，源容器扩缩容时接收方也不会知道。数据库这类单实例服务可以靠它勉强工作，前端访问后端这类多副本场景就不行。

替代方案就是 6.2 的自定义网络加内嵌 DNS：容器名和 `--alias` 由 `127.0.0.11` 解析，网络成员变化时 DNS 记录跟着变；需要给服务一个稳定名字，就在 `docker network connect` 时加别名，或者在建容器时用 `--network-alias`。应用配置里写 `postgres`、`redis`、`api`，不写 IP，也不依赖 `/etc/hosts` 的静态行。

迁移时要注意，link 的环境变量名和自定义网络的别名不是一回事。旧代码可能读 `DB_PORT_5432_TCP_ADDR`，这个变量在 29.x 默认不再注入；换成自定义网络后，要把连接地址改成 `postgres:5432` 这样的“名字 + 端口”，而不是继续找环境变量。应用如果依赖 `<别名>_ENV_<变量>` 这类注入，需要改成显式配置或配置文件。

Docker 文档说非默认网络上的 link 仍然支持；但“支持”不等于“推荐”。它仍然是静态 hosts 记录，仍然没有服务发现。新项目直接用自定义网络，老项目迁移时把 `--link` 换成网络别名，通常只需要改连接地址和加一条 `docker network connect`。

> **旧资料提示**：旧教程用 `--link db:db` 做容器互联。默认 bridge 上的 link 已弃用，计划在 Docker Engine 30.0 移除，29.6 起创建时告警；替代是自定义网络 + 内嵌 DNS。不要在新项目里再用 `--link`。

## 6.6 防火墙：Docker 为什么绕过 UFW

Docker 不走 UFW 的规则，不是因为 Docker 故意和 UFW 作对，而是因为两者工作的位置不同。UFW 管的是宿主 `INPUT`/`OUTPUT` 链，按“进入宿主本机的流量”做过滤；Docker 发布端口时在 `nat` 表的 `PREROUTING` 做 DNAT，包在到达 `INPUT` 之前就已经被改写并转发给容器了。Docker 文档的原话是：流量在到达 ufw 使用的 `INPUT`/`OUTPUT` 链之前就被改道了。

从包的路径看更清楚：外部包到宿主网卡，先过 `PREROUTING`，在 `nat` 表命中 DNAT，目的地址变成容器 IP；然后内核重新做路由决策，发现目的地是 `docker0` 或 `br-...` 所在的网段，于是走 `FORWARD` 链，而不是 `INPUT`；最后从 bridge 出去到容器。UFW 的 `INPUT` 规则在这一路上根本没有被查询，所以“我明明 deny 了 8080”不会生效。回包走 `FORWARD` 和 conntrack，也不需要 UFW 放行。

Docker 在 iptables 后端下会建一组自己的链：`DOCKER-USER`、`DOCKER-FORWARD`、`DOCKER`、`DOCKER-BRIDGE`、`DOCKER-INTERNAL`、`DOCKER-CT`，以及 Swarm 用的 `DOCKER-INGRESS`；`FORWARD` 链会跳到这些链。`DOCKER-USER` 是留给用户的入口，规则在 Docker 自己的规则之前执行。注意包到达 `DOCKER-USER` 时已经过了 DNAT，所以匹配到的是容器 IP 和容器端口；要按原始目的地址/端口匹配，得用 `conntrack` 的 `--ctorigdst`/`--ctorigdstport`。

`docker info` 给出 `firewall_backend=iptables`，这是 Docker 29 的默认后端。`nft list tables` 里能看到 `ip nat`、`ip filter`、`ip6 nat`、`ip6 filter`、`ip raw`，这些表是 iptables-nft 的兼容层，不是 Docker 的 nftables 后端。`nft list chain ip nat DOCKER` 的警告写得很清楚：“table ip nat is managed by iptables-nft, do not touch!”；规则体里显示的是 `xt target "DNAT"`，因为 nft 只能把 iptables 的扩展目标当成兼容目标展示，真正的匹配条件要到 `iptables-save` 里看。

`nft list chain ip nat POSTROUTING` 里的 `MASQUERADE` 是容器出站的源地址转换：`172.19.0.0/16` 和 `172.18.0.0/16` 的包从对应 bridge 出去时，源地址被改成宿主地址。`DOCKER-USER` 链是空的；如果要在 Docker 的规则之前加过滤，就往这里插规则。

`iptables-save` 的第一行带 `(nf_tables)`，说明这个“iptables”命令操作的是 nf_tables 内核接口，不是老的 x_tables。后面的 DNAT/MASQUERADE 规则和 nft 看到的是同一批，只是 iptables 的语法把匹配条件和目标写得更完整。这个区别很重要：看到 `nft list ruleset` 里有规则，不代表 Docker 用的是 nftables 后端；在 29.x 上默认仍是 iptables 后端，只是 iptables 本身跑在 nf_tables 上。

Docker 29.0 起支持 `firewall-backend=nftables`，但官方标为实验特性。切到 nftables 后端后，Docker 不再建 `DOCKER-USER` 链，而是建 `ip docker-bridges` 和 `ip6 docker-bridges` 两张表，里面的 base chain 用固定的 priority；overlay 的规则还没有从 iptables 迁移，所以 Swarm 模式下不能启用。Docker 也不会再自动打开 IP forwarding，需要宿主自己设 `net.ipv4.ip_forward=1` 和 `net.ipv6.conf.all.forwarding=1`，否则创建需要转发的 bridge 网络会报错。原有 `DOCKER-USER` 里的规则不会自动迁移；nftables 里没有“先 ACCEPT 就最终通过”的语义，要放行被 Docker drop 的流量得用 `--bridge-accept-fwmark` 标记。

这也是为什么排障时不能只看一个工具。iptables 后端下，`iptables-save` 和 `nft list ruleset` 都能看到规则，因为 iptables 可能跑在 nf_tables 上；nftables 后端下，规则在 `docker-bridges` 表里，`iptables-save` 不一定能看到，`DOCKER-USER` 也可能根本不存在。先确认 `docker info` 的 `FirewallBackend`，再决定读哪一侧，能省掉很多“规则明明在、为什么不生效”的困惑。

那 UFW 的 `DEFAULT_FORWARD_POLICY` 呢？它是 UFW 自己的转发默认策略，控制的是 UFW 管理的 `FORWARD` 链默认动作，不是 Docker 的容器策略。把它设成 `ACCEPT` 只是让转发不被 UFW 拦，既不会只放行某个容器端口，也不会给容器之间加隔离。要限制入站，应该在 `DOCKER-USER` 链里按源地址/接口加规则，或者在 nftables 后端下建自己的表和 base chain；要限制容器之间，得靠 Kubernetes NetworkPolicy（第 24 章）或主机上的其他机制，UFW 不是容器防火墙。

同一 bridge 网络里的容器默认可以访问对方的所有端口，Docker 文档明确说这是“unrestricted network access”。所以“容器之间没有防火墙”不是危言耸听，而是默认值。需要隔离时，要么把容器放进不同的自定义网络，要么在支持 NetworkPolicy 的编排平台上定义策略；只开 UFW 不会改变容器之间的东西向流量。

## 6.7 排障：连不上是 DNS、监听地址还是防火墙

“连不上”至少有三类原因，报错文本能把它们分开。DNS 失败通常是没有这个名字，或者解析到错的地址；路由/防火墙问题通常表现为超时；`connection refused` 则是包到了目标机器的网络栈，但目标地址和端口上没有监听者。下面的例子故意让 api 监听 `127.0.0.1:8080`，再从另一个容器访问 `api:8080`。

```console

```

先看 api 的启动日志：`"addr":"127.0.0.1:8080"`，它只监听回环地址。从 `shorty-net` 里的 busybox 看，`ping api` 能解析并收到回包，`ip route` 的默认网关指向 bridge，说明 DNS 和路由都正常。但 `wget http://api:8080/healthz` 报 `Connection refused`，不是超时，也不是“bad address”。

`nsenter -t <pid> -n ss -lntp` 给出答案：api 的 netns 里只有 `127.0.0.1:8080` 在监听，没有 `0.0.0.0:8080` 或容器 IP 上的 8080。从别的容器访问时，目标地址是容器的 IP，包到了容器网卡，但内核发现这个地址上没有监听者，于是回 RST，客户端看到的就是 `Connection refused`。`nsenter` 里的 `ip route` 也确认容器有 `172.19.0.0/16` 的直连路由和默认网关，进一步排除了路由问题。

这里有个容易误判的地方：宿主 `curl localhost:8080` 的结果不能代表容器里应用监听了哪个地址。发布端口只说明宿主上有人接，DNAT 的目标是容器 IP；应用只监听容器里的 `127.0.0.1` 时，这条路径可能被 `docker-proxy` 接住，也可能直接失败。判断时不要只看宿主端口是否在听，要进容器的 netns 看应用到底绑在哪个地址。`docker logs` 里的 `"addr":"127.0.0.1:8080"` 往往比 `docker port` 更直接。

修复是把 `SHORTY_LISTEN` 从 `127.0.0.1:8080` 改成 `:8080`，重建容器。改完后同一个 busybox 的 `wget http://api:8080/healthz` 返回 `ok`。这也说明 `-p 127.0.0.1:8080:8080` 只限制“宿主上哪个地址能进来”，不改变容器里应用监听哪个地址；应用只监听回环时，连宿主发布端口也可能失败，因为 DNAT 的目标是容器 IP，不是容器里的 `127.0.0.1`。

第二个故障是端口冲突。api 已经发布在宿主 `127.0.0.1:8080`，再起一个同样 `-p 8080:8080` 的容器：

```console

```

Docker 在设置容器网络时就失败了，报 `Bind for 127.0.0.1:8080 failed: port is already allocated`。这个错误发生在应用启动之前，所以容器日志里不会有 shorty 的输出。`docker ps --filter publish=8080` 找到占用者是 `shorty-api`，宿主的 `ss` 看到 `docker-proxy` 监听 `127.0.0.1:8080`。换一个宿主端口 `-p 8081:8080` 就能并存，容器里仍然是 8080；或者停掉旧的 `shorty-api`。

两类冲突要分开看。host 网络的冲突是应用 `bind()` 失败，Docker 已经把容器启动了，只是进程退出；发布端口的冲突是 Docker 在配置 NAT 和 `docker-proxy` 时发现宿主端口被占，容器根本没有启动。前者去查应用为什么绑这个端口，后者去查宿主上谁占了端口；`docker ps` 的 `PORTS` 列、`docker port` 和 `ss -lntp` 是三个不同的视角，要对着看。

把两个故障放在一起，排障顺序可以固定下来：先用 `getent hosts`/`ping` 确认名字解析，再用 `ip route` 确认网段和默认网关，然后用 `ss -lntp`（或 `nsenter` 进 netns）确认监听地址，最后才看防火墙和端口发布。`Connection refused` 优先怀疑监听地址；超时优先怀疑防火墙、路由或安全组；名字解析失败才去看 DNS 和 `/etc/hosts`。端口冲突则在 `docker run` 阶段就会报 `port is already allocated`，不用进容器。

本章结束时，`shorty-api`、`shorty-pg`、`shorty-redis` 都在 `shorty-net` 上，`postgres`、`redis`、`api` 三个名字可解析；api 监听 `:8080`，发布在宿主 `127.0.0.1:8080`，数据库连接串里写的是 `postgres`，不再是容器 IP。

## 上生产前

**用自定义网络，不要用默认 bridge + `--link`。** 默认 bridge 没有内嵌 DNS，容器只能按 IP 访问；`--link` 是静态 hosts 记录，方向单一，计划在 Engine 30.0 移除。给每组服务建一个自定义网络，用容器名或 `--network-alias` 当服务名，代码和配置里不写容器 IP。需要把一个运行中的容器临时接入另一个网络时用 `docker network connect`，不要重建。

**只发布必要端口，优先绑 `127.0.0.1`。** `-p 8080:8080` 默认绑宿主所有地址，宿主有公网 IP 时端口就直接对外；`-p 127.0.0.1:8080:8080` 只允许宿主本机访问，公网入口交给反向代理或负载均衡。数据库、Redis 这类后端不发布端口，只让同一网络里的应用访问。发布前确认宿主端口没有被其他服务占用，`docker ps` 的 `PORTS` 列和 `ss -lntp` 都要看。

**不要把 UFW 当容器策略。** Docker 在 `nat` 表做 DNAT，流量在到达 UFW 的 `INPUT`/`OUTPUT` 之前就被转给容器；`DEFAULT_FORWARD_POLICY` 只是 UFW 自己的转发默认值，不是按容器端口的策略。要限制入站，在 iptables 后端的 `DOCKER-USER` 链里加规则，或在 nftables 后端下建自己的表和 base chain；要限制容器之间，用 Kubernetes NetworkPolicy（第 24 章）或平台提供的网络策略。同一 bridge 网络内的容器默认可以互访所有端口，这一点要在威胁模型里写明。

**端口发布在创建后不可变，先规划再创建。** `docker update` 没有发布端口的选项，`HostConfig.PortBindings` 在创建时固定；改宿主端口、绑定地址或协议都要重建容器。把宿主端口当成部署参数管理，避免和宿主服务、其他容器冲突；临时实验用 `-P` 随机端口，生产入口用固定端口加反向代理。

**切换 nftables 后端要先测试。** Docker 29 的 nftables 后端仍是实验特性，规则写在 `ip docker-bridges`/`ip6 docker-bridges`，没有 `DOCKER-USER` 链，overlay 规则未迁移，Swarm 模式下不能启用。切换后 Docker 不会自动打开 IP forwarding，原有 `DOCKER-USER` 规则可能被忽略；先在预发验证发布端口、容器出站和自定义规则，再动生产。

- [IPvlan network driver](https://docs.docker.com/engine/network/drivers/ipvlan/)：L2/L3 模式、共享 MAC 和 L3 的广播/组播限制。
