# 第 13 章 软件供应链：SBOM、provenance、签名与验签

第 12 章结束时，`shorty:0.1` 已经推到了本地 registry，Pod 清单里写的是 `@sha256:...` 而不是 `:0.1`。这解决了“内容有没有被换掉”：只要 digest 对得上，拉下来的字节就是当初那一份。但它没有回答另外三个问题。第一，这一份镜像里到底装了什么，除了 shorty 自己的二进制，还有哪些基础镜像的包和语言依赖？第二，这个 digest 是谁、在什么机器上、用什么参数构建出来的，构建时用的是不是我们 review 过的 commit？第三，集群能不能在 Pod 创建之前就拒绝一个没有签名、或者签名者对不上的镜像？

digest 只证明“内容没变”，不证明“内容是我构建的”。攻击者如果能往 registry 推一个 tag，就可以把 `shorty:0.1` 指到另一份字节完全不同的镜像；这份镜像有自己的合法 digest，你的清单如果还写 tag，就会拉到它。反过来，即使 digest 没变，镜像里多了一个有已知漏洞的依赖，digest 也不会告诉你。供应链安全要补的正是这几段空白：用 SBOM 说明里面有什么，用 provenance 说明怎么构建的，用签名把“这个 digest 由持有某把密钥的人认可”固定下来，最后用准入控制器把“只部署验过签的镜像”变成集群策略。

这一章继续用 shorty 的 `api` 镜像。先在本地 registry 上给它加 SBOM 和 provenance，再看这两种 attestation 长什么样；然后生成密钥、对 digest 签名并验签；接着把公钥交给 policy-controller，让 Kubernetes 在准入阶段拒绝未签名镜像；最后用 Trivy 和 `docker build --check` 做扫描门禁，并把签名、SBOM、provenance 放在一起盘点。DCT（Docker Content Trust）和 Notary v1 只作为历史对照出现：它们不是今天的主线，本章也不安排示例。

> **起点**：第 12 章结束时的本地 registry 里有一个未签名的 `shorty:0.1`，Kubernetes 还没有接入验签。第 12 章的 registry 发布在 `localhost:5000`，只有 lab 自己能访问；本章 13.4 要让 kind 节点和 webhook 也能拉签名，setup 把它换成监听 docker0 网关的 `172.18.0.1:5000`（HTTPS，自签 CA），示例里的 `$REG` 就是它。运行 `bash code/ch13/setup.sh` 会把 lab 带到这个起点：起 registry，装 cosign 2.4.1，预拉 Trivy 和 policy-controller 的镜像，预热漏洞库，并推一个未签名的 `shorty:0.1`。本章后面会在这个 registry 上构建、签名，再起一个单节点 kind 集群做准入实验。

## 13.1 SBOM：镜像里到底有什么

SBOM（Software Bill of Materials，软件物料清单）是镜像内容的依赖清单：每个包的名称、版本、许可证、来源，以及包与文件之间的包含关系。它有两种常见格式，SPDX 和 CycloneDX；Docker 的 BuildKit 生成的是 SPDX JSON 文档，外面包一层 in-toto 的 attestation 信封。清单本身不是漏洞报告：它只列“有什么”，有没有 CVE 要拿版本去漏洞库里匹配，这是 13.5 扫描要做的事。

BuildKit 在构建时生成 SBOM，不需要先把镜像拉到别处再扫。打开方式是 `--sbom=true`，等价于 `--attest type=sbom`；默认用 BuildKit 的 Syft scanner 扫描最终阶段。SBOM 作为一条 attestation 记录挂在镜像索引（image index）上，而不是塞进 `linux/amd64` 那个镜像 manifest 里。因此 `docker buildx imagetools inspect` 会看到一个 `Platform: unknown/unknown` 的条目，注解写着 `vnd.docker.reference.type: attestation-manifest`，它指向真正的平台镜像 digest。也正因为它是索引里的一个 manifest，查看 SBOM 不需要把整个镜像层拉下来。

构建输出的最后几行里，`exporting attestation manifest` 是 SBOM 被写进索引的证据，`exporting manifest list` 则是整个索引的 digest。`imagetools inspect` 列出两个 manifest：`linux/amd64` 是能运行的镜像，`unknown/unknown` 是 attestation；后者的 `vnd.docker.reference.digest` 指回前者的 digest，说明它不是另一个平台的镜像，而是这份镜像的附属记录。attestation manifest 里可以放多条 predicate，13.2 同时打开 SBOM 和 provenance 时，仍然只有一个 `unknown/unknown` 条目，两种记录作为这个 manifest 的不同 layer 一起推上去。

SBOM 的内容可以直接从 `.SBOM.SPDX` 取出来。这里打印 SPDX 版本、包数量和前几个包：`SPDX-2.3` 是文档格式版本，`packages: 19` 是这份镜像里识别出的包数。前面几行是 distroless 基础镜像带进来的 `base-files`、`ca-certificates`，后面是 Go 二进制里的模块信息，`github.com/jackc/pgx/v5@v5.11.0`、`github.com/redis/go-redis/v9@v9.23.0` 这些是 shorty 真正依赖的库。shorty 的最终镜像基于 distroless，没有 shell 和包管理器，Syft 是从二进制的 Go module 信息里读出这些模块的，不是从 `/var/lib/dpkg` 读的。

这里有一个容易误解的边界：默认只扫最终阶段。shorty 的多阶段 Dockerfile 里，`golang:1.27.3-trixie` 那个构建阶段装了 Go 工具链、下载了模块缓存，这些内容不会进入最终镜像，默认也不会进 SBOM。如果构建阶段本身有漏洞，或者你想知道构建时用了哪些工具，需要在 Dockerfile 里用 `ARG BUILDKIT_SBOM_SCAN_STAGE=true`（或指定阶段名）扩大扫描范围，构建上下文则用 `BUILDKIT_SBOM_SCAN_CONTEXT=true`。这两个值只能用显式 `ARG` 声明，不能用环境变量替换。对 shorty 来说，Go 模块已经编进二进制、能被扫到，但构建工具链不在清单里，这是读 SBOM 时要知道的缺口。

SBOM 也不负责证明“这份清单是构建者给这个 digest 的”。它只是随镜像推上去的 JSON，任何人都可以在自己的构建里生成一份内容不同的 SBOM。要让别人相信这份清单确实属于某个 digest、由某个人构建，需要下一节的 provenance，以及 13.3 的签名。

SPDX 和 CycloneDX 都能表达“包、版本、许可证、关系”，区别在字段组织和工具生态；BuildKit 直接给的是 SPDX，接入其他工具生成的 CycloneDX 时，attestation 的 `predicateType` 会不同，下游的扫描器和策略要按类型解析，不能假定所有 SBOM 都是同一种 JSON。

## 13.2 provenance：谁在什么环境构建的

provenance（来源证明）记录构建过程：构建器是谁、构建从哪个源和 commit 开始、用了哪些材料（基础镜像、Dockerfile 前端、SBOM 扫描器）、构建参数是什么、什么时候开始和结束。它同样以 attestation 的形式挂在镜像索引上，默认是 SLSA provenance schema。Docker 文档把详细程度分成两档：`mode=min` 是默认值，只记录时间、frontend、材料、源仓库和 revision、平台等最少信息；`mode=max` 额外记录完整的 LLB 构建步骤、Dockerfile 原文（base64）和层与构建步骤的映射。排查“这个镜像到底是怎么构建出来的”时，`max` 的信息量明显更大。

SLSA 是构建来源可信度的一套分级，不是漏洞等级。一个镜像可以 provenance 很完整、却带着一个刚公开的 CVE；也可以没有 provenance、但内容是干净的。两者解决不同问题，不能用一个分数代替另一个。本章只生成和验证 provenance，不宣称 shorty 达到了某个 SLSA 级别；级别要看构建器是否受控、材料是否可验证、provenance 是否由构建平台自动签发，这些是 CI 平台和构建基础设施要保证的事。

`mode=max` 的代价是会把构建参数的值写进 attestation。Docker 文档明确警告：不要用 `--build-arg` 传密码、token 等敏感值，否则它们会进入 provenance；需要构建期凭据时用 `--mount=type=secret`，secret 不会离开构建过程，也不会进 provenance。shorty 的 Dockerfile 用 `ARG VERSION` 传版本号，这是可以公开的值；如果把数据库密码写成 `ARG DB_PASSWORD`，即使构建成功，密码也已经跟着 attestation 推到 registry 了。

provenance 和 SBOM 一样，只是“随镜像推上去的记录”，BuildKit 不会替它签名。下面先用 cosign 给这两种 attestation 签一次名，确认 `.att` 标签里的内容确实由持有 attest 私钥的人签过，再在 13.4 给镜像本身签名。

上一节看到，BuildKit 生成 SBOM 和 provenance 后只是把它们作为 manifest 推到 registry，attestation 本身没有签名。`cosign verify-attestation` 要找的是 cosign 自己签出来的 `.att` 记录，不是索引里那个 `unknown/unknown` manifest。所以要把 provenance 纳入验签链，得先用 `cosign attest` 把同样的 predicate 包成 in-toto statement、用私钥签一次，再推到 `<repo>:sha256-<digest>.att` 这个标签上。SBOM 同理，用 `--type spdxjson` 再签一次，两个 DSSE 信封会追加到同一个 `.att` 标签。

cosign 支持两种密钥模式：本地密钥对和 keyless（OIDC）。keyless 用 Fulcio 签发短期证书、把签名事件写进 Rekor，验证时用 `--certificate-identity` 和 `--certificate-oidc-issuer` 约束身份，Kubernetes 文档里的发布流程就是这么验的。keyless 省掉了长期私钥，但依赖 OIDC 身份提供方和公开的透明日志；本书的 lab 没有云账号，所以用密钥对，把这条依赖留在本地。密钥对用 `cosign generate-key-pair` 生成，私钥默认写 `cosign.key` 并用口令加密，口令从 `COSIGN_PASSWORD` 读，避免交互式输入。

## 13.3 签名：cosign 与 digest

镜像签名和 attestation 签名用的是同一套 cosign 机制，区别在签名对象：`cosign sign` 签的是镜像 manifest 的 digest，`cosign attest` 签的是 attestation 的 predicate。签名对象是 digest，不是 tag。`cosign sign $IMAGE:0.1` 会先把 tag 解析成 digest，再对 digest 签名；签名存成仓库里的 `sha256-<digest>.sig` 标签，而不是改写 `0.1` 这个 tag。把 tag 移到另一个 digest，`.sig` 标签不会跟着移动，原来的签名仍然只属于原来的 digest。

签名私钥的安全等级决定了签名的意义。私钥放在 CI 的仓库变量里，任何能改流水线的人都能拿到它，签名就退化成“谁都能签”；私钥放在 KMS/HSM，签名请求要经过云权限和审计，泄露风险小得多。keyless 则把长期私钥换成了 OIDC 身份和短期证书，验证方用 `--certificate-identity` 约束“必须是某个 CI 工作负载”，用 `--certificate-oidc-issuer` 约束签发者；代价是依赖 Fulcio/Rekor 的可用性。无论哪种方式，密钥和身份都要能轮换，轮换后旧 digest 的签名仍然要能验。

## 13.4 准入验签：把“能部署”变成策略

签名只解决“这个 digest 被某把私钥认可过”。要让集群只运行被认可的镜像，还得在 API Server 的准入链上拦一道。Kubernetes 的准入控制发生在对象写入 etcd 之前：创建 Pod 时，API Server 把请求交给注册的 validating admission webhook，webhook 返回 allow 或 deny，deny 的话对象根本不会创建。sigstore 的 policy-controller 就是这样一个 webhook：它监听 `ClusterImagePolicy`，从 Pod 的 `image` 字段解析出 registry、仓库和 digest，去同一个 registry 拉 `.sig` 和 `.att`，用策略里配置的公钥验签，再决定放行还是拒绝。

`ClusterImagePolicy` 是集群级对象。`spec.images[].glob` 决定哪些镜像受管，`spec.authorities[]` 决定用哪些公钥或 keyless 身份验收，`spec.mode` 决定拒绝还是只警告。下面的清单匹配以 `__REGISTRY__/shorty` 开头的所有镜像，要求签名者是 `cosign-system` 命名空间里 `cosign-pub` Secret 中的公钥；示例运行时会把 `__REGISTRY__` 换成实际的 registry 地址：

policy-controller 还有一个默认值：`no-match-policy` 没有配置时，不匹配任何 `ClusterImagePolicy` 的镜像也会被拒绝，chart 的 README 写明了这一点。本章的 glob 覆盖 shorty，所以签名镜像能过；如果命名空间里还有别的镜像，要么扩大 glob，要么在 `config-policy-controller` 里显式设 `allow` 或 `warn`，否则它们会在策略上线后被一起挡住。

示例在装 policy-controller 之前先把未签名镜像跑了一次，Pod 正常 Ready。这一步很重要：它说明本 lab 默认配置下的 kubelet 和节点 containerd 不会替我们验签，镜像只要 digest 存在就能拉下来运行；验签是准入层的职责，不是运行时的默认行为。接着在 `mode: warn` 下再建一个未签名 Pod，API Server 返回 `Warning`，内容里能看到 `signature key validation failed ... no signatures found`，但 Pod 仍然创建成功。这就是 audit：策略在观察流量，把会被拒绝的对象记下来，而不影响现有部署。

把 `mode` 改成 `enforce` 后，同样的未签名镜像会被拒绝，错误是 `admission webhook "policy.sigstore.dev" denied the request: validation failed: failed policy: shorty-signed`，后面跟着 `signature key validation failed ... no signatures found`。注意这条拒绝信息出现在 `kubectl` 的错误里，不在 Pod 的 Event 里：Pod 对象没有创建，就不会有 Pod Event，也没有 Pod 可查。排查时应该看 API Server 的审计日志、webhook 自己的日志，或者直接把 `kubectl apply` 的错误留下来，而不是去 `kubectl describe pod` 一个不存在的对象。

最后用 `$REG/shorty@$DIGEST` 建 Pod，策略验签通过，kubelet 从同一个 registry 拉镜像，Pod 进入 Ready。镜像引用写成 digest，而不是 `:0.1`，这样即使 tag 后来被移动，Pod 拿到的仍然是策略验过的那一份；如果写 tag，webhook 验的是 tag 当前指向的 digest，tag 一换，验签对象也就换了。

webhook 的 `failurePolicy` 默认是 `Fail`：webhook 不可用、超时，或者它访问不了 registry，API Server 会拒绝请求。对安全策略来说这通常是想要的 fail-closed，但它也意味着 registry 或 policy-controller 一挂，带标签的命名空间就创建不了新 Pod。生产上要么给 webhook 多副本和足够的超时，要么把 `failurePolicy` 改成 `Ignore` 并接受“webhook 挂掉时放行”的风险；这个取舍要在策略上线前想清楚，不能等故障时再改。

## 13.5 扫描与门禁

SBOM 回答“有什么”，Trivy、Grype 这类扫描器回答“这些东西有没有已知漏洞”。Trivy 会读 OS 包数据库（apk、dpkg、rpm）和语言依赖（Go module、npm、pip 等），把包版本和漏洞库比对；它不执行镜像，也不需要镜像能启动。CI 里常见的门禁是 `--severity HIGH,CRITICAL --exit-code 1`：只关心高危和严重，发现一个就让命令以非 0 退出，流水线在这一步停下。

扫描数据库是门禁里最容易在离线环境翻车的一环。Trivy 默认启动时检查并下载新库，CI 跑在无外网或限流的网络里就会失败。做法有两种：在 CI 镜像里预置固定版本的库并用 `--skip-db-update`，或者把库缓存目录挂成持久卷、在流水线开始前显式更新。固定库版本的好处是同一份代码在不同时间跑出可复现的结果，代价是新漏洞要等下一次更新；缓存的好处是快，但缓存损坏或过期时会得到过期结果。两种都要在流水线里留下库的版本或更新时间。扫描报告也要存档，并和镜像 digest 绑定；只留一个退出码，事后无法证明当时扫的是哪一份镜像、用的哪一版库。

构建配置本身也能挡。Docker 的 build checks 从 Dockerfile 1.8 起提供，Buildx 0.15.0 起支持；它不执行构建，只检查 Dockerfile 和构建选项。下面的 `check.Dockerfile` 有三类问题：`MAINTAINER` 已弃用，`ENV API_TOKEN` 把敏感值写进镜像配置，`CMD echo hello` 不是 JSON 形式、信号处理会不对。`docker build --check` 把三条都报出来并以 1 退出；换成 `check-fixed.Dockerfile` 后输出 `Check complete, no warnings found`：

CI 里还有一个顺序问题：先构建、测试，再推送。Docker 文档的 test-before-push 流程是先用 `load: true` 把镜像导进本地 Docker，跑测试，确认能启动后再做多平台构建并 `push: true`。如果先推再测，测试失败的镜像已经进了 registry，tag 也可能已经被覆盖；后面即使回滚，别人仍可能在那段时间里拉到坏镜像。测试通过后再推，registry 里的 digest 才有“测过”的含义。

## 13.6 供应链威胁模型

把前面几节串起来，供应链攻击面大致是五类。**typosquatting（错拼抢注）**：攻击者注册一个和常用镜像名只差一个字符的仓库，开发者手滑就拉错；对策是把镜像名写全、用 digest，并在准入层只允许受信任的 registry 前缀。**可变 tag**：`shorty:0.1` 可以被重新推到另一个 digest，清单里写 tag 就等于把“拉什么”交给 registry 的当前状态；对策是部署 digest。**被投毒的构建器**：CI runner 或 BuildKit 被替换后，构建出的镜像和 provenance 都可能是假的；对策是受控 builder、固定构建镜像、用 `builder-id` 和 provenance 核对构建来源，必要时要求 SLSA 级别。**泄露的 CI token**：能推 registry 的 token 一旦泄露，攻击者可以覆盖 tag、删签名；对策是最小权限、短期凭据、把构建和签名权限分开、定期轮换。**依赖混淆**：内部包名和公共仓库重名时，构建可能拉到攻击者发布的同名包；对策是锁定包源、提交 lockfile、用 SBOM 核对实际解析到的版本。

供应链记录不是签完就结束，registry 里的签名、attestation 和镜像 digest 要定期对账，发现 tag 被移动、签名被删或 provenance 缺失时能追溯到时间和操作者。

防御不是单独某一项，而是一条链：digest 固定内容，受控 builder 和 provenance 说明来源，SBOM 说明依赖，签名把 digest 和签名者绑定，准入验签保证只有绑定过的 digest 能进集群。缺任何一环，攻击者都有绕过的空间。比如只签 tag 不签 digest，tag 一换签名就失效；只生成 SBOM 不签名，SBOM 可能是攻击者构建时伪造的；只在 CI 里验签、不在准入层验，集群里仍然可以 `kubectl run` 一个未签名镜像。

```console

```

输出里的 `.att` 标签下有两个 DSSE 记录，分别对应 `https://spdx.dev/Document` 和 `https://slsa.dev/provenance/v0.2`；`.sig` 标签下是镜像签名。三项都指向同一个 digest，这才是“这个镜像有完整的供应链记录”的意思。`cosign tree` 只按标签发现记录，如果镜像被复制到另一个 registry 而没有复制 `.sig`/`.att`，树里就只剩镜像本身；跨 registry 复制时要么把签名一起复制，要么在新 registry 重新签。

如果要在准入层连 provenance 一起卡，`ClusterImagePolicy` 的 `authorities[].attestations[]` 可以按 `predicateType` 要求某类 attestation，缺了就不放行。本章的示例只演示了镜像签名这一条，没有在 lab 里验证 attestation 策略；写生产策略时可以先从“必须有 slsaprovenance、且 builder.id 符合预期”开始，再逐步加 SBOM 内容检查。

> **旧资料提示**：旧教程把 Docker Content Trust 当成推荐方案，`export DOCKER_CONTENT_TRUST=1` 后只允许拉签名过的 tag。DCT 正在退役，Notary v1 服务 `notary.docker.io` 将在 2026 年 12 月 8 日停止；它签的是 tag，和今天 cosign 签 digest、准入层验签的模型不是一回事。新项目应转向 cosign/Sigstore。

> **旧资料提示**：旧资料说“容器运行时会自动验证镜像签名，Kubernetes 不参与”。本章的未签名 Pod 在策略安装前正常跑起来了，验证发生在准入控制器；Kubernetes 文档给出的验签路径也是 policy-controller 这类准入 webhook，而不是等 kubelet 拉镜像时自动完成。

> **旧资料提示**：旧流水线把扫描当成可选的报告步骤，扫出什么都继续推。现在的做法是把 `--severity HIGH,CRITICAL --exit-code 1` 和 `docker build --check` 放进主流水线，扫描失败就停止；例外要有负责人、到期时间和记录，不能靠“先推上去再说”。

## 13.7 排障：cosign 验不过、策略拒绝所有 Pod

`cosign verify` 报 `no matching signatures` 或 `no signatures found` 时，先分清验的是谁。cosign 的签名对象是 digest：`cosign sign` 如果收到 tag，会先解析成 digest 再签，签名存成 `sha256-<digest>.sig`。之后 tag 被移到另一个 digest，`cosign verify $IMAGE:tag` 就会去验新 digest，找不到签名。排查的第一步是把 tag 解析成 digest，和签名时记录的 digest 对比：

```console
{{#include code/ch13/13_10_troubleshoot.out}}
```

`cosign tree` 按 `.sig` 和 `.att` 标签找记录，标签名里直接带 digest；如果树里只有镜像、没有 `.sig`，说明这个 digest 没有签名，而不是签名“内容不对”。第二步确认签名和镜像在同一个 registry、同一个仓库：cosign 把签名写在镜像仓库的独立 tag 上，把镜像 `docker pull`/`docker push` 到另一个 registry 不会自动带走 `.sig`/`.att`；跨 registry 迁移要么用能复制 referrers 的工具，要么在新 registry 重新签。第三步确认验签用的公钥就是签名用的私钥对应的公钥，`cosign.pub` 和 `attest.pub` 不要混。

`policy-controller` 拒绝所有 Pod 时，先看 `ClusterImagePolicy` 的 `spec.images[].glob`。本章的字段是 `images` 加 `glob`，不是旧资料里的 `imageReferences`；glob 写错一个字符，策略就匹配不到目标镜像，而带 `policy.sigstore.dev/include=true` 的命名空间里，所有 Pod 都会走 webhook。接着看命名空间标签：没有这个标签，策略不会生效；标签加到了错误的命名空间，同样会出现“怎么都不拦”的假象。

`failurePolicy` 决定 webhook 不可用时 API Server 怎么办。示例里查到的值是 `Fail`，意味着 webhook 没就绪、超时、或者访问不了 registry 时，带标签的命名空间创建不了新 Pod。排障时先看 policy-controller 的 Deployment 是不是 `1/1`、Service 和 webhook 配置是否存在、webhook 日志里有没有 TLS 或 registry 连接错误。私有 registry 用自签证书时，CA 要同时给节点（kubelet/containerd 拉镜像）和 webhook（拉签名）；只给一边，会出现“镜像能拉、验签失败”或反过来。

修复的顺序是先 audit 再 enforce：把 `mode` 设成 `warn`，观察一段时间内哪些 Pod 会被拒绝、是签名缺失还是公钥不符、有没有合理的例外；确认策略和 glob 都对了，再改成 `enforce`。如果 registry 或 webhook 的可用性不够，先补副本、超时和 CA，再切 enforce；不要用 `failurePolicy: Ignore` 掩盖问题，那等于在 webhook 挂掉时自动放行所有镜像。

## 上生产前

用 digest 部署，不要用 tag；签名在 push 之后立即做，验签放在准入层，SBOM 和 provenance 随镜像一起保存。tag 只是指针，digest 才是签名和策略的对象；push 和 sign 之间如果隔了人工步骤，中间那段时间镜像就是未签名状态。

CI 的签名私钥放 KMS/HSM，或者用 keyless OIDC 换短期证书，不要放仓库变量、不要写进镜像。密钥要能轮换，轮换后旧 digest 的签名仍然要能验；构建权限和签名权限分开，能推 registry 的 token 不应该同时能签生产镜像。

扫描门禁按 severity 分级，HIGH/CRITICAL 阻断，允许的例外要有负责人、到期时间和记录。漏洞库固定版本或缓存，并在流水线里记录库的版本和更新时间；`--ignore-unfixed` 这类放宽要单独评审，不能默认打开。

策略先 `warn` 再 `enforce`，给团队留出观察和修镜像的时间。`failurePolicy` 要结合 registry 和 webhook 的可用性来定：`Fail` 安全但会在故障时阻断部署，`Ignore` 可用性高但会在故障时放行；无论选哪个，都要监控 webhook 的拒绝率和延迟。

私有 registry 的 CA 要同时装到节点和验签组件；跨 registry 复制镜像时把 `.sig`/`.att` 一起复制，或者在新 registry 重新签名。只复制镜像层、不复制签名，到了新环境 `cosign verify` 必然失败。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `docker buildx build --sbom=true` | 生成 SBOM attestation | 等价于 `--attest type=sbom`，默认只扫最终阶段 |
| `--provenance=mode=max` | 生成详细 provenance | `min` 是默认；`max` 会暴露 build-arg 的值 |
| `--provenance=...,builder-id=URL` | 写入构建器标识 | 不写时 BuildKit 留空 |
| `docker buildx imagetools inspect` | 看索引里的 attestation | `unknown/unknown` 是附属 manifest |
| `--format '{{json .SBOM.SPDX}}'` | 取 SPDX 文档 | provenance 用 `.Provenance.SLSA` |
| `cosign generate-key-pair` | 生成本地密钥对 | 私钥用 `COSIGN_PASSWORD` 加密 |
| `cosign sign --key cosign.key IMAGE@sha256:...` | 签 digest | 签名存 `<repo>:sha256-<digest>.sig` |
| `cosign verify --key cosign.pub ...` | 验镜像签名 | lab 加 `--insecure-ignore-tlog` |
| `cosign attest --type slsaprovenance` | 签 provenance | SBOM 用 `--type spdxjson` |
| `cosign verify-attestation --type ...` | 按类型验 attestation | 缺记录时报 `no matching attestations` |
| `cosign tree IMAGE@sha256:...` | 列签名和 attestation | 按 `.sig`/`.att` 标签发现 |
| `spec.images[].glob` | 策略匹配的镜像前缀 | 不是旧资料里的 `imageReferences` |
| `spec.mode: warn` / `enforce` | audit 或拒绝 | 默认 `enforce` |
| `failurePolicy` | webhook 失败时的行为 | 默认 `Fail`，故障时拒绝 |
| `trivy image --severity HIGH,CRITICAL --exit-code 1` | 漏洞门禁 | 有命中时退出 1 |
| `docker build --check` | 只检查构建配置 | 有问题时退出 1 |

本章结束时，`shorty:0.1` 在本地 registry 上带着 SBOM、provenance 和 `.sig`/`.att`；`cosign verify` 和 `cosign verify-attestation` 都通过；kind 集群里的 `ClusterImagePolicy` 处于 `enforce`，未签名镜像被拒绝，签名镜像能按 digest 部署。下一章从这个 registry 和镜像出发，讲 Compose 的完整开发栈。
