# 第 1 章 从进程到容器：namespace、cgroup、rootfs（手工用 `unshare` 做一个容器）

shorty 是全书贯穿使用的短链服务：一个 Go 写的 API 接收长链接、生成短码，一个 worker 从队列里取任务、抓取网页标题。[第 4 章](ch04.md)会第一次用 `docker run` 把它跑起来；到那时，你会看到 `docker ps` 里有一个叫 `shorty-api` 的容器，`docker logs` 里是它的 JSON 启动日志。现在先不看 Docker 的命令，只看一个问题：这个叫“容器”的东西，在 Linux 内核眼里到底是什么？

如果你在 `shorty-api` 容器里执行 `ps`，通常只会看到自己的进程；执行 `uname -a`，看到的却是宿主的内核版本；从宿主执行 `ps`，又能看到这个容器里的进程，只是 PID 不一样。同一个进程，为什么在两边的“视野”不同？`docker inspect` 里的 namespace、cgroup 和 rootfs 又分别对应内核的什么对象？

这一章不用 Docker 创建容器，只用 `unshare`、`mount` 和 `/sys/fs/cgroup` 手工搭一个最小容器。做完之后，你会得到一张自己的图：进程 → namespace → cgroup → rootfs。Docker、containerd、runc 后来做的，是把这张图上的每一步产品化、加上镜像和生命周期管理。

> **起点**：本章从一台只有 Docker 29 和基础工具的 Linux 开始，没有 kind 集群，也没有长期运行的容器。在仓库根目录执行 `bash code/ch01/setup.sh`，它会用 lab 自带的 BusyBox 打一个本地镜像 `lab/busybox:1.37`，并编译出 shorty 的二进制 `/tmp/ch01-shorty`；不会启动任何长期容器。

## 1.1 隔离的单位是进程，不是机器

先纠正一个常见的直觉：容器不是一台小虚拟机。虚拟机有自己的内核，容器没有。容器里的进程和宿主上的进程用的是同一个内核，只是这个内核给它们看了不同的“视图”，并且用 cgroup 给它们算了不同的资源账。Docker 的入门文档把容器定义成“一个隔离的进程，加上它运行所需的全部文件”；Kubernetes 文档则强调容器是共享节点内核的、可重复的运行单元。两句话说的是同一件事：隔离的单位是进程，不是机器。

Linux 用 namespace 做“视图”隔离。一个进程可以同时属于多个 namespace，每个 namespace 管一类资源。日常最常打交道的六类如下。

| namespace | 隔离什么 | 在容器里能观察到的现象 |
|---|---|---|
| PID | 进程 ID、PID 1、父子关系 | 容器里的进程从 PID 1 开始编号，`ps` 看不到宿主进程 |
| Mount | 挂载表、根目录 | 容器有自己的 `/`、`/proc`、`/sys`，看不到宿主的挂载 |
| UTS | 主机名、域名 | 容器可以有自己的 hostname，`uname -a` 里的主机名不同 |
| IPC | System V/POSIX 消息队列、信号量、共享内存 | 容器之间的共享内存和消息队列互不可见 |
| Network | 网卡、IP、路由、端口、iptables 规则 | 容器有独立的 `eth0`、IP 和端口空间 |
| User | UID/GID 映射、capability 的生效范围 | 容器里的 root 可以被映射成宿主的非 root；也可以和宿主共用 |

这六类不是“容器”这个对象自带的属性，而是进程的属性。你可以只给一个进程新建 PID namespace，也可以只新建 network namespace；Docker 只是按一套默认组合一次性建好。`/proc/<pid>/ns/` 下的符号链接就是这些 namespace 的句柄，同一类 namespace 的 inode 相同，不同类的 inode 不同。下面的示例就是用 inode 来对比。

cgroup（控制组）是另一套机制，负责“用多少”，不负责“看得见什么”。cgroup v2 把 CPU、内存、进程数等控制器放在一棵统一的树里，给一组进程记账并设上限。namespace 让进程看不到别的进程，cgroup 让进程不能无限吃内存和 CPU；两者经常一起出现，但解决的是不同问题。一个进程可以没有新的 namespace，却仍然被放进某个 cgroup；反过来，一个容器即使 namespace 都建好了，只要没设 cgroup 限额，它仍然可以吃满宿主内存。

最后是内核。容器和宿主共享内核，所以 `uname -a` 在容器里仍然是宿主的 kernel release；容器不能加载只属于自己内核的模块，也不能靠 namespace 防住内核漏洞。Docker 文档说容器“共享同一个内核”，Kubernetes 文档说容器是共享节点内核的隔离进程，都是这个意思。

这六类 namespace 里，最容易被忽略的是 user namespace。PID、mount、UTS、IPC、network 在 Docker 的默认配置里都会新建，user 却不一定：Docker 的 `userns-remap` 默认没有开，容器里的 uid 0 直接就是宿主上的 uid 0。1.1 的表里 `user` 一行三列相同，就是这件事的证据。没有 user namespace 时，容器里的 root 在宿主上也是 root；namespace 隔离的是“看什么”，不是“是谁”。这也解释了为什么只靠 namespace 不能做多租户安全边界：真正的权限边界还要靠 user namespace、capability、seccomp、AppArmor/SELinux 和 cgroup 设备控制一起构成。

namespace 也不是越多越好。每建一层 namespace，进程和宿主之间的对应关系就多一层：宿主上的 PID 和容器里的 PID 不再相同，`docker exec` 要经过运行时找到正确的 namespace，监控 agent 要能从宿主侧读到容器里的 `/proc`。这些复杂性是容器运行时替你付的代价；理解它的目的是排障时知道该看哪一层，而不是自己手工维护一套。

从这个角度看，`docker run` 的本质可以拆成三步：用 `clone(CLONE_NEW*)` 或 `unshare` 建一组 namespace；准备一个 rootfs，把进程的根切过去；把进程放进 cgroup，再执行镜像里的入口命令。Docker 自己不实现这三步，它把活交给 containerd，containerd 再调用 runc；runc 负责按 OCI 规范建 namespace、挂 rootfs、写 cgroup、`exec` 容器进程。1.5 会看到这条链在 `runc list`/`runc state` 里的痕迹。

这张表有三列 inode，读法要分清：

- `container` 是从容器里的 `/proc/1/ns/*` 读到的值；`host-same-pid` 是从宿主读 `/proc/<容器PID>/ns/*`，指向的是同一个进程，所以这一列和 `container` 完全一样。它证明“容器里的 PID 1”和“宿主上的某个 PID”是同一个进程，只是编号不同。
- `host-init` 是宿主 PID 1 的 namespace。`pid`、`mnt`、`uts`、`ipc`、`net` 五行都和它不同，说明容器确实拿到了新的 PID、mount、UTS、IPC、network namespace。
- `user` 一行三列相同，说明这个容器没有新的 user namespace。Docker 没有开 `userns-remap` 时，容器里的 root 就是宿主的 uid 0；1.7 会看到 `CapEff` 也一样，这不是“容器里的 root 被关起来了”，而是它本来就没有被映射走。

`NSpid` 把 PID 的两层编号写在一起。容器里读 `/proc/1/status` 只看到 `NSpid: 1`；宿主读同一个进程的 status，看到 `NSpid: <宿主PID> 1`。第一个数是宿主 PID namespace 里的编号，第二个数是容器 PID namespace 里的编号。PID namespace 可以嵌套，`NSpid` 就会有多段；这里只有两层。`ps` 只看到自己，是因为容器里的 `/proc` 是在新 PID namespace 里挂的，读到的进程表自然只有这个 namespace 的成员。

在宿主上还可以用 `lsns` 把同一件事列出来：`lsns -t pid` 会列出每个 PID namespace 的 inode、PID 1 和进程数。容器里的 PID namespace 会有自己的 inode 和 PID 1；`nsenter -t <pid> -p -m` 则可以进入某个进程的 PID 和 mount namespace，看到它那一侧的进程表。`lsns` 是从宿主侧看 namespace 的入口，`/proc/<pid>/ns/*` 是从进程侧看；两者指向同一批 inode。

`CapEff` 在两边都是 `00000000a80425fb`，这是 Docker 默认保留的 capability 集合，不是全 1。`uname -a` 的内核 release 两边相同，只有主机名不同：主机名属于 UTS namespace，内核版本不属于任何 namespace。把这三件事放在一起，就能回答本章开头的问题：容器里的进程不是“另一个内核上的进程”，而是“同一个内核里、被换了视图的进程”。

> **旧资料提示**：把容器说成“轻量虚拟机”是旧教程里最常见的错误。虚拟机有独立内核，容器共享宿主内核；容器能隔离进程的视图，但不能防内核漏洞。需要强隔离时要用虚拟机或 gVisor 这类沙箱，不能只靠 namespace。

## 1.2 用 unshare 手工做一个容器

`unshare` 的作用是把当前进程的一部分资源拆出去，放进新的 namespace，然后执行给定命令。它不需要 Docker，也不需要镜像；只要内核支持，root 就能用。下面的命令把 user、mount、PID、UTS、IPC、network 六类 namespace 一次建好，再在新 PID namespace 里重新挂 `/proc`：

```bash
unshare --user --map-root-user --pid --fork --mount --uts --ipc --net --mount-proc \
    /bin/busybox sh
```

这段命令不长，但每个参数都有原因。

- `--user` 新建 user namespace。它让后面的 mount、UTS、network 操作有一个“局部 root”可用：在这个 user namespace 里，进程拥有 `CAP_SYS_ADMIN`，可以挂载、改主机名、建网卡，但这些能力只在这个 namespace 内有效。
- `--map-root-user` 把当前 uid 映射成新 namespace 里的 0。它只写当前 uid/gid 到 0 的映射，不需要 `/etc/subuid`；`/etc/subuid` 是 Docker 的 `userns-remap` 用来分配一大段 subordinate UID 的，和这个参数不是一回事。1.8 会专门验证这一点。
- `--pid` 新建 PID namespace。单独用它只会影响之后创建的子进程，所以还要 `--fork`：让 `unshare` fork 一个子进程，这个子进程在新 PID namespace 里成为 PID 1。
- `--mount` 新建 mount namespace。建好之后，挂载和卸载只影响这个 namespace，不会污染宿主。
- `--mount-proc` 在新的 mount namespace 里重新挂一个 `/proc`。这一步必须做，而且必须在新的 PID namespace 生效之后做。否则 `/proc` 还是宿主那份，`ps` 仍然会列出宿主的进程，PID namespace 看起来就像没生效。
- `--uts` 让主机名可以独立修改；`--ipc` 隔离消息队列和共享内存；`--net` 新建 network namespace，里面只有一块默认关闭的 loopback。

建 user namespace 时，内核会为它准备 `uid_map` 和 `gid_map` 两个映射文件。`--map-root-user` 写的是“当前 uid → 0”这一条；如果要把一段 UID 范围映射进去，就要写多行，并且通常需要 `/etc/subuid` 里的 subordinate 范围。Docker 的 `userns-remap` 走的是后一条路：daemon 用 `dockremap` 这个用户和 `/etc/subuid` 里的一段范围，把容器里的 0–65535 映射到宿主上的高 UID。两者目的相似，机制和配置完全不同，排障时不要拿 `/etc/subuid` 去解释 `--map-root-user` 的失败。

mount namespace 还要注意传播属性。`unshare --mount` 默认会把新 namespace 的挂载传播设为 private，这样里面的挂载不会传回宿主；如果手工用 `mount --make-shared` 改回共享，容器里的挂载事件就可能影响宿主。runc 在准备 rootfs 时会显式设置传播属性，原因就在这里。

这里没有用 `chroot`。`chroot` 只改进程的根目录指针，不改变 mount namespace 的根挂载；进程已经打开的文件描述符、当前目录仍然可能指向旧根，所以它从来不是安全边界。现代 OCI 运行时在挂好 rootfs 之后用 `pivot_root` 切换根，再把旧根卸载掉。1.4 会手工做一遍这两步，并看它们的差别。

## 1.3 cgroup v2：限额写在哪

cgroup v2 把控制器挂在一棵统一的树上，通常挂在 `/sys/fs/cgroup`。每个目录是一个 cgroup，目录里的文件就是接口：读文件看状态，写文件设限制。和 namespace 不同，cgroup 不改变进程能看到什么，只改变它能用多少。

创建子 cgroup 之前，要先看父 cgroup 有没有把控制器启用给子树。`cgroup.controllers` 列出当前 cgroup 可用的控制器，`cgroup.subtree_control` 列出已经启用给子 cgroup 的控制器。顺序是自顶向下：父 cgroup 先把某个控制器写进 `cgroup.subtree_control`，子 cgroup 才会出现对应的控制文件。1.3 的示例里根 cgroup 已经启用了 `memory`、`cpu`、`pids`，所以新建的 `ch01demo` 直接就有这些文件。

Linux 发行版和 systemd 通常会在 `/sys/fs/cgroup` 下预先建好 `system.slice`、`user.slice` 这类层级；Docker 用 cgroupfs 驱动和 systemd 驱动时，容器在这棵树里的位置不一样（systemd 驱动下通常是 `system.slice/docker-<容器ID>.scope`），文件名和语义一样。容器里的 `/sys/fs/cgroup` 默认是 cgroup namespace 的根，看起来像一棵独立的树；从宿主看，它仍然挂在整棵树的某个位置。排障时以宿主上的实际路径为准，不要只看容器里的 `/sys/fs/cgroup`。

cgroup v2 还有一条“no internal processes”规则：一个 cgroup 如果要把控制器启用给子 cgroup，它自己就不应该再放进程；进程要放在叶子 cgroup 里。示例先打印根 cgroup 的 `cgroup.procs` 行数，结果是 0；然后把 shorty 的 PID 写进 `ch01demo/cgroup.procs`。`ch01demo` 没有子 cgroup，是叶子，所以这样放是合法的。把进程放在中间层会失败，这是 cgroup v2 和 v1 的一个明显差异。

三个最常用的限额文件：

- `memory.max`：硬上限，单位是字节，也可以写 `64M` 这样的后缀。进程组用量达到上限时，内核会在 cgroup 内触发 OOM，杀掉进程。`memory.current` 是当前用量，`memory.peak` 是峰值，`memory.events` 里能看到 `max`、`oom`、`oom_kill` 等计数。
- `cpu.max`：两个字段，`quota period`，单位都是微秒。`50000 100000` 表示每个 100 ms 周期最多用 50 ms CPU，也就是 0.5 个 CPU。默认的 period 是 100000 微秒；Docker 的 `--cpus=1.5` 等价于 `--cpu-quota=150000 --cpu-period=100000`，写进 cgroup v2 就是 `150000 100000`。
- `pids.max`：这个 cgroup 里最多能有多少个进程/线程。它防的是 fork bomb：内存还够、CPU 还够，但进程表被瞬间打满。Docker 用 `--pids-limit` 对应它。

fork bomb 的经典写法是一个函数不断 fork 自己。没有 `pids.max` 时，内核会在 PID 耗尽或内存耗尽时才失败，期间整台机器可能已经无法登录；有了 `pids.max`，fork 到上限就返回 `EAGAIN`，爆炸被限制在一个 cgroup 里。这个上限要按应用的线程模型设：Go 程序的线程数会随 GOMAXPROCS 和阻塞 syscall 增长，Java 程序还要算上 GC 线程，不能照抄“32”这种拍脑袋的值。本章的 32 只是为了让文件里有一个非默认值，shorty 在这个实验里用不到这么多线程。

## 1.4 rootfs、overlay 与 pivot_root

namespace 解决了“看什么”，cgroup 解决了“用多少”，容器还缺一个“从哪里读文件”。容器进程看到的 `/` 就是它的 rootfs。对 Docker 来说，这个 rootfs 通常是一个 overlay 挂载：镜像的层是只读的 lowerdir，容器自己的可写层是 upperdir，OverlayFS 把两者合起来，在 merged 目录露出一个统一的视图。

四个目录各司其职：

- `lowerdir`：镜像层，只读。可以有多层，用冒号分隔。Docker 的 overlay2 驱动最多支持 128 个 lower 层。
- `upperdir`：容器的可写层。容器第一次写某个文件时，OverlayFS 把整个文件从 lower 复制到 upper，这叫 copy-up；之后对该文件的写都落在 upper。
- `workdir`：OverlayFS 内部使用的空目录，必须和 upperdir 在同一个文件系统上。
- `merged`：lower 和 upper 合并后的视图，也就是容器里看到的根目录。

copy-up 是“第一次写”时发生的，而且按文件复制，不是按块。一个 1 GiB 的文件只改一个字节，也要先复制整个文件；这是 overlay 写性能不如卷的原因之一。删除文件时，OverlayFS 在 upper 里放一个 whiteout 文件，而不是删 lower；删除目录则用 opaque 目录。容器删除后 upper 层丢掉，镜像层不受影响。

这也是为什么数据库这类写密集的服务要把数据目录放在卷上：卷直接挂进容器，绕过 overlay 的 copy-up，写放大和层数都不会影响它。反过来，容器里临时写的文件留在 upper，容器删除就消失；把“需要持久化”误当成“镜像里会有”是另一个常见错误，[第 5 章](ch05.md)会专门处理卷。

切根这一步，现代运行时用的是 `pivot_root`，不是 `chroot`。两者的差别不在“换不换根”，而在“旧根还在不在”：

- `chroot` 只改进程的 `fs_struct` 根目录指针。进程已经打开的文件描述符、当前工作目录仍然可以指向旧根；有足够权限的进程还能用 `fchdir` 加 `chroot` 逃出去。它从来不是安全边界。
- `pivot_root(new_root, put_old)` 要求 new_root 是一个挂载点；它把当前 mount namespace 的根挂载换成 new_root，并把旧根挂到 put_old 下。旧根成了一个普通的挂载点，运行时可以 `umount` 掉，之后从新根再也走不回去。

## 1.5 Docker/containerd/runc 只是把这些步骤产品化

把 1.1 到 1.4 串起来，`docker run` 的链路可以写成：

```text
docker CLI → dockerd → containerd → containerd-shim → runc → 容器进程
```

dockerd 负责接收 API 请求、管理镜像/网络/卷；containerd 负责容器生命周期；runc 是真正调用 `clone`/`unshare`、挂 rootfs、写 cgroup、`pivot_root`、`exec` 的那个 OCI 运行时。containerd 和 runc 之间还有一个 shim：容器进程的父进程是 `containerd-shim-runc-v2`，不是 dockerd。shim 负责转发 stdio、回收退出状态，让 dockerd/containerd 重启时容器还能活着。Docker 文档说 containerd 默认用 runc 作为运行时；Kubernetes 的 CRI 文档说 kubelet 通过 gRPC 调容器运行时，CRI 从 1.23 起 stable，1.26 起要求运行时支持 v1 API。两条链路不同，但底下都是 OCI 运行时这套东西。

OCI runtime bundle 是运行时的输入：一个目录里放 `config.json` 和 `rootfs/`。`config.json` 描述进程参数、根文件系统、namespace 列表、挂载、cgroup 资源等；`rootfs/` 是解开的根文件系统。`runc create` 按 config 建好容器但不启动进程，`runc start` 再执行；`runc state` 读运行状态。Docker 的 bundle 由 containerd 生成，放在 `/run/docker/containerd/daemon/io.containerd.runtime.v2.task/moby/<容器ID>` 下。

`config.json` 里的 `ociVersion` 是 OCI Runtime Spec 的版本，不是 Kubernetes 或 Docker 的版本；这个 lab 的 runc 1.5.2 写的是 1.3.0。不同运行时实现同一个 spec，所以 `runc`、`crun`、`youki` 都能被 containerd 调用；Docker 文档说 containerd 默认用 runc，也支持通过 shim 换 gVisor、Kata 这类运行时。换运行时换的是“怎么建这个进程”，namespace、cgroup、rootfs 这套内核接口不变。

Kubernetes 节点上的链路是 kubelet → CRI → containerd（或 CRI-O）→ runc，比 Docker 少了一个 dockerd。CRI 是 kubelet 和运行时之间的 gRPC 接口，1.23 起 stable；1.26 起 kubelet 要求运行时支持 v1 API，不支持 v1 的运行时无法注册节点。所以“容器运行时”在 Docker 和 Kubernetes 两个语境里指的是同一层东西，只是调用方不同。

## 1.6 什么时候不该用容器

容器适合“无状态、可重启、按进程模型设计”的服务：进程收到 SIGTERM 能优雅退出，状态放在数据库、对象存储或卷里，启动不依赖宿主上某个特定的内核模块或设备。Kubernetes 文档明确说容器应当无状态、不可变；要改代码就构建新镜像、重建容器，而不是进容器里改。shorty 的 API 就按这个模型写：启动时连数据库和 Redis，收到 SIGTERM 先停止接新请求，再关闭 HTTP。

下面这些场景，容器不是不能跑，而是不适合作为默认方案：

- **需要加载内核模块**：容器和宿主共享内核，`modprobe` 加载的模块会影响宿主，而且需要 `CAP_SYS_MODULE`。把驱动或内核模块放进容器，等于把宿主内核的一部分交给容器；这种程序应该跑在虚拟机上。
- **直接访问硬件**：GPU、串口、USB、特定网卡需要把设备节点传进容器（`--device`），或者干脆用 `--privileged`。设备直通能做，但隔离边界会变薄，调度和迁移也更麻烦。
- **GUI/X11**：需要 X11 socket、GPU、可能还有宿主 IPC；把桌面程序塞进容器通常要挂一堆 socket 和设备，收益很低。
- **完整 systemd**：systemd 假定自己是 PID 1、能管 cgroup、能挂载、能改内核参数；容器是“一个进程”的模型，在容器里跑 systemd 需要额外的特权和对 cgroup 的委派，不是默认用法。
- **必须使用宿主网络命名空间的程序**：网络插件、VPN、某些监控 agent 需要看宿主网卡和路由；`--network=host` 能跑，但它已经放弃了 network namespace 隔离。

这些边界不是“容器做不到”，而是“硬做要付出不合适的代价”。比如 GPU 训练可以容器化，因为厂商提供了 device plugin 和专门的运行时；但一个需要加载自研内核模块的存储驱动，放进容器只会把宿主内核变成它的一部分，节点一升级就一起坏。又比如 systemd：在容器里跑 systemd 需要把 cgroup 委派给它、允许它挂载、把它当 PID 1，这已经接近“在容器里跑一台小系统”，不如直接用虚拟机。判断标准可以简化成一句：这个程序是否把宿主内核、宿主设备或宿主网络当成自己的一部分？如果是，容器不是首选。

反过来，shorty 这类服务适合容器：进程模型清晰，状态在外部，启动和退出都可重复。第 4 章会看到它的 API 进程如何接收 SIGTERM、如何把 readiness 置为失败；第 8 章会把它的 capability 和 seccomp 收紧；第 32 章会在集群层面检查哪些工作负载拿到了不该有的特权。这三章反复问的是同一个问题：哪些东西应该留在容器外。

`--privileged` 是这些边界的“总开关”。Kubernetes 文档说，特权容器会拿到所有 Linux capability，覆盖 seccomp、AppArmor、SELinux 的限制；Docker 的 `--privileged` 同样会给所有设备、关闭默认 seccomp/AppArmor 约束。它适合“必须操作宿主网络栈或访问硬件”的受信任容器，不适合当默认值。需要某一项能力时，优先用 `--cap-add`、`--device` 精确授予，而不是直接 `--privileged`。

## 1.7 排障：unshare 报 Operation not permitted

`unshare` 失败时最常见的一句话是：

```text
unshare: unshare(0x10000000): Operation not permitted
```

`0x10000000` 是 `CLONE_NEWUSER`，也就是 `--user` 对应的标志。这个错误只说明“内核拒绝创建 user namespace”，不说明“内核不支持容器”。按下面的顺序查，通常几分钟就能定位。

第一步，看宿主允不允许非特权用户创建 user namespace。`/proc/sys/kernel/unprivileged_userns_clone` 为 1 表示允许，为 0 表示禁止；很多发行版还加了 AppArmor 限制，`kernel.apparmor_restrict_unprivileged_userns=1` 时非特权用户会被拦，root 仍然可以。以 root 执行 `unshare --user --map-root-user id -u` 能返回 0，就说明内核和 root 这条路径没问题。

第二步，看是不是 seccomp 或 AppArmor 在拦。容器里的 `/proc/self/status` 如果有 `Seccomp: 2`，说明 seccomp 过滤器已启用；Docker 默认 profile 会拦掉一批 syscall，其中包括 `unshare` 的非 user 用法，也可能被自定义 profile 全部拦掉。AppArmor 的 `docker-default` profile 也会限制 mount 这类操作。`unshare` 返回 EPERM 时，先确认是哪个 LSM/过滤器，不要直接怪内核。

第三步，不要把 `--map-root-user` 和 `/etc/subuid` 混在一起。`--map-root-user` 只把当前 uid 映射成新 namespace 里的 0，只需要当前 uid/gid 的映射；`/etc/subuid` 是 Docker 的 `userns-remap` 用来分配 subordinate UID 范围的。示例里的 `/etc/subuid` 只有 `dockremap` 一条，没有 root，但宿主上的 `unshare --user --map-root-user` 仍然成功。

实际操作时，可以把三条命令并排跑：在宿主上 `unshare --user --map-root-user id -u`；在容器里读 `/proc/self/status` 的 `Seccomp`；在容器里用同一个镜像跑 `unshare --user true`。如果宿主成功、容器里 `Seccomp: 2`，问题就在容器的安全配置，不在内核。再检查 `/proc/sys/kernel/unprivileged_userns_clone` 和 `kernel.apparmor_restrict_unprivileged_userns`，就能区分“sysctl 禁止”和“LSM/seccomp 拦截”。`dmesg` 里如果有 `apparmor="DENIED"` 的记录，也能帮助定位，但容器里的 dmesg 常常被限制，优先看 `/proc/self/status` 和运行时配置。

## 上生产前

- 不要在容器里跑需要内核模块或宿主设备的程序。必须用时走 `--device` 或 `--privileged` 的审批，明确写清楚为什么需要、影响哪些节点；不要把它们写进默认的部署模板。Kubernetes 文档对特权容器的建议也是能用 `securityContext.capabilities` 精确授予就不要用 `privileged`。
- 给每个容器设 `pids.max` 和 `memory.max`。`pids.max` 防 fork bomb，`memory.max` 防单容器吃光节点内存；不要依赖“节点内存还够”这种运行时判断。Docker 对应 `--pids-limit` 和 `--memory`，Kubernetes 对应 Pod 的 `resources.limits` 和 kubelet 的 `--pod-max-pids`（后者是节点级默认值，按需确认）。
- 用 `docker inspect .State.Pid` 加 `/proc/<pid>/cgroup`，或用 `crictl inspect`，记录实际生效的 cgroup 路径。排障时以文件内容为准：`memory.max`、`memory.events`、`cpu.max`、`pids.max` 读到什么就是什么，不要靠 `docker inspect` 的配置字段猜运行时最终写了什么。
- 不要用 `chroot` 做安全边界。需要切根时用 `pivot_root`，这件事由 runc 完成；自己写运行时或调试脚本时，pivot_root 之后要记得卸载旧根。
- 没有开 user namespace 的 Docker，容器里的 root 就是宿主 uid 0。需要把容器 root 映射走时用 `userns-remap`（或 Kubernetes 的 `hostUsers: false`），但这会带来卷、设备、特权容器的兼容问题；先把不需要 root 的容器改成非 root，再考虑 userns。

## 速查

| 命令或字段 | 作用 | 默认值或备注 |
|---|---|---|
| `unshare --user` | 新建 user namespace | 非 root 需要 `unprivileged_userns_clone=1` 且未被 LSM 拦截 |
| `unshare --map-root-user` | 当前 uid/gid 映射为 0 | 只写当前 uid/gid，不需要 `/etc/subuid` |
| `unshare --pid --fork` | 新建 PID namespace 并让子进程当 PID 1 | 单独 `--pid` 只影响之后 fork 的子进程 |
| `unshare --mount --mount-proc` | 新建 mount namespace 并重挂 `/proc` | 不重挂 `/proc`，`ps` 仍看宿主进程 |
| `unshare --uts --ipc --net` | 隔离主机名、IPC、网络 | `--net` 新 namespace 里只有 down 的 loopback |
| `/proc/<pid>/ns/*` | 查进程的 namespace inode | 同 inode 表示同一个 namespace |
| `lsns`、`nsenter -t <pid> -n` | 列出/进入 namespace | 调试时用，需要相应权限 |
| `cgroup.controllers` | 当前 cgroup 可用控制器 | 只读 |
| `cgroup.subtree_control` | 启用给子 cgroup 的控制器 | 写 `+memory +pids` 这类值 |
| `memory.max` / `memory.current` / `memory.peak` | 内存硬上限/当前/峰值 | 字节，可写 `64M` |
| `memory.events` | OOM、撞上限等计数 | `oom_kill 1` 表示杀了一个进程 |
| `cpu.max` | `quota period`，微秒 | `50000 100000` 是 0.5 CPU |
| `pids.max` | 进程/线程数上限 | Docker `--pids-limit` 对应它 |
| `mount -t overlay overlay -o lowerdir=...,upperdir=...,workdir=... merged` | 手工挂 overlay | 第一次写触发 copy-up |
| `pivot_root . oldroot` | 切换 mount namespace 的根 | 旧根挂到 oldroot，可卸载 |
| `runc --root /run/docker/runtime-runc/moby list` | 列出 Docker 的 runc 容器 | 默认 root 下通常是空的 |
| `runc state <id>` | 看 pid/status/bundle/rootfs | bundle 里有 `config.json` 和 `rootfs` |
| `docker inspect -f '{{.State.Pid}}'` | 容器进程的宿主 PID | 对应 `/proc/<pid>/cgroup` |
| `docker inspect -f '{{.HostConfig.PidMode}}'` | 是否共享宿主 PID namespace | `host` 表示共享；没有 `NamespaceMode` 字段 |
| `docker inspect -f '{{.HostConfig.NetworkMode}}'` | 网络模式 | `host` 表示共享宿主网络 |

本章结束时，lab 里没有长期容器；`ch01demo` cgroup 已删除，`/tmp/ch01-ovl` 和 `/tmp/ch01-pivot` 已清理，shorty 只在第 4 章才以容器形式跑起来。[第 2 章](ch02.md)从镜像层开始：这些 lowerdir 里的层到底是怎么存、怎么寻址的。
