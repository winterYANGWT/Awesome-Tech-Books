# 第 16 章 从 Compose 到 Kubernetes：声明式 API、控制循环，用 kind 起集群

第 14 章结束时，`shorty` 的五个服务已经能用一条 `docker compose up -d` 起来：PostgreSQL、Redis、一次性的 migrate、api 和 worker。`docker compose ps` 里该 Running 的 Running，该 Exited 0 的 Exited 0，`curl localhost:8080/healthz` 也能返回 `ok`。这套东西在一台机器上很好用，但它回答不了一个问题：如果 api 的进程在凌晨两点挂掉，谁把它拉起来？

Compose 的 `up` 做的是“把这份配置变成一组容器”，它是一次性的收敛。容器建好之后，Docker 守护进程按容器的 `restart` 策略决定要不要重启进程；短小的 `api` 服务没有写 `restart`，默认就是 `no`。即使写了 `restart: always`，那也只是同一台机器上的 Docker 在重启同一个容器，换一台机器、节点磁盘坏了、整个容器被删了，都不在它的职责里。Compose 管的是“这台机器上的这组容器”，Kubernetes 管的是“集群里应该有多少个这样的 Pod，以及它们现在是否真的在跑”。

`kubectl apply` 之后，保证副本数的不是这条命令，而是集群里的控制器。你把“要 2 个 api Pod”写进 Deployment 的 `spec`，API server 把它存进 etcd；Deployment 控制器创建 ReplicaSet，ReplicaSet 控制器再创建 Pod；kubelet 在节点上启动容器。之后任何一个 Pod 消失，ReplicaSet 控制器都会发现“现在只有 1 个，期望是 2 个”，再创建一个。这个循环不会在 `kubectl apply` 返回时结束。

这一章先用一个 2 副本的 Deployment 看控制器把删掉的 Pod 补回来，再拆开对象看 `spec`、`status` 和 `kubectl apply` 的记录方式；然后用 kind 从零建一个单节点集群，把第 14 章的 Compose 模型交给 Compose Bridge 转一遍，最后手写 `Deployment api` 和 `Service api`，把 shorty 的最小版本跑起来。过程中会反复对照 Compose 的 `depends_on`、`healthcheck`、命名卷和 `scale`，看清哪些能直接映射，哪些必须换一种做法。

> **起点**：第 14 章结束。`shorty` 的 Compose 栈可用，镜像 `shorty:0.1`、`shorty-worker:0.1` 已经构建过，lab 里还没有 Kubernetes 集群。在仓库根目录执行 `bash code/ch16/setup.sh`，它会建一个名为 `shorty` 的单节点 kind 集群，把两个 shorty 镜像加载进节点，并预拉本章要用的 Compose Bridge 转换器；16.3 会把这个集群删掉重建，完整走一遍 `kind create`。

## 16.1 从“一次性命令”到“期望状态”

先把 Compose 的行为说清楚，避免把 `docker compose up` 当成一个常驻的编排器。`up` 会创建网络、卷和容器，等依赖满足后启动服务，然后（不加 `-d` 时）把日志接到终端。它不会在后台持续比较“应该有几个 api”和“现在有几个 api”；容器退出后，是否重启由 `restart` 策略决定，默认值是 `no`。`docker compose start` 只启动之前创建过、后来停掉的容器，不会补建新容器。这个模型适合单机开发，也适合一台机器上的小规模部署，但它的“保证”停留在容器创建和 Docker 的重启策略这一层。

Kubernetes 把“保证”换成了另一种写法。一个对象通常有 `spec` 和 `status` 两个字段：`spec` 是你写的期望状态，`status` 是 Kubernetes 写回的当前状态。控制器（controller）持续观察某类对象，发现当前状态和期望状态有差距，就通过 API server 做出改动。它不是只执行一次，而是一个不会自己停下来的循环；官方文档把它类比成房间里的恒温器：你设定温度，恒温器不断比较实际温度，决定开或关设备。

Kubernetes 里有很多个小控制器，而不是一个包办一切的大循环。Deployment 控制器管 Deployment 和 ReplicaSet，ReplicaSet 控制器管 Pod 的数量，Job 控制器管一次性的任务，EndpointSlice 控制器管 Service 的端点。它们各自只看自己关心的对象，通过标签区分哪些 Pod 属于自己。这样做的好处是单个控制器可以失败、可以替换，不会把整个系统绑死在一个进程上。

自愈也不是一句“挂了就重启”，它至少分四层，责任方不同：

| 层次 | 谁来做 | 触发条件 | 结果 |
|---|---|---|---|
| 容器重启 | 节点上的 kubelet | 容器进程退出，且 Pod 的 `restartPolicy` 允许重启 | 在同一个 Pod 里重启容器，Pod 名字不变 |
| 副本替换 | Deployment/ReplicaSet 控制器 | Pod 被删除、被驱逐或所在节点失联 | 创建一个新的 Pod，名字和 UID 都会变 |
| 存储重挂 | PV/PVC 与节点上的存储插件 | 节点故障，Pod 被调度到另一台节点 | 把持久卷重新挂到新 Pod；是否成功取决于存储后端 |
| Service 摘除 | EndpointSlice 控制器与 kubelet 的就绪状态 | Pod 不再 Ready 或被删除 | 把该 Pod 从 Service 的端点里去掉，流量不再打过去 |

这四层不能互相替代。容器反复崩溃时，kubelet 只能重启它；如果整个 Pod 被删掉，就要靠副本控制器补；如果 Pod 用了持久卷，新 Pod 能不能挂上同一块卷，取决于存储系统；如果 Pod 还 Ready，Service 就不会把它摘掉，哪怕应用已经在返回错误。排障时先判断坏在哪一层，比盯着一个 `kubectl get pods` 有用。

## 16.2 对象、spec/status 与 apply

Kubernetes 的对象不是一个随手写的配置文件，而是 API server 里一条有结构的记录。几乎每个对象都有四个顶层字段：`apiVersion` 说明用哪个 API 版本，`kind` 说明对象类型，`metadata` 放名字、命名空间、标签和注解，`spec` 放你期望的状态。很多对象还有 `status`，但它不是你写的，而是控制器根据实际情况回写的。`kubectl get -o yaml` 把这两部分放在同一份 YAML 里，读的时候要分清哪一段是自己的意图，哪一段是集群的观察结果。

下面的 `jq` 只是把 JSON 里关心的字段挑出来，不是 Kubernetes 的一部分。第一段 `jq` 把 Deployment 的 `spec.replicas` 和 `status` 里的副本数放在一起，四个值都是 2：这是已经收敛的状态，不是“apply 之后立刻就是这样”。第二段用 `--show-managed-fields` 才看到 `managedFields`，因为 `kubectl get` 默认不显示它。两条记录分别是 `kubectl-client-side-apply` 和 `kube-controller-manager`：前者是你这次 `kubectl apply` 的客户端身份，后者是 Deployment 控制器写 `status` 的身份。字段的归属由 API server 记录，不是靠注释猜的。

第三段把 `kubectl.kubernetes.io/last-applied-configuration` 注解解析出来，只打印 `kind`、名字和副本数。这个注解是客户端 apply 留下的“上次应用的完整清单”，`kubectl apply` 下次会用它与新文件、与实时对象做三方合并。它属于客户端 apply 的机制；服务端 apply（server-side apply，SSA）的字段所有权记录在 `managedFields` 里，不靠这个注解做合并。两种方式不要混在同一个对象上，官方文档明确说同一对象只应使用一种管理技术。

`kubectl apply --dry-run=server` 的输出是 `unchanged (server dry run)`：请求确实到了 API server，走了准入和字段校验，但没有写进 etcd。它比 `--dry-run=client` 更接近真正 apply 的结果，因为服务端会检查字段、默认值和准入策略。接着的 `kubectl diff` 在没有差异时退出码是 0；把副本数改成 3 后，diff 打印出 `-  replicas: 2` 和 `+  replicas: 3`，退出码是 1。`kubectl diff` 的 1 表示“有差异”，不是命令失败；在 CI 里要把这个退出码和真正的错误（大于 1）分开处理。

这段 diff 里还会看到 `generation: 1` 变成 `2`，以及 `last-applied-configuration` 的内容。它们是服务端或客户端 apply 自己维护的字段，不是你要改的业务配置。读 `kubectl diff` 时先找 `spec` 下真正变化的行；如果只看到 `generation`、时间戳、UID 这类值，通常说明没有实质变更。`kubectl diff` 本身会在服务端做一次 apply 的 dry-run，所以它需要 `PATCH`、`CREATE`、`UPDATE` 权限，这一点和只看文件的 `diff` 不同。

最后一段故意写了一个不存在的 `spec.replicasCount`。服务端返回的 `strict decoding error: unknown field "spec.replicasCount"` 说明字段没有通过严格解码，不会被静默丢掉。Kubernetes 1.25 起 API server 提供这种服务端字段校验，1.27 起所有受支持的版本都具备；`kubectl` 的 `--validate=true` 等价于 `strict`，默认就是严格模式。字段名写错时，先看这条错误，不要靠 `kubectl apply` 成功与否猜。

`kubectl get -o yaml` 里 `spec` 是你写的，`status` 是控制器写的；但 `metadata` 里混着两边的东西，`resourceVersion`、`uid`、`generation`、`managedFields` 都由服务端维护。手工 `kubectl edit` 改 `status` 通常会被控制器覆盖，改 `spec` 又会绕过 Git 里的清单。这一章先把清单当成唯一来源，下一章再讨论服务端 apply 和字段所有权。

## 16.3 用 kind 起集群

kind 的名字来自 “Kubernetes in Docker”：它把每个 Kubernetes 节点做成一个 Docker 容器，在容器里跑 kubelet、containerd 和 kube-proxy。宿主机上的 Docker 只负责启动这些“节点容器”，Pod 里的容器由节点里的 containerd 创建。这样做的好处是几十秒能建一个集群，删掉也不留下系统服务；代价是它跟生产节点的网络、存储和升级方式都不一样，官方文档明确说 kind 主要用于测试 Kubernetes 本身，也可以用于本地开发和 CI。

`kind delete cluster` 先删节点容器，再删 kubeconfig 里的 context。`kind create cluster` 的每一步都对应一件事：`Ensuring node image` 检查本地有没有 `kindest/node` 镜像，`Preparing nodes` 启动节点容器并准备文件系统，`Writing configuration` 写 kubeadm 配置，`Starting control-plane` 启动 API server、etcd、控制器和调度器，`Installing CNI` 装默认网络插件，`Installing StorageClass` 装默认存储类。最后一行 `Ready after ...` 是控制平面就绪的时间，不是节点上所有系统 Pod 都就绪的时间。

`--image "$KIND_NODE_IMAGE"` 用的是 lab 里固定的 `kindest/node:v1.37.0@sha256:...`，不是 `latest`。`docker inspect` 显示节点容器的镜像也是这个 digest。节点容器里的 `systemctl is-active containerd kubelet` 两行都是 `active`；`crictl info` 显示默认运行时是 `runc`，运行时类型是 `io.containerd.runc.v2`；检查 `/var/run/docker.sock` 的结果是“节点里没有 Docker daemon socket”。这三件事一起说明：节点里跑的是 containerd + kubelet，不是 Docker。

`kubectl get nodes -o wide` 的 `CONTAINER-RUNTIME` 一列写的是 `containerd://2.3.4`，`STATUS` 是 `Ready`，`ROLES` 是 `control-plane`。`KERNEL-VERSION` 显示的是 lab 宿主的内核版本，因为 kind 节点容器和宿主共享内核；不要把这个版本当成节点自己装了一个内核。`INTERNAL-IP` 是节点容器在 Docker 网络里的地址，Pod 网段又是另一层，后面看 EndpointSlice 时会再遇到。

`kind export kubeconfig` 把集群的证书和 API server 地址写进 `~/.kube/config`，并把当前 context 切到 `kind-shorty`；`kubectl config current-context` 因此输出 `kind-shorty`。`kubectl cluster-info` 里的 `https://127.0.0.1:<端口>` 是 kind 映射到宿主（在 lab 里是 lab 容器）的 API server 地址，端口每次创建都可能不同，不要写死。多个 kind 集群并存时，命令要带 `--context kind-<名字>`，否则 `kubectl` 可能连到另一个集群。

`docker stats` 显示节点容器占用八百多 MiB。这个数字包含节点里的系统 Pod、镜像的 page cache 和容器本身的开销，会随创建后的时间、拉取的镜像和内核缓存变化；单节点空载大致在 0.8–1 GB 这个量级。它和 kubeadm 生产安装的门槛不是一回事：kubeadm 文档要求每台机器至少 2 GB 内存，控制平面至少 2 个 CPU，因为生产节点还要跑更多系统组件和业务 Pod。

> **旧资料提示**：旧教程里用 Play with Kubernetes 在浏览器里起集群。这个托管 playground 已经停服，本地实验改用 kind、minikube 或 k3d；本书选 kind，是因为它和 Docker 的集成最直接，删掉也不留系统服务。

> **旧资料提示**：旧教程常说 minikube 必须要 VirtualBox 或 Hyper-V。现代 minikube 支持多种 driver，包括 Docker 和 Podman，具体支持矩阵以 minikube 官方文档为准；如果只是本地验证清单，kind 和 minikube 都能用，不必先装虚拟机。

## 16.4 Compose Bridge：把模型转成清单

Compose 的模型由 service、network、volume、config、secret 这些概念组成；Kubernetes 的模型由 Deployment、Service、PersistentVolumeClaim、ConfigMap、Secret 这些对象组成。两者不是一对一：一个 Compose service 通常会变成一个 Deployment 加一个 Service，命名卷变成 PVC，secret 变成 Secret，网络拓扑可能变成 NetworkPolicy。Compose Bridge 做的就是把这套模型按一组模板转成 Kubernetes 清单，默认还会生成一个 Kustomize overlay。

Compose Bridge 的转换器本身是一个 OCI 镜像：它接收解析后的 Compose 模型，按 Go 模板生成文件。lab 的 Compose v5.6.1 自带 `docker compose bridge` 子命令；不同发行版和版本可能把 `compose-bridge` 作为单独的二进制或 Docker Desktop 的组件提供。如果你的环境没有这个子命令，不必卡住：这一节的概念仍然成立，直接跳到 16.5 手写清单即可。示例把转换器镜像锁到了 digest，避免每次运行拿到不同的 `latest`。

`kubectl apply --dry-run=server` 对 api Deployment 和 `api-published` Service 返回 `created (server dry run)`，对 Namespace 返回 `configured (server dry run)`，说明这几个对象的字段都能通过服务端校验。Namespace 在前面已经创建过，所以是 `configured`；这只是 dry-run，不会真的改对象。紧接着的 migrate Deployment 却被拒绝：`spec.template.spec.restartPolicy: Unsupported value: "Never"`。Deployment 的 Pod 模板只允许 `restartPolicy: Always`，而 Compose 里 migrate 是一次性任务，`restart: "no"` 被转成了 `Never`。这不是字段名的小错，而是模型错位：一次性任务在 Kubernetes 里应该用 Job，不是 Deployment。

这段失败正好说明“转换结果需要手工修”。Compose Bridge 能识别镜像、端口、环境变量、命名卷和 secret 这些结构，但它不知道 migrate 只应该跑一次，也不知道 `depends_on` 的启动顺序在 Kubernetes 里没有直接等价物。实际迁移时，至少要检查四类地方：一次性服务改成 Job 或 initContainer，`healthcheck` 改成合适的 probe，`depends_on` 改成显式的初始化或应用重试，secret 改成合适的 Secret 挂载和权限。它适合做一次迁移的起点，不适合当成长期的交付方式。

输出后半段把生成物和手写清单压成同样的字段来对比。拿来对比的生成物 `api-expose.yaml` 和手写 Service 都叫 `api`，但生成物的 selector 是 `com.docker.compose.project` 和 `com.docker.compose.service` 两个标签，targetPort 是 `api-8080`；手写版的 selector 是 `app.kubernetes.io/name: api`，targetPort 是命名端口 `http`。生成物的 Deployment 用 `Recreate` 策略，环境变量有七个，secret 挂在 `/run/secrets/db_password`；手写的最小版不写 `strategy`，默认是 `RollingUpdate`，没有环境变量和挂载。两边都能跑，但标签、命名和更新策略是两套约定，不能混着改同一个对象。

生成物里的 `healthcheck` 也不能直接当成 Kubernetes 的 probe：Compose 的 healthcheck 主要影响依赖服务和 `docker ps` 的健康状态，Kubernetes 的 livenessProbe 失败会重启容器，readinessProbe 失败会把 Pod 从 Service 端点摘掉。第 19 章会分别设计 startup、readiness、liveness 三种探针。生成的 Secret 文件把内容放在 `data` 字段里；Kubernetes Secret 默认只是 base64 编码后存进 etcd，不是加密，访问控制要靠 RBAC 和静态加密，这些第 27 章再展开。

## 16.5 第一个 Deployment 与 Service

现在不用生成物，手写 shorty 的最小清单。Deployment 的三个核心字段是 `replicas`、`selector` 和 `template`：`replicas` 是期望的 Pod 数，`selector` 决定这个 Deployment 管哪些 Pod，`template` 是创建 Pod 时用的模板。`selector.matchLabels` 必须匹配 `template.metadata.labels`，否则 API server 会拒绝；`replicas` 不写时默认是 1。Deployment 不直接创建 Pod，它创建 ReplicaSet，ReplicaSet 再创建 Pod；滚动更新时新旧 ReplicaSet 的 Pod 模板哈希不同，所以 Pod 名字也会换。

Service 的核心字段是 `selector`、`ports` 和 `type`。`selector` 选中一组 Pod，`ports[].port` 是 Service 自己暴露的端口，`targetPort` 是 Pod 上的端口；`targetPort` 可以写数字，也可以写容器端口的名字，不写时默认等于 `port`。`type` 不写时默认是 `ClusterIP`，只给集群内部一个虚拟 IP 和 DNS 名。Service 不直接转发到 Pod IP，背后由 EndpointSlice 记录当前 Ready 的 Pod 地址，kube-proxy 或数据面再按这些端点转发。

## 16.6 Compose 与 Kubernetes 的语义差异

把 Compose 的 service 直接叫成“Kubernetes 的 Service”会引出一连串误解。Compose 的 service 是“用同一个镜像和配置运行的一个或多个容器”，它描述的是应用模型里的一个计算组件；Kubernetes 的 Pod 是“一个或多个共享网络和存储的容器”，是最小调度单位；Deployment 才是“维持一组相同 Pod”的工作负载对象；Service 则是“给一组 Pod 一个稳定网络入口”的对象。一个 Compose service 通常对应一个 Deployment 加一个 Service，而不是一个同名的 Kubernetes Service。

如果一个 Compose service 里确实有多个紧密耦合的进程，比如一个应用容器加一个只给本地用的 sidecar，那么它更接近一个多容器 Pod；如果只是同一个镜像的多个副本，就应该用 Deployment 的 `replicas`，不要把它们塞进一个 Pod。这个判断决定了后面所有字段怎么摆。

| 语义点 | Compose | Kubernetes | 迁移时的做法 |
|---|---|---|---|
| 运行单元 | service 是应用组件，由平台创建容器 | Pod 是最小调度单位，Deployment 管一组 Pod | 一个 service 一般拆成 Deployment + Service |
| 启动顺序 | `depends_on` 按条件等待依赖 | 控制器各自协调，没有全局启动 DAG | 用 initContainer、Job、应用重试和就绪探针 |
| 健康检查 | `healthcheck` 标记 healthy，供依赖判断 | startup/readiness/liveness 三种 probe，作用不同 | 不要把一个 healthcheck 原样搬成 liveness |
| 持久数据 | 命名卷由 Docker 管理 | PVC 申领 PV，StorageClass 动态供给 | 数据库等有状态服务要单独设计 |
| 配置注入 | `environment`、`env_file`、secret 文件 | `env`、`envFrom`、ConfigMap、Secret 挂载 | 注意环境变量在容器启动时固定 |
| 扩缩容 | `docker compose up --scale` 或 `deploy.replicas` | `spec.replicas`；自动扩缩用 HPA | 无状态服务优先用副本数，不要手工改容器 |

`depends_on` 是最容易被低估的一条。Compose 的短语法只保证依赖服务已经启动，长语法可以等 `service_healthy` 或 `service_completed_successfully`；它确实会按依赖顺序创建容器。Kubernetes 没有“先起数据库再起 api”的全局顺序：Deployment 控制器只关心自己的 Pod 数量，Postgres 的 Pod 还没 Ready 时，api 的 Pod 也可能已经被创建。正确的做法不是找一个 `depends_on` 的替代字段，而是让应用能承受依赖暂时不可用：启动时重试连接，readiness 在依赖可用前返回失败，需要初始化的 schema 用 Job 或 initContainer 完成。shorty 的 api 已经这样做了：数据库连不上时进程不退出，`/readyz` 返回 503，后台每 2 秒重试。

`healthcheck` 也不是一个字段换一个字段。Compose 的 healthcheck 是容器健康状态，主要影响 `depends_on: service_healthy` 和 `docker ps` 的显示；Kubernetes 的 livenessProbe 失败会重启容器，readinessProbe 失败会把 Pod 从 Service 端点摘掉，startupProbe 用来保护启动慢的应用。把 Compose 的 healthcheck 直接写成 livenessProbe，可能会让一个只是暂时连不上数据库的进程被反复重启；写成 readinessProbe，又可能让一个已经死锁的进程继续留在端点里。第 19 章会按这三个问题分别设计。

命名卷和 PVC 的差别不只是名字。Compose 的命名卷由当前 Docker 守护进程管理，挂载时只关心容器里的路径；Kubernetes 的 PVC 要说明访问模式（例如 `ReadWriteOnce`）、容量和 StorageClass，Pod 被调度到另一台节点时还要看 PV 的节点亲和性和存储插件。kind 自带一个默认 StorageClass，所以单节点实验里 PVC 很容易绑定；这并不代表生产上的数据库可以随便把 Compose 卷声明改成 PVC。

环境变量的注入方式看起来很像，实际边界不同。Compose 会在启动容器前把 `environment`、`env_file` 和 secret 文件准备好；Kubernetes 把普通配置放在 ConfigMap、敏感配置放在 Secret，容器可以用 `env` 逐个引用，也可以用 `envFrom` 批量注入，或者挂成文件。环境变量在容器启动时确定，之后改 ConfigMap 或 Secret 不会自动改已经运行的进程；需要热更新时，应用要读文件或自己 watch，不能假设环境变量会变。

扩缩容也是同样的道理。Compose 可以用 `docker compose up --scale api=3` 起三个容器，也可以用 `deploy.replicas` 声明副本数；它仍然是在一台 Docker 主机上做这件事。Kubernetes 的 `spec.replicas` 由 Deployment 控制器持续维持，HPA 还能按指标改这个字段。前者的“3”是一次命令的参数，后者的“3”是存在 API server 里的期望状态；这就是 16.1 看到的差别在扩缩容上的延伸。

## 16.7 排障：kind 建不起来，kubectl 连错集群

`kind create cluster` 失败时，最后一行通常只说“集群没建起来”，真正的原因在更早的输出里。常见的两种文本是 `failed to create cluster: command "docker run ..." failed` 和节点准备阶段的超时或日志匹配失败；前者要去看 Docker 为什么起不了节点容器，后者要去看节点容器里的 kubelet、containerd 或内核日志。不要只盯着最后一行，也不要连续重试，先把环境检查一遍。

第一步是确认 lab 里的 Docker daemon 正常。`docker info` 能返回 Server Version、Storage Driver 和 Cgroup Version，说明客户端连上了 daemon；如果这里就报 `Cannot connect to the Docker daemon`，后面的 `kind` 一定失败。第二步看磁盘：`df -h /var/lib/docker` 看 Docker 数据目录所在文件系统有没有空间，镜像层、节点容器和 kubelet 的日志都写在这里。第三步看内存：`free -m` 给出系统的 Mem 行，但容器里的 `free` 可能显示宿主的总内存，真正限制 lab 的是 cgroup 的 `memory.max`，所以还要读 `/sys/fs/cgroup/memory.max` 和 `memory.current`。

第二个常见故障不是集群坏了，而是 `kubectl` 连错了 context。`kubectl config current-context` 应该输出 `kind-shorty`；如果输出的是别的名字，先看 `kubectl config get-contexts`，确认那个 context 指向哪个 API server。修复方法不是手工改 server 地址，而是重新执行 `kind export kubeconfig --name shorty`，让 kind 把当前集群的证书和地址写回 kubeconfig。示例先造了一个指向 `127.0.0.1:1` 的旧 context，`kubectl get nodes` 报连接被拒绝；`kind export` 之后 current-context 回到 `kind-shorty`，节点仍然 Ready。

多集群环境里，最安全的做法是给每条命令带 `--context kind-shorty`，或者在执行前把 `current-context` 打印出来。`kubectl delete`、`kubectl apply` 这类命令不会问你“确定要操作这个集群吗”，连错 context 的代价可能是把对象建到测试集群，或者把生产对象删掉。kind 的 context 名字是 `kind-<集群名>`，这个约定比记 IP 地址可靠。

## 上生产前

kind 是本地实验工具，不是生产集群。它把节点做成 Docker 容器，控制平面和数据面都跑在同一个 Docker 守护进程上，节点故障、内核升级、磁盘损坏这些生产问题在这里都不会以真实的方式出现。生产要么用托管 Kubernetes，要么用 kubeadm 在独立机器上装；kubeadm 文档要求每台机器至少 2 GB 内存，控制平面至少 2 个 CPU，而且要用实现了 CRI 的容器运行时。Docker Engine 本身不实现 CRI，kubelet 从 1.24 起移除了内置的 dockershim，所以“生产节点上装个 Docker 就能跑 kubelet”这条老路已经不通；containerd 或 CRI-O 才是默认选择。

清单要进 Git，`kubectl apply` 只做执行。不要在生产上 `kubectl edit` 改对象，也不要把 Compose Bridge 生成的文件直接当成源码；生成物可以做迁移起点，但改完要落到版本库，下一次才能复现。`kubectl diff` 可以在 apply 前看差异，服务端 apply 和字段所有权能让多人协作时知道谁改了哪个字段，这些做法比“记住上次改了什么”可靠。第 18 章会把 shorty 的对象切到服务端 apply，第 34 章再讲 GitOps。

镜像用 digest，不用可变的 `latest`。`kind load docker-image` 只适合本地：它把镜像直接塞进节点，生产节点不会共享你的 Docker 守护进程，也不应该共享。生产要从 registry 拉镜像，Deployment 里写 `image@sha256:...` 或至少写不可变标签；配合镜像签名、SBOM 和准入策略，才能保证“跑的是审过的那一份”。本章的 `shorty:0.1` 是本地标签，生产要换成 registry 地址加 digest。

迁移前先设计 namespace、label 和资源配额，不要把所有对象塞进 `default`。namespace 是 RBAC、配额、网络策略和名字冲突的边界；label 是 Service、Deployment、NetworkPolicy 互相选中的依据；ResourceQuota 和 LimitRange 要在应用进来之前设好，否则一个没有 requests/limits 的 Deployment 可能把节点内存吃光。shorty 从第 16 章起就放在 `shorty` namespace，后面加数据库、Redis、worker 时不需要再搬一次。

Secret 不是“写进 YAML 就安全了”。Compose Bridge 生成的 Secret 把文件内容 base64 放进 `data`，base64 只是编码，不是加密；Kubernetes 默认把 Secret 以未加密形式存在 etcd 里，能读 API 或 etcd 的人都能拿到。生产要开静态加密、收紧 RBAC，并尽量避免把密码放进环境变量或镜像层。数据库这类有状态服务还要单独设计 PVC、备份和恢复，不能因为 kind 的默认 StorageClass 能绑定，就认为生产存储也自动可靠。
