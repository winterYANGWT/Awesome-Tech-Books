## 6.1 分段：三个检查同时跑

分段（sectioning）的前提是子任务互不依赖。三项检查各自看草稿的不同侧面，不需要读彼此的结论；如果后一个要用前一个的输出，那是链，不是分段（[第 5 章](ch05.md)）。

每个检查只拿自己需要的上下文：政策检查拿 `search_policies` 的条款，语气检查拿 `SUPPORT_PROMPT` 和草稿，隐私检查拿 `policies/privacy.md`。不要把整段对话复制三份。

| 检查 | 只拿什么 | 看什么 |
|---|---|---|
| 政策 | `search_policies` 返回的条款 | 回复是否与条款一致 |
| 语气 | `SUPPORT_PROMPT` + 草稿 | 是否简洁、礼貌、有下一步 |
| 隐私 | `policies/privacy.md` | 是否泄露其他顾客信息 |

每个检查输出同一个 JSON 结构：`{"pass": bool, "issues": [...], "evidence": "..."}`。`evidence` 必须能定位：草稿原句或政策条款标题。

草稿变长时，先做两件事：

- 截断到要检查的段落；
- 三项请求里的草稿都只发截断后的版本。

汇总规则是代码，不是模型：

- 三项全过才通过；
- 任一项失败，就把 `issues` 按“政策 > 隐私 > 语气”排序后回给生成步；
- 不要再用另一个模型“综合三个检查”，那会把确定性又变回概率。

三项都通过时，汇总只是 `ok == len(CHECKS)`（等价于 `all(...)`）；不通过时，排序也只是字典。把这三行逻辑交给模型，等于把可测试的代码换成一次采样。

## 6.2 并行的实现细节和失败

默认的 `asyncio.gather` 在一个任务抛异常时会立刻把异常抛给 `await`，另外两个任务即使继续跑完，结果也回不到调用处。下面这张图是一次失败注入：三个请求同时发出，语气检查最先拿到回复，随后在 `check` 返回结果前抛 `ValueError`。


这次运行的输出：

```text
{{#include code/ch06/6_2_gather.out}}
```

政策、隐私两项的结论保住了，语气一项显示为“失败”，汇总走“需人工/重试一次”。这就是 `return_exceptions=True` 的作用：它让 `gather` 等齐所有任务，把异常当成一个返回值。

失败注入要放在协程里，不要放在 `gather` 外面。放在外面，异常在发请求之前就抛出，另外两个任务根本没机会启动。

去掉它，代码通常长这样：

```python
results = await asyncio.gather(*(check(spec) for spec in CHECKS))
print([r["pass"] for r in results])   # 一个异常，整行都拿不到
```

一个任务抛异常，`gather` 立刻向上抛；另外两个协程不会被取消，但结果回不到这里。要保住它们，要么加 `return_exceptions=True`，要么给每个任务包一层 `try/except`。

并行示例用 `AsyncOpenAI`，不是同步的 `OpenAI`。同步客户端在事件循环里会阻塞，`gather` 实际上变成串行；这是本书示例约定的唯一例外。

```python
from openai import AsyncOpenAI
client = AsyncOpenAI()
```

其余细节：

- 请求内容必须互不相同。每个请求带上自己的 `check` 名或 `reviewer` 编号，否则回放时答案可能被分错。
- 打印顺序要固定。`gather` 的返回顺序和输入顺序一致，但完成顺序不一定；示例按输入顺序 `zip` 回去打印。
- 一个检查失败时，用“未完成”占位，不要直接 `[r["pass"] for r in results]`；返回列表里可能是异常对象。
- 失败不等于丢掉整次检查：政策、隐私的结论仍然保留，汇总只需要补一句“语气项需人工”。
- 失败的那次请求也计费；示例的 token 行只统计成功的两项。

## 6.3 投票：同一问题问多次

投票（voting）是同一个问题问 N 次，再按多数或阈值决定。N 次调用要独立且不同角度：严格按政策、站在顾客角度、只看金额、只看时限、找反例。复制同一个提示五次，更容易得到高度相关的错误。

这次 4 票“不可退”、1 票“可退”，多数票是“不可退”。投“可退”的是只看时限的评审：签收 12 天，在 15 天内；它按自己的检查项投票，没有看商品类型。

五个评审看的是同一份材料，但检查项不同。只看金额的评审这次没有算钱，直接按教辅拆封投了不可退；只看时限的评审只算 12 天，漏掉了拆封条款。

分歧不一定按分配的检查项出现，这正是要保留每票理由的原因；只存一个“多数票”会丢掉最有用的信息。计票规则本身也是代码：

- 每个评审输出 `{"verdict": "可退"|"不可退"|"需人工", "reason": "..."}`；
- 用 `Counter` 计票，5 票里至少 3 票才算多数；
- 票数相同或没有多数时进入“需人工”，不要随机挑一个。

| `Counter` 看到的票型 | 结果 |
|---|---|
| 3:2 | 3 票的一方是多数 |
| 2:2:1 | 两个并列最高，没有多数，转人工 |
| 1:1:1:1:1 | 没有 3 票，转人工 |

这张表是构造的计数示例，不是一次模型运行；6.4 的 8 题这次没有平票。

5 票是成本/稳定性的折中。票越多越贵，相关错误不会因为票多而消失，这一节只讲这一次的票型，不宣称“5 票一定比 1 票准”。6.4 用同一批票比较单票和多数票。

| 票数 | 调用数 | 什么时候值得 |
|---|---|---|
| 1 | 1 | 高频、错误代价低 |
| 5 | 5 | 判断不稳定、错了代价高 |

5 票不是固定规则。判断越贵、越不稳定，可以加票；但票数增加时，成本线性上涨，相关错误不会自动消失。

投票的成本是 N 次调用加 N 份材料；如果材料很长，先把事实压缩成一段共用背景，再让评审各自补自己的检查项。

投票适合“有明确对错但模型不稳定”的判断，比如 T14 这种教辅拆封、非质量问题的退货。它不适合“需要最新事实”或“需要多步工具”的任务；后者要先取事实，再投票。

每片带稳定 id `B07-R01` 到 `B07-R10`，返回后按 id 排序，不依赖完成顺序。reduce 只拿 `review_id/issue/stars/quote`，按 `issue` 计数、按星级排序、挑两条原句作引用。

map 的输出只有四个字段：

- `review_id`：稳定 id，例如 `B07-R04`；
- `issue`：五类之一；
- `stars`：星级；
- `quote`：评论原句。

reduce 分三步：先按 `issue` 计数，再按 `(stars, review_id)` 排序，最后取前两条非“无问题”的 `quote`。排序键里带 `review_id`，同星级时顺序也固定。

计数是 `Counter` 做的，模型只写最后两句概述，不要把计数交给模型再加一遍。reduce 的输入带 `review_id`，正文才能回到具体评论，引用时也不用再翻原文。示例没有处理缺片：`gather` 默认在第一个异常处抛出，reduce 也拿不到已经返回的片。

真要处理缺片，至少做三件事：

- 保留已返回的片和缺的 `review_id`；
- 别把缺片当成“无问题”混进计数；
- 缺多少要重跑，按业务定，本章没有给出阈值。

下面的 `# llm: none` 示例只演示索引这一层：不调用模型，收到 9 片却仍按 10 片汇总。

20 条评论（B07 11 + B19 9）如果全跑，就是 20 次 map 加 1 次 reduce；示例只跑 B07 最近的 10 条，省下 10 次 map 调用，不影响“按 id 排序、缺片可定位”的演示。

同一件事在三种写法里的差别：

| | `asyncio.gather` | LangGraph 并行节点 + `operator.add` | LangGraph `Send` map-reduce |
|---|---|---|---|
| 并发单位 | 一个协程 / 一个请求 | 一个节点 / 一条分支 | 每个 `Send` 一项 |
| 结果怎么聚合 | 列表下标或 `zip` 按输入顺序取 | 写入同一 state key，用 `operator.add` 追加 | map 结果进 list，reduce 节点汇总 |
| 顺序谁保证 | `gather` 的返回顺序等于输入顺序 | `operator.add` 只保证都追加，不保证顺序 | 返回顺序不保证，reduce 里按 id 排序 |
| 一个分片失败怎么办 | `return_exceptions=True` 保留其余，异常占位 | 默认向上抛，整步失败；可在节点内捕获或配 `retry_policy` | 同左，默认整步失败；节点内捕获后可跳过 |
| 适合的场景 | 少量固定分支、三项检查 | 固定并行分支、共享 state | 片数由输入决定的大 map |

三种写法都能并行，差别在“谁保证顺序”和“失败怎么留痕”。`gather` 把顺序写进代码，LangGraph 把顺序交给 reducer 的追加顺序或 reduce 里的排序。

> **旧资料提示**：LangChain Academy 模块 4 的 parallelization 用 Tavily 和 Wikipedia（联网、要 key），本书改用本地书店数据和本地文件。那门课用 `gpt-4o`，本书用 `deepseek-flash`；它的并行节点写入同一 state key 时需要 `operator.add`，否则报 `InvalidUpdateError`。本章的 `gather` 版本用输入列表的顺序保证顺序，LangGraph 版见[第 26 章](ch26.md)。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `AsyncOpenAI` + `asyncio.gather` | 并发发请求 | 同步 `OpenAI` 会阻塞事件循环 |
| `return_exceptions=True` | 一个任务异常时保留其余结果 | 返回列表可能是异常对象，逐个判断 |
| 固定打印顺序 | 输出可回放 | 返回顺序等于输入顺序，完成顺序不一定 |
| 请求内容互不相同 | 回放不串答案 | 带上 `check` 名或 `reviewer` 编号 |
| `Counter` 计票 | 多数 / 平票 / 需人工 | 5 票至少 3 票；平票转人工 |
| `review_id` 稳定 id | map 分片可重放 | 返回后按 id 排序 |
| map 输出 schema | 只传结构化结果 | `review_id/issue/stars/quote` |
| `operator.add` | LangGraph 并行追加 | 只保证追加，不保证顺序 |
| `Send` | 动态 map | 第 26 章 |
| `harness.run(..., verbose=False)` | 不逐步打印每一轮 | 并行跑多个 agent 时用：各自的打印会交错，等全部结束后按固定顺序打印 |

## 思考题

1. 找错：`6_2_gather.py` 如果去掉 `return_exceptions=True`，一个检查抛异常时另外两个的结果会怎样？怎么改才能保住？

   <details><summary>提示</summary>

   默认的 `gather` 会立刻把异常抛给 `await`，其余结果拿不到；它们不会被取消。加 `return_exceptions=True`，或者给每个任务包一层 `try/except` 返回占位。

   </details>

2. 预测：T14 的 5 票里，如果 5 个评审用完全相同的提示，票型会更集中还是更分散？为什么？

   <details><summary>提示</summary>

   更集中，但错误也更容易一起犯。相同提示、相同模型、相同材料，五次调用只是同一判断的近似复制；分歧少了，相关错误不会消失。

   </details>

3. 权衡：5 票投票和 1 票加人工复核，哪个更便宜、哪个更适合高频工单？

   <details><summary>提示</summary>

   本章没有 token 单价和人工时薪，算不出具体金额。按常见人工成本，1 票加人工通常比 5 次模型调用贵；高频工单里人工是瓶颈，更适合 5 票或单票加抽检，人工只处理平票和高风险单。

   </details>

4. 迁移：把 B07 的评论 map-reduce 改成“按季度汇总退货原因”，数据源、分片键和 reduce 的计数维度要怎么改？

   <details><summary>提示</summary>

   数据源从 `reviews` 换成 `returns`（`reason` 在 `returns` 表，`reviews` 只有星级和正文）；分片键从 `review_id` 换成“季度 + `return_id`”，季度取 `returns.created`；reduce 的计数维度从 `issue` 换成“季度 × `reason`”，按季度排序。缺片按季度分别统计。

   </details>
