# 第 2 章 模型 API：消息、token、思考和流式输出

账单上，一次客服回答长这样：

```text
prompt_tokens=89  completion_tokens=588  total_tokens=677
```

这是 2.1 那次运行的数字。多轮对话里，系统提示和历史每轮都要重发，`prompt_tokens` 会涨到上千；模型上下文有 1,048,576 token，不设 `max_tokens` 时，非思考模式默认只给 8K 输出，答案可能在中途被截断。

这一章把一次 Chat Completions 请求拆开：消息怎么排、token 花在哪、思考怎么关、流式怎么拼、截断和错误怎么处理。

| role | content | 什么时候用 |
|---|---|---|
| `system` | 必填 | 身份、规则，放在最前 |
| `user` | 必填 | 顾客的话 |
| `assistant` | 带 `tool_calls` 时可为 `None` 或空串 | 模型上一轮的回答 |
| `tool` | 必填 | 工具结果，带 `tool_call_id`（[第 3 章](ch03.md)） |

四种角色里，`system` 不是特殊字段，只是排在最前面的第一条消息。放在最前面最省事，也最容易被缓存命中（2.2）。

请求里常用的可选参数还有：

- `temperature`：采样温度，0 更集中、2 更发散；思考模式下不起作用（2.3）。`top_p` 才有 0.95 的下限。
- `max_tokens`：输出上限；不设时默认 8K/64K，`reasoning_effort=max` 时 128K（2.2）。
- `stream`、`tools`/`tool_choice`、`response_format`：分别在 2.4、[第 3 章](ch03.md)、[第 4 章](ch04.md)。

`deepseek-flash` 和 `deepseek-v4-pro` 都接受文本，前者还接受图像。本章示例用 `deepseek-flash`。

`finish_reason` 的 `stop` 是正常结束，`length` 是碰到 `max_tokens` 或输出顶到上下文上限，`tool_calls` 是模型要调工具。多轮时 `assistant` 消息原样放回，`tool` 消息跟在它后面；顺序错了会被 400 拒绝（[第 3 章](ch03.md)）。

1,048,576 是输入加输出的总上限，不是每次都能写 1M；输出还受 `max_tokens` 和模型最大输出 393,216 的限制。

{{#fig ch02/context_budget}}

图里左边括号是 `prompt_tokens`，右边括号是 `max_tokens`，都是示意值，不按比例。1,048,576 的窗口是横轴总长，不是免费额度：系统提示、工具定义和历史每轮都要重发、重新计费。

`messages` 是模型能看到的全部内容；订单表、政策文件、数据库都不会自动出现。要让模型看到，必须有人把它们放进消息，或者通过工具结果送进去（[第 3 章](ch03.md)）。

2.1 的示例只传 `temperature` 和 `max_tokens`；`stream` 在 2.4，`tools`/`tool_choice` 在[第 3 章](ch03.md)，`response_format` 在[第 4 章](ch04.md)。

## 2.2 token 和 usage

`usage` 有三个主字段：`prompt_tokens` 是这次请求的输入，`completion_tokens` 是输出（含思考 token），`total_tokens` 是两者之和。多轮循环要把每轮的 `usage` 累加；[第 3 章](ch03.md)的 `Result.usage` 就是这么做的。


这次运行的输出：

```text
{{#include code/ch02/2_2_usage.out}}
```

第一次 `prompt_tokens=403`，`prompt_cache_hit_tokens=0`。第二次 `prompt_tokens=411`，命中 256。两次只差问题那句，前缀相同，第二次有 256 个 token 按缓存价计费。

`prompt_tokens_details.cached_tokens=256` 是 OpenAI 风格的同一个数；DeepSeek 在 `usage` 顶层另给 `prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens`。

缓存只说明“前缀相同的部分可能便宜”，这次只命中 256/411，不是整段都便宜。前缀越长，重复发送时可能省下的越多。命中规则、命中率和省多少钱留到[第 23 章](ch23.md)。

| 字段 | 含义 |
|---|---|
| `prompt_tokens` | 本次输入；等于 `prompt_cache_hit_tokens + prompt_cache_miss_tokens` |
| `completion_tokens` | 本次输出，含思考 token |
| `total_tokens` | 输入加输出 |
| `prompt_cache_hit_tokens` | 命中缓存的前缀 token（DeepSeek 顶层） |
| `prompt_cache_miss_tokens` | 未命中的前缀 token（DeepSeek 顶层） |
| `prompt_tokens_details.cached_tokens` | 同一个命中数，OpenAI 风格 |
| `completion_tokens_details.reasoning_tokens` | 思考 token（2.3） |

多轮和估算时记住几点：

- `prompt_tokens` 每轮都重发，第 10 轮通常比第 1 轮大。
- `completion_tokens` 含思考 token，回答长或思考多都会变大。
- 一次会话的账单是每轮 `usage` 的和，不是最后一次的值；估算成本要累加每轮实际 `usage`，不能拿第一轮的 `usage` 乘轮数。
- 命中不是整段：这次 411 个 prompt token 里只有 256 个命中，规则见[第 23 章](ch23.md)。

`max_tokens` 的上限是模型的最大输出，`/models` 返回 393,216。不设时非思考模式默认 8K，思考模式 64K，`reasoning_effort=max` 时 128K（DeepSeek 2026-11 文档）。`max_completion_tokens` 在 DeepSeek 上被接受但不生效，本书统一用 `max_tokens`。

输入加输出不能超过上下文长度 1,048,576。输入本身就超长时，请求会在生成前被拒绝（通常 400）；生成过程中把总长度顶到上限时，HTTP 仍是 200，`finish_reason=length`。

token 不等于字数：政策全文 544 个字符（其中 322 个汉字），连同前面的回答要求，这次 prompt 是 403 个 token。本例关掉了思考，所以 `completion_tokens` 只反映回答长度，分别是 19 和 27。中文、英文、JSON、代码的切分不同，估算只能靠 `usage` 实测，正文不写“每个汉字等于多少 token”。

## 2.3 思考模式

DeepSeek 默认开启思考。响应消息里多一个 `reasoning_content`，`usage.completion_tokens_details.reasoning_tokens` 是思考花掉的 token。两者都不该直接展示给顾客：思考是模型的草稿，不是给顾客的答复。


默认思考这次用了 290 个 reasoning token，`completion_tokens=403`；关掉后 reasoning 为 0，`completion_tokens=59`。回答本身也从 176 字符缩到 88 字符，这次关掉思考让回答更短。

注意这是同一个问题；拿两个不同问题比，说明不了关闭思考的效果。

| 项目 | 做法 |
|---|---|
| 默认思考 | 开启；`reasoning_effort` 默认 `high` |
| 关闭 | `extra_body={"thinking": {"type": "disabled"}}`，或 `reasoning_effort="none"` |
| 思考内容 | `message.reasoning_content` |
| 思考 token | `usage.completion_tokens_details.reasoning_tokens` |
| 下一轮是否回填 | 带 `tools` 时之前所有轮次都要原样放回；不带 `tools` 不必；本书 harness 一律放回（[第 3 章](ch03.md)） |

{{#fig ch02/thinking_split}}

图里第 3 步的思考随响应返回，第 5 步客户端把回答和思考一起放回 assistant 消息，下一轮请求带上 `reasoning_content`（带 `tools` 时必须这样做）。对顾客只返回 `content`，`reasoning_content` 可以记日志，不要拼进客服话术。

`thinking` 对象优先于 `reasoning_effort`：

- `none`：关闭思考。
- `low`/`high`/`max`：开启思考，力度递增，默认 `high`。
- `minimal` 映射到 `low`，`medium`/`xhigh` 映射到 `high`。
- `reasoning_effort` 只影响思考力度，不改变问题；`low` 通常更省，`max` 更慢更贵。

DeepSeek 的文档写明，思考模式下 `temperature` 不起作用；`deepseek-flash` 的 `top_p` 在思考模式默认 1.0、低于 0.95 按 0.95 处理，非思考模式固定 1.0。实测传 `temperature=0` 或 `seed` 都不会让回答变确定，可复现只能靠录制回放。

DeepSeek 的文档规定：思考模式下，请求里带 `tools` 时，之前所有轮次 assistant 消息的 `reasoning_content` 都要原样放回，否则 API 可能返回 400。不带 `tools` 的请求不需要放回，放了也会被忽略。本书的 `harness.run` 一律放回（[第 3 章](ch03.md)），带 `tools` 时不能为了省 token 省掉。

思考 token 计入 `completion_tokens`，所以关掉思考不一定让回答变短，但少了这部分 token，账单更可控。这次回答也短了，问题简单；首个 token 的延迟本章没有量，本书的离线回放也测不出来。

流式下不能靠 chunk 数量判断结束，要看 `finish_reason` 或 `[DONE]`。如果只想显示文本，收到 `finish_reason` 就停，不要等连接自己断。网络断开时，已收到的片段还在，但拿不到完整 `usage`。

{{#fig ch02/stream_pieces}}

流式代码里还有几个细节：

- 每个 chunk 还有 `id`、`created`、`model` 等元数据，拼文本只用 `delta.content`。
- 最后一个 chunk 的 `usage` 和 2.2 的非流式 `usage` 是同一套字段。
- 页面可以边收边显示，落库和计费要等最后一个 chunk。

`stream_options={"include_usage": True}` 时，每个 chunk 都有 `usage` 字段，除最后一个外都是 `null`；最后一个内容 chunk 带整次请求的统计，没有单独的 usage-only chunk。不传 `stream_options` 时，`usage` 只在最后一个 chunk 出现。

工具调用在流式下也会分片到达，拼接细节本章不展开；本章只处理文本，非流式的 `tool_calls` 结构见[3.2 节](ch03.md)。本书的离线回放是整段返回的，不能用来量首个 token 的延迟，本章不写毫秒数。

## 2.5 三种接口格式

Chat Completions、Responses、Anthropic Messages 说的是同一件事：把系统提示、消息和回答放进请求与响应，只是字段名不同。本章的示例只发了 Chat Completions；下表把同样的东西在另两种格式里的字段名并排列出来：

| 概念 | Chat Completions | Responses | Anthropic Messages |
|---|---|---|---|
| 系统提示 | `messages[0].role="system"` | `instructions` | 顶层 `system` |
| 消息数组 | `messages` | `input` | `messages`，content 是 block 数组 |
| 工具调用 | `message.tool_calls` | `output` 里的 `function_call` | `tool_use` block |
| 工具结果 | `role:"tool"` + `tool_call_id` | `function_call_output` + `call_id` | `tool_result` block + `tool_use_id` |
| 思考 | `message.reasoning_content` | `reasoning` item | `thinking` block |
| 流式 | `choices[0].delta` | `response.output_text.delta` 等事件 | `content_block_delta` 等事件 |
| usage | `prompt_tokens`/`completion_tokens` | `input_tokens`/`output_tokens` | `input_tokens`/`output_tokens` |
| 结构化输出 | `response_format` | `text.format` | `output_config.format`（`json_schema`） |
| DeepSeek 支持 | 是 | 是（`POST /responses`） | 是（`/anthropic`） |

{{#fig ch02/three_formats}}

三套格式的差别可以归成几点：

- Responses 把消息、工具调用、工具结果都当成 item，`output_text` 是便捷属性。
- Anthropic 的 `content` 是 block 数组，一条消息可以同时有文字和工具调用。
- 三套格式的 `usage` 名字不同，但都能算出输入和输出；迁移时先对齐 system、工具 schema 和停止原因。
- Responses 的 `input` 可以是一条字符串或 item 数组；Anthropic 的 `system` 不放进 `messages`。
- 输出上限的字段不同：Chat 用 `max_tokens`（可省，DeepSeek 不设时按 8K/64K/128K），Responses 用 `max_output_tokens`，Anthropic 的 `max_tokens` 必填。
- 流式事件名也不同：Responses 用 `response.*`，Anthropic 用 `message_*` 和 `content_block_*`。
- 三套格式都要显式把上下文放进去；没有一个接口会自动把数据库塞进请求。

DeepSeek 还提供 Responses 接口（`POST /responses`）和 `/anthropic` 兼容接口（`POST /v1/messages`）。Responses 的 `output` 里有 `reasoning` 项和 `message` 项。

`/anthropic` 带 `tools` 正常，返回 `thinking` 和 `tool_use` block，`stop_reason: tool_use`。正文用 Chat Completions，三套请求体的完整对照在[附录 A](appendix-a.md)。

兼容不等于完全兼容：Chat 的 `response_format: json_schema` 在 DeepSeek 上返回 400，Responses 的 `text.format` 支持 `json_schema`；`reasoning_content` 和 `thinking` 字段名不同，输出上限的字段名和是否必填也不同。[第 4 章](ch04.md)、[附录 A](appendix-a.md) 细讲。

> **旧资料提示**：OpenAI 2025-04 的实践指南还推荐用当时的推理模型来生成指令；到 2026-11，用当前的强模型即可，不必照搬型号。

## 2.6 长度、截断和错误

`max_tokens` 限制输出。碰到上限时 `finish_reason="length"`，`content` 可能在句子中间断掉，JSON 也会断在半截；不要对截断的输出做 `json.loads` 后继续。


这次运行的输出：

```text
{{#include code/ch02/2_6_max_tokens.out}}
```

这次 32 个 completion token 正好用完，`finish_reason=length`，内容停在“无需退回”，`以句号结尾：False`。这里关掉思考，让 32 个 token 都给回答；如果开着思考，思考会先吃掉预算，`content` 可能为空。

`max_tokens` 只限制输出，不限制输入；输入太长要在发请求前裁剪，不能靠调大 `max_tokens` 解决。

Responses 里这个字段叫 `max_output_tokens`；Anthropic 的 `max_tokens` 必填，没有默认值。

| 情况 | 状态码/信号 | 做法 |
|---|---|---|
| 参数、格式、超长 | 400 | 不要原样重试；改请求 |
| 限流、服务端错误 | 429/5xx | 退避重试 |
| 输出到上限 | 200 + `finish_reason=length` | 先看 `max_tokens` 是否用完；没用完就缩短输入 |
| 认证/余额 | 401/402 | 修 key 或充值，不重试 |

SDK 默认会重试一部分错误；要看原始错误，用 `client.with_options(max_retries=0)`。写示例时只打印 `status_code`、`error.type`、`error.message` 和 `finish_reason`，不打印耗时、随机 id 和完整堆栈。

错误消息里的 `request_id` 每次不同，打印前删掉；`error.type` 比 HTTP 状态码更具体。重试要加退避和上限，400 重试只会重复同样的错误，429/5xx 才值得等一会儿再发。

遇到 400 先把请求体打出来（去掉 key），对照文档看字段名和类型。

{{#fig ch02/limits}}

图里三行是三把尺子：上下文窗口 1,048,576，单次输出上限 393,216，默认输出 8K/64K（`reasoning_effort=max` 时 128K）。输入本身超过窗口通常返回 400；生成把总长度顶到上限时是 200 + `finish_reason=length`。

长对话要么裁剪、要么压缩（[第 13 章](ch13.md)、[第 15 章](ch15.md)），不要靠“上下文很大”硬塞。

这三把尺子要分开看：

- 窗口决定能不能发。
- `max_tokens` 决定这次能写多少。
- 模型最大输出决定 `max_tokens` 能设到多大。

裁剪是删旧消息，压缩是把旧消息换成摘要，两者的取舍在[第 13 章](ch13.md)、[第 15 章](ch15.md)。

> **旧资料提示**：Anthropic 2025-06 的多 agent 调研文章按 200,000 token 的上下文做截断设计；DeepSeek-V4.1-Flash 在 2026-11 是 1,048,576。

> **旧资料提示**：把上下文长度当成免费空间的旧习惯要改：每轮重发都计费，长上下文还要看缓存命中（[第 13 章](ch13.md)）。

| `reasoning_content` | 思考内容 | 不展示给顾客；带 `tools` 时之前所有轮次的都要原样放回 |
| `completion_tokens_details.reasoning_tokens` | 思考 token | 计入 completion |
| `extra_body={"thinking":{"type":"disabled"}}` | 关思考 | 优先于 effort |
| `reasoning_effort` | 思考力度 | `none`/`low`/`high`/`max` |
| `stream=True` | 流式 | 拼 `delta.content` |
| `stream_options={"include_usage": True}` | 每个 chunk 带 usage | 最后一个才是统计 |

| `finish_reason` | 含义 | 做法 |
|---|---|---|
| `stop` | 正常结束 | 用 `content` |
| `length` | 碰到 `max_tokens`，或输出顶到上下文上限 | `max_tokens` 用完就加大，否则缩短输入；不要解析半截 JSON |
| `tool_calls` | 要调工具 | 执行后回填（[第 3 章](ch03.md)） |

## 思考题

1. 估算：假设 `SUPPORT_PROMPT` 加 9 个工具定义约 1,500 token，每轮新增约 200 token，输出每轮约 300 token。第 10 轮请求比第 1 轮多花多少 prompt token？10 轮一共多少 token？

   <details><summary>提示</summary>

   第 1 轮 prompt 约 1,500；第 10 轮约 1,500 + 9×200 = 3,300。10 轮 prompt 是等差数列，再加 10×300 的输出。

   </details>

2. 分析：`2_2_usage.py` 第一次请求的 `prompt_cache_hit_tokens` 是 0，第二次是 256。解释这个差别；如果第二次也是 0，列出三种可能原因。

   <details><summary>提示</summary>

   两次请求只差问题那句，前缀相同，第一次写入缓存、第二次才命中。第二次仍为 0 时：前缀变了（system、消息顺序、时间戳）；缓存没热或已过期；换了模型、接口或请求参数。

   </details>

3. 预测：把 `stream=True` 的 `delta.content` 直接 `"".join(...)`，遇到 `None` 会怎样？怎么改？

   <details><summary>提示</summary>

   `TypeError: sequence item 0: expected str instance, NoneType found`。改成 `"".join(x or "" for x in pieces)`，或者只收集非空片段。

   </details>

4. 迁移：把 2.1 的 Chat Completions 请求改写成 Anthropic Messages 的 `system`/`content` 结构，哪些字段必须搬家？

   <details><summary>提示</summary>

   system 从 `messages[0]` 搬到顶层 `system`；user 消息的 `content` 变成 `[{"type":"text","text":…}]`；`max_tokens` 必填；用 DeepSeek 的 `/anthropic` 时 `model` 仍是 `deepseek-flash`，换到 Anthropic 服务才换成 Claude 型号；usage 和停止原因改看 `input_tokens`/`output_tokens` 和 `stop_reason`。

   </details>
