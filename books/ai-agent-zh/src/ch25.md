## 25.1 检查点和 thread：给图装上记忆

`compile(checkpointer=InMemorySaver())` 只是给图装了存储，调用时还要告诉它存到哪个 thread。`config={"configurable": {"thread_id": "T06-A"}}` 里的 `thread_id` 就是索引，也是最终必需的；config 里一个键都没有时，LangGraph 1.2 抛 `ValueError`，消息里列出 `thread_id`、`checkpoint_ns`、`checkpoint_id` 三个键。

```python
graph = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "T06-A"}}
graph.invoke({"messages": [HumanMessage("那能退多少？")]}, config)
```

每个超步结束写一个检查点。`graph.get_state(config)` 返回一个 `StateSnapshot`，常用字段如下：

| 字段 | 里面是什么 | 什么时候看 |
|---|---|---|
| `values` | 当前 state 的各个键 | 取消息、金额、订单 |
| `next` | 下一步要跑的节点名，`()` 表示已结束 | 判断图停在哪 |
| `config` | 带 `thread_id` 和 `checkpoint_id` 的配置 | 重放、分叉时原样传回去 |
| `metadata` | `step`、`source`（`input`/`loop`/`update`/`fork`）、`parents` | 看这一步是输入、循环、更新还是分叉 |
| `created_at` | 检查点建立时间 | 排序、清理旧检查点 |
| `parent_config` | 上一个检查点的配置，第一个是 `None` | 追检查点链 |
| `tasks` | 本步的任务，含 `interrupts` | 查有没有挂起的中断 |

`get_state_history(config)` 按时间逆序返回整条 thread 的所有检查点，最新的在前；传入带 `checkpoint_id` 的 config 时只返回那个检查点。两个容易混的地方：`snapshot.next` 是“还要跑什么”，`snapshot.config["configurable"]["checkpoint_id"]` 才是“站在哪个检查点上”。

新 `thread_id` 是空状态；同一个 `thread_id` 再 `invoke` 新输入，消息走 `add_messages` 追加，不会清空旧历史。下面这个示例把同一句话分别发给线程 A 和线程 B。

`MemorySaver` 是 `InMemorySaver` 的别名，实测 `MemorySaver is InMemorySaver` 为 `True`。两者都只把检查点放在内存里，进程重启就没了；25.5 换成 `SqliteSaver`。

检查点保存的是图 state，不是模型的上下文窗口。第 15 章的压缩、裁剪如果只改了发给模型的那份消息，没有写回 state，下一轮仍会从旧的完整历史重建上下文。

## 25.2 中断：把大额退款交给主管

静态断点 `compile(interrupt_before=["tools"])` 只能停在节点边界，而且每次到 `tools` 都停。金额超过 500 元才需要批准，这种条件判断写在 `propose` 之后的路由里：`interrupt(payload)` 把 `payload` 交给调用方，然后暂停。

`payload` 必须能 JSON 序列化。恢复用 `graph.invoke(Command(resume=value), config)`，`value` 成为 `interrupt()` 的返回值。

节点恢复时从头执行，`interrupt()` 之前的代码会重跑。退款、发消息这类副作用要放在 `interrupt()` 之后，或者保证幂等；示例里的 `propose` 只读订单，重跑也不会改数据。

静态断点同样要有 checkpointer，但恢复方式不同：`compile(interrupt_before=["tools"])` 停下来后用 `invoke(None, config)` 继续，不需要 `Command`。它只能按节点名停，不能判断“这笔退款是否超过 500 元”。

同一个 thread 的下一次 `Command(resume=...)` 对应最近一次中断。多个并行分支同时中断时，文档的写法是把 `{interrupt.id: resume_value}` 传给 `Command(resume=...)`；本书示例只有一个中断，没有展开这个写法。

| | 第 20 章的同步审批 | 本章 `interrupt()` | 静态 `interrupt_before` |
|---|---|---|---|
| 在哪暂停 | `risky` 工具执行前 | 节点里任意一行 | 指定节点执行前/后 |
| 状态存在哪 | 进程内存（或自己写 `pending.json`） | 检查点 | 检查点 |
| 怎么恢复 | 同一个函数继续，或读 `pending.json` | `Command(resume=...)` | `invoke(None, config)` |
| 能不能改状态 | 不能，只能返回 `True` 或拒绝理由 | 可以在恢复前 `update_state` | 可以 `update_state` |
| 适合什么 | 工具级的同步审批 | 按金额、按条件、节点内部暂停 | 调试、逐节点步进 |

> **旧资料提示**：
> - LangChain Academy 的 breakpoints 用 `interrupt_before=["tools"]` 做静态暂停；dynamic-breakpoints 用 `NodeInterrupt` 按条件暂停。LangGraph 1.2 仍保留这两种写法，条件审批改用节点内 `interrupt()` 加 `Command(resume=...)`。
> - LangChain Academy 常用 `invoke(None, config)` 继续；回答中断要用 `Command`，`None` 只用于继续未完成的工作或重放。
> - LangChain Academy 用 `MemorySaver`，现在文档主用 `InMemorySaver`，两者是同一个类；LangChain Academy 的 API 示例写 `checkpoint_id`/`parent_checkpoint_id`，Python 的 `StateSnapshot` 用 `config.configurable.checkpoint_id` 和 `parent_config`。

## 25.3 编辑状态：让人改动 agent 的提案

`graph.update_state(config, values, as_node=...)` 在最新检查点后追加一个检查点，不会回滚历史。`as_node` 指定“这次更新算哪个节点写的”，也就决定图从哪个后继继续。

| 检查点 | step | amount | 写的节点 | 改的人 / 理由 |
|---|---|---|---|---|
| 入口 | 0 | 0.0 | 输入 | — |
| 原提案 | 1 | 680.0 | `propose` | — |
| 人改后 | 2 | 600.0 | `update_state` | 主管 / 按主管意见改金额 |
| 批准（重跑） | 3 | 600.0 | `approve` | 主管 |
| 执行 | 4 | 600.0 | `execute` | — |

这张表就是审计视图：原提案、改后的值和执行金额都在，`metadata` 只说明这一步是 `input`、`loop`、`update` 还是 `fork`，不记改的人。示例把 `edited_by` 和 `edit_note` 写进 state，时间看 `created_at`，真实系统还要把审批记录和工单号一起存。

审计记录里至少要留三样：原提案、改后的值、谁改的以及理由。`as_node` 推断在多分支同一超步写同一个键时会失败，抛 `InvalidUpdateError`；这种时候显式写节点名更稳。

对 `messages` 用 `add_messages`：带相同 `id` 覆盖，不带 `id` 追加，删除用 `RemoveMessage(id=...)`。改消息内容时保留原 `id`，否则会变成一条新消息，旧消息还在。

## 25.4 时间回溯：重放和分叉

重放是把旧检查点的 `config` 传回 `invoke`：`graph.invoke(None, snapshot.config)`。`checkpoint_id` 之后的节点重新执行，模型调用也会重发，不是读缓存。

从最终检查点重放是 no-op，因为 `next=()`，所以要选 `next` 非空的检查点。重放会在同一 thread 里追加新检查点，原来的检查点不会消失，两者靠 `parent_config` 连成链。分叉后 `get_state(config)` 返回最新分支，要拿旧分支就用它的 `checkpoint_id` 再查一次。

分叉是在旧检查点上先 `update_state` 得到新 `config`，再 `invoke(None, fork_config)`。原 thread 的历史保留，新分支追加。下面的确定性图把 `calc(680)`、`draft`、`finish` 三步分开，方便看哪些节点重跑。

{{#fig ch25/time_travel}}

两条分支的终态都留在历史里：`退款 680.0 已执行` 和 `退款 500.0 已执行`。重放会重新触发 `interrupt()`，需要重新 `Command(resume=...)`；分叉也一样。

| | 历史 | 模型调用 | 副作用 |
|---|---|---|---|
| 重放 | 原分支保留，追加一条同起点的分支 | 重新发请求 | 节点里的退款、发消息会再执行一次 |
| 分叉 | 从指定检查点长出新分支，原分支不动 | 重新发请求 | 同上，而且金额/参数可能不同 |
| 新 `thread_id` | 全新一条，不继承旧 thread 的检查点 | 从空状态开始 | 共享业务库里旧 thread 的副作用仍会影响它 |

时间回溯适合调试和“如果当时改成 500 会怎样”；不要用它撤销已经发生的副作用。退款已经出去，重放到退款前再跑一次，会再调用一次退款接口，本章的 `Store` 会按剩余金额拒绝，真实支付网关不一定，所以外部副作用仍要幂等。

## 25.5 持久化检查点：SqliteSaver 和进程重启

`InMemorySaver` 的检查点在进程内存里。换成 `SqliteSaver`，检查点写进文件，新进程打开同一个文件、同一个 `thread_id` 就能接着跑。

```python
from langgraph.checkpoint.sqlite import SqliteSaver

with SqliteSaver.from_conn_string("state.db") as saver:
    graph = builder.compile(checkpointer=saver)
```

`state.db` 存在就直接用；同一个 `thread_id` 加同一个 db，新进程 `Command(resume=...)` 能恢复。示例让 `main.py` 起两个子进程：phase 1 跑到中断后退出，phase 2 打开同一个 `state.db` 完成。

示例的两个进程各自 `Store()`，业务库不共享；检查点共享，业务数据不共享。真实系统要把两者都放到持久存储，并让退款带幂等键。

{{#fig ch25/sqlite_restart}}

`SqliteSaver` 是单机同步实现，适合本地和小规模使用；生产常用 Postgres 或 Agent Server。`SqliteSaver.from_conn_string` 是上下文管理器，退出时关闭连接。

文件可以直接复制备份，但复制时最好停写。多个进程同时写同一个 thread 需要自己加锁或排队，SQLite 的文件锁不会替你解决业务顺序。Agent Server 会自动处理检查点，不需要自己编译时传 saver。

检查点会随对话增长，一个 20 轮的客服会话，每轮又可能有模型、工具、模型几个超步，检查点数量和体积都不小。生产要设保留策略或定期清理，常见做法有三种（本节末尾演示按 thread 删除）：

- 按 thread 删除：一条会话结束、过了审计期就整条删。
- 按时间删除：只留最近 30 天的检查点，适合调试。
- 只保留最近 N 个：控制单条 thread 的长度，旧步骤不再可回溯。

检查点也不是长期记忆，跨 thread 的顾客档案用 `Store`（第 26 章）。

```python
with SqliteSaver.from_conn_string("state.db") as saver:
    saver.delete_thread("T06-A")      # 删除这条 thread 的全部检查点
```

删之前先确认审计要求：原始事件日志（第 22 章）和检查点解决的不是同一件事，日志可能要留得更久。

`SqliteSaver` 只保存图 state 和待执行的写入。节点里已经发生的外部副作用不在事务里：phase 2 如果退了款、还没写下完成检查点就崩，重跑会再退一次。退款接口要有幂等键（第 23 章），不能把“检查点恢复”当成“副作用只发生一次”的保证。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `InMemorySaver()` / `MemorySaver()` | 内存检查点 | 进程退出就没了；两者是同一个类 |
| `SqliteSaver.from_conn_string("state.db")` | 文件检查点 | 单机同步；多进程写同一 thread 要排队 |
| `config={"configurable": {"thread_id": ...}}` | 选 thread | 必须带；新 id 是空状态 |
| `get_state(config)` | 最新 `StateSnapshot` | 看 `values`、`next`、`config`、`metadata`、`tasks` |
| `get_state_history(config)` | 全部检查点 | 时间逆序，最新的在前 |
| `update_state(config, values, as_node=...)` | 追加一个检查点 | 不回滚；`as_node` 决定从哪个后继继续 |
| `interrupt(payload)` | 节点内暂停 | payload 要能 JSON 序列化；恢复时节点从头跑 |
| `Command(resume=value)` | 恢复中断 | 没有 checkpointer 抛 `RuntimeError` |
| `interrupt_before=["tools"]` | 静态断点 | 只能停在节点边界，条件审批用 `interrupt()` |
| `invoke(None, snapshot.config)` | 重放 | 选 `next` 非空的检查点；会重跑模型和副作用 |
| `update_state(snapshot.config, values, as_node=...)` | 分叉的起点 | 原分支保留；分叉后用 `invoke(None, fork_config)` |
| `RemoveMessage(id=...)` | 删除一条消息 | 只对 `add_messages` 的 channel 有效 |

## 思考题

1. 预测：`25_2_no_checkpointer_fail.py` 如果先 `invoke` 两次再 `Command(resume=...)`，第二次会不会也返回 `__interrupt__`？为什么？

   <details><summary>提示</summary>没有检查点时，每次 `invoke` 都从入口重新执行；`approve` 每次都会再调用一次 `interrupt()`。示例的输出已经跑过这条路径。</details>

2. 找错：某个节点在 `interrupt()` 之前就调用了 `store.refund`，恢复时会发生什么？怎么改？

   <details><summary>提示</summary>节点恢复时从头执行，`interrupt()` 之前的退款会再执行一次。把退款移到 `interrupt()` 之后，或把它拆到单独的节点，并给退款加幂等键。</details>

3. 权衡：680 元退款用“中断等主管”还是“直接拒绝并由 `execute` 提交主管”，从顾客体验和审计各说一条。

   <details><summary>提示</summary>中断等主管能保留“批准后自动执行”的体验，但顾客要等；直接拒绝由 `execute` 提交主管，回复更快，但退款要再走一次人工流程。审计上，中断的 payload 和 resume 值都在检查点里，后者要靠 `actions` 和事件日志补齐。</details>

4. 估算：一个 20 轮的客服会话会产生多少个检查点，`SqliteSaver` 里大概占多少空间？

   <details><summary>提示</summary>按每轮 3–4 个超步估算，约 60–80 个检查点；每个检查点保存当时的 state，消息列表越长，后面的检查点越大。用 `get_state_history` 数条数，用 `state.db` 的文件大小估上限。</details>
