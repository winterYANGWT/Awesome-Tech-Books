T13 的顾客要退 680 元的典藏版。订单 A1680 已签收，三卷装订脱落，签收 19 天，还在质量问题的 60 天内，但金额超过 500 元。

## 20.1 什么时候需要人：金额、不可逆、失败阈值

OpenAI 在 2025 年的实践指南里把人工介入的触发条件分成两类：失败阈值和高风险动作。前者是重试次数太多、连续几轮没听懂顾客；后者是敏感、不可逆、金额大，指南举的例子是取消订单、大额退款、付款。

书店把“大额”定成单笔超过 500 元；改收货地址按 `shipping.md` 只在发货前可改，本书把它当中风险的执行前检查；投诉升级是本书客服场景的约定。

`shop` 把退款上限写成 `REFUND_LIMIT = 500.0`。`Store.refund` 在 `amount > 500` 且没有 `approved_by` 时抛 `ShopError`，消息是“单笔退款超过 500 元需要主管批准，请改为提交主管审批，不要直接退款”。`update_address` 只允许“待发货”的订单，已发货的订单在数据层就改不了。

| 触发线 | 例子 | 本章的对象 |
|---|---|---|
| 高风险：金额 | 单笔退款超过 500 元 | A1680，680 元 |
| 高风险：不可逆 | 已批准的退款、对外发消息 | 20.3 的已批准退款 |
| 中风险：可逆 | 改地址：待发货可改，已发货只能转寄或拒收 | A1679 改地址 |
| 失败阈值 | 重试太多、连续几轮没听懂 | 本章没有单独的失败计数示例；20.5 只演示拒绝后改方案 |

## 20.2 approve 回调：同步审批的契约

`harness.run(..., approve=fn)` 只对 `tool.risky` 调用 `fn(tool, args)`：返回 `True` 放行，返回字符串则写进 `role: tool` 的 `错误：这个操作没有被批准（…）`。`approve` 只能返回布尔或理由，不能改参数。

要改金额或地址，有两条路：让模型看到理由后重新生成调用，或者用带 `approval_id` 的工具。本章用后者：`request_approval(order_id, amount, reason)` 生成批准单和 `approval_id`；`issue_refund_approved(..., approval_id)` 是 `risky` 工具，`approve` 回调只校验批准单和参数是否一致，不再问人。

`shop.tools.issue_refund` 没有 `approved_by` 参数。示例另写 `issue_refund_approved`，内部调用 `store.refund(..., approved_by=...)`，并把 `approval_id`、订单、金额、批准人写进 `actions.detail`。审批单存在业务库的 `approvals` 表里，`shop` 的 schema 不动。

> `request_approval` 同时在 `actions` 里写一条 `escalate`，工单系统不用读 `approvals` 表也知道已经转主管。

## 20.3 暂停、持久化、恢复

同步 `approve` 在进程里等。进程一退出，等待中的退款就丢了。真实系统要把待批准的动作写下来，让进程可以退出，之后从同一处恢复。

| 字段 | 作用 |
|---|---|
| `request_id` | 批准单号；审批这一侧靠它去重（和 [23.4 节](ch23.md) 执行退款时的幂等键不是一回事） |
| `conversation_id` | 这段对话的标识 |
| `tool` | 待执行的工具名 |
| `args` | 工具参数，恢复时原样使用 |
| `messages` | 到 assistant 的 `tool_calls` 为止的消息 |
| `tool_call_id` | 恢复时写 `role: tool` 要配的 id |
| `created_at` / `expires_at` | 什么时候创建、什么时候过期 |
| `status` | `pending` / `approved` / `rejected` / `expired` |

`PAUSED` 之后 `ask` 已经退出，`resume` 是另一个进程。它先查批准单状态，再查 `actions.detail.approval_id` 有没有这个批准单号，然后才执行退款。工具结果作为 `role: tool` 追加到原来的消息后面，再调 `run(messages)` 让模型写最终回答。

恢复时最容易犯的错是直接重新调用 `run(messages)`。直接重放不会原样退两次：`issue_refund(680)` 会再撞一次 500 元上限，同一个批准单的 `issue_refund_approved` 会被 `actions` 查重跳过，换订单或金额则过不了批准单的参数校验。

## 20.5 拒绝之后：把理由交回模型

拒绝不是终点。理由作为 `role: tool` 的错误文字回到模型，模型可以改参数、换工具、向顾客解释，或者转主管。拒绝和工具失败走同一条路：作为结果交回模型，程序不抛异常。

- 只改审批卡上的显示，`actions` 里仍然是旧值。

## 20.6 审批的工程细节：超时、批量、审计

`expires_at` 到点后，不能再批准，也不能执行。示例的 `decide` 在 `at > expires_at` 时把单写成 `expired`，`execute_approved_refund` 也会拒绝过期单；没有定时任务，直接查 `approvals` 时状态可能还是 `approved` 或 `pending`，要自动转态得加定时任务或在查询时惰性更新，不能让请求永远挂着。

同一顾客的多张订单可以合并成一张审批卡，但每笔退款仍要单独记录 `order_id` 和金额。合并只减少审批人的点击次数，不减少审计记录。

审计查两张表：`actions` 记录实际做了什么，`approvals` 记录谁批的、什么时候批的、理由是什么。`actions.detail.approval_id` 等于 `approvals.request_id`，审计按它对上。

| 暂停点 | 状态存在哪 | 怎么恢复 | 能否改参数 |
|---|---|---|---|
| 本机同步 `approve` | 进程内存 | 同一进程继续 | 不能，只能返回 `True` 或理由 |
| 本机 `pending.json` | 文件 | `resume` 子进程读文件 | 能，改批准单或重新生成调用 |
| LangGraph `compile(interrupt_before=["tools"])` | checkpointer | `graph.invoke(None, config)` | 能，`update_state(..., as_node=...)` |
| LangGraph `interrupt()` + `Command(resume=...)` | checkpointer | 用同一个 `thread_id` 再 `invoke` | 能，`Command(resume=...)` 带修改后的值 |
| Agents SDK 0.24 `needs_approval` | `RunState` | `result.to_state()` 后 `Runner.run(agent, state)` | 不能直接改；`reject(..., rejection_message=...)` 让模型重来 |

LangGraph 的静态中断在 1.2 里仍然可用：`compile(interrupt_before=["tools"])` 把图停在工具节点前，`graph.get_state(config).next` 看下一步，`graph.invoke(None, config)` 从检查点继续。当前文档把这条路径放在调试一节，HITL 的主路径是节点里的 `interrupt()` 加 `Command(resume=...)`。

Agents SDK 0.24 的写法是 `function_tool(needs_approval=True)`，`result = await Runner.run(agent, ...)` 在工具前停下来，待批准项在 `result.interruptions`；先 `state = result.to_state()`，再 `state.approve(result.interruptions[0])` 或 `state.reject(..., rejection_message=...)`，最后 `result = await Runner.run(agent, state)` 从同一个状态继续。

> **旧资料提示**：OpenAI 2025-04 的指南只讲“人工介入的触发条件”，没有给出暂停/恢复接口；Agents SDK 0.24 的 `needs_approval` 和 `RunState` 是后来的做法。本章按 0.24 写。

> **旧资料提示**：LangChain Academy 2024 年录制的 module-3 用 `compile(interrupt_before=["tools"])`、`graph.stream(None, thread)` 和 `update_state`。LangGraph 1.2 仍支持，但当前文档推荐在节点里用 `interrupt()` 加 `Command(resume=...)`。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `run(..., approve=fn)` | `risky` 工具执行前询问 | 只对 `tool.risky` 调用；返回 `True` 或拒绝理由字符串 |
| `request_approval(order_id, amount, reason)` | 生成批准单 | 只生成记录，不退款；返回 `approval_id` |
| `issue_refund_approved(..., approval_id)` | 凭批准单退款 | 再查状态、参数、过期和 `actions` 幂等 |
| `approvals` 表 | 存批准单 | `request_id`、`approver`、`decision`、`reason`、`decided_at`、`executed_at` |
| `pending.json` | 待批准动作 | 进程退出后恢复用；恢复时不要重新问模型 |
| 思考模式 + `tool_choice` | 固定某次工具调用 | DeepSeek 思考模式不接受指定函数的 `tool_choice`，示例用 `extra_body` 关闭思考 |

| 框架 | 暂停与恢复 | 改状态 |
|---|---|---|
| 本机 `harness` | `approve` 回调，进程内等待 | 不能改参数 |
| 本机 `pending.json` | 写文件、退出、`resume` | 改批准单或重新生成调用 |
| LangGraph | `interrupt_before` + `invoke(None, config)` 或 `stream(None, config)`；`interrupt()` + `Command(resume=...)` | `update_state(..., as_node=...)` |
| Agents SDK 0.24 | `needs_approval=True` + `RunState` | `approve` / `reject`，拒绝理由回给模型 |

## 思考题

1. 预测：如果 `approve` 在工具执行后才返回拒绝，`actions` 里会不会已经有一条退款？用 20.2 的路径说明“先审批、后执行”的顺序。

<details><summary>提示</summary>

`harness.run` 先算 `verdict`，再决定要不要 `toolbox.call`。20.2 是手写的同一个顺序：先 `gate(None, call)`，再 `box.call(...)`。把顺序反过来，退款已经写进 `actions`，拒绝只是一句事后的话。

</details>

2. 找错：恢复时直接重新调用 `run(messages)`，模型又生成了一次 `issue_refund(680)`。指出这会导致什么，并给出两种修法。

<details><summary>提示</summary>

直接重放不会原样退两次：`issue_refund(680)` 再撞上限，同一个批准单的 `issue_refund_approved` 被 `actions` 查重跳过，换订单或金额过不了批准单校验。风险在模型不执行却回答“已退款”，以及 `store.refund` 和 `_tag_last_action` 之间崩溃留下的无 `approval_id` 记录。修法一：照 `pending.json` 直接执行已批准的工具，把结果作为 `role: tool` 追加。修法二：执行前按 `approval_id` 查 `actions`，已执行就跳过。

</details>

3. 权衡：所有退款都人工审批，还是只审批超过 500 元的退款？用审批量、误操作率和顾客等待时间三个指标说明取舍。

<details><summary>提示</summary>

全量审批把误操作压到最低，但审批量大、等待时间长；只审大额把大部分退款留给自动路径，要接受小额误退的风险。可以用抽样复核补上中间地带。

</details>

4. 迁移：把“改地址”也做成审批，批准单里要多哪些字段？已发货订单的“转寄”应该由谁执行？

<details><summary>提示</summary>

多旧地址、新地址、订单状态、是否已发货、快递公司和转寄选项。已发货的转寄通常由快递或仓库执行，agent 只能提交申请并记录结果。

</details>
