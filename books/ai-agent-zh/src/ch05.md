# 第 5 章 提示链和路由

T06 的原话是：“收到的《大运河两千年》中间缺了二十多页，订单号 A1659，怎么处理？”[第 1 章](ch01.md)把这句话直接发给模型，它回“已为您办理全额退款，退款金额为 68.00 元”。

订单实付 82.0 元，`store.actions()` 是空的。失败不在文笔，而在模型没有拿到订单事实。把同一件事拆成几次调用，每一步的输入输出都能单独看，闸门能在发出去之前拦住。

## 5.1 提示链：把一件事拆成几次

{{#fig ch05/chain_gate}}

链的每一步只做一件事，输入是上一步的输出加必要的事实。T06 的链是四步：取事实、摘要、草稿、闸门。取事实只查本地数据，摘要和草稿各调一次模型，闸门是代码。

| 步骤 | 谁来做 | 输出契约 | 失败时 |
|---|---|---|---|
| 取事实 | `get_order` + `search_policies` | 订单字段、政策条款标题 | 订单号不存在就让顾客补 |
| 摘要 | 模型，JSON 模式 | `order_id`、`amount`、`policy_sections`、`open_questions` | 缺字段由闸门拦下，不可重试 |
| 草稿 | 模型，纯文本 | 给顾客的回复 | 可重试的问题带着错误重写 |
| 闸门 | 代码 | `pass`、`issues` | 不可重试就转人工 |

链的 token 是各步之和，延迟也是各步之和。它用“多一次调用”换“每次更简单、更可控”。

- Anthropic 在《Building effective agents》里把这种做法叫 prompt chaining，并建议在中间步骤加程序化检查；适合步骤能预先拆开的任务，不适合需要模型自己决定下一步查什么的探索。
- 中间结果要落在变量里，不要靠模型“记住”。
- 例子里的草稿只收到摘要 JSON 和顾客原话，没有把前两步的整段历史拼进去。
- 每一步可以单独重跑，失败也能定位到步。
- 摘要缺 `amount` 时，草稿仍会先写出来；闸门拿摘要一比就发现缺字段，标为不可重试，直接转人工，不让它带着错误重写。

闸门也会把业务分支当成草稿错误。T13 的 680 元退款本来就应该转主管，如果把它当成“草稿错误”反复重写，只会浪费两次调用；这类业务分支要在生成前就分流，5.6 的流水线会这样做。

本章的路由表按这个原则来：复杂类别留在 `deepseek-v4-pro`，简单类别换成 `deepseek-flash`。5.5 的对照也从 pro 开始，再用 flash 试降级。

- 降级要有回退：小模型返回空、格式错、或闸门连续失败时，升级到强模型重跑一次，不要静默返回坏结果。
- 对照实验只换模型，不换提示和工具，否则无法判断差异来自模型还是提示。
- 成本要按“路由 × 模型”统计，不要只看全章平均。
- 高价值退款单用强模型可能更便宜，因为少了重试和人工。
- 低风险的物流查询用强模型则是浪费。

共享变量就是 `facts` 字典：

- `text`：工单原话；退货退款分支另加 `decision`，放代码算出的结论。

错误传播要一层层写清楚，任何一步都不要把异常吞掉。

- 分类失败 → 兜底话术。
- 取事实失败 → 让顾客补信息。
- 草稿失败 → 重写不超过 2 次。
- 闸门失败 → 转人工。

这套流水线仍然是 workflow：路径由代码决定，模型只在每一步内部做判断。[第 1 章](ch01.md)用 T06 演示了单次调用、固定流程和 agent 循环，这一章用 workflow 重做同一批工单，作为结构对照。不是谁取代谁，也不要因为加了路由就叫它 agent。

| | 普通 Python 函数 | LangGraph `StateGraph` + `add_conditional_edges` | LangChain `create_agent` |
|---|---|---|---|
| 控制流写在哪 | `if` / `for` | 节点和边；条件边是一个返回下一节点名的函数 | 模型决定调不调工具，运行时负责循环 |
| 状态怎么传 | 局部变量、dict | 带 reducer 的 state，可加检查点 | 消息列表，可加检查点 |
| 路由条件 | 代码里的 `if` | 条件边函数读 state | 模型选工具，`tools_condition` 看有没有工具调用 |
| 调试方式 | 打印、日志 | 图的结构、每步 state、检查点 | 消息轨迹、每轮工具调用 |
| 适合的规模 | 几步固定流程 | 多节点、多分支、要恢复 | 开放式、工具多、路径不固定 |

LangChain Academy 的 router 课用 `ToolNode` + `tools_condition` 做“模型决定调不调工具”，那是 agent 内部的工具循环；本章的路由是“代码按类别分派”，两者不要混。

> **旧资料提示**：LangChain Academy 的代码用 `gpt-4o`，本书用 `deepseek-flash`，对照用 `deepseek-v4-pro`；LangGraph 旧版本里常见的 `create_react_agent` 从 v1 起改用 `langchain.agents.create_agent`，[第 24 章](ch24.md)重写。OpenAI 2025 年的指南建议用 o1/o3-mini 从文档生成指令，2026-11 用当前强模型即可；Anthropic 2024 年的文章用 Haiku 4.5 / Sonnet 4.5 举例，本书只说小模型和强模型，不写型号和排名。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| 链的四步 | 取事实 → 摘要 → 草稿 → 闸门 | 取事实和闸门不调模型 |
| 摘要契约 | `order_id`、`amount`、`policy_sections`、`open_questions` | `amount` 是数字；缺了由闸门拦下，不可重试 |
| 草稿契约 | 纯文本 | 只带摘要和顾客原话，不带整段历史 |
| 闸门输出 | `{"pass": bool, "issues": [...]}` | 解析不出就按失败处理 |
| 四类检查 | 字段 / 金额 / 政策 / 措辞 | 金额查剩余可退，政策查 500 元上限 |
| 重试上限 | 2 次 | 草稿缺订单号可重试；摘要缺字段、超限、政策不允许不重试 |
| `submit_route` | 强制分类工具 | 7 个枚举；只给工单文本，不给业务工具 |
| 路由表 | `handler`、`prompt`、`tools`、`model` | 模型名写表里；本章只用 `prompt`/`model`，`handler`/`tools` 是计划配置 |
| 模型分工 | `deepseek-flash` / `deepseek-v4-pro` | 简单类别 flash，复杂类别 pro；建基线时都用 pro |
| 共享事实 | `facts` 的 `order`、`policies`、`books`、`text` | `TODAY` 用来算签收天数；不塞无法检查的语气要求 |
| 结构化日志 | `step`、`model`、`in`、`out`、`key` | 生产里加 `duration_ms`、`gate` |
| `# output: varies` | 回放不逐字比对 | 只用于输出里有实际耗时的示例；本章示例不打印耗时，所以不用 |

订单号格式对，只说明“引用了某张订单”，不代表金额没超限。缺的是“金额与剩余可退金额比较”和“超过 500 元必须有主管”这两条政策检查。措辞检查只查固定禁词，“直接退款”这类语义承诺不在词表里，不能靠它兜底。

</details>

2. 预测：把 T24“寄到广州用的是哪家快递？能换顺路吗？”放进路由，分类器最可能分到哪一类，为什么？

<details><summary>提示</summary>

句子里有“快递”“寄到”，容易被拉到物流查询；但它问的是“用哪家、能不能换”，是规则而不是某张订单的轨迹。分类器的类别说明和提示写法都会影响结果，这次运行分到了政策咨询，换一版提示可能就变。

</details>

3. 权衡：30 张工单用“一个大提示”还是“先路由再处理”？从 token、可维护性、分类错误代价各说一条。

<details><summary>提示</summary>

token：本章 B 是 A 的 1.76 倍，短工单上路由不省；可维护性：每类的提示、工具、模型可以单独改；分类错误代价：错一次会把整条链带错，但终态不一定错，要同时看分类、终态和关键词三个指标。

</details>

4. 迁移：把“退款链”的闸门换成“改地址链”的闸门，哪些检查可以复用，哪些必须新写？

<details><summary>提示</summary>

可复用订单号正则、字段齐全、措辞检查（词表里已经有“一定能改”）；必须新写“订单状态必须是待发货”、新地址是否为空或完整（本章没有格式和省份校验）、以及“已发货只能转寄或拒收”的政策分支。退款金额检查不再适用。

</details>
