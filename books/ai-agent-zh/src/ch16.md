# 第 16 章 Skills：按需加载的专业知识

退款规程的正文有 50 行，政策原文还有 25 行。放进系统提示就要每轮重发，不放进，模型把“教辅拆封不退”和“超过 500 元要主管批准”算错。新加的月度运营报告规程更糟：模型根本不知道它存在。

| 做法 | 结果 |
|---|---|
| 全塞进系统提示 | 每轮重发；改一处要重发全部 |
| 全不塞 | 模型不知道规程存在，金额算错 |
| 目录常驻、正文按需 | 目录很小，正文和资源用到才进来 |

## 16.1 一个目录就是一个 Skill：SKILL.md 和三层

{{#fig ch16/skill_layers}}

Skill 是一个目录，至少含 `SKILL.md`，还可以有 `scripts/`、`references/`、`assets/`。`SKILL.md` 由 YAML frontmatter 和 Markdown 正文组成，frontmatter 至少写 `name` 和 `description`。

| 字段 | 必填 | 约束 |
|---|---|---|
| `name` | 是 | 1–64 字符；小写字母、数字、连字符；不能以连字符开头或结尾，不能连续两个连字符；与目录名一致 |
| `description` | 是 | 1–1024 字符；写清“做什么 + 什么时候用” |
| `license` | 否 | 许可证名称或指向捆绑的许可证文件 |
| `compatibility` | 否 | ≤500 字符；运行环境要求 |
| `metadata` | 否 | 字符串键值对 |
| `allowed-tools` | 否 | 空格分隔的工具名；实验性字段 |

`name` 与目录名一致这条最容易被忽略：客户端按目录发现 Skill，按 `name` 建索引，两者对不上时，激活工具拿到的名字和文件路径会分叉。

三层渐进式披露是 Skill 的核心：目录只放 `name` 和 `description`，每个约 50–100 token，激活时读整份正文，建议小于 5000 token、正文小于 500 行，`scripts/`、`references/`、`assets/` 只在正文指向它们、任务又确实需要时读。

- Skill 负责“怎么做”的规程和资源。
- 连接外部系统、读实时数据仍然用工具或 MCP，边界在 16.7 节。

## 16.2 发现、目录和激活

{{#fig ch16/activate}}

发现位置有两个范围，每个范围两条路径：项目级 `<project>/.<client>/skills/`、`<project>/.agents/skills/`；用户级 `~/.<client>/skills/`、`~/.agents/skills/`。同名时项目级覆盖用户级，并打印一条警告，让用户知道有一个被遮住了。

解析 frontmatter 后，记录里至少存 `name`、`description`、`location`。正文可以现在读，也可以激活时从 `location` 读，相对路径以 Skill 目录为基准，这样脚本和参考文件不用写绝对路径。

目录可以放系统提示，也可以放激活工具的描述里。两种都能工作：

- 系统提示：更简单，所有客户端都能做。
- 工具描述：把“发现”和“激活”放在一起，目录跟着工具走。

激活也有两条路：模型用文件读取工具读 `SKILL.md`，或调用专用工具 `activate_skill(name)`。

`activate_skill` 的 `name` 参数用 enum 限定在有效 Skill 名里，防止模型编造一个不存在的名字。它返回正文（可以去掉 frontmatter）和捆绑文件列表，但不要预读这些文件，预读就把第三层又变成了第一层。

已经激活过的 Skill 不重复注入。客户端还要把 Skill 内容标记为受保护，压缩时不清掉；否则对话到一半，规程会被摘要掉，模型悄悄失去依据。

- 项目级 Skill 可能来自不可信的仓库，加载前做信任检查。
- 用户显式 `/skill-name` 激活可以作为补充。

## 16.4 脚本：确定性和省 token

算术、排序、解析、格式转换交给代码：确定、可重复、输出短。脚本的回报首先是确定性，省 token 要看任务；让模型在 token 里做多步算术，既慢又容易错。

适合交给脚本的活有几类：折扣和税费、部分退货的分摊、按金额排序、把 CSV 转成 JSON、检查日期是否超过 15/60 天。

脚本为 agent 设计，有几条硬要求：

- 不等待交互输入，所有参数走命令行或环境变量。
- `--help` 可读，写清参数、默认值和退出码。
- 错误说清期望值和可选值，不要只说“参数不对”。
- 数据走 stdout，诊断走 stderr，stdout 只放机器能读的格式。
- 重复执行安全，有副作用或危险操作时提供 `--dry-run`。

## 16.6 评估和优化触发描述

{{#fig ch16/trigger_eval}}

触发由 `description` 决定，不是由正文决定。描述要写“做什么 + 什么时候用 + 关键词”，不要只写“帮助处理退款”。

评测集有 20 条查询：10 条应该触发（退款、缺页、退货金额、超过 500、教辅拆封、部分退货等），10 条不应该触发（运费、发票、会员、推荐书、月报、越界请求等）。两版描述各跑 3 轮，共 120 次。

`16_6_trigger_eval.py` 的输出是两行 CSV：

```text
{{#include code/ch16/16_6_trigger_eval.out}}
```

A 版“帮助处理退款”该触发 10 条全中，但误触发 3 条，B 版具体描述该触发仍是 10 条，按 3 轮至少 2 轮的阈值，误触发降到 0。B 版也不是每轮都干净：运费和越界各有 1 轮触发，只是没到阈值。这个结果说明：在这个模型和这 20 条查询上，具体描述没有提高该触发数，改善的是边界，换成更弱的模型或更模糊的查询，该触发数可能也会变。

指标看两个：该触发时的触发率、不该触发时的误触发率。不要只看总数，这次 A 版误触发的是发票查询、改地址请求和一条越界指令。误触发一条发票查询只是多读一份无关正文，误触发一条越界指令却可能让模型按规程去处理一个本不该受理的退款。

优化描述要防过拟合：按约 60%/40% 把查询分成 train 和 validation，只用 train 的失败改描述，validation 只用来验收。这个示例为了对比两版，整集都跑了，真正迭代时按这个比例改和验。描述超过 1024 字符直接不合法，细节放正文，描述只留触发信号。

- 触发率阈值常用 0.5：3 轮里至少 2 轮触发，就算这条查询触发。
- 20 条查询的样本很小，差一条会让百分比跳 10 个点。
- 看具体哪条错，不要只看总数。

输出质量另有一套评估，和触发评测分开做：

- 每个用例写输入、期望输出或断言、评分标准。
- 每个用例多次运行，取通过率。
- 通过率高的用例也要人工看一遍，异常往往在“全过”的样本里。

一次输出好看，不能说明 Skill 稳定。

## 16.7 Skill 与 MCP、子 agent 的边界

{{#fig ch16/boundaries}}

Skill 是过程性知识（怎么做），MCP 是工具、资源、提示的协议（能做什么），子 agent 是隔离的上下文（谁来做）。三者可以组合，不要互相替代。

MCP 文档里的 `mcp-server-dev` 插件就是一组 Skill：`build-mcp-server` 做入口，`build-mcp-app` 加 UI，`build-mcpb` 打包本地 server，每个 Skill 带 `references/`，按需读。这组 Skill 先问“连接什么、谁用、动作面多大、要不要 UI、上游怎么认证”，再推荐远程 Streamable HTTP、MCP apps、MCPB 或本地 stdio。这是把设计决策写进 Skill 的例子，不是协议本身。

Skill 可以引用 MCP 工具，但 `allowed-tools` 仍是实验性字段。权限、OAuth、凭据由 MCP 客户端和服务端管（第 12、19 章），不要写进 `SKILL.md`。

- 安全上，只安装可信来源的 Skill。
- 审计捆绑脚本和外部链接。
- 项目级 Skill 要有信任门。
- Skill 里的指令同样可能被注入（第 19 章）。

选择很简单：固定规程用 Skill，外部数据和动作用 MCP，并行探索用子 agent，一次性小提示不值得建 Skill。

| 能力 | 放在哪 | 加载方式 | 权限 | 适用 |
|---|---|---|---|---|
| 系统提示 | 每次请求的 system 消息 | 每轮都在 | harness 控制 | 短、稳定、所有任务都要 |
| Skill | 目录里的 `SKILL.md` 和资源 | 目录常驻，正文激活时读，资源按需 | 文件读取或激活工具 | 长、按需、要版本化 |
| MCP 工具 | MCP server | 工具调用，JSON-RPC | OAuth、服务端授权 | 数据或动作在外部系统 |
| 子 agent | 独立的一次运行 | 主 agent 派任务，收回摘要 | 继承或过滤父上下文 | 并行探索、上下文隔离 |

| 接口 | 边界 |
|---|---|
| Agent Skills 规范 | 定义目录、`SKILL.md` frontmatter 和三层披露；客户端自己实现发现和激活，不是运行时协议 |
| LangChain 文档里的 `load_skill` 工具模式 | 自己用 `@tool` 写一个读 Skill 的函数，注册给 `create_agent`；接口由使用者的工具实现，不是跨客户端标准 |
| MCP 的 prompts | server 暴露提示模板，客户端用 `prompts/list` / `prompts/get` 取；用户选择，不是模型自己发现 |

三者的接口不同，解决的问题也不同。规范定义文件格式，LangChain 文档里的 `load_skill` 是读者自己写的工具，MCP prompts 是 server 给客户端的一份模板。把三者混在一起讲，容易把“怎么发现”和“怎么执行”混成同一件事。

> **旧资料提示**：2025 年的文章常把 Skill 写成 Claude 的专有功能。2025-12 起它成为开放标准，规范面向所有客户端。
>
> **旧资料提示**：也有文章说 `name`/`description` 必须预加载到系统提示。规范也允许把目录放进激活工具的描述，两种都能工作。
>
> **旧资料提示**：`description` 不是随便写。1–1024 字符，写清做什么和何时用，用触发评测优化，不靠感觉。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `SKILL.md` | YAML frontmatter + Markdown 正文 | 必填 `name`、`description` |
| `name` | Skill 的标识 | 1–64，小写字母/数字/连字符，匹配目录名 |
| `description` | 触发信号 | 1–1024，做什么 + 何时用 |
| 三层 token | 目录 50–100/Skill；正文 <5000；资源按需 | 正文建议 <500 行 |
| `activate_skill(name)` | 读正文和资源列表 | `name` 用 enum；不预读资源 |
| 发现路径 | `.agents/skills/`、客户端目录、用户目录 | 项目级覆盖用户级，打印警告 |
| 脚本 | 计算、排序、解析、格式转换 | `--help`、无交互、stdout 数据、stderr 诊断、明确退出码、危险操作 `--dry-run` |
| 触发评测 | 20 条查询、两版描述、3 轮 | 看该触发率和误触发率 |
| 安全 | 可信来源、审计脚本、项目信任门 | `allowed-tools` 实验性 |

几条规则每轮都发，但短；50 行正文按需读，但要求模型先发现它。触发面越窄，越适合 Skill。

</details>
