# 第 3 章 工具调用和 agent 循环：手写一个最小的 harness

模型返回了 `tool_calls`，程序却只打印 `message.content`：

```text
finish_reason=tool_calls
content=''
tool_calls=1 个   ← 程序没有读这个字段
```

下一轮请求里没有 `role: "tool"` 的结果，模型只好说“我没有收到查询结果”，或者 API 直接以 400 拒绝。这一章从工具定义写起，手写一个 harness（驱动模型循环、执行工具调用的那层程序），把工具执行、结果回填、错误处理和轮数上限都补上。

## 3.1 工具就是一段 JSON Schema

请求里的 `tools` 是一个数组，每一项形如 `{"type": "function", "function": {"name", "description", "parameters"}}`。`parameters` 是 JSON Schema 对象，根上至少写 `type: "object"`，`properties` 和 `required` 按需要写，没参数的工具可以省略 `parameters`。模型只看得见这段 schema，看不见 Python 函数体。

{{#fig ch03/schema_to_model}}

`harness.tool` 从函数签名生成这段 JSON。参数说明写成 `Annotated[str, "订单号，例如 A1234"]` 才会进 `description`。

`get_order` 的 `required` 里只有 `order_id`；`issue_refund` 的 `amount` 是 `number` 而不是 `string`，三个参数都必填。`issue_refund.description` 里那句“单笔超过 500 元不能直接退”不是装饰：`shop.tools` 里有一行断言，退款规则改了而描述没改，构造工具箱（调用 `support_tools()`）时就会失败。

`description` 是模型选工具的主要依据，要写清“做什么、什么时候用、有什么限制”。Anthropic 在讲工具设计的附录里建议把工具定义当成给新同事写的 docstring，还要替模型想好边界情况；这也是后面第 8、9 章的主题。

两种常见格式的字段对应关系：

| 项目 | OpenAI Chat Completions | Anthropic Messages |
|---|---|---|
| 工具数组 | `tools` | `tools` |
| 一项的形状 | `{"type": "function", "function": {...}}` | `{"name", "description", "input_schema"}` |
| 参数 schema | `function.parameters` | `input_schema` |
| 模型返回 | `tool_calls[]`，`function.arguments` 是 JSON 字符串 | `tool_use` 内容块，`input` 是对象 |
| 结果回填 | `role: "tool"` + `tool_call_id` | `user` 消息里的 `tool_result` + `tool_use_id` |

`parameters` 里的 `type` 决定模型怎么填：`string` 是文本，`number` 是数字（整数或小数），`integer` 只收整数，`boolean` 是开关，`array` 要再写 `items`。模型看不到 Python 的默认值，只看到 `required` 名单。

`tool_choice` 取 `none`、`auto`（有工具时的默认）、`required`，或者 `{"type": "function", "function": {"name": "..."}}`。关掉思考后，四种写法在 DeepSeek 上实测都被接受（2026-11）。强制某个工具时用最后一种，第 4 章用它做结构化输出。

`finish_reason` 是 `tool_calls`，`content` 是空字符串，模型只给了要调用的函数和参数。这里能强制它选 `get_order`，是因为 `tool_choice` 点名了这个函数；平时留 `auto`，让模型自己决定。

按用途分，工具常见三类：data（查数据，本章的 `get_order`、`search_policies`）、action（改数据或发消息，`issue_refund`、`update_address`）、orchestration（把另一个 agent 当工具，第 17 章）。`harness.tool` 只支持 `str/int/float/bool`、`Literal`、`list`、`Optional` 和 `Annotated`；复杂嵌套对象要自己写 schema，或者把参数拆成几个简单字段。

第一次响应没有答案，只有 `get_order` 和参数，工具结果是一段 JSON 文本。第二次请求把 assistant 的 `tool_calls`、`reasoning_content` 和 `role: "tool"` 的结果一起发回去，模型才写出“迅达快递”。答案里的快递公司来自工具结果，不是模型编的。

最后那句“省内 1～3 天”是模型的常识估计，工具里没有这个字段。

回填有几条硬规则：

- 思考模式下，之前每一轮 assistant 消息的 `reasoning_content` 都要原样放回：带 `tools` 的请求必须放，否则 DeepSeek 可能返回 400；不带 `tools` 时放回也会被忽略。这是 DeepSeek 的字段，OpenAI 的 Chat Completions 没有。
- `tool_call_id` 必须和 assistant 消息里的 `id` 一一对应，缺一条或写错都会被 API 以 400 拒绝。顺序错了也可能被拒绝，最稳的做法是按原顺序回填。
- 只发 `role: "tool"` 的结果、不发 assistant 的 `tool_calls`，同样会 400；两者要成对出现。
- 本章的 `Toolbox.call` 统一回填字符串：dict/list 用 `json.dumps(..., ensure_ascii=False)` 转成 JSON 文本，模型看到的是文本，不是 Python 对象。OpenAI 的 `tool` 消息 `content` 类型也接受文本片段数组；DeepSeek 的兼容层本书没有实测。

`tool_calls` 的顺序就是模型给调用排的顺序。一轮里有多个调用时，少回填一个，下一轮历史就不完整。

```python
{{#include code/ch03/3_3_loop.py}}
```

这次运行的输出：

```text
{{#include code/ch03/3_3_loop.out}}
```

这一次模型在第 1 轮同时要了 `get_order` 和 `search_policies`，第 2 轮退款，第 3 轮写答案，所以 `turns=3`、`stop=answer`。循环不关心一轮里有几个调用，只关心还有没有调用；轮次和调用数不是一回事。

`turns` 是调模型的次数，`steps` 是执行过的工具步骤列表，`len(steps)` 才是个数，两者不要混，调试时两个都打印。

`Result.stop` 只有两个值，另有一类异常退出：

- `answer`：模型不再调工具，`content` 就是答案。
- `max_turns`：轮数用完，`answer` 可能是 `None`。本书的 `Result.stop` 用这两个值。
- 异常：不可恢复的错误直接抛出，不会写进 `Result.stop`；工具自己的错误属于可恢复，见 3.5。

`max_turns` 默认 10 是本书的选择，不是 API 的默认值。本章这几张工单 1–3 轮就给出答案，第 21 章 30 张工单平均 2.3 轮、最多 5 轮，超过上限通常说明模型在打转，或者工具在反复报错。把上限压到 1，就能看到另一个出口：

```python
{{#include code/ch03/3_3_loop_fail.py}}
```

这次运行的输出：

```text
{{#include code/ch03/3_3_loop_fail.out}}
```

第 1 轮的两个工具都执行了，结果也回填了，但轮数已经用完，程序拿不到答案，以 1 退出。生产代码不能把这个状态当成成功；要么把 `answer=None` 交给人工，要么在上限内重试一次。

每轮把 `usage` 累加，记录 `turns` 和 `steps`（每步 `turn/name/arguments/result`）。调试时打印“第 N 轮 → 工具(参数) ← 结果前 40 字”就够了，不要打印完整 JSON。

循环里不要写 `except Exception: pass`，工具异常要变成给模型看的错误文字。未知工具、坏 JSON、缺必填/多传参数要在 `Toolbox.call` 里统一处理。

一轮返回 N 个调用还会放大 token：下一轮请求要带 N 条工具结果，长结果要先截断（第 9 章）。

五段文字分别做五件事：

- 说清 JSON 哪里坏了。
- 带上 `parameters` 的 JSON，模型能照着重写。
- `shop.tools.guard` 把 `ShopError` 包成 `ToolError`，直接告诉模型“改为提交主管审批”。
- 第 5 段是示例临时造的工具，抛 `RuntimeError`；`Toolbox.call` 带上类型名，模型知道是工具内部坏了，不是参数问题。

`Toolbox.call` 不校验 JSON Schema 的类型：`order_id` 给一个整数 `123`，不会触发 `TypeError`，会直接进函数，`get_order` 只返回“订单 123 不存在”。示例最后一行就是这种情况；类型不对要在工具入口自己检查，或者换一个会校验 schema 的框架。

`ToolError` 的消息是写给模型看的：说清“错在哪、该怎么改”，不要只写“失败”。工具报错不是循环终止；错误字符串回填后，模型通常会在下一轮改用别的参数或别的工具。

```python
{{#include code/ch03/3_5_recover.py}}
```

这次运行的输出：

```text
{{#include code/ch03/3_5_recover.out}}
```

这一次第 2 轮模型直接调 `issue_refund` 退 680 元，工具返回“超过 500 元需要主管批准”；第 3 轮它改调 `escalate_to_supervisor`，最终回答里告诉顾客已提交主管。错误文字成了下一轮的输入，而不是程序的崩溃。

不要把 Python traceback 直接回填，模型读不懂，也会暴露内部路径。Python 的 `TypeError` 原文带着内部函数名（形如 `support_tools.<locals>.get_order()`），`Toolbox.call` 把它换成了工具名，所以示例第 3 段里模型看到的是 `get_order()`。

更稳的做法是在工具入口先按 schema 校验参数，只回填 schema 和一句人话。连续两轮同一错误，应该停下来转人工，而不是无限重试。

`before_model(messages)` 在每次请求前决定实际发送的消息（第 13、15 章做裁剪和压缩）。`approve(tool, args)` 在执行 `risky=True` 的工具前调用，返回 `True` 放行，返回字符串则作为拒绝理由交给模型（第 19、20 章）。`risky=True` 只做标记，不自动审批。

`Toolbox.schemas()` 给请求用，`Toolbox.call` 给执行用，两个入口不要混。同一件事在三种写法里的位置如下。

| 项目 | 本章 harness | LangGraph 的 `assistant` + `ToolNode` | Agents SDK 的 `Runner.run` |
|---|---|---|---|
| 谁决定下一步 | 模型返回的 `tool_calls` | 模型节点返回的 `tool_calls`，`tools_condition` 路由 | Runner 循环里的模型输出 |
| 停止条件 | `answer` 或 `max_turns` | 没有工具调用，或图的递归上限 | 最终输出、没有工具调用、`max_turns` |
| 消息怎么存 | 调用方传进来的 `messages` 列表，就地追加 | 图状态里的 `messages`，可接检查点 | `RunResult` 的输入输出列表，或 session |
| 工具结果怎么回填 | `role: "tool"` + `tool_call_id` | `ToolNode` 追加 `ToolMessage` | Runner 追加 `function_call_output` |
| 代码量 | 约 220 行，无框架 | 几十行，加 LangGraph | 十几行，加 SDK |

细节分别指向[第 24 章](ch24.md)和[第 27 章](ch27.md)。`src/code/harness/` 就是本章这套循环的成品，第 4–23 章直接 `from harness import run, Toolbox, tool`，第 24–27 章会用 LangGraph 和 Agents SDK 把同一循环重写一遍做对照。它只有 200 多行，没有魔法。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `{"type": "function", "function": {...}}` | 请求里的一个工具 | `parameters` 根上至少 `type: "object"`；`properties`/`required` 按需 |
| `Annotated[str, "说明"]` | 参数说明 | 会变成 `description`；默认值决定是否进 `required` |
| `tool_choice` | 控制选不选工具 | `none`/`auto`/`required`/指定函数；DeepSeek 思考模式不支持 `required` 和指定函数 |
| `tool_calls[]` | 模型要调用的工具 | `function.arguments` 是 JSON 字符串 |
| `role: "tool"` + `tool_call_id` | 回填工具结果 | 每个 `id` 一条，按原顺序；缺一条就 400 |
| `max_turns` | 轮数上限 | 默认 10 是本书的选择；用完时 `answer` 可能为 `None` |
| `Result.stop/turns/usage/steps` | 循环的结果 | `stop` 只有 `answer` 和 `max_turns` |
| `Toolbox.call` 的错误处理 | 把异常变成文字 | 未知工具、坏 JSON、缺参/多传、内部异常；业务规则由 `guard` 包成 `ToolError` |
| `ToolError` | 工具主动报告的错误 | 消息写给模型看：错在哪、怎么改 |
| `risky=True` | 标记有副作用的工具 | 只做标记，审批要靠 `approve` |
| `before_model` / `approve` | 请求前改消息 / 执行前审批 | 第 13、15、19、20 章用 |

   错误会落在 `tool_calls` 和 `tool_call_id` 上：assistant 的每个 `id` 都要有一条对应的 tool 消息。`function.name` 是 `get_order`，不是 `call_...`，对不上。

   </details>

2. **预测**：在 3.3 的提示下（“缺了二十多页，订单号 A1659，怎么处理？”），模型第一轮会调哪个工具？如果把问题换成“A1659 能退吗”，它可能怎么调？

   <details><summary>提示</summary>

   问题里同时有“哪张订单”和“怎么处理”两件事，模型可能先查订单，也可能同时查订单和政策；3.3 录到了一次两个都调。3.4 的提示明确写了“请同时查”，不能拿来证明模型会自发并行；它的两组统计只说明提示会影响概率。

   </details>

3. **权衡**：并行调用三个查询和串行调用三次，token、延迟、失败处理各有什么代价？

   <details><summary>提示</summary>

   并行省模型往返，但下一轮要带三条结果，token 更集中；串行每次只带一条，历史更长。并行时一个失败不影响其余，但要为失败项占位；有副作用的调用不能并行。

   </details>

4. **迁移**：把 `get_order` 的 `order_id` 从 `string` 改成 `Literal["A1659", "A1670", ...]` 的枚举，模型行为会怎么变？什么时候不该这么写？

   <details><summary>提示</summary>

   枚举把可选值变成闭集，模型更难编造订单号，但订单有几百张，全列进 schema 会撑大请求；订单号经常变化时也不该写死。适合少量固定分类，不适合开放集合。

   </details>
