# 第 22 章 harness 的结构：session、harness、sandbox

设想 T06 的顾客说《大运河两千年》缺了二十多页。Agent 查到 A1659 实付 82 元，算好应退 82，进程在调用退款前被杀掉。重启后内存里的 `messages` 全没了，它又问顾客“请问订单号是多少”。

更糟的是退款已经发生、结果还没写回：重启再退一次，顾客收到两笔钱。这一章把 agent 拆成三个对象，用本机的 JSONL 和子进程做出崩溃后继续跑的版本。

{{#fig ch22/brains_hands}}

Anthropic 在 2026 年的 Managed Agents 文章里给出这三个对象：session 是 append-only 的事件日志，harness 是调用模型、路由工具调用的循环，sandbox 是执行代码和改文件的运行环境。图里 harness 两边都只是接口：读写日志、调模型、`execute` 一个工具。

## 22.1 三个对象：session、harness、sandbox

文章先讲的是反例：最开始把三个对象塞进一个容器。文件改动是直接系统调用，也不用设计服务边界，但接着遇到三个问题。

- 容器成了“宠物”：它有名字、要手工照料，挂了 session 就没了。
- 出问题只能看 WebSocket 事件流，分不清是 harness 的 bug、事件流丢包还是容器离线；进容器排查又常常碰到用户数据。
- harness 假设资源就在容器里，接客户的 VPC 只能对等网络，或者把 harness 搬进客户环境。

拆开以后，容器对 harness 只是一个工具：`execute(name, input) -> string`。容器死了，这个错误像工具错误一样交回模型；模型决定重试，就用 `provision({resources})` 建一个新的。

session 留在 harness 外面。harness 崩了，新 harness 用 `wake(sessionId)` 启动，`getSession(id)` 取回日志，从最后一个事件继续；循环中用 `emitEvent(id, event)` 追加。

| 对象 | 负责 | 不负责 |
|---|---|---|
| session | 持久记录发生过的事 | 决定这一轮给模型看多少 |
| harness | 调模型、路由工具、写事件 | 执行代码、保存业务数据 |
| sandbox | 跑代码、改文件 | 持有凭据、决定什么时候被调用 |

接口要有主见，实现没有：文章说他们对接口的形状有主张，对后面跑什么没有。本书用本地 JSONL 和子进程模拟，不依赖托管服务。

三个对象可以各自换实现，只要接口不变。先看事件长什么样：

## 22.3 无状态 harness：杀掉再 wake

harness 不保存状态：每一轮都从 session 读事件、重建消息、调模型。进程退出不影响 session；内存里的 `messages` 只是 session 的一个投影。

{{#fig ch22/crash_resume}}

恢复流程是固定的五步：

1. `wake(session_id)` 启动新 harness，`getSession()` 取回事件。
2. 找最后一条 `assistant`（带 `tool_calls`）、`tool_call` 或 `tool_result`，看有没有没配对的调用。
3. 工具没执行，就直接执行它，不重新问模型。
4. 工具执行了、结果没写回，先查幂等键或业务库（[第 23 章](ch23.md)），再决定写结果还是跳过。
5. `emitEvent()` 追加结果，继续调模型。

第一个窗口里还没有 `tool_call` 事件，第 2 步靠 `assistant` 里的 `tool_calls` 判断。

三个崩溃窗口的恢复动作不同：

| 崩溃窗口 | 日志里看到什么 | 恢复动作 |
|---|---|---|
| 模型返回 `tool_calls` 后、工具执行前 | assistant 有调用，没有 `tool_call` / `tool_result` | 直接执行这个调用 |
| 工具执行后、结果写回前 | `tool_call` 有，`tool_result` 缺 | 先查幂等键，可能已经退过 |
| 结果写回后、模型下一轮前 | `tool_result` 有 | 从下一条读起，继续调模型 |

第二个窗口最危险：日志里有执行意图，没有结果，业务库可能已经变了。恢复前先查幂等键，别急着重做。

本地用两个文件：`ch22/22_3_resume/shop.db` 保留业务数据，`ch22/22_3_resume/session.jsonl` 保留事件。两个进程共享文件，不共享内存。

- 内存限制：示例没有设上限。
- 网络隔离：要靠容器或防火墙规则；各种容器平台、托管沙箱默认是否允许出网各不相同，上线前逐个确认，不要假设默认就是断网的。
- 文件系统只读：临时目录能写，别处靠 `..` 检查和 cwd。

不要在宿主机上直接跑不可信代码。示例的 `Sandbox` 还有两点没做：

- 没有持久化：每次启动 `Sandbox` 用一个临时目录；同一个 `Sandbox` 的多次 `execute` 共用它，跨运行不保留。
- 没有限制 CPU 和进程数，结束后才销毁。

工具结果只回字符串：退出码、stdout 前 N 个字符、stderr 的最后一行。不要把整个环境变量表或文件系统目录回传给模型，那既费 token，也把沙箱里的信息带进上下文。超时和截断也都变成字符串结果，模型能看懂发生了什么。

代码执行让 agent 能算金额、读 CSV，也扩大攻击面。高风险工具要审批（[第 20 章](ch20.md)）。

## 22.5 凭据隔离：令牌不进沙箱

反例最容易理解：容器里放着 `GITHUB_TOKEN`，注入让模型 `cat .env` 或读环境变量，令牌就泄露。拿到令牌可以开新会话、委派工作，影响超出这一个 session。

结构上的做法是把凭据放在 sandbox 外的 vault。Git 在 sandbox 初始化时用仓库 token clone，把 token 写进 local remote，模型不接触它；MCP 工具走代理，代理按 session 从 vault 取凭据。

{{#fig ch22/credentials}}

图里 sandbox 和 vault 之间没有边。harness 不知道凭据，工具 schema 和结果里没有 token，沙箱进程的环境变量里也没有。示例里的代理和外部服务都是本地假服务，只演示 token 的流向。

沙箱的环境变量是空的（Python 自己补的 `LC_CTYPE` 不算凭据），`.env` 找不到；直接调 `/service` 没有 bearer token，返回 401；带一个 `X-Session` 调代理，代理从 vault 取 token，返回 200，沙箱只看到结果字符串。

父进程另外检查了 token 没有出现在沙箱输出里。另外三条边界也要一起做：

- Git 初始化：clone 时由 harness 用仓库 token，token 写进 sandbox 里的 local remote；之后 push 和 pull 由 git 使用它，模型不接触。
- vault 限权：代理只能取这个 session 对应的 audience，不能拿一个万能 token 读所有仓库。
- 授权：MCP token 的 audience、禁止 passthrough（[12.2 节](ch12.md)、[19.6 节](ch19.md)），state handle 绑定到用户。

示例没有做归属校验：代理只查 `X-Session` 在不在映射表里，知道 `S-T06` 的人都能拿到 token。真实代理要把 session 绑定到已认证的调用方，光有 session id 不够。

## 22.6 多大脑多只手：按需 provision

一个容器里跑 harness 时，每个 session 都要等容器启动：clone 仓库、起进程、取事件，然后才能推理。不需要 sandbox 的 session 也付这笔钱。

Managed Agents 文章说，拆开以后他们的 p50 TTFT（time-to-first-token，首个 token 的等待时间）降了约 60%，p95 降了 90% 以上。这是他们的内部数据，不是普遍规律。

{{#fig ch22/many_hands}}

拆开后，不需要 sandbox 的 session 直接开始推理，需要时 `execute` 触发 `provision`。一个 brain 也可以连多只手，每个 hand 都是一个 `execute(name, input)` 工具，可以按需连接、替换或在 brain 之间传递。本书没有演示一个 hand 故障时其余 hand 的行为。

两种顺序下，一个要用 sandbox 的 session 各要等什么：

| 顺序 | 等到首个 token | 等到第一次工具结果 |
|---|---|---|
| 先 provision 再推理 | provision + 模型首 token | provision + 模型首 token + 工具 |
| 先推理，用到才 provision | 模型首 token | 模型首 token + provision + 工具 |

首个 token 早了整整一个 provision 的时间；第一次工具结果却一样晚。provision 没有消失，只是从“每个 session 都先付”变成“用到才付”，不用 sandbox 的 session 就一直不付。

| 能力 | Managed Agents 的接口 | 本地模拟 |
|---|---|---|
| 调执行环境 | `execute(name, input)` | `subprocess.run(..., cwd=, timeout=, env=)` |
| 建环境 | `provision({resources})` | `tempfile.TemporaryDirectory()` |
| 多处执行 | 每个 hand 一个工具 | 多个 sandbox 对象 |

按需 provision 也改变了监控：要记录每个 session 什么时候第一次用 sandbox、等了多久。没有这些事件，TTFT 的改善无法归因。

代价是多一层调度、事件一致性和错误传播。多只手同时改同一份数据时，事件顺序要能解释；一个 hand 失败，错误要能定位到是哪个环境。

同步执行仍然是瓶颈，模型还要决定把活发给哪个环境，这比在一个 shell 里操作更难。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `seq` / `type` / `payload` / `created_at` | 一条 session 事件 | 只追加，不改旧行 |
| `session_started` / `user` / `assistant` / `tool_result` | 能重建消息的类型 | `assistant` 要带 `tool_calls`，带 `tools` 时还要 `reasoning_content` |
| `tool_call` / `tool_result` | 执行意图和结果，按 `tool_call_id` 配对 | 崩溃恢复靠它们查缺 |
| `answer` / `decision` / `session_ended` | 最终回答、harness 的决定、结束 | `decision` 不作为普通对话消息；可作系统注记 |
| `wake` / `getSession` / `getEvents` / `emitEvent` | 启新 harness、取日志、切片、追加 | 都按 session id |
| `execute(name, input)` | 调执行环境 | 返回字符串，错误也交回模型 |
| `provision({resources})` | 建新环境 | 文章没给返回值；`execute` 仍返回字符串 |
| `get_events(after/before/n)` | 本地的位置切片 | 按 token 预算取，别全塞 |
| `subprocess.run(..., timeout=, cwd=, env=)` | 本地 sandbox | `env` 清空、`..` 拒绝、输出截断 |
| vault / MCP proxy / token audience | 凭据隔离 | 沙箱和 vault 之间不留边 |

4. 把本章的 session 日志用到[第 20 章](ch20.md)的审批，`pending.json` 里的哪些字段可以删掉、哪些必须保留？

<details><summary>提示</summary>

`messages` 可以由 session 事件重建，可以删；`tool_call_id`、`tool`、`args`、`request_id`（批准单号，审批侧按它查重）、`conversation_id`（找到对应的 session 日志）必须保留，否则恢复时对不上调用、也可能重复执行。`status` 和 `expires_at` 仍然要留，它们不是消息的一部分；`created_at` 留作审计，事件时间能推出，但审批单本身要有记录。

</details>
