## 14.1 预先检索的天花板：top-3 条款和“没被检索到”的答案

Anthropic 在 2025-09 的上下文工程文章里提到，很多应用在调用模型前用 embedding 做预取（pre-inference retrieval），并建议在此基础上加“即时检索”（just-in-time retrieval）：只把文件路径、查询这类轻量标识放进上下文，模型在循环里用工具取正文。本章的 `search_policies` 是另一种预取——按关键词匹配，不是文章里的 embedding。

`search_policies` 走预取这条路。它把查询切成两字词片，数每个词片在各节里出现的次数，取分数最高的 3 节。问法一换，词片就换，排序也换。

- 10 题命中 8 题、答对 8 题，两处答错正好对应两次没命中。预先检索是一次性的：top-k 没拿到的节，模型没有第二次机会。

两字词片不看词义，也不看否定。“签收以后多少天”被切成 签收 / 收以 / 以后 / 后多 / 多少 / 少天。换一个字，词片就换一批，排序跟着变。

| 检索方式 | 怎么排序 | 漏的原因 |
|---|---|---|
| 两字词片 | 词片在各节出现的次数 | 换个问法就换一批词片 |
| embedding | 查询和块的向量相似度 | 语义近的块不一定含答案 |

换成 embedding 也一样：相似度高的块排在前面，问法绕一层，正确节仍可能落在 top-k 外。top-k 越大越不容易漏，每次请求的 token 也越多。词片检索快、可解释，缺点也正是只认字面。

政策正文合计 1275 字（连同文档标题和 `##` 行 1483 字），约 1k token，全部塞进上下文也能跑。680 张订单按 13.5 节的量约 6.5 万 token，也塞得进去；问题是每轮都要重发，数据一变就失效，130 条评论和“箱子压坏”这种长尾问法也不适合全部预取。

预先检索不是错。错在把它当唯一入口：稳定、短、每次都用得上的内容适合预取，其余交给工具。

> **旧资料提示**：2025 年及以前的教程常把 RAG 当成默认检索方式。Anthropic 2025-09 的文章把预检索放进混合策略的一层，更多检索改成工具按需取；具体项目仍按数据量选。

## 14.5 混合策略：哪些预先放、哪些现查

| 策略 | 上下文里放什么 | 轮数 | 可追溯性 | 适用问题 |
|---|---|---|---|---|
| top-k 预检索 | top-3 原文块 | 1 | 只看到块，难回查整节 | 短、稳定、问法固定 |
| 目录 + 按需读取 | 目录和读到的小节 | 2–4 | 返回文档名和小节标题 | 长尾政策、多份文档 |
| SQL 聚合 | 表结构和查询结果 | 2–4 | SQL 和结果都能回放 | 计数、分组、趋势 |
| 混合 | 固定摘要加工具 | 1–4 | 摘要带来源和日期 | 客服日常、政策加订单 |

固定放的和现查的分开：

- 固定：`SUPPORT_PROMPT`、今天的日期、`returns.md` 里“退货期限”和“质量问题”两节的摘要，再加工具使用规则。

- 边界：摘要里只放最常问的两节，其余都留工具；摘要每次请求都要付 token。

## 14.6 检索工具的设计：范围、过滤、分页

参数要能收窄：`query`、`doc`、`title`、SQL 里的 `WHERE` 和 `LIMIT/OFFSET`。政策检索默认取 3 节（`Store.search_policies` 的 `limit=3`），SQL 默认 `max_rows=50`。

| 工具 | 收窄参数 | 截断时 |
|---|---|---|
| `search_policies` | `query`（底层 `Store.search_policies` 可传 `limit`） | 返回小节标题，让模型换词 |
| `read_section` | `doc`、`title` | 列出这份文档的可选小节 |
| `sql_query` | SQL 里的 `WHERE`、`LIMIT/OFFSET`、`max_rows` | 返回 `truncated` 和 `hint` |

- 默认值要按任务定：政策 3 节、SQL 50 行。太大浪费 token，太小增加轮数。
- 问题越窄，`limit` 可以越小。
- 示例的政策工具只暴露 `query`，`limit` 留在包装层；要让模型自己收窄，就把它加进工具参数。

分页或可能被截断的返回至少要带 `returned` 和 `truncated`；能算出 `total` 就一起给。`total` 是满足条件的总行数，`returned` 是本次返回的行数。

截断时在结果里写清怎么继续：SQL 用 `LIMIT/OFFSET` 或更窄的 `WHERE`；普通工具按[第 9 章](ch09.md)用不透明 `cursor`，返回 `has_more`、`next_cursor`。不要静默切掉。

正例是精确查询：

| 正例 | 怎么收窄 | 返回什么 |
|---|---|---|
| `get_order(order_id)` | 按订单号精确查 | 书目、金额、状态、物流 |
| `sql_query`（包 `readonly_sql`） | `WHERE` 加 `LIMIT/OFFSET` | 列名、行、`truncated` |
| `search_policies` | 换 `query`；底层 `limit` 可收窄节数 | 小节标题和正文 |

错误信息也要能指导下一步：

- 政策检索没命中时，列出可用文档名，例如 returns、shipping、membership、invoice、privacy。
- `read_section` 的标题写错时，列出这份文档所有可选小节。
- SQL 写错时，说明只允许 `SELECT`，或者给出语法错误的位置。

这些比一句 “not found” 有用。第 9 章讲过工具错误信息的写法。

资料取进来以后，长对话还会把窗口填满；[第 15 章](ch15.md)讲压缩、清理工具结果和结构化笔记。

> **旧资料提示**：有人说上下文 200k 足够装下整个知识库。`deepseek-flash` 的上下文是 1,048,576（2026-11）；680 张订单连同明细、物流和评论的四表 JSON 约 34 万字，按每字约一个 token 粗估约 34 万 token，仍在窗口内。数据再大 10 倍（约 340 万字）才会超过 1M；装得下不等于该装，每轮重发、按 token 计费，数据一变缓存也救不了。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `list_docs()` | 返回文档名、小节标题、字数 | 目录约 300 token，不放正文 |
| `read_section(doc, title)` | 读一节 | 返回 `doc`、`section`、`text`、`length` |
| `search_policies(query)` | 两字词片打分，默认取 3 节 | 兜底入口；`Store.search_policies` 可传 `limit` |
| `readonly_sql(sql, max_rows=50)` | 只读 SQL | authorizer 拒绝写操作；它本身不报截断 |
| `list_tables()` / `describe_table(name)` | 先看结构再写 SQL | 不要每轮重发全 schema |
| `returned` / `truncated` | 告诉模型结果有没有被切过 | 截断时必须给出继续方式 |
| SQL 的 `LIMIT/OFFSET` | 限制返回行数 | 通用工具分页按第 9 章用 `cursor`/`next_cursor` |
| 预取三判据 | 决定放固定上下文还是做工具 | 每次都相关、内容稳定、短到可承受 |

   <details><summary>提示</summary>`returned=50` 与 `total=680` 对不上。工具没有 `offset`；`find_order` 只在 `read_all_orders` 返回的 50 条缓存里查，超出这个范围就等于没有按编号查。</details>

3. 权衡：一个每天被问 1 万次的退货期限问题，预取还是现查？把 token、延迟、更新频率各算一笔。

   <details><summary>提示</summary>预取每次省掉一次工具往返，但每次请求都带摘要；现查多一轮，更新政策时不用改摘要。算一算每天多花的 token 和少掉的延迟。</details>

4. 迁移：把“目录 + 读取 + SQL”换成“文件系统 + `grep` + `read`”，工具参数要怎么改？

   <details><summary>提示</summary>`list_docs` 变成列目录，`read_section` 变成按路径和行号读，`search_policies` 变成 `grep`。记得给 `grep` 加路径、模式和上下文行数，给 `read` 加 offset 和 limit。</details>
