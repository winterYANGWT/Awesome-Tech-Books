# 第 26 章 LangGraph（三）：子图、map-reduce 和长期记忆

第 6 章用 `asyncio.gather` 并行检查回复，第 15 章把顾客信息写进 `NOTES.md`。换成图以后，并行分支写同一个 key 会报 `InvalidUpdateError`，子图的私有状态父图看不见，`Store` 的 namespace 排反了又会把其他顾客的档案一起查出来。

这一章把三件事分开：子图封装一组节点，`Send` 负责运行时才知道数量的扇出，`Store` 把顾客档案放到 thread 之外。

| 本章 | 之前在哪手写过 | 解决什么 |
|---|---|---|
| 子图 | 第 6 章 `asyncio.gather` 里的一个检查函数 | 把一组节点封装成可复用的节点，自己有内部状态 |
| `Send` | 第 6 章 `gather` 的多个任务 | 扇出几个 worker 由运行时数据决定 |
| `Store` | 第 15 章 `NOTES.md` | 跨 thread 的顾客档案，不随对话结束消失 |

## 26.1 子图：把政策检查装进一个节点

子图是编译后的 graph，挂到父图有两种方式。

- `builder.add_node("policy_check", subgraph)`：父子共享同名 key，子图直接读写父图的 channel。

父图的 State 里也有 `policy_text`，子图内部确实写了政策原文；但 `StateGraph(SubState, output_schema=SubOutput)` 把它挡在输出外，所以父图里仍是空串。`verdict` 和 `reason` 在 `SubOutput` 里，才进了父图。

三个细节：

- `output_schema` 只管子图对外给什么；子图内部的 `judge` 仍然读得到 `policy_text`。父图 State 里写这个键，只是给父图留了一个空 channel，不会把子图内部的值自动搬过来。
- 共享 key 时，子图的写入也走父图的 reducer。子图返回 `{"log": ["sub"]}` 时，父图的 reducer 会把它并进父图已有的 `log`，不会覆盖；26.1 的两个 schema 里没有这个键，这里说的是共享同名键的规则。
- 什么时候值得包成子图：同一组检查被多张图复用、检查内部有很多中间结果、需要单独查看这一段的检查点。只包一个函数时，普通函数更短。

两个边界：

- 子图不是“多 agent”。它只是把一组节点包起来，节点之间仍然按边执行；manager 和 handoff 是第 17 章的另一件事。
- 子图里的 `interrupt()` 会冒泡到父图。父图 thread 上执行 `Command(resume=...)`，值会传进子图里那个 `interrupt()` 的返回值；恢复和检查点仍是第 25 章的机制。

| 做法 | schema 是否共享 | 检查点命名空间 | 能否单独流式看 | 复用方式 |
|---|---|---|---|---|
| 子图作为节点 | 同名 key 共享，父图 reducer 生效 | 以子图节点名开头 | `subgraphs=True` 时能看到子图节点 | 编译一次，挂到多个父节点 |
| 节点里 `invoke` | 不共享，手动映射输入输出 | 父节点名开头（继承 checkpointer 时） | 同样出现在 `subgraphs=True` 的流里 | 当普通函数调用，可改输入 |
| 普通函数 | 不涉及 | 没有 | 看不到内部步骤 | 代码复用，不参与图 |


开 `subgraphs=True` 时，每项是 `(namespace, chunk)`；namespace 是 tuple。

子图的 namespace 形如 `('policy_check:2f4c…',)`，去掉冒号后的 uuid 就是父图节点名。父图自己的 namespace 是 `()`。

两个打印细节：

- uuid 每次运行都不一样；打印时只取冒号前的节点名，回放输出才不会漂。
- 不开 `subgraphs` 时只剩两行：`policy_check`、`privacy_check`。子图内部的 `lookup`、`check` 不会出现。

检查点也是两层。父图的 `get_state_history` 只列空 namespace 的检查点；要看子图那层，用 `checkpointer.list(...)`，输出里会同时出现 `policy_check`、`privacy_check` 和父图的 `''`。

LangGraph 1.2.22 实测如此。恢复时只传带 `thread_id` 的 config，不需要指定子图；LangGraph 会按 `checkpoint_ns` 找回停下的那个子图。

三个容易踩的点：

- 子图有自己的 state，父图不会自动看到 `detail`；要共享就写同名 key，要对外只给结论就用 `output_schema`。
- 同一个子图实例挂两次时，`checkpoint_ns` 按父节点名区分；不要用全局变量存子图状态。
- 子图抛错会作为父图节点错误冒出来；检查点保留失败前已完成的超步，恢复时从失败节点继续，不必重跑上游。

## 26.3 Send 和 map-reduce：一次检查三个政策

条件边函数可以返回一组 `Send`，每个 `Send` 指定目标节点和这一次的输入。目标节点被调用几次，由列表长度决定。

`Send` 的第二个参数不必等于父 state。这里每个 worker 只拿到 `check`、`policy`、`rule`、`draft` 四个字段，父图的 `checks`、`tokens` 它看不到。worker 返回的键仍写回父图，所以 reducer 挂在父图这一层。

{{#fig ch26/map_reduce_send}}

```python
{{#include code/ch26/26_3_send_policies.py}}
```

这次运行的输出：

```text
{{#include code/ch26/26_3_send_policies.out}}
```

三条结果按 `check` 排序打印：口径不通过，退货政策和隐私通过，总 token 1666。排序是 reduce 节点用代码做的；worker 完成的先后不保证，不排序回放就会漂。

并行省的是等待时间，不省 token：三个 worker 各自带着草稿和政策原文，输入会重复。这次三次调用合计 1666 token；按这个示例的输入估算，顺序调三次的 token 数接近，但等待时间会叠加。

三个 worker 都写 `checks` 和 `tokens`，所以这两个 key 必须带 reducer：

```python
checks: Annotated[list[dict], operator.add]
tokens: Annotated[list[int], operator.add]
```

去掉 reducer，三个 worker 在同一超步各写一次，就会抛 `InvalidUpdateError`，消息里指出 `checks` 只能收到一个值。

两种固定写法：

- 固定两个分支就用普通边。
- 固定并行就用 `add_edge(START, "a")` 和 `add_edge(START, "b")`。

`Send` 适合“扇出几个，运行时才知道”的情况。三个请求的内容必须不同：每个 worker 的提示里写清自己的检查项，否则回放时答案可能被分错。错误定位也靠这个字段：结果里带 `check`，reduce 排序后哪一项不通过一眼能看到。

reduce 不一定是模型。这里只排序；需要综合三条结论写一句话时，再在 `reduce` 节点里调一次模型。

## 26.4 长期记忆：Store 的命名空间和键

`InMemoryStore` 是一个跨 thread 的 key-value 存储。`put(namespace, key, value)` 的三个参数都是显式的：namespace 是 tuple，key 是字符串，value 是 dict。

| namespace | 存的字段 | `search(("C082",))` | `search(("C083",))` | `search(("C08",))` |
|---|---|---|---|---|
| `("C082", "profile")` | 发票抬头：天津 | 命中 | — | — |
| `("C082", "memories")` | 偏好：历史 | 命中 | — | — |
| `("C083", "profile")` | 发票抬头：苏州 | — | 命中 | — |

`C082` 命中它自己的 `profile` 和 `memories` 两行，`C083` 只有 `profile`；`C08` 不等于任何一段，三行都不命中。namespace 是按整段匹配的，不是字符串前缀。

```python

```

这次运行的输出：

```text
{{#include code/ch26/26_4_store_basics.out}}
```

`search(("C082",))` 返回两条：`C082/profile` 和 `C082/memories`。前缀匹配按 tuple 的整段比较，不是字符串前缀；`("C08",)` 不会匹配 `("C082", ...)`，实测是 0 条。

命名和键的三个细节：

- namespace 的层数没有限制，但层数越多，查询越容易写错。本书统一把顾客号放第一段、类别放第二段；`("C082",)` 能一次拿到这个顾客的全部记忆，查单类时再写完整 namespace。
- `get` 返回 `Item`，有 `.value`、`.key`、`.namespace`、`.created_at`、`.updated_at`。示例只打印 namespace、key 和 value，因为时间戳每次运行都不同。
- key 在 namespace 内唯一；同一个 key 再 `put` 是覆盖，不是追加。`InMemoryStore` 在覆盖时连 `created_at` 也一起重设，想记首次创建时间要自己存一个字段。

namespace 用 tuple 而不是字符串，是为了不靠分隔符解析。`"C082/profile"` 只是一个字符串，斜杠是内容的一部分，没法可靠地拆回两段。

前缀真正危险的地方在 namespace 的排法。下面这个反例把类别放在第一段、顾客放在第二段：


这次运行的输出：

```text

```

`search(("profile",))` 把 C082 和 C083 的档案一起查了出来。修法是 namespace 以顾客开头：`("C082", "profile")`、`("C083", "profile")`，查询时用完整 namespace；确实要跨顾客按类别查时，再在客户端按 `item.namespace[1]` 过滤（顾客号在 `[0]`）。

后端的三个细节：

- `InMemoryStore` 按插入顺序返回，Postgres 按 `updated_at` 降序。不要依赖顺序，打印前按 key 或 namespace 排序。
- `search` 默认最多 10 条，超出静默截断，没有“还有更多”的信号。要全量就把 `limit` 调大，或者用 `offset` 分页。
- 删除的最小单位是 `(namespace, key)`。`InMemoryStore` 没有按 namespace 删除的方法，清空一个顾客的档案要先 `search` 再逐条 `delete`。

要语义搜索时给 `InMemoryStore(index={...})` 配 embedding，`search(..., query=...)` 才会排序；本书不配 embedding，只做精确 key 和前缀检索。

几个设计点：

- key 用稳定的 `"invoice"`，不要 `uuid4()`；否则每次写入多一条，输出也不可复现。
- 写记忆放在单独的 `save_profile` 节点，先 `get` 旧值再合并，不覆盖 `preference` 等别的字段。
- 抽取用 `with_structured_output(Profile, method="function_calling")`。它会强制 `tool_choice`；DeepSeek 思考模式不支持 `required` 或指定函数名，这里直接关掉思考（`extra_body={"thinking": {"type": "disabled"}}`），避开这个限制。
- 读记忆放进系统提示的“已知顾客信息”，不要把全部历史消息塞进去。
- 冲突时以顾客当前说法为准，并更新 `updated` 和 `source_thread`。

`save_profile` 只处理明确说“以后”的输入，日常问问题不写档案。这个路由是示例的简化；生产可以看抽取结果是否为空，再决定写不写。

示例的 `Profile` 只有一个字段，`respond` 把整条记录放进系统提示就够了。字段一多，每轮都塞进去会占掉上下文预算，按当前问题取 `invoice_title` 或 `address`。

| 存储 | 作用域 | 生命周期 | 存什么 | 怎么删 |
|---|---|---|---|---|
| checkpointer | 一个 thread | 进程或数据库 | 图 state 的每个超步 | `delete_thread(thread_id)` |
| `Store` | 跨 thread | 进程或后端存储 | 顾客档案、偏好等 dict | `delete(namespace, key)` |
| `NOTES.md`（第 15 章） | 一个项目/会话 | 文件在就在 | 固定五节的短笔记 | 编辑或删文件 |

隐私上，namespace 按顾客隔离；日志里不要打印完整地址和电话。顾客要求删除时，`profile` 和 `memories` 两个 namespace 都要 `delete`，只删一个会留下另一份。

同一句“书收到了，包装很好”，两种提示各跑 8 次。A 组只记明确事实，B 组要求尽量补全偏好，模型和用户消息相同，只改系统提示。每次调用在系统提示末尾加序号，让请求互不相同。


这次运行的输出：

```text
{{#include code/ch26/26_6_memory_inference.out}}
```

A 组 0/8 写入 `preference`，B 组 8/8。不是说 B 组一定这样，而是一次运行里两组的方向很清楚：提示让模型“补全”，它就会把“包装很好”推断成一种偏好。只记顾客明确说的事实，推断出的内容不进档案。

N 只有 8，两组各 8 次，不能把这个比例当成普遍规律；它说明的是提示方向会改变抽取结果。要比较提示好坏，用第 21 章的评测集和更多次重复。

| 组 | 提示 | 写入 preference |
|---|---|---|
| A | 只记明确事实 | 0/8 |
| B | 尽量补全偏好 | 8/8 |

写记忆前先问三个问题：顾客明确说了吗？这个字段会过期吗？谁会读到它？

三个答案不清楚时，宁可先不写。具体做法：

- 只写顾客原话里出现的字段，推断出的内容留在回复里，不进档案。
- 每条记忆带 `updated` 和来源 thread，冲突时才知道该信哪条。
- 不确定的字段留空，不填“未知”“可能”这类占位值。

这三个问题是写入前的闸门，不是给模型看的提示。字段越多，越要按这个顺序过一遍。

记忆还会过期和冲突：

- 地址、发票抬头变更后覆盖旧值，不要追加成两条互相矛盾的记录。
- 读的时候按 `updated` 取最新；`InMemoryStore` 的返回顺序不能当时间顺序。
- 每轮都把整个 profile 塞进系统提示会占 token；按当前问题取需要的字段（第 13 章）。

隐私上还有两条：`search` 的前缀会跨类别，查完要按 namespace 过滤；删除要同时覆盖 `profile` 和 `memories`。

> **旧资料提示**：LangChain Academy 用 `trustcall` 的 `create_extractor` 更新 profile，本书用 `with_structured_output(method="function_calling")` 加 Pydantic 校验，`trustcall` 不在依赖里。LangChain Academy 的 memory store 示例用 `uuid.uuid4()` 生成 key，本书用稳定 key `"invoice"`。LangChain Academy 的 research-assistant 用 Tavily 联网，本书只读本地 `shop` 数据。LangChain Academy 常用 `MemorySaver`，现在主用 `InMemorySaver`，`MemorySaver` 仍是别名。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `StateGraph(SubState, output_schema=SubOutput)` | 限制子图对外输出 | 子图只写回 `SubOutput` 的键 |
| `add_node("name", subgraph)` | 子图作为节点 | 父子共享同名 key，父图 reducer 生效 |
| `subgraph.invoke({...})` | 节点里调用子图 | schema 不同，自己做输入/输出映射 |
| `checkpoint_ns` | 检查点所属的图 | 父图 `''`，子图以节点名开头 |
| `stream(..., subgraphs=True)` | 看子图内部步骤 | 每项是 `(namespace, chunk)` |
| `Send(node, arg)` | 运行时扇出 | 第二个参数是这次 worker 的输入 |
| `Annotated[..., operator.add]` | 合并并行写入 | 没有 reducer 会 `InvalidUpdateError` |
| `InMemoryStore()` | 跨 thread 的 key-value | 进程结束即丢 |
| `put/get/search/delete` | 存取删 | `search` 按 namespace 前缀，不是字符串前缀 |
| `Item.value/key/namespace/updated_at` | 一条记录 | 时间戳不要打进可复现输出 |
| `compile(checkpointer=..., store=...)` | 同时装 thread 记忆和长期记忆 | 两者作用域不同 |
| `BaseStore` 注入 | 节点里读写 store | 顾客号从 config 取 |
| `with_structured_output(method="function_calling")` | 结构化抽取 | 会强制 `tool_choice`，思考模式要先关 |
