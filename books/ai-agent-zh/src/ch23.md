# 第 23 章 生产中的 agent：追踪、持久执行、缓存和成本

账单上通常只有汇总：三次模型调用、5,442 token，比预期高；想知道哪一轮最贵，日志里翻不到。退款接口超时后重试了一次，顾客收到两笔退款。

这一章拆四件事：一次会话怎么记追踪、token 怎么变成成本、缓存为什么没命中、重试怎么不重复副作用。问题大概长这样：

```text
账单汇总：3 次模型调用，5,442 token
退款记录：A1656  50.00 元  ×2
想知道：哪一轮最贵？缓存为什么没命中？
```

## 23.1 一次会话的追踪：每一步一行

{{#fig ch23/trace_waterfall}}

一次会话里的每个动作记一行，JSONL 追加写，一行一个 span。出问题按 `trace_id` 把整条会话捞出来，按 `parent_id` 还原谁调用了谁。每行至少这些字段：

| 字段 | 写什么 | 例子 |
|---|---|---|
| `trace_id` | 一次会话一个 | `tr-t06-0001` |
| `session_id` | 对应的 session，用来取正文 | `S-T06` |
| `ticket_id` | 第 21 章评估记录里的工单号 | `T06` |
| `span_id` / `parent_id` | 这一行和它的上一层 | `sp-05` / `sp-04` |
| `turn` | 第几次模型调用 | `2` |
| `kind` | `model`、`tool`、`approval`、`answer` | `tool` |
| `started_at`、`duration_ms` | 开始时间和耗时 | `2026-11-17T14:03:07`、`0` |
| `status` | `ok` 或 `error` | `ok` |
| `tokens` | 模型调用才有 | `prompt`、`completion`、`cache_hit` |

按 `kind` 看，每种 span 记的东西不同：

- `model`：模型名、消息条数、`finish_reason`、`tool_calls` 个数。
- `tool`：工具名、参数键、结果字节数、错误类型。
- `approval`：谁批的、决定、等了多久。

正文一概不记：提示只记条数，工具结果只记字节数和 hash，回答只记长度。要内容时按 trace 里的 `session_id` 回 session 里取（第 22 章）。trace 里也不放金额：金额由 23.2 从 usage 算，不然改了单价，旧 trace 全对不上。

时间字段有两条纪律：

- `started_at` 用本机时钟，`duration_ms` 用单调时钟算，避免系统时间跳变。
- 两个字段合起来，才能把不同机器的 span 排成一条时间线。

## 23.3 上下文缓存：什么让命中率归零

{{#fig ch23/cache_prefix}}

缓存按前缀匹配：从第一个 token 开始，连续相同的部分才可能命中。系统提示开头一变，后面的工具定义、历史、工具结果全部重算。

保住前缀的三件事：

- 系统提示稳定，变化的部分放末尾或用户消息。
- 工具定义顺序固定，不按字典序每次重排。
- 历史只追加，不回头改旧消息。

两组各 6 次，同一段 1,666 字的系统提示加 9 个工具定义。A 组固定；B 组在系统提示最前面写当前时间，每次差一秒：

```

```

读两组数：

- A 组第 1 次 0，后面 5 次都命中 1,920 / 2,165（88.7%）。
- B 组 6 次全是 0，尽管两组的系统提示只差开头十几个字。

命中率不是 100%：最后一段（用户消息和尾部）每次都要重算，A 组也留了 245 个 token 没命中。DeepSeek 的文档没有给出固定的缓存保留时间和容量，本书也没有测。

| 组 | 系统提示 | 6 次命中 | 原因 |
|---|---|---|---|
| A | 固定 | 9,600 / 12,990（73.9%） | 前缀一直一样 |
| B | 开头写时间戳 | 0 / 13,086（0.0%） | 第一个 token 就分叉 |

B 组不是“缓存坏了”，是每次都是新前缀：时间戳在第一行，后面两千多 token 谁也没见过。把时间戳挪到系统提示末尾，只能保住它前面的那一段，工具定义、用户消息和尾部仍要重算，命中率会下降，不会回到 A 组；要保住整段系统提示，变化得放到用户消息里或请求末尾。

缓存不影响正确性，只影响成本和首 token 延迟。示例为了把前缀拉长才把政策全文放进系统提示；生产里别这么做，挤掉的是真正需要模型看的上下文。

观测和调优按这个顺序：

- 在 trace 里记 `cache_hit / prompt`，按天看趋势。
- 命中率掉一半就按 23.6 告警，再回头查系统提示和工具顺序有没有变。

> **旧资料提示**：如果你读过把上下文缓存说成“自动命中、无需设计”的教程，注意 DeepSeek 2026-11 的缓存按前缀匹配：系统提示或工具顺序一变就失效，见 23.3 的 B 组。

## 23.4 持久执行：重试、幂等和断点

读这次输出：

- 有幂等键时，第一次退款成功但响应丢了，调用方（`with_retry`）只看到超时；重试带着同一个 key，查到上次结果，累计还是 50。

最多尝试 3 次（两次重试），退避 0.1、0.2 秒。真实系统用指数退避加抖动，别让一批请求同时回来。

只重试可重试的错误：

| 错误 | 例子 | 怎么办 |
|---|---|---|
| 超时、连接断开 | 退款网关超时 | 退避重试，带同一个 key |
| 429、5xx | 限流、服务端错 | 退避重试，有次数上限 |
| 业务错误 `ShopError` | 超过可退金额、状态不对 | 不重试，把消息交回模型 |
| 参数错误 | 坏 JSON、缺字段 | 不重试，修参数或改工具描述 |

另外三条规则：

- 业务错误不重试：`ShopError` 的消息本来就是写给模型看的，模型可以换个金额、先提交主管，或者向顾客解释。
- 断点先查 session：`tool_call` 和 `tool_result` 已经在事件日志里（第 22 章），先看这个 `tool_call_id` 有没有结果。
- 不要在模型层重试整个循环：那会把前面的工具调用再做一遍，退款就退两次。

示例还有一处没做到原子：`refund` 提交后、幂等记录写入前崩溃，仍会重复；生产里要让两者在同一个事务里，或者用带唯一约束的 `actions` 表兜底。更稳的办法是让数据库替你去重，而不是靠应用层记得先查一次。

## 23.5 部署和并发：彩虹部署、double-texting

{{#fig ch23/deploy_double}}

彩虹部署：新旧版本同时跑，逐步把流量从旧版本切到新版本。建议在 `session_started` 的 payload 里带上 `harness_version`，恢复时用同一版本或兼容版本，不能让新代码去读旧版本写到一半的事件。

彩虹部署的关键不是“两个版本”，是“会话别跨版本”。旧 run 用旧版本跑完，新 run 才进新版本；恢复时版本不兼容就拒绝恢复，不要硬读。

double-texting 是上一次 run 还没完，用户又发来一条。LangGraph Platform 把处理办法叫 `multitask_strategy`，有四种。拿一个例子看：顾客先发“订单 A1659 缺页，退我 82 元”，run 1 刚跑完 `get_order`，第二条“先别退款，我想换货”到了。

| 策略 | 第二条到达时 | 这个例子的结果 |
|---|---|---|
| `reject` | 回 409，第二条进不来 | run 1 照样退了 82 元，顾客改主意的消息丢了 |
| `enqueue` | 排队，等 run 1 跑完 | 先退款，再登记换货，两件都做了 |
| `interrupt` | 停掉 run 1，保留已完成的工作，用新消息接着跑 | 用已经查到的订单登记换货，没有退款 |
| `rollback` | 删掉 run 1 的事件，从第二条重跑 | 订单要重查；如果 run 1 已经退了款，删事件删不掉钱 |

客服场景这样选：

- 补充信息用 `enqueue`：前一条的结论仍然有效，第二条接着处理。
- 改主意用 `interrupt`：停掉还没执行副作用的那一步，保留已经查到的事实。
- 重复发送用 `reject`：回一句“正在处理”，别让两条一样的消息都去退款。
- 上一句说错了用 `rollback`：它删得掉事件，删不掉已经发生的退款。

`enqueue` 的代价是延迟：第二条要等第一条跑完，长任务可能等几十秒。`interrupt` 的代价是第一条没有回答，要给顾客一个“已停下”的提示。两条消息间隔很短时，排队也比丢消息好。

并发还要防重复：同一 session 两个 run 会打乱事件顺序，用 session 级锁或单写者。单写者可以是一把锁，也可以是一个按 session 分区的队列；关键是同一 session 的事件只能由一个进程追加。

取消不是杀进程：建议在 session 里追加一条 `cancelled` 事件，工具侧在每一步检查取消标记。已经在执行的退款不会因为进程被杀而退回，这和 23.4 的幂等是同一个问题。恢复时先看最后一条事件是不是 `cancelled`，是就不要接着跑。

| 能力 | LangGraph Platform 的做法 | 本书本地做法 |
|---|---|---|
| Runs | 一次执行，可查状态 | `run()` 加 `trace.jsonl` |
| Threads | 多轮、人工介入 | session JSONL（第 22 章） |
| Store | 长期记忆 | SQLite / `NOTES.md`（第 15 章） |
| double-texting | `multitask_strategy` 四种 | 事件日志模拟 |
| assistants | 配置和版本 | `harness_version` 加提示文件 |
| 部署 | Docker + Redis + Postgres | 只讲原理，不写示例 |

> **旧资料提示**：LangChain Academy 的 module-6（2026-06）要在 LangGraph Platform 上部署，依赖 LangSmith 账号和 Docker、Redis、Postgres。本机没有这些账号，23.5 只讲 runs、threads、store 和 double-texting 的原理。

## 23.6 值班：从 trace 到告警

{{#fig ch23/dashboard}}

值班看这些指标：

| 指标 | 怎么算 | 告警线 |
|---|---|---|
| 请求数 | 每分钟新 run | 突增或掉零 |
| 延迟 | p50、p95 | p95 超过基线 2 倍 |
| 错误率 | 工具错、模型错、审批超时 | 超过 5% |
| `max_turns` 比例 | 轮数用完的 run 占比 | 明显上升 |
| 缓存命中率 | `cache_hit / prompt` | 掉一半 |
| 每会话 token | 先按 `trace_id` 分组，再对每组求和 | 超过预算 |

阈值这样定：

- 先跑一周基线，再按 2 倍和 5% 这类粗线设。
- 定得太紧，一次网络抖动就告警。
- 定得太松，顾客投诉了还没动静。

2. 找错：`idempotency_key` 用 `order_id + amount`，同一订单两次不同原因的 50 元退款会被当成一次。应该用什么做键？会带来什么新问题？

<details><summary>提示</summary>

应该用 `session_id + ":" + tool_call_id`，一次工具调用一个键；同一笔退款的重试会带同一个 `tool_call_id`。新问题是：模型换了 `tool_call_id` 再调一次，幂等键就不同了，所以业务层还要有“这笔退款是否已经存在”的约束，不能只靠键。

</details>

3. double-texting 选 `reject`、`enqueue` 还是 `interrupt`？用“顾客改主意”“顾客补充信息”“顾客重复发送”三种情况说明。

<details><summary>提示</summary>

改主意用 `interrupt`：停掉还没执行副作用的那一步，保留已经查到的事实。补充信息用 `enqueue`：前一条的结论仍然有效，后一条接着处理，不丢消息。重复发送用 `reject` 最简单，回一句“正在处理”，但要保证顾客能看见上一条的进度。三种情况都可能出现，策略要能按消息内容选，而不是全局固定一个。

</details>

4. 估算：一次 9 轮、每轮 4k prompt、500 completion 的会话，缓存命中率从 0 提到 80% 能省多少输入 token？输出 token 省不省？

<details><summary>提示</summary>

输入总量 9 × 4k = 36k，80% 命中就是 28.8k 个输入 token 按缓存价计费，省下的是这 28.8k 的单价差。输出是 9 × 500 = 4.5k，缓存只作用于输入，一个也不省。再按 23.2 的占位单价算，输出那部分仍占大头。

</details>
