## 12.2 授权：OAuth 2.1 的角色和流程

{{#fig ch12/oauth}}

三个角色要分清：MCP server 是 OAuth 2.1 的 resource server，client 是 OAuth client，authorization server 负责登录和发 token。stdio server 不适用 OAuth，凭据从环境或本地库取。

{{#figref ch12/oauth}} 把四条泳道走一遍：client 先吃一个 401，读两份元数据，再用 PKCE、`resource`、`scope` 换 token。


```text

```

看 401 的 `WWW-Authenticate`：`resource_metadata` 指向 Protected Resource Metadata（PRM，RFC 9728），`scope` 给出这次操作要的最小权限。

401 不是错误页，它是发现入口。client 先读 PRM 拿 `authorization_servers` 和 `scopes_supported`，再读 AS metadata（RFC 8414 或 OIDC）拿 `issuer`、授权端点、token 端点和 `code_challenge_methods_supported`。

授权 URL 和 token 请求里的参数：

| 位置 | 参数 | 说明 |
|---|---|---|
| 授权 URL | `response_type=code` | 授权码模式 |
| 授权 URL | `client_id` | 预注册、CIMD URL 或 DCR 拿到的 id |
| 授权 URL | `redirect_uri` | 必须精确匹配注册值；本地是 `127.0.0.1` |
| 授权 URL | `scope` | 先用 401 里的最小集合 |
| 授权 URL | `state` | client 保存，回调时比对 |
| 授权 URL | `code_challenge` + `S256` | PKCE，`code_verifier` 留在 client |
| 授权 URL | `resource` | MCP endpoint 的规范 URI |
| token 请求 | `code_verifier` | 换 token 时证明自己是发起方 |
| token 请求 | `resource` | 再带一次，绑定 token 的受众 |

回调带 `code`、`iss` 和 `state`。client 先校验 `iss` 与记录的 issuer、`state` 与发起时的值，才拿 `code` 去换 token。

token 的 `aud` 必须等于这个 MCP endpoint，scope 要覆盖这次操作。

注册顺序按规范来：

1. 有预注册凭据，先用它。
2. 没有就用 Client ID Metadata Documents（CIMD）：HTTPS URL 作为 `client_id`，AS 去抓元数据。
3. 最后才是 Dynamic Client Registration（RFC 7591），它已弃用但保留兼容。

scope 先用 401 里的值。运行中收到 403 `insufficient_scope` 再 step-up，把新 scope 和原来的并集重新授权。

预注册和 DCR 的 client 凭据按 issuer 存，换 AS 要重新注册。CIMD 的 `client_id` 是客户端自托管的 HTTPS URL，可跨 AS 用，不用重新注册。

server 收到 token 要验签（JWT 时）、`aud`、过期时间和 scope。给别的资源签的 token 一律拒绝：

```text
{{#include code/ch12/12_2_audience_fail.out}}
```

完整程序见 [12_2_audience_fail.py](code/ch12/12_2_audience_fail.py)：它只做 `aud` 校验和 401，没有上游调用。

如果 server 再调上游 API，它在上游面前是另一个 OAuth client，要用另一个 token。把 client 的 token 原样转给上游叫 token passthrough，规范明确禁止：上游会以为这个 token 是发给它的，审计和限流也会错位。

| 认证方式 | 适用场景 | 主要风险 |
|---|---|---|
| stdio 环境变量 | 本地 server，单机 | 进程继承整个环境；第三方 server 能看到所有变量 |
| HTTP OAuth 2.1 | 远程 server | token 泄露、`aud` 不校验、透传、scope 过大 |
| API key | 简单内部服务，或 server 不支持 OAuth | 长期有效、难轮换；放进 sandbox 就等于交给模型 |

API key 不在 MCP 的 OAuth 流程里；它只是把长期凭据放进 header，适合内部服务。

> **旧资料提示**：DCR 曾经是默认推荐。现在有预注册先用预注册，没有就 CIMD，DCR 只做兼容。token passthrough 也被明确禁止；不要把一个 token 同时给 MCP server 和上游 API。

三栏各自看到的东西不交叉：

远程工具则走 MCP 代理：代理接收 session token，去 vault 取对应的 OAuth token，再调外部服务。harness 和 sandbox 都看不到凭据。

- 本地 stdio server 不是 sandbox，它和 host 在同一个信任域。
- 它继承启动它的环境变量，能读你的账号能读的文件。
- 第三方 server 只给它必需的 `env`，不要把整个环境传进去。

本地 server 的供应链风险也更直接：它拿到的是你的用户权限，不是协议沙箱。只装需要的 server，固定版本，能把本地 server 放进容器就放进去。

四个注解的默认值来自 schema：

| 注解 | 默认 | 含义 |
|---|---|---|
| `readOnlyHint` | `false` | 工具会修改环境 |
| `destructiveHint` | `true` | 修改可能是破坏性的 |
| `idempotentHint` | `false` | 重复调用可能再次生效 |
| `openWorldHint` | `true` | 会接触开放世界的外部实体 |

注解和真实行为不一致时，策略要能回退到人工。默认值只是起点：`readOnlyHint` 为 false 的工具不一定危险，为 true 的工具也不一定安全。

注解只是提示，不是保证。来自不可信 server 的注解，client 不能拿来做自动批准。

## 12.5 安全清单：威胁、边界和默认值

{{#fig ch12/security_layers}}

五层不是五个 checkbox。用户同意和 host 策略决定“能不能做”，server 校验和 sandbox 决定“怎么做”，vault 决定“做完拿什么凭据”。

{{#figref ch12/security_layers}} 画了五层：用户同意、host 策略、server 输入校验、sandbox 执行、vault 和上游 API。每层各守一个默认值，任一层缺失，红边就连通。

三类检查各管一段：

- `ResourceSecurity` 真的在拦路径穿越、绝对路径和 NUL 字节。
- 本地策略用集合和长度判断拦未知工具和超大参数。
- 示例用几行布尔检查模拟 `Content-Type`、`aud` 和过期状态的校验。

示例里的状态 token 用 HMAC 加了签名和 TTL，SDK 的 `RequestStateSecurity` 做的是同一类事。

| 攻击 | 这里怎么防 |
|---|---|
| confused deputy：代理替用户做了没同意的操作 | 每次高风险动作都回到用户或 host 的 `approve`，代理不跳过 |
| token passthrough：把 client 的 token 转给上游 | 上游用单独 token；server 只接受 `aud` 是自己的 token |
| SSRF：资源 URL 或 schema 的 `$ref` 指向内网 | 默认不解析网络 `$ref`；URL 允许列表，拒绝 loopback、link-local、私网 |
| state handle hijacking：拿到句柄就操作别人的状态 | 显式句柄要绑定认证主体，不把“持有句柄”当认证 |
| 本地 server 被投毒或供应链污染 | 只装需要的 server、固定版本、看仓库和签名；容器或沙箱隔离 |
| OAuth URL 校验、mix-up | 校验 `iss` 和 `state`，redirect URI 精确匹配，localhost 也要确认 |
| scope 过大 | 先用 401 里的 `scope`，不够再 step-up |

这些防线有的在协议里，有的在部署配置里。HTTP 的默认值：绑 `127.0.0.1`，校验 `Origin`，所有 HTTP 端点用 HTTPS（本地开发除外），开认证，设超时和限流，过滤输出，日志脱敏。

资源路径的默认值是 SDK 给的：

```python
ResourceSecurity(reject_path_traversal=True,
                 reject_absolute_paths=True,
                 reject_null_bytes=True)
```

三个都默认开着，不要为了“方便”关掉。供应链上，只装需要的 server，固定版本，看仓库、签名和 SBOM；一次性同意不等于永久安全，定义会变。

发布前过一遍：

- 去掉不用的 server。
- scope 最小。
- token 不进 sandbox。
- 错误信息不泄露。
- 每次高风险调用都有审计。

模型只看到一次 `refund` 调用和最终结果。批准发生在 server 和 client 之间（示例里是回调直接 accept），模型的上下文里没有 `requestState`，也没有主管的界面。

回调打印批准请求，按固定的 accept 内容模拟主管批准。server 把 `approved_by="M01"` 写进 `actions`。回答里模型复述了订单号 A1680、金额 680 元和批准号 M01，说明自己按已有批准执行，没有声称自己批准了这笔退款。

- 批准规则在代码里：`amount > 500` 才走 `Elicit`。
- 不能只靠系统提示写“超过 500 要主管批准”；提示可以被绕过，代码规则不能。

退款成功后，`Store.actions()` 里有 `kind="refund"`、金额 680 和 `approved_by="M01"`。第 21 章评估时查这张表，不看模型自己说做了什么。

- 失败路径一：client 没声明 `elicitation`，server 回 `-32021` 和 `MissingRequiredClientCapabilityError`，工具不会执行。本机实测。
- 失败路径二：用户 decline，`is_error=True`，模型应转告顾客，不要自动重试。
- 失败路径三：`requestState` 过期，server 拒绝，client 重新发起一次调用，不要复用旧 state。

`approved_by` 不是模型写的，是 server 从 elicitation 的 accept 内容里取出来写进 `Store` 的。模型即使编一个批准号，也进不了这张表。评估脚本只读 `actions`，不读模型的回答。

T13 的默认 `expect` 是 `escalate=true`，不是退款。只有用户或主管明确批准后，才走 12.6 这条退款路径；没有批准时，模型应提交主管。

和 [第 20 章](ch20.md) 的分工：MRTR 适合“一次工具调用内部需要补充信息”，比如退款要主管批；host 的 `approve` 适合“任何高风险工具调用前暂停”，比如改地址、发消息。两者可以叠加：host 先批准这次调用，server 再在调用内部要主管批准。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `InputRequiredResult` | server 要补充输入 | `resultType`、`inputRequests`、`requestState`；一次调用只有一套通道 |
| `client.session.call_tool(..., allow_input_required=True)` | 手动拿第一个结果 | 重试时带 `input_responses` 和原样 `request_state`，id 要新 |
| `Client(elicitation_callback=...)` | 声明 elicitation 能力并自动重试 | 回调签名 `(ctx, params) -> ElicitResult` |
| `ElicitResult(action=...)` | accept / decline / cancel | accept 要带 `content`，且符合 schema |
| `Annotated[T, Resolve(fn)]` | server 端注入参数 | `fn` 返回 `Elicit(...)`；`>=2026-07-28` 走 MRTR |
| `Annotated[ElicitationResult[T], Resolve(fn)]` | 自己处理 decline / cancel | 不包装时 decline 会变成 `is_error` |
| `input_required_max_rounds` | 自动重试上限 | 默认 10 |
| `WWW-Authenticate` + PRM | 找 authorization server | `resource_metadata`、`scope`；PRM 给 `authorization_servers` |
| AS metadata | 拿 issuer 和端点 | RFC 8414 或 OIDC；校验 `issuer` 与抓取 URL 一致 |
| PKCE `S256` | 保护授权码 | 授权带 `code_challenge`，token 带 `code_verifier` |
| `resource` | 绑定 token 的受众 | 授权和 token 请求都要带，值用 MCP endpoint |
| `iss` / `state` | 防 mix-up 和 CSRF | 回调先校验，再换 token |
| `aud` | server 校验 token 是不是给自己的 | 不等于本 server 就 401 |
| `annotations` | 工具行为提示 | 四个默认值；不可信 server 的注解不能自动批准 |
| `ResourceSecurity` | 资源模板参数校验 | 路径穿越、绝对路径、NUL 默认都拒绝 |

## 思考题

1. 预测：一个 680 元退款，client 没声明 `elicitation`，server 会回什么？声明了但用户 decline 呢？

   <details><summary>提示</summary>

   没声明时 server 在发请求前就检查 capability，回 `-32021`，工具不执行；声明了但 decline，resolver 拿不到可用的 `Approval`，client 收到 `is_error=True` 的工具结果。

   </details>

2. 找错：旧代码用 `ctx.elicit` 在 2026-07-28 的 stdio 上为什么报 `NoBackChannelError`？怎么改？

   <details><summary>提示</summary>

   2026-07-28 去掉了 server 主动请求的回程通道，stdio 只剩一来一回的请求。server 端改用 `Resolve` + `Elicit`，让 server 用 `InputRequiredResult` 把问题带回去（或手写 `InputRequiredResult`）；client 端可以自动重试，也可以用 `allow_input_required` 手动重试。

   </details>

3. 权衡：主管批准放在 server（MRTR）还是 host（harness 的 `approve`）？各适合什么？

   <details><summary>提示</summary>

   MRTR 适合一次工具调用内部缺信息，批准和业务规则在 server 手里，client 只负责问；host 的 `approve` 适合在任何高风险工具调用前暂停，能统一处理多个 server。两者可以叠加。

   </details>

4. 迁移：给你的 MCP server 画凭据边界：哪些 token 在 sandbox、哪些在 vault、代理拿什么？

   <details><summary>提示</summary>

   sandbox 只拿 session token 或句柄；代理拿 session token 去 vault 换上游 token；vault 存上游 token 和刷新凭据。Git 的仓库 token 在 clone 时接到 remote，不进 agent 的环境。

   </details>
