解析失败要分三类计数，否则一个总失败率看不出该改哪里：

- 格式不对：没有“类别：”，或者整段被 Markdown 包住。
- 值不在允许集合：写“退款”，而标签是“退货退款”。
- 字段缺失：没有订单号，或者订单号写成了“订单号见上”。

解析出的 7 条都在枚举内，另外 3 条没解析出来，没进入枚举判断。订单号缺失 0 条，不代表下一批没有。T24 被归成“物流查询”，真实类别是“政策咨询”，这是类别错，不是格式错。

格式正确和业务正确是两件事。T13 的 680 元退款就是例子：类别写对了，动作仍然要转主管。这一节只量格式和关键词，真正的处置决定在 4.4。

计数可以直接写进程序：

- 解析失败一个计数器。
- 枚举失败一个计数器。
- 字段缺失一个计数器。

日志里留原文。复盘时才知道该改提示，还是该改解析器。

一个结构化方案至少要保证三件事：可解析、值在枚举内、缺字段能发现。做不到这三条，不如让人工填表。下一节开始换接口，但每换一次都拿这三条验收。

空 `content` 常见有三种来源：

- 提示里没有出现“json”，或者没给例子，模型回了普通文本，API 把整段替换成空格。
- 模型把 JSON 包进代码块，前后又加了解释，API 认不出来。
- `max_tokens` 太小，JSON 被截断；这时 `finish_reason` 通常是 `length`，不是 `stop`。

文档里还有一个容易漏掉的分支：如果模型输出无法识别为 JSON，API 会把非 JSON 内容替换成空格，`content` 可能全是空格，`finish_reason` 仍然是 `stop`。所以 `if not content.strip()` 要单独处理，不能直接 `json.loads`。

`max_tokens` 也要给够。被截断的 JSON 不要猜着补括号，直接重试或降级；补出来的对象比没有对象更危险。

```json
{"category": "退货退款", "order_id": "A1659"}
```

上面是提示里那个例子的形状。`json_object` 非空时只约束“这是一个 JSON 对象”，字段名、`order_id` 的格式、`category` 的七个值，全靠提示和客户端手写校验。

{{#fig ch04/json_mode}}

{{#figref ch04/json_mode}} 里最后一步是独立分支：请求、解析、校验都走完，仍要防“空 content”。JSON 模式把格式问题收窄了，但没有把校验省掉。

> **旧资料提示**：Anthropic 2024 年的文章说，代码放在 JSON 里比放在 Markdown 里更难写，因为要多转义换行和引号。今天的 JSON 模式和工具 schema 接过了大部分格式工作，但截断、转义和空 `content` 仍要自己防。

| | JSON 模式 | 强制工具 |
|---|---|---|
| 请求字段 | `response_format={"type": "json_object"}` 加提示里的例子 | `tools=[schema]` 加 `tool_choice` 指定函数 |
| 结果在哪 | `message.content` 字符串 | `message.tool_calls[0].function.arguments` 字符串 |
| 谁约束 | 提示，非空时只保证“是 JSON” | 工具 schema 提示字段、类型、枚举和 `required` |
| 客户端还要做 | `json.loads` 加手写校验 | `json.loads` 加字段/类型校验和业务校验 |

Chat Completions 有一个模式差异：思考模式下不接受 `required` 或指定函数名的 `tool_choice`，会返回 400。

上面的示例用 `extra_body={"thinking": {"type": "disabled"}}` 关掉思考。非思考模式支持指定函数；这个限制不是“兼容层坏了”，是接口本身的边界。

{{#fig ch04/forced_tool}}

这个工具不应该有副作用。函数体只 `return` 参数，不退款、不发消息、不改地址。

它只是“结构化输出的载体”。真正的退款留给业务工具，并且要审批。schema 是请求的一部分，每次调用都要带上它，这也是成本。

如果模型没调用指定工具，`tool_calls` 会是空的。这时不要假设成功：重试一次，或者降级到 `json_object`，再不行转人工。{{#figref ch04/forced_tool}} 的虚线就是这条出口。

Pydantic 能查和不能查的要分开：

## 4.5 四种做法和它们的失败方式

把四种做法放在一张表里，差别主要在“谁保证格式”。`json_schema` 有两条接口，分开列：

| 做法 | 谁保证格式 | DeepSeek 2026-11 是否支持 | 典型失败 | 适合场景 |
|---|---|---|---|---|
| 自由文本 + 正则 | 客户端 | 可用 | 格式变、值不在枚举 | 兜底、人工复核 |
| `json_object` | 非空时 API 保证是 JSON，字段靠提示 | 可用 | 空 `content`、截断、枚举外 | 字段少、暂时不想维护 schema |
| 强制工具 | 工具 schema 提示字段，`tool_choice` 指定函数 | 可用；思考模式要关掉 | 没调用、参数类型不对 | 分类、抽取、提交结果 |
| `json_schema`（Chat Completions） | 服务端 schema | 不可用，返回 400 | 请求直接失败 | 只在支持的服务上用 |
| `json_schema`（Responses `text.format`） | 服务端 schema | 可用 | schema 写错仍会失败 | 需要严格 schema 且能用 Responses |
| Agents SDK `output_type` | 底层用 `json_schema` | Chat Completions 模式 400；Responses 模式可用 | 模式选错就失败 | 确认 SDK 走哪个接口，见[第 27 章](ch27.md) |

这张表只描述 2026-11 的 DeepSeek 兼容接口，换服务商要重新测。`json_schema` 在支持它的服务上是首选；在 DeepSeek 的 Chat Completions 上不是“效果差”，是请求根本发不出去。

兼容层可以接受参数，不代表上游真的支持那个值；400 比静默降级好定位。先查支持列表，再写提示和代码。

OpenAI 2025 年的实践指南把“final-output tool”当作一种退出条件：模型调用一个只收结果的工具，循环就结束。这个思路在 DeepSeek 上仍然有效，等价于本章的 `submit_ticket`。

坏的只是 Agents SDK 在 Chat Completions 模式下把 `output_type` 翻成 `json_schema` 的那条路；Responses 模式下 `output_type` 能用，结构化输出本身没有坏。

选择顺序可以记成四步：

- 能用强制工具就用强制工具。
- 字段少、暂时不想维护 schema 时用 `json_object`。
- 服务端支持 `json_schema` 时用它；DeepSeek 上走 Responses 的 `text.format`，Chat Completions 会 400。
- 正则只做兜底，并且把失败计数留在日志里。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `response_format={"type": "json_object"}` | 非空时得到 JSON 对象 | 提示里要有“json”和例子；查空 `content` |
| `tool_choice={"type": "function", "function": {"name": "submit_ticket"}}` | 强制调用指定工具 | Chat Completions 思考模式返回 400，示例关思考 |
| `Literal[...]`、`float`、`required` | 生成 `enum`、`number`、必填字段 | schema 只是提示，客户端仍要校验；提交工具不要有副作用 |
| `json.loads` | 解析 `content` 或 `arguments` | 截断的 JSON 不要补括号 |
| `BaseModel`、`Field`、`model_validate` | schema 层校验 | 业务规则另查 `store.order()` |
| `Field(ge=0, le=500)` | 金额范围 | 超过 500 转主管 |
| 重试设上限（如 2 次） | 把具体错误回填 | 仍失败转人工，不传坏对象 |
| `response_format={"type": "json_schema", ...}` | Chat Completions 的服务端 schema | DeepSeek 2026-11 返回 400 |
| `text={"format": {"type": "json_schema", ...}}` | Responses 的服务端 schema | DeepSeek 2026-11 可用；字段名与 Chat 不同 |
| Agents SDK `output_type` | 依赖 `json_schema` | Chat Completions 模式 400；Responses 模式可用，见[第 27 章](ch27.md) |

枚举既限制值，也提示了允许的类别；去掉以后，模型可能写出更贴切的同义词，但下游的标签集合对不上。

</details>

3. 权衡：1,000 张工单的批处理，强制工具要多传一份 schema，`json_object` 不用。两种做法各有什么成本？

<details><summary>提示</summary>

算 prompt token、completion token、重试次数和人工复核；schema 在每个请求里都要重发，但可能省掉解析失败。

</details>

4. 迁移：把 `RefundDecision` 的 `amount` 上限从 500 改成“订单剩余可退金额”，Pydantic 还能校验吗，业务校验该放哪？

<details><summary>提示</summary>

Pydantic 只能看到传进去的字段；剩余可退要查 `store.order()`，属于业务层。

</details>
