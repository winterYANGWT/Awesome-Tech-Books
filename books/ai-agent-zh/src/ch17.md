# 第 17 章 两种编排：manager 和 handoff

```text
T05 物流查询 | get_order(A1536) → issue_refund(A1536, 91) | ✗ 多退了 91.00 元
```

单 agent 带 9 个客服工具，T05 只是问“箱子压坏了，你们用的什么快递”，它查完订单却直接退了 91 元。

拆成三个专员能修掉这类错，但多一个 agent 就多一次模型调用，也多一份要维护的提示。先看两条控制路径怎么选、怎么坏。

## 17.1 什么时候拆：复杂逻辑和工具重叠

OpenAI 在 2025-04 的实践指南里给的判据不是工具数量，而是工具是否相似、重叠，以及提示里是否堆了很多 if-then 分支。多于 15 个界限清楚的工具可能没事，少于 10 个重叠工具就可能让模型选错。

| 域 | 工具子集 | 典型信号 |
|---|---|---|
| 物流 | `get_order`、`update_address` | 快递公司、签收日期、配送进度、破损、改地址 |
| 退款 | `get_order`、`search_policies`、`issue_refund`、`escalate_to_supervisor` | 退多少、按哪条政策、超过 500 元要审批；这 12 张单没有超限的，T13 另测 |
| 政策 | `search_policies` | 会员、积分、发票、某地区用哪家快递 |

- 每个域的工具子集不超过 4 个。
- 拆完要有对照：终态是否正确、调用次数、token。
- 没有这三列，拆分只是感觉更好，17.6 会把这三列量出来。

不要按组织架构拆。客服部、物流部、财务部的边界是给人看的，模型只认工具和提示。

按域拆完，再按评估口径检查。本章的判断函数 `problems` 只查终态动作和必提词：退款金额、地址修改、是否升级、回答里有没有 `expect.mention` 列出的词（T01/T03/T24 的快递公司、T12 的“15 天”），不查签收日期、审批记录和条款引用，这三项留给后续评估章。

这三个域不是永久标签，下面任何一项变了都要重新量那三列：

- 工具描述改了。
- 政策加了一节。
- 提示多了一条分支。

## 17.2 manager：把子 agent 包成工具

manager 自己保留对话和用户，把三个专员包成三个工具：`ask_logistics(question)`、`ask_refund(question)`、`ask_policy(question)`。专员只看到自己的系统提示和一个聚焦问题，返回一段摘要；manager 综合摘要后对用户说话。

工具描述写“什么时候问它”，不写“它很专业”。`ask_logistics` 写“查某张订单的快递、签收、破损、改地址，配送规则不要问它”，比“物流专员”有用。`ask_policy` 写“某个地区用哪家快递、能不能指定快递”，T24 才会落到政策专员。

| 工具 | 描述里写什么 |
|---|---|
| `ask_logistics` | 某张订单的快递、签收、破损、改地址；配送规则不要问 |
| `ask_refund` | 退款金额、退货进度、超过 500 元审批 |
| `ask_policy` | 会员、积分、发票、某地区快递、能否指定 |

manager 的四种常见坏法：

- 简单问题也转给专员，多花一次调用。
- 同一个问题问两个专员，拿到两份互相矛盾的摘要。
- 专员摘要丢掉订单号，manager 只能回头再问。
- 专员返回空摘要，manager 把它当成“没问题”。

同一次问答里同一个域出现两次，就去看提示里的边界是不是写重了；计数比感觉可靠。

Agents SDK 的对应写法是 `agent.as_tool(tool_name=…, tool_description=…)`，手写版就是一个普通工具函数，内部跑一次 `harness.run`。两套 API 不要混在一个示例里：本章只做 `as_tool` 的接口对照，不跑 SDK 版，handoff 的 SDK 写法在第 27 章。

manager 可以一轮返回多个 `tool_calls`；`harness.run` 按顺序执行。要并行，得自己写循环或 `ThreadPoolExecutor`，18.3 再讲。

交接要带状态，但不必带全部内部推理；其他顾客的数据、内部笔记、凭据，要在交接前过滤掉。

Agents SDK 0.24 的 `handoff()` 有输入过滤的钩子 `input_filter`：不设时下一个 agent 看到全部历史，设了就由你的函数决定交出去哪些。手写循环就在 `messages[0]` 和工具子集上自己裁。

| 要过滤 | 例子 |
|---|---|
| 其他顾客数据 | 别人的订单、地址、电话 |
| 内部笔记 | “这个顾客很难缠” |
| 凭据 | token、内部 URL |

单向不等于永远不回头。要给专员留一条“明确无法处理才转回”的路，同时用 `max_handoffs` 封顶，否则就会变成 17.4 的乒乓。

工具描述写“什么时候转”，不写“怎么解决”。手写循环里设 `max_handoffs=3`，防止来回踢皮球；这个参数是我们自己的循环参数，不是 Agents SDK 的参数。

Agents SDK 里 handoff 是一种工具或函数：`handoff(agent)` 或 `Agent(..., handoffs=[…])`。调用后新 agent 带着最新对话状态继续跑，`Runner.run(starting_agent, input)` 的循环不变。

## 17.4 两种编排怎么坏：重复派发、乒乓交接

manager 多问一个专员通常还能汇总，代价是多一次调用。重复派发怎么发现，17.2 末尾写了计数方法。这一节只跑 handoff 的乒乓，因为它两次转接就能复现，而且会把回答丢掉。

handoff 的坏法是乒乓：退款 agent 缺政策工具，把对话转回分诊；分诊按“退款归退款”又转回退款。内部 trace 里连续转接，用户没有拿到回答，最后抛 `HandoffLoop`。

为了每次都能复现，这个失败例子把两边都写成硬路由：分诊见退款就转退款，退款见缺政策就转回分诊。真实系统里是提示和工具缺口让模型自己这么绕，次数不固定。

退款专员的工具列表里没有 `search_policies`，这是它转回分诊的直接原因。这次它把 `get_order` 也写进了缺失理由，但工具列表里有 `get_order`，这是模型的措辞错。

计数指标不能只看最后一次回答：每个工单的转接次数、重复调用同一专员的次数、最终谁回答、终态是否正确，都要留下。出错时还要保留“谁转给谁、为什么”的记录，否则分不清是路由错还是专员答错。

| 指标 | 怎么看 | 这次的值 |
|---|---|---|
| 完成的转接 | `transfers` 的长度 | 3 次 |
| 尝试的转接 | trace 里的 `transfer_to_*` | 4 次，第 4 次被拒 |
| 重复专员调用 | 同一个域被问几次 | 退款 2 次、分诊 2 次 |
| 最终回答者 | 最后一条没有 `tool_calls` 的 agent | 没有，抛 `HandoffLoop` |
| 终态 | `store.actions()` | 没有退款 |

防护也分两边。manager 给每个专员写清边界和“不要重复问”；handoff 设 `max_handoffs`、给专员补足工具，并规定“只有明确无法处理才转回”。

## 17.5 上下文和“谁对用户说话”

同一个 T06，manager 的发言者只有 manager 一个，模型调用 5 次；handoff 的发言者是分诊和退款专员两个，模型调用 4 次。manager 多出来的一次调用，花在把专员摘要综合成统一口径上。

统一口径不只是把几段话拼起来。manager 要决定哪些信息对顾客可见，哪些留在内部；handoff 没有这个角色，接手的 agent 直接说。

| 维度 | 单 agent | manager | handoff |
|---|---|---|---|
| 谁持有对话 | 这个 agent | manager | 接手的 agent |
| 谁对用户说话 | 它 | manager | 接手的 agent |
| 上下文怎么传 | 全部历史 | 问题 + 必要字段 | 默认全部历史，可过滤 |
| 怎么返回 | 直接回答 | 专员摘要回 manager，再综合 | 新 agent 直接回答，原 agent 不再参与 |
| Agents SDK 写法 | `Agent(...)` + `Runner.run(...)` | `agent.as_tool(...)` + `Runner.run(...)` | `handoffs=[...]` + `Runner.run(...)` |
| LangGraph 写法 | agent + tools 图（`create_agent`） | supervisor 把子 agent 当工具 | `Command` 改状态，或换一个 agent 节点 |
| 适合场景 | 工具少且不重叠 | 要一个声音、要汇总 | 分诊、转移控制权 |

谁回答决定评估口径：manager 看最终综合答案，handoff 看接手的 agent 是否答对，不能混在一起算。17.6 的正确数是按这个口径分别数的。

两种编排可以组合：分诊先 handoff 给 manager，manager 再调专员；或者 manager 内部用 handoff 做升级。不要把它们当成二选一。

OpenAI 在 2025-04 的实践指南里更倾向代码优先，认为声明式图在动态流程里会变得笨重。这是那篇文章的观点，不是规范；本章用代码优先的普通工具，图的写法留到第 24–26 章。

> **旧资料提示**：2025 年的文章里还有 `Agents.run(agent, [UserMessage(...)])`；0.24 的入口是 `Runner.run(agent, input)`，`input` 可以直接是字符串。

- T05 退了不该退的 91 元。
- T09 没有退款。
- T24 反问订单号而没有答政策。

manager 和 handoff 都对了 7 张，错法不同。manager 错在 T09：退款专员核对后说订单里只有一本、没有可退的第二本，请 manager 先确认顾客的实际情况。manager 自己追问是不是另一张订单，退款没有发生。

handoff 错在 T06：分诊把缺页工单转给物流专员，物流专员识别为印装问题但只登记换货，没有退款，也没有汇总者纠正。

| 配置 | 模型调用 | 总 prompt | 终态正确 |
|---|---|---|---|
| 单 agent | 19 | 29,913 | 5/8 |
| manager | 34 | 24,577 | 7/8 |
| handoff | 27 | 21,426 | 7/8 |

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `ask_<domain>(question)` | 把专员包成 manager 的工具 | 描述写“什么时候问它”；专员只回摘要 |
| `transfer_to_<name>` | 把控制权交给另一个 agent | 单向；交接后原 agent 不再参与 |
| `role: tool` 的“已转接”结果 | 补完这次工具调用 | 不补，下一轮消息不合法 |
| `max_handoffs` | 限制来回转接 | 手写循环的参数，不是 Agents SDK 的参数 |
| `agent.as_tool(tool_name=…, tool_description=…)` | Agents SDK 的 manager 写法 | 和手写 `harness.run` 不要混在一个示例里 |
| `handoffs=[...]` + `Runner.run(...)` | Agents SDK 的 handoff 写法 | agent 的 `name` 用 ASCII，中文会被替换并告警（0.24 实测） |
| `handoff(agent, input_filter=...)` | 过滤交给下一个 agent 的历史 | 签名 `Callable[[HandoffInputData], HandoffInputData]`；默认 `None`，下一个 agent 看到全部历史 |
| 计数四件套 | 调用次数、转接次数、最终回答者、终态正确 | 不要只看最后一次回答 |
| `prompt_tokens` | 比较配置的固定前缀成本 | 单次小不等于总账小；要按调用次数累加 |

4. 估算：manager 有 3 个专员，一次问答至少几次模型调用？handoff 两次交接呢？

   <details><summary>提示</summary>manager 逐个问 3 个专员，至少 4 次自己的调用加 3 次专员调用，共 7 次；一轮并行派发可以降到 5 次。handoff 两次交接至少 3 个 agent 各跑一次，专员查工具还要加。17.6 的 34/27 是 8 张单各问 1 个专员的总数，不能直接反推 3 个专员。</details>
