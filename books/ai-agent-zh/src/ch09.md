# 第 9 章 工具的返回值：信息量、token 预算和错误信息

`get_order` 最早的版本把订单表的整行原样返回：顾客、地址、折扣、两条物流事件。第 8 章那组按表包装的工具更糟：agent 会先把几百条订单记录拉进上下文，T01 一个“到哪了”的问题，输入 token 比用好工具时多出一个数量级（[8.2 节](ch08.md)）。

工具结果写进 `role: "tool"` 消息，下一轮又整段发回模型。工具出错时也一样：如果返回的只是一句 `KeyError: 'customer'`，模型拿到的是一个它没法照着改的错误（9.4 节）。

## 9.1 返回值也是上下文：只给下一步要用的字段

工具结果不是调用完就结束的日志，而是对话的一部分。它作为一条 `role: "tool"` 消息进入 `messages`，之后每次请求都从头再发一遍。一个 1k token 的结果，在第 3 次请求里还要再付一次，直到压缩或裁剪把它清掉（[第 15 章](ch15.md)）。

{{#figref ch09/payload_budget}} 画的是同一张订单的两种结果：固定开销一样，原始结果吃掉 9 格，简洁结果只占 3 格，空出来的格子可以放下一次查询。

`get_order` 现在有 10 个顶层字段。重写时保留 9 个高信号字段：

- `order_id`、`customer_id`、`status`、`created`、`total_paid`、`refunded`、`shipping_fee`；
- `items[]` 只留 `book_id`、`title`、`qty`、`paid`；
- `shipment` 只留 `courier`、`delivered`、`latest`，破损理赔时再加 `damaged`。

姓名、电话和完整地址不进默认返回，`address` 只在改地址、查物流这类场景按需给。内部 UUID、`mime_type`、`256px_image_url`、数据库行号和没有意义的嵌套都不要。ID 用人类可读的 `A1659`、`B12`（Anthropic 在工具设计文章里把这条列为“返回有意义的上下文”）。

### `structuredContent` 不是给模型看的

MCP 2026-07-28 的工具结果可以同时带 `content` 和 `structuredContent`。后者是服务端产出的结果数据，供客户端按 `outputSchema` 校验；规范明确它与模型的 structured outputs 无关，并建议（SHOULD）返回结构化内容时也序列化一份放进 text，照顾旧客户端。

| 字段 | 给谁 | 模型能看到吗 |
|---|---|---|
| `content[].text` | 模型和客户端 | 能，模型读的是这段文字 |
| `structuredContent` | 客户端做 schema 校验 | 通常不能，SDK 另给一份 text |
| `outputSchema` | 客户端校验 structured 结果 | 不改变模型看到的文字 |

所以别指望加一个 `outputSchema` 就让模型更懂返回值。要让模型看懂，改 text 的字段、格式和措辞。

> **旧资料提示**：2025 年的 MCP 教程常把 `structuredContent` 说成“结构化输出”。MCP 2026-07-28 写明它与 LLM 的 structured outputs 无关，前者是客户端校验用的结果数据。

## 9.2 ID、枚举和可读标识：模型拿什么去调下一个工具

模型下一步调用要传的是 ID。返回里必须带可用的 ID，但可读的 `A1659`、`B12`、`C082` 比 UUID 好核对，不容易抄错；UUID 还会提高幻觉和错配，一长串字符既占 token，又没有语义让模型自查。

后端只有 UUID 时，可以在工具内部映射成短 ID 或名称，也可以加一个 `response_format` 枚举：`concise` 只给内容，`detailed` 带 UUID 供后续调用，让模型自己选。

名称更像训练数据，但可能重名；0 起的编号也比 UUID 好读，但同一实体在不同工具里要用同一个编号，格式写进描述和参数：`order_id` 形如 `A1234`，`book_id` 形如 `B07`，`customer_id` 形如 `C042`。不要一轮 `B12`、一轮 UUID。

- 隐私：不要把其他顾客的 ID、姓名和地址放进结果。T27 的 `must_not_mention` 只自动检查了地址“浙江杭州市和平街171号”，ID 和姓名还没有对应的自动检查。

## 9.3 分页、过滤、截断：给返回值定预算

可能很大的返回要实现分页、范围、过滤或截断，并给合理默认值。店里的默认上限是：`search_books` 5 条、`list_reviews` 5 条、`search_policies` 3 节、`get_customer_context` 的最近订单 5 张、`readonly_sql` 50 行。

截断要明说“还有 N 条，用 `cursor`/`offset` 或更窄的 `query`”。MCP 的 `tools/list` 和 `resources/list` 都用 `cursor`/`nextCursor`：请求带 `cursor`，响应带 `nextCursor`，没有这个字段就是最后一页。

分页参数优先用不透明的 `cursor`，`offset` 要让模型算数，容易错。MCP 的列表响应只有 `nextCursor`，没有 `total`/`has_more`，每页条数也由服务端定；自建工具可以再加 `total` 和 `has_more`，字段名要统一（MCP 用 camelCase 的 `nextCursor`，本章示例用 snake_case 的 `next_cursor`）。

- 过滤参数优先于让模型自己筛：`category`、`since`、`status`、`book_id`；
- 能写进 enum 的参数就别让模型自由发挥，日期写清格式（`2026-11-17`）。

坏截断是“结果太多”四个字，没有下一步，好截断是前 N 条加明确的继续方式。

## 9.4 错误信息：写给模型看的恢复指南

错误分两类。MCP 的 JSON-RPC 协议错误（请求结构不合法、未知方法、游标无效）走 `error` 对象，模型通常看不到，也多半改不了。工具执行错误是业务规则、API 失败、参数值不合法（比如日期格式不对），用 `ToolError` 或 MCP 的 `isError: true` 返回给模型。

harness 还会把未知工具和坏 JSON 转成 `role: "tool"` 的错误文字（“错误：没有名为……的工具”“错误：参数不是合法的 JSON”），这两种模型能看到，也能照着改（[3.5 节](ch03.md)）。

错误要写“错在哪、期望什么、下一步怎么做”。店里的坏例子是 `ValueError: invalid`；好例子是：

> 订单 A1673 状态是“已发货”，只有待发货的订单能改地址；可以联系快递转寄，或拒收后重新下单。

三句话分别给了现状、规则和两条出路。错误信息也占 token，不要把整个 schema 或长文档塞进每个错误，给一个正确参数例子就够。

工具内部的 bug 不要吞掉。本章的 harness 回给模型的是 `工具执行失败（KeyError: ...）`，只带异常类型和消息，不写日志，也不带堆栈；生产环境要另记完整堆栈，给模型的话仍要短，不要泄露 key、文件路径和其他顾客信息。

同一参数连续失败两次，就换路或升级到人，`max_turns` 兜底（[第 3 章](ch03.md)）。

| 错误发生在哪 | 表示 | 模型能自己改吗 |
|---|---|---|
| harness 的 `ToolError` | `role: "tool"` 的 content：“错误：……” | 能，文本就是写给模型的 |
| OpenAI Chat Completions | `role: "tool"` 的 content，没有单独的 `is_error` 字段 | 能，取决于文字 |
| Anthropic Messages | `tool_result` 块 + `is_error: true` | 能，文字同样要写清 |
| MCP 工具执行错误 | `CallToolResult` 的 `isError: true` + content | 能，规范建议（SHOULD）把它交给模型 |
| MCP 协议错误 | JSON-RPC 的 `error` 对象 | 多半不能，模型看不到请求结构哪坏了 |

Markdown 表没有更省，因为只有一行数据，表头和分隔行摊不掉；行数多时表头只写一次，才会显出优势。紧凑文本最省，但嵌套一深就不如 JSON 清楚。

Anthropic 文章里 detailed 的 token 约为 concise 的 3 倍，那是字段多少的差别，不是 JSON 换成纯文本。**拿自己的评测选**，不要凭“JSON 一定费 token”下结论。

| 格式 | 优点 | 代价 | 适合 |
|---|---|---|---|
| JSON | 程序好解析，嵌套清楚 | 引号、括号、转义多 | 结构深、要给程序消费 |
| Markdown | 模型读表格自然，表头摊薄 | 宽表容易错列 | 多行同类记录 |
| `key=value` | 最省 token，平铺直读 | 嵌套要靠命名 | 字段少、一层 |
| XML | 标签自解释 | 最啰嗦 | 已有系统要求 |

格式要稳定：同一工具每次返回同一形状、字段顺序固定，`null` 统一处理：省略，或换成“未签收”这类明确值；v2 用后者，不要一处 `null` 一处空字符串。

不要一会儿对象一会儿数组。对模型隐藏技术字段（MIME、URL），但保留后续调用要用的 ID。`response_format` 枚举让模型选 `concise`/`detailed`。

结构化输出（[第 4 章](ch04.md)）和工具返回格式是两件事：前者约束模型生成什么，后者决定模型读到什么。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `get_order_v2` 的 9 个字段 | 订单查询的默认返回 | 不给地址、姓名、电话；`address` 按需 |
| `search_books`/`list_reviews`/`search_policies`/`get_customer_context`/`readonly_sql` | 默认上限 5/5/3/5/50 | 上限写进描述 |
| `cursor`/`limit`/`next_cursor`/`has_more` | 分页 | `cursor` 不透明；`limit` 封顶 |
| “错在哪 + 期望什么 + 下一步” | 错误模板 | 给一个正确参数例子，不塞整个 schema |
| `ToolError` / MCP `isError: true` | 工具执行错误 | 模型能改；协议错误走 JSON-RPC |
| `response_format` 的 `concise`/`detailed` | 让模型选详细程度 | `concise` 不给 ID 就无法后续调用 |
| `structuredContent` | 客户端校验 | 模型读 `content` 的 text |
| JSON / Markdown / compact | 返回格式 | 按评测选，不凭感觉 |

## 思考题

1. 预测：T01 的原始订单行里有两段物流事件，`get_order` 只返回 `latest`。模型会看哪条？只留 `latest` 会丢什么？

<details><summary>提示</summary>

看最后一条的概率最高，因为它最接近“现在到哪了”。只留 `latest` 会丢掉“什么时候揽收、什么时候开始运输”这类过程信息；如果顾客问“为什么三天没动”，过程就有用。

</details>

2. 找错：一个工具返回 `{"id": "3f9c…", "data": {…}}`，agent 退款退错了单。从 ID、字段和格式三处找原因。

<details><summary>提示</summary>

ID 只有 UUID，没有可读订单号可核对；`data` 里可能还有别的 ID，模型分不清哪个是订单；字段名 `id` 没说是订单还是顾客。三处都指向同一件事：返回里缺少能让人和模型都看懂的标识。

</details>

3. 权衡：5 条结果和 500 条结果，分别该分页还是一次返回？为什么？

<details><summary>提示</summary>

5 条一次返回，省一轮调用；500 条必须分页或过滤，否则一次就吃掉大半个上下文，还会把后面的轮次一起拖贵。判断标准是“这次结果会不会在后续每轮重复”，不是条数的绝对值。

</details>

4. 迁移：给你手头一个返回大 JSON 的 API，设计 `concise`/`detailed` 两种返回和一条错误文本。

<details><summary>提示</summary>

`concise` 只留回答当前问题要用的字段和一个可读 ID；`detailed` 补上后续调用需要的 ID 和原始值。错误文本写清缺什么、期望什么格式、下一步调哪个工具，并给一个正确参数例子。

</details>
