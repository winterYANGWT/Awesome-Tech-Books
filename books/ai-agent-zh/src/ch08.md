# 第 8 章 给 agent 设计工具：选什么、叫什么、怎么描述

T01 只问 A1670 到哪了。坏工具集让模型先按订单号查明细、再翻 50 条物流，接着把物流上限加到 500 条、700 条，又数了总数、按日期翻订单、列了全部政策，7 轮、54,362 输入 token 之后，回答里仍然没有“迅达快递”。同样一张订单，`get_order("A1670")` 一次就能拿到快递公司和最新一条物流事件。

这不是模型笨。工具按数据库表拆开，模型只能靠名字猜哪张表里有答案，猜错就翻页，翻页把无关行塞进上下文，越查越远。

## 8.1 模型看到的只有名字、描述和参数

schema 的成本分三块：

- 9 个任务工具合计约 1010 token。
- 24 个 CRUD 包装约 1250 token，描述是空的。
- 如果每个包装补上字段说明和例子，按 200 token 一个算，40 个就是 8k 上下。

这些定义每轮都在上下文里，不会因为模型这次不调用就消失。

同一份工具，三种接口的字段名不同，内容都是 JSON Schema：

| 项目 | Chat Completions | Anthropic Messages | MCP |
|---|---|---|---|
| 工具数组 | `tools` | `tools` | `tools/list` 返回的 `tools` |
| 一项的字段 | `type: "function"` + `function.name`、`description`、`parameters` | `name`、`description`、`input_schema` | `name`、`description`、`inputSchema`、`annotations` |
| 参数 schema | `function.parameters` | `input_schema` | `inputSchema` |
| 结果回填 | `role: "tool"` + `tool_call_id` | `user` 消息里的 `tool_result` + `tool_use_id` | `tools/call` 的 `content` |

模型可能选错工具、参数写错、少调工具，或者调了却误读结果。前三种是工具设计的责任，这一章管，第四种是返回值设计，见[第 9 章](ch09.md)。

这也是两种契约的差别。`get_order("A1659")` 是确定性函数，同样的输入每次结果一样，模型这一侧不确定：它可能不调、调错，或者调了不用结果。工具定义要替这几种情况留好路。

## 8.3 合并与命名：让模型在一堆工具里找到对的那个

{{#fig ch08/namespace}}

MCP 工具名建议 1–128 个字符，区分大小写，只用 `A-Za-z0-9_.-`，同一 server 内唯一。聚合多个 server 时 host 要处理同名冲突：两个 server 都可能暴露 `search`，而 `serverInfo.name` 不保证唯一。

前缀和后缀（`asana_search` 与 `search_asana`）的效果因模型而异，要用自己的评测选。本书优先“动作_资源”：`get_order`、`search_books`，跨 server 时再加服务名和双下划线前缀：`shop__search_books`、`crm__find_customers`。

参数名带名词：

- `user_id` 不写 `user`，`order_id` 不写 `id`。
- 布尔用 `is_`、`has_`，例如 `is_gift`。
- 金额单位写进描述，例如“元”。

模糊的 `search`、`update` 比 `search_books`、`update_address` 更容易选错。

## 8.4 描述和参数：把隐含知识写出来

描述按“给新同事”写，六件事：

- 做什么：一句话说清返回什么，例如“查一张订单，含物流”。
- 什么时候用、什么时候不用：例如“查政策条款，不查订单和物流”。
- 输入格式：id 长什么样，query 用长句还是关键词。
- 边界：单笔上限、时间范围、只读还是可写。
- 一个例子：`order_id="A1234"`。
- 失败怎么办：查不到时换什么参数，或者转给谁。

docstring 第一行是摘要，后面几行写细节，参数说明用 `Annotated`。

参数名和类型要能防错：

- `order_id` 写清格式 `A####`，不要让模型从“订单号”三个字里猜。
- `kind` 用 `Literal["质量问题", "不想要了"]`，不要收自由文本。
- 不要把“按政策算金额”留给模型。

退货政策有两条路。质量问题退全款（书款加运费，签收 60 天内），非质量问题只退书款，运费不退。T06 应退 82（76+6），T09 应退 50（56−6）。

## 8.5 防呆：让错误参数写不出来

{{#fig ch08/poka_yoke}}

防呆（poka-yoke）是改参数，让错误更难发生：

- 路径：绝对路径而不是相对路径。
- 类别：`Literal`/enum 而不是自由文本。
- 订单号：schema 里写 `pattern: "^A[0-9]{4}$"`，长度和前缀都定死。
- 日期：`format: "date"`，不让模型猜“下周三”怎么写。
- 金额：schema 里写 `exclusiveMinimum: 0`；本书的 `issue_refund` 没有这个关键字，0 和负数由 `store.refund` 在运行时拒绝。
- 必填：不确定的参数不给默认值。

专用工具优于通用 `update(order_id, field, value)`：字段名自由，工具就得自己定一套词汇，词汇和数据库、和模型的习惯不一致时，模型只能靠报错试出来。专用 `update_address(order_id, address)` 只有一个动作。

`harness.tool` 只生成基础类型、`Literal` 的 enum、数组和可选值，`pattern`、`format`、`exclusiveMinimum` 这些关键字要自己写进 `Tool.parameters`，或者用别的 schema 生成器。别在注解里写个正则就以为会进 schema。

高风险动作单独命名，并标 `risky=True`：

- `issue_refund`、`update_address` 不藏在通用工具里。
- 第 19、20 章用它做审批。
- 标记本身不是安全边界，`harness.run` 只有在传了 `approve` 时才会问。

默认值要安全。`limit=5` 而不是 1000，不确定的参数设为必填，让模型问用户，而不是猜。防呆不替模型做业务判断，业务规则仍在工具里，返回可读错误（[第 9 章](ch09.md)）。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `@tool` + 类型注解 | 生成 `Tool` 和 JSON Schema | 描述取 docstring，参数说明用 `Annotated` |
| 有默认值的参数 | 不进 `required` | 不确定的参数不要给默认值 |
| `Tool.schema()` | 得到 `{"type":"function","function":{…}}` | 模型只看到这一段 |
| `Literal[...]` | 生成 `enum` | 比自由文本少一类参数错 |
| `pattern` / `format` / `exclusiveMinimum` | 正则、日期、金额下限 | `harness.tool` 不自动生成，要写进 `Tool.parameters` |
| `Toolbox.add` | 按名字注册工具 | 同名静默覆盖 |
| MCP 工具名 | 1–128 字符，`A-Za-z0-9_.-`，同 server 唯一 | 跨 server 加前缀 |
| `risky=True` | 标记有副作用的工具 | 要配合 `approve` 才生效 |

| 做法 | 好处 | 代价 |
|---|---|---|
| 按任务合并（`get_order`） | 调用少、返回聚焦 | 参数变多，要用评测确认 |
| 按服务加前缀 | 多 server 下能分清 | 名字变长，前缀/后缀要实测 |
| 专用工具（`update_address`） | 错误参数写不出来 | 工具数增加 |
| 金额在工具里算（`kind`） | 政策只有一份实现 | 工具要能读订单和政策 |
| 重复跑同一组工单 | 改前改后可比较 | 时间和 token 成本 |

3. 权衡：把 `get_customer_context` 合并成一个工具、返回最近 5 张订单，什么情况下反而更差？

<details><summary>提示</summary>

顾客有几百张订单、目标订单不在最近 5 张时，或者任务只需要一个订单号，返回 5 张只是噪声。还要考虑隐私：不同工单能看到的字段不一样。

</details>

4. 迁移：把你手头一个 REST API 改成 3 个任务工具，列出删掉哪些端点、合并哪些、每个工具的 `required` 参数。

<details><summary>提示</summary>

先列用户要完成的任务，再把同一任务里总要连用的端点合并。`required` 只留任务离不开的 id 或查询词，能默认的安全值给默认值，不确定的设为必填。

</details>
