# 第 10 章 MCP 的架构和三种原语

书店的 9 个工具已经能在 harness 里跑。另一个团队要把同一组工具接进 CRM 助手，还要连一个 CRM：每个应用复制一遍 Python 函数、改 import、重写 schema，就是 3 个应用 × 4 个服务的 12 条适配。

MCP 把这一层固定成消息：应用实现一次 host，服务实现一次 server，消息格式由规范管。但 2026-07-28 版删掉了 `initialize` 握手和协议级会话；在只支持这一版的 server 上，照 2024–2025 年教程写的第一条消息就会错。

## 10.1 从 M×N 到 M+N：host、client、server

{{#fig ch10/host_client_server}}

host 是 AI 应用本身：它创建并管理 client，管连接权限、用户同意和上下文聚合。client 由 host 创建，每个只连一个 server；server 提供 tools、resources、prompts 三种原语，可以是本地进程，也可以是远程服务。

一套适配原来要做三件事：

- 把 Python 函数签名翻译成应用要的 schema。
- 把返回值翻译成模型能读的文字。
- 把异常翻译成各家的错误格式。

每换一个 host 或 server，这三件事都要重写。有协议以后，它们由两端分担：server 声明 schema 和返回内容，host 把消息转成模型能用的工具定义。新增一个 host 只写一份 host 实现，新增一个 server 只写一份 server 实现。

这层结构把适配从 M×N 压成 M+N：开头的 3 个 host 和 4 个 server，原来要 12 条定制适配，现在 host 各实现一次、server 各实现一次，共 7 个。

host 还有一件日常工作：两个 server 都有 `get_order`，`serverInfo.name` 又不保证唯一，所以 host 加前缀再交给模型（[第 8 章](ch08.md)）：

| server | 工具 | host 交给模型的名字 |
|---|---|---|
| 书店 | `get_order` | `shop__get_order` |
| CRM | `get_order` | `crm__get_order` |
| 书店 | `search_books` | `shop__search_books` |

client 一一对应还有安全上的后果：每个 server 只拿到自己需要的那部分上下文，host 是唯一能看到全部对话的地方。M+N 也不是免费：host 要发现 server、合并工具列表、处理重名和权限；这些工作只做一次，但要做对。

协议分两层：

- data layer：JSON-RPC 消息和三种原语。
- transport layer：stdio 和 Streamable HTTP。传输细节在[第 11 章](ch11.md)；协议本身不管模型怎么用上下文。

MCP 2026-07-28 的 Architecture 列了四条设计原则：

- server 容易写：host 承担编排，server 只做窄功能。
- server 可组合：多个 server 能接进同一个 host。
- server 看不到整个对话，也看不到别的 server；上下文聚合留在 host。
- 能力可以逐步加：核心协议只保留最少功能，其余按需协商。

所以 server 不应假设自己知道顾客在别的 server 里说过什么。要跨调用保留购物车、事务这类状态，得由 server 发一个显式的 handle，client 下次把它当普通参数传回来。

## 10.2 JSON-RPC 2.0：一条消息长什么样

{{#fig ch10/jsonrpc}}

四种消息只有两个区别：有没有 `id`，以及带的是 `result` 还是 `error`。请求和响应共用一个 `id`；通知没有 `id`，收到也不回。

`jsonrpc` 固定是 `"2.0"`；MCP 的版本号不放在这里，而是放在每个请求的 `_meta`。`id` 只用来把响应配回请求，不表示会话：同一个连接上可以交错发多个不相关的请求。

| JSON-RPC | OpenAI Chat Completions | Anthropic Messages |
|---|---|---|
| 请求 `tools/call` | assistant 的 `tool_calls[]`，每项有 `id`、`function.name`、`function.arguments`（JSON 字符串） | assistant 的 `tool_use` 块，有 `id`、`name`、`input`（对象） |
| 结果 `content` | `role: "tool"` 的消息，带 `tool_call_id`、`content` | user 的 `tool_result` 块，带 `tool_use_id`、`content`，可带 `is_error` |
| 工具报错 | 通常也放回 `role: "tool"` 的内容里 | `tool_result` 的 `is_error: true` |
| 通知（没有 `id`） | 没有对应物；工具调用是请求-响应 | 没有对应物；工具调用是请求-响应 |

同一件事在三种格式里的字段名不同，语义是同一件事。MCP 的通知在两家的格式里没有对应物：工具调用本身都是请求-响应。

四种信封各一条，按规范手写（第 11 章用 SDK 写真正的 server 和 client）。前四行依次是请求、结果、错误、通知，最后两行是一个缺 `clientCapabilities` 的请求和它得到的错误：

```json
{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientInfo":{"name":"bookstore-host","version":"1.0.0"},"io.modelcontextprotocol/clientCapabilities":{}}}}
{"jsonrpc":"2.0","id":1,"result":{"resultType":"complete","tools":[{"name":"get_order","title":"查订单","description":"查一张订单的金额、状态和物流","inputSchema":{"type":"object","properties":{"order_id":{"type":"string"}},"required":["order_id"]},"annotations":{"readOnlyHint":true,"openWorldHint":false}}],"ttlMs":0,"cacheScope":"private"}}
{"jsonrpc":"2.0","id":2,"error":{"code":-32602,"message":"Unknown tool: refund_all","data":{"tool":"refund_all","available":["get_order","issue_refund"]}}}
{"jsonrpc":"2.0","method":"notifications/progress","params":{"progressToken":"call-7","progress":2,"total":3,"message":"正在核对订单"}}
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"get_order","arguments":{"order_id":"A1680"},"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientInfo":{"name":"bookstore-host","version":"1.0.0"}}}}
{"jsonrpc":"2.0","id":3,"error":{"code":-32602,"message":"Missing required _meta field: io.modelcontextprotocol/clientCapabilities"}}
```

看七处：

- 请求的 `id` 是字符串或整数，不能是 `null`；同一发送方未完成的请求不能重号。
- 结果里的 `result` 必须带 `resultType`：`complete` 或 `input_required`。老 server 不带这个字段时，client 按 `complete` 处理。
- 错误里的标准码是 `-32700`、`-32600`…`-32603`；MCP 自己的是 `-32020` HeaderMismatch、`-32021` MissingRequiredClientCapability、`-32022` UnsupportedProtocolVersion。
- 错误分两层：JSON-RPC 层说请求本身坏了，工具层说业务没通过。前者模型通常改不了，后者应放进结果里让模型读（[10.5 节](ch10.md)）。
- `-32002`（资源不存在）已被 `-32602` 取代；旧 server 还会发，client 仍应接受。
- 通知例如 `notifications/tools/list_changed`、`notifications/progress`；后者带 `progressToken`、`progress`，可带 `total` 和 `message`。
- 每个请求的 `params._meta` 必须带 `io.modelcontextprotocol/protocolVersion` 和 `io.modelcontextprotocol/clientCapabilities`。`clientInfo` 可选；缺必填字段 server 必须回 `-32602`，HTTP 上是 400。

- `tools/list` 的每一项必须有 `name`、`inputSchema`；`description` 建议写，`title`、`icons`、`outputSchema`、`annotations` 可选，`annotations` 里还可以有 `title`。
- `tools/call` 的 `params` 至少有 `name` 和 `_meta`；`arguments` 可选，给了就必须符合 `inputSchema`。server 要求补充输入（MRTR，Multi Round-Trip Requests）时，重试还可能带 `inputResponses`、`requestState`。
- `title` 给人看，`description` 给模型看。
- `inputSchema` 是 JSON Schema，没写 `$schema` 时按 2020-12 解析；`outputSchema` 可选，有它时 `structuredContent` 必须符合它。
- URI 是资源的身份，不一定是真实文件路径；`shop://` 是本书自定义的 scheme。带参数的资源用 `resources/templates/list` 列模板，`shop://policies/{name}` 就是一个模板。
- server 在 `server/discover` 的 `capabilities` 里声明支持什么：`tools.listChanged`、`resources.subscribe/listChanged`、`prompts.listChanged`、`completions`。client 能力现在主要是 `elicitation`；sampling 和 roots 从 2026-07-28 起弃用。

能力声明是“我支持这类方法”，不是“我已经加载了内容”。server 声明了 `resources`，client 才知道可以发 `resources/list`；没声明就发，属于用错协议。

`logging` 也弃用了：stdio server 把日志写 stderr，或者用 OpenTelemetry，不要依赖 `logging/setLevel`。

| 书里的东西 | 对应的原语 | 差别 |
|---|---|---|
| harness 的 `Tool` | tools | MCP 把 schema 和调用固定成 `tools/list` / `tools/call` 消息 |
| 按需读的文件、`before_model` 里挑的上下文 | resources | 用 URI 标识，由应用决定读哪份 |
| 系统提示、提示模板 | prompts | 由用户选，server 提供模板和参数 |

资源与工具的分界不是“读还是写”，而是“谁决定什么时候用”。模型自己决定查政策，走 `search_policies`；host 在启动时或用户点开时加载政策，走 resource。

工具名只在 server 内唯一；两个 server 都叫 `get_order` 很常见，所以 10.1 的前缀不是可选项。

同一个政策可以既有 resource 又有 `search_policies` 工具，但两份内容要从同一份文件生成，否则答案会互相矛盾。

## 10.4 无状态与发现：2026-07-28 的请求里带什么

{{#fig ch10/discover}}

2026-07-28 版没有 `initialize`、`notifications/initialized`，也没有 `Mcp-Session-Id` 和协议级会话。每个请求自带版本和能力，server 不得从前一个请求推断状态。

第一条消息的新旧对照同样按规范手写，前两行是 `server/discover` 和它的结果，后两行是旧教程的 `initialize` 和它得到的错误：

```json
{"jsonrpc":"2.0","id":1,"method":"server/discover","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientInfo":{"name":"bookstore-host","version":"1.0.0"},"io.modelcontextprotocol/clientCapabilities":{"elicitation":{}}}}}
{"jsonrpc":"2.0","id":1,"result":{"resultType":"complete","supportedVersions":["2026-07-28"],"capabilities":{"tools":{"listChanged":false},"resources":{"subscribe":false,"listChanged":false},"prompts":{"listChanged":false},"completions":{}},"instructions":"青石书店客服：先查订单和政策，再回答；退款和改地址有副作用。","_meta":{"io.modelcontextprotocol/serverInfo":{"name":"qingshi-shop","version":"0.1.0"}},"ttlMs":3600000,"cacheScope":"public"}}
{"jsonrpc":"2.0","id":2,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"old-tutorial-client","version":"0.0.1"}}}
{"jsonrpc":"2.0","id":2,"error":{"code":-32601,"message":"Method not found: initialize"}}
```

第一条是 `server/discover`，结果里 `supportedVersions` 只有 `2026-07-28`；这个 server 只支持这一版，旧教程的 `initialize` 只会拿到错误。同时支持新旧两套语义的 server 会用 `initialize` 选旧版协议，`server/discover` 也仍然可用。

这一版还有两处删改：

- 移除了 `ping`。
- 实验性的 tasks 从核心协议移到官方扩展 `io.modelcontextprotocol/tasks`：`tasks/result` 换成轮询 `tasks/get`，新增 `tasks/update`，取消 `tasks/list`。

无状态不是说 server 不能存数据，而是说不能把“上一个请求说过什么”当成这个请求的输入。数据库、购物车、长任务都可以存，但要靠请求里的 id 或 handle 找回来。

`server/discover` 是 server 必须实现、client 可选的 RPC：它返回 `supportedVersions`、`capabilities`、`instructions`，以及 `ttlMs`/`cacheScope`。client 也可以跳过它直接发 `tools/list`；版本不支持时 server 回 `-32022`，`data.supported` 里是可用版本，client 挑一个重试。

两个字段要分清：

- `instructions` 是给模型看的自然语言说明，适合写“先查订单再回答”这类全局约束，不该重复每个工具的 description。
- `serverInfo` 是自报的，协议不验证，只适合显示和排查。

缺必填字段的后果就是 10.2 那段 JSON 的最后两行：server 回 `-32602`，HTTP 上状态码是 400。

这两个错误要分清：缺字段是请求格式问题，换一个版本解决不了；版本不支持是版本问题，改 `_meta` 里的版本才有用。

> **旧资料提示**：2025 年教程用 `initialize` 先握手、用 `Mcp-Session-Id` 维持会话、用 `resources/subscribe` 加 GET SSE 订阅变更。2026-07-28 把这三样都去掉了：版本和能力放进每个请求的 `_meta`，跨调用状态用显式 handle，变更改走 `subscriptions/listen`。

变更通知走 `subscriptions/listen`：一个请求开一条长响应流，`notifications` 里选 `toolsListChanged`、`promptsListChanged`、`resourcesListChanged`、`resourceSubscriptions`。server 先回 `notifications/subscriptions/acknowledged`，之后每条通知的 `_meta` 带 `io.modelcontextprotocol/subscriptionId`。

订阅和缓存还有三条规则：

- 请求级的 `notifications/progress` 不走这条流，它还在原请求的响应流上。
- `ttlMs` 是新鲜度提示，不是轮询间隔：client 需要数据时才检查是否过期。`cacheScope=public` 的结果可能被共享缓存给别的调用方；带用户数据的结果要用 private。
- `tools/list`、`resources/list`、`resources/templates/list`、`resources/read`、`prompts/list`、`server/discover` 这些结果带 `ttlMs` 和 `cacheScope`。`ttlMs` 是毫秒，0 表示立刻过期；本机 mcp 2.3 的 `CacheableResult` 默认 `ttl_ms=0`、`cache_scope="private"`，要缓存就在 handler 里设，或给 `MCPServer` 传 `cache_hints`。

- `tools/call` 的 `params` 至少有 `name` 和 `_meta`；`arguments` 可选，值不合法（格式不对、越界）时回 `isError: true`，未知工具或请求结构不符时回 `-32602`。
- 协议层错误：未知工具、坏 JSON、请求结构不符。这类错误模型一般改不了。
- 工具层错误：业务规则不允许、参数值越界。放进结果里 `isError: true`，模型能读，也可能改对。
- 没有握手，抓包时第一行就是 `server/discover` 或直接 `tools/list`；不要把旧教程的 `initialize` 当成必经步骤。

协议错误和工具错误里，只有工具层错误值得让模型重试；协议错误就算重发，通常还是同一个错误。

算一下暴露成本：

## 速查

| 消息 | 必填字段 | 注意 |
|---|---|---|
| 请求 | `jsonrpc`、`id`、`method`、`params` | `id` 是字符串或整数，不能 `null`；未完成的请求不重号 |
| 结果 | `jsonrpc`、`id`、`result.resultType` | `complete` 或 `input_required`；老 server 缺 `resultType` 时按 `complete` |
| 错误 | `jsonrpc`、`id`、`error.code`、`error.message` | `-32602` 参数错、`-32020` header 不匹配、`-32021` 缺 client 能力、`-32022` 版本不支持 |
| 通知 | `jsonrpc`、`method` | 没有 `id`，不要求响应 |
| `params._meta` | `io.modelcontextprotocol/protocolVersion`、`.../clientCapabilities` | 每个请求必带；`clientInfo` 可选 |

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `server/discover` | server 必须实现，返回版本、能力、`instructions` | client 可选；版本不对回 `-32022`，按 `data.supported` 重试 |
| `tools/list`、`tools/call` | 列工具、调工具 | `arguments` 要符合 `inputSchema`；业务错误放 `isError` |
| `resources/list`、`resources/templates/list`、`resources/read` | 列资源、列模板、读内容 | 资源不存在回 `-32602`，不要回空 `contents` |
| `prompts/list`、`prompts/get` | 列提示、取提示 | 参数都是字符串；缺参数回 `-32602` |
| `subscriptions/listen` | 开一条变更通知流 | 过滤器是 `toolsListChanged` 等四个字段；通知带 `subscriptionId` |
| `ttlMs`、`cacheScope` | 缓存新鲜度和范围 | 本机 SDK 默认 `0` / `private`，要显式设 |
| annotations | 工具行为提示 | `readOnlyHint`、`destructiveHint`、`openWorldHint`；不能当安全边界 |
| 前缀 | host 消歧同名工具 | `serverInfo.name` 不保证唯一，用 `shop__` 这类前缀 |

## 思考题

1. 预测：一个 client 直接发 `tools/call` 但不带 `_meta`，server 会回什么？带了 `_meta` 但版本是 `1900-01-01` 呢？

<details><summary>提示</summary>

缺必填字段是 `-32602`（HTTP 400）；版本不受支持是 `-32022`，错误里有 `data.supported`。两种都不是 `initialize` 的结果。

</details>

2. 找错：一段 2025 年教程先发 `initialize`，在只支持 2026-07-28 的 server 上哪一步失败？为什么错误码不是 `-32022`？

<details><summary>提示</summary>

`initialize` 不是这个 server 的方法，而且请求没有每个请求必带的 `_meta`。错误码由实现定（常见 `-32601` 或 `-32602`）；`-32022` 留给“版本字段存在但不受支持”。同时支持旧版的 server 会接受 `initialize`，按协商到的旧版本服务。

</details>

3. 权衡：政策文档做成 resource 还是 tool？谁控制、什么时候进上下文？

<details><summary>提示</summary>

resource 由应用决定读哪份，按需进上下文；tool 由模型决定调用，适合让模型自己搜条款。两者都做时，内容要从同一份文件生成，别维护两套。

</details>

4. 迁移：给你的服务画 host/client/server 和三种原语，列出哪些是 tool、resource、prompt。

<details><summary>提示</summary>

先列对象和动作：由模型决定何时调用（包括只读查询）→ tool；由应用决定加载的数据 → resource；由用户选择的模板 → prompt。再检查同名工具、权限边界和哪些内容不该让 server 看到。

</details>
