编排者的工具清单只有 `submit_plan`。退款、改地址这类副作用工具在代码的执行层，不在编排者的上下文里；即使模型想越权，也没有可调用的函数。

这套分工也有代价。计划多一次调用，三个工作者各一次，汇总再 1 次。T06 的 5 次调用比第 5 章的链贵，但任务数随工单变化、事先不知道时，这笔钱买的是覆盖面。

## 7.2 委派说明：worker 需要什么

一条能执行的委派说明至少有五项：

- 目标：要回答的具体问题，不是“看看这个”。
- 输入：订单号、书号、顾客编号这类具体 id。
- 输出格式：JSON 字段、长度上限、引用要求。
- 停止条件：查到哪一步就停。
- 禁止事项：不退款、不联系顾客、不猜。

| 委派说明 | 输入数据 | 输出格式 | 引用原句 |
|---|---|---|---|
| 模糊版 | 有 | 缺 | 缺 |

具体版的目标可以写成一句话：“回答有没有人提到缺页或装订问题，列出用到的 review_id。”这句话本身就能被检查：输出里有没有 id，摘要有没有回答这个问题。

工作者看不到主对话。如果主对话里说过“今天不能承诺到账”，而委派说明没写，工作者不会自动遵守；这条约束必须显式复制到 `goal` 或禁止事项里。

- 重复 id：指出哪两个任务同名。

依赖不是执行顺序的装饰。T3 的 `depends_on` 让校验器能检查“回复草稿引用的任务是否存在”；如果 T1 被删掉，T3 应该一起被拒绝，而不是等汇总时才发现少了订单事实。

## 7.4 评估者-优化者：写—评—改

生成者和评估者是两个独立调用：提示不同，职责也不同。评估者只输出 `{"pass", "score", "issues"}`，每条 issue 带 `type`、`quote`、`fix`；它不改写草稿。

评分标准要具体到可检查，每条对应一个 `type`：

- `over_limit`：金额是否超过 500 元。
- `unauthorized_promise`：是否承诺今天到账或直接退款。
- `missing_supervisor`：是否明确说提交主管。
- `privacy`：是否泄露其他顾客信息。
- `citation`：有没有引用政策条款。
- `tone`：是否简洁、给了下一步。

7.4 的评估提示定义了 `over_limit`、`unauthorized_promise`、`missing_supervisor` 和 `tone`，但这次输出只出现 `missing_supervisor` 和 `unauthorized_promise` 两类 issue：`over_limit` 写在 pass 条件里，没有单独成条；`tone` 这次没用上。

## 7.5 评估标准从哪来

评分标准来自三处：

| 来源 | 例子 | 检查方式 |
|---|---|---|
| `tickets()` 的 `expect` | T06 应退 82 元；T27 不得出现某地址 | 代码 |
| `policies/*.md` | 单笔超过 500 元需主管批准 | 代码，必要时评委解释 |
| 本章的语气要求 | 简洁、解释政策、给下一步 | 模型评委，1–5 分 |

前两类是硬标准，能用代码查就不交给模型。软标准才用评委，并要求它引用草稿原句，避免只给一个“感觉不错”。

硬标准用代码，输出的是可复现的布尔值。T06 的金额、T27 的地址、回复里的必提词（`tickets()` 的 `mention`，回答里必须出现的词；`must_not_mention` 相反），都能在毫秒内查完，不需要模型。

|---|---|---|

漏判只有一处，但结论足够清楚：评委的判断不稳定，不能替代规则。

评委的偏差至少有这三种可能：

- 同一模型评自己的输出，可能偏宽松（本章没有量化这一点）。
- 长回答可能显得更“完整”，掩盖越权承诺。
- 评委可能越界去判隐私，也可能放过金额。

所以流程固定为：规则先查，评委补主观项。软标准也要写成可检查的句子，例如“有没有解释政策依据”“有没有告诉顾客下一步”，而不是“写得好不好”。本章只从 30 张工单的 `expect` 里取了两条硬标准做小样本校准，完整的评测集和评委方法留到第 21 章。

## 7.6 组合和边界

7.6 把前面几节接成一条可运行的流水线：编排者计划 → 工作者并行 → 汇总者写草稿 → 规则检查 → 评估者 → 回复或转人工。计划最多 4 个任务；计划不完整时回给编排者重规划 1 次，仍不完整就用固定的订单、政策、评论 3 个任务。

评估最多 2 轮，第 2 轮不过就转人工。金额没超过 500 元时，规则通过后直接退款，不调评估者；T06 走这条，T13 才多一次评估。

T2 的 `digest` 先按 `policy_section` 去重再计数：T06 是 2 节 / 2 条，T13 是 2 节 / 7 条。T13 的 7 条来自两个政策小节，只看“7 条”会高估覆盖面，只看“2 节”会漏掉条款细节。

T06 用 5 次调用：1 次计划、3 次工作者、1 次汇总。规则通过后代码执行 `issue_refund`。

T13 多 1 次评估，第 1 轮就 `pass=True`（score=4，另有一条 issue，type 是模型自己写的“表述模糊”），代码按 pass 不再改稿；最终动作是 `escalate_to_supervisor`，不是 `issue_refund`。两个动作都由代码根据金额和规则决定，模型只写计划和草稿。

- 调用数按工具轮数乘，不是按工作者人数乘：每个工作者自己调 2 轮工具，就是 3 次模型调用（2 轮工具 + 1 次归纳），T06 会变成 1 + 3×3 + 1 = 11 次。
- 本机的 5 次和 6 次只是本章示例的账；真实工单的工作者数量会变，预算要按上限留。

- `gather` 用 `return_exceptions=True` 等齐所有工作者；一个失败时，汇总者用其余结果写“部分信息 + 需人工确认”的回复。这次两张工单都没有失败。
- 不要因为一个子任务失败就丢掉整张工单；全部失败才直接转人工。

什么时候不用这套：

- 物流查询：一次 `get_order` 加模板就够（数据里没有预计送达时间，模板不要替顾客编一个）。
- 政策问答：检索加一次调用就够。
- 退款/投诉：任务数随工单变化，才值得拆。
- 草稿改写：有明确评分标准，才值得加评估者。

步骤固定的物流查询、政策问答用第 5 章的链或路由更便宜。编排者-工作者适合“子任务数量随工单变化”的退款和投诉。

追踪字段不能省：计划里每个任务带 `id`，汇总时写成 `task_id`，工作者带 `worker`，评估打印 `round=1`。第 23 章的 trace 用 `trace_id`、`span_id`、`turn` 组织会话；本章这三个字段在日志和汇总提示里用，没有单独导出。

| 做法 | 谁拆任务 | 子任务怎么并行 | 结果怎么汇总 | 权限怎么隔离 | 代码量 |
|---|---|---|---|---|---|
| 本章手写 | 编排者模型输出计划 | `asyncio.gather` | 汇总者读任务和结果 | 编排者与工作者都没有退款工具 | 约 150 行 |
| LangGraph 子图 + 并行节点 | 图里的规划节点 | 并行边和 reducer | 子图返回值进父图 | 工具绑在具体节点上 | 中，需要图和状态 |
| Agents SDK manager（agents as tools） | manager agent | 由 manager 逐个调工具 | manager 读子 agent 的返回 | 子 agent 的工具各自配置 | 少，封装多 |

| 做法 | 谁评估 | 主要风险 |
|---|---|---|
| 简单 reflection | 同一个模型、同一段提示 | 容易只改语气，放过金额和权限错误 |
| 本章的评估者-优化者 | 独立提示的评估者 + 规则检查 | 仍有偏差，但 issue 可定位、可回查 |

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `submit_plan` | 编排者只提交计划 | `tool_choice` 指定函数名或 `required` 时，思考模式下返回 400；本章因此关闭思考 |
| `tasks/id/role/goal/inputs/output_schema` | 计划的最小结构 | `role` 用枚举，`inputs` 至少一个具体 id |
| `max_length=4` | 限制任务数 | 超过就拒绝，提示合并成 3 个 |
| Pydantic `model_validator` | 校验重复 id、空 goal、未知依赖 | 拒绝理由回给编排者，最多重规划 1 次 |
| `asyncio.gather` | 并行执行工作者 | 每个请求内容要不同；结果按任务顺序打印 |
| `review_id`/`order_id`/`policy_section` | 汇总引用的锚点 | 没有引用就无法回查 |
| `pass/score/issues` | 评估者的输出 | `issues` 带 `type/quote/fix`，评估者不改稿 |
| 最多 2 轮 | 评估循环的上限 | 第 2 轮不过就转人工 |
| 规则检查优先 | 金额、订单号、禁提词 | 评委只补语气、完整性等主观项 |
| `id/task_id`、`worker`、`round` | 编排层追踪字段 | 计划里叫 `id`，汇总时写 `task_id`；第 23 章 trace 用 `trace_id/span_id/turn` |

评论是顾客写的，不是店铺规定。它能提示“有没有同类问题”，但不能替代政策条款；引用时要带 `review_id`，不能把评论当政策。

</details>

3. 权衡：同样 4 个任务，串行和并行在 token、延迟、失败隔离上各有什么代价？

<details><summary>提示</summary>

并行缩短墙钟时间，但每个工作者仍各发一次提示，token 总量不因并行减少；串行不会因为并发而乱序，但一个失败会拖住后面。失败隔离看汇总者能不能用部分结果写出“需人工确认”。2 个工作者是覆盖面更小，不是串行省 token。

</details>

4. 迁移：把“退款评估者”的评分标准迁移到“改地址”场景，哪些硬标准要换、哪些软标准可以复用？

<details><summary>提示</summary>

硬标准换成订单状态是否“待发货”、新地址是否完整、是否真的调用了 `update_address`；语气、解释政策依据、给下一步这些软标准可以复用。

</details>
