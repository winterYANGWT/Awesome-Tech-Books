同一个 host 可以同时有两条连接：一条把 server 当本地子进程，一条连远程 URL。两条连接最终进的是同一套 `MCPServer` 代码，区别只在消息怎么走。

### stdio：一行一条 JSON

stdio 的 client 启动 server 子进程，两边用子进程的 stdin/stdout 传 JSON-RPC。规则很短：

- 每条消息一行 JSON，不能有内嵌换行。
- server 的 stdout 只能写协议消息。
- 日志写 stderr；`print()` 默认写 stdout，会破坏协议。

`StdioServerParameters` 是配置，不是连接。`command`、`args`、`env`、`cwd` 只是描述“怎么启动”，进入 `Client(...)` 的 `async with` 时才真正 `fork` 子进程。

2026-07-28 的 Streamable HTTP 去掉了 GET 流和协议级会话。变更通知不再靠一条常驻 GET 流，而是 client 发 `subscriptions/listen`，server 在这个请求的 SSE 流里持续推。请求本身没有 `initialize` 握手，版本和客户端能力放在每个请求的 `_meta` 里。

本地 HTTP 只绑 `127.0.0.1`。示例里的 `streamable_http_app(host="127.0.0.1")` 会自动打开 DNS rebinding 保护，校验 `Origin`，手写 ASGI 服务时这条要自己加。远程部署则要认证，不能把没有认证的 endpoint 暴露到公网。

| 方面 | stdio | Streamable HTTP |
|---|---|---|
| 谁启动进程 | client 启动子进程 | server 独立运行，client 连 URL |
| 消息 framing | stdin/stdout，一行一条 JSON | 每个消息一个 POST，响应 JSON 或 SSE |
| 必需头 | 没有 HTTP 头 | `MCP-Protocol-Version`、`Mcp-Method`，按方法加 `Mcp-Name` |
| 会话 | 无协议级会话 | 2026-07-28 无协议级会话，变更通知用 `subscriptions/listen` |
| 适用场景 | 本机工具、文件、数据库 | 远程服务、多用户、需要认证 |
| 调试方式 | 看 stderr，手动跑 server | curl、浏览器 Network、server 日志 |

选传输看三件事：server 跑在哪、谁负责启动、要不要认证和多用户。本机工具用 stdio，一行命令就能跑；跨机器、多人用、需要 OAuth 的服务用 Streamable HTTP。

> **旧资料提示**：2025 年的教程先 `initialize` 握手，再保存 `Mcp-Session-Id`，再用一条 GET 流收通知。2026-07-28 把这三件事都改了：没有握手、没有协议级会话、没有 GET 流。`ClientSession` 加 `stdio_client` 仍能连旧 server，但它走旧握手，协商到 `2025-11-25`；本书用高层 `Client`，协商到 `2026-07-28`。


9 个工具都在，顺序就是注册顺序。`required` 来自每个函数的必填参数：`get_order` 只要 `order_id`，`issue_refund` 要 `order_id`、`amount`、`reason`。`issue_refund` 的 `destructiveHint` 是 `true`，`get_order` 的 `readOnlyHint` 是 `true`，`escalate_to_supervisor` 的 `destructiveHint` 是 `false`。

Python 属性是 snake_case（`read_only_hint`），`model_dump(by_alias=True)` 才是线上的 camelCase（`readOnlyHint`）。不写的字段在 Python 里是 `None`，线上省略，client 按规范默认值解释：

| 字段 | 规范默认 | 含义 |
|---|---|---|
| `readOnlyHint` | `false` | 会改环境 |
| `destructiveHint` | `true` | 可能做破坏性更新 |
| `idempotentHint` | `false` | 重复调用可能再次生效 |
| `openWorldHint` | `true` | 可能访问开放世界 |

annotations 只是提示，不是权限。host 不能因为 `readOnlyHint=true` 就跳过审批；真正的边界在 host 的审批回调和服务器的访问控制里。

annotations 只影响 client 的提示和审批 UI，不会替你校验参数；参数校验仍然看 `inputSchema`。

返回值分三种情况：

- 返回 pydantic 模型：SDK 生成 `outputSchema`，结果同时有 `structuredContent` 和 text。
- 返回裸 `dict`：本书的包装函数保留原签名，SDK 不生成 `outputSchema`，结果只有 text JSON。
- `structured_output=False` 强制关掉；`structured_output=True` 要求返回类型可序列化，给裸 `dict` 加 `True` 会在注册时抛 `InvalidSignature`。

错误分两种：业务错误抛 `mcp.server.mcpserver.exceptions.ToolError`，client 收到 `is_error=True`，文本前面带 `Error executing tool get_order:`。未预期异常只给模型 `Error executing tool get_order`，堆栈进 server 日志。所以“订单不存在”这类可预期错误必须自己转成 `ToolError`，否则模型看不到原因。

工具名建议只用 `A-Za-z0-9_.-`，长度 1–128，同一个 server 内唯一。`tools/list` 的顺序在本书里固定为注册顺序，方便缓存和 prompt cache，不要按集合或字典的偶然顺序返回。

这 9 个工具的函数体没有改，`support_tools` 里怎么写，server 里就怎么执行；换传输时也不用重写。

## 11.4 客户端：list_tools、call_tool、内容块和错误

`list_tools()` 返回 `ListToolsResult`。每个 tool 的 Python 属性是 snake_case：`input_schema`、`output_schema`；`model_dump(by_alias=True)` 才是 `inputSchema`、`outputSchema`。

`call_tool(name, arguments)` 返回 `CallToolResult`，三块内容要分开看：

- `content`：内容块列表，常见的是 `TextContent`，还可能是图片、音频、资源链接、嵌入资源。
- `structured_content`：可选的 JSON。有 `outputSchema` 时必须符合它，没有 `outputSchema` 也能返回，工具直接返回 `CallToolResult` 时就常这样。SDK 自动生成 `outputSchema` 只对可序列化的返回类型。
- `is_error`：工具执行错误是 `true`；JSON-RPC 层的错误（坏 JSON、缺必填 `_meta`）会抛异常，不进这个字段。本机 SDK 对未知工具也返回 `is_error=True`。

```text

```

`content[0].type` 是 `text`，`content[0].text` 是 JSON 文本。`get_order` 返回裸 `dict`，所以 `structured_content` 是 `None`。不存在的订单返回 `is_error=True`，文本里带 `Error executing tool get_order:` 和具体原因。

模型只读 host 转成文本的那部分。多块 text 用换行拼接，图片和音频要么转述，要么忽略。不要把整个 `CallToolResult` 的 `repr` 塞给模型，那会把 `TextContent(...)` 这类 Python 表示也带进去。

| `CallToolResult` | host 适配函数的返回 | Chat Completions 的 `role: tool` | Anthropic Messages 的 `tool_result` |
|---|---|---|---|
| `content` 里的 text 块 | 拼成一段字符串 | `content` 字符串 | `content` 的 text 块 |
| `structured_content` | 有 text 就用 text，否则 JSON 序列化 | 同上，模型只看字符串 | 同上 |
| `is_error=True` | 前面加 `错误：` 的字符串 | 同上 | text 块加 `is_error: true` |

这张表是 host 适配层的全部工作：把内容块变成字符串，把 `is_error` 变成带“错误：”的 tool 消息。适配层越薄，模型看到的越接近 server 的原话。

把 MCP 工具转成 harness 的 `Tool`，需要四个字段：`Tool(name, description, parameters=input_schema, fn=...)`。前三个字段构成发给模型的 schema，`fn` 是执行函数。

- `fn` 里调 `call_tool`，`is_error=True` 时返回带“错误：”的字符串，让循环把它放回对话。
- JSON-RPC 层的错误（坏 JSON、缺必填 `_meta`）会抛异常，属于程序 bug。工具层错误（参数不符合 `inputSchema`、业务规则）交给模型。
- 本机 SDK 把未知工具也报成 `is_error=True`，不要假设它会抛异常。

`read_timeout_seconds` 设单次调用超时；`Client` 还有 `input_required_max_rounds`，控制服务端要求补充输入时最多重试几轮，[第 12 章](ch12.md)讲。

## 11.5 同步 harness 接异步 client

{{#fig ch11/bridge}}

`harness.run` 是同步函数，`Client.call_tool` 是协程。不能在工具函数里每次 `asyncio.run`：它新建一个事件循环，而 `Client` 的连接在另一个循环里，协程拿不到那条连接。也不能让 `harness.run` 在事件循环线程里同步等 `call_tool`，因为 `call_tool` 要回到同一个循环才能完成。

`protocol_version` 是 `2026-07-28`，`server_info` 是 `shop 0.1`。能力里有 `tools.listChanged`、`resources`、`prompts`，说明 server 声明了三类原语。配置里没有 `KEY`、`TOKEN`、`SECRET`，密钥不应该放在命令行参数或配置明文里，需要环境变量时用 host 的密钥管理，日志里也不要打印。

日志一律走 stderr：`logging.getLogger(__name__)` 默认写 stderr，stdout 留给协议。HTTP server 没有“stderr 被 host 捕获”这回事，日志走自己的日志系统或 OpenTelemetry。协议里的 `notifications/message` 在 2026-07-28 已弃用，不要把它当主要日志通道。

调试顺序：

1. 用 `Client` 列工具、资源模板、提示，确认数量和名字。
2. 逐个调用：一个成功、一个业务错误、一个超时。
3. 看 `client.protocol_version`、`client.server_info`、`client.server_capabilities`。
4. 还看不清，再用 MCP Inspector 的 CLI/TUI 看原始消息；它需要 Node，本机示例不依赖它。

Inspector 的 CLI 适合脚本：`npx @modelcontextprotocol/inspector --cli ... --method tools/list` 能直接打印 `tools/list` 的原始结果；TUI 适合手动点。Inspector 只是调试工具，不是运行时依赖。

HTTP 还要多看三处：`Origin` 是否被校验，认证头是否带上，endpoint 路径是不是 `/mcp`。

发布前检查：

| 检查项 | 通过标准 |
|---|---|
| 工具名 | 唯一，1–128 字符，只用 `A-Za-z0-9_.-` |
| schema | 必填项和描述完整，`inputSchema` 是合法 JSON Schema |
| 错误 | 业务错误是 `is_error=True`，文本能指导下一步 |
| 密钥 | 不在命令行、配置、日志、工具结果里 |
| stdio | stdout 没有 `print`，日志都走 stderr |
| HTTP | 只绑本地或有认证，`Origin` 受校验 |

> **旧资料提示**：2025 年的教程说 server 可以主动发 `elicitation/create` 请求。2026-07-28 改成 MRTR：server 在结果里返回 `InputRequiredResult`，client 带着 `inputResponses` 重试原请求，见[第 12 章](ch12.md)。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `MCPServer(name, version=..., instructions=...)` | 建 server | 从 `mcp.server.mcpserver` 导入，不是 `fastmcp` |
| `@mcp.tool()` | 注册工具 | 括号不能省；类型注解和 docstring 生成 `inputSchema` |
| `@mcp.resource("shop://policies/{name}", ...)` | 注册资源模板 | 函数参数从 URI 模板来，返回 str |
| `@mcp.prompt(name=..., description=...)` | 注册提示 | 线上参数都是字符串，`prompts/get` 返回 `messages` |
| `mcp.run(transport="stdio")` | 跑 stdio | stdout 只写协议，日志走 stderr |
| `mcp.run(transport="streamable-http", host="127.0.0.1", port=P)` | 跑 HTTP | 本地只绑 `127.0.0.1`，校验 `Origin` |
| `StdioServerParameters(command, args, env, cwd)` | stdio 配置 | 不是连接；进 `async with` 才启动子进程 |
| `Client(StdioServerParameters(...))` / `Client(url)` | 连 server | 高层 `Client` 协商到 `2026-07-28` |
| `list_tools` / `call_tool` | 工具 | `input_schema`、`structured_content`、`is_error` 都是 snake_case |
| `list_resources` / `list_resource_templates` / `read_resource` | 资源 | `resources/list` 可能为空，模板在 `templates/list` |
| `list_prompts` / `get_prompt` | 提示 | 参数名和 `required`；消息是 role + content |
| `ToolError` | 业务错误 | client 收到 `is_error=True`，文本带 `Error executing tool <name>:` |
| `read_timeout_seconds` | 单次调用超时 | 和 `future.result(timeout)` 两层一起用 |
| `MCP-Protocol-Version` / `Mcp-Method` / `Mcp-Name` | HTTP 路由头 | 每个 POST 都带前两个，按方法带 `Mcp-Name` |
| stdio 的 stdout | 协议通道 | 一行一条 JSON，不能有内嵌换行，不能 `print` |

## 思考题

1. 预测：在 tool 里 `print("debug")` 会发生什么？为什么日志必须走 stderr？

<details><summary>提示</summary>

先想 stdout 是谁在读。stdio 的 client 把每一行都当 JSON-RPC 解析；`debug` 不是 JSON，解析失败。即使这次请求的结果还能回来，协议通道已经不可靠了。

</details>

2. 找错：一个 client 用 `ClientSession` 看到 `protocol_version=2025-11-25`，为什么不是 `2026-07-28`？

<details><summary>提示</summary>

`ClientSession` 不会自动握手，要自己调 `initialize()`，所以协商到 `2025-11-25`。它也有 `discover()`，显式调用才会探测 `server/discover`，高层 `Client` 的 `mode="auto"` 才会自动先探测。2026-07-28 没有握手，版本放在每个请求的 `_meta` 里，原始消息见[10.4 节](ch10.md)。

</details>

3. 权衡：同一个 server 用 stdio 还是 Streamable HTTP？列出三个判断条件。

<details><summary>提示</summary>

看 server 跑在哪、谁来启动、要不要多用户和认证。本机工具用 stdio 简单；远程、多用户、需要 OAuth 的用 HTTP。还要看调试方式：stdio 能直接看 stderr，HTTP 要看 server 日志和 Network。

</details>

4. 迁移：把现有 REST 服务包成 MCP server，哪些做 tools、resources、prompts？

<details><summary>提示</summary>

有副作用、需要模型决定参数的动作做 tools；应用想预先加载的文档、配置、模板做 resources；用户会主动选择的话术做 prompts。不要把整个数据库表做成资源。

</details>
