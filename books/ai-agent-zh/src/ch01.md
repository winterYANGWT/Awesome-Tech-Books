## 1.2 什么时候不该用 agent

先把选择写成四个问题，前两问先排除简单做法，后两问决定要不要把控制权交给模型：

1. 回复是否只需一段文字或一次检索？是→单次调用。
2. 步骤能否用代码写死？是→固定流程。
3. 错误代价是否高到必须可审计？是→把日志、审批和回滚写进固定流程，或转人工。
4. 输入是否必须靠多轮工具反馈才能澄清？是→agent；否→转人工或先补检索，不要再进循环。

顺序不能换：前两问最便宜、最可测；第三问决定要不要把控制权收回来；只有第四问答“是”，才值得让模型在循环里改下一步。

## 1.3 agent 循环长什么样

{{#figref ch01/three_runs}} 把三次运行叠在一条时间线上。agent 段的 7 行就是这一节要看的循环。

循环只有四步：

1. 把工具清单和对话发给模型。
2. 模型返回“要调用哪个工具、参数是什么”。
3. 程序执行工具。
4. 把结果放回对话，再问。

字段名、消息格式和错误处理在第 3 章；这里只看现象。

一个 agent 由模型、工具和指令三样东西组成，循环把这三样串起来。四步里只有第 2 步是模型做的，其余三步都是程序。模型的价值在第 2 步：它可以根据上一轮的结果，改变下一轮要调用的工具。

模型自己不记得上一轮。每轮请求都重发系统提示、用户原话、每次工具调用（tool calling）和每次工具结果。

```python
{{#include code/ch01/1_3_loop_trace.py}}
```

这次运行的输出：

```text
{{#include code/ch01/1_3_loop_trace.out}}
```

第 2、3、4 次请求各比上次多 2 条：一条 `assistant`（带 `tool_calls`），一条 `tool`（结果）。第 4 次请求有 8 条消息：`system`、`user`，加 3 对 `assistant`/`tool`；模型拿到退款结果后才写最终回答。

历史越长，每轮重发的 token 越多；第 2 章会把这条曲线算出来。

停止条件只有两类：

- 模型不再要求调用工具。
- 达到轮数上限。

工具报错不是停止条件；错误文字要交给模型让它改（第 3 章）。

轮数上限不是可选项。模型可能一直要工具，程序必须有一个数字让它停；这个数字多大，取决于工具的价格和失败的代价。

循环本身没有错误处理、日志和正式上限；`call_tool` 只把 `ShopError` 转成文字，`for turn in range(1, 8)` 只是防止示例跑飞。第 3 章把它补成 `harness.run`，后面各章直接复用。

| 写法 | 谁决定下一步 | 停止条件 | 代码量 |
|---|---|---|---|
| 本章裸循环 | 模型返回的 `tool_calls`，程序只执行 | 没有 `tool_calls`，或 7 轮用完 | 循环约 30 行，工具定义另算 |
| OpenAI Agents SDK 的 `Runner.run` | SDK 的 run loop 读模型输出 | 最终输出工具，或没有工具调用 | 几行调用，循环在 SDK 里 |
| LangGraph 的 assistant↔tools 图 | `tools_condition` 检查最后一条消息 | 没有工具调用就走到 END；另有递归上限 | 两个节点加条件边和回边 |

harness 也会过时：它编码了对模型能力的假设；模型变强后，旧的重试、压缩和轮数上限要重新检查（第 22 章）。

## 1.4 把选择写成规则

{{#fig ch01/decision_tree}}

这棵树就是 1.2 的四问：先单次，再固定，写不死时看要不要审计、要不要多轮工具，最后才是 agent，出口是转人工和先补检索。不要因为“agent 听起来更强”跳到最后一问。

6 张代表性工单在树上停在哪里：

| 工单 | 停在哪一问 | 做法 |
|---|---|---|
| T27 | 能一次回答？是 | 单次调用 |
| T01、T12、T14 | 步骤固定？是 | 固定流程 |
| T13 | 要可审计？是 | 转人工；agent 可以先查和判断 |
| T06 | 多轮工具？是 | agent |

下面的表不是打分表，是失败方式的对照。单次调用失败在编造，固定流程失败在漏分支，agent 失败在选错工具或停不下来。

| 做法 | 实现成本 | 每次请求的延迟 | 可测试性 | 典型失败 |
|---|---|---|---|---|
| 单次调用 | 最低，一次请求 | 一次往返 | 容易，固定输入输出 | 编造金额或状态 |
| 固定流程 | 中，每个分支都要写 | 一次模型调用加本地代码 | 高，每个分支可单测 | 没覆盖的分支（T14） |
| agent | 高，工具、循环、日志 | 这次 4 次，工单不同会变 | 低，只能重复 N 次统计 | 选错工具或轮数失控 |

agent 每一轮都重发系统提示、工具定义和全部历史，这笔账在第 2 章用 `usage` 算，成功率怎么统计在第 21 章。示例都在 `Store()` 的内存副本上跑，失败可以丢掉重来，生产环境的沙箱和凭据隔离在第 22 章。

Anthropic 把 agent 设计的三条原则写成简单、透明、ACI（agent-computer interface）：选择表对应简单，逐轮打印对应透明，工具接口设计留给第 8 章。

| 说法 | 边界 | 对本书的影响 |
|---|---|---|
| Anthropic：workflow 是代码写死路径，agent 是模型自己决定过程和工具 | 两者都叫 agent 类系统；只在确实提升结果时增加复杂度 | 本章用“步骤能否写死”区分；第 5–7 章讲 workflow |
| OpenAI：agent 是能独立完成任务的系统，用 LLM 管流程、有工具、有护栏；单轮聊天和分类器不算 | 适合复杂判断、难维护的规则、非结构化输入 | 退款里要边查边判断的才用 agent；T12/T14 这类固定结论和物流查询用固定流程 |
| Anthropic 的上下文工程文章：agent 是“LLM 在循环里自主使用工具” | 运行时检索比预先检索慢；工具选不好会浪费上下文 | 本章的循环是这个定义的最小实现；检索和上下文留到第 13–14 章 |

三家的说法用词不同，边界却一致：能用代码写死的，不要交给模型；必须根据工具结果改下一步的，才让模型进循环。

## 1.5 放回整个系统：一个入口，几条路线

前几节是一张一张地选做法。上线以后顾客只看到一个入口，物流、退款、闲聊混在一起进来，总得先决定每张工单走哪条路。这件事交给谁，是客服系统架构上最大的分歧。

资料里有三种常见的答法：

| 做法 | 谁决定路线 | 出处 | 好处 | 代价 |
|---|---|---|---|---|
| 一个 agent 包办 | 模型：简单的直接回答或只调一次工具，复杂的多查几轮 | OpenAI 指南建议先把单个 agent 做满；LangGraph 入门课的 router 让模型在“直接回答”和“调工具”之间选 | 一套提示和工具，好维护 | 简单工单快不快，看模型自觉；每次请求都带全部工具定义；“物流单只查一次”没法写单元测试 |
| 先路由再分派 | 分类器：规则或小模型 | Anthropic 的 routing：一般问题、退款、技术支持分到不同的流程、提示和工具，简单问题交给小模型 | 每条路线单独改；快速通道由代码保证 | 用模型分类要多一次调用；分错了整条链跟着错 |
| 分诊 agent 加 handoff | 分诊 agent 把对话交给专门的 agent | OpenAI 指南的 decentralized 模式：triage agent 把订单问题交给订单 agent | 每个 agent 提示短、工具少 | 交接可能来回踢；谁对顾客说话要设计 |

三种做法不互斥。两份指南都强调的有三条：

- 先从简单的做起，确实需要才加复杂度。
- 规则写进代码，不靠模型自觉。
- 退款这类高风险动作要有人兜底。

把它们拼起来，就是本书推荐的结构：

| 层 | 做什么 | 书店里的例子 | 细节 |
|---|---|---|---|
| 入口分诊 | 先过输入护栏；规则认得出的直接分走，模糊的交给小模型；分不准就进 agent，不去猜 | T28 要求“忽略之前的指令”，护栏直接拒绝；“订单号 + 到哪了”走物流模板 | [第 5 章](ch05.md)、[第 19 章](ch19.md) |
| 快速通道 | 模板、检索加一次调用、写死的分支 | 1.2 表里归到单次调用和固定流程的 23 张 | 本章 1.2 |
| agent | 边查边判断的工单；工具按类别收紧 | T06–T11 | [第 3 章](ch03.md)、[第 8 章](ch08.md) |
| 工具层 | 硬规则写在工具里，所有路线共用；按读、写、付钱分风险 | `store.refund` 遇到超过 500 元又没有主管批准的退款就拒绝 | [19.5 节](ch19.md) |
| 人工 | 高风险动作；超过失败阈值 | T13 的 680 元；agent 轮数用完还没结束 | [第 20 章](ch20.md) |
| 记录 | 每单记下路线、轮数、工具序列、`usage`、停止原因 | 看简单工单是不是真的一轮结束，分诊分错了多少 | [第 21 章](ch21.md)、[第 23 章](ch23.md) |

工具层最容易被忽略。快速通道和 agent 最后调用的是同一批工具，硬规则放在这里，工单走哪条路都兜得住。“教辅拆封不退”现在没写进 `store.refund`，所以 1.1 的固定流程漏了这一支就能把 T14 退掉，挪进工具层以后，固定流程和 agent 都退不出去。

分诊先用规则。第 5 章在这 30 张工单上量过：先用模型分类再处理，比一个大提示多花不少 token，终态并没有更好。所以规则能判的不花模型调用，模型只分规则拿不准的那部分。

常见的想法是整个客服做成一个 agent，简单问题让它少调几次、快速返回。方向没错，问题在“快速返回”靠什么保证：

- 只写进提示：模型倾向于少调，但不保证。
- 分诊时把高频、步骤固定的工单截走：代码保证。
- 把固定流程包成一个工具，比如 `track_order` 直接返回写好的物流回复：模型调一次就能结束，但调不调仍由模型决定。

反过来，固定流程里也可以嵌一次模型调用写回复，像 1.1 的 T06 那样。

落地的顺序可以这样走：

1. 先上一个 agent，硬规则放进工具层，每单都记录。
2. 跑一段时间看记录，把量大、步骤稳定的类别（这里是物流和政策咨询）拆成快速通道，分诊先用规则。
3. 规则分不清的再加小模型分类；某类工单的提示和工具多到互相干扰时，再拆成专门的 agent（[第 17 章](ch17.md)）。

这和两份指南的建议一致：OpenAI 主张逐步加工具、先把单个 agent 做满，Anthropic 主张只在确实提升结果时增加复杂度。路线也不是一次定死的：可以先用强模型建基线，再把简单的路线换成小模型（[第 5 章](ch05.md)）。

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `chat.completions.create(model, messages, tools, tool_choice)` | 发一次请求 | 不传 `tools`，模型就只能凭文字回答 |
| `messages` 的 `system` / `user` / `assistant` | 对话角色 | `tool` 角色和 `tool_call_id` 在第 3 章 |
| `store.actions()` | 判终态 | 看 `kind` 和 `detail`，不看回复 |
| `store.order(id)` | 查订单 | `total` 是实付，含运费 |
| `store.refund(id, amount, reason)` | 退款 | 业务规则不允许时抛 `ShopError` |
| `store.search_policies(query)` | 查政策 | 返回最相关的 3 节原文 |
| `support_tools(store, include=(...))` | 标准客服工具 | 本章手写工具，不 import harness |
| `SUPPORT_PROMPT` | 标准系统提示 | 单次调用用了更短的本地提示 |
| 选择顺序 | 单次调用→固定流程→审计/转人工→agent | 写不死且必须多轮工具才用 agent |
| 入口分诊 | 规则先分，模糊的交给小模型 | 用模型分类要多一次调用；分不准就进 agent |
| 工具层的硬规则 | 所有路线共用的最后一道检查 | 没写进工具的规则（教辅拆封）挡不住漏了分支的固定流程 |
| `max_turns` / `stop` | 循环上限和停止原因 | 第 3 章的 `harness.run` |

## 思考题

1. 给 T13 的订单和一句“顾客要求全额退款”，分别写出单次调用、固定流程、agent 的第一步，猜哪个会先犯错。

<details><summary>提示</summary>

单次调用看不到 680 元和“超过 500 元”的规则；固定流程要先写“金额 > 500”的分支；agent 的第一步可能是 `get_order`，也可能先查政策。

</details>

2. 如果 `1_1_agent_loop.py` 把某一轮的工具结果放错位置，或者少放一条，第几次请求会失败、错误长什么样？

<details><summary>提示</summary>

每个 `tool_call_id` 都要有一条 `role: tool` 的消息配对；少一条，下一次请求会收到 400：“An assistant message with 'tool_calls' must be followed by tool messages…”。字段规则在第 3 章。

</details>

3. 把 30 张工单全交给一个带全部客服工具的 agent，T01 这类物流单可能出什么问题？说两种让它稳定地一轮结束的办法，以及各自的代价。

<details><summary>提示</summary>

可能不查单就答（编出到达时间），也可能多查几次；每次请求都带全部工具定义。一种办法是分诊时用规则截走，走 `get_order` 加模板，代价是多维护一条路线，还要处理分错的情况；另一种是把物流包成一个 `track_order` 工具，模型调一次就结束，代价是这次请求仍带着全部工具定义，模型也仍可能不调它。

</details>

4. 把“先查订单再查政策”换成“先查库存再查配送”，哪些部分能复用，哪些必须重写？

<details><summary>提示</summary>

循环骨架、消息回填、把工具结果转成文字的做法能复用；具体工具的名字、参数和 schema，工具实现，系统提示里的判断规则，终态检查要重写。库存和配送的失败代价也不同。

</details>
