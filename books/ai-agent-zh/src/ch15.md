|---|---|---|---|

摘要检查这次是：`原卡=False 82.00=True 1–3=False 短信=True`。最后一次摘要没有逐字保留“原卡”和“1–3 个工作日”，但写了“原路退卡”和“最晚 11-20”。

最终答案从最近几条原文和摘要里补回“原路退回您原来的银行卡，不进账户余额”。字段检查要查语义，不能只查字面。

摘要比 300 字长：第一次 511 字，第二次 499 字。这符合“先求全再求精”。至少要保留：

- 订单号和金额。
- 退款去向和用户约束。
- 已完成的动作和结果。
- 未决事项和下一步。
- 引用过的政策条款。

压得太狠，后面就找不回来。

- 压缩不可逆：示例把旧消息从上下文里删掉了，只保留摘要和最近 4 条；真实系统要在压缩前把原消息另存成 JSONL，第 22 章用 session 日志做这件事。
- 已经激活的 Skill 正文这类规程也不该进摘要：固定在系统提示里，或在压缩后重新注入（16.2 会讲）。

摘要调用也花 token。两次摘要合计约 4,200 token。如果每两轮压一次，摘要费会超过省下的历史，触发点要放在里程碑或预算线，不要每轮都摘要。

- 保留 ID、金额、状态：`[已清理 get_order(A1659)：金额 82.00，状态 已签收]` 比“已清理”有用，最后回答问题就靠这几个字段。
- 错误结果也要留错误类型和原因，不要只写“失败”。

第 8 轮的实际 prompt 是 1,689，答案仍是 82.00 和“原路退回你原来那张卡”。清结果没有额外模型调用，只花了本地计算。

| 做法 | 改动 | 配对 | 什么时候用 |
|---|---|---|---|
| 换 stub | 只换 `content` | 不变 | 旧工具结果很长 |
| 删整条 tool | 删消息 | 要连 `tool_calls` 一起删 | 结果完全没用 |
| 摘要 | 换整段历史 | 不涉及 | 清完还超预算 |

顺序是先清结果，再压缩。不要反过来：先摘要、再发现工具结果本来就可以丢，等于多花一次摘要调用。清完还超预算，才走 15.2。

清之前先算一笔账：旧工具结果占多少、保留最近几条、清完预计多少。算不清就先打印前三条的字符数，别凭感觉删。

写笔记的时机是里程碑，不要每轮写。这次是 `WRITE_TURNS` 把时机写死，真实系统要靠提示或状态判断，不能只靠模型自觉。写得太勤，笔记会变成另一份过期文档。

- 五节齐全。
- 整份不超过 500 token。
- 只写事实和出处，不写猜测。

`write_notes` 整文件替换：先写临时文件，再 `os.replace`，避免半截文件。五节缺一节就抛 `NotesError`，让模型补。超过 500 token 也拒绝。

笔记是给 agent 自己看的，不是给顾客的回复。五节里最关键的是关键事实和待办，它们决定重置后还能不能继续。不要把内部猜测、其他顾客的信息写进去，重置后先读笔记，不要重复问订单号。

> **旧资料提示**：Anthropic 在之前的 harness 里给 Sonnet 4.5 加了 context reset，用来缓解它接近上下文上限时提前收尾的“context anxiety”。2026-04 换到 Opus 4.5，这个行为消失，resets 成了死重。重置不是每个模型都需要的固定件，换模型或升级后要重新测。

摘要却写成“未取得三本书的 book_id，评论查询无效”，把 B12 的有效评论和 B07 的线索都丢了；主 agent 只能按摘要说不能确认。

`gaps` 是子 agent 不能直接问用户时的出口。需要澄清的问题写进 `gaps`，由主 agent 决定是否追问；不要让子 agent 猜，也不要让主 agent 把摘要当成全部证据。

| 合同项 | 这次写的 |
|---|---|
| 目标 | C082 半年内有没有同样缺页的订单 |
| 输出格式 | 结论 + 证据（书号、订单号、日期）+ `gaps`，合同写 300 字 |
| 工具 | `customer_orders`、`get_order`、`list_reviews`、`search_policies` |
| 边界 | 不联系顾客，不替主 agent 退款 |
| 交回 | 摘要 + `gaps` |

合同有两处和工具对不上：

- 写 300 字，这次摘要 396 字；
- 要“评论编号”，但 `list_reviews` 只返回星级、正文和日期，没有 id。

子 agent 只能写“未取得”。要么给工具加 `review_id`，要么把合同改成“书号 + 日期”。

成本是额外的模型调用和重复的固定前缀。子 agent 只适合可并行、上下文大的探索，需要共享细微状态的对话（退款谈到第几轮、顾客刚改了什么）不适合拆出去。先算调用费，再决定开不开。

- 主 agent 需要逐条核对金额和条款时，摘要不够，别开子 agent。
- 只需要一个结论时，子 agent 才划算；证据不够就补查。

摘要要带证据 ID 和文件路径。更稳的做法是子 agent 把原始结果落成 JSON/Markdown，主 agent 只读引用。这样能避免多段转述的“传话游戏”，Anthropic 的多 agent 调研文章也提到这一点，18.6 再用。

## 15.6 三种方法怎么选

{{#fig ch15/choose}}

三种方法不是互斥选项：压缩、笔记、子 agent；压缩又分清工具结果、按 token 裁剪和摘要。超预算时按这个顺序判断：

- 旧工具结果多，先清；
- 清完还超，再看有没有明确的里程碑，有就写笔记；
- 还需要大范围、可并行的探索，就开子 agent；
- 这些都不够，才做摘要压缩。

摘要最贵，也最容易丢细节，放在最后。

| 方法 | 何时用 | 丢什么 | LangGraph 对应 |
|---|---|---|---|
| 压缩：清工具结果 | 旧工具结果多、推理历史不长 | 原始 JSON 细节，保留 ID、金额、状态 | 无专用接口；节点里改 `ToolMessage.content` |
| 压缩：按 token 裁剪（对照） | 只要最近几轮；按条数/token 硬切，见 [13.4 节](ch13.md) | 旧对话和工具结果 | `trim_messages(...)` |
| 压缩：摘要 | 来回确认多、要保留对话流 | 细节；不可逆 | `summary` 状态 + `RemoveMessage` |
| 笔记 | 有明确里程碑的长任务 | 没写进笔记的细节 | 文件或 `Store`（`BaseStore`、`InMemoryStore`） |
| 子 agent | 可并行、上下文大的探索 | 原始结果；只剩摘要 | 子图（subgraph） |

压缩保留对话流，适合来回确认多的客服；代价是摘要可能丢细节，而且不可逆。清结果最便宜，但不能解决“早期约束被淹没”：它只动工具结果，不动用户消息的位置。

笔记适合有明确里程碑的长任务。它要在里程碑由 harness 提示或拦截来写、按时读，写得太勤会变成另一份过期文档。子 agent 适合并行探索、上下文隔离，代价是额外调用和摘要损失。

同一场 30 轮退款对话，主 agent 需要看到的是订单号、金额、顾客约束和审批状态，这些写进笔记最省；把每张订单的明细都交给子 agent，主 agent 只读摘要，适合查历史，不适合谈当前这一单。组合时先做便宜的：

- 清结果不花模型调用；
- 笔记在里程碑写几次，读写也占模型调用；
- 摘要和子 agent 的调用更多。

> **旧资料提示**：Anthropic 的上下文工程文章写于 2025-09，提到 memory tool 公测。2026-11 用本地 `NOTES.md` 和文件工具复现同样的能力，不依赖某个产品功能。接口名以当时的文档为准。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `before_model(messages)` | 调用前决定发什么 | harness 提供，返回新列表；本章为看清每一步手动改 `messages`，没有挂这个钩子 |
| 摘要保留字段 | 订单号、金额、用户约束、未决事项、政策出处 | 先求全再求精；每次摘要后检查 |
| 工具结果 stub | 换掉旧 `content` | 保留 `tool_call_id`、ID、金额、状态；消息不能乱删 |
| `NOTES.md` 五节 | 目标、已完成、待办、关键事实、来源 | 整份 <500 token；在里程碑写，由 harness 提示或拦截 |
| `read_notes()` / `write_notes(text)` | 读、整文件替换 | 先写临时文件再 `os.replace` |
| 子 agent 合同 | 目标、输出格式、工具、边界 | 通常 1,000–2,000 token 摘要 + `gaps`；本次约 231，合同要和工具字段对得上 |
| `trim_messages(...)` / `RemoveMessage` | LangChain 的消息裁剪和删除（`langchain_core.messages`），LangGraph 里常用 | 只作对照；`RemoveMessage` 要和 `add_messages` 一起用 |
| 原始记录 | 压缩前另存 JSONL | 摘要不能替代原始日志 |

   </details>

3. 权衡：一场 30 轮的退款对话，用笔记还是子 agent？把“谁需要看到细节”说清楚。

   <details><summary>提示</summary>

   主 agent 要继续谈这一单，需要订单号、金额、顾客约束、审批状态，这些用笔记；子 agent 拿不到这些细微状态，只适合查历史订单、并行翻评论。如果子 agent 查到的证据要影响当前退款，摘要必须带证据 ID，主 agent 还要能回读原始文件。

   </details>

4. 估算：12 轮、每轮新增 2k token、每 6 轮压缩一次，压缩调用 1.5k，和不压缩相比省多少？什么情况下反而更贵？

   <details><summary>提示</summary>

   假设压缩后摘要和保留原文共 4k，压缩在第 6、12 轮提问前发生，压缩后还要加当轮新增的 2k。不压缩累计约 2k×(1+…+12)=156k；压缩后第 1–5 轮 30k，第 6–11 轮从 6k 起每轮加 2k 共 66k，第 12 轮 6k，加两次摘要 3k，合计约 105k，省约 33%。如果压缩太频繁、摘要写得比省下的历史还长，或者压缩后马上又长回去，摘要费会吃掉省下的部分。

   </details>
