# 第 18 章 多 agent 调研系统

运营问：“2026 年 Q3 退货率为什么上升，Q4 为什么回落？”单 agent 算出 Q3 是 18.3%，也抓到批次和快递两条，却漏掉退货期，政策引用 0 处。

调研是开放、路径依赖的：先查什么、下一步查哪里，取决于上一步。图里是本章的做法：主 agent 拆题，三个子 agent 并行查，最后只交回带来源的摘要。

|---|---|---|---|

| Q3 | 208 | 38 | 18.3% |
| Q4（到 11-16） | 98 | 8 | 8.2% |

这次单 agent 的失败不是“不会查”，是两条线都查得很扎实，却没有一张清单提醒它还缺政策；预算也在这一步用完了。它没有把问题拆成互不重叠的线，于是“查到哪里算够”只能由模型自己判断。

覆盖检查也有盲区：它只按关键词和数字匹配，措辞换了就可能漏判。正文引用这次运行的输出，统计结论仍要看 18.5 的 5 个问题 × 3 种配置。

这次回答还有三处口径要指出来：

- 20 笔缺页/装订占的是 38 张有退货的订单（52.6%），不是 42 条退货记录（20/42=47.6%）。
- 订单数据只到 11-16，回答里的“截至 11-17”把今天当成了截止日。
- 迅达 10/39=25.6% 是 Q3，18.3 的 16/65=24.6% 是 Q3+Q4。

季度总量算对了，但分母和时间窗写错；只看数字有没有出处，抓不到这类错。

- Anthropic 2025-06 的文章把搜索说成压缩：子 agent 在各自窗口里探索，只把最重要的 token 交回主 agent。
- Anthropic 2025-09 的上下文工程文章给的量级是每个子 agent 只返回 1,000–2,000 token 的摘要。

这样主 agent 的上下文不会被 208 张订单的明细和 22 条评论填满。

- 代价是 token：Anthropic 2025-06 的文章里，多 agent 系统约用聊天 15 倍的 token。
- 适用边界：任务价值高、能并行、信息超过单窗口的调研；不适合所有问题。

这也是为什么先量清楚覆盖，再决定拆不拆。

> **旧资料提示**：“多 agent 比单 agent 强 90.2%”“token 解释 80% 方差”“约 15 倍 token”都来自 Anthropic 2025-06 的内部评测，不是普遍规律。本书引用时注明来源，实验用本地数据；18.5 量的是覆盖、重复和 token，不是某个榜单分数。

本章的三条线这样分：退货记录查数量和比例，评论查顾客原话和样本缺口，政策查条款和生效日期。每条线都要“结论 + 证据 + 来源”，否则不算查到。

这次 1 个覆盖 3.0，3 个和 5 个都是 2.8：Q3 的 3/5 配置都少了政策这一条，5 个还多一次重复查询，token 从 1,104 涨到 2,574。样本只有 5 个问题，0.2 的差不能当规律；能确定的是，把已经取好的证据拆给更多子 agent，没有提高覆盖，反而多花 token。

5 个配置把 SQL 拆成“原因”和“快递”两条，两条都要先查季度总量，所以每题多 1 次重复查询；评论拆成两半，B12 本来就只有 2 条。Q3 少的那条是政策：3 个配置里政策线没写出 finding，5 个配置里政策线把结论标成了批次或快递，`cause` 里都没有“政策”。

- 静态 RAG 适合资料稳定、问题短的情况；单 agent 适合证据已经取好、只需汇总的追问。
- 能拆成独立线只是前提，值不值得还要看覆盖有没有升、token 涨了多少。

这里的“重复查询”按同一证据编号被几条线取用来算。5 个配置里 `sql:quarterly` 被 `sql-reason` 和 `sql-ship` 各查一次，所以每题多 1 次。

那篇文章的努力分级是启发式：简单事实 1 个、比较 2–4 个、复杂可以到 10 个以上。本书把复杂调研收在 3–5 个，因为数据源通常只有几条。最终用本章的覆盖、重复和 token 定，这次的结果不支持“多拆更好”。

| 做法 | 拆题 | 并行 | 汇总 | 引用 | 失败 |
|---|---|---|---|---|---|
| 静态 RAG | 不拆，按问题取 top-k | 无 | 模型一次回答 | 块 ID | 取不到就答“没有” |
| 单 agent | 自己边查边拆 | 串行 | 自己汇总 | 常常没有 | 用满预算或停在自洽解释上，漏线 |
| Anthropic 的 orchestrator-workers | 主 agent 拆给子 agent | 子 agent 并行 | 主 agent 综合 | CitationAgent | 错误累积，要断点续跑 |
| LangGraph map-reduce | `Send(node, arg)` 按列表分发 | 图节点并行 | reduce 节点 | 状态里带摘要 | 子图隔离状态，异常要自己收 |
| LangChain Academy 的 research-assistant | 先定子题再访谈 | map-reduce | 汇总成报告 | 访谈记录 | 访谈轮数要设上限 |

LangGraph 这一行只列接口名：`Send(node, arg)` 做 map-reduce，子图隔离内部状态，写法见[第 26 章](ch26.md)。

OpenAI 指南里的 manager 和 handoff 回答的是“谁持有对话、谁对用户说话”；本章回答“谁拆题、谁并行查”。

两组概念不要混：manager 可以调一个做调研的子 agent，但调研系统本身不一定对用户说话。

> **旧资料提示**：2025 年及以前常说“200k 上下文会被截断，所以要拆子 agent”。`deepseek-flash` 在 2026-11 是 1,048,576 token，主窗口装得下更多；子 agent 仍然有价值，因为上下文隔离和并行探索，不是因为主窗口一定装不下。Anthropic 2025-06 的文章说同步等待是当时的瓶颈；异步可行，但结果协调、状态一致和错误传播更难，本书示例用同步。

子 agent 的输出写成文件，主 agent 读引用而不是把全文复制进对话，能避免“传话游戏”（Anthropic 2025-06 的附录）。文件也是断点：进程挂了，已完成的线不用重查。

- 同步等待是瓶颈：主 agent 要等最慢的子 agent。本章并行发出、同步等全部完成，再按固定顺序打印。
- 异步的协调成本更高：谁先完成、结果怎么排序、一个失败要不要取消其他线，都要额外状态。先把同步版的产物和状态写清楚，再考虑异步。
- 失败文件也要有统一的字段，主 agent 才能用同一段代码读三种结果。

生产系统要把状态、产物、耗时都写下来，下一次才不用从聊天记录里猜发生了什么。

- 可观测性：每个任务记 id、工具、token、状态、耗时。本章打印了 status、turns 和合计 token，18.6 的产物只有 status、findings、gaps，id、工具和耗时要在生产系统里补。出错时才能分清是计划错、工具错还是汇总错，完整的追踪见[第 23 章](ch23.md)。
- 终态评估：覆盖只看带数字的 claim，不校验数字对错；真要判断数字对不对，还要另加核对。完整的评测方法在[第 21 章](ch21.md)。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| 计划 JSON `tasks[]` | 每项 `objective`、`output`、`tools`、`boundaries` | `json_object` + Pydantic 校验，失败重试一次 |
| 子 agent 合同 | 干净上下文、任务四字段、返回 `findings`/`gaps`/`status` | 不直接问用户，不查别的线 |
| 并行 | `ThreadPoolExecutor`，每个 `harness.run(..., verbose=False)` | 请求内容互不相同，结果按固定顺序取 |
| 共享数据库 | 工具里加锁，串行访问一个连接 | 模型调用可并行，SQLite 连接不能同时用 |
| 引用 | findings 的 `source` 写表名 + 字段 + 计数/比例 + 时间；报告段末标 `[数据]`/`[政策]`/`[评论]` | 检查器只查数字和标记，不核对来源对应 |
| 产物 | `findings/*.json`；主 agent 读引用 | 失败写 `status: failed` 和 `gaps` |
| 覆盖指标 | 三条原因覆盖几条、重复查询几次、token 多少 | 只数带数字的 claim，不校验数字对错 |
| LangGraph 对照 | `Send(node, arg)` 做 map-reduce，子图隔离状态 | 细节在第 26 章 |

## 思考题

1. 预测：把三条线并成一条“什么都查”的子 agent，覆盖和 token 会怎么变？先写下你的预测，再用 18.5 的口径量一次。

   <details><summary>提示</summary>

   按 18.5 这一次，1 条线的 token 是 1,104，3 条是 1,836，5 条是 2,574；1 条线覆盖 3.0，3/5 都是 2.8。注意 18.5 的证据已经取好，和 18.1 让单 agent 自己查不是一回事；先分清测的是搜索还是汇总。

   </details>

2. 找错：`18_4_uncited_fail.py` 的报告哪一句没有数据？应该从哪个子 agent 的 finding 里补？

   <details><summary>提示</summary>

   第一句“退货政策变宽松是主因”没有数字也没有来源，而且是提示指定照抄的。这句没有哪个 finding 能补：“主因”是因果判断，政策线只能给出生效日期；应删掉或改成“退货期限在 2026-07-01 改过，但它解释不了质量退货”。

   </details>

3. 权衡：Q3 退货率上升的主因，怎么用数据排除“只是退货期变长”？需要哪几个对照数字？

   <details><summary>提示</summary>

   先看质量原因的笔数（缺页 15、装订 5、运输破损 9）和 Q1/Q2 的同口径退货率。要排除期限，还需要政策生效前后普通退货（买错了、不想要、重复购买）的 Q2/Q3 对照；本章没有给这个数字，需要自己按 `returns.reason` 分组查。质量退货占了大头，期限只能解释一小部分。

   </details>

4. 迁移：把“SQL/评论/政策”换成“日志/工单/文档”，委派说明的四个字段要怎么改？

   <details><summary>提示</summary>

   `tools` 换成日志查询、工单检索、文档阅读；`boundaries` 写时间窗、只读、脱敏和“找不到写 gap”；`output` 仍要字段、数字和来源。四个字段仍对应第 7 章的五项：输入并入 `objective`，停止条件和禁止事项并入 `boundaries`。

   </details>
