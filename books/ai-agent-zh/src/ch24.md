`state 0` 是入口，`state 1` 到 `state 3` 是三个节点跑完后的 state，`steps` 的顺序就是节点执行的顺序。`get_graph()` 里多了 `__start__` 和 `__end__`：`add_edge(START, ...)` 从 `__start__` 出发，`add_edge(..., END)` 指向 `__end__`。

把第 3 章的循环拆开，对应关系是：

| `harness.run` 里的东西 | 图里的东西 |
|---|---|
| `for turn in range(max_turns)` 和 `if msg.tool_calls` | 固定边和条件边 |
| `messages` 列表 | `State` 的 channel |
| `Toolbox.call(name, args)` | `tools` 节点 |
| `stop == "answer"` | 走到 `END` |
| `max_turns` | `recursion_limit`（数超步，不是轮次；24.6） |

LangGraph 的运行时按超步（super-step）推进：同一个超步里的节点可以并行，下一个超步看到上一个超步的全部写入；检查点也按超步落盘（[第 25 章](ch25.md)）。

`StateGraph(State)` 的 `State` 是所有节点共享的 schema，`START`/`END` 是特殊节点，`compile()` 检查未知节点和边，返回可 `invoke`/`stream` 的图。孤立节点不报错，但永远不会执行（1.2.22 实测）。

不是所有流程都值得画图：固定顺序的三步用普通函数更短；需要暂停、恢复、并行、时间回溯或可视化时才引入图。

- 图把“下一步走哪”从循环体里拿出来，放到边上。
- 重试可以挂在节点上，人工审批可以停在节点或边前，并行检查可以开两条边，改这些不用动其他节点。
- 代价是多了 schema 和连边的代码；三个节点时看不出来，节点多、分支多时才划算。

没有 reducer 的键默认是覆盖。同一个超步里两个节点写同一个键，会抛 `InvalidUpdateError`，消息以 `At key 'log': Can receive only one value per step` 开头。这是 24.3 要解决的问题。

错误先给键名 `'log'`，再说一个超步只能收一个值；示例只打印第一行，完整的错误末尾还有文档链接。这个错误不会自动重试，两个分支也不会替你合并。

错误发生在第一个超步结束时，不是某个分支跑到一半。两个分支都会跑完，合并写入时才检查同一个键收到了几个值。

消息列表有专门的 reducer：

- `Annotated[list[str], operator.add]` 让每次写入追加，示例用它合并两节政策。
- `add_messages` 处理消息：不带 `id` 的追加，带相同 `id` 的覆盖，`RemoveMessage(id=...)` 删除。
- 并行分支的完成顺序不保证，输出要排序或按 key 汇总，不能依赖“谁先跑完”。
- reducer 只负责合并，不负责校验。两条分支写同一张订单的退款金额时，金额冲突仍要在节点里判断。
- `RemoveMessage` 适合在压缩或人工编辑后删消息；它只对带 `add_messages` 的键有效。普通列表键用 `operator.add` 时，删除要自己写 reducer。

这几行代码对应 24.1 的对照表：

- `ChatOpenAI(model=MODEL).bind_tools(tools)` 把工具 schema 绑到模型上，模型才知道能调用什么。
- `ToolNode(tools)` 执行最后一条 AIMessage 里的 `tool_calls`，把每个结果写成 `ToolMessage`；`tools_condition` 有 `tool_calls` 返回 `"tools"`，否则返回 `END`。
- 边是 `START → assistant`、`assistant --tools_condition--> tools` 或 `END`、`tools → assistant`；停止条件仍是“模型不再要工具”。
- `ToolNode` 默认并行执行同一轮里的多个调用。两个各睡 0.3 秒的工具，一起跑完约 0.3 秒（实测）。
- 工具异常默认只把参数校验这类调用错误变成消息，其他异常会往上抛；`handle_tool_errors=True` 把异常转成 `ToolMessage`，模型能读到错误并改参数，代价是程序不会崩。`harness.Toolbox.call` 则把所有错误都变成给模型看的文字（[第 3 章](ch03.md)）。
- 系统提示放在 `assistant` 节点里，用 `[SystemMessage(...)] + state["messages"]` 现拼，不写回 state；如果把每轮的 `SystemMessage` 也追加进 state，历史里会多出一条，token 一直涨。

示例里有一层适配：`support_tools(store)` 返回的是 `harness.Toolbox`，`as_langchain` 把每个 `Tool` 包成 `StructuredTool`，参数 schema 原样传过去。`shop` 和 `harness` 都没有改。

24.4 的代码比第 3 章的 `run` 长，因为 schema、节点、连边都要写出来。换来的是每一步能单独替换：把 `assistant` 换成会分诊的节点，`tools` 不用动；把 `tools` 换成只读工具，审批逻辑也不用改。

示例还关掉了 DeepSeek 的思考模式（`extra_body={"thinking": {"type": "disabled"}}`）。LangChain 的 `ChatOpenAI` 不提取也不保留 `reasoning_content`，而 DeepSeek 在带 `tools` 的思考模式里要求把之前每轮的 `reasoning_content` 原样放回（[3.2 节](ch03.md)）。关掉思考最省事，要保留思考就得自己在消息里带上它。

- 从 `langchain.agents` 导入 `create_agent`。常用参数有 `model`、`tools`、`system_prompt`、`checkpointer`、`store`、`response_format`、`interrupt_before`，另有 `middleware`、`state_schema` 等。
- 它内部就是 24.4 的图，只是模型节点叫 `model`：`get_graph()` 里是 `__start__`、`model`、`tools`、`__end__` 和四条边。middleware 负责动态提示、人工介入、摘要这类横切逻辑。
- `create_agent(...).invoke({"messages": [...]}, config)` 返回 `{"messages": [...]}`。`config` 里带 `thread_id`、并且建 agent 时给了 checkpointer，才有跨轮记忆（[第 25 章](ch25.md)）。
- 旧写法 `langgraph.prebuilt.create_react_agent` 在 LangGraph v1 已弃用，改用 `langchain.agents.create_agent`；`ToolNode` 和 `tools_condition` 仍然可用。
- 返回的对象也是 `CompiledStateGraph`，`get_graph()`、`stream()` 的用法和 24.4 一样。

> **旧资料提示**：LangChain Academy 的笔记本用 `gpt-4o`；这里模型名从 `MODEL` 读，2026-11 的默认是 `deepseek-flash`。LangChain Academy 常用的 `MemorySaver` 现在文档主用 `InMemorySaver`，`MemorySaver` 仍是同一个类的别名（实测 `InMemorySaver is MemorySaver`）。

预置 agent 省的是循环代码，不省提示设计和工具设计。提示、工具、模型仍要自己选（[第 8–9 章](ch08.md)）。

“标准循环”指“模型要工具→执行→再问模型”这一种。如果每一步都要改 state、加自定义分支，24.4 的图更直接；`create_agent` 也收 `middleware`，但 middleware 仍要自己写。

`response_format` 用来做结构化输出；在 Chat Completions 上，DeepSeek 不支持 `response_format: json_schema`，`json_object` 可用，用之前先看 [第 4 章](ch04.md)。`interrupt_before` 在节点前暂停，配合 checkpointer 才能恢复（[第 25 章](ch25.md)）。

## 24.6 图的边界：递归、编译检查和流式查看

图里的环必须有停止条件。`recursion_limit` 放在 `config` 顶层（不是 `configurable` 里），数的是超步；LangGraph 1.2.22 的默认值是 10007，可用环境变量 `LANGGRAPH_DEFAULT_RECURSION_LIMIT` 改，旧文档常写 25。

```python
{{#include code/ch24/24_6_recursion_fail.py}}
```

这次运行的输出：

```text
{{#include code/ch24/24_6_recursion_fail.out}}
```

`tick` 每次都回到自己，五个超步以后到达上限。错误里的 “Recursion limit of 5 reached” 是配置值，不是模型的轮数。

- `compile()` 能查结构，查不了语义。`add_edge("没注册", END)` 会抛 `ValueError: Found edge starting at unknown node '没注册'`；节点返回 schema 里没有的键会被忽略，类型写错也不报错（实测）。
- 编译检查只保证边连到了已注册的节点，不保证节点返回的东西能用；schema 是给类型检查器和编辑器看的，运行时不会替你校验。
- `stream_mode="values"` 每步给完整 state，`"updates"` 只给本步写入，`"messages"` 给模型 token 流（[第 2 章](ch02.md)）；要同时看每步更新和 token，传 `["updates", "messages"]`。调结构时先看 `get_graph()`。
- 节点里做 I/O 要自己保证幂等：重放会重新执行节点，模型调用和写文件都会重发，外部副作用不会被撤销（[第 25 章](ch25.md)）。
- 图里没有单独的“轮次”计数器；`updates` 的到达次数是节点执行次数，模型轮次由 `assistant` 节点的调用次数决定。
- `recursion_limit` 太小会在正常的多步流程里误报；按图的超步数量留余量，不要照抄教程的 25。
- `recursion_limit` 是运行时保护，不是业务停止条件；业务停止条件仍要写在节点或条件边里。
- 图不是 sandbox。节点里能读写文件、数据库和网络，权限边界仍要靠 [第 22 章](ch22.md) 的 harness/sandbox 设计。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `StateGraph(State)` | 用状态 schema 建图 | 键就是 channel |
| `add_node` / `add_edge` / `add_conditional_edges` | 注册节点、连固定边和条件边 | 路由函数返回节点名或 `END` |
| `START` / `END` | 特殊入口、出口节点 | `get_graph()` 里显示成 `__start__`/`__end__` |
| `compile()` | 检查结构，返回可运行图 | 孤立节点不报错，也不会执行 |
| `TypedDict` / `dataclass` / Pydantic | 定义 State | 文档建议 `TypedDict` 或 `dataclass`（性能考虑） |
| `Annotated[..., operator.add]` | 让写入追加 | 自定义 reducer 要先处理 `None` |
| `add_messages` | 消息专用 reducer | 同 `id` 覆盖，`RemoveMessage` 删除 |
| `ChatOpenAI(model=MODEL).bind_tools(tools)` | 把工具绑到模型 | 思考模式下注意 `reasoning_content` |
| `ToolNode(tools)` / `tools_condition` | 执行工具、决定去 `tools` 还是 `END` | 多个调用默认并行 |
| `create_agent(...)` | 预置的模型加工具循环 | 参数含 `checkpointer`、`store`、`response_format`、`interrupt_before` |
| `invoke` / `stream(stream_mode=...)` | 跑图、看每一步 | `updates` 适合打印轮次 |
| `recursion_limit` | 限制超步数 | 1.2.22 默认 10007，放 `config` 顶层 |
| `get_graph().draw_mermaid()` | 返回图结构文本 | 要 `print` 才显示 |
| `InvalidUpdateError` / `GraphRecursionError` | 并行写冲突、环超限 | 都不会自动重试 |

## 思考题

1. **预测**：把 24.3 的 reducer 去掉，两个并行分支同时写 `log`，错误会在第几个超步出现，消息里指出哪个键？

   <details><summary>提示</summary>

   两个分支在第一个超步一起写；更新在超步结束时合并，所以错误在第一个超步末出现，键名是 `log`。

   </details>

2. **找错**：24.4 的图如果 `tools_condition` 永远返回 `"tools"`，`recursion_limit` 设成 100，会先耗尽轮数还是先报错，为什么？

   <details><summary>提示</summary>

   先报 `GraphRecursionError`。上限数的是超步，不是模型的轮数；`assistant → tools → assistant` 每个来回占两个超步，条件边永远不去 `END`。

   </details>

3. **权衡**：T06 的退货咨询用 24.2 的四节点图，还是 24.5 的 `create_agent`？用调用次数和代码量各说一条。

   <details><summary>提示</summary>

   四节点图把查订单、查政策写成普通节点，起草用模板，这次 0 次模型调用；要模型生成回答，就把起草节点换成一次模型调用。`create_agent` 让模型自己决定调工具，24.5 这次用了 2 次调用；代码更短，但工具和提示仍要自己配。

   </details>

4. **迁移**：把 24.4 的 `assistant/tools` 换成“分诊/退款/物流”三个节点，哪些边要改，状态要加什么键？

   <details><summary>提示</summary>

   把 `assistant` 的条件边改成分诊节点发出的三条条件边；退款、物流各自成一个节点，执行完回到一个回复节点或 `END`。状态可加 `intent`、`refund_result`、`tracking`。

   </details>
