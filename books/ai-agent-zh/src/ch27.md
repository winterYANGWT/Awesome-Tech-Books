## 27.1 Agents SDK 的四件东西：Agent、Runner、function_tool、handoff

Agents SDK 把第 3 章手写的循环拆成四个名字。先对照它们各自接的是哪一段，再看最小的程序。

| SDK 里的东西 | 第 3 章手写时是什么 | 第 24 章 LangGraph 里对应什么 |
|---|---|---|
| `Agent` | 系统提示、工具子集、模型参数的组合 | 节点里跑的那个 agent，或一张子图 |
| `Runner` | `harness.run` 的循环：调模型、执行工具、放回结果、判断停止 | 图的运行时：推进节点，直到没有下一步 |
| `@function_tool` | `@tool` 生成的 JSON Schema 和本地函数 | 节点里绑定给模型的工具 |
| `handoff` | 第 17 章的“换系统提示、换工具子集、补一条 tool 消息” | 条件边跳到另一个节点或子图 |

四个名字的分工可以这样记：`Agent` 是配置，`Runner` 是循环，工具和 handoff 是循环可调用的两种动作。配置里没有 `messages`，历史由 Runner 每次传进去，这也是 27.5 要自己传会话的原因。

- `Runner.run_sync(agent, input, max_turns=10, context=..., run_config=...)` 是同步入口，异步用 `await Runner.run(...)`。返回的 `RunResult` 有 `final_output`、`last_agent`、`new_items`、`to_input_list()`、`max_turns`，护栏结果也在里面。

> **旧资料提示**：OpenAI 2025-04 指南里的 `Agents.run(agent, [UserMessage(...)])` 不是 0.24 的接口，用 `Runner.run_sync(agent, "…")` 或 `await Runner.run(...)`。同一份材料里的 `name=Triage Agent"` 少引号、护栏例子里 `agent` 未定义、`datetime.time()` 用法不对、`math_homework_tripwire` 不在代码里；本章示例按 0.24 重写，不复制这些错误。

- 记录里 T01 是 3 次模型调用，T06 是 4 次。分诊一次，专员第一次调用（T06 同时要订单和政策），拿到工具结果后再调用，退款后还要一次收尾。交接不是免费的，每次多一轮模型调用。
- `handoff_description` 影响分诊选择；`on_handoff` 可以挂一个回调做审计；`input_filter` 可以裁剪交给下一个 agent 的历史，`agents.extensions.handoff_filters.remove_all_tools` 是现成的过滤器。
- handoff 后原 agent 不再参与。要回到分诊，就在专员上加一个反向 handoff，这会再多一轮模型调用。
- 分诊提示要写清四类边界：物流、退款、政策、越界。T28、T29 这类越界请求不要进 handoff，T27 的他人地址也不该交给专员，它们归 27.4 的护栏管。
- 这里按业务域拆工具子集：logistics 只有 `get_order`，refunds 有四个（查单、查政策、退款、升级），policy 只有一个。refunds 的工具最多，提示里要写清“先核对、再退款、超过 500 元升级”的边界。

handoff 不是 manager：manager 把专员包成工具，自己保留对话和用户，handoff 把控制权交出去，原 agent 退出。两种编排的实现和取舍在第 17 章，这里只对照写法。

## 27.3 结构化输出：output_type 的三种走法

`Agent(output_type=TicketCategory)` 把 Pydantic 模型转成 JSON Schema。SDK 把这个 schema 放在哪个字段，取决于它走哪条接口：Chat Completions 模式放进 `response_format`，Responses 模式放进 `text.format`。

DeepSeek 的 Chat Completions 只支持 `json_object`，前一条请求在模型开始生成之前就被拒绝；Responses 支持 `json_schema`，后一条能过。

终止工具的参数 schema 仍然是普通的工具 schema：`category` 是枚举，模型通常按枚举选。`function_tool` 在本地仍会校验，枚举外的值会变成一条错误结果回给模型，而不是让程序崩掉。

- 0.24 有一个细节：agent 的 `output_type` 为空时，终止工具的返回值会被转成字符串，不是原样的 dict。示例让 `submit_category` 直接返回 JSON 文本，再用 `json.loads` 取 `category`；这样既避开了 `json_schema`，也不用依赖 SDK 的内部类型。
- 不要用 `tool_choice` 去强制 `submit_category`。DeepSeek 在思考模式下指定函数名或 `"required"` 会返回 400；这里靠提示让模型自己选，靠 `stop_at_tool_names` 停下来。

三种做法放在一起：

| 做法 | 请求里的格式 | DeepSeek 2026-11 | 代价 |
|---|---|---|---|
| `output_type`，Chat Completions | `response_format` 的 `json_schema` | 400，模型开始生成前拒绝 | 这条路走不通 |
| `output_type`，Responses（默认模式） | `text.format` 的 `json_schema` | 可用，返回 Pydantic 实例 | 换接口，schema 和提示不变 |
| 终止工具 | 普通 `tools` | 可用，返回值是字符串 | 多一个工具定义，要自己 `json.loads` |

如果不想让模型的返回值经过工具调用，还可以用普通文本加 `response_format={"type": "json_object"}`；这要自己调 `client.chat.completions.create`，不走 Agent 的 `output_type`，做法在第 4 章。

> **旧资料提示**：OpenAI 2025-04 指南用 `output_type` 做结构化输出。2026-11 在 DeepSeek 上实测：Chat Completions 模式下会 400，Responses 模式下可用；`json_object` 也可用，`json_schema` 只在 Responses 的 `text.format` 里可用。

`Runner.run_sync(agent, "…")` 每次都是独立的 run，上一轮的消息不会自动带进来。多轮有两条路：把 `result.to_input_list()` 作为下一次的 `input`，或者传一个 `session=`。


这次运行的输出：

```text

```

第一轮 T06 退款 82 元，第二轮只问“刚才那单退款多少”，模型答出 82。`SQLiteSession("c082", ":memory:")` 把消息历史存在内存 SQLite 里；第一轮结束是 10 条，第二轮结束是 13 条，包含用户消息、工具调用、工具结果和最终回答。

- `max_turns` 默认 10。超过就抛 `MaxTurnsExceeded`，不是返回一个半成品；要部分结果就自己捕获异常，从 `new_items` 里取已经发生的步骤。
- `set_tracing_disabled(True)` 必须开。否则 SDK 会往 OpenAI 发追踪；本书不启用外部追踪服务。
- `new_items` 是本次新增的 message、tool call、handoff 项；`to_input_list()` 是完整历史。打印时只取需要的字段，不要把整个 `new_items` 倒出来。
- 会话存的是消息历史，不是图 state。需要“暂停、恢复、批准”时用 `RunState` 和 `interruptions`，写法见[第 20 章](ch20.md)。0.24 的 `function_tool` 有 `needs_approval` 参数，本章只列接口，没有在 DeepSeek 上实测它。
- `SQLiteSession` 的 `:memory:` 只在这个进程里有效；要跨进程恢复就传文件路径，像 `sessions.db`。消息表会随轮数增长，生产要设保留策略，不要把它当长期记忆。

## 27.6 什么时候该用框架

先把需求拆成几列，再看哪个框架替你接管。下面这张表不是“哪个好”，是“哪一列你愿意自己写”。

先问三个问题：流程是不是固定、需不需要在中间停下来等人、状态要不要跨进程恢复。三个都否，手写 harness 最省；有一个是，框架才开始有价值。

| 需求 | 手写 `harness.run` | LangGraph | OpenAI Agents SDK |
|---|---|---|---|
| 循环控制 | 自己写 while 和停止条件 | 图加边，运行时推进 | Runner 接管 |
| 状态持久化 | 自己写日志和恢复 | checkpointer | `SQLiteSession` 只存消息 |
| 人工中断 | `approve` 回调自己实现 | `interrupt()` + 恢复 | `RunState` / `needs_approval` |
| 并行、子图 | 自己起线程或子进程 | 子图、`Send`、并行节点 | 多 agent 靠 handoff，不提供图 |
| 多 agent | 自己写 manager 或 handoff | 节点或子图 | handoff / agent-as-tool |
| 结构化输出 | 工具或 JSON 模式 | 节点里自己解析 | `output_type`；Chat Completions 400，Responses 可用 |
| DeepSeek 兼容性 | 完全可控 | 工具调用正常 | 工具和 handoff 正常；`output_type` 要走 Responses |
| 代码量 | 最多，但每一行都看得见 | 中等，学习成本在 state 和 reducer | 最少，标准循环不用写 |

手写 harness 适合教学、极简和完全可控的场景。循环、消息和审批回调在一个文件里，出问题能直接打断点；代价是检查点、恢复、时间回溯都要自己写，第 22 章的事件日志就是其中一种做法。

LangGraph 适合需要图结构、检查点、时间回溯、子图和 map-reduce 的系统。它的学习成本不在 API，而在 state schema 和 reducer：哪些字段追加、哪些覆盖、并行节点写同一个 key 怎么合并。第 24–26 章已经把这些铺开。

Agents SDK 适合标准循环、handoff 和护栏，代码量最少。它的边界也清楚：DeepSeek 上 `output_type` 走 Responses 可用、走 Chat Completions 会 400，复杂暂停/恢复不如 LangGraph，会话只保存消息，不保存图状态。

| | 消息历史 | 检查点 | 中断和恢复 | 长期记忆 |
|---|---|---|---|---|
| 手写 harness | 你自己的 `messages` 列表 | 自己写（[第 22 章](ch22.md)的事件日志） | 自己写（[第 20 章](ch20.md)的 `approve`） | 自己写 |
| LangGraph | 图状态里的 `messages`，reducer 合并 | checkpointer 自动存 | `interrupt()` 加 `Command(resume=...)` | `Store` |
| Agents SDK | `RunResult` 或 session 里的消息 | 没有自动 checkpointer；`RunState.to_json()` 要自己存 | `RunState` 的 interruptions | 自己写 |

选型不是二选一：可以用 LangGraph 管流程，在节点里跑一个 Agents SDK 的 agent，图负责检查点、人工中断和子图，agent 负责一次交接或一段工具循环。代价是两套状态和追踪要对齐，这种组合本书没有演示。

迁移成本分三块：工具 schema 大多能复用（`@function_tool` 和 `@tool` 都是函数签名加描述），提示和评测集能复用；状态和中断语义要重写，因为 LangGraph 的 checkpointer 存的是图状态，Agents SDK 的 session 存的是消息。换框架前先把这三块分开估。

不管选哪个，先把评测集跑通。评测集和工具函数是跨框架资产，循环和状态不是；先有基线，再谈迁移。

| 比较项 | 手写 `harness.run` | LangGraph | OpenAI Agents SDK |
|---|---|---|---|
| 循环谁控制 | 你的 `for turn in range(1, max_turns + 1)` | 图的运行时 | `Runner` |
| 状态在哪 | 你传的 `messages` 列表 | `State` + checkpointer | 消息列表或 `Session` |
| 怎么暂停 | `approve` 回调里阻塞 | `interrupt()` 后等恢复 | `RunState` / 中断项 |
| 怎么做 handoff | 换提示、换工具、补 tool 消息 | 条件边跳节点 | `handoffs=[...]` 生成 `transfer_to_*` |
| 结构化输出 | 工具或 `json_object` | 节点里解析 | `output_type`；Chat Completions 400，Responses 可用 |
| 护栏 | 自己在循环前后加检查 | 节点或边里加检查 | `input_guardrails` / `output_guardrails` |
| 代码量 | 最多 | 中等 | 最少 |
| DeepSeek 兼容性 | 取决于你写的代码 | 工具调用正常 | 工具和 handoff 正常；`output_type` 走 Responses |

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `Agent(name, instructions, tools, handoffs, model, ...)` | 定义一个 agent | `name` 用 ASCII，会变成 `transfer_to_<name>` |
| `Runner.run_sync` / `Runner.run` | 同步 / 异步跑一次 | `max_turns` 默认 10 |
| `RunResult.final_output` / `last_agent` | 最终输出 / 最后接手的 agent | handoff 后看 `last_agent` |
| `RunResult.new_items` / `to_input_list()` | 本次新增项 / 完整历史 | 多轮把 `to_input_list()` 传回去 |
| `@function_tool` | 从签名和 docstring 生成工具 | 异常默认变成固定错误结果 |
| `handoff_description` / `input_filter` | 给分诊模型看的说明 / 裁剪交接历史 | `on_handoff` 可做审计 |
| `tool_use_behavior={"stop_at_tool_names": [...]}` | 工具返回后停止循环 | 终止工具的返回值成为 `final_output` |
| `@input_guardrail` / `@output_guardrail` | 输入 / 输出护栏 | 返回 `GuardrailFunctionOutput` |
| `InputGuardrailTripwireTriggered` 等 | 护栏命中的异常 | 输入护栏默认并行；输出护栏在 final 之后 |
| `SQLiteSession("id", ":memory:")` | 保存多轮消息 | 存消息，不存图状态 |
| `set_default_openai_api("chat_completions")` | 走 Chat Completions | 配合 `set_tracing_disabled(True)` |
| `set_default_openai_client(AsyncOpenAI())` | 走默认 Responses 模式 | 不调 `set_default_openai_api` |
| `output_type` | 结构化输出 | Chat Completions 模式 400；Responses 模式可用 |

## 思考题

1. 预测：T28 的注入文本如果放进 T06 的工单里（而不是单独一条），输入护栏还会不会触发？提示：护栏看的是整段输入文本，还是只看第一条用户消息？

<details><summary>提示</summary>

本章的输入护栏对整个 `input` 做正则匹配，不区分“工单正文”和“注入句子”。把“忽略之前的指令”塞进 T06 的缺页描述里，正则仍会命中；代价是正常工单里只要出现这些词也会被拦，规则要拿误杀样本调。

</details>

2. 找错：在 `27_3_output_type_fail.py` 强制 Chat Completions 的前提下，把 `output_type` 换成 `AgentOutputSchema(..., strict_json_schema=False)`，错误会不会消失，为什么？

<details><summary>提示</summary>

不会。`strict_json_schema` 只改 schema 里的 `strict` 字段；`response_format` 的 `type` 仍是 `json_schema`，DeepSeek 仍在模型开始生成前拒绝。同一个 `output_type` 换到 Responses 模式（`27_3_output_type_responses.py`）就能用，因为字段从 `response_format` 换成了 `text.format`。

</details>

3. 权衡：分诊用 handoff 还是 manager（第 17 章），从状态归属和调试成本各说一条。

<details><summary>提示</summary>

状态归属：handoff 把对话交给专员，原 agent 不再持有；manager 始终持有对话，专员只返回摘要。调试成本：handoff 的控制流在 SDK 里，出错时看 `last_agent` 和 handoff 项；manager 的每次调用都是一个普通工具调用，输入输出都在自己的日志里，但要多维护一层摘要。

</details>

4. 迁移：把 27.5 的 `SQLiteSession` 换成 LangGraph 的 checkpointer，哪些代码要改、哪些能复用？

<details><summary>提示</summary>

要改的是会话创建、`Runner` 的调用和消息读取；图那边要定义 `State`、`thread_id` 和 checkpointer。能复用提示、工具函数和评测集；不能直接复用消息历史的存储格式，因为 checkpointer 存的是图状态，不是 SDK 的会话表。

</details>
