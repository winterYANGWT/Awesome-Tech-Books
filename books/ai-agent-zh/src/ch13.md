## 13.2 上下文腐化：旧信息拖累新判断

{{#fig ch13/stale_docs}}

Anthropic 在讲上下文工程的文章里把这种现象叫上下文腐化（context rot）：上下文里的 token 越多，模型准确召回其中信息的能力越差。原因是 transformer 的注意力关系随 token 数按 n² 增长，而训练数据里短序列更常见。

他们把这种下降描述成性能梯度，不是硬悬崖：模型在长上下文里仍然可用，只是长距离检索和推理的精度下降。所以“再加大窗口”不解决腐化，得靠挑 token。

两个条件的资料不同：

- 条件 A：只给现行 `returns.md` 的“退货期限”“质量问题”两节。

- 删掉旧版本，不留在上下文里。

- 把现行条款放前面。

13.1 里的 A1469 不是这种反例：它是用户在第二轮主动追问的，`get_order` 返回了 `created: 2026-08-06`、`status: 部分退款`、`refunded: 48.0`，不是模型自己翻出来的旧账，也不是没有标记的工具结果。

> **旧资料提示**：2025 年有些材料把上下文腐化说成“过了某个长度就突然崩”。Anthropic 的原文说的是性能梯度；本章用 10 次重复看方向，不把一次运行当规律。

全量塞入不是“更准”，只是把检索成本从工具调用换成输入 token。数据一变就要重发，缓存也救不了内容变化。680 张约 6.5 万个 token，按同样密度，1 万张约 96 万个 token，已经贴着 1M 上限。

680 张的 JSON 里，书名和地址的字符合计不到一成，占地方的是 items 明细和其他结构字段。只留编号、金额、状态，字符数从 157,533 降到 29,573，省八成，但省掉的信息往往正是问题要问的。

| 情况 | 做法 |
|---|---|
| 数据量小、查询可枚举 | 全量塞入 |
| 数据量大、查询开放 | 按需查 |
| 两者之间 | 固定摘要 + 按需查 |

结论是“按需查 + 必要的固定摘要”，不是“永远不要预先检索”。预先检索可以用，但要按问题取一小块，预算紧时先砍固定前缀，不是先砍最近的对话。混合策略见 14.5 节。

## 速查

| 接口或做法 | 作用 | 注意 |
|---|---|---|
| `usage.prompt_tokens` | 本次输入计费 | 不是字符数，别用 `len()` 代替 |
| `usage.prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` | 缓存命中与未命中 | 命中的是与上一轮相同的前缀（含历史）；前缀越长越容易命中 |
| `usage.completion_tokens_details.reasoning_tokens` | 思考 token | 默认开启；本章示例都关掉（`extra_body={"thinking": {"type": "disabled"}}`）。开着且带 `tools` 时，之前轮次的 `reasoning_content` 要原样放回（2.3 节），否则 400 |
| `before_model(messages)` | 调用前裁剪 | 返回新列表，别就地改乱原列表 |
| `tool_calls[i].id` ↔ `role: tool` 的 `tool_call_id` | 工具调用与回复配对 | 必须成对；删一半会 400 |
| `trim_messages(...)` | LangChain 的按 token 裁剪，可在 LangGraph 节点里用 | `strategy="last"`、`include_system=True`、`allow_partial=False` |
| `max_tokens` | 输出上限 | 预算要同时算输入和输出 |
| `BudgetExceeded` | 本地闸 | 错误信息写清当前值、预算和占比；第二道会话闸本章未实现 |

## 思考题

1. **预测**：把 `SUPPORT_PROMPT` 从 4 条扩到 40 条 if-else，T06 的 `prompt_tokens` 和正确率会怎么变？

   <details><summary>提示</summary>

   固定部分每轮都重发，40 条会把每轮抬高几百到一千 token；正确率不一定升，13.3 的 if-else 版 token 最多、正确数最低，因为它把政策写死了。

   </details>

2. **找错**：`13_4_trim_fail.py` 的切片为什么通不过本地配对校验？如果原样发给 API，缺了哪条消息、为什么会 400？

   <details><summary>提示</summary>

   示例只做本地 `check_pairs`，不发 API。切片从 `tool` 回复开始，前面的 assistant `tool_calls` 被切掉；最后一条 assistant `tool_calls` 又没有对应的 `tool` 回复。本地先报 `call_a1659` 前面没有 `tool_calls`；原样发送时，API 会因为这条孤立的 tool 消息返回 400。`call_a1659` 要和它前面那条 assistant 消息一起删，或者两条都留。

   </details>

3. **估算**：680 张订单约 6.5 万 token，1 万张、10 万张各约多少？按 1M 上限，什么时候必须改成按需查？

   <details><summary>提示</summary>

   按每张约 96 token 线性外推：1 万张约 96 万，10 万张约 960 万。1 万张就已经贴着 1M 上限，必须改成按需查或先摘要。

   </details>

4. **权衡**：什么情况下宁可全量塞入，也不让 agent 多轮查？给出两个判据。

   <details><summary>提示</summary>

   数据量小到一次放得下，且查询集合可枚举、答案要在一眼内比较时，全量塞入更省往返。数据经常变、查询开放、或者 token 已经接近预算时，按需查更稳。
