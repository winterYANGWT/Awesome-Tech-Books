# 第 33 章 与图形和外部 API 互操作

CUDA 算出来的东西常常要交给图形 API：模拟的结果要画在屏幕上，处理过的视频帧要送去编码；反过来，渲染出来的图像也常常要交给 CUDA 做后处理或者送进神经网络。数据本来就在显存里，如果经过主机内存拷一个来回，既浪费 PCIe 带宽又增加延迟。互操作（interop）就是让 CUDA 和图形 API 直接访问同一块显存。

CUDA 提供两代互操作接口。老的一代针对 OpenGL 和 Direct3D 9/10/11：把图形 API 的资源注册给 CUDA，用的时候映射、用完解除映射，同步由驱动隐式完成。新的一代是通用的外部资源接口：Vulkan、Direct3D 12 这类显式 API 把内存和同步对象导出成句柄，CUDA 导入以后直接使用，同步用导入的 semaphore 显式完成。这台机器没有显示器，但两种接口都可以在没有窗口的情况下使用，本章各用一个程序演示。

## 33.1 没有窗口的 OpenGL

OpenGL 程序通常靠窗口系统（X11、Wayland）建立上下文。没有窗口时可以用 EGL 的 device 平台，直接在某块 GPU 上建立一个 OpenGL 上下文。[gl_interop.cu](code/ch33/gl_interop.cu) 先枚举 EGL 看到的设备，挑出 CUDA 设备 0 对应的那个（NVIDIA 的 EGL 设备可以查询 `EGL_CUDA_DEVICE_NV` 属性得到 CUDA 设备号），然后建立一个不带任何绘制表面的上下文：

```cpp
{{#include code/ch33/gl_interop.cu:egl}}
```

```text
$ ./gl_interop
EGL 1.5，OpenGL 4.6.0 NVIDIA 610.57.04，NVIDIA GeForce RTX 5060 Laptop GPU/PCIe/SSE2
```

这样得到的就是一个完整的 OpenGL 4.6 上下文，只是不能直接显示，渲染结果可以画到帧缓冲对象里。服务器上的离屏渲染也是这样做的。

## 33.2 注册、映射、解除映射

OpenGL 分配一个 64 MB 的 buffer（比如用作顶点缓冲），注册给 CUDA：

```cpp
{{#include code/ch33/gl_interop.cu:register}}
```

注册只需要做一次。之后每一帧，CUDA 要用这个 buffer 时先映射，取得设备指针，启动 kernel 写入，然后解除映射，把它交还给 OpenGL：

```cpp
{{#include code/ch33/gl_interop.cu:frame}}
```

跑完 200 帧以后，由 OpenGL 读回 buffer 的内容检查：

```cpp
{{#include code/ch33/gl_interop.cu:readback}}
```

```text
注册 64 MB 的 buffer：5333 us
每帧：映射 + kernel + 解除映射 298 us，只有 kernel 185 us
OpenGL 读回第 200 帧，错误 0 个
```

OpenGL 读到的正是 CUDA 最后一帧写入的内容，中间没有任何拷贝。几个数字值得注意：

- 注册要 5 ms 多，所以只能在初始化时做一次，绝不能每帧注册、注销。
- 每一帧的映射和解除映射多花了约 110 us。映射时驱动要保证 OpenGL 对这个 buffer 已经发出的操作都完成了，解除映射时要保证 CUDA 的写入对 OpenGL 后续的操作可见，这些隐式的同步就是代价。kernel 越短，这个开销占的比例越大。映射期间 OpenGL 不能使用这个 buffer。
- 注册时的 `cudaGraphicsRegisterFlagsWriteDiscard` 告诉驱动 CUDA 每次都会覆盖全部内容，不需要保留原来的数据；只读的情况用 `cudaGraphicsRegisterFlagsReadOnly`。这些提示能让驱动省掉一些工作。

纹理用 `cudaGraphicsGLRegisterImage` 注册，映射以后得到的不是指针，而是一个 `cudaArray`，要通过 texture 或 surface 对象读写（第 7 章提过，本书不展开）。Direct3D 9/10/11 的互操作是同样的模式，换成对应的注册函数即可。

## 33.3 Vulkan：导出和导入

Vulkan 没有这样的注册函数，它和 CUDA 的互操作走通用的外部资源接口：Vulkan 分配内存时声明“可以导出”，导出成一个文件描述符（Windows 上是 NT 句柄），CUDA 用 `cudaImportExternalMemory` 导入。同步也一样，Vulkan 建一个可导出的 semaphore，CUDA 导入以后可以在 stream 里等待它、给它发信号。这和第 32 章 VMM 的跨进程共享是同一套思路，所以两边也完全可以在不同的进程里。

## 33.4 用 semaphore 同步

OpenGL 互操作的同步藏在映射和解除映射里；外部资源接口则完全显式。timeline semaphore 带一个只增不减的 64 位计数，任何一方都可以等待它达到某个值，也可以把它设成更大的值。程序用一个 semaphore 完成两个方向的同步：值到 1 表示数据准备好了，CUDA 可以开始；值到 2 表示 CUDA 算完了：

```cpp
{{#include code/ch33/vk_interop.cu:sync}}
```

真实的程序里，等待和发信号的是 Vulkan 队列上提交的渲染命令，这里为了不写一大段 Vulkan 命令缓冲的代码，由主机直接写数据、直接用 `vkSignalSemaphore` 发信号、用 `vkWaitSemaphores` 等待，原理一样。

```text
任务已经排进 stream，100 ms 后 stream 的状态：cudaErrorNotReady
Vulkan 发信号以后 CUDA 才开始算；在 Vulkan 这边检查结果，错误 0 个
```

kernel 和两个 semaphore 操作都已经排进了 stream，过了 100 ms，stream 仍然没有完成：CUDA 确实在 GPU 上等着 semaphore 到 1，主机线程没有被阻塞。主机发出信号以后，CUDA 才开始计算，算完把 semaphore 设成 2，Vulkan 那边等到以后读到了正确的结果。

代码里有一行看起来多余的空跑：在等待 semaphore 之前，先用 0 个元素启动一次 kernel。程序的第一版没有这一行，运行时卡死在 `square<<<...>>>` 那一行，永远不返回。原因是 CUDA 默认按需加载 kernel（第 34 章），kernel 第一次启动时才把它装进上下文，而从结果看，这一步要等 GPU 上已经排队的工作做完，排队的工作又在等主机发信号，主机却卡在启动这一行上，于是死锁了。设置环境变量 `CUDA_MODULE_LOADING=EAGER` 也能解决。凡是让 stream 等待一个外部事件、而这个事件要等主机之后才触发的场合，都要当心这个问题。

## 33.5 导入的内存在哪里

导入的内存对 kernel 来说和普通的设备指针没什么两样，但它在哪里，决定了访问它有多快。程序最后用同一个 kernel（每个元素取负）分别在三块内存上读写一遍 64 MB，数据分随机数和全零两种：

```text
读写一遍 64 MB    导入的主机内存   导入的显存   cudaMalloc 的显存
随机数据              5.965 ms        0.435 ms        0.435 ms
全零                  5.970 ms        0.100 ms        0.435 ms
```

导入的主机内存要经过 PCIe 访问，慢了 14 倍；导入的显存和 `cudaMalloc` 的显存一样快。所以和图形 API 共享的数据应该放在显存里，主机可见的内存只适合做中转。

全零那一行有个意外：导入的显存读写全零数据只要 0.1 ms，是 `cudaMalloc` 的四倍多，而随机数据又一样快。这正是第 32 章可压缩内存的特征。看起来驱动给 Vulkan 在显存里的这块分配打开了压缩，图形 API 分配的显存常常是这样。只看全零或者常数数据测出来的带宽，可能会得出错误的结论。

## 33.6 其他 API

Direct3D 12 的互操作和 Vulkan 一样走外部资源接口：内存导出成 NT 句柄，同步用 D3D12 fence（对应 timeline semaphore）。NVIDIA 的嵌入式平台（Jetson、DRIVE）上，相机、编解码器、显示和 CUDA 之间交换数据用 NvSciBuf 和 NvSciSync，CUDA 同样通过 `cudaImportExternalMemory` 和 `cudaImportExternalSemaphore` 导入；那里还常用 EGLImage 和 EGLStream（`cudaGraphicsEGLRegisterImage`）。视频编解码库 NVENC/NVDEC 本身就能直接接受 CUDA 的设备指针。

## 33.7 回头看

互操作让 CUDA 和图形 API 直接访问同一块显存。OpenGL 和 Direct3D 11 以前的 API 用注册、映射、解除映射的模式：注册很贵（这里 5 ms），只做一次；每帧映射和解除映射有隐式同步，这里每帧约 110 us。Vulkan 和 Direct3D 12 用外部资源接口：图形 API 导出内存和 semaphore 的句柄，CUDA 导入，同步完全显式；设备要按 UUID 对上，导入的内存应该在显存里，否则访问要过 PCIe。让 stream 等待一个要由主机稍后触发的外部信号时，kernel 的第一次启动可能因为按需加载而死锁，要先预热 kernel 或者关掉按需加载。

## 33.8 练习

1. 在 `gl_interop.cu` 里把 buffer 改成 1 MB，每帧的映射开销占多大比例？试着把一帧里的映射和解除映射提到循环外面（只映射一次），然后 OpenGL 读回，结果对吗？为什么不能这样做？
2. 用一个 OpenGL 纹理代替 buffer：`cudaGraphicsGLRegisterImage` 注册，映射得到 `cudaArray`，用 surface 对象在 kernel 里写入，再用 `glGetTexImage` 读回检查。
3. 去掉 `vk_interop.cu` 里空跑 kernel 的那一行，确认程序会卡住；再用 `CUDA_MODULE_LOADING=EAGER` 运行同一个程序。
4. 让 Vulkan 用计算着色器或者 `vkCmdFillBuffer` 往显存那块 buffer 里写数据，通过 semaphore 通知 CUDA，CUDA 处理完再通知 Vulkan 拷到主机可见的 buffer 里读回。这就是真实程序里的完整流程。
