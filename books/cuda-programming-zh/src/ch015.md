# 第 15 章 把 host 代码和复杂拷贝放进异步流程

Stream 不只排 kernel。它也可以排异步 copy、memset、event，甚至排一个 host function。真实程序里的数据也不总是一维连续数组：图像有 pitch，三维体数据有 extent，大量小块 copy 可能需要批处理。

本章补上几个容易被略过的工程细节：host function、2D/3D copy 和 batched memory transfer。

## 15.1 问题的由来

基础 vector add 只需要一段连续内存和一个 kernel。但真实应用经常更复杂：

- GPU 工作完成后，需要通知 CPU 侧队列或线程。
- 图像每行有 pitch，不能当作紧密一维数组拷贝。
- 三维体数据需要按 width/height/depth 拷贝。
- 稀疏 tile 或分段 buffer 有很多小 copy，逐个提交开销大。

如果这些工作不进入 stream 依赖系统，你就会被迫在 host 侧用大同步串起来，损失并发机会。

host function 在 stream 里占一个位置，但它运行在 host 上；copy 也在 stream 里占一个位置，但可能由 copy engine 执行。stream 把这些由不同执行者完成的工作按依赖顺序连起来。

## 15.3 详解

### 15.3.1 Host function

新代码优先使用 `cudaLaunchHostFunc`，不再推荐旧的 callback 接口。

```cpp
void CUDART_CB after_gpu(void* user_data)
{
    auto* flag = static_cast<std::atomic<int>*>(user_data);
    flag->store(1, std::memory_order_release);
}
cudaLaunchHostFunc(stream, after_gpu, &flag);
```

这个函数会在 stream 中排在它前面的工作完成后，由 host 执行。它适合做通知、状态更新、唤醒另一个线程、归还 buffer 等轻量工作。

host function 里不能调用任何 CUDA API，包括看起来无害的查询类调用：runtime 可能返回 `cudaErrorNotPermitted`，但并不保证报错，也可能直接死锁。它也不能等待任何没有被规定排在它之前的 GPU 工作。需要据此提交后续 CUDA 工作时，让 host function 只发通知，由另一个 host 线程去调用 CUDA API。

### 15.3.2 2D copy

二维数据常有 pitch。比如图像每行实际存储跨度大于有效宽度。此时不能用一次普通 `cudaMemcpy` 复制 `width * height` 字节，应该用 `cudaMemcpy2D` 或 `cudaMemcpy2DAsync`。

```cpp
cudaMemcpy2DAsync(dst, dst_pitch,
                  src, src_pitch,
                  width_bytes, height,
                  cudaMemcpyDeviceToDevice,
                  stream);
```

这里 `width_bytes` 是每行有效字节数，pitch 是每行跨度。两者不能混淆。

### 15.3.3 3D copy

三维 copy 使用 `cudaMemcpy3DParms` 描述 source、destination、extent：

```cpp
cudaMemcpy3DParms p = {};
p.srcPtr = make_cudaPitchedPtr(src, src_pitch, width, height);
p.dstPtr = make_cudaPitchedPtr(dst, dst_pitch, width, height);
p.extent = make_cudaExtent(width_bytes, height, depth);
p.kind = cudaMemcpyDeviceToDevice;
cudaMemcpy3DAsync(&p, stream);
```

它适合体数据、三维数组、分层图像等场景。核心仍然是把布局信息写清楚。

### 15.3.4 Batched copy

如果程序有大量小 copy，逐个提交可能让 CPU launch overhead 变成瓶颈。batched memory transfer 允许一次提交多个 copy request。使用时要明确每个 request 的源、目的、大小、方向和访问顺序，不能指望 batched API 自动解决数据 hazard。

如果多个 request 之间有重叠或依赖，要么按顺序表达，要么拆成不同阶段。

## 15.4 代码示例

一个 stream 中 copy、kernel、host notification 的组合：

```cpp
struct DoneFlag {
    std::atomic<int>* flag;
};
void CUDART_CB mark_done(void* data)
{
    DoneFlag* done = static_cast<DoneFlag*>(data);
    done->flag->store(1, std::memory_order_release);
}
void submit_image_work(cudaStream_t stream,
                       float* d_dst, size_t dst_pitch,
                       const float* d_src, size_t src_pitch,
                       int width, int height,
                       DoneFlag* done)
{
    size_t width_bytes = static_cast<size_t>(width) * sizeof(float);
    cudaMemcpy2DAsync(d_dst, dst_pitch,
                      d_src, src_pitch,
                      width_bytes, height,
                      cudaMemcpyDeviceToDevice,
                      stream);
    dim3 block(16, 16);
    dim3 grid((width + block.x - 1) / block.x,
              (height + block.y - 1) / block.y);
    process_image<<<grid, block, 0, stream>>>(d_dst, dst_pitch, width, height);
    cudaLaunchHostFunc(stream, mark_done, done);
}
```

这个函数没有在提交后同步。调用者可以继续提交其他工作，稍后再查询 `done->flag` 指向的标志。

## 15.5 工程判断

| 需求 | 用法 | 风险 |
|---|---|---|
| GPU 完成后通知 CPU | `cudaLaunchHostFunc` | 回调里调用任何 CUDA API |
| pitch 图像 copy | `cudaMemcpy2DAsync` | 把 pitch 当 width |
| 三维体数据 copy | `cudaMemcpy3DAsync` | extent 单位和布局描述错误 |
| 大量小 copy | batched transfer | request 间重叠未处理 |
| copy 后 kernel 处理 | copy 和 kernel 放同一 stream | host 先同步再 launch，破坏 overlap |
| host buffer 异步 copy | pinned memory | pageable memory 导致隐式同步 |

## 15.6 API 与要点速查

Host function：

| API | 说明 |
|---|---|
| `cudaLaunchHostFunc` | 在 stream 中排入 host 函数 |
| `cudaStreamAddCallback` | 旧 callback 机制，新代码不优先使用 |

2D/3D copy：

| API | 场景 |
|---|---|
| `cudaMemcpy2D` | 同步二维 copy |
| `cudaMemcpy2DAsync` | stream 中二维 copy |
| `cudaMemcpy3D` | 同步三维 copy |
| `cudaMemcpy3DAsync` | stream 中三维 copy |
| `cudaPitchedPtr` | 描述 pitch 布局 |
| `cudaExtent` | 描述三维范围 |

Batched transfer 关注点：

| 关注点 | 说明 |
|---|---|
| request 粒度 | 太小的 copy 更可能受提交开销影响 |
| overlap | 重叠范围需要明确顺序 |
| stream | batch 本身仍要放入依赖系统 |
| flags | copy 行为和访问顺序由参数决定 |

## 15.7 小结

读完本章，你应该能够：

- 把 host 侧通知放进 stream 顺序里。
- 判断 pitch 数据什么时候需要 2D/3D copy。
- 避免把 pitch、width、extent 混淆。
- 知道 batched copy 解决的是提交开销，不自动解决依赖。
- 把复杂 copy 和 kernel 放在同一异步流程里思考。
