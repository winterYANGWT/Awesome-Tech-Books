# 第 35 章 CUDA C++ 能用到什么程度

CUDA C++ 就是 C++：nvcc 用主机上的 C++ 编译器处理主机代码，设备代码由 NVIDIA 自己的前端编译，支持的语言标准一直跟着主机编译器走，CUDA 13 默认是 C++17，也可以用 `-std=c++20`。但设备代码运行在一个没有操作系统、没有标准库实现、没有异常处理机制的环境里，所以有些 C++ 特性能用，有些不能。这一章先看哪些现代 C++ 写法在设备代码里可以放心使用、哪些不行，再看三个只能在设备代码里使用的功能：调用张量核的 WMMA、为动态规划准备的 DPX 函数，以及在 kernel 里启动 kernel 的动态并行。


```text
$ ./cpp
```

模板、`constexpr`、范围 for 循环、结构化绑定、concept 都能在设备代码里用，它们大多只在编译期起作用，生成的代码和手写的没有区别。`std::floating_point` 这样的 concept 来自主机的标准库头文件，但它只是编译期的判断，所以也能用。

运行期要调用的库函数就不一样了。主机标准库（`std::vector`、`std::string`、`std::cout`……）的函数都是主机函数，设备代码不能调用。设备代码能用的标准库是 libcu++（`cuda::std::` 命名空间），它是 CUDA 自带的 CCCL 库的一部分，提供了 `array`、`span`、`tuple`、`complex`、`optional`、`numeric_limits`、`atomic`（第 22 章用过的 `cuda::atomic_ref` 也在这里）等主机和设备都能用的版本。

## 35.2 不能用的东西

把几种不允许的写法分别用 `-DSHOW_ERROR=1`、`-DSHOW_ERROR=2` 打开编译：

```text
$ nvcc -O2 -arch=native -std=c++20 --extended-lambda -DSHOW_ERROR=1 cpp.cu -o cpp
cpp.cu(86): error: device code does not support exception handling
      if (*p < 0) throw 1;
                  ^

1 error detected in the compilation of "cpp.cu".
$ nvcc -O2 -arch=native -std=c++20 --extended-lambda -DSHOW_ERROR=2 cpp.cu -o cpp 2>&1 | head -4
/usr/include/c++/15/bits/allocator.h(172): error: calling a constexpr __host__ function("__new_allocator") from a __global__ function("bad") is not allowed. The experimental flag '--expt-relaxed-constexpr' can be used to allow this (note: for a __tile__/__tile_global__ caller, the flag guarantees support only for calls that are required by language rules to be evaluated at compile time).
        allocator(const allocator& __a) noexcept
        ^
```

设备代码不支持异常，也不支持运行时类型信息（`typeid`、`dynamic_cast`）。在 kernel 里用 `std::vector`，编译器报的是它内部某个主机函数不能从设备代码调用，错误信息指向标准库的头文件，乍看有点摸不着头脑，看到 “calling a `__host__` function from a `__global__` function” 就该想到这一类问题。提示里的 `--expt-relaxed-constexpr` 允许设备代码调用主机的 `constexpr` 函数，对 `std::vector` 这样要在运行时分配内存的类型并没有用。

虚函数可以用，但有一个条件：

```cpp
{{#include code/ch35/cpp.cu:virtual}}
```

对象在 kernel 里用 `new` 构造（从设备堆上分配，默认 8 MB，可以用 `cudaDeviceSetLimit(cudaLimitMallocHeapSize, ...)` 调大），它的虚函数表指针指向设备代码，调用就没有问题（上面输出的第三行）。如果对象在主机上构造，再整块拷到显存，虚函数表指针指向的是主机上的地址，设备代码沿着它找函数一定会出错。`-DSHOW_ERROR=3` 就是这种写法，在这台机器上 kernel 直接卡死，只能杀掉进程。所以带虚函数的对象不能在主机和设备之间拷贝，需要多态的数据结构，通常改用模板或者用一个类型标签加 `switch`。

## 35.3 张量核：WMMA

第 25 章用 cuBLAS 做 bf16 矩阵乘时达到了 35.7 TFLOPS，是普通单精度运算的好几倍，靠的是张量核（tensor core）：一种专门做小矩阵乘加的运算单元，一条指令由整个 warp 合作完成一次比如 16×16×16 的矩阵乘加。在 CUDA C++ 里直接使用张量核，最简单的接口是 `nvcuda::wmma`（warp matrix multiply-accumulate）。

[wmma.cu](code/ch35/wmma.cu) 先写最直接的版本，每个 warp 负责结果矩阵的一个 16×16 块：

```cpp
{{#include code/ch35/wmma.cu:simple}}
```

`fragment` 是分布在一个 warp 的 32 个线程寄存器里的一个小矩阵，每个线程具体持有哪些元素是不公开的，只能通过 `load_matrix_sync`、`mma_sync`、`store_matrix_sync` 这些函数整体操作。函数名里的 `_sync` 说明 warp 里的所有线程都必须一起调用。半精度输入时片段的形状是 16×16×16，另外还支持 bf16、tf32、int8 等类型和几种形状。

```text
4096×4096×4096，half 输入、float 累加
WMMA 每个 warp 一块，直接读显存   16.66 ms    8.2 TFLOPS  和 cuBLAS 的最大差 0.0e+00
WMMA 经 shared memory 分块         4.23 ms   32.5 TFLOPS  和 cuBLAS 的最大差 0.0e+00

```

直接读显存的版本只有 8.2 TFLOPS，但已经超过了第 25 章寄存器分块的单精度 kernel（5.69 TFLOPS）。加上 shared memory 分块以后达到 32.5 TFLOPS，是 cuBLAS 的 91%，这个差距对几十行代码来说已经很小了。三者的结果完全相同，说明它们沿 K 方向累加的顺序一样；一般来说不同的实现之间会有舍入误差上的差别（第 36 章）。

再往上走，cuBLAS 和 CUTLASS 还用了 WMMA 做不到的东西：WMMA 的片段布局不公开，没法像 PTX 的 `mma.sync` 和 `ldmatrix` 指令那样精细地安排数据在寄存器里怎么摆；搬数据还可以用异步拷贝流水线（第 20 章）；在 H100、B200 这些数据中心 GPU 上还有 `wgmma`、`tcgen05` 这类更大粒度的张量核指令，WMMA 都用不到。实际的程序里，矩阵乘还是应该交给 cuBLAS 或 CUTLASS；WMMA 适合那些需要把小矩阵乘嵌进自己 kernel 的场合，比如把矩阵乘和前后的运算融合在一起。

## 35.4 DPX

序列比对（Smith-Waterman）、动态时间规整这类动态规划算法，内层循环几乎全是“加一个数再和另一个数取最大”。CUDA 12 为此加了一组 DPX 函数，比如 `__viaddmax_s32(a, b, c)` 计算 max(a + b, c)，`__viaddmax_s32_relu` 再和 0 取最大。[dpx.cu](code/ch35/dpx.cu) 用 DPX 函数和手写的 `max` 各写一遍同样的递推：

```cpp
{{#include code/ch35/dpx.cu:kernels}}
```

```text
$ ./dpx
159744 个线程，每个 4096 步：DPX 内建函数 0.849 ms，手写 max 0.881 ms，结果不同的线程 0 个
```

两者几乎一样快。看一下机器码就明白了，分别为本机的 sm_120 和 H100 的 sm_90 编译，统计取最大值一类的指令：

```text
$ nvcc -cubin -arch=sm_120 dpx.cu -o dpx_sm_120.cubin && cuobjdump -sass dpx_sm_120.cubin  # 按 kernel 统计 min/max 类指令
  29 _Z12dp_intrinsicPKiPii VIMNMX.S32
  29 _Z12dp_intrinsicPKiPii VIMNMX.S32.RELU
  15 _Z8dp_plainPKiPii VIMNMX.S32
  15 _Z8dp_plainPKiPii VIMNMX.S32.RELU
$ nvcc -cubin -arch=sm_90 dpx.cu -o dpx_sm_90.cubin && cuobjdump -sass dpx_sm_90.cubin  # 按 kernel 统计 min/max 类指令
  5 _Z12dp_intrinsicPKiPii VIADDMNMX
  5 _Z12dp_intrinsicPKiPii VIADDMNMX.RELU
  29 _Z8dp_plainPKiPii VIADDMNMX
  29 _Z8dp_plainPKiPii VIADDMNMX.RELU
```

sm_90 有把加法和取最大合在一起的 `VIADDMNMX` 指令，而且手写的 `max(h + sc, e)` 也被编译器认了出来，同样用上了这条指令。sm_120 没有这条指令，DPX 函数和手写的代码都编译成普通的取最大值指令加上单独的加法（各自的循环展开程度不同，所以条数不一样）。也就是说，DPX 函数是一种可移植的写法，在任何 GPU 上都能编译运行，硬件加速只在部分架构上有；而在有硬件支持的架构上，编译器往往也能从普通的写法里认出来。这类“专用指令”到底有没有用上，最可靠的办法是看机器码（第 4 章）。

## 35.5 动态并行：在 kernel 里启动 kernel

动态并行（CUDA Dynamic Parallelism，CDP）允许设备代码用三尖括号启动 kernel，适合那些要处理多少工作、怎么划分，只有在 GPU 上算到一半才知道的问题。编译时要加 `-rdc=true`（可重定位设备代码）并链接 `libcudadevrt`。

先看启动的开销。[cdp.cu](code/ch35/cdp.cu) 分别让主机、一个 GPU 线程、4096 个 GPU 线程启动 4096 个空 kernel：

```cpp
{{#include code/ch35/cdp.cu:launch}}
```

```text
$ ./cdp
启动 4096 个空 kernel：主机上逐个启动 6.76 ms，一个 GPU 线程逐个启动 17.94 ms，4096 个 GPU 线程各启动一个 0.44 ms
```

设备端启动的 kernel 要放进一个 stream。CUDA 12 起的新版动态并行提供了两个特殊的 stream：`cudaStreamFireAndForget`，启动以后各自独立执行；`cudaStreamTailLaunch`，等父 grid 做完再执行，适合安排“这一步做完再做下一步”。父 grid 要等它启动的所有子 grid 都完成，才算完成，所以主机等父 kernel 就等于等全部子 kernel。旧版里在设备代码中调用 `cudaDeviceSynchronize` 等待子 grid 的写法，CUDA 12 已经不再支持。

一个 GPU 线程逐个启动，每次要 4.4 us，比主机上的 1.65 us 还慢，设备端启动并不便宜。但很多线程同时启动时，平均每个只要 0.1 us，设备端启动的优势在于可以大量并行地发出。

再看一个有实际意义的例子：一组长度极不均匀的段，每段求和。4096 段里，每 64 段有一段长 52 万多，其余只有 256。三种做法：

```cpp
{{#include code/ch35/cdp.cu:segments}}
```

```text
4096 段，共 34586624 个 float（138 MB），最长的段 524288，最短的 256：
  一个线程一段                12.125 ms，错误 0 段
  一个 block 一段              0.671 ms，错误 0 段
  长段再启动子 grid（CDP）      0.430 ms，错误 0 段
  （读一遍这些数据按 336 GB/s 算要 0.412 ms）
```

一个线程一段最慢：64 个线程各自顺序读 2 MB，其余线程早就做完了，而且同一个 warp 里相邻线程读的地址相隔很远，没法合并访问。一个 block 一段好得多，但 64 个长段各自只有一个 block，最后一段时间里只有这 64 个 block 在跑，GPU 没有被占满。用动态并行，长段由 block 的 0 号线程按段的长度启动一个子 grid，最多 128 个 block 合作求和，总时间 0.43 ms，已经接近按显存带宽算的下限。

不用动态并行也能做到同样的负载均衡：比如先在主机上把长段挑出来单独启动一个 kernel，或者事先把所有段切成大小相近的工作块，算出各块的部分和再加回各段（类似第 11 章归约的两步做法）。动态并行的好处是写起来直接，尤其是段的长度、要不要细分本身就是在 GPU 上算出来的时候，不用把信息传回主机再决定。代价是 `-rdc=true` 下编译器对设备函数的优化更保守，可能让别的 kernel 也慢一点，设备端启动本身也有开销，所以只在工作量确实不规则时才值得用。

## 35.6 回头看

设备代码可以使用模板、lambda、`constexpr`、concept、结构化绑定等现代 C++ 特性，标准库要用 libcu++ 的 `cuda::std::` 版本；异常、运行时类型信息和主机标准库的运行期函数不能用；虚函数可以用，但对象必须在设备上构造。WMMA 让 CUDA C++ 直接使用张量核，几十行的分块 kernel 达到了 cuBLAS 91% 的速度。DPX 函数在 sm_90 上有专门的指令，在本机的 sm_120 上编译成普通指令，速度和手写的一样。动态并行在设备上启动 kernel，单个线程逐个启动比主机还慢，大量线程并行启动则很快；处理长度不均匀的段时，长段由子 grid 分担，速度接近显存带宽的上限。
