# 第 86 章 MD whole-code data residency：为什么只迁移一个 kernel 不够

## 86.1 问题的由来

force-only CUDA port 往往能带来第一轮加速，但也会暴露下一个瓶颈：如果每个时间步都把位置从 host 拷到 device，再把力和势能拷回 host，数据传输可能吞掉 kernel 带来的加速。端到端案例需要走到这一层，而不是停在“写了一个 kernel”。

## 86.2 核心模型

| 阶段 | 数据位置 | 风险 |
|---|---|---|
| CPU baseline | 全部在 host | 计算热点慢 |
| force-only port | 位置/力在 host 与 device 之间往返 | kernel 加速被传输抵消 |
| whole-code port | 主循环关键数组常驻 device | 需要迁移更多函数和同步边界 |

判断数据该不该常驻 device，要看一个时间步内哪些数据需要频繁跨越 PCIe/NVLink，而不是看还能多写几个 kernel。

## 86.3 详解

回到[第 85 章](ch085.md)的 force-only port。它的 host 包装函数 `compute_forces_gpu` 替代了 CPU 版的 `compute_forces_cpu`，主循环每个时间步调用一次：

```cpp
struct DeviceArrays {               // cudaMalloc 得到的 device 指针，初始化时分配一次
    double *x, *y, *z, *fx, *fy, *fz, *epot;
    int *nbr_count, *nbr_list;      // nbr_list 已按转置布局上传，邻居表不变时不必重传
};

void compute_forces_gpu(MdSystem& s, const DeviceArrays& dev)
{
    const size_t bytes = sizeof(double) * s.count;

    // 1. 位置刚在 host 上做完积分更新，每步都要 H2D
    cudaMemcpy(dev.x, s.x.data(), bytes, cudaMemcpyHostToDevice);
    cudaMemcpy(dev.y, s.y.data(), bytes, cudaMemcpyHostToDevice);
    cudaMemcpy(dev.z, s.z.data(), bytes, cudaMemcpyHostToDevice);

    // 2. 在 device 上求力
    const int block = 128;
    const int grid = (s.count + block - 1) / block;
    forces_kernel<<<grid, block>>>(s.count, s.box_len, dev.nbr_count, dev.nbr_list,
                                   dev.x, dev.y, dev.z,
                                   dev.fx, dev.fy, dev.fz, dev.epot);

    // 3. 下一步的积分和能量统计还在 host 上，力和势能每步都要 D2H
    cudaMemcpy(s.fx.data(), dev.fx, bytes, cudaMemcpyDeviceToHost);
    cudaMemcpy(s.fy.data(), dev.fy, bytes, cudaMemcpyDeviceToHost);
    cudaMemcpy(s.fz.data(), dev.fz, bytes, cudaMemcpyDeviceToHost);
    cudaMemcpy(s.epot.data(), dev.epot, bytes, cudaMemcpyDeviceToHost);
}
```

每调用一次就是 3 次 H2D 和 4 次 D2H，而且这里的 `cudaMemcpy` 都是同步拷贝：D2H 要等 kernel 算完、数据拷回才返回，CPU 拿到力之后才能继续积分；CPU 做积分的这段时间里，GPU 则完全空闲。如果这段代码每个时间步都要执行一次，程序就仍然被 host/device 边界切得很碎。进一步迁移的思路可以概括为：位置、速度、力、势能、邻居表等主循环数据尽量常驻 device；积分、求和、速度缩放等与这些数组紧密相关的步骤，也要逐步移到 device 上。

## 86.5 工程判断

| 迁移候选 | 什么时候迁 |
|---|---|
| 积分更新 | 如果每步都依赖 position/velocity/force，且这些数组已在 device |
| 势能/动能归约 | 如果每步或频繁输出需要总能量 |
| 速度缩放 | 如果温控步骤频繁触碰全体粒子速度 |
| 邻居表更新 | 如果构建成本高，且数据布局适合 GPU |
| host 输出 | 保留为低频边界，不要放在每个细粒度步骤里 |

## 86.6 API 与要点速查

| 要点 | 说明 |
|---|---|
| 数据驻留 | 关注点从“单个 kernel 的加速”转到“整个时间步的数据路径” |
| 归约 | 能量求和等归约可以参考 atomic 与 warp 函数（[第 73 章](ch073.md)）和 Cooperative Groups（[第 43 章](ch043.md)） |
| 迁移顺序 | 本章给出的是迁移顺序和判断依据，具体代码要结合自己的程序结构来写 |

## 86.7 小结

读完本章，你应该能够在 force-only port 的基础上继续追问：数据每步在哪里，哪些数组被反复搬运，哪些 CPU 函数应该跟着热点一起迁移。端到端 CUDA 优化看的不是 kernel 数量，而是主循环的数据路径能不能稳定地留在 device 上。
