# 第 30 章 多 GPU

第七部分收拢一些系统层面的话题：多 GPU、Driver API、跨进程共享、和图形 API 互操作、运行时的环境变量，以及 CUDA C++ 和浮点运算的一些细节。它们不是每个 CUDA 程序都要用到，但遇到的时候需要知道从哪里下手。这几章比前面的短，有些内容在这台只有一张笔记本显卡的机器上没法实测，遇到这种情况会明确说出来。

这一章讲多 GPU。CUDA 不会自动把一个 kernel 分到几张卡上，多 GPU 程序的分工完全由主机代码安排：在每张卡上分配内存、创建 stream、启动 kernel，卡和卡之间需要交换数据时自己安排拷贝和同步。这台机器只有一张卡，所以本章的程序都写成对任意张卡都成立，然后在一张卡上运行；30.5 节会说明，这样做本身就是调试多 GPU 程序的一个好办法。

`cudaGetDeviceCount` 返回的是这个进程能看到的设备数，设备编号从 0 开始。能看到哪些设备，由环境变量 `CUDA_VISIBLE_DEVICES` 控制。用几种不同的设置分别运行：

```text
能否直接访问对方显存（行访问列）：
   -
$ CUDA_VISIBLE_DEVICES=1 ./devices
CUDA_VISIBLE_DEVICES=1
devices.cu:23: cudaErrorNoDevice (no CUDA-capable device is detected)
$ CUDA_VISIBLE_DEVICES=0,1 ./devices
CUDA_VISIBLE_DEVICES=0,1
设备 0：NVIDIA GeForce RTX 5060 Laptop GPU，计算能力 12.0，7746 MB，PCI 0000:01:00.0，UUID GPU-58d8291b-a226-84b5-774b-f273795c8484

能否直接访问对方显存（行访问列）：
   -
$ CUDA_VISIBLE_DEVICES=1,0 ./devices
CUDA_VISIBLE_DEVICES=1,0
devices.cu:23: cudaErrorNoDevice (no CUDA-capable device is detected)
$ CUDA_VISIBLE_DEVICES=0,0 ./devices
CUDA_VISIBLE_DEVICES=0,0
devices.cu:23: cudaErrorInvalidDevice (invalid device ordinal)
```

几点值得注意：

- 不设置时能看到全部设备。设成空字符串，一个也看不到，`cudaGetDeviceCount` 返回 `cudaErrorNoDevice`。
- 可以写编号，也可以写 UUID（`nvidia-smi -L` 能查到），UUID 只要写出足以区分的前缀就行。不管怎么写，进程里的设备总是重新从 0 开始编号：如果设 `CUDA_VISIBLE_DEVICES=2,3`，进程里的设备 0 就是机器上的 2 号卡。
- 列表里遇到不存在的编号，从那里起后面的都被忽略：`0,1` 只剩设备 0，`1,0` 一个都没有。重复的编号直接报错。这些情况都不会给出警告，所以写脚本时最好让程序启动时打印一下实际看到的设备。

还有一个容易混淆的地方：CUDA 默认把算力强的卡排在前面，而 `nvidia-smi` 按 PCI 总线号排序，两边的编号在装了不同型号显卡的机器上可能对不上。设置 `CUDA_DEVICE_ORDER=PCI_BUS_ID` 可以让 CUDA 也按总线号排序；用 UUID 指定设备则完全没有这个问题。

`CUDA_VISIBLE_DEVICES` 最常见的用途，是在多卡机器上让每个进程只看到一张卡：同时启动几个进程，各设一个不同的值，每个进程都以为自己在一台单卡机器上运行。很多时候，这比在一个进程里管理多张卡简单得多，30.6 节再说。

## 30.2 当前设备

在一个进程里使用多张卡，靠的是“当前设备”：调用 `cudaSetDevice(d)` 以后，这个主机线程后面的 `cudaMalloc`、创建 stream 和 event、启动 kernel，都发生在设备 d 上。没有调用过的话，当前设备是 0。

当前设备是每个主机线程各自的状态。新创建的线程不会继承创建它的线程的设置，它的当前设备仍然是 0。用多个线程分别驱动几张卡时，每个线程开头都要先调用 `cudaSetDevice`。同一个进程里，所有线程使用同一张卡时共享同一个上下文（第 31 章），一个线程在这张卡上分配的内存，别的线程可以直接用。

stream 和 event 在创建时就属于当时的当前设备，此后不会改变。按照编程指南，混用不同设备的对象有以下规则（这台机器只有一张卡，没法演示出错的情况）：

- 往不属于当前设备的 stream 里启动 kernel，会失败。
- 往不属于当前设备的 stream 里发起内存拷贝，可以成功。
- `cudaEventRecord` 要求 event 和 stream 属于同一个设备；两个 event 属于不同设备时，`cudaEventElapsedTime` 会失败。
- `cudaStreamWaitEvent` 可以让一个设备的 stream 等待另一个设备上的 event，这是不同的卡之间建立先后顺序的基本手段。`cudaEventSynchronize` 和 `cudaEventQuery` 也可以用于别的设备的 event。

内存则不需要记它属于哪个设备。64 位系统上所有设备的显存和主机的 pinned 内存共用一个统一的虚拟地址空间（UVA），指针本身就能说明它在哪里：`cudaPointerGetAttributes` 可以查到一个指针属于哪个设备，`cudaMemcpy` 用 `cudaMemcpyDefault` 时运行时会自己判断拷贝方向。但统一地址空间只是说地址不会冲突，不等于一张卡的 kernel 能直接读另一张卡的显存，那需要下一节的 peer access。

## 30.3 卡和卡之间

两张卡之间的连接方式决定了它们能否直接访问对方的显存。`devices.cu` 的后半部分检查每两张卡之间的情况：

```cpp
{{#include code/ch30/devices.cu:peer}}
```

`cudaDeviceCanAccessPeer(&can, a, b)` 回答设备 a 能否直接访问设备 b 的显存。能的话，在设备 a 是当前设备时调用 `cudaDeviceEnablePeerAccess(b, 0)` 打开，此后 a 上的 kernel 可以直接读写 b 上分配的内存，指针照常传进去就行。这个开关是单向的，b 访问 a 要在 b 上另外打开。`cudaDevP2PAttrPerformanceRank` 给出这条连接相对的快慢，数字越小越快。

这台机器只有一张卡，矩阵只有对角线，实在没什么可看的。`nvidia-smi topo -m` 显示的拓扑也是如此：

```text
$ nvidia-smi topo -m
        GPU0    CPU Affinity    NUMA Affinity   GPU NUMA ID
GPU0     X      0-31    0               N/A
```

在多卡机器上，这个矩阵的每一格会标出两张卡之间的连接方式：`NV#` 是通过 NVLink 直连；`PIX`、`PXB` 是挂在同一个 PCIe 交换芯片下面；`PHB`、`NODE` 要经过 CPU 的 PCIe 根节点；`SYS` 要跨过两颗 CPU 之间的互联。越往后越慢，跨 CPU 插槽的 P2P 往往干脆不支持。另外两列说明这张卡离哪些 CPU 核和哪个 NUMA 节点近，驱动这张卡的主机线程和它用的 pinned 内存最好放在那里。很多消费级显卡不支持 P2P，即使插在同一个 PCIe 交换芯片下面也一样，一切以 `cudaDeviceCanAccessPeer` 的结果为准。

不支持 P2P 也照样能在卡之间拷贝数据。`cudaMemcpyPeerAsync(dst, dst_dev, src, src_dev, bytes, stream)` 把一张卡上的数据拷到另一张卡上：打开了 peer access 时直接通过 NVLink 或 PCIe 传输，否则驱动经过主机内存中转，结果一样，只是更慢、更占 PCIe 带宽。所以代码可以统一用 peer 拷贝，能打开 peer access 就打开，不能也不影响正确性。

## 30.4 把一个网格分到几张卡上

最常见的多 GPU 分工方式是区域分解：把数据切成几块，每张卡负责一块，相邻的块每步交换边界。[halo.cu](code/ch30/halo.cu) 用二维热传导演示这个过程：4096×4096 的网格，每个格点每步变成自己和上下左右四个邻居的加权平均，上下左右都是周期边界。网格按行切成 P 块，每块除了自己负责的行，上下还各多存一行邻居的数据，叫 halo（或 ghost cell）。每一步开始前，各块从上下邻居那里各拷来一行，填进自己的 halo，然后各自计算。

每一步分两个阶段。先交换 halo：每块在自己的 stream 上，等上下邻居上一步的计算做完（`cudaStreamWaitEvent`，event 可以属于别的设备），再用 peer 拷贝从邻居那里取来一行。然后各块在自己的 stream 上计算，记下 `done`：

```cpp
{{#include code/ch30/halo.cu:step}}
```

这里只有一个主机线程，在循环里不停切换当前设备，依次给每张卡下达任务。因为这些调用都是异步的，主机线程很快就把一步的任务都发出去了，各张卡同时执行，不需要每张卡一个线程。主机线程每发一步要调用几十次 API，块数很多时它可能成为瓶颈，那时再考虑多线程。

同步的设计要想清楚两件事。第一，拷贝邻居的边界行之前，邻居必须已经把这一行算完，这由等待邻居的 `done` 保证。第二，拷贝完成之前，邻居不能开始覆盖这一行。程序用两个缓冲轮流读写：第 k 步从 `u[k % 2]` 读、往另一个写，所以第 k 步拷走的行要到邻居的第 k + 1 步才会被覆盖；而邻居的第 k + 1 步要先等这一块第 k 步的 `done`，这时这一块第 k 步的拷贝早已完成，因为拷贝和计算在同一个 stream 里排在 `done` 前面。

只有一张卡时，所有的块都在设备 0 上。程序先用 1 块跑出参考结果，再用不同的块数各跑一遍，和参考结果逐点比较：

```text
$ ./halo 2 4 8 16 32 64
1 个设备，打开了 0 对 peer access；网格 4096×4096，200 步
  块数    每步       相对 1 块   和 1 块结果的最大差
     1    0.406 ms
     2    0.407 ms      1.00   0
     4    0.408 ms      1.01   0
     8    0.413 ms      1.02   0
    16    0.417 ms      1.03   0
    32    0.428 ms      1.05   0
    64    0.445 ms      1.10   0
```

不论切成几块，结果都和不切分时逐位相同：每个格点的计算公式和顺序都一样，只是数据放的地方不同，结果本来就该一模一样，任何一点差别都说明分块或同步有错。在同一张卡上切成 64 块，每步要做 128 次小拷贝、64 次 kernel 启动，时间只多了 10%。

这组时间说明不了多卡上能快多少。到了多卡上，每张卡的计算量变成 1/N，但每步要多出卡间的 halo 拷贝（每行 16 KB，经过 PCIe 时主要是延迟）和跨卡的同步。这个例子每步的计算有 0.4 ms，两张卡时每张卡的计算降到 0.2 ms 左右，相比之下几次十几 KB 的拷贝不算什么；但网格越小、每步的计算越少，拷贝和同步占的比例就越大。真实的程序还会先算内部、同时拷贝 halo，最后再算边界行，把通信藏到计算后面（练习 1）。

## 30.5 先在一张卡上把同步调对

切成几块放在同一张卡上运行，并不只是没有多卡时的权宜之计。各块用的是不同的 stream，即使在同一张卡上，它们也会并发执行，块之间的同步写错了，在单卡上一样会暴露出来。把 halo 交换前的两个 `cudaStreamWaitEvent` 去掉，运行两次：

```text
$ ./halo nowait 2 4 8 16
1 个设备，打开了 0 对 peer access；网格 4096×4096，200 步，块之间不等待
  块数    每步       相对 1 块   和 1 块结果的最大差
     1    0.406 ms
     2    0.407 ms      1.00   0.48534
     4    0.407 ms      1.00   0.499477
     8    0.412 ms      1.02   0.464447
    16    0.418 ms      1.03   0.460545
$ ./halo nowait 2 4 8 16
1 个设备，打开了 0 对 peer access；网格 4096×4096，200 步，块之间不等待
  块数    每步       相对 1 块   和 1 块结果的最大差
     1    0.406 ms
     2    0.407 ms      1.00   0.48534
     4    0.406 ms      1.00   0.510441
     8    0.412 ms      1.02   0.488266
    16    0.418 ms      1.03   0.521404
```

格点的数值在 0 到 100 之间，0.5 的误差已经很明显了，而且两次运行的结果不一样：可能拷到了邻居还没算完的行，也可能拷贝之前邻居已经开始写下一步，具体发生哪一种取决于各个 stream 的调度时机。这正是第 13 章说过的，不同 stream 之间没有任何顺序保证。时间上几乎看不出差别，因为每块的拷贝和计算本来就都排在 GPU 上，省掉的只是两次等待。

单卡测试也有查不出的错误。所有的块都在设备 0 上时，漏掉一句 `cudaSetDevice`、在错误的设备上分配了内存，程序照样正确；也测不出打开 peer access 前后的性能差别。所以单卡上验证的是分块和同步的逻辑，到了多卡机器上，还要再跑一遍同样的比较。到时候在代码里用 `cudaPointerGetAttributes` 检查每块的缓冲确实在它该在的设备上（练习 3），可以让这类错误直接报出来，而不是表现为莫名其妙的变慢。

## 30.6 其他组织方式

上面的程序是一个进程管理所有的卡。另一种做法是一个进程只管一张卡：启动 N 个进程，用 `CUDA_VISIBLE_DEVICES` 或者在程序开头按进程编号调用 `cudaSetDevice`，进程之间用 MPI 通信。大规模的科学计算程序几乎都是这样组织的，因为同一份代码可以从一台机器的几张卡扩展到几百台机器。支持 CUDA 的 MPI 实现可以直接收发显存指针，同一台机器内的卡之间还能走 P2P。

卡之间需要的如果是归约、广播、全收集这类集合通信（深度学习的数据并行训练每一步都要把各张卡的梯度加起来），应该用 NCCL。它针对 NVLink、PCIe 和网络的拓扑选择通信路径，自己手写 peer 拷贝很难达到它的效率。需要在 kernel 里直接读写其他卡（甚至其他机器）上的数据时，有 NVSHMEM。

托管内存也可以用于多 GPU，第 16 章的 `cudaMemAdvise` 可以设置一块数据的首选位置、声明哪些卡会访问它，但多张卡交替写同一块托管内存时，页面会在卡之间来回迁移，性能很难预测。同一台机器上不同进程之间共享显存，见第 32 章。

## 30.7 回头看

进程能看到哪些卡由 `CUDA_VISIBLE_DEVICES` 决定，进程里的编号总是从 0 开始，写错的项会让后面的项被悄悄忽略。`cudaSetDevice` 设置当前主机线程的当前设备，之后的分配、stream、event 和 kernel 都属于它；跨卡的先后顺序用 `cudaStreamWaitEvent` 建立。peer 拷贝在任何两张卡之间都能用，支持 P2P 并打开 peer access 后走直连路径。把网格分块、按块号轮流分配到各张卡上，一张卡的机器也能运行多卡的代码：分块的结果必须和不分块逐位相同，块之间漏掉同步在单卡上同样会暴露出来。

## 30.8 练习

1. 改写 `step`：先算每块的内部行（不依赖 halo 的行），同时在另一个 stream 上做 halo 拷贝，等拷贝完成再算上下两条边界行。单卡上的每步时间有变化吗？在多卡上你预计会怎样？
2. 改成每张卡一个主机线程（`std::thread`），每个线程负责分配到自己那张卡上的块。块之间的 event 怎么传递？注意每个线程开头的 `cudaSetDevice`。
3. 在 `step` 开头用 `cudaPointerGetAttributes` 检查每块的两个缓冲都在 `q.dev` 上。然后故意删掉 `setup` 里的 `cudaSetDevice`，单卡上这个检查能发现问题吗？
4. 如果你能用到多卡的机器：运行 `devices` 看看 P2P 矩阵，再分别在打开和不打开 peer access 时运行 `halo`，比较每步时间。
