# 第 34 章 调节运行时行为

同一个 CUDA 程序，不改代码、不重新编译，行为也可能因为驱动的设置而不同：kernel 什么时候装进 GPU、PTX 要不要现场编译、编译结果缓存在哪里、出错时打印多少信息、各个 stream 能用多少 SM。这些大多通过环境变量控制，少数（比如 green context）通过 API。这一章挑几个最常碰到的，在这台机器上逐个试一试。

## 34.1 kernel 什么时候装进 GPU

nvcc 把每个编译单元（.cu 文件）的设备代码编成一个模块，嵌在可执行文件里。程序运行时，这些模块要装进 GPU 的上下文才能启动其中的 kernel。早期的 CUDA 在建立上下文时把所有模块一次装完；从 CUDA 12.2 起，Linux 上默认改成按需加载（lazy loading）：kernel 第一次启动时才装载它。环境变量 `CUDA_MODULE_LOADING=EAGER` 可以恢复一次装完的方式。第 4 章已经看到过它对第一次启动时间的影响，这里再看看显存占用，以及一个不太明显的副作用。

[lazy.cu](code/ch34/lazy.cu) 用模板实例化出 200 个不同的 kernel，另一个文件 [lazy_late.cu](code/ch34/lazy_late.cu) 里还有一个，它在可执行文件里是另一个模块。程序先测建立上下文的时间和显存占用：

```cpp
{{#include code/ch34/lazy.cu:init}}
```

再测其中一个 kernel 第一次和第二次启动到完成的时间：

```cpp
{{#include code/ch34/lazy.cu:first}}
```

两种加载方式各运行一次（完整的输出在下一节一起看）：

```text
$ ./lazy busy
加载方式 LAZY：建立上下文 235.3 ms，显存已用 122 MB
work<7> 第一次启动到完成 8.493 ms，第二次 0.034 ms
$ CUDA_MODULE_LOADING=EAGER ./lazy busy
加载方式 EAGER：建立上下文 179.8 ms，显存已用 138 MB
work<7> 第一次启动到完成 0.049 ms，第二次 0.034 ms
```

按需加载时，kernel 第一次启动要多花 8 ms 多来装载，第二次就和一次装完的一样快了。一次装完的方式则把这些代价放在建立上下文时，还多占了 16 MB 显存，因为 200 个 kernel 的机器码都装进去了。建立上下文的时间波动比较大，多次运行，按需加载一般在 150 到 170 ms，一次装完多 20 ms 左右。

这个程序只有 200 个 kernel，差别还不大。cuBLAS、cuDNN、PyTorch 这样的库里有成千上万个 kernel，一个程序实际用到的往往只是其中一小部分，按需加载能省下几百 MB 显存和可观的启动时间，这是它成为默认方式的原因。代价是第一次启动变慢了，所以测量 kernel 的时间之前一定要先预热（前面各章的程序都这样做了）。

顺便一提，这台笔记本的独显打开了运行时电源管理，空闲一阵就会断电，偶尔会看到建立上下文花了 2.7 秒，那是在等 GPU 上电和驱动初始化。服务器上通常打开 persistence 模式（`nvidia-smi -pm 1` 或者 `nvidia-persistenced` 服务），让驱动始终保持初始化状态。

## 34.2 按需加载的隐患

按需加载还有一个不那么明显的副作用。程序的最后一部分，让 stream `s1` 处于两种“没做完”的状态之一：要么正在执行一个还要跑 300 ms 的 kernel，要么排着一个等主机线程放行的主机函数（2 秒后放行）。然后在另一个 stream `s2` 上第一次启动另一个模块里的 kernel，看启动这一行要花多久：

```cpp
{{#include code/ch34/lazy.cu:blocked}}
```

```text
$ ./lazy busy
加载方式 LAZY：建立上下文 235.3 ms，显存已用 122 MB
work<7> 第一次启动到完成 8.493 ms，第二次 0.034 ms
s1 上的 kernel 还要跑 300 ms时，第一次启动另一个模块里的 kernel：启动这一行花了 280.0 ms
$ ./lazy host
加载方式 LAZY：建立上下文 166.4 ms，显存已用 122 MB
work<7> 第一次启动到完成 9.129 ms，第二次 0.034 ms
s1 在等主机放行时，第一次启动另一个模块里的 kernel：启动这一行花了 1980.1 ms
$ CUDA_MODULE_LOADING=EAGER ./lazy busy
加载方式 EAGER：建立上下文 179.8 ms，显存已用 138 MB
work<7> 第一次启动到完成 0.049 ms，第二次 0.034 ms
s1 上的 kernel 还要跑 300 ms时，第一次启动另一个模块里的 kernel：启动这一行花了 0.1 ms
$ CUDA_MODULE_LOADING=EAGER ./lazy host
加载方式 EAGER：建立上下文 185.0 ms，显存已用 138 MB
work<7> 第一次启动到完成 0.052 ms，第二次 0.034 ms
s1 在等主机放行时，第一次启动另一个模块里的 kernel：启动这一行花了 0.1 ms
```

一次装完时，启动只要 0.1 ms，本来就该这样，启动是异步的。按需加载时，启动这一行阻塞了 280 ms，正好等到 `s1` 上的 kernel 跑完；`s1` 在等主机放行时，它一直等到 2 秒后放行为止。也就是说，在这台机器上，装载一个新模块要等上下文里已经提交的工作都完成，不管它们在哪个 stream 上。

这带来两个问题。一是隐藏的同步：流水线运行到一半，第一次用到某个模块里的 kernel，主机线程会停下来等 GPU 上所有的工作做完，本来重叠得好好的 CPU 和 GPU 突然串行了一次。二是死锁：如果某个 stream 在等主机之后才会做的事（主机函数里等一个标志、等一个外部 semaphore），而主机线程恰好在这之前第一次启动一个新模块里的 kernel，启动永远不会返回。第 33 章的 Vulkan 互操作程序第一版就是这样卡死的，这里那个 2 秒后自动放行的线程，就是为了不让程序真的卡死。

解决办法是在程序初始化时，让会用到的 kernel 提前装载：每个 kernel 先空跑一次，或者对它调用一次 `cudaFuncGetAttributes`（在这台机器上试过，调用以后再启动就不阻塞了）。对这类问题敏感、又不在乎多占一些显存的程序，也可以直接设置 `CUDA_MODULE_LOADING=EAGER`。

## 34.3 PTX、JIT 和缓存

第 4 章讲过，可执行文件里的 fatbin 可以装机器码（SASS），也可以装 PTX，PTX 要由驱动编译成机器码才能运行；装什么由 nvcc 的 `-arch` 和 `-gencode` 选项决定。把 `lazy.cu` 用三种选项各编译一次，用 `cuobjdump` 看看里面有什么：

```text
$ nvcc -O2 -arch=native lazy.cu lazy_late.cu -lcuda -o lazy && cuobjdump --list-elf --list-ptx lazy
ELF file    1: lazy.1.sm_120.cubin
ELF file    2: lazy.2.sm_120.cubin
ELF file    3: lazy.3.sm_120.cubin
$ nvcc -O2 -arch=sm_120 lazy.cu lazy_late.cu -lcuda -o lazy_both && cuobjdump --list-elf --list-ptx lazy_both
ELF file    1: lazy_both.1.sm_120.cubin
ELF file    2: lazy_both.2.sm_120.cubin
PTX file    1: lazy_both.1.sm_120.ptx
ELF file    3: lazy_both.3.sm_120.cubin
PTX file    2: lazy_both.2.sm_120.ptx
$ nvcc -O2 -gencode arch=compute_120,code=compute_120 lazy.cu lazy_late.cu -lcuda -o lazy_ptx && cuobjdump --list-elf --list-ptx lazy_ptx
PTX file    1: lazy_ptx.1.sm_120.ptx
PTX file    2: lazy_ptx.2.sm_120.ptx
```

`-arch=native` 只为本机的 GPU 生成机器码（cubin），没有 PTX；`-arch=sm_120` 同时放了机器码和 PTX；只写 `code=compute_120` 则只有 PTX。（第 1 个 cubin 里没有 kernel，第 2 个是 `lazy.cu` 的 201 个，第 3 个是 `lazy_late.cu` 的 1 个。）程序运行时，驱动优先使用和 GPU 匹配的机器码；没有的话，就把 PTX 现场编译（JIT）成机器码。只有机器码的程序在更新一代的 GPU 上无法运行，带上 PTX 则可以由新驱动 JIT 编译，所以分发出去的程序通常至少带一份最新架构的 PTX。

JIT 的代价有多大？用只有 PTX 的版本，在空的缓存目录里运行两次：

```text
$ nvcc -O2 -gencode arch=compute_120,code=compute_120 lazy.cu lazy_late.cu -lcuda -o lazy_ptx
$ CUDA_CACHE_PATH=./cache ./lazy_ptx busy          # 缓存目录是空的
加载方式 LAZY：建立上下文 164.3 ms，显存已用 122 MB
work<7> 第一次启动到完成 13718.623 ms，第二次 0.034 ms
$ CUDA_CACHE_PATH=./cache ./lazy_ptx busy          # 再运行一次
加载方式 LAZY：建立上下文 158.6 ms，显存已用 122 MB
work<7> 第一次启动到完成 46.523 ms，第二次 0.034 ms
$ du -sh cache
32M	cache
$ rm -rf cache; CUDA_CACHE_PATH=./cache CUDA_MODULE_LOADING=EAGER ./lazy_ptx busy
加载方式 EAGER：建立上下文 13978.2 ms，显存已用 138 MB
work<7> 第一次启动到完成 0.054 ms，第二次 0.034 ms
$ CUDA_DISABLE_PTX_JIT=1 ./lazy_ptx busy
加载方式 LAZY：建立上下文 2723.8 ms，显存已用 122 MB
lazy.cu:82: cudaErrorJitCompilationDisabled (PTX JIT compilation was disabled)
```

第一次运行，`work<7>` 的第一次启动花了 13.7 秒：按需加载时，JIT 发生在模块装载的时候，而且整个模块的 201 个 kernel 都要编译。第二次运行只要 47 ms，因为驱动把 JIT 的结果存进了缓存目录（32 MB）。一次装完的方式下，同样的 14 秒挪到了建立上下文的时候。设置 `CUDA_DISABLE_PTX_JIT=1` 禁止 JIT，只有 PTX 的 kernel 就无法启动了。这个变量可以用来检查程序是否真的带了本机能用的机器码：一个本该有机器码的程序如果在这个设置下报错，就说明它一直在悄悄地 JIT。

和缓存相关的环境变量有三个：`CUDA_CACHE_PATH` 指定缓存目录（Linux 上默认是 `~/.nv/ComputeCache`），`CUDA_CACHE_MAXSIZE` 指定缓存的大小上限，`CUDA_CACHE_DISABLE=1` 关闭缓存。第 31 章看到，NVRTC 的编译缓存也放在这里。容器里运行的程序每次启动都是新的文件系统，缓存目录如果不挂载到持久的存储上，每次启动都要重新 JIT。另外还有一个 `CUDA_FORCE_PTX_JIT=1`，按文档的说法会让驱动忽略机器码、一律 JIT 编译 PTX，但在这台机器上试的时候，没有看到它对 `lazy` 和 `lazy_both` 产生预期的效果。

## 34.4 让驱动说清楚错误

CUDA 的错误码往往很笼统。[log.cu](code/ch34/log.cu) 犯了两个常见的错误，返回的都是 `cudaErrorInvalidValue`，看不出是哪个参数不对。设置 `CUDA_LOG_FILE` 以后，驱动会把详细的原因写到指定的文件里（`stdout`、`stderr` 表示标准输出、标准错误）：

```text
$ ./log
启动 2048 个线程的 block：cudaErrorInvalidValue
申请 200 KB 动态 shared memory：cudaErrorInvalidValue
$ CUDA_LOG_FILE=stdout ./log
[15:47:15.158][123908492591104][CUDA][E] One or more of block dimensions of (2048,1,1) exceeds corresponding maximum value of (1024,1024,64)
[15:47:15.158][123908492591104][CUDA][E] Returning 1 (CUDA_ERROR_INVALID_VALUE) from cuLaunchKernel
启动 2048 个线程的 block：cudaErrorInvalidValue
[15:47:15.158][123908492591104][CUDA][E] Requested dynamic shared memory size of 204800 bytes exceeds maximum dynamic shared memory size of 49152 bytes
[15:47:15.158][123908492591104][CUDA][E] Returning 1 (CUDA_ERROR_INVALID_VALUE) from cuLaunchKernel
申请 200 KB 动态 shared memory：cudaErrorInvalidValue
```

日志直接说出了错在哪里：block 的 x 维度 2048 超过了上限 1024；申请的 204800 字节动态 shared memory 超过了默认的上限 49152 字节（第 7 章，要更多得先用 `cudaFuncSetAttribute` 申请）。调试时这比对着错误码猜要快得多。

其他几个常用的环境变量，前面各章已经遇到过：`CUDA_LAUNCH_BLOCKING=1` 让每次 kernel 启动都同步执行，错误会在出错的那次启动处报出来（第 5 章）；`CUDA_VISIBLE_DEVICES` 和 `CUDA_DEVICE_ORDER` 控制进程能看到哪些 GPU、怎样编号（第 30 章）。

还有一个经常被提起的 `CUDA_DEVICE_MAX_CONNECTIONS`，它设置主机和 GPU 之间硬件工作队列的数量，默认是 8。老资料的说法是：stream 比队列多时，几个 stream 共用一个队列，同一个队列里的工作会互相阻塞，产生“假依赖”。[connections.cu](code/ch34/connections.cu) 用 16 个 stream 检验这一点，每个 stream 先后两个互相依赖的 kernel，每个 kernel 跑 5 ms，分别按 stream 依次发和交错着发：

```cpp
{{#include code/ch34/connections.cu:issue}}
```

```text
$ for c in "" 1 2 8 32; do CUDA_DEVICE_MAX_CONNECTIONS=$c ./connections; done
CUDA_DEVICE_MAX_CONNECTIONS=未设置 按 stream 依次发：  10.1 ms   交错着发：  10.0 ms
CUDA_DEVICE_MAX_CONNECTIONS=1      按 stream 依次发：  10.1 ms   交错着发：  10.0 ms
CUDA_DEVICE_MAX_CONNECTIONS=2      按 stream 依次发：  10.1 ms   交错着发：  10.0 ms
CUDA_DEVICE_MAX_CONNECTIONS=8      按 stream 依次发：  10.1 ms   交错着发：  10.0 ms
CUDA_DEVICE_MAX_CONNECTIONS=32     按 stream 依次发：  10.1 ms   交错着发：  10.0 ms
```

如果有假依赖，队列少时总时间会明显超过理想的 10 ms。在这块 GPU 上，即使只有 1 个队列，16 个 stream 也完全并行（换成 64 个 stream 也一样）。至少在这台机器上，不必为这个变量操心。有些分布式训练框架把它设成 1，目的是让通信 kernel 严格按发出的顺序执行，这个用法依赖的是同一个机制，在新的 GPU 上是否还成立，也要实测确认。

## 34.5 green context：给不同的工作划分 SM

最后看一个用 API 调节的功能。设想一个推理服务：GPU 上一直跑着一个占满所有 SM 的后台任务（比如批量处理），同时不时有一个很小的请求要尽快完成。[green.cu](code/ch34/green.cu) 模拟这个场景：后台 kernel 有 3900 个 block，每个 block 占着 SM 忙 2 ms，整个 kernel 在全部 26 个 SM 上大约跑 150 ms；在它运行期间，每隔 5 ms 发一个只有 8 个 block 的请求，共 20 个，每个请求用自己的 stream，测量从发出到完成的时间。

前两种做法用普通的 stream：一种是请求和后台用同样的优先级，一种是请求用高优先级的 stream。第三种用 green context，把 SM 分成两份，请求和后台各用各的：

```cpp
{{#include code/ch34/green.cu:green}}
```

`cudaDeviceGetDevResource` 取得设备的 SM 资源，`cudaDevSmResourceSplitByCount` 从中分出一组（这里要求至少 4 个 SM），剩下的放在 `rest` 里。每份资源生成一个描述符，再各建一个 green context。green context 本身不是当前上下文那样的东西，用法是从它创建 stream：在这样的 stream 上启动的 kernel，只会被调度到这份资源包含的 SM 上。

```cpp
{{#include code/ch34/green.cu:trials}}
```

```text
$ ./green
共 26 个 SM，最小分区 8 个、按 8 个对齐；分给请求 8 个，后台 18 个
GPU 空闲                  请求延迟 中位数   0.129 ms，最大   0.893 ms
普通 stream               请求延迟 中位数  97.449 ms，最大 145.053 ms；后台 kernel  150.0 ms
请求用高优先级 stream     请求延迟 中位数   1.200 ms，最大   2.098 ms；后台 kernel  150.0 ms
green context 各用各的 SM  请求延迟 中位数   0.217 ms，最大   0.473 ms；后台 kernel  218.0 ms
```

第一行说明了划分的粒度：这块 GPU 的分区最少 8 个 SM、按 8 个对齐，所以要求 4 个，实际分到了 8 个，后台用剩下的 18 个。

用普通的 stream，请求延迟的中位数是 97 ms，最长 145 ms，几乎就是等后台 kernel 跑完。GPU 的 block 调度器基本上按 kernel 发出的顺序分配 SM：后台 kernel 还有 block 没分配出去，后来的请求就分不到 SM。请求用高优先级的 stream 时，调度器一有空位就先给它，但已经在运行的 block 不会被打断，所以请求要等某个后台 block 结束，平均等 1 ms 左右，最长约 2 ms，正好是一个后台 block 的时长。用 green context 时，请求有自己的 8 个 SM，延迟和 GPU 空闲时差不多（这里的延迟是用 stream 里紧跟请求的主机函数测的，包括了主机函数被调用的延迟，所以空闲时也有 0.1 ms 以上）。

代价也很清楚：后台 kernel 只能用 18 个 SM，从 150 ms 变成了 218 ms，正好是 150 × 26 / 18。而且没有请求的时候，那 8 个 SM 也只能空着。green context 适合延迟要求严格、值得为它预留资源的场合；如果只是希望请求不要等太久，高优先级 stream 加上让后台 kernel 的 block 短一些，往往就够了。多个进程共享 GPU 时，类似的划分由 MPS（Multi-Process Service）完成，用环境变量 `CUDA_MPS_ACTIVE_THREAD_PERCENTAGE` 限制每个进程能用的 SM 比例。

## 34.6 回头看

CUDA 12.2 以后默认按需加载模块：建立上下文更快、显存占用更少，代价是 kernel 第一次启动时才装载；在这台机器上，装载新模块要等上下文里已提交的工作都完成，会造成隐藏的同步，甚至死锁，初始化时预热 kernel 或设置 `CUDA_MODULE_LOADING=EAGER` 可以避免。只带 PTX 的程序要在运行时 JIT，这里 201 个 kernel 的模块要编译 14 秒，有缓存时降到 47 ms；`CUDA_DISABLE_PTX_JIT=1` 可以检查程序是否在悄悄 JIT。`CUDA_LOG_FILE` 让驱动说出错误的具体原因。`CUDA_DEVICE_MAX_CONNECTIONS` 在这块 GPU 上没有测出任何影响。green context 把 SM 划分给不同的 stream，能让小请求在 GPU 被占满时依然立即执行，代价是被划走的 SM 别人不能用。
