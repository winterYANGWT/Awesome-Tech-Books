# 第 19 章 Cooperative Groups 与 thread block cluster

前面的 kernel 里，线程之间的协作只有两个层次：warp 内用 shuffle（第 11 章），block 内用 shared memory 和 `__syncthreads()`（第 9 章）。block 之间则完全不能直接协作，要么等 kernel 结束，要么通过 global memory 加原子操作。这一章介绍两样扩展协作范围的工具：Cooperative Groups 把“哪些线程在一起协作”写成显式的对象，并提供整个 grid 的同步；thread block cluster 让几个 block 被一起调度，可以直接读写彼此的 shared memory。每样工具都会实测，其中有一个结果和设计初衷相差很远。

## 19.1 把线程组写成对象

Cooperative Groups 是 CUDA 自带的一个头文件库（`<cooperative_groups.h>`）。它把线程组表示成对象：整个 block 是一个 `thread_block`，可以再切成固定大小的 `thread_block_tile`，整个 grid 是一个 `grid_group`。组提供同步、编号、以及组内的集体操作。[cg_reduce.cu](code/ch19/cg_reduce.cu) 用它重写了第 11 章版本 4 的归约：

```cpp
{{#include code/ch19/cg_reduce.cu:cg}}
```

```text
手写 shuffle    0.768 ms  和 = 3.352087e+07
Cooperative Groups  0.766 ms  和 = 3.352087e+07
```

速度和结果完全一样，编译出来的指令基本相同。区别在可读性和安全性：`cg::reduce(warp, sum, cg::plus<float>())` 一眼就能看出是在 warp 内求和，不用自己写 shuffle 循环、自己管掩码；`block.sync()` 明确了同步的范围；`warp.meta_group_rank()` 说明了“这是第几个 warp”。还可以写接收线程组参数的函数，同一个函数既能用于 warp，也能用于 16 个线程的小组。第 6 章说过 warp 内的线程不保证步调一致，Cooperative Groups 的集体操作都会正确地处理同步，写起来更不容易出错。

## 19.2 整个 grid 一起同步

block 之间不能互相等待，原因在第 3 章讲过：GPU 不保证所有 block 同时在运行，一个 block 等另一个还没被调度的 block，就会永远等下去。但如果 grid 小到所有 block 都能同时驻留在 GPU 上，全 grid 同步就是安全的。Cooperative Groups 的 `grid.sync()` 就是这样的同步，代价是 kernel 必须用 `cudaLaunchCooperativeKernel` 启动，由运行时检查 grid 是否满足条件。

[gridsync.cu](code/ch19/gridsync.cu) 做一个一维平滑迭代：每一步把每个元素换成它和左右邻居的平均值，共 1000 步，每一步都依赖上一步全部完成。通常的写法是每步启动一个 kernel，kernel 的结束就是天然的全局同步。另一种写法是只启动一个常驻的 kernel，在步与步之间同步整个 grid：

结果可能出乎意料：每步工作量大的时候，两种写法一样快；只有每步的工作量小到一两微秒时，常驻 kernel 才快一点（1.43 µs 对 1.11 µs）。这说明两件事。第一，连续启动的 kernel 之间，GPU 侧的衔接只要一微秒多一点，只要 host 提交得过来（第 17 章），启动开销并没有想象中大；第二，`grid.sync()` 本身也要一微秒左右，所有 block 要通过 global memory 互相确认到齐。最后一行说明了协作启动的限制：grid 比能同时驻留的 block 数多一个，启动就直接失败。

所以全 grid 同步的价值主要不在省启动开销，而在于两点：步与步之间，每个线程的寄存器和 shared memory 里的数据都还在，不必像重新启动 kernel 那样从 global memory 重新读一遍；以及能在一个复杂的算法中间任意插入全局同步点，而不必把算法拆成很多个 kernel。

## 19.3 thread block cluster

从计算能力 9.0 开始，CUDA 在 block 和 grid 之间加了一个层次：**thread block cluster**。一个 cluster 由几个 block 组成，硬件保证它们被同时调度到相邻的一组 SM 上（同一个 GPC）。于是 cluster 内的 block 之间可以同步，还能直接读写彼此的 shared memory，这叫**分布式 shared memory**（distributed shared memory）。这块 RTX 5060 的计算能力是 12.0，也支持 cluster。

用法有两种。大小固定时，在 kernel 上加 `__cluster_dims__(2, 1, 1)` 这样的属性；大小要在运行时决定时，用 `cudaLaunchKernelEx` 加一个启动属性。kernel 里通过 `cg::this_cluster()` 拿到 cluster 对象，`cluster.sync()` 同步整个 cluster，`cluster.map_shared_rank(ptr, rank)` 把本 block 的 shared memory 地址换成 cluster 里第 `rank` 个 block 对应的地址，之后就可以像普通指针一样读写。一个 cluster 最多 8 个 block（可移植的上限），能同时驻留多少个 cluster，用 `cudaOccupancyMaxActiveClusters` 查询。

典型的设想用途是：一个 block 的 shared memory 不够大时，让几个 block 合起来用。直方图是个例子：64K 个桶需要 256 KB，单个 block 最多只有 99 KB 的 shared memory，放不下；分给一个 cluster 里的 4 个 block，每个 64 KB，就放下了。[cluster_hist.cu](code/ch19/cluster_hist.cu) 就是这么做的：

## 19.4 在这块 GPU 上，分布式 shared memory 很慢

是 shared memory 原子操作本身慢，还是跨 block 访问慢？程序的第三组实验把桶数减到 16K（64 KB），单个 block 也放得下，cluster 大小从 1 到 4：

```text
16384 个桶，均匀分布
   2.23 ms  global memory 原子加
   0.98 ms  cluster：1 个 block 一组，每个 block 64 KB，共 26 组
   6.79 ms  cluster：2 个 block 一组，每个 block 32 KB，共 13 组
  11.33 ms  cluster：4 个 block 一组，每个 block 16 KB，共 6 组
```

cluster 大小为 1，也就是每个 block 只用自己的 shared memory，是最快的，比 global 原子加快一倍多。一旦有一半的原子操作要打到另一个 block 的 shared memory 上，就慢了 7 倍；四分之三打到别人那里，慢了 11 倍。问题出在跨 block 的访问上。

再直接量一下读的带宽。[dsm_read.cu](code/ch19/dsm_read.cu) 让每个 block 反复成块地读一段 32 KB 的数据，数据分别来自自己的 shared memory、cluster 里另一个 block 的 shared memory、以及 global memory（这么小的数据会留在 L2 里）：

```cpp
{{#include code/ch19/dsm_read.cu:kernel}}
```

```text
   7905 GB/s  自己的 shared memory
    282 GB/s  cluster 里另一个 block 的 shared memory
   1768 GB/s  global memory（在 L2 里）
```

在这块笔记本 GPU 上，读另一个 block 的 shared memory 比读自己的慢 28 倍，甚至比读 L2 还慢 6 倍。cluster 和分布式 shared memory 的设计初衷，是让同一个 GPC 里的 SM 通过一条专门的通路快速交换数据，比绕道 L2 更快；这块 GPU 在功能上支持它，程序能正确运行，但性能上完全不是这么回事。不同的 GPU 上结果可能截然不同，数据中心级的 GPU 是这项功能的主要目标。这里没有那样的硬件，没法给出对照数字。

这个结果的教训比结论本身更重要：GPU 的新特性未必在每一款支持它的硬件上都有同样的性能，使用之前要在目标硬件上量一量。在这块 GPU 上，需要比单个 block 更大的 shared memory 时，更实际的办法是把问题拆小，让每个 block 只处理放得进自己 shared memory 的一部分（比如 16K 桶的直方图就比 global 原子加快一倍），或者干脆依靠 L2。

## 19.5 回头看

Cooperative Groups 把线程组写成对象，让协作的范围和同步一目了然，`cg::reduce` 这样的集体操作和手写 shuffle 一样快。`grid.sync()` 能在一个 kernel 里同步整个 grid，前提是用协作启动、所有 block 能同时驻留；它本身也要一微秒左右，在这里只在每步工作量极小时才比逐个启动 kernel 快，更大的价值在于跨步保留寄存器和 shared memory 里的数据。thread block cluster 让几个 block 一起调度、互相读写 shared memory，但在这块笔记本 GPU 上，跨 block 访问 shared memory 比读 L2 还慢，用之前务必实测。
