# 第 6 章 warp：硬件真正的执行单位

第 3 章提到，block 里的线程每 32 个组成一个 warp。写 kernel 时我们面对的是一个个线程，每个线程有自己的下标、自己的变量，可以走自己的分支。但硬件并不是一个线程一个线程地执行的，它一次取一条指令，让一个 warp 的 32 个线程同时执行。这种方式叫 SIMT（single instruction, multiple threads）。

先把两个名词说清楚（图 6.1）。block 里的线程从 0 开始编号，每 32 个一组，这一组就是 **warp**；线程在自己那个 warp 里排第几，叫它的 **lane**，从 0 到 31。一维的 block 里这样算：

```cpp
int warp = threadIdx.x / 32;   // 这个线程属于 block 里的第几个 warp
int lane = threadIdx.x % 32;   // 在这个 warp 里排第几
```

二维、三维的 block 先按第 3 章说的 x 优先顺序编成一维的号，`threadIdx.x + threadIdx.y * blockDim.x + threadIdx.z * blockDim.x * blockDim.y`，再这样分。32 在代码里也可以写成内置变量 `warpSize`。执行时，调度器一次取一条指令交给一个 warp，它的 32 个 lane 同时执行这条指令，各自用自己的寄存器、算自己的数据。

<noscript><p class="cu-warp-fallback">block 有 128 个线程：threadIdx.x 0–31 是 warp 0，32–63 是 warp 1，64–95 是 warp 2，96–127 是 warp 3。每个 warp 里的线程按 lane 0–31 排列，lane = threadIdx.x % 32。</p></noscript>

</figure>

这样做的好处在第 1 章已经看到了：取指令、译码、调度这些控制逻辑由 32 个线程共用，芯片面积可以省下来多放运算单元。代价是：当同一个 warp 里的线程想走不同的路时，硬件只能让它们轮流走。这一章量一量这个代价有多大，以及怎么避开它。

## 6.1 分支发散

[diverge.cu](code/ch06/diverge.cu) 里的 kernel 让每个线程属于 `ways` 条路径中的一条，每条路径做同样多的计算，线程只做自己那一条：

```cpp
{{#include code/ch06/diverge.cu:kernel}}
```

线程归属哪条路径有两种分法：`by_warp` 为真时，按 warp 编号分，同一个 warp 的 32 个线程走同一条路径；否则按 lane 分，相邻的线程走不同的路径。不管哪种分法，每个线程的计算量都完全一样，总计算量也一样。

按 warp 分的时候，路径再多，时间也不变。按线程分的时候，时间和路径数成正比，32 条路径时慢了 31 倍。

原因就在 SIMT。一个 warp 执行到 `if (path == p)` 时，32 个线程各自判断条件，结果可能有真有假。硬件的处理办法是：条件为真的那部分线程执行 `if` 里面的代码，其余线程原地等着；然后再轮到别的分支。这种情况叫**分支发散**（branch divergence）。按线程分路径时，每个 warp 里 32 条路径都有人要走，`for (p ...)` 循环的每一轮都得执行一遍内层计算，每次只有一个线程在干活，所以是 32 倍的时间。按 warp 分时，一个 warp 里所有线程条件相同，不需要执行的那 31 轮整个 warp 一起跳过，没有任何浪费。

可以直接看到哪些线程在执行。`__activemask()` 返回一个 32 位的掩码，第 k 位为 1 表示 lane k 此刻正在执行这条指令。[mask.cu](code/ch06/mask.cu) 让 lane 0、3、6……走 `if`，其余走 `else`，在两个分支里各打印一次掩码：

```cpp
{{#include code/ch06/mask.cu:kernel}}
```

```text
if   分支：49249249
else 分支：b6db6db6
分支之前：ffffffff
```

`0x49249249` 的二进制是 `0100 1001 0010 0100 1001 0010 0100 1001`，正好是第 0、3、6……30 位；`0xb6db6db6` 是它的补集。两个分支分别由一部分线程执行，分支之前和之后，32 个线程都在。

## 6.3 让同一个 warp 走同一条路

发散的代价取决于同一个 warp 里的线程有多“不一样”。所以减少发散的思路是：把行为相近的工作安排到同一个 warp 里。

排序本身也要花时间。如果数据只处理一次，排序的开销可能抵消收益；如果同一批数据要处理很多遍（比如模拟里每个时间步都要处理所有粒子），或者排序可以顺带在别的步骤里完成，就很值得。第 24 章会用 GPU 上的库函数做排序。

别的减少发散的办法本质上都一样：

- 让分支条件依赖 warp 编号或 block 编号，而不是 lane 编号。比如两类工作分别交给不同的 block，而不是同一个 block 里的奇偶线程。
- 把不规则的工作量拆平。如果每个线程要处理的元素个数差别很大（比如图里每个顶点的邻居数不同），干得快的线程只能等干得慢的；可以改成一个 warp 合作处理一个元素，或者先把工作分组。
- 很短的分支不用操心。`x > 0 ? a : b` 这类分支，编译器通常直接让所有线程把两边都算一遍再挑结果，根本不产生跳转。

## 6.4 warp 怎么被调度

再从调度的角度看 warp。这块 GPU 的每个 SM 分成 4 个分区，每个分区有一个 warp 调度器和 32 条 FP32 运算通道（4 × 32 = 128，就是第 1 章说的每个 SM 128 条通道）。每个周期，调度器从分到自己名下的 warp 里挑一个已经准备好的（下一条指令的操作数都已就绪），发射它的一条指令。

某个 warp 发出读显存的指令后，数据要几百纳秒才回来，在这之前，用到这个数据的下一条指令发不出去。图 6.5 用一个简化的模型演示调度器这时怎么办：每个 warp 反复执行“3 条计算、1 条读显存”，读显存的结果要 16 个周期后才能用，下一轮的第一条计算就要用它。调度器的规则是：上个周期发射的 warp 还能发，就接着发它；不能发了，就换一个准备好的、最久没发射过的 warp。选一个调度器名下的 warp 数，按“播放”或“单步”看每个周期发射了谁。

模型里一轮是 19 个周期（3 条计算加 16 个周期的等待），一个 warp 一轮只能发 4 条指令，所以要 19 ÷ 4，向上取整是 5 个 warp，调度器才不会空着。真实的显存延迟是几百个周期，要填满就需要多得多的 warp，或者每个 warp 在等数据之前有更多不依赖它的指令可做。这块 GPU 的一个 SM 最多驻留 1536 个线程，也就是 48 个 warp，每个调度器名下 12 个。

第 1 章说“GPU 靠大量线程掩盖延迟”，在硬件层面就是这样实现的：只要每个周期都能找到一个准备好的 warp，运算单元就不会闲着。驻留的 warp 越多，调度器的选择余地越大，第 10 章会接着讨论这一点。

## 6.5 warp 里的线程并不保证同步执行

最后一个容易误解的地方。既然一个 warp 的 32 个线程执行同一条指令，是不是可以认为它们总是步调一致？

早期的 GPU 上基本是这样，于是有不少代码依赖这一点，比如 warp 内的线程不加同步就互相读写 shared memory，认为“反正同一个 warp 是一起执行的”。但从 Volta（计算能力 7.0）开始，每个线程有了自己的程序计数器，发散的分支可以交错执行，编译器和硬件也不再保证 warp 内的线程在任意时刻都处于同一条指令。依赖“warp 内天然同步”的老代码可能会出错，而且错误时有时无。

需要 warp 内线程协作时，要显式地写出来：用 `__syncwarp()` 让 warp 内的线程在某一点会合；或者用带 `_sync` 后缀的 warp 级函数，比如 `__shfl_sync`（在线程之间直接交换寄存器里的值）、`__ballot_sync`（统计 warp 里哪些线程的条件为真）。这些函数的第一个参数是一个掩码，说明哪些线程参与。第 11 章会用 `__shfl_sync` 写一个很快的归约。

## 6.6 回头看

硬件以 warp 为单位执行指令，同一个 warp 的线程走不同分支时要轮流执行，代价和 warp 内的路径数成正比，最坏可达 32 倍。ncu 的 `smsp__thread_inst_executed_per_inst_executed.ratio` 能直接量出发散的程度。减少发散的办法是让同一个 warp 里的线程做相似的事：按类型排序数据、让分支条件以 warp 或 block 为单位。warp 也是调度的单位，调度器靠在多个 warp 之间切换来掩盖延迟。需要 warp 内协作时，要用 `__syncwarp()` 和 `_sync` 系列函数显式同步。
