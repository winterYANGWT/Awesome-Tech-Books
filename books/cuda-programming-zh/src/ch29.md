# 第 29 章 让数据留在 GPU 上

上一章结尾的诊断很清楚：GPU 上的工作每步只要零点几毫秒，大部分时间都耗在 CPU 建邻居表和数据来回拷贝上。这一章把时间步的每个阶段都放到 GPU 上：粒子数据在程序开始时拷上去一次，此后一直留在显存里，只有在报告能量时才把两个数拷回来。程序是 [md_gpu.cu](code/ch29/md_gpu.cu)。

## 29.1 整个时间步都在 GPU 上

积分的两个半步都是每个粒子各自更新，写成 kernel 毫无难度；求力沿用上一章的混合精度 kernel；剩下的就是建邻居表。时间步循环变成了一串 kernel 启动：

```cpp
{{#include code/ch29/md_gpu.cu:loop}}
```

循环里的 event 只是为了分阶段计时。报告能量时，一个 kernel 把动能和势能各自加起来，只拷回两个 `double`。

## 29.2 在 GPU 上建邻居表

CPU 版本的格子法用链表把每个格子里的粒子串起来，这在 GPU 上不好做：成千上万个线程同时往链表里插入，要么用原子操作，要么就乱了。GPU 上更常用的办法是排序：

```cpp
{{#include code/ch29/md_gpu.cu:cells}}
```

一共四步：

1. 每个线程算出一个粒子所在的格子号。
2. 以格子号为键、粒子编号为值，用 CUB 的基数排序排一遍（第 24 章）。排好以后，同一个格子里的粒子在数组里挨在一起。
3. 每个线程看排序结果里的一个位置，如果它和前一个位置的格子号不同，这里就是一个格子的开头；和后一个不同，就是结尾。这样就得到了每个格子在排序结果里的起止位置。
4. 每个线程负责一个粒子，按起止位置遍历周围 27 个格子里的粒子，把距离足够近的写进邻居表，同样转置存放。

`rebuild` 把这四步串起来（中间那段重新排列的代码，29.4 节再说）：

```cpp
{{#include code/ch29/md_gpu.cu:rebuild}}
```

第四步的距离判断和求力 kernel 一样用了混合精度：第一版全用 `double`、每个候选粒子做三次双精度除法，建一次邻居表要 11 ms，每步分摊 1.1 ms，比求力还慢好几倍；改成和上一章一样的写法以后，降到了五分之一。这块 GPU 上，kernel 里的双精度运算要格外小心。

## 29.4 数据布局：粒子的编号顺序

程序还有一个隐藏的有利条件：粒子是按 FCC 晶格的顺序生成的，编号相邻的粒子在空间上也相邻。求力时，一个 warp 里的 32 个线程处理 32 个编号相邻的粒子，它们的邻居也大多是同一批粒子，读 `x[j]` 时缓存的命中率很高。真实的程序里，粒子的编号往往是任意的，比如从文件读入、或者经过很多步扩散以后。

把初始的粒子编号随机打乱，模拟这种情况：

```cpp
{{#include code/ch29/md_gpu.cu:shuffle}}
```

```text
$ ./md_gpu shuffled
55296 个粒子，500 步，14×14×14 个格子，初始随机打乱，之后顺序不变
总能量相对漂移 1.7e-05

阶段                      GPU 时间    每步
求力（含后半步 kick）      180.0 ms   0.360 ms
邻居表                   173.6 ms   0.347 ms
积分（前半步）             10.3 ms   0.021 ms
整个循环（墙钟时间）      367.1 ms   0.734 ms
```

计算的内容完全一样，结果也一样，求力和建邻居表却都慢了一大截，每步从 0.445 ms 变成 0.734 ms。现在一个 warp 里的 32 个粒子在空间上散落各处，它们的邻居也各不相同，读邻居坐标的访问分散到了整个数组上，缓存几乎不起作用了。

解决办法也就在建邻居表的过程里：既然已经按格子号排好了序，就顺手把所有粒子数组按这个顺序重新排列一遍（`rebuild` 里 `reorder` 那一段），让空间上相邻的粒子在内存里也相邻：

```text
$ ./md_gpu reorder
55296 个粒子，500 步，14×14×14 个格子，初始随机打乱，重建邻居表时按格子重新排列
总能量相对漂移 1.7e-05

阶段                      GPU 时间    每步
求力（含后半步 kick）      112.6 ms   0.225 ms
邻居表                    85.9 ms   0.172 ms
积分（前半步）             10.3 ms   0.021 ms
整个循环（墙钟时间）      212.0 ms   0.424 ms
```

每步 0.424 ms，不但恢复了，还比原始的晶格顺序略快一点：按格子排序后，同一个格子里的粒子编号是连续的，建邻居表时一个格子的粒子坐标正好是连续的一段内存。重新排列每 10 步做一次，每次只是几个 gather kernel，代价可以忽略。这和第 8 章的结论是一回事：数据怎么摆，往往和算法本身一样重要。更讲究的程序会按空间填充曲线（比如 Morton 序或 Hilbert 序）排列粒子，局部性更好。

## 29.5 回头看

把整个时间步都留在 GPU 上以后，55296 个粒子的 MD 程序每步从 35.65 ms 降到 0.424 ms，快了 84 倍；只移植求力时只快了 1.6 倍。关键的几步是：在 GPU 上用“算格子号、排序、找边界、查周围格子”建邻居表；计算中尽量用单精度，双精度只留给相减和累加；每次重建邻居表时按格子顺序重新排列粒子，保持数据的空间局部性。第六部分的案例到此结束，它把前面几部分的内容串了起来：合并访问、混合精度、库函数、Amdahl 定律，以及最重要的一条，让数据留在 GPU 上。
