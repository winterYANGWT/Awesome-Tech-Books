# 第 24 章 Thrust 与 CUB

第 1 章说过，能用现成的库就先用库。第五部分介绍几个最常用的 CUDA 库，这一章从 Thrust 和 CUB 开始：前者让你像用 C++ 标准库一样在 GPU 上排序、归约、扫描，后者提供构成这些算法的高性能积木，既能整体调用，也能嵌进自己的 kernel。两者都随 CUDA Toolkit 一起提供，只需要包含头文件（CUDA 13 里它们的头文件在 `include/cccl/` 下，nvcc 会自动找到）。

本部分的示例选题参考了樊哲勇《CUDA 编程：基础与实践》（清华大学出版社，2020）。该书基于 CUDA 10.x 编写，部分工具和性能结论已经过时，这里只沿用示例思路。

## 24.1 像用标准库一样用 GPU

Thrust 的核心是 `thrust::device_vector`，它像 `std::vector` 一样管理一块显存，构造时可以直接从主机数据拷贝：

```cpp
{{#include code/ch24/thrust_basics.cu:vectors}}
```

在它上面可以调用和标准库同名的算法。[thrust_basics.cu](code/ch24/thrust_basics.cu) 在 3200 多万个元素上做了几种常见的操作，并和 CPU 单线程的标准库实现比较：

```text
33554432 个元素           GPU（Thrust）   CPU 单线程
排序 unsigned            4.7 ms     1845.4 ms   结果一致
平方和                  0.47 ms       13.4 ms   相对差 4.6e-08
前缀和                  0.94 ms       13.6 ms
只保留正数              1.53 ms      117.3 ms   留下 16766384 / 16766384 个
按 1000 组统计         10.05 ms   第 0 组：33496 个元素，和 16.73
```

排序快了将近 400 倍。Thrust 对整数这类可以按位比较的键用的是基数排序，非常适合 GPU：

分组统计是数据处理里的常见需求，相当于 SQL 的 `GROUP BY`。在 GPU 上的标准做法是先按组号排序，让同一组的元素挨在一起，再用 `reduce_by_key` 对每一段连续的相同键做归约：

```cpp
{{#include code/ch24/thrust_basics.cu:groupby}}
```

这里用了 `__device__` lambda，编译时要加 `--extended-lambda`。`constant_iterator<int>(1)` 是一个“永远返回 1”的虚拟序列，对它按组求和就是计数。这和第 6 章按类型排序数据的思路一样：排序之后，同类的数据挨在一起，处理起来又快又简单。

使用 Thrust 要注意它的同步行为。像 `transform_reduce` 这样把结果返回给主机的算法，必然要等 GPU 算完才能返回；其他算法默认也会在返回前同步。想要异步执行、或者放进指定的 stream，用执行策略 `thrust::cuda::par_nosync.on(stream)` 作为第一个参数。另外，Thrust 和自己写的 kernel 可以混用：`thrust::raw_pointer_cast(v.data())` 取出 `device_vector` 的裸指针传给 kernel；反过来，`thrust::device_pointer_cast(p)` 把 `cudaMalloc` 来的指针包装成 Thrust 算法能接受的迭代器。

## 24.2 反复调用：CUB 和预分配的临时空间

排序、扫描这类算法需要临时空间。Thrust 每次调用都在内部申请一块，用完释放。数据量小、调用频繁时，这笔开销就显出来了（第 18 章）。CUB 的设备级算法把临时空间交给调用者管理，第 11 章的 `cub::DeviceReduce::Sum` 已经见过这种接口：

```cpp
{{#include code/ch24/repeat_sort.cu:cub}}
```

[repeat_sort.cu](code/ch24/repeat_sort.cu) 把同样大小的排序各做 100 次：

```text
     元素个数    thrust::sort    CUB（预分配临时空间）   CUB 需要的临时空间
        65536        40.5 us              36.0 us               0.3 MB   结果一致
      1048576       154.7 us             114.3 us               4.1 MB   结果一致
     16777216      2432.8 us            2191.6 us              66.1 MB   结果一致
```

（两边的计时里都包含每轮一次同样大小的显存内拷贝：Thrust 是原地排序，每轮要先恢复输入。）CUB 快了 10% 到 26%。临时空间并不小，排 1600 多万个元素要 66 MB，这正是 Thrust 每次都要申请的。CUB 的设备级算法还都接受一个 stream 参数，可以放进第 13 章那样的流水线里。

实际上 Thrust 的大部分 CUDA 后端就是建立在 CUB 之上的。一般的经验是：写起来方便、调用不频繁时用 Thrust；在性能敏感的循环里、或者需要精确控制内存和 stream 时用 CUB。

## 24.3 在自己的 kernel 里用 CUB

CUB 更独特的地方，是它还提供 block 级和 warp 级的原语，可以直接用在自己的 kernel 里。第 11 章手写的 block 内归约，换成 `cub::BlockReduce` 是这样：

```cpp
{{#include code/ch24/block_reduce.cu:cub}}
```

```text
 0.772 ms  和 = 3.352087e+07  手写 shuffle
 0.770 ms  和 = 3.352087e+07  cub::BlockReduce
```

一样快，结果相同。`BlockReduce` 需要的 shared memory 由 `TempStorage` 类型描述，调用者声明一份传进去，这样同一块 shared memory 还能在别处复用。类似的原语还有 `cub::BlockScan`（block 内前缀和）、`cub::BlockRadixSort`（block 内排序）、`cub::BlockLoad` 和 `cub::BlockStore`（按合并访问的方式成块读写，第 8 章）、`cub::WarpReduce` 等。写一个需要“block 内先归约一下”“block 内先排个序”的 kernel 时，用这些原语比自己写更可靠，而且它们会针对不同的 GPU 架构选择合适的实现。

## 24.4 回头看

Thrust 用标准库风格的接口提供 GPU 上的排序、归约、扫描、流压缩、分组统计，在 3200 万个元素上比 CPU 单线程快几十到几百倍，写起来和标准库几乎一样。它的算法默认会同步，并在每次调用时临时申请内存；反复调用时，用 CUB 预先分配临时空间能快 10% 到 26%。CUB 的 block 级和 warp 级原语可以直接嵌进自己的 kernel，和手写的代码一样快，又少了出错的机会。
