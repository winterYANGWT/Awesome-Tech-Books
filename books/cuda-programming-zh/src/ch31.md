# 第 31 章 Driver API

前面所有的程序用的都是 Runtime API：`cudaMalloc`、`cudaMemcpy`、三尖括号启动 kernel。它下面还有一层 Driver API，函数名以 `cu` 开头，由显卡驱动自带的 `libcuda` 提供。Runtime API 本身就是在 Driver API 上实现的，它替你做了几件事：程序启动时把编译进可执行文件的 kernel 注册好，第一次调用时初始化设备、建立上下文，启动 kernel 时按名字找到它、把参数打包。

大多数程序用不着直接碰 Driver API。需要它的场合主要有两类：一是 kernel 的代码在程序运行时才确定，比如 Python 的 CuPy、Numba、Triton 这些库，以及根据用户输入生成 kernel 的程序；二是需要精细控制上下文、模块加载或函数版本的库和框架。这一章用三个程序分别看这几件事：运行时编译和装载 kernel，Runtime 和 Driver 两套 API 混用时的上下文，以及按版本取得 Driver API 的函数指针。

## 31.1 在运行时生成 kernel

设想要对大量的点求同一个多项式的值，多项式的系数在程序运行时才知道（比如从文件里读入、或者是另一步计算的结果）。用普通的方式写 kernel，次数和系数只能作为参数传进去。如果能在拿到系数以后再生成 kernel 的源码，把它们直接写进代码里，编译器就能把它们当常量处理。

[rtc.cpp](code/ch31/rtc.cpp) 准备了两份源码，都是字符串：

```cpp
{{#include code/ch31/rtc.cpp:source}}
```

通用版是一个普通的 kernel，系数放在数组里。专用版由 `specialized_src` 在运行时生成，生成的源码有 513 行 `r = r * v + 常数` 这样的语句。两份源码的 kernel 都声明成 `extern "C"`，这样编译出来的函数名就是 `poly`，不经过 C++ 的名字修饰，后面按名字查找时比较方便。模板 kernel 没法这样做，要用 `nvrtcAddNameExpression` 和 `nvrtcGetLoweredName` 查出修饰后的名字。

源码交给 NVRTC 编译，它是 CUDA 提供的运行时编译库，相当于把 nvcc 的设备代码编译部分做成了函数调用：

```cpp
{{#include code/ch31/rtc.cpp:compile}}
```

编译选项和 nvcc 的写法一样。`-arch=compute_120` 生成 PTX，这是一种和具体 GPU 型号无关的中间代码，装载时由驱动再编译成机器码；`-arch=sm_120` 直接生成这个架构的机器码（cubin）。编译出错时一定要把日志打出来，不然只知道失败，不知道错在哪里。

整个文件里没有一行设备代码，用 g++ 就能编译，只需要链接 `libnvrtc` 和 `libcuda`。

## 31.2 用 Driver API 装载和启动

拿到编译结果以后，Runtime API 那一套自动的事情就都要自己做了。先初始化驱动、取得设备、建立上下文：

```cpp
{{#include code/ch31/rtc.cpp:driver}}
```

上下文（context）是 GPU 上的一个“进程”：显存的分配、装载的模块、stream 和 event 都属于某个上下文。Runtime API 给每个设备用一个**主上下文**（primary context），同一个进程里所有使用这张卡的线程共享它。Driver API 可以用 `cuCtxCreate` 另建上下文，但一般应该像这里一样，用 `cuDevicePrimaryCtxRetain` 取得那个主上下文，这样和程序里其他使用 Runtime API 的代码用的是同一个，31.4 节会看到为什么。

然后装载模块、找到函数、启动：

```cpp
{{#include code/ch31/rtc.cpp:launch}}
```

`cuModuleLoadData` 接受 PTX 或 cubin，如果是 PTX，驱动在这里把它编译成机器码。`cuLaunchKernel` 的参数不是直接列出来的，而是一个指针数组，每个元素指向一个参数的值，顺序和类型必须和 kernel 的声明完全一致。这里没有编译器帮你检查，类型写错了（比如把 `int` 写成 `size_t`），kernel 会读到错误的参数，程序不会报错。三尖括号语法替你做的，就是这件事。

CUDA 12 以后还有另一套装载接口 `cuLibraryLoadData`，Runtime API 里也有对应的 `cudaLibraryLoadData` 和 `cudaLibraryGetKernel`，装载一次就能在所有上下文里使用。只是想运行 NVRTC 编译出来的代码，用这一套就可以完全不碰 Driver API 的上下文。需要把几段分别编译的设备代码链接到一起时，用 nvJitLink 库。

## 31.3 结果

依次用 PTX 和 cubin 两种格式，各编译、装载、运行一遍两个版本。NVRTC 编译和驱动的 JIT 编译都会缓存结果，所以用一个空的缓存目录运行两次，再关掉缓存运行一次：

```text
$ CUDA_CACHE_PATH=./jitcache ./rtc      # 缓存目录是空的
16777216 个点，512 次多项式；生成的专用源码 15949 字节
版本  格式               NVRTC        装载      kernel
通用  compute_120     20.0 ms     7.84 ms    7.953 ms
通用  sm_120          12.6 ms     0.07 ms    7.332 ms
专用  compute_120     23.3 ms    10.72 ms    1.074 ms
专用  sm_120          21.3 ms     0.07 ms    1.082 ms
两个版本结果的最大差 0
$ CUDA_CACHE_PATH=./jitcache ./rtc      # 再运行一次
16777216 个点，512 次多项式；生成的专用源码 15949 字节
版本  格式               NVRTC        装载      kernel
通用  compute_120      7.5 ms     0.09 ms    7.326 ms
通用  sm_120           5.3 ms     0.05 ms    7.348 ms
专用  compute_120      7.4 ms     0.10 ms    1.074 ms
专用  sm_120           7.2 ms     0.05 ms    1.086 ms
两个版本结果的最大差 0
$ CUDA_CACHE_DISABLE=1 ./rtc
16777216 个点，512 次多项式；生成的专用源码 15949 字节
版本  格式               NVRTC        装载      kernel
通用  compute_120     19.7 ms     7.47 ms    7.325 ms
通用  sm_120          24.3 ms     0.08 ms    7.349 ms
专用  compute_120     23.1 ms    10.57 ms    1.073 ms
专用  sm_120          33.7 ms     0.09 ms    1.069 ms
两个版本结果的最大差 0
```

先看最后一列。专用版的 kernel 只要 1.07 ms，通用版要 7.33 ms，快了将近 7 倍，结果却逐位相同（两者做的是同样的 FMA 序列）。1677 万个点、每个点 512 次乘加，专用版的算力达到 16 TFLOPS，接近这块 GPU 单精度峰值的 90%。看一下通用版的机器码就知道原因：把它用 nvcc 编译成 cubin，`cuobjdump -sass` 里有 29 条 FFMA 和 31 条 LDG，几乎每做一次乘加都要从内存（缓存）里读一个系数，访存指令的吞吐比 FMA 低得多，成了瓶颈。专用版里系数是直接编码在 FFMA 指令里的常数，循环也没有了，只剩一串乘加。

这个例子里的提速主要来自系数变成了常数。如果只是次数需要固定，而它的取值只有少数几种，用模板参数在编译期把几种情况都实例化就行，不需要运行时编译（练习 2）。运行时编译适合的是可能性多到没法事先枚举的情况：用户输入的表达式、按数据形状生成的 kernel、深度学习框架把一串运算融合成一个 kernel。

再看编译和装载的代价：

- **NVRTC 编译**：没有缓存时，编译这样一个小 kernel 要 13 到 34 ms，生成 cubin 比生成 PTX 多一步汇编，通常更慢。NVRTC 自己也有缓存，同样的源码和选项再编译一次只要 5 到 8 ms，它和驱动的 JIT 缓存放在一起，同样受 `CUDA_CACHE_PATH` 和 `CUDA_CACHE_DISABLE` 控制，编译选项 `--no-cache` 可以单独关掉它。
- **装载**：cubin 直接装载，不到 0.1 ms。PTX 要在装载时由驱动编译成机器码，要 7 到 11 ms；第二次运行时驱动的 JIT 缓存命中，也降到 0.1 ms。第 34 章会再谈 JIT 缓存。

所以一个运行时生成 kernel 的程序，每个新 kernel 大约要付出几十毫秒的一次性代价，同一个 kernel 应该编译一次、反复使用。cubin 只能在同一代架构的 GPU 上运行，PTX 则可以在更新的 GPU 上由驱动 JIT 编译，所以在本机上运行时编译时可以直接生成 cubin（架构从设备属性里查到），要分发出去的预编译代码则应该带上 PTX。

## 31.4 两套 API 共用上下文

Runtime API 和 Driver API 可以在同一个程序里混用，关键是要清楚当前用的是哪个上下文。[ctx.cu](code/ch31/ctx.cu) 先看正常的情况：

```cpp
{{#include code/ch31/ctx.cu:primary}}
```

```text
$ ./ctx
主上下文 0x63ea398982a0，当前上下文 0x63ea398982a0，a 属于 0x63ea398982a0
cuLaunchKernel 启动 Runtime 的 kernel 以后 a[12345] = 1
```

`cudaMalloc` 初始化了设备 0 的主上下文并把它设为当前上下文，`cuDevicePrimaryCtxRetain` 取到的是同一个，`cuPointerGetAttribute` 也说明 `a` 属于它。两套 API 的句柄可以直接互换：`cudaStream_t` 和 `CUstream` 是同一个类型，设备指针在 Driver API 里是 `CUdeviceptr`（一个整数），强制转换一下即可；`cudaGetFuncBySymbol` 能取得 Runtime 程序里某个 kernel 对应的 `CUfunction`，再用 `cuLaunchKernel` 启动。

问题出在自己建立的上下文上：

```cpp
{{#include code/ch31/ctx.cu:own}}
```

```text
自建上下文 0x63ea3a8333c0，之后 cudaMalloc 的 b 属于 0x63ea3a8333c0
```

`cuCtxCreate` 新建的上下文会立即成为当前线程的当前上下文。Runtime API 总是使用当前上下文，只有当前没有上下文时才去用主上下文，所以此后的 `cudaMalloc` 分配的内存都属于这个新的上下文，调用者完全察觉不到。设想一个库在初始化时这样建了自己的上下文，又没有恢复原来的设置，程序里接下来的所有 Runtime API 调用就都落进了这个库的上下文。等到库清理自己的资源时：

```cpp
{{#include code/ch31/ctx.cu:restore}}
```

```text
销毁自建上下文以后 cudaMemset(b)：cudaErrorIllegalAddress
接着在主上下文里读 a：cudaErrorIllegalAddress
cudaDeviceReset 以后重新分配：cudaErrorDevicesUnavailable
```

上下文销毁时，属于它的内存也一起被释放了，`b` 成了悬空指针。对它做 `cudaMemset`，GPU 报出非法地址。第 5 章说过，这类错误会让上下文进入不可恢复的状态，此后读一个毫不相干的 `a` 也失败了；这里还多试了一步 `cudaDeviceReset`，在这台机器的驱动上它也救不回来，之后的调用全部返回 `cudaErrorDevicesUnavailable`，只能结束进程。

所以写使用 Driver API 的库时有两条规矩。第一，尽量使用主上下文（`cuDevicePrimaryCtxRetain`），不要另建上下文。第二，确实需要切换上下文时，用 `cuCtxPushCurrent` 换成自己的，用完以后 `cuCtxPopCurrent` 恢复调用者原来的当前上下文，绝不把自己的上下文留在当前线程上。CUDA 12 的 `cuLibraryLoadData` 让模块不再绑定到某个上下文，也减少了库自建上下文的理由。

## 31.5 按版本取得函数指针

最后一个问题和链接有关。Driver API 的函数在 `libcuda` 里，它随显卡驱动安装，而不是随 CUDA 工具包安装。程序如果直接链接 `libcuda`（`-lcuda`），在没装驱动的机器上连启动都不行，而且只能调用编译时那个版本就有的函数。所以很多程序不直接链接，而是在运行时取得函数指针：Runtime API 提供 `cudaGetDriverEntryPointByVersion`，Driver API 里对应的是 `cuGetProcAddress`。

取函数指针时必须说明要哪个 CUDA 版本的函数，因为同一个函数名在不同版本里可能有不同的参数。比如 `cuCtxCreate`，CUDA 13 的 `cuda.h` 里写的是 `#define cuCtxCreate cuCtxCreate_v4`，程序里写的 `cuCtxCreate` 实际调用的是 `cuCtxCreate_v4`；而 `libcuda` 为了兼容老程序，导出的 `cuCtxCreate` 这个名字仍然是最早的那个参数形式。[entry.cu](code/ch31/entry.cu) 按不同的版本去取同一个名字，再到 `libcuda` 导出的符号里找出拿到的到底是哪一个：

```cpp
{{#include code/ch31/entry.cu:query}}
```

```cpp
{{#include code/ch31/entry.cu:run}}
```

```text
$ ./entry
驱动支持到 CUDA 13.3，程序用的运行时是 CUDA 13.3
  cuCtxCreate        按 11.0 取：cuCtxCreate_v2
  cuCtxCreate        按 12.0 取：cuCtxCreate_v3
  cuCtxCreate        按 12.5 取：cuCtxCreate_v4
  cuCtxCreate        按 13.0 取：cuCtxCreate_v4
  cuMemcpyAsync      按 13.0 取：cuMemcpyAsync
  cuMemcpyAsync      按 13.0 取（每线程默认 stream）：cuMemcpyAsync_ptsz
  cuLibraryLoadData  按 11.8 取：这个版本还没有这个函数
  cuLibraryLoadData  按 12.0 取：cuLibraryLoadData

通过函数指针调用 cuDeviceGetName：0，NVIDIA GeForce RTX 5060 Laptop GPU
```

同样叫 `cuCtxCreate`，按 11.0 取到的是 `_v2`（三个参数），按 12.0 取到的是 CUDA 11.4 加入的 `_v3`（多了执行亲和性参数），按 12.5 以后取到的是 `_v4`（参数换成了一个结构体）。驱动返回的是“不晚于所请求版本的最新参数形式”。如果代码是按某个版本的参数写的，却按另一个版本去取，拿到的函数参数对不上，调用时不会有任何类型检查，结果可能是崩溃，也可能是悄悄做错事。

`cudaTypedefs.h` 为每个函数的每种参数形式都定义了函数指针类型，类型名末尾的数字就是这种形式出现的版本，比如 `PFN_cuCtxCreate_v3020`、`PFN_cuCtxCreate_v11040`、`PFN_cuCtxCreate_v12050`。正确的用法是让请求的版本和使用的类型对应起来：

另外两组结果：`cuMemcpyAsync` 这类涉及默认 stream 的函数，每线程默认 stream（第 13 章）有单独的 `_ptsz` 版本，由 flags 参数选择。驱动比请求的版本旧、还没有这个函数时，状态是 `cudaDriverEntryPointVersionNotSufficent`（拼写错误是 API 里原有的），程序可以据此退回到别的实现，这正是运行时取函数指针的好处：同一个程序在新驱动上用新功能，在旧驱动上也能运行。

## 31.6 回头看

Runtime API 建立在 Driver API 之上，替你完成了模块注册、上下文管理和参数打包。NVRTC 加 Driver API 可以在运行时生成、编译、装载 kernel：把运行时才知道的系数写成常量，这个多项式 kernel 快了 7 倍；代价是每个新 kernel 几十毫秒的编译，PTX 还要再加几毫秒的 JIT，两者都有缓存。两套 API 混用时共享主上下文，句柄可以互换；库自建上下文而不恢复，会让调用者的 Runtime API 调用悄悄落进别的上下文，上下文销毁时内存随之消失，一次非法访问就会让整个进程的 CUDA 无法再用。运行时取 Driver API 函数指针时要指定版本，并用对应版本的函数指针类型，因为同一个函数名在不同版本里参数可能不同。
