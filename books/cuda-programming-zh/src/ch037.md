# 第 37 章 CUDA Graph 为什么存在：降低重复提交开销，而不是让代码自动变快

CUDA Graph 不是一种 kernel 优化技巧，它解决的是另一个问题：当程序反复提交同一串 kernel、copy、memset、host function 或库调用时，CPU 侧每轮逐个调用 Runtime API 的开销会变得明显。Graph 把这串工作和依赖关系提前定义、实例化，然后重复 launch。

如果 stream 是队列，graph 就是依赖图。它让 CUDA 在执行前看到整个 workload 的形状。

## 37.1 问题的由来

很多应用都有固定迭代结构：

- 推理服务反复跑同一张模型子图。
- 仿真程序每个 timestep 提交同样的 kernel 序列。
- 训练 step 中小 kernel 很多，CPU launch overhead 占比变高。
- 多个 memcpy/memset/kernel 组合成固定 pipeline。

普通 stream 写法每轮都要逐个提交 API 调用。单次提交成本不大，但在小 kernel、多节点、高频迭代场景中会积累。Graph 的思路是：先把图定义出来，实例化成 executable graph，后续只 launch 这张图。

## 37.2 核心模型

`cudaGraph_t` 是图定义，`cudaGraphExec_t` 是验证和准备后的可执行对象。重复执行时，应该复用 `cudaGraphExec_t`。

图 37.1 是一张 graph 从定义到反复执行的过程：先定义 `cudaGraph_t`，加入 node 和依赖边；再实例化成 `cudaGraphExec_t`；可以先用 `cudaGraphUpload` 做好准备，然后反复 launch。参数变化而结构兼容时，直接更新 executable graph，不必重新实例化。

## 37.3 详解

### 37.3.1 Node 和 edge

Graph 的 node 表示操作，edge 表示依赖。一个 node 只要依赖的前驱完成，就可以被调度。Graph 支持很多 node 类型：

| Node 类型 | 作用 |
|---|---|
| Kernel node | 启动 kernel |
| Memcpy node | 内存拷贝 |
| Memset node | 内存初始化 |
| Host node | host function |
| Empty node | 只表达依赖 |
| Event record/wait node | event 依赖 |
| Child graph node | 嵌套 graph |
| Conditional node | 图内条件/循环控制 |
| Memory allocation/free node | 图内内存生命周期 |
| External semaphore node | 外部同步对象互操作 |

Child graph 适合把一个复杂流程拆成可复用子图：父 graph 里的一个 node 本身就是一张完整的 graph，子图内部的依赖照常生效，整个子图在父 graph 中又像一个普通 node 一样参与依赖。

### 37.3.2 手工构图

手工构图适合图结构清楚、需要精确控制节点和边的场景。它比 capture 啰嗦，但 graph 的结构完全显式。

### 37.3.3 Stream capture

Stream capture 适合把已有 stream 代码迁移成 graph。它捕获的是 CUDA work 和依赖，不是任意 C++ 代码执行过程。

### 37.3.4 Graph launch 仍然在 stream 中

`cudaGraphLaunch(exec, stream)` 把 executable graph 提交到一个 stream。这个 stream 主要用于 graph 和图外工作建立顺序。Graph 内部的 node 仍按 graph 依赖关系调度，不是被压成一条线。

## 37.4 代码示例

Stream capture 的最小例子：

```cpp
cudaGraph_t graph;
cudaGraphExec_t exec;
cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
cudaMemcpyAsync(d_in, h_in, bytes, cudaMemcpyHostToDevice, stream);
kernel<<<grid, block, 0, stream>>>(d_in, d_out);
cudaMemcpyAsync(h_out, d_out, bytes, cudaMemcpyDeviceToHost, stream);
cudaStreamEndCapture(stream, &graph);
cudaGraphInstantiate(&exec, graph, 0);  // 第三个参数是 instantiate flags
for (int iter = 0; iter < iters; ++iter) {
    cudaGraphLaunch(exec, stream);
}
cudaStreamSynchronize(stream);
cudaGraphExecDestroy(exec);
cudaGraphDestroy(graph);
```

CUDA 11 的 `cudaGraphInstantiate` 有五个参数（多出 error node 和 log buffer），CUDA 12 起改成现在的 `(exec, graph, flags)`。`cuda_runtime.h` 为旧写法留了一个 C++ 兼容重载，但它直接忽略 error node 和 log buffer，新代码应该用三参数形式；需要失败诊断时用 `cudaGraphInstantiateWithParams`（见[第 42 章](ch042.md)）。

手工添加 kernel node 的形态：

```cpp
cudaGraph_t graph;
cudaGraphCreate(&graph, 0);
cudaKernelNodeParams params{};
params.func = reinterpret_cast<void*>(my_kernel);
params.gridDim = grid;
params.blockDim = block;
params.sharedMemBytes = 0;
params.kernelParams = kernel_args;
cudaGraphNode_t kernel_node;
cudaGraphAddKernelNode(&kernel_node, graph, nullptr, 0, &params);
```

## 37.5 工程判断

| 场景 | 是否适合 Graph | 原因 |
|---|---|---|
| 每轮拓扑一致，参数变化 | 适合 | 可 instantiate 后 update/launch |
| 大量短 kernel | 适合 | CPU launch overhead 占比高 |
| 单个长 kernel | 收益有限 | kernel 执行时间占主导 |
| 每轮节点数量和依赖变化很大 | 不一定适合 | 重建成本可能抵消收益 |
| 需要捕获库调用 | 适合 stream capture | 前提是库使用同一 stream |
| 需要动态设备侧控制 | 可能用 device graph launch | 结构和 node 类型受限 |

## 37.6 API 与要点速查

Graph 生命周期 API：

| API | 用途 |
|---|---|
| `cudaGraphCreate` | 创建 graph definition |
| `cudaGraphDestroy` | 销毁 graph definition |
| `cudaGraphInstantiate` | 创建 executable graph |
| `cudaGraphExecDestroy` | 销毁 executable graph |
| `cudaGraphLaunch` | 提交 graphExec |
| `cudaGraphUpload` | 预上传和准备 graphExec |
| `cudaGraphDebugDotPrint` | 导出 graph dot 文件 |

Graph 不会自动优化 kernel 本身。它主要优化 host 提交路径、依赖表达和运行时全局视角。

## 37.7 小结

读完本章，你应该能够：

- 解释 CUDA Graph 解决的是重复提交开销。
- 区分 graph definition 和 executable graph。
- 判断手工构图和 stream capture 的适用场景。
- 理解 graph launch 仍然在 stream 中发生。
