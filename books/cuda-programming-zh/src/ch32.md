# 第 32 章 跨进程共享与虚拟内存管理

`cudaMalloc` 一次做了三件事：在 GPU 的虚拟地址空间里找一段地址，分配一块物理显存，把两者映射起来并允许当前设备访问。这对绝大多数程序都够用了，但有些需求它满足不了：让另一个进程也能访问这块显存；让一个数组变大时地址保持不变；给显存设置特殊的属性。这一章先看最简单的跨进程共享，再看把这三件事拆开、分别控制的虚拟内存管理（VMM）API，最后用 VMM 试一试显存压缩。

## 32.1 两个进程共享显存

推理服务、数据预处理流水线这类程序，常常由几个进程分工：一个进程把数据准备好放在显存里，另一个进程直接使用，不想经过主机内存拷来拷去。CUDA 最早提供的办法是 `cudaIpcGetMemHandle`：对一块 `cudaMalloc` 分配的显存取得一个 64 字节的句柄，用任何进程间通信手段（管道、套接字、共享文件）把句柄传给另一个进程，对方用 `cudaIpcOpenMemHandle` 打开，就得到了指向同一块物理显存的指针。

[ipc.cu](code/ch32/ipc.cu) 用 `fork` 产生一个子进程，父子进程之间用一对 Unix 域套接字通信。父进程分配 256 MB 显存并启动 kernel 填入数据，然后把句柄发给子进程：

```cpp
{{#include code/ch32/ipc.cu:parent}}
```

（`vmm` 那个分支在 32.3 节再看。）子进程收到句柄，打开同一块显存，给每个元素加上 1000000：

```cpp

```

```text
$ ./ipc legacy
cudaIpc*：两个进程共享 256 MB 显存
子进程：打开用了 0.03 ms；父进程里的地址 0x1000ac00000，子进程里的地址 0x1000ec00000
父进程：a[7] = 1000007，a[N-1] = 68108863
```

子进程的修改父进程看得到，两个进程用的确实是同一块显存。打开句柄只要 0.03 ms，之后子进程访问这块内存和访问自己分配的显存没有区别。

有几个细节：

- `fork` 必须在任何 CUDA 调用之前。CUDA 不支持在已经初始化的进程里 fork 出子进程再使用 CUDA。实际的程序通常是两个独立启动的进程，就没有这个问题。
- 同一块显存在两个进程里的地址不一样（子进程先分配了一块别的内存，地址布局就错开了）。指针的值在进程之间没有意义，要传的是句柄。
- 父进程的 `fill` 是异步的，句柄发出去的时候它可能还没做完。所以父进程同时传了一个跨进程的 event：创建时带 `cudaEventInterprocess`（必须同时带 `cudaEventDisableTiming`），用 `cudaIpcGetEventHandle` 取得句柄。子进程打开以后用 `cudaStreamWaitEvent` 在 GPU 上等它，不需要父进程在主机上同步。
- 父进程要等子进程用完并关闭（`cudaIpcCloseMemHandle`）以后才能释放这块显存，这个约定要靠两个进程自己维护。

这套接口用起来简单，限制也不少。[ipc_limits.cu](code/ch32/ipc_limits.cu) 试了几种情况：

```cpp
{{#include code/ch32/ipc_limits.cu:limits}}
```

```text
$ ./ipc_limits
对 a + 1000 取句柄：cudaSuccess，和 a 的句柄完全相同
在分配它的进程里打开：cudaErrorDeviceUninitialized
托管内存取句柄：cudaErrorInvalidValue
cudaMallocAsync 的内存取句柄：cudaErrorInvalidValue
```

第一条最容易出错：对一块分配中间的指针取句柄不会报错，但得到的是整块分配的句柄，对方打开以后拿到的是分配的起始地址。程序里如果有自己的内存池，从一大块里切出小块分给各处使用，传句柄时必须把偏移量一起传过去（`cuMemGetAddressRange` 可以查到一个指针所在分配的起始地址）。另外，句柄只能在别的进程里打开，托管内存和 `cudaMallocAsync` 默认内存池里的内存都不能这样共享。流序分配器要跨进程共享，得自己用 `cudaMemPoolCreate` 建一个声明了导出句柄类型的内存池。

## 32.2 地址和物理内存分开管理

VMM 把 `cudaMalloc` 做的三件事拆成了独立的 Driver API 调用：

- `cuMemAddressReserve`：预留一段虚拟地址。只是占住地址，不分配任何显存。
- `cuMemCreate`：分配一块物理显存，返回一个句柄。这时它还没有地址，不能访问。
- `cuMemMap`：把物理显存映射到预留的地址上。
- `cuMemSetAccess`：允许某些设备以某种方式（只读或读写）访问这段地址。不调用它，访问映射好的地址也会出错。

大小都必须是分配粒度的整数倍。[vmm.cu](code/ch32/vmm.cu) 先查询设备对 VMM 相关功能的支持和分配粒度：

```text
$ ./vmm

导出为 POSIX 文件描述符：支持
multicast：不支持
压缩内存：支持
VMM 分配主机 NUMA 内存：支持
分配粒度：最小 2048 KB，推荐 2048 KB
```

粒度是 2 MB，和 GPU 页表使用的大页一样大。物理内存的属性和访问权限各用一个结构描述：

数组从 64 MB 开始，每次长 64 MB，一直长到 2 GB，每次只填新长出来的部分：

```text
数组从 64 MB 长到 2 GB，每次长 64 MB：
  重新分配并拷贝：   311.3 ms，错误 0 个
  VMM 接着映射：      11.9 ms，错误 0 个
```

重新分配的办法每长一次都要把已有的内容全部搬一遍，长到 2 GB 累计要拷贝 31 GB，还要反复地 `cudaMalloc` 和 `cudaFree`。VMM 的办法里，填满 2 GB 本身按带宽算就要 6 ms 左右，32 次映射一共只多花了几毫秒，地址也始终不变，别处保存的指针不会失效。而且重新分配时新旧两块要同时存在，峰值显存是数组大小的两倍，VMM 没有这个问题。`cudaMallocAsync` 的内存池和 PyTorch 显存分配器的 `expandable_segments` 选项，用的都是这个机制。

第二个例子反过来：把同一块物理内存映射到两段地址上。环形缓冲区（ring buffer）读写到末尾时要绕回开头，代码里到处是取模和分段处理。如果预留两倍大小的地址，把同一块物理内存映射在前后两半，那么从任何位置开始连续读写一个不超过缓冲区大小的区间，地址自然会从后一半“绕回”到同一块物理内存的开头：


数据只通过前一半写入了一次，跨过末尾连续读的 8 个数却正好接上了开头。kernel 处理环形缓冲里的数据时，也可以把它当成一段连续的数组。

## 32.3 用 VMM 跨进程共享

VMM 分配的物理内存也能跨进程共享，而且比 `cudaIpc*` 灵活。创建时在属性里声明要导出的句柄类型（`requestedHandleTypes`），然后用 `cuMemExportToShareableHandle` 导出成一个句柄。在 Linux 上它是一个文件描述符，Windows 上是 Win32 句柄，在通过 NVLink 交换机连起来的多节点系统上还可以是跨节点的 fabric 句柄。

文件描述符不能像普通数据那样写进管道：一个整数离开了自己的进程就没有意义。要用 Unix 域套接字的 `SCM_RIGHTS` 控制消息传递，内核会在接收进程里建立一个指向同一个对象的新描述符：

```cpp
{{#include code/ch32/ipc.cu:fd}}
```

接收方用 `cuMemImportFromShareableHandle` 导入，得到物理内存的句柄，然后在自己预留的地址上映射、设置访问权限，和本地分配的物理内存一样处理（见 32.1 节代码里 `vmm` 的分支）：

```text
$ ./ipc vmm
VMM + 文件描述符：两个进程共享 256 MB 显存
子进程：打开用了 0.06 ms；父进程里的地址 0x1000ac00000，子进程里的地址 0x1000ec00000
父进程：a[7] = 1000007，a[N-1] = 68108863
```

和 `cudaIpc*` 相比，VMM 共享的单位是一块物理内存而不是一次 `cudaMalloc`，不存在偏移量丢失的问题；每个进程自己决定映射到哪里、给哪些设备什么权限，比如可以只给只读权限（`CU_MEM_ACCESS_FLAGS_PROT_READ`）；文件描述符遵循操作系统的权限模型，只有拿到描述符的进程才能导入，什么时候所有进程都关闭了描述符、释放了句柄，物理内存才真正释放。代价是代码多了不少。新写的程序需要跨进程共享显存时，应该优先考虑 VMM。

## 32.4 可压缩内存

VMM 还能给物理内存设置一些 `cudaMalloc` 设置不了的属性，压缩就是其中之一。在属性里设 `compressionType`，申请可压缩的显存：

```cpp
{{#include code/ch32/compress.cu:alloc}}
```

申请了不一定能得到，所以要用 `cuMemGetAllocationPropertiesFromHandle` 确认。[compress.cu](code/ch32/compress.cu) 分别在普通显存和可压缩显存里写入三种数据，测量读写带宽：

```text
$ ./compress
1 GB 显存，每项重复 10 次取平均
内存      数据          读           写
普通    全零           369 GB/s     358 GB/s
普通    0–255 循环     369 GB/s     359 GB/s
普通    随机           370 GB/s     359 GB/s
可压缩  全零          1532 GB/s    1048 GB/s
可压缩  0–255 循环    1077 GB/s     855 GB/s
可压缩  随机           367 GB/s     264 GB/s
```

普通显存里，数据是什么都不影响带宽。可压缩显存里差别很大：全零的数据读带宽达到 1532 GB/s，是显存带宽的四倍多（多次运行在 1500 到 1700 GB/s 之间，已经接近第 19 章测到的 L2 带宽）；有规律的数据也快了将近三倍；随机数据压不动，读带宽和普通显存一样，写反而慢了四分之一。

压缩发生在 L2 和显存之间，数据在显存里以压缩的形式存放，读写时少传输了字节，所以省的是带宽，不是容量（分配多少还是占多少）。它适合含有大量零或重复值的数据，比如稀疏的激活值、初始化后大部分还没写过的缓冲区；对随机数据没有好处，还会拖慢写入。用不用要靠实测，最好先确认自己的数据有多大比例能被压缩。

## 32.5 multicast 及其他

`vmm` 的输出里，这块 GPU 不支持 multicast。multicast 对象是给通过 NVSwitch 连接的多 GPU 系统用的：一段地址同时绑定到几张卡各自的一块物理显存上，往这段地址写一次，数据会被交换机复制到所有的卡；PTX 里的 `multimem` 指令还能让交换机在传输途中完成归约。NCCL 这类通信库用它实现更快的集合通信，应用程序一般不直接使用。

VMM 的物理内存也不一定在显存里。把位置类型设成主机的 NUMA 节点（`CU_MEM_LOCATION_TYPE_HOST_NUMA`），分配的就是主机内存，同样可以映射到 GPU 的地址空间。在 Grace Hopper 这类 CPU 和 GPU 之间有高速互联的系统上，这是让 GPU 直接使用大量主机内存的方式。

## 32.6 回头看

`cudaIpcGetMemHandle` 和 `cudaIpcOpenMemHandle` 是跨进程共享显存最简单的方法，打开只要几十微秒，但只适用于 `cudaMalloc` 的内存，句柄总是指向整块分配，中间的偏移量要自己传。VMM 把虚拟地址、物理内存、映射和访问权限分开：数组变大时在预留的地址后面接着映射，比重新分配加拷贝快了 26 倍且地址不变；同一块物理内存可以映射到多处，做出不用处理绕回的环形缓冲；物理内存可以导出成文件描述符跨进程共享，每个进程自己控制映射和权限。VMM 还能申请可压缩的显存，容易压缩的数据读带宽能提高到四倍以上，随机数据则没有好处。
