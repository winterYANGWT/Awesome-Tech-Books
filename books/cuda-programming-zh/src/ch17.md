# 第 17 章 CUDA Graph：把重复提交的开销省掉

很多 GPU 程序的结构是一个大循环：模拟程序的每个时间步、神经网络推理的每一次前向计算，都要按固定的顺序启动几十上百个 kernel，然后一遍又一遍地重复。如果每个 kernel 都很小，启动本身的开销就会变得显眼。CUDA Graph 的思路是：把这一串操作和它们之间的依赖关系记录下来，变成一个整体，以后每次只提交这一个整体。这一章先量一量启动开销到底有多大，再看 graph 能省下多少，以及使用 graph 时要注意的规则。

## 17.1 小 kernel 的启动开销

[launch.cu](code/ch17/launch.cu) 模拟一个时间步：20 个很小的 kernel，后一个依赖前一个的结果，一共 1000 步。每个 kernel 只处理 6656 个元素，GPU 上执行不到一微秒：

```cpp
{{#include code/ch17/launch.cu:step}}
```

先用普通的办法，一步一步地逐个启动：

```text
                        总时间     平均每个 kernel   其中 host 提交
逐个启动                 30.9 ms     1.55 us           30.9 ms
```

2 万个 kernel 用了 30.9 ms，平均每个 1.55 微秒。最后一列是 host 把所有 kernel 提交完所用的时间：也是 30.9 ms。也就是说，GPU 一直在等 host：host 每提交一个 kernel 要花 1.5 微秒左右的 CPU 时间，GPU 执行它却用不了这么久。

用 Nsight Systems 看 GPU 这边的情况（profiler 本身会让启动变慢一些，所以这里的绝对数字比不用 profiler 时大）：

```text
               kernel 数   平均执行时间   kernel 之间的平均空隙
逐个启动            20000       0.57 us         1.97 us
graph（1 步）      20000       0.48 us         0.34 us
graph（10 步）     20000       0.47 us         0.18 us
```

先看第一行：每个 kernel 执行 0.57 微秒，前后两个 kernel 之间却空着 1.97 微秒，GPU 有将近八成的时间在闲着。另外两行是下面用 graph 的结果。

## 17.2 把一个时间步捕获成 graph

创建 graph 最方便的办法是**stream 捕获**：在一条 stream 上开始捕获，照常调用启动 kernel、拷贝这些函数，它们不会真的执行，而是被记录下来；结束捕获时得到一个 graph。然后把 graph **实例化**，得到一个可以执行的对象：

```cpp
{{#include code/ch17/launch.cu:capture}}
```

以后每一步只需要启动这个实例：

```cpp
{{#include code/ch17/launch.cu:launch}}
```

```text
捕获 176 us，实例化 478 us

                        总时间     平均每个 kernel   其中 host 提交
逐个启动                 30.9 ms     1.55 us           30.9 ms
graph（1 步）            14.4 ms     0.72 us            2.5 ms
graph（10 步）           12.9 ms     0.65 us            0.2 ms
```

同样 2 万个 kernel，用 graph 只要 14.4 ms，快了一倍多。host 提交 1000 次 graph 只用了 2.5 ms，剩下的时间它都可以去做别的事；瓶颈从 CPU 转到了 GPU。再看上一节 nsys 的数字，kernel 之间的空隙从 1.97 微秒缩到了 0.34 微秒。如果一次捕获 10 个时间步，每个 graph 里有 200 个 kernel，空隙还能再小一点，host 的提交时间几乎可以忽略。

graph 为什么快？实例化时，驱动已经检查过所有参数、确定了所有依赖关系，把整串工作预先处理成了 GPU 可以直接执行的形式。启动时只需要把这个预处理好的整体交给 GPU，不用每个 kernel 都走一遍完整的提交流程；GPU 也事先知道后面要做什么，可以更紧凑地衔接。

代价是捕获和实例化：这里一共 650 微秒左右。每步省下的时间是 20 ×（1.55 − 0.72）≈ 17 微秒，graph 要重复启动 40 次左右才能把这笔开销挣回来。所以 graph 适合结构固定、反复执行的工作；只执行一两次的工作没必要做成 graph。

## 17.3 捕获的规则

stream 捕获看上去只是“照常写代码”，但有几条规则不了解的话很容易出错。[rules.cu](code/ch17/rules.cu) 在捕获期间做了几种常见的操作，看看各自的结果：

```text
这个调用返回                         结束捕获时返回                       捕获期间做的事
cudaSuccess                          cudaSuccess                          cudaMemsetAsync（同一条 stream）
cudaSuccess                          cudaSuccess                          cudaMallocAsync（同一条 stream）
cudaErrorStreamCaptureUnsupported    cudaErrorStreamCaptureInvalidated    cudaMalloc
cudaSuccess                          cudaSuccess                          cudaMemcpy（同步拷贝）
cudaErrorStreamCaptureUnsupported    cudaErrorStreamCaptureInvalidated    cudaStreamSynchronize
cudaSuccess                          cudaSuccess                          在默认 stream 上启动 kernel
cudaSuccess                          cudaSuccess                          在另一条 stream 上启动 kernel
cudaErrorStreamCaptureImplicit       cudaErrorStreamCaptureInvalidated    默认 stream 启动（捕获普通 stream）
```

可以分成三类：

- **被记录进 graph 的**：在被捕获的 stream 上进行的异步操作，比如 `cudaMemsetAsync`、kernel 启动、`cudaMemcpyAsync`。`cudaMallocAsync` 也可以，它会变成 graph 里的一个内存分配节点（第 18 章）。
- **会让捕获失败的**：要等待被捕获 stream 的操作，比如 `cudaStreamSynchronize`，以及在默认（global）捕获模式下被认为不安全的调用，比如 `cudaMalloc`。这些调用本身返回错误，而且整个捕获作废，结束捕获时得到 `cudaErrorStreamCaptureInvalidated`。最后一行也属于这一类：被捕获的是一条普通（blocking）stream，在默认 stream 上启动 kernel 会和它产生隐式的依赖（第 13 章），这是不允许的。
- **既不报错、也不进 graph 的**：在和捕获无关的 stream 上进行的操作。被捕获的 `s` 是用 `cudaStreamNonBlocking` 创建的，和默认 stream 之间没有隐式依赖，所以同步的 `cudaMemcpy`、默认 stream 上的 kernel、另一条 stream 上的 kernel，都照常**当场执行**了。

最后一类最隐蔽，因为它们看起来像是写进了 graph。rules.cu 专门验证了一下：

```cpp
{{#include code/ch17/rules.cu:eager}}
```

```text
捕获结束、graph 还没启动时，d[0] = 1
```

graph 还一次都没启动，`d[0]` 已经被加了 1，这是 `other` 上那个 kernel 当场执行的结果，而它并不在 graph 里。如果你以为它是 graph 的一部分，每次启动 graph 时就会少做一步。

捕获模式（`cudaStreamBeginCapture` 的第二个参数）决定了“不安全的调用”管得多严：`cudaStreamCaptureModeGlobal` 只要有任何线程在捕获，就禁止所有线程做这类调用；`ThreadLocal` 只管当前线程；`Relaxed` 不管。一般用默认的 Global，它能帮你发现问题。

捕获也能跨多条 stream。第 14 章的 fork-join 写法在捕获期间同样适用：另一条 stream 通过 `cudaStreamWaitEvent` 等待被捕获 stream 上记录的 event，就加入了捕获；最后再用 event 汇合回来：

```cpp
{{#include code/ch17/rules.cu:forkjoin}}
```

```text
fork-join 捕获得到的 graph：4 个节点，4 条边
```

4 个 kernel 节点，4 条依赖边：A 指向 B 和 C，B 和 C 都指向 D。B 和 C 之间没有边，执行时可以并行。graph 记录的是依赖关系，不是 stream，所以捕获时的并行结构会原样保留下来。

## 17.4 参数变了怎么办

graph 里记录的是 kernel 的参数值，包括指针。如果每一步要换一块缓冲区（比如两块缓冲区轮流用），graph 就得跟着改。[update.cu](code/ch17/update.cu) 比较了三种改法，每轮换一次缓冲区、启动 20 个 kernel 的 graph 并等它做完：

```text
每轮（20 个 kernel，换一次参数，启动并等待）：
  重新捕获 + 重新实例化     46.0 us
  重新捕获 + ExecUpdate     24.9 us
  逐个修改节点参数          21.4 us
  参照：不改参数            17.3 us
```

每次都重新实例化最贵，46 微秒，比直接逐个启动 20 个 kernel（约 31 微秒）还慢，graph 的好处全没了。另外两种办法都在已有的实例上修改。一种是照常重新捕获，然后用 `cudaGraphExecUpdate` 把新 graph 里的参数灌进旧的实例：

```cpp
{{#include code/ch17/update.cu:exec_update}}
```

它要求新旧两个 graph 的结构（节点和依赖关系）相同，只是参数不同；结构变了就会失败，只能重新实例化。另一种是直接修改实例里每个 kernel 节点的参数，连捕获都省了：

```cpp
{{#include code/ch17/update.cu:node_update}}
```

两者都只比不改参数多几微秒。还有一种从设计上绕开问题的办法：让 kernel 不直接接收会变的参数，而是从显存里的一块固定位置读取（比如一个指针表），每次启动 graph 前只更新这块内存，graph 本身永远不变。

## 17.5 让 GPU 自己决定循环几次

迭代算法常常要算到收敛为止，事先不知道要多少步。通常的写法是每一步之后把收敛标志拷回主机检查，这意味着每一步都要同步一次。[conditional.cu](code/ch17/conditional.cu) 用一个简单的例子演示：256 个元素，每一步向目标值靠近千分之一，直到所有元素离目标都不超过 10⁻³：

```cpp
{{#include code/ch17/conditional.cu:step}}
```

每一步都回到主机检查：

```cpp
{{#include code/ch17/conditional.cu:host_loop}}
```

CUDA Graph 从 12.3 版开始支持**条件节点**，可以把这个循环整个放进 graph：一个 while 节点，它的循环体是一个子 graph，kernel 在里面调用 `cudaGraphSetConditional` 设置条件值，值非零就再执行一遍循环体：

```cpp
{{#include code/ch17/conditional.cu:build}}
```

```text
每步回到主机检查： 6892 步，  57.1 ms，平均每步  8.28 us
graph while 循环： 6892 步，  22.8 ms，平均每步  3.30 us
```

两种做法都迭代了 6892 步，graph 版本快了一倍半：整个循环一次提交，每一步不再需要一个往返主机的拷贝和同步。除了 while，条件节点还有 if（条件为真时执行一次）和 switch（按条件值选择一个分支）两种。

## 17.6 什么时候用 graph

graph 的收益来自省掉每个操作的提交开销，所以它适合：大量的小 kernel、结构固定、反复执行。模拟程序的时间步、神经网络的推理都是典型的例子，PyTorch 等框架里的 “CUDA Graphs” 功能就是这个机制。如果 kernel 本身要跑几毫秒，每个省下一两微秒就无关紧要了。

使用时要记住：graph 里的指针和参数是捕获时的值，换了缓冲区要更新；捕获期间只有被捕获的 stream（以及通过 event 加入的 stream）上的操作会被记录；捕获和实例化有几百微秒的开销，要靠反复启动来摊薄。

## 17.7 回头看

每次启动 kernel，host 要花一微秒多的 CPU 时间，kernel 很小时 GPU 大部分时间都在等。CUDA Graph 把一串操作和它们的依赖关系记录成一个整体，实例化一次以后反复启动，在这个例子里把每个 kernel 的平均开销从 1.55 微秒降到了 0.72 微秒，host 几乎不再占用时间。stream 捕获是创建 graph 最方便的方式，但要注意哪些调用会被记录、哪些会让捕获失败、哪些会被当场执行。参数变化时用 `cudaGraphExecUpdate` 或直接修改节点，不要重新实例化。条件节点还能把“算到收敛为止”这样的循环整个放到 GPU 上。
