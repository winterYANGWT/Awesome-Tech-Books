# 第 16 章 Unified Memory：按需迁移的代价

前面三章，数据在主机内存和显存之间怎么走，都是程序显式安排的：什么时候拷、拷到哪、用哪条 stream。Unified Memory 提供了另一种方式：分配一块内存，得到一个指针，CPU 和 GPU 都能直接用它，数据在需要的时候由驱动自动搬到正在访问它的一方。这省掉了大量的拷贝代码，对指针串起来的复杂数据结构尤其方便。代价是什么时候搬、搬多少，不再由你直接控制。这一章把这些代价量出来，并介绍控制它们的手段。

## 16.1 一个指针，两边都能用

`cudaMallocManaged` 分配的内存叫 managed memory：

```cpp
{{#include code/ch16/um.cu:managed}}
```

CPU 直接往里写，然后 kernel 直接拿同一个指针去读写，中间没有任何 `cudaMemcpy`。背后的机制是按页迁移：managed memory 的每一页在某一时刻只住在一个地方，主机内存或者显存。CPU 初始化之后，所有页都在主机内存里；GPU 第一次访问某一页时发生缺页（page fault），驱动把这一页搬到显存，再让 GPU 继续。CPU 再访问时也一样，缺页，搬回来。

[um.cu](code/ch16/um.cu) 用 256 MB 的 managed memory 量了一下这些搬运的代价（`scale` 是一个读写每个元素的 kernel，`cpu_sum` 在 CPU 上把数组读一遍）：

```text
参照：CPU 读一遍普通内存   26.5 ms

managed 内存，CPU 初始化之后：
  GPU 第一次读写        34.7 ms
  GPU 第二次读写         1.7 ms
  CPU 读一遍            62.2 ms
  CPU 再读一遍          26.3 ms
  prefetch 到 GPU       19.3 ms，之后 GPU 读写   1.6 ms
```

GPU 第一次读写要 34.7 ms，第二次只要 1.7 ms，差的那 33 ms 就是缺页和迁移。256 MB 用了 34.7 ms，折合 7.7 GB/s，只有 pinned 内存拷贝速度（14.4 GB/s，第 15 章）的一半左右：GPU 发生缺页时，相关的 warp 要停下来，等驱动处理完缺页、把数据搬过来才能继续，搬运是一批一批零敲碎打地进行的。

CPU 回头再读，数据又要一页页地迁回主机内存，62.2 ms，是读普通内存的两倍多。再读第二遍，页面已经在主机内存里了，就和普通内存一样快。

## 16.2 prefetch：提前告诉驱动

如果事先知道接下来 GPU 要用哪块数据，可以让驱动提前整块搬过去，不必等缺页：

```cpp
{{#include code/ch16/um.cu:prefetch}}
```

prefetch 用了 19.3 ms，正好是 pinned 内存拷贝 256 MB 的速度，之后 GPU 读写只要 1.6 ms。整块地、成批地搬运，比靠缺页一点点地搬快得多。`cudaMemPrefetchAsync` 和 `cudaMemcpyAsync` 一样是放进 stream 的异步操作，可以和别的工作重叠（第 13 章）；把位置换成 `cudaMemLocationTypeHost`，就是把数据预先搬回主机内存。

注意这个函数在 CUDA 13 里换了签名：目标位置用 `cudaMemLocation` 结构表示，多了一个 `flags` 参数。CUDA 12 及以前的写法是 `cudaMemPrefetchAsync(ptr, bytes, device, stream)`，第三个参数直接是设备编号，CPU 用 `cudaCpuDeviceId`。

## 16.3 CPU 和 GPU 交替读

有些数据要被 CPU 和 GPU 轮流使用。如果两边都只读不写，按上面的机制，每次换一边读，数据就要整块搬一趟。um.cu 让 GPU 和 CPU 交替把同一块数据读 5 轮：

```text
交替读 5 轮            ：GPU 共  134.8 ms，CPU 共  311.9 ms
交替读 5 轮（ReadMostly）：GPU 共   34.8 ms，CPU 共  131.4 ms
```

不加任何提示时，每一轮 GPU 都要缺页迁移（平均 27 ms），CPU 也要缺页迁回（平均 62 ms）。第二行在开始前给了驱动一个提示：

```cpp
{{#include code/ch16/um.cu:advise}}
```

`cudaMemAdviseSetReadMostly` 告诉驱动这块数据主要是读的。驱动于是允许每一页在主机内存和显存里各有一份只读的副本：GPU 第一次读时复制一份过去，之后 CPU 读主机那份、GPU 读显存那份，谁都不用再搬。5 轮下来，GPU 只在第一轮付了复制的钱，CPU 每轮都是普通内存的速度。代价是如果有一方写了某一页，其他副本就要作废，下次读时再重新复制。

另外两种常用的提示：

- `cudaMemAdviseSetPreferredLocation`：让数据尽量住在指定的位置。别的处理器访问时，驱动会尽量建立映射让它远程访问，而不是把页搬走。
- `cudaMemAdviseSetAccessedBy`：让指定的处理器总能直接访问这块数据，不发生缺页。数据住在别处时，访问经 PCIe 远程进行，相当于第 15 章的零拷贝。

## 16.4 比显存还大的数据

managed memory 还有一个显式拷贝做不到的能力：分配的总量可以超过显存。显存满了，驱动就把一部分页赶回主机内存，需要时再搬回来。[oversub.cu](code/ch16/oversub.cu) 分配 2 到 9 GB 的 managed memory（这里的 GB 是 2³⁰ 字节），先用 kernel 在 GPU 上初始化，再把整块数据读写两遍：

```text
显存 8.1 GB，其中可用 8.0 GB

数据量    第一遍读写       第二遍读写
   2 GB        14 ms 299.2 GB/s        14 ms 300.3 GB/s
   4 GB        29 ms 294.9 GB/s        29 ms 295.1 GB/s
   6 GB        44 ms 291.7 GB/s        44 ms 292.1 GB/s
   7 GB        52 ms 291.9 GB/s        52 ms 291.6 GB/s
   8 GB      3994 ms   4.3 GB/s      1780 ms   9.7 GB/s
   9 GB      3991 ms   4.8 GB/s      1913 ms  10.1 GB/s
```

7 GB 以内，数据全在显存里，速度和普通显存差不多。8 GB 已经超出了显存实际能用的部分，速度一下掉到原来的几十分之一。

原因在于访问方式。这个 kernel 从头到尾扫一遍数组，数据比显存大一点点，扫到后面时，显存装不下，驱动就得把前面的页赶出去；下一遍从头开始扫，前面的页又不在了，再把后面的页赶出去换回来。几乎每一页每一遍都要在 PCIe 上走一个来回。这和操作系统内存不够时的频繁换页是一回事。

所以，超量分配能保证程序正确地跑完，但不能保证跑得快。数据真比显存大时，更好的做法是自己分块：每次只把放得下的一块搬上来处理完，像第 13 章那样流水线化；或者至少按块 prefetch，让驱动提前成批地搬，而不是靠缺页。只扫一遍的流式数据，也可以用 `cudaMemAdviseSetAccessedBy` 让 GPU 直接远程读，免得来回迁移。

## 16.5 HMM：malloc 的内存也能直接用

第 2 章提到，这台机器上 kernel 可以直接读写 `malloc` 来的普通内存，因为 Linux 开源驱动支持 HMM（heterogeneous memory management）。um.cu 的最后一部分把一块 `malloc` 来、在 CPU 上初始化过的 256 MB 内存直接交给 kernel：

```cpp
{{#include code/ch16/um.cu:hmm}}
```

```text
malloc 内存（HMM），CPU 初始化之后：
  GPU 第一次读写       211.2 ms
  GPU 第二次读写         2.0 ms
  CPU 读一遍           150.0 ms
```

和 managed memory 的行为很像：第一次访问时页面被迁到显存，第二次就快了，CPU 再读又迁回来。但每一步都慢得多：GPU 第一次读写要 211 ms，是 managed memory 的 6 倍；CPU 迁回要 150 ms，是 2.4 倍。HMM 的缺页要经过操作系统通用的内存管理路径，处理每一页的开销比驱动自己管理的 managed memory 大。

HMM 最大的价值在于移植：一个已有的大型 CPU 程序，数据结构都是 `new` 和 `malloc` 出来的，可以先把热点函数改写成 kernel，直接传指针进去，程序马上就能跑；然后再看 profiler 的报告，把真正频繁使用的数据改成显式管理。它的限制是平台：需要 Linux、较新的内核和开源版本的 NVIDIA 内核驱动，Windows 和 WSL 上没有这个能力。

## 16.6 什么时候用 Unified Memory

把这一章的实验归纳一下：

- **适合**：快速写出能跑的原型；数据结构里有大量指针、深拷贝很麻烦的场合（树、图、带指针的结构体数组）；需要处理超过显存的数据、而且可以接受慢一些的场合。
- **要提速**：在已知的访问模式上加 prefetch 和 advice。做到位以后，managed memory 可以和显式拷贝一样快，代码却简洁得多。
- **需要可预测的性能时**：用 `cudaMalloc` 加显式拷贝，配合第 13 章的 stream 流水线。缺页迁移的时间很难预测，对延迟敏感的程序不合适。

还有一个平台差异要注意。在这台 Linux 机器上，`cudaDevAttrConcurrentManagedAccess` 属性是 1，CPU 可以在 GPU 运行 kernel 的同时访问 managed memory（各自缺页迁移就是了）。在 Windows 等不支持并发访问的平台上，这个属性是 0，GPU 上有工作在执行时，CPU 访问 managed memory 会出错，必须先同步。写跨平台的代码，访问之前同步一下最稳妥。

## 16.7 回头看

Unified Memory 让 CPU 和 GPU 共用一个指针，数据按页在主机内存和显存之间自动迁移。靠缺页迁移比成批拷贝慢一倍左右，CPU 和 GPU 交替访问时会来回搬运；用 `cudaMemPrefetchAsync` 提前成批地搬，用 `cudaMemAdvise` 告诉驱动访问模式（比如 ReadMostly 让两边各留一份只读副本），可以把这些代价大部分省掉。managed memory 允许超量分配，但数据超过显存时，顺序扫描会导致每一页反复换入换出，慢几十倍。HMM 让 `malloc` 来的内存也能直接交给 kernel，方便移植，但缺页的代价更高。

## 16.8 练习

1. 在 um.cu 里，CPU 初始化之后先 prefetch 到 GPU，再让 GPU 读写，和直接读写比较；然后把 prefetch 放进一条单独的 stream，同时在另一条 stream 上跑一个无关的 kernel，用 nsys 看两者是否重叠。
2. 把交替读的实验改成 GPU 读写、CPU 只读。加了 ReadMostly 以后还快吗？为什么？
3. 给 oversub.cu 的 9 GB 情况加上分块 prefetch：每次 prefetch 1 GB 到 GPU，处理完这 1 GB 再 prefetch 下一块。和原来的版本比较。
4. 用 `cudaMemAdviseSetAccessedBy` 和 `cudaMemAdviseSetPreferredLocation`（位置设为主机）处理 8 GB 的情况，让 GPU 直接远程读写而不迁移。速度变成多少？和 PCIe 带宽对照。
