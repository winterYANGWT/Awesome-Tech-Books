# 第 22 章 内存模型：atomic、fence 与作用域

第 5 章遇到的数据竞争发生在一个 block 内部，用 `__syncthreads()` 就能解决。可一旦线程要跨越 block、甚至跨越 CPU 和 GPU 通过内存通信，事情就复杂了：一个线程写下的值，另一个线程什么时候能看到？两次写入，对方看到的顺序和写的顺序一致吗？回答这些问题的规则叫**内存模型**。这一章用几个实验说明不遵守规则会出什么问题，以及 CUDA 提供的工具：原子操作、内存序和作用域。

## 22.1 两个 block 之间传消息

[message.cu](code/ch22/message.cu) 让一个 kernel 里的两个 block 来回传 2000 轮消息：block 0 是生产者，写好 4096 个 `int` 的数据，再把标志 `flag` 设成轮次号；block 1 是消费者，等到标志变成这一轮的号码，读出数据检查，读完把确认 `ack` 设成轮次号；生产者等到确认，再写下一轮。两个 block 一定同时驻留，所以互相等待不会死锁。为了防止卡死，每次等待最多转一千万圈。

最直接的写法，数据、标志、确认都是普通变量：

```cpp
{{#include code/ch22/message.cu:plain}}
```

第二种写法把标志和确认改成 `volatile` 访问，数据仍是普通变量；第三种用原子操作，后面再看。结果：

```text
普通变量                 读到旧数据 8188320 个，等不到对方 2955 次
volatile 标志              读到旧数据 8187904 个，等不到对方    0 次
atomic_ref release/acquire   读到旧数据       0 个，等不到对方    0 次
```

**普通变量**：几乎所有读取都是旧数据，还有将近 3000 次等不到对方。编译器看到 `while (s->flag != r)` 这个循环里没有任何代码修改 `flag`，就有权只读一次、把值留在寄存器里反复比较。对编译器来说，这是完全合法的优化，因为普通变量没有“别的线程会改它”的语义。

**volatile**：`volatile` 强迫每次都真的去内存里读，标志的问题解决了，不再有等不到的情况。可是 2000 轮、819.2 万次读取里，有 818.8 万次读到了旧数据，只有第一轮的 4096 次是对的。原因在缓存：每个 SM 有自己的 L1 缓存，它们之间不保持一致。消费者第一轮读数据时，这些数据进了它所在 SM 的 L1；之后生产者在另一个 SM 上写的新值进了 L2，消费者的 L1 却并不知道，照样把旧值交给它。

所以“看得见”有两层：编译器不能把值藏在寄存器里，硬件也不能让你读到过期的缓存。`volatile` 只解决了前一层。

## 22.2 release 和 acquire

正确的写法是用原子操作，并指明内存序：

```cpp
{{#include code/ch22/message.cu:acquire_release}}
```

`cuda::atomic_ref` 来自 CUDA 自带的 libcu++（`<cuda/atomic>`），把一个普通变量当作原子变量来访问，用法和 C++ 标准库的 `std::atomic_ref` 一样，多了一个作用域参数。这里的关键是两个内存序：

- 生产者用 `memory_order_release` 写标志：在此之前它写的所有数据，都会在这次写入之前变得对外可见。
- 消费者用 `memory_order_acquire` 读标志：如果读到了生产者写的那个值，那么在此之后的读取一定能看到生产者 release 之前写的所有数据，不会拿到过期的缓存。

两者配对，消息就能正确传递。release 和 acquire 本身只作用在标志这一个变量上，但它们约束了前后所有普通内存访问的可见性和顺序，这正是“内存序”的含义。其他几种内存序：`relaxed` 只保证这一次操作本身是原子的，不约束别的访问，适合纯粹的计数器；`acq_rel` 同时具有两者的效果，用于“读-改-写”的原子操作；`seq_cst`（默认值）最严格，所有线程看到的顺序都一致，也最慢。

也可以把原子操作和内存序分开写：普通的原子写加一个单独的 fence（`cuda::atomic_thread_fence(cuda::memory_order_release, cuda::thread_scope_device)`）。老代码里常见的 `__threadfence()` 加 `volatile` 的写法也能工作，但很容易漏掉一边。新代码建议直接用 libcu++ 的原子类型，意图写在代码里，编译器和硬件都照着做。

## 22.3 作用域

`cuda::atomic_ref<int, cuda::thread_scope_device>` 的第二个参数是**作用域**，说明这个原子操作要对哪些线程保证原子性和可见性：

- `thread_scope_block`：同一个 block 里的线程；
- `thread_scope_device`：同一块 GPU 上的所有线程；
- `thread_scope_system`：所有 GPU 上的线程，以及 CPU。

对应的旧式函数是 `atomicAdd_block`、`atomicAdd` 和 `atomicAdd_system`。原则上作用域越小，硬件需要做的协调越少。[atomics.cu](code/ch22/atomics.cu) 让每个 block 的线程争一个计数器，分别用三种作用域：

```cpp
{{#include code/ch22/atomics.cu:scope}}
```

```text
作用域（每个 block 一个计数器）：
    0.47 ms   1420.0 亿次/秒  atomicAdd_block（block 作用域）
    0.47 ms   1405.0 亿次/秒  atomicAdd（device 作用域）
    0.47 ms   1423.2 亿次/秒  atomicAdd_system（system 作用域）
```

在 global memory 上，三者一样快：这块 GPU 的 global memory 原子操作都在 L2 里完成。作用域的意义主要在正确性上。atomics.cu 的最后一部分让 CPU 和 GPU 同时给同一个计数器各加 100 万次，结果应该是 200 万：

```cpp
{{#include code/ch22/atomics.cu:cpu_gpu}}
```

```text
GPU 对主机内存的原生原子操作：不支持
CPU 和 GPU 同时给一个计数器各加 100 万次：
  pinned 内存 GPU 用 atomicAdd         结果 1000000
  pinned 内存 GPU 用 atomicAdd_system  结果 1000000
  managed 内存 GPU 用 atomicAdd         结果 1537396
  managed 内存 GPU 用 atomicAdd_system  结果 2000000
```

只有最后一行是对的。先看 managed 内存（第 16 章）：计数器所在的页在 CPU 和 GPU 之间来回迁移，用 system 作用域时，驱动和硬件保证 CPU 和 GPU 的原子操作互不干扰；用 device 作用域时，原子性只对 GPU 内部的线程保证，丢了 46 万次。

pinned 内存上，两种作用域都只得到 100 万，有一方的更新整个丢了。第一行的输出说明了原因：这台机器的设备属性 `cudaDevAttrHostNativeAtomicSupported` 是 0，PCIe 链路不支持 GPU 对主机内存做原生的原子操作，GPU 对零拷贝内存的“原子加”并不是在主机内存上原子地完成的。不是所有平台都这样，这个属性在有的服务器上是 1。所以 CPU 和 GPU 要共享原子变量时，先查这个属性；为 0 时用 managed 内存。

## 22.4 原子操作的代价取决于争用

最后看原子操作的速度。atomics.cu 的第一部分做 6400 万次原子加，只改地址的分布：

```cpp
{{#include code/ch22/atomics.cu:contention}}
```

```text
争用程度：
    0.82 ms    813.2 亿次/秒  所有线程加同一个地址
    5.04 ms    131.8 亿次/秒  每个 warp 一个地址
    0.34 ms   1972.5 亿次/秒  每个线程一个地址
    0.82 ms    811.2 亿次/秒  warp 内先合并，再加同一个地址
```

每个线程加自己的地址，没有争用，最快，每秒近 2000 亿次。每个 warp 一个地址时，同一个 warp 的 32 个线程挤在同一个地址上，硬件只能依次处理，慢了 15 倍。

奇怪的是第一行：所有线程都加同一个地址，争用应该最严重，却比每个 warp 一个地址快 6 倍，和第四行手工做的“warp 内先合并”一样快。看一下 SASS 就明白了：`one_address` 里出现了 `VOTEU`、`POPC` 和 `UFLO`，编译器证明了所有线程的地址相同、加的都是 1，于是自动把每个 warp 的 32 次原子加合并成一次，加数是活跃线程的个数。`per_warp` 的地址因线程而异，编译器证明不了它在 warp 内相同，就老老实实地让每个线程各做一次。

所以减少原子操作争用的基本办法是先在局部合并：warp 内用 `cg::reduce` 或 shuffle（第 11 章）合并，block 内用 shared memory 合并（第 19 章的直方图），最后才对 global memory 做一次原子操作。地址能分散就尽量分散。编译器的自动合并只在它能证明地址和加数都一致时才会发生，不能指望。

## 22.5 回头看

线程之间通过内存通信时，要同时防住编译器和硬件：编译器可能把普通变量的值留在寄存器里，每个 SM 的 L1 缓存之间也不保持一致。`volatile` 只能解决前者。正确的做法是用 libcu++ 的原子操作配合内存序：写的一方 release，读的一方 acquire，之前写下的数据就一定能被看到。作用域说明原子操作要对谁有效，CPU 和 GPU 共享的变量必须用 system 作用域，而且要先确认平台支持；这台机器的 PCIe 链路不支持对主机内存的原生原子操作，只有 managed 内存配合 system 作用域才得到了正确结果。原子操作的速度取决于争用程度，先局部合并再原子操作，是最有效的优化。
