# 第 26 章 cuRAND 与 cuFFT

这一章介绍另外两个常用的库：生成随机数的 cuRAND 和做快速傅里叶变换的 cuFFT。蒙特卡洛模拟、随机初始化、数据增强都离不开大量的随机数；信号处理、卷积、偏微分方程的谱方法都离不开 FFT。两个库的用法都不复杂，但各有一个影响性能的关键：cuRAND 是生成器的选择和初始化方式，cuFFT 是 plan 的复用和变换长度。

## 26.1 cuRAND 的主机端 API

cuRAND 有两套接口。主机端 API 由主机调用，一次在显存里生成一大批随机数，用法类似 cuBLAS：创建生成器、设种子、生成。[rng.cu](code/ch26/rng.cu) 用四种生成器各生成 2.5 亿多个均匀分布的 `float`，再用这些数两两一组估算 π（落在单位圆里的比例约为 π/4）。链接时加 `-lcurand`：

```cpp
{{#include code/ch26/rng.cu:host_api}}
```

```text
生成 268435456 个均匀分布的 float：
  XORWOW（默认）   3.11 ms    345 GB/s   π ≈ 3.141511
  Philox4x32-10      2.99 ms    360 GB/s   π ≈ 3.141616
  MRG32k3a           6.38 ms    168 GB/s   π ≈ 3.141499
  MT19937            6.63 ms    162 GB/s   π ≈ 3.141611
  CPU std::mt19937     35 ms（只生成了十分之一，折合全部 352 ms）
```

XORWOW 和 Philox 生成随机数的速度，基本就是把它们写进显存的速度（第 1 章测过最高约 336 GB/s），生成本身几乎不花时间。MRG32k3a 和 MT19937 的统计性质更好，速度慢一半。和 CPU 单线程的 `std::mt19937` 比，快了一百多倍。

主机端 API 适合“先生成、后使用”的场合。缺点是要先把随机数写进显存，用的时候再读出来，多了一读一写。如果随机数只在一个 kernel 里用一次，更好的办法是在 kernel 里边生成边用。

## 26.2 在 kernel 里生成：初始化的代价

设备端 API（`<curand_kernel.h>`）让每个线程持有自己的生成器状态：

```cpp
{{#include code/ch26/rng.cu:device_api}}
```

`curand_init(seed, id, 0, &st)` 的第二个参数是子序列编号：所有线程用同一个种子，各取一条不同的子序列，保证彼此不相关。rng.cu 的后半部分用 16 万个线程、每个生成 4096 对随机数估算 π，并单独测一下只做初始化要多久：

```text
在 kernel 里生成（159744 个线程，每个 4096 对）：
  XORWOW             只做 curand_init：   2.23 ms
  XORWOW             初始化并生成：     3.11 ms   π ≈ 3.141662
  Philox             只做 curand_init：   0.51 ms
  Philox             初始化并生成：     5.51 ms   π ≈ 3.141630
  Philox，uniform4  只做 curand_init：   0.33 ms
  Philox，uniform4  初始化并生成：     4.11 ms   π ≈ 3.141630
```

两种生成器的代价分布截然不同。XORWOW 的初始化很贵：要跳到第 `id` 条子序列，需要做一连串的矩阵运算，光初始化就花了 2.23 ms；但之后生成每个数很快。Philox 是基于计数器的生成器，跳到任意位置几乎不花时间，初始化只要零点几毫秒；但它每次内部产生 4 个数，用 `curand_uniform` 一次只取一个时有浪费，换成 `curand_uniform4` 一次拿 4 个，就从 5.51 ms 降到 4.11 ms。

在这个例子里，每个线程要生成 8192 个数，XORWOW 昂贵的初始化被摊薄了，总时间仍然最短。如果每个线程只需要几个随机数，比如每个粒子每一步要一个随机扰动、每步都重新初始化，初始化就会成为主要开销，这时 Philox 合适得多。另一个常见的做法是把生成器状态保存在显存里，下次 kernel 接着用，只在程序开始时初始化一次。

## 26.3 cuFFT：plan 和执行

cuFFT 的用法分两步：先创建 plan，告诉它变换的长度、类型和批量；再用 plan 执行变换。[fft.cu](code/ch26/fft.cu) 对 2²⁴ 个复数做一维 FFT，链接时加 `-lcufft`：

```cpp
{{#include code/ch26/fft.cu:plan}}
```

```text
长度 2^24 的复数 FFT：创建 plan 1.9 ms，执行一次 2.40 ms
正变换再逆变换，与原始数据的最大误差 2.0e-06
```

创建 plan 时，cuFFT 根据长度选择算法、分解方式，分配工作区，和执行一次变换的时间差不多。在这台机器上第一次运行这个程序时，创建第一个 plan 用了 80 ms，以后再运行都只要 2 ms 左右；关掉 JIT 缓存（第 4 章）也还是 2 ms，所以不是在编译 kernel。cuFFT 的库文件有 245 MB，很可能是第一次运行时把它从磁盘读进内存花了时间。第 25 章 cuSOLVER 第一次调用多出来的开销，也是同一类问题。不管哪种情况，结论都一样：plan 要在程序开始时创建好，反复使用，不要每做一次变换就创建一次。

结果的验证用正变换再逆变换：

```cpp
{{#include code/ch26/fft.cu:roundtrip}}
```

注意 cuFFT 的逆变换不做归一化，结果是原数据的 n 倍，要自己除以 n。

## 26.4 长度和批量

FFT 的速度和变换长度的分解方式有关。fft.cu 比较了三种差不多长的变换：

```text
长度              创建 plan    执行一次
 16777216（2^24）     0.5 ms      2.40 ms
 16000000（2^10·5^6）     0.5 ms      2.28 ms
 16777213（质数）    64.1 ms     10.28 ms
```

只含 2、3、5、7 这类小质因子的长度，速度都差不多；质数长度要用另一套算法（把它转化成更长的、可以快速计算的卷积），创建 plan 要 64 ms，执行慢了 4 倍多。所以设计算法时，如果长度可以选择，就把它补齐到只含小质因子的长度，比如在数据末尾填零。

很多应用要做大量独立的小变换，比如对一幅图像的每一行分别做 FFT。不要在循环里一个个地做，而是用 `cufftPlanMany` 一次提交：

```cpp
{{#include code/ch26/fft.cu:batch}}
```

```text
4096 个长度 4096 的变换（批量）：执行一次 0.80 ms
```

总点数和前面的 2²⁴ 一样，时间却只有三分之一。长度 4096 的变换可以整个放进一个 block 的 shared memory 里完成，而 2²⁴ 的大变换要分几趟在显存里来回读写。

最后，输入是实数时，用实数到复数（R2C）的变换：

```cpp
{{#include code/ch26/fft.cu:r2c}}
```

```text
长度 2^24 的实数 FFT（R2C）：执行一次 1.57 ms
```

实数信号的频谱是共轭对称的，另一半可以由这一半推出，所以输出只需要 n/2 + 1 个复数，计算量也几乎减半，比把实数补成复数再做 C2C 快了三分之一。逆变换用 C2R。

## 26.5 回头看

cuRAND 的主机端 API 生成随机数的速度接近显存带宽，比 CPU 快一百多倍；在 kernel 里生成时，要在 XORWOW（初始化贵、生成快）和 Philox（初始化便宜、要成组地取数）之间按用量选择，或者把生成器状态保存下来反复使用。cuFFT 的 plan 要一次创建、反复执行；变换长度最好只含小质因子，质数长度慢 4 倍；大量小变换用批量接口一次提交；实数输入用 R2C。和上一章一样，这些库第一次调用都可能有可观的初始化开销，测量时要预热。
