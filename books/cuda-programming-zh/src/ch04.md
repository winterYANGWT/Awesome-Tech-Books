# 第 4 章 nvcc 做了什么

一个 `.cu` 文件里同时有两种代码：`main` 这样的主机代码在 CPU 上跑，kernel 在 GPU 上跑。两种处理器的指令集完全不同，nvcc 要把它们分开编译，再装进同一个可执行文件。平时 `nvcc foo.cu -o foo` 一条命令就完事了，但有几件事迟早会碰到：程序拷到另一台机器上报 “no kernel image is available”；同一个程序第一次运行比后来慢好几百毫秒；调试版本慢得离谱。这些都和编译产物有关。本章用一个最小的程序 [tiny.cu](code/ch04/tiny.cu) 把 nvcc 的工作过程拆开看：

```cpp
{{#include code/ch04/tiny.cu:kernel}}
```

nvcc 自己不编译任何东西，它是个调度者。13 步分成三路：

- <span class="cu-map-at" data-on="tiny.cu gcc-host-pre cudafe++ gcc-host tiny.cu>gcc-host-pre gcc-host-pre>cudafe++ cudafe++>gcc-host fatbin>gcc-host"></span>**主机这一路**（第 1、2、8 步）：`gcc` 先按主机的视角预处理，`cudafe++` 从中拆出主机代码，把 `saxpy<<<...>>>(...)` 换成对 CUDA 运行时库的普通函数调用，最后由 `gcc` 编译成目标文件。
- <span class="cu-map-at" data-on="tiny.cu gcc-gpu-pre cicc ptx ptxas sass fatbinary fatbin tiny.cu>gcc-gpu-pre gcc-gpu-pre>cicc cicc>ptx ptx>ptxas ptxas>sass sass>fatbinary ptx>fatbinary fatbinary>fatbin fatbin>gcc-host"></span>**GPU 这一路**（第 3–6 步）：`gcc` 定义 `__CUDA_ARCH__` 把源码再预处理一遍；`cicc` 是 NVIDIA 基于 LLVM 的 GPU 编译器，把 kernel 编译成 **PTX**；`ptxas` 把 PTX 汇编成 sm_120 这种具体架构的机器码，叫 **SASS**，装在 `.cubin` 文件里；`fatbinary` 把 cubin 和 PTX 打成一个包，叫 **fatbin**，写成一个 C 数组，第 8 步编译主机代码时一起编进去。
- <span class="cu-map-at" data-on="gcc-host nvlink g++ exe gcc-host>nvlink nvlink>g++ g++>exe"></span>**链接**（第 9–13 步）：`nvlink` 做 GPU 代码的链接，结果同样打包、编进一个小目标文件，最后 `g++` 把所有目标文件和 CUDA 运行时库链接成可执行文件。

真正编译 kernel 的只有 `cicc` 和 `ptxas` 两步，`gcc` 却出现了四次：两次预处理，两次编译。同一个源文件预处理两次，是因为 `__CUDA_ARCH__` 只在编译 GPU 代码时才有定义，代码可以用它让主机和 GPU 走不同的分支。

<span class="cu-map-at" data-on="ptx sass"></span>加上 `-keep` 选项，这些中间文件都会留在当前目录里，其中 `tiny.ptx` 和 `tiny.sm_120.cubin` 就是下面要看的两样东西。

## 4.2 PTX 和 SASS

<span class="cu-map-at" data-on="cicc cicc>ptx ptx ptx>ptxas ptxas ptxas>sass sass"></span>kernel 从源码到在 GPU 上执行，要经过两次翻译：

- `cicc` 把 C++ 编译成 **PTX**。PTX 是一种“虚拟”指令集：寄存器（`%r1`、`%rd3`……）要多少有多少，指令也不对应任何一代具体的硬件。
- `ptxas` 把 PTX 汇编成 **SASS**，也就是某一代 GPU 的机器码，这里是 sm_120。寄存器分配、指令调度这些和硬件密切相关的优化，都在这一步做。
- 真正在 GPU 上执行的是 SASS。PTX 还会原样装进可执行文件，留给驱动以后在更新的 GPU 上重新编译（4.3 节）。

三者怎么对应起来？编译时加上 `-lineinfo`，PTX 里会多出 `.loc` 行，标出每段指令来自源码第几行；`nvdisasm -g` 和 `-gp` 能标出每条 SASS 来自源码和 PTX 的哪一行。`-lineinfo` 不改变生成的代码，指令和不加时完全一样。图 4.2 就是用这三份输出做的：点任意一行，另外两栏里对应的行会亮起来；也可以按“下一步”从上往下走一遍。

即使没学过 PTX 也能大致读懂。`_Z5saxpyifPKfPf` 是 `saxpy(int, float, const float*, float*)` 经过 C++ 名字修饰后的名字。`%ctaid.x`、`%ntid.x`、`%tid.x` 就是 `blockIdx.x`、`blockDim.x`、`threadIdx.x`，`mad.lo.s32` 算出 `i`。`setp.ge.s32` 和 `@%p1 bra` 是 `if (i < n)`：条件不成立就跳到结尾。然后两次 `ld.global` 读 `x[i]` 和 `y[i]`，`fma.rn.f32` 算 `a * x[i] + y[i]`（这就是第 3 章说的乘加合并），`st.global` 写回。

SASS 的结构和 PTX 大体对应，但已经是具体的硬件了：寄存器有了编号（`R0`、`R7`），`S2R` 读取线程编号这样的特殊寄存器，`LDG`、`STG` 读写显存，`FFMA` 是浮点乘加。另外还有一组 `UR` 开头的寄存器，存放对整个 warp 都相同的值，比如 `blockIdx.x` 和参数 `a`，这样每个 warp 只需要算一次。对照着看，还能看出 `ptxas` 做了哪些改动：

- PTX 开头的四条 `ld.param` 在 SASS 里没有对应的指令。kernel 的参数留在常量存储 `c[0x0][0x380]` 起的位置，用到时才由 `LDC`、`LDCU` 读出来：`n` 在比较之前读，`a` 在乘加之前读。
- 两条 `cvta.to.global` 消失了，`mul.wide` 和 `add` 合成了一条 `IMAD.WIDE`。
- 跳到结尾的 `@%p1 bra` 变成了带条件的 `@P0 EXIT`：越界的线程直接结束。
- 也有 PTX 里没有的指令：函数入口的 `LDC R1, c[0x0][0x37c]` 给 R1 赋初值（按约定 R1 是栈指针，这个 kernel 用不上），`LDCU.64 UR4, c[0x0][0x358]` 读出的 `UR4`，后面在 `desc[UR4]` 里用作访存的描述符。

所以分析性能时，要看的是 SASS。第 1 章就是数 SASS 里的 `FMUL` 和 `FFMA` 算出 heavy 跑到了峰值的几成。

## 4.3 fatbin 里装了什么，能在哪些 GPU 上跑

<span class="cu-map-at" data-on="fatbin exe exe>fatbin-exe fatbin-exe fatbin-exe>driver driver driver>has-sass has-sass has-sass>direct direct has-sass>jit jit has-sass>noimage noimage"></span>`-arch` 和 `-gencode` 两个选项决定 fatbin 里装什么。先分清两个名字：

- **`compute_XY` 是虚拟架构**：一级 PTX 功能集，意思是“按计算能力 X.Y 的功能写出的 PTX”。它不是哪一块具体的 GPU。
- **`sm_XY` 是真实架构**：计算能力 X.Y 那一代 GPU 的机器码 SASS。这块 RTX 5060 的计算能力是 12.0，它直接认的是 sm_120。

`-gencode arch=…,code=…` 的两个参数，分别管图 4.1 里的第 4 步和第 5 步：

- `arch=compute_XY` 决定 `cicc` 按哪一级虚拟架构生成 PTX，也就决定了代码能用哪些功能。
- `code=` 决定最后往 fatbin 里装什么。写 `sm_XY`，就让 `ptxas` 把 PTX 汇编成那一代的 SASS 装进去；写 `compute_XY`，就把 PTX 本身装进去，留给驱动在运行时编译；两样都要就写 `code=[sm_XY,compute_XY]`。`code` 里的架构不能低于 `arch`：按 compute_100 的功能写出的 PTX，没法汇编成 sm_90 的机器码。

`-arch=sm_XY` 是个简写，等于 `-gencode arch=compute_XY,code=[sm_XY,compute_XY]`。

程序启动 kernel 时，驱动在 fatbin 里按这个顺序找：

1. 有没有这块 GPU 能直接用的 SASS：主版本相同、次版本不高于它。在 12.0 上，sm_120 的 SASS 能用；sm_121（次版本更高）、sm_90 和 sm_86（主版本不同）都不行。
2. 没有的话，找计算能力不高于它的 PTX，JIT（just-in-time）编译成 sm_120 的 SASS 再运行。4.4 节会看到这一步要花时间。
3. 两样都没有，报 `cudaErrorNoKernelImageForDevice`：“no kernel image is available for execution on the device”。

每种 SASS 在 `cuobjdump` 里是两个 ELF 文件，一个是 kernel 本身，一个是 `nvlink` 生成的辅助代码。

这就解释了两个看上去矛盾的结果。`code=sm_90` 装进去的只有 sm_90 的 SASS，主版本是 9，这块 12.0 的 GPU 用不了，又没有 PTX 可以退而求其次，于是报错。`code=compute_80` 装进去的是 PTX，计算能力 8.0 不高于 12.0，驱动把它 JIT 编译成 sm_120 的 SASS，就能运行。PTX 可以在计算能力不低于它的任何 GPU 上运行；SASS 只能在同一个主版本里往后用。

`-arch=native` 只为本机的 GPU 生成 SASS，**不带 PTX**，这样编出来的程序换到更新一代的 GPU 上就跑不了。

计算能力还可以带两种后缀。`sm_90a`、`sm_120a` 这种 `a` 后缀表示“只属于这一个架构的特性”，比如 Hopper 上的某些矩阵指令，这样编出的代码只能在计算能力完全相同的 GPU 上运行。`f` 后缀表示“这一家族共有的特性”，可以在同一家族里计算能力不低于它的 GPU 上运行。本机只能验证它们在 12.0 上自己能跑，到别的 GPU 上的行为这里没法实测。不使用这些特定架构的指令时，用不带后缀的版本就行。

发布程序时的常见做法是：为打算支持的每种架构各生成一份 SASS，再加上最新架构的 PTX。前者保证已知的 GPU 不用 JIT，后者保证将来的新 GPU 也能跑：

```bash
nvcc -gencode arch=compute_80,code=sm_80 \
     -gencode arch=compute_90,code=sm_90 \
     -gencode arch=compute_120,code=sm_120 \
     -gencode arch=compute_120,code=compute_120 \
     app.cu -o app
```

只带 PTX 的版本，第一轮启动 64 个 kernel 花了 260 ms，比 SASS 版本多了两百多倍，多出来的就是驱动现场编译这 64 个 kernel 的时间。第二轮就和 SASS 版本一样了，因为编译结果已经在内存里。

驱动会把 JIT 的结果存到磁盘上的缓存里（Linux 下默认是 `~/.nv/ComputeCache`），下次运行同一个程序就直接取出来用。上面用 `CUDA_CACHE_DISABLE=1` 关掉了缓存，所以每次都要重新编译；打开缓存以后，第一次运行仍要编译 265 ms，第二次第一轮只要 2.3 ms。缓存的位置和大小可以用环境变量 `CUDA_CACHE_PATH`、`CUDA_CACHE_MAXSIZE` 调整。

这个实验只有 64 个小 kernel。真实的大型程序和库里可能有成千上万个 kernel，如果发布时没有为某种 GPU 带 SASS，在这种 GPU 上第一次启动就可能要 JIT 编译好几分钟。新一代 GPU 刚上市、软件还没来得及更新的时候，这种情况很常见。

## 4.5 kernel 是什么时候装进 GPU 的

<span class="cu-map-at" data-on="direct>lazy jit>lazy lazy lazy>gpu gpu"></span>即使不需要 JIT，SASS 版本的第一轮也比第二轮慢：1.0 ms 对 0.2 ms。第 2 章遇到过同样的现象：第一次启动 kernel 慢了 0.1 ms。

原因是 CUDA 默认采用 lazy loading：程序初始化时并不把所有 kernel 的机器码都装到 GPU 上，而是等某个 kernel 第一次被启动时才装载它。64 个 kernel 各装载一次，平均十几微秒。设置 `CUDA_MODULE_LOADING=EAGER` 可以改回在初始化时全部装载，上面最后一行就是这样做的，结果 JIT 编译的时间整个挪到了初始化阶段，初始化变成了 431 ms，第一轮则和第二轮一样快。

lazy loading 让程序启动更快，没用到的 kernel 也不占显存，一般来说是好事。代价是每个 kernel 第一次启动时会有一次额外的延迟。做性能测量时要先把要测的 kernel 跑一遍预热；对延迟很敏感的服务，也可以在启动阶段把关键 kernel 预先跑一遍。
