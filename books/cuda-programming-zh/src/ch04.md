# 第 4 章 nvcc 做了什么

一个 `.cu` 文件里同时有两种代码：`main` 这样的主机代码在 CPU 上跑，kernel 在 GPU 上跑。两种处理器的指令集完全不同，nvcc 要把它们分开编译，再装进同一个可执行文件。平时 `nvcc foo.cu -o foo` 一条命令就完事了，但有几件事迟早会碰到：程序拷到另一台机器上报 “no kernel image is available”；同一个程序第一次运行比后来慢好几百毫秒；调试版本慢得离谱。这些都和编译产物有关。本章用一个最小的程序 [tiny.cu](code/ch04/tiny.cu) 把 nvcc 的工作过程拆开看：

```cpp
{{#include code/ch04/tiny.cu:kernel}}
```

nvcc 自己不编译任何东西，它是个调度者，按顺序调用一串工具：

- <span class="cu-map-at" data-on="tiny.cu tiny.cu>gcc-pre gcc-pre gcc-pre>cudafe++ cudafe++"></span>第一个 `gcc` 只做预处理，展开 `#include` 和宏，得到给 GPU 编译用的源码。
- <span class="cu-map-at" data-on="gcc-pre>cudafe++ cudafe++ cudafe++>cicc cicc cudafe++>host-code host-code"></span>`cudafe++` 把源码拆成两半：GPU 上执行的函数交给 GPU 编译链；主机代码留下来，其中的 `saxpy<<<...>>>(...)` 被替换成对 CUDA 运行时库的普通函数调用。
- <span class="cu-map-at" data-on="cicc cicc>ptx ptx"></span>`cicc` 是 NVIDIA 基于 LLVM 的 GPU 编译器，把 kernel 编译成 **PTX**。
- <span class="cu-map-at" data-on="ptxas ptxas>sass sass"></span>`ptxas` 把 PTX 汇编成 sm_120 这种具体架构的机器码，叫 **SASS**，装在一个 `.cubin` 文件里。
- <span class="cu-map-at" data-on="fatbinary sass>fatbinary ptx>fatbinary fatbinary>fatbin fatbin"></span>`fatbinary` 把 cubin 和 PTX 打成一个包，叫 **fatbin**。
- <span class="cu-map-at" data-on="host-code host-code>gcc-host gcc-host fatbin fatbin>gcc-host gcc-host>nvlink nvlink"></span>第二个 `gcc` 编译主机代码，fatbin 作为一个大数组嵌进去。
- <span class="cu-map-at" data-on="nvlink fatbin>nvlink gcc-host>nvlink nvlink>g++ g++ g++>exe exe"></span>`nvlink` 做 GPU 代码的链接，最后的 `g++` 把所有东西和 CUDA 运行时库链接成可执行文件。

<span class="cu-map-at" data-on="ptx sass"></span>加上 `-keep` 选项，这些中间文件都会留在当前目录里，其中 `tiny.ptx` 和 `tiny.sm_120.cubin` 就是下面要看的两样东西。

## 4.2 PTX 和 SASS

<span class="cu-map-at" data-on="cicc cicc>ptx ptx ptx>ptxas ptxas ptxas>sass sass"></span>先看 `tiny.ptx` 里的 saxpy：

```text
.visible .entry _Z5saxpyifPKfPf(
	.param .u32 _Z5saxpyifPKfPf_param_0,
	.param .f32 _Z5saxpyifPKfPf_param_1,
	.param .u64 .ptr .align 1 _Z5saxpyifPKfPf_param_2,
	.param .u64 .ptr .align 1 _Z5saxpyifPKfPf_param_3
)
{
	.reg .pred 	%p<2>;
	.reg .b32 	%r<10>;
	.reg .b64 	%rd<8>;

	ld.param.b32 	%r3, [_Z5saxpyifPKfPf_param_0];
	ld.param.b32 	%r2, [_Z5saxpyifPKfPf_param_1];
	ld.param.b64 	%rd1, [_Z5saxpyifPKfPf_param_2];
	ld.param.b64 	%rd2, [_Z5saxpyifPKfPf_param_3];
	mov.u32 	%r4, %ctaid.x;
	mov.u32 	%r5, %ntid.x;
	mov.u32 	%r6, %tid.x;
	mad.lo.s32 	%r1, %r4, %r5, %r6;
	setp.ge.s32 	%p1, %r1, %r3;
	@%p1 bra 	$L__BB0_2;
	cvta.to.global.u64 	%rd3, %rd1;
	cvta.to.global.u64 	%rd4, %rd2;
	mul.wide.s32 	%rd5, %r1, 4;
	add.s64 	%rd6, %rd3, %rd5;
	ld.global.b32 	%r7, [%rd6];
	add.s64 	%rd7, %rd4, %rd5;
	ld.global.b32 	%r8, [%rd7];
	fma.rn.f32 	%r9, %r2, %r7, %r8;
	st.global.b32 	[%rd7], %r9;
$L__BB0_2:
	ret;

}
```

即使没学过 PTX 也能大致读懂。`_Z5saxpyifPKfPf` 是 `saxpy(int, float, const float*, float*)` 经过 C++ 名字修饰后的名字。`%ctaid.x`、`%ntid.x`、`%tid.x` 就是 `blockIdx.x`、`blockDim.x`、`threadIdx.x`，`mad.lo.s32` 算出 `i`。`setp.ge.s32` 和 `@%p1 bra` 是 `if (i < n)`：条件不成立就跳到结尾。然后两次 `ld.global` 读 `x[i]` 和 `y[i]`，`fma.rn.f32` 算 `a * x[i] + y[i]`（这就是第 3 章说的乘加合并），`st.global` 写回。

PTX 是一种“虚拟”指令集。它的寄存器（`%r1`、`%rd3`……）要多少有多少，指令也不对应任何一代具体的硬件。NVIDIA 保证 PTX 向前兼容：为 compute_80 生成的 PTX，以后任何一代 GPU 都能把它编译成自己的机器码。

真正在 GPU 上执行的是 SASS。用 `cuobjdump -sass tiny` 查看（这里只保留了指令部分，省略了每行末尾的二进制编码和结尾用来填充的 `NOP`）：

```text
0000  LDC R1, c[0x0][0x37c] ;
0010  S2R R0, SR_TID.X ;
0020  S2UR UR4, SR_CTAID.X ;
0030  LDCU UR5, c[0x0][0x380] ;
0040  LDC R7, c[0x0][0x360] ;
0050  IMAD R7, R7, UR4, R0 ;
0060  ISETP.GE.AND P0, PT, R7, UR5, PT ;
0070  @P0 EXIT ;
0080  LDC.64 R2, c[0x0][0x388] ;
0090  LDCU.64 UR4, c[0x0][0x358] ;
00a0  LDCU UR6, c[0x0][0x384] ;
00b0  LDC.64 R4, c[0x0][0x390] ;
00c0  IMAD.WIDE R2, R7, 0x4, R2 ;
00d0  LDG.E R2, desc[UR4][R2.64] ;
00e0  IMAD.WIDE R4, R7, 0x4, R4 ;
00f0  LDG.E R7, desc[UR4][R4.64] ;
0100  FFMA R7, R2, UR6, R7 ;
0110  STG.E desc[UR4][R4.64], R7 ;
0120  EXIT ;
```

结构和 PTX 一一对应，但已经是具体的硬件了：寄存器有了编号（`R0`、`R7`），kernel 的参数放在常量存储 `c[0x0][...]` 里由 `LDC` 读取，`S2R` 读取线程编号这样的特殊寄存器，`LDG`、`STG` 读写显存，`FFMA` 是浮点乘加，越界的线程直接 `EXIT`。另外还有一组 `UR` 开头的寄存器，存放对整个 warp 都相同的值，比如 `blockIdx.x` 和参数 `a`，这样每个 warp 只需要算一次。

PTX 到 SASS 这一步由 `ptxas` 完成，寄存器分配、指令调度这些和硬件密切相关的优化都在这里做。所以分析性能时，要看的是 SASS。第 1 章就是数 SASS 里的 `FMUL` 和 `FFMA` 算出 heavy 跑到了峰值的几成。

## 4.3 fatbin 里装了什么，能在哪些 GPU 上跑

<span class="cu-map-at" data-on="fatbin exe exe>fatbin-exe fatbin-exe fatbin-exe>driver driver driver>has-sass has-sass has-sass>direct direct has-sass>jit jit has-sass>noimage noimage"></span>`-arch` 和 `-gencode` 两个选项决定 fatbin 里装什么。`cuobjdump --list-elf --list-ptx` 可以列出来，比如 `-arch=sm_120`：

```text
ELF file    1: tiny.1.sm_120.cubin
ELF file    2: tiny.2.sm_120.cubin
PTX file    1: tiny.1.sm_120.ptx
```

一份 sm_120 的 SASS（两个 ELF 文件，一个是 kernel 本身，一个是 `nvlink` 生成的辅助代码），外加一份 PTX。用几种不同的选项编译 tiny.cu，看看里面装了什么，在这块 sm_120 的 GPU 上能不能跑：

| 编译选项 | fatbin 里的内容 | 在 sm_120 上运行 |
|---|---|---|
| `-arch=native` | sm_120 的 SASS | 成功 |
| `-arch=sm_120` | sm_120 的 SASS + PTX | 成功 |
| `-arch=sm_90` | sm_90 的 SASS + compute_90 的 PTX | 成功（JIT 编译 PTX） |
| `-gencode arch=compute_90,code=sm_90` | sm_90 的 SASS | `cudaErrorNoKernelImageForDevice` |
| `-gencode arch=compute_86,code=sm_86` | sm_86 的 SASS | `cudaErrorNoKernelImageForDevice` |
| `-gencode arch=compute_121,code=sm_121` | sm_121 的 SASS | `cudaErrorNoKernelImageForDevice` |
| `-gencode arch=compute_80,code=compute_80` | compute_80 的 PTX | 成功（JIT 编译 PTX） |
| `-arch=all` | sm_75 到 sm_121 每一种的 SASS + sm_120 的 PTX | 成功 |

报错的那几行，错误信息都是 “no kernel image is available for execution on the device”。从这张表能总结出 CUDA 的兼容规则：

- **SASS 只能在同一个主版本、次版本号不低于它的 GPU 上运行。** sm_120 是计算能力 12.0，sm_86 和 sm_90 的 SASS 主版本不同，不能用；sm_121 次版本更高，也不能用。反过来，sm_80 的 SASS 可以在 8.6、8.9 的 GPU 上运行。
- **PTX 可以在计算能力不低于它的任何 GPU 上运行**，驱动会在运行时把它编译成那块 GPU 的 SASS，这叫 JIT（just-in-time）编译。
- `-arch=sm_XY` 是个简写，等于 SASS sm_XY 加 PTX compute_XY。`-arch=native` 只为本机的 GPU 生成 SASS，**不带 PTX**，这样编出来的程序换到更新一代的 GPU 上就跑不了。

计算能力还可以带两种后缀。`sm_90a`、`sm_120a` 这种 `a` 后缀表示“只属于这一个架构的特性”，比如 Hopper 上的某些矩阵指令，这样编出的代码只能在计算能力完全相同的 GPU 上运行。`f` 后缀表示“这一家族共有的特性”，可以在同一家族里计算能力不低于它的 GPU 上运行。本机只能验证它们在 12.0 上自己能跑，到别的 GPU 上的行为这里没法实测。不使用这些特定架构的指令时，用不带后缀的版本就行。

发布程序时的常见做法是：为打算支持的每种架构各生成一份 SASS，再加上最新架构的 PTX。前者保证已知的 GPU 不用 JIT，后者保证将来的新 GPU 也能跑：

```bash
nvcc -gencode arch=compute_80,code=sm_80 \
     -gencode arch=compute_90,code=sm_90 \
     -gencode arch=compute_120,code=sm_120 \
     -gencode arch=compute_120,code=compute_120 \
     app.cu -o app
```

只带 PTX 的版本，第一轮启动 64 个 kernel 花了 260 ms，比 SASS 版本多了两百多倍，多出来的就是驱动现场编译这 64 个 kernel 的时间。第二轮就和 SASS 版本一样了，因为编译结果已经在内存里。

## 4.5 kernel 是什么时候装进 GPU 的

<span class="cu-map-at" data-on="direct>lazy jit>lazy lazy lazy>gpu gpu"></span>即使不需要 JIT，SASS 版本的第一轮也比第二轮慢：1.0 ms 对 0.2 ms。第 2 章遇到过同样的现象：第一次启动 kernel 慢了 0.1 ms。

原因是 CUDA 默认采用 lazy loading：程序初始化时并不把所有 kernel 的机器码都装到 GPU 上，而是等某个 kernel 第一次被启动时才装载它。64 个 kernel 各装载一次，平均十几微秒。设置 `CUDA_MODULE_LOADING=EAGER` 可以改回在初始化时全部装载，上面最后一行就是这样做的，结果 JIT 编译的时间整个挪到了初始化阶段，初始化变成了 431 ms，第一轮则和第二轮一样快。

lazy loading 让程序启动更快，没用到的 kernel 也不占显存，一般来说是好事。代价是每个 kernel 第一次启动时会有一次额外的延迟。做性能测量时要先把要测的 kernel 跑一遍预热；对延迟很敏感的服务，也可以在启动阶段把关键 kernel 预先跑一遍。

## 4.7 回头看

<span class="cu-map-at" data-on="tiny.cu gcc-pre cudafe++ cicc ptx ptxas sass fatbinary fatbin host-code gcc-host nvlink g++ exe tiny.cu>gcc-pre gcc-pre>cudafe++ cudafe++>cicc cudafe++>host-code cicc>ptx ptx>ptxas ptxas>sass sass>fatbinary ptx>fatbinary fatbinary>fatbin host-code>gcc-host fatbin>gcc-host gcc-host>nvlink fatbin>nvlink nvlink>g++ g++>exe fatbin-exe driver has-sass direct jit jit-cache noimage lazy gpu exe>fatbin-exe fatbin-exe>driver driver>has-sass has-sass>direct has-sass>jit has-sass>noimage jit>jit-cache direct>lazy jit>lazy lazy>gpu"></span>nvcc 把 kernel 编译成两种形式：PTX 是可移植的虚拟指令集，SASS 是某一代 GPU 的机器码，两者都打包在可执行文件的 fatbin 里。程序运行时，驱动优先找匹配当前 GPU 的 SASS，找不到就 JIT 编译 PTX，两样都没有就报 “no kernel image”。JIT 的结果会缓存起来，kernel 默认在第一次使用时才装载。这些机制解释了第一次运行为什么慢，也决定了发布程序时该带哪些架构。

## 4.8 练习

1. 用 `-gencode arch=compute_80,code=compute_80 -gencode arch=compute_120,code=sm_120` 编译 jit.cu，运行之前先预测第一轮要多久，再用 `CUDA_CACHE_DISABLE=1` 运行验证。
2. 用 `-keep` 编译第 1 章的 loops.cu，打开 `.ptx` 文件找到 `heavy_gpu`，看看 PTX 里的循环是否已经展开；再用 `cuobjdump -sass` 对照 SASS。
3. 看看你的机器上 `~/.nv/ComputeCache` 有多大。把 `CUDA_CACHE_MAXSIZE` 设成一个很小的值（比如 `1024`），再运行两次 `./jit_ptx`，第二次还快吗？
4. 用 `-arch=sm_120 -Xptxas -v` 编译 tiny.cu，ptxas 会打印每个 kernel 用了多少寄存器。记下这个数，第 10 章会用到它。
