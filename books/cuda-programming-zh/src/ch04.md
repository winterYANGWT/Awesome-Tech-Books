# 第 4 章 nvcc 做了什么

一个 `.cu` 文件里同时有两种代码：`main` 这样的主机代码在 CPU 上跑，kernel 在 GPU 上跑。两种处理器的指令集完全不同，nvcc 要把它们分开编译，再装进同一个可执行文件。平时 `nvcc foo.cu -o foo` 一条命令就完事了，但有几件事迟早会碰到：程序拷到另一台机器上报 “no kernel image is available”；同一个程序第一次运行比后来慢好几百毫秒；调试版本慢得离谱。这些都和编译产物有关。本章用一个最小的程序 [tiny.cu](code/ch04/tiny.cu) 把 nvcc 的工作过程拆开看：


## 4.1 一条命令，两条编译链

`--dryrun` 让 nvcc 只打印它要执行的命令而不真正执行。把每条命令的程序名挑出来，一共 13 步（图 4.1）：

```text
$ nvcc -arch=sm_120 tiny.cu -o tiny --dryrun 2>&1 | awk '/^#\$ [a-z"]/ {print $2}' | sed 's|.*/||; s|"||g'
```

nvcc 自己不编译任何东西，它是个调度者。13 步分成三路：

- **主机这一路**（第 1、2、8 步）：`gcc` 先按主机的视角预处理，`cudafe++` 从中拆出主机代码，把 `saxpy<<<...>>>(...)` 换成对 CUDA 运行时库的普通函数调用，最后由 `gcc` 编译成目标文件。
- **GPU 这一路**（第 3–6 步）：`gcc` 定义 `__CUDA_ARCH__` 把源码再预处理一遍；`cicc` 是 NVIDIA 基于 LLVM 的 GPU 编译器，把 kernel 编译成 **PTX**；`ptxas` 把 PTX 汇编成 sm_120 这种具体架构的机器码，叫 **SASS**，装在 `.cubin` 文件里；`fatbinary` 把 cubin 和 PTX 打成一个包，叫 **fatbin**，写成一个 C 数组，第 8 步编译主机代码时一起编进去。
- **链接**（第 9–13 步）：`nvlink` 做 GPU 代码的链接，结果同样打包、编进一个小目标文件，最后 `g++` 把所有目标文件和 CUDA 运行时库链接成可执行文件。

真正编译 kernel 的只有 `cicc` 和 `ptxas` 两步，`gcc` 却出现了四次：两次预处理，两次编译。同一个源文件预处理两次，是因为 `__CUDA_ARCH__` 只在编译 GPU 代码时才有定义，代码可以用它让主机和 GPU 走不同的分支。

加上 `-keep` 选项，这些中间文件都会留在当前目录里，其中 `tiny.ptx` 和 `tiny.sm_120.cubin` 就是下面要看的两样东西。

## 4.2 PTX 和 SASS

kernel 从源码到在 GPU 上执行，要经过两次翻译：`cicc` 把 C++ 编译成 **PTX**，`ptxas` 再把 PTX 汇编成 **SASS**。图 4.2 用两个标签分别看这两次翻译：左边是翻译前，右边是翻译后，连线表示对应关系，每次翻译的分析在图下，随标签切换。对应关系是工具给的：编译时加上 `-lineinfo`，PTX 里会多出 `.loc` 行，标出每段指令来自源码第几行；`nvdisasm -gp` 能标出每条 SASS 来自 PTX 的哪一行。`-lineinfo` 不改变生成的代码，指令和不加时完全一样。

<div class="cu-xref-notes" data-for="cu-ptx">

PTX 是一种“虚拟”指令集：寄存器（`%r1`、`%rd3`……）要多少有多少，指令也不对应任何一代具体的硬件。按源码逐行看：

1. **第 17 行，函数头。** `_Z5saxpyifPKfPf` 是 `saxpy(int, float, const float*, float*)` 经过 C++ 名字修饰后的名字，四个 `.param` 就是四个参数，`.reg` 声明要用的虚拟寄存器。函数体一开始，四条 `ld.param` 把参数读进寄存器。
2. **第 18 行，算 `i`。** 内置变量 `blockIdx.x`、`blockDim.x`、`threadIdx.x` 在 PTX 里是特殊寄存器 `%ctaid.x`、`%ntid.x`、`%tid.x`，`mad.lo.s32` 一条指令算出 `blockIdx.x * blockDim.x + threadIdx.x`。
3. **第 19 行，判断和计算。** `setp.ge.s32` 比较 `i >= n`，成立时 `@%p1 bra` 跳到结尾，这就是 `if (i < n)`。`mul.wide.s32` 算出字节偏移 `i * 4`，`add` 得到 `x[i]`、`y[i]` 的地址；两次 `ld.global` 读数，`fma.rn.f32` 算 `a * x[i] + y[i]`（第 3 章说的乘加合并），`st.global` 写回。
4. **第 20 行，结束。** `ret` 返回。

还有两条 `cvta.to.global`，把参数里的指针转换成显存地址。编译器把它们记在了第 18 行，所以点第 18 行时它们也会亮：行号信息只是编译器尽量给出的对应，不总是精确。

整体上，PTX 和源码还是一句对几句的关系，看得出程序原来的样子。NVIDIA 保证 PTX 向前兼容：为 compute_80 生成的 PTX，以后各代 GPU 都能把它编译成自己的机器码（4.3 节）。

</div>
<div class="cu-xref-notes" data-for="ptx-sass">

真正在 GPU 上执行的是 SASS，这里是 sm_120 这一代的机器码。PTX 到 SASS 这一步由 `ptxas` 完成，寄存器分配、指令调度这些和硬件密切相关的优化都在这里做。分 6 步看：

1. **函数入口。** PTX 的四条 `ld.param` 在 SASS 里没有对应的指令：参数留在常量存储里，`n`、`a`、`x`、`y` 依次放在 `c[0x0][0x380]`、`0x384`、`0x388`、`0x390`，用到时才读。入口处反而多了两条 PTX 里没有的指令：`LDC R1, c[0x0][0x37c]` 给 R1 赋初值（按约定 R1 是栈指针，这个 kernel 用不上），`LDCU.64 UR4, c[0x0][0x358]` 读出的 `UR4`，后面在 `desc[UR4]` 里用作访存的描述符。
2. **算 `i`。** `%tid.x`、`%ctaid.x` 变成 `S2R`、`S2UR`，从特殊寄存器读出；`blockDim.x` 则是 `LDC` 从常量存储 `c[0x0][0x360]` 读的。`mad.lo` 变成 `IMAD`。这一步的连线是交叉的：`ptxas` 调整了指令顺序，读 `%tid.x` 的指令排到了最前面。
3. **`if (i < n)`。** `n` 到比较之前才读进 `UR5`。跳到结尾的 `@%p1 bra` 变成了带条件的 `@P0 EXIT`：越界的线程直接结束。
4. **算地址。** 两条 `cvta.to.global` 在 SASS 里没有对应；`mul.wide` 和 `add` 合成一条 `IMAD.WIDE`。
5. **读、算、写。** 两条 `LDG` 读 `x[i]`、`y[i]`，`a` 读进 `UR6`，`FFMA` 乘加，`STG` 写回。
6. **结束。** `ret` 变成 `EXIT`。

寄存器也从 PTX 里要多少有多少的 `%r`、`%rd`，变成了编号固定的 `R0`、`R7`。`UR` 开头的是 uniform 寄存器，存放对整个 warp 都相同的值，比如 `blockIdx.x` 和参数 `a`，每个 warp 只算一次。所以分析性能时，要看的是 SASS：第 1 章就是数 SASS 里的 `FMUL` 和 `FFMA`，算出 heavy 跑到了峰值的几成。

</div>

## 4.3 fatbin 里装了什么，能在哪些 GPU 上跑

`-arch` 和 `-gencode` 两个选项决定 fatbin 里装什么。先分清两个名字：

- **`compute_XY` 是虚拟架构**：一级 PTX 功能集，意思是“按计算能力 X.Y 的功能写出的 PTX”。它不是哪一块具体的 GPU。
- **`sm_XY` 是真实架构**：计算能力 X.Y 那一代 GPU 的机器码 SASS。这块 RTX 5060 的计算能力是 12.0，它直接认的是 sm_120。

`-gencode arch=…,code=…` 的两个参数，分别管图 4.1 里的第 4 步和第 5 步：

- `arch=compute_XY` 决定 `cicc` 按哪一级虚拟架构生成 PTX，也就决定了代码能用哪些功能。
- `code=` 决定最后往 fatbin 里装什么。写 `sm_XY`，就让 `ptxas` 把 PTX 汇编成那一代的 SASS 装进去；写 `compute_XY`，就把 PTX 本身装进去，留给驱动在运行时编译；两样都要就写 `code=[sm_XY,compute_XY]`。`code` 里的架构不能低于 `arch`：按 compute_100 的功能写出的 PTX，没法汇编成 sm_90 的机器码。

`-arch=sm_XY` 是个简写，等于 `-gencode arch=compute_XY,code=[sm_XY,compute_XY]`。

程序启动 kernel 时，驱动在 fatbin 里按这个顺序找：

1. 有没有这块 GPU 能直接用的 SASS：主版本相同、次版本不高于它。在 12.0 上，sm_120 的 SASS 能用；sm_121（次版本更高）、sm_90 和 sm_86（主版本不同）都不行。
2. 没有的话，找计算能力不高于它的 PTX，JIT（just-in-time）编译成 sm_120 的 SASS 再运行。4.4 节会看到这一步要花时间。
3. 两样都没有，报 `cudaErrorNoKernelImageForDevice`：“no kernel image is available for execution on the device”。

每种 SASS 在 `cuobjdump` 里是两个 ELF 文件，一个是 kernel 本身，一个是 `nvlink` 生成的辅助代码。

这就解释了两个看上去矛盾的结果。`code=sm_90` 装进去的只有 sm_90 的 SASS，主版本是 9，这块 12.0 的 GPU 用不了，又没有 PTX 可以退而求其次，于是报错。`code=compute_80` 装进去的是 PTX，计算能力 8.0 不高于 12.0，驱动把它 JIT 编译成 sm_120 的 SASS，就能运行。PTX 可以在计算能力不低于它的任何 GPU 上运行；SASS 只能在同一个主版本里往后用。

`-arch=native` 只为本机的 GPU 生成 SASS，**不带 PTX**，这样编出来的程序换到更新一代的 GPU 上就跑不了。

计算能力还可以带两种后缀。`sm_90a`、`sm_120a` 这种 `a` 后缀表示“只属于这一个架构的特性”，比如 Hopper 上的某些矩阵指令，这样编出的代码只能在计算能力完全相同的 GPU 上运行。`f` 后缀表示“这一家族共有的特性”，可以在同一家族里计算能力不低于它的 GPU 上运行。本机只能验证它们在 12.0 上自己能跑，到别的 GPU 上的行为这里没法实测。不使用这些特定架构的指令时，用不带后缀的版本就行。

发布程序时的常见做法是：为打算支持的每种架构各生成一份 SASS，再加上最新架构的 PTX。前者保证已知的 GPU 不用 JIT，后者保证将来的新 GPU 也能跑：

```bash
nvcc -gencode arch=compute_80,code=sm_80 \
     -gencode arch=compute_90,code=sm_90 \
     -gencode arch=compute_120,code=sm_120 \
     -gencode arch=compute_120,code=compute_120 \
     app.cu -o app
```

## 4.4 第一次运行为什么慢

JIT 编译要花时间。[jit.cu](code/ch04/jit.cu) 用一个模板生成 64 个 kernel，每个都有几百条指令。程序先初始化 context，再把 64 个 kernel 各启动一遍，然后再来一轮，三段分别计时。把它编译成只带 SASS 和只带 PTX 的两个版本：

```bash
nvcc -O2 -arch=native jit.cu -o jit_sass
nvcc -O2 -gencode arch=compute_80,code=compute_80 jit.cu -o jit_ptx
```

SASS 版本跑一次。PTX 版本跑五次：用 `CUDA_CACHE_DISABLE=1` 关掉 JIT 缓存跑两次，打开缓存跑两次，最后一次再加上 `CUDA_MODULE_LOADING=EAGER`（4.5 节讲）。结果见图 4.4，每种情况的分析在图下，随选择切换。

## 4.5 kernel 是什么时候装进 GPU 的

即使不需要 JIT，图 4.4 里 SASS 版本的第一轮也比第二轮慢：1.0 ms 对 0.2 ms。第 2 章遇到过同样的现象：第一次启动 kernel 慢了 0.1 ms。

原因是 CUDA 默认采用 lazy loading：程序初始化时并不把所有 kernel 的机器码都装到 GPU 上，而是等某个 kernel 第一次被启动时才装载它，只带 PTX 时 JIT 编译也在这时进行。64 个 kernel 各装载一次，平均十几微秒。设置 `CUDA_MODULE_LOADING=EAGER` 可以改回在初始化时全部装载、全部编译，图 4.4 的最后一行就是这样跑的：初始化变成了 431.0 ms，第一轮则和第二轮一样快。

lazy loading 让程序启动更快，没用到的 kernel 也不占显存，一般来说是好事。代价是每个 kernel 第一次启动时会有一次额外的延迟。做性能测量时要先把要测的 kernel 跑一遍预热；对延迟很敏感的服务，也可以在启动阶段把关键 kernel 预先跑一遍。

GPU 时间不到 1 ms，CPU 时间要几百毫秒，差了三个数量级。两组都显示时，图 4.5 用对数刻度，否则 GPU 的柱子短得看不见；在对数刻度上，柱子长出多少代表慢了几倍：`-G` 那一组，GPU 的柱子比 `-O2` 长出一大截，CPU 的只长出一小截。点图例可以只看其中一组，这时换回普通刻度。（`-G` 那次没有加 `-O2`，所以主机代码也没优化，CPU 时间也变长了。）

kernel 慢了 12 倍。和 CPU 结果的差异也消失了：没有优化，乘加就不会合并成 FMA。访存为主的 kernel 受的影响小一些，第 1 章的 threads.cu 用 `-G` 编译，带宽从 336 GB/s 降到了 309 GB/s；计算为主的 kernel 受影响最大。所以 `-G` 只用于调试逻辑，**永远不要拿 `-G` 编译的程序测性能**。

`-lineinfo` 则完全不同：它只在 SASS 旁边记下每条指令对应源码的哪一行，不改变生成的代码，速度和普通的 `-O2` 一样。第 5 章的 compute-sanitizer 和第 12 章的 Nsight Compute 都靠它把问题定位到源码行，平时编译时加上它没有坏处。

## 4.7 回头看

nvcc 把 kernel 编译成两种形式：PTX 是可移植的虚拟指令集，SASS 是某一代 GPU 的机器码，两者都打包在可执行文件的 fatbin 里。程序运行时，驱动优先找匹配当前 GPU 的 SASS，找不到就 JIT 编译 PTX，两样都没有就报 “no kernel image”。JIT 的结果会缓存起来，kernel 默认在第一次使用时才装载。这些机制解释了第一次运行为什么慢，也决定了发布程序时该带哪些架构。
