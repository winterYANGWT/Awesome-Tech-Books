# 第 18 章 流序内存分配：cudaMallocAsync 与内存池

很多程序每一步都需要一些临时缓冲区：排序要一块额外的空间，归约要存放各个 block 的部分结果，库函数要一块工作区。最直接的写法是用的时候 `cudaMalloc`，用完 `cudaFree`。这一章先看这样做要付出什么代价，再介绍 CUDA 的流序内存分配器：把分配和释放也变成 stream 里的操作。

## 18.1 cudaMalloc 和 cudaFree 的代价

[alloc.cu](code/ch18/alloc.cu) 模拟每一轮都要一块 64 MB 临时缓冲区的情形，kernel 把它写一遍再读一遍，一共 200 轮：

```cpp
{{#include code/ch18/alloc.cu:sync_alloc}}
```

```text
  188.8 us  参照：只分配一次
  404.7 us  cudaMalloc + cudaFree
```

只分配一次时每轮 189 微秒，都是 kernel 的时间；每轮分配、释放一次，就变成了 405 微秒，多出来的 200 多微秒全花在内存管理上。驱动每次都要向系统申请显存、建立地址映射，释放时再拆掉。

还有一个更隐蔽的代价。[order.cu](code/ch18/order.cu) 在 GPU 正忙着跑一个十几毫秒的 kernel 时，释放一块和这个 kernel 毫无关系的内存：

```cpp
{{#include code/ch18/order.cu:blocking}}
```

```text
GPU 忙时，cudaFree 让 host 等了  14.51 ms，cudaFreeAsync 只用了  0.003 ms
```

`cudaFree` 让 host 一直等到 GPU 上的那个 kernel 跑完才返回。驱动不知道 GPU 上正在执行的工作会不会用到这块内存，为了安全，只能等所有工作都做完再释放。这相当于在程序里插了一次 `cudaDeviceSynchronize`，第 13 章辛苦安排的拷贝和计算重叠，可能就被一个不起眼的 `cudaFree` 打断了。

## 18.2 把分配和释放排进 stream

`cudaMallocAsync` 和 `cudaFreeAsync` 多了一个 stream 参数，分配和释放都成了这条 stream 里的操作：

```cpp
{{#include code/ch18/alloc.cu:async_alloc}}
```

```text
  190.0 us  cudaMallocAsync + cudaFreeAsync
```

和只分配一次一样快，内存管理的开销几乎消失了。上面 order.cu 的那一行也说明，`cudaFreeAsync` 不会等任何东西，3 微秒就返回了。

它的语义是按 stream 的顺序来理解的：`cudaMallocAsync` 返回的指针，只能被这条 stream 里排在它后面的工作使用；`cudaFreeAsync` 排在 stream 里，等前面的工作都做完，这块内存才真正被释放。host 调用这两个函数时都不等待，它们只是往队列里放了一个“分配”和一个“释放”。

快的原因是内存池：每个 GPU 有一个默认的内存池，`cudaFreeAsync` 释放的内存并不还给系统，而是放回池子里，下一次 `cudaMallocAsync` 直接从池子里拿。这个例子里，第二轮开始就一直在复用第一轮那 64 MB。

## 18.3 内存池什么时候把内存还回去

内存池也不会无限地攒着内存。它有一个释放阈值：每当发生同步（比如 `cudaStreamSynchronize`），池子里空闲的内存超过阈值的部分就会还给系统。默认阈值是 0，也就是每次同步都把空闲内存全部还回去。如果程序每一轮都要同步一次（比如要把结果拷回主机看看），就会出现这样的情况：

```text
  403.9 us  同上，每轮同步，阈值为 0（默认）
  194.6 us  同上，每轮同步，阈值为无限大
```

每轮同步一次，内存每轮都被还回系统，下一轮又得重新申请，又回到了和 `cudaMalloc` 差不多的速度。把阈值调大，内存池就会把内存留在手里：

```cpp
{{#include code/ch18/alloc.cu:threshold}}
```

阈值的设置是一个取舍：留住的内存越多，分配越快，但别的程序（或者本程序里用 `cudaMalloc` 的部分）能用的显存就越少。一般设为程序稳定运行时需要的临时内存总量就够了。内存池的使用情况可以随时查询，不需要的时候也可以手动把空闲内存还回去：

```cpp
{{#include code/ch18/alloc.cu:stats}}
```

```text
内存池：当前保留 64 MB，正在使用 0 MB，最多时保留 64 MB
cudaMemPoolTrimTo(pool, 0) 之后保留 0 MB
```

除了默认的内存池，还可以用 `cudaMemPoolCreate` 创建自己的池，配合 `cudaMallocFromPoolAsync` 使用。比如为不同的模块分别设置阈值，或者创建可以导出给别的进程使用的池（第 32 章）。

## 18.4 刚释放的内存什么时候能被复用

“按 stream 的顺序”这个语义，决定了内存池什么时候可以把刚释放的内存交给下一次分配。order.cu 的后半部分在 `s1` 上分配一块内存，交给一个还在运行的 kernel，然后释放；接着分别在几种情况下再分配同样大小的内存，看拿到的是不是同一块：

```cpp
{{#include code/ch18/order.cu:reuse}}
```

```text
同一条 stream 上再分配：       复用了刚释放的那块
另一条 stream，没有依赖：      拿到另一块
另一条 stream，等待释放的 event：复用了刚释放的那块
```

- **同一条 stream**：即使前面那个 kernel 还没跑完，也可以复用。新分配的内存只会被 `s1` 里更后面的工作使用，它们一定在 kernel 结束、释放完成之后才执行，不会冲突。
- **另一条 stream、没有依赖**：不能复用。`s2` 上的工作可能和 `s1` 上还没跑完的 kernel 同时执行，两者用同一块内存就是数据竞争。
- **另一条 stream、等待了释放之后记录的 event**：可以复用。event 建立了顺序（第 14 章），`s2` 之后的工作一定在释放之后。

内存池的这几条复用策略可以用 `cudaMemPoolSetAttribute` 调整，默认开启的 `cudaMemPoolReuseFollowEventDependencies` 就是第三种情况；`cudaMemPoolReuseAllowOpportunistic` 允许在分配时如果释放已经实际完成就直接复用，结果取决于时机。

反过来，这也划定了使用流序内存时的规则：指针只在“分配之后、释放之前”这段 stream 顺序里有效。在另一条 stream 上使用它，必须先用 event 建立依赖，否则就和第 14 章的生产者消费者一样，是数据竞争。

## 18.5 graph 里的内存节点

第 17 章提到，捕获期间可以调用 `cudaMallocAsync` 和 `cudaFreeAsync`。[graphmem.cu](code/ch18/graphmem.cu) 把临时缓冲区的分配和释放也录进了 graph：

```cpp
{{#include code/ch18/graphmem.cu:capture}}
```

```text
带内存节点的 graph 有 3 个节点
实例化之后，为 graph 保留的显存 0 MB
第一次启动之后，为 graph 保留的显存 64 MB

  193.7 us  graph 用预先分配好的缓冲区
  193.7 us  graph 里分配和释放临时缓冲区

销毁 graph 并 trim 之后，为 graph 保留的显存 0 MB
```

graph 里多了一个分配节点和一个释放节点。显存在第一次启动时才真正保留下来，之后每次启动都复用这 64 MB，和使用预先分配好的缓冲区一样快。graph 销毁以后，用 `cudaDeviceGraphMemTrim` 把这部分显存还给系统。这样写的好处是 graph 自己管理自己的临时内存，调用者不必为它准备缓冲区；多个不会同时执行的 graph 之间，驱动还可以让它们共用同一块物理显存。

## 18.6 回头看

`cudaMalloc` 和 `cudaFree` 每次都要和系统打交道，而且 `cudaFree` 会等 GPU 上所有的工作做完，在循环里使用既慢又会打断异步执行。`cudaMallocAsync` 和 `cudaFreeAsync` 把分配和释放变成 stream 里的操作，内存来自内存池，反复分配同样大小的内存几乎没有开销。内存池默认在每次同步时把空闲内存还给系统，经常同步的程序要调大释放阈值。流序分配的内存只在 stream 顺序上“分配之后、释放之前”有效，跨 stream 使用要用 event 建立依赖，内存池也正是按照这些依赖决定能否复用。捕获进 graph 的分配和释放会变成内存节点，由 graph 自己管理。

## 18.7 练习

2. 把阈值设成 32 MB（小于每轮需要的 64 MB），每轮同步的版本会是什么结果？

4. 用 `cudaMemPoolCreate` 创建一个自己的内存池，用 `cudaMallocFromPoolAsync` 重写 alloc.cu 里的异步版本，并用 `cudaMemPoolAttrMaxPoolSize` 把它的上限设成 32 MB，分配 64 MB 时会发生什么？
