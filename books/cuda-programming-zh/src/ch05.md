# 第 5 章 出错了怎么办

CPU 程序数组越界，运气不好会立刻段错误，调试器能指出是哪一行。GPU 程序出了同样的错，多半什么也不发生：程序正常结束，只是结果不对，或者在很久以后、一个毫不相干的地方报出一个错误。这一章先看清 GPU 程序出错时到底会发生什么，再介绍把错误定位到源码行的工具。

[bugs.cu](code/ch05/bugs.cu) 里有六个故意写错的 kernel，用命令行参数选择运行哪一个。每次运行以后，程序都把 kernel 启动和同步的结果打印出来，再做一次和 kernel 毫无关系的 `cudaMalloc`，看看它会不会受影响：

```cpp
{{#include code/ch05/bugs.cu:after}}
```

编译时加上 `-lineinfo`（第 4 章讲过，它不影响性能），后面的工具才能报出源码行号：

```bash
nvcc -O2 -lineinfo -arch=native bugs.cu -o bugs
```

## 5.1 大多数错误不会自己暴露

先不用任何工具，直接运行六个场景：

```text
$ ./bugs edge
启动：cudaSuccess，同步：cudaSuccess
之后的 cudaMalloc：cudaSuccess
$ ./bugs near
启动：cudaSuccess，同步：cudaSuccess
之后的 cudaMalloc：cudaSuccess
$ ./bugs far
启动：cudaSuccess，同步：cudaErrorIllegalAddress
之后的 cudaMalloc：cudaErrorIllegalAddress
$ ./bugs race
479 个元素反转错了
启动：cudaSuccess，同步：cudaSuccess
之后的 cudaMalloc：cudaSuccess
$ ./bugs uninit
启动：cudaSuccess，同步：cudaSuccess
之后的 cudaMalloc：cudaSuccess
$ ./bugs assert
bugs.cu:61: void take_sqrt(float *, int): block: [1,0,0], thread: [244,0,0] Assertion `p[i] >= 0.0f` failed.
启动：cudaSuccess，同步：cudaErrorAssert
之后的 cudaMalloc：cudaErrorAssert
```

六个 bug，只有两个被 CUDA 报告出来。逐个看。

**edge** 就是第 2 章练习 4 的情形：kernel 漏了边界检查，数组有 1000 个元素，开了 4 个 256 线程的 block，最后 24 个线程读写到了数组外面：

```cpp
{{#include code/ch05/bugs.cu:edge}}
```

越界了几十个字节，程序却一切正常。GPU 的内存保护以页为单位，`cudaMalloc` 又是从更大的内存块里切出一小块给你，紧挨着数组后面的地址通常仍然属于某个有效的页，访问它不会触发任何保护。

**near** 和 **far** 用的是同一个下标算错的 kernel，只是 `stride` 不同：

```cpp
{{#include code/ch05/bugs.cu:far}}
```

near 的 `stride` 是 1024，最远写到数组后面 4 MB 的地方，同样没有报错。这比 edge 更危险：那片地址恰好是映射着的，这次运行很可能已经悄悄写坏了别的数据。同样的写法放到一个只分配了这一块内存的小程序里，就会报非法地址，结果取决于附近有没有别的分配。far 的 `stride` 是一百万，最远写到 4 GB 以外，那里没有任何映射，GPU 的内存管理单元（MMU）拦下了这次访问，报出 `cudaErrorIllegalAddress`。

**race** 让每个 block 用 shared memory 把自己那一段数组反转：

```cpp
{{#include code/ch05/bugs.cu:race}}
```

问题在于写 `tile` 和读 `tile` 之间少了 `__syncthreads()`：一个线程去读 `tile[255 - t]` 的时候，负责写这个位置的线程可能还没写。shared memory 和 `__syncthreads()` 是第 9 章的内容，这里只需要知道这是一个经典的数据竞争。结果错了 479 个元素，但从硬件的角度看，每一次读写都是合法的，没有什么可报告的。

**uninit** 读了一块刚分配、从没写过的显存：

```cpp
{{#include code/ch05/bugs.cu:uninit}}
```

`cudaMalloc` 不会清零，读出来的是什么都有可能。这同样是合法的访问。

**assert** 是唯一一个“设计好的”报错。kernel 里可以像主机代码一样用 `assert`：

```cpp
{{#include code/ch05/bugs.cu:assert}}
```

程序把 `a[500]` 设成了 −1，第 1 个 block 的第 244 号线程（1 × 256 + 244 = 500）检查失败，打印出文件、行号、函数和线程坐标，kernel 被终止，同步时返回 `cudaErrorAssert`。用 `-DNDEBUG` 编译可以去掉所有 `assert`，和主机代码一样。

## 5.2 错误报告得晚，而且一错全错

far 和 assert 两个场景有一个共同点：kernel 启动返回的是 `cudaSuccess`，错误要到同步时才出现。原因在第 2 章说过：kernel 启动是异步的，启动调用返回时 kernel 可能还没开始执行，执行中出的错，host 要到下一个同步点才知道。真实的程序里，启动和同步之间可能隔着好几个 kernel 和拷贝，第一个报告错误的往往是后面某个完全无辜的 `cudaMemcpy`。

更麻烦的是最后一行：一次和 kernel 毫无关系的 `cudaMalloc` 也失败了，返回的还是同一个错误。非法地址、assert 失败这类错误会让整个 context 进入不可恢复的状态，此后这个进程里的所有 CUDA 调用都返回这个错误。唯一的办法是结束进程重新开始。所以看到一个 CUDA 调用失败，先别急着怀疑它本身，要往前找最近的那个 kernel。

调试时有个简单的办法缩小范围：设置环境变量 `CUDA_LAUNCH_BLOCKING=1`，每次 kernel 启动都会等到 kernel 执行完才返回，执行中的错误在启动之后马上就能取到：

```text
$ CUDA_LAUNCH_BLOCKING=1 ./bugs far
启动：cudaErrorIllegalAddress，同步：cudaErrorIllegalAddress
之后的 cudaMalloc：cudaErrorIllegalAddress
```

这样第一个报错的位置就是出问题的那个 kernel。代价是所有异步执行都变成了同步，这个设置只用于调试。

## 5.3 compute-sanitizer：找出越界的那一行

edge 和 near 这样不报错的越界，要靠工具来找。CUDA 自带的 compute-sanitizer 会在每次访存时检查地址是否落在某个有效的分配里，用法是把它放在程序前面：

```text
$ compute-sanitizer --print-limit 1 ./bugs edge
========= COMPUTE-SANITIZER
========= Invalid __global__ read of size 4 bytes
=========     at add_no_check(const float *, const float *, float *)+0xa0 in bugs.cu:24
=========     by thread (232,0,0) in block (3,0,0)
=========     Access to 0x1000ea00fa0 is out of bounds
=========     and is 1 bytes after the nearest allocation at 0x1000ea00000 of size 4000 bytes
=========     Saved host backtrace up to driver entry point at kernel launch time
=========         Host Frame: main [0x8e8d] in bugs
========= 
启动：cudaSuccess，同步：cudaErrorLaunchFailure
之后的 cudaMalloc：cudaErrorLaunchFailure
========= ERROR SUMMARY: 27 errors
========= ERROR SUMMARY: 26 errors were not printed. Use --print-limit option to adjust the number of printed errors
```

报告里有需要的一切：是读还是写、几个字节、哪个 kernel 的哪一行（bugs.cu 第 24 行）、哪个线程（第 3 个 block 的 232 号线程，下标正好是 1000）、越界到了离哪个分配多远的地方。`--print-limit 1` 只打印第一处错误，一共发现 27 处。near 的报告也一样清楚：

```text
$ compute-sanitizer --print-limit 1 ./bugs near
========= COMPUTE-SANITIZER
========= Invalid __global__ read of size 4 bytes
=========     at scale_wrong(float *, int, int)+0xd0 in bugs.cu:32
=========     by thread (32,0,0) in block (0,0,0)
=========     Access to 0x1000ea20000 is out of bounds
=========     and is 118881 bytes after the nearest allocation at 0x1000ea02000 of size 4000 bytes
=========     Saved host backtrace up to driver entry point at kernel launch time
=========         Host Frame: main [0x8e17] in bugs
========= 
启动：cudaSuccess，同步：cudaErrorLaunchFailure
之后的 cudaMalloc：cudaErrorLaunchFailure
========= ERROR SUMMARY: 970 errors
========= ERROR SUMMARY: 969 errors were not printed. Use --print-limit option to adjust the number of printed errors
```

这次一共报告了 970 处错误，1000 个线程几乎个个越界。要注意 memcheck 的检查方式：它判断的是地址有没有落在某个有效的分配里。如果算错的地址恰好落进了另一个有效的分配，比如程序里的另一个数组，它是看不出来的。

发现错误后，compute-sanitizer 会终止那个 kernel，所以程序看到的是 `cudaErrorLaunchFailure`。

compute-sanitizer 的代价是速度。用第 3 章的两个程序试了一下：

```text
$ ./mandelbrot
GPU 0.55 ms，CPU 单线程 574.0 ms，9115 个像素和 CPU 结果不同
$ compute-sanitizer ./mandelbrot
GPU 1.84 ms，CPU 单线程 577.2 ms，9115 个像素和 CPU 结果不同
$ ./shapes | sed -n 3p
  256 × 1       1.59 ms    338 GB/s
$ compute-sanitizer ./shapes | sed -n 4p
  256 × 1      40.52 ms     13 GB/s
```

计算为主的 mandelbrot 慢了 3 倍多，访存为主的 shapes 慢了 25 倍，因为每一次访存都要检查。所以平时测试用小规模的数据跑一遍 compute-sanitizer，而不是拿它跑完整的大任务。

## 5.4 数据竞争和未初始化

compute-sanitizer 默认运行的工具叫 memcheck，查的是越界和非法访问。另外几个工具用 `--tool` 选择。racecheck 查 shared memory 上的数据竞争：

```text
$ compute-sanitizer --tool racecheck ./bugs race
========= COMPUTE-SANITIZER
========= Error: Race reported between Write access at reverse_block(float *)+0x100 in bugs.cu:43
=========     and Read access at reverse_block(float *)+0x110 in bugs.cu:45 [4096 hazards]
========= 
224 个元素反转错了
启动：cudaSuccess，同步：cudaSuccess
之后的 cudaMalloc：cudaSuccess
========= RACECHECK SUMMARY: 1 hazard displayed (1 error, 0 warnings)
```

它指出第 43 行的写和第 45 行的读之间存在竞争，正是缺了 `__syncthreads()` 的地方。注意这次错的是 224 个元素，上一次是 479 个：数据竞争的结果取决于线程实际的执行时序，每次运行都可能不同。结果时对时错、换台机器就变，是数据竞争最典型的症状。

initcheck 查读取未初始化显存的情况：

```text
$ compute-sanitizer --tool initcheck ./bugs uninit
========= COMPUTE-SANITIZER
========= Uninitialized __global__ memory read of size 4 bytes
=========     at sum_first(const float *, float *)+0x30 in bugs.cu:52
=========     by thread (0,0,0) in block (0,0,0)
=========     Address 0x1000dc03000
=========     Saved host backtrace up to driver entry point at kernel launch time
=========         Host Frame: main [0x9141] in bugs
========= 
========= Uninitialized __global__ memory read of size 4 bytes
=========     at sum_first(const float *, float *)+0x40 in bugs.cu:52
=========     by thread (0,0,0) in block (0,0,0)
=========     Address 0x1000dc03004
=========     Saved host backtrace up to driver entry point at kernel launch time
=========         Host Frame: main [0x9141] in bugs
========= 
启动：cudaSuccess，同步：cudaSuccess
之后的 cudaMalloc：cudaSuccess
========= ERROR SUMMARY: 2 errors
```

`p[0]` 和 `p[1]` 两次读取都被抓到了。还有一个 synccheck 工具，检查 `__syncthreads()` 用错的情况，比如只有一部分线程执行到了同步点，第 9 章会提到。

## 5.5 cuda-gdb

compute-sanitizer 告诉你哪里错了，但不告诉你为什么错。要看出错时变量的值，可以用 cuda-gdb，它是 gdb 的扩展，能像调试主机代码一样调试 kernel。为了看到局部变量，要用 `-G` 编译（第 4 章说过它会让 kernel 慢很多，只在调试时用）：

```bash
nvcc -G -g -arch=native bugs.cu -o bugs_g
cuda-gdb --args ./bugs_g far
```

在 cuda-gdb 里输入 `run`，kernel 一出错就停下来，然后可以查看变量：

```text
CUDA Exception: Warp MMU Fault
The exception was triggered at PC 0x1000571da90  scale_wrong(float*, int, int)  (bugs.cu:32)

Thread 1 "bugs_g" received signal CUDA_EXCEPTION_30, Warp MMU Fault.
[Switching focus to CUDA kernel 0, grid 1, block (0,0,0), thread (192,0,0), device 0, sm 0, warp 6, lane 0]
0x000001000571daa0 in scale_wrong<<<(4,1,1),(256,1,1)>>> (p=0x1000b600000, n=1000, stride=1000000) at bugs.cu:32
32	    if (i < n) p[i * stride] *= 2.0f;
$1 = 192
$2 = 1000000
$3 = (@generic float * @parameter) 0x1000b600000
block (0,0,0), thread (192,0,0)
```

（这段输出依次来自 `run`、`print i`、`print stride`、`print p` 和 `cuda block thread` 五条命令。）

cuda-gdb 停在了第 32 行，当前焦点是第 0 个 block 的 192 号线程，`i` 是 192，`stride` 是一百万，`p[i * stride]` 显然远远超出了数组。`cuda block (1,0,0) thread (5,0,0)` 这样的命令可以切换到别的线程查看；`break bugs.cu:32` 可以在 kernel 里设断点，停下来以后 `next`、`step` 单步执行，和调试主机代码一样。不加 `-G` 也能用 cuda-gdb 看到出错的位置，但看不到局部变量，会提示 “No symbol "i" in current context”。

## 5.6 printf

最朴素的办法也能用：kernel 里可以调用 `printf`。

```cpp
if (i == 500) printf("p[%d] = %f\n", i, p[i]);
```

GPU 上的 `printf` 先把内容写进一块缓冲区，等到下一个同步点才由主机打印出来，所以输出出现的时机和 kernel 执行的时机不一致。几万个线程同时打印会很快填满缓冲区（默认大小可以用 `cudaDeviceSetLimit(cudaLimitPrintfFifoSize, ...)` 调整），而且输出的顺序是乱的。像上面这样只让一个或少数几个线程打印，才看得清楚。

## 5.7 一个排查顺序

把这一章的内容串起来，kernel 结果不对或者报错时，可以按这个顺序排查：

1. 每个 CUDA 调用都检查返回值，每次 kernel 启动后调用 `cudaGetLastError()`。这一步应该一开始就做好。
2. 报错的位置看起来莫名其妙时，用 `CUDA_LAUNCH_BLOCKING=1` 运行，让错误出现在出问题的 kernel 那里。
3. 用 compute-sanitizer 跑一遍小规模的输入，先 memcheck，结果时对时错再加 racecheck，怀疑用了没初始化的数据就用 initcheck。编译时带上 `-lineinfo`。
4. 知道了哪一行出错但想不明白为什么，用 `-G` 编译，在 cuda-gdb 里看变量的值。
5. 在 kernel 里用 `assert` 写下自己的假设，比如下标的范围、输入的符号，让错误尽早暴露在离源头最近的地方。

## 5.8 回头看

GPU 程序的错误有三个让人头疼的特点：很多错误根本不报告；报告的错误来得晚，出现在后面某个无辜的调用上；严重错误会让此后所有 CUDA 调用都失败。应对的办法是检查每一个返回值，并且习惯性地用 compute-sanitizer 跑一遍。第一部分到这里结束，接下来的第二部分讨论怎么让 kernel 跑得更快。

2. 把 bugs.cu 里 `reverse_block` 的 `__syncthreads()` 取消注释，用 racecheck 再跑一遍，确认竞争消失、结果全对。
