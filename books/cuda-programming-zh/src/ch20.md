# 第 20 章 异步拷贝、barrier 与 pipeline

第 9 章的 shared memory 用法有一个固定的节奏：block 里的线程合作把一块数据从 global memory 搬进 shared memory，同步，各自计算，再同步，然后搬下一块。在一个 block 内部，搬运和计算是轮流进行的：搬的时候不能算，算的时候不搬。延迟能被掩盖，靠的是同一个 SM 上的其他 block 正好在计算（第 10 章）。

从计算能力 8.0 开始，GPU 可以把数据从 global memory 直接异步地拷进 shared memory，不经过寄存器，发起拷贝的线程也不用等它完成。于是一个 block 就能自己安排流水线：算这一块的同时，下一块已经在路上。这一章实测这种做法什么时候有用，并介绍两种跟踪拷贝完成的机制：pipeline 和 barrier。

## 20.1 例子：FIR 滤波

FIR 滤波是信号处理里最常见的运算：每个输出是 64 个相邻输入的加权和，y[i] = Σ h[t]·x[i+t]。相邻的输出共用大部分输入，适合先把一段输入搬进 shared memory，再让每个线程从 shared memory 里反复读。[fir.cu](code/ch20/fir.cu) 让每个 block 一次处理 1024 个输出，需要 1088 个输入；每个线程算 4 个相邻的输出，系数放在 constant memory 里（所有线程同时读同一个系数，第 7 章）。

最朴素的写法不用 shared memory，直接从 global memory 读，靠 L1 缓存复用。第二种写法是第 9 章的节奏：

```cpp
{{#include code/ch20/fir.cu:pipeline}}
```

`cuda::memcpy_async` 发起一次从 global memory 到 shared memory 的异步拷贝，调用后立刻返回。`cuda::pipeline` 负责记账：`producer_acquire` 和 `producer_commit` 之间发起的拷贝算作流水线的一级；`consumer_wait` 等最早的那一级完成；`consumer_release` 表示这一级的数据用完了。循环一开始先把下一块发出去，再去等当前这一块，所以算当前块的时候，下一块已经在搬了。这里用的是每个线程各自一条的流水线（`thread_scope_thread`），每个线程只等自己发起的拷贝，所以等完之后还要 `__syncthreads()`，确保别的线程搬的那部分也到了。

用 `cuobjdump -sass` 看 `fir_pipeline` 的 SASS，会看到 12 条 `LDGSTS` 指令：这就是硬件的异步拷贝，从 global memory 直接写进 shared memory，数据不经过寄存器，配合 `LDGDEPBAR` 和 `DEPBAR` 指令跟踪完成情况。第 9 章的写法则是先 `LDG` 读进寄存器，再写进 shared memory。

## 20.3 什么时候有用

3200 多万个输出，三种写法的成绩如下。为了看 occupancy 的影响，程序还用第 10 章的办法（动态 shared memory 占位）把每个 SM 驻留的 block 数限制到 2 个和 1 个。表里还有第四种写法，20.4 节再讲：

```text
每个 SM 最多 6 个 block：
  1.357 ms    3166 GFLOPS  直接读 global
  0.805 ms    5334 GFLOPS  同步：先读后算
  0.806 ms    5326 GFLOPS  memcpy_async 两级流水线
  0.801 ms    5361 GFLOPS  memcpy_async + barrier

每个 SM 最多 2 个 block：
  1.327 ms    3238 GFLOPS  直接读 global
  0.886 ms    4846 GFLOPS  同步：先读后算
  0.803 ms    5347 GFLOPS  memcpy_async 两级流水线
  0.798 ms    5384 GFLOPS  memcpy_async + barrier

每个 SM 最多 1 个 block：
  1.579 ms    2720 GFLOPS  直接读 global
  1.400 ms    3068 GFLOPS  同步：先读后算
  0.832 ms    5162 GFLOPS  memcpy_async 两级流水线
  0.829 ms    5183 GFLOPS  memcpy_async + barrier
```

先看第一组：用 shared memory 比直接读 global 快了 40%，但流水线版本和同步版本一样快。每个 SM 驻留 6 个 block 时，一个 block 在等数据，另外五个正在计算，搬运的延迟已经被别的 block 掩盖了，block 内部再搭流水线也没有余地可挖。

限制 occupancy 以后情况就变了。每个 SM 只有一个 block 时，同步版本在搬运期间整个 SM 都闲着，降到 1.400 ms；流水线版本几乎不受影响，0.832 ms，快了 1.7 倍。这和第 10 章的结论是同一个道理：掩盖延迟可以靠更多的 warp，也可以靠每个 warp 内部更多的独立工作，异步拷贝流水线属于后一种。

实际的 kernel 里，occupancy 低往往不是人为限制的结果，而是因为每个 block 要用很大的 shared memory，或者每个线程要用很多寄存器（比如高性能的矩阵乘法）。这时异步拷贝流水线就是必要的。它还有一个附带的好处：数据不经过寄存器，省下了原本用来中转的寄存器。

## 20.4 用 barrier 跟踪拷贝

第四种写法做的事情完全一样，只是拷贝完成的通知交给了 `cuda::barrier`：

```cpp
{{#include code/ch20/fir.cu:barrier}}
```

barrier 初始化时指定参与的线程数（这里是整个 block）。`cuda::memcpy_async(block, dst, src, size, bar)` 由整个 block 合作发起一块拷贝，并把它登记在 barrier 上；`bar.arrive_and_wait()` 要等两件事都发生才返回：block 里所有线程都到达了，登记在上面的拷贝也都完成了。之后 barrier 自动进入下一个阶段，可以反复使用。

性能和 pipeline 版本一样，但 SASS 不一样了：`fir_barrier` 里没有 `LDGSTS`，取而代之的是 `UBLKCP` 和一组 `SYNCS` 指令。拷贝的大小按 16 字节对齐（`cuda::aligned_size_t<16>`），而且由整个 block 合作发起，编译器就用上了批量异步拷贝：由一个线程发出一条指令，搬运整块数据的工作交给专门的拷贝单元，完成情况记录在 shared memory 里的硬件 barrier 上。这正是下一章 TMA 用的那套硬件。

`arrive_and_wait` 还可以拆成两半：`auto token = bar.arrive();` 先报到，然后去做不依赖这块数据的事，最后 `bar.wait(std::move(token));` 再等。拆开之后，先到的线程不必干等，可以做些别的工作。更进一步的写法是把 warp 分工：一部分 warp 专门负责发起拷贝（生产者），其余的 warp 专门计算（消费者），每块 shared memory 配两个 barrier，一个表示“数据已经到了”，一个表示“数据已经用完、可以覆盖了”。高性能的矩阵乘法 kernel 大多采用这种结构。

## 20.5 回头看

异步拷贝让数据从 global memory 直接进入 shared memory，不经过寄存器，发起的线程也不必等待。配合双缓冲，一个 block 可以在计算当前块的同时搬运下一块。它的收益取决于 occupancy：每个 SM 驻留的 block 多时，别的 block 已经掩盖了延迟，流水线看不出效果；每个 SM 只有一两个 block 时，它能快 1.7 倍。`cuda::pipeline` 和 `cuda::barrier` 是两种跟踪拷贝完成的机制，后者在整个 block 合作拷贝对齐的数据块时会用上批量拷贝硬件，这也是 TMA 的基础。

## 20.6 练习

1. 把 fir.cu 的流水线改成三级（三块 shared memory 轮流用，先发出两块再开始计算）。每个 SM 一个 block 时，和两级相比还有提升吗？
2. 把 `TAPS` 改成 16，让计算量变成原来的四分之一，再比较四种写法。计算变少以后，流水线的收益是变大还是变小？
3. 把 `fir_barrier` 里的 `cuda::aligned_size_t<16>(...)` 换成普通的字节数 `SPAN * sizeof(float)`，重新编译，用 `cuobjdump -sass` 看看还有没有 `UBLKCP`，速度有没有变化。
4. 用 `bar.arrive()` 和 `bar.wait()` 改写 `fir_barrier`，把 `block.sync()` 也换成第二组 barrier，让每块 shared memory 有“数据已到”和“已经用完”两个 barrier。
