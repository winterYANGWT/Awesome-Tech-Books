# 第 1 章 GPU 擅长什么：从一个 for 循环说起

刚接触 CUDA 的人，最想知道的往往是：GPU 到底比 CPU 快多少？这个问题没有一个固定答案。有的程序换到 GPU 上快几十倍，有的反而更慢，差别取决于程序在做什么、数据在哪里。与其背结论，不如直接量一量。

本章拿两个最简单的循环做实验。一个很轻，每个元素只做一次乘加：

```cpp
{{#include code/ch01/loops.cu:loops}}
```

`saxpy` 是线性代数里的老朋友，`y = a·x + y`；`heavy` 则让每个元素迭代 256 次。`__host__ __device__` 让同一个函数既能在 CPU 上调用，也能在 GPU 上调用，这样两边算的东西完全一样。

两个循环都处理 6711 万个 `float`，分别用四种方式跑：CPU 单线程；CPU 全部 32 个线程（用 OpenMP 分配，每个线程内部再用 AVX-512 一次算 16 个元素，对 CPU 算是公平的）；GPU 只算 kernel，数据事先已经在显存里；GPU 从主机内存开始，算上把数据拷上去、把结果拷回来的时间。完整程序是 [loops.cu](code/ch01/loops.cu)。

两个循环的差别全在“算多少”和“搬多少”上（元素个数是代码里的 `N = 64 << 20`，即 6711 万）：

| | saxpy | heavy |
|---|---|---|
| 循环体执行次数 | 6711 万次，每个元素一次 | 6711 万次，每个元素一次 |
| 每次的计算 | 1 次乘加，算 2 次浮点运算 | 768 次浮点运算：256 次迭代，每次两次乘、一次加 |
| 每次读写内存 | 读 8 字节（`x[i]`、`y[i]`），写 4 字节，共 12 字节 | 读 4 字节，写 4 字节，共 8 字节 |
| 总计算 | 约 1.3 亿次 | 约 515 亿次 |
| 总读写 | 768 MiB | 512 MiB |
| 算术强度：每读写 1 字节做几次浮点运算 | 1/6 ≈ 0.17 | 96 |
| 算上拷贝时，经过 PCIe 的数据 | 768 MiB：`x`、`y` 拷上去，`y` 拷回来 | 512 MiB：`x` 拷上去，`y` 拷回来 |

两个循环搬的数据差不多，算的却差了 384 倍。1.2 节会看到，正是“算术强度”这一行，决定了它们在 CPU 和 GPU 上各自卡在哪里。

本书的测量都在同一台笔记本上完成：CPU 是 16 核 32 线程的 Ryzen 9 9955HX，GPU 是 RTX 5060 Laptop GPU（8 GB 显存），两者之间是 PCIe 4.0 x8，CUDA 13.3。换一台机器数字会变，但本章的现象都能复现。

## 1.1 同一个循环，换成 GPU 的写法

GPU 版本长这样：

```cpp
{{#include code/ch01/loops.cu:kernels}}
```

最明显的变化是 `for` 循环不见了。`__global__` 标记的函数叫 kernel，在 GPU 上执行。启动 kernel 时，GPU 会同时开出成千上万个线程，每个线程都执行这同一个函数体，区别只在于 `blockIdx`、`blockDim`、`threadIdx` 这几个内置变量的值不同。`i = blockIdx.x * blockDim.x + threadIdx.x` 把它们换算成一个全局编号，于是每个线程认领一个 `i`，处理一个元素。原来循环的每一次迭代，变成了一个线程。

线程是成组启动的：256 个线程一组，叫一个 block，6711 万个元素需要 262144 个 block。启动的写法是：

```cpp
int threads = 256, blocks = (N + threads - 1) / threads;
saxpy_gpu<<<blocks, threads>>>(N, 2.0f, d_x, d_y);
```

尖括号里的两个数就是 block 的个数和每个 block 的线程数。`(N + threads - 1) / threads` 是向上取整，最后一个 block 可能有几个线程分不到元素，所以 kernel 里要有 `if (i < n)` 这道检查。这些坐标怎么用、block 该开多大，第 3 章会细讲；分配显存、拷贝数据这些准备工作，第 2 章会一步步写出来。这一章只关心结果。

图 1.1 里有四件事值得注意：

1. saxpy 用 32 个 CPU 线程，并不比 1 个线程快。
2. saxpy 换到 GPU，kernel 快了 10 倍；算上拷贝，反而比 CPU 单线程慢 3 倍。

4. heavy 换到 GPU，kernel 又快了 14–20 倍；算上拷贝，仍然比 CPU 全部线程快。

同样是加线程、换 GPU，两个循环的反应完全相反。原因是它们卡在不同的地方。

**瓶颈：计算和搬运，哪边重。** 循环要做两件事：算，和把数据搬到算的地方。这两件事是同时进行的，谁慢，总时间就由谁决定：

> 时间 ≈ max（总计算 ÷ 算力，总搬运 ÷ 带宽）

可以把它想成一架天平，一边放计算，一边放搬运，哪边重，程序就卡在哪边。天平往哪边倒，取决于两个比值：

- 任务的比值：每读写 1 字节做几次浮点运算，就是开头那张表里的**算术强度**，saxpy 是 1/6，heavy 是 96。
- 机器的比值：算力 ÷ 带宽，也就是机器搬 1 字节的工夫能做几次浮点运算，叫它**平衡点**。

算术强度低于平衡点，搬运那边重，程序**受带宽限制**：给它再多算力也没用，只有带宽高了才会快。高于平衡点，计算那边重，程序**受算力限制**：带宽再高也没用，要靠更多的算力。第 12 章用 Nsight Compute 判断瓶颈时，用的也是这两个说法。

四种跑法的平衡点可以用图 1.1 自己的数据量出来：算力取 heavy 跑出来的浮点运算速度，带宽取 saxpy 跑出来的读写速度。把两个循环的算术强度也放上去（图 1.2）：

拿两个循环的比值去对，四件事就都有了解释：

- **saxpy 的 1/6 低于所有平衡点，在哪里都受带宽限制。** 时间基本就是 768 MiB ÷ 带宽。32 个线程共用同一套内存，算力多了，带宽没多（第 1 件）。GPU 的显存带宽是 CPU 内存的 10 倍，所以 kernel 快 10 倍；可一算上拷贝，这 768 MiB 要走只有 12 GB/s 的 PCIe，就成了最慢的跑法（第 2 件）。
- **heavy 的 96 高于 CPU 的两个平衡点，在 CPU 上受算力限制。** 所以加线程直接见效（第 3 件）。它也高于 GPU 显存的平衡点 34，kernel 的时间由算力决定，1.4 节会算它离算力峰值还有多远（第 4 件）。
- **但 96 远低于 PCIe 的平衡点 1000。** 一算上拷贝，heavy 也受带宽限制了：50.4 ms 里有 46 ms 花在 PCIe 上。它还能赢 CPU，只是因为 CPU 那边算得更慢。严格说，这里拷贝和计算是先后进行的，时间是两者相加而不是取大，但卡在哪边的道理一样。

所以 GPU 划算的条件，就是让天平往计算那边倒：一是每搬 1 字节要有足够多的计算，越过 GPU 的平衡点；二是数据留在显存里连续做很多步计算，只在开头和结尾过一次 PCIe，不让 PCIe 那个 1000 的平衡点起作用。真实的 GPU 程序，从深度学习训练到分子动力学模拟，都是按第二种方式组织的。第 12 章会把这架天平画成 roofline 图，用峰值算出更精确的平衡点；第 13 章讲怎么让拷贝和计算同时进行；第 29 章用一个完整的案例演示，让数据留在 GPU 上能省下多少时间。

32 个 GPU 线程只能跑出 0.7 GB/s，而上一节 CPU 一个线程就跑到了 34 GB/s。带宽随线程数几乎成正比地上升，一直到 3 万多个线程才停在 330 GB/s 左右。

原因在于一次显存访问要等多久。从 32 个线程那一点可以估算出来：32 个线程每轮各读 4 字节，一共 128 字节，0.7 GB/s 里读和写各占一半，算下来每一轮要花大约 360 纳秒。也就是说，一个线程发出读请求以后，要等几百纳秒数据才回来，这段时间里它什么也做不了。

CPU 也面对同样的延迟，但它花了大量芯片面积来对付它：几十 MB 的多级缓存、能提前猜出下一次访问地址的预取器、在等数据时先去执行后面不相关指令的乱序执行。所以一个 CPU 线程看到的内存很“快”。GPU 没在单个线程上下这么多功夫。它的办法是让大量线程同时驻留在芯片上，一批线程在等数据，就切换到另一批已经拿到数据的线程去执行，切换几乎没有代价。只要同时在等的请求足够多，总带宽就能跑满。

需要多少线程？按 32 个线程时的速度，每个线程能贡献 0.7 GB/s ÷ 32 ≈ 22 MB/s，要跑到 330 GB/s，大约需要 1.5 万个线程。实测 1.6 万个线程时是 275 GB/s，要到 3.3 万个才饱和，比估算多了一倍。差别在于延迟不是固定的：显存空闲时一次访问等 360 纳秒，忙起来以后请求要排队，每个请求等得更久，就需要更多线程同时在路上补足。这个关系就是排队论里的 Little 定律：同时在路上的数据量 = 带宽 × 延迟。想要的带宽越高、延迟越长，同时在路上的请求就得越多。

这就是 GPU 编程最基本的约束：**要给它几万个可以同时推进的独立任务**。一个线程本身很慢，GPU 的速度来自同时有几万个线程在跑。上一节的 saxpy 启动了 6711 万个线程，远远超过需要，所以能跑满带宽；如果一个任务只能拆成几百份，放到 GPU 上多半比 CPU 还慢。

## 1.4 这块 GPU 里有什么

几万个线程同时驻留在哪里？GPU 芯片由许多个 SM（streaming multiprocessor）组成，线程以 block 为单位分配到各个 SM 上执行。这块 RTX 5060 Laptop GPU 有 26 个 SM，每个 SM 最多同时驻留 1536 个线程，全卡就是将近 4 万个，正好覆盖上一节需要的 3 万多。

和这台笔记本的 CPU 对比一下：

| | CPU（Ryzen 9 9955HX） | GPU（RTX 5060 Laptop） |
|---|---|---|
| 核心 | 16 个核心，每个 2 个硬件线程 | 26 个 SM，每个最多 1536 个驻留线程 |
| 同时运行的线程 | 32 | 约 4 万 |
| 末级缓存 | 64 MB L3 | 32 MB L2 |
| 内存带宽（实测） | 约 34 GB/s | 330～350 GB/s |

每个 SM 有 128 条 FP32 运算通道，全卡 3328 条。heavy kernel 跑的时候 SM 频率是 2.8 GHz 左右（`nvidia-smi` 可以看到），理论上每秒能执行 3328 × 2.8 G ≈ 9.4 万亿条 FP32 指令。用 `cuobjdump -sass` 看编译出来的指令，heavy 的每次迭代正好是一条乘法和一条乘加，6711 万个元素 × 256 次迭代 × 2 条指令，4.3 ms 跑完，相当于每秒 8 万亿条，达到了峰值的 85% 左右。这样一个没做任何优化的 kernel 就能接近算术峰值，是因为它的计算完全独立、几乎不访问内存。大多数真实的 kernel 没有这么理想，后面第二部分会讲怎么找出它们离峰值差在哪里。

每个 SM 上还有 64K 个 32 位寄存器和 100 KB 的 shared memory，由驻留在上面的线程分着用。这两样资源决定了一个 SM 实际能驻留多少线程，第 10 章会专门讨论。

## 1.5 什么时候该用 GPU

把本章的实验归纳一下，一个任务适合放到 GPU 上，通常要满足这几条：

- **能拆成大量独立的小任务**，至少几万个，最好几百万个。每个任务之间很少需要互相等待。
- **计算相对数据搬运足够多**，或者数据能长期留在显存里，不必每次都过 PCIe。
- **各个任务做的事情大体相同**。GPU 的线程是按组执行的，同一组里的线程走不同的分支，就要轮流执行，第 6 章会量化这个代价。

满足这几条以后，也不一定要自己写 kernel。矩阵乘法、FFT、排序、随机数、深度学习算子，NVIDIA 和社区都有高度优化的库（cuBLAS、cuFFT、Thrust、cuDNN 等），PyTorch 这样的框架又在它们之上包了一层。能用库就先用库，第五部分会介绍其中几个。自己写 kernel 的理由通常是：没有现成的库覆盖你的计算；或者几个算子之间来回读写显存，想把它们合成一个 kernel；或者需要精细控制数据放置、stream、同步。本书讲的就是这种时候需要的知识。

## 1.6 回头看

GPU 的快，来自几万个线程同时在跑，而不是单个线程快。显存带宽是 CPU 内存的 10 倍，算力也高出一个数量级，但前提是给它足够多的并行任务，而且数据不能频繁地往返 PCIe。下一章从头写一个完整的 CUDA 程序，看看分配显存、拷贝数据、启动 kernel、检查错误这一整套流程具体怎么写，以及每一步花多少时间。
