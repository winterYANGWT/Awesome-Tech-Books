# 第 25 章 cuBLAS 与 cuSOLVER

线性代数是 GPU 最早、也最成熟的应用领域。cuBLAS 提供 BLAS 标准里的向量和矩阵运算，最重要的是矩阵乘法（GEMM）；cuSOLVER 提供 LAPACK 风格的矩阵分解、线性方程组求解和特征值计算。这一章先用矩阵乘法看看库和自己写的 kernel 差多少、差在哪里，再讲使用 cuBLAS 最容易踩的坑：列主序；最后用 cuSOLVER 求特征值，说明它特有的错误报告方式。

## 25.1 矩阵乘法：自己写和用库差多少

[gemm.cu](code/ch25/gemm.cu) 计算两个 4096×4096 的 `float` 矩阵的乘积，矩阵按 C++ 的习惯行主序存放。每种做法的结果都和 GPU 上用 `double` 算出的参考答案比较，误差的度量是 |c − c_ref| / (|c_ref| + 1) 在抽样元素上的最大值（矩阵元素的大小在几十以内）。链接时要加 `-lcublas`。

```text
cublasCreate 用了 2.2 ms

  140.22 ms    0.98 TFLOPS  最大相对误差 5.7e-05  朴素 kernel
  149.73 ms    0.92 TFLOPS  最大相对误差 5.7e-05  分块 kernel（shared memory）
   24.15 ms    5.69 TFLOPS  最大相对误差 5.7e-05  寄存器分块 kernel（每线程 4×4）
   12.25 ms   11.22 TFLOPS  最大相对误差 5.7e-05  cuBLAS SGEMM（FP32）
    7.88 ms   17.45 TFLOPS  最大相对误差 1.7e-02  cuBLAS SGEMM（TF32 张量核）
    3.85 ms   35.73 TFLOPS  最大相对误差 1.5e-01  cuBLAS GemmEx（BF16 输入，FP32 累加）
   11.80 ms   11.65 TFLOPS  最大相对误差 6.5e+01  cuBLAS SGEMM，参数顺序没有调换（错误）
```

前三行是自己写的 kernel。朴素写法让一个线程算 C 的一个元素：

```cpp
{{#include code/ch25/gemm.cu:naive}}
```

0.98 TFLOPS，不到这块 GPU FP32 峰值（18.4 TFLOPS，第 10 章）的十分之一。按第 9 章的思路，让 block 把 A 和 B 各取 32×32 的一块放进 shared memory 再算，结果反而更慢了一点。原因在于朴素写法已经靠 L1 和 L2 缓存得到了不少复用（同一个 warp 读 A 的同一个元素、读 B 的连续元素），而分块版本里每个线程仍然只算一个输出：每从 shared memory 读两个数，只做一次乘加，瓶颈换成了 shared memory 的读取。

真正的进步来自寄存器层面的复用。第三个 kernel 让每个线程同时算 4×4 个输出：

```cpp
{{#include code/ch25/gemm.cu:reg}}
```

每一步从 shared memory 读 4 个 A 和 4 个 B 进寄存器，就能做 16 次乘加，复用率提高了 8 倍，速度到了 5.69 TFLOPS，是朴素写法的 6 倍。这也是第 10 章说的：为了让每个线程多用寄存器、多做独立的计算，牺牲一些 occupancy 是值得的。

但它仍然只有 cuBLAS 的一半。cuBLAS 的 FP32 矩阵乘法跑到了 11.22 TFLOPS，峰值的六成，它的实现还用了更大的寄存器分块、向量化读取、第 20 章的异步拷贝流水线、针对每种 GPU 精心调好的参数。自己写一个比得上 cuBLAS 的 GEMM 是非常专业的工作，一般没有必要。

## 25.2 张量核：更快，但精度更低

后两行用上了张量核（Tensor Core），这是 GPU 上专门做小矩阵乘加的单元，速度远高于普通的 FP32 运算单元，代价是输入的精度更低。

```cpp
{{#include code/ch25/gemm.cu:tf32}}
```

`CUBLAS_TF32_TENSOR_OP_MATH` 允许 cuBLAS 把 FP32 的输入截成 TF32（10 位尾数，和 FP16 一样；指数范围和 FP32 一样）送进张量核，累加仍用 FP32。速度提高到 17.45 TFLOPS，误差从 5.7e-05 增加到 1.7e-02，大了 300 倍。

```cpp
{{#include code/ch25/gemm.cu:bf16}}
```

再进一步，把输入转成 bfloat16（只有 7 位尾数），用 `cublasGemmEx` 指定输入类型和计算类型。35.73 TFLOPS，是 FP32 的三倍多，误差也到了 0.15。深度学习训练和推理大量使用这种精度，因为神经网络对这种误差不敏感；科学计算里就要慎重，最好先评估误差是否可以接受。注意 TF32 模式是用一个开关打开的，代码其余部分一个字不用改，结果却变了，所以在别人的代码或框架里看到“FP32 矩阵乘法”时，要确认它是否悄悄用了 TF32（比如 PyTorch 就有相应的全局开关）。

## 25.3 列主序

cuBLAS 沿袭了 Fortran BLAS 的约定：矩阵按**列主序**存放，第 j 列的元素连续排列。C++ 程序里的二维数组通常是行主序的。同样一块内存，行主序读出来是矩阵 M，列主序读出来就是 Mᵀ。

所以行主序的 A、B、C，在 cuBLAS 看来是 Aᵀ、Bᵀ、Cᵀ。我们要的是 C = A·B，两边转置就是 Cᵀ = Bᵀ·Aᵀ，也就是说，只要把 B 放在第一个位置、A 放在第二个位置，cuBLAS 按列主序算出的“Bᵀ·Aᵀ”写回内存，按行主序读出来正好是 A·B：

```cpp
{{#include code/ch25/gemm.cu:sgemm}}
```

（参数 `m`、`n`、`k` 和 leading dimension 也要相应地按交换后的角色填写；这里是方阵，看不出区别，非方阵时尤其要小心。）

照着数学公式的顺序把 A、B 传进去，是最常见的错误：

```cpp
{{#include code/ch25/gemm.cu:wrong}}
```

它不会报任何错，速度也一样，只是结果完全不对：误差 65，算出来的是行主序下的 B·A。cuBLAS 没有办法知道你的数据是按什么顺序存放的，一定要用参考结果验证。

另一件小事是 handle：`cublasCreate` 会初始化库、分配内部资源，这里用了 2.2 ms（第一次运行、库文件还不在操作系统缓存里时会更久），应该在程序开始时创建一个，反复使用：

```cpp
{{#include code/ch25/gemm.cu:handle}}
```

handle 默认使用默认 stream，要和第 13 章的 stream 流水线配合，用 `cublasSetStream` 指定；cuBLAS 函数本身都是异步的，返回时计算不一定完成。

## 25.4 cuSOLVER：工作区和 devInfo

cuSOLVER 的密集矩阵接口（`cusolverDn`）和 LAPACK 很像。[solver.cu](code/ch25/solver.cu) 用 `syevd` 求一个 2048×2048 随机对称矩阵的全部特征值和特征向量，链接时要加 `-lcusolver`：

```cpp
{{#include code/ch25/solver.cu:syevd}}
```

cuSOLVER 的函数大多分两步：先调 `_bufferSize` 版本问需要多大的工作区，分配好，再调真正的计算函数。这和第 24 章 CUB 的临时空间是一个思路，工作区也可以分配一次反复使用。

```text
2048×2048 对称矩阵的特征分解：42.7 ms，工作区 65.1 MB，devInfo = 0
最小特征值 -51.9132，最大特征值 52.1416，‖A·v − λ·v‖ 最大为 4.5e-05

cusolverDnSpotrf 返回 成功，devInfo = 1
```

计算后，A 被特征向量覆盖（列主序，第 k 列是第 k 个特征向量），特征值从小到大存在 W 里。程序抽查了三个特征对，A·v − λ·v 的大小在 10⁻⁵ 量级，结果正确。42.7 ms 是预热之后的时间，第一次调用要多花 190 ms 左右，同样是库的初始化开销。

第二部分演示了 cuSOLVER 报告错误的方式。Cholesky 分解（`potrf`）要求矩阵正定，而这个随机对称矩阵有负特征值，分解注定失败：

```cpp
{{#include code/ch25/solver.cu:potrf}}
```

函数本身返回的是成功：它只负责检查参数是否合法、计算有没有顺利启动。计算结果是否有效，记在设备内存里的 `devInfo` 上：0 表示成功，正数 i 表示第 i 个主子式不是正定的（这里第一个对角元就是负的），负数 −i 表示第 i 个参数不合法。`devInfo` 在显存里，要拷回主机才能检查，而这次拷贝本身就会等计算完成。忘记检查它，程序就会拿着一个没算完的分解继续往下走。

## 25.5 回头看

矩阵乘法上，库和自己写的 kernel 差距巨大：朴素写法不到 1 TFLOPS，寄存器分块能到 5.7 TFLOPS，cuBLAS 是 11.2 TFLOPS，用上张量核以后 TF32 是 17.5 TFLOPS、BF16 是 35.7 TFLOPS，误差也相应增大。cuBLAS 按列主序理解矩阵，行主序的数据要交换参数顺序，算错了也不会报错，必须验证。handle 和工作区都要一次创建、反复使用。cuSOLVER 函数的返回值只说明调用是否合法，计算是否成功要看 `devInfo`。

## 25.6 练习

1. 把 gemm.cu 的矩阵改成 A 为 4096×1024、B 为 1024×2048 的非方阵，正确地填写 `cublasSgemm` 的 `m`、`n`、`k` 和三个 leading dimension，用参考答案验证。
2. 用 `cublasGemmEx` 加 `CUDA_R_16F`（FP16）输入再试一次，速度和误差与 BF16 相比如何？矩阵元素放大到 ±1000 时，FP16 会出什么问题？
3. 把寄存器分块 kernel 改成每个线程算 8×8 个输出（block 仍是 256 个线程，算 128×128 的块），速度能提高多少？用 `-Xptxas -v` 看看寄存器用量和有没有 spill。
4. 用 cuSOLVER 的 `getrf` 和 `getrs` 解一个 4096 阶的线性方程组 A·x = b，检查 `devInfo`，并计算残差 ‖A·x − b‖。
