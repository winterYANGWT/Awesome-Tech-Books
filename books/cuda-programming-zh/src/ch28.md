# 第 28 章 先移植求力

这一章按最直接的思路，只把求力搬到 GPU 上，其余部分不动。程序是 [md_force_gpu.cu](code/ch28/md_force_gpu.cu)，它包含上一章的 `md_common.h`。

## 28.1 一个线程负责一个粒子

CPU 版本的求力利用牛顿第三定律，每对粒子算一次，同时更新两个粒子。如果照搬到 GPU，让每个线程处理一个粒子 i 和它的一半邻居，那么线程 i 在给粒子 j 加力的同时，线程 j 可能也在给自己加力，这就是第 5 章的数据竞争。可以用原子操作，但每个粒子的力每步要被几十个线程原子地加，代价不小（第 22 章）。

更简单的办法是放弃牛顿第三定律：用完整的邻居表，每对粒子在两个粒子的表里各出现一次，每个线程只计算并写入自己的力。计算量翻倍，但完全没有写冲突：

```cpp
{{#include code/ch28/md_force_gpu.cu:kernel}}
```

邻居表在拷到 GPU 之前做了一次转置：粒子 i 的第 k 个邻居存放在 `nbr[k * n + i]`。这样同一个 warp 里的 32 个线程同时读各自的第 k 个邻居时，读的是连续的 32 个整数，是合并访问（第 8 章）。按 CPU 那样每个粒子的邻居连续存放，相邻线程读的地址就隔了 128 个整数。

`Real` 模板参数决定计算用什么精度，28.4 节再说。

## 28.2 每一步的数据流

每一步算力时，位置拷上去，力拷回来：

```cpp
{{#include code/ch28/md_force_gpu.cu:step}}
```

每 10 步重建一次邻居表仍然在 CPU 上做，建好以后转置，整个拷到 GPU（5 万多个粒子 × 128 个位置，28 MB）。

先用全 `double` 的版本：

```text
$ ./md_force_gpu double

  步数     动能/N     势能/N     总能量/N
     0    1.08300   -6.33281   -5.249812
   100    0.56967   -5.81938   -5.249713
   200    0.58731   -5.83703   -5.249721
   300    0.58642   -5.83614   -5.249719
   400    0.58617   -5.83589   -5.249718
   500    0.58602   -5.83574   -5.249722
总能量相对漂移 1.7e-05

阶段                       时间        占比    每步
求力 kernel              637.5 ms    5.4%    1.28 ms
位置拷上去             76.7 ms    0.6%    0.15 ms
力拷回来               150.8 ms    1.3%    0.30 ms

```

能量漂移和 CPU 版本完全一样，结果是对的。求力 kernel 每步 1.28 ms，CPU 上要 23.91 ms，快了将近 19 倍，而且 GPU 算的粒子对还多了一倍。每步拷位置和力加起来只要 0.45 ms，数据量小，不是问题。

可整个程序每步只从 35.65 ms 降到 23.81 ms，快了 1.5 倍。原因就在倒数第二行：建邻居表现在占了 91% 的时间，每步分摊 21.74 ms，比 CPU 版本的 11.42 ms 还多。GPU 版本要的是完整的邻居表，CPU 要多找一倍的邻居，还要转置、拷贝 28 MB。这正是上一章预告的 Amdahl 定律：加速了一部分，剩下的部分就成了全部。

## 28.4 精度：这块 GPU 的 FP64 很慢

求力 kernel 的第一版，最小镜像是这样写的：`dx -= box * rint(dx / box)`，全部用 `double`，每个邻居做三次双精度除法，每步要 1.94 ms。把除以盒长改成乘以它的倒数（倒数在 kernel 外面算好传进来），就降到了上面的 1.28 ms。原因是这块消费级 GPU 的双精度运算单元很少，FP64 吞吐只有 FP32 的几十分之一，双精度除法更是要展开成一长串指令。

所以再进一步，用混合精度：只有两个坐标相减这一步用 `double`（两个几十大小的数相减，结果可能只有零点几，单精度会损失有效数字），相减之后的位移、最小镜像、LJ 势的计算都用 `float`，模板参数 `Real` 取 `float`（能量表的前几位和全 `double` 一样，这里略去）：

```text
$ ./md_force_gpu mixed
55296 个粒子，500 步，求力用 混合精度
总能量相对漂移 1.7e-05

阶段                       时间        占比    每步
求力 kernel              131.6 ms    1.2%    0.26 ms
位置拷上去             76.1 ms    0.7%    0.15 ms
力拷回来               150.8 ms    1.3%    0.30 ms
邻居表（CPU，含拷贝）   10884.6 ms   95.4%   21.77 ms
积分（CPU）            169.7 ms    1.5%    0.34 ms
合计                   11412.9 ms           22.83 ms
```

求力 kernel 降到 0.26 ms，是全 `double` 版本的五分之一，比 CPU 快 90 倍。能量漂移仍然是 1.7 × 10⁻⁵，在这个精度下看不出任何差别。位置和速度的积分、能量的累加仍然用 `double`，误差不会一步步积累起来。这种“关键的地方用双精度，大量的计算用单精度”的做法，是 GPU 上的分子动力学程序普遍采用的策略。在别的问题里，单精度是否够用要具体检验，能量守恒这样的物理量就是很好的检验标准。第 36 章会进一步讨论浮点精度。

## 28.5 下一步该做什么

现在 95% 的时间都花在 CPU 建邻居表上，GPU 上的工作每步只占 0.7 ms 左右。继续优化求力 kernel 已经毫无意义，要做的是把邻居表也搬到 GPU 上；而一旦邻居表在 GPU 上建，位置就不必每步拷上去，积分也可以放到 GPU 上，力也不必拷回来。下一章就这样做。

## 28.6 回头看

只移植求力时，为了避免写冲突，GPU 版本用完整的邻居表、一个线程负责一个粒子，计算量翻倍但不需要原子操作；邻居表转置存放，读取可以合并。求力 kernel 比 CPU 快了近 20 倍，用混合精度后快了 90 倍，能量守恒丝毫不受影响；这块 GPU 的双精度很慢，去掉 kernel 里的双精度除法就快了三分之一。但整个程序只快了 1.5 倍：留在 CPU 上的邻居表成了瓶颈，而且 GPU 版本需要的完整邻居表让它更慢了。

## 28.7 练习

1. 去掉邻居表的转置，让 kernel 按 `nbr[i * max_nbr + k]` 读取，求力 kernel 慢了多少？用 ncu 看看每个读请求的 sector 数（第 8 章）。
2. 在 GPU 上利用牛顿第三定律：用一半的邻居表，给粒子 j 加力时用 `atomicAdd`（`double` 和 `float` 各试一次）。比起完整邻居表、不用原子操作的版本，谁快？
3. 把位置和力的主机数组换成 pinned 内存（第 15 章），拷贝时间能省多少？对整体有影响吗？
4. 用 Nsight Systems 看一个时间步的时间线，确认 GPU 有多大比例的时间在闲着。
