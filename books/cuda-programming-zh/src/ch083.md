# 第 83 章 CUDA 库错误处理 reference：不要只检查 Runtime API

## 83.1 问题的由来

前面几章的库示例给出了 cuBLAS、cuSolver、cuRAND 的完整调用路径，很适合入门，但它们有一个共同的问题：错误检查最多只覆盖了 Runtime API，库函数自己的返回状态都没有检查。照着这些示例写代码，很容易只记住 `CHECK_CUDA(cudaMalloc(...))`，却忘了库函数本身也有独立的返回状态。

本章把这几类错误放在一起对照：Runtime API、cuBLAS、cuSolver、cuRAND、Thrust 报告错误的方式各不相同，检查的位置也不完全一样。

## 83.2 核心模型

| 调用类型 | 主要状态来源 | 典型检查点 |
|---|---|---|
| CUDA Runtime API | `cudaError_t` | 分配、拷贝、同步、kernel launch 后 |
| cuBLAS | `cublasStatus_t` | 每个 `cublas*` 调用后 |
| cuSolver | library status + device `devInfo` | workspace query、solve 调用、求解完成后的 `devInfo` |
| cuRAND Host API | `curandStatus_t` | generator 创建、seed 设置、随机数生成 |
| Thrust | C++ 调用边界和底层 CUDA 错误 | 算法调用后、host 读取或显式同步处 |

工程上要把“API 是否成功提交”和“数值算法是否成功完成”分开。cuSolver 的 `devInfo` 是最典型的例子：库调用返回成功，并不等于求解结果一定可用。

## 83.3 详解

[第 79 章](ch079.md)的 cuBLAS 示例里，Runtime API 调用都包在 `CHECK_CUDA` 中，但 `cublasCreate`、`cublasDgemm`、`cublasDestroy` 的返回状态没有检查。把它和[第 80 章](ch080.md)的 cuSolver 调用放在一起，按第 79 章的习惯只检查 Runtime API，代码是这样的：

```cpp
// 只有分配和拷贝包在 CHECK_CUDA 里，库函数的返回值全被丢掉了
CHECK_CUDA(cudaMemcpy(dA, A.data(), sizeof(double) * m * k, cudaMemcpyHostToDevice));
CHECK_CUDA(cudaMemcpy(dB, B.data(), sizeof(double) * k * n, cudaMemcpyHostToDevice));
cublasCreate(&blas);
cublasDgemm(blas, CUBLAS_OP_N, CUBLAS_OP_N, m, n, k,
            &alpha, dA, m, dB, k, &beta, dC, m);
CHECK_CUDA(cudaMemcpy(C.data(), dC, sizeof(double) * m * n, cudaMemcpyDeviceToHost));

cusolverDnCreate(&solver);
cusolverDnDsyevd_bufferSize(solver, jobz, uplo, dim, dS, dim, dW, &lwork);
CHECK_CUDA(cudaMalloc(&work, sizeof(double) * lwork));   // 查询失败时 lwork 可能没被写入
cusolverDnDsyevd(solver, jobz, uplo, dim, dS, dim, dW, work, lwork, dInfo);
CHECK_CUDA(cudaMemcpy(W, dW, sizeof(double) * dim, cudaMemcpyDeviceToHost));
// dInfo 从没读回：即使求解失败，W 也会被当成正确结果使用
```

这段代码在一切正常时能得到正确结果，出错时程序却不会停下来。例如 leading dimension 填得比矩阵行数还小时，`cublasDgemm` 返回 `CUBLAS_STATUS_INVALID_VALUE`，不做任何计算，拷回的 `C` 只是 `dC` 里原有的内容，程序照样往下走；workspace 查询失败时，`lwork` 可能根本没被写入，`work` 就按错误的大小分配。cuSolver 路径还多一层：除了 `cusolverDnDsyevd_bufferSize` 和 `cusolverDnDsyevd` 的返回状态，`dInfo` 也必须作为求解输出的一部分读回检查。用下文的检查宏改写后，每个调用都落到同一个检查习惯里：

```cpp
CHECK_CUDA(cudaMemcpy(dA, A.data(), sizeof(double) * m * k, cudaMemcpyHostToDevice));
CHECK_CUDA(cudaMemcpy(dB, B.data(), sizeof(double) * k * n, cudaMemcpyHostToDevice));
CHECK_CUBLAS(cublasCreate(&blas));
CHECK_CUBLAS(cublasDgemm(blas, CUBLAS_OP_N, CUBLAS_OP_N, m, n, k,
                         &alpha, dA, m, dB, k, &beta, dC, m));
CHECK_CUDA(cudaMemcpy(C.data(), dC, sizeof(double) * m * n, cudaMemcpyDeviceToHost));

CHECK_CUSOLVER(cusolverDnCreate(&solver));
CHECK_CUSOLVER(cusolverDnDsyevd_bufferSize(solver, jobz, uplo, dim, dS, dim, dW, &lwork));
CHECK_CUDA(cudaMalloc(&work, sizeof(double) * lwork));
CHECK_CUSOLVER(cusolverDnDsyevd(solver, jobz, uplo, dim, dS, dim, dW, work, lwork, dInfo));
int info = 0;
CHECK_CUDA(cudaMemcpy(&info, dInfo, sizeof(int), cudaMemcpyDeviceToHost));
if (info != 0) {                        // 库调用成功，不等于求解成功
    fprintf(stderr, "cusolverDnDsyevd: info = %d\n", info);
    exit(EXIT_FAILURE);
}
CHECK_CUDA(cudaMemcpy(W, dW, sizeof(double) * dim, cudaMemcpyDeviceToHost));
```

`cublasDgemm` 的参数里有很多逗号，但它们都在调用自己的括号里，整个调用仍然只算宏的一个参数。`info` 的检查不能交给宏：它不是函数返回值，而是求解写在 device 上的输出，要先拷回 host 才能判断。

[第 81 章](ch081.md)的 cuRAND Host API 则应检查 generator 生命周期中的每一步，写法相同，例如 `CHECK_CURAND(curandGenerateNormal(rng, dSamples, count, mean, stddev))`。seed 不属于错误处理，但它是实验可复现性的一部分，应该和 generator 类型一起记录。

## 83.4 代码示例

上面用到的几个检查宏思路相同：执行调用，把返回值和该库的成功状态（`cudaSuccess`、`CUBLAS_STATUS_SUCCESS`、`CUSOLVER_STATUS_SUCCESS`、`CURAND_STATUS_SUCCESS`）比较，不相等时打印文件名、行号、调用表达式和状态码。几种状态类型可以共用一个函数模板：

```cpp
#include <cublas_v2.h>
#include <curand.h>
#include <cusolverDn.h>
#include <cstdio>
#include <cstdlib>

// 状态不等于 ok 时，报告位置、调用表达式和状态码，然后退出
template <typename Status>
void check_status(Status status, Status ok, const char* expr,
                  const char* file, int line)
{
    if (status != ok) {
        fprintf(stderr, "%s:%d: %s returned %d\n",
                file, line, expr, static_cast<int>(status));
        exit(EXIT_FAILURE);
    }
}
#define CHECK_CUDA(call) \
    check_status((call), cudaSuccess, #call, __FILE__, __LINE__)
#define CHECK_CUBLAS(call) \
    check_status((call), CUBLAS_STATUS_SUCCESS, #call, __FILE__, __LINE__)
#define CHECK_CUSOLVER(call) \
    check_status((call), CUSOLVER_STATUS_SUCCESS, #call, __FILE__, __LINE__)
#define CHECK_CURAND(call) \
    check_status((call), CURAND_STATUS_SUCCESS, #call, __FILE__, __LINE__)
```

链接时按用到的库加 `-lcublas`、`-lcusolver`、`-lcurand`。

## 83.5 工程判断

| 情况 | 处理 |
|---|---|
| Runtime API 失败 | 立刻返回或抛错，并带上文件、行号、调用表达式 |
| library API 失败 | 不要用 `cudaGetLastError` 代替库 status，应该检查库自己的返回值 |
| kernel launch 后 | 检查 launch error，再在需要的位置同步捕获异步执行错误 |
| cuSolver 求解后 | 同时检查 library status 和 `devInfo` |
| Thrust 算法后结果异常 | 查输入范围、execution policy、同步边界和底层 CUDA 错误 |

## 83.6 API 与要点速查

| 库 | 要点 |
|---|---|
| cuBLAS | 示例只展示调用路径，工程代码里每个调用都要检查 `cublasStatus_t` |
| cuSolver | 不能只分配 `dInfo`，还要读回并解释求解状态 |
| cuRAND | 用完 destroy generator，检查每一步的 status，并记录 seed 和 generator 类型 |
| Thrust | 不要硬套 Runtime API 的 `CHECK_CUDA`，要在 C++ 调用和同步边界处处理错误 |

## 83.7 小结

读完本章，你应该能够在任何 CUDA 库代码里先问三件事：这个调用返回什么状态，异步错误在哪里暴露，数值算法本身有没有额外的状态输出。把这三层分开检查，库调用出错时才不会被漏掉。
