# 第 10 章 occupancy：驻留的 warp 越多越好吗

前面几章反复遇到同一个问题：一个 SM 上同时驻留了多少个 warp。第 1 章说要几万个线程才能跑满显存带宽；第 3 章发现 block 太小或太大都会变慢，原因是驻留的线程不够；第 6 章讲了调度器靠在 warp 之间切换来掩盖延迟。一个 SM 实际驻留的 warp 数占它最多能驻留的 warp 数的比例，叫 **occupancy**（占用率）。这一章回答三个问题：什么限制了 occupancy，它到底有多重要，以及为什么它不是越高越好。

## 10.1 什么限制了驻留的 warp 数

这块 GPU 的每个 SM 最多驻留 48 个 warp（1536 个线程）。实际能驻留多少，取决于四个上限，哪个先到就由哪个决定：

- **线程数**：最多 1536 个。
- **block 数**：最多 24 个（第 3 章，block 太小时就是被它卡住的）。
- **寄存器**：一共 65536 个，每个线程用多少，就要从这里扣多少。
- **shared memory**：一共 100 KB，每个 block 用多少就扣多少，另外每个 block 还有 1 KB 由系统保留。

寄存器是最常见的限制。[limits.cu](code/ch10/limits.cu) 用一个模板生成几个寄存器用量不同的 kernel，然后用两个运行时函数查询它们实际用了多少寄存器、每个 SM 能驻留几个 256 线程的 block：

```cpp
{{#include code/ch10/limits.cu:query}}
```

```text
256 线程的 block：
 18 个寄存器  每 SM 6 个 block  48/48 个 warp
 38 个寄存器  每 SM 6 个 block  48/48 个 warp
 54 个寄存器  每 SM 4 个 block  32/48 个 warp
 70 个寄存器  每 SM 3 个 block  24/48 个 warp
106 个寄存器  每 SM 2 个 block  16/48 个 warp
```

拿 54 个寄存器那一行算一下：一个 256 线程的 block 要用 54 × 256 = 13824 个寄存器，65536 个寄存器只够放 4 个这样的 block，也就是 32 个 warp，occupancy 是 2/3。要驻留满 48 个 warp，每个线程最多只能用 65536 ÷ 1536 ≈ 42 个寄存器。（实际分配还有一定的粒度，所以边界附近的数字要以查询结果为准。）

shared memory 的算法一样：每个 block 用 32 KB，加上保留的 1 KB，100 KB 只放得下 3 个 block。

这些数字不用自己算。`cudaOccupancyMaxActiveBlocksPerMultiprocessor` 给出指定 block 大小下每个 SM 能驻留几个 block；`cudaOccupancyMaxPotentialBlockSize` 直接推荐一个让 occupancy 最高的 block 大小；Nsight Compute 的报告里也有一节 Occupancy，列出理论值、实际值和起限制作用的是哪一项。

## 10.2 访存为主的 kernel 需要很多 warp

occupancy 到底有多重要？[occupancy.cu](code/ch10/occupancy.cu) 用一个小技巧控制它：启动时给每个 block 分配一大块动态 shared memory，kernel 里根本不用，只是占着地方，让一个 SM 只放得下 1 到 6 个 block。程序用 occupancy API 搜出每种情况需要分配多少：

```cpp
{{#include code/ch10/occupancy.cu:limit}}
```

先看访存为主的拷贝（就是第 1 章那种 grid-stride 拷贝，grid 正好填满所有 SM 一轮），每个 block 256 个线程，也就是 8 个 warp：

```cpp
{{#include code/ch10/occupancy.cu:kernels}}
```

结果的前两列：

```text
驻留 warp   copy      copy4      chain1         chain4
   8/48   141 GB/s   308 GB/s   7.64 TFLOPS  15.81 TFLOPS
  16/48   238 GB/s   325 GB/s  15.86 TFLOPS  18.15 TFLOPS
  24/48   304 GB/s   325 GB/s  17.32 TFLOPS  18.36 TFLOPS
  32/48   321 GB/s   325 GB/s  17.62 TFLOPS  18.40 TFLOPS
  40/48   323 GB/s   318 GB/s  17.77 TFLOPS  18.37 TFLOPS
  48/48   322 GB/s   312 GB/s  17.77 TFLOPS  18.44 TFLOPS
```

`copy` 每个 SM 只驻留 8 个 warp 时只有 141 GB/s，要到 32 个 warp 才跑满。这和第 1 章的 Little 定律是一回事：每个线程一次只有一个读请求在路上，要跑满带宽就需要足够多的线程同时在等。

## 10.3 不一定非要靠 warp：指令级并行

再看 `copy4`。它做的事情完全一样，只是每个线程一轮先连续发出 4 个互不相干的读，再写回 4 个。8 个 warp 时它已经跑到了 308 GB/s，16 个 warp 就满了。每个线程同时有 4 个请求在路上，掩盖延迟所需的线程数就少了四分之三。

计算也是一样。`chain1` 里每次乘加都要等上一次的结果；`chain4` 有四条互不相干的链，总运算量是 `chain1` 的 4 倍，表里换算成了每秒的浮点运算次数。一次乘加从发射到结果可用需要几个时钟周期，在这期间，`chain1` 的一个 warp 什么也发射不了，调度器只能靠别的 warp 填补空档，所以它要 24 到 32 个 warp 才接近峰值；`chain4` 的一个 warp 可以连着发射四条互不依赖的乘加，16 个 warp 就基本满了。满载时的 18.4 TFLOPS 正好是这块 GPU 的理论峰值：26 个 SM × 128 条通道 × 每次乘加 2 次运算 × 2.77 GHz。

这种“一个线程内部有多条可以同时进行的指令”叫**指令级并行**（instruction-level parallelism，ILP）。掩盖延迟有两条路：靠更多的 warp（occupancy），或者靠每个 warp 内部更多的独立指令（ILP）。两者可以互相替代。

所以 occupancy 本身不是目标。第 7 章的 spill.cu 就是一个反例：`mix_tight` 为了让每个 SM 驻留 48 个 warp，把寄存器压到 40 个，结果变量溢出到 local memory，比只驻留 32 个 warp、用 56 个寄存器的 `mix_free` 慢了 6 倍多。让每个线程多用一些寄存器，把更多数据留在寄存器里、做更多独立的计算，即使 occupancy 低一些，也常常更快。高性能的矩阵乘法 kernel 往往就是这样：occupancy 不高，但每个线程在寄存器里攒着一大块结果。

## 10.4 grid 的大小：一轮和多一个 block

occupancy 说的是一个 SM 同时放几个 block。和它相关的另一个问题是整个 grid 有多少个 block。limits.cu 的后半部分用一个每个 block 计算量固定的 kernel：

```cpp
{{#include code/ch10/limits.cu:work}}
```

block 是 256 个线程时，26 个 SM 每个放 6 个，一轮能同时运行 156 个 block。分别启动正好一轮、一轮多一个、两轮、两轮多一个：

```text
256 线程的 block，一轮最多同时运行 26 × 6 = 156 个
  156 个 block     3.44 ms
  157 个 block     4.00 ms
  312 个 block     6.85 ms
  313 个 block     7.41 ms

1024 线程的 block，一轮最多同时运行 26 × 1 = 26 个
   26 个 block     2.28 ms
   27 个 block     4.55 ms
   52 个 block     4.57 ms
   53 个 block     6.83 ms
```

先看 1024 线程的情况：每个 SM 只放得下一个 block，26 个 block 正好一轮。多一个 block，它只能等第一轮结束以后单独再跑一轮，这一轮里 25 个 SM 闲着，总时间翻了一倍。这叫**尾部效应**（tail effect）。

256 线程的情况就没这么糟：多一个 block 只多花了 17%。原因是第一轮里每个 SM 挤着 6 个 block，它们分享 SM 的运算单元；多出来的那个 block 在第二轮独占一个 SM，跑得比挤在一起时快得多。这个 kernel 有 4 条独立的链，一个 block 的 8 个 warp 就能把 SM 的运算单元基本用满（10.3 节的 `chain4`），所以它大约只要第一轮六分之一的时间。

要减小尾部效应，可以让 grid 包含很多轮 block，这样最后不满的一轮占比很小；或者用 grid-stride 循环（第 3 章），grid 大小直接设为“SM 数 × 每个 SM 驻留的 block 数”，正好一轮。

## 10.5 实际怎么做

把本章的内容变成具体的做法：

- block 大小从 128 或 256 开始，是 32 的倍数。
- 用 `-Xptxas -v` 看寄存器用量和有没有 spill，用 occupancy API 或 Nsight Compute 看理论 occupancy 和限制它的因素。
- 访存为主的 kernel，occupancy 太低（比如每个 SM 只有十几个 warp）时值得想办法提高：减少寄存器或 shared memory 用量，或者让每个线程同时处理几个元素，用 ILP 补上。
- 计算为主的 kernel，不要为了 occupancy 牺牲寄存器。出现 spill 往往比 occupancy 低更糟。
- grid 要么很大，要么正好是整数轮。

最终还是要以实测为准。下一章的归约会把前面几章的内容综合起来用一遍。

## 10.6 回头看

occupancy 是一个 SM 实际驻留的 warp 数占上限的比例，由线程数、block 数、寄存器、shared memory 四个上限中最紧的那个决定。访存为主的 kernel 需要足够多的 warp 来掩盖延迟，但同样的效果也可以靠指令级并行得到：每个线程同时发出多个独立的访存或计算。所以 occupancy 是手段而不是目标，为了它把寄存器压到溢出是得不偿失的。grid 的大小也要注意，比整数轮多出一点点的 block 可能让时间大幅增加。
