# 第 36 章 GPU 和 CPU 的浮点结果为什么不一样

把一个程序移植到 GPU 上，第一件事往往是拿 GPU 的结果和原来 CPU 的结果对比，然后发现最后几位对不上。前面好几章都遇到过：第 3 章的 Mandelbrot 有 0.4% 的像素颜色不同，第 11 章的几种归约在小数点后第七位上各不相同，第 29 章的能量和 CPU 版本差在第六位。这不一定是程序错了，浮点运算本来就有很多地方会因为实现不同而产生不同的舍入。这一章把这些来源逐个测一遍：乘加合并、数学函数、编译选项、求和顺序，最后看不同精度的运算速度，以及应该怎样比较两边的结果。

## 36.1 乘加合并

第 3 章已经看到，nvcc 默认把 `a * b + c` 编译成一条 FMA 指令，乘积不经舍入直接参与加法；CPU 上的普通写法则是先把乘积舍入成 `float`，再加、再舍入。[fma.cu](code/ch36/fma.cu) 在 GPU 上分别用默认的写法和 `__fmul_rn`、`__fadd_rn` 算一遍：

```cpp
{{#include code/ch36/fma.cu:kernel}}
```

再在 CPU 上分别用先乘后加和 C 标准库的 `fmaf` 算一遍，逐个比较：

```cpp
{{#include code/ch36/fma.cu:compare}}
```

```text
$ ./fma
4194304 组 [-1,1) 之间的 a、b、c：
  CPU 先乘后加 vs GPU 默认（FMA）       不同  19.97%
  CPU 先乘后加 vs GPU __fmul_rn/__fadd_rn 不同   0.00%
  CPU fmaf     vs GPU 默认（FMA）       不同   0.00%
```

五分之一的结果不同，差别都在最后一位。只要两边做的是同样的运算（都合并，或者都不合并），结果就逐位相同。`__fmul_rn`、`__fadd_rn` 这类带舍入方式后缀的函数，可以在某一处禁止合并而不影响其他地方；`-fmad=false` 则对整个文件禁止合并（第 3 章）。

反过来，CPU 的结果也不是固定的：GCC 在目标处理器支持 FMA 指令时（比如加了 `-march=native`）默认也会做同样的合并，同一份 CPU 代码换个编译选项，结果就会变。FMA 少一次舍入，通常更准确，所以不必为了和 CPU 对上而关掉它，除非调试时需要逐位比较。

```cpp
{{#include code/ch36/mathfn.cu:apply}}
```

每个函数在一个区间上均匀取 400 多万个点，统计 GPU 和 CPU 结果不同的比例，以及各自和双精度参考值的最大误差。误差以 ulp（unit in the last place，最后一位的单位）计：0.5 ulp 表示结果就是离准确值最近的那个 `float`，这是能达到的最好结果，叫正确舍入。最后一列是 GPU 上每个函数的吞吐：

```text
$ ./mathfn
函数            和 CPU 不同   GPU 最大误差（绝对误差）    CPU 最大误差      GPU 吞吐
sinf(x)            18.32%          1.4 ulp（8.2e-08）       0.6 ulp     2654 亿次/秒
expf(x)            30.32%          1.9 ulp（6.3e+27）       0.5 ulp     7454 亿次/秒
logf(x)             3.62%          0.8 ulp（2.8e-07）       0.7 ulp     3221 亿次/秒
powf(x, 2.5f)       6.33%          0.9 ulp（6.8e-03）       0.5 ulp     1153 亿次/秒
sqrtf(x)            0.00%          0.5 ulp（3.1e-05）       0.5 ulp     5625 亿次/秒
1.0f / x            0.00%          0.5 ulp（4.7e-07）       0.5 ulp     5625 亿次/秒
次正规数：sqrtf(1e-39f) 在 GPU 上 = 3.16228e-20，CPU 上 = 3.16228e-20
```

（`expf` 的结果最大到 10³⁴ 量级，所以绝对误差看起来很大，看 ulp 就行。）

`sqrtf` 和除法两边逐位相同：IEEE 754 标准要求这两种运算正确舍入，CUDA 默认也照办。`sinf` 和 `expf` 则有 18% 和 30% 的结果和 CPU 不同，GPU 的误差最大到 1.4 和 1.9 ulp，而 glibc 的实现几乎是正确舍入的。CUDA 编程指南为每个数学函数列出了误差上限（比如 `sinf`、`expf` 是 2 ulp），实测都在范围之内。也就是说，两边的结果都是“对的”，只是 GPU 为了速度允许多差一点。

吞吐差别也很大：`powf` 每秒 1151 亿次，只有除法的五分之一，`sinf` 不到除法的一半。数学函数密集的 kernel，函数本身往往就是瓶颈。

## 36.3 -use_fast_math

如果允许更大的误差，`-use_fast_math` 能让这些函数快得多。同一个程序加上这个选项重新编译：

```text
$ nvcc -O2 -arch=native -use_fast_math mathfn.cu -o mathfn_fast && ./mathfn_fast
函数            和 CPU 不同   GPU 最大误差（绝对误差）    CPU 最大误差      GPU 吞吐
sinf(x)            88.61%  329682477.8 ulp（1.3e-06）       0.6 ulp    10114 亿次/秒
expf(x)            93.70%         61.5 ulp（2.0e+29）       0.5 ulp    10816 亿次/秒
logf(x)            48.92%      25959.2 ulp（9.0e-07）       0.7 ulp    10794 亿次/秒
powf(x, 2.5f)      91.25%         19.8 ulp（1.5e-01）       0.5 ulp     5705 亿次/秒
sqrtf(x)           17.04%          0.9 ulp（5.7e-05）       0.5 ulp    10794 亿次/秒
1.0f / x           13.22%          1.0 ulp（6.1e-07）       0.5 ulp    10794 亿次/秒
次正规数：sqrtf(1e-39f) 在 GPU 上 = 0，CPU 上 = 3.16228e-20
```

`-use_fast_math` 同时打开了几样东西：`sinf`、`expf`、`logf` 等换成对应的快速版本 `__sinf`、`__expf`、`__logf`，它们直接用硬件的特殊函数单元计算；除法和平方根改用近似算法（`-prec-div=false`、`-prec-sqrt=false`）；次正规数一律当作 0（`-ftz=true`）。

速度上，`sinf` 快了将近 4 倍，`powf` 快了 5 倍，其余几个都到了每秒一万亿次左右，这已经是这个测试循环本身的开销上限。误差则大了几个数量级。`__sinf` 的绝对误差只有 10⁻⁶ 量级，但在 sin 的零点附近，函数值本身很小，相对误差就非常大，所以按 ulp 算出了三亿多；`__logf` 在 1 附近也是同样的情况。除法和平方根的误差还在 1 ulp 以内，但也不再和 CPU 逐位相同了。最后一行是次正规数：比最小的规格化 `float`（约 1.18 × 10⁻³⁸）还小的数被当作 0，开平方得到 0 而不是 3.16 × 10⁻²⁰。

所以 `-use_fast_math` 不适合一股脑打开。比较稳妥的做法是在确实需要速度、并且误差可以接受的地方，直接调用 `__sinf`、`__expf` 这些快速函数，其余地方保持默认，就像 36.1 节对 FMA 的处理一样逐处控制。图形、神经网络的激活函数这类场合通常能容忍这些误差，科学计算里要谨慎得多，尤其是参数可能落在函数零点或者 1 附近的时候。

## 36.4 求和的顺序

浮点加法不满足结合律，(a + b) + c 和 a + (b + c) 的舍入不同。并行程序里最常见的就是求和顺序的变化。第 11 章已经比较过几种归约的误差，这里关心另一个问题：同一个程序反复运行，结果是不是每次都一样。[sum_order.cu](code/ch36/sum_order.cu) 对 400 多万个 [0, 1) 之间的 `float` 求和，CPU 上分别从前往后、从后往前和用 Kahan 补偿求和：

```text
  2097780.500000  相对误差  2.8e-06  CPU 从前往后
  2097774.500000  相对误差 -5.6e-08  CPU 从后往前
  2097774.500000  相对误差 -5.6e-08  CPU Kahan 求和
  2097773.750000  相对误差 -4.1e-07  GPU 部分和 + atomicAdd（运行 20 次，得到 3 种结果，从 2097773.250000 到 2097773.750000）
  2097774.500000  相对误差 -5.6e-08  GPU 部分和 + 固定顺序（运行 20 次，得到 1 种结果）
  2097774.500000  相对误差 -5.6e-08  GPU CUB DeviceReduce（运行 20 次，得到 1 种结果）
$ ./sum_order
  2097773.500000  相对误差 -5.3e-07  GPU 部分和 + atomicAdd（运行 20 次，得到 2 种结果，从 2097773.500000 到 2097773.750000）
  2097774.500000  相对误差 -5.6e-08  GPU 部分和 + 固定顺序（运行 20 次，得到 1 种结果）
  2097774.500000  相对误差 -5.6e-08  GPU CUB DeviceReduce（运行 20 次，得到 1 种结果）
```

和在 200 万左右时，相邻两个 `float` 相差 0.25，离参考值最近的 `float` 是 2097774.5，相对误差 −5.6 × 10⁻⁸ 就是能做到的最好结果。CPU 从前往后顺序累加的误差最大，是它的 50 倍；从后往前这次正好得到了最好的结果，Kahan 求和则是靠补偿得到的。GPU 上，按固定顺序汇总和 CUB 也得到了最好的结果，因为它们都是树形求和，每次相加的两个数大小相近。并行求和不仅不比 CPU 的顺序累加差，通常还更准确。

问题在 `atomicAdd` 那一行：20 次运行得到了 3 种不同的结果，再运行一次又不一样。各个 block 的部分和以什么顺序加到总和上，取决于哪个 block 先做完，每次运行都可能不同，舍入也就不同。误差本身不大，但结果不可重复会带来很多麻烦：调试时没法确定一个变化是改代码引起的还是运气，回归测试不能用逐位比较，深度学习训练两次得到的模型不一样。

要让结果可重复，就要固定运算顺序：像 `sum_partial` 和 `sum_final` 那样，部分和写到固定的位置，再按固定顺序合并，多一次 kernel 启动，换来逐位可重复的结果。cuBLAS 默认不使用会破坏可重复性的原子操作（`cublasSetAtomicsMode` 可以修改），深度学习框架也提供“确定性算法”的开关（比如 PyTorch 的 `torch.use_deterministic_algorithms`），代价都是一些速度。需要注意，这种可重复只在同一块 GPU、同样的启动配置下成立；换一块 SM 数不同的 GPU，CUB 选择的划分可能就不一样了。

## 36.5 精度和速度

最后看不同精度的运算速度。[fp_rate.cu](code/ch36/fp_rate.cu) 用一个模板 kernel 分别测 FP32、FP64，以及两个一组打包的 FP16（`half2`）和 BF16（`__nv_bfloat162`）的乘加吞吐，不用张量核：

```cpp
{{#include code/ch36/fp_rate.cu:kernel}}
```

```text
$ ./fp_rate
FP32        17.90 TFLOPS
FP64         0.25 TFLOPS
FP16x2      18.92 TFLOPS
BF16x2      18.83 TFLOPS
FP64 / FP32 = 1 / 72
```

FP32 跑到了 17.9 TFLOPS，接近这块 GPU 的单精度峰值。FP64 只有 0.25 TFLOPS，是单精度的 1/72，这就是第 28 章求力 kernel 用双精度慢了五倍的原因。打包的 FP16 和 BF16 和 FP32 差不多快：一条指令虽然做两个乘加，但从结果看，这类指令每周期能执行的数量只有 FP32 乘加的一半；半精度要快，得靠张量核，第 25 章和第 35 章看到半精度矩阵乘在张量核上能到 32 到 36 TFLOPS。

消费级 GPU 都是这样，双精度单元很少；A100、H100 这类数据中心 GPU 的 FP64 吞吐是 FP32 的一半。在这类 GPU 上，选择精度首先要看程序到底需要什么：大量计算用 `float`，只在会损失有效数字或者误差会累积的地方用 `double`（第 28 章的坐标相减、能量累加），再用守恒量或者和双精度参考结果的比较来确认精度够用。

## 36.6 怎样比较两边的结果

综合起来，GPU 和 CPU 结果不同的来源有：乘加是否合并、数学函数的实现、是否用了快速数学选项、求和与归约的顺序，以及有意选择的较低精度。比较两边的结果时可以这样做：

- **不要指望逐位相同**，而是比较相对误差，容差按算法估计。比如 n 个数求和，误差的量级是 n 乘以 `float` 的机器精度（约 6 × 10⁻⁸）再打一个折扣；逐元素计算的函数，可以按 ulp 比较。
- **参考值用更高的精度算**。用 CPU 的 `double` 算出的结果做参考，GPU 的 `float` 结果和 CPU 的 `float` 结果都和它比，而不是互相比。本章所有的误差都是这样算的。
- **需要逐位对比来定位错误时**，先让两边做同样的运算：GPU 用 `-fmad=false` 或 `__fmul_rn`，不用 `-use_fast_math`，归约用固定的顺序，CPU 也用同样的求和顺序。确认逻辑正确以后，再恢复这些优化。
- **结果不可重复时**，先找原子操作。浮点数的 `atomicAdd` 是最常见的来源。

## 36.7 回头看

FMA 让 GPU 默认的乘加少一次舍入，五分之一的结果和 CPU 先乘后加不同，两边做同样的运算就逐位相同。CUDA 的 `sinf`、`expf` 等函数误差在 2 ulp 以内，和 CPU 的结果有一二成不同；除法和平方根正确舍入，和 CPU 完全一致。`-use_fast_math` 让数学函数快了 1.5 到 5 倍，代价是误差大了几个数量级、次正规数变成 0，适合逐处有选择地使用。树形的并行求和通常比 CPU 的顺序累加更准确；用 `atomicAdd` 汇总的结果每次运行都可能不同，固定合并顺序就能逐位可重复。这块 GPU 的 FP64 吞吐只有 FP32 的 1/72，打包的半精度也不比 FP32 快，精度要按需要选择，并用更高精度的参考值检验。
