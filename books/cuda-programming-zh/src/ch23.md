# 第 23 章 L2 持久化与 Programmatic Dependent Launch

这一章介绍两个不改变计算本身、只影响硬件怎么安排工作的特性。L2 持久化让你告诉 GPU 哪段数据值得一直留在 L2 里；Programmatic Dependent Launch（PDL）让前后两个有依赖的 kernel 部分地重叠执行。两者都是对已经比较优化的程序再挤一点性能，效果取决于具体情况，实验也会说明它们什么时候有用、什么时候没用。

## 23.1 L2 持久化：让反复用的数据留在 L2

第 7 章量过，数据在 L2 里时拷贝带宽是 1.8 TB/s，在显存里只有 337 GB/s。一个 kernel 如果既要流式地扫过大量只用一次的数据，又要反复访问一小块数据，就会担心后者被前者挤出 L2。计算能力 8.0 起，可以从 L2 里划出一部分专门留给“持久化”的数据，再给一段地址设一个访问策略窗口，让落在窗口里的访问尽量留在这部分里。

`hitRatio` 指定窗口里有多大比例的访问按 `hitProp`（持久化）处理，其余按 `missProp` 处理。窗口比持久化区域大时，把比例设小一些，免得窗口里的数据互相挤占。用完以后要恢复：把窗口清空，用 `cudaCtxResetPersistingL2Cache` 把已经标成持久化的缓存行变回普通状态，再把限额设回 0。

查找表分别取 16、32、48 MB，每种情况依次测四种状态：

```text
$ ./l2persist 16
查找表 16 MB；L2 32 MB，最多可留给持久化数据 20 MB
   2.45 ms  不做设置
   2.44 ms  查找表设为持久化窗口
   2.45 ms  清掉窗口，但 20 MB 限额还在
   2.45 ms  限额也设回 0
$ ./l2persist 32
查找表 32 MB；L2 32 MB，最多可留给持久化数据 20 MB
   8.66 ms  不做设置
   6.10 ms  查找表设为持久化窗口
   5.97 ms  清掉窗口，但 20 MB 限额还在
   8.74 ms  限额也设回 0
$ ./l2persist 48
查找表 48 MB；L2 32 MB，最多可留给持久化数据 20 MB
  12.69 ms  不做设置
  10.25 ms  查找表设为持久化窗口
  11.66 ms  清掉窗口，但 20 MB 限额还在
  12.78 ms  限额也设回 0
```

**16 MB 的查找表，设不设都一样。** 用 ncu 看 L2 的命中率（`lts__t_sector_hit_rate.pct`），两种情况都是 79%：流过的 256 MB 数据全部落空，查表几乎全部命中。L2 默认的替换策略已经把反复访问的查找表留下了，只用一次的流式数据自己就被挤了出去，持久化没有发挥的余地。

**32 MB 的查找表和 L2 一样大，设了以后快了 30%。** 但第三行出人意料：窗口已经清掉、持久化标记也重置了，只要 20 MB 的限额还在，速度就和设了窗口时一样；限额设回 0 才回到原来的速度。也就是说，这种情况下的收益几乎全部来自“划出持久化区域”这一步本身，它改变了 L2 的替换行为。L2 具体的替换策略 NVIDIA 没有公开，这里只能报告现象。

**48 MB 的查找表比 L2 还大，窗口带来了额外的收益**（10.25 ms 对只有限额时的 11.66 ms），因为这时数据确实放不下，指定哪 20 MB 优先留着就有了意义。

结论是：工作集明显小于 L2 时，默认策略往往已经够好；工作集接近或超过 L2 时，持久化才可能有用，而且要实测，效果并不完全按文档的描述来。别忘了这是一个全局的设置，划给持久化的部分，其他 kernel 和其他 stream 就少了一块 L2 可用，用完要恢复。

## 23.2 Programmatic Dependent Launch

第 17 章看到，一串小 kernel 之间的衔接有一微秒多的开销。同一条 stream 里，后一个 kernel 要等前一个完全结束才开始。可很多 kernel 开头有一段不依赖前一个 kernel 结果的准备工作：读参数、算一些系数、读一张不变的表。PDL 允许后一个 kernel 提前开始做这部分，等真正要用前一个 kernel 的结果时再等。


两个设备端函数的分工是：`cudaTriggerProgrammaticLaunchCompletion()` 由前一个 kernel 调用，表示“下一个 kernel 可以被调度了”，它只影响调度，不保证内存可见性；`cudaGridDependencySynchronize()` 由后一个 kernel 调用，会一直等到前一个 kernel 全部完成、写的数据都可见。所以信号发得早，不会让后一个 kernel 读到不完整的数据，只会让它更早地开始准备工作。

2000 个这样的 kernel 连续执行，准备工作分别是 0、500、2000 次迭代：

```text
准备工作的迭代次数   普通启动   PDL，末尾发信号   PDL，开头发信号（每个 kernel 的平均时间）
         0             1.58 us           1.53 us             1.65 us
       500             2.80 us           2.55 us             1.83 us
      2000             8.40 us           8.09 us             6.85 us
```

没有准备工作时，PDL 没有用处。有准备工作时，信号发得越早，收益越大：在 kernel 末尾才发信号，下一个 kernel 的准备工作只能和这个 kernel 的收尾重叠，快了不到 10%；在 kernel 一开头就发信号，下一个 kernel 的 block 一有空位就开始准备，500 次迭代时每个 kernel 从 2.80 µs 降到 1.83 µs，快了三分之一。三种写法的结果完全相同，程序逐个元素核对过。

PDL 能重叠多少，还取决于 GPU 上有没有空位：前一个 kernel 的 block 已经占满了所有 SM，后一个就算获准调度，也只能等。这个例子里每个 kernel 只有 104 个 block，没有占满 GPU，所以重叠的余地比较大。

## 23.3 回头看

L2 持久化通过划出一块专用区域和设置访问窗口，让指定的数据尽量留在 L2 里。实测中，工作集小于 L2 时默认策略已经足够好，持久化毫无作用；工作集接近或超过 L2 时它能快 20% 到 30%，但收益的来源并不完全符合直觉，必须实测。PDL 让同一条 stream 里有依赖的 kernel 部分重叠：后一个 kernel 的准备工作可以在前一个结束之前进行，`cudaGridDependencySynchronize()` 保证读到的数据是完整的。信号要尽早发出，收益才明显。两者都是全局或者跨 kernel 的设置，用完要恢复，组合进程序之前要量一量。
