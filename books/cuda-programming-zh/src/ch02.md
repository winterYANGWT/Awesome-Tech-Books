# 第 2 章 第一个完整程序：分配、拷贝、启动、检查

上一章只展示了 kernel，略过了它前后的准备工作。这一章把一个完整的 CUDA 程序从头写到尾：两个向量相加，`c[i] = a[i] + b[i]`。为了能自动检查结果，输入取 `a[i] = sin²(i)`、`b[i] = cos²(i)`，每个结果都应该等于 1。

完整程序是 [vecadd.cu](code/ch02/vecadd.cu)，一共六步：

1. 在主机内存里准备输入；
2. 在显存里分配数组；
3. 把输入从主机内存拷到显存；
4. 启动 kernel；
5. 把结果拷回主机内存，检查；
6. 释放内存。

程序还在每一步后面记了时间。先把代码过一遍，最后再看时间都花在哪里。

## 2.1 两块内存，两套指针

第一步和普通 C++ 程序没有区别：

```cpp
{{#include code/ch02/vecadd.cu:host}}
```

第二、三步开始用到 CUDA：

```cpp
{{#include code/ch02/vecadd.cu:device}}
```

（`CHECK` 是检查返回值的宏，2.5 节再讲。）

GPU 有自己的内存，就是显卡上那 8 GB GDDR7 显存，和主机内存是两块物理上分开的存储器。`cudaMalloc` 在显存里分配空间，把地址写进 `d_a`。这个地址存在一个普通的 `float*` 变量里，编译器看不出它和 `malloc` 返回的指针有什么不同，但它指向的是显存，主机代码不能直接读写。为了不把两种指针弄混，习惯上主机指针加 `h_` 前缀，显存指针加 `d_` 前缀。

如果在主机代码里直接读显存指针，会怎么样？[mistakes.cu](code/ch02/mistakes.cu) 里的第一个错误就是这样：

```cpp
{{#include code/ch02/mistakes.cu:deref}}
```

```text
$ ./mistakes deref
d = 0x1000ac00000
Segmentation fault (core dumped)
```

指针本身可以打印出来，就是一个数，但一读它指向的内容，程序立刻崩溃。CPU 的页表里没有这个地址对应的主机内存。

反过来，kernel 能不能直接用 `malloc` 得到的主机指针？传统上也不行。不过在这台机器上它确实能工作：Linux 下较新的 NVIDIA 开源内核驱动支持 HMM（heterogeneous memory management），GPU 可以通过它访问普通的主机内存（`nvidia-smi -q` 里的 Addressing Mode 一项会显示 HMM）。但 Windows、WSL 和较旧的驱动上没有这个能力，而且这样访问的代价不小，第 16 章会实测。写可移植的程序，仍然应该把数据显式放进显存。

`cudaMemcpy` 的参数顺序和 C 的 `memcpy` 一样，目标在前，源在后，最后一个参数说明方向：`cudaMemcpyHostToDevice` 从主机拷到显存，`cudaMemcpyDeviceToHost` 反过来。方向写反了会怎样？mistakes.cu 的第三个错误故意把一次主机到显存的拷贝写成了 `cudaMemcpyDeviceToHost`：

```cpp
{{#include code/ch02/mistakes.cu:kind}}
```

```text
$ ./mistakes kind
拷贝返回成功，d[0] = 2.000000
```

居然拷对了。原因是 64 位系统上 CUDA 使用统一虚拟地址（unified virtual addressing，UVA）：主机内存和每块 GPU 的显存占用同一个虚拟地址空间里互不重叠的区域，驱动看地址就知道它在哪块内存上，于是忽略了写错的方向。但文档并没有承诺方向写错时会这样处理，这只是“在我的机器上能跑”。如果想让驱动自己判断方向，就明确地传 `cudaMemcpyDefault`；否则就把方向写对。

## 2.2 启动 kernel

kernel 和上一章的 saxpy 是一个样子：

```cpp
{{#include code/ch02/vecadd.cu:kernel}}
```

第四步启动它，然后等它跑完：

```cpp
{{#include code/ch02/vecadd.cu:launch}}
```

`add<<<blocks, threads>>>(...)` 让 GPU 开出 `blocks` 个 block、每个 block `threads` 个线程，一起执行 `add`。这个调用一提交就返回，不等 kernel 跑完，host 可以接着做别的事。所以它也没有返回值，启动时出的错要靠紧接着的 `cudaGetLastError()` 去取。

`cudaDeviceSynchronize()` 让 host 停下来，等 GPU 上已经提交的所有工作做完。kernel 执行过程中出的错，比如越界访问，要到这里才会报告出来，第 5 章会专门讲这种“迟到”的错误。这个程序里其实可以省掉这次同步，因为第五步的 `cudaMemcpy` 本身就会等 kernel 做完才开始拷贝（第 13 章会解释原因）。这里显式写出来，是为了把 kernel 执行期间的错误和拷贝的错误分开报告，也为了单独量出 kernel 的时间。

启动时会出什么错？一个 block 最多 1024 个线程。mistakes.cu 的第二个错误开了 2048 个：

```cpp
{{#include code/ch02/mistakes.cu:config}}
```

```text
$ ./mistakes config
不检查：h[0] = 0.000000
mistakes.cu:47: cudaErrorInvalidValue (invalid argument)
```

第一次启动不做检查，程序没有任何提示，只是结果不对：kernel 根本没有执行，数组还是 `cudaMemset` 清零后的样子。在真实的程序里，这种错误可能要过很久才被发现。第二次在启动后调用 `cudaGetLastError()`，问题马上就暴露了。CUDA 13.3 把这类配置错误报告为 `cudaErrorInvalidValue`，单看 “invalid argument” 不好猜原因，看到它出现在 kernel 启动之后，首先就该检查 block 和 grid 的大小。

最后两步把结果拷回来、检查、释放：

```cpp

```

## 2.3 时间都花在哪里

程序的输出：

```text
   79.291 ms  准备主机数据
  157.595 ms  cudaMalloc d_a（程序里第一个 CUDA 调用）
    0.049 ms  cudaMalloc d_b、d_c
   14.844 ms  cudaMemcpy 两个输入，主机 -> 显存
    0.121 ms  启动 kernel（第一次）
    0.524 ms  cudaDeviceSynchronize，等 kernel 跑完
    0.003 ms  再启动一次 kernel
    0.577 ms  cudaDeviceSynchronize
   13.808 ms  cudaMemcpy 结果，显存 -> 主机
0 个元素不等于 1
```

逐行看。

**第一个 CUDA 调用花了 158 ms**，后面两次 `cudaMalloc` 加起来只要 0.05 ms。时间并没有花在分配上，而是花在初始化上：程序里第一次调用 CUDA 时，驱动要打开设备、为这个进程在 GPU 上建立一个 context（GPU 侧的地址空间、各种运行时状态都挂在它下面），这一步在这台机器上要 150 到 250 ms。哪个调用排在第一个，这笔时间就算在谁头上。所以做性能测量时，要先用一个无关紧要的调用把初始化做掉，常见的写法是在 `main` 开头调用 `cudaSetDevice(0)` 或者 `cudaFree(0)`，否则第一次测到的时间会莫名其妙地大。

**两个 64 MiB 的输入拷上去花了 14.8 ms**，合 9 GB/s 左右。普通 `malloc` 分配的内存拷起来比 pinned 内存慢，第 13 章会解释原因并换成更快的写法。

**第一次启动 kernel 用了 0.12 ms，第二次只用了 3 微秒。** 多出的时间主要是在把 kernel 的机器码装到 GPU 上。CUDA 默认在第一次用到某个 kernel 时才加载它（lazy loading），设置环境变量 `CUDA_MODULE_LOADING=EAGER` 改成启动时全部加载，第一次启动就降到 0.04 ms 左右，相应地初始化变长。第 4 章会细讲 kernel 代码是怎么编译、打包和加载的。注意这两行量的都是启动调用返回所用的时间，不是 kernel 执行的时间。

**kernel 本身大约 0.55 ms。** 第二次的 0.58 ms 里还包含了同步本身的一点延迟，按它算，三个 64 MiB 的数组读两个写一个，合 350 GB/s 左右，和上一章 saxpy 的带宽差不多。（第一次同步只用了 0.52 ms，是因为 kernel 在“启动”那一行的计时里就已经开始执行了。）

**结果拷回来又花了 13.8 ms。** 和上一章的结论一样：数据在 PCIe 上来回一趟要将近 29 ms，kernel 只占 0.55 ms。这个程序作为“第一个 CUDA 程序”很合适，作为 GPU 加速的例子就不合格了。

## 2.4 kernel 的时间该怎么量

上面用主机时钟量 kernel，是靠“启动之后马上同步”凑出来的：同步返回时 kernel 肯定已经结束，两次计时之差就包含了 kernel 的执行时间。这个办法在简单程序里够用，但量到的时间里混着启动开销和同步本身的延迟，而且一旦 host 在启动和同步之间还做了别的事，就不准了。

更准确的办法有两个。一是 CUDA event：在 kernel 前后各插一个 event，GPU 执行到它时记下时间戳，量的是 GPU 上的时间，第 1 章的 threads.cu 就是这样量的，第 14 章会细讲。二是用 Nsight Systems 这样的工具直接看时间线，第 13 章的图 13.1 就是这么来的。

## 2.5 CHECK 宏

几乎每个 CUDA API 都返回一个 `cudaError_t`，成功时是 `cudaSuccess`。本书的程序都用同一个宏检查返回值：

```cpp
{{#include code/ch02/vecadd.cu:check}}
```

出错时它打印出错的文件和行号、错误名和说明，然后退出。`do { ... } while (0)` 是让宏在 `if` 语句里也能像一条普通语句那样使用的惯用写法。

教学程序遇到错误直接退出就行。真实的项目里，通常会把错误转换成异常或者返回给上层，但原则一样：每个 CUDA 调用的返回值都要检查，kernel 启动之后要调用 `cudaGetLastError()`。CUDA 的错误还有一个特点：kernel 执行中出现非法地址访问这类严重错误以后，这个进程的 context 就坏了，后续所有 CUDA 调用都会返回同一个错误，所以第一个报告错误的地方不一定是真正出问题的地方。上面那种配置错误不属于这一类，它只让那一次启动失败。第 5 章会讲怎么找到真正出错的那一行。

## 2.6 回头看

一个 CUDA 程序的骨架就是这六步：准备数据、分配显存、拷上去、启动 kernel、拷回来、释放。几个要记住的点：主机指针和显存指针类型相同，但不能混用；kernel 启动是异步的，没有返回值，要用 `cudaGetLastError()` 检查；第一次 CUDA 调用要付一笔一两百毫秒的初始化费用；对这种算得很少的 kernel，几乎所有时间都花在 PCIe 上。

## 2.7 练习

1. 在 `main` 的开头加一行 `CHECK(cudaFree(0));`，再运行。初始化的时间现在算到谁头上了？`cudaMalloc d_a` 那一行变成多少？
2. 把 `n` 改成 `1 << 10`（1024 个元素）。哪几步的时间几乎不变？由此估计一次 `cudaMemcpy` 和一次 kernel 启动的固定开销各是多少。
3. 把 `threads` 依次改成 1024 和 1025，看看哪个能正常运行，报的是什么错误。
4. 把 kernel 里的 `if (i < n)` 删掉，再把 `n` 改成一个不是 256 的倍数的数，比如 `16 * 1024 * 1024 + 1`。程序会崩溃吗？结果对吗？记下你的观察，第 5 章会用工具找出这里到底发生了什么。
