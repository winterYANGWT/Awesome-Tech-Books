# 第 11 章 归约：从最直接的写法到跑满带宽

前几章分别讲了 warp、内存层次、合并访问、shared memory 和 occupancy。这一章把它们放到一个具体的问题上综合运用：把 6400 万个 `float` 加起来。求和、求最大值、求平均这类把一大堆数变成一个数的操作叫**归约**（reduction），是并行计算里最基本的操作之一。它看起来简单，但并行化时要面对一个真正的困难：所有线程的结果最终要汇到一处。

256 MB 的数据，只读不写，按第 8 章的估算，时间下限大约是 0.7 ms。完整程序是 [reduce.cu](code/ch11/reduce.cu)，所有版本的结果都和 CPU 上用 `double` 算出的参考值比较。先看最终的成绩单：

```text
0 atomicAdd              79.016 ms      3 GB/s  相对误差 5.0e-01
1 树形，取模         1.774 ms    151 GB/s  相对误差 3.2e-05
2 树形，前一半干活    1.734 ms    155 GB/s  相对误差 3.1e-05
3 先在寄存器里累加    0.766 ms    350 GB/s  相对误差 8.7e-08
4 warp shuffle            0.765 ms    351 GB/s  相对误差 3.3e-07
5 float4                  0.729 ms    368 GB/s  相对误差 1.5e-07
CUB DeviceReduce::Sum     0.728 ms    369 GB/s  相对误差 3.3e-08
```

下面一个一个版本地看。

## 11.1 版本 0：大家都往一个地方加

最直接的写法：每个线程把自己负责的元素加到结果上。多个线程同时修改同一个变量，必须用原子操作，`atomicAdd` 保证“读出、相加、写回”作为一个整体完成，不会被别的线程打断：

```cpp
{{#include code/ch11/reduce.cu:v0}}
```

79 ms，比下限慢了一百多倍。6400 万次原子操作全打在同一个地址上，硬件只能一个一个地处理，并行完全没有了。

更糟的是结果：相对误差 0.5，算出来的和只有正确值的一半。这不是原子操作的问题，而是浮点数的问题。`float` 只有 24 位有效数字，当累加的和超过 2²⁴（约 1678 万）以后，相邻两个可表示的数之间相差 2，再往上加一个小于 1 的数，结果舍入回原值，等于没加。这 6400 万个数的平均值约 0.5，和应该是 3200 多万，可加到 1678 万左右就再也加不上去了。按顺序把大量的数累加到同一个 `float` 上，在 CPU 上也会遇到同样的问题。下面的树形求和顺带解决了它：每次相加的两个数大小相近，误差小得多。

## 11.2 版本 1 和 2：block 内的树形求和

改进的思路是分层：每个 block 先在内部求出自己那 256 个元素的和，最后每个 block 只做一次原子加。block 内部用 shared memory 两两相加：第一轮把相邻的两个数加起来，256 个数变 128 个；第二轮再两两相加，变 64 个；8 轮以后只剩一个。

```cpp
{{#include code/ch11/reduce.cu:v1}}
```

每一轮之后都要 `__syncthreads()`，因为下一轮要用到别的线程这一轮的结果。时间降到 1.77 ms，快了 45 倍。

这个版本有教科书上常说的两个毛病。一是 warp 发散：第一轮只有偶数号线程干活，第二轮只有 4 的倍数号线程干活，每个 warp 里都是有的干活、有的闲着。二是 bank conflict：干活的线程隔得越来越远，访问的 shared memory 落在同一个 bank 上。标准的改法是让前一半线程干活，每轮把后一半加到前一半上：

```cpp
{{#include code/ch11/reduce.cu:v2}}
```

这样干活的线程总是连续的，前几轮整个 warp 要么都干活、要么都不干，访问的地址也是连续的。可结果只快了 2%。用 ncu 看几个计数器：

```text
kernel            执行的 warp 指令数   每条指令的线程数   shared bank conflict
reduce_atomic           31,457,280        32.00                0
reduce_tree            251,396,096        31.77          210,094
reduce_tree_seq        217,841,664        31.74           90,975
reduce_stride           12,718,788        32.00               68
reduce_shuffle          12,633,612        32.00               24
reduce_vec4              4,769,292        32.00               24
```

版本 2 的 bank conflict 少了一半多，指令也少了 13%，但这两个版本共同的问题远比这些大：执行了两亿多条 warp 指令，平均每个元素要三条多。每 256 个元素就要做 8 轮相加和 8 次同步，还有 26 万个 block 要调度、要各做一次原子加。这些开销摊到每个元素上，比读这个元素本身贵得多。（每条指令的线程数接近 32，是因为编译器把短小的 `if` 编成了带条件的指令，第 6 章提过。）

这是一个很好的提醒：ncu 报告的问题不一定是瓶颈。消除 bank conflict 和发散，计数器变好看了，时间却几乎不动。先找到真正的瓶颈，第 12 章会给出系统的方法。

## 11.3 版本 3：先在寄存器里累加

既然每个元素分摊的 block 内归约开销太大，那就让每个线程先多处理一些元素。grid 只开满一轮（26 个 SM × 每个 SM 6 个 block），每个线程用 grid-stride 循环（第 3 章）把很多个元素在寄存器里累加起来，最后才做一次 block 内的归约：

```cpp
{{#include code/ch11/reduce.cu:v3}}
```

6400 万个元素分给 4 万个线程，每个线程要累加 1600 个左右。循环里每个元素只需要一次读和一次加法，block 内的归约和原子操作在整个 kernel 里只有 156 次。指令数从两亿多降到 1270 万，时间降到 0.77 ms，达到了 350 GB/s。到这一步，kernel 已经被显存带宽卡住了。

这个版本的精度也是最好的之一：每个线程累加的 1600 个数不算多，然后再树形相加。

## 11.4 版本 4：warp shuffle

block 内的归约还可以写得更简洁。第 6 章提到过 warp 级函数：同一个 warp 的线程可以用 `__shfl_down_sync` 直接读别的线程寄存器里的值，不经过 shared memory，也不需要 `__syncthreads()`：

```cpp
{{#include code/ch11/reduce.cu:v4}}
```

`__shfl_down_sync(0xffffffff, v, offset)` 让每个线程拿到比自己的 lane 编号大 `offset` 的那个线程的 `v`，第一个参数是参与的线程掩码，这里是全部 32 个。`offset` 依次取 16、8、4、2、1，5 轮以后 lane 0 手里就是整个 warp 的和。block 里的 8 个 warp 各得到一个和，写进 shared memory，再由第一个 warp 用同样的办法把这 8 个数加起来。整个 block 只需要一次 `__syncthreads()`。

时间和版本 3 一样，因为 kernel 已经被带宽卡住，block 内归约本来就只占很小一部分。但这种写法更短、更不容易出错，是现在写归约的标准方式。

## 11.5 版本 5：一次读 16 字节

最后一点余量来自读取本身。版本 5 把输入当作 `float4` 数组，每次读 16 字节：

```cpp
{{#include code/ch11/reduce.cu:v5}}
```

指令数又少了一大半（循环的次数只有原来的四分之一），而且每轮有 4 个互不相干的加法，正是第 10 章说的指令级并行。时间降到 0.73 ms，368 GB/s。这比第 1 章拷贝测到的 336 GB/s 还高，因为拷贝要读一遍、写一遍，显存在读写之间切换有一些损耗，这里只读不写。这个版本要求元素个数是 4 的倍数、数组按 16 字节对齐（`cudaMalloc` 返回的地址总是对齐的），通用的实现还要单独处理末尾剩下的几个元素。

## 11.6 和库比一比

CUB 是 CUDA 自带的并行算法库，`cub::DeviceReduce::Sum` 就是现成的归约：

```cpp
{{#include code/ch11/reduce.cu:cub}}
```

CUB 的接口有点特别：第一次调用时传入空指针，它只告诉你需要多大的临时空间；分配好以后第二次调用才真正计算。成绩是 0.728 ms，369 GB/s，和我们一步步优化出来的版本 5 一样快，精度还更好一些。实际工作中，归约、扫描、排序这类基本操作应该直接用 CUB 或 Thrust（第 24 章），自己写的意义在于理解它们为什么快，以及在库不能直接用的时候（比如归约要和别的计算融合在同一个 kernel 里）知道怎么写。

## 11.7 回头看

从 79 ms 到 0.73 ms，最大的两步是：从全局原子操作改成 block 内先归约（45 倍），以及让每个线程先在寄存器里累加很多元素（2.3 倍）。教科书上常提的消除发散和 bank conflict，在这里几乎没有效果，因为它们不是瓶颈。warp shuffle 和向量化读取则让代码更简洁、榨出了最后一点带宽。几个版本的结果在小数点后第七位上各不相同，因为浮点加法的顺序不同，结果就不同，第 36 章会专门讨论这一点。

## 11.8 练习

1. 把版本 0 的累加改成 `double`（`atomicAdd` 有 `double` 版本），误差变成多少？时间呢？
2. 版本 3 里 grid 开的是一轮。把它改成 2 轮、4 轮、64 轮，时间和误差怎么变？
3. 改写版本 4，让它求数组的最大值而不是和。`__shfl_down_sync` 那一行要怎么改？最后的 `atomicAdd` 要换成什么？（提示：`float` 没有 `atomicMax`，可以利用非负浮点数的位模式和整数大小顺序一致这一点。）
4. 用 ncu 的 `dram__throughput.avg.pct_of_peak_sustained_elapsed` 指标看看版本 1、3、5 分别用到了显存带宽的多少（如果这个指标在你的 GPU 上不可用，用 `ncu --section MemoryWorkloadAnalysis` 看报告里的带宽数字）。
