# 第 36 章 Driver JIT/linker reference：从 PTX 到 module 的运行时装配路径

## 36.1 问题的由来

[第 32 章](ch032.md)已经给出 Driver API 的最小路径：device、context、module、function、launch。Driver API 还提供一组更底层的能力：运行时 link PTX/cubin/fatbin、设置 JIT options、读取 info/error log、构造 launch parameter buffer。

这些内容不适合放进入门的 Driver API 章节，但对插件系统、JIT kernel、DSL 编译器、运行时生成 PTX 的框架很重要。

## 36.2 核心模型

运行时装配分两段。第一段是链接：用 `cuLinkCreate` 带上一组 `CU_JIT_*` 选项创建 link state，用 `cuLinkAddData` 或 `cuLinkAddFile` 加入 PTX、cubin 或 fatbin，再由 `cuLinkComplete` 输出一份链接好的 cubin image。第二段是加载和执行：`cuModuleLoadData` 加载这份 image，`cuModuleGetFunction` 取出 kernel，`cuLaunchKernel` 启动。

Driver linker 把运行时输入装配成可加载 image；module/function API 再负责执行。

## 36.3 详解

`cuModuleLoad` 适合直接加载已有 cubin/fatbin/PTX 文件。`cuModuleLoadData` 和 linker API 适合把内存中的 PTX 或 cubin 动态装配。

JIT options 最常见用途是：

- 指定目标架构或从当前 context 推断目标。
- 收集 info log 和 error log。
- 统计 wall time。
- 控制 binary loader thread count。

Launch param buffer 是旧式或底层 launch 路径中会看到的概念。现代 `cuLaunchKernel` 通常用 `void** kernelParams`，但它的 `extra` 参数仍然接受 `CU_LAUNCH_PARAM_BUFFER_POINTER`、`CU_LAUNCH_PARAM_BUFFER_SIZE`、`CU_LAUNCH_PARAM_END` 这类 token，阅读底层代码时需要能认出来。

## 36.4 代码示例

运行时 link PTX：

```cpp
CUjit_option options[6];
void* values[6];
char info_log[8192];
char error_log[8192];
options[0] = CU_JIT_INFO_LOG_BUFFER;
values[0] = info_log;
options[1] = CU_JIT_INFO_LOG_BUFFER_SIZE_BYTES;
values[1] = reinterpret_cast<void*>(sizeof(info_log));
options[2] = CU_JIT_ERROR_LOG_BUFFER;
values[2] = error_log;
options[3] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[3] = reinterpret_cast<void*>(sizeof(error_log));
options[4] = CU_JIT_WALL_TIME;
values[4] = nullptr;  // 输出项：driver 把耗时（float，毫秒）直接写进这个槽位
options[5] = CU_JIT_TARGET_FROM_CUCONTEXT;
values[5] = nullptr;
CUlinkState link_state{};
cuLinkCreate(6, options, values, &link_state);
cuLinkAddData(link_state,
              CU_JIT_INPUT_PTX,
              ptx_buffer,
              ptx_size,
              "generated.ptx",
              0,
              nullptr,
              nullptr);
void* cubin = nullptr;
size_t cubin_size = 0;
cuLinkComplete(link_state, &cubin, &cubin_size);
CUmodule module{};
cuModuleLoadData(&module, cubin);  // cubin 归 link_state 所有，要在销毁前加载
float wall_ms = 0.0f;
std::memcpy(&wall_ms, &values[4], sizeof(wall_ms));  // 需要 <cstring>
cuLinkDestroy(link_state);         // module 已经加载，cubin 随 link state 一起释放
CUfunction fn{};
cuModuleGetFunction(&fn, module, "kernel_name");
```

两处容易写错。第一，`cuLinkComplete` 返回的 cubin 指针归 link state 所有，不需要也不能自己释放；它在 `cuLinkDestroy` 时随 link state 一起释放，所以必须先 `cuModuleLoadData`，再销毁 link state。module 加载完成后就不再依赖这块内存。第二，`CU_JIT_WALL_TIME` 是输出型选项：driver 把耗时直接写进 `values` 数组对应的槽位，而不是写到槽位里指针所指的地方，所以这里放 `nullptr`，link 完成后再从槽位里取出 float。有输出型选项时，`values` 数组要一直有效，直到 link state 销毁。

Kernel params：

```cpp
void* args[] = { &d_out, &d_in, &n };
cuLaunchKernel(fn,
               grid_x, grid_y, grid_z,
               block_x, block_y, block_z,
               shared_bytes,
               stream,
               args,
               nullptr);
```

Launch param buffer tokens：

```cpp
void* config[] = {
    CU_LAUNCH_PARAM_BUFFER_POINTER, param_buffer,
    CU_LAUNCH_PARAM_BUFFER_SIZE,    &param_size,
    CU_LAUNCH_PARAM_END
};
```

## 36.5 工程判断

| 需求 | 机制 | 注意点 |
|---|---|---|
| 直接加载 cubin/fatbin/PTX 文件 | `cuModuleLoad` | 文件路径和 JIT 行为要可控 |
| 加载内存中的 image | `cuModuleLoadData` | image 生命周期要保持到加载完成 |
| 动态 link 多段 PTX/cubin | `cuLink*` | log buffer 和 target option 要设置 |
| 诊断 JIT 失败 | `CU_JIT_ERROR_LOG_BUFFER` | buffer size 要足够 |
| 获取性能/耗时 | `CU_JIT_WALL_TIME` | 只测 JIT/link 阶段 |
| 手写底层 launch config | launch param buffer | 对齐、size 和参数顺序易错 |

## 36.6 API 与要点速查

Driver linker API：

| API | 作用 |
|---|---|
| `cuLinkCreate` | 创建 link state |
| `cuLinkAddData` | 添加内存中的 PTX/cubin/fatbin |
| `cuLinkAddFile` | 添加文件输入 |
| `cuLinkComplete` | 完成 link，得到 cubin image |
| `cuLinkDestroy` | 销毁 link state |

JIT input / options：

| Token | 作用 |
|---|---|
| `CU_JIT_INPUT_PTX` | 输入 PTX |
| `CU_JIT_INPUT_CUBIN` | 输入 cubin |
| `CU_JIT_INPUT_FATBINARY` | 输入 fatbin |
| `CU_JIT_TARGET_FROM_CUCONTEXT` | 从当前 context 推断目标 |
| `CU_JIT_INFO_LOG_BUFFER` | info log buffer |
| `CU_JIT_INFO_LOG_BUFFER_SIZE_BYTES` | info log buffer size |
| `CU_JIT_ERROR_LOG_BUFFER` | error log buffer |
| `CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES` | error log buffer size |
| `CU_JIT_LOG_VERBOSE` | verbose log |
| `CU_JIT_WALL_TIME` | JIT wall time |
| `CU_JIT_BINARY_LOADER_THREAD_COUNT` | binary loader thread count |

Driver object tokens：

| Token | 说明 |
|---|---|
| `CUdevice` | device handle |
| `CUcontext` | context handle |
| `CUmodule` | module |
| `CUfunction` | function |
| `CUstream` | stream |
| `CUDA_ERROR_INVALID_CONTEXT` | context 错误 |

Launch param buffer：

| Token | 作用 |
|---|---|
| `CU_LAUNCH_PARAM_BUFFER_POINTER` | 参数缓冲地址 |
| `CU_LAUNCH_PARAM_BUFFER_SIZE` | 参数缓冲大小 |
| `CU_LAUNCH_PARAM_END` | config 终止 |
| `ALIGN_UP` | 底层示例代码里常见的自定义宏（不是 CUDA API），把偏移按参数的对齐要求向上取整 |
| `ADD_TO_PARAM_BUFFER` | 同样是自定义宏，按对齐后的偏移把参数写入缓冲 |

## 36.7 小结

读完本章，你应该能够：

- 把 Driver API 从“加载模块”扩展到“运行时 link/JIT”。
- 知道 `CU_JIT_*` options 解决哪些问题。
- 读懂底层 launch param buffer 代码。
- 为 DSL/JIT/插件型 CUDA 程序设计 Driver API 装配路径。
