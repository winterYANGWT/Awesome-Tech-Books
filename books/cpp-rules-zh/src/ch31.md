# 第 31 章 协程与 std::execution

订单服务要读配置、查库存、写审计，三步都是异步的。用回调写，控制流会散成几层：

```cpp
load_config([&](Config cfg) {
    fetch_stock(cfg, [&](Stock s) {
        write_audit(s, [&](Status st) {
            reply(st);
        });
    });
});
```

每多一步就多一层缩进，错误处理要在每一层各写一遍，循环和提前返回也变得别扭。换成一个线程从头到尾阻塞着做，代码是好看了，可每个请求占一个线程，几千个并发连接就把线程和栈内存吃光。C++20 的协程想解决的就是这个矛盾：函数体可以写成顺序执行的样式，遇到还没好的数据就在中间暂停，把线程让出来，等数据到了再从原地继续。

协程不是线程，也不是调度器。语言只提供“暂停—恢复”的机制和一套定制点，谁来恢复、在哪个线程恢复、什么时候取消，仍要由库或框架决定。本章按四层往下走：31.1 看三个关键字怎样把函数变成状态机，31.2 拆开 `co_await` 和 `promise_type` 的调用顺序，31.3 用生成器说明惰性序列和线程的区别，31.4 看 C++26 的 `std::execution` 想统一什么、在它可用之前项目怎么分工。本章没有对应的原书条目，讲的都是 C++20 以后新增的语言和库设施；原书里与异步、任务相关的建议在第 30 章讨论。

## 31.1 三个关键字把函数变成状态机

`before creating the task` 之后，函数体一行都没执行：`initial_suspend()` 返回 `std::suspend_always`，协程在进入函数体之前就停住了。第一次 `resume()` 才让它从 `step = 0` 开始跑，到第一个 `co_await` 处暂停，控制权回到 `main`；第二次恢复时，`step` 已经是 1，说明这个局部变量没有随函数调用栈消失，而是活在协程帧里。第三次恢复执行到 `co_return`，停在 `final_suspend()`，此时 `done()` 从 0 变成 1。之后就不能再 `resume()` 了——对已经结束的协程调用 `resume()` 是未定义行为（undefined behavior，UB）。

编译器怎么知道该找哪个 `promise_type`？它把返回类型和参数类型交给 `std::coroutine_traits`，默认实现去找返回类型里嵌套的 `promise_type`。所以 `Task`、`Countdown` 这些类型只要内嵌一个 `promise_type` 就能当协程返回类型；也可以特化 `std::coroutine_traits`，让一个原本不是协程类型的返回类型（比如自己库里的 `Future<T>`）接上自己的 promise。帧的布局由编译器决定，哪些局部变量放进帧、哪些留在寄存器里也由它决定；能跨挂起点使用的变量必须在帧里，只在两个挂起点之间短暂使用的变量可以不留。标准不暴露帧的大小和字段顺序，调试器看到的帧布局、不同编译器之间的帧大小都可能不同。

`initial_suspend` 返回 `suspend_always` 还是 `suspend_never`，决定了协程是“懒惰”还是“急切”。`Task` 和生成器通常用 `suspend_always`：创建返回对象时函数体不跑，调用方决定什么时候启动；31.1 那个悬垂例子为了先执行到 `co_await` 再借出指针，用的是 `suspend_never`。急切启动适合“构造即开始”的场景，但调用方在构造函数里创建立即启动的协程时，协程体可能在对象构造完成前就运行，不能让它去碰还没构造好的成员；懒惰启动把“什么时候开始”交给调用方，也把“创建了却从不启动”的泄漏风险交给了调用方。

三个关键字的分工可以这样记：`co_await` 在表达式处暂停，等一个 awaiter 就绪；`co_yield` 把一个值交给调用方再暂停，标准规定它等价于 `co_await promise.yield_value(值)`；`co_return` 结束协程，调用 promise 的 `return_void()` 或 `return_value(...)`；函数体自然走到末尾等同于 `co_return;`（要求 promise 有 `return_void`）。一个函数只要出现其中任何一个关键字，就是协程，返回类型必须有匹配的 `promise_type`，否则编译不过。返回类型不是“协程类型”而写了 `co_return`，同样过不了编译。

帧分配也不是“每次调用都一定 new 一次”。标准允许编译器在能证明协程帧不会逃逸时省略这次分配（通常的做法是直接复用调用者的栈空间）；是否省略、什么条件下省略由实现决定。所以不要用“分配次数”来判断程序对不对，也不要把自定义 `operator new` 当成稳定的观测点；能依赖的是“帧至少活到协程结束”，以及自定义分配器必须和对应的 `operator delete` 配对。协程的恢复是一次间接调用，帧访问又多一层指针，和普通函数调用相比不是零成本；它的价值在于把等待期间的线程让出来，而不是让单次调用更快。

除了引用参数，还有几种同类的借用：成员协程保存 `this`，对象析构后恢复就悬垂；lambda 协程按引用捕获局部变量，闭包先销毁、协程后恢复，捕获的引用就没了；把容器元素的指针或 `string_view` 存进帧，容器扩容或清空后也会悬垂。判断方法很直接：问“这个地址在挂起期间由谁保证有效”。答案不能是“调用方应该还在”，除非接口把这条约束写成了类型或文档，并有测试守着。`clang-tidy` 21 的 `cppcoreguidelines-avoid-reference-coroutine-parameters` 会把引用参数标出来（本机实测），但它只能提示风险，不能证明数据一定活得够久。

## 31.2 promise_type 与 awaiter：co_await 到底做了什么

`co_await` 看起来像“等一个值”，编译器实际做的是一串固定调用。它先取得表达式对应的 awaiter（等待器）——可以是表达式自己的 `operator co_await`，也可以由 promise 的 `await_transform` 改写——然后依次问三个问题：现在能拿到结果吗（`await_ready`）？不能的话，挂起前要做什么（`await_suspend`）？恢复之后，结果怎么取（`await_resume`）？下面这个 awaiter 在三个函数里各打印一行：

第一个 `Probe` 的 `await_ready` 返回 `false`，于是调用 `await_suspend`，协程停住，控制权回到 `main`；下一次 `resume()` 从挂起点继续，先执行 `await_resume` 得到 42，再执行 `co_await` 后面的语句。第二个 `Probe` 的 `await_ready` 返回 `true`，`await_suspend` 根本没被调用，`await_resume` 紧接着执行，协程没有真正挂起。`await_suspend` 的返回类型决定挂起后发生什么：返回 `void` 就是普通挂起；返回 `bool` 时，`false` 表示“别挂了，马上继续”，`true` 表示挂起；返回一个 `coroutine_handle<>` 表示对称转移（symmetric transfer），直接去恢复那个协程，而不是层层返回到调用者。

`co_await` 后面的表达式不一定是 awaiter 本身。编译器先看 promise 有没有 `await_transform`，有就先把表达式改写成它的返回值；没有的话，再找成员或非成员的 `operator co_await`。`std::suspend_always` 和 `std::suspend_never` 本身就是 awaiter，所以可以直接 `co_await`。库作者常用 `await_transform` 把任意 `future`、回调或第三方类型包成 awaiter，把适配逻辑集中到 promise 里，而不必给每个类型加 `operator co_await`。`await_ready` 只应做快速检查，不要在里面做真正的等待；`await_resume` 可以抛异常，异常会从 `co_await` 表达式抛出；如果协程体没有捕获它，最后交给 `unhandled_exception`。`await_suspend` 里则要小心：它运行在“已经挂起、但还没把控制权交出去”的窗口里，把句柄放进队列、注册回调都可以，但不要在这里同步恢复同一个协程，否则会重入。

`promise_type`（承诺对象类型）是协程和外界之间的约定。编译器要求它提供 `get_return_object()` 产生调用方拿到的返回对象、`initial_suspend()` 决定函数体是否立刻开始、`final_suspend()` 决定结束时的动作、`return_void()` 或 `return_value(v)` 接收 `co_return`、`unhandled_exception()` 接收协程体内逃出的异常。标准库主要给了 `coroutine_handle`、`suspend_always`、`suspend_never`、`noop_coroutine` 这些零件，没有给通用的 `Task`。约定对不上就编译不过，比如 promise 只写了 `return_void`，函数却 `co_return 1`：

`load_order` 执行到 `co_await parse_id(raw)` 时，`parse_id` 还没开始（它的 `initial_suspend` 也是 `suspend_always`）。`Task::await_suspend` 把 `load_order` 的句柄记进 `parse_id` 的 promise，然后返回 `parse_id` 的句柄，运行时直接跳到 `parse_id`；`parse_id` 执行 `co_return 42` 后在 `final_suspend` 里返回记录下的父亲句柄，又直接跳回 `load_order`。这一来一回没有经过 `resume()` 的返回路径，嵌套再深也不会把调用栈叠高。失败的那次，`parse_id` 在函数体里抛出 `runtime_error`，`unhandled_exception` 把 `current_exception()` 存进 promise；`load_order` 的 `await_resume` 重新抛出，`load_order` 自己的 `unhandled_exception` 再存一次；最外层的 `result()` 第三次抛出，`main` 才接到。每一层都只是“存下异常、结束、恢复上一层”，没有 `try/catch` 也能把异常送到调用方。

这里的 `final_suspend` 返回 `suspend_always`，所以子协程结束后帧还留着，等 `Task` 临时对象析构时统一 `destroy()`；如果返回 `suspend_never`，控制流离开协程时帧会自动销毁，但父亲就不能再从子协程的 promise 里读结果了。两种设计都有人用，关键是配套：选择“结束后保留帧”，就必须有对象负责销毁；选择“结束即销毁”，就必须在结束前把结果搬走。`std::noop_coroutine()` 是“没有下一个协程”的句柄，`final_suspend` 在找不到 continuation 时返回它，运行时就回到最初调用 `resume()` 的地方。

还有一个容易忽略的临时对象：`co_await parse_id(raw)` 里的 `Task<int>` 临时对象，活到整个 `co_await` 表达式结束，也就是 `await_resume` 返回之后。所以 `await_resume` 必须把结果按值返回或移动出来，不能返回子协程帧里的引用；否则临时 `Task` 一析构，引用就悬垂。这也是为什么示例里的 `value` 用 `std::optional<T>` 存值、`await_resume` 返回 `T` 而不是 `T&`。

这份 `Task` 仍然是教学用的简化版：它没有取消，没有调度器，`Task<void>` 也没有特化；`result()` 只能在协程结束后调用，重复调用会再次移动同一个值，对只可移动类型不可靠。真实项目里更稳妥的做法是用经过测试的协程类型库，而不是在每个服务里重写一遍 promise。手写时至少要注意两个生命周期问题。第一，`await_suspend` 把句柄交给调度器之后，调度器必须在协程帧销毁前恢复它；任务被取消时要走销毁路径，不能把句柄留在队列里。`co_await` 的 awaiter 临时对象活到 `await_resume` 返回之后，若调度器在更晚的时候才使用指向它的指针，同样会悬垂。第二，协程帧里跨挂起点存活的 RAII 对象不会在挂起时自动析构：一个 `std::lock_guard` 如果在 `co_await` 之前加锁，挂起期间锁一直被持有，别的线程进不来，极端情况下直接死锁；`clang-tidy` 21 的 `misc-coroutine-hostile-raii` 会对这种“锁跨越挂起点”的写法报警（本机实测）。`cppcoreguidelines-avoid-reference-coroutine-parameters` 则专门抓引用参数，正是 31.1 那个悬垂例子的成因（本机实测）。

创建 `counter` 时函数体没有运行，`begin()` 构造迭代器时才第一次 `resume()`，跑到 `co_yield 3` 停住；`operator*` 读的是 promise 里的 `current`，`operator++` 再恢复一次。取到 2 就 `break`，剩下的循环不再执行，`countdown` 里的 `Cleanup` 也没有机会走到函数末尾——它在生成器析构、协程帧被销毁时才执行，所以 `body: cleanup` 出现在 `after the loop` 之后。这就是惰性序列的代价：控制流被拆成一次次恢复，局部对象的销毁时机也跟着帧走，而不是跟着某次函数调用走。

`co_yield v` 不是独立的关键字语义，标准规定它等价于 `co_await promise.yield_value(v)`。`yield_value` 返回 `suspend_always`，协程就停在这里；返回 `suspend_never`，就变成“产出但不停”，调用方拿不到中间值。生成器迭代器通常在 `operator++` 里 `resume()`，在 `operator==` 里比较句柄是否为空，和上面这个手写版本是同一个套路。

`produce` 里的 `expected` 是 worker 线程自己的 id，每一行都打印 `true`；主线程在 `join` 之后比较两个 id，得到 `true`（不同线程）。这说明协程没有创建任何线程：`squares` 的函数体是在 worker 调用 `begin()`/`operator++` 时、在 worker 的栈上恢复执行的。协程只提供“在这里暂停、从这里恢复”的机制；恢复发生在哪个线程，取决于谁拿着句柄调用 `resume()`。想要“在后台线程跑、完成后回到主线程”，仍然需要一个调度器或线程池来搬运句柄；生成器只是把“谁来推进”交给了迭代器。把协程当成线程，或者以为 `co_await` 会自动切到另一个线程，是这一章最常见的误解。

`std::generator` 的模板参数决定它产出的是值还是引用：`std::generator<int>` 产出 `int`，`std::generator<const std::string&>` 产出引用，`std::generator<std::string>` 会把每个值复制或移动进生成器状态。产出引用省拷贝，但引用的有效期取决于它指向谁：指向生成器内部保存的值时，只保证到下一次恢复；指向外部对象时，则取决于外部对象活多久。迭代器解引用拿到引用后，如果先 `++` 再使用，之前那个引用可能已经失效。生成器是单遍的输入 range：不能像 `vector` 那样从头再遍历一次，也不能复制生成器（它是 move-only 的）；需要多遍就重新创建，或者先把结果收进容器。

它和 `views::filter`、`views::transform` 的区别在写法，不在惰性：view（视图）用声明式组合描述“取哪些、怎么变换”，生成器用普通的 `for`、`if`、递归和局部状态描述“按什么顺序产出”。生成器适合状态机式的流、分页读取、需要 `try/catch` 或多层循环的序列；view 适合简单的逐元素变换。生成器是单遍的，view 能不能多遍遍历取决于底层 range；两者都按需计算，生成器通常不拥有它遍历的源数据（它产出的值可能由帧自己保存），view 也不拥有底层 range，混用时要注意谁先销毁。

C++23 的 `std::generator` 在本机的 Clang 21 + libstdc++ 15 和 GCC 15 上都能用（两个编译器都实测通过）；libc++ 21 还没有这个头文件，写可移植代码时要留一个 C++20 的退路。手写生成器时，异常处理也常被忽略：协程体抛出的异常会进入 `unhandled_exception`，如果这个函数只是返回，异常就被吞掉，调用方永远不知道；如果让它重新抛出（`throw;`），异常会离开协程、从调用方那次 `resume()` 里抛出来，协程则视为停在最终挂起点（本机两个编译器实测都是如此）；只有当 `resume()` 恰好在 `noexcept` 函数里被调用（比如一个标了 `noexcept` 的迭代器 `operator++`）时，才会变成 `std::terminate`。要传播异常，得像 31.2 的 `Task` 那样把 `exception_ptr` 存下来，在恢复或取结果时重抛；`std::generator` 已经替你做了这件事，迭代时会把异常重新抛出。生成器的每次恢复都是一次间接调用，帧本身也要分配，和直接写循环相比不是零成本；它适合“序列很长、可能提前结束、元素按需计算”的场景，不适合把每个短循环都改写成生成器。

## 31.4 std::execution 尚未落地，async/Asio 仍要分工

前面三节都在讲“一个协程怎么暂停、怎么恢复”。真正做异步系统还要回答另外几个问题：这一步在哪个线程上跑？几个步骤怎样组合？中途取消时，已经启动的工作怎么收尾？C++26 采纳的 `std::execution`（P2300）想用 sender（发送方）/receiver（接收方）模型统一回答这些问题。它的核心分工是：sender 描述“要做什么”，以及成功、失败、取消三种完成方式；receiver 提供 `set_value`、`set_error`、`set_stopped` 三个入口；`connect(sender, receiver)` 把两者接成一个 operation state（操作状态），调用 `start()` 才开始执行。sender 是惰性的，组合 sender 只是搭描述，不会启动任何工作。

标准库还没有普遍实现这套设施，但模型本身可以先用手写的小例子理解。下面的 `JustSender`、`ThenSender` 和 `PrintReceiver` 是教学模型，不是 `std::execution` 的实现：

标准里的 `std::execution` 在这套骨架上补了类型系统和调度：sender 带有完成签名（可能成功、可能失败、可能取消），`connect` 是定制点，调度器（scheduler）通过 `schedule()` 产出一个“在该执行上下文上开始”的 sender；`then`、`when_all`、`continues_on`（早期草案里叫 `transfer`）这些适配器负责组合，`std::this_thread::sync_wait` 负责在测试或 `main` 里把 sender 跑完并取结果。取消不是靠一个全局标志，而是通过 receiver 环境里的停止令牌（stop token）传递：上游发现令牌被触发，就调用 `set_stopped` 结束，不把取消伪装成异常。`when_all` 则把一组 sender 组成结构化的整体：等所有子任务结束后才完成；按 P2300 的设计，一个子任务失败时可以请求其余停止。这些名字和分工在提案里已经成型，但本书环境无法编译验证，具体细节需核实。

Asio 的定位不同：它首先是一个 I/O 库，`io_context` 负责事件循环，`co_spawn(executor, awaitable, token)` 把协程挂到某个 executor 上，恢复时回到该 executor 的线程。它解决的是 socket、定时器、连接生命周期这些标准库没有的东西；sender/receiver 解决的是“任务怎样组合、怎样取消”，两者不在一个层面上。P2300 本身也不提供 I/O，只提供调度和组合的抽象。选 Asio 不代表不能用协程，反而它的 `awaitable<T>` 就是协程任务类型；代价是引入第三方依赖，错误处理有异常和 `error_code` 两套风格，跨版本升级也要留神。

所以今天的选型可以按边界来分：只在一两个任务之间取结果，`std::async` 足够；需要大量 I/O、定时器、连接管理和线程池，用 Asio（Boost.Asio 或独立版），它的 executor（执行器）和协程支持已经成熟；需要 sender/receiver 风格的组合，可以用 libunifex、stdexec 这类实验实现，但要接受它们和最终标准可能有差异；只需要惰性序列，C++23 的 `std::generator` 已经够用。自己写协程任务类型也不是不行，但要把调度、取消、异常和帧的生命周期都想清楚，否则就是在重造一个不完整的 `std::execution`。把协程接到现有回调库上时，还要注意恢复线程：Asio 的 `co_spawn` 会把恢复调度回它的 executor，而裸 `coroutine_handle::resume()` 就在当前线程继续跑，两者的线程安全假设不一样。

## 回头看

四节连起来看，协程提供的只是“把函数切成可恢复的片段”这一件事。`co_await` 决定在哪里切，`promise_type` 决定切完以后返回什么、异常往哪里放，生成器决定切出来的值怎么交给调用方；而“谁来恢复、在哪个线程恢复、取消时怎么收尾”始终在语言之外。C++20 把状态机和定制点做进了编译器，C++23 补了一个标准的 `std::generator`，但通用任务类型、线程池和调度器仍要由库提供。这也是为什么同一段 `co_await` 代码，接上不同的 promise 和调度器，行为会差很远。

已经由标准兜底的是语法变换、awaiter 协议、帧的分配与销毁规则、生成器的惰性迭代；仍要靠写法和工具的是数据生命周期、恢复线程的同步、取消路径和 RAII 跨越挂起点的语义。判断一个协程设计是否可靠，可以沿着帧问三个问题：帧里的每个指针和引用，在恢复时还有效吗？帧由谁销毁，销毁发生在恢复之前还是之后？挂起期间持有的锁、事务和临时状态，是否应该继续持有？ASan 能抓住已经发生的悬垂，`clang-tidy` 能提示引用参数和跨挂起点的锁，但这两个问题最终要在接口设计里回答。
