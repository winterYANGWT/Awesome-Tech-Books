# 第 26 章 迭代器、区间与删除：remove 为什么没删

`std::remove` 明明调用了，容器的大小为什么一点没变？

```cpp
std::vector<int> v{1, 99, 2, 99, 3};
auto newEnd = std::remove(v.begin(), v.end(), 99);
std::printf("size=%zu，逻辑尾之后还有 %td 个\n", v.size(), v.end() - newEnd);
```

打印出来是 `size=5，逻辑尾之后还有 2 个`。`remove` 把要保留的元素往前挪，返回新的逻辑终点，却没有删掉任何元素——它只拿到一对迭代器，不知道这对迭代器属于哪个容器，也就没有 `erase` 可调。真正能改变容器大小的只有容器自己的成员函数。

从这句话可以拉出本章的整条线：迭代器能做什么、不能做什么；区间怎么表示；容器什么时候让迭代器失效；删除为什么分成“算法搬移”和“容器 erase”两步。每一步都有原书条目对应，但把它们放在一起看，会发现大多数错误都源于同一个误解：把迭代器当成容器，或者把算法当成能看见容器的操作。

## 26.1 优先 const_iterator，反向迭代器的 base 有偏移

一个只读取数据的函数，参数是 `const std::vector<int>&`，返回找到的位置。它天然拿到 `const_iterator`，因为不能通过迭代器改元素。麻烦出在另一类函数：参数是非 const 容器，但函数本身只读，返回的迭代器却留给了调用方。如果返回普通 `iterator`，调用方就多了一条修改元素的通道，而函数作者本来没有这个意图。把返回类型改成 `const_iterator` 才是准确的接口，剩下的问题是：拿得到、用得上吗？

在 C++98 里，这两件事都不容易。`const_iterator` 只能从 const 容器或转换得到，而 `insert`、`erase` 的位置参数只接受 `iterator`；`iterator` 到 `const_iterator` 是单向转换，反向没有可移植的路径。于是 ESTL-26 在当时给出了一条实用建议：操作用 `iterator`，只读用 `const_iterator`。这条建议的前提是 C++98 的接口限制，不是 const 正确性不重要。Meyers 在 ESTL-26 里把四种迭代器的关系讲得很清楚：`iterator` 能转 `const_iterator`，`reverse_iterator` 能转 `const_reverse_iterator`，反向都不行；算法不挑迭代器类型，麻烦集中在容器成员函数和两类迭代器的混合比较上。

C++11 把前提拆掉了。标准容器有了成员 `cbegin`/`cend`，`insert`/`erase` 接受 `const_iterator`，`iterator` 与 `const_iterator` 之间也要求可以比较。EMC-13 因此可以直接说“优先用 const_iterator”，并且给出的 C++11 写法短到不需要解释：

## 26.2 迭代器失效：解引用前先过四道检查

迭代器错误的麻烦之处在于它大多数时候不报错。`std::find` 找不到目标时返回传入的 `end`，紧接着解引用就把值写到了容器尾后；两次独立的 `find` 各返回一个位置，如果第一个落在末尾、第二个命中前面的元素，`[first, last)` 就是一个反向区间，`copy` 会一路走出容器。Sutter 在 EXC-01 里把这些归纳成四道检查：这个迭代器可解引用吗；自取得以来失效了吗；和另一个迭代器配对时构成同一容器内的有效区间吗；有没有去修改内建类型的临时量（典型写法是 `--e.end()`）。

四道检查里，前三道没有编译器能替你完成，第四道有时能。`--e.end()` 在 vector 迭代器就是指针的实现上编译不过，因为不能对函数返回的指针临时量做自减；写成 `e.end() - 1` 能编译，但容器为空时得到的仍是无效位置。C++11 之后 `std::prev(e.end())` 把“先复制、再后退”写在名字里，意图比 `- 1` 清楚，但空容器这个前提仍然要自己保证。

失效规则和容器操作绑在一起。对 vector 和 string，`erase` 让被删元素及其后所有迭代器失效；deque 只有删两端时才把影响限制在局部，删中间元素时全部迭代器失效。vector 的 `push_back` 在扩容时让全部迭代器失效，不扩容时至少让 `end()` 失效；deque 的 `push_back` 让所有迭代器失效，但对已有元素的引用仍然有效。所以删除循环必须用 `it = c.erase(it)` 接住返回值，不能 `c.erase(it); ++it;`。ACC-06 补的是另一半：循环条件里不要缓存 `end()` 或 `size()`。`end()` 的失效不只发生在扩容时；即使 `reserve` 留足了容量，`push_back` 仍会让先前保存的 `end()` 失效。

## 26.3 remove 不删，erase-remove 才删

回到开头的问题。`remove` 的声明只接收一对迭代器和一个值，它没有容器参数，也没办法从迭代器反推出容器。C++ 标准库没有“从迭代器找到所属容器”的接口，所以 `remove` 不可能调用 `erase`；能改变容器大小的只有容器自己的成员函数。MXC-02 把这层因果关系讲得最直接：算法拿到的是区间，不是容器；它能做的只有对区间里的元素赋值。ESTL-32 则给了它一个形象的说法：`remove` 是在做压缩，把保留的元素依次前移，被删除的值留下一个个“洞”，后面的保留值把洞填上，返回下一个待填的位置。洞里的旧值最后是什么，标准没有规定，不能依赖。

历史上有两处写法已经变了。C++98 的关联容器 `erase(iterator)` 返回 void，循环删除只能写 `c.erase(i++)`，先记下后继再删；C++11 起它返回后继，`i = c.erase(i)` 对所有容器都成立。C++20 又加了 `std::erase(c, value)` 和 `std::erase_if(c, pred)`，序列容器和 string 的按值删除、除 array 外所有标准容器的按谓词删除都能一行完成，示例里 `std::erase` 和 `std::erase_if` 的返回值就是删除个数；它最后先删 103、再删光偶数，所以打印为空。这两步都没有改变底层事实：`std::ranges::remove` 仍然只重排，`remove` 算法仍然拿不到容器。C++17 的节点句柄（`extract`）能在不拷贝元素的情况下改关联容器的键，但它也不是删除接口，删除仍靠 `erase` 或 `erase_if`。

MXC-02 还提醒了手写删除算法的两个坑。自己写 `remove_nth(first, last, n)` 时，先用循环把 `first` 前进 n 步，如果 n 超过区间长度，迭代器会被推过 `last`，形成一个非法区间；前提要用 `distance(first, last) >= n` 检查，而且前进应交给 `std::advance`，它会按迭代器类别分派，随机访问迭代器上是常数时间，不会退化成手写循环的线性时间。另一个坑是把“第 n 次返回 true”的有状态函数对象当 `remove_if` 的谓词：算法可以任意复制谓词，各副本的状态互不共享，删哪个元素就变得不可预测。谓词要是纯的，这件事在[第 27 章](ch27.md)还会展开。

## 26.4 批量操作要用区间成员函数和目标区间

示例先在 200 个元素、容量 300 的 vector 中间插入 50 个元素，排除了扩容的干扰，剩下的差别全是搬移。逐个 `insert` 移动了 6275 次，区间 `insert` 只移动 100 次，拷贝次数都是 50。逐个插入的第 k 次要把插入点之后的约 100+k 个元素各挪一格，累计是二次的；区间插入先算出长度，把插入点之后的 100 个元素整体挪 50 格，一次完成。list 的收益不同：区间插入只新建并链接这批节点，已有节点一个都不用动；关联容器的区间插入把一段元素一次交给容器，接口上省掉逐次调用，复杂度仍是对数级。

同样的道理适用于构造和赋值。用区间构造，或者对已有容器 `assign(first, last)`，通常比默认构造之后逐个 `push_back` 更明确，也给实现留出了算长度的机会。C++11 的初始化列表让 `v.insert(v.end(), {1, 2, 3})` 这种小批量写法不必先造临时容器；C++23 给序列容器加了 `insert_range`、`append_range`、`assign_range`，可以直接接一个 range，本机 clang 21 + libstdc++ 15 和 GCC 15 在 `-std=c++23` 下都能编译。输入迭代器（比如 `istream_iterator`）无法预知长度，区间插入仍可能多次扩容，收益主要在接口和批量语义，不在复杂度。

## 26.5 半开区间和迭代器类别决定算法能做什么

标准库的区间是半开的：`[begin, end)` 包含 `begin`，不包含 `end`。`end` 是哨兵（sentinel），指向最后一个元素之后，只用来比较，不能解引用；空区间的 `begin` 和 `end` 相等。TIC-31 在讲自定义容器迭代器时专门点过这一句，因为“最后一个元素之后”这个位置在内存里通常真实存在（就是缓冲区末尾），解引用它不一定立刻崩溃，可能读到别的数据，也可能在下一次扩容后变成悬垂访问。`*end`、`end->` 都是未定义行为；循环条件写 `it != end`，不要写 `it <= end`，后者对非随机访问迭代器根本不成立。

示例里的 `countLess` 只用了 `!=`、`*`、`++` 三个操作，所以 vector、list、`istream_iterator` 都能传进来。这不是巧合，而是泛型函数的正确要求：需要什么操作，就在接口上只要求那些操作。ACC-11 把五类迭代器讲成一道能力阶梯：input/output 只能单遍读写，forward 可以多遍，bidirectional 还能后退，random-access 还能 `+ n`、下标和比较大小；`find` 只要 input，`reverse` 要 bidirectional，`sort` 要 random-access。用 `it < end` 或 `it + i` 遍历，就把 list 和输入迭代器排除在外了；如果实现里确实需要随机访问，应该在接口或文档里明说，而不是嘴上说泛型、代码里偷偷用下标。

输入迭代器还有一条额外约束：它只保证单遍遍历。算法不能保存一个旧迭代器，走一段之后再回头从旧位置读；需要多遍扫描时，要求必须提高到 forward。示例里 `std::accumulate` 消费 `istream_iterator` 时一路向前，不回头，正好符合这条约束。`static_assert` 把类别写成了编译期事实：`istream_iterator` 是 input，list 的迭代器是 bidirectional 但不是 random-access，vector 的是 random-access，示例里的 vector 满足 `std::ranges::sort` 要的 random-access range，list 不满足；本机实测把 list 传给 `std::sort` 会编译失败。

手写迭代器是 ESS-14 的主题。只实现 `!=`、`*`、`++`，够写一个手写的 while 循环，但不够进标准算法。标准算法通过 `std::iterator_traits<It>` 取五个嵌套类型：`value_type`、`difference_type`、`pointer`、`reference`、`iterator_category`；少了任何一个，`std::distance`、`std::accumulate` 这类模板就会在实例化时找不到类型：

C++20 的 concepts 把这件事变成可检查的约束：`std::input_iterator`、`std::forward_iterator`、`std::random_access_iterator`、`std::contiguous_iterator` 逐级加要求，写新迭代器时用 `static_assert` 自检，比等到某个算法实例化失败更早发现问题。ranges 还引入了 `iterator_concept`，允许迭代器的 ranges 类别和旧式 `iterator_category` 不同（典型是 `views` 的迭代器）；标准算法仍看 traits，ranges 算法看 concept。今天绝大多数场合不需要自己写迭代器：`std::span`（C++20）、容器迭代器、ranges 视图已经覆盖了只读切片、过滤、变换这些需求。ESS-14 的结论在新标准下没有失效，只是“必须手写”的场景变少了。

## 26.6 容器不拥有裸指针，reserve 也不创建元素

EXS-01 从另一个方向问“容器管理什么”：size 是已经存在的元素个数，capacity 是不重新分配的前提下最多能放多少个。`reserve(n)` 只保证 capacity 至少到 n，不改变 size，也不构造任何元素；实现可能给得比 n 更大，所以断言 `capacity() == n` 可能失败，只能断言 `>= n`。对空 vector 写 `v[0]` 是未定义行为，典型实现上可能“看似成功”，因为缓冲区已经分配；但下一次 `reserve` 触发重新分配时只会搬 size 个元素，先前写进去的值会无声消失。`operator[]` 出于效率不做检查，越界属于未定义行为；需要检查时用 `at`，越界抛 `std::out_of_range`。

## 回头看

本章的规则表面上分散在迭代器、删除、批量操作和所有权，实际上都在纠正同一个越界：把迭代器当成容器。算法只看见区间，看不见容器；迭代器只是位置，不知道容器何时重新分配；`reserve` 只改容量，不构造对象；裸指针元素只被当作值销毁。C++11 之后，语言和标准库替我们补上了不少：`const_iterator` 随手可得，`erase` 返回后继，C++20 的 `erase`/`erase_if` 把常见删除变成一行，ranges 的 concept 把迭代器要求写进类型。但 `remove` 仍然不删，`end` 仍然不能解引用，扩容仍然让迭代器失效，裸指针容器仍然不拥有对象——这些不是历史包袱，而是“算法与容器分离”这一设计的直接结果。写得对比记得住规则更重要：先问这段代码有没有容器，再问这个位置还有效吗。
