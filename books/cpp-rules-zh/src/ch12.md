# 第 12 章 异常安全：三档保证、copy-and-swap 与 noexcept

先看一段每天都会写出来的转账代码：

```cpp
void transfer(Account& from, Account& to, long cents) {
    from.withdraw(cents);   // 已经改了 from
    to.deposit(cents);      // 这里抛，钱就少了
}
```

`deposit` 可能因为记账字符串分配失败、审计日志写不进去或者账户已冻结而抛异常。异常一抛，`withdraw` 已经生效，`deposit` 没有发生，两个账户的总额对不上。给 `transfer` 套一个 `try/catch` 并不能把 `from` 恢复原样：`catch` 块里要么手工把金额加回去，而“加回去”本身还可能失败；要么承认这个函数没有能力回滚，只能把问题留给调用方。异常安全讲的不是“哪里写 catch”，而是“一个操作失败时，对象和程序究竟留在什么状态”。

本章围绕这个问题往下走：先把“失败后还能不能用”分成三档明确的承诺；再看异常安全的实现为什么主要靠 `throw` 的位置和析构函数的自动清理，而不是靠 `catch`；然后用 copy-and-swap 和包含把“可能失败的工作”与“不会失败的提交”分开；最后讨论 `noexcept` 如何把“不抛”写进类型，以及动态异常规格这段失败的历史。每一条都指向同一个判断：函数抛出异常之后，它碰过的东西还能不能兑现原来的约定。

`new Artwork("poison")` 抛出之后，`art_` 仍然指向已经被 `delete` 的旧对象，`revision_` 也已经加过。程序甚至没有机会进入 `catch` 块里的补救逻辑，因为函数自己没有任何补救逻辑；`Gallery` 析构时对悬垂指针再 `delete` 一次，ASan 才把这个错误变成确定的崩溃。这里连“基本保证”都没有做到：资源泄漏、对象损坏、不变式被破坏，三者全中。

Meyers 在 EC-29 里把异常安全的函数应满足的条件拆成两条：不泄漏资源，不让数据结构损坏。在这两条之上，Sutter 在 EXC-11 里给出三档保证，Sutter 与 Alexandrescu 在 CCS-71 里把它们写成同一条设计顺序：

- **基本保证（basic guarantee）**：异常发生后，程序仍处于有效状态；不泄漏，所有对象仍满足不变式，仍可析构、仍可继续使用。具体状态可能不可预测——`Mailbox` 里可能多了一部分信，也可能一封都没多。
- **强保证（strong guarantee）**：失败时状态与调用前完全相同，像事务一样提交或回滚；对象内部的引用、指向容器的迭代器也不能失效。成功就完全成功，失败就像从未调用。
- **不抛保证（nothrow guarantee）**：函数承诺不失败。Sutter 在 EXS-12 里更愿意叫它 nofail，因为这个承诺同样适用于错误码式的接口：不管用什么方式报告错误，这个操作都不允许失败。

三档是严格的包含关系：不抛蕴含强，强蕴含基本；基本之下没有第四档。CCS-71 把“连基本保证都做不到”直接归为程序缺陷，而不是“弱一点的保证”。`Gallery::replace` 就是这种缺陷的样本。

三档之中，哪些该给哪一档？EC-29、EXS-12 和 CCS-71 的答案一致：在不惩罚不需要该保证的调用者的前提下，给能给出的最强保证。能不做失败就不失败；做不到不失败，就尽量做成事务；连事务都太贵，至少守住基本保证。`std::vector::insert` 是这条原则的经典例子：每次插入都整份复制容器当然能换来强保证，但所有调用方都要为少数需要强保证的人付账；标准库选择不这么做，而是把“复制、在副本上插入、成功后 `swap`”的工具留给需要的人。12.5 节会看到标准库具体把哪一档给了哪些操作。

`deliver_strong` 先在 `temp` 上复制整个邮箱，再把整批信投进去；`"poison"` 在 `temp` 上抛出时，`mailbox` 一个元素都没动，所以大小仍是 1。`deliver_basic` 直接往 `mailbox` 里逐封投递，前两封已经进去，第三封抛出，大小变成 3。这个状态仍然是有效的：邮箱可以继续收信、可以析构、已有的信都完整；但调用方没法预知失败时究竟投进去几封，这正是“基本”的含义。

强保证的代价在 `deliver_strong` 里看得很清楚：每次投递都要复制整个邮箱。信越多，这份复制越贵。如果调用方只关心“不要泄漏、对象别坏”，基本保证就够了；如果它要在失败后重试，或者要把邮箱交给另一个线程继续使用，强保证才值得这份复制。承诺的档位应该写进接口文档，而不是让调用方从实现里猜——EC-29 把异常安全保证称为接口的一部分，理由就在这里。

有一类函数没有选择：析构函数、释放函数（`operator delete`、`operator delete[]`）和 `swap` 必须不失败。CCS-51 的解释是，它们分别是回滚和提交的最后一步：回滚要靠析构把半成品清理掉，提交要靠 `swap` 把新状态换进去；如果最后一步自己还会失败，前面所有的保证都没有退路。C++11 起析构函数默认是 `noexcept(true)`，异常从析构函数逃出去会直接 `std::terminate`（[第 11 章](ch11.md) 展开了这条规则）；标准库也要求与它一起使用的类型的析构不抛。`12_1_tiers.cpp` 用两个 `static_assert` 把这件事写成了编译期检查：

```cpp
static_assert(std::is_nothrow_destructible_v<Mailbox>);
static_assert(std::is_nothrow_swappable_v<Mailbox>);
```

`std::is_nothrow_swappable_v` 检查的是 `using std::swap; swap(a, b);` 这条真实调用路径，所以示例除了成员 `swap`，还在类型所在的命名空间提供了不抛的非成员 `swap`。这两个断言不能证明实现一定正确，但能挡住“给成员加了会抛的操作，却忘了更新承诺”这类退化。

新标准没有改变三档保证的分类，但改变了实现它们的成本。C++11 的移动语义让容器在扩容时可以搬移元素，也让按值传参的赋值对右值实参更便宜；`std::unique_ptr` 让资源所有权可以随对象一起移动，回滚时不需要手写 `delete`。C++17 的 `std::is_nothrow_swappable` 和 C++20 的 concepts 让“这个类型能不能不抛地交换”从文档约定变成可检查的约束。C++23 的 `std::expected` 则给“可预期的失败”提供了异常之外的返回通道，这一点在[第 13 章](ch13.md)展开。工具方面，clang 21 对析构函数里直接 `throw` 报 `-Wexceptions`，GCC 15 报 `-Wterminate`；两者都只能抓直接写出来的抛出，抓不到隔着函数调用的抛出，所以 `static_assert` 和设计约束仍然不能省。

`legacy_import` 在取得资源之后、释放资源之前抛出，`gate.release()` 没有机会执行，`still open=1` 就是漏掉的资源。`raii_import` 把同一份资源的生命周期交给局部的 `Lease`：无论函数正常返回还是异常展开，`Lease` 的析构函数都会执行，所以 `still open=0`。两段代码的差别不在 `catch` 写在哪，而在“谁负责释放”这件事有没有绑定到一个对象上。`parse_port` 则演示了 `throw` 的位置：它在检测到非法输入、而且自己无法给出合理结果的地方抛出；调用方拿到异常后可以就地换成默认端口 80，于是错误在最近的、有足够知识处理它的地方结束，不需要一路往上报告。

Sutter 在 EXS-11 里把异常安全拆成三个问题：在哪里 `throw`，在哪里 `catch`，以及异常从任意一次函数调用中穿过时，代码是否仍然安全。只有第二个问题和 `catch` 有关，而且它经常可以被析构函数替代。他的三条准则是：为应用或子系统定下统一的错误报告、传播和处理策略；只在检测到错误且自己处理不了的地方 `throw`；只在有足够知识处理错误、翻译异常或守住策略边界的地方写 `try/catch`。真正耗时的是第三个问题——让异常经过时没有泄漏、类的不变式不被破坏——这必须在设计里解决，事后补几个 `catch` 无济于事。

这条准则在今天比 Sutter 写作时更容易执行，因为“自动清理”有了标准工具。C++11 的 `std::unique_ptr` 和 `std::shared_ptr` 把最常见的堆资源接管过去，C++14 的 `std::make_unique` 让“分配后立刻交给所有者”写成一条表达式；锁有 `std::lock_guard`/`std::unique_lock`，文件有 `std::fstream`，它的析构函数负责关闭。C++11 的 `std::exception_ptr`、`std::current_exception` 和 `std::rethrow_exception` 让“捕获、保存、在另一个上下文重抛”成为可能，`std::throw_with_nested` 和 `std::nested_exception` 则能在翻译异常时保留原因链；这些工具替代了不少手写的 `catch (...)`。C++17 的 `std::uncaught_exceptions()` 返回当前线程正在传播的异常个数，使 scope guard 能正确判断“现在是不是已经在展开”，而不必依赖那个只能回答“有没有”的旧布尔函数。RAII 本身的机制在[第 8 章](ch08.md)展开；本节的落点是：把清理交给析构之后，`catch` 只应出现在真正要处理或翻译错误的地方。

`write_together` 失败时，输出流里留下了 `total: `；`write_after_compute` 失败时，流是空的。原因是 C++17 起（P0145），用运算符写法调用的重载运算符，操作数按内置运算符的顺序求值：`a << b` 一定先求 `a`，再求 `b`，不论 `operator<<` 是成员还是自由函数。所以 `out << "total: "` 先完成、前缀已经写进流里，`total(broken)` 才被求值并抛出。C++17 之前这个顺序没有规定，同一行代码在不同编译器上可能写出前缀，也可能不写。可依赖的规则不是记住某条顺序，而是不要把“可能失败的计算”和“输出”放进同一条语句。

ACC-05 还提醒了格式化状态：如果代码在输出前改了 `precision`、`fill` 或 `flags`，异常会让恢复语句被跳过，流就带着改过的状态继续服务后面的代码。`write_after_compute` 只解决了“计算失败时不要碰输出”，没有解决“输出自身失败时留下半截内容”；后者无法靠语句顺序消除，只能承认流输出不是可回滚的操作（EXC-19 会继续讨论这个问题）。C++20 的 `std::format` 先把整个结果格式化成字符串，再把字符串交给一次输出，能把“格式化失败”和“写流失败”分开；本机 Clang 21 + libstdc++ 15 在 `-std=c++20` 下已经支持它。但它仍不能保证底层 I/O 不失败。

工程上可以把这条纪律落成检查：让函数只做一件事，把 I/O 留在最外层；在代码评审里专门找“一条语句里既有函数调用又有 `<<`、`push_back`、赋值”的地方。编译器不会因为一条语句有两个副作用就报警，`-Wunused-result` 和 `[[nodiscard]]` 管的是返回值被忽略，不是副作用混在一起；这部分只能靠写法和评审。异常真正穿过模块边界时怎么翻译成错误码，是[第 13 章](ch13.md)和[第 35 章](ch35.md)的主题。

## 12.3 copy-and-swap 与包含：怎么只写不抛的提交

`add_unsafe` 失败后 `count=3` 而 `order` 只有两个名字，`consistent=0`；对象仍然可以析构、可以继续用，但它已经违反了自己的不变式——这连基本保证都不算。`add` 先把整个 `Directory` 复制到 `temp`，在 `temp` 上完成两步修改，全部成功后才 `swap(temp)`；`"poison"` 让 `temp` 的第二步抛出时，原对象一个元素都没动，所以 `count=2`、`consistent=1`。`swap` 只交换两个容器的内部指针，标了 `noexcept`；提交阶段没有分配、没有复制、没有可能失败的调用。

`operator=` 用了同样的思路，只是把“复制”放进了按值形参的构造：

```cpp
Directory& operator=(Directory other) noexcept {
    swap(other);
    return *this;
}
```

所有可能抛的工作——复制或移动实参来构造 `other`——都发生在进入函数之前；函数体里的 `swap` 不抛，所以这个函数本身可以诚实地标 `noexcept`。如果实参的复制抛出，异常在调用点就传播了，`*this` 还没有被碰过；如果实参是右值，移动构造通常更便宜。自赋值也不需要 `if (this != &other)`：复制一份自己再换回来，结果仍然正确，示例通过 `assign_from(safe, safe)` 这种别名调用验证了这一点。`swap` 的实现细节、两段式 `using std::swap; swap(a, b);` 以及 `std::swap` 的定制规则，在 [6.5 节](ch06.md)已经展开；本节关心的是它在异常安全里扮演的角色：**提交必须是不会失败的操作**。

Sutter 在 EXC-13 里用一个 `Stack` 演示了同样的结构。他把“分配原始内存、在指定位置构造、显式析构、归还内存”抽成一个 `StackImpl`，让 `Stack` 私有继承它：`Stack` 的默认构造只转发给 `StackImpl` 分配缓冲区；拷贝构造先让基类按 `other.vused_` 分配同样多的槽位，再逐个 `construct`，某个 `T` 的复制构造抛出时，基类析构只销毁已经成功构造的那些；`operator=` 写成 `Stack temp(other); Swap(temp); return *this;`。`Push` 需要扩容时也不在原缓冲区上折腾，而是新建一个更大的临时 `Stack`，把旧元素和新元素都放进去，全部成功后才 `Swap`。整个类没有一行 `try/catch`：异常安全来自“资源由对象持有”和“可能抛的工作都在旁边做完”，不是来自捕获。

EXC-14 把同一个 `StackImpl` 从基类改成私有成员 `impl_`，异常安全策略完全不变，代价是每次访问要多写 `impl_.`。EXC-15 接着给出选择：实现复用优先用包含，只有需要访问 `protected` 成员、需要覆盖虚函数，或者必须让某个基类先于其他子对象构造时，才用私有继承。这个建议和今天“优先组合，而非继承”的共识一致（[第 18 章](ch18.md)）；`12_3_copy_and_swap.cpp` 用的就是成员 `impl_`，`Directory` 只能通过 `impl_` 的公开接口访问它，耦合比私有继承低。C++20 的 `[[no_unique_address]]` 可以让编译器把空的实现类成员与其他成员重叠，减少空间占用，部分替代当年“空基类优化”的动机。

EXC-15 还有一半讲的是泛型容器不要写异常规范。Sutter 的理由是：容器作者不知道 `T` 的操作会抛什么，给 `Push`、`Top` 这类函数写 `throw()` 等于替未知的 `T` 打包票；给 `Count()` 这种确定不抛的函数写 `throw()`，又会限制未来实现变更，还可能给派生类带来过强约束。今天的对应规则不是“一概不写 `noexcept`”，而是分清对象：析构、`swap`、移动构造这些已经确定不抛的关键操作应当标 `noexcept`；泛型接口里依赖 `T` 的操作不要凭空承诺，需要条件化时写 `noexcept(noexcept(表达式))`，让编译器按 `T` 的实际能力推导。C++17 起 `noexcept` 是函数类型的一部分，写错不再只是文档问题：异常真的逃出去会直接 `std::terminate`（12.6 节会看到）。

新标准让 copy-and-swap 在右值实参和可移动成员的情况下更便宜，但没有让它变成所有赋值的默认写法。C++11 的移动构造让临时对象可以搬走资源而不是深拷贝，C++17 的保证复制消除让按值返回纯右值不再产生额外的复制；如果类的成员都是 `std::vector`、`std::string`、`std::unique_ptr` 这类自带正确拷贝/移动的类型，零法则（[第 6 章](ch06.md)）通常比手写 copy-and-swap 更好。手写这套结构的场合，是类自己管理资源、或者像 `Directory` 这样要把多个子操作合成一个事务的时候。标准库已经把很多单元素容器操作做成了强保证，只有在“多个容器必须一起改”或者“外部副作用必须一起发生”时，才需要自己搭提交阶段。

`pop_value` 返回 `beta` 时，栈已经少了一个元素；调用方 `received = ...` 的赋值抛出后，`beta` 既不在栈里，也没有到达 `received`，输出里的 `received=[none]` 就是丢掉的证据。`pop_into` 把顺序倒过来：先把值复制进调用方的引用，成功后才 `pop_back`，所以赋值失败时栈仍然是 1 个元素。最彻底的还是 `top()` 加 `pop()`：查询只返回引用，弹出只负责改栈，调用方在两次调用之间自己决定什么时候复制、失败了要不要继续。

EXC-10 把这件事说成“会修改状态的函数不要按值返回”。`Pop` 同时承担“弹出元素”和“把元素交出去”两个职责；只要交付路径上还有一次可能抛的复制/移动，函数就无法保证两个副作用同时成功或同时不发生。Sutter 给的三个方案里，`void Pop(T& result)` 是最小改动，`T& Top()` 加 `void Pop()` 是更彻底的责任分离，返回内部引用则是他明确反对的做法——引用把“已经不算存在”的资源交给调用方，换个实现就会悬垂。标准库的 `std::stack::pop()` 至今返回 `void`，`std::queue::pop()` 也一样，原因正在这里。C++11 的移动语义和 C++17 的保证复制消除让交付路径上的失败窗口变小了，但没有消失：如果 `T` 的移动构造可能抛，值仍然可能丢；`std::optional<T>` 只是把“可能没有值”写进类型，没有改变“先修改栈、再交付”的顺序。

`report_by_value` 先把名字算好，再输出，最后按值返回；输出已经完成，调用方赋值失败时结果仍然丢了。`report_by_pointer` 先在堆上构造 `Name`，输出之后返回 `std::unique_ptr<Name>`，所有权转移是 `noexcept` 的移动，所以输出和交付可以按顺序完成，后者不会失败。EXC-19 的原版用 `auto_ptr` 做同样的事，C++11 起 `auto_ptr` 被弃用、C++17 从标准移除，正确的替代就是 `std::unique_ptr` 加 `std::make_unique`。如果计算本身失败，`report_by_pointer` 在输出之前就抛了，`printed=[]` 说明流没有被碰过。

这里的“原子”不是数据库意义上的原子。`report_by_pointer` 仍然可能遇到流本身写了一半就失败，标准流没有办法把已经写出的字符收回来；C++20 的 `std::format` 先把整个消息格式化成字符串，能保证“格式化失败时一个字都没写”，但底层 `write` 失败时仍然可能留下半截输出。EXC-19 因此把强保证的边界说得很清楚：函数只能控制自己手里的副作用，控制不了流、数据库、网络对端。如果两个副作用无法安排成“前面只做可能失败的计算，最后只做不抛的提交”，那就不存在强保证；这时要么退到基本保证，要么把函数拆成两个，让调用方看见这两步不可能原子完成。CCS-71 举的“发射卫星”是同一个道理：卫星已经上天之后，后面再失败，函数没有办法把它收回来。

这也解释了为什么“一个函数只做一件事”在异常安全里反复出现。`pop_value` 和 `report_by_value` 都不是因为实现写得差才不安全，而是接口本身要求它们同时完成两件不能原子完成的事。把 `top`/`pop` 分开、把“计算名字”和“输出消息”分开、把“发射”和“记录”分开，强保证才有落脚点。拆开之后，调用方会多写几行，但它能看清楚哪一步可能失败、失败了之后状态是什么，而不是面对一个“要么成功要么可能丢值”的黑盒。

## 12.5 三行代码 23 条执行路径与标准库保证

EXC-18 数过一个看似只有三行的函数：

```cpp

    cout << e.First() << " " << e.Last() << " is overpaid" << endl;
}
return e.First() + " " + e.Last();
```

正常路径只有 3 条：标题是 CEO，短路掉薪水判断；标题不是 CEO 但薪水超限；两者都不满足，不打印。剩下 20 条是异常路径：按值传参的一次复制、`Title()`/`Salary()`/`First()`/`Last()` 自己或它们返回的临时量、字符串字面量转换出的临时对象、重载的 `==`、`>`、`||`、五个 `operator<<`、返回值的 `+` 拼接和复制，每一处都可能抛。Sutter 的统计口径把被调函数当原子：只问它“正常返回”还是“抛异常”，不展开内部；参数求值顺序和析构函数抛出被忽略，因为析构抛出本身已经是设计错误。这样数出来的结论不是“别用异常”，而是“写代码时要知道哪些操作可能抛，才能决定哪一段需要强保证、测试要覆盖哪些失败点”。

这条计数方法在今天只会更复杂。C++11 的移动构造/移动赋值、lambda 捕获对象的复制、`std::function` 的构造与调用，C++17 的 `std::optional`/`std::variant` 访问，C++20 的协程和 `std::format`，都增加了可能抛的位置。C++17 的保证复制消除消掉了一些返回纯右值时的复制路径，但没有消掉函数调用、分配和用户自定义操作。`noexcept` 能在路径统计里剪掉确定不抛的分支，但前提是标得对；标错只是把“可能抛”改成了“抛了就 terminate”，并不会让异常消失。

EXC-17 把同样的思路用到标准库容器上。所有标准容器对所有操作至少给基本保证：异常之后容器仍可析构、仍处于一致状态，迭代器可以安全复制。单元素操作通常给强保证，但有明确例外；`12_5_containers.cpp` 把四种情况放在一起：

C++11 之后，容器的保证还多了一层与元素移动有关的条件。`vector` 扩容时用 `std::move_if_noexcept` 决定搬移还是复制：元素的移动构造标了 `noexcept`，就把旧元素搬过去；移动可能抛而元素又可拷贝，就退回复制，以保住强保证。如果元素只能移动、移动又可能抛，扩容失败时 `vector` 只能给基本保证——原来那些元素可能已经被移走了一部分。这也是为什么自定义类型的移动构造应当尽量标 `noexcept`（12.6 节展开）。`vector::push_back` 的标准措辞也留了这个口子：异常不是由不可拷贝元素的移动构造抛出时，操作没有效果；否则不保证。

需要强保证而标准库不给时，办法仍然是 12.3 节的“复制、在副本上改、成功后 `swap`”：`std::vector` 的 `swap` 只换缓冲区指针，是 `noexcept` 的，所以这个包装不会在提交阶段失败。C++17 的 `try_emplace` 让关联容器可以“只在插入成功时构造值”，C++20 的 `std::erase_if` 把“删除满足条件的元素”收成一次调用；它们减少了自己手写循环的机会，但没有改变“多元素操作通常只给基本保证”这个分层。选容器时如果异常安全是硬要求，先看这个操作在标准里的保证档位，再看元素类型的复制/移动是否可能抛，最后才看性能数字（[第 24 章](ch24.md)、[第 26 章](ch26.md)）。

## 12.6 异常有成本，noexcept 是接口的一部分

MEC-15 提醒过，异常处理不是免费的：即使代码里没有 `try`/`throw`/`catch`，实现也要为“哪些对象已经构造完成”准备簿记，异常抛出时还要查表、找到匹配的处理器、逐个析构局部对象。Meyers 在 1996 年给出的“代码变大 5–10%、变慢类似比例”来自当时的传闻和少量基准，他自己也提醒不要把这些数字当定律；今天的具体开销取决于 ABI、编译选项和负载，唯一稳定的结论是：**不抛时开销很小，抛出去很贵**。GCC 和 Clang 在 Linux 上使用的 Itanium C++ ABI 把栈展开信息放在独立的表里，正常路径不需要为每个 `try` 执行额外分支；但一旦抛出，分配异常对象、查表、展开栈、逐个调用析构函数的成本远高于一次普通返回。因此异常只该用于真正的例外情况，不要拿它表示“遍历结束”“循环终止”这类常见控制流；`try` 块也只写在确实要处理或翻译错误的地方，而不是给每条语句加保险。

C++11 的 `noexcept` 把“不抛”从注释变成了接口的一部分。EMC-14 的论证分两层。第一层是调用方：调用方可以查询一个函数是否 `noexcept`，并据此决定自己的异常安全策略或优化。第二层是编译器：一个 `noexcept` 函数不需要为“异常从函数里逃出去”保持可展开的栈状态，优化器可以少做很多工作。对移动构造、移动赋值、`swap` 和析构函数，这个差别尤其大，因为标准库会拿 `noexcept` 做实际决策。`12_6_noexcept.cpp` 把最直接的一处决策显示出来：

大多数函数其实是“异常中立”的：它们自己不做会失败的事，但调用的函数可能抛，异常只是从它们中间穿过去。这样的函数不应该标 `noexcept`，因为“穿过去”也是“可能发出异常”。EMC-14 还提醒了窄契约（narrow contract）的麻烦：一个函数有前置条件，平时不抛，但它可能选择在调试或测试时检查前置条件并抛出“违反前置条件”的异常；一旦标了 `noexcept`，这个检查就只能变成终止。标准库通常只给宽契约（wide contract，没有前置条件）的函数标 `noexcept`，自己的接口要不要这样做，取决于你打算怎么报告前置条件违反。

析构函数和释放函数是默认的 `noexcept`：C++11 起，用户写的和编译器生成的析构函数都隐式带 `noexcept(true)`，除非某个成员或基类的析构明确是 `noexcept(false)`。这意味着你通常不需要给析构函数手写 `noexcept`，也不应该给它写 `noexcept(false)` 来“留一条抛出的路”；`delete`/`delete[]` 同样不该抛。`swap` 则应当尽量做成 `noexcept`，并在类型所在的命名空间提供非成员版本，让 `std::is_nothrow_swappable` 和泛型代码能查到。MEC-15 还提到 `-fno-exceptions`：只有当整个程序以及链接的所有库都不使用异常时才能开，现实中很少能满足；把它当成“性能开关”之前先测量，不要凭 1996 年的比例做决定（[第 29 章](ch29.md)）。

## 12.7 动态异常规格的历史：从 throw() 到 noexcept

在 `noexcept` 之前，C++ 用动态异常规格声明一个函数“只抛哪些类型”：

```cpp
void fetch() throw(int);   // 只允许抛 int
void ping() throw();       // 声称什么都不抛
```

这套语法看起来像类型契约，实际行为却是运行期检查。函数体里抛出了列表之外的异常，实现会调用 `std::unexpected`；`unexpected` 只有两条出路：转抛一个列表允许的异常，或者调用 `std::terminate`。它不能正常返回，所以绝大多数情况下程序直接终止。Sutter 在 EXS-13 里把它称为“影子类型系统”：写进 `typedef` 是非法的，去掉 `typedef` 的同样声明却合法；函数指针赋值时会检查“目标规格不得比源更严格”；虚函数重写又要求派生类的规格不能更宽松。同一套规则在不同类型语境下不一致，编译器也无法在调用点静态检查“被调函数会不会抛出列表外的异常”。MEC-14 举的例子很直接：`void f2() throw(int)` 里完全可以调用一个没有规格、可能抛任何东西的 `f1()`，编译器不会拒绝，只有运行期撞上 `unexpected` 才知道。

动态规格还带来实打实的成本。实现要在函数体周围生成隐式的 `try/catch` 式检查，有的编译器因此拒绝内联；函数模板更写不出有意义的规格，因为作者不知道模板参数的操作会抛什么。Sutter 与 Alexandrescu 在 CCS-75 里把它归为“典型的过早劣化”：为几乎总是导致终止的检查付运行期开销。MEC-14 和 EXS-13 的结论一致：不要写动态异常规格，连空的 `throw()` 也最好别写；只有在重写一个已经带规格、自己又改不了的基类虚函数时，才跟着写一个兼容且不更严格的规格。

C++11 弃用了动态异常规格，同时引入 `noexcept`。C++17 正式移除 `throw(类型列表)` 和 `std::unexpected`/`std::set_unexpected`，只把 `throw()` 保留为 `noexcept(true)` 的弃用写法；C++20 连 `throw()` 也从标准中移除。`12_7_dynamic_spec_fail.cpp` 在 `-std=c++20` 下声明 `throw(int)`，两个编译器都直接报错：


这说明实现把它当作 `noexcept(true)` 的兼容写法保留了下来；**这不代表标准还允许它**。新代码要文档化“不抛”就写 `noexcept`，不要写 `throw()`；如果看到旧代码里的 `throw()`，把它当成历史遗留的 `noexcept(true)` 来读，而不是当成“标准仍然推荐”的写法。`std::unexpected()`/`std::set_unexpected` 也一样：标准在 C++17 移除，libstdc++ 15 在 `-std=c++17`/`c++20` 下仍以 deprecated 的形式提供，到 `-std=c++23` 才真正拿掉——因为 C++23 把 `std::unexpected` 这个名字重新用作 `std::expected` 的错误包装类型（[第 13 章](ch13.md)），两者毫无关系。

历史教训不是“异常规格这个想法不好”，而是“承诺一个自己无法静态保证的异常类型集合，代价会落在运行期”。`noexcept` 换了一种承诺：不再列出“能抛什么”，只回答“抛不抛”；它从 C++17 起进入函数类型，调用方和标准库可以查询；违反时同样 `std::terminate`，而且标准不保证栈展开。它适合移动构造、移动赋值、`swap`、析构这些本来就不该失败的操作，也适合确实不会抛的叶子函数；异常中立的转发函数、可能检查前置条件并报告错误的函数，不应该标。C++20 的 concepts 可以用 `std::is_nothrow_*` 和 requires 表达式里的 `{ expr } noexcept;` 要求把“不抛”写成约束，C++23 的 `std::expected` 则给“可预期的失败”提供了返回类型这条通道；C++26 采纳的 contracts（P2900）把前置条件、后置条件写进声明，但本书环境的 clang 21 和 GCC 15 都还不能编译它的语法，实现进展需核实。它们都没有改变一个事实：`noexcept` 是接口上的承诺，不是编译器替你做的证明。

## 回头看

这一章把“异常之后还能不能用”拆成了三层：先承诺，再实现，最后把承诺写进接口。`Gallery::replace` 说明手工管理资源时连基本保证都守不住；三档保证给出了可以写进文档的承诺，`Mailbox` 的两种投递方式则说明强保证不是免费的，它要用“在副本上做完、再用不抛的 `swap` 提交”换回来。异常安全的实现重心因此不在 `catch`，而在 `throw` 的位置、资源的归属和提交阶段的纯度：析构函数负责回滚，`swap` 负责提交，两者都必须不失败。`Pop` 和“输出加返回值”这两个例子进一步说明，有些函数的不安全来自接口本身要求它同时完成两件不能原子完成的事；这时正确的做法常常是拆函数，而不是在函数体里补 `try`。

标准库和语言在这些年接过了不少工作：C++11 的 `unique_ptr`/`shared_ptr` 让资源清理成为默认写法，移动语义让副本提交更便宜，析构函数默认 `noexcept` 把“清理不能失败”变成硬约束，`noexcept` 进入函数类型后又能被容器和泛型代码查询；C++17 的保证复制消除、`std::is_nothrow_swappable` 和 `std::move_if_noexcept` 让“什么时候移动、什么时候退回复制”有了统一规则。标准容器也给出了明确的保证分层：基本保证全覆盖，单元素操作通常强，`vector`/`deque` 的区间插入只给基本，`list` 和关联容器的单元素插入更强。但“给哪一档”“哪些副作用不能拆”“这个函数该不该标 `noexcept`”仍然要靠设计判断；标错 `noexcept` 不会让异常消失，只会把可控的失败变成 `std::terminate`。C++20 的 concepts 和 C++23 的 `std::expected` 都只能帮你表达承诺，不能替你决定承诺什么。
