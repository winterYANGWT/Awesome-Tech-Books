# 第 28 章 字符串、流与格式化

一个空的 `std::vector<char>`，把 `data()` 交给要写入的 C 函数；一个八字节的栈缓冲区，用 `sprintf` 写进一个可能九位的订单号。两行代码都能编译，甚至在测试里“碰巧”跑对：

```cpp
std::vector<char> name;
std::strcpy(name.data(), "Ada");   // 空 vector 没有可写的元素

char text[8];
std::sprintf(text, "%d", orderId); // orderId 有九位时越界
```

它们暴露的是同一类问题：C++ 的字符串和容器知道自己的大小，C API 和格式化函数却只拿到一个指针；一旦跨过边界时没有把长度和容量一起带过去，剩下的只能靠运气。本章沿着“文本和字节缓冲区怎样进出现代 C++”这条线，先看 `string` 的大小与增长为什么不能假设，再讲连续数据怎样安全地交给 C API，然后把 `sprintf` 换成类型安全的格式化，最后落到流、文件、流迭代器和字符集这些日常接口上。

这些话题看起来分散，其实都在回答同一个问题：**谁拥有缓冲区，谁知道它有多长，失败时谁负责报告**。`string` 自己拥有并维护长度；`string_view` 和 `span` 只借看，不拥有；C API 只认指针，长度要调用方另传；iostream 把格式化和缓冲藏在流对象里，状态也要调用方检查。把这条所有权和长度线索抓住，各节的具体写法就有了共同的判据。

这些数字只描述这台机器上的 libstdc++ 15。换一个标准库、换一个版本，甚至同一家的不同 ABI，`sizeof`、空串的 `capacity()`、短串优化的阈值都可能变。Meyers 在 ESTL-15 里考察了四种当时常见的实现：有的对象只有一个指针，字符串的长度、容量、引用计数和字符缓冲区都在堆上；有的对象本身就比较大，内部留了十几个字符的位置；有的使用引用计数，拷贝时共享缓冲区，写入前再分离。它们都能满足 C++98 的 `string` 接口，所以标准没有理由规定哪一种。ESTL-15 的结论不是“别用 string”，而是“继续用，但别把 `sizeof`、最小容量、是否共享写进可移植假设”；跨标准库且在意内存或分配次数时，用基准测试和实现文档确认。

C++11 和 C++17 改变了这个领域的两条底层规则。第一，`basic_string` 要求元素连续存储，`operator[]` 返回真实字符的引用，写入一个 string 不能影响另一个 string；引用计数的写时复制要实现这些语义会非常别扭，主流实现因此转向短串优化（SSO）。libstdc++ 的现代版本采用 SSO，这是实现选择，不是标准规定。第二，C++17 的 `std::pmr::string` 把分配器变成运行期多态对象，对象布局又多了一种可能。今天仍然可以放心用 `string`，但不能放心的东西没有变：`capacity()` 的精确值、扩容因子、短串是否分配，都只能测，不能猜。COW 为什么从“优化明星”变成“线程安全和迭代器失效的来源”，留到[第 29 章](ch29.md)展开。

如果自己写一个带缓冲区的类，增长策略倒是可以讲清楚。MXC-13 用一个只有指针、容量、已用长度的 `String` 说明：每次追加都按需精确分配，追加 N 个字符要 N 次分配，平均每个字符被复制 O(N) 次；每次固定加 32 字节，分配次数和复制量仍随长度线性增长；按约 1.5 倍做几何增长，分配次数是 O(log N)，每个字符平均只被复制 O(1) 次。示例把四种策略放在一起数：

## 28.2 把连续数据交给 C API，守住大小边界

C 接口没有容器，只有指针；要么再给一个长度，要么约定一个哨兵（字符串的 `'\0'`）。C++ 这边能提供连续存储的容器恰好适合做这个桥：`vector` 保证元素连续，`string` 自 C++11 起也保证连续，并且 `data()`/`c_str()` 返回的缓冲区在 `[0, size()]` 范围内有效，末尾有 `'\0'`。ESTL-16 和 CCS-78 都把这条边界总结成一句话：可以让 C API 读写**已有元素**，不能让它改变容器的 `size()` 或 `capacity()`。下面的程序把输入、输出和空容器三种情况放在一起：

空容器是另一个容易写错的地方。`&v[0]` 在 `v` 为空时对不存在的元素取地址，是 UB；C++11 起应改用 `v.data()`，它可能返回空指针，也可能返回别的合法值，但配合 `size() == 0` 传给一个不越界读的 C 函数是安全的。CCS-78 还提醒不要假设 `v.begin()` 是 `T*`：有的实现用裸指针，有的用包装类，调试模式下更可能不是指针。要地址就写 `&v[n]` 或 `&*it`，而且要先把下标算对再取地址——`&v[n]` 让带检查的实现有机会验证 `n`，`&v.front() + n` 则绕过了这次检查。

`string` 的坑在哨兵。C API 看到 `c_str()` 后会在第一个 `'\0'` 处停下，而 `string` 允许内部包含 `'\0'`；示例里的 `record` 有 10 个字符，`strlen(c_str())` 只有 3。这是 C 接口的约定，不是 `string` 丢了数据。反过来说，`std::string_view` 不保证以 `'\0'` 结尾，不能把 `sv.data()` 直接交给要求 C 字符串的函数，必须另带 `sv.size()` 或先构造 `std::string`。

C++17 给 `string::data()` 加了非 const 重载，C++20 的 `std::span<T>` 把“指针 + 长度”打包成一个参数，跨边界传参时可以优先用 `span<const T>`/`span<T>`，让长度不再靠调用双方记。C++23 的 `string::resize_and_overwrite` 进一步允许先把缓冲区交给一个写入回调，再由回调返回实际长度，适合“C API 直接写进 string”的场景；它需要 `-std=c++23`，本机 clang 21 + libstdc++ 15 可用，更早的实现需核实。无论用哪种包装，“C API 不能改变容器大小”这条边界都不会消失。跨语言边界的 ABI、对齐和所有权问题，[第 35 章](ch35.md)还会展开。

## 28.3 sprintf 既不知道长度也不检查类型，改用 to_chars/format

`std::sprintf` 有两个真实的优点：格式串表达力强，写起来短；结果直接写进调用方给的缓冲区，不经过额外的动态分配。EXS-02 把它的缺点也列得很清楚：不知道目标缓冲区多大、不检查实参类型、很难在模板里泛型使用。第一条最致命。宽度说明符 `%4d` 规定的是**最小**宽度，不是上限；因此“先 sprintf，再拿返回值和缓冲区长度比较”没有意义——等你比较时，越界已经发生：

`snprintf` 只多了一个长度参数，就把“可能必然越界”变成“最多截断”。它返回的是“如果缓冲区够大，本应写入多少字符”，返回值大于等于缓冲区大小说明发生了截断（返回负值则是编码错误）；但调用者仍可能把长度传错，所以它是长度受检，不是绝对安全。类型问题则一点没解决：`printf` 家族走 C 的变参列表，实参类型在调用点已经擦除，只能靠格式串和实参的约定。写错 `%d`/`%ld` 在 `int` 与 `long` 同样宽的平台上可能长期不报错，移植时才暴露；更隐蔽的是把整数当成 `%s` 的指针。`-Wformat` 能检查字面量格式串的一部分错误，运行期拼出来的格式串就完全无能为力；变参本身的风险在[第 35 章](ch35.md)还会讲。

EXS-03 接着比较了当年的替代品：`stringstream` 用 `operator<<` 的重载决议获得类型安全和自动扩容，也能模板化，代价是代码更长、通常多几次动态分配；`strstream` 允许复用调用方缓冲区，但从 C++98 起就被弃用，C++26 已决定将它移除（P2867R1；本书环境未实现，需核实）；`boost::lexical_cast` 只是 `stringstream` 的薄包装，做不了宽度、精度这些格式化。书里的结论是“没有唯一最优解，按安全性和实测性能选，sprintf 一律弃用”。这条框架今天仍然成立，默认答案却换了：C++17 的 `std::to_chars` 把整数或浮点写进调用方缓冲区，无分配、无 locale、按重载选类型；C++20 的 `std::format` 用格式串做 printf 式排版，但实参按类型传递，字面量格式串在编译期解析；C++23 的 `std::print`/`println` 再把结果直接写到标准输出。

## 28.4 用 streambuf 与模板统一处理控制台和文件流

`out << in.rdbuf()` 能成立，是因为 `basic_ios::rdbuf()` 返回流内部的 `streambuf`，而 `basic_ostream` 有一个接收 `basic_streambuf*` 的 `operator<<`，会把它一直读到耗尽。它短得像是技巧，适合“原样复制”这种明确场景；一旦要转换、统计或过滤，就不该把逻辑塞进这一行。MXC-01 对此给了两条工程准则：优先可读性，别写短而难懂的代码；两个方案成本相近时优先可扩展性，但别借机过度设计。更根本的是分离关注点——知道“输入从哪来、输出到哪去”的代码，不该同时知道“数据怎么处理”。

模板方案也不是没有边界。`std::istream`/`std::ostream` 是 `char` 的特化，接受它们的函数只处理窄字符；要处理 `wchar_t` 或自定义 traits 的流，就写成 `template<class C, class Traits> void process(std::basic_istream<C, Traits>&, std::basic_ostream<C, Traits>&)`。示例用 `In`/`Out` 两个类型参数更宽松，能接受 `istringstream`/`ostringstream` 这些派生类型；如果函数内部要调用 `rdbuf()` 或依赖 `istream` 的成员，参数类型就要收紧到 `std::istream&`，否则模板实例化时才报错。这是模板接口的常见取舍：参数越泛，能接受的类型越多，对成员的要求也越晚被检查。C++20 的 concepts 可以把这些要求写到签名上，第 21 章有专门讨论。

MEC-23 把同一件事放到“选库”层面：功能相近的库在性能、可移植性、类型安全上取舍不同。书里的例子是 iostream 与 stdio——stdio 往往生成更小更快的程序，iostream 类型安全、可扩展。但 Meyers 自己紧接着说基准会骗人：它只说明特定实现、特定输入下的相对表现。这个差距高度依赖实现，今天的 iostream 未必重复当年的结果；`to_chars`、`format`、`print` 又提供了新的组合。如果 profiler 证明确实卡在 I/O 上，可以换实现或换设施，但要用有代表性的负载测，不能把“stdio 更快”当成定律。反过来说，为了一个没测量过的瓶颈把整套流接口换成 `printf`，通常只是把类型安全问题换了回来。

## 28.5 大小写不敏感更适合比较操作，而不是字符串类型

`std::string` 并不是一个独立的类，而是 `basic_string<char, char_traits<char>, allocator<char>>` 的别名。`char_traits` 负责字符怎样比较、查找、复制；把其中的 `eq`、`lt`、`compare`、`find` 换掉，`basic_string` 的比较和查找语义就整体变了。EXC-02 用这个办法做了 `ci_string`：字符仍按原样存储，只是比较时忽略大小写，因此 `s == "abcde"` 为真，而 `s.c_str()` 仍然是 `"AbCdE"`。示例只改这四个函数，其余成员从 `char_traits<char>` 继承：

真正的问题是 EXC-02 的第三问：大小写不敏感应该是字符串对象的属性吗？如果 `string a = "aaa"; ci_string b = "aAa";`，`a == b` 应该为真还是假？再引入一个按第三种规则比较的 `yz_string`，两个不同 traits 的字符串相遇时，该采用谁的大小写规则没有合理答案。把规则做成比较函数或谓词，语义就明确得多；只有绝大多数比较都直接对字面量进行、并且“这个类型的值就是大小写不敏感”确实是领域语义时，做成类型才划算。大小写折叠本身还依赖语言和 locale：`toupper` 只按当前 C locale 映射，把带重音的字符、土耳其语的 `i` 这类问题交给它，答案不会是通用的；对负值 `char` 直接调用 `toupper` 还是 UB，必须先转 `unsigned char`。

C++17 的 `std::string_view` 让只读参数可以接受两种字符串而不用复制，但它不会自动做大小写折叠；C++20 的 `<=>` 也只是增加比较入口。今天如果要“忽略大小写比较两个字符串”，更轻的写法是用 `std::ranges::equal` 配一个 lambda 谓词，或者先把两边规范化再比较；只有类型本身确实应该带着这条语义时，才值得复制一份 traits 和一圈边界适配。

## 28.6 文件流默认截断，打开后先验状态

文件流最危险的两个默认行为，都不需要写错代码就会遇到：`ofstream("x")` 默认以输出模式打开并**截断**同名文件；打开失败默认**不抛异常**，只是把流置为失败状态。ACC-18 和 ESS-01 都要求构造后立刻检查流对象，区别只是前者从“打开文件”讲，后者从“默认截断/追加”讲。下面的程序把截断、追加、app 的读写位置和打开失败放在一条时间线上：

第一次和第二次用默认 `ofstream` 打开同一个文件，第二次把第一次写的 `first` 截掉了，所以只剩 `second`。要保留旧内容必须显式写 `std::ios_base::app`；`app` 的语义是每次写之前定位到末尾，不是“打开时定位一次”。

ESS-01 说以 `in|app` 打开的文件初始位置在末尾，直接读会立刻遇到 EOF，必须先 `seekg(0)`。本机实测并非如此：clang 21 + libstdc++ 15、GCC 15 以及 clang 21 + libc++ 21 下，`in|app` 和 `in|out|app` 的初始读位置都在文件开头，能直接读到第一行；只有 `out|app` 这种不可读模式的写位置在末尾。C 标准对 `a+` 的规定也是“读从开头，写总在末尾”，所以更准确的说法是：`app` 保证写定位到末尾，不保证读位置；如果某个实现把读位置放在末尾，才需要先 `clear()` 再 `seekg(0)`。示例用 `in|out|app` 验证了更有用的那半条：读完第一行后用 `io <<` 写，内容仍落到末尾；要重新从头读，必须把读位置移回去。

打开失败为什么不抛异常？因为 `fstream` 的 `exceptions()` 掩码默认是空的；只有显式调用 `exceptions(std::ios_base::failbit | std::ios_base::badbit)` 之后，失败才会以异常形式报告。默认情况下只能靠 `if (!in)` 或 `is_open()` 检查。`!in` 比 `is_open()` 更全面：它把打开失败和其他失败状态一起算进去。诊断信息写到 `std::cerr`，它默认带 `unitbuf`，每次插入后立即刷新；`std::clog` 有缓冲，适合普通日志。关闭文件不需要手动 `close()`，`ifstream`/`ofstream` 的析构函数会做；但如果要检测“写盘失败”这类关闭时才暴露的错误，就得显式 `close()` 后检查流状态，因为析构函数不会把异常抛给调用方。

文件名在 C++11 起可以直接传 `std::string`，不必再写 `c_str()`；C++17 起可以用 `std::filesystem::path`，路径拼接、存在性检查和临时目录都更直接。示例用 `temp_directory_path()` 生成临时文件，避免把测试产物留在源码目录。路径类型不改变流状态规则：`ifstream` 打开一个不存在的路径仍然只是失败状态。

读取循环的规则来自 ACC-04：用 `while (in >> value)` 或 `if (in >> value)` 检查这次读取是否成功，不要写 `while (!in.eof())`。`eof()` 只有在**尝试读取之后**才可能置位，用它控制循环会把最后一次旧值多处理一遍。读取失败后，`value` 里可能是旧值、部分写入的值或根本没动，不能拿来用；已经成功读入容器的元素仍然有效，只是不要把失败那一次算进去。如果还要继续读，先 `clear()` 清状态，再 `ignore()` 掉坏字符；只 `clear()` 会让下一次读取从同一个坏字符重新失败。

流的状态位值得单独记一下：`goodbit` 表示一切正常，`eofbit` 表示读到文件尾，`failbit` 表示格式转换失败或打开失败，`badbit` 表示更严重的 I/O 错误。`operator bool` 在 `failbit` 或 `badbit` 置位时返回 false，所以它适合做“这次操作成功了吗”的判断；`eof()` 只回答“是不是读到尾了”，不适合当循环条件。ACC-04 的这条建议在 `std::views::istream` 这类新设施里仍然成立：设施换了，失败后不要用旧值这条规则没变。

## 28.7 流迭代器构造即预读，endl 会 flush

ACC-12 和 ESS-05 讲的是同一组工具的两种用法：`istream_iterator<T>` 把输入流包装成单遍输入迭代器，`ostream_iterator<T>` 把输出流包装成输出迭代器，于是 `copy`、`transform` 这些算法可以直接读写流，不必先落进容器。坑在构造：`istream_iterator<T> it(in)` 的构造函数里已经执行了一次 `>>`，所以还没 `++it`，`*it` 就能读到第一个值；表示区间终点的不是某个带流对象的迭代器，而是**默认构造**的 `istream_iterator<T>{}`。示例先打印构造后立刻解引用的值，再用默认构造的 `end` 做 `copy` 的终点：

```cpp
{{#include code/ch28/28_7_stream_iterators.cpp}}
```

输出：

```text
{{#include code/ch28/28_7_stream_iterators.out}}
```

`copy` 的输入迭代器是按值传的，算法内部推进的是副本，调用方的 `it` 不会跟着到结尾；但副本与原迭代器共享同一个流，算法把流读完后，原来的 `it` 也不该再用来继续读。这是迭代器接口的常态，不是流迭代器特有的。流迭代器真正特殊的是单遍：它不能回退，也不能保存下来再遍历第二次；读过的值不会留在流里，需要多趟访问就先存进容器。默认的 `>>` 还会跳过空白，所以 `istream_iterator<std::string>` 读到的是一个个单词，空格和换行都丢了；要逐字符保留空白，得关掉 `skipws` 或改用下一节的 `istreambuf_iterator`。

输出侧的 `ostream_iterator<int> out(os, ", ")` 第二个参数是每个元素后的分隔符，省略就什么也不加。注意示例的输出是 `[10, 20, 30, ]`：分隔符写在每个元素之后，最后一个元素后面也有一个。要精确控制分隔符，就在循环里判断是否首元素；把 `ostream_iterator` 当“自动处理分隔符”的工具会多出尾部分隔符。C++20 的 `std::views::istream<T>` 提供了 range 形式，语义仍是按 `>>` 读、仍是单遍，`ranges::to` 可以把结果物化到容器；它没有改变“构造/开始遍历时就会读”的基本模型。

`endl` 是另一个常被误认为“换行的另一种写法”的东西。它的语义是写入 `'\n'` 之后调用 `flush()`，也就是让流的缓冲区立刻同步到目标。示例用一个只实现 `overflow`/`sync` 的 `CountingBuf` 把这件事变成计数：写 `'\n'` 后 `sync` 次数仍是 0，写 `std::endl` 后变成 1。差别在大量小输出时最明显：循环里每条都 `endl`，本来可以合并的写出被拆成多次系统调用；只要换行就写 `'\n'`，需要立刻看到输出（日志、进度、崩溃前的诊断）时才 flush。

`std::cerr` 默认带 `unitbuf`，每次插入后都会刷新，往它写 `endl` 的 flush 意义不大；`std::cout` 的缓冲策略还受输出目标是终端还是管道、以及是否与 stdio 同步影响。需要表达“现在刷新”时，用 `std::flush` 比 `endl` 更清楚：

```cpp
std::cout << "正在处理 " << i << std::flush;
```

这条短句只写一个值，放在这里是为了说明意图；循环里是否真的需要每次刷新，要看输出给谁看、丢了会怎样。到了 C++23 的 `std::println`，换行仍然只是换行；刷新策略要看具体设施，不能把换行当 flush。

逐字符读流用 `std::istreambuf_iterator<char>`。ESTL-29 的解释是：`istream_iterator<char>` 走 `operator>>`，每次都要构造 sentry、检查流状态和异常掩码、按格式化规则解析；`istreambuf_iterator` 直接通过 `rdbuf()->sgetc()` 取缓冲区里的字符，不跳过空白，也不做格式转换。示例里同一段 `"  ab\ncd  "`，`istreambuf_iterator` 原样读到 9 个字符，`istream_iterator<std::string>` 只读到 `ab` 和 `cd` 两个单词。输出侧对应的是 `ostreambuf_iterator`，比 `ostream_iterator` 少一层格式化开销。要一次读入整块数据，`istream::read` 配合已知长度通常比逐字符迭代更快；C++23 的 `string::resize_and_overwrite` 可以先把 string 的缓冲区交给读操作，再设定实际长度。`std::views::istream<T>` 仍然是按 `>>` 读，解决不了保留空白的问题。

`atoi` 的问题不是“不检查错误”，而是它**没有能力**报告错误：`atoi("0")`、`atoi("abc")`、`atoi("")` 都返回 0，调用方无法区分“值就是 0”和“根本没解析出数字”；溢出还是 UB。TIC-27 因此建议用 C++17 的 `std::from_chars`：它不抛异常、不分配、不需要 `'\0'` 结尾，返回一个 `std::errc` 和一个指向停止位置的指针。示例里 `"12x"` 解析出 12 但 `ptr != end`，说明只消费了前缀；`"999999999999999999999"` 返回 `result_out_of_range`；`"abc"` 返回 `invalid_argument`。要判断“整个字段都合法”，必须像示例一样再检查 `ptr == end`，只看 `ec` 是不够的。若错误就应该抛异常，`std::stoi` 也可以，但它用异常报告错误，会抛 `invalid_argument`/`out_of_range`，内部还依赖 `strtol` 的语义，行为和 `from_chars` 不完全相同；C++23 的 `std::expected` 则适合把解析错误放进返回值，具体封装方式需核实。

字符集方面，ACC-26 的规则很短：标准只保证 `'0'` 到 `'9'` 的编码连续，所以 `c - '0'` 可以把数字字符转成数值，`d + '0'` 可以转回去；字母、标点不保证连续，`'a' + 1 == 'b'`、`c - 'A'` 在 EBCDIC 这类字符集上会错。判断字母用 `std::isalpha`/`std::isdigit`，转换用 `std::toupper`/`std::tolower`，并且先把 `char` 转成 `unsigned char`——直接把负值传进 ctype 函数是 UB。示例对 `'7'`、`'a'`、`'A'` 分别打印分类和转换结果。`toupper` 只按当前 C locale 工作，处理 Unicode 文本要靠专门的库；C++20 的 `char8_t`/`std::u8string` 只是把 UTF-8 字节的类型标出来，不会让字母范围变得可移植。

字面量是只读数组。TIC-03 写作时 `char* p = "howdy";` 还只是被弃用，C++11 起标准不再允许这种隐式转换；字面量的类型是 `const char[N]`，示例用 `static_assert` 证明了这一点。要修改内容，先复制到 `std::string` 或字符数组 `char buf[] = "howdy";`；只读传递用 `const char*`，C++17 起优先 `std::string_view`。不要把 `string_view` 指向一个临时 `std::string`，视图不拥有数据，临时对象销毁后它就悬垂了。对这条已经非法的转换，GCC 和 clang 默认都只给警告（clang 的警告名是 `-Wwritable-strings`，GCC 是 `-Wwrite-strings`），把它当错误还是当扩展由编译器旗标决定；示例用 `-Werror=write-strings` 让两个编译器都拒绝：

## 回头看

这些小节看起来分别在讲 `string` 布局、C API、格式化、流和字符集，合起来其实只有一条线：**缓冲区归谁所有、长度由谁知道、失败由谁报告**。`string` 和 `vector` 自己拥有缓冲区并维护长度，所以它们能安全地扩容、能给出 `data()` 和 `size()`；一旦把指针交给 C API，长度和维护责任就临时转到了调用方，越界不会再有人替你兜住。格式化设施的区别也在这里：`sprintf` 只拿到一个指针，长度和类型都不在它的视野里；`snprintf` 补上了长度；`to_chars` 让调用方给容量并返回写入终点；`format` 则把结果的所有权收回标准库，同时把格式串和实参类型的匹配提前到编译期。流的 `rdbuf`、状态位和 `endl` 同样是所有权与责任的问题：缓冲区在流对象里，刷新和失败检查就得由使用流的人决定什么时候做。

C++11 以后，语言和标准库确实兜住了一部分：`string` 保证连续，`data()` 在 C++17 后可直接写，`string_view`/`span` 把“指针 + 长度”变成类型，`from_chars`/`to_chars` 和 `format` 把格式化的长度与类型安全补上，`filesystem::path` 让文件名不必再猜编码。仍然要靠写法、警告和工具的是另一半：C API 不会因为参数是 `span` 就自动尊重长度，文件流的默认截断和失败状态不会自己报告，运行期拼出来的格式串仍只能运行期检查，大小写折叠和字符集假设仍取决于 locale 与实现。ASan 能抓住示例里那两次越界，`-Wformat` 能抓住字面量格式串的一部分错误，`-Wwrite-strings`/`-Wwritable-strings` 能提醒字面量不可写；但“空 vector 上取 `&v[0]`”“C 函数偷偷写了第 4 个元素”“`atoi` 把失败折成 0”这些，编译器通常不会替你发现。边界处的长度参数、失败后的状态检查、以及对“这个假设是否可移植”的自觉，仍然得写在代码里。
