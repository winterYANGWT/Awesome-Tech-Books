# 第 32 章 宏与预处理器：最后手段

结算代码里有一个“取较大值”的宏，平时算出来的数字都对，直到有人把自增写进了实参：

```cpp
#define MAX(a, b) ((a) < (b) ? (b) : (a))
int i = 20, j = 10;
int m = MAX(++i, j);   // i 变成 22，不是 21
```

展开后的条件是 `(++i) < (j) ? (j) : (++i)`：条件里的 `++i` 把 `i` 加到 21，比较为假，选中的分支又是 `++i`，于是 `i` 变成 22。宏不认得 `++`，它只认得记号。同一类问题还有更安静的版本：一行注释以 `??/` 结尾，在 C++17 之前会被换成反斜杠，再把下一行拼进注释，下一行的自增就凭空消失了。这两个例子一个来自文本替换，一个来自翻译阶段，都发生在语法分析和类型检查之前。

预处理器不是编译器的一部分，它只做记号级的替换、条件包含和文件包含。C++ 用 const、enum、inline、template 管住宏原本要表达的东西，后来又加上 constexpr、lambda；这些设施都受类型、作用域和重载规则约束。本章先看常量宏和函数宏怎样让位给语言设施，再看宏在名字和翻译阶段上留下的坑，最后看字符串化这个仍值得保留的技巧。

## 32.1 宏的合理用途只剩少数几种

上面的 `MAX` 其实已经写得很小心：每个参数都加了括号，整个展开也加了括号。它仍然可能把实参求值两次，因为 `a` 在宏体里出现了两次。把 `MAX` 换成 `std::max` 或一个 `inline` 函数，实参只求值一次，类型由编译器检查，重载决议也会正常工作。Meyers 在 EC-02 里把这件事概括成“让编译器而不是预处理器看见常量和函数”，理由不只是风格：宏名在预处理后就从源码里消失了，它通常不进符号表，编译错误里剩下的是字面值，调试器也看不到你写的名字。

常量宏的第一个代价是丢掉类型和作用域。`#define TAX_RATE 0.08` 没有类型，也没有“私有”这一说；一旦定义，它就在本翻译单元里一直有效到 `#undef`，连类成员、函数参数和别的命名空间里的同名标识符都会一起被替换。`constexpr double kTaxRate = 0.08;` 有类型，受作用域约束，可以放进类里、命名空间里或函数里，也可以取地址。EC-02 当年还担心浮点常量宏会在目标代码里复制多份，而 `const` 对象只有一份；这条理由今天弱得多，优化器通常会把常量折叠掉，但符号表和调试信息这条代价没有变。

第二个代价是函数宏既不像函数，也不像模板。`inline` 函数有参数类型、有返回类型、能重载、能递归；宏没有参数类型，不能重载，也不能递归。EC-02 给的替代路线是 `const`/`enum` 管常量、`inline` 管函数；C++11 之后这条路线更宽：`constexpr` 变量和函数能在编译期求值，`enum class` 给枚举一个独立类型，可变参数模板和 lambda 接过了大部分“写一个像函数的宏”的需求。类内常量也变了：C++98 允许在类内初始化 `static const` 整型成员，但有些老编译器不接受，需要数组边界时人们就用 `enum { NumTurns = 5 };` 这种“enum hack”绕过；C++11 允许 `static constexpr` 成员，C++17 又规定 `static constexpr` 数据成员隐式 `inline`，于是类外那行定义也不用写了。老代码里的 enum hack 仍然合法，认得出它就行，新代码不必再写。

EC-02 还提醒常量指针要写两个 `const`：`const char* const authorName = "..."` 少了第二个，指针本身就能被改；今天更常用的写法是 `constexpr std::string_view`。把头文件里的常量改成 `const`/`constexpr` 还会遇到链接问题：命名空间作用域的 `const` 对象默认内部链接，每个翻译单元各一份，放在头文件里不会重复定义；要全程序共享同一个对象，C++17 起写 `inline constexpr`，或者用 `extern const` 配一处定义（细节见[第 33 章](ch33.md)）。

MXC-34 没有把预处理器一棍子打死。Sutter 列出的例外包括：头文件保护、`__FILE__`/`__LINE__`/`__DATE__`/`__TIME__` 这类预定义宏、`#`/`##` 运算符，以及为可移植性或调试而做的条件编译；平台差异大时优先用工厂或抽象接口，差异很小时才用条件编译，而且放在 `.cpp` 里。他的 Guideline 是“避免预处理宏”，例外只留 `#include` 守卫、`.cpp` 里（不是 `.h` 里）的可移植/调试条件编译，和包在可移植性条件里的 `#pragma` 警告抑制。MXC-34 举的错误码表就是 X-macro 的思路：把一张表只写一遍，展开成 `enum` 和查找表。调试代码他建议写成 `if (MY_DEBUG)` 这种常量条件，而不是 `#ifdef`，这样只有一份程序要编译和测试，编译器能检查被关掉的那段代码，也能把死代码消掉。

这些例外在今天要按新工具重新排一下。`std::source_location`（C++20）能在日志和断言里取代 `__FILE__`/`__LINE__`；C++17 的 `if constexpr` 能取代一部分用宏做的编译期分支；C++20 modules 能减少头文件守卫，但条件编译仍归预处理器管，模块接口里的宏也不会随 `import` 导出。`#pragma once` 在 clang 和 GCC 上都能用，但它仍然不是标准；`#include` 守卫是可移植的写法。`__DATE__`/`__TIME__` 还会让构建不可复现，发布构建里最好避开。探测标准库能力仍然只能靠预处理器：`__cpp_lib_source_location`、`__has_include` 这些宏就是为“问实现有没有某个特性”而存在的。

## 32.2 max 宏会被优先级、重复求值和改名坑到

MXC-35 拿 `max` 当标本，列出四类坑。第一类是参数没加括号：`#define max(a,b) a < b ? b : a` 收到 `max(i += 3, j)`，展开成 `i += 3 < j ? j : i += 3`，`+=` 的优先级比 `<` 低，实际含义变成 `i += (3 < j ? j : (i += 3))`。第二类是整个展开没加括号：即使写成 `((a) < (b) ? (b) : (a))`，`max(i, j) + 42` 也要看条件走哪边，`+42` 只加在其中一个分支上。第三类是重复求值：`a` 在宏体里出现两次，`max(++i, j)` 可能自增两次，`max(f(), p)` 可能调用 `f()` 两次；自增几次甚至取决于比较结果。

第四类是名字篡改，EXS-31 把它写成了一个完整的调试故事。某个平台头文件为了兼容，写了 `#define Sleep SleepEx`。源码里从此没有 `Sleep` 这个记号：符号表和链接映射里找不到它，调试器却又能正确步进到函数体，因为真正被编译的是 `SleepEx`。如果 `SleepEx` 恰好是库里已有的函数，你的 `Sleep` 就成了它的一个隐式重载；不同调用点按各自的实参类型做重载决议，于是“有时调用我的版本，有时调用库的版本”。宏不认类型，也不认作用域：全局变量、类成员、别的命名空间里的同名实体都会被一起改掉。Sutter 的 Guideline 很直接：避免宏；绝不要写以常用词或常见缩写命名的宏；优先用命名空间封装名字；实在要写，就用长而独特、带项目前缀的名字，不放进头文件，用完立刻 `#undef`。

错误落在 `bits/algorithmfwd.h` 里，而不是我们写 `#define` 的那一行。`<algorithm>` 里的 `min` 声明被宏当成一次调用，参数个数对不上，函数名也被替换掉。在包含之后再定义 `max` 宏，头文件能保住，但之后每次写 `std::max(3, 5)` 仍会展开成 `std::((3) < (5) ? (5) : (3))`，一样编译不过。宏的作用范围是“从定义点到文件末尾”，它不认识 `std::`，也不认识命名空间。

MXC-35 还列了几条不是坑、但绕不过去的限制：宏不能递归展开，没有地址，调试器通常只能看到展开后的代码；宏名从定义点一直有效到文件末尾，`#undef` 只是从那一行起解除，前面已经展开的代码不受影响。这就是为什么库头文件里的宏一旦泄漏，使用者很难在本地把它关掉。

EXS-28 讲的是同一层上的另一个问题：关键字不是空白。C++98/03 里 `auto` 是冗余的存储类说明符，写不写都一样，`auto int(j);` 照样声明 `j`，`auto int f();` 仍然被解析成函数声明（尽管 `auto` 用在函数上不合法）；Sutter 还指出标准注释里“auto 可用来区分声明与表达式”的说法是错的。C++ 消歧的总规则是“只要能解释成声明就按声明处理”，加不加 `auto` 都不改变这一点。C++11 把 `auto` 重新定义为从初始化器推导类型的占位符，今天写 `auto i = v.begin();` 是标准写法，而 `auto int j = 0;` 不再是可移植代码。`register` 走的是另一条路：C++11 弃用，C++17 连同这个存储类说明符一起移除。被语言回收又重新分配的名字不止这两个：`export` 的导出模板语义在 C++11 被移除、关键字本身保留，C++20 又把它给了模块；`inline` 在 C++17 从“给编译器的提示”扩展到变量。本机实测两家编译器的诊断并不一致：`-std=c++17/20` 下，clang 21 对 `auto int j` 只给 `-Wauto-storage-class` 警告并按扩展接受，GCC 15 直接报错；`register int x;` 则是 clang 报错、GCC 只给 `-Wregister` 警告。两边都不该写。把当前没有语义的记号当成空白，和用宏占用一个常用词，是同一个错误：名字的语义由语言决定，语言随时可以把它收回去。

今天的替代写法很直接：要最大值用 `std::max`，要类型无关就用函数模板或 `constexpr` 函数，要一组同名的操作就写重载，要避免重名就放进命名空间。clang-tidy 的 `bugprone-macro-parentheses` 能抓出没加括号的参数，也能提示 `x / 2` 这类需要整体加括号的展开；`bugprone-macro-repeated-side-effects` 专门盯实参里的副作用被重复展开，此外还有 `bugprone-multiple-statement-macro`。`-Wunused-macros` 抓定义了却没用的宏。这些工具能挡住 MXC-35 的前三类坑，挡不住第四类：一个叫 `log` 的宏从定义点开始替换，编译器不会觉得奇怪，只有读代码的人和 `__func__` 会。

## 32.3 不可见字符能改写程序，合法代码也可能像笔误

EXS-32 里有一个真实事故：一条注释以几个问号加斜杠结尾，下一行的自增就再也没执行。原因是 `??/` 是 trigraph，在翻译阶段 1 被替换成反斜杠，阶段 2 再把反斜杠和行尾换行一起删掉，下一行于是并进了注释。C++17 移除了 trigraph，`??/` 从 C++17 起只是普通的三个字符，同样的代码会正常自增；但“反斜杠续行”本身没有消失，注释行尾直接写一个 `\` 仍然会吞掉下一行。这个坑不是宏造成的，却和宏同属一层：它们都发生在 C++ 语法和类型系统看到代码之前。

标准把翻译过程分成若干阶段，理解这几个阶段比记个别陷阱有用。阶段 1 处理 trigraph（C++17 前）和通用字符名；阶段 2 删除反斜杠加换行的续行；阶段 3 把源码分解成预处理记号，同时识别并删除注释；阶段 4 才执行预处理指令和宏展开。顺序决定了几件事：注释是在续行之后才被删的，所以注释里的反斜杠能改变注释的边界；宏在阶段 4 才展开，所以宏不能生成 trigraph、通用字符名、续行反斜杠、注释，也不能生成另一条预处理指令；字符串字面量和字符字面量在阶段 3 已经是单个记号，宏不会去替换里面的名字。MXC-35 提到过一种“用 `##` 拼出注释”的写法，它在某些编译器上能工作，但标准不允许，能工作只说明那个编译器没有按阶段实现。

两个示例都关掉了相关警告，否则在 `-Werror` 下根本跑不起来。clang 21 在 C++14 下对 trigraph 版本报 `-Wcomment`；GCC 15 同时报 `-Wtrigraphs` 和 `-Wcomment`。反斜杠版本两家都报 `-Wcomment`。警告名不同，结论一样：这类字符值得让编译器喊一声。EXS-32 提醒过不要指望警告兜底，它引的 GCC 文档曾说“注释内的 trigraph 不影响语义，所以不警告”，而那个真实事故正是反例；今天 GCC 已经会报，但不能把“这次没警告”当成“这次没问题”。

不可见字符不只 trigraph 一种。源码里混进零宽空格（U+200B）时，clang 21 报 “character <U+200B> not allowed in an identifier”，GCC 15 报 “extended character is not valid in an identifier”；全角分号 `；` 会被 clang 当成数字字面量的后缀，给出 “invalid suffix” 加一个“标识符里有非法字符”的错误（本机实测）。这些大多会变成硬错误，真正危险的是落在注释、字符串和行尾的那些：编译器不会报，读代码的人也看不见。把编辑器设成显示空白字符、评审时用能高亮非 ASCII 的 diff 工具，比事后搜索有效。

逐条拆开：`0[p]` 和 `p[0]` 等价，因为 `x[y]` 的定义就是 `*(x + y)`，加法可交换；`and` 和 `not` 是 `&&` 和 `!` 的替代记号（alternative token），它们是关键字，不是宏，不需要包含任何头文件；`:>` 是 `]` 的 digraph，`p[1:>>p[2]` 就是 `p[1] > p[2]`；`<:` 和 `:>` 分别可以写 `[` 和 `]`，于是 `int a<:LIMIT:>` 就是 `int a[3]`；`%:` 是 `#` 的 digraph，行首的 `%:define` 就是一条 `#define`；类作用域里多一个分号是空成员声明，命名空间作用域的空声明从 C++11 起也明确合法。C++17 删掉的是 trigraph，digraph 和 `and`/`not` 这些替代记号都保留了下来。判断这些代码要看记号，不能看形状。

## 32.4 字符串化宏仍值得留在日志库里

调试时最常写的一种输出是“把表达式和它的值一起打印”：

```cpp
std::cout << "a + b = " << a + b << '\n';
```

表达式写了两遍，改代码时很容易只改一处，日志里于是留下一个和值对不上的字符串。《Thinking in C++》在讲调试技巧时给了一个很短的 `P` 宏，用 `#` 把实参变成字符串，调用 `P(a + b)` 就能打印 `a + b: 3`（TIC-32）。`#` 是预处理器的字符串化运算符：在宏体里写 `#参数`，预处理时会把该实参的记号序列变成一个字符串字面量，中间的空白序列压成一个空格，首尾空白去掉。它只认实参写在源码里的样子，不认类型，也不认值。`#x` 产生的是字符串字面量，所以能和相邻的 `" = "` 在编译期拼成一个字符串，不需要运行时连接。

字符串化有两个容易踩的细节。第一，`#x` 不会展开实参里的宏：如果 `LIMIT` 是 `#define LIMIT 10`，`#LIMIT` 得到的是字符串 `"LIMIT"`，不是 `"10"`。要拿到展开后的文本，得套两层：外层宏把实参展开，内层宏再做字符串化。第二，`#` 和 `##` 只能出现在宏定义里，不能当普通运算符用；`##` 负责把两个记号粘成一个，字符串化只负责变成一个字符串。两者都是预处理阶段的事，拿不到任何类型信息。

一个能用的日志宏大概是这样：

```cpp
{{#include code/ch32/32_4_stringize_log.cpp}}
```

输出：

```text
{{#include code/ch32/32_4_stringize_log.out}}
```

`LOG_EXPR(a + b)` 打印的 `a + b` 来自 `#expr`，3 来自实际求值；`LOG_EXPR(next())` 只调用 `next()` 一次，因为宏体先把实参存进 `value`，之后只用 `value`。`LOG_EXPR(LIMIT)` 打印的是 `LIMIT = 10`，`STRINGIZE(LIMIT)` 打印的是 `10`，这两行把“单层不展开、双层才展开”摆在了同一个输出里。`LOG_EXPR(a  +   b)` 里的多个空格被压成一个，这是字符串化的标准行为：它保留记号，不保留排版。最后一行用 `std::source_location` 的默认实参 `current()` 拿到调用点的行号和函数名，`__LINE__`/`__FILE__` 能做的事，C++20 起有了类型安全的替代。

多语句宏必须包成一条语句，`do { ... } while (0)` 是标准做法：

```cpp

```

clang 的诊断：

```text
{{#include code/ch32/32_4_log_macro_fail.out}}
```

宏体写成 `{ ... }` 时，调用点的 `TRACE("ok");` 展开成 `{ ... };`，那个分号是一条空语句，后面的 `else` 就没有可以配对的 `if` 了。clang 21 报 “expected expression”，GCC 15 报 “‘else’ without a previous ‘if’”（本机实测），措辞不同，问题相同。改成 `do { ... } while (0)` 之后，整个宏加上调用点的分号是一条 `do` 语句，`if (ok) TRACE("ok"); else ...` 就能正常配对。这个写法还有两个约束：调用点必须写分号，宏体里的实参要么只出现一次，要么先存进局部变量；否则重复求值的问题会从 `max` 宏原样搬过来。

日志宏通常还要接可变参数。C++11 的可变参数宏用 `__VA_ARGS__` 转发参数，C++20 又加了 `__VA_OPT__`，可以在参数为空时决定那个逗号去留：`#define LOG(fmt, ...) std::printf(fmt __VA_OPT__(,) __VA_ARGS__)` 既能写 `LOG("hello\n")`，也能写 `LOG("%d-%d\n", 1, 2)`。`__VA_OPT__` 需要 `-std=c++20`，Clang 21 和 GCC 15 都已支持（本机用 `-Werror` 实测）。

工具方面，`printf` 风格的日志宏可以靠 `-Wformat` 检查字面格式串；换成 `std::format` 且格式串写成字面量时，格式错误在编译期就会报出来，能提前到构建阶段。字符串化宏今天的位置，是“库的实现细节”，不是每个文件里随手定义的 `P`。测试框架的 `CHECK(expr)`、日志库的 `LOG(expr)` 需要把表达式原文写进失败信息，这是 `#x` 仍然不可替代的地方；`std::source_location` 能给出位置，`std::format`（C++20）和 `std::print`（C++23）能给出格式化的值，但都拿不到“用户写的是 `a + b`”这段文本。把宏封装进库，调用方看到的是 `CHECK(a + b)` 这样的接口，宏名、`do-while`、`#x`、`#undef` 都藏在库里，污染范围和重复求值的风险才收得住。`assert` 至今仍是宏，也是同一个原因：它要记录失败的表达式原文，还要能被 `NDEBUG` 整体关掉。C++26 已经采纳 contracts（P2900），语法是 `pre(...)`/`post(...)`/`contract_assert`，但本书环境的 Clang 21 和 GCC 15 都不支持最终语法，短期内 `assert` 宏仍是可移植的选择。

## 回头看

四节讲的是同一件事的四个面。预处理器在语法、类型和作用域规则之前工作，所以它能做编译器做不到的事：条件包含、按一张表生成重复代码、把表达式原文带进日志；也正因为在规则之前，它看不见类型、作用域、重载，连模板的尖括号都数不对。EC-02、MXC-34、MXC-35、CCS-16 的警告仍然成立，变的是替代品的密度：`constexpr`、`enum class`、`inline` 变量、`if constexpr`、`std::source_location`、modules 把常量、函数、调试分支、位置信息和头文件边界一个个接了过去，宏的合理用途收缩到条件编译、特性探测、字符串化和 X-macro 这几处。EXS-31、EXS-32 提醒的是另一面：名字和字符这一层一旦被改写，后面的类型检查再严也看不见。EXS-28 则反过来了：它当年说 `auto`/`register` 是空白，今天这两个词恰好证明名字的语义会被语言收回——`auto` 从“空白”变成类型推导，`register` 从“提示”变成非法；再加上 `Sleep` 被宏改成 `SleepEx`、注释行尾的 `??/` 吞掉下一行，这些都是同一层上的事故。

今天能交给工具的就交给工具：`-Wcomment`、`-Wtrigraphs`、`-Wempty-body`、`-Wunused-macros` 各自守住一类字符或空语句，clang-tidy 的 `cppcoreguidelines-macro-usage`、`bugprone-macro-parentheses`、`bugprone-macro-repeated-side-effects`、`bugprone-multiple-statement-macro` 守住宏的写法。工具守不住的是“这个宏名会不会替换掉别人的函数”“这行注释的结尾有没有看不见的字符”“这个 `for` 后面的分号是不是手滑”，这些只能靠按记号读代码的习惯和评审。宏没有消失，但它应该待在库里、待在实现文件里、待在条件编译的少数几行里，而不是散落在业务代码中间。
