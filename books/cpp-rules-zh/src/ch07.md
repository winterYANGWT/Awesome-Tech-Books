# 第 7 章 移动语义：什么时候移动真的省了

`std::move` 长得像一次操作，实际上只是一个 cast：它把表达式标成右值，让重载决议去选移动构造或移动赋值（EMC-23、EMC-25 把这一步拆得很细，见[第 5 章](ch05.md)）。真正会不会搬走东西，取决于目标类型有没有可用的移动操作、这次移动便不便宜、当前语境允不允许它抛异常，以及源对象是不是右值。下面这段代码把这四件事压在一行里：

```cpp
struct Profile { std::string name; std::vector<int> history; };

void adopt(Profile&& incoming) {
    Profile taken = std::move(incoming);   // 形参是右值引用，可以掏空
}

Profile p{"Ada", {1, 2, 3}};
adopt(std::move(p));   // p 的 name/history 可能已被搬走
```

`adopt(p)` 编译不过，因为 `Profile&&` 只接右值；加上 `std::move` 才能通过，而这一加也就把“可以搬”的许可交给了 `adopt`。此后 `p` 仍然有效，但它的值已经不在语言保证的范围内。移动语义最容易被误解的地方就在这里：它是一套有条件的优化，不是一次无条件的内存转移。

沿着这条线，本章要回答四个问题：移动在什么条件下才真的发生、才真的便宜；一个注定要被复制的形参该按值还是按引用接；临时对象从哪里来、返回值能不能被消除；临时对象到底是不是 const，以及为什么不能拿拷贝构造的调用次数当程序语义。四个问题都指向同一件事：先看语义和所有权，再看能不能省下这次拷贝。

## 7.1 移动不一定发生，sink 参数要按条件选

先看一个常见的直觉：`auto b = std::move(a);` 对 `std::vector` 只是偷走几个指针，对 `std::array` 却要逐个元素移动。两者都叫“移动”，成本差了一个数量级。Meyers 在 EMC-29 里把结论压成一句：在泛型代码和类型不稳定的代码里，应当假定移动操作不存在、不便宜、也不会被使用；只有当你确知具体类型、也确知当前语境会调用移动时，才可以依赖它。

“不存在”是第一种情况。很多旧类型没有移动构造，或者因为用户声明了拷贝构造、拷贝赋值或析构函数而抑制了移动操作的生成（[第 6 章](ch06.md)）。对这类类型，`std::move` 只是把实参标成右值，重载决议最后还是落到拷贝构造上，一次也不会少。“不便宜”是第二种情况：`std::array` 的数据直接放在对象里，没有可偷的堆指针，移动它必须遍历每个元素；`std::string` 在启用小字符串优化（SSO）时把短字符串放在对象内部的缓冲区里，移动同样要复制这段缓冲区。“不会被使用”是第三种情况：即使类型有高效的移动构造，只要它没有声明 `noexcept`，`std::vector` 为了维持强异常安全保证，在扩容时仍可能改选拷贝；EMC-14 对这个选择有完整分析（[第 12 章](ch12.md)）。第四种情况更基础：左值不能作为移动源，除非你显式写 `std::move` 或 `std::forward`。

把视角从“移动一个对象”换到“函数怎么接参数”，会得到另一组选择。Sutter 与 Alexandrescu 在 CCS-25 里先要求分清输入、输出、输入输出三类语义：纯输入参数，指针和引用一律加 `const`，基本类型和拷贝廉价的小对象按值传，其余用户定义类型按 `const&` 传；输出或输入输出参数，如果实参可能缺失，或者函数要保存指针、插手所有权，就用（智能）指针，实参必需且函数不保存它时用引用。这个分类今天仍然有效，只是 C++11 之后多了一种“函数本来就要一份拷贝”的 sink 形参。

Meyers 在 EMC-41 里把 sink 形参的条件列得很窄：类型可拷贝、移动便宜、形参总是被复制进成员或容器、并且不涉及多态切片。四条都满足时，按值接参再 `std::move` 进目标，代码只写一份，左值实参付一次拷贝加一次移动，将亡值实参付两次移动（C++17 起纯右值实参在初始化形参时能消除一次，只剩一次移动）；作为对照，`const&` 加 `&&` 的重载对左值只付一次拷贝，对右值只付一次移动。按值方案多出来的那次移动通常很便宜，换来的是少写一个重载、少一份文档、少一份目标代码。C++17 起，纯右值实参初始化按值形参时可以保证消除这次移动，所以 `shelf.add_value(Label("x"))` 这种调用只剩进入容器时的一次移动；如果实参是 `std::move(lvalue)` 这样的将亡值，按值形参仍要先移动构造，总共两次移动。

按值还有两个硬限制。第一，移动-only 类型（例如 `std::unique_ptr`）不能按值接左值，因为拷贝构造已被删除；此时 `T&&` 形参只需要一次移动，按值反而要两次，EMC-41 因此明确把按值限定在“可拷贝”的类型上。第二，按值会发生切片：如果形参类型是基类，传入派生类对象时派生部分会被切掉，多态接口只能用引用或指针。通用引用加 `std::forward` 是第三条路，能同时接左值和右值，也能对可转换类型做到零临时对象，但它会把实现推到头文件里，还会遇到推导失败和错误信息难读的问题（[第 5 章](ch05.md)、[第 21 章](ch21.md)）。泛型接口还可以用 C++20 的 concepts 把“可拷贝、可移动”写成约束，用 `std::remove_cvref_t<T>` 把转发引用推导出的引用和 cv 去掉再作判断；这些工具让错误更早暴露，但不改变按值/按引用的成本账。C++23 的 `std::forward_like` 处理的是成员的值类别，和形参选择无关，本章不展开。

今天的默认写法可以收成几句。只读参数优先 `const T&`，除非 `T` 是内置类型、迭代器或函数对象这类按约定就该按值传的小类型；确实要把参数收进成员或容器时，才考虑按值加 `std::move`，并且先确认四条条件；性能敏感的接口可以保留 `const&` 和 `&&` 两个重载，把选择留给调用点。移动构造和移动赋值应尽量标 `noexcept`，否则标准容器在扩容时可能退回拷贝；`std::move` 只用在对象的最后一次使用上，提前转走会让后面的读取拿到未指定值。容器扩容时到底选移动还是拷贝，由 `std::move_if_noexcept` 一类的规则决定，细节放在[第 12 章](ch12.md)。编译器方面，clang 和 GCC 都有 `-Wpessimizing-move`，clang-tidy 的 `performance-move-const-arg` 能指出对 `const` 对象做 `std::move` 没有效果，`performance-unnecessary-value-param` 能指出按值形参只被拷贝一次、可以改成移动或引用（本机 clang-tidy 21 实测）。

隐式转换那两行是另一种临时对象。`same(directory.people[0].name, "Ada")` 的第二个实参是 `const char[4]`，形参是 `const Label&`，编译器必须先用 `Label(const char*)` 构造一个临时 `Label` 才能绑定；直接比较 `name.text` 就不需要这个临时对象。把单参数构造函数写成 `explicit` 不能让这次调用“零构造”，但能让它编译不过，逼调用方把 `Label("Ada")` 写在明面上；更彻底的办法是让只读接口直接接受 `std::string_view`，连 `Label` 都不构造。

这些建议里有两项被新标准改写了一半。范围 for（C++11）会在循环开始时缓存 `end()`，手写 `for` 里的重复求值仍然存在，但大多数遍历已经不必自己缓存。`std::string_view`（C++17）和 `std::span`（C++20）让只读字符串、只读连续区间可以直接接受底层缓冲区，不再为 `const std::string&` 或 `const std::vector<T>&` 构造临时对象；它们不拥有数据，不能比源对象活得更久，这一点在[第 28 章](ch28.md)和[第 26 章](ch26.md)展开。移动语义则让“按值接 sink 参数”在某些场景下合理，但那只适用于函数本来就要留下一份拷贝的情况；只读参数没有这份需求，按值只会白付一次构造和析构。

今天的默认写法没有变：只读的用户定义类型用 `const T&`，只读的字符序列用 `std::string_view`，只读的连续区间用 `std::span`，内置类型、迭代器和函数对象按值。只有函数确实要保存一份独立副本时，才回到 7.1 节的四条条件去考虑按值加 `std::move`。工具方面，clang-tidy 的 `performance-unnecessary-value-param` 会指出按值形参只被拷贝一次、可以改成移动或引用，`performance-move-const-arg` 会指出对 `const` 对象做 `std::move` 没有效果；这两个检查在本机 clang-tidy 21 上都实际触发过。编译器警告能抓到的更多是类型和生命周期问题，值传参这种“语义上允许、只是多花一次构造”的写法，还是要靠评审和静态分析；拷贝到底值多少钱，MXC-14 的建议是先测量再下结论（[第 29 章](ch29.md)）。

按值返回的对象本身就是临时对象。MEC-20 的建议是：必须返回对象时，返回“构造实参的表达式”，而不是先建一个具名局部变量再返回。写成 `return Rational(a, b);` 时，返回表达式是纯右值，编译器历来更容易把函数内部的临时量和返回临时量都消除掉，直接在调用方的目标位置构造；写成 `Rational r(a, b); return r;` 时，`r` 是有名字的对象，消除它属于另一类优化（NRVO），标准不保证。C++17 把前一类变成了硬保证：纯右值的复制消除不需要拷贝/移动构造函数可用，也不再依赖编译器的心情。工厂函数返回纯右值（例如 C++14 的 `std::make_unique`）时，调用方按值接住也不需要额外的移动。

纯右值返回仍然是 0 次拷贝、0 次移动，因为 `-fno-elide-constructors` 关不掉 C++17 的强制消除；具名局部变量返回是 0 次拷贝、1 次移动，`return std::move(local)` 也是 0 次拷贝、1 次移动。也就是说，在 NRVO 没有发生时，编译器本来就会把局部变量当右值返回，显式 `std::move` 一次移动也省不掉；而在 NRVO 本来可以发生时，显式 `std::move` 反而会让它无法发生。本机 Clang 21 和 GCC 15 在默认选项下对 `make_named` 都做了 NRVO，计数是 0 次移动，但这不是标准保证，换编译器、换优化级别都可能变。

如果函数必须产生一个新对象，EC-21 的结论是直接按值返回，不要为了省一次构造去返回引用或指针。返回局部对象的引用或指针，函数一返回就悬垂；返回堆对象的引用，调用方拿不到指针，`x * y * z` 这样的表达式会一次泄漏多个对象；返回函数内 `static` 对象的引用，所有调用共享同一结果，`(a * b) == (c * d)` 可能永远为真，多线程下还会互相踩。下面只演示第一种，因为它最容易被“我不想拷贝”这个念头带出来。

## 7.4 临时对象不是 const，拷贝次数也不是语义

《Thinking in C++》在讲 const 时反复说“临时对象自动是 const”，这个说法在 C++11 之后已经不准确；即使按当时的规则，它也只是对“右值不能绑定非 const 左值引用”的简写，并不是说临时对象本身带 const 限定。TIC-34 把它纠正为：产生临时对象的表达式是右值，右值不能绑定到非 const 左值引用；但临时对象本身没有 const 限定，可以调用非 const 成员函数，C++11 起还能绑定到 `T&&`。把“不能绑定 `T&`”说成“临时对象是 const”，会让人误以为 `make().modify()` 非法，也会让人不理解为什么 `T&&` 能接住临时对象。

`Gauge::make(10).bump()` 直接在一个纯右值上调用非 const 成员函数，合法；`std::move(gauge).bump()` 把左值转成将亡值，也调用 `&&` 版本。`Gauge&& bound = Gauge::make(20);` 把这个临时对象的寿命延长到 `bound` 的作用域，但 `bound` 这个表达式本身是左值，所以 `bound.bump()` 调用的是 `&` 版本，输出“左值 bump -> 21”。这正是 C++11 引用限定符（ref-qualifier）的用途：成员函数可以用 `&` 或 `&&` 限定自己只作用于左值或右值，让“修改临时对象”从运行期才发现的逻辑错误变成重载决议上的选择。修改临时对象的结果通常在完整表达式结束时就丢了，所以这仍然是一个设计上的坏主意，只是语言并不禁止。

修复的方向不是想办法“逼编译器调用拷贝构造”，而是把副作用放到语义正确的位置。`FixedAccount` 把注册放进普通构造函数，拷贝和移动保持默认；需要“再建一个账户”时调用具名的 `clone()`，由它调用普通构造函数。这样无论编译器省不省略拷贝，`registered` 都只在实际创建对象时增加。计数也是同样的道理：如果确实要统计逻辑对象，就把计数放在普通构造和析构里，或者用显式的 `create()`/`clone()` 表达“这是一个新对象”；不要把它塞进拷贝构造，更不要用拷贝构造去获取锁、开文件、注册回调。

需要观察拷贝/移动行为时，可以用 `-fno-elide-constructors` 做实验，就像 7.3 节的 `Payload` 那样；这个选项只适合实验，不适合生产构建。NRVO 仍然是可选优化，同一段代码在不同编译器、不同优化级别下的拷贝次数可能不同；C++17 只是把纯右值那一类变成了保证。TIC-33 的结论在今天比写作时更重要：移动语义让“被省略的拷贝”变成“可能发生的移动”，拷贝/移动构造的副作用更不可依赖。把资源管理交给 RAII、把复制语义交给 `= default` 或显式的 `clone()`，比数构造函数的调用次数可靠得多。

## 回头看

这四节其实在拆同一个错觉：`std::move` 不是“移动”，按值不是“现代”，返回时的临时对象也不是“一定会构造”。移动要成立，得同时满足有移动操作、移动比拷贝便宜、当前语境允许它抛异常、源对象是右值；sink 形参要按值，得同时满足可拷贝、移动便宜、总是被复制、不切片；返回值要省，得让纯右值直接初始化目标，而不是先建具名对象再 `std::move`；临时对象不是 const，拷贝构造也不该承担注册、计数或资源管理。四件事的落点都是同一条：先确定语义和所有权，再决定用哪种写法。

C++17 把纯右值的复制消除变成硬保证，C++11 的移动语义给 NRVO 失效时留了退路，C++17 的 `string_view` 和 C++20 的 `span` 让只读参数不必再为构造临时对象买单。但语言没有替我们选对形参，也没有保证 NRVO，更没有阻止把副作用写进拷贝构造。剩下的仍要靠写法：只读参数用 `const&` 或视图，sink 参数按四条条件选，返回局部对象时直接写名字，观察拷贝次数只在实验里用 `-fno-elide-constructors`。工具能帮一部分：`-Wpessimizing-move`、`-Wreturn-stack-address`/`-Wreturn-local-addr`、clang-tidy 的 `performance-*` 检查，以及运行期的 ASan；它们各自覆盖一个阶段，不能互相替代。
