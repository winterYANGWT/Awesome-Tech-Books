# 第 14 章 封装：数据私有、句柄与不变式

先看一个不起眼的钱包类型：

```cpp
class Wallet {
public:
    long cents;                  // 任何代码都能改
};

void spend(Wallet& w, long amount) {
    if (w.cents >= amount) w.cents -= amount;
}
```

`spend` 检查了余额，看上去没有问题。但检查只对“调用 `spend` 之前的状态”负责：另一个函数可以写 `w.cents = -50`，也可以把 `cents` 当成“元”而不是“分”来赋值，还可以在 `spend` 检查完、扣款前通过另一个引用改掉它。类没有任何机会说“这个值不合法”，因为它根本不知道谁会来写。把 `cents` 改成 private、再加一个 `spend` 成员，代码只多了一行访问说明符，却把“余额不能为负、单位是分”这条规则从“所有调用方的共同约定”变成了“类自己维护的事实”。

这一章讨论的就是这条边界：类的哪些部分算是内部，调用方通过什么方式碰到它，以及内部状态要满足什么条件才算合法。私有数据是边界的第一道墙；返回内部引用、指针或迭代器是在墙上开洞；`private` 只挡名字的使用，不挡名字的可见性，也不挡成员模板的显式特化；一个类揽下太多职责时，墙会多到没人记得住；不变式没写清楚，墙内也会出问题；最后，没有合理零值的类型硬造默认构造，等于允许墙里先放一个半成品。

## 14.1 数据成员为什么一律私有

先看公开数据成员的实际代价。`SpeedStats` 如果写成 `struct`，`count`、`sum`、`max` 三个字段谁都能改，下面这些状态都能出现：`count == 0` 但 `sum != 0`；`max` 小于某条已经加入的记录；`count` 为负。每个使用 `SpeedStats` 的函数都只能假设最坏情况，或者自己再检查一遍。这正是 Sutter 与 Alexandrescu 在 CCS-41 里说的“把一个或多个不变式的维护责任分摊给无界的调用方代码”：类的状态可以以任意、不可预测的方式变化，类自己却没有任何拦截点。

`running` 和 `replay` 的公开接口完全一样，内部却一个是三个计数器、一个是 `std::vector`。`report` 是模板，只要求 `count()`、`max()`、`average()` 这三个名字存在，所以两个实现都能直接传进去；把 `SpeedStats` 的内部换成“保留全部样本、平均现算”，调用方一行都不用改。这就是 Meyers 在 EC-22 里所说的实现自由，也是封装最值钱的地方：不是“不让别人看”，而是“以后换实现时不用求别人改代码”。

EC-22 还给了两个较小的理由。第一是语法一致：公开接口里如果全是函数，调用方不用记哪个成员带括号、哪个不带。第二是访问粒度：数据成员一旦 public，就是可读可写；用函数可以做出只读、只写、读写、完全不可访问四种接口。真实类里很少有每个成员都需要 getter 和 setter，通常大部分成员只需要其中一两种访问方式，剩下的根本不该出现在公开接口上。

EXS-17 把这件事讲得更绝对：任何 public 或 protected 数据成员，都可以在几乎不损失功能、也几乎不损失效率的前提下，改写成“private 数据 + 返回引用的 inline 访问函数”（位域除外，引用不能绑定到位域）。访问函数返回引用，所以没有拷贝；inline 之后通常被完全优化掉，和直接访问成员生成的代码一样。但改写之后，类获得了在函数里加日志、断点、校验、统计、替换存储方式的能力，而调用方只多写一对括号。既然这个变换几乎总是可行，代价又通常可以忽略，那就没有理由从错误的一边开始。Sutter 由此推出他的“第二次机会定律”：接口一旦被广泛使用，改起来可能永远得不到批准；内部实现以后总能改，所以第一次就要把接口设计对。

protected 数据经常被当成“比 public 封装得好一点”，EC-22 和 CCS-41 都明确否定这个看法。封装程度和“改掉它时可能破坏多少代码”成反比：public 数据可能被任意多的调用方使用，protected 数据可能被任意多的当前和未来派生类使用，两者都是无界集合，实际上一旦发布就很难再动。更直接的问题是，任何代码都能派生一个类，让新类的成员函数读写自己继承来的 protected 部分，所以 protected 并不是“只给作者选定的派生类”，而是“给所有愿意写一行继承的人”。下面的例子让派生类绕过 `push` 直接改 `used_`，基类的不变式当场失效，随后一次写入越过了数组边界：

唯一的例外是纯数据聚合。CCS-41 和 EXS-17 都把它写成“所有成员 public、不打算封装任何东西的 C 风格 struct”：数据成员本身就是接口，没有不变式要维护。上面的 `Reading` 就是这种类型，`static_assert(std::is_aggregate_v<Reading>)` 把“它必须是聚合体”写进了编译期；`SpeedStats` 因为有 private 成员，`static_assert(!std::is_aggregate_v<SpeedStats>)` 同样成立。只要有一个 private 或 protected 非静态数据成员，类型就不再是聚合体；C++20 又收紧了聚合体的条件：只要有用户声明的构造函数，哪怕只是 `= default` 或 `= delete`，类型就不再是聚合体（C++17 只看用户提供的构造函数）；同时引入指定初始化器，要求按声明顺序书写（乱序时 GCC 15 报错，clang 21 默认只给 `-Wreorder-init-list` 警告）。这些规则把“纯聚合”和“封装类”的界线划得更清楚：要么全部公开、只当数据包；要么全部私有、由类维护状态。CCS-41 特别提醒不要公私混用：一个类里既有 public 数据又有 private 数据，几乎总说明作者没想清楚它到底是抽象还是 struct。`std::pair` 的公开成员是合法例外，因为它只把两个元素捆在一起，不添加行为或不变式；但 `std::pair` 是标准库为“聚合两个值”专门设计的类型，不能拿它给有不变式的普通类开脱。

C++11 以后写私有数据加访问函数比原来省事。默认成员初始化器让成员在声明处就有初值，不必在每个构造函数里重复；`= default` 让“编译器生成的版本就够用”变成显式声明；`constexpr` 成员函数让简单的 getter 能在编译期求值。C++17 的 `[[nodiscard]]` 可以标在 getter 上，调用方忽略返回值时通常会得到 `-Wunused-result` 警告，这正好补上“getter 没有副作用、返回值必须被使用”这一类约束。C++20 的 `[[no_unique_address]]` 允许把空的策略对象或分配器作为成员而不占额外空间，它解决的是布局问题，不是访问控制问题——成员仍然可以是 private，不需要为了省空间把它公开。C++20 的 modules 也不会让 private 成员变得可改：类定义仍然写在接口单元里，布局和访问控制照旧。

工具方面，clang 21 的 `-Wunused-private-field` 会报告从未被使用的私有数据成员，GCC 15 不认识这个选项（本机实测 `unrecognized command-line option`），跨编译器项目不能把它写进公共编译选项。clang-tidy 21 有 `misc-non-private-member-variables-in-classes` 和 `cppcoreguidelines-non-private-member-variables-in-classes` 两个检查，专门找公开或受保护的数据成员；本机 `clang-tidy --list-checks` 能看到它们。这些检查只能提示“这里有公开数据”，判断它是不是合法的聚合体仍然要人来做。反过来，如果一个类几乎全是 getter 和 setter，CCS-41 的建议是先决定它到底想当抽象还是想当 struct：一个提供抽象的类应该暴露领域操作（`deposit`、`withdraw`、`average`），而不是把每个字段都开一对读写函数，让调用方继续按字段的粒度思考。如果连成员本身都不想出现在头文件里，可以把私有实现藏到不透明指针后面；Pimpl（CCS-43）在第 6 章 6.7 节讲，写法和代价都在那里。

## 14.2 返回内部句柄为什么让 const 形同虚设

14.1 节说访问函数可以返回引用，这样写和直接公开数据“功能等价、效率通常相同”。等价的前提是返回的引用不会变成后门。Meyers 在 EC-28 里给的场景很典型：一个矩形把两个角点放在辅助结构里，`upperLeft()` 和 `lowerRight()` 是 const 成员函数，返回的却是 `Point&`。调用方拿到引用后可以调用 `setX`，而被修改的对象在语法上还是 `const Rectangle`。原因不在于编译器没检查 const，而在于 const 是“按位”的：const 成员函数让对象自己的成员变成 const，`std::shared_ptr<RectData>` 或 `std::unique_ptr<Impl>` 这个指针确实不能改，但它指向的那块内存不在对象的字节里，指针的 const 传不过去。

把返回类型改成 `const Point&` 能挡住写入，`cline.at(0).setX(99)` 会变成编译错误。但这只解决了一半问题，另一半是悬空。EC-28 用 `boundingBox(*pgo).upperLeft()` 举例：`boundingBox` 按值返回一个临时 `Rectangle`，`upperLeft()` 返回临时对象内部的引用，语句结束时临时对象销毁，引用（或由它取地址得到的指针）立刻失效。把返回类型加上 const 并不能延长任何东西的寿命。C++17 的保证复制消除让按值返回本身更便宜、更确定，但它不会让临时对象活过完整表达式；相反，正是“按值返回”制造了这个临时对象。

Sutter 与 Alexandrescu 在 CCS-42 里从“对象拥有什么”的角度讲同一件事。一个 `Socket` 类如果提供 `int GetHandle() const`，调用方拿到操作系统句柄后可以直接 `close` 它，而 `Socket` 对象仍然以为自己拥有这个句柄；之后析构函数再关一次，或者成员函数继续使用一个已经无效的句柄，类完全不知道。类也无法再可靠地加代理、日志、统计或错误处理，因为调用方有两条路：走 `Socket` 的抽象，或者绕过它直接操作底层句柄。`const` 在这里同样是浅的：`char* GetBuffer() const` 返回的是可写指针，`strcpy(s.GetBuffer(), ...)` 能编译，也确实会写进对象的缓冲区（当然，调用方仍要自己保证容量足够）；至少返回 `const char*`，误用者才必须写一个显式转换。CCS-42 还提醒，调用方可能把句柄存下来，等类已经使它失效之后再用——这和 `string_view` 的悬空是同一类事故，只是句柄的类型不同。

新标准没有让句柄更安全，只是让“交出视图”变得更方便。C++17 给 `std::string::data()` 增加了返回可写 `char*` 的重载（此前只有 const 版本），C++20 引入 `std::span`，C++23 引入 `std::mdspan`；它们都把“指向内部存储”做得更类型化、长度更清楚，但没有一个延长生命周期。`std::unique_ptr::get()` 和 `std::shared_ptr::get()` 也是一样：拿到裸指针的代码不受所有权约束，删除、悬空、重复释放都可能发生。判断一个返回句柄的接口是否合理，要问三个问题：调用方需要写吗？句柄能活过对象吗？实现以后还能换吗？三个答案里只要有一个不合适，就应该换一种接口。

今天的做法可以按优先级排。第一选择是返回值：C++17 起按值返回有保证复制消除，普通结构体很便宜，调用方拿到的是独立对象，没有有效期问题。第二选择是返回只读的 const 引用或 `std::span<const T>`，并在注释或文档里写清楚“下一次修改容器的操作会使它失效”，标准库的迭代器失效规则就是这种契约的样板。第三选择是提供领域操作而不是暴露内部，例如 `Polyline::translate(dx, dy)` 而不是 `Point& at(i)`；调用方要做的事往往可以用一个操作表达，不必碰到表示。通常只有在为了兼容 C 接口或遗留代码时，才值得保留 `c_str()`/`data()` 这类后门，并且明确它只在“下一个修改操作之前”有效。工具能帮的忙有限：clang 的 `-Wreturn-stack-address` 抓的是返回局部变量地址，ASan 抓的是实际发生的悬空访问；没有哪个警告能证明一个 `string_view` 成员返回值的有效期，那是接口契约的一部分。

## 14.3 访问控制挡误用，不挡可见性与重载

private 经常被误解成“外面看不见”。准确的说法是：private 控制的是“谁能使用这个名字”，不是“谁能在类定义里看到它”。EXS-16 把一次调用的处理拆成三步：先做名字查找，找到一组同名候选；再做重载决议，选出唯一最佳匹配；最后才检查选中的那个函数是否可访问。顺序很重要，因为重载决议可能在访问检查之前就失败，而失败的原因和“私有”没有关系。

先看访问检查排最后造成的后果。`Calc` 有一个 public 的 `twice(double)` 和两个 private 的 `twice(int)`、`twice(complex<float>)`。调用 `c.twice(21)` 时，名字查找在 `Calc` 作用域里找到三个 `twice`，停止向外层查找；重载决议发现 `21` 是 `int`，精确匹配 `twice(int)`；最后访问检查发现它是 private，报错。唯一可访问的 `twice(double)` 从头到尾没有参与竞争，因为“更好的匹配”比“可访问的匹配”优先：

可见性还有两个具体的副作用。第一，私有成员的参数类型必须在类定义处至少已经声明；如果私有函数在类内联定义，参数类型还必须完整。也就是说，一个外部代码根本调用不到的私有函数，仍然会把它的参数类型所依赖的头文件带进每一个看到类定义的地方。第二，有访问权的成员或友元可以把指向私有成员的指针交给外部。`Meter::expose()` 返回 `&Meter::scale`，外部代码拿到这个成员指针后直接调用，不需要任何访问权限：

EXS-15 把另外三种常见做法归为“伪造、扒手和调包”，三种都不合法。复制一份类定义、在里面加 `friend` 声明，违反单一定义规则（ODR）：同一个类型在程序里出现了两个不同的定义，行为未定义，编译器通常不报错。用 `#define private public` 再 `#include` 头文件，一方面包含了标准库头文件的翻译单元不允许把关键字定义成宏，另一方面它同样制造了两个不同的类定义，还是 ODR 违规；它在某个编译器上“能用”只是布局碰巧没变。把对象 `reinterpret_cast` 成一个布局相同的“诱饵类”再写成员，既没有布局保证，也违反严格别名规则，是未定义行为。这三种手段都只能在“防君子不防小人”的意义上讨论：访问控制的目标是防无心之误（Murphy），不是防铁了心作弊的人（Machiavelli）；真要防恶意代码，进程边界和权限系统才是工具，C++ 的访问说明符从来不是安全边界。

## 14.4 一个小类只承担一个职责

14.1 到 14.3 讨论的是“一个类的边界在哪里”。边界画错还有另一种表现：类本身太大。一个 `Report` 类如果同时负责读取数据、计算统计量、生成 CSV、生成 HTML、发送告警，那么每加一种输出格式、每改一次告警阈值，都要回到这个类里改；每个成员函数都顺手拿到了访问内部 `std::vector` 的通行证；任何一个功能出错，测试都要把整个类拖进来。CCS-05 把这条写成“一个实体只承担一个内聚的职责”，实体可以是变量、类、函数、命名空间、模块或库；CCS-33 把它落到类上，主张小而专的类优于大杂烩类；CCS-11 从信息隐藏的角度补充：类越大，内部信息暴露给越多成员函数，封装被稀释得越厉害。

CCS-05 的论证是“成本大于各部分之和”。多职责实体通常意味着多组状态，行为和状态的组合数会爆炸；用其中一个功能，就得背上其余全部功能的理解成本。它举的两个反面教材很典型：C 的 `realloc` 把分配、释放、原地扩展和搬移混在一个接口里，既难扩展又容易用错；`std::basic_string` 想当容器又不完全是容器，迭代和下标两套风格并存，还重复了算法能做的事。这两个接口都不是“写得不够好”，而是职责从一开始就分叉了，后面只能不断打补丁。

CCS-33 补了两个类特有的代价。第一是部署粒度：一个 `Matrix` 类顺手实现了特征值计算，只想做矩阵加法的用户也得链接、测试、发布这一整块代码；把特征值计算做成非成员函数，功能区域就能单独测试和交付。第二是封装稀释：大类里有很多“本不必是成员却写成成员”的函数，它们都拿到了访问私有数据的权限，私有数据就退化成“只有语法上私有的公开变量”。CCS-33 还提醒，“一次给出完整方案”几乎从不成功：用户总想要更多，也总有人只想要更少，最后接口被各种旗标和重载撑大，每个用途都只被照顾到一点。

如果把这些函数都写成 `Series` 的成员，代码也能工作，但每个成员都自动拥有访问 `readings_` 的权限，`Series` 的不变式（比如“元素个数等于 `size()`”）就从“只有 `add` 需要维护”变成“所有成员都可能破坏”。CCS-11 把这一点讲成信息隐藏的两个收益：改动的影响被局部化，维护不变式的代码被限制在少数几个函数里。反过来，自由函数没有 `this`，拿不到私有成员，想破坏也没有路径；它们只能通过公开抽象工作，这既是限制，也是保证。

“小”不等于“碎”。`Series` 仍然是一个完整的抽象：它拥有数据，维护“元素连续存放、`size()` 与 `vector` 一致”的表示，扩容交给 `vector`。把 `vector` 直接公开、让调用方自己 `push_back`，并不会让类更小，只会让它失去唯一的不变式。CCS-11 的例外也值得记住：测试代码经常需要白盒访问，可以用 `friend` 或测试专用接口；纯数据聚合（C 风格 struct）本身不提供抽象，数据就是接口，不需要隐藏。除这两种情况外，公开数据或公开内部容器都只是把职责推回给调用方。

C++11 以后，写小类型和自由函数比原来轻松。lambda 和 `auto` 让一次性的小函数不必单独起名字；`std::string_view`（C++17）和 `std::span`（C++20）让自由函数直接处理外部数据，不需要拷贝，也不需要为了“能传进来”而继承某个基类；ranges（C++20）把“小类型 + 一组视图/算法”的组合方式变成了标准库的默认风格。C++20 的 concepts 还能把自由函数对类型的要求写成约束，让“这个函数需要什么”出现在签名上，而不是藏在文档里。modules 能缩短编译时间，但不会消除大类在理解和部署上的耦合：一个类如果揽了五件事，把它放进模块也还是五件事。

落到今天的写法：先问这个实体的一句话职责是什么，写不出来就说明还没想清楚；能做成自由函数的操作不要做成成员，尤其是那些只读、只计算、不需要访问表示的操作；需要维护状态或不变式的部分才做成小类，并让它只暴露抽象操作。`Series` 这样的容器型小类适合持有数据，`LaneFilter` 这样的策略型小类适合持有判断条件，两者用组合拼起来，比一个 `Report` 大类更容易测试、复用和替换。把操作放到类外还有一条独立的理由：非成员非友元函数不会扩大接口，CCS-44 和第 15 章专门讲这个取舍。

## 14.5 把类不变式写清楚，把 friend 缩到最小

“对象始终有效”是一句没有内容的话。有效是什么意思？哪些字段之间必须保持什么关系？什么时候由谁负责恢复？《Accelerated C++》在 ACC-21 里用 `Vec` 的写法给了一个可以照搬的模板：不变式要写成具体的指针顺序和区间状态，构造函数负责建立它，每个公开成员在返回前恢复它，公开接口不直接暴露那三个指针。

在这个类里，构造函数是唯一需要“从零建立不变式”的地方。`IntVec(n, value)` 先分配 `n` 个元素的空间，把 `avail_` 和 `limit_` 都设到末尾，再逐个构造。如果构造过程中抛异常，对象本身还没有建成，它的析构函数不会被调用（已经构造完成的成员仍会析构），已经分配的内存和已经构造的元素必须由构造函数自己清理。这个例子只存 `int`，`std::construct_at` 不会抛，所以省掉了 `try`/`catch`；换成可能抛的类型，就要在异常路径上销毁已构造的部分并归还内存。ACC-21 把这一点讲得很清楚：构造函数要么完整建立对象，要么让对象不存在，不能留下一个“看起来构造完了、其实只初始化了一半”的对象。

`assert` 只在调试构建里有效。定义 `NDEBUG` 之后，`assert(invariant())` 整句消失，发布版本里不再有任何检查；所以不能把“运行期错误处理”寄托在断言上。断言的作用是让违反不变式的内部 bug 在开发阶段尽早暴露，而不是替调用方处理错误输入。需要运行期拒绝的输入（比如 14.1 节的负速度）要用异常或返回错误码；需要在编译期保证的性质（比如“这个类型不能拷贝”）用 `static_assert`。C++20 的 contracts 没有进入标准；C++26 采纳了 contracts（P2900，`pre(...)`/`post(...)`/`contract_assert(...)`），但本书环境的 clang 21 和 GCC 15 都还不支持。即便 contracts 可用，它也只能表达“进入函数时/离开函数时检查什么”，类不变式仍然要靠封装、断言和测试来维护。

什么时候值得用 `friend`？ESS-06 的判断是：只读写一个成员时，公开的 inline 访问函数通常已经够用，还能保持封装和不变式；运算符需要访问两个不同类型的内部表示（比如 `Point` 乘 `Matrix`）或性能敏感（比如矩阵乘向量要直接遍历内部数组）时，才值得开一个友元。C++20 的 `<=>` 常写成隐藏友元（hidden friend），定义在类内、靠 ADL 找到，这样两边操作数都能隐式转换；这是“最小授权”的一个现代例子：只授给这一个运算符，而不是整个类。语言设施一直在变，但“授给谁、授多大”的取舍没有变。

工具对不变式和友元的帮助有限。`assert` 是宏，`-DNDEBUG` 一开就没了；clang-tidy 有 `bugprone-assert-side-effect` 之类的检查，防止在 `assert` 里写有副作用的表达式，但没有检查能证明“这个类的不变式写全了”。友元也没有对应的警告：编译器不会告诉你“这个 friend class 授得太宽”，因为从语言角度看它完全合法。这两件事只能靠设计评审和测试：把不变式写成注释加 `invariant()`，让每个修改状态的公开成员都调用它；把 `friend` 限制到单个函数，并在代码评审时问一句“这个函数真的需要访问私有成员吗”。

## 14.6 没有合理零值就别硬造默认构造

Meyers 在 MEC-04 里把默认构造函数称为“C++ 里‘不劳而获’的方式”：它在没有任何外部信息的情况下初始化对象。对数值、指针、容器这类类型，零值通常有明确含义（0、空指针、空容器），默认构造是合理的；对“通讯录条目”“设备编号”这类类型，没有编号就根本不是一条有效记录，硬给它一个默认构造，等于允许一个不合法的状态存在。

不允许默认构造的代价是具体的。MEC-04 列了三处：不能直接定义对象数组（`EquipmentPiece a[10]` 需要逐个默认构造）；可能不被某些要求默认构造的容器或模板接受；作为虚基类时，最派生类必须层层传递构造实参。它还给了三种数组的绕法：定义时用初始化列表逐个给实参、用指针数组、或者用 placement new 在原始内存上逐个构造。最后一种最麻烦：要手工逐个析构，再用 `operator delete[]` 释放原始内存；对不是 `new[]` 来的指针用 `delete[]` 是未定义行为。这些代价是真实的，不能假装看不见。

但另一种“解决方式”代价更大：给参数加一个默认值，造一个哨兵值表示“未指定”。MEC-04 的例子是给构造参数加一个默认值，用一个特殊的哨兵编号表示“未指定”；对象能默认构造了，但每个成员函数都不再能假设 ID 存在，必须在使用前检查；检查带来运行期分支、代码体积和新的出错路径。检查失败时怎么办？抛异常、终止程序，或者继续用一个无意义的值算下去——三种都不比“一开始就不让这个对象存在”更好。MEC-04 的结论是：这些成本通常大于“缺少默认构造”带来的容器兼容性成本。

`static_assert(!std::is_default_constructible_v<AccountId>)` 把“这个类型没有零值”写进了编译期；`static_assert(std::is_default_constructible_v<LegacyAccountId>)` 则说明哨兵版本确实能被默认构造，代价是 `checks=1`、`checks=2` 这两次检查——每多一个使用点，就多一次“它到底有没有值”的判断。真实代码里这种检查会散落在几十个函数里，而且总有人忘记。

新标准大幅降低了“没有默认构造”的疼痛，所以 MEC-04 的状态是“部分过时”而不是“仍成立”。C++11 的 `emplace_back`/`emplace` 让容器在原位构造元素，不再要求先默认构造再赋值；默认成员初始化器和委托构造让“每个构造函数都要重复初始化”少了很多；C++17 的 `std::optional` 提供了标准的“可能还没有值”的表示，`std::variant` 也能表达“几种状态之一”；C++17 的保证复制消除让按值返回更便宜；C++20 的指定初始化器让聚合体的初始化顺序和字段名更清楚。仍然存在的限制是：`std::vector<AccountId> v(3)` 这种“先造 n 个默认元素”的写法依然要求默认构造；`std::array<AccountId, 2> a;` 也一样，必须在定义处逐个给初值。碰到这些场合，应该换用 `reserve` + `emplace_back`、`std::optional` 或指针/索引，而不是给类型加一个假的零值。

Meyers 在 MEC-32 里把同一思路扩展到整个类的设计，标题是“用将来时写程序”。它的意思是：假设这个类以后会被继承、被复制、被误用、被移植，把设计约束用语言机制写出来，而不是只写在注释里。不打算被继承就用 `final`；不允许复制就 `= delete`；构造参数不能隐式转换就 `explicit`；覆盖虚函数就写 `override`；编译期能检查的条件就写 `static_assert`。MEC-32 还特别反对“按需虚化”：不要等有人提出需求才把函数改成 virtual，而要看它在抽象里是否应该可重定义；因为一旦发布，再加 virtual 在常见实现上会改变 vtable 布局，所有客户端都要重新编译，甚至破坏 ABI。

MEC-32 还提醒不要走极端。将来时不是“现在就把所有可能的功能都加上”，而是在满足当前编译器、平台和性能约束的前提下，为可预见的演化留出空间。`Session` 如果现在确实不需要移动，删掉拷贝就够了；如果业务上以后可能要把会话放进容器，就应该现在决定“移动后源对象是什么状态”，并显式实现移动。判断标准不是“以后也许会用到”，而是“这个类型在抽象上应不应该具备这个操作”。这和 14.4 节的职责划分是同一件事：先想清楚类型是什么，再决定它支持什么。`Session` 的拷贝控制只是一个例子；切片和按值传基类的规则（CCS-54）属于第 6 章的范围，这里不再重复。

## 回头看

把六节放在一起看，它们防的是同一类事故：对象的内部状态在类不知情的情况下被改掉。私有数据把写入口收窄到成员函数；句柄规则防止成员函数把刚收窄的入口重新打开；访问控制规则说明这道墙只挡误用、不挡有意绕过；职责划分决定墙内要维护多少条互不相干的状态；不变式把“有效”变成可检查的条件；默认构造则决定墙里能不能先放一个半成品。`friend` 和 const 视图是墙上开的门：门可以开，但要只开给需要的人，并写明有效期。

语言和标准库在 C++11 之后补上了不少工具：`= default`/`= delete`、`final`/`override`/`explicit`、`[[nodiscard]]`、`std::optional`、`std::span`/`std::string_view`、concepts、modules。它们让约束更容易写、句柄更容易表达，但没有替类维护不变式，也没有替调用方检查生命周期。编译器能抓的是语法和类型层面的误用；访问控制的绕过、悬空视图、`friend` 授得太宽，仍然要靠设计评审、断言、ASan/UBSan 和测试。封装不是一组可以勾选的规则，而是一条持续的选择：每次决定公开什么、返回什么、授权给谁时，都要问这一步会不会让类失去对自己状态的控制。
