# 第 35 章 跨边界：ABI、C 互操作与不安全接口

支付模块内部用异常报告“卡被拒了”，导出给 C 宿主的函数却只返回一个 `int`。有人在导出函数里漏了 `catch`，在本机测试时异常居然一路传到了宿主的 C++ 测试代码里，看起来没事；换一个编译器、换一组运行库重新构建宿主后，进程在回调处直接消失。C++ 标准没有规定异常怎样在二进制层面传播，也没有规定 `std::string` 在两个编译器眼里必须长得一样。边界两边只要对这些事情的理解不一致，同一块内存就会被两种规则解释。

这里的“模块”指独立构建、独立发布的库或子系统，不是 C++20 的 module。C++20 module 改变的是名字可见性和编译模型，不提供跨编译器 ABI；一个模块接口里导出的 `std::string` 仍然要求导入方用兼容的标准库。本章按四条边界展开：异常怎样在接口处停下，接口上能出现哪些类型，省略号和失效对象为什么危险，以及数组、退出函数和 ABI 这些从 C 时代留下来的坑。

Sutter 与 Alexandrescu 在 CCS-62 里的说法很直接：C++ 标准没有规定异常传播的实现方式，连一个大多数系统都遵守的事实标准都没有；异常机制不仅随操作系统和编译器变化，还随编译选项变化。因此，只有当你控制边界两边所用的编译器和编译选项时，才可以让异常穿过这条边界。跨模块、跨子系统时，应该在边界上用 `catch (...)` 兜住，再转换成该边界约定的错误码。这里的“模块”是独立构建的单位，不是语言里的 module。

需要设兜底的位置不止导出函数。`main` 外层要有一个，否则未捕获异常会让程序以一个没有上下文的 `terminate` 结束；操作系统或第三方库调用的回调要有一个，因为调用你的代码可能根本不是 C++；线程入口要有一个，异常不能从线程主函数里逃回创建线程的那一侧；析构函数内部也要有，析构函数默认是 `noexcept` 的，让异常逃出去同样会终止程序。把这些位置列出来会发现，它们都是“控制权即将交给别人的地方”。

`catch (...)` 也不是万能的。CCS-62 提醒，有些平台会把空指针解引用一类底层错误也挂在 C++ 异常机制上，这时 `catch (...)` 接住的东西可能不是普通的 C++ 异常，程序状态是否还能继续用要查平台文档。另一个常见误区是用一长串 `catch (E1&) ... catch (En&)` 代替 `catch (...)`：每接入一个自带异常体系的库，就要回来改这份列表，漏掉一个类型就等于没有兜底。`catch (...)` 的职责不是“理解错误”，而是“保证不越过这条线”，具体的错误分类应该在模块内部完成。

C++11 引入的 `noexcept` 让“这个函数不抛”写进声明，C++17 起它还成为函数类型的一部分；标准容器在选择移动还是拷贝时会看它，但 `noexcept` 不是异常翻译器，它只是把“异常不得离开”写成可检查的承诺。C++11 的 `std::error_code`/`std::system_error` 给了边界一组标准化的错误值，C++23 的 `std::expected`（需要 `-std=c++23`）让“返回值携带错误”可以用类型表达；C++23 的 `std::to_underlying` 则把枚举状态安全地转成底层整数交给 C，需要 `-std=c++23`，本书示例为了保持 C++20 仍用 `static_cast<int>`。它们都适合放在接口上，但不能自动把模块内部的异常接住；翻译仍然要有人写。C++20 modules 也没有改变这件事：模块接口可以隐藏名字，不能把两个编译器之间的异常 ABI 变成标准。

今天的做法是：模块内部继续用异常，因为构造失败、容器越界、标准库实现都可能抛，完全不用异常反而要写更多检查；对外接口只暴露错误码、状态枚举或 `expected`，把“异常到错误码”的转换集中在少数几个 `translate` 函数里。导出函数标 `noexcept`，并在函数体内用 `catch (...)` 收尾；不要在每一个业务函数里各写一遍 `try/catch`，否则错误处理会散落在整个模块。至于错误码怎么设计、什么时候用 `expected`，是[第 13 章](ch13.md)的主题；`noexcept` 对移动和容器的影响在[第 12 章](ch12.md)已经讲过。这里只强调边界上的那条规矩：异常可以留在模块里，不能未经翻译就交给邻居。

## 35.2 接口只用调用方能正确理解的类型

假设动态库导出一个函数 `std::string translate(const std::string&)`。库和调用方都用 C++，看起来没有问题；但库是用 libstdc++ 的旧 ABI 构建的，调用方用的是新 ABI，`std::string` 在两边的大小和内部指针布局不一样。调用方按自己的布局构造一个字符串，库按自己的布局去读它，读到的长度、指针和容量全是另一套解释。即使两边用的是同一份标准库，`-D_GLIBCXX_USE_CXX11_ABI=0` 这样的构建选项也能让同一个 `std::string` 变成另一种布局。CCS-63 的判断标准不是“这个类型标不标准”，而是“我能不能保证所有调用方都按同样的布局理解它”。

Sutter 与 Alexandrescu 把接口类型的选择写成一个取舍：控制不了调用方的构建环境时，只能退到平台类型和内置类型；能控制时，才可以使用双方都理解的高层类型。他们用文件名参数举了三个层次：`char*` 覆盖面最广，但谁分配、谁释放、缓冲区多大都要另说；`std::string` 要求调用方也用 C++、同一标准库、兼容的编译选项；`istream` 或自定义 `File` 抽象层次最高，但同样要求同一编译器、同一套构建配置。层次越低越可移植，越需要把被抽象掉的约束补回来。

这份取舍在今天的做法是“内部高、边界低”。模块内部照常用 `std::string`、`std::vector` 和类对象，只在导出函数上把结果写进调用方提供的缓冲区，或者返回一个不透明的句柄。下面的 C 接口接收一个 C 结构体，把格式化结果写进 `char*`，并返回所需长度：

头文件要同时被 C 和 C++ 包含，标准写法是用 `__cplusplus` 把 `extern "C"` 包起来，如上面的 `sensor_api.h`。C 编译器看不到 `extern "C"`，只看到普通的函数声明；C++ 编译器看到 `extern "C"`，按 C 链接方式生成符号。这个头文件还借 `__cplusplus` 定义了 `SENSOR_NOEXCEPT`：C 看到空宏，C++ 看到 `noexcept`，同一份声明在两边都合法。这个模式从 MEC-34 的时代一直用到今天，C++20 modules 也没有改变 C 链接规则。

MEC-34 还列了另外三件事。第一是静态对象的初始化：很多实现把全局对象的构造和析构挂在 `main` 前后，如果整个程序的入口是用 C 写的，C++ 的静态对象可能不会被构造或析构。Meyers 的建议是尽量用 C++ 写 `main`；如果主程序是 C，就把 C 的 `main` 改名成 `realMain`，由 C++ 的 `main` 转调。第二是动态内存：`new` 出来的必须 `delete`，`malloc` 出来的必须 `free`，混用是未定义行为。第三是数据结构兼容：只有两边都能编译的结构体、内置类型、普通指针和非成员/静态函数指针才适合跨语言传递。C++ 版本可以带非虚成员函数，C 侧看不到这些函数，通常也不改变数据布局；加虚函数、继承或虚基类则会改变布局。

ASan 报 `alloc-dealloc-mismatch (operator new vs free)`。没有 sanitizer 时，这段代码可能当场崩溃，也可能污染分配器的内部状态，过很久才在无关的地方出问题。EXC-35 把自由存储和堆分成两套设施，`new`/`delete` 与 `malloc`/`free` 不能交叉配对，见[第 10 章](ch10.md)。`strdup` 是 MEC-34 特别点名的例子：它返回的内存在一些实现里该用 `free`，在另一些实现里该用 `delete`，标准没有统一答案；跨边界时要么不用，要么把它封在一个明确负责释放的函数里。

新标准没有让 ABI 问题消失。C++17 的 `std::string_view` 和 C++20 的 `std::span` 只是“指针加长度”的视图，它们不拥有数据，也不保证跨编译器布局一致；把它们放进出口，仍然要求两边对指针、长度和元素类型有相同理解。C++20 的 `std::is_layout_compatible` 可以检查两个 C++ 类型是否布局兼容，但它只能比较 C++ 类型，不能替你问 C 编译器；C++20 modules 提供的是源码层的接口边界，不是二进制 ABI。C++23 的 `std::expected` 可以改善错误返回的类型安全，也同样不改变对象布局。

所以接口设计要先问“谁会调用我”。同一个团队、同一套工具链、同时构建的代码，可以传 `std::string` 和类对象；要发给外部客户、要跨 DLL、要允许 C 或其他语言调用时，就把接口收窄到 C 兼容的结构体、固定宽度整数、指针加长度和不透明句柄。固定宽度类型用 `<cstdint>` 里的 `std::int32_t` 一类，不要假设 `int` 一定是 32 位；结构体最好只放数据成员，并在文档里写清字段顺序、对齐和所有权。需要扩展时加一个 `size` 或 `version` 字段，让两边能判断自己看到的是哪一版布局。

把 `printf` 换成自己写的 `void log(const char* fmt, ...)`，这条警告就没有了。省略号告诉编译器“后面的实参不再检查”，类型和个数全靠调用方与被调方之间的一套口头协议；格式串写错、参数少给一个、把 `double` 按 `%d` 读，语言层面都无法阻止。Sutter 与 Alexandrescu 在 CCS-98 里把这一点说得更重：省略号等于让编译器“关掉所有检查，剩下的我自己来”；传非平凡类类型对象给省略号在 C++98/03 是未定义行为，C++11 起变成条件支持、语义由实现定义，仍然不可移植。两个编译器对它的态度还不一样：本机 Clang 21 直接报 `-Wnon-pod-varargs` 错误，GCC 15 在 `-Wall -Wextra` 下静默接受；不报警告不等于代码可移植。

省略号还有第二个问题：连“有几个参数”都要另立协议。`printf` 靠格式串里的转换说明计数，`execl` 靠结尾的 `nullptr` 哨兵，自己写的 `min(int count, ...)` 靠一个额外的 `count`。这些协议都不在类型系统里，调用方漏写一个参数，被调方只能继续往下读栈。CCS-98 的建议是不要在函数签名里用省略号，也不要轻易调用带省略号的函数，包括 `sprintf` 这类标准 C 函数；需要可变参数时，用类型安全的设施，或者把 C API 包进一个薄的类型安全封装。

CCS-99 讲的是另一类边界：对象的生命周期。失效对象大致有三类。第一类是生命周期已经结束的，比如出了作用域的自动对象、已经 `delete` 的堆对象。第二类是语义上失效的，比如 `delete p` 之后的 `p`、`vector` 重新分配后的旧迭代器；悬垂指针和失效迭代器是同一件事的两种写法。第三类是从未合法存在的，比如用 `reinterpret_cast` 伪造的指针、越界得到的地址。对失效对象唯一安全的操作是给它赋一个新的有效值；`delete p` 不会把 `p` 变成 `nullptr`，继续解引用或再次 `delete` 都是未定义行为。

ASan 报 `stack-buffer-overflow`，写入位置正好越过 `label` 的边界。没有 sanitizer 时，多出来的字节可能覆盖返回地址、相邻变量或栈保护值；是否立刻崩溃取决于布局和优化级别。换成 `std::string` 后，缓冲区由字符串自己增长；必须写进固定缓冲区时，用能接收容量的接口，检查返回值，并显式补 `'\0'`。`std::format_to_n` 是 C++20 的一个选择：它接收输出区间和最大长度，返回输出迭代器，以及“如果没有截断本应写入的总长度”（不是实际写入的字节数）；它仍然要求你给出正确的容量，不能把“有边界检查”理解成“永远不会写错”。

不要手工调用析构函数再用 placement new 复活对象，除非你在写容器、`std::optional` 这类底层设施。普通代码里，对象的生命周期交给 RAII 类型：`std::vector` 管理缓冲区，`std::unique_ptr` 管理堆对象，`std::optional` 表示“可能有值”，`std::variant` 表示“几种类型之一”。C++20 的 `std::construct_at`/`std::destroy_at` 把构造和析构写成函数模板，适合泛型代码，但它们不会替你检查存储是否对齐、是否足够大、对象是否真的活着。C++17 的 `std::string_view` 和 C++20 的 `std::span` 则提醒另一面：它们不拥有数据，底层字符串或容器一旦重新分配，视图就悬垂；轻量不等于安全。

今天的工具能抓住一部分问题：`-Wformat` 在 `-Wall` 里，ASan 抓越界和 use-after-free，UBSan 抓空指针解引用和对齐错误，libstdc++ 的断言能在 `vector::operator[]`、`front` 这类地方提前终止。它们都只是测试期的网，不能替代“不制造失效对象”的设计。接口上少一个省略号、少一个裸 `strcpy`，比在每一个调用点加检查更有效。

## 回头看

四节讲的是四种不同的边界，问题却是同一个：边界两边必须对一套没有写进类型系统的协议达成一致。异常那一节里，协议是“错误怎么表示、谁来接住”；类型那一节里，协议是“这块内存按什么布局解释、名字在目标文件里叫什么”；省略号和失效对象那一节里，协议是“参数有几个、类型是什么、指针还指向不指向活对象”；数组和 ABI 那一节里，协议是“长度在哪里、谁负责清理、二进制接口由谁保证”。这些协议一旦靠口头约定，编译器就帮不上忙，错误往往要等到链接、运行或换一台机器才出现。

C++20 以后有一些工具能把这套协议写得更清楚：`std::span` 把指针和长度绑在一起，`std::format` 把格式串和实参的类型对上，`std::is_layout_compatible` 能检查两个 C++ 类型的布局，modules 能把名字可见性划清楚。但它们都不是 ABI 条约：span 和 string_view 不拥有数据，format 管不了 C API 的省略号，layout-compatible 问不了 C 编译器，modules 也不保证跨编译器。边界仍然要有人设计：导出函数用 `noexcept` 加 `catch (...)` 收口，接口收窄到双方都能正确解释的类型，数组带长度，失效对象不再使用，跨 ABI 时选择 C 接口或明确限定工具链。编译器的 `-Wformat`、`-Wsizeof-array-argument` 和 ASan/UBSan 能抓住其中一部分，剩下的靠这些写法本身。
