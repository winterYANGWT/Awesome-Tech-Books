# 第 17 章 继承：可替换性与契约

一个 `Square` 继承 `Rectangle`，编译器不会反对：正方形在数学上确实是矩形，类型系统也只检查“是不是派生自”。可一旦把 `Square` 交给一个只使用 `Rectangle` 接口的函数，函数里“改宽不会改高”的假设就会失效：

```cpp
void growWidth(Rectangle& r) {
    int old = r.height();
    r.setWidth(r.width() + 10);
    assert(r.height() == old);   // Rectangle 的契约
}
Square s(10);
growWidth(s);                    // 编译通过，断言却会失败
```

`growWidth` 没有做错任何事，它只是按 `Rectangle` 的契约办事，而 `Square` 兑现不了这份契约。public 继承在类型系统里承诺的正是“任何使用 `Rectangle&` 的地方都能换成 `Square&`”，调用方一旦相信这句话，就会按基类的行为写代码。本章围绕这份承诺展开：“是一种”（is-a）到底承诺了什么，接口继承和实现继承怎样分开，名字隐藏、非虚函数和默认实参为什么总能绕过动态绑定，以及 NVI（non-virtual interface，非虚接口）和纯虚基类怎样把契约收回到基类手里。

普通矩形被加宽后高度不变；正方形为了维持“宽高相等”，只能把高度一起改掉。Meyers 在 EC-32 里把 public 继承说成 C++ 面向对象设计里最重要的一条规则：`D` 公开继承 `B`，等于告诉编译器和读代码的人，每个 `D` 对象也是 `B` 对象，任何接受 `B&` 或 `B*` 的函数都能接受 `D` 对象，反过来则不成立。他举的例子是 `Person` 和 `Student`：`eat(const Person&)` 能接受学生，`study(const Student&)` 不能接受普通人。这不是一条风格建议，而是语言在重载决议、指针转换和虚调用里实际执行的模型。

问题在于，C++ 能检查的只有“接口能不能替换”，检查不了“行为能不能替换”。`Rectangle` 的接口里有 `setWidth`，`Square` 通过继承也拿到了它，签名完全匹配；但 `Rectangle` 的使用者还依赖一条没有写进签名的契约：改宽度不会改高度。`Square` 守住自己的“宽高永远相等”就必然破坏前一条。两边的不变式都合理，冲突无法调和，所以正确的结论不是给 `Square::setWidth` 加一个运行期断言，而是承认 `Square` 不是行为意义上的 `Rectangle`，不要 public 继承。CCS-37 因此更愿意用 works-like-a（用起来像）而不是 is-a：判断标准是基类的所有不变量和文档承诺，派生类是否都守得住。

Liskov 替换原则把这份契约说成前置条件和后置条件：覆盖版本可以要求更少、承诺更多，不能要求更多、承诺更少。基类说“传进来的宽度必须为正”，派生类不能改成“还必须为偶数”；基类说“调用后对象仍然可用”，派生类不能让它进入半失效状态。这些条件通常只写在注释和文档里，编译器看不见，`override` 也检查不了。CCS-38 把这一点展开成“安全覆盖”：签名对上只是入场券，真正的覆盖还要守住异常规格、默认实参和前后条件（17.5 节会回到这里）。

企鹅是另一个常被误用的类比。如果 `Bird` 声明了 `virtual void fly()`，这条声明就不只是“鸟有一个叫 fly 的成员”，而是“所有鸟都能飞”。`Penguin` 继承 `Bird` 却飞不起来，只有在 `Penguin::fly` 里抛异常或打印错误；这等于说“企鹅能飞，但真让它飞会出错”，错误被推迟到运行期。EC-32 建议把“会飞”拆到 `FlyingBird`，让 `Bird` 根本不声明 `fly`，于是 `penguin.fly()` 在编译期就找不到函数。这比运行期报错好，因为非法操作根本没有进入程序。反过来说，如果这个程序只关心喙和翅膀，从不处理飞行，那么不拆 `FlyingBird` 也可以是合理设计；EC-32 特意保留了这层限定：没有脱离用途的“唯一正确层次”。

EXC-22 从另一个方向补了一刀：public 继承是为了“被已有代码复用”，不是为了“复用基类的代码”。它评审的两个协议类只是调用 `BasicProtocol` 的公开函数来完成公共工作，基类没有虚函数、没有 protected 成员，派生类也没有多态替换的需求；这种关系是 is-implemented-in-terms-of（用某类型实现），应该把 `BasicProtocol` 变成成员，而不是基类。判断线索很实用：如果基类除析构外没有虚函数、没有 protected 成员、派生类只用到基类的公开接口，那么 public 继承几乎一定是误用。复用实现请用成员，只有确实需要访问 protected 成员或覆盖虚函数时才考虑私有继承，这部分留到[第 18 章](ch18.md)。

新标准没有替我们判断语义。C++11 的 `final` 能阻止继续派生，适合给值类型封口；C++20 的 `std::derived_from` 概念能在模板里检查“是不是公开派生”，但也只检查类型关系。它们都无法验证“改宽不改高”这类承诺。C++26 采纳的 contracts（P2900）可以把前置/后置条件写进函数声明，但本书环境（Clang 21、GCC 15）都还不支持；在编译器跟上之前，契约主要靠文档、命名、测试和代码评审守。即便有了 contracts，它检查的也只是写下来的条件，“改宽不改高”这种跨调用的行为承诺仍然要靠设计。今天能做的，是让基类接口尽量小、把契约写清楚，并在测试里始终通过基类引用去调用派生对象——只测 `Square s; s.setWidth(...)` 发现不了替换性问题，只有把它放进 `Rectangle&` 才会暴露。

## 17.2 先确定写的是哪一类 class

CCS-32 的建议是动笔前先回答一个问题：这个 class 到底是值类型、基类、traits、policy、异常类，还是辅助类？它们共用 `class` 关键字，规则却几乎相反。值类型模仿内置类型：析构、拷贝、赋值公开且带值语义，没有虚函数，也不打算被继承，通常放在栈上或作为成员直接持有，`std::pair`、`std::vector`、`Money` 都是例子。基类用来搭层次：析构要么 public + virtual，要么 protected + nonvirtual；拷贝构造和赋值通常非公开，防止切片；接口靠虚函数确立，对象一般经（智能）指针使用。traits 只装类型别名和静态函数，没有可变状态；policy 是可插拔行为的碎片，可能作为基类或成员出现；异常类按值抛出、按引用捕获，拷贝构造不能失败，常带虚函数和 clone。

CCS-36 处理另一端：如果要建层次结构，优先让根是一个抽象接口——只由纯虚函数组成、没有数据成员、通常也没有实现。依赖倒置原则要求高层模块和低层模块都依赖抽象，而不是高层直接依赖具体实现；备份程序如果直接调用“读目录”和“写磁带”的具体函数，换文件系统或换硬件就得改核心逻辑，改成依赖两个抽象接口后，新需求只需要新实现。抽象接口不带状态，构造、拷贝、赋值、析构的麻烦都被推到实现类里，这是它比“具体基类”简单的地方。接口也是最难改的部分，实现可以后修，接口改错可能再也没有机会。

CCS-36 说的是“优先”，不是“只能”。抽象接口把所有重复实现推给每个派生类，层次封闭、派生类由同一团队维护时，把共享的长度检查、元素存取、输出格式上提到基类会更省事；这部分取舍在 17.3 节结合 ESS-09 展开。C++20 的 concepts 提供了另一条静态接口的路：类型在编译期已知时，可以用一组表达式要求代替基类，不必付虚表的代价；但需要运行期替换实现时，抽象基类仍然不可替代。`std::unique_ptr<Formatter>` 配合公开虚析构，是今天表达“拥有一个多态实现”的常规写法；值类型则继续留在栈上，两者不要混着设计。

## 17.3 区分接口继承与实现继承

EC-34 把 public 继承拆成两件事：继承函数的接口，和继承函数的实现。三种成员函数声明正好对应三种组合。纯虚函数只给接口：具体派生类必须重新声明它，基类通常不提供实现，意思是“你必须会做这件事，但我不知道怎么做”。普通虚函数给接口加一份默认实现：派生类可以覆盖，也可以什么都不写，直接继承基类的做法。非虚函数给接口加一份强制实现：它表示一种不随特化改变的不变式，所有派生类都该用同一套行为。`Document` 的三个函数正好演示这三档：

`Invoice` 实现了 `body`，也覆盖了 `footer`，所以页脚是 `thank you`；`Memo` 只实现了 `body`，忘记覆盖 `footer`，于是默默继承了 `(no footer)`。这正是 EC-34 警告的默认实现风险：派生类作者可能根本不知道有这份默认行为，或者以为它会做别的事。书里的 `ModelC` 就是这样被当成 `ModelA` 飞出去的。想保留默认实现又不让派生类误继承，可以把默认实现放进独立的非虚 `defaultFly`，把 `fly` 改成纯虚，要求派生类在函数体里显式调用 `defaultFly`；另一种写法是给纯虚函数本身写定义，派生类要使用时写 `Base::fly(...)`，从而把“我要用默认实现”变成一次显式请求。两种写法都把“默认”从自动继承改成主动选择。

`header` 是非虚函数，所有文档的标题格式必须一致；`decorated` 也是非虚的，它把标题、正文、页脚按固定顺序拼起来，内部调用虚函数 `body` 和 `footer`。这已经带上了 NVI 的味道：基类掌握流程，派生类只填步骤。EC-34 还提醒不要走两个极端：全部非虚会让派生类没有任何特化空间，全部虚则放弃了不变式。担心虚调用开销时，80/20 规律通常比“把所有函数都写成非虚”更有说服力；真正热的 20% 才值得为内联做特殊设计。

纯虚函数也可以有定义，而且纯虚析构函数必须有定义，因为派生类析构时一定会调用它。MEC-33 把这一点用在一个很实际的地方：如果一个类没有天然的纯虚函数，又需要它成为抽象类，就把析构函数声明为纯虚并给出定义。抽象类的关键不是“一个函数都没有实现”，而是“不能直接创建对象”。

ESS-09 从派生类作者的角度补充了另一半：抽象基类不必是纯接口。纯接口依赖最小、替换最自由，但每个派生类都要重复长度检查、元素存取、输出格式这些不变逻辑；层次封闭、派生类由同一团队维护时，把共享数据和无类型依赖的算法上提到基类更省事。`Document` 保存了 `title_`，还提供了 `decorated`，属于偏厚的基类；如果这个层次要开放给外部扩展，薄接口加组合通常更稳。判断依据不是“抽象基类应该多纯”，而是谁写派生类、层次会不会经常扩展、共享实现值不值得让基类变大。

这组输出同时演示了 EC-37：`base->open()` 的函数体由动态类型决定，调用的是 `FileStore::open`，默认实参却由静态类型 `Store*` 决定，所以传入的是 `1` 而不是 `2`。默认实参不属于函数签名，不参与覆盖匹配，也不参与动态绑定；`override` 只检查签名，管不了默认值。只在派生类里重复写一个相同的默认值也不安全：基类将来改了默认值，所有重复处都要跟着改，漏一处就重新制造出“同一个对象、两种默认值”的问题。

EC-36 还给了一个设计层面的二难：如果 `FileStore` 真的需要另一套 `describe`，那它就不是行为意义上的 `Store`，不该 public 继承；如果它确实是 `Store`，`describe` 就该是所有派生类共享的不变式，不该在派生类里重定义。两者只能改一个。需要禁止进一步覆盖时，C++11 的 `final` 可以封住虚函数或整个类，但它不会把非虚函数变成可多态调用的函数；`override` 也不能写在非虚函数上，编译器会直接报错。

多态基类的析构函数是这个规则最重要的特例。析构函数在派生类里总会被“重新定义”，如果基类的析构不是虚的，通过基类指针 `delete` 就只调用基类版本；如果基类本来还有别的虚函数，GCC 和 clang 在 `-Wall` 下都会给出 `-Wdelete-non-virtual-dtor` 一类警告（clang 21 的诊断名是 `-Wdelete-non-abstract-non-virtual-dtor`），但 `std::string` 这种不是多态类的类型不会触发警告，17.2 节的 ASan 例子就是这种情况。析构函数的完整规则在[第 11 章](ch11.md)。

默认实参的静态绑定没有好的“就地修复”办法。EC-37 推荐 NVI：公开的非虚函数持有默认值，调用私有的虚函数完成实际工作，派生类只覆盖后者且不声明默认值。这样默认值只有一份，且在基类手里；17.6 节会把 NVI 完整展开。另一个方向是少用默认实参，改成重载或具名的配置对象，让每个调用点都明确写出参数；这不会改变绑定规则，但能让“用的是哪个值”在代码里看得见。

## 17.5 覆盖时守住契约：override、const 与 Base::f()

CCS-38 把“安全覆盖”拆成机械和语义两半。机械的一半是签名必须真的匹配：基类函数是虚函数，名字、参数类型、`const`/`volatile` 限定、引用限定符一致，返回类型相同或协变，异常规格不能比基类更宽松。语义的一半是前后条件：派生类可以要求更少、承诺更多，不能要求更多、承诺更少。基类的 `withdraw(amount)` 说“amount 为正即可”，派生类不能加一条“还必须是 100 的倍数”；基类说“失败时账户不变”，派生类不能让失败留下半扣款状态。签名对了只说明你覆盖了某个函数，不说明你守住了它承诺的行为。

诊断说得很具体：标记了 `override` 的函数并不是虚函数，它隐藏了 `Base::describe`，区别在 `const` 限定。EMC-12 因此建议所有意在覆盖的函数都写 `override`；`override` 不是关键字，只在成员函数声明的末尾有特殊含义，写错位置的代价远小于漏写。C++11 同时给了 `final`，用来封住虚函数或整个类，阻止下一层继续覆盖；它和 `override` 一样只作用于继承关系，不管前后条件。

`Base::f()` 是另一半。ESS-07 指出，在成员函数里写 `Base::name()` 或 `p->Base::name()` 会让调用在编译期绑定到指定版本，完全跳过虚分发。示例里的 `extendedName()` 先用 `Base::name()` 拿到 `"Base"`，再用未限定的 `name()` 做虚调用拿到 `"Derived"`，拼成 `Base+Derived`；`base.Base::name()` 则直接输出 `Base`。这两种写法本身没有错，错的是意图和写法不一致：想要多态却加了限定，或者想复用基类实现却忘了限定，前者静默调错版本，后者在 `log()` 这样的覆盖里会变成无限递归。

构造和析构期间的虚调用是这条规则的边缘情况：构造函数体执行时，派生类部分还没构造好；析构函数体执行时，派生类部分已经销毁。此时未限定的虚调用只会分派到当前构造/析构的那个类，不会到达更派生的版本。这也是为什么在基类构造/析构里调用虚函数通常得不到你想要的多态行为，[第 11 章](ch11.md)从对象生命周期的角度讲过。

覆盖时的异常规格有一条从 C++11 就存在的规则：基类函数是 `noexcept`，覆盖版本也必须是 `noexcept`，不能反而可能抛（C++17 把 `noexcept` 纳入函数类型，但没有改变这条覆盖规则）。C++20 允许 `constexpr` 虚函数，但不改变覆盖匹配规则。编译器这边，clang 21 的 `-Wall` 包含 `-Woverloaded-virtual`，能提示“这个同名函数隐藏了基类的虚重载”，本节的运行示例为了展示行为暂时关掉了它；GCC 15 在 `-Wall` 下也会给出 `-Woverloaded-virtual`。此外，GCC 的 `-Wsuggest-override` 能对每个漏写 `override` 的覆盖给出提示；clang 的 `-Winconsistent-missing-override` 则在一个类里有的覆盖写了 `override`、有的没写时报告不一致，是否启用取决于项目对告警的容忍度。

## 17.6 公开函数非虚，虚函数私有：NVI

CCS-39 和 EXS-18 讲的是同一件事：一个 public virtual 函数同时服务两拨人。对外，它是类公开接口的一部分，调用方依赖它的名字、参数和语义；对内，它是派生类的定制点，派生类依赖它的签名和调用时机。这两拨人的需求经常冲突，一个函数很难同时满足。NVI 的做法是把它们拆开：公开函数非虚，负责“什么时候做、做之前之后检查什么”；私有的虚函数负责“具体怎么做”。下面的 `Importer` 把路径检查和尝试计数放在公开的 `import` 里，派生类只实现 `doImport`：

空路径在进入 `doImport` 之前就被外壳拒绝，`CsvImporter` 根本不需要重复这段检查；每次尝试的计数也由基类统一维护，派生类想改也改不了。`doImport` 是 private 的，但 `CsvImporter` 照样能覆盖它：访问控制约束的是“谁能调用”，不是“谁能覆盖”。外部代码不能直接调用 `doImport`，只能走 `import`，于是基类始终掌握接口和策略。把 `import` 写成一行转发也不会留下运行期开销，内联之后通常和直接调用虚函数一样；EXS-18 特意指出，先放一个“什么也不做”的外壳，以后再加检查、日志或拆步骤，比先写 public virtual 再回头包一层容易得多，因为后者必然要动调用方或派生类中的一边。

虚函数默认放 private，只有派生类确实需要调用基类版本时才放 protected。EXS-18 的第三条准则说的是这个边界：`protected` 不是为了“让派生类方便”，而是为了“派生类必须能调到基类实现”。一旦放成 protected，派生类作者就会开始依赖它，基类的实现细节也就变成了接口的一部分。析构函数是这条规则的例外，因为它不适用 NVI：基类析构函数体执行时，派生类部分已经销毁，再虚分派也到不了更派生的版本。

析构函数的规则可以压缩成二选一：允许经基类指针多态删除，就 public + virtual；不允许，就 protected + nonvirtual。前者的典型是 `Importer`，`std::unique_ptr<Importer>` 能在 `Importer*` 上正确调用 `CsvImporter` 的析构；后者的典型是只作为基类、从不在堆上多态删除的工具类，析构设成 protected 后，`delete base` 在编译期就失败：

```cpp

```

最糟的是第三种：public 且非虚。它看起来允许删除，实际只调用基类析构，派生类成员没有释放，标准说这是未定义行为。17.2 节的 `std::string` 例子在 ASan 下报的就是这一类问题。如果基类本来就有别的虚函数，GCC 和 clang 在 `-Wall` 下会用 `-Wdelete-non-virtual-dtor` 一类警告提醒；如果基类一个虚函数都没有（`std::string` 就是），这条警告不会出现，只能靠“不要从具体类派生”的规则来防。EXS-18 提到的 `std::unary_function`/`std::binary_function` 是“只作基类、不给多态删除”的旧例子，它们在 C++11 被弃用、C++17 从标准中移除；本机的 libstdc++ 15 仍以弃用形式保留，所以旧代码在 C++20 下只会得到弃用警告。这种设计本身仍在；`std::exception::what` 至今还是 public virtual，因为标准库需要让调用方直接取到异常描述。

C++11 之后，NVI 的机械部分更容易写对：私有虚函数上的 `override` 照样检查签名，公开外壳可以用 `[[nodiscard]]`（C++17）把“别忽略返回值”写进类型，用 `final` 封住不该再改的类。C++20 的 concepts 提供了另一条“静态接口 + 非虚实现”的路，适合类型在编译期已知的场合；需要运行期替换实现时，NVI 仍然是首选。唯一要留意的例外是协变返回：如果调用方需要直接看到 `Derived*` 而不愿 `dynamic_cast`，把那个虚函数保持 public 会更省事（17.7 节会看到 clone 的写法），这也是 CCS-39 自己列出的例外。

## 17.7 纯虚基类从编译期阻止切片，clone 可以协变返回

切片（slicing）是把派生类对象复制进一个基类对象，只留下基类子对象，派生类新增的成员被静默丢掉。最典型的入口是按值传基类：

```cpp

Circle circle;
print(circle);             // 只复制 Shape 部分
```

错误落在两处：形参类型 `Shape` 是抽象类，调用点又试图创建一个抽象类对象作为实参。TIC-16 把这条技巧总结得很直接：把基类的关键函数声明为纯虚，基类就变成抽象类，“按值传基类”的函数根本没法被调用，切片在编译期就被挡住。它比运行期检查可靠，也不需要给基类写 clone；代价是基类不能再作为独立的值类型使用。如果确实需要“多态的值”，C++17 的 `std::variant` 可以表达封闭类型集合，类型擦除的值包装则能表达开放集合，这两条路都不需要靠继承加按值复制。

纯虚函数还有一条常被忽略的性质：它可以有定义，纯虚析构函数必须有定义。抽象类的关键不是“没有实现”，而是“不能直接创建对象”；派生类仍然可以调用 `Base::f()` 使用那份实现（17.3 节讲默认实现时提过这个写法）。这也解释了为什么“把析构函数设为纯虚”能让一个没有其他纯虚函数的类变成抽象类，而派生类的析构仍然能正常调用它。

## 回头看

这一章反复出现的是同一件事：继承把“接口能替换”写进了类型系统，却没有把“行为能替换”写进去。正方形与矩形、企鹅与飞行、具体基类与部分赋值，都是行为契约守不住；名字隐藏、非虚重定义、默认实参和少写的 `const`，则是调用方以为自己在做多态，实际按静态类型选中了另一个函数。它们看起来是四类问题，根子都是“声明和承诺不一致”：派生类声明自己是一种基类，却没有兑现基类的全部承诺，或者调用点声明自己按基类使用对象，实际却停在派生类的作用域里。

C++11 以后，机械的部分大多能交给编译器：`override` 把签名不匹配变成错误，`final` 封住不该继续覆盖的类或函数，`using` 把被隐藏的重载拉回来，`= default`/`= delete` 把特殊成员函数的意图写清楚，`[[nodiscard]]` 把“别忽略返回值”放进类型，`std::derived_from` 能在模板里检查继承关系。NVI、抽象接口和“析构要么 public + virtual、要么 protected + nonvirtual”仍然是设计层面的选择，语言只能帮你把选错的后果提前到编译期。语义契约——前置条件、后置条件、默认实参该取什么值、这个层次该不该存在——仍然要靠文档、测试和评审；C++26 采纳的 contracts 会多一件工具，但本书环境还不支持，本章没有用它写示例。
