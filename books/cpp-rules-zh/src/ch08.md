# 第 8 章 RAII：把资源交给对象

先看一段每天都会出现的代码：

```cpp
void import(const char* path) {
    std::FILE* f = std::fopen(path, "r");
    if (!header_ok(f)) return;       // f 没有关闭
    parse(f);                        // 可能抛异常
    std::fclose(f);
}
```

`header_ok` 返回 false 时提前返回，`fclose` 被跳过；`parse` 抛异常时也一样。把 `return` 改成 `break`、`goto`，或者以后有人在中间加一个 `return`，清理路径就又多一条缺口。这不是写代码的人不小心，而是“释放”和“获取”被放在两个地方，任何控制流分支都要记得回到第二个地方。C++ 的析构函数在对象离开作用域时自动执行，包括栈展开（stack unwinding）的时候；把资源和对象绑定，清理就不再依赖每一条返回路径。

把资源交给对象，接下来要回答四个问题。资源不只有堆内存，锁、文件描述符、窗口句柄、数据库连接都遵循同一套配对规则；资源管理对象被复制时，资源是共享、复制、转移还是根本不允许复制；对象构造到一半失败时，已经获取的资源由谁释放；最后，现实 API 只认裸资源，资源还要跨过模块边界，怎么借出、由谁释放。下面四节沿着这四步走。

析构的顺序也值得知道：局部对象按构造的逆序析构，成员按声明顺序构造、按逆序析构。这个顺序让“后取得的资源先释放”成为默认行为，正好对应依赖关系——如果 B 使用 A 的资源，通常先构造 A、再构造 B，离开作用域时先析构 B、再析构 A。RAII 类如果有多个资源成员，声明顺序就应该按依赖关系排；把顺序写反，析构时可能先释放别人还在用的东西。

RAII 也不是“把资源塞进对象就万事大吉”。构造函数本身也可能失败：如果构造函数先取得资源 A、再取得资源 B，而 B 的获取抛出，构造函数没有跑完，这个对象自己的析构函数不会执行，A 就漏了。这个问题是 8.3 节的主题；8.1 先记住一个更简单的纪律：一个对象尽量只负责一份资源，或者让每份资源各由一个成员对象负责，这样构造失败时已经构造完成的成员会自动析构。另一个边界是 `setjmp`/`longjmp`：它跳过栈展开，局部对象的析构函数不会执行；C++ 代码不应该用 `longjmp` 做错误处理，异常和返回值才是正常路径。

Meyers 在 EC-13 里把这件事说成两条：资源取得后立刻交给资源管理对象；资源管理对象用析构函数保证释放。他举的是工厂返回 `Investment*` 的例子，调用方要在每条路径上记得 `delete`。EC-13 的重点不是某个智能指针，而是“对象”这一层：只要资源在构造函数里取得、在析构函数里归还，正常返回、提前返回和异常展开都会走到同一个清理点。MEC-09 从另一个方向补上同一件事：资源不一定是堆内存，窗口句柄、文件、锁都可以放进“构造获取、析构释放”的包装类；书里的 `WindowHandle` 还把拷贝构造和拷贝赋值设为私有，避免同一个句柄被释放多次。Sutter 与 Alexandrescu 在 CCS-13 里把这条规则写成工程纪律：C++ 的构造/析构对称性正好对应 `fopen`/`fclose`、`lock`/`unlock`、`new`/`delete` 的对称性，不要手写配对；每次显式分配都放在单独语句里，并立刻交给管理者。

EC-13 写作时标准库还没有 `unique_ptr`，书里用 `auto_ptr` 和 TR1 的 `shared_ptr`。`auto_ptr` 拷贝时把所有权转走并把源置空，不能放进 STL 容器；C++11 起由移动语义和 `std::unique_ptr` 承担它的职责，`auto_ptr` 本身在 C++17 从标准中移除。本机的 libstdc++ 15 仍通过向后兼容头提供 `std::auto_ptr`，使用时给弃用警告，但新代码没有理由再用它。C++11 还带来 `std::lock_guard`，C++17 带来 `std::scoped_lock` 和 `std::shared_mutex`，它们把“加锁”和“解锁”绑在对象的生命周期上；读写锁的读侧用 `std::shared_lock`、写侧用 `std::unique_lock`，同样由析构函数解锁。标准库的 `std::fstream`、`std::unique_ptr`、`std::shared_ptr` 都是同一模式的现成实现。

`update_shared_state` 在持锁时抛异常，`lock_guard` 的析构函数仍然解锁；异常被捕获后 `try_lock` 成功，说明锁没有留在加锁状态。`update_two` 用 C++17 的 `scoped_lock` 一次锁两个 mutex，函数返回时两个锁一起释放。`use_widget` 在提前 `return` 之前没有写 `delete`，`unique_ptr` 的析构函数仍然打印了 `Widget` 的析构。这三个例子分别覆盖锁、多个锁和堆内存，清理点都只有一个：对象离开作用域。

C++17 还改了函数实参的求值规则，这一点和 CCS-13 的“一条语句只分配一个资源”有关。原书写道，`f(std::shared_ptr<Widget>(new Widget), std::shared_ptr<Widget>(new Widget))` 可能先把两个 `new` 都执行完，再构造两个 `shared_ptr`；如果第二个构造函数抛异常，第一块内存就没人释放。C++17 起，函数实参的求值顺序仍然不确定，但各个实参的求值不能交错（indeterminately sequenced）：一个实参里的 `new Widget` 和随后的 `shared_ptr` 构造不会被另一个实参插进来，所以这个具体的泄漏在 C++17 下不再发生。今天仍推荐 `std::make_shared` 和 `std::make_unique`，理由变成写法更短、不用重复类型名，以及 `make_shared` 只分配一次；而“每次显式分配单独成句”仍然是好习惯，因为第三方 API、自定义删除器和 C++17 之前的代码都还在。

管理数组时要小心释放形式。`unique_ptr<T>` 和 `shared_ptr<T>` 默认用 `delete`，拿它们管 `new[]` 会用错形式；`std::vector`、`std::string` 通常比数组包装更合适。`std::unique_ptr<T[]>` 从 C++11 就有，`std::make_unique<T[]>(n)` 从 C++14 起可用，析构时调用 `delete[]`；C++17 起标准库提供 `std::shared_ptr<T[]>`，同样记得用数组形式。原书用 `auto_ptr` 管 `new[]` 的例子在标准里是明确的错误，而不是“能编译但不好”；本机的兼容头即使让它编译，释放形式仍然是错的。“作用域结束时执行一段代码”的通用工具 `scope_exit`、`scope_fail`、`scope_success` 目前在 Library Fundamentals TS v3 里，写作 `std::experimental::scope_exit`，还没有进入正式的 C++ 标准（C++26 是否收录需核实）。本机 libstdc++ 15 的 `<experimental/scope>` 已经提供，clang 21 下实测可用；正式代码里更常见的是自己写一个十来行的作用域守卫，或者用 GSL 的 `gsl::finally`。

编译器能帮的忙有限，但不是没有。`[[nodiscard]]` 配合 `-Wunused-result` 能提醒调用方别丢掉返回值。把 `std::lock_guard` 写成临时对象而不是命名变量，Clang 21 会用 `-Wunused-value`、GCC 15 会用 `-Wunused-result` 警告；本机 libstdc++ 15 给它的构造函数加了 `[[nodiscard]]`，所以两个编译器都会提醒这个临时对象马上就被销毁了。命名但从未使用的 RAII 对象通常不会触发 `-Wunused-variable`，因为构造和析构本身就有副作用。clang-tidy 的 `cppcoreguidelines-owning-memory` 会检查用裸指针接管所有权的地方，`cppcoreguidelines-no-malloc` 会盯着 `malloc`/`free` 与 C++ 对象混用。运行时用 ASan 的 LeakSanitizer（本书检查默认开启 `detect_leaks=1`）能抓住忘记释放的堆内存；非内存资源则要靠自己把状态打印出来，或者用计数包装类观察，正如本节的两个例子。

Meyers 在 EC-14 里把资源管理类的复制行为归成四类，要求作者先选一种再写代码，而不是让编译器替他选。第一类是禁止复制：锁、文件句柄、唯一连接通常没有“副本”的意义。C++11 起写 `= delete`，在此之前是“声明为 private 且不定义”。第二类是对底层资源做引用计数：最后一个使用者消失时才释放；EC-14 的例子是把 `Mutex*` 换成带 `unlock` 删除器的 `shared_ptr`。第三类是深拷贝：每个对象拥有自己的资源副本，`std::string`、`std::vector` 都是这个语义。第四类是转移所有权；EC-14 写作时这靠 `auto_ptr` 的“拷贝即转移”实现，C++11 以后它属于移动构造和移动赋值，不再伪装成拷贝。

`SharedPass` 的复制只增加 `shared_ptr` 的引用计数，不重复加锁；两个 `SharedPass` 离开作用域后，外部的 `shared` 还在，所以 `depth` 仍是 1，直到 `shared.reset()` 让计数归零，控制块里的删除器才执行 `unlock`。这里删除器先检查 `depth()`，是为了避免 `lock()` 自己抛异常时去解锁一把没有锁上的 mutex；`Gate` 放在栈上、删除器只 `unlock` 不 `delete`，也是为了观察计数，真实代码应让 `Gate` 的生命周期由同一个 `shared_ptr` 或更外层的对象管理。

`Buffer` 的拷贝构造重新分配数组并逐个复制元素，所以修改 `copy[0]` 不影响 `original[0]`。它的拷贝赋值先用复制构造做出临时对象，再交换成员；如果复制中途抛异常，原对象保持不变。反过来，先 `delete` 旧数组再复制新数组，一旦复制失败，对象就留下一个悬垂指针——这是资源管理类赋值最常见的顺序错误。`Exclusive` 把拷贝构造和拷贝赋值都 `= delete`，只保留移动；两个 `static_assert` 在编译期证明它不可拷贝、可移动。标准库的 `std::lock_guard` 同样不可拷贝，`std::unique_lock` 可移动，`std::unique_ptr` 可移动不可拷贝；这些都可以用 `std::is_copy_constructible_v` 和 `std::is_move_constructible_v` 验证。

移动赋值要注意“移后源”的状态。标准只保证被移动的对象仍然有效、可以析构和重新赋值，不保证它保留原来的值；`std::unique_ptr` 被移动后变成空指针，`std::string` 被移动后的内容标准不作保证。资源管理类的移动构造应该把源对象的资源指针置空，移动赋值要先释放自己原有的资源、再接管源对象的资源，并处理自赋值。这些细节和第 7 章的移动语义共用一套规则；本节的重点是：如果类里出现“转移所有权”这个选项，它应该写成移动操作，而不是让拷贝偷偷把源对象掏空。

C++11 的移动语义把“转移所有权”从一种奇怪的拷贝变成了语言支持的正规操作，也让 `std::unique_ptr` 成为默认的独占所有权类型。`= delete` 让“禁止复制”的意图直接出现在类定义里，不必再依赖“私有且不定义”的链接期把戏。C++17 起 `std::shared_ptr<T[]>` 可以管理数组；`std::make_unique` 是 C++14 加入的。EC-14 里 `auto_ptr` 的例子今天只剩历史意义：`auto_ptr` 在 C++17 从标准中移除，本机 libstdc++ 仍通过向后兼容头提供它，但使用会给弃用警告。

引用计数不是万能的。`shared_ptr` 的计数是原子操作，拷贝有成本；两个对象互相持有 `shared_ptr` 会形成环，计数永远不归零，需要 `weak_ptr` 打破环（[第 9 章](ch09.md)）。如果资源的释放动作不是 `delete`，而是 `unlock`、`fclose`、`ReleaseHandle`，就用自定义删除器把释放动作绑在控制块里；如果只需要一个所有者，`unique_ptr` 加函数指针删除器更轻，删除器是类型的一部分，不需要控制块。这些选择属于“所有权语义”的问题，第 9 章会展开；本节要记住的是：资源管理类必须显式选择拷贝行为，编译器生成的版本不会替你考虑资源。

## 8.3 构造函数失败也不能泄漏

8.2 讨论的是对象已经存在之后怎么复制；构造过程本身也会失败。C++ 只析构“完全构造完成”的对象：构造函数抛出时，这个对象自己的析构函数不会执行，但已经构造完成的成员子对象会执行析构。这条规则决定了资源应该放在哪里。

`RawBook` 先 `new Slot("image")`，再 `new Slot("audio")`；第二个 `Slot` 的构造函数抛出，`RawBook` 的构造函数没有跑完，`~RawBook` 不会执行，`image_` 指向的槽位就留在登记表里。输出里的“仍占用 1 个槽位”不是抽象说法，而是 `SlotPool::live` 里真的还留着一个 id。这里泄漏的是 `Slot` 对象本身，而不是 `new` 分配的原始内存：`new Slot(...)` 的构造函数抛出时，new 表达式会自动调用对应的 `operator delete` 还掉那块内存；但 `Slot` 构造函数里已经登记到 `SlotPool` 的槽位不在那块内存里，必须由 `~Slot` 释放。`CatchBook` 在构造函数体里用 `try/catch(...)` 捕获，`delete image_` 后重新抛出，槽位回到 0；代价是清理代码要在析构函数里再写一遍，资源一多，`catch` 块就要跟着维护。`SafeBook` 把两个指针换成 `std::unique_ptr<Slot>`，在成员初始化列表里用 `std::make_unique` 创建；`audio_` 抛出时，已经构造完成的 `image_` 作为成员子对象自动析构，`SafeBook` 的析构函数根本不需要写。

`SafeBook` 能成立依赖成员声明顺序：`image_` 声明在 `audio_` 前面，所以先构造 `image_`；`audio_` 抛出时，`image_` 已经是一个完整对象，栈展开会析构它。如果把 `audio_` 声明在前面，它先构造并抛出，`image_` 还没构造，也就没有泄漏——结果碰巧也对，但依赖的是“失败发生在第一个资源”，而不是异常安全的设计。成员初始化列表的书写顺序不决定构造顺序，真正决定顺序的是声明顺序；这也是第 4 章反复提醒的规则。

MEC-10 把这条规则讲得很细。构造函数抛出时，C++ 不会调用这个对象的析构函数，因为对象还没有完整地存在；如果析构函数硬要运行，它无法知道哪些成员已经构造、哪些还没有，除非给每个对象加一份“构造进度”记录，这会给所有对象增加开销。Meyers 给的直接修法是在构造函数体里 `catch (...)`，释放已经拿到的资源，再 `throw;`；更稳的修法是把资源交给成员对象，让成员的析构函数在栈展开时完成清理。书里还专门讨论了 `const` 指针成员：`Image* const image_` 必须在初始化列表里赋值，于是有人写成 `image_(new Image(...))`、`audio_(new Audio(...))`；如果第二个初始化抛异常，第一个 `new` 出来的对象没有人释放。初始化列表只能写表达式，不能包 `try/catch`，所以书里给的做法是私有 `initImage`/`initAudioClip` 函数，或者在成员里直接放智能指针。用私有初始化函数时，第一个函数不需要处理异常（它失败时还没有别的资源），第二个函数要 `catch` 住并释放第一个函数的成果；这种“谁在后面谁负责前面”的分工很容易写错，也正是成员对象方案更省心的原因。

C++11 的委托构造函数和类内成员初始化器能减少重复的初始化代码，`std::make_unique`（C++14）让“分配后立刻交给成员”写成一条表达式；但“构造函数抛异常不调用自身析构函数”的规则没有变。`std::unique_ptr` 成员的析构函数在栈展开时执行，正好补上这个缺口。构造函数函数 try 块（function-try-block）看起来能包住初始化列表，实际也救不回对象：成员在进入 handler 之前已经析构，handler 执行完还会自动重新抛出当前异常；它适合记录日志或转换异常，不适合把构造继续下去。

析构函数还有一个现代 C++ 的默认约定：从 C++11 起，析构函数默认是 `noexcept(true)`。如果资源释放本身可能抛异常，异常会在析构函数里触发 `std::terminate`，而不是让调用方处理。Clang 21 对“默认 `noexcept` 的析构函数里 `throw`”给 `-Wexceptions` 警告，GCC 15 给 `-Wterminate`（后者的警告文案直接说明会调用 `terminate`）。所以 RAII 类设计时要把“释放不会失败”当作前提；确实可能失败的清理（比如网络关闭）应在析构函数里吞掉错误或只记日志，把可报告的错误留给显式的 `close()`（[第 11 章](ch11.md)）。

构造函数泄漏用 ASan 的 LeakSanitizer 很容易看见：本节示例若去掉 `delete g_leaked_image`，程序退出时就会报一条 direct leak。静态分析里 clang 的 `clang-analyzer-cplusplus.NewDeleteLeaks` 可以找“分配后没有释放”的位置，包括构造过程和异常路径。示例里的全局 `g_leaked_image` 只是为了让演示程序自己回收，真实代码没有这根救命稻草；这正是要把资源放进成员对象的原因。

## 8.4 裸资源要给受控出口，内存要谁分配谁释放

资源管理类不能把资源关起来不让人用。大量 C API 只接受 `FILE*`、`HANDLE`、`sqlite3*` 这样的裸句柄，调用方必须能拿到内部资源。问题是“拿到”不等于“接管”：`get()` 借出指针，所有权仍在 RAII 对象手里；隐式转换则可能在调用方没注意的时候把指针带出对象的生命周期。

`Font` 提供三种访问：`get()` 返回裸指针，`operator->` 和 `operator*` 让对象用起来像指针。`face_set_size(title.get(), 18)` 在调用点明确写出了“这里要交给 C API 一个裸指针”，读代码的人能看到所有权的边界；`title->size` 和 `(*title).size` 则保留指针的用法，但生命周期仍由 `title` 决定。`get()` 不转移所有权，`borrowed` 与 `title.get()` 指向同一块内存，`Font` 析构后 `borrowed` 就悬垂了。EC-15 的判断是：显式转换（`get()`）通常更安全，隐式转换更方便；选择哪一个，要看这个 RAII 类主要解决什么问题。RAII 类的首要职责是保证释放，不是把资源藏起来；`shared_ptr` 隐藏了引用计数的实现，但仍然提供 `get()` 和 `operator->`。

`get()` 借出资源、所有权仍留在智能指针手里，`release()` 放弃所有权，两者不能混。`std::unique_ptr::release()` 返回裸指针并把智能指针置空，调用方从此负责释放；它适合把资源交给一个只接受裸指针的旧接口，或者交给另一个所有者。`std::shared_ptr` 没有 `release()`，因为共享所有权不能从计数里“抽走”一个引用而不通知控制块。用 `get()` 把指针传进 C 函数后，如果函数内部保存了这个指针、在 RAII 对象析构之后才使用，责任在调用方：RAII 类无法知道外面借了多久。这也是显式接口的价值——它把“这里只是借”写在代码里，而不是藏在一次隐式转换后面。

`device.h` 只声明 `struct Device;`，`main.cpp` 不知道它的大小和布局；`device_open` 在插件里 `new`，`device_close` 在插件里 `delete`。`std::unique_ptr<Device, void (*)(Device*)>` 把 `device_close` 写进类型，`std::shared_ptr<Device>` 把 `device_close` 存进控制块；两者离开作用域时都调用插件里的释放函数，输出里两次 `plugin: 关闭设备` 就是证明。`shared_ptr` 的删除器是类型擦除的：`shared_ptr<Device>` 的类型不因为删除器不同而改变，删除器跟着控制块走，所以它能跨过只知道 `Device` 前置声明的边界。`unique_ptr` 的删除器是类型的一部分，`unique_ptr<Device, void(*)(Device*)>` 比默认的 `unique_ptr<Device>` 多存一个函数指针，但不需要控制块。

`shared_ptr` 只保证“调用正确的释放函数”，不保证原模块还在。控制块在构造 `shared_ptr` 的模块里分配；如果插件把 `shared_ptr` 返回给调用方，控制块和删除器捕获的状态就可能落在插件的堆上，模块卸载后它们一起失效。即使控制块在调用方，删除器指向的代码仍在插件里；如果插件已经被卸载，删除器再正确也无法安全执行。`shared_ptr` 对象本身的跨模块传递还要求两边对它的布局和 ABI 有一致理解，标准库版本不同时尤其危险。更稳的接口是成对导出 `create`/`destroy`，让调用方只持有不透明句柄，或者由调用方提供缓冲区并负责释放。示例里的两个模块用同一套编译器和标准库编译，所以它证明的是“删除器走对了函数”，不是“任意 ABI 都兼容”。

## 回头看

四节合起来防的是同一件事：资源的获取和释放被控制流拆散。8.1 把释放放进析构函数，让正常返回、提前返回和异常展开走同一个清理点；8.2 决定这个对象被复制时资源怎么办，避免两个析构函数释放同一份资源；8.3 把同样的思路提前到构造阶段，让构造失败的半成品也能由成员对象收拾；8.4 承认资源终究要交给只认裸指针的 API，于是把“借出”和“释放”分开：`get()` 明确借出，删除器或 `create`/`destroy` 对明确释放。四步里任何一步含糊，前面的自动清理都会被绕开。

C++11 以后，语言和标准库替我们兜住了大部分常见情况：移动语义让独占所有权可以按值传递，`unique_ptr`/`shared_ptr` 和 `lock_guard`/`scoped_lock` 把释放写成类型的一部分，`= delete` 把禁止复制写进类定义；C++17 的求值顺序让“两个实参各分配一个资源”的经典泄漏不再发生，C++23 的 `out_ptr` 让 C API 的输出参数也能接回智能指针。仍然要靠人的是语义选择：这个资源能不能复制、共享到什么时候、释放动作是否可能失败、跨模块时哪一边负责释放、析构函数是否真的不会抛。工具能检查其中一部分——ASan 抓堆泄漏和分配/释放不匹配，clang-tidy 抓裸指针接管所有权——但“谁拥有这份资源”这个决定，编译器替不了。
