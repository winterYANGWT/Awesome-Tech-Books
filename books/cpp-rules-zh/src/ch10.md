# 第 10 章 new/delete、分配器与内存账本

下面这段代码想给 `Order` 加一个“在指定地址构造”的入口，结果普通的 `new Order` 反而编译不过：

```cpp
class Order {
public:
    static void* operator new(std::size_t size, void* where) noexcept {
        return ::operator new(size, where);
    }
};

Order* p = new Order;   // 错误：类里的 operator new 把全局的普通形式挡住了
```

类里只要出现一个名为 `operator new` 的函数，名字查找就停在类作用域，全局的普通、`nothrow`、placement 三个版本都不再参与重载决议。写这个类的人以为只加了一个方便函数，用这个类的人却连最普通的动态分配都做不了。

这类问题之所以反复出现，是因为 `new` 这个词在 C++ 里指的不是一件事：`new T` 是语言内建的 new 表达式，`operator new` 是可替换的分配函数，placement new 是带额外参数的分配函数，`new[]` 又是另一套名字。再往下，标准容器不直接调用 `new`，而是经过分配器（allocator）向运行库要内存；运行库再向操作系统要。每一层都可能有自己的块大小、块头和取整策略。本章沿这条链往下走：先拆开 new 表达式，再看什么时候值得替换全局分配函数、类级版本要遵守哪些约定，然后进入分配器的契约与内存账本，最后讨论“对象该在堆上还是栈上、数量要不要限制”。

## 10.1 new 表达式到底做了什么

`new Account("alice", 100)` 这一行看起来是一个动作，实际是两步：先调用分配函数拿到一块足够大的原始内存，再在这块内存上调用构造函数。`delete a` 正好反过来：先调用析构函数，再调用释放函数把内存还回去。Meyers 在 MEC-08 里把这两件事分得很清楚：new 表达式（new expression）是语言内建的运算符，它的“分配 + 构造”语义不能改；`operator new` 只是一个返回 `void*` 的普通函数，负责找内存，不知道构造函数是什么。

第 1 步先打印 `Account::operator new(40)`（本机 `sizeof(Account)` 是 40），再打印构造函数，顺序不能反；第 2 步先析构再释放。第 3 步只有分配和释放，没有任何构造、析构。第 4 步的 placement new 调用的是 `operator new(size_t, void*)`，标准库在 `<new>` 里提供的版本只是把传入的地址原样返回；对象构造在这块现成的存储上，所以既没有分配，也不能用 `delete` 释放——存储来自栈数组，不是 `operator new`。MEC-08 的结论是：想管理裸内存就直接调用 `operator new`/`operator delete`，它们相当于 C 的 `malloc`/`free`；想在已有地址上构造对象才用 placement new，并且要显式调用析构函数。

第 5 步是 EC-51 强调的一个细节：类级 `operator new` 会被派生类继承调用，`new Derived` 传给 `Base::operator new` 的是 `sizeof(Derived)`，不是 `sizeof(Base)`。如果这个分配函数是按 `Base` 的大小特调的，就必须在尺寸不匹配时转给全局版本：

```cpp
static void* operator new(std::size_t size) {
    if (size != sizeof(Base)) return ::operator new(size);
    // 这里才按 Base 的大小做特殊分配
}
```

同样的道理，类级 `operator delete` 收到不匹配的尺寸时也要转给 `::operator delete`。EC-51 还要求分配函数把 0 字节的请求当成合法请求，返回一个可以传给释放函数的非空指针（第 6 步）；释放函数必须安全接受空指针。`operator new[]` 则连“元素个数”都推不出来：字节数里可能有数组 cookie，元素类型也可能是派生类，所以不要在 `operator new[]` 里做任何依赖元素类型的构造或析构。`new[]` 与 `delete[]` 的形式配对在[第 9 章](ch09.md)已经从所有权角度讲过（EC-16）；这里只强调分配函数这一侧。

placement new 的配套规则是 EC-52 的主题，也是最容易漏的一条。普通 `delete p` 永远只调用普通的 `operator delete`，不会调用任何 placement 版本；placement delete 只在一种情况下由运行时调用：用带额外参数的 `operator new` 分配成功、但构造函数抛出异常时。运行时按 `operator new` 的额外参数列表去找签名匹配的 `operator delete`，找不到就什么也不做，那块内存就泄漏了。下面的程序用一个自己记账的 `Arena` 把三种情况摆在一起：构造成功后由调用方显式析构并归还存储；构造抛异常且写了匹配的 placement delete 时自动归还；没写匹配版本时块数停在 1。

最后是 EXC-35 提醒的存储区域问题。C++ 程序里至少有五类存储：const 数据区（字符串字面量等，只读）、栈（自动变量）、自由存储（free store，`new`/`delete` 管理）、堆（heap，`malloc`/`free` 管理）、全局/静态区。自由存储和堆是两套设施：标准不规定 `new` 是否用 `malloc` 实现，但明确规定 `malloc`/`free` 不得调用 `operator new`/`operator delete`，所以 `new` 出来的块不能交给 `free`，`malloc` 出来的块也不能交给 `delete`。下面的写法在标准里没有定义，ASan 通常会当场报 `alloc-dealloc-mismatch (operator new vs free)`：

```cpp
int* p = new int(1);
std::free(p);           // 未定义行为：自由存储的块交给堆的释放函数
```

EXC-35 的建议是优先用自由存储、避免直接操作堆；今天这条建议可以扩展成：优先用容器和智能指针，只有在写分配器或底层设施时才直接碰 `operator new`。

## 10.2 什么时候值得替换全局 new/delete

替换全局 `operator new`/`operator delete` 的诱惑通常来自三件事：想知道程序到底分配了多少、想抓住越界和重复释放、嫌默认分配器太慢或太占内存。EC-50 把正当理由列得很全：检测使用错误（泄漏、重复删除、越界写）、收集分配统计（块大小分布、生命周期、高水位）、提高特定分配模式的性能、减少每块的空间开销、修正默认分配器的对齐、把相关对象聚到相近的页、接入共享内存等特殊区域。它也给了同样的警告：默认分配器要在长跑服务器和短命小工具、大块和小块、长期存活和频繁创建销毁之间折中，因此对谁都不是最优；自定义版本可以在特定程序里快很多、省很多，但写错的机会也多得多。

对齐是 EC-50 点名的经典陷阱。下面的“前后加签名”的调试分配器看起来很合理，却在返回给用户的指针前加了一个 `int`，于是原本由 `malloc` 保证的最大对齐被破坏：

```cpp
void* p = std::malloc(size + 2 * sizeof(int));
// 在 p 前后写签名，然后返回 p + sizeof(int)
return static_cast<std::byte*>(p) + sizeof(int);   // 可能不再对齐 double
```

今天的替代品比 2005 年多：ASan/LSan 能抓越界、重复释放和泄漏，Valgrind 也能，很多运行库自带调试分配器；只在需要统计或特殊内存来源时才自己写。真要替换，先测量，再决定是全局替换还是只给某个类写类级版本。

全局替换必须遵守 EC-51 的约定。`operator new` 内部是一个循环：尝试分配，失败就取当前 new-handler 并调用；handler 返回后再次尝试，直到成功、handler 抛出异常或终止程序。请求 0 字节要返回合法指针；分配失败最终抛 `std::bad_alloc`；`operator delete` 必须安全接受空指针。C++14 起还有 sized deallocation，`operator delete(void*, std::size_t)` 可能被调用；C++17 起还有对齐版 `operator new(std::size_t, std::align_val_t)` 及配套 delete。替换全局版本时，普通、数组、sized、对齐这几组要一起提供：只替换一半，会让某些分配走你的版本、释放走库的版本（或反过来），账目和配对都对不上。下面的程序替换了全局的单对象和数组版本（含 sized delete），没有替换对齐版，所以过对齐分配不记在这本账上；只统计自己关心的两次操作；数组那行多出来的 8 字节是本机 libstdc++ 为“元素个数”加的数组 cookie，`operator new[]` 收到的字节数并不等于元素大小乘个数。

“检查分配失败”本身也常常不值得。EXS-23 举了三个理由：在不立即提交内存的系统上，分配几乎总是成功，真正缺内存时可能是在访问某一页时被 OOM killer 终止；在虚拟内存系统里，系统往往先颠簸到不可用，再由管理员杀进程；真到了那一步，能做的也很有限，连构造一个带字符串的异常对象都可能再需要内存。真正值得检查的是“请求的尺寸本身不合理”：报文长度、文件大小这类外部输入给出的缓冲区尺寸必须校验，否则既是拒绝服务攻击面，也是溢出漏洞的来源。C++11 还加了 `std::bad_array_new_length`，专门报告“元素个数大到不可能”的情况。

C++17 的 `std::pmr` 提供了另一条路：不替换全局 new/delete，而是把某几个容器接到 `monotonic_buffer_resource`、`unsynchronized_pool_resource` 或自定义 `memory_resource` 上。这样内存来源是局部的，失败点也局部化，不会影响整个程序。ASan/LSan、Valgrind 和计数分配器能替代大部分“调试型全局分配器”的需求；真要为性能替换，先 profile，再考虑 `std::pmr` 或 Boost.Pool 这类成熟实现，不要从 `malloc` 加偏移开始手写。全局替换还会影响跨模块释放；“谁分配谁释放”的边界在[第 8 章](ch08.md)讲过（CCS-60），本章不展开。

## 10.3 类级 new 会隐藏全局形式，还要配齐数组和 placement 版本

10.1 节开头的编译错误就是这一节的核心。Sutter 在 EXS-22 里把名字查找的规则说得很直接：编译器从当前作用域往外找 `operator new`，一旦在类（或它的基类）里找到至少一个同名函数，就停止向外查找，只在找到的这组重载里做决议；即使没有一个签名匹配，即使选中的函数不可访问，也不会回头去看全局版本。下面的反例把四种被挡住的写法放在一起：类里只有 placement new、基类里有带额外参数的版本、类里只有带额外参数的 `operator new[]`。

前三个 `new` 表达式是同一个 `operator new` 名字被类作用域截住；最后一个 `new[]` 是 `operator new[]`，它是另一个名字，单独被类里的数组版本截住。注意类级 `operator new` 不会挡住全局 `operator new[]`，反过来也一样：单对象和数组是两套名字、两套查找，配齐时要分别检查。EXS-22 的处方因此是三条：提供任何类级 new 时，总要同时提供普通的单参数版本；总要提供类级 in-place 版本；考虑提供 nothrow 版本，否则它会被前两个版本挡住。数组形式同理，需要单独提供。

普通版本应该保持全局语义，通常直接转调 `::operator new(size)`，这样全局 new 被替换成调试或统计版本时，类级版本也能跟着生效；in-place 版本应保持不分配、不抛，转调 `::operator new(size, where)`；nothrow 版本可以转调全局 nothrow，也可以在自己的普通版本外面包一层 `try`/`catch` 后返回空指针。类内不能写 `using ::operator new;` 来引入全局名字——类里的 using 声明只能引入基类成员——所以要么手写这几个透传函数，要么继承一个像下面这样的基类，再用 `using` 把名字带进来。

```cpp
class StandardNewDeleteForms {
public:
    static void* operator new(std::size_t s) { return ::operator new(s); }
    static void operator delete(void* p) noexcept { ::operator delete(p); }
    static void* operator new(std::size_t s, void* w) noexcept { return ::operator new(s, w); }
    static void operator delete(void* p, void* w) noexcept { ::operator delete(p, w); }
    static void* operator new(std::size_t s, const std::nothrow_t& t) noexcept {
        return ::operator new(s, t);
    }
    static void operator delete(void* p, const std::nothrow_t&) noexcept { ::operator delete(p); }
};
```

EXC-36 补充的是配对和数组两条。提供类级 `operator new` 就必须提供对应的 `operator delete`，只写 delete 不写 new 更危险：默认 new 分配的存储未必适合这个类，派生类再自定义 new 时就会错配。数组版也要成对，`new[]` 配 `delete[]`。`operator new`/`operator delete` 即使不写 `static` 也永远是静态成员，不能赋给成员函数指针，显式写 `static` 是给读者的提醒。通过基类指针删除派生类数组是未定义行为：`Base* p = new Derived[3]; delete[] p;` 里，数组的元素个数和每个元素的真实大小只有派生类知道，运行时的释放函数按静态类型 `Base` 去算，ASan 会报 `new-delete-type-mismatch`。下面的程序演示这一点，正常代码应该用 `std::vector<std::unique_ptr<Base>>` 或 `std::vector<Derived>` 代替。

## 10.4 分配器的契约：按对象个数分配，不构造

先看一个容易读错的调用：

```cpp
std::allocator<int> alloc;
int* p = alloc.allocate(4);   // 4 个 int 的存储，不是 4 字节
```

`allocate(n)` 的参数是“能容纳多少个 `T` 对象”，不是字节数；返回的 `T*` 指向未构造的存储，里面还没有 `int` 对象，构造是调用方的事。ESTL-10 把这条契约讲得很细，因为分配器和 `operator new`、`malloc` 的接口都不一样：`operator new` 按字节要内存、返回 `void*`；`malloc` 也按字节；分配器按对象个数，返回 `T*`。把写 `operator new` 的经验直接搬到分配器上，第一步就会把 `n * sizeof(T)` 算错。

EXS-20 把内存管理分成四层：操作系统内核、编译器运行库（`malloc`/`operator new`）、标准容器与分配器、用户自定义容器与分配器。每一层都可以覆盖下一层的策略。通用分配器能处理任意大小，但每次要做更多工作，反复分配释放会留下外部碎片；固定大小分配器只发一种尺寸，快且不产生同类碎片，却只服务一个尺寸。实际实现几乎总是混合：按 16、32 字节等尺寸分档，请求 17 字节就从 32 字节的档里取，15 字节白白浪费。这个“向上取整”是后面算内存账的关键。

分配器还有几条容易忽略的约束。基于节点的容器（`list`、`set`、`map`）不会用 `allocator<T>` 直接分配 `T`，而是通过 `rebind` 取得节点类型的分配器，再按“一个节点”分配；所以传给 `list<int>` 的 `allocator<int>` 可能一次都没有分配过 `int`。C++98 还允许实现假定同类型的分配器都相等，因此可移植的分配器不能带影响行为的非静态状态；C++11 的 `allocator_traits` 正式支持有状态分配器，用 `propagate_on_container_copy_assignment`、`propagate_on_container_move_assignment`、`propagate_on_container_swap` 决定复制、移动、交换容器时分配器怎么走；`swap` 按 `propagate_on_container_swap` 处理，`splice` 仍要求两边的分配器相等。`pointer`/`reference` 这两个 typedef 在 C++98 是为了抽象内存模型，标准允许实现假定它们就是 `T*`/`T&`；今天日常写分配器仍应保持这个默认，不要用代理引用。

ESTL-11 讲的是分配器的正当用途：换元素内存的来源，而不是重写通用内存管理。典型场景是共享内存堆、按容器分组的专用堆（把堆编码成类型参数，而不是运行期对象参数）、单线程免同步的池，以及让常一起访问的元素彼此靠近。分配器只负责元素存储；不手动 placement new 的话，容器对象本身（指针、大小、分配器）仍在普通内存里。要把整个容器放进共享内存，得手工四步：分配共享内存、placement new 构造容器、显式析构、释放共享内存，四步都不能省。C++17 的 `std::pmr` 把这些需求做成了标准设施：`monotonic_buffer_resource` 适合“只增不减”的批量对象，`unsynchronized_pool_resource` 按尺寸分档，自定义 `memory_resource` 可以接共享内存；C++11 起的 `std::allocate_shared` 还能让共享指针的控制块使用指定分配器。

## 10.5 分配与构造分离：容器为什么不用 new T[n]

手写一个 `vector` 时，最自然的写法是 `new T[n]`，但它一下子做了两件事：分配存储，并且把 n 个槽位全部默认构造。对容器来说，这两件事必须分开。第一，容量里没用到的槽位不应该含已构造的对象；第二，`new T[n]` 要求 `T` 可默认构造，而 `std::vector` 没有这个要求，`vector<Record>` 里的 `Record` 可以只有 `Record(int)`。ACC-20 因此把“分配内存”和“构造对象”当成手写容器的第一条分界线：先用分配器拿原始存储，再在需要时逐个构造，销毁时只析构已经构造的区间，最后归还整块存储。

## 10.6 对象该在堆上还是栈上，数量要不要限制


MEC-27 还专门拆穿了几种“判断对象在不在堆上”的土办法。比较局部变量地址和对象地址不可移植：栈的增长方向由平台决定，而且静态/全局对象既不在栈上也不在堆上，会被误判成堆对象。在 `operator new` 里设一个标志、在构造函数里检查也不可靠：数组只调用一次 `operator new[]` 却调用多次构造函数，基类子对象和成员子对象的构造也会走同一个构造函数，标志会在错误的时机被清掉。C++ 没有标准 trait 能回答“这个地址是不是 `operator new` 返回的”；真需要判断能否安全 `delete this`，只能自己记录 `operator new` 返回过的地址（Meyers 的 `HeapTracked` mixin），或者用 `dynamic_cast<const void*>(this)` 取得对象起始地址再查表。C++20 的 `std::is_layout_compatible` 只谈布局，不解决堆归属。

C++11 之后，这些手法的替代品多了一些：要求堆上创建可以用 `std::unique_ptr<T, Deleter>` 配合自定义删除器，把 `destroy()` 的逻辑放进删除器；禁止堆上创建可以用 `= delete`，比 private 声明更醒目；数量限制可以用 `std::atomic` 计数器或 `std::call_once`。但 MEC-27 的核心结论没有变：语言没有“对象在堆上”这个类型级属性，任何检查都是约定或记录，不是编译期保证；把限制写进构造函数、析构函数和 `operator new` 的访问控制，才是能被编译器执行的部分。

## 回头看

这一章沿着同一块内存走了四手：new 表达式把“大小”交给分配函数，分配函数把“块”交给分配器，分配器把“对象个数”换算成字节，最后落到运行库和内核。每换一手，单位、对齐、配对关系和所有权都可能变一次。new 表达式保证“分配 + 构造”的顺序，`operator new` 只保证返回一块未构造的存储；placement new 把构造搬到调用方给的地址，于是释放也必须由调用方负责；类级 new 改变了名字查找的起点，隐藏了全局形式；分配器把字节数换成对象个数，还要求调用方自己构造；容器的容量、块取整和块头又让“元素大小乘个数”变成一个下界，而不是实际占用。

C++11 以后，标准库接管了这条链上的不少手工活：`allocator_traits` 统一分配器接口并支持有状态分配器，C++14 的 sized deallocation 和 C++17 的对齐 new/delete 补齐了释放函数的签名，C++17 的 `pmr` 把池化资源做成标准设施，C++20 的 `construct_at`/`destroy_at` 和 destroying delete 把构造、析构的边界写进库，C++23 的 `allocate_at_least` 承认分配器可能多给。但语言没有替我们决定类级 new 要不要成套、placement new 要不要配 delete、容器该不该换分配器，也没有提供“这个地址在不在堆上”的 trait。这些仍要靠写法、约定和测量；ASan/LSan、`-Wdelete-incomplete`、计数分配器能替你抓到一部分错误和账目，抓不到设计上的配对缺失。
