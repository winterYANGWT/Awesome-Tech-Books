# 第 30 章 并发与内存模型

传感器校准一次要跑三秒。为了不重复算，`calibrated()` 把结果塞进 `mutable` 成员，算完把 `valid_` 置真：

```cpp
Samples calibrated() const {            // 看起来只是读
    if (!valid_) {
        compute(samples_);              // 实际写了两个 mutable 成员
        valid_ = true;
    }
    return samples_;
}
```

函数是 `const` 的，调用方看到它就像看到 `size()` 一样放心，于是四个线程同时调用了它。这里没有一行“写共享变量”的显眼代码，却同时发生了 `valid_` 和 `samples_` 的读写；多个线程对同一批内存读写、中间没有任何同步，C++11 的内存模型把这种情况定义为数据竞争（data race），后果是未定义行为（undefined behavior，UB）。`const` 修饰的是 `this` 指针，不是并发语义；编译器也无法替你把 `mutable` 缓存变成线程安全的。

这一章从“哪些数据真的被共享”开始，把并发拆成四层：30.1 讲共享的边界和类型该向调用方承诺什么；30.2 讲任务与线程句柄的生命周期，为什么优先 `std::async`、什么时候必须写 `std::launch::async`、`std::thread` 和 `future` 析构时各自会做什么；30.3 用 `promise<void>`/`future<void>` 做一次性事件；30.4 回到最底层的 `std::atomic` 与 `volatile`，并区分函数内 `static` 的“初始化安全”和“访问安全”。异常保证与 `noexcept` 对线程函数的影响放在[第 12 章](ch12.md)，写时复制带来的隐藏共享放在[第 29 章](ch29.md)。

锁的代价和副作用要说清楚。`std::mutex` 不可复制，所以 `Polynomial` 失去了复制能力；EMC-16 接着说“它仍然可以移动”，但 `std::mutex` 本身既没有拷贝构造也没有移动构造，含 `mutex` 成员的类连隐式移动构造也会被删除。上面两个 `static_assert` 在 Clang 21 和 GCC 15 下都成立。想要可移动，只能自己写移动构造函数：锁住源对象、移动数据、让新对象拥有自己的新 mutex；这不是编译器替你生成的东西。`std::atomic` 成员也一样，它既不可复制也不可移动，原书把它们统称为“move-only”并不准确。

如果共享的只是一个计数器，`std::atomic<unsigned>` 通常比 mutex 便宜：`++callCount` 是原子的读-改-写，其他线程不会看到中间值。但原子性只覆盖单个变量。EMC-16 里那个用 `atomic<bool> cacheValid` 和 `atomic<int> cachedValue` 做缓存的例子，两种赋值顺序都不对：先写值再置标志，别的线程可能看到标志为假而重复计算；先置标志再写值，别的线程可能看到标志为真、读到的却是尚未写入的值。两个变量要作为一组一起变，仍然得用 mutex，把它们变回普通成员。这是“锁的粒度由不变式决定”的最小例子。

再往外一层是“要不要共享”。CCS-10 的建议是尽量不共享：命名空间作用域的外部链接对象、类的 static 成员、跨线程共享的数据，都会把一段代码的正确性绑到“谁在什么时候改过它”的历史上，单元测试没法孤立地验证，之后所有使用者都受它影响。全局对象还有初始化顺序问题：不同翻译单元之间的动态初始化顺序未定义，跨线程的初始化更要自己排。C++11 的 `thread_local` 能给每个线程一份独立数据，C++17 的 `inline` 变量让头文件里的全局常量不必再挑一个 `.cpp` 定义，C++20 的 `constinit` 能强制某个全局对象走常量初始化、不参与动态初始化；它们减少了具体的麻烦，但没有改变“共享可变状态越少越好”的结论。`cin`、`cout`、`cerr` 由实现特殊处理，工厂的类型注册表通常全程序一份，但应封装在工厂内部，而不是再摆一个全局对象。

到了必须共享的时候，CCS-12 要求先明确责任划分，再写并发。外部锁由调用方负责序列化，`std::string` 和大多数容器都是这个模式；内部锁让每个成员函数自己加锁，适合生产者/消费者队列这种“对象几乎总被共享、一次调用就是一个完整操作”的类型；无锁或不可变对象则根本不需要锁，每次操作返回新对象。内部锁最容易被误用成“每个函数都加锁就万事大吉”，下面这个队列就是反例：

`size()` 和 `pop()` 各自都加了锁，单次调用都没有数据竞争，但“先看有没有、再取”这个复合操作跨了两次加锁。A 看到 1 单，B 在两次调用之间把订单取走，A 的 `pop()` 只能抛异常。要修，不能靠把锁加得更细，而要把接口做粗：提供一个 `try_pop()` 返回 `std::optional<int>`，或者提供 `pop_if_nonempty()`，让“判断”和“取走”在同一把锁里完成。如果调用方总是需要自己把几个操作拼起来，内部锁就白加了，不如明确改成外部锁。需要多把锁时，所有代码按同一顺序获取（例如按对象地址递增），释放顺序不限，这是避免死锁的基本约定。

标准容器遵循同一套契约，ESTL-12 把它总结为两条：多个线程同时读同一个容器是安全的，不同线程写不同的容器也是安全的；只要有一个线程在写同一个容器，读写都必须由你加锁，而且锁要覆盖整个复合操作。`find` 返回迭代器后锁就释放，另一个线程一插入就可能让迭代器失效，后面的解引用就是悬垂访问；`vector` 扩容会让所有指针、引用、迭代器失效，这种失效会跨线程传播，库无法检测。ESTL-12 写作时标准对线程只字未提，C++11 之后情况变了：标准明确保证不同线程修改不同元素不构成数据竞争（`vector<bool>` 的位打包除外），也提供了 `mutex`、`lock_guard`、`unique_lock`。但“容器不提供事务级线程安全”这个结论没有变，`if (c.empty()) c.push_back(x)` 依然要靠外部锁或更粗的成员函数。

今天的做法可以压缩成几句：默认不共享，共享就写清契约；优先不可变对象和消息传递；必须用可变共享状态时，让锁的粒度与不变式对齐，接口做成一次调用完成一件事；用 `std::scoped_lock`（C++17）一次锁多把锁，用 `std::shared_mutex`（C++17）区分读写，C++20 的 `std::atomic_ref` 可以给已有的非原子对象做原子操作，`std::atomic<std::shared_ptr<T>>` 让“读一个不可变快照”不必再加锁。验证手段是 ThreadSanitizer：本章所有数据竞争示例都用 `-fsanitize=thread` 跑，报告会直接指出冲突的两处访问。

EMC-35 还解释了任务式为什么在资源管理上更省心。硬件线程是真正执行计算的核（或核上的超线程），软件线程由操作系统调度，`std::thread` 只是进程里代表软件线程的句柄。软件线程是有限资源，创建失败会抛 `std::system_error`，即使目标函数声明了 `noexcept` 也一样——`noexcept` 约束的是函数体，不是创建线程这个动作，关于 `noexcept` 的边界见 EMC-14 和[第 12 章](ch12.md)。可运行的软件线程多于硬件线程就是超额订阅（oversubscription），调度器只能靠上下文切换轮转，缓存被反复冲刷；最优比例随负载变化，手工很难调。`std::async` 把这些决定交给标准库实现，实现可以在系统繁忙时把任务推迟到等待结果的线程上执行，从而降低线程耗尽和超额订阅的概率。代价是控制权也交出去了：标准不要求 `std::async` 使用线程池，它本身不是线程池，频繁提交大量任务仍可能每次新建线程。

控制权交出去之后，“到底什么时候执行”就成了问题。EMC-36 的核心是 `std::async` 的启动策略（launch policy）：`std::launch::async` 要求在新线程上异步执行，`std::launch::deferred` 只允许在调用 future 的 `get()`/`wait()` 时由调用线程同步执行；不指定策略时默认是两者按位或，实现可以任选。deferred 的语义可以直接观察：

任务式并发的边界也要说清。`std::async` 适合“提交一个任务、稍后要结果”的场景，不适合需要长期存活的工作线程、需要精细控制优先级或亲和性的场景，也没有提供取消机制；`std::jthread` 的 `stop_token` 是协作取消，目标函数不检查就停不下来。C++20 的 `std::latch`、`std::barrier`、`std::counting_semaphore` 补上了计数和阶段同步，C++26 的 `std::execution`（P2300，sender/receiver）已被采纳，但本书环境的 Clang 21 和 GCC 15 都还不能编译，具体实现进度需核实。今天写新代码，默认从任务式接口开始，确实需要线程时才用 `std::jthread` 或 RAII 包住的 `std::thread`。

## 30.3 用 void future 做一次性事件通知

一个线程负责初始化数据结构或等待传感器就绪，另一个线程要等这件事发生才能继续。最直觉的工具是条件变量（condition variable），但裸用 `condition_variable` 有三个坑：检测方在等待方调用 `wait` 之前就 `notify_one()`，通知会丢失，等待方永远睡下去；`wait` 可能在没有通知的情况下虚假唤醒（spurious wakeup）；为了用条件变量，双方还得共享一个互斥量，哪怕它们根本没有共享数据。标准库因此让 `wait` 接受一个谓词，醒来后先检查条件再决定是否继续等，但等待方往往没有能力判断“事件是否已经发生”——它等的正是这个信息。

退而求其次是用一个 `std::atomic<bool>` 标志轮询：检测方置真，等待方 `while (!flag);`。它没有漏通知，也没有虚假唤醒，但等待期间线程仍然占着硬件线程，反复取标志、反复被调度，不是真正的阻塞。把条件变量和标志组合起来可以既正确又阻塞：检测方在锁内置标志、解锁后 `notify_one()`，等待方用 `wait(lock, [&]{ return flag; })`。问题是通信方式很绕：置标志表示“肯定发生了”，通知只是把对方叫醒去看标志，两套机制缺一不可。

EMC-39 提出的第三条路是把事件本身放进 `std::promise`/`future` 通道。检测方持有 `std::promise<void>`，事件发生时调用 `set_value()`；等待方持有对应的 `std::future<void>` 或 `std::shared_future<void>`，调用 `wait()` 或 `get()`。`void` 表示通道里不传数据，只传“已经发生”这一件事。等待方在 `wait()` 里是真正阻塞的，不占 CPU；检测方先 set 还是等待方先 wait 都无所谓，共享状态会记住；条件变量才有的虚假唤醒也不存在。多个等待者不能共用同一个 `std::future`（它不可复制），要先 `share()` 得到 `std::shared_future`，再按值分发给每个线程：

C++20 之后，一次性事件有了更直接的设施。`std::latch` 是一个单次使用的倒计数器：构造时给计数，`count_down()` 减一，`wait()` 阻塞到计数归零；等待方数量已知、事件只发生一次时，它比 promise/future 更贴近语义。`std::barrier` 可以重复使用，适合分阶段的计算；`std::counting_semaphore` 适合控制并发数量；`std::atomic<T>` 的 `wait()`/`notify_one()`/`notify_all()` 让“等一个原子值变化”不必轮询，也不需要条件变量。今天再写“等一件事发生”，优先在这些原语里选：只需要一个线程等一次，`latch` 最清楚；要传一个值，`promise<T>` 仍然合适；要重复通知，`condition_variable` 配谓词或 `atomic::wait` 更合适。`promise<void>` 没有过时，但它不再是默认答案。

## 30.4 共享数据用 atomic，volatile 不是同步

`volatile` 在 Java 和 C# 里是线程同步工具，在 C++ 里不是。EMC-40 开头就说它“本不该出现在并发这一章”：C++ 的 `volatile` 只告诉编译器“这块内存的读写不能被优化掉”，既不保证原子性，也不建立线程之间的先后关系。两个线程各自对 `counter` 做一次自增，无论 `counter` 是 `int` 还是 `volatile int`，都是读、加一、写回三步；三步之间被另一个线程插进来，就会丢掉一次更新。下面用两个 promise 把交错顺序固定住：两个线程都读到 0，再各自写回 1，结果只加了一次。这段代码没有并发访问，所以不是数据竞争，但足以说明 `volatile` 不提供原子性：

四个线程各加 25000 次，结果是精确的 100000：`++count` 是原子的读-改-写（read-modify-write，RMW），其他线程只可能看到加之前或加之后的值。`std::atomic` 的成员函数默认使用顺序一致性（sequentially consistent，seq_cst），它同时限制编译器重排和硬件可见顺序：在 atomic 写之前发生的操作，不会被移到写之后。第二段利用的正是这一点：`payload` 是普通 `int`，`ready` 用 `memory_order_release` 发布，消费者用 `memory_order_acquire` 读到 `true` 后，`payload = 12345` 一定已经可见。若把 `ready` 换成 `volatile bool`，编译器没有义务把 `payload` 的赋值保留在 `ready = true` 之前，硬件也可能让另一个核先看到 `ready` 变化，消费者就会读到 0。这就是 EMC-40 说的“atomic 限制重排，volatile 不限制”。

内存序不必一上来就用弱的。默认的 seq_cst 最好理解，出错也最少；release/acquire 适合“一个线程准备数据、另一个线程消费”的发布模式；`memory_order_relaxed` 只保证这一个原子变量自身的原子性，不建立其他变量的先后关系，只在计数器、统计量这类不携带其他数据的场景才安全。EMC-40 特别反对在没有测量和形式化推理的情况下使用 relaxed：省下的通常只是很少的指令，换来的是极难复现的错误。C++20 还给 `std::atomic` 加了 `wait()`/`notify_one()`/`notify_all()`，等一个原子值变化不必再写自旋；`std::atomic_ref` 可以对一个已有的非原子对象做原子操作，`std::atomic<std::shared_ptr<T>>` 让“读一个不可变快照”不必加锁。C++17 起 `std::atomic<int> n = 0;` 也合法了（保证复制消除），C++11/14 下同样的写法会编译失败，初始化请用 `n{0}` 或 `n(0)`。

`volatile` 仍然有不可替代的用途：内存映射 I/O 的寄存器、由外部设备或中断修改的内存、需要每次读写都真正发生的特殊内存。普通内存的冗余读可以被合并、死写可以被删除；特殊内存不行，第二次读温度传感器可能读到新值，向电台控制端口先写 10 再写 20 是两条命令，少一条就变了意思。`std::atomic` 不能代替它：标准只保证原子性和顺序，没有给原子访问 `volatile` 那种“每次读写都必须真正发生”的保证；对特殊内存来说，少一次读或多一次写都可能改变设备状态。必要时可以写 `volatile std::atomic<int>`，让访问既原子又不被优化掉。EMC-40 末尾还提到，即使不需要，显式写 `load()`/`store()` 也能提醒读者“这不是普通变量”，并让潜在的扩展性瓶颈更容易被发现。

两个线程同时第一次调用 `fib(50)`，`FibCache` 的构造函数只执行了一次——C++11 起，函数内 `static` 变量的初始化是线程安全的（常被称为 magic statics），编译器会保证只有一个线程执行初始化，其他线程等它完成。但“初始化只做一次”不等于“之后的访问安全”：构造完成后，两个线程再调用 `fib` 并 `push_back`，仍然要自己加锁；示例里的 `std::mutex` 就是干这个的。把锁去掉，两个线程同时 `push_back` 就是数据竞争，`30_1_const_cache_race` 已经演示过 TSan 会当场报出冲突。初始化还有两个边界。第一，初始化只保证“完成一次”，不保证“成功一次”：如果构造函数抛异常，这次初始化算没有完成，下一次调用会重新尝试；示例的 `FibCache` 没有抛，但真实缓存如果要做 I/O 或分配，必须考虑这一点。第二，局部 static 在程序退出时销毁，销毁顺序与它的构造完成顺序相反，如果它持有指向其他全局对象的引用，那个对象可能已经先没了；这类退出期的顺序问题，和 CCS-10 说的全局对象初始化顺序是同一类麻烦。

ESS-02 的教训可以推广成三条。不要返回指向函数内缓存的指针或引用，返回按值拷贝的快照，或者返回 `std::shared_ptr<const T>` 这样的不可变视图；缓存本身的读写要么整体加锁，要么改成不可变对象、每次生成新版本；确实只需要初始化一次时，用 `std::once_flag`/`std::call_once` 或函数内 static，但要把“初始化”和“后续修改”当成两件事分别保护。C++20 的 `constinit` 能让全局或静态对象走常量初始化、避开动态初始化顺序，但它管不了运行期的并发修改。验证这些说法最直接的工具仍是 TSan：本章的 `30_1_const_cache_race` 就在 `-fsanitize=thread` 下当场报出冲突，而不是等到线上出现一个“偶尔算错”的结果。

## 回头看

这四节讲的是同一件事的两面：并发错误几乎都来自“以为没共享”或“以为共享是安全的”。`const` 函数里的缓存、全局注册表、容器的“先查再改”、函数内的 `static`，都把可变状态藏在看起来无害的接口后面；`thread`/`future` 的析构则把生命周期责任藏进句柄的析构函数。EMC-16、EMC-37、EMC-38 看似在讲三条互不相关的规则，实际都在问同一个问题：这份共享状态由谁拥有，谁负责在最后一个使用者离开时让它变得不可访问，以及“等它做完”和“放手不管”哪个才是正确的默认。

C++11 给出了内存模型和最小工具集，C++17/20 补上了 `shared_mutex`、`scoped_lock`、`jthread`、`latch`/`barrier`/`semaphore`、`atomic_ref`、`atomic<shared_ptr>` 和 `atomic` 的等待/通知，C++26 的 `std::execution` 已被采纳但本书环境还不能编译。语言和标准库能保证单个操作的原子性、给出 `happens-before` 的规则、把线程生命周期包进 `jthread`，却不能替你决定共享的边界、锁的粒度和析构的语义。TSan 能抓数据竞争，也能报出锁顺序反转的潜在死锁，但抓不到漏通知、谓词写错和“锁释放后迭代器失效”这类逻辑错误；所以顺序仍然是先设计共享与契约，再选原语，最后用 TSan 和代码评审验证。
