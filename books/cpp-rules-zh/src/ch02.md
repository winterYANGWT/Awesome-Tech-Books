# 第 2 章 让类型替你说话：强类型接口、const 与显式转换

`Date d(30, 3, 1995)` 和 `Date d(3, 40, 1995)` 都能编译。前一个把月和日传反了，后一个给出了不存在的日期。接口长这样：

```cpp
class Date {
public:
    Date(int month, int day, int year);
};
```

编译器看到的只是三个 `int`，没有理由怀疑它们的顺序，也不知道 3 月只有 31 天。问题不在调用方粗心，而在于接口把“月、日、年”这三件不同的事都交给了同一个类型。只要参数类型相同，位置就可以互换；只要值域没有写进类型，非法值就只能在运行期暴露。

这一章沿两条线展开。第一条是**把约定写进类型**：能让编译器拒绝的错误，不要留到运行期；只能运行期检查的，就把检查放进构造函数并维持不变式。第二条是**把转换摆到明面上**：隐式转换会在你没写转换代码的地方替你做决定，`const` 则相反，它把“不许改”的承诺写进接口，让编译器替你守。两条线最后都落到同一个目标上：让正确用法自然，让错误用法编译不过，或者至少不会静默地算出另一个结果。

## 2.1 怎样让正确用法自然、错误用法编译不过

先看两个很容易犯的错。第一类是顺序错误：`Date d(30, 3, 1995)` 想写 1995 年 3 月 30 日，却把 30 放进了 month。第二类是值域错误：`Date d(3, 40, 1995)` 里的 40 不是合法的日。两个调用都符合 `Date(int, int, int)` 的签名，所以编译器没有任何意见。Meyers 在 EC-18 里把这类问题归结为接口设计：假设调用方是善意但会犯错的，接口至少要承担一部分责任；理想情况下，错误的用法根本编译不过，能编译的用法就做调用方期待的事。

EC-19 把这件事说得更彻底：在 C++ 里定义一个 class，就是向类型系统加入一个新类型。动手写之前要先回答一串设计问题——对象怎么创建和销毁，初始化和赋值有什么不同，按值传递意味着什么，哪些值组合合法，要不要进入继承体系，允许哪些转换，哪些运算符有意义，谁可以访问成员，以及这个新类型到底该是 class、class template，还是根本不需要。`Date` 这个例子只碰到其中几项，但已经足够说明问题：合法值、构造方式、转换规则，任何一项没想清楚，接口就会把责任推给调用方。

这条错误的可贵之处在于它指向调用点，而不是等到程序跑出 `1995-02-29` 之后再去猜哪里出了问题。Sutter 与 Alexandrescu 在 CCS-14 里把这条经验说成“能在编译期或链接期发现的错误，不要留到运行期”：静态检查与输入、控制流无关，覆盖所有执行路径，也不付运行期开销；运行期检查则依赖测试样本，你很难证明它覆盖了全部情况。具体到这段代码，`static_assert` 可以证明 `Month` 不会隐式变成 `int`，`enum class` 可以把月份的可选值收窄，模板和 concepts 可以把泛型参数的要求写进签名；而“2 月有没有 29 日”仍然只能在运行期查，因为它取决于年份这个运行时输入。

EC-19 的清单里还有一项在这里特别有用：这个类型允许哪些转换？`Day`、`Year` 的构造函数是 `explicit`，`Month` 是 `enum class`，所以从 `int` 到 `Date` 没有一条隐式路径。反过来说，如果哪天有人为了方便加了一个 `Date(int, int, int)`，前面所有的类型保护就都被绕过了。类型设计不是把包装类写出来就结束，还要守住“只留一条正确入口”这件事。数据成员私有、把不变式留在类内部，是同一件事的另一面，[第 14 章](ch14.md)会展开（EC-22、CCS-41）。

C++11 以后，这类接口有了更多表达手段：`enum class` 管住封闭值集，`static_assert` 把编译期布尔条件写成诊断，`= delete` 可以明确禁止某个转换或重载，`constexpr` 让一部分检查前移到编译期；C++17 的单参数 `static_assert` 让消息更短，`[[nodiscard]]` 能提醒调用方别丢掉工厂函数的返回值；C++20 的 concepts 把模板实参的要求写成可检查的约束。工具方面，`-Wconversion`、`-Wsign-conversion` 能抓住包装类里漏掉的窄化，`-Wswitch-enum` 会提醒 `switch` 漏了某个枚举值。它们都只是补充，真正的第一道防线仍然是类型本身。

## 2.2 指针还是引用：怎么表达“可能没有对象”

第二个常见问题是“这个参数可不可以没有”。比如渲染函数需要一个文档，主题则是可选的：

```cpp
void render(const Document& document, const Theme& theme);   // theme 不能缺
void render(const Document& document, const Theme* theme);   // theme 可以为空
```

第一种写法承诺“调用时一定有一个 theme”，第二种写法把“可能没有”写进了类型。MEC-01 的判据很直接：引用必须绑定到一个对象，而且一经初始化不能改绑，所以只要设计允许“没有对象”，就应该用指针；如果对象一定存在、而且始终是同一个，就用引用。用解引用空指针来制造一个“空引用”是未定义行为（undefined behavior，UB），不能拿它当设计依据。引用也不是完全为了性能：它省掉一次判空，但真正的价值是让接口语义更清楚。

反过来，`operator[]` 这类需要作为赋值目标的运算符通常返回引用，否则调用方得写 `*v[i] = 10`，看起来像在操作指针数组。这里的取舍仍然是契约：返回值一定代表容器里的某个元素，所以用引用；如果“没有这个元素”是正常情况，就不该用 `operator[]`，而应该用 `at()` 抛异常，或者返回 `std::optional`。

表示“空”的时候，C++11 起统一写 `nullptr`。EMC-08 讲得很清楚：`0` 的类型是 `int`，`NULL` 在多数实现里也是某种整型，它们只是“空指针常量”，不是指针；`nullptr` 的类型是 `std::nullptr_t`，可以隐式转换成任意原始指针，但不是整数。这个区别在重载和模板推导里会被放大：

“可能没有值”还有比空指针更合适的表达。C++17 的 `std::optional<T>` 把“有值/无值”做成类型的一部分，调用方要显式检查，不需要约定“这个指针可能是空的”；C++20 的 `std::span` 和 C++17 的 `std::string_view` 则适合“可能为空的范围”，它们不拥有数据，生命周期仍要自己保证。指针仍然适合“可能为空、而且以后会改指”的场景，比如观察者、缓存槽位、链表节点；如果只是“这个参数可以省略”，`std::optional<T>` 往往比 `T*` 更清楚。编译器对空指针只能做有限的数据流分析，`-Wnull-dereference` 之类的警告覆盖不了跨函数的约定，所以接口选型比事后检查更重要。

`Fraction` 提供了 `operator double`，所以 `std::cout << half` 没有找 `Fraction` 的 `operator<<`，而是把 `half` 转成 `double`，打印出 `0.5`。如果本意是打印 `1/2`，这个结果不算崩溃，却已经完全不是调用方想要的东西。`Buffer` 的问题更隐蔽：`a == b[3]` 漏写了一个下标，正常应该报错，但 `b[3]` 是 `int`，而 `Buffer(std::size_t)` 不是 `explicit`，编译器就用它造了一个临时的 `Buffer(3)`，然后拿 `a` 和一个“3 个 0 的 Buffer”比较。程序输出 `false`，看起来像“两个缓冲区不相等”，实际上比较的对象根本不是 `b` 的元素。

Meyers 在 MEC-05 里把这两类函数放在一起讲：单参构造函数和转换运算符都能让编译器在你没要求的地方插入转换。他的建议很直接——需要转换就提供具名函数，比如 `asDouble()`、`c_str()`，把“要转换”的义务放回调用点；单参构造函数默认加 `explicit`。Sutter 与 Alexandrescu 在 CCS-40 里把这条建议写成默认规则：隐式转换默认关掉，需要转换就写成显式的；一次转换序列最多允许一个用户定义转换，再叠加内置转换之后，重载决议的结果往往连作者都推不出来。Sutter 在 EXC-39 里用 `std::string` 举例：标准库故意不提供到 `const char*` 的隐式转换，否则 `s1 = s2 - s3` 这种明显写错的表达式会先把两个 string 转成指针再相减，代码“干净地”编译，行为却是 UB。

C++11 把 `explicit` 扩展到了转换运算符，`explicit operator bool` 是最常见的用法；C++20 的 `explicit(bool)` 让“满足条件才显式”可以用常量表达式控制，泛型包装类因此不必为两种情形各写一个构造函数。`= delete` 可以直接删掉不想要的转换或重载，`nullptr` 则消除了 `NULL`/`0` 在重载里的整型歧义（上一节）。需要特别注意，`std::string_view` 从 `std::string` 的隐式构造是有意保留的轻量设计，但它不拥有数据，悬垂风险和“隐式转换都安全”是两回事；`std::span` 也一样。

工具方面，`-Wconversion` 只能抓住内置数值类型之间的窄化，抓不住用户定义的转换；clang-tidy 21 的 `google-explicit-constructor` 会同时指出“单参构造函数应加 explicit”和“转换运算符应加 explicit”，拿它扫一遍老代码通常能翻出一批隐患。真正要养成习惯的是：每次写单参构造函数或转换运算符，都先问一句“我愿意让编译器在哪些地方自动调用它”；答不上来就加 `explicit`，需要时再提供具名函数。

## 2.4 explicit 该加在哪：看它决定结构还是值

“单参构造函数一律加 explicit”是一个安全的默认，但它没有回答“为什么”。ACC-22 给了一个更细的判据：看实参是否成为对象值的一部分。只决定结构或尺寸的构造函数应该显式，决定内容的可以保留隐式。比如 `std::vector<T>(n)` 只说明要几个元素，不说明元素是什么；`std::string(const char*)` 的实参本身就是字符串的值。前者如果允许隐式转换，`frame(42)` 会得到一个 42 行的空图片，几乎肯定是误用；后者允许 `const char*` 隐式变成 `std::string`，调用代码才自然。

判据不是参数个数，这一点值得重复。一个构造函数可以有两个参数、其中一个有默认值，因而仍然能当单参构造函数用；反过来，一个多参构造函数也可能只决定结构。判断标准始终是“这些实参是在描述对象长什么样，还是在提供对象的内容”。

`explicit` 只能关掉一条转换路径，关不掉重载决议里的所有歧义。《Thinking in C++》提醒过转换扇出的问题（TIC-22）：一个类型同时提供到多个类型的转换，平时可能没事，直到有人新增一个重载：


`Apple` 既能转成 `Orange`，也能转成 `Pear`，`eat(a)` 于是有两个同样好的候选。双向转换更糟：`A` 有 `operator B()`，`B` 又有 `B(const A&)`，从 `A` 到 `B` 就有两条路，编译器只能报二义。`explicit` 能关掉其中一条，但如果另一条还在，调用点仍然可能选到你不想要的那个。TIC-22 的建议是只保留一条自动转换路径，其他转换写成 `to_orange()`、`make_pear()` 这样的具名函数；C++11 的 `explicit` 转换运算符和 C++20 的 concepts 让约束更清楚，但重载决议的二义性规则没有变，`<=>` 也不解决用户定义转换的歧义。

`const char*` 是另一条特别容易惹祸的转换路径。《Thinking in C++》用 `operator const char*` 让自定义字符串直接调用 C 函数（TIC-23），今天看这个技巧代价太大：任何接受 `const char*` 的函数都能悄悄接收这个类型，临时对象转出来的指针在完整表达式结束后就悬垂，隐式转换还会参与指针比较和 `bool` 转换。需要 C 字符串就提供具名的 `c_str()`，需要只读字符范围就用 C++17 的 `std::string_view`；如果必须保留转换运算符，至少标 `explicit`（C++11 起支持），并保证返回的缓冲区生命周期不短于对象。

今天写新类型，可以按这个顺序决策：先问“这个构造函数是在给值还是给结构”，给结构就 `explicit`；再问“这个转换是否需要在调用点自动发生”，不需要就写成具名函数；最后检查“是否存在第二条自动路径”，有就删掉或改成显式。clang-tidy 的 `google-explicit-constructor` 能帮你发现漏掉的 `explicit`，但它不会替你判断“值 vs 结构”，那仍然是设计问题。

## 2.5 用 enum class 和值域把类型管住

## 2.6 const 是接口契约，不是优化提示

很多人第一次听到“const 不是为了优化”会有点意外。`const` 确实可能让编译器把对象放进只读段，但那是很窄的情形；它的主要作用是表达接口契约，让编译器替你检查“这个对象、这个参数、这个成员函数不应该改”。EC-03 把 `const` 的各种位置摊开：对象、参数、返回值、成员函数，以及 `const T*`、`T* const`、`const T* const` 的区别；编译器执行的是 bitwise const（位级 const），而设计时应该按 logical const（逻辑 const）思考——缓存、计数这类不影响可观察状态的成员，用 `mutable` 标明。

`total()` 是 const 成员函数，因为它不改变可观察状态；它内部会更新 `cached_` 和 `dirty_`，所以这两个成员是 `mutable`。`name()` 提供了 const 和非 const 两个重载，const 对象拿到 `const std::string&`，非 const 对象拿到可修改的引用；两个 `static_assert` 把返回类型固定下来。这里没有 `const_cast`，也不需要为了“优化”把什么东西搬进只读内存。

CCS-15 补充了几个容易忽略的点：`const` 不是深 const，`const` 对象里类型为 `X*` 的成员变成的是“指针本身 const”，它所指的 `X` 并不是 const；按值传参的顶层 `const` 在函数声明里会被忽略，`void f(int)` 和 `void f(const int)` 是同一个函数，但在定义处保留 `const` 可以抓住意外的自增；`const` 会传染，给旧代码补 const 很费工，却常常能翻出潜伏的 bug。EXC-43 把“该加的地方加，不该加的地方别乱加”讲得更细：不修改可观察状态的成员函数都该 const；`const_cast` 掉一个真正 const 对象的 const 再写入是 UB（四种 cast 的分工和 `const_cast` 的边界在[第 3 章](ch03.md)展开，EXC-44）；按值返回内建类型加 const 没有意义。它建议“按值返回非内建类型时返回 const 值”，这一条在今天已经过时。

`make_const()` 返回 `const Tracer`，`v.push_back(make_const())` 只能走 `const T&` 重载，拷贝一次；`make_plain()` 返回 `Tracer`，走 `T&&` 重载，移动一次。移动构造为什么通常标 `noexcept`、`vector` 扩容如何在移动和拷贝之间选择，[第 12 章](ch12.md)会接着讲（EXS-13）。C++17 的保证复制消除（guaranteed copy elision）让 `return Tracer{}` 不再产生额外的拷贝/移动，但它不改变“把纯右值传给 `push_back` 时选哪个重载”。所以现代写法是返回 `T`，不是 `const T`；EXC-43 和 EC-03 的这一部分要按 C++11 之后重读。clang-tidy 21 的 `readability-const-return-type` 会直接指出 `const Tracer make_const()`；`-Wignored-qualifiers` 只覆盖 `const int` 这类标量返回类型，管不到类类型。

EXS-24 把“const 首先约束人，其次才可能优化代码”讲得最透。对 `const X&` 参数和 `const Y&` 返回值谈优化是找错了地方：它们本来就不复制，而且被引用对象的真正定义在函数之外，编译器既不能把它搬进只读内存，也不能假定它的位不变——`mutable` 成员、成员函数里的 `const_cast`、可能别名同一对象的非 const 引用，都让“声明了 const 就等于位级 const”不成立。按值传 `const Z z` 只在很窄的条件下可能省掉拷贝，而且那通常是 as-if 规则下的编译器优化，不是 const 的功劳；更现实的做法是直接写 `const Z&`。唯一可靠的“ROM-able”情形，是对象在定义点就是 const，尤其是内存映像可以在编译期生成的 POD。今天表达“编译期常量”有更正当的工具：C++11 的 `constexpr`、C++20 的 `consteval`（强制编译期求值）和 `constinit`（只保证静态初始化），它们的区别在[第 22 章](ch22.md)展开（EMC-15）。

const 也不等于线程安全。一个 const 成员函数可以改 `mutable` 缓存，如果多个线程同时调用，缓存本身仍然要加锁或用原子操作；const 只承诺“不改变可观察状态”，不承诺“内部没有写操作”。这也是为什么把 const 当成优化提示会失望：优化器看到的 const 比你想象的少，而人看到的契约比你想象的多。

## 2.7 基本类型的坑：float 精度与 bool 的内建性

主流平台的 `float` 有 24 位二进制精度，能精确表示全部整数的范围到 2^24；1e8 本身恰好可表示，但它附近相邻两个 float 的间隔（ulp）是 8，所以 `x - 1.0f` 会被舍回 `x`，循环永远停在 1e8。`double` 在这个量级上的间隔远小于 1，所以每个整数都还装得下，`d - 1.0 != d`。标准只保证 `double` 的精度不低于 `float`、`float` 的值集合是 `double` 的子集，并没有保证 float 更快；为了“省一点内存”把 double 降成 float，先要确认业务范围装得下。

第二个坑是 bool。EXC-45 问了一个很好的设计问题：既然可以 `typedef int bool`、`#define bool int`、`enum bool { false, true }` 或 `class bool`，为什么还要内建 bool？答案是这四种模拟都至少有一项做不到。`typedef int bool` 不能让 `f(int)` 和 `f(bool)` 成为不同重载；`#define` 更糟，宏不认作用域，会把客户代码里叫 `false` 的变量一起改掉；`enum bool` 允许重载，但 `b = (i == j)` 不能把 `int` 隐式转成枚举；`class bool` 允许重载，但如果不提供到 `int`/`void*` 的转换，`if (b)` 就不能写，提供了又会干扰重载决议——两难。

float 和 bool 放在一起，是因为它们都提醒我们：基本类型的语义是语言和实现共同规定的，不要凭直觉假设。float 的精度、窄化规则、比较是否可靠，bool 的重载、隐式转换、条件测试，都是设计类型时要先查清楚的事。

## 回头看

这些规则合起来，防的是同一类事故：程序编译通过、运行不崩，却做了另一件事。强类型把参数顺序和值域写进签名，`enum class` 把封闭值集关进作用域，`nullptr` 和引用/指针的分工把“可能没有”摆到接口上，`explicit` 和具名转换函数把转换的义务还给调用点，`const` 把“不许改”的承诺交给编译器，值域检查和 float 精度则提醒我们哪些事只能在运行期或按业务上限处理。它们的共同点是：先让错误难以表达，再谈检查和测试。

C++11 以后，语言替我们兜住了其中很大一部分：`enum class`、`nullptr`、`explicit operator bool`、`static_assert`、`constexpr`、`= delete`；C++17 又加了 `[[nodiscard]]`、`std::optional`、`std::string_view`、`std::as_const`；C++20 的 `explicit(bool)`、concepts、`consteval`/`constinit`、`std::span` 把约束和求值语境写得更细；C++23 的 `std::expected`、`std::to_underlying` 继续补工具。但语言管不到“这个转换该不该自动发生”“这个参数该不该是引用”“这个上限该定在哪里”，这些仍然是设计决定。工具能帮的是执行决定：`-Wconversion`、`-Wsign-conversion`、`-Wswitch-enum`、`-fsanitize=undefined`，以及 clang-tidy 的 `google-explicit-constructor`、`readability-const-return-type`。把警告当错误、把 sanitizer 放进 CI，剩下的才是人该判断的部分。
