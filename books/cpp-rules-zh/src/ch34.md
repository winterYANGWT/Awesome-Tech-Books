# 第 34 章 从 #include 到 modules

一个老库的头文件里写着 `#define min(a, b) ((a) < (b) ? (a) : (b))`，另一个库的头文件里恰好有一个 `min` 函数模板：

```cpp
#define min(a, b) ((a) < (b) ? (a) : (b))

template <class T>
const T& min(const T& a, const T& b);   // 预处理后，函数名被宏替换成了表达式
```

先包含哪个头文件、中间有没有 `#undef`，决定了这段代码能不能编译。问题不在宏写得粗心，而在 `#include` 的本质：预处理器把被包含文件的记号原样倒进当前翻译单元（translation unit），两个库的宏、类型名和重载集从此共享同一个平面。头文件被这样文本包含了几十年，C++20 的 modules 想改变的正是这个平面：让一个模块的接口先独立编译，导入方只看见 `export` 出去的名字。但 modules 没有把模板实例化、对象布局和 ABI 的旧账一笔勾销。要判断 modules 值不值得用，得先弄清楚 `export` 曾经承诺过什么、又为什么失败。

## 34.1 export 的历史：只隐藏依赖，不等于分离编译

`export` 在 C++ 里出现过两次，含义完全不同。第一次是 C++98 的“导出模板”：只要在头文件里写 `export template<typename T> void f(T);`，模板定义就可以放进 `.cpp`，调用方只看见声明。Sutter 在 EXS-09 里解释了它为什么没有兑现这个承诺。普通函数的分离编译能成立，是因为调用方只需要签名，函数体可以提前编译成目标代码；模板不行，`f<int>` 和 `f<double>` 是两份不同的代码，而要用哪些类型，直到使用点才知道。导出模板至多做到“分离解析、部分编译”，每个实例化点仍然要把完整定义编译一遍。

EXS-09 把两种源码组织方式分成包含模型（inclusion model）和分离模型（separation model），并强调它们只是**源码怎么摆**的区别，不是实例化模型的区别。包含模型要求定义对使用点可见，效果等同于把实现放进头文件；分离模型只把定义从调用方的视野里移走。编译器实例化时仍要读定义，因为依赖名（dependent name）要在定义上下文和实例化点两处查找。C++03 的依赖名解析规则（[temp.dep.res]）说的是，依赖名的查找同时考虑模板定义上下文和实例化点上下文。定义上下文不只是模板那几行，还包括定义所在文件里在它之前出现的重载和声明。所以库作者可以把 `.cpp` 藏起来不给用户看，编译器却必须能看到它；源码保护没有实现，改模板体之后每个实例化它的翻译单元仍要重新编译，构建加速也没有实现。EXS-09 的结论很短：`export` 只隐藏依赖，不消除依赖。

EXS-10 接着讲这个设计怎样把语言的其他部分搅乱。导出模板用到的未命名命名空间或文件级 `static` 函数，本来只属于一个翻译单元，现在必须像 `extern` 一样被其他翻译单元调用，还可能和任意多个源文件里的同名函数一起参与重载；名字查找要同时面对多个翻译单元的符号表，类在不同翻译单元里的友元声明还可能引出新的二义和 ODR 违规。Sutter 给出的操作性建议是“可移植代码不要用 `export`”，即使手里有当时唯一支持它的 Comeau 编译器，也最好让别人先试。历史也说明了代价：`export` 1996 年进入草案，2002 年才有第一个实现，EDG 说它一个特性花掉的人年相当于其他三个主要语言特性。

这段历史在今天还能看到痕迹。C++11 删除了导出模板，`export` 关键字被保留下来；C++20 又把它重新用作模块的 `export`。但“删除”不等于所有编译器都立刻报错。下面这个程序用 `-std=c++17` 编译：

```cpp
{{#include code/ch34/34_1_export_template.cpp}}
```

clang 的诊断：

```text
{{#include code/ch34/34_1_export_template.out}}
```

Clang 21 只给一句 `exported templates are unsupported`，然后把 `export` 忽略掉，程序仍按普通模板编译；GCC 15 也只警告 `keyword 'export' is deprecated, and is ignored`。换到 `-std=c++20`，Clang 21 会报 `export declaration can only be used within a module purview`，因为此时 `export` 已经是模块声明的一部分；GCC 15 仍然只警告 `keyword 'export' is enabled with '-fmodules'` 并接受。两个编译器对这段历史语法的处理并不一致，这也说明它不能再当作可依赖的分离编译机制。

导出模板消失后，“让模板代码只编译一次”的需求并没有消失，今天能用的办法是显式实例化（explicit instantiation），而且只对**列出来的类型**有效。下面的例子把普通函数和函数模板放在一起：`base_rate` 的声明在头文件、定义在 `.cpp`，这是普通函数的分离编译；`clamp_charge` 也是声明在头文件、定义在 `.cpp`，但 `.cpp` 里多了一行 `template int clamp_charge<int>(int);`，头文件里用 `extern template` 告诉调用方“int 版不要在这里实例化”。


```cpp

```


`quote.o` 里有 `clamp_charge<int>` 的定义，没有 `clamp_charge<double>`；`main.o` 对 int 版的引用是未定义符号 `U`，链接时由 `quote.o` 补上。这正是普通函数分离编译的效果：调用方不需要看见模板体，改模板体只要重编 `quote.cpp` 再链接。代价是实例化的编译工作从每个调用方搬到了库这一侧，库要维护一张“支持哪些类型”的清单；清单外的类型只能在调用方重新编译模板定义，或者由库作者追加一行再发布新版本。它只覆盖 `int`。`main_other.cpp` 调用 `clamp_charge(120.0)`，编译器在头文件里看不到定义，只能留下一个对 `clamp_charge<double>` 的未定义引用，链接器找不到就报错。要让 double 也能用，库作者必须在 `.cpp` 里再加一行显式实例化，重新编译库；用户自己定义的新类型通常没法由库提前列进这张清单。这就是 EXS-09 说的“分离编译”与模板的真实距离：能分离的是**已知类型的那几份代码**，不是模板的定义本身。

```cpp

```

输出：

```text
{{#include code/ch34/34_1_two_phase_lookup.out}}
```

同一个 `units_of` 模板，对 `warehouse::Crate` 找到 `warehouse::describe`，对 `depot::Pallet` 找到 `depot::describe`，结果分别是 7 和 70。模板定义本身没有变，变的只是实例化点的上下文。包含模型下这个上下文是调用方所在的翻译单元；导出模板想让定义待在另一个翻译单元里，却仍要把那边的声明和重载一起拉进查找，EXS-10 说的“多个符号表同时在场”就是这么来的。C++20 模块把模板定义放进 BMI，导入方实例化时用的仍是模块接口里的定义上下文，查找规则没有变成“只看调用方”。

所以今天的做法很清楚：不要写 `export template`；需要把模板代码从调用方移走时，用显式实例化覆盖少数固定类型，并用 `extern template` 避免调用方重复实例化；需要真正的接口边界时，用下一节的模块，而不要把模块当成“模板版的普通函数”。`export` 的教训也不是“分离编译不可能”，而是“只移走声明、不移走实例化所需的信息”换不来分离编译。第 33 章讲的 Pimpl 和前置声明解决的是另一件事——减少头文件里的完整类型依赖；它们同样不改变模板实例化的位置。

## 34.2 模块用 export 和 import 划出接口边界

头文件的问题是它没有“只给你看这些”的机制：`#include <string>` 会把 `<string>` 里所有在那个时候可见的名字、宏和 `using` 声明都带进来，至于哪些是给你用的，只能靠命名约定和文档。模块把这条边界写进语言：一个模块接口单元用 `export module 名字;` 声明自己，用 `export` 标出哪些声明属于接口，导入方用 `import 名字;` 消费，其余名字留在模块内部。下面是一个很小的几何模块：

```cpp
{{#include code/ch34/34_2_module_boundary/geometry.cppm}}
```

`detail` 没有 `export`，`pi` 和 `square` 只供模块自己使用；`geo` 命名空间整体被 `export`，所以 `circle_area`、`max_sides`、`Circle` 和 `area` 对导入方可见。导入方这样写：

```cpp
{{#include code/ch34/34_2_module_boundary/main.cpp}}
```

输出：

```text
{{#include code/ch34/34_2_module_boundary/output.out}}
```

这里有一个容易踩的误会：`import geometry;` 不会把导出的名字包进 `geometry::`。模块名只是模块的名字，`circle_area` 仍在 `geo` 命名空间里，所以调用写 `geo::circle_area`，而不是 `geometry::circle_area`。把模块名和命名空间当成同一层，是刚接触模块时最常见的错误之一。

`export` 可以逐条加在声明前面，也可以像 `export namespace geo { ... }` 这样整块导出；C++20 还允许 `export { ... }` 把一段声明一起导出。没有 `export` 的名字不是“private 成员”那种访问控制，而是根本不在导入方可见的名字集合里。下面的反例试图从导入方调用 `detail` 里的 `square`：

```cpp
{{#include code/ch34/34_2_module_boundary/hidden.cpp}}
```

脚本把这次编译的失败信息也记在同一份输出里。接着看宏的边界。`main.cpp` 在 `import geometry;` 之前写了 `#define square(x) 0`，如果模块还是头文件，这个宏会把 `geometry.cppm` 里的 `square` 定义改得面目全非；但模块接口在导入之前就已经独立编译成 BMI，导入方这边的宏碰不到它，所以 `circle_area` 仍算出 12.5664。反方向也一样：`geometry.cppm` 里的 `GEOMETRY_INTERNAL_LIMIT` 不会出现在导入方的预处理环境里，`macro.cpp` 的 `#ifdef` 因此不成立。Sutter 在 EXS-10 里把“宏不跨翻译单元泄漏”列为 `export` 的一个真实优点，只是当年的 `export` 模板没有推广开；C++20 模块把这一点做成了常规行为。

这也是模块和头文件最实在的差别。头文件的接口是“文本上恰好可见的东西”，模块的接口是编译器从 BMI 里读出的导出集合；头文件需要包含守卫来防止重复展开，模块接口不需要；头文件里的 `inline` 函数要在每个包含它的翻译单元里定义，模块接口里的函数体只在接口编译时解析和检查一次（`inline` 函数仍可能被导入方内联展开）。第 33 章讲的“每个头文件都要能独立编译”在模块接口上仍然成立，只是检查方式从“单独 `#include` 一次”变成了“单独编译这个 `.cppm`”。

模块接口单元和模块实现单元要分清。接口单元以 `export module 名字;` 开头，它决定导入方能看到什么；实现单元以 `module 名字;` 开头，可以定义接口里声明的函数，但不能 `export`，它的内容不进入 BMI。一个模块可以有多个实现单元，也可以有多个分区；导入方永远只面对接口。这个划分让“接口变更”和“实现变更”有了不同的重建范围，34.3 会用构建顺序把这一点摊开。

原书讨论 `export` 时的核心问题是“依赖有没有消失”。模块这边要分清楚：接口里 `#include` 的头文件仍然会进入模块接口的编译，模块内部用的类型仍然要完整；被隐藏的只是导入方按名字访问的能力和宏的传播。换句话说，`export` 划出的是**名字可见性**的边界，不是“实现代码不存在于构建过程中”的边界。模块接口里没有导出的函数仍然要编译，只是导入方看不见它的名字。

今天的做法是把模块接口当成真正的 API 清单：只 `export` 用户需要调用的函数、类型和常量，辅助函数放进不导出的 `detail` 命名空间；不要把整个实现命名空间一股脑 `export` 出去，也不要在接口里放只给实现用的宏。导入方的宏仍然作用于它自己的代码，不要用宏去碰导出的名字；模块接口那一侧则完全不受这些宏影响。Clang 21 用 `-std=c++20` 就能编译上面这个例子，GCC 15 则要加 `-fmodules`（GCC 15 起的正式名字，旧名 `-fmodules-ts` 仍可用）；本机实测这个简单模块在 GCC 15 下也能编译、导入和运行，更复杂的模块特性成熟度需核实。

## 34.3 BMI 和模块分区把负担推给构建系统

头文件的构建模型很简单：源文件依赖头文件，改了就重编。模块多出一个中间产物：编译器把模块接口单元编译成二进制模块接口（binary module interface，BMI），导入方读 BMI，而不是重新解析 `.cppm` 的文本。Clang 把 BMI 叫 `.pcm`，用 `--precompile` 生成；GCC 把它放进 `gcm.cache`，扩展名是 `.gcm`。这个文件不是源码，也不是可以随便拷贝的库：它是编译器自己的序列化格式，Clang 的 `.pcm` 不能喂给 GCC，标准也没有规定它的格式。构建系统必须先算出“谁依赖谁的 BMI”，再按顺序编译。

先看没有 BMI 时会发生什么。把导入 `shop` 的 `main.cpp` 直接交给编译器：

```cpp
{{#include code/ch34/34_3_missing_bmi.cpp}}
```

clang 的诊断：

```text
{{#include code/ch34/34_3_missing_bmi.out}}
```

编译器不会去目录里找 `shop.cppm` 再替你编译；`import shop;` 要求构建系统通过 `-fmodule-file=shop=...` 或等价参数告诉它 BMI 在哪里。头文件时代，`#include "shop.h"` 自己就能找到文件；模块时代，这个“自己找”的能力没有了，构建脚本必须显式描述依赖。这正是模块把负担推给构建系统的地方。

模块分区（partition）用来把一个大接口拆小。下面的 `shop` 有两个分区，分别算小计和税：

```cpp

```

```cpp

```

主接口只负责重新导出：

```cpp

```

分区名写成 `模块名:分区名`，`export import :pricing;` 表示把 `:pricing` 的导出集合再导出给 `shop` 的导入方；如果只写 `import :pricing;`，分区里的名字只在 `shop` 内部可用，不会传给导入方。每个分区可以单独编译成 BMI，互不依赖的分区还能并行构建。脚本按“分区 → 主接口 → 导入方”的顺序构建并运行：

例子还用了模块实现单元：`shop.cppm` 只声明 `packaging_fee`，函数体放在 `shop_impl.cpp` 的 `module shop;` 里。

```cpp
{{#include code/ch34/34_3_partitions/shop_impl.cpp}}
```

实现单元不是接口单元，函数体不进入 BMI，导入方只从 BMI 拿到声明，链接时再由实现单元的目标文件补上符号。这样一来，改 `packaging_fee` 的函数体只要重编 `shop_impl.cpp` 再链接，导入方不必重编；只有改接口单元（声明、类定义、接口里的 `inline` 函数体，或它包含的头文件和宏）才需要重建 BMI、重编导入方。这是模块相对头文件最接近“普通函数分离编译”的地方。模板不享受这个待遇：模板定义若放在接口里，导入方实例化时仍要读定义；若藏在实现单元，就只有显式实例化的类型能用。这一点下一节用例子说明。

构建顺序也解释了为什么模块接口不能“随手放几个 `.cppm` 就算了”。`shop.cppm` 编译时需要 `:pricing` 和 `:tax` 的 BMI，导入方编译时需要 `shop` 的 BMI；如果构建系统只看到 `.cpp` 和 `.h`，它不知道这些新文件类型，也不知道 `-fmodule-file` 参数该传给谁。今天的 CMake、Ninja 等工具已经在补这块支持，但具体版本和生成器对模块的覆盖程度需核实；手工写 `example.sh` 时，顺序就是上面这几行，错一步就报 `module 'shop' not found`。

编译器支持方面，Clang 21 用 `-std=c++20` 就能走完上面的流程，不需要额外开关；GCC 15 要加 `-fmodules`（旧名 `-fmodules-ts`），本机实测简单模块可以编译、导入、运行，但复杂项目里的分区、实现单元和增量构建成熟度需核实。MSVC 不在本书环境里，支持情况需核实。BMI 是本地构建产物，不要提交到仓库，也不要指望在一台机器上生成后拿到另一台机器或另一个编译器上复用。

## 34.4 模块解决了什么、没解决什么

模块最先解决的是重复解析。头文件在每个包含它的翻译单元里被预处理器展开、被编译器重新解析一遍，标准库那些几千行的头文件也不例外；模块接口只编译一次，导入方读 BMI。它同时解决了宏和名字的泄漏：上一节的 `square` 宏进不了模块，模块内部的 `detail` 也进不了导入方。对于大型项目，这两点合起来能减少大量重复工作，也让“这个翻译单元里到底有哪些名字”变得可枚举。

但模块没有让模板变成普通函数。下面这个模块导出 `discounted` 的声明，把定义和显式实例化留在实现单元：

```cpp
{{#include code/ch34/34_4_template_dependency/catalog.cppm}}
```

```cpp
{{#include code/ch34/34_4_template_dependency/catalog.cpp}}
```

导入方可以调用 `int` 和 `double` 版，因为实现单元为这两个类型生成了代码；换一个没有显式实例化的类型，链接就失败：

```cpp
{{#include code/ch34/34_4_template_dependency/main.cpp}}
```

```text
{{#include code/ch34/34_4_template_dependency/output.out}}
```

这和 34.1 的 `extern template` 是同一个结构，只是把 `.cpp` 换成了模块实现单元。模块并没有“提前知道用户会用哪些类型”的能力；模板定义要么随 BMI 交给导入方，让它在导入方实例化，要么留在实现单元，只覆盖作者列出的类型。EXS-09 说的“依赖只是被隐藏，没有消失”，在模块时代仍然成立，只是隐藏的方式从“头文件里的定义”变成了“BMI 里的定义或实现单元里的显式实例化”。

模块也不改变对象布局。例子里的 `static_assert(sizeof(store::Item) == sizeof(int))` 成立，因为 `Item` 仍然是一个普通的 `int` 成员结构体；模块改变的是名字怎么被找到、接口怎么被编译，不是类的布局规则。给 `Item` 加一个成员或改它的布局，接口里的类定义就变，BMI 要重建，导入方仍要重编；想把表示藏起来，仍然要用 Pimpl 或“接口类 + 工厂”，见[第 33 章](ch33.md)。模块不是 Pimpl 的替代品，它只是让“接口里有哪些名字”更清楚。

再往外是 ABI。模块没有规定跨编译器的二进制接口：BMI 是编译器私有的，类的布局、名字改编、异常和 RTTI 的实现仍由各家 ABI 决定。Clang 和 GCC 编出的模块目标文件不能随意互相链接，跨 DLL 或跨编译器传递 `std::string` 仍然危险；这些是[第 35 章](ch35.md)的话题。模块能让一个项目内部的边界更干净，但不能替代 `extern "C"`、稳定的 C ABI 或经过设计的跨边界类型。

C++23 的 `import std;` 把标准库本身也做成了一个模块。它省掉每个翻译单元重复包含和解析标准库头文件的工作，写法也短：

```cpp
{{#include code/ch34/34_4_import_std/app.cpp}}
```

输出：

```text
{{#include code/ch34/34_4_import_std/output.out}}
```

这个例子的构建方式和普通模块一样：先预编译标准库的 `std.cppm` 得到 `std.pcm`，再用 `-fmodule-file=std=...` 编译导入方。本机是 Clang 21 + libc++ 21，需要 `-std=c++23` 和 libc++。GCC 15 走的是同样的两步，只是标准库模块的源文件在 libstdc++ 里：先 `g++ -std=c++23 -fmodules -fsearch-include-path -c bits/std.cc` 生成 `gcm.cache/std.gcm` 和对应的目标文件，再用 `-fmodules` 编译导入方并链接那个目标文件（本机实测可以运行）；跳过第一步直接 `import std;`，就会报找不到 `std.gcm`。`import std;` 不是“标准库变快了”，它只是把标准库也纳入了同一套模块构建流程，代价是构建系统多了一个必须先产出的 `std.pcm`。

`import std;` 还有一个容易忽略的约束：`std.pcm` 必须由同一套编译器、同一套标准库和兼容的编译选项生成。用 libc++ 预编译的 `std.pcm` 不能拿去配 libstdc++ 的目标文件，换 `-std=`、`-D` 或 ABI 相关选项也可能让 BMI 失效。它省掉的是重复解析，不是把标准库变成与工具链无关的二进制包；构建系统仍要记录“这个 BMI 是用哪条命令生成的”。

所以模块的账要分开算：省下的是头文件的重复解析、宏污染和名字泄漏；没有省下的是模板实例化、对象布局、ABI 和链接依赖。把这两类问题混在一起，就会得到“用了模块就不用管头文件了”或者“模块能替代 Pimpl”这类错误期待。

## 34.5 迁移要允许头文件和模块长期并存

一个几十万行的项目不可能因为 C++20 有了模块，就停下来把所有头文件改成 `.cppm`。现实的做法是让两种组织方式在同一个程序里共存：旧代码继续 `#include`，新代码 `import`，模块接口在边界上包住旧头文件。下面的例子只有几个文件，却包含两条完整的构建路径。旧头文件不变：

```cpp
{{#include code/ch34/34_5_mixed_build/legacy_pricing.h}}
```

模块接口用全局模块片段（global module fragment）包含它：

```cpp
{{#include code/ch34/34_5_mixed_build/pricing.cppm}}
```

`module;` 开始的部分是全局模块片段，里面的 `#include` 仍然按文本包含处理，`legacy::list_price` 的声明因此进入模块接口的编译；`export module pricing;` 之后才是模块自己的声明。新客户端导入模块：

```cpp
{{#include code/ch34/34_5_mixed_build/new_client.cpp}}
```

旧客户端完全不知道模块存在，继续包含头文件、和 `legacy_pricing.cpp` 一起编译：

```cpp
{{#include code/ch34/34_5_mixed_build/old_client.cpp}}
```

脚本把两条路径都编译并运行：

```text
{{#include code/ch34/34_5_mixed_build/output.out}}
```

两个客户端输出不同，是因为它们问的是不同的问题：新客户端问“7 号商品买 3 件多少钱”，旧客户端只问单价。构建上它们是两个独立的可执行文件，旧客户端那条命令没有出现任何模块参数，这说明模块没有强迫旧代码改变。

全局模块片段是迁移时最常用的接口。它让模块作者继续使用现成的头文件、C 库和第三方库，而不必先等这些库提供模块版本。代价是这些头文件的宏会留在模块接口的翻译单元里，可能影响后面的模块代码；如果旧头文件里有 `min`/`max` 这类宏，包含之后要按需 `#undef`，或者把包含范围缩到最小。同一个头文件不要在模块里又 `#include` 又 `import`，那会让它的声明以两种身份进入同一个翻译单元，ODR 和宏状态都更难说清。

C++20 还提供头文件单元（header unit），可以写 `import "legacy_pricing.h";` 把旧头文件也变成可导入的 BMI；它需要编译器额外支持，构建方式与普通模块不同，本书环境没有用它，具体可用性需核实。头文件单元适合“这个头文件以后不再改、也不想每次重新解析”的场景；如果头文件还要被 C 代码包含，或者里面有大量条件编译，留在全局模块片段里通常更稳。

迁移的顺序比工具更重要。先把新写的、边界稳定的库做成模块接口，让新代码 `import`；旧代码和 C 互操作继续走头文件。等构建系统能稳定处理 BMI、IDE 能正确索引模块、团队对 `export` 的边界有共识之后，再考虑把热点库迁过去。不要为了“统一”把每个 `.h` 都改成 `.cppm`：一个只被旧代码包含、或者要给 C 编译器看的头文件，留在头文件世界更省事。模块和头文件不是两个互斥的阵营，它们可以在一个程序里各管一段，接口在模块这一侧收口。

这条迁移路线也解释了本章开头那个宏问题为什么不能靠“全部改成模块”解决。模块能阻止宏穿过模块边界，但旧头文件里的宏仍然在包含它的翻译单元里生效；只要还有 `#include`，预处理器的文本替换就还在。真正的改善来自把边界一步步移到模块接口上，让新代码不再被旧宏影响，而不是指望一次切换。

模块的构建依赖也要和迁移节奏匹配。一个模块接口的 BMI 必须在使用它的目标之前生成，构建系统要能表达这条边；如果项目还在用只认识 `.cpp`/`.h` 的旧脚本，先把模块例子放进独立目标，跑通“先 BMI、后导入方”的顺序，再扩大范围。编译器版本也要统一：Clang 21 直接支持 C++20 模块，GCC 15 要加 `-fmodules`，两者生成的 BMI 不能互换；团队里混用编译器和标准库时，先固定一条能工作的工具链，再谈迁移。

## 回头看

从 `export` 到 modules，变化的是关键字背后的机制，不变的是“依赖在哪里”。`export` 想把模板定义移出调用方的视野，却没有移走实例化所需的信息；C++20 模块把接口编译成 BMI，真正省掉了头文件的重复解析和宏的传播，但对模板，它仍然只有两条路：把定义放进 BMI 让导入方实例化，或者留在实现单元只覆盖显式实例化的类型。模块让普通函数可以做到“改实现只重链接”，却没有把模板的实例化变成链接期的事，也没有规定对象布局和 ABI。今天写模块，先想清楚边界划在哪：哪些名字要 `export`，哪些头文件只能留在全局模块片段，哪些模板必须把定义交给导入方；再让构建系统按 BMI 的依赖顺序工作。头文件和模块会长期共存，迁移的价值在于让新边界不再继承旧头文件的宏和名字泄漏，而不是把 `.h` 批量改名成 `.cppm`。
