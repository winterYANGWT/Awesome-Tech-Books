# 第 33 章 头文件、命名空间与物理依赖

改一个类的私有成员，为什么半个项目都要重编译？下面这个头文件给出了最常见的原因：

```cpp
// order.h
#include <string>
#include "customer.h"     // Customer 的完整定义
#include "address.h"      // Address 的完整定义

class Order {
public:
    // ...
private:
    Customer customer_;   // 按值成员：编译器要知道 Customer 的大小
    Address  ship_to_;    // 按值成员：还要知道 Address 的布局
};
```

`Order` 的公开接口没有提到 `Customer` 和 `Address`，但这两个私有成员仍然逼着每个包含 `order.h` 的翻译单元（translation unit）去解析 `customer.h` 和 `address.h`。`Customer` 加一个字段，`Order` 的对象布局就变了，所有见过 `order.h` 的 `.cpp` 都得重新编译。物理依赖不是由“谁调用谁”决定的，而是由“谁必须看见谁的定义”决定的。

同一类问题也发生在命名空间（namespace）里。头文件里一句 `using namespace std;`，会让后面所有代码的名字查找都多出一大批候选；某个头文件里一句 `using N::f;`，又可能让另一个头文件里的调用从 `f(int)` 悄悄换成 `f(double)`。这两种毛病看起来一个属于构建、一个属于语言，根子却是同一个：头文件是会被别人复制进翻译单元的文本，它暴露的每一样东西都会影响所有包含者。

这一章沿着两条线走。前半段讲“谁能藏在头文件外”：前置声明、Pimpl、自足头文件、包含守卫、只放声明；后半段讲“名字放在哪个命名空间”：别名、`using` 声明与指示、ADL、内部链接。两条线在最后一节合起来：头文件里定义的 `const` 为什么不会重复定义，而同样位置的普通变量会。

## 33.1 尽量减少文件之间的编译依赖

C++ 的类定义必须让编译器看到对象的完整布局：每个成员多大、对齐多少、基类子对象放在哪里、虚函数表指针占几个字节。这些信息不能推迟到链接期，所以只要一个类按值含有另一个类，或者公开继承另一个类，后者的定义就必须出现在前者的头文件里。EC-31 把这种依赖称为“定义依赖”（definitional dependency），并给出了替代方案：把成员换成指针或引用，只留前置声明；需要更彻底地把实现移走时，用 Handle class（Pimpl）或只含纯虚函数的 Interface class。

“尽量少包含”不等于“什么都不能包含”。EC-31 提醒，函数的参数和返回值即使按值传递，声明时也只需要类型名，不需要定义；只有调用方真正构造或销毁那个类型的对象时，才需要完整定义。这一点常被误解成“按值传参一定要 include”，于是头文件里堆了一堆其实可以换成前置声明的包含。下面这个例子把几种“只需要名字”的场合放在一起：

```cpp
{{#include code/ch33/33_1_declarations.cpp}}
```

输出：

```text
{{#include code/ch33/33_1_declarations.out}}
```

`Report` 在前置声明之后立刻被用于按值返回的函数声明、`const Report&` 参数、`Report*` 成员，`decltype(make_report())` 也能通过 `static_assert`；直到 `Dashboard::lines()` 真正访问 `report_->lines`，编译器才需要 `Report` 的完整定义。把 `Report` 的定义放到 `report.cpp`，`dashboard.h` 就只剩一行 `struct Report;`，`Report` 的私有成员怎么改都不会触发 `Dashboard` 客户端重编译。这是 EC-31 的第一条具体做法：能用指针或引用表示的成员关系，就不要用按值成员；能只声明函数，就不要为了声明去包含定义。

第二类问题是循环。两个头文件互相包含时，编译能不能过取决于从哪个头文件进入：先展开的那个类还没看到对方的名字。CCS-22 把这种关系放到模块层面看：两个直接或间接互相依赖的模块，其实已经粘成了一个更大的发布单元，测试、发布和复用都无法独立进行。它给出的破环手段是依赖倒置：让双方都依赖抽象接口，或者至少让其中一边只持指针/引用。先看坏版本：

```cpp
{{#include code/ch33/33_1_cycle/parent_bad.h}}

{{#include code/ch33/33_1_cycle/child_bad.h}}
```

从 `main_bad.cpp` 包含 `child_bad.h` 开始，`child_bad.h` 先展开 `parent_bad.h`，此时 `Child` 还没声明，`Parent::attach(Child*)` 就找不到 `Child`。把两边的 `#include` 都换成前置声明，环就断了：

```cpp
{{#include code/ch33/33_1_cycle/parent.h}}

{{#include code/ch33/33_1_cycle/child.h}}
```

编译并运行：

```text
{{#include code/ch33/33_1_cycle/output.out}}
```

脚本先尝试坏版本，确认它编译失败，再编译前置声明版本。注意，断环的不是“把 include 挪个位置”，而是把“需要完整定义”降级成“只需要名字”：`Parent` 只存 `Child*`，不调用 `Child` 的成员，所以看到 `class Child;` 就够了。如果 `Parent` 按值含有 `Child`，前置声明救不了它，只能改用指针、Pimpl，或者重新划分两个类的职责。

前置声明也有边界。标准库类型不能手写声明，这一点 33.3 会展开；自己写的类，前置声明必须和定义用同一个 `class`/`struct` 关键字，否则 clang 会给出 `-Wmismatched-tags`，在 `-Werror` 下直接变成错误。库作者最好成对提供 `date.h` 和 `datefwd.h`，让调用方包含声明头，而不是各自手写 `class Date;`——手写的前置声明一旦和真实定义漂移，错误会跑到调用方那里。

EC-31 给出的两条彻底方案是 Handle class 和 Interface class。Handle class 就是 Pimpl：可见类只留一个指向 `XImpl` 的指针，所有成员函数转发给实现类；Interface class 则只有纯虚函数和虚析构，客户通过工厂函数拿到 `unique_ptr<Base>`，具体类完全藏在 `.cpp` 里。两者的代价一样：每次访问多一层间接，每个对象多一个指针（Interface class 还多一个 vptr），构造/析构可能多一次动态分配，而且实现细节被藏起来后很难内联。EC-31 的建议不是“所有类都 Pimpl”，而是按演化方式使用：开发期用 Pimpl/Interface 降低客户的重编译成本，等 profiler 证明运行期开销真的重要，再把热点类还原成具体类。

C++11 以后，Pimpl 的写法比原书安全：裸指针换成 `std::unique_ptr<XImpl>`，`new` 换成 `std::make_unique`（C++14），移动操作可以 `= default`。代价是 `unique_ptr` 的析构要求 `XImpl` 完整，所以可见类的析构函数必须在 `.cpp` 里定义，不能直接在头文件里 `= default`；这个坑在 33.3 用编译错误演示。`std::shared_ptr` 的删除器在构造时已经类型擦除，析构不要求完整类型，对不完整类型更宽容，但它带来引用计数和所有权语义，不能只为省一个析构定义就换。

C++20 的 modules 从语言层面改变了“文本包含”这件事：模块接口单元只导出 `export` 的名字，导入方不需要为了声明去解析一整串头文件，函数体可以放到模块实现单元；模块之间也不允许循环导入。对“减少文件之间的编译依赖”来说，这消除了头文件的重复解析和宏泄漏，但**没有**消除类布局依赖：一个 exported 类的私有成员仍然写在接口单元里，改布局仍然会影响导入方。所以 modules 不是 Pimpl 的替代品，EC-31 的“声明还是定义”之分在模块里仍然成立。迁移期内头文件仍是主流，构建系统、编译器和 IDE 对模块的支持并不齐，BMI 也不跨编译器稳定；今天写头文件，仍然按 EC-31 和 CCS-22 的规则组织依赖，模块是另一条并行的路，第 34 章会专门讲。

最后是工具。`clang++ -H` 会把实际展开的头文件树打到 stderr，能直接看出某个 `.cpp` 被哪些头文件拖住；`-MM` 只列用户头文件，适合喂给构建系统或做依赖统计。clang-tidy 的 `misc-header-include-cycle` 能查头文件包含环，`misc-include-cleaner` 能提示多余或缺失的包含。这些工具不能替你决定“这个成员该不该按值放”，但能让你在改完一个私有成员之后，看见到底有多少翻译单元被卷进来。

## 33.2 每个头文件都要能独立编译

判断一个头文件是否自足，最简单的办法是把它当成源文件单独编译一次：不先包含任何别的项目头文件，直接 `clang++ -fsyntax-only -x c++-header foo.h`。如果它漏了 `<string>`、漏了某个基类的定义，这一步就会报错。CCS-23 把这条叫作“头文件要自足”：谁包含这个头，谁就有权假定它带来的名字是完整的，而不是被要求“先包含 A 再包含 B”。

自足不等于把见过的头文件都塞进去。CCS-23 同时提醒：不要包含用不到的头，否则只是把依赖换了个方向。真正的判据是“这个头文件的声明和定义直接需要什么”。`account.h` 按值含有 `Money` 和 `std::string`，所以它必须包含 `money.h` 和 `<string>`；`report.h` 只声明 `std::ostream& operator<<(std::ostream&, const Account&)`，`Account` 是引用参数，`std::ostream` 也只需要名字，于是它包含 `<iosfwd>`、前置声明 `Account` 就够了。EXC-26 把这条讲得更细：`<iostream>` 几乎总是多余，`<ostream>` 也可以降成 `<iosfwd>`；内联的 `operator<<` 只要不调用 `ostream` 的成员函数，看到 `ostream&` 并不等于需要完整定义。

```cpp
{{#include code/ch33/33_2_headers/report.h}}
```

这段头文件里没有任何定义，只有声明。它甚至没有包含 `account.h`，因为 `Account` 只以引用出现。真正需要 `Account` 完整定义的是 `report.cpp`，它包含 `account.h` 并调用 `owner()`、`balance()`；这就是“声明放头文件、定义放实现文件”的分界线。

模板会让缺失的包含延迟暴露。CCS-23 举的例子是：一个模板类里有 `std::deque<T>` 成员，只要没人实例化这个模板，编译器就不会报告 `<deque>` 没包含；成员函数模板更是只有被调用时才实例化。于是“我的测试能过”不能证明头文件自足，必须专门做“每个头文件单独编译”的检查。把这一步放进 CI，比在代码评审里靠眼睛找漏包含可靠得多。

只有声明还不够，头文件还要防止自己被重复包含。CCS-24 要求每个头文件用自己的包含守卫（include guard）把全部内容包住：

```cpp
#ifndef CH33_ACCOUNT_H
#define CH33_ACCOUNT_H
// ... 全部内容 ...
#endif
```

守卫名至少要在项目内唯一，通常把项目名或路径编进去；守卫要“笨”而标准，宏判断紧贴文件首尾，守卫之外不要放代码或注释，因为编译器识别守卫时可能只认这种固定形状。不要写外部守卫——也就是让调用方在 `#include "foo.h"` 外面套 `#ifndef FOO_H`。那等于把宏名变成调用方和头文件之间的隐式契约，改文件名、复制头文件或换一个包含点就可能失配。`#pragma once` 更短，主流编译器都支持，但它至今不在 C++ 标准里（截至 C++23），跨平台库不能把它当成唯一手段。

有一类头文件故意要被多次包含，例如用宏展开生成表的 X-macro 文件；这类文件不能加普通守卫，属于 CCS-24 明确留的例外。除此之外，守卫应该是无条件的，不要用 `#ifdef` 包住守卫本身。

CCS-61 接着规定：头文件里只放声明，有链接的实体放到实现文件。命名空间级的 `int refresh_count = 0;` 被两个 `.cpp` 包含，就在两个翻译单元各有一份定义，链接器会报重复符号；`static int refresh_count` 或匿名命名空间虽然能躲过链接错误，却让每个包含者拿到一份私有副本，被五十个翻译单元包含就有五十份，而且那个“全局变量”其实各改各的。这个反例在示例脚本里会实际链接一次：

```text
{{#include code/ch33/33_2_headers/output.out}}
```

脚本先用 `-fsyntax-only -x c++-header` 逐个编译 `money.h`、`account.h`、`report.h`，再故意编译漏了 `<string>` 的 `missing_include.h`，确认它失败；然后编译正常运行的程序；最后把 `shared_counter.h` 放进两个翻译单元，确认链接器报 `multiple definition`。`main.cpp` 连续两次包含 `account.h`，第二次被守卫挡掉，所以没有重定义。

例外也要说清楚。`inline` 函数可以放头文件，链接器保证多份副本不会冲突，取地址在整个程序中唯一；函数模板、类模板和类模板的静态数据成员可以放头文件，重复实例化由编译器和链接器合并。C++17 起，`inline` 变量也可以在头文件里定义，`inline int refresh_count = 0;` 是全程序唯一的一份，取代了“`extern` 声明 + 一个 `.cpp` 定义”的老套路；`static constexpr` 数据成员从 C++17 起隐式 `inline`，也不再需要类外定义。注意没有 `inline` 的命名空间级 `const`/`constexpr` 变量默认是内部链接，在头文件里定义仍然等于每个翻译单元一份，只是不会链接冲突——33.6 会专门讲这一点。

`<iosfwd>` 是 EXC-26 和 MXC-37 都强调的例外。`std::ostream` 不是类，而是 `basic_ostream<char>` 的 typedef；`std::string` 是 `basic_string<char>` 的 typedef。标准禁止用户向 `namespace std` 添加声明，实现还可能给标准模板加默认参数，所以手写 `class ostream;` 或 `class string;` 不可移植。需要流的前置声明时包含 `<iosfwd>`；需要 `std::string` 时没有对应的 `stringfwd` 头，只能包含 `<string>`。MXC-37 的结论是：前置声明对“自己的类”可靠，对标准库类型要用标准提供的设施，`<iosfwd>` 是专门为流开的口子，不是通例。

C++17 的 `__has_include` 让“有条件地包含”可以可移植地写出来，例如只在存在 `<optional>` 时才启用某个接口；但这只解决“头文件在不在”，不解决“名字该不该暴露”。C++20 modules 让模块单元显式 `import` 依赖，从机制上消除了“忘记包含”，但现有代码仍以头文件为主，单独编译每个头的检查依旧值得保留。

工具方面，`-Wheader-hygiene` 是 clang 的检查，会在头文件的全局作用域出现 `using namespace` 时警告；GCC 没有这个选项。clang-tidy 的 `misc-definitions-in-headers` 查头文件里的非 inline 定义，`misc-include-cleaner` 查多余或缺失的包含。它们能覆盖 CCS-23、CCS-24、CCS-61 的大部分机械部分，但“这个头文件到底该不该包含那个定义”仍要人来判断。

## 33.3 前置声明、Pimpl 和不完整类型：谁能藏在头文件外

前置声明不是万能钥匙。编译器要在头文件里确定一个类对象的大小和布局，所以有两类东西必须看到完整定义：基类子对象，以及按值存放的数据成员。下面这个反例把 `Engine` 只声明成不完整类型，却拿它当 `Car` 的成员：

```cpp
{{#include code/ch33/33_3_incomplete_member_fail.cpp}}
```

clang 的诊断：

```text
{{#include code/ch33/33_3_incomplete_member_fail.out}}
```

`Engine` 的大小未知，`Car` 的布局就定不下来，所以这不是“链接时再说”的问题，而是编译期错误。基类同理：`class Derived : public Base` 要求 `Base` 完整，因为基类子对象要嵌在派生对象里。EXC-27 把这条总结成：`a.h`、`b.h` 不能去掉，因为 `X` 公有继承 `A`、私有继承 `B`；`std::list<C>` 和 `D` 作为私有成员时也去不掉，因为成员按值存放。能去掉的是那些只以指针、引用、参数或返回值出现的类型。

Pimpl 的作用，就是把“按值成员”换成“指向实现的指针”，从而把 `list`、`C`、`D` 这些定义从公开头文件里移走。可见类只留一个不透明指针：

```cpp
{{#include code/ch33/33_3_pimpl/document.h}}
```

实现文件才定义 `Document::Impl`：

```cpp
{{#include code/ch33/33_3_pimpl/document.cpp}}
```

客户端只看到 `document.h`，`Impl` 里的 `std::string body`、`int reads` 怎么改都不影响它：

```text
{{#include code/ch33/33_3_pimpl/output.out}}
```

本机 `sizeof(Document)` 是 24 字节：一个 vptr、一个 `revision_`、一个 `unique_ptr` 指针，加上对齐。`Impl` 里再加多少成员，这个数字都不变。这不是“省内存”，而是“把布局变化挡在客户端之外”。代价是每个对象多一次动态分配、每次访问多一层间接；`Document` 的拷贝被删掉，移动操作也放到 `.cpp` 里 `= default`；真正需要完整 `Impl` 的是析构，移动本身只搬指针。

EXC-29 讨论 Pimpl 里到底放什么，给出了四种做法。只放私有数据能隐藏“仅作为数据成员出现的类型”，但私有函数仍留在头文件里；放全部非虚私有成员（数据加函数）是作者常用的 10/10 方案；把 protected 也塞进去是 0/10，因为 protected 成员本来就是给派生类看的，藏进 `Impl` 后派生类根本用不了；把 `XImpl` 做成完整实现、可见类只做转发（handle/body 变体）能避免回指指针，但可见类通常不再适合当基类或派生类。

还有一条硬规则：虚函数不能藏进 Pimpl，哪怕它是 private 的。如果虚函数覆盖基类版本，它必须出现在真正的派生类里才能参与覆盖；如果它不是继承来的，也必须留在可见类里，才能被更下一层的派生类覆盖。`document.h` 里的 `virtual std::string render() const` 就是这样的例子，`HtmlDocument` 覆盖它并调用 `Document::render()`；`revision_` 留在 protected，`HtmlDocument::revise()` 才能直接改。派生类需要调用基类版本时，虚函数还得是 protected 而不是 private。

Pimpl 的函数如果要回调可见类的 public 或虚函数，`Impl` 就需要一个指回 `X` 的 `self_` 指针，这会再多一层间接。EXC-29 的建议是：优先按“全部非虚私有成员”放，只把被私有函数调用的少量非私有函数放进 `Impl`，不要为了“看起来更隐藏”把接口拆得七零八落。

现代 Pimpl 最常见的坑是 `unique_ptr` 的析构。`unique_ptr<T>` 的默认删除器在析构时要求 `T` 完整，所以可见类的析构函数必须在 `.cpp` 里定义。下面这个头文件把 `~Session() = default` 留在类内：

```cpp
{{#include code/ch33/33_3_pimpl_dtor/bad_session.h}}
```

客户端一构造 `Session`，编译就失败：


## 33.4 用 using 控制名字与可替换性

这种顺序依赖在头文件里会变成灾难。CCS-59 和 MXC-40 的规则很硬：头文件里不要写 `using namespace`，也不要写命名空间级的 `using N::f;`；实现文件里可以随便用，但必须放在所有 `#include` 之后。原因是头文件会被任意多个翻译单元以任意顺序包含：`using` 声明在某个头文件里取了快照，另一个头文件又给同一个命名空间加了重载，`B::g` 调用的 `f` 就取决于包含顺序；如果 `B::g` 是 inline 函数或模板，两份翻译单元可能生成两个不同的定义，直接违反 ODR。把 `using` 放在 `#include` 之前更糟：它会改变被包含头文件里的名字查找，等于在别人的代码上动手脚。

```cpp
// 头文件里不要这样写
using namespace std;          // 把整个 std 倒进每个包含者
namespace app {
using std::string;            // 命名空间级 using 声明也不行
}
```

正确做法是头文件里全部写 `std::string`、`std::vector`，实现文件在所有 `#include` 结束后再写 `using std::string;` 或 `using namespace std;`。MXC-40 给大规模迁移留了一个务实的办法：先用脚本把 `.h` 里的 `string`、`vector` 批量改成 `std::string`、`std::vector`，再建一个 `myproject_last.h`，里面只写 `using namespace std;`，每个 `.cpp` 在最后包含它。这样短期能编译，长期也不用“撤销”什么，只是把统一的 using 逐步换成按需的 using。

类的成员 `using` 不受这条限制：在派生类里写 `using Base::f;` 把基类的重载引入派生类作用域，是解决名字隐藏的标准手段（第 17 章）；它只影响这个类，不会污染包含者。C++20 的 `using enum` 把枚举项引入作用域，属于 using 声明家族；C++11 的 inline namespace 和 C++17 的嵌套命名空间定义 `namespace a::b {}` 减少了必须靠 using 才能少写限定词的情况。C++20 modules 让接口单元有明确的导出边界，非导出的 using 不会像头文件那样自动泄漏，但用 `#include` 组织的代码规则完全不变。

工具方面，clang 的 `-Wheader-hygiene` 会在头文件的全局作用域出现 `using namespace` 时警告（GCC 没有这个选项）；clang-tidy 的 `google-build-using-namespace` 也查全局 `using namespace`，`misc-unused-using-decls` 查没被用到的 using 声明。它们能抓住“写错位置”，但抓不住“这个 using 声明取快照时到底看见了哪些重载”，后者只能靠把 using 放到所有声明之后、或者干脆全限定来避免。

## 33.5 命名空间怎么分：ADL 与类型接口

命名空间不只是“防止重名”的文件夹。C++ 在查找函数时，除了从当前作用域逐层向外找，还会到实参类型的所属命名空间里找同名函数，这就是实参依赖查找（argument-dependent lookup，ADL，也叫 Koenig 查找）。ADL 的设计目的就是让类型的非成员接口——运算符、`swap`、`begin`/`end`、格式化函数——用起来和成员函数一样自然。CCS-57 把这条叫接口原则：一个函数如果既提到类型 `X`，又和 `X` 一起提供，它就是 `X` 接口的一部分，应该和 `X` 放在同一个命名空间，不管它是成员还是非成员。

MXC-40 把命名空间的使用总结成几条可执行的规则，并给了大规模迁移的策略。长期方案是：每个项目一个顶层命名空间，按模块划子命名空间；头文件里所有标准名显式 `std::` 限定，绝不写命名空间级 `using`；实现文件在所有 `#include` 之后可以随意 `using`；不要往别人的命名空间里加东西。迁移旧代码时，先用脚本给头文件补 `std::`，再建一个只含 `using namespace std;` 的 `myproject_last.h`，让每个 `.cpp` 最后包含它；等有空时再逐个文件换成按需的 `using` 声明。这套策略在 33.4 已经展开，这里只强调它的命名空间目标：让每个名字的归属清楚，让 ADL 只带来“本来就属于这个类型”的函数。

C++17 的嵌套命名空间定义 `namespace app::billing {}` 让层级更好写；C++11 的 inline namespace 可以做版本化，例如 `namespace api { inline namespace v2 { ... } }`，旧代码仍写 `api::foo`，新代码可以显式写 `api::v2::foo`。C++20 的 `using enum` 把枚举项引入当前作用域；如果写在头文件的命名空间作用域，它同样会泄漏给包含者，仍要遵守 CCS-59。C++20 modules 给接口单元一个明确的导出边界，非导出的名字不会像头文件那样泄漏，但 ADL 规则没有变：模块里的类型仍然按它所在的命名空间参与查找，`export` 只决定导入方能不能看见名字，不改变关联命名空间的计算。C++20 的 `<=>` 和 `operator==` 常写成 hidden friend（在类内定义的友元），这种函数只能被 ADL 找到，正好符合 CCS-57；把它挪到类外另一个命名空间，`a == b` 就会找不到。

命名空间的组织没有编译器能替你做的“正确性检查”，但有几条工具线索：clang-tidy 的 `google-build-using-namespace` 查全局 `using namespace`，`misc-unused-using-decls` 查没用的 using 声明，`misc-header-include-cycle` 和 `misc-include-cleaner` 则从物理依赖侧面提醒你命名空间的边界有没有被头文件搅乱。真正要守的还是那两句话：类型和它的非成员接口同处一个命名空间；无关的函数，尤其模板和运算符，坚决不要放进去。

## 33.6 头文件里的 const 默认内部链接，不会重复定义

C++ 和 C 在这里有一条容易被忽略的差异：命名空间作用域的 `const` 变量默认是内部链接（internal linkage），每个翻译单元各有一份；C 的文件作用域 `const` 默认是外部链接，放进头文件被多个 `.cpp` 包含就会重复定义。TIC-01 把这条当作“为什么可以把 `const int n = 10;` 放进头文件”的理由：C++ 的默认内部链接正是为了让头文件里的常量安全。

```cpp
{{#include code/ch33/33_6_const_linkage/config.h}}
```

`kMaxRetries` 在每个包含 `config.h` 的翻译单元里都是一份独立的 `const int`；`a.cpp` 和 `b.cpp` 各自取地址，得到两个不同的地址。`kBufferSize` 是 `inline constexpr`，C++17 起 inline 变量在全程序只有一个实体，两个翻译单元取到同一个地址。`kTimeoutMs` 在头文件里只有 `extern` 声明，定义放在 `a.cpp`，所以也是同一个对象：

```text
{{#include code/ch33/33_6_const_linkage/output.out}}
```

这正是 TIC-01 说的三种情况：普通 `const` 放头文件不会链接冲突，但每个翻译单元一份；要全程序共享同一个对象，就在头文件写 `extern const int n;`，在一个 `.cpp` 写 `extern const int n = 10;`；C++17 以后更简单的写法是 `inline constexpr int n = 10;`。`main` 里 `&cfg::kMaxRetries` 和 `a.cpp` 里的地址也不同，说明 `main.cpp` 自己也有一份，不是“A 和 B 碰巧不同”。

为什么普通 `const` 不会冲突？因为编译器通常把 `const` 的值折叠进代码，不分配存储；只有在取地址、绑定引用、按引用传参，或者写 `extern` 时，才一定需要存储。TIC-01 还提醒，`const` 的内部链接只适用于命名空间作用域；块作用域的 `const` 本来就没有链接，函数里的 `const int n = 10;` 是自动变量，和链接无关。`constexpr` 本身不改变链接：命名空间作用域的 `constexpr` 变量仍然是 `const`，仍然默认内部链接；只有加上 `inline` 才变成全程序一个实体。C++17 的 `static constexpr` 数据成员是隐式 `inline`，所以类内定义就够了，不再需要类外定义；C++17 之前的 `static const int` 在 odr-use 时仍要类外定义，这一点第 22 章讲过。

内部链接的“每个翻译单元一份”不总是无害。如果某个头文件里写 `const std::string kName = "app";`，每个包含者都构造一份，程序启动/退出时各析构一次；如果代码比较 `&kName` 来判断“是不是同一个配置对象”，结果会随翻译单元变化。需要身份唯一时，用 `inline constexpr`（要求字面类型）或 `extern const` 加一个定义；需要在运行期初始化、又不想重复构造时，用函数局部静态对象（C++11 起初始化线程安全），把“首次访问初始化”变成显式调用依赖。

`const` 的内部链接和 33.2 的 CCS-61 是同一枚硬币的两面。CCS-61 说头文件里不要放有链接的实体；普通 `const` 因为有内部链接，不会造成重复定义，但仍然是“每个翻译单元一份”的实体，不是“全程序共享的常量”。写库时把这两件事分开：需要编译期常量且不关心地址，用 `inline constexpr`；需要运行期对象且全程序唯一，用 `extern const` 或函数局部静态；只是某个 `.cpp` 内部用的常量，放 `.cpp` 的匿名命名空间或 `static`，不要放公共头文件。

C++20 modules 不改变链接规则：模块接口单元里导出的 `const` 仍然按它自己的链接属性处理，`inline` 变量仍然全程序唯一。`constinit`（C++20）保证变量做常量初始化，但它管的是初始化时机，不是链接；不要把它和 `inline` 混为一谈。

## 回头看

这一章的规则都在回答两个问题：一个翻译单元必须看见什么，以及它看得见哪些名字。头文件是会被复制进每个包含者的文本，所以每多一个 `#include`、每多一个定义、每多一句 `using`，都在扩大别人必须接受的上下文。前置声明、Pimpl、自足头文件、包含守卫、只放声明，都是把“必须看见的定义”压到最小；命名空间、ADL、using 声明与指示、内部链接，则是把“名字从哪里来”说清楚。两条线在 `const` 那一节合流：同一个 `const int` 放在头文件里不冲突，是因为它默认内部链接，每个翻译单元各有一份；要共享身份，就得写 `extern` 或 `inline`。

C++17 和 C++20 抬高了一部分地板：`inline` 变量让头文件里的全程序唯一对象有了直接写法，`static constexpr` 成员不再需要类外定义，`__has_include` 让条件包含可移植，modules 把“文本包含”换成了显式的导入/导出边界。但对象布局、ABI、ADL 和名字查找没有因此消失：模块不改变类的成员布局，也不改变关联命名空间；`#pragma once` 至今不是标准；Pimpl 仍然要为一次分配和一层间接付账。工具能替我们查包含环、多余包含、头文件里的定义和 `using namespace`，但“这个成员该不该按值放”“这个运算符算不算 `X` 的接口”“这个常量需不需要全程序唯一”仍要写代码的人判断。规则的价值不在于记住条目，而在于下次改一个私有成员之前，先想一下谁会因此重编译；下次往头文件里放一个名字之前，先想一下它会跟着谁走。
