# 第 20 章 模板基础：隐式接口、依赖名与特化

模板报错常常一屏接一屏，第一行还落在标准库内部，实际原因却在几百行之后。多数时候不是模板写错了，而是某个类型没有提供模板正文里用到的那几个表达式：少一个 `size()`，`size()` 的返回值不能和 `int` 比较，或者迭代器不是指针。模板不会先声明一份接口再检查实参，它把正文里出现的每个表达式都当成对类型的要求，等到实例化时才逐条核对。知道这一点，读报错时就能先找“哪一个表达式不成立”，而不是从第一行开始逐字读。

这些要求有的写在函数体里，有的藏在被调用的另一个模板里；有的依赖名要加 `typename` 才能通过语法分析，有的名字因为基类是模板而根本不会被查找。再往后，定制行为的方式也分成两套：类模板可以全特化和偏特化，函数模板只能全特化，而且特化不参与重载决议。本章按“模板到底在检查什么”这条线，把这些规则串起来。

`Gauge::normalize` 把 `id` 加一，`temp.swap(w)` 再把这个新值换进 `w`，所以打印 2；`Ticket` 的 `size()` 是 3，条件不成立，什么也没发生。`process` 对类型的要求不是一张函数签名表，而是一组必须成立的表达式：`w.size()` 的结果要能和 `10` 比大小，整个条件要能当 `bool` 用，`w != other` 要合法，`w.normalize()`、`w.swap(w)` 和 `T(w)` 都要能编译。这就是 Meyers 在 EC-41 里说的隐式接口（implicit interface）：它由合法表达式组成，而不是由声明组成。`Gauge::size()` 返回 `Celsius`，`Celsius` 也不是数值类型，只因为定义了 `operator>(Celsius, int)`，`w.size() > 10` 就成立。按签名找接口会认为这里必须返回整数，按表达式看就不会。甚至 `!=` 也可以由转换或重载提供，模板并不要求 `T` 自己有一个 `operator!=` 成员。

`static_assert(!Processable<Unprepared>)` 说明这份接口可以用 C++20 的 concept 提前写成一句可检查的约束，`Processable<Gauge>` 和 `Processable<Ticket>` 则说明两个毫无亲缘关系的类型都能通过。concept 没有改变模板的工作方式，它只是把原本散落在函数体里的表达式要求提到接口上，让不满足时在约束检查处就报错，而不是实例化到一半才报错（[第 21 章](ch21.md)）。EC-41 还提醒，隐式接口的错误通常出现在实例化点，定位比普通类的接口错误困难；concept 改善的是错误位置和长度，不是检查的时机——两类接口本来都在编译期检查。

## 20.2 依赖名是类型就要写 typename

`typename` 在模板声明里和 `class` 完全等价：`template<class T>` 与 `template<typename T>` 没有任何区别，EC-42 开头问的就是这个。它还有第二种用法：当模板里的某个名字依赖于模板参数、而且表示一个类型时，必须在前面写 `typename`。原因是语法分析器在看到 `C::const_iterator * x;` 时不知道 `C::const_iterator` 是类型还是静态数据成员；如果是后者，这行就是乘法。标准选择了一个保守规则：依赖的限定名一律先当作非类型，除非用 `typename` 明确。

```cpp

```

输出：

```text

```

`C::const_iterator` 和 `C::value_type` 都嵌套在依赖的类里，是“嵌套依赖类型名”：示例里的变量声明 `typename C::const_iterator it` 不能省；`std::iterator_traits<It>::value_type` 也是同样的名字，先用 `using value_type = typename ...` 把它收短，后面的 `value_type temp` 就是普通类型名了。MXC-05 把这称为“再导出”：标准库里有不少只提供一堆 typedef 的空基类（俗称 bags-o-typedefs），派生类看似重复地把这些 typedef 再写一遍，实际是把依赖名变成非依赖名，让后面的代码不必在每个使用点都写 `typename X_base<B>::...`。C++11 的 `using` 别名比 `typedef` 读起来清楚，但不会改变依赖规则。

C++20 的 P0634R3 放宽了一部分上下文：在只可能是类型的位置，`typename` 可以省略。示例里的别名声明 `using inner = T::value_type;`、返回类型 `T::value_type first()`、参数声明 `void take(T::value_type)` 在 C++20 下都不再需要 `typename`；C++17 下同样的代码在 GCC 15 会直接报错，Clang 21 则把它当作 C++20 扩展给出 `-Wc++20-extensions` 警告。块作用域的变量声明仍然是需要 `typename` 的典型位置：`C::const_iterator it = ...` 即使加 `-std=c++20` 也过不了，`20_2_dependent_names_fail.cpp` 的第一条错误就是它。基类列表和成员初始化列表里的基类标识符是反方向的例外：那里不能写 `typename`，本机两个编译器都会报“不允许/多余”。所以“C++20 以后 typename 可以随便省”是错的；写库代码时，如果在某个位置拿不准，加上 `typename` 仍然是最稳的选择，除非那个位置明确禁止。

## 20.3 模板多态不靠继承，构造和转换都要换写法

Sutter 在 EXS-05 里把两种多态摆在一起：运行期多态要求类型有共同基类、通过指针或引用调用虚函数，每次调用多一次间接跳转；模板的编译期多态只要求用到的表达式对实参类型合法，两个毫无亲缘关系的类型可以进同一个模板，代价是定义必须对调用点可见、每种类型生成一份代码。示例里的 `construct` 就是这种“按表达式工作”的工具，它把 `T1` 和 `T2` 分成两个模板参数：

模板实参推导不会考虑隐式转换，这一点和 EC-46 要讲的 `operator*` 是同一个规则。把 `T1` 和 `T2` 分开，`construct` 的调用方就不必写 `construct<double>(&d, 42)` 或 `construct<Base>(pb, der)`；代价是它默许窄化（`int` 到 `double`）和切片（`Derived` 到 `Base`，`extra` 被丢掉）。切片有时正是想要的，工具不该替调用方禁止，但接口文档要说清楚。

`construct` 的实现是 placement new：不申请内存，在 `p` 指向的原始存储上以 direct-initialization 构造对象，所以 `explicit Token(int)` 也能用。构造成功后对象的生命周期才开始，必须显式调用析构函数销毁，绝不能对 `p` 用 `delete`；如果构造函数抛异常，对象没有诞生，不需要析构，存储仍由调用方负责。示例用 `Storage<T>` 把对齐和字节数组包起来，用 `destroy_at` 显式析构，`sizeof(Base)` 与 `sizeof(Derived)` 的差说明了切片丢了什么。今天手写 `construct` 的必要性已经不大：C++11 的 `allocator_traits::construct` 支持可变参数和完美转发，C++20 的 `std::construct_at` 是这个函数的直接替代，而且是 `constexpr`；`std::allocator::construct` 在 C++17 弃用、C++20 移除。placement new 仍然可用，但复用存储的某些场景从 C++17 起需要 `std::launder`，优先用标准设施更稳。

同一个模板里，`T` 该按值传还是按 `const&` 传？ESS-11 的建议是：写模板时不知道 `T` 是内置类型还是昂贵的类，默认按类类型对待，形参用 `const T&`，成员在构造函数初始化列表里构造。示例里的 `Matrix` 把默认构造、拷贝构造和拷贝赋值都计数：`Node<Matrix>` 在初始化列表里只拷贝一次，`NodeAssigned<Matrix>` 先默认构造再赋值，比初始化列表多了一次默认构造，拷贝构造也换成了拷贝赋值。对 `int` 两种写法没有区别，对 `Matrix` 就有。C++11 的移动语义给“按值传 + `std::move`”添了新的理由：如果函数总是要存一份实参，按值传对右值更便宜；但模板作者不能假定 `T` 可移动或移动便宜，`const&` 仍是通用默认，C++20 的 concepts 可以把“可拷贝/可移动”写成约束，却不能替调用方决定哪种传参更合适。

## 20.4 函数模板特化不参与重载决议，类模板才有偏特化

类模板可以全特化，也可以偏特化；函数模板只能全特化，而且“偏特化”写出来其实是另一个主模板。看下面这组声明：

```cpp
{{#include code/ch20/20_4_specialization_order.cpp}}
```

输出：

```text
{{#include code/ch20/20_4_specialization_order.out}}
```

`f(&i)` 调用的是 `f(T*)`，不是那个看起来更精确的 `f<int*>` 特化。原因是重载决议只比较非模板函数和各个主模板，`f<int*>` 是 `f(T)` 的特化，它不参加这一轮比较；等 `f(T)` 被选中之后，编译器才回头看它有没有匹配的特化。这里 `f(T*)` 比 `f(T)` 更特化，先赢下重载决议，`f<int*>` 根本没机会上场。`f<int*>(&i)` 显式指定模板实参，只考虑模板，才选中特化。Sutter 在 EXS-07 里把这个例子归给 Dimov 和 Abrahams，并给出一条容易记住的说法：特化不重载（specializations don't overload）。

非模板函数的地位不同。`g(1)` 选非模板 `g(int)`，因为它精确匹配；`g(1.0)` 选模板，因为非模板需要把 `double` 转成 `int`，而“非模板优先”只在匹配质量不差于模板时成立。MXC-10 把这套规则拆成两层：非模板是一等公民，主模板是二等公民；主模板之间按“更特化”决胜。MXC-10 还提醒，主模板一多就容易出现反直觉结果，比如 `g(&i, &i)` 会选 `g(T, T)` 而不是某个看起来更贴合指针的重载，甚至可能二义。函数模板的“偏特化”只能靠增加重载来模拟，而重载集合一复杂，可预测性就下降。

如果希望自己的版本在精确匹配时一定被选中，就不要写特化，写普通函数。反过来，一旦给某个函数模板提供了重载，就不要再给它提供特化——两者混在一起，调用点选中谁取决于主模板的比较，而不是你写特化时的直觉。这就是 EXS-07 的 Moral #1 和它的推论，CCS-66 把同一件事写成“不要特化函数模板，改用重载”。

`FixedVector<int, 4> b(a)` 之后模板计数器仍是 0，说明精确同类型走的是编译器生成的拷贝构造，成员模板没有抢走它。`FixedVector<int, 4> narrow(wide)` 的元素类型和长度都不同，才落到成员模板上，拷贝 `min(4, 6)` 个元素。赋值同理：跨类型时模板计数器加到 1，同类型再赋值时计数不变。成员模板构造函数不是拷贝构造函数，它也不会阻止编译器生成普通拷贝构造；两者都声明，才能既控制同类型拷贝，又支持兼容类型。EXC-05 引用了标准里的这条注释：模板构造函数参与重载决议，但精确同类型时非模板版本胜出。

跨长度就要定义“短的一方怎么办”，这是接口语义，不能留给实现偶然决定。示例的选择是构造时拷贝 `min(N, M)` 个、其余元素值初始化（`data_[N]{}`），赋值时只覆盖前 `min(N, M)` 个、其余保持原值。也可以选择清空、填默认值或直接禁止长度不同，但必须写进文档。另有一个容易忽略的副作用：一旦声明了任何构造函数（这里是接受 `initializer_list` 的那个），隐式默认构造函数就不再生成，所以示例显式写了 `FixedVector() = default;`。EXC-05 里“写一个空默认构造函数”的理由，在 C++11 之后用 `= default` 表达更清楚。

异常保证是另一半。`FixedVector<Element, 4>::operator=` 逐元素赋值，第三个元素抛出时前两个已经改了、后两个还是原值。前面完整输出里的 `dst = 1,2,9,9` 说明 `dst` 仍然是有效对象，可以析构、可以继续用，所以满足基本保证（basic guarantee）；但它不是“要么全改、要么全不改”的强保证（strong guarantee）。要强保证，通常得把元素放进可原子交换的动态存储，在临时对象上完成全部赋值，再用不抛的 `swap` 提交——也就是 copy-and-swap。成员数组没法原子交换，这是 EXC-05 特意指出的设计限制：异常安全不是实现细节，它会影响存储方式的选择。C++11 的移动语义和 `noexcept` 让“临时对象 + swap”更便宜，也让容器在扩容时能按移动是否 `noexcept` 决定搬移还是复制；C++20 的 concepts 可以把“源元素能赋值给目标元素”写成约束，让不兼容的类型在重载决议阶段就被拒绝，而不是实例化到 `std::copy` 里才报错。

`SmartPtr` 仍然显式声明了普通拷贝构造和拷贝赋值（这里 `= default`）。成员模板不会抑制它们，也不会替它们完成同类型拷贝；EC-45 因此要求两者都写。标准库的 `std::shared_ptr` 同时提供普通拷贝和广义拷贝，`std::unique_ptr` 用成员模板支持派生到基类的转换，但把普通拷贝删掉以保持独占语义——要不要允许同类型拷贝，是类的语义决定的，不是成员模板决定的。`explicit` 也要按内置指针的规则分配：从裸指针构造通常 `explicit`，从兼容的智能指针构造可以隐式，这样 `SmartPtr<Top> p = smartMiddle;` 像 `Top* p = rawMiddle;` 一样自然。

`Range<int>` 和 `Range<int, std::greater<int>>` 是两个类型，`static_assert` 证明了这一点；换策略就是换类型，不能运行期切换。策略类要提供什么，原先只能靠文档和命名约定：`comp(a, b)` 要能调用、返回值要能当 `bool` 用，写错名字不会在定义处报错，只会在实例化时炸出一长串错误。ESS-13 举的 `NumericSequence<num_seq>` 更典型：策略类必须提供 `calc_elems()`、`is_elem()` 这些按名字调用的成员，模板正文只是转发。C++20 的 concept 把这份约定写进了签名：`Comparator<T>` 检查 `comp(a, b)` 的返回类型，`Bad` 这种返回 `void` 的策略在 `static_assert(!Comparator<Bad, std::string>)` 处就被拒绝，不用等到实例化。`std::ranges` 的投影和比较器参数也是这个思路，只不过标准库把它们包装成了定制点对象（[第 21 章](ch21.md) 讲 concepts 本身，[第 26 章](ch26.md) 讲 range）。

## 回头看

这一章从“模板报错为什么落在实例化点”出发，看到同一条规则在不同层面的表现：类型要满足的是一组合法表达式，不是一张签名表；依赖名的语法歧义要靠 `typename` 消除，依赖基类的名字要靠 `this->`、`using` 或基类限定找回来；定制行为要么走类模板的全特化/偏特化，要么走普通函数或重载，函数模板特化不参与重载决议；成员模板只扩展转换，不会取代编译器生成的拷贝控制；非类型参数和策略模板则把配置与算法编进类型。它们防的是同一类问题：把只在实例化时才暴露的要求，误当成已经写在接口上的承诺。

C++20 以后，concepts 把隐式接口写成命名约束，`if constexpr` 和 `void_t` 减少了偏特化分派，`std::construct_at`/`std::destroy_at` 接过了手写的生命周期工具，ranges 的定制点对象避开了函数模板特化；但依赖名查找、特化不重载、模板实参推导不考虑隐式转换这些规则没有变。今天能交给语言和标准库的，是把要求写进签名、用标准设施管理生命周期、用 `static_assert` 把假设写死；仍要靠人的，是判断一个类型到底该满足哪些表达式、定制点放在类模板还是普通函数、以及成员模板要不要和普通拷贝一起声明。编译器能帮的有限：在 `-std=c++17` 下漏写 `typename`，Clang 21 只给 `-Wc++20-extensions` 警告，GCC 15 直接报错，跨编译器时不要依赖警告；同一块堆内存被 `delete` 两次这类运行时错误，ASan 能抓住，但名字查找和重载决议的错误只能靠编译器和测试。
