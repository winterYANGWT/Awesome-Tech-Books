# 第 27 章 算法：从“能跑”到“说清楚在做什么”

促销页面要列出销售额最高的三个门店。代码把全部门店放进 `std::sort`，然后取前三个：

```cpp
std::sort(stores.begin(), stores.end(),
          [](const Store& a, const Store& b) { return a.sales > b.sales; });
for (std::size_t i = 0; i != 3; ++i) show(stores[i]);
```

结果是对的，但这段代码对读者说的是“把所有门店排好”，而需求只是“找出前三名”。门店从一千家变成十万家时，多出来的那部分排序工作不会自己消失。把 `sort` 换成 `partial_sort`，调用点会直接说出“我只要前三个，而且它们要有序”；换成 `nth_element`，则说出“我只要前三名是哪几个，内部顺序无所谓”。三种写法都能跑，区别在于读代码的人要不要从循环和下标里反推意图。

算法首先是一套词汇。`partition`、`nth_element`、`partial_sort`、`lower_bound`、`accumulate` 这些名字各自带着明确的后置条件和复杂度承诺，写在调用点上，读代码的人就不必重新推导一遍循环在做什么。本章沿着“需要多少顺序、区间是否有序、结果是一个值还是一段输出”这条线，把排序、查找、归约、谓词和输出迭代器串起来；最后回到手写循环仍会犯的错：循环不变式、随机数取模和二分中点。

这些规则大多来自 C++98/03 年代的 STL 实践，但今天的写法变了不少：lambda 取代了手写仿函数和绑定器，C++20 的 ranges 算法接受整个区间和投影，C++17 还给一批算法加了并行版本。下面每一节都先看旧规则要防的问题，再看新标准把哪一部分接了过去。

## 27.1 按“到底需要多少顺序”选排序算法

排序算法最容易被当成一个开关：要排序就调 `sort`。可“排序”这个词覆盖了好几种不同的需求。只想知道哪些元素满足条件、不关心两组内部谁先谁后，是分组；只想知道第 n 名是谁、或者前 n 名是哪几个，不关心这 n 个的内部顺序，是选择；要前 n 名按顺序站好，是部分排序；要整个区间有序，才是全排序。做的功越少，能表达的信息越精确，通常也越快。

Meyers 在 ESTL-31 里把这组选择按代价排开：`partition`、`stable_partition`、`nth_element`、`partial_sort`、`sort`、`stable_sort`。CCS-86 用一句话概括成“sort just enough”：先弄清需要多少顺序，再选最便宜的那个。这个顺序不是标准规定的精确性能表，而是一个足够可靠的趋势：`partition` 只扫一遍、交换元素；`nth_element` 平均线性时间；`partial_sort` 要把前 k 个维护成有序，代价约为 `N log k`；`sort` 是 `N log N`；`stable_sort` 还要为稳定性付出额外的时间或空间。

先看分组。`partition` 接受一个谓词，把满足和不满足的元素分别聚到区间两端，返回第一个不满足的位置。它不保证两组内部的顺序，也不保证等价元素的相对次序；需要组内保持原序时用 `stable_partition`。下面的程序把申请者按“分数是否达到 80”分成两组，再分别看两组的人数和名单：

`partition` 那两行只说明“5 人通过、5 人未通过”，组内名单是程序为了打印另排的；`partition` 本身没有承诺这个顺序。接下来的 `nth_element` 把下标 2 上的元素放成全序中的第 3 个，并保证它前面的元素按比较器都不排在它后面、后面的都不排在它前面，所以前三个一定是 95、91、91 这三位；但这三个内部谁先谁后没有保证。`partial_sort` 多做一些功，前三个已经按比较器排好。`sort` 把十个元素全部排好。`stable_sort` 只比分数，两个 91 分的申请者保持输入里的先后：Ada 在 Cyd 前面。

`nth_element` 的第二、第三个参数不是“前 n 个”的结束位置，而是“第 n 个位置”。`nth_element(v.begin(), v.begin() + 2, v.end())` 保证 `v[2]` 是全序中的第 3 个（从 0 数），前两个不大于它，后面的不小于它；`partial_sort(v.begin(), v.begin() + 3, v.end())` 才是“前三个排好”。差一个下标是这类调用最常见的错误，写的时候把“位置”和“个数”在变量名里区分开，比事后调试便宜。ESTL-31 还提醒，`nth_element` 不只用来取前 k 名：取中位数就是让 `begin + size() / 2` 就位，取 75 分位就是让 `begin + size() * 3 / 4` 就位，代价远低于全排序。

稳定性只在“等价元素的相对顺序有意义”时才需要。`sort` 不保证稳定，`partial_sort` 和 `nth_element` 也不稳定，标准没有提供它们的稳定版本；`stable_sort` 稳定，但可能分配额外内存、也可能退化为 `N log² N`。如果只需要前 k 名且必须稳定，通常只能退回 `stable_sort`，或者自己给比较器加一个稳定的次序键（例如原始下标）——后者把“稳定”写进了比较规则，代价是比较器多比较一个字段，但不再依赖算法的稳定性。

这些算法对迭代器的要求也不一样。`nth_element`、`partial_sort`、`sort`、`stable_sort` 都要随机访问迭代器，`list` 用不了；`partition` 只要求前向迭代器，`stable_partition` 要求双向迭代器。ESTL-31 说 `partition` 和 `stable_partition` 都需要双向迭代器，这在 C++98 是对的；C++11 把 `partition` 的要求放宽到前向迭代器，`stable_partition` 仍需要双向。本机 libstdc++ 15 的 `stable_partition` 对 `forward_list` 也能编译（GCC 15 同样如此），但标准要求双向迭代器，别把这个实现上的宽松当成可移植保证。对 `list`，成员 `sort` 是稳定排序，直接用它；想要 `partial_sort` 或 `nth_element` 的效果，可以把迭代器或下标装进一个 `vector` 再排，这就是 27.6 要讲的索引表。直接把 `list` 交给 `std::sort` 会得到一屏模板错误：

## 27.2 查找先看区间是否有序，成员版本优先

查找的第一个问题不是“用哪个函数”，而是“区间现在是什么状态”。无序区间里没有可利用的顺序，只能从头扫；有序区间才能二分。ESTL-34 列了一组以有序为前提的算法：`binary_search`、`lower_bound`、`upper_bound`、`equal_range`，四个集合操作，`merge`、`inplace_merge`、`includes`。它们用二分或单遍归并把代价压到对数或线性，交换条件就是“输入已经按同一个比较器排好”。二分族的比较次数是对数，但只有随机访问迭代器时移动也是对数；在 `list` 这种双向迭代器上，移动仍是线性，ESTL-34 专门提醒过这一点。违反这个前提，标准不要求编译器诊断，运行时是未定义行为（undefined behavior，UB）。

比较器必须前后一致，这是最容易漏的一半。用 `std::greater<>` 把区间排成降序，查找时却用默认的 `std::less<>`，二分会在错误的方向上缩小范围。示例里先用 `is_sorted` 分别检查默认顺序和 `greater` 顺序，再用 `greater` 调 `binary_search`，把“排序和查找用同一个比较器”写成看得见的代码。标准对二分查找族的要求其实比“有序”稍弱：区间相对给定值要“已划分”（partitioned），即所有满足 `comp(element, value)` 的元素都在不满足的前面；已排序是产生这种划分的常见方式。记“有序”足够日常使用，但别把它理解成“随便什么顺序都行”。

确定区间有序之后，第二个问题是到底需要什么信息。CCS-85 用一张很短的表把它分开：只问“在不在”，`binary_search` 就够；要位置，用 `lower_bound`（第一个不小于 value 的位置）或 `upper_bound`（最后一个等价元素之后的位置）；要“在不在、有几个、分别是哪些”，`equal_range` 一次给出左右边界。`binary_search` 的名字最顺口，却常常不够用，因为它只返回一个 `bool`，拿不到位置。`equal_range` 一次给出两端，标准允许它做至多约两倍对数次的比较；实现可能用一次划分同时得到两端，也可能退化成两次二分，但调用方不必自己写两遍。

无序区间里，`find` 和 `count` 的区别也值得说清楚。`find` 命中就停，适合只关心“有没有”或“第一个在哪”；`count` 必须扫到区间末尾，因为它要数完所有匹配。示例里 `std::find(raw.begin(), raw.end(), 4)` 在无序的 `raw` 上命中，排序后 `binary_search` 才成立；这两行不是为了比较快慢，而是说明同一份数据换了顺序，可用的工具就换了。ESTL-45 把这些选择按“想知道什么”整理成一张表，核心就是先分有序/无序，再分存在性/位置/个数/全部等价元素。

`lower_bound` 的结果不能随手用 `*it == value` 验证。它按等价搜索，返回的是第一个“不小于” value 的位置；这个位置上的元素可能与 value 等价但不等（例如同一个 id、不同名字），也可能根本不存在。示例里的 `probe` 是 `{"Zoe", 42}`，`lower_bound` 指向 `{"Ada", 42}`，`*it == probe` 是 `false`，但按 `ById` 判断两者等价，所以查找其实成功了。正确的验证方式是先确认 `it != end()`，再用传给 `lower_bound` 的同一个比较器做双向比较，或者干脆用 `equal_range`：它返回的 `[lo, hi)` 天然只依赖等价关系，`hi - lo` 就是等价元素的个数。ESTL-45 推荐后者，理由是“不用记得保持两套比较逻辑同步”。

成员版本优先，是这条线上另一个独立的判断。ESTL-44 说得很直接：容器提供同名成员函数时，优先用成员版本，因为它更快，而且和容器的其他操作共享同一套“相同”的定义。`std::set<User, ById>` 的成员 `find` 走树，对数时间，用 `ById` 判断等价；`std::find` 线性扫描，用 `operator==` 判断相等。示例里 `by_id.find(probe)` 找到 `Ada`，`std::find(by_id.begin(), by_id.end(), probe)` 找不到，因为 `User` 的 `operator==` 还比较了名字。`map` 更明显：成员 `count(42)` 只看键，返回 1；`std::count` 把整个 `pair` 拿去和 `{42, "Zoe"}` 比，返回 0。`list` 的 `remove`、`unique`、`sort`、`merge` 也是成员版本更合适：它们搬节点而不是搬值，`remove` 还真的删元素，不需要再接 `erase`。完整的等价语义在[第 25 章](ch25.md)，这里只强调查找时不要把它们混用。

泛型代码里成员函数不总是可用：`vector` 没有 `find`，`list` 没有 `lower_bound`，不同关联容器的 `insert` 返回类型也不一样。C++20 的 ranges 算法给了另一条统一路径：`std::ranges::find`、`std::ranges::lower_bound` 接受整个区间，还能传投影，`std::ranges::lower_bound(users, probe.id, {}, &User::id)` 直接按 id 比较。注意投影只作用于区间里的元素，查找值仍是投影后的类型：这里要传 `probe.id`，传整个 `User` 编译不过。它仍然要求区间有序，也仍然不会替你检查；`std::ranges::contains`（C++23）和关联容器的 `contains()`（C++20）只是把“在不在”写得更短。C++14 起的透明比较器（`std::less<>`）让有序容器支持异质查找，查找 `std::string_view` 时不必先构造一个 `std::string`，这是实际开销上的改进，但不改变等价规则。

能替这条规则把关的工具不多。编译器不会因为你在无序区间上调用 `binary_search` 而警告，sanitizer 也抓不到“顺序错了”这种语义错误。可行的做法是在调试构建或测试里加 `assert(std::is_sorted(v.begin(), v.end(), comp))`，把“这个区间必须有序”写成可执行的前提；生产代码里则把排序和查找放在同一个函数或同一个类里，让比较器只有一处定义。C++20 的 concepts（例如 `std::strict_weak_order`）能检查比较器的签名，检查不了它是否真的产生全序，这一点在 27.4 还会遇到。

## 27.3 用算法表达意图，别手写循环

同一段业务逻辑，手写循环和算法组合都能得到正确结果，但读起来是两种东西。手写循环把“遍历、判断、累加、收集”压在一个 `for` 里，读的人必须同时跟踪下标、总额和目标容器；算法组合把每个动作拆成有名字的调用，`accumulate` 说“归约成一个值”，`copy_if` 说“筛选”，`find_if` 说“找第一个”，`count_if` 说“数个数”。后者的调用点更长，但每个名字都在回答“这段代码在做什么”。

ESTL-43、CCS-84 和 EXC-07 从三个角度论证同一件事。效率上，算法只对 `end()` 求值一次，库实现者还掌握容器的内部布局，能写出普通用户写不出的优化；正确性上，手写循环最容易犯的恰是迭代器失效和区间边界错误，算法把这些逻辑关进已经反复测试过的实现里；可维护性上，`transform`、`replace_if`、`partition` 这些名字本身就是文档，而 `for` 只说明“在循环”。EXC-07 还补了一个细节：用 `find` 取代逐个比较的循环，不会为每次比较构造临时对象，前提是 `operator==` 有接受“元素类型和查找键”的重载；否则算法每次比较都可能构造一个临时 `std::string`。

新标准还改变了“算法一定比循环快”的强度。ESTL-43 写作时，`end()` 的重复求值确实可能留在循环里；今天的编译器通常能把它提到循环外，range-for 也会缓存 `end()`。所以效率不再是主要理由，正确性和表达意图才是。C++17 的并行算法把“谓词不能修改共享状态、不能抛异常”变成硬约束；C++20 的 ranges 算法支持投影，`std::ranges::sort(orders, {}, &Order::cents)` 这类写法省掉了比较器；C++23 的 `std::ranges::to` 可以把视图直接物化成容器（本机 clang 21 + libstdc++ 15、GCC 15 在 `-std=c++23` 下可用）。工具方面，编译器不会因为一个可改写成 `any_of` 的循环而警告；能帮忙的是代码评审、把长循环抽成函数，以及在测试里覆盖空区间、单元素和“找不到”这三种边界。

## 27.4 比较器要内联，谓词要纯

给算法传比较器时，传函数名、函数对象还是 lambda，结果通常都对，区别在编译器能看见什么。函数名作实参时会退化为函数指针，算法模板实例化出来的形参类型是 `bool (*)(const T&, const T&)`；算法内部通过这个指针调用比较函数，编译器一般不会跨过一个运行期才知道指向哪里的指针去做内联。函数对象和 lambda 不一样，它们的 `operator()` 是类型的一部分，算法模板实例化时函数体是可见的，编译器可以对它做内联，也可以围绕它做进一步优化。

ESTL-46 用 `greater<double>` 和手写 `doubleGreater` 的对比讲了这件事，并在四个 STL 平台上测到函数对象版本更快。具体百分比依赖编译器和数据，不该当成定律；可靠的结论是机制上的：函数指针多一层运行期才能确定的间接调用，函数对象至少把函数体暴露给了编译器。`inline` 关键字也救不了函数指针——它只是允许函数在多个翻译单元里定义，是否展开仍由编译器决定，而通过指针的调用通常不在它能展开的范围里。

这里说的“内联”是优化机会，不是正确性要求。函数指针版本的结果完全正确，编译器通常也不会为此警告；只有性能剖析能告诉你这个比较器是不是热点。ESTL-46 还提到当年一些 STL 平台对 const 成员函数指针和函数模板显式实例化的支持缺陷，函数对象绕开了这些实现问题。这些具体缺陷在今天的编译器上大多已经消失，lambda 又把“就地写函数对象”变成了默认写法，所以这一条的现代形式是：**优先让比较器的类型携带函数体，而不是让运行期的指针携带它**。

## 27.5 归约用 accumulate，写算法用输出迭代器

“把整个区间变成一个值”是另一类常见任务：求和、求积、求平均、把一组字符串的长度加起来。手写循环当然能做，但 ESTL-37 建议优先用 `<numeric>` 里的 `accumulate`，需要副作用或要同时维护多个量时用 `for_each`。`accumulate` 的名字直接说明“归约”，调用点只需要三件事：区间、初值、可选的二元操作。它只要求输入迭代器，所以可以直接接 `istream_iterator`，从流里读数求和。

`accumulate` 最容易错的地方是初值类型。它内部用初值的类型声明累加器，返回值也是这个类型；对 `double` 序列写 `accumulate(v.begin(), v.end(), 0)`，每一步加法都会截断成 `int`，最后再把结果转回 `double`。示例里正确值是 28.74，写成 `0` 得到 27。求积同理，初值要写 `1.0`，写 `0` 永远得到 0。自定义操作的形式是“当前累计值、下一个元素 → 新的累计值”，返回类型通常和第一个参数相同；如果累计值类型和元素类型不同（比如把字符串长度累加成 `size_t`），第一个参数就用累计值类型。

标准对 `accumulate` 的操作有一个容易被忽略的要求：它不应有副作用。ESTL-37 提到，有人用带计数器的仿函数在 `accumulate` 里求平均，严格说这不符合标准措辞；`for_each` 则明确允许副作用。示例里的 `Average` 用 `for_each` 累计 `sum` 和 `count`，再通过返回的函数对象取 `mean()`，这是 `for_each` 的典型用法。`for_each` 按值返回函数对象（C++11 起返回 `std::move(f)`），所以统计结果要通过成员函数取出来；如果只需要对每个元素做一件事、不关心返回值，直接忽略返回值即可。

## 27.6 忽略大小写、copy_if 和索引表各有各的写法

不区分大小写的字符串比较是一个小需求，却能把“算法组合”的几件事同时摆出来：字符级比较要先处理 `char` 的符号，字符串级比较可以用 `mismatch` 拼出 `strcmp` 式的三态返回，也可以用 `lexicographical_compare` 拼出能放进关联容器的严格弱序。ESTL-35 把这两种接口都写了一遍，理由很实际：调用方有时要“小于/等于/大于”，有时只要一个布尔谓词。

## 27.7 循环不变式、随机数和二分中点都容易写错

算法能替你处理遍历，但不能替你处理所有推理。手写循环仍然要回答“每轮开始时什么为真”，有界随机数仍然要回答“映射是否均匀”，二分查找仍然要回答“中点怎么算才不溢出”。这三件事看起来分散，实际都是同一个问题：代码能跑，不代表作者说清楚了它为什么正确。

ACC-02 建议在循环前写一句不变式：初始化让它成立，循环体末尾恢复它，循环结束时条件为假，三者合起来才能证明结果。计数循环从 0 开始、用 `i != n` 结束，退出时能推出 `i == n`，恰好处理 n 次；写成 `i <= n` 只能推出“至少 n 次”，是否多一次要看循环体怎么用 `i`。示例里的 `sum_first_n` 把不变式写在注释里，循环体只有一行，仍然值得写：读的人不必自己模拟 10 次加法。不变式不是注释越多越好，它要覆盖循环真正依赖的变量和边界；需要机器检查时再加 `assert`，两者解决的不是同一件事。

二分查找的中点是一个具体的不变式练习。ACC-13 指出，`(begin + end) / 2` 对指针可能先做一次越界的加法，对大整数下标可能溢出；写成 `begin + (end - begin) / 2`，先求距离再折半，加回去的位置仍在区间内。对数组下标就是 `lo + (hi - lo) / 2`。C++20 的 `std::midpoint` 对整数和指针都做了防溢出处理，可以直接表达“中点”；但它不接受任意迭代器，泛型代码里仍常写 `begin + (end - begin) / 2`。标准库的 `lower_bound` 已经处理了这些细节，业务代码优先调用它，别手写二分；要手写时，至少把区间要求和不变式写清楚。


`(lo + hi)` 在 `int` 里溢出是未定义行为（UB），UBSan 报 `signed integer overflow`。这类错误在测试数据小的时候完全看不见，只有边界值才会触发；用 `std::midpoint` 或先减后加，能把这一类问题从“靠运气”变成“结构上不可能”。编译器不一定会警告 `(lo + hi) / 2`，因为它不知道 `lo`、`hi` 的取值范围；UBSan 和边界测试才是这里的工具。

ACC-10 讲的是另一类“看起来能跑”的代码：`rand() % n`。它有两个问题。第一，许多伪随机数生成器的低位质量差，连续结果可能交替奇偶，取模到 2 就会交替出 0 和 1；第二，`RAND_MAX` 不一定被 n 整除，余数的概率不均等。ACC 举的例子是 `RAND_MAX = 32767`、`n = 20000`：`rand() % 20000` 得到 10000 的值有两个（10000 和 30000），得到 15000 的值只有一个，前者出现的概率是后者的两倍。真实引擎的范围通常大得多，偏差比例小，但机制相同。

这三条规则并没有因为新标准而消失。`std::midpoint` 只是把中点写对的工具，循环不变式仍然只能写成注释或 `assert`，`uniform_int_distribution` 也只是把分布写对的工具；用不用、用对没有，仍然取决于写代码的人。UBSan 能抓住溢出，测试能抓住边界，代码评审能抓住“这个循环到底跑几次”，但没有一个开关能替你把这三件事一起关掉。

## 回头看

这些规则合起来，说的是一件事：算法调用是一个带前提和承诺的句子。`sort` 承诺全序，`partial_sort` 只承诺前 k 个有序，`nth_element` 只承诺第 n 位就位；`lower_bound` 承诺对数次比较，前提是区间已按同一个比较器划分；`accumulate` 承诺把区间折成一个值，前提是操作不偷改状态。写代码的人只要选错句子，或者漏掉前提，程序仍然能编译、常常也能跑，但读代码的人已经无法从调用点知道它到底保证了什么。

C++11 的 lambda、C++17 的并行重载、C++20 的 ranges 和 concepts 把写法变短了，也把一部分检查前移到了编译期：ranges 算法会把迭代器类别不对、投影类型不匹配、谓词签名不对变成 concepts 不满足的诊断；经典算法没有这层约束，仍可能只给出一屏模板错误。但它们拦不住“区间其实没排序”“比较器不是严格弱序”“谓词藏了可变状态”“循环少跑一次”“中点加法溢出”这些语义问题。这些问题仍然要靠写作者把前提写进类型、注释、断言和测试里；工具只能在运行期抓住其中一部分，剩下的由代码评审和边界用例负责。
