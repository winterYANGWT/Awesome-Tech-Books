# 第 21 章 concepts：把模板要求写在接口上

一个模板对类型有什么要求，编译器不会从声明里读出来，只会到函数体里逐条试。下面这个 `label` 只对带 `name()` 的类型有意义，签名却是“接受任何 `T`”：

```cpp
template <typename T>
std::string label(const T& value) {
    return value.name();          // 要求藏在函数体里
}

struct Order { std::string id; };
label(Order{"A-1"});              // 能编译到这里，才在函数体里报错
label(42);                        // 同样，错误指向 value.name()
```

调用方看到的是一个无约束的接口，编译器也只能等实例化到函数体时才发现 `Order` 没有 `name()`；如果 `label` 再转调几层模板，错误就会落在某一层实例化的内部，和调用点隔得很远。模板的隐式接口（implicit interface）本来就是这么工作的：类型是否合格，由函数体里出现的表达式决定，而不由声明决定（EC-41 讲的正是这一点，见[第 20 章](ch20.md)）。

C++20 的 concepts（概念）把这份要求从函数体搬到模板头部。约束成了声明的一部分：调用方能看到，编译器在重载决议阶段就会检查，不满足的类型根本不会进入函数体。这也是 EC-18 说的“让接口易于正确使用、难以错误使用”在模板上的版本：类型要求不再靠文档和实现暗示，而是接口本身的一部分（EC-18，见[第 2 章](ch02.md)）。要求写出来之后，剩下的是怎么写得准、怎么组合、怎么和旧代码共存——以及为什么 C++11/14 时代那些绕开通用引用（universal reference，也就是转发引用）重载的技巧，今天大多可以换成一条 `requires`。

## 21.1 从 SFINAE 到 requires：约束应该写在接口上

先看一个具体的模板。`add` 对能相加的类型才有意义，可是最直观的写法把要求留在函数体里：

```cpp
template <typename T>
T add(const T& lhs, const T& rhs) {
    return lhs + rhs;
}
```

调用 `add(Order{...}, Order{...})` 时，错误会指向 `lhs + rhs`；`add` 本身仍然是“接受任何类型”的候选，甚至可能在其他重载里制造意外的匹配。C++11/14 时代的标准库和大量库代码用 SFINAE（substitution failure is not an error，替换失败不是错误）解决这个问题：把条件塞进返回类型或默认模板实参，让条件不满足时这个模板在重载决议中“消失”，而不是让函数体报错。C++17 的 `std::void_t` 又让检测表达式的写法短了不少，但它没有改变一件事——要求仍然藏在模板的某个角落里。

`legacy::add` 和 `modern::add` 都接受 `int`、`double` 和 `std::string`，因为它们检查的是同一个表达式 `lhs + rhs`。`static_assert(requires { ... })` 在编译期确认这两个接口都接受 `int`；`requires` 表达式本身不会调用函数，只检查表达式是否良构。

requires 子句可以写在模板参数列表之后、函数返回类型之前，也可以写在函数声明的末尾；前者更常见，因为要求紧挨着模板参数。约束不满足时，这个候选在重载决议里被淘汰，不会实例化函数体——这正是 SFINAE 想达到的效果，只是现在由语言直接支持。C++20 还允许把概念直接写在类型参数的位置（`template <Number T>`），以及用缩写函数模板 `void f(Number auto x)` 省掉 `template` 头；两种写法都要求编译器支持 concepts。本书环境里 Clang 21 + libstdc++ 15 和 GCC 15 都支持 C++20 concepts，示例用 `-std=c++20` 编译。

SFINAE 能工作，靠的是语言的一条规则：模板替换过程中，如果某个类型或表达式在“立即上下文”里不合法，这个候选被静默移除，而不是让整个程序报错。`std::enable_if_t<B, T>` 在 B 为假时没有 `type`，正好触发这种移除；`void_t<...>` 在表达式不合法时同样让别名替换失败。也正因为如此，条件必须写在签名能触发替换的位置：返回类型、模板参数、默认模板实参都行，函数体里不行。requires 子句把这条规则收进了约束系统：候选是否可行由约束是否满足决定，函数体仍然只在候选胜出后实例化。

requires 子句可以写成 `template <typename T> requires C<T>`，也可以写成 `template <C T>`；对函数模板，C++20 还允许把约束放在函数声明末尾（`template <typename T> void f(T) requires C<T>`），成员函数需要按条件约束时这种形式很有用。不在任何模板里的普通函数不能带 requires 子句；但类模板的非模板成员函数可以写尾置 requires 子句（`void reserve(std::size_t n) requires Resizable<Storage>;`），用类模板实参决定这个成员是否可用，这是 C++20 之前要靠 `enable_if` 加默认模板实参才能做到的事。缩写函数模板 `void f(C auto x)` 只是 `template <C T> void f(T)` 的简写，参数多、约束复杂时，显式的模板头更好读。

旧写法并没有立刻消失。维护 C++17 代码库时，`std::enable_if`、`std::void_t` 仍然是主要工具，而且它们没有运行期开销；如果暂时不能升级标准，至少可以把条件提取成一个有名字的 `constexpr` 布尔变量或别名，让接口比一屏模板实参清楚一点。新代码则没有理由再把约束藏进返回类型：概念可以复用、可以组合，也能被 `static_assert` 和文档直接引用。迁移时还要记住，concepts 检查的是表达式能不能编译，不检查表达式算得对不对；这一点在 21.3 节会用一个“能相加但算错”的类型说明。

## 21.2 concept 怎么定义、组合并参与重载决议

概念（concept）的定义形式很固定：一个 `template` 头，一个名字，等号右边是一个编译期布尔表达式，通常写成 requires 表达式。requires 表达式不执行任何代码，它只问“这些表达式写在函数体里能不能编译”：

```cpp
template <typename T>
concept Sized = requires(const T& value) {
    { value.size() } -> std::convertible_to<std::size_t>;
};
```

`requires(...)` 括号里的参数只在这个表达式的检查里可见，不是函数参数；花括号里的每条语句都是一项要求。`value.size()` 是简单要求，`{ value.size() } -> std::convertible_to<std::size_t>` 是复合要求（compound requirement）：表达式必须合法，结果还必须能转换成 `std::size_t`。`typename T::key_type;` 这类写法是类型要求，用来检查嵌套类型是否存在。一个概念可以只检查一个表达式，也可以把多个要求放进同一个 requires 表达式。

MXC-04 当年讨论过用 traits 而不是继承来分类模板参数：给外部类型补上类型别名和常量，再按 traits 特化选实现。concept 把“这个类型具备哪些操作”的判断直接变成接口约束，读起来更直接；traits 仍然适合补充类型信息，两者不是替代关系（MXC-04，见[第 20 章](ch20.md)）。ESS-13 的策略模板靠命名约定要求策略类提供 `comp(a, b)` 之类的成员，concept 可以把这些约定写成可检查的约束，让错误从实例化深处回到接口（ESS-13，见[第 20 章](ch20.md)）。

多个概念可以用 `&&`、`||`、`!` 组合。真正影响重载决议的是合取：`Reportable<T>` 如果定义成 `Printable<T> && Named<T>`，那么满足 `Reportable` 的类型一定满足 `Printable`，约束 `Reportable` 比 `Printable` 更严格。两个重载都可行时，编译器按约束的包含关系选出更严格的那个，和声明顺序无关。

`||` 的方向相反：它把约束放宽。`A || B` 不会比 `A` 更严格：只满足 `A` 的类型同时满足两者，重载决议在 `A` 和 `A || B` 之间会选前者。写重载时不要把 `||` 当成“更具体”的标记，它通常只是一个更宽的入口。真正让约束变严格的是 `&&` 串起来的命名约束。

requires 表达式里的参数（例如 `requires(const T& value)` 里的 `value`）只是检查用的假设对象，不会真的构造一个 `T`；所以写 `requires(T value)` 并不要求 `T` 可默认构造。`typename T::key_type;` 检查嵌套类型是否存在，`{ expr } noexcept;` 检查表达式不抛异常，`{ expr } -> C;` 检查返回类型满足概念 `C`；这些要求可以混在同一个 requires 表达式里。概念定义本身不能被特化，也不能显式实例化；要加条件就再定义一个概念，用 `&&` 把旧概念接上。概念还能直接用在 `if constexpr` 和 `static_assert` 里，因为它们的结果就是编译期 `bool`。

概念可以有多个模板参数，例如“能从 `From` 转换到 `To`”可以写成两个参数的概念；参数顺序要按读起来自然的方式安排，标准库的 `std::derived_from<Derived, Base>` 就是先写派生类、再写基类。概念不是类模板，不能偏特化或全特化，也不能像变量模板那样显式实例化；组合是扩展概念的唯一正路。

概念也可以直接写在类型参数的位置：`template <Sized T>` 和 `template <typename T> requires Sized<T>` 等价；`void print(Sized auto const& value)` 是缩写函数模板，编译器替你补一个 `template` 头。缩写形式适合简单的单参数接口，参数一多、约束一复杂，显式的 `template` 头更容易读。所有这些都需要 C++20；本书的 Clang 21 + libstdc++ 15 和 GCC 15 都支持，编译时用 `-std=c++20`。概念本身没有运行期开销，约束在编译期检查完就消失。

## 21.3 标准 concepts 够用，迁移要分三步

自己动手定义概念之前，先看 `<concepts>` 里已经有什么。`std::same_as` 检查两个类型完全相同，不做隐式转换；`std::convertible_to` 检查能隐式转换；`std::constructible_from` 在 `is_constructible` 之上还要求被构造的类型可析构；`std::integral` 和 `std::floating_point` 把数值类型分成两组（`integral` 包括 `bool` 和字符类型）；`std::derived_from` 检查公开、无歧义的继承；`std::invocable` 检查“能不能用这组实参调用”，`std::predicate` 在此之上要求返回值能当布尔值用。还有 `std::regular`、`std::semiregular`、`std::totally_ordered` 这些描述一整组操作的 concept，以及 `<iterator>` 和 `<ranges>` 里的 `input_iterator`、`random_access_iterator`、`range` 等。标准库已经覆盖的常见要求，不要重新发明一个同名概念；自定义概念应当表达业务或库特有的约束。

这些 concept 不是孤立的检查项，标准库自己就用它们拼更上层的概念：`std::sortable` 由迭代器概念和比较概念组合而成，`std::ranges::range` 又建立在 `begin`/`end` 表达式上。自己写库时也应优先复用这些零件，而不是重新检查一遍 `operator<` 或 `size()`；标准 concept 的命名和包含关系已经被库作者考虑过，组合起来更容易参与重载决议。需要注意的是，`std::equality_comparable`、`std::totally_ordered` 检查的是一组相关运算都存在、结果能当布尔值用，不是它们的结果是否满足数学公理；`std::regular` 也一样，结构检查和语义契约是两回事。

迁移 C++17 的 SFINAE 代码可以分三步。第一步处理接口：把返回类型或默认模板实参里的 `enable_if` 条件提出来，写成 concept 或 requires 子句，优先用标准 concept；这一步决定调用方看到什么。第二步处理实现细节：原来用 SFINAE 在几个辅助重载之间做选择的代码，可以换成 `if constexpr`、普通重载或带约束的辅助函数；只在一个实现文件里用、调用方永远看不到的 `enable_if` 不必急着改，它不影响接口。第三步处理错误信息：在函数体里用 `static_assert` 补上“类型必须能构造出 `std::string`”这类语义前提，或者把前提写进 concept，让错误在接口处就出现。EMC-27 提醒过，成员初始化列表在构造函数体之前执行，写在函数体里的 `static_assert` 可能排在长串模板错误之后；能放进 requires 子句的前提，就不要留到函数体。

具体到类型工具，`std::is_integral_v<T>` 对应 `std::integral<T>`，`std::is_base_of_v<B, D>` 对应 `std::derived_from<D, B>`（注意实参顺序反过来），`std::is_constructible_v<T, Args...>` 对应 `std::constructible_from<T, Args...>`，`std::is_convertible_v<From, To>` 对应 `std::convertible_to<From, To>`。但不是机械替换：`std::same_as` 是概念，可以直接放在模板头上，`std::is_same_v` 是变量模板，要包一层 requires 子句；`std::derived_from` 比 `is_base_of` 多要求公开且无歧义的转换，私有继承的类型在旧 trait 下为真，在新概念下为假。迁移前先确认原代码到底想表达哪一个。

迁移时还要注意兼容性。C++17 代码库没有 concepts，`std::enable_if` 和 `std::void_t` 仍然要保留；可以用 `#if` 按标准版本切换两套声明，也可以先只在新代码里用 concepts。不要在同一组重载里一半用 `enable_if`、一半用 requires 子句来表达同一个条件，那会让“哪个候选被淘汰”更难读。本书环境里 Clang 21 + libstdc++ 15 和 GCC 15 都支持这里用到的 C++20 concepts；示例用 `-std=c++20` 编译，不需要额外库。

`record(7)` 走 `int` 重载，因为非模板函数和模板同样精确时非模板优先；`record(short{7})` 却走了转发重载。原因是 `T&&` 对 `short` 推导出 `T = short`，参数类型正好是 `short&&`，属于精确匹配；而 `int` 重载需要一次整型提升。精确匹配胜过提升，转发重载赢。字符数组也一样，`T` 推成 `const char(&)[6]`，转发重载不需要先构造 `std::string`。如果另一个重载是 `const std::string&`，非 const 左值 `std::string` 同样会被转发重载抢走：`T` 推成 `std::string&`，比需要加上 const 的引用更匹配；只有 const 左值才会回到非模板重载；输出里 `draft` 走转发重载，`invoice` 走 `const string&` 重载。Meyers 在 EMC-26 里把这种参数叫“C++ 里最贪婪的函数”：它能替几乎任何实参实例化出一个精确匹配，所以一旦和别的重载放在一起，抢走调用几乎是默认结果。

构造函数更麻烦，因为拷贝构造和移动构造是编译器生成的，模板转发构造会和它们一起参与重载。`Person p("Nancy"); Person q(p);` 里 `p` 是非 const 左值：转发构造推导出 `T = Person&`，参数是 `Person&`；拷贝构造的参数是 `const Person&`，要把 `p` 加上 const 才能匹配。转发构造更精确，于是“用一个 Person 拷贝另一个 Person”走进了转发构造，接着在成员初始化列表里试图用 `Person` 构造 `std::string`：

错误最后落在 `std::string` 的构造函数列表里，`Person` 自己的接口看起来完全正常。换成 `const Person cp(...); Person r(cp);`，拷贝构造反而会赢：两者都能精确匹配，非模板的拷贝构造优先。右值 `Person s(std::move(q))` 也走移动构造，理由相同。继承会把问题再放大一层：派生类的拷贝构造按常规写 `: Person(rhs)` 时，`rhs` 是 `SpecialPerson`（或本例的 `Employee`），基类的转发构造对它是精确匹配，而基类拷贝构造需要派生到基类的转换，于是基类部分又走了转发构造。EMC-26 的结论很直接：能不对通用引用做重载，就不要做；尤其是完美转发构造函数。

EMC-27 列出的替代方案，可以按“还要不要完美转发”分成两组。第一组放弃完美转发：给不同用途的函数起不同名字（构造函数不能改名，所以这条对构造函数无效）；参数改回 `const T&`；或者按值传递再 `std::move`。改名最简单，调用点也最清楚；`const T&` 行为可预测，代价是右值和字面量可能多一次临时对象；按值传递对“反正要拷贝一份”的类型常常足够好。`Person(std::string name)` 加 `Person(int idx)` 的重载集合里没有模板，`short` 和 `int` 都走 `int` 重载，字符数组隐式构造 `std::string`。代价是字面量先构造临时 `std::string`，再移动进成员；传左值 `std::string` 时则是拷贝进形参、再移动进成员。`const std::string&` 版本对右值实参也只能拷贝进成员，省掉形参那一次移动，但对左值仍是一次拷贝。哪个更划算取决于调用方传左值还是右值、移动是否便宜，不能笼统地说按值一定更快；EMC-27 推荐它，是因为它让重载集合简单，而不是因为它永远最优。

第二组保留完美转发：标签分派（tag dispatch）和 `enable_if` 约束。

条件有两项：`!std::is_base_of_v<Person, std::decay_t<T>>` 排除 `Person` 和它的派生类，`!std::is_integral_v<std::remove_reference_t<T>>` 把整型留给 `int` 重载。这里不能图省事写成 `!std::is_same_v<Person, T>`：`T` 从非 const 左值推导出来是 `Person&`，`is_same<Person, Person&>` 为假，模板仍然启用，劫持照旧。`is_base_of_v<Person, Person>` 为真，所以用 `is_base_of` 连“自身”一起排除，不需要再写一次 `is_same`；`decay_t` 对字符数组得到 `const char*`，对 `Person&` 得到 `Person`，正好适合这项判断。`std::decay_t` 去掉引用和 cv 限定（还会把数组和函数退化成指针），`std::remove_reference_t` 只去引用；前者用于“这是不是 Person”，后者用于“这是不是整型”。这两项都满足时 `enable_if_t` 才是 `void`，构造函数模板才存在；不满足时它从重载集合里消失，拷贝构造或 `int` 构造接手。输出里非 const 左值走拷贝、`short` 走 `int`、派生类的拷贝和移动都回到基类对应的构造，符合预期。代价是声明很难读，条件写错时诊断也难懂；EMC-27 把这套写法留到最后不是没有原因。

`PersonSource` 直接读作“能作为 Person 的名字来源”：不是 Person 或其派生类、不是整型、并且能构造 `std::string`。enable_if 版本只排除了前两类，像 `double` 这样的实参仍会进入转发构造，然后在 `std::string` 构造处失败；`PersonSource` 把“能构造目标类型”也写进接口，非法实参在重载决议阶段就被挡住。`std::derived_from` 比 `std::is_base_of` 更严格，它要求公开且无歧义的继承；`std::constructible_from<std::string, T>` 取代了原书在函数体里写的 `static_assert(std::is_constructible<...>)`，而且检查发生在重载决议阶段，不会等到成员初始化列表之后才报错。约束写在 `template <PersonSource T>` 上，调用方在声明处就能看到要求；条件不满足时，诊断会指出是哪个 concept 没满足，而不是一串 `enable_if` 模板实参。

这段代码里 `Person` 只做了前置声明，`PersonSource` 却已经能写；约束的检查发生在构造函数模板被使用、`Person` 已经完整的时候，所以不会读到不完整的基类信息。概念可以先定义、在头文件里复用，具体类型可以稍后完整定义，这一点比把条件塞进一长串 `enable_if` 更适合库接口。

这几种写法今天怎么选？如果接口本来就不需要完美转发，改名、`const T&` 或按值传递仍然最省心；如果确实要把字面量、右值原样送进容器，优先用 concept 约束转发构造函数，把“排除自身和派生类、排除整型、能构造目标类型”一次写清。tag dispatch 在 C++17 之后主要留给“按类型标签选择实现”的库代码，`if constexpr` 能在函数体里完成的分支就不必再开一组 `Impl` 重载；`enable_if` 则留给还要兼容 C++17 的代码。EMC-27 的“部分过时”不是说它列的技巧错了，而是说其中大部分在 C++20 有了更直接的替代：concept 能表达同样的条件，诊断更好，也不会把要求藏进返回类型。

最后别忘了效率与可读性的取舍。完美转发少一次临时对象，但它把类型要求推迟到实例化，调用方传错时的错误更深；`const T&` 或按值传递可能多一次构造或移动，却让接口和重载集合都简单。Meyers 在 EMC-27 末尾的判断是：通用引用通常有性能优势，但可用性往往更差；不是性能敏感的地方，简单写法更划算。这句话在 concepts 时代仍然成立，只是“简单写法”里多了一个选择——把约束写成一句能读的 concept。

## 回头看

把这几节连起来看，concepts 解决的是“模板的要求没有出现在接口上”这个老问题。SFINAE 时代的 `enable_if`、`void_t` 能让错误的类型在重载决议里消失，但条件是模板实参的一部分，调用方和诊断都只能绕着看；concepts 把同一条件变成声明的一部分，还能组合、命名、复用到 `static_assert` 里。代价是概念只认表达式：`Ledger` 的 `operator+` 通过 `Addable` 检查却做减法，编译器不会替业务语义把关，测试和命名仍然要自己负责。

EMC-26/27 讲的是同一件事的另一面：通用引用对几乎任何实参都能精确匹配，所以它一旦和其他重载并列，就会抢走 `short`、非 const 左值和派生类基类部分的调用。改名、`const T&`、按值传递、tag dispatch、`enable_if` 都是旧时代为这件事付出的绕路成本；C++20 之后，一句 `PersonSource` 就能把“不是自身或派生类、不是整型、能构造目标类型”写在构造函数上。语言和标准库已经替我们兜住了约束的表达和检查，但“要不要完美转发”“这个 `+` 是否符合语义”“旧代码值不值得迁移”仍然要靠判断，工具只能在你写清楚之后替你检查。
