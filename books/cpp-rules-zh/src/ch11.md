# 第 11 章 构造、析构与异常：对象从哪一刻开始存在

一个工厂函数按配置返回不同传感器的指针，调用方只看见基类：

```cpp
#include <vector>

struct Sensor { ~Sensor() = default; };
struct Thermometer : Sensor { std::vector<double> samples; };

void recycle(Sensor* s) {
    delete s;          // 只执行 ~Sensor，samples 的缓冲区没有释放
}
```

这段代码能编译，`delete` 看上去也完成了工作：内存回到了分配器，`~Sensor` 正常返回，程序继续往下跑。但 `Thermometer` 那一部分从未被析构，`samples` 持有的缓冲区泄漏了；标准把这种删除称为未定义行为（undefined behavior，UB）。更麻烦的是，如果派生类成员析构时会访问自己的状态，未定义行为可能表现为数据损坏，而不是一次容易定位的泄漏。Meyers 在 EC-07 里用“部分销毁的对象”形容这种状态：基类部分死了，派生类部分还活着，却再也没人认领。

本章沿着对象的生命线走：基类的析构函数怎样决定能不能通过基类指针删除派生对象；析构函数里为什么不能抛异常；构造和析构期间调用虚函数，为什么调用不到派生类；构造函数抛异常时，哪些子对象会被销毁、对象本身为什么不算存在过；异常对象在抛出和捕获之间又被复制了几次。这些问题看起来分散，其实都围着同一条规则转：对象的生命从构造函数正常完成那一刻开始，到析构函数开始那一刻结束；在这条线之外，不要去碰对象，也不要假装它存在。

`unique_ptr<Sensor>` 的默认删除器执行的是 `delete` 一个 `Sensor*`，所以 `Sensor` 的析构必须是虚的；`shared_ptr` 则在从 `shared_ptr<Detailed>` 构造 `shared_ptr<Plain>` 时，把原来的删除器存进了控制块，之后无论谁来持有，删除的都是 `Detailed`。这个差别很容易被误读成“`shared_ptr` 可以替代虚析构”。它只保护“由派生类指针构造出来”的那条转换链；如果一开始拿到的是 `Plain*`，或者对象是用 `new Detailed` 之后赋给 `Plain*` 再交给 `shared_ptr` 的，控制块里保存的仍然是 `Plain` 的删除器，问题照旧。基类该不该有虚析构，取决于它是不是多态基类，而不是取决于智能指针的类型。多态删除只是生命周期问题的一半：按值传递或拷贝基类会切片，需要完整复制时提供虚 `Clone`，这两条分别在第 6 章（CCS-54）和第 19 章（MEC-25）展开。

反过来的错误同样常见：给不准备做基类的类型加虚析构。常见实现用 vptr 支持虚函数，加上虚析构后对象会变大（本机实测：两个 `int` 的类型从 8 字节变成 16 字节），也不再与同布局的 C 结构体兼容；一个本来能塞进寄存器的坐标类型，加上虚析构就塞不进去了。Meyers 在 EC-07 里的判断是“有多态用途的基类才需要虚析构”，而不是“所有基类都要虚析构”。标准没有给 `std::string` 和容器类型虚析构函数，从它们派生再通过基类指针删除同样是未定义行为；C++11 的 `final` 可以阻止别人继承你自己写的类，但改不了标准库的类型，能做的只是不把它们当基类。

真正危险的是第三种组合：析构函数 public 且非 virtual。它允许调用方写出 `delete base_ptr`，却不能让这次删除正确完成。CCS-50 把选择压缩成两个：允许通过基类指针多态删除，就让析构函数 public 且 virtual；不允许，就 protected 且非 virtual。Sutter 与 Alexandrescu 特别指出，NVI（非虚接口）那套“public 非虚函数转调 private 虚函数”的办法不能套到析构函数上，因为构造和析构期间做不了深层虚调用（11.3 节会看到原因）。这条规则还有一个直接的推论：编译器隐式生成的析构函数是 public 且非 virtual，所以基类必须自己写析构函数，C++11 之后写 `virtual ~Base() = default;` 就够了，不会比手写一个空的虚析构多出成本（虚函数本身的 vptr 开销仍然存在）。

## 11.2 别让异常逃出析构函数

析构函数可能在两种时机被调用：对象正常离开作用域，或者栈展开（stack unwinding）把它的作用域掀掉。MEC-11 一开头就点明，从析构函数内部无法可靠区分这两种情形，所以只能按最坏情况写：假定此刻已经有一个异常在路上。C++98 的后果是“终止或未定义行为”，C++11 把这条规则硬化了——析构函数默认带 `noexcept(true)`，异常一旦逃出就直接调用 `std::terminate`。下面的程序里并没有第二个异常在传播，`~Session` 仍然把整个程序终止了：

这段代码里，`throw` 藏在一个普通函数 `flush_failed` 后面，编译器在析构函数里只看到一次普通函数调用，不做跨函数的抛出分析，所以能安安静静地编译。如果直接写 `throw`，clang 21 会用 `-Wexceptions` 报“non-throwing exception specification but can still throw”，GCC 15 用 `-Wterminate` 报“throw will always call terminate”；两个警告都在说同一件事：这个析构函数的异常规格和函数体矛盾。警告能抓到直接写法，抓不到隔着函数调用的写法，所以不能把“没警告”当成“不会抛”。

EC-08 的原始论证是“同时有两个活动异常，对 C++ 来说太多了”。C++11 之后这个论证变得更强：不需要两个，析构函数从 `noexcept(true)` 里逃出来的那一个异常就足以终止程序。MEC-11 还给了第二个理由，这个理由和异常规格无关：异常从析构函数抛出后，析构函数停在抛出处，后面的清理步骤不会执行。一个 `Session` 析构先写日志、再结束数据库事务，日志失败就让事务永远悬着；把 `logDestruction` 包进 `try/catch` 能挡住终止，但如果 `catch` 块里的日志输出又抛，就回到原点。Meyers 的结论很干脆：日志失败就放弃日志，`catch(...)` 里不能再抛。

那么析构函数里确实有会失败的操作怎么办？EC-08 给了两个都不太舒服的选择：捕获后 `std::abort()`（或记录后让 `std::terminate` 发生），或者吞掉异常。前者适合“出错后程序无法继续”，至少避免未定义行为；后者只在程序能可靠地带着这个错误继续跑时才成立。更好的做法是把可能失败的操作挪到一个普通成员函数里，让调用方有机会处理，析构函数只做兜底：

EXC-08 从另一个方向说明了同一条约束。`new T[n]` 分两步：先调用 `operator new[]` 拿内存，再逐个调用元素的默认构造函数；只要某个构造函数抛出，已经构造完成的元素会逆序析构，内存由语言自动归还。这套清理之所以可靠，前提是元素析构不抛。`delete[]` 同理：它先逐个调用元素析构，再调用 `operator delete[]`；释放函数按标准必须不抛，唯一可能抛的就是元素析构函数。于是“元素析构绝不抛”不是风格建议，而是 `new[]`/`delete[]` 能工作的前提。

最后是 MXC-19 专门拆掉的那个“聪明办法”：用 `std::uncaught_exception()` 判断“现在有没有异常在传播”，有就走不抛的路径，没有就走可能抛的路径。Sutter 反对它有技术理由，也有设计理由。技术上的问题是它答不了“现在抛是否安全”：析构函数可能被外层的 `catch(...)` 保护着，此时抛出其实能被接住，函数却仍然返回 `true`，于是走了保守路径；反过来，当前没有异常在传播，也不等于从这个析构函数抛出去就一定有人处理。设计上的问题更根本：同一个析构函数有时抛、有时不抛，等于给错误报告两套语义，调用方必须同时应付两种，接口和心智负担都变重。

`Transaction` 构造函数里的 `typeid` 说对象就是 `Transaction`，`identify()` 也打印 `Transaction`；直到 `BuyTransaction` 的构造函数体开始执行，对象才成为 `BuyTransaction`，此后的调用才派发到派生类。析构方向相反：`~BuyTransaction` 执行完，对象退回 `Transaction`，`~Transaction` 里的虚调用又只到基类。语言对 `typeid`、`dynamic_cast` 和虚函数一视同仁，都按“当前正在构造或析构的那一层”处理。

这不是编译器偷懒，而是在保护派生类的成员。基类构造函数执行时，派生类的数据成员还没有构造；析构到基类时，它们已经销毁。如果虚调用真的派发下去，派生类函数会去读一块尚未初始化或已经失效的内存，那才是稳定的未定义行为。C++ 干脆不让这种派发发生。Sutter 与 Alexandrescu 在 CCS-49 里把这一点说成“虚函数只在虚的时候才虚”：构造和析构期间，它不虚。

`Base::init` 是纯虚函数且没有定义，构造 `Derived` 时动态类型还是 `Base`；在这套实现上，虚表里这一格指向运行期的纯虚调用检查，于是打印 `pure virtual method called` 并终止。标准把“在构造或析构期间对没有定义的纯虚函数做虚调用”定为未定义行为，libstdc++ 选择用一条明确的终止消息来实现它。这里经了一层 `call_init`，两个编译器都不再静态诊断；如果直接在构造函数里写 `init()`，clang 21 会用 `-Wcall-to-pure-virtual-from-ctor-dtor` 警告，GCC 15 也会给出默认开启的“pure virtual called from constructor”警告。警告能抓到直接写法，抓不到隔着几层函数调用的写法。

正确的做法不是想办法让虚调用“虚到底”，而是把派生类才知道的信息在构造时传给基类。EC-09 建议把 `logTransaction` 改成非虚函数，让派生类构造函数把日志内容作为参数传给基类构造函数；如果内容需要计算，就用一个 private static 辅助函数，避免碰到还没构造的成员。上面的 `BuyTransaction::create_log_info()` 就是这个角色，`Transaction::audit()` 是非虚的，因此在基类构造函数里调用完全安全。需要“整对象构造完成后再执行一次虚行为”的设计，CCS-49 列了几种办法：文档要求调用方手动调用后初始化函数；首次调用成员函数时惰性初始化，用基类里的布尔标志记住是否已经做过；利用虚基类的构造函数由最派生类选择这一规则；或者用工厂函数在 `new` 之后强制调用 `PostInitialize`。每一种都有代价：工厂方案要求派生类不暴露 public 构造函数、分配方式被限制在 `operator new`、派生类构造函数签名必须和工厂匹配；惰性初始化把错误从构造期推迟到第一次使用。C++11 的 `std::make_shared` 让工厂写法在异常安全上更省心（一次分配、配对释放），但没有消除这些设计约束。

新标准没有改变这条规则。`override` 和 `final` 只检查覆盖关系，`= default`/`= delete` 只影响特殊成员函数，C++20 的 concepts 只能约束类型参数，都不能让构造期间的动态类型提前变成派生类。能改变的只有写法：把“构造后必须执行的虚行为”做成显式的两阶段协议，或者干脆用组合代替继承，让需要初始化的部分成为一个成员，由成员自己的构造函数负责。后一种做法通常更容易保证异常安全，也不需要和虚派发的时机较劲。

## 11.4 构造失败意味着对象从未存在

MXC-17 把对象的生命线画得很清楚：生命周期从构造函数正常完成、返回调用方的那一刻开始，到析构函数开始执行的那一刻结束。构造函数只有两种结局——正常走到末尾（或执行 `return`），对象存在；以异常退出，对象从未存在。没有“构造了一半的对象”这种状态，也没有“先构造、发现不对再补一个析构”的余地。语言不会为失败的对象调用析构函数，因为压根没有对象可析构；它只会销毁那些已经构造完成的基类子对象和成员子对象。显式调用析构、再在同一块存储上 placement new 的边界属于另一个话题，见第 6 章（EXC-40）。

这正是构造函数报告失败只能用异常的原因。构造函数没有返回值，也没有一个合法的“失败但对象可用”状态可以返回；设置一个 `ok_` 标志再提供 `IsOK()` 的两阶段构造，把检查责任推给每个调用方，忘检查就得到半个对象。MXC-18 把这种做法称为过时的、危险的、繁琐的，并且明确说它不比抛异常更好。需要“可选成员”时，正确做法是用指针或 Pimpl 把可选部分放到对象外面，用空指针表示缺失；基类子对象没法这样处理，因为基类不能被 Pimpl 掉，这也是少用继承的一个理由。

那能不能用 function try block 把基类或成员构造抛出的异常吞掉，让构造函数正常返回？MXC-18 的答案是不能。构造函数的 function try block 的 handler 必须以抛出结束，正常写法有三种结果：`throw;` 重抛原异常；抛另一个异常，替换原异常；走到 handler 末尾，此时标准要求自动重抛原异常。`return;` 在 handler 里不合法。原因还是对象生命周期：基类或成员构造失败时，整个对象的构造必须失败，语言不可能让一个没有构造完成的对象进入“可用”状态；已经构造的子对象也已经自动销毁，handler 里引用任何非静态成员或基类都是未定义行为（clang 21 会对此给 `-Wexceptions` 警告，GCC 15 不警告，但标准说的是未定义行为，编译通过不代表能这么写）。handler 能做的只有翻译异常、记录日志这类不影响对象状态的事。

`Connection` 的 handler 把 `runtime_error` 翻译成 `ConnectionError`，调用方看到的是新类型；`FallThrough` 的 handler 只记录、不抛，走到末尾后原异常被自动重抛，调用方仍然捕获 `runtime_error`。两个例子都说明 function try block 不是“构造函数的 catch”：它接不住失败，只能改写失败的表现形式。MXC-18 因此说构造函数 function try block 唯一有价值的用途是翻译基类或成员构造抛出的异常（顺带记录日志），析构函数和其他函数的 function try block 几乎没有实用价值；普通函数里能捕获的东西，函数体内的普通 `try` 块同样能捕获。

还有一个和异常规格有关的后果。构造函数的 `noexcept` 必须覆盖所有基类和成员可能抛出的异常；如果构造函数声明了 `noexcept`，而某个子对象的构造函数真的抛出，C++11 起直接 `std::terminate`，不再经过 `std::unexpected`（标准在 C++17 移除了 `std::unexpected` 和 `std::set_unexpected`，libstdc++ 15 仍保留为 deprecated）。反过来说，只有当所有子对象都保证不抛时，才能诚实地给构造函数加 `noexcept`；一个空的 `throw()` 在 C++98 里也是同样的谎言。C++11 的委托构造函数不改变这套规则：目标构造函数抛出时，异常同样传给委托方，委托方的 function try block 也只能翻译，不能吞掉。

C++26 采纳了 contracts（契约，P2900），给前置条件、后置条件、断言一套语言级语法。C++26 最终采用的语法是写在函数声明后面的 `pre(...)`、`post(...)` 和语句 `contract_assert(...)`。本机实测：clang 21 没有 `-fcontracts`；GCC 15 的 `-fcontracts` 实现的是更早的属性语法 `[[pre: ...]]`，不认 `pre(...)`，所以本书环境里没有可以验证 C++26 契约的编译器。契约和构造失败如何交互（违反前置条件时是终止、继续还是抛异常，取决于构建时选择的求值语义）需核实；在本书以 C++20 为基准的范围内，构造函数报告失败的手段仍然只有异常。今天写构造函数，比较稳妥的顺序是：先把每个资源交给一个成员对象管理（RAII），让成员构造失败时自动清理；构造函数体里只做那些不会失败、或者失败后能安全抛出的收尾工作；需要可选部分就用指针或 Pimpl；不要提供 `IsOK()` 之后再让调用方补救。

## 11.5 异常按值抛出、按引用捕获，重抛只写 throw;

MEC-12 把 `throw` 和函数传参、虚调用放在一起比较，结论对写过 Java 或 C# 的人不太直观：异常对象总是被复制，复制的类型由操作数的静态类型决定；`catch` 的匹配只做极少的转换，并且按源码顺序“先到先得”。函数传参可以按引用绑定原对象，虚调用按动态类型选最合适的覆盖版本；异常在抛出点不绑定原对象，捕获匹配也不做“最佳匹配”。

MEC-13 把三种捕获方式摆在了一起。按指针捕获看起来最省：只复制一个指针，不复制对象。但它把生命周期问题推给了捕获方：抛局部对象的地址，`catch` 拿到的是悬垂指针；抛 `new` 出来的对象，捕获方不知道该不该 `delete`——删除可能重复释放，不删一定泄漏。标准异常（`std::bad_alloc`、`std::bad_cast` 等）本身是对象而不是指针，按指针捕获根本匹配不上。按值捕获没有删除问题，但如果捕获基类就会切片，还多一次复制。按引用捕获避开了前两者的全部问题：只复制一次异常对象，没有切片，虚函数正常派发，也不需要判断所有权。今天写 `catch (const T&)`，需要修改异常对象时写 `catch (T&)`；异常对象是临时对象，但标准允许它绑定到非 const 左值引用，这一点和普通函数传参不同。

捕获的匹配规则也和重载决议不同。`catch` 不做算术转换、用户定义转换，也不做 `int` 到 `double` 这类标准转换；只允许标准里那几类指针和继承转换，例如派生类到基类、任意对象指针到 `const void*`。所以 `throw 42` 不会被 `catch (double)` 接住。更隐蔽的是顺序：`catch` 子句按出现顺序逐个尝试，第一个能匹配的就执行；基类子句放在派生类前面，派生类子句永远不可达。MEC-12 把这总结成“异常处理是 first fit，虚函数是 best fit”。编译器能看出这种顺序问题时会给警告：

## 回头看

这五节守的是同一条边界：构造函数完成之前、析构函数开始之后，对象都不存在，任何“它还活着”的假设都会落空。基类的析构方式决定了能不能通过基类指针删除派生对象；析构函数的 `noexcept` 决定了清理途中还能不能抛；构造和析构期间的虚调用边界保护着尚未构造或已经销毁的派生成员；构造失败时语言只销毁已完成的子对象，`function try block` 只能翻译异常；异常对象在抛出点按静态类型复制，捕获方式决定了会不会再切一次。把这些放在一起看，EC-07 的“部分销毁”、EC-09 的“虚函数不虚”、MXC-17 的“对象从未存在”其实是同一条生命周期规则在不同阶段的表现。

C++11 以后，语言替我们兜住了一部分：析构默认 `noexcept`，让“析构不抛”从纪律变成终止保证；`= delete` 让基类能干净地挡住派生类的隐式特殊成员；`std::exception_ptr` 让异常可以延迟重抛而不丢动态类型；C++17 的 `uncaught_exceptions` 让 scope guard 能区分正常退出和栈展开；C++20 的 destroying delete 让类可以接管删除表达式。但语言没有替我们决定基类要不要支持多态删除，没有让 function try block 吞掉构造失败，也没有让 `delete[]` 对会抛的析构函数给出安全语义。剩下的仍然靠写法：基类按 CCS-50 二选一，析构只做不抛的清理、把可失败的操作留给显式 `close()`，构造期间需要派生信息就往上传参，异常按值抛、按引用捕、重抛只写 `throw;`。工具能提前发现其中一部分——clang 的 `-Wdelete-non-abstract-non-virtual-dtor`/`-Wdelete-abstract-non-virtual-dtor`、GCC 的 `-Wdelete-non-virtual-dtor`、clang 的 `-Wexceptions` 与 GCC 的 `-Wterminate`（catch 顺序问题两者都用 `-Wexceptions`），ASan 的 `new-delete-type-mismatch`，以及 clang-tidy 的 `cppcoreguidelines-virtual-class-destructor`——但它们都要求代码先写出某种形状，设计层面的选择仍然在人这边。
