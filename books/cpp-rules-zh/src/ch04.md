# 第 4 章 对象什么时候才算存在：初始化、顺序与静态对象

`Employee` 的构造函数初始化列表读起来是从上到下：先 `first_`，再 `last_`，最后拼出 `email_`。实际执行不是这个顺序。

```cpp
class Employee {
public:
    Employee(std::string first, std::string last)
        : first_(std::move(first)), last_(std::move(last)),
          email_(first_ + "." + last_ + "@example.com") {}
private:
    std::string email_;          // 声明在最前，实际最先构造
    std::string first_, last_;
};
```

成员按类定义里的声明顺序构造，`email_` 声明在最前面，所以它最先构造，此时 `first_`、`last_` 还没有值。读它们就是未定义行为（undefined behavior，UB）；构造函数定义在另一个 `.cpp` 时，这个错误更难看出来。

对象的“存在”不是从写下变量名那一刻开始，而是从它的构造完成那一刻开始。本章沿着这条线看几种常见的错位：变量定义得太早或太晚、初始化列表和声明顺序不一致、`()` 与 `{}` 被解析成别的东西、把赋值当成初始化、跨翻译单元（translation unit）的全局对象互相等待，以及一行声明里藏着的多个对象。

## 4.1 使用前初始化，并且尽量晚定义

Meyers 在 EC-04 里先承认 C++ 的初始化规则“反复无常”：同样是 `int x;`，写在函数里和写在命名空间作用域，是否清零并不一样。他的建议不是背下所有规则，而是内置类型一律手动给初值。Sutter 与 Alexandrescu 在 CCS-19 里把这条说成纪律：变量在定义处就要有确定初值。理由不是清零花不了多少时间，而是读取未初始化的值就是 UB；更麻烦的是它经常不崩溃——内存里的位恰好合用，程序能跑几个月，换个调用上下文、重编译或改动别处才以间歇性故障出现。

内置类型的局部变量是重灾区。`int timeout;` 只分配存储，不写值；`new int` 也一样，而 `new int()` 和 `int timeout{};` 才做值初始化。类类型看起来安全些，但构造函数漏掉一个内置类型成员时，这个成员同样没有初值，`std::string` 这类成员则会被默认构造。C++11 的默认成员初始化器（default member initializer，NSDMI）让成员可以在声明处写 `int timeout_ = 30;` 或 `int timeout_{30};`，漏写的风险小了很多，但它只负责“没在初始化列表里提到”的成员，不能替代构造函数该做的初始化。

“使用前初始化”还有一半是“别定义得太早”。EC-26 和 CCS-18 从两个方向说同一件事。EC-26 算的是构造和析构的成本：带构造函数、析构函数的对象，控制流一进入它的作用域就构造，离开就析构；如果函数在用到它之前就抛异常，这两次开销都白付。CCS-18 算的是理解成本：生命周期超过需要的变量让读者必须跟踪它什么时候被改、哪一次修改才有效，还会把名字留在过大的作用域里。两份账合起来指向同一个写法：等到能给出有意义的初值、并且马上就要用的时候再定义。

把这两条放在一起，会发现它们并不矛盾。CCS-19 要求定义处有初值，CCS-18 要求定义贴近使用点；如果先声明 `Payload p;`，等检查通过后再 `p = Payload(...)`，定义和赋值之间就留出了一段空档，既多了一次默认构造，也正好是 CCS-19 警告的那种“先声明、以后再说”。晚定义不是把初始化推后，而是让定义和初始化重新重合。

这条警告不是保证：编译器只在对控制流看得足够清楚时才报，跨函数、经过指针或数组之后就可能漏掉。所以 `-Wuninitialized`（clang 和 GCC 的 `-Wall` 都已包含）、GCC 的 `-Wmaybe-uninitialized`、clang-tidy 的 `cppcoreguidelines-init-variables` 都只能当兜底。GCC 15 对成员那一行报的是 `-Winit-self`，属于同一组检查。clang 还有 `-ftrivial-auto-var-init=pattern`，把未初始化的自动变量预填成固定模式，让原本“碰巧能用”的 bug 尽早暴露；它是调试手段，不是修复，不能替代在定义处写初值。C++26 又往前走了一步：读取未初始化的自动变量不再是未定义行为，而是“错误行为”（erroneous behavior，P2795）。程序读到的是实现给定的某个值，编译器可以诊断它，但它仍然是 bug，不是许可。各编译器对这一项的支持情况需核实。

推迟定义在循环里有一个经典权衡。EC-26 把两种写法拆成操作次数：定义在循环外是“1 次构造 + 1 次析构 + n 次赋值”，定义在循环内是“n 次构造 + n 次析构”。除非赋值明显比构造加析构便宜、并且这段确实是热点，否则默认选后者；它不仅通常更快，还让变量名只活在循环体里。CCS-18 也留了同一个例外：把变量提到循环外有时确实有益，但要有测量依据。

C++11 以后，语言和标准库让“晚定义”更容易落地。`auto` 强制在定义处给初值，写不出“先声明、以后再推导”的空档；范围 for 和 lambda 捕获让循环变量不必提前声明；C++17 的 `if`/`switch` 初始化语句把变量限制在语句内部（4.5 节会看到它和 `while` 的区别）；`std::optional<T>` 用“可能没有值”表达延迟构造，不必为了等一个可能不存在的对象而默认构造一个空壳或改用裸指针。C++20 的 `constinit` 则从另一个方向保证静态对象在编译期完成初始化，4.5 节再展开。

今天可以照下面的顺序检查一段代码：变量是否在定义处就有初值；这个初值是否就是最终要用的值；如果中间隔着参数检查或查找，能不能把定义移到检查之后；如果对象可能根本不存在，是否该用 `std::optional` 而不是一个空的默认对象。前三问靠读代码，最后一问靠接口设计。

## 4.2 构造函数体内赋值不算初始化

构造函数体开始执行时，所有基类和成员都已经构造完毕。这句话是理解本节的关键：初始化列表不是一串按书写顺序执行的语句，而是给“即将构造的子对象”准备实参的地方。真正决定顺序的是类定义：先虚基类（深度优先、从左到右），再直接基类（按声明顺序），再非静态成员（按声明顺序），最后才进入函数体。

Sutter 在 EXS-14 里用一个学生写的构造函数说明越过顺序的后果：`B() : A(s = f())` 把 `s = f()` 放在 `A` 基类的实参位置，于是 `A::f()` 会在 `A` 子对象和 `s` 成员都还不存在时被调用，`operator=` 也会落到一个尚未构造的 `std::string` 上。标准不要求编译器诊断这种用法，所以它能在多个编译器上静默通过。EXS-14 给出的顺序规则和上面一致，虚基类由最派生类的构造函数负责，按深度优先、从左到右构造，析构则完全逆序。

CCS-47 处理的是同一件事的另一个面：实际顺序由声明顺序决定，初始化列表的书写顺序会被忽略。书里的 `Employee` 把 `email_` 声明在 `firstName_`、`lastName_` 之前，初始化列表却用后两者拼出邮箱，于是 `email_` 最先构造，读到的是两个还没构造的 `string`。这类错误在构造函数定义于另一个源文件时尤其难发现，因为读者只看到初始化列表，看不到成员声明。语言之所以规定按声明顺序初始化，是为了让析构顺序唯一：否则析构函数得按每个构造函数实际构造的顺序逆序销毁，运行时需要额外记账。

`Account` 只在初始化列表里构造两个成员；`LegacyAccount` 先默认构造两个 `Text`，再用临时对象赋值，于是多出两次默认构造和两次移动赋值。这里临时对象是移动进去的，已经算便宜；如果成员类型没有移动赋值，代价会更高。

有些成员根本没有默认构造函数，或者是 `const`、引用类型，此时只有初始化列表能写：

```cpp
class Session {
public:
    Session(int id, std::string& name) : id_(id), name_(name) {}
private:
    const int id_;
    std::string& name_;
};
```

统一用初始化列表，就不必记住哪些成员“必须”写、哪些“可以”漏。CCS-48 留了一个例外：`new` 这类非托管资源获取应放在构造函数体里，不要放进初始化列表，否则后面的成员构造抛出时这块内存没人释放。更好的办法是根本不留裸资源，用 `std::unique_ptr` 之类的成员，让它的构造函数接管所有权（[第 8 章](ch08.md)、[第 9 章](ch09.md)）。

C++11 以后有两项变化值得知道。默认成员初始化器让“没在列表里提到”的成员也有确定初值，委托构造函数则允许一个构造函数先完整执行另一个构造函数，再进入自己的函数体；这两项都减少了手写重复列表的机会，但不改变“按声明顺序构造”的规则。C++20 的指定初始化器（designated initializers）对聚合体更进了一步：标准要求指定符按声明顺序写，写反了是 ill-formed（4.4 节会看到 clang 和 GCC 执行得并不一样严格）。工具方面，除了 `-Wreorder`，`-Wuninitialized` 能抓出一部分“成员没初始化就被读”的情况，但它只在能看清数据流时有效；CCS-47 说的“按声明顺序写，让非法依赖一眼可见”仍然是主要防线。

EXC-47 把这类问题放进一次控制流审查：`Array` 的成员声明是 `buffer_`、`used_`、`size_`，初始化列表却写 `used_(0), size_(startingSize), buffer_(new T[size_])`，实际执行时 `buffer_` 最先构造，`new T[size_]` 读到的 `size_` 还没有值。它和 CCS-47 是同一个错误的两种外衣：一个读字符串，一个读长度。EXC-47 还提醒，`assert` 里的副作用在 `NDEBUG` 下会消失，函数实参的求值顺序也不能依赖；这些都属于“控制流看起来从左到右，实际不是”的同一个主题。

## 4.3 圆括号、花括号和函数声明：一条语句为什么没构造对象

Sutter 在 EXC-42 里把四行只差几个字符的代码摆在一起，问它们有什么区别：

```cpp
T t;        // 默认初始化
T t();      // 函数声明，不是对象
T t(u);     // 直接初始化
T t = u;    // 拷贝初始化，不是赋值
```

`T t;` 对类类型调用默认构造函数，对内建类型则是默认初始化，值不确定。`T t();` 声明一个名为 `t`、没有参数、返回 `T` 的函数。`T t(u);` 在 `u` 是变量时是直接初始化，调用 `T::T(u)`；如果 `u` 恰好是类型名，它就变成函数声明：`t` 是一个以 `u` 类型为参数、返回 `T` 的函数。`T t = u;` 永远是初始化，不会调用 `operator=`，4.4 节再展开。

最令人烦恼的解析（most vexing parse）就出在第二行。ESTL-06 和 EXS-29 讲的是同一个陷阱在 STL 里的样子：用两个 `istream_iterator` 构造容器，第二个实参写成 `istream_iterator<int>()`，整句就符合函数声明的语法——第一个参数是名为 `numbers` 的 `istream_iterator<int>`，第二个参数是一个无名的函数指针，指向返回 `istream_iterator<int>`、没有参数的函数。于是这行代码不构造任何对象、不读任何输入，只声明了一个函数。C++ 从 C 继承的消歧规则是：一段代码如果能被解释为声明，就必须当声明（[stmt.ambig]）。EXS-29 把这类写法叫作语言的暗角，建议构造函数实参优先用命名变量。

花括号还有两个好处，EMC-07 把它们和 `initializer_list` 的麻烦一起讲。第一，它拒绝隐式窄化：`int rounded{measured}` 在 `measured` 是 `double` 时直接编译失败，而 `int rounded(measured)` 和 `int rounded = measured` 会静默截断。第二，它能用在圆括号不能用的地方，比如非静态成员的默认初始化器；`std::atomic` 这类不可拷贝对象，在 C++11/14 下只能用花括号或圆括号初始化，`std::atomic<int> n = 0;` 编译不过；C++17 保证复制消除之后，这种写法也合法了（本机 Clang 21、GCC 15 在 `-std=c++17` 下实测通过），所以 EMC-07 的这一条理由今天已经不成立。但花括号碰到 `std::initializer_list` 构造函数时会强烈优先选它，哪怕别的构造函数匹配得更好。

clang 把这条检查叫 `-Wc++11-narrowing`，GCC 叫 `-Wnarrowing`，两者在 C++11 及以后都默认开启。标准把它规定为 ill-formed，所以不要依赖 GCC 默认的宽松处理。注意它只拒绝“不能保证用目标类型表示”的转换；`int x{42}`、`char c{65}` 这类常量在范围内时仍然可以。

EMC-07 没有给出“一律用花括号”的结论。Meyers 说两派都有道理：花括号适用面最广、拒绝窄化、免疫 most vexing parse；圆括号与 C++98 传统一致，不会被 `initializer_list` 劫持，`auto` 也不会推成 `initializer_list`。他的建议是选一种作为默认，另一种在必须时显式使用，并在项目里保持一致。对类作者，他的建议更具体：如果一组重载里包含 `initializer_list` 构造函数，客户用花括号时可能只看得到它，所以要么避免这种设计，要么保证两种括号选出同一个构造函数。`std::vector` 的接口今天被当作反面教材。

C++17 的类模板实参推导（CTAD）让 `std::vector v{1, 2, 3}` 可以省略元素类型，但花括号仍优先匹配 `initializer_list`，`v` 是三个 `int`。C++20 的 P0960 允许用圆括号初始化聚合体，`Point p(1, 2)` 从 C++20 起合法（Clang 21 和 GCC 15 都支持），这缩小了“只有花括号能初始化聚合体”的差距；它不改变 `initializer_list` 的优先规则，也不改变窄化检查只作用于花括号的事实。

## 4.4 初始化、拷贝初始化与赋值是不同的事

`T t = u;` 里的 `=` 是初始化语法，不是赋值运算。《Accelerated C++》在 ACC-19 里把这条当作类作者必须分清的第一件事：初始化创建新对象，赋值改写已经存在的对象；初始化调用构造函数，赋值调用 `operator=`。两者面对的资源状态不同——赋值要先处理左边已有的资源，初始化只用管一个新对象。把两者混用，轻则多做一次工作，重则泄漏或重复释放。

Sutter 在 MXC-36 里把初始化分成两类。直接初始化写作 `T t(u)`，直接用某个构造函数，允许 `explicit`；拷贝初始化写作 `T t = u`，先按需做用户定义转换，再调用拷贝构造函数，不能使用 `explicit` 构造函数。基类和成员的初始化列表、`static_cast<T>(u)`、函数式转换 `T(u)`、`new T(u)` 都是直接初始化；函数传参、返回值、`throw`、按值 `catch`、花括号数组初始化都是拷贝初始化。`reinterpret_cast`、`dynamic_cast`、`const_cast` 在这里只产生引用（或指针），不创建新对象，不属于初始化。MXC-36 还给了一条今天仍然有用的建议：变量定义优先写 `T t(u)`，语义更直接，也不受 `explicit` 限制。

## 4.5 全局对象的初始化顺序不能靠链接顺序

EC-04 和 CCS-21 都盯着同一类对象：命名空间级变量、类的静态成员、文件级 `static`，以及函数内的 `static`。前三种叫非局部静态对象（non-local static object），它们在程序启动阶段构造（标准允许把动态初始化推迟到所属翻译单元第一次被使用之前），在程序结束时析构。C++ 只保证同一个翻译单元里的非局部静态对象按定义顺序初始化，跨翻译单元的顺序未定义。链接器碰巧按目标文件顺序初始化只是当前工具链的偶然行为；换编译器版本、改构建脚本或调整文件顺序，程序就可能在小改动后神秘崩溃。

更麻烦的是零初始化。命名空间级对象在构造函数运行之前先被零初始化，于是未就绪时它看起来完全“合法”：字符串是空的、指针是 null、整数是 0。CCS-21 说这种“看起来正常”比直接崩溃更难查。动态初始化的基本类型也一样，比如某个库用一个注册函数的返回值初始化命名空间级的 `bool`，这个 `bool` 是否已经算好，取决于库里其他全局状态有没有就绪。

CCS-21 给的首选是尽量不用命名空间级变量；确实需要时，用“首次访问时初始化”的函数局部静态对象，把顺序依赖变成显式调用依赖。下面的例子就是这样：`Auditor` 是命名空间级对象，它的构造函数调用 `Registry::instance()`，`Registry` 在第一次调用时才构造。

这个办法不是万能的。CCS-21 自己就说，singleton 本质仍是披着羊皮的全局变量，遇到互相依赖或循环依赖照样失效：A 的初始化需要 B 已构造，B 的初始化又需要 A 已构造，函数局部静态也救不了。此时应该重新设计依赖，而不是继续加一层 `instance()`。

C++17 的 inline 变量让在头文件里定义全局对象变得轻而易举，跨翻译单元的动态初始化问题反而更常见。C++20 的 `constinit` 从另一个方向解决：它要求变量做常量初始化，不满足就编译失败，不会留到运行期。示例里的 `constinit int max_sessions = 64;` 在编译期完成，没有动态初始化，也就不参与“谁先构造”的竞争。`constinit` 从 GCC 10、Clang 10 起支持；它只管初始化，不管 `const`，变量之后仍可修改。需要运行期一次性初始化又不想用函数局部静态时，`std::call_once` 是另一个选择。

clang 还有 `-Wglobal-constructors` 和 `-Wexit-time-destructors`，能对“需要运行期构造/析构的全局对象”发出警告；它们不在 `-Wall` 里，GCC 也没有对应选项，需要单独打开。这类警告适合用在库的公共头文件上，不适合一刀切地要求所有全局对象都消失。

## 4.6 一行一个对象，构造函数不会自动继承

《Thinking in C++》提醒过（TIC-05）一桩纯语法问题，它却经常和初始化纠缠在一起：在声明符语法里，`*` 只绑定紧跟它的标识符。`int* a, b, c;` 中只有 `a` 是 `int*`，`b`、`c` 是普通 `int`；把 `*` 贴着类型写会强化“它们都是指针”的错觉。引用、函数指针、成员指针有同样的陷阱，`int& r = x, s = y;` 里只有 `r` 是引用。

五个 `static_assert` 把声明符的真实类型固定下来，读代码的人不必靠记忆。TIC-05 的建议是一行只声明一个变量，或者至少把 `*`、`&` 贴着变量名写：`int *a, b, c;` 比 `int* a, b, c;` 更不容易误读。更彻底的做法是每个对象单独一行并就地初始化：

```cpp

```

这样既没有“哪个是指针”的问题，也满足 4.1 节的“定义处给初值”。`auto` 只挡住了一半。同一行里的 `auto` 必须为每个声明符推出同一个类型，所以 `auto a = &x, b = y;` 直接编译失败，clang 报 “'auto' deduced as 'int *' in declaration of 'a' and deduced as 'int' in declaration of 'b'”；但声明符的绑定规则没变，`auto *a = &x, b = x;` 里 `auto` 推成 `int`，`a` 是 `int*`、`b` 是 `int`，照样能编译，也照样容易误读。所以用 `auto` 时仍然建议一行一个。结构化绑定（C++17）适合从聚合或 `pair` 里拆出多个名字，不适合把一组无关变量塞进一行。

《Thinking in C++》还提醒过（TIC-17）继承里的“不自动”。构造函数、析构函数、`operator=` 处理的是对象的创建、销毁和赋值，派生类必须知道自己的基类部分怎么处理，所以它们不会像普通成员函数那样自动继承。没有 `using` 时，`Derived d(42)` 找不到 `Base(int)`，只能在 `Derived(int x) : Base(x) {}` 里手动转发。TIC 写作时这是一条绝对规则；C++11 引入继承构造函数（inheriting constructors，N2541）之后，规则变成了“不会自动继承，但可以用 `using Base::Base;` 显式引入”。

`Sensor sensor(42)` 走的是引入的 `Device(int)`，`label_` 用自己的默认成员初始化器变成 `"unset"`；引入的构造函数只负责基类部分，不会替派生类的新成员编出一个值。`Sensor copy = sensor` 仍然调用 `Sensor` 自己生成的拷贝构造函数，`label_` 被一起复制。`Sensor defaulted` 能编译，说明 `using Base::Base` 不抑制派生类默认构造函数的生成；拷贝、移动构造同样按自己的规则生成，不会被引入的构造函数取代。`explicit` 属性跟着被引入的构造函数一起保留，所以 `static_assert` 里 `is_constructible_v<Sensor, int>` 为真、`is_convertible_v<int, Sensor>` 为假。

TIC-17 还提到 `operator=` 不继承。C++11 之后可以用 `using Base::operator=;` 把基类的赋值运算符引入派生类的作用域，但这和“继承构造函数”是两件事；它不会替派生类成员做赋值，写的时候要清楚自己在调用哪一层（[第 6 章](ch06.md)）。析构函数则始终不能继承，派生类需要自己的析构函数来释放自己的资源；需要多态删除时，基类的析构函数必须是 `virtual`（[第 17 章](ch17.md)）。

## 回头看

这六节看似在讲六种不同的意外，其实都在守同一条线：对象只有在生命周期开始之后才可用。初始化列表、声明顺序、花括号、拷贝初始化、静态对象的首次访问、继承构造函数的引入，都是这条线在不同位置的表现。把“定义”和“初始化”分开，就会留下空档；把“书写顺序”当成“执行顺序”，就会读到尚未构造的子对象；把“能被解析成声明”的语句当成构造，就会一个对象都不创建；把跨翻译单元的顺序交给链接器，就会在换构建脚本时崩溃。规则的目的不是让人背下所有语法，而是让“对象何时存在”这件事在代码里看得见。

C++11 以后，语言替我们兜住了一部分：默认成员初始化器、`{}` 值初始化、函数局部静态的线程安全初始化、保证复制消除、`constinit`、指定初始化器，分别把“漏写成员”“窄化”“静态顺序”“多余拷贝”“动态初始化”“聚合字段顺序”中的一块接了过去。剩下的仍要靠写法：局部内置类型不会自动清零，成员之间的初始化依赖仍要按声明顺序审，`while` 条件里仍没有清晰的声明写法，跨翻译单元的全局对象仍没有唯一顺序。工具能帮一部分忙——`-Wuninitialized`、`-Wreorder`、`-Wvexing-parse`、`-Wmissing-field-initializers`、clang 的 `-Wglobal-constructors`，以及 clang-tidy 的 `cppcoreguidelines-init-variables`；但 ASan 和 UBSan 抓不到未初始化读取，需要 MSan 才能检测，或者用 `-ftrivial-auto-var-init` 让故障更稳定地复现。所以这一章的结论不是“打开某个开关”，而是把初始化写成对象定义的一部分，把顺序写成结构的一部分。

## 原书条目对照

| 条目 | 原书的主张 | 本章 | 新标准下 | 说明 |
|---|---|---|---|---|
| EC-04 确保对象在使用前已经初始化 | 内置类型手动初始化，成员用初始化列表，跨翻译单元的静态对象用函数局部静态代替 | 4.1 | 仍成立 | C++11 的默认成员初始化器和 `{}` 值初始化减少遗漏，函数局部静态的初始化从 C++11 起线程安全 |
| CCS-19 定义变量时就初始化 | 变量在定义处就要有确定初值，不要留下“先声明、以后再说”的空档 | 4.1 | 仍成立 | C++11 的 NSDMI 和 `{}` 补上了一部分遗漏，但局部内置类型到 C++20 仍默认不初始化；C++26 把读取它从 UB 改为“错误行为”，仍然是 bug |
| EC-26 尽量推迟变量的定义 | 等到需要且已有初值再定义，避免白构造和默认构造后赋值 | 4.1 | 仍成立 | C++11 的 `auto`、C++17 的 if/switch 初始化语句和 `std::optional` 让“贴近使用点定义”更容易 |
| CCS-18 变量声明得越晚越好，紧挨第一次使用 | 作用域和生命周期越短越好，定义放在能给出有意义初值且马上要用之处 | 4.1 | 仍成立 | C++17 的 if/switch 初始化语句进一步缩小作用域；循环外提前定义仍要测量后再做 |
| EXS-14 构造顺序由继承结构和声明顺序决定，不要使用尚未构造的子对象 | 先虚基类、再直接基类、再成员、最后函数体；列表书写顺序不改变它 | 4.2 | 仍成立 | C++11 的委托构造和 NSDMI 不改变顺序规则，C++20 的 constexpr 构造函数能让部分错误在编译期暴露 |
| CCS-47 成员的声明顺序就是初始化顺序，初始化列表要照着写 | 初始化列表按声明顺序写，避免成员间的非法初始化依赖 | 4.2 | 仍成立 | C++20 的指定初始化器也要求按声明顺序书写（GCC 报错，clang 默认只给 `-Wreorder-init-list` 警告） |
| CCS-48 构造函数里直接初始化成员，不要先默认构造再赋值 | 成员在初始化列表里直接构造，避免多余的默认构造和赋值 | 4.2 | 仍成立 | C++11 的 NSDMI 和委托构造减少重复列表；移动赋值可能让赋值变便宜，但多余构造仍在 |
| EXC-47 控制流审查：初始化顺序、求值顺序、assert 副作用与异常安全 | 不依赖初始化列表书写顺序和函数实参求值顺序，不在 assert 里放副作用 | 4.2 | 部分过时 | C++17 规定函数实参“顺序不确定但不能交错求值”，依赖顺序仍是未指定结果而非 UB；初始化顺序和 assert 的规则未变 |
| EXC-42 T t;、T t();、T t(u);、T t = u; 是四件不同的事 | 默认初始化、函数声明、直接初始化、拷贝初始化，四者语义不同 | 4.3 | 部分过时 | 四类语法的区别仍在，但 C++11 的 `{}` 提供了避开 most vexing parse 的首选写法；C++17 让 `T t = u` 的临时拷贝不再可观察 |
| ESTL-06 构造对象的语句可能被解析成函数声明 | 实参能被读成参数声明时，整句按函数声明解析；用命名变量或括号消歧 | 4.3 | 仍成立 | 声明文法到 C++20/23 未变；C++11 的花括号是更干净的规避手段，但 `initializer_list` 会带来新的重载选择 |
| EXS-29 最令人烦恼的解析：能被看作声明的语句就是声明 | 语法上能解释为声明就必须当声明，推荐用命名变量作构造实参 | 4.3 | 部分过时 | [stmt.ambig] 的规则未变，C++11 的 `{}` 提供了不依赖语言暗角的修法，但 `std::vector` 这类类型的列表构造函数仍需留意 |
| EMC-07 区分创建对象时的 () 与 {} | 花括号适用面最广、拒绝窄化、免疫 most vexing parse，但会被 `initializer_list` 劫持 | 4.3 | 仍成立 | C++20 的 P0960 允许圆括号初始化聚合体，缩小了两种括号的差距；`initializer_list` 优先和窄化规则未变 |
| ACC-19 区分初始化和赋值 | 声明中的 `=` 调用拷贝构造，表达式中的 `=` 调用赋值 | 4.4 | 部分过时 | C++17 的保证复制消除改变了返回值和 `T x = T()` 的拷贝次数，但“初始化 vs 赋值”的分界未变 |
| MXC-36 直接初始化与拷贝初始化的区别 | 直接初始化直接用构造函数，拷贝初始化先转换再拷贝，且不能用 `explicit` | 4.4 | 部分过时 | C++17 起纯右值的拷贝初始化不再要求拷贝构造可访问；`explicit` 只允许直接初始化的区别仍在 |
| TIC-07 聚合初始化按声明顺序，增删成员会悄悄改变含义 | 聚合按成员声明顺序匹配，未给出的成员按默认成员初始化器或值初始化处理，插入成员会改变旧初始化的含义 | 4.4 | 更加重要 | C++20 的指定初始化器让字段名可写且强制声明顺序，但位置初始化仍然怕增删成员 |
| CCS-21 跨编译单元的全局对象不能互相等待初始化 | 不同编译单元的命名空间级对象初始化顺序未定义，用首次访问初始化把依赖显式化 | 4.5 | 更加重要 | C++11 的函数局部静态初始化线程安全；C++17 的 inline 变量让问题更常见；C++20 的 `constinit` 可强制常量初始化 |
| TIC-08 goto 和 switch 不能跳过对象的初始化 | 跳转目标位于带初始化对象的作用域内时，编译器必须拒绝 | 4.5 | 仍成立 | C++20/23 没有放宽跳转规则；`constexpr`、`consteval` 也不让运行时跳转绕过生命周期 |
| TIC-28 不要在 while/if 条件里声明变量；C++17 只救了 if/switch | 条件里的声明受语法限制，`=` 与 `!=` 的优先级容易把 char 初始化成 bool | 4.5 | 部分过时 | C++17 的 if/switch 初始化语句（P0305R1）解决了 if/switch；`while` 仍没有 init-statement，C++20 也未增加 |
| TIC-05 `int* a, b, c;` 只声明了一个指针 | `*` 只绑定紧跟的标识符，一行一个声明最不容易误读 | 4.6 | 仍成立 | 声明符语法没有变；`auto` 要求各声明符推出同一类型，但 `auto *a = &x, b = x;` 仍会混出指针和非指针 |
| TIC-17 构造函数不会被继承；C++11 的 using Base::Base 是另一回事 | 构造函数、析构函数、`operator=` 不自动继承，派生类要自己写转发 | 4.6 | 部分过时 | C++11 起可以用 `using Base::Base` 引入基类构造函数；它只初始化基类部分，不抑制派生类默认/拷贝/移动构造的生成 |
