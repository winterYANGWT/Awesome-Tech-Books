# 第 18 章 组合、私有继承与多继承：复用不等于 is-a

下面这个“唯一名字集合”看起来只差一个 `add` 函数：

```cpp
class UniqueNames : public std::list<std::string> {
public:
    void add(const std::string& name) {
        if (std::find(begin(), end(), name) == end()) push_back(name);
    }
};
UniqueNames names;
names.add("ada");
names.push_back("ada");   // 编译通过，“唯一”却没了
```

`UniqueNames` 公开继承了 `std::list`，于是 list 的整套接口都成了它的公开接口，包括允许重复的 `push_back`。`add` 守住的规则可以被任何一个 list 成员绕过去；更糟的是，任何接受 `std::list<std::string>&` 的函数都能把 `UniqueNames` 当成普通 list 使用，并合理地期待它可以存重复元素。这里缺的不是一个更严格的 `add`，而是对关系的判断：`UniqueNames` **用 list 实现**，但它**不是** list。

C++ 里表达“复用实现”的手段不止一种，组合、私有继承、多继承都能让一个类站到另一个类的肩膀上，但它们表达的语义和耦合强度完全不同。Meyers 在 EC-38 里把组合分成应用域的 has-a 和实现域的 is-implemented-in-terms-of；EC-39 和 EC-40 接着讨论私有继承与多继承，Sutter 则从耦合和异常安全的角度反复追问“能不能用更弱的关系”。本章沿着这条线走：先看组合怎样表达两种“有”，再看私有继承在什么条件下才值得，然后处理多继承的菱形与同名虚函数，最后回到两个容易被忽略的细节——纯虚函数的定义和数组的多态陷阱。

## 18.1 用组合表达 has-a 与 is-implemented-in-terms-of

组合（composition）最直白的含义是“一个对象里含有另一个对象”。`Customer` 含有 `Address`，所以它有名字、有地址；说“顾客是一个地址”显然不通。这是应用域的 has-a。另一类组合发生在实现域：`UniqueNames` 需要一个能按插入顺序保存名字的容器，于是它内含一个 `std::list<std::string>`；这不是因为“唯一名字集合是一种链表”，而是因为链表恰好能完成这项工作。EC-38 把后者称为 is-implemented-in-terms-of（用某类型实现），并强调它和 has-a 一样，都不该用 public 继承表达。

`BadUniqueNames` 的 `add` 第一次去重成功，第二次也返回了“已存在”，看起来没问题；但只要调用继承来的 `push_back`，重复元素就进来了，`size()` 也从 1 变成 2。这不是 `add` 写错了，而是 public 继承把“list 允许重复”这条基类契约一起带进了派生类，而派生类的名字又承诺了“唯一”。EC-38 的判据很朴素：如果 `D` 公开继承 `B`，那么所有对 `B` 成立的事都该对 `D` 成立；list 可以含重复元素，`UniqueNames` 不可以，所以它不满足 is-a。把 `std::list` 换成 `std::vector`、`std::unordered_set` 或自己写的哈希表，只改变实现选择，不改变“它仍然不是 list”这个结论。

`UniqueNames` 把 `names_` 放在 private 里，只暴露 `add` 和 `size`。这样做的直接好处是客户看不见 `begin`、`push_back`、`sort` 这些 list 操作，`add` 的去重规则没有旁路；间接好处是内部容器可以随时更换，只要 `add` 和 `size` 的语义不变，客户代码不用改。CCS-34 把这一点放在耦合的框架里：继承是 C++ 中仅次于 friend 的强耦合关系，派生类依赖基类的 public 和 protected 部分，基类的定义必须完整可见，基类所在命名空间的名字还会被拉进查找范围；成员只依赖被包含类型的 public 接口，而且可以用前置声明、指针或 Pimpl 把这份依赖再藏深一层。能表达同一个关系时，选更弱的那一种。

`static_assert` 把两种关系的类型层面差别钉死了：`BadUniqueNames` 的基类确实是 `std::list<std::string>`，`UniqueNames` 则完全不是。这个检查在重构时很有用——如果有人为了“少写几个转发函数”把 `UniqueNames` 改成继承，编译期就会有人注意到。需要提醒的是，`std::is_base_of_v` 只回答“有没有基类子对象”，不回答“这个继承是否合理”；`BadUniqueNames` 也能通过它，所以它适合守住已经做出的设计决定，不适合代替设计判断。

组合也不是只有“按值放一个成员”这一种写法。Sutter 在 MXC-23 里比较了私有继承和委托（delegation）在异常安全上的差别，结论对今天同样成立。假设有一个老式的 `LegacyBuffer`，它的拷贝赋值会逐个元素写入，中途可能抛异常；如果 `Doc` 私有继承 `LegacyBuffer`，编译器生成的 `Doc::operator=` 只能调用 `LegacyBuffer::operator=`，于是异常发生时目标对象已经被改了一半，`Doc` 无法回滚。把 `LegacyBuffer` 放到 `std::unique_ptr` 后面，赋值时先 `make_unique` 复制一份新的，成功后再替换指针，失败时旧指针原封不动，强异常安全就只依赖指针操作：

C++11 以后，组合的写法更轻：`std::unique_ptr` 让 Pimpl 和运行期替换实现更容易，移动语义让按值持有的成员可以低成本转移，`[[no_unique_address]]`（C++20）还让空成员有机会不占空间。这些都没有改变语义判断。标准库里的 `std::stack`、`std::queue` 就是组合的典型：它们默认内含一个 `std::deque`，并通过模板参数允许换实现，但从不让客户把 `stack` 当成 `deque` 用。选容器时先问“这个类要用什么来实现”，再问“它是不是那个东西”；前一个问题的答案是成员，后一个问题的答案才可能是 public 继承。

## 18.2 私有继承只在必要时用

私有继承最关键的规则有两条，两条都改变了类的对外面貌。第一，派生类对象不能隐式转换成基类对象，`Student` 私有继承 `Person` 之后，`eat(student)` 这种调用在类外编译不过；第二，基类的 public 和 protected 成员在派生类里都变成 private，客户看不见，派生类的派生类也看不见。EC-39 因此说，私有继承在软件设计阶段没有意义，它纯粹是实现技巧：只继承实现，不继承接口。它和组合一样表达 is-implemented-in-terms-of，但耦合更强，所以默认应该选组合。

私有继承的正当理由可以收成一张短名单：需要覆盖虚函数；需要访问 protected 成员；需要让被用对象先于或晚于另一个基类子对象构造、析构；需要共享或改写虚基类的构造；确实需要空基类优化；需要受控多态。名单之外，优先用成员。C++20 的 `[[no_unique_address]]` 让空成员也可能不占空间，进一步削弱了空基类优化作为理由的分量；C++11 的 `final` 和 `= delete` 让“禁止继承”“禁止拷贝”更容易表达，但它们不会把私有继承变成组合。判断标准仍然是：成员能不能完成？能，就不要付继承的耦合。

## 18.3 继承是近乎最强的耦合

CCS-34 和 EXC-24 都把继承排在 friend 之后，称为 C++ 里第二强的类关系。这个排序不是修辞：public 继承让派生类依赖基类的 public 和 protected 接口、基类的布局、基类的虚函数表，甚至基类所在命名空间的名字查找；基类改一个成员，所有派生类都可能要重编译。组合只依赖被包含类型的 public 接口，而且这份依赖还可以继续用指针、Pimpl 或模板参数藏起来。EXC-24 因此给了一条很硬的判断：public 继承只用来表达真正的 IS-A，而且要同时满足 WORKS-LIKE-A；如果只是想复用基类的代码，就应该用成员。它把“正方形继承矩形”称为 IS-ALMOST-A：数学上成立，行为上不成立，正是第 17 章开头那段代码的另一种说法。

把两段放在一起，判断顺序可以这样走：先问关系是不是真正的 IS-A，不是就用成员；再问实现需不需要被替换、要不要多个实例、能不能用 Pimpl 隔离，能就用组合；最后才问有没有成员给不了的能力，比如覆盖虚函数或访问 protected，这时才考虑私有继承。ACC-24 补的是另一半：如果数据本身有结构，而且操作依赖这个结构，就不要为了“简单”把它压平；用组合保留结构，用共享指针避免复制。两条建议并不冲突，它们都在要求关系被如实表达，而不是被最省事的语法掩盖。

虚继承也不是免费的：对象布局更复杂，访问虚基类成员通常要经过额外间接，构造和赋值的规则也更难解释。EC-40 的建议是默认用非虚继承，只有确实需要共享同一份基类数据时才用虚继承；用了之后，尽量让虚基类不含数据。Java 和 .NET 的接口不允许数据成员，部分原因就是避开这类初始化与赋值麻烦。标准库的 `basic_iostream` 也用了虚继承来共享 `basic_ios`，这说明它有用武之地，但不说明它应该成为默认。

## 18.5 纯虚函数也可以有定义

纯虚函数（pure virtual function）的 `= 0` 只表示“具体派生类必须覆盖”，它不表示“基类不提供实现”。含未覆盖纯虚函数的类是抽象类，不能直接创建对象；但纯虚函数本身可以有函数体，派生类覆盖之后仍然可以用 `Base::f()` 显式调用那份实现。MXC-27 把这条规则展开成几种用途，最常见的是纯虚析构：如果基类没有别的纯虚函数，又想让它成为抽象类，就把析构声明为纯虚；但派生类析构一定会调用基类析构，所以这个纯虚析构必须有定义，否则链接会失败。

`Task::~Task()` 是纯虚的，`Task` 因此是抽象类；但它的定义 `= default` 仍然存在，`std::unique_ptr<Task>` 删除 `RetryTask` 时能正常调用基类析构。`Task::describe()` 也是纯虚函数，却有一份返回 `"task"` 的函数体；`RetryTask::describe` 显式调用 `Task::describe()` 再包一层，得到 `RetryTask(task)`；`SilentTask` 也显式调用它，得到 `task`。`StillAbstract` 没有覆盖 `describe`，所以即使它实现了 `run`，仍然是抽象类，`std::is_abstract_v<StillAbstract>` 为真。

这套写法解决的是“默认实现要不要自动继承”的问题。普通虚函数给一份默认实现，派生类什么都不写就默默继承了；如果默认行为只在少数情况下合适，这种“默默”就会变成错误。把函数设为纯虚、同时给出定义，派生类想用默认实现就必须写 `Base::f()`，这是一次显式请求。MXC-27 用 State 模式举例：状态的默认处理可能是“忽略这个事件”，但每个具体状态都应该自己决定要不要忽略，而不是因为忘记覆盖就继承一个可能不合适的默认行为。反过来，如果默认行为是大多数派生类都需要的，普通虚函数更省事；纯虚加定义适合“默认存在，但必须被主动选择”的场合。

纯虚析构还有一条容易忽略的规则：只声明 `virtual ~Base() = 0;` 而不给定义，派生类仍然可以声明，但一旦构造或析构派生类对象，链接器就会报 `Base::~Base()` 未定义。MXC-27 因此把“基类析构要么 public + virtual，要么 protected + nonvirtual”作为配套准则：前者支持通过基类指针多态删除，后者阻止这种删除；纯虚析构属于前者，必须把定义补上。C++11 起析构函数默认是 `noexcept`，这份定义也不应该抛异常，否则 `std::terminate` 会在析构途中被调用。

C++11 的 `override` 和 `final` 让纯虚接口的意图更清楚：`override` 保证派生类真的覆盖了某个虚函数，`final` 可以封住某个实现或整个类；`= default` 让纯虚析构的定义更简洁。C++20 的 concepts 可以在编译期表达“支持某组操作”，适合静态多态；运行期多态仍然要靠虚函数，纯虚函数加定义这套规则没有变。今天写抽象基类时，先问析构要不要多态删除：要，就 public virtual（需要时纯虚并给定义）；不要，就 protected nonvirtual。再问默认实现要不要强制派生类显式选择：要，就纯虚加定义；不要，就普通虚函数或 NVI。纯虚不等于“没有实现”，它只是把“必须覆盖”写进了类型系统。

## 18.6 不要通过基类指针操作派生数组

单个派生类对象可以安全地当成基类对象使用：`Derived*` 转成 `Base*` 时，编译器知道怎么调整指针，虚调用也会找到派生版本。数组是另一回事。`Base* p = derivedArray;` 之后，`p[i]` 等价于 `*(p + i * sizeof(Base))`，编译器只用静态类型 `Base` 计算步长；实际元素是 `Derived`，每个元素更大，从第二个开始就指到了对象中间。MEC-03 和 CCS-100 都把这条规则称为“数组与多态不能混用”：单对象的多态替换合法，加上指针算术就破坏了可替换性。

ASan 报 `SEGV`，因为虚调用从一个不是虚表指针的地址取函数入口。没有 sanitizer 时，这类错误可能只是读到错误的值、写坏别的对象，或者在稍后某个完全无关的地方崩溃；clang 在 `-Werror` 下也照样接受了这段代码，所以不能指望类型检查兜底。通过基类指针 `delete[]` 派生数组同样危险：编译器按 `Base` 的大小和析构函数逐元素处理，派生类的析构函数不会正确调用，标准规定行为未定义。MEC-03 因此建议从设计上避免“具体类继承具体类”，需要多态集合时用“指向基类的指针的容器”。

上面的正确写法就是 `std::vector<std::unique_ptr<Base>>`：每个元素是一个指针，指向单独分配的派生对象，`item->label()` 通过基类接口虚分派，容器本身从不做“按 `Base` 大小跨过 `Derived` 对象”的算术。`std::array` 和 `std::vector` 也存不了按值切片的多态对象，放进去的 `Derived` 会被切成 `Base`；要保留动态类型，就存指针或 `std::reference_wrapper`。C++20 的 `std::span<Base>` 也不能修复步长：它的 `size_bytes()` 仍按 `sizeof(Base)` 计算，把 `Derived` 数组的首地址转成 `Base*` 再构造 `span` 之后，`span[1]` 的地址和 `array[1]` 依然对不上（本机实测两个元素时 `size_bytes()` 是 32，而 `Derived[2]` 实际占 48 字节）。`final` 只能阻止继续派生，不能把错误的指针算术变成合法。

接口设计也能减少误用。函数只需要一个对象时，参数用 `Base&` 而不是 `Base*`，调用方就不会误以为可以按数组传递；确实需要数组时，把数组封进一个容器类，只暴露多态的遍历接口，让下标运算留在知道真实元素类型的代码里。MEC-03 把“避免具体类继承具体类”放在这条规则的最后，因为如果 `Derived` 不是从具体类 `Base` 派生出来的，很多数组误用从一开始就不会出现；CCS-100 则补上标准库的替代方案：`vector<unique_ptr<Base>>`、`shared_ptr` 容器，或者一个内部管理数组、外部只提供多态迭代的封装类。

## 回头看

六节其实在防同一类错误：把“我能用它的代码”误当成“我就是它”。`UniqueNames` 想复用 list 的存储，`CPerson` 想复用 `PersonInfo` 的格式化，图片想复用字符串的字符，这些都是实现层面的“用”，一旦写成 public 继承，就被提升成了对外的“是”，客户会按基类的契约使用派生类，数组、赋值、异常安全和名字查找随后都可能出问题。组合把关系降回成员，私有继承在确实需要虚函数或 protected 成员时保留一份受控的“用”，多继承则要求每条继承边都能单独说清理由；ACC-24 反过来提醒，弱耦合不等于把结构压平，该保留的共享结构要用指针和值语义好好表达。

C++11 以后，语言和标准库替我们兜住了一部分：`unique_ptr`/`shared_ptr` 让 Pimpl 和结构共享更安全，`override`/`final` 让覆盖意图可检查，`std::variant` 给封闭类型集合提供了不靠菱形继承的写法，`[[no_unique_address]]` 削弱了空基类优化作为私有继承理由的分量，concepts 提供了不继承的静态多态。剩下的判断仍然在人手里：这段关系到底是 has-a、is-implemented-in-terms-of 还是 is-a；多继承的每条边是否都值得；虚基类该不该有数据；数组会不会被当成基类数组。编译器能替你检查签名和访问权限，检查不了“这个继承在语义上是否成立”。
