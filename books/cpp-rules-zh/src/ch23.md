## 23.1 避免默认捕获，把对象移动进闭包

上面的崩溃来自 `this`：`[this]` 存进闭包的是一根指针，`Sensor` 被 `reset` 之后，指针指向的内存已经归还给堆。同样的故事换成引用捕获一样成立。假设过滤器表按值保存闭包，而闭包按引用捕获了局部变量：

```cpp
std::vector<std::function<bool(int)>> filters;

void addDivisorFilter(int divisor) {
    filters.emplace_back([&](int value) { return value % divisor == 0; });
}   // divisor 随栈帧消失，filters 里的引用立刻悬垂
```

`[&]` 的问题在于它把“依赖哪些局部变量”藏了起来。读代码的人看到 `filters.emplace_back`，不一定意识到闭包会比函数活得久；写代码的人也可能只是在函数里临时用一下，后来这段代码被复制到别处，捕获方式就跟着一起搬过去了。Meyers 在 EMC-31 里的建议是显式列出每个依赖：`[&divisor]` 至少把变量名摆在眼前，逼着人做一次生命周期分析。只在“闭包立即使用、不会被保存”的算法调用里，默认引用捕获才通常安全；而这条前提一旦变化，编译器不会提醒。

`[=]` 看起来是解药，其实只是换了一种悬垂。它按值复制的是指针本身，不是指针指向的对象；在成员函数里，它复制的则是 `this`，而不是成员变量的值。成员变量和静态存储期对象根本不能被捕获：成员要通过 `this` 访问，静态变量则直接被闭包引用，既不复制也不延长生命。这三件事合起来，就是“默认按值捕获让闭包看起来自包含，实际并不”。C++20 起，在 `[=]` 里隐式捕获 `this` 被标记为弃用（P0806R2），两个编译器都会给出诊断：

## 23.2 泛型 lambda 用 decltype 转发，别用 bind

C++14 的泛型 lambda 让参数写成 `auto`，闭包类的 `operator()` 因此变成一个模板。这带来一个容易忽略的后果：模板形参按值接收时，形参本身在函数体里是左值，不管调用者传进来的是左值还是右值。写一个只做转发的 lambda，如果用 `auto x`，右值实参也会被当成左值传下去，被调函数的重载决议就走错分支：

```cpp

```

输出：


`byValue` 两次都打印“左值重载”，原因不是 `consume` 写错了，而是 lambda 的形参 `x` 是一个有名字的变量，表达式 `x` 永远是左值。把形参改成 `auto&&`，它就落进转发引用（forwarding reference）的规则：左值实参让 `decltype(x)` 成为 `T&`，右值实参让它是 `T&&`；`std::forward<decltype(x)>(x)` 对两种情况都给出原本的值类别。最后两行输出把这个类型直接打了出来。EMC-33 的解释是：普通模板函数里有 `T` 可写 `std::forward<T>`，泛型 lambda 里拿不到 `T`，但 `decltype(x)` 已经携带了同样的信息；右值情形的 `T&&` 经引用折叠后与传非引用的 `T` 等价，所以两种情形都能用。

C++20 允许 lambda 显式写模板参数列表，`[]<typename T>(T&& x)` 就能直接写 `std::forward<T>(x)`，不必再借 `decltype`。两种写法都合法，新代码用哪一种取决于团队习惯；`decltype` 版本在 C++14/17 下也能编译，而在 C++14/17 下，可变参数版本只能写 `[](auto&&... ps)`，再对每个 `ps` 做 `std::forward<decltype(ps)>(ps)`。转发引用和引用折叠的完整规则在 [第 5 章](ch05.md) 5.4 节，这里只强调一点：只在需要保留值类别时才用 `auto&&`，只读不转发的形参写成 `const auto&` 更清楚。

C++17 起 lambda 可以是 `constexpr`（函数体满足常量表达式的要求时），C++20 起无捕获的 lambda 还能默认构造、也能出现在 `decltype` 这类未求值语境里（本机 clang 21 和 GCC 15 都实测通过）。这些改动让闭包越来越像普通的值，和捕获、复制这条主线同向。

`std::bind` 是 C++11 从 TR1 收进来的，接替 C++98 的 `bind1st`/`bind2nd`，在 lambda 普及之前是绑定实参的主要工具。它的问题不在功能，而在每一处语义都要读者背下来。最典型的是求值时机：传给 `std::bind` 的普通实参在创建 bind 对象时就被求值并存进去，只有占位符 `_1`、`_2` 的位置留到调用时填；lambda 的规则和普通函数一样，函数体里的表达式在调用时才算：

`bound` 里的时刻停在创建时的 `tick=1`，`lambda` 每次调用都重新取当前时刻，`deferred` 套了一层 `std::bind(clockTick)` 才把求值推迟。EMC-34 用闹钟的例子讲的正是这件事：想表达“从现在起一小时后响”，bind 版本却写成了“从创建 bind 对象起一小时”，编译器不会提醒，因为两种写法在语法上都合法。bind 对象还会复制它的普通实参（左值复制、右值移动），要按引用保存得包一层 `std::ref`；调用时它又把实参按完美转发传给目标，所以 `_1` 位置可以是 `int&`，示例最后一行的 `counter` 被改成了 1。这些规则都不是秘密，但每一条都要在读代码时重新推一遍。

重载函数名是 bind 的另一个硬伤：`std::bind` 只拿到一个函数名，没有实参可供重载决议，遇到重载集就直接失败。lambda 的函数体里是一次普通调用，重载决议照常进行。这个问题的细节和两种修法放在 23.7 节。可读性之外，EMC-34 还提到经函数指针的调用更不容易被内联，这一点取决于优化器和具体代码，本章不把它当作可移植的性能结论；能确定的是 lambda 的调用目标在源码里可见，读起来不需要在脑内做占位符映射。

今天的结论很直接：C++14 之后，lambda 的初始化捕获和泛型 lambda 覆盖了 `std::bind` 仅有的两个合理用途（模拟移动捕获、绑定带模板 `operator()` 的对象）。C++20 的 `std::bind_front` 和 C++23 的 `std::bind_back` 比 `std::bind` 简单，只固定前几个或后几个实参，不涉及占位符重排，适合做局部的偏应用；但只要需要读捕获的值、需要转发、需要包一层重载名，写 lambda 仍然更清楚。`std::bind` 本身没有被弃用，读旧代码时得认识它，新代码没有理由优先选它。

## 23.3 函数对象按值传递来设计

标准算法的签名就把答案写死了：`for_each(first, last, f)` 的 `f` 是按值传递、按值返回的，`find_if` 的谓词、`sort` 的比较器也一样。调用点当然可以显式指定 `for_each<Iter, Functor&>` 逼它按引用接收，但很多算法的实现假定自己拿到的是一个独立的值，这种写法依赖实现，不该当作常规手段。ESTL-38 因此给出两条设计约束：函数对象要小、拷贝要便宜；不能靠虚函数做多态，按值传给基类形参时派生部分会被切掉。需要大量状态或多态时，把状态和虚函数放进一个实现类，外层只留一个指向实现的指针和转发用的 `operator()`：

CCS-89 把这几条收成一句“写对函数对象”：廉价可拷贝、单一 `operator()`、重状态藏进 Pimpl。单一 `operator()` 在 C++98 是为了让 `argument_type`/`result_type` 只有一套，这套 typedef 今天已经没了（23.5 节），但“一个函数对象只表达一种操作”仍然成立：重载的 `operator()` 会让调用点难以判断到底命中哪一个，也让模板对“这个类型能接受什么实参”的判断变复杂。C++11 的 lambda 天生没有虚函数、只有一个 `operator()`；是否廉价可拷贝，取决于捕获列表——捕获列表决定闭包的大小。捕获一个大对象仍然会让每次拷贝变贵，所以捕获 `shared_ptr` 或指针、把状态放到闭包外面，和手写函数对象时的取舍一样。

## 23.4 谓词必须是纯函数

谓词（predicate）是返回 bool（或可隐式转成 bool 的值）的函数对象，算法的 `find_if`、`remove_if`、`count_if` 和关联容器的比较器都收它。纯函数的意思是返回值只由实参决定：同样的实参调多少次都得到同样的结果，函数不读也不写任何会变的外部状态。这两条放在一起，就把“在谓词里放一个计数器”判成了错误。下面的例子想删掉序列里的第三个元素，于是让谓词每调用一次就加一：

删掉的是第 3 个和第 6 个元素（值 3 和 6），而传进去的那个 `third` 对象一次都没被调用——两个副本各数到 3。原因在本机的 libstdc++ 15 里看得很清楚：`remove_if` 先把谓词的一份拷贝交给内部的 `find_if`，找到第一个满足条件的元素；随后用自己那份从未被调用、计数仍为 0 的副本从下一个元素继续扫，到元素 6 时又数到 3。ESTL-39 和 CCS-87 都拿这个 `FlagNth` 说明问题，书里举的实现是 `find_if` 加 `remove_copy_if` 各拿一份拷贝，本机这一版是 `find_if` 加同一份副本继续扫，机制不同，结果一样。标准并没有规定 `remove_if` 必须这样实现，也没有规定谓词被调用几次、以什么顺序调用；`remove_if` 只保证把不满足条件的元素按原顺序搬到前面并返回新的末尾（示例再用 `erase` 删掉尾巴），而“第三个”这种依赖调用次序的需求本来就没有定义。换一个标准库实现，删掉的可能是另外两个，甚至可能只删一个，这正说明代码依赖了未指定的行为。

`operator()` 声明为 `const` 是必要的第一步：它让谓词能被 const 对象和 const 引用调用，也让直接改成员被编译器挡住：

但 const 只挡住了直接改成员这一种写法。`mutable` 成员、函数内的 `static` 变量、全局对象和命名空间作用域的对象都能绕过它，示例里的 `FlagNthMutable` 把计数器声明成 `mutable`，`operator()` 是 const，结果和刚才完全一样。所以 CCS-87 的措辞是“把 `operator()` 写成 const 让编译器帮你”，而不是“写了 const 就安全”。

C++11 之后这类错误反而更容易出现：lambda 捕获一个计数器、在函数体里自增，只需要在捕获列表后面加一个 `mutable`，语法上毫无阻碍。C++20 的 `std::predicate` 概念把“不修改函数对象和实参、同样输入产生同样输出”写进了语义要求，但概念只检查表达式是否合法，不检查纯度，编译器不会因此报错。C++17 的并行算法把后果又加重了一层：谓词可能被多个线程同时调用，带状态的谓词从“结果不确定”升级成数据竞争，标准明确要求传给并行算法的谓词、比较器这类函数对象不得通过实参直接或间接修改对象；它们一旦抛出异常，程序直接调用 `std::terminate`。用 `std::ref` 包一层能避开拷贝，却避不开调用顺序，多个线程同时改一个计数器仍然是数据竞争。

需要“只处理前 N 个”这类逻辑时，把状态放在算法外面：显式循环、带下标的 `for`，或者先 `find_if` 找到位置再处理。谓词只回答“这个元素满不满足条件”，不回答“这是第几个”。

## 23.5 not1/bind1st 要的 typedef 和 mem_fun 都已是历史

C++98 的标准库有一套函数适配器：`not1`/`not2` 取反一元/二元谓词，`bind1st`/`bind2nd` 固定第一个或第二个实参。它们靠一套嵌套 typedef 工作：一元仿函数要有 `argument_type` 和 `result_type`，二元仿函数要有 `first_argument_type`、`second_argument_type` 和 `result_type`。手写这些 typedef 很烦，所以标准库提供了 `std::unary_function` 和 `std::binary_function` 两个基类，继承它们就自动获得对应的 typedef。ESTL-40 的建议是“让仿函数可适配”：写函数对象时顺手继承一下，就能交给 `not1`、`bind2nd` 使用。这套协议的一个副作用是，一个函数对象只能有一套 `operator()` 签名，因为一套 typedef 只能描述一种参数和返回类型；重载了 `operator()` 就等于放弃可适配性。

函数指针没有这些 typedef，于是 `ptr_fun` 出现了。它做的事情只有一件：把普通函数指针包成一个带 `argument_type`/`result_type` 的适配器对象。它不改变调用语法，`not1(isInteresting)` 编译不过的原因不是调用方式不对，而是 `isInteresting` 这个函数指针缺少 `not1` 要读的 typedef，套一层 `ptr_fun` 就能过。`mem_fun`/`mem_fun_ref` 解决的是另一个问题：标准算法内部统一写 `f(*it)`，只认非成员函数的调用语法，而成员函数要用 `x.f()` 或 `p->f()`。`mem_fun_ref` 把成员函数指针包成 `operator()(T&)`，内部执行 `(obj.*pmf)()`；`mem_fun` 包成 `operator()(T*)`，内部执行 `(ptr->*pmf)()`。容器存对象用前者，存指针用后者；ESTL-41 说这两个名字是历史产物，先有指针容器的需求，后来才补上对象版本。

这套东西今天全部作废了。`unary_function`/`binary_function`、`ptr_fun`、`mem_fun`、`mem_fun_ref`、`bind1st`/`bind2nd` 在 C++11 弃用、C++17 从标准移除，`not1`/`not2` 在 C++17 弃用、C++20 移除。libstdc++ 15 仍以弃用扩展保留它们，所以在 `-std=c++20` 下写 `std::ptr_fun` 还能编译，只是会收到 `-Wdeprecated-declarations` 警告（本机实测）；换一个标准库实现就未必还有。读旧代码时知道它们在做什么即可，不要在新代码里用。

同一个“名字不构成值”的问题，在标准库成员函数上还有一层额外风险。EXS-04 问的是 `std::mem_fun(&std::vector<int>::clear)` 是否可移植，答案是否定的，原因不在 `mem_fun`，而在 `&std::vector<int>::clear` 这个指针的类型。标准允许实现给成员函数增加额外的默认参数（书里戏称为“peekaboo”参数），也允许把一个带默认参数的签名换成多个行为等价的重载；平时直接调用 `v.clear()` 时多出来的参数由默认值补上，取地址时却必须写出精确的指针类型，这时实现留出的余地就暴露了。标准还明确，除特别指明外，标准库函数不保证是“可取地址的”（addressable function），所以即便某个实现今天能编过，也不该依赖它。

示例里取 `&std::vector<int>::clear` 的那段用 `__GLIBCXX__` 包了起来，因为只有 libstdc++ 当前这个版本恰好把它实现成无参函数；换成别的标准库，这段可能直接编译失败。这不是示例在回避问题，而是把“依赖实现”这件事明明白白写在条件编译里。可移植的写法是包一层 lambda（示例最后一段），或者干脆在需要调用的地方直接写 `container.clear()`。同理，`std::mem_fn`、`std::invoke` 可以用在自家类的成员函数上，不要拿标准库类型的成员函数指针去喂它们；标准库没有承诺这些指针的签名，标准库的实现者也没有义务为你保留它。

## 回头看

这七节讲的是同一件事的两个方向：闭包是一个值，值会被复制、被存起来、可能被跨线程调用；而它里面装的是指针、引用还是一份副本，决定了这个值安不安全。C++11 到 C++20 把大量“怎么写”的问题解决了：lambda 取代了手写函数对象和 `mem_fun` 系列，初始化捕获解决了移动捕获，`[*this]` 和 C++20 对隐式 `this` 捕获的弃用让所有权更显式，`std::invoke`、`std::mem_fn`、`std::not_fn` 统一了调用形式和取反，concepts 把可调用性写进了接口。这些变化让 23.5 节那套 typedef 协议彻底成了历史，也让 23.6 节的局部类模拟只剩教学价值。

但“值不值”的问题语言管不了：捕获的引用会不会比闭包先死、谓词里有没有藏着计数器、函数对象拷贝起来贵不贵、重载名能不能落到唯一的目标上，都得靠设计。工具能帮一部分：ASan 在真的发生悬垂时抓住它，`-Wdeprecated-this-capture` 和 `cppcoreguidelines-misleading-capture-default-by-value` 抓 `[=]` 加隐式 `this`，`-Wdeprecated-declarations` 提醒旧适配器还在被使用；纯度和拷贝成本没有现成的检查器，只能靠“捕获列表写明白、`operator()` 写 const、重状态放外面”这些习惯。标准算法和 ranges 算法仍然按值接收谓词，这条约定没有随新标准改变，它正是前面所有设计准则的地基。
