# 第 13 章 错误处理策略：异常、错误码与 expected 的边界

一个服务在缓存里查用户配置，查不到是每天几万次的常态：

```cpp
std::string get_config(const std::string& key) {
    if (auto it = cache.find(key); it != cache.end()) return it->second;
    throw NotFound{key};          // 每一次未命中都变成异常
}
```

调用方只好在每个请求外面套一层 `try/catch`，把“没有配置”和“配置文件损坏”记进同一个错误日志。监控上看，错误率跟着缓存命中率一起波动，真正需要处理的磁盘故障反而被淹没了。

这段代码编译、运行都没有问题，问题在于它把“正常的没有”和“契约被破坏”混成了一种信号。本章沿着两个问题走：一个函数该抛异常、返回错误码，还是返回一个可能没有值的对象；错误又该在哪一层被报告、传播、翻译和处理。前者是接口形状，后者是分层策略，两者都取决于同一件事——函数的契约到底承诺了什么。C++11 的 `std::error_code`、C++17 的 `optional` 和 `[[nodiscard]]`、C++23 的 `expected` 让表达方式变多了，但没有替任何人决定哪一类失败该走哪条路。

## 13.1 先定策略，再定什么算错误

Sutter 与 Alexandrescu 在 CCS-69 里把错误处理策略拆成六件事：识别（哪些条件算错误）、分级（多严重、多紧急）、检测（哪段代码负责发现）、传播（模块内部用什么机制把错误送到上层）、处理（谁负责采取行动）、报告（日志、用户提示、告警怎么走）。他们要求在设计早期就把这套策略定下来，并且严格执行；最忌讳的不是选错机制，而是同一个模块里一半函数抛异常、一半函数返回错误码，调用方根本写不出可靠的处理代码。

这里的“模块”指子系统或库的边界，不是 C++20 的 module。CCS-69 允许模块内部和模块接口使用不同的机制：C++ 实现内部统一用异常，对外的 C API 统一返回错误码，这很常见；但所有入口函数都要负责在边界上转换，回调函数和线程入口按定义也在边界上。策略一旦在某个边界切换，就必须在每一个入口切换，不能有的入口转、有的入口漏。第 35 章讲 C 互操作时会再碰到这些边界（CCS-62），13.2 会给出一个转换的例子。

策略里最容易含糊的是第一项：什么算错误。CCS-70 给了一个可以逐函数执行的判据：函数是一个工作单元，一次失败只有在下面三种情况下才算错误——它检测到自己的前置条件被违反，或者它无法达成自己的后置条件，或者它退出时没能恢复自己负责的不变式。其余情况都是合法结果，不应该按错误上报。

前置条件由调用方负责满足，后置条件由被调函数负责建立。非私有成员函数在函数体中途破坏不变式是正常且必要的：一个同时维护 `std::vector` 和 `size_` 的类，在追加元素和更新 `size_` 之间，两个值会短暂对不上；只要函数返回前把不变式恢复，就没有问题。“带着被破坏的不变式离开函数”才是缺陷。下面这个 `Schedule` 把三种情况分得很清楚：`at` 的前置条件是下标在范围内，违反时抛 `std::out_of_range`；`find` 找不到标题是合法结果，返回空指针；`add` 的前置条件是标题非空，后置条件是加入后不超过容量，两种失败分别抛 `std::invalid_argument` 和 `std::length_error`。

同一个 `std::vector` 类型也能说明“同一个条件，在不同函数里地位不同”。`vector::at` 把越界当作前置条件违反，抛 `std::out_of_range`；`vector::operator[]` 的前置条件同样是下标有效，但它明确不检查，越界是未定义行为（undefined behavior，UB），责任完全在调用方。两者都不是“越界是正常结果”，区别只在于违反契约后由谁发现、用什么代价报告。`find` 这类查找函数则相反：未命中本来就是它的正常返回之一，硬把它翻译成异常，等于让调用方为每次未命中付一次栈展开的代价，也把“没有”排除在了返回值类型之外。

如果只保留 `require` 而删掉 `lookup`，那么所有想“有就用、没有就用默认值”的调用方都只能靠捕获异常来走正常分支；如果只保留 `lookup` 而删掉 `require`，每个需要该配置的调用方都要重复写一次“为空就抛”的检查，错误类型和消息也会各写各的。两个函数并存不是接口冗余，而是把“是不是错误”的决定放在拥有足够上下文的那一层——这正是 13.2 要展开的报告与处理分层。

CCS-70 还提醒了一条容易被忽视的限制：一条条件只有在“要求所有调用方在调用前检查它是合理的”时，才适合写进前置条件。一个接受文件名的函数如果把“文件存在”写成前置条件，调用方其实无法可靠地满足它——检查完到真正打开之间，另一个进程可能已经把文件删掉或改名；要加锁才能消除这个竞态，而锁又不在调用方的职责里。正确做法是换成更强的类型：要求调用方先打开文件，把已经打开的流或文件对象传进来。这样“文件存在且可读”由类型和构造过程保证，函数不必再处理一个自己既不该检查、也检查不好的条件。很多前置条件都可以这样被类型消掉，把运行期错误提前成编译期错误。

再往下走一层，如果条件违反只可能是同一团队内部的编程错误——调用方和被调方在同一个模块里，参数错误说明代码写错了——那就不该用异常，而该用断言（CCS-68）。断言在发布构建里可能被关掉，所以它只适合“这里出错就说明程序有 bug，继续跑也没有意义”的场合；用户输入、文件损坏、网络断开这些外部失败不能用断言兜底。CCS-69 把这条边界也写进了策略：异常处理针对的是运行期错误，不是内部编码错误。

新标准没有改变“是否违反契约”这条判据，只是多了几种表达“没有值”和“可恢复失败”的类型。C++17 的 `std::optional` 适合“没有值但不是错误”，C++23 的 `std::expected<T, E>` 适合“失败要带原因、但调用方很可能就地处理”。它们让 13.4 的接口替代成为可能，却不能替人判断某个未命中该不该算错误；CCS-70 的原话是“任何其他条件都不是错误，因此不应该作为错误上报”，这句话在 C++20 之后仍然成立。C++20 曾计划引入 contracts，最终在 2019 年被撤出；C++26 重新采纳了一版（P2900：函数声明上的 `pre(...)`、`post(...)` 和语句 `contract_assert(...)`），但本书环境的 clang 21 和 GCC 15 都还不能编译它，所以今天把契约写进类型、注释、断言和测试仍然是主要手段。

落到写法上，这一节给出的检查顺序是：先写清函数的前置条件、后置条件和它维护的不变式；再问“这个失败违反了哪一条”；如果答案是“都不是”，就把它做成正常返回值，而不是异常或错误码。接口设计时优先用类型把能静态保证的条件表达出来，剩下的运行期条件才留给异常或错误码。这个顺序确定之后，13.2 才谈得上选异常还是错误码。

## 13.2 异常优先，但报告、抛出、捕获和翻译都要守规矩

13.1 把错误从正常结果里挑出来之后，下一步才是选报告机制。CCS-72 的结论很明确：默认用异常报告错误，状态码留给非错误的状态，以及确实不能用异常的场合。理由不是“异常更现代”，而是四条具体的性质。异常无法被静默忽略——想忽略必须显式写 `catch`，错误码可以只写 `read(...)` 而把返回值丢掉；异常会自动跨作用域传播——中间层不必为了把错误送到上层而写一行转发代码，错误码则要在每一层手写检查；异常把恢复代码从主控制流里挪进 `catch`，正常路径不必被 `if (rc != 0)` 切碎；构造函数没有返回类型，不少运算符的签名也不能随便加一个错误码参数，错误码在这些位置没有自然的位置。

错误码最致命的弱点就是这里的“默认被忽略”。给返回码加 C++17 的 `[[nodiscard]]` 能把一部分漏检变成编译期警告（13.4 会看到），但它只能覆盖返回值，覆盖不了 `errno` 这种旁路状态，也覆盖不了“检查了却只记日志、不处理”的写法。异常也不是万能的：`catch (...)` 同样可以静默吞掉一切，只是这个动作必须显式写出来，评审时看得见。

CCS-72 并没有说异常适用于所有场合。它给出两个同时成立才考虑错误码的条件：异常的收益完全不适用，比如几乎总是由直接调用方就地处理、几乎不需要传播；并且实测抛出比返回码慢，而这个差异真的影响关键路径。硬实时项目关闭异常处理是最后的最后手段，即便关也应该只限少数模块。性能通常不构成理由：不抛异常时，异常处理的开销通常接近于零，但必须打开编译器的异常支持，否则 `operator new` 和标准库无法按标准报错。反过来说，如果 `try` 块的成功次数和失败次数在同一数量级，那多半是把正常控制流当成了异常——13.1 的查找未命中就是一个典型。

按引用捕获的理由是保留动态类型：`catch (const std::exception&)` 能接到派生类异常并调用派生类的 `what()`，按值捕获 `std::exception` 则会切片，只剩基类部分。重抛写 `throw e;` 会按 `e` 的静态类型再复制一份，同样会切片；`throw;` 重抛当前正在处理的异常对象，不复制，也不改变动态类型。第 11 章已经用例子量过这几种写法的复制次数和切片结果（MEC-12、MEC-13），这里只补一个本章关心的推论：翻译异常时如果写 `catch (const LowLevel& e) { throw HighLevel(e.what()); }`，原始异常的类型和附加信息就丢了；C++11 的 `std::throw_with_nested` 把原异常挂在 `std::nested_exception` 里，捕获方可以沿链取回，既完成了翻译，又没有把低层原因抹掉。跨线程搬运异常则用 `std::exception_ptr`、`std::current_exception()` 和 `std::rethrow_exception()`，它们保存的是异常对象本身，重抛时动态类型不变。

有了机制，还剩分层问题：在哪一层报告、在哪一层处理、在哪一层翻译。CCS-74 给的三句话可以直接当检查表。报告在检测到并确认它是错误的地方——也就是 13.1 判据成立、函数自己解决不了、继续执行也没有意义的位置。处理在有足够知识正确处理它的最近一层；典型的位置是 `main`、线程入口，以及析构函数和释放函数内部，这些地方必须吞掉异常（第 11 章讲过为什么析构不能让异常逃出去）。翻译只有两个正当理由：补充高层语义，比如把“文件意外结束”翻译成“文档损坏”；或者更换报告机制，比如模块内部用异常、C API 边界上转成错误码。

没有上下文做任何有用事情的中间层，不应该“接受”错误：既不吞掉，也不为了留痕而层层包装。每层都 `catch` 再 `throw` 同一个异常，除了增加栈展开和日志噪声，没有改变任何事情；CCS-74 只允许一种例外——为了加日志、计数等埋点而捕获并原样重抛，此时并没有真正处理它。真正需要补充语义时，翻译要带着原始信息走，别把 `e.what()` 拼成一个字符串就丢掉类型；需要按类型区分处理时，保留异常类型比保留文本更有用。

C++11 起，标准库把“错误码加类别”规范成了 `std::error_code`/`std::error_condition`，系统调用和 C API 的错误可以用 `std::system_error` 在边界上转成异常，也可以反向转回去；`std::error_code` 的 `category` 让不同来源的错误码有可比较的语义。C++23 的 `std::expected<T, E>` 则让“边界函数返回错误值而不是抛异常”有了类型安全的写法，13.4 会用它替代 `bool` 加输出参数。它们改变的是错误的表达方式，不是 CCS-74 的分层原则：检测点报告，能处理的最近一层处理，只在补充语义或更换机制时翻译。

工具方面，clang 21 的 `-Wexceptions` 会抓 `catch` 顺序问题和 `noexcept` 函数里的直接 `throw`；GCC 15 用 `-Wterminate` 抓同样的 `noexcept` 冲突，用 `-Wexceptions` 抓 `catch` 顺序，另外还有 clang 没有的 `-Wcatch-value`，对“按值捕获多态类型”给出警告，而 clang 21 没有 `-Wcatch-value` 这个选项（本机实测会报 unknown warning option），所以同一段代码在两个编译器下的提醒并不对称。clang-tidy 21 的 `bugprone-exception-escape` 检查可能从 `noexcept` 函数或析构函数逃出的异常，适合放在 CI 里补编译器警告的盲区。

## 13.3 what() 的指针要活到异常销毁，catch(...) 抓不到崩溃

异常类型是错误信息跨越栈帧的载体。Lippman 在 ESS-15 里关心的是这个载体上的文本接口：从 `std::exception` 派生并覆盖 `what()` 时，返回的 `const char*` 必须指向一块在异常对象存活期间一直有效、且不会被下一次调用悄悄改掉的缓冲区。三种常见写法正好对应三种结局。

动态异常规格本身也是这段历史的一部分：C++11 弃用 `throw(类型列表)`，C++17 移除它，`throw()` 保留为 `noexcept(true)` 的弃用写法、C++20 才移出标准（EXS-13，第 12 章）。今天要声明“不抛”就写 `noexcept`，不要再写空的 `throw()`。

这条约束有实际后果：`what()` 里不能做可能抛异常的事情，包括分配内存、拼格式化字符串、调用可能失败的 I/O。消息应当在构造函数里构造好；如果消息本身需要格式化，就在构造函数里用 `std::ostringstream` 或 `std::format` 生成，再存进成员。`what()` 只做一次 `c_str()` 返回。

Lippman 在 ESS-16 里换了一个方向：`catch (...)` 看起来什么都能接，但它接的只是“某处 `throw` 出来的对象”。空指针解引用、数组越界、除零这些是硬件异常或未定义行为，标准 C++ 没有把它们变成 C++ 异常的机制；`std::terminate` 也不是抛出来的，`catch (...)` 同样接不住。下面的程序先让 `catch (...)` 接住 `throw 42`，再解引用空指针：

空指针解引用是未定义行为，本机在 ASan 下表现为 SEGV；换一个平台或优化选项，它也可能表现为别的东西，但不会是能被 `catch (...)` 接住的 C++ 异常。`catch (...)` 的正当用途是在模块边界做最后清理、记日志，然后把异常重新抛出或翻译成边界约定的错误码；它不是把崩溃恢复成继续运行的开关。把 `catch (...)` 写在业务逻辑里吞掉一切，只会让程序带着被破坏的状态继续跑。

这类错误要靠断言、静态分析、ASan/UBSan 和测试去发现。`assert` 在 `NDEBUG` 下会消失，不能当运行期错误处理；它适合抓“这里出错说明程序有 bug”的内部违反。Windows 的 SEH、POSIX 的 `signal` 加 `siglongjmp` 是平台扩展，和 C++ 的栈展开、析构顺序不保证兼容，跨平台代码不要依赖它们把信号变成异常。C++23 的 `std::stacktrace` 能让诊断信息更完整，但它只是记录“从哪里来”，不改变“异常只能由 throw 产生”这个模型；C++26 的 contracts 检查的是程序员写下的条件，同样不能捕获硬件错误。

## 13.4 bool + 输出参数应被 optional/expected 取代

Lippman 在 ESS-18 里用 `bool fibon_elem(int pos, int& elem)` 举例，这是一个很典型的旧接口：成功返回 `true` 并把结果写进 `elem`，失败返回 `false`，也把 `elem` 写成一个约定好的值。它有三个问题。调用方必须先构造一个 `elem`，即使函数失败，这个对象也已经被写过；返回值和输出参数是两条独立的信息通道，调用方可以只看其中一条；失败时写什么值完全靠文档约定，`0` 常常同时是合法结果和失败标记。

`E` 可以是枚举、结构体，也可以是 `std::error_code`；选枚举还是带消息的结构体，取决于调用方需不需要把原因展示给用户。`expected` 的成员函数 `value()` 在无值时抛 `std::bad_expected_access<E>`，所以它并不要求调用方关掉异常；如果项目不使用异常，就用 `has_value()`/`error()` 分支，别调用会抛的 `value()`。C++23 还给 `expected` 加了 `and_then`、`transform`、`or_else` 这些单子操作，例子里的 `transform` 只在有值时执行转换，错误原样保留；本机 Clang 21 + libstdc++ 15 和 GCC 15 都用 `-std=c++23` 编译运行通过，用更早的标准则没有 `std::expected`。

三种返回类型的分工可以这样记：`optional<T>` 表达“可能没有”，不解释原因；`expected<T, E>` 表达“可能失败，失败有原因”，适合调用方大概率就地处理的错误；异常表达“函数无法完成契约，且错误需要跨层传播”，尤其是构造函数、运算符和那些中间层没有上下文处理的失败。`expected` 不能取代构造函数里的异常——构造函数没有返回值可以包；也不适合“每层都要补充语义”的深调用链，因为每一层都要把 `expected` 拆开再重新包装，代码会比 `throw` 更啰嗦。CCS-72 的“默认用异常”仍然成立，`expected` 是给那些“错误频繁、调用方就在旁边、不想付栈展开代价”的接口准备的。

`[[nodiscard]]` 也可以加在返回 `optional`/`expected` 的函数上，让“忽略了可能失败的结果”变成编译期警告；它和这两种类型是互补的，不是替代关系。需要一次返回多个值时，C++17 的结构化绑定可以解包 `std::tuple` 或普通结构体，但“成功/失败”仍然建议用 `expected` 表达，不要把 `bool` 和几个输出参数重新拼成一个元组。跨 C ABI 时不要直接传 `optional`/`expected`：它们不是 C 类型，布局由标准库实现决定，C 调用方也读不懂；在边界上转成状态码加输出参数或固定布局的结构体，进入 C++ 后再包成 `optional`/`expected`（CCS-62，第 35 章）。

工具上，`-Wunused-result` 是 `[[nodiscard]]` 的主力；clang-tidy 21 的 `bugprone-unused-return-value` 默认把 `std::expected`、`std::error_code` 等类型列为要检查的返回类型，能覆盖一些编译器不警告的“返回值被丢弃”情形，适合在 CI 里对关键接口开启。它们都只能抓“没看返回值”，抓不到“看了但处理错了”——后者仍然要靠 13.1 的契约和 13.2 的分层来判断。

## 回头看

四节其实在回答同一个问题的四个阶段：契约先决定什么算错误，机制决定错误怎么离开检测点，分层决定谁处理、谁翻译，类型决定接口把“没有值”和“失败”表达成什么。13.1 的判据如果含糊，后面选异常还是 `expected` 都会变成口味之争；13.2 的默认异常如果被“每层都 `catch` 一下”破坏，分层就退化成日志噪声；13.3 的 `what()` 和 `catch (...)` 是异常载体的边界，前者管信息活多久，后者管哪些失败根本不在这套机制里；13.4 的 `optional`/`expected` 把“可能没有”和“可能失败”从文档约定搬进类型，但它们只在契约清楚时才有意义。

C++11 以后，标准库补上了 `exception_ptr`、`nested_exception`、`error_code` 和 `noexcept`；C++17 补上 `optional` 和 `[[nodiscard]]`；C++23 补上 `expected`。语言能保证异常对象的复制和销毁、`what()` 的 `noexcept`、忽略 `[[nodiscard]]` 返回值时的警告，但不能保证每个函数的前置条件写得对、每个边界都做了翻译、每个 `what()` 都不返回悬垂指针。剩下这些仍然靠设计时定策略、写代码时守契约，以及 ASan/UBSan、`-W` 选项和 clang-tidy 在 CI 里把关。
