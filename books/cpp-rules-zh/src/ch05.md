# 第 5 章 auto、decltype 与完美转发：编译器到底推成了什么

下面这个转发函数看起来只是把参数原样交给下一层：

```cpp
template <typename T>
void relay(T&& value) {
    sink(std::move(value));   // 无条件当成右值
}

std::string name = "Ada";
relay(name);                  // name 被搬空，调用者却以为只是读了一下
```

`T&&` 在这里不是“右值引用”四个字能解释的：传左值时 `T` 推成 `std::string&`，形参经引用折叠变成 `std::string&`；传右值时 `T` 才是 `std::string`。而函数体里的 `std::move` 不管这些，一律把 `value` 转成右值，于是左值也被偷走。要看出这两步，得先知道编译器把 `T` 推成了什么。

本章沿着“一个声明到底让编译器推出了什么类型”往下走。函数模板和 `auto` 共用一套算法，区别只在花括号和少数退化规则；`decltype` 另有一套更“照抄”的规则；通用引用和引用折叠把左值/右值信息编码进 `T`；`std::move`/`std::forward` 只是两种 cast，真正决定调用哪个构造函数的是重载决议；最后看完美转发在哪些实参上会推不出或推错。

## 5.1 函数模板和 auto 到底把类型推成了什么

先看一个不需要任何运行期输出的问题：调用 `f(x)` 之后，`T` 是 `int`、`int&` 还是 `const int&`？很多人会凭“`x` 是 `int`”回答 `int`，但答案取决于形参写成 `T`、`T&`、`const T&` 还是 `T&&`。Meyers 在 EMC-01 里把这件事拆成三类，依据不是函数体，而是 `ParamType` 的形状：指针或普通引用、通用引用、按值。

第一类是非通用引用的指针或引用形参。编译器先忽略实参表达式的引用性，再拿剩下的类型去匹配 `ParamType`。实参的 `const` 会留在 `T` 里，除非形参自己已经写了 `const`。所以 `T&` 遇到 `const int` 得到 `T = const int`，而 `const T&` 遇到同样的实参得到 `T = int`，`const` 由形参提供。第二类是 `T&&` 且 `T` 参与推导的通用引用，左值实参让 `T` 推成左值引用，右值实参让 `T` 推成非引用；这是三类里唯一会把 `T` 推成引用的情形。第三类是按值形参，引用性、顶层 `const` 和 `volatile` 都被丢掉，因为形参是一个独立的新对象，实参能不能改与这个副本能不能改无关。

数组和函数是这套规则里的两个特殊角落。数组名在大多数表达式里会退化成指向首元素的指针，所以按值形参推出 `const char*`；但引用形参可以保留数组类型本身，`T` 推成 `const char[13]`，函数形参因此是 `const char (&)[13]`。这也是 `array_size` 这类模板能工作的原因：`N` 从数组类型里数出来，不需要额外的 `sizeof` 除法。函数名同理，按值退化成函数指针，按引用保留函数类型。实际代码里很少直接写“引用的数组”，但范围 for、C++17 的 `std::size` 和模板库都依赖这条规则。

`auto` 的推导几乎是同一套算法：把 `auto` 当成模板参数 `T`，把声明里 `auto` 前面的修饰（`const`、`&`、`&&`、`*`）当成 `ParamType`。`auto x = 27` 对应按值，`const auto& rx = x` 对应 `const T&`，`auto&& uref = x` 对应通用引用。数组和函数名的退化也照旧。

## 5.2 auto 省事，但可能存下代理对象

`auto` 最直接的好处是消灭“写错类型”的机会。EMC-05 列了四种典型：变量必须有初始化器，因此不会留下未初始化的 `int`；`v.size()` 存成 `auto` 就是 `size_type`，不必猜它是不是 `unsigned`；遍历 `unordered_map` 时 `const auto&` 能绑定到真正的 `pair<const Key, T>`，不会每轮构造临时 `pair`；闭包的类型只有编译器知道，`auto` 能原样保存它，而 `std::function` 会做类型擦除。

最后一点值得展开。在同一个实现里，同一签名的 `std::function` 大小是固定的，闭包装不下时它通常会去堆上分配；调用要通过间接层，通常比直接调用闭包慢。`auto` 保存的变量类型就是闭包本身，大小等于闭包实际需要的大小。下面的例子同时统计了错误 `pair` 类型造成的复制，并打印本机两种保存方式的大小。

原书写这段时，`auto highPriority = features(w)[5];` 的悬垂是“未定义行为，可能过很久才炸”；ASan 把它变成一条确定的 `heap-use-after-free`。这不是说 `auto` 不好，而是说 `auto` 推出的是初始化表达式的类型，不是你脑子里想要的那个类型。EMC-06 给的修法是“显式类型初始化器”（explicitly typed initializer idiom）：仍然写 `auto`，但用 `static_cast<bool>` 把表达式先转成目标类型，再让 `auto` 推。`auto corrected = static_cast<bool>(flags[4]);` 既保留了“必须初始化、不重复写类型”的好处，又保证变量是 `bool`。如果只是声明处写 `bool value = flags[4];`，效果一样，但 `static_cast` 把“我在这里故意换了类型”写得更显眼，也适用于 `double` 转 `float`、浮点转下标这类有损转换。

今天的做法可以总结成三句话。默认用 `auto`，因为它避免类型捷径、强制初始化、跟得上重构；初始化表达式来自临时对象、且返回类型看起来不像普通 `T&` 时，用 `static_cast<T>` 或显式类型把它落回值；花括号和代理是 `auto` 的两个已知缺口，前者在 5.1 节，后者在本节，其他场合不必因为这两个缺口退回手写类型。

## 5.3 decltype 与别名：把推导出的类型写出来

按值的 `auto` 和按值的模板推导都在“去掉一些东西”：引用、顶层 `const`、数组的维度。`decltype` 的默认行为相反，它几乎照抄你给它的名字或表达式。Meyers 在 EMC-03 里把规则压成两句：给一个名字，得到这个名字的声明类型；给一个比名字复杂的左值表达式，如果它的类型是 `T`，得到 `T&`。再加两条值类别：将亡值（xvalue）得到 `T&&`，纯右值（prvalue）得到 `T`。

“名字”和“表达式”的分界比想象中细。`decltype(x)` 里 `x` 是名字，得到 `int`；`decltype((x))` 里 `(x)` 是一个左值表达式，得到 `int&`。多一对括号就多一层引用，这在普通代码里只是冷知识，但配上 C++14 的 `decltype(auto)` 就会改变函数的返回类型：`return x;` 返回 `int`，`return (x);` 返回 `int&`。如果 `x` 是局部变量，后者返回的是悬垂引用。

最后是别名。EMC-09 的建议是优先写 `using X = ...;`，而不是 `typedef ... X;`。对普通类型两者完全等价，真正的差别在模板：`typedef` 不能直接参数化，C++98 只能用一个模板结构体包一个 `typedef type`，用的时候写 `OldRow<T>::type`，在模板里还得加 `typename`；alias template 写 `Row<T>`，名字本身就是类型，既不用 `::type` 也不用 `typename`。

```cpp
template <typename T>
using Row = std::vector<T>;

template <typename T>
struct OldRow {
    typedef std::vector<T> type;
};
```

示例里的 `build_rows` 把两种写法放在同一个函数模板里，`static_assert` 证明它们推出同一个类型，`typename OldRow<T>::type` 则展示了旧写法多出来的那层语法。alias template 有一个限制：它不能被特化；如果确实需要为某个类型换实现，仍要用类模板包 `type`，或者用 `if constexpr`、concepts 在别名指向的模板上做选择。C++14 给所有 C++11 的类型变换加了 `_t` 版本，`std::remove_const_t<T>` 就是 `typename std::remove_const<T>::type` 的别名；这本书以 C++20 为基准，直接写 `_t` 即可。

## 5.4 通用引用不是右值引用：引用折叠决定一切

源码里的 `T&&` 有两种完全不同的含义。一种是右值引用：它只绑定右值，用来标记“这个对象可以被搬走”。另一种能绑定左值、右值、const、non-const，几乎什么都能接。Meyers 在 EMC-24 里给它起名“通用引用”（universal reference），标准里的正式名字是转发引用（forwarding reference）。

判断一个 `T&&` 是不是通用引用，只看两件事：形式必须恰好是 `T&&`，并且 `T` 在这个位置参与推导。函数模板 `template<typename T> void f(T&&)` 满足，`auto&&` 变量满足，C++14 泛型 lambda 的 `auto&&` 参数、C++20 简写函数模板的 `auto&&` 也满足。`const T&&` 不满足，因为形式多了 `const`；`std::vector<T>&&` 不满足，因为 `T` 被包在 `vector` 里；类模板的成员 `void push_back(T&&)` 看起来是 `T&&`，但 `T` 在类实例化时就固定了，调用 `push_back` 时不再推导，所以它是右值引用。同一个类里的 `template<class... Args> void emplace_back(Args&&...)` 则是通用引用，因为 `Args` 是每次调用独立推导的。同样的机制也用在类模板的广义拷贝构造上：`SmartPtr<U>` 到 `SmartPtr<T>` 的转换靠成员函数模板，而不是为每种类型写一个重载；EC-45 讲这条，[第 20 章](ch20.md)会展开它和普通拷贝构造的关系。

三条错误都是“左值不能绑定到右值引用”。`const T&&` 不能靠 `const` 变成通用引用，`vector<T>&&` 不能靠“里面有 T”变成通用引用，类模板的 `T&&` 也不能靠“写在模板里”变成通用引用。反过来说，只要看到 `T&&` 就认为它能接左值，是读现代 C++ 时最常见的误判之一。

“通用”也不等于“无视 const”。通用引用能绑定 const 左值，但 `T` 会推成 `const X&`，函数里看到的仍是只读对象；想修改参数，就得在接口上拒绝 const 实参，或者按值接收一份副本。`auto&&` 同样有形式要求：`const auto&&` 多了 `const`，是普通右值引用，不能拿左值初始化。泛型 lambda 里常见的写法 `[](auto&& x) { f(std::forward<decltype(x)>(x)); }` 之所以成立，是因为 `decltype(x)` 正好就是那个编码了值类别的 `T`，不是另一套规则。

通用引用的底层机制是引用折叠（reference collapsing）。C++ 不允许直接声明“引用的引用”，写 `int& &` 会编译失败；但在模板实例化、`auto` 类型生成、`typedef`/alias 和 `decltype` 这四个语境里，编译器会临时造出“引用的引用”，再按一条规则折叠：只要两个引用里有一个是左值引用，结果就是左值引用；只有两个都是右值引用，结果才是右值引用。

## 5.5 std::move 和 std::forward 只是 cast

先纠正一个常见的心理模型：`std::move` 不移动任何东西，`std::forward` 也不转发任何东西。两者都是函数模板，运行期不生成一条指令，只改变表达式的值类别，让重载决议去挑移动构造、移动赋值或者接受右值的函数。真正搬走资源的是被选中的那个构造函数或赋值运算符。

Meyers 在 EMC-23 里把 `std::move` 的实现摊开：先对 `T` 做 `remove_reference`，再加 `&&`，然后 `static_cast` 成这个右值引用。`std::forward<T>` 则是条件 cast：`T` 是左值引用时，`T&&` 折叠成左值引用，cast 回左值；`T` 是非引用时，`T&&` 保持右值引用，cast 成右值。条件不是运行时判断，而是编码在 `T` 里的编译期信息。

`const` 对象上的 `move` 是另一个静默失败。`std::move(frozen)` 得到的是 `const Item&&`，移动构造接受 `Item&&`，两者不匹配；拷贝构造接受 `const Item&`，可以绑定到 const 右值，于是调用的是拷贝。示例里 `thawed` 拿到了值，`frozen.moved_from` 仍是假，拷贝计数加一。想移动就不要把对象声明成 `const`；`std::move` 只保证结果是右值，不保证这个右值能被移动。

最后一段说明“cast 本身无副作用”：把 `untouched` 转成右值引用、绑定到 `auto&&`，只要没有调用移动构造或移动赋值，对象一点没变。反过来，真正调用移动操作之后，源对象处于“有效但状态未指定”的状态，只能析构、重新赋值，或者调用不依赖其值的操作（[第 7 章](ch07.md)）。

返回局部对象是这条规则最容易被“优化”坏的地方。EMC-25 专门讲了 `return std::move(w);`：返回值优化（RVO）和具名返回值优化（NRVO）允许编译器把局部对象直接构造在返回值的位置，但前提是返回的表达式就是那个局部对象；`std::move(w)` 返回的是一个绑定到 `w` 的右值引用表达式，不是 `w` 本身，条件不成立，编译器只能移动。更糟的是，即使编译器不做 NRVO，标准也要求把 `return w;` 按右值处理（隐式 move），所以手写 `std::move` 帮不上忙，只会挡住消除。

## 5.6 完美转发会在哪里失败

完美转发的目标不是“把值传过去”，而是“让下一层看到和直接调用时一样的实参”：同样的类型、同样的左值/右值、同样的 const/volatile。只传值做不到这一点，按值形参会多一次拷贝；只传指针也不行，调用方被迫改变写法。通用引用加 `std::forward` 是通用解，但它不是万能的。Meyers 在 EMC-30 里把失败归结成两类：编译器推不出类型，或者推出来的类型让调用行为与直接调用不同。具体的实参有五类。

第一类是花括号初始化列表。直接写 `target({1, 2, 3})` 时，编译器看得到 `target` 的形参是 `const std::vector<int>&`，于是用列表构造一个临时 `vector`；经过 `fwd({1, 2, 3})` 时，编译器先要推导 `fwd` 的 `T`，而花括号对“不是 `initializer_list` 的模板形参”是非推导语境，推导直接失败。第二类是 `0` 和 `NULL`。直接 `target_pointer(0)` 里 `0` 是空指针常量，可以转成 `int*`；经过转发函数后 `T` 推成 `int`，`std::forward<int>` 产生的是一个 `int` 表达式，不再是字面量 `0`，空指针转换不适用。换成 `nullptr` 就没事，`T` 推成 `std::nullptr_t`，它能转成任意指针。

第三类是只有声明、没有定义的 `static const` 整型成员。直接按值使用 `Widget::MinVals` 时，编译器把 28 嵌进代码，不需要为它分配存储；一旦按引用传递，引用需要一个真实对象，链接器就找不到定义。本机用 Clang 21 和 GCC 15 各试了一次，都是编译通过、链接阶段报 `undefined reference to` 这个成员。C++17 的 inline 变量解决了这一类：`inline static constexpr std::size_t MinVals = 28;` 在类内就是定义，取地址也有实体。注意它只解决“用新写法声明”的成员；已有的 `static const` 声明不会自动变成 inline，仍要在 `.cpp` 里补 `const std::size_t Widget::MinVals;`。

第四类是重载函数名和函数模板名。直接 `target(process_value)` 时，`target` 的形参类型 `int (*)(int)` 反过来告诉编译器选哪个重载；经过 `fwd` 时没有任何目标类型信息，`process_value` 这个名字本身没有唯一类型，推导失败。函数模板名更明显：`work_on_value` 代表一族实例化，必须先指定 `work_on_value<int>` 或转成函数指针。第五类是位域。非 const 引用不能绑定到位域，因为位域可能只占机器字里的几位，没有独立地址；`T&&` 推导出来后要绑定引用，于是在推导或绑定阶段失败。下一层如果按值接收位域，它收到的本来就是一份拷贝，所以手工先拷贝到普通变量再转发，语义不变。

Sutter 在 EXC-46 里讨论的是另一类“转发函数”：不是泛型库里的 `fwd`，而是一个只把参数继续交给下一层的普通函数，比如 `bool f(X x) { return g(x); }`。他给出的第一条建议是按 `const X&` 接参，理由是 1997 年标准草案收紧了对“参数只用于继续传递”的拷贝消除许可，按值至少要多一次拷贝；第二条是不要默认 `inline`，先写在外层，等剖析证明调用开销显著再内联。EXC-46 写作时完美转发还不存在，所以它的“const& 默认”针对的是只读转发。

这两套建议今天可以并存：如果转发函数只读、不需要保留左值/右值身份，`const X&` 仍是最简单、最不容易出错的选择，也不会因为 C++17 的保证复制消除而失去意义——保证复制消除覆盖的是用纯右值初始化对象（包括用纯右值实参初始化形参），不包括把有名字的形参 `x` 再按值传给下一层时的那次拷贝。如果函数要收藏参数、要区分左值和右值、或者是 `make_unique`、`emplace_back` 这类泛型工厂，就用 `T&&` + `std::forward`，并用 concepts 把可接受的类型写清楚。`inline` 的含义也变了：它如今主要解决单一定义规则（ODR）和链接问题，是否真正内联由编译器决定；C++20 的 modules 能减少内联带来的重编译耦合，但不改变“先剖析、再优化”的顺序。完美转发会放大重载决议和实参依赖查找（ADL）的复杂度，这也是 EMC-26、EMC-27 把“不要对通用引用重载”单独拿出来讲的原因（[第 21 章](ch21.md)）。

## 回头看

这六节讲的是同一件事的不同侧面：声明写在源码里，类型却由编译器在另一层算出来。模板推导和 `auto` 是同一套算法，一个把 `auto` 当 `T`、把声明修饰当 `ParamType`；`decltype` 单独一套，对名字照抄、对左值加引用；通用引用不是新类型，而是“推导 + 引用折叠”造出来的假象；`move`/`forward` 只是把值类别重新标一下，真正的动作发生在被选中的构造函数里；完美转发则要求这套标注在每一层都不丢失信息。理解这条链，才能解释为什么 `auto` 有时得到代理、为什么 `T&&` 有时能接左值、为什么 `return std::move(w)` 反而更慢、为什么一个花括号就让转发函数找不到类型。

C++17 和 C++20 替我们修掉了几处旧坑，也挪动了几处边界。C++17 改了 `auto` 直接列表初始化的规则，让 `auto x{1}` 得到 `int`；C++17 的 inline 变量让 `static constexpr` 成员按引用传递也有定义；C++17 的保证复制消除让返回纯右值不再需要拷贝构造，但 NRVO 仍是可选优化，`return std::move(w)` 仍然会挡住它。C++20 的简写函数模板和 concepts 扩大了通用引用的用武之地，也让转发函数的约束更清楚，但没有让花括号变成可推导类型，没有改变 `decltype` 的规则，也没有让 `typeid` 保留引用和 const。剩下的仍要靠写法：用 `auto` 时留意代理和临时对象，用 `decltype(auto)` 时留意括号，对通用引用只 `forward` 不 `move`，返回局部对象时直接写名字，转发失败的五类实参按 5.6 节的办法绕开。

工具能拦下一部分。clang 和 GCC 的 `-Wrange-loop-construct` 会指出 `unordered_map` 循环里的错误 `pair` 类型，`-Wpessimizing-move` 会指出 `return std::move(w)`，clang 的 `-Wreturn-stack-address` 和 GCC 的 `-Wreturn-local-addr` 会指出返回局部变量引用的 `decltype(auto)`；ASan 把悬垂代理变成确定的 `heap-use-after-free`，而不是“偶尔算错”。这些检查都不改变规则本身，只是把“编译器推成了什么”提前摆到眼前。真正要养成的习惯，是在写下 `auto`、`T&&`、`decltype(auto)` 和 `std::move` 时，能自己先说出编译器会推出什么、调用会落到哪个重载上。
