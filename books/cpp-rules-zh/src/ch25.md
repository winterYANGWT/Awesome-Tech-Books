# 第 25 章 关联容器与比较器：等价不是相等

一个忽略大小写的拦截名单里存着 `"Admin"`。有人用 `find` 成员函数查 `"admin"`，命中；同一份数据交给 `std::find`，却返回 `end()`。更奇怪的是，再插入一次 `"ADMIN"`，容器大小没有变。三个操作，两个答案：

```cpp
std::set<std::string, IgnoreCase> blocked{"Admin"};
blocked.insert("ADMIN");                    // 没有插入：与 "Admin" 等价
blocked.find("admin") != blocked.end();     // true
std::find(blocked.begin(), blocked.end(), "admin") == blocked.end();  // 也是 true
```

问题不在 `find` 或 `insert` 谁有 bug，而在它们用了两套“相同”的定义。`std::find` 用 `operator==` 判断相等，关联容器用比较器判断等价。有序关联容器必须维护元素的顺序，于是它只保留一个比较器，并让这个比较器同时决定“谁排在谁前面”和“两个键算不算同一个”。相等是另一个关系，两者可以不一致。

沿着这条线索往下走，会依次碰到几个问题：查找为什么该用成员函数、比较器为什么必须满足严格弱序、存指针时为什么排序结果和字符串内容无关、键插入后为什么不能原地改，以及 `map` 的插入与更新接口怎样按“键是否已存在”来选。C++11 以后的 `unordered_*`、C++14 的透明比较器、C++17 的节点句柄、C++20 的 `contains` 和 `<=>`，都在不同位置上改写这些问题的写法，但没有改写“等价由比较器定义”这个前提。

用公式写出来，两个键 `a`、`b` 关于容器 `c` 等价，当且仅当

```cpp
!c.key_comp()(a, b) && !c.key_comp()(b, a)
```

`key_comp()` 返回容器持有的比较器。默认比较器是 `std::less<Key>`，对大多数类型就是调用 `operator<`；自定义比较器则完全可能忽略大小写、只比较某个成员，或者按绝对值排序。等价只关心“参与排序的那部分”，`operator==` 可以关心别的成员，这正是 Meyers 在 ESTL-19 里区分的相等与等价。

关联容器只保留一个比较器，不是为了省一个模板参数。设想一个“排序忽略大小写、判等区分大小写”的容器：先插入 `"Persephone"`，再插入 `"persephone"`。排序器说这两个字符串之间没有先后，判等器说它们不相等，那么第二个元素该放在哪里？如果放进去，容器就失去了确定的遍历顺序；如果不放，之后按判等器查找又会失败。ESTL-19 用这个两难说明：让一个比较器同时负责顺序和身份，虽然初看别扭，但避免了“两套比较函数互相打架”的无解局面。无序容器走另一条路：C++11 的 `unordered_*` 用哈希函数定位桶，再用 `equal_to` 判等，根本不需要排序，也就没有“等价”这个概念；同一个键要在哈希和判等两处保持一致，这是另一种约束。

`count` 和 `equal_range` 也遵循同一套定义。它们的名字里有“相等”，统计的却是等价元素：在一个忽略大小写的 `multiset<string>` 里，`count("content-type")` 会把 `"Content-Type"`、`"content-type"` 这些写法都算进去，尽管 `operator==` 只认其中一种写法。名字和语义的错位，是 ESTL-19 要读者记住“等价不是相等”的另一个原因。

查找为什么不能拿 `std::find` 代替成员函数，到这里就清楚了：`std::find` 逐个比较 `operator==`，既不知道比较器，也要线性的时间；成员 `find` 走树，用等价判断，是对数时间。ESTL-44 把这条建议概括成“同名成员函数优先于泛型算法”，完整的讨论在[第 27 章](ch27.md)。如果使用模式是批量建立、大量查找、几乎不插入删除，排序 `vector` 加二分查找往往比树容器更省内存、缓存更友好（ESTL-23，[第 24 章](ch24.md)）；树容器适合查找与插入删除交织的场景。这里还要补一句新标准的变化：C++14 起，比较器可以定义 `is_transparent` 并接受多种键类型，成员 `find`、`count`、`lower_bound`、`equal_range` 就能直接收 `const char*` 或其他键类型，不必先构造一个 `std::string`；C++17 有了 `std::string_view` 之后，`string_view` 也能直接传进去。示例里的 `HeaderLess` 正是这样写的。C++23 又把异质键扩展到 `erase` 和 `extract`（P2077），但本机的 libstdc++ 15 和 libc++ 21 都还不接受 `erase(string_view)`。这些特性只影响调用形式，不影响“等价由比较器定义”。

C++20 的 `<=>` 很容易让人以为关联容器会改用 `==`。不会。`set`、`map` 仍然只调用比较器，`<=>` 只改变 `operator<`、`operator==` 这些运算符的生成与改写方式。如果类型同时定义了 `<=>` 和 `==`，而自定义比较器又与它们语义不一致，等价和相等的分叉只会更隐蔽：排序按一套规则，判等按另一套规则，`std::find` 和成员 `find` 继续给出不同答案。`std::strict_weak_order` 概念（C++20，`<concepts>`）能检查比较器“可调用、返回布尔、参数类型对得上”，但检查不了它运行时是否自相矛盾；示例里的 `static_assert` 通过，不代表比较器一定正确。

这种分叉在测试里也会出现。生产代码用 `set::find` 判断某个头字段是否存在，测试却用 `std::find` 遍历容器做断言，于是测试可能在功能正确时失败，也可能在功能错误时通过；两边都“找到了”或都“没找到”时，也不代表它们检查的是同一个东西。写测试时要么调用和产品代码相同的成员函数，要么明确断言“按比较器等价”和“按 `==` 相等”两个结论，别让测试替另一套语义背书。

比较器真正必须满足的是严格弱序（strict weak ordering）。最容易违反、后果也最直接的一条是：对相等的值必须返回 `false`。ESTL-21 用 `std::less_equal<int>` 做例子：它判断等价时计算 `!(10 <= 10) && !(10 <= 10)`，结果是 `false`，于是 `set` 认为两个 `10` 不等价，会把第二个也插进去。标准上这是未定义行为（undefined behavior，UB）；在本机的 libstdc++ 15 上连续插入三个 `10`，`set` 会把它们全部留下，而 `equal_range(10)` 返回空范围——容器既不再像 `set`，也没法正确回答“哪些元素等价于 10”。书里想要降序时还有另一个常见错法：把 `*a < *b` 取反写成 `!(*a < *b)`，那等于 `>=`；正确做法是交换实参，写 `*b < *a`。

第一组按数组下标顺序打印，也就是地址升序，与字符串内容毫无关系；第二组才是字典序。`set<std::string*>` 展开是 `set<std::string*, std::less<std::string*>>`，`std::less` 对指针比较地址。这里用同一个数组的元素而不是 `new` 出来的字符串，是因为数组元素的地址随下标递增，输出才是确定的；换成堆上的独立分配，顺序就取决于分配器这次给了哪些地址，每次运行都可能不同。ESTL-20 的例子里，四个动物名按地址排有 24 种可能，道理相同。

`std::less` 对指针还有一个容易忽略的性质：它保证任意两个指针之间都有确定的顺序，即使它们指向不相关的对象；直接用内置的 `<` 比较不相关对象的指针，结果未指定。所以“默认按地址排序”不是实现细节，而是标准保证的行为，只是这个顺序对业务没有意义。C++14 的 `std::less<>`（透明版本）对指针仍然如此，C++20 给指针加上 `<=>` 之后也仍然如此；解引用这件事，标准库不会替你做。

要按内容排序，就得把“先解引用，再比较”写进比较器。示例里的 `DereferenceLess` 是一个模板，对任何支持 `*p` 和 `<` 的类型都能用：裸指针、迭代器、`shared_ptr`、`unique_ptr` 都可以。第三组用 `std::shared_ptr<std::string>` 验证了这一点。这里要区分 `DereferenceLess` 和 `std::owner_less`：前者比较所指对象的值，后者比较 `shared_ptr`、`weak_ptr` 的所有权归属，用于按所有权查找，不关心对象内容。`shared_ptr` 的默认比较看的是 `get()` 的地址，同样不是内容。

指针容器还有两个和比较器无关、但经常一起出现的问题。第一是所有权：`set<string*>` 不拥有那些 `string`，容器销毁时只销毁指针，指向的对象要另外释放，用裸指针就得自己配一个 RAII 的拥有者（[第 9 章](ch09.md)）。第二是类型安全：ESTL-20 提到，把 `std::string*` 的元素直接拷进 `std::ostream_iterator<std::string>` 会编译失败，因为算法要求元素能写成 `std::string`，而实际类型是 `std::string*`；这个错误比“打印出一堆地址”更早暴露，也说明让类型系统参与检查比手工循环可靠。能用 `set<string>` 存值时就别存指针；确有多态或共享所有权需求时，比较器和所有权要一起设计。

最后有一个和下一节相连的坑：一旦比较器解引用，键就不在指针里，而在被指对象里。通过 `set<string*>` 的迭代器拿到的是 `string*`，改 `*p` 完全合法，容器却不知道排序依据变了。所以指针容器用了解引用比较器之后，“不要改键”这条规则约束的是被指对象的内容，而不是指针本身。能存值就存值（`set<std::string>`），需要多态或共享所有权时再考虑指针，并且把“谁能改被指对象”一起设计进去。只读的字符串表、配置项这类场景，按值存 `std::string` 几乎总是更省心：迭代器直接给出内容，拷贝和移动的代价由标准库管理，也不用再回答“谁负责 delete”。

## 25.3 键插入后不能原地改

关联容器靠比较器维持顺序，而比较器只认“键”。键一旦进了树，它的相对位置就被树的结构固定下来；此后把键改成一个会改变顺序的值，容器不会重新排，也无法发现自己已经不在有序状态。`map` 用类型系统把这件事挡住：元素类型是 `pair<const Key, T>`，`first` 是 const。`set` 的元素类型就是 `T` 本身，看起来可以改，但 C++11 起 `set` 和 `multiset` 的 `iterator` 与 `const_iterator` 都是常量迭代器，解引用得到 `const T&`：

```cpp

两条错误说明的是同一件事：标准库不打算让你通过迭代器改键。MXC-08 把根本要求写成一条“Key Rule”：键插入关联容器后，绝不能让它的值发生改变相对位置的变化。容器不能检测这种变化，所以一旦改动改变了相对位置，之后的查找、插入都是未定义行为；即使改完碰巧仍保持有序，也只是碰巧，不能依赖。`const_cast` 掉 `map` 键的 const 再写入更糟：那是在修改一个 const 对象，本身就是 UB。MXC-08 还提醒，间接的改法不止 `const_cast`：键里有参与比较的 `mutable` 成员、键持有指向外部共享缓冲区的指针、比较器去读文件内容，这些都能在容器不知情时改变顺序，“先 erase 再 insert”的纪律也防不住，只能靠设计上别让比较依据从容器外被改动。

C++98 时代 ESTL-22 讨论过 `set` 的尴尬：标准说元素类型是 `T` 而不是 `const T`，却又允许实现让 `set::iterator` 解引用出 `const T&`，于是同一段 `i->setTitle(...)` 在某些实现上能编译、在另一些上不能。C++11 把这件事定死了，`set` 的迭代器统一是常量迭代器，可移植的写法只剩两种：`const_cast` 掉 `*i` 的 const（对象本身不是 const、且只改不参与比较的部分时才有定义），或者把元素取出来改。

“取出来改”在 C++17 之前是一套手工步骤，ESTL-22 把它拆成五步：找到元素、拷贝一份、`erase` 掉原元素、改副本、用原位置作提示插回。拷贝是必须的，因为 `erase` 之后原对象已经不存在；`erase(i++)` 要先用后置递增把迭代器移到后继，否则 `i` 失效，下一步没有合法的提示位置；`insert(hint, value)` 的提示如果正确，插入是摊还常数时间，而不是对数时间。这段代码在示例的最后一段，今天仍然有效，只是啰嗦。

```

第一行改的是 `map` 的键：`extract(13)` 之后 `key()` 可以写，改成 42 再插回，`inserted` 为 `true`。第二行演示撞键：把节点改成已存在的 7，`insert` 返回 `inserted == false`，元素没有被吃掉，而是留在 `failed.node` 里；把键改回 42 再插，第三行显示元素回来了。这一点很重要——节点句柄是元素的唯一所有者，`insert` 失败后如果直接让它析构，元素就跟着没了。`set` 那一段改的是 `Employee::title`，它不参与 `ById` 比较，所以相对位置不变；`extract` 让这种修改不必再借 `const_cast`。

节点句柄也不是“随便改”的许可证：`extract` 之后、`insert` 之前，元素不在任何容器里，指向它的迭代器已经失效；改键时要自己保证新键在目标容器中不冲突，冲突了就得决定丢弃、改回还是插到另一个容器。`merge` 能在同类型的关联容器之间整体搬节点，撞键的节点留在原容器，不拷贝也不移动元素，适合做“把一批记录从一个索引转到另一个索引”。C++20 的 `contains` 和 C++14 的异质查找只改变查询写法，不改变“键不能原地改”这条约束；C++23 的 `flat_map`/`flat_set` 底层是有序 `vector`，更没有节点句柄可用，改键只能走“取出值、改、重新插入”的老路。

工具方面，`const_cast` 是编译器不会拦的显式操作，`-Wcast-qual` 对 C 风格转换去掉 const 会报警，却不管 `const_cast`（本机 clang 21、GCC 15 实测都不报）。clang-tidy 21 的 `cppcoreguidelines-pro-type-const-cast` 会指出每一处去掉 const 的 `const_cast`，可以把它当成评审时的提醒；真正的保证仍然来自“改键走 extract”这个写法习惯。

## 25.4 按“键是否存在”选择插入与更新

`m[k] = v` 看起来像赋值，实际是“有则改、无则插”。键不存在时，`operator[]` 先值初始化一个 `mapped_type`（类类型就是调用默认构造），返回它的引用，随后 `= v` 再赋值；键存在时才只做赋值。ESTL-24 把这层语义拆开算账：新增元素用 `insert(value_type(k, v))`，直接用目标值构造整个元素，省掉默认构造、赋值和一次析构；更新已有元素反而 `operator[]` 更省，因为 `insert` 必须先造出一个完整的 `pair`，再发现键已存在、把它丢掉。下面用一个会记账的 `Price` 把两条路径的差别打印出来：

第一行是新键走 `operator[]`：默认构造一次、赋值一次。第二行是已有键走 `operator[]`：只有赋值。`emplace(3, Price{30.0})` 和 `try_emplace(4, 40.0)` 都是直接构造，默认构造为 0；区别在于 `emplace` 要求先把 `Price` 造出来（哪怕键已存在，临时对象也已经造好），`try_emplace` 只在键不存在时才用实参构造，键已存在时连实参都不碰——所以 `try_emplace(1, 99.0)` 一行全是 0。`insert_or_assign(1, 55.0)` 对已有键只赋值，`insert_or_assign(5, 77.0)` 对新键直接构造。倒数第二行的 `insert({1, Price{88.0}})` 最能说明 `insert` 的语义：键已存在时它什么也不改，但 `Price{88.0}` 已经构造出来又销毁；最后一行确认 `catalog.at(1).amount` 仍然是 55。这些计数是本机 libstdc++ 15 的实现细节，标准保证的是语义和复杂度；不过“`operator[]` 要求 mapped_type 可值初始化、`try_emplace` 在键已存在时不构造实参”是接口本身的规定，可以放心依赖。

C++17 的 `try_emplace` 和 `insert_or_assign` 把 ESTL-24 里手写的 `efficientAddOrUpdate` 收进了标准。那个手写版本先用 `lower_bound` 找位置，再按 `key_comp()` 判断等价，最后用 `insert(hint, value_type(k, v))` 插入；提示正确时插入是摊还常数时间，`KeyArgType`、`ValueArgType` 保留可转换的实参类型，避免提前构造 `mapped_type`。今天只有在需要同时拿到“是否插入”和“插入位置”、或者要在一次查找里做更复杂的判断时，才值得手写；普通的新增和更新直接用标准接口，意图也更清楚：

- 只想插入，键已存在就保持原值：`try_emplace`（不构造 mapped）或 `insert`（构造整个 value_type）；
- 有则赋值、无则插入：`insert_or_assign`；
- 确定键已存在，要读或改：`operator[]` 或 `at`；
- 只查不改：`find`、`contains`、`at`，别用 `operator[]`。

这几个接口对 `mapped_type` 的要求也不同。`operator[]` 要求它可值初始化（类类型要有默认构造函数），因为键不存在时容器必须先造一个值出来；`try_emplace` 只要求它能从给定的实参构造，`insert` 要求整个 `value_type` 可构造。`mapped_type` 没有默认构造函数时，`operator[]` 直接编译失败，`try_emplace` 仍然可用；这不是风格问题，而是接口能力差异。`insert_or_assign` 和 `try_emplace` 都返回 `pair<iterator, bool>`，`bool` 表示是否真的插入了新元素，需要区分“插入”和“覆盖”时用返回值，不必再查一次。

`stock["P999"]` 让 `size` 从 2 变成 3，还留下一个值为 0 的元素；如果这是一次拼写错误的查询，容器里就多了一条假数据，后续遍历、序列化、对账都会带上它。`find` 和 C++20 的 `contains` 只读，`at` 在键不存在时抛 `std::out_of_range`，三者都不会改变容器。`const map` 没有 `operator[]`，示例用概念把这一点变成编译期断言：`Subscriptable<const std::map<...>>` 为 `false`。这不是实现偷懒，而是 const 正确性在阻止“查询顺便插入”。

同一个示例还演示了 C++14 透明比较器的用处。`std::map<std::string, int>` 的 `find` 只接受 `const std::string&`，传 `string_view` 编译不过，因为 `string` 从 `string_view` 构造是显式的；把比较器换成 `std::less<>` 之后，`find`、`count`、`lower_bound` 等可以直接收 `string_view`、`const char*`，查找不再构造临时 `std::string`。C++17 的 `string_view` 和 C++14 的透明比较器要配合使用，自定义比较器则要自己写 `is_transparent` 和相应的重载。C++20 的 `contains` 只是把“找到没有”写得更直接，`operator[]` 会静默插入这一点从 C++98 到 C++23 都没有变。

选接口时先问一句“这个键本来就可能不在吗，不在的时候我要插入还是报错”。要插入，用 `try_emplace`/`insert_or_assign`；要报错，用 `at`；只想知道在不在，用 `contains`/`find`。`operator[]` 留给“我确定要它存在，不存在就创建一个默认值”的场合。工具方面，clang-tidy 21 的 `readability-container-contains` 会把 `m.count(k) != 0` 改写成 `m.contains(k)`，但它管不到 `operator[]` 的静默插入；这一条仍然靠接口选择和代码评审。

## 回头看

四节守的是同一个不变式：容器里每个元素的相对位置，必须由它当前的键和容器持有的那一个比较器共同决定。成员 `find` 与 `std::find` 给出不同答案，是因为一个用比较器、一个用 `==`；比较器对相等的值返回 `true`，是让这个不变式从根上失效；存指针却按地址排序，是让“键”变成了与内容无关的地址；原地改键，是在容器不知情时把元素搬到了错误的位置。插入与更新的选择看起来只是效率问题，其实也在守同一个边界：`operator[]` 会为了“可能不存在”而改变容器，只查不改时用它，等于让查询带上了写入的副作用。

C++11 以后，语言和标准库把其中一部分兜底了：`unordered_*` 提供了另一套基于哈希和相等的模型；`set` 的迭代器被规定为常量迭代器；C++17 的 `extract`/`merge` 给了改键的正规通道；C++17 的 `try_emplace`、`insert_or_assign` 和 C++20 的 `contains` 让“插入”“更新”“只查”在接口上分开；C++20 还让无捕获 lambda 的闭包类型可以直接当比较器类型。但比较器写得对不对、指针后面到底该按什么排序、被指对象会不会在容器外被改，这些仍然只能靠写代码的人决定。编译器能检查签名，`std::strict_weak_order` 能检查可调用性，ASan/UBSan 能在算法越界时抓住比较器的逻辑错误；对关联容器本身，没有一个开关能告诉你树已经乱了，测试和评审仍然是最后一道防线。
