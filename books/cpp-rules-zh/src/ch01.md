# 第 1 章 C++ 不是一种语言：子语言、标准与工具箱

接手一份年代跨度很大的 C++ 代码，最先撞上的往往不是语法，而是互相矛盾的经验。同一个管理堆内存的类，在 C 里按值传意味着复制几个字节；到了 C++ 里，按值传复制的是指针，两个析构函数会释放同一块内存。同一个“大对象按 const 引用传”的建议，碰到 STL 的迭代器和函数对象又反了过来：标准算法就是按值接收它们。有人记得“数组传参要带长度”，有人改用 `std::span`；有人说 `shared_ptr` 是标准库，有人还在写 `std::tr1::shared_ptr`。

这些说法各自都有成立的场景，问题在于它们默认了不同的前提。Meyers 在 EC-01 里给了一张地图：C++ 不是一套统一规则的语言，而是 C、面向对象 C++、模板 C++、STL 四个子语言的联合体。Sutter 在 EXC-25 里从另一个角度说同一件事：C++ 是多范式语言，面向对象只是其中一种组织方式，把它当成“特性清单”会漏掉泛型编程，也会漏掉后来加入的工具。

读后面那些具体规则时，先做三件事：判断自己站在哪个子语言里；确认这条规则依据的是哪个标准版本；再确认标准库或成熟第三方库里是否已经有现成组件。这一章先把这三件事的地图铺开。

## 1.1 四个子语言，为什么同一条规则会失灵

先看传递参数。C 的内置类型按值传，复制一个 `long` 和复制一个指针差不多，函数调用通常还能让编译器把值放进寄存器。面向对象的类就不同了：按值传一个左值要调用拷贝构造函数，对象里若有 `std::string`、`std::vector`，一次“看起来只是传个参数”的调用就可能分配内存。STL 又把规则翻回去：迭代器被设计成指针的泛化，函数对象通常很小，标准算法按值接收它们，复制迭代器和函数对象本来就是惯例。

`by_value(record)` 调用一次拷贝构造，`by_const_ref(record)` 一次也不调用，`by_value(std::move(record))` 调用的是移动构造。这不是“按值传递好”或“按引用传递好”能回答的问题，得先知道 `Record` 属于哪个子语言：它是带资源的类，默认该按 `const&` 读；如果函数要接管所有权，才按值或右值引用。而 `long add_c(long, long)` 的按值传参没有问题，`std::for_each` 按值接收 `CountCalls` 也没有问题——后者甚至要靠返回值或 `std::ref` 才能看见函数对象内部累加的 `calls`，因为算法操作的是副本。

EC-01 把 C++ 分成四块：C 提供语句、预处理、内置类型、数组和指针；面向对象 C++ 提供 class、封装、继承、虚函数；模板 C++ 提供泛型编程，并衍生出模板元编程；STL 则是一套关于容器、迭代器、算法和函数对象的特殊约定。四块各有各的有效写法，跨过边界时规则会变。Meyers 举的例子正是参数传递：C 的内置类型按值传通常更便宜，面向对象 C++ 的类类型通常用 `const&`，到了 STL，迭代器和函数对象又回到按值传。

EXC-25 补的是态度。Sutter 先问“C++ 是不是面向对象语言”，然后指出这个问题没有唯一答案，因为连“面向对象”包含哪些特性都没有共识：继承和多态几乎人人承认，封装多数人承认，异常处理只有少数人算，模板则很少有人算。C++ 不强迫任何一种风格，可以写纯 C 风格、面向对象、泛型，也可以混合。Sutter 还说，C++ 有静态类型，但不一定算“强类型”：隐式转换和 C 风格转换留了缺口（[第 2 章](ch02.md)、[第 3 章](ch03.md)会讲这些缺口）。把 C++ 当成“OO 特性清单”，就会以为继承是唯一的抽象手段，从而错过模板和算法。

C 版本用数组和下标，面向对象版本用基类指针和虚函数，模板版本对任意区间做范围 `for`，STL 版本把循环交给 `std::accumulate`。四种写法都正确，选择取决于你想让哪部分变化：如果要在运行期替换计价策略，虚函数合适；如果类型在编译期已知、想避免间接调用，模板合适；如果只是遍历一个容器，算法最短。模板元编程那一小段 `Factorial` 又是另一种东西：它在编译期算完，运行期没有循环，也没有函数调用。EC-01 说模板元编程的规则和日常 C++ 的交集很小，不必为了“统一”硬把它塞进日常写法。

这张地图不是按文件分的：一个函数里可以先用 C 数组、再调用虚函数、最后把结果交给算法。它的用处是提醒你，写每一行时知道自己在用哪套惯例。代码评审里说“这里不要按值传”时，也要说清楚是在哪个子语言里、传的是什么类型，否则建议本身就会变成新的教条。

`fill` 的形参是 `Buffer`，传参时编译器生成的拷贝构造函数被调用，`data_` 被原样复制。`fill` 返回时形参析构，`delete[]` 了那块内存；`main` 里的 `buffer` 还指着它，程序结束时再次 `delete[]`，ASan 报 double-free。这个错误不是“C 的按值传参错了”，而是把 C 的复制语义搬到了一个需要自己管理资源的类型上。修正方向有三条：禁用拷贝、写深拷贝、或者干脆用 `std::vector<int>` 让标准库管理内存。前两条属于特殊成员函数的规则，[第 6 章](ch06.md)会展开（EC-05、EC-06）；第三条是 RAII 的思路，[第 8 章](ch08.md)会讲（EC-13）。

C++11 以后，子语言只增不减。`auto`、lambda、移动语义、并发库让函数式和泛型写法更顺手；C++20 的 concepts 和 ranges 把模板子语言推到新的表达力，协程又引入一种新的控制流写法；C++23 的 `std::expected` 之类的设施继续扩充工具箱。按 EC-01 的地图走路，比背一条“万能规则”更稳：先认子语言，再谈惯例。EXC-25 写作时 C++ 还没有模块系统，这一项在 C++20 由 modules 补上了（[第 34 章](ch34.md)）；它说的“没有垃圾回收”仍然成立，RAII 和智能指针是替代方案，不是 GC。

边界上最实用的做法是加一层适配，而不是让一种惯例侵入另一种。C 数组要交给 STL 算法，用 `std::span`（C++20）把指针和长度绑成一个区间；回调要存进容器，用 `std::function`（C++11）接住 lambda 和函数对象；只读字符串参数用 `std::string_view`（C++17），既不复制，也不假设以 `'\0'` 结尾。适配层写清楚，两边就都能按自己的规矩办事。

## 1.2 标准库和 Boost 各自扮演什么角色

第二个常见困惑是“这个东西要不要自己写”。2005 年，Meyers 在 EC-54 里提醒读者：C++98 的标准库远不止容器，还包括 iostream、locale、数值组件、异常体系和 C89 库；而当时正在制定的 TR1 又规划了 14 个新组件，`shared_ptr`/`weak_ptr`、`function`、`bind`、无序容器、正则、`tuple`、`array`、`mem_fn`、`reference_wrapper`、随机数、数学特殊函数、C99 兼容层、type traits、`result_of` 都在其中。他用“standard C++ 1.1”形容这批补充，意思是它们值得每个 C++ 程序员提前熟悉。

`std::function` 把 lambda 存成一个可按签名调用的对象，`unordered_map` 按名字找回调；`b` 的引用计数在 `a.reset()` 后从 2 降到 1，`parent` 是 `weak_ptr`，所以 `a` 释放后它自动失效，不会把 `b` 一起拖住。`tuple` 和 `array` 则是 TR1 里另外两件小工具。EC-54 说“有现成的高质量组件就用，不要重复造轮子”，这句话在 C++11 之后更好执行：TR1 的绝大部分内容并入了 `std`，不用再找 `std::tr1`。

`std::function` 的灵活性有代价：它做类型擦除，可能为可调用对象分配内存，调用时多一次间接。热路径上如果可调用对象的类型在编译期已知，模板参数或函数指针更合适；`std::bind` 在 C++11 之后大多被 lambda 取代，C++20 的 `std::bind_front` 又把“绑定前几个参数”这个最常见的用法写得短一些。熟悉标准库不等于每个组件都无条件使用，知道代价才知道什么时候该换。

TR1 本身只是一份技术报告，不是 C++11 标准的一部分。C++11 把其中大部分设施收进 `std`，名字去掉了 `tr1::`；`std::tr1` 这个命名空间在标准里没有位置。libstdc++ 15 仍然带着 `<tr1/memory>` 一类头文件，`std::tr1::shared_ptr` 也还能编译，但那是实现为了旧代码保留的兼容层，不是可移植的写法。EC-54 当年还介绍过一个把 `std::tr1` 别名到 `boost` 的技巧，并明确说这等于往 `std` 里加东西，属于未定义行为；今天更没有必要冒这个险。

标准库的历史是一条不断并入的线：C++11 收下 TR1 的智能指针、`function`、无序容器、正则、`tuple`、`array`、type traits 和随机数；C++17 加入 `filesystem`、`optional`、`variant`、`any`、`string_view`；C++20 加入 ranges、concepts、`format`、`span`、`bit`；C++23 又加入 `expected`、`print`、`mdspan`、`flat_map` 等。C++23 这些设施在各家标准库里的完成度并不整齐，用到时先查该编译器版本的库支持表（需核实），不要因为标准里写了就假设一定能编过。C++26 还在草案阶段，本书不把它当作可用前提。

EC-55 讲的是标准库之外的另一半：Boost。Boost 既是社区也是库集合，采用公开同行评审，要求至少能在两个编译器上编译、文档清楚、许可证允许商用；TR1 的 14 个组件里超过三分之二基于 Boost 的工作。它不是“标准库的替代品”，而是试验场：一个库先在 Boost 里被使用、被挑错、被重新设计，成熟后才可能进入标准。EC-55 写作时，Boost 不覆盖整个编程领域，GUI 和数据库访问都不在里面；组件目录会变，今天要用的某个领域是否已有成熟库，得查当前版本。

今天选库的顺序可以很直接：先查标准库有没有；没有再查 Boost 或其他成熟库；最后才考虑自己写。Boost 仍在 Asio、Beast、Spirit、Hana、MP11 等方向提供标准库没有的东西，但引入它意味着多一份依赖、构建配置和版本升级的负担，团队规范里通常要单独讨论。反过来，也不要因为“Boost 里有过”就把某个组件当成标准；标准化的版本和 Boost 版本在接口、错误处理、ABI 上都可能不同。

Boost 的质量也不等于零成本。Asio 这类库往往要链接、要处理平台差异，header-only 的库会拉长编译时间；版本升级还可能带来 API 变化。团队决定引入 Boost 之前，通常要回答三个问题：标准库是否已经够用，这个库是否维护活跃，依赖带来的构建和发布成本由谁承担。EC-55 的建议是“熟悉它”，不是“凡项目必用”。

旧工具箱里的东西会退场。`std::auto_ptr` 在 C++17 被标准移除，因为它的“拷贝即转移所有权”与容器、算法要求的可拷贝语义冲突（ESTL-08 讲过这个问题，[第 9 章](ch09.md)会接着讲）。libstdc++ 15 仍把 `auto_ptr` 放在 `backward/auto_ptr.h` 里，用 `<memory>` 就能带进来，但编译器会给出弃用警告：

```cpp
{{#include code/ch01/1_2_auto_ptr.cpp}}
```

clang 的诊断：

```text
{{#include code/ch01/1_2_auto_ptr.out}}
```

这条警告不是“换个写法就没事”，而是标准库在提示：这个类型已经从标准里删除，换一个标准库实现可能直接编不过。新代码用 `std::unique_ptr` 表达独占所有权，用 `std::shared_ptr` 表达共享所有权；`auto_ptr` 只应出现在你必须维护的旧代码里。

EC-54 和 EC-55 合起来，其实在说“熟悉工具箱”这件事的两面：标准库是底盘，必须熟悉到知道什么问题已经有现成答案；Boost 是前沿，能提前看到标准可能往哪走，但不能把试验场当成标准。C++11 以后，底盘变大了，前沿也还在移动，判断“该用哪一个”仍然要先看标准版本，再看实现支持。

## 1.3 以标准为准，规范只管重要的事

第三个困惑是“该信谁”。旧书、博客、同事的经验、编译器的默认行为，都可能在某个版本上是对的，换个标准就变了。Meyers 在 MEC-35 里处理过同样的问题：他写作时，很多人还在把 ARM（《The Annotated C++ Reference Manual》，1990）当作权威，但 ISO 标准已经加进了 RTTI、namespace、bool、`mutable`、`explicit`、枚举的运算符重载、类内初始化整型 `static const` 成员，扩展了模板、异常规格、`new[]`/`delete[]` 和四种具名转换。ARM 不再够用，判断“C++ 里有没有这个”要看标准。

MEC-35 还提醒，标准库是 C++ 不可分割的一部分，而且远不止容器：C 库支持、`string`、本地化、iostream、复数与 `valarray`、STL 都在里面。STL 的三大概念是容器、迭代器、算法；迭代器用半开区间 `[begin, end)`，`end` 指向最后一个元素之后，查找失败就返回它；指针本身就是合法的迭代器；容器提供 `begin`/`end` 和 `iterator` 类型，算法只要求迭代器支持它用到的操作，不要求继承层次。这种“靠约定、不靠继承”的设计让 STL 可以扩展，也让标准库的组件能互相组合。

`std` 命名空间的使用也有讲究。头文件里写 `using namespace std;`，会把整个标准库拖进每个包含它的翻译单元，名字冲突和重载决议的变化都可能出现；需要哪个名字就用 `using std::string;` 这样的 using 声明，或者干脆写全名。MEC-35 特意区分了 using 指令和 using 声明，原因就在这里：标准库在 `std` 里，但把它整个倒进全局作用域并不是“方便”，而是把检查交给了运气。

clang 只说 `std` 里没有 `optional` 模板；GCC 15 会多一句“`std::optional` 从 C++17 起才可用”。两个编译器都把这段代码拒绝掉，差别只在提示信息。`std::optional` 是 C++17 的库设施，`<optional>` 头文件在 C++14 模式下不会提供它。这里没有“编译器太严格”的问题，是编译选项选错了标准。这正是 CCS-14 说的“能在编译期发现的错误，不要留到运行期”（[第 2 章](ch02.md)）。写代码时把 `-std=c++20` 固定进构建系统，比在源文件里到处写兼容宏可靠；需要支持多个标准时，用特性测试宏做条件编译，而不是用 `#if __cplusplus == 202002L` 这种脆弱的相等判断。

C++ 的标准版本大致是：C++98 是第一个 ISO 标准，C++03 是一次缺陷修正，C++11 加入 auto、lambda、移动语义、并发库和 TR1 的大部分内容，C++14 补齐泛型 lambda、变量模板等，C++17 加入 filesystem、optional、variant、string_view、`if constexpr`，C++20 加入 concepts、ranges、协程、modules、`std::format`，C++23 加入 expected、print、mdspan、flat_map 等。C++26 还在草案阶段，具体特性以 WG21 提案和最终标准为准（需核实）。本章的示例以 C++20 为基准，在 Clang 21 + libstdc++ 15 和 GCC 15 下都按 `-std=c++20` 编译；C++23/26 的内容会单独注明所需选项和支持情况。

查证顺序可以是：先看标准文本或 cppreference 的条目，确认这个特性属于哪个版本；再看 WG21 提案，弄清它为什么这样设计、有没有被后续提案修改；最后在 Compiler Explorer 或本机用两个编译器实测。cppreference 不是标准文本，但它通常比二手教程准确；Compiler Explorer 能让你把同一段代码在 GCC、Clang、MSVC 上并排编译，看出实现差异。C++ Core Guidelines 则是另一层：它是由 Stroustrup、Sutter 等人维护的工程建议集合，不是 ISO 标准，适合当评审清单和教学材料，不适合拿来判断“这段代码是否合法”。[第 36 章](ch36.md)会讲怎么把它和警告、sanitizer、clang-tidy 一起用（EC-53）。

MEC-35 的“以标准为准”管的是语言行为；CCS-00 管的是团队规范，两者经常被混在一起。Sutter 与 Alexandrescu 在 CCS-00 里说得很直接：只写真正重要的事，不要把个人口味写进规范。缩进几个空格、行长多少、左花括号放哪一行，对正确性和可读性没有实质影响；同一个文件、同一个项目里保持一致就够了，维护旧文件时跟随它已有的风格。真正需要规定的是会影响行为的约束：命名不要以下划线开头或包含双下划线，避免撞上实现保留的标识符；宏名全大写，而且不要占用 `T`、`U` 这类常见模板参数名，`#define T` 会把模板代码里的 `T` 一起换掉。宏本身该不该用、什么时候该让位给 `constexpr` 或 inline 函数，是[第 32 章](ch32.md)的主题（CCS-16）。

CCS-00 还点名了几个不该强制的旧习惯。匈牙利命名法在类型不安全的 C 里还有点用，在面向对象和泛型编程里只有坏处，或者根本行不通；“单入口单出口”（SESE）在有了异常和析构函数之后已经过时，函数本来就有许多隐式出口，应该用短函数和 RAII 控制复杂度，而不是强行只写一个 `return`。注释也一样：解释意图和理由，不要复述代码；复述代码的注释会随着代码改动而过时。

这些建议在 C++11 之后更容易执行。嵌套模板的 `>>` 不再需要插空格，`clang-format` 一类工具能把格式统一自动化，C++20 的 modules 又改变了物理文件与接口的组织方式（[第 34 章](ch34.md)）。格式越是可以交给工具，规范越应该把篇幅留给真正重要的约束：不要未定义行为、不要泄漏、接口要能表达所有权、错误要能传播。CCS-00 的结论没有变，只是“哪些事值得写进规范”的答案更清楚了。

## 1.4 正确、简单、清晰优先，别写魔法数

最后一个问题看起来最“软”，其实最容易在维护时变成事故。报价函数里直接写 `0.19`、`5000`、`100`，当时能跑；半年后税率从 19% 调到 20%，有人改了其中一处，漏了另一处，测试没覆盖到那条路径，错就发出去了。更隐蔽的是“心算出来的常量”：上面写 `42`，下面写 `84`，注释说“42 的两倍”；哪天 42 改成 43，84 不会跟着变。

Sutter 与 Alexandrescu 在 CCS-17 里把这类问题归为“匿名且不自解释的重复”：裸数字没有名字，散落在多处后很难检索，改一个值要靠人眼找全；两个 42 未必是同一个东西，程序员心算出来的 84 让替换更容易出错。常量应该是具名、作用域恰当的 enumerator 或 `const` 值：与领域相关的放命名空间，只与某个类相关的放类作用域；字符串也一样，集中到专门的资源或常量里，既减少重复，也方便校对和本地化。

`shop::kTaxPercent`、`shop::kFreeShippingCents` 这些名字说明了数字的用途，`shop` 命名空间说明了作用域；`Order::kMaxLines` 只属于订单，放在类里，数组大小和边界检查用的是同一个常量，不可能一边 8 一边 10。`std::numbers::pi` 替代了 `3.14159` 和 `M_PI`：`M_PI` 不是标准 C++ 的一部分，`std::numbers` 是 C++20 的设施，`pi_v<T>` 还能按 `float`、`long double` 取对应精度的值。`std::string_view` 承载不分配内存的常量字符串，适合这种编译期就知道的文本。

常量的类型也值得选。一组互斥的状态用 `enum class`，比一串 `constexpr int` 更难混；要和外部协议交换数值时，给枚举指定底层类型，再显式 `static_cast` 到底层类型，别让枚举悄悄变成整数。字符串常量集中到一处（源文件或资源文件），既减少重复，也让非程序员能校对，为本地化留出位置。

这背后是 CCS-06：正确、简单、清晰优先于快和奇巧。代码首先是写给人读的，维护者常常就是半年后忘了上下文的自己；看不懂的代码没法有把握地修改。性能与清晰冲突时先保清晰，除非已经有测量证明必须让步——正确的程序改快，远比快的程序改正确容易。Sutter 与 Alexandrescu 举过一个故意炫技的例子：某个 GUI 库让用户写 `w + c` 来表示给窗口 `w` 加子控件 `c`，读代码的人根本猜不到这是“加子控件”。运算符重载本身没有问题，问题是它没有表达出操作的含义（[第 16 章](ch16.md)会讲什么时候该重载）。

UBSan 在执行到 `samples[4]` 时报告 `index 4 out of bounds for type 'int[4]'`。如果这道边界写成 `std::size(samples)`（C 数组）或 `samples.size()`（`std::array`），循环就不可能超过数组长度；如果遍历用范围 `for`，连下标都不用写。这里没有“编译器为什么不提醒”的问题：编译器不会因为你写了 42 就报警，它只能在越界真的发生时由 sanitizer 抓住。把 `-fsanitize=address,undefined` 放进测试和 CI，能让这类错误在合并前暴露，而不是等到线上（[第 36 章](ch36.md)）。

CCS-06 还提到一个很具体的习惯：构造函数的实参优先用具名变量，而不是临时量。更典型的歧义是 `Rect r(Point(), Point());`：两个实参都是临时量时，整句会被解析成一个函数声明，不构造任何对象（[第 4 章](ch04.md)的 4.3 节专门讲这个陷阱）。先写 `Point origin{0, 0};`、`Point corner{4, 3};`，再写 `Rect r(origin, corner);`，意图清楚，也避开了这类解析。这不是风格洁癖，而是把“这行代码到底声明了什么”从读者脑子里拿出来，交给编译器检查。

新标准让“给常量起名字”便宜了很多。C++11 的 `constexpr` 让常量真正能在编译期求值，整型结果可用于数组大小和非类型模板实参；C++20 起浮点类型的非类型模板参数也合法；`enum class` 给枚举常量加上作用域，不会把名字泄漏到外层。C++17 的 inline 变量解决了头文件里定义命名空间常量和静态成员的 ODR 问题，类内的 `static constexpr` 成员从 C++17 起隐式 inline，不必再在类外补定义。C++20 的 `std::numbers` 把 `pi`、`e`、`sqrt2` 这些数学常量收进标准库，`consteval` 和 `constinit` 则分别表达“必须编译期求值”和“只保证静态初始化”（后者在[第 22 章](ch22.md)展开，EMC-15）。这些工具都只是让正确写法更短，不能代替“这个数字该不该有名字、该放在哪个作用域”的判断。

“先写对、再写快”也不等于永远不优化。CCS-06 说的是不要为了想象中的性能牺牲清晰；真到了需要优化的时候，先测量，再改热点，改完再测（[第 29 章](ch29.md)）。一份正确、简单、常量有名字的代码，改起来有明确的落点；一份靠 42、84、`w + c` 堆起来的“聪明”代码，连作者自己都要重新猜一遍。

## 回头看

四节线索可以收在一起：先用 EC-01 的地图判断自己站在哪个子语言里，再用 MEC-35 的标准版本判断这条规则今天是否还成立，然后用 EC-54/EC-55 的工具箱判断要不要自己写，最后用 CCS-06/CCS-17 的写法把正确、简单、清晰落进代码。它们防的是同一类事故：把局部经验当成普遍规则，或者把“能编译”当成“写对了”。子语言判断错了，会把 C 的复制语义套到资源类上；标准版本判断错了，会在 C++14 里找 `std::optional`；工具箱判断错了，会手写一个漏洞更多的 `shared_ptr`；写法判断错了，会让一个 42 散落成十几处，改一处漏一处。

C++20 以后，语言和标准库替我们兜住了一部分：concepts 和 ranges 让泛型接口的要求更清楚，modules 改变了物理组织方式，`constexpr`、inline 变量、`std::numbers` 让具名常量更便宜，`std::function`、智能指针、`std::span`、`std::string_view` 让跨子语言的适配更容易。但哪套惯例适用、以哪个标准为基线、要不要引入 Boost、常量该放哪个作用域、什么时候值得为性能让步，仍然是人做的判断。编译器警告、sanitizer、静态分析和 CI 能替你抓住越界、泄漏和一部分类型错误（[第 36 章](ch36.md)），抓不住“这个数字为什么是 42”。
