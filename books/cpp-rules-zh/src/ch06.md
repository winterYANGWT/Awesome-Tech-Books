# 第 6 章 特殊成员函数：拷贝控制与三/五/零法则

下面这个 `Session` 只是包了一个文件描述符：

```cpp
class Session {
public:
    explicit Session(int fd) : fd_(fd) {}
    ~Session() { ::close(fd_); }
private:
    int fd_;
};

std::vector<Session> sessions;
sessions.push_back(Session{3});   // 能编译：拷贝构造还在
```

`Session` 没有写拷贝构造，编译器替它生成了一个，`fd_` 被按位复制。`push_back` 的临时对象和容器里的对象于是都持有 3，析构时关两次同一个文件描述符。更隐蔽的是，`~Session` 一写，移动构造就不再生成；`vector` 扩容时本来可以搬移，现在只能拷贝，而这次拷贝恰好把一个独占资源复制成了两份。编译器不会提醒“你写的析构函数让移动消失了”，代码照样通过编译。

这一章沿着“一个对象的复制、赋值、交换和销毁必须成套考虑”往下走。先弄清编译器在什么时候替你生成了什么、声明什么会让它不再生成；再看手写拷贝时最容易漏掉的基类部分，以及按值传基类造成的切片；然后回到赋值运算符的签名、自赋值和异常安全，把 copy-and-swap、`swap` 与 Pimpl 串成一条线。最后两节处理两个经常被当成“技巧”的角落：析构后 placement new，以及 Pimpl 的特殊成员为什么要放到实现文件里。

## 6.1 编译器默默生成了哪些函数，什么时候又不再生成

先看一个空类。Meyers 在 EC-05 里提醒过：`class Empty {};` 并不空。只要代码用到，编译器就会为它声明默认构造、拷贝构造、拷贝赋值和析构这四个函数；C++11 又加上移动构造和移动赋值，一共六个。它们都是 `public`、`inline` 的，析构函数默认不是虚的，除非基类的析构是虚的。生成出来的拷贝构造和拷贝赋值逐成员处理：类类型成员调用自己的拷贝操作，内置类型成员按位复制。

“按需生成”这几个字很重要。默认构造函数只在类里没有任何用户声明的构造函数时生成；一旦你写了 `Empty(int)`，无参构造就没了，想要就写 `= default`。拷贝构造和拷贝赋值则彼此独立：只写拷贝构造，不妨碍编译器生成拷贝赋值；只写析构，也不妨碍生成两个拷贝操作。EC-05 还列了拷贝赋值生成不出来的几种情况：成员里有引用或 `const` 子对象，或者基类的拷贝赋值不可访问。引用成员不能重新绑定，`const` 成员不能赋值，编译器不知道该怎么办，C++11 起把这种隐式拷贝赋值定义为 deleted。

`Plain` 的移动计数是 1，说明编译器生成的移动构造确实被调用了。`WithDtor` 和 `WithCopy` 的移动计数是 0、拷贝计数是 1：`std::move(a)` 仍然是一个右值，但没有移动构造可调，拷贝构造接受 `const WithDtor&`，于是把右值绑了过去。这就是“移动没有生成”在日常代码里的样子——不报错，只是悄悄多了一次深拷贝。`WithMove` 只声明了移动构造，拷贝构造被定义为 deleted，所以 `static_assert(!std::is_copy_constructible_v<WithMove>)` 成立；它的移动赋值也没有生成，因为两个移动操作不独立：声明其中一个，另一个就不会由编译器生成。

`WithTemplate` 说明成员函数模板从不抑制特殊成员函数。类里有一个 `template<typename T> WithTemplate(const T&)`，编译器照样生成拷贝构造；复制一个 `WithTemplate` 时，模板推出的 `const WithTemplate&` 和拷贝构造的形参一模一样，两者打平，非模板优先，所以调用的是拷贝构造。成员模板要是写成转发引用 `template<typename T> WithTemplate(T&&)`，情况就反过来了：对非 const 左值，`T&&` 推成 `WithTemplate&`，比拷贝构造的 `const WithTemplate&` 匹配得更好，复制会被模板抢走（本机实测）。这个坑属于重载决议，[第 21 章](ch21.md)讲 EMC-26 时会展开。

EC-05 写于 C++98，那时只有四个函数；EMC-17 把 C++11 的规则补全了。移动构造和移动赋值只在类没有用户声明的拷贝操作、移动操作和析构函数时才生成。它们对成员做的是“逐成员移动请求”：支持移动的成员走移动，不支持移动的成员退回拷贝，所以“生成了移动构造”不等于“每个成员都真的被移动”。反方向还有一条更硬的规则：声明移动操作会把拷贝操作定义为 deleted。理由和“声明拷贝操作会抑制移动”对称——既然默认的逐成员移动不合适，默认的逐成员拷贝多半也不合适。

析构函数是这套规则里最容易踩的一脚。C++98 里，写了析构不影响拷贝操作的生成；C++11 保留了这个行为，以免破坏旧代码，但把这种隐式生成标为 deprecated（弃用）。原因是“需要写非平凡析构”通常意味着类在手工管理资源，那么逐成员拷贝多半是错的。EMC-17 举的例子很实在：一个 `StringTable` 本来只有 `std::map` 成员，某天为了打日志加了析构函数，移动操作立刻消失，之后所有“移动”都变成 `map` 的深拷贝，功能测试完全看不出来，性能却差了几个数量级。今天的修法是把想要的版本显式写出来：

```cpp
class Base {
public:
    virtual ~Base() = default;
    Base(Base&&) = default;
    Base& operator=(Base&&) = default;
    Base(const Base&) = default;
    Base& operator=(const Base&) = default;
};
```

这五行不是样板戏，而是把“我要默认的析构、默认的移动、默认的拷贝”逐条说出来。只要其中任何一条的行为不对，就该在对应位置写真正的实现，而不是让编译器猜。示例里的 `ExplicitFive` 用 `= default` 把五件套全部要了回来，`static_assert(std::is_nothrow_move_constructible_v<ExplicitFive>)` 也随之成立。

那么不想让某个函数被调用时怎么办？EC-06 记录的是 C++98 的做法：把拷贝构造和拷贝赋值声明为 private 且不给定义。声明阻止编译器生成，private 阻止类外调用，不定义让成员或友元的误用变成链接错误。这个办法能用，但错误来得晚，而且只适用于成员函数。EMC-11 的建议是换成 `= delete`：函数还在声明里，参与重载决议，但任何调用都在编译期被拒绝。

前三条错误来自 `isLucky` 的三个 deleted 重载。`'a'` 选 `char`，`true` 选 `bool`，`3.5f` 选 `double` 而不是 `int`——`float` 到 `double` 是浮点提升，到 `int` 是浮点转整数的转换，前者更好。这正是 EMC-11 说的“deleted 函数仍参与重载决议”：它不是靠“名字找不到”来禁止调用，而是先把调用吸引过来，再在编译期拒绝。后两条错误是 `Session` 的拷贝构造和拷贝赋值，诊断直接落在 `Session second(first);` 和 `second = first;` 上，不需要等到链接。

`= delete` 还能做 private 方案做不到的事：删除非成员函数，删除函数模板的特定实例化。比如 `template<> void processPointer<void>(void*) = delete;` 写在命名空间作用域，类内成员模板的特化本来就不能在类内声明成不同的访问级别，deleted 版本没有这个问题。惯例是把 deleted 函数声明为 public：编译器先检查可访问性，再检查是否 deleted；EMC-11 提醒，声明成 private 时旧实现可能只报“private”，把真正的原因藏起来。本机 Clang 21 和 GCC 15 对 private 的 deleted 拷贝构造已经直接报 deleted，但 public 仍是更清楚的写法。

新标准没有改写这套生成规则。C++17 的保证复制消除只影响“用纯右值初始化对象”时是否调用拷贝/移动构造，不会让被抑制的移动操作重新出现；C++20 的 concepts 可以约束特殊成员函数模板，但不能把已经 deleted 的拷贝操作变回来。C++20 仍然把“有用户析构时隐式生成拷贝操作”标为 deprecated；本机 Clang 21 在 `-std=c++20` 下用 `-Wdeprecated-copy-with-user-provided-dtor` 警告，GCC 15 用 `-Wdeprecated-copy-dtor`，两者都不在 `-Wall` 里，要显式打开。clang-tidy 21 的 `cppcoreguidelines-special-member-functions` 会在类只定义析构、没定义其余四个时提示。

日常写法可以压成一句：默认让编译器生成（零法则）；一旦写了析构、拷贝或移动中的任何一个，就把另外几个的去留想清楚，想要的用 `= default` 写出来，不想要的用 `= delete` 写出来。最怕的不是写错，而是根本没意识到自己写了一个析构函数，然后让移动悄悄消失。

## 6.2 拷贝为什么会漏掉基类，按值传又为什么会切片

EC-12 的标题是“拷贝对象时不要漏掉任何部分”。这句话听起来像废话，直到你亲手写了一次拷贝构造，后来又在类里加了一个成员。编译器生成的拷贝会复制全部非静态数据成员；你一旦接手，编译器就不再核对，也不会因为新成员没被复制而报警。下面的 `Customer` 有两个成员，手写的拷贝函数只记得 `name_`：

`Customer` 拷贝出来的 `id` 是 0，赋值之后目标仍是原来的 9。`id_` 有默认成员初始化器，所以程序没有未定义行为，只是安静地少复制了一个字段。`Contract` 更隐蔽：它的拷贝构造在初始化列表里只写了 `pages_`，基类 `Document` 被默认构造，标题变成空串；拷贝赋值没有调用 `Document::operator=`，目标的旧标题原封不动。`FixedContract` 用 `= default` 把两个拷贝操作交回编译器，基类和成员都处理对了。

基类部分出问题的方式和普通成员略有不同。派生类的拷贝构造如果不提基类，基类会被默认构造；基类没有默认构造时，这里会编译失败，反而是一道安全网。派生类的拷贝赋值如果不调用基类的赋值，基类部分就保持原值，连编译错误都没有。正确写法是把基类当成一个必须显式处理的成员：拷贝构造写 `Document(rhs)`，拷贝赋值写 `Document::operator=(rhs)`。这也是 EC-12 的重点：所谓“复制全部”包括两层，复制本类的所有数据成员，调用所有基类对应的拷贝操作。

手写拷贝函数通常是为了打日志、管理资源或维持某个不变式。这时 `= default` 不一定适用，能做的是把“复制所有部分”变成一条可以检查的规则：新增成员时同时改拷贝构造和拷贝赋值，或者把公共逻辑抽到一个 private 的 `init()` 里让两者都调用。EC-12 特别反对让一个拷贝函数去调用另一个：拷贝赋值去调用拷贝构造，等于在一个已经存在的对象上重新构造；拷贝构造去调用拷贝赋值，等于对一个还没构造完的对象做赋值。两种方向都说不通。现代写法里的 copy-and-swap 看似“让赋值复用了拷贝构造”，其实是在旁边构造一个独立的临时对象，再交换状态，并没有对 `*this` 调用拷贝构造，所以不违反这条。

错误落在 `audit(savings)` 这一行：函数需要按值构造一个 `Account`，而拷贝构造对类外不可见。派生类自己的隐式拷贝构造仍然能调用这个 protected 基类拷贝构造，所以正常的派生类复制不受影响。CCS-54 还提醒，把拷贝构造写成 `explicit` 也能挡住隐式切片，但它会连带禁掉所有按值传递，而且原书写作时有些编译器对这类调用的接受程度不一致；protected 加 `Clone` 更稳。

`Clone` 的正确形状是 NVI（非虚接口）：公开一个非虚的 `clone()`，转调 protected 的 `do_clone()`，并在转调之后检查返回对象的动态类型和 `*this` 一致。示例为了短，直接在 `clone()` 里写了虚函数；真实代码里拆成两层，才能用 `assert(typeid(*p) == typeid(*this))` 抓住“某个更深的派生类忘了 override”这种编译器发现不了的错误。C++11 的 `override` 只能检查 `do_clone` 是否真的覆盖了基类虚函数，不能检查更深一层的派生类有没有实现；`final` 可以封住继承链，从源头消掉这类遗漏。C++17 的 `[[nodiscard]]` 适合加在 `clone()` 上，避免调用方把新对象丢掉造成泄漏。

返回类型也要选。`Clone` 返回裸指针是原书的写法；今天更常见的是返回 `std::unique_ptr<Base>`，把所有权写进类型。代价是协变返回只适用于指针和引用，`unique_ptr<Derived>` 不能协变成 `unique_ptr<Base>`，所以派生类的 `do_clone` 返回 `std::unique_ptr<Base>` 再隐式转换。若继承体系的一部分来自第三方库、必须保留 public 拷贝构造，CCS-54 的建议是优先按（智能）指针传递而不是按引用：指针要求调用方显式取地址，误把派生对象拷进基类形参的机会更小。基类通常也不该是具体类，这一层设计问题在[第 17 章](ch17.md)讲可替换性时还会遇到。

编译器不会为“漏复制一个成员”报警：Clang 21 和 GCC 15 在 `-Wall -Wextra` 下都能安静地编过本节第一个程序。切片倒是能被工具抓到，clang-tidy 21 的 `cppcoreguidelines-slicing` 会指出 `audit(savings)` 把 `Savings` 切成 `Account`、丢掉了多少字节。剩下的仍靠写法：能 `= default` 就不要手写；一旦手写，就把所有成员和基类列出来；基类要么禁止按值复制，要么提供 `Clone`，不要让调用方在“看起来能编过”的按值传递里丢掉派生部分。

## 6.3 赋值运算符该长什么样：返回引用、处理自赋值

内置类型的赋值可以连成一串：`x = y = z = 15` 从右向左结合，`15` 赋给 `z`，表达式的结果是更新后的 `z`，再赋给 `y`，最后赋给 `x`。EC-10 说的就是把这套约定照搬到自定义类型：赋值运算符返回 `T&`，函数末尾 `return *this;`。这条约定不只管 `operator=`，也管 `+=`、`-=` 这些复合赋值，以及参数类型不常规的赋值，比如 `operator=(int)`。

`a = b = c` 能成立，是因为 `b = c` 返回 `b` 的引用，外层赋值拿到的是一个左值。`(a += 10) += 5` 同理。示例用 C++20 的 `std::assignable_from<Account&, const Account&>` 把返回类型固定下来；`FrozenAccount` 返回 `const FrozenAccount&`，这个 concept 不成立。CCS-55 的原话说返回 `const T&` 会让类型“无法放进标准容器”；更准确地说，是容器和算法里那些要求赋值的操作不再满足 `assignable_from`，`push_back` 这类只要求拷贝插入的操作未必受影响。传统 `std::sort` 的实现也不一定检查返回类型，所以这条错误可能编过一部分代码，却在 ranges 的 `sortable` 约束或别的标准库实现上失败。规范写法只有一个：返回 `T&`。

赋值运算符应当是公开、非虚的成员函数。CCS-55 给了两个规范签名：`T& operator=(const T&)` 和按值的 `T& operator=(T)`。按值版把复制放进了形参构造，天然适合 copy-and-swap，对右值实参还会走移动构造；如果函数内部本来就要复制一份实参，按值版可以少一次复制。不要把它设成 `virtual`：虚赋值在派生类里很容易只改一半对象，需要多态赋值时应当另写一个具名的 `virtual void assign(const T&)`，让调用方知道自己调用的是什么。

`delete pb_` 释放的正是 `rhs.pb_` 指向的 `Bitmap`，下一行再去复制它，读的就是已经释放的内存。ASan 把这条路径变成确定的 `heap-use-after-free`，而不是“偶尔算错”。就算没有自赋值，这个版本也不具备异常安全：`new Bitmap(*rhs.pb_)` 抛出时，`pb_` 已经指向被释放的内存，对象连基本保证都没有。

EC-11 给了两种修法。第一种是调整顺序：先把旧指针存下来，用 `rhs` 构造新资源，成功后再释放旧资源。这样即使 `new` 抛出，`pb_` 仍指向原来的对象；自赋值时先复制出一份新 `Bitmap`，再删掉旧的，也能正确工作。第二种是 copy-and-swap：在旁边构造临时对象，再和一个不抛的 `swap` 交换状态。6.5 节会展开。

`if (this == &rhs) return *this;` 能把最直接的自赋值挡掉，但它只该当优化，不该是正确性的前提。EXC-38 讲得很清楚：一个必须靠自赋值检查才能正确的赋值运算符，通常说明它在异常安全上有问题；copy-and-swap 在修改自身之前完成所有可能抛的工作，失败时原对象不变，自赋值也天然安全。加检查的代价是一次分支和更大的代码，只有自赋值确实频繁、并且测得出收益时才值得。

这个检查本身也可能被骗。类可以重载 `operator&`，`&other` 就不再是对象的真实地址；示例里的 `OddAddress` 让 `operator&` 返回 `nullptr`，`this != &other` 对自赋值也成立，`revision_` 被多加了一次。C++11 的 `std::addressof` 绕过重载的 `operator&`，拿到真实地址；C++17 起它还是 `constexpr`。示例第二段用 `std::addressof` 之后，自赋值不再增加 `revision_`。不过要记住，这仍然只是优化：正确性应当由“先完成可能抛的工作、再用不抛操作提交”来保证，而不是由地址比较来保证。构造函数里检查 `this != &other` 没有意义，因为对象还没构造完；`operator!=` 也不会干扰这个比较，因为重载运算符至少有一个参数必须是类类型，不可能为两个指针写一个 `operator!=`。

C++11 给这套规则加了移动赋值。移动赋值同样返回 `T&`，通常标 `noexcept`；`x = std::move(x)` 是合法的自移动，但结果通常是“有效但值未指定”，不能假定它没有副作用。C++20 的 `std::assignable_from` 把“赋值表达式返回 `T&`”写成了 concept，标准库和 ranges 可以用它约束模板；这比原书写作时靠文档约定又前进了一步。工具方面，Clang 21 的 `-Wself-assign-overloaded` 会抓字面上的 `a = a`，GCC 15 在 `-Wall -Wextra` 下对这个例子没有警告（它只有针对 `std::move` 的 `-Wself-move`）；通过别名发生的自赋值两边都不报，仍要靠 ASan 和测试。

## 6.4 三/五/零法则：拷贝、赋值、析构要一起想

CCS-52 把三个函数的关系说成“不对称地互相关联”：写了或禁用了拷贝构造，通常也要对拷贝赋值做同样处理；拷贝构造里分配或复制了资源，析构函数就要负责释放；需要写非平凡析构，往往意味着拷贝时得深拷贝或干脆禁用拷贝。原因不复杂：这三个函数描述的是同一份资源的生命周期，只改其中一头，另一头就会用默认的逐成员语义处理，而默认语义多半不是你要的。

CCS-53 把这件事推进成一条更主动的规则：定义类时必须在“禁用拷贝”“自己写拷贝”“用编译器生成的拷贝”三者中做出选择，不能因为忘了想而默认获得逐成员拷贝。默认行为正确时，最好的写法是不声明，再留一句注释说明“默认逐成员拷贝是正确的”；这样读代码的人知道你考虑过，而不是漏掉了另外两个选项。C++11 之后，选择的手段变成了 `= delete` 和 `= default`，要禁止就明确禁止，要默认就明确默认。

把视角放大到 C++11，就是常说的三法则变成五法则，再变成零法则。三法则说：只要写了拷贝构造、拷贝赋值、析构中的任何一个，就要审视另外两个。五法则加上移动构造和移动赋值：显式声明析构、拷贝构造或拷贝赋值中的任何一个，都会抑制移动操作的隐式生成，之后对右值的“移动”会退化成拷贝。零法则说：如果成员都能自己管理资源（`std::string`、`std::vector`、`std::unique_ptr`），就一个特殊成员都不写，让编译器生成整套。零法则是默认，五法则是持有资源时的例外。

所以 `= default` 不是“让编译器随便生成”的咒语，它本身就是一次用户声明。只写 `~Buffer() = default;` 而不同时写移动操作，移动仍然不会生成；示例里的 `Buffer` 之所以能移动，是因为它把析构、拷贝和移动五条都写了出来。反过来，如果默认行为正确，把这五条都写出来也比漏掉一条强：读代码的人能一眼看到类的复制、移动、销毁契约。

`MoveOnly` 展示了“只允许移动”的选择：移动构造和移动赋值 `= default`，拷贝构造和拷贝赋值 `= delete`，`static_assert` 确认它不可拷贝、可 `noexcept` 移动。`RuleOfZero` 展示了另一个极端：只放 `std::string` 和 `std::vector` 成员，一个特殊成员都不写，编译器生成的拷贝和移动都正确，移动还是 `noexcept` 的。两者之间没有“更高级”的写法，只有“这个类需不需要自己管资源”的区别。

还有一个容易被忽略的细节：移动构造不标 `noexcept` 时，`std::vector` 为了强异常安全可能宁可不搬移，改用拷贝（`std::move_if_noexcept` 的行为，[第 7 章](ch07.md)会讲）。这时“我写了移动构造”并不等于“扩容一定会移动”。移动构造能否标 `noexcept`，取决于它搬移的每个成员是否都不抛；`std::vector`、`std::string`、`std::unique_ptr` 的移动都是 `noexcept` 的，由它们组成的类通常也能做到。

C++11 之后，标准库提供了 `std::is_copy_constructible`、`std::is_move_assignable`、`std::is_nothrow_move_constructible` 这些 traits，可以把“这个类应该可拷贝/可移动/不抛”写成 `static_assert` 留在代码里。它们检查的是表达式是否合法，不是“是否真的生成了一个独立的移动操作”：一个只有拷贝构造的类，`is_move_constructible` 仍然为真，因为拷贝构造能绑定右值。要看“移动是不是退化成拷贝”，还得靠计数器或 `is_nothrow_move_constructible` 这类更细的检查。编译器警告方面，6.1 节提到的 `-Wdeprecated-copy-with-user-provided-dtor`（Clang）和 `-Wdeprecated-copy-dtor`（GCC）会提示“有析构却隐式生成拷贝”，clang-tidy 的 `cppcoreguidelines-special-member-functions` 会提示五件套没配齐；它们都只能提示，不能替你决定这个类到底该不该拷贝。

## 6.5 强异常安全的赋值：copy-and-swap、swap 与提交

`exchange` 里的 `swap(lhs, rhs)` 没有加限定，ADL 找到了 `imaging::swap`，`custom_swaps` 变成 1。后面直接写 `std::swap(first, second)`，限定名把查找锁在 `std` 里，专用版本没有被调用，`custom_swaps` 仍是 1；值仍然换回来了，因为 `Image` 有 `noexcept` 的移动构造和移动赋值，`std::swap` 走的是移动。这个对比说明“调用方怎么写”会决定“调用哪个 swap”：泛型代码要的是两段式，知道自己类型的代码可以直接 `std::swap`，但后者放弃了类型专用版本，遇到移动不够快的类型就会退化。

成员 `swap` 应当声明 `noexcept`，这是 copy-and-swap 能提供强保证的前提。`Image::operator=` 先构造 `temp(rhs)`，所有可能抛的工作（分配、复制）都在这一步；成功之后 `swap(temp)` 只交换指针、字符串和向量，不分配、不抛。若 `temp` 的构造抛出，`*this` 一个字节都没改。`Document` 的赋值演示了同一条路径：把 `ThrowingPayload::armed` 打开后，`stable = incoming` 在构造临时对象时抛出 `payload copy failed`，捕获之后 `stable` 的标题和版本仍是原值。

这就是 MXC-22 和 EXC-09 共用的“先在旁边做完，再提交”原则。异常安全通常分三档：基本保证要求不泄漏、对象仍可析构和使用，但状态可能已经改变；强保证要求失败时状态不变，像事务一样要么提交要么回滚；不抛保证要求函数在任何情况下都不抛。析构、`delete`、指针交换这些“清理和提交”操作必须不抛，否则上层根本没法实现前两档。copy-and-swap 把“可能抛的工作”和“提交”分开，提交阶段只做不抛的 `swap`，于是自然得到强保证，也天然处理自赋值：自赋值时不过是复制一份自己再换回来。

`swap` 的实现有一条固定套路：对每个成员写 `using std::swap; swap(member, other.member);`。容器和智能指针的 `swap` 通常只换内部指针，内建类型用 `std::swap`，只要每个成员的 `swap` 不抛，外层就不会抛。不要图省事写 `std::swap(member, other.member)`，那会屏蔽成员类型自己的 ADL 版本；也不要忘了在类型所在命名空间提供非成员 `swap`，否则 `using std::swap; swap(a,b)` 找不到专用版本。EC-25 当年还建议为普通类全特化 `std::swap`，这一条今天要放弃：C++20 起标准明确禁止程序特化标准库的函数模板（P0551），而类模板本来就做不到（函数模板不能偏特化），向 `std` 添加新的重载也一直不允许。非成员 `swap` 放在类型自己的命名空间、靠 ADL 被找到，是唯一的正路。C++17 的 `std::is_nothrow_swappable` 可以把“这个类型的 swap 不抛”写成 `static_assert`，示例里对 `Image` 和 `Document` 都做了检查。

如果成员类型 `U` 没有不抛的 `swap`，CCS-56 给了两条路：`U` 的拷贝构造和拷贝赋值都不抛时，`std::swap` 就能用；`U` 的拷贝可能抛时，改存指向 `U` 的（智能）指针，最好把所有这类成员收进一个 Pimpl，分配和间接访问的代价只付一次。这也是 6.7 节 Pimpl 的另一个动机。绝对不要用“显式析构 + placement new”来实现赋值，那正是 6.6 节要拆的反例。

新标准让 `swap` 比 EC-25 写作时更重要。C++11 的移动语义把 `std::swap` 的实现改成移动构造加两次移动赋值，`noexcept` 的移动操作直接决定 `std::swap` 是否 `noexcept`；`std::vector` 扩容时用 `std::move_if_noexcept`，移动可能抛且拷贝可用时会退回拷贝，原因就是强异常安全（[第 7 章](ch07.md)、[第 12 章](ch12.md)）。C++11 也确立了 `using std::swap; swap(a, b);` 的两段式写法，C++17 补上 `std::is_swappable`/`std::is_nothrow_swappable` 供约束和检查，C++20 的 `std::ranges::swap` 把同一套查找规则包装成定制点。Pimpl 在 C++11 后通常改用 `std::unique_ptr`，它的 `swap` 只是交换指针、是 `noexcept` 的；代价是析构必须看到完整类型，这条限制在 6.7 节展开。

析构之后、`placement new` 之前，`t` 和 `rt` 都不指向任何对象，不能访问成员；重建之后，`rt` 仍然绑定原来的存储位置，看到的是新对象。计数器显示构造两次、析构两次，没有多也没有少。C++ 允许这种“透明替换”（transparent replacement）：新对象与旧对象同类型、同 cv 限定，旧名字和引用可以直接指代新对象，不需要 `std::launder`。换成不同类型、或者新对象是 `const`，规则就不一样了。

第二次析构是未定义行为。示例里的 `Resource(int)` 故意不初始化 `data` 就抛出，旧对象留下的指针没有被覆盖；`t` 作为自动变量在栈展开时再次调用析构，`delete` 同一块内存，ASan 报 `double-free`。真实代码里构造函数的抛出点不会这么刻意，但只要“显式析构”和“构造抛出”同时出现，这条路径就存在。

EXC-41 把这种写法用来实现赋值，称它为反惯用法：

```cpp
T& T::operator=(const T& rhs) {
    if (this != &rhs) {
        this->~T();
        new (this) T(rhs);
    }
    return *this;
}
```

它的目标并不坏：让拷贝赋值复用拷贝构造，避免两处代码重复。但手段带来一串问题。第一，切片：若 `T` 的析构是虚的，在派生类对象上调用 `this->~T()` 会销毁整个派生对象，再用 `T` 重建，对象不再是原来的派生类型；派生类的赋值代码接着操作一个被切掉的对象。第二，异常安全：拷贝构造抛出时旧对象已销毁、新对象未建成，外面不知道析构已经运行，最终可能再次析构。第三，生命周期副作用：构造和析构通常承担加锁、开事务、获取资源等职责，赋值时强行销毁重建会把锁和事务释放再重新获取，破坏 RAII 和不变式。第四，它必须靠 `this != &rhs` 才能处理自赋值，而 6.3 节已经说明，这个检查只该当优化。第五，它强迫所有派生类跟着用同一套把戏，编译器生成的派生类赋值不会这么做，继承体系里会留下一半对象用新生命周期、一半用旧生命周期的裂缝。

正确做法还是 copy-and-swap：在旁边的临时对象上完成复制，再用不抛的 `swap` 提交。它同样让赋值复用拷贝构造，但不碰 `*this` 的生命周期，不切片，不需要自赋值检查。含引用成员的类本来就不应该可赋值；如果确实需要“让引用改指向”，那应该用指针，而不是靠析构加 placement new 绕过语言规则。

现代 C++ 提供了更直接的表达。`std::optional<T>` 的 `emplace` 会先销毁旧值、再构造新值，`reset` 销毁当前值；`std::variant` 用 `emplace<T>` 做类型安全的换值。示例后半段用 `optional` 重写了“销毁并重建”：`slot.emplace("second", 2)` 先析构 `first`，再构造 `second`，没有第二次析构的风险。要注意 `optional::emplace` 在构造抛出时留下的是“没有值”的状态，属于基本保证；要强保证，仍应先在旁边构造临时对象再提交。C++20 的 `std::construct_at`/`std::destroy_at` 让合法的显式构造、析构可以在 `constexpr` 里使用，C++17 的 `std::launder` 处理复用存储后通过旧指针访问新对象的情形；它们是工具，不会把“析构 + placement new 实现赋值”变安全。C++23 的 `std::start_lifetime_as` 用于显式开始隐式生命周期类型的生命周期，本机 Clang 21 + libstdc++ 15 和 GCC 15 都还没有这个函数（用 `-std=c++23` 实测报“不是 std 的成员”），其他实现的支持情况需核实。

Sutter 在 EXC-40 末尾的建议是“避免语言的冷门角落，用最简单有效的技术”。这句话放在这里很合适：`optional`、`variant`、copy-and-swap 都是常规工具，析构加 placement new 则要求读者同时理解生命周期、异常和切片三套规则，出错的方式还都很隐蔽。工具能帮上一点忙：ASan 抓到了这里的双重 `delete`；但栈上对象显式析构后再访问，ASan 不一定能发现，所以这类写法不能靠 sanitizer 兜底。

## 6.7 Pimpl 的特殊成员为什么要放到实现文件

CCS-43 的出发点是 C++ 把“可访问性”和“可见性”分开：私有成员对外不可调用，但对所有看到类定义的代码都可见。一个按值持有的私有成员类型必须在头文件里完整定义，它依赖的头文件也会被传递进来；私有成员函数虽然不可调用，却参与名字查找和重载决议，查找发生在可访问性检查之前。下面这个 `Calc` 的 `test()` 想调用全局 `twice(int)`，但类内的两个 `twice` 已经把名字藏住了，全局版本根本不参与重载：

```cpp
int twice(int);
class Calc {
public:
    std::string twice(std::string);
private:
    char* twice(char*);              // 不可调用，但参与查找
    int test() { return twice(21); } // 错误：找不到可调用的成员版本
};
```

Pimpl（pointer to implementation，指向实现的指针）把私有数据和私有函数都塞进一个只声明、不定义的结构体，头文件只留一个指针。这样改实现时客户端不必重新编译，这个 `Widget` 的布局也只剩一个指针，ABI 更稳定；私有重载也不会再干扰调用方。代价是每个对象多一次堆分配、多一层间接访问、多一个指针，只有收益足够时才值得。CCS-43 说“审慎使用”，重点在“审慎”：不是为了追时髦给每个类都套一层。

`sizeof(Widget)` 在本机 64 位环境是 8，也就是一个指针的大小；标准不保证这个数值，但这个 `Widget` 只含一个指针这个结构是稳定的。`Widget` 的拷贝是深拷贝：拷贝构造用 `std::make_unique<Impl>(*rhs.pImpl)` 新建一份 `Impl`，拷贝赋值先构造新 `Impl` 再替换指针。移动构造和移动赋值只是搬 `unique_ptr`，所以能标 `noexcept`。所有这一切都发生在 `widget.cpp` 里，因为只有这里能看到 `Impl` 的完整定义。

EMC-22 讲的就是那个必须把特殊成员搬到实现文件的理由。`std::unique_ptr<Impl>` 的默认删除器在销毁时对 `Impl` 做 `delete`，而 `delete` 需要完整类型；如果 `~Widget()` 在头文件里由编译器隐式生成，它是一个 inline 函数，会在每个使用 `Widget` 的翻译单元里实例化，那里 `Impl` 还不完整，`unique_ptr` 内部的 `static_assert` 就会失败。修法不是自己写 `delete pImpl;`，而是把析构的定义推迟到 `Impl` 完整之后：

```cpp
// widget.h
class Widget {
public:
    ~Widget();   // 只声明
    // ...
};

// widget.cpp，在 struct Widget::Impl { ... }; 之后
Widget::~Widget() = default;
```

移动操作有同样的要求。移动赋值需要先销毁 `pImpl` 原来指向的对象，再接管新的指针；移动构造在异常路径上也可能需要销毁 `pImpl`。这两件事都要求 `Impl` 完整，所以移动构造和移动赋值也只能在 `widget.cpp` 里 `= default`。拷贝操作则根本不能依赖默认版本：`unique_ptr` 不可拷贝，默认拷贝会被删除；即使换成 `shared_ptr` 让默认拷贝能编过，逐成员拷贝也只会复制指针（浅拷贝），而我们要的是把 `Impl` 的内容也复制一份。所以拷贝构造和拷贝赋值必须自己写，并且同样放在实现文件里。

EMC-22 还留了一个例外：把 `pImpl` 换成 `std::shared_ptr<Impl>`，析构就不需要 `Impl` 完整，因为 `shared_ptr` 的删除器类型被擦除了，销毁时不需要知道 `Impl` 的大小。本机验证过，只有 `std::shared_ptr<Impl>` 成员、没有自定义析构的类可以正常销毁；但 `std::make_shared<Impl>` 仍然要求 `Impl` 完整，所以分配还是得放在实现文件里。`shared_ptr` 的控制块更大、引用计数是原子操作，Pimpl 这种独占关系没有理由为它付这份成本，`unique_ptr` 仍是默认选择。

头文件里那段 `struct Impl;` 和 `std::unique_ptr<Impl> pImpl;` 要写成两条声明。合并成 `struct Impl* pImpl;` 也合法，但含义不同：`Impl` 会落在外层命名空间，而不是 `Widget` 的嵌套类型。这个细节在 CCS-43 里专门提过，影响的是名字查找和后续能不能把 `Impl` 定义成 `Widget::Impl`。

新标准没有改变这套做法。C++11 的 `= default`/`= delete` 让“只声明、在实现文件里默认”更干净，C++14 的 `std::make_unique` 省掉了 `new`，C++17 的保证复制消除只改变纯右值初始化时是否调用拷贝/移动构造，不会让不完整的 `Impl` 变得可删除。C++20 的 modules 能减少头文件的文本处理开销，但类定义（包括私有成员）仍在接口单元里，仍决定布局和 ABI，Pimpl 的隔离价值不变。C++23 对 `unique_ptr` 的 constexpr 支持（本机 Clang 21 + libstdc++ 15 与 GCC 15 用 `-std=c++23` 实测可用）也不改变“销毁点需要完整类型”这条规则。

Pimpl 和 6.5 节的 copy-and-swap 可以配合：在 `widget.cpp` 里写一个 `swap(Widget&, Widget&) noexcept`，交换两个 `unique_ptr`，拷贝赋值就可以写成“按值传参 + swap”，代码更短，强保证也更容易看出来。示例选择了“先 `make_unique` 新 `Impl`、再替换指针”的写法，效果一样：新 `Impl` 构造失败时旧指针没动，构造成功后 `unique_ptr` 的移动赋值是 `noexcept` 的。两种写法都可行，而在头文件里让编译器默认生成根本处理不了不完整类型。

## 回头看

这七节讲的是同一组函数的不同侧面：编译器替你生成什么、你声明什么会让它不再生成、手写的拷贝要覆盖哪些部分、赋值该返回什么、异常从哪里来、对象什么时候真正存在，以及 Pimpl 为什么把析构藏到实现文件里。它们防的是同一类事故：两个对象以为各自拥有一份资源，实际共享同一块内存；派生对象被按值传进基类形参，悄悄丢掉派生部分；赋值先释放再读取，自赋值时读到已释放的内存；构造函数抛出后旧对象已经没了，析构却还会再来一次；以及最安静的一种——写了一个析构函数，移动操作从此消失，所有“移动”都变成深拷贝。

C++11 之后，语言和标准库接过了很大一部分工作。`= default` 和 `= delete` 让“我要默认版本”和“我不要这个函数”都变成显式声明；移动构造和移动赋值让资源可以搬走而不是复制；`std::unique_ptr` 让零法则成为默认，`std::optional` 和 `std::variant` 让“销毁并重建”不必手写析构加 placement new；C++17 的保证复制消除、`std::launder` 和 `std::is_nothrow_swappable`，C++20 的 `std::construct_at`/`std::destroy_at`、concepts 和 `std::assignable_from`，都在把边角规则写进类型系统。但它们没有替你做决定：这个类到底该可拷贝、只可移动，还是两者都不行；基类要不要禁止按值复制；swap 能不能保证不抛；Pimpl 的析构该放在哪里。这些仍是设计选择，选错时编译器往往只给一个很远的错误，或者干脆不报。

剩下的部分要靠写法、警告和工具。拷贝函数手写时列全成员和基类，能 `= default` 就不手写；赋值用 copy-and-swap 或“先构造新资源、再替换旧资源”，不要依赖 `this != &other` 保证正确；基类用 protected 拷贝加 `Clone`，或者按智能指针传递；Pimpl 的析构、拷贝、移动都放到能看到完整 `Impl` 的实现文件里。Clang 的 `-Wdeprecated-copy-with-user-provided-dtor`、GCC 的 `-Wdeprecated-copy-dtor`、clang-tidy 的 `cppcoreguidelines-special-member-functions` 和 `cppcoreguidelines-slicing` 能提前指出一部分问题，ASan 能把自赋值后的 use-after-free 和双重析构变成确定的报错。工具不能替你决定语义，但能让你在选错之后尽早知道。
