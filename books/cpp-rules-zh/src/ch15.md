# 第 15 章 成员还是非成员：接口最小化

给 `Report` 增加一个“打印摘要”的功能，最顺手的写法是打开类定义，添一个成员函数：

```cpp
class Report {
public:
    void printSummary() const;   // 只用 name()、size()、total() 这些公开 getter
    // ...
};
```

这个函数没有碰任何私有数据，却成了 `Report` 的成员。从今以后，能访问 `Report` 私有部分的函数多了一个；所有包含 `Report` 定义的翻译单元都要重新编译；别的类想复用同样的摘要逻辑，只能再抄一遍。它本来可以是一个自由函数，服务任何提供 `name()`、`size()`、`total()` 的类型。

`std::string` 把这种“顺手加成员”的做法推到了极端：按 C++98/03 的标准，`basic_string` 连构造函数在内有 103 个成员函数和成员函数模板。查找、比较、截取、替换、追加，几乎所有能想到的字符串操作都挂在类上。这 103 个成员里，真正因为语言规定或必须访问内部表示而只能做成员的大约三分之一；其余大多可以在类外用公开接口实现，而且实现出来还能服务别的字符容器。Sutter 在 EXS-37 到 EXS-40 里拿它当反面样本，不是为了嘲笑标准库，而是因为它是每个人都熟悉的巨类，拆解它的过程能把“函数到底该放在哪里”讲清楚。

## 15.1 能写成非成员，就别塞进类里

假设有一个记录传感器读数的类。最自然的设计是只暴露读数据所需的最小接口，把统计操作放在类外：

```cpp
namespace monitoring {
class SensorLog {
public:
    void record(double value);
    std::size_t size() const;
    double operator[](std::size_t i) const;
    auto begin() const;
    auto end() const;
    // ...
};
}
```

平均值、峰值、“有多少个读数超过阈值”这些事情，都可以只靠 `size()`、`begin()`、`end()` 完成。把它们写成 `monitoring` 命名空间里的自由函数，比现在多一个成员函数要小得多。Meyers 在 EC-23 里讲的就是这种合成操作：假设一个 `Playlist` 已经有 `removeMissing()`、`sortByTitle()`、`dedupe()` 三个成员，再把三者合起来的 `cleanup()` 也做成成员，它就获得了访问播放列表全部私有数据的能力；写成同命名空间的 `cleanup(Playlist&)` 则只能用公开接口，类的私有部分少一个潜在的依赖者。

封装的粗略度量是“有多少函数能看见这份数据”。私有数据只有成员和友元能看见，所以每加一个成员或友元，能看见它的函数就多一个；非成员非友元不增加这个数目。EC-23 因此把选择说成“成员 vs 非成员非友元”，而不是“成员 vs 非成员”：友元和成员一样能碰私有成员，把成员改成友元并不改善封装。这一点常被忽略——`friend` 不是封装的中性修饰符，它只是把访问权限从类内挪到了类外。

非成员还有一个成员给不了的好处：分包。类定义必须整体出现在一个头文件里，不能把 `SensorLog` 的成员函数按主题拆到三个头文件；命名空间可以。把所有与传感器相关的便利函数放进 `monitoring` 命名空间，但把统计、告警、导出分别放在 `sensor_stats.h`、`sensor_alerts.h`、`sensor_export.h`，只关心统计的客户就不必看见告警和导出的声明。C++98 时代这是减少编译依赖的主要手段，今天仍然有效；C++20 modules 只是把“按头文件分包”换成了“按模块分区分包”，原则没有变（见[第 34 章](ch34.md)）。

扩展性也是同一个道理。客户想加一个“超过阈值的读数个数”，不需要改类定义，不需要继承，只要在 `monitoring` 命名空间里写一个自由函数：

```cpp
namespace monitoring {
std::size_t count_above(const SensorLog& log, double limit);
}
```

它和类自带的函数看起来一样，调用方式也一样。如果类把便利操作都做成成员，客户后来加的自由函数就只能用 `count_above(log, 70)` 这种“不像成员”的写法，永远是这个类接口里的二等公民。Sutter 在 EXS-37 里把这称为巨石类的次要代价；主要代价是把本来可以独立、可以服务其他类型的算法焊死在一个类上。

Sutter 与 Alexandrescu 在 CCS-44 里给了一个决策顺序，可以当作默认流程：

1. 语言强制必须是成员的，没得选：`operator=`、`operator->`、`operator[]`、`operator()`，以及构造函数、析构函数。需要虚分派的函数通常也留在类里，或者留一个私有虚函数给非成员转调。
2. 需要访问非公开接口才能实现的，做成成员或友元。这里的“需要”要严格判断：能用公开的 `size()`、`data()`、迭代器拼出来的，就不算需要。
3. 其余一律优先写成非成员非友元。

C++11 以后，这条建议的写法更自然了。range-for 和 lambda 让“自由函数 + 算法”的组合更容易读；C++20 的 ranges 把 `begin`/`end`、`size`、`empty` 这些操作统一成命名空间级的定制点对象（customization point object，CPO），算法本身也是非成员设施，只要求类型满足 concept。标准库的 `std::ranges::sort`、`std::ranges::find` 不会为了某个容器变成成员，你的领域算法也没有理由反过来做。需要提醒的是，“非成员”不等于“扔进全局命名空间”：自由函数应该和类待在同一个命名空间里，靠实参依赖查找（ADL）被找到，也不要在 `std` 里添加声明（见[第 33 章](ch33.md)）。

C++23 的 deducing this 让成员函数把对象参数写成显式的 `this` 参数，看起来更像自由函数，但它仍然是成员，仍然能访问私有数据，所以“优先非成员”的取舍不变（需要 `-std=c++23`；本机 Clang 21 和 GCC 15 都已支持）。

编译器不会替你判断一个函数该不该是成员，但 clang-tidy 的 `readability-convert-member-functions-to-static` 能找出不碰 `this` 的成员函数。它只建议改成 `static` 成员，而 `static` 成员仍然能访问私有数据，所以它只是一条线索：一个成员函数如果不使用任何成员状态，先问问它是不是本该是自由函数。

## 15.2 std::string 的 103 个成员：哪些真的必须是成员

EXS-37 把 `basic_string` 当作巨石类（monolithic class）的样本。按 C++98/03 的标准，它连构造函数在内有 103 个成员函数和成员函数模板。这个数字今天已经不准了：C++11 之后标准只往里加，没有删过。但作为一次接口审计的练习题，它仍然有效——Sutter 的结论是，103 个里大约 32 个需要成员身份，71 个可以写成非成员非友元而不损失效率（EXS-40）。

这 32 个不是一个拍脑袋的比例。按 EXS-38 的分法，先把它们分成三档：

- 语言强制必须是成员：6 个构造函数、析构函数、3 个 `operator=`、2 个 `operator[]`，共 12 个。这一档没有讨论余地。
- 需要访问内部表示，或者被选作其他操作的基础原语：8 个 `begin`/`end`/`rbegin`/`rend`（各有 const 与非 const 两版），`size`、`max_size`、`capacity`、`reserve`、`swap`、`c_str`、`data`、`get_allocator`，再加上三参数 `insert`、`erase(iter, iter)` 和两个 `replace`。
- 其余 71 个：能在公开接口之上等价实现，默认应该写成非成员非友元。

第一档是语法问题，第二档是设计判断。判断“需不需要成员身份”时，要问的是这个操作是否真的必须碰内部表示，而不是“写成成员方不方便”。`empty()` 不需要：`size() == 0` 或 `begin() == end()` 都行。反过来，`size()` 不能由 `empty()` 实现，所以两个里面留 `size()`。`at()` 可以由 `size()` 加 `operator[]` 实现，`clear()` 就是 `erase(begin(), end())`，`length()` 只是 `size()` 的同义词。选成员的原则是选最灵活、又不会因此损失效率的那个原语，让其他操作在它上面搭起来（EXS-38）。泛化有边界：靠 `size()` 实现的 `empty()` 对没有 `size()` 的类型不成立，`at()` 的复杂度也随容器而异（`vector` 是常数，`map` 是对数），非成员模板只能依赖该类型已经公开、且足够支撑这个操作的接口。

效率不是保留臃肿接口的理由。非成员版本可以和成员版本一样快，Sutter 在 EXS-38 里特意逐个检查，就是为了堵住“外移会变慢”这个借口。但“一样快”要逐个验证，不能想当然。EXS-39 举了一个反例：把缩短字符串的 `resize(n)` 实现成“拷贝前 n 个字符再 `swap`”，在 C++11 之后是实打实的 O(n) 深拷贝，还可能重新分配；成员版本只需要改长度并补结尾空字符。这类操作留在类里有性能理由。类似地，`replace` 不能用 `erase` 加 `insert` 拼出来——两趟字符搬移，还可能多一次重新分配；`erase` 也没有不损失效率的外部等价物：外部只能用拷贝覆盖再 `resize`，搬移次数更多。所以 EXS-40 的结论不是“除了 32 个全删”，而是“该留的留，能外移的才外移”。

EXS-39 把“原语”的选择讲得最具体：`insert` 比 `append` 更基础。留下三参数 `insert`，六个 `append` 都可以归约到它，三个 `+=` 又可以归约到 `append`，`push_back` 按容器要求本来就等价于 `insert(end(), x)`。`assign` 的六种形式可以用“构造临时对象 + `operator=`”表达。最容易答错的是 `operator+=`：它在语法上被归入赋值运算符，但语言只强制 `operator=` 本身是成员，`operator+=` 完全可以写成非成员。

C++11 之后，`basic_string` 的实现被要求连续存储，`data()` 返回内部缓冲区的指针，`operator[]` 返回其中元素的引用，写时复制（COW）事实上不再可行；同时加入移动构造和移动赋值，`substr`、`operator+` 这类按值返回的自由函数不再有 C++98 时代的深拷贝顾虑。C++17 的 `string_view` 把“只读、不拥有”的视图独立出来，`substr` 变成 O(1) 的切片，`find`、`compare` 可以在视图上做，一份实现同时服务 `std::string`、字面量和 `const char*`。这正是“把算法从容器里解耦”的现代形态：不是把 `std::string` 改造瘦，而是在类外重建一层更通用的接口。

## 15.3 与类同处的自由函数也是接口

前面说自由函数可以扩展类的接口。这句话比它听起来更强：只要一个自由函数“提到”某个类，并且和这个类放在同一个头文件或命名空间里，它就是那个类接口的一部分，不管它有没有 `friend`、是不是成员。Sutter 在 EXC-32 里把它写成接口原则（Interface Principle）：

> 对类 X，所有既“提到”X、又与 X“一起提供”的函数，包括自由函数，都逻辑上属于 X，因为它们构成 X 接口的一部分。

“提到”包括按值、引用、指针传参或返回；“一起提供”可以理解为同一个头文件和/或同一个命名空间。成员函数天然满足这两条，所以这条原则主要是把自由函数也算进来。它的用处不在命名，而在依赖分析：一个类依赖什么，不能只数它的成员函数提到了哪些类型。

最典型的例子是 `operator<<`。假设 `Invoice` 和下面这个自由函数都放在 `invoice.h` 里：

```cpp
std::ostream& operator<<(std::ostream& os, const Invoice& inv);
```

`Invoice` 的成员函数一个都没有提 `ostream`，但这个头文件仍然需要一个 `ostream` 的声明（至少是 `<iosfwd>`），任何包含 `invoice.h` 的翻译单元也一样。按接口原则，`operator<<` 是 `Invoice` 接口的一部分，而它依赖 `ostream`，所以 `Invoice` 这个包依赖 `ostream`。把函数体挪到 `.cpp` 只改变“谁需要完整的 `ostream` 定义”，不改变头文件里的声明依赖。

接口原则和实参依赖查找（ADL）是同一件事的两面。ADL 让与实参类型同命名空间的函数被找到，接口原则解释为什么这些函数应该放在一起。下面的程序把这个机制变成一次编译错误：`billing::Invoice` 和它的 `operator<<` 同处 `billing`；审计模块 `audit` 又写了一个 `operator<<`，也在自己的命名空间里。`audit::dump` 里的 `std::cout << inv` 先做普通查找，找到 `audit::operator<<`，ADL 又把 `billing::operator<<` 带进来，两个候选一样好：

```cpp

```

clang 的诊断：

```text

```

这不是 `billing` 破坏了 `audit` 的代码。按接口原则，`billing` 后来加的那个函数本来就是 `Invoice` 接口的一部分；`audit` 想给同一个类型再提供一个“同处”的输出函数，就必须明确自己要哪一个，比如在调用点写 `billing::operator<<(std::cout, inv)`，或者给自己的函数换个名字。Myers 在 1997 年给出的那个例子也是这个结构：命名空间 A 里的 `X` 新增一个 `f(X)`，命名空间 B 里原本调用 `B::f(A::X)` 的代码就出现二义。成员函数的关系仍然更强：在类成员函数里，如果类作用域已经找到同名函数，编译器不会再做 ADL；访问权限也是成员和友元的特权。

接口原则直接回答了“`operator<<` 该不该虚”这个老问题。EXC-33 比较了两种写法。第一种是自由函数直接输出，类里完全不提 `ostream`；第二种是类里放一个虚 `Print(std::ostream&)`，自由 `operator<<` 转调它。传统分析说第一种依赖更少、还省一次虚调用。但按接口原则，第一种的 `operator<<` 只要和类同处一个头文件，它就属于类的接口，而它提到 `ostream`，所以类照样依赖 `ostream`；两种写法在头文件层面都需要 `ostream` 的声明，在实现层面都需要完整的 `ostream` 来写字符。第一种“少依赖”的优势是错觉，真正的取舍只剩“要不要为派生类保留多态输出”。

如果需要，虚 `Print` 是常见做法：自由 `operator<<` 只负责转调，动态类型由虚函数决定。下面的例子里，`Camera` 通过 `Device&` 输出仍然是 `Camera(cam-1)`；对照的 `Report::label()` 不是虚函数，通过 `Report&` 调自由 `operator<<` 只能得到 `Report`，只有直接对 `AuditReport` 对象调用 `label()` 才得到派生类的文字：

`Device` 和 `Report` 的 `operator<<` 都只使用公开接口，都和类同处 `devices` 命名空间。差别不在依赖，而在分派：`Device::print` 是虚函数，`operator<<` 收到 `const Device&` 后调的是动态类型的那一份；`Report::label` 不是虚函数，`operator<<` 的参数静态类型是 `const Report&`，调用的就是 `Report::label`。如果输出不需要多态，第一种写法更直接；如果需要，就别为了“少一层调用”放弃虚函数——一次虚调用的成本通常远小于输出本身的成本。

这里也能看出接口原则的实际用法：分析一个类依赖哪些类型时，把同处一处的自由函数、`formatter` 特化、`operator<<` 都算进去；反过来设计接口时，如果你不想让类依赖某个类型，就不要让同处的自由函数在签名或实现里提到它。隐藏友元（hidden friend）是另一个相关技巧：把 `operator<<` 定义成类内的 `friend` 函数，只能通过 ADL 找到，不能靠普通查找或显式限定调用；它仍然是类接口的一部分，但减少了命名空间里的名字。ADL 与命名空间的组织见[第 33 章](ch33.md)。

## 15.4 输出参数和默认实参都容易掩盖意图

《Thinking in C++》在讲引用时提醒过一件事：`cin.get(c)` 的调用点看起来和传值一样，读者不会立刻想到 `c` 被改写了；但 `get` 的全部目的就是往 `c` 里写。TIC-12 因此建议，普通函数需要修改外部对象时用指针，让调用点必须写 `&c`；输入参数用 `const T&`，输出或输入输出参数用 `T*`。这条建议针对的是普通函数的输出参数，不针对运算符和必须修改自身的成员函数——`operator<<` 当然要改流，`vector::push_back` 当然要改容器，它们的语义从名字就看得出来。

非 const 引用做输出参数的问题不只是“看不出”，还会让失败路径变得隐蔽。考虑一个解析端口的函数：

```cpp
bool parse_port(std::string_view text, int& port);
```

调用 `parse_port(line, port)` 时，`port` 看起来像输入；如果解析失败，函数可能根本没碰 `port`，调用方拿到的还是上一次的旧值。返回值 `bool` 如果被忽略，编译器默认也不会提醒（除非标了 `[[nodiscard]]`）。改成指针版本 `parse_port(line, &port)`，至少取地址这个动作会让人多看一眼；改成返回 `std::optional<int>`，调用方必须处理“没有值”的情况，数据流从签名就看得到。


第二次 `parse_port_ref("port=oops", port)` 失败后，`port` 仍然是 443；调用点没有 `&`，也没有“返回值被忽略”的提示，只有读函数体才知道它没改。指针版本多了一个 `&`，optional 版本则把“成功才有值”写进了类型。`split_pair` 的调用 `split_pair("db:5432", service, host)` 完全合法，参数类型一样，编译器没有任何理由拒绝；两个输出参数的类型相同，就是把顺序交给调用者记忆。要避免这种问题，可以让函数返回一个 `struct { std::string host; std::string service; }`，调用方用 C++17 的结构化绑定接住，或者至少给两个参数起不可能混淆的类型。

C++17 的 `std::optional`、结构化绑定和 `std::tuple` 让多返回值比 C++98 时代容易得多；C++20 的 `std::span` 适合“调用方提供缓冲区”的场景，函数不再用一个裸指针加一个长度做输出参数；C++23 的 `std::expected<T, E>` 把值和错误原因放进同一个返回类型，需要 `-std=c++23`，本机 Clang 21 + libstdc++ 15 已支持。非 const 引用并没有被淘汰：运算符、必须修改自身的成员函数、以及“参数一定有效且必须修改”的接口仍然适合它。TIC-12 的要点是，普通函数的输出参数应该让调用点显式，而不是让引用语法替它打掩护。

默认实参有类似的问题。TIC-13 的建议是：默认值应该是调用者本来就会写在那里的普通值；如果某个默认值会触发完全不同的代码路径，它就成了一个开关，应该拆成重载、`std::optional` 或命名工厂函数，而不是在函数体里用 `if (arg == default)` 分流。

默认实参还有两个现代替代品。需要区分“没提供”和“提供了一个值”时，用 `std::optional<T>` 参数或返回类型；需要一组可选配置时，用选项结构体加 C++20 的指定初始化器（`Options{.limit = 4096}`），比 `void f(int a, int b = 0, int c = 0, int d = 0)` 这种占位实参好读。TIC-13 也提醒，占位实参仍然要求调用者按位置补齐，今天不如直接写重载或选项结构体。给已有函数追加末尾的默认参数、以少破坏既有调用，是默认实参最正当的用途之一；但新增的参数如果改变行为分支，就不该靠默认值悄悄发生。

默认实参是静态绑定的：它在调用点被编译器补进实参列表，不参与动态分派。把默认值写在虚函数上，通过基类指针调用时用的是基类声明的默认值，即使实际调用的是派生类覆盖——这一点属于继承那一章的话题（EC-37，见[第 17 章](ch17.md)），这里只需记住：默认值不是运行时策略，别用它表达“派生类可以换一个默认行为”。

## 回头看

这一章的几条规则防的是同一件事：接口在没有必要的地方变宽。成员函数、友元、与类同处的自由函数、非 const 引用输出参数、当开关用的默认实参，都会让“这个类到底承诺了什么”变得模糊。非成员非友元把能碰私有数据的函数数量压到最小；接口最小化把“必须碰内部表示”的操作压到少数原语；接口原则提醒你，自由函数并不会因为不在类里就自动离开接口，依赖分析要把它算进去；输出参数和默认实参则是在函数签名这一层，把“谁会改什么”“走哪条路”重新变得可见。

C++20/23 以来，语言和标准库替我们兜住了一部分。ranges 和定制点对象让自由算法成为默认写法，`string_view` 让只读的字符串操作脱离具体容器，`std::erase`/`erase_if` 把删除操作搬到类外，`std::format` 提供了不经过 `ostream` 的格式化接口，`std::optional`/`std::expected` 让返回值比输出参数更能表达失败。但“这个函数该不该是成员”仍然没有编译器能替你判断：`std::string` 没有因为 `string_view` 出现就瘦身，标准库自己也在兼容性和新接口之间折中。能帮你的是 clang-tidy 的 `readability-convert-member-functions-to-static`、依赖分析工具和代码评审；真正的判据还是那三个问题——语言是否强制、是否必须碰内部表示、其余能不能用公开接口实现。
