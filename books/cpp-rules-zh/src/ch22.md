# 第 22 章 编译期计算：constexpr、traits 与反射

一个模板只因为尺寸参数不同，就各实例化一份几乎一样的循环；一个 `constexpr` 函数在数组长度里被编译期求值，换一个运行期实参又变成普通函数调用；一段用 `typeid` 判断迭代器类别的代码，在 `list` 上不是慢一点，而是根本编译不过。这三件事看着分散，问的其实是同一个问题：哪些工作可以搬到编译期，搬过去要付什么代价，边界又在哪里。

C++ 给出的工具分成两层。值层面的常量和初始化靠 `constexpr`、`consteval` 和 `constinit`，它们让常量、函数和对象的初始化进入翻译阶段；类型层面的计算靠模板、特化和 traits（类型特征），它在模板实例化时完成，产出类型和按类型生成的代码。两层工具都能把运行期的工作提前，但都不会凭空消失：模板会为每组实参生成代码，`constexpr` 函数仍然要满足一堆限制，编译期报错也未必比运行期报错好读。

本章按“先看代价，再看工具，最后看接口”的顺序走。先处理模板带来的代码膨胀，再讲 traits 和模板元编程怎样在类型层面做判断，然后把 `constexpr` 的规则和类内 static 成员的定义问题讲清楚，最后落到定制点的设计：一个模板允许调用方在哪里插入代码，以及怎样不把代码写死在某种具体容器上。

两个 `GridN` 的计数各自是 1，说明 `GridN<int, 4>::total` 和 `GridN<int, 64>::total` 是两份独立的函数，各自带着一个 `bodies_` 静态变量；`GridShared` 的两个尺寸报告的计数都是 2，因为它们调用的 `GridBase<int>::total_impl` 只有一份，静态变量也只有一份。代价直接写在 `sizeof` 里：`GridShared<int, 4>` 比 `GridN<int, 4>` 大 16 字节，那是基类里保存数据指针和尺寸的两个成员；64×64 的版本同样多 16 字节，在 16 KB 的数据面前不算什么，但如果矩阵元素很少、对象很多，这个比例就不能忽略了。

EC-44 把这个过程叫“共性/变化性分析”（commonality and variability analysis）：先找出实现里哪些部分随参数变化、哪些部分不变，把不变的部分搬到一处，只让变化的部分留在模板里。非模板代码里的重复是看得见的，两个函数长得一样，你会立刻想到提取公共函数；模板代码里的重复是隐式的，源码只有一份，重复发生在实例化之后，所以更容易被忽略。Meyers 举的是 `SquareMatrix<T, n>` 的 `invert`：`n` 是 5 还是 10，函数体只差几个常数，却要各编译一份。

做法是把尺寸从模板参数降级为构造函数的参数，只保留按元素类型参数化的非模板基类。基类保存数据指针和尺寸，`invert` 或 `total` 的实现搬进去；数据可以放在派生类对象里，也可以放在堆上，基类只认指针和尺寸。派生类模板仍然按 `T` 和 `N` 区分类型，`GridN<int, 4>` 和 `GridN<int, 64>` 依旧不能互相赋值，但它们的成员函数只是对内联基类实现的一层薄包装。示例里用私有继承，因为基类存在的目的只是共享实现，不表达“是一种”的关系；如果基类实现被声明为 `inline`，编译器仍可能把它的函数体复制进每个包装函数，膨胀就又回来了，所以示例给共享实现加了 `[[gnu::noinline]]`。

这笔账不是单向的。尺寸变成运行期值之后，编译器不再知道循环要跑多少圈，常量传播、按已知边界展开循环、把边界折进指令这些机会就少了很多；共享版本的对象还多了一个指针和一个尺寸字段。EC-44 的结论是两种效果谁占上风只能实测：在代码体积、指令缓存局部性和单次调用速度之间权衡，不能只凭“少一层模板”就认定更快。原书写作时还没有 `std::span`，今天把“指针 + 长度”传给非模板实现可以写成 `std::span<T>`（C++20），接口更清楚，但运行期长度这个事实没有变。

类型参数也会造成同样的重复。64 位 Linux 上 `long` 和 `long long` 都是 64 位，`vector<long>` 和 `vector<long long>` 的成员函数机器码就可能一模一样（EC-44 写作时举的是 `int` 和 `long`，那在 32 位平台上成立；今天 `int` 是 32 位、`long` 是 64 位，不能直接套用）；各种指针类型的实例也常常只在类型检查上有区别。EC-44 提到一些标准库实现把强类型指针的操作转交给 `void*` 版本的公共实现，正是这个思路。不过链接器是否会合并相同的函数体（identical code folding，ICF）取决于工具链：lld 和 gold 提供 `--icf=all`，GNU ld 没有等价选项，所以“反正链接器会合并”不能当作设计前提。

新标准没有取消这条规则。C++11 的变参模板减少了“参数个数不同就重写一遍”的情况，C++17 的 `if constexpr` 可以避免实例化不满足条件的分支，`extern template`（C++11）能阻止同一个实例在多个翻译单元里重复生成，C++20 的 concepts 只约束参数、不会自动合并实例。非类型模板参数把配置编进类型这件事本身仍然有用，《Essential C++》把它列为泛型编程的基本手法（ESS-12，见 [第 20 章](ch20.md) 20.6 节）；要不要为体积放弃它，得看这份代码被实例化多少次、每次的循环有多大。

今天的做法是先量再改。`nm -C --size-sort` 能按符号大小列出目标文件里的函数，`-C` 会把模板实例的名字还原出来；如果某个 `T` 或某个 `N` 的实例占了可观的体积，再考虑抽离。反过来，如果这段代码在热路径上、尺寸参与优化，保留编译期尺寸往往比省几 KB 更划算。EC-44 不是“模板要少用”，而是“模板生成的重复要看得见”。

主函数 `advance_by` 只做两件事：从 `iterator_traits` 取出 `iterator_category`，用这个类型造一个标签对象传给 `do_advance`。真正的工作由三个 `do_advance` 重载完成，重载决议在编译期挑出唯一匹配的那一个，没被选中的函数体不会进入这个实例化。`vector` 的迭代器类别正好是 `random_access_iterator_tag`，精确匹配；`list` 的类别是 `bidirectional_iterator_tag`，选双向版本；`forward_list` 的类别是 `forward_iterator_tag`，示例里没给它写重载，但 `forward_iterator_tag` 继承自 `input_iterator_tag`，派生类到基类的转换让单向版本成为可行候选。标签之间的继承关系不是装饰，它让“为 input 写的实现”自动覆盖 forward，这正是 EC-47 强调的编译期 if-else。

指针没有嵌套 typedef，按说 traits 对它无能为力，但 `iterator_traits` 有一个 `T*` 的偏特化，把指针的类别定为随机访问、`value_type` 定为去掉 cv 的 `T`。示例最后用裸指针和 `const int*` 调用了同一套函数，`static_assert` 把 `value_type` 是 `int` 这件事写死在编译期。EC-47 把设计 traits 的步骤总结成三步：先确定要暴露什么信息（迭代器类别、值类型），再给信息起名字（`iterator_category`、`value_type`），最后提供一个主模板和一组特化，让用户类型和内置类型都能落到某个特化上。traits 不是关键字，也不是语言设施，它只是一个约定：用一个类模板承载“关于类型的信息”，需要时特化它。

`if constexpr`（C++17）把这套 worker 重载收进了一个函数，C++20 的 `std::random_access_iterator`、`std::bidirectional_iterator` 又把类别判断写成了 concept。示例里的 `advance_by20` 与 `advance_by` 行为相同，但少了一组辅助函数，条件不成立的分支在实例化时被丢弃，不会产生 `it += d` 对 `list` 非法的错误。`if constexpr` 不是运行期 `if` 的优化版：条件必须是常量表达式，丢弃的分支仍然要能通过语法检查，但不参与实例化。这一点和前面 `typeid` 的例子正好相反，也是它能把 traits 的 tag dispatch 大部分取代的原因。

traits 解决了“类型信息从哪来”，模板元编程解决“拿这些信息做什么”。EC-48 把模板元编程（template metaprogramming，TMP）定义为“在编译期执行的模板程序”：递归实例化代替循环，全特化提供终止条件，`enum` 或 `static const` 保存中间结果。阶乘是它的 hello world：

`Factorial<10>` 不是一个数，而是一个类型；`::value` 是实例化过程中算出来的静态成员。`Factorial<10>` 引用 `Factorial<9>`，一路递归到 `Factorial<0>` 的全特化才停。C++11 之前没有 `constexpr`，`enum { value = ... }` 是常用写法；现在写 `static constexpr` 更直接。真正的收益不在阶乘本身，而在“把判断和计算前移到编译期”：维度单位检查、表达式模板、policy-based design 都建立在这个机制上。代价也明确：每个递归层次都是一次模板实例化，编译时间随参数增长；错误信息会穿过一长串实例化栈；调试器对编译期求值基本无能为力。把要求写成 `static_assert` 或 concept，能让错误停在调用点而不是几十层实例化之后；编译时间真的成问题时，clang 的 `-ftime-trace` 能把耗时归到具体的模板实例上（本机 Clang 21 可用），比凭感觉删模板参数可靠。

同一个阶乘，今天用 `constexpr` 函数写更短，C++14 之后还能直接用循环。`static_assert(factorial_loop(6) == 720)` 证明它在编译期算出了结果，而运行时传入变量时它又退回普通函数。值层面的 TMP 因此基本被 `constexpr` 取代了，但类型层面的 TMP 还在：`std::integer_sequence` 要把下标包展开成 `std::array` 的初始化列表，最直接的写法是可变参数模板；表达式模板、`std::tuple` 的实现、反射库也仍然靠模板生成类型和代码。C++20 的 `consteval` 把“必须编译期求值”写进函数类型，`std::is_constant_evaluated` 让一个函数能区分两种求值环境；C++23 的 `if consteval` 把这个判断变成语句。

C++11 的 `<type_traits>` 把常用的类型判断（`is_same`、`is_base_of`、`enable_if` 等）收进了标准库，不用再自己写一套。写 traits 时还有一个现代习惯：用别名模板而不是 `typedef` 暴露结果。`std::iterator_traits<It>::value_type` 是类型，用户要写 `typename`；标准库为常用 traits 配了 `_t` 别名（C++14 起，如 `std::remove_cv_t`）和 `_v` 变量模板（C++17 起，如 `std::is_same_v`），写约束和 `static_assert` 时短很多。EMC-09 讲的就是这件事：`using` 别名比 `typedef` 更易读，而且能直接带模板参数，见 [第 5 章](ch05.md) 5.3 节。

静态反射是这条线的下一站。C++26 的 P2996 引入 `^^` 运算符和 `std::meta`，能在编译期枚举类的成员、拼接类型、生成代码，很多今天靠手写 traits 和宏维持的样板可以省掉。本书环境（Clang 21、GCC 15）都不支持它，没有可运行的示例；其它编译器或库的支持情况需核实。在它落地之前，traits、`if constexpr` 和 concepts 仍是类型层面计算的主力。

`a` 用运行期读到的值初始化，完全合法，因为 `const` 只要求初始化之后不再修改；`b` 要求编译期初值，`runtime` 不是常量表达式，编译器只能拒绝。数组长度、模板实参、`case` 标签、位域宽度这些位置要的是常量表达式，`const` 不够，`constexpr` 才行。EMC-15 把这一点说得很直接：所有 `constexpr` 对象都是 `const`，但不是所有 `const` 对象都是 `constexpr`。

`constexpr` 用在函数上又是另一回事。它不保证每次调用都在编译期求值，也不保证返回 `const`；它保证的是“实参是常量表达式时，结果可以出现在要求常量表达式的地方”。实参是运行期值时，同一个函数就是普通函数。下面的程序把两种调用并排放在一起：

`constexpr` 还会改变接口。一个函数加上 `constexpr` 之后，客户端可以在模板实参、数组长度里使用它；以后为了调试往函数里加一句 I/O，或者调用一个非 `constexpr` 的函数，就可能让这些客户端全部编译失败。EMC-15 把 `constexpr` 称为接口的一部分，意思是要么长期维护这个约束，要么一开始就别加。C++20 的 `consteval` 把约束再收紧一档：调用点必须能求出常量，否则就是错误，适合那些“离开编译期就没有意义”的函数，比如生成固定表、检查格式串。`std::format` 的格式串参数就是这样一个例子：`std::format("{:s}", 42)` 在本机 Clang 21 + libstdc++ 15 和 GCC 15 上都会在编译期报 `call to consteval function ... is not a constant expression`。

TIC-02 讲的就是这件事，它提醒：编译器不保证在编译期诊断，漏定义通常表现为链接错误。在头文件的类里写 `static const int`、多个翻译单元取它的地址，是最容易踩的形态；模板里的静态成员更难定位，因为实例化点可能在别的翻译单元。C++17 之后，首选写法是 `static constexpr`（隐式 inline）或 `inline static`，把定义留在头文件里；需要兼容 C++14 时，仍然要在某个 `.cpp` 里补一行定义。C++20 的 modules 不改变 odr-use 规则，只是把“哪个翻译单元看得到定义”这个问题换了个形式。

`constexpr` 的收益要放在具体场景里看。它能保证常量初始化，可能把对象放进只读段，让计算在编译期完成；代价是编译时间、函数体限制和接口承诺。对小的工具函数、尺寸和表，加上 `constexpr` 通常没有坏处；对会读文件、会分配内存、会打日志的函数，硬套 `constexpr` 只会把实现拧成一团。`consteval` 和 `constinit` 是更精确的工具：需要“必须编译期”就用 `consteval`，需要“静态初始化但不只读”就用 `constinit`，不要用 `constexpr` 一把抓。

`billing::audit` 要求 `T` 提供成员 `audit()`，这是“隐式接口”式的定制点；`billing::exchange` 里的 `swap(a, b)` 是非限定调用，ADL（argument-dependent lookup，实参依赖查找）会到 `customer` 命名空间里找 `swap`，于是 `customer::swap` 被选中；`billing::total_cents` 把“怎么把类型换算成 cents”交给 `amount_traits<T>`，用户在自己的类型定义之后特化这个类模板，特化写在库的命名空间 `billing` 里。前两种定制点一次就能被多个库复用，但名字的语义必须足够通用；traits 特化把定制隔离在库自己的命名空间里，适合“同一个名字在不同库里含义不同”的操作，代价是每个库都要写一份适配器。

意外发生在 `settle_wrong`。它本来只想调用库内部的 `detail::adjust`，但 `using detail::adjust;` 让这个名字进入了 `billing` 的普通查找，非限定的 `adjust(t)` 又触发了 ADL，`customer::adjust(const Invoice&)` 的精确匹配胜过了 `adjust(long long)` 的整数转换，于是 800 cents 变成了 1000800。`settle_right` 把调用限定成 `detail::adjust(t.cents)`，ADL 被关掉，结果才是预期的 900。CCS-65 的建议很具体：模板内部的辅助函数放进嵌套命名空间，并且用限定调用；如果不想改命名空间，把函数名放进括号写成 `(adjust)(t)` 也能关掉 ADL（本机 clang 21 和 GCC 15 都如此），但限定名更清楚，读代码的人不用记住这条冷知识。

三种定制点各有适用范围。成员函数适合“类型本身就该提供这个操作”的情况，比如 `audit()`、`size()`、`begin()`；ADL 非成员适合操作符和 `swap` 这类“类型作者和库作者都可能实现”的服务；traits 特化适合含义随库而变的操作，也适合内置类型——`int` 没有成员，也没有关联命名空间，想让库为 `int` 定制，最可靠的方式是特化库提供的 traits。选中一种之后，还要在文档里写清楚：这个定制点要求什么签名、有什么后置条件、失败时怎么报告。只写“T 要有 foo”不够，调用方还需要知道 `foo` 能不能抛、返回空表示什么。

C++20 起标准明确禁止特化标准库的函数模板（P0551），所以给 `std::swap` 写全特化不是选项，在类型所在命名空间写重载、让通用代码通过 `using std::swap; swap(a, b)` 找到它，才是合规做法；这个惯用法在[第 20 章](ch20.md) 20.4 节讲函数模板特化时还会出现。C++20 的定制点对象（customization point object，CPO）则把 ADL 的查找顺序固定下来。`std::ranges::begin` 是一个函数对象，它先找成员 `begin`，再找 ADL 能找到的 `begin`，并用 concept 检查返回值；调用方写 `std::ranges::begin(r)`，查找顺序和返回值要求都是固定的，不会像裸 ADL 那样被任意同名函数抢走，也不需要在每个调用点写 `using std::begin;`。这是 CCS-65 的原则被标准库制度化的例子：定制点仍然存在，但“怎么找、找到哪个、找到后要求什么”都写进了类型和约束里，而不是留给非限定调用的运气。

这条规则在新标准下有一半理由变了。C++11 要求提供 `size()` 的标准容器都在常数时间内返回（`forward_list` 干脆不提供 `size()`），所以“`list` 的 `size()==0` 很慢”不再成立；但 `empty()` 仍然更准确：它表达的是“有没有元素”，不要求容器能报出确切大小；对输入迭代器这类只能比较 `first == last` 的范围，“是否为空”本来就是比“大小”更原始的概念。C++20 的 `std::ranges::sized_range` 也把“知道大小”和“能遍历”分成了两个概念。迭代器优先于下标也一样：`list` 根本没有 `operator[]`，但所有容器都有迭代器；C++11 的 range-for 和 `auto` 让迭代成为默认写法，C++20 的 ranges 又把“需要哪些能力”变成编译期可检查的约束。CCS-67 还提醒一个例外：有些场合下标确实能让编译器生成更好的代码，但要用之前先确认真的需要，并且编译器真的做了。

“最抽象”不等于“越泛化越好”。如果一个函数只需要读一遍元素，就不要要求容器可多次遍历；如果只需要 `forward_range`，就不要写成 `random_access_range`。对类型的要求越少，能进来的类型越多；要求少到不够实现用，也不行。CCS-67 的判断标准是“对接口的能力要求最低”，不是“模板参数最多”。EC-41 说的隐式接口是同一件事的另一面：模板对类型的要求藏在函数体里，编译器只检查用到的表达式，所以接口写宽了不会报错，写窄了才会在实例化时炸；把要求写成 concept 或文档，是让隐式接口变得可见的办法，见 [第 20 章](ch20.md) 20.1 节。

定制点和泛化最终都要落到“谁负责什么”。库作者负责选一种定制机制、把查找规则和语义写清楚、把内部辅助函数藏好；使用者负责按文档提供成员、ADL 函数或 traits 特化，不去猜库内部用了哪个名字。C++20 之后，concepts 和 CPO 让这件事比以前更容易检查，但没有替你做决定：一个模板可以同时有成员、ADL 和 traits 三个口子，也可以一个都不开，选择哪一种、在哪里开，仍然要写代码的人有意识地定下来。

## 回头看

把四节连起来看，编译期计算不是一种孤立技巧，而是一组交换：把运行期的循环、判断和类型选择搬到翻译期，换来更早的错误和更少的运行期工作，付出的是目标代码体积、编译时间和接口上的长期承诺。22.1 的模板膨胀和 22.2 的 TMP 是同一枚硬币的两面，重复都发生在源码看不见的实例化之后；22.3 的 `constexpr` 把值层面的计算从模板语法里解放出来，22.4 则把问题推回接口：一个模板允许调用方在哪里插入代码，查找规则和语义由谁负责。

C++20 以后，语言接管了相当一部分工作：值计算有 `constexpr`/`consteval`，分支有 `if constexpr`，接口约束有 concepts，定制点有 CPO。但代码膨胀不会自动消失，定制点的语义仍要人写清楚，泛化到什么程度仍要人判断。能替你把关的是测量（`nm -C --size-sort`）、编译器警告（clang 的 `-Wconstant-evaluated`、GCC 的 `-Wtautological-compare`）和 sanitizer，以及把假设写成 `static_assert` 的习惯——它们都比“我觉得这样更快”可靠。
