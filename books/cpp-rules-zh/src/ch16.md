# 第 16 章 运算符重载与比较：让自定义类型像内置类型

一个数值类型的 `operator+` 写成成员函数，`z + 1.0` 能编译，`1.0 + z` 却报错：

```cpp
Complex z(1.0, 0.5);
Complex a = z + 1.0;   // 可以，1.0 转成 Complex
Complex b = 1.0 + z;   // 不行，double 没有成员 operator+
```

编译器把第一行拆成 `z.operator+(1.0)`，`1.0` 是参数列表里的实参，可以隐式转换成 `Complex`；第二行想拆成 `1.0.operator+(z)`，而 `double` 根本没有这个成员函数。问题不在转换本身，而在成员函数的 `this` 是一个不出现在参数列表里的隐式参数，它不参与隐式转换。本章就从这里开始，把运算符重载当成接口设计的一部分：哪些运算符必须写成非成员，复合赋值和独立运算符怎样分工，前后置 `++` 的返回类型为什么不同，哪些运算符碰不得，比较器与 `operator<` 的关系，以及求值顺序和几个容易被忽视的边界。

运算符重载的目标不是“让代码看起来像数学”，而是让自定义类型在常见写法下表现得像内置类型，同时不破坏读者对内置运算符的预期。这条线贯穿整章：能守住语义就提供，守不住就改用具名函数；能让编译器替你生成（例如 C++20 的 `<=>`），就不要手写六份容易互相矛盾的比较。

`z + 1.0` 和 `1.0 + z` 都会为 `1.0` 构造一个临时 `Complex`，两次转换各一次，结果相同。转换并没有消失，只是现在两侧都能用它。`operator+` 的实现是 `Complex operator+(Complex lhs, const Complex& rhs) { return lhs += rhs; }`：第一个参数按值接收，左值传进来时复制一次，纯右值传进来时直接初始化；函数体只调用 `operator+=`，独立运算符不再重复写加法逻辑。这正是 CCS-27 推荐的规范形式：定义了 `a @ b` 就提供 `a @= b`，并让 `a @= b` 完成实际工作，`a @ b` 在副本上调用它。好处有两个：语义只有一份，`+` 和 `+=` 不会在维护中分叉；`+=` 直接改写左操作数、返回引用，不产生返回值的临时对象，需要效率时调用方可以选它。MEC-22 说的是同一件事，只是更强调“独立的 `op` 用 `op=` 实现”，并提醒模板化这组运算符时约束要写清楚，否则错误会推迟到实例化才出现。

Sutter 在 EXC-20 里评审过一个 `Complex` 类，问题几乎都落在这条线上：`operator+` 是成员函数，所以 `1.0 + b` 不工作；它修改 `*this` 并返回 `void`，把加法写成了 `+=`；参数按值传递，多了一次不必要的复制；`operator<<` 是成员函数、第二个参数按值传 `ostream`、返回 `void`，既不能链式输出，也不该是成员；前置 `++` 按值返回，后置 `++` 返回非 const 值且没有复用前置版本；成员名以下划线开头，踩进了保留名的灰色地带。修正后的骨架就是本节和下一节的例子：复合赋值返回 `T&`，独立运算符是非成员、返回 `T`，流运算符返回 `std::ostream&`，前后置 `++` 分开实现。EXC-20 还有一条今天更值得强调的建议：动手写 `Complex` 之前先看 `std::complex`，标准库已经把这组运算符和边界情况处理好了。

有一处原书的结论需要按 C++11 之后的情况改写。EXC-20 和 CCS-27 都提到把 `operator+` 的返回类型写成 `const T`，用“不能给 const 临时对象赋值”来禁止 `a + b = c`。这个技巧在 C++98 里有效，但在 C++11 之后代价变大：`const T` 返回值不能绑定到 `T&&`，会抑制移动。C++17 的保证复制消除覆盖了 `T c = a + b;` 这种用纯右值直接初始化同类型对象的情况，所以这个具体写法不再多一次复制；但 `v.push_back(a + b)`、`T c = std::move(a + b)` 这类需要绑定到 `T&&` 的场景仍会退回复制。现代写法返回非 const 的 `T`，接受 `a + b = c` 仍然能编译这个瑕疵——对类类型的纯右值调用成员 `operator=` 是合法的，本节示例用 `static_assert` 把这一点固定下来。真想禁止对临时对象赋值，C++11 的引用限定符更合适：把 `operator=` 声明为 `T& operator=(const T&) &`，右值就不能调用它；这比修改返回类型精确，也不会妨碍移动。

C++20 的三路比较 `<=>` 处理的是比较运算符，不改变算术运算符的写法；`std::rel_ops` 那套“用 `==` 和 `<` 自动补出其余比较”的工具也因此不再推荐。算术类型仍然要自己决定提供哪些运算、哪些复合赋值，以及返回类型。下一节看自增自减，它把“前置做实际工作、后置返回旧值”这条分工体现得最清楚。

`Step old = s++;` 先构造 `old` 保存旧值，再把 `s` 加一；`++s` 直接加一，返回 `*this` 的引用。输出里后置版本多出一次复制，前置版本没有增加复制；在 `-O0` 下这也是确定的，因为“旧值必须留下来”本身就是后置语义的一部分。C++11 的移动语义能让返回旧值这一步在合适的时候变成移动，但它消不掉“多一个旧值对象”这件事。CCS-28 因此建议：不需要旧值时优先写前置，语义相同、少一个对象；这不是过早优化，而是避免无谓劣化。对迭代器尤其如此，泛型代码里的 `it++` 可能真的付出一次拷贝。

MEC-06 和 CCS-28 给出的规范形式完全一致：前置版本做增量并返回 `T&`；后置版本带一个哑元 `int` 参数，用来和前置版本区分，函数体里不要使用这个参数（省略参数名就不会触发“未使用参数”的警告）；后置版本先保存旧值，再调用前置版本，最后按值返回旧值。后置版本调用前置版本这一点很关键，它保证两种形式的增量逻辑只有一份，不会在维护中分叉。MEC-06 还解释了后置版本为什么不能返回引用：它返回的是已经消失的旧状态，必须是一个独立对象。

原书用“返回 `const T`”来禁止 `i++++`：第一次后置 `++` 返回 const 临时对象，第二次 `++` 是非 const 成员函数，不能作用在 const 对象上。这个技巧在 C++11 之后有了更精确的替代品：给后置 `++` 加引用限定符 `&`，写成 `T operator++(int) &`，它就只能作用于左值，对第一次返回的纯右值再调用会直接找不到成员函数：

复合赋值与独立运算符的分工在本节也能看到：`(s += 3) += 4` 能继续往左结合，是因为 `operator+=` 返回 `T&` 而不是值。MEC-22 和 CCS-27 都建议把 `operator+` 建立在 `operator+=` 上，16.1 的例子已经这样做了；这里再补一个细节：`operator+=` 只求值左操作数一次，而 `a = a + b` 要先算 `a + b` 再赋值，前者通常更省。两者语义必须一致，差别只允许在效率上。C++11 的移动赋值让 `a = a + b` 在独立运算符返回后可以移动，缩小了差距，但没有消除中间对象。函数参数按值接收再调用 `+=` 的写法（`T operator+(T lhs, const T& rhs) { return lhs += rhs; }`）还有一个好处：左值复制、纯右值直接初始化，编译器可以自己选最合适的构造方式。

C++20 之后，调用侧还有一个习惯值得保留：范围 `for`、算法和迭代器都大量使用前置 `++`。自己写循环时把 `it++` 改成 `++it`，对内置指针没有区别，对用户定义迭代器则少一次旧值构造。

## 16.3 不要重载 &&、|| 和逗号

`&&` 和 `||` 的价值不在“与”和“或”，而在短路：左边已经能决定结果时，右边根本不会被求值。`if (ptr && ptr->valid())` 之所以安全，是因为 `ptr` 为空时 `ptr->valid()` 不会执行。重载这两个运算符会把表达式变成函数调用，函数调用的规则是“所有实参先求值，再进入函数体”，短路随之消失。下面的程序把内置版本和重载版本放在一起，让求值过程自己说话：


内置 `&&` 只求值了左边，右边的 `check("右", true)` 没有出现；重载版本先构造两个 `Guard`，再调用 `operator&&`，右边无论左边真假都已经被求值。`||` 同理。逗号的情况和标准版本有关：内置逗号保证先左后右；重载之后，C++17 之前两个操作数的求值顺序没有规定，C++17 起（P0145）用运算符写法调用的重载 `&&`、`||` 和逗号也按内置运算符的顺序先算左边、再算右边。但这只恢复了顺序，没有恢复短路：两边总是都会求值。输出里 `operator,` 那一行出现在两个 `tag` 调用之后，正说明两个操作数都已经求值完，函数体才开始执行。

MEC-07 的标题就是结论：“永远不要重载 `&&`、`||` 或逗号。”CCS-30 把理由写得更完整：这三个运算符的特殊语义无法用重载复现，而程序员对它们的预期又非常牢固。CCS-30 举的例子很典型：一个智能指针重载了 `&&`，`e && e->Manager()` 在 `e` 为空时仍然调用 `Manager()`，看起来完全正常的代码于是解引用了空指针。下面的反例就是这件事的最小版本：

UBSan 报的是“在空指针上访问成员”，而不是“`&&` 写错了”；错误信息离真正的原因很远，这正是这类重载危险的地方。原书写作时，重载逗号还有一个顺序问题：`f(i++), g(i++)` 重载后哪个函数拿到 0、哪个拿到 1 没有规定。C++17 修掉了这一半，重载的逗号、`&&`、`||` 都保证先左后右；但短路是函数调用给不了的，`e && e->Manager()` 里右边照样会被求值，所以 MEC-07 和 CCS-30 的结论在 C++20 下仍然成立，只是理由从“顺序和短路都没了”缩成了“短路没了，读者的预期也被打破”。

有没有正当理由重载它们？表达式模板（expression template）是一个例外：矩阵、线性代数或 DSL 库会有意捕获整套运算符，把 `a + b * c` 记成一棵表达式树，等到赋值时再求值。这种设计需要接管运算符的语法，也会自己定义求值策略，和“给普通类型随手加一个 `operator&&`”不是一回事。CCS-30 明确把表达式模板列为受控的例外，同时提醒：例外之所以成立，是因为库作者清楚自己在改写语义，并且整套约定前后一致。

今天还有两个变化让重载逗号更没有理由。C++11 的 `initializer_list` 让“一次加入多个值”可以写成 `container += {"a", "b"}`，当年重载逗号的主要动机消失了；C++23 引入多维下标，并弃用下标表达式里的逗号（`a[i, j]` 在 C++20 里是逗号表达式，在 C++23 里可以是多个下标参数），标准本身在收紧逗号的用法。最后别忘了有些运算符根本不能重载：`.`、`.*`、`::`、`?:`、`sizeof`、`typeid` 和四种具名转换。能重载不等于应该重载；如果语义无法与内置版本保持一致，就写一个有名字的函数。

通用签名 `same(const Text&, const Text&)` 仍然会构造一个临时 `Text`；补上 `(const Text&, const char*)` 和 `(const char*, const Text&)` 之后，两个方向都不再构造 `Text`。三个版本通常共用一个后端实现，重复的只是签名，不是逻辑。只补一边不够：`"hello" == text` 会走另一条转换路径，优化只做了一半。MEC-21 把这件事推广到所有“混合类型调用”：如果常见组合会为转换付出临时对象成本，就直接为这些组合提供重载；重载消除的是转换成本，不改变运算的含义。MEC-21 也提醒，重载数量会随类型组合膨胀，先确认这是热点再动手，否则维护成本大于收益。

C++17 的 `std::string_view` 给这类问题提供了另一种解法：把只读字符串参数统一成 `string_view`，一个签名就能接受字符串字面量、`std::string` 和字符数组，而且不复制字符。它和“精确匹配重载”不冲突，但要想清楚所有权：`string_view` 不拥有数据，不能返回指向临时字符串的 view。另一个现代工具是完美转发模板，一个模板能吃掉所有实参类型，但它会改变重载决议、拖慢编译，错误信息也更难读；C++20 的 concepts 可以把约束写清楚，却不会让重载集合自动变简单。

省临时对象只是手段，语义才是底线。CCS-26 要求重载运算符守住内置运算符的自然语义：用 `operator+` 做减法谁都看得出是错的，难的是 `Tensor::operator*` 到底是点积还是叉积、`operator+=` 是逐元素加还是改变尺寸。值类型可以遵循“拿不准就照 `int` 做”的原则：`a @ b` 可用时，问一问 `b @ a` 是否也可用、`a @= b` 是否存在、`+` 和 `-`、`*` 和 `/` 这类互逆运算是否配对。运算符在读者心里是成套出现的，缺一个就会让人猜；语义有疑问时，具名函数比运算符更诚实。正则表达式引擎、解析器生成器这类领域库会有意定义与 C++ 相差很远的运算符约定，那是受控的领域语言，不是给普通值类型随手加运算符的理由。

C++20 之后这条规则还多了两层约束。`std::ranges::less` 是另一个比较器类型，ranges 算法默认用它；偷偷特化 `std::less` 不会改变 `ranges::less` 的行为，只会让两套接口不一致。`std::strict_weak_order`、`std::totally_ordered` 这些 concept 要求比较器与 `operator<`、`operator==` 的语义自洽；一个和 `operator<` 不一致的 `less` 会同时破坏有序容器的前提和这些约束。需要另一种次序时，具名比较器仍然是最简单、最可读的答案。

## 16.5 最长匹配和代理类把运算符推到语言暗角

C++ 的词法分析采用最长匹配（maximal munch）：从当前位置出发，尽可能取最长的 token。`>>` 因此永远是一个右移/流提取 token，而不是两个 `>`；`++++++a` 会被切成 `++ ++ ++ a`，只要 `operator++` 返回左值引用，这串加号就能编译。下面的 `Tally` 同时提供前置 `++` 和一元 `+`，把偶数个和奇数个加号都接住：

最长匹配还有一个实际影响。C++11 之前，嵌套模板的右尖括号必须写成 `X<Y> >`，因为 `>>` 会被当成一个 token；C++11 起标准专门允许 `>>` 在模板参数列表的末尾闭合两个模板，`std::vector<std::vector<int>>` 可以直接写。C++17 移除了 trigraph，EXS-33 里 `???` 靠 `??-` 被替换成 `~` 的例子在标准 C++17 之后不再成立，只有仍支持 trigraph 扩展的编译器才接受。C++20 新增的 `<=>` 也是一个三字符 token，最长匹配规则没有变：`a <=> b` 不会被切成 `a <= > b`。

删除 20 和 40 的循环用的是 `values.erase(it++)`：`it++` 先把 `it` 移到下一个元素，再把旧迭代器交给 `erase`，所以 `erase` 失效的是旧位置，`it` 仍然有效。如果写成 `values.erase(it); ++it;`，`erase` 之后 `it` 已经失效，再递增它是未定义行为。MXC-09 用 `list::erase(i++)` 专门讲了这个差别，并给出一般性的警告：不要因为“函数调用里不该有副作用”的规范，就把这个唯一合法的惯用法也改掉。C++11 起 `erase` 返回下一个迭代器，`it = values.erase(it)` 是另一种清楚的写法；`std::next(it)` 也能表达“先取下一个”，但会多一次迭代器复制。三者语义相同，选一个读得懂的即可。

异常让差别更明显。`observe(a++)` 里 `a` 先变成 2，`f` 看到的是旧值 1，然后抛异常；捕获之后 `a` 仍然是 2。`observe(b); b++;` 里 `f` 抛异常，`b++` 根本没有执行，所以 `b` 还是 1。MXC-09 还提醒：如果 `f` 能通过别的途径观察到 `a` 的状态，即使不抛异常，两种写法的可观察行为也可能不同。宏会把这个问题放大：宏实参可能被求值多次，顺序也不可控，所以不要把带副作用的表达式塞进宏。

本机 clang 21 先算左边，所以 `a=1, b=2`；本机 GCC 15 先算右边，同样的源码输出是 `a=2, b=1`。这不是语言保证，换编译器、换优化选项或换调用点都可能改变结果。把它改成两条具名变量的语句，顺序由语句边界固定，读代码的人也不用猜。CCS-31 说这就是唯一的解法：先把实参算进有名字的局部变量，再调用函数。顺带的好处是调试时能看清每一步的值，减少全局状态和共享状态也能减少这类纠缠。

C++17 细化了求值顺序，但没有把函数实参改成从左到右。它规定函数调用的后缀表达式先于各实参求值，实参之间是“不确定顺序”（indeterminately sequenced）而不是无序：`f(i++, i++)` 从“未定义行为”降级为“结果未指定”，两个自增不会交错，但哪个实参拿到哪个值仍然不可依赖。clang 21 仍会对这个写法给出 `-Wunsequenced` 警告，GCC 15 给 `-Wsequence-point`；标准定义了它，不代表应该写它。同一轮规则（P0145）还固定了 `a = b`（先算右边）、下标、成员访问和 `<<`/`>>` 的次序，而且这些次序对用运算符写法调用的重载运算符同样适用：`std::cout << f() << g()` 从 C++17 起保证先调用 `f()` 再调用 `g()`，这个例子正是当年提案的动机之一。C++17 之前它的顺序没有规定。C++11 的花括号初始化列表按书写顺序求值，需要固定顺序时也可以借用这个特性，但不要为了顺序而滥用初始化列表。

今天的建议可以压成两句话：带副作用的表达式不要挤进同一次函数调用的多个实参；确实需要“先用旧值、再让对象前进”时，`it++` 作为实参是少数值得保留的惯用法，其余情况先写具名变量。

`&buffer` 的类型是 `int*`，不是 `Buffer*`；`std::addressof(buffer)` 才是对象自己的地址。TIC-19 提醒：在 `operator&` 内部不能对 `*this` 再取地址（`&*this` 会递归调用自己），要直接返回 `this`；C++11 起标准库提供了 `std::addressof`，泛型代码和容器应该用它，而不是假设 `&x` 就是地址。`std::addressof` 在 C++17 起是 `constexpr`，在常量表达式里也能用。重载一元 `&` 还会影响所有“看起来只是取地址”的代码，除非有非常强的理由（例如代理/句柄必须隐藏真实地址），否则不要重载。如果确实要重载，至少让 `operator&` 和 `std::addressof` 返回同一个真实地址，并在文档里写清楚。

## 回头看

这一章的规则看起来分散，实际上都在回答同一个问题：怎样让 `a + b`、`++i`、`it->member()`、`m[i, j]` 这些写法对自定义类型也成立，同时不欠下读者看不见的债。运算符是接口的一部分，成员与非成员的选择决定了哪一侧能隐式转换；复合赋值与独立运算符的分工决定了语义有几份、临时对象有几个；前后置 `++` 的返回类型决定了调用方能不能链式使用、会不会多复制一次；`&&`、`||` 和逗号则提醒我们，有些运算符的特殊语义不是“实现得不够好”，而是重载机制本身给不了。比较器、求值顺序和 `&`/`->`/`[]` 的边界，也都是同一件事的不同侧面：让自定义类型在常见写法下可预测，在边界写法下不意外。

C++20 以后，语言替我们兜住了一部分。`<=>` 把六个比较运算符收成一条声明，`std::addressof` 让泛型代码绕过被劫持的 `&`，C++23 的多参数 `operator[]` 让多维容器不必再写两层下标。但算术运算符的语义、`op` 与 `op=` 的一致性、短路语义、实参求值顺序、移位量检查，仍然要人来设计或避免；编译器能查签名不匹配，UBSan 能查越界移位，却查不出“这个 `operator*` 到底是点积还是叉积”。所以今天的做法仍然是：能复用标准库就复用，需要自定义时守住内置语义，拿不准就写具名函数，把不能重载或不该重载的运算符留给语言。
