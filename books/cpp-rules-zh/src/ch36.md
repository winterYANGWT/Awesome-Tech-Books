# 第 36 章 质量工具链：警告、sanitizer、测试与 CI

仓库里有一个算运费的函数，三种运输方式各返回一个数，看起来没有问题。它能在开发机上编译、运行，打印出的总价也像个合理的数字。可是打开 `-Wall -Wextra` 之后，编译器对这一个文件报了五条警告：枚举漏了一个值、函数可能不返回值、参数没用、局部变量没用、有符号数和无符号数比较。每一条单看都不致命，合在一起说明这段代码从来没有被认真检查过。更糟的是，如果构建日志里长期躺着几十条这样的消息，真正危险的那一条也会被一起略过。

这一章讲的是怎么让机器替人守住这些底线：把警告当代码缺陷处理，用一条命令完成可重复的构建，让评审和测试在每次提交时自动跑起来。工具不能替你设计接口，也不能替你判断所有权和异常安全；它们能做的是把“本来可以更早发现”的错误提前到编译或测试阶段。先从不花钱的那一道防线开始。

## 36.1 让编译器和工具替你挑错

把警告级别开到最高，是成本最低的一次代码审查。下面这个文件没有被任何测试覆盖，只靠编译器就暴露了五个问题：


clang 的诊断：

```text

```

这五条警告各自指向不同的东西。`-Wswitch` 说 `carrier_name` 没有处理 `Drone`，将来新增一种运输方式时，这个函数会悄悄落到 `switch` 外面；`-Wreturn-type` 说函数可能走到末尾还没有返回值，这已经是未定义行为；`-Wunused-parameter` 和 `-Wunused-variable` 说明代码里有没被使用的意图，可能是一个漏掉的判断，也可能只是过期的残留；`-Wsign-compare` 则把 `int` 和 `size_type` 的隐式转换摆到明面上。它们都不是“编译器太挑剔”，而是代码没有把意图说清楚。

Sutter 与 Alexandrescu 在 CCS-01 里把做法说得很直接：用编译器支持的最高警告级别，要求每次构建零警告；消除警告的顺序是先理解它，再改写代码，让人和编译器都更清楚这段代码要做什么，而不是降低警告级别或者加一个强制转换把它压住。Meyers 在 EC-53 里从另一个角度补了一句：警告是编译器相关的，换一个编译器可能一条都不报，所以不能把“编译器的警告”当成安全检查的全部。他举的例子是派生类的 `f()` 漏写 `const`：一个编译器提示“隐藏了基类的虚函数”，另一个编译器可能什么都不说，而程序的行为已经错了。CCS-01 和 EC-53 合起来是同一个流程的两半：先把本地能发现的都发现，再承认本地能发现的东西有边界。

漏写 `const` 这个错误在 C++11 之后有了更可靠的写法。基类的 `send` 是 `const` 成员函数，派生类写成非 `const` 时，两个函数不是覆盖关系，派生类的名字会把基类的名字藏起来：

```cpp
{{#include code/ch36/36_1_hidden_virtual.cpp}}
```

clang 的诊断：

```text
{{#include code/ch36/36_1_hidden_virtual.out}}
```

这里 clang 21 的措辞是“标记了 `override` 的非虚成员函数隐藏了虚函数”，GCC 15 则报“标记了 `override` 但没有覆盖”，并另给一条 `-Woverloaded-virtual` 警告。两个编译器的措辞不同，结论一致：`override` 让签名不匹配从运行期的“调错了函数”变成编译错误。这是 C++11 给 CCS-01 加的一道保险：如果只写 `virtual void send(int);` 而不写 `override`，这段代码能编译，可能只得到一条警告，甚至一条都没有；写上 `override` 之后，漏 `const`、参数类型变了、基类函数被删掉，都会在编译时被拦住。`final` 也是同一类工具，它把“不要再覆盖”写进类型系统。

`[[maybe_unused]]` 用于“签名由接口决定、实现里确实用不到”的参数，比删掉参数名更能表达意图；删掉名字也是合法写法，但读代码的人要自己推断为什么这个参数没有名字。`[[nodiscard]]` 则相反，它让“返回值必须被使用”成为类型的一部分，丢掉返回值时编译器会警告。C++20 的 `consteval` 和 concepts 把这个思路继续前移：能在编译期判定的条件就不该留到运行期。这些属性都不是万能的，`[[nodiscard]]` 只能保护返回值，不能保护输出参数；`override` 只能检查覆盖，不能检查基类接口本身设计得对不对。

工程上通常把 `-Wall -Wextra -Wpedantic -Werror` 写进构建脚本，MSVC 对应 `/W4 /WX`。`-Werror` 的作用不是“让警告更严重”，而是让新出现的警告无法混进已有的噪声里：一旦基线是零，任何一条新警告都会立即让构建失败。它也会带来麻烦：升级编译器后，新版本可能对同一段代码给出新警告，整个项目突然构建不过。比较稳妥的做法是先在 CI 里用不带 `-Werror` 的构建收集一轮新警告，确认都是代码问题后再改代码或调整选项；不要为了升级工具链而把 `-Werror` 永久关掉。对于无法修改的第三方头文件，可以写一个包装头，只在包含它的那几行用 `#pragma GCC diagnostic push/pop` 或 clang 的对应 pragma 局部关闭特定警告，并在注释里写清楚原因和退出条件。这比在项目级别关掉整类警告好得多，因为后者会连自己代码里的同类问题一起放过。

警告只能看见编译器“愿意看”的东西。未初始化的读取、越界访问、数据竞争、跨翻译单元的所有权错误，很多在编译时无法判定；警告也不理解你的业务不变式。下一节先解决“每次都用一个命令、在干净环境里跑同样的检查”，再往工具链里加 sanitizer 和测试。

## 36.2 一键构建、版本控制与 CI 是同一件事

上一节的警告是在一台已经配好环境的机器上看到的。换一台机器，如果没人记得该加哪些编译选项、该先跑哪个脚本、该把哪个目录传给测试程序，那么“零警告”只是这一台机器的偶然状态。Sutter 与 Alexandrescu 在 CCS-02 里要求项目提供“一个动作”的构建：不需要人工干预，能从源码可重复地产出交付物；他们把增量构建和全量构建并列，还给出一个很实用的判据——连续做两次增量构建，第二次不应该写出任何输出文件，否则多半存在依赖环，或者构建系统在做无谓的重复工作。CCS-03 接着把这件事放进版本控制：代码要频繁提交，提交前相关测试要通过，仓库里的代码必须始终能构建。

下面这个小项目把配置、编译和测试收进一个 `ci.sh`。`CMakeLists.txt` 只做三件事：声明一个库、一个测试程序、一条测试：

```cmake

```

库的接口和实现分开，测试只依赖公开头文件：

```cpp

```

```cpp

```

`ci.sh` 就是那个“一个动作”。它把构建目录作为参数，CI 服务器每次从干净的工作区调用它，开发者在本地也可以调用同一个脚本：

```bash

```

脚本先跑一次干净的配置、构建和 `ctest`，再检查第二次增量构建有没有重写目标文件，最后改一个源文件，确认只有受影响的翻译单元被重编：

```text
{{#include code/ch36/36_2_build/output.out}}
```

输出里 `[ 50%] Built target freight` 这样的行是构建系统的进度信息；真正要守住的是后三行：第二次构建没有重写任何 `.o`，改动 `freight.cpp` 之后只有一个 `.o` 被重写，测试程序最后打印 `all 4 checks passed`。如果第二次构建仍然重写了目标文件，说明依赖关系有问题，或者构建脚本每次都在生成新的临时文件；这类问题在项目变大后会变成“改一行等十分钟”。全量构建则应该能从空目录开始，用同样的命令得到同样的结果——CI 从干净目录开始，等于每次全量，本地开发才享受增量。

构建系统之上还有几层工程选择。CMake Presets 把编译器、构建类型、生成器和选项组合写进 `CMakePresets.json`，避免每个人在命令行里拼不同的参数；Ninja 比 Make 更适合大项目，因为它把依赖图一次性读进来；ccache 缓存编译结果，切换分支后重复编译同样的翻译单元会快很多。C++20 modules 给构建系统增加了新的输入：编译器要先扫描 `import`、算出模块依赖、生成 BMI，再编译导入方。CMake 从 3.28 起加入了对模块依赖扫描的支持，不同生成器和编译器的组合成熟度不一样，具体配置需核实；第 34 章讲过 BMI 是编译器私有的中间产物，它和 `.o`、可执行文件一样属于生成物，不应该提交到仓库。第三方依赖用 vcpkg 或 Conan 声明版本并锁定，不要把预编译库直接丢进仓库；GitHub Actions、GitLab CI 这些平台只是执行器，真正要维护的仍是仓库里那条 `ci.sh`。

版本控制在这里不是“备份代码”的工具，而是让上面那条命令有意义的前提。只有所有源码、构建脚本、测试和依赖声明都进了仓库，干净工作区里的构建才可重复；只有提交是小步的，`git bisect` 才能把“哪次改动引入了缺陷”缩小到几个文件；只有每次提交都跑过测试，“仓库始终能构建”才不是一句口号。CI 做的事就是把 `ci.sh` 在一个没有本地缓存、没有手工改过的环境里再跑一遍：拉取代码、配置、构建、测试，失败就阻止合并。CI 不替代本地测试，它只是保证“在别人机器上也能通过”这件事每次都被检查。提交前跑测试、合并前跑 CI、构建产物不进仓库，这三条合起来才是 CCS-03 说的“不破坏构建”。

一键构建也有它的边界：它保证的是“同样的输入得到同样的产物”，不保证产物是对的。测试写得少，CI 只会稳定地告诉你“编译通过了”；测试依赖外部网络或当前时间，CI 会时好时坏。下一节回到代码本身：在自动检查之前，代码得先能被同事读懂、接手。

## 36.3 评审和可读性决定代码能不能被接手

代码评审最常挑出的是“这里少了一个判断”，但评审真正省时间的地方在更前面：一段代码如果只有作者能读懂，评审者只能猜它的意图，缺陷和设计问题都会从猜错的缝隙里漏过去。Sutter 与 Alexandrescu 在 CCS-04 里把评审当成投资：更多双眼睛能发现缺陷、不可移植的代码和扩展性问题，也能让新人熟悉代码库、让老成员重新审视自己的习惯；评审要成为开发流程的常规环节，并留下书面记录。Meyers 在 ESTL-47 里从写作者这一侧提出同样的要求：不要生产“只写代码”（write-only code），也就是写的时候顺着思路很顺、读的时候却要逐层反解的东西。

`keep_after_checkpoint_dense` 和 `keep_after_checkpoint` 的结果完全一样，差别只在阅读路径。拆开后的版本把“最后一个检查点”命名成一个变量，把“从它后面开始”写成一行注释，再用一条 erase-remove 完成删除；算法仍然是标准算法，没有退回手写循环。ESTL-47 的原例用了 `bind2nd` 和 `less<int>`，这两个绑定器在 C++17 从标准中删除；本机 libstdc++ 15 在 C++20 模式下仍把它们作为弃用扩展提供（clang 21 会报 `-Wdeprecated-declarations`），libc++ 21 则直接报“没有 `bind2nd`”，所以原例已经不能当作可移植写法。今天的写法用 lambda 取代绑定器，但“把嵌套调用拆成有名字的中间步骤”这条建议没有过时。C++20 的 ranges 管道可以写得更紧凑，风险反而更大：一个由 `views::filter`、`views::transform`、`views::reverse` 串起来的表达式，读者同样要在脑子里反解求值顺序和 view 的生命周期。如果团队里不是每个人都熟悉 ranges，拆成几个具名变量比炫耀管道更划算。

同一个文件里的 `bonus_points_dense` 展示了 CCS-20 说的另一件事：函数长、嵌套深，通常不是因为它必须这么长，而是因为作者没有给中间步骤起名字。多层 `if`/`for` 叠在一起，读者要维护一个“括号栈”，连右括号属于哪一层都要回头找。拆成 `contributes_bonus`、`points_per_unit`、`scored_units` 之后，主循环只剩一个 guard clause 和一行累加，每一层都能单独测试。CCS-20 给的降嵌套手法很具体：用 `&&` 合并连续条件，用析构函数和 RAII 代替 `try` 块做清理，用标准算法代替手写循环，用多态代替按类型标签的 `switch`。C++11 的 lambda 让“就地定义一个小函数”变得便宜，但一个四十行的 lambda 只是把长函数换了个位置；C++17 的 `if constexpr` 和结构化绑定能压平模板与解包代码，C++20 的 ranges 能让循环体更短，它们都不会自动阻止你把逻辑堆在一个函数里。例外也要承认：如果每种拆分都要传一长串局部变量，拆完反而更难读，可以保持原样；但如果几个候选函数需要相同的参数，那通常说明它们应该成为某个新类的成员。

可读性还有一条很硬的底线：头文件必须自足。C++ 标准从来没有规定一个标准头文件必须包含哪些其他头文件，ESTL-48 当年在五个实现上做过实验，发现 `<vector>` 是否包含 `<string>`、`<iostream>` 是否包含 `<iterator>` 因实现而异；能编译不等于可移植。下面这个头文件用到了 `std::string`、`std::vector`、`std::size_t` 和 `std::move`，却一个头文件都没包含：

```cpp

```

```cpp

```

```bash

```

```text

```

`audit.hpp` 之所以在某个 `.cpp` 里可能编译通过，只是因为那个 `.cpp` 先包含了 `<string>` 和 `<vector>`；换一个包含顺序、换一个标准库实现，错误就冒出来了。ESTL-48 的规则因此不是“多写几个 `#include`”，而是“谁使用谁负责”：头文件包含它声明所需的一切，使用者只包含自己直接使用的组件。这条规则也让编译防火墙和模块化改造容易得多：[第 33 章](ch33.md)讲的前置声明和 Pimpl 都要求头文件不偷偷依赖别的完整类型；[第 34 章](ch34.md)的 `import std;` 目前仍不是所有工具链都能用的基线，头文件自足仍是可移植的默认做法。C++20 起标准库头文件之间的包含关系仍然没有保证，C++23 的 `import std;` 改变的是写法，不是这条责任。

评审时可以把这几件事做成检查表：这个函数能不能用一句话说清职责，最深层嵌套在做什么，名字有没有暴露意图，头文件能不能单独编译，新增的依赖有没有写进构建脚本。机械的部分交给工具：clang-format 统一格式，clang-tidy 的 `readability-*` 和 `bugprone-*` 检查能接管一部分命名、容器用法和明显错误，CI 保证这些检查每次都被执行。人只需要看工具看不见的东西：接口契约、所有权、异常安全和并发。

## 36.4 读懂模板报错、用断言和测试

模板报错之所以吓人，是因为编译器把“你写错了一个类型”翻译成了“两个内部类型不能互相转换”。下面这段代码想在 `const` 成员函数里用 `iterator` 接收 `find` 的返回值：

```cpp
{{#include code/ch36/36_4_template_error.cpp}}
```

clang 的诊断：

```text
{{#include code/ch36/36_4_template_error.out}}
```

第一条错误已经说了关键：`const_iterator` 不能转成 `std::map<std::string, std::string>::iterator`。后面的 `_Rb_tree_const_iterator`、`std::pair<const std::basic_string<char, ...>, ...>` 是 libstdc++ 的实现细节，`basic_string<char, char_traits<char>, allocator<char>>` 就是 `string`。Meyers 在 ESTL-49 里建议把这类消息里的冗长类型换回自己写的 `typedef`，或者干脆用一个短名字；换完以后，剩下的就是“在 `const` 成员函数里，`entries_` 是 const map，`find` 返回 `const_iterator`”这一句。原因不在模板，在 `const`：成员函数承诺不修改对象，就不能给出一个可以修改元素的迭代器。修法不是加 `const_cast`，而是让接收方的类型正确，或者重新考虑这个函数该不该是 `const`。

C++11 的 `auto` 把这类错误消掉了一大半：写 `auto it = entries_.find(nickname);`，编译器自然给出 `const_iterator`，不需要手写类型，也就不会写错。把 map 的类型收进 `using NicknameMap = ...` 之后，诊断里即使还出现模板名，也能一眼认出是自己的容器：

ASan（AddressSanitizer）在分配的内存周围放红区，用影子内存记录哪一块可访问；越界访问一发生就报出地址、大小和调用栈，而不是等到程序在别处崩溃。这里用 `data()` 指针访问，是为了绕开 `operator[]` 的检查：本机的 libstdc++ 15 在不开优化时默认定义 `_GLIBCXX_ASSERTIONS`（GCC 15 起的行为），`quantities[3]` 会先触发标准库自己的断言；加上 `-O2` 这层检查就自动消失了，越界访问不再报错（本机实测）。所以测试构建要显式写 `-D_GLIBCXX_ASSERTIONS` 或 sanitizer 选项，不能指望默认值。这正是 CCS-83 说的“带检查的 STL”：它能抓住越界、失效迭代器和非法区间，但对 C 指针、C 库返回的缓冲区就无能为力。ASan 和 checked STL 是两层网，不能互相替代。

TSan 记录每个内存访问和同步事件，发现两个线程对同一变量的访问没有 happens-before 关系时报出竞争。它和 ASan 不能同时使用，因为两者都要接管内存访问；实际项目一般分成两个 CI 任务，一个跑 `-fsanitize=address,undefined`，一个跑 `-fsanitize=thread`。MSan（MemorySanitizer，`-fsanitize=memory`）检查未初始化读取，要求整个程序（包括 C++ 标准库）都用 MSan 构建，配置成本最高，标准库没有插桩时报告不可信。所有 sanitizer 都会让程序变慢、占用更多内存，它们适合在测试和 CI 里常开，不适合作为发布构建。

`clang-tidy sample.cpp --checks='-*,bugprone-*,performance-*,readability-*'` 这种写法先用 `-*` 关掉默认集合，再打开关心的类别；项目里通常把配置写进 `.clang-tidy`，让本地和 CI 用同一套检查。`--warnings-as-errors=*` 可以让新发现阻止合并，但在第一次接入旧项目时，最好先只统计数量、分批修，否则一次打开几百条警告，团队很快就会学会忽略它。GCC 的 `-fanalyzer` 做过程间路径分析，能发现一些泄漏和空指针解引用；cppcheck 是独立工具，规则集与 clang-tidy 不同；Clang 的静态分析器可以用 `scan-build` 或 `clang --analyze` 调用。它们的共同点是会产生误报，接入时要有人负责判断“这条是真问题还是工具不理解代码”，不能把误报当成噪声关掉整类检查。

测试框架解决的是“把测试组织起来、失败时给出可读信息”。本书示例用 CTest 和返回码已经够用；实际项目常用 GoogleTest、Catch2 或 doctest，它们提供断言宏、测试夹具、参数化测试和测试发现。模糊测试（fuzzing）则把输入交给程序自动变异：libFuzzer 随 Clang 提供，写一个 `LLVMFuzzerTestOneInput` 入口，用 `-fsanitize=fuzzer,address` 编译，就能在覆盖率引导下持续生成输入；AFL++ 是另一套需要单独安装的工具。36.4 的差分测试适合验证一个函数的语义，模糊测试适合验证“任何输入都不崩”，两者都不能证明程序正确，但都能在发布前把边界条件翻出来。

工具需要一条规范来决定“什么算问题”。C++ Core Guidelines 由 Stroustrup 和 Sutter 主持维护，把语言和标准库的用法按 philosophy、interfaces、functions、classes、resource management、performance、concurrency 等类别组织起来；它不是 ISO 标准，也没有强制力，价值在于团队可以挑其中一部分写成自己的规则，再用 clang-tidy 的 `cppcoreguidelines-*` 检查、CI 和评审去执行。Sutter 与 Alexandrescu 在 CCS-00 里提醒过另一面：规范只应规定影响正确性、可读性和可维护性的事，缩进、行长、花括号位置这类个人口味交给 clang-format 和项目现有风格，不要把规范写成个人偏好的清单。MEC-16 讲性能时说的是同一件事的另一个版本：不要靠直觉判断瓶颈，用剖析器测量；工具链里的每一项也应该有明确的职责，而不是“多跑一个检查总没坏处”。

流程把这些工具固定下来：提交前跑格式化和单元测试，合并请求触发编译、clang-tidy、ASan/UBSan 任务， nightly 跑 TSan 和模糊测试，发布构建也保留测试和静态检查。C++20 的 `std::source_location` 让自制的日志和断言设施能直接拿到文件名、行号和函数名，不必再写 `__FILE__`/`__LINE__` 宏；C++20 modules 则要求 CI 先编译模块接口、管理 BMI，构建缓存和增量规则都要跟着改（见[第 34 章](ch34.md)）。工具会换代，编译器警告、sanitizer 和测试的职责划分不会变：越靠近编译期越便宜，越靠近运行期越接近真实，每一层都只覆盖一部分真相。

## 回头看

这一章的五节其实在回答同一个问题：一段代码凭什么值得别人相信。警告和 `override` 让编译器在翻译阶段就否定明显错误的写法；一键构建和版本控制保证“在我机器上能跑”不是唯一的运行环境；短函数、具名步骤和自足的头文件让评审者能看懂改动会影响到哪里；断言、模板诊断和差分测试把“作者以为”变成可检查的条件；sanitizer、静态分析和 CI 再把检查固定成每次提交都要经过的流程。它们防的不是某一种具体 bug，而是“错误可以悄悄留在仓库里”这件事。

C++20 以后，有一部分检查确实由语言接管了：`override`/`final`、`[[nodiscard]]`、`[[maybe_unused]]`、`static_assert`、concepts 和 `consteval` 把越来越多的约定写进类型和编译期。但内存越界、数据竞争、失效迭代器、跨翻译单元的所有权错误，仍然要靠在运行时真正执行代码的工具；而“函数该不该这么长”“这个头文件该不该包含那个头文件”“这次评审有没有看懂接口契约”，任何编译器都不会替你判断。工具链的价值不在于工具本身，而在于它让团队对“什么算完成”有一致的、可重复的答案。
