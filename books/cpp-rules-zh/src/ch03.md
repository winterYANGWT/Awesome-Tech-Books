# 第 3 章 四种 cast、对象表示与类型双关

下面这个函数每次都能编译：

```cpp
struct Base { virtual ~Base() = default; };
struct Derived : Base { int extra = 0; };

void bump(Base* base) {
    auto* derived = static_cast<Derived*>(base);   // 没有运行期检查
    derived->extra += 1;
}
```

如果 `base` 实际指向的不是 `Derived`（可能是 `Base` 本身，也可能是同一体系里的另一个派生类），`derived` 仍然非空，`extra` 写入的位置却不在那个对象里。转换在这里没有改变任何东西，它只是让编译器不再追问“你确定吗”。同样能编译的还有把 `std::string` 按字节 `memcpy` 到另一个对象、写一个 `union` 成员再从另一个成员读出来：类型系统看上去还在，实际上已经被绕过去了。

这一章从“类型系统在哪里被撬开”讲起。先看四种具名转换各自负责什么、为什么比 C 风格转换好；再看标准对对象表示到底保证了什么，为什么不能拿内存布局当契约；最后处理三类最常见的双关：`reinterpret_cast`、继承体系里的向下转型与去 `const`，以及 `memcpy`/`union` 伪装成的变体类型。

## 3.1 少用转换，必须用时选对那一种

先看一个比例计算里的小问题。`7 / 2` 是整数除法，要得到小数结果，可以把其中一个操作数转成 `double`；反过来把 `double` 存进 `int`，也需要明确说明要截断。这些转换本身没有错，问题在于写的人常常不说明“为什么转”：

```cpp
int pages = (int)(width / scale);
```

Meyers 在 EC-27 里把转换看成对类型系统的破坏：正常情况下，程序能编译就说明没有对对象做不安全、不合理的操作，而转换让编译器放弃这层保证。他的建议不是“永远不转”，而是能不用就不用；必须用时优先四种具名形式，并把转换封在函数里，别让缺口扩散到调用方。MEC-02 把四种形式的分工讲得更细：`static_cast` 处理相关的类型（数值、有继承关系的指针和引用、`void*` 往返），但不能去掉 `const`，也不能把结构体当整数、把浮点数当指针；`const_cast` 只增删 `const`/`volatile`，用它做向下转型会被编译器拒绝；`dynamic_cast` 只用于多态类型的继承体系，指针失败得 `nullptr`，引用失败抛 `std::bad_cast`，并且不能去掉 `const`；`reinterpret_cast` 的结果几乎总是实现定义，函数指针互转尤其不可移植。Sutter 在 EXC-44 里补了一条关键区别：`dynamic_cast` 没有 C 风格的等价物，C 风格转换只是在 `const_cast`、`static_cast`、`reinterpret_cast` 之间按上下文挑一个，挑中哪个读代码的人看不出来。

`dynamic_cast` 尤其如此。连续几个 `if (auto* p = dynamic_cast<A*>(x)) ... else if ...` 通常说明基类接口太薄：派生类各自加功能，调用方只好每次转回去。EC-27 给出两条替代路线：容器直接存派生类指针（需要混合存放时用多个类型安全的容器），或者把需要的能力提升为基类的虚函数。C++17 的 `std::variant` 与 `std::visit` 提供了第三条路：当类型集合封闭时，把“当前是哪一种”变成可检查的标签，访问由编译器分派，不需要 `dynamic_cast`（3.5 节会给出完整例子）。反过来说，如果类型集合是开放的、以后还会加派生类，虚函数比类型判断更合适；如果只是想在几个固定类型之间选一个，`variant` 往往比继承体系更轻。

新标准没有改变四种转换的语义，但改变了很多“不得不转”的场景。C++11 的 `nullptr` 和 `explicit operator bool` 减少了“先转成 `void*` 再判断”的旧技巧；C++17 的 `std::variant`、`std::any` 把一部分 `void*` 加标签的写法变成类型安全的接口；C++20 的 `std::bit_cast` 接手了“按位重解释”的一类需求，`concepts` 让编译期的约束不必再靠 SFINAE 和转换技巧表达；C++23 的 `std::to_underlying` 专门处理“枚举转底层整数”，本机 Clang 21 + libstdc++ 15 在 `-std=c++23` 下已支持。反过来说，`dynamic_cast` 在性能敏感路径仍然要谨慎，RTTI 还能被 `-fno-rtti` 关掉。

工具方面，`-Wold-style-cast` 会把所有 `(T)x` 形式的 C 风格转换标出来，`-Wcast-qual` 抓 C 风格转换里去掉 `const` 的写法（`const_cast` 是显式声明，不会触发它），`-Wcast-align` 抓可能破坏对齐的指针转换（clang 21 直接报 C 风格转换；GCC 15 在 x86-64 上要加 `-Wcast-align=strict` 才报）；clang-tidy 21 有 `cppcoreguidelines-pro-type-cstyle-cast`、`cppcoreguidelines-pro-type-const-cast`、`cppcoreguidelines-pro-type-reinterpret-cast`、`cppcoreguidelines-pro-type-static-cast-downcast` 四条对应检查。它们的共同前提是转换写得足够具体，能一眼看出属于哪一类；如果一开始就写成 `(T)x`，工具只能告诉你“这里有一个转换”，说不出它实际做了什么。

## 3.2 不要假设对象在内存里长什么样

把一个结构体直接写进文件、再按同样的偏移读回来，是很多“临时持久化”代码的起点：

```cpp
struct Packet { char kind; int sequence; char payload; };
std::ofstream out("packet.bin", std::ios::binary);
out.write(reinterpret_cast<const char*>(&packet), sizeof packet);
```

这段代码能跑，是因为它默默假定了三件事：成员之间没有填充，成员的偏移在读写两端一致，对象的字节就是它的值。三件事都不在标准的保证范围内。Sutter 与 Alexandrescu 在 CCS-91 里把标题写成“依赖类型，不要偷看对象的内存表示”：类型应该自己决定怎么读写，而不是让外部代码拿 `sizeof` 和偏移去猜。

先看标准到底保证了什么。标准布局（standard layout）类型的非静态数据成员按声明顺序排列，这是 `offsetof` 有意义的前提；类里可以有对齐填充，可以有隐藏的虚表指针，基类子对象的位置也不保证。`sizeof(int)` 不保证 32 位，指针和整数不保证同宽，函数指针与 `void*` 不保证同大小；把指针转成整数再比大小，得到的顺序不保证和原指针顺序一致；自动变量在栈上的相对位置、栈的增长方向，同样不可移植。

这台 x86-64 机器上 `Packet` 占 12 字节：`kind` 在 0，`sequence` 为了 4 字节对齐放在 4，`payload` 在 8，末尾还有 3 字节填充。换一台对齐要求不同的机器，这些数字就会变，所以正文只把它们当作“本机实测”，不当作接口。`alignas(16)` 的 `Vec4` 用 `static_assert(alignof(Vec4) == 16)` 把对齐要求固定下来，这是 C++11 以后才有的表达手段；在那之前，对齐只能靠编译器扩展或平台约定。

《Thinking in C++》在 TIC-14 里补了一条更细的规则：同一个访问控制块（access block）内的非静态数据成员才保证按声明顺序排列（中间可以有填充），不同块之间的相对顺序没有保证，标准允许编译器为了私有/保护数据的特殊内存区域而重排。实际上没有哪个主流编译器这样做过，C++23 干脆把它写进了标准（P1847R4）：所有非静态数据成员都按声明顺序分配，不再看访问控制。但另一半规则没有变：标准布局（standard layout）仍然要求所有非静态数据成员的访问控制相同。`Split` 把 `public`、`private`、`public` 切开，因此不是标准布局类型，`offsetof` 对它仍然只是条件支持。下面的程序不是要得到偏移，而是让编译器把“前提不成立”指出来：

`-Winvalid-offsetof` 在 clang 和 GCC 上都会出现，但默认只是警告，程序照样能编译、照样可能给出一个“看起来对”的偏移。要稳定布局，正确做法是把数据放进一个单独的聚合或标准布局结构体，让类持有它，再用 `std::is_standard_layout` 把这个前提写成 `static_assert`。

`char` 是另一个常被当成“就是一个字节”的类型。《Thinking in C++》在 TIC-06 里提醒过：plain `char` 的符号性由实现决定，可能是 `signed char`，也可能是 `unsigned char`；把大于 127 的值塞进 `char` 再参与算术或传进可变参数，结果会随平台变化。上面的输出里 `plain char signed=1`，`(char)0x80` 变成 `-128`，而 `unsigned char` 的 `0x80` 是 `128`。存字节或二进制数据应该用 `unsigned char`，C++17 起更推荐 `std::byte`：它是独立的类型，只支持位运算和比较，不参与算术，不会像 `char` 那样悄悄变成整数。C++20 的 `char8_t` 又是另一种类型，专门表示 UTF-8 代码单元，和 `char` 不能混用。

还有一条容易被忽略：`sizeof(char)` 恒为 1，但“1 字节”不保证 8 位。上面的 `CHAR_BIT=8` 是本机结果；需要固定宽度时用 `<cstdint>` 的 `std::int8_t`/`std::uint8_t`，而且它们只在实现确实有 8 位类型时才存在。

新标准把一些布局条件变成了可查询的事实：C++11 的 `alignof`/`alignas`、`std::is_standard_layout`、`std::is_trivially_copyable`（`_v` 简写是 C++17 才有的）；C++17 的 `std::byte`；C++20 明确要求有符号整数采用二补数表示（P0907），并加入 `std::bit_cast`。CCS-91 写于 C++03，它列的“整数按二进制”在当年已经成立，“负数按二补数”却不是标准保证，只能算常见实现；C++20 起这两条都写进了语言规则。但填充、vptr、指针宽度、函数指针与对象指针的关系，仍然没有普遍保证，所以“别偷看表示”这条建议没有过时，只是判断“能不能按字节搬”的工具更好了。

工具方面，`-Wpadded` 会提示编译器为了对齐插入了填充（对每个结构体都开通常太吵，适合检查跨边界的数据结构）；`-Winvalid-offsetof` 抓非标准布局上的 `offsetof`；`static_assert(std::is_standard_layout_v<T>)` 和 `static_assert(std::is_trivially_copyable_v<T>)` 把前提写在编译期。需要序列化时，写一个显式的 `encode`/`decode`，规定字段顺序、宽度和字节序，不要直接把对象内存倒进文件。

`correct` 指向完整对象的开头，`wrong` 停在 `Base2` 子对象的位置，两者指向同一块存储的不同位置，地址不同。`Derived` 同时继承 `Base1` 和 `Base2`，`Base2` 子对象在对象里有一个非零偏移；`static_cast` 知道这层关系，会把指针调整到完整对象的开头。`c_style` 看到的 `Derived` 只有前置声明，编译器不知道它和 `Base2` 有关系，于是这行 C 风格转换退化成按位重解释，偏移没有加。程序能编译、能打印，`wrong` 却指在对象的中间；解引用它就是未定义行为。如果把 `c_style` 里的转换改成 `static_cast<Derived*>(base)`，在类型不完整时编译器会直接报错——这正是我们想要的结果。

EC-27 提醒过，一个对象可能有多个地址：多重继承、基类子对象都会让 `Base*` 和 `Derived*` 的数值不同，所以不能假设布局，更不能基于布局做指针运算。CCS-92 把 `reinterpret_cast` 称为“程序员对对象表示能做出的最强假设”：它让编译器不再检查，却不保证对齐、严格别名（strict aliasing）或对象生命周期中的任何一项。标准只保证少数可逆情形，例如指针转成足够大的整数再转回原指针；其余结果由实现定义，函数指针与对象指针互转还只是条件支持。

`reinterpret_cast` 不会替你检查地址是不是 4 的倍数。缓冲区按 4 字节对齐，`buffer + 1` 就落在 1 mod 4 的地址上，一定不是 4 对齐，于是读操作本身就是未定义行为。严格别名是另一个坑：用 `float*` 去读一个 `int` 对象的字节，即使地址对齐，也可能因为编译器假定不同类型的指针不指向同一块内存而读到旧值。编译器不会为这类错误发诊断，`-Wcast-align` 只能抓住一部分能在编译期看出对齐下降的转换。本机实测这个 `std::byte*` 到 `uint32_t*` 的转换在 clang 21 的 `-Wcast-align` 下没有警告，GCC 15 的 `-Wcast-align=strict` 才会报，所以警告只能当补充。

`std::bit_cast` 在常量表达式里也能用，编译器可以直接算出 `1.0f` 的位模式。它覆盖的是“同一块位、换一种类型看”的需求，比如浮点数和整数之间、两个布局相同的结构体之间；它不覆盖“把指针变成另一种指针”或“访问硬件寄存器”，那些仍然要靠 `reinterpret_cast`，并且要把平台假设写进注释、封在少数几个函数里。CCS-92 还建议：需要在无关指针类型之间转换时，先转 `void*` 再 `static_cast`，让“这两个类型无关”这件事在代码里显式可见。Sutter 在 EXC-44 里补了一个细节：`char`、`signed char`、`unsigned char` 是三种不同的类型，它们的指针之间必须用 `reinterpret_cast`，`static_cast` 不行。

C 风格转换（CCS-95）把这些选择全藏在一对括号里。同一种写法，可能因为包含的头文件不同、`typedef` 改了底层类型，就从 `static_cast` 变成 `reinterpret_cast`。书里的 `EmployeeID` 例子很典型：ID 原本是指针，`(Secretary*)id` 做的是有调整的转换；后来 ID 改成整数，同一行代码变成把整数按位当成指针，编译照过，运行就出事。C 风格转换还能转到私有基类，绕过访问控制，而 `static_cast` 会拒绝；它也无法用 `grep` 可靠检索。在 `Derived` 已经完整定义的地方写 `reinterpret_cast<Derived*>(base)`，clang 21 会给出 `-Wreinterpret-base-class`，提示它与 `static_cast` 行为不同；可是在 `c_style` 那样类型还不完整的地方，编译器自己也不知道两者有继承关系，这条诊断出不来，C 风格写法更是只剩 `-Wold-style-cast` 会提醒“这里有一个旧式转换”（本机实测）。GCC 15 的 `-Wold-style-cast` 甚至会在修复建议里直接写出 `reinterpret_cast<Derived*>(base)`，算是把隐藏的选择摆到了台面上。

C++23 的 `std::byteswap` 处理字节序翻转，本机 Clang 21 + libstdc++ 15 在 `-std=c++23` 下已支持；`std::start_lifetime_as` 也是 C++23 的设施，但本机 libstdc++ 15 和 libc++ 21 都还没有提供，MSVC 等其他实现的支持情况需核实。它们都只解决具体问题，不改变“先把转换意图写清楚”这条原则。

## 3.4 向下转型与去 const：两种最容易被误用的 cast

继承体系里最常见的一句“我知道它其实是派生类”，写出来就是 `static_cast<Derived*>(base)`。编译器只检查静态类型：只要 `Base` 和 `Derived` 有继承关系，转换就合法；它不检查 `base` 此刻指向的到底是 `Derived`、兄弟类，还是别的什么。猜对了什么也不会发生，猜错了就是未定义行为。CCS-93 因此建议：继承体系里的向下转型优先用 `dynamic_cast`，或者干脆重新设计，别用 `static_cast` 假定“它一定是那个派生类”。

`dynamic_cast` 要求类型是多态的（至少有一个虚函数），它查运行期类型信息：指针版失败返回 `nullptr`，引用版失败抛 `std::bad_cast`；它还能做交叉转换，沿着继承图从一个分支转到另一个分支。这些能力是 C 风格转换和 `static_cast` 都没有的。

新标准还提供了绕开向下转型的设计手段。类型集合封闭时，C++17 的 `std::variant` 加 `std::visit` 把运行期类型判断变成对标签的分派；需要存放任意类型时，`std::any` 加 `std::any_cast` 比 `void*` 安全；C++20 的 concepts 和 `if constexpr` 把一部分类型选择移到编译期。它们不适用于所有场景：开放继承体系仍然要靠虚函数，和 C API 交界处仍然可能拿到 `void*`。RTTI 也不是一定可用，`-fno-rtti` 下 clang 21 和 GCC 15 都会拒绝所有需要运行期检查的 `dynamic_cast`（只有向上转换这种编译期就能确定的不受影响），库代码不能假设调用方一定开着它。

工具方面，`-Wcast-qual` 抓 C 风格转换里去掉 `const`/`volatile` 的写法，它不会拦下显式的 `const_cast`；clang-tidy 21 的 `cppcoreguidelines-pro-type-const-cast` 和 `cppcoreguidelines-pro-type-static-cast-downcast` 分别盯住这两类写法；`-Wreinterpret-base-class`（clang）能提示显式 `reinterpret_cast` 向下转换与 `static_cast` 的差异。它们都只能提醒，判断“这个对象到底是不是 `const`、到底是不是那个派生类”仍然要由写代码的人负责。

## 3.5 memcpy 和 union 都不能做类型双关

有些对象不能按字节搬，最典型的是自己管理资源的类。下面这段代码把一个 `std::string` 的字节复制到另一个 `std::string`：

`memcpy` 只搬字节，不调用拷贝构造函数。复制完成后两个 `string` 对象的指针字段指向同一块堆内存，打印时看起来一切正常，作用域结束时两个析构函数各释放一次，ASan 报 `double-free`。如果把 `std::string` 换成 `std::shared_ptr`，问题是一样的：控制块被复制了两份，引用计数却没有增加，最后会重复释放控制块或访问已经释放的内存（本机 ASan 报 `heap-use-after-free`）。CCS-96 把 `memcpy` 复制对象比作“用复印机印钱”：它绕过了构造函数、赋值运算符和析构函数，也就绕过了对象对自己资源的全部管理。

`memcmp` 的问题更隐蔽：它比较的是字节，而对象的字节里有一部分不属于值。看这个结构体：

两个对象的 `code` 和 `value` 都相同，`memcmp` 却返回 170。原因是 `char code` 和 `int value` 之间有 3 个填充字节，示例故意把 `a` 的填充写成 `0xAA`、`b` 的填充写成 0；`memcmp` 在第一个填充字节上就分出了大小。即使不做这个人为的 `memset`，不同构造路径留下的填充内容也可能不同，标准从没保证填充会被清零。可平凡复制（trivially copyable）只说明“这块内存可以按字节搬到另一个同类型对象”，不说明“字节相同就等于值相同”；`memcmp` 需要后者，所以它对带填充的结构体从来不是值比较。它还有另一种常见误用：比较两个 `char*` 变量本身，比的是指针的字节表示，而不是字符串内容。

第二是**生存期**：缓冲区里什么时候有对象、什么时候该调用析构，全靠手写代码记着；拷贝构造和拷贝赋值如果没跟着写，编译器生成的版本会逐位复制缓冲区，两个对象于是共享同一个内部指针，析构时二次销毁。这正是三法则（Rule of Three）说的问题：自定义了析构、拷贝构造、拷贝赋值中的任何一个，通常三个都需要。第三是**脆弱**：增加一种类型要同步改标签、访问器、清理函数和缓冲区大小，漏一处就留下一个运行期炸弹。

C++11 的 unrestricted unions 允许 `union` 直接拥有带非平凡构造、析构、拷贝的成员，但代价是对应的特殊成员函数会被定义为 deleted（除非用户提供），生存期仍要手工管理：`placement new` 启动，显式调用析构结束。对齐设施在 C++11 落地为 `alignas`/`alignof`、`std::max_align_t` 和 `std::aligned_storage`（后者 C++23 起弃用，P1413R3）；C++17 的 `std::launder` 补上了“在同一块存储上重建对象后怎样取得有效指针”的规则；C++17 的 `std::destroy_at` 和 C++20 的 `std::construct_at` 让这类手工构造析构可以写进常量求值（`destroy_at` 从 C++20 起才是 `constexpr`）。C++23 的 `std::start_lifetime_as` 只适用于隐式生命周期类型（implicit-lifetime types），`std::string` 这类带非平凡析构的类仍然不行；而且本机 libstdc++ 15 和 libc++ 21 都还没有提供它，其他实现的支持情况需核实。今天写新代码，`std::variant`、`std::any`、`std::optional` 和 `std::bit_cast` 已经覆盖了绝大多数“手写标签联合”的动机，剩下的底层内存管理应该封在容器或分配器里，而不是散落在业务类型中。

工具方面，GCC 15 的 `-Wclass-memaccess` 和 clang 21 的 `-Wnontrivial-memcall` 会对明显作用于非平凡类型的 `memcpy`/`memset` 发出警告；ASan 能抓住双重释放和越界，UBSan 能抓住错位构造；`union` 非活跃成员的读只有常量求值阶段一定会被拒绝，运行期要靠代码审查和 `std::variant` 这类设施从源头避免。把 `static_assert(std::is_trivially_copyable_v<T>)` 放在真正需要字节操作的函数里，至少能让“这个类型能不能按字节搬”变成编译期问题。

## 回头看

这些规则防的是同一类事故：代码编译通过、程序跑完不崩，做的却是另一件事。四种具名转换把“为什么转”写进代码，C 风格转换把这层意图藏进括号；`dynamic_cast` 和 `static_cast` 的分工，本质上是在问“动态类型到底知不知道”；`const_cast` 的边界，问的是“对象本身是不是 `const`”；而对布局、填充、`char` 符号性和 `union` 活跃成员的假设，问的是“标准到底承诺了什么”。它们合起来只有一句话：类型系统被撬开的地方越少，程序能静默出错的地方就越少。

C++11 以后，语言和标准库替我们补上了不少兜底：`alignas`/`alignof`、`std::is_standard_layout`/`is_trivially_copyable` 把布局前提变成可查询的事实，`std::byte` 把字节和字符分开，`std::variant` 取代手写标签联合，`std::bit_cast` 取代一部分按位重解释，`std::launder`、`std::construct_at`/`destroy_at` 把对象生存期的规则写进库。工具也更有力：`-Wold-style-cast`、`-Wcast-qual`、`-Wcast-align`、`-Wreinterpret-base-class`、`-Winvalid-offsetof`，以及 ASan/UBSan 能当场抓住双重释放和错位访问。但“这个向下转型有没有必要”“这个对象是不是真的 `const`”“这个二进制格式要不要考虑字节序”仍然是设计判断，工具只能在你已经写错之后提醒。转换写得越少、越具体，这些判断就越容易做对。
